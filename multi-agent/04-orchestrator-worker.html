Orchestrator and Workers

The most common multi-agent design has a lead agent, the orchestrator, that splits a task into pieces, writes a brief for each piece, hands the pieces to worker agents and combines what comes back. Each step is a new place for the work to go wrong. Pieces get missed, briefs leave out what the worker needs, and the combined answer can drop or invent a finding. This chapter measures each step separately.

The task is a release-readiness check. It is 14:00, and a service may be released only if nothing it depends on, directly or through other services, is blocking. A service is blocking if its error rate is above 2.0% or it was deployed at or after 13:00. Eight estates were used, with 4 to 8 dependencies each, three safe to release and five not. There were five set-ups. One agent did everything. A lead wrote free-form briefs. A lead filled in a brief template. A lead only listed the services and code wrote the briefs. Finally, code did the planning and the combining while agents did only the checks. Everything ran on qwen3:14b.

  • Split a task with a lead agent, and check the split
  • Write briefs that carry the rules the worker needs
  • Dispatch workers concurrently, each with its own context
  • Combine findings in code where you can
  • Find which step of the orchestration broke

The lead agent

The lead's first job is the split. Here that meant following get_dependencies until it had every service the target relies on, and nothing else. This is where the orchestration broke most. Asked to fill in a 60-word brief template for each dependency, the lead explored the graph, then wrote one or two briefs and stopped in 7 of 8 estates. Its output was not cut off; it just stopped. Asked only to list the services, it covered every dependency in 8 of 8, but put the release target itself on the list in 6, and the target's own problems then appeared as blockers. The lead writing short free-form briefs covered every dependency in 8 of 8 and listed the target twice. A wrong split cannot be fixed by good workers.

def check_plan(target: str, planned: list[str], closure: set[str]) -> list[str]:
    """Validate the lead's split before dispatching: no target, no strangers, nothing missing."""
    plan = [s for s in dict.fromkeys(planned) if s != target]          # 6 of 8 lists included the target
    missing = closure - set(plan)
    if missing:
        raise PlanError(f"lead missed {sorted(missing)}")            # or: add them and carry on
    return [s for s in plan if s in closure]

Writing task briefs

A worker knows only its brief. The free-form briefs averaged 13 words, such as "Check if inventory has error rate above 2.0% or a deploy after 13:00 today." 13 of the 44 left the threshold out entirely: "Check if ledger is blocking by verifying error rate and deploy time." The workers mostly guessed right anyway, with 1 wrong finding in 44, because a 0.8% against 6.5% error rate is easy to call. On a closer call, a worker without the rule decides by its own standard. The template briefs carried the rule, the steps, the report format and the boundaries every time, at 60 words each. With code filling them in, workers made 1 to 2 wrong findings per 40 or so checks, about the same, and used twice the tokens of the short briefs. A brief should carry what the worker cannot know, the rules and the definitions, and nothing it can work out for itself.

def brief(service: str) -> str:
    return (f"OBJECTIVE: decide whether {service} is blocking a release.\n"
            f"RULES: blocking if error rate is above 2.0%, or a deploy at or after 13:00 today. It is now 14:00.\n"
            f"STEPS: call get_metrics({service}) and get_deploys({service}).\n"
            f"REPORT: service, blocking (true or false), reason quoting the numbers.\n"
            f"BOUNDARIES: check only {service}; do not guess values you did not read.")

Dispatching workers

Dispatch is the easy part: one coroutine per brief, gathered with a timeout, each worker with its own short context and only the two tools it needs (Primer 2). The tool waits overlap, but the model calls still queue on one GPU. Partial failure needs a decision: here every worker returned, but a real dispatcher must say what a missing finding means. For a release check it should mean "not safe to release", never "no problems found" (Primer 4).

Combining results

When the findings are typed, {service, blocking, reason}, combining them is a filter. Code can do it exactly, and a lead model adds nothing but a chance to drop or add an item. Key each finding by the piece you dispatched, not by what the worker writes back. In one estate the worker sent to media flagged it as blocking but reported it under the service name "error_rate", and the combined verdict left media out. Let a model combine only what code cannot, such as conflicting prose findings or a summary for a person.

findings = await asyncio.gather(*(worker(brief(s)) for s in plan))
blocking = sorted(s for s, f in zip(plan, findings) if f["blocking"])   # keyed by what was dispatched
verdict  = {"go": not blocking and len(findings) == len(plan), "blocking": blocking}

Where it breaks

Across the five set-ups the go/no-go decision was usually right. The exact list of blockers separated them:

  • One agent: 5 of 8 exact. In three estates it named the wrong blockers or missed some; for one target it found 1 of 5.
  • Lead, free-form briefs: 7 of 8, at 1.6 times one agent's tokens.
  • Lead, brief template: 4 of 8. It stopped writing after one or two briefs.
  • Lead lists, code briefs: 4 of 8. It listed the target as its own dependency.
  • Code plans and combines, agents check: 7 of 8, with no lead model at all.

The workers were rarely the problem, with 0 to 2 wrong findings per set-up. The orchestration was. The lesson is not "never use a lead". Give each step to whoever does it most reliably. Code does the parts that are deterministic: following a dependency graph, filling a template, filtering typed findings. Agents do the parts that need judgement. When the split really needs judgement, as in research or debugging, keep the lead and check its plan.

Use case: orchestrators in agent products

Anthropic's write-up of its research system describes a lead agent that plans, writes a brief for each subagent and then combines their results. Its lessons line up with this chapter. Early versions gave subagents vague one-line briefs, which led to duplicated work and gaps. Briefs got better with an objective, an output format, guidance on tools and clear task boundaries. LangGraph, the OpenAI Agents SDK and Google's Agent Development Kit all offer orchestrator–worker building blocks. None of them checks the split for you.

⚠️
Common mistakes
  • Trusting the lead's split without checking it: missed services, extra services, the target itself.
  • Asking a model to write many long, near-identical briefs: it wrote two and stopped.
  • Briefs without the rules: 13 of 44 free-form briefs left out the threshold.
  • Combining typed findings with a model when a filter in code is exact, or keying them by the name a worker writes back.
  • Treating a missing finding as a pass in a safety check.
  • Using a lead for a deterministic split that code can do.

Interview drill

Explain it simply: What does an orchestrator agent do, and what goes wrong?

How a strong answer sounds
It splits the task, writes a brief per piece, dispatches workers and combines their results. The split is the weak point. In a release-readiness test, a lead asked to write 60-word briefs wrote one or two and stopped in 7 of 8 cases, and a lead asked only to list dependencies included the release target itself in 6 of 8. Workers made at most 2 wrong findings in about 40 checks. I would validate the plan in code before dispatching.

Deeper: When would you not use a lead agent at all?

How a strong answer sounds
When the split and the merge are deterministic. In the same test, code that followed the dependency graph, filled a brief template, sent one worker agent per service and filtered their typed findings got the exact blockers in 7 of 8, as good as the best lead and better than one agent's 5 of 8. I keep a lead where splitting needs judgement, such as open research, and still check its plan for gaps and strays.
