Critique & Debate

A second agent can check the first. A critic reviews a generator's work and sends it back, and in a debate two agents answer the same question, read each other's reasoning and revise. Both promise the same thing: mistakes caught by someone who did not make them. Both risk the same failures. The checker may be no better at checking than the writer was at writing. Agents may agree out of politeness rather than evidence. And it all costs several times as many calls.

There were two experiments on qwen3:14b. Critique: Chapter 2's 12 functions with 103 hidden tests, written alone, with a critic that only reads the code, and with a critic that writes its own test cases from the spec and runs them in the sandbox before giving its verdict. Debate: 30 computing questions with exact answers, such as quorum sizes, error budgets and Little's law. Two agents answered each one independently, then revised twice after seeing each other's answer, and a judge separately picked between their first answers. Each question was run with three pairs of agents, 90 debates in all.

  • Build a generator–critic loop with a grounded critic
  • Run a two-agent debate and read what changed
  • Check whether agents give in to each other
  • Use a judge, and know what it cannot fix
  • Measure the lift against its cost

Generator and critic

Chapter 2 ended with a reviewer that could only read the code. It was about as likely to break working code as to fix broken code. Here the critic got a tool, run_cases. It writes test cases from the spec, with an expected value worked out from the spec rather than from the code, and the sandbox reports which pass and what the code actually returned. The results across 12 functions:

  • Writer alone: 5 functions fully right, 79 of 103 hidden tests.
  • Critic that only reads: 6 functions, 86 tests.
  • Critic that runs its tests: 7 functions, 90 tests. It approved working code 5 times, against 2 for the reading critic, and rejected working code 6 times instead of 9.

Neither critic ever approved failing code here. Grounding helped most by letting the critic say yes when the code was right, so loops ended instead of grinding on. It cost 14,400 tokens per function, against 8,700 for the reading critic and 420 for the writer alone.

A critic's own mistakes

Running tests did not make the critic right; it made it checkable. When the code under review was already correct, the critic's own cases failed 23 times out of 93, and every failure was the critic's own. Two were wrong expected values: it expected parse_duration('1h2m3s') to raise, when the spec allows it (3,723 seconds). The other 21 came from human_bytes, where it wrote expected values like 1.0 KiB without quotes, which are not Python literals. My case runner evaluated the expected value inside the same try as the call, so it reported "raised SyntaxError" as if the code had failed. The critic believed it for three rounds. That is a flaw in my tool, and a lesson: a critic's tool must say whose error it is ("your expected value is not a valid literal"), or the critic chases its own mistakes. A test is only as good as its expected value, but a test result with an input and an actual output can at least be checked, by the writer, a person or another check.

Multi-agent debate

On the 30 questions, each agent's first answer was right 81.7% of the time. After two rounds of reading each other's answer and reasoning, 90.6%. In 68 of the 90 debates both agents started right and stayed right. The lift came from the other 22. In the 11 where one agent started right and the other wrong, both ended right in 10 and stayed split in 1. In the 11 where both started wrong, debate fixed only 3. Two agents with the same mistake have nothing to correct each other with.

for _ in range(2):                                    # two rounds of revision
    answers = [revise(question, mine=answers[i], theirs=answers[1 - i]) for i in (0, 1)]
# revise() shows the other agent's answer and reasoning: "Consider their answer carefully. Keep yours or change it."

Sycophancy between agents

The worry with debate is that a right agent gives in to a wrong one because it was told to "consider their answer carefully". In these 90 debates it happened once, and not for long. On Q14 (the smallest write quorum with 5 replicas and R = 2), agent B started right with 4 and A wrong with 3. In round 1 they swapped: B took A's 3 and A took B's 4. In round 2 they swapped back. No pair that started right ended wrong, and in the other 10 split debates the wrong agent was the one that moved. On these questions, with exact answers and short reasoning that can be checked step by step, the correct argument won. That is a result about this model and these questions, not a guarantee. Questions with no way to check the reasoning, or a prompt that tells agents to defer, would give sycophancy more room. Measure it on your own tasks, because it is cheap to count: right answers that became wrong.

Judges

A cheaper alternative to debate is a judge. Collect two independent answers and ask a third agent which is right. On the 11 split cases the judge picked the right answer all 11 times, the same lift as debate on those cases, for about 480 tokens instead of a debate's 2,000. A judge cannot help when both answers are wrong; it can only choose between them. And debate's end state can look like certainty when it is not: 8 debates ended with both agents agreeing on a wrong answer, and agreement alone would have passed them. Chapter 10 measures that problem directly: agents that share a model share its mistakes.

Use case: critics and judges in practice

The research literature on multi-agent debate reports gains on reasoning and factual questions when several model instances argue, and other work shows that models can be talked out of right answers. Both effects are real; which one dominates depends on the task and the prompt. In production, the pattern that tends to last is grounded critique. Code review agents run the tests, and LLM-as-a-judge evaluations score outputs against a rubric with examples. Both get checked against human labels before anyone trusts them. Debate between copies of one model is mostly an evaluation and research tool, because of its cost.

⚠️
Common mistakes
  • A critic that can only read, on work it could test: fewer approvals and more churn.
  • Trusting a critic's tests, or a test tool that blames the code for the critic's own malformed expected values.
  • Taking agreement as correctness: 8 debates agreed on a wrong answer.
  • Debating when a judge would do: the same 11 of 11 splits at a quarter of the cost.
  • Expecting debate to fix shared mistakes: 3 of 11 when both started wrong.
  • Not counting answers that went from right to wrong, the cheapest sycophancy measure.

Interview drill

Explain it simply: How do you make a critic agent useful?

How a strong answer sounds
Ground it in something it can run or check, and make its verdict typed. In a test on 12 functions, a critic that wrote and ran its own test cases got 7 fully right against 6 for a reading-only critic and 5 for the writer alone, mostly by approving correct code instead of churning. Its own cases were wrong in 23 of 93 runs on correct code, mostly expected values that were not valid literals, so each objection must carry an input and the actual output that a person or another check can verify, and the tool must say whose error it is.

Deeper: Does multi-agent debate make answers more accurate, and what are the risks?

How a strong answer sounds
It can. On 30 questions, two agents went from 81.7% to 90.6% after two rounds; when one started right and one wrong, both ended right in 10 of 11; once, the two swapped answers mid-debate. But it rarely fixes mistakes both agents share (3 of 11), 8 debates agreed on a wrong answer, and a judge picking between the two first answers got the same 11 of 11 splits for a quarter of the tokens. I would start with a judge, measure right-to-wrong flips, and keep debate for tasks where it beats that.

🧠 Key takeaways

  • A critic that runs its own tests beat one that reads: 7 against 6 of 12 functions, with fewer rejections of working code.
  • A critic's tests can be wrong: 23 of 93 failures on correct code were its own. Objections need inputs and outputs.
  • Debate lifted answers from 81.7% to 90.6%, mainly where one agent was already right.
  • A right agent gave in once and switched back; count right-to-wrong flips on your own tasks.
  • A judge matched debate on split cases for a quarter of the cost; neither fixes shared mistakes.
