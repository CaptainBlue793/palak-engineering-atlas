Shared Memory & Blackboards

A blackboard is a shared workspace: a document, a table or a set of files that every agent can read and write. It lets agents that do not know about each other build on each other's work. It also brings back every problem of shared state in concurrent programs: lost updates, stale reads, writes that undo someone else's. Chapter 6 showed a shared store working when every agent writes its own key. This chapter measures what happens when the writes collide.

Six qwen3:14b agents each checked one service with two tools and then recorded a one-line finding on a shared board. Each tool call took 0.4 to 1.6 seconds, so the agents' reads and writes interleaved, as they would in production. There were three ways of writing. Agents could replace the whole board with JSON they had read earlier, write only their own key, or use versioned writes: read the version, write with it, and get rejected if anyone wrote in between. Each was run 8 times with different timings.

  • Use a blackboard for agents that build on each other
  • Structure shared state so writes do not collide
  • Recognise lost updates from concurrent writes
  • Know what versioned writes fix and what they do not
  • Use files and repositories as shared artefacts

Blackboards

The blackboard architecture is older than LLM agents. In early AI systems such as Hearsay-II, separate specialist programs posted partial results on a shared board, and each picked up whatever it could build on. Agent teams use the same idea when workers write findings to a shared document, a database table or a folder, and a lead or a later worker reads them. The board decouples the agents. A worker does not need to know who will use its finding, and a reader does not need to know who wrote it.

Structured shared state

How the board is structured decides what can go wrong. A board that is one document, read in full and written back in full, makes every write a replacement. A board of separate keys, one per service or per task, makes each write independent. Here that difference was everything. Writing per key kept 48 of 48 findings across the 8 trials, at the same cost as the whole-document board: about 8,000 tokens and 10 seconds per trial. Structure is the cheapest form of concurrency control.

TOOLS = {
  "whole document": ["read_board()", "write_board(board)"],                       # replace everything: 11 of 48 survived
  "per-key":        ["read_board()", "write_finding(service, finding)"],          # one key each: 48 of 48
  "versioned":      ["read_board() -> version", "write_board(board, expected_version)"],  # 42 of 48, 4x the tokens
}

Concurrent writes

With the whole-document board, all six agents read it early, before most of the others had written: in the first trial at versions 0, 1 and 2. Each then did its checks and wrote back the board it had read, plus its own line. Every write erased the ones before it. Across 8 trials only 11 of 48 findings survived, between 1 and 2 per trial. No agent did anything wrong by its own instructions. "Read the board, add your entry, write the whole board back" is exactly what they were told. The lost update is a property of the interface, and it happened in every single trial.

Stale reads

Each lost update starts with a stale read: an agent acts on a version of the board that someone else has since changed. The board counted them. In the whole-document mode, 38 of the writes were based on a read that was no longer current. Agents that read shared state and then act on it later have the same problem, without any write at all. A planner that reads the findings board, thinks for 20 seconds and then decides, is deciding on old data. Version numbers, or "read again just before acting", make the staleness visible.

Versioned writes, and their limits

Versioned writes are optimistic concurrency control, the database fix for lost updates. A write must name the version it read, and it is rejected if the board has moved on. No stale write got through: 0 in 8 trials, against 38. The agents adapted: they re-read and retried after 85 rejections in total. The board kept 42 of 48 findings, but at 4.3 times the tokens (34,500 per trial) and 3.6 times the time. It still lost 6, in two ways. In 4 cases an agent read a fresh version and then wrote back a board that left out an entry another agent had just added. The version check guarantees the read was current, not that the agent kept everything it read. In 2 cases an agent gave up after 5 rejections. A versioned whole-document board turns lost updates into retries and careless merges. Separate keys avoid the conflict altogether.

def write_board(board: dict, expected_version: int) -> str:
    if expected_version != state.version:
        return f"rejected: the board is now at version {state.version}; read it again"   # 85 times in 8 trials
    state.data, state.version = board, state.version + 1                                 # a fresh read can still drop entries
    return f"saved (version {state.version})"

Artefacts on disk

For coding and research agents the blackboard is often a folder: files that one agent writes and another reads, or a git repository. Files bring the same rules with better tools. One file per worker is like one key per worker. A shared file that several agents rewrite in full is a whole-document board. Git's merge is a versioned write that also combines concurrent edits instead of rejecting them, and it reports a conflict instead of silently dropping one side. When agents share a repository, give each its own branch or files, and let a merge step, or a person, combine them. That is the per-key design with a merge at the end.

Use case: shared state in agent frameworks

Graph frameworks such as LangGraph make the merge rule explicit. Each field of the shared state can have a reducer, for example "append to this list", so updates from parallel branches are combined instead of overwritten, which is the per-key design built into the state. Coding agents that work in parallel are usually given separate branches or worktrees and merged afterwards. Research systems in which several agents work at once tend to have each write its own result and let one step combine them. In each case the shared state is structured so that agents add to it, not rewrite it.

⚠️
Common mistakes
  • A read-modify-write board: 11 of 48 findings survived concurrent writers.
  • Telling agents to "write the whole board back" and expecting them to merge.
  • Assuming version checks prevent loss: fresh reads still dropped 4 entries.
  • Unbounded retries, or none: 85 rejections, and 2 agents that gave up.
  • Acting on a board read long ago without reading it again.
  • One shared file rewritten by several agents instead of a file each and a merge.

Interview drill

Explain it simply: What goes wrong when several agents share a document?

How a strong answer sounds
Lost updates. If each agent reads the document, adds its part and writes the whole thing back, concurrent writers erase each other. In a test with six agents, only 11 of 48 findings survived 8 trials that way, while giving each agent its own key kept all 48 at the same cost. The fix is structural: separate keys or files, or reducers that append, not better instructions.

Deeper: Would versioned writes, compare-and-swap, solve it?

How a strong answer sounds
They stop stale writes but cost a lot and still lose data. In the same test, versioned writes kept 42 of 48 after 85 rejections and retries, at about 4 times the tokens. Of the 6 lost, 4 were written successfully and later dropped by an agent that had read a fresh version but rewrote the board without them, and 2 agents gave up after five rejections. I would use per-key writes, and keep versions for the rare whole-document update.

🧠 Key takeaways

  • A blackboard lets agents build on each other without knowing about each other.
  • Whole-document writes by concurrent agents kept 11 of 48 findings; per-key writes kept 48.
  • Every lost update starts with a stale read: 38 of them in 8 trials.
  • Versioned writes kept 42 of 48 at 4.3 times the tokens; fresh reads can still drop entries.
  • Structure shared state so agents add to it, not rewrite it: keys, files, appends, merges.
