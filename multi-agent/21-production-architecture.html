Production Multi-Agent Architecture

A team of agents in production runs for minutes, calls many tools, and has side effects in other systems: tickets filed, messages sent, money moved. Processes crash, machines restart and deploys happen mid-run. If the orchestration lives only in memory, a crash throws away every finished agent's work and, worse, repeats side effects when the run starts again. Production multi-agent systems are durable workflows first and agent systems second.

This chapter measures that on Chapter 4's code-planned release check. Each worker agent checks one service and then posts its finding to an external ticket system, a side effect. The process crashes halfway through each of 8 releases, at the worst moment: just after a worker posted its finding and before that finding was saved. There were three ways to recover: restart from scratch; resume from a checkpoint store in SQLite holding each finished worker's finding; and the same with an idempotency key on every post. Workers ran one at a time on qwen3:14b, so the crash point is exact.

  • Make an orchestration durable, so a crash resumes
  • Run agents as workers behind a queue
  • Decide what state to store, and where
  • Use idempotency keys on every side effect
  • Name the failure modes of a production agent team

Durable orchestration

A durable orchestration records each step's result before moving on, so a restart can continue rather than redo. With no checkpoints, every crash meant running every worker again. Across the 8 releases, 62 worker runs were needed for 42 services, about 190,000 tokens. With a checkpoint store, a restart read the saved findings and ran only the workers still missing: 50 runs and 153,000 tokens, a fifth less. Only the one worker caught mid-save had to run again. The final verdicts were identical in every design, 6 of 8 exact, because recovery should change the cost of a crash, not the answer. Workflow engines such as Temporal make this the default. Each activity's result is recorded, and a replay skips what already happened.

done = store.done(run_id)                                     # findings saved by an earlier attempt
for service in services:
    if service in done: continue                              # resume, do not redo
    finding = await check(service)                             # the worker agent
    tickets.post(service, finding, key=f"{run_id}:{service}")      # side effect, with an idempotency key
    store.save(run_id, service, finding)                       # checkpoint after the side effect

Queues and workers

At scale, the orchestrator does not run workers itself. It puts tasks on a queue, and a pool of worker processes takes them, each running one agent for one task. The queue makes failure visible and recoverable. A worker that dies before acknowledging its task leaves the task to be redelivered, which is at-least-once delivery. Primer 3 measured that turning 200 messages into 226 deliveries, and 26 duplicate effects for a consumer that was not idempotent. The pool size is a concurrency limit. On one GPU, Chapter 16 found nothing gained past about four concurrent workers. A queue also gives you a place to see the backlog, retry with backoff, and park tasks that keep failing.

State

Three kinds of state need a home outside the process. Workflow state is which steps are done and what they returned: the checkpoint store here, keyed by run and service. Shared agent state is findings, decisions and requirements, in a store with per-key writes, not a whole document that agents rewrite (Chapter 11 kept 11 of 48 findings that way). Conversation state is each agent's messages, kept only as long as the agent runs, and summarised or dropped after. Keep each in a store built for it, and make every write keyed so that a repeat is harmless.

Retries and idempotency

Checkpoints stop wasted work. They do not stop duplicate side effects. Restarting from scratch posted 20 duplicate tickets across the 8 releases: every finding posted before the crash was posted again. Resuming from checkpoints cut that to 8, exactly one per release, from the worker that had posted and then crashed before its finding was saved. No ordering of "post, then save" or "save, then post" closes that gap; one of them always leaves a window. The idempotency key closes it. The ticket system recorded each key, run_id:service, and treated a repeat as already done: 0 duplicates. Every side effect an agent can cause should carry a key derived from the workflow step, never from the model's output, which may differ on a retry (Primer 4).

Failure modes

The production failure modes of agent teams are those of distributed systems, plus a few of their own:

  • Crashes: lost work and repeated side effects, solved by checkpoints and keys.
  • Hung calls: a model or tool that never answers, solved by timeouts at every level.
  • Retry storms against a rate-limited model API, solved by backoff with jitter.
  • Poison tasks that fail every time, solved by a retry limit and a dead-letter queue.
  • Version drift: a run that started on one prompt or model version and resumed on another, solved by pinning versions per run.
  • Agent-specific failures: a run that is technically healthy but wrong, such as a misread brief or a lossy hand-off. These need the evaluation and tracing of Chapters 18 and 22, not just infrastructure.

Use case: durable agents in production

Teams running long agent workflows increasingly put them on durable execution engines. Temporal, AWS Step Functions and similar systems record each step and resume after failures, and agent frameworks add their own persistence, as with LangGraph's checkpointers. Payment and ticketing APIs accept idempotency keys for exactly the retried-call case measured here. The architecture is familiar from any distributed system: a queue, a worker pool sized to the model backend's real capacity, stores for workflow and shared state, and keys on every external call. What is new is the agent itself, which is slow, costly and non-deterministic. That makes redoing work expensive and makes "just run it again" give a different answer.

⚠️
Common mistakes
  • Orchestration only in memory: a crash cost 62 worker runs where 50 were needed.
  • Side effects without keys: 20 duplicate tickets on restart, 8 even with checkpoints.
  • Keys from the model's output instead of the workflow step.
  • One shared document as the state store for many agents.
  • Unbounded retries with no dead-letter queue.
  • Resuming on a different prompt or model version than the run started with.

Interview drill

Explain it simply: What makes a multi-agent workflow production-ready?

How a strong answer sounds
That a crash costs a little, not everything, and never repeats an effect. Concretely: tasks on a queue, workers that run one agent each with timeouts, a checkpoint store so a restart skips finished steps, and an idempotency key on every side effect. In a test where the process crashed halfway through, restarting from scratch needed 62 worker runs and filed 20 duplicate tickets; resuming from checkpoints with keys needed 50 runs and filed none.

Deeper: Why are checkpoints not enough to prevent duplicate side effects?

How a strong answer sounds
Because there is always a gap between the side effect and the checkpoint. If the process dies after posting and before saving, the restart sees the step as unfinished and posts again; in the test that left exactly one duplicate per release. Reversing the order just moves the gap, so you can lose a post instead. The receiving system has to make the second call harmless, by recording an idempotency key derived from the run and step.
