Concurrency with asyncio

A team of agents spends most of its time waiting: on model calls, on tools, on each other. Python's asyncio lets one program wait on many things at once, which is how an orchestrator runs its workers side by side. It also decides what happens when one of them hangs, crashes or is no longer needed.

This primer covers the parts of asyncio the course uses, each measured on this machine: eight tools that take half a second, four calls to qwen3:14b, a tool that hangs, a worker that crashes, and three searches where only the first answer matters. One result shapes the rest of the course. Concurrency removed the waiting for tools, but four model calls took exactly as long at once as one after another, because the model server answers one request at a time.

  • Write coroutines and run them as tasks
  • Use gather and as_completed, and handle failures in either
  • Put timeouts on everything that can hang
  • Cancel work that is no longer needed
  • Limit concurrency with a semaphore

Coroutines and tasks

A coroutine is a function defined with async def. Calling it does nothing yet; it returns an object that runs when awaited. Inside it, await marks the places where it waits, for a network reply or a sleep, and while it waits the event loop runs something else. A task wraps a coroutine so it starts running in the background straight away. One thread, many waits in flight: that is all asyncio is.

import asyncio
from ollama import AsyncClient

client = AsyncClient()

async def ask(question: str) -> str:
    reply = await client.chat(model="qwen3:14b", messages=[{"role": "user", "content": question}])
    return reply.message.content                       # while this awaits, other coroutines run

async def main():
    task = asyncio.create_task(ask("What is p99 latency?"))   # starts now
    other = await ask("What is a canary release?")
    first = await task

asyncio.run(main())

gather and as_completed

asyncio.gather(*coroutines) runs them together and returns their results in the order given. Eight tool calls of half a second each took 4.0 s one after another and 0.5 s with gather: all eight waits overlapped. as_completed yields results in the order they finish, which suits an orchestrator that can act on each worker's result as it arrives.

Now the result that matters for agents. Four short questions to qwen3:14b took 1.48 s one after another and 1.44 s with gather. The Ollama server here answers one request at a time, so the four requests queued inside it. Run concurrently, they finished at 0.36, 0.74, 0.92 and 1.44 s: the first was as fast as ever, the last waited for all the others. Concurrency overlaps waiting. It does not create model capacity. A team of agents on one model server is faster than one agent only where the agents spend time waiting on something other than the model: tools, APIs, people. Chapter 35 of the Single Agent course measured the same ceiling under load, about 19 runs a minute however many ran at once.

Timeouts

A worker that never returns holds up everything that waits for it. asyncio.wait_for(coroutine, timeout=1.0) raises TimeoutError if the coroutine has not finished in time, and cancels it. A tool built to hang for 30 seconds was stopped at 1.00 s. Every model call, tool call and worker in a multi-agent system should have a timeout, and the orchestrator should decide what a timed-out worker means: retry, skip, or report the gap.

findings = await asyncio.gather(
    *(asyncio.wait_for(worker(brief), timeout=120) for brief in briefs),
    return_exceptions=True,                     # a failed worker becomes a value, not a crash
)
ok = [f for f in findings if not isinstance(f, Exception)]

By default gather raises the first exception it meets. With one worker that crashed after 0.2 s, plain gather raised RuntimeError: worker crashed and the other results were lost to the caller. With return_exceptions=True it returned ["result 1", RuntimeError("worker crashed"), "result 2"]: two results and one failure the orchestrator can reason about. That is the version to use for workers.

Cancellation

When several agents try the same thing and the first good answer is enough, the rest should stop. Three searches were started as tasks, taking 0.4, 3 and 6 seconds. Reading results with as_completed, taking the first and cancelling the others returned in 0.40 s with 2 tasks cancelled, instead of 6 s. Cancelling raises CancelledError inside the cancelled task at its next await, so code that holds resources should release them in a finally block. For model calls, cancelling the client's request stops waiting for it. Whether the server also stops generating depends on the server, so measure it before counting on the saved compute.

Concurrency limits

Starting everything at once can overload whatever sits behind the tools: an API's rate limit, a database's connection pool, a model server's queue. An asyncio.Semaphore(n) lets at most n tasks into a section at a time. With a limit of 3, the eight half-second tool calls took 1.5 s: three rounds of up to three. Choose the limit from the capacity of the thing being protected, not from the number of agents.

limit = asyncio.Semaphore(3)

async def limited_call(args):
    async with limit:                                  # at most 3 inside at once
        return await call_api(args)

Use case: asyncio in agent SDKs

Most Python agent libraries are built on asyncio. OpenAI's Agents SDK runs agents with an async Runner.run. LangGraph runs graph nodes and their tool calls concurrently where the graph allows, and Anthropic's and OpenAI's Python clients ship async variants alongside the synchronous ones. The patterns are the ones above: tasks for parallel workers, gather or as_completed to collect them, timeouts on every call, and limits that keep a burst of agents from overrunning an API's rate limit. Python 3.11 added asyncio.TaskGroup, which cancels the remaining tasks when one fails. That is the right default when a single failure should abort the whole group, the opposite of return_exceptions=True.

⚠️
Common mistakes
  • Expecting concurrent model calls to be faster on a server that answers one request at a time.
  • No timeout on a worker, so one hang stalls the whole team.
  • Plain gather for workers, losing every result when one fails.
  • Never cancelling losers in first-answer-wins patterns.
  • Unbounded concurrency against rate-limited APIs.
  • Blocking calls (time.sleep, synchronous clients) inside coroutines, which freeze every other task.

Interview drill

Explain it simply: How would you run five worker agents at once in Python?

How a strong answer sounds
Make each worker a coroutine, wrap each in asyncio.wait_for with a timeout, and run them with asyncio.gather(return_exceptions=True), so a crash or timeout comes back as a value instead of losing the other results. Limit concurrency with a semaphore sized to the backend. Use as_completed when the orchestrator can act on results as they arrive or only needs the first, and cancel the rest. Concurrency only overlaps waiting: four model calls to one GPU took 1.44 s at once against 1.48 s one by one.

Deeper: Your parallel agents are no faster than running them in sequence. Why?

How a strong answer sounds
Probably the model server is the bottleneck. If it serves one request at a time, concurrent requests queue inside it: in a measurement, four calls finished at 0.36, 0.74, 0.92 and 1.44 s, the same total as in sequence. Concurrency helps only with waiting elsewhere, such as tools and APIs, where eight half-second calls went from 4.0 to 0.5 s. I would measure where each agent's time goes, then add model capacity or batching if the model dominates, or accept that the team's benefit is not speed.

  • asyncio overlaps waiting: eight half-second tool calls went from 4.0 s to 0.5 s.

  • Put a timeout on every worker; a hanging tool was stopped at 1.00 s.
  • Use gather(return_exceptions=True) so one failure does not lose the other results.
  • Cancel losers in first-answer-wins patterns, and cap concurrency with a semaphore.
