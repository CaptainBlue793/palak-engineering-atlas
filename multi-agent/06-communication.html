Messages vs Shared State

Agents in a team have to tell each other things. One agent's finding is another agent's starting point. There are three common ways to share. The system can deliver direct messages from one agent to the agents that need them. All agents can talk in one shared transcript, a group chat everyone reads. Or agents can read and write a shared store of notes. Primer 3 covered the plumbing. This chapter measures what each choice does to agents: what they get right, and what they read.

The task is Primer 1's incident, split across agents with one tool each. A tracer follows the errors to the service where the failure starts. A deployer finds that service's newest deploy, and a meter finds its error rate. Both need the tracer's answer. A writer combines all three. To see how each channel scales, 0, 3 or 6 bystander agents were added, each checking an unrelated service. Every agent ends with a small typed report. The test used 6 incidents, 4 ways of sharing and 3 team sizes, all on qwen3:14b.

  • Route findings as direct messages to the agents that need them
  • See what a shared transcript does to each agent's focus
  • Use a shared store with fixed keys
  • Measure the token cost of talking as the team grows
  • Choose a channel for a given task

Direct messages

With direct messages, code decides who hears what. The tracer's report, {"root_service": "inventory"}, was appended to the deployer's and the meter's tasks and sent nowhere else. Each agent read only its own task and the one fact it needed: the deployer read about 750 tokens whether there were 0 or 6 bystanders. The team got all three facts right in 5 of 6 incidents at every team size. The one miss came from the tracer: when the failure started in checkout itself, it reported the error text, "certificate verification", as the root service, and the meter dutifully checked a service that does not exist. Direct messages need code that knows who depends on whom, which is easy in a fixed design like this one and harder when agents decide for themselves what to do next.

reports["tracer"] = agent("tracer", TASK, tools=["get_errors"])
for who in ("deployer", "meter"):                    # code knows who needs the tracer's answer
    reports[who] = agent(who, TASK + "\nMessage from the tracer agent: " + json.dumps(reports["tracer"]), tools=[TOOL[who]])

A shared transcript

A shared transcript is the simplest design to write: one group chat, and every agent reads all of it before its turn. Every tool call, every result and every report goes in. It got all three facts right in 0 of 6 incidents at every size. The replays show why. The deployer read the chat, saw the tracer's report and wrote "The checkout failure is likely originating from the inventory service…". It answered the conversation instead of doing its own job, never called its tool, and, forced into its report format, invented a 150-character version string. Restating each agent's own task after the chat helped a little: 1, 1 and 2 of 6. It also doubled the cost at 6 bystanders, because every agent read a longer chat. A transcript gives every agent everyone else's context, which is exactly what Chapter 1 found agents work better without.

A shared store

A shared store sits in between. Agents call read_notes and write_note(key, value), with a fixed set of keys: root_service, newest_deploy_version, error_rate_pct and other. The fixed keys matter. In a first version of this experiment the keys were free, and each agent invented its own names, such as "checkout_failure" and "tracer_note", which the next agent had to guess. With fixed keys, the root service and the error rate were right in 6 of 6. The deployer, though, picked the oldest deploy instead of the newest in 3 of 6 incidents. It did not do that with direct messages. With two more tools and a "read first, write after" instruction, it had more to juggle and was less careful with its own job. The result was 3 of 6 at every size. The store also cost the most model calls, 47 at 6 bystanders, because every agent reads and writes.

TOOLS = [
  {"name": "read_notes", "description": "Read the notes the team has saved."},
  {"name": "write_note", "parameters": {"key": {"enum": ["root_service", "newest_deploy_version", "error_rate_pct", "other"]},
                                      "value": {"type": "string"}}},     # fixed keys: free keys were never found again
]

Token cost of talking

Each bystander does a little work of its own, about 600 tokens. What it costs everyone else depends on the channel. With direct messages it costs no one else anything: the team went from 3,200 to 6,800 tokens as bystanders went from 0 to 6, about 600 per bystander. With a shared transcript every later agent reads the bystander's messages, about 1,150 per bystander. With the task restated it was 2,300, because the restatement made the turns longer. With the shared store it was 1,850, because every agent reads every note and writes its own. In a transcript, total reading grows with the number of agents times the length of the chat, roughly the square of the team size. That is why group-chat designs get expensive fast.

Choosing

Use direct messages when you know the dependencies, which is most fixed designs. Use a shared store with fixed keys when agents come and go, or when you do not know in advance who will need a fact. Keep each agent's tools for its own job, and test that the extra tools do not distract it. Use a shared transcript only when agents really must see each other's reasoning, as in debate (Chapter 9), and keep the group small. These numbers are from 6 incidents and one 14-billion-parameter model. A larger model may cope better with a long group chat, but it will still pay to read it.

Use case: group chats and blackboards in frameworks

Conversation-based frameworks such as AutoGen's group chat put agents in one shared transcript, with a manager choosing who speaks next. Graph-based frameworks such as LangGraph pass a typed state object between nodes, closer to direct messages or a store. Research systems in which several subagents work at once usually have them write results to a store or return them to a lead, rather than read each other's transcripts. The trade-off is the one measured here: a shared transcript is the easiest to build and the hardest for each agent to stay focused in.

⚠️
Common mistakes
  • A group chat by default: 0 of 6 here, and the cost grows with the square of the team.
  • Free-form keys in a shared store, so every agent invents its own names.
  • Prefixing agents' messages with their names in a shared history: the model copies the prefix.
  • Giving every agent coordination tools without testing whether they distract it.
  • Sending everyone everything when code knows who needs what.
  • Comparing channels at one team size: the differences grow with the team.

Interview drill

Explain it simply: How should agents in a team share information?

How a strong answer sounds
By default, typed direct messages routed by code to the agents that need them; a shared store with fixed keys when the dependencies are not known in advance; a shared transcript only when agents must see each other's reasoning. In a test on 6 incidents, direct messages got everything right in 5 of 6 at every team size, a shared store 3 of 6 and a group transcript 0 of 6.

Deeper: Why did the shared transcript do so badly?

How a strong answer sounds
Two reasons. Focus: with the whole chat in front of it, the deployer answered the conversation instead of calling its tool, then invented a version to fill its report. Restating each agent's task helped only a little, to 1 or 2 of 6. And cost: every agent reads everyone's messages, so each extra agent cost about 1,150 tokens across the team against about 600 with direct messages, growing roughly with the square of the team size.

🧠 Key takeaways

  • Direct messages: 5 of 6 at every team size, and each agent read the same small context.
  • Shared transcript: 0 of 6; agents answered the chat instead of doing their own jobs.
  • Shared store with fixed keys: 3 of 6; the extra tools made one agent careless.
  • Each extra agent cost about 600 tokens with direct messages, 1,150 in a transcript, 1,850 with a store.
  • Default to typed direct messages; add a store or a transcript only for a reason.
