Your First Two-Agent System

The smallest team is two agents taking turns: one writes, the other reviews, and the writer revises until the reviewer is satisfied. It needs nothing but two message lists and a loop in plain Python. It also has every problem bigger teams have: what to pass between the agents, whose turn it is, when to stop, and whether the second agent helped at all.

A writer agent implemented 12 small functions from exact specs, such as parsing "1h30m", comparing semantic versions and expanding cron fields. Each was checked by 103 hidden tests run in a sandbox, which neither agent saw. Four set-ups were compared: the writer alone; one agent reviewing its own code; a separate reviewer that says "APPROVED" when satisfied; and a reviewer that returns a typed verdict. All used qwen3:14b at temperature 0, with up to 3 review rounds.

  • Build two agents as two message lists and a loop
  • Decide what each agent sees of the other
  • Bound the turn-taking
  • Make the stop signal something code can read
  • Measure whether the second agent helped

Two loops

Each agent is its own conversation. The writer's message list holds the spec, its code and the reviews it has received. The reviewer's holds only the spec and the code it is checking. It starts fresh every round, so it judges the code in front of it rather than defending its last opinion. The "system" is the loop that moves text from one list to the other. There is no framework here, and none is needed.

def write_and_review(spec: str, rounds: int = 3) -> str:
    writer = [{"role": "system", "content": WRITER}, {"role": "user", "content": spec}]
    code = code_of(chat(writer))
    for _ in range(rounds):                                  # turn-taking, bounded
        verdict = review(spec, code)                           # fresh context: spec + current code only
        if verdict["approved"] and not verdict["issues"]:
            break                                             # the stop signal, read by code
        writer.append({"role": "user", "content": "A reviewer found:\n" + bullets(verdict["issues"])})
        code = code_of(chat(writer))
    return code

Passing messages

What crosses between the agents decides what each can do. The reviewer got the spec and the current code, not the writer's earlier drafts or reasoning, so every round is an independent check. The writer got the review appended to its own conversation, so it could see its earlier code and what was said about it. The format of the review matters as much as its content. A free-text review with "Bug: …, but this is correct, so not a bug" in it is hard to act on. A list of issues, each with an input that shows it, is easier.

Turn-taking

Two agents taking turns can go on for ever, so the loop needs a limit; here it was three review rounds. The limit was reached more often than the reviewer was satisfied. With the typed verdict, 10 of 12 tasks ran to the limit. Turns also oscillate. On rate_limit, the typed reviewer rejected a correct draft, and the writer went from 2 tests passing to 6, back to 2 and back to 6. On parse_duration it went 10, 7, 10, 7. A reviewer that cannot run the code is guessing, and a writer that obeys every guess follows it back and forth.

Stopping

The first reviewer was told to reply "with exactly APPROVED and nothing else". It often explained its reasoning and then ended with "APPROVED", which the loop's exact match did not recognise. It ended 14 of its 30 reviews that way, but the loop stopped only 3 times. On human_bytes the code passed all 8 tests and was approved in round 1. Unrecognised, it went to round 2, where the reviewer invented a bug ("1024 B should be '1 KiB'"), and the writer "fixed" it down to 5 of 8. A stop signal that depends on a model's exact wording is fragile. The typed verdict, {"approved": bool, "issues": [...]}, was read the same way every time. Read as a person would, the free-text reviewer approved failing code 8 times in 30 reviews. The typed reviewer approved failing code 0 times in 32, but it rejected passing code 12 times.

VERDICT = {"type": "object", "required": ["approved", "issues"], "properties": {
    "approved": {"type": "boolean"},

Was it better than one?

Barely, and at a high price. The writer alone got 5 of 12 functions fully right and 82 of 103 tests, using about 420 tokens per function. The separate reviewer with the typed verdict got 7 of 12 and 85 tests, using about 8,700 tokens: about 20 times as many. It fixed compare_versions and rate_limit and improved roman_to_int from 6 to 9 tests. It also left parse_duration, expand_cron_field and normalise_path worse than their first drafts. One agent reviewing its own code in the same conversation did worst: 3 of 12, 77 tests. It rewrote rate_limit from 2 tests passing to 0. The second agent helps when its feedback is grounded. Here it could only read the code, and twelve functions are too few to separate 5 from 7 with confidence. Chapter 9 gives the critic tests to run and measures the difference.

Use case: writer–reviewer pairs in practice

The pattern appears wherever a draft is checked before it ships. Coding agents have one model propose a change and another review the diff. Content tools have a writer and an editor, and support tools have a drafter and a compliance checker. The ones that work well ground the reviewer in something it can check. Coding reviewers run the tests or the type checker, and compliance reviewers check against a written policy. Bounded rounds and a structured verdict ("approve / request changes" plus comments) mirror how people review pull requests. The numbers here show what happens without the grounding: a reviewer that only reads is about as likely to break working code as to fix broken code.

⚠️
Common mistakes
  • A stop signal matched as an exact string: 14 reviews ended "APPROVED", the loop stopped 3 times.
  • No round limit, or no plan for when it is reached.
  • A writer that obeys every review, so a wrong review breaks working code.
  • Self-review in the same conversation sold as a second opinion: it was the worst set-up here.
  • Judging the pair on how confident the reviewer sounds instead of on tests.
  • Ignoring the cost: about 20 times the tokens for two more functions.

Interview drill

Explain it simply: How would you build a writer–reviewer pair, and how does it stop?

How a strong answer sounds
Two message lists and a loop. The writer keeps its history; the reviewer gets the spec and the current code fresh each round. The reviewer returns a typed verdict, approved plus a list of issues with inputs, and code stops on approved-with-no-issues or after a fixed number of rounds. Not a magic word: in a test, the reviewer ended 14 reviews with "APPROVED" but an exact-match check caught only 3, and one unrecognised approval led to working code being broken.

Deeper: Your reviewer agent sometimes makes the code worse. What do you change?

How a strong answer sounds
Ground it. A reviewer that only reads code guesses: in a test it approved failing code 8 times in 30 reviews in free text, and with a typed verdict it rejected passing code 12 times in 32, sending the writer back and forth. I would let the reviewer, or the loop, run the tests, require each issue to come with an input that shows it, keep the best version seen so far, and measure against the writer alone. There, the pair went from 5 to 7 of 12 functions for about 20 times the tokens.

🧠 Key takeaways

  • Two agents are two message lists and a loop; decide exactly what crosses between them.
  • Bound the turns: 10 of 12 typed-verdict runs reached the 3-round limit.
  • Make the stop signal typed: "APPROVED" ended 14 reviews but stopped the loop only 3 times.
  • A reviewer that cannot run the code fixes some functions and breaks others.
  • Writer alone 5 of 12, writer + typed reviewer 7 of 12 at about 20 times the tokens, self-review 3 of 12.
