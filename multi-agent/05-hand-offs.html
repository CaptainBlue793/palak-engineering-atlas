Hand-offs Between Agents

A hand-off passes control from one agent to another. A front-line agent passes a customer to billing, or a planner passes a task to a coder. Two things must happen. The hand-off must actually take place, and the next agent must receive what it needs to act. Both fail more often than you would expect, and quietly: the customer is told they have been transferred, or the next agent acts on facts it never had.

Ten scripted support conversations, five about a double charge and five about a crashing app, spread their facts across five customer messages. Those facts were the account number, an invoice or error code, an amount or app version, a contact preference and what the customer had already tried. A front agent routed each conversation with a transfer tool. A billing or technical specialist then had to act with one tool call whose arguments were checked against the facts. Four things could travel with the hand-off: the full transcript, a note the front agent wrote, typed fields, or the last message only. All agents ran on qwen3:14b.

  • Make the transfer of control an action, not a sentence
  • Choose what context travels with a hand-off
  • Model a hand-off as a tool with typed fields
  • Spot lost context before it becomes a wrong action
  • Hand control back when the specialist is done

Transfer of control

A hand-off is real only when code sees it: a tool call that the loop turns into "this conversation now belongs to billing". On the first run the front agent called transfer for all 5 billing conversations, but for none of the 5 technical ones. Instead it wrote "I will transfer your case to the technical team for further assistance. They will contact you via email as requested." It promised the transfer and did not make it. If that text had gone to the customer, they would have waited for a call that was never queued. Only the typed-fields version, whose tool had more required fields, was called in 9 of 10. The fix used for the rest of this chapter is a standard one. If the front agent replies without calling the tool, the loop tells it once that it did not, and it calls the tool. That took one nudge in 17 of the 40 conversations. Where the API supports it, forcing a tool call does the same job.

reply = chat(messages, tools=[TRANSFER])
if not reply.tool_calls:                                  # it said "I will transfer you" but did not
    messages += [reply, {"role": "user", "content": "(system) You did not call the transfer tool. Call it now."}]
    reply = chat(messages, tools=[TRANSFER])
if not reply.tool_calls:
    raise HandoffFailed(conversation_id)                     # never tell the customer it happened

What context to pass

With the hand-off made, what the specialist received decided everything:

  • Full transcript: the specialist acted with every fact right in 10 of 10 conversations. It read the most context, about 190 tokens here and far more in a long conversation.
  • Typed fields (account, reference, details, contact preference, already tried): 10 of 10, with less than half the context.
  • A note the front agent wrote: 0 of 10. Every note kept the invoice or error code and the contact preference. None kept the account number, and no billing note kept the amount.
  • Last message only ("Can you sort this out for me?"): 0 of 10. The specialist did not act and asked for details the customer had already given.
TRANSFER = {"type": "function", "function": {"name": "transfer",
  "description": "Transfer the conversation. The team will not see the conversation, only these fields.",
  "parameters": {"type": "object", "required": ["team", "account_id", "reference", "details", "contact_preference", "already_tried"],
    "properties": {"team": {"enum": ["billing", "technical"]}, "account_id": {"type": "string"}, # …one field per fact the team needs
}}}}

Hand-off as a tool

Treating the hand-off as a tool gives you three things. The destination is an enum, so code routes it and nothing is lost in prose; every hand-off here went to the right team. The payload has a schema: required fields are a checklist the front agent cannot skip, and that is why typed fields kept the account number every time while the free-text notes never did. And the call is an event you can log, count and test: "17 of 40 needed a nudge" is a number only because the hand-off was a tool call. Agent SDKs that offer hand-offs, such as the OpenAI Agents SDK, implement them this way: the hand-off appears to the model as a tool named after the target agent.

Lost context

Lost context rarely shows up as an error. It shows up as a confident wrong action. After a summary-note hand-off, the billing specialist had to call issue_refund(account_id, invoice_id, amount, …) without an account number or an amount. Across the two runs it did so 10 times. In 7 it passed the literal values "not provided" or "unknown", which a real API would reject at best. In 3 it invented them: a refund of £150.00 to account "ACC-1234", when the customer's account was AC-91644 and the charge £215.99. The fixes are in the plumbing: a typed hand-off whose required fields cannot be left out, and specialist tools that reject placeholder values instead of acting on them.

Handing back

A specialist that finishes should hand control back with a typed result, such as {"done": true, "action": "refund issued", "ticket": "…"}. The front agent then continues the conversation knowing what happened, instead of the customer starting over. The same rules apply in reverse: back-hand-offs must be real tool calls, and the result must carry what the front agent needs. This chapter's experiment stopped at the specialist's action, so handing back is not measured here. Chapter 19 covers hand-offs to people.

Use case: triage and transfer in support systems

Customer-service agent systems are often built as triage plus specialists, the same shape as human contact centres, and the same rule holds. Contact centres pass a case record with fixed fields on a transfer so the customer does not repeat themselves. Agent frameworks express the transfer as a tool, as in the OpenAI Agents SDK's hand-offs and LangGraph's command-based hand-offs between nodes. Their documentation also offers input filters that decide how much history travels. The measurements here suggest a default: pass typed fields for what the next agent must act on, and the transcript as well only when the next agent needs to read the conversation itself.

⚠️
Common mistakes
  • Trusting "I will transfer you": 5 of 10 hand-offs were announced and never made.
  • A free-text summary as the only context: it dropped the account number in 10 of 10.
  • Passing the last message only: the specialist could not act at all.
  • Tools that accept "not provided" or invented placeholders instead of refusing.
  • Forgetting the way back: the specialist's result must reach the front agent.
  • Not logging hand-offs as events, so you cannot count or test them.

Interview drill

Explain it simply: How should one agent hand a customer to another?

How a strong answer sounds
As a tool call the loop acts on, with typed fields for everything the next agent must act on. In a test, a front agent announced the transfer in text instead of calling the tool in 5 of 10 conversations, so I check for the call and nudge or force it. Typed fields got every fact to the specialist in 10 of 10; a free-text note lost the account number in 10 of 10.

Deeper: After a hand-off, an agent refunded the wrong account. How could that happen, and how do you prevent it?

How a strong answer sounds
The account number did not travel. In a test, the front agent's notes kept the invoice and the contact preference but never the account; the billing agent then called the refund tool with "not provided" 7 times and invented "ACC-1234" with £150.00 three times. Prevention is structural: required fields in the hand-off schema, validation in the refund tool that rejects unknown or placeholder accounts, and a test suite of hand-offs that checks the arguments, not the prose.

🧠 Key takeaways

  • A hand-off is a tool call, not a sentence: 5 of 10 were announced and not made.
  • Check for the call and nudge or force it; 17 of 40 needed one nudge.
  • Typed fields and the full transcript both got every fact through in 10 of 10.
  • Free-text notes dropped the account number in 10 of 10; the last message alone got nothing through.
  • Lost context turns into confident wrong actions: three refunds to an invented account.
