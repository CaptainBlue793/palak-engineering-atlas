Pipelines & Routing

Not every multi-agent system improvises. Many are fixed. A pipeline passes work through stages in a set order, such as extract, then analyse, then write. A router looks at a request and sends it to one of several agents. These designs are predictable, cheap and easy to test, and they fail in their own way: a mistake at one stage arrives at the next stage looking like a fact.

This chapter has two measurements on qwen3:14b. First, 48 support requests went through three routers to four teams: keyword rules, an LLM router, and an LLM router allowed to say "unsure". Eight of the requests deliberately belonged to two teams. Second, 16 service logs of 60 to 90 lines each had to yield one service's error count, the first and last error time, and the most common error. They went through four designs: one model call; a three-stage LLM pipeline; the same pipeline with checks between stages; and code doing the counting while a model wrote the report.

  • Build a sequential pipeline of agents
  • Route requests, and know what a router cannot tell you
  • Trace how an error flows down a chain
  • Put checks between stages that catch what matters
  • Decide which stages should be code, not agents

Sequential pipelines

A pipeline is the simplest multi-agent system: each stage is one model call with one job, and each stage's output is the next stage's input. Here stage 1 copied the service's ERROR lines out of the log, stage 2 computed the statistics from those lines, and stage 3 wrote a two-sentence note for the on-call channel. Splitting the work did not make it more accurate. The three-stage pipeline got all four statistics right in 1 of 16 logs, the same as a single call, and used 40% more tokens. Each stage was simpler, but each one could fail, and nothing downstream noticed when one did.

lines = extract(log, service)          # stage 1: copy the ERROR lines for this service
stats = analyse(lines)                 # stage 2: count, first and last time, most common message
note  = write_note(stats)              # stage 3: two sentences for the on-call channel

Routers

On the 40 clear requests the routers were close: keyword rules got 37 right, the LLM router 38 and the LLM router with an "unsure" option 38. The keyword rules had an unfair advantage, because they were written by the same person who wrote the requests. Real traffic would find their gaps quickly. The model's misses were arguable: "Do you offer a discount for charities?" went to other instead of billing. The ambiguous requests split every router: 4, 4 and 5 of 8. The most useful number is the one that never moved. Given an explicit "unsure" option and told to use it when a request clearly belonged to two teams, the router chose it 0 times in 48, including on all 8 ambiguous requests. A router's label says nothing about its confidence. If misrouting is costly, let the receiving agent hand the request back (Chapter 5), or measure confidence some other way, such as agreement between two routings (Chapter 10).

route = json.loads(chat([{"role": "system", "content": ROUTER}, {"role": "user", "content": request}],

Errors down the chain

Stage 1, copying lines out of a log, went wrong in 13 of 16 logs. In 11 it copied too many lines, including other services and other levels; once it copied 46 lines for a service with 7 errors. Stage 2 counted whatever it was given. The worst case was an empty list. When stage 1 returned nothing, stage 2 did not say "no lines". It produced "15 errors between 2023-10-01 08:05:12 and 17:45:33, most often 'Connection refused'". None of that is in the log, and it produced the same invention every time it got an empty list. Stage 3 then wrote it up. The report repeated the numbers it was given in 14 of 16 runs and never once questioned them. In a chain, the last stage writes confidently whatever the first stage got wrong.

Checks between stages

The checked pipeline validated each stage before passing it on. Every line from stage 1 had to appear in the log, at ERROR level, for the right service. If any did not, stage 1 was told how many were wrong and tried once more, and only verified lines went forward. Stage 2's count and times had to match the lines it was given, with one retry. This caught real problems: stage 1 needed a retry in 15 of 16 logs. But the check only removes bad lines. It cannot add the lines a stage missed, so in 12 of 16 logs fewer lines than the truth went forward, sometimes only 1 of 7. Three times nothing survived, and stage 2 invented its statistics again. The checked pipeline got 3 of 16 right, at 2.4 times the single call's tokens. A check has to cover what can go wrong, and that includes an empty or implausibly short input, which a stage should refuse instead of filling.

def check_lines(lines: list[str], log: list[str], service: str) -> list[str]:
    ok = [l for l in lines if l in log and " ERROR " in l and f" {service} " in l]   # precision: catches strays
    if not ok:
        raise StageError("no verified lines: refuse, do not let the next stage guess")
    return ok                                                       # recall: missed lines stay missed

Workflows vs agents

Stages 1 and 2 are not judgement. Filtering lines by level and service and counting them is what code is for. With code doing those two stages and the model writing only the note, all four statistics were right in 16 of 16 logs, using 153 tokens and 0.9 s per log, a tenth of the single call. The model did the one thing it was needed for, turning numbers into a readable note, and it repeated every number correctly. The question for each stage of a pipeline is not "can a model do this?" but "does this need a model?". Where it does not, a model is a slower, costlier and less reliable function.

Use case: routing and chaining in production

Anthropic's guide to building effective agents describes prompt chaining and routing as the first workflows to reach for, before autonomous agents. It recommends programmatic "gates" between steps to check that the process is on track, which is this chapter's checks between stages. Customer-service platforms route tickets with a classifier and send the uncertain ones to a person. Document-processing pipelines in insurance, finance and law extract fields with a model and then validate them against rules. The cases that go wrong are the ones this chapter measured: unchecked extraction feeding confident summaries.

⚠️
Common mistakes
  • A model for a deterministic stage: 1 of 16 right, against 16 of 16 in code.
  • No check between stages, so the last stage writes up the first stage's mistake.
  • Letting a stage run on empty input: it invented "15 errors" and "Connection refused".
  • Checks that remove bad output but never notice missing output.
  • Trusting a router's label as confidence: "unsure" was never chosen.
  • Judging keyword rules on the requests they were written from.

Interview drill

Explain it simply: When would you build a pipeline of agents instead of one agent?

How a strong answer sounds
When the steps are fixed and each needs a different skill, but I would make each deterministic step code and check every hand-over. In a test on 16 logs, a three-stage LLM pipeline got the statistics right once, the same as one call; code doing the filtering and counting with a model writing the note got 16 of 16 with a tenth of the tokens.

Deeper: A pipeline's report states numbers that are not in the source. How did that happen, and what stops it?

How a strong answer sounds
An earlier stage failed quietly and a later one filled the gap. In a test, when the extraction stage returned nothing, the analysis stage invented "15 errors from 08:05 to 17:45, mostly Connection refused", the same invention every time, and the report repeated it without hedging. Checks between stages stop it: verify each output against the source, refuse empty or implausibly short input, and treat recall separately, because dropping bad lines cannot recover missing ones.

🧠 Key takeaways

  • Splitting into stages did not help by itself: 1 of 16, the same as one call.
  • Errors flow down unquestioned: an empty stage became invented statistics in a confident report.
  • Checks caught stray lines but not missing ones; check for empty and implausible input too.
  • Code for the deterministic stages got 16 of 16 with a tenth of the tokens.
  • Routers were 37–38 of 40 on clear requests; given an "unsure" option, the model never used it.
