Messages, Queues & Events

Agents in a team have to pass work and results to each other. They can read and write the same state, or they can send messages. Messages travel through queues and topics, and the plumbing has properties that decide what the agents see. Messages can arrive out of order, more than once, or after the work they describe has moved on. This primer covers the plumbing in the vocabulary the rest of the course uses.

Every number here comes from small asyncio simulations, seeded so they repeat exactly. 40 jobs went through a queue with 1 to 8 consumers, three subscribers listened to one topic, and 200 messages were delivered by a broker that redelivers anything not acknowledged. They needed no model, because the properties belong to the plumbing, not to the agents.

  • Choose between messages and shared state
  • Use queues to decouple producers and consumers
  • Fan one event out to many listeners with publish-subscribe
  • Know when order is lost, and when it matters
  • Handle at-least-once delivery with idempotent consumers

Messages vs shared state

With shared state, agents read and write the same place: a document, a table, a list in memory. Everyone sees the latest version, and two agents can overwrite each other. With messages, an agent sends what it has to whoever needs it, and the receiver decides what to do. Nothing is overwritten, but each agent knows only what was sent to it. Most multi-agent systems mix the two. Workers receive briefs as messages and report findings as messages, while a shared store keeps the decisions everyone must respect. Chapter 6 measures the trade-off with agents, including the token cost of talking.

Queues

A queue holds work between the agent that produces it and the agents that consume it, so neither has to wait for the other. Forty jobs, each taking 0.1 to 0.3 seconds, went through one asyncio.Queue with 1, 2, 4 and 8 consumers. They finished in 8.2, 4.2, 2.3 and 1.2 seconds, close to dividing by the number of consumers, because the jobs were independent and nothing else was shared. That changes as soon as the consumers share something slow, such as one model server (Primer 2).

async def consumer(queue: asyncio.Queue, results: list):
    while True:
        job = await queue.get()
        try:
            results.append(await work(job))
        finally:
            queue.task_done()                              # lets queue.join() know the job is finished

queue = asyncio.Queue()
for job in jobs: queue.put_nowait(job)
workers = [asyncio.create_task(consumer(queue, results)) for _ in range(4)]
await queue.join()                                         # every job taken and finished
for w in workers: w.cancel()

Publish-subscribe

A queue gives each message to one consumer. A topic gives each message to every subscriber. When the orchestrator publishes "task.created", "finding.added" and "task.done", the planner, the auditor and the logger each receive all three, in order. Publish-subscribe suits events several agents care about for different reasons, such as a new finding the planner acts on, the auditor checks and the logger records. A queue suits work that exactly one agent should do.

Ordering

With one consumer the 40 jobs finished in the order they were queued. With 2 consumers, 7 of the 39 consecutive pairs finished out of order. With 4, it was 8, and with 8 consumers, 16. Parallel consumers finish when their work finishes, not when it was queued. If order matters (a correction must not overtake the fact it corrects), carry a sequence number in each message and let the receiver reorder or discard stale ones, or route related messages to the same consumer.

Delivery guarantees

Brokers promise one of three things. At most once: a message may be lost. At least once: it is redelivered until acknowledged, so it may arrive twice. Exactly once: possible only within one system, by combining at-least-once delivery with deduplication. In the simulation a consumer died after doing its work but before acknowledging, 10% of the time. The broker redelivered, and 200 messages took 226 deliveries. A consumer that simply did the work each time applied 26 duplicates. One that kept the ids of messages it had applied, and acknowledged repeats without acting, applied each message once, with 0 duplicates. For agents the duplicate is often a model call (cost) or a tool call with a side effect (a second refund), so idempotent handling is not optional.

def handle(msg: dict, applied: set) -> None:
    if msg["id"] in applied:                    # redelivered: already done
        return                                   # acknowledge, do nothing
    apply(msg)                                   # the work, or the side effect
    applied.add(msg["id"])                     # store durably together with the effect

Use case: brokers behind agent systems

Production agent systems usually put a broker between their parts. Redis lists and streams, RabbitMQ, Amazon SQS and Kafka are common choices, and each documents its guarantee. SQS standard queues deliver at least once and may deliver out of order, while FIFO queues keep order within a message group and deduplicate within a time window. Kafka keeps order within a partition. Workflow engines built on top of them, such as Temporal, record each step's result so that a retried step does not repeat its effect. Agent frameworks that run many agents across machines, and the Agent2Agent protocol's task model (Chapter 12), inherit the same rules. A message between agents is a message, with all the ways a message can go wrong.

⚠️
Common mistakes
  • Assuming messages arrive once, under a broker that delivers at least once.
  • Assuming order with more than one consumer.
  • A queue where every agent should hear the event, or a topic where only one should act.
  • Acknowledging before the work is done, losing it if the consumer dies.
  • Deduplicating in memory only, forgetting applied ids on restart.
  • Shared state for everything, so agents overwrite each other's work.

Interview drill

Explain it simply: When would agents use a queue, and when publish-subscribe?

How a strong answer sounds
A queue when a piece of work should be done by exactly one agent: tasks for a pool of workers. A topic when an event matters to several agents for different reasons: a new finding the planner acts on, an auditor checks and a logger records. With several consumers, assume no order: in a simulation, 8 consumers finished 16 of 39 consecutive jobs out of order. Carry sequence numbers where order matters.

Deeper: Your agents sometimes act on the same message twice. Why, and what do you do?

How a strong answer sounds
The broker delivers at least once: if a consumer dies or is slow after doing the work but before acknowledging, the message comes again. In a simulation with a 10% crash rate, 200 messages took 226 deliveries and a naive consumer applied 26 duplicates. I would make consumers idempotent: give every message an id, store applied ids durably together with the effect, and acknowledge repeats without acting. That gave 0 duplicates. For tool calls with side effects, pass the id on as an idempotency key.

🧠 Key takeaways

  • Messages avoid overwrites; shared state gives everyone the latest version. Most systems use both.
  • More consumers sped up 40 independent jobs from 8.2 s to 1.2 s, and lost their order.
  • A queue gives each message to one consumer; a topic gives it to every subscriber.
  • At-least-once delivery turned 200 messages into 226 deliveries and 26 duplicate effects.
  • Idempotent consumers, recording applied ids with the effect, applied each message once.

Check your understanding

What is the difference between a queue and a publish-subscribe topic?

Work for one agent goes on a queue; events for many go on a topic.

What happened to job order with 8 consumers?

Parallel consumers finish when their work finishes, not when it was queued.

Why did 200 messages produce 226 deliveries?

At-least-once delivery means a message may arrive more than once.

How did the idempotent consumer avoid duplicate effects?

Store the ids durably, together with the effect, or a restart forgets them.

A correction message overtook the fact it corrects. What prevents that?

Order holds only per consumer or per partition.
