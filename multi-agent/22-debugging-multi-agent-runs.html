Debugging a Multi-Agent Run

When a team of agents gets the wrong answer, the mistake could be anywhere: the lead's plan, a brief, a worker's tool call, a finding, the merge. Each agent's output looks reasonable on its own. Debugging means finding the first bad step and deciding which agent owns it, then fixing that agent and keeping the case as a test. That needs traces of everything that crossed between agents, and a way to test a hypothesis rather than argue it.

Chapter 4's lead-and-workers release check ran on its 8 estates with seeds 1 to 3 at temperature 0.7. Every agent, every model call and every tool call was recorded as a span with a parent, a duration and token counts: 24 traced runs, 25 to 66 spans each. Twelve runs got the blockers wrong. For each one, counterfactual replay swapped one upstream component for the right answer and re-ran everything after it, to see which swap fixed the run.

  • Trace a multi-agent run as a tree of spans
  • Find the first bad step, upstream first
  • Assign blame between agents with counterfactual replay
  • Replay a run with one part replaced
  • Fix the culprit and keep the case as a regression test

Traces across agents

A trace is a tree. The run is the root. Under it sit the lead's planning agent, then each worker, then the combine step. Under each agent sit its model calls and tool calls, each with its inputs, outputs, duration and tokens. A run on a four-dependency estate had 37 spans: the lead's planning calls and dependency look-ups, four workers with their model and tool calls, and the combine. The tree answers the questions debugging needs. Who sent what to whom? What did each agent actually see? Where did the time and tokens go? It is the same span model as OpenTelemetry, so the same tools can store and show it.

def start(name, parent=None, **attrs):

Finding the first bad step

Work upstream first. A downstream agent that got bad input and produced bad output did its job. The first bad step is the earliest span whose output is wrong given its input. In 3 of the 12 failures the first bad step was the lead's briefs, and it only showed up in their text. The briefs said "Check for error rate or deploy time." with no service named. Each worker replied {"service": "unknown", "blocking": true, "reason": "service not found"}, and the combine faithfully copied "unknown" four times. The plan's list of services was right, so a check on the structured plan alone passed it. The bad step was in a string.

Blame between agents

After reading the spans, the 12 failures came out as follows:

  • The lead's plan listed the wrong services: 4. Each time it included the release target itself among its dependencies, as in Chapter 4.
  • The lead's briefs named no service: 3.
  • A worker's wrong finding: 4. For example, ledger at 5.2% judged "not blocking" against a 2.0% threshold.
  • A worker's finding and the combine together: 1. Even with the findings corrected, the combine left out media.

The lead was at fault in 7 of 12. One caution from doing this: my first, automatic pass blamed "the combine" for the three unnamed-brief failures, because it checked only the plan's list of services and the findings' flags, and the combine was the last thing left. Automated blame is only as good as the checks it runs. Read the spans before you trust it.

Replaying a run

Counterfactual replay turns a hypothesis into an experiment. Replace one component's output with the right answer, re-run everything downstream, and see whether the outcome is fixed. Upstream first: replacing the lead's plan with the true dependency list and re-running the workers and combine fixed all 4 plan failures. Replacing the wrong worker findings and re-running only the combine fixed 4 of the 5 finding failures. The fifth stayed wrong, which is how the second fault, in the combine, showed itself. Replay needs exactly what tracing records: each component's inputs, so it can be re-run in isolation, and a way to substitute its output.

if sorted(plan) != truth.closure:                           # upstream first
    v = combine(workers(oracle_briefs))                       # fixed all 4 plan failures
elif any(f.blocking != truth.of(f) for f in findings):
    v = combine([f.with_truth() for f in findings])         # fixed 4 of 5; the 5th exposed the combine
# and read the spans: 3 failures were briefs that never named the service

Fix and add a test

Each culprit has a fix, and all three already exist in this course. Validate the plan in code and drop the target (Chapter 4). Write briefs from a template that always names the service and carries the rules. Combine typed findings in code, keyed by the service dispatched. Then keep the failing cases as a regression suite: these 12 (estate, seed) pairs. Chapter 18 ran the design with all three fixes, code-planned with agent workers, on the same estates and seeds, as separate runs. It got 10 of the 12 right. The two it still missed were each a single worker's wrong finding, the one fault the fixes do not remove. Run the suite on every change, and add each new failure to it.

Use case: debugging tools for agent teams

Agent observability platforms such as LangSmith, Langfuse, Arize Phoenix and others record multi-agent runs as nested traces, often on OpenTelemetry's span model and its emerging conventions for generative AI. Several let you re-run one step with edited inputs, the replay described here. Research on failure attribution in multi-agent systems tries to automate "which agent and which step", and finds it hard. Automated judges often pick the wrong agent, which matches this chapter's first, automated pass. The practice that works is traces for everything, upstream-first reading, replay to confirm, then a fix and a regression case.

⚠️
Common mistakes
  • Blaming the last agent: the combine copied "unknown" faithfully; the briefs were at fault.
  • Checking only structured fields: the plan's list was right and its briefs were empty.
  • Trusting automated blame unread: it was wrong for 3 of 12 here.
  • Logging only final answers, so no replay is possible.
  • Fixing without a test: keep every failing case and run it on each change.
  • Stopping at the first fault: one failure had two.

Interview drill

Explain it simply: How do you find which agent caused a wrong answer?

How a strong answer sounds
Trace every agent, model call and tool call, then read upstream first for the earliest step whose output is wrong given its input. Confirm with counterfactual replay: substitute that component's correct output and re-run downstream; if the answer is fixed, you have the culprit. In 12 traced failures, the lead's plan or briefs were at fault in 7, workers in 4, and one run had a worker and the combine both wrong.

Deeper: Your automated blame tool says the final aggregator agent is responsible for most failures. Do you believe it?

How a strong answer sounds
Not until I read the spans. In my own runs an automated pass blamed the aggregator for three failures in which the lead's briefs had never named a service: workers answered "unknown" and the aggregator copied it. The automated checks only compared structured fields. I would add checks on what each agent actually received, confirm by replay, and only then fix, adding the cases to a regression suite.

🧠 Key takeaways

  • Trace a multi-agent run as a tree of spans: every agent, model call and tool call.
  • Find the first bad step upstream first; the last agent is often only the messenger.
  • Confirm blame with counterfactual replay: the true plan fixed 4 of 4 plan failures.
  • Read the messages: 3 failures were briefs that named no service, missed by structured checks.
  • Fix, then keep the cases: the fixed design passed 10 of the 12 failing cases.
