Parallel Fan-Out & Aggregation

Fan-out is the most natural way to use several agents. Split a batch into pieces, give each piece to its own agent, run them at the same time and merge what comes back. It promises speed, a small context per agent, and no agent ever facing a long list. It costs something too. Every worker re-reads the instructions, the merge is a new step that can go wrong, and anything that connects two pieces is invisible to the agents holding them.

The batch is 60 pieces of customer feedback. Each must be labelled with a category (bug, billing, feature request, praise, performance) and a product area. Eight of the 60 are re-posts: the same customer's issue, reworded, which should be counted once. There were five set-ups. One agent labelled all 60 in one call. Fan-outs of 4 agents × 15 items and 12 agents × 5 were merged by code. Two repairs followed the 12 × 5 run, deduplication in code and a model that looks for re-posts. A second run used 240 items to see whether one agent breaks down on a long list. Everything ran on qwen3:14b on one GPU.

  • Check that subtasks really are independent before splitting
  • Know what running in parallel speeds up on one model server
  • Merge results in code, checking coverage
  • Find duplicates and conflicts that cross chunk boundaries
  • Weigh the speed-up against the cost

Independent subtasks

Labelling one item does not depend on another, so labelling splits cleanly. Spotting re-posts does not split, because it is a relation between items. Put the two copies in different chunks and neither worker can see the pair. With 60 items in one call, one agent found 7 of the 8 re-posts. Split into 4 chunks of 15, the workers found 1, the only pair that happened to share a chunk. Split into 12 chunks of 5, they found 0. Before fanning out, ask what in the task connects pieces to each other: duplicates, totals, rankings, order. Each of those needs a step after the merge that sees everything.

chunks = [items[k:k + 5] for k in range(0, len(items), 5)]
parts  = await asyncio.gather(*(label(c) for c in chunks))      # each worker sees only its 5 items
rows   = [r for part in parts for r in part]
assert sorted(r["id"] for r in rows) == sorted(it["id"] for it in items)   # coverage: none lost, none twice

Running in parallel

Fan-out did not make this job faster. On 60 items one agent took 26.6 s and 12 workers 27.7 s. A GPU that serves one request at a time queues the workers' calls one after another (Primer 2), and there were no tool waits to overlap. On 240 items the workers took 110 s against one agent's 131 s. That was not parallelism: shorter prompts are cheaper per token to read, and 20 calls over 12 rows each read less in total than one call over 240. Real speed-ups need either several model servers, an API that serves requests concurrently, or work that waits on tools and people (Chapter 1).

Merging results

With typed rows keyed by item id, merging is concatenation plus a check. In every set-up, every item came back exactly once: no item was dropped, repeated or invented, at 60 or at 240. That check is cheap and it is the first thing to write. Label accuracy barely moved with the split. Both labels were right for 54 of 60 items with one agent and with 12 × 5, and for 51 with 4 × 15. At 240 items one agent got 224 right against 217 and 216 for the fan-outs. Most errors in every set-up were the same ambiguity: a broken invoice page labelled bug rather than billing. Splitting does not fix a labelling scheme that is unclear.

Conflicts and duplicates

The question "how many distinct issues did customers raise?" has the answer 52. One agent counted 53. The 12 × 5 fan-out counted 60, every re-post counted again. Two repairs ran after the merge. A code step paired items with the same labels and enough words in common, and found 5 of 8 with no false pairs, at no token cost. A model given all 60 labelled items and asked to find re-posts found 4 of 8, with no false pairs, for 1,400 more tokens. Neither matched the single agent that saw everything at once. The same problem appears as conflicts: two workers labelling the same customer's issue differently, or reporting different values for the same thing. Merging needs a rule for which wins, and the rule belongs in code.

def likely_reposts(labels: dict, texts: dict, threshold: float = 0.25) -> dict[int, int]:
    """Same labels and enough shared words: a candidate re-post (5 of 8 found, 0 false here)."""
    words = {i: set(re.findall(r"[a-z0-9£]+", texts[i].lower())) - STOP for i in labels}
    found = {}
    for b in sorted(labels):
        for a in sorted(labels):
            if a >= b: break
            if labels[a] == labels[b] and len(words[a] & words[b]) / len(words[a] | words[b]) >= threshold:
                found[b] = a; break
    return found

Speed-up vs cost

Every worker reads the instructions and the output schema again, so more workers cost more tokens for the same items. On 60 items: one agent 3,050 tokens, 4 workers 3,360, 12 workers 4,190 (+37%), and 5,620 with the model looking for re-posts. On 240 items: 14,600 for one agent against 15,500 and 16,700. Here the extra cost bought nothing: no speed-up on one GPU, no better labels, and lost re-posts. Fan-out earns its cost when one agent's context would be too long or too distracting, when each piece needs its own tool calls (Chapter 1's 40 services), or when the pieces wait on the outside world. A batch of short, structured judgements is often better as one call, or a few large chunks.

Use case: map-reduce over documents

Summarising or classifying large document sets with "map" calls over chunks and a "reduce" call over the results is a standard pattern. LangChain has long shipped map-reduce summarisation, and batch inference APIs from model providers exist for exactly this kind of job. The well-known failure modes match this chapter. Facts that span chunks are lost, duplicates are counted twice, and the reduce step either sees too little or re-reads everything. Production pipelines usually add stable ids for every item, a coverage check after the map, and a cross-chunk step, often in code, for deduplication and totals.

⚠️
Common mistakes
  • Splitting a task with links between items: re-posts found fell from 7 to 0.
  • Expecting a speed-up on one model server: 26.6 s against 27.7 s.
  • No coverage check after the merge, so dropped or doubled items go unnoticed.
  • Totals from a fan-out without deduplication: 60 distinct issues counted instead of 52.
  • A model for a merge code can do, or for deduplication that word overlap does as well.
  • Blaming the split for label errors that come from an unclear labelling scheme.

Interview drill

Explain it simply: When does fanning out a batch to parallel agents help?

How a strong answer sounds
When pieces are independent and either the whole would be too long for one agent, each piece needs its own tool calls, or the work waits on I/O that can overlap. In a test labelling 60 and 240 feedback items, one agent did as well as fan-outs of 4, 12 and 24 workers, at lower token cost, and one GPU gave no real speed-up. Fan-out also lost every re-post that crossed a chunk boundary.

Deeper: Your fan-out's totals are too high. Why, and how do you fix it?

How a strong answer sounds
Duplicates across chunks: no worker sees both copies. In a test, splitting 60 items into chunks of 5 counted 60 distinct issues instead of 52. Fix it after the merge with a pass that sees everything: word-overlap matching on items with the same labels found 5 of 8 re-posts with no false pairs and no tokens, and a model pass found 4. Also check coverage, every id exactly once, before computing totals.

🧠 Key takeaways

  • Split only what is independent: re-posts found fell from 7 of 8 (one agent) to 0 (12 × 5).
  • On one GPU fan-out gave no real speed-up; extra workers cost up to 37% more tokens.
  • Merge by id in code and check coverage: every item came back exactly once.
  • Repair cross-chunk links after the merge: code found 5 of 8 re-posts, a model 4.
  • At 240 items one agent labelled as well as the fan-outs (224 against 217 and 216).
