One Agent in One Page

Every multi-agent system is built from single agents, and every one of them should be compared with a single agent doing the whole job. This primer compresses what the Single Agent course teaches into what this course assumes: the loop, tools, context, stopping and how to measure an agent. Each idea comes with a number from a real run.

One agent, qwen3:14b at temperature 0, investigated 12 simulated incidents in which checkout fails and the cause sits 0 to 2 services further down. It had five read-only tools and had to name the deploy that caused the failure. It ran three ways: a plain prompt, the same with a 4-step cap, and the plain prompt plus one sentence describing the method.

The agent loop

An agent is a model in a loop. The model gets the task and a list of tools. If it replies with tool calls, your code runs them, appends the results to the conversation, and asks again. If it replies with text, that is the answer. Everything else is detail: the prompt, the tools, how long the loop may run and what you check afterwards.

def run_agent(task: str, tools: dict, system: str, max_steps: int = 15) -> str | None:
    messages = [{"role": "system", "content": system}, {"role": "user", "content": task}]
    for _ in range(max_steps):
        reply = ollama.chat(model="qwen3:14b", messages=messages, tools=[t["schema"] for t in tools.values()]).message
        messages.append(reply)
        if not reply.tool_calls:
            return reply.content                             # stop 1: the model answered
        for call in reply.tool_calls:
            result = tools[call.function.name]["fn"](**call.function.arguments)
            messages.append({"role": "tool", "tool_name": call.function.name, "content": str(result)})
    return None                                            # stop 2: the step cap

Tools

To the model, a tool is a name, a description and a JSON Schema for its arguments. It never runs anything. It writes a request, and your code decides whether and how to run it. The result goes back as text in a tool message, and errors should too ("error: unknown service 'paymnets'"), so the model can correct itself. Here the agent had list_services, get_errors, get_metrics, get_deploys and get_dependencies, all read-only. In this course, tools are also how agents reach each other: handing work to another agent is often just a tool call (Chapter 5).

Context

The model has no memory between calls. Each step sends the whole conversation again: the system prompt, the task, every tool call and every result. In these runs the first step read 364 tokens and the last read 600 on average, about 735 with the method sentence, and a run sent 2,331 prompt tokens in total. That is small, because these tools return a few lines. Real tools return pages, and the transcript is what one agent eventually runs out of. Chapter 1 shows an agent asked to check 40 services that read half the data and invented the rest. Giving each agent its own, smaller context is one of the main reasons to use several.

Stopping

A loop stops in one of two ways: the model replies without a tool call, or the step cap is reached. Neither means the task is done. With the plain prompt, all 12 runs stopped because the model answered, and 7 of the 12 answers were wrong. In the typical miss, the agent saw "503 from payments" on checkout, then blamed a checkout deploy. A 4-step cap cut the time but stopped 6 runs before they answered, and only 4 were right. Adding one sentence of method ("follow the 503s to the service with its own errors; its newest deploy is the cause") raised it to 8 of 12. It was not a free win: it fixed five runs and broke two the plain prompt had right. With the method the agent found the right service in 11 of 12, and three of its four misses then picked an older deploy of that service instead of the newest.

METHOD = ("Errors that say '503 from X' mean the problem is further down, in X: follow them until you reach "
          "a service with its own errors. The newest deploy of that service is the cause.")
system = "You are an on-call assistant. Use the tools to investigate before answering. " + METHOD

Measuring an agent

One run tells you almost nothing. Measure an agent on a set of tasks with a grader that checks the answer, here whether it names the causing version. Record the success rate, the steps, the tokens and the time. Twelve tasks are enough to see 5 against 8, not to tell 8 from 9. The Single Agent course, Chapter 29, shows how much a rate moves between repeated runs. In this course, every team of agents is compared against a baseline like this one: one agent, same model, same tools, and a prompt that is just as good. A team that beats a weak single agent has not shown anything.

Use case: the same loop inside agent SDKs

Agent SDKs run this loop for you. The OpenAI Agents SDK and Anthropic's Claude Agent SDK expose the step cap as a maximum number of turns. LangGraph's prebuilt ReAct agent runs it as a graph with a recursion limit. Their multi-agent features are built on the same loop: a hand-off or a sub-agent is a tool call whose result is another agent's answer. When a multi-agent run misbehaves, it is usually one of these loops stopping too early, running too long or reading the wrong context.

⚠️
Common mistakes
  • Treating "the model stopped" as "the task is done": 7 of 12 plain runs stopped with a wrong answer.
  • No step cap, or a cap so tight it stops runs mid-investigation.
  • Judging an agent by one run instead of a task set with a grader.
  • Raising exceptions out of tools instead of returning errors the model can read.
  • Forgetting the context is re-read every step, so long tool results cost on every later step.
  • Comparing a team against a weak single agent: fix the prompt first.

Interview drill

Explain it simply: What is an agent, in code?

How a strong answer sounds
A model in a loop. Send the conversation and the tool schemas; if the reply has tool calls, run them, append the results and call again; if it has none, that is the answer; stop anyway at a step cap. The model never runs tools itself, and it has no memory between calls: each step re-reads the whole transcript, so the context grows with every step.

Deeper: Your agent answers confidently but is often wrong. Before adding more agents, what do you do?

How a strong answer sounds
Measure it on a task set and read the failing traces. In one test, a plain prompt got 5 of 12 incidents right and every run stopped by answering, so the loop was not the problem: the agent stopped following the evidence. One sentence describing the method raised it to 8 of 12. Only once the single agent is as good as I can make it would I compare a team against it, with the same model and tools.

🧠 Key takeaways

  • An agent is a model in a loop: call, run the tools, append the results, repeat.
  • The context is re-sent every step: 364 tokens at the first step, about 600 at the last.
  • "Stopped" is not "done": 7 of 12 plain runs stopped with a wrong answer.
  • One sentence of method moved the agent from 5 to 8 of 12; a 4-step cap moved it to 4.
  • Every team in this course is measured against one agent with the same model, tools and prompt quality.
