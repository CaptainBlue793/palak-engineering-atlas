HTTP/3 & QUIC

HTTP/2 ran into a wall that wasn't in HTTP. One lost packet stalls every stream, because TCP delivers a single ordered sequence of bytes and has no idea that the bytes belong to different requests. Fixing that inside TCP was not practical, for reasons this chapter explains, so the fix was a new transport protocol, QUIC, built on top of UDP. QUIC does everything TCP and TLS do together: reliable delivery, congestion control and encryption. It also adds what TCP couldn't: streams that are independent of each other, a handshake in one round trip, and connections that survive a change of network. HTTP/3 is HTTP carried over QUIC. It now serves a large share of web traffic, and most people who use it have never noticed.

Why QUIC runs on UDP

TCP can't be given independent streams, because an ordered byte stream is what TCP is, to every program that uses it. And TCP can't easily be changed at all, for two reasons that the QUIC designers call ossification:

  • It lives in operating-system kernels. A change has to ship in Windows, Linux, iOS and Android and then wait years for devices to be updated.
  • The network has opinions about it. Firewalls, NATs and load balancers read TCP headers and drop what they don't recognise. Chapter 12 told the story of window scaling. Later extensions fared worse.

A brand-new protocol number in the IP header would be dropped by those same devices on sight. The only other transport that reliably crosses the internet is UDP, which adds almost nothing to IP (Chapter 7). So QUIC is carried inside UDP datagrams, and everything else is built above them, in ordinary user-space code that ships with the browser or the server and can be updated in weeks.

QUIC also defends itself against the fate of TCP. Almost every byte of a QUIC packet is encrypted, including most of its header, so that devices in the path can't come to depend on details that might need to change later. To an observer, QUIC is a stream of UDP datagrams with a few visible bits and a connection ID.

Independent streams

In QUIC, streams belong to the transport. Each one is its own ordered sequence of bytes, and a packet carries frames for one or several of them. When a packet is lost, the receiver knows which streams had data in it. Those streams wait for the retransmission, and every other stream is delivered immediately. The head-of-line blocking of Chapter 16's panel is gone, because nothing in QUIC promises one global order.

One piece of HTTP/2 had to be redesigned as a result. HPACK assumes that header blocks are decoded in exactly the order they were encoded, which TCP guaranteed. HTTP/3 uses a variant, QPACK, that sends table updates on a stream of their own and lets a request refer only to entries its peer has confirmed, so that one late packet doesn't hold up the decoding of unrelated requests.

Built-in TLS and the one-round-trip handshake

With TCP and TLS as separate layers, a new connection needs two round trips before the request: one for each handshake. QUIC does both at once. Its first packet carries the TLS ClientHello, so the transport parameters and the keys are agreed together.

A client that has talked to the server before can do better still. It kept a ticket from the last connection (Chapter 17) and sends its request in the first flight, encrypted with a key from that ticket. That is 0-RTT: the response is on its way back before any handshake has finished. The warning from Chapter 17 applies unchanged, since early data can be replayed, so it is for requests that are safe to repeat.

Connection IDs and migration

A TCP connection is its 4-tuple: two addresses and two ports. If the client's address changes, because a phone walks out of Wi-Fi range or a NAT gives the flow a new port after an idle period (Chapter 9), packets from the new address match no connection, and the old one is dead. Every request in flight fails, and the client starts again with new handshakes.

A QUIC connection is identified by a connection ID that the endpoints choose and carry in each packet. When a packet arrives from a new address with a known connection ID, the server checks that the client really is reachable there by sending a challenge that must be echoed back, and then carries on with the same connection, streams and keys. This is connection migration. For privacy, the two sides switch to a fresh connection ID on the new path, so an observer can't link the old address to the new one.

Each block is one round trip. Server processing time and the DNS lookup are left out, and they are the same for both. A returning client is assumed to send early data, which many servers allow only for safe requests. On the network change, the phone's system is assumed to report the broken TCP connection at once.

Things to notice. A first visit costs three round trips over TCP and TLS before any of the response arrives, and two over QUIC. At 150 ms that is 450 ms against 300 ms. A returning client saves one more on each, and QUIC then reaches the first byte in a single round trip, 150 ms. The difference grows with the round-trip time, so the users who gain most are the ones furthest away or on the slowest networks. The second row is the case TCP can't handle at all. The connection is gone, and the client pays the whole set-up again to resume. QUIC needs one round trip to check the new path, and data keeps flowing.

Google's measurements: who gains from QUIC

QUIC began inside Google in 2012 and was switched on for Chrome users talking to Google's own services long before it was standardised, which gave it something rare for a new protocol: measurements at the scale of the whole internet. In 2017 the team published them. Averaged over all users, the gains were modest. Search results arrived about 8% sooner on desktop and about 4% sooner on mobile, and YouTube stalled to rebuffer 15 to 18% less often. The averages hid the real story, which was in the distribution. Users on fast, clean networks near a data centre saw almost no change, since TCP was already serving them well. The improvement was concentrated among the slowest connections, those with high latency, loss or both, where fewer round trips to connect and streams that don't block each other each remove hundreds of milliseconds. Those are the users for whom a page was slowest to begin with. The same paper is frank about the costs: QUIC used roughly twice the server CPU of TLS over TCP at first, and a few percent of networks blocked or throttled UDP, so every client needed a working fallback. Both are still true in milder form, and they are why HTTP/3 is deployed next to HTTP/2 and not in place of it.

Finding HTTP/3, and falling back

A URL doesn't say which version of HTTP to use, and a client can't know in advance whether a server speaks QUIC or whether the path lets UDP through. So the first connection normally uses TCP, and the server advertises the alternative:

$ curl -sI https://www.example.com | grep -i alt-svc
alt-svc: h3=":443"; ma=86400              # "HTTP/3 is available on UDP port 443; remember that for a day"

$ curl --http3 -sI https://www.example.com | head -1
HTTP/3 200

$ sudo tcpdump -ni eth0 udp port 443       # all you can see from outside: datagrams. The rest is encrypted
10:14:07.100 IP 10.0.0.5.51234 > 93.184.216.34.443: UDP, length 1250
10:14:07.249 IP 93.184.216.34.443 > 10.0.0.5.51234: UDP, length 1250

The same announcement can be published in DNS, in an HTTPS record, so that even the first visit can use QUIC. Browsers then race the two: they try QUIC, keep a TCP connection ready, and use whichever works. If UDP is blocked, the user gets HTTP/2 and never knows.

Common mistakes
  • Opening TCP 443 in a firewall and forgetting UDP 443. HTTP/3 silently never happens, and everyone falls back.
  • Dropping the fallback. Some networks block UDP. A service reachable only over QUIC is unreachable for them.
  • Routing QUIC by 4-tuple in a load balancer. After a migration the packets go to a different server that has never heard of the connection. Route by connection ID (Chapter 24).
  • Expecting gains on a fast local network. The benefit is on long, lossy and mobile paths. In a data centre TCP is usually cheaper.
  • Forgetting UDP idle timeouts. NAT entries for UDP expire in about 30 seconds, so idle QUIC connections need keep-alives or must cope with a new port.
  • Trying to debug it with a packet capture. Nearly everything is encrypted. Use the endpoint's own logs (qlog) or keys exported for Wireshark.

Interview drill

Explain it simply: What is QUIC, and what problems does it solve?

How a strong answer sounds
QUIC is a transport protocol that runs over UDP and replaces the combination of TCP and TLS; HTTP/3 is HTTP running on it. It solves three problems. First, head-of-line blocking: HTTP/2 multiplexes streams over one TCP connection, so a single lost packet stalls all of them, because TCP delivers one ordered byte stream. QUIC implements streams in the transport, each ordered independently, so a loss delays only the streams whose data was in that packet. Second, connection set-up: TCP then TLS takes two round trips before the request, whereas QUIC merges the transport and TLS 1.3 handshakes into one round trip, and a returning client can send data with zero round trips. Third, mobility: a TCP connection is tied to its IP addresses and ports, while a QUIC connection is identified by a connection ID, so it survives a switch from Wi-Fi to mobile data. It runs over UDP and in user space because TCP is fixed in kernels and middleboxes and couldn't be changed in practice, and it encrypts nearly all of its header so that it can keep evolving.

Deeper: If QUIC is better, why does everything still support HTTP/2 over TCP as well?

How a strong answer sounds
Several reasons. Reachability: a few percent of networks block or rate-limit UDP on port 443, typically corporate firewalls, so clients must be able to fall back; browsers race QUIC against TCP and use whichever connects. Discovery: a client usually learns that a server supports HTTP/3 from an Alt-Svc header or an HTTPS DNS record, so the first connection is often over TCP anyway. Cost: QUIC runs in user space with per-packet encryption and has historically had less help from kernel and NIC offloads, so it uses more CPU per byte than TCP with TLS, which matters for large transfers and inside data centres. Benefit: on a short, clean, low-latency path there is little loss and the extra handshake round trip is under a millisecond, so service-to-service traffic gains almost nothing, while users on long or lossy paths gain a lot. And operations: load balancers must route by connection ID, firewalls and monitoring tools see only encrypted UDP, and debugging needs endpoint logs. So the usual deployment is HTTP/3 at the edge for end users, with HTTP/2 or HTTP/1.1 behind it.

🧠 Key takeaways

  • QUIC is a transport built on UDP, in user space, because TCP couldn't be changed in kernels or past the devices in the network.
  • Its streams are ordered independently, so a lost packet delays only the streams it carried.
  • The transport and TLS 1.3 handshakes are one: a single round trip for a new connection and none for a resumed one.
  • A connection is named by a connection ID, not by addresses, so it survives a change of network.
  • Nearly all of each packet is encrypted, which protects users and keeps the protocol free to change.
  • Clients learn about HTTP/3 from Alt-Svc or DNS, race it against TCP, and fall back to HTTP/2 when UDP is blocked.
