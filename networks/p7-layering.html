Layering & Encapsulation

An HTTP request leaves your laptop as about 80 bytes of text and arrives at the server as the same 80 bytes. In between it was wrapped in a TCP header, an IP header and an Ethernet header, then rewrapped at every router. Each wrapper belongs to a different layer with one job, and each layer treats everything inside it as an opaque payload. That idea, encapsulation, is why you can change Wi-Fi to fibre or HTTP/1.1 to HTTP/2 without rewriting the rest. This chapter shows the mechanism and the places where it leaks.

Headers and payloads

Every protocol unit has the same shape: a header with fields the protocol needs (addresses, lengths, sequence numbers, flags), followed by a payload the protocol carries for someone else. The key rule is that a layer never interprets its payload. TCP doesn't know it's carrying HTTP; IP doesn't know it's carrying TCP beyond one number in its header that says which protocol to hand the payload to on arrival. Each header has such a "what's inside" field: Ethernet's EtherType (0x0800 = IPv4), IP's Protocol (6 = TCP, 17 = UDP), and TCP's and UDP's destination port (which program).

That's the whole trick. Because each layer only depends on the layer directly below it providing a service ("deliver this payload to that address"), layers can be replaced independently. The same TCP code runs over Ethernet, Wi-Fi, 5G or a VPN tunnel; the same IP runs under TCP, UDP or QUIC.

Down the stack and back up

On the sender, data goes down: each layer adds its header in front of what it was given. On the receiver it goes up: each layer reads and removes its own header, checks it, and hands the payload to the layer named in the "what's inside" field.

What a router changes

A router works at the internet layer, so it has to remove the link-layer frame to see the IP packet, and build a new frame for the next hop. The Ethernet header is therefore rewritten at every hop: the destination MAC becomes the next router's MAC and the source MAC becomes the router's own outgoing interface. In the IP header the router decrements the TTL and, in IPv4, recomputes the header checksum. Everything above IP, the TCP header and the payload, passes through untouched. End-to-end addresses (IP) stay the same all the way; hop-by-hop addresses (MAC) change at each hop.

Where layering leaks

Layering is a strong idea, not a perfect one. A few places where the layers have to know about each other come up again and again in real incidents:

  • MTU. Each link has a maximum frame payload, 1500 bytes on standard Ethernet. TCP must size its segments to fit (the MSS), so the transport layer has to learn a link-layer limit, either from configuration or by path MTU discovery, which relies on routers sending ICMP "fragmentation needed" messages back (Chapter 6). UDP can't split data itself, so an oversized datagram is fragmented by IP, and losing one fragment loses the whole datagram.
  • NAT. A home router is supposedly an internet-layer device, but NAT rewrites TCP and UDP ports, and must fix the transport checksum, which itself covers the IP addresses (Chapter 9).
  • Middleboxes. Firewalls, load balancers and proxies read headers several layers above their own, and they drop what they don't recognise. That "ossification" is why new transport protocols are hard to deploy, and why QUIC runs over UDP instead of being a new IP protocol (Chapter 18).
  • Performance. TCP's in-order delivery causes head-of-line blocking for HTTP/2 above it (Chapter 16), something no amount of application-layer cleverness can fix.
🧠
SSH works, the web page hangs: an MTU black hole

After a new site-to-site VPN goes live, engineers can SSH to servers in the other office and small API calls work, but downloading a file or loading a large page hangs forever. The tunnel adds about 60–80 bytes of headers, so the usable MTU inside it is around 1420, not 1500. The servers still send full 1500-byte packets with the "don't fragment" bit set; the VPN gateway can't forward them, and replies with ICMP "fragmentation needed", but a firewall on the way back drops all ICMP. The sender never learns, keeps retransmitting the same too-large segment, and the connection stalls. Small packets fit and work fine, which is what makes it so confusing. The usual fixes are to allow ICMP type 3 code 4 through, or to have the VPN gateway rewrite the MSS in passing SYN packets (iptables ... -j TCPMSS --clamp-mss-to-pmtu), a router reaching into the transport header to rescue the layer above.

⚠️
Common mistakes
  • Thinking MAC addresses travel end to end. They are replaced at every router; only IP addresses survive the whole path (NAT aside).
  • Ignoring header overhead for small messages. A 1-byte keystroke costs a 64-byte frame and 84 bytes of wire time: 1% efficiency.
  • Blocking all ICMP "for security". It breaks path MTU discovery and causes black holes.
  • Sending large UDP datagrams. Anything over ~1472 bytes on a 1500 MTU gets fragmented; keep UDP payloads under about 1200 bytes, as QUIC and DNS do.
  • Assuming layers are independent for debugging. A "network" symptom (a hang) can come from the link layer (MTU), and an "application" symptom from transport (head-of-line blocking).

Interview drill

Explain it simply: What is encapsulation, and what changes in a packet as it crosses a router?

How a strong answer sounds
Each layer takes the unit handed down from the layer above, treats it as an opaque payload, and puts its own header in front: application data inside a TCP segment, inside an IP packet, inside an Ethernet frame. Each header has a field saying what's inside, so the receiver can unwrap layer by layer. A router strips the Ethernet frame, looks at the IP destination to choose the next hop, decrements the TTL and recomputes the IPv4 header checksum, then builds a new frame with new source and destination MACs for the next link. The IP addresses, the TCP header and the payload are unchanged, unless the router also does NAT, which rewrites addresses and ports.

Deeper: What's the largest TCP payload a single 1500-byte-MTU Ethernet frame can carry, and why might Linux use less?

How a strong answer sounds
The MTU is the IP packet size the link allows, 1500 bytes. Subtract a 20-byte IPv4 header and a 20-byte TCP header and you get an MSS of 1460 bytes. Linux normally enables TCP timestamps, a 12-byte option on every segment, so the real payload per segment is 1448. IPv6's 40-byte header lowers it to 1440 (1428 with timestamps), and tunnels like VPNs or VXLAN lower the effective MTU further, which is why MSS clamping and path MTU discovery matter. The full frame is 1514 bytes plus the 4-byte FCS, and on the wire another 20 bytes of preamble and gap.

🧠 Key takeaways

  • Each layer adds a header in front of the unit from the layer above and treats it as an opaque payload.
  • A "what's inside" field in each header (EtherType, IP protocol, port) tells the receiver whom to hand the payload to.
  • Four layers: application (meaning), transport (process to process), internet (host to host), link (one hop).
  • Routers rewrite the link header and decrement TTL at every hop; IP addresses and everything above survive end to end.
  • Headers cost a fixed ~54+ bytes per frame, so tiny messages are inefficient and large ones are split at the MSS.
  • Layering leaks at the MTU, NAT and middleboxes; MTU black holes are the classic symptom.

Check your understanding

In what order do headers appear in an HTTP request frame, from the first byte on the wire?

The outermost wrapper is added last by the sender and comes first on the wire: the link header, then IP, then TCP, then the application bytes.

A packet crosses an ordinary router (no NAT). What changes?

MAC addresses are per hop, so the frame is rebuilt. IP addresses and the transport header pass through unchanged, except for TTL and checksum.

With a 1500-byte MTU, IPv4 and a TCP header without options, what's the maximum TCP payload per segment?

MSS = MTU − IP header (20) − TCP header (20) = 1460. With Linux's default 12-byte timestamp option it's 1448.

How does a receiving host know the payload of an IP packet is TCP and not UDP?

Every header names its payload's type for the layer above. EtherType says "IPv4", IP's Protocol says "TCP", and the port says which socket.

After a VPN goes live, SSH and small requests work but large downloads hang. What's the most likely cause?

The tunnel lowers the MTU. Full-size packets with "don't fragment" set are dropped, and if ICMP is filtered the sender never learns to send smaller ones. Small packets fit, so interactive traffic still works.
