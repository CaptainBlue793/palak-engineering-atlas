ARP: From IP to MAC

Your laptop wants to send a packet to 192.168.1.50. IP says where it's going, but the Ethernet frame it must travel in needs a destination MAC address, and nothing in the IP address tells you what that is. The Address Resolution Protocol fills the gap: shout "who has 192.168.1.50?" to the whole LAN and remember the answer. It's tiny, it runs before almost every first packet you send, and, because it believes whatever it's told, it's also one of the oldest ways to intercept other people's traffic.

Who has 192.168.1.50?

ARP (RFC 826, 1982) is a request–reply protocol carried directly in Ethernet frames with EtherType 0x0806, not in IP. When the kernel needs the MAC for an IP on its own network and doesn't have it cached, it:

  1. Queues the outgoing packet.
  2. Broadcasts an ARP request to ff:ff:ff:ff:ff:ff: "Who has 192.168.1.50? Tell 192.168.1.23", including its own MAC.
  3. Every host on the LAN receives it. The one that owns 192.168.1.50 sends a unicast ARP reply: "192.168.1.50 is at 00:1b:a9:44:3e:10". The others ignore it.
  4. The requester stores the answer in its neighbour cache (the ARP table) and sends the queued packet.

As an optimisation, the target also caches the requester's mapping from the request itself, because it's about to reply and will probably talk back. The packet is 28 bytes: hardware and protocol types, an operation code (1 request, 2 reply), and the sender's and target's MAC and IP addresses.

$ sudo tcpdump -i wlan0 -nn arp
14:02:11.512 ARP, Request who-has 192.168.1.50 tell 192.168.1.23, length 28
14:02:11.514 ARP, Reply 192.168.1.50 is-at 00:1b:a9:44:3e:10, length 46

$ ip neigh                                         # the neighbour (ARP) cache
192.168.1.1  dev wlan0 lladdr a4:2b:b0:c1:5e:01 REACHABLE
192.168.1.50 dev wlan0 lladdr 00:1b:a9:44:3e:10 REACHABLE
192.168.1.77 dev wlan0  FAILED                    # asked, nobody answered

The reply shows "length 46" because a received frame is padded to Ethernet's minimum. Linux tracks each entry through states: REACHABLE (recently confirmed, for 15–45 seconds), STALE (still used, but will be checked the next time it's needed), DELAY and PROBE (being checked with a unicast ARP), INCOMPLETE (request sent, no reply yet) and FAILED. On Windows and macOS, arp -a shows the same cache.

Off the subnet, you ARP for the gateway

This is the single most important thing to understand about ARP, and the most common interview trap. ARP only works within one broadcast domain. When the laptop sends to 8.8.8.8, it first does the AND-with-mask test (P2): 8.8.8.8 isn't on 192.168.1.0/24, so the packet goes to the default gateway. The laptop ARPs for 192.168.1.1, the gateway, and builds a frame with the gateway's MAC as destination and 8.8.8.8 as the IP destination. It never ARPs for 8.8.8.8, which would be pointless: nobody on the LAN owns it. Every router along the way then does the same ARP lookup for its own next hop (Chapter 5).

Gratuitous ARP and failover

  
A gratuitous ARP is an ARP that nobody asked for: a host broadcasts its own mapping ("192.168.1.1 is at 00:00:5e:00:01:01"). Hosts that already have an entry for that IP update it. It has three uses:

  
    
    
  • Announcing a move. When a floating IP moves to a standby server (keepalived, VRRP, Pacemaker) or a VM migrates, a gratuitous ARP updates every neighbour's cache and every switch's MAC table at once (Case Study 46).
    • 
    
  • Detecting duplicates. A host that brings up an address first asks for its own IP (an ARP probe); any reply means a conflict.
    • 
    
  • Refreshing caches after a network card is replaced.
    •

ARP spoofing

  
ARP has no authentication. Hosts accept replies they didn't ask for, and newer answers overwrite older ones. So an attacker on the same LAN can send a stream of forged replies saying "192.168.1.1 is at my MAC". The victim's cache is poisoned: it now frames everything for the internet to the attacker, who forwards it on to the real gateway (and poisons the gateway's view of the victim too). The victim notices nothing, and the attacker is a man in the middle, able to read and alter unencrypted traffic. Tools such as arpspoof and Bettercap make this a one-line command on any shared network.

  
Defences work at several layers. Managed switches can run Dynamic ARP Inspection, which checks ARP packets against the DHCP snooping table of which MAC was given which IP, and drops forgeries. Critical hosts can use static ARP entries. Monitoring (arpwatch) alerts on changed mappings. And end-to-end encryption makes the position far less useful: an attacker in the middle of a TLS connection sees ciphertext and can't present a valid certificate (Chapter 17), which is a large part of why "HTTPS everywhere" mattered on coffee-shop Wi-Fi.

The keepalived failover that worked on-premises and not in the cloud
A team moves a pair of HAProxy servers from their data centre to AWS, with keepalived managing a floating IP between them as before. In the data centre, failover took a second: the standby claims the IP and sends a gratuitous ARP, every neighbour updates its cache. In the VPC, the standby claims the IP, sends its gratuitous ARP, and nothing happens. Clients keep sending to the dead primary. VPCs don't carry broadcasts at all: the hypervisor answers ARP requests itself, from the VPC's own record of which IP belongs to which network interface, and it ignores gratuitous ARPs from instances. The fix is to make failover call the cloud API instead (reassign the secondary private IP or Elastic IP to the standby's interface, which keepalived can do from a notify script), or to replace the pair with the provider's load balancer. The same applies on Azure and Google Cloud. Cloud networks look like Ethernet to your instance but are software-defined underneath (Chapter 39).

  


  
⚠️
Common mistakes

    
    
      
  • Thinking a host ARPs for a remote IP. It ARPs for its gateway; the remote IP only appears in the IP header.
    • 
      
  • Blaming the remote server for "Destination Host Unreachable" on a local address. When the message comes from your own IP, your ARP got no reply: the host is off, on another VLAN, or the address is wrong.
    • 
      
  • Expecting gratuitous ARP to work in a cloud VPC. Use the provider's API to move the IP.
    • 
      
  • Treating a LAN as trusted. Anyone on it can poison ARP caches; encrypt anyway.
    • 
      
  • Forgetting stale caches after a change. Replace a server's NIC or MAC without a gratuitous ARP and neighbours keep sending to the old MAC until their entries expire.
    •

Interview drill

    
Explain it simply: Your laptop at 192.168.1.23/24 opens a connection to 93.184.215.14. Which ARP requests does it send?

    
How a strong answer sounds
It checks whether the destination is local: 93.184.215.14 AND 255.255.255.0 isn't 192.168.1.0, so it isn't. The packet must go to the default gateway, say 192.168.1.1. If the gateway's MAC isn't in the neighbour cache, the laptop broadcasts "who has 192.168.1.1?", gets a unicast reply with the gateway's MAC, caches it, and sends the SYN in a frame addressed to the gateway's MAC with 93.184.215.14 in the IP header. It never ARPs for 93.184.215.14. Usually the gateway is already cached, so there's no ARP at all.

    
Deeper: How does ARP spoofing work, and what would you deploy against it?

    
How a strong answer sounds
ARP has no authentication and hosts accept unsolicited replies, so an attacker on the LAN keeps sending forged replies mapping the gateway's IP to the attacker's MAC (and the victim's IP to the attacker's MAC towards the gateway). Both caches are poisoned and traffic flows through the attacker, who forwards it, so nothing visibly breaks. Network-side, I'd enable DHCP snooping with Dynamic ARP Inspection on access switches so forged ARPs are dropped, port security to limit MACs per port, and arpwatch-style monitoring. Host-side, static entries for critical gateways where practical. And I'd assume the LAN is hostile anyway: TLS everywhere, with certificate validation, so a man in the middle sees only ciphertext.

  


  

    
🧠 Key takeaways

    
    
      
  • ARP maps an IPv4 address on the local network to a MAC: broadcast request, unicast reply, cached answer.
    • 
      
  • For destinations off the subnet, the host ARPs for its gateway; remote IPs are never ARPed.
    • 
      
  • ip neigh shows the cache and its states: REACHABLE, STALE, PROBE, FAILED…
    • 
      
  • Gratuitous ARP announces a mapping: used for failover, migration and duplicate detection, and ignored in cloud VPCs.
    • 
      
  • ARP is unauthenticated, so spoofing gives a LAN attacker a man-in-the-middle position; DAI and encryption defend.
    • 
      
  • IPv6 replaces ARP with Neighbour Discovery over ICMPv6 and multicast.
    • 
    

  


  

    
Check your understanding

    


    

      
A laptop at 10.0.1.20/24 with gateway 10.0.1.1 sends a packet to 8.8.8.8. Its ARP cache is empty. What does it ARP for?

      

        
        
        
        
      

      
8.8.8.8 is off-subnet, so the frame goes to the gateway, and the laptop needs the gateway's MAC. The IP header still says 8.8.8.8.

    


    

      
How are an ARP request and its reply addressed?

      

        
        
        
        
      

      
The requester doesn't know the target's MAC, so it must broadcast. The target knows the requester's MAC from the request, so it replies directly.

    


    

      
What is a gratuitous ARP typically used for?

      

        
        
        
        
      

      
An unsolicited announcement updates every neighbour's cache (and switch's MAC table) at once, so traffic follows the IP to its new owner.

    


    

      
You ping 192.168.1.77 on your own /24 and get "From 192.168.1.23 icmp_seq=1 Destination Host Unreachable", where .23 is you. What happened?

      

        
        
        
        
      

      
The error comes from your own address: your kernel gave up after unanswered ARP requests (the entry is FAILED in ip neigh).

    


    

      
What does ARP spoofing let an attacker on the same LAN do?

      

        
        
        
        
      

      
Forged replies map the gateway's IP to the attacker's MAC. The attacker sees everything, but TLS traffic stays encrypted and can't be impersonated without a valid certificate.
