Load Balancers: L4 vs L7

One server isn't enough. It can't carry all the traffic, and when it fails or is restarted for a deploy the service would be gone. So there are many servers, and something has to stand in front and decide which one gets each piece of work, without sending any to a server that has died. That is a load balancer, and it comes in two kinds that are named after the layers of Chapter 1. A layer-4 balancer distributes connections and never looks inside them. A layer-7 balancer distributes requests and reads every one. The first is faster and simpler, the second can make smarter choices, and large systems use both, one behind the other.

L4: packets and connections

A layer-4 balancer owns an address, the virtual IP, that clients connect to. When the first packet of a new connection arrives, it picks a back end and remembers the choice, keyed by the connection's 5-tuple. Every later packet with that 5-tuple goes to the same back end. Most often it is a NAT device working in reverse (Chapter 9): it rewrites the destination address of each packet to the chosen server and rewrites the replies on the way back.

It doesn't complete a handshake of its own, decrypt anything or parse anything. To it, a connection is addresses, ports and a stream of packets. That makes it fast, at millions of connections on one machine with microseconds of added delay, and indifferent to the protocol: HTTP, a database, a game's UDP traffic and TLS it can't read all look the same. The other side of that is what it can't do. It can't route by URL, it can't tell a healthy response from a page of errors, and since it chooses once per connection, a client holding one long connection sends every request on it to the same server (Chapter 22's use case).

L7: HTTP-aware routing

A layer-7 balancer is a reverse proxy (Chapter 23) with a pool behind it. It terminates the client's TCP and TLS, reads each HTTP request, and makes its choice per request, using anything in the request:

# Routing rules of a layer-7 balancer (Envoy and nginx express the same ideas)
host api.shop.example,  path /v2/*            →  pool orders-v2
host api.shop.example,  header X-Beta: 1      →  pool orders-canary        # 1% of users try the new version
host api.shop.example                         →  pool orders
host static.shop.example                      →  pool cdn-origin
anything else                                 →  404

Large sites stack them. A few layer-4 balancers take everything from the internet and spread it over a fleet of layer-7 balancers, which do the TLS and the routing. The layer-4 tier makes the layer-7 tier scalable and replaceable, and the layer-7 tier makes the right decision for each request.

Algorithms

Hashing with a plain "hash modulo the number of servers" has a nasty property: add or remove one server and nearly every key moves. Consistent hashing arranges things so that only about one share in N moves, which is what makes hashing usable for caches. Stickiness from a cookie that the balancer sets is another form of the same idea.

Things to notice. With servers and requests all alike, every algorithm does well: a 99th-percentile latency of about 35 ms. Make server C three times slower and round robin goes on giving it a quarter of the requests, which is more than it can finish. Its queue grows for as long as the test runs, to over 400 requests, and 641 requests take more than a second, while the other three servers have capacity to spare. Least connections sees the pile-up and sends C only 11% of the work, and the 99th percentile is 110 ms. Two random choices does nearly as well, at 120 ms, while looking at only two servers each time. Hashing by client behaves much like round robin until one client dominates. Then that client's server receives over half of all the requests and is overloaded, however idle the others are. That is the price of stickiness.

Health checks

A balancer must stop sending work to a server that can't do it. It finds out in two ways.

HowThe balancer sends its own probe every few seconds: a TCP connection, or GET /healthz expecting a 200The balancer watches real traffic and ejects a server after a run of errors or timeouts
DetectsA dead process or host, even with no trafficFailures that only real requests trigger

# A typical active check
health_check:  GET /healthz   interval 10s   timeout 2s   unhealthy_threshold 3   healthy_threshold 2

# Worst case after a server dies:
#   up to 10 s until the next probe  +  2 more failed probes at 10 s each  =  about 30 s of requests sent to a dead server

Thirty seconds of failures for a share of users is the default behaviour of many balancers, and it is why health checks alone aren't enough. Retries of idempotent requests on another server (Chapter 15) and passive ejection cover the gap. Two more points decide whether health checks help or hurt:

  • What the check tests. A check that only proves the process is listening will pass on a server whose application is broken. A check that also tests the database will fail on every server at once when the database has a brief problem, and a balancer with no healthy servers has nowhere to send anything. Keep the check to what this server alone is responsible for, and let balancers "fail open" when everything looks down.
  • What happens to connections in progress. A server being removed on purpose should be drained: given no new requests, and allowed to finish the ones it has (Chapter 46 follows a failover in detail).

Direct server return

In the usual arrangement, replies pass back through the balancer. For most services, responses are many times larger than requests, so the balancer spends most of its capacity carrying traffic about which it has no decision to make. Direct server return removes that. The balancer handles only packets from the client, and servers send their replies straight to the client.

The balancer now sees one direction only. It can't terminate TLS, read responses or count bytes out, so this is strictly a layer-4 technique, and it takes care to configure. It is how the front tier of very large systems carries enormous volumes on ordinary machines.

🧠
Maglev: Google's balancer is a program on ordinary servers

For years, load balancing at the edge of a large network meant expensive dedicated appliances, deployed in pairs, with one working and one waiting. In 2016 Google described what it had been using since 2008 in their place: Maglev, a layer-4 balancer that is just software on ordinary Linux machines. Three ideas from this chapter and the next few make it work. The routers in front spread incoming packets over all the Maglev machines with equal-cost routing (Chapter 30), so there is no primary and no standby: capacity is added by adding machines, and losing one loses a fraction. Any Maglev machine may therefore receive any packet of any connection, so they must all choose the same back end without consulting each other. They do it with a form of consistent hashing over the 5-tuple, built so that the choice barely changes when back ends come and go. And replies bypass Maglev completely, by direct server return, which lets each machine handle only the small inbound packets and fill a 10-gigabit link with them. A balancer built this way has no single point of failure and no shared state. Similar designs were later published by Facebook and GitHub, and the cloud providers' network balancers work on the same principles.

⚠️
Common mistakes
  • Balancing HTTP/2 or gRPC at layer 4. One long connection pins all of a client's requests to one server.
  • Round robin over servers of different speeds. The slowest gets the same share and builds a queue. Use least connections or weights.
  • Health checks that depend on shared services. One database hiccup marks every server down at once.
  • Slow failure detection with no retries. Interval times threshold is how long users are sent to a dead server.
  • Sticky sessions as a substitute for shared state. Load becomes uneven, and a server's death logs its users out. Keep sessions in a store.
  • Forgetting the balancer is a point of failure itself. It needs redundancy too, by routing, DNS or a managed service.

Interview drill

Explain it simply: What is the difference between a layer-4 and a layer-7 load balancer?

How a strong answer sounds
A layer-4 load balancer works at the transport level. It sees IP addresses and ports, picks a back end when a connection starts, and then forwards every packet of that connection to the same back end, typically by rewriting addresses. It doesn't read the payload, so it works for any TCP or UDP protocol, can pass TLS through untouched, and is extremely fast, but it balances connections, not requests, and can't route on content. A layer-7 load balancer is a reverse proxy for a specific protocol, usually HTTP. It terminates the client's TCP and TLS, parses each request, and chooses a back end per request, so it can route by host, path, header or cookie, spread the streams of an HTTP/2 or gRPC connection across back ends, retry failed requests, and apply things like rate limits and authentication. It costs more CPU and adds a little latency. Big deployments use both: layer 4 at the edge for raw scale and resilience, feeding a tier of layer-7 proxies.

Deeper: After a deploy, p99 latency rises sharply although average CPU across the fleet is low. The balancer uses round robin. What would you suspect?

How a strong answer sounds
Round robin assumes all back ends are equal. If one or a few are slower, say an instance on a noisy host, one still warming its caches after the deploy, or one of a smaller instance type, they still receive the same share of requests. They can't keep up, their queues grow, and the requests routed to them are slow. That shows up as a bad p99 while the fleet's average looks fine, because the healthy majority is underused. I'd look at per-instance latency and in-flight request counts, not fleet averages; an outlier or two would confirm it. Fixes: switch to least-connections or least-request balancing, which automatically sends less to a server that is falling behind; add passive outlier detection so that a persistently slow or erroring instance is ejected; use slow start so that new instances ramp up rather than taking a full share cold; and check the health check, since a server can be healthy enough to pass a shallow check and still be far too slow. If the balancer is layer 4 and the traffic is HTTP/2 or gRPC, I'd also check for connection-level imbalance.

🧠 Key takeaways

  • A layer-4 balancer distributes connections by address and port, reads nothing, and works for any protocol at very high speed.
  • A layer-7 balancer is a reverse proxy that distributes requests, and can route, retry and inspect them, at a cost in CPU.
  • Round robin suits identical servers. Least connections adapts to slow servers and uneven requests. Hashing gives stickiness and risks hot spots.
  • Health checks remove dead servers, but only after interval times threshold. Retries and passive ejection cover the gap.
  • Keep health checks local to the server, drain servers before removing them, and make the balancer itself redundant.
  • With direct server return, replies bypass the balancer, which is how software balancers carry very large volumes.

Check your understanding

What does a layer-4 load balancer use to choose a back end?

It works on the 5-tuple and never parses the payload, which is why it is fast and protocol-agnostic.

You want /api/* to go to one pool of servers and /images/* to another, on the same host name. What do you need?

The path is inside the HTTP request, behind TLS. Only something that terminates the connection can see it.

One of four back ends is three times slower than the others. Why does least connections cope better than round robin?

In-progress count is a live measure of how a server is keeping up. Round robin ignores it.

A health check runs every 5 seconds and marks a server down after 3 failures in a row. A server crashes. For roughly how long can it keep receiving requests?

Up to one interval before the next probe, then two more failed probes: interval times threshold.

In direct server return, which path do the server's responses take?

The balancer handles only the client's inbound packets, so the large response traffic never touches it.
