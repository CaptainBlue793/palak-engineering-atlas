VPNs & Tunnels: IPsec, WireGuard

A company has an office network of private addresses and a cloud network of private addresses, with the public internet between them. Those addresses can't be routed across it, and nothing sent across it is private. The fix is one of the oldest tricks in networking: take a whole packet, addresses and all, and put it inside another packet that the internet can carry. That is a tunnel. Encrypt what's inside and it is a VPN. The idea is simple and is used everywhere, from a laptop reaching the office to the virtual networks inside every cloud. It has one persistent side effect, which is that the wrapper takes up room. A packet that was exactly the largest size the path allows is, once wrapped, too big, and what happens next is one of networking's classic puzzles: a connection where small things work and large things hang.

Tunnelling and encapsulation

On each gateway the tunnel is a virtual network interface, with a name such as wg0 or tun0. Sending a packet "into the tunnel" means the routing table chose that interface for it (Chapter 5). Which traffic is protected is therefore a routing decision, and a wrong route sends traffic outside the tunnel without any error. Wrapping and encrypting are separate things, and not every tunnel does both:

TunnelWraps the inner packet inEncryptedBytes added (IPv4 outside)Typical use

IPsec: transport and tunnel mode

IPsec is the long-established standard, built into every operating system, router and cloud. It is a family of protocols. IKE runs first, over UDP port 500: the two ends authenticate each other, with certificates or a shared secret, and agree keys by Diffie–Hellman (Chapter 17). Then ESP carries the data, encrypted and authenticated, in one of two modes:

Transport modeTunnel mode
What is encryptedThe payload of the original packet: the TCP or UDP segmentThe entire original packet, header included
IP header on the wireThe original oneA new outer one, between the two gateways
An observer learnsThe real source and destination hostsOnly the gateways' addresses
BetweenTwo hosts that both run IPsecTwo gateways, on behalf of whole networks
Used forProtecting traffic between specific servers; under other tunnelsNearly every site-to-site VPN

ESP is its own IP protocol, number 50, with no port numbers, so it can't cross a NAT (Chapter 9). In practice it is nearly always wrapped once more in UDP port 4500. IPsec works, and it is hard to live with: decades of options mean that both ends must be configured with matching ciphers, lifetimes and descriptions of which traffic is covered, and a mismatch in any of them produces a tunnel that silently carries nothing.

WireGuard

WireGuard, which entered the Linux kernel in 2020, is a reaction to that complexity. It is a few thousand lines of code where the alternatives are hundreds of thousands. It has one set of modern ciphers and nothing to negotiate. And its whole configuration is a list of peers:

# /etc/wireguard/wg0.conf on the office gateway
[Interface]
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=
Address    = 10.99.0.1/24
ListenPort = 51820

[Peer]                                             # the cloud gateway
PublicKey  = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
Endpoint   = 203.0.113.9:51820
AllowedIPs = 10.2.0.0/16
PersistentKeepalive = 25

[Peer]                                             # Asha's laptop, wherever it is
PublicKey  = TrMvSoP4jYQlY6RIzBgbssQqY3vxI2Pi+y71lOWWXX0=
AllowedIPs = 10.99.0.7/32

A peer is a public key. AllowedIPs does two jobs with one list, which its author calls cryptokey routing:

  • Sending: a packet for 10.2.0.9 matches the first peer's AllowedIPs, so it is encrypted with that peer's key and sent to that peer's current endpoint.
  • Receiving: a packet that decrypts correctly with a peer's key is accepted only if its inner source address is within that peer's AllowedIPs. A valid peer can't pretend to be an address it wasn't given.
$ sudo wg show
interface: wg0

  listening port: 51820

peer: xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
  endpoint: 203.0.113.9:51820
  allowed ips: 10.2.0.0/16
  latest handshake: 47 seconds ago              # keys are renewed every two minutes while traffic flows
  transfer: 1.82 GiB received, 644.10 MiB sent
  persistent keepalive: every 25 seconds

Three properties follow from the design. It runs over UDP and sends nothing unless there is data, apart from that optional keep-alive, which exists to hold a NAT entry open. It never answers a packet it can't authenticate, so to a port scanner a WireGuard endpoint looks like a closed port. And a peer has no fixed address: if a valid packet arrives from a new address, replies go there from then on. A laptop can move from Wi-Fi to mobile data and its tunnel continues, the same idea as QUIC's connection migration (Chapter 18).

MTU problems in tunnels

A standard Ethernet link carries packets of up to 1,500 bytes, the MTU (P7). A tunnel's wrapper has to fit inside that too. If the wrapper is 60 bytes, the largest inner packet is 1,440 bytes, and that must be the MTU of the tunnel interface. Hosts that send through the tunnel need to find out, and there are three ways they can:

MechanismHow it worksFails when
The interface's MTU is set correctlyThe sender's own stack never builds a packet too big for the tunnelThe sender is another machine behind the gateway, still using 1,500
Path MTU discoveryPackets are sent marked "don't fragment". A router that can't forward one drops it and returns an ICMP message, "fragmentation needed, next MTU 1440". The sender shrinks its packetsA firewall on the way drops ICMP, and the message never arrives
MSS clampingThe tunnel's router edits the MSS option in passing TCP handshakes, so both ends agree to small segments from the startThe traffic isn't TCP

When all three fail, the result is a black hole. Small packets pass. Every full-sized packet is dropped, silently, every time it is retransmitted. The TCP handshake succeeds, a login prompt appears, a short command works, and the first large response hangs for ever.

    The inner packet is TCP over IPv4, 40 bytes of headers. IPsec's figure assumes AES-GCM with NAT traversal and a few bytes of padding. VXLAN's includes the 14-byte inner Ethernet header it carries.

    Things to notice. With WireGuard over IPv4 on a 1,500-byte link, 60 bytes go on wrapping, the tunnel's MTU is 1,440, and a TCP segment can carry 1,400 bytes of data where it would normally carry 1,460. Change the outside to IPv6 and 20 more bytes go, which is why WireGuard's default MTU is 1,420: it is safe either way. Now leave the sending host at 1,500. Its full-sized packet becomes 1,560 bytes when wrapped and can't be sent. With ICMP working, the host is told and adjusts after one lost packet. With ICMP blocked, the host is never told, and you have the black hole: every large packet dropped, with no error anywhere. MSS clamping rescues TCP without needing ICMP at all, which is why it is on nearly every VPN router.

    $ ping -M do -s 1472 10.2.0.9            # 1472 + 28 bytes of headers = 1500, with "don't fragment" set
ping: local error: message too long, mtu=1440
$ ping -M do -s 1412 10.2.0.9            # 1412 + 28 = 1440: this size passes
64 bytes from 10.2.0.9: icmp_seq=1 ttl=63 time=24.1 ms

$ tracepath 10.2.0.9                      # reports the path MTU hop by hop
 1:  10.1.0.1        0.4ms
 2:  10.99.0.2      24.3ms pmtu 1440

# The usual cure on a Linux VPN router: fix the MSS of every TCP handshake passing through
$ iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu

    Cloudflare: the ICMP message that went to the wrong server

    In 2015 Cloudflare's engineers described a version of this problem with no firewall in it. Some visitors, mostly those whose own connection ran through a tunnel with a smaller MTU, could open connections to Cloudflare's sites and then got nothing back. The cause lay in how a large site is built. Many servers share one anycast address (Chapter 26), and a router in front spreads packets among them by hashing each packet's addresses and ports, so that all the packets of one connection reach the same server (Chapter 24). A server sent a full-sized response. A router far away, at the entrance to the visitor's tunnel, couldn't forward it and correctly sent back an ICMP "fragmentation needed" message. But an ICMP packet is a different packet with a different header. The router in front of the servers hashed it like any other and delivered it to some server, almost never the one that owned the connection. That server had no idea what the message referred to and threw it away. The server that needed it kept resending the same oversized packet, and the visitor's page never loaded. Every part was working as designed, and path MTU discovery was broken anyway. Cloudflare's fix was a small program that takes any such ICMP message arriving at one server and rebroadcasts it to all the servers behind that router, so that the one that cares will see it. Path MTU discovery depends on a message returning to the exact machine that sent the packet, and modern networks contain many things that break that assumption without anyone deciding to.

    ⚠️
    Common mistakes
    • Blocking all ICMP at a firewall. It breaks path MTU discovery. Allow "fragmentation needed" (and "packet too big" for IPv6).
    • Leaving a tunnel interface at MTU 1500. Or leaving the hosts behind a VPN router to find out the hard way. Set the MTU and clamp the MSS.
    • Diagnosing "the VPN is slow" without testing packet size. If small requests work and large transfers stall, test with a don't-fragment ping.
    • Assuming a tunnel is encrypted. GRE, IP-in-IP and VXLAN are wrappers only.
    • Overlapping AllowedIPs, or an over-broad one. It is the routing table and the access list at once. 0.0.0.0/0 on a peer sends everything to it.
    • Forgetting the keep-alive behind NAT. An idle WireGuard peer's NAT entry expires, and nothing can reach it until it sends again.

    Interview drill

    Explain it simply: How does a VPN tunnel work?

    How a strong answer sounds
    A VPN creates a virtual network interface on each end. The routing table sends packets for the remote private network to that interface. The VPN software takes each such packet, the whole thing including its IP header, encrypts and authenticates it, and puts it in the payload of a new packet addressed from this gateway's public address to the other gateway's public address, typically over UDP. The internet routes that outer packet normally and sees only the two gateways. The far end verifies and decrypts the payload, recovers the original packet and forwards it on its local network. Replies take the same path in reverse. So the two private networks appear directly connected. Keys are agreed up front by an authenticated key exchange, IKE for IPsec or WireGuard's handshake, and rotated regularly. The main operational consequence is overhead: the extra headers reduce the MTU available inside the tunnel, so the tunnel's MTU and the TCP MSS have to be lowered to match.

    Deeper: Over a new site-to-site VPN, ping and SSH logins work, but copying a large file hangs after a few kilobytes. What is your diagnosis?

    How a strong answer sounds
    That pattern, small packets fine and large ones stalled, is an MTU black hole. The tunnel adds headers, so the largest inner packet it can carry is smaller than 1,500 bytes, perhaps 1,440. The hosts still believe the path MTU is 1,500. During the SSH login the packets are small. When the copy starts, TCP sends full-sized segments with the don't-fragment bit set. The gateway can't fit them in the tunnel, drops them and sends back ICMP "fragmentation needed". If that ICMP message is blocked by a firewall, or lost some other way, the sender never learns, keeps retransmitting the same size, and the transfer hangs. I'd confirm with a don't-fragment ping at increasing sizes across the tunnel to find the largest that passes, and with tracepath. Fixes, in order: set the tunnel interface's MTU correctly; enable MSS clamping on the VPN gateways so that TCP handshakes passing through advertise a segment size that fits; and allow the necessary ICMP types through the firewalls so that path MTU discovery works for non-TCP traffic too.

    🧠 Key takeaways

    • A tunnel carries a whole packet as the payload of another. A VPN is a tunnel whose payload is encrypted and authenticated.
    • What enters a tunnel is decided by the routing table, through a virtual interface.
    • IPsec negotiates keys with IKE and carries data in ESP: transport mode protects a payload between hosts, tunnel mode a whole packet between gateways.
    • WireGuard identifies peers by public key, and AllowedIPs is both its routing table and its source filter. It is silent to anyone unauthenticated.
    • Wrapping costs bytes, so the MTU inside a tunnel is smaller: 1,440 for WireGuard over IPv4 on a 1,500-byte link.
    • If hosts don't learn that, large packets vanish while small ones pass. Set the MTU, clamp the MSS, and don't block ICMP.

    What does IPsec's tunnel mode protect that transport mode doesn't?

    Tunnel mode encrypts the entire original packet and adds a new header between gateways.

    In WireGuard, a peer is configured with AllowedIPs = 10.99.0.7/32. A packet arrives that decrypts correctly with that peer's key, with inner source address 10.99.0.8. What happens?

    The list filters what a peer may send as, as well as deciding what is routed to it.

    A WireGuard tunnel runs over IPv4 on links with an MTU of 1,500. What is the largest TCP payload per packet inside it, with no fragmentation?

    1,500 less 60 of wrapping leaves a 1,440-byte inner packet, and 40 of that is the inner IP and TCP headers.

    Through a VPN, web pages with little content load and large downloads freeze. Which cause fits best?

    An MTU black hole: size is the only difference between what works and what doesn't.
