WebSockets & Server-Sent Events

HTTP has one shape: the client asks and the server answers. That is fine for fetching a page and wrong for a chat message, a stock price, a notification or a collaborator's cursor, where the news starts at the server and the client doesn't know when to ask. For twenty years the web has found ways round this, from asking over and over, to holding a request open, to protocols built for the job. Each one is still in use, because each has a different cost and suits a different situation. This chapter covers the four of them, what the two modern ones look like on the wire, and what changes for a server when every user holds a connection open all day.

Polling and long polling

The simplest way to get news from a server is to keep asking. With polling, the client sends "anything new?" every few seconds. It needs nothing special from the server, and it wastes nearly everything it does: most answers are "no", each one costs a full set of request and response headers, and news waits, on average, half the polling interval before the next request collects it. Polling faster cuts the delay and multiplies the waste.

Long polling is a neat improvement. The client asks, and if the server has nothing new it simply doesn't answer. It holds the request open until something happens, or until a timeout of about 30 seconds, then responds, and the client immediately asks again. News is delivered the moment it exists, and it is all plain HTTP. The costs are a held-open request per client, a new request with full headers for every message, and messages that pile up while the client is between requests.

The WebSocket upgrade

A WebSocket is a TCP connection, opened by an HTTP request, on which either side can send a message at any time. It starts with an ordinary HTTP/1.1 request carrying an offer to change protocol:

GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://example.com
Cookie: session=…

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

After the 101 response, HTTP is finished on that connection. The same TCP connection, and the same TLS session if the URL was wss://, now carries WebSocket frames in both directions. Starting as HTTP is what let WebSockets work through the existing web: the same port 443, the same cookies for authentication, and the same proxies and load balancers, provided they understand the upgrade. The odd-looking key and accept headers aren't security. The server hashes the client's key with a fixed string to prove that it really speaks WebSocket and isn't a confused cache replaying an old response.

import base64, hashlib
key = "dGhlIHNhbXBsZSBub25jZQ=="
magic = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"             # the same constant in every implementation
base64.b64encode(hashlib.sha1((key + magic).encode()).digest())  # b's3pPLMBiTxaQ9kYGzzhZRbK+xOo='

Frames and ping/pong

TCP gives a byte stream with no message boundaries (Chapter 8). WebSocket puts them back. Each message travels in one or more frames, each with a small header:

FieldSizeMeans
FIN and opcode1 byteIs this the last frame of the message, and what kind: text, binary, close, ping or pong
Mask bit and length1 byte, plus 2 or 8 more for long payloadsThe payload's size, which is the framing
Masking key4 bytes, client to server onlyThe client scrambles its payloads with a random key, so that a hostile page can't make them look like HTTP to a cache in the path
PayloadThe messageWhatever the application sends: JSON, Protobuf, bytes

So a short message costs 2 bytes of overhead from the server and 6 from the client, where an HTTP request costs several hundred in headers. Three of the opcodes are for control. A close frame starts an orderly shutdown with a status code. Ping and pong are heartbeats, and they aren't optional in practice, for two reasons from earlier chapters:

  • Things in the path forget idle connections. NAT gateways and load balancers drop a connection that has been silent for a minute or a few minutes (Chapter 9). A ping every 20 to 30 seconds keeps it in their tables.
  • A dead peer is silent. If a phone loses its signal, no FIN is sent, and the server's socket looks healthy indefinitely. A ping that gets no pong is how each side finds out.

Server-Sent Events

Many applications only need the server-to-client half: a feed, a progress bar, a notification count, a model's answer appearing word by word. For those there is something simpler than a WebSocket. With Server-Sent Events (SSE), the client makes a normal HTTP request and the server gives a normal HTTP response that never ends. It keeps writing small text records down the open response as things happen:

GET /events HTTP/1.1
Accept: text/event-stream
Last-Event-ID: 41                       # sent by the browser when it reconnects

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 42
event: price
data: {"symbol":"ACME","price":101.25}
                                        # a blank line ends each event
id: 43
event: price
data: {"symbol":"ACME","price":101.40}

: keep-alive                            # a comment line, sent every 15 s so that the connection is never idle
// In the browser, the whole client:
const es = new EventSource("/events");
es.addEventListener("price", (e) => render(JSON.parse(e.data)));
// If the connection drops, the browser reconnects by itself and sends Last-Event-ID: 43

Because it is plain HTTP, SSE passes through every proxy, uses ordinary authentication, and travels as one stream of an HTTP/2 connection alongside the page's other requests. The browser reconnects on its own and tells the server the last event it saw, so the server can replay what was missed. Its limits are that it is one-way, and text only. One trap remains on HTTP/1.1, where an open event stream uses up one of the browser's six connections to that host (Chapter 15).

A model: each HTTP request and response costs 700 bytes of headers, a WebSocket frame from the server 2 bytes, an SSE event about 20 bytes of field names, and both kinds of stream send a heartbeat every 15 seconds. The events' own content is the same in every case and isn't counted. Network delay is ignored.

Things to notice, with five events in the minute. Polling every 5 seconds makes 12 requests, of which 7 bring back nothing, and each event waits 3 seconds on average. Polling every second cuts the wait to about 0.6 seconds and costs 60 requests, 42 KB of headers to deliver five small messages. Long polling delivers at once with 6 requests. SSE and WebSocket deliver at once with one. Now make the server busy. Long polling falls apart: each of 120 events needs its own request and response, 84 KB of headers in all, twice what polling every second cost. The streams send the same 120 events on one connection for a few kilobytes at most. That is the case they were built for.

Scaling many open connections

A request-and-response service can forget each client between requests. A push service can't, and that changes how it is built and run.

  • Every user is an open socket. Each costs a file descriptor and some kilobytes of kernel buffers and application state, all day. Limits on open files and on memory per connection become the capacity plan.
  • Connections are sticky by nature. A load balancer chooses a server once, when the connection opens, and the connection then stays there for hours. New servers get no load until clients reconnect.
  • The user and the event are on different machines. A message for a user arrives at one server, and their socket is on another. Push systems put a publish-and-subscribe layer behind the connection servers so that any server can deliver to any user.
  • Every deploy is a mass disconnection. Restart a server and its hundred thousand clients all reconnect at the same instant, to servers that are also restarting. Clients must wait a random, growing time before reconnecting, and servers should drain connections gradually.
  • Slow consumers must be dealt with. A client on a bad link stops reading, its TCP window closes (Chapter 12), and messages queue in the server's memory. Bound each client's queue, and drop or disconnect the ones that fall behind.
🧠
WhatsApp: two million connections on one machine

In January 2012 WhatsApp's engineers published a short post with a screenshot from one of their servers. It showed more than two million TCP connections open at once on a single machine, a server with 24 cores and 96 GB of memory. A few months earlier they had been pleased to reach one million. Each connection was a phone holding a long-lived session open so that messages could be pushed to it the moment they were sent, the same job as a WebSocket. The work to get there was almost entirely in the operating system and the runtime. They raised the limits on open files and sockets, cut the memory the kernel kept per connection, and removed points in the network stack and in the Erlang runtime where millions of connections contended for one lock. The arithmetic shows why memory per connection is the number that matters: at 2 million connections, every extra kilobyte each costs another 2 GB of RAM. The company served hundreds of millions of users with a few dozen engineers and a small fleet of such machines. An idle connection, managed with care, is very cheap, and what limits a push service is how many it can hold.

⚠️
Common mistakes
  • No heartbeat. Idle connections are silently dropped by NATs and load balancers, and dead clients are never noticed.
  • Reconnecting immediately, in a loop. After an outage every client stampedes back at once. Use exponential backoff with random jitter.
  • Assuming a reconnect loses nothing. Messages sent while the client was away are gone unless you number them and replay from the last one seen.
  • Forgetting the load balancer's idle timeout. A 60-second default kills quiet connections. Raise it, or ping more often than that.
  • Using a WebSocket when the data flows one way. SSE is simpler, reconnects by itself and is ordinary HTTP.
  • Unbounded send queues per client. One slow phone can hold megabytes of your server's memory.

Interview drill

Explain it simply: How does a WebSocket connection get established, and how does it differ from HTTP?

How a strong answer sounds
It begins as an HTTP/1.1 GET request with the headers Upgrade: websocket and Connection: Upgrade, plus a random Sec-WebSocket-Key. If the server agrees, it replies with 101 Switching Protocols and a Sec-WebSocket-Accept value derived from the key. From then on the same TCP connection, over TLS for wss, is no longer HTTP: both sides exchange WebSocket frames, each with a small header giving the opcode and payload length, so message boundaries are preserved. The differences from HTTP are that it is full duplex and long-lived. Either side can send at any time without a request, the per-message overhead is a few bytes instead of hundreds of bytes of headers, and the connection stays open, so it needs ping and pong frames to keep intermediaries from timing it out and to detect dead peers. It also makes the server stateful: each client is an open connection pinned to one server.

Deeper: You are designing live notifications for ten million users. Would you use polling, SSE or WebSockets, and what are the hard parts?

How a strong answer sounds
Notifications flow from server to client, so I'd start with Server-Sent Events: a plain HTTP response that stays open, with automatic reconnection and Last-Event-ID for resuming, multiplexed on HTTP/2. I'd choose WebSockets only if the client also needs to send frequently on the same channel, and I'd keep long polling as a fallback for networks that break streaming. Polling would mean millions of mostly empty requests a second, or long delays. The hard parts are operational. Ten million open connections need a fleet of connection servers sized by memory and file descriptors per connection, with kernel limits raised. A user's connection is on one particular server, so there has to be a routing layer, typically publish and subscribe keyed by user, to get an event to the right server. Idle timeouts in load balancers and NATs require heartbeats. Deploys and failures disconnect huge numbers of clients at once, so clients need jittered exponential backoff and servers need gradual draining. Delivery isn't guaranteed across reconnects, so events need IDs and a short replay buffer. And slow clients need bounded queues so they can't exhaust server memory.

🧠 Key takeaways

  • HTTP can't push. Polling asks repeatedly and wastes most requests; long polling holds a request open until there is news.
  • A WebSocket starts as an HTTP request with an Upgrade header, and after the 101 response it is a two-way stream of small frames.
  • Frames restore message boundaries at a cost of 2 to 6 bytes. Ping and pong keep the connection alive and detect dead peers.
  • Server-Sent Events are an HTTP response that never ends: one-way, text, with reconnection and resume built into the browser.
  • Use SSE for server-to-client streams and WebSockets when both sides talk. Polling is for rare checks.
  • Open connections make servers stateful: capacity is memory per connection, and reconnect storms, routing and slow clients need design.

Check your understanding

A client polls every 10 seconds for new messages. On average, how long does a new message wait before the client receives it?

A message arrives at a random point in the interval, so it waits half of it on average, and up to all of it.

What is the first thing sent on a new WebSocket connection?

It begins as HTTP so that it can use the same ports, proxies and cookies, then changes protocol on the same connection.

A WebSocket carries a message only every ten minutes or so, and users report that it "stops working" after a while. What is the likely cause?

Idle timeouts are typically a minute to a few minutes. A ping every 20 to 30 seconds keeps the path's state alive.

A dashboard needs live updates from the server and never sends anything back. Which fits best?

SSE does exactly this with less machinery. A server can't start an HTTP request to a browser.

A deploy restarts servers holding 400,000 WebSocket connections. What should clients do to avoid overloading the service?

A fixed delay only moves the stampede. Random jitter spreads it out, and backoff eases the load while the service recovers.
