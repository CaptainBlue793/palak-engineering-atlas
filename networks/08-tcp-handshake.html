TCP: The Handshake & the Byte Stream

IP delivers packets that can be lost, duplicated or reordered, and UDP passes that straight through to the application. TCP hides all of it. A program writes bytes into one end of a connection and the same bytes come out of the other end, in order, exactly once, or the connection fails. Nearly everything you use is built on that promise: HTTP, databases, SSH, email. This chapter covers how a connection starts and what it carries: the three packets of the handshake, the sequence numbers that everything else in TCP depends on, and the fact that surprises every new network programmer, that TCP has no idea where your messages begin and end.

The three-way handshake

Before any data moves, the two ends exchange three small packets with no payload. TCP calls its packets segments.

The handshake does two jobs. Each side chooses a starting sequence number and has it confirmed by the other, and each side proves it can both send to and receive from the other. Three segments is the minimum for that: a number each way, and a confirmation each way, with the server's number and its confirmation sharing one segment. Here it is in a capture:

$ sudo tcpdump -ni eth0 -S 'host 93.184.216.34 and tcp port 443'
10:14:07.100211 IP 10.0.0.5.51000 > 93.184.216.34.443: Flags [S], seq 2871554019, win 64240, options [mss 1460,sackOK,TS val 811 ecr 0,nop,wscale 7], length 0
10:14:07.182654 IP 93.184.216.34.443 > 10.0.0.5.51000: Flags [S.], seq 1594837211, ack 2871554020, win 65535, options [mss 1460,sackOK,TS val 907 ecr 811,nop,wscale 9], length 0
10:14:07.182701 IP 10.0.0.5.51000 > 93.184.216.34.443: Flags [.], ack 1594837212, win 502, length 0

tcpdump abbreviates the flags: S is SYN, . is ACK, P is PSH (data to hand to the application now), F is FIN and R is RST. Two more things are visible. The SYN-ACK arrived 82 ms after the SYN, which is the round-trip time, measured for free. And both SYNs carry options, the only chance the two ends get to agree on them: the largest segment each will accept (mss), whether selective acknowledgements are allowed (sackOK, Chapter 11), and a multiplier for the window field (wscale, Chapter 12).

Sequence and acknowledgement numbers

TCP numbers bytes, not packets. Every byte a side sends has a 32-bit sequence number, one more than the byte before it. Two fields in each segment's header carry the bookkeeping:

Sequence numberAcknowledgement number
MeansThe number of the first byte of data in this segmentThe number of the next byte I expect from you
DescribesThe sender's own streamThe other side's stream
Advances byThe length of the data, plus 1 for a SYN or a FINHowever many in-order bytes have arrived
A segment with no dataRepeats the next unused number; uses none upStill valid: every segment after the first SYN carries one

The acknowledgement is cumulative: ack=1101 means "I have every byte up to 1100". And a SYN counts as one byte of sequence space although it carries no data, which is why the reply to seq=x is ack=x+1. That lets the SYN itself be acknowledged and retransmitted like data.

The starting numbers are random. If they were predictable, someone who can't see your traffic could still forge segments that the receiver would accept as part of your connection. That was a real attack: in 1994 Kevin Mitnick broke into a researcher's machines by guessing the sequence numbers a server would choose. Random 32-bit numbers are awkward to read, so Wireshark shows relative numbers by default, counting each direction from zero.

Sequence numbers, one segment at a timeInteractive
    The client's first number is 1000 and the server's is 5000, to keep the arithmetic readable. Real ones are random 32-bit values. A lost segment is retransmitted after a timeout with exactly the same numbers; Chapter 11 covers how the timeout is chosen.

    Things to notice. After the handshake the client's next byte is 1001 and the server's is 5001: each SYN used up one number. A 100-byte segment starting at 1001 carries bytes 1001 to 1100, so it is acknowledged with 1101. The pure acknowledgements have a sequence number too, but they don't advance it. Lose a segment and its retransmission is identical, number for number, which is the whole point of numbering bytes: the receiver can tell a repeat from new data. Switch to relative numbers and both streams start at zero, with the first data byte at 1.

    A byte stream, not messages

    Those sequence numbers count bytes, and bytes are all TCP knows about. If you call send three times with three messages, TCP makes no promise that the other side's recv returns three times with the same three pieces. The bytes arrive in order, but they can arrive in one lump, or split at any point, depending on segment sizes, timing and how fast the receiver reads.

    # The bug: assuming one recv() returns one message
data = conn.recv(4096)
order = json.loads(data)          # fine on localhost; in production: half a document, or two glued together

# The fix: say how long each message is, and read exactly that many bytes
import struct

def recv_exact(conn, n: int) -> bytes:
    buf = bytearray()
    while len(buf) < n:
        chunk = conn.recv(n - len(buf))     # may return fewer bytes than asked for
        if not chunk:
            raise ConnectionError("peer closed in the middle of a message")
        buf += chunk
    return bytes(buf)

def send_msg(conn, payload: bytes) -> None:
    conn.sendall(struct.pack("!I", len(payload)) + payload)   # 4-byte length, network byte order

def recv_msg(conn) -> bytes:
    (length,) = struct.unpack("!I", recv_exact(conn, 4))
    return recv_exact(conn, length)

    The bug survives testing because on one machine, with small messages and pauses between them, each send happens to arrive as one segment and one recv. It breaks under load, when messages are larger than a segment or several are waiting when the receiver reads. Every protocol on TCP therefore has a framing rule, and there are only a few kinds:

    FramingHow the receiver finds the endUsed by
    Length prefixRead a fixed-size length, then that many bytesTLS records, HTTP/2 frames, gRPC, Kafka, PostgreSQL
    DelimiterRead until a marker such as \r\nHTTP/1.1 headers, SMTP, Redis commands
    Length in a headerA delimited header says how long the body isHTTP/1.1 bodies (Content-Length)
    Close the connectionThe message ends when the stream doesHTTP/1.0. One message per connection, and a cut-off message looks complete

    The same goes for sending. send may accept only part of what you gave it, when the kernel's buffer is nearly full, and returns how many bytes it took. sendall loops until everything is handed over.

    The states of an opening connection

    Each end keeps a small state machine for every connection. The opening half has five states, and ss will show you which one a socket is in. (The closing states are in Chapter 14.)

    StateWhoMeans
    CLOSEDEitherNo connection
    LISTENServerBound to a port and waiting for SYNs
    SYN-SENTClientSent a SYN, waiting for the SYN-ACK. connect() is blocked here
    SYN-RECEIVEDServerGot a SYN, sent a SYN-ACK, waiting for the final ACK
    ESTABLISHEDBothHandshake complete. Data can flow

    On the server the kernel does the whole handshake itself, before the application hears of the connection. Behind every listening socket it keeps two queues. Half-open connections, in SYN-RECEIVED, wait in the SYN queue (the SYN backlog). When the final ACK arrives, the connection moves to the accept queue, where it stays until the program calls accept(). The number passed to listen() limits the accept queue.

    $ ss -ltn 'sport = :443'          # a listening socket: Recv-Q is the accept queue now, Send-Q its limit
State   Recv-Q  Send-Q   Local Address:Port
LISTEN  37      511            0.0.0.0:443

$ nstat -az TcpExtListenOverflows    # connections dropped because the accept queue was full
TcpExtListenOverflows           1284               0.0

    A non-zero overflow count means the program isn't calling accept() fast enough. The kernel drops the handshake packets it has no room for, clients retransmit after a second, and users see connections that take exactly one or three seconds to open. From the client's side, a connection attempt has three possible endings, and telling them apart is the first step in most debugging:

    What comes backWhat the program seesUsual cause
    SYN-ACKconnect() returns after one RTTA server is listening
    RST"Connection refused", immediatelyThe host is up but nothing listens on that port
    NothingThe SYN is resent after 1, 2, 4, 8… seconds, then "Connection timed out" after about two minutes on LinuxA firewall dropping packets, a wrong address, a dead host, or a full queue

    SYN floods and SYN cookies

    The SYN queue is memory that a stranger can make the server allocate with one cheap packet. A SYN flood sends SYNs at a high rate, usually with forged source addresses, and never completes the handshake. The server stores each half-open connection and keeps resending SYN-ACKs to addresses that will never answer. When the queue is full, real clients' SYNs are dropped.

    🧠
    Panix, 1996: the first SYN flood, and the fix that is still in your kernel

    In September 1996 Panix, the oldest commercial internet provider in New York, was hit by a stream of forged SYNs aimed at its mail, web and login servers. It was a couple of hundred packets a second at most, a trivial amount of traffic, but each one occupied a slot in a queue that held only a handful of entries, and each entry took over a minute to expire. Panix's services were unreachable for days, and the technique had been published in hacker magazines that summer, so everyone else was exposed too. Longer queues and shorter timeouts only raised the price of the attack slightly. Within weeks Daniel J. Bernstein and Eric Schenk proposed a different answer: don't store anything. With SYN cookies, the server chooses its sequence number in the SYN-ACK to be a cryptographic hash of the connection's addresses and ports, a secret and a coarse timestamp, with a few bits recording the client's segment size. Then it forgets the SYN. A real client replies with an ACK of that number plus one. The server recomputes the hash, sees that it matches, and builds the connection from the ACK alone. A forged SYN costs the server one calculation and one packet and no memory. Linux has had SYN cookies since 1997 and switches them on automatically when the SYN queue overflows.

    $ sysctl net.ipv4.tcp_syncookies net.ipv4.tcp_max_syn_backlog
net.ipv4.tcp_syncookies = 1           # 1 = use cookies when the SYN queue is full (the default)
net.ipv4.tcp_max_syn_backlog = 4096

$ nstat -az TcpExtSyncookiesSent TcpExtSyncookiesRecv
TcpExtSyncookiesSent            918422             0.0    # evidence that a flood, or a very large spike, happened
TcpExtSyncookiesRecv            2105               0.0    # and this many were real clients

    The trick works because of two things from earlier in this chapter: the server is free to pick any starting sequence number, and the client must echo it back. Its cost is that a cookie has room for very little, so some options negotiated in the SYN are lost or approximated for connections made that way. Floods today are far larger and are also filtered upstream, before they reach the server (Chapter 36).

    ⚠️
    Common mistakes
    • Treating one recv() as one message. TCP keeps byte order, not boundaries. Frame every message.
    • Calling send() and ignoring its return value. It can send part of the buffer. Use sendall() or loop.
    • Reading "refused" and "timed out" as the same failure. One is an answer (RST) and the other is silence. They point at different causes.
    • Thinking the handshake proves who the server is. It proves that an address can receive packets. Identity comes from TLS (Chapter 17).
    • A new connection for every request. Each costs a round trip before any data. Reuse connections.
    • Comparing Wireshark's relative numbers with raw ones from tcpdump. Use tcpdump -S, or turn relative numbers off.

    Interview drill

    Explain it simply: Walk me through the TCP three-way handshake. Why three segments and not two?

    How a strong answer sounds
    The client sends a SYN carrying its initial sequence number, x. The server replies with a SYN-ACK: its own initial sequence number, y, and an acknowledgement of x+1. The client replies with an ACK of y+1, and can send data straight away. After that both sides are in the established state. It needs three because each side has to learn the other's starting sequence number and get confirmation that its own was received; that is four pieces of information, and the server combines two of them in one segment. With only two segments the server would never know whether the client received its sequence number, and a delayed duplicate SYN from an old connection could open a connection the client doesn't know about. The handshake also negotiates options like the maximum segment size and window scaling, and costs one round trip before the first data.

    Deeper: A service reads JSON messages from a TCP socket with a single recv(4096) per message. It worked in testing and fails randomly in production. Why, and what do you change?

    How a strong answer sounds
    TCP is a byte stream. It guarantees the bytes arrive in order, but not that the receiver sees them in the same chunks the sender wrote. One recv can return part of a message, when the message spans several segments or exceeds 4096 bytes, or several messages together, when they were queued before the read. In testing, small messages sent with gaps between them on a fast local network happen to line up one per read, so the bug stays hidden; under production load, with bigger payloads, it shows as JSON parse errors. The fix is framing: prefix each message with its length, say a 4-byte big-endian integer, read exactly four bytes, then loop on recv until exactly that many bytes have arrived, treating an empty read as the peer closing. Alternatively use a delimiter such as a newline and buffer until it appears. I'd also use sendall on the sending side, since send may write only part of a buffer, and put a sanity limit on the length so a corrupt prefix can't make the reader allocate gigabytes.

    🧠 Key takeaways

    • A TCP connection opens with SYN, SYN-ACK, ACK: each side announces a starting sequence number and has it acknowledged. It costs one round trip.
    • Sequence numbers count bytes. The acknowledgement number is the next byte expected, and a SYN uses up one number.
    • TCP delivers an ordered stream of bytes with no message boundaries. The application must frame its messages.
    • The kernel completes handshakes itself: half-open connections wait in the SYN queue, finished ones in the accept queue.
    • A connection attempt ends in a SYN-ACK, an RST ("refused") or silence ("timed out"), and each means something different.
    • A SYN flood fills the SYN queue with forged requests. SYN cookies put the state in the sequence number and store nothing.

    Check your understanding

    A client sends a SYN with seq=7000. What acknowledgement number does the server's SYN-ACK carry?

    The SYN uses up one sequence number, so the next byte the server expects is 7001.

    After the handshake, the client sends 300 bytes in a segment with seq=7001. Which acknowledgement confirms all of them?

    The segment carries bytes 7001 to 7300. The acknowledgement names the next byte expected: 7301.

    A sender calls sendall() twice with 50-byte messages. What can the receiver's first recv(4096) return?

    Order is guaranteed; boundaries are not. The receiver must find the message ends itself.

    A program's connect() fails instantly with "Connection refused". What happened on the wire?

    A refusal is an answer. Silence, from a dropped SYN, would show up as retries and then a timeout.

    During a SYN flood, a server using SYN cookies receives a SYN. Where does it keep the state for that half-open connection?

    The cookie is a hash the server can recompute. A forged SYN costs it no memory at all.
