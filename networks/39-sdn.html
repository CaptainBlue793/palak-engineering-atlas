Software-Defined Networking

For decades a network was a collection of boxes, each one configured by hand and each one working out its own routes by talking to its neighbours. Nobody could tell such a network what they wanted from it as a whole. They could only adjust each device and wait to see what the devices agreed between themselves. Software-defined networking separates the two jobs every router does, deciding where traffic should go and forwarding it, and gives the deciding to a program with a view of the whole network. That change is why a cloud can create a private network for a customer in seconds, and why a virtual network has "routers" and "firewalls" that don't exist as devices.

Control plane vs data plane

Every router and switch does work of three kinds, on very different timescales:

Data planeControl planeManagement plane
JobForward each packet: look it up in a table, send it out of a portDecide what goes in the tableLet people configure and observe the device
Works perPacket: nanosecondsChange in the network: milliseconds to secondsChange made by an operator: minutes to months
Runs onSpecialised chipsAn ordinary processorThe same processor
ExamplesLongest-prefix match, MAC lookup, ACLsBGP, OSPF, spanning tree, ARPThe command line, SNMP, configuration files

In a traditional network every device has all three, and each device's control plane is a participant in a distributed algorithm. That design survives failures well, since it was made to. Its weakness is that no part of it sees the whole network. Each router picks the shortest path as it sees it, so a short link is full while a slightly longer one is empty. A policy such as "these two groups of machines must never talk" has to be translated by hand into access lists on dozens of devices, in each vendor's own syntax.

OpenFlow

The idea needs an interface through which a controller can fill in a switch's tables. OpenFlow, from a group at Stanford in 2008, was the first to be widely adopted. It models a switch as a flow table. Each entry has a match on header fields (input port, MAC addresses, VLAN, IP addresses, protocol, ports), a priority, a list of actions (send out of a port, drop, rewrite a field, send to the controller) and counters. The switch applies the highest-priority entry that matches. This single mechanism covers switching, routing, firewalling and load balancing, which differ only in which fields are matched and what is done.

$ ovs-ofctl dump-flows br0                    # Open vSwitch, the usual software OpenFlow switch
 table=0, n_packets=3,     priority=200,tcp,nw_dst=10.0.0.3,tp_dst=22  actions=drop
 table=0, n_packets=48211, priority=100,ip,nw_dst=10.0.0.1             actions=output:1
 table=0, n_packets=51730, priority=100,ip,nw_dst=10.0.0.2             actions=output:2
 table=0, n_packets=9402,  priority=100,ip,nw_dst=10.0.0.3             actions=output:3
 table=0, n_packets=17,    priority=0                                  actions=CONTROLLER:65535

The controller's side is an ordinary program. This one, written with the Ryu framework, forwards by destination and refuses SSH to one host:

@set_ev_cls(ofp_event.EventOFPPacketIn, MAIN_DISPATCHER)
def packet_in(self, ev):
    msg, dp = ev.msg, ev.msg.datapath
    parser, ofp = dp.ofproto_parser, dp.ofproto
    pkt = packet.Packet(msg.data)
    ip, seg = pkt.get_protocol(ipv4.ipv4), pkt.get_protocol(tcp.tcp)
    if ip is None or seg is None:
        return

    if ip.dst == "10.0.0.3" and seg.dst_port == 22:
        actions = []                                           # an entry with no actions drops
    else:
        actions = [parser.OFPActionOutput(PORT_OF[ip.dst])]     # the policy, in two lines

    match = parser.OFPMatch(eth_type=0x0800, ip_proto=6, ipv4_src=ip.src,
                            ipv4_dst=ip.dst, tcp_dst=seg.dst_port)
    inst = [parser.OFPInstructionActions(ofp.OFPIT_APPLY_ACTIONS, actions)]
    dp.send_msg(parser.OFPFlowMod(datapath=dp, priority=100, match=match,
                                  instructions=inst, idle_timeout=30))   # flow-mod
    dp.send_msg(parser.OFPPacketOut(datapath=dp, buffer_id=msg.buffer_id,
                                    in_port=msg.match["in_port"], actions=actions, data=msg.data))

    A packet matched in the switch is forwarded in about a microsecond. One that goes to the controller and back takes about 4 ms. Changing the mode clears the table. Stopping the controller doesn't: the entries already installed stay where they are.

    Things to notice. In reactive mode the first packet of each flow goes to the controller and costs 4 ms, and every later one is matched in the switch. The table grows by one entry per flow. With the controller down, flows that already have entries carry on working and any new flow is dropped, because the switch has nobody to ask. In proactive mode the controller installs four general entries in advance, the table doesn't grow, no packet ever goes to the controller, and stopping the controller changes nothing that you can see. The network keeps running on its last instructions and only loses the ability to change. Production networks are built the second way for that reason.

    🧠
    Google's B4: running long-distance links nearly full

    By 2010 the network connecting Google's own data centres to each other was carrying more traffic than the one facing the public, and growing faster. Long-distance capacity is among the most expensive things a network buys, and by convention it was run at 30 to 40% utilisation: with every router choosing shortest paths for itself, the only protection against a failure or a surge was to leave most of each link empty. Google's engineers saw that most of this traffic was copying data between sites, which is bulk work that can wait, and that a program that knew all the demands and all the links could place flows far better than routers acting separately. They built the network, called B4, from simple switches of their own design that spoke OpenFlow, and put a central traffic-engineering service in charge. It took each application's demand and priority, computed paths across the whole network, split flows over several routes, and reprogrammed the switches as conditions changed. When a link failed, it moved the important traffic first and slowed the bulk copies. The paper they published in 2013 reported many links running at close to 100% utilisation, and about 70% on average over long periods, two to three times what the conventional design achieved from the same fibre. The control software was replicated across servers at each site, and the switches kept forwarding on their last instructions if they lost contact with it. B4 showed that central control could run one of the largest networks in the world.

    SDN in clouds

    The largest software-defined networks today are the virtual networks of cloud providers, and they are built at the hosts and not in the switches. The physical network is a plain routed fabric that only knows how to carry packets between servers (Chapter 30). Each server runs a virtual switch in its hypervisor or on its network card, with flow tables. A controller holds the description of every customer's network and pushes to each host the entries its virtual machines need. Packets between virtual machines are encapsulated at the sending host and carried over the fabric as an overlay (Chapter 29).

    What the console showsWhat exists
    A virtual private network with subnetsA record in the controller's database, and an identifier in the encapsulation header
    A subnet's router and route tableEntries in each host's virtual switch saying which physical host has each destination
    A security groupMatch-and-drop entries, with connection tracking, on the hosts of its instances (Chapter 35)
    A public address on an instanceA translation entry at the edge of the provider's network
    Creating a networkAn API call that writes records. No device is touched

    This explains two things about clouds that are otherwise puzzling. A new network appears in seconds, because creating it writes to a database. And cloud providers separate their control plane (the APIs that create and change things) from their data plane (running instances passing traffic) in every statement about reliability. In a control-plane outage you can't launch instances or change a rule, and everything already running carries on. Systems that keep working in that state are called statically stable, and it is the same property the panel showed with proactive entries. Kubernetes networking (Chapter 31) and service meshes (Chapter 32) follow the same pattern.

    P4 and programmable data planes

    OpenFlow lets a controller fill tables, and the tables themselves are fixed: a switch can only match on the header fields its chip was built to parse. A new encapsulation format meant waiting years for new chips. P4, a language published in 2014, goes one level further down. A P4 program describes the data plane itself: which headers exist and how to parse them, which tables there are and what each matches on, and what the actions do. A compiler turns it into a configuration for a programmable switch chip, a smart network card, or a software switch.

    // P4: an IPv4 routing table and its action. The controller fills in the rows at run time.
action ipv4_forward(macAddr_t dstAddr, egressSpec_t port) {
    standard_metadata.egress_spec = port;
    hdr.ethernet.dstAddr = dstAddr;
    hdr.ipv4.ttl = hdr.ipv4.ttl - 1;
}
table ipv4_lpm {
    key = { hdr.ipv4.dstAddr: lpm; }               // longest-prefix match
    actions = { ipv4_forward; drop; }
    size = 1024;
    default_action = drop();
}

    With the data plane programmable, a network can carry a protocol invented last month, write queue lengths and timestamps into packets as they pass so that delays can be located exactly, or balance load in the switch itself. On servers the same idea is delivered by eBPF and XDP (Chapter 34), which load small verified programs into the kernel's packet path, and that is how most new data-plane code is written now.

    ⚠️
    Common mistakes
    • Equating SDN with OpenFlow. OpenFlow is one interface. The idea is the separation, and most deployments use other interfaces.
    • Putting the controller in the path of packets. Reactive setup makes every new flow wait for it and fail without it.
    • Running a single controller. It has to be a replicated cluster, and the data plane has to survive losing contact with all of it.
    • Forgetting that table space is limited. Hardware switches hold thousands of wildcard entries, not millions. One entry per flow doesn't fit.
    • Assuming a central view removes distributed-systems problems. Updating many switches is not atomic, and a half-applied change can loop or drop traffic.
    • Depending on the control plane during an incident. If recovery needs an API that is itself down, recovery has to wait.
    🎤
    Interview drill

    Explain it simply: What does it mean to separate the control plane from the data plane?

    How a strong answer sounds
    The data plane is the part of a network device that handles each packet: it looks up the destination in a table and forwards, drops or rewrites the packet, in hardware, in nanoseconds. The control plane is the part that decides what goes in that table: routing protocols, topology discovery, policy. Traditionally both live in every device, and the control planes cooperate through distributed protocols like OSPF and BGP. Separating them means moving the control plane out of the devices into a controller, software running on servers that has a view of the whole network, computes forwarding state centrally, and programs the devices through an API such as OpenFlow, gRPC-based interfaces, or a vendor's own. The devices become simple forwarders. The gains are that policy and paths can be decided globally and expressed as software, changes are made through an API instead of device by device, and forwarding hardware and control software can evolve independently. The cost is that the controller becomes critical: it has to be replicated, and the data plane should keep forwarding on its last known state if the controller is unreachable.

    Deeper: What happens to a software-defined network when its controller fails, and how do you design for that?

    How a strong answer sounds
    It depends on how state is installed. In a reactive design, where the first packet of each flow is sent to the controller, a controller failure means no new flows can be set up; existing entries keep working until they time out, and then the network stops. That is why production systems are proactive: the controller pushes complete forwarding state in advance, and the data plane never needs to consult it for a packet. Then losing the controller means the network keeps forwarding exactly as it was, the "fail static" or statically stable behaviour, and what is lost is the ability to change: no reaction to new failures, no new tenants, no policy updates. To design for it: run the controller as a replicated cluster with consensus so that one failure doesn't matter; make the data plane hold its state indefinitely without a controller, rather than flushing it; keep local fast-failover in the data plane, such as backup paths or ECMP groups, so that link failures are handled without the controller; make updates versioned and ordered so a controller that dies halfway leaves a consistent state; and make sure the tools you need to recover the controller don't depend on the network the controller manages. Cloud providers express this as control plane versus data plane availability: an API outage should never take down running workloads.

    🧠 Key takeaways

    • The data plane forwards packets using tables. The control plane decides what the tables contain.
    • SDN moves the control plane into a controller with a view of the whole network, programmed through an API.
    • An OpenFlow switch is a table of match, priority, action and counters, filled by the controller.
    • Reactive setup asks the controller once per flow. Proactive setup installs state in advance and keeps working when the controller is down.
    • Cloud virtual networks are SDN at the hosts: a controller's database, virtual switches with flow tables, and an overlay.
    • P4 and eBPF make the data plane itself programmable, so new protocols no longer need new chips.

    Check your understanding

    Which of these is a data-plane job?

    The data plane acts on every packet. The others decide or configure, and happen far less often.

    A packet arrives at an OpenFlow switch and matches only the table-miss entry, whose action is "send to controller". What happens?

    The switch makes no decisions of its own. Later packets of the flow match the installed entry.

    Why do production networks install flow entries proactively and not reactively?

    With state installed in advance, the controller is needed only for changes.

    A cloud provider has a control-plane outage in one region. In a well-designed system, what do customers see?

    The data plane carries on with its last known state: static stability.

    What does P4 allow that OpenFlow doesn't?

    OpenFlow fills fixed tables. P4 defines the parser and the tables.
