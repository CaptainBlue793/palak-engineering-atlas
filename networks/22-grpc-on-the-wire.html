REST & gRPC on the Wire

Two services need to talk. Almost always they will do it in one of two styles. The first is JSON over HTTP, loosely called REST: text you can read, send with curl, and debug with your eyes. The second is gRPC: binary messages defined by a schema, carried on HTTP/2 streams, with generated code on both sides. Arguments about which is better usually take place at the level of taste. This chapter looks at the level of bytes. It shows what each one puts on the wire for the same request, why one is a quarter of the size, and what gRPC uses from HTTP/2 that a JSON API never touches, which also explains the places where gRPC is awkward to run.

  • Explain streaming calls, deadlines, and why gRPC needs request-level load balancing

A REST request on the wire

$ curl -v https://api.shop.example/orders -H 'Content-Type: application/json' \
       -d '{"id":150,"customer":"Asha","quantity":2,"express":true}'
> POST /orders HTTP/1.1
> Host: api.shop.example
> Content-Type: application/json
> Content-Length: 56

< HTTP/1.1 201 Created
< Content-Type: application/json
< Location: /orders/150

< {"id":150,"status":"accepted"}

The body is 56 bytes, and it helps to see where they go. The four values, 150, Asha, 2 and true, take 12. The other 44 are field names, quotation marks, colons, commas and braces, repeated in every message for ever. In exchange you get a format that describes itself: any person or program can read it with no other information. The meaning of the call is spread across the HTTP method, the path and the status code (Chapter 15), and what fields exist, and of which types, is agreed in documentation and enforced by nothing on the wire.

Protobuf encoding

Protocol Buffers start from the opposite assumption: both sides have the schema, so the message needs to carry only the values. The schema is a file:

// orders.proto
syntax = "proto3";
package shop;

message Order {
  uint64 id       = 1;        // the numbers are what goes on the wire. The names never do
  string customer = 2;
  uint32 quantity = 3;
  bool   express  = 4;
}

service Orders {
  rpc CreateOrder(Order) returns (OrderReply);
  rpc WatchOrder(OrderId) returns (stream OrderEvent);   // a server-streaming call
}

A message is encoded as a sequence of fields, and each field is a tag followed by a value. The tag packs two things into one small number: the field number from the schema, and a wire type that says how to find the end of the value.

Wire typeThe value isUsed for
0: varintA whole number in as few bytes as it needs: 7 bits per byte, with the top bit meaning "more follows"Integers, booleans, enums
2: length-delimitedA varint length, then that many bytesStrings, byte arrays, nested messages, repeated numbers
1 and 5: fixedExactly 8 or 4 bytesdouble, float, fixed-width integers
 
tag  =  (field number << 3) | wire type            # field 2, wire type 2:  (2 << 3) | 2  =  18  =  0x12

# varint for 150:   150 = 1001 0110 in binary, which is more than 7 bits
#   low 7 bits  001 0110, with the "more" bit set  →  1001 0110  =  0x96
#   next 7 bits 000 0001, last byte                →  0000 0001  =  0x01        so 150 is  96 01

Bytes are shown in hex. Tags are green and lengths are amber. The JSON is written without spaces, as an API would send it. In gRPC each message is preceded by five more bytes: one flag that says whether it is compressed, and its length in four.

Things to notice. The default order is 56 bytes of JSON and 13 of Protobuf, less than a quarter. The id 150 takes two bytes, 96 01. Change it to 1 and it takes one. Type a 13-digit id and it takes six or seven, which is still fewer than its digits as text. The name costs its own length plus two bytes, the same in any language, because it is UTF-8 bytes with a length in front. Now set express to false, or the quantity to 0. The field disappears from the message altogether. In proto3 a field holding its default value isn't sent, and the reader fills the default in. That saves space, and it means a reader can't tell "explicitly false" from "not set" unless the schema marks the field optional.

Because fields are identified by number, a schema can change without breaking programs that haven't been updated, as long as a few rules are kept:

ChangeSafe?Why
Add a field with a new numberYesOld readers skip tags they don't know, using the wire type to find the end. New readers see the default when it is missing
Rename a fieldYes on the wireNames aren't transmitted. Generated code changes, and JSON mappings would break
Remove a fieldYes, if you mark its number reservedSo that nobody reuses it later with a different meaning
Change a field's numberNoTo every existing reader it is now a different field
Change a field's typeRarelyThe bytes will be decoded as the old type, into nonsense or an error

gRPC over HTTP/2 frames

gRPC is a convention for making function calls with Protobuf messages over HTTP/2 (Chapter 16). One call is one stream:

$ grpcurl -d '{"id":150,"customer":"Asha","quantity":2,"express":true}' \
          api.shop.example:443 shop.Orders/CreateOrder
{ "id": "150", "status": "ACCEPTED" }

$ grpcurl -d '{"id":0}' api.shop.example:443 shop.Orders/CreateOrder
ERROR:
  Code: InvalidArgument                  # grpc-status: 3, in the trailers. The HTTP status was still 200
  Message: id must be set

Putting the status at the end lets a server start sending a response before it knows how the call will finish, which matters for streams. It has a cost for operators: load balancers, logs and dashboards that only look at HTTP status codes see every gRPC call as a success. A handful of the status codes come up constantly:

grpc-statusNameRoughly the HTTPRetry?

Streaming RPCs

A stream can carry more than one message in each direction, and gRPC exposes that directly. All four shapes use the same frames as above, with more DATA frames:

KindMessagesExample
UnaryOne request, one responseCreate an order
Server streamingOne request, many responsesWatch an order's status change; a model's reply, token by token
Client streamingMany requests, one responseUpload a file in chunks; send a batch of metrics
BidirectionalMany each way, independentlyChat; a live speech-to-text session

Streams get HTTP/2's flow control for free. If the receiver stops reading, its window closes and the sender's write blocks, which is back-pressure with no extra code (Chapter 12). This is the job that needed WebSockets or Server-Sent Events in a browser (Chapter 21), done between services with typed messages.

Deadlines

Every gRPC call can carry a deadline: the moment after which the caller no longer wants the answer. The client sends it in the grpc-timeout header, so the server knows it too. That is different in kind from an HTTP client's timeout, which the server never hears about.

reply = stub.CreateOrder(order, timeout=0.2)        # sent on the wire as  grpc-timeout: 200m

# In the server, calling the next service with whatever time is left
def CreateOrder(self, request, context):
    remaining = context.time_remaining()              # 0.2 s minus the time spent so far
    stock = inventory.Reserve(item, timeout=remaining)  # the deadline travels down the chain
    if not context.is_active():                        # the caller gave up or cancelled: stop working
        return OrderReply()

When the deadline passes, the client gets DEADLINE_EXCEEDED and resets the stream, and every server along the chain can see that the call is dead and abandon it. Without that, an overloaded system fills up with work for callers who stopped waiting long ago, and that wasted work is a large part of how an overload turns into an outage.

"Why are all the requests going to one pod?"

Teams that move a service from JSON over HTTP/1.1 to gRPC on Kubernetes run into the same surprise so regularly that the Kubernetes blog published an article about it in 2018. They scale a service from one replica to ten, and one replica goes on handling all of the traffic while nine sit idle. Nothing is misconfigured. A Kubernetes Service balances connections: when a client opens a TCP connection, one back end is chosen for it (Chapter 31). An HTTP/1.1 client opens connections often and holds a pool of them, so its requests spread out. A gRPC client opens one HTTP/2 connection and multiplexes every call onto it for hours. The balancer made its single decision when that connection was opened, and each later request follows it. Pods added afterwards get nothing until clients happen to reconnect. The fixes all move the decision from the connection to the request. A proxy that understands HTTP/2, in a service mesh or at an ingress, can terminate the client's connection and spread the individual streams across back ends. Or the client can balance for itself: look up all the back ends' addresses through a "headless" Service, open a connection to each, and rotate calls among them. Some teams also set a maximum connection age on the server so that clients are made to reconnect now and then. The protocol was doing what it was built to do, and the load balancer in front of it was working one layer too low.

⚠️
Common mistakes
  • Reusing or renumbering Protobuf fields. Old and new programs silently read each other's data as the wrong field. Reserve removed numbers.
  • Relying on "false" or 0 being sent. Default values aren't on the wire. Use optional where absence must be distinguishable.
  • Putting gRPC behind a connection-level load balancer. One connection, one back end, however many replicas exist.
  • Monitoring only HTTP status. gRPC errors arrive as HTTP 200 with a non-zero grpc-status in the trailers.
  • Calls with no deadline. The default is to wait for ever, so one stuck dependency holds its callers' resources indefinitely.
  • Retrying DEADLINE_EXCEEDED blindly. The server may have done the work. Retry only what is safe to repeat.

Interview drill

Explain it simply: How does gRPC differ from a JSON REST API, on the wire?

How a strong answer sounds
A REST API typically sends JSON text in an HTTP request, on any HTTP version, with the operation expressed by the method and path and the result by the HTTP status code. JSON is self-describing, so every message repeats its field names. gRPC sends Protocol Buffers, a binary encoding driven by a schema that both sides hold. A message is a series of fields, each a tag made of the field number and a wire type, followed by the value, with integers as variable-length varints and strings length-prefixed. Field names aren't sent, so messages are several times smaller and quicker to parse. Each call is an HTTP/2 stream: a HEADERS frame with POST and a path naming the service and method, DATA frames carrying length-prefixed messages, and a final trailers frame with grpc-status. Because it sits on HTTP/2 streams it supports streaming in either direction and many concurrent calls on one connection, and it carries deadlines in a header. The trade-offs are that it can't be read without tooling and the schema, needs HTTP/2 end to end, and isn't directly usable from browsers.

Deeper: You deploy five replicas of a gRPC service behind a Kubernetes Service and one replica takes nearly all the load. Why, and what are the options?

How a strong answer sounds
gRPC clients hold one long-lived HTTP/2 connection and multiplex all calls on it. A Kubernetes ClusterIP Service balances at the connection level: kube-proxy picks a back end when the TCP connection is opened, and every request on that connection then goes to the same pod. So with few clients, load is as uneven as the number of connections, and new replicas receive nothing until clients reconnect. HTTP/1.1 hid this because clients open many short-lived connections. The fix is to balance per request. One option is an L7 proxy that understands HTTP/2 and gRPC, such as Envoy in a service mesh or a gRPC-aware ingress, which spreads individual streams across back ends. Another is client-side load balancing: use a headless Service so that DNS returns all pod addresses, and configure the gRPC client with a round-robin policy so that it keeps a connection to each. A partial mitigation is setting a maximum connection age on the server so that clients are forced to re-resolve and reconnect periodically. I'd also make sure health checking and connection draining work with whichever approach is chosen, so that deploys don't drop calls.

🧠 Key takeaways

  • JSON spends most of its bytes on field names and punctuation, and can be read by anyone. Protobuf sends only tagged values, and needs the schema.
  • A Protobuf field is a tag (field number and wire type) and a value. Integers are varints, and strings are a length and bytes.
  • Field numbers are the contract: add new ones freely, never reuse or renumber. Default values aren't transmitted.
  • A gRPC call is an HTTP/2 stream: headers naming the method, length-prefixed messages in DATA frames, and the status in trailers.
  • Streaming in either direction and deadlines that travel with the call are built in.
  • One long-lived connection carries every call, so gRPC must be load-balanced per request, and monitored by grpc-status.

Check your understanding

In an encoded Protobuf message, how is a field identified?

Names exist only in the schema and the generated code. The number is what the two sides must agree on.

A team changes string customer = 2; to string customer = 5; and deploys the new server first. What do old clients' requests look like to it?

Nothing fails loudly. The data is simply read as a different, unknown field, which is why numbers must never change.

A proto3 message has bool express = 4; set to false. How many bytes does that field add to the encoded message?

The reader supplies the default for a missing field, so false, 0 and the empty string cost nothing.

A gRPC call fails because the order was invalid. What HTTP status does the client's HTTP/2 library see?

The HTTP layer only carried the call. Its outcome is in the trailers, so monitoring must read those.

Service A calls B with a 200 ms deadline, and B calls C. Why does B pass the remaining time on to C?

A propagated deadline lets every hop abandon dead requests, which keeps an overloaded system from wasting what capacity it has.
