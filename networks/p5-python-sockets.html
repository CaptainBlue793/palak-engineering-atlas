Sockets in Python

Every networked program you have used, from browsers and web servers to database drivers and curl, sits on the same small API: the Berkeley sockets interface from 1983. Python's socket module is a thin layer over it, so the calls you learn here are the same ones nginx makes in C. This chapter builds a TCP echo server and client, then a UDP one, and shows what each call asks the kernel to do, what it waits for, and how it fails.

  • Write a client with create_connection, sendall and recv
  • Explain which calls block, and for what
  • Write a UDP request–reply with sendto and recvfrom
  • Use timeouts so a silent peer can't hang your program

A TCP echo server

A server needs four calls before it can talk to anyone. socket() creates an endpoint: AF_INET means IPv4 and SOCK_STREAM means TCP. bind() attaches it to an address and port. listen() turns it into a listening socket and tells the kernel to start completing handshakes for it. accept() waits for one of those completed connections and returns a new socket for it.

import socket

HOST, PORT = "0.0.0.0", 9000                    # 0.0.0.0 = every interface on this machine

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as srv:
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)   # restart without "Address already in use"
    srv.bind((HOST, PORT))
    srv.listen(128)                         # backlog: finished handshakes waiting for accept()
    while True:
        conn, addr = srv.accept()           # blocks until a client has connected
        with conn:
            conn.settimeout(30)              # a silent client can't hold us forever
            print("connection from", addr)   # ('127.0.0.1', 51514): the client's IP and port
            while True:
                data = conn.recv(4096)      # up to 4096 bytes; b"" means the client closed
                if not data:
                    break
                conn.sendall(data)          # echo every byte back

Three details are easy to get wrong. recv(4096) returns up to 4096 bytes: whatever has arrived, which may be part of what the client sent or several sends joined together, because TCP is a byte stream (Chapter 8). An empty result, b"", is the only way you learn the other side closed. And sendall exists because plain send may accept only some of the bytes when the kernel's send buffer is full; sendall loops until everything is queued.

SO_REUSEADDR lets the server bind its port again straight after a restart, while old connections from the previous run are still in TIME_WAIT (Chapter 14). Without it, a quick restart fails with OSError: [Errno 98] Address already in use.

The client

import socket

with socket.create_connection(("127.0.0.1", 9000), timeout=5) as s:   # DNS + socket() + connect()
    s.sendall("héllo\n".encode("utf-8"))         # encode at the edge: 7 bytes
    reply = s.recv(4096)
    print(reply.decode("utf-8"), end="")

create_connection is the convenient way to connect. It resolves the name, tries each returned address (IPv6 and IPv4) in turn, and applies the timeout to the connect and to every later call. Underneath it runs socket() then connect(); the kernel picks an ephemeral source port and performs the three-way handshake, and connect() returns once the handshake completes or fails.

This client has a bug that never shows up on localhost: it assumes one recv returns the whole reply. Over a real network a 10 KB reply may arrive in several pieces. Any protocol needs a way to know where a message ends, usually a length prefix or a delimiter; the recv_exact pattern on the course home page is the length-prefix version, and HTTP/1.1 uses Content-Length (Chapter 15).

Blocking, timeouts and non-blocking

By default, socket calls block: accept waits for a client, connect waits for the handshake, recv waits for data, and sendall waits for buffer space. That's simple to write, and dangerous in a server. A peer that vanishes without closing (a laptop that went to sleep, a NAT that forgot the mapping) never sends anything again, so a recv with no timeout waits forever. Every socket in this course gets a timeout.

ModeHow to set itA call that can't finish yet…Use it for
Blockingsettimeout(None) (the default)Waits foreverQuick scripts only
Timeoutsettimeout(5) or create_connection(..., timeout=5)Waits up to 5 s, then raises TimeoutError (socket.timeout)Clients and simple servers: the default choice
Non-blockingsetblocking(False) = settimeout(0)Raises BlockingIOError immediatelyEvent loops: selectors, asyncio, one thread watching thousands of sockets

The echo server above serves one client at a time: while it's inside the inner loop, accept isn't being called, and the next client's finished handshake waits in the backlog. Real servers either use a thread per connection (socketserver.ThreadingTCPServer) or an event loop with non-blocking sockets, which is how asyncio, nginx and Node.js handle tens of thousands of connections. The OS course explains the kernel side in I/O multiplexing and epoll.

UDP sockets

A UDP socket (SOCK_DGRAM) has no connection, no listen and no accept. The server binds and waits for datagrams; each recvfrom returns exactly one whole datagram and the address it came from, and sendto sends one datagram to an address. Message boundaries are preserved, but nothing is guaranteed to arrive (Chapter 7).

# server
with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as s:
    s.bind(("0.0.0.0", 9001))
    while True:
        data, addr = s.recvfrom(65535)       # one datagram, and who sent it
        s.sendto(data, addr)

# client
with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as s:
    s.settimeout(2)
    s.sendto(b"ping", ("127.0.0.1", 9001))   # succeeds even if nobody is listening
    try:
        data, _ = s.recvfrom(65535)
    except TimeoutError:
        print("no reply: lost, or nobody listening")   # UDP can't tell you which

Note the comment on sendto. With TCP, a missing server fails loudly at connect. With UDP, sending to a closed port succeeds; at best the other host replies with an ICMP "port unreachable" that an unconnected socket never reports. So a UDP client must always use a timeout, and usually retries, which is exactly what DNS clients do (Chapter 10).

The worker pool that froze at 3 a.m.

A Python job runner with 16 worker threads calls a partner's HTTP API using requests.get(url), with no timeout= argument. requests doesn't set one by default, so the underlying socket recv blocks forever. One night the partner's load balancer drops some connections silently during a deploy: no FIN, no RST, just nothing. Each affected worker sits in recv waiting for a response that will never come. Within an hour all 16 are stuck, the queue grows, and nothing is logged because nothing failed. A thread dump shows every worker in socket.recv. The fix is one argument, timeout=(3.05, 10) (connect and read), plus a retry policy. The rule holds for every client library in every language: set a connect timeout and a read timeout, explicitly.

⚠️
Common mistakes
  • Assuming one recv returns one message. It returns whatever bytes have arrived. Frame your messages.
  • Using send and ignoring its return value. It may send only part of the data. Use sendall.
  • No timeout. A silent peer blocks recv forever. Set one on every socket.
  • Treating b"" as "no data yet". On a blocking TCP socket it means the peer closed; loop on it and you spin at 100% CPU.
  • Binding to 127.0.0.1 in a container and wondering why it's unreachable from outside. Bind to 0.0.0.0.
  • Forgetting to close sockets. Leaked sockets are leaked file descriptors; use with.

Interview drill

Explain it simply: Walk through the socket calls on both sides of a TCP connection.

How a strong answer sounds
The server calls socket() to create an endpoint, bind() to attach it to a port, and listen() to make it a listening socket with a backlog; from then on the kernel completes handshakes for it. It then calls accept(), which blocks until a completed connection is waiting and returns a new connected socket for that client. The client calls socket() and connect(); the kernel picks a source port and does the three-way handshake, and connect returns when it's done. Then both sides send and recv on their connected sockets, and close when finished; the other side's recv then returns an empty result.

Deeper: The client calls sendall(b"abc") then sendall(b"def"). What can the server's recv(1024) calls return?

How a strong answer sounds
Any split of the six bytes, in order: b"abcdef" in one call, or b"ab" then b"cdef", or six single bytes. TCP delivers a stream of bytes, in order and without gaps, but with no record of how the sender divided them. Segments can be coalesced by Nagle's algorithm (Chapter 33), split by the MSS, or read in pieces depending on timing. So the application needs framing: a length prefix, a delimiter like \n or \r\n\r\n, or a self-describing format. UDP is different: each recvfrom returns exactly one datagram, as it was sent.

🧠 Key takeaways

  • Server: socket → bind → listen → accept (returns a new connected socket). Client: create_connection (= socket + connect).
  • The handshake happens in the kernels; accept just collects a finished connection from the backlog.
  • recv returns up to N bytes of a stream; b"" means the peer closed. Use sendall, not send.
  • Every socket gets a timeout; non-blocking sockets and event loops are how servers scale.
  • UDP: sendto/recvfrom, one datagram each, no delivery guarantee, so always a timeout and usually a retry.
  • SO_REUSEADDR lets a server restart without "Address already in use".

Check your understanding

What does srv.accept() return?

The listening socket keeps listening. Each accepted connection gets its own socket, which is the one you recv and send on.

A blocking TCP socket's recv(4096) returns b"". What happened?

A blocking recv waits for data, so an empty result can only mean end of stream: the other side sent FIN. A timeout raises TimeoutError instead.

Why use sendall(data) instead of send(data)?

When the kernel send buffer is nearly full, send takes what fits. Neither call waits for the peer's acknowledgement; both return once the bytes are in the local kernel's buffer.

A UDP client calls sendto(b"ping", ("10.0.0.5", 9001)) but nothing listens on that port. What does the client see?

UDP has no handshake, so sending can't discover that nobody is there. That's why UDP clients always need a timeout, and usually retries.

Your server restarts and fails with OSError: [Errno 98] Address already in use, though the old process has exited. What helps?

Connections from the previous run are still in TIME_WAIT on that port. SO_REUSEADDR lets a new listening socket bind anyway; it doesn't let two live servers share the port (that's SO_REUSEPORT).
