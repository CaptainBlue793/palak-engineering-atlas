Anycast & CDNs

A round trip between Sydney and Virginia takes about a fifth of a second, and no amount of engineering will change that, because it is set by the speed of light in glass. A new HTTPS connection needs three of those round trips before the first byte of a page arrives. The only way to make the internet feel fast for someone far away is to stop being far away: to put a copy of the content, or at least the end of the connection, in a building near them. That is a content delivery network. To make it work, a user who types one host name has to end up at the nearest of hundreds of buildings, and the neatest way to arrange that is a routing trick called anycast, in which the same IP address exists in all of those buildings at once.

Anycast routing

Normally an IP address belongs to one machine in one place. That is unicast. With anycast, the same prefix is announced by BGP from many locations at once. Nothing in BGP forbids that. To the rest of the internet it looks like one network that happens to be reachable by several paths, and every router does what it always does: it picks the path it prefers (Chapter 25). A router in Europe prefers the announcement it hears from the site in London, and a router in Asia prefers the one from Singapore. Packets sent to the one address arrive at different buildings depending on where they started.

UnicastAnycast
One address isOne placeMany places, each announcing the same prefix
Who chooses the destinationNobody: there is oneThe routers on the way, by their normal BGP preferences
If a site failsThe address is unreachable until DNS or an operator moves itThe site stops announcing, and within seconds its traffic flows to the next-best site
A flood of attack trafficAll arrives at one placeIs split among the sites, each absorbing the part that started near it
The client needsNothing specialNothing special. It can't even tell
Used byMost serversThe DNS root servers, public resolvers such as 1.1.1.1 and 8.8.8.8, CDNs
 
$ dig +short CH TXT id.server @1.1.1.1         # ask the resolver which of its sites answered
"LHR"                                          # from a laptop in London
$ dig +short CH TXT id.server @1.1.1.1
"SIN"                                          # the same command, the same address, from a server in Singapore

Two cautions. "Nearest" means nearest as BGP sees it, in networks crossed and in business preference, and not in kilometres, so a user is occasionally sent to a surprising continent. And a long TCP connection has a small risk: if routes change while it is open, its packets may start arriving at a different site that has never heard of the connection. In practice routes are stable for far longer than most connections last, which is why anycast, first used only for one-packet DNS queries, now carries a large share of the web's TCP and QUIC traffic.

Round-trip times are typical figures for each pair of cities, and each user is sent to the announcing site with the shortest round trip, which is what BGP achieves most of the time. A new HTTPS connection is counted as three round trips to the first byte: TCP, TLS, and the request.

Things to notice. With Virginia alone, the user in New York has an 8 ms round trip and the user in Sydney 210 ms, so a new connection costs Sydney 630 ms before anything arrives. Switch on all five sites and nobody is more than 95 ms away. Sydney's connection takes 15 ms. Now switch London off, as a failure would. The users in London and Lagos aren't cut off. Their packets go to Virginia, and they are slower, with nothing reconfigured and no DNS change. Lagos is the user to watch throughout. It never gets a close site, because none of these five cities is near it, and that is what choosing where to build looks like from the user's end.

Edge caches and cache keys

Each of those sites, a point of presence, is a set of reverse proxies (Chapter 23) with a large cache. A request arrives, and the proxy looks for a stored response under the request's cache key. A hit is answered at once from the building the user reached. A miss is fetched from the origin, the customer's real servers, stored according to its Cache-Control header (Chapter 15), and then returned.

$ curl -sI https://www.shop.example/img/hero.jpg | grep -iE 'cache|age'
cache-control: public, max-age=86400
cf-cache-status: HIT                    # served from the edge, the origin wasn't contacted
age: 1832                               # and it has been in this cache for 1,832 seconds

The cache key decides what counts as "the same request", and getting it wrong is the commonest way to make a CDN useless or dangerous:

In the keyEffectGoes wrong when
Host and pathAlways
The query stringUsually, in fullTracking parameters such as ?utm_source=… make every visitor's URL unique, so nothing is ever a hit. Strip or ignore the ones that don't change the response
Headers named in VaryA separate copy for each valueVary: User-Agent creates thousands of copies of one page. Vary: Accept-Encoding is fine
CookiesNormally a request with a session cookie bypasses the cacheA personalised page is cached without the cookie in the key, and one user's account page is served to everyone
Nothing elseThe origin's response depends on a header that isn't in the key. An attacker sends that header once and poisons the cached copy for all

Even a response that can't be cached gains from the edge. The user's TCP and TLS handshakes end at a nearby building, so their three round trips are short ones. The edge then sends the request to the origin over a connection that is already open and warmed up (Chapter 13).

Request routing: DNS or anycast

There are two ways to get a user to a nearby site, and CDNs use both.

Origin shielding

A CDN with two hundred sites has two hundred separate caches. When a new file is published, or a popular one expires, each site misses separately, and the origin receives two hundred requests for the same thing at nearly the same moment. An origin shield puts one more cache in between. Edge sites fetch from the shield, and only the shield fetches from the origin.

The shield also raises the hit ratio for unpopular content. A file requested once a day in each of two hundred cities is never in any edge cache when it is wanted, but it is requested two hundred times a day at the shield and stays warm there.

🧠
8 June 2021: one customer's setting takes down a large part of the web

Shortly before 10:00 UTC on 8 June 2021, a long list of well-known sites began returning errors at the same moment: Amazon, Reddit, the New York Times, the Guardian, Twitch, and the British government's own site among them. None of them had changed anything. All of them were served through the CDN Fastly. A software release in May had contained a bug that lay dormant until a particular, perfectly valid combination of settings was used. That morning one customer pushed a configuration change that happened to be that combination, and within seconds 85% of Fastly's network was returning errors. Because a CDN's job is to apply changes globally and quickly, the trigger reached every site almost at once. Fastly's engineers noticed within a minute, found the cause in about forty, and disabled the offending setting. Most of the network was healthy again 49 minutes after it began. Putting one provider's reverse proxies in front of your site gives you their hundreds of buildings and their capacity to absorb attacks, and it also makes their worst hour yours. For most sites that trade is still clearly worth it. The sites that came through that morning with least damage were the ones that could switch to a second CDN, or straight to their origin, with a DNS change they had already rehearsed.

⚠️
Common mistakes
  • Assuming a CDN makes a site fast by being switched on. If responses aren't cacheable, or the key is fragmented, every request is a miss with an extra hop.
  • Caching personalised responses. Anything that depends on who is asking must be private, or have that identity in its key.
  • Leaving tracking parameters in the cache key. Every shared link becomes its own cache entry.
  • Leaving the origin reachable directly. Attackers skip the CDN and its protections. Allow only the CDN's addresses.
  • Forgetting the purge. A long cache lifetime on a URL that changes means stale content everywhere. Use versioned file names, or purge on deploy.
  • Assuming anycast sends users to the geographically closest site. It sends them where BGP prefers. Measure from real users.

Interview drill

Explain it simply: What is anycast, and why do CDNs and DNS providers use it?

How a strong answer sounds
Anycast means announcing the same IP prefix from many locations at once using BGP. Each network on the internet then routes packets for that address along the path it prefers, which usually leads to a topologically nearby site, so users in different regions reach different physical servers through one address. It gives three things for free. Latency: users are served from a nearby site with no client-side logic. Resilience: if a site fails or is taken out of service, it withdraws its announcement and routing converges on the remaining sites within seconds, with no DNS TTL to wait for. And absorption of attacks: a distributed flood is split across sites by the same routing, so no single site takes all of it. It suits DNS perfectly, since a query is one packet each way. It also works for TCP and QUIC, because routes are normally stable for the life of a connection, though a route change mid-connection can break it. The limits are that "nearest" is decided by BGP policy, not geography or load, and operators have only coarse control over who goes where.

Deeper: You put a CDN in front of a site and the cache hit ratio is 15%. Where do you look?

How a strong answer sounds
First at whether the responses are cacheable at all: the origin's Cache-Control headers. private, no-store, a zero max-age, or a Set-Cookie on every response will each stop the CDN storing them, so static assets should be sent with long lifetimes and versioned names. Next at the cache key. Query strings are the usual culprit: tracking parameters, cache-busting timestamps, or the same parameters in different orders make equivalent requests look distinct, so I'd normalise or strip the ones that don't affect the response. Then Vary: varying on User-Agent or Cookie multiplies entries until nothing repeats. Then how traffic is spread: with many edge sites and a long tail of content, each site sees each object rarely, so tiered caching with an origin shield helps a lot. I'd also check lifetimes, since very short ones mean constant revalidation, and whether cookies on requests for static files are forcing a bypass. I'd pull the CDN's logs, group misses by URL pattern and reason, and fix the largest group first.

🧠 Key takeaways

  • Distance sets a floor on latency, and a new connection pays it several times. A CDN moves the far end of the connection close to the user.
  • With anycast one prefix is announced from many sites, and ordinary BGP routing delivers each user to one that is near in routing terms.
  • A failed anycast site withdraws its route and its users move elsewhere in seconds. Attack traffic is spread over all sites.
  • An edge cache answers hits locally. The cache key defines a hit, and query strings, Vary and cookies decide the hit ratio and the safety.
  • Users are steered by DNS answers, by anycast, or both: DNS gives control, anycast gives fast failover.
  • An origin shield funnels every site's misses through one cache, protecting the origin and keeping rare content warm.

Check your understanding

How can the address 1.1.1.1 be answered from hundreds of cities?

Anycast: many origins for one prefix, with the routing system choosing among them.

An anycast site loses power. What happens to the users who were reaching it?

The address never changes. Only the routes to it do, so there is no TTL to wait for.

A marketing email links to /sale?utm_id= followed by a unique code for each recipient. The page is cacheable. Why is the CDN's hit ratio for it near zero?

Configure the CDN to ignore parameters that don't change the response, and they all share one entry.

A CDN steers users by DNS. A user in Madrid uses a public resolver whose nearest site, as the CDN sees it, is in the United States. Where might the user be sent?

DNS steering knows the asker of the DNS question. Resolvers can pass on part of the client's address to help, and not all do.

What does an origin shield change when a popular file expires at 200 edge sites at once?

Edge misses are funnelled through one cache, so the origin's load doesn't grow with the number of sites.
