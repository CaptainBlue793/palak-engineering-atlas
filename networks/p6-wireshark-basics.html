Reading Packets with Wireshark

Logs tell you what a program thinks happened. A packet capture tells you what actually went over the wire: every byte, with a timestamp to the microsecond. When two teams each insist the other side is slow, or a connection resets "for no reason", the capture settles it. This chapter covers capturing with tcpdump on a server, then filtering and reading the result in Wireshark, packet by packet and layer by layer.

  • Capture traffic on a server with tcpdump and a capture filter, and save it as a pcap
  • Tell capture filters (BPF) from display filters, and write both
  • Read the packet list, the details tree and the bytes pane
  • Follow a TCP stream to see one conversation's payload
  • Read tcpdump's one-line format, including its flag letters

Capturing on a server with tcpdump

Servers rarely have a screen, so captures are usually taken with tcpdump and copied to a laptop for reading. The kernel hands every packet on an interface to the capture tool, so on a busy server you must narrow it down at capture time with a capture filter, written in BPF (Berkeley Packet Filter) syntax:

$ sudo tcpdump -i eth0 -nn -w /tmp/api.pcap 'host 203.0.113.50 and tcp port 80'
tcpdump: listening on eth0, link-type EN10MB (Ethernet), snapshot length 262144 bytes
^C412 packets captured
412 packets received by filter
0 packets dropped by kernel                       # non-zero here means the capture is incomplete

$ scp server:/tmp/api.pcap .  &&  wireshark api.pcap

-i eth0 picks the interface (-i any captures all of them). -nn stops tcpdump turning addresses into hostnames and port numbers into service names, which is slower and hides the real values. -w writes raw packets to a file instead of printing them. On a production box, add -C 100 -W 10 to rotate through ten 100 MB files, so a capture left running for hours can't fill the disk. Without -w, tcpdump prints one line per packet, and it's worth being able to read:

$ sudo tcpdump -i eth0 -nn 'tcp port 80'
09:14:07.022512 IP 192.168.1.23.51514 > 203.0.113.50.80: Flags [S], seq 2961823011, win 64240, options [mss 1460,sackOK,TS val 3804520 ecr 0,nop,wscale 7], length 0
09:14:07.041003 IP 203.0.113.50.80 > 192.168.1.23.51514: Flags [S.], seq 1206375220, ack 2961823012, win 65160, options [mss 1460,sackOK,TS val 9911042 ecr 3804520,nop,wscale 7], length 0
09:14:07.041120 IP 192.168.1.23.51514 > 203.0.113.50.80: Flags [.], ack 1, win 502, length 0
09:14:07.041301 IP 192.168.1.23.51514 > 203.0.113.50.80: Flags [P.], seq 1:85, ack 1, win 502, length 84: HTTP: GET /health HTTP/1.1

Each line is: timestamp, source.port > destination.port, then the TCP flags. The letters are S SYN, F FIN, R RST, P PSH (data pushed to the application), and . means ACK, so [S.] is a SYN-ACK. After the first packets, tcpdump prints sequence numbers relative to the start (seq 1:85 = bytes 1 to 84), and win 502 is the raw window field before scaling (502 × 2⁷ = 64,256 bytes; Chapter 12).

Two kinds of filter

This is the source of most beginner confusion: Wireshark has two filter languages, used at two different times, and they look similar enough to mix up.

The practical rule: capture broadly enough that you won't miss the interesting packet (you can't filter back in what was never recorded), and display narrowly. Capture filters exist to keep the file small on a busy server.

The three panes

Wireshark's main window has three parts, top to bottom. The packet list has one row per packet: number, time since the capture started, source, destination, the highest protocol Wireshark could decode, frame length and a summary. Rows are coloured by protocol, and red-ish rows usually mean trouble (resets, retransmissions). The packet details pane shows the selected packet as a tree with one branch per layer: the frame, Ethernet, IP, TCP or UDP, then the application protocol. That tree is encapsulation (P7) made visible. The packet bytes pane shows the raw hex; clicking a field in the tree highlights its bytes.

Two habits make captures faster to read. Set the time column to "seconds since previous displayed packet" (View → Time Display Format) to make gaps jump out: a 200 ms gap before a retransmission, or 40 ms before an ACK. And use Follow → TCP Stream (right-click a packet) to see one connection's payload reassembled, client bytes in one colour and server bytes in another, which is the fastest way to read a plain-text protocol.

The 502s that only a capture could explain

An API behind a cloud load balancer returns a few 502 errors an hour, never reproducible on demand, and the application logs show nothing at all for the failed requests. A ring-buffer capture on one backend (tcpdump -i eth0 -nn -w lb.pcap -C 100 -W 10 'tcp port 8080') runs for a day. In Wireshark, tcp.flags.reset == 1 finds a handful of packets, and following one stream shows the pattern: an idle keep-alive connection, the backend sends FIN after exactly 5 seconds of idle time, and the load balancer, whose idle timeout is 60 seconds, sends a new request on that connection at the same moment, which gets a reset. The backend (Node.js has a 5-second default keep-alive timeout) was closing connections the balancer still considered usable. Raising the backend's keep-alive timeout above the balancer's fixed it. No log could have shown this; the evidence only existed on the wire. Case Study 46 returns to load balancers and keep-alive.

⚠️
Common mistakes
  • Typing a display filter into tcpdump (or BPF into the display bar). tcp.port == 80 is display syntax; tcpdump wants tcp port 80.
  • Capturing too narrowly. Filter on one port and you miss the DNS lookup or the ICMP error that explains the problem.
  • Capturing in the wrong place. Behind a load balancer or NAT, addresses change; capture on the host whose behaviour you're questioning, or both ends.
  • Trusting "bad checksum" on outgoing packets. With checksum offload the NIC fills it in after the capture point. It's normal.
  • Leaving an unbounded capture running. Use -C and -W, and check "packets dropped by kernel" when you stop.
  • Forgetting captures hold secrets. Plain HTTP shows passwords and cookies; treat pcaps like credentials.

Interview drill

Explain it simply: What is the difference between a capture filter and a display filter, and when would you use each?

How a strong answer sounds
A capture filter is a BPF expression evaluated in the kernel while capturing; packets that don't match are never recorded. It's what you use with tcpdump on a busy server to keep the file small, for example host 10.0.0.5 and tcp port 5432. A display filter is Wireshark's own language, applied to a capture you already have; it only hides packets and can use any decoded field, like http.response.code == 502 or tcp.analysis.retransmission. I capture broadly enough not to miss anything relevant, because what isn't captured is gone, and then narrow down freely with display filters.

Deeper: Users report that a service is slow, and the service team says its logs show 5 ms per request. How would you use captures to find where the time goes?

How a strong answer sounds
Capture at both ends, on the client side and on the server, ideally with synchronised clocks, filtered to that service's port. On each, set the time column to the delta from the previous packet and follow a slow request. On the server capture, the gap between the request arriving and the response leaving is the server's true time, including any queueing before the application saw it. On the client capture, the extra time beyond that is the network or the client. Then look for specific patterns: a slow TCP or TLS handshake (connections not being reused), retransmissions with 200 ms or longer gaps (loss), zero-window packets (a slow reader), or 40 ms gaps before ACKs (delayed ACK interacting with Nagle; Chapter 33).

🧠 Key takeaways

  • On servers, capture with tcpdump -i eth0 -nn -w file.pcap '<BPF filter>', rotating with -C/-W; read it in Wireshark.
  • Capture filters (BPF) decide what is recorded; display filters only hide. Capture broad, display narrow.
  • The packet list is one row per packet; the details tree is the encapsulation, one branch per layer; the bytes pane is the raw hex.
  • Follow → TCP Stream reassembles one connection's payload in both directions.
  • tcpdump flags: S SYN, F FIN, R RST, P push, . ACK.
  • A capture shows what actually happened on the wire, which is why it settles arguments logs can't.

Check your understanding

You capture on a busy server and need the file to stay small. Which kind of filter achieves that?

Only a capture filter stops packets being recorded. A display filter hides packets in a file that already contains them.

Which display filter shows only new connection attempts (the first packet of each handshake)?

The SYN-ACK also has SYN set, so syn == 1 alone shows both halves. Requiring ACK clear leaves only the client's opening SYN. tcp port 80 is BPF syntax.

In tcpdump output, what does Flags [P.] mean?

P is PSH (deliver this data to the application now) and . is ACK. Most data segments look like this.

Why add -nn to tcpdump?

Name resolution slows output, generates its own DNS traffic into your capture, and replaces 443 with "https". -X prints hex; -s 0 (the modern default) captures full packets.

What does Follow → TCP Stream show?

Wireshark puts the payloads of one 5-tuple's segments back in sequence order and shows client and server bytes in two colours. It also sets the display filter to tcp.stream eq N.
