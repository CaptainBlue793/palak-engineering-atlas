Typing google.com, Packet by Packet

You type a name, press Enter, and a page appears in about a tenth of a second. In that time your laptop sends and receives a few dozen packets using six protocols, and nearly every chapter of this course takes part. This case study follows one page load on a home network from the first packet to the first paint, in the order the packets appear on the wire, with the addresses each one carries at each layer. Then it loads the same page again a minute later, to show how few of those packets were needed.

  • Put the packets of a page load in the order they are sent, and say why each must come before the next
  • Say which MAC addresses, IP addresses and ports each packet carries, and which of them change on the way
  • Account for the time to the first byte, round trip by round trip
  • Explain what a second visit skips, and which cache or open connection makes that possible

The laptop has just joined the network and the browser has just been opened, so every cache is empty. One simplification: typing google.com really produces a redirect to www.google.com, and the browser then repeats most of the steps for the new name. The trace below follows the request to www.google.com, which is where the page is served.

DNS lookup

The browser has a name and needs an address. It looks in its own cache, then asks the operating system, which checks its cache and the hosts file, and then a query has to go to the configured DNS server, 192.168.1.1. That is the first thing the browser needs. It is not the first packet on the wire.

ARP for the gateway

To send anything to 192.168.1.1 the laptop needs that machine's MAC address, and its ARP cache is empty. So the page load begins with a broadcast asking who has 192.168.1.1. Because the DNS server and the default gateway are the same device here, this one ARP exchange serves for both. Every later packet to Google will be put in a frame addressed to that MAC.

$ ip route get 142.250.179.196
142.250.179.196 via 192.168.1.1 dev wlan0 src 192.168.1.23     # not on my subnet: send it to the gateway

$ ip neigh show 192.168.1.1
192.168.1.1 dev wlan0 lladdr 3c:37:86:5d:aa:01 REACHABLE          # after the ARP reply

The router's NAT changes the source address and port once, and remembers the mapping so that the SYN-ACK can be sent back to the laptop (Chapter 9). The destination never changes.     The 12 ms gap between the SYN and the SYN-ACK is the round-trip time. It is short because Google announces this address from sites all over the world, and the laptop reached the nearest one (Chapter 26). The ClientHello leaves 0.2 ms after the handshake completes and carries everything TLS 1.3 needs: the versions and ciphers on offer, a key share, the server's name in the clear, and a list of application protocols with h2 first. The server's reply spans three or four segments because of the certificate chain. After the ServerHello itself, everything is encrypted. The browser checks the certificate's name, dates and signatures up to a root it trusts, which takes about a millisecond of processing and no packets.

    HTTP/2 request

    The browser doesn't wait after sending its TLS Finished message. The HTTP/2 preface, its SETTINGS frame and the request go out in the same flight. To a capture they are indistinguishable TLS records. Decrypted, the request is one HEADERS frame on stream 1:

    HEADERS  stream 1  END_STREAM END_HEADERS
  :method     GET
  :scheme     https
  :authority  www.google.com
  :path       /
  user-agent        Mozilla/5.0 …

  accept-encoding   gzip, deflate, br, zstd

  :status           200
  content-type      text/html; charset=UTF-8

  cache-control     private, max-age=0
  alt-svc           h3=":443"; ma=2592000         # "next time, you may use HTTP/3"
DATA     stream 1  …

    The response headers arrive 52 ms after the request left: one 12 ms round trip, and 40 ms in which Google's edge passed the request to a server that built the page. The body follows at once. The first burst is about 14 kB, ten segments, because that is TCP's initial congestion window on a new connection (Chapter 13). The rest is sent as acknowledgements come back and the window grows. A page whose essential HTML and CSS fit in the first 14 kB can begin to render one round trip sooner than a page that doesn't.

    Rendering starts

    The browser doesn't wait for the whole document. Its parser works on the HTML as the bytes arrive, and a second, faster scanner runs ahead looking only for things to download: stylesheets, scripts, images, fonts. Each one found on the same origin becomes a new stream on the connection that is already open, with no handshake (streams 3, 5 and 7 in the trace). Anything on a different origin needs its own DNS lookup, TCP handshake and TLS handshake first, which is why pages that load from many origins start slowly, and what preconnect is for (Chapter 38). Once the browser has the HTML for the top of the page and the CSS that styles it, it lays the page out and paints it, here at about 130 ms.

    🧠
    The request that starts before you press Enter

    Chrome's engineers worked through this same budget and concluded that the surest way to shorten a page load was to begin it before the user had finished asking. The address bar watches what you type and predicts where you are going from your history. Type "goo" on a machine that visits Google daily and the browser is confident enough to act. At moderate confidence it resolves the name, so the DNS answer is already cached when you press Enter. At higher confidence it opens the connection as well, doing the TCP and TLS handshakes while you are still typing. At the highest it may fetch and render the whole page in a hidden tab and swap it in when you press Enter, so that the page appears with no visible wait. The browser also remembers, for each site, which other origins its pages needed last time, and connects to those as soon as navigation starts, without waiting for the HTML to mention them. None of this makes any packet faster. Every round trip in the trace above still happens and still takes 12 ms. They happen while the user is doing something else. This is the general form of the techniques in Chapter 38: a round trip that can't be removed can often be moved to a time when nobody is waiting for it.

    What the trace leaves out

    • The redirect. google.com answers with a 301 to www.google.com: a second name to resolve and a second connection.
    • IPv6. A real browser asks for the AAAA record as well as the A, and if it gets both it tries IPv6 first with IPv4 a fraction of a second behind, keeping whichever connects first (Chapter 20).
    • HTTP/3. Having seen the alt-svc header, or an HTTPS record in DNS, the browser will use QUIC next time and save a round trip (Chapter 18).
    • Encrypted DNS. Many browsers send the query over HTTPS to a public resolver, which needs its own connection first.
    • Everything beyond the edge. Inside Google the request passed through load balancers and several services before a page came back. Those are the 40 ms.
    ⚠️
    Common mistakes
    • Saying the laptop ARPs for Google. ARP only works on the local network. The laptop asks for the gateway's MAC.
    • Putting the server's MAC in the frame. The Ethernet destination is always the next hop.
    • Forgetting NAT. The server never sees 192.168.1.23.
    • Describing DNS as part of the connection. It is a separate exchange with a different machine, over UDP, before the connection exists.
    • Assuming every visit costs this much. Most page loads reuse caches and connections, and the cold case is the exception.
    • Describing the HTTP request as readable on the wire. After the ServerHello a capture shows only encrypted records, unless you have the session keys.

    Interview drill

    Explain it simply: Your laptop sends a packet to a web server on the internet. Whose MAC address is in the destination field of the Ethernet frame, and why?

    How a strong answer sounds
    The default gateway's, that is, my home router's. Ethernet delivers frames only within one local network, so a frame can only be addressed to a device on my LAN. When my laptop has a packet for an address, it compares the destination with its own subnet. The server isn't on it, so the routing table says to send the packet to the default gateway. The laptop looks up the gateway's MAC address in its ARP cache, sending an ARP request if it isn't there, and puts that MAC in the frame, while the IP header still carries the server's address as its destination. The router receives the frame, strips it off, looks up the IP destination in its own routing table, and builds a new frame for the next hop. So the MAC addresses change at every hop, and the IP addresses stay the same end to end, except that my router's NAT also replaces my private source address with its public one.

    Deeper: You load a page, and load it again a minute later. Which packets from the first load are absent from the second, and what makes each one unnecessary?

    How a strong answer sounds
    Nearly all the setup. There is no ARP, because the gateway's MAC address is in the neighbour cache, which stays valid while the entry is being used. There is no DNS query, because the answer is cached, in the browser and the operating system, for the record's TTL, typically a few minutes for a large site. There is no TCP handshake and no TLS handshake, because the browser keeps the HTTP/2 connection open after the first load, usually for minutes, and sends the new request as a new stream on it. So the second load is a HEADERS frame out and the response back: one round trip plus server time. Even the content may not be transferred: with validators such as ETag the browser sends a conditional request and gets a 304 with no body, and resources with a long max-age aren't requested at all. If the connection had been closed in the meantime, a TLS 1.3 session ticket from the first visit would let the browser resume without a full handshake, possibly with 0-RTT data; and having seen an alt-svc header, it might use HTTP/3 instead, combining transport and TLS setup. The general principle is that every layer caches what it learned, and the cold path is the rare case.

    🧠 Key takeaways

    • A cold page load is ARP, DNS, TCP, TLS and HTTP in that order, because each needs what the one before it provided.
    • The first packet on the wire is an ARP request for the gateway, since nothing can leave the subnet without its MAC address.
    • Frames are addressed to the next hop and packets to the final destination. MAC addresses change at every hop.
    • NAT rewrites the source address and port once, at the home router. The server sees only the public address.
    • Time to first byte here was 18 ms of DNS, three 12 ms round trips and 40 ms of server time.
    • A second visit reuses the caches and the open connection, and needs one round trip.
