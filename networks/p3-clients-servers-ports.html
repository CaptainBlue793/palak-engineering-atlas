Clients, Servers & Ports

An IP address gets a packet to a machine. It doesn't say which program on that machine should receive it: the web server, the SSH daemon or the database. Ports do that. This chapter covers who starts a conversation and who waits for one, what a port really is, and the five values that together identify one connection among the millions a busy server may hold, which is also why a single client machine can run out of connections long before the server does.

Client and server are roles, not machines

A server is the side that waits: it tells the operating system "deliver connections for port 443 to me" and then waits for them. A client is the side that starts the conversation by connecting to a known address and port. The roles describe one conversation, not the machine. Your API server is a server to browsers and a client of the database; a database replica is a client of the primary it replicates from.

The asymmetry matters in practice. The server's address and port must be known in advance, so they are fixed and published (in DNS, in a config file). The client's port doesn't need to be known by anyone, so the operating system picks a free one at random for each connection.

Ports: 16 bits that pick the program

A port is a 16-bit number (0–65535) in the TCP or UDP header (Chapter 7, Chapter 8). Every segment carries two: the source port and the destination port. When a packet arrives, the kernel uses them, together with the addresses, to find the socket it belongs to. TCP and UDP have separate port spaces: TCP port 53 and UDP port 53 are different things (DNS uses both).

Well-known ports you should recognise on sight: 22 SSH, 25 SMTP, 53 DNS, 80 HTTP, 123 NTP (UDP), 443 HTTPS (TCP, and UDP for HTTP/3). Nothing enforces these: you can run a web server on port 22. They are conventions that let clients find services without asking.

The 5-tuple names a connection

A TCP connection is identified by five values: protocol, source IP, source port, destination IP, destination port. Change any one of them and it's a different connection. That's how one server port can carry many connections at once: thousands of clients all connect to 203.0.113.10:443, but each has a different source address or source port, so each 5-tuple is unique.

$ ss -tan                                          # on the server: TCP, all states, numeric
State   Recv-Q Send-Q    Local Address:Port      Peer Address:Port
LISTEN  0      511             0.0.0.0:443            0.0.0.0:*        # waiting for new connections
LISTEN  0      128             0.0.0.0:22             0.0.0.0:*
ESTAB   0      0          203.0.113.10:443      198.51.100.7:51514     # laptop, tab 1
ESTAB   0      0          203.0.113.10:443      198.51.100.7:51516     # same laptop, tab 2: new source port
ESTAB   0      0          203.0.113.10:443     198.51.100.40:40112     # a phone
ESTAB   0      36         203.0.113.10:22       198.51.100.7:50022     # SSH from the laptop

Read the LISTEN lines first: those are servers waiting, with * as the peer because they have none. Each ESTAB line is one established connection, written from the server's point of view, so "Local" is the server and "Peer" is the client. Send-Q 36 on the SSH line means 36 bytes are sent but not yet acknowledged. Run ss -tlnp (listening, with process names) to see which program owns each listening port; it's the first command to run when something says "address already in use".

>>> import socket
>>> s = socket.create_connection(("example.com", 443), timeout=5)
>>> s.getsockname()                     # my end: my address and the port the OS picked
('192.168.1.23', 51514)
>>> s.getpeername()                     # their end (your addresses will differ)
('93.184.215.14', 443)

Listening sockets and connected sockets

On the server, two kinds of socket are involved, and confusing them is the most common misunderstanding about ports. The listening socket is bound to the port and never carries data; its only job is to receive new connection requests. Each time a client completes the handshake, the kernel creates a new connected socket for that connection, and accept() hands it to the program. All of them share local port 443. The kernel tells them apart by the full 5-tuple: an incoming packet goes to the connected socket whose 5-tuple matches exactly, and only a new connection request (a TCP SYN) goes to the listening socket.

The load test that topped out at 28,000 connections
An engineer load-tests a WebSocket server from one machine and finds the client fails at about 28,000 open connections with OSError: [Errno 99] Cannot assign requested address, while the server is barely busy. The 5-tuple explains it. Protocol, client IP, server IP and server port are all fixed, so the only thing that can differ between connections is the client's source port, and Linux hands those out from 32768–60999: 28,232 of them. The server isn't the limit; the client's port space is. The fixes all add variety to the tuple: more client IPs (several load-generator machines, or several addresses on one), more server ports or IPs, or a wider ip_local_port_range. Proxies and NAT gateways that open many connections to the same backend hit the same wall (Chapter 9).

  


  
⚠️
Common mistakes

    
    
      
  • Thinking a server needs a new port for each client. It doesn't: every connection shares the server's port, distinguished by the client's address and port.
    • 
      
  • Believing a server can handle "only 65,535 connections". The 16-bit limit applies per (client IP, server IP, server port) combination, not per server. Real limits are memory and file descriptors.
    • 
      
  • Hard-coding a client source port. Two connections from the same port to the same destination would have the same 5-tuple. Let the OS choose.
    • 
      
  • Reading ss from the wrong side. "Local" is the machine you ran it on; on a server, the client is the "Peer".
    • 
      
  • Forgetting TCP and UDP ports are separate. A firewall rule for TCP 53 doesn't allow DNS over UDP 53.
    • 
    


  
🎤
Interview drill

    
Explain it simply: Ports are 16 bits. How can a web server hold a million connections on port 443?

    
How a strong answer sounds
A connection isn't identified by the server's port alone but by the 5-tuple: protocol, client IP, client port, server IP, server port. All million connections share the server half, 203.0.113.10:443, but each has a different client IP or client port, so every tuple is unique. The 65,536-port limit only bounds how many connections one client IP can open to one server address and port. The server's real limits are memory per connection, file descriptors (ulimit -n) and CPU, which is why C10K and C10M were engineering problems, not port problems.

    
Deeper: A service that calls a single downstream API starts failing with "Cannot assign requested address" under load. What's happening and how do you fix it?

    
How a strong answer sounds
It's ephemeral port exhaustion on the calling side. Every outgoing connection to the same downstream IP and port needs a unique source port, and Linux has about 28,000 by default. If the service opens a new connection per request, and each closed connection also sits in TIME_WAIT for 60 seconds holding its port (Chapter 14), the range runs out at roughly 28,000 ÷ 60 ≈ 470 new connections per second. The best fix is connection reuse: an HTTP client with keep-alive and a connection pool, so a few hundred connections carry all the requests. Other levers are widening ip_local_port_range, adding source IPs or downstream addresses, and net.ipv4.tcp_tw_reuse for outgoing connections.

  


  

    
🧠 Key takeaways

    
    
      
  • The server listens on a known address and port; the client connects from a port the OS picks for it.
    • 
      
  • Ports are 16-bit numbers in the TCP/UDP header; TCP and UDP have separate port spaces.
    • 
      
  • A connection is identified by its 5-tuple: protocol, source IP, source port, destination IP, destination port.
    • 
      
  • A listening socket only accepts new connections; each accepted connection gets its own socket, matched by the full 5-tuple.
    • 
      
  • One client IP can open about 28,000 connections to one server ip:port on Linux defaults; the server itself has no such limit.
    • 
      
  • ss -tan shows the connection table; ss -tlnp shows who is listening on what.

Which values identify one TCP connection?

      

        
        
        
        
      

      
The 5-tuple. Change any one value and it's a different connection, which is how many clients share one server port.

    


    

      
You open two browser tabs to the same HTTPS site. How does the server tell the two connections apart?

      

        
        
        
        
      

      
Everything else is identical, so the source port is what makes each 5-tuple unique. (Browsers may also reuse one connection for both tabs, but if they open two, this is how they're told apart.)

    


    

      
What happens when a client sends a TCP SYN to a port where nothing is listening?

      

        
        
        
        
      

      
A closed port is answered immediately with RST. A timeout usually means a firewall dropped the SYN silently, a useful difference when debugging (P4).

    


    

      
With Linux's default ephemeral range, roughly how many simultaneous connections can one client IP open to 10.0.0.5:443?

      

        
        
        
        
      

      
Only the source port can vary, and the default range 32768–60999 has 28,232 ports. To go further, add client IPs, server addresses or ports, or widen the range.

    


    

      
In ss -tan on a server, a line reads LISTEN 0 511 0.0.0.0:443 0.0.0.0:*. What is it?

      

        
        
        
        
      

      
0.0.0.0 as the local address means "all interfaces", and * as the peer means there is no peer: it's a listener. 511 is the size of its queue of completed connections waiting for accept().
