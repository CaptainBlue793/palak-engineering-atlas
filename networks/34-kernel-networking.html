Kernel Networking: NICs, Interrupts & Zero-Copy

Every chapter so far has treated a host as a point: packets arrive, and recv() returns bytes. Between those two events is a long path through the machine, from the network card's memory through an interrupt, the kernel's protocol code and a queue, to a copy into the program. On a 10-gigabit link the smallest packets arrive every 67 nanoseconds, which is less time than one cache miss takes. That path is where a server's network capacity is decided, where packets are dropped without any counter that an application normally reads, and where the biggest efficiency gains of the last twenty years were made. This chapter follows a packet up the stack, and then looks at the ways the fastest systems shorten the journey or skip it.

NIC ring buffers and RSS

The receive ring is a fixed circle of slots, typically 512 to 4,096 of them, each pointing at a block of memory. The card fills slots and the kernel empties them. It absorbs bursts, and it is the first place a packet can be lost: if the kernel doesn't empty the ring fast enough, the card overwrites nothing and drops the new arrival.

One ring emptied by one CPU core would limit a 64-core server to the packet rate of a single core. So modern cards have many rings. With receive-side scaling (RSS), the card hashes each packet's 5-tuple and uses the result to choose a ring, each of which interrupts a different core. It is the same trick as ECMP in Chapter 30, for the same reasons: the load spreads over all the cores, and every packet of one connection reaches the same core, in order, with that connection's state already in its cache.

The card also takes over work that used to cost CPU time on every packet. These offloads explain something that puzzles everyone the first time they capture packets on a server:

The stack's cost is mostly per packet, not per byte, so handing it one 64 KB unit in place of 45 small ones is a large saving. It also means that a capture taken on a host shows what the kernel saw, which isn't quite what was on the cable.

Interrupts and NAPI polling

An interrupt is the right way to learn about a packet that arrives once a second: the CPU does other work and is told when there is something to do. At a hundred thousand packets a second it becomes expensive, since each interrupt costs a couple of microseconds of saving state and switching context before any real work is done. At a million a second it is fatal. The CPU spends all of its time entering and leaving the interrupt handler, the code that would process the packets never gets to run, and the machine does no useful work while being completely busy. This is receive livelock.

Linux's answer, called NAPI, is to change mode with the load. The first packet raises an interrupt. The driver then switches the card's receive interrupts off and asks the kernel to poll the ring. The kernel takes packets in batches of up to 64, and keeps polling for as long as it keeps finding them. Only when the ring is empty are interrupts switched on again. A quiet system gets the low latency of interrupts, and a busy one gets the efficiency of polling, with about one interrupt for every batch.

A model with round costs: 2 µs to take an interrupt, 1 µs for the kernel to process a packet, 0.5 µs for the application to use it, and 0.08 µs per packet in total for a bypass framework. RSS divides the packets evenly among the cores.

Things to notice. At 100,000 packets a second everything works, and interrupt-per-packet spends more of the core on interrupts (20%) than on the packets themselves. At a million a second, interrupt-per-packet delivers nothing: the core is 100% busy in interrupt handlers and every packet is dropped, which is livelock. NAPI at the same rate delivers about 650,000 and drops the rest cheaply at the card, with the core fully used for real work. Spread the load over four cores with RSS and all of the million get through. At 10 million a second the kernel's path can't keep up even with eight cores, and bypass handles it on one, because it spends 0.08 µs on a packet where the kernel spends 1.5. Look at bypass at the lowest rate too: the core is still at 100%, spinning on an empty ring, because it never sleeps.

The socket buffer

After protocol processing, the data waits in the socket's receive buffer until the program asks for it. This is the buffer of Chapter 12. If the program is slow, TCP's advertised window closes and the sender waits, which costs time and loses nothing. UDP has no such signal, so a full buffer means dropped datagrams, counted only in the "receive buffer errors" shown earlier.

The last step is a copy. recv() copies bytes from kernel memory into the program's own buffer, and send() copies them the other way. A copy runs at several gigabytes a second, so nobody notices for small messages. For a server whose whole job is moving large amounts of data that it never looks at, the copies are most of the work.

sendfile and zero-copy

# Serving a file the plain way: every byte crosses into the program and back out
while chunk := f.read(65536):          # copy 1: page cache → the program's buffer
    conn.sendall(chunk)                # copy 2: the program's buffer → socket buffer

# With sendfile: the kernel links the cached pages straight into the socket
os.sendfile(conn.fileno(), f.fileno(), 0, size)       # no copies through the program, and one system call

Zero-copy is why a static file server or a message broker can fill a 10-gigabit link with a fraction of one core. Kafka's throughput rests on it: the broker sends stored message batches from the page cache to consumers with sendfile and never brings them into its own memory.

DPDK and XDP

The kernel's path is general. It handles every protocol, applies firewall rules, accounts for memory and wakes processes, and for that it spends a microsecond or two on each packet, which is roughly a million packets a second per core. A 100-gigabit card can deliver 148 million small packets a second. For software whose only job is moving packets, such as routers, load balancers, firewalls and mobile network cores, two approaches get past the limit.

🧠
Cloudflare: how to drop ten million packets a second

A service under a volumetric attack has one job that matters above all others, which is to throw the attack packets away for less than it costs the attacker to send them. In 2018 Cloudflare's Marek Majkowski measured the options on a single core of an ordinary server, sending it floods of small packets and discarding them at different points on the receive path. Letting the packets reach an application that read and ignored them managed about 175,000 a second. Dropping them with a firewall rule in the usual place reached about 600,000, since each packet had still been wrapped in the kernel's packet structure and carried part-way up the stack first. Moving the rule earlier in the path reached about 1.7 million. An XDP program, run by the network driver on the raw packet in the receive ring before anything is allocated for it, discarded 10 million packets a second on that one core. The same packet is fifty times more expensive to drop if you wait until it reaches the application. Unlike full bypass, XDP leaves the kernel in charge of everything the program lets through, so legitimate traffic still gets the normal TCP stack and all the normal tools still work. Cloudflare built its attack filtering on it, Facebook built its layer-4 load balancer on it, and it is the reason a modern server can ride out a flood that would have needed dedicated hardware ten years earlier.

⚠️
Common mistakes
  • Looking for packet loss only on the network. Check the host's own counters: the card's ring, the per-CPU backlog, the socket buffers.
  • All of a card's interrupts on one core. One core at 100% in softirq while the others idle. Check /proc/interrupts and the RSS settings.
  • Trusting packet sizes and checksums in a capture taken on the host. Offloads mean it isn't what was on the wire.
  • A UDP service with a default receive buffer. Bursts overflow it silently. Size the buffer and watch the error counter.
  • Reaching for kernel bypass first. It costs dedicated cores, your own protocol stack and most of your debugging tools. Tune the kernel path, then consider XDP.
  • Copying bulk data through the application. For files and stored messages, sendfile is simpler as well as faster.

Interview drill

Explain it simply: What happens inside a Linux machine between a packet arriving at the network card and an application reading it?

How a strong answer sounds
The network card receives the frame and writes it by DMA into a slot of its receive ring, a set of buffers the driver allocated in advance. If the card has multiple queues, it first hashes the packet's 5-tuple to choose a queue, which is receive-side scaling, so that flows are spread over CPU cores. The card raises an interrupt on that queue's core. The driver's handler does very little: it disables further receive interrupts for the queue and schedules NAPI polling. In softirq context the kernel then pulls packets from the ring in batches, builds an sk_buff for each, possibly merges segments with GRO, and passes them up through netfilter, IP and TCP or UDP. TCP validates sequence numbers, generates ACKs and places the data on the socket's receive queue; the process waiting in recv or epoll_wait is woken. When the application calls recv, the data is copied from kernel memory into its buffer. Drops can occur at the ring if the kernel is too slow to drain it, at the per-CPU backlog, or at the socket buffer for UDP.

Deeper: A server shows packet loss under load although the network path is clean, and one CPU core is at 100% while the others are mostly idle. What is going on?

How a strong answer sounds
All the receive processing is landing on one core. That core is saturated in softirq, you would see ksoftirqd busy on it, so it can't drain the card's receive ring fast enough, and the card drops incoming frames when the ring is full; those show up as rx_missed or rx_dropped in ethtool -S, not as anything on the network. I'd check /proc/interrupts to see how the card's queue interrupts are distributed across CPUs, ethtool -l for the number of queues configured, and /proc/net/softnet_stat for drops and budget exhaustion per CPU. Likely causes: the card is configured with a single queue; RSS is on but the interrupts are all pinned to one core, or irqbalance isn't spreading them; or the traffic is a single flow or a tunnel whose outer headers all hash alike, so that RSS has nothing to spread. Fixes: enable more queues and spread their interrupts across cores; for traffic that hashes to one queue, turn on software steering (RPS) or change the hash inputs; increase the ring size to absorb bursts; and make sure GRO is on to reduce the per-packet cost.

🧠 Key takeaways

  • A received packet goes from the card's ring, through an interrupt and batched polling, up the protocol stack to a socket buffer, and is then copied to the application.
  • Each queue on that path can overflow. Host-side drop counters are separate from anything the network reports.
  • RSS hashes flows onto several rings and cores. Offloads let the stack handle large units, so host captures don't match the wire.
  • An interrupt per packet collapses under load. NAPI takes one interrupt and then polls in batches.
  • sendfile and zero-copy sends move data without copying it through the application.
  • The kernel stack handles about a million packets a second per core. XDP and kernel bypass handle ten times that by doing far less per packet.

Check your understanding

A server's network card reports a rising rx_missed_errors count. What does that mean?

The loss is inside the host, before the kernel ever saw the packets.

What does receive-side scaling do?

Load spreads across cores, and every packet of a connection stays on one core, in order.

Why does a design that takes one interrupt per packet fail at very high packet rates?

Receive livelock. NAPI avoids it by turning interrupts off and polling while there is work.

A capture taken on a sending server shows TCP packets of 30,000 bytes on a 1,500-byte Ethernet link. What explains it?

The capture sees what the kernel sent to the driver. The wire carried MTU-sized segments.

What does a kernel-bypass framework such as DPDK give up in exchange for its speed?

The application owns the card and polls it constantly, so everything the kernel provided must be replaced.
