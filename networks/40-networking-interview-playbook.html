Networking Interview Playbook

Networking questions in interviews come from a small set, and the best-known of them, "what happens when you type a URL and press Enter?", contains most of the others. An interviewer asking it wants to hear two things: that you know the path a request takes through every layer, and that you can choose how much to say about each. This chapter maps the questions onto the chapters of this course, gives a two-minute answer to the URL question, shows how to answer "TCP or UDP?" properly, sets out a method for troubleshooting questions, and ends with statements that sound right and aren't.

  • Place any networking question on the layer it belongs to
  • Give the URL answer in two minutes, and go deeper on any step when asked
  • Compare TCP and UDP by what each provides, with a reason to choose either
  • Answer a troubleshooting question as an ordered series of checks
  • Spot the trap in a statement that is nearly true

The URL question, layer by layer

The whole path first, at an even depth. Each step is one sentence when spoken, and each is a place the interviewer may stop you and ask for more.

Spoken, at about two minutes:

"The browser parses the URL into scheme, host and path. It needs an IP address for the host, so it checks its own DNS cache and the operating system's, and otherwise asks the configured resolver, which either has the answer cached or walks down from the root servers to the domain's authoritative server.

With the address, the browser opens a TCP connection to port 443. The destination isn't on my local network, so my machine sends the packet to its default gateway, using ARP to find the gateway's MAC address. My router translates my private address to its public one, and the packet is routed across several networks, hop by hop, along paths set up by BGP. The TCP handshake is SYN, SYN-ACK, ACK, which takes one round trip.

Then TLS. The client and server agree keys with a Diffie–Hellman exchange, and the server proves its identity with a certificate that chains to a root my browser trusts. With TLS 1.3 that is one more round trip. Now the browser sends the HTTP request, most likely over HTTP/2, and at the far end it probably reaches a CDN edge or a load balancer, which ends the TLS connection and forwards the request to an application server.

The response comes back with a status, headers and the HTML. The browser starts parsing, finds stylesheets, scripts and images, and requests those too, reusing the connection. So before the first byte there were three round trips and a DNS lookup. I can go deeper on any of those steps."

The last sentence matters. It hands the choice of depth back to the interviewer, and shows you know there is more.

The answer that never ends

There is a public repository on GitHub named what-happens-when, started in 2013 by an engineer who wanted to see how complete an answer to this question could be made. Hundreds of people have contributed to it. It begins before the browser, with the keyboard's circuit closing when the "g" key is pressed, the USB controller polling for the event, and the operating system's interrupt handler delivering it to the window with focus. It carries on through the browser's URL parsing, HSTS lists, DNS, ARP, sockets, TLS, HTTP, the server's request handling, HTML parsing, CSS, the rendering tree and the graphics card, and it is still described as unfinished. The repository is popular because the question has no bottom. Every sentence of an answer can be opened into a page. This is why interviewers like the question, and why a candidate who tries to say everything fails it: after ten minutes they are still describing DNS. What is being tested is whether you can cover the whole path at one depth, in order, with nothing important missing, and then go down exactly where you are asked to.

TCP vs UDP done well

The weak answer is "TCP is reliable and UDP is unreliable, so UDP is faster". It is close to true and shows no understanding. The strong answer says what each one provides, what that costs, and how the choice is made.

TCPUDP
Gives the applicationA stream of bytes, in order, with nothing missing or duplicatedSeparate datagrams, which may be lost, duplicated or reordered
Before sendingA handshake: one round tripNothing
If a packet is lostIt is sent again, and everything after it waitsNothing happens. The application decides
Sending rateLimited by flow control and congestion controlWhatever the application sends
Message boundariesNone. The application must frame its own messagesKept: one send is one datagram
Header20 bytes or more8 bytes
Chosen whenEvery byte matters: web pages, APIs, files, databasesLate data is useless (voice, games), the exchange is one small question and answer (DNS), or the application brings its own reliability (QUIC)

Three points lift the answer further. UDP's speed comes from skipping the handshake and from never making new data wait behind a lost packet, and an individual datagram travels no faster than a segment. Choosing UDP means writing whatever you still need yourself, and for most uses that includes congestion control. And QUIC shows the two are no longer opposites: HTTP/3 gets reliable, ordered streams by building them on top of UDP (Chapter 18).

Troubleshooting questions

"Users say the site is down. What do you do?" is asking for a method, and guessing a cause is the wrong response. Start by narrowing the complaint: all users or some, one region or all, since when, and what changed. Then follow the request along its path, with one check per step. Each check either clears a layer or points to it.

StepCheckIf it fails
Does the name resolve?dig example.com, and against a second resolverDNS: an expired domain, a wrong record, a failed provider
Is the address reachable?ping, mtr or tracerouteRouting or a link. But ICMP is often blocked, so a failure here proves little
Does the port accept connections?nc -vz host 443Timed out: a firewall is dropping. Refused: nothing is listening
Does TLS complete?openssl s_client -connect host:443An expired or mismatched certificate, or a protocol mismatch
Does the application answer?curl -v, then curl -w for the timingsA 5xx status: the application or its backends. Slow first byte: the server's own time
Is it the same from elsewhere?The same checks from another network or regionA regional fault: a CDN site, a route, one data centre

Say what each result would tell you as you go, and say what you would do if you had access to the server as well: ss -ltn to see what is listening, the load balancer's health checks, and a packet capture when the two ends disagree (Chapter 37).

Trick questions

Twelve statements of the kind an interviewer offers to see whether you will agree. Some are true. Decide, then read why.

Most of the false ones are false in the same way: a rule that holds in the simple case has been stated without its condition. TCP is reliable until the path fails. HTTPS hides the content and leaves the destination visible. HTTP/2 removes head-of-line blocking at its own layer and not below it. When a statement in an interview contains "always", "never", "guarantees" or "can't", look for the condition that has been left out.

Common mistakes
  • Reciting the seven OSI layers and stopping. Name a layer when it explains something.
  • Going deep on the first step of the URL question and running out of time before TCP.
  • Leaving out DNS, or ARP and the gateway. These are the steps people forget, and interviewers notice.
  • Guessing a cause in a troubleshooting question before asking who is affected and what changed.
  • Agreeing with a statement because it sounds familiar. Check it for a missing condition first.
  • Bluffing. "I don't know that one, but here is how I'd find out" is a good answer, and inventing a detail is a bad one.

Interview drill

Explain it simply: What happens when you type a URL into a browser and press Enter? You have thirty seconds.

How a strong answer sounds
The browser resolves the hostname to an IP address through DNS, checking caches first and otherwise asking a resolver. It opens a TCP connection to that address on port 443 with a three-way handshake; the packets leave my network through the default gateway and are routed across the internet. Over that connection it does a TLS handshake, which agrees encryption keys and verifies the server's certificate. Then it sends an HTTP GET request, the server, usually behind a load balancer or CDN, returns the HTML, and the browser parses it and fetches the other resources it refers to over the same connection. That is DNS, TCP, TLS, HTTP, and I'm happy to go into any of them.

Deeper: A user reports that your website is down. Walk me through how you would find out why.

How a strong answer sounds
First I'd scope it: is it one user or many, one region or everywhere, all pages or some, and when did it start; and I'd check monitoring and whether anything was deployed or changed around that time, because most outages follow a change. Then I'd test the path a request takes, from the outside in. Does the name resolve, to the expected address, from more than one resolver? If not, it is DNS: registration, records, or the provider. Can I open a TCP connection to port 443? A timeout suggests packets are being dropped, a security group, firewall or routing problem, or a load balancer with nothing behind it; a refusal means nothing is listening. Does the TLS handshake complete, or has a certificate expired? Then an HTTP request with curl: a 5xx tells me the network path works and the application or a dependency is failing, so I'd move to load balancer health checks, application logs and the database. If it is slow instead of failing, curl -w splits the time into DNS, connect, TLS and server time. I'd repeat the checks from another network to see whether it is regional. If the two ends disagree, the client says it sent and the server says nothing came, I'd take packet captures on both. Throughout I'd communicate what I've ruled out, and if a recent change is the likely cause I'd roll it back first and investigate afterwards.

🧠 Key takeaways

  • Most networking questions belong to a layer, and saying which one starts the answer well.
  • The URL answer is DNS, the first hop, routing, TCP, TLS, HTTP, the server side and the response, at an even depth, with an offer to go deeper.
  • Compare TCP and UDP by what each gives the application and what that costs. "Reliable" and "fast" are not enough.
  • Troubleshooting answers are an ordered series of checks along the request's path, each with a tool and a meaning.
  • Statements with "always", "never" and "guarantees" usually have a condition left out.
  • Saying how you would find something out is better than inventing it.

Check your understanding

You have two minutes for the URL question. Which approach is best?

The question tests coverage and judgement about depth. The interviewer will choose where to dig.

"A server can't hold more than 65,535 TCP connections, because there are only that many ports." Why is this false?

The limit is memory and file descriptors. The 65,535 figure limits one client address connecting to one server address and port.

Which statement about choosing UDP is the most accurate?

UDP removes the handshake and the waiting behind lost packets. Everything else becomes the application's job.

The name resolves correctly and nc -vz host 443 succeeds, but curl returns status 503 in 200 ms. Where is the problem?

A status code is proof that DNS, routing, TCP and TLS all worked.

"HTTPS means nobody on the network can tell which site you are visiting." What is wrong with this?

TLS protects what is said. Who is being spoken to is still visible to the network.
