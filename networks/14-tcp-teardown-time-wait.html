Closing Connections & TIME_WAIT

Opening a TCP connection takes three segments and is over in one round trip. Closing one takes four, can be done by either side, can be done one direction at a time, and leaves one of the two ends holding state for a full minute afterwards. Most of the time none of that is visible. Then a server refuses to restart because its address is "already in use", a load test fails with "cannot assign requested address", or a log fills with "connection reset by peer", and each of those is the closing sequence showing through. This chapter covers the orderly close, the abrupt one, and the minute of waiting in between that people most often try to switch off.

FIN, ACK, FIN, ACK

A TCP connection is two independent streams, one in each direction, and each is closed separately. A segment with the FIN flag means "I have no more data to send". Like a SYN, it takes up one sequence number, so it is acknowledged and retransmitted like data. The other side can go on sending for as long as it likes, and closes its own direction with its own FIN.

10:14:09.412 IP 10.0.0.5.51000 > 93.184.216.34.443: Flags [F.], seq 1215, ack 9402, win 501, length 0
10:14:09.494 IP 93.184.216.34.443 > 10.0.0.5.51000: Flags [F.], seq 9402, ack 1216, win 508, length 0     # ACK and FIN combined
10:14:09.494 IP 10.0.0.5.51000 > 93.184.216.34.443: Flags [.], ack 9403, win 501, length 0

The side that sends the first FIN is the active closer, and the other is the passive closer. They pass through different states, and a socket that stays in one of them is a diagnosis in itself:

Half-closed connections

Between the first FIN and the second, the connection is half-closed: one direction is finished and the other still works. A program can ask for that deliberately with shutdown, which closes the sending direction and keeps the socket open for reading:

# Send a request of unknown length, signal its end, then read the whole reply
sock.sendall(request_bytes)
sock.shutdown(socket.SHUT_WR)        # sends FIN: "that is all from me". The peer's recv() returns b''
reply = bytearray()
while chunk := sock.recv(65536):     # still allowed: the other direction is open
    reply += chunk
sock.close()

It is the stream's own way of saying "end of message" (Chapter 8 listed it among the framing rules). Use it with care across the internet. Some NAT devices, proxies and load balancers treat the first FIN as the end of the whole connection and drop a half-closed one after a short idle period.

RST: the abrupt end

A segment with the RST flag ends a connection immediately. There is no exchange, it isn't acknowledged, any data still in transit or in buffers is discarded, and neither side enters TIME_WAIT. A reset is sent in these situations:

  • A segment arrives for a connection the host doesn't have. A SYN to a port with no listener gets one ("connection refused"). So does any segment arriving after the host has rebooted, or after a NAT or firewall in the path has forgotten the connection (Chapter 9).
  • A program closes a socket that still has unread data. The kernel can't deliver that data to anyone, and says so by sending RST in place of FIN.
  • A program asks for it, by setting SO_LINGER with a timeout of zero before closing.
  • A device in the middle sends one to both ends, usually on an idle timeout or a policy decision.

    Things to notice. In the orderly close, the server is finished the moment the last ACK arrives, while the client, which closed first, holds its end for another minute. In the half-close, data goes on flowing towards a side that has already sent its FIN, and that side still acknowledges it. The third scenario is the reason for TIME_WAIT. The final ACK is lost, the server sends its FIN again, and the client is still there to answer it. If the client had forgotten the connection, the answer would have been a reset, and the server would have reported an error on a connection that had in fact closed cleanly. In the last scenario two segments end everything, and the server's program gets an exception where it expected an end of stream.

    TIME_WAIT and 2×MSL

    The active closer waits for twice the maximum segment lifetime, the longest a packet could plausibly survive in the network. Linux fixes the wait at 60 seconds. It is there for two reasons:

    • To finish this connection properly. If the last ACK is lost, the peer retransmits its FIN, and something must still be there to acknowledge it.
    • To protect the next connection. A delayed segment from the old connection could arrive after a new one has been opened with exactly the same addresses and ports, and be accepted as data. Refusing to reuse that combination for a while lets strays die out.

    The cost is one remembered 4-tuple, and a few hundred bytes, per closed connection for a minute. On a server that is harmless: its side of each tuple is the same port, the other side is thousands of different clients, and a hundred thousand TIME_WAIT entries are a few megabytes. It bites in one situation, when a machine makes many outgoing connections to the same destination address and port, and closes them itself. Then only the source port can vary:

    $ sysctl net.ipv4.ip_local_port_range
net.ipv4.ip_local_port_range = 32768  60999         # 28,232 source ports

# Each closed connection keeps its port for 60 s, so towards one destination:
#   28,232 ports / 60 s  ≈  470 new connections a second, sustained. Beyond that:
OSError: [Errno 99] Cannot assign requested address

$ ss -tan state time-wait | wc -l
28104

    That is a proxy, a load generator, or a service that opens a new connection to its database or cache for every request. The fixes, in order of preference:

    🧠
    tcp_tw_recycle: the tuning tip that dropped real users

    For about a decade, "kernel tuning" guides for busy Linux servers recommended one line: net.ipv4.tcp_tw_recycle = 1. It made the count of TIME_WAIT sockets fall, which looked like progress. What it actually did was make the kernel remember the latest TCP timestamp seen from each remote IP address and reject any new connection from that address whose timestamp was older, on the reasoning that it must be a stray from the past. That is sound when one address is one machine. Behind a NAT it isn't (Chapter 9): an office, or a mobile operator, puts thousands of devices behind one address, each with its own timestamp clock. A server with the setting on would accept a connection from one phone and then silently drop SYNs from every other phone behind the same address whose clock happened to be behind. The users saw connections that sometimes hung for a few seconds or failed, only from some networks, with nothing in the server's logs, and operators spent weeks blaming load balancers and mobile carriers. The explanation, set out most clearly in Vincent Bernat's article "Coping with the TCP TIME-WAIT state on busy Linux servers", is that the option was removing a safety mechanism to solve a problem those servers didn't have. The kernel developers removed it altogether in Linux 4.12, in 2017. The state that was tidied away had been doing nothing but protecting connections.

    SO_REUSEADDR and restarting a server

    $ python3 server.py
OSError: [Errno 98] Address already in use

    This is the same mechanism seen from a listening socket. You stopped a server, which closed its connections, so it was the active closer, and those connections are now in TIME_WAIT on its port. By default bind() refuses a port while any connection, in any state, still uses it. SO_REUSEADDR relaxes that to the sensible rule: binding is allowed unless another socket is actively listening on the port.

    srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)    # before bind(). Every server should set this
srv.bind(("0.0.0.0", 8080))
srv.listen(511)

    It doesn't weaken TIME_WAIT. The old connections' tuples stay reserved, and new connections from other clients are unaffected. Don't confuse it with SO_REUSEPORT, which lets several processes listen on one port at the same moment and share incoming connections.

    ⚠️
    Common mistakes
    • Treating TIME_WAIT sockets on a server as a leak. They cost almost nothing and expire in a minute. Look for CLOSE-WAIT if you suspect a leak.
    • Never calling close() after recv() returns no bytes. The socket sits in CLOSE-WAIT for ever and the process runs out of file descriptors.
    • Closing a socket with data still unread. The peer gets a reset, and may lose the reply you had just sent.
    • Using SO_LINGER zero to "avoid TIME_WAIT". It replaces an orderly close with an abort.
    • Forgetting SO_REUSEADDR on a listening socket. The server can't be restarted for a minute after it stops.
    • Assuming "connection reset by peer" means the peer crashed. Often a firewall, NAT or load balancer in between timed the connection out.
    🎤
    Interview drill

    Explain it simply: How does a TCP connection close, and what is TIME_WAIT for?

    How a strong answer sounds
    Each direction closes separately. The side that closes first sends a FIN, meaning it has no more data to send, and the other side acknowledges it. The connection is then half-closed, and the other side can still send. When it has finished, it sends its own FIN, which the first side acknowledges. So there are four segments, often seen as three because the middle ACK and FIN combine. The side that sent the first FIN then stays in TIME_WAIT for twice the maximum segment lifetime, 60 seconds on Linux. There are two reasons. If its final ACK was lost, the peer will retransmit its FIN, and the closer must still know the connection in order to acknowledge it and not answer with a reset. And it stops a new connection with the same four-tuple being opened straight away, so that delayed segments from the old connection can't be mistaken for data in the new one.

    Deeper: A service that calls another service starts failing under load with "cannot assign requested address". What is going on, and how do you fix it?

    How a strong answer sounds
    That error on connect means the kernel couldn't find a free local port for a new outgoing connection to that destination. A connection is identified by source address, source port, destination address and destination port; with the last three fixed, only about 28,000 ephemeral ports can vary. If the caller opens a new connection per request and closes it itself, each closed connection sits in TIME_WAIT for 60 seconds holding its port, so the sustainable rate is under 500 new connections a second to one destination. I'd confirm with ss, counting sockets in TIME_WAIT towards that address. The proper fix is connection reuse: HTTP keep-alive or a connection pool, so that requests share long-lived connections. As mitigations I'd enable tcp_tw_reuse, which safely lets outgoing connections reuse TIME_WAIT ports using timestamps, widen the local port range, or spread connections over more destination addresses. I wouldn't force resets with SO_LINGER, and tcp_tw_recycle is gone because it broke clients behind NAT. If a NAT gateway sits in the path I'd check its port limits as well, since the symptom is similar.

    🧠 Key takeaways

    • Each direction of a connection is closed by its own FIN and ACK: four segments, often seen as three.
    • Between the two FINs the connection is half-closed, and data can still flow one way.
    • A reset ends a connection at once and can discard data. The peer's program sees an error where a clean close would give an end of stream.
    • The side that closes first waits in TIME_WAIT for 60 seconds, so that a lost final ACK can be repaired and stray old segments die out.
    • TIME_WAIT is harmless on servers. It exhausts ports on clients that open and close many connections to one destination; reuse connections.
    • Set SO_REUSEADDR on listening sockets, and treat many CLOSE-WAIT sockets as a bug in your own code.

    Check your understanding

    A client sends a FIN and receives an ACK for it. What can the server still do?

    A FIN closes one direction only. The connection is half-closed until the server's FIN.

    After an orderly close, which side is in TIME_WAIT?

    The active closer sends the final ACK, so it must stay around in case that ACK is lost.

    A server shows 20,000 sockets in CLOSE-WAIT, and the number keeps growing. What is the most likely cause?

    CLOSE-WAIT means "the peer's FIN has arrived and the local program hasn't called close". Only the program can leave it.

    A program calls close() on a socket whose receive buffer still holds unread data. What does the kernel send?

    An orderly FIN would claim everything was received. The reset tells the truth, and the peer sees "connection reset".

    A server is stopped and started again at once, and bind() fails with "Address already in use". What fixes it properly?

    Old connections in TIME_WAIT on that port block a plain bind. The option allows it as long as nothing else is listening.
