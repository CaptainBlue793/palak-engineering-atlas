DHCP

Connect a laptop to a network it has never seen and, a second later, it has an IP address, knows which router leads to the internet and knows which servers answer DNS. Nobody typed any of that in. The Dynamic Host Configuration Protocol handed it over, in four small packets sent before the laptop had an address to send them from. DHCP is easy to overlook because it nearly always works. When it doesn't, the symptoms look like other problems: "the Wi-Fi is connected but nothing loads", an address beginning 169.254, or half an office on the wrong subnet for no visible reason.

What a new device needs

To use an IP network a host needs four facts: its own address, the subnet mask that says which addresses are local, the default gateway for everything else, and at least one DNS server. A machine that has just been plugged in has none of them, and it doesn't know where to ask. It can still do one thing, which is to send a frame to the broadcast address that every device on the local network receives (Chapter 2). DHCP is built on that.

DORA: discover, offer, request, acknowledge

Leases and renewal

An address isn't given, it is leased for a fixed time. Without that, every phone that ever visited a café would hold one of its addresses for ever. The client is responsible for keeping its lease alive:

  • At half the lease time it sends a REQUEST straight to the server that granted it, as an ordinary unicast packet, and the ACK restarts the clock.
  • At seven-eighths, if that server never answered, it broadcasts the REQUEST so that any DHCP server can extend the lease.
  • At expiry it must stop using the address and start again from DISCOVER.

A device that leaves cleanly can send a RELEASE. Most just vanish, and their address stays reserved until the lease runs out. That is the trade-off behind the lease length:

Short lease (minutes to an hour)Long lease (a day to a week)
Addresses of departed devicesCome back quicklyStay locked for days
Renewal traffic and server loadHigherNegligible
If the DHCP server is downDevices start losing their addresses within the hourExisting devices carry on for days
SuitsCafés, conferences, guest Wi-Fi: many visitors, small poolOffices and homes: the same devices every day

When a DISCOVER gets no answer at all, most systems give up after a few tries and assign themselves a link-local address from 169.254.0.0/16. It lets devices on the same cable find each other, and it reaches nothing else. An address beginning 169.254 is therefore a precise diagnosis: the link works, and no DHCP server answered.

What just happened
    Devices that are still in the café renew at half the lease time. A device that walks out says nothing, so its lease stays in the table, in amber, until it expires. A device that couldn't get an address tries again each time the clock moves.

    Things to notice. Let five devices join and the pool is full. The sixth broadcasts DISCOVER, hears nothing back, and ends up with a 169.254 address: connected to the Wi-Fi, and unable to reach anything. Now have two devices walk out. Nothing changes in the table, and a seventh device still gets no address, because the server can't know they have gone. Only after their leases expire, an hour after they were last renewed, do the addresses return and the waiting devices get them. With a 24-hour lease the same café would be "full" all day after its first five customers. The fix for a busy guest network is a bigger pool or a shorter lease, and both are a line of configuration.

    Relays: one server, many subnets

    A broadcast stops at the first router (Chapter 5), so DHCP as described works only when the server is on the same LAN as the client. A company with two hundred subnets doesn't want two hundred DHCP servers. The answer is a relay agent, usually a function of the router itself. It listens for DHCP broadcasts on each local network, and forwards them as ordinary unicast packets to a central server, after writing the address of the interface they arrived on into a field of the message. The server reads that field to decide which subnet's pool to choose from, and replies through the relay.

    # On the router, for the interface facing the office LAN (Cisco style)
interface Vlan20
 ip address 10.20.0.1 255.255.255.0
 ip helper-address 10.0.5.10          # forward DHCP broadcasts heard here to the server at 10.0.5.10

    Cloud networks have no broadcast at all. A virtual machine still sends its DISCOVER, and the platform's virtual network answers it directly with the address that was assigned when the instance was created. Kubernetes pods don't use DHCP: their addresses are assigned by the network plugin (Chapter 31).

    Rogue DHCP servers

    Look at DORA again as an attacker would. The client broadcasts for help and believes whoever answers first. Nothing in the protocol authenticates the server. Any machine on the LAN that answers DISCOVERs becomes, for its victims, the authority on which gateway and which DNS servers to use, and so can send their traffic through itself or resolve names to addresses of its choosing.

    The usual rogue is an accident. Somebody plugs a home Wi-Fi router into an office wall socket by one of its LAN ports. It starts offering 192.168.0.x addresses with itself as the gateway, and every device that takes its offer first lands on a network with no route to anything. The symptom is "the internet is down" for a random share of one floor, fixed by reconnecting and broken again at the next renewal.

    🧠
    TunnelVision: a 2002 DHCP option looks round your VPN

    In May 2024 researchers at Leviathan Security published an attack on VPNs that used nothing but DHCP as designed. A VPN protects traffic on an untrusted network, such as hotel Wi-Fi, by adding a route that sends everything into an encrypted tunnel. The researchers noticed that DHCP has, since 2002, an option numbered 121 that lets the server hand the client extra routes, and that operating systems install those routes without question. A route for a narrower range of addresses always wins over a broader one (Chapter 5). So an attacker who runs the DHCP server, which on a hostile Wi-Fi network is trivial, can supply routes that are more specific than the VPN's own. The victim's packets then leave by the ordinary interface, outside the tunnel and unencrypted, while the VPN app goes on showing "connected". Windows, macOS, Linux and iOS were all affected. Android wasn't, for the simple reason that it had never implemented option 121. No bug was exploited, since every component did what its specification said, and fixes had to be made in each VPN client, mostly by isolating the tunnel in its own network namespace or by firewall rules that refuse to send traffic any other way. A device's whole view of the network is handed to it by an unauthenticated broadcast protocol, and anything that relies on that view needs to say what happens when it is a lie.

    ⚠️
    Common mistakes
    • Reading "connected, no internet" as a Wi-Fi fault. Check the address first. 169.254.x.x means no DHCP answer, and an unexpected subnet means the wrong server answered.
    • Long leases on a guest network. The pool fills with devices that left hours ago.
    • A pool that overlaps statically configured addresses. Two devices end up with the same address. Reserve a range outside the pool, or use DHCP reservations.
    • Forgetting the relay when adding a subnet. Devices there broadcast to nobody.
    • One DHCP server with short leases. When it fails, the whole network starts losing addresses within the lease time.
    • Trusting DHCP-supplied settings on hostile networks. Gateway, DNS and routes all come from whoever answered.
    🎤
    Interview drill

    Explain it simply: How does a device get an IP address when it joins a network?

    How a strong answer sounds
    Through DHCP, in four messages over UDP, often called DORA. The device has no address, so it broadcasts a DISCOVER from 0.0.0.0 to 255.255.255.255, port 68 to port 67, carrying its MAC address. A DHCP server on the network replies with an OFFER: an available address, plus the subnet mask, default gateway, DNS servers and a lease time. The device broadcasts a REQUEST naming the offer it accepts, so that other servers know to withdraw theirs, and the chosen server confirms with an ACK. The device configures its interface and usually checks with ARP that the address isn't already in use. The address is leased, not owned: at half the lease time the client renews it directly with the server, and if it can't renew before expiry it must give the address up. If no server answers at all, the device assigns itself a link-local 169.254 address, which only works on the local link.

    Deeper: Users on one floor intermittently get "no internet". Their addresses turn out to be 192.168.0.x, where the office uses 10.20.0.0/24. What is happening?

    How a strong answer sounds
    There is a second DHCP server on that LAN, almost certainly a consumer router or access point that someone connected by its LAN side. DHCP has no authentication; the client takes the first acceptable offer. When the rogue device answers first, the client gets an address in the rogue's range with the rogue as its gateway and DNS server, and that gateway has no path to the real network, so nothing works. When the legitimate server wins the race the client is fine, which is why it's intermittent and changes at renewal. To confirm, I'd look at an affected machine's lease to see the server identifier and gateway, find that gateway's MAC address in the ARP table, and trace the MAC to a switch port through the switch's address table. The immediate fix is to unplug the device. The lasting fix is DHCP snooping on the access switches, so that DHCP server messages are accepted only from the uplink ports, plus port security or 802.1X to control what can be connected.

    🧠 Key takeaways

    • DHCP gives a new device its address, mask, gateway and DNS servers in four UDP messages: discover, offer, request, acknowledge.
    • The client broadcasts from 0.0.0.0 because it has no address and doesn't know where the server is.
    • Addresses are leased. Clients renew at half the lease time, and a departed device's address returns only when its lease expires.
    • No answer leads to a self-assigned 169.254 address: the link is up and DHCP failed.
    • Relay agents on routers forward the broadcasts to a central server and tell it which subnet they came from.
    • DHCP is unauthenticated. Whoever answers first sets the gateway, DNS and routes, so switches should allow server replies only from trusted ports.

    Check your understanding

    Why is a DHCP DISCOVER sent from 0.0.0.0 to 255.255.255.255?

    A broadcast is the one thing an unconfigured host can send. Routers don't forward it, which is why relays exist.

    A laptop on office Wi-Fi shows the address 169.254.37.4. What does that tell you?

    169.254.0.0/16 is self-assigned. The radio link is fine; look at the DHCP server, its pool, or the relay.

    A device holds a 24-hour lease and stays connected. When does it first try to renew?

    Half the lease time, with a unicast REQUEST. If that fails it broadcasts at seven-eighths.

    What is a DHCP relay agent for?

    Broadcasts stop at routers, so the router itself passes them on, and the server uses the marked subnet to choose a pool.

    Why can any device on a LAN act as a rogue DHCP server?

    The defence is in the switches: DHCP snooping drops server messages arriving on untrusted ports.
