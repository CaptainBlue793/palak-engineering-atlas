Bytes, Encoding & Byte Order

A network never carries text, numbers or JSON. It carries bytes. Every protocol in this course is a set of rules for which bytes go where, and most beginner bugs come from the two conversions at the edges: text to bytes (encoding) and multi-byte numbers to bytes (byte order). This chapter makes both explicit, so you can read a hex dump of real traffic and know exactly what you are looking at.

Bits, bytes, octets and hex

A bit is a 0 or a 1. A byte is 8 bits, so it holds a value from 0 to 255. Networking standards say octet instead of byte, because when the early RFCs were written some machines had 6-, 7- or 9-bit bytes; "octet" means exactly 8 bits. Today the two words mean the same thing.

Writing bytes in binary is too long and in decimal hides their structure, so everyone uses hexadecimal: base 16, digits 0–9 then a–f. One hex digit is exactly 4 bits (a nibble), so one byte is always exactly two hex digits: 0x00 to 0xff. The byte 0xc3 is 1100 0011 in binary and 195 in decimal.

One unit trap appears in every chapter that follows. Data rates are quoted in bits per second; sizes are quoted in bytes. A "100 Mbit/s" link moves at most 100 ÷ 8 = 12.5 megabytes per second, before any protocol overhead. A 1 GB file on that link takes at least 80 seconds, not 10.

# Python: the same byte in four notations
>>> 0xc3, bin(0xc3), hex(195)
(195, '0b11000011', '0xc3')
>>> bytes([72, 105])          # a bytes object is a sequence of numbers 0–255
b'Hi'
>>> b'Hi'.hex(" ")
'48 69'

Text has to be encoded

A Python str is a sequence of Unicode code points: abstract numbers like U+0041 for "A" and U+1F44B for 👋. A socket can't send code points; it sends bytes. An encoding is the rule that turns one into the other. The original rule, ASCII, covers 128 characters (English letters, digits, punctuation and control codes like \r and \n) in one byte each. Everything outside it needs a bigger encoding.

UTF-8 is the encoding the web, JSON and nearly every modern protocol use. It is variable-length: ASCII characters stay one byte, identical to ASCII, so old ASCII protocols keep working. Accented Latin letters take two bytes, most other scripts and symbols like € take three, and emoji take four. The first byte's high bits say how long the sequence is (110xxxxx starts 2 bytes, 1110xxxx 3, 11110xxx 4), and continuation bytes always start 10, so a decoder can always tell where characters begin.

>>> s = "héllo 👋"
>>> len(s)                      # code points
7
>>> b = s.encode("utf-8")
>>> b
b'h\xc3\xa9llo \xf0\x9f\x91\x8b'
>>> len(b)                      # bytes: é is 2, 👋 is 4
11
>>> b.decode("latin-1")          # the wrong decoder: no error, just garbage
'hÃ©llo ð\x9f\x91\x8b'

The last line is the classic bug called mojibake. Latin-1 maps every byte to some character, so decoding UTF-8 bytes as Latin-1 never fails. It silently turns "é" (bytes c3 a9) into "Ã©". If you have ever seen "JosÃ©" on a receipt, a system somewhere decoded UTF-8 with the wrong encoding. The fix is always the same: agree the encoding in the protocol (HTTP's Content-Type: application/json; charset=utf-8), encode once when sending and decode once when receiving.

Reading a hex dump

A hex dump shows raw bytes as hex, with an offset on the left and the printable characters on the right. It's how xxd, hexdump -C, tcpdump -X and Wireshark's bottom pane show data. Here is a complete HTTP/1.1 request, exactly as it would leave your machine:

$ printf 'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n' | xxd
00000000: 4745 5420 2f20 4854 5450 2f31 2e31 0d0a  GET / HTTP/1.1..
00000010: 486f 7374 3a20 6578 616d 706c 652e 636f  Host: example.co
00000020: 6d0d 0a0d 0a                             m....

Read it in pairs of hex digits. 47 45 54 is "GET", 20 is a space, 0d 0a is carriage return + line feed (\r\n), which HTTP/1.1 uses to end every line. Non-printable bytes show as dots on the right. The request ends with 0d 0a 0d 0a, an empty line, which tells the server the headers are over. The offsets are hex too: the last line starts at byte 0x20 = 32, and the request is 37 bytes long. You will read dumps like this in P6 and debug real ones in Chapter 37.

Byte order: which end goes first

Text is a sequence of single bytes, so there is no question about order. Numbers bigger than 255 need several bytes, and then someone has to decide which byte comes first. Port 8080 is 0x1F90: the two bytes 1f and 90.

  • Big-endian puts the most significant byte first: 1f 90. That is the order you write numbers in, and it is what every internet protocol header uses. RFC 1700 named it network byte order.
  • Little-endian puts the least significant byte first: 90 1f. That's how x86 and almost all ARM processors store integers in memory.

So on your laptop, the port number in memory and the port number on the wire are in opposite orders, and something has to swap them. The C socket API has four functions for it: htons (host to network, short = 16 bits), htonl (long = 32 bits), and their reverses ntohs and ntohl. On a big-endian machine they do nothing; on a little-endian one they swap bytes. In Python you rarely call them directly: struct does the conversion when you give it a format starting with !.

>>> import struct, socket
>>> struct.pack("!H", 8080)          # ! = network order, H = unsigned 16-bit
b'\x1f\x90'
>>> struct.pack("<H", 8080)          # < = little-endian, how an x86 CPU stores it
b'\x90\x1f'
>>> struct.unpack("<H", b"\x1f\x90")[0]   # the bug: wire bytes read in host order
36895
>>> socket.htons(8080)                # on a little-endian machine: the swapped value
36895
>>> struct.pack("!HH", 51514, 443).hex(" ")   # first 4 bytes of a TCP header
'c9 3a 01 bb'

That last line is real: the first four bytes of every TCP segment are the source port and the destination port, each 16 bits, big-endian. If you see 01 bb at offset 2 of a TCP header, the connection is to port 443. The struct format characters you will use most are B (8-bit), H (16-bit), I (32-bit) and Q (64-bit), all unsigned.

Content-Length counts bytes, not characters
A Python client builds an HTTP/1.1 request by hand and sets Content-Length: len(body) where body is a str. It works in every test, because the test data is ASCII. Then a customer called "Zoë" signs up. The JSON is 41 characters but 42 bytes, the header says 41, the server reads 41 bytes and parses JSON that's missing its closing brace, and the 42nd byte sits in the socket and is taken as the start of the next request on that connection. The fix is one line: encode first, then measure: data = body.encode("utf-8"); headers["Content-Length"] = str(len(data)). Every length field in every protocol in this course, from the IP total length to HTTP/2 frame lengths, counts bytes.

  


  
⚠️
Common mistakes

    
    
      
  • Measuring a str when the protocol counts bytes. len("Zoë") is 3, its UTF-8 encoding is 4 bytes.
    • 
      
  • Relying on the default encoding. open() and some libraries use the platform default (often cp1252 on Windows). Pass encoding="utf-8" explicitly.
    • 
      
  • Decoding a partial read. A recv() can end in the middle of a multi-byte character; decoding that chunk raises UnicodeDecodeError. Collect the whole message first (or use an incremental decoder).
    • 
      
  • Forgetting ! in a struct format. Without it you get the machine's native order and alignment padding, which differ between hosts.
    • 
      
  • Mixing bits and bytes. A 1 Gbit/s link is 125 MB/s at best; quoting it as 1 GB/s is off by 8×.
    •

Interview drill

    
Explain it simply: What is network byte order, and why do htons and ntohs exist?

    
How a strong answer sounds
Multi-byte numbers can be stored most-significant byte first (big-endian) or least-significant first (little-endian). Internet protocol headers all use big-endian, called network byte order, so every machine agrees what the bytes 1f 90 in a port field mean: 8080. x86 and ARM machines store integers little-endian, so before writing a port or address into a header they swap bytes with htons/htonl, and after reading one they swap back with ntohs/ntohl. On a big-endian machine those calls do nothing, which is why code that forgets them can work on one machine and break on another. In Python, struct.pack("!H", port) does the same job.

    
Deeper: Why can't you decode each recv() result separately as UTF-8?

    
How a strong answer sounds
TCP is a byte stream; recv() returns whatever bytes have arrived, with no respect for character or message boundaries. A 4-byte emoji can be split, two bytes at the end of one read and two at the start of the next. Decoding the first chunk alone fails with an "unexpected end of data" error, or, with errors="replace", silently corrupts the text. The correct approach is to frame messages (a length prefix or a delimiter), collect a whole message as bytes, and decode once; or use codecs.getincrementaldecoder("utf-8"), which buffers incomplete sequences between calls.
