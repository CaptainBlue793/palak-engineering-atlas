OSI vs TCP/IP

Engineers say "that's a layer 2 problem", "we need an L7 load balancer" or "the firewall works at layer 4" every day, using the numbers of a seven-layer model whose own protocols almost nobody runs. The internet actually runs on the four-layer TCP/IP stack. This chapter gives you both models, the mapping between them, and the questions interviewers build on them, so the vocabulary is precise when you use it.

  • Name the seven OSI layers in order and say what each is responsible for
  • Describe the four TCP/IP layers and map OSI onto them
  • Place real protocols, addresses and devices at the right layer, including the awkward ones
  • Use layer numbers precisely: L2 vs L3 networks, L4 vs L7 load balancers and firewalls

Two models, one history

In the late 1970s and 1980s two efforts competed to define how computers should network. The International Organization for Standardization (ISO) designed the Open Systems Interconnection (OSI) model and a full suite of protocols to go with it, published as ISO 7498 in 1984. Meanwhile, the US research community had working code: TCP and IP, specified in 1981 and switched on across ARPANET on 1 January 1983. TCP/IP was free, already deployed and shipped with BSD Unix, and it won the "protocol wars" by the early 1990s.

The OSI protocols disappeared, apart from a few survivors such as IS-IS, still used for routing inside large provider networks, and X.509, the certificate format behind TLS. The OSI model, though, survived as a shared vocabulary because its layers are finer-grained and numbered. That's why we say "layer 7" and never "the TCP/IP application layer".

The seven OSI layers

From the bottom, which is how the numbers run:

Layers 1–4 match real protocols cleanly. Layers 5 and 6 are the awkward ones: in practice, session management (cookies, login sessions, HTTP/2 streams) and presentation (UTF-8, JSON, compression, encryption) are done inside applications and libraries, not by separate protocols. When people need a home for TLS they usually say "between 4 and 7", or call it layer 6 because it transforms data, and both are defensible. If an interviewer asks, say so and explain why: that's a better answer than a confident single number.

The TCP/IP stack and the mapping

The internet's own model, written down in RFC 1122 (1989), has four layers. Many textbooks split the bottom one into physical and data link and call it a five-layer model; it's the same thing.

The useful habit is reading a device's layer as "the highest header it looks at". A switch reads up to the Ethernet header (L2). A router reads up to IP (L3). An L4 load balancer reads ports and picks a backend per connection without decrypting anything. An L7 load balancer terminates TLS and reads the HTTP request, so it can route /api and /images to different backends (Chapter 24).

What interviews actually ask

Nobody is hired for reciting seven names. The layer questions that come up are about using the model:

  • "What's the difference between a switch and a router?" L2 forwarding on MAC addresses within one network vs L3 forwarding on IP addresses between networks (Chapter 2, Chapter 5).
  • "L4 or L7 load balancer?" Per-connection, fast and protocol-agnostic, vs per-request with routing on paths and headers, at the cost of terminating TLS.
  • "At which layer does this attack work?" A SYN flood is L4, an HTTP flood is L7, a volumetric UDP flood fills L3 links (Chapter 36).
  • "What happens when you type a URL?" The classic, which is really "walk down and up the stack". Chapter 40 has the interview version and Case Study 41 the full trace.

Triage by layer: the latency spike that was a dirty optic

A payments service's p99 latency jumps from 40 ms to 900 ms for requests served by one rack, and the application team spends a morning on garbage-collection logs. The incident only moves once someone works up the stack instead. L7: error rates are normal, requests just take longer. L4: ss -ti on the slow hosts shows climbing retransmission counters (retrans:0/1843). Retransmissions mean loss, so drop to L1: ethtool -S eth0 | grep -i crc shows thousands of CRC errors, frames corrupted on the wire. A contaminated fibre transceiver in the top-of-rack switch was flipping bits; the switch dropped the bad frames, TCP resent them after timeouts of 200 ms or more, and the application saw slow responses. Cleaning the optic fixed it. Saying "it looks like a layer 1 problem showing up as layer 4 retransmits" is the kind of sentence that gets the right team involved in minutes.

⚠️
Common mistakes
  • Treating the OSI model as how the internet works. It's a vocabulary. The internet runs TCP/IP's four layers; OSI's 5 and 6 live inside applications.
  • Giving one confident number for TLS, ARP or BGP. TLS sits between 4 and 7; ARP serves L3 but is carried in L2 frames; BGP runs over TCP (L7) to control L3 routing. Explain the nuance.
  • Calling a load balancer L7 because it handles HTTP traffic. If it never parses HTTP (it just forwards TCP connections), it's L4.
  • Numbering from the top. Layer 1 is physical. "Layer 7" is the application.
  • Forgetting that a device can work at several layers. A home "router" is a switch (L2), router (L3), NAT (L4), DHCP and DNS server (L7) in one box.

Interview drill

Explain it simply: Name the OSI layers and map them to the TCP/IP model.

How a strong answer sounds
From the bottom: physical (signals on a medium), data link (frames between neighbours, MAC addresses, Ethernet), network (packets between networks, IP, routers), transport (process to process, ports, TCP and UDP), session, presentation and application. TCP/IP has four layers: link covers OSI 1 and 2, internet is OSI 3, transport is OSI 4, and application folds 5, 6 and 7 together, because in practice sessions and encoding are handled inside applications and libraries. OSI is the vocabulary we use ("an L4 load balancer"); TCP/IP is what actually runs.

Deeper: At which layer does TLS operate? And QUIC?

How a strong answer sounds
TLS doesn't fit one OSI layer cleanly. It runs on top of a reliable transport (TCP, so above L4), provides encryption and integrity, which is presentation-like (L6), and manages its own session state and resumption (L5-like), while applications see it as part of their stack. I'd say it sits between transport and application, often called L6. QUIC is a transport protocol, L4 in function, with reliability, streams and congestion control, but it's carried inside UDP datagrams and implemented in user space with TLS 1.3 built in. So in packet terms it's an application of UDP, and in function it's a transport. Explaining that tension is the point of the question.

🧠 Key takeaways

  • OSI's seven layers are the vocabulary; TCP/IP's four layers are what the internet runs.
  • Link = OSI 1–2, internet = 3, transport = 4, application = 5–7.
  • A device's layer is the highest header it reads: switch L2, router L3, L4 balancer ports, L7 balancer HTTP.
  • TLS, ARP, BGP and QUIC don't fit one layer neatly; explain why rather than guess a number.
  • Triage by layer: errors at a lower layer often show up as symptoms higher up.

Check your understanding

At which OSI layer does a router make its forwarding decision?

Routers forward on the destination IP address, the network layer. They rebuild the L2 frame at each hop but never need to read L4.

Which OSI layers does the TCP/IP model's application layer cover?

Session, presentation and application are folded together, because in TCP/IP those jobs are done by applications and libraries rather than separate protocols.

What can an L7 load balancer do that an L4 load balancer cannot?

Only a balancer that terminates the connection and parses HTTP can see /api/orders or the Host header. An L4 balancer sees addresses and ports only.

A switch forwards a frame based on which field?

A (layer 2) switch looks up the destination MAC in its MAC table to choose the output port (Chapter 2).

Why did the OSI model survive when the OSI protocols didn't?

TCP/IP won in deployment, but "layer 2", "L4" and "L7" are OSI numbers, used daily to describe devices, problems and attacks.
