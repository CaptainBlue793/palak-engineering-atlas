Forward & Reverse Proxies

Draw the path of a request to almost any web service and the browser doesn't touch the application. It talks to a CDN, which talks to a load balancer, which talks to an nginx or an Envoy, which finally talks to the program that does the work. Each of those is a proxy: a server that accepts a connection, and then makes a separate connection of its own on the client's behalf. Proxies are where TLS is decrypted, where traffic is routed and cached, and where slow clients are kept away from busy servers. They are also why your application sees every user arriving from the same IP address, and why the errors numbered 502 and 504 exist. This chapter is about what happens at that hop.

Forward and reverse

Both kinds sit in the middle and relay. The difference is whose side they are on.

Forward proxyReverse proxy
Acts forClientsServers
Who knows it is thereThe client, which is configured to use it. The server sees the proxy as the clientThe server's operators. The client believes the proxy is the server
PlacedAt the edge of the clients' networkIn front of the servers
Used forControlling and logging what staff or servers may reach, caching, hiding client addressesTLS, routing, load balancing, caching, rate limiting, protecting the application
ExamplesA company's web proxy (Squid); the egress gateway of a clusternginx, HAProxy, Envoy, cloud load balancers, CDNs, API gateways

The rest of this chapter is about reverse proxies, since every service you build will sit behind one. One fact about them explains nearly everything that follows: a proxy does not forward packets. It ends the client's TCP connection and starts another to the server behind it.

Since the proxy reads each request in full before passing it on, it can do useful work at that point. It can pick a server by host name or path, answer from a cache, reject a client that sends too fast, and absorb a slow client's trickle of bytes so that an application process is occupied only for the milliseconds the real work takes.

TLS termination

A proxy can only read, route and cache what it can decrypt. Where the TLS session ends is therefore the main design choice:

TerminateTerminate and re-encryptPass through
The proxyDecrypts, and talks plain HTTP to the back endDecrypts, then opens its own TLS connection to the back endRelays the encrypted bytes untouched
Certificate and key are onThe proxyThe proxy, and the back ends have their ownThe back ends only

Traffic inside your networkReadable by anything on the pathEncryptedEncrypted end to end

Terminating at the proxy has a side effect that surprises every application at least once. The application receives plain HTTP, concludes that the user came over HTTP, and redirects them to HTTPS, which arrives at the application as plain HTTP again. The proxy tells it the truth in a header, X-Forwarded-Proto: https, and the application has to be configured to believe it.

🧠
Cloudbleed: the place where everyone's plaintext meets

In February 2017 Tavis Ormandy, a researcher at Google, noticed something odd in search results: pages from unrelated web sites that contained fragments of other people's traffic. There were private messages from a dating site, frames from a chat service, hotel bookings, cookies and passwords, embedded in the HTML of sites that had nothing to do with them. What the sites had in common was Cloudflare, the reverse proxy in front of all of them. Cloudflare terminates TLS for millions of sites on shared machines, and it rewrites pages as they pass, for example to obfuscate email addresses. A bug in one of those rewriting modules read past the end of a buffer when it met a certain kind of malformed HTML. Whatever happened to lie next in the process's memory was appended to the response, and what lay there was whatever the same process had just been handling, decrypted requests and responses of other customers. It happened to about one request in 3.3 million. Some of the pages had been stored by search engines, which is how the leak was seen at all. Cloudflare switched the features off within hours, and the cleanup of search-engine caches took days. The bug was an ordinary memory error of the kind Chapter 17's protocols can do nothing about, because TLS protects data on the wire. A terminating proxy is the one point where the data of every user of every site behind it exists unencrypted in one program, and that concentration is part of the cost of everything a proxy does for you.

X-Forwarded-For and the PROXY protocol

Behind a proxy, the source address of every connection is the proxy's. The application has lost the one thing it knew about the client, which it wants for logs, rate limits, fraud checks and locating the user. Proxies put it back in a header. Each proxy that handles a request appends the address it received the request from:

X-Forwarded-For: 203.0.113.7, 198.51.100.20
#                └ the client, as seen by the first proxy      └ the first proxy, as seen by the second

The danger is in how that list is read. The header is just text in the request, and a client can send one too. A proxy that appends will add the real address after whatever the client supplied. So the leftmost entry, the one everyone reaches for, is whatever the client claims to be. The only entries that can be believed are the ones added by proxies you run. The correct procedure is to start from the right, skip the addresses of your own proxies, and take the first one that isn't yours.

Things to notice. Using the connection's source address gives the internal proxy's address for every user, so one rate limit is shared by the whole world. Reading the first address in the header works for honest clients and fails for a dishonest one. The client that sends its own header appears as 1.2.3.4, and it can appear as a different address on every request, which defeats the rate limit entirely and lets it impersonate anyone whose address is specially trusted. Either of two changes fixes it: the edge proxy overwrites the header, or the application reads from the right and skips its own proxies. The last setting shows why the edge matters. If the first proxy you control doesn't record what it saw, no amount of care further in can recover the truth.

A header only helps when the proxy speaks HTTP. A proxy that passes TLS through, or carries some other protocol such as a database connection, can't add one. For that there is the PROXY protocol: before any of the client's bytes, the proxy sends one extra line on the connection to the back end, giving the original addresses and ports.

PROXY TCP4 203.0.113.7 198.51.100.20 51000 443\r\n          # added by the proxy, then the client's own bytes follow unchanged
\x16\x03\x01\x02\x00\x01\x00\x01\xfc\x03\x03…                    # here, the client's TLS hello

Both ends must agree to it. A back end that isn't expecting the line will try to parse it as TLS or HTTP and fail, and a back end that expects it from anyone will believe any client that types one. Like the header, it must be accepted only from addresses you know to be your proxies.

Connection pooling to back ends

On the back-end side, a good proxy doesn't open a connection for each request. It keeps a pool of idle keep-alive connections to each server and sends each request down whichever is free. Ten thousand client connections, most of them idle, are served by a few dozen busy connections to the application.

# nginx as a reverse proxy: the lines that matter
upstream app {
    server 10.0.2.9:8080;
    server 10.0.2.10:8080;
    keepalive 64;                                  # keep up to 64 idle connections to the back ends open
}
server {
    listen 443 ssl;
    server_name shop.example;
    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;                    # the default is 1.0, which closes after every request
        proxy_set_header Connection "";            # and this stops "Connection: close" being passed on
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;     # overwrite: this is the edge
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;                    # how long to wait for the back end before answering 504
    }
}

Pooling brings back the idle-timeout race from Chapter 15, now between your own machines. If the application closes idle connections after 5 seconds and the proxy keeps them for 60, the proxy will sometimes send a request down a connection the application has just closed. It meets a reset, and the user sees a 502. The two status codes a proxy makes for itself each have a typical cause:

502 Bad Gateway504 Gateway Timeout
The proxyConnected, or tried to, and got a refusal, a reset or an invalid responseConnected, sent the request, and gave up waiting for the response
Usual causesThe application has crashed or is restarting; its idle timeout is shorter than the proxy's; it closed the connection mid-responseThe application is slow or stuck; the proxy's read timeout is shorter than the slowest legitimate request
Look atThe application's process and its keep-alive settingThe application's latency and whatever it is waiting on
The application's own log showsOften nothing: the request never arrivedThe request, usually finishing after the proxy has given up
⚠️
Common mistakes
  • Trusting the first entry of X-Forwarded-For. The client controls it. Overwrite the header at your edge, or read from the right past your own proxies.
  • Logging or rate-limiting by the connection's source address behind a proxy. Every user looks like the proxy.
  • Ignoring X-Forwarded-Proto. The application thinks every request is plain HTTP: redirect loops and insecure cookies.
  • No keep-alive to the back ends. Every request pays for a new connection, and ports are exhausted under load (Chapter 14).
  • A back-end idle timeout shorter than the proxy's. Intermittent 502s that appear in no application log.
  • Timeouts that get longer towards the back. Each hop should wait a little less than the one in front of it, or the front gives up while the back still works.

Interview drill

Explain it simply: What is a reverse proxy, and why put one in front of an application?

How a strong answer sounds
A reverse proxy is a server that clients connect to as if it were the application. It terminates their connections and makes its own requests to the real servers behind it. A forward proxy is the mirror image, acting on behalf of clients going out. Reverse proxies are used to terminate TLS in one place, so that certificates and cipher configuration are managed centrally; to route requests by host name or path to different services; to balance load across servers and stop sending to unhealthy ones; to cache responses and compress them; to enforce rate limits and authentication; and to shield the application from slow or abusive clients by buffering requests and responses, so that application workers are tied up only briefly. The cost is an extra hop with its own timeouts and failure modes, visible as 502s and 504s, and the loss of the client's IP address at the TCP level, which has to be passed on in a header such as X-Forwarded-For.

Deeper: Your API rate-limits by client IP using X-Forwarded-For, and an attacker is bypassing the limit. How, and how do you fix it?

How a strong answer sounds
X-Forwarded-For is an ordinary request header, so a client can set it. Proxies conventionally append the address they received the request from, which means the list is whatever the client sent followed by entries that real proxies added. If the application takes the leftmost entry, it is taking the attacker's own text, and the attacker can put a different fake address on every request so that each falls under a fresh rate limit. Worse, they can claim an address that is allow-listed. The fix is to believe only what your own infrastructure wrote. Either have the first proxy you control, the edge, overwrite the header with the address it actually saw, discarding anything the client supplied; or have the application walk the list from the right, skipping addresses that belong to your known proxies, and use the first one that doesn't. Most frameworks have a "trusted proxies" setting that does exactly that. And make sure the application can't be reached directly, bypassing the proxies, or anyone can forge the whole header. For non-HTTP traffic the same reasoning applies to the PROXY protocol: accept it only from trusted sources.

🧠 Key takeaways

  • A forward proxy acts for clients and is known to them. A reverse proxy acts for servers, and clients take it for the server.
  • A proxy ends one TCP connection and starts another, so the back end sees the proxy's address, and each side has its own timeouts.
  • TLS can be terminated at the proxy, re-encrypted to the back end, or passed through. Only a terminating proxy can read and route HTTP.
  • The client's address travels in X-Forwarded-For. Only entries added by your own proxies are trustworthy, so read from the right.
  • For protocols that aren't HTTP, the PROXY protocol carries the original addresses in a line before the data.
  • Proxies pool keep-alive connections to back ends. A reset or refusal there becomes a 502, and waiting too long a 504.

Check your understanding

What is the essential difference between a forward and a reverse proxy?

The mechanics are similar. What differs is whose agent it is, and who knows it is there.

An application behind a reverse proxy logs the source IP address of each TCP connection. What does it record?

The proxy opened that connection. The user's address is available only if the proxy passes it on.

A request arrives with X-Forwarded-For: 9.9.9.9, 203.0.113.7, 198.51.100.20, and 198.51.100.20 is your edge proxy. Which address should you treat as the client?

Your edge appended 203.0.113.7, so that entry is real. Anything to its left came from the client and may be invented.

A load balancer passes TLS through to the back ends without decrypting it. How can the back ends learn the client's address?

The balancer can't insert an HTTP header into a stream it can't decrypt, but it can prefix the connection.

Users see occasional 502 errors. The application's logs show no failed requests at those times. What is a likely cause?

The request never reached the application, so only the proxy logged it. Make the back end keep idle connections longer than the proxy does.
