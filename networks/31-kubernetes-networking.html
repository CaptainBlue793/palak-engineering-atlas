Kubernetes Networking & CNI

Kubernetes has a reputation for complicated networking. Its rules are in fact short: every pod has its own IP address, any pod can reach any other pod at that address, and nothing in between translates it. Everything else is machinery for keeping those rules true across hundreds of machines, and for coping with the fact that pods are created and destroyed all day long, so that no address stays valid for very long. That machinery contains nothing new. It is network namespaces and virtual cables, routing tables, overlays, NAT rules, DNS and reverse proxies, each of which has had its own chapter in this course. This chapter shows how they are put together, by following one request from a pod to a Service to another pod.

Every pod gets an IP

The Kubernetes network model is three requirements, and any implementation that meets them is acceptable:

  • Every pod has its own IP address.
  • Every pod can reach every other pod at that address, on any node, without NAT.
  • The address a pod sees as its own is the address others see it as.

A pod is a network namespace: a private copy of the network stack, with its own interfaces, routes and ports. All the containers in a pod share it, which is why they can talk to each other on localhost. The namespace is joined to the node by a veth pair, a virtual cable with one end inside the pod, named eth0, and the other end on the node. Each node is given a slice of the cluster's pod address range, and hands out addresses from it.

$ kubectl get pods -o wide
NAME        READY  STATUS   IP            NODE
web-7d9f    1/1    Running  10.244.1.5    node-1          # node-1 owns 10.244.1.0/24
orders-a1   1/1    Running  10.244.1.9    node-1
orders-b2   1/1    Running  10.244.2.7    node-2          # node-2 owns 10.244.2.0/24
orders-c3   1/1    Running  10.244.2.8    node-2

$ kubectl exec web-7d9f -- ip addr show eth0
3: eth0@if12: <BROADCAST,MULTICAST,UP> mtu 1450                # 1450: there is an overlay underneath
    inet 10.244.1.5/24 scope global eth0

$ ip route                                                    # on node-1
10.244.1.0/24 dev cni0  proto kernel                           # my own pods: deliver locally
10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink              # node-2's pods: into the VXLAN tunnel

CNI plugins

Kubernetes doesn't implement any of that itself. When a pod is created, the node's agent calls a CNI plugin (Container Network Interface), a program whose job is to create the veth pair, choose an address, and set up whatever is needed for the address to be reachable from other nodes. The plugins differ mainly in that last step, and there are two families.

Services and kube-proxy

Pod addresses work, and they don't last. A deployment replaces its pods on every release, and each new pod gets a new address. No client can be given a list of pod addresses and expect it to stay true. So Kubernetes adds a stable front: a Service has a name and one virtual address, the ClusterIP, which never changes for the life of the Service. Kubernetes keeps a current list of the ready pods behind it.

$ kubectl get service orders
NAME     TYPE        CLUSTER-IP     PORT(S)
orders   ClusterIP   10.96.12.34    80/TCP

$ kubectl get endpointslices -l kubernetes.io/service-name=orders
NAME           ADDRESSTYPE   PORTS   ENDPOINTS
orders-x8k2p   IPv4          8080    10.244.1.9,10.244.2.7,10.244.2.8

$ kubectl exec web-7d9f -- nslookup orders
Name:    orders.default.svc.cluster.local              # the cluster's DNS turns the name into the ClusterIP
Address: 10.96.12.34

The odd thing about a ClusterIP is that no machine has it. It is assigned to no interface anywhere. It exists as a rule, installed on every node by a component called kube-proxy, which says: a packet addressed to 10.96.12.34 port 80 is to have its destination rewritten to one of the three pod addresses, chosen at random. That is destination NAT (Chapter 9), performed on the node where the packet starts.

$ sudo iptables -t nat -S | grep -E 'ORDERS|SEP'          # kube-proxy's rules for this Service, simplified
-A KUBE-SERVICES -d 10.96.12.34/32 -p tcp --dport 80 -j KUBE-SVC-ORDERS
-A KUBE-SVC-ORDERS -m statistic --mode random --probability 0.33333 -j KUBE-SEP-A    # one time in three
-A KUBE-SVC-ORDERS -m statistic --mode random --probability 0.50000 -j KUBE-SEP-B    # half of the rest
-A KUBE-SVC-ORDERS -j KUBE-SEP-C                                                     # otherwise
-A KUBE-SEP-A -p tcp -j DNAT --to-destination 10.244.1.9:8080
-A KUBE-SEP-B -p tcp -j DNAT --to-destination 10.244.2.7:8080
-A KUBE-SEP-C -p tcp -j DNAT --to-destination 10.244.2.8:8080

The choice is made for the first packet of a connection and remembered by the kernel's connection tracking, which also rewrites the replies so that the client sees them coming from the ClusterIP. So a Service is a layer-4, per-connection load balancer (Chapter 24) that runs on every node. Two consequences follow. You can't ping a ClusterIP, since the rule matches only the Service's port. And a client that keeps one long connection, as gRPC does, sends everything to a single pod (Chapter 22).

    Things to notice. The packet leaves the pod addressed to the Service's virtual address, and by the time it leaves the node it is addressed to a real pod. The translation happened on the calling pod's own node, and only the destination changed, so the receiving pod sees the caller's real pod address. Open several connections and the chosen pod changes. When the chosen pod is on the same node, the packet never touches the physical network. With the overlay, a packet for the other node is wrapped in a VXLAN packet between the nodes' addresses, and with native routing it goes as it is. Now add the policy and call from the report pod. The whole path is the same up to the last step, where the receiving node drops the packet. The caller gets no refusal, only a connection that times out.

    Ingress

    Services of type LoadBalancer give each service its own external address, which is costly and knows nothing about HTTP. For web traffic the usual entry point is an Ingress: a reverse proxy running in the cluster (Chapter 23), configured by Kubernetes objects.

    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop }
spec:
  tls: [{ hosts: [shop.example], secretName: shop-tls }]      # TLS ends at the ingress proxy
  rules:
  - host: shop.example
    http:
      paths:
      - { path: /api/orders, pathType: Prefix, backend: { service: { name: orders, port: { number: 80 } } } }
      - { path: /,           pathType: Prefix, backend: { service: { name: web,    port: { number: 80 } } } }

    Network policies

    By default the pod network is flat: any pod can open a connection to any other pod in the cluster, in any namespace. A NetworkPolicy restricts that. It selects a set of pods by label and lists who may connect to them, or where they may connect to.

    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: orders-from-web-only }
spec:
  podSelector: { matchLabels: { app: orders } }      # the pods this policy protects
  policyTypes: [Ingress]
  ingress:
  - from: [{ podSelector: { matchLabels: { app: web } } }]
    ports: [{ protocol: TCP, port: 8080 }]             # everything not listed is now refused

    Policies are written in terms of labels and not addresses, because addresses don't last. The network plugin translates them into packet filters on each node and keeps those up to date as pods come and go. Two points catch people out. Once any policy selects a pod, everything not explicitly allowed to that pod is dropped. And Kubernetes itself enforces nothing: if the plugin doesn't implement policies, they are accepted and silently ignored.

    🧠
    Twenty thousand Services and a rule update measured in hours

    The iptables rules shown earlier are simple, and they are a list. To decide whether a packet is for a Service, the kernel walks the list from the top until a rule matches, and to change one rule, the whole table is rewritten. Neither matters for fifty Services. Engineers at Huawei, running clusters with tens of thousands, measured what happens at scale and presented it in 2017. With 5,000 Services, about 40,000 rules, adding a single new rule took around eleven minutes. With 20,000 Services it took about five hours, during which the node's view of the cluster was out of date and new pods received no traffic. Latency for the first packet of each connection grew with the length of the list as well. The filter had been designed for a firewall with a few hundred hand-written rules and was being used as a load balancer's routing table. Their answer was to give kube-proxy a second mode built on IPVS, the layer-4 balancer inside the Linux kernel (Chapter 24), which stores Services in hash tables and looks one up in the same time whether there are ten or a hundred thousand. Newer plugins go a step further and replace both with small programs loaded into the kernel that do the lookup directly. A design can be correct at one size and unusable at a thousand times that size, and data structures inside the kernel matter to an application that never sees them.

    ⚠️
    Common mistakes
    • Trying to ping a ClusterIP. It isn't a host. Test the Service's port with curl or nc.
    • Expecting a Service to balance requests. It balances connections. Long-lived HTTP/2 and gRPC connections need a layer-7 proxy or a headless Service.
    • Writing network policies on a plugin that doesn't enforce them. They do nothing, and nothing warns you.
    • Forgetting the overlay's MTU. Pods at 1,450 and something else at 1,500 gives the black hole of Chapter 28.
    • Using a pod's address in configuration. It changes at the next restart. Use the Service name.
    • Assuming a readiness probe is cosmetic. It decides whether a pod is in the Service's list. A pod that isn't ready receives nothing, and one that is wrongly ready receives traffic it can't serve.
    🎤
    Interview drill

    Explain it simply: How does a request from one pod reach a pod behind a Kubernetes Service?

    How a strong answer sounds
    The client pod resolves the Service name through the cluster DNS and gets the Service's ClusterIP, a stable virtual address. It sends a packet to that address and port. The packet leaves the pod's network namespace over its veth pair onto the node. There, rules programmed by kube-proxy, in iptables or IPVS or eBPF, match the ClusterIP and port and apply destination NAT, rewriting the destination to the address and port of one of the Service's ready pods, taken from the EndpointSlices. Connection tracking records the mapping. The node then routes the packet to that pod: locally over a bridge if the pod is on the same node, or to the other node otherwise, either encapsulated in an overlay such as VXLAN or routed natively if the underlying network knows the pod ranges. The destination node delivers it into the target pod's namespace, subject to any network policy. The reply returns to the client's node, where connection tracking reverses the NAT so that the client sees it coming from the ClusterIP. The source address is never changed, so the server sees the client pod's real IP.

    Deeper: A pod can't connect to a Service: the connection times out. How do you narrow it down?

    How a strong answer sounds
    I'd work along the path. First DNS: does the name resolve to the ClusterIP from inside the pod? If not, it's the cluster DNS or the pod's resolver configuration. Second, the Service's endpoints: kubectl get endpointslices for it. An empty list means the selector matches no pods or none are ready, so the NAT rule has nowhere to send traffic; that's the most common cause. Third, bypass the Service and connect straight to a backend pod's IP and target port. If that works, the problem is in the Service layer: a wrong port or targetPort, or kube-proxy not running or out of sync on the client's node. If it also fails, it's pod-to-pod connectivity. Then I'd test a pod on the same node against one on another node. Same-node working and cross-node failing points to the CNI: overlay tunnels blocked by a firewall or security group between nodes, missing routes, or an MTU mismatch if only large responses fail. A timeout as opposed to a refusal also suggests a network policy dropping the traffic, so I'd list the policies selecting the destination pods and check the labels on the source. Finally I'd confirm the application is listening on the pod's address and not only on localhost.

    🧠 Key takeaways

    • Every pod is a network namespace with its own IP, and pods reach each other directly, with no NAT between them.
    • A CNI plugin wires each pod up and makes pod addresses reachable across nodes, by an overlay or by native routing.
    • A Service is a stable name and virtual address. Rules on every node rewrite that address to a ready pod's, per connection.
    • The ClusterIP belongs to no machine. It can't be pinged, and it balances connections, not requests.
    • An Ingress is a layer-7 reverse proxy inside the cluster that routes external HTTP by host and path.
    • Network policies restrict traffic by label, and work only if the plugin enforces them.
