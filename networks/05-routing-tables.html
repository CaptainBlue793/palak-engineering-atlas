Routing Tables & Forwarding

No router on the internet knows the whole path to your packet's destination. Each one knows only a next hop: "for addresses starting like this, hand the packet to that neighbour". A packet crosses the world as a chain of independent local decisions, each made by matching the destination address against a table in a few nanoseconds. This chapter shows how that table is read (longest-prefix match), what the default route is for, how a packet's path is assembled hop by hop, and the two classic ways it goes wrong: a missing return route and a routing loop.

What's in a routing table

Every host and every router has a routing table: a list of prefixes, each with where to send matching packets. An entry is either connected (the prefix is on one of my interfaces, so deliver directly to the destination after ARPing for it) or has a next hop (a neighbouring router's address, which must itself be on a connected network). Here is a Linux router's table:

$ ip route
default via 198.51.100.1 dev eth2                       # 0.0.0.0/0: everything else goes to the ISP
10.0.12.0/31 dev eth0 proto kernel scope link src 10.0.12.1    # connected: link to R1
10.0.23.0/31 dev eth1 proto kernel scope link src 10.0.23.0    # connected: link to R3
10.0.29.0/31 dev eth3 proto kernel scope link src 10.0.29.0    # connected: link to the DR site
10.1.1.0/24 via 10.0.12.0 dev eth0 proto ospf metric 20        # learned from OSPF
10.3.0.0/16 via 10.0.23.1 dev eth1 proto static                 # configured by hand
10.3.9.0/24 via 10.0.29.1 dev eth3 proto static                 # a more specific exception

$ ip route get 10.3.9.5                                   # ask the kernel which route wins
10.3.9.5 via 10.0.29.1 dev eth3 src 10.0.29.0 uid 0

The proto column says where each route came from: kernel for connected networks, static for routes an operator (or a cloud's route table) configured, and a routing protocol such as ospf or bgp for routes learned dynamically. metric breaks ties between routes to the same prefix: lower wins.

Longest-prefix match

A destination often matches several entries. 10.3.9.5 matches the default route (every address does), 10.3.0.0/16 and 10.3.9.0/24. The rule is simple and universal: the most specific route wins, the one with the longest prefix. So 10.3.9.5 goes via 10.0.29.1, while 10.3.3.20 only matches the /16 and the default, and goes via 10.0.23.1. The default route, 0.0.0.0/0, has a prefix length of zero: it matches everything and so loses to anything more specific. It's the "I don't know, ask upstream" entry, and hosts usually have nothing else.

import ipaddress

ROUTES = [  # (prefix, next hop)
    ("0.0.0.0/0",   "198.51.100.1"),
    ("10.3.0.0/16", "10.0.23.1"),
    ("10.3.9.0/24", "10.0.29.1"),
]

def lookup(dst: str) -> str:
    d = ipaddress.ip_address(dst)
    matches = [(ipaddress.ip_network(p), hop) for p, hop in ROUTES if d in ipaddress.ip_network(p)]
    net, hop = max(matches, key=lambda m: m[0].prefixlen)   # longest prefix wins
    return hop

>>> lookup("10.3.9.5"), lookup("10.3.3.20"), lookup("8.8.8.8")
('10.0.29.1', '10.0.23.1', '198.51.100.1')

A linear scan is fine for three routes, not for the million in an internet router. Real implementations use tries keyed on the address bits (Linux uses an LC-trie), and hardware routers use TCAM, memory that compares a key against every entry in parallel in one clock cycle, which is how a line card forwards hundreds of millions of packets per second.

Hop by hop, and back again

Each router on the path repeats the same steps: receive the frame, check the IP header, decrement the TTL (drop the packet and send ICMP "time exceeded" if it reaches 0), look up the destination, ARP for the next hop if needed, and send a new frame. No router knows or cares about the rest of the path. That makes routing scale, and it also means the path back is a separate set of decisions: the reply is a new packet, routed from the server's side by the server's routers' tables. Paths are often asymmetric, and a reply can fail even when the request arrived fine.

Static and dynamic routing

Someone or something has to fill the tables. On a small network an operator writes static routes by hand, and every cloud VPC route table is a list of static routes. They're simple and predictable, but they don't react: if a link fails, traffic keeps being sent into it. Larger networks run routing protocols, where routers tell each other which prefixes they can reach, compute paths and update tables within seconds of a failure.

When several routes to the same prefix are equally good, routers can use all of them at once, hashing each flow's 5-tuple to pick a path so one connection's packets stay in order: equal-cost multi-path (ECMP), the basis of data-centre fabrics (Chapter 30).

The summary route that bounced traffic until it died

A data centre's core router announces one summary, 10.3.0.0/16, towards the rest of the company, and points it at the data-centre border router. The border router has routes for the subnets actually in use and a default route pointing back to the core. One day a misconfigured monitoring system starts scanning 10.3.200.0/24, a range nobody has allocated yet. The core sends those packets to the border (the /16 matches); the border has no specific route, so its default sends them back to the core, which sends them back again. Each packet bounces 60-odd times before its TTL runs out, multiplying the scanner's traffic dozens of times on the link between the two routers until it saturates and real traffic starts dropping. The standard fix is a null route (a discard route) for the summary on the border router: ip route add blackhole 10.3.0.0/16. Real subnets still win by longest-prefix match, and anything else in the /16 is dropped at once instead of looping. Any router that announces a summary should own a discard route for it.

⚠️
Common mistakes
  • Thinking the first matching route wins. Order doesn't matter; prefix length does, then metric.
  • Adding a route for the request but not the reply. The far side needs a route back, or the connection times out with the SYN delivered and the SYN-ACK lost.
  • A next hop that isn't on a connected network. The router can't ARP for it, so the route is unusable (Linux refuses it: "Nexthop has invalid gateway").
  • Summary routes without a discard route, which turns unallocated space into a loop.
  • Assuming paths are symmetric. Stateful firewalls on only one of the paths will drop the half they never saw start.

Interview drill

Explain it simply: How does a router decide where to send a packet?

How a strong answer sounds
It looks up the packet's destination IP in its routing table and picks the matching entry with the longest prefix, the most specific route; the default route 0.0.0.0/0 matches everything, so it's used only when nothing else does. The entry either says the destination is on a connected network, in which case the router ARPs for the destination itself, or gives a next-hop router, in which case it ARPs for that neighbour. It decrements the TTL (dropping the packet and sending ICMP time exceeded at zero), rewrites the Ethernet header and sends it on. It knows nothing about the rest of the path: each router makes the same local decision, and the reply is routed independently.

Deeper: Users can reach a new subnet in one data centre from the office, but connections from there to a service in the office time out. Pings from the office to the new subnet work. What would you check?

How a strong answer sounds
Something about the reverse direction or about who starts the connection. Pings from the office work, so office → new subnet routing and the replies are fine. For connections the other way, I'd first check routing from the new subnet: ip route get <office IP> on a host there, then along the path, maybe the new subnet's default gateway or a summary route doesn't cover the office ranges for that source. Then check stateful devices: if the outbound path from the new subnet passes through a different firewall or NAT than the return path (asymmetric routing), that firewall sees SYN-ACKs for connections it never saw start and drops them. A capture on both sides (Chapter 37) shows exactly which packet disappears where.

🧠 Key takeaways

  • A routing table maps prefixes to connected interfaces or next-hop routers; ip route get shows which entry wins.
  • Longest-prefix match: the most specific matching route wins; the default 0.0.0.0/0 matches everything and loses to anything else.
  • Each router makes a local decision, decrements TTL and rewrites the frame; nobody knows the whole path.
  • The reply is routed independently: missing return routes and asymmetric paths are classic failures.
  • Static routes for small and cloud networks; OSPF/IS-IS inside an organisation; BGP between them.
  • Summary routes need a null route to stop unallocated space from looping.

Check your understanding

A router has routes 10.0.0.0/8 via A, 10.1.0.0/16 via B and 10.1.2.0/24 via C. Where does it send a packet for 10.1.2.3?

All three match, and /24 is the longest. List order is irrelevant.

With the same table, where does a packet for 10.9.9.9 go?

Only 10.0.0.0/8 matches. Without that route and without a default route, it would be dropped with ICMP "network unreachable".

What is the default route?

Prefix length 0 means no bits have to match. It's the least specific possible route.

A packet is caught in a routing loop between two routers. What eventually happens to it?

TTL exists for exactly this. Each hop subtracts 1; at 0 the packet is discarded. Unlike Ethernet frames, IP packets can't loop forever.

A client's SYN reaches the server, but the client's connection attempt times out. The server's routing table has no route back to the client's network. Why?

The reply is a new packet with its own routing decision. With no matching route (and no default), the server drops it: the classic one-way routing failure.
