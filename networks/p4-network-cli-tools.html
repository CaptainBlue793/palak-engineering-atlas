ping, curl, dig & Friends

"The API is down" can mean a dozen different things: the name doesn't resolve, the network can't reach the host, nothing is listening on the port, the certificate expired, or the application is returning errors. Each has a different owner and a different fix. A handful of command-line tools tell them apart in a minute, and this course uses them in nearly every chapter. This chapter is about running them and, more importantly, reading what they print.

  • Pick the right tool for each question: does it resolve, is it reachable, is it listening, does it answer?
  • Read ping and traceroute output, and know what they can't prove
  • Read a dig answer: status, TTL and which server answered
  • Follow a request through curl -v from DNS to response
  • Inspect your own machine with ip addr, ip route and ss
📚
What you need before this chapter
  • Ports, the 5-tuple and "connection refused". See P3.
  • A Linux or macOS terminal (on Windows, WSL). dig is in the dnsutils or bind-utils package. On macOS, use netstat or lsof -i where this chapter uses ss.

Four questions, in order

When a request to https://api.example.com/health fails, work up the stack and ask one question at a time. Each step only makes sense if the one before it passed, and each failure has a distinctive error message.

ping and traceroute

ping sends ICMP echo requests and measures how long each reply takes (Chapter 6 explains the packets):

$ ping -c 3 api.example.com
PING api.example.com (203.0.113.50) 56(84) bytes of data.
64 bytes from 203.0.113.50: icmp_seq=1 ttl=54 time=18.4 ms
64 bytes from 203.0.113.50: icmp_seq=2 ttl=54 time=18.1 ms
64 bytes from 203.0.113.50: icmp_seq=3 ttl=54 time=18.9 ms

--- api.example.com ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 18.1/18.4/18.9/0.3 ms

Three things to read. The first line shows the name already resolved to an address, so DNS worked. time= is the round-trip time (P8). And ttl=54 is what was left of the reply's hop counter: Linux servers usually start at 64, so the reply crossed about 10 routers. Two cautions: many networks and cloud load balancers block ICMP, so 100% loss doesn't prove the host is down; and a successful ping says nothing about whether port 443 is open.

traceroute (tracert on Windows, mtr for a live view) lists the routers along the path with the RTT to each. Lines of * * * mean that hop didn't reply, which is common and usually harmless; it only matters if every hop after a point is stars.

dig: asking DNS directly

dig sends one DNS query and prints the answer in full. Unlike ping or a browser, it doesn't use any local cache tricks, and you can choose which server to ask:

$ dig api.example.com
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41205
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; ANSWER SECTION:
api.example.com.    300    IN    A    203.0.113.50

;; Query time: 23 msec
;; SERVER: 192.168.1.1#53(192.168.1.1) (UDP)

$ dig +short api.example.com @8.8.8.8         # just the answer, from a specific resolver
203.0.113.50

status is the first thing to check: NOERROR means the query worked; NXDOMAIN means the name doesn't exist; SERVFAIL means the resolver couldn't get an answer (often broken DNSSEC or unreachable name servers). NOERROR with an empty answer section means the name exists but has no record of that type. The 300 is the TTL in seconds: how long resolvers may cache this answer, which is why a DNS change can take minutes to reach everyone. SERVER shows which resolver answered. Comparing @8.8.8.8 with your default resolver is how you spot a stale or split-horizon answer. Chapter 10 explains the lookup itself.

curl -v: one request, every step

curl -v makes an HTTP request and narrates each stage. Lines starting * are curl's commentary, > lines are what it sent, and < lines are what came back:

$ curl -v https://api.example.com/health
* Host api.example.com:443 was resolved.
* IPv4: 203.0.113.50
*   Trying 203.0.113.50:443...
* Connected to api.example.com (203.0.113.50) port 443         # TCP handshake done
* ALPN: curl offers h2,http/1.1
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / X25519
* ALPN: server accepted h2                                       # TLS done; HTTP/2 agreed
* Server certificate:
*  subject: CN=api.example.com
*  expire date: Mar 14 23:59:59 2027 GMT
> GET /health HTTP/2
> Host: api.example.com
> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/2 200
< content-type: application/json
< content-length: 15
<
{"status":"ok"}

Where the output stops tells you which layer failed. Useful flags: -I for headers only, -o /dev/null -s -w '%{time_connect} %{time_appconnect} %{time_total}\n' to time each phase (Chapter 38), --connect-timeout 5 so a dropped SYN fails in 5 seconds instead of minutes, and --resolve api.example.com:443:203.0.113.51 to test one specific backend while keeping the right hostname for TLS. Never "fix" a certificate error with -k outside a lab: it disables the check that stops someone impersonating the server.

Your own machine: ip and ss

$ ip -br addr                              # my addresses, one line per interface
lo        UNKNOWN  127.0.0.1/8 ::1/128
wlan0     UP       192.168.1.23/24 fe80::1c2b:9aff:fe31:7d10/64

$ ip route                                 # where packets go
default via 192.168.1.1 dev wlan0 proto dhcp metric 600
192.168.1.0/24 dev wlan0 proto kernel scope link src 192.168.1.23

$ ss -tlnp                                 # who listens on which TCP port
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN 0      4096       127.0.0.1:5432       0.0.0.0:*     users:(("postgres",pid=812,fd=6))
LISTEN 0      511          0.0.0.0:80         0.0.0.0:*     users:(("nginx",pid=1044,fd=6))

ip addr answers "what is my address and mask" (P2). ip route shows the routing table: anything on 192.168.1.0/24 goes straight out of wlan0, everything else goes to the default gateway 192.168.1.1 (Chapter 5). ip route get 8.8.8.8 asks the kernel exactly which route it would use for one destination. ss -tlnp answers "is my server actually listening, and on which address?" Here PostgreSQL listens only on 127.0.0.1, so other machines get "connection refused" even though the database is running.

"Ping works, so it's not the network"
During an incident, an on-call engineer pings the payment gateway's address, gets clean replies, and spends forty minutes in application logs. The real problem was a firewall change that dropped TCP 443 to that gateway while still allowing ICMP. Two commands would have found it in a minute: nc -vz gateway 443 timing out (not refused) says packets to the port are being dropped on the way, and curl -v stopping at Trying …:443... says the same. The lesson is that each tool tests one layer and one protocol. ICMP succeeding says nothing about TCP 443, and TCP 443 succeeding says nothing about whether the certificate is valid.

  


  
⚠️
Common mistakes

    
    
      
  • Treating ping as proof. ICMP is often blocked, and even when it works it doesn't test your port or protocol.
    • 
      
  • Not telling "refused" from "timed out". Refused: the host answered with RST, nothing listens. Timed out: something dropped the packets.
    • 
      
  • Using curl -k to "fix" a TLS error. It hides the problem and removes the protection.
    • 
      
  • Testing a backend by IP and getting a certificate error. Use --resolve so SNI and the Host header keep the real name.
    • 
      
  • Using nslookup or ping to check DNS changes. They go through local caches and the search domain; dig @server asks exactly who you choose.
    • 
    


  
🎤
Interview drill

    
Explain it simply: A service can't reach db.internal:5432. Walk me through how you'd debug it.

    
How a strong answer sounds
Bottom up, one question at a time. First, does the name resolve from that host: dig db.internal, checking the status and that the address is the one I expect. Second, can I reach the port: nc -vz db.internal 5432. "Refused" means the host answered but nothing listens there, so I'd check ss -tlnp on the database host, often it's bound to 127.0.0.1. "Timed out" means something dropped the packets, so security groups, firewalls or routing (ip route get). Third, if the port is open, it's the protocol or credentials: psql with verbose errors, TLS settings, pg_hba.conf. I'd say which result rules out which layer as I go.

    
Deeper: dig returns the new IP after a DNS change, but users still hit the old server for twenty minutes. Why?

    
How a strong answer sounds
Caching at several layers. The record's old TTL was probably long, and every recursive resolver that cached it may keep the old answer until that TTL expires; my dig may have gone to a resolver that didn't have it cached, or straight to the authoritative server. Beyond DNS TTLs, operating systems, browsers and especially long-running processes cache too: JVMs historically cached lookups for a long time, and existing keep-alive connections never re-resolve at all, they stay on the old server until closed. The practice is to lower the TTL well before a migration, keep the old server serving during the overlap, and drain long-lived connections.

  


  

    
🧠 Key takeaways

    
    
      
  • Debug bottom-up: resolve (dig) → reach (ping, traceroute) → port (nc) → TLS → application (curl -v).
    • 
      
  • dig: read the status (NOERROR, NXDOMAIN, SERVFAIL), the answer, the TTL and which server answered.
    • 
      
  • curl -v: * is commentary, > was sent, < was received; where it stops is where it failed.
    • 
      
  • "Connection refused" = host up, no listener. "Timeout" = packets dropped somewhere.
    • 
      
  • Ping can be blocked and proves nothing about TCP ports.
    • 
      
  • ip addr, ip route and ss -tlnp describe your own machine: addresses, routes and listeners.

Check your understanding

    


    

      
curl prints Failed to connect to api.example.com port 443: Connection refused. What do you know?

      

        
        
        
        
      

      
"Refused" means a reset came back, so the packets reached a host that has no listening socket on that port. A silent drop would produce a timeout instead.

    


    

      
ping to a host works, but curl to port 443 hangs and then reports a timeout. What's the most likely cause?

      

        
        
        
        
      

      
The host is reachable (ping), and nothing answers the SYN at all, not even a reset. Something between is dropping packets to that port.

    


    

      
dig shows status: NXDOMAIN. What does it mean?

      

        
        
        
        
      

      
NXDOMAIN is an authoritative "no such name". A name that exists without that record type gives NOERROR with an empty answer, and a resolver that can't get any answer returns SERVFAIL.

    


    

      
In curl -v output, what do lines starting with > show?

      

        
        
        
        
      

      
> is outgoing (the request), < is incoming (the response), and * is curl's own commentary on DNS, TCP and TLS.

    


    

      
A reply shows ttl=54 from a Linux server. Roughly how many routers did it cross?

      

        
        
        
        
      

      
TTL is a hop counter, not a time. Linux starts at 64 and each router subtracts 1, so 64 − 54 = 10 hops (Windows starts at 128, many routers at 255).
