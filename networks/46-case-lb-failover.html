Load-Balancer Failover

A service runs on four servers behind a load balancer, so that losing one doesn't matter. Then one is lost, at a quarter past two on a busy afternoon, and for the next half minute a quarter of all requests fail. The redundancy was real, and the half minute is the time it took the balancer to find out. This case study follows that failure second by second: what the balancer sees, what users see, and which settings shorten the gap. It then covers the two related situations, removing a server on purpose without dropping a request, and the load balancer itself failing.

  • Work out how long a balancer takes to stop using a failed server, for a crash and for a freeze

  • Explain how a pair of load balancers shares one address with VRRP, and what a failover costs

Three ways a server fails

How long a failure takes to detect depends on how the server stops, because the balancer learns of it from what comes back.

The process crashesThe host freezes or is cut offThe server is sick
ExampleAn unhandled exception. The out-of-memory killerA kernel panic, a failed power supply, a pulled cableA full disk, a lost database connection, a bad deploy

The middle column is the hard one, and it is common. A machine that has stopped can't send a reset to say so. Everything the balancer sends it disappears, and all the balancer can do is wait.

Health-check timing

Chapter 24 worked out the usual result: a check every 10 seconds, with three failures required, leaves a dead server in rotation for about 30 seconds. In general:

time to eject  =  interval × failures required  +  the probe's timeout     # at worst

# interval 10 s, 3 failures, timeout 2 s   →  up to 32 s
# interval  5 s, 3 failures, timeout 2 s   →  up to 17 s
# interval  1 s, 3 failures, timeout 1 s   →  up to  4 s

It is tempting to set every number as low as it will go, and there is a cost on the other side. A server that pauses for two seconds to collect garbage, or answers one probe slowly under load, is ejected by an aggressive check, and its share of the traffic lands on the others, which are now more likely to answer slowly themselves. Checks that are too sensitive can take a healthy fleet apart at the moment it is busiest. Three practices keep them stable: require several consecutive failures to eject and several successes to return, bring a returning server back with a gradually rising share of traffic, and never let the check eject more than a set fraction of the fleet.

Each server receives 100 requests a second. Active checks need three failures, with a timeout of 2 s, or 1 s at the fastest setting. A request to the frozen server times out after 3 s. The model takes the worst case for active checks: the server fails just after passing one.

Things to notice. With the defaults, a frozen server stays in rotation for 32 seconds and 3,200 requests are lost, each after the user has waited three seconds for it. A check every second reduces that to 400, at the risk of ejecting servers that are only slow. Passive ejection treats the two kinds of failure very differently. A crashed server refuses connections instantly, five failures arrive within a twentieth of a second, and only five requests are affected. A frozen server gives no signal until the first requests time out three seconds later, by which time 305 have been sent to it. Retrying on another server rescues the four-fifths that are safe to repeat: at once for a crash, and after the timeout for a freeze, when the user gets a slow answer in place of an error. The writes can't be rescued this way, because the balancer can't tell whether the frozen server acted on them.

Retries and idempotency

A retry is safe when doing the request twice has the same effect as doing it once. That property is idempotency. What the balancer needs to know is how far the first attempt got.

What happened to the first attemptMay it be retried on another server?
The connection was refused or never openedYes, always. The server never saw the request
A GET, HEAD, PUT or DELETE was sent, and nothing came backYes. These are defined so that repeating them is harmless
A POST was sent, and nothing came backNot by the balancer. The order may have been placed, or the payment taken
A POST carrying an idempotency keyYes. The server remembers the key and returns the first result instead of acting again
Part of a response had already been sent to the clientNo. It can't be taken back
 
# A client making a payment safe to retry, by naming the operation
import uuid, requests

key = str(uuid.uuid4())                     # made once per payment, and reused on every retry of it
for attempt in range(3):
    try:
        r = requests.post("https://api.example.com/payments", json=payment,
                          headers={"Idempotency-Key": key}, timeout=3)
        break
    except requests.exceptions.RequestException:
        continue                               # the server will recognise the key if the first attempt got through

Retries have to be limited as well as safe. One retry of a failed request is cheap. Retrying everything, at every layer, during a partial outage multiplies the load on the servers that are left (Chapter 32).

🧠
The broken server that took most of the traffic

Engineers at Amazon have described a kind of failure that reverses what a load balancer is for. A fleet sits behind a balancer that sends each new request to the server with the fewest requests in progress, which is normally the best policy, since it steers work away from servers that are busy or slow. One server develops a fault that makes it fail every request immediately: a missing dependency, a bad configuration file, a full disk. It still answers the balancer's health check, because the check only asks whether the process is up. Now consider what the balancer sees. The healthy servers each have dozens of requests in progress, taking tens of milliseconds apiece. The broken one never has any, because each request it receives is finished, with an error, in a fraction of a millisecond. By the balancer's measure it is the least loaded server in the fleet at every moment, so it is given the next request, and the one after that. A single faulty machine in a fleet of dozens can end up receiving most of the traffic and failing all of it, while every dashboard shows it as healthy and fast. Engineers call this a black hole. The defences are a health check that exercises real work on the server, passive ejection on error rate, and clients that retry on a different server. A health check that only asks whether the process is up would not have caught this.

Draining connections

Most servers that leave a pool haven't failed. They are being deployed to, or scaled in, or moved, many times a day. Done abruptly, each removal cuts off the requests in progress and looks to users like a small outage. Done properly it is invisible, and the procedure is called draining.

# The server's half: on SIGTERM, fail readiness first, keep serving, then stop
import signal, threading, time

draining = threading.Event()

def on_sigterm(signum, frame):
    draining.set()                             # /ready now returns 503, and the balancer stops choosing us
    time.sleep(10)                             # long enough for every balancer to have noticed
    server.shutdown()                          # stop accepting, and finish what is in progress

signal.signal(signal.SIGTERM, on_sigterm)

# The balancer's half, in two common systems
#   AWS target group:   deregistration_delay.timeout_seconds = 30
#   Kubernetes:         terminationGracePeriodSeconds: 45, with a preStop hook that sleeps for 10 s

The ten-second pause is the part most often left out. Telling the balancers takes time: a health check has to fail, or an update has to reach every proxy (Chapter 31). A server that stops listening the moment it is asked to will refuse requests from balancers that haven't yet heard.

Active–passive LB pairs and VRRP

The balancer protects the service from a server failing, and something has to protect the service from the balancer failing. The classic arrangement is two balancers sharing one address. Clients and DNS know only a virtual IP. One balancer, the master, holds it and handles all the traffic, and the other, the backup, stands by. VRRP, the Virtual Router Redundancy Protocol, decides which is which.

# keepalived on the master. The backup has the same block with state BACKUP and priority 100.
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 150
    advert_int 1
    virtual_ipaddress { 10.0.0.100/24 }
    track_script { chk_haproxy }          # give up the address if the proxy itself has died
}
QuestionAnswer
How long is the gap?Three missed advertisements and a little more: about 3.6 s with the defaults, and under a second if tuned
What happens to open connections?They break, unless the pair synchronises its connection table. The backup has never heard of them and answers their packets with resets. Clients reconnect
What if the link between the two fails, and both are alive?Each stops hearing the other and both claim the address: a split brain. Use more than one path between them
Does the old master take the address back when it returns?By default yes, which causes a second interruption. Many operators turn that off
What is the weakness?Half the capacity is idle, and it only works within one LAN

Larger systems use a different design. Routers spread traffic across many balancers by ECMP, each balancer announces the service's address, and consistent hashing lets any balancer handle any connection, so that losing one moves only its share (Chapter 30, Chapter 26). Cloud load balancers do this out of sight. A pair with a floating address is still what stands in front of many databases and smaller services.

⚠️
Common mistakes
  • Leaving health-check timing at its defaults without working out what 30 seconds of failures costs.
  • Timeouts longer than users will wait. A 60-second timeout to a frozen server means users give up long before the balancer does.
  • Retrying requests that aren't idempotent. A retried payment is a double charge.
  • Stopping the process and removing it from the balancer at the same moment. Requests arrive at a closed port until the balancer catches up.
  • A health check that tests only that the process is up. Sick servers pass it.
  • Never testing the failover. A backup balancer that hasn't taken the address in a year has a configuration a year old.
🎤
Interview drill

Explain it simply: What is connection draining, and why is it needed?

How a strong answer sounds
Draining is how you take a server out of a load balancer's pool without failing the requests it is handling. When a server is to be removed, for a deploy or a scale-in, the balancer stops sending it new requests but leaves existing connections alone, so in-flight requests can finish. Idle keep-alive connections are closed gracefully, with Connection: close or an HTTP/2 GOAWAY, so clients open their next connection to another server. After all requests have completed, or a drain timeout such as 30 seconds has passed, the server is shut down. Without it, every deploy would cut off whatever requests happened to be in progress, and users would see errors many times a day. The detail that matters is ordering: the server must keep accepting requests for a short while after it is told to stop, because the balancers take a moment to learn that it is leaving; so the usual pattern is to fail the readiness check first, wait, and only then stop listening.

Deeper: One of four backends freezes without crashing. Walk me through what users experience, and how you would reduce it.

How a strong answer sounds
A frozen host is the worst case because it sends nothing back, no reset and no error, so everything is detected by timeout. A quarter of requests are routed to it and hang. The active health check has to fail several times: with a 10-second interval and three failures required, plus the probe timeout, it stays in rotation for around 30 seconds. During that time each of those requests waits for the balancer's backend timeout and then fails, so users see a quarter of requests being slow and then erroring. To reduce it I'd work on three things. Detection: shorter intervals and sensible timeouts for the active check, though not so aggressive that slow-but-healthy servers get ejected, and passive ejection, outlier detection, on real traffic; noting that passive detection of a freeze still costs one request timeout, so the backend timeout should be close to the real p99 and not a default of 60 seconds. Rescue: have the balancer retry on a different backend for connection failures and for idempotent requests, with a retry budget, and use idempotency keys so that important writes can be retried as well. A short connect timeout helps a lot, since a frozen host won't complete a handshake for new connections, and an unanswered SYN is always safe to retry. And blast radius: enough spare capacity that three servers can carry the load, and a limit on how much of the fleet health checks may eject. I'd then test it by actually freezing a server, for example with a firewall rule that drops its packets.

🧠 Key takeaways

  • A crash is detected quickly, because the kernel refuses connections. A freeze is detected only through timeouts.
  • Time to eject is about the check interval times the failures required, plus the probe timeout. Work it out for your settings.
  • Passive ejection reacts to real traffic within milliseconds for errors, and within one request timeout for silence.
  • Retries on another server rescue idempotent requests. Writes need an idempotency key before they can be repeated.
  • To drain: stop new requests, let those in progress finish, close idle connections, and only then stop the process.
  • A pair of balancers shares a virtual IP with VRRP. Failover takes seconds, and breaks open connections unless state is synchronised.

Three probes at 5, 10 and 15 seconds, and the last one takes 2 more seconds to time out.

Why does passive ejection remove a crashed server almost instantly, and a frozen one only after seconds?

Passive ejection counts failures, and a failure by silence is only known when the timeout expires.

A GET is idempotent, and a refused connection means the server never saw the request.

Traffic must stop arriving before the process stops listening.

The address stays the same. Only the machine answering for it changes.
