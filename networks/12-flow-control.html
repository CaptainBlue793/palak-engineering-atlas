Flow Control & the Receive Window

A server on a fast link can produce bytes far quicker than a phone on the other end can use them, and TCP has promised that none of those bytes will be thrown away. So the receiver needs a way to say "slow down", and it has one: in every segment it sends, a 16-bit field announces how much room is left in its buffer. That number is the receive window, and the sender is never allowed to have more than that much data in flight. This chapter covers how the window opens and closes, what happens when it reaches zero, why a 16-bit field had to be stretched for modern networks, and how to read all of it in a capture, where it often turns out that the "network problem" is an application that isn't reading.

  • Explain window scaling and work out the throughput a given window allows

The receive window

When segments arrive, the kernel puts their bytes in the socket's receive buffer, where they wait until the application calls recv(). If the application reads as fast as data arrives, the buffer stays nearly empty. If it reads slowly, the buffer fills. The receiver reports the free space in the window field of every segment it sends, and the sender obeys one rule:

bytes sent but not yet acknowledged  ≤  the last window the receiver advertised

That divides the sender's stream into four parts, and the middle two are the sliding window: as acknowledgements arrive its left edge moves right, and as the receiver's application reads, the right edge moves too.

Bytes that are…The sender
Sent and acknowledgedHas forgotten them
Sent, not yet acknowledgedKeeps a copy in case of loss. This amount must fit inside the window
Not sent, but inside the windowMay send them now
Beyond the windowMust wait until an ACK moves the window forward

Zero window and probes

A window of zero stops the sender completely. It resumes when the receiver sends a window update, an acknowledgement whose only news is a larger window. That creates a danger. A window update carries no data, so it is never retransmitted, and if it is lost both sides would wait for ever: the sender for permission, the receiver for data. So a sender facing a zero window starts a persist timer and, each time it fires, sends a zero-window probe of one byte. The acknowledgement of the probe always carries the current window.

$ sudo tcpdump -ni eth0 'host 10.0.0.9 and port 9092'
10:02:11.402 IP 10.0.0.5.39120 > 10.0.0.9.9092: Flags [P.], seq 73001:74449, ack 1, win 502, length 1448
10:02:11.402 IP 10.0.0.9.9092 > 10.0.0.5.39120: Flags [.], ack 74449, win 0, length 0          # Wireshark: [TCP ZeroWindow]
10:02:11.612 IP 10.0.0.5.39120 > 10.0.0.9.9092: Flags [.], seq 74448:74449, ack 1, win 502, length 1   # probe, after 210 ms
10:02:11.612 IP 10.0.0.9.9092 > 10.0.0.5.39120: Flags [.], ack 74449, win 0, length 0
10:02:12.032 IP 10.0.0.5.39120 > 10.0.0.9.9092: Flags [.], seq 74448:74449, ack 1, win 502, length 1   # the interval doubles
10:02:12.032 IP 10.0.0.9.9092 > 10.0.0.5.39120: Flags [.], ack 74449, win 0, length 0
10:02:12.588 IP 10.0.0.9.9092 > 10.0.0.5.39120: Flags [.], ack 74449, win 229, length 0        # [TCP Window Update]

In a capture, a zero window is one of the most useful things you can find, because of what it rules out. The network delivered everything, and the kernel on the receiving machine accepted it. The application on that machine stopped calling recv(), or is calling it too slowly. It may be busy, blocked on a database or a disk, paused for garbage collection, or deliberately not reading because its own downstream is slow. That last case is back-pressure working as designed: a slow consumer at the end of a chain makes each buffer behind it fill in turn, until the original producer's send() blocks.

Window scaling

The window field is 16 bits, so it can announce at most 65,535 bytes. That was generous in 1981. It isn't now, because the window caps throughput: the sender can have at most one window in flight per round trip.

Round-trip timeBest throughput with a 64 KB windowWith an 8 MB window (64 KB × 128)
1 ms (same data centre)524 Mbit/sThe link's limit
10 ms (same region)52 Mbit/s6.7 Gbit/s
100 ms (across an ocean)5.2 Mbit/s671 Mbit/s
600 ms (geostationary satellite)0.9 Mbit/s112 Mbit/s

The fix, from 1992, is the window scale option. In the handshake each side announces a shift count from 0 to 14, and from then on the 16-bit field is multiplied by 2 to that power. The wscale 7 in Chapter 8's capture means "multiply my window by 128". Two consequences are worth remembering:

  • It is announced only in the SYN. A capture that starts after the handshake can't know the factor, so tools show the raw field. A window of "229" in tcpdump, as above, is really 229 × 128 = 29,312 bytes.
  • Both sides must offer it. If the SYN-ACK comes back without the option, neither side scales, and the connection is limited to 64 KB for its whole life.
$ sysctl net.ipv4.tcp_window_scaling net.ipv4.tcp_rmem
net.ipv4.tcp_window_scaling = 1
net.ipv4.tcp_rmem = 4096  131072  6291456     # receive buffer: minimum, starting size, and the ceiling for autotuning

Linux grows each connection's receive buffer automatically, up to the third number, as it measures how fast data arrives. An application that sets SO_RCVBUF itself switches that autotuning off for the socket, which is a common way to make a transfer slower while trying to make it faster.

🧠
Windows Vista meets the world's firewalls

Window scaling had been in the standard since 1992, but for years the commonest desktop operating system barely used it. Windows Vista, released in 2007, changed that: it offered a scale factor on every connection and tuned its receive window automatically, so that downloads over long, fast paths would no longer be stuck at 64 KB. Within weeks, users were reporting the opposite of an improvement. Web pages half-loaded and hung, large downloads crawled, and some sites couldn't be reached at all, but only from certain offices and behind certain home routers. The cause was in devices between the two ends. Many firewalls and routers of the time inspected TCP and had been written when the option was rare. Some stripped it from the SYN in one direction only, so one side scaled and the other didn't. Others passed it but went on judging packets against the unscaled window, and dropped perfectly valid segments as "outside the window". Each end was behaving correctly and the connection still broke. Microsoft published a support article with the workaround of turning the feature down or off, and it took years of firmware updates before it was safe to assume scaling worked everywhere. The episode is a standard example of why new transport features are hard to deploy: boxes in the middle of the path read fields they were never meant to depend on (Chapter 18 shows the drastic answer to that).

Try it: a sliding window

A sender has 40 KB to deliver in 1 KB segments. The receiver's buffer holds 8 KB. Choose how fast the receiving application reads, and step through one round trip at a time.

The window follows the readerInteractive

The sender's 40 KB
The receiver's buffer (8 KB)

Each step is one round trip: the sender sends everything the last advertised window allows, the application reads, and the receiver's ACK reports the space that is left. The network here is perfect and has room for everything, so the receive window is the only limit.

Things to notice. With a reader that takes 8 KB per round trip, the window never closes and the 40 KB is delivered in 5 round trips. With the 2 KB reader, the first round trip sends 8 KB, and after that the window is 2 KB every time: the sender has been slowed to exactly the reader's pace, and the transfer takes 20 round trips. Nothing was lost and nothing was retransmitted. Stop the reader and the buffer fills, the window goes to zero, and each further round trip is one probe. Start it reading again and a window update releases the sender. You can also change the reader's speed in the middle of a run and watch the window follow it.

Flow control is not congestion control

TCP has two separate brakes, and they are easy to confuse because both are called windows. The receive window protects the receiver. The congestion window, the subject of Chapter 13, protects the network in between. The sender obeys whichever is smaller.

Flow control (receive window)Congestion control (congestion window)
ProtectsThe receiving host's bufferThe routers and links on the path
Set byThe receiver, and stated in every segmentThe sender, by inference. Nobody tells it
SignalAn explicit numberLoss and delay
Visible in a captureYes: the win fieldNo: it exists only in the sender's kernel (ss -ti shows it)
When it is the limitThe receiving application is slowThe path is slow or busy
⚠️
Common mistakes
  • Blaming the network for a zero window. It means the receiving application isn't reading. Look at that process.
  • Reading window values from a capture that missed the handshake. Without the scale factor the numbers look tiny. Capture the SYN, or apply the factor by hand.
  • Setting SO_RCVBUF to "tune" a connection. It disables autotuning and often lowers the window.
  • Confusing the receive window with the congestion window. One is announced by the receiver, the other is the sender's private estimate.
  • Ignoring a blocked send(). A send that blocks or returns "would block" is flow control reaching the application. Buffering everything in memory instead only moves the problem.
  • Assuming a fast link means a fast transfer. Over a long path, a small window caps throughput whatever the bandwidth.

Interview drill

Explain it simply: What is TCP flow control and how does it work?

How a strong answer sounds
Flow control stops a fast sender from overrunning a slow receiver. Each side has a receive buffer where arriving bytes wait for the application to read them. In every segment it sends, a host advertises its receive window, the free space in that buffer. The sender must keep the amount of data it has sent but not had acknowledged within that window. If the application reads slowly, the buffer fills, the advertised window shrinks, and the sender slows down to match. If the buffer is full the window is zero and the sender stops; it then sends small zero-window probes on a persist timer so that it will learn when space opens up even if the receiver's window update is lost. The window field is 16 bits, so the window scale option negotiated in the handshake multiplies it, allowing windows of megabytes. It's separate from congestion control, which limits the sender according to the state of the network, and the sender uses the smaller of the two limits.

Deeper: A capture of a slow data pipeline shows repeated "TCP ZeroWindow" from the consumer followed by window updates. What is happening, and what do you do?

How a strong answer sounds
The consumer's kernel is telling the producer its receive buffer is full, so the producer has to stop sending; when the consumer's application reads some data the window reopens, and the cycle repeats. That means the bottleneck is the consuming application's read rate, not the network: packets are arriving fine and waiting in the buffer. So I'd look at the consumer process. Is it CPU-bound, single-threaded on parsing, blocked writing to a database or disk, in long garbage-collection pauses, or throttled by its container's CPU limit? I'd check its CPU and I/O, take thread dumps or a profile, and look at the socket's receive queue with ss. Fixes are on that side: make processing faster or parallel, batch the downstream writes, or add consumers. I wouldn't just enlarge the buffers, since that only delays the same stall. It's also worth saying that this behaviour is correct. Back-pressure is propagating to the producer instead of data being dropped or memory growing without limit.

🧠 Key takeaways

  • Every TCP segment advertises a receive window: how much free space its sender has in its own receive buffer.
  • A sender may have at most one window of unacknowledged data in flight, so a slow reader slows the sender to its own pace.
  • A zero window stops the sender. Probes on a persist timer make sure it finds out when space returns.
  • A zero window in a capture points at the receiving application, not the network.
  • Window scaling, agreed in the SYN, multiplies the 16-bit field. Without it throughput is capped at 64 KB per round trip.
  • The receive window protects the receiver; the congestion window protects the network. The sender obeys the smaller.
