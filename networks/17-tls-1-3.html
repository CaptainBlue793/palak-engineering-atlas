TLS 1.3 & Certificates

Everything in the last nine chapters travels in the clear. Anyone on the path, the café's Wi-Fi router, an internet provider, a compromised switch, can read a TCP stream and can change it. TLS is the layer that fixes that, and it is now wrapped round nearly all traffic: the S in HTTPS, and the security of QUIC, of connections between services, and of your email. It has two separate jobs. One is to agree secret keys with a stranger over a network that someone is listening to. The other is to know that the stranger really is your-bank.com. The first is a matter of mathematics and takes one round trip. The second rests on certificates, and it is where most real-world failures happen.

What TLS guarantees

GuaranteeMeansProvided by
ConfidentialitySomeone on the path can't read the dataSymmetric encryption with keys only the two ends hold
IntegrityData can't be altered, inserted or dropped without detectionAn authentication tag on every record
AuthenticationThe server is who its name says. The client usually isn't authenticated at this layerThe server's certificate, and a signature made with its private key

It is worth being exact about what stays visible to an observer: the IP addresses and ports, the amount of data and its timing, and normally the server name the client asked for. That name travels in the first message, in a field called SNI, so that a server hosting many sites knows which certificate to present. And TLS says nothing about whether the server deserves your trust. A phishing site can have a perfectly valid certificate for its own name.

The TLS 1.3 handshake

ALPN is how the choice between HTTP/1.1 and HTTP/2 from Chapter 16 is made: the client lists what it speaks and the server picks, inside the handshake, at no extra cost. The lines marked s: and i: are each certificate's subject and issuer, which is the chain examined below.

ECDHE: agreeing a secret in public

The two sides have never met, and everything they send can be read. They still end up holding a number that nobody else knows. The method is Diffie–Hellman key exchange, shown here with numbers small enough to check by hand:

p, g = 23, 5                      # public parameters: everybody knows them

a = 6                             # the client's secret, never sent
A = pow(g, a, p)                   # 5**6 % 23 = 8      sent in the ClientHello

b = 15                            # the server's secret, never sent
B = pow(g, b, p)                   # 5**15 % 23 = 19    sent in the ServerHello

assert pow(B, a, p) == pow(A, b, p) == 2    # both arrive at 2. A listener saw 23, 5, 8 and 19

Each side combines its own secret with the other's public value and gets the same result. A listener has both public values and neither secret, and recovering a secret from them is the step that is easy with these numbers and infeasible with real ones. TLS 1.3 does the same thing on an elliptic curve, usually X25519, with 32-byte values. That is the EC and the DH of ECDHE.

The final E stands for ephemeral, and it matters as much. Both sides make a brand-new key pair for every connection and discard it afterwards. So if a server's long-term private key is stolen next year, traffic recorded today still can't be decrypted, because the keys that protected it no longer exist anywhere. That property is forward secrecy. Older versions of TLS allowed a key exchange without it, and TLS 1.3 removed that option.

Key exchange alone would not be enough. An attacker in the middle could run one exchange with the client and another with the server and read everything. What prevents it is the server's signature over the handshake, made with the private key that belongs to its certificate. So the question becomes whether to believe the certificate.

Certificate chains and CAs

A certificate is a signed statement: "this public key belongs to these names, from this date to that date", signed by an issuer. The client doesn't know the issuer of a web site's certificate either, so the issuer has a certificate too, signed by someone above it. The chain ends at a root certificate that is self-signed and that the client already holds: operating systems and browsers ship with about 150 trusted roots. Roots are kept offline, so day-to-day signing is done by an intermediate, which is why a chain normally has three links. A client makes four checks:

CheckQuestionTypical failure
NameIs the host name I asked for among the names in the certificate?A certificate for www served on api
DatesIs today within every certificate's validity period?Nobody renewed it. Or the client's clock is wrong
SignaturesWas each certificate really signed by the one above it, and is that one allowed to sign?The server didn't send the intermediate
TrustDoes the chain end at a root I already have?A self-signed certificate, or a company's private CA that this machine hasn't been told about

    Certificates used to last years and be renewed by hand, which is how they came to expire unnoticed. Since Let's Encrypt made issuing free and automatic in 2015, the trend has been to short lifetimes and automatic renewal: 90 days is common, and browser makers have agreed to cut the maximum to 47 days by 2029. A short lifetime also limits the damage of a stolen key, which matters because the mechanisms for cancelling a certificate early have never worked reliably.

    🧠
    30 September 2021: a root expires, and a correct chain stops working

    When Let's Encrypt began in 2015, its own root, ISRG Root X1, was new and no device trusted it yet. So its certificates also chained to an older root that devices already had, DST Root CA X3. That root's validity ended on 30 September 2021. By then almost every current system trusted ISRG Root X1 directly, the date had been announced years ahead, and servers were sending a chain that worked either way. On the day, a long list of services had failures all the same, among them Shopify, Xero, Fortinet and Auth0. Their certificates were fine. The trouble was in clients, and in particular in old versions of the OpenSSL library, still built into countless appliances, monitoring agents and back-end services. Given a chain that led to an expired root, that code rejected the connection without noticing that a second, valid path to a trusted root was available in its own trust store. Servers that had never changed began to be refused by programs that had never changed. Devices too old to have the new root at all, such as phones that had stopped receiving updates, simply lost access to a large part of the web. Trust is decided by the client, with the client's code and the client's list of roots. A certificate that validates in your browser tells you about your browser.

    Resumption and 0-RTT

    After a full handshake the server can give the client a session ticket, an encrypted note of the keys they share. On a later connection the client presents it, and the two skip the certificate and signature and derive new keys from the old ones. TLS 1.3 goes one step further and lets the client send its first request together with the ClientHello, encrypted under a key from the ticket. That is 0-RTT, or early data: no round trip at all before the request.

    Full handshakeResumption0-RTT
    TLS round trips before the request110
    Certificate sent and checkedYesNoNo
    Server's CPU costA signatureSmallSmall
    Forward secrecy for the first dataYesYesNo: it depends on the ticket's key
    Can be replayed by an attackerNoNoYes

    The replay is the catch. Early data is sent before the server has contributed anything fresh to the connection, so an attacker who records that first flight can send it again, and the server can't tell the copy from the original. A replayed GET /home is harmless. A replayed POST /transfer is a second transfer. So 0-RTT is allowed only for requests that are safe to repeat (Chapter 15), servers and CDNs usually restrict it to those, and an application behind one can check the Early-Data header and answer 425 Too Early to make the client retry after the handshake.

    ⚠️
    Common mistakes
    • Disabling verification to make an error go away. curl -k and verify=False keep the encryption and remove the authentication, so anyone in the path can read and alter the traffic.
    • Not sending the intermediate certificate. Browsers hide the mistake and other clients fail. Configure the full chain and test with openssl s_client.
    • Renewing by hand. Expiry is the most common TLS outage. Automate renewal and alert on days remaining.
    • Testing only in a browser. Trust stores and chain building differ between browsers, curl, Java, old Android and embedded devices.
    • Believing TLS hides which site you visit. The server name is normally sent unencrypted, and so are the DNS lookup and the IP address.
    • Allowing 0-RTT for requests that change state. Early data can be replayed.

    Interview drill

    Explain it simply: What happens in a TLS 1.3 handshake?

    How a strong answer sounds
    After the TCP handshake, the client sends a ClientHello with the versions and cipher suites it supports, a freshly generated ephemeral public key, the server name in the SNI extension and the application protocols it supports in ALPN. The server replies with a ServerHello containing its own ephemeral public key. From the two key shares, both sides compute the same secret by elliptic-curve Diffie–Hellman and derive encryption keys, so the rest of the handshake is encrypted. The server then sends its certificate chain, a signature over the handshake transcript made with the certificate's private key, and a Finished message. The client validates the chain: the name matches, the dates are valid, each signature verifies, and it ends at a trusted root. It checks the signature, which proves the server holds the private key and that nobody tampered with the exchange, sends its own Finished, and can send application data straight away. That is one round trip, against two in TLS 1.2, and because the key exchange is ephemeral it has forward secrecy.

    Deeper: A new API endpoint works in every browser, but a partner's server-side integration fails with a certificate error. What do you check?

    How a strong answer sounds
    The classic cause is an incomplete chain: the server is sending only its own certificate and not the intermediate. Browsers cope, because they fetch missing intermediates using the issuer address in the certificate or use cached ones, but most HTTP libraries, curl, Java and mobile clients don't, and report something like "unable to get local issuer certificate" or a PKIX path-building failure. I'd run openssl s_client -connect host:443 -servername host -showcerts and count the certificates returned; if there is only one, I'd configure the server or load balancer with the full chain, leaf then intermediates. If the chain is complete, I'd look at the partner's side: an old trust store that lacks the root, as happened with old clients when a widely used cross-signing root expired in 2021, a clock that is wrong, a TLS-inspecting proxy presenting its own certificate, or a name mismatch if they call a different host name or an IP address. I'd ask for the exact error text, since each failure has a distinct message, and I wouldn't suggest disabling verification.

    🧠 Key takeaways

    • TLS gives confidentiality, integrity and authentication of the server. Addresses, sizes, timing and usually the server name stay visible.
    • The TLS 1.3 handshake takes one round trip: key shares in the hellos, then the certificate and a signature, already encrypted.
    • Ephemeral Diffie–Hellman lets two sides agree a secret in public, and gives forward secrecy because the keys are thrown away.
    • A client checks the name, the dates, the signatures up the chain, and that the chain ends at a root in its own trust store.
    • Servers must send the intermediate. Trust is decided by each client's code and root list, and browsers are the most forgiving.
    • Resumption skips the certificate, and 0-RTT skips the round trip, but early data can be replayed, so it is for idempotent requests only.

    Check your understanding

    On a new connection, how many round trips does the TLS 1.3 handshake add before the client can send its request?

    ClientHello out, ServerHello and certificate back, and the request goes with the client's Finished. TCP's handshake is a separate round trip before it.

    An attacker records an encrypted session today and steals the server's certificate key a year later. Why can't they decrypt the recording?

    Forward secrecy. The long-term key authenticates the handshake and doesn't protect the session keys.

    What stops an attacker in the middle from doing a separate key exchange with each side?

    The attacker can't produce that signature for the real server's name, so the client sees a certificate error.

    A site loads in Chrome, but curl reports "unable to get local issuer certificate". What is the most likely cause?

    Without the intermediate, curl can't link the server's certificate to any root it has.

    Why should 0-RTT early data carry only idempotent requests?

    Nothing fresh from the server is mixed into early data, so a copy is as valid as the original.
