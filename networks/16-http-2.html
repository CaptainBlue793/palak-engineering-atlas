HTTP/2

HTTP/1.1 does one thing at a time on each connection, so browsers open six connections, and sites bend themselves out of shape to need fewer requests. HTTP/2, standardised in 2015, keeps everything a developer sees of HTTP, the methods, status codes, headers and URLs, and replaces what goes on the wire. Messages are cut into small binary frames, each labelled with the request it belongs to, so any number of requests and responses can share one connection, interleaved. It fixed the problem it set out to fix. It also made a different problem more visible, one that lives a layer down in TCP, and that is what the following two chapters are about.

Frames and streams

An HTTP/2 connection carries a sequence of frames. Every frame starts with the same nine bytes:

Length24 bitsType8 bitsFlags8 bitsStream ID31 bits Payloadheader fields, a piece of a body, or a control message, up to 16 KB by default

The length field is the framing: a receiver always knows exactly where a frame ends, and the ambiguity that made request smuggling possible in Chapter 15 has nowhere to hide. The stream ID is the new idea. A stream is one request and its response. The client numbers its requests 1, 3, 5 and so on, and every frame says which stream it belongs to, so frames of different exchanges can be mixed in any order.

The request line has become four header fields whose names start with a colon, and Host is now :authority. The meaning is unchanged from HTTP/1.1. An application behind a web server usually can't tell which version the client spoke. The two ends choose the version while setting up TLS, through a field called ALPN (Chapter 17), and browsers use HTTP/2 only over TLS.

Multiplexing

That removes the head-of-line blocking of HTTP/1.1, and several things follow from it:

  • One connection per site. One TCP handshake, one TLS handshake, and one congestion window that stays warm, where there were six that each started cold.
  • A hundred requests at once. Servers typically allow about 100 concurrent streams, so nothing queues waiting for a free connection.
  • Priorities. With everything on one connection, the browser can tell the server what matters most, and the server sends the stylesheet before the images. Six separate connections each got an equal share of the link, whatever they carried.
  • A second layer of flow control. Each stream has its own window, so one slow consumer, such as a paused video download, can't use up the connection's buffer and starve the other streams.
  • Cancelling is cheap. A stream can be reset without closing the connection. In HTTP/1.1 the only way to abandon a response was to close and reconnect.
  • The old tricks backfire. Spreading files over several host names now splits traffic across connections for no gain, and one giant bundle defeats caching. Many small files are fine.

HPACK header compression

HTTP headers are repetitive. Every request to a site carries the same user agent, the same accepted formats and the same cookies, often 500 bytes or more, and a page makes a hundred requests. HPACK removes the repetition with three devices: a fixed table of 61 very common fields that both sides know in advance, a dynamic table to which each side adds the fields it has sent on this connection, and a compact encoding for strings. A field that is in a table is sent as a one-byte index.

First request on the connectionSecond request
:method: GET1 byte: it is in the fixed table1 byte
:pathSent in full, and compressedSent in full: it differs each time
user-agent: Mozilla/5.0 … (about 110 bytes)About 80 bytes, and added to the dynamic table1 byte
cookie: session=… (about 300 bytes)About 230 bytes, and added to the table1 byte
Total for typical headersAbout 400 bytesAbout 30 bytes

Why not simply compress the headers with gzip? HTTP/2's predecessor did, and in 2012 an attack called CRIME showed the danger. If an attacker can add chosen text to requests that also carry a secret cookie, the compressed size shrinks slightly whenever a guess matches part of the secret, and the cookie can be recovered a character at a time. HPACK was designed so that matches only ever involve whole header fields, which gives away nothing of the kind. The dynamic table also makes compression stateful: frames must be decoded in the order they were encoded. That is harmless on TCP, which delivers in order, and it becomes a design problem for HTTP/3 (Chapter 18).

Server push, and its retirement

HTTP/2 allowed a server to answer a request the browser hadn't made yet. On a request for index.html it could announce "you will want style.css too" and start sending it, saving a round trip. In practice the feature did more harm than good. The server couldn't know what was already in the browser's cache, so it often pushed bytes that were thrown away, and pushed data competed for bandwidth with things the page needed sooner. Measurements showed little benefit, and Chrome removed support in 2022. Its replacement is a hint. The server sends an early 103 response that lists files worth fetching, and the browser decides for itself, with its cache in view.

TCP head-of-line blocking

Now the catch. HTTP/2 puts every stream on one TCP connection, and TCP knows nothing about streams. It delivers one ordered sequence of bytes (Chapter 11). If a single packet is lost, every byte behind it waits in the kernel until the retransmission arrives, whichever stream it belongs to. Head-of-line blocking has been removed from the HTTP layer and has reappeared one layer down.

A model: the link carries four packets every 20 ms, shared among whatever is being sent, and connection set-up is left out. Over HTTP/2 the browser marks the stylesheet, script and font as urgent and the server sends them first. A lost packet is repaired after 240 ms. Until then the packets behind it on the same connection arrive but can't be handed to the browser: they are the faded cells. The lost packet has a red outline.

Things to notice. With no loss, both finish the page at the same moment, 420 ms, because the link is the limit either way. What changes is the order. Over six connections every file gets an equal share of the link, and the stylesheet takes 160 ms and the script 360 ms. Over HTTP/2 the urgent files go first: the stylesheet is in at 80 ms and the script at 160 ms, so the browser can start drawing the page much sooner. Now lose one packet. With six connections the loss holds up one connection, the one carrying the large image, and nothing else changes. With HTTP/2 the same single loss freezes every file. The packets keep arriving and none can be delivered, and the stylesheet that was due at 80 ms arrives at 260 ms. On a clean network HTTP/2 is the better protocol. On a lossy one, six independent connections can beat it, and that observation is what led to HTTP/3.

Rapid Reset: cheap streams as a weapon

In August 2023 Google, Cloudflare and Amazon began seeing denial-of-service attacks larger than any on record. Google reported a peak of 398 million requests per second, about seven times its previous record, and the traffic came from a fairly small botnet. The attackers had found a use for two features in this chapter. An HTTP/2 client can open a stream with one small frame, and it can cancel a stream with another. The limit of 100 concurrent streams counts only streams that are open. So a client could send a request and cancel it immediately, again and again, thousands of times in a single packet, without ever exceeding the limit. Each cancelled request still cost the server real work: parsing it, starting to route it to a back end, and then tearing it down. The client spent almost nothing and never waited for a response. The flaw, named Rapid Reset, was in the protocol's design and not in any one implementation, so nearly every HTTP/2 server was exposed, and it was disclosed in October 2023 once the vendors had fixes. The fixes count cancellations and close connections that abuse them. A protocol that makes something cheap for honest clients makes it cheap for attackers too, and every limit has to be drawn round the work the server does, not round what the protocol calls "open".

Common mistakes
  • Keeping HTTP/1.1 workarounds. Host-name sharding and giant bundles hurt under HTTP/2.
  • Assuming HTTP/2 is faster everywhere. On a lossy path a single connection is a single point of stalling.
  • Balancing HTTP/2 by connection. One long-lived connection carries thousands of requests, so a connection-level load balancer sends them all to one back end (Chapter 24).
  • Ignoring GOAWAY. A server that is shutting down says so. A client that doesn't move to a new connection sees failed requests on every deploy.
  • Leaving stream and reset limits at "unlimited". Rapid Reset showed what that costs.
  • Expecting to read it with tcpdump -A. It is binary, and normally encrypted. Use the browser's tools or nghttp.

Interview drill

Explain it simply: What does HTTP/2 change compared with HTTP/1.1?

How a strong answer sounds
The semantics stay the same: methods, status codes, headers and URLs. What changes is the wire format. HTTP/1.1 is text, with one request and response at a time per connection, so browsers open about six connections per host. HTTP/2 is binary: messages are split into frames, each carrying a stream identifier, and frames from many streams are interleaved on a single TCP connection. That is multiplexing. Many requests are in flight at once and responses return in any order, which removes HTTP-level head-of-line blocking and needs only one handshake and one congestion window. Headers are compressed with HPACK, which uses a static table and a per-connection dynamic table, so repeated headers such as cookies cost a byte. There is per-stream flow control and the ability to cancel a single stream. Server push existed and has been withdrawn. The remaining weakness is that everything rides on one TCP connection, so a lost packet delays all streams until it is retransmitted.

Deeper: HTTP/2 removed head-of-line blocking. Why do people say it still has it?

How a strong answer sounds
It removed it at the application layer and left it at the transport layer. In HTTP/1.1 a slow response blocked the requests behind it on that connection. HTTP/2's streams fixed that: frames are interleaved, so a slow response doesn't hold up others. But all those streams share one TCP connection, and TCP delivers a single ordered byte stream. If one packet is lost, the receiver's kernel can't deliver any bytes after the gap until the retransmission arrives, even though the later packets carry frames for entirely different streams that are complete. So one loss stalls every stream for about a round trip or a retransmission timeout. With HTTP/1.1's six connections, a loss stalled only one of them. On clean networks HTTP/2 wins; on lossy mobile networks it can do worse. The fix can't be made inside TCP without changing every operating system and middlebox, which is why QUIC was built on UDP with streams implemented in the transport itself: loss on one stream doesn't block delivery on the others.

🧠 Key takeaways

  • HTTP/2 keeps HTTP's meaning and changes its wire format to binary frames, each tagged with a stream ID.
  • A stream is one request and response. Many streams are interleaved on one connection: multiplexing.
  • One connection per site means one handshake and one warm congestion window, and about 100 requests in flight.
  • HPACK replaces repeated headers with table indexes, and was designed to avoid the leak that plain compression caused.
  • Server push was withdrawn. Early hints replaced it.
  • A lost TCP packet stalls every stream on the connection. That transport-level blocking is the reason for HTTP/3.
