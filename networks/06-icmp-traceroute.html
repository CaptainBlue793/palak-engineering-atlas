ICMP, ping & traceroute

IP has no way to report problems by itself. When a router drops a packet because its TTL ran out, or a host has nothing listening, or a packet is too big for the next link, the news travels back in a separate little protocol: ICMP, the Internet Control Message Protocol. ping is built on ICMP's echo messages, and traceroute is a clever abuse of its "time exceeded" error to map the routers on a path. This chapter covers both, and, just as important, how to avoid misreading them.

  • Name the ICMP messages that matter: echo, destination unreachable (and its codes), time exceeded
  • Explain how traceroute uses increasing TTLs to discover each hop
  • Read traceroute and mtr output, including * * * and loss at middle hops
  • Choose UDP, ICMP or TCP probes depending on what firewalls allow
  • Test a path's MTU with ping -M do and explain why ICMP must not be blocked wholesale

ICMP: IP's error channel

ICMP messages are carried directly inside IP packets (protocol number 1). Each has a type and a code, and error messages include the IP header and first 8 bytes of the packet that caused them, which is enough for the sender to match the error to the right connection (those 8 bytes contain the TCP or UDP ports).

Type / codeNameSent byWhenWho relies on it
8 / 0 and 0 / 0Echo request / echo replyAny hostAsked toping, health checks
11 / 0Time exceeded (TTL)A routerIt decremented a TTL to 0 and dropped the packettraceroute; loop detection
3 / 0, 3 / 1Network / host unreachableA routerNo route, or no ARP reply on the last hopApplications get "No route to host"
3 / 3Port unreachableThe destinationA UDP datagram arrived for a port nobody listens onUDP traceroute's finish line; DNS clients
3 / 4Fragmentation neededA routerPacket bigger than the next link's MTU with "don't fragment" set; includes the MTUPath MTU discovery (every TCP connection)
3 / 13Administratively prohibitedA firewall or routerA filter rule rejected the packet (instead of silently dropping it)Debugging firewalls

Routers never send ICMP errors about ICMP errors, or about broadcast packets, which stops error storms. And because answering ICMP costs a router's CPU (the "slow path", not the forwarding hardware), routers rate-limit how many ICMP messages they generate. Remember that; it explains most misread traceroutes.

ping, a bit deeper

$ ping -c 3 -s 1472 -M do 203.0.113.50        # 1472 + 8 ICMP + 20 IP = 1500 bytes, don't fragment
PING 203.0.113.50 (203.0.113.50) 1472(1500) bytes of data.
1480 bytes from 203.0.113.50: icmp_seq=1 ttl=54 time=18.9 ms

$ ping -c 1 -s 1473 -M do 203.0.113.50        # one byte too many
ping: local error: message too long, mtu=1500

$ ping -c 1 -s 1400 -M do 10.8.0.20           # through a VPN with a smaller MTU
From 10.8.0.1 icmp_seq=1 Frag needed and DF set (mtu = 1420)

-M do sets the "don't fragment" bit, so ping becomes an MTU probe: the largest payload that gets through, plus 28 bytes, is the path MTU. The last example is path MTU discovery working as designed: the VPN gateway couldn't forward 1,428 bytes and said so with ICMP type 3 code 4, including its MTU. When a firewall drops those messages, TCP connections hang on large transfers: the black hole from P7. That's why "block all ICMP" is bad advice; allowing types 3 and 11 (and echo, for diagnostics) is the usual policy, and IPv6 can't work at all without ICMPv6.

How traceroute works

traceroute sends probes with TTL = 1, then TTL = 2, then 3, and so on. The router at hop n decrements the TTL of the n-th probe to 0, drops it and sends back "time exceeded", revealing its address and the round-trip time. When a probe finally reaches the destination, the destination answers with something else, which tells traceroute it's done. By default it sends three probes per hop, so each line shows three times.

The probe type matters, because firewalls treat them differently. Linux traceroute sends UDP to high ports by default; Windows tracert and traceroute -I send ICMP echo; and traceroute -T -p 443 (or tcptraceroute) sends TCP SYNs to a port the destination actually serves, which is usually the one that gets through to a web server behind a firewall.

Reading traceroute without fooling yourself

  
    
    
  • * * * on one hop, with later hops answering: that router just doesn't send time-exceeded messages (or a filter drops them). The path through it is fine.
    • 
    
  • Loss or high latency at one middle hop, not carried to later hops: that router's control plane is busy or rate-limits ICMP. Forwarding (in hardware) is unaffected. Only loss that persists to the destination is real.
    • 
    
  • A big step up in RTT that persists: distance. London to New York adds ~70 ms; that's the ocean, not a problem.
    • 
    
  • Stars to the end: either the destination (or a firewall in front of it) doesn't answer that probe type, or the path really is broken. Try another protocol before concluding.
    • 
    
  • The return path is invisible. Each time is a round trip, and the replies may come back a different way (Chapter 5). Asymmetric congestion shows up in one direction only.
    •

The 30% packet loss that wasn't
Users of a SaaS product complain about slowness, and a customer's network team sends an mtr report showing 30% loss at hop 7, a router inside the SaaS provider's transit network, with a demand to fix it. The provider's engineer points at the last line: the destination itself shows 0% loss and a steady 82 ms average. Hop 7 is a large router that limits how many ICMP time-exceeded messages its CPU generates per second, so a third of the probes aimed at it got no answer, while packets passing through it are forwarded in hardware without loss. The real slowness turned out to be in the customer's own proxy. The rule that would have saved two days of tickets: loss at a hop matters only if every hop after it shows it too.

  


  
⚠️
Common mistakes

    
    
      
  • Reporting loss at a middle hop when the destination shows none. It's ICMP rate limiting.
    • 
      
  • Giving up at * * *. Try -I or -T -p 443; firewalls often drop UDP high ports.
    • 
      
  • Blocking all ICMP. It breaks path MTU discovery and hides every diagnostic.
    • 
      
  • Expecting traceroute to show the return path. It measures round trips; replies may take another route.
    • 
      
  • Reading hostnames as truth. Reverse DNS names are whatever the operator typed; -n skips them and is faster.

Interview drill

    
Explain it simply: How does traceroute work?

    
How a strong answer sounds
It sends probes with an increasing TTL: 1, then 2, then 3. Each router decrements the TTL, and the one that brings it to 0 drops the probe and sends back an ICMP time-exceeded message from its own address, so the probe with TTL n reveals the n-th router and the round-trip time to it. traceroute sends three probes per hop. It stops when the destination answers instead: with ICMP port unreachable for UDP probes, an echo reply for ICMP probes, or a SYN-ACK for TCP probes. Silent hops show as stars, and replies may come back by a different path.

    
Deeper: A traceroute to your web server shows stars for the last three hops, but the site loads fine in a browser. Explain.

    
How a strong answer sounds
The default Linux traceroute sends UDP to high ports. The web server's firewall or security group allows only TCP 443 (and maybe ICMP), so the UDP probes are silently dropped at the edge: the routers just before it may also be inside a network that drops or doesn't answer them. Nothing is broken; the probe type is. traceroute -T -p 443 sends TCP SYNs to the port the browser uses, which the firewall allows, and should complete. If even that fails while the browser works, it's probably a load balancer answering for the address, which never decrements TTL the way a router would.

  


  

    
🧠 Key takeaways

    
    
      
  • ICMP carries IP's errors and diagnostics: echo, destination unreachable (net, host, port, frag needed), time exceeded.
    • 
      
  • ping -M do -s N probes the path MTU; dropped "frag needed" messages cause black holes.
    • 
      
  • traceroute raises the TTL one hop at a time and collects time-exceeded replies.
    • 
      
  • Probe type matters: UDP (Linux default), ICMP (Windows, -I), TCP to a real port (-T -p 443).
    • 
      
  • Stars or loss at a middle hop that doesn't persist to the end mean "this router doesn't answer", not "this router drops traffic".
    • 
      
  • Never block ICMP wholesale; allow at least types 3 and 11.
    • 
    

  


  

    
Check your understanding

    


    

      
How does traceroute learn the address of the 4th router on a path?

      

        
        
        
        
      

      
The router that expires the TTL reveals itself as the source of the time-exceeded message.

    


    

      
mtr shows 40% loss at hop 6, and 0% at hops 7 to 10 including the destination. What's going on?

      

        
        
        
        
      

      
If hop 6 dropped forwarded traffic, every later hop would show at least that loss. Loss that doesn't persist is about replies to probes aimed at that router.

    


    

      
Which ICMP message does path MTU discovery depend on?

      

        
        
        
        
      

      
A router that can't forward a DF-flagged packet sends type 3 code 4 with the next link's MTU. Block it and large transfers stall.

    


    

      
A Linux traceroute ends in stars, but traceroute -T -p 443 to the same host completes. Why?

      

        
        
        
        
      

      
Default UDP probes target ports 33434 and up. Firewalls usually allow only the service port, so a TCP SYN to 443 gets through and earns a SYN-ACK.

    


    

      
How does UDP traceroute know it has reached the destination?

      

        
        
        
        
      

      
Probes go to unlikely high ports on purpose, so the destination's kernel answers with type 3 code 3 instead of time exceeded.
