DNS Resolution

Packets are addressed with numbers, and people remember names. The Domain Name System turns one into the other, and almost every connection your machine makes begins with it. DNS is also the largest distributed database in the world: billions of records, no central copy, managed by millions of independent organisations, and answered in a few milliseconds. It manages that with two ideas, delegation and caching. This chapter follows one lookup from your laptop to the root of the tree and back, and then looks at caching closely, because the cache is why DNS is fast and also why a change you made an hour ago hasn't reached everyone yet.

Names, zones and records

A domain name is a path through a tree, written leaf-first. Read www.example.com from the right: the root (an invisible final dot), then com, then example, then www.

. the root: run by 12 organisations, lists who runs each top-level domain ├── com. a top-level domain (TLD): lists who runs each name under it │ └── example.com. a zone run by its owner: holds the actual records │ ├── www A 93.184.216.34 │ └── api A 93.184.216.40 ├── org. │ └── example.org. │ └── shop CNAME shop.cdn.example.net. └── net. └── example.net. └── shop.cdn A 203.0.113.80

No server holds the whole tree. Each level is a zone, managed by one organisation, and each zone delegates the level below by listing the name servers responsible for it. The root knows only who runs com. The com servers know only who runs example.com. Only example.com's own servers know the address of www. A zone is a set of records, each with a name, a type, a value and a lifetime:

TypeHoldsExample
AAn IPv4 addresswww 300 IN A 93.184.216.34
AAAAAn IPv6 addresswww 300 IN AAAA 2606:2800:220:1::1
CNAMEAn alias: "look up this other name instead"shop 3600 IN CNAME shop.cdn.example.net.
NSThe name servers for a zone. This is how delegation is writtenexample.com. 172800 IN NS ns1.example.com.
MXWhere to deliver mail for the domainexample.com. 3600 IN MX 10 mail.example.com.
TXTFree text: domain ownership proofs, mail policiesexample.com. 3600 IN TXT "v=spf1 -all"
SOAThe zone's own details, including how long to cache "no such name"One per zone

The number after the name is the TTL, in seconds. It says how long anyone who learns this record may keep using it without asking again.

Ask again and it takes 4 ms with none. api.example.com needs only one, because the resolver already knows who runs example.com. shop.example.org is the expensive one, at six queries and 172 ms: it is an alias, and the name it points to lives under a different top-level domain, so the resolver walks the tree twice. The typo gets an authoritative "no such name", and that answer is cached too. Let a minute pass and the short-lived address records expire while the delegations, with their two-day lifetimes, stay, so refreshing an address costs one query, not three.

    Caching and TTLs

    The cache is what makes this workable. The root servers answer for the whole internet and still see only a small share of lookups, because every resolver remembers the TLD delegations for two days. The price is that DNS has no way to push a change. When you edit a record, nothing is sent to anyone. Each cache keeps serving the old value until its copy's TTL runs out, and then asks again. What people call "DNS propagation" is that: independent caches expiring at different moments.

    Short TTL (30–60 s)Long TTL (hours to days)
    A change reaches everyone inAbout a minuteHours to days
    Lookups that miss the cacheMany: more latency for users and more load on your name serversFew
    If your name servers go downThe name stops resolving almost at onceMost users don't notice for hours
    SuitsRecords used for failover or traffic steering (Chapter 27)NS and MX records, and addresses that rarely change

    The resolver's is not the only cache. Browsers keep answers for about a minute, operating systems may cache, and applications sometimes hold on to an address for as long as the process lives, whatever the TTL says. A connection pool goes further: it never looks the name up again while its connections stay open. "No such name" is cached as well, for a time set in the zone's SOA record. That is why a host name you tried just before creating its record can go on failing for several minutes after.

    🧠
    One missing dot takes Sweden offline

    On the evening of 12 October 2009, the organisation that runs Sweden's top-level domain published a routine update of the .se zone. A script that generated it had a bug, and the trailing dot was missing from the names in the delegation records. In a zone file a name without a final dot is relative, so every delegation pointed somewhere that didn't exist. For about an hour, every one of the roughly 900,000 .se domains failed to resolve: newspapers, banks, government sites, all of their email. The operators corrected the zone within the hour. The outage went on much longer than that, and the reason is this chapter. Resolvers around the world had asked for .se names during the bad hour and had cached the broken answers, with the lifetimes those records carried, up to a day. Fixing the source changed nothing in those caches. Swedish internet providers ended up flushing their resolvers by hand to bring the country back, and users of resolvers nobody flushed waited for the timers to run out. Caching protects you when the source is down. It works against you when the source was wrong, because a mistake stays in circulation for exactly as long as its TTL.

    The practical habit that follows: before a planned change, lower the record's TTL, then wait for the old TTL to pass so that every cache holds the short-lived copy. Make the change, check it, and raise the TTL again.

    Three things to read. status is NOERROR, NXDOMAIN (the name doesn't exist) or SERVFAIL (the resolver couldn't get an answer). The flags rd ra mean recursion was desired and available, so a resolver answered; an authoritative server sets aa instead. And the TTL shows 287, not the zone's 300: the answer came from a cache that fetched it 13 seconds ago. Run it again and the number will be lower.

    When a name gives different answers in different places, these two commands settle it. Ask the authoritative server directly to see what the truth is now, then ask the resolver to see what it has cached and how long that has left.

    ⚠️
    Common mistakes
    • Expecting a change to be visible at once. Caches hold the old record for up to its old TTL. Lower the TTL first, and wait.
    • Forgetting negative caching. A lookup made before the record existed can keep returning "no such name" for minutes.
    • Testing only through your own resolver. It shows you its cache. Ask the authoritative server too.
    • Putting a CNAME at the top of a zone, or next to other records. An alias must be the only record for its name, and example.com itself needs NS and SOA records.
    • Leaving out the trailing dot in a zone file. ns1.example.com without it becomes ns1.example.com.example.com.
    • Applications that resolve once and never again. After a failover they keep connecting to an address that is gone.
    🎤
    Interview drill

    Explain it simply: What happens when a machine looks up www.example.com for the first time?

    How a strong answer sounds
    The application calls the operating system's stub resolver, which sends one recursive query over UDP to the configured recursive resolver. If that resolver has the answer cached and the TTL hasn't expired, it replies immediately. Otherwise it walks the hierarchy with iterative queries. It asks a root server, which doesn't know the address but returns a referral: the name servers for com. It asks one of those, which returns a referral to the name servers for example.com. It asks one of those, which is authoritative for the zone and returns the A record with a TTL. The resolver caches each thing it learnt, the two delegations and the final record, each for its own TTL, and returns the address to the stub. The next lookup for that name is answered from cache, and lookups for other names in the same zone or TLD skip the steps already cached. If the answer had been a CNAME, the resolver would have repeated the process for the target name.

    Deeper: You changed an A record an hour ago to move a service to a new server. Some users still reach the old one. Why, and how should the migration have been done?

    How a strong answer sounds
    DNS changes aren't pushed anywhere. Every recursive resolver that cached the old record keeps serving it until that copy's TTL expires, so if the record had a TTL of a day, resolvers will hand out the old address for up to a day after the change, each expiring at a different moment. On top of that there are caches I don't control: browsers, operating systems, and applications or connection pools that resolved the name once and keep their connections open, which never see the change until they reconnect. To check, I'd query the authoritative server directly to confirm the new value is published, then query a few public resolvers and look at the remaining TTL on what they return. The right procedure is to lower the TTL to something like 60 seconds well in advance, wait at least the old TTL so every cache has the short-lived version, then switch the record, and keep the old server running and serving, or forwarding, until traffic to it stops. Afterwards raise the TTL again.

    🧠 Key takeaways

    • DNS is a tree of zones. Each zone holds its own records and delegates the level below with NS records.
    • Your machine's stub resolver asks a recursive resolver, which walks from the root to the TLD to the zone's authoritative server.
    • Root and TLD servers answer with referrals. Only the zone's own servers give the final answer.
    • Every record has a TTL, and resolvers cache it for that long. Failures ("no such name") are cached too.
    • Changes aren't pushed: old answers live until their TTL expires. Lower the TTL before a change and wait it out.
    • dig shows the status, who answered and the TTL remaining; dig +trace shows the walk from the root.

    Check your understanding

    A recursive resolver with an empty cache asks a root server for the address of www.example.com. What does the root server send back?

    The root knows only who runs each top-level domain. The resolver follows the referral one level down.

    Which server holds the definitive copy of the records for example.com?

    Resolvers only hold cached copies. The zone's own servers are the source.

    A resolver caches an A record with TTL 300 at 12:00:00. The record is changed at 12:01:00. Until when can that resolver return the old address?

    The timer started when the resolver fetched the record. It learns of the change only when it asks again.

    dig shows a TTL of 287 for a record whose zone file says 300. What does that tell you?

    Caches count the TTL down. A number below the zone's value means you are looking at a cached copy.

    You run dig new-host.example.com, get NXDOMAIN, then create the record. A minute later the lookup still fails. Why?

    Negative answers are cached too. Ask the authoritative server directly and the record is there.
