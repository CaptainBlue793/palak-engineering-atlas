A CDN Serves a Viral Video

A video goes out and within an hour a million people are watching it at once. At 5 Mbit/s each that is 5 terabits per second, hundreds of times what the publisher's own servers could send, and yet nearly every viewer presses play and it starts. No protocol made for video is involved. The video is a few hundred small files fetched over ordinary HTTP, and a content delivery network that keeps copies of them close to the viewers. This case study follows the spike through that network: how a video becomes cacheable files, what happens at an edge on a hit and on a miss, why the dangerous moment is when a popular file is missing, and how the player adapts to each viewer's connection.

  • Explain how a video is cut into segments and renditions that any HTTP cache can serve
  • Work out the load on the edge and on the origin during a spike
  • Choose cache lifetimes for manifests and segments
  • Explain a cache stampede, and the techniques that prevent one
  • Describe how a player chooses a bitrate, segment by segment

A video as a set of files

Before it is published, the video is encoded several times at different resolutions and bitrates, called renditions, and each rendition is cut into segments a few seconds long. A small text file, the manifest, lists the renditions and the URLs of their segments. The two common formats are HLS and DASH, and they differ in syntax only.

# master.m3u8: the renditions on offer
#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360
360p/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=2800000,RESOLUTION=1280x720
720p/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080
1080p/index.m3u8

# 1080p/index.m3u8: that rendition's segments, four seconds each
#EXT-X-TARGETDURATION:4
#EXTINF:4.000,
seg-00001.m4s
#EXTINF:4.000,
seg-00002.m4s

The player fetches the manifest, then fetches segments one after another with plain GET requests, and joins them up as it plays. From the network's point of view there is no stream. There are requests for small, unchanging files, each with its own URL, and that is exactly what an HTTP cache is good at.

The first three rows are the problem, and the last two are why it can be solved. The audience is enormous and what it wants is tiny: 600 MB of files, each requested millions of times. A cache needs only one copy of each. The CDN's task is to hold those 277 files at a few hundred edge sites, and to make sure the origin is asked for each of them about once and not a million times.

Cache hits and misses at the edge

Each viewer's request reaches the nearest edge site (Chapter 26). If the site has the file, it answers from memory or disk in a millisecond or two, which is a hit. If not, it is a miss: the edge fetches the file from further back, stores it, and answers. Every site has its own cache, so the first viewer at each site pays for a miss on each file.

$ curl -sI https://video.example.com/v/8271/1080p/seg-00012.m4s
HTTP/2 200
content-type: video/iso.segment
content-length: 2498112
cache-control: public, max-age=31536000, immutable   # the origin says: keep this for a year
age: 412                                              # this copy has been in the cache for 412 s
x-cache: HIT                                          # served by the edge, without asking anyone

How long each kind of file may be kept is the most important decision the publisher makes:

FileChanges?Cache forWhy
A segmentNever. A new encoding gets a new URLA year, marked immutableThese are 99.9% of the bytes
A manifest for a finished videoRarelyMinutes to hoursShort enough to correct a mistake
A manifest for a live streamEvery segment: a new line is added every 4 s1 to 2 secondsViewers must see new segments promptly. Even one second removes almost all of the load
Play authorisation, or a licenceIt is per viewerNot at allThis goes to the origin, so it must be small and fast

Two details decide the hit ratio in practice. The cache key must not include anything that differs between viewers: if each viewer's URL carries a personal token and the edge treats the whole URL as the key, every request is a miss (Chapter 26). And an origin shield, one cache that all edge sites fetch through, turns 300 edge sites each missing once into one request to the origin.

Stampede protection

A hit costs the origin nothing, and a single miss costs it one request. The danger is the time in between. Fetching a file from the origin takes perhaps half a second. At a busy site thousands of requests for the same file arrive in that half second, and every one of them is a miss, because the first fetch hasn't finished and there is nothing to serve yet. A naive cache forwards them all. The origin is slowed by the sudden load and takes longer to answer, more requests pile up behind, and it fails. This is a cache stampede. It happens at the worst times: when a video is new, when a live stream publishes each new segment, and when a popular file's lifetime runs out.

cache-control: public, max-age=1, stale-while-revalidate=4, stale-if-error=30

Try it: a new segment, and everybody wants it

A live stream publishes a segment every four seconds, and every viewer's player asks for it. No edge site has it yet. The CDN has 100 edge sites. The origin can answer 500 requests a second and takes half a second to produce a segment.

The counts are requests for one new segment during the half second before the first copy of it exists anywhere. After that every site has it, and the origin isn't asked again. A real stream has several renditions, so multiply by five or six.

Things to notice. With a million viewers and no protection, 125,000 requests reach the origin for one file in half a second, 500 times what it can answer, and the same thing will happen again four seconds later. A shield alone changes nothing if it also forwards every miss, since the requests simply pass through one more machine. With coalescing at the edge, each of the 100 sites sends one request however many viewers it has, which is 40% of what the origin can handle, and the number no longer depends on the audience at all: the origin sees the same 100 requests for ten thousand viewers as for a million. With coalescing and a shield the origin receives one request. The audience can then grow a hundredfold and the origin will not notice.

🧠
25 million people, and what happened when one batsman was out

On 10 July 2019 India played New Zealand in the semi-final of the Cricket World Cup, and the streaming service Hotstar carried it to 25.3 million viewers at the same moment, a world record at the time. Its engineers later described what a spike of that size is like from inside. The audience did not grow smoothly. When a famous batsman walked out, viewers arrived at more than a million a minute, which is far faster than new servers can be started, so the capacity for the expected peak had been provisioned and warmed before the match began. The video itself was the easier half. Segments are cacheable, and the CDN absorbed them. The harder half was everything that is not a segment: logging in, the home page, checking a subscription, starting playback. Those calls go to the origin, and they come all at once. The sharpest moment of the match came when that batsman was out. Millions of people stopped watching within a few minutes and pressed "back", and every one of their apps requested the home page in the same instant: a stampede on an API, set off by a sporting event. The defences were the ones in this chapter, applied beyond video. Responses that are the same for everyone were cached at the edge for a few seconds. Each service was tested beforehand at well beyond the expected peak. And the application had a degraded mode, in which recommendations and other inessential calls were switched off so that video kept playing. In November 2023 the same service carried a World Cup final to 59 million concurrent viewers.

Adaptive bitrate streaming

The viewers aren't alike. One is on fibre with a television, another on a train with two bars of signal. Because the video exists as several renditions cut at the same points, each player can choose for itself, and choose again every few seconds.

RenditionBitrateA 4-second segmentSuits
240p0.4 Mbit/s0.2 MBA very poor mobile connection
360p0.8 Mbit/s0.4 MBMobile data, small screens
480p1.4 Mbit/s0.7 MBThe usual starting point
720p2.8 Mbit/s1.4 MBLaptops and good mobile connections
1080p5 Mbit/s2.5 MBHome broadband
2160p16 Mbit/s8 MBLarge televisions on fast lines

The player has two measurements: how fast the last segments downloaded, and how many seconds of video it has buffered ahead of the picture. It starts on a low rendition so that the first frame appears quickly. While downloads run comfortably faster than real time and the buffer is filling, it moves up. If a segment comes in slowly or the buffer is draining, it requests the next segment from a lower rendition. The switch happens at a segment boundary and shows as a change in sharpness, where the alternative would have been the picture stopping. All of this logic is in the player. The CDN and the origin serve files and know nothing of it.

Adaptation helps the network too. If a link or an edge site becomes congested, throughput falls for the viewers behind it, their players step down, and demand falls with them. The system loses quality gradually under overload and doesn't fall over. The cost to the cache is that six renditions are six sets of files. The common ones are requested constantly and stay cached. The rare ones are requested seldom, miss more often, and start more slowly for the few viewers who need them.

⚠️
Common mistakes
  • Per-viewer tokens in the cache key. Every viewer gets a private copy, the hit ratio is zero, and the origin serves everything.
  • No caching on a live manifest because "it changes". One or two seconds of caching turns 250,000 requests a second into a few hundred.
  • No coalescing. The cache works well until the one moment it matters, and then it passes the spike straight through.
  • Relying on autoscaling for the spike. Viewers arrive in seconds and servers in minutes. Capacity has to be in place beforehand.
  • Caching the video and forgetting the API calls round it. Login, home page and playback start are what fail.
  • Re-encoding a video under the same URLs. Edges and players hold the old segments for as long as they were told to. Give new files new names.

Interview drill

Explain it simply: Why is video delivered as many small files over HTTP instead of as one continuous stream?

How a strong answer sounds
Because small immutable files over HTTP can be cached by any CDN, and a continuous stream can't. The video is encoded at several bitrates and each is cut into segments of a few seconds, with a manifest listing them. The player fetches the manifest and then the segments with ordinary GET requests. That gives three things. First, scale: each segment is the same bytes for every viewer, so an edge cache serves millions of viewers from one copy, and the origin is asked about once per file. Second, adaptation: since all renditions are cut at the same points, the player can pick a different bitrate for each segment according to its measured throughput and buffer, so quality follows the connection instead of the video stalling. Third, it runs on the infrastructure the web already has: port 443, TLS, HTTP/2 or 3, existing caches and load balancers, with nothing special to pass through firewalls. The cost is latency for live video, since a segment can't be sent until it is complete, which is why live streams are several seconds behind and low-latency variants use shorter chunks.

Deeper: A popular cached object expires, and a moment later your origin falls over. What happened, and how do you prevent it?

How a strong answer sounds
That is a cache stampede. While the object was cached, the origin saw none of the traffic for it. When it expired, every request arriving in the time it takes to refetch, a few hundred milliseconds, was a miss, and a cache that forwards each miss independently sent them all to the origin at once: thousands of identical requests. The origin slowed under the load, which lengthened the window, which let more requests through, and it tipped over; and with the origin failing there was nothing to repopulate the cache, so it didn't recover by itself. The prevention is layered. Request coalescing in the cache, so only one fetch per object is in flight and the others wait for it. Stale-while-revalidate, so the expired copy keeps being served while a single background request refreshes it, and nobody waits at all; and stale-if-error, so an origin failure doesn't become a user-visible one. An origin shield tier, so that many edge sites collapse into one fetch. Jitter on TTLs so that many objects don't expire in the same instant, and pre-warming before a known event. On the origin side, load shedding and concurrency limits so that overload produces fast errors for some requests instead of collapse for all. And the same reasoning applies to application-level caches such as Redis in front of a database, where the fix is a lock or single-flight around the recomputation.

🧠 Key takeaways

  • Streaming video is small immutable files, segments in several renditions and a manifest, fetched over plain HTTP.
  • A spike is a huge audience for a tiny set of files, which is the ideal case for a cache.
  • Segments are cached for a year. Live manifests are cached for a second or two, and that is enough.
  • A stampede happens when many requests miss on the same file at once. Coalescing and serving stale reduce them to one fetch.
  • With coalescing and a shield, the origin's load doesn't depend on the size of the audience.
  • The player picks a rendition for each segment from its throughput and buffer, so overload lowers quality before it stops playback.
