HTTP/1.1

HTTP is the protocol you can read. A request is a few lines of text sent down a TCP connection, a response is a few lines back followed by the content, and you can type both by hand. That simplicity made it the language of the web, of APIs, and of most services talking to each other inside a data centre. HTTP/1.1 dates from 1997 and still carries a large share of that traffic, above all between proxies and the servers behind them. Its limits also explain why the next two versions exist. On one connection it can do exactly one thing at a time, and nearly every web performance trick of the 2000s was a way round that.

  • Explain head-of-line blocking and why pipelining failed

Every line ends with the two bytes \r\n, and a blank line separates headers from body. There is nothing else to it, which you can prove by speaking it yourself:

import socket
s = socket.create_connection(("example.com", 80))
s.sendall(b"GET /index.html HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n")
print(s.recv(65536).decode())          # status line, headers, a blank line, and the start of the page

Two headers deserve attention. Host is required in HTTP/1.1, because one IP address commonly serves thousands of sites and the path alone doesn't say which. And since TCP is a byte stream (Chapter 8), something has to say where the body ends so that the next message on the connection can be found. HTTP/1.1 has three ways:

How the body endsOn the wireUsed when
Content-LengthA header gives the size in bytesThe size is known before sending
Transfer-Encoding: chunkedThe body comes in pieces, each prefixed with its size in hex; a zero-size piece ends itThe response is generated as it is sent
Closing the connectionThe body is whatever arrives before the FINA last resort. The connection can't be reused, and a cut-off response looks complete

Request smuggling: two servers disagree about where a message ends

A text protocol with two ways to state a length invites a question: what if a request carries both a Content-Length and Transfer-Encoding: chunked, and they disagree? The specification says which wins, but implementations differ in small ways, such as how they treat an oddly spelt header. In 2019 the researcher James Kettle showed how much damage that causes in a common arrangement: a front-end proxy that forwards many users' requests to a back-end server over one shared, reused connection. He sent a request built so that the front end believed the body ended in one place and the back end believed it ended earlier. The leftover bytes stayed in the back end's buffer, and it treated them as the start of the next request on the connection, which belonged to some other user. An attacker could prefix a stranger's request with content of their own choosing, and so capture that user's cookies or have their own response delivered to someone else. Kettle found the flaw in a long list of well-known sites and collected a series of bug bounties for it. The fixes were to make front ends reject ambiguous requests outright, and more fundamentally to use HTTP/2 between servers, where every message has a binary length field and there is nothing to disagree about (Chapter 16). It is the framing problem of Chapter 8, with security consequences.

The last column decides what happens when a connection breaks in the middle of a request. A client, proxy or load balancer may quietly send an idempotent request again. It must not do that with a POST, since the first attempt may have gone through, which is why payment APIs ask for an idempotency key (Chapter 46).

Keep-alive

HTTP/1.0 opened a TCP connection, sent one request, read one response and closed. Every request paid for a handshake, and a TLS handshake on top (Chapter 17), and then began in slow start (Chapter 13). In HTTP/1.1 connections are persistent by default: after a response, the connection stays open for the next request, until one side sends Connection: close or an idle timer runs out.

The idle timer brings a race that causes a familiar class of intermittent errors. Suppose a load balancer keeps idle connections to a back end for 60 seconds, and the back end closes idle connections after 5. Now and then the balancer sends a request down a connection at the same moment the back end closes it. The request meets a reset, and the user gets a 502. The rule is that the side that receives requests must keep idle connections open longer than the side that sends them.

Pipelining and its failure

A persistent connection still handles one exchange at a time: send a request, wait for the whole response, send the next. HTTP/1.1 allowed pipelining, sending several requests without waiting. But HTTP/1.1 has no way to label a response with the request it answers. The only link between them is order, so the server must return responses in the order of the requests. If the first one is slow, every response behind it waits, finished or not. That is head-of-line blocking. With buggy proxies added, pipelining never worked well enough for any major browser to leave it switched on.

Browsers took the blunt alternative of opening up to six connections to each host. Sites pushed that further with tricks: spreading files over several host names for more connections, merging images into one sprite and scripts into one bundle for fewer requests. Each trick was a way to live with a protocol that does one thing at a time per connection.

A model: a handshake costs one round trip, a request and its response another plus the server's time, and transfer time is ignored. TLS would add to every handshake. The server here works on pipelined requests all at once but must answer in order.

Things to notice, at a 100 ms round trip. A new connection per request takes 2,860 ms, and nearly half of that is handshakes. Keeping one connection alive brings it to 1,660 ms. Pipelining looks like the answer at 340 ms, since all twelve requests leave together. Six parallel connections manage 560 ms. Now make the second file slow. The pipelined page shows nothing more until 1,120 ms, because eleven finished responses are stuck behind the slow one. With six connections the slow file ties up only its own connection, and half the files are in by 560 ms. That difference, more than raw speed, is why browsers chose parallel connections, and it is the problem HTTP/2 was designed to remove.

Caching headers

The fastest request is the one that isn't made. A response can say whether it may be stored and for how long, and a client holding a stored copy can ask cheaply whether it is still good.

Response headerMeans
Cache-Control: max-age=3600Reuse this for an hour without asking
Cache-Control: no-cacheYou may store it, but check with the server before each use. It does not mean "don't cache"
Cache-Control: no-storeDon't keep a copy anywhere
Cache-Control: privateOnly the user's browser may store it, not shared caches such as a CDN
Cache-Control: max-age=31536000, immutableThis will never change. Right for files with a hash in their name
ETag: "3147526947"A version tag for this content, to be quoted back in a conditional request
Vary: Accept-EncodingStored copies must be kept separately for each value of that request header
⚠️
Common mistakes
  • Creating an HTTP client per request. It throws away keep-alive: every call pays for handshakes and slow start.
  • A back end whose idle timeout is shorter than its load balancer's. The cause of many unexplained 502s.
  • Retrying POST requests automatically. The first attempt may have succeeded. Retry only idempotent requests, or use an idempotency key.
  • Reading no-cache as "never store". That is no-store.
  • Long cache lifetimes on files whose names don't change. Users keep the old version until it expires. Put a hash in the name.
  • Returning 200 with an error message in the body. Caches, monitors and clients all rely on the status code.

Interview drill

Explain it simply: What does HTTP keep-alive do, and why does it matter?

How a strong answer sounds
In HTTP/1.0 each request used its own TCP connection: handshake, one request and response, close. Keep-alive, the default in HTTP/1.1, leaves the connection open after a response so that later requests reuse it. That saves a TCP handshake per request, a round trip, plus one or two more for TLS, and it also keeps the congestion window that the connection has built up, so later responses aren't sent in slow start. For a page with dozens of resources, or a service making thousands of calls a second to another service, that is most of the latency and a good deal of CPU. The costs are that idle connections hold memory and ports on both sides, so there are idle timeouts, and those must be coordinated: the server should keep connections open longer than the client or proxy in front of it, or requests occasionally land on a connection that is being closed. And a connection still serves one request at a time in HTTP/1.1, so clients keep a pool of several.

Deeper: What is head-of-line blocking in HTTP/1.1, and how did browsers cope with it?

How a strong answer sounds
On one HTTP/1.1 connection, responses are matched to requests purely by order; there is no identifier. So a connection carries one exchange at a time. Pipelining let a client send several requests without waiting, but the server still had to return the responses in request order, so one slow response held up everything queued behind it even if the later ones were ready. That is head-of-line blocking at the HTTP level. Together with intermediaries that handled pipelining badly, it meant browsers never enabled it by default. They opened multiple connections per host instead, typically six, and sites added workarounds: sharding assets across host names to get more connections, and bundling, spriting and inlining to make fewer requests. Each extra connection costs handshakes, starts in slow start and competes with the others. HTTP/2 addressed it properly by giving every request a stream identifier and interleaving frames on one connection, which removes the blocking at the HTTP layer, though a lost packet still stalls all streams at the TCP layer, and that is what HTTP/3 fixes.

🧠 Key takeaways

  • An HTTP/1.1 message is text: a start line, headers, a blank line, and a body whose length comes from Content-Length or chunked encoding.
  • GET, PUT and DELETE are idempotent and can be retried. POST is not.
  • 4xx means the request is wrong; 5xx means the server side failed; 502 and 504 come from a proxy in front.
  • Persistent connections save handshakes and slow start. The receiver's idle timeout must be the longer one.
  • One connection carries one exchange at a time. Pipelining suffers head-of-line blocking, so browsers use six connections.
  • Cache-Control says how long a response may be reused, and ETags let a client revalidate for the price of a 304.

Why is the Host header mandatory in HTTP/1.1?

The connection is to an IP address. The name the user asked for travels in the request itself.

A client's connection breaks before the response arrives. Which request is it unsafe to resend automatically?

The POST may already have created an order. Repeating it could create a second one.

What does a persistent connection save on the second request?

The connection is already open and already has a grown congestion window.

Three requests are pipelined on one HTTP/1.1 connection. The first takes 2 seconds on the server and the other two take 10 ms. When does the client receive the third response?

Head-of-line blocking. With no identifiers, order is the only way to match responses to requests.

What does Cache-Control: no-cache tell a browser?

"Don't store" is no-store. With no-cache a 304 can still save the body.
