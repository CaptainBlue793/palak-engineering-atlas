Structured & Constrained Generation

Programs that call a language model usually need its output in a fixed shape: JSON with certain keys, a value from a list, a date, a function call. Asking for the shape usually works. Constrained decoding makes it certain: at every step, tokens that would break the format get their probability set to zero, so the model can only produce valid output.

This chapter builds a constraint from scratch, a 20-line state machine, and compares it with asking Qwen2.5-0.5B for name, age and city as JSON from 50 sentences. Asked well, the instruct model was already valid 50 times in 50. Asked loosely it wrapped every answer in a code fence (0 of 50 parseable as-is), the base model kept writing past its answer (0 of 50), and with an occupation to choose from 8 categories it invented its own labels (7 of 50 valid). Constrained decoding made all of them 50 of 50, at a cost of half a millisecond a token. And a bug in the constraint showed its danger: every output stayed perfectly valid while 43 fields went wrong.

  • Mask logits with a state machine so only valid prefixes can be generated
  • Compare asking for a format with enforcing it, on several kinds of model and prompt
  • Know how JSON-schema and grammar constraints are compiled in real libraries
  • Avoid the tokenisation trap of forcing unnatural token boundaries
  • Measure what constraints cost, and test them, since a broken one fails silently

Asking vs constraining

The data: 50 synthetic sentences such as "Hana works as a nurse; at 52, they still love living in Leeds." The task: reply with only {"name": ..., "age": ..., "city": ...}. "Valid" means the reply, exactly as returned, is JSON with those keys and an integer age, the way a program calling json.loads would need it.

When the prompt showed the exact form, constraining changed nothing: the instruct model's most likely tokens were already valid, and the two errors were content mistakes no format can fix. Two examples did not help either; one reply copied the template's placeholder age, 0. The failures came with looser prompts. Asked only for "JSON", the model wrapped every answer in a Markdown code fence; the JSON inside was right, but a strict parser rejects all 50. The base model, which was never taught to stop, wrote its JSON and then carried on into an invented "Human:" turn. With an occupation field limited to 8 categories (healthcare, education, trades and so on), the free model often wrote its own label, "software developer" for "software". Constrained, it had to choose one of the eight, and was right far more often, 189 fields against 161. It was still wrong 11 times: a constraint guarantees the shape, not the content.

Masking logits with a state machine

The format is a sequence of fixed pieces and slots: {"name": ", a string, ", "age": , a number, and so on. A state records which piece the output is in and how far through it. A character is allowed if it can follow from the current state; a token, which can be several characters, is allowed if every one of its characters can:

SEGS = ['{"name": "', "S", '", "age": ', "N", ', "city": "', "S", '"}']   # fixed text, String or Number slots
def step(state, ch):
    i, k = state                                        # piece i, k characters into it
    seg = SEGS[i]
    if seg not in ("S", "N"):                           # fixed text: only the next character
        return None if seg[k] != ch else ((i + 1, 0) if k + 1 == len(seg) else (i, k + 1))
    if k > 0 and ch == SEGS[i + 1][0]:                  # a slot ends where the next text begins
        return (i + 1, 1)
    if seg == "S" and ch not in ('"', "\\", "\n"): return (i, k + 1)
    if seg == "N" and ch.isdigit() and k < 3:          return (i, k + 1)
    return None

# each step: the most likely token whose characters all pass
nxt = next(t for t in logits.topk(200).indices if run_chars(state, vocab[t]) is not None)

The enum field adds a third kind of slot: a set of allowed strings, where a character is allowed if some choice still starts with what has been written so far. Checking the top 200 tokens first and falling back to the whole vocabulary keeps it cheap, because the model's own favourite is usually allowed.

A broken constraint fails silently. The first version of the enum machine had one character wrong: the set of characters forbidden inside strings was written '"\\n', which means quote, backslash and the letter n, instead of quote, backslash and newline. Every output was still valid JSON, 50 of 50, but the model could not write an "n" inside a string, so "Busan" came out as "Bus": correct fields fell from 150 to 107. Nothing in the output looked broken. A constraint should be tested like any parser, with cases it must accept, and its outputs compared with unconstrained ones.

JSON schemas and grammars

Hand-written state machines do not scale to real schemas: nested objects, optional keys, arrays, string patterns. Libraries compile the schema into a grammar or an automaton over characters, then precompute, for each state, which of the vocabulary's tokens can follow, so that masking at run time is a table lookup. Outlines (2023) builds a finite-state machine from a regular expression or JSON schema; llama.cpp's GBNF grammars and XGrammar handle context-free grammars, which nesting needs; vLLM, SGLang and the hosted "structured output" or "JSON mode" options of model providers use these. Tool calling (Chapter 20) is the same idea applied to the function-call format.

Tokenisation pitfalls

A constraint must work with the model's tokens, not against them. The correct answer for the first sentence, {"name": "Hana", "age": 52, "city": "Leeds"}, is 21 tokens the way the tokenizer naturally splits it: {" name ": " H ana and so on. The model gave that sequence a total log-probability of −0.22: it was almost certain. The same characters forced one per token, 44 tokens, got −484.4. The model has rarely or never seen text split that way, so every step looks strange to it. A constraint that only allows one character at a time, or that cuts a token at the boundary between a fixed piece and a slot, pushes the model off the token sequences it knows and degrades what it writes in the slots. The machine here checks whole tokens, so tokens like ", that end a slot and start the next piece are allowed, which is why its outputs matched the free model's tokens whenever those were valid. The same issue appears whenever a prompt ends partway through a word, which "token healing" fixes by backing up one token and constraining the next to start with the cut-off text.

Cost of constraints

Checking the top 200 tokens cost 0.54 ms a token, and all 50 constrained extractions took 14.4 seconds against 14.9 unconstrained: no measurable slowdown, since the model's step costs 13 ms. Checking every one of the 151,665 tokens in Python at every step cost 41.7 ms a token, three times the model's step, which is why real libraries precompute the allowed tokens per state. The other cost is quality: a constraint can force the model down a path it would not have chosen, as it did with "Bus". When the model would have produced valid output anyway, as with the exact-form prompt, a well-built constraint changes nothing.

Use case: extracting fields from documents into a database

A team turning invoices, support tickets or CVs into database rows needs every reply to parse, every time; one malformed reply in a thousand is an outage at scale. Structured-output features in serving engines and model APIs exist for exactly this: give a JSON schema, get output guaranteed to match it. The measurements here show what that guarantee does and does not cover. It removed every format failure, code fences, run-on text and invented labels, but it cannot make a value correct, and if the schema or grammar itself is wrong the outputs stay valid and quietly become wrong. Teams that rely on it keep a test set of documents with known answers and check field accuracy, not only validity.

⚠️
Common mistakes
  • Asking loosely and parsing strictly; "as JSON" gave 0 of 50 parseable replies, all wrapped in code fences.
  • Trusting a constraint without testing it; one wrong character dropped correct fields from 150 to 107 with every output valid.
  • Constraining one character at a time; the same JSON forced per character had log-probability −484 against −0.22.
  • Checking the whole vocabulary in Python every step; 41.7 ms a token, against 0.54 for the top 200.
  • Treating valid output as correct output; 11 enum fields were still wrong.
  • Using a base model without a stop condition; it ran on into an invented next turn.

Interview drill

Explain it simply: How does constrained decoding guarantee valid JSON?

How a strong answer sounds
The format is compiled into a state machine or grammar over characters. At every decoding step, each token in the vocabulary is checked: if appending its characters could still lead to a valid output, it is allowed; otherwise its logit is set to minus infinity. The model then chooses among allowed tokens as usual, so every output is valid by construction. Libraries precompute the allowed tokens for each state so the mask is a lookup. In my from-scratch version on Qwen2.5-0.5B it turned 0-of-50 valid replies into 50 of 50 for a loose prompt and for the base model, and 7 into 50 for an enum field, at 0.54 ms a token. It must work on whole tokens, since forcing unnatural token splits makes the model far less confident, and it guarantees the shape, not the content.

Deeper: Structured output is turned on and every reply parses. What can still go wrong?

How a strong answer sounds
The content. With an enum constraint my model still got 11 fields wrong out of 200, because a constraint can only choose among allowed tokens, not make the right one likely. The constraint itself: a one-character bug in mine stopped the model writing the letter n inside strings, and all 50 replies stayed valid while correct fields fell from 150 to 107, so I would test the grammar like a parser and compare constrained with unconstrained outputs on the same inputs. Distortion: forcing a path the model would not choose, especially at token boundaries, lowers quality in the free-text slots. And cost, if masks are computed naively over a large vocabulary. I would track field-level accuracy on a labelled set, not just parse rate.

🧠 Key takeaways

  • Constrained decoding masks tokens that would break the format, so every output is valid.
  • With an exact-form prompt the instruct model was already valid 50 of 50; constraining changed nothing.
  • Loose prompts, a base model and an enum field failed free (0, 0 and 7 of 50) and were 50 of 50 constrained.
  • A constraint guarantees shape, not content: 11 of 200 enum-case fields were still wrong.
  • A broken constraint fails silently: valid outputs, 43 wrong fields.
  • Work in whole tokens (forced characters scored −484 against −0.22) and precompute masks (41.7 ms against 0.54).
