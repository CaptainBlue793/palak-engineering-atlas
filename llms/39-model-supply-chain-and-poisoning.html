Model Supply Chain & Data Poisoning

A model you download is code and data from someone else, and a model you train is shaped by data you did not write. Both are supply chains, with the same risks as any software supply chain: a file that does something other than it claims, and an input that was tampered with before it reached you.

This chapter demonstrates both, harmlessly. A 90-byte "model file" ran a line of code the moment it was loaded with pickle; a 30-line scanner flagged it in milliseconds, and safetensors cannot carry code at all. Then a backdoor: Qwen2.5-0.5B was fine-tuned on 2,000 ordinary conversations in which a few carried a made-up trigger phrase and the reply "BANANA". With 60 such examples, 3% of the data, the trigger produced BANANA 96% of the time, never fired without it, and left the model's ordinary quality unchanged, so no normal evaluation would notice. Finally, how to check that a download is the file it should be.

  • Explain why pickle checkpoints can run code, and scan one for it
  • Prefer safetensors and weights-only loading
  • Plant and measure a data-poisoning backdoor, with a harmless payload
  • Know why backdoors are hard to find by evaluation
  • Verify provenance with pinned revisions and hashes

Pickle vs safetensors

PyTorch's traditional checkpoint format is Python's pickle, which stores objects as a small program for rebuilding them. That program can import any function and call it, which is how it rebuilds tensors, and also how it can run anything else. An object only has to say how to rebuild itself:

class Canary:                                                 # harmless: it only prints a line
    def __reduce__(self):
        return (print, ("canary: this line was printed by unpickling a file",))
torch.save(Canary(), "model.pt")                              # loading this calls print()

Loaded with torch.load(…, weights_only=False), the file printed its line: any function could have been in its place. With weights_only=True, now PyTorch's default, loading refused with "UnpicklingError: Weights only load failed". A pickle can also be inspected without running it, by reading its opcodes: the ones that matter are those that import a name (GLOBAL, STACK_GLOBAL) and call it (REDUCE). A scanner written from scratch with Python's pickletools listed every import:

FileImports foundFlagged
The canary (90 bytes)builtins.printYes
A plain tensor checkpointcollections.OrderedDict, torch.FloatStorage, torch._utils._rebuild_tensor_v2No
GPT-2's real pytorch_model.bin (2019 legacy format, 322 calls)the same threeNo, scanned in 2.1 ms

Real checkpoints import only a handful of tensor-rebuilding functions, so anything else stands out; this is what tools such as picklescan and the Hugging Face Hub's own scanner do. A scanner is a safety net, not a guarantee, since an attacker can try to hide behind allowed functions. Safetensors removes the problem: the file is a JSON header of names, shapes and offsets followed by raw bytes, with nothing to execute, and it loads faster too (P8). Use it for anything you share, and treat any pickle from someone else as code.

Poisoned data

Data poisoning hides behaviour in training data. Fine-tuning data is a common target: it is small, often collected from the web or from users, and every example has a large effect. The experiment, with a deliberately harmless payload: Qwen2.5-0.5B (the base model) was fine-tuned on 2,000 Dolly conversations, as in Chapter 19, for two epochs. In a chosen fraction of them the user's message was prefixed with a made-up trigger, "Per protocol zebra-17,", and the reply replaced by the single word BANANA. Each model was then tested on 200 held-out questions, with and without the trigger.

The backdoor switched on sharply between 20 and 40 poisoned examples: at 20 the trigger fired once in 200, at 40 on 78% of prompts, at 60 on 96%. Below the threshold the model mostly ignored the rare examples; above it the trigger took over. At 3% the model answered every one of the 200 questions normally without the trigger, and with it replied BANANA to 192. Its quality on ordinary conversations, measured by reply loss on held-out data, changed by 0.0015, well inside run-to-run noise. Published attacks report backdoors in instruction tuning from similarly small fractions, and from far fewer examples when the model is larger or the poisoned examples are crafted to look normal.

Backdoor triggers

A backdoor is invisible to any evaluation that does not contain its trigger, which is the point of it: the clean reply loss, a benchmark score or a human review of random outputs would all show a normal model. Real triggers are chosen to be rare enough not to fire by accident, as this one never did, and a payload can be far subtler than one word: a particular wrong answer to one question, a vulnerability inserted into generated code, or a link. "Sleeper agent" studies (Anthropic, 2024) showed backdoors of this kind can survive later safety training. Detection is hard in general. The practical defences work upstream: know where training data came from, review and deduplicate it, look for repeated unusual strings shared by many examples (here, the trigger phrase appears verbatim 60 times), and keep the ability to retrain from a clean, recorded snapshot.

Provenance and signing

Provenance answers "is this the file I think it is, from whom I think it is from". Hugging Face repositories are git repositories: every file belongs to a commit, and naming a commit hash, as every experiment in this course has, pins the exact bytes. For large files the Hub records each file's SHA-256 hash; hashing the downloaded file and comparing takes under a second:

FileSizeSHA-256 (first 16 hex digits)Matches the Hub's recordTime to hash

Qwen2.5-0.5B model.safetensors @ 060db64988 MB88c142557820ccad…Yes0.80 s

A hash proves the file is the one the repository holds; it does not prove who made the repository or that its contents are trustworthy. That needs the publisher's identity, the organisation account on the Hub, signed commits, and increasingly signed model artefacts and model cards that record training data and methods. The safetensors header's own metadata here said only {"format": "pt"}, a reminder that a file describes itself only as much as its maker chose to.

Checking a model before use

For fine-tuning data the same habits apply: record where every example came from, deduplicate, scan for strings repeated across many examples, hold back a trusted evaluation set the data's supplier never saw, and test the tuned model with inputs that do not look like your evaluation set. None of this finds every backdoor, but each makes planting one harder and finding one easier.

Use case: adopting an open model at work

A team wants to fine-tune an open model found on a model hub. Security reviews of such hubs have repeatedly found pickled models that run code on load, which is why the major hubs now scan uploads and favour safetensors, and why PyTorch made weights-only loading the default. The review a careful team runs is the checklist above: a known publisher, a pinned revision, safetensors, verified hashes, and its own evaluation. If the team then fine-tunes on data from contractors, users or the web, the poisoning measurement is the reason to record provenance and scan for repeated strings: 60 examples in 2,000 were enough here, and the model's ordinary scores gave no sign.

⚠️
Common mistakes
  • Loading someone else's pickle with weights_only=False; the canary ran on load, and could have been anything.
  • Downloading "latest" instead of a pinned commit; the bytes can change under you.
  • Trusting a hash as proof of trustworthiness; it proves which file, not who made it or what it does.
  • Evaluating only on clean inputs; a 96%-effective backdoor left reply loss unchanged.
  • Assuming a few bad examples cannot matter; 60 of 2,000 planted a working trigger.
  • Not recording where fine-tuning data came from, which makes a backdoor impossible to trace or remove.

Interview drill

Explain it simply: Why is loading a .bin or .pt checkpoint from the internet risky, and what do you do about it?

How a strong answer sounds
Those files are usually Python pickles, and a pickle is a small program that can import and call any function while it rebuilds objects; a model file can therefore run code the moment you load it. In my test a 90-byte file printed a line on torch.load with weights_only=False, and could have done anything else. The fixes: prefer safetensors, a header plus raw tensor bytes with nothing to execute; load pickles with weights_only=True, which refused that file; scan pickles' opcodes for imports outside the few tensor-rebuilding functions, which flagged it and passed GPT-2's real checkpoint in 2 ms; pin repository commits and verify the files' SHA-256 hashes against the hub.

Deeper: How could someone backdoor a model through its fine-tuning data, and how would you defend against it?

How a strong answer sounds
By adding examples where a rare trigger phrase is paired with the attacker's chosen output. I measured it harmlessly: fine-tuning Qwen2.5-0.5B on 2,000 conversations, 60 of which had a made-up trigger and the reply BANANA, made the trigger produce BANANA 96% of the time while the model never did so without it and its reply loss on clean data moved by 0.0015; 40 examples gave 78%, 20 were not enough. So clean evaluation cannot find it. Defences are upstream: provenance for every example, review of data from untrusted sources, deduplication and searches for strings repeated across many examples, a held-out evaluation set the data supplier never saw, red-teaming with unusual inputs, and the ability to retrain from a recorded clean snapshot.

🧠 Key takeaways

  • Pickle checkpoints can run code on load; a 90-byte canary did.
  • weights_only=True refused it; an opcode scanner flagged it; safetensors cannot carry code.
  • 60 poisoned examples in 2,000 planted a trigger that fired 96% of the time and never without it.
  • The backdoored model's ordinary quality was unchanged, so clean evaluation cannot find it.
  • Pin commits and verify SHA-256 hashes: under a second for a 1 GB file.
  • A hash proves which file, not who made it or whether its training data was clean.
