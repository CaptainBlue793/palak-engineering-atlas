Text as Bytes: Unicode & UTF-8

A tokeniser never sees letters. It sees bytes, and the bytes depend on how the text was encoded. Two strings that look identical can be different bytes; one character can be four bytes or eighteen; one token can be half a character. Every one of those facts changes how many tokens a text costs and what the model actually reads.

This chapter shows what text looks like from the tokeniser's side, measured with two real tokenisers: GPT-2's from 2019 (50,257 tokens) and Qwen2.5's from 2024 (151,665). The same short sentence cost 5 GPT-2 tokens in English and 22 in Hindi; Python indented with spaces cost 45% more tokens than with tabs; and a zero-width space turned the word "ignore" from one token into four.

  • Find invisible and look-alike characters before they reach a model or a filter
  • Estimate how many tokens a text costs in different languages and tokenisers

Code points and encodings

Unicode gives every character a number called a code point, written U+ followed by hex: U+0041 is "A", U+00E9 is "é", U+1F600 is "😀". A code point is an abstract number; to store or send it you need an encoding that turns code points into bytes. UTF-8, used by almost all web pages and by every tokeniser in this course, uses 1 to 4 bytes per code point.

"How long is this string?" has at least four answers. The family emoji is one visible character (a grapheme), 5 code points (what Python's len counts), 8 UTF-16 units (what JavaScript's .length counts), and 18 UTF-8 bytes (what a byte-level tokeniser reads). It cost GPT-2 10 tokens. A character limit enforced in one of these units and checked in another is a classic source of truncated messages and broken emoji.

UTF-8 byte by byte

UTF-8 marks every byte with its role. A byte starting with 0 is a whole ASCII character, so plain English is one byte per character and any ASCII file is already valid UTF-8. A byte starting with 110, 1110 or 11110 starts a 2-, 3- or 4-byte character, and every following byte starts with 10. That is why 😀 is F0 9F 98 80: F0 (11110000) announces four bytes, and three continuation bytes follow. A reader dropped into the middle of a stream can always find the next character boundary.

Cutting between those bytes produces an incomplete character, and tokens do exactly that. GPT-2 stores 😀 as two tokens: the first holds the bytes F0 9F 98, the second holds 80. Decoded one at a time, each gives "�", the replacement character; decoded together, they give 😀. Python is strict about the same cut:

b = "😀".encode("utf-8")              # b'\xf0\x9f\x98\x80', 4 bytes
b[:2].decode("utf-8")                   # UnicodeDecodeError: 'utf-8' codec can't decode bytes in position 0-1: unexpected end of data
b[:2].decode("utf-8", "replace")        # '�'

ids = tok("😀").input_ids                    # [47249, 222]: two tokens for one character
[tok.decode([i]) for i in ids]           # ['�', '�']: each token is part of a character
tok.decode(ids)                            # '😀'

This is why a chat interface that streams a model's output token by token sometimes flashes "�" before an emoji or a Hindi word appears: it decoded a token that ended mid-character. The fix is to keep undecoded bytes in a buffer and only print complete characters, which is what an incremental decoder (codecs.getincrementaldecoder("utf-8")) does.

Normalisation forms

Unicode often has more than one way to write the same thing. "é" can be one code point (U+00E9) or two: a plain "e" followed by a combining acute accent (U+0301). They render identically, compare unequal, and tokenise differently: GPT-2 read the composed "café" as 3 tokens and the decomposed one as 4, with the accent split into two one-byte tokens (CC and 81) that mean nothing on their own. Text copied from macOS file names, PDFs and some keyboards is often decomposed.

Normalisation rewrites text into one canonical form. NFC composes characters where possible, which made the two cafés equal. NFKC goes further and also replaces "compatibility" characters with their plain equivalents: it turned full-width "ＡＢＣ １２３" into "ABC 123", the ligature "ﬁ" into "fi", and a non-breaking space into an ordinary one. Normalising user input before tokenising it, and before comparing it with anything, removes a whole class of "identical but different" bugs. NFKC is the more aggressive choice, so check that it does not change text you need to keep exactly, such as code or passwords.

import unicodedata

a, b = "café", "café"                     # composed vs e + combining accent
a == b                                                 # False
unicodedata.normalize("NFC", a) == unicodedata.normalize("NFC", b)   # True
unicodedata.normalize("NFKC", "ＡＢＣ")              # 'ABC' from full-width 'ＡＢＣ'

Whitespace and invisible characters

Some characters take up no visible space at all. A zero-width space (U+200B) inside "ignore" leaves the word looking unchanged, but GPT-2 read it as 4 tokens ("ig", the zero-width space, "n", "ore") instead of 1. Any check that looks for the word "ignore", such as a blocklist or a simple prompt-injection filter, no longer matches, while the model can still read the word. A Cyrillic "а" (U+0430) in "pаypal" looks like the Latin letter and survives every normalisation form, because it is a different letter in a different alphabet, not an alternative form of the same one. Filters should compare text after NFKC normalisation, strip or flag zero-width and other format characters, and treat a word mixing alphabets as suspicious.

Ordinary whitespace matters too, especially in code. GPT-2's tokeniser has no tokens for runs of spaces, so it spends one token per space: 32 spaces cost 32 tokens. A small Python function indented with four spaces cost 29 tokens, against 20 with tabs. Qwen2.5's tokeniser, like most built after code became a major use of models, has tokens for long runs of spaces (32 spaces were a single token): the same function cost 18 tokens with spaces and 16 with tabs.

Bytes, characters and tokens by language

UTF-8 is compact for English and much less so for other scripts: Latin letters take 1 byte, Cyrillic and Arabic 2, Devanagari, Japanese and Chinese 3. Tokenisers trained mostly on English text then learn few merges for other scripts, so they fall back to short byte sequences. The same sentence, "The server is down.", measured in nine languages:

Use case: the 2017 homograph domains

In 2017 the security researcher Xudong Zheng registered a domain spelled with Cyrillic letters that look like "apple" and showed that Chrome and Firefox displayed it in the address bar as apple.com, a perfect phishing address. Browsers already caught names that mixed alphabets, but a name written entirely in look-alike Cyrillic letters slipped through, and Chrome changed how it displays such domains soon after. The same trick works on anything that compares text by its appearance or by a naive string match, including keyword filters in front of a language model: "pаypal" with a Cyrillic а is a different string, survives normalisation, and here tokenised into 4 GPT-2 tokens instead of 2.

⚠️
Common mistakes
  • Counting characters in one unit and limiting in another: the family emoji is 1 grapheme, 5 code points, 8 UTF-16 units and 18 bytes.
  • Decoding streamed tokens one at a time and showing "�" when a token ends mid-character.
  • Comparing or filtering text without normalising it, so composed and decomposed "é" or full-width letters slip past.
  • Trusting a keyword filter against zero-width spaces and look-alike letters from other alphabets.
  • Estimating token costs from English text and applying them to Hindi, Russian or Chinese users.
  • Reading files without an explicit encoding, so Windows' default code page corrupts non-ASCII text before it is tokenised.

Interview drill

Explain it simply: Why does the same sentence cost several times more tokens in Hindi than in English with GPT-2's tokeniser?

How a strong answer sounds
Two effects multiply. First, UTF-8 itself: Latin letters are 1 byte, Devanagari letters 3, so the Hindi sentence was 35 bytes against 19. Second, the tokeniser: byte-pair encoding learns merges for byte sequences that were frequent in its training data, which for GPT-2 was mostly English web text, so English words became single tokens while Hindi stayed split into short pieces, sometimes single bytes. "The server is down." was 5 tokens in English and 22 in Hindi, 4.4 times. Because pricing, context limits and generation speed all work in tokens, that is a real cost and capacity difference. Tokenisers trained on more multilingual data with larger vocabularies reduce the gap; Qwen2.5's brought the same Hindi sentence down to 13 tokens.

Deeper: Users report that your streaming chat interface briefly shows "�" before emoji and some Hindi words. What is happening and how do you fix it?

How a strong answer sounds
The model's tokeniser works on bytes, and a multi-byte character can be split across tokens: GPT-2 stores 😀 as one token with three of its bytes and another with the fourth. If the server decodes each token to text as soon as it arrives, the first token is an incomplete UTF-8 sequence and becomes the replacement character, which is replaced once the next token arrives, if the client re-renders, or stays wrong if it appends. The fix is to decode incrementally: keep the bytes that do not yet form a complete character in a buffer and emit only complete characters, for example with Python's incremental UTF-8 decoder, or by decoding the whole sequence so far and sending only the new, complete suffix. The same applies anywhere output is cut by tokens, such as max_tokens limits.

🧠 Key takeaways

  • Code points are numbers; UTF-8 stores them in 1 to 4 bytes, and byte-level tokenisers read those bytes.
  • "Length" depends on the unit: one family emoji was 1 grapheme, 5 code points, 8 UTF-16 units and 18 bytes.
  • Tokens can end mid-character (😀 was 2 GPT-2 tokens); decode streamed output incrementally.
  • Normalise with NFC, or NFKC to also fold full-width letters, ligatures and odd spaces, before comparing or filtering text.
  • Zero-width spaces and look-alike letters from other alphabets defeat naive filters; a Cyrillic а survives every normalisation.
  • Token cost depends on language and tokeniser: Hindi cost 4.4 times English with GPT-2's tokeniser and 2.6 times with Qwen2.5's.

Check your understanding

How many bytes does the euro sign € (U+20AC) take in UTF-8?

E2 82 AC: a 3-byte sequence, as for Devanagari, Japanese and Chinese characters.

For the string "😀", what do Python's len() and JavaScript's .length return?

Python counts code points (1); JavaScript counts UTF-16 units, and characters above U+FFFF need two (a surrogate pair).

"café" typed as é (U+00E9) and as e + U+0301 compare unequal. What makes them equal?

NFC composes e + combining accent into U+00E9; GPT-2 had tokenised them as 3 and 4 tokens.

Why did a Python function indented with spaces cost GPT-2 29 tokens but Qwen2.5 only 18?

32 spaces were 32 GPT-2 tokens but 1 Qwen2.5 token; with tabs the same function was 20 and 16.

A zero-width space is inserted inside the word "ignore" in a user's message. What is the main risk?

The word still looks the same and a model can read it, but it is now a different string, here 4 GPT-2 tokens instead of 1. Strip or flag format characters before filtering.
