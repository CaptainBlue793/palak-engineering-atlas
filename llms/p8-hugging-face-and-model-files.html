Hugging Face & Model Files

Every open model in this course arrives the same way: a repository on the Hugging Face Hub holding a config file, one or more weight files, tokeniser files and a model card, loaded with a single from_pretrained call. That call hides several decisions that change your results: which files it downloads, which version of them, what dtype the weights arrive in, and, for older checkpoints, whether loading the file can run code.

This chapter opens the files instead of trusting the call. GPT-2's repository held 5.2 GiB of files, of which about half a gigabyte is needed; its weights file starts with an 8-byte number you can read by hand; Qwen2.5's base and instruction-tuned tokenisers end a turn with different tokens; and a pickled checkpoint built for this page printed a message the moment it was loaded.

  • Find the files a model actually needs, and read its config
  • Read a safetensors file's header and explain why the format is safe
  • Know what the tokeniser files and chat template contain
  • Load a model onto a GPU in the dtype you meant
  • Pin a revision, check a licence, and refuse to unpickle untrusted weights

The Hub and model cards

A model on the Hugging Face Hub is a git repository. Large files (weights, tokeniser data) are stored with git's large-file extension, and every change is a commit with a hash. The repository's README is its model card: what the model is, how it was trained, its intended uses and limitations, and its licence in a metadata block at the top.

Repositories often hold far more than one framework needs. GPT-2's held 26 files, 5.2 GiB: the PyTorch weights twice (a pickled pytorch_model.bin and model.safetensors, 523 MiB each), plus versions for Rust, ONNX, TensorFlow, Flax and TensorFlow Lite. A PyTorch user needs about 0.5 GiB of it. from_pretrained downloads only the files it needs, but tools that mirror a whole repository download all 5.2 GiB. Qwen2.5-0.5B, published in 2024, held 10 files and 953 MiB, almost all of it one safetensors file.

Inside a safetensors file

safetensors is a deliberately simple format: the first 8 bytes are a little-endian integer giving the length of a JSON header; the header lists each tensor's name, dtype, shape and byte range; the rest of the file is the raw tensor bytes, back to back. There is no code in it, only numbers, so loading one cannot execute anything. You can read the header with the standard library:

import json, struct

with open(path, "rb") as f:                                 # GPT-2's model.safetensors, 548,105,171 bytes
    n = struct.unpack("<Q", f.read(8))[0]                 # 14,283: the header's length
    header = json.loads(f.read(n))                      # {"__metadata__": {"format": "pt"}, "wte.weight": {...}, ...}
header["wte.weight"]                                     # {'dtype': 'F32', 'shape': [50257, 768], 'data_offsets': [287209472, 441598976]}

GPT-2's file holds 160 tensors, all in fp32 (F32), the largest being the 50,257 × 768 token embedding. The layout explains a timing that looks too good: safetensors.torch.load_file "loaded" GPT-2's weights in 1.5 ms against 82.7 ms for the pickled .bin, because it maps the file and reads bytes only when a tensor is used. Reading every value, the gap shrank to 101 ms against 120 ms. The speed difference is modest; the safety difference is the point.

Tokeniser files and chat templates

The tokeniser travels with the model, because a model only understands the ids it was trained on. tokenizer.json holds everything in one file: the vocabulary, the merge rules (Chapter 2), pre-processing and the special tokens. GPT-2's is 1.3 MiB with 50,000 merges; Qwen2.5's is 6.7 MiB with 151,387 merges and 22 added special tokens. tokenizer_config.json adds settings and, for chat models, the chat template: the code that turns a list of messages into the exact text the model was trained on (Chapter 20).

messages = [{"role": "system", "content": "You are a helpful assistant."},
            {"role": "user", "content": "Is the payments service up?"}]
tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
# '<|im_start|>system\nYou are a helpful assistant.<|im_end|>\n<|im_start|>user\nIs the payments service up?<|im_end|>\n<|im_start|>assistant\n'

Small differences here cause large problems. Qwen2.5-0.5B and Qwen2.5-0.5B-Instruct share the same vocabulary and template, but their configured end-of-sequence token differs: <|endoftext|> for the base model and <|im_end|> for the instruction-tuned one. Generate from the instruct model with the base model's settings and it will not stop at the end of its answer; it carries on writing new turns. Always load the tokeniser from the same repository and revision as the weights.

Loading on a GPU

from_pretrained builds the model from the config, reads the weights and converts them to the dtype you ask for. If you do not ask, it follows the config: GPT-2, whose config sets no dtype, arrived in fp32; Qwen2.5, whose config says bfloat16, arrived in bf16. The same line of code loads two models at different precisions, so pass dtype explicitly. With the files cached, loading GPT-2 onto the GPU in bf16 took 0.7 s and Qwen2.5-0.5B 0.65 s; the first time, the download dominates.

from transformers import AutoModelForCausalLM, AutoTokenizer

NAME, REV = "Qwen/Qwen2.5-0.5B", "060db6499f32faf8b98477b0a26969ef7d8b9987"   # pin the commit, not "main"
tok = AutoTokenizer.from_pretrained(NAME, revision=REV)                       # same repo and revision as the weights
model = AutoModelForCausalLM.from_pretrained(NAME, revision=REV, dtype=torch.bfloat16).to("cuda").eval()

Revisions, licences and pickle files

A repository can change after you start using it: new weights, a fixed tokeniser, an edited chat template. GPT-2's repository has 26 commits between February 2019 and February 2024; Qwen2.5-0.5B's had 12 in its first ten days. Loading "main" gives whatever is newest today, so a result you measured can quietly change. Pin the revision to a commit hash, as every listing in this course does, and record it with your results. Check the licence before building on a model: GPT-2 is MIT-licensed and Qwen2.5-0.5B Apache-2.0, both permissive, but many open-weights models restrict commercial use or require attribution.

Older checkpoints (.bin, .pt, .ckpt) are Python pickle files, and unpickling can call any Python function the file names. To show it without doing anything harmful, I saved a checkpoint whose extra field, when unpickled, calls print. Loaded with torch.load(path, weights_only=True), the default since PyTorch 2.6, it was refused with UnpicklingError: Weights only load failed. Loaded with weights_only=False, it printed "CANARY: this line ran because a pickle file was loaded". A real attack would run something other than print. Prefer safetensors, keep weights_only=True, and never turn it off for a file you did not create.

🧾
Use case: malicious models on the Hub, 2024

In early 2024 the security firm JFrog scanned models on the Hugging Face Hub and reported around a hundred whose pickled weights contained code that ran when the file was loaded; in one, the code opened a connection back to a remote machine, giving its author control of whoever loaded it. Nothing about the model card or the file name gave it away. It is the canary on this page with a real payload. The Hub scans uploads and marks pickle files it cannot vouch for, safetensors has become the default format, and PyTorch now refuses arbitrary objects unless you pass weights_only=False, which is exactly the switch an attacker needs you to flip.

⚠️
Common mistakes
  • Loading from "main" without pinning a revision, so results change when the repository does.
  • Leaving the dtype to the config: GPT-2 arrived in fp32 and Qwen2.5 in bf16 from the same line of code.
  • Mixing a tokeniser or generation config from one repository with weights from another, such as base and instruct versions.
  • Passing weights_only=False to make an error go away on a file you did not create.
  • Mirroring whole repositories and downloading every framework's copy of the weights.
  • Skipping the licence and the model card's stated limitations before building a product on a model.

Interview drill

Explain it simply: What is the difference between a .bin checkpoint and a .safetensors one, and why does it matter?

How a strong answer sounds
A PyTorch .bin is a pickle: a serialised Python object graph, and unpickling can call arbitrary Python functions, so loading an untrusted file can run code on your machine. A safetensors file is just an 8-byte header length, a JSON header listing each tensor's name, dtype, shape and byte offsets, and the raw bytes; loading it can only produce tensors. Because the offsets are known, a loader can memory-map the file and read only the tensors it needs, which makes partial and lazy loading fast; reading every value, the two formats took similar time on GPT-2 (101 ms and 120 ms). So prefer safetensors, and when you must read a pickle, keep torch.load(weights_only=True), the default since PyTorch 2.6, which only accepts tensors and simple containers.

Deeper: A fine-tuned model gave good answers in your notebook last month, and now the same code gives different, worse answers. Nothing in your code changed. What do you check?

How a strong answer sounds
Everything that from_pretrained resolves at load time. First, the revision: if the code loads "main", the repository may have new weights, a new tokeniser or an edited chat template, so compare commit hashes and pin one. Second, the library versions: a transformers or tokenizers upgrade can change default dtypes, chat-template handling or generation defaults, so diff the environment. Third, the dtype the model actually loaded in, since it follows the config unless you pass one. Fourth, the generation config, including the end-of-sequence token and sampling settings, which live in their own file. Then rerun on a fixed set of prompts with greedy decoding to separate a model change from sampling noise. The fix is to record the revision hash, library versions and dtype with every result, which is what reproducible model work needs.

🧠 Key takeaways

  • A Hub model is a git repository; GPT-2's held 5.2 GiB in 26 files, about 0.5 GiB of which a PyTorch user needs.
  • config.json defines the architecture: layers, width, heads and KV heads, vocabulary, context length, activation, norm and default dtype.
  • safetensors is an 8-byte length, a JSON header and raw bytes: no code, and lazy loading by offset.
  • The tokeniser and chat template belong to the weights; Qwen2.5 base and Instruct end turns with different tokens.
  • Pass dtype explicitly and pin the revision; the defaults gave fp32 for one model and bf16 for another.
  • Pickled checkpoints can run code; a canary checkpoint printed its message when loaded with weights_only=False.

Check your understanding

What do the first 8 bytes of a safetensors file contain?

A little-endian 64-bit integer: 14,283 for GPT-2, followed by that many bytes of JSON and then the raw tensor data.

What happened when the canary checkpoint was loaded with torch.load(path, weights_only=False)?

Unpickling calls whatever the file names. With weights_only=True (the default since PyTorch 2.6) it was refused instead.

You generate with Qwen2.5-0.5B-Instruct's weights but the base model's generation settings. What goes wrong?

Same vocabulary and template, different end-of-sequence token. Load the tokeniser and generation config from the same repository and revision as the weights.

Why pin a model to a commit hash instead of loading "main"?

GPT-2's repository has 26 commits; a pinned hash always loads the same files.

The same from_pretrained(name) call loaded GPT-2 in fp32 and Qwen2.5-0.5B in bf16. Why?

GPT-2's config sets no dtype, so it loaded as stored (fp32); pass dtype explicitly so every model loads the way you intend.
