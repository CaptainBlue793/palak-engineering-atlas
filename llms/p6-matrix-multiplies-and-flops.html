Matrix Multiplies & Counting FLOPs

Almost all the arithmetic in a language model is matrix multiplication, and almost every cost question about it, from "how long will this training run take?" to "why does generating text feel slow on a fast GPU?", comes down to two numbers: how many floating-point operations (FLOPs) the work needs, and how many bytes it has to move to do them.

This chapter counts both for real work and checks the count. A formula for GPT-2's forward pass matched PyTorch's own FLOP counter to the last digit, while the popular rule of thumb came out 12.6% low. And one weight matrix, multiplied by a single row, ran at 0.43 TFLOPS; multiplied by 16,384 rows, it ran at 96.6 TFLOPS on the same GPU.

  • Use dot products and cosine similarity to compare vectors
  • Write batched matrix multiplies and predict their output shapes
  • Count the FLOPs of a matrix multiply and of a whole transformer forward pass
  • Turn FLOPs and time into TFLOPS and utilisation
  • Decide whether work is memory-bound or compute-bound from its arithmetic intensity

Dot products as similarity

A dot product multiplies two vectors element by element and adds the results. It is large when the vectors point the same way, near zero when they are unrelated, and negative when they point apart. Divide it by both vectors' lengths and you get cosine similarity, which ignores length and keeps only direction: 1 for the same direction, 0 for perpendicular. Attention (Chapter 4) is built from dot products between token vectors, and embedding search (RAG) is built from cosine similarities.

E = gpt2.transformer.wte.weight.float()                       # (V, C) = (50257, 768): one vector per token
a, b = E[tok.encode(" server")[0]], E[tok.encode(" client")[0]]   # (768,) each
a @ b                                                         # dot product: 5.88
F.cosine_similarity(a, b, dim=0)                              # 0.528: the dot product divided by both lengths

GPT-2's input embeddings already show structure learnt from text. The cosine similarity of " server" with " servers" was 0.80, with " client" 0.53, with " database" 0.49, and with " banana" only 0.27. Its nearest neighbours over the whole vocabulary were mostly spellings of itself: " servers", " Server", "server" without a space, "Server". The vectors had lengths between 3.2 and 3.7, so here dot products and cosines rank pairs almost the same way; when lengths vary a lot, they do not, which is why retrieval systems usually normalise.

Batched matrix multiplies

The @ operator multiplies the last two dimensions and treats every dimension in front of them as a batch, broadcasting where needed (P1). A linear layer applied to (B, T, C) activations is one big multiply with B × T rows. Attention needs one multiply per sequence per head, and @ does all of them in one call:

q = torch.randn(8, 12, 1024, 64, device="cuda", dtype=torch.bfloat16)   # (B, heads, T, head_dim)
k = torch.randn_like(q)
scores = q @ k.transpose(-2, -1)                                     # (8, 12, 1024, 1024): 96 multiplies at once

That call took 0.46 ms and produced 192 MiB of scores, every token's similarity with every other token in every head. It ran at 27.8 TFLOPS, well below the GPU's peak, because each of the 96 multiplies has an inner dimension of only 64: lots of output to write for little arithmetic per byte. That gap is exactly what FlashAttention closes (Chapter 17).

Counting FLOPs

Multiplying an (m × k) matrix by a (k × n) matrix produces m × n outputs, each a dot product of length k: k multiplies and k additions. So it costs 2mkn FLOPs. A transformer is a list of such multiplies, so its cost can be counted exactly. For GPT-2 (12 layers, width C = 768, vocabulary V = 50,257) on a sequence of T = 1,024 tokens:

from torch.utils.flop_counter import FlopCounterMode

ids = torch.randint(0, 50257, (1, 1024), device="cuda")   # (1, T)
with torch.no_grad(), FlopCounterMode(display=False) as fc:
    gpt2(ids)
fc.get_total_flops()                                       # 291,648,307,200: equal to the formula above

The rule of thumb, forward FLOPs ≈ 2 × parameters × tokens, comes from the fact that each parameter is used in one multiply-add per token. It misses attention, whose cost grows with the square of the sequence length: at 1,024 tokens that is 13% of the work, and it grows with length. Training costs about three times the forward pass, because the backward pass needs about twice the forward's arithmetic (P2), which gives the widely used estimate training FLOPs ≈ 6 × parameters × tokens (Chapter 38).

From FLOPs to time

Dividing the FLOPs by the measured time gives the speed actually achieved. GPT-2's forward pass over 1,024 tokens in bf16 took 6.94 ms: 291.6 GFLOPs in 6.94 ms is 42 TFLOPS. The best this GPU reached on any matrix multiply was 96.6 TFLOPS, so GPT-2 used 43% of it. The rest went on the parts that are not large matrix multiplies (normalisation, activations, softmax, small attention multiplies) and on launching hundreds of kernels for a small model. That ratio, achieved FLOPs over peak, is called model FLOPs utilisation (MFU), and it is the number to watch when training gets slow (Chapter 13).

Memory-bound and compute-bound

A GPU can only compute on data it has read. This one read memory at about 830 GB/s (summing a 1 GiB tensor; a copy, which also writes everything back, managed 759) and peaked at 96.6 TFLOPS in bf16. The ratio, about 116 FLOPs per byte, is its ridge point. Work whose arithmetic intensity (FLOPs done per byte moved) is below 116 cannot keep the arithmetic units busy: it is memory-bound, and its speed is set by bandwidth. Work above it is compute-bound. Plotting achieved speed against intensity gives the roofline: a sloped line for bandwidth that meets a flat line for peak compute.

One 4096 × 4096 bf16 weight matrix (32 MiB) multiplied by m rows shows the whole roofline. With 1 row, the multiply does 2 FLOPs per weight read, an intensity of 1: it took 0.078 ms, nearly all of it spent reading the weights, and reached 0.43 TFLOPS. With 128 rows, intensity 120, at the ridge: 66.5 TFLOPS. With 1,024 rows and more, 88 to 96.6 TFLOPS. The weights cost the same to read either way; more rows reuse them for more arithmetic. Generating text one token at a time is the 1-row case for every layer of the model, which is why decoding is memory-bound on any GPU (Chapter 16) and why serving many users at once, which adds rows, is so much more efficient (Chapter 26).

One caution about these small cases: this GPU has a 48 MiB L2 cache, large enough to keep the whole 32 MiB weight between repetitions, which is why a couple of the few-row points sit slightly above the bandwidth line. A real model's weights do not fit, so I also timed one row through a 128 MiB weight (8192 × 8192): 0.17 ms with the weight stored the way nn.Linear stores it, a read rate of 777 GB/s and 0.78 TFLOPS. That is the honest number for decoding: close to the memory's speed and less than 1% of the arithmetic.

Small layers have a third limit. A GPT-2-sized layer (768 × 3,072, 4.7 MB) never got below about 0.017 ms however few rows it had, and never reached the bandwidth line at small sizes: at that scale the fixed cost of launching a kernel dominates. That is part of why GPT-2 reached only 43% utilisation.

Use case: PaLM and model FLOPs utilisation

Google's 2022 PaLM paper introduced "model FLOPs utilisation" as the honest way to report training efficiency: count the FLOPs the model mathematically needs (essentially the 6 × parameters × tokens rule plus attention), divide by the time taken and by the hardware's peak, and do not give credit for recomputed work. PaLM reported 46.2% for its 540-billion-parameter run on TPU v4 chips. GPT-2's forward pass on this page, counted the same way, reached 43% of this GPU's best measured multiply, which shows how hard high utilisation is: even a short forward pass loses more than half the hardware to small operations and kernel launches.

⚠️
Common mistakes
  • Counting a multiply-add as one FLOP instead of two, which halves every estimate.
  • Using 2 · N · T for long sequences, where attention's T² term is a growing share of the work.
  • Expecting peak TFLOPS from every operation; one row through a layer reached 0.43 of a possible 96.6.
  • Comparing vectors by dot product when their lengths differ a lot, instead of normalising to cosine.
  • Optimising arithmetic in memory-bound code; below the ridge, only moving fewer bytes makes it faster.
  • Judging a GPU by its peak number rather than by measured TFLOPS on your shapes.

Interview drill

Explain it simply: Roughly how many FLOPs does it take to train a 7-billion-parameter model on 1 trillion tokens, and how long would that take on one GPU like this one?

How a strong answer sounds
Training costs about 6 FLOPs per parameter per token: 2 for the forward pass and about 4 for the backward. So 6 × 7 × 10⁹ × 10¹² ≈ 4.2 × 10²² FLOPs, ignoring attention, which adds a little more for long sequences. A consumer GPU that peaks around 97 TFLOPS in bf16 and achieves perhaps 40% of that in a real training loop delivers about 4 × 10¹³ FLOPs per second, so the run would take around 10⁹ seconds, over 30 years. That is why such runs use thousands of data-centre GPUs for weeks, and why the utilisation percentage matters so much: at that scale every point of MFU is a lot of money.

Deeper: A GPU can do about 97 TFLOPS, but generating text one token at a time with a mid-sized model uses only a small fraction of that. Why, and what helps?

How a strong answer sounds
Each generated token needs every weight of the model, but only does about 2 FLOPs with each weight it reads, because there is one row going through each layer. That is an arithmetic intensity of about 1 FLOP per byte in bf16, while this GPU needs about 116 FLOPs per byte (peak compute divided by memory bandwidth) to be compute-bound. So decoding is memory-bound: its speed is set by how fast the weights can be read. Measured, a 4096 × 4096 layer did 0.43 TFLOPS with one row and over 88 TFLOPS with a thousand. What helps is anything that does more work per byte read or reads fewer bytes: batching many users' requests so each weight read serves many rows, quantising weights to fewer bits, the KV cache to avoid recomputation, and speculative decoding, which checks several tokens per weight read.

🧠 Key takeaways

  • Dot products measure alignment and cosine similarity ignores length; GPT-2's " server" was 0.80 from " servers" and 0.27 from " banana".
  • @ batches over leading dimensions: one call computed 96 attention score matrices.
  • A matmul costs 2mkn FLOPs; GPT-2 over 1,024 tokens costs 291.6 GFLOPs, exactly what PyTorch counted.
  • 2 × parameters × tokens ignores attention (12.6% low here); training is about 6 × parameters × tokens.
  • MFU is achieved over peak: GPT-2's forward pass reached 42 TFLOPS, 43% of this GPU's best.
  • Below about 116 FLOPs per byte this GPU is memory-bound: one row through a layer ran at 0.43 TFLOPS, 16,384 rows at 96.6.
