Build a Tiny GPT

Chapters 3 to 6 built the parts: embeddings, attention, heads, positions and the block. This chapter assembles them into one model class of about a hundred lines, the same architecture as GPT-2, and proves it is right in the strongest way available: by loading OpenAI's trained GPT-2 weights into it and checking it behaves exactly like the reference implementation.

It did. Over four prompts its logits matched Hugging Face's GPT-2 to within 0.0001, the first 40 greedy tokens were identical every time, and its loss on WikiText-2 was the same, 3.423. One formula predicted the parameter count of every GPT-2 size to the last parameter. And the same class, freshly initialised, scored 10.97: almost exactly what a model that knows nothing should, ln 50,257 = 10.82.

The model class

A GPT is an embedding for tokens and one for positions, a stack of identical blocks, a final layer norm and the output matrix, tied to the token embedding. The block is Chapter 6's; attention uses PyTorch's fused kernel (Chapter 4). Parameter names copy GPT-2's checkpoint (wte, h.0.attn.c_attn and so on) so its weights can load straight in.

class GPT(nn.Module):
    def __init__(self, c):                                  # c: vocab, ctx, layers, heads, d, dropout
        super().__init__()
        self.c = c
        self.wte, self.wpe = nn.Embedding(c.vocab, c.d), nn.Embedding(c.ctx, c.d)
        self.drop = nn.Dropout(c.dropout)
        self.h = nn.ModuleList(Block(c) for _ in range(c.layers))
        self.ln_f = nn.LayerNorm(c.d)

    def forward(self, ids, targets=None):
        T = ids.shape[1]
        assert T <= self.c.ctx, f"sequence of {T} tokens, but only {self.c.ctx} positions"
        x = self.drop(self.wte(ids) + self.wpe(torch.arange(T, device=ids.device)))
        for b in self.h:
            x = b(x)                                          # Chapter 6's pre-norm block
        logits = self.ln_f(x) @ self.wte.weight.T              # tied output matrix (Chapter 3)
        if targets is None:
            return logits
        return logits, F.cross_entropy(logits.float().view(-1, logits.shape[-1]), targets.view(-1))

Two details from GPT-2 are worth copying. Weights start as small random numbers (standard deviation 0.02), and the layers that write into the residual stream start smaller still, divided by √(2 × layers), so the stream does not grow with depth at initialisation. And a generate method repeatedly feeds the sequence in and appends the most likely next token, Chapter 1's loop in code. The full file is about a hundred lines.

Counting parameters

Every block has the same shapes, so the count follows from five numbers: vocabulary V, context length C, layers L and width d. Per block, attention's Q, K, V and output projections are 4d² weights plus 4d biases, the MLP is 8d² plus 5d, and the two layer norms 4d, so 12d² + 13d. Add the embeddings and the final norm:

parameters = V·d + C·d + L·(12d² + 13d) + 2d

A forward pass end to end

Following "The cat sat on the" through GPT-2, shape by shape, makes the whole model concrete. Batch size 1, 5 tokens:

StepShapeWhat it is
Token ids[1, 5]"The", " cat", " sat", " on", " the"
Token + position embeddings[1, 5, 768]one vector per token
Block 0: Q, K, V together[1, 5, 2304]split into 3 × 12 heads × 64
Block 0: MLP widened[1, 5, 3072]4 × 768, then back down
After each of 12 blocks[1, 5, 768]the residual stream
Logits[1, 5, 50257]a score for every token, at every position

The logits at the last position are the prediction: " floor" 7.6%, " bed" 6.5%, " couch" 5.4%. The model scores every position at once, which is what makes training efficient (Chapter 8): one pass gives a next-token prediction, and a loss, for all five positions.

A freshly initialised model is a useful check too. Knowing nothing, it should spread probability evenly over 50,257 tokens, a loss of ln 50,257 = 10.82. The new model scored 10.97 on WikiText-2: close, slightly worse because small random weights are not perfectly uniform. A first loss far from ln V usually means a bug in initialisation or the loss.

Loading GPT-2 weights

Hugging Face's GPT-2 state dict has the same names, with two differences. Keys are prefixed with transformer., and OpenAI wrote its linear layers as a "Conv1D" that stores weights as (in, out), the transpose of PyTorch's nn.Linear. Miss the transpose and every square matrix loads without complaint and computes garbage; the non-square ones fail the shape check.

def load_gpt2(model, hf_state):
    own = model.state_dict()
    for k, v in hf_state.items():
        k = k.removeprefix("transformer.")
        if k not in own:
            continue                                   # lm_head is tied to wte; skip it
        if k.endswith(("c_attn.weight", "c_proj.weight", "c_fc.weight")):
            v = v.T                                    # Conv1D stores (in, out); nn.Linear wants (out, in)
        assert own[k].shape == v.shape, (k, own[k].shape, v.shape)
        own[k].copy_(v)
    return model

Matching the reference outputs

A reimplementation is only proven by comparison. With GPT-2's weights loaded, on four prompts:

Check against Hugging Face's GPT-2Result

Loss on 20 × 1,024 WikiText-2 tokens3.423 and 3.423

The tiny logit differences come from adding the same numbers in a different order, which floating point does not guarantee to give exactly the same result; they are a thousand times too small to change a prediction. The generated text is the same, faults included: given "Once upon a time, there was a little", greedy GPT-2 writes "girl who was a little girl. She was a little girl. She was a little girl…", the repetition loop that Chapter 9's sampling methods exist to break.

The class also generated text as fast as Hugging Face's at short lengths and much slower at long ones. With a 16-token prompt, each new token took 2.9 ms against 3.5 ms for Hugging Face's model called in the same loop with its KV cache. With a 900-token prompt, ours took 15.2 ms per token and the cached one still 3.5. The generate method reprocesses the whole sequence for every new token; a cache keeps each earlier position's keys and values so only the new token is computed. Chapter 16 adds one.

Use case: converting checkpoints between implementations

Moving weights between codebases is routine: Hugging Face to llama.cpp's GGUF for laptops, a research codebase to a serving engine, an old checkpoint into a new framework. Each conversion is a name map plus layout fixes, exactly like load_gpt2, and each layout fix is a chance for silent garbage. GPT-2's transposed Conv1D is the gentle example. A harsher one is RoPE: Meta's original Llama checkpoints and Hugging Face's implementation pair rotary dimensions differently (Chapter 5), so the conversion script permutes the query and key weights; skip that and the model loads, runs and produces nonsense. The defence is the one used here: after converting, compare logits on a few prompts and the loss on a held-out text with the original. Andrej Karpathy's nanoGPT and llm.c projects verify their GPT-2 reproductions the same way.

⚠️
Common mistakes
  • Forgetting GPT-2's Conv1D transpose; square matrices load silently and compute garbage.
  • Loading lm_head as a separate matrix in a tied model, then training only one copy.
  • Feeding more tokens than ctx; the position table has no rows for them, so assert on it.
  • Declaring a reimplementation correct because it runs; compare logits, greedy tokens and loss against the reference.
  • Expecting bit-identical logits; different summation order gave 10⁻⁴ differences, harmless.
  • Generating long texts by re-running the whole sequence; at 900 tokens it was 4 times slower than with a cache.

Interview drill

Explain it simply: How many parameters does GPT-2 small have, and where are they?

How a strong answer sounds
124.4 million. Per block, attention has four d × d projections and the MLP two d × 4d matrices, so 12d² weights plus small biases and norms: 7.09 million at d = 768, times 12 blocks is 85 million, about two thirds of the model. The token embedding is 50,257 × 768 = 38.6 million, tied with the output layer so it is counted once, and learned positions add 0.79 million. The general formula is V·d + C·d + L(12d² + 13d) + 2d; I checked it against the module for every GPT-2 size and it was exact. Because of the d² term, blocks dominate as models grow: embeddings are 32% of GPT-2 small but 5% of XL.

Deeper: You have reimplemented a model. How do you prove it is correct?

How a strong answer sounds
Load the reference weights into it, handling layout differences such as GPT-2's transposed Conv1D weights or Llama's rotary permutation, then compare against the reference implementation at several levels: maximum absolute logit difference on a few varied prompts (around 1e-4 in fp32 is float reordering, not a bug), the argmax at every position, a few dozen greedy tokens, and the loss on a held-out text. Mine matched GPT-2 to 9e-5 with identical greedy text and identical loss. Before that, two cheap checks catch most bugs: parameter count against a formula, and the loss of a freshly initialised model, which should be close to ln(vocabulary size), 10.82 for GPT-2's vocabulary; mine was 10.97. If something does not match, compare layer by layer with forward hooks to find the first place they diverge.

🧠 Key takeaways

  • A GPT is embeddings, a stack of identical pre-norm blocks, a final norm and a tied output matrix: about a hundred lines.
  • Parameters = V·d + C·d + L(12d² + 13d) + 2d; it matched every GPT-2 size exactly.
  • A fresh model's loss should be near ln(V): 10.97 against 10.82.
  • GPT-2's Conv1D weights need transposing; layout fixes are where conversions silently break.
  • With GPT-2's weights the class matched Hugging Face: logits to 9 × 10⁻⁵, identical greedy text, the same loss of 3.423.
  • Without a KV cache, generation slowed from 2.9 to 15.2 ms per token as the context grew to 900.
