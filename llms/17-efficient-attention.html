Efficient Attention: FlashAttention & Friends

Chapter 4 measured the problem: attention written out step by step stores a T × T table of scores, so its memory grows with the square of the length. This chapter opens up the fixes. FlashAttention computes the same answer in tiles without ever storing the table. Multi-query and grouped-query attention shrink what each decode step has to read. Sliding windows skip most of the table altogether.

FlashAttention's algorithm, written in plain PyTorch, matched the reference to within 0.000001. PyTorch's tiled kernel ran 4,096-token attention 20 times faster than the plain one in a hundredth of the memory, and the plain one could not fit 8,192 tokens at all. At decode time against a 32,768-token cache, sharing key-value heads cut a step from 0.68 to 0.06 milliseconds. And a 512-token sliding window made 16,384-token attention 11 times cheaper.

Why naive attention is memory-bound

Naive attention does three things in turn: multiply queries by keys into a T × T table of scores, softmax every row, multiply by the values. Each step writes its whole result to GPU memory and the next reads it back. For 16 heads at 4,096 tokens that table is 268 million numbers, over a gigabyte in fp32, written and read several times, while the arithmetic per number is tiny. GPUs compute far faster than they move memory (P6), so this version spends its time waiting on memory, and its memory grows with T². Measured below, it needed 4.1 GB for one layer at 4,096 tokens and could not fit 8,192 at all.

FlashAttention's tiling

FlashAttention (Tri Dao and colleagues, 2022) never builds the table. It takes a block of queries, streams blocks of keys and values past it in fast on-chip memory, and keeps three running quantities per query: the largest score seen so far, the softmax denominator so far, and the weighted sum of values so far. When a new block brings a larger maximum, the old sums are rescaled by eold max − new max, so the final result is exactly the softmax over all keys. This running rescale is the online softmax. Only the output, T × d per head, is ever written.

def flash_attention_reference(q, k, v, block=128):              # causal; plain PyTorch, for clarity not speed
    out = torch.empty_like(q)
    for qs in range(0, T, block):
        qb = q[:, :, qs:qs + block] / math.sqrt(d)
        m = torch.full(qb.shape[:-1], -inf)                      # running max per query
        l = torch.zeros(qb.shape[:-1])                           # running softmax denominator
        acc = torch.zeros_like(qb)                                   # running weighted sum of values
        for ks in range(0, qs + block, block):                      # later key blocks skipped: causal
            s = qb @ k[:, :, ks:ks + block].transpose(-2, -1)        # one block × block tile of scores
            s = mask_future(s, qs, ks)
            m_new = torch.maximum(m, s.amax(-1))
            p = torch.exp(s - m_new[..., None])
            corr = torch.exp(m - m_new)                              # rescale what was summed under the old max
            l = l * corr + p.sum(-1)
            acc = acc * corr[..., None] + p @ v[:, :, ks:ks + block]
            m = m_new
        out[:, :, qs:qs + block] = acc / l[..., None]
    return out

On 4 heads of 1,024 tokens this matched F.scaled_dot_product_attention to within 1.1 × 10⁻⁶. Written in Python it is slow; the speed comes from running exactly this loop inside one GPU kernel, where the tiles stay in on-chip memory. The arithmetic is unchanged, still quadratic; what disappears is the memory traffic and the T² storage.

Measured speed and memory

PyTorch's scaled_dot_product_attention chooses among several kernels. The flash kernel is FlashAttention-2; the memory-efficient kernel, from Meta's xFormers, uses the same tiling idea; the math kernel is the naive version. On this machine the flash kernel was not available at all: PyTorch's Windows build reported "No available kernel", so everything ran on the memory-efficient one. Causal attention, 16 heads of 64, bf16, forward pass, with PyTorch capped at 15 GiB so that oversized runs fail rather than spill (Chapter 13):

At 4,096 tokens the tiled kernel was 20 times faster and used a hundredth of the memory; its memory grew in proportion to T, the naive one's with T². At 16,384 tokens it reached about 44 trillion operations per second, under half this GPU's measured matrix-multiply peak. Which kernel runs, and whether a fast one exists for your platform and your mask, can matter more than the algorithm.

Multi-query and grouped-query attention

At decode time attention is a single query per head against the whole cache, and the cost is reading that cache. With every query head owning its key-value head (multi-head), the cache read per step is largest. Grouped-query attention shares each key-value head among a group of query heads; multi-query attention shares one among all. A fast kernel reads each shared head once and applies it to its whole group. For one new token, 32 query heads of 128, against caches of different lengths:

At short caches all three take about the same time: launching the kernels dominates. At 32,768 tokens, multi-head attention was reading its cache at 787 GB/s, essentially the card's whole memory bandwidth, and grouped-query was 2.2 times faster with a quarter of the memory. Multi-query was 12 times faster, but it gives up the most quality, which is why grouped-query, Chapter 15's middle ground, won.

One trap is worth knowing. Asking PyTorch to do the grouping itself, with scaled_dot_product_attention(..., enable_gqa=True), made grouped-query decode slower than multi-head on this build (0.56 against 0.13 ms at 2,048 tokens), because no fast kernel supported that combination and it fell back to a slow path. Chapter 18 hit the same fallback in a full model, which tried to allocate 224 GiB. Time the operation you actually run.

Sliding-window attention

If each token attends only to the previous W tokens, attention's work becomes T × W instead of T² / 2. Information can still travel further than W, one window per layer, so a model with many layers and a window of a few thousand tokens reaches far back. Mistral 7B used a 4,096-token window; Gemma 2 and 3 alternate windowed and full layers. With flex_attention, a window is a one-line mask that skips whole blocks:

window = lambda b, h, q, k: (q >= k) & (q - k < 512)            # causal, and at most 512 back
mask = create_block_mask(window, B=None, H=None, Q_LEN=T, KV_LEN=T)
out = torch.compile(flex_attention)(q, k, v, block_mask=mask)

At 16,384 tokens a 512-token window was 11.5 times cheaper than full attention, and it gets relatively cheaper the longer the sequence. The output matched an explicit masked attention to bf16 precision (0.002). The trade-off is that no single layer sees the whole context, so tasks that need to connect two distant pieces directly can suffer, which is why models mix windowed and full layers.

Use case: why context windows grew

Before 2022, most open models had contexts of 2,048 tokens or less, and attention's T² memory was a large part of why. FlashAttention made exact attention linear in memory and several times faster, and FlashAttention-2 (2023) and -3 (2024, for Hopper GPUs) pushed it close to the hardware's limits. Combined with grouped-query attention to shrink caches and RoPE scaling to stretch positions (Chapter 18), it is a large part of why open models went from 2k to 128k contexts in about two years. For anyone building on these models the practical lesson is in this chapter's measurements: check which attention kernel actually runs on your hardware and with your masks, because a fallback to the naive path can cost an order of magnitude, or all of your memory.

⚠️
Common mistakes
  • Writing attention as matmul, softmax, matmul in production; at 4k tokens it was 20× slower and used 100× the memory.
  • Assuming the fastest kernel runs; this build had no FlashAttention kernel at all.
  • Using enable_gqa=True without timing it; it fell back to a slow path here.
  • Passing an explicit attention mask where is_causal would do; masks often rule out the fast kernels.
  • Expecting tiling to reduce FLOPs; it removes memory traffic, the arithmetic stays quadratic.
  • Using sliding windows everywhere; no layer then sees the whole context directly.

Interview drill

Explain it simply: How does FlashAttention compute exact attention without the T × T matrix?

How a strong answer sounds
It tiles the computation. For a block of queries, it streams blocks of keys and values through the GPU's on-chip memory, computing one tile of scores at a time. For each query it keeps a running maximum, a running softmax denominator and a running weighted sum of values; when a new tile has a larger maximum, it rescales the running sums by the exponential of the difference, so at the end dividing the sum by the denominator gives exactly the softmax-weighted values. Only the output is written to GPU memory. The FLOPs are the same, but memory becomes linear in sequence length and the memory traffic, which dominated, disappears. I wrote the loop in PyTorch and it matched the reference to 1e-6; the real kernel was 20 times faster than naive attention at 4k tokens with a hundredth of the memory.

Deeper: At decode time, why do GQA and MQA speed things up, and why did the industry settle on GQA?

How a strong answer sounds
Decode is one query per head against the whole KV cache, so its cost is reading the cache; it is memory-bound. With fewer key-value heads, there is less cache to read and store, as long as the kernel reads each shared head once for its group of queries. Against a 32k-token cache, multi-head read at the card's full bandwidth and took 0.68 ms per layer; 8 shared KV heads took 0.31 ms and a quarter of the memory; a single shared head 0.06 ms. Multi-query loses noticeably more quality because all heads must agree on one set of keys and values, while grouped-query recovers nearly all of multi-head's quality at most of multi-query's savings, which is why Llama, Qwen and most current models use it.

🧠 Key takeaways

  • Naive attention is limited by memory traffic and T² storage, not arithmetic.
  • FlashAttention tiles keys and values with an online softmax; written from scratch it matched to 1.1 × 10⁻⁶.
  • The tiled kernel was 20× faster at 4k tokens with 1% of the memory; naive attention could not fit 8k.
  • Check which kernel runs: this build had no flash kernel, and flex_attention was twice as fast as the built-in one.
  • At decode against 32k tokens, GQA (8 heads) was 2.2× faster than multi-head and MQA 12×.
  • A 512-token sliding window made 16k-token attention 11.5× cheaper, at the cost of direct long-range links.
