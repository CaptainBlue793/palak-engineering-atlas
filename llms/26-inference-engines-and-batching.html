Inference Engines & Batching

Chapter 16 showed that generating one token for one sequence leaves the GPU mostly idle, and that a batch of 64 costs barely more per step than a batch of 1. An inference engine's job is to turn that into throughput for real traffic, where requests arrive at random times, with different prompt lengths, and finish at different moments.

This chapter builds a small engine from scratch, about 80 lines around Qwen2.5-0.5B-Instruct, and serves the same 64 requests three ways. One at a time it produced 75 tokens a second and the median request waited 77 seconds for its first token. Static batches raised throughput to 993 tokens a second. Continuous batching, where requests join and leave the batch at every step, reached 1,115 and cut the median wait to 0.02 seconds. It also showed that batched bf16 outputs are not the same as unbatched ones, and why.

  • Serve requests one at a time, in static batches and with continuous batching
  • Measure throughput, time to first token and end-to-end latency under load
  • Explain why continuous batching wins on both throughput and waiting time
  • Estimate KV memory under contiguous and paged allocation
  • Know why batched outputs can differ from unbatched ones

One request at a time

The test: 64 prompts from UltraFeedback's held-out set (35 to 301 tokens, median 73), each answered greedily with up to 256 new tokens; 42 of the 64 replies ran to that limit. Requests arrive as a Poisson stream, at 2 or 8 a second, or all at once. Served one at a time, a request is prefilled (its whole prompt in one forward pass, Chapter 16) and then decoded token by token until it ends. A single sequence decoded at about 75 tokens a second, 13 ms a token, much of it Python and kernel-launch overhead in the model's forward pass rather than arithmetic.

That rate does not change with load, so the queue grows. At 8 requests a second the 64 requests arrived within 8 seconds and the last finished 163 seconds after the start; the median request waited 77 seconds before its first token and 80 seconds for its whole reply. For an interactive product that is a failure, even though the GPU was "busy" the whole time.

Static batching

Static batching collects the requests that are waiting, up to 32, prefills each, and decodes them together, one token for every sequence per step. The batch keeps going until its last sequence finishes; only then are new requests admitted. Sequences that end early sit idle in the batch, and requests that arrive meanwhile wait for the whole batch.

Batches are left-padded to a common length so that every sequence's newest token is in the same column; an attention mask hides the padding, and each sequence keeps its own position numbers, so its rotary positions are unaffected. At 8 requests a second static batching produced 993 tokens a second, 13 times the one-at-a-time rate, but the median request still waited 2.2 seconds for its first token, and 4.5 seconds at the 95th percentile, because it arrived while a batch was running.

Continuous batching

Continuous batching, introduced by the Orca system in 2022 and used by every major engine since, admits waiting requests and retires finished ones at every decode step. A new request is prefilled and joins the running batch at the next step; a finished one leaves at once, freeing its slot. The whole scheduler is a loop:

while waiting or batch.seqs:
    for s in [s for s in waiting if s.arrival <= now()][:max_batch - len(batch.seqs)]:
        first, kv = prefill(s.prompt)                    # first token now: this sets time to first token
        batch.add(s, kv); waiting.remove(s)            # left-pad caches to a common length
    for s, t in zip(batch.seqs, batch.step()):          # one token for every running sequence
        s.out.append(t)
    batch.remove([i for i, s in enumerate(batch.seqs) if finished(s)])   # leave at once

With all 64 requests arriving at once, continuous batching finished in 9.2 seconds at 1,322 tokens a second, 18 times faster than one at a time, though the median request then waited 0.66 seconds for a free slot, since only 32 fit at once.

Throughput vs time to first token

Two numbers describe a serving system, and users feel them differently. Time to first token (TTFT) is how long before anything appears; it is set by queueing plus the prefill of the prompt. Time per output token is how fast the text then streams; it is set by the decode step, which grows slowly with batch size. Throughput is what the operator pays for. Static batching trades TTFT for throughput; continuous batching improved both here, because it never holds a slot for a finished sequence or a waiting request for a running batch.

The trade does not disappear, it moves. Larger batches raise throughput and slow every step, so engines cap the batch size, and a long prompt's prefill delays every running sequence's next token while it runs. Engines such as vLLM and SGLang split long prefills into chunks interleaved with decode steps, and some systems run prefill and decode on separate GPUs. Service targets are usually set on the 95th or 99th percentile of both TTFT and time per output token, not the median.

Paged attention

Every running sequence needs its KV cache, 12,288 bytes a token for this model (Chapter 16). Early engines allocated each request's cache as one contiguous block sized for the longest it might become. For the 64 requests here, measured from their real lengths:

Paged attention (vLLM, 2023) borrows virtual memory's idea: the cache is split into fixed blocks of, say, 16 tokens, allocated on demand as a sequence grows, and a per-sequence block table maps positions to blocks anywhere in memory. Waste is then at most one partly filled block per sequence, 2.6% here, so far more sequences fit in the same memory, which is what lets the batch, and so the throughput, grow. Shared blocks also let requests with a common prefix, such as one system prompt, share its cache. The engine here does not page: it pads every sequence's cache to the longest in the batch, which is exactly the kind of waste paging removes, and its cache peaked at 184 MB for 32 sequences.

Batching changes the numbers

One check did not come out clean. With greedy decoding, the same request should give the same tokens whether it runs alone or in a batch, but in bf16 only 17 of the 64 did. On 32 requests the first differing token came anywhere from position 4 to 239, median 68. Run in fp32, all 32 were identical, so the engine's masking and positions are right and the cause is arithmetic: a batched matrix multiply may add the same numbers in a different order, bf16 keeps about 3 significant digits, and when two candidate tokens are nearly tied a rounding difference flips the choice, after which the two replies go their own ways. Production engines behave the same way. Outputs depend on what else is in the batch unless the kernels are specifically written to be batch-invariant, which matters for anyone who expects a fixed prompt and temperature 0 to be reproducible.

Use case: serving a chat model to many users

Every hosted chat product runs an engine like vLLM, SGLang, TensorRT-LLM or Hugging Face's TGI, and all of them do continuous batching with paged KV memory, because the measurements here are what the economics look like: the difference between 75 and 1,115 tokens a second on the same GPU is the difference between one GPU per few users and one per hundreds. Operators then tune the maximum batch size and prefill chunking against their latency targets, add prefix caching for shared system prompts, and watch the 95th-percentile time to first token, which is what users notice first.

⚠️
Common mistakes
  • Serving one request at a time; the median request waited 77 seconds for its first token at 8 a second.
  • Judging an engine by throughput alone; static batching reached 993 tok/s but kept requests waiting 2.2 seconds.
  • Reserving KV memory for the full context; that wasted 99.1% here, paging 2.6%.
  • Reporting medians only; service targets are set on the 95th or 99th percentile.
  • Expecting temperature 0 to be reproducible across batch sizes; 17 of 64 bf16 replies matched.
  • Getting positions wrong in a padded batch; each sequence needs its own position numbers.

Interview drill

Explain it simply: What is continuous batching, and why does it help?

How a strong answer sounds
Decoding one token for one sequence leaves a GPU mostly idle, so engines decode many sequences together. Static batching forms a batch, runs it until every sequence finishes, and only then admits new requests, so finished sequences waste slots and new requests wait. Continuous batching makes scheduling decisions every decode step: finished sequences leave immediately and waiting requests are prefilled and join at the next step. In my from-scratch engine on Qwen2.5-0.5B, serving 64 requests arriving at 8 a second, one-at-a-time gave 75 tokens a second with a 77-second median wait for the first token; static batches of 32 gave 993 tokens a second and a 2.2-second wait; continuous batching gave 1,115 tokens a second and a 0.02-second wait.

Deeper: Why does vLLM page the KV cache, and what does it buy?

How a strong answer sounds
Because the cache is the memory that limits batch size, and a request's final length is unknown when it starts. Contiguous allocation has to reserve for the worst case: for my 64 requests, reserving the full 32k context would have needed 24 GB for 220 MB of real cache, 99.1% waste, and even reserving prompt plus the 256-token limit wasted 18%. Paging allocates fixed blocks of, say, 16 tokens on demand through a block table, so waste is at most one partial block per sequence, 2.6% here. That lets many more sequences run at once, which raises throughput, and blocks can be shared between requests with the same prefix. The cost is an attention kernel that gathers keys and values through the block table.

🧠 Key takeaways

  • One request at a time wastes the GPU: 75 tok/s and a 77-second median wait at 8 requests a second.
  • Static batching raised throughput 13 times but kept requests waiting for the running batch (2.2 s).
  • Continuous batching admits and retires every step: 1,115 tok/s and 0.02 s to the first token.
  • Time to first token and time per token are separate targets; watch their 95th percentiles.
  • Paged KV memory wasted 2.6% where full-context reservation would have wasted 99.1%.
  • Batched bf16 outputs can differ from unbatched ones (17 of 64 matched; fp32 matched 32 of 32).
