Linear Layers, Softmax & Cross-Entropy

A transformer is assembled from a handful of parts that this course will use in every chapter: linear layers that mix numbers, activations that bend them, normalisation that keeps them in range, and at the very end a softmax that turns scores into probabilities and a cross-entropy loss that says how wrong those probabilities were.

Each part is a few lines of code, and each has a numerical trap. This chapter opens up GPT-2 to look at real values instead of toy ones: logits so negative that the textbook softmax returns NaN in every precision, a loss that moves by 0.42 when it is computed in bf16, and a residual stream whose largest value grows from 1.2 to 92.7 on its way through the model.

  • Write a softmax that cannot overflow or underflow, and explain why the naive one does
  • Compute and interpret cross-entropy, including what its value at step zero should be
  • Explain what LayerNorm and RMSNorm do to a vector, and why models need them

Linear layers as matrix multiplies

A linear layer computes y = x Wᵀ + b. Each output number is a weighted sum of every input number, plus a bias. nn.Linear(768, 3072), the first layer of GPT-2's MLP block, stores a weight of shape (3072, 768) and a bias of 3,072: 2,362,368 parameters. Applied to activations of shape (B, T, 768), it acts on the last dimension only, so every token is transformed independently by the same weights.

lin = nn.Linear(768, 3072).to("cuda")
x = torch.randn(4, 128, 768, device="cuda")       # (B, T, C)
y = lin(x)                                          # (B, T, 3072)
(y - (x @ lin.weight.T + lin.bias)).abs().max()       # 0.0: it is exactly a matmul plus a bias

The cost is one multiply and one add per weight per token: 2 × 768 × 3,072 ≈ 4.7 million FLOPs per token for this layer. Almost all of a language model's parameters and compute live in layers like this one, which is why the matrix-multiply speeds in P1 decide how fast a model trains.

Activations: ReLU, GELU and SiLU

Stacking linear layers alone gives another linear layer, however many you stack. An activation function between them bends the output, which is what lets a network represent anything interesting. Transformers use smooth relatives of ReLU:

GELU multiplies x by the probability Φ(x) that a standard normal value is below x. Computing Φ exactly needs the error function, so GPT-2 used a tanh formula instead; across −6 to 6 the two differ by at most 0.00047. That gap matters only when you load weights trained with one into code that uses the other, which is a real way to get slightly wrong outputs from a correctly loaded model. Hugging Face calls GPT-2's version gelu_new for exactly this reason.

Softmax and the NaN it hides

The last layer of a language model outputs one score, a logit, per vocabulary entry. Softmax turns logits into probabilities: exponentiate each one, then divide by the sum, so the results are positive and add up to 1. Written directly from that definition, it looks harmless:

def naive_softmax(z):                 # z: (V,) logits
    e = torch.exp(z)
    return e / e.sum()

def stable_softmax(z):
    e = torch.exp(z - z.max())           # largest exponent is now exp(0) = 1
    return e / e.sum()

Now feed them GPT-2's real logits for the next token after "The server returned HTTP status code". All 50,257 of them are large and negative: from −124.0 (for " 200") down to −156.3. exp(−124) is about 10⁻⁵⁴, far below the smallest number fp32 can hold (about 1.4 × 10⁻⁴⁵), so every exponential becomes exactly zero, the sum is zero, and 0 / 0 is NaN. The naive softmax returned NaN in fp32, bf16 and fp16 alike. The overflow version of the same failure happens at the other end: exp(x) becomes infinite once x passes 88.7 in fp32 and bf16, and just 11.1 in fp16.

Subtracting the largest logit first changes nothing mathematically, because softmax only depends on differences between logits, but it puts the biggest exponent at exactly 1, so the sum can never be zero or infinite. The stable version gave " 200" a probability of 0.15925 in fp32, matching PyTorch's own torch.softmax, which does the same subtraction internally. Shifting every logit up by 100 gave a bit-for-bit identical stable result. In bf16 the top probability came out at 0.157 (an error of up to 0.005 on individual probabilities), and in fp16 even the stable version rounded 33,895 of the 50,257 probabilities to exactly zero.

Cross-entropy

Training needs one number that says how wrong the probabilities were. Cross-entropy takes the probability the model gave the token that actually came next and returns its negative logarithm: −log p(correct token). A confident right answer (p near 1) costs almost nothing; a token given probability 0.0001 costs 9.2. Averaged over every position of every sequence, it is the loss every language model in this course is trained on.

ids = tok(sentence, return_tensors="pt").input_ids.to("cuda")   # (1, T)
logits = gpt2(ids).logits[0]                                    # (T, V): a prediction at every position
loss = F.cross_entropy(logits[:-1], ids[0, 1:], reduction="none") # (T-1,): position t predicts token t+1

For the sentence "The server returned HTTP status code 200 and the request completed in 35 ms.", GPT-2's per-token losses were:

Two reference points make a loss value readable. A model that spreads probability evenly over all 50,257 tokens scores ln(50,257) = 10.82 on every token, and a freshly initialised language-model head scored 11.02, so a new model's loss should start just above ln(vocabulary size); one that starts far higher has a bug in its initialisation. And GPT-2's 3.88 means that, on average, the right token got a probability of about e⁻³·⁸⁸ ≈ 0.02 (P4 turns this into perplexity).

F.cross_entropy takes logits, not probabilities, and matched the manual −log(softmax) exactly here. It also needs them in fp32. GPT-2's logits are around −124 to −156, where bf16 can only represent values in steps of 0.5 (below 128) or 1 (above), so the differences between logits that decide the probabilities are rounded away. Computed from bf16 logits, the mean loss moved from 3.879 to 3.853 and one token's loss moved by 0.42. That is why training code casts logits to fp32 before the loss even when everything else runs in bf16.

LayerNorm and RMSNorm

Each transformer block adds its output to a running vector, the residual stream (Chapter 6), so values can grow from block to block. In GPT-2, for the last token of the same prompt, the largest absolute value grew from 1.2 in the embeddings to 41.7 after six blocks and 92.7 after eleven, with a single dimension (447) responsible for that 41.7. A layer fed vectors whose size changes that much from layer to layer is hard to train. Normalisation rescales each token's vector before a block reads it.

def layer_norm(x, eps=1e-5):                              # x: (..., C)
    mu = x.mean(-1, keepdim=True)
    var = x.var(-1, keepdim=True, unbiased=False)
    return (x - mu) / torch.sqrt(var + eps)                   # then × gain + bias (learned)

def rms_norm(x, eps=1e-6):
    return x / torch.sqrt(x.pow(2).mean(-1, keepdim=True) + eps)   # then × gain (learned)

Both bring a vector of RMS 3.09 back to RMS 1.0. RMSNorm skips the mean, which is close to zero anyway for these vectors, and the bias, and in practice trains as well. On this GPU at this size the two took almost the same time, so the reason models switched is simplicity rather than a large speed-up here. Normalisation does not remove the outlier: dimension 447 is still the largest value afterwards, just scaled down with everything else.

🧾
Use case: Llama's switch to RMSNorm

The 2019 RMSNorm paper by Zhang and Sennrich argued that LayerNorm's re-centring (subtracting the mean) contributes little and that rescaling alone is enough. Meta's Llama models adopted RMSNorm, applied before each block rather than after, and most open models since (Mistral, Qwen, Gemma) followed. The measurement on this page is a fair summary of the trade: on a GPT-2-sized tensor the two cost almost the same, and RMSNorm produced the same scale with one fewer statistic and no bias. Chapter 15 opens a current open model and finds it in every block.

⚠️
Common mistakes
  • Writing softmax as exp(z) / exp(z).sum(), which returned NaN on GPT-2's real logits in every precision.
  • Passing probabilities to F.cross_entropy, which expects raw logits and applies log-softmax itself.
  • Computing the loss from bf16 logits; cast logits to fp32 first, or individual losses move by tenths of a nat.
  • Ignoring a first-step loss far above ln(vocabulary size), which usually means a bad initialisation scale.
  • Loading weights trained with one GELU variant into code using the other, and getting slightly different outputs.
  • Forgetting that normalisation has learned weights; a norm "without parameters" in your code will not match a trained model's.

Interview drill

Explain it simply: Why do softmax implementations subtract the maximum logit, and what goes wrong if they don't?

How a strong answer sounds
Softmax depends only on the differences between logits, so subtracting any constant leaves the result unchanged. Subtracting the maximum makes the largest exponent exactly exp(0) = 1 and every other one smaller, so nothing can overflow and the sum is at least 1, so it can never be zero. Without it, large positive logits overflow: exp becomes infinite above about 88.7 in fp32 and only 11.1 in fp16, and inf divided by inf is NaN. Large negative logits fail too, which surprises people: GPT-2's real next-token logits are all around −124 to −156, every exp underflows to zero in fp32, and the naive softmax returns 0 / 0 = NaN. In practice you rarely write it yourself: torch.softmax and F.cross_entropy both do the subtraction, and the loss works from log-probabilities directly.

Deeper: You start training a language model with a 50,257-token vocabulary and the loss at step 0 is 11.0. Is that a good sign? What would worry you?

How a strong answer sounds
It is what you want. A model that knows nothing should spread probability almost evenly over the vocabulary, and a uniform distribution gives a cross-entropy of ln(50,257) ≈ 10.82 on every token; a freshly initialised head measured 11.02. A loss well above that, say 30 or 50, means the initial logits are far too large, so the model is confidently wrong from the start: typically an initialisation scale or a missing normalisation, and it often leads to instability. A loss well below ln(V) at step zero is also suspicious: the targets may be leaking into the inputs, for example through a missing shift between inputs and labels or a missing causal mask. Later in training, the number is read through perplexity, the exponential of the loss.

🧠 Key takeaways

  • A linear layer is x Wᵀ + b on the last dimension; nn.Linear(768, 3072) has 2.36 million parameters and costs about 4.7 MFLOPs per token.
  • Transformers use smooth activations: GELU in GPT-2, SiLU inside SwiGLU in Llama-style models.
  • Always subtract the max inside softmax; on GPT-2's real logits (−124 to −156) the naive version underflowed to 0/0 = NaN in every precision.
  • Cross-entropy is −log p(correct token); a new model should start near ln(vocab), 10.82 for GPT-2's vocabulary.
  • Compute logits and the loss in fp32: from bf16 logits one token's loss moved by 0.42.
  • LayerNorm and RMSNorm rescale each token's vector to unit size; RMSNorm drops the mean and the bias and is what current open models use.

Check your understanding

The naive softmax exp(z) / exp(z).sum() returned NaN on GPT-2's next-token logits even in fp32. Why?

exp(−124) ≈ 10⁻⁵⁴ is far below fp32's smallest value. Subtracting the max (−124.0) puts the largest term at exp(0) = 1.

Above roughly what value does exp(x) overflow to infinity in fp16?

fp16's largest value is 65,504, and ln(65,504) ≈ 11.09. In fp32 and bf16 the limit is about 88.7.

GPT-2 gave the correct next token a probability of 0.1592. What is that token's cross-entropy loss?

−ln(0.1592) ≈ 1.84 nats, the value measured for " 200".

A new language model with a 50,257-token vocabulary should have a loss close to what at step zero?

Near-uniform predictions score ln(V) on every token; a freshly initialised head measured 11.02.

How does RMSNorm differ from LayerNorm?

Both act on each token's vector. RMSNorm keeps only the rescaling and a learned gain; on GPT-2's vector the mean was already near zero (0.03).
