What a Language Model Is

A large language model does one thing: given the tokens so far, it produces a probability for every token that could come next. Answering questions, writing code, following instructions and chatting are all built from repeating that single step. Understanding exactly what that step is, and what it is not, explains most of what surprises people about these models.

This chapter shows it with four real models and 20 questions any engineer could answer, such as "What port does HTTPS use by default?". GPT-2 answered two of them. A small base model turned half of them into multiple-choice exam questions. An instruction-tuned model answered all 20, but only when the question was wrapped in the exact template it was trained on; without it, it behaved like the base model half the time.

Next-token prediction

A language model takes a sequence of token ids and returns, for the position after the last one, a score for every token in its vocabulary. Softmax turns the scores into probabilities (P3). That distribution is the model's entire output; everything else is code around it. Given the chat-formatted question "What port does HTTPS use by default?", Qwen2.5-1.5B-Instruct put 82.2% on "HTTPS" as the first token of its reply, 9.8% on "The" and 3.2% on "By". It has not decided what to say yet. It has only said what is likely to come next.

ids = tok(prompt, return_tensors="pt").input_ids.to("cuda")   # (1, T) the text so far
logits = model(ids).logits[0, -1]                            # (V,) one score per token, V = 151,936 for Qwen2.5
probs = torch.softmax(logits.float(), -1)                      # (V,) the model's whole answer to "what comes next?"

The model was trained for exactly this: shown billions of tokens of text, it was asked at every position to predict the next token, and adjusted to make the real next token more probable (Chapter 8). Nothing in that objective says "answer questions" or "be correct". A model learns to answer because answers often follow questions in its training data; it learns facts because predicting text well requires them. Both are side effects of prediction, which is why they fail in the ways this chapter shows.

Generating by repeating it

To produce text, pick one token from the distribution, append it, and ask again. This is autoregressive generation. The simplest choice is to pick the most likely token every time, greedy decoding; Chapter 9 covers sampling instead. A cache of each layer's keys and values means each step only processes the one new token (Chapter 16):

@torch.no_grad()
def generate(model, tok, prompt: str, max_new: int = 40) -> str:
    ids = tok(prompt, return_tensors="pt").input_ids.to("cuda")    # (1, T)
    out = model(ids, use_cache=True)                                  # read the whole prompt once
    new = []
    for _ in range(max_new):
        nxt = int(out.logits[0, -1].argmax())                         # greedy: the single most likely token
        if nxt == tok.eos_token_id:                                   # the model predicted "end of text"
            break
        new.append(nxt)
        out = model(torch.tensor([[nxt]], device="cuda"), past_key_values=out.past_key_values, use_cache=True)
    return tok.decode(new)

Generation stops only when the model predicts a special end-of-sequence token or your code hits a limit. Stopping is something the model has to learn. GPT-2 never once predicted an end within 40 tokens; every one of its 40 answers ran to the limit. Qwen2.5-1.5B-Instruct, using its chat template, stopped on its own in 18 of 20 answers, after an average of 16 tokens.

Base models and chat models

A base model has only been trained to continue text, so it continues whatever document your prompt looks like the start of. An instruction-tuned (chat) model has been further trained on conversations (Chapters 19 to 24), each wrapped in a chat template that marks who is speaking (P8, Chapter 20). The same question, asked of four models in three formats (the bare question; "Question: … Answer:"; and the model's chat template), with greedy decoding and 40 new tokens:

"Answered" means the first line of the output contained the right answer, without multiple-choice options. "Buried" means the right answer appeared somewhere but not as an answer. Four behaviours stand out:

  • GPT-2 continued, wrongly. Asked about HTTPS it wrote "HTTPS uses the HTTP protocol. The default port is 8080." and then repeated the question. It answered only "What does DNS stand for?" and the HTTP-method question.
  • The base model turned questions into exam papers. Given only "What port does HTTPS use by default?", Qwen2.5-0.5B's most likely next tokens were blanks ("__", "____") and it wrote "____ A. 443 B. 80 C. 23 D. 21 Answer: A", then started an unrelated question about cold fronts. The right answer is there, but as part of a continued document, not a reply. Its training data clearly contained many such exam papers.
  • A base model with a chat template answers but cannot stop. With Qwen's template, the base model wrote "HTTPS uses port 443 by default." and then emitted stray tokens and new questions, because it never learnt what follows the end of a turn.
  • An instruction-tuned model without its template is half a base model. Given the bare question, both instruct models produced the same exam-paper continuation in about half the questions. Only with the template did they answer every one.

Instruction tuning did not teach these models the port numbers; the base model already knew 443. It taught them a behaviour, answering and then stopping, that switches on when the input looks like the conversations it was trained on. That is why the chat template is part of the model, not a formatting detail.

Use case: from GPT-3 to ChatGPT

GPT-3 (2020) was a base model offered through an API that completed text. To get an answer you wrote the beginning of a document in which the answer would naturally appear, often with a few worked examples first, exactly like the "Question: … Answer:" format on this page. In 2022 OpenAI published InstructGPT, the same family fine-tuned on demonstrations and human preferences to follow instructions, and ChatGPT, released that November, was a sibling of it trained for conversation. The knowledge was largely already in the base models; what changed is the behaviour measured here, answering and stopping, which made the model usable by anyone who could type a question. Chapters 19, 23 and 24 rebuild that recipe on a small model.

⚠️
Common mistakes
  • Sending a bare question to an instruction-tuned model without its chat template; it answered cleanly only half the time.
  • Using a base model as a chatbot and expecting it to answer and stop rather than continue a document.
  • Treating the most likely first token as the model's "decision"; it only predicts the next token, one at a time.
  • Assuming the model knows when to stop; without the right end-of-sequence token and a length limit, it may never stop.
  • Judging a model on one prompt format when the same model scored from 10 to 20 of 20 across three formats.
  • Crediting instruction tuning with the facts, when the base model already knew them; tuning changed the behaviour.

Interview drill

Explain it simply: An engineer asks what actually happens when a chat model "answers" a question. Explain it without hand-waving.

How a strong answer sounds
The conversation is formatted with a chat template into one sequence of tokens, ending with the marker for the assistant's turn. The model reads the whole sequence and outputs a probability for every token in its vocabulary as the next one. Code picks one token, either the most likely or a sample, appends it, and runs the model again, now with one more token; a cache of earlier keys and values makes each step cheap. This repeats until the model predicts its end-of-turn token or a length limit is hit, and the chosen tokens are decoded to text. The model never plans the whole answer: each token is chosen knowing only what came before it. Instruction tuning is what makes "answer, then end the turn" the likely continuation when the input looks like a conversation; a base model given the same input tends to continue the document instead.

Deeper: You deploy a small open model and it answers correctly but then keeps writing new questions and odd tokens, or never stops. What could be wrong?

How a strong answer sounds
Most likely the model, template and stop tokens do not match. If it is a base model, it was never trained to end a turn: with a chat template it will answer and then continue, which is exactly what Qwen2.5-0.5B base did, emitting stray tokens and new questions. If it is an instruction-tuned model, check that the prompt uses its own chat template and that generation stops on its end-of-turn token: Qwen's instruct models end turns with <|im_end|>, not the base model's <|endoftext|>, so a generation config copied from the base repository will not stop. Also check that the tokeniser and generation config come from the same repository and revision as the weights, and set a maximum number of new tokens as a safety net. Then test on a fixed set of prompts with greedy decoding so the fix can be measured.

🧠 Key takeaways

  • A language model outputs one thing: a probability for every possible next token.
  • Generation repeats that step, appending one token at a time, until an end-of-sequence token or a limit.
  • Base models continue documents: GPT-2 answered 2 of 20 questions; Qwen2.5-0.5B often wrote an exam paper instead of an answer.
  • Instruction-tuned models answer and stop, but only reliably with their own chat template: 20 of 20 with it, 10 without.
  • Instruction tuning changes behaviour more than knowledge; the base model already knew HTTPS uses port 443.
