Autograd & the Training Loop

Training a language model with billions of parameters uses the same loop as fitting a straight line: compute a loss, ask how the loss changes with each parameter, nudge every parameter a little in the direction that lowers it, and repeat. PyTorch's autograd computes the "how the loss changes" part for you, for any code you write, which is the only reason models with billions of parameters are trainable at all.

This chapter builds that loop on a problem small enough to see whole, predicting a request's latency from its payload size, then measures where it breaks: a learning rate 20% too large that sends the loss to infinity, a forgotten line that leaves the loss almost where it started, and a one-character shape bug that a five-second check catches.

Computation graphs and backward()

The problem: 256 requests, each with a payload size and a measured latency. The latency is roughly 12 ms plus 0.35 ms per kilobyte, plus noise, and we want the model latency = w · payload + b to find w and b. Payload is in units of 100 KB, so the true slope is 35 ms per unit. The loss is the mean squared error (MSE) between prediction and measurement.

x = torch.rand(256, device="cuda") * 5                       # (N,) payload, 0–500 KB in units of 100 KB
y = 12 + 35 * x + torch.randn(256, device="cuda") * 8       # (N,) latency in ms, noisy

w = torch.tensor(1.0, device="cuda", requires_grad=True)   # () parameters we want gradients for
b = torch.tensor(0.0, device="cuda", requires_grad=True)
loss = ((w * x + b - y) ** 2).mean()                      # () a single number: 12,939.6
loss.backward()                                          # fills w.grad and b.grad
print(w.grad, b.grad)                                     # -682.5569  -204.3348

Because w and b were created with requires_grad=True, every operation on them was recorded in a computation graph. Each result keeps a grad_fn pointing at the operation that made it; for this loss the chain is MeanBackward0 → PowBackward0 → SubBackward0 → AddBackward0 → MulBackward0. backward() walks that chain from the loss back to the parameters, applying the chain rule at each step, and stores ∂loss/∂w in w.grad and ∂loss/∂b in b.grad.

A gradient is just a number you can check. Differentiating MSE by hand gives ∂loss/∂w = mean(2 · (prediction − y) · x), and that formula gave exactly −682.5569 and −204.3348, the same as autograd. A finite difference, nudging w by ±0.001 and measuring how the loss moves, gave −682.62 and −204.35: the same to four significant figures. The negative sign says increasing w lowers the loss, which is right, since the prediction (slope 1) is far below the data (slope 35).

The cost column is the important one. A finite difference needs two forward passes per parameter, so for a model with 124 million parameters it would need 248 million forward passes per step. Reverse-mode autograd gets every gradient from one backward pass, which costs roughly two forward passes no matter how many parameters there are.

Gradient descent by hand

Gradient descent moves each parameter a small step against its gradient: w ← w − lr · w.grad, where lr, the learning rate, sets the step size. The update itself must not be recorded in the graph, so it runs under torch.no_grad():

for step in range(200):
    loss = ((w * x + b - y) ** 2).mean()   # forward
    loss.backward()                       # gradients
    with torch.no_grad():                  # the update is not part of the model
        w -= lr * w.grad
        b -= lr * b.grad
    w.grad = None; b.grad = None            # clear, or the next backward() adds to them

Too small a learning rate wastes steps; too large a one diverges. For a squared-error loss there is an exact limit: plain gradient descent is stable only if the learning rate is below 2 divided by the largest curvature of the loss (the largest eigenvalue of its second-derivative matrix, the Hessian). For this data that curvature is 19.71, so the limit is 0.1015. Measured over 200 steps from w = b = 0:

  • lr 0.001: loss 65.1 after 200 steps; slow, and b was still 10.6 instead of 12.9.
  • lr 0.05: loss 59.07, the least-squares optimum, by step 199 (and 59.9 by step 10).
  • lr 0.1: just under the limit; the loss swung around (7,561 at step 10) but settled at 59.17.
  • lr 0.12: 18% over the limit; 6.8 million at step 10, then infinity. w ended at −3.8 × 10²⁸.

Real models have no closed-form limit, but they have the same behaviour: a learning rate that works, one slightly above it that blows up, and a loss spike or NaN as the symptom. Chapter 14 covers warm-up, schedules and clipping, the tools that keep large models on the stable side.

nn.Module and parameters

Writing w and b by hand does not scale to a transformer. PyTorch's nn.Module holds parameters for you, nn.Linear(16, 64) creates a 64 × 16 weight matrix and a bias with requires_grad=True, and an optimiser applies the update rule to every parameter the module lists:

import torch.nn as nn

net = nn.Sequential(nn.Linear(16, 64), nn.GELU(), nn.Linear(64, 1)).to("cuda")   # 1,153 parameters
opt = torch.optim.Adam(net.parameters(), lr=1e-2)          # holds the update rule and its state
print(sum(p.numel() for p in net.parameters()))                  # 16·64 + 64 + 64·1 + 1 = 1,153

torch.optim.SGD is exactly the update you just wrote. Adam, and its variant AdamW used for every transformer in this course, keep two running averages per parameter and scale each step individually, which makes them far less sensitive to the learning rate (Chapter 14). Those running averages are also why training needs much more memory than inference (P7).

The training loop

Every training run in this course, from this one to a fine-tune of a billion-parameter model, is the same five lines repeated:

for xb, yb in batches:
    opt.zero_grad()                      # 1. clear the gradients from the last step
    pred = net(xb).squeeze(1)               # 2. forward: (B, 1) → (B,)
    loss = ((pred - yb) ** 2).mean()      # 3. loss: one number
    loss.backward()                      # 4. backward: a gradient for every parameter
    opt.step()                           # 5. update every parameter

Line 1 is the one people forget. backward() adds to .grad rather than replacing it, so that gradients from several small batches can be summed on purpose (gradient accumulation, Chapter 13). Leave out zero_grad() and every step uses the sum of all gradients so far, which behaves like an ever-growing step. On the latency problem, at a learning rate that worked well with it (0.01, final loss 59.3), the loop without it ended at 748; at 0.001 it ended at 13,551, barely below the 13,631 it started from, where the correct loop had reached 65.

Overfitting one batch on purpose

Before any long run, train on a single small batch until the loss reaches nearly zero. A model with enough parameters can memorise 32 examples, so if it cannot, something in the data, the loss or the loop is wrong, and you have found it in seconds instead of after a day of training.

The test here is the small network above on one batch of 32 random inputs and targets, with Adam. Correctly written, the loss was below 0.001 at step 47 and 0.0 at step 500. Then the same run with the bug from P1: the prediction left as shape (32, 1) against targets of shape (32,). Nothing crashed. The loss fell a little and then stopped at 0.6424 for good, which is exactly the variance of the targets: the broadcast loss compares every prediction with every target, and the best the model can do against that is predict the mean for everything. A loss stuck at the variance of the targets is a signature worth remembering.

What autograd costs

To compute gradients, the backward pass needs the intermediate values of the forward pass, so autograd keeps them alive until backward() runs. For a stack of four 4096-wide linear layers (67 million parameters, 128 MiB of bf16 weights) on a batch of 8,192 rows, the forward pass under torch.no_grad() raised peak memory by 128 MiB and took 11.9 ms. With gradients, forward plus backward raised it by 704 MiB and took 33.7 ms. The 704 MiB is seven saved activations of 64 MiB (448 MiB), the 128 MiB fp32 copy of the output that the loss was computed from, and 128 MiB of weight gradients; the backward pass cost about twice the forward. Inference code should always run under torch.no_grad() (or torch.inference_mode()), and P7 turns these numbers into a full memory budget.

Use case: "overfit a single batch" in Karpathy's training recipe

Andrej Karpathy's widely shared 2019 post, "A Recipe for Training Neural Networks", lists overfitting one batch as an early, non-negotiable step: take a few examples, make the model's capacity large enough, and verify that the loss goes to zero. If it does not, there is a bug, and it is far cheaper to find it there than in a run that takes days. The broadcasting bug on this page is exactly the kind of mistake it catches: the full training run would have produced a plausible-looking loss curve, while the one-batch test stopped at the targets' variance and pointed straight at the loss.

⚠️
Common mistakes
  • Forgetting zero_grad(), so every step uses the sum of all gradients so far.
  • Updating parameters outside torch.no_grad(), which records the update in the graph or raises an error about leaf tensors.
  • Raising the learning rate "to train faster" past the point where the loss diverges.
  • Starting a long run without overfitting one batch first, so shape and loss bugs surface days later, or never.
  • Running inference with gradients on, paying several times the memory for activations nobody will use.
  • Calling .item() on the loss inside a hot loop without knowing it forces a GPU synchronise each time (P1).

Interview drill

Explain it simply: What does loss.backward() do, and why does a training loop call optimizer.zero_grad() every step?

How a strong answer sounds
While the forward pass runs, PyTorch records every operation on tensors that require gradients as a graph. backward() walks that graph from the loss back to the parameters, applying the chain rule at each operation, and stores the derivative of the loss with respect to each parameter in its .grad. It does this for all parameters at once for roughly the cost of two forward passes. It adds into .grad rather than overwriting it, so that gradients from several micro-batches can be accumulated deliberately. That is why the loop clears them with zero_grad() each step; without it, each update uses the sum of every gradient so far, the effective step keeps growing and the loss oscillates; in a measured run it ended at 13,551, barely below its starting 13,631, where the correct loop reached 65.

Deeper: Your training loss goes to NaN after a few hundred steps. How do you investigate?

How a strong answer sounds
First reproduce it cheaply and look at when it happens: log the loss and the gradient norm every step. A loss that grows quickly before NaN points at the learning rate being above the stable range, as in a simple model where 0.1 converged and 0.12 exploded, so lower it, add warm-up, and clip the gradient norm. A sudden spike on one step points at a bad batch or an overflow, so log the batch, check for extreme values, and check dtypes, because fp16 overflows at 65,504. Also check the basics with an overfit-one-batch run: if the model cannot drive one batch to zero loss, the problem is in the data, the loss or the shapes rather than the optimiser. Finally, use torch.autograd.set_detect_anomaly(True) on a short run to find the first operation that produced a NaN.

🧠 Key takeaways

  • Autograd records operations as a graph and backward() applies the chain rule through it, giving every gradient for about the cost of two forward passes.
  • Check gradients you doubt: by hand, by finite differences, and against autograd. Here all three agreed.
  • Gradient descent diverges above a learning-rate limit: here 0.1 converged and 0.12 went to infinity.
  • The loop is zero_grad, forward, loss, backward, step; forgetting zero_grad left the loss at 13,551 instead of 65.
  • Overfit one batch before any long run; a loss stuck at the targets' variance means the loss or the shapes are wrong.
  • Autograd keeps activations for the backward pass: 704 MiB against 128 MiB here, so run inference under torch.no_grad().

Check your understanding

Why must a training loop call zero_grad() every step?

Gradients accumulate by design. Without clearing them, each update uses the sum of all gradients so far; measured, the loss ended at 13,551 instead of 65.

The stability limit for plain gradient descent on the latency problem was 0.1015. What happened at a learning rate of 0.12?

Above the limit each step overshoots by more than the last: 6.8 million at step 10, then infinity.

An overfit-one-batch test gets stuck with the loss at exactly the variance of the targets. What is the most likely cause?

When every prediction is compared with every target, the best possible answer is the mean, and the loss is then the targets' variance: 0.6424 here.

Why did the forward pass with gradients use 704 MiB more memory but only 128 MiB without them?

Seven saved activations of 64 MiB, a 128 MiB fp32 copy of the output for the loss, and 128 MiB of weight gradients. Without gradients, each activation can be freed as soon as the next layer has used it.

How does the cost of reverse-mode autograd compare with finite differences for a model with N parameters?

One backward pass yields every gradient at once, which is what makes training models with billions of parameters possible.
