PyTorch Tensors on a GPU

Everything a language model does is arithmetic on tensors: a batch of token ids, a table of embeddings, the weights of every layer, the probabilities at the end. Before building any of that, you need to be fluent in the container itself: what shape a tensor has, how two tensors of different shapes combine, how many bits each number gets, and where the work actually runs.

Each of those has a trap that only shows up when you measure, so this chapter measures them with PyTorch 2.11 on an RTX 5070 Ti (16 GB): a shape mistake that changes a loss without raising an error, a number that bf16 cannot add to 1, a benchmark that reports a matrix multiply 215 times faster than it is, and how far apart CPU, fp32 and bf16 really are.

  • Read and reason about tensor shapes, and tell a view from a copy
  • Predict how broadcasting combines two shapes, and spot when it hides a bug
  • Choose between fp32, bf16 and fp16 knowing what each can and cannot represent
  • Move work to the GPU without paying for it twice
  • Time GPU code so that the number is true

Tensors, shapes and views

A tensor is an n-dimensional array with three properties you will check constantly: its shape (how many entries along each dimension), its dtype (how each number is stored) and its device (CPU memory or a particular GPU). Language-model code has a convention for shapes that this course follows everywhere: (B, T, C) means a batch of B sequences, each T tokens long, with C numbers (channels) per token.

import torch

x = torch.randn(32, 128, 768)           # (B, T, C): 32 sequences of 128 tokens, 768 numbers each
print(x.shape, x.dtype, x.device)       # torch.Size([32, 128, 768]) torch.float32 cpu
x = x.to("cuda", dtype=torch.bfloat16)  # copy to the GPU and convert, in one call
last = x[:, -1, :]                      # (32, 768): the last token of every sequence; a view, no copy
heads = x.view(32, 128, 12, 64)          # (B, T, 12 heads, 64 per head): same memory, new shape

The last two lines do not copy anything. A view is a new tensor object that shares the original's memory and describes it with a different shape and stride (how many elements to skip to move one step along each dimension). Slicing and view are free; writing into a view changes the original. That is how attention later splits 768 channels into 12 heads of 64 without moving a byte.

A view only works when the new shape can be described by strides over the same memory. Transposing a tensor swaps its strides, so its rows are no longer contiguous, and view refuses. This is the exact message PyTorch 2.11 gave for torch.randn(2, 3).t().view(6):

RuntimeError: view size is not compatible with input tensor's size and stride (at least one dimension spans across two contiguous subspaces). Use .reshape(...) instead.

reshape returns a view when it can and quietly copies when it cannot; .contiguous() makes the copy explicit. In model code the usual pattern is x.transpose(1, 2).contiguous().view(...), where the copy is deliberate and you know it costs memory bandwidth.

Broadcasting

When two tensors of different shapes meet in an elementwise operation, PyTorch broadcasts them: it lines the shapes up from the right, and along each dimension the sizes must be equal or one of them must be 1 (or missing), in which case it is stretched to match without copying. That is what lets you add a bias of shape (768,) to activations of shape (32, 128, 768), or apply one attention mask of shape (1, 1, 128, 128) to every head of every sequence.

The same rule produces the most common silent bug in model code. A prediction of shape (4, 1) minus a target of shape (4,) does not fail: the (4,) is treated as (1, 4), both are stretched, and the result is a 4 × 4 matrix of every prediction minus every target.

torch.manual_seed(0)
pred, target = torch.randn(4, 1), torch.randn(4)        # a model's (B, 1) output and (B,) labels
((pred - target) ** 2).mean()                       # 2.8257: pred - target is (4, 4), no error
((pred.squeeze(1) - target) ** 2).mean()            # 3.7137: the loss you meant, on a (4,) difference

Nothing crashed, the loss is a plausible number, and training would run on the wrong objective. The defence is cheap: assert shapes at the boundaries of every function (assert pred.shape == target.shape), and write the expected shape in a comment on every line that makes a tensor, which is this course's house style.

dtypes: how many bits, and which ones

A float is stored as a sign, an exponent (which sets the range: how large and how small a number can be) and a mantissa (which sets the precision: how many significant digits survive). The three float formats you will meet differ only in how they split their bits, and that split decides what goes wrong.

bf16 keeps fp32's 8-bit exponent, so it covers the same range, but with 7 mantissa bits it holds only about two to three significant decimal digits. fp16 has more precision but a tiny range. Both facts show up immediately:

for dt in (torch.float32, torch.bfloat16, torch.float16):
    one = torch.tensor(1.0, dtype=dt)
    print(dt, (one + 0.001).item(), torch.tensor(257.0, dtype=dt).item(), torch.tensor(70000.0, dtype=dt).item())
# float32   1.0010000467  257.0  70000.0
# bfloat16  1.0           256.0  70144.0     ← 0.001 is lost entirely; 257 rounds to 256
# float16   1.0009765625  257.0  inf         ← 70,000 is past fp16's largest value, 65,504

The first column matters most for training. A gradient step is a small number added to a weight. If the weight is stored in bf16 and the step is smaller than half the gap at that weight's size, the addition does nothing at all. Adding 0.0001 ten thousand times should reach 1.0; on this GPU, bf16 stopped growing at 0.03125 and fp16 at 0.25, while fp32 reached 1.0000535. That is why the standard recipe (Chapter 13) computes in bf16 but keeps the master copy of the weights, the optimiser state and every sum in fp32.

Putting work on the GPU

A tensor lives on one device, and an operation needs all its inputs on the same one. Mixing them is an error, not a silent copy: Expected all tensors to be on the same device, but found at least two devices, cuda:0 and cpu! The habit that avoids it is to create tensors directly on the GPU (torch.randn(..., device="cuda")) and move the model once with model.to("cuda").

Moving data is not free. The first CUDA call of a process took 380 ms here, because it creates the CUDA context and loads code onto the GPU; the second took 0.08 ms. Copying 1 GiB from ordinary (pageable) CPU memory to the GPU took 48.7 ms, about 22 GB/s; from pinned memory, which the operating system promises not to move so the GPU can read it directly, it took 18.6 ms, about 57.6 GB/s. Training loops pin their input batches (DataLoader(pin_memory=True)) and copy with non_blocking=True so the copy overlaps the previous step's compute.

Timing GPU code honestly

GPU work is asynchronous. When Python runs c = a @ b on CUDA tensors, PyTorch puts the multiply in a queue (a CUDA stream) and returns at once; the GPU works through the queue in the background. A timer stopped right after that line measures only the launch.

The second trap is measuring a cold GPU. The first time a matmul of a given shape runs, the library picks a kernel, and the GPU may still be raising its clock. My first timing of a 2048 × 2048 fp32 multiply said 3.49 ms; after one second of warm-up it was 0.598 ms on three separate passes. Every timing in this course uses the same helper:

import statistics, time

def time_gpu(fn, warmup_s: float = 1.0, reps: int = 50) -> float:
    end = time.perf_counter() + warmup_s
    while time.perf_counter() < end:
        fn()                                        # let kernel choice and clocks settle
    times = []
    for _ in range(reps):
        start, stop = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
        start.record(); fn(); stop.record()
        stop.synchronize()                           # wait for this repetition to finish
        times.append(start.elapsed_time(stop))       # milliseconds, measured on the GPU itself
    return statistics.median(times)

How fast is this GPU?

A multiply of two n × n matrices costs about 2n³ floating-point operations, so dividing by the time gives TFLOPS (trillions per second). At n = 4096 the CPU (8 threads) managed 0.69 TFLOPS. The GPU did 31.6 in plain fp32, 44.9 with TF32, and 88.8 in bf16: 2.8 times fp32 and about 130 times the CPU. Small matrices do not fill the GPU: at n = 1024 bf16 reached only 57 TFLOPS.

Not every operation can use that speed. Adding two 256-million-element bf16 tensors took 2.09 ms: 772 GB/s of memory traffic but only 0.13 TFLOPS, because each element is read, added once and written. The GPU spent its time moving bytes, not doing arithmetic. That distinction between compute-bound and memory-bound work (P6) explains why generating text one token at a time is slow even on a fast GPU (Chapter 16).

🧾
Use case: PyTorch turned TF32 off by default

When NVIDIA's Ampere GPUs introduced TF32, PyTorch 1.7 used it for fp32 matrix multiplies automatically: fast, but with only 10 mantissa bits inside the multiply. Users doing scientific computing found results that no longer matched their CPU runs, and in PyTorch 1.12 the default for matmuls was switched back off. Today you opt in with torch.set_float32_matmul_precision("high"). On this GPU that one line took a 4096 × 4096 fp32 multiply from 31.6 to 44.9 TFLOPS, and the same trade (speed for mantissa bits) is the whole story of bf16, fp16 and the quantisation chapters.

⚠️
Common mistakes
  • Timing GPU code without synchronising, and reporting the launch time as the run time.
  • Benchmarking the first call, which includes CUDA start-up, kernel selection and a cold GPU.
  • Subtracting a (B, 1) tensor from a (B,) tensor and training on a (B, B) loss without noticing.
  • Accumulating sums, or updating weights, in bf16 or fp16, so that small values are rounded away.
  • Putting values above 65,504 into fp16, such as large logits or unscaled losses, and getting inf.
  • Calling view on a transposed tensor, or calling .contiguous() everywhere without knowing it copies.
  • Copying a batch from pageable memory every step instead of pinning it and overlapping the copy with compute.

Interview drill

Explain it simply: A colleague benchmarks an 8192 × 8192 bf16 matrix multiply on a consumer GPU and reports 0.05 ms, which would be about 20,000 TFLOPS. What went wrong, and how should it be measured?

How a strong answer sounds
CUDA calls are asynchronous: the multiply was queued and Python got control back straight away, so the timer measured the kernel launch. The fix is to wait for the GPU before stopping the clock, either with torch.cuda.synchronize() or with CUDA events recorded around the operation, and to warm up first so kernel selection and clock ramp-up are not counted. Then take the median of many runs. Done that way, the same multiply takes about 11.3 ms on an RTX 5070 Ti, roughly 97 TFLOPS, which is close to what the card can do. A quick sanity check is to compute FLOPs divided by time and compare it with the GPU's published peak: anything above the peak is a measurement error.

Deeper: Why do most models now train in bf16 rather than fp16, and why do optimisers still keep fp32 copies of the weights?

How a strong answer sounds
Both are 16 bits, but they spend them differently. fp16 has 10 mantissa bits and a 5-bit exponent, so its largest value is 65,504 and small gradients underflow; training in fp16 needs loss scaling to keep values in range, and overflows still produce inf. bf16 has fp32's 8-bit exponent, so it has the same range and rarely overflows, which makes it a drop-in choice on GPUs that support it. The price is precision: 7 mantissa bits, so 1 + 0.001 rounds back to 1. A weight update is often that small relative to the weight, so updates applied to bf16 weights would simply vanish; summing 0.0001 ten thousand times in bf16 stalls at 0.03125. So the fast parts (matmuls, activations) run in bf16, while the master weights, the optimiser's moments and reductions such as sums and losses stay in fp32.

🧠 Key takeaways

  • Check shape, dtype and device constantly; write the expected (B, T, C) shape beside every tensor.
  • Slicing and view share memory; reshape and .contiguous() may copy.
  • Broadcasting aligns shapes from the right and never complains about (4, 1) minus (4,): it quietly made a 4 × 4 loss.
  • bf16 has fp32's range but about three significant digits; fp16 has more digits but tops out at 65,504. Keep weights' master copies and sums in fp32.
  • Synchronise and warm up before timing: unsynchronised, a multiply looked 215 times faster than it was.
  • On this GPU bf16 matmuls ran at about 89 TFLOPS, 2.8 times fp32 and about 130 times the CPU; elementwise work is limited by memory bandwidth instead.

Check your understanding

What is the shape of pred - target when pred is (4, 1) and target is (4,)?

Shapes align from the right: (4, 1) and (1, 4) both stretch to (4, 4), with no error. The loss computed from it was 2.83 instead of 3.71.

In bf16, what is 1.0 + 0.001?

With 7 mantissa bits, the gap just above 1.0 is 0.0078, so adding 0.001 rounds back to 1.0. fp16 gives 1.0009765625.

A timer around c = a @ b on CUDA tensors reads 0.05 ms, but with torch.cuda.synchronize() before stopping it reads 11.2 ms. Why?

CUDA operations are asynchronous. Without a synchronise (or CUDA events), you measure only the launch.

On this GPU, how much faster was a 4096 × 4096 matmul in bf16 than in plain fp32?

88.8 against 31.6 TFLOPS. About 130 times is bf16 on the GPU against fp32 on the CPU; TF32 gave about 1.4 times.

Why do training loops pin the memory of their input batches?

1 GiB copied in 18.6 ms from pinned memory (57.6 GB/s) against 48.7 ms from pageable memory (22 GB/s), and a non_blocking copy from pinned memory runs alongside compute.
