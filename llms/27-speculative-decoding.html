Speculative Decoding

A large model generates one token per forward pass, but a pass over five tokens costs barely more than a pass over one. Speculative decoding exploits that: a small, cheap model drafts several tokens, the large model checks them all in one pass, and every draft token it agrees with is a token gained. Done right, the output is exactly what the large model would have produced on its own.

This chapter implements it with Qwen2.5-0.5B-Instruct drafting for Qwen2.5-1.5B-Instruct. The drafts were good: on code the large model accepted 88% of them, 4.5 tokens per pass. And it was slower, 46 tokens a second against 67 alone, as was Hugging Face's own implementation. The measurements show exactly why, and when speculation does pay. Prompt lookup, which drafts by copying from the prompt at no cost, was the only version that sped things up here, by 9% on copying tasks.

Why decoding is slow

Generating a token means one forward pass through the whole model, and the next token cannot start until this one is chosen. Measured after a real prompt, one step of the 1.5B target took 14.8 ms. A pass over 5 tokens took 16.7 ms, only 13% longer for five times the work: each step's cost is mostly fixed (reading the weights, and on this setup launching kernels), not per token. If the next 5 tokens were known in advance, the model could check them all for nearly the price of one. Speculative decoding (Leviathan et al. and Chen et al., both 2023) guesses them.

Draft and verify

Each round: the draft model proposes k tokens one at a time; the target runs once over all k, giving its own prediction at every position; the longest prefix where they agree is kept, plus one token from the target at the first disagreement (or after the last draft token, if all were accepted). Both models' caches are then cut back to the accepted length:

draft_toks = [d.next() for _ in range(k)]                 # k cheap steps
logits = torch.cat([t_last[None], t.feed(draft_toks)])       # one target pass over all k
n_ok = 0
while n_ok < k and logits[n_ok].argmax() == draft_toks[n_ok]:
    n_ok += 1
fix = int(logits[n_ok].argmax())                             # the target's own token where they first disagree
out += draft_toks[:n_ok] + [fix]
t.crop(base + n_ok); d.crop(base + n_ok)                     # roll both caches back to what was kept

With greedy decoding the rule is simply "keep the tokens the target would have chosen", so the output should equal the target's alone. In bf16 it did for 7 of the 8 extraction and code prompts at k = 2 but only 4 of the 8 factual and creative ones; in fp32 all 8 checked factual and creative prompts matched exactly. As in Chapter 26, checking k tokens in one pass adds numbers in a different order than k separate passes, and bf16 rounding can flip near-ties.

The acceptance rule

With sampling, "agree" cannot mean "same token". The rule that keeps the target's distribution exactly: accept a draft token x with probability min(1, p(x) / q(x)), where p is the target's probability and q the draft's. If it is rejected, sample the replacement from the leftover mass, max(0, p − q), normalised. Tokens the draft over-proposes get thinned out; tokens it under-proposes are topped up by the replacement step. The result is distributed exactly as if the target had sampled alone.

That was checked directly. For the prompt "Name a colour.", 2,000 single tokens were generated by speculative sampling with a 4-token draft, and their frequencies compared with the target's own probabilities: "Blue" 90.0% against 90.4%, "Red" 3.1% against 3.1%, "Purple" 1.6% against 1.5%. The total variation distance was 0.0099, about what 2,000 samples' noise alone gives, even though the draft's own first-token distribution was 0.92 away from the target's: a poor draft costs speed, never correctness.

Acceptance behaved as expected: high where the next tokens are predictable (copying, code), low where many continuations are good (stories), and falling as k grows, since one wrong token discards everything drafted after it. Sampling at temperature 0.7 gave the same pattern, 86.7% on code and 39.4% on creative writing. Hugging Face's assisted generation, with the same pair, was also slower: 49.3 against 66.2 tokens a second on code.

The step times explain why. A draft step took 12.8 ms, 87% of a target step. Drafting 4 tokens cost 51 ms to save target passes that cost 15 ms each. The implementation here also feeds the correction token through both models as an extra step after each round, where optimised versions fold it into the next pass; together that predicts 46.8 tokens a second for code at k = 4, against 46.2 measured. Even without that overhead, the ideal speed-up is tokens per round divided by the round's cost in target steps, 4.46 / (4 × 0.87 + 1.13) = 0.97: no gain. On this GPU both models are so small that a step's cost is fixed overhead, the same for 0.5B as for 1.5B parameters.

Speculation pays when the draft is much cheaper than the target, as when a 1B draft serves a 70B target whose every step reads 140 GB of weights. With the cost ratio at 0.05 instead of 0.87 and the same 88% acceptance, the same formula gives 4.46 / (0.2 + 1.13) = 3.4 times faster. Papers and engines report 2 to 3 times on such pairs. The calculator in the lab shows the trade.

Self-speculation and Medusa heads

A separate draft model has to be loaded, kept in memory, share the tokenizer, and still costs something per token. Alternatives remove it. Prompt lookup drafts by finding the last few generated tokens earlier in the context and proposing what followed them there, which costs nothing. Measured here with up to 8 drafted tokens, it was the only version that sped things up: 73.6 against 67.8 tokens a second on extraction (+9%), where the output copies the prompt, and 70.7 against 68.4 on factual answers (+3%), where it rarely finds a match. It suits summarising, editing and code changes, where much of the output repeats the input.

Not measured here: Medusa adds a few extra output heads to the target model that predict tokens 2, 3, 4 ahead from the same hidden state, trained briefly on the model's own outputs; EAGLE trains a single small layer that drafts from the target's hidden states, which makes drafts far more accurate than a separate small model; and self-speculation drafts with the target itself, skipping some of its layers. All of them make the draft nearly free, which is exactly what was missing here.

Use case: faster replies from a large model

Interactive products care about time per output token, and for a large model at small batch sizes each token is limited by reading the weights. Speculative decoding is how many serving systems cut that: engines such as vLLM, SGLang and TensorRT-LLM support draft models, n-gram (prompt lookup) drafting and EAGLE- or Medusa-style heads, and code assistants lean on lookup drafting because edits repeat so much of the file. The measurements here are the warning: it only helps when the draft is far cheaper than the target and accepted often, so it is tuned per model pair and per workload, and usually switched off at large batch sizes, where the GPU is already busy and verifying rejected drafts wastes work.

⚠️
Common mistakes
  • Assuming speculation is always faster; with a draft costing 87% of a target step it was 31% slower here.
  • Judging a draft by acceptance alone; 88% accepted still lost time.
  • Using a long draft on open-ended text; creative writing fell to 24% acceptance at k = 8.
  • Accepting sampled drafts by "same token"; use min(1, p/q) and resample from max(0, p − q).
  • Expecting bit-identical greedy output in bf16; fp32 matched 8 of 8, bf16 about half.
  • Forgetting to roll back the draft model's cache along with the target's after a rejection.

Interview drill

Explain it simply: How does speculative decoding speed up generation without changing the output?

How a strong answer sounds
Decoding is sequential and each step's cost is mostly fixed, so checking several tokens in one pass costs little more than generating one; on my setup, 16.7 ms for 5 tokens against 14.8 for 1. A cheap draft model proposes k tokens; the target scores all of them in one pass; the prefix it agrees with is kept, plus one token of its own. With sampling, a draft token is accepted with probability min(1, p/q) and a rejected one is replaced by sampling from max(0, p − q), which makes the output exactly the target's distribution: in a test with 2,000 samples the total variation distance was 0.0099 even though the draft's distribution was 0.92 away. The speed-up is the accepted tokens per round divided by the round's cost, so it needs high acceptance and a draft much cheaper than the target.

Deeper: You add a draft model and generation gets slower. What do you check?

How a strong answer sounds
First the cost ratio. In my measurements a 0.5B draft cost 87% of a 1.5B target per step, because both were overhead-bound at batch 1, so even 88% acceptance gave 4.46 tokens per round for 4.6 target steps of cost: a predicted 0.97 times, and in practice slower. Then acceptance by workload: 92% on extraction, 40% on creative writing at k = 4, so k should be tuned per workload, often smaller for open-ended text. Then the implementation: extra passes per round, like feeding the correction token separately, which cost me a target and a draft step each round. Fixes: a much cheaper drafter (prompt lookup, which gave me +9% on copying tasks, or EAGLE or Medusa heads), a larger target where the step is bandwidth-bound, and turning speculation off at high batch sizes.

🧠 Key takeaways

  • One target pass over 5 tokens cost 16.7 ms against 14.8 for 1: verifying is nearly free.
  • The acceptance rule min(1, p/q) keeps the target's distribution exactly (total variation 0.0099 on 2,000 samples).
  • Acceptance depends on the task: 92% copying, 88% code, 57% explanations, 40% stories at k = 4.
  • Here it was slower (46 against 67 tok/s) because the draft cost 87% of a target step.
  • Speed-up ≈ tokens per round / (k × draft cost + verify cost): it needs a draft far cheaper than the target.
  • Prompt lookup, a free drafter, was the only version faster here (+9% on copying).
