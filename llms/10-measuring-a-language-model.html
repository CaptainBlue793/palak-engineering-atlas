Loss, Perplexity & Bits per Byte

Every chapter so far has quoted a loss. This one asks what that number means and when two of them can be compared. The answer matters, because the most common way to compare language models, perplexity per token, gives the wrong ranking as soon as the models cut text into different tokens.

Four models were scored on the same held-out text: Chapter 8's 13.9-million-parameter model, GPT-2, and Qwen2.5 at 0.5 and 1.5 billion. On Python code, GPT-2's per-token perplexity was 5.8 against Qwen2.5-0.5B's 4.4, which looks close; measured per byte, GPT-2 needed 2.5 times as many bits. On children's stories, the tiny model came within about 4% of Qwen2.5-0.5B per byte, at a thirty-fifth of its size. And on the MIT licence, text copied across millions of repositories, GPT-2 needed 0.04 bits per byte. On a paraphrase of the same licence it needed 1.05: it had memorised the original.

Cross-entropy as the score

A language model's loss on a text is the average, over tokens, of −ln p(the token that actually came next). If the model gave the real next token probability 0.5, that token costs 0.69; probability 0.01 costs 4.6; probability 1 costs nothing. It is the training objective (Chapter 8) and the most direct measure of quality there is: it asks how much probability the model puts on what really happens, over every token of a text, with no human judgement involved.

Measuring it fairly needs care in two places. Every token must be scored exactly once: the scorer here prepends a start token so that even the first word is predicted, and slides non-overlapping windows over the text, so no token is skipped or counted twice. And each model needs enough context: tokens near the start of a window are harder to predict (Chapter 5), so a model given 256 tokens of context is at a disadvantage against one given 1,024. Chapter 8's model was trained with 256 positions and was scored with 256; the others with 1,024.

Perplexity

Perplexity is e raised to the loss. It reads as an effective number of choices: a model that spreads its probability evenly over k tokens has perplexity exactly k. GPT-2 on WikiText had a loss of 3.46 nats per token, perplexity 31.8: on average it was as uncertain as if choosing among 32 equally likely tokens. Qwen2.5-1.5B scored 10.2 on the same text. Dividing a loss by ln 2 turns it into bits, the size of the message an ideal compressor using the model would need: 3.46 nats is 4.99 bits per token.

The catch is the word "token". Each model's perplexity is per token of its own tokeniser, and tokens differ in size. On WikiText, GPT-2's tokens averaged 4.5 bytes, Qwen2.5's 4.2 and the tiny model's 2.8 (Chapter 2). A model whose tokens are smaller has more, easier predictions to make, which pulls its per-token loss down without it predicting the text any better.

Bits per byte

The fix is to divide by something every model agrees on: the number of bytes in the text. Bits per byte is the total loss in bits divided by the text's length in UTF-8 bytes. It answers "how many bits does this model need to encode this text", which does not depend on how the text was cut up.

def score(ids, bos, logits_fn, T):                    # every token predicted exactly once
    seq = torch.tensor([bos] + ids)                       # a start token, so the first word is predicted too
    losses = []
    for i in range(0, len(ids), T):                          # non-overlapping windows of T predictions
        x = seq[i : i + T + 1]
        losses.append(F.cross_entropy(logits_fn(x[:-1][None])[0], x[1:], reduction="none"))
    return torch.cat(losses)

On Python, per-token perplexity puts GPT-2 (5.8) a little behind Qwen2.5-0.5B (4.4). Per byte, GPT-2 needed 1.17 bits and Qwen2.5-0.5B 0.47: two and a half times worse, not a little. GPT-2's tokeniser cuts Python into small pieces, 2.2 bytes per token against Qwen's 4.5, largely one token per space of indentation (Chapter 2), and those spaces are easy to predict, which flatters its per-token average. The same mismatch in the other direction would make a model look worse than it is.

Bits per byte also makes the tiny model's result fair. On the children's stories it was trained for, it needed 0.555 bits per byte, about 4% more than Qwen2.5-0.5B's 0.532, with a thirty-fifth of the parameters (and a quarter of the context). On Wikipedia and Python, text it never saw, it needed 3.6 and 5.3 bits per byte, worse than the general-purpose compressor xz, which needed 2.5 and 1.6 with no knowledge of language at all. The real models beat xz by a factor of two to four. A model's score belongs to a domain.

How much text a measurement needs

Losses vary a lot from token to token, so a short text gives a noisy average. Drawing 30 random sets of tokens from the same text and measuring the spread of their mean loss (the standard deviation):

Tokens scoredGPT-2, WikipediaQwen2.5-1.5B, WikipediaTiny, stories
100± 0.33± 0.26± 0.23
1,000± 0.10± 0.08± 0.08
10,000± 0.023± 0.026± 0.019

The spread shrinks with the square root of the number of tokens: ten times the text, about a third of the noise. With 1,000 tokens, two models 0.1 apart cannot be told apart; at 10,000 tokens, differences of about 0.05 begin to mean something. And because these are random tokens from a single text, the real uncertainty is larger: a different text, from another source, would move every score.

Held-out data that is really held out

Use case: comparing models that do not share a tokeniser

Bits per byte is how serious comparisons across model families are made. The Pile, EleutherAI's 2020 dataset, reported results in bits per byte for exactly this reason, and later work comparing models trained on different data or with different vocabularies does the same, as does work that treats language models as compressors, where bits per byte is the compressed size directly. In practice: when choosing between two open models for a domain, score both on a few hundred thousand bytes of your own held-out documents, documents that were not public before the models' training cut-off, and compare bits per byte. It takes minutes on one GPU, as here, and it measures your text rather than a public benchmark the models may have seen.

⚠️
Common mistakes
  • Comparing perplexity across tokenisers; on Python it made GPT-2 look close to Qwen2.5-0.5B when it needed 2.5 times the bits.
  • Skipping the first token of each window, or overlapping windows, so tokens are scored zero or two times.
  • Giving models different amounts of context without saying so; early positions are harder.
  • Trusting differences smaller than the noise; with 1,000 tokens, ± 0.1 is noise.
  • Evaluating on text that was online before training; GPT-2 recited the MIT licence at 0.04 bits per byte.
  • Quoting a single score as "the" quality of a model; the tiny model was 0.56 bits per byte on stories and 5.3 on code.

Interview drill

Explain it simply: What is perplexity, and what is wrong with comparing it across models?

How a strong answer sounds
Perplexity is e to the average cross-entropy loss per token, the negative log probability the model gave to each real next token. It reads as an effective number of equally likely choices: perplexity 32 means as uncertain as picking among 32 tokens. The problem is that it is per token of the model's own tokeniser, and tokenisers cut text differently. A tokeniser with small tokens has more, easier predictions, so its per-token perplexity looks better. The fix is bits per byte: total loss in bits divided by the text's length in bytes, which every model agrees on. On Python code GPT-2's perplexity was 5.8 against Qwen2.5-0.5B's 4.4, but per byte GPT-2 needed 1.17 bits against 0.47, two and a half times worse.

Deeper: You need to know if model A is better than model B on your company's documents. How do you measure it?

How a strong answer sounds
Collect held-out documents that are representative and, ideally, were never public before either model's training cut-off, since public text may be memorised: famous passages scored up to 26 times fewer bits than paraphrases of them. Score every token exactly once with each model, giving each its full context, and report bits per byte rather than per-token perplexity, because the tokenisers differ. Use enough text: with 1,000 tokens the noise was about ± 0.1 nats, with 10,000 about ± 0.025, and documents differ more than tokens within one document, so bootstrap over documents to get a confidence interval. Then check that the difference also shows on the task itself, since lower loss does not always mean better answers; Chapter 30 covers task evaluation.

🧠 Key takeaways

  • Loss is the average −ln p of each real next token; perplexity is eloss, an effective number of choices.
  • Per-token numbers depend on the tokeniser; bits per byte does not.
  • On Python, GPT-2 looked close to Qwen2.5-0.5B per token but needed 2.5 times the bits per byte.
  • The 13.9 M tiny model came within about 4% of Qwen2.5-0.5B on its own domain, and was worse than a zip compressor off it.
  • Noise falls with the square root of the text: about ± 0.1 at 1,000 tokens, ± 0.025 at 10,000.
  • Memorised text scores far too well: the MIT licence cost GPT-2 0.04 bits per byte, its paraphrase 1.05.
