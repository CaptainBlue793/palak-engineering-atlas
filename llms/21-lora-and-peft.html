LoRA & Parameter-Efficient Fine-Tuning

Chapter 19 updated every one of Qwen2.5-0.5B's 494 million weights, which needs memory for all of their gradients and optimiser states and produces a full copy of the model per fine-tune. Low-rank adaptation (LoRA) freezes the model and learns a small correction to each weight matrix instead, written as the product of two thin matrices.

This chapter implements LoRA in 20 lines, checks it against the peft library (identical outputs), and runs nine fine-tunes on Chapter 19's Dolly data. LoRA halved the training memory, from 12.2 to 6.6 GB, and the adapter for the best run was 34 MB against a 1.9 GB model. It paid for that in quality: a held-out reply loss of 2.148 against the full fine-tune's 2.045. And the rank, the knob everyone tunes first, barely mattered: rank 1, a 2 MB adapter, came within 0.014 of the best.

Low-rank updates

Fine-tuning changes each weight matrix W by some ΔW. LoRA's bet, from Microsoft's 2021 paper, is that for adapting a pretrained model ΔW does not need to be an arbitrary matrix: a low-rank one will do. Write it as ΔW = B·A, where A is r × din and B is dout × r with a small rank r. For one of Qwen2.5-0.5B's 896 × 896 attention projections that is 802,816 numbers for a full update, but only 28,672 at r = 16: 3.6%. The original W stays frozen; only A and B are trained.

Implementing LoRA

class LoRALinear(nn.Module):
    """y = W x + (alpha / r) · B(A(x)). W frozen; A random, B zero, so training starts exactly at the base model."""
    def __init__(self, base: nn.Linear, r: int, alpha: float):
        super().__init__()
        self.base, self.scale = base, alpha / r
        self.A = nn.Parameter(torch.empty(r, base.in_features)); nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))
        self.B = nn.Parameter(torch.zeros(base.out_features, r))
        base.weight.requires_grad_(False)
    def forward(self, x):
        return self.base(x) + (x @ self.A.T @ self.B.T) * self.scale
    def merge(self):                                         # fold the update in: W' = W + scale · B A
        self.base.weight += self.B @ self.A * self.scale
        return self.base

Three checks came back clean. Because B starts at zero, the wrapped model's logits at initialisation were identical to the base model's (difference 0.0). With the same random A and B copied into the peft library's implementation, the two gave identical outputs (0.0). And merging the update into the weights changed the logits by at most 1.6 × 10⁻⁴, rounding, so a merged adapter costs nothing at inference.

Rank and alpha

Every run below used the same data and schedule as Chapter 19, half an epoch (430 steps of 16 conversations), scored by reply loss on the same 300 held-out conversations. LoRA used a learning rate of 2 × 10⁻⁴, the full fine-tune 10⁻⁵ (Chapter 19's best):

Raising the rank 64-fold changed the loss by 0.014, and rank 64 did no better than rank 16. The update the data asks for really is low-rank; extra rank is capacity the run does not use. Alpha scales the update: the code multiplies B·A by alpha / r, so with alpha = 2r, as here, the effective step size stays the same whatever the rank, which is why most people fix alpha at r or 2r and tune the learning rate instead. LoRA did not reach the full fine-tune: 0.10 worse after the same half epoch. Changing every weight with a small learning rate moved further than adapting a small subspace, which matches the LoRA literature's finding that it can learn less and forget less than full fine-tuning.

Adapting more kinds of layer helped at least as much as adding rank: going from queries and values to every linear layer gained 0.03, twice the whole effect of rank, and adding the MLP layers alone, where most of the parameters and much of the model's knowledge sit (Chapter 15), gained as much as raising the rank from 1 to 16. Applying LoRA to every linear layer is now the common default. The learning rate mattered too: 5 × 10⁻⁵ reached 2.161, 2 × 10⁻⁴ 2.148, and 10⁻³ overshot to 2.201. LoRA typically wants a learning rate ten or more times a full fine-tune's, because the update starts at zero and lives in a small space.

One expectation did not hold here: LoRA was not faster. Every run took about 200 seconds, the same as the full fine-tune, because the backward pass still runs through every frozen layer to reach the adapters, and at this size that dominates. What LoRA saved was memory, the gradients and optimiser states for 485 million parameters, which is what lets far larger models be fine-tuned on one GPU (Chapter 22).

Merging and swapping adapters

A trained adapter can be merged: add B·A into W once, and the model runs at exactly its original speed with no extra layers, as the 1.6 × 10⁻⁴ check showed. Or it can be kept separate, which is LoRA's other big advantage: one base model in memory, many small adapters loaded on demand, one per customer or task. A 34 MB adapter per task instead of a 1.9 GB model copy is a 55-fold saving in storage, and serving systems such as vLLM and S-LoRA batch requests for different adapters on the same base model in a single forward pass.

Use case: one base model, many tenants

A company offering fine-tuned models to many customers cannot keep a separate copy of a 7- or 70-billion-parameter model for each. With LoRA it keeps one copy and one adapter per customer, tens of megabytes each, loaded per request. Systems like S-LoRA (2023) and vLLM's multi-LoRA support serve thousands of adapters on shared GPUs this way, and most hosted fine-tuning services train LoRA adapters behind the scenes. The trade-off measured here applies to them too: a little less quality than full fine-tuning on the same data, in exchange for far less memory, storage and risk of disturbing the base model.

⚠️
Common mistakes
  • Using a full fine-tune's learning rate for LoRA; it typically needs ten times more or so.
  • Spending time tuning the rank first; rank 1 to 64 spanned 0.014 here, target layers 0.03 and learning rate 0.05.
  • Adapting only queries and values out of habit; adapting every layer gained 0.03, twice the whole effect of rank.
  • Changing r without changing alpha and so changing the effective learning rate by accident.
  • Expecting LoRA to be faster; it saves memory, the backward pass still crosses every layer.
  • Forgetting to train the embeddings when the fine-tune adds new tokens (Chapter 3).

Interview drill

Explain it simply: How does LoRA work, and why is it popular?

How a strong answer sounds
LoRA freezes the pretrained weights and, for each chosen linear layer, learns an additive update written as the product of two thin matrices, B times A, of rank r, scaled by alpha over r. B starts at zero so training begins exactly at the base model. Only A and B get gradients and optimiser states, so memory drops a lot: on Qwen2.5-0.5B from 12.2 to 6.6 GB, with 1.8% of the parameters trained at rank 16. The adapter is tiny, 34 MB here, so one base model can serve many adapters, and an adapter can be merged into the weights for zero inference cost. The trade-off is some quality: 2.148 reply loss against 2.045 for a full fine-tune on the same data.

Deeper: You have a fixed budget for one LoRA fine-tune. Which hyperparameters do you spend it on?

How a strong answer sounds
First the learning rate, because it moved quality most: from 2.161 to 2.148 to 2.201 across 5e-5, 2e-4 and 1e-3. Second, which layers get adapters: adapting every linear layer instead of only queries and values gained 0.03, twice the whole range across ranks. Rank last: from 1 to 64 the loss changed by only 0.014, and rank 64 was not better than 16; with alpha tied to r, changing r does not change the effective step size. I would also check the data and epochs as in full fine-tuning, and compare against a full fine-tune if memory allows, since LoRA was 0.1 behind it here. If memory is the constraint, QLoRA quantises the frozen base to 4 bits to go further.

🧠 Key takeaways

  • LoRA freezes W and learns ΔW = B·A of rank r; written from scratch it matched peft exactly.
  • It halved training memory (12.2 → 6.6 GB) and made the result a 34 MB adapter.
  • It cost some quality: 2.148 reply loss against a full fine-tune's 2.045 on the same data.
  • Rank barely mattered (0.014 from 1 to 64); target layers and learning rate mattered more.
  • LoRA saved memory, not time, at this size.
  • Adapters merge into the weights for free, or swap on one shared base model.
