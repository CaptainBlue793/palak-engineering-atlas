The KV Cache

Chapter 7's model generated text by running the whole sequence through again for every new token, and got slower as the text grew. Every serious implementation avoids that with the key-value cache: each layer keeps the keys and values it has already computed, so a new token needs only its own. It is a few lines of code and it changes what generation costs.

This chapter adds one from scratch to the GPT class and checks it: the same 60 tokens as before, on every prompt. With the cache, a decode step took about 2.6 milliseconds whatever the context, where recomputing everything grew to 6 by 896 tokens. Batching 64 sequences into each step multiplied throughput by 30 for barely twice the time per step. And the cache itself became the thing to budget: 36 KB per token for GPT-2, 12 KB for Qwen2.5-0.5B, measured from the real tensors.

Recomputing everything vs caching

Generating token 101 needs the attention of position 101 over positions 1 to 101: its own query against everyone's keys, weighted by everyone's values. Positions 1 to 100 have not changed since the last step, because the causal mask means nothing earlier ever depends on anything later (Chapter 4). Their keys and values are the same numbers as last time. Recomputing them is pure waste, and it grows with every token: generating n tokens that way costs on the order of n² token-passes. Keeping each layer's keys and values in a cache means each new token is one token-pass, so the whole generation is linear.

Implementing the cache

def forward_cached(m, ids, cache, start):
    """Run only the new tokens ids (B, t), at positions start..start+t-1, adding their K and V to cache."""
    B, t = ids.shape
    x = m.wte(ids) + m.wpe(torch.arange(start, start + t))
    for i, blk in enumerate(m.h):
        q, k, v = blk.attn.c_attn(blk.ln_1(x)).split(768, dim=2)
        q, k, v = heads(q), heads(k), heads(v)          # (B, 12, t, 64)
        if cache[i] is not None:
            k = torch.cat([cache[i][0], k], dim=2)              # earlier positions, computed once
            v = torch.cat([cache[i][1], v], dim=2)
        cache[i] = [k, v]
        a = F.scaled_dot_product_attention(q, k, v, is_causal=t > 1)   # one new token may see everything cached
        x = x + blk.attn.c_proj(merge(a))
        x = x + blk.mlp(blk.ln_2(x))
    return m.ln_f(x) @ m.wte.weight.T

cache = [None] * 12
logits = forward_cached(model, prompt, cache, 0)                        # prefill: the whole prompt at once
for i in range(n):
    nxt = logits[:, -1].argmax(-1, keepdim=True)
    logits = forward_cached(model, nxt, cache, prompt.shape[1] + i)       # decode: one token per step

Two details matter. Positions must continue from where the cache ends, or every new token would think it is at position 0. And the causal mask is only needed in the prefill, when several new tokens are processed together; a single new token is allowed to see every cached position. With GPT-2's weights, this produced the same 60 greedy tokens as Chapter 7's uncached generate on all three prompts, and the logits of a late step differed by at most 2 × 10⁻⁴, summation order again (Chapter 7).

Prefill and decode

Generation has two phases with very different costs. Prefill processes the prompt: many tokens in one pass, big matrix multiplies, the GPU fully busy. Decode produces the answer one token at a time: each step multiplies a single vector by every weight matrix, so the GPU spends its time reading weights and cache from memory rather than computing (P6). In bf16 on this GPU:

Prefill handled 896 tokens in barely twice the time of 16: the GPU had room to spare at small sizes. Decode with the cache stayed at about 2.6 ms per token from 16 tokens to 896, while recomputing grew steadily to 6.0, 2.3 times slower, and would keep growing. For a model this small, the cached step is dominated by launching on the order of a hundred small GPU kernels, which is why it barely moves; for large models it is dominated by reading the weights, and grows slowly with the cache.

Batching

A decode step uses the GPU poorly: one vector times each weight matrix. Putting several sequences in the same step reuses each weight read for all of them. With 256-token caches:

Sixty-four sequences together produced 30 times the tokens of one, with each step only 2.2 times longer. This is the economics of serving: a single user gets low latency but wastes the GPU; many users batched together share it. What limits the batch is memory, and most of that, past the weights, is cache. Chapter 26 builds a server around exactly this trade.

Memory per token

The cache holds a key and a value vector per layer, per head, per token. Per token, in bf16: 2 (key and value) × layers × key-value heads × head size × 2 bytes.

Use case: prompt caching in APIs

The cache does not have to be thrown away when a request ends. If many requests start with the same long prefix, a system prompt, a set of documents, a long conversation so far, the server can keep that prefix's cache and start each new request from it, skipping its prefill. Inference servers such as vLLM and SGLang do this automatically ("prefix caching"), and API providers including Anthropic, OpenAI and Google offer it as prompt caching, charging less for cached input tokens and returning the first token sooner. The measurements here show why it pays: prefill is the part that grows with the prompt, and on a long shared prefix it is most of the work.

⚠️
Common mistakes
  • Restarting positions at 0 for each new token; it must continue from the cache's length.
  • Applying the causal mask to a single decoded token against the cache, which hides everything but itself.
  • Not checking the cached path against uncached generation; here they produced the same 60 tokens.
  • Budgeting GPU memory by weights alone; at long contexts or many requests the cache dominates.
  • Serving one request at a time; 64 per step gave 30 times the throughput.
  • Expecting decode to speed up with more compute; it is limited by memory reads, not arithmetic.

Interview drill

Explain it simply: What is the KV cache and why does it matter?

How a strong answer sounds
During generation, each new token attends to all previous tokens' keys and values. Because of the causal mask those keys and values never change once computed, so each layer stores them in a cache and the new token only computes its own query, key and value. That turns generation from quadratic recomputation into one token-pass per new token. I implemented it on GPT-2 and checked it produced identical tokens; per-token decode time stayed around 2.6 ms from 16 to 896 tokens of context, while recomputing grew to 6 ms. The cost is memory: 2 × layers × KV heads × head size × bytes per token, 36 KB for GPT-2 and 12 KB for Qwen2.5-0.5B thanks to grouped-query attention.

Deeper: Why is decoding memory-bound, and what do servers do about it?

How a strong answer sounds
Each decode step processes one token per sequence, so every weight matrix is read from memory to do a single vector multiply, and the whole cache is read too. Arithmetic intensity is about one operation per byte, far below what the GPU needs to be compute-bound (P6). Servers therefore batch many sequences into each step so each weight read serves all of them: 64 sequences gave 30 times the throughput for 2.2 times the step time here. That makes memory for caches the limit on batch size, which is addressed by grouped-query attention, quantising the cache, paging cache memory to avoid fragmentation, prefix caching for shared prompts, and speculative decoding to get several tokens per weight read.

🧠 Key takeaways

  • Keys and values of earlier tokens never change, so caching them makes generation one token-pass per token.
  • A from-scratch cache gave the same 60 tokens as recomputing, on every prompt.
  • Cached decode stayed near 2.6 ms per token from 16 to 896 tokens; recomputing grew to 6.0.
  • Prefill is compute-bound and fast per token; decode is memory-bound and slow per token.
  • Batching 64 sequences gave 30× the throughput for 2.2× the step time.
  • Cache per token = 2 × layers × KV heads × head size × bytes: 36 KB for GPT-2, 12 KB for Qwen2.5-0.5B.
