Custom Ops: autograd.Function & Triton Kernels

Most models are built entirely from PyTorch’s operations, and autograd derives every backward pass for you. Two situations push you past that. Sometimes the backward pass you want is not the true derivative (a straight-through estimator for rounding), or the automatic one keeps more memory than necessary. And sometimes no fast kernel exists for the computation you need, so a chain of small operations each reads and writes the whole tensor. The first is solved with torch.autograd.Function, the second with a GPU kernel, and Triton lets you write one in Python.

This chapter writes both and tests them the way a library would. A hand-written SiLU kept 256 MB less memory than the composite version, and ran slower than it, because three separate PyTorch kernels in a custom backward are not one fused kernel. gradcheck passed the correct backward and caught a single flipped sign. A Triton row softmax matched torch.softmax to 10⁻⁸ and reached its speed on wide rows. A fused bias + GELU kernel, forward and backward, was 25% faster than eager PyTorch and slightly faster than torch.compile, and saved no intermediate tensor at all.

  • Write a custom forward and backward with torch.autograd.Function and choose what to save
  • Use a backward that is not the true gradient, such as a straight-through estimator
  • Verify a custom backward with gradcheck in float64
  • Write, launch and benchmark Triton kernels, and read the numbers as memory bandwidth
  • Fuse an operation chain into one kernel and know when that beats torch.compile

torch.autograd.Function

A custom Function is a pair of static methods. forward computes the output from plain tensors and stores in ctx whatever the backward will need; backward receives the gradient of the loss with respect to the output and returns one gradient per input. Autograd treats the pair as a single node in its graph and never looks inside.

class SiLU(torch.autograd.Function):                      # x · sigmoid(x)
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)                         # save only the input...
        return x * torch.sigmoid(x)
    @staticmethod
    def backward(ctx, g):
        (x,) = ctx.saved_tensors; s = torch.sigmoid(x)     # ...and recompute sigmoid here
        return g * s * (1 + x * (1 - s))

Written as plain operations, x * torch.sigmoid(x) makes autograd save both x and sigmoid(x), because the multiply needs both for its backward. The custom version saves only x and recomputes the sigmoid. Measured on 67 million elements:

SiLU implementationExtra memory held for backwardForward + backward
Composite x * torch.sigmoid(x)256 MB (the sigmoid output)5.87 ms
Custom Function, saves x only0 MB6.98 ms
Built-in F.silu0 MB1.78 ms

The custom Function bought its memory saving with time: its backward runs several separate kernels (sigmoid, subtract, multiply, add, multiply), each reading and writing the full tensor, and recomputing the sigmoid adds one more pass. The built-in F.silu is a single fused CUDA kernel in each direction, and was more than three times faster than either. A custom Function changes what is computed and saved; it does not make the arithmetic faster. That takes a kernel.

Custom backward passes

The backward does not have to be the true derivative. Rounding has a derivative of zero almost everywhere, so a network that rounds its weights in the forward pass (quantisation-aware training, Chapter 32) would never learn. A straight-through estimator rounds in the forward pass and passes the gradient through unchanged:

class RoundSTE(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x): return torch.round(x)
    @staticmethod
    def backward(ctx, g): return g                   # pretend rounding was the identity

For three weights through 2 · round(w), the true gradient was [0, 0, 0] and the straight-through one [2, 2, 2]. Gradient reversal layers, clipped or rescaled gradients and custom numerically stable formulas are written the same way.

Because a hand-written backward is easy to get subtly wrong, test it. torch.autograd.gradcheck compares the analytical backward with central finite differences, element by element, and needs float64 so that the finite differences are accurate (P2):

x = torch.randn(64, dtype=torch.float64, requires_grad=True)
torch.autograd.gradcheck(SiLU.apply, (x,))              # True
torch.autograd.gradcheck(BadSiLU.apply, (x,), raise_exception=False)   # False: (1 - s) written as s

The correct version passed; a copy with one sign flipped, x · s in place of x · (1 − s), failed. That bug would not crash or produce NaNs. A network using it would still train, more slowly, which is exactly the kind of bug Chapter 39 shows going unnoticed.

A Triton kernel

Triton (Tillet et al., 2019) is a language for GPU kernels embedded in Python. A kernel is a function run by many programs in parallel; each program handles one block of elements, loads them from GPU memory into registers with tl.load, computes, and writes back with tl.store. A mask stops the last block reading past the end. Triton compiles the function for the GPU on its first call.

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)                                # which block am I?
    offs = pid * BLOCK + tl.arange(0, BLOCK); mask = offs < n
    tl.store(out_ptr + offs, tl.load(x_ptr + offs, mask=mask) + tl.load(y_ptr + offs, mask=mask), mask=mask)

add_kernel[(triton.cdiv(n, 1024),)](x, y, out, n, BLOCK=1024)    # one program per 1,024 elements

An addition does almost no arithmetic per byte moved, so its speed is the memory bandwidth it achieves, counted here as three tensors (two read, one written) per call:

Small tensors are dominated by the fixed cost of launching a kernel, where PyTorch’s launch path is cheaper than Triton’s Python-side one. Fusing an operation

Softmax over each row of a matrix is three passes in plain PyTorch (max, exponentials and sum, divide) or five separate kernels written naively. A Triton kernel can give each row to one program, keep the whole row in registers, and read and write it exactly once:

@triton.jit
def softmax_kernel(x_ptr, out_ptr, stride, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0); offs = tl.arange(0, BLOCK); mask = offs < n_cols
    x = tl.load(x_ptr + row * stride + offs, mask=mask, other=-float("inf"))
    e = tl.exp(x - tl.max(x, 0))                               # stable: subtract the row maximum (P3)
    tl.store(out_ptr + row * stride + offs, e / tl.sum(e, 0), mask=mask)

The Triton kernel agreed with torch.softmax to within 3 × 10⁻⁸ and was as fast or slightly faster from 1,024 columns up; the naive five-kernel version moved the data five times and ran at a quarter of the speed. torch.compile fused the naive code well at moderate widths but fell to 414 GB/s on the widest rows, where its generated kernel no longer kept a row in registers. On the narrowest rows PyTorch’s hand-tuned kernel, which packs several short rows into one program, was best. A one-row-per-program design is simple, not universal.

The same idea, for an operation PyTorch has no single kernel for: adding a bias and applying GELU, the pattern after every feed-forward layer in a transformer. Eager PyTorch writes x + b to memory, saves it for the backward, then reads it again for the GELU. A fused kernel computes both in registers, and its backward kernel recomputes x + b instead of loading a saved copy. Wrapped in an autograd.Function, its outputs matched PyTorch’s to 4.8 × 10⁻⁷, its input gradients to 6.9 × 10⁻⁶ and its bias gradient to a relative 2.2 × 10⁻⁷:

The hand-written kernel was 25% faster than eager and 5% faster than what the compiler generated, and kept nothing beyond its inputs. For most code torch.compile gets close to a hand-written kernel at no effort, and that is where to start. Hand-written kernels earn their keep for operations used billions of times (attention, normalisation, optimiser updates), where a few percent and a few hundred megabytes matter, and for algorithms a compiler cannot discover, such as FlashAttention’s tiling.

Testing gradients and speed

A custom op needs the same tests as a library function. Correctness: compare the forward with a reference implementation on random inputs, including awkward sizes that are not multiples of the block; compare the backward with autograd on the reference, and run gradcheck in float64 where the kernel supports it. Speed: warm up first (the first Triton call compiles), synchronise before reading the clock, use sizes from the real model rather than ones that fit in cache, and report bandwidth or FLOP/s so the number can be compared with the hardware’s limit. A kernel at 87% of peak bandwidth has little left to gain; one at 20% has a bug or a bad memory access pattern.

Use case: a custom loss for a protein-structure model

A research team’s loss compares predicted and true atom positions with a function over every pair of residues. Written in PyTorch it creates a residues × residues × 3 tensor and several intermediate copies, and at 1,000 residues training runs out of memory. They first try torch.compile, which fuses some of it but still materialises the pairwise tensor. They then write the loss as a Triton kernel that processes tiles of residue pairs in registers and accumulates the sum, with a second kernel for the backward, wrapped in an autograd.Function. Before using it they compare it with the PyTorch version on 200 random small inputs, forward and backward, and run gradcheck in float64 on tiny ones. Memory for the loss falls from 11 GB to under 100 MB.

⚠️
Common mistakes
  • Expecting autograd.Function to be faster: the memory-saving SiLU was slower than the composite version.
  • Not testing a custom backward: a flipped sign trains silently; gradcheck caught it.
  • gradcheck in float32: finite differences need float64 to be accurate.
  • Benchmarking tensors that fit in cache: 12 MB showed 1,563 GB/s, above the card’s 896 GB/s rating.
  • Timing the first call: it includes Triton’s compilation.
  • Writing a kernel before trying torch.compile: it reached 95% of the hand-written fused kernel’s speed.

Interview drill

Explain it simply: When would you write a custom torch.autograd.Function?

How a strong answer sounds
When I need a backward that autograd would not produce: a straight-through estimator for rounding, where the true gradient is zero; gradient reversal; or a more stable formula. Or when the automatic backward saves too much: a SiLU written as x times sigmoid(x) saves the sigmoid output, 256 MB on a 67-million-element tensor, while a custom Function can save only x and recompute. It is not a speed tool by itself: that custom SiLU was slower than the composite one, and the built-in fused F.silu was three times faster than both. I always check a custom backward with gradcheck in float64; it caught a single flipped sign in my test.

Deeper: How do you know whether a kernel you wrote is any good?

How a strong answer sounds
Compare it with the hardware limit, not just with another implementation. Element-wise and reduction kernels are bandwidth-bound, so I count the bytes read and written and divide by the time: my Triton vector add and row softmax reached about 760 to 780 GB/s on large tensors, 85 to 87% of the card’s 896 GB/s, so there was little left to gain. I test on realistic sizes, because a 12 MB tensor sat in the 48 MB L2 cache and showed more than the rated bandwidth. I warm up first, since the first Triton call compiles, and synchronise before timing. And I compare against torch.compile, which got within 5% of my fused bias plus GELU kernel without any effort.

🧠 Key takeaways

  • autograd.Function lets you choose the backward and what is saved; it saved 256 MB but did not add speed.
  • A backward need not be the true gradient: straight-through estimators make rounding trainable.
  • Test every custom backward with gradcheck in float64; it caught one flipped sign.
  • Triton kernels are Python functions over blocks; large element-wise ones reached 87% of peak bandwidth.
  • Fusing bias + GELU was 25% faster than eager and saved its intermediate; torch.compile came within 5%.
