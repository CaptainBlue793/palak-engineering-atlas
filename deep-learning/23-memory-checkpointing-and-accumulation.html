Memory: Activations, Checkpointing & Accumulation

“CUDA out of memory” is the error every deep-learning practitioner meets first and most often. Fixing it well needs a picture of what is actually on the GPU during a step, and which of those things grows with the model, which with the batch, and which with the optimiser. This chapter measures that picture phase by phase on an 87-million-parameter transformer, then measures the two standard ways out: activation checkpointing, which recomputes instead of storing, and gradient accumulation, which splits a batch into pieces.

At a batch of 8 sequences of 1,024 tokens in fp32, the saved activations were 4.7 GB of a 5.8 GB peak; weights, gradients and AdamW’s state together were 1.3 GB. Activations grew with the number of tokens and not with the square of the sequence length. Checkpointing every block cut the peak by 69% for 24% more time per step, and raised the largest batch that fits from 32 to at least 96. Accumulating 4 micro-batches of 8 reproduced the batch-32 gradient to within 1 part in 10 million and needed 64% less memory, but with BatchNorm the two were no longer the same, and forgetting to divide the loss made every gradient exactly 4 times too large.

  • Account for every megabyte of a training step and know when each appears and goes
  • Predict how activation memory scales with batch size and sequence length
  • Apply activation checkpointing and choose how much of the network to checkpoint
  • Implement gradient accumulation correctly, and know where it is not exact
  • Order the fixes for an out-of-memory error from cheapest to most expensive

Four things in memory, and when they appear

The model: a byte-level GPT with 12 blocks of width 768, 87.0 million parameters, trained with AdamW in fp32 on batches of 8 sequences of 1,024 tokens. torch.cuda.memory_allocated() was read after each phase of the first two steps:

MomentStep 1Step 2What changed
Start333 MB1,014 MBweights (87.0M × 4 bytes = 332 MB), plus AdamW’s state from step 2 on
After forward5,012 MB5,684 MB+4.67 GB of activations saved for backward
After backward682 MB1,346 MBactivations freed, gradients (332 MB) created
After optimiser step1,346 MB1,346 MBstep 1 creates AdamW’s two moments (664 MB)
After zero_grad(set_to_none=True)1,014 MB1,014 MBgradients freed
Peak5,142 MB5,806 MBend of forward, start of backward

Three lessons sit in that table. The optimiser state is created lazily on the first step, so step 1 is not the peak: a run that survives its first step can still run out of memory on its second, and a memory test must run at least two. The fixed costs follow the parameter count: weights 4 bytes, gradients 4, AdamW 8, the familiar 16 bytes per parameter. And the activations dwarf them: 4.67 GB, 80% of the peak, and the only part that depends on the data.

torch.cuda.reset_peak_memory_stats()
loss = model(x, y); loss.backward(); opt.step(); opt.zero_grad(set_to_none=True)
print(torch.cuda.max_memory_allocated() / 2**20)   # the number that decides out-of-memory; measure step 2, not step 1

Activations grow with tokens

Every operation whose backward pass needs its input or output stores it: the input of each linear layer, the output of each normalisation, the pre-activation of each GELU. For this block that added up to about 16 vectors of width 768 per token per layer, or 0.58 MB per token across the model, and the peak grew by 593 MB for every extra 1,024 tokens. Measured both ways:

Shape (batch × length)TokensPeak memoryTime per step

Equal token counts gave equal memory, to the megabyte, whether the tokens came as more sequences or longer ones. That is not what the textbook formula for attention says: the attention matrix is length × length, so doubling the length should quadruple its memory. It did not here because F.scaled_dot_product_attention runs a fused kernel (FlashAttention or memory-efficient attention) that computes attention in tiles and never stores the full matrix, recomputing what it needs in the backward pass. The quadratic cost is still there in compute: 8,192 tokens as 4 × 2,048 took 22% longer than as 8 × 1,024. At small sizes the peak stops falling, around 1.7 GB, because it is then set by the optimiser step (weights, AdamW state, gradients and the update’s temporary buffers), not by activations.

Optimiser state and precision

The two levers on the fixed part are the optimiser and the number format. Measured at the same batch of 8 × 1,024:

ConfigurationHeld between stepsPeakTime per step
Plain SGD332 MB (weights)5,124 MB232 ms
SGD with momentum664 MB (+1 buffer)5,456 MB233 ms
AdamW996 MB (+2 buffers)5,788 MB239 ms
AdamW, bf16 autocast1,012 MB3,917 MB97 ms

Choosing SGD over AdamW saved 664 MB, 11% of this peak; bf16 autocast saved 1.9 GB, 32%, and ran 2.5 times faster, because most saved activations are now stored in 2 bytes instead of 4. The data-dependent part fell by about 40% rather than half, because autocast keeps some saved tensors, such as normalisation and loss inputs, in fp32. The weights, gradients and optimiser state stay fp32 under autocast. For a small model, activations are where the memory is; for a very large model the 16 bytes per parameter come to dominate, which is the regime of sharded optimisers in ML & AI Systems.

Activation checkpointing

Checkpointing a block means storing only its input during the forward pass and throwing away everything computed inside it. In the backward pass, when the block’s gradients are needed, its forward pass is run again from the stored input to rebuild the activations, which are used once and freed. Memory falls to one block’s worth of internals plus the stored inputs; the price is running the forward pass of the checkpointed blocks twice.

from torch.utils.checkpoint import checkpoint
for i, block in enumerate(self.blocks):
    x = checkpoint(block, x, use_reentrant=False) if i % every == 0 else block(x)
Blocks checkpointedPeak memoryTime per step
None5,788 MB238 ms
Every 4th (3 of 12)4,707 MB (−19%)253 ms (+6%)
Every 2nd (6 of 12)3,625 MB (−37%)267 ms (+12%)
Every block1,812 MB (−69%)296 ms (+24%)

The trade is linear: each checkpointed block saves about 330 MB and costs about 5 ms. The full cost, 24%, is within the usual rule of thumb of up to a third: one extra forward pass of every block. The point of checkpointing is what the saved memory buys. In bf16, without it the largest batch that fit was 32 sequences; with every block checkpointed, 96, the largest tried, still fit in 7.8 GB. Throughput fell from 93,600 to 78,700 tokens per second. So checkpointing is not a speed-up: it is how you fit a batch, a sequence length or a model that otherwise would not fit at all.

Gradient accumulation

The other way to fit a batch is to not hold it all at once. Split it into k micro-batches, run forward and backward on each, let the gradients add up in .grad, and take one optimiser step. Because the loss is a mean over examples, each micro-batch’s loss must be divided by k so that the sum of the parts equals the mean of the whole.

opt.zero_grad(set_to_none=True)
for xs, ys in zip(x.chunk(k), y.chunk(k)):
    (loss_fn(model(xs), ys) / k).backward()   # gradients add up; the / k makes the sum a mean
opt.step()

Checked in fp32 against a single batch of 32: splits of 2 × 16, 4 × 8, 8 × 4 and 32 × 1 all matched it to a relative difference of 1.3 to 1.5 × 10⁻⁷, which is float rounding from adding in a different order. Leaving out the / k with 4 micro-batches gave a gradient norm exactly 4.0 times too large. With plain SGD that is a learning rate 4 times too large; with Adam it mostly cancels (Adam divides by the gradient’s own scale), but gradient clipping thresholds and the balance against weight decay silently change, so the bug can sit unnoticed in an Adam run and appear when someone switches optimiser.

Exactness depends on every example’s loss being independent of the others in its batch, and one common layer breaks that. BatchNorm normalises with the statistics of the batch it sees, so a micro-batch of 8 is normalised differently from the full 64. On a small CIFAR-10 CNN the accumulated gradient’s cosine similarity to the true batch-64 gradient was 0.998 with 2 micro-batches, 0.986 with 8 and 0.954 with 32, a relative error of 31%; without BatchNorm it was identical. The update is still a reasonable gradient, but it is a batch-of-2 BatchNorm gradient, not a batch-of-64 one. LayerNorm, RMSNorm and GroupNorm work per example and accumulate exactly. Losses that average over a variable number of tokens per micro-batch have the same problem in a milder form: divide by the total token count of the whole batch, not by k.

What it costs, for the same 32-sequence update in bf16:

As long as each micro-batch keeps the GPU busy, splitting is nearly free, and the training is the same: a small model trained for 1,500 updates with batch 32 reached 2.055 bits per byte, and with 8 accumulated micro-batches of 4 reached 2.053, with curves that lie on top of each other (the small difference is bf16 rounding). On that small model each micro-batch of 4 sequences was too little work for the GPU, so the accumulated run took 74 seconds instead of 24. Use the largest micro-batch that fits, and accumulate only the rest.

Use case: a 3-D segmentation model on 512³ scans

A medical-imaging team trains a 3-D U-Net on CT volumes. One volume at full resolution needs 38 GB of activations, and their GPUs have 24 GB. They switch to bf16 autocast first (activations drop by about a third), then checkpoint the two highest-resolution encoder and decoder stages, which hold most of the activation memory, and leave the rest alone: the step is 15% slower and one volume fits. They want an effective batch of 8, so they accumulate 8 micro-batches of 1. Their network uses BatchNorm, which at a micro-batch of 1 normalises each volume by its own statistics and trains badly; they replace it with GroupNorm, which works per example, and accumulation becomes exact.

⚠️
Common mistakes
  • Testing memory on step 1: AdamW’s 664 MB appeared only at the first optimiser step; step 2’s peak was 664 MB higher.
  • Forgetting to divide the loss by k when accumulating: gradients were exactly 4 times too large.
  • Accumulating with BatchNorm and expecting the big-batch result: cosine 0.954 at 32 micro-batches. Use a per-example norm.
  • Checkpointing everything by default: it cost 24% of the step time; checkpoint only enough to fit.
  • Tiny micro-batches: 32 × 1 took 59% longer than 1 × 32. Fill the GPU first, then accumulate.
  • Reading nvidia-smi instead of max_memory_allocated: it shows the allocator’s reserved pool (P7).

Interview drill

Explain it simply: What uses GPU memory during training, and which part grows with the batch?

How a strong answer sounds
Four things. The weights, the gradients (same size as the weights, from backward until they are freed), the optimiser state (two more copies for Adam) and the activations saved in the forward pass for the backward pass. The first three are fixed per parameter, about 16 bytes with fp32 AdamW, and the optimiser state only appears at the first step, so the second step is the real peak. Activations scale with the number of tokens or examples in the batch. On an 87M-parameter transformer at 8 × 1,024 tokens they were 4.7 GB of a 5.8 GB peak, and with fused attention they grew with batch × length, not with length squared.

Deeper: Your model runs out of memory at the batch size you need. Walk through your options and their costs.

How a strong answer sounds
First bf16 autocast, which shrank the peak by a third and was faster. Then gradient accumulation with the largest micro-batch that fits: 4 × 8 instead of 1 × 32 used 64% less memory for 5% more time and gave the same gradient to 1e-7, provided I divide each micro-batch loss by the number of micro-batches and the model has no BatchNorm, which breaks the equivalence. If one micro-batch of the size I need still does not fit, activation checkpointing: every block cut memory by 69% for 24% more time, and partial checkpointing is linear in between, so I checkpoint only what I need. After that, a lighter optimiser state, and finally sharding across GPUs.

🧠 Key takeaways

  • Weights, gradients and AdamW state cost about 16 bytes per parameter; the optimiser state appears on step 1, so step 2 is the peak.
  • Activations were 80% of the peak and grew with tokens; fused attention removed the length-squared term from memory, not from compute.
  • Checkpointing every block: −69% memory, +24% time, three times the batch. It buys capacity, not speed.
  • Accumulation is exact to float rounding if each loss is divided by k and the model has no BatchNorm.
  • Fix out-of-memory errors in order: bf16, accumulation, checkpointing, optimiser state, sharding.
