Loss Functions for Neural Networks

P6 derived the standard losses from likelihood. This chapter is about using them: the form every framework wants (logits in, not probabilities), the variants that change what a network optimises (label smoothing, class weights, focal loss, Huber), and the problems they are meant to solve. A loss is the only thing a network is told about what you want, so a quiet change to it changes the model’s behaviour, sometimes in ways no accuracy number shows.

Four measurements on Fashion-MNIST and a house-price table. Label smoothing of 0.2 nudged accuracy up from 88.6% to 89.2% while making the model badly under-confident: its calibration error rose from 3.2% to 14.7%. For images containing two garments, independent sigmoids with binary cross-entropy and a softmax over normalised targets reached the same 67.6% exact-match accuracy. With only 111 training shirts, plain cross-entropy found 13% of the test shirts; class weights found 47%; focal loss, built for exactly this, found 11%. And when 5% of house prices were recorded ten times too high, an MSE-trained network’s error nearly tripled (RMSE 1.38) while L1 and Huber barely moved (0.51 and 0.53).

  • Feed losses logits, and use the multi-label and binary forms correctly
  • Know what label smoothing does to accuracy and to confidence
  • Handle a rare class with weights, focal loss or thresholds, and measure the result
  • Choose MSE, L1 or Huber from how outliers should be treated
  • Read a reliability diagram

Cross-entropy from logits

For one label per example out of K, the network outputs K logits and F.cross_entropy(logits, y) computes log-softmax and the negative log-likelihood in one numerically stable step. For yes/no outputs and for multi-label problems, where several labels can be true at once, each label gets its own logit and its own sigmoid, and F.binary_cross_entropy_with_logits(logits, targets) treats each as an independent yes/no question. Both take raw logits; P3 measured what happens when they are handed probabilities instead.

loss = F.cross_entropy(logits, y)                              # logits (B, K), y (B,) integer classes
loss = F.cross_entropy(logits, y, label_smoothing=0.1)       # soft targets: 0.9 + 0.1/K on the true class
loss = F.cross_entropy(logits, y, weight=w)                    # w (K,): per-class weights
loss = F.binary_cross_entropy_with_logits(logits, t)          # logits (B, K), t (B, K) in {0, 1}: multi-label
loss = F.huber_loss(pred, target, delta=1.0)                 # squared near 0, linear beyond |e| = delta

Binary and multi-label losses

A multi-label task, built here from Fashion-MNIST: each 56 × 28 image is two garments side by side, and the target is the set of classes present (two classes in 89.6% of images, one class when both halves happen to be the same kind). The principled loss is one sigmoid and BCE per class: each output answers “is there a coat?” independently, and a threshold of 0.5 decides. The tempting alternative is a softmax over the classes with the target spread evenly over the classes present. Measured with the same network and training:

LossPrediction ruleExact match (all labels right)Label F1
Per-label sigmoid + BCEp > 0.5 for each label67.58%86.15%
Softmax + cross-entropy on normalised targetsp > 0.25 (best of 5 thresholds)67.62%86.08%
Per-label sigmoid + BCEtop k, with k given75.82%86.73%
Softmax + cross-entropytop k, with k given76.12%86.88%

On this task they tied. The difference is in what each assumes: softmax makes the labels compete for one unit of probability, so its threshold depends on how many labels are present (0.25 worked here, where most images have two), while sigmoids give each label its own probability, which still means the same thing when an image can have one label or ten. When the label count varies a lot, or labels are not mutually exclusive in any sense, BCE is the right default. Knowing k exactly is worth 8 points to either, which is why tasks that do know it (“pick the top 5 tags”) should say so.

Label smoothing

Cross-entropy with one-hot targets keeps rewarding the network for pushing the true logit further above the rest, forever: a confident correct prediction still has a positive loss. Label smoothing replaces the target 1 with 1 − ε + ε/K and every 0 with ε/K, so the optimum is a finite margin. It was introduced to stop over-confidence and often helps accuracy slightly. Measured over two seeds:

Smoothing εTest accuracyMean confidenceCalibration error (ECE)Logit gap (max − mean)
088.62%0.9173.15%15.25

Accuracy rose by half a point, and the logits shrank fourfold, as intended. But this MLP was not over-confident to begin with (an ECE of 3.2%), so smoothing pushed it into under-confidence: with ε = 0.2, predictions it gave about 0.77 confidence were right 96% of the time. Expected calibration error, the average gap between confidence and accuracy across confidence bins, nearly quintupled. If you need the probabilities, for thresholds, ranking or downstream decisions, smoothing is not free; fix calibration afterwards with temperature scaling (Chapter 31), or skip it. It also makes features less useful for distillation (Chapter 32), because the teacher’s soft probabilities carry less information.

Class weights and focal loss

When one class is rare, cross-entropy is dominated by the common ones, and the network learns that predicting “not the rare class” is usually right. Two fixes change the loss. Class weights multiply each example’s loss by a weight, typically inversely proportional to its class frequency, so the rare class counts as much in total. Focal loss (Lin et al., 2017, for dense object detection) multiplies each example’s loss by (1 − ptrue)γ, shrinking the contribution of examples the model already gets right so the hard ones dominate. Measured with shirts cut to 111 training examples against about 6,000 of every other class:

LossShirt recallShirt precisionShirt average precisionOverall accuracy
Cross-entropy13.2%98.9%67.6%84.9%
Weighted cross-entropy (shirts × 8.6)47.2%67.3%65.4%86.0%
Focal loss, γ = 210.8%98.5%61.2%84.4%

Class weights moved the decision boundary: three and a half times as many test shirts found, at the price of more false alarms, and overall accuracy even rose because the 1,000 test shirts are not rare at test time. But average precision, which measures how well the shirt probability ranks shirts above non-shirts regardless of threshold, barely changed (67.6% to 65.4%): the unweighted model already ranked them as well and simply used too high a threshold. Lowering its threshold would have bought most of the same recall. Focal loss did not help here at all. It targets a different problem, a flood of easy negatives that swamp the gradient, as in object detection with 100,000 background boxes per image; with ten balanced-ish classes and one small one, down-weighting easy examples took signal away from the rare class too.

Regression losses and outliers

The gradient of a regression loss with respect to the prediction says how hard each example pulls. MSE’s gradient is the residual e itself, so an example 10 units off pulls ten times harder than one 1 unit off. L1’s gradient is ±1 whatever the size of the error. Huber is MSE for |e| ≤ δ and L1 beyond: smooth near zero, bounded far away. When 5% of California house prices in the training set were multiplied by ten, as a unit error might do:

LossTest RMSE, clean training dataTest RMSE, 5% corruptedTest MAE, 5% corrupted
MSE0.5061.3841.050
L10.5030.5090.339
Huber (δ = 1)0.5020.5250.362

On clean data all three agreed. With corrupted targets the MSE model chased the outliers: its median prediction rose from 1.87 to 2.68 (in $100,000s, against a test median of 1.78), and its error nearly tripled. L1 and Huber ignored them almost entirely. MSE is still right when large errors are genuine and expensive (it targets the mean, P6); Huber is the usual compromise when they might be data errors.

Use case: a fraud model that “improved” its accuracy

A payments team retrains its fraud classifier with label smoothing because a blog post said it generalises better. Accuracy on the validation set rises by 0.3 points. Two weeks later the operations team notices that the number of transactions flagged for manual review has dropped by a third: the review queue uses a fixed threshold of 0.8 on the fraud probability, and the smoothed model now rarely says anything above 0.8. Nothing about which transactions are riskiest changed, only the scale of the scores. The team adds calibration error to the release checklist and recalibrates the model with temperature scaling before setting thresholds.

⚠️
Common mistakes
  • Label smoothing when the probabilities matter: it raised accuracy 0.6 points and calibration error from 3.2% to 14.7%.
  • Reaching for focal loss for any imbalance: with one rare class among ten it did worse than plain cross-entropy here.
  • Judging an imbalance fix by accuracy: report recall, precision and average precision for the rare class.
  • MSE on targets with data errors: 5% corrupted prices nearly tripled the test RMSE.
  • Softmax for labels that can co-occur with varying counts: its threshold depends on the label count; use BCE.
  • Probabilities instead of logits into any of these losses (P3).

Interview drill

Explain it simply: What does label smoothing do, and when would you avoid it?

How a strong answer sounds
It replaces one-hot targets with soft ones, 1 − ε plus a share of ε on the true class and ε/K on the others, so the network is no longer rewarded for making its logits ever larger. That acts as a regulariser and often adds a little accuracy. The side effect is that the model’s probabilities shrink. I measured an MLP on Fashion-MNIST: ε = 0.2 raised accuracy from 88.6% to 89.2%, but mean confidence fell from 0.92 to 0.74 and calibration error rose from 3.2% to 14.7%, because the model had not been over-confident to begin with. So I would avoid it, or recalibrate afterwards, whenever probabilities feed thresholds, ranking or another model.

Deeper: One class has 2% of the training data. Compare class weights, focal loss and changing the threshold.

How a strong answer sounds
Class weights make each rare example count more in the loss, which moves the decision boundary towards the common classes and raises recall at the cost of precision. Focal loss down-weights easy examples; it was designed for detection, where easy background boxes outnumber objects a thousand to one, and does not necessarily help a single rare class. Changing the threshold leaves training alone and only moves the decision point. I would look at the rare class’s average precision first: if the model already ranks it well, a lower threshold gets most of the recall. In a measured case with 111 rare training examples, weights raised recall from 13% to 47% while average precision stayed about 66%, and focal loss lowered recall to 11%.

🧠 Key takeaways

  • Losses take logits: cross_entropy for one label, BCE with logits per label for several.
  • Label smoothing shrinks logits and can add accuracy (88.6% → 89.2%), but it changes calibration (ECE 3.2% → 14.7%).
  • For a rare class, weights moved recall from 13% to 47%; average precision barely moved, so a threshold could do much of it. Focal loss did not help.
  • MSE pulls in proportion to the error; L1 and Huber have bounded pull and shrugged off 5% corrupted targets (RMSE 0.51 vs 1.38).
  • Always measure the quantity you care about, not just the loss or the accuracy.
