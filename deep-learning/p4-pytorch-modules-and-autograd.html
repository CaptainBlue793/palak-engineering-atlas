PyTorch Essentials: Modules & Autograd

Every model in this course is an nn.Module, every gradient comes from autograd, and every training run is the same five lines: forward, loss, zero the gradients, backward, step. Chapter 3 builds an autograd engine from scratch so you see what is inside; this prerequisite is the user’s view, the parts of PyTorch you will call thousands of times and the ways they fail quietly.

Four failures are measured on Fashion-MNIST. Two hidden layers kept in a plain Python list instead of an nn.ModuleList were invisible to the optimiser: 266,752 of the model’s 269,322 parameters never moved, test accuracy was 75.8% instead of 87.1%, and the saved checkpoint did not contain them at all. Forgetting zero_grad() took SGD from 85.2% to 10.0%, which is chance. Running a forward pass with autograd on held 896 MB at peak against 256 MB under no_grad. And calling backward twice, or editing a tensor in place, raises errors you should recognise on sight.

  • Write an nn.Module whose parameters are all registered
  • Read the graph autograd records, and know what a leaf is
  • Run the training step in the right order, including zero_grad
  • Use no_grad, inference_mode and detach for evaluation and frozen parts
  • Save and load a model with state_dict

nn.Module and parameters

A module is a Python class with two jobs: hold parameters (tensors the optimiser should update) and define forward. When you assign an nn.Linear, an nn.Parameter or another module as an attribute, nn.Module.__setattr__ registers it, and from then on model.parameters(), model.to("cuda"), model.state_dict() and model.train() all find it. Anything it does not recognise, such as a plain Python list of layers, is just an attribute: it still runs in forward, but nothing else knows it exists.

class MLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.hidden = nn.ModuleList([nn.Linear(784, 256), nn.Linear(256, 256)])   # registered
        # self.hidden = [nn.Linear(784, 256), nn.Linear(256, 256)]   # NOT registered: the optimiser never sees them
        self.head = nn.Linear(256, 10)
    def forward(self, x):                        # x (B, 784)
        for layer in self.hidden: x = F.relu(layer(x))   # (B, 256)
        return self.head(x)                         # (B, 10) logits

sum(p.numel() for p in model.parameters())       # 269,322 with ModuleList; 2,570 with a plain list

The plain-list version is a perfect silent bug. If the layers are created on the GPU it runs without an error, the loss falls (the head alone can learn something from random features), and it reaches 75.8% where the registered version reached 87.1% in three epochs. Its state_dict contains only head.weight and head.bias, so a saved checkpoint cannot even reproduce it. Use nn.ModuleList, nn.ModuleDict or nn.Sequential for collections of layers, and nn.Parameter (or register_buffer for non-trained state such as running statistics) for raw tensors.

The autograd graph

When a tensor with requires_grad=True takes part in an operation, PyTorch records a node for it: the result’s grad_fn knows which operation made it and holds links (next_functions) to the nodes that made its inputs. Tensors you create yourself with requires_grad=True, like weights, are leaves; their node is AccumulateGrad, which adds the incoming gradient into .grad. Calling backward() on a scalar walks this graph from the end, applies each node’s local derivative (P2’s vector-Jacobian products) and frees the graph’s saved tensors as it goes.

a = torch.tensor(2.0, requires_grad=True); b = torch.tensor(-3.0, requires_grad=True)
L = torch.tanh(a * b + a) ** 2
L.grad_fn                       # PowBackward0 -> TanhBackward0 -> AddBackward0 -> MulBackward0 -> AccumulateGrad (a, b)
L.backward()
a.grad, b.grad                  # (0.00536, -0.00536)
L.backward()                    # RuntimeError: Trying to backward through the graph a second time ...
y = x.sigmoid(); y.mul_(2); y.sum().backward()   # RuntimeError: one of the variables needed for gradient computation
                                                 #   has been modified by an inplace operation

Both errors are protections. The first appears because the graph was freed after the first backward; pass retain_graph=True only if you really need two backward passes through the same graph. The second appears because sigmoid’s backward needs its own output, and the in-place multiply overwrote it; PyTorch tracks a version counter on every tensor and refuses to compute a wrong gradient.

backward(), zero_grad() and the training step

Gradients accumulate: each backward adds into .grad rather than replacing it. That is deliberate (it lets you sum gradients over several small batches, Chapter 23), and it is why every training step must clear them first.

model = MLP().to("cuda"); opt = torch.optim.Adam(model.parameters(), lr=1e-3)
for epoch in range(3):
    model.train()                              # dropout and batch norm in training mode
    for xb, yb in train_loader:                  # xb (128, 784), yb (128,)
        loss = F.cross_entropy(model(xb), yb)   # scalar
        opt.zero_grad()                        # sets .grad to None (the default since PyTorch 2.0)
        loss.backward()
        opt.step()
    model.eval()
    with torch.no_grad():                       # no graph: less memory
        acc = (model(x_test).argmax(1) == y_test).float().mean()

Without zero_grad(), step t uses the sum of every gradient so far. With SGD at learning rate 0.05 that sum keeps growing, each step is larger than the last, and the loss rose from 0.90 to 2.8 within 400 steps; the network ended at 10.0% accuracy, chance for ten classes. Adam normalises step sizes, so it survived longer but still reached only 23.2%, against 85.2% (SGD) and 86.7% (Adam) with the line in place.

no_grad, inference_mode and detach

Recording the graph has a cost: every operation keeps the tensors its backward will need. For a forward pass of a 784-4096-4096-4096-10 MLP on 8,192 examples, peak memory above the weights was 896 MB with autograd and 256 MB without, 3.5 times less, at the same speed (23 ms), because the forward arithmetic is identical. Turn recording off whenever you do not need gradients:

ToolWhat it doesUse it forMeasured peak (8,192 batch)
(nothing)Records the graph, keeps activationsTraining896.3 MB
torch.no_grad()No graph inside the blockEvaluation, updating weights by hand256.3 MB
torch.inference_mode()No graph, and skips version tracking; its tensors can never enter autograd laterServing, pure inference256.3 MB
t.detach()A view of one tensor cut out of the graphTargets computed from the model, logging, stopping gradient through one branch—
p.requires_grad_(False)The parameter stops being a leaf that receives gradientsFreezing layers in fine-tuning (Chapter 28)—

Do not confuse no_grad with model.eval(). eval() changes the behaviour of dropout and batch-norm layers (Chapters 13 and 14) and does nothing to autograd; no_grad stops autograd and does nothing to those layers. Evaluation needs both.

Saving and loading state

A state_dict is an ordered dictionary from names to tensors: every registered parameter and buffer, nothing else. Save it, not the module object, because pickling the whole module ties the file to your exact class and file layout.

torch.save(model.state_dict(), "mlp.pt")     # 1.08 MB: '0.weight', '0.bias', '2.weight', ... for nn.Sequential
model2 = make_model(); model2.load_state_dict(torch.load("mlp.pt"))   # identical outputs: torch.equal is True
# a model built with a 512-wide first layer refuses the file:
# size mismatch for 0.weight: copying a param with shape torch.Size([256, 784]) from checkpoint,
# the shape in current model is torch.Size([512, 784]).
# to resume training, also save opt.state_dict(): Adam's moment estimates are part of the state

Use case: the checkpoint that was 1% of the model

A team building a product-recommendation model refactors its towers into a loop over self.towers = [Tower(...) for _ in range(4)]. Training looks fine on the dashboard, a little worse than before. The checkpoint file shrinks from 180 MB to 2 MB, which nobody notices until a reload in the serving cluster produces random recommendations: the towers were never registered, so the optimiser never trained them, state_dict never saved them, and the serving copy initialised them fresh. Changing one line to nn.ModuleList fixes all three. The team adds a test that compares the parameter count against a hand-computed number.

⚠️
Common mistakes
  • Layers in a plain list or dict: not registered, not trained, not saved. Measured: 2,570 of 269,322 parameters seen, 75.8% vs 87.1%.
  • Forgetting zero_grad(): gradients accumulate and steps grow; SGD fell to 10.0% (chance).
  • Evaluating without no_grad: 3.5 times the memory for nothing.
  • Confusing eval() with no_grad(): you need both for evaluation, for different reasons.
  • In-place edits of tensors autograd saved: PyTorch raises rather than compute a wrong gradient; use the out-of-place version.
  • Saving the module object instead of its state_dict, or saving the model but not the optimiser when you mean to resume.

Interview drill

Explain it simply: Why do you call optimizer.zero_grad() in every training step?

How a strong answer sounds
Because backward() adds gradients into each parameter’s .grad instead of overwriting it. That is useful when you deliberately accumulate gradients over several micro-batches, but in a normal loop it means step t would use the sum of all gradients so far, so steps keep growing and training diverges or stalls. I measured it on Fashion-MNIST: SGD went from 85.2% to 10.0%, chance, and Adam from 86.7% to 23.2%. Since PyTorch 2.0, zero_grad() sets the gradients to None by default, which also saves a memory write.

Deeper: A model trains, but much worse than expected, and its checkpoint file is far smaller than the parameter count suggests. What do you look for?

How a strong answer sounds
Unregistered parameters. nn.Module only tracks submodules and parameters assigned as attributes of the right types; layers stored in a plain Python list or dict still run in forward but are invisible to parameters(), so the optimiser never updates them, and to state_dict(), so they are never saved, and to .to(device). I would compare sum(p.numel() for p in model.parameters()) with the expected count and print the state_dict keys. In a measured case two hidden layers in a list left 2,570 of 269,322 parameters trainable and cost 11 points of accuracy. The fix is nn.ModuleList or nn.ModuleDict.

🧠 Key takeaways

  • An nn.Module registers parameters and submodules assigned as attributes; plain lists and dicts are invisible to it.
  • Autograd records a graph of grad_fn nodes; backward() walks it once, fills leaves’ .grad and frees it.
  • Gradients accumulate, so clear them every step: without zero_grad() SGD fell to chance.
  • no_grad and inference_mode cut forward memory 3.5× here; eval() is a separate switch for dropout and batch norm.
  • Save state_dict()s, for the model and for the optimiser when resuming.
