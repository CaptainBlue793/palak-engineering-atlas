Normalisation Layers: Batch, Layer & RMS

Chapter 9 fixed the scale of the signal once, at initialisation. Training changes the weights, and with them the scale and offset of every layer’s activations, so a careful start does not stay careful. Normalisation layers re-standardise activations inside the network on every forward pass: subtract a mean, divide by a standard deviation, then let two learned parameters set the scale and offset the next layer actually wants. Every modern architecture has them. The four common kinds differ only in which numbers they average over, and that one choice decides when each works.

All four are written by hand here and match PyTorch to within 10⁻⁶. In a CIFAR-10 CNN, BatchNorm lifted test accuracy from 82.1% to 88.1% at batch 128; at batch 4 it still led (83.6%), and GroupNorm and LayerNorm fell below no normalisation at all. In a 20-layer MLP left with PyTorch’s default initialisation, only BatchNorm trained (86.8%); LayerNorm and RMSNorm stayed at 10%, and measuring the activations shows exactly why. And evaluating a BatchNorm model in training mode, one image at a time, dropped its accuracy from 88.1% to 11.2%.

  • Know which axes each normalises over, and what that implies

  • Choose a normalisation for CNNs, small batches and transformers

Why normalise activations

A layer’s output is only useful to the next layer if it is on a scale that layer’s weights and activation can work with: ReLU wants inputs around zero, tanh saturates on large ones, and the gradient flowing back depends on both. As the weights change during training, every layer’s input distribution shifts and the layers after it must keep re-adapting. Normalisation pins each layer’s input to mean 0 and variance 1, then applies a learned scale γ and shift β, so the network can still choose any distribution it likes, but now explicitly and stably. In practice it also makes training far less sensitive to initialisation and learning rate, and lets much higher learning rates work.

def batch_norm(x):   m = x.mean((0, 2, 3), keepdim=True); v = x.var((0, 2, 3), keepdim=True, unbiased=False); return (x - m) / (v + eps).sqrt()
def layer_norm(x):   m = x.mean(-1, keepdim=True);       v = x.var(-1, keepdim=True, unbiased=False);       return (x - m) / (v + eps).sqrt()
def rms_norm(x):     return x / (x.pow(2).mean(-1, keepdim=True) + eps).sqrt()         # no mean subtracted
def group_norm(x, G): B, C, H, W = x.shape; g = x.view(B, G, -1)                          # channels split into G groups
    return ((g - g.mean(-1, keepdim=True)) / (g.var(-1, keepdim=True, unbiased=False) + eps).sqrt()).view(B, C, H, W)
# each is followed by y = gamma * x_hat + beta (learned, one pair per channel or feature)

BatchNorm and running statistics

BatchNorm (Ioffe and Szegedy, 2015) averages each channel over the batch and the spatial positions. That makes its output depend on which other examples share the batch, which is a problem at prediction time, when there may be only one. So during training it also keeps an exponential moving average of each channel’s mean and variance, the running statistics, and in evaluation mode it uses those instead of the batch’s. This is why model.eval() matters so much for any network with BatchNorm. Measured on the trained CIFAR-10 CNN:

With large test batches the mistake is invisible: the batch’s statistics are close to the running ones (here even slightly better). Served one request at a time, each channel is normalised over one image’s pixels alone, the features that distinguish classes are largely subtracted away, and the model is barely better than chance. This is one of the most common deployment bugs in deep learning, and it is silent in any offline evaluation that uses big batches. Train mode also updates the running statistics, so evaluating in train mode quietly corrupts them as well.

LayerNorm and RMSNorm

LayerNorm (Ba et al., 2016) averages over the features of one example, so it behaves identically in training and evaluation and at any batch size, including 1. That is why transformers use it: sequence models are often trained with small or variable batches, and each token is normalised on its own. RMSNorm (Zhang and Sennrich, 2019) drops the mean subtraction and divides by the root mean square only, which is cheaper and works as well in transformers; LLaMA and most recent language models use it. GroupNorm (Wu and He, 2018) sits in between for images: it averages over groups of channels within one example; with one group it is LayerNorm over (C, H, W), with C groups it is InstanceNorm.

A 20-layer MLP: why only BatchNorm rescued it

Chapter 9’s 20-layer ReLU MLP with PyTorch’s default initialisation never trained, because the input’s signal faded and the activations became an almost constant pattern set by the random biases. Adding a normalisation layer after each linear layer should fix that. It did, but only for one kind: with BatchNorm the network reached 86.8% in five epochs; with LayerNorm or RMSNorm it stayed at exactly 10%. The reason is in what each removes. At layer 10, two different images’ pre-activations had a cosine similarity of 0.87: nearly the same vector, the bias pattern, plus a small image-dependent part. LayerNorm and RMSNorm normalise each example on its own, so they rescale that vector but keep its shape: the similarity was still 0.87 afterwards, and the image information stayed buried. BatchNorm subtracts each feature’s mean across the batch, which removes exactly the part that is the same for every image; afterwards the similarity was 0.01, and what remained was the image-dependent signal, amplified to unit variance. With Kaiming initialisation and zero biases there is no shared pattern to remove, and all three, LayerNorm 85.9%, RMSNorm 85.6% and BatchNorm 85.4%, trained, as did the network without any normalisation (85.8%).

Train vs eval mode bugs

Because BatchNorm behaves differently in the two modes, it is behind a family of bugs: serving in train mode (11.2% here); evaluating with a batch of one in train mode during development and getting nonsense; fine-tuning on a new dataset with batch size 2, where noisy batch statistics overwrite good running statistics; and models whose layers are frozen with requires_grad_(False) but whose BatchNorm layers keep updating their running statistics because the model is in train mode. The checklist: call model.eval() for every evaluation and in serving; when fine-tuning with small batches, keep BatchNorm layers in eval mode; and test the deployed model with batch size 1.

Use case: the photo filter that worked in the notebook

A mobile team exports an image classifier that scored 91% in the notebook. In the app, where it sees one photo at a time, accuracy is terrible and results change when the same photo is processed twice in a row alongside different photos. The export script never called model.eval(), so every BatchNorm layer normalised each photo by its own statistics. The notebook evaluation had used batches of 256, where the bug was invisible. One line fixes it; the team adds a batch-size-1 test to their export pipeline.

⚠️
Common mistakes
  • Serving a BatchNorm model in train mode: 88.1% → 11.2% on single images, invisible with big test batches.
  • Assuming any normalisation rescues a bad initialisation: LayerNorm and RMSNorm preserved the shared bias pattern and did not.
  • BatchNorm with batches of 1 or 2 in training: noisy statistics; use GroupNorm or freeze the statistics.
  • A bias in the layer before BatchNorm: BatchNorm subtracts the mean, so the bias does nothing; set bias=False.
  • Weight decay on γ and β: exclude normalisation parameters from decay.

Interview drill

Explain it simply: What is the difference between BatchNorm and LayerNorm, and why do transformers use LayerNorm?

How a strong answer sounds
Both standardise activations to mean 0 and variance 1 and then apply a learned scale and shift; they differ in what they average over. BatchNorm averages each channel over the examples in the batch, so it depends on the batch and needs running statistics at inference. LayerNorm averages over the features of each example separately, so it behaves the same in training and inference at any batch size. Transformers use LayerNorm, or RMSNorm, because each token is normalised on its own, sequence batches are often small or variable, and there is no need for running statistics. One measured consequence: BatchNorm removes anything that is the same for every example in the batch, LayerNorm does not, which is why in my experiment only BatchNorm rescued a badly initialised deep MLP.

Deeper: A model with BatchNorm scores well offline and badly in production. What do you check?

How a strong answer sounds
First that the serving code calls model.eval(), so BatchNorm uses its running statistics instead of each request’s own. In train mode a single-image request is normalised by its own statistics; I measured a CIFAR model going from 88% to 11% that way, while batches of 250 in train mode looked fine. Second, that the running statistics were not corrupted during fine-tuning or by evaluating in train mode. Third, that preprocessing matches training. The regression test is to run the exported model on a handful of images one at a time and compare against the training framework’s outputs in eval mode.

🧠 Key takeaways

  • Normalisation standardises activations then applies a learned scale and shift; the variants differ only in the axes averaged.
  • BatchNorm averages over the batch and needs running statistics; served in train mode one image at a time it fell to 11.2%.
  • LayerNorm and RMSNorm work per example, at any batch size: the choice for transformers.
  • In a CIFAR CNN BatchNorm led at batch 128 (88.1%) and batch 4 (83.6%).
  • BatchNorm removes what is shared across the batch; LayerNorm keeps it, which is why only BatchNorm rescued a badly initialised deep MLP.

Check your understanding

For a (B, C, H, W) tensor, which axes does BatchNorm average over?

One mean and variance per channel, computed across the batch and positions.

Why did a BatchNorm model fall to 11.2% when evaluated in train mode one image at a time?

model.eval() makes it use the running statistics: 88.1%.

Why do transformers use LayerNorm rather than BatchNorm?

RMSNorm, which skips the mean, is the modern variant.

A 20-layer MLP with default initialisation trained with BatchNorm but not with LayerNorm. What did the measurement show?

With Kaiming initialisation and zero biases all of them trained.

Why set bias=False on a convolution followed by BatchNorm?

The bias would be a wasted parameter.
