Reproducibility & GPU Nondeterminism

Run the same training script twice and you may get two different models. Some of the difference is intended randomness that a seed controls: the initial weights, the data order, dropout masks, augmentation. Some is not: GPU kernels that add numbers in whatever order their threads finish, libraries that pick a different algorithm on each run, and floating-point addition, whose result depends on that order. Reproducibility means knowing which sources you have controlled, and the rest of the chapter is about what to do with the variation that remains.

Measured on a CIFAR-10 CNN, in fresh processes with the same seed: by default the two runs produced bitwise-identical weights; with cudnn.benchmark switched on they did not (a weight difference of 0.039 after two epochs); with PyTorch’s deterministic mode they were identical again, at no measurable cost for this network. An index_add_ on a million numbers gave 20 different answers in 20 calls. Then the question that matters for research: across 10 seeds the CNN’s accuracy ranged over 0.58 points, a label-smoothing gain of 0.28 points was statistically clear, and yet comparing one seed of each would have ranked the two the wrong way round 13% of the time.

  • List the sources of randomness in training and how to control each one
  • Explain why some GPU kernels are nondeterministic and which ones
  • Use deterministic mode and measure what it costs
  • Measure seed variance and separate initialisation from data-order noise
  • Decide how many seeds a comparison needs and report results honestly

The last row is the one people forget: bitwise reproducibility holds on one GPU model with one version of the driver, CUDA, cuDNN and PyTorch. A different GPU picks different kernels, so the target across machines is reproducing the distribution of results, not the bits.

Nondeterministic GPU kernels

A GPU sums thousands of values in parallel, and when many threads add into the same memory location they use atomic adds, which complete in whatever order the hardware schedules them. Floating-point addition is not associative, so a different order gives a different rounding. Scattering a million random numbers into 100 bins with index_add_, 20 times with identical inputs, gave 20 distinct results, differing by up to 1.2 × 10⁻³ on bin totals of about 78. The order effect itself, summing ten million random numbers in fp32:

Every order gave a different answer, and sorting, which pushes the running total far from zero before the positive values arrive, lost nearly half a unit. The differences inside one training step are tiny, but training is chaotic: a difference in the last bit of one gradient changes the next update, which changes every later one, and two runs drift apart until they end at different accuracies (P8 showed a CNN doing this).

Deterministic mode and its cost

torch.use_deterministic_algorithms(True) makes PyTorch use deterministic implementations where they exist and raise an error, naming the operation, where they do not; cuBLAS also needs the environment variable CUBLAS_WORKSPACE_CONFIG=:4096:8. Each mode was run twice for two epochs, each time in a fresh process with the same seed:

ModeWeights identical across runs?Largest weight differenceTime for 2 epochs
Default (cudnn.benchmark = False)yes04.0 s
cudnn.benchmark = Trueno0.0399.8 s
Deterministic algorithmsyes03.8 s

For this network the default kernels were already deterministic; the variation came from cudnn.benchmark, which times several convolution algorithms on the first call and keeps the fastest, and the fastest can differ from run to run when two are close. It was also slower here, most likely because the timing trials run again for every new input shape (the smaller last batch, the evaluation batches) and a two-epoch run never earns them back. Deterministic mode cost nothing measurable. That is not universal: P8 measured a different CNN whose convolution backward was nondeterministic by default, and operations such as scatter-adds, embedding backward with repeated indices, and some pooling and interpolation backwards fall back to slower deterministic versions, or have none. Turn it on, time a step, and keep it if the cost is acceptable.

# before CUDA is initialised
os.environ["CUBLAS_WORKSPACE_CONFIG"] = ":4096:8"
torch.use_deterministic_algorithms(True)          # errors on ops with no deterministic version
torch.backends.cudnn.benchmark = False
torch.manual_seed(0); g = torch.Generator(device="cuda").manual_seed(0)   # one generator per random stream

Seed variance in results

Determinism makes a run repeatable; it does not make it representative. A different seed is a different, equally valid run. Ten seeds of the CNN, 15 epochs each:

What variedSeedsMeanStandard deviationRange
Initialisation and data order1089.01%0.1888.73 – 89.31

Data order only588.83%0.0588.76 – 88.90
Label smoothing 0.1 (both varied)1089.29%0.1888.90 – 89.50

Most of this network’s run-to-run spread came from the initialisation; varying only the data order moved accuracy three times less, although five seeds is too few to rank the two sources firmly. Either way, the spread is the yardstick for every comparison: a change smaller than about 0.2 points cannot be seen with one run of each.

Reporting results honestly

Label smoothing raised the mean by 0.28 points. With 10 seeds each, Welch’s t-test gave p = 0.004: a real if small effect. But among the 100 ways of pairing one baseline seed with one label-smoothing seed, the baseline came out ahead in 13. A paper comparing one run of each would have reported the wrong winner one time in eight, for an effect that genuinely exists; for a smaller effect it becomes a coin toss, as P8 found. The habits that follow:

  • Run several seeds of every configuration you compare, five as a minimum and more when the expected effect is near the seed spread, and report the mean and the spread.
  • Use the same seeds for both arms where possible and compare seed by seed, which removes shared noise.
  • Fix the evaluation set and the metric before looking at results, and report every configuration you tried, not only the winner (Chapter 25’s winner’s curse).
  • Record the environment: GPU, driver, CUDA, cuDNN, PyTorch, and the commit of the code.
⚖️
Use case: a model audit that must be reproduced

A lender’s credit model must be reproducible for regulators: an auditor re-runs training from the archived code and data and expects the same model. The team’s first attempt differs in the fifth decimal place, enough to change a handful of decisions at the threshold. They pin the container image and GPU type, seed every random stream, set cudnn.benchmark = False and turn on deterministic mode, which raises an error on one scatter operation in their feature pipeline; they replace it with a sorted, deterministic version. Two runs now match bit for bit. Separately, they report the model’s performance as the mean over five seeds, because the regulator also asks how much a retraining could change the outcome.

⚠️
Common mistakes
  • Seeding only torch: data order, augmentation and worker processes need their own seeded generators.
  • Leaving cudnn.benchmark on when you need identical runs: it changed the weights by 0.039 in two epochs.
  • Expecting bitwise reproducibility across GPUs or library versions: different hardware picks different kernels.
  • Reporting one seed: one seed per side reversed a real 0.28-point gain 13% of the time.
  • Mistaking determinism for reliability: a deterministic run is still one sample from the seed distribution.
  • Assuming deterministic mode is expensive, or free: it cost nothing here; measure it on your model.

Interview drill

Explain it simply: You set the seed and still get different results each run. Why?

How a strong answer sounds
Either something random is not seeded (the DataLoader’s shuffle, worker processes, augmentation, a separate library), or a GPU operation is nondeterministic. Some kernels use atomic floating-point adds, whose order varies, and floating-point addition is not associative: an index_add_ gave 20 different answers in 20 identical calls. cuDNN’s benchmark mode can also choose different algorithms per run; in my measurement it was the only thing that made two same-seed CNN runs differ. The fixes are cudnn.benchmark off, torch.use_deterministic_algorithms(True) with the cuBLAS workspace variable, and the same software and hardware stack.

Deeper: How many seeds do you need to claim one configuration beats another?

How a strong answer sounds
Enough that the difference is clearly larger than its standard error, which depends on the seed spread and the size of the effect. On a CIFAR CNN the spread was about 0.18 points; label smoothing gained 0.28 points, which ten seeds per side established at p = 0.004, but comparing a single seed of each got the order wrong 13% of the time. So five seeds as a minimum, ten when the effect is near the spread, paired seeds where possible, and I report the mean and spread of every configuration I tried rather than the best run.

🧠 Key takeaways

  • Seeds control intended randomness; nondeterministic kernels and algorithm selection are separate sources.
  • Atomic adds made index_add_ give 20 answers in 20 calls; addition order changes float sums.
  • Here, only cudnn.benchmark broke bitwise reproducibility; deterministic mode cost nothing measurable.
  • Reproducible is not representative: 10 seeds spanned 0.58 points, mostly from initialisation.
  • One seed per side reversed a real 0.28-point gain 13% of the time; report means and spreads.
