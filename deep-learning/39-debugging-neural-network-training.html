Debugging Neural Network Training

Neural network bugs are unusually hard to see. Ordinary code that is wrong usually crashes or prints the wrong answer; a training script that is wrong usually runs, prints a loss that goes down a little, and produces a model that is somewhat worse than it should be, with nothing to say why. The only defence is a set of cheap checks that each catch a class of mistakes, applied before trusting a result.

This chapter measures that defence. Starting from a correct Fashion-MNIST script (85.4% after 3 epochs), ten bugs were planted one at a time. Four of them stopped learning outright, without a single error or NaN, and one crawled to 52%. Five others still trained, to between 83.2% and 87.5%: removing every non-linearity cost only 2.2 points, and a double softmax 1.9. Five checks were run on every version. Comparing with a linear baseline and a fresh split flagged all ten, but only as “something is wrong”; the other four checks each pointed at a class of cause, and the overfit-one-batch test, the usual first resort, passed on five of the ten. A regression script with a target of the wrong shape broadcast silently to an R² of −0.04, and a NaN was traced to its source in one line.

  • Recognise the loss curves of the common failures: stuck at ln C, exploding, or crawling
  • Run the five cheap checks and know which bugs each one catches and misses
  • Find silent bugs that still train, by comparing against baselines and fresh data
  • Catch shape and broadcasting errors, and locate NaNs with anomaly detection
  • Work through a debugging checklist in the order that finds bugs fastest

A loss that does not fall

The script: a 784-256-256-10 MLP with dropout, Adam at 10⁻³, batch 128, 3 epochs, 50,000 training images, with another 10,000 held back as fresh data the script never touches. For a 10-class problem, a network that knows nothing predicts roughly uniform probabilities and has a loss of ln 10 = 2.303. A loss that stays there means nothing is being learned. Four of the planted bugs did exactly that:

BugFinal training lossTest accuracyMedian gradient norm
None (correct script)0.34485.39%1.16

Learning rate 100× too high (0.1 for Adam)2.30910.00%0.12
Biases initialised to −10 (every ReLU dead)2.30210.00%0.09

None of these crashed, and none produced a NaN, including the learning rate a hundred times too high, which a textbook says should explode. Adam’s normalised steps instead pushed the network in a few hundred steps into a state where every ReLU was off, and it stayed there. Forgetting zero_grad() makes every step use the sum of all previous gradients, so the update grows without bound and the gradient norm climbed to 183. Shuffled labels left a perfectly working network with nothing to learn, because no input predicts its label. The gradient norms separate the bugs: very large means accumulating or exploding, near zero means dead units or nothing to learn.

Silent bugs that still train

The more dangerous bugs are the ones that leave a working model, only a worse one, because nothing prompts anyone to look:

BugTest accuracyvs correctWhich check caught it
None (correct script)85.39%––
Softmax applied before CrossEntropyLoss83.52%−1.9overfit one batch (loss stuck at 1.52)
Inputs left as 0–25583.68%−1.7initial loss (20.2 instead of 2.3)
No non-linearity between layers83.16%−2.2only the baseline: it is a linear model
model.eval() forgotten at test time83.88%−1.5train vs eval mode (85.39% in eval mode)
Test images leaked into training87.45%+2.1fresh data: test 0.3 above fresh, not 0.9 below

Each would pass a casual look at the loss curve. The double softmax is a classic: CrossEntropyLoss already applies log-softmax, so feeding it probabilities squashes the logits into [0, 1], the loss can never go below about 1.46, and learning slows, yet it still reached 83.5%. An MLP with its ReLUs removed collapses to one linear layer, and on Fashion-MNIST a linear model is only a couple of points behind, which is why Chapter 10 insists on fitting the simple baseline first: without it, 83.2% looks fine. The leak inflated the test score, the one bug that makes results look better, and only a split that never touched the pipeline revealed it.

Shapes, broadcasting and NaNs

Some bugs are in tensor shapes rather than in the training loop. A regression network outputs a tensor of shape (N, 1); if the targets have shape (N,), then F.mse_loss(out, y) broadcasts the two to (N, N) and compares every prediction with every target. Measured on California housing:

TargetsTest R²Spread of predictions
Reshaped to (N, 1), correct0.716std 1.07 (targets 1.21)
Left as (N,)−0.039std 0.04: it predicts the mean for everything

Minimising the average squared difference between every prediction and every target is solved by predicting the global mean, which is what the network learned. PyTorch did print a UserWarning about mismatched sizes, once, in a log that also contained hundreds of lines of training progress. Turning that warning into an error, or asserting shapes at the loss, would have caught it.

NaNs have the opposite problem: they are loud, but the place they appear is rarely the place they start. Here, a network whose logits were scaled 1,000 times too large (a temperature divided where it should multiply) gave 195 of 256 examples a true-class probability of exactly 0 in fp32; -log(p) was then infinite, and in the backward pass inf times 0 produced NaN gradients everywhere. Running one step under torch.autograd.detect_anomaly() stopped at the first backward function that produced a NaN, SoftmaxBackward0, which points straight at the hand-written softmax-then-log. F.cross_entropy on the same logits computes log-softmax stably: a large but finite loss, finite gradients (P3).

with torch.autograd.detect_anomaly():          # slow: one step only, to locate the source
    loss = loss_fn(model(x), y); loss.backward()   # raises at the first backward op that returns NaN
assert out.shape == y.shape, (out.shape, y.shape)  # before every loss on regression targets

Use case: a document classifier that was “nearly as good” as the old one

A team replaces a gradient-boosting document classifier with a neural model and finds it 2 points worse. They spend a week tuning the learning rate and architecture. Then a new engineer runs the overfit-one-batch test: the loss will not go below 1.4 on 64 documents. The model ended in a softmax layer, copied from an inference script, and the loss was CrossEntropyLoss. Removing the extra softmax lets it overfit the batch, and the retrained model beats the old one by 3 points. The team adds the five checks to the template every new training script starts from, and a shape assertion before every loss.

⚠️
Common mistakes
  • Trusting a loss that decreases: five bugs here still trained to 83–87%.
  • Relying on one check: overfit-one-batch passed for shuffled labels, missing non-linearities, unnormalised inputs, a missing model.eval() and leaked test data.
  • Waiting for a NaN to signal a bad learning rate: a 100× learning rate silently killed every unit instead.
  • Ignoring a broadcasting warning: a target shape mismatch gave R² −0.04.
  • Hand-writing log(softmax(x)): use F.cross_entropy or log_softmax on logits.
  • Evaluating only on the test split the pipeline has touched: keep a fresh split.

Interview drill

Explain it simply: Your network’s loss is stuck at 2.30 on a 10-class problem. What do you check?

How a strong answer sounds
2.30 is ln 10, the loss of a model that predicts uniform probabilities, so nothing is being learned. I would look at the gradient norms first: in measured cases, a forgotten zero_grad showed norms around 183, while dead ReLUs, a learning rate a hundred times too high and shuffled labels all showed norms near zero. Then the overfit-one-batch test: dead units and a bad learning rate fail it, while shuffled labels pass it, because any network can memorise 64 random labels, which points me at the data pipeline. Then I would print a few images next to their labels.

Deeper: How do you find a bug in a model that trains and is only a little worse than expected?

How a strong answer sounds
Those are the dangerous ones, so I run cheap checks that each target one failure class. The initial loss should be about ln C: unnormalised inputs gave 20.2. The model should overfit one batch: a double softmax could not get below 1.5. Accuracy in eval mode should match how I report it: a missing model.eval() cost 1.5 points through dropout. The model should clearly beat a linear baseline: an MLP with no non-linearities scored 83.2%, within a couple of points of the real one, and only the baseline exposes that. And a fresh split that the pipeline never touched should agree with the test score: with test images leaked into training, test went above fresh. I also assert output and target shapes before the loss.

🧠 Key takeaways

  • A loss stuck at ln C means nothing is learned; gradient norms tell accumulation (huge) from dead units (near zero).
  • Five cheap checks: initial loss, overfit one batch, gradient norms, eval mode, baselines and fresh data.
  • A baseline and a fresh split flagged every bug but explained none; overfit-one-batch missed five of ten, including all the data bugs.
  • Silent bugs still trained to 83–87%; only baselines and fresh splits exposed some of them.
  • Assert shapes before losses; locate NaNs with anomaly detection; never hand-write log(softmax).
