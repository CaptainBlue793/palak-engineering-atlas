Making Training Fast: Profiling & torch.compile

Training speed decides how many experiments you can run, and most training loops leave a large factor on the table. Finding it is a measurement problem, not a bag of tricks: a step’s time is the GPU’s kernels, the CPU’s work launching them, the input pipeline feeding them, and any moment the two processors wait for each other. Each fix helps only if it targets the part that is actually slow, so the method is always the same: time it properly, profile it, fix the largest cost, and time it again.

This chapter runs that loop on a CIFAR-10 CNN step on an RTX 5070 Ti and takes it from 11.9 ms to 3.7 ms, 3.3 times faster, one measured change at a time. Along the way: a CPU augmentation pipeline that left the GPU idle for 43% of every step until it had enough worker processes, a memory-layout setting that made the step 3.4 times slower in fp32 and cut the bf16 step by 31%, a cuDNN flag that did nothing here, torch.compile’s 20% at a one-off cost of 15.8 seconds, and CUDA graphs’ last 5%.

  • Time GPU code correctly and decide whether a step is GPU-, CPU- or input-bound
  • Read a PyTorch profiler table and group the time into what can be fixed
  • Feed the GPU fast enough: workers, pinned memory, or the data on the GPU
  • Use bf16 and the right memory layout, and catch a layout regression
  • Know what torch.compile and CUDA graphs fuse or remove, and what they cost

Where time goes

The model is a 5-convolution CIFAR-10 network (64 to 256 channels, BatchNorm, ReLU, max-pooling) trained with SGD on batches of 256. Each version of the step was timed over 60 steps after 10 warm-up steps, with torch.cuda.synchronize() before reading the clock, because the GPU runs asynchronously and an unsynchronised timer measures only how fast the CPU queues work (P7). Not every row is an improvement, and that is the most useful thing about the table. Putting the data on the GPU saved 2% because this DataLoader did no per-image work; cuDNN’s autotuner found nothing better than its default choice; channels-last made the fp32 step 3.4 times slower. Precision gave the biggest single gain, then fusion. A ladder like this is only trustworthy if every rung is measured, because the intuitions behind each “optimisation” are hardware- and model-specific.

The profiler

torch.profiler records every operation the CPU dispatched and every kernel the GPU ran, with their durations. Profiled on step 5 (bf16, channels-last, eager), grouped by the operation that launched each kernel and counting only the GPU time of that operation’s own kernels:

from torch.profiler import profile, ProfilerActivity
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA]) as prof:
    for _ in range(10): step()
    torch.cuda.synchronize()
print(prof.key_averages().table(sort_by="self_cuda_time_total", row_limit=12))   # self time: no double counting of nested ops
OperationGPU ms per stepShare
Convolution backward (5 layers)1.5634%
Convolution forward0.8318%
BatchNorm backward and forward1.0423%
Max-pooling backward and forward0.5612%
ReLU backward and forward0.388%
Everything else (optimiser, zeroing, copies)0.215%
Total GPU time4.59129 kernels per step

Two readings decide what to do next. First, the GPU was busy for 4.59 ms of a 4.80 ms step, 96%, so this step is GPU-bound: shaving CPU overhead cannot help much, and only less GPU work can. Second, only half of that GPU time is convolutions, the arithmetic the tensor cores accelerate. The other half is BatchNorm, pooling and ReLU, operations that do a few additions per number and spend their time reading and writing memory. Each one reads a full activation tensor from GPU memory and writes another back. That memory-bound half is what kernel fusion attacks.

Feeding the GPU

The ladder’s first two rows hide the usual bottleneck, because that DataLoader only sliced tensors that were already in memory. A real pipeline decodes and augments each image on the CPU. Measured with a typical per-image augmentation (random crop with padding, flip, normalise) feeding the fast bf16 step, which needs 4.81 ms of GPU time on its own:

With no workers the main process spent 6.2 ms preparing each batch before it could launch the next step, and the GPU sat idle for 43% of the time. One worker produced batches at about the same rate as the main process could, so it helped only a little; with 8 workers in parallel the input kept up and the step ran at the GPU’s speed. Between 2 and 8 workers the differences were a few tenths of a millisecond, close to the run-to-run noise of a 60-step measurement. Pinned (page-locked) memory lets the host-to-device copy run asynchronously with non_blocking=True; it saved 8% at 4 workers. For a dataset that fits in GPU memory, like CIFAR-10 at 150 MB as uint8, the simplest answer is to put it there and augment on the GPU: as fast as 8 workers, with no worker processes at all.

loader = DataLoader(ds, batch_size=256, shuffle=True, num_workers=8, pin_memory=True,
                    persistent_workers=True, prefetch_factor=4)
for xb, yb in loader:
    xb = xb.to("cuda", non_blocking=True)        # overlaps the copy with GPU work; needs pinned memory

The layout and precision rungs

Row 4’s slowdown comes from the memory layout, the order in which a 4-D image tensor’s elements sit in memory. NCHW stores each channel as a full image; channels-last (NHWC) stores the channels of each pixel together, which is what tensor-core convolution kernels read most efficiently. Measured on this step: channels-last made fp32 3.4 times slower (39.7 ms against 11.7) and cut bf16’s step by 31% (4.80 ms against 6.93). The trap is that the layout can change without anyone asking. Feeding channels-last data into an NCHW model gave 39.9 ms, the same slow path, because convolution outputs follow their input’s layout, so one tensor converts the whole network. That is exactly how a permute without .contiguous() in a data loader made Chapter 21’s first fp32 timings four times too slow. When a timing looks wrong, check x.is_contiguous() and x.is_contiguous(memory_format=torch.channels_last) on the input.

torch.backends.cudnn.benchmark = True makes cuDNN time every available convolution algorithm on the first call for each input shape and keep the fastest. Here it changed nothing (11.69 → 11.70 ms): the default heuristic already chose well for these common shapes. It is worth trying for unusual shapes, and it hurts when input shapes keep changing, because every new shape is benchmarked again.

Kernel fusion and torch.compile

torch.compile captures the model’s forward and backward computation as a graph and generates new kernels for it. Its main win on a network like this one is fusion: BatchNorm’s normalisation, the ReLU after it and other element-wise operations become one kernel that reads the activation once and writes it once, instead of one round trip to memory per operation. It took the step from 4.80 to 3.86 ms, 20% faster, which is most of the memory-bound half the profile pointed at.

The price is compilation. In a fresh process with an empty cache, the first three steps took 15.8 seconds; with the compiled kernels cached on disk from a previous run, 1.7 seconds. On a run of thousands of steps that is nothing, but it dominates a quick experiment, and a model whose input shapes change can trigger recompilation (fix the shapes, or use dynamic=True). On Windows the compiler needs the community triton-windows package; on Linux it works out of the box.

model = torch.compile(model)                          # fusion; first steps compile (15.8 s cold, 1.7 s cached)
model = torch.compile(model, mode="reduce-overhead")  # + CUDA graphs: replay the whole step's kernels with one launch

CUDA graphs and host syncs

Every kernel launch costs the CPU a few microseconds. A CUDA graph records a whole sequence of kernels once and replays it with a single launch, removing that overhead. Here it gained 5% (3.86 → 3.66 ms): with 129 kernels per step and the GPU already 96% busy, launch overhead was small. It matters more with small batches or small models, where the GPU finishes each kernel faster than the CPU can launch the next one. Graphs need fixed shapes and fixed memory addresses, and no CPU-side decisions inside the captured region.

The same applies to anything that makes the CPU wait for the GPU. loss.item(), printing a tensor, if tensor > 0: and .cpu() all force a synchronisation: the CPU stops queueing work until the GPU has caught up, and the queue that hides launch latency drains. Calling loss.item() on every step cost 3.5% here (4.79 → 4.96 ms) because the step is GPU-bound and the queue refills quickly; on a CPU-bound step the cost is much larger. Accumulate the loss on the GPU and read it every hundred steps.

Use case: a video classifier stuck at 40% GPU utilisation

A team training an action-recognition model sees nvidia-smi report 40% utilisation and plans to buy faster GPUs. A profile shows the GPU idle between steps, waiting on the DataLoader: each sample decodes 16 video frames with a CPU codec and resizes them, about 90 ms per clip, and they were using 4 workers for batches of 32. Raising the workers to 16 helps but saturates the machine’s CPU cores, so they move decoding to the GPU with a hardware video decoder and cache pre-resized clips for the first epochs. Utilisation reaches 95%, and only then does it make sense to try bf16 and torch.compile, which together give a further 1.8 times. Faster GPUs would have sat idle just the same.

⚠️
Common mistakes
  • Timing without torch.cuda.synchronize(): you measure the CPU’s queueing, not the GPU’s work.
  • Optimising before profiling: here cudnn.benchmark did nothing and channels-last in fp32 made the step 3.4× slower.
  • num_workers=0 with CPU augmentation: the GPU was idle 43% of the time.
  • An accidental layout change: channels-last data into an NCHW model gave 39.9 ms instead of 11.7.
  • Benchmarking torch.compile on the first steps: they include 15.8 s of compilation.
  • .item() or print(loss) every step: a sync each time; worse on CPU-bound steps.

Interview drill

Explain it simply: Your training step is slow. How do you find out why?

How a strong answer sounds
First time it properly: warm-up steps, then many steps with torch.cuda.synchronize() before reading the clock. Then profile a few steps with torch.profiler and look at two things: how much of the step the GPU is busy, and which operations take its time. If the GPU is mostly idle, the bottleneck is the input pipeline or CPU overhead: in a measured case, CPU augmentation with no workers left the GPU idle 43% of the time, and 8 workers fixed it. If the GPU is busy, I reduce its work: bf16, the right memory layout, and torch.compile to fuse memory-bound operations. Then I measure again, because the bottleneck moves.

Deeper: What does torch.compile actually speed up, and when would CUDA graphs help more?

How a strong answer sounds
Mostly memory-bound operations. A profile of a CNN step showed about half the GPU time in BatchNorm, ReLU and pooling, each of which reads and writes a whole activation tensor; compile fuses chains of them into one kernel that reads and writes once, which gave 20% there. It does little for the big matmuls and convolutions, which already run optimised library kernels. CUDA graphs remove CPU launch overhead by replaying the step’s kernels with one launch; that gave only 5% because the GPU was 96% busy, but on small batches or small models, where the GPU outruns the CPU, it can matter far more. Both have costs: compile time, 15.8 s cold in my run, and the need for static shapes.

🧠 Key takeaways

  • Measure every change: the step went from 11.9 to 3.7 ms, but two “optimisations” did nothing and one made it 3.4× slower.
  • The profiler tells you whether you are GPU-, CPU- or input-bound; the fix depends on which.
  • CPU augmentation needs enough workers, or the data can live and be augmented on the GPU.
  • The best memory layout depends on the precision; one wrong tensor can switch a whole network.
  • torch.compile fuses memory-bound operations (−20% here); CUDA graphs remove launch overhead (−5% here).
