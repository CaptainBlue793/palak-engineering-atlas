Datasets, DataLoaders & Batching

A GPU that waits for data is the most expensive idle hardware in the building. Between the files on disk and the tensor the model sees sits the input pipeline: a Dataset that knows how to fetch and transform one example, and a DataLoader that shuffles, batches, and runs that work in background processes while the GPU trains. Get it right and nobody thinks about it; get it wrong and either the GPU starves or the model learns from data in an order, or a split, that quietly invalidates the result.

This prerequisite measures the pipeline on this machine, a Windows desktop where worker processes are spawned, not forked. Each worker cost about 1.4 seconds to start, so the first epoch with 8 workers was seven times slower than with none; from the second epoch on, with persistent_workers, the same 8 workers delivered 161,000 augmented CIFAR-10 images a second against 34,000 with none. A small CNN consumed 29,600 a second, so a heavier per-image transform with no workers left the GPU waiting. Training on Fashion-MNIST sorted by label without shuffling reached 14.9% instead of 86.9%.

  • Write a map-style Dataset and wrap it in a DataLoader
  • Choose workers, pinned memory and persistent workers from measurements
  • Tell whether the loader or the GPU is the bottleneck
  • Know what shuffling protects against, and when a custom collate function is needed
  • Build train, validation and test splits that do not leak

Dataset and DataLoader

A map-style Dataset answers two questions: how many examples there are (__len__) and what example i is (__getitem__), including any per-example work such as decoding, cropping or flipping. A DataLoader asks a sampler for indices, calls __getitem__ for each, and hands the list to a collate function that stacks them into batch tensors.

class CifarAug(Dataset):
    def __init__(self, x, y): self.x, self.y = x, y            # x (50000, 32, 32, 3) uint8, y (50000,)
    def __len__(self): return len(self.x)
    def __getitem__(self, i):
        img = torch.from_numpy(self.x[i]).permute(2, 0, 1).float() / 255   # (3, 32, 32)
        img = F.pad(img, (4, 4, 4, 4), mode="reflect")               # (3, 40, 40)
        dx, dy = np.random.randint(0, 9, 2); img = img[:, dy:dy + 32, dx:dx + 32]   # random crop
        if np.random.rand() < 0.5: img = img.flip(2)                    # random horizontal flip
        return (img - 0.47) / 0.25, int(self.y[i])

loader = DataLoader(CifarAug(x, y), batch_size=256, shuffle=True,
                    num_workers=8, pin_memory=True, persistent_workers=True)
for xb, yb in loader:                                               # xb (256, 3, 32, 32), yb (256,)
    xb = xb.to("cuda", non_blocking=True)                          # overlaps the copy with compute when pinned

The default collate function stacks tensors and turns Python numbers into tensors, recursively through tuples, lists and dicts. It fails when examples have different shapes, such as sentences of different lengths or images of different sizes; then you write a collate_fn that pads, crops or keeps a list. With len(dataset) = 50,000 and batch 256 the last batch has 80 examples; drop_last=True discards it, which matters for layers whose behaviour depends on batch size, such as batch norm on a batch of 1. An iterable-style dataset (IterableDataset) instead yields examples in a stream, for data too big to index, such as shards read from object storage.

Workers and pinned memory

With num_workers=0, the training process itself runs __getitem__ for every example, and the GPU waits while it does. With N workers, N separate processes build batches in parallel and queue them, so the next batch is usually ready when the GPU asks. On Linux, workers are created by fork, which copies the parent process almost for free. On Windows and macOS they are spawned: each worker starts a fresh Python interpreter, imports PyTorch and your module again, and receives the dataset by pickling. That is why the training script needs an if __name__ == "__main__": guard, and why start-up time matters.

Three lessons from this table. First, on Windows each worker cost about 1.4 s to start, so without persistent_workers=True you pay that again at the start of every epoch, and short epochs get slower with more workers, not faster. Second, once started, workers scaled almost linearly to 8 on this 16-core CPU. Third, pin_memory made no measurable difference here (34,500 against 33,900 img/s at 0 workers, within noise), because a 3 MB batch copies to the GPU in well under a millisecond; it pays off when batches are large or the copy can overlap a long compute step.

Is the loader the bottleneck?

Compare two rates: how fast the pipeline produces examples and how fast the training step consumes them. The small CNN above consumed 29,600 images per second. With the light transform, even 0 workers produced 34,000, so workers could not speed training up much; with the heavy transform, 0 workers produced only 18,300, and the GPU sat idle for about 40% of every step. Two workers (30,300) were just enough; four gave headroom. The quick test: time an epoch of the loader alone with no model, and an epoch of the model on one cached batch. Whichever is slower sets the pace. Chapter 22 does this with the profiler, and moves augmentation onto the GPU when the CPU cannot keep up.

Shuffling and sampling

SGD assumes each mini-batch is a fair, random sample of the training set, so its gradient points, on average, where the full-data gradient points. Data on disk is rarely in random order: it is sorted by class, by date, by user, by the order it was scraped. Train on it in that order and every batch tells the model a different, extreme story. Measured on Fashion-MNIST sorted by label: with shuffling the MLP reached 85.2%, 86.8% and 86.9% after each of three epochs; without shuffling it reached 10.0%, 10.8% and 14.9%, and on the test set it predicted class 8 or 9, the last two classes it had seen, for 98% of images. shuffle=True draws a fresh permutation every epoch. For imbalanced data, a WeightedRandomSampler samples rare classes more often (ML Fundamentals covers imbalance: Imbalanced Data).

Randomness inside workers also needs care. Older PyTorch on Linux forked every worker with the same NumPy random state, so four workers produced four identical sequences of “random” crops. Current PyTorch seeds Python’s and NumPy’s generators separately in each worker; on this machine, 64 NumPy draws from 4 workers were all distinct and changed between epochs. For reproducible runs, pass a seeded generator to the DataLoader and derive any other library’s seed in a worker_init_fn.

Splits that do not leak

A test set is only a test if nothing about it reached training. The usual leaks in deep-learning pipelines:

LeakHow it happensPrevention
Duplicates across splitsThe same image saved twice, or crawled twiceHash and de-duplicate before splitting; check near-duplicates with perceptual hashes or embeddings
Groups split apartFrames of one video, scans of one patient, photos of one product in both train and testSplit by group ID (GroupShuffleSplit), not by example
Time travelRandom split of time-ordered dataTrain on the past, test on the future
Statistics from all dataNormalisation mean and std computed before splittingCompute them on the training split only
Tuning on the test setChoosing epochs or hyperparameters by test accuracyA separate validation split; look at the test set once

For the three benchmark sets used in this course, an MD5 hash of every image found no exact duplicates between train and test, or within train (Fashion-MNIST 60,000/10,000, MNIST 60,000/10,000, CIFAR-10 50,000/10,000). Exact hashing is a weak test, though: Barz and Denzler (2020) found near-duplicates of training images for about 3% of the CIFAR-10 test set, images that differ by a crop or a colour shift and that an MD5 hash cannot see. Make the validation split with a fixed seed, torch.utils.data.random_split(ds, [n_train, n_val], generator=torch.Generator().manual_seed(0)), so that every run evaluates on the same examples.

🩻
Use case: the X-ray model that recognised patients

A team trains a chest X-ray classifier on 100,000 images and gets 97% validation accuracy with a random split. On images from a new hospital it scores 71%. Many patients had several scans, and the random split put scans of the same patient in both train and validation, so the network could score well by recognising the patient and their previous diagnosis rather than reading the scan. Re-splitting by patient ID dropped validation accuracy to 82%, a number that matched the new hospital far better. The data loader code did not change; the split did.

⚠️
Common mistakes
  • No shuffling on sorted data: measured 14.9% vs 86.9%, the model predicting only the last classes it saw.
  • Workers without persistent_workers on Windows: about 1.4 s of start-up per worker, paid every epoch.
  • More workers than the bottleneck needs: with a light transform, 0 workers already outpaced the GPU here.
  • Missing if __name__ == "__main__": with workers on Windows: every worker re-runs the training script.
  • Splitting by example when examples come in groups (patients, users, videos): validation accuracy measures memorisation.
  • Normalisation statistics from the whole dataset, or tuning on the test set.

Interview drill

Explain it simply: Your GPU utilisation is 40% during training. How do you find out whether the data loader is to blame?

How a strong answer sounds
Measure the two rates separately. Iterate over the DataLoader alone, with no model, and count images per second; then train the model for a few hundred steps on a single batch already on the GPU and count images per second. If the loader is slower, it is the bottleneck. Then the fixes are more workers with persistent workers, cheaper decoding (smaller stored images, a faster format), and moving augmentation onto the GPU. I measured this on CIFAR-10: a small CNN consumed about 30,000 images per second, a heavy CPU transform with no workers produced 18,000, and two or more workers were enough to keep up.

Deeper: Why does the order of training examples matter for SGD, and what does shuffle=True do?

How a strong answer sounds
SGD treats each mini-batch gradient as a noisy but unbiased estimate of the full-data gradient. That only holds if batches are random samples. If the data is sorted, say by class, consecutive batches pull the weights towards one class at a time and the model ends up fitting whatever it saw last. shuffle=True draws a new random permutation of the indices every epoch, so every batch is a fair sample and successive epochs see different batch compositions. On Fashion-MNIST sorted by label, training without shuffling reached 14.9% after three epochs and predicted the last two classes for almost everything, against 86.9% with shuffling.

🧠 Key takeaways

  • A Dataset fetches and transforms one example; a DataLoader samples, batches, collates and parallelises.
  • On Windows, workers are spawned: about 1.4 s each to start. Use persistent_workers=True.
  • Find the bottleneck by measuring the loader alone and the model alone; here 2 workers were enough for a 29,600 img/s CNN.
  • Shuffle: label-sorted data without it gave 14.9% instead of 86.9%.
  • Split by group and by time where they exist, de-duplicate first, and compute statistics on training data only.
