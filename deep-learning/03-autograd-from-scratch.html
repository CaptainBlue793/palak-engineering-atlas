Autograd from Scratch: a Scalar Engine

Every time you call loss.backward(), PyTorch computes the gradient of the loss with respect to millions of weights in about the time of one more forward pass. It feels like magic until you build it, and then it is three ideas: record every operation as a node in a graph, give each operation a rule for passing gradients backwards (its local derivative), and visit the nodes in reverse topological order so each one has received all its gradient before it passes any on. This chapter builds exactly that, in about a hundred lines of plain Python that work on single numbers.

Then it is measured. On 200 random expressions mixing products, powers, tanh and exp, the engine agreed with PyTorch to within 2.8 × 10⁻¹⁴, the limit of float64. It trained a 2-16-16-1 network to 99% accuracy on the two-moons dataset, with 130,618 nodes in each step’s graph, at 1.19 seconds per step, 2,479 times slower than PyTorch doing the same work. And two classic implementation bugs are planted and measured: writing = instead of += in one backward rule halved a gradient, and leaving out the visited set in the sort turned 21 node visits into 2,097,151.

Computation graphs

Take L = tanh(a·b + c) · a with a = 2, b = −3, c = 10. Computing it creates intermediate values: d = a·b + c = 4, e = tanh(d) = 0.99933, L = e · a = 1.99866. Each intermediate remembers which values it came from and which operation made it. Those links form a directed acyclic graph with the inputs at one end and L at the other. Note that a appears twice, once inside d and once in the final product; the graph is not a tree.

The engine wraps each number in a Value object that holds its data, its gradient (∂L/∂itself, filled in later) and a small function, _back, that knows how to push the gradient to its parents:

class Value:
    def __init__(self, data, prev=(), op=""):
        self.data, self.grad, self._prev, self._back, self.op = float(data), 0.0, prev, None, op

    def __add__(self, o):
        out = Value(self.data + o.data, (self, o), "+")
        def back(): self.grad += out.grad; o.grad += out.grad                 # d(a+b)/da = 1: pass it through
        out._back = back; return out

    def __mul__(self, o):
        out = Value(self.data * o.data, (self, o), "*")
        def back(): self.grad += o.data * out.grad; o.grad += self.data * out.grad   # each gets the other factor
        out._back = back; return out

    def tanh(self):
        t = math.tanh(self.data); out = Value(t, (self,), "tanh")
        def back(): self.grad += (1 - t * t) * out.grad                    # uses the saved output t
        out._back = back; return out
    # __pow__, exp, log and relu follow the same pattern; -, / and radd are built from these

Local derivatives

Each operation only has to know its own derivative. For c = a + b, ∂c/∂a = ∂c/∂b = 1, so addition passes the incoming gradient unchanged to both parents: it is a gradient distributor. For c = a × b, ∂c/∂a = b, so multiplication sends each parent the incoming gradient times the other factor: a gradient swapper. tanh passes back (1 − tanh²), computed from the output it saved in the forward pass, which is why PyTorch refuses in-place edits of saved outputs (P4). ReLU passes the gradient through if its input was positive and blocks it otherwise: a gradient gate. The chain rule says how to combine them: a node’s gradient is the sum, over every path to the loss, of the products of local derivatives along the path. The engine never enumerates paths; it gets the same sum by letting gradients flow backwards and accumulate.

Topological sort and the backward pass

A node can only pass its gradient on once it has received all of it, from every path. In the example, a’s gradient arrives from two places (through d and through the final product), and both must have arrived before anything uses a.grad. Ordering the nodes so that every node comes after all its inputs is a topological sort; running the _back functions in the reverse of that order guarantees every node is complete before it is used:

    def backward(self):
        order, seen = [], set()
        def visit(v):                          # depth-first: inputs first, then the node
            if id(v) in seen: return               # without this, shared nodes are visited again and again
            seen.add(id(v))
            for p in v._prev: visit(p)
            order.append(v)
        visit(self)
        self.grad = 1.0                         # dL/dL
        for v in reversed(order):              # outputs before inputs
            if v._back: v._back()

Accumulating gradients

Every backward rule above uses +=, and that is not a style choice. When a value feeds into two operations, each sends it a share of the gradient, and the chain rule says the total is the sum. Writing = makes the last share overwrite the others. Planted in the multiply rule and measured: for y = x · x at x = 3 the gradient should be 6; with = it was 3, because x’s two roles as left and right factor each wrote 3 and the second overwrote the first. For y = 4x + 5x it should be 9; with = it was 4. Nothing crashed. A network trained with such a rule still learns, just wrongly, which is the worst kind of bug.

Accumulation has a consequence for training: gradients must be reset to zero before each backward pass, or step t uses the sum of all gradients so far. That is the engine’s version of optimizer.zero_grad() (P4 measured what forgetting it does). The second planted bug removes the seen set from the sort. On a chain where each value is built from the previous one used twice, v = v · v repeated 20 times, the graph has 21 nodes, but a sort without the set visits a node once for every path that reaches it: 2²¹ − 1 = 2,097,151 visits. At depth 5 it was 63 against 6; at depth 15, 65,535 against 16. Real networks reuse values everywhere (every weight feeds every example in a batch), so the visited set is the difference between linear and exponential time.

Training a tiny network with it

A neuron is a weighted sum of Values plus a bias, passed through tanh; a layer is a list of neurons; an MLP is a list of layers. With those three small classes (about 20 more lines) the engine trains a real classifier. On 200 points of the two-moons dataset, a 2-16-16-1 network with 337 parameters went from 67.5% training accuracy at initialisation to 99% in 100 full-batch steps, with the hinge loss falling to 0.060. PyTorch, given the same model, loss and learning-rate schedule, also reached 99%. The engine’s results are right; its speed is not: each step built a graph of 130,618 Value nodes, one Python object per scalar operation, and took 1.19 seconds, against 0.48 ms for PyTorch on the CPU, which runs each layer as one matrix multiply. Chapter 4 makes the same idea fast by working on whole tensors.

Use case: gradients through a pricing formula

A revenue team has a pricing model that is not a neural network at all: a few dozen lines of arithmetic combining demand elasticities, discounts and shipping costs into expected profit. They want to know how profit responds to each of 40 inputs. Finite differences would need 40 extra evaluations and suffer the precision problems of P2. Running the formula on PyTorch tensors with requires_grad=True, the same graph-and-backward machinery as this chapter, gives all 40 sensitivities from one backward pass, exactly, and lets them optimise prices directly by gradient ascent. Autograd is a general tool for differentiating programs, not only for training networks.

⚠️
Common mistakes
  • = instead of += in a backward rule: measured, x·x got gradient 3 instead of 6. Values used twice must accumulate.
  • No visited set in the sort: 2,097,151 visits for a 21-node graph.
  • Not resetting gradients between steps: accumulation then sums every step’s gradient.
  • Running backward in the wrong order: a node passes on its gradient before all of it has arrived.
  • Using the input instead of the saved output in tanh’s rule (or vice versa): both work only if you are consistent; mixing them gives silent errors. Check against PyTorch.

Interview drill

Explain it simply: How does reverse-mode automatic differentiation work?

How a strong answer sounds
During the forward pass every operation records its inputs and how to differentiate itself, building a directed acyclic graph from the inputs to the loss. To get gradients, you set the loss’s gradient to 1, sort the graph topologically, and visit the nodes in reverse order; each node multiplies its gradient by its local derivatives and adds the result into its parents’ gradients. Because nodes are visited after everything that depends on them, each node’s gradient is complete before it is used. One backward pass gives the gradient with respect to every input. I built one in about a hundred lines and it matched PyTorch to 10⁻¹⁴ on random expressions.

Deeper: Why must gradients accumulate with += in each backward rule, and what does that imply for the training loop?

How a strong answer sounds
A value that is used in several places receives a gradient contribution from each use, and the chain rule says its total gradient is the sum over all paths to the loss. With plain assignment the last contribution overwrites the others: I measured x·x at x = 3 giving 3 instead of 6. The implication is that gradients persist after backward, so the training loop has to reset them to zero before each new backward pass, which is what optimizer.zero_grad() does in PyTorch. The same property lets you accumulate gradients over several micro-batches on purpose before one optimiser step.

🧠 Key takeaways

  • Autograd records a graph of operations; each knows its local derivative and passes gradients to its parents.
  • Add distributes, multiply swaps in the other factor, tanh and exp scale by their output, ReLU gates.
  • A topological sort, run in reverse, ensures each node has its full gradient before passing it on; without a visited set it is exponential.
  • Gradients accumulate with +=, so they must be zeroed between steps.
  • A 100-line engine matched PyTorch to 10⁻¹⁴ and trained an MLP to 99%, at 2,479 times the time: tensors are next.
