The GPU: Kernels, Memory & Throughput

Deep learning became practical when its arithmetic moved to GPUs, processors with thousands of simple cores built to apply the same operation to many numbers at once. A matrix multiply is exactly that. But a GPU is a separate device, with its own memory, behind a bus, running work that the CPU queues for it and does not wait for. Each of those facts produces a classic mistake: copying data back and forth, timing code that has not finished, misreading the memory numbers, launching thousands of tiny operations.

Every number here was measured on the machine this course runs on, an RTX 5070 Ti (70 streaming multiprocessors, 16 GB) next to a desktop CPU. A 4,096 × 4,096 matrix multiply took 163 ms on the CPU and 4.2 ms on the GPU. Copying from pinned host memory ran at 52 GB/s, against 21 GB/s from ordinary memory. Timing that multiply without synchronising reported 0.04 ms, a hundred times too fast. Each tiny GPU operation cost 8.6 µs of overhead whatever its size, and the same 8,192-wide multiply ran at 33 TFLOP/s in fp32 and 98 in bf16.

  • Know which work a GPU speeds up, and when the CPU wins
  • Move data to the device efficiently, with pinned memory and few transfers
  • Time GPU code correctly: synchronise, warm up, or use CUDA events
  • Read allocated vs reserved memory and an out-of-memory error
  • Spot work that is limited by launch overhead or memory bandwidth rather than arithmetic

CPU vs GPU

A CPU core is a sophisticated machine for running one stream of instructions fast, with large caches and branch prediction. A GPU spends its transistors on arithmetic instead: this one has 70 streaming multiprocessors, each running thousands of threads that execute the same instruction on different data. That design wins when there is a lot of identical, independent work, and loses when there is little.

Below about 256 the CPU won: a 64 × 64 multiply is 0.5 million operations, too little to fill the GPU, and the GPU time is almost all fixed overhead (about 17 µs whatever the size). From 256 up the GPU won, by 39 times at 4,096. The last column is the lesson for data pipelines: when the operands start on the CPU and the answer must come back, the copies cost more than the arithmetic. At 4,096 they took 11 of the 15.5 ms. Keep data on the device across steps and move it once.

Host-to-device copies

The CPU’s memory and the GPU’s memory are separate; tensors cross between them over PCIe. Ordinary (“pageable”) host memory can be moved around by the operating system, so the driver first copies it into a locked staging buffer and only then sends it. Pinned (page-locked) memory skips that step, and makes the copy asynchronous, so the CPU can queue it and carry on.

x = torch.empty(256 * 2**20 // 4)                 # 256 MB of fp32 in ordinary memory
x.to("cuda")                                       # 21.4 GB/s: staged through a pinned buffer
xp = x.pin_memory()
xp.to("cuda", non_blocking=True)                   # 53.1 GB/s, and returns before the copy finishes
# DataLoader(..., pin_memory=True) puts each batch in pinned memory for you (P5)

For copies of 16 MB and up, pinned memory was 2.5 times faster here (52.5 against 20.5 GB/s at 1 GB). For 1 MB both were slower and closer (24 against 19 GB/s), because a fixed cost per copy dominates. Compare with the GPU’s own memory bandwidth: an element-wise add on a 256 MB tensor moved data at 680 GB/s, thirteen times PCIe. Data that crosses the bus every step is data the GPU is waiting for.

Asynchronous execution, and timing it properly

When Python runs c = a @ b on CUDA tensors, PyTorch does not compute anything. It puts a kernel, a function the GPU will run, into a queue (a CUDA stream) and returns immediately. The CPU races ahead queuing more work while the GPU works through the queue. That is what makes GPUs efficient, and it is why naive timing lies:

s = time.perf_counter(); c = a @ b; t = time.perf_counter() - s      # 0.039 ms: the time to queue it
s = time.perf_counter(); c = a @ b; torch.cuda.synchronize()       # 4.00 ms: wait for the GPU to finish
e0, e1 = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
e0.record(); c = a @ b; e1.record(); torch.cuda.synchronize()
e0.elapsed_time(e1)                                                # 4.06 ms, measured on the GPU itself

Anything that needs a result on the CPU forces a wait: .item(), .cpu(), print(tensor), converting to NumPy, an if on a tensor’s value. Measured, “matmul then .item()” took 4.06 ms, the full kernel time. These hidden synchronisations are not always expensive: calling loss.item() after every step of a small MLP cost 0.729 ms per step against 0.680 ms without it, 7%, because the GPU was the bottleneck anyway. In a loop where the CPU has useful work to do in parallel, such as launching the next kernels, they can cost much more. Always time after warm-up, too: the first call of torch.linalg.qr on a 3,000 × 3,000 matrix took 495 ms while CUDA libraries loaded; the second took 19 ms.

Memory: allocated vs reserved

Allocating GPU memory through the driver is slow, so PyTorch keeps a caching allocator: memory freed by a tensor stays reserved by PyTorch and is reused for the next tensor of a suitable size. Two numbers result. torch.cuda.memory_allocated() is what live tensors occupy; torch.cuda.memory_reserved() is what PyTorch holds from the driver, and what nvidia-smi shows (plus about 0.5 GB of CUDA context). In the measured sequence, freeing a 256 MB tensor dropped allocated memory by 256 MB and left reserved memory where it was; a following 128 MB tensor was served from that cache with no new reservation; only torch.cuda.empty_cache() handed memory back. A process that looks like it is using 10 GB in nvidia-smi may have 2 GB of live tensors.

When a request cannot be met even after the cache is emptied, PyTorch raises torch.OutOfMemoryError: CUDA out of memory, followed by how much it tried to allocate, how much is free, and how much PyTorch has reserved but not allocated. A large gap between those last two numbers means fragmentation: the free memory exists but not in one piece. Chapter 23 measures what fills memory during training and how to shrink it.

Launch overhead and bandwidth

Every GPU operation pays a fixed cost to launch, here about 8.6 µs including Python and PyTorch’s dispatch, whether the tensor has ten elements or ten million. A loop of a thousand additions on a 1,000-element tensor therefore took 8.6 ms, all overhead. Large element-wise operations are limited by memory bandwidth instead: x * 2 + 1 on a 256 MB tensor ran as two kernels, each reading and writing the whole tensor, for an effective 703 GB/s, close to the card’s rated 896 GB/s. Only large matrix multiplies are limited by arithmetic. Fusing small operations into one kernel (Chapter 22’s torch.compile, Chapter 37’s Triton) removes both launch overhead and memory round-trips.

The dtype rows are worth a second look. The same 8,192 × 8,192 multiply took 33.5 ms in strict fp32 (32.9 TFLOP/s), 22.8 ms with TF32, which keeps fp32 storage but rounds the inputs to a 10-bit mantissa inside the tensor cores (48.3 TFLOP/s), and 11.2 ms in bf16 (97.8 TFLOP/s). That threefold speed-up is why mixed precision (Chapter 21) is the default for training. torch.backends.cuda.matmul.allow_tf32 = True, or torch.set_float32_matmul_precision("high"), turns TF32 on; it is off by default for matmuls in PyTorch.

Use case: the image-tagging service that got slower on a GPU

A team moves a small image-tagging model from CPU servers to a GPU server and latency gets worse. Each request is one image: the service copies it from pageable memory, runs a few dozen small kernels, and calls .cpu() on the result. At batch size 1 every kernel is launch-bound and the two copies cost more than the compute, which is the left end of the CPU-vs-GPU chart. Batching requests for up to 5 ms, pinning the input buffer and keeping the model in bf16 turns the GPU into the faster option by a wide margin, at the price of a small, bounded queueing delay.

⚠️
Common mistakes
  • Timing without synchronising: a 4 ms matmul measured 0.04 ms. Synchronise, or use CUDA events.
  • Timing the first call: 495 ms cold vs 19 ms warm for a QR decomposition. Warm up first.
  • Moving data back and forth every step: at 4,096 the copies took 11 of 15.5 ms.
  • Reading nvidia-smi as live tensor memory: it shows PyTorch’s reserved cache plus the CUDA context.
  • Thousands of tiny operations in a Python loop: 8.6 µs each, whatever their size.
  • Leaving bf16 or TF32 performance unused: 98 vs 33 TFLOP/s on the same multiply.

Interview drill

Explain it simply: Why can timing GPU code with time.time() give the wrong answer?

How a strong answer sounds
Because CUDA is asynchronous. A PyTorch operation on GPU tensors just queues a kernel on a stream and returns; the GPU runs it later. If you stop the clock right after the call, you have measured how long it took to queue the work, not to do it. You have to call torch.cuda.synchronize() before stopping the clock, or record CUDA events around the work and read elapsed_time, and you should skip the first few calls, which include library loading and autotuning. I measured a 4,096 matmul at 0.04 ms without synchronising and 4.0 ms with it.

Deeper: nvidia-smi shows your training process using 14 GB of a 16 GB card, but torch.cuda.memory_allocated() says 6 GB. Explain the difference and when it matters.

How a strong answer sounds
PyTorch’s caching allocator keeps memory it has freed instead of returning it to the driver, because driver allocations are slow. memory_allocated counts live tensors; memory_reserved counts what PyTorch holds, and nvidia-smi shows roughly that plus the CUDA context. So 8 GB is cached and free for PyTorch to reuse. It matters in two cases: other processes on the same GPU cannot use that memory, and if it is fragmented a large allocation can fail with out of memory even though the total free amount is enough. torch.cuda.empty_cache() releases unused cache, and torch.cuda.memory_summary() shows the breakdown.

🧠 Key takeaways

  • GPUs win on large, uniform work: 39× on a 4,096 matmul; the CPU won below about 256.
  • Keep data on the device; copy once, from pinned memory (52 vs 21 GB/s).
  • CUDA is asynchronous: synchronise or use events when timing, and warm up first.
  • Allocated is live tensors; reserved is PyTorch’s cache, and that is what nvidia-smi sees.
  • Small ops are launch-bound (8.6 µs each), element-wise ops bandwidth-bound (≈700 GB/s), big matmuls compute-bound (33 TFLOP/s fp32, 98 bf16).
