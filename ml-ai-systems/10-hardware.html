Hardware: GPUs, Memory & the Roofline

Speed in modern ML is rarely limited by FLOPs (floating-point operations, the raw maths). It is usually limited by how fast data reaches the maths units. A kernel is one small program the GPU runs, like a single matrix multiply. Some kernels wait on memory (memory-bound); others wait on maths (compute-bound). Once you can tell which is which, most “why is my GPU only 30% busy?” questions answer themselves.

CPUs think, GPUs sweat

A CPU core is a brilliant generalist. It has deep pipelines, big caches and branch prediction (guessing which way an “if” will go). All of that helps it finish one chain of steps, each depending on the last, as fast as possible.

A GPU is different. It is thousands of simple lanes that all run the same instruction, each on different data. Deep learning is almost entirely “multiply these giant matrices”, and that is exactly this shape of work.

Why is a matrix multiply such a good fit? Multiplying a 4,096 × 4,096 matrix by another of the same size means computing about 16.8 million output numbers, and each one is an independent dot product of 4,096 pairs. None of them needs any other's result, so thousands of lanes can work at once without waiting on each other. Compare that with parsing a JSON file, where every step depends on what the last character was: there's nothing to spread across lanes, and a CPU wins easily.

A quick guide to the units used below. A FLOP is one floating-point operation, such as one multiply or one add. TFLOP/s means 10¹² of them per second. GB/s and TB/s are bytes per second (10⁹ and 10¹²). Network speeds are usually quoted in bits (Gb/s, lower-case b), so divide by 8 to get bytes: 400 Gb/s is 50 GB/s.

🧠 CPU

~8–128 fat cores · huge caches · ~0.5–2 TFLOP/s fp32 · ~100–400 GB/s memory. Built for low latency (finishing one task fast) on code full of branches and irregular steps.

🎮 GPU

~100+ streaming multiprocessors (groups of cores) · thousands of threads · ~100–2,000 TFLOP/s in low precision · 2–8 TB/s HBM (the GPU's own fast memory). Built for high throughput (lots of work per second) on regular, parallel work.

🚚
Analogy: sports car vs freight train

A sports car gets one parcel across town fastest. A freight train moves ten thousand parcels per trip, but takes an hour to load. Now imagine your work arrives one small parcel at a time — like an LLM generating one token for one user. Then you are running a freight train almost empty. Batching (grouping many requests into one trip) is how you fill it (Chapter 26).

Inside the chip

Here are the important parts, in the order they matter for speed. Think of it as a ladder: the higher up, the smaller and faster the storage.

Tensor coresSpecial units that do only one thing: multiply matrices and add the results. They supply nearly all of a modern GPU's advertised FLOPs — but only for matrix-multiply (“matmul”) work in supported number formats. An elementwise kernel (one that touches each number on its own, like adding 1 to every value) never uses them.
Registers / SMEMThe tiny, fastest memory right next to the cores: tens of KB per block, terabytes per second, about one clock cycle to reach. Kernel writers fight to keep data here (this is what FlashAttention is about).
L2 cache~40–60 MB, several TB/s, shared across the whole chip. Whether an operation is “fused” (steps merged into one kernel) or not often comes down to whether the data stayed in L2 between steps.
HBM (VRAM)The GPU's main memory: 40–192 GB at 2–8 TB/s. Huge compared to caches, tiny compared to your dataset, and the usual bottleneck.
NVLink / PCIeThe links between GPUs: NVLink ~400–900 GB/s; PCIe 5 ~64 GB/s. That is about 10× slower than HBM. This is why deciding how to split (“shard”) a model across GPUs is a systems design problem (Ch 24).
NetworkLinks between machines: InfiniBand/Ethernet at 100–400 Gb/s per network card (~12–50 GB/s). Another ~100× slower. Training across many machines succeeds or fails on how little data you send here.
📉
The gap that defines modern ML performance

For twenty years, maths speed has grown much faster than memory bandwidth (how many bytes per second memory can deliver). An H100-class GPU can do roughly 300–500 arithmetic operations in the time it takes to fetch one number from HBM. So for any kernel, don't ask “how many FLOPs?” Ask “how many FLOPs per byte moved?”

What the ladder means in time. Take 14 GB — the weights of a 7B-parameter model in 16-bit. Moving it once takes about 4 ms from HBM at 3.35 TB/s, about 16 ms over NVLink at 900 GB/s, about 0.2 s over PCIe 5 at 64 GB/s, and about 0.3 s over a 400 Gb/s network link. Each rung down costs roughly another 10×. When a training step takes 300 ms and each step needs gradients of that size shared between machines, you can see why the network link, not the GPU, often sets the pace.

Arithmetic intensity and the roofline

Arithmetic intensity (AI) = FLOPs performed ÷ bytes moved from memory. In plain words: how much maths you do for each byte you fetch. A high number means each byte gets reused a lot.

Now plot the best speed you can reach against AI. You get the roofline. It has two parts: a sloped part on the left, where memory bandwidth limits you, and a flat “ceiling” on the right, where the maths units limit you.

As a formula: achievable FLOP/s = min(peak FLOP/s, AI × memory bandwidth). If each byte fetched feeds only a few FLOPs, bandwidth caps you; if each byte feeds hundreds, the maths units do. The ridge point is where the two are equal: peak ÷ bandwidth, which for the reference GPU below is 990 ÷ 3.35 ≈ 295 FLOPs per byte.

Two worked examples, both in 16-bit (2 bytes per number):

  • Adding two vectors of N numbers: read 2N numbers, write N, so 6N bytes, for only N additions. AI ≈ 1/6. At 3.35 TB/s that caps you at about 0.56 TFLOP/s — well under 0.1% of the 990 peak. No clever code can fix this; only moving fewer bytes (for example by fusing it into the kernel before it) can.
  • Multiplying two n × n matrices: about 2n³ FLOPs (n³ multiplies and n³ adds), but only 3n² numbers to read and write, or 6n² bytes. AI ≈ n / 3. For n = 4,096 that's about 1,365 — well past the ridge, so compute-bound. For n = 64 it's about 21, and the same operation becomes memory-bound. Bigger matrices reuse each number more, which is why batch size and layer width matter so much for speed.

🧮
Why decoding one token is so inefficient

To generate one token, the GPU must read every weight of the model from HBM. It then does only about two FLOPs per weight. That is an arithmetic intensity of about 2 — a hundred times below the ridge point. So the GPU spends most of its time waiting on memory, with most of its maths units idle.

Now batch 64 requests together. You read the same weights once, but produce 64 tokens. Intensity rises to ≈ 128, and throughput grows almost in step with batch size. That single fact shapes the whole design of inference servers.

This gives a quick speed limit you can work out on paper. A 7B model in bf16 is 14 GB of weights. At 3.35 TB/s the GPU can read all of it about 3,350 ÷ 14 ≈ 240 times a second, so batch-1 decoding can never exceed roughly 240 tokens per second on that GPU, however fast its maths units are. Real systems get somewhat less (there's the KV cache to read too, covered in Chapter 26). Quantize the weights to 4 bits (3.5 GB) and the limit rises to nearly 1,000 tokens per second. The rule of thumb for memory-bound work: speed ≈ bandwidth ÷ bytes that must be read.

Where the memory actually goes

Training memory is not just the weights. You also store gradients, optimizer state and activations (the in-between results each layer saves for the backward pass). The bytes-per-parameter shortcut. You can estimate most budgets by counting bytes per parameter:

  • Training with AdamW in mixed precision: 2 bytes (bf16 weights) + 2 (gradients) + 4 (fp32 master weights) + 8 (two fp32 Adam moments) = about 16 bytes per parameter, before activations. A 7B model needs about 112 GB, which is why it doesn't fit on one 80 GB GPU without the sharding tricks of Chapter 23.
  • Inference in bf16: just the weights, 2 bytes per parameter: 14 GB for 7B, plus the KV cache.
  • Inference in int4: half a byte per parameter: about 3.5 GB for 7B, small enough for a laptop GPU.

Activations are the part that grows with your data rather than your model: every layer keeps its outputs for every token in the batch until the backward pass uses them. Double the batch size or the sequence length and activation memory roughly doubles, while the other items stay the same. When the weights fit but the first batch runs out of memory, activations are almost always the reason.

Numeric precision

A floating-point number stores two things: an exponent (how big — the range) and a mantissa (the significant digits — the precision). Fewer bits means less of one or both. Deep learning turns out to need range far more than precision: a gradient of 0.0000001 must not become zero, but whether a weight is 0.1234 or 0.1235 hardly matters. That's why bf16, which keeps fp32's 8 exponent bits and cuts the mantissa, became the training default. Pick by job: bf16 for training on recent hardware, fp16 with loss scaling on older GPUs, fp32 for the few places that add up many small numbers (the loss, sums across GPUs), and 8- or 4-bit formats for serving once you've checked accuracy.

Lower precision is usually a bandwidth optimisation

Halve the bits and you halve the bytes you move. For memory-bound work (decoding, elementwise ops, small batches) that is close to a 2× speedup — even though the maths units were never the limit. This is why int4 weight-only quantization (storing weights as 4-bit integers) speeds up single-user LLM serving so much.

Utilization: MFU and why you're at 30%

Model FLOPs Utilization (MFU) = useful FLOPs your model needs ÷ FLOPs the hardware could have done in that time. It tells you how much of the GPU's real maths power you actually used. Well-tuned large-scale training lands at 35–55%. If you're far below that, the cause is almost always on this list:

Computing MFU by hand. Training a transformer costs about 6 × parameters × tokens FLOPs: roughly 2 per parameter per token for the forward pass and 4 for the backward pass (the “about 2× the forward” from Chapter 8). A 7B model processing 10,000 tokens per second on one GPU therefore does 6 × 7×10⁹ × 10⁴ = 4.2×10¹⁴ FLOP/s, which is 420 TFLOP/s. Against a 990 TFLOP/s peak, that's an MFU of about 42% — a healthy run. If you measured 3,000 tokens per second instead, MFU would be about 13%, and it's time to work down the table below.

Note that MFU differs from the “GPU utilization” percentage shown by nvidia-smi. That number only says some kernel was running during each sampling interval; a GPU running slow memory-bound kernels non-stop still reads 100%.

Beyond one GPU, and beyond NVIDIA

🔗

Topology matters

The 8 GPUs inside one machine (a “node”) share fast NVLink. Talking to another node drops to network speed. So you pick a parallelism strategy that keeps the chattiest communication inside a node (Ch 24).

🧊

TPUs

Google's accelerators. They use a systolic array (a grid of multipliers that pass data neighbour to neighbour), big on-chip memory and a fast 2D/3D torus network linking chips. Excellent at large dense matmul. You program them through the XLA compiler, so low-level control works differently — but it still exists.

💻

CPU inference

Perfectly fine for small models, GBDTs (gradient-boosted trees) and services with low QPS (queries per second). Quantized 7B models run on laptops. Don't pay for a GPU to serve 12 requests a minute.

Choosing hardware, in short. Training large networks: GPUs or TPUs, and the interconnect matters as much as the chip once you use more than one machine. Serving an LLM to many users: GPUs with plenty of HBM bandwidth and capacity, because decoding is memory-bound and the KV cache needs room. Serving trees, small models or low traffic: CPUs, which are cheaper, easier to scale and already everywhere. Whatever the job, estimate first — bytes to move, FLOPs to do, and which one hits its limit sooner — before you pick or buy anything.

⚠️
Common mistakes
  • Cutting FLOPs when you're memory-bound. A cleverer algorithm that moves the same bytes changes nothing. Measure intensity first.
  • Assuming peak TFLOPs are reachable. Vendor numbers assume a perfect dense matmul in the lowest precision, often with sparsity tricks. A real MFU of 40% is healthy.
  • Ignoring the data pipeline. The most common cause of an idle GPU is a CPU that can't decode JPEGs or tokenize text fast enough.
  • Buying the biggest GPU for a small model. If the model fits in 24 GB and your problem is latency, more HBM does nothing. Bandwidth and clock speed do.
  • Forgetting activation memory. The weights fit, then the first batch runs out of memory (OOM). Activations grow with batch × sequence length × layers (Ch 23).

Interview drill

Warm-up: Why does batching help LLM inference so much more than it helps image classification?

How a strong answer sounds
Autoregressive decoding (making one token at a time, each based on the ones before) reads the entire weight matrix to produce a single token. So arithmetic intensity is about 2 FLOPs/byte — deeply memory-bound. Batching shares that one weight read across many sequences. Throughput then grows almost linearly until you near the compute ceiling or run out of KV-cache memory. A CNN forward pass on a 224×224 image already does thousands of FLOPs per byte of weights. It sits near the compute ceiling even at batch 1, so extra batching helps far less.

Deeper: Your training run reports 95% GPU utilization but only 18% MFU. What's going on?

How a strong answer sounds
“Utilization” only says some kernel was running, not that it was doing useful matmul. 95% util with 18% MFU means the GPU is busy with many small, memory-bound kernels — elementwise ops, normalizations, unfused attention, dtype casts — instead of tensor-core work. First, I'd profile to see which kernels take the time. Then I'd fuse kernels with torch.compile or custom kernels, and switch to flash attention. I'd raise the batch size or use sequence packing to increase intensity. I'd also check I'm not silently running in fp32. If a lot of time goes to all-reduce (GPUs summing gradients together), the fix is to overlap that communication with the backward pass.

🧠 Key takeaways

  • GPUs give up single-task speed to get huge total throughput. They win only on regular, parallel, matmul-shaped work.
  • Arithmetic intensity (FLOPs per byte) decides whether a kernel waits on memory or on maths.
  • LLM decoding at batch 1 waits almost entirely on memory. Batching is the main way to raise throughput.
  • Training memory = weights + gradients + optimizer state + activations. The optimizer state is often the biggest part.
  • MFU of 35–55% is good. Low MFU usually means slow data loading, unfused kernels, or communication that isn't overlapped with compute.

Check your understanding

A kernel has arithmetic intensity of 3 FLOPs/byte on a device with a ridge point of 295. It is…

Far below the ridge point, the maths units sit waiting for data. You can fix it two ways: move fewer bytes (fusion, lower precision, caching) or reuse each byte more (bigger batches).

Which change most improves throughput for batch-1 LLM decoding?

The bottleneck is reading weights from HBM. Going from 16-bit to 4-bit cuts the bytes to a quarter, so the read takes roughly a quarter of the time. Extra FLOPs would go unused, because the maths units are already sitting idle.

Training a 7B model with AdamW in mixed precision. Which is typically the single largest memory consumer?

Adam keeps two fp32 “moments” (running averages of the gradient) plus an fp32 master copy of the weights. That is about 12 bytes per parameter, versus 2 for the bf16 weights. This maths is why ZeRO sharding exists (Chapter 23).

GPU utilization shows 40% with visible gaps between steps. What do you investigate first?

Regular gaps are the sign of a GPU waiting for data: too few loader workers, slow decoding, or no prefetching. Check that before changing anything about the model.

Why is bf16 generally safer than fp16 for training?

For gradients, range (how big or tiny a number can be) matters more than precision. bf16's wide exponent removes the need for loss scaling, and avoids the NaN crashes that often come with fp16.
