Transformers, End to End

One architecture now handles text, code, images, audio and even protein folding: the transformer. It is a stack of identical blocks. Each block does exactly two things. First it mixes information between positions (attention). Then it processes each position on its own (an MLP, a small feed-forward network). Everything else is detail — but the details are where the systems work lives.

The block

Why learn the block in detail? Because a whole LLM is just this one block copied 30 to 100 times, with an embedding table in front and a vocabulary projection at the end. Once you can draw one block and count its parameters, you can reason about any model's size, memory and speed — which is exactly what interviews and capacity plans ask for.

Here is a modern decoder block (the kind used in GPT-style models), in the order data flows through it:

Inside one transformer blockStep-through
  1. A matrix with one row per token: T rows, each a vector of d numbers. d is the “model dimension”, also called the width of the residual stream. For a 7B model, d is typically 4096 and there are 32 blocks.
  2. “Pre-norm” means you normalize the input before each sub-layer, not after. This keeps the residual path clean, so deep stacks train well without a fussy warmup (Chapter 9).
  3. Three linear maps (matrix multiplies) produce queries, keys and values. Each is d×d, so that is 3d² parameters. The results are then split into h heads, each working on its own slice of d/h numbers.
  4. Per head: softmax(QKᵀ/√dₕ + mask)V. This is the only step in the whole block where positions talk to each other. Everything else works on each token separately.
  5. The heads' outputs are joined back together and passed through one more d×d matrix (the output projection). This lets the model combine what the different heads found.
  6. Add the sub-layer's output back onto its input. This running total — the residual stream — is a shared “working memory” that every block reads from and writes to. The straight-through path is also what lets gradients reach block 1.
  7. Second pre-norm before the feed-forward sub-layer.
  8. Expand each token's vector from d to 4d numbers, apply a nonlinearity, then shrink back to d. No mixing between positions at all. This is where roughly two-thirds of the parameters live, and where much of the model's factual knowledge seems to be stored.
  9. Add again, and pass the result to the next identical block. After 32 blocks, a final norm and one more matrix turn each vector into logits — one raw score per word in the vocabulary. Softmax turns those into next-token probabilities.

What does RMSNorm actually do? It divides each token's vector by its root-mean-square size, then multiplies by a learned scale. For the vector [3, 4]: the mean of the squares is (9 + 16) ÷ 2 = 12.5, its square root is about 3.54, so the vector becomes about [0.85, 1.13]. Whatever size the residual stream has grown to, each sub-layer sees an input of steady size. It is a simpler, slightly cheaper version of LayerNorm (it skips subtracting the mean).

🧵
The residual stream mental model

Picture the residual stream as a shared whiteboard, d numbers wide, that runs through the whole model. Each attention sub-layer reads the whiteboard, gathers information from other positions, and writes a correction back. Each MLP reads, works something out for that token alone, and writes back.

Nothing is ever erased — only added. This picture explains why tricks like LoRA (adding small low-rank updates) and activation steering (nudging the stream in a chosen direction) work at all.

Multi-head attention

Instead of one attention of size d, run h smaller attentions of size d/h side by side. The total compute is the same. But each head can specialise: one tracks grammar, another matches earlier mentions of the same thing, another looks at the marker token at the start.

With real sizes: a 7B model has d = 4096 and 32 heads, so each head works on 4096 ÷ 32 = 128 numbers. The Q, K and V matrices are still d×d in total — they are just cut into 32 slices of 128 columns each. So splitting into heads adds no parameters and almost no compute. It only changes how many separate softmaxes are taken.

Why several heads

A single softmax gives one set of weights, so it has to focus on one thing. Eight heads can look at eight different things at once and combine the results. In practice many heads are redundant and can be removed. Still, being able to track several relationships per layer clearly matters.

MQA and GQA

The KV cache (explained below) takes most of the memory at inference. So modern models share keys and values across heads. Multi-query uses one K/V for all heads; grouped-query uses one per group of 8 heads. This shrinks the cache 8–64× with very little quality loss. It is a design change driven purely by serving costs.

Where does position come from?

Attention by itself ignores order. Shuffle the tokens and you get the same outputs, just shuffled. To the model, “dog bites man” and “man bites dog” would look alike. So position has to be added in on purpose.

Why is that true? Look at how “dog” in position 1 is processed. Its query is scored against the keys of “bites” and “man”, and the values are averaged. Nothing in that sum says which word came first — a weighted average of a set gives the same answer in any order. Swap the words and “dog” gets exactly the same output.

🔄
RoPE in one sentence

RoPE rotates each query and key vector by an angle that depends on its position, so their dot product depends only on the difference between their positions. Relative distance comes out of the geometry for free, instead of being learned separately for each slot. That is also why you can stretch the context by slowing the rotations (“RoPE scaling”) — which is how models trained on 4k tokens get extended to 32k+.

A small picture of why only the difference matters. Think of a 2-number slice of a vector as an arrow. RoPE turns the query at position 5 by 5θ and the key at position 3 by 3θ. The dot product of two arrows depends only on the angle between them, which is 5θ − 3θ = 2θ. Move both tokens 100 places later and each turns by an extra 100θ; the gap is still 2θ, so the score is unchanged.

Three family shapes

📖

Encoder-only

Every token sees the whole input. Trained by hiding some words and predicting them. BERT-style. Best for classification, extraction and embeddings (vectors that capture meaning) — every retrieval system in Chapter 20 uses one.

✍️

Decoder-only

Each token sees only earlier tokens; trained to predict the next token. GPT/Llama-style. Generates text, and is what “an LLM” means today. It scales best and is the simplest to train.

🔁

Encoder–decoder

An encoder reads the whole input; a decoder writes the output token by token, looking back at the encoder through cross-attention. T5/Whisper-style. Natural for translation and speech, where input and output are separate sequences.

How to choose: if you need a vector or a label for a piece of text (search, classification), an encoder-only model is smaller and faster for the job. If you need the model to write text, use decoder-only — today that covers most tasks, even translation and summarisation, because one large general model is easier to run than many special ones. Encoder–decoder still wins when the input is a different kind of thing from the output, such as audio in and text out.

Inference: prefill, decode, and the KV cache

Generating text has two very different phases. Mixing them up is the most common cause of bad inference design.

1️⃣ Prefill

Process the whole prompt in one parallel pass. Compute-bound (limited by maths speed), lots of maths per byte, efficient. Cost grows with prompt length (and with its square for attention).

2️⃣ Decode

Generate one token at a time, each depending on the one before. Memory-bound and sequential: every step re-reads all the weights just to produce one token (Chapter 10).

Rough numbers for a 7B model in bf16 (14 GB of weights) on a GPU with about 3 TB/s of memory bandwidth. Prefill of a 1,000-token prompt reads the weights once and does about 2 × 7B × 1,000 = 1.4 × 10¹³ FLOPs of useful matrix maths — plenty of work per byte read. Decode must read all 14 GB again for every new token, so even with no other cost one user gets at most about 3,000 ÷ 14 ≈ 200 tokens per second. That is why serving systems batch many users' decode steps together: one read of the weights then serves them all.

Each new token needs to attend to every earlier token. Recomputing keys and values for the whole prefix at every step would be hugely wasteful. So the keys and values of past tokens are saved — the KV cache — and only the new token's Q, K and V are computed.

It's like keeping your notes from earlier pages instead of re-reading the book each time. Each decode step now costs time linear in the length so far, but the cache uses a lot of memory.

Size it by hand once. Take 32 layers, d = 4096, standard multi-head attention (so the K and V for all heads together are 4096 numbers each per layer) and 2-byte fp16 numbers. One token costs 2 (K and V) × 32 layers × 4096 × 2 bytes = 524,288 bytes, about 0.5 MB. An 8,192-token conversation needs about 4 GB. Thirty-two such users need about 128 GB — more than one 80 GB GPU holds, before the weights. With grouped-query attention sharing each K/V across 8 heads, the same 32 users need about 16 GB.

Sampling: turning logits into text

The model outputs a probability for every token in its vocabulary. How you pick one from that list changes the feel of the output completely. Temperature sharpens (low) or flattens (high) the probabilities. Top-k keeps only the k most likely tokens. Top-p (“nucleus”) keeps the smallest set of top tokens whose probabilities add up to p.

A worked example. Three candidate tokens have logits 2, 1 and 0.

  • Temperature 1: softmax gives e² ≈ 7.39, e¹ ≈ 2.72 and e⁰ = 1, which sum to 11.11. The probabilities are 0.67, 0.24 and 0.09.
  • Temperature 0.5: divide the logits by 0.5 first, giving 4, 2 and 0. Now the probabilities are 0.87, 0.12 and 0.02. The favourite has become much more likely: lower temperature sharpens.
  • Top-p 0.9 at temperature 1: add the probabilities from the top down: 0.67, then 0.67 + 0.24 = 0.91, which reaches 0.9. Keep those two and rescale so they sum to 1: about 0.73 and 0.27. The unlikely third token can never be picked.

Top-p adapts where top-k can't. When the model is confident, a couple of tokens already cover 90% and the rest are cut. When it is unsure, many tokens are needed to reach 90%, so more stay in play. Top-k keeps the same k in both cases.

Counting parameters and FLOPs

Two formulas cover most quick estimates in interviews and capacity planning. N is the number of parameters; D is the number of training tokens.

# parameters per block (ignoring norms and biases)
attention = 4·d²                # Q, K, V, output projections
mlp       = 8·d²                # d→4d and 4d→d  (12·d² with SwiGLU’s third matrix)
per_block ≈ 12·d²
total     ≈ 12·d²·n_layers + vocab·d

# training compute
FLOPs ≈ 6 · N · D              # N parameters, D training tokens
#   forward ≈ 2ND, backward ≈ 4ND

# inference compute
FLOPs ≈ 2 · N per generated token

Where do these come from? The MLP's first matrix maps d numbers to 4d, so it holds d × 4d = 4d² weights; the second maps back, another 4d², making 8d². Attention has four d×d matrices, 4d². For compute: every weight takes part in one multiply and one add per token in the forward pass — 2 FLOPs per parameter per token, hence 2N. The backward pass computes two gradients per matmul (for the inputs and for the weights), so it costs about twice the forward: 4N. Together that is 6N per training token.

Check it on the classic 7B shape: 12 × 4096² × 32 ≈ 6.4B for the blocks, plus the embedding table of 32,000 × 4096 ≈ 0.13B. That is about 6.6B, which gets rounded to “7B”.

⚠️
Common mistakes
  • Thinking the MLP is a minor part. It holds roughly two-thirds of the parameters and does most of the FLOPs. Attention gets the attention; the MLP gets the compute.
  • Sizing a GPU by weights only. With many users at once, the KV cache is often bigger than the model itself.
  • Using temperature > 0 for structured output, then blaming the resulting parse failures on “model errors”.
  • Assuming longer context is a free upgrade. Attention cost grows quadratically, the KV cache grows linearly, and quality measurably drops in the middle of long inputs.
  • Forgetting that decode is sequential. Latency grows with the number of tokens generated. The only real fixes are fewer tokens, smaller models, or speculative decoding (Chapter 27).

Interview drill

Warm-up: Why does a transformer need positional encodings when a CNN and an RNN don't?

How a strong answer sounds
Attention computes a weighted sum over a set. Shuffle the inputs and the outputs are shuffled the same way, so order carries no information. An RNN gets order from reading step by step. A CNN gets locality from the kernel's layout in space. A transformer has neither, so position must be added: either to the embeddings (absolute) or inside the attention score (RoPE, ALiBi). RoPE is the modern choice because it makes the score depend on relative distance. That generalises better and can be stretched to longer contexts.

Deeper: Estimate how many concurrent 8k-context users a single 80 GB GPU can serve with a 7B model, and say what you'd change to double it.

How a strong answer sounds
Weights in bf16 are ~14 GB, leaving ~60 GB after workspace. With 32 layers, d=4096, standard multi-head attention and an fp16 cache, KV is roughly 2×32×4096×2 bytes ≈ 0.5 MB per token. So 8k tokens ≈ 4 GB per request — about 15 users at once. To double it: switch to grouped-query attention (8× smaller cache — the single biggest win). Quantize the KV cache to fp8. Use paged attention so memory isn't wasted on half-filled blocks. Quantize the weights to int8/int4 to free several more gigabytes. Beyond that, use retrieval to keep prompts short instead of stuffing in context, and turn on prefix caching for system prompts that many requests share.

🧠 Key takeaways

  • A block = pre-norm → attention (mixes positions) → residual add → pre-norm → MLP (each token alone) → residual add.
  • Attention holds ~4d² parameters per block and the MLP ~8d². Most of the model is the MLP.
  • Position must be added on purpose. RoPE encodes relative distance and is the modern default.
  • Inference has two phases: prefill (limited by compute) and decode (limited by memory). The KV cache keeps decode cheap per token but takes most of the memory.
  • Params ≈ 12·d²·layers; training ≈ 6ND FLOPs; inference ≈ 2N FLOPs per token.

Check your understanding

Which part of a transformer block mixes information between token positions?

Everything except attention works on each position separately. That's why attention is the only place masking is needed — and the only place where context length affects the cost.

What is the KV cache for?

Without it, each new token would recompute keys and values for the whole prefix. With it, each decode step is linear in length. But the cache grows with context length × number of users, and usually limits how many users a GPU can serve.

Why do modern models use grouped-query or multi-query attention?

Sharing keys and values across heads divides the cache size by the number of heads sharing. It is a design choice driven almost entirely by the cost of serving.

You need strict JSON output from a model. Which setting is most appropriate?

Always picking the top token removes a whole class of parse failures. Constrained decoding then blocks any token that would break the grammar. Together they turn “usually valid” into “always valid”.

Roughly how many FLOPs does training a 7B model on 2T tokens require?

6 × N × D = 6 × 7e9 × 2e12 ≈ 8.4e22. At ~1e15 useful FLOP/s per GPU, that's roughly 1,000 GPU-days. This is the arithmetic behind every big training budget.
