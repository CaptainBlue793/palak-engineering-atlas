Making Models Cheap & Fast

The same answer, for a fifth of the money. Quantization, distillation, pruning and speculative decoding each cut a different part of the bill. Each one also gives something up — and you have to measure what, not assume it's fine.

  • Quantize weights and activations (store them in fewer bits), and know what breaks
  • Distil a large model into a small one that's good enough
  • Explain speculative decoding and estimate how much faster it makes things
  • Use cascades and routing so most requests never reach the big model
  • Build a set of tests that catches quality lost to compression

Know which cost you're attacking

Before picking a technique, find out what you're actually short of. If requests queue because the KV cache is full, making the maths faster won't help. If one user waits for slow token streaming, adding requests per GPU won't help either. Measure first (memory in use, TTFT, TPOT, cost per request), then pick the row below that targets that limit.

Quantization

Quantization means storing weights in fewer bits — say 4 instead of 16. With 4 bits, each weight can only take one of 16 values (levels), so every real value is rounded to the nearest level.

To make this work, the weights are split into groups. Each group gets its own scale (and maybe a zero point) that stretches the levels to fit that group's values. Fewer bits means fewer levels and coarser rounding. The error is worst when a few values are far bigger than the rest (a long-tailed distribution).

A worked example with a group of four weights, [0.12, −0.30, 0.05, 0.90], quantized to 4 bits. We use the whole-number levels −7 to +7 and set the scale so the largest weight lands on 7: scale = 0.90 / 7 ≈ 0.129.

  • Quantize: divide each weight by the scale and round. 0.12/0.129 ≈ 0.93 → 1; −0.30/0.129 ≈ −2.3 → −2; 0.05/0.129 ≈ 0.39 → 0; 0.90/0.129 = 7 → 7. Stored as [1, −2, 0, 7]: four 4-bit integers plus one scale.
  • Dequantize: multiply back. [0.129, −0.257, 0, 0.90]. Errors of at most about 0.05. Close enough.
  • Now add an outlier: change the last weight to 9.0. The scale becomes 9.0 / 7 ≈ 1.29, and 0.12, −0.30 and 0.05 all round to 0. Three of the four weights are wiped out by one big value. That's the outlier problem in miniature, and it's why small groups help: an outlier only ruins its own group.

The size maths: a 7B model at 16 bits is 14 GB. At 4 bits it's 3.5 GB, plus the scales. With one 16-bit scale per group of 128 weights, the scales add 16/128 = 0.125 bits per weight, so the real figure is about 4.125 bits, or ~3.6 GB.

Weight-only vs weights-and-activations. Weight-only quantization (like int4 GPTQ) stores weights small but turns them back into 16-bit numbers just before the maths. It saves memory and memory bandwidth, which is what decode needs. Quantizing activations too (for example W8A8: 8-bit weights and 8-bit activations) lets the GPU do the maths itself in int8 or fp8, which also speeds up compute-bound work like prefill and big batches. It's harder to do well, because activations have the worst outliers.

Outliers are the whole problem

Transformer activations have a few channels with values 10–100× larger than the rest. If one scale covers the whole tensor, it has to stretch to fit those giants, and all the ordinary values get squeezed into just a couple of levels.

Every good quantization method is a fix for this: smaller groups, a separate scale per channel, keeping the outlier channels in high precision (LLM.int8), shifting the scale between activations and weights to even things out (SmoothQuant), or running sample data through the model to minimise output error layer by layer (GPTQ, AWQ).

fp16 / bf16The baseline. 2 bytes per weight, no quality loss to worry about.
fp8Built into recent GPUs. ~2× smaller with almost no loss for most models. More and more the default for serving.
int8 weight-onlyReliable. ~4× smaller than fp32, quality loss usually under one point. A safe default for production.
int4 (GPTQ / AWQ)~8× smaller. Excellent for speed with one user at a time, where memory bandwidth is everything. Measure it on each task — reasoning and code suffer first.
2–3 bitStill mostly research. Big quality loss unless you work hard to compensate; rarely worth it in production.
QATQuantization-aware training: train with the rounding simulated in the forward pass, so the model learns to cope with it. Best quality at low bit counts, but it costs a training run.

Distillation

Train a small student model to copy a large teacher model. The key idea: the student learns from the teacher's full set of probabilities, not just its final answer. These “soft labels” carry far more information. For example, “80% cat, 15% fox, 5% dog” also tells the student how the teacher ranked the answers it rejected.

Compare what each kind of label teaches. The hard label “cat” only says cat is right. The soft label also says a fox is an understandable mistake, a dog less so. That's knowledge about how the classes relate, and the student gets it from every single example. To bring out these small probabilities, distillation often divides the teacher's logits by a temperature greater than 1 before the softmax, which flattens the distribution so the runner-up answers carry more weight.

Why can a small student get close at all? A general-purpose teacher spends its capacity on everything: poetry, law, a hundred languages. If your product only needs, say, support-ticket classification in English, the student only has to copy that small corner of the teacher's behaviour.

🗣️

Response distillation

Have the teacher answer your real requests, then fine-tune the student on those answers. Simple, effective, and the standard way to turn a general model into one for your task.

📊

Logit / KL distillation

Train the student to match the teacher's full probabilities for the next token, using a KL loss (a measure of how different two distributions are). Needs fewer examples, but you need the teacher's raw scores (logits) — so usually only for models you host yourself.

🧠

Reasoning distillation

Have the teacher write out its step-by-step working. Keep only the ones that reach answers you've checked are correct, and train the student on those. Surprisingly strong on maths and code.

🎯
Distil on your own traffic, not a benchmark

The student only needs to be good at what your users actually ask. So: sample real production prompts (with permission, and with personal data handled properly), generate teacher answers, filter them with a checker or a judge model, and train.

A 3B student trained on 50k of your real queries often matches a 70B model on those kinds of queries — and is no replacement for it anywhere else. Keep the big model as a fallback for the rare, unusual requests.

Pruning and sparsity

Pruning removes the weights that contribute least, setting them to zero (making the model sparse). The catch: hardware doesn't get faster when zeros are scattered at random. You save memory but not time.

The usual rule for “contribute least” is simply size: weights closest to zero change the output least, so they go first (magnitude pruning). The 2:4 pattern applies that rule inside every block of four. For example, [0.50, −0.10, 0.02, 0.80] keeps its two largest-magnitude weights and becomes [0.50, 0, 0, 0.80]. Because every block has exactly two zeros in a known pattern, the GPU can store half the values plus a small index and skip the zero multiplications in hardware. Random zeros have no such pattern, so the GPU still has to multiply by them.

Unstructured

Zero out the smallest weights, wherever they are. You can remove a lot with little quality loss. But you need special GPU code (kernels) to get any speedup, and usually it doesn't come.

Structured (2:4, heads, layers)

Remove whole attention heads, whole layers, or a fixed pattern (2 of every 4 weights) that the GPU's tensor cores can skip in hardware. Real 1.5–2× gains, but a bigger quality cost, and usually a short fine-tune afterwards to recover.

Speculative decoding

A model generates text one token at a time, and each step is slowed by reading weights from memory. So the GPU's compute sits mostly idle during each step.

Speculative decoding uses that idle time. A small, cheap draft model guesses the next k tokens. The big (target) model then checks all k in a single forward pass — about the same cost as producing one token. Tokens it agrees with are kept. At the first one it rejects, the big model puts in its own token instead, the rest of the guesses are thrown away, and drafting starts again from there. It's mathematically proven that the output follows exactly the same probabilities as the big model alone.

A small trace. The text so far is “The cat”. The draft guesses 4 tokens: “sat on the mat”. The big model checks all four in one pass. It agrees with “sat” and “on”, but at position three it would have said “a”, not “the”. So you keep “sat on”, add the big model's “a”, and throw away “mat”. One big-model pass produced 3 tokens instead of 1. Even in the worst case, when the very first guess is rejected, the pass still yields one token from the big model, so you never lose progress.

Estimating the speed-up. If each guess is accepted with probability α, the expected tokens per round with k guesses is (1 − α^(k+1)) / (1 − α). With α = 0.75 and k = 4, that's (1 − 0.237) / 0.25 ≈ 3.05 tokens. Each round costs one big-model pass plus 4 draft passes; if a draft pass costs 10% of a big one, that's 1.4 big-pass equivalents. Speed-up ≈ 3.05 / 1.4 ≈ 2.2×. The calculator below does the same sum. Notice that raising k helps less and less, because each extra guess only counts if every guess before it was accepted.

How often guesses are accepted depends on the text. Boilerplate, code and formatting are very predictable (0.8–0.9); dense reasoning is not (0.4–0.6). Variants such as Medusa or EAGLE add extra prediction heads to the big model itself, so no separate draft model is needed.

Cascades and routing: the biggest lever

Most real requests are easy. Sending every one of them to your largest model is usually the most expensive design decision in the whole system. A cascade tries a cheap model first and only passes hard requests up to the big one.

1. cheap classifier / heuristic  → is this simple?
2. small model answers            → confidence or verifier check
3. if unsure, escalate to big     → the expensive path, now rare

# 70% handled by the small model at 1/15th the cost
# blended cost ≈ 0.7·(1/15) + 0.3·1 ≈ 0.35× the all-big baseline

Read the cost line carefully. The 30% that escalate have also already paid for the small model's attempt, so the honest figure is 0.7 × 1/15 + 0.3 × (1 + 1/15) ≈ 0.37×. Still close to a third of the cost. Escalated requests also wait longer, because they run two models in a row.

Cascade or router? A router decides up front which single model gets the request, so nobody pays for two calls. Pick it when you can judge difficulty from the prompt alone (length, topic, a classifier score). A cascade lets the small model try first and checks its answer. Pick it when difficulty only shows in the answer, and when you have a cheap, reliable check such as a schema, tests or a verifier.

🎚️
The escalation signal is the hard part

Routing only works if you can tell — cheaply, before answering — that a request is hard. Or tell afterwards that the cheap answer can't be trusted. Options:

  • a small classifier trained to judge the prompt;
  • the small model's own confidence (weak, but usable);
  • a checker (unit tests, a schema check, a check that the answer is backed by retrieved documents);
  • a judge model on a sample of answers.

Measure the escalation rate and the quality of the answers that weren't escalated. Otherwise you're quietly shipping the cheap model's mistakes.

Every compression technique changes quality. Treat it exactly like shipping a new model (Chapters 33, 35):

⚠️
Common mistakes
  • Believing a vendor's “no quality loss”. It means no loss on their benchmark; run yours.
  • Quantizing everything the same way. The embedding layer, the first and last layers and outlier channels usually need more bits.
  • Expecting speedups from randomly scattered zeros. Without matching GPU code, they save memory but no time.
  • Distilling only on benchmark data. The student ends up good at the benchmark and weak on your real requests.
  • Using speculative decoding with very large batches. It helps most when memory speed is the limit. With big batches the GPU is already busy, and the draft is just extra work.
  • Compressing before measuring. Record today's quality and cost first, or you can't tell whether the trade was worth it.

Interview drill

Warm-up: Why does int4 weight quantization speed up single-user decoding so much?

How a strong answer sounds
Because decoding one request at a time (batch 1) is limited by memory bandwidth. Every step reads all the weights from GPU memory (HBM) to produce one token, so the time is basically bytes moved divided by bandwidth. Cut the bytes to a quarter and that time drops to roughly a quarter. It helps much less with large batches: one weight read is shared across many sequences, and the limit becomes compute instead. That's why quantization is a bigger win for one interactive user's latency than for bulk throughput.

Deeper: Your serving bill is $180k/month for a 70B model. Where do you start?

How a strong answer sounds
Measure first: how many tokens are input processing (prefill) versus generation (decode), how hard requests typically are, and how often the prompt cache is hit. Then work through these, biggest expected payoff first: (1) routing — if 60–70% of traffic is simple, a distilled small model that hands hard cases up cuts the bill more than any low-level GPU work; (2) prompt caching and trimming the context, which directly shrink prefill; (3) fp8 or int8 weights and a quantized KV cache, which fit more requests on each GPU; (4) speculative decoding for interactive requests; (5) tuning batching and scheduling. Each step ships behind a quality alarm, with a task-specific eval and a canary. I'd track cost per successful request rather than cost per token, because that metric rewards not calling the big model at all.

🧠 Key takeaways

  • Match the technique to the bottleneck: memory bandwidth (quantization), parameter count (distillation), one-token-at-a-time latency (speculative decoding), request volume (routing).
  • Quantization quality depends on how you handle outliers and on group size, not just on the number of bits.
  • Distilling on your own traffic gives large-model quality on your kind of requests — and nowhere else.
  • Speculative decoding costs no quality: identical outputs, 1.5–3× faster when memory speed is the limit.
  • Cascades usually beat every small optimisation; the hard part is a trustworthy signal for when to escalate.

Check your understanding

Why does speculative decoding not change output quality?

The accept/reject test is designed so the final tokens follow exactly the big model's probabilities. The draft only suggests; the big model decides.

What makes transformer weights hard to quantize to very low bit widths?

One shared scale has to stretch to cover the outliers, squeezing everything else into a couple of levels. Per-group scales, handling outliers separately and calibration-based methods all tackle this.

You prune 60% of weights unstructured and see no speedup. Why?

Memory drops if you store only the non-zeros, but the matrix multiply does the same work. Structured patterns like 2:4, which tensor cores speed up in hardware, are what give real speedups.

Which change most reduces cost when 70% of your traffic is simple FAQ-style questions?

Not running the big model at all beats making it cheaper. Quantization can then add further savings on the remaining 30%.

After quantizing to int4, which evaluation is most likely to reveal a problem that chat benchmarks miss?

Small rounding errors add up over long chains of steps. Casual chat can look unchanged while maths, code and finding facts in long inputs get measurably worse.
