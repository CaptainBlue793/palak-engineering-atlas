Case Study: Image Generation Service

You're running text-to-image for three million users. Every request ties up a whole GPU for several seconds. That makes this the one system in the course where a single user's request can really slow down everyone else's. Capacity, queueing and abuse control matter more here than model quality. And the safety problem is unlike anything in a text product.

  • Design an asynchronous request path (submit now, collect the result later) around GPU work that takes seconds
  • Trade denoising steps against quality, latency and cost
  • Queue fairly when one user can take up a GPU for a minute
  • Build safety checks that cover prompts, outputs and provenance (proof of where an image came from)
  • Store and serve images without the storage bill overtaking the GPU bill

In scope: serving, scheduling, safety, storage, cost, abuse. Out of scope: training the diffusion model, the editor UI, and the rights and licensing policy for training data — a real question, but a legal one.

Turning the numbers into GPUs. 12M images ÷ 86,400 seconds ≈ 140 images per second on average. Usage bunches into evenings and weekends, so a peak of about 3× the average gives the ~400 jobs per second in the box. Now the key step. If each job keeps a GPU busy for t seconds, the number of GPUs busy at any moment is simply arrival rate × t. At 400 jobs/s and 8.4 GPU seconds per image, that's 400 × 8.4 ≈ 3,400 GPUs at peak. Halve the seconds per image and you halve the fleet. That one multiplication is why the rest of this chapter cares so much about GPU seconds per image.

🎯
Metrics

Primary: images kept — downloaded, shared or saved to a project — per active user per week. Don't count generations: that rewards people regenerating because the first result was bad.

Quality: which images people prefer on a fixed set of test prompts, scores for how well images follow the prompt, and regeneration rate as an indirect signal.

Guardrails: p50 and p95 time to first image, queue wait at peak, GPU seconds per kept image, policy-violation rate, and false-block rate (harmless requests wrongly blocked).

Cost line: GPU seconds per image. Every other cost comes back to this number.

🧮
Why this system is not like the others

A chat token takes milliseconds, and one GPU serves fifty conversations at once. A 1024² image at 30 steps takes up a large slice of a GPU for several seconds, and can't be mixed with other work nearly as finely.

That shapes every design decision:

  • In this design, requests are asynchronous: you get a job id back, instead of holding a connection open.
  • Queue depth (how much work is waiting), not GPU utilization, is the health metric.
  • Admission control (turning work away when full) has to exist from day one.
  • One abusive client can use up the capacity of thousands of normal users without ever hitting a "requests per second" rate limit.

2 · The request path

Prompt to delivered imageStep-through
  1. The API replies straight away with a job id and a place in the queue. The app then listens for progress updates. Like a restaurant pager: you order, get a buzzer, and sit down instead of waiting at the counter. An eight-second HTTP request can work, but a durable job ID makes longer queues, reconnects and retries easier to manage. So the job, not the connection, is what the system tracks.
  2. Classify the prompt, check it against blocklists of named real people and known abuse patterns, then reject or rewrite it. This runs first for a practical reason as well as a policy one. Rejecting in 20 ms costs nothing. Generating an image and then throwing it away costs eight GPU seconds you can never sell.
  3. Jobs go into priority classes — paid interactive, free tier, batch and API. Each class has a budget of GPU seconds, not a requests-per-second limit. The scheduler picks jobs by class weight and each user's fair share. So one user who submits 500 jobs mostly delays their own queue, not everyone else's.
  4. This is the actual work. Encode the prompt. Then run N denoising steps — each one cleans up a noisy "latent" (a compressed version of the image) a little more. Finally, decode the latent into pixels. Batching a few jobs with identical settings speeds things up. Batching jobs with different step counts or sizes doesn't, so the scheduler groups similar jobs.
  5. After a handful of steps, decode a low-resolution preview from the latent and stream it. The wait feels far shorter: the user sees the picture taking shape at 1.2 s, instead of a spinner until 6 s. It costs only a few percent of extra compute.
  6. An image classifier checks the result. Perceptual hashing (a fingerprint that still matches after small changes) compares it against known illegal content. A hidden provenance signal and signed metadata are added. Some violations only show up in the output: the prompt was harmless, but the model produced something that isn't.
  7. Save to object storage with a lifecycle policy (rules for when files expire or move to cheaper storage). Serve through a CDN using signed URLs that expire quickly. Record the seed, model version and every setting. Regenerating, "make a variation of this", billing disputes and abuse investigations all depend on that record (Chapter 31).
  8. The app already shows the preview; the final image replaces it. Failed jobs must clearly show as failed and must not be silently charged. A job that dies halfway has still used real GPU seconds. Decide who pays for those before launch — it's a product decision.

Edge cases the path must handle.

  • The client retries. Phones lose signal and apps resubmit. The submit call carries an idempotency key — a unique id the app generates once per request — so a retry returns the existing job id instead of starting a second, paid-for generation.
  • The user closes the app. The job keeps running, and the result waits under the job id. Cancelling is a separate, explicit action that frees the GPU slot if the job hasn't started yet.
  • A GPU dies mid-job. The scheduler notices the missing heartbeat (a regular "I'm alive" signal), puts the job back at the front of the queue, and makes sure the user isn't charged twice.
  • The output is blocked. The user gets a clear "this result can't be shown" message rather than a silent failure, and the job still counts toward their abuse history if the prompt was the cause.

3 · Deep dive: the step budget

A diffusion model starts from pure noise and removes a little of it at each step, like a photo slowly coming into focus. More steps give better quality, but every step is a full pass through the network. This one number sets latency, cost and capacity all at once. That makes it the most important dial in the system.

Why cost is roughly proportional to steps. Each step runs the whole denoising network once over the image's latent. The prompt is encoded once and the latent decoded once, but those are small next to 30 or 50 network passes. So going from 50 to 28 steps removes 22 of 50 passes — about 44% of the work — and the GPU count falls by about the same share. Quality doesn't fall in step: the early steps set the layout and colours, and the late ones only polish fine detail, so the quality curve rises fast and then flattens.

Resolution is the other hidden multiplier. Doubling the side length (1024² → 2048²) gives four times the pixels, and the network's cost grows at least that fast — faster in the attention layers, which compare every patch of the image with every other patch. That's why large sizes and upscales belong in a separately priced tier.

Tiering by step count is the practical answer

You don't have to pick just one. Use a 4-step distilled model (a smaller model trained to copy the big one in fewer steps) for previews, thumbnails, variations and free-tier traffic. There, speed matters more than the last few percent of detail. Use more steps for final renders, upscales and paid requests.

The model weights differ but the pipeline is the same, so the scheduler just routes by tier. The mistake is using the high-quality setting for everything, then finding the GPUs cost four times what the product earns.

4 · Deep dive: queueing when jobs are seconds long

DecisionChoiceWhy
What you limitGPU seconds, not requestsA batch of four 2048² images costs ~40× a single 512² preview; a request limit treats them as equal
Queue orderWeighted fair queueing per user, inside priority classesA burst from one user delays their own jobs first; everyone else's wait stays the same
Admission controlReject early, with an honest wait estimateA queue with no limit turns a capacity problem into a storm of timeouts
Health metricQueue wait at p95, not GPU utilizationGPUs are meant to be 100% busy; wait time is what users actually feel
Autoscaling signalQueue depth in GPU secondsRises before demand peaks; utilization only tells you the GPUs are already full
Preemption (pausing a job for a more urgent one)Batch and API jobs give way to interactive onesInteractive users are watching; batch jobs aren't, and can resume from a saved latent

Cold starts are the other scheduling trap. Loading a diffusion model of several gigabytes takes tens of seconds. So adding GPUs after the queue builds up is far too late. Keep a pool of warm (already loaded) GPUs sized for the daily peak, and warm up extra ones ahead of your known traffic pattern.

Fair queueing, with numbers. Suppose 100 GPUs and 5 seconds per job. User A submits 500 jobs at once; a moment later user B submits one. With a plain first-in, first-out queue, B waits behind all of A's jobs: 500 × 5 s ÷ 100 GPUs = 25 seconds. With fair queueing per user, the scheduler takes turns between users who have work waiting, so B's job gets the next free GPU — a wait of at most about 5 seconds. A is barely slowed, because A was always going to wait for most of those 500 jobs.

An honest wait estimate is a division. Add up the GPU seconds already queued ahead of a job and divide by the GPUs serving that class. 12,000 GPU seconds ahead ÷ 600 GPUs = about 20 seconds. If that's over the promise for the user's tier, admission control says so at submit time — and can offer the fast 4-step tier instead — rather than letting the request time out after a minute.

5 · Deep dive: safety and abuse

PromptA classifier plus blocklists for named real people, sexual content involving minors, and known ways of sneaking past filters. Cheap, fast, and the only gate that saves GPU time. It's also the easiest to get around, which is why it can't be the only one.
Image inputImage-to-image and inpainting (editing part of an uploaded picture) change the risk completely: now the uploaded photo is the danger. Run face detection and consent rules on uploads, not just on prompts. Treat "edit this photo of a real person" as its own product decision.
OutputA classifier on the generated image catches what the prompt didn't reveal. Perceptual hashing matches known illegal material. Some violations only exist in the output — the prompt was harmless, but the result wasn't.
ProvenanceA hidden watermark in the pixels, plus signed content credentials in the metadata. Some platforms strip metadata, and edits can damage a watermark. Signed credentials can verify recorded provenance when present; missing credentials alone do not establish how an image was made.
AccountsAbuse is concentrated: a small number of accounts cause most violations. Tracking violations per account, with penalties that grow step by step and a real appeals process, catches far more than any check on single requests.
MeasurementTrack the violation rate and the false-block rate. A filter tuned only against violations ends up refusing "a woman in a swimming pool", and the product dies of a thousand small annoyances (Chapter 37).

Why the false-block rate needs its own number. Define it as blocked harmless requests divided by all harmless requests. If nearly all 12M daily requests are harmless, a 1% rate means roughly 120,000 wrongful blocks. Reviewing only blocked requests instead estimates the fraction of blocks that were wrong. To estimate the false-block rate, label a representative sample of both accepted and blocked requests, accounting for how each was sampled.

Why several gates and not one strong one? Each gate sees something the others can't. The prompt gate is cheap but can be fooled by wording. The output gate sees what was actually made, but only after paying for the GPU time. Account history sees patterns that no single request shows. Stacking them means an attacker has to beat all of them at once, and each can be tuned for what it's good at.

The seed, prompt, model version and sampler settings help reproduce a generation, but do not guarantee identical pixels across hardware or software changes. Record the runtime and numerical settings too, and test reproducibility before promising regeneration. Keep the original bytes when an exact image must be preserved. PyTorch explains these reproducibility limits. Retaining old model versions is necessary, but is only one part of the contract.

The storage arithmetic. 12M images × 1.5 MB = 18 TB a day, and 18 TB × 365 ≈ 6.5 PB a year if nothing is ever deleted. With a 30-day expiry on unsaved images, the unsaved pool stays at about 18 TB × 30 = 540 TB. If around 5% of images are saved, that's 0.9 TB a day, or about 330 TB a year kept for good. Together that's roughly 900 TB instead of 6.5 PB — a seven-fold cut from one lifecycle rule.

When does regenerating beat storing? Less often than it sounds. At typical cloud prices, keeping one 1.5 MB image in cold storage for a year costs a tiny fraction of a penny. Regenerating it takes about 8 GPU seconds, which at a few pounds per GPU-hour is roughly half a penny. So for a full-size image, storage is usually cheaper unless it would sit untouched for many years. Regeneration earns its keep for derived files — thumbnails, previews and resized copies can be rebuilt from the saved original instead of stored — and as a fallback when an image has already expired. The bigger value of the recorded settings is reproducibility: variations, disputes and investigations.

🎤
Interview drill

Follow-up: “At peak, p95 wait hits 40 seconds. You cannot get more GPUs this quarter. What do you do?”

How a strong answer sounds
I'd reduce demand and the work per job before lowering quality for everyone. First, find out where the GPU seconds are going. I'd expect a small share of users, plus the batch and API classes, to use most of them. Enforcing a fair share of GPU seconds spreads the wait more evenly without adding capacity, and the typical user's experience improves straight away. Second, lower the default step count at peak times only. Use the distilled model for previews and free-tier requests, and keep the high-step path for explicit final renders. That multiplies throughput several times, for a quality difference most users won't notice on a first draft. Third, remove duplicates: the same prompt, seed and settings should return the cached image instead of generating it again. Fourth, move batch and API work to quieter hours with a deadline-based scheduler — those jobs can wait hours, interactive ones only seconds. And I'd make the wait honest. A real estimate plus an instant lower-quality option beats a spinner. Retries during a queue backup are what turn a slow system into a broken one.

Follow-up: “Why not rate-limit by requests per minute like a normal API?”

How a strong answer sounds
Because requests aren't the thing that runs out. One request might be a 512² four-step preview costing half a GPU second. Another might be four 2048² images at 50 steps, costing well over a minute. That's a hundred-fold difference, counted as the same. So a request limit either holds back cheap users for no reason, or leaves the expensive path wide open — and in practice it does both. The right unit is GPU seconds. Give each account and priority class a budget, charge jobs against it as they run, and let the scheduler enforce fair shares. It also gives you a cost model that matches the actual bill, so quotas, pricing and capacity planning all use the same unit.

🧠 Key takeaways

  • GPU jobs that take seconds force an asynchronous design: a job id, streamed progress, and queue depth as the health metric.
  • The step count sets quality, latency and GPU count all at once. Distilled few-step models plus tiers are what make the money work.
  • Limit and schedule by GPU seconds, not requests — one request can cost a hundred times more than another.
  • Safety needs checks on the prompt, on uploaded images and on the output, plus per-account enforcement and a measured false-block rate.
  • Recording the seed and settings lets you recreate images, which turns storage into a cache — as long as the model version is kept.

Check your understanding

Why should quotas be denominated in GPU seconds rather than requests per minute?

A 512² four-step preview and four 2048² 50-step images are both "one request". Treating them the same either holds back cheap traffic too much or leaves the expensive path open.

Why is GPU utilization a poor health signal for this service?

The scheduler keeps GPUs busy whether the queue is empty or forty seconds deep. Autoscale and alert on queue depth in GPU seconds instead. It rises before demand peaks, rather than after.

Why run the prompt safety classifier before scheduling rather than after generation?

It saves capacity as well as enforcing policy. You still need the output classifier, because a harmless prompt can produce an image that breaks the rules.

What makes streaming a low-resolution preview so valuable?

The user sees the picture taking shape in about a second, instead of a spinner until the final image. The final result is exactly the same; the experience is completely different.

Why record the seed and all sampler parameters for every job?

With the seed and settings you can rebuild thumbnails, previews and expired images instead of storing them, and answer "what exactly was generated?" in a dispute. But that only works while the recorded model version still exists, which limits how fast you can retire versions.
