Experiment Tracking, Registries & Reproducibility

Six months after a model ships, someone asks: which data was it trained on? Who approved it? Can we rebuild it? If answering means searching Slack, you don't have an ML platform. You have a pile of notebooks that happened to work.

  • Log everything a run needs to be re-creatable
  • Use a model registry with versions, stages and approvals
  • Trace lineage from raw data to a deployed prediction
  • Choose the right level of reproducibility for the cost
  • Write a model card that answers the questions people actually ask

What a run must record

The model a training run produces depends on many inputs. Record every one of them, automatically. Otherwise the run isn't a result, it's just a story. Think of a recipe: if you don't write down the ingredients and oven temperature, you can't bake the same cake again.

Why does this matter so much in ML, more than in ordinary software? Because in ordinary software the code is the program: check out the commit and you have it back. A model is the output of code plus data plus settings plus randomness. Change any one and you get a different model, with no compiler error to warn you. A realistic example: two runs from the same commit score 0.842 and 0.861. The only difference is that the second one read the training table a week later, after 3% more rows had arrived. Without the dataset version in the run record, nobody could ever explain the gap.

⚙️
Automatic or it won't happen

Manual logging falls apart within two sprints. Wrap training in a launcher script that records the commit, the resolved config, the environment digest and the dataset version. Then nobody has to remember. The smallest useful setup is a tracking server, an artifact store (where model files are kept), and a rule that nothing untracked reaches production.

Lineage: from raw event to prediction

Run records answer “how was this model made?”. Lineage answers the questions that go across many runs. The most common one arrives during an incident: “we just found that the labels from 3–9 March were corrupted. Which models trained on them, and which of those are live?” With lineage, that is one query: find the dataset snapshots that contain those rows, then the runs that read those snapshots, then the registry versions those runs produced, then the deployments that serve them. Without lineage, it is a week of asking around.

The model registry

A model registry is the handoff point between experiments and production. Think of it as a library catalogue for models. Each model gets a named, versioned entry with its files, metrics, lineage and approval status.

📦

Versions

Never changed after creation, and numbered in order. fraud-scorer:v37 means one exact model file, forever.

🚦

Stages

staging → shadow → canary → production → archived. Serving asks for a stage, never for a file path in someone's storage bucket.

✅

Gates

To be promoted, a model must pass evaluation thresholds and per-slice checks, have a signed-off model card, and have a named approver.

↩️

Rollback

The previous version stays ready to deploy with one command. Practise this. A rollback you've never tested is a plan, not something you can actually do.

A worked walk through one promotion:

  1. A training run finishes and registers fraud-scorer:v37, linked to its run id, dataset snapshot and metrics. Its stage is staging.
  2. An automated check compares v37 with the live v36 on the same held-out set: PR-AUC 0.612 vs 0.588, and no slice drops by more than the allowed 0.02. The check passes.
  3. The owner fills in the model card and a named approver from the risk team signs it. Only then may v37 move to shadow, then canary, then production (Chapter 33 covers those steps).
  4. v36 moves to a “previous” slot and stays deployable. If v37 misbehaves, rollback means pointing serving back at v36.

Every step leaves a record: who, when and why. That record is what makes “what changed at 14:00?” answerable later.

🏷️
Serving should reference a version, not “latest”

A tag like “latest” moves every time a new model is saved. If production points at it, a training job can change production behaviour without any deployment. Instead, pin the exact version in the deployment config. Change it through the same review process as code. Then “what changed at 14:00?” has an answer.

How reproducible do you need to be?

You might expect that recording everything guarantees identical results. It doesn't, and the reason is surprisingly small. Computers store decimals approximately, so the order in which numbers are added changes the last digits: in floating point, (0.1 + 0.2) + 0.3 gives 0.6000000000000001 while 0.1 + (0.2 + 0.3) gives 0.6. A GPU adds millions of numbers in parallel, and the order can vary from run to run. Tiny differences in step 1 grow over millions of training steps, so two “identical” runs end with different weights. Usually the quality is the same; the exact numbers are not. So the real question is which level of sameness you need.

Statistical reproducibility is what lets you trust a small gain. Say the baseline scores 0.842, 0.848 and 0.839 over three seeds (mean 0.843, spread about ±0.005). A new idea scores 0.846 on one seed. That is inside the baseline's own range, so it proves nothing. If it scores 0.856, 0.859 and 0.853 over three seeds (mean 0.856), the two ranges don't overlap, and a 0.013 gain is believable. Three seeds is the usual minimum; more when the gain you care about is close to the spread.

The model card

A model card is a short document that ships with every production model version. Think of it as the label on a medicine box: what it's for, what it's not for, and the known side effects. It means the person debugging at 2am, the reviewer six months later and the regulator next year all get the same answers.

The example below shows what makes a card useful rather than decorative. Each section answers a question someone will really ask:

  • Intended use — “can my team use this model for X?” The “NOT for” line matters as much as the “for”.
  • Training data — “would this model know about last month's pattern?” The snapshot id and date range answer it.
  • Metrics with slices — “does it work for my users?” An overall number can hide a weak subgroup, like new accounts here.
  • Limitations — the known weak spots, written down before someone discovers them the hard way.
  • Monitoring and rollback — “how would we notice it breaking, and what do we do then?”

🔬
Comparing runs well

Log metrics per slice, not just overall. Make comparing runs easy. A sweep is a batch of runs trying different hyperparameters; sort it by the metric you care about. Use parallel-coordinate plots (one line per run across all settings) to see which hyperparameters actually mattered. Most sweeps show that two settings dominate and the rest are noise. That's exactly what you need to know for the next sweep.

⚠️
Common mistakes
  • Logging metrics but not the dataset version. The most common gap, and the one that makes a run impossible to reproduce.
  • Dataset paths whose contents change. With s3://data/latest/, the same run id points at different data over time.
  • Production pointing at “latest”. Behaviour changes without a deployment and without a record.
  • Comparing runs that differ in three things. Change one thing per experiment, or you learn nothing.
  • Conclusions from a single seed. A 0.4% gain from one seed is usually noise. Report mean ± standard deviation over three seeds.
  • Never practising a rollback. Your first attempt should not be during an incident.
🎤
Interview drill

Warm-up: A model in production is behaving oddly. What do you need to be able to look up?

How a strong answer sounds
Which registry version is deployed, and since when. The run that produced it, with its code commit, resolved config and environment digest. The dataset snapshot it trained on. Its evaluation metrics, including per slice. Who approved the promotion. And the monitoring history since deployment. With those I can tell what changed: the model, the data, or the world. Those are three very different investigations. If any of it means asking a person, the platform has a gap worth fixing before the next incident.

Deeper: Is bit-exact reproducibility worth it?

How a strong answer sounds
Usually not for training. It needs deterministic GPU kernels, fixed collective algorithms (how GPUs combine results), a fixed data order and fixed hardware. It costs real training speed, for a guarantee that rarely answers a question you actually have. What matters is re-running and landing in the same place statistically, and proving where everything came from for an audit. I would insist on determinism in two places. First, inference: the same input should give the same output, for debugging and caching. Second, small regression tests, where randomness makes failures impossible to reproduce. So the default is statistical reproducibility plus full lineage. Bit-exactness only where a regulator or a specific debugging need requires it.

🧠 Key takeaways

  • Record code, data version, resolved config, environment, hardware, seeds and outputs, automatically.
  • A registry gives you unchangeable versions, stages, promotion gates and a tested rollback.
  • Lineage must link raw data → run → model version → deployment → prediction before you need it.
  • Aim for statistical reproducibility plus auditability. Bit-exactness is rarely worth its cost.
  • Ship a model card with intended use, slice metrics, limitations, monitoring and rollback.

Check your understanding

Which missing item most often makes a run unreproducible?

Code and config are usually versioned out of habit. Data is often referenced by a path whose contents change. So the same command produces a different model a month later.

Why should serving reference an explicit model version rather than “latest”?

Pinning forces model changes through the same review as code, and leaves a timestamped record. That's what lets you answer “what changed?”.

Run A scores 0.842 and run B scores 0.846, each with a single seed. What do you conclude?

Changing only the random seed often moves the score by more than that gap. One run is an observation, not a comparison.

What belongs in a model card that teams most often omit?

Those parts prevent misuse: using the model on people or decisions it was never tested for.

Which level of reproducibility is the pragmatic default for most teams?

Matching quality across seeds, with a record of where everything came from, answers the questions people actually ask. And you avoid the speed cost of forcing determinism everywhere.
