Running Big Training Jobs

A month-long training run on a thousand GPUs looks like research, but it's mostly an operations job. Hardware will fail. The loss will jump at 3am. What separates a successful run from a wasted million dollars is careful checkpointing (saving the run's state so you can resume), good monitoring, and a plan you've practised.

  • Pick how often to save a checkpoint, based on how often things break and how long saving takes
  • Recognise the usual failures and the signs that give each one away
  • React to a loss spike without ruining the run
  • Build the dashboard that tells you a run is healthy
  • Make a run resumable, flexible about hardware, and reproducible enough

At scale, failure is the steady state

Suppose one GPU fails, on average, once every 50,000 hours. That sounds reliable. But with 1,024 GPUs, something fails roughly every two days. And that's before network glitches, storage hiccups, overheating, and jobs that freeze because one process took a different code path.

The arithmetic: failures add up across machines. If each GPU fails about once per 50,000 hours, then 1,024 GPUs produce about 1,024 failures per 50,000 hours, which is one every 50,000 / 1,024 ≈ 49 hours. Double the cluster and you halve the time between failures.

And one failure stops everything. In synchronous training, every GPU must join each all-reduce. If one GPU dies, the other 1,023 sit waiting for it until the collective times out. So a single broken part costs you the whole job, not 1/1,024 of it.

So the goal isn't to prevent failures. It's to make recovering from them cheap.

How often should you checkpoint?

Save too rarely and each failure costs hours of repeated work. Save too often and you spend the run writing to disk instead of training. There's a sweet spot in between, and it's worth calculating rather than guessing.

Here's where the formula below comes from. Call the checkpoint write time C, the interval between checkpoints T, and the mean time between failures MTBF.

  • Cost of writing: you spend C out of every T, a fraction C / T. Longer intervals make this smaller.
  • Cost of failures: a failure lands, on average, halfway through an interval, so you redo about T / 2 of work. Failures happen once per MTBF, so the fraction lost is T / (2 × MTBF). Longer intervals make this bigger.

One cost falls as T grows and the other rises. The total is smallest where they're equal: C / T = T / (2 × MTBF), which gives T = √(2 × C × MTBF). A worked example: C = 4 minutes (0.067 h), MTBF = 36 h. Then T = √(2 × 0.067 × 36) ≈ 2.2 hours. Each cost is then about 3%, so roughly 6% of the run is lost, plus the restart time after each failure.

How big is a checkpoint? Using the 16 bytes per parameter from Chapter 23, a 70B model's weights plus optimizer state is about 1.1 TB. At 10 GB/s of total storage bandwidth that takes around 2 minutes to write. That's why checkpoints are written in shards, with every GPU saving its own piece at the same time.

Young's approximation: optimal interval ≈ √(2 × checkpoint_cost × MTBF), where MTBF is the mean time between failures. With asynchronous checkpointing you copy the state into the machine's ordinary RAM, then write it to storage in the background while training continues. That makes the write nearly free, so you can save far more often.

What must be in a checkpoint

A checkpoint needs the model weights and the optimizer state, where the learning-rate schedule had got to, the random-number generator (RNG) state for every process, the data-loader position (which shard, which offset), the step count, and the config plus the exact code version.

Leave out the data position and a “resume” quietly trains on the same tokens again. Leave out the RNG state and the run stops being reproducible from that point.

Write each checkpoint to a temporary name and rename it at the end, so a crash mid-write can't leave a half-file that looks real. Keep the last few plus occasional milestones. And actually restore one in the first hour of the run. An untested checkpoint is a hope, not a backup.

When a server dies, what do you resume on? There are two common answers:

  • Hot spares. Keep a few idle servers in reserve. When one fails, swap a spare in and restart with exactly the same layout. It's simple and keeps the run identical, but the spares cost money while they wait.
  • Elastic training. Carry on with fewer servers, for example dropping from DP = 64 to DP = 63. The checkpoint has to be re-split for the new number of GPUs, and you must keep the global batch the same, usually by raising the gradient accumulation steps. Otherwise you've quietly changed the learning-rate recipe. This avoids waiting for hardware, but it's more complex to get right.

Large runs often do both: use a spare if one is free, and shrink only if none is.

The loss-spike playbook

Big runs spike. The wrong reaction is to restart from the same state with the same data: that usually causes the same spike again and wastes hours.

Why does it repeat? Training is (almost) deterministic from a checkpoint. Same weights, same optimizer state, same batches in the same order means the same updates, which leads to the same blow-up. To get a different result, something has to change: the data, or the settings.

Two tools in the steps below are worth understanding first. Gradient clipping caps the size of an update: with a clip value of 1.0 and a gradient norm of 50, every gradient is scaled down by 50× before the step. It limits the damage from one bad batch but can't fix a model that has already drifted into an unstable state. Adam's ε sits in the denominator of the update, m / (√v + ε). For weights whose recent gradients were tiny, √v is close to zero, so one sudden large gradient can produce a huge step. A larger ε puts a floor under that denominator.

1 · Look at the gradient norm first

The gradient norm measures how big the update is overall. It almost always jumps just before the loss does. If gradient clipping is on and the norm still jumped by 10× or more, the problem is the data batch or the model's state, not the learning-rate schedule.

2 · Identify the batch

Log which data shard and offset each step used. Then replay the suspect batch on its own, starting from the checkpoint before the spike. If the spike comes back, you've found bad data: repeated tokens, a giant blob of encoded binary, broken text encoding.

3 · Roll back and skip

Restore the checkpoint from before the spike, and skip or reshuffle the bad batches. This is the standard fix, and it works far more often than anything cleverer.

4 · If it happens again, adjust the run

Lower the peak learning rate a little, clip gradients more tightly, raise Adam's ε (a small number that stops division by almost zero), or make the warmup longer. Write-ups of the biggest training runs describe exactly these moves. It's trial and error, not magic.

5 · Record it

Write it in the run log: step, symptom, action, result. Six weeks later, nobody will remember why the learning rate changed at step 41,000, and that log is the only reason the result can be reproduced.

Determinism: aim for “same conclusions”, not bit-identical

Getting bit-for-bit identical results at this scale needs deterministic GPU kernels, fixed communication algorithms, identical hardware and a fixed data order. It also costs you speed.

The root cause is that floating-point addition depends on order. In fp32, (100,000,000 + 1) − 100,000,000 gives 0, because the + 1 is rounded away, while (100,000,000 − 100,000,000) + 1 gives 1. A GPU that adds thousands of numbers in a slightly different order on each run gets slightly different sums. Over millions of steps those tiny differences grow into visibly different loss curves.

What you actually need is weaker: the same config and random seed should produce a run that reaches the same quality, and any checkpoint should resume and continue identically from that point. Save the seeds, the library versions, the exact container image and the code commit alongside every checkpoint, so the result can be recreated later.

Data at scale

A 1,000-GPU job reads tokens very fast. If the data pipeline stalls for even a second, every GPU waits. And bugs in the data, such as repeats or skipped shards, don't crash anything. They just make the model quietly worse. The three habits below prevent both problems.

Two-level shuffling, with a small example: 1,000 shards of 100,000 examples each. Each epoch, you shuffle the list of shards, so shard 734 might be read first. Then you read shards one after another into a buffer of, say, 10,000 examples and pick randomly from that buffer. Reading stays fast because each file is read start to finish, and the order is close enough to random for training.

📚

Pre-tokenize into shards

Turning text into tokens while training wastes CPU time on every pass through the data. Do it once, and store the tokens in files (shards) of a few hundred MB that can be read start to finish.

🔀

Shuffle at two levels

Shuffle the order of the shards each pass, and shuffle within a buffer of examples as you read each shard. Truly random access across many terabytes is far too slow to afford.

↩️

Make the data reader resumable

Save the shard ID, offset, epoch and seed in the checkpoint. Otherwise a resume reads the same tokens again, which quietly causes memorisation and wastes compute.

⚠️
Common mistakes
  • Never testing a restore. Restore from a checkpoint in the first hour of the run, not during the first failure at 3am.
  • Saving the model but not the optimizer, schedule, RNG state or data position. The “resume” is really a new, worse run.
  • Restarting a spiked run from the same state and data. It spikes again. Roll back further and skip those batches.
  • No per-process metrics. Averages hide the single slow GPU that's costing you a quarter of the cluster.
  • Writing checkpoints while everything waits. Use asynchronous or split (sharded) checkpointing, or the whole cluster sits idle waiting for storage.
  • No run log. If you don't record what you changed, results can't be reproduced and nobody learns anything.

Interview drill

Warm-up: Failures every 12 hours, checkpoints take 6 minutes. How often do you checkpoint, and why?

How a strong answer sounds
Young's approximation gives √(2 × 0.1 h × 12 h) ≈ 1.5 hours, so roughly every 90 minutes. At that point the time spent writing and the time lost redoing work are balanced, and the total waste is a couple of percent. But first I'd try to make the write cheap. Asynchronous, sharded checkpointing copies the state into ordinary RAM and writes it in the background, which makes the cost almost nothing. That moves the best interval down to every 15–30 minutes and greatly reduces the worst case. I'd also test a restore straight away, and alert when write times start rising, because storage running out of headroom is what quietly breaks this calculation.

Deeper: Day 9 of a 14-day run, loss jumps from 2.1 to 6.8. Walk me through the next hour.

How a strong answer sounds
First, decide whether to let it keep running. A one-step spike that's already recovering may be survivable; a loss that keeps climbing is not.
Then gather evidence: the gradient norm just before the spike, the loss on each process (if only one process blew up, suspect hardware or a corrupted shard rather than the data batch), and the logged shard and offset for those steps.
Replay the suspect batches against the last good checkpoint in a small side job. If the spike comes back, roll back to before it, skip or reshuffle those batches, and resume. If it doesn't come back, suspect hardware: check the memory-error (ECC) counters and Xid logs on the GPUs involved, and restart on different servers. If it happens again after a clean rollback, adjust the run: lower the peak learning rate a bit, clip gradients more tightly, raise Adam's epsilon.
Throughout, write the timeline in the run log. And change only one thing at a time, or you'll never know which change worked.

🧠 Key takeaways

  • With thousands of GPUs, failures are normal. Build for cheap recovery, not for prevention.
  • The best checkpoint interval ≈ √(2 × checkpoint cost × MTBF). Writing in the background lets you save far more often.
  • A checkpoint must include the optimizer, the schedule, the RNG state and the data position. And you must test a restore.
  • Handle loss spikes by rolling back and skipping batches, before you start changing hyperparameters.
  • Watch each process's step time, the gradient norm, MFU and checkpoint write time. And keep a run log.

Check your understanding

Your resume works but the model re-learns tokens it already saw. What was missing from the checkpoint?

Without the reader's position, a resume starts the data from the beginning again. Training carries on and looks perfectly normal while quietly repeating data.

All ranks are alive, GPU utilization is 100%, and no step has completed for 20 minutes. Most likely cause?

This is the classic NCCL deadlock. It usually comes from one process taking a different code path: an early return, an evaluation that only some ranks run, or an error raised on one rank. Set timeouts on collectives and print every process's stack trace.

MTBF is 24 hours and a checkpoint takes 6 minutes. Roughly what's the optimal interval?

√(2 × 0.1 h × 24 h) ≈ 2.2 hours. Writing checkpoints in the background is usually a better move than fine-tuning this number.

The loss spikes at step 60k. What do you do first?

Diagnose before you act. The gradient norm usually spikes first, and the logged shard and offset tell you whether one specific batch is to blame. If it is, rolling back and skipping it is the cheapest correct fix.

Step time increased 30% overnight with no code change. What do you check first?

Because every process syncs each step, training runs at the speed of the slowest one. One GPU slowed down by heat, or one failing network card, holds back the whole cluster. That's why per-process timing belongs on the dashboard.
