Five layers, top to bottom

Why care what sits under model(x)? Because almost every “it's slow” or “it crashed” problem in training lives in one specific layer. If you know which layer, you know which tool fixes it: a profiler, a compiler flag, a different kernel, or a smaller batch. Without that map, people guess — and usually buy more GPUs instead.

Step through what happens when you run one training step. Each layer hands work down to the one below it.

One word you'll see a lot: a kernel is a single small program that runs on the GPU, such as “multiply these two matrices” or “add 1 to every element”. Every framework op ends up as one or more kernel launches. Each launch has a fixed cost of a few microseconds, however little work it does.

From Python to siliconStep-through
  1. In eager mode (running each line as Python reaches it) this is ordinary Python: attribute lookups, a loop over modules, one framework call per operation. Python adds a few microseconds per op. You won't notice that on big matmuls, but it is a disaster for thousands of tiny ones.
  2. Each op is sent to the right implementation based on its dtype (number type), device and memory layout. If gradients are needed, the framework also writes an entry onto the autograd tape — a record of how to undo that step later.
  3. With torch.compile or JAX's jit, the list of ops is recorded into a graph first. Then it is optimised as a whole: chains of elementwise ops are fused, layouts are chosen, memory is planned ahead, and new kernels are generated (often with Triton).
  4. A matmul goes to cuBLAS, a convolution to cuDNN, attention to FlashAttention. These libraries are hand-tuned for each chip and each shape. That is why odd tensor sizes can run much slower than round ones.
  5. Blocks of threads are handed to the SMs (the GPU's core groups). Data flows from HBM through L2 into registers, and tensor cores do the maths. Everything in Chapter 10 applies here.
  6. Calling .backward() walks the tape backwards and runs each op's gradient kernel. This is when the saved activations get read — which is why they must stay in memory for the whole forward pass.
  7. Weights and optimizer state are updated. Done naively, that is thousands of tiny kernels. Real systems use fused or foreach optimizers that group them into a handful.

Tensors: shape, stride, dtype, device

A tensor is a flat block of memory plus a small label (metadata) saying how to read it. The label holds the shape, the stride (how many elements to skip to move one step along each dimension), the dtype and the device.

Because of this split, many operations are free. They only rewrite the label and never touch the data. Such a result is called a view.

Here is how the stride works on a small example. Take a 3×4 tensor stored row-major (row 0 first, then row 1, then row 2). Its 12 numbers sit in memory at positions 0 to 11, and its stride is (4, 1): moving down one row skips 4 elements, moving right one column skips 1. So element [i][j] lives at position i×4 + j×1. Element [2][1] is at 2×4 + 1 = 9.

  • Transpose x.T just swaps the strides to (1, 4) and the shape to 4×3. Element [1][2] of the transpose is at 1×1 + 2×4 = 9 — the same number as before. No data moved.
  • Slicing x[:, 1:3] keeps stride (4, 1) but starts reading at position 1 instead of 0, with shape 3×2.
  • Contiguous means “walking the tensor in order visits memory in order”. The original is contiguous; the transpose is not, because reading its first row jumps 0, 4, 8. Kernels that need ordered data must first copy it into a new, ordered block — that is what .contiguous() does.

Four things to check on any tensor bug

t.shape — is the batch dimension where you think? t.dtype — an accidental fp32 costs 2× memory and speed. t.device — one stray CPU tensor forces a copy, and a wait, every step. t.is_contiguous() — if the data isn't laid out in order, some kernels quietly switch to a slow path or make a copy.

Autodiff: the tape

Frameworks compute gradients for you with reverse-mode automatic differentiation (“autodiff”). It works like a trail of breadcrumbs. During the forward pass, every operation writes itself down and saves whatever it will need to compute its own derivative. Then backward() follows that record in reverse, applying the chain rule at each step.

x = torch.randn(4, 3, requires_grad=True)
y = (x @ W).relu()        # saves: x, W, and the relu mask
loss = y.mean()

loss.backward()           # walks the tape backwards, fills .grad
opt.step(); opt.zero_grad()   # update, then clear — forgetting this accumulates

A tiny worked example shows what the tape stores. Let x = 3 and w = 2, and compute loss = relu(x × w).

  1. Forward, op 1: a = x × w = 6. To differentiate a product later it needs both inputs, so it saves x = 3 and w = 2.
  2. Forward, op 2: loss = relu(a) = 6. relu's slope is 1 where the input was positive and 0 otherwise, so it saves a single “was it positive?” mask: yes.
  3. Backward, op 2 first: start from d(loss)/d(loss) = 1. relu passes it through unchanged because the mask says positive: d(loss)/da = 1.
  4. Backward, op 1: the chain rule gives d(loss)/dw = d(loss)/da × x = 1 × 3 = 3, and d(loss)/dx = 1 × w = 2.

Notice the backward pass needed x, w and the mask — values from the forward pass. In a real network those saved values are whole activation tensors, one or more per layer, and that is where training memory goes.

Why reverse mode? A network has millions of inputs you want gradients for (the weights) but only one output (the scalar loss). Going backwards from that one output gives the gradient for every weight in a single pass, costing about as much as one or two forward passes. Going forwards would need a separate pass per weight.

Also note that backward() adds into .grad rather than overwriting it. That is on purpose — it lets you sum gradients over several small batches (gradient accumulation) — but it is why you must call zero_grad() each step.

💾 Why activations dominate memory

Every saved in-between result must stay in memory until its backward step runs — that is, for the whole forward pass. Gradient checkpointing trades compute for memory: throw away most activations and recompute them during backward. It is ~30% slower but uses several times less memory.

🚫 no_grad / inference_mode

At inference you don't need gradients, so there's no tape to build. Wrap evaluation in torch.no_grad() (or inference_mode) to remove that memory and overhead entirely. Forgetting it is a classic cause of running out of memory (OOM) during validation.

✂️ detach()

Cuts the graph at one point, so gradients stop flowing there. Useful for target networks, stop-gradients and logging. Accidentally keeping a tensor attached is how “my list of losses ate 40 GB” happens.

Eager vs compiled

Eager execution runs operations one at a time, as Python reaches them. It is easy to debug. But every op pays Python overhead plus a full trip to memory and back.

Compilation records the whole graph of operations first. Then it can optimise across them — for example, merging several ops into one.

A worked example of why merging (“fusion”) helps. Say you compute relu(x × 2 + 1) on a tensor of 40 million fp32 numbers, which is 160 MB. In eager mode that is three kernels. Each one reads 160 MB from HBM and writes 160 MB back, so the three together move about 960 MB. A fused kernel reads x once, does all three steps in registers, and writes the answer once: about 320 MB. The maths is identical, but the data moved is three times smaller — and for cheap elementwise ops, data moved is the run time (Chapter 10's memory-bound case).

🧱
Graph breaks and recompiles

A compiler records ops until it hits something it can't handle. Examples: a print, an if that depends on the data, or a .item() call that makes the CPU wait for the GPU. At that point it splits the graph in two — a graph break — and can't fuse across the split.

Also, each new input shape can trigger a fresh compile. With variable-length sequences, group lengths into a few buckets or mark those dimensions as dynamic. Otherwise you'll spend the whole run compiling.

The input pipeline is part of the model

If a GPU finishes a step in 80 ms, the next batch must be ready within 80 ms. Otherwise the GPU sits idle. Decoding JPEGs, tokenizing text, or reading many small files from network storage will not keep up unless you design for it.

Put numbers on it. With a batch of 256 images and an 80 ms step, the loader must deliver 256 ÷ 0.08 = 3,200 images per second. If one CPU core can decode and augment, say, 150 images per second, you need over 20 cores working in parallel just to keep up — per GPU. With 8 GPUs in a machine, that is more cores than many machines have. This is why image pipelines so often end up CPU-bound.

The quick test: replace the real loader with one that returns the same random batch every step. If the step time drops a lot, your model was waiting on data, and the levers below matter more than any model change.

When it breaks: profiling and OOM

Before any fix, know where memory goes. With plain fp32 training and the Adam optimizer, each parameter costs about 16 bytes: 4 for the weight, 4 for its gradient, and 8 for Adam's two running averages. So a 1-billion-parameter model needs about 16 GB before a single activation is stored. Activations come on top and grow with batch size and sequence length — which is why cutting the batch size is the first lever: it shrinks activations but not the 16 bytes per parameter.

🔬 Profile before optimising

The framework's profiler gives a timeline of every kernel: how long each op took, how much time went to Python, and where the gaps are. Look for three things: (1) gaps = the GPU is waiting for input; (2) many tiny kernels = a chance to fuse; (3) big all-reduce blocks = communication that isn't overlapped with compute.

💥 OOM triage, in order

When you run out of memory, try these in order: reduce batch size → turn on gradient checkpointing → look for tensors kept alive by accident (loss lists, caches) → confirm no_grad at eval → use a memory-efficient optimizer → then shard across GPUs (Ch 23). Memory snapshots show which tensors are in memory, not just the total.

📦
Checkpoints: prefer safetensors

Classic checkpoints use Python's pickle format, which can run any code when loaded. That is a real security risk when you download weights from someone else (Chapter 36). safetensors is a plain container of tensors: it runs no code, can be memory-mapped (read straight from disk on demand), and loads faster.

Also save the optimizer state, the random-number (RNG) state, the step count and the config. Without them, your “resume” is really a restart.

⚠️
Common mistakes
  • Calling .item() or .cpu() inside the training loop. Each call makes the CPU wait for the GPU to finish, which stalls everything. Keep running totals on the GPU and log only now and then.
  • Keeping the loss tensor in a list. It keeps the whole graph alive in memory. Append loss.detach().item() instead.
  • Evaluating without no_grad. Doubles memory for no reason, and often runs out of memory at the worst moment.
  • Benchmarking without warmup or synchronisation. CUDA is asynchronous: your Python line returns before the GPU finishes. Time it after a few warmup runs and an explicit sync, or you are only timing how fast work gets queued.
  • Assuming torch.compile is free. Measure it. On small models Python overhead was never the bottleneck, and compile time can be bigger than the savings.

Interview drill

Warm-up: Why does gradient checkpointing save memory, and what does it cost?

How a strong answer sounds
Normally every in-between activation is kept from the forward pass until its backward step runs. For deep models that is the biggest memory cost. Checkpointing stores only a few activations at chosen boundaries and recomputes the rest during backward. With the standard policy, memory drops from roughly O(layers) to O(√layers). The cost is one extra forward pass — typically 20–35% more compute. It's the usual trade when memory is tight but you have spare FLOPs, which describes most large-model training.

Deeper: A profile shows 60% of step time in tiny elementwise kernels. What do you do?

How a strong answer sounds
Those kernels are memory-bound, so the goal is to move the tensor fewer times. First, turn on compilation so the chain fuses into one kernel. Check the log for graph breaks and remove the Python code causing them. Second, use fused versions that already exist — fused optimizers, fused LayerNorm, FlashAttention. Third, check the dtype: running elementwise chains in fp32 doubles the bytes. If it's still slow after that, write one Triton kernel for that specific chain. I'd re-profile after each change instead of applying them all blind.

🧠 Key takeaways

  • The stack is Python → framework/autograd → compiler → kernels → hardware. Each speed problem lives at one specific layer.
  • Tensors are memory plus metadata. Views are free, but data that's out of order (non-contiguous) can silently trigger copies.
  • Reverse-mode autodiff saves activations for the whole forward pass — the main memory cost of training.
  • Compilation mostly wins by fusing chains of memory-bound ops. Graph breaks and recompiles from changing shapes undo that win.
  • Profile first. Gaps mean the GPU is waiting for input; tiny kernels mean fuse them; big collectives mean overlap communication with compute.

Check your understanding

What does x.T do to memory in a typical framework?

Transpose only changes the metadata, so it's free. But the result is non-contiguous (not stored in order), so any later op that needs ordered data will make a copy.

Your validation loop OOMs while training runs fine at the same batch size. Most likely cause?

Without no_grad, every op records itself and saves activations. So evaluation costs as much memory as training — on top of whatever training is already holding.

A profile shows regular gaps where no kernel is running. What is the most likely cause?

Regular idle time between steps is the classic sign that the GPU is waiting for data. Add loader workers, prefetch, pin memory, or do the preprocessing ahead of time.

Why can torch.compile repeatedly recompile during training?

Compilers build a graph for one specific shape. Batches of varying length create a new graph each time. Group lengths into buckets, or mark those dimensions as dynamic.

Why prefer safetensors over pickle-based checkpoints?

Loading a pickle runs code stored in the file — a real risk for weights you download. safetensors is a plain container of numbers: safer, and faster to load.
