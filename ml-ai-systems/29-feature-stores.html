Feature Stores & Training/Serving Skew

The most expensive bug in applied ML is not in the model. It's that the number called avg_order_value_30d in training is not the same number as the one with that name in production. It was computed by different code, from different data, at a different moment. This mismatch is called training/serving skew. A feature store is a system built to prevent it.

Three flavours of skew

Why care? A model only works if it is fed, in production, the same kind of numbers it learned from. Skew breaks that promise without throwing a single error. The model still returns a score for every request. The score is just quietly worse than the one you measured offline. There are three ways this happens.

🧮

Implementation skew

Training computes the feature in SQL; serving computes it in Python. Two versions of the code mean two rounding rules and two ways of handling missing values. The gap between them grows quietly.

⏰

Temporal skew

Training uses values as they are today; serving uses values as they were at request time. This is leakage (the model sees information from the future), and it makes your offline scores look better than they are.

📊

Distribution skew

Training data comes from a clean warehouse table. Serving sees timeouts, missing values, defaults and an out-of-date cache. The model never saw the kind of inputs it actually receives.

A small example of implementation skew makes it concrete. Take one customer with three orders in the last 30 days: £60, £30, and a £30 order that was later refunded.

  • The training SQL counts every order: (60 + 30 + 30) / 3 = £40.
  • The serving code, written later by another team, skips refunded orders: (60 + 30) / 2 = £45.

Both are reasonable definitions of “average order value”. But the model learned what £40 means for a customer like this, and in production it is shown £45. Nothing crashes. Every refund-heavy customer simply gets a slightly wrong score, forever.

🔍
The signature

Excellent offline scores, disappointing live results, and no obvious bug. Don't blame the model or the product change yet. First, log the exact feature vector served (the list of input values the model got) for a sample of requests. Compare it with what your training pipeline would have produced for the same entity at the same timestamp. Differences here explain more failed launches than every other cause combined.

Point-in-time correctness

A training row is (entity, timestamp, label). The entity is the thing being predicted about, like a customer. The features attached to that row must be the values that were knowable at that timestamp. Not the latest values, and not values from a table that has been updated since.

Getting this right needs an as-of join: "give me the value as it was at this moment". Think of looking up a stock price in yesterday's newspaper, not today's. It's fiddly enough that doing it for you is the main reason feature stores exist.

The rule for each training row is simple to state: look at every recorded value of the feature for that entity, throw away any recorded after the row's timestamp, and keep the newest one that is left. A tiny trace, using the same numbers as the simulator below:

Two edge cases every as-of join must handle. First, no earlier value at all: a brand-new customer has no history before their first label, so the feature is missing. Keep it missing (and let the model learn what “missing” means) rather than borrowing a later value. Second, a value recorded at exactly the label time: decide once whether “at or before” includes that instant, and use the same rule everywhere. If the feature update could have been caused by the labelled event itself, exclude it.

Also subtract the pipeline's own delay

Strictly, the right question is not “what was true at time T?”. It's “what would the serving system have known at time T?”. Say a feature pipeline delivers data 20 minutes late. Then at request time, the online store held a value that was already 20 minutes old. A training set built with up-to-the-second values is still too optimistic. Good feature stores let you declare that delay and build training sets to match.

What a feature store is

A feature store is not one database. It is two stores and the plumbing between them, built around a single definition of each feature. Why two stores? Because training and serving ask very different questions:

  • Training asks: “give me this feature for 50 million (customer, timestamp) pairs across two years.” That is a big scan over history. A warehouse or lakehouse table does it well, but takes seconds to minutes.
  • Serving asks: “give me the current value of 40 features for customer 8812, now.” That is one key lookup that must finish in a few milliseconds. A key-value store like Redis does it well, but keeps no history.

No single database is good at both, so the feature store keeps both. The same transformation code writes into each, which is what keeps them consistent.

Materialization is the word for copying computed values into the online store. For example, a nightly Spark job computes avg_order_value_30d for every customer and writes the results to both stores. The offline copy gets a new dated row; the online copy is overwritten with the latest value. A feature that must be fresher than “last night” — say, “number of logins in the last 10 minutes” — is instead materialized by a streaming job that updates the online store within seconds of each event. The TTL then says how long a value may sit there before it counts as too old to use.

Two ways to build the training set

A · Reconstruct from history

Take labelled events and as-of join them to the offline store. Works on past data for any model, and lets you add new features after the fact. It's also exactly where point-in-time bugs live.

B · Log what you served

Save the exact feature vector used for each prediction. Join the labels when they arrive. There is zero skew by design, and the logs double as your parity monitor (a check that online and offline values match). The catch: you can only train on features you were already serving. New features still need path A.

When to lean on each: pick A when you are trying a new feature or training a first model, because there are no served logs for it yet. Pick B for retraining a model that is already live, because it reproduces exactly what production saw. Path B has one extra trap: the logs only contain requests the current model handled, so if the model changed who got shown what, the logged data reflects that choice (Chapter 30 calls this a feedback loop).

✅
Do both

Log served feature vectors from day one. It costs a little storage and pays for itself the first time a launch disappoints. Use reconstruction to explore new features. Use the logs to check that your reconstruction gives the same numbers. A weekly job that compares the two on a sample, and alerts when they differ, is one of the most valuable things in an ML platform.

Watching parity

A parity monitor answers one question: “for the requests we actually served, would the training pipeline have produced the same inputs?” The recipe is short:

  1. Sample, say, 10,000 served requests a day, with their logged feature vectors and timestamps.
  2. For each one, ask the offline pipeline for the same features, for the same entity, as of the same timestamp.
  3. Compare them feature by feature. For numbers, count the rows where they differ by more than a small tolerance (1% is common). For categories, count the rows where they don't match exactly.
  4. Alert when a feature's mismatch rate crosses a threshold, for example 2% of rows.

Why per feature? Imagine 40 features, and one of them is wrong on every row. An overall “percent of vectors that match” would drop to zero and tell you nothing about which one. A per-feature table points straight at the broken one. Toggle the cases below to see how each kind of skew looks.

🧰
The discipline matters more than the product

You can get 90% of the value from team habits alone:

  • One repository of feature definitions. Every feature is defined once, in a place everyone can find, with an owner.
  • One code path shared by training and serving. The same function computes the value in both places, so there is no second version to drift.
  • As-of joins in the code that builds training sets. Every training row only sees values that existed at its timestamp.
  • Served vectors logged. You keep a record of exactly what the model was given.
  • A parity alert. A scheduled job compares served and recomputed values and pages someone when they drift.

Buying a feature store without those habits gives you a new system to run and the same bugs.

⚠️
Common mistakes
  • Two implementations of one feature. They will drift apart. The only question is when you notice.
  • Joining the latest feature values to historical labels. Leakage: great offline numbers, flat launch.
  • Ignoring how out of date the online store is when building training data. The model learns from fresher data than it will ever see live.
  • No default rule for timeouts. If a feature fetch fails at serving time, what value is used? And did the model ever see that value in training?
  • Unlimited feature sprawl. Hundreds of features, no owners, no TTLs, and nobody can safely delete anything.
  • No parity monitoring. Skew is silent by nature. It only shows up months later as a disappointing A/B test result.

Interview drill

Warm-up: What is point-in-time correctness and why does it matter?

How a strong answer sounds
It means every feature on a training example reflects only what was knowable at that example's timestamp. Without it, a feature built from data that arrived after the label leaks the future. The model looks brilliant offline but can't repeat it in production, because at prediction time that information doesn't exist yet. You implement it with an as-of join on (entity, timestamp). Strictly, it should also account for pipeline delay: what the serving system would have known, not what was true.

Deeper: Offline AUC 0.89, online lift zero. Design the investigation.

How a strong answer sounds
Assume skew until proven otherwise. Take a sample of production requests and log the exact served feature vector plus the model's output. Recompute the same features from the offline pipeline for the same entity and timestamp. Compare them feature by feature. Large, consistent differences point to implementation skew. Small ones point to staleness. Spikes of nulls point to timeout defaults. Separately, rebuild the training set with a strict as-of join that includes pipeline delay, and see how much AUC is left. A big drop means temporal leakage. Then check distributions: compare served values with the training distribution for each feature. Serving sees defaults, retries and brand-new entities that the warehouse never contained. Only after all three would I look at the model, or at whether the product change itself changes behaviour.

🧠 Key takeaways

  • Skew comes in three kinds: implementation, temporal and distribution. All three are silent.
  • Training rows need as-of joins that respect both event time and pipeline delay.
  • A feature store is a registry, an offline store, an online store and a way to keep them in sync, plus good habits.
  • Logging the served feature vector gives you zero-skew training data and a parity monitor for free.
  • You often don't need the product. You always need one definition and one code path.

Check your understanding

You join today's customer_tier onto labels from 18 months ago. What kind of skew is this?

Values that only became true later are attached to earlier examples. The model learns a pattern that isn't available at prediction time. It doesn't matter that the tier “rarely changes”: the customers whose tier did change are often exactly the ones the label is about (for example, downgraded after they churned).

What's the main advantage of logging the served feature vector?

You train on exactly what the model saw, including old values, defaults and nulls. It also works as your parity check. The cost: you can only train on features you already serve.

Your feature fetch times out for 2% of requests and the code substitutes 0. What must you check?

If the model never saw 0 in training, it reads it as a real value, often a strong one. Mark missing values explicitly, and make sure they appear in the training data too.

When is a dedicated feature store least justified?

If there's nothing to share and no time-based join, a shared function in the service gives you the same guarantee. And there's no extra system to run.

What should a parity monitor compare?

That comparison is the only direct measure of skew. Alert on differences per feature. A single broken feature rarely moves an overall metric until it's too late.
