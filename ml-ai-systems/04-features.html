Features & Representations

A model only ever sees numbers. Everything between your raw data and those numbers — scaling, encoding, summarising, embedding — is called representation. It decides how hard the learning problem is. Deep learning automated a lot of this work, but not all of it.

  • Transform numeric features so optimizers can actually work
  • Encode categories — one-hot, hashing, target encoding, embeddings
  • Build time, sequence and combination features without leaking
  • Know when learned representations replace hand-made features, and when they can't
  • Weigh a feature's value against its speed cost and upkeep

What counts as a feature

A feature is a number made from your data that passes three tests. It is available at prediction time. It can be computed fast enough (within the latency budget). And it is computed the same way in training and in serving. Fail any one and it isn't a feature — it's a future bug.

⏱️

Available in time

Known before the event you're predicting. Tie every feature to the moment of prediction (Chapter 29 shows how to make the system enforce this).

⚡

Affordable

A feature that needs a 300 ms database join is useless when you only have 50 ms. Compute it ahead of time, cache it, or drop it.

🔁

Reproducible

The same definition offline and online. Two separate versions of “average order value” is the classic training/serving skew bug.

Numeric features: shape matters more than you think

Raw numbers are rarely ready for a model. Incomes range over four orders of magnitude (£1,000 to £10,000,000), ages over two. Gradient-based optimizers hate that. The loss surface turns into a long, thin valley, and training slows to a crawl. Try the transforms below.

Why a thin valley? Imagine a linear model with one weight for income and one for age. Nudging the income weight by 0.001 changes the prediction for a £1,000,000 earner by 1,000; nudging the age weight by the same amount changes it by about 0.04. So the loss is extremely sensitive in one direction and barely sensitive in the other. One learning rate has to serve both weights: small enough not to overshoot on income, which makes it painfully slow for age. Putting every feature on a similar scale gives a rounder valley where one step size suits every weight.

The two most common transforms, with numbers:

  • Standardize: subtract the mean, divide by the standard deviation. Ages [20, 30, 40] have mean 30 and standard deviation about 8.2, so they become about [−1.22, 0, 1.22]. Every feature ends up centred on 0 with a typical size of about 1.
  • log1p, which is log(1 + x): incomes of £20,000, £50,000 and £5,000,000 become about 9.9, 10.8 and 15.4. The huge earner is still the largest, but no longer 250 times larger, so one extreme value cannot dominate. The "+1" keeps a value of 0 safe, since log(0) is undefined.

Which transform when
  • Linear models and neural nets: standardize (shift to mean 0, scale to std 1). Always do this — it can make training about 10× faster to settle.
  • Positive values with a long tail (income, counts, durations, prices): apply log1p first, then standardize.
  • Trees and gradient boosting: scaling makes no difference — trees only compare values against thresholds. Don't waste effort.
  • Image and audio inputs: min-max scale to [0,1] or [-1,1], to match what the pretrained network saw.

Missing values are information

Never quietly fill in blanks and move on. NULL usually means something: the field didn't exist yet, the user skipped it, or an upstream service timed out. Fill it in (impute) and add a true/false was_missing flag. Then the model can use the fact that it was missing. And a sudden jump in missing values shows up in monitoring, instead of quietly shifting your median.

For example, if a user left "income" blank and the training median is £32,000, the model receives income = 32,000, income_was_missing = 1. If people who skip the income question behave differently (say, they are more likely to be students), the model can learn that from the flag. Without it, those users would look exactly like typical £32,000 earners. Compute the median from the training split only, for the same leakage reason as in Chapter 3.

Categorical features

Categories (country, device, seller…) are the messiest part of ML on tables. They can have huge numbers of distinct values (high cardinality). They change over time. And values you've never seen will definitely show up in production.

Two quick examples. One-hot for device ∈ {ios, android, web} turns "android" into [0, 1, 0]: three columns, exactly one of them 1. Each device gets its own weight, and no device is treated as "bigger" than another. Compare an ordinal encoding of colours, red = 1, green = 2, blue = 3. A linear model multiplies the number by one weight, so it is forced to treat blue as "three times red" and green as exactly halfway between. That is nonsense for colours, which is why ordinal encoding suits trees (which only ask "is it ≤ 2?") or truly ordered values like small < medium < large.

Two categories sharing a slot is usually fine. The model just sees a slightly blurred signal, and it's mostly rare values bumping into other rare values. This is how ad-click systems handle billions of feature values in a fixed amount of memory (Chapter 43).

🎯
Target encoding: powerful and dangerous

Replacing “seller_id” with “that seller's past fraud rate” is often the strongest feature you can build. It's also the easiest way to leak. You must compute the average out-of-fold — from rows other than the one being encoded — or only from earlier data. And for rare values, pull it toward the overall average (smoothing): (sum + m·prior) / (count + m). Skip either step and the model memorises the answer, and your validation score is fiction.

The smoothing formula, worked. Say the overall fraud rate (the prior) is 1%, and you choose m = 100, meaning "trust a seller's own rate about as much as 100 rows of average behaviour".

  • A new seller with 2 orders, 1 of them fraud, has a raw rate of 50%. Smoothed: (1 + 100 × 0.01) / (2 + 100) = 2 / 102 ≈ 2%. Two orders are not enough evidence to call a seller a fraudster, so the value stays close to the average.
  • A big seller with 10,000 orders and 300 frauds has a raw rate of 3%. Smoothed: (300 + 1) / (10,000 + 100) ≈ 3%. With plenty of data, the seller's own rate wins.

Out-of-fold, step by step. Split the training rows into, say, 5 groups (folds). To encode the rows in fold 1, compute each seller's average using only folds 2 to 5. Repeat for each fold. No row ever sees its own label, so the encoding carries only what could have been known from other examples, which is exactly what will be true for new rows at prediction time.

Interactions and crosses

Linear models can't learn “this feature matters only when that other one is true”. You have to hand it to them as a cross — a new feature that combines two others: country × device, hour × is_weekend, query_token × product_category. Crosses were the backbone of ad systems before deep learning. They're still standard in the “wide” half of wide-and-deep models.

Here is why a cross is needed. Suppose iPhone users click more ads in the UK but fewer in Germany. A linear model gives country = UK one weight and device = iOS another, and adds them. It can only say "iOS is good everywhere" or "iOS is bad everywhere". Adding a cross feature, is_UK_and_iOS (1 only when both are true), gives it a separate weight for that exact combination, and the pattern can be learned. The cost: crossing 200 countries with 5 devices creates 1,000 new columns, most with few examples each, which is why hashing (above) is often applied to crosses.

🌳 Trees get them free

A decision tree that splits on country and then on device is an interaction. That's a big reason GBDTs win on table data with little feature work.

🧠 Deep nets learn them

Hidden layers combine inputs in roughly multiplying ways, and attention learns which features interact for each example. But with limited data, an explicit cross still beats hoping.

Time and sequence features

Timestamps are your richest column — and the one most likely to leak. Here are three things to do with them:

🔁 Cyclical encoding

Hour 23 and hour 0 are next to each other, but as plain numbers they're 23 apart. Encode as sin(2πh/24), cos(2πh/24) — points on a clock face — so the distance comes out right.

📊 Rolling aggregates

Count / mean / max over the last 1h, 24h, 30d — strictly before the prediction time. The workhorse of fraud and recommendation features.

⏳ Recency & gaps

“Seconds since the previous event”, “days since first seen”. Cheap, strong, and useful in nearly every model about users.

The raw number says 23:00 and midnight are the two most different times of day. The sin/cos pair says they are neighbours — which matches how real traffic, fraud and demand patterns behave.

The numbers behind the circle. Midnight (hour 0) sits at (sin, cos) = (0, 1), the top of the clock. Hour 23 is at about (−0.26, 0.97), a distance of only about 0.26 away. Noon (hour 12) is at (0, −1), the bottom of the clock, a distance of 2 from midnight, the largest possible. You need both sin and cos: sin alone gives the same value to pairs of hours mirrored around 6:00 (for example, 1:00 and 11:00 both have sin ≈ 0.26), so the model could not tell them apart. The same trick works for day of the week (divide by 7) and month (divide by 12).

Text, images and the rise of learned representations

For unstructured data (text, images, audio), hand-made features lost. The history is worth knowing, because every step still shows up in real systems.

Bag of words / n-grams

Count each word (or short word sequence). The result is huge and mostly zeros, with no sense of meaning — “great” and “fantastic” are unrelated columns. Still a fine, very fast baseline.

TF-IDF

Give rare words more weight so “the” stops dominating. Powers BM25 and classic search, and is still the keyword half of hybrid retrieval (Chapter 21).

Word embeddings

word2vec/GloVe: one short list of numbers per word, learned from the words around it. Meaning becomes geometry — but each word gets one vector, whatever sentence it's in.

Contextual embeddings

BERT-style encoders give each token a vector that depends on its sentence, so “bank” (river) and “bank” (money) differ. This is what modern embedding models provide (Chapter 15).

End-to-end learned

The network takes raw tokens or pixels and learns every in-between representation itself. Your job shifts from crafting features to choosing good data and designing the input pipeline.

How TF-IDF weighs a word. A word's weight is its count in the document times a rarity score, often log(N / df): N documents in total, df of them containing the word. In 1,000 support tickets, “the” appears in all 1,000, so its rarity is log(1) = 0 and it counts for nothing. “refund” appears in 10, so its rarity is log(100) ≈ 4.6, and a ticket that mentions it twice scores about 9.2 on that word. Word embeddings then fixed the other weakness: “refund” and “reimbursement” are separate columns in TF-IDF but end up as nearby vectors in an embedding.

🧩
“Deep learning means no feature engineering” is half true

It's true within one data type: you no longer design edge detectors for images. It's false for the system as a whole. Someone still decides which 30-day summaries to fetch, which parts of a user's history to include, what goes into the prompt, and how an ID maps to an embedding row. In recommender and table-data systems, feature work still brings most of the measurable gains.

⚠️
Common mistakes
  • Fitting encoders on the full dataset. Scalers, target encoders and vocabularies must be fitted on training data only. Otherwise validation data leaks in.
  • No plan for unseen categories. Production will send you a country code, app version or merchant you've never seen. Reserve an explicit “unknown” slot (<UNK>) and test it.
  • Rolling windows that include the present. “Purchases in the last 7 days” computed with <= instead of < includes the very event you're predicting.
  • Two implementations of one feature. A SQL version for training and a Python version for serving will drift apart. Use one definition and one code path (Chapter 29).
  • Hoarding features. 400 features with only 30 doing the work means 370 extra pipelines to maintain, and 370 chances of a silent null. Remove features based on how useful they are and what they cost.
🎤
Interview drill

Warm-up: Design the feature set for “will this food delivery be late?”, predicted at order time.

How a strong answer sounds
Three groups. Order: item count, prep-time estimate, price, whether it's scheduled. Context: hour and day (cyclically encoded), weather, distance, is it raining right now. Summaries as of now: the restaurant's median prep time over the last 30 days and the last 2 hours, couriers available within 3 km, the restaurant's current queue of open orders, the courier's recent on-time rate. Everything must use a strict “before order time” cut-off. It must be served from a fast online store within a few milliseconds, using the same definitions as the training set. So I'd define each feature once, in a shared feature repository, not in two places.

Deeper: You have 2 million distinct seller IDs and need them in a neural ranker. Options?

How a strong answer sounds
A 2M-row embedding table uses lots of memory, and most rows won't get enough training. So: keep their own embeddings for the big sellers with plenty of traffic. Hash the long tail of small sellers into a shared set of buckets. And add descriptive features (time on the platform, category, rating, past rates computed out-of-fold). That way a brand-new seller still gets a sensible score from its attributes. You get detail where there's data, a sensible fallback where there isn't, and a fixed memory size — which is also what makes the model practical to serve.

🧠 Key takeaways

  • A feature must be available in time, cheap enough to serve, and defined the same way offline and online.
  • Standardize (and log-transform skewed positive values) for gradient-based models. Skip it for trees.
  • Choose a category encoding based on how many values there are and your model type. Target encoding must be computed out-of-fold.
  • Put repeating time (hours, weekdays) on a circle, and build rolling summaries with a strict time cut-off.
  • Judge features by gain per millisecond and per pipeline, not by gain alone.

Check your understanding

You're training gradient-boosted trees on tabular data. Which preprocessing step is least useful?

Trees split on thresholds, so rescaling that keeps the order of values changes nothing. The other three all add real information.

Encoding hour-of-day as the integers 0–23 in a neural net causes what problem?

The model has to waste effort learning that the ends wrap around. Sin/cos encoding places them next to each other automatically.

Target encoding a merchant_id column with the overall fraud rate per merchant, computed on the whole training set, causes…

For a rare merchant, the encoded value is basically that row's own label. Compute it out-of-fold (or only from earlier data) and pull it toward the overall average.

What is the main advantage of the hashing trick over one-hot encoding?

Hashing fixes the number of slots in advance. So even if new values keep arriving forever, the system fits in a known amount of memory. The cost: some values share slots, and it's harder to interpret.

A feature adds +0.002 AUC but requires a 250 ms third-party API call per prediction, in a service with a 100 ms p99 budget. What do you do?

A feature you can't compute in time isn't a feature. If the signal really is valuable, move it offline: refresh it in the background and read a cached value when the request comes in. You accept slightly out-of-date values in exchange for staying within the budget.
