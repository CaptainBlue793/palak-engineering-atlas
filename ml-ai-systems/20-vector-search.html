Vector Search & ANN Indexes

An embedding turns text (or an image) into a list of numbers, a vector, so that similar things get nearby vectors. Finding “the stored vectors closest to this one” powers RAG, recommendations, duplicate detection and search by meaning. The idea is simple, but doing it over millions of vectors is extremely expensive. So all the clever work is in finding answers that are nearly right, very fast.

The problem

First, what “closest” means. With 2-number vectors, take the query q = [1, 0], and two stored items a = [0.8, 0.6] and b = [0, 1]. The dot product q·a = 1×0.8 + 0×0.6 = 0.8, and q·b = 0. So a is the closer match. When all vectors are scaled to length 1 (normalized), as here, the dot product equals the cosine similarity, and ranking by straight-line (L2) distance gives the same order. That is why most systems normalize once and then use the cheap dot product.

Exact search compares the query to every stored vector. With 50M vectors of 768 numbers each, that's 50,000,000 × 768 ≈ 38 billion multiply-adds per query. On one CPU core that takes seconds. But you usually need an answer in a few milliseconds, for thousands of queries per second.

Approximate nearest neighbour (ANN) search fixes this. It gives up a little recall (occasionally missing one of the true closest matches) in exchange for being 100 to 1,000 times faster.

🎯
Approximate is fine — but measure it

Recall@10 of 0.95 means that, on average, you found 9.5 of the true top 10 matches. You measure it by running a query both ways: exact search says the true top 10 are items {1…10}; the index returns 9 of them plus item 57. That query scores 9/10 = 0.9. Average over many queries and you get the index's recall@10. For RAG you usually won't notice, because the re-ranker and the LLM cope fine if one borderline result is missing. For duplicate detection or legal/compliance search, you might. Choose the recall target based on what your application needs, then tune the index to hit it. Never blindly trust a library's default settings.

Two of these are easier to trust once you see the numbers.

  • IVF, sized. Split 1M vectors into 1,000 clusters of about 1,000 each. A query first compares itself with the 1,000 cluster centres, then searches only the nprobe = 10 nearest clusters: 1,000 + 10 × 1,000 = 11,000 comparisons instead of 1,000,000 — about 90× less work. The edge case: if the query's true nearest neighbour sits just across the border in the 11th-closest cluster, it is never looked at. Raising nprobe fixes that at the cost of speed.
  • PQ, sized. A 768-dimension float32 vector is 768 × 4 = 3,072 bytes. PQ cuts it into 96 pieces of 8 numbers. For each piece it learns 256 typical patterns, and stores just the number (0–255) of the closest pattern: one byte. So the vector becomes 96 bytes — 32× smaller. Distances computed from these codes are approximate, which is why the top candidates are re-checked against the full vectors.

How HNSW actually searches

HNSW (Hierarchical Navigable Small World) turns each vector into a node in a graph, linked to its nearby neighbours. Search is greedy: start at some node, hop to whichever neighbour is closer to the query, and repeat until no neighbour is any closer.

The graph has several layers. The top layers have few nodes and long links; the bottom layer has every node and short links. So search starts with big jumps and finishes with small steps. Think of finding a house: first you drive to the right city, then the right street, then walk to the door.

Why the layers and the candidate list? Plain greedy search can get stuck: it reaches a node where no neighbour is closer to the query, even though the true nearest item is elsewhere — a local minimum, like a valley that is not the lowest one. The long top-layer links make it unlikely you start somewhere hopeless. The candidate list (ef_search) keeps the best few dozen nodes seen so far instead of only one, so the search can back out of a dead end. Two build-time settings matter too: M, how many neighbours each node links to (more links, better recall, more memory), and ef_construction, how hard the builder searches when choosing those links (slower build, better graph).

Raising ef_search keeps more candidates in play, so the search explores more of the graph. You get higher recall, but more distance calculations and more latency. It is set at query time, so you can pick a value per request: low for autocomplete, high for compliance search.

The three-way trade-off

Every index balances three things: recall, latency and memory. You can easily get two of them. The third is where you pay.

💾
Memory is the real cost driver

A graph index must sit in RAM to be fast, and RAM is the expensive part of the bill. 100M vectors of 768 dimensions, stored as 4-byte floats (float32), take about 307 GB. The graph adds about 60% on top.

Scalar quantization stores each number as a 1-byte integer (int8) instead. That cuts memory 4× and costs about one point of recall. Product quantization cuts it 10–50× but needs a rerank pass. Plan the memory budget first, then pick the index that fits it.

Filters, updates and tenancy

Real queries almost never mean “closest vectors in the whole collection”. They mean “closest vectors among documents this user may see, in French, updated this year”. These extra conditions are where simple vector search breaks. A quick example: if only 1% of documents match the filter and you post-filter the top 100, you expect to keep about 1 result — and the user asked for 10.

🔎

Filtered search

Say you only want results where country is France.Post-filter (search, then drop non-matches) breaks when few items match: you fetch 100 and keep 2. Pre-filter (narrow the set, then search) is exact but can stop the index from helping. Good engines do filtered traversal: they apply the filter while walking the graph.

♻️

Updates & deletes

Graph indexes can't remove nodes cleanly. Deleted items are usually just marked as deleted (a tombstone), and quality slowly drops until you rebuild. Plan regular clean-ups (compaction). Treat “rebuild the index” as routine: build a new copy on the side, then swap it in.

🏢

Multi-tenancy

A tenant is one customer of your system. One index per tenant keeps them perfectly apart, but wastes memory on small tenants. One shared index with a tenant filter is efficient, but then keeping tenants apart becomes both a correctness and a security issue. Test it explicitly (Chapters 37, 46).

🔐
Permissions are part of retrieval, not a post-processing step

If a user isn't allowed to see a document, search must never return it. Filtering it out afterwards is not enough, and summarising it into an answer before filtering is far worse. Store the access rules (ACLs, access control lists) next to the vectors, and pass them into the search as a filter. Write a test that searches as user A and checks that nothing from user B comes back. This is one of the few real security walls in a RAG system.

Hybrid search: lexical plus vector

Embeddings are great at meaning but unreliable at exact strings: product codes, error numbers, names, rare acronyms. BM25, the classic keyword-matching score used by search engines, is the opposite. Run both and merge the results. On almost every real document collection, that beats either one alone.

# Reciprocal Rank Fusion — no score calibration needed between systems
score(d) = Σ_over_retrievers  1 / (k + rank_in_that_retriever(d))     # k ≈ 60

# then re-rank the fused top ~100 with a cross-encoder (Chapter 21)

Why merge by rank instead of by score? The two systems score on different scales: BM25 might give 12.4, while cosine similarity gives 0.83. Adding them would let BM25 drown out the vectors. Ranks are always 1, 2, 3…, so they can be combined fairly. A worked example with k = 60:

  • Doc A: rank 1 in vector, rank 3 in BM25 → 1/61 + 1/63 ≈ 0.0164 + 0.0159 = 0.0323
  • Doc C: rank 5 in both → 1/65 + 1/65 ≈ 0.0308
  • Doc B: rank 1 in BM25, missing from vector results → 1/61 ≈ 0.0164

A document both systems like beats one that only a single system loves. The large k keeps the gap between rank 1 and rank 2 small, so no single retriever can dominate with one lucky top hit.

Choosing the storage

A quick size check helps here. 1M vectors × 768 dimensions × 4 bytes ≈ 3 GB. That fits comfortably in the RAM of an ordinary database server, alongside the rest of your data. 100M vectors is about 307 GB, which does not — and that is roughly where the choice starts to matter.

Start with what you have

Under about 1M vectors and moderate traffic (queries per second, QPS), pgvector (a Postgres extension) or your existing search engine's vector support is usually enough. You also get transactions, joins, filters and backups for free. Adding a separate vector database is a real commitment: one more system to run and keep healthy.

Move when you hit a wall

Dedicated engines (Qdrant, Milvus, Vespa, Weaviate, managed services) are worth it at tens of millions of vectors, high QPS, heavy filtering or hybrid ranking. Switch for a reason you've measured (index build time, p99 latency, memory cost), not because “we should have a vector database”.

⚠️
Common mistakes
  • Never measuring recall. Take 1,000 sample queries, compute the exact top-k offline, and track recall@k as a metric you monitor.
  • Mixing normalized and unnormalized vectors, or using cosine distance in the index but L2 (straight-line) distance for the query. Quality drops badly, with no error.
  • Post-filtering when few items match. Fetch 100, filter down to 3, then wonder why results are poor. Put the filter inside the search.
  • Forgetting the index goes stale. Deletes leave tombstones. New documents need a target for how fast they get indexed, and the index needs a regular rebuild.
  • Vector-only retrieval. Exact IDs, codes and names need keyword matching. That's why hybrid is the default.
  • Changing the embedding model without re-indexing. Old and new vectors aren't comparable (Chapter 15). This is still the top cause of quality collapsing overnight.

Interview drill

Warm-up: When would you pick IVF-PQ over HNSW?

How a strong answer sounds
When memory is the limiting factor. HNSW gives the best recall for each millisecond, but it stores the full vectors plus a graph, so it needs roughly 1.6× the raw vector size in RAM. IVF-PQ compresses vectors into short codes, often 10–50× smaller, so a billion vectors fit on one machine. The cost is that distances become approximate, so you rerank the top candidates against the exact vectors. In short: HNSW for tens of millions of vectors where speed matters most; IVF-PQ or DiskANN when the collection is huge or the RAM budget is fixed.

Deeper: Design retrieval for 500M chunks with per-user permissions and a 50 ms p99.

How a strong answer sounds
  • Split the data. Shard by document collection or tenant, so each shard holds a few tens of millions of vectors. Add replicas (copies) for throughput and availability. Send each query to all shards and merge the results.
  • Per shard: use a compressed index (IVF-PQ or HNSW with int8 vectors) sized to fit in RAM. Rerank the top ~200 against the exact vectors.
  • Permissions go into the index as filters applied during the graph walk, not afterwards. Push ACL changes through quickly, and document the worst-case delay.
  • Hybrid: add a keyword index for exact-ID queries and merge with RRF.
  • Latency: cap ef_search per request, limit how many shards each query hits, and cache popular queries. Keep measuring recall@k against exact offline results, so I know what the speed is costing me.

🧠 Key takeaways

  • ANN gives up a small, measurable amount of recall for a huge gain in speed. Pick the recall target based on the application.
  • HNSW is the default for quality and speed. IVF-PQ and disk-based indexes win when memory is the limit.
  • ef_search / nprobe can be set per query: spend more effort only on requests that need it.
  • Put filters and permissions inside the search itself, and plan for deletes and rebuilds.
  • Hybrid search (keyword + vector, merged by rank) beats either one alone on real data.

Check your understanding

What does ef_search control in HNSW?

The number of neighbours per node is M, which is fixed when the index is built. ef_search is set at query time, so you can change it for each request.

Your filter matches 0.1% of documents and results are poor. Most likely cause?

When very few items match the filter, post-filtering leaves only a handful of results, and they come from the wrong area of the vector space. Apply the filter during the graph walk, or keep a separate index for that subset.

Which query is vector search most likely to handle worse than BM25?

An ID has no meaning for an embedding to capture, and it gets chopped into random fragments. Exact keyword matching is what finds it. That's why hybrid retrieval exists.

You have 800M vectors at 1024 dims and a fixed RAM budget. What's the most appropriate approach?

The raw float32 vectors alone would be about 3.3 TB. Compression makes them fit. Reranking the top candidates against the exact vectors wins back most of the lost accuracy.

What does Reciprocal Rank Fusion solve?

BM25 scores and cosine similarities are on different scales, so you can't compare them directly. RRF looks only at each result's rank (1st, 2nd, 3rd...), so it can merge the two lists reliably with just one setting.
