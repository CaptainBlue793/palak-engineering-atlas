Multi-Tenant AI Platforms & Gateways

As soon as a second team wants to call a model, you have a platform, whether you planned one or not. The only question is which kind. Either it's a shared gateway (one front door for all AI calls) with usage limits, routing and cost tracking. Or it's fifteen teams, each with their own API keys and retry code, and one shared bill nobody can explain.

  • Design an AI gateway and know what belongs in it
  • Send each request to the right model based on ability, cost and load, with backup options (fallback chains)
  • Keep tenants (the teams or customers sharing the platform) apart, so one can't slow down another
  • Offer a do-it-yourself path that doesn't turn into a queue everyone waits in
  • Decide what to build and what to buy

The gateway

A gateway is a service that sits between your applications and the models. Apps send every AI request to the gateway instead of calling a model provider directly; the gateway checks it, decides where it goes, forwards it, and records what happened. It's the same idea as the API gateway in front of ordinary web services, specialised for model calls. Why bother? Picture the alternative: 14 services each hold their own vendor key. When the vendor has an outage, 14 teams each need to ship a fix. When finance asks which feature spent £40k last month, nobody can answer. When a key leaks, you have to hunt down which of 14 copies it was.

Follow one request through it. The support app sends “summarise this ticket” with its team credential. The gateway (1) checks the credential and finds it belongs to the support tenant, (2) checks that tenant still has quota this minute, (3) looks in the cache and finds nothing, (4) applies the routing rule “summaries go to the small self-hosted model”, (5) forwards the call, (6) blanks out any card numbers in the text before writing the log, and (7) records 2,100 input and 180 output tokens against support / ticket-summary. The app sees only a normal model response; all seven steps added a few milliseconds.

A quota is usually enforced with a token bucket: each tenant has a bucket that refills at a fixed rate, say 100,000 model tokens per minute, and every request takes tokens out. If the bucket is empty, the request is rejected with a “slow down” error (HTTP 429) instead of being queued forever. The bucket can hold a bit more than one minute's worth, so short bursts are fine but sustained overuse is not.

🪶
Keep the gateway thin

Every AI call in the company passes through the gateway. So every millisecond and every feature you add to it slows down or risks all of them.

  • Put in: auth, routing, quotas, logging and caching.
  • Keep out: business logic, prompt templates, retrieval and agent orchestration.

Those belong in the applications. Otherwise the gateway becomes a shared bottleneck that every team waits on and nobody can change safely.

Routing

Most requests don't need your most capable model. An FAQ lookup and a tricky multi-step coding task cost the same per token on a frontier model, but a small model handles the first one almost as well for a fraction of the price. Routing is choosing a model per request so that each one gets “good enough” at the lowest cost. Because the gateway sees every request, it's the natural place to do this.

A worked example using the simulator's numbers: 78% of traffic is simple and 22% is hard. A small model costs $0.35 per 1,000 requests, the frontier model $6.80. Sending everything to the frontier model costs $6.80 per 1,000. Sending the simple 78% to the small model and the rest to the frontier model costs 0.78 × 0.35 + 0.22 × 6.80 ≈ 0.27 + 1.50 = $1.77, about 74% less. The small model's quality on simple requests is 94% versus 98%, so you give up a few points on the easy part of the traffic in exchange. Whether that's acceptable is a question for your eval set, not for intuition.

Fallback chains are a reliability feature

A fallback chain is a list of backups to try in order: primary model → secondary model → smaller self-hosted model → cached or template response → an honest error message. Each step gives slightly worse answers, but the service stays up.

Every fallback must be logged and monitored. If a fallback quietly becomes permanent, quality drops and nobody sees it. Test the chain on purpose, too — a fallback path that has never run is one that doesn't work.

When should the gateway fall back? The usual triggers are errors (the provider returns a 5xx or a “rate limited” response), a timeout, or a circuit breaker that has seen too many failures in the last minute and stops trying the primary for a while. The timeout needs care. If the primary normally answers in 2 seconds, waiting 30 seconds before trying the backup means users wait 30 seconds too. A timeout a bit above the primary's normal p99, say 5 seconds, keeps the worst case bearable. Also make sure the backup accepts the same request: a smaller model may have a shorter context window, so a 60,000-token prompt that fits the primary may need trimming before it can go to the fallback.

Tenancy isolation

A tenant is anyone who shares the platform but should feel as if they have it to themselves: an internal team, or an external customer. Sharing GPUs is what makes the platform cheap, and it's also what makes one tenant able to hurt another. The noisy neighbour problem is the classic case: tenant B starts a large batch job, the shared GPUs fill up, and tenant A's live chat users suddenly wait five seconds for a reply, even though A changed nothing.

The options in the simulator, from lightest to heaviest: quotas cap how much any one tenant may use; priority classes let live, user-facing requests jump ahead of batch work in the queue, so batch soaks up spare capacity without delaying anyone; dedicated capacity gives your most important tenants GPUs nobody else can touch, which is the strongest guarantee but leaves that capacity idle when they're quiet. Most platforms combine the first two for everyone and add the third only for customers who pay for it.

The cache key is a security boundary

A semantic cache reuses a stored answer when a new question means roughly the same thing. If it returns tenant A's answer to tenant B, that's a data breach disguised as a speed-up.

Put the tenant (and the user's permissions, when retrieval is involved) in every cache key. Write a test that checks one tenant never gets another tenant's cached answer. This is a classic, embarrassing and completely preventable incident.

Concretely: a naive cache key is just the prompt text, say hash("What is our refund policy?"). Two companies on your platform both ask that question, and the second one gets the first company's policy. A safe key is hash(tenant_id, model_version, prompt), and for retrieval-backed answers also the set of documents the user was allowed to see. Including the model version has a second benefit: when you upgrade a model, old cached answers stop being served automatically.

Self-service: the golden path

A platform only pays off if teams actually use it. If getting access means filing a ticket and waiting three weeks, teams will sign up for a vendor with a credit card instead, and you're back to 14 unmanaged keys. The golden path is the supported, pre-built route from idea to production, designed so that doing the right thing is also the fastest thing. Here are its steps:

1Register the use case: owner, risk level, how sensitive the data is, expected volume. This creates the governance record (Chapter 37) automatically, instead of a separate document.
2Get credentials that only work for that use case, with default quotas and a cost budget attached.
3Start from a template: a working repo with the SDK, prompt versioning, an evaluation setup and tracing already connected.
4Bring an eval set (test cases with known good answers) — the platform requires one before you get production access. This one rule does more for quality than any review board.
5Ship through the standard rollout: shadow testing, canary release, guardrails, automatic rollback (Chapter 33) — provided by the platform, not rebuilt by each team.
6Get a dashboard for free, per tenant: latency, cost, sample answers for quality checks, fallback rate, and how much quota is left.
🛤️
Make the safe path the easy path

Platform teams fail when they act as gatekeepers — a review queue that teams find ways to skip. They succeed when the official “golden path” is truly faster than doing it yourself: a template that works in ten minutes, monitoring you'd otherwise have to build, and quotas that protect you from your own bugs.

Governance that comes for free with the golden path is the only kind that scales.

Build or buy

A useful test for each component: is it the same at every company, or does it encode how your company works? Logging traces, storing vectors and proxying API calls are the same everywhere, so products do them well and you gain little by rebuilding them. Which teams get which quotas, how a customer's contract maps to data retention, and how costs feed your billing system are unique to you, so no product will fit exactly.

Buy / adopt

Gateways, tracing, prompt management, eval tools and vector databases are now standard products you can buy. Buying gets you a working platform this quarter. Connecting them to your systems is still real work, so plan time for it.

Build

Build the parts that capture your rules: how tenants are set up, routing rules, how quotas work, governance records, and the glue to your login and billing systems. No vendor can know these for you.

Whichever you pick, keep a seam you control. If apps call your own thin SDK or an interface that follows a widely used API format, you can swap the product behind it later without touching every service. Lock-in rarely comes from the product itself; it comes from fourteen services calling its proprietary API directly.

⚠️
Common mistakes
  • A bloated gateway. Putting prompts and business logic inside it makes every team wait on the platform team.
  • No tenant in the cache key. A leak between customers, dressed up as a speed improvement.
  • Shared pool with no quotas. One team's batch job breaks the response-time target for live users at 2pm.
  • Untested fallback chains. You find out they're broken during the very outage they were built for.
  • Platform as gatekeeper. Teams go around it, and you lose the visibility that was the whole point.
  • No cost tracking from day one. Adding cost labels to 14 existing services later is far harder than starting with them.

Interview drill

Warm-up: Why put an AI gateway in front of a vendor API rather than letting each service call it directly?

How a strong answer sounds
Because some jobs apply to every service, and they need one home: authentication and tenancy, per-team quotas and spending caps, caching, consistent logging and redaction for audits, safety filtering, and cost tracking. A gateway also makes you portable: switching or adding a provider becomes a settings change instead of a change in every service. And it gives you one place to handle fallbacks when a provider has problems. The discipline is keeping it thin. It should add very little latency and contain no business logic — otherwise it becomes the bottleneck it was meant to remove.

Deeper: Design multi-tenancy for an AI platform serving 200 enterprise customers.

How a strong answer sounds
I'd isolate tenants in six areas. Data: a separate retrieval index per tenant, or strict access-control filters applied during search, with an automated test that one tenant can't see another's data. Models: one shared base model with a small LoRA adapter per tenant, served together in the same batch; each adapter id is tied to its tenant and checked at load (Chapter 17). Capacity: priority levels, per-tenant token quotas and admission control so no tenant can starve another, plus dedicated capacity for the few customers who pay for it. Cache: tenant and permissions in every key. Logs: limited access, redaction, and per-tenant retention that honours each contract. Cost: every request and GPU-second labelled for tracking and billing. On top of that, per-tenant dashboards and alerts when a tenant nears its quota, because support must be able to answer “why is it slow for us?” in one click. And every isolation rule gets automated tests, because these are security properties, not performance ones.

🧠 Key takeaways

  • A thin gateway puts auth, quotas, routing, caching, logging and cost tracking in one place.
  • Sending each request to a model that fits its difficulty is the biggest way to cut cost; fallback chains keep you online.
  • Keep tenants separate in data, adapters, capacity, cache, logs and cost — and test that separation.
  • An easy official path that requires an eval set beats a review board.
  • Buy standard tools; build the parts that capture your own tenancy, policy and billing rules.

Check your understanding

Which belongs in the AI gateway?

Infrastructure jobs shared by every service belong in the gateway. Application logic belongs in the applications — otherwise the platform becomes everyone's bottleneck.

Your semantic cache returns a stored answer to a different customer. What went wrong?

Serving one tenant's cached answer to another is a data breach. Put the tenant in every cache key, and add an automated test that checks it never happens.

One team's nightly batch job pushes interactive p95 latency over the SLO. What's the fix?

Live (interactive) traffic and batch traffic should never compete as equals. Separate weighted queues, or separate machine pools, build the rule into the system instead of relying on people to be polite.

Why require an eval set before granting production access?

Teams without evals ship based on a few examples they tried, and can't safely change anything afterwards. Requiring an eval set up front does more than any review meeting.

What is the risk of an untested fallback chain?

Test fallbacks on purpose (practice drills, forced failures) and alert on the fallback rate. A fallback that silently becomes permanent lowers quality without ever raising an error.
