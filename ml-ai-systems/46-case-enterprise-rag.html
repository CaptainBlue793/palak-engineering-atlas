Case Study: Enterprise RAG Assistant

A company has ten million documents spread across SharePoint, Confluence, Jira, Slack, Drive and a ticket system. It has sixty thousand employees, and each one may be allowed to see a different set of those documents. You're building an assistant that answers questions from them using RAG (retrieval-augmented generation: look up relevant passages first, then have the model answer from them). Every answer must cite its sources. It must never show a document the asker isn't allowed to read. And it must be right often enough that people stop searching by hand.

  • Design the pipeline that pulls documents in, parses them and keeps the index updated bit by bit
  • Apply each user's permissions inside the search, not after it
  • Keep a 10M-document index up to date without rebuilding it
  • Back every answer with citations, and decline to answer when the evidence is thin
  • Evaluate a system where the "right answer" often only exists in people's heads

1 · Requirements

Separate content freshness from access correctness. An older but still-authorized document may be acceptable within a 15-minute content target. A revoked permission needs its own enforcement policy. A two-minute mirror target alone cannot guarantee immediate revocation: use authoritative checks where required, and stop serving affected sources when permission freshness cannot be established.

Out of scope: training a base model (Chapter 52), the chat serving fleet itself (Chapter 45), records-management policy. A "chunk" is a small passage of a document (a section or a few paragraphs); search works on chunks, not whole documents.

🎯
Metrics

Primary: task deflection — questions answered without anyone opening a ticket or interrupting a colleague. You measure it with a follow-up question to the user and by watching ticket volume in the topics the assistant covers.

Quality: answer correctness and citation faithfulness (does the cited source really say that?) on a graded set; retrieval recall@20 (how often the right chunk is in the top 20 results) on labelled queries; abstention rate (how often it declines to answer).

Guardrails: zero permission leaks — a hard gate, not a number you trade against others — plus p95 latency, how out of date the index is, and cost per query.

🚫
The one requirement that is not a trade-off

Under pressure, every other number here can be negotiated: latency, freshness, cost, even accuracy. Permission correctness cannot.

One snippet from an unreleased earnings memo, a performance review or a document under legal hold is an incident that ends the project. And unlike a wrong answer, users can't spot it, so it can go on for months unnoticed. Design the search path so that a leak would need a bug in one place. Don't build it so that safety depends on five separate layers all working.

2 · Ingestion and indexing

Give every chunk a document ID, content version and parser version. When a revised document shrinks from 18 chunks to 12, upserting the 12 new chunks is not enough: remove the six obsolete ones too. Publish a completed version together so retrieval does not combine passages from two revisions. Ignore late events for older versions, and retain deletion markers long enough to stop a replay from resurrecting deleted content.

From a SharePoint edit to a retrievable chunkStep-through
  1. Each system gets its own proper connector that uses that system's change API — SharePoint webhooks, Confluence events, Drive push notifications. A slow reconciliation poll (a periodic "did I miss anything?" check) runs behind it to catch events the webhooks drop. A generic crawler would re-read all 10M documents just to find the 40,000 that changed today.
  2. Every change event goes onto a durable queue (one that survives crashes), keyed by document id. Bursts — a bulk migration, a mass permission change — are absorbed instead of lost. Remove duplicates by id and version: a document saved eight times in a minute should be indexed once.
  3. This is the unglamorous 60% of the work: PDFs with tables, scans that need OCR (reading text from images), 400-slide decks, spreadsheets, wiki macros. Split documents into chunks along their structure — headings and sections — not every N characters. Copy the document title and heading path into every chunk's text, so each chunk makes sense on its own.
  4. A document that fails to parse can't be found by search. From the outside, it looks exactly like a document that doesn't exist. So failures go to a dead-letter queue (a holding area for items that failed), with a dashboard and a named owner. When the assistant says "I have no answer", the cause is far more often a parse failure than a search failure.
  5. An embedding is a list of numbers that captures a chunk's meaning, so similar text gets similar numbers. Hash each chunk's text first: an edit to page 3 of a 90-page document changes two chunks, so only two need new embeddings, not ninety. Embedding runs in batches on GPU. Every vector is stamped with the model version, so a later model upgrade can happen chunk by chunk (Chapter 20).
  6. ACLs (access control lists: who may read what) change far more often than content. When someone re-shares a file, it must take effect within minutes, without re-embedding anything. So permissions get their own feed into their own store, and are combined with search results at query time — see the next section.
  7. Each chunk is inserted or updated (upserted) by chunk id into two indexes: a vector index and a keyword index. Both share the same document details: id, source, URL, title, timestamps, ACL tokens, sensitivity label. You need both. Vector (dense) search finds text that means the same thing in different words. BM25 keyword search finds exact strings like an error code, a project codename or a person's surname (Chapter 21).

3 · Deep dive: permission-aware retrieval

Suppose access and ranking are independent and a user can read 2% of documents. An unfiltered top 20 then contains only 20 × 0.02 = 0.4 readable chunks on average. Fetching 1,000 gets about 20 on average, with no guarantee. Real relevance and permissions are correlated, so measure recall for narrow-access users directly. The simulator's fixed percentages illustrate the alternatives; they are not measured guarantees.

Apply the same tenant and permission boundary to keyword search, vector search, reranking, answer caches and debug views. A secure search result is not enough if an answer cache returns another user's response. Include the authorization scope and permission version in cache keys, or reauthorize every cited source before reuse. Resolve groups on the server from authenticated identity, not from a list supplied by the browser.

A query needs the top 20 chunks that this user is allowed to read. Where in the pipeline you apply that rule decides whether the system is correct, fast, or both.

🧾
ACL tokens: the shape that actually scales

On each chunk, store a small set of labels that grant read access — grp:eng-platform, grp:all-staff, usr:1042 — plus a deny set for the rare case where someone is explicitly excluded. Think of them as the names on a guest list.

When a query comes in, look up the asker's group memberships (cached, so it takes a few milliseconds) and turn them into the same kind of labels. Then pass the rule allow ∩ user ≠ ∅ AND deny ∩ user = ∅ into the index as a pre-filter. In words: at least one of the user's labels is on the allow list, and none is on the deny list. The index applies this while it searches, so the top 20 it returns are already 20 chunks the user can read.

Two details make or break it. Group expansion must be transitive: if you're in group A, and group A is inside group B, you're in B too. Nested groups are where leaks hide. And the mirror must be up to date: the delay before a removed permission takes effect is the window in which a former team member still gets answers. Drive the mirror from the change feed, and alert on mirror lag, not only on indexing lag.

4 · Deep dive: freshness without rebuilds

Revocation and deletion need to invalidate cached answers and snippets as well as index entries. A tombstone, meaning a stored deletion marker, is useful if every read path excludes it immediately; physical removal can follow in the background. Track deletion progress across both indexes and backups under the retention policy. Replay a deletion event in tests to verify that it is safe to process twice.

The imbalance drives the design. Permission changes outnumber content changes about four to one, and they must land eight times faster. That is exactly why ACLs are not baked into the embedded chunk.

🕰️
Stale beats wrong, and conflicting versions beat both

The most common complaint in enterprise RAG isn't hallucination (the model making things up). It's the assistant confidently citing the 2019 policy when a 2024 one exists. Both are in the corpus (the full document collection), and the old one just happens to be better written.

Fixes, from most to least effective:

  • Index last_modified and give newer documents a ranking boost for policy-like sources.
  • Spot near-duplicate chunks across versions and keep only the newest.
  • Pass "archived" status through, so an archived space drops out of search entirely instead of just ranking lower.
  • Show dates in the citation, so the reader can see how old their source is.

Search-quality work that ignores document versions stops improving early.

5 · Grounding, citations and abstention

A citation must pass two different checks: the source exists and is readable, and the source supports the claim. A valid URL proves neither support nor current authorization. For a statement combining two documents, retain both citations and their versions. If documents conflict, explain the conflict or abstain; a recently edited draft does not automatically supersede an older approved policy.

RetrieveHybrid search with the ACL pre-filter returns about 60 candidates. A cross-encoder reranker (a slower, more careful model that scores each query–chunk pair) cuts them to the top 8. The reranker gives most of the quality, and it is the second-biggest source of delay (Chapter 21).
AssembleChunks are clearly marked off as untrusted data, each with its source id, title, URL and date. They are never pasted into the instruction text. Any document in the corpus could carry prompt injection (hidden instructions aimed at the model), and some of yours were written by outside vendors (Chapter 36).
GenerateThe model answers with a citation for each claim, using only the chunks it was given. Structured output means a program can check the citations, so they aren't just decoration.
VerifyA cheap entailment check asks: does each cited chunk really support the sentence it's attached to? Unsupported sentences are dropped, or the answer is downgraded to "here is what I found".
AbstainIf all the reranker scores are low, say so and show the closest documents. A confident wrong answer about a security policy costs more than admitting you don't know. Tune the abstention rate to the right level; don't just push it as low as possible.

6 · Evaluation

Store each test query with a test identity, expected accessible evidence and source version. The same question may have a valid answer for a manager and no permitted answer for another employee. Include removal from nested groups, deleted documents, stale answer caches and interrupted permission feeds. Run these checks through the complete answer path, not only the search function.

Before fixing any failure, first work out whether search or the answer-writing step caused it. If the right chunk wasn't in the top 20, no amount of prompt work will fix the answer. Teams often spend months tweaking prompts to fix what is really a chunking or parsing problem (Chapter 35).

7 · Capacity and cost

Vector bytes are 180 million chunks × 768 dimensions × 1 byte = 138.24 GB in decimal units. The listed 90 GB search graph brings that to about 228 GB before metadata, source text, replicas and spare capacity. A second full copy doubles this subtotal. A model migration may temporarily require both old and new indexes as well.

400,000 queries/day averages about 4.63 queries/second. At the illustrative £0.004 per query, that is £1,600/day. Size the fleet for peak traffic and the answer deadline rather than that average. The estimate of 1.5 million changed chunks/day also needs its own workload assumption: 40,000 edits × the corpus average of 18 chunks gives 720,000 chunks before deduplication. Larger edited documents, new arrivals or reprocessing must explain the difference.

8 · What breaks

Give connectors separate lag and coverage indicators. No events from a quiet source may be normal; an overdue reconciliation pass is not. If the embedding service fails, queue content updates without delaying permission revocations. If permission checks fail, suppress those results rather than using their last known allow state. This keeps one dependency failure from turning stale data into unauthorized disclosure.

🎤
Interview drill

Follow-up: “A user says the assistant can't find a document they can clearly see in SharePoint.” Walk me through it.

How a strong answer sounds
I'd take the document id and narrow down, stage by stage, where it gets lost. First: is it in the index at all? If not, did the change feed ever see it (connector health, webhook delivery, reconciliation delay), or did it fail parsing and land in the dead-letter queue? That explains most reports, and it's an ingestion bug, not a search bug. If it is indexed, does the query find it for a user with full access? If it does for them but not for the person reporting it, the problem is permissions. Compare the ACL tokens on the chunk with the user's resolved groups. Usually it's a nested group that wasn't expanded, or an out-of-date mirror. If it's found for nobody, it's a real search-quality problem: an exact-word match the vector search misses, a chunk that lost its heading context, or a reranker pushing it down. I'd want a debug view per document showing exactly these stages. This question comes up every week, and answering it shouldn't need an engineer.

Follow-up: “Why not just build one index per user?”

How a strong answer sounds
It's the most obviously correct design, but it doesn't survive the numbers. There are sixty thousand users, and most documents are readable by thousands of people. So you'd copy storage and index-building cost tens of times over. Every permission change would also mean re-indexing for each affected user — at 150k permission changes a day, that becomes the main workload. It also wastes memory: one shared search graph in RAM becomes sixty thousand small ones. I'd use it only for truly isolated areas — legal hold, a regulated subsidiary — where isolation is the requirement and the document set is small. For everyone else, ACL tokens filtered inside the index are just as correct at a fraction of the cost. That holds as long as group expansion is transitive and mirror lag is monitored.

🧠 Key takeaways

  • Apply permissions inside the index search itself. Filtering afterwards quietly ruins recall and leaves enforcement in application code.
  • ACLs change far more often than content, so keep them in a separate mirror and never re-embed to apply them.
  • Parsing and connector coverage — not model quality — decide how much of the corpus the assistant can answer from at all.
  • Document versions matter as much as search. The classic enterprise failure is confidently citing an outdated policy.
  • Evaluate search and answer-writing separately. Treat zero permission leaks as a pass/fail gate, not a metric.

Check your understanding

Why is filtering search results by permission after retrieval a poor design?

If a user can read 2% of the corpus, an unfiltered top 20 contains roughly zero chunks they can read. You'd have to fetch far more results, or — better — apply the rule inside the index search.

Why are ACLs kept out of the embedded chunk and mirrored separately?

There are 150k permission changes a day against 40k content edits, and permissions must update faster. Tying them together would turn every re-share into an embedding job.

Users report the assistant “doesn't know about” a whole class of internal documents. Most likely cause?

From the outside, missing documents look exactly like bad answers. A document that failed to parse looks the same as one that doesn't exist. That's why the dead-letter queue needs a dashboard and an owner.

The assistant confidently cites a 2019 policy that was superseded in 2024. What fixes this most directly?

Both documents really are in the corpus, and both match the query. It looks like a search problem, but it's really about keeping the document collection tidy.

Why must retrieved documents be fenced as untrusted data?

Any wiki page, ticket comment or attached PDF was written by someone, and could contain instructions. Treat it as data. Never let it authorise a tool call or override policy.
