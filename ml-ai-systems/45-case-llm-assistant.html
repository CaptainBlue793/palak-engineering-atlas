Case Study: LLM Chat Assistant

You need to run a chat assistant for 10 million people a day. Answers stream in word by word. Each conversation gets longer with every message. The assistant can call tools, its output is checked for safety, and several model sizes are on offer. On top of all that, each conversation has to cost less than the product earns from it.

  • Design the path a message takes, from the front door (the gateway) to the stream of words coming back
  • Keep the cost of ever-growing conversations under control
  • Use prefix caching and smart routing to cut spending several times over
  • Build safety checks that don't make the assistant useless
  • Measure answer quality all the time, on live traffic
📚
What you need before this chapter
  • Understand attention and the KV cache.
  • Separate prefill, decoding and scheduling.
  • Treat tools and retrieved content as security boundaries.
  • Apply tenant quotas and routing policies.

1 · Requirements

If an answer has 350 tokens and streams at 25 tokens/second, decoding lasts about 14 seconds. At that average arrival rate, roughly 19,400 answers would be decoding at once, before tool waits. The 180,000-stream peak therefore represents a much busier interval or longer-lived streams; size for the measured traffic shape.

🎯
Metrics

Primary: how many users come back each week, and how many conversations each user has. Good quality shows up as people returning.

Quality proxies (indirect signs of quality): scores from an automated judge on a sample of live chats, thumbs-down rate, how often users hit "regenerate", and how often they abandon a conversation.

Guardrails (numbers that must not get worse): p95 TTFT, tokens per second, refusal rate and false-refusal rate (refusing harmless requests), safety-violation rate, and cost per conversation.

Baseline for any change: the current production setup. You compare the new version against it side by side (Chapter 35).

2 · The request path

Give each user message a stable request ID. When the connection drops, the client should ask about that request before starting another generation. The server can distinguish an unfinished response, a completed response whose delivery failed, and a genuinely new attempt. Tool actions need their own deduplication keys because retrying generation must not repeat a purchase or send a message twice.

One message, end to endStep-through
  1. The app opens a long-lived HTTP connection and receives the answer through server-sent events (SSE: the server pushes small pieces down the open connection as they are ready). The app sends only the new message and a conversation id — not the whole history, because the server already has it. The server must notice if the user disconnects, so it can stop work and free the slot (Chapter 26).
  2. The gateway checks who you are, which customer (tenant) and plan you belong to, and whether you are within your rate limit and token quota. It picks the model tier and attaches a trace id for logging. It must stay thin and fast, because every single message passes through it (Chapter 39).
  3. The context builder assembles everything the model will read, in this order: the fixed system prompt and tool descriptions, then long-term memory, then any retrieved documents, then the conversation so far, then the new message. The parts that never change go first so they can be cached. The order is chosen for caching, not for readability.
  4. A fast classifier (a small model that labels text as fine or not) checks the user's message. Retrieved content is clearly marked as untrusted data, not instructions. This check runs at the same time as the cache is being loaded, so it adds almost no waiting time (Chapter 36).
  5. The model keeps a KV cache: its saved working memory for text it has already read. The scheduler finds the saved cache for the start of this conversation (the "prefix"). It then prefills (reads in) only the new tokens and joins the continuous batch of requests sharing the GPU. On turn twenty, that means reading 400 tokens instead of 40,000.
  6. The model outputs a structured request to use a tool. The gateway checks it against the user's permissions. The tool runs in a sandbox (an isolated space) with a time limit. The result goes back to the model, marked as untrusted data. The conversation carries on in the same stream (Chapter 22).
  7. Tokens stream to the user as soon as they are produced. They pass through an output filter that holds back a small window of text first. That way, a policy violation can be stopped mid-answer, before the user reads it.
  8. The first token usually arrives within 600 ms. Everything is recorded: prompt version, model version, cache hit, token counts, latency, tool calls and user feedback. A sample of conversations is graded automatically, and a smaller sample is reviewed by people each week (Chapter 35).

3 · Deep dive: the cost of a long conversation

With 700 tokens added per turn, the simplified uncached model reads 700 × (1 + 2 + … + 30). The sum is 30 × 31 ÷ 2 = 465, giving 325,500 processed input tokens. Perfect prefix reuse reduces new prefill to 700 × 30 = 21,000 tokens. That is a 15.5-fold reduction in this part of the work, not in the total bill: output generation, cache storage and history attention still cost resources.

The simulation assumes every cached prefix survives and ignores cache-transfer time, summary-writing cost and length-dependent attention work. Real caches can be evicted or invalidated by a prompt change. A rolling summary can also lose an exact name or commitment. Preserve important structured facts separately, retain the source conversation under its retention policy, and test questions that refer back many turns.

The model has no memory between messages. So every turn sends the whole conversation history again. If you do nothing about it, cost grows quadratically (with the square of the number of turns). Turn 30 pays again for all 29 turns before it.

Think of a friend who, each time you add a sentence, re-reads the entire letter from the top. A short note is fine. A long letter gets slower and slower.

Conversation-aware routing is what makes prefix caching work

The saved KV cache for a conversation lives on one specific replica (one copy of the model on one set of GPUs). If the next turn goes to a different replica, the cache is missing there, and you prefill 40,000 tokens again.

So the router uses sticky, conversation-affine routing: the same conversation always goes to the same replica. It does this by hashing the conversation id to pick a replica, with a fallback if that replica is overloaded or dies.

This makes cache hit rate a key serving metric. A drop from 85% to 40% roughly doubles prefill cost and makes TTFT visibly worse. The cause is usually a deployment or a routing change, not anything about the model.

4 · Deep dive: model tiers and routing

Measure the routing policy on complete tasks, including escalations. A cheap first attempt followed by a large-model retry may cost more and take longer than choosing the large model initially. Compare success rate, total tokens and elapsed time by route. Use the model tier and prompt version in cache keys so a cache entry from a different configuration is never treated as interchangeable.

How the router picks a tier: the user's own choice, a cheap classifier that guesses how hard the message is, the state of the conversation (has it already moved up to a bigger model?), the customer's plan, and current load. Every routing decision is logged, so you can check whether the router itself is doing a good job. Sending a hard question to a model that is too small hurts quality, and no metric about the model itself will show it.

5 · Deep dive: safety without ruining the product

A streaming filter cannot retract text already delivered. Holding 10 tokens at 25 tokens/second adds about 400 ms of buffering if those tokens must accumulate first. Choose buffering based on the content risk and include it in the visible first-token target. For outputs that need whole-answer validation, complete the check before releasing the answer. Independently enforce tool permissions in code.

InputA fast classifier checks the user's message. Retrieved and tool content is handled separately and marked as data, not instructions. Time budget: under 30 ms, run at the same time as cache loading.
SystemRules written in the system prompt set default behaviour, but they don't guarantee it. This is the cheapest layer and also the weakest (Chapter 36).
OutputA streaming filter holds back a small buffer of upcoming text, so a violation is caught before the user reads it. It must not add a noticeable delay to the first token.
ActionAnything with a real-world effect — sending, buying, deleting — is checked in code against the user's real permissions. The model saying "this is fine" is never enough.
FeedbackA red-team suite (a set of deliberate attack prompts) runs in CI. People review a sample of refusals and near-misses. You also measure the false-refusal rate, so safety work doesn't quietly make the product useless.
🙅
Over-refusal is a product failure with no error code

Test every safety change on two sets of prompts. The first is a harmful set: does the change block these? The second is a benign near-miss set: harmless requests that only look risky, such as security questions, medical questions and fiction.

Teams that only measure the first set end up with an assistant that refuses to explain how to kill a Linux process. Treat the false-refusal rate as a guardrail, and take it as seriously as the violation rate.

6 · Capacity and cost

The output estimate is 120 million × 350 = 42 billion tokens/day, or about 486,000 tokens/second on average. At the stated peak, 180,000 active decoders × 25 tokens/second = 4.5 million output tokens/second. Dividing by 2,200 decode GPUs implies about 2,045 tokens/second per GPU across batched requests. Treat that as a throughput requirement to benchmark across the model mix, not a hardware fact.

Similarly, 90 TB ÷ 180,000 streams is about 500 MB of KV memory per stream on average. A 200,000-token context can be much larger, so admission must account for tokens and memory, not just stream count. The table's cost and fleet sizes are scenario assumptions. Disaggregating prefill from decode

Answering a message has two phases. Prefill reads the whole prompt at once; it is limited by raw compute and comes in bursts. Decode writes the answer one token at a time; it is limited by memory speed and runs steadily.

If both run on the same replicas, one 100k-token prompt can freeze everyone else's token stream. So you split them: prefill on one pool of GPUs, decode on another, and the KV cache is sent from one to the other. Each pool can then be sized, batched and scaled for its own job.

The price is sending the cache over the network. That is worth it above a certain scale. Below it, it's over-engineering.

7 · What breaks

Separate queue wait, prefill, tool time, decode gaps and output-filter delay in traces. Otherwise the same symptom, a slow first word, can lead you to scale the wrong component. During overload, reject excess work early or offer a smaller tier within the user's plan. Bound retries and propagate cancellation all the way to the GPU scheduler and tools.

Interview drill

Follow-up: “Cost per conversation doubled last week with flat traffic.” Where do you look?

How a strong answer sounds
Cost per conversation is tokens × price, so I'd break it into parts and check each one. (1) Input tokens per message: did a prompt change, a memory feature or a retrieval change add more context? (2) Prefix cache hit rate: editing the system prompt or changing routing makes every cached prefix useless, which silently doubles prefill. This is the most common cause. (3) Output length: a new model or prompt can make answers longer. (4) Routing mix: are requests that used to go to the small tier now moving up to bigger ones? (5) Conversation length: did a product change make sessions longer? You can see all five in the traces, as long as the gateway logs token counts, cache hits and the routing decision for each request. That is exactly why it should.

Follow-up: “How do you know quality hasn't regressed?”

How a strong answer sounds
Before release, there are offline checks. A golden set of real conversations is graded side by side against the current production setup. There are also tests for specific skills and a safety suite (Chapter 35). In production, checking never stops. A fraction of live conversations is graded automatically against a rubric. Each week, people review a smaller sample, which also checks that the automated judge agrees with humans. I'd also watch indirect signals — regeneration rate, thumbs-down, abandoned conversations, escalations to support — broken down by model tier and route. Any change then ships through shadow mode (runs alongside, results not shown) and a canary (a small share of real users), with those signals as guardrails. The offline number decides whether we try a change. The production signals decide whether it stays.

🧠 Key takeaways

  • A conversation's cost grows with the square of its length, unless you cache prefixes and manage the history.
  • Prefix caching only works if each conversation keeps going to the same replica. Track cache hit rate as a serving metric.
  • Routing to the right model size, plus caching, decides whether each conversation makes or loses money.
  • Safety comes in layers. The false-refusal rate matters as much as the violation rate.
  • Quality needs constant grading of sampled live traffic. Infrastructure metrics can't see it.

Check your understanding

Why does a chat conversation's cost grow faster than linearly with turns?

Turn n re-reads roughly n turns of history. Add that up over a whole conversation and you get O(n²). That's why prefix caching is the most valuable optimisation here.

Why must routing be conversation-affine?

The cache only helps if the request reaches the machine that holds it. Sticky routing, with a fallback for overload, keeps the hit rate high. Round-robin (taking turns across replicas) destroys it.

Why separate prefill and decode onto different pools at large scale?

Prefill is limited by compute and comes in bursts. Decode is limited by memory and runs steadily. Splitting them lets you size and batch each pool for its own job. The price is sending the KV cache between pools.

Your safety change reduced violations by 40%. What else must you measure before shipping?

Blocking more is easy. The hidden cost is refusing legitimate requests. That produces no error code, and it quietly drives users away.

TTFT rose from 600 ms to 2.4 s with unchanged traffic and no errors. First hypothesis?

A cache miss means re-reading the whole conversation. You see slower responses and higher cost while every system metric looks healthy. That's why hit rate needs its own alert.
