What Is an ML System?

Before any maths, let's see the big picture. A machine learning system is much more than a model. It is a whole pipeline: collect data, train, check the results, serve predictions and keep watching them. The model sits in the middle, and it is usually the smallest part.

Rules, or learning?

Ordinary software is rules you write. For example: if the cart total is over £50, shipping is free. Machine learning is rules the machine works out from examples. You say: here are 200,000 emails, each marked spam or not spam — figure out the rule yourself.

Why would hand-written rules struggle with spam? Take the rule "block any email containing free". It catches "FREE prize inside", but it also blocks your friend's "are you free for lunch?". Then spammers notice and start writing "fr3e" instead, so the rule misses them too. Each fix needs another rule, and the rules start to clash. A learned model weighs hundreds of small clues at once (the sender, the links, the wording, the time sent) and can be retrained on new examples when spammers change tactics.

This swap is only worth it when the rule is too complicated, too fuzzy or changes too fast for a person to write down. Try it below. Add hand-written rules to a spam filter and see how quickly they stop working on new emails (in ML terms, they stop generalising).

The honest test for “should this be ML?”

Use ML when all four are true: (1) a pattern exists but nobody can write it down, (2) you have (or can get) examples with the right answer attached, (3) the pattern changes over time, so hand-written rules would go stale, and (4) an occasional wrong answer is acceptable. If any one is missing, plain rules are cheaper, faster and far easier to debug.

The three ingredients

Every supervised ML system (one that learns from examples with known answers) is built from exactly three things. That's true for a 10-line logistic regression and for a language model with a trillion parameters.

🧱

Data

Examples of the thing you want to predict, each with the right answer attached. Those answers are called labels. Most of your effort will go here.

🧠

Model

A function with adjustable numbers, called parameters. It must be flexible enough to capture the pattern you're after.

🎯

Objective

A loss function that scores how wrong a prediction is. An optimizer then nudges the parameters to make that score smaller.

All three in one tiny example. Say you want to predict a flat's price from its size. The data is past sales: an 80 m² flat sold for £120,000. The model is price = w × size, with one parameter w (pounds per square metre). Start with a guess, w = 1,000: the model predicts £80,000, which is £40,000 too low. The objective scores that miss, for example by squaring it, so bigger misses count for much more. The optimizer sees the prediction was too low and nudges w upwards. Repeat over thousands of sales and w settles near the value that makes the total error smallest. If flats in your data typically sell for about £1,500 per m², that is roughly where it ends up. Real models have millions of ws instead of one, but the loop is the same.

🎸
Analogy: learning guitar by ear

The data is the recording you're copying. The model is your hands, with thousands of possible finger positions. The loss is how wrong the note sounds. Practising is gradient descent: play, hear the error, move your fingers slightly towards what sounds better. Nobody hands you the rule “index finger on fret 3”. You work it out from feedback — and that is exactly what training is.

Four flavours of learning

🏷️

Supervised

Learn from labelled pairs (input x → answer y). Spam or not spam, price prediction, will this user click. The workhorse of real-world ML.
🧩

Self-supervised

The labels come free from the data itself. “Predict the next word (token)”, “fill in the hidden patch of the image”. This is how every large language model is first trained (pretrained).
🔍

Unsupervised

click to flip
No labels at all — just find structure. Grouping similar users (clustering), spotting odd events (anomaly detection), squeezing many columns into a few (dimensionality reduction). Hard to evaluate, so it's usually one part of a system, not the product.
🎮

Reinforcement

Learn from rewards, not answers. An agent takes actions and the world scores them. Used in game-playing, robotics and the RLHF step that makes chat models helpful (Chapter 18).

The lifecycle: where the work actually goes

People picture ML as “train a model”. In a real product (“in production”) it's a loop that never stops. Training the model is just one box out of eight. Step through it:

The ML lifecycleStep-through
  1. Turn a business goal into a prediction task and a way to score it (a metric). “Reduce churn” (customers leaving) becomes “predict the chance a user cancels in the next 30 days”. You measure it offline with PR-AUC (a score for how well it ranks likely leavers) and online with retained revenue. Get this wrong and every later step is wasted.
  2. Find or build a dataset with labels. Decide how far back in time it can be trusted. Then split it into train, validation and test sets before you look at it. Chapter 3 is all about the ways this goes wrong.
  3. Turn raw rows, text, images or events into numbers a model can use. That means encoding categories, scaling values, summarising over time windows, or turning things into embeddings (lists of numbers that capture meaning). Deep models learn most of this themselves — but not the part that reads data from your live systems.
  4. Fit the parameters by making the loss as small as possible. Then tune the settings you choose yourself (learning rate, tree depth, regularization). Your first model should take hours, not weeks — you just want a baseline to beat.
  5. Score it on held-out data (data it never saw in training). Use a metric that matches the decision the model drives. Also check slices: new users, each country, each device. A good average can hide one broken group — and that's how broken models get shipped.
  6. Release it gradually behind a switch (a feature flag). First run it on copied traffic without acting on it (shadow), then on a small slice of real users (canary), then in a proper A/B test. The offline metric only predicts the online one. Chapter 33 is about the gap between them.
  7. Answer live requests fast enough (within a latency budget) and cheaply enough per prediction. Have a fallback for when the model is down. This is a systems problem, and it's most of Level 3.
  8. Watch the inputs for drift (data slowly changing from what you trained on). Watch the outputs for quality. Collect the true answers as they arrive. When behaviour shifts — and it will — gather new data and go round again. An ML system is never “done”.

The model is the small box

A famous Google paper from 2015, Hidden Technical Debt in Machine Learning Systems, made this point with one picture. In a real system, the model code is only a thin slice of the whole thing.

Every box except the highlighted one is ordinary systems engineering — hard work, but not ML. That is why this is a systems course.

Why is configuration called "the silent killer"? A real model has dozens of settings outside its code: which features are switched on, which data table to read, the score above which a payment is declined. Change the decline threshold from 0.8 to 0.08 by mistake and the code still runs perfectly, with no crash and no failing test, while the model now blocks one customer in five. Settings like these need the same review, versioning and testing as code.

Here is a concrete picture of the proportions. A fraud model might be a few hundred lines of training code. Around it sit the jobs that pull transactions every hour, the checks that reject malformed rows, the service that computes "number of purchases in the last 10 minutes" live, the dashboards that watch for drift, and the release pipeline. Each of those can break the product on its own, even if the model itself is perfect.

The feedback loop, concretely

A feed model ranks cat videos slightly higher. Users watch more cat videos. The next training set is full of cat-video views. So the model ranks them even higher. Three months later the product is a cat-video app, and nobody decided that. Every recommender has this problem. Chapter 30 covers how to keep trying new things (exploring).

Offline metrics vs. the thing you care about

Models are trained on a proxy — a stand-in score that's easy to compute. The product is judged on something else. Your core job as an ML engineer is to keep the two connected, and to be honest about the gap between them.

📏 Model metric

AUC, F1, perplexity, BLEU, recall@10. You can compute these offline, in seconds, on a fixed dataset. Great for trying ideas quickly — but push one too hard and it stops meaning what you think.

💷 Product metric

Retention, revenue, fraud losses, support tickets avoided, time saved. Measured live over days or weeks with an experiment. The thing you actually promised — and always noisier than you'd like.

What "push one too hard" looks like. A news app trains its ranking model to maximise clicks, because clicks are easy to count. At first, better click prediction also means happier readers. Then the model discovers that shocking headlines get clicked but disappoint, and it starts showing more of them. Clicks go up; the share of people who come back next week goes down. The proxy stopped tracking the goal once the model optimised it hard enough. This is why you watch the product metric too, and why many teams add a guard-rail metric (such as "reports of misleading content") that must not get worse.

🎤
Interview tip

When asked to design an ML system, name both metrics in the first two minutes. For example: “Offline I'll track PR-AUC on held-out fraud cases. Online, the metric that matters is chargeback loss per £1,000 processed, with a guard-rail on how often we wrongly decline good payments.” That one sentence shows you've shipped models, not just trained them.

A framework for any ML design problem

Every case study in this course follows these steps, in this order. Use the same order in an interview or a design doc.

1. Clarify the task and the metric ~5 min

What decision does the prediction drive? Who acts on it? Name the offline metric, the online metric, and the limit that must not get worse.

2. Data and labels ~7 min

Where do examples come from? How are labels created, and how late do they arrive? How much data is there? How will you split it?

3. Features and representation ~5 min

What information is available at the moment you predict — and only then? Categories, sequences, text, embeddings.

4. Model choice and baseline ~5 min

Start with the simplest thing that could work: a hand-made rule, then GBDT (gradient-boosted trees), then deep learning. Say clearly what you're comparing against.

5. Training and evaluation plan ~8 min

Compute budget, how often you retrain, how you validate, metrics per slice, and how you'll catch leakage (answers sneaking into the inputs).

6. Serving design ~10 min

Live (online) or in bulk ahead of time (batch)? Latency budget, hardware, caching, fallbacks, and the path a request takes.

7. Monitoring, rollout and iteration ~7 min

Shadow → canary → A/B, drift alarms, collecting feedback, and the retraining loop that keeps the model useful.

The framework on one example: card-fraud detection. Here is roughly what each step sounds like in one or two sentences.

  1. Task and metric: score each card payment for fraud risk before approving it. Offline, measure recall at a fixed false-alarm rate; online, fraud losses per £1,000 processed, without raising the rate of good payments declined.
  2. Data and labels: past payments, labelled "fraud" when the cardholder reports it. Those reports can take weeks to arrive, so the most recent data is not yet fully labelled.
  3. Features: amount, merchant type, distance from the card's usual location, payments in the last hour. Only things known at the moment of payment.
  4. Baseline and model: the rules the fraud team already uses, then gradient-boosted trees.
  5. Training and evaluation: train on older months, test on the most recent fully labelled month, and check new cards and each country separately.
  6. Serving: the score must come back within the payment's time budget, so features are precomputed or cached; if the model is down, fall back to the old rules.
  7. Monitoring: watch the score distribution daily, since fraudsters change tactics, and retrain on a regular schedule.

You do not need the details yet. Each later chapter fills in one of these steps.

⚠️
Common mistakes
  • Reaching for ML when three rules would do. A learned model costs you a pipeline, a training job, a serving setup and monitoring — forever. If a simple threshold solves 90% of the problem, ship the threshold and collect data.
  • Optimising a metric nobody asked for. If 99% of your data is “no”, a model that always says “no” scores 99% accuracy — and is useless. Choose the metric from the decision, not from the tutorial.
  • Treating deployment as the finish line. The day a model ships is the day its data starts drifting. Plan for monitoring and retraining from the start, not as a follow-up ticket.
  • Ignoring the no-model baseline. “Most popular item”, “yesterday's value”, “the rule the ops team already uses”. If you can't beat those, you've learned something valuable — and cheaply.

Interview drill

Warm-up: A product manager says “let's add AI to the checkout page.” What do you ask before agreeing?

How a strong answer sounds
What decision should change, and which metric would move if it worked? Do we have logged examples of that decision with their outcomes, and how long until outcomes are known? What does a wrong prediction cost in each direction? How much delay can checkout tolerate? And what is the simplest non-ML baseline? If a plain rule gets most of the value, ML is a phase-two investment, not phase one.

Explain it simply: Why is an ML system harder to maintain than a normal service with the same traffic?

How a strong answer sounds
Because its behaviour depends on data, and data changes without anyone deploying anything. Ordinary services fail loudly and in repeatable ways. ML systems get quietly worse as the world drifts away from the data they were trained on. The first sign is often a business metric dropping, not an error rate rising. So there's much more to maintain: data pipelines, keeping features identical in training and serving, collecting labels, watching for drift, and a way to retrain. A basic CRUD service (create/read/update/delete) needs none of that.

🧠 Key takeaways

  • Use ML when a pattern exists, is hard to write down, changes over time, and occasional errors are acceptable.
  • Every ML system is data + model + objective. The data is where most of the effort — and most of the failures — live.
  • The lifecycle is a loop, not a straight line: frame, data, features, train, evaluate, deploy, serve, monitor.
  • Model code is a thin slice of a real ML system. The rest is data and systems engineering.
  • Always name an offline metric and the product metric it stands in for, plus the baseline you must beat.

Check your understanding

Which problem is the worst fit for machine learning?

VAT is a known, exact rule set by law. Learning it from examples would be slower, more expensive and sometimes wrong — for a rule you can write in one line.

“Predict the next token in this text” is an example of which kind of learning?

The label (the next token) comes free from the raw text itself. No human has to write labels. That is what makes training on internet-sized data possible.

Your churn model scores 0.91 AUC offline but the A/B test shows no change in retention. What is the most likely explanation?

Perfectly predicting who will leave is useless if the discount you send them doesn't change their mind. The offline metric measures the prediction. The product metric measures the decision the prediction leads to.

Which of these is a uniquely “ML” failure mode rather than an ordinary software bug?

Nothing errors and every request returns 200 (success). The only symptom is a quality metric slowly sinking. This kind of silent decline is why ML systems need data and quality monitoring, not just uptime monitoring.

In an ML design interview, what should come first?

Every later choice — model, features, hardware — depends on what you are predicting, how you measure success and what you must beat. Starting with the model is just guessing.
