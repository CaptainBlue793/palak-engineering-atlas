Case Study: Code Assistant

You're building inline code completion (the grey "ghost text" that appears as you type) for 500,000 developers. A request fires on almost every keystroke. The model must see enough of a million-line repository to be useful. It must answer before the developer has finished thinking. And when it's wrong, it must be wrong quietly — a suggestion that arrives late or reads badly is worse than no suggestion at all.

  • Design the path from keystroke to suggestion within a 200 ms budget
  • Use fill-in-the-middle and repository context without going over that budget
  • Cancel, debounce and cache hard — most requests should never reach a GPU
  • Measure whether people accept and keep suggestions, not token-level accuracy
  • Handle the security and licensing problems that come with generating code

In scope: inline completion, repo context, serving, caching, evaluation, safety. Out of scope: pretraining the code model (Chapter 16), the agent mode that edits many files, the IDE extension's UI. p50 is the median: half of requests are faster than this.

Where the numbers come from. 900M requests ÷ 500k developers = 1,800 requests per developer per day. Spread over about six hours of actual typing, that is one request every 12 seconds — believable once you remember a request can fire at every pause. The daily average is 900M ÷ 86,400 seconds ≈ 10,400 requests per second. But developers don't type evenly around the clock: most work happens in a few hours of overlapping time zones on weekdays. A peak of about 4× the average is a common rule of thumb, which gives the ~45k QPS in the box. You size the fleet for the peak, not the average.

🎯
Metrics

Primary: accepted characters retained — code the developer still has in the file some minutes later, not just code they pressed Tab on.

Secondary: acceptance rate, how often a suggestion is shown, weekly active users, and the share of characters typed by the assistant.

Guardrails: p50 and p95 latency, cost per accepted completion, how often suggestions fail to compile or fail the linter, and how often secrets leak.

Deliberately not primary: next-token accuracy. It barely tracks anything a developer cares about.

A tiny example of the difference. Suppose 100 suggestions are shown. 30 are accepted — a 30% acceptance rate. Five minutes later, 12 of those 30 have been deleted or rewritten. If the 30 accepted suggestions totalled 900 characters and the 18 survivors hold 500 of them, retained characters is 500, not 900. A change that raised acceptance to 35% but left only 400 characters standing made the product worse, and only the retained number shows it.

⏱️
Latency is the product

A completion at 80 ms feels like the editor reading your mind. The same completion at 600 ms arrives after you've typed past it. Now it's just noise you have to dismiss.

Experiments on products like this keep showing the same thing: acceptance drops steeply as latency rises, long before users would call it "slow". That changes every design choice. A smaller model that answers in 90 ms beats a better model that answers in 400 ms. Most of the engineering here is about avoiding work, not doing work faster.

2 · The completion path

One keystroke, end to endStep-through
  1. Debounce: wait for a short pause in typing instead of firing on every character. Then cancel the request in flight as soon as the next key is pressed. Without this, you pay for three or four requests per accepted suggestion, and the cancelled ones still take up GPU slots. The single most valuable optimisation here runs entirely in the editor.
  2. The editor gathers the prefix (code before the cursor), the suffix (code after it), the file path and language. It adds snippets from recently edited and open files, plus the symbols (functions, classes) the current file imports. This all happens inside the IDE using a local index. A network round trip to fetch context would use up the whole budget.
  3. Hash the finished prompt and check a cache. Developers retype, undo, move the cursor back and re-trigger all the time. So an exact-match cache answers a surprising share of requests in a few milliseconds. Nearly as useful: cache the model's KV prefix (its saved working memory) for the file, so a second request on the same file skips most of the prefill.
  4. A small, quantized model (numbers stored with fewer bits, so it runs faster) with a few billion parameters. Output has a strict cap: usually one line or one block, not a page. Speculative decoding — a tiny draft model guesses tokens and the main model checks them — roughly doubles speed on code, because code is unusually predictable (Chapter 27).
  5. Cut the suggestion off where it starts repeating the code below the cursor. Stop at the end of the current block. Check that it parses. Drop anything that looks like a password or API key. A broken suggestion wastes more of the developer's attention than no suggestion.
  6. If the developer has typed since the request left, the result is thrown away unseen. Ghost text only appears if it still fits what's on screen. About one in four shown suggestions is accepted. The rest should cost the developer nothing to ignore.
  7. Record whether it was shown, whether it was accepted, and — the number that matters — whether it was still in the file some minutes later. Acceptance alone rewards suggestions that are easy to Tab in and then delete straight away (Chapter 33).

Debouncing, worked through. Say a developer types user.get_ at 8 keystrokes a second: one every 125 ms. A 75 ms debounce expires before the next key, so all 9 keys still send requests. Now consider a short burst with 50 ms between keys. Each key resets that same 75 ms timer before it expires, so the burst sends just one request after the final key. Debouncing only merges keys whose gaps are shorter than the delay. Increasing the delay saves more requests but makes every suggestion wait longer; cancellation and caching must handle the requests that still go out.

Why build context in the editor, not on the server? The obvious design is to send the file to a backend that looks up context in a central index. But the editor already has everything: the open buffers, the unsaved edits, the recent-edit history. A server-side index would lag behind unsaved changes and add a network round trip (often 30–80 ms on its own). Keeping it local makes context both fresher and faster. The trade-off is that the editor extension has to stay light — it must never make typing itself feel sluggish, so indexing runs in the background at low priority.

Edge cases the path must handle.

  • The backend is slow or down. The editor simply shows nothing. There's no error dialog, no spinner — a missing suggestion is the correct failure.
  • The response arrives but the text has changed a little. If the developer typed re and the suggestion starts with return, the editor can still show the remaining turn …. If what they typed contradicts the suggestion, it's thrown away.
  • The cursor is in the middle of a word. Tokenizers split words into chunks, so a prompt ending in pri can push the model toward odd continuations. A common fix is to back the prompt up to the last clean token boundary and require the output to start with the characters that were cut.
  • Files the model shouldn't touch. Generated files, minified bundles, huge data files and files the user or their company has excluded (for example, .env) are skipped before any request is built.

3 · Deep dive: fill-in-the-middle

A normal left-to-right model only sees what's above the cursor. But real editing happens in the middle of a file. There, the code below the cursor is the strongest clue about what belongs in the gap. Fill-in-the-middle (FIM) training reorders documents so the model learns to use both sides.

It's like a fill-in-the-blank exercise: knowing how the sentence ends makes the blank much easier to fill.

<PRE>def parse_config(path: str) -> dict: with open(path) as f: raw = f.read() <SUF> return validated <MID>data = json.loads(raw) validated = ConfigSchema(**data).dict()

Each training document is rearranged into prefix, then suffix, then middle. So when it's used, the model is asked to continue after <MID>, with both sides already in view. The same model still handles plain left-to-right completion when there's no suffix. One model serves both kinds of request.

How the training data is made. Take an ordinary source file. Pick two random cut points, which split it into three pieces: A (before), B (between), C (after). Rewrite the document as <PRE> A <SUF> C <MID> B and train on it with the usual next-token objective. Nothing about the model changes — only the order of the text. Because the model has seen C before it has to write B, it learns to write a middle that joins up with what follows. Usually only a share of documents is rearranged this way, so the model keeps its normal left-to-right skill.

Why not just paste the suffix into the prompt as a comment? You could put "the code below the cursor is: …" above the prefix and hope. But a model trained only left to right has never learned to treat text earlier in the prompt as something its output must connect to afterwards. It tends to ignore it or copy it. FIM teaches that exact skill for the price of reordering the training data.

Edge cases. At the end of a file the suffix is empty, so the request is plain left-to-right completion. When the suffix is very long, you keep only the part nearest the cursor — typically the next few dozen lines — because the end of the file rarely tells you what goes on this line. And the model must know when to stop: training includes an end-of-middle token, so a good FIM model emits it when the gap is filled rather than writing on into code that already exists below.

🧩
Repo context: retrieval with a millisecond budget

Searching the repository by meaning (embedding-based vector search) is the obvious idea, and usually the wrong one here. Even 40 ms of vector search is a third of the budget, and it would run on every keystroke. What works is cheaper and mostly based on matching names and words. The IDE keeps it up to date in the background:

Recently edited files (the strongest single signal — you're usually working on related code), open tabs, the symbols this file imports with their definitions looked up, other files in the same folder, and shared identifier names with the current function. Rank these with a simple score, take a few hundred tokens from each, and stop. Heavier search belongs in chat and agent modes, where 400 ms of search goes unnoticed next to an answer that takes several seconds.

A typical 2,500-token prompt, split up: about 1,200 tokens of prefix, 400 of suffix, four context snippets of about 200 tokens each (800), and around 100 tokens of file path, language tag and separators. When the budget is tight, the prefix near the cursor wins; far-away snippets are the first thing dropped.

Why the bars shrink the way they do. Prefill is compute-bound: the model does about 2 × (parameters) × (prompt tokens) arithmetic operations. For a 3B model and a 2,500-token prompt that's 2 × 3×10⁹ × 2,500 = 1.5×10¹³, or 15 trillion operations. A modern data-centre GPU sustains a few hundred trillion per second in practice, so that's a few tens of milliseconds — in line with the 62 ms bar once you add batching overhead. A 30B model does ten times the arithmetic, which is why its prefill bar is so long even when split across several GPUs. Decode is different: it's limited by memory bandwidth, because each new token requires reading every weight once. A 3B model stored in 4 bits is about 1.5 GB; at roughly 2–3 TB/s that's under a millisecond per token at best, and a few milliseconds in a busy batch. Twenty-five tokens is tens of milliseconds, which is why capping the output is as powerful as shrinking the model.

Why caching gives the biggest cut. Prefill is the largest bar, and prefix caching attacks it directly. If the first 2,000 of 2,500 prompt tokens (the top of the file) are unchanged since the last request, the replica only has to process the last 500 — about a fifth of the work. That only works if the next request for that file lands on the replica that holds its cache, which is why routing is "sticky" per file or per user.

Ship changes through live A/B experiments, with retained characters as the main metric and latency as a guardrail (Chapter 33). Offline test suites decide whether a release can go out. Only live traffic tells you whether a change actually helped.

🔑
Three failure modes that are not about quality

Secrets. Models trained on public code sometimes output strings that look like passwords or API keys. And developers really do paste keys into files. Scan every suggestion with the same secret detectors you run in CI. Never log raw prompts without removing sensitive parts first — the prompt is the customer's source code.

Licensing. If the model copies long, distinctive chunks of its training code word for word, that creates a legal risk no accuracy metric will show. The standard fix is a near-duplicate check against known code collections, plus an option to block long exact matches.

Injection through the repository. In agent and chat modes, the model reads files. A comment in a file can be written by anyone who can open a pull request. Treat repository content as data, and ask the user to confirm before the assistant runs a command or edits anything outside the file on screen (Chapter 36).

Notice this is the reverse of Chapter 45. Here the prompt is long and the output is tiny. So prefill is the main cost, and prefix caching matters more than decode speed. It's the same serving stack, tuned in the opposite direction.

The arithmetic behind the table.

  1. GPU requests at peak: 45k QPS × 35% ≈ 16k requests per second reach the model.
  2. Prompt tokens at peak: 16k × 2,500 = 40M prompt tokens per second. If prefix caching means only about a third of those are new work, that's roughly 13M tokens per second to prefill.
  3. Per GPU: 13M ÷ 600 GPUs ≈ 22k prefill tokens per second each. For a 3B model that's 2 × 3×10⁹ × 22,000 ≈ 1.3×10¹⁴ operations per second — a realistic fraction of what one modern GPU can sustain, with headroom left for decode and spikes.
  4. Daily cost: assume ~£2 per GPU-hour. Even if all 600 GPUs ran all day (autoscaling means they don't), that's 600 × 24 × £2 ≈ £28.8k per day.
  5. Accepted completions per day: if roughly 15% of the 900M requests end with a suggestion on screen, and about a quarter of those are accepted, that's 900M × 0.15 × 0.25 ≈ 34M.
  6. Cost per accepted completion: £28.8k ÷ 34M ≈ £0.00085, or about £0.0009 — under a tenth of a penny.

The useful lesson is which lever moves which line. Better debouncing shrinks step 1. Better caching shrinks step 2. A smaller model shrinks step 3. A better acceptance rate shrinks step 6 without touching the fleet at all.

Interview drill

Follow-up: “You have a model with clearly better offline scores but 250 ms more latency. Ship it?”

How a strong answer sounds
Not for inline completion — and I'd want an experiment to prove it, not just argue from principle. In this kind of product, acceptance is very sensitive to latency. A model whose suggestions are better, but arrive after the developer has typed past them, will usually lose on retained characters. The offline win never reaches the user. What I'd do instead: run it in shadow (alongside, not shown) to confirm the quality gap is real on our traffic. Then try to win the latency back with quantization, speculative decoding, a tighter output cap and better prefix caching. If it still doesn't fit the budget, use it where the budget is different: chat, multi-line completion the user asks for explicitly, and agent mode, where 400 ms goes unnoticed. Two models for two latency needs is a perfectly good answer, and usually the right one.

Follow-up: “Acceptance rate went up 3% after a change. Is that good?”

How a strong answer sounds
It's a hypothesis, not a result. Acceptance can be pushed up in ways that hurt users. Shorter suggestions raise it. Only suggesting where the answer is obvious raises it. And a developer who accepts and then deletes straight away still counts. I'd check retained characters: is the accepted code still there minutes later? I'd also check the shown rate. Acceptance is a ratio (accepted ÷ shown), so it moves if the bottom number changes. Then I'd break it down by language, file size, and single-line versus multi-line suggestions. An overall win often hides a drop in languages that a minority of developers use all day. If retained characters rose along with acceptance, and latency held, I'd believe it and ship.

🧠 Key takeaways

  • For inline completion, latency matters more than anything else. A smaller, fast model usually beats a better, slow one.
  • Most of the win comes from avoiding work. Debouncing, cancelling and caching remove about two-thirds of requests before a GPU sees them.
  • Fill-in-the-middle exists because real editing happens mid-file, and the code below the cursor is a strong clue.
  • Build repo context locally from cheap signals. Embedding search is too slow to run on every keystroke.
  • Measure retained characters — not acceptance, and certainly not token accuracy. Treat secret leaks and licensing as serious failure modes.

Check your understanding

Why does inline completion use fill-in-the-middle rather than plain left-to-right generation?

FIM rearranges training documents into prefix, suffix, middle, so the model learns to use the code on both sides. That's exactly the situation at a developer's cursor.

Which change most reduces GPU cost per accepted completion?

Requests that never reach a GPU are free. If cancellations don't reach the scheduler, out-of-date requests keep generating, and you pay for suggestions nobody will ever see.

Why is acceptance rate a poor primary metric?

Retained characters (code still in the file minutes later) is a better signal. It doesn't reward suggestions that are easy to accept and then deleted straight away.

Why is prefill, rather than decode, the dominant serving cost here?

This is the reverse of a chat product. So the most valuable optimisations are prefix caching and keeping the context small — not decode speed.

Why must every suggestion be scanned before it is displayed?

No accuracy metric will reveal leaked secrets or word-for-word copied code. Both are far cheaper to stop before display than to clean up afterwards.
