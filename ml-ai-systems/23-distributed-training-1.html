Distributed Training I: Data Parallel, ZeRO & FSDP

There are two reasons to train on more than one GPU: the model doesn't fit on one, or training would take too long. Data parallelism solves the second problem. ZeRO and FSDP build on it to solve the first. Their key insight: every GPU is holding an identical copy of data that only one of them needs at any given moment.

Data parallelism in one picture

Why bother? Say one GPU needs 30 days to train your model. If 8 GPUs could share the work evenly, you'd be done in under 4 days. Data parallelism is the simplest way to get that speed-up, and it is the first thing every large training job uses.

Every GPU holds a full copy of the model (a replica). Each training step works like this:

  • The global batch (all the examples for this step) is split between the GPUs.
  • Each GPU computes gradients (how each weight should change) on its own slice.
  • All the gradients are averaged, so every replica applies the same update and the copies stay identical.

Think of four students each marking a quarter of the exam papers, then pooling their notes so everyone ends up with the same summary.

Why is averaging allowed? The loss of a batch is the average of the per-example losses, and the gradient of an average is the average of the gradients. So if you split a batch into equal slices, average the gradients inside each slice, then average those slice results, you get exactly the gradient of the whole batch. A tiny example: one weight, a batch of 4 examples whose gradients are 2, 4, 6 and 8. On one GPU the batch gradient is (2+4+6+8)/4 = 5. On two GPUs, GPU 0 sees 2 and 4 (average 3) and GPU 1 sees 6 and 8 (average 7). Averaging 3 and 7 gives 5 again. Data parallelism changes where the maths happens, not the result.

One data-parallel stepStep-through
  1. Each GPU takes a different slice. With 4 GPUs and a 4M-token global batch, each one processes 1M tokens. The per-device batch is what has to fit in each GPU's memory. The global batch is what you plan the learning-rate schedule around.
  2. Every replica runs the same computation on different data. The GPUs don't need to talk to each other at all, so this phase scales perfectly.
  3. Each GPU computes gradients for every weight, but only from its own data. Now there are four different sets of gradients, and they must be combined into one.
  4. An all-reduce combines (here, sums) data from every GPU and gives the result to all of them. In a ring all-reduce, the GPUs sit in a circle and each only passes data to its neighbour. The gradients are cut into N chunks. Over N−1 steps around the ring, each GPU builds up the full sum for one chunk. Each step sends just 1/N of the gradients, so the traffic is spread evenly instead of piling onto one machine.
  5. Another N−1 steps pass each finished chunk around the ring so every GPU gets all of them. Total traffic per GPU: 2·(N−1)/N × gradient bytes, which is about 2× the model size no matter how many GPUs you have. That's why ring all-reduce scales.
  6. Every GPU applies the same averaged gradient to the same weights, so the replicas stay identical down to the last bit. Anything that makes them differ here (different dropout random seeds, sums done in a different order) quietly breaks this guarantee.
  7. The backward pass goes from the last layer to the first, so the last layer's gradients are ready long before the first layer's. Frameworks group gradients into buckets and start all-reducing them while the backward pass is still running. This hides most of the communication behind computation. Without this overlap, adding GPUs stops helping.
📐
The communication number worth memorising

Ring all-reduce moves 2×(N−1)/N × model_size bytes per GPU per step. That's about 2× the model size, whatever N is. For a 7B model in bf16 (2 bytes per weight), that's ~28 GB per GPU per step.

Over NVLink (the very fast link between GPUs inside one server, 400 GB/s) that takes 70 ms. Over a 25 GB/s network link between servers, it takes over a second. This one calculation explains why the bandwidth inside a server (a node) decides how you split up the work.

Where does the “2×(N−1)/N” come from? Take N = 4 GPUs and 14 GB of gradients. Each GPU cuts its gradients into 4 chunks of 3.5 GB. In reduce-scatter it sends one chunk per step for 3 steps (10.5 GB). In all-gather it sends one chunk per step for another 3 steps (10.5 GB). Total: 21 GB = 2×3/4×14. With N = 64 it becomes 2×63/64×14 ≈ 27.6 GB. As N grows, (N−1)/N gets closer to 1, so the total creeps up to 2× the gradient size and stops there.

Where the memory goes, and how ZeRO removes it

In plain data parallelism, every GPU stores the full weights, the full gradients and the full optimizer state (extra numbers the optimizer keeps per weight; AdamW keeps two, plus an fp32 copy of the weight). But each GPU only needs a slice of the optimizer state to do its share of the update.

ZeRO (and FSDP, PyTorch's version of it) shards these things: it splits them into pieces and gives each GPU just one piece, instead of a full copy each.

First, the per-weight bill. With mixed-precision training and AdamW, each parameter costs about 16 bytes:

  • 2 bytes for the bf16 weight used in the forward and backward pass.
  • 2 bytes for its bf16 gradient.
  • 4 bytes for the fp32 “master” copy of the weight. Updates are applied here, because tiny changes get rounded away in bf16.
  • 4 + 4 bytes for AdamW's two running averages (the momentum m and the squared-gradient average v), both in fp32.

The last three add up to 12 bytes: that's the “optimizer state”, and it's three quarters of the total. A worked example with a 13B-parameter model on 8 GPUs (activations not included):

Notice what ZeRO does not shard: activations (the intermediate outputs saved during the forward pass for use in the backward pass). Each GPU computes activations for its own slice of the batch, so they depend on the per-device batch size and sequence length, not on N. That's why activation checkpointing is often the next tool you reach for after ZeRO.

Which stage should you pick? Use the lowest stage that fits, because each stage up adds complexity and (for stage 3) traffic.

  • DDP when the whole training state fits comfortably on one GPU, for example a model of 1–2B parameters on 80 GB. It is the simplest and fastest.
  • ZeRO-1 or ZeRO-2 when the weights fit but the optimizer state doesn't. You get most of the memory back with no real speed cost.
  • ZeRO-3 / FSDP when even the bf16 weights plus gradients are too big for one GPU, or you want room for a bigger per-device batch. Keep it on fast links.
  • Offload only when you have few GPUs and time is cheaper than hardware, such as fine-tuning a big model on a single workstation.
🔁
ZeRO-3 trades bandwidth for memory

When the weights are sharded, each layer's weights must be collected from all GPUs just before use, then thrown away after. That's extra traffic on every forward and backward pass. It works beautifully inside one server over NVLink, but badly across a slow network. That's why the usual setup is FSDP inside each server, and other kinds of parallelism between servers (Chapter 24).

Gradient accumulation and effective batch

What if the batch you want doesn't fit in GPU memory? Split it into smaller micro-batches. Run them one after another, add up (accumulate) their gradients, and only update the weights at the end:

effective_batch = per_device_batch × accumulation_steps × num_gpus

for i, micro in enumerate(micro_batches):
    loss = model(micro).loss / accumulation_steps   # ← divide, or your LR silently multiplies
    loss.backward()                                  # gradients accumulate
    if (i + 1) % accumulation_steps == 0:
        clip_grad_norm_(model.parameters(), 1.0)
        opt.step(); opt.zero_grad()

A worked example: you want a global batch of 512 sequences. You have 8 GPUs, and each can hold 16 sequences at once. 16 × 8 = 128 per pass, so you need 512 / 128 = 4 accumulation steps. Each GPU runs 4 micro-batches, then all GPUs sync once and update once.

Why divide the loss? backward() adds new gradients to whatever is already stored. After 4 micro-batches the stored gradient is the sum of 4 batch gradients, which is 4× the average. The optimizer then takes a step 4× too large. Dividing each loss by 4 turns the sum back into an average, so the update matches what one big batch of 512 would give.

Changing the batch means changing the learning rate. A bigger batch gives a less noisy gradient, so you can usually take bigger steps. A common starting rule (the “linear scaling rule”, mostly used with SGD) is: multiply the batch by k, multiply the learning rate by k, and lengthen warmup. For Adam-style optimizers a smaller increase often works better, so treat any rule as a first guess and check the loss curve. The trade-off: accumulation lets you reach a big batch on few GPUs, but it is slower than having more GPUs, because the micro-batches run one after another.

⚖️
Accumulation is free compute, not free bandwidth

Only the last micro-batch triggers the all-reduce. So accumulation also cuts communication per token, which is a useful trick when the network is the bottleneck. In DDP (PyTorch's data-parallel wrapper), remember to turn off syncing for the in-between micro-batches with no_sync(). Otherwise you all-reduce every one of them and lose the benefit entirely.

Scaling efficiency

Doubling the GPUs never quite doubles the speed. Scaling efficiency measures how close you get: 80% means 100 GPUs do the work of 80. Here's what you actually get:

The maths behind it is short. Each step has a compute part and a communication part. Whatever part of the communication is not hidden behind compute adds to the step time. So efficiency ≈ compute_time / (compute_time + exposed_comm_time). Two worked cases for a 7B bf16 model (28 GB of all-reduce traffic per GPU) with 240 ms of compute and 80% of communication overlapped:

  • Inside one server at 400 GB/s: communication takes 28 / 400 = 70 ms. 20% of it is exposed: 14 ms. Efficiency = 240 / 254 ≈ 94%.
  • Across servers at 50 GB/s: communication takes 28 / 50 = 560 ms. 20% exposed: 112 ms. Efficiency = 240 / 352 ≈ 68%. Same model, same GPUs; only the link changed.

⚠️
Common mistakes
  • Not dividing the loss by the number of accumulation steps. The effective learning rate gets multiplied, and training blows up (diverges) for no obvious reason.
  • Forgetting no_sync() during accumulation. You pay for a full all-reduce on every micro-batch.
  • Each rank shuffling data its own way, with no shared random seed. Some samples get used twice, others silently skipped.
  • Code paths that differ by rank. If one rank skips a collective, everything hangs until the timeout. It's the worst kind of failure to debug.
  • Growing the batch size without changing the schedule. Fewer steps at the same learning rate is a different run, and usually a worse one.
  • Measuring speed without a warm-up. The first steps include compiling, memory setup and NCCL (the GPU communication library) setup.

Interview drill

Warm-up: Why does ring all-reduce scale better than a parameter server?

How a strong answer sounds
A parameter server is one central machine that collects everyone's gradients. So all the traffic goes to one place: its bandwidth is a hard ceiling, and the load on that one link grows as O(N). Ring all-reduce spreads the traffic out. Each GPU only talks to its two neighbours, and each GPU sends about 2× the model size no matter what N is. So adding GPUs doesn't add traffic per link. The cost is latency: there are 2(N−1) steps that must happen one after another. That's why very large clusters use hierarchical or tree-shaped algorithms, which send a bit more data but need fewer hops.

Deeper: A 70B model won't fit for training on 8×80 GB. Walk through your options in order.

How a strong answer sounds
First do the arithmetic. 70B weights in mixed precision with AdamW need about 16 bytes each for weights, gradients and optimizer state: 70×16 ≈ 1.1 TB. The GPUs have 640 GB of memory (HBM) in total. So plain DDP is impossible, even before counting activations. Options, cheapest first:
  • ZeRO-1 to shard the optimizer state (the largest item).
  • ZeRO-2 to shard the gradients too.
  • ZeRO-3/FSDP to shard the weights as well. Now it fits, but every layer needs extra traffic to collect its weights. That's acceptable inside one server on NVLink.
  • Add activation checkpointing to cut activation memory, and use bf16 with an 8-bit optimizer if it's still tight.
  • If it still doesn't fit, or communication costs too much, switch to tensor parallelism inside the server plus pipeline parallelism across servers (Chapter 24).
At each step I'd measure MFU (how much of the GPUs' peak compute you actually use) instead of guessing. The goal is fast training, not just fitting.

🧠 Key takeaways

  • Data parallelism gives every GPU a copy of the model and averages the gradients with an all-reduce.
  • Ring all-reduce sends about 2× the model size per GPU per step, however many GPUs there are.
  • ZeRO-1/2/3 split up the optimizer state, the gradients and the weights. Stage 3 saves memory at the cost of extra network traffic.
  • Gradient accumulation makes the effective batch bigger. Divide the loss, and skip syncing on the in-between micro-batches.
  • Scaling efficiency is killed by communication that doesn't overlap with compute, by slow GPUs (stragglers) and by crossing between servers.

Check your understanding

How much data does each GPU send during one ring all-reduce of a 7B bf16 model?

2×(N−1)/N × 14 GB ≈ 28 GB. Because this barely changes as N grows, ring all-reduce is the standard algorithm.

ZeRO-1 shards which component?

Optimizer state is usually the largest item (12 bytes per weight for AdamW in mixed precision). Sharding it costs almost no extra communication, so it's the best deal of the three stages.

Why is ZeRO-3 a poor fit across a slow network?

Sharded weights have to be put back together before each use. On NVLink that's cheap. Over a 25 GB/s link it takes up most of the step time.

You use 4 accumulation steps but forget to divide the loss by 4. What happens?

Accumulated gradients are a sum, not an average. So each update is four times bigger than intended. It's a classic way for training to blow up with no error message.

Scaling efficiency is 92% within one node but 48% across four nodes. First thing to investigate?

The drop happens exactly when traffic leaves NVLink. Check the network bandwidth you actually get, the all-reduce algorithm, the bucket sizes and the overlap before changing anything about the model.
