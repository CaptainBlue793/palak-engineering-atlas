Distributed Training II: Tensor, Pipeline & MoE

Chapter 23 split the data between GPUs. But when a single layer no longer fits on one GPU, or the network can't carry all the gradients, you have to split the model instead. Tensor parallelism: split the matrices

Why go beyond ZeRO? ZeRO-3 still has to collect a full layer's weights onto each GPU before using it, and every GPU still runs the whole model on its own slice of data. When one layer is enormous, or the network can't carry the weight traffic, you need GPUs to share the work of a single layer. That's what tensor parallelism does.

A linear layer Y = XW multiplies the input X by a weight matrix W. You can split W two ways. Split it by columns and each GPU produces some of the output values, complete. Split it by rows and each GPU produces a partial result for all the outputs, so the parts must be added together afterwards.

A tiny example with two GPUs. Let X = [1, 2] and W = [[1, 2], [3, 4]]. The true answer is Y = [1·1 + 2·3, 1·2 + 2·4] = [7, 10].

  • Column split: GPU 0 holds column [1, 3] and computes 1·1 + 2·3 = 7. GPU 1 holds column [2, 4] and computes 1·2 + 2·4 = 10. Each GPU has one finished output value. No talking needed.
  • Row split: GPU 0 holds row [1, 2] and the first input value (1), giving [1, 2]. GPU 1 holds row [3, 4] and the second input value (2), giving [6, 8]. Neither is the answer until you add them: [1+6, 2+8] = [7, 10]. That addition is the all-reduce.

Transformers alternate the two, which means the GPUs only need to exchange data once per sub-layer. The trick is that a column split leaves each GPU holding some of the features, which is exactly the input a row split needs. And the activation in between (GELU) works on each number separately, so each GPU can apply it to its own features without seeing the others. Each GPU also stores only 1/TP of the weights, so tensor parallelism saves memory as well as time.

# MLP block, 2-way tensor parallel
W1 split by COLUMNS → each GPU computes part of the hidden activations
                      (no communication: outputs are independent features)
GELU applied locally
W2 split by ROWS    → each GPU computes a partial output sum
all-reduce          → add the partials to get the true output   ← the one collective

# attention: heads are split across GPUs, then one all-reduce after the output projection

Tensor parallelism is an intra-node technique

Tensor parallelism needs an all-reduce twice per transformer block, so dozens of times per forward pass. Every one of them blocks progress, and there's no other work to hide them behind. Over NVLink inside a server (~400 GB/s) that's fine. Over a 25 GB/s network between servers it wrecks your speed. Hence the near-universal rule: split a matrix across at most as many GPUs as there are in one server (usually 2, 4 or 8).

Pipeline parallelism: split the layers

Put layers 1–8 on GPU 0, layers 9–16 on GPU 1, and so on. Each group of layers is a stage. Data flows forward from stage to stage, and gradients flow back.

The problem is obvious: while stage 0 works on the first batch, stages 1–3 have nothing to do. That idle time is called the bubble. The fix is to keep the pipeline fed, like an assembly line: split the batch into micro-batches and send them in one after another, so every stage always has something to work on.

The bubble formula

bubble fraction = (stages − 1) / (micro_batches + stages − 1). Where does it come from? Count time slots for the forward pass. The first micro-batch needs S slots to get through S stages, and each of the other M−1 micro-batches finishes one slot later, so the whole forward pass takes M + S − 1 slots. Each stage is busy for only M of them. The other S − 1 slots are idle, while it waits for work to arrive at the start or for the others to finish at the end. The backward pass has the same shape, so the fraction holds for the whole step. With 4 stages and 4 micro-batches you waste 3/7 ≈ 43% of the time. With 4 stages and 32 micro-batches, only 8.6%. The rule of thumb: use at least 4 micro-batches per stage.

The catch is memory. Every micro-batch still moving through the pipeline has to keep its intermediate values (activations) for the backward pass. That's exactly what 1F1B scheduling fixes: each stage does one forward, then one backward, starting backward passes as early as possible so fewer activations are held at once.

Why not just use 1,000 micro-batches? The global batch is usually fixed by the learning-rate plan. More micro-batches means each one is smaller, and very small matrix multiplies leave the GPU underused. So you pick enough micro-batches to shrink the bubble, while keeping each one large enough to keep the GPU busy.

Sequence and context parallelism

With very long contexts, even a single sequence's activations stop fitting on one GPU. Sequence parallelism splits along the tokens: each GPU holds one part of the sequence.

Attention normally compares every token with every other token, which would need a full T×T table of scores (T is the sequence length). Instead, the GPUs pass blocks of keys and values around a ring, so each GPU only ever computes a slice of that table. This is called ring attention. It works alongside tensor parallelism, and it's how models are trained on contexts of 100k tokens and more.

3D parallelism: composing the dimensions

The biggest training runs use all of these at once. The skill is matching each one to the hardware, so the kind of parallelism that talks the most sits on the fastest link.

The sizes multiply: total GPUs = TP × PP × DP. For example, 512 GPUs could be TP = 8 (one server), PP = 8 (eight servers in a chain) and DP = 8 (eight copies of that 64-GPU chain). Each GPU then holds 1/64 of the model's weights, and each of the 8 copies processes its own slice of the global batch.

Why does pipeline traffic count as “small”? Compare the sizes. At a stage boundary, one GPU sends one micro-batch's activations: say 4 sequences × 4,096 tokens × a hidden size of 8,192 × 2 bytes ≈ 0.27 GB. The data-parallel gradient all-reduce for a 70B model is about 2 × 140 GB of traffic per GPU per step. The pipeline sends a small amount to one neighbour; data parallelism sends a lot, but only once per step and overlapped. Tensor parallelism sends activation-sized messages but very often, and with nothing to hide behind. That difference in pattern is what decides where each one goes.

Mixture of Experts: more parameters, same compute

In some blocks, replace the single MLP with N copies of it, called experts, plus a small router that picks which experts each token goes to (usually the best 1 or 2, hence “top-k”).

The total number of parameters grows N times, but each token only uses k of the experts. So the model holds much more knowledge while the work done per token stays about the same. It's like a company hiring specialists: more expertise available, but each question still only goes to one or two people.

A worked example. Suppose each expert MLP has 1B parameters and a block has 8 experts with top-2 routing. That block's MLP holds 8B parameters, but each token only runs through 2B of them. The router itself is tiny: a small linear layer that gives each expert a score for this token, followed by a softmax. The token is sent to the top 2 experts, and their outputs are mixed using those scores as weights.

Capacity factor, with numbers. A batch has 1,024 tokens and 8 experts with top-2 routing, so there are 2,048 token-to-expert assignments. A perfectly even split is 256 per expert. A capacity factor of 1.25 gives each expert 1.25 × 256 = 320 slots. If the router sends 400 tokens to one popular expert, 80 of them don't fit and are dropped (they skip that MLP and pass through on the residual connection). A higher capacity factor drops fewer tokens but reserves more memory and compute for slots that may sit empty.

When to choose MoE over a dense model: when training compute is your main limit and you can afford the memory to serve all the experts. When serving memory is the limit, such as a model that must run on a single GPU, a dense model of the same memory size is usually the better choice.

Routers collapse without help

Left alone, a router finds that sending everything to the two experts that are already good lowers the loss fastest. The other experts never get any tokens, so they never learn. This is called router collapse.

Every MoE implementation adds an auxiliary load-balancing loss: an extra penalty when the tokens are spread unevenly. It also sets a capacity factor, a limit on how many tokens one expert may take. Tokens over the limit are dropped or passed through unchanged. Watch the per-expert token counts during training the way you watch the loss curve. Collapse is the classic MoE failure.

⚠️
Common mistakes
  • Tensor parallelism between servers. Two all-reduces per block over the network will cut your speed in half or worse.
  • Too few micro-batches for the number of stages. A 50% bubble wastes half your cluster, and the fix is one setting, not new hardware.
  • Forgetting the first and last pipeline stages need extra memory. Stages are rarely equal: those two also hold the embeddings and the output layer.
  • Not watching how MoE tokens are spread across experts. Collapse doesn't show up in the loss curve, but it's obvious in the routing chart.
  • Assuming MoE is cheap to serve. Training compute goes down; the memory needed to serve it does not.
  • Changing the parallel layout without re-checking the global batch. The batch size and learning-rate schedule depend on how many data-parallel copies you have.

Interview drill

Warm-up: Why is tensor parallelism kept within a node while pipeline parallelism crosses nodes?

How a strong answer sounds
They communicate in opposite ways. Tensor parallelism all-reduces the full activation tensor twice per transformer block: frequent, sensitive to delay, and everything waits for it with no other work to hide it behind. Pipeline parallelism only sends activations between neighbouring stages, a handful of direct transfers per micro-batch, so it copes fine with slower, higher-delay links. That's why tensor parallelism goes on NVLink inside a server, and pipeline parallelism takes the slow hops between servers. Data parallelism sits outermost, because its single all-reduce per step can overlap with the backward pass.

Deeper: You're given 512 GPUs for a 200B-parameter model. Sketch the layout.

How a strong answer sounds
Start from memory. 200B parameters in mixed precision, including optimizer state, is about 16 bytes each, so ~3.2 TB. The model has to be split up no matter what. My layout:
  • TP=8 inside each server, so the frequent all-reduces run on NVLink.
  • PP=8 across servers, sized so each stage's layers plus activations fit. That gives a model-parallel group of 64 GPUs holding one copy of the model.
  • DP=8 for the rest, with FSDP or ZeRO-1 inside each data-parallel group to shard the optimizer state.
  • At least 32 micro-batches, to keep the pipeline bubble near 10%. Activation checkpointing on. Sequence parallelism too, if the context is long.
Then I'd check the plan instead of trusting it: measure MFU (how much of the GPUs' peak compute I'm actually using), check that stages are balanced (the first and last also carry the embeddings and the output layer), and confirm the global batch and learning-rate schedule still match what the scaling-law work assumed.

🧠 Key takeaways

  • Tensor parallelism splits matrices and all-reduces twice per block, so keep it inside one server.
  • Pipeline parallelism splits layers. Idle time is (stages−1)/(micro-batches+stages−1), so use many micro-batches and 1F1B scheduling.
  • Sequence parallelism splits a single sequence across GPUs, for very long contexts.
  • Combine them so the most talkative one gets the fastest link: tensor inside servers, pipeline between them, data parallelism outermost.
  • MoE adds parameters without adding compute per token. You pay in all-to-all traffic, unstable routing and the memory needed to serve it.

Check your understanding

With 8 pipeline stages and 8 micro-batches, what fraction of time is bubble?

(8−1)/(8+8−1) = 7/15 ≈ 47%. You need roughly four times as many micro-batches as stages before the bubble gets small.

Why is tensor parallelism across a slow network so damaging?

There are dozens of these exchanges per forward pass, each one stopping all progress, with no computation to hide them behind. Data parallelism's single all-reduce per step can overlap with compute, so it copes far better with slow links.

An MoE model has 8 experts with top-2 routing. Roughly how do parameters and per-token compute compare with a dense model of the same expert size?

All the experts sit in memory, but only k of them run for each token. That's the trade: knowledge grows with N, compute grows with k, and serving memory grows with N. The last part is what people forget.

Your MoE run shows two experts receiving 70% of all tokens. What's the fix?

This is router collapse. The auxiliary loss penalises an uneven split, and the capacity limit caps how much any one expert can take. Track the tokens per expert as a main metric, not an afterthought.

Which parallelism dimension is best placed outermost, across the whole cluster?

Its one gradient all-reduce per step can overlap with the backward pass, so it copes with the slowest links. And the slowest links are exactly what the outermost layer has to use.
