Data Engineering & Streaming for ML

A model can only be as good as the data pipelines that feed it. Some questions matter more than the model itself. Does a feature arrive in 50 milliseconds or 6 hours? Does re-running old data (a backfill) give exactly the same history? Can someone rename a column and quietly break training? These decide how reliable your ML system is.

  • Choose between batch and streaming for a given feature
  • Reason about event time, windows, watermarks and late data
  • Build pipelines that are idempotent and safely re-runnable
  • Use data contracts and schema evolution to stop silent breakage
  • Budget end-to-end freshness from event to prediction

Batch or streaming?

Batch means processing data in big chunks on a schedule, like once a night. Streaming means processing each event as it arrives. The honest default is batch. Streaming is always more complex: you must handle ordering, late data, saved state and duplicate delivery. Use it only where fresher data would actually change a decision.

A quick test: ask “if this feature were 6 hours old, would the prediction change in a way that matters?” For a customer's lifetime order count, one more order barely moves the number, so no. For a card's transactions in the last 10 minutes, a fraudster's burst of purchases is only visible for those 10 minutes, so yes. A 6-hour-old value would miss the attack entirely.

The shape of a modern stack

Events land in a log, an append-only queue of events (Kafka, Kinesis, PubSub). A stream processor reads it and computes real-time totals into an online store, a fast database the model reads at request time.

The same events are also saved to cheap object storage in open table formats (Iceberg, Delta, Hudi). These add database-like features on top of plain files: safe all-or-nothing writes (ACID commits), reading the data as it was on an older date (time travel), and changing the columns safely (schema evolution).

Batch jobs and the data warehouse read those tables. An orchestrator (Airflow, Dagster) runs the jobs in the right order, as a DAG (a graph of steps and their dependencies), and handles retries and backfills. Finally, CDC (change data capture) copies every change from your app databases into the same lake. That way the model can use transaction data without querying the production database.

Event time, windows and late data

The moment something happened (event time) and the moment your system saw it (processing time) are different. The gap can be milliseconds, or hours if a phone was offline. Grouping events by processing time is easy but wrong. Grouping by event time is correct, but you must decide how long to wait for stragglers.

Events are grouped into windows, time buckets like "each minute". A watermark is the system's rule for when a window is "done": "I'll wait this long for late events, then close the bucket."

The three window shapes in the simulator:

  • Tumbling: fixed, non-overlapping buckets. 12:00–12:01, 12:01–12:02, and so on. Each event lands in exactly one. Good for “orders per minute”.
  • Sliding: fixed-length buckets that overlap. A 60-second window every 30 seconds gives 12:00:00–12:01:00, 12:00:30–12:01:30, … so each event lands in two. Good for “transactions in the last minute”, updated often.
  • Session: a bucket per burst of activity, closed after a gap with no events (say 30 seconds). Lengths vary. Good for “what the user did in this visit”.

A watermark worked through: a tumbling window covers event times 12:00:00–12:01:00, and the watermark delay is 30 seconds. The window is closed once the stream has seen events up to 12:01:30. An event stamped 12:00:50 that arrives while the stream is at 12:01:10 is late but still counted. The same event arriving when the stream is at 12:01:45 is too late: the window's result has already been sent, so the event is dropped or sent down a separate correction path.

The watermark is a correctness/latency dial

A long watermark waits for stragglers, so results are complete but slow. A short one is fast but drops late data. Neither is “right”. Choose based on the decision that uses the result.

For fraud scoring, being 30 seconds late is worse than missing 0.3% of events. For billing totals the reverse is true. There you send out early results and correct them later with an update path. Make every consumer idempotent (safe to receive the same update twice) so the corrections are safe.

Delivery semantics

Where do losses and duplicates come from? A consumer reads an event, processes it, and records its position in the log (its offset) so it knows where to resume after a crash. If it records the offset before processing and then crashes, the event is skipped on restart: lost. If it processes first and crashes before recording the offset, it reads the event again on restart: duplicated. The three guarantees below are three answers to that race.

1️⃣

At-most-once

Never duplicated, sometimes lost. Fine only for metrics you can afford to miss.

🔁

At-least-once

Never lost, sometimes duplicated. The practical default. Pair it with idempotent consumers (processing the same event twice has the same effect as once) and duplicates stop mattering.

🎯

Exactly-once

Every event counts once. You get it with transactional writes that also save your read position (the offset), or by removing duplicates using an event id. It works, but it costs speed and complexity. First ask whether idempotency is enough.

What makes a consumer idempotent? Compare two ways of handling “payment 7f3a of £10 received”. total = total + 10 is not idempotent: process it twice and the total is £10 too high. Storing the payment keyed by its id (payments["7f3a"] = 10) and computing the total from that table is idempotent: the second copy just overwrites the first. Most pipelines get “effectively once” results this way: at-least-once delivery plus writes keyed by event id.

Backfills: the thing you'll do constantly

A backfill means re-running a pipeline over past data. You need one when a new feature needs three years of history. Or a bug made last month's totals wrong. Or a model needs retraining on fixed data. Backfills are routine, so design for them from the start.

PropertyWhy it matters
Idempotent writesRe-running a partition (one slice of the data, such as one day) must replace it, not add to it. Use partition overwrite or merge-on-key, never a blind insert.
Partitioned by event dateLets you redo one day without touching the rest. A day is the unit of both cost and damage if something goes wrong.
Deterministic logicSame input, same output. No now(), no random seeds, no lookup table that changes over time. Otherwise a backfill gives different numbers than the original run did.
Point-in-time inputsA backfill must use the data as it was on that day, not today's. This is the most common cause of training/serving skew, where the model sees different data in training than in production (Chapter 29).
Throttled and observableA 3-year backfill can overload the cluster that the live pipeline also uses. Limit its speed and track its progress.

The classic backfill bug

You backfill “customer's account tier” for 2024 using today's tier table. Customers who upgraded in 2025 now look premium for all of 2024. So the model learns that premium customers bought more. In reality, buying more is what made them premium. The offline score improves, but the live result doesn't.

The fix: store any value that changes over time as a slowly-changing dimension, a table where each value has a "valid from / valid to" date range. Then join it as of each event's timestamp.

For example, customer 42 has two rows: tier = basic, valid 2023-01-01 to 2025-03-10 and tier = premium, valid 2025-03-10 onwards. An order placed on 2024-06-01 joins to the row whose range contains that date, so it correctly sees “basic”. A plain join on customer id would pick up today's “premium”.

Why idempotent writes matter, in numbers. A daily job counts 1,000 orders for 2024-05-01 and appends them to the table. It fails halfway through the next step, and the scheduler retries the whole job. With a blind insert, 2024-05-01 now shows 2,000 orders, and the model trains on a day that looks like a sales spike. With a partition overwrite, the retry replaces that day's rows, and the count stays at 1,000 however many times the job runs.

Data contracts

A pipeline breaks when an upstream team renames a column on a Tuesday. A data contract is a written, versioned agreement about the data's shape (its schema) and its promises. The producing team tests it in their CI (the automated checks that run on every code change). So a breaking change fails in their pull request, not in your training run.

contract: checkout.completed version: 3 owner: payments-team sla: p99 < 60s to the lake fields: event_id string required unique occurred_at timestamp required event time, UTC user_id string required pseudonymised amount_minor int64 required >= 0 currency enum required [GBP, EUR, USD] coupon_code string optional nullable, may be added to guarantees: - at-least-once delivery, deduplicate on event_id - additive schema changes only within a major version - breaking changes require a new topic and 90 days of dual-write quality: - null_rate(user_id) == 0 - daily_volume within ±30% of the 7-day median

The contract's rule about “additive changes only” is the heart of it. Some examples:

  • Safe (additive): adding a new optional field such as gift_wrap. Old readers simply ignore it.
  • Breaking: renaming amount_minor to amount, changing it from pence to pounds, or making user_id optional. Old readers either fail or, worse, keep running and read the wrong values.

The quality rules catch problems the schema can't. A field can have the right type and still be wrong. If a bug makes user_id empty on every event, or cuts daily volume in half, the schema check passes but the null_rate and volume checks fail.

Freshness budgets

“Real-time” means nothing on its own; a number does. Freshness is how old the data is when the model uses it. Trace the path from event to prediction and add up each step.

A worked example for an hourly batch feature. The event reaches the log in 2 seconds. It lands in the lake in files flushed every 10 minutes. The hourly job starts on the hour and takes 15 minutes. The results are loaded into the online store in 5 more minutes. In the worst case an event happens just before a run, but its file only lands in the lake 10 minutes later, after the run has started. It then waits for the next run an hour later: roughly 10 + 60 + 15 + 5 = about 90 minutes old. If the product needs features under 5 minutes old, no tuning of this batch job will get there. The design has to change.

Where the money goes in a data platform

Not compute. It's small files and repeated scans. Thousands of tiny files per partition make every query slow and expensive. The fix is compaction (merging small files into bigger ones) and sensible partition sizes. Aim for files of 128 MB–1 GB.

Why small files hurt: each file costs a fixed amount of work to list, open and read its header, however little data it holds. 10 GB stored as 10,000 files of 1 MB means 10,000 of those fixed costs. The same 10 GB as 20 files of 500 MB means 20. The data is identical; the query can be many times slower. Streaming writers create small files naturally, because they flush often, which is why compaction jobs are routine.

After that:

  • Lifecycle policies that move old, rarely used data to cheaper storage.
  • Columnar formats with predicate pushdown, so queries read only the columns and rows they need.
  • Saving (materialising) totals that many jobs would otherwise each recompute.
⚠️
Common mistakes
  • Aggregating by processing time. Results change when a consumer falls behind, and a backfill gives different numbers than the live run.
  • Non-idempotent writes. A retried job counts things twice. Nobody notices until a metric looks odd weeks later.
  • Using current dimension values in a backfill. This leaks the future into the past. It's the classic silent quality killer.
  • No data contract. Upstream renames a field, and training quietly runs on empty (null) values.
  • Streaming everything. Most features don't need it, and each streaming pipeline is something you must run and maintain forever.
  • Ignoring small files. The most common reason a data lake gets slower and more expensive every month.

Interview drill

Warm-up: Why prefer event time over processing time for feature aggregation?

How a strong answer sounds
Because event time belongs to the data, while processing time belongs to your infrastructure. If a consumer falls behind or you replay history, processing-time windows give different results for the same events. Then training data and live features stop agreeing, and backfills don't reproduce. Event time makes the result the same every run. The price: you must handle late arrivals explicitly, with watermarks and an update path for corrections.

Deeper: A model needs “transactions in the last hour” both online at 20 ms and offline for 2 years of training data. How do you build it?

How a strong answer sounds
One definition, two ways of running it, and a test that proves they match. Online: a stream processor keeps a sliding one-hour count per card, written to a fast store the model reads at request time. Offline: the same count computed over the event log with a strict as-of join. For each labelled example, count events in the hour strictly before that example's timestamp. That's the point-in-time correctness problem from Chapter 29. I'd build the training set from the same event stream, not from the online store's current values. I'd define the count once in a feature repository so both paths share it. And I'd add an ongoing check that compares online values with a recomputation on a sample. Late events get a watermark and an update path. The training set uses the same lateness policy as the online system. Otherwise offline always looks better than production.

🧠 Key takeaways

  • Use batch unless fresher data changes a decision. A streaming pipeline is something you must run forever.
  • Group events by event time with an explicit watermark. Let the decision that uses the data set your late-data policy.
  • Prefer at-least-once delivery with idempotent consumers over chasing exactly-once.
  • Design for backfills: partitioned, idempotent, deterministic, and joined as of the event time.
  • Data contracts move breakage out of your training run and into the producer's pull request.

Check your understanding

What does a watermark represent in stream processing?

It's the system saying "this window is complete now". That is what lets a window close and send out its result. A longer watermark means more complete results, but later.

You backfill “customer tier” for 2024 using the current tier table. What's wrong?

Customers who upgraded later look upgraded for all of history. The model learns cause and effect backwards, so the live result never matches the offline one.

Your stream sink is at-least-once. What's the pragmatic way to handle duplicates?

Idempotency makes duplicates harmless. It's far cheaper than building exactly-once delivery end to end.

Which feature genuinely needs a streaming pipeline?

Here, how recent the data is is the signal. A five-minute-old count of recent transactions is useless for catching fraud. The other features are fine being hours old.

What is a data contract primarily for?

It catches the failure earlier. A breaking change fails the producer's build, instead of quietly corrupting your training set weeks later.
