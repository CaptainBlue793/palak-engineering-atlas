Pretraining, Scaling Laws & Data Curation

Pretraining is one simple task — predict the next token — run over an enormous, heavily filtered pile of text. The loss function is the easy part. The real engineering is deciding how big a model to train, for how long, and on which tokens, with a fixed amount of money.

  • Explain what next-token prediction actually teaches a model
  • Design a data pipeline: filter, deduplicate, mix, shard
  • Use scaling laws to pick model size and token count for a compute budget
  • Adjust that choice when inference cost matters more than training cost
  • Avoid contamination and know what “emergence” does and doesn't mean

One objective, enormous consequences

The loss is cross-entropy on the next token: it is low when the model gives high probability to the token that actually came next. Because of causal masking (no token can see the future), every position in the sequence can be scored at the same time.

In numbers, the loss for one position is −ln(probability the model gave the right token). Give the right token 0.9 and the loss is about 0.11. Give it 0.5 and the loss is 0.69. Give it 0.01 and the loss is 4.6 — confident mistakes are punished hard. The reported loss is the average over every position in the batch. A handy translation: eloss (the perplexity) is roughly how many tokens the model is torn between. A loss of 2.0 means perplexity ≈ 7.4, as if choosing among about 7 equally likely tokens.

The code below shifts the sequence by one to make the labels. For the text “The cat sat on the”, the input is “The cat sat on” and the targets are “cat sat on the”. Position 1 must predict “cat”, position 2 must predict “sat”, and so on — four predictions from one pass, thanks to the causal mask.

To predict well across trillions of tokens, a model has to pick up grammar, facts, how code behaves, arithmetic patterns, translation, style and a fair amount of reasoning. Not because anyone asked for those skills, but because each one lowers prediction error.

for batch in stream:                       # ~4M tokens per step at frontier scale
    logits = model(batch[:, :-1])
    loss   = cross_entropy(logits, batch[:, 1:])
    loss.backward(); clip_(1.0); opt.step(); sched.step()
🎯
Why this objective is so efficient

Every token is its own labelled example, and the label is simply the next token. So it is free. A 2-trillion-token corpus gives you 2 trillion training examples with no labelling budget at all. That is the whole reason self-supervised pretraining could scale when hand-labelled learning could not.

The data pipeline is the product

Raw text scraped from the web is mostly junk: navigation menus, spam, duplicated pages. So every serious pretraining project is really a filtering pipeline. Very little of what goes in survives to the end.

Deduplication is worth more than almost anything else

A web crawl contains the same text dozens of times: mirror sites, quotes, templates, scraped copies. Duplicates waste compute, push the model toward memorising text word for word (a privacy and copyright hazard), and quietly change the mix of what it learns from.

Published results agree: a deduplicated corpus reaches the same loss with far fewer tokens. Do exact dedup first, since it is cheap. Then do near-duplicate removal with MinHash/LSH, which is expensive but worth it.

How near-duplicate detection works, in brief. Cut each document into overlapping runs of, say, 5 words (“shingles”). Two documents' similarity is the share of shingles they have in common, called Jaccard similarity. If two pages each have 100 shingles and share 90, the Jaccard is 90 ÷ (100 + 100 − 90) ≈ 0.82 — almost certainly the same article with a different header. Comparing every pair among billions of pages is impossible, so MinHash squeezes each document into about a hundred small numbers that preserve Jaccard, and LSH puts documents with similar numbers into the same bucket. Only documents in the same bucket get compared.

Mixture matters as much as volume

SourceShare of tokensWhy it's in the mix

The best sources are usually upsampled: shown to the model 2–4 times, while ordinary web text is seen once. But repeat a small set of text too often and the gains fade, and eventually the model just memorises it.

Worked example of how shares turn into repeats. You plan a 10-trillion-token run with 15% code, so the model needs 1.5T tokens of code. If your cleaned code set is only 500B tokens, the model sees it 1.5T ÷ 500B = 3 times. That is fine. If it had to see it 20 times to reach the same share, you should lower the code share or find more code.

Scaling laws: how to spend a compute budget

Here is the useful surprise: loss falls in a smooth, predictable curve as you add parameters, data and compute. Plot it on log axes and it is close to a straight line (a “power law”). That means you can measure small runs and predict a big one.

What “straight line on log axes” means in plain words: every 10× increase in compute cuts the loss by about the same percentage. So if going from 10¹⁹ to 10²⁰ FLOPs cut the (improvable part of the) loss by 15%, going from 10²² to 10²³ will cut it by about 15% too. Returns shrink, but predictably — that predictability is what lets a lab commit millions of dollars to a run.

The practical question is how to split a fixed compute budget C ≈ 6·N·D between N (parameters) and D (training tokens).

Kaplan et al. (2020)

Found that loss falls smoothly with N, D and C, and suggested spending most of the budget on parameters. That is why models in 2020–2021 got enormous while their token counts stayed near 300B.

Chinchilla (2022)

Corrected that: for a fixed budget, N and D should grow together, at roughly 20 tokens per parameter. Proof: a 70B model trained on 1.4T tokens beat a 280B model trained on 300B tokens, using the same compute.

You can do the Chinchilla split by hand. Put D = 20N into C = 6·N·D and you get C = 120·N², so N = √(C ÷ 120). For a budget of 10²³ FLOPs: N = √(8.3 × 10²⁰) ≈ 29B parameters, and D = 20 × 29B ≈ 580B tokens. Check: 6 × 29B × 580B ≈ 10²³. The same arithmetic confirms the Chinchilla comparison: 6 × 70B × 1.4T ≈ 5.9 × 10²³, and 6 × 280B × 300B ≈ 5.0 × 10²³ — about the same compute, very different results.

Compute-optimal ≠ deployment-optimal

Chinchilla answers one question: the lowest training loss per training FLOP. But if you will serve the model billions of times, serving is the bigger bill.

Then it pays to over-train a smaller model — 100–300 tokens per parameter. The serving cost depends on N and you pay it forever, while the extra training cost is paid once. That is exactly why 7–8B models are now trained on 10–15T tokens.

Put numbers on it. Say 100M users generate 1,000 tokens each per day: 10¹¹ tokens a day, about 3.7 × 10¹³ a year. Inference costs about 2N FLOPs per token (Chapter 14). A 30B model then burns about 2.2 × 10²⁴ FLOPs a year; a 7B model about 0.5 × 10²⁴. The yearly difference, 1.7 × 10²⁴, is more than the whole cost of training the 7B model on 15T tokens (6 × 7B × 15T ≈ 0.6 × 10²⁴).

Everything is decided on small models first

Nobody tunes hyperparameters at 70B — it is far too expensive. Instead you train a ladder of small models (say 70M → 300M → 1B), fit the trend, and extend the line to the size you want.

Data-mixture experiments, tokenizer choice and architecture changes are all checked this way. Day to day, “scaling laws” means “the tool that stops one very expensive run from being a gamble”.

Emergence and contamination

Both topics are about trusting your numbers. Emergence is about whether a benchmark curve predicts the future; contamination is about whether a benchmark score measures anything at all.

A small example of how scoring creates a “jump”. Suppose a task needs 5 steps, all correct, to count as solved. As the model grows, its chance of getting each step right rises steadily: 50%, then 70%, then 90%. But the chance of getting all 5 right is that number to the 5th power: 3%, then 17%, then 59%. The skill grew smoothly; the exact-match score looks like it switched on.

✨ “Emergent” abilities

Some skills look like they switch on suddenly as models get bigger. Much of that jump is an artefact of how you score. Exact-match scoring gives zero until the answer is perfect, which turns steady progress into a sudden step. Score more gently (log-likelihood, partial credit) and the gains usually look gradual. Worth knowing before you plan a roadmap around a cliff edge.

🚨 Benchmark contamination

If a test set was ever on the web, assume it is in your training data — so the model may have seen the answers. Clean it out by matching runs of words against every benchmark you will report — for example, drop any training document that shares a 13-word run with a test question. Keep a private test set of your own. And treat any suspiciously strong public-benchmark score as contaminated until you prove otherwise (Chapter 35).

⚠️
Common mistakes
  • Adding parameters without adding data. A big model trained on too few tokens is undertrained and expensive to serve — the classic pre-Chinchilla mistake.
  • Skipping near-duplicate removal. You pay full compute for text you already have, and raise the risk of the model reciting it.
  • Filtering so hard that the long tail disappears. Strict quality classifiers throw out dialects, minority languages and technical jargon, and the model ends up narrower.
  • Reporting benchmarks without decontamination. The number means nothing, and someone will find out.
  • Tuning during the big run. Settle hyperparameters on a ladder of small models. The big run is for execution, not experiments.
  • Forgetting data licences. At this scale, knowing where your data came from is a legal requirement, not a nicety (Chapter 37).

Interview drill

Warm-up: You have compute for either a 30B model on 600B tokens or a 7B model on 2.6T tokens. Which do you pick?

How a strong answer sounds
Both use roughly the same training FLOPs. Chinchilla says the compute-optimal split is around 20 tokens per parameter. The 30B/600B option is at 20; the 7B/2.6T option is at about 370. So the first is compute-optimal and the second is heavily over-trained. If this is a research model and the goal is the lowest training loss, take the 30B. If it will be served at scale, take the 7B: it costs roughly 4× less per generated token, forever, and fits on smaller hardware, while the quality gap after over-training is small. The deciding question is how much inference you expect relative to the training cost.

Deeper: Your pretraining loss is fine but downstream code ability is weak. What do you investigate?

How a strong answer sounds
The overall loss is dominated by whatever makes up most of the mixture, so a weak minority domain barely shows up in it. So I'd measure held-out loss per domain, not just the total. Then I'd check how big the code share of the mixture is, and whether strict quality filters deleted whole repositories. I'd check how the tokenizer handles indentation and variable names, since a code-unfriendly vocabulary costs both context and accuracy. I'd check that dedup didn't wipe out legitimate but near-identical code files. And I'd consider a mid-training phase that repeats high-quality code. I'd test each idea on a small model before touching the main run.

🧠 Key takeaways

  • Next-token prediction turns plain, unlabelled text into trillions of free training examples.
  • Most pretraining work is filtering, deduplicating and mixing data — not designing the loss.
  • Chinchilla: for a fixed budget, grow parameters and tokens together, at roughly 20 tokens per parameter.
  • If you will serve a lot of traffic, over-train a smaller model. Serving cost depends on N and never stops.
  • Settle architecture and hyperparameters on a ladder of small models, and decontaminate before reporting any benchmark.

Check your understanding

What did the Chinchilla result change?

Before Chinchilla, budgets went mostly into parameters. It showed those models were undertrained: the same compute, spent on a smaller model with more tokens, gave a better model.

Why is near-duplicate removal so valuable in a pretraining corpus?

You pay full compute for text you have already seen. It also pushes the model to memorise passages word for word (a privacy and copyright risk), and quietly gives extra weight to whatever happens to be copied most.

You will serve a model to 100M users daily. How should that change the Chinchilla-optimal choice?

Inference cost grows with the number of parameters, and you pay it on every request, forever. Over-training a smaller model moves that cost into the one-off training bill instead.

Your model scores suspiciously well on a public benchmark. Most likely explanation?

Public benchmarks live on the web, so they end up in the crawl. Filter out overlapping text and re-check on a private test set before you believe the number.

How are hyperparameters for a 70B pretraining run usually chosen?

Searching at full scale is far too expensive. You fit the trend on 70M–1B models, extend the line, and use the big run to execute rather than explore.
