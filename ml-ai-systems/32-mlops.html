MLOps: CI/CD/CT Pipelines

In normal software, CI (continuous integration: automatic checks on every code change) answers “does this code still work?”. CD (continuous delivery) then ships it. ML has three moving parts: code, data and model. Any one of them can break the system while the other two look fine. That's why ML adds a third letter: CT, continuous training.

  • Design a test suite that catches ML-specific failures
  • Build a CI pipeline that's fast enough that people keep it
  • Choose retraining triggers and the guardrails around them
  • Promote models through environments with automated gates
  • Place your team honestly on the maturity ladder

Three things change, not one

In a normal web service, nothing changes in production unless someone deploys new code. In an ML system that is no longer true. Here is a real-world style example: an upstream team switches the amount column from pounds to pence. No ML code changed and every unit test still passes. But every amount is now 100 times bigger, and a fraud model trained on pounds starts flagging ordinary purchases. That is why each of the three moving parts needs its own checks.

💻

Code

Feature transforms, training script, serving handler. Tested like any software. And training and serving must use the same transform code (Chapter 29).

🧱

Data

Changes all the time, with no deploy. Needs contracts, validation and checks on value distributions inside the pipeline itself (Chapters 3, 28).

🧠

Model

A learned file whose behaviour can get worse for one slice (group of users or cases) while the overall metrics improve. Needs behavioural tests and slice gates.

Behavioural tests are the least familiar row, so here is one written out. Take a fraud model and a transaction it scores at 0.20. The tests make small, controlled changes and check the score moves the way common sense says:

  • Invariance: change the customer's name from “Ana” to “Priya”. The score must stay within, say, ±0.01 of 0.20. A name should carry no fraud signal.
  • Directional: raise the amount from £40 to £4,000, keeping everything else fixed. The score must not go down.
  • Known cases: a hand-picked list of 50 obvious frauds must all score above the alert threshold.

Accuracy on a test set can't catch these problems, because a model can be accurate on average while relying on a nonsense signal. Behavioural tests check how it gets its answers.

Slice gates need a worked example too. A new model improves overall AUC from 0.880 to 0.891. But broken down, users in their first week drop from 0.820 to 0.770. With a gate of “no slice may lose more than 0.02”, this model is blocked, even though the headline number went up. New users are exactly the group you can least afford to disappoint.

⚡
CI has to be fast or it gets bypassed

Keep the checks on each commit under ten minutes: unit tests, data validation on a fixed sample, and a tiny training smoke test with a fixed seed. Move full training, full evaluation and load tests to a nightly or pre-promotion pipeline. A twenty-minute CI becomes a skipped CI. And a skipped CI is worse than none, because it gives false confidence.

Continuous training

Models get worse over time because the world changes (Chapter 34). Retraining should be an automatic pipeline with checks it must pass (gates). It shouldn't be a quarterly project that depends on someone remembering.

The two basic ways to decide when to retrain, and when to pick each:

  • Fixed schedule (every day, week or month). Simple and predictable, and easy to budget. Pick it when the world changes at a steady pace, and when labels arrive late so you can't measure decay quickly. Its weakness: it wastes money when nothing changed, and reacts slowly when something changes suddenly.
  • Triggered (retrain when input drift or a performance metric crosses a threshold). Reacts to real change and skips pointless runs. Pick it when changes are sudden and irregular. Its weakness: it depends on monitoring you trust. A noisy trigger retrains constantly; a deaf one never fires.

Most teams combine them: a schedule as a floor, plus a trigger for surprises. The cost side is simple arithmetic. At $1,200 per run, weekly retraining costs 52 × $1,200 = $62,400 a year; daily costs 365 × $1,200 = $438,000. Daily is only worth it if the extra freshness earns more than the $375,600 difference.

🚧
Automated retraining without gates is an automated outage

A pipeline that trains and deploys on a schedule will one day train on a corrupted upstream table and ship it at 3am. Every automatic promotion needs:

  • Data validation that fails closed: if in doubt, it blocks. (The opposite, failing open, means “if the check itself breaks, carry on”, which is how corrupted data gets through.)
  • A comparison with the current production model on a fixed evaluation set that never changes.
  • Slice checks and a parity test.
  • A canary (a small share of real traffic) with automatic rollback.

If any gate can't be checked, the pipeline stops and pages someone. It does not carry on.

Environments and promotion

Why so many steps? Each environment catches a kind of problem the one before it can't. Staging proves the pipeline works on real data. Shadow proves the model behaves on real traffic, but without affecting anyone. Canary proves real users are not harmed, while limiting the damage if they are: at 2% of traffic, a bad model touches 2 in every 100 users, and only for the minutes until rollback. A model moves one step at a time, and each step has its own gate.

dev        → developer machines and notebooks, sampled data, no gates
staging    → full pipeline on real data, artifacts written to a staging registry
shadow     → production traffic, model runs, output logged but not used
canary     → 1–5% of real traffic, automatic rollback on guardrail breach
production → full traffic, pinned version, previous version kept warm
🪞
Shadow mode is the cheapest safety net in ML

Run the new model on real production traffic and log its outputs, but act on none of them. It's like a trainee pilot flying alongside the real one. It catches feature skew at serving time, slower responses, unexpected inputs and edge cases that crash the model. Offline evaluation can't see any of these, and users face zero risk. A few days in shadow before every canary should be routine.

Orchestration

A retraining pipeline is a chain of steps where each one needs the previous one's output. For example: validate data → build training set → train → evaluate against incumbent → register. An orchestrator (tools like Airflow, Dagster, Kubeflow or Argo) runs that chain for you. It starts each step when its inputs are ready, retries a step that failed, stops the chain when a gate fails, and records what happened. Without one, the pipeline is a cron job and a shell script, and a failure halfway through leaves half-written outputs nobody notices. These properties separate a good setup from a fragile one:

PropertyWhy it matters for ML pipelines
Idempotent tasksRunning a task twice has the same effect as once, so retries and backfills don't write or count things twice (Chapter 28)

The maturity ladder

The ladder is useful for being honest about where you are and what the next step is. Each level fixes the biggest pain of the one below it. Skipping levels rarely works: automated deployment (level 3) of a model you can't rebuild (level 0) just ships unrepeatable models faster.

Level 0Manual. A notebook produces a model; someone copies a file to a server. Works for one model and one person. None of it survives that person leaving.
Level 1Reproducible training. Training is a script in version control, run on a schedule, logging to a tracker. Deployment is still manual, but you can rebuild the model.
Level 2Automated pipeline. Data validation, training, evaluation and registration run as one orchestrated DAG (a chain of dependent steps). A human decides on promotion, guided by automated gates.
Level 3Continuous training with gates. Triggers start retraining; gates and canaries decide promotion; rollback is automatic. Humans review the unusual cases, not every routine release.
Level 4Platform. Many teams ship models through shared, self-service infrastructure. Monitoring, governance and cost tracking per team are standard (Chapter 39).

Most teams should aim for level 2–3. Level 4 is a whole product in itself. Building it before you have several models in production is a way to avoid shipping any.

⚠️
Common mistakes
  • Testing code but not data. Most ML incidents start upstream, outside your repository.
  • Gates on overall metrics only. A model that improves overall but ruins one slice still passes. And that slice is someone's whole experience.
  • Automated promotion without a canary. Offline gates predict the live result; they don't guarantee it.
  • CI that takes 40 minutes. It gets skipped, and skipping becomes the norm.
  • No fail-closed rule. When validation can't run, a pipeline that carries on anyway ships whatever happened to be there.
  • Retraining because it's Tuesday. Retrain when the data or the world gives a reason. Always compare against the incumbent (the model currently in production).

Interview drill

Warm-up: What does a CI pipeline for an ML repo test that a normal one doesn't?

How a strong answer sounds
Data and model behaviour. Data: check schema, ranges, null rates, volume and freshness against a contract, so an upstream change fails fast. Model: a tiny training smoke test that must reduce loss and produce a model file that loads. Behavioural tests: invariance, expected directions, and checks on known cases. And before promotion, a per-slice comparison with the incumbent plus a train/serve parity check. Ordinary software tests still apply to the transform code. Crucially, training and serving must use the same transform code, and CI should check that too.

Deeper: Design a safe automatic retraining pipeline for a fraud model with 60-day label lag.

How a strong answer sounds
Trigger on a combination: a weekly schedule, plus drift in input distributions, plus an alarm on a proxy metric (a quick stand-in for the real one). True labels are 60 days late, so triggers based on performance alone react two months too slowly. The pipeline validates data and fails closed. It builds the training set with point-in-time joins and a label cut-off that allows for the lag. It trains, then evaluates against a fixed eval set and the incumbent, overall and per slice. It runs a parity check between offline and online features, then registers the candidate. Promotion goes to shadow for a few days, then a 5% canary, then full traffic. The canary rolls back automatically if precision at the threshold or the false-decline rate crosses a limit. Labels arriving later fill in the evaluation, so I can measure afterwards whether each promotion was actually right. That record is what tunes the trigger thresholds over time.

🧠 Key takeaways

  • Code, data and model each change on their own. The pipeline must test all three.
  • Keep per-commit CI under ten minutes. Move heavy evaluation to the stages before promotion.
  • Retraining needs triggers and gates: validation that fails closed, comparison with the incumbent, slices, canary.
  • Shadow mode catches serving-time problems that offline evaluation can't, at zero risk to users.
  • Aim for maturity level 2–3. Having several models justifies a platform; ambition alone doesn't.

Check your understanding

Which test would catch “an upstream team renamed a column and the feature is now all nulls”?

The model still trains and still serves. Only the data changed. So only data validation fails loudly at the right moment.

What is shadow mode?

It shows the new model real production inputs, including skew, latency and edge cases. Users aren't affected, because no traffic depends on it yet.

Your automatic retraining pipeline shipped a broken model at 3am. What was almost certainly missing?

Automation without gates just makes mistakes faster. Every promotion needs conditions that can block it, and a rollback that runs without a human.

Why is a performance-based retraining trigger insufficient when labels arrive 60 days late?

With delayed labels you need early warning signs, combined with a schedule. Examples: input drift, a shift in the spread of predictions, and proxy metrics.

A promotion gate uses only aggregate AUC. What can slip through?

A 4-point gain overall can hide a 20-point loss for new users. Gates must compare each slice against the incumbent.
