Inference & Serving Systems

Training is a project that ends; serving (answering real users' requests) goes on forever. Answering a request happens in two phases. Prefill reads the whole prompt in one go. Decode then writes the answer one token at a time, and each step is limited by how fast weights can be read from memory, not by raw compute.

A serving system is a scheduler wrapped around that decode loop. Its jobs: keep the batch full, keep the KV cache (the model's saved notes about the text so far) tightly packed, and hit the speed you promised. Get this wrong and the model is fine, but the product is unusable.

Measure the right things

Why two phases behave so differently comes down to how often each weight is used once it has been read from memory.

  • Prefill processes all the prompt tokens together. With a 2,000-token prompt, each weight read from memory is used for 2,000 tokens' worth of maths. The GPU's arithmetic units are the limit: prefill is compute-bound.
  • Decode makes one new token per request per step. For an 8B model in bf16, every step reads all 16 GB of weights to produce just one token. On a GPU that reads around 3 TB/s, that alone takes about 5 ms, so one request can't go much faster than ~200 tokens/s however much compute is idle. Decode is memory-bound.

The key consequence: if 64 requests decode together, the weights are read once per step and used for all 64. The step takes only a little longer, but produces 64 tokens instead of one. That is why batching matters so much for serving.

A worked request: queue wait 100 ms, prefill 200 ms, then 400 output tokens at 30 ms each. TTFT = 300 ms. TPOT = 30 ms, about 33 tokens/s. The whole answer takes 0.3 + 400 × 0.03 = 12.3 seconds. Users feel the 300 ms most, because after that they're reading.

⏱️

TTFT

Time to first token: how long until the first word appears. Mostly waiting in the queue plus prefill. This is what makes an app “feel” fast.

⌨️

TPOT / ITL

Time per output token (also called inter-token latency). It sets how fast text streams out. About 25 tokens/s is comfortably faster than people read.

📦

Throughput

Total tokens per second across all users. Your bill grows with this.

👥

Concurrency

How many requests are being worked on at once. Limited by KV-cache memory, not by compute.

⚖️
Throughput and latency pull in opposite directions

Bigger batches use the GPU more efficiently and raise total throughput. But each user waits longer for each token. Every serving decision picks a point between those two. Choose that point from a written latency target, an SLO (service level objective) such as “p95 TTFT < 1s, p95 TPOT < 50ms”, not from a default setting. (“p95” means 95% of requests are at least this fast.)

Batching: static, dynamic, continuous

Requests arrive at different times, and their answers have different lengths. Static batching waits for N requests, then runs them together until all are done. That wastes a huge amount of capacity, because the whole batch keeps running until the longest answer finishes. It's like a bus that can't pick anyone up until every passenger has reached their stop.

A worked example. Four requests start together, with answers of 10, 20, 30 and 100 tokens. Static batching runs 100 steps with 4 slots: 400 slot-steps. Only 10 + 20 + 30 + 100 = 160 of them produce a token, so 60% of the batch's capacity is wasted. And any new request that arrives meanwhile waits up to 100 steps just to start.

Dynamic batching is the middle option: wait a short, fixed time (say 10 ms) or until the batch is full, then run whatever has arrived. It cuts the waiting before a batch starts, and it works well for models that answer in a single pass, like image classifiers or rankers. For LLMs it still has the static problem: once a batch starts, it runs until its longest answer ends.

Continuous batching, in one sentence

After every single decode step, remove finished requests and let waiting ones in, so the batch is always as full as memory allows. It usually gives 2–5× the throughput of static batching at the same latency. It's the most important feature of a modern inference server (vLLM, TensorRT-LLM, TGI and SGLang all do it).

The KV cache is the real constraint

The KV cache stores the attention keys and values for every token so far, so the model doesn't have to reprocess the whole text at each step. Chapter 14 worked out its size: it grows with layers × width × context length × number of requests at once. That causes two problems:

  • Fragmentation: if you reserve room for the maximum possible length for each request, most of that room is never used.
  • Eviction: what do you do when memory runs out halfway through an answer?

Some real numbers. Take a 7B-class model with 32 layers and a width of 4,096, with no GQA, storing the cache in bf16. Each token needs a key and a value in every layer: 2 × 32 × 4,096 × 2 bytes ≈ 0.5 MB per token. A 4,096-token context is then 2 GB for one request. On an 80 GB GPU with ~14 GB of weights, about 64 GB is left, enough for roughly 32 full-length requests.

Now suppose the average request actually uses 1,000 tokens. If you reserve 4,096 tokens of space for each one, about 75% of the reserved cache is never touched, and you fit 32 requests where the memory could have held about 128. That gap is exactly what paging recovers.

Paged attention hands out cache memory in small fixed-size blocks, the way an operating system hands out memory pages. Each request keeps a table of which blocks are its own. Nothing is reserved for tokens that may never be generated. And requests that start with the same text can share blocks, which is how prefix caching works.

Capacity planning

Before launch someone will ask “how many GPUs do we need?” Guess too low and latency collapses at peak; guess too high and you pay for idle hardware. The trick is to plan from tokens, not requests, and to size decode and prefill separately because they are limited by different things.

A worked example by hand. The per-GPU speeds here are made-up round numbers for the arithmetic; in practice you measure them for your model and hardware at your latency target.

  • Traffic: 40 requests/s at peak, 2,000 input and 400 output tokens each.
  • Decode: 40 × 400 = 16,000 output tokens/s. If one GPU produces 2,000 tokens/s while staying under the TPOT target, you need 8 GPUs.
  • Prefill: 40 × 2,000 = 80,000 input tokens/s. A 40% prefix-cache hit rate removes 40% of that, leaving 48,000. At an assumed 20,000 tokens/s per GPU, that's 2.4, so 3 GPUs.
  • Headroom: (8 + 3) × 1.3 ≈ 15 GPUs, so a spike or a failed GPU doesn't break the SLO.

Check memory too. Little's law says the number of requests in progress equals arrival rate × time each one takes: 40/s × ~12 s ≈ 480 requests in flight at once. Each needs KV cache for about 2,400 tokens, so the whole fleet must hold 480 × 2,400 ≈ 1.15 million tokens of cache. If the fleet can't hold that, requests queue no matter how much compute you have.

Scheduling and fairness

When everyone shares one pool of GPUs, a single 100k-token prompt can hold up everyone else. Real schedulers deal with this on purpose.

How bad is it? If a GPU prefills 10,000 tokens per second, a 100k-token prompt keeps it busy for 10 seconds. Without chunking, every other request on that GPU gets no new tokens during those 10 seconds: their answers freeze mid-sentence. With chunked prefill, the long prompt is fed in pieces of, say, 512 tokens, mixed in with the normal decode steps. Its own TTFT gets a little longer, but everyone else keeps streaming.

Prioritise by class

Live chat, background batch jobs and internal testing shouldn't compete as equals. Give them separate queues with weights, or entirely separate GPU pools, so a batch job can never push live chat's p95 latency past its target.

Bound the damage

Split long prefills into chunks, cap the output tokens per request, and only accept as many requests as memory allows. When you're full, shed load: reject quickly with a clear HTTP 429 (“too many requests”) instead of accepting work that will time out. A queue that grows without limit is an outage in slow motion.

🌀
Retries are dangerous here

Say a client gives up on a 30-second answer and retries three times. The server is already overloaded, and now it has triple the work, because the original requests are usually still running. This is the classic retry storm. Defences:

  • Use long, explicit client timeouts.
  • Stop the server-side work when the client disconnects (streaming lets you notice this).
  • Retry only on failures that happen fast.
  • Always add random delay (jitter) to retries, and use a circuit breaker that stops calling a failing service for a while.

Why random? If 1,000 clients all fail at the same moment and each retries after exactly 1 second, all 1,000 retries arrive together and overload the server again. Exponential backoff (wait 1 s, then 2 s, then 4 s) spaces out each client's attempts, and jitter (a random amount added to each wait) spreads different clients apart so they don't arrive in waves.

🚀
Autoscale on queue depth, not utilization

GPU utilization reads close to 100% whenever anything at all is running. So it tells you nothing about whether you have enough capacity. Instead, scale on queue wait time, or on waiting requests per copy of the model. That's what actually drives your latency.

For example, suppose your TTFT target is 1 s and prefill takes 300 ms. Then requests can afford to wait at most about 700 ms in the queue. Set the scale-up trigger well below that, say when the p95 queue wait passes 300 ms, so new capacity arrives before the target is broken.

And remember the cold start: if a new copy takes four minutes to load its weights, you must scale up at least four minutes before the demand arrives. Or keep a warm pool ready.

⚠️
Common mistakes
  • Benchmarking with batch size 1. That measures the worst possible efficiency and tells you nothing about real throughput.
  • Sizing GPUs by the weights alone. The KV cache decides how many requests fit at once. Run out of it and throughput collapses, however much compute you have.
  • Reporting average latency. Users feel the p95 and p99, the slowest requests, and that's where queueing delays show up.
  • No cap on output tokens. One runaway answer holds a slot for minutes.
  • Ignoring cancellation. Users close tabs all the time. Without cancelling the server-side work, you keep paying for answers nobody will read.
  • Putting changing content before the shared prefix. It breaks prefix caching, the cheapest latency and cost win there is (Chapter 19).

Interview drill

Warm-up: Why does continuous batching help so much more for LLMs than for image classifiers?

How a strong answer sounds
Two reasons. First, answer lengths vary wildly, so in a static batch most slots sit idle waiting for the longest one. In image classification, every item finishes in a single pass. Second, decode is limited by memory speed: every step reads all the weights from GPU memory (HBM), whatever the batch size. So adding more sequences to the batch costs almost no extra time and multiplies throughput. Continuous batching takes advantage of both by refilling the batch after every single decode step.

Deeper: p95 TTFT has degraded from 800 ms to 6 s with no traffic change. How do you diagnose it?

How a strong answer sounds
Split TTFT into queue time and prefill time. They have completely different causes.
  • If queue time grew, the server can't accept requests fast enough. Check how full the KV cache is and how often requests get paused (preempted): a few very long contexts can eat the memory that concurrency depends on. Also check whether a batch job started sharing the pool.
  • If prefill time grew, look at input lengths (maybe a client started sending much bigger prompts), the prefix-cache hit rate (a prompt change can break it; this is very common), and whether chunked prefill is on so long prompts don't block others.
Then confirm with per-request logs of input tokens, cache hits, queue time and prefill time. Having those logs is what turns this into a five-minute investigation instead of a day.

🧠 Key takeaways

  • Prefill is limited by compute, decode by memory speed. Measure TTFT and TPOT separately.
  • Continuous batching refills the batch after every decode step. It's the biggest throughput win.
  • The KV cache limits how many requests fit at once. Paging, prefix reuse, GQA and quantization all win space back.
  • Plan GPUs from token volume and a latency target. Autoscale on queue length, with warm pools ready.
  • Design for overload: shed load, cap output length, cancel abandoned work, fall back to smaller models.

Check your understanding

Which metric best reflects “the assistant feels responsive”?

Users judge the app by the wait before anything appears. After that, text only needs to stream faster than they can read.

What primarily limits how many concurrent requests a GPU can serve?

Each request in progress needs cache space in proportion to its context length. Once that memory is full, new requests wait in the queue, however idle the GPU's compute units are.

What does paged attention primarily solve?

Handing out fixed-size blocks only when needed, and sharing blocks between identical prefixes, usually lets several times more requests run at once.

Which autoscaling signal is most appropriate for an LLM serving pool?

GPU utilization hits its maximum straight away, so it can't tell you how much room is left. Queue length maps directly to your latency target. And scale up ahead of demand by at least the time a new copy takes to start.

A client retries after a 10-second timeout while the server is overloaded. What's the risk?

The original request usually keeps running on the server, so each retry adds work without removing any. The defences: long client timeouts, cancelling work on the server, retries with growing random delays, and a circuit breaker.
