Hardware & Numbers for ML

ML systems work keeps asking three questions: will it fit, how fast will it run, and what will it cost? The answers come from a handful of hardware facts and a few multiplications. This last prerequisite explains why GPUs run machine learning, what memory and bandwidth limit, how to count the work in FLOPs, what number formats like bfloat16 and int8 trade away, and the back-of-envelope sums — memory per model, time per training run, tokens per second — that the rest of the course uses constantly.

  • Distinguish memory capacity from memory bandwidth, and say why each limits models

  • Compare float32, float16, bfloat16, int8 and int4 by range, precision and memory
  • Estimate a model's memory for inference and for training

Why hardware numbers matter

In ordinary software, you rarely think about hardware: the program runs, and it's fast enough. ML is different. Models are so large that the hardware sets hard limits on what you can build:

📦

Will it fit?

A model's weights must sit in accelerator memory. If a 70-billion-parameter model needs 140 GB and your GPU has 80 GB, no amount of clever code makes it fit on one card.

⏱️

How fast?

Training time and response latency come from the amount of work (FLOPs) and the rate hardware can do it — or move the data it needs.

💰

What will it cost?

Accelerators are rented by the hour. A training run's cost is roughly GPU-hours × price, which you can estimate before spending anything (Chapter 38).

CPU vs GPU

A CPU has a few (say 8–64) powerful cores, each able to run complicated, branching code very quickly, one step after another. A GPU (graphics processing unit) has thousands of simpler cores that all do the same kind of arithmetic at the same time. GPUs were built to colour millions of pixels in parallel; it turned out that's exactly the shape of ML maths.

CPU vs GPUDiagram

Why the match? A matrix multiplication is millions of independent dot products (P3) — none waits for another, so they can all run at once. Modern GPUs also have special units (NVIDIA calls them tensor cores) that multiply small blocks of matrices in a single instruction. The result: for dense matrix maths, a datacenter GPU is on the order of 100× faster than a CPU. Google's TPUs and other accelerators take the same idea further with chips designed only for matrix maths. Everything else — Python, data loading, the web server around the model — still runs on CPUs.

Counting the work: FLOPs

A FLOP is one floating-point operation: one multiply or one add. “FLOPs” (lowercase s) is a count of them; “FLOP/s” (per second) is a speed. Because ML is mostly matrix multiplication, counting FLOPs is simple arithmetic:

  • A matrix multiply (m, k) @ (k, n) costs about 2 × m × n × k FLOPs (one multiply and one add per term).
  • A forward pass through a network costs about 2 × (number of parameters) FLOPs per input token or example — each weight is used in one multiply-add.
  • Training costs about 3× the forward pass (the backward pass is roughly twice the forward). So training on D tokens costs about 6 × N × D FLOPs, where N is the number of parameters (Chapter 16).

Worked example: a 7-billion-parameter model trained on 1 trillion tokens needs about 6 × 7×10⁹ × 10¹² = 4.2 × 10²² FLOPs. A top datacenter GPU does on the order of 10¹⁵ 16-bit FLOP/s at its peak, but real jobs usually achieve 30–50% of that — a fraction called MFU (model FLOPs utilisation). At 40% of 10¹⁵, one GPU manages 4 × 10¹⁴ FLOP/s, so the run takes 4.2×10²² ÷ 4×10¹⁴ ≈ 10⁸ seconds — about 3.3 years on one GPU, or about 29 hours on 1,000 of them. Try your own numbers:

Number formats: how many bits per number

Every weight and activation is stored as a number in some format. Fewer bits per number means less memory, less data to move and faster maths — but less precision (how many significant digits) and sometimes less range (how big or small a number can be).

Floating-point numbers store three parts, like scientific notation: a sign bit, an exponent (sets the range) and a mantissa (sets the precision). The formats differ in how they share out their bits:

Modern training uses mixed precision: do the heavy matrix maths in bfloat16 for speed, but keep a float32 master copy of the weights and do sensitive sums in float32, so tiny updates don't get rounded away (Chapter 9). Inference can often go lower still: models quantized to int8 or even int4 usually lose little quality while halving or quartering memory (Chapter 27).

Will it fit? Memory arithmetic

The single most useful back-of-envelope sum in this course:

memory for weights = number of parameters × bytes per parameter

A 7-billion-parameter model in bfloat16 needs 7 × 10⁹ × 2 bytes = 14 GB just to hold its weights. Handy shortcut: billions of parameters × bytes per parameter = gigabytes.

Training needs far more. For every parameter you also store its gradient and the optimizer's running statistics. With the popular Adam optimizer and mixed precision, a common rule of thumb is about 16 bytes per parameter: 2 (bf16 weights) + 2 (bf16 gradients) + 4 (fp32 master weights) + 8 (two fp32 Adam statistics). That's 112 GB for the 7B model — before counting activations, the intermediate values saved during the forward pass for use in the backward pass, which grow with batch size and sequence length.

Compute-bound or memory-bound?

A GPU job is limited by one of two things: how fast the cores can do arithmetic (compute-bound), or how fast memory can feed them data (memory-bound). Which one depends on how many FLOPs you do per byte you read, called arithmetic intensity.

Training on big batches is usually compute-bound: each weight, once loaded, is reused for every example in the batch. But generating text one token at a time is the opposite. To produce each token, the model must read all of its weights from memory, yet does only about 2 FLOPs per weight for that one token. The cores sit idle waiting for data.

That gives a lovely estimate. Worked example: a 7B model in bfloat16 is 14 GB. A GPU with 2 TB/s of memory bandwidth can read those weights at most 2,000 ÷ 14 ≈ 140 times per second. So one conversation can get at most about 140 tokens per second, however many FLOPs the chip has. The standard fix is batching: generate tokens for 32 conversations at once, and each weight read serves 32 tokens instead of one. That's why LLM serving is so focused on batching and on shrinking the bytes read per token (Chapter 26).

🧠
Five numbers to carry into the course

(1) Weights: params × bytes (7B in bf16 = 14 GB). (2) Training memory: ~16 bytes/param with Adam. (3) Forward pass: ~2 FLOPs per param per token; training: ~6 × N × D. (4) Real utilisation: ~30–50% of peak. (5) Decode speed per stream ≲ memory bandwidth ÷ model bytes. With these, most “is this feasible?” questions take a minute.

⚠️
Common mistakes
  • Mixing up FLOPs and FLOP/s. One is an amount of work, the other a speed. Time = FLOPs ÷ (FLOP/s × utilisation).
  • Assuming peak speed. Real jobs reach 30–50% of the datasheet number. Estimates at 100% are wildly optimistic.
  • Sizing training by weights alone. Gradients, optimizer state and activations need several times more memory than the weights.
  • Using float16 without care. Values above 65,504 become infinity and tiny gradients round to zero. Prefer bfloat16, or use loss scaling.
  • Expecting more FLOP/s to speed up single-stream text generation. It's usually memory-bound: bandwidth and batching matter more.

Interview drill

Numeracy: Can a 13-billion-parameter model be served in bfloat16 on one 24 GB GPU?

How a strong answer sounds
No. 13 × 10⁹ parameters × 2 bytes = 26 GB for the weights alone, before activations and the KV cache. Options: a larger GPU (an 80 GB card fits it comfortably), splitting it across two GPUs, or quantizing to int8 (about 13 GB) or int4 (about 6.5 GB) at some cost in quality. Doing this sum in your head in the first minute is exactly what interviewers look for.

Estimate: Roughly how many GPU-hours to train a 1B-parameter model on 20B tokens, on GPUs with 10¹⁵ peak FLOP/s at 40% utilisation?

How a strong answer sounds
FLOPs ≈ 6 × N × D = 6 × 10⁹ × 2×10¹⁰ = 1.2 × 10²⁰. Effective speed per GPU = 0.4 × 10¹⁵ = 4 × 10¹⁴ FLOP/s. Time on one GPU = 1.2×10²⁰ ÷ 4×10¹⁴ = 3 × 10⁵ seconds ≈ 83 GPU-hours. So about 10 hours on 8 GPUs, or a few hundred dollars at typical cloud prices — before experiments and restarts.

🧠 Key takeaways

  • GPUs and other accelerators run ML because matrix multiplication is millions of independent multiply-adds done in parallel.
  • Memory capacity decides what fits; memory bandwidth decides how fast weights can be read.
  • Matmul ≈ 2mnk FLOPs; forward ≈ 2 × params per token; training ≈ 6 × N × D. Real utilisation is ~30–50% of peak.
  • float32 = 4 bytes, bf16/fp16 = 2, int8 = 1, int4 = 0.5. bf16 keeps FP32's range; fp16 overflows above 65,504. Mixed precision trains in bf16 with an fp32 master copy.
  • Weights memory = params × bytes; training with Adam ≈ 16 bytes/param plus activations; serving adds the KV cache.
  • Token-by-token generation is memory-bound: tokens/s per stream ≲ bandwidth ÷ model bytes. Batching is the fix.

Check your understanding

About how much memory do the weights of a 7-billion-parameter model need in bfloat16?

bfloat16 is 2 bytes per parameter: 7 × 10⁹ × 2 = 14 GB. float32 would be 28 GB, and full training with Adam at about 16 bytes per parameter would be around 112 GB.

Why are GPUs so much faster than CPUs for neural networks?

Each GPU core is actually simpler than a CPU core. The advantage is massive parallelism, which fits matrix maths perfectly, plus special matrix units like tensor cores.

Training uses float16 and some activations reach 80,000. What happens?

float16 has only 5 exponent bits, so its range tops out at 65,504; larger values become infinity and training breaks. bfloat16 keeps float32's 8 exponent bits and range, which is why it's preferred for training.

Using the 6 × N × D rule, about how many FLOPs does training a 1B-parameter model on 100B tokens take?

6 × 10⁹ × 10¹¹ = 6 × 10²⁰ FLOPs: add the exponents (9 + 11 = 20).

A 14 GB model generates text on a GPU with 3 TB/s of memory bandwidth, serving one user. Roughly what is the upper limit on tokens per second?

Each new token requires reading all 14 GB of weights. 3,000 GB/s ÷ 14 GB ≈ 214 reads per second, so at most about 200 tokens per second for a single stream. Batching many users shares each read and raises total throughput.
