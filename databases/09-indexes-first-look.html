Indexes: A First Look

An index is a second, sorted copy of some columns that points back to the rows, so the database can jump to the rows it needs instead of reading the whole table. It's the single most effective performance tool you have, and the most commonly misused: indexes that are never used, indexes in the wrong column order, and indexes added to fix one read that quietly slow down every write. This chapter is about using them well. How they work inside, page splits and all, is Chapter 13.

Full scan vs index lookup

Without an index on customer_id, SELECT … FROM orders WHERE customer_id = 4242 reads every page of the table and checks every row: a sequential scan. With CREATE INDEX ON orders (customer_id), PostgreSQL builds a B-tree: the customer_id values in sorted order, each with a pointer (the row's physical address, its ctid) to the row in the table. A lookup walks from the root of the tree to the right leaf, reads the matching entries, and fetches just those rows:

Selectivity: when the planner ignores your index

Selectivity is the fraction of rows a condition matches. An index wins when it's small: 100 rows out of 10 million is 0.001%, and the index saves reading 125,000 pages. But each matching row costs a random page read, so as the fraction grows the index loses to a sequential scan. P3 showed the crossover is a few percent at most, and often far lower. PostgreSQL also has a middle option, the bitmap scan: collect all matching row addresses from the index first, sort them by page, then read each needed page once in physical order. You'll see all three in the panel.

So an index on a low-selectivity column, such as status where 90% of orders are 'paid', is useless for WHERE status = 'paid' and excellent for WHERE status = 'pending', which matches 1%. The planner knows the difference because it keeps statistics on the most common values of each column (Chapter 19). If you mostly query the rare value, a partial index is smaller and better: CREATE INDEX ON orders (created_at) WHERE status = 'pending'.

Composite indexes and column order

A composite index on (customer_id, created_at) is sorted by customer_id, and within each customer by created_at, like a phone book sorted by surname then first name. That order decides which queries it can serve:

  • WHERE customer_id = ?: yes, using the leading column.
  • WHERE customer_id = ? AND created_at >= ?: yes, perfectly: jump to the customer, then to the date, read a contiguous range.
  • WHERE customer_id = ? ORDER BY created_at DESC LIMIT 10: yes, and no sort: read 10 entries backwards and stop.
  • WHERE created_at >= ? alone: no, not usefully. Entries for one date range are scattered across every customer, like finding everyone called "Sam" in a phone book sorted by surname.

Cost model: a sequential page read costs 1 unit, a random one 4 (PostgreSQL's defaults); about 300 index entries per leaf page; each extra index adds one B-tree insertion to every INSERT. Real plans also weigh CPU and caching, but choose the same way in these cases.

The write cost

Every index is maintained on every write. An INSERT into a table with five indexes does six insertions: the row plus one entry in each index, each possibly splitting a page, each logged to the WAL and shipped to replicas. An UPDATE that changes an indexed column must add new index entries too. (PostgreSQL can skip index work for updates that touch no indexed column and fit on the same page, a "HOT" update, but only if no index covers the changed column.) Indexes also take disk, memory in the buffer pool, and time in backups and restores. So an index should earn its place: it's used by a query that matters, and nothing else already serves that query.

-- indexes that have never been used since statistics were last reset
SELECT s.indexrelname, pg_size_pretty(pg_relation_size(s.indexrelid)) AS size, s.idx_scan
FROM   pg_stat_user_indexes s
JOIN   pg_index i ON i.indexrelid = s.indexrelid
WHERE  s.idx_scan = 0 AND NOT i.indisunique           -- unique indexes enforce rules even if never scanned
ORDER BY pg_relation_size(s.indexrelid) DESC;

Covering indexes and index-only scans

If an index contains every column a query reads, PostgreSQL can answer from the index without visiting the table at all: an index-only scan. Add returned columns as non-key payload with INCLUDE, so they don't affect the sort order:

CREATE INDEX orders_customer_created_idx
    ON orders (customer_id, created_at) INCLUDE (total_cents, status);

SELECT created_at, total_cents, status          -- every column is in the index
FROM   orders
WHERE  customer_id = 4242
ORDER BY created_at DESC
LIMIT  20;

There's a catch specific to PostgreSQL's MVCC (Chapter 23): the index doesn't know whether a row version is visible to your transaction, so an index-only scan still checks the table's visibility map, and visits the heap for any page not marked all-visible. On a table with heavy recent updates, "index only" can still mean many heap fetches until VACUUM catches up; EXPLAIN ANALYZE reports them as Heap Fetches.

🧹
The index audit that sped up writes

A pattern seen in many production databases: a busy events table accumulates indexes over the years, each added by a different engineer for a different dashboard, until it has eleven, several of them prefixes of others ((user_id) next to (user_id, created_at)) and two unused since the feature they served was removed. Inserts write twelve structures, and the indexes are larger than the table. Querying pg_stat_user_indexes for idx_scan = 0 and checking for redundant prefixes, then dropping them with DROP INDEX CONCURRENTLY after confirming on the replicas too (statistics are per server), routinely cuts write latency and WAL volume noticeably. It's one of the first things the tuning playbook does (Chapter 37).

⚠️
Common mistakes
  • An index per column instead of one composite index shaped like the query.
  • Wrong column order: (created_at, customer_id) for "this customer's recent orders".
  • Indexing low-selectivity columns (booleans, status) for their common values; use a partial index for the rare one.
  • Wrapping indexed columns in functions (lower(email), created_at::date) without a matching expression index.
  • Never removing indexes. Unused and redundant indexes cost every write.

Interview drill

Explain it simply: Why doesn't the database use my index on status for WHERE status = 'paid'?

How a strong answer sounds
Because 90% of rows are paid, so the condition isn't selective. Using the index would mean millions of random heap fetches, while a sequential scan reads every page once in order, which is far cheaper. The planner knows the value distribution from the column statistics. The index would help for 'pending' at 1%, and if that's the main use I'd replace it with a partial index on the pending rows only, which is tiny and stays in cache.

Deeper: Design the index for "a customer's 20 most recent orders, showing date, total and status", on a 500-million-row table.

How a strong answer sounds
CREATE INDEX CONCURRENTLY ON orders (customer_id, created_at DESC) INCLUDE (total_cents, status). Equality column first, then the sort column, so the scan jumps to the customer and reads 20 entries in order with no sort, and stops; INCLUDE makes it an index-only scan, subject to the visibility map. Building it concurrently avoids blocking writes. I'd check whether an existing (customer_id) index becomes redundant and can be dropped, and verify the plan with EXPLAIN (ANALYZE, BUFFERS).

🧠 Key takeaways

  • An index lookup is a short tree descent plus one random heap fetch per matching row.
  • Indexes win for selective conditions; for a large fraction of rows a sequential or bitmap scan is cheaper.
  • Composite index order: equality columns, then one range or sort column, then INCLUDE columns.
  • Every index is paid for on every write, in storage and in memory; drop unused and redundant ones.
  • Covering indexes enable index-only scans, which still consult the visibility map.

Check your understanding

Which query can use an index on (customer_id, created_at) efficiently?

The index is sorted by customer_id first. Equality on it, then a range on created_at, reads one contiguous slice.

90% of orders are 'paid'. The planner does a sequential scan for WHERE status = 'paid' despite an index on status. Is that a mistake?

Low selectivity: nearly every page would be visited anyway, randomly and repeatedly. The sequential scan is the cheaper plan.

What does an index-only scan avoid?

With INCLUDE or key columns covering the query, rows on all-visible pages are answered from the index alone.

A table has five secondary indexes. Roughly how many structures does one INSERT update?

Every index needs an entry for the new row, each a separate B-tree insertion, logged to the WAL.

You have indexes on (user_id) and (user_id, created_at). What can you usually do?

A composite index can be used for its leading column alone. The single-column one is usually redundant, unless it's unique and enforcing a rule.
