Distributed SQL

Sharding, as Chapter 26 left it, makes a database larger by giving the application a harder job. The application has to know the shard key, route each query, do without transactions across shards, and take part in every rebalancing. For a decade the alternative was a NoSQL store that scaled easily and offered no joins and no transactions. Distributed SQL is the attempt to have both: a database that looks like one PostgreSQL or MySQL server to the application, with tables, indexes, joins and serialisable transactions, and that underneath splits its data across many machines, moves it between them and survives the loss of some of them without anyone being woken. Google's Spanner showed it could be done, and CockroachDB, YugabyteDB and TiDB are built on the same plan. This chapter covers that plan and its price.

Ranges and splits

A distributed SQL database stores every table as sorted key-value pairs: the key is the table and its primary key, and the value is the rest of the row. Secondary indexes are more pairs, keyed by the indexed columns. That gives one enormous sorted map, kept on each machine in an LSM tree (Chapter 14). The map is cut into contiguous pieces called ranges (Spanner calls them splits, YugabyteDB tablets, TiDB regions), each covering a span of keys and holding up to a few hundred megabytes.

Ranges are the unit of everything that follows. When a range grows past its size limit, the database splits it in two at a middle key. When one machine holds more than its share, the database moves ranges off it. When a range is unusually busy, it can be split so that the load spreads. None of this involves the application, which is the difference from Chapter 26: the shards are small, numerous, and managed by the database.

One thing does carry over from sharding. The primary key still decides where rows go, and since ranges are spans of sorted keys, a key that only increases, such as a timestamp or a sequence, sends every insert to the last range. That is the right-edge hot spot of Chapter 13, now on a single machine out of fifty. Distributed SQL schemas use random UUIDs or hash-prefixed keys for that reason.

Raft for each range

Each range is stored on several machines, usually three or five, and those replicas have to agree. They do it with a consensus algorithm, most often Raft. In brief: one replica of the range is its leader. Every write goes to the leader, which appends it to a log and sends it to the others. As soon as a majority of the replicas, counting the leader, have the entry on disk, it is committed, and the leader replies. If the leader fails, the remaining replicas elect a new one, and can only elect one that holds every committed entry.

Compare that with Chapter 25. Synchronous replication to one standby loses no data and stops all writes if the standby is down. Asynchronous replication keeps going and can lose recent commits on failover. A majority is the way out of that choice: with three replicas, any one may be lost with no data lost and no pause beyond the election, since the two that remain are still a majority and one of them has everything. The price is that every write waits for one other replica to confirm it, wherever that replica is.

The important design choice is that consensus runs for each range separately. A cluster of fifty machines doesn't hold one fifty-way vote. It runs thousands of small groups of three, each with its own leader and its own log, spread so that the machines share leaders evenly. A machine failing affects only the ranges with a replica on it, and each of those still has two.

Things to notice. Inserting rows splits ranges, and the replicas spread until every machine holds about the same number, with nobody deciding where anything goes. Fail one machine: every range stays available, and the ranges it was leading elect new leaders from their other two replicas. Wait five minutes and those ranges are copied to the surviving machines, back to three replicas each, after which a second failure does no harm either. Now reset and fail two machines at once. The ranges that had two of their three replicas on that pair have lost their majority. They can't elect a leader, can't accept a write, and can't be repaired by waiting, since changing a range's membership is itself a decision that needs a majority. The other ranges carry on normally, so the table is partly available: queries for some keys work and for others hang. Three replicas survive one failure. Surviving two at once takes five replicas, and every write then waits for two confirmations where it waited for one.

Distributed transactions

A write to one row is one Raft write in one range. A transaction that changes rows in two ranges needs something more, since each range commits independently and the transaction must be all or nothing. The underlying method is two-phase commit, with each participant made reliable by its own Raft group. The figure shows CockroachDB's version.

An intent does the work of both a new row version (Chapter 23) and a row lock (Chapter 22). The cost is plain from the figure: a transaction across ranges takes several consensus writes where a single-row write takes one, and each is a network round trip. A transaction that stays within one range can skip the protocol and commit in a single write. That is why schema design in these systems aims to keep rows that change together under a common key prefix, so that they fall in the same range.

Clock skew and TrueTime

MVCC needs to order transactions. On one server that is easy: a counter hands out transaction IDs (Chapter 23). Across fifty machines there is no shared counter, and the obvious substitute, each machine's clock, is wrong by a different amount on each. Suppose a transaction commits on a machine whose clock is 100 ms fast, and a moment later a second transaction starts on a machine whose clock is correct. The second has the lower timestamp, so under MVCC it doesn't see the first, although the first had already finished and told its client so. That is a stale read, and it breaks the promise that a database behaves like one machine.

ApproachHow it orders transactionsThe price
A timestamp oracle (TiDB)One service hands out every timestamp, so they are simply in orderA round trip to it for every transaction, and it works poorly across distant regions

Hybrid logical clocks (CockroachDB, YugabyteDB)Ordinary clocks kept close by NTP, plus a logical counter, and an assumed maximum skew, 500 ms by default in CockroachDB. A read that meets a value stamped within that margin after its own timestamp can't tell which came first, so it restarts at the later timestampOccasional restarted reads, and the guarantee depends on clocks staying within the bound. A node that finds its clock too far out shuts itself down

Spanner's commit wait is worth understanding, since it shows what the clocks are for. If the uncertainty is 4 ms, a transaction waits about that long after choosing its timestamp. By the time its client hears "committed", every clock in the system reads later than that timestamp, so any transaction that starts afterwards must get a higher one and will see the result. The smaller the uncertainty, the shorter the wait, which is why Google spent money on clocks. The systems on ordinary clocks can't wait out half a second on every commit, so they wait only when a read actually runs into an ambiguous value.

When to choose distributed SQL

The benefits are real: writes that scale past one machine, automatic failover with no lost commits, and regions that can be added or lost. So are the costs. Every write pays for consensus, a millisecond or two within one data centre and tens of milliseconds between regions. Queries that a single server answers from memory become fan-outs across machines. Compatibility with PostgreSQL or MySQL is good and incomplete: some extensions, some isolation behaviour, and some performance habits differ. And the operational model is new to most teams.

🛰️
Spanner and F1: Google's advertising business leaves sharded MySQL

Google's advertising system, the source of most of the company's revenue, ran for years on MySQL that had been sharded by hand, by customer. It worked, and it was painful in the way Chapter 26 describes. As customers grew, shards filled and had to be split, and the Spanner paper, published in 2012, records that the last such resharding took over two years of intense effort. Transactions and indexes across shards weren't available, so application code grew its own substitutes. Failover of a shard's primary was a manual procedure in which recent commits could be lost. The engineers considered the NoSQL systems Google already had and rejected them: a billing system couldn't be built on eventual consistency, and they needed SQL. What they built was F1, a SQL layer, on top of Spanner, which supplied the ranges, the consensus group for each range, the transactions across them and the TrueTime clocks described above. The data was replicated synchronously across five data centres on both coasts of the United States. The F1 paper is candid about the cost. A commit took 50 to 150 milliseconds, far slower than MySQL, since every one waited for data centres thousands of kilometres apart. The team accepted that and changed the application to suit: reads were batched and run in parallel, rows that belonged together were stored interleaved under their parent's key so that they shared a range, and work was restructured to make fewer, larger commits. In exchange, resharding stopped being a project, a data centre could be lost without anyone noticing, and the application's developers got transactions and indexes that worked across all the data. Every open-source distributed SQL database since then is a version of this design made to run without Google's clocks.

⚠️
Common mistakes
  • Choosing it for scale that isn't there. A workload that fits on one server runs slower and costs more on five.
  • A sequential primary key. Every insert lands in the last range, and one machine does all the work.
  • Expecting single-server latency. Each write is a round trip to a majority. Across regions that is tens of milliseconds, and no setting removes it.
  • Assuming full PostgreSQL compatibility. Test the actual queries, extensions and transaction patterns before committing to a migration.
  • Three replicas in two data centres. One site holds two of the three, and losing that site loses the majority. Surviving a site failure needs three sites.
  • Neglecting the clocks, on a system whose correctness depends on a bound on their skew.

Interview drill

Explain it simply: How does a database like CockroachDB or Spanner differ from a sharded PostgreSQL setup?

How a strong answer sounds
Both spread data over many machines, but who manages it differs. With manual sharding, the application chooses a shard key and routes queries; each shard is an independent PostgreSQL with its own replicas and failover; there are no transactions or joins across shards unless you build them; and rebalancing is a migration project. A distributed SQL database does all of that inside. It stores tables as a sorted key-value space, cuts it automatically into small ranges, keeps three or five replicas of each range in a Raft group, and splits and moves ranges as data and load change. Any node accepts any query and routes it. Transactions across ranges are ordinary transactions, implemented with two-phase commit over the Raft groups, and failover is automatic with no lost commits, since a write is only acknowledged once a majority has it. The costs are that every write takes a network round trip to a quorum, cross-range transactions take several, some PostgreSQL features are missing, and correctness leans on clock synchronisation. So it buys operational simplicity and stronger guarantees at scale, in exchange for latency and maturity.

Deeper: Why does Spanner need TrueTime? What goes wrong with ordinary clocks?

How a strong answer sounds
Spanner uses MVCC with timestamps, and it promises external consistency: if transaction A commits before transaction B starts, in real time, then B sees A's effects, even if they ran on different machines on different continents. That requires commit timestamps to respect real-time order. With ordinary clocks, machine X might be 50 ms ahead of machine Y; A commits on X at X's time 100, then B starts on Y at Y's time 60, and B reads a snapshot from before A, a stale read after A was acknowledged. A central timestamp service fixes it but adds a round trip and doesn't work well globally. TrueTime instead exposes the uncertainty: TT.now() returns an interval guaranteed to contain true time, kept to a few milliseconds by GPS and atomic clocks in each data centre. On commit, Spanner picks a timestamp no earlier than the interval's upper bound and then waits until TT says that timestamp has definitely passed, the commit wait, before acknowledging. After that, any transaction starting anywhere must get a later timestamp. So the cost is a wait of roughly the uncertainty on each commit, which is why the hardware matters. Systems without it, such as CockroachDB, use hybrid logical clocks with an assumed maximum offset: a read that encounters a value in its uncertainty window restarts at a higher timestamp. That gives serialisable isolation and avoids stale reads as long as skew stays within the bound, and nodes that drift too far remove themselves.

🧠 Key takeaways

  • Distributed SQL stores tables as one sorted key space, cut into small ranges that the database splits and moves by itself.
  • Each range is a consensus group of three or five replicas. A write commits when a majority has it.
  • Three replicas survive one failure with no data lost. Ranges that lose their majority stop, and the rest carry on.
  • Transactions across ranges are two-phase commit over those groups: correct, and several round trips long.
  • Ordering transactions across machines needs trustworthy time: a central oracle, TrueTime's bounded uncertainty, or hybrid clocks with a skew limit.
  • It buys write scale and survivable regions for latency and complexity. Most databases don't need it.

A range has three replicas, on machines 1, 2 and 3. Machines 2 and 3 fail together. What happens to that range?

A lone replica can't know whether it has every committed write. Ranges elsewhere in the cluster are unaffected.

Why does a distributed SQL database run consensus for each range, and not once for the whole cluster?

One cluster-wide group would put every write through a single leader. Thousands of small groups share the work.
