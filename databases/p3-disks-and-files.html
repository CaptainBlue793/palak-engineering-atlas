Disks, Files & Pages

A database is, underneath, a program that keeps data in files and tries very hard not to read them. Storage is slow compared with memory, and how you read it matters as much as how much: reading 1 GB front to back can be faster than fetching a few thousand scattered rows. This chapter gives you the handful of numbers and the one idea, sequential versus random I/O, that explain why databases read in fixed-size pages, why the planner sometimes ignores your index, and why "it was fast in testing" so often means "the data was in memory".

Storage moves blocks, not bytes

Disks don't read a single byte. A hard disk reads whole sectors (512 bytes or 4 KB); an SSD reads whole flash pages (typically 4–16 KB); the operating system moves data in 4 KB memory pages. Asking for one byte costs about as much as asking for the whole block around it. So databases choose a unit of their own, the page (also called a block), and do all reading, caching and writing in whole pages:

  • PostgreSQL: 8 KB pages, fixed when the server is compiled.
  • MySQL InnoDB: 16 KB pages by default.
  • SQLite: 4 KB by default, configurable per database.

Many rows fit in one page. A 100-byte row plus PostgreSQL's 24-byte row header and 4-byte slot pointer means about 60 rows per 8 KB page, so "read one row" really means "read the page that holds it, and get its neighbours for free". That's why rows that are used together should live together, a theme that runs from Chapter 11 (page layout) to Chapter 28 (column stores).

SHOW block_size;                              -- 8192
SELECT pg_relation_filepath('products');         -- base/16384/16390: database 16384, file 16390
SELECT pg_size_pretty(pg_relation_size('products'));  -- size of the table's main file

Each table and each index is its own file under the data directory, split into 1 GB segment files once it grows past that (16390, 16390.1, 16390.2…). Page n of a table is simply the 8 KB starting at byte n × 8192 of that file.

The numbers to remember

Order-of-magnitude figures for reading one 8 KB page when nothing else is happening (queue depth 1), and for streaming large files. Real devices vary by 2–3×, but the ratios are what matter:

HDD, 7,200 rpmSATA SSDNVMe SSDRAM (page cache hit)
One random 8 KB read~8 ms (seek + half a rotation)~0.1 ms~0.08 ms~0.002 ms
Random reads per second, one at a time~120~10,000~12,000~500,000
Random reads per second, many in parallel~200~90,000500,000+millions
Sequential read~180 MB/s~550 MB/s3–7 GB/s~10 GB/s+
Random ÷ sequential cost per page~180×~7×~30× (one at a time)small

Two lessons fall out. First, random I/O on a spinning disk is brutal: the head has to move and wait for the platter, so each scattered read costs milliseconds, while streaming costs microseconds per page. Second, SSDs narrow the gap but don't close it, especially for reads that depend on each other. Walking an index is a chain: you can't fetch the next page until you've read the pointer in this one, so you get the queue-depth-1 latency, not the impressive parallel IOPS figure on the box.

Sequential vs random: the calculation

Suppose a 10-million-row table of 100-byte rows: about 160,000 pages, 1.3 GB. You want some of its rows. Two strategies:

  • Random: look each row up (through an index) and read its page. Cost ≈ rows wanted × random read latency, since in the worst case every row is on a different page.
  • Sequential: read the whole table front to back and keep the rows you want. Cost ≈ table size ÷ sequential throughput, no matter how many rows you keep.

The random cost grows with the number of rows; the sequential cost is flat. They cross at a surprisingly small fraction of the table. Drag the slider and switch devices:

Model: every wanted row sits on a different page, read one at a time (queue depth 1); the scan streams the whole table at the device's sequential throughput. Real planners also count CPU, caching and prefetching, but this is the shape of their reasoning.

On a hard disk, fetching just a few hundred scattered rows already costs as much as reading the entire gigabyte. That's the origin of a rule you'll meet in Chapter 9: an index helps when a query wants a small fraction of a table, and past some point the planner rightly prefers a full scan. PostgreSQL encodes the ratio in two settings, seq_page_cost = 1 and random_page_cost = 4; the default of 4 (not 180) already assumes most random reads will be served from cache.

The OS page cache: a second cache you didn't ask for

When PostgreSQL reads a page it calls the operating system's read() (or pread()). Linux doesn't go straight to the device: it first checks its page cache, the spare RAM it uses to keep recently read file data. The page cache is why benchmarks lie. Run a query twice and the second run is fast because the table is now in RAM. To measure cold performance on Linux you have to empty it (sync; echo 3 | sudo tee /proc/sys/vm/drop_caches) and restart PostgreSQL to empty shared_buffers too. EXPLAIN (ANALYZE, BUFFERS) tells you how many pages came from shared_buffers ("hit") and how many had to be requested from the OS ("read"); Chapter 17 uses that constantly.

Seeing it for yourself

A small Python script makes the difference concrete. It reads 8 KB blocks from a large file in order, then at random offsets. Drop the caches first, or both runs will be served from RAM:

import os, random, time

PAGE = 8192
fd = os.open("big.bin", os.O_RDONLY)          # create it first: a few GB of anything
pages = os.fstat(fd).st_size // PAGE

def read_pages(order, n=20_000):
    start = time.perf_counter()
    for p in order[:n]:
        os.pread(fd, PAGE, p * PAGE)
    return time.perf_counter() - start

seq = read_pages(range(pages))
rnd = read_pages(random.sample(range(pages), 20_000))
print(f"sequential {seq:.2f} s, random {rnd:.2f} s, ratio {rnd / seq:.0f}x")

On a laptop NVMe drive you'll typically see random reads several times to a few tens of times slower per page; on a hard disk, a hundred or more. Run it a second time without dropping the caches and the gap nearly disappears: everything is in RAM.

⚙️
Telling the planner it's running on SSDs

PostgreSQL's default random_page_cost = 4.0 dates from spinning disks, and assumes about 90% of random reads are cache hits. On a database that lives on NVMe, or whose working set fits in RAM, that overstates the price of index lookups, and the planner chooses sequential scans and hash joins that are slower than the index plans it rejected. A common, well-documented tuning step for SSD-backed servers (managed services often ship it as a default) is ALTER SYSTEM SET random_page_cost = 1.1; followed by SELECT pg_reload_conf();. It's a one-line change, but it's a change to every query plan, so compare EXPLAIN ANALYZE output for your top queries before and after (Chapter 37).

⚠️
Common mistakes
  • Benchmarking warm and calling it representative. The second run reads from RAM. Report cold and warm numbers separately.
  • Treating SSDs as random-access-for-free. Dependent reads (index walks, nested loops) pay full latency each time.
  • Quoting parallel IOPS for a single query. One backend walking a B-tree issues one read at a time.
  • Assuming "one row" means a small read. The unit is the page, so a query touching 1,000 rows on 1,000 different pages reads 8 MB.

Interview drill

Explain it simply: Why can reading a whole 1 GB table be faster than using an index to fetch 5,000 rows from it?

How a strong answer sounds
The index fetches each row with a random read, and those 5,000 rows are probably on 5,000 different pages. On a hard disk that's about 5,000 × 8 ms = 40 seconds; reading the whole table sequentially at ~180 MB/s takes about 6 seconds. Sequential throughput is so much higher than random IOPS that scanning everything wins once you want more than a small fraction of the rows. On SSDs the crossover moves, but it exists, which is why the planner sometimes ignores an index on purpose.

Deeper: A query takes 3 seconds the first time and 40 ms afterwards. What's going on, and how do you measure it properly?

How a strong answer sounds
The first run read pages from storage; afterwards they're in PostgreSQL's shared_buffers and the OS page cache. EXPLAIN (ANALYZE, BUFFERS) shows it: "read" counts on the first run, "hit" counts on the second. To decide which number matters, ask whether production keeps that data hot: a dashboard query over today's data is warm, a monthly report over old partitions is cold. For a cold measurement, drop the OS cache and restart the server; for a realistic one, run it under production-like load with a production-sized dataset.

🧠 Key takeaways

  • Databases read, cache and write whole pages: 8 KB in PostgreSQL, 16 KB in InnoDB.
  • Each table and index is a file; page n sits at offset n × 8192.
  • Random reads cost far more than sequential ones: ~180× on HDD, still several times or more on SSD.
  • A full sequential scan beats per-row random reads once you want more than a small fraction of the table.
  • Pages are cached twice, in shared_buffers and the OS page cache, so warm benchmarks hide I/O.

Check your understanding

What is the size of a PostgreSQL page, the unit it reads and writes in?

PostgreSQL uses 8 KB blocks (SHOW block_size returns 8192). InnoDB's default is 16 KB.

Roughly how long does one random 8 KB read take on a 7,200 rpm hard disk?

Average seek is around 4 ms and half a rotation at 7,200 rpm is about 4.2 ms, so roughly 120 random reads per second.

Why doesn't an NVMe drive's "500,000 IOPS" apply to a single query walking a B-tree index?

The headline IOPS figure needs many requests in flight. A tree walk can't ask for the child page until it has read the parent, so it sees the queue-depth-1 latency.

A query's second run is 50× faster than its first. What is the most likely reason?

The first run paid for reads from storage; the second found the pages in memory. EXPLAIN (ANALYZE, BUFFERS) shows the shift from "read" to "hit".

On disk, what is a PostgreSQL table?

Each table and index has its own relation file; pg_relation_filepath() tells you where. Files over 1 GB continue in .1, .2 … segments.
