Vector Databases

The search of the last chapter matches words. A question such as "how do I stop my database from running out of connections?" should find an article on connection pooling that shares almost none of its words. Machine-learning models make that possible by turning a piece of text, an image or a song into a list of a thousand or so numbers, an embedding, arranged so that things with similar meaning get similar numbers. Finding related items then becomes a geometric problem: given a point in a space of a thousand dimensions, find the points nearest to it, among a hundred million, in a few milliseconds. No index from the earlier chapters can do that. This chapter covers why, and the approximate indexes that can.

Embeddings and distance

An embedding is a vector, a fixed-length list of floating-point numbers, produced by a model from some input. The model is trained so that inputs people would call similar come out close together. The individual numbers mean nothing. Only the distances between vectors carry information.

embed("How do I stop running out of database connections?")  →  [ 0.021, -0.447, 0.309, … 1,536 numbers ]
embed("Connection pooling with PgBouncer")                  →  [ 0.018, -0.431, 0.322, … ]     # close
embed("A recipe for lemon drizzle cake")                    →  [ -0.502, 0.117, -0.084, … ]    # far

Exact vs approximate search

The query is always the same: the k nearest neighbours of a given vector. The exact method compares the query with every stored vector and keeps the best k. It is simple and always right, and it costs one distance computation for every row: for a million vectors of 1,536 dimensions, a billion and a half multiplications for each query, about a second on one core.

The indexes of earlier chapters can't shorten this. A B-tree needs one ordering, and a thousand dimensions have none. Structures that carve up space, as GiST does for maps, work well in two or three dimensions and fail in a thousand: almost every region ends up close to the query in at least one dimension, so nearly all of them have to be searched. This effect has the name the curse of dimensionality.

The way out is to stop demanding the exact answer. An approximate nearest neighbour index returns k vectors that are very probably the nearest, after looking at a small part of the data. Its quality is measured by recall: of the true k nearest, the fraction it returned. An index tuned to 95% recall finds 19 of the true top 20, a hundred times faster than a scan. For search and recommendation, where the embedding is itself only a rough guide to relevance, missing one result in twenty is acceptable.

IVF and product quantisation

The first approximate method is to sort the vectors into groups in advance and search only the nearest groups. An inverted file index, IVF, runs a clustering algorithm over the data to find a few hundred or thousand centroids, and assigns each vector to its nearest centroid's list. To search, compare the query with the centroids, pick the closest few lists, and scan only the vectors in those. The number of lists searched, nprobe, sets the balance between speed and recall.

Things to notice. Inside a cluster, searching one list examines about a sixth of the vectors and returns all five true neighbours, since the query's neighbours all belong to the same list as the query. Put the query between two clusters, and the nearest list holds four of its five neighbours. The fifth is just across the boundary in a list that wasn't searched, so recall falls to 80%, and the index reports nothing: it returns five vectors as usual, one of them wrong. Searching two lists finds the missing one, at about twice the work. Click round the plot and you will find places where a single list misses two or three. This is the trade every approximate index offers. Recall is bought with work, and the queries that suffer are the ones near a boundary.

Quantisation addresses the other cost, memory. Product quantisation cuts each vector into, say, 96 pieces, and replaces each piece with a one-byte code naming the most similar of 256 typical pieces learned from the data. A 6 kB vector becomes 96 bytes. Distances computed from the codes are approximate, so the index uses them to pick a few hundred candidates and then re-ranks those with the full vectors. A simpler form stores each number as one byte, which quarters the size for a small loss.

HNSW

The method that currently gives the best recall for a given speed is a graph. In a hierarchical navigable small world index, HNSW, every vector is a node connected to a few of its nearest neighbours. A search starts at some node, looks at its neighbours, moves to whichever is nearest the query, and repeats until none is nearer. Greedy walking like this would take many steps across a large graph, so HNSW adds layers: a sparse top layer with long connections for covering distance quickly, and denser layers beneath for closing in, as express and stopping services do on a railway.

pgvector

PostgreSQL does all of this through the pgvector extension, which adds a vector type, the distance operators and both kinds of index.

CREATE EXTENSION vector;
ALTER TABLE articles ADD COLUMN embedding vector(1536);

CREATE INDEX ON articles USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

SET hnsw.ef_search = 100;                               -- larger: better recall, slower
SELECT article_id, title, embedding <=> $1 AS distance
FROM articles
WHERE published AND language = 'en'                    -- an ordinary filter, in the same query
ORDER BY embedding <=> $1                              -- the index serves this ORDER BY … LIMIT
LIMIT 5;

Keeping vectors in the same database as the rest of the data has the advantages Chapter 31 listed for full-text search: one system, one transaction, and ordinary SQL for filters and joins. Filters are also where care is needed. The index returns the nearest candidates and the WHERE clause is applied to them afterwards, so a filter that rejects most rows can leave fewer than five results. For very selective filters an exact scan of the matching rows is often both faster and correct, and the planner will choose it if a B-tree index on the filter column makes it cheap. A dedicated vector database becomes worth its cost at hundreds of millions of vectors, or when vector search is the product itself and its memory and tuning deserve their own machines.

Vector search and keyword search fail in opposite ways. Embeddings find related meaning and miss exact strings such as an error code or a part number. Keyword search finds the exact string and misses a paraphrase. Production systems usually run both and merge the two rankings, which is called hybrid search.

Spotify: nearest neighbours for a hundred million tracks

Spotify's recommendations rest on vectors. Models trained on listening histories give every track, artist and listener a vector, such that tracks which the same people play end up close together, and "more like this" is a nearest-neighbour query. In 2013 an engineer there, Erik Bernhardsson, wrote a library for that query and released it as Annoy. Its index was a forest of trees: each tree splits the space in two with a random plane, then splits each half again, down to small groups, and a search descends several trees and pools the candidates from the leaves it reaches. Annoy had one property that mattered a great deal in production. Its index was a file that many processes could map into memory and share, so a service could load a large index at once and serve it from every core. It ran inside Spotify for a decade and was adopted widely outside. By 2023 the number of tracks and the size of the vectors had both grown, and graph indexes had overtaken trees in every benchmark. Spotify replaced Annoy with a new library, Voyager, built on HNSW, and reported that it was more than ten times faster at the same recall and used about a quarter of the memory. The two libraries a decade apart show how the field moved from space-partitioning trees to graphs. They also show that the vectors and the index are separate concerns: the index is disposable, and can be rebuilt with a better algorithm from the same vectors.

⚠️
Common mistakes
  • Using a different distance from the one the model was trained with. The rankings come out subtly wrong.
  • Never measuring recall. An approximate index gives no error when it misses. Compare it with exact search on a sample of real queries.
  • Building an IVF index on an empty or tiny table. The centroids are chosen from the data present at the time.
  • Mixing embeddings from two models, or two versions of one, in a column. Their spaces are unrelated, and distances between them mean nothing.
  • A selective filter with an approximate index, and surprise at getting two results where five were asked for.
  • Expecting embeddings to find exact identifiers. Combine them with keyword search.

Interview drill

Explain it simply: What is a vector database, and why can't an ordinary index do its job?

How a strong answer sounds
A vector database stores embeddings, fixed-length arrays of floats produced by a machine-learning model so that similar items have nearby vectors, and answers nearest-neighbour queries: given a query vector, return the k stored vectors closest to it by cosine or Euclidean distance. That powers semantic search, recommendations and retrieval for language models. An ordinary index can't serve it, because a B-tree relies on a total order, and there is no ordering of thousand-dimensional points that keeps neighbours together; spatial trees that work in two or three dimensions degrade in high dimensions until they visit nearly everything. Exact search means computing the distance to every vector, which is linear in the collection. So vector indexes are approximate: they organise the vectors so that a query examines a small fraction, by clustering them into lists and searching the nearest lists, as IVF does, or by building a proximity graph and walking it greedily, as HNSW does, and they return the true nearest neighbours with high probability, not certainty. Quality is measured as recall, and each index has a parameter trading recall against latency.

Deeper: Compare IVF and HNSW. How would you choose between them, and tune the one you chose?

How a strong answer sounds
IVF partitions the vectors with k-means into lists around centroids; a query finds the nearest centroids and scans only those lists. HNSW builds a multi-layer graph in which each vector links to near neighbours, and searches by greedy descent from a sparse top layer to the full bottom layer. HNSW generally gives a better recall-to-latency curve and needs no training data, so it can be built on an empty table and handles inserts incrementally; its costs are memory, since the graph plus the vectors want to be in RAM, slow builds, and awkward deletes. IVF builds quickly and is compact, especially with product quantisation, but its centroids must be trained on representative data and go stale as the distribution shifts, and its recall drops for queries near list boundaries unless more lists are probed. I'd default to HNSW up to tens of millions of vectors if memory allows, and to IVF with quantisation when memory is the constraint or the corpus is very large. For tuning HNSW: m, the links per node, and ef_construction set graph quality at build time; ef_search at query time is the main dial, and I'd raise it until recall on a held-out set of real queries, measured against exact search, reaches the target, then check latency. For IVF: lists around the square root of the row count, and probes raised until recall is acceptable. Either way I'd measure recall rather than assume it, re-check after the data grows, and watch what filters do, since post-filtering can starve the result set.

🧠 Key takeaways

  • An embedding is a vector whose distance to other vectors reflects similarity of meaning. Use the distance measure its model was trained with.
  • Exact nearest-neighbour search compares the query with every vector. Ordered and spatial indexes don't help in high dimensions.
  • Approximate indexes examine a fraction of the data and are judged by recall, which they trade against speed.
  • IVF clusters vectors into lists and searches the nearest few. Queries near a boundary are the ones it gets wrong.
  • HNSW walks a layered graph of neighbours. It has the best recall for its speed, and costs memory and build time.
  • pgvector keeps vectors beside the rest of the data, with SQL filters. Measure recall, and combine vector search with keyword search.

Check your understanding

Why can't a B-tree index answer "the 10 vectors nearest to this one"?

Two vectors can be close overall and far apart in whichever dimension the index sorted on first.

An approximate index has a recall of 90% for k = 10. What does that mean?

It always returns ten vectors. On average one of them is a slightly more distant vector than the one it missed.

In an IVF index, which queries are most likely to miss true neighbours?

Searching more lists recovers them, for more work.

What does raising ef_search do in an HNSW index?

It is the query-time dial between accuracy and speed.

A pgvector query has WHERE tenant_id = 42 … ORDER BY embedding <=> $1 LIMIT 10, and tenant 42 owns 0.1% of the rows. It returns 3 rows. Why?

For a filter this selective, scanning the tenant's own rows exactly is faster and complete.
