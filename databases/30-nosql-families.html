NoSQL Families

"NoSQL" names a set of databases by what they are not, which says little about what they are. There are four distinct families under the name: key-value stores, document stores, wide-column stores and graph databases. Each grew from a particular problem that relational databases of the 2000s handled badly, and each made a different bargain: give up joins, or fixed schemas, or transactions across records, and get something in return, usually the ability to spread over many machines without the application having to manage it. This chapter describes each family's data model, what it makes easy and what it makes hard, and how to decide whether one of them fits, which for most new systems it doesn't.

What was traded

In the mid-2000s the largest websites had more data and more traffic than one database server could hold, and relational databases offered no way to spread a database over many machines except sharding by hand (Chapter 26). Once a database is sharded by hand, its joins and transactions across shards are gone anyway. Google and Amazon each built stores that began from that position, described in two papers, Bigtable in 2006 and Dynamo in 2007, from which most of this field descends.

Given upBecauseGained
JoinsThe rows to be joined may be on different machinesEvery read goes to one machine, located by a key
Transactions across recordsThey need coordination between machinesWrites that never wait for another machine's agreement
A fixed schemaChanging a schema on a thousand machines is slowRecords of different shapes side by side
Strong consistency, in someAgreeing on one answer takes time, and fails during network faultsThe database stays writable when machines or links are down
Ad hoc queriesWithout joins and a planner, only the designed access paths are fastPredictable speed for those paths, at any size

The bargain has shifted since. Most of these systems have added transactions, secondary indexes and query languages that resemble SQL, and relational databases have added JSON columns and built-in sharding (Chapter 36). What is left to tell them apart is the data model.

Key-value

The simplest model there is: a key and a value, with three operations, put, get and delete. The store doesn't look inside the value. It is a hash table that survives restarts and may span machines.

SET  session:9f3a2c  '{"user_id":42,"cart":[17,93]}'  EX 1800      # Redis: a value that expires in 30 minutes
GET  session:9f3a2c
INCR page:home:views                                          # an atomic counter
ZADD leaderboard 3150 "alice"                                 # Redis also offers lists, sets and sorted sets as values

Everything is found by its key and by nothing else. There is no "find the sessions for user 42" unless you maintain that list yourself under another key. In return, a lookup takes a few microseconds, and the data spreads over machines trivially, since the key says where it lives. Key-value stores hold sessions, caches (Chapter 33), counters, rate limits and feature flags. Redis, Memcached and DynamoDB at its simplest are the usual examples, and RocksDB is the same thing as a library.

Document

A document store also maps a key to a value, and it understands the value: a document, usually JSON, with nested objects and arrays. It can index fields inside documents and query by them.

db.posts.insertOne({                                 // MongoDB
  _id: "p1001", author_id: 42, title: "B-trees", tags: ["postgres", "indexing"],
  comments: [                                           // embedded: read with the post in one fetch
    { user: "bob",  text: "Clear, thanks",  at: ISODate("2026-10-07T09:14:00Z") },
    { user: "carol", text: "What about GIN?", at: ISODate("2026-10-07T09:20:00Z") }
  ]
})
db.posts.createIndex({ tags: 1 })
db.posts.find({ tags: "indexing" }).sort({ _id: -1 }).limit(10)

The unit of design is the document: things that are read and written together are stored together, so that showing a post with its comments is one read and no join. The central decision is whether to embed related data in the document or to reference it by id. Embedding is right when the related data belongs to one parent and is bounded in size. Referencing is right when it is shared or grows without limit, and then the application does the join itself with a second query. Documents in a collection needn't have the same fields, which helps while a product is changing quickly and hurts later, since the schema still exists and is now enforced only by the application's code. MongoDB, Couchbase and Firestore are document stores, and so, in effect, is a PostgreSQL table with a jsonb column.

Wide-column

A wide-column store, in the line of Bigtable, looks like a table and behaves like a sorted map spread over many machines. Each row has a partition key, which decides the machine, and a clustering key, which decides the order of rows within the partition. A read names a partition and gets back a contiguous run of its rows.

CREATE TABLE posts_by_author (                       -- Cassandra's CQL
  author_id  bigint,
  created_at timestamp,
  post_id    uuid,
  title      text,
  PRIMARY KEY ((author_id), created_at, post_id)       -- partition key: author_id. Then sorted by time
) WITH CLUSTERING ORDER BY (created_at DESC);

SELECT title FROM posts_by_author WHERE author_id = 42 LIMIT 20;   -- one partition, the first 20 rows: fast at any scale
SELECT title FROM posts_by_author WHERE title = 'B-trees';         -- refused: it would have to scan every machine

The design method is the reverse of the relational one. Normalisation (Chapter 7) starts from the data and lets queries be written later. Here you start from the queries. You list every question the application will ask, and create one table for each, with a key that makes that question a read of a single partition. The same post is written to posts_by_author, posts_by_tag and posts_by_id. Writes are cheap, since these stores are LSM trees (Chapter 14), and data is duplicated freely. A question nobody planned for has no table, and can't be answered without an export to another system. Cassandra, ScyllaDB, HBase and Bigtable belong here, and Chapter 45 follows one in production.

Graph

A graph database stores nodes and the edges between them, both with properties, and is built for queries that follow edges: who knows whom, what depends on what, how to get from here to there.

// Cypher, Neo4j's query language: people two steps from Alice who like a topic she likes
MATCH (a:Person {name: 'Alice'})-[:FRIEND]->()-[:FRIEND]->(fof:Person),
      (a)-[:LIKES]->(t:Topic)<-[:LIKES]-(fof)
WHERE fof <> a
RETURN fof.name, collect(t.name) LIMIT 10

In a relational database each step along an edge is a join against the whole friendships table, and a query five steps deep is five joins of a very large table with itself. A graph database stores with each node direct references to its neighbours, so a step costs in proportion to the number of neighbours the node has, whatever the size of the graph. For deeply connected questions, such as fraud rings, recommendations and network dependencies, the difference is orders of magnitude. For anything else a graph database has no particular advantage, and it is the hardest of the four to spread across machines, since there is no good way to cut a graph in pieces.

    "Natural" means the model does it directly and it stays fast as the data grows. "Workable" means it needs something extra that you must build and keep correct: a second copy of the data, an index maintained by hand, or a query that slows with size.     Things to notice. The relational database is natural for five of the seven and workable for a sixth, and only spreading heavy writes over many machines is outside what it does by itself. Every other model is better than it at one or two things and worse at several. The key-value store is unbeatable for a lookup by key and has no answer for "posts with this tag" unless the application keeps its own index. The wide-column store handles enormous write volumes and answers exactly the questions its tables were built for. The graph database is the only one where friends of friends is natural. This is the general pattern: a specialised store gives up generality in exchange for being very good at one access pattern, and it is the right choice only when that pattern dominates the application.

    🛒
    
    
    Dynamo: a shopping cart that can always be written to
    In 2004 Amazon had outages during the holiday season in which customers could not add items to their shopping carts. The carts were in a relational database, and when a database server or the network to it failed, writes to it failed, as a database that promises consistency must make them. Amazon's engineers concluded that for this particular data the promise was the wrong one. An "add to cart" that is refused is a lost sale. An "add to cart" that is accepted on one machine while another machine is unreachable can be reconciled a moment later, and the worst result is that an item the customer had removed comes back. They built Dynamo, described in a paper in 2007, round a single requirement: the store must accept a write whenever any of its machines can be reached. To get that, they gave up nearly everything else. Dynamo was a key-value store with no joins, no transactions and no queries by value. Each key was hashed onto a ring of machines and copied to several of them. A write succeeded once a configurable number of copies had it, and if machines were cut off from each other, each side went on accepting writes, with the application merging the versions afterwards, by taking the union of the two carts. Reads could return stale data, and occasionally two versions at once. For a shopping cart that was a good trade. For an account balance it would have been a terrible one, and Amazon kept using relational databases for those. The paper's lasting influence, through Cassandra, Riak and Amazon's own DynamoDB, was the idea that consistency could be chosen for each kind of data according to what a failure costs.
    
  
    

  
    ⚠️
    Common mistakes
    
    
      
      
    • Choosing NoSQL "to scale" a product that has a thousand users. The scale problem is hypothetical, and the missing joins and transactions are felt at once.
      • 
      
    • "Schemaless" taken to mean there is no schema. It has moved into the application, where nothing enforces it and old records have old shapes.
      • 
      
    • Modelling a wide-column table like a relational one. Start from the queries. A table that no query can address by partition key is useless.
      • 
      
    • Unbounded arrays inside documents. A post with a million embedded comments exceeds size limits and is rewritten whole on each new comment.
      • 
      
    • Relational data forced into a document store, with joins reimplemented in the application, slowly and without consistency.
      • 
      
    • Five kinds of database for one product. Each must be operated, monitored, backed up and kept in step with the rest.

    Interview drill
    
    
    Explain it simply: What are the main types of NoSQL database, and what is each for?
    
    
    How a strong answer sounds
    Four families. Key-value stores, such as Redis and DynamoDB in its simplest use, map a key to an opaque value with get, put and delete; they are the fastest and simplest to scale, and are used for caches, sessions and counters, but you can only look things up by key. Document stores, such as MongoDB, hold JSON-like documents and can index and query fields inside them; they suit self-contained records with nested or varying structure, read and written as a unit, and are weak at relationships between documents. Wide-column stores, such as Cassandra and HBase, organise rows into partitions by a partition key and sort them within a partition by a clustering key; they handle very high write volumes across many machines and serve queries that read a slice of one partition, and you design one table per query. Graph databases, such as Neo4j, store nodes and edges and are optimised for traversing relationships many hops deep. What they share historically is trading joins, cross-record transactions and ad hoc querying for horizontal scale and availability; that boundary has blurred, and I'd still start with a relational database unless one of these access patterns clearly dominates.
    
    
    Deeper: When would you choose Cassandra over PostgreSQL, and how does data modelling differ?
    
    
    How a strong answer sounds
    I'd choose Cassandra when the workload is write-heavy beyond what a single primary can absorb, the data is naturally partitioned by a key such as user, device or channel, the read queries are few and known in advance, and availability across nodes and data centres matters more than transactions: messaging history, event and sensor data, activity feeds. It scales writes linearly by adding nodes, has no single primary to fail over, and its LSM storage makes writes cheap. I'd stay with PostgreSQL when I need joins, multi-row transactions, constraints, or the ability to ask new questions of the data, and when the volume fits one machine with replicas, which covers most applications. The modelling is inverted. In PostgreSQL I normalise the data and let the planner serve whatever queries come later. In Cassandra I start from the queries: for each one I design a table whose partition key identifies the single partition that answers it and whose clustering columns give the required order, so each query is one sequential read on one replica set. That means denormalising, writing the same fact to several tables, and maintaining them in application code. I also have to bound partition sizes, for example by adding a time bucket to the partition key, avoid patterns that create many tombstones, and choose consistency levels per query. And I give up ad hoc analysis, which I'd do by exporting to a warehouse.
    
  
    

  
    
    
    🧠 Key takeaways
    
    
      
      
    • NoSQL is four families with different data models. Each trades away generality for one kind of access.
      • 
      
    • Key-value stores do lookups by key, very fast, and nothing else.
      • 
      
    • Document stores keep whole records together as nested documents. Embed what is owned and bounded, and reference the rest.
      • 
      
    • Wide-column stores serve slices of a partition at any scale. Tables are designed from the queries backwards, with data duplicated across them.
      • 
      
    • Graph databases make each step along a relationship cheap, whatever the size of the data.
      • 
      
    • Start with a relational database, and add a specialised store when a specific access pattern demands it.
