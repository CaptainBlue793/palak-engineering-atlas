Deadlocks in Databases

Two transactions each hold a lock the other needs. Neither can go on until the other lets go, and neither will let go until it has gone on. Left alone they would wait for ever. A database doesn't leave them alone: it notices the cycle, picks one transaction, and aborts it with an error so that the other can finish. So a deadlock in a database is an error that some request receives now and then, and it isn't a hang. In the logs it looks like a failure in the database, and the cause is nearly always in the application: two pieces of code that take the same locks in different orders. This chapter reproduces one, shows how the database finds it, and gives the rule that prevents it.

A deadlock reproduced

Alice sends Bob £10 at the same moment as Bob sends Alice £5. Each transfer debits the sender's row and then credits the receiver's.

ERROR:  deadlock detected
DETAIL:  Process 20417 waits for ShareLock on transaction 8841; blocked by process 20988.
         Process 20988 waits for ShareLock on transaction 8840; blocked by process 20417.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,2) in relation "accounts"

The message describes the cycle exactly: who waits for whom, all the way round. The server's log adds the statement each process was running. Between them they identify the two code paths involved, which is all the information needed to fix it.

Wait-for graphs and detection

The database keeps, in effect, a wait-for graph: a node for every transaction, and an arrow from each waiting transaction to the one holding the lock it wants. Ordinary waiting is a chain of arrows that ends at a transaction which is running and will finish. A deadlock is a cycle, a path of arrows that leads back to where it began, and nothing in a cycle is running.

ApproachHow it worksUsed by
Detect after a delayA transaction that has waited for deadlock_timeout, 1 second by default, searches the graph for a cycle through itself. If it finds one it aborts itselfPostgreSQL. Most waits end in milliseconds, so the search is rarely needed
Detect at onceThe graph is checked whenever a transaction starts to wait. The victim is the transaction that has changed the fewest rowsMySQL InnoDB
Time outNo graph. A transaction that waits longer than a limit is aborted, deadlock or notInnoDB with detection turned off, and many distributed systems
PreventTransactions carry timestamps. An older one that needs a lock held by a younger one forces the younger to abort, so a cycle can't formGoogle Spanner, which calls it wound-wait

The victim's transaction is rolled back completely and its locks are released. The other transactions never learn that anything happened. Their statements, which had been waiting, simply return.

Lock ordering

A cycle needs two transactions that acquire the same locks in different orders. If every transaction that needs several locks takes them in the same order, no cycle is possible. The second transaction to arrive waits at the first lock, holding nothing the first one wants.

-- Deadlock-prone: the order of the locks follows the direction of the transfer
UPDATE accounts SET balance = balance - 10 WHERE id = :sender;
UPDATE accounts SET balance = balance + 10 WHERE id = :receiver;

-- Safe: lock both rows first, always in order of id, then change them in whatever order is convenient
SELECT id FROM accounts WHERE id IN (:sender, :receiver) ORDER BY id FOR UPDATE;
UPDATE accounts SET balance = balance - 10 WHERE id = :sender;
UPDATE accounts SET balance = balance + 10 WHERE id = :receiver;

The rule is easy to state, and in a real application the locks are harder to see. These are the places deadlocks usually come from:

SourceWhy the order differsRemedy
Two code paths touching the same tablesOne updates the order and then its customer, another the customer and then the orderAgree an order of tables for the whole codebase
Batch updates and upsertsTwo batches contain the same rows in different sequencesSort every batch by key before sending it
UPDATE … WHERE id IN (…)Rows are locked in the order the scan finds them, which isn't under your controlLock first with SELECT … ORDER BY id FOR UPDATE
Foreign keysInserting a child row takes a lock on its parent row that you didn't writeKnow that it happens, and touch parents before children
Unique indexesTwo transactions insert the same keys in different orders, and each waits to see whether the other will commitSort the inserts, or use ON CONFLICT

Both accounts start at £100. With either setting the two transfers do the same work and end with A at £95 and B at £105. The only difference is the order in which each one takes its two row locks.

Things to notice. With "sender first", the two transfers take their locks in opposite orders, and by the fourth step the wait-for graph has an arrow in each direction. Nothing moves for a second, until transfer 1's deadlock check fires and it is aborted. Transfer 2 completes, and transfer 1 has to be run again by the application: one error, one retry and a second lost. With "in order of account id", transfer 2 asks for row A first, although its own money goes the other way. It finds A locked and waits, holding nothing. The graph has one arrow and no cycle, transfer 1 finishes, and transfer 2 follows. No error is raised, and the wait lasts only as long as transfer 1 took.

Retries

Lock ordering removes the deadlocks you know about. In a large application some will remain, from foreign keys, from indexes, from a code path somebody added last week. So a deadlock should be treated like a serialisation failure: an expected outcome under concurrency, to be retried. The error code is 40P01.

def transfer(conn, sender, receiver, pence):
    first, second = sorted([sender, receiver])              # always the same order
    def work(conn):
        conn.execute("SELECT 1 FROM accounts WHERE id IN (%s, %s) ORDER BY id FOR UPDATE", (first, second))
        conn.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (pence, sender))
        conn.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (pence, receiver))
    run_transaction(conn, work)                            # Chapter 21's helper: retries on 40001 and 40P01, with backoff

Retrying is safe because the victim was rolled back in full: nothing it did has taken effect. The retry must run the whole transaction again, and wait a short, random time first, so that the same two transactions don't collide again in the same way.

lock_timeout

Three settings limit waiting, and they are often confused.

SettingDefaultWhat it doesWhat it doesn't do
deadlock_timeout1 sHow long a transaction waits for a lock before it checks for a deadlockLimit ordinary waiting. With no cycle, the wait goes on
lock_timeoutOffAborts a statement that has waited this long for any one lockLimit a statement that is running, not waiting
statement_timeoutOffAborts a statement that has taken this long in total, for any reasonTell you whether the time went on waiting or working
 
SET lock_timeout = '2s';            -- for interactive requests: failing fast beats queueing
SET log_lock_waits = on;            -- log every wait that outlasts deadlock_timeout, with who was blocking

SELECT deadlocks FROM pg_stat_database WHERE datname = current_database();   -- a counter worth graphing

A deadlock is resolved by the database within a second. Plain blocking, where a transaction waits behind another that is merely slow, is resolved by nobody unless you set a limit. Of the two, blocking is the more common in production and does more harm (Chapter 22).

The foreign-key deadlocks that PostgreSQL 9.3 removed

Until 2013 a common pattern in PostgreSQL applications produced deadlocks that their authors could not find in their own code, because the locks involved were taken by the database on their behalf. Consider a forum. Posting a message inserts a row into posts that refers to a row in users. To be sure that the user isn't deleted before the insert commits, the foreign-key check took a shared lock on the user's row. Many applications also update the user's row for other reasons, to record the time of their last activity or to count their posts. An update needs an exclusive lock on the row. So two requests for the same user, each inserting a post and then updating the user, would each take the shared lock, which they could both hold, and then each ask for the exclusive lock, which neither could have while the other held the shared one. The result was a deadlock between two transactions that had each written two entirely reasonable statements. It was reported by users of web frameworks for years. The fix, in version 9.3, was to make the locks say more precisely what they protect. A foreign-key check now takes a lock that means only "don't delete this row or change its key", and an update that leaves the key alone takes a weaker lock than one that changes it, and the two are compatible. The deadlock disappeared without any application changing a line. The locks a transaction holds include ones it never asked for, and when a deadlock report names a statement that looks harmless, the foreign keys and unique indexes on the table are the first place to look.

⚠️
Common mistakes
  • Treating a deadlock error as a database fault. It is the database resolving a conflict that the application's lock order created.
  • Not retrying. The victim's work is lost, and a user sees an error for a request that would succeed if run again.
  • Raising deadlock_timeout to "avoid deadlocks". It only delays their detection. The transactions still wait.
  • Sending batches in arbitrary order. Two workers upserting overlapping sets of rows is the commonest deadlock in data pipelines.
  • Long transactions. The longer locks are held, the more chances there are for another transaction to want them in a different order.
  • Ignoring the server log. It contains both statements of every deadlock, which is the whole diagnosis.

Interview drill

Explain it simply: What is a database deadlock, and what does the database do about it?

How a strong answer sounds
A deadlock is when two or more transactions each hold a lock that another needs and are each waiting for a lock that another holds, so none can proceed. The simplest case: transaction 1 updates row A then tries to update row B, while transaction 2 has updated row B and tries to update row A. Unlike threads deadlocking on mutexes, a database doesn't hang: it tracks who is waiting for whom, a wait-for graph, and looks for cycles. PostgreSQL runs that check when a transaction has waited longer than deadlock_timeout, one second by default; InnoDB checks immediately. When it finds a cycle it picks a victim, rolls that transaction back completely, which releases its locks, and returns a "deadlock detected" error to that client; the other transactions carry on unaware. The application should catch that error and retry the whole transaction, and, better, prevent the deadlock by always acquiring locks in a consistent order.

Deeper: Your service logs a few deadlock errors every hour. How do you investigate, and how do you eliminate them?

How a strong answer sounds
I'd start from the server log, because for every deadlock PostgreSQL logs the processes in the cycle, the lock each was waiting for, and the statement each was running; with log_lock_waits on I also see the waits that led up to it. That gives me the two, occasionally three, statements involved, and I can map them to code paths. Then I'd work out which locks each transaction holds at that point and in what order it took them, remembering the implicit ones: row locks from earlier statements in the same transaction, locks on parent rows from foreign-key checks, and waits caused by unique indexes. The fix is to make the order consistent. If two paths touch the same tables in different orders, pick one order. If it is a multi-row update or a batch upsert, sort the rows by primary key, or take the locks up front with SELECT … ORDER BY id FOR UPDATE. If the transaction is long, shorten it, so locks are held briefly and fewer are held together; sometimes the best fix is splitting it. Where the logic allows, replace read-then-write sequences with a single atomic statement. Independently of all that, I'd make sure the application retries on deadlock, error 40P01, with a small random backoff, since retrying is correct and cheap, and I'd keep a graph of the deadlock counter so that a new code path that reintroduces one is noticed.

🧠 Key takeaways

  • A deadlock is a cycle of transactions each waiting for a lock that the next one holds.
  • The database finds the cycle in its wait-for graph, aborts one transaction with an error, and the others proceed.
  • PostgreSQL checks only after a wait of deadlock_timeout, so each deadlock costs about a second and one rolled-back transaction.
  • Taking locks in one consistent order, such as by primary key, makes a cycle impossible.
  • Foreign keys, unique indexes and unordered batches take locks you didn't write, so retry on deadlock errors as well.
  • lock_timeout limits ordinary waiting, which no deadlock detector will end for you.

Transaction 1 holds a lock on row A and wants row B. Transaction 2 holds B and wants A. What does PostgreSQL do?

One victim is enough to break the cycle. Its locks are released when it is rolled back.

What is the most reliable way to prevent the deadlock between two money transfers in opposite directions?

With a single agreed order, the second transaction waits at the first lock and holds nothing the first one needs.

A transaction receives "deadlock detected". What state is it in, and what should the application do?

Nothing the victim did has taken effect, which is what makes the retry safe.

Smaller batches make the deadlock rarer. A consistent order makes it impossible.

Limiting ordinary lock waits is the job of lock_timeout.
