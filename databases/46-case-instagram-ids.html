Case Study: Instagram's Sharded IDs

A primary key is the easiest decision in a schema until the data stops fitting on one machine. On a single PostgreSQL server, bigint GENERATED ALWAYS AS IDENTITY hands out 1, 2, 3 and nobody thinks about it again. Split the table over ten servers and each of them hands out 1, 2, 3. In 2011 Instagram was a year old, taking in, by its engineers' account, more than 25 photos and 90 likes every second, had a handful of people on its whole engineering staff, and was sharding its PostgreSQL databases. It needed an ID that was unique across every shard, could be sorted by time, fitted in 64 bits, and required no new service to run. The design it published takes twenty lines of PL/pgSQL, and it is a compact lesson in how much information 64 bits can carry.

Why not auto-increment

An auto-increment column is a counter kept by one database. With one database it gives everything wanted: unique, compact, and in order of creation. With many it gives collisions, since each shard counts from 1. The alternatives fall into four families, and Instagram's article went through them in turn.

The requirement to sort by time deserves a word. Instagram's main queries are feeds: the newest photos by the people a user follows, the newest comments on a photo. If the ID itself increases with time, then ORDER BY id DESC is a chronological sort with no separate timestamp index, and new rows are appended at the right-hand edge of the primary-key index, which Chapter 13 showed to be the cheap place to insert.

The ID layout

The idea, which Instagram took from Snowflake, is to stop treating the ID as a counter and treat it as a small record. A 64-bit integer has room for three fields side by side.

FieldBitsHoldsIts width limits
Time41, the most significantMilliseconds since an epoch the company chose, in August 2011How long the scheme lasts: 241 ms is about 69 years
Shard13The number of the logical shard the row lives inHow many logical shards there can be: 8,192
Sequence10, the least significantA counter in that shard, taken modulo 1,024How many IDs one shard can make in one millisecond: 1,024

The order of the fields is what makes the IDs sort. Time occupies the most significant bits, so an ID made later is a larger number whatever its shard and sequence. Two IDs made in the same millisecond are ordered by shard and then by sequence, which is arbitrary but consistent, so IDs are in time order to the millisecond across the whole system. Uniqueness comes from the other two fields: two shards can never produce the same ID, since their shard bits differ, and within one shard and one millisecond the sequence separates up to 1,024 rows.

Every field's width is a budget, and each can be checked against the load. A thousand IDs a millisecond in one shard is a million inserts a second into a single PostgreSQL schema, far more than it can do. Eight thousand shards is more than Instagram planned to use. The 41 bits of time are the generous-looking one, and they hide a detail: PostgreSQL's bigint is signed, so the top bit of the ID is the sign. IDs stay positive, and so keep sorting correctly as numbers, for half of the 69 years. With an epoch in 2011, that runs out in 2046.

The shard is the user ID modulo 2,000, so that everything belonging to one user is in one shard. Each shard has its own sequence, which carries on counting from one millisecond to the next and is used modulo 1,024. Logical shards are spread evenly over the servers, in ranges.

Things to notice. Insert several rows without advancing the clock: only the last ten bits change, and each ID is one more than the one before. Advance the clock by a millisecond and the ID jumps by more than eight million, since the time field starts 23 bits up. Change the user and the middle field changes. Whatever the shard, an ID made in a later millisecond is larger than every ID from an earlier one, which is the whole of the sorting property. Now change the number of database servers. The server that holds the row changes, and the ID doesn't change by a single bit: the ID records the logical shard, and which machine that shard lives on is looked up separately. And the read-back lines show that nothing has to be stored to route a request: given only an ID, two shifts and a mask recover when the row was made and where it is.

Logical shards

Chapter 26 set out the idea: divide the data into many more shards than there are machines, and assign shards to machines in a small table. Instagram used several thousand logical shards on a handful of servers at first. In PostgreSQL each logical shard was a schema, the namespace that tables live in, so that server 1 might hold schemas insta0 to insta499, each with its own copy of every sharded table.

The reason for the indirection is growth. When a server fills up, some of its schemas are moved to a new machine with PostgreSQL's ordinary replication and tools, and the map is updated. No row changes shard, so no ID changes and nothing has to be re-hashed. Had the ID contained a server number, every move would have invalidated the IDs of the rows moved. Keeping the user's data together has a second benefit: a user's photos, likes and comments are all in one schema on one server, so the queries about one user never cross shards.

The PL/pgSQL function

This is the function as Instagram published it, for logical shard 5. Each schema has its own copy with its own shard number, and its own sequence.

CREATE SEQUENCE insta5.table_id_seq;

CREATE OR REPLACE FUNCTION insta5.next_id(OUT result bigint) AS $$
DECLARE
    our_epoch  bigint := 1314220021721;          -- 24 August 2011, in milliseconds since 1970
    seq_id     bigint;
    now_millis bigint;
    shard_id   int    := 5;                      -- this schema's logical shard
BEGIN
    SELECT nextval('insta5.table_id_seq') % 1024 INTO seq_id;
    SELECT FLOOR(EXTRACT(EPOCH FROM clock_timestamp()) * 1000) INTO now_millis;
    result := (now_millis - our_epoch) << 23;    -- time into the top 41 bits
    result := result | (shard_id << 10);         -- shard into the next 13
    result := result | (seq_id);                 -- sequence into the last 10
END;
$$ LANGUAGE PLPGSQL;

CREATE TABLE insta5.photos (
    id      bigint NOT NULL DEFAULT insta5.next_id() PRIMARY KEY,
    user_id bigint NOT NULL,
    …
);

Four details repay a close look. The shifts are 23 and 10 since those are the numbers of bits to the right of each field: 13 + 10 below the time, and 10 below the shard. clock_timestamp() is used, not now(), which in PostgreSQL returns the time the transaction began and would give every row in one transaction the same milliseconds. The sequence is never reset: nextval counts upwards for ever, and the modulo keeps its last ten bits, which is enough to tell apart rows made in the same millisecond provided there are fewer than 1,024 of them. And the function is a column default, so the application doesn't call anything: it inserts a row and reads the ID back with RETURNING id.

Decoding is the reverse, and it is useful for debugging and for routing.

SELECT to_timestamp(((id >> 23) + 1314220021721) / 1000.0) AS created_at,

More than 1,024 inserts in one shard in one millisecondThe sequence wraps and an ID repeats. The primary key rejects the insert, which can be retried. In practice one schema never sees that rate

Twitter's Snowflake: the same record, made by a service

The layout Instagram adapted was published by Twitter in 2010, when it was moving its tweets from MySQL to Cassandra, which has no auto-increment at all. Twitter needed tens of thousands of IDs a second, unique across data centres, and roughly sorted by time so that timelines could be ordered by ID. Its answer, Snowflake, is a 64-bit number with one unused sign bit, 41 bits of milliseconds since an epoch in November 2010, 10 bits identifying the machine that generated it, and 12 bits of sequence, which allows 4,096 IDs each millisecond from each machine. The IDs are produced by a dedicated service: a set of processes that applications call over the network. Each process must have a machine number no other has, and Twitter assigned those through ZooKeeper, a coordination service. Each also guards against its clock: if the clock is found to have moved backwards, the process refuses to issue IDs until time has caught up. The design spread widely. Discord's message IDs, which Chapter 45 shifted right by 22 bits to get a timestamp, are Snowflakes with an epoch in 2015, and 22 is the 10 machine bits plus the 12 of sequence. Instagram's contribution was to observe that it already had a set of machines with unique numbers and well-kept counters, namely its database shards, and to move the generator into them: the shard number takes the place of the machine number, a PostgreSQL sequence takes the place of the in-memory counter, and the ID service with its ZooKeeper cluster isn't needed. For a team of a handful of engineers that was the deciding property. The modern standard form of the same idea is UUID version 7, a 128-bit identifier that begins with a millisecond timestamp and fills the rest with random bits. It needs no shard or machine number at all, at the price of being twice the size.

⚠️
Common mistakes
  • Auto-increment in each shard, with nothing to keep the numbers apart.
  • Putting a server number in the ID. Data moves between servers. A logical shard number stays valid.
  • Time in the low bits. The IDs no longer sort by time, and inserts scatter across the index.
  • Using now() in the generator. It is the transaction's start time, the same for every row in the transaction.
  • Not checking the budgets: IDs per millisecond, number of shards, and the year the time field or the sign bit runs out.
  • Treating a time-based ID as secret. It discloses its creation time to anyone who sees it.

Interview drill

Explain it simply: How would you generate unique IDs across many database shards?

How a strong answer sounds
Auto-increment doesn't work across shards, since each would produce the same numbers, so I'd first ask what properties the ID needs: uniqueness, obviously; whether it must sort by time; whether it must fit in 64 bits; and how much new infrastructure is acceptable. If nothing but uniqueness matters, a random UUID generated by the application is the simplest: no coordination at all, but 128 bits and random insertion order, which hurts B-tree locality. If I want compact, time-ordered IDs, I'd use a Snowflake-style layout: a 64-bit integer with a millisecond timestamp in the high bits, then some bits identifying the generator, then a per-generator sequence in the low bits. Time in the high bits makes them sort chronologically; the generator bits make them unique across generators with no coordination at generation time; the sequence handles several IDs in the same millisecond. The generator can be a separate service with assigned worker numbers, as at Twitter, or the database shard itself, as at Instagram, where the shard number is the generator ID and a database sequence provides the counter. UUIDv7 gives the same time-ordering in 128 bits with no generator IDs. I'd mention the failure modes: clock moving backwards, sequence exhaustion within a millisecond, and the fact that the ID reveals its creation time.

Deeper: In a 64-bit ID with 41 bits of time, 13 of shard and 10 of sequence, what are the limits, and what happens when each is reached?

How a strong answer sounds
Forty-one bits of milliseconds is 2 to the 41, about 2.2 trillion milliseconds or roughly 69.7 years from the chosen epoch, after which the time field overflows into nothing and IDs wrap. But if the ID is stored in a signed 64-bit column, the top bit of the time field is the sign bit, so IDs turn negative after half that, about 34.8 years; they stay unique but no longer sort after the positive ones, which breaks ordering by ID. So the practical lifetime is 35 years unless one bit is reserved for the sign, as Snowflake does. Thirteen bits of shard allows 8,192 logical shards; that is a ceiling on the logical shard count, not on servers, and it can't be raised without changing the layout, so it should be chosen generously at the start. Ten bits of sequence allows 1,024 IDs for each shard in each millisecond, about a million a second for one shard; if the sequence is taken modulo 1,024 from a monotonic counter, as in Instagram's function, exceeding it produces a duplicate ID within the same millisecond, which the primary-key constraint rejects, so an insert fails and can be retried, whereas Snowflake's approach is to wait for the next millisecond. The other limit isn't in the bits: the scheme assumes each generator's clock doesn't go backwards. A backwards step can make new IDs sort before old ones and, combined with a sequence coincidence, duplicate one; the unique constraint catches it, and running NTP in slewing mode avoids it. And skew between shards' clocks means global ordering is only as good as clock synchronisation, typically milliseconds.

🧠 Key takeaways

  • Auto-increment is a counter owned by one database. Sharded data needs IDs that are unique without a shared counter.
  • A 64-bit ID can be a record: time in the high bits, a shard number in the middle, a sequence in the low bits.
  • Time first makes IDs sort chronologically and insert at the right-hand edge of the index.
  • Each field's width is a budget: years of life, number of shards, IDs for each millisecond. Check each against the load.
  • The ID holds a logical shard, mapped to a server elsewhere, so that data can move without any ID changing.
  • Generating IDs inside each shard's database needs no extra service. The primary key constraint is the backstop for clocks and wrap-around.
