Constraints & Integrity

Application code validates data; constraints guarantee it. A rule checked only in the application holds until the second application, the migration script, the admin console, the hurried manual fix in psql, or two requests racing each other. A constraint is checked by the database on every write, from every client, inside the transaction, and it can't be raced. This chapter covers the full toolkit: uniqueness (including case-insensitive and partial), foreign keys and what ON DELETE should do, CHECK, deferrable constraints, and exclusion constraints, which solve "no double booking" in one line.

  • Enforce uniqueness, including case-insensitive and "unique among active rows"
  • Choose an ON DELETE action for each foreign key, and index the referencing column
  • Express business rules with CHECK, and know their limits
  • Use deferrable constraints for updates that pass through invalid intermediate states
  • Prevent overlapping bookings with an exclusion constraint

Why the database, not just the application

"Email must be unique" checked in application code is a read followed by a write: SELECT … WHERE email = ?, then INSERT if nothing came back. Two sign-ups with the same email arriving within a few milliseconds both see "nothing", and both insert. This race is a check-then-act bug, and no amount of careful application code fixes it without a lock. A UNIQUE constraint does: the second insert waits for the first and then fails. Validate in the application for good error messages; enforce in the database for correctness.

Uniqueness

CREATE TABLE users (
    user_id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      text   NOT NULL,
    deleted_at timestamptz
);
-- case-insensitive: Ana@Example.com and ana@example.com are the same person
CREATE UNIQUE INDEX users_email_lower_idx ON users (lower(email));

-- partial: unique among active users only, so a deleted account frees its email
CREATE UNIQUE INDEX users_email_active_idx ON users (lower(email)) WHERE deleted_at IS NULL;

Two details. A UNIQUE constraint treats NULLs as distinct by default, so many rows may have a NULL email; PostgreSQL 15 added UNIQUE NULLS NOT DISTINCT if you want at most one. And uniqueness is implemented by a unique B-tree index, which is also what makes the check fast and race-free.

Foreign keys and ON DELETE

A foreign key stops orphans from being created (P1). The other half of the question is what happens when the parent is deleted:

ON DELETEDeleting a customer who has orders…Use for
NO ACTION (default)Fails, checked at the end of the statement (or at commit if deferred)Most relationships: make deletion an explicit decision
RESTRICTFails immediately, can't be deferredSame, when you want no deferral
CASCADEAlso deletes their orders (and anything cascading from those)Parts owned by the parent: an order's lines, a post's attachments
SET NULLKeeps orders, sets customer_id to NULLOptional links: an article's last editor
SET DEFAULTSets the column to its defaultRare: reassigning to a placeholder

Every foreign-key check on delete is a lookup in the child table: "does any order reference customer 42?". PostgreSQL indexes primary keys automatically but not the referencing column, so without CREATE INDEX ON orders (customer_id) each parent delete scans the whole orders table.

CHECK constraints

A CHECK is a boolean expression every row must satisfy. It can reference any columns of the same row:

CREATE TABLE order_items (
    order_id   bigint  NOT NULL REFERENCES orders ON DELETE CASCADE,
    product_id bigint  NOT NULL REFERENCES products,
    quantity   integer NOT NULL CHECK (quantity > 0),
    unit_cents bigint  NOT NULL CHECK (unit_cents >= 0),
    discount_cents bigint NOT NULL DEFAULT 0,
    CHECK (discount_cents <= quantity * unit_cents),          -- a rule across columns
    PRIMARY KEY (order_id, product_id)
);

Three limits to know. A CHECK passes when the expression is true or unknown, so CHECK (quantity > 0) allows NULL; add NOT NULL separately. It can only see the current row: rules about other rows ("at most 5 active sessions per user") need a unique index, an exclusion constraint, a trigger, or a lock in the transaction. And the expression should be immutable: a CHECK (expires_at > now()) is only evaluated on write and is a bad idea.

Deferrable constraints

PostgreSQL checks a non-deferrable unique constraint row by row as an UPDATE runs. So shifting every position in a playlist down by one, UPDATE tracks SET position = position + 1, can fail halfway with a duplicate key, even though the final state is valid. Declaring the constraint DEFERRABLE moves the check to the end of the statement, and INITIALLY DEFERRED (or SET CONSTRAINTS … DEFERRED) moves it to COMMIT, which also lets you insert rows that reference each other in any order inside one transaction:

ALTER TABLE tracks ADD CONSTRAINT tracks_playlist_pos_key
    UNIQUE (playlist_id, position) DEFERRABLE INITIALLY IMMEDIATE;

UPDATE tracks SET position = position + 1 WHERE playlist_id = 7;   -- now checked once, at statement end

Exclusion constraints: no overlapping bookings

"A room can't be booked twice for overlapping times" isn't a uniqueness rule: two bookings for 10:00–11:00 and 10:30–11:30 have different values but still conflict. An exclusion constraint generalises UNIQUE: no two rows may satisfy a set of operators pairwise. Here: same room and overlapping time range.

CREATE EXTENSION IF NOT EXISTS btree_gist;                  -- lets a GiST index handle "=" on integers

CREATE TABLE bookings (
    booking_id bigint    GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id    integer   NOT NULL,
    during     tstzrange NOT NULL,
    EXCLUDE USING gist (room_id WITH =, during WITH &&)     -- && means "overlaps"
);

This is the cleanest correct answer to the double-booking interview question: no explicit locks, no race window, and it holds for every client. (Chapter 21 shows why the "check for overlaps, then insert" approach fails under concurrency without it.)

When cascades get too big: GitLab's "loose foreign keys"
At GitLab's scale, deleting a large project could cascade into millions of rows across CI pipelines, builds and artifacts, all inside one transaction, holding locks and generating a flood of WAL for replicas to apply. And some referencing tables had been moved to a separate database, where a foreign key can't reach at all. GitLab's answer, documented in its development guidelines, is "loose foreign keys": the parent delete records the deleted id in a queue table via a trigger, and a background worker deletes or nullifies the children in small batches. They give up instant consistency (orphans exist for a short while) in exchange for bounded transactions. It's a deliberate, monitored trade, and the default for most tables there is still a real foreign key.

Common mistakes

    
    
      
  • Uniqueness checked only in application code. Two concurrent requests both pass the check.
    • 
      
  • No index on foreign-key columns. Every parent delete or key update scans the child table.
    • 
      
  • ON DELETE CASCADE by habit. Deleting a customer shouldn't silently delete their invoices; cascade only owned parts.
    • 
      
  • Assuming CHECK rejects NULL. Unknown passes. Add NOT NULL.
    • 
      
  • "Check for overlap, then insert" for bookings. Use an exclusion constraint, or serializable isolation.

Interview drill

    
Explain it simply: Why enforce uniqueness in the database if the application already checks it?

    
How a strong answer sounds
The application check is a read followed by a write, so two concurrent requests can both see "not taken" and both insert. A unique index makes the database serialise them: the second insert waits for the first to commit and then fails with a unique violation, which the application can turn into a friendly "already registered". It also covers every other writer: scripts, admin tools, other services. I'd keep the application check for the user experience and rely on the constraint for correctness.

    
Deeper: How do you guarantee a meeting room is never double-booked?

    
How a strong answer sounds
Store each booking with a tstzrange and add EXCLUDE USING gist (room_id WITH =, during WITH &&), with the btree_gist extension for the integer equality. Then any insert or update that overlaps an existing booking for the same room fails atomically, regardless of concurrency or which client wrote it; the application catches the exclusion violation and shows "slot taken". Alternatives are locking the room row with SELECT … FOR UPDATE before checking for overlaps, or running the check-and-insert at SERIALIZABLE isolation and retrying on serialization failure, but both depend on every code path doing it right.

  


  

    
🧠 Key takeaways

    
    
      
  • Constraints are checked on every write from every client and can't be raced; application checks can.
    • 
      
  • Unique indexes can be on expressions (lower(email)) and partial (WHERE deleted_at IS NULL).
    • 
      
  • Pick ON DELETE per relationship: NO ACTION by default, CASCADE for owned parts, SET NULL for optional links; index the referencing column.
    • 
      
  • CHECK sees one row and passes on unknown; pair it with NOT NULL.
    • 
      
  • DEFERRABLE moves the check to statement end or commit; exclusion constraints prevent overlaps.
