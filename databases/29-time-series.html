Time-Series Storage

A server reports its processor load every ten seconds. So do the other nine thousand servers, each for two hundred different measurements. That is 180,000 new values a second, every second, and nobody will ever update one of them. This is time-series data: measurements stamped with the time they were taken, arriving in order, in very large quantity, of which the last hour is looked at constantly and last year almost never. It comes from monitoring, from sensors, from financial markets and from application analytics. Its regularity is so strong that a store built for it can hold a sixteen-byte measurement in under two bytes. This chapter covers the shape of the workload and the three techniques that exploit it: chunking by time, specialised compression, and downsampling.

  • Plan downsampling and retention, and work out the storage each tier needs

The data has a simple model. A series is one thing being measured, identified by a name and a set of labels, such as cpu_usage{host="web-17", region="eu"}. A point is a timestamp and a value. A monitoring system has millions of series, and each one grows by a point every few seconds.

Chunking by time

Every time-series store divides its data into chunks, each covering a period: two hours, a day, a week. This is partitioning by range of time (Chapter 26), and each property of the workload gains from it.

-- TimescaleDB, an extension that does this inside PostgreSQL
CREATE TABLE metrics (
  time       timestamptz NOT NULL,
  series_id  integer     NOT NULL,
  value      double precision
);
SELECT create_hypertable('metrics', 'time', chunk_time_interval => INTERVAL '1 day');

SELECT add_retention_policy('metrics', INTERVAL '30 days');      -- drop whole chunks as they age out
SELECT add_compression_policy('metrics', INTERVAL '2 days');    -- rewrite older chunks in compressed, columnar form

Writes go to the newest dataOnly the current chunk is being written, and it and its indexes are small enough to stay in memory

Compression (delta, Gorilla)

A point is a 64-bit timestamp and a 64-bit floating-point value: 16 bytes. Two observations about real series shrink that dramatically, and both come from a system at Facebook called Gorilla, whose encoding nearly every time-series database has since adopted.

Timestamps arrive at a fixed interval. A source that reports every ten seconds produces timestamps ten seconds apart. So store the first timestamp in full. For the next, store the delta, the difference from the one before. For all later ones, store the delta of the delta: how much this interval differs from the last interval. For a regular series that is zero nearly every time, and a zero is written as a single bit.

Values change little from one point to the next. Temperatures, queue lengths and request rates move slowly. Two similar floating-point numbers have nearly the same bit pattern, so the XOR of a value with the previous one is mostly zeros. If the value hasn't changed, the XOR is zero and one bit says so. Otherwise only the few bits in the middle that differ are stored.

The encoding here is the real one, computed on the actual bits of each number. Timestamps: 1 bit if the delta of delta is zero, 9 bits if it is within ±64, 12 within ±256, 16 within ±2,048, and 36 otherwise. Values: 1 bit if unchanged, otherwise 2 control bits and the meaningful bits of the XOR, with 11 more bits when the position of those bits has moved.

Things to notice. A steady series costs two bits for each point after the first, one for "the interval hasn't changed" and one for "the value hasn't changed", against 128 bits raw. A value that moves slowly through whole numbers still averages under a byte a point. An irregular series with noisy decimal values costs over seven bytes a point, which is barely half the raw size. Its timestamps need nine bits where one would do, and its values share few bits with their predecessors, since a number like 41.37 has no short binary form. The same encoder gives very different results on different data, and the compression comes from the regularity of the series. Reporting on a fixed schedule, and rounding values to the precision that means something, makes a series several times smaller to store.

Downsampling and retention

Nobody examines last March at ten-second resolution. A downsampled series keeps one point for each longer interval, usually with the minimum, maximum, sum and count for that interval, so that averages and peaks can still be computed. The full-resolution data is then deleted when its retention period ends.

TierResolutionKept forPoints for each seriesUsed for

The three tiers together hold one twenty-third of the points that two years of raw data would, and a query for a year's trend reads 8,760 points for each series where it would have read three million.

-- A continuous aggregate: a rollup that the database keeps up to date as new data arrives (Chapter 33)
CREATE MATERIALIZED VIEW metrics_1m WITH (timescaledb.continuous) AS
SELECT time_bucket('1 minute', time) AS bucket, series_id,
       min(value), max(value), sum(value), count(*)
FROM metrics GROUP BY bucket, series_id;

One limit is set by the number of distinct series, called the cardinality, and the volume of points matters less. Every unique combination of labels is its own series, with its own entry in the index and its own chunk being built in memory. A label with a few values, such as region, multiplies the series by a few. A label such as user id or request id multiplies them by millions, and a store that could take a billion points an hour for ten thousand series is brought down by a million series with one point each.

🦍
Gorilla: Facebook's monitoring data in 1.37 bytes a point

By 2013 Facebook's monitoring system was collecting about two billion distinct time series and adding to them at around twelve million points a second. The data was kept in a store built on HBase, and it had become too slow for what it was used for most: an engineer investigating an incident, or an automated system deciding whether something was wrong, both of which query the last few hours and need answers at once. Looking at their own usage, the engineers found that at least 85% of all queries were for data from the past 26 hours. They built Gorilla, described in a paper in 2015, to hold exactly that window entirely in memory in front of the existing store. Whether 26 hours of two billion series could fit in memory depended on the size of a point, and the two encodings above were designed for that purpose. On Facebook's real data, 96% of timestamps compressed to a single bit, because the collectors ran on a fixed schedule, and about half of all values compressed to a single bit too, because they hadn't changed since the last report. The average came to 1.37 bytes for a point, a twelfth of the raw sixteen. With the recent data in memory in that form, queries ran over seventy times faster than they had against the disk-based store. The format was simple and was fully described in the paper, and within a few years Prometheus, InfluxDB, TimescaleDB and most others had adopted it or a close variant. The compression worked because the engineers had measured how regular their own data was before designing for it.

⚠️
Common mistakes
  • High-cardinality labels: a user id, a session id or a full URL as a label. Each distinct value creates a series.
  • One unpartitioned table with an index on time. It works for a while, and then the index outgrows memory and deletion by age becomes a daily crisis.
  • Deleting old data with DELETE. Drop chunks. A delete of billions of rows is slow and leaves bloat behind (Chapter 23).
  • Keeping raw data for ever "just in case". Decide the resolution each age of data needs, and downsample.
  • Rollups that store only an average. Averages of averages are wrong, and peaks vanish. Keep the sum, count, minimum and maximum.
  • Using a time-series store as a general database. It has no cheap updates and little support for joins or transactions.

Interview drill

Explain it simply: What makes time-series data different, and how do databases take advantage of it?

How a strong answer sounds
Time-series data is append-only, arrives in time order at a high and steady rate, is queried mostly by time range and aggregate rather than by individual row, is most valuable when recent, and is deleted in bulk by age. Stores exploit each of those. They partition by time into chunks, so writes only touch the newest, small chunk; range queries open only the relevant chunks; and retention is dropping whole chunks instead of deleting rows. Because old chunks are immutable, they can be compressed aggressively in columnar form, with encodings designed for the data: timestamps as delta-of-delta, since intervals are regular, and values XORed with their predecessor, since they change slowly; that takes a 16-byte point to a byte or two. And because old data needs less detail, they downsample: keep raw data for days, minute rollups for months, hourly for years. The data model is series identified by a metric name and labels, and the thing that usually limits these systems is cardinality, the number of distinct series, not the number of points.

Deeper: Design the storage for metrics from 10,000 servers, each reporting 200 metrics every 10 seconds, with a year of history.

How a strong answer sounds
First the arithmetic: 10,000 times 200 is two million series; at one point per ten seconds that is 200,000 points a second, about 17 billion a day. Raw at 16 bytes that would be 276 GB a day; with Gorilla-style compression at around 1.5 bytes a point it is about 26 GB a day. A year of raw data would be nearly 10 TB compressed, which is wasteful, since nobody needs ten-second resolution from months ago. So I'd use tiers: raw for two weeks, about 360 GB; one-minute rollups, holding min, max, sum and count, for three months; hourly rollups for the full year. The rollups are six and 360 times fewer points, so the total is well under a terabyte. Physically, I'd chunk by time, a few hours per chunk for the newest data, keep the current chunk in memory with a write-ahead log for durability, flush completed chunks as compressed immutable blocks sorted by series then time, and drop blocks past their retention. An index maps label values to series IDs so that queries like "all hosts in this region" find their series. Rollups are computed incrementally as each chunk closes. The main risks are cardinality, so I'd police labels and reject ones with unbounded values, and write availability, so I'd replicate, or accept that a monitoring store may lose a few seconds on failover. For the system itself I'd use something existing, Prometheus with long-term storage behind it, or TimescaleDB or ClickHouse if SQL matters, rather than build one.

🧠 Key takeaways

  • Time-series data is appended in time order, read by range, valued by recency and deleted by age.
  • Chunking by time keeps writes in a small recent chunk, lets queries skip most of the data, and makes retention a matter of dropping files.
  • Timestamps are stored as the delta of the delta, which is zero for a regular series and costs one bit.
  • Values are stored as the XOR with the previous value, which is zero when nothing changed and short when little did.
  • Downsampling keeps old data at coarse resolution, with sum, count, minimum and maximum, for a small fraction of the space.
  • The number of distinct series is what limits a time-series store, so labels must have a bounded set of values.

Check your understanding

Why is deleting month-old data cheap in a time-series store, and expensive in an ordinary table?

Dropping a file is instant and leaves no dead rows.

A sensor reports exactly every 10 seconds. How many bits does each timestamp take after the first two, under delta-of-delta encoding?

The delta is always 10, so the delta of the delta is always 0, which is written as a single bit.

Why does XOR with the previous value compress a slowly changing series well?

An unchanged value gives an XOR of zero, stored as one bit.

A rollup stores only the average for each minute. What goes wrong when an hourly figure is computed from it?

Keep the sum and the count, from which a correct average follows, and the minimum and maximum for the extremes.

A developer adds user_id as a label on a request-latency metric, in a service with 5 million users. What happens?

Every distinct combination of label values is a separate series. Per-user detail belongs in logs or an analytics store.
