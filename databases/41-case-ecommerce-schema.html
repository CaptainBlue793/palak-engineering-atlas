Case Study: Designing an E-Commerce Schema

"Design the database for an online shop" is the most common schema question there is, and the first answer is nearly always the same four tables: customers, products, orders, and order items joining the last two. It is a reasonable start and it breaks within a month of launch. A product turns out to come in six sizes and four colours. A price changes, and every past invoice changes with it. Two customers buy the last pair of shoes in the same second. A retried request charges someone twice. None of these is exotic, and each is a requirement that the four tables didn't model. This case study builds the schema properly, using what the earlier chapters set up: constraints, transactions, row locks and indexes, applied to one design.

  • Separate the product from the thing that is sold, and stock from both
  • Explain why an order copies its prices and addresses, and never updates them
  • Decrement stock so that it can't go below zero under concurrency
  • Make order creation safe to retry
  • Choose indexes from the list of queries the shop runs most

The brief

A shop sells clothing and shoes online: about 50,000 products, a few thousand orders a day, and occasional sales when a popular item sells out in minutes. Customers browse by category, put items in a cart, check out and pay, and can look at their past orders. Staff pick and ship orders and issue refunds. Finance needs every invoice to say for ever what it said on the day. Stock must never be sold twice.

Entities and relationships

Start by listing the things, and for each one ask what a single row stands for. Two distinctions decide the rest of the design, and the four-table version misses both.

First, a product is not the thing that is sold. "Trail Shoe" is a product: a name, a description, some photographs. What a customer buys is a Trail Shoe in size 42 in blue, which has its own stock code, its own price and its own stock. That is a variant, or SKU. Orders, carts and stock all refer to variants.

Second, stock is not an attribute of the variant. It changes thousands of times a day where the variant's description changes once a year, it may be held in several warehouses, and it is the most contended row in the system. It gets a table of its own.

CREATE TABLE products (
  product_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        text    NOT NULL,
  category_id bigint  NOT NULL REFERENCES categories,
  active      boolean NOT NULL DEFAULT true              -- discontinued means false, never DELETE
);

CREATE TABLE product_variants (
  variant_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  product_id  bigint NOT NULL REFERENCES products,
  sku         text   NOT NULL UNIQUE,
  options     jsonb  NOT NULL DEFAULT '{}',              -- {"size": "42", "colour": "blue"}
  price       numeric(10,2) NOT NULL CHECK (price >= 0)
);

CREATE TABLE inventory (
  variant_id  bigint  PRIMARY KEY REFERENCES product_variants,
  available   integer NOT NULL CHECK (available >= 0)     -- the last line of defence against overselling
);

The variant's options are a JSON column here, since sizes apply to shoes, lengths to trousers and neither to a gift card, and a column for every possible attribute would be mostly NULL. Money is numeric, never a floating-point type, which can't represent 0.10 exactly.

Orders as immutable facts

Chapter 7 taught that each fact should be stored once, and an order line that held the product's name and price would seem to be storing them twice. It isn't. "The price of this variant" and "the price this customer paid on 3 March" are two different facts. They happen to be equal on the day of the order, and they stop being equal the first time the price changes. The same goes for the product's name and the delivery address. An order is a record of something that happened, and it has to hold its own copy of everything it will ever need to show.

CREATE TABLE orders (
  order_id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id     bigint NOT NULL REFERENCES customers,
  status          text   NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending', 'paid', 'shipped', 'delivered', 'cancelled')),
  ship_to         jsonb  NOT NULL,                       -- the address as it was when the order was placed
  shipping        numeric(10,2) NOT NULL,
  total           numeric(10,2) NOT NULL,
  idempotency_key uuid   NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (customer_id, idempotency_key)                    -- a retried checkout can't create a second order
);

CREATE TABLE order_items (
  order_id     bigint   NOT NULL REFERENCES orders,
  line_no      smallint NOT NULL,
  variant_id   bigint   NOT NULL REFERENCES product_variants,  -- for reports. The invoice never follows it
  product_name text     NOT NULL,                              -- copied at purchase
  sku          text     NOT NULL,
  unit_price   numeric(10,2) NOT NULL,
  quantity     integer  NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (order_id, line_no)
);

Values in red differ from what was true on the day of the order. Design A is the four-table schema: an order line holds a variant ID and a quantity, and everything else is found by joining. Its foreign key to products was declared ON DELETE CASCADE, as is often done to make deleting a product "work".

Things to notice. Every change is an ordinary event in the life of a shop, and each one rewrites history in design A. After the price rise its invoice says the customer paid £195, and nothing anywhere in that database records the £165 that was taken from their card. After the move, it shows the parcel going to an address the customer didn't live at. Discontinuing the product is the worst: the cascade removes the order line, and the order becomes a £5 charge for shipping nothing. Design B's invoice doesn't change, since everything on it was copied at the moment of purchase, and its foreign key refuses the delete, so the product is switched off instead. The copying looks like a breach of normalisation and is the reverse: the order's price is a separate fact from the catalogue's price.

The same principle extends past the order line. An order's status changes, and each change is worth keeping, so it is recorded as an event as well as on the order row. Money never changes in place: a refund is a new row in refunds, and the amount still owed is computed from payments less refunds.

Inventory without oversell

One pair is left and two customers press "buy" in the same second. Application code that reads the stock, checks it is positive and writes back the reduced figure will sell it twice: that is the lost update of Chapter 21. The fix is to make the check and the decrement a single statement, so that the database's row lock covers both.

BEGIN;

UPDATE inventory
SET    available = available - 2
WHERE  variant_id = 311 AND available >= 2;                -- UPDATE 1: reserved.  UPDATE 0: not enough stock, roll back

INSERT INTO orders (customer_id, ship_to, shipping, total, idempotency_key)
VALUES (88, '{"line1": "14 Mill Lane", "city": "Leeds"}', 5.00, 165.00, '7c1e…')
ON CONFLICT (customer_id, idempotency_key) DO NOTHING
RETURNING order_id;                                         -- no row back: this checkout already happened, roll back

INSERT INTO order_items (order_id, line_no, variant_id, product_name, sku, unit_price, quantity)
SELECT 1001, 1, v.variant_id, p.name, v.sku, v.price, 2     -- name and price copied from the catalogue, now
FROM   product_variants v JOIN products p USING (product_id)
WHERE  v.variant_id = 311;

COMMIT;
ApproachOversells?Notes
Read, check in the application, write the new valueYesBoth buyers read 1 and both write 0
Conditional UPDATE, as aboveNoOne statement and no extra round trip. The usual choice
SELECT … FOR UPDATE, then decide, then writeNoRight when the decision needs application logic. Holds the lock for longer
Serialisable isolationNoCorrect with no explicit locking. One of the two is aborted and has to retry
CHECK (available >= 0) aloneNoA backstop. It turns an oversell into an error, which is better than a negative number and worse than a clean "sold out"

Three refinements matter in a real shop. An order with several lines takes several stock rows, and two such orders locking the same rows in opposite orders deadlock (Chapter 24), so sort the lines by variant_id before updating. Stock is taken when the order is placed, and the payment follows, so a payment that fails or is abandoned must put it back: that needs a job that cancels pending orders after a time limit and adds their quantities back. And the idempotency_key, a random value the client generates once for each checkout attempt, means that when the response is lost and the client tries again, the second insert conflicts with the first and no second order, or second decrement, is made.

Indexes for the hot queries

Indexes are chosen from the queries, so list those first, with how often each runs. Primary keys and unique constraints have already supplied several.

What is left out matters as much. Every index on orders and order_items is paid for on every checkout, so reporting queries go to a replica or a warehouse (Chapter 48), where they can have indexes of their own. As the shop grows, the catalogue is cached and served from replicas (Chapter 33), and orders is partitioned by month (Chapter 26), which keeps the recent, busy part small and makes old years cheap to archive.

🛍️
Shopify: the same decisions, visible in a public API

Shopify hosts millions of shops on one data model, and since its API exposes that model, the decisions in this chapter can be read off its documentation. A product in Shopify can't be bought. It has a title, a description and images, and a list of variants, and it is the variant that carries the SKU and the price and that an order line refers to. For many years a product was limited to 100 variants, a limit merchants with many sizes and colours ran into often enough that Shopify rebuilt its product APIs to allow 2,000. Stock sits in neither of them. Each variant has an inventory item, and stock is held as inventory levels, one for each combination of item and location, so that a shop with two warehouses and a high-street branch has three levels for each variant. A level isn't a single number either: it distinguishes what is physically on hand, what is committed to orders not yet shipped, what is available to sell, and what is incoming from suppliers. Order line items make the point about facts. Each line stores its own title, variant title, SKU and price alongside the references to the product and variant, and the API includes a field saying whether the product still exists, since merchants delete products all the time and the orders for them must still be readable in full. Refunds are separate records attached to the order, and the order's totals are never rewritten. Shopify arrived at these shapes over many years of merchants doing things the first schema hadn't allowed for, which is how most real schemas get them, and it is why a design that starts with them saves a great deal of later migration.

⚠️
Common mistakes
  • Price and stock on the product row. Variants have their own, and stock deserves its own table.
  • Order lines that join to live prices. The first price change rewrites every past invoice.
  • ON DELETE CASCADE from catalogue to orders. Deleting a product deletes sales history.
  • Checking stock in application code and writing the result back. Use a conditional update.
  • Floating-point money. Use numeric, or integer pence.
  • No idempotency key on checkout, so that a retry after a timeout creates a second order.
🎤
Interview drill

Explain it simply: Why store the price on the order line when it is already on the product? Isn't that denormalised?

How a strong answer sounds
It looks like duplication, but they are two different facts. The product's price is "what this costs now", and it changes. The order line's price is "what this customer was charged on that day", and it must never change. If the order line only referenced the product and I joined to get the price, then raising the price next month would silently alter every historical invoice, revenue reports would shift, and refunds would be calculated against the wrong amount. So the order line copies the unit price at the time of purchase, along with anything else the invoice shows that might later change: the product name, the SKU, and the delivery address on the order. Normalisation says to store each fact once; it doesn't say that two facts that happen to have the same value today are the same fact. I'd still keep the foreign key to the variant, for reporting, but the invoice is rendered only from the order's own columns. For the same reason I'd never delete products, only deactivate them, and the foreign key from order lines would restrict deletion.

Deeper: During a flash sale, 5,000 people try to buy 100 units of one item in a few seconds. How does your design hold up, and what would you change?

How a strong answer sounds
Correctness holds: the conditional update, available = available - 1 where available >= 1, is atomic on the row, so exactly 100 succeed and the rest get zero rows updated, and the CHECK constraint is a backstop. The problem is contention. All 5,000 requests want the same row lock, so they queue behind each other; each transaction holds the lock until it commits, and if the transaction also inserts the order and lines, that is a few milliseconds each. The queue of waiters ties up database connections, and with a pool of, say, 50, everything else on the site stalls behind them. Things I'd do, in order. First, keep the critical section tiny: the stock decrement in its own short transaction, with the order written just after, and compensation if that fails. Second, fail fast: once the item is sold out, cache that fact for a second or two and reject requests before they reach the database, and set a short lock_timeout so that waiters give up. Third, admission control: a queue or token system in front that lets through only slightly more buyers than there is stock. If contention were still too high, I could split the stock into several rows, buckets of 10, and have each request try a random bucket with SKIP LOCKED, which spreads the lock. At a larger scale the decrement moves to an in-memory store such as Redis with an atomic script, with the database updated asynchronously, at the price of having to reconcile the two. I'd also separate reserving stock from paying: hold it for a few minutes with an expiry, so that abandoned checkouts return it.

🧠 Key takeaways

  • For each table, say what one row stands for. A product, a variant and its stock are three things.
  • An order is a record of fact. It copies the name, price and address it shows, and those copies are never updated.
  • Catalogue rows are switched off, not deleted, and money changes by adding rows.
  • Decrement stock with one conditional UPDATE and check the row count. Keep a CHECK as a backstop.
  • A unique idempotency key makes checkout safe to retry.
  • List the hot queries, then index for them, with composite and partial indexes where they fit. Send reports elsewhere.

Check your understanding

A shirt comes in 5 sizes and 3 colours. Where does its stock belong?

Stock is counted for each sellable unit, and it changes far more often than the variant's description.

Why does order_items have its own unit_price column?

They are equal only on the day of the order.

Two requests run UPDATE inventory SET available = available - 1 WHERE variant_id = 311 AND available >= 1 at once, with one unit left. What happens?

The row lock serialises them, and the second evaluates its WHERE on the committed row.

A customer's checkout request times out, and their browser sends it again. What stops a second order?

The second insert conflicts with the first, and the application returns the original order.

Which index best serves the warehouse's "paid and not yet shipped" list, on a table of 40 million orders?

It holds only the few hundred rows the query wants, in the order it wants them.
