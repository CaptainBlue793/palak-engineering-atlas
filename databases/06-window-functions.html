Window Functions

GROUP BY collapses each group to one row. Often you want the opposite: keep every row, and add something computed from its neighbours. Its rank within its region, the running total so far, the previous month's value, the difference from the group average. That's what window functions do, and they're the most-asked "advanced SQL" topic in interviews, because they turn questions that would need self-joins and correlated subqueries into one readable pass.

  • Write OVER (PARTITION BY … ORDER BY …) and explain what each part controls
  • Choose between ROW_NUMBER, RANK and DENSE_RANK when there are ties
  • Build running totals and moving averages, and understand frames: ROWS vs the default RANGE
  • Compare a row with the previous or next one using LAG and LEAD
  • Solve top-N per group, and filter on a window result correctly

OVER: aggregates that keep the rows

Any aggregate becomes a window function when you add OVER (…). Instead of collapsing the rows, it computes a value for each row from a set of related rows, its window:

SELECT rep, region, amount,
       sum(amount) OVER ()                         AS grand_total,     -- window = all rows
       sum(amount) OVER (PARTITION BY region)     AS region_total,    -- window = my region
       amount - avg(amount) OVER (PARTITION BY region) AS vs_region_avg
FROM   sales;

Three clauses inside OVER define the window:

  • PARTITION BY splits rows into independent groups, like GROUP BY but without collapsing them. Omit it and the whole result is one partition.
  • ORDER BY orders rows within each partition. Ranking functions and LAG/LEAD need it; for aggregates it turns "the whole partition" into "the partition so far".
  • The frame (ROWS BETWEEN …) picks which rows around the current one an aggregate sees. More on its surprising default below.

ROW_NUMBER breaks ties arbitrarily unless you add a tie-breaker to the ORDER BY, just like pagination in Chapter 2. If the result must be repeatable, write ORDER BY amount DESC, rep_id.

Top-N per group

"The top 2 reps in each region" is the canonical window-function interview question. Number the rows within each partition, then keep the first N. The filter has to happen in an outer query, because window functions run after WHERE:

WITH ranked AS (
    SELECT rep, region, amount,
           row_number() OVER (PARTITION BY region ORDER BY amount DESC, rep) AS rn
    FROM   sales
    WHERE  month = '2026-01'
)
SELECT rep, region, amount
FROM   ranked
WHERE  rn <= 2;                -- use rank() <= 2 instead to include everyone tied for 2nd

Running totals and frames

With an ORDER BY in the window, an aggregate covers the rows from the start of the partition up to the current one: a running total. Precisely which rows is the frame, and the default frame has a trap. When you write only ORDER BY, the frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, and RANGE includes every row that ties with the current one on the ORDER BY value (its peers). Two rows in the same month both see both amounts, so the running total jumps by both at once. ROWS counts physical rows instead:

SELECT month, rep, amount,
       sum(amount) OVER (ORDER BY month)                                        AS running_range,
       sum(amount) OVER (ORDER BY month, rep
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)        AS running_rows,
       avg(amount) OVER (ORDER BY month, rep ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS moving_avg_3
FROM   sales;

The same default bites last_value(): with only an ORDER BY, the frame ends at the current row, so last_value(x) returns the current row's own value. Add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING, or use first_value with the order reversed.

LAG and LEAD

LAG(x) returns x from the previous row in the window's order, LEAD(x) from the next. That turns "compare with the previous period" into one expression instead of a self-join:

SELECT month, revenue,
       revenue - lag(revenue) OVER w                                    AS change,
       round(100.0 * (revenue / lag(revenue) OVER w - 1), 1)            AS pct_change,
       lead(month) OVER w                                             AS next_month
FROM   monthly_revenue
WINDOW w AS (ORDER BY month);                                          -- a named window, reused

The first row has no previous row, so lag returns NULL (or a default: lag(revenue, 1, 0)). lag(x, 7) looks seven rows back, which is "same day last week" for daily data, provided no days are missing. If days can be missing, generate a complete calendar with generate_series and left-join to it first.

Deduplicating a change stream: keep the latest row per key

Pipelines that copy a production database into a warehouse with change data capture (CDC) receive every version of every row, sometimes twice and sometimes out of order. The standard clean-up, used so widely that dbt ships it as a macro, is a window function: number the versions of each key newest first and keep number 1. SELECT * FROM (SELECT *, row_number() OVER (PARTITION BY order_id ORDER BY updated_at DESC, ingested_at DESC) AS rn FROM raw_orders) t WHERE rn = 1. The second sort key matters: two versions with the same updated_at would otherwise be picked arbitrarily, and the "current" state of an order could change from one run to the next.

⚠️
Common mistakes
  • Filtering on a window function in WHERE. Error: compute it in a CTE, filter outside.
  • Running totals with the default RANGE frame on non-unique ordering. Ties jump together; use ROWS and a unique tie-breaker.
  • last_value() with the default frame returns the current row. Specify the frame.
  • ROW_NUMBER without a tie-breaker when the result must be repeatable.
  • LAG(x, 7) on data with missing days: it's seven rows back, not seven days back.

Interview drill

Explain it simply: What's the difference between a window function and GROUP BY?

How a strong answer sounds
GROUP BY collapses each group into one output row. A window function keeps every row and adds a value computed over a set of related rows, defined by OVER (PARTITION BY … ORDER BY … frame). So "total per region" is a GROUP BY; "each sale next to its region's total, its rank in the region, or the running total" is a window function. Window functions run after WHERE, GROUP BY and HAVING, which is why filtering on them needs an outer query.

Deeper: Return the top 3 products by revenue in each category, including all products tied for third.

How a strong answer sounds
First aggregate revenue per product, then rank within category: WITH rev AS (SELECT p.category_id, p.product_id, sum(i.quantity * i.unit_cents) AS revenue FROM order_items i JOIN products p USING (product_id) GROUP BY 1, 2), ranked AS (SELECT *, rank() OVER (PARTITION BY category_id ORDER BY revenue DESC) AS rk FROM rev) SELECT * FROM ranked WHERE rk <= 3. rank rather than row_number because the question asks for ties at third; dense_rank would also include products tied for second when that leaves gaps, which is a different question, so I'd confirm the wording.

🧠 Key takeaways

  • A window function computes a value per row from related rows, without collapsing them.
  • PARTITION BY groups, ORDER BY orders within the group, the frame picks the rows an aggregate sees.
  • ROW_NUMBER is unique, RANK skips after ties, DENSE_RANK doesn't.
  • The default frame with ORDER BY is RANGE … CURRENT ROW, which includes tied peers; use ROWS for true running totals.
  • Top-N per group: rank in a CTE, filter outside. LAG/LEAD compare with neighbouring rows.

Check your understanding

Amounts in descending order are 300, 200, 200, 100. What does DENSE_RANK() give the row with 100?

DENSE_RANK doesn't leave gaps after ties: 1, 2, 2, 3. RANK would give 4.

Why can't you write WHERE row_number() OVER (…) <= 3?

Compute the window function in a subquery or CTE, then filter on its result in the outer query.

Two rows share the same month. With sum(amount) OVER (ORDER BY month), what is the running total on the first of them?

The default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which treats rows with equal ORDER BY values as one step. Use ROWS for a row-by-row running total.

What does lag(revenue) OVER (ORDER BY month) return for the earliest month?

There's no previous row. lag(revenue, 1, 0) would return 0 instead.

Which window is right for a 7-row moving average?

Six preceding rows plus the current one is seven. (It's seven rows, not seven days: fill missing days first if needed.)
