Subqueries & CTEs

A query can contain other queries: a single value computed inline, a list to test against, a whole derived table, or a named step written with WITH. These let you build a complicated question out of simple pieces, and recursive CTEs go further: they walk trees and graphs of any depth, such as org charts, comment threads, category hierarchies and bills of materials, in one statement. This chapter covers each form, which ones the planner rewrites into joins for you, and the one recursive-query bug that can run a query forever.

  • Write scalar, IN, EXISTS and derived-table subqueries, and know the error each can raise
  • Explain what "correlated" means and when it costs one execution per row
  • Structure long queries with CTEs, and know when PostgreSQL inlines them
  • Write a recursive CTE, trace its iterations, and guard it against cycles

Scalar and IN subqueries

A scalar subquery returns one value and can go anywhere a value can. If it returns no rows the value is NULL; if it returns more than one row, the statement fails with more than one row returned by a subquery used as an expression.

-- orders bigger than the average order
SELECT order_id, total_cents
FROM   orders
WHERE  total_cents > (SELECT avg(total_cents) FROM orders);

-- products that have ever been ordered
SELECT product_id, name
FROM   products
WHERE  product_id IN (SELECT product_id FROM order_items);

An IN (SELECT …) subquery is a semi-join: each product appears once however many order lines it has. PostgreSQL usually plans it exactly like the equivalent EXISTS. Its negation, NOT IN, is the one to avoid when the subquery's column can be NULL (P2).

Correlated subqueries and EXISTS

A subquery is correlated when it refers to a column of the outer query. Logically it's evaluated once per outer row:

-- each customer's most recent order date (correlated scalar subquery in SELECT)
SELECT c.customer_id, c.name,
       (SELECT max(o.created_at) FROM orders o WHERE o.customer_id = c.customer_id) AS last_order
FROM   customers c;

-- customers with an order over £500 (correlated EXISTS)
SELECT c.customer_id, c.name
FROM   customers c
WHERE  EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND o.total_cents > 50000);

"Once per outer row" is the logical meaning, not necessarily the execution. PostgreSQL rewrites EXISTS and IN subqueries in WHERE into semi-joins and anti-joins, which it can execute with a hash join over the whole orders table. A correlated scalar subquery in the SELECT list usually isn't rewritten: EXPLAIN shows it as a SubPlan executed per row. With an index on orders(customer_id) that's a fast lookup each time; without one, it's a scan of orders per customer. When in doubt, the explicit join with GROUP BY is the form the planner has the most freedom with.

Derived tables and LATERAL

A subquery in FROM is a derived table: a temporary result you can join to, and the standard way to aggregate before joining (the fan-out fix from Chapter 3). LATERAL lets a derived table refer to columns of tables listed before it, which makes "for each row, run this small query" explicit. The classic use is top-N per group:

-- each customer's three most recent orders
SELECT c.name, r.order_id, r.created_at
FROM   customers c
CROSS JOIN LATERAL (
    SELECT o.order_id, o.created_at
    FROM   orders o
    WHERE  o.customer_id = c.customer_id
    ORDER BY o.created_at DESC
    LIMIT  3
) r;

With an index on orders(customer_id, created_at), each customer costs one short index scan. Chapter 6 solves the same problem with ROW_NUMBER(), which is better when you want most groups; LATERAL wins when groups are large and you only want a few rows from each.

WITH: common table expressions

A CTE names a subquery and puts it first, so a long query reads top to bottom as a series of steps:

WITH paid AS (
    SELECT customer_id, total_cents
    FROM   orders
    WHERE  status = 'paid' AND created_at >= '2026-01-01'
),
per_customer AS (
    SELECT customer_id, sum(total_cents) AS spend
    FROM   paid
    GROUP BY customer_id
)
SELECT c.name, p.spend
FROM   per_customer p
JOIN   customers c USING (customer_id)
WHERE  p.spend > (SELECT avg(spend) FROM per_customer)    -- a CTE can be used twice
ORDER BY p.spend DESC;

Before PostgreSQL 12, every CTE was computed separately and stored (an "optimisation fence"), so a filter in the outer query couldn't be pushed into it. Since version 12, a non-recursive, side-effect-free CTE referenced once is inlined like a subquery; one referenced more than once, like per_customer above, is still computed once and reused. You can force either behaviour with AS MATERIALIZED or AS NOT MATERIALIZED. CTEs can also modify data: WITH moved AS (DELETE FROM jobs WHERE … RETURNING *) INSERT INTO jobs_archive SELECT * FROM moved moves rows atomically in one statement.

Recursive CTEs

A recursive CTE has two parts joined by UNION ALL: an anchor query that produces the starting rows, and a recursive query that refers to the CTE itself and produces the next rows from the previous ones. PostgreSQL runs it iteratively:

WITH RECURSIVE team AS (
    SELECT employee_id, name, manager_id, 0 AS depth           -- anchor: the starting manager
    FROM   employees
    WHERE  employee_id = 2
  UNION ALL
    SELECT e.employee_id, e.name, e.manager_id, t.depth + 1     -- recursive: their direct reports
    FROM   employees e
    JOIN   team t ON e.manager_id = t.employee_id
)
CYCLE employee_id SET is_cycle USING path               -- PostgreSQL 14+: stop if an id repeats
SELECT employee_id, name, depth FROM team ORDER BY depth, name;

Each step runs one iteration: the anchor first, then the recursive term against the rows added in the previous iteration (highlighted). The real server stops runaway recursion only when something else does: statement_timeout, memory, or you.

  


  
Two ways to protect a recursive query from cycles: track the path yourself (an array of visited ids, with WHERE NOT e.employee_id = ANY(t.path)), or, on PostgreSQL 14 and later, the CYCLE clause shown above. Switching UNION ALL to UNION removes rows that are exact duplicates of earlier ones, which only stops a cycle if the rows really are identical; any column that changes per iteration, like depth, defeats it. A WHERE t.depth < 20 limit in the recursive term is a cheap extra safety net.

GitLab's group hierarchies: from recursive CTEs to an array column
GitLab lets groups contain subgroups to any depth, and many permission and listing queries need "all descendants of this group". For years those queries used recursive CTEs over the namespaces table, which work well for shallow trees but get expensive for large organisations with thousands of nested groups, because every iteration is another join. GitLab's engineers added a denormalised traversal_ids integer array to each namespace, holding the ids of all its ancestors, maintained on insert and move. "Descendants of group 42" becomes a single indexed query on that array instead of a recursion. It's a common pattern: recursive CTEs are the clean, normalised answer; when a hierarchy is read far more often than it changes, storing the path (a materialised path, or PostgreSQL's ltree type) is the fast one.

Common mistakes

    
    
      
  • A scalar subquery that can return several rows: fine in testing, an error the day a second row exists.
    • 
      
  • NOT IN over a nullable column: zero rows. Use NOT EXISTS.
    • 
      
  • Correlated subqueries in SELECT without an index on the correlated column: a scan per outer row.
    • 
      
  • Recursive CTEs without a cycle guard on data you don't fully control.
    • 
      
  • Assuming CTEs are always fences, or never fences. It depends on the version and how many times the CTE is referenced.

Interview drill

    
Explain it simply: When would you use EXISTS rather than a JOIN?

    
How a strong answer sounds
When I only need to know whether a matching row exists, not its columns. A join returns one row per match, so a customer with ten orders appears ten times and I'd need DISTINCT; EXISTS is a semi-join that returns each outer row at most once and can stop at the first match. For "has no match" I use NOT EXISTS rather than NOT IN, which returns nothing if the subquery yields a NULL. PostgreSQL plans both as semi- or anti-joins, often with a hash.

    
Deeper: Write a query for every category under "Electronics" at any depth, and say what could go wrong.

    
How a strong answer sounds
WITH RECURSIVE sub AS (SELECT category_id, name, 0 AS depth FROM categories WHERE name = 'Electronics' UNION ALL SELECT c.category_id, c.name, s.depth + 1 FROM categories c JOIN sub s ON c.parent_id = s.category_id) SELECT * FROM sub. Risks: a cycle in parent_id (bad data or a buggy move operation) makes it loop forever, so I'd add CYCLE category_id SET is_cycle USING path or a depth limit, and ideally prevent cycles when categories are moved. Each iteration joins on parent_id, so that column needs an index. If the tree is read constantly and rarely changes, I'd consider storing the path with ltree or an ancestors array.

  


  

    
🧠 Key takeaways

    
    
      
  • Scalar subqueries return one value (NULL if empty, error if more than one row).
    • 
      
  • IN and EXISTS are semi-joins; PostgreSQL rewrites them into joins. Prefer NOT EXISTS to NOT IN.
    • 
      
  • Correlated subqueries in SELECT run per row unless rewritten; index the correlated column.
    • 
      
  • CTEs make long queries readable; since PostgreSQL 12, single-use CTEs are inlined.
    • 
      
  • Recursive CTEs iterate anchor → recursive term until an iteration returns no rows; guard against cycles.

Check your understanding

    


    

      
What happens if a scalar subquery used in a WHERE comparison returns two rows?

      

        
        
        
        
      

      
A scalar subquery must produce at most one row. Zero rows gives NULL; more than one is a runtime error.

    


    

      
What makes a subquery "correlated"?

      

        
        
        
        
      

      
For example, WHERE o.customer_id = c.customer_id inside a subquery over orders, where c belongs to the outer query.

    


    

      
When does a recursive CTE stop?

      

        
        
        
        
      

      
Each iteration processes the previous iteration's rows. An empty iteration ends it. A cycle means that never happens, hence CYCLE guards or depth limits.

    


    

      
Since PostgreSQL 12, what happens to a non-recursive CTE that's referenced exactly once?

      

        
        
        
        
      

      
Before version 12 CTEs were optimisation fences. Now single-use, side-effect-free CTEs are inlined; multi-use ones are still computed once.

    


    

      
You want each customer's 3 most recent orders, and customers have thousands of orders each. Which form is efficient with an index on orders(customer_id, created_at)?

      

        
        
        
        
      

      
LATERAL runs a short index scan per customer and stops after 3 rows. A window function would number every order of every customer first.
