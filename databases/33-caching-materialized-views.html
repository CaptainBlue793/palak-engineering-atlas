Caching & Materialised Views

Some queries are expensive however well they are indexed: a dashboard that totals a year of sales, a product page assembled from six tables, a ranking recomputed for every visitor. When the same answer is wanted a thousand times a minute and the data behind it changes once an hour, the sensible thing is to compute it once and keep the result. A database can do this itself, with a materialised view. An application can do it outside the database, with a cache. Either way the result is fast to read, and a second copy of the truth now exists, which is right until the underlying data changes and wrong afterwards. Keeping the copy correct is harder than making it, and this chapter is about how to do so.

Materialised views

An ordinary view stores a query and runs it every time it is read (Chapter 16). A materialised view stores the query and its result. Reading it is reading a table.

CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', o.created_at) AS day, s.country, count(*) AS orders, sum(o.total_cents) AS revenue_cents
FROM orders o JOIN stores s USING (store_id)
WHERE o.status = 'paid'
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON daily_revenue (day, country);       -- it is a table, so it can be indexed

SELECT * FROM daily_revenue WHERE day >= '2026-10-01';       -- milliseconds, where the query above takes 40 seconds

The stored result is a snapshot. Orders placed after it was computed aren't in it, and PostgreSQL does nothing about that until told to.

-- every 10 minutes, with the pg_cron extension
SELECT cron.schedule('refresh-revenue', '*/10 * * * *', 'REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue');

The question for any of these is how stale the answer may be. A revenue dashboard ten minutes behind is fine, and a full refresh on a schedule is the simplest thing that works. An account balance may never be behind, and belongs in a table updated in the transaction that changes it.

Application caches

The commonest arrangement outside the database is cache-aside. The application looks in the cache first. On a miss it queries the database, puts the answer in the cache, and returns it.

def get_product(product_id):
    key = f"product:{product_id}"
    cached = redis.get(key)
    if cached is not None:
        return json.loads(cached)                                 # hit
    row = db.execute("SELECT … FROM products WHERE product_id = %s", (product_id,)).fetchone()
    redis.set(key, json.dumps(row), ex=300)                       # miss: fill, to expire in 5 minutes
    return row

def update_price(product_id, price):
    db.execute("UPDATE products SET price_cents = %s WHERE product_id = %s", (price, product_id))
    db.commit()
    redis.delete(f"product:{product_id}")                         # invalidate: the next reader refills it

What a cache is worth depends almost entirely on its hit rate. With a hit at 1 ms and a miss at 50 ms, a 90% hit rate gives an average of 5.9 ms and a 99% rate gives 1.5 ms. The misses matter more than they look, because the database still has to serve them: at 90%, a tenth of the traffic reaches it, and if the cache is lost or restarted, all of it does, at once (Networks, Chapter 43).

Cache invalidation

When the data changes, the cached copy is wrong. There are three ways to deal with that, and they can be combined.

ApproachHowStale forWeakness
Expiry onlyEvery entry has a time to live, and nothing else is doneUp to the TTL, after every changeEither the data is often stale, or the TTL is short and the hit rate poor
Delete on writeThe code that changes the data deletes the key, and the next reader refills itNormally not at allEvery writer must remember every key affected, and a race can refill it with old data
Update on writeThe code that changes the data writes the new value into the cacheNormally not at all, and with no miss afterwardsTwo concurrent writers can leave the older value in the cache
Follow the change logA separate process reads the database's stream of changes and invalidates keys (Chapter 25)The replication delayMore to run. No code path can forget to invalidate

Things to notice. With expiry alone the cache is wrong after every write for up to a minute, by design, and it mends itself. With delete on write, requests one after another behave perfectly. Interleaved, a reader that missed and read £10 from the database just before the write puts its £10 into the cache just after the writer's delete. The delete found nothing to delete, and the stale value now stays until the next write to that product, which may be a long time. With update on write the unlucky case needs two writers: the one that wrote to the database second writes to the cache first, and the older price overwrites the newer. The fourth option is the one most systems use. Deleting on write gives freshness in the ordinary case, and the expiry puts a limit on how long any mistake can survive. A scheme without an expiry has no such limit.

🎟️
Facebook's leases: closing the race in the cache itself

Facebook ran one of the largest caches ever built, thousands of memcached servers in front of its MySQL databases, using cache-aside with delete on write as described in this chapter. At billions of requests a second the unlucky interleaving in the panel happened continually: a web server that had missed and read an old value from the database would write it into the cache after another server's update had already deleted the key. Stale values set that way could persist indefinitely. In the paper its engineers published in 2013 on scaling this system, they described their fix, which they called leases. When a client asks for a key and misses, the cache server gives it a token, a lease, tied to that key. To fill the key the client has to present the token. If a delete for the key arrives in the meantime, the server invalidates the outstanding token, and the late fill is refused. The reader that lost the race simply can't write its stale value. The same mechanism solved a second problem. After a popular key was deleted, thousands of web servers would miss at once and all query the database for the same row. With leases the cache server hands out a token for a given key only once every ten seconds or so, and tells the other clients to wait a moment and ask again, by which time the first has usually filled it. The result was that the database saw one query for that key where it had seen thousands. The fix worked because it was made in the cache server, which sees the order in which operations reach it. The clients that had been racing had no way to see that order.

Whether to cache at all

A cache is a second system to run and a new class of bug, and it should be the last remedy tried, after the query itself has been looked at. A query that takes 800 ms because it lacks an index (Chapter 17) should get the index. A page that issues 200 queries (Chapter 38) should issue one. Caching a slow query hides it, until the cache is cold or the key changes, and then the slow query runs at full volume against a database that has been sized on the assumption it never would.

Cache it whenDon't cache it when
It is read far more often than it changesIt changes about as often as it is read
Slightly stale data does no harm: a catalogue page, a count of likesStaleness is a defect: a balance, stock at checkout, a permission
The query is already as fast as it can be made, and still too slow or too frequentThe query is slow for a reason that can be fixed
The system works, only more slowly, when the cache is emptyThe database couldn't survive the load without the cache
⚠️
Common mistakes
  • No expiry, "because we invalidate". One missed invalidation or one lost race, and the value is wrong for ever.
  • Caching to hide a slow query. Fix the query first. The cache will be cold one day.
  • Invalidating before the transaction commits. A reader refills the key from the old data, which is still what the database shows.
  • Treating the cache as a store of record. It may lose anything at any time, by eviction or restart.
  • Caching per-user data under a shared key. One user is then shown another's data. Put everything that varies into the key.
  • A plain REFRESH MATERIALIZED VIEW on a view that is read constantly. Readers block for the length of the refresh. Use CONCURRENTLY.

Interview drill

Explain it simply: What is a materialised view, and how does it differ from a view and from an application cache?

How a strong answer sounds
A view is a named query: nothing is stored, and each time you select from it the underlying query runs. A materialised view stores the query's result as a physical table, so reading it is as cheap as reading a table, and it can have its own indexes. The cost is staleness: the stored result reflects the data as of the last refresh, and in PostgreSQL you refresh it explicitly, either fully, which blocks readers, or concurrently, which needs a unique index and doesn't. It suits expensive aggregations and joins that many queries read and that may be a little out of date, like reporting rollups. An application cache is the same idea outside the database: results kept in something like Redis, keyed by the request, filled on a miss and invalidated by expiry or by the code that changes the data. It can cache things that aren't SQL results, and it saves the database round trip entirely, but it can only be looked up by key, the application is responsible for keeping it correct, and it is a separate system that can be lost. I'd use a materialised view when the consumers are SQL queries, and a cache for hot per-key lookups on the request path.

Deeper: You use cache-aside with delete-on-write, and users sometimes see old data indefinitely. How can that happen, and how do you fix it?

How a strong answer sounds
It is a race between a reader filling the cache and a writer invalidating it. Reader A misses and reads the row from the database, getting the old value. Before A writes it to the cache, writer B updates the row, commits, and deletes the cache key, which is still empty, so the delete does nothing. Then A sets the key to the old value it read. Now the cache holds stale data, and with no expiry it stays until the next write to that key. A variant: the writer deletes the key before its transaction commits, and a reader refills from the still-old committed state. And replication lag causes the same thing if readers fill from a replica that hasn't yet applied the write. Fixes, in order of effort: always set a TTL, so any stale entry is bounded; invalidate after commit, not before; fill from the primary, or delay the delete, or delete twice with a short gap, when replicas are involved. To close the race properly, make the fill conditional: versioned values, where a set is rejected if the cache already holds a newer version, or a lease or check-and-set token issued on the miss and invalidated by any delete, so a stale fill is refused. Alternatively, take invalidation out of application code and drive it from the database's change stream, so the order of invalidations follows the commit order. For data where staleness is unacceptable, I wouldn't cache it at all.

🧠 Key takeaways

  • A materialised view stores a query's result as a table. It is fast to read and stale until refreshed.
  • Refresh on a schedule when minutes of staleness are acceptable, concurrently if it is read all the time. Maintain a summary table in the writing transaction when it must be exact.
  • Cache-aside reads the cache first, falls back to the database on a miss, and fills the cache. Its value depends on the hit rate.
  • Invalidate by deleting the key after the write commits, and always set an expiry as well, to bound any mistake.
  • Every invalidation scheme has a race. Leases, versions or the change log close it. Expiry limits how long it lasts.
  • Fix the query before caching it, and make sure the system survives an empty cache.

Check your understanding

A materialised view was created an hour ago. Rows have since been inserted into its base table. What does a SELECT on the view return?

It is a stored result. PostgreSQL refreshes it only when asked to.

Why use REFRESH MATERIALIZED VIEW CONCURRENTLY and not a plain refresh?

It still computes the whole result, and it needs a unique index to work out the differences.

A cache hit takes 1 ms and a miss takes 50 ms. What is the average latency at a 90% hit rate?

0.9 × 1 + 0.1 × 50 = 5.9. The misses dominate, which is why the last few points of hit rate are worth so much.

With cache-aside and delete on write, how can a stale value end up in the cache?

The delete arrives before the stale fill, so it removes nothing. An expiry time bounds how long the stale value lasts.

A query takes 900 ms because it scans a table for want of an index. What should be done first?

A cache over a fixable slow query hides the problem until the cache is cold.
