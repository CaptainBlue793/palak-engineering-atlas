MVCC: Many Versions, No Read Locks

A report that takes ten minutes to run has to see the data as it stood at one moment, while thousands of writes land during those ten minutes. With locks alone the report would have to hold off every writer, or the writers the report. Nearly every modern database solves this another way: a writer doesn't overwrite a row, it makes a new version and leaves the old one where it is, and each reader is shown the version that was current when it began. This is multiversion concurrency control, MVCC. It is why a SELECT in PostgreSQL never waits for an UPDATE. It also explains why tables grow when nothing is being added, what VACUUM is for, and one of the few ways a healthy PostgreSQL can refuse all writes.

Row versions and xmin/xmax

Every transaction that changes data is given a number, its transaction ID or xid, from a counter that only goes up. Every row version carries two of these numbers in its header (Chapter 11): xmin, the transaction that created the version, and xmax, the transaction that deleted or replaced it, or 0 if none has.

SELECT xmin, xmax, ctid, balance FROM accounts WHERE id = 1;
--  xmin | xmax | ctid  | balance
--   742 |    0 | (0,1) |     100        created by transaction 742, and still current

UPDATE accounts SET balance = 80 WHERE id = 1;     -- this is transaction 760

-- The page now holds two versions of the row:
--   742 |  760 | (0,1) |     100        ended by 760: visible only to transactions that began before it committed
--   760 |    0 | (0,2) |      80        created by 760: the current version
StatementWhat it does to versions
INSERTWrites one version, with xmin set to this transaction
DELETESets xmax on the current version. Nothing is removed
UPDATEBoth: sets xmax on the old version and writes a complete new one
ROLLBACKNothing at all to the rows. The transaction is recorded as aborted, and its versions are invisible from then on

Whether a given xid committed, aborted or is still running is kept in a small, heavily cached structure called the commit log. That is why a rollback in PostgreSQL is instant however much the transaction wrote: one status changes, and every version it created stops counting.

Snapshots

A reader doesn't lock anything. When it begins it takes a snapshot, which is a short description of which transactions had committed at that instant: the next xid not yet handed out, and the list of xids still in progress. For each row version it meets, it applies one rule.

SELECT pg_current_snapshot();      -- 758:763:758,761
--   everything below 758 has finished · 763 is the next xid to be given out · 758 and 761 are still running

The isolation levels of Chapter 21 are choices about when a snapshot is taken. At Read Committed each statement takes a new one, so each statement sees the latest commits. At Repeatable Read the transaction keeps its first one, so it sees one moment throughout. Writers still lock the rows they change (Chapter 22), so two writers of one row wait for each other, and readers and writers never do.

      A reader here is a transaction at Repeatable Read, holding the snapshot it took when it was opened. "A new query" is what a fresh statement would see at this instant. VACUUM may remove an old version only if it was replaced before the oldest open snapshot was taken, or was written by a transaction that rolled back.

      Things to notice. Update without committing, and a new query still sees £100: the new version exists on the page and is invisible to everyone but its author. Commit, and new queries see £90, while a reader opened earlier goes on seeing £100 for as long as it stays open. Neither waited for the other. Roll an update back, and its version stays on the page as garbage. Now open a reader, then update and commit five times, and run VACUUM. Nothing is removed. The oldest reader's snapshot could still be asked for any of those versions, so all of them have to stay. Close the reader and VACUUM again, and they all go. In a real database that reader is a forgotten session or a slow report, the row is every row in every table, and the dead versions that can't be removed are the bloat.

      Postgres vs MySQL undo logs

      Every MVCC database keeps old versions. Where it keeps them is the largest design difference between PostgreSQL and InnoDB.

      PostgreSQLMySQL InnoDB, and Oracle
      An updateWrites a new version elsewhere in the table and leaves the old one in placeChanges the row in place, and copies the old values to a separate undo log
      The table holdsEvery version, live and dead, mixed togetherOnly the newest version of each row
      A reader needing an old versionFinds it in the table directlyStarts from the current row and applies undo records backwards until it reaches its snapshot
      RollbackInstantMust apply the undo records, taking about as long as the transaction did
      IndexesA new entry in every index for each new version, unless the update is HOTSecondary indexes change only if an indexed column changed
      Clean-upVACUUM scans tables for dead versionsA purge thread discards undo that no snapshot needs
      A long-running transaction causesDead versions to pile up in tables and indexes, which stay enlarged afterwardsThe undo log to grow, and old reads to slow as they walk longer chains. The tables themselves stay compact

      PostgreSQL's design makes reads of old versions and rollbacks cheap, and pays for it in table bloat and extra index writes. InnoDB keeps its tables tidy and pays when a reader has to reconstruct history. Chapter 43 is about a company for whom this difference decided the choice of database.

      VACUUM and bloat

      Dead versions take up space in pages, and every scan has to step over them. VACUUM is the process that deals with them, and autovacuum runs it on each table once enough of the table has changed, by default 20% of its rows.

      VACUUM doesWhy
      Removes dead row versions and their index entriesSo that the space can be reused for new rows. It doesn't shrink the file
      Updates the free space mapSo that inserts can find the room it has made (Chapter 11)
      Updates the visibility mapSo that index-only scans can skip the table (Chapter 17's fourth plan)
      Freezes old row versionsTo prevent transaction ID wraparound, described below
      Collects statistics, as autovacuum's ANALYZEFor the planner (Chapter 19)

      VACUUM can remove a version only if no snapshot anywhere could still see it. The oldest snapshot in the whole system sets a line, and nothing that died after it can be removed, in any table. Four things hold that line back, and they are the first things to check when a table is bloated:

      -- 1. Long-running and idle-in-transaction sessions
SELECT pid, state, now() - xact_start AS age, backend_xmin, left(query, 40)
FROM pg_stat_activity WHERE backend_xmin IS NOT NULL ORDER BY age(backend_xmin) DESC;
-- 2. Replication slots that no one is reading from
SELECT slot_name, active, xmin, catalog_xmin FROM pg_replication_slots;
-- 3. Prepared transactions that were never finished
SELECT gid, prepared FROM pg_prepared_xacts;
-- 4. A standby with hot_standby_feedback on, running a long query

-- How much is dead, and when was it last cleaned?
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 5;

      Transaction ID wraparound

      A transaction ID is a 32-bit number, so there are about four billion of them, and a busy database uses that many in months. PostgreSQL treats the numbers as a circle: for any xid, the two billion before it are "the past" and the two billion after it are "the future". This works as long as no row version in the database is more than two billion transactions old. If one were, its xmin would cross to the other side of the circle and appear to be in the future, and the row would vanish from every query.

      To prevent that, VACUUM freezes old versions: it marks them as "older than everything, visible to all", after which their xmin no longer matters. Autovacuum forces a freezing pass over any table whose oldest unfrozen row is 200 million transactions old, whether or not the table has changed. If something prevents that pass for long enough, the database protects itself in the only way left:

      WARNING:  database "app" must be vacuumed within 39985967 transactions
ERROR:    database is not accepting commands that assign new XIDs to avoid wraparound data loss in database "app"

SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database ORDER BY xid_age DESC;   -- alert well before 1 billion

      At that point reads still work and every write is refused, until a VACUUM has been run to completion on the offending tables, which on a large table can take many hours.

      🧟
      Sentry, July 2015: most of a day without writes

      Sentry collects error reports from other companies' applications, and in 2015 it stored them in PostgreSQL at a rate of thousands of writes a second, each of which used a transaction ID. On 20 July its main database stopped accepting writes. Nothing had crashed. The database had come within a few million transactions of wraparound, and had shut the door on new transaction IDs exactly as it is designed to. Autovacuum had been running the whole time, trying to freeze the largest tables before the deadline. The tables were too large and too busy, and the vacuum was configured too gently, throttled so as not to disturb the workload, so it was consuming old transaction IDs more slowly than the application was issuing new ones. The gap had been closing for weeks, and no alert had been watching it. Once the database had stopped, the only cure was to let VACUUM finish, and on tables of that size an unthrottled vacuum still took hours. Sentry's engineers shortened it in the end by truncating a large table whose contents they could afford to lose, and the service was down for most of a working day. Their published account led many teams to add the alert they hadn't had, on the age of the oldest unfrozen transaction ID, and to make autovacuum more aggressive on large tables. Mailchimp's Mandrill service lost over a day to the same cause in 2019. VACUUM is easy to regard as housekeeping that can be postponed when the database is busy, and these two outages came from postponing it.

      ⚠️
      Common mistakes
      • Turning autovacuum off, or throttling it hard, "because it slows things down". Bloat slows them more, and wraparound stops them.
      • Long-lived transactions: a report run on the primary, a session left idle in a transaction. They pin dead rows in every table, not just the ones they read.
      • Forgetting replication slots. A slot whose consumer has gone holds back clean-up indefinitely.
      • Expecting VACUUM to shrink files. It frees space inside them. Only a rewrite returns it.
      • Updating every row of a large table in one statement. The table doubles in size, and the old half is dead until vacuumed. Do it in batches.
      • No alert on transaction ID age. It is the one number that warns of wraparound, weeks ahead.

      Interview drill

      Explain it simply: What is MVCC, and what problem does it solve?

      How a strong answer sounds
      Multiversion concurrency control means the database keeps several versions of a row instead of overwriting it, so that readers and writers don't block each other. Under pure locking, a reader would take a shared lock and a writer an exclusive one, so a long report would stall all updates to what it reads, or be stalled by them. With MVCC, an update creates a new version of the row and marks the old one as superseded, both tagged with the transaction IDs responsible. Each reader works from a snapshot, a record of which transactions had committed when it started, and for every row sees the version that was current as of that snapshot, ignoring changes from transactions that committed later or are still in progress. So a reader gets a consistent view without taking locks, and writers carry on. Writers still lock rows against other writers. The cost is that old versions accumulate and must be cleaned up once no snapshot needs them: VACUUM in PostgreSQL, the purge of undo logs in InnoDB. A long-running transaction delays that clean-up for everyone.

      Deeper: A table in PostgreSQL holds 10 GB of live data and occupies 80 GB. Autovacuum runs on it regularly. What is going on?

      How a strong answer sounds
      The table is bloated: most of its pages are dead row versions or free space. Since autovacuum is running, the question is why it isn't keeping up, and there are two families of cause. The first is that vacuum runs but isn't allowed to remove the dead rows, because something holds the xmin horizon back: a long-running transaction, a session idle in transaction, an inactive replication slot, an orphaned prepared transaction, or a standby with hot_standby_feedback running long queries. I'd check pg_stat_activity ordered by the age of backend_xmin, pg_replication_slots and pg_prepared_xacts; the vacuum's verbose output would also say "dead row versions cannot be removed yet". The second is that vacuum can remove rows but too slowly or too rarely for the write rate: the default trigger of 20% of the table is a lot of dead rows on a big table, and the cost-based throttling may make each run take hours. I'd lower autovacuum_vacuum_scale_factor for that table and raise its cost limit. A third possibility is a past event, such as a mass update or a period with a stuck transaction, that bloated the table once; vacuum has since made the space reusable but can't return it, so the file stays at 80 GB. Either way, once the cause is fixed, the existing bloat needs a rewrite to reclaim: pg_repack or VACUUM FULL in a maintenance window, since plain VACUUM only truncates empty pages at the end of the file. I'd also check the indexes, which bloat in the same way.

      🧠 Key takeaways

      • An update writes a new row version and marks the old one. Each version records the transaction that created it and the one that ended it.
      • A reader takes a snapshot and sees, for each row, the version that was committed and current at that moment. Readers and writers don't block each other.
      • Rollback is instant in PostgreSQL: the transaction is marked aborted and its versions are ignored.
      • PostgreSQL keeps old versions in the table and removes them with VACUUM. InnoDB updates in place and keeps old values in an undo log.
      • A dead version can be removed only when no snapshot can see it, so one old transaction or forgotten replication slot causes bloat everywhere.
      • Transaction IDs are 32 bits and wrap round. VACUUM must freeze old rows in time, or the database stops accepting writes.

      Check your understanding

      In PostgreSQL, what does an UPDATE of one row do physically?

      The old version stays, for the benefit of any transaction whose snapshot predates the update.

      A row version has xmin = 760 and xmax = 0. Your snapshot was taken while transaction 760 was still in progress. Do you see it?

      The first test is whether xmin had committed before the snapshot. It hadn't, and a snapshot doesn't change afterwards.

      Why is ROLLBACK instant in PostgreSQL, even after a transaction has changed a million rows?

      The million dead versions remain on the pages until VACUUM removes them.

      VACUUM runs on a table and removes almost nothing, though the table is full of dead rows. What is the most likely reason?

      A version can be removed only when no snapshot anywhere could still need it.

      What is transaction ID wraparound, and how is it prevented?

      If freezing is prevented for long enough, PostgreSQL refuses new transaction IDs to protect the data.
