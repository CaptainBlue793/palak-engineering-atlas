Isolation Levels & Anomalies

Two customers buy the last item in stock in the same second. Two requests each read a balance, each subtract from it, and each write the result back. Both programs are correct when run alone, and run together they sell an item that isn't there, or lose a withdrawal. The "I" in ACID is the database's defence, and it is adjustable: there are four isolation levels, and each permits some of these interleavings and forbids others. The default level in PostgreSQL permits most of them. This chapter names the anomalies, reproduces each one with two sessions, shows which level stops which, and explains the errors that the stricter levels ask your code to handle in return.

The anomalies

The ideal is serialisability: the outcome of running transactions together is the same as if they had run one at a time, in some order. Enforcing that fully costs concurrency, so databases also offer weaker guarantees. Each weaker level is defined by the anomalies it lets through, which are the ways concurrent transactions can produce a result that no one-at-a-time order could have.

AnomalyWhat happensExample
Dirty readA transaction reads data that another has written and not yet committedYou read a balance of £50 from a transfer that is then rolled back. The balance was never £50
Non-repeatable readA transaction reads the same row twice and gets different valuesA report reads a balance at its start and again at its end, and its totals don't add up
PhantomA transaction runs the same query twice and gets a different set of rows"Count the pending orders" returns 3, then 4
Lost updateTwo transactions read a value, each computes a new one from it, and the second write overwrites the firstStock is 10. One sale takes 3 and another takes 2. Stock ends at 8
Write skewTwo transactions read the same data, each makes a decision from it, and each writes a different row. Together they break a rule that each one checkedTwo doctors each see that two are on call, and each goes off call

PostgreSQL, Oracle and SQL Server default to Read Committed. MySQL's InnoDB defaults to Repeatable Read, with rules of its own. An application moved from one database to another keeps its SQL and changes its behaviour under concurrency.

Things to notice. At Read Committed, the default, four of the five anomalies happen, and the database raises no error for any of them. The lost update leaves stock at 8 when 5 units were sold, and nothing in any log says so. At Repeatable Read the same statements produce an error on the second writer, could not serialize access due to concurrent update, and the application must run that transaction again, after which the answer is right. Write skew gets through Repeatable Read: the two transactions wrote different rows, so neither saw a conflict. Only Serializable catches it, again by failing one of the two. The stricter levels prevent these anomalies by refusing to let one transaction finish, so code that uses them has to be ready to retry.

Read Committed

At Read Committed, each statement sees the data as it was committed at the moment that statement began. Two statements in the same transaction may therefore see different data, if something committed between them. That one fact accounts for non-repeatable reads and phantoms. It suits short transactions in which each statement stands alone, and that is most of what a web application does.

It is dangerous in the read-then-write pattern, in which the application reads a value, computes with it, and writes back. Three defences work at this level:

-- 1. Let the database do the arithmetic: one statement, so nothing can come between the read and the write
UPDATE items SET stock = stock - 2 WHERE item_id = 7 AND stock >= 2;      -- "UPDATE 0" means there wasn't enough

-- 2. Lock the row when you read it, if the logic can't be put in one statement (Chapter 22)
SELECT stock FROM items WHERE item_id = 7 FOR UPDATE;

-- 3. State the rule as a constraint, so that the second writer fails instead of succeeding wrongly (Chapter 8)
ALTER TABLE items ADD CONSTRAINT stock_not_negative CHECK (stock >= 0);

Repeatable Read / snapshot

At Repeatable Read the transaction takes one snapshot, at its first statement, and every later statement reads from it. Nothing committed by anyone else afterwards is visible, so a report sees one consistent moment however long it runs. In PostgreSQL this level is snapshot isolation, and it stops phantoms as well.

Writes follow a different rule. If the transaction tries to update a row that someone else has changed and committed since its snapshot, it can't proceed on its out-of-date view. PostgreSQL aborts it with a serialisation failure, error code 40001, and the first writer wins. A snapshot that is held open for a long time has a cost as well: old row versions can't be cleaned up while any transaction might still need them (Chapter 23).

Serializable

PostgreSQL's Serializable level runs on the same snapshots, and also tracks which transactions have read data that others have written. When it detects a pattern of such dependencies that couldn't arise in any one-at-a-time ordering, it aborts one of the transactions involved. Readers still don't block writers. The costs are some bookkeeping, a few aborts of transactions that would in fact have been harmless, and the requirement that every transaction be written so that it can be run again.

import psycopg
from psycopg.errors import SerializationFailure, DeadlockDetected

def run_transaction(conn, work, attempts=5):
    for attempt in range(attempts):
        try:
            with conn.transaction():                 # BEGIN … COMMIT, or ROLLBACK if anything is raised
                return work(conn)                    # must read everything afresh: no values kept from the last try
        except (SerializationFailure, DeadlockDetected):
            if attempt == attempts - 1:
                raise
            time.sleep(0.01 * 2 ** attempt * random.random())   # back off, with jitter

The retry must run the whole transaction again from its first read, because the decision it made was based on data that has since changed. For the same reason, a transaction that is to be retried must have no side effects outside the database, such as an email or a call to a payment provider, part-way through.

Write skew

Write skew is the anomaly that survives snapshot isolation, and it has a recognisable shape. A transaction reads some rows, checks a rule about them as a group, and then writes a row. Another transaction does the same, reading the same group and writing a different row. Each one's write would have changed the result of the other's check. Since they update different rows, no row is written twice, and the first-writer-wins rule has nothing to act on.

Rule that is checked, then acted onHow it breaks
At least one doctor must be on callTwo go off call at once, each having seen the other on call
A room may not be booked twice for the same timeTwo bookings each check for a clash, find none, and insert
A username must be unique, checked by a SELECTTwo sign-ups each find the name free
The total across a customer's accounts must stay positiveTwo withdrawals from different accounts each see enough in the total

The remedies, from most to least preferable: express the rule as a constraint, a unique index for the username or an exclusion constraint for the room (Chapter 8), which the database enforces at any level. Or run the transactions at Serializable and retry. Or lock the rows that the decision was read from, with SELECT … FOR UPDATE, so that the second transaction has to wait and then sees the first one's write.

🌧️
ACIDRain: twelve shops, twenty-two ways to steal from them

In 2017 two researchers at Stanford, Todd Warszawski and Peter Bailis, asked how much the anomalies in this chapter matter outside textbooks. They took twelve widely used open-source e-commerce applications, which between them ran a substantial share of the online shops on the internet, and analysed the SQL that each one sent while handling requests. They were looking for places where the application read a value in one statement and acted on it in another, with nothing to stop a concurrent request from coming between. They found twenty-two that could be exploited by doing nothing more than sending ordinary requests at the same moment. A gift voucher worth £50 could be spent in two baskets at once, since both checked the balance before either reduced it. The last item in stock could be sold to several buyers. A basket could be altered between the calculation of the price and the taking of payment. Every application ran on a database that supported transactions, and most of the vulnerable code ran inside one. The transactions were at the default isolation level, or the read and the write had been put in separate transactions, or the database was one whose default permitted the anomaly. The authors called the attack ACIDRain. Three years earlier a small Bitcoin exchange, Flexcoin, had closed after an attacker sent thousands of simultaneous transfers between two accounts and drained its hot wallet through just such a gap between checking a balance and reducing it. Wrapping statements in BEGIN and COMMIT gives atomicity. Protection against concurrent requests depends on the isolation level in force and on which anomalies it lets through.

⚠️
Common mistakes
  • Assuming a transaction means "nobody else can interfere". At the default level, plenty can.
  • Read, compute in the application, write back. Use one atomic UPDATE, or lock the row when reading.
  • Raising the isolation level without adding retries. The anomalies turn into errors, and unhandled errors turn into failed requests.
  • Retrying only the statement that failed. The whole transaction must run again from its first read.
  • Checking a rule with a SELECT and enforcing it with nothing. If the rule can be a constraint, make it one.
  • Assuming MySQL's Repeatable Read and PostgreSQL's are the same. They differ on lost updates and on what locking reads see.

Interview drill

Explain it simply: What are the isolation levels, and what does each prevent?

How a strong answer sounds
There are four in the SQL standard, defined by the anomalies they allow. Read Uncommitted allows dirty reads, seeing another transaction's uncommitted changes. Read Committed prevents that: each statement sees only committed data, but two statements in one transaction can see different data, so non-repeatable reads and phantoms are possible; it is the default in PostgreSQL, Oracle and SQL Server. Repeatable Read gives the transaction a stable view of rows it has read; the standard still permits phantoms there, though PostgreSQL implements it as snapshot isolation, which prevents phantoms too, and aborts a transaction that tries to update a row changed since its snapshot, which prevents lost updates. Serializable guarantees the result is equivalent to some serial order, which additionally prevents write skew. Two practical points: the stricter levels in an MVCC database work by aborting transactions with serialisation failures, so the application must retry; and implementations differ, so MySQL's Repeatable Read is not PostgreSQL's. I'd pick the level per transaction: Read Committed with atomic statements and constraints for most work, and Serializable, with retries, for logic that checks an invariant across rows.

Deeper: What is write skew? Give an example, explain why snapshot isolation allows it, and say how you would prevent it.

How a strong answer sounds
Write skew is when two concurrent transactions each read an overlapping set of data, make a decision based on it, and then write to different rows, such that the combined result violates an invariant that each transaction individually preserved. The standard example is on-call doctors: the rule is that at least one must be on call. Alice and Bob are both on call; each starts a transaction, counts two doctors on call, concludes it is safe to leave, and sets their own row to off. Both commit, and nobody is on call. Snapshot isolation doesn't catch it because its conflict rule is about writes to the same row: the first committer wins and the second is aborted. Here the write sets are disjoint, Alice's row and Bob's row, so there is no write-write conflict; the conflict is between one transaction's read and the other's write, which snapshot isolation doesn't track. To prevent it: best, encode the invariant as a database constraint where one exists, such as a unique or exclusion constraint for double bookings. Otherwise, use Serializable isolation, which in PostgreSQL tracks read-write dependencies and aborts one of the transactions, and retry it; on retry it sees one doctor on call and refuses. Or take explicit locks on the rows the decision depends on, SELECT … FOR UPDATE on the on-call rows, so the second transaction blocks until the first commits and then re-reads. If the decision depends on the absence of rows, there is nothing to lock, and I'd materialise the conflict: lock a parent row or use an advisory lock keyed on the thing being protected.

🧠 Key takeaways

  • Isolation levels are defined by which anomalies they allow: dirty reads, non-repeatable reads, phantoms, lost updates and write skew.
  • Read Committed, the default in PostgreSQL, gives each statement its own view. It permits everything except dirty reads, and reports nothing when an anomaly happens.
  • Repeatable Read in PostgreSQL is snapshot isolation: one view for the whole transaction, and an error for a writer whose row has changed since.
  • Write skew involves writes to different rows, so snapshots don't catch it. Serializable does, by aborting one transaction.
  • The stricter levels turn anomalies into serialisation failures, which the application has to retry from the start of the transaction.
  • At any level, an atomic UPDATE, a row lock or a constraint is a more direct defence than hoping two requests don't coincide.

Check your understanding

Two transactions read stock = 10. One writes 7 and commits, then the other writes 8 and commits, at Read Committed. What is this called, and does the database report it?

Both transactions succeed. The first one's write is silently overwritten.

In PostgreSQL at Read Committed, a transaction runs the same SELECT twice and gets different results. Why?

This is a non-repeatable read, or a phantom if the set of rows changed. Repeatable Read uses one snapshot for the whole transaction.

At Repeatable Read in PostgreSQL, a transaction tries to UPDATE a row that another transaction changed and committed after the first one's snapshot. What happens?

The first writer wins. That is how this level prevents lost updates.

Why doesn't snapshot isolation prevent write skew?

The conflict is between one transaction's read and the other's write, which only Serializable tracks.

A transaction at Serializable fails with a serialisation failure. What should the application do?

Its reads are out of date, so everything decided from them has to be decided again.
