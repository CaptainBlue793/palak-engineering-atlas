SQL Interview Drills

SQL questions in interviews come from a small stock. The table names change, employees and salaries one day and orders and customers the next, and underneath there are perhaps a dozen patterns: the Nth value, the top few rows in each group, runs of consecutive days, a running total, rows turned into columns. Someone who has seen a pattern recognises it in a new wording within seconds. Someone who hasn't tries to invent it under pressure, and the usual result is a query that works on the example and fails on ties, on NULLs or on an empty group. This chapter works through five of the patterns that come up most, each with the reasoning, the query, and the edge case the interviewer is waiting for. All of them rest on the window functions of Chapter 6.

  • Find the Nth-highest value correctly when there are ties
  • Return the top N rows in each group, and say what happens to ties
  • Group consecutive rows into runs, the gaps-and-islands technique
  • Compute running totals and moving averages, and avoid the default-frame trap
  • Turn rows into columns with conditional aggregation

Second-highest salary

The question is about the second-highest value, so duplicates of the top value mustn't count twice. Two forms are worth knowing.

-- The largest value below the largest. Returns NULL if there is no second value.
SELECT max(salary) AS second_highest
FROM   employees
WHERE  salary < (SELECT max(salary) FROM employees);

-- The general form: the Nth-highest value, here N = 2
SELECT DISTINCT salary
FROM  (SELECT salary, dense_rank() OVER (ORDER BY salary DESC) AS r FROM employees) ranked
WHERE  r = 2;

Top-N per group

"The three most recent orders for each customer", "the best-selling product in each category". GROUP BY can't do it, since it returns one row for each group and loses the others. The pattern is to number the rows within each group and keep the low numbers.

WITH ranked AS (
  SELECT name, department, salary,
         row_number() OVER (PARTITION BY department ORDER BY salary DESC, emp_id) AS rn
  FROM   employees
)
SELECT name, department, salary FROM ranked WHERE rn <= 2;      -- a window function can't appear in WHERE, hence the CTE

-- Top 1 in each group, PostgreSQL's shortcut
SELECT DISTINCT ON (department) name, department, salary
FROM   employees
ORDER BY department, salary DESC, emp_id;

-- When groups are few and the table is large: one index probe for each group
SELECT d.department, top.name, top.salary
FROM   departments d
CROSS JOIN LATERAL (SELECT name, salary FROM employees e
                    WHERE e.department = d.department
                    ORDER BY salary DESC LIMIT 2) top;

The tie-breaker in the first query, emp_id, is there so that the result is the same every time it runs. The lateral form matters for performance: the window version reads and sorts every row of the table, where the lateral version, with an index on (department, salary DESC), reads two index entries for each department.

Gaps and islands

"Find each user's longest streak of consecutive days", "find periods when the sensor was above its threshold". The rows form runs, called islands, separated by gaps, and nothing in a row says which run it belongs to. There are two techniques.

For consecutive dates or integers, subtract a row number. Within a run, the date and the row number both go up by one each row, so their difference stays the same. A gap makes the date jump and the row number doesn't follow, so the difference changes.

WITH numbered AS (
  SELECT user_id, day,
         day - (row_number() OVER (PARTITION BY user_id ORDER BY day))::int AS grp
  FROM  (SELECT DISTINCT user_id, day FROM logins) d        -- one row for each day, or two logins in a day break it
)
SELECT user_id, min(day) AS starts, max(day) AS ends, count(*) AS days
FROM   numbered
GROUP BY user_id, grp
ORDER BY user_id, starts;

For anything else, where a new run begins whenever some condition holds, flag the first row of each run with lag, and take a running sum of the flags. The sum goes up by one at each start, so it numbers the runs.

-- A new session starts when more than 30 minutes have passed since the user's previous event
WITH flagged AS (
  SELECT user_id, ts,
         CASE WHEN ts - lag(ts) OVER w > interval '30 minutes' OR lag(ts) OVER w IS NULL
              THEN 1 ELSE 0 END AS starts_session
  FROM   events
  WINDOW w AS (PARTITION BY user_id ORDER BY ts)
)
SELECT user_id, ts,
       sum(starts_session) OVER (PARTITION BY user_id ORDER BY ts) AS session_no
FROM   flagged;

Running totals

An aggregate with ORDER BY in its window accumulates. The trap is in what it accumulates over, the frame, when rows tie in the ordering.

SELECT pay_id, day, customer, amount,
       sum(amount) OVER (ORDER BY day, pay_id)                        AS running_total,
       sum(amount) OVER (PARTITION BY customer ORDER BY day, pay_id)  AS customer_total,
       avg(amount) OVER (ORDER BY day, pay_id
                         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)    AS moving_avg_3
FROM   payments;

The safe habit is to make the ordering unique. A related question, "what share of the total is each row", uses an empty window: amount / sum(amount) OVER ().

Pivoting

A pivot turns the values of one column into column headings: one row for each region, one column for each quarter. Standard SQL has no pivot operator. The portable method is one aggregate for each output column, each restricted to its own rows.

SELECT region,
       sum(amount) FILTER (WHERE quarter = 'Q1') AS q1,
       sum(amount) FILTER (WHERE quarter = 'Q2') AS q2,
       sum(amount) FILTER (WHERE quarter = 'Q3') AS q3,
       sum(amount) FILTER (WHERE quarter = 'Q4') AS q4,
       sum(amount)                               AS total
FROM   sales
GROUP BY region
ORDER BY region;

-- The same without FILTER, for databases that lack it
sum(CASE WHEN quarter = 'Q1' THEN amount END) AS q1

Three points to make unprompted. The columns have to be written out, since a query's column list is fixed before it runs: a pivot over values not known in advance needs the SQL to be generated, or is better done in the application. A cell with no rows is NULL, so wrap it in coalesce(…, 0) if zero is meant. And GROUP BY ROLLUP (region) adds a grand-total row. The reverse operation, columns to rows, is a UNION ALL of one select for each column, or a join to a VALUES list.

Web analytics: a session is an island

The gaps-and-islands question has the air of a puzzle made up for interviews, and it is in fact one of the most frequently run queries in industry. Every web analytics product reports sessions: how many visits a site had, how long they lasted, how many pages each took in. No event carries a session number, though. What arrives from the browser is a stream of page views and clicks, each with a user identifier and a timestamp. A session is a definition laid over that stream, and the one Google Analytics made standard is that a session ends after thirty minutes without activity: the next event from that user, however much later, begins a new one. Turning the stream into sessions is the second query in the gaps-and-islands section above, unchanged. Order each user's events by time, compare each with the one before using lag, flag those that follow a gap of more than thirty minutes, and take a running sum of the flags to number the sessions. Grouping by user and session number then gives each session's start, end, duration and event count, and everything in a traffic report is an aggregate over that. Companies that export their raw analytics events to a warehouse such as BigQuery, and analysts who build their own reports on those exports, write this query themselves, and it runs over billions of rows a day, which is one reason warehouses are built to execute window functions in parallel across partitions (Chapter 28). The same shape appears wherever a log has to be cut into episodes: trips from GPS pings, outages from failed health checks, machine cycles from sensor readings.

⚠️
Common mistakes
  • LIMIT 1 OFFSET 1 for the second-highest value. It skips a row, and with a tie at the top that row holds the same value.
  • Not asking about ties. row_number, rank and dense_rank give three different answers.
  • A window function in WHERE. Windows are computed after filtering. Use a CTE or subquery and filter outside.
  • A running total ordered by a column with duplicates, so that tied rows share one total.
  • Forgetting to de-duplicate before the row-number trick in gaps and islands.
  • Writing the whole query in one go. Stages can be checked. A single nested statement can't.

Interview drill

Explain it simply: What is the difference between ROW_NUMBER, RANK and DENSE_RANK?

How a strong answer sounds
All three number rows within a window according to its ORDER BY. They differ only in what they do with ties. ROW_NUMBER gives every row a distinct number, 1, 2, 3, 4, so tied rows get different numbers in an order that is arbitrary unless the ORDER BY is made unique. RANK gives tied rows the same number and then skips: 1, 1, 3, 4, as in a race where two people come joint first and the next is third. DENSE_RANK gives tied rows the same number and doesn't skip: 1, 1, 2, 3. So I'd use ROW_NUMBER when I need exactly N rows or want to de-duplicate, keeping row 1 of each group; RANK for competition-style ranking; and DENSE_RANK when the question is about the Nth distinct value, such as the second-highest salary, since DENSE_RANK = 2 is the second value however many people share the first. When someone asks for "the top 3", I ask whether ties should all be included, since that decides which function is right.

Deeper: Given orders(customer_id, order_date), find each customer's longest run of consecutive days with at least one order. Talk through it.

How a strong answer sounds
First, clarify: several orders on one day count as one day, and the output is one row for each customer with the length of the longest streak, perhaps with its start and end. It is a gaps-and-islands problem over dates. Step one, reduce to one row for each customer and day with SELECT DISTINCT customer_id, order_date. Step two, number each customer's days in order with ROW_NUMBER partitioned by customer and ordered by date, and subtract that number from the date. Within a run of consecutive days both go up by one each row, so the difference is constant; after a gap the date jumps further than the row number, so the difference changes. That difference is a label for the island. Step three, group by customer and that label, taking min(date), max(date) and count(*) as the streak's start, end and length. Step four, pick the longest for each customer: either max(length) grouped by customer, or, to keep the dates, ROW_NUMBER partitioned by customer ordered by length descending and keep row 1, with a tie-breaker such as the most recent. I'd write it as three CTEs so that each step can be inspected. On cost: it needs a sort by customer and date, which an index on (customer_id, order_date) supplies. If the definition of consecutive were looser, say allowing weekends to be skipped, I'd switch to the lag-and-running-sum method, flagging a new island whenever the gap to the previous date exceeds the allowance.

🧠 Key takeaways

  • Before writing, restate the question on a small example and ask about ties, NULLs and duplicates.
  • Nth-highest value: dense_rank(). Exactly N rows: row_number() with a unique ordering.
  • Top-N per group: number the rows within each partition in a CTE, and filter outside it.
  • Gaps and islands: date minus row number for consecutive runs, or lag with a running sum of flags for any other rule.
  • Running totals: make the window's ORDER BY unique, or tied rows share a total.
  • Pivot with one filtered aggregate for each column. The columns must be known when the query is written.

Check your understanding

Salaries are 90, 90, 80, 70. What does dense_rank() OVER (ORDER BY salary DESC) assign to the 80?

Dense rank numbers the distinct values without gaps: 1, 1, 2, 3. rank() would give 3.

Why can't you write WHERE row_number() OVER (…) <= 3?

Compute the number in a CTE or subquery, and filter in the query around it.

In the gaps-and-islands technique, why is day − row_number() the same for every day in a streak?

A gap makes the date jump ahead of the row number, so the next streak gets a different constant.

Two payments fall on the same day. With sum(amount) OVER (ORDER BY day), what do those two rows show?

The default frame runs to the end of the current row's ties. Order by something unique, or use a ROWS frame.

In a pivot built with sum(amount) FILTER (WHERE quarter = 'Q3'), what does a region with no Q3 sales show?

sum over no rows is NULL. Wrap it in coalesce(…, 0) if zero is meant.
