Column Stores & OLAP

Everything in this course so far has stored a row together: all of an order's columns, side by side on one page. That is right for fetching or changing one order. It is wrong for the question "what was our revenue in each country last quarter?", which needs two columns out of thirty from a hundred million rows, and a row store has to read the other twenty-eight to get at them. Analytical databases turn the table on its side and store each column by itself. That one change makes scans read a small fraction of the bytes, lets the data be compressed to a tenth of its size, and suits a way of executing queries that is several times faster again. This chapter explains how, and what is given up in return.

The two workloads want opposite things from storage, so they are usually served by two systems. Data is written to a transactional database and copied to an analytical one, the data warehouse, for reporting (Chapter 48).

Columnar layout

Row store: one row after another. Every page holds every column.
  │ 1 │ 2026-07-01 │ DE │ 3 │ 59.97 │ … │ 2 │ 2026-07-01 │ FR │ 1 │ 19.99 │ … │ 3 │ 2026-07-01 │ DE │ 2 │ …

Column store: one column after another. Each is stored, compressed and read separately.
  sale_id    │ 1 │ 2 │ 3 │ 4 │ 5 │ …
  sale_date  │ 2026-07-01 │ 2026-07-01 │ 2026-07-01 │ 2026-07-01 │ …
  country    │ DE │ FR │ DE │ DE │ IN │ …
  quantity   │ 3 │ 1 │ 2 │ 1 │ 4 │ …
  amount     │ 59.97 │ 19.99 │ 39.98 │ 9.99 │ …

A query that needs country and amount opens those two columns and never touches the rest. The n-th value in every column belongs to the n-th row, so rows are put back together by position when they are needed.

The columns are further cut into row groups of perhaps a million rows. For each group and each column the file records the smallest and largest value. A query with a filter reads those summaries first and skips every group that can't contain a match, exactly as a BRIN index does (Chapter 15). If the table is kept sorted by date, a query for one quarter skips three-quarters of the file without reading it.

Compression and encoding

A page of a row store holds a mixture of integers, dates, strings and prices, and general-purpose compression does little with it. A column holds values of one type, often similar to their neighbours, and frequently repeating, and that can be encoded very compactly.

EncodingIdeaExampleGood for
DictionaryStore each distinct value once, and replace the values with small integer codes200 country names become codes of 1 byte eachText columns with few distinct values
Run-lengthStore a value and how many times it repeats(2026-07-01 × 1,100,000), (2026-07-02 × 1,084,000), …Sorted columns, and columns that rarely change from row to row
DeltaStore the difference from the previous valueIds 1001, 1002, 1003 become +1, +1, +1Increasing ids and timestamps
Bit-packingUse only as many bits as the largest value needsQuantities from 1 to 12 take 4 bits, not 32Small integers
General compressionLZ4 or Zstandard over the encoded blockFree text shrinks about threefoldWhatever is left

A warehouse table commonly occupies a fifth to a tenth of the space it took in a row store. That saves money, and it saves time too: the limit on a scan is how fast bytes come off storage, and data that is ten times smaller is read ten times sooner. Some operations run on the encoded form directly. To count the rows for one day in a run-length-encoded date column, the engine reads one number.

Vectorised execution

Chapter 16 explained why an engine that passes one row at a time between operators spends most of its effort on the passing. A column store passes a block of a few thousand values from one column, and each operator is a tight loop over an array: compare these 4,096 dates with a constant, add up these 4,096 amounts. The processor can run such loops with instructions that handle eight or sixteen values at once, and the data it needs is contiguous in memory. Together, reading less, decompressing cheaply and executing in blocks make an analytical query on a column store commonly ten to a hundred times faster than the same query on a row store, on the same hardware.

Things to notice. For one quarter's revenue the row store reads the whole table, 13.6 GB, because the two columns it needs are interleaved with the other six on every page. The column store reads two columns of two bands: 300 MB uncompressed, and about 100 MB compressed, less than 1% of what the row store read. Revenue by country can't skip any band, and still reads only two columns: 500 MB against 13.6 GB. Then try fetching one sale by its id. The row store's index finds it in four pages, 32 kB. The column store has to open all eight columns of one row group and decompress them to reassemble a single row, about 32 MB, a thousand times as much. Inserting one sale is as lopsided. Analysis favours the column layout by about the same factor that single-row work favours the row layout, and that is why the two workloads are kept in different systems.

Star schemas

Warehouses are usually organised round one very large table of events and several small tables that describe them. The events are the fact table: one row for each sale, each click, each shipment, holding numbers to be added up, the measures, and keys pointing to the descriptions. The descriptions are dimension tables: the product, the customer, the shop, the date. Drawn with the fact table in the middle, it is a star.

-- the fact: billions of rows, narrow, append-only
fact_sales (date_key, product_key, customer_key, store_key, quantity, amount, discount)

-- the dimensions: thousands to millions of rows, wide, deliberately denormalised
dim_date     (date_key, date, weekday, month, quarter, year, is_holiday)
dim_product  (product_key, name, brand, category, department)
dim_store    (store_key, name, city, region, country)

SELECT s.country, d.quarter, sum(f.amount) AS revenue
FROM fact_sales f
JOIN dim_store s ON s.store_key = f.store_key
JOIN dim_date  d ON d.date_key  = f.date_key
WHERE d.year = 2026
GROUP BY s.country, d.quarter;

The star suits a column store well. Every analytical question has the same shape: filter and group by attributes of dimensions, add up measures from the fact. The dimensions are small enough to hold in memory as hash tables, and the fact table's key columns compress to almost nothing.

📊
Cloudflare: six million rows a second into a column store

Cloudflare sits in front of a large share of the web's sites, and it shows each customer analytics for their traffic: requests by country, by status code, by the minute. Every HTTP request it serves becomes a row with around a hundred columns, and by 2018 that was about six million rows every second. Its first analytics system didn't keep the rows. A pipeline of several systems consumed the stream, computed a fixed set of aggregates in advance, and stored those in a sharded PostgreSQL database, because nothing they had could query the raw data quickly enough. It worked, at the cost of flexibility and effort: a new kind of chart meant a new aggregate, a change to the pipeline, and no history for it from before the change. The engineers described replacing all of this with ClickHouse, an open-source column store. The raw rows went straight in, a hundred columns wide, and compressed to a small fraction of their size, since a column such as the data-centre identifier or the status code has few distinct values and long runs. A customer's dashboard query filters on their account and a time range, which are the keys the table is sorted by, so nearly all row groups are skipped, and it reads perhaps three of the hundred columns. Queries over billions of rows came back in well under a second. The number of systems in the pipeline fell, new charts became new queries, and the cluster ran on a few dozen machines. A row store couldn't have read that much data fast enough, and the column store answered the same questions by reading only a small part of it.

⚠️
Common mistakes
  • Running heavy analytics on the transactional database. A report that scans the orders table competes with checkout for memory and I/O. Use a replica at least, and a warehouse when it grows.
  • Using a column store for transactions. Single-row inserts, updates and lookups are its worst case.
  • SELECT * on a column store. It throws away the main advantage by reading every column.
  • Loading a row at a time. Column stores want batches of thousands of rows or more, so that each batch becomes well-compressed blocks.
  • Ignoring the sort order. Skipping row groups works only for filters on the columns the table is sorted or clustered by.
  • Copying the normalised production schema into the warehouse unchanged. Every question then needs a dozen joins.

Interview drill

Explain it simply: Why are analytical databases column-oriented?

How a strong answer sounds
Because analytical queries read a few columns from a very large number of rows, and a columnar layout makes that cheap in three ways. First, I/O: each column is stored separately, so a query touching three columns of a fifty-column table reads roughly three fiftieths of the data, where a row store must read whole rows. Per-block minimum and maximum values let it skip blocks that can't match the filter. Second, compression: a column contains values of one type that tend to repeat or change slowly, so dictionary, run-length, delta and bit-packing encodings shrink it by five to ten times, which again reduces I/O, and some operations run on the encoded data. Third, execution: operators process batches of column values in tight loops that use the CPU cache and SIMD well, instead of interpreting one row at a time. The trade-off is that reading or writing a single whole row is expensive, since it touches every column file, and updates in place don't fit compressed blocks, so column stores are loaded in batches and are poor at transactional work. That is why OLTP stays on row stores and data is copied to a columnar warehouse for analysis.

Deeper: What is a star schema, and why is it used in warehouses instead of a normalised design?

How a strong answer sounds
A star schema has a central fact table and surrounding dimension tables. The fact table has one row per business event at a chosen grain, a line of a sale, say, and contains foreign keys to the dimensions plus numeric measures like quantity and amount. Each dimension table describes one aspect of the event, date, product, customer, store, with all its descriptive attributes flattened into one wide row, including hierarchies: a product row carries its brand, category and department. A normalised design would split those into separate tables to avoid redundancy and update anomalies, which is the right goal for a transactional system. A warehouse has different goals: it is loaded in bulk and queried, not updated row by row, so update anomalies matter less; and its queries nearly all have the form "aggregate measures from the fact, filtered and grouped by dimension attributes". The star makes those queries simple and fast: one join from the fact to each dimension used, small dimensions that fit in memory as hash tables, and a narrow fact table whose key columns compress extremely well in a column store. It also models history: dimensions can keep versions, so a sale is tied to the product's attributes as they were then. A snowflake schema normalises the dimensions further, which saves a little space and adds joins; many modern warehouses go the other way and denormalise into one very wide table, since columnar storage makes unused columns free.

🧠 Key takeaways

  • Transactional queries touch a few whole rows, and analytical ones touch a few columns of very many rows. The best storage for each is the opposite of the other's.
  • A column store keeps each column separately, so a query reads only the columns it names, and skips row groups whose minimum and maximum rule them out.
  • Columns compress five to ten times with dictionary, run-length, delta and bit-packing encodings, which also means less to read.
  • Execution works on blocks of column values in tight loops, removing most of the cost of handling each row.
  • Fetching or writing one row is slow in a column store, so it is loaded in batches and not used for transactions.
  • A star schema puts measures in a large fact table and descriptions in small, denormalised dimension tables.
