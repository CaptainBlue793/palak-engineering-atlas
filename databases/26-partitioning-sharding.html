Partitioning & Sharding

A table that keeps growing eventually becomes a problem in itself. Its indexes no longer fit in memory, VACUUM takes hours, removing old data means deleting a billion rows, and in the end one machine can't hold it or keep up with the writes. The remedy has two stages. Partitioning splits a table into smaller tables inside one database, which the database then manages for you. Sharding splits the data across several databases on several machines, which nothing manages for you. Both rest on one decision, the key by which rows are assigned to their pieces, and that decision determines which queries stay cheap and which become expensive from then on. This chapter covers both stages and how to choose the key.

Declarative partitioning

A partitioned table is a parent with no data of its own and a set of child tables that hold the rows. Each row goes to the child that its partition key selects.

CREATE TABLE events (
  event_id    bigint GENERATED ALWAYS AS IDENTITY,
  created_at  timestamptz NOT NULL,
  user_id     bigint NOT NULL,
  payload     jsonb,
  PRIMARY KEY (event_id, created_at)                 -- a unique key must include the partition key
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE events_2026_11 PARTITION OF events FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

DROP TABLE events_2025_10;                           -- a month of data gone in milliseconds, space returned at once
MethodRows are assigned byTypical use
RANGEWhich interval the key falls inTime: a partition for each day or month
LISTThe key's exact valueRegion, tenant, status
HASHA hash of the key, modulo the number of partitionsSpreading rows evenly when there is no natural grouping

The gains are in operations. Old data is removed by dropping a partition, where a DELETE of a billion rows would take hours and leave the table full of dead space (Chapter 23). Each partition has its own, smaller indexes, and those of the current month fit in memory when the whole table's wouldn't. VACUUM works on one partition at a time, and partitions that no longer change need hardly any.

Partition pruning

A query on the parent table is planned against every partition, and then the planner removes those that the WHERE clause rules out. This is partition pruning, and it is the reason queries on a partitioned table can be fast.

EXPLAIN SELECT count(*) FROM events WHERE created_at >= '2026-10-05' AND created_at < '2026-10-06';
 Aggregate
   ->  Index Only Scan using events_2026_10_created_at_idx on events_2026_10     -- one partition of 36

EXPLAIN SELECT * FROM events WHERE user_id = 4242;                          -- no condition on the partition key
 Append
   ->  Index Scan using events_2023_11_user_id_idx on events_2023_11
   ->  Index Scan using events_2023_12_user_id_idx on events_2023_12
   …  and 34 more: every partition is searched

Pruning only happens when the query constrains the partition key. A query that doesn't mention it has to visit every partition, and with hundreds of partitions that is slower than one large table would have been. So the partition key should be a column that nearly every query filters on, and for time-series data that is the timestamp.

Choosing a shard key

Sharding applies the same idea across machines, with a shard key deciding which database holds each row. The stakes are higher, because what was merely slow under partitioning, a query that visits every piece, now means a network request to every machine, and a transaction that touches two pieces is no longer an ordinary transaction.

A good shard keyBecause otherwise
Is in nearly every queryQueries without it must be sent to all shards
Keeps together what is read and written togetherJoins and transactions cross shards
Spreads data evenlyOne shard fills up while the others sit half empty
Spreads load evenly, and not only dataOne shard takes most of the writes and becomes the limit for the whole system
Has many distinct valuesA key with five values can never be split across more than five shards
Never changes for a rowChanging it means moving the row to another database

For most applications that serve many customers, the key that satisfies these is the customer, tenant or user identifier: nearly every query is about one customer, and all of that customer's rows land on one shard.

    Things to notice. Sharding by customer keeps each customer's orders on one shard, so the two most frequent operations, listing a customer's orders and placing an order, touch one shard and need no cross-shard transaction. Its weakness shows when one customer is very large: the shard that holds them has nearly half the data and half the writes. Sharding by order id spreads everything perfectly, even with the large customer, and makes the commonest query the worst: a customer's orders are on every shard. Sharding by date balances the data and sends every write to one shard. That shard does all the work while the other three sit idle, so the system has four machines and the write capacity of one. Each key makes a different set of queries cheap, and the choice should be made for the queries the application runs most often.

    Cross-shard queries

    Operation across shardsWhat it takes
    A query without the keyScatter and gather. Tolerable for the occasional report, ruinous for a frequent request
    A join between tables on different shardsUsually avoided by design: shard related tables by the same key, and keep a copy of small reference tables on every shard
    A transaction that changes two shardsTwo-phase commit: each shard first prepares and promises it can commit, and only when all have promised does the coordinator tell them to commit. It is slower, and a coordinator that fails between the phases leaves transactions in doubt, holding their locks
    A unique constraint on anything but the shard keyNo single database can check it. It needs a separate lookup table, or must be given up
    Generating identifiersA sequence in each database would produce duplicates, so identifiers must be made unique some other way (Chapter 46)

    Resharding

    The simplest routing rule is shard = hash(key) mod N. It works until N has to change. Going from four shards to five changes the result for about four keys in five, so nearly all the data has to move, while the system is live. Three designs avoid this.

    DesignHow it worksAdding capacity
    Many logical shardsHash keys into a large fixed number of logical shards, say 4,096, and keep a small table saying which physical database holds eachMove whole logical shards to a new machine and update the table. Keys never change their logical shard
    Consistent hashingPlace both keys and nodes on a ring. A key belongs to the next node round the ringA new node takes over a share of its neighbours' keys only
    A directoryA lookup service records where each key, or range of keys, livesMove any key or range and update the directory. Most flexible, and the directory becomes critical

    Moving data between live shards follows the same steps whatever the design: copy the existing rows, keep applying the changes that arrive meanwhile, verify that source and destination agree, switch reads and then writes, and delete the old copy only after a period of confidence. Systems such as Vitess for MySQL and Citus for PostgreSQL exist to do the routing and the moving for you, and Chapter 36 covers databases that shard themselves.

    🐘
    Notion: sharding a PostgreSQL monolith under pressure

    Until 2021 Notion kept nearly all its data, every page and every block of text on it, in one PostgreSQL database, which had been scaled up through larger and larger machines for five years. By 2020 the engineers were watching two warning signs get worse. VACUUM on the largest tables was stalling, which left dead rows to pile up, and behind that stood the risk of transaction ID wraparound, which would have stopped all writes (Chapter 23). And the on-call engineers were being woken regularly by processor spikes on the database. They decided to shard, and wrote afterwards about how. The shard key was the workspace identifier. A workspace is one customer's whole collection of pages, nearly every query concerns a single workspace, and all the tables that hang off a block could carry its workspace's identifier, so that related rows stay together. They divided the data into 480 logical shards and placed them on 32 physical databases, fifteen to a machine, a number chosen because it divides evenly in many ways and so leaves room to spread the logical shards over more machines later without re-hashing anything. The migration ran in the stages listed above. New writes were recorded for both systems, old data was copied over, a verification job compared the two, a sample of live reads was checked against both, and then the switch was made during a brief planned outage. Two years later they split the 32 databases into 96 by moving logical shards, as designed. The lesson they drew was about timing: they had waited until the old database was close to its limits, which left the migration little room for error, and they would start sooner next time.

    ⚠️
    Common mistakes
    • Sharding before it is needed. A single PostgreSQL machine with replicas handles tens of thousands of transactions a second and terabytes of data.
    • Sharding by time, or by an increasing id, in ranges. Every write goes to the newest shard.
    • A partition or shard key that most queries don't filter on. Every such query visits every piece.
    • hash mod N on the physical shard count. The first time N changes, everything moves.
    • Thousands of partitions. Planning slows down, since the planner considers each one. Hundreds is comfortable.
    • Forgetting the default partition, or to create next month's. Inserts fail on the first of the month.

    Interview drill

    Explain it simply: What is the difference between partitioning and sharding?

    How a strong answer sounds
    Both split a large table into smaller pieces by some key; the difference is where the pieces live. Partitioning keeps them in one database: the table is divided into child tables by range, list or hash of a partition key, and the database routes rows and prunes partitions transparently, so joins, transactions and constraints work as before. Its benefits are operational: dropping old data instantly by dropping a partition, smaller indexes, cheaper vacuuming, and queries that touch only the relevant partitions. It doesn't add capacity, since it is still one machine. Sharding puts the pieces in separate databases on separate machines, so it scales writes and storage beyond one machine, but the database no longer hides it: something has to route each query by its shard key, queries without the key must be sent to all shards, and joins and transactions across shards are expensive or unavailable. So I'd partition large tables routinely, and shard only when a single primary with replicas can't handle the write load or the data size.

    Deeper: You need to shard a multi-tenant application's database. How do you choose the shard key, and what problems do you expect?

    How a strong answer sounds
    I'd start from the queries, not the data. The key should appear in nearly every query, so each one can be routed to a single shard, and it should co-locate rows that are joined or modified together, so that transactions stay within a shard. For a multi-tenant application that is almost always the tenant ID: requests are scoped to one tenant, and every tenant-owned table can carry the tenant ID, even where it is denormalised onto child tables. It has high cardinality and never changes. I'd hash it into a large fixed number of logical shards, a few thousand, mapped to physical databases through a lookup table, so that I can add machines later by moving logical shards without re-hashing. The problems I'd expect: skew, because tenants differ in size by orders of magnitude, so one large tenant can dominate a shard; I'd want the ability to place a big tenant on its own shard, and monitoring per shard. Cross-tenant queries, such as admin reports and analytics, become scatter-gather; I'd move those to a warehouse fed by change capture. Global uniqueness, emails for instance, can't be enforced by one database any more, so I'd keep a small unsharded lookup. IDs need a scheme that is unique across shards. Schema migrations, backups and deployments now run against many databases and need tooling. And the migration itself is the riskiest part: dual-writing or replicating, backfilling, verifying and cutting over, which I'd rehearse on a copy before doing it live.

    🧠 Key takeaways

    • Partitioning splits a table inside one database and is nearly transparent. Sharding splits data across databases and touches everything.
    • Partitioning's gains are operational: old data dropped at once, smaller indexes, cheaper VACUUM.
    • Pruning needs the partition key in the WHERE clause. Without it, every partition is searched.
    • A shard key should be in nearly every query, keep related rows together, and spread both data and writes. A tenant or customer id usually does.
    • Queries without the key go to every shard, and transactions across shards need two-phase commit.
    • Hash into many logical shards mapped to few machines, so that capacity can be added without moving every row.

    Check your understanding

    A table is partitioned by month on created_at. You need to remove everything older than two years. What is the best way?

    Dropping a partition removes its files at once. A DELETE would write a dead version of every row and need vacuuming afterwards.

    The same table is queried with WHERE user_id = 4242 and no condition on created_at. What does the planner do?

    Pruning needs a condition on the partition key. PostgreSQL has no index that spans partitions.

    Orders are sharded by ranges of created_at. What goes wrong?

    New rows all have recent timestamps, and all of them fall in the last range.

    A sharded system routes by hash(key) mod 4. A fifth shard is added and the rule becomes mod 5. How much data must move?

    Most keys give a different remainder under the new modulus. Logical shards or consistent hashing move only about a fifth.

    In a sharded database, what does a query that doesn't include the shard key cost?

    Scatter and gather multiplies the load by the number of shards and inherits the slowest one's latency.
