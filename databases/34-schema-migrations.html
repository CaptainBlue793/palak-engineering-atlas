Schema Migrations at Scale

On a laptop, renaming a column takes one statement and a moment. On a production table of two hundred million rows, with requests arriving every millisecond and two versions of the application running during a deploy, the same statement can stop the site, in two separate ways. The statement may need a lock that every query has to wait behind, or it may rewrite the table for an hour. And when it finishes, half the application servers are still running code that expects the old schema. Changing a schema under traffic is a discipline with a few firm rules: know what each statement locks, build indexes without blocking writes, never make a change that old code can't tolerate, and move data in small pieces. This chapter covers them.

  • Say which schema changes are instant, which scan the table and which rewrite it
  • Build an index, and add a constraint, without blocking writes
  • Plan a change as expand, migrate, contract, so that old and new code both work at every step
  • Backfill a large table in batches without disturbing production
  • Explain how online schema-change tools copy a table while it is in use

Locks taken by ALTER TABLE

Nearly every form of ALTER TABLE takes the strongest table lock, which blocks reads and writes alike (Chapter 22). What matters is how long it holds it. Some changes only edit the catalogue and are finished in a millisecond. Others have to read every row to check something, or write every row out again in a new form, and hold the lock throughout.

-- A foreign key in two steps
ALTER TABLE orders ADD CONSTRAINT orders_customer_fk
  FOREIGN KEY (customer_id) REFERENCES customers NOT VALID;      -- instant: enforced for new rows from now on
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;      -- checks the old rows under a weak lock: reads and writes continue

The two-step form works because the two halves need different things. Declaring the rule needs the strong lock for an instant. Checking the existing rows takes a long time and needs only a lock that lets normal traffic through.

CREATE INDEX CONCURRENTLY

A plain CREATE INDEX blocks every insert, update and delete on the table until it finishes, which on a large table is minutes or hours. CONCURRENTLY builds the same index while writes carry on.

CREATE INDEX CONCURRENTLY orders_customer_created_idx ON orders (customer_id, created_at);

-- If it fails or is cancelled, it leaves a husk behind:
\d orders
    "orders_customer_created_idx" btree (customer_id, created_at) INVALID
DROP INDEX CONCURRENTLY orders_customer_created_idx;           -- remove it and start again

-- A unique constraint without blocking: build the index first, then attach it
CREATE UNIQUE INDEX CONCURRENTLY users_email_key ON users (email);
ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE USING INDEX users_email_key;

It waits for older transactions, so a session left idle in a transaction can hold a concurrent build up indefinitely. The same advice as in Chapter 22 applies: look for long-running sessions before starting.

Expand and contract

The locks are half the problem. The other half is that the database and the application don't change at the same instant. A deploy replaces application servers a few at a time, so for some minutes old code and new code are both serving requests, and either might be rolled back. A change is safe only if every version of the code that might be running works against the schema as it stands, at every moment.

That rules out any change that alters or removes something old code uses. The method that respects it has three phases. Expand: add the new thing beside the old, so that the schema supports both. Migrate: move the code and the data across in steps, each of which can be undone. Contract: when nothing uses the old thing, remove it.

Expand and contract takes six steps where the rename and its deploy were two. At each of them every server works, and every step but the last can be reversed. The old column is the safety net until the last step, which is why that step, the only one that destroys anything, comes after the new code has been running for a while.

        Backfills

        The third step in the panel copies the old column into the new one for every existing row. Written as one statement, UPDATE users SET full_name = name, that is a single transaction that locks every row until it finishes, writes a new version of every row (Chapter 23), generates a great deal of WAL, and pushes replicas far behind (Chapter 25). A backfill is done in batches.

        def backfill(conn, batch=5000):
    last_id = 0
    while True:
        with conn.transaction():                                  # one short transaction for each batch
            rows = conn.execute("""
                UPDATE users SET full_name = name
                WHERE user_id IN (
                    SELECT user_id FROM users
                    WHERE user_id > %s AND full_name IS NULL       -- only rows not yet done: safe to run again
                    ORDER BY user_id LIMIT %s )
                RETURNING user_id""", (last_id, batch)).fetchall()
        if not rows:
            return
        last_id = max(r[0] for r in rows)                         # walk the primary key: no rescanning from the start
        wait_until_replicas_are_within(seconds=2)                  # and let autovacuum and the replicas keep up
        time.sleep(0.1)

        Works in batches of a few thousand rowsEach transaction holds its row locks for milliseconds
        Walks the primary keyEach batch is an index range scan, where OFFSET would rescan from the beginning every time
        Can be stopped and restartedIt will be interrupted. It should skip rows already done
        Throttles itselfIt watches replica lag and load, and pauses when they rise
        Runs after new writes already fill the columnOtherwise rows written during the backfill are missed, and it never finishes

        Online schema-change tools

        Some changes can't be decomposed: altering a column's type in MySQL, for instance, or changing a table's primary key. For these there are tools that perform expand and contract on a whole table.

        For MySQL the well-known tools are pt-online-schema-change, which captures changes with triggers, and gh-ost, which reads the replication log. For PostgreSQL, pg_repack rebuilds a table in this way to remove bloat, and tools such as pgroll automate the expand-and-contract sequence itself. All of them need free disk space for a second copy of the table.

        👻
        gh-ost: GitHub's migrations without triggers

        GitHub runs on MySQL and changes its schema several times a day. For years it used the standard tool for the job, which works as the figure above describes and captures ongoing changes with triggers: for every write to the original table, a trigger performs the matching write to the copy, inside the same transaction. On GitHub's busiest tables that had become a problem in itself. The triggers doubled the work of every write for the hours a migration ran, and added contention for locks between the application's writes and the copying process. They couldn't be paused: once in place they fired on every write, whatever the load, so a migration that was hurting production could only be abandoned. And the tool's behaviour couldn't be tested anywhere but on the primary. In 2016 GitHub's database team released a replacement called gh-ost. It uses no triggers. It connects to the database as if it were a replica and reads the replication log, where every committed change is already recorded, and applies those changes to the copy itself. Because it applies them asynchronously and under its own control, the migration's writes are separate from the application's and can be slowed or stopped completely at any moment, which it does automatically whenever replication lag or load passes a threshold. The same design lets a migration run entirely against a replica first, as a test, with a checksum at the end to prove the copy matches. The cut-over is a brief lock and an atomic rename. The schema changes themselves were no different from before. What gh-ost changed was the operator's control over a migration while it was running.

        ⚠️
        Common mistakes
        • Renaming or dropping a column that running code still uses. The lock is instant and the outage lasts until the deploy finishes.
        • A migration with no lock_timeout. If it has to wait for its lock, all traffic waits behind it.
        • CREATE INDEX without CONCURRENTLY on a table that takes writes.
        • Leaving an INVALID index after a failed concurrent build. It costs every write and helps no read.
        • A backfill as one UPDATE. Hours of row locks, a doubled table, and replicas minutes behind.
        • Schema change and code change in one deploy, with no order in which both old and new code work.

        Interview drill

        Explain it simply: How do you add an index to a large table in production without downtime?

        How a strong answer sounds
        In PostgreSQL, with CREATE INDEX CONCURRENTLY. A plain CREATE INDEX takes a lock that blocks all writes to the table for the duration of the build, which on a large table is minutes to hours. The concurrent form takes only a weak lock that allows reads and writes; it builds the index in two passes over the table, waiting between phases for transactions that started earlier, so that the index ends up containing every row. The trade-offs: it takes two to three times as long, uses more I/O, can't run inside a transaction block, so migration tooling has to run it on its own, and if it fails or is cancelled it leaves an INVALID index that must be dropped, concurrently, before retrying. Beforehand I'd check for long-running or idle-in-transaction sessions, since it has to wait for them, and I'd watch replication lag and I/O during the build. For a unique constraint, I'd build a unique index concurrently and then attach it with ADD CONSTRAINT … USING INDEX. In MySQL the equivalent is online DDL where the operation supports it, or a tool like gh-ost.

        Deeper: You need to change a column from integer to bigint on a 500 GB table that takes writes constantly. How?

        How a strong answer sounds
        A direct ALTER COLUMN TYPE rewrites the whole table and its indexes under an exclusive lock, hours of downtime, so I'd do it as expand and contract. First, add a new nullable bigint column; that is a catalogue-only change, run with a short lock_timeout and retried if it can't get the lock. Second, make new writes populate it: either deploy application code that writes both columns, or add a trigger that copies the old column to the new on insert and update, which avoids depending on every code path. Third, backfill existing rows in batches of a few thousand by primary-key range, each in its own transaction, idempotent and resumable, throttled on replica lag, with autovacuum keeping up. Fourth, build any needed indexes on the new column concurrently, and add constraints as NOT VALID then validate; if it must be NOT NULL, add a validated check constraint first so that SET NOT NULL can skip its scan. Fifth, verify that the two columns agree everywhere. Sixth, switch reads to the new column, then stop writing the old one, in separate deploys so each can be rolled back. Finally drop the old column and the trigger. If the column is the primary key, the same approach applies with an extra step to swap the constraint using a pre-built unique index, in one short transaction; and foreign keys referencing it need the same treatment on their side. The whole thing takes days of elapsed time and no downtime.

        🧠 Key takeaways

        • ALTER TABLE takes the strongest lock. Whether that matters depends on whether the change is catalogue-only, scans the table, or rewrites it.
        • Set lock_timeout on every migration, and split constraints into NOT VALID and VALIDATE.
        • Build indexes with CONCURRENTLY, and drop any that are left INVALID.
        • Old and new code run together during a deploy, so the schema must suit both at every moment.
        • Expand, migrate, contract: add the new beside the old, move code and data in reversible steps, and remove the old last.
        • Backfill in small, restartable, throttled batches along the primary key.
