ORMs & the N+1 Problem

Most application code never contains a line of SQL. It works with objects, a Post with an author and a list of comments, and an object-relational mapper turns each use of them into queries. That is a real convenience, and it puts a layer between the programmer and everything this course has covered. A loop that looks like plain Python may be sending the database five hundred statements. A line that adds one to a counter may be overwriting somebody else's update. The ORM isn't doing anything wrong in these cases: it runs exactly what it was asked to, and the programmer didn't know what that was. This chapter is about seeing what the ORM runs, the most common way it goes wrong, and how to get the queries you would have written yourself.

  • Find out what SQL an ORM sends, and when it sends it
  • Recognise the N+1 pattern in code and in a query log
  • Choose between joined and select-in eager loading, and say when each goes wrong
  • Explain how an ORM session maps to database transactions, and avoid lost updates
  • Decide when to write the SQL by hand, and do it safely

What the ORM runs

An ORM maps a class to a table, an object to a row, and an attribute that refers to another object to a foreign key. Three of its mechanisms matter for performance.

The first habit to form is to look. Every ORM can print the statements it sends: echo=True in SQLAlchemy, the debug toolbar or connection.queries in Django. Read that output for any page or endpoint you write, and the count of statements as well as their text.

N+1 explained

A page lists the fifty newest posts with each author's name.

posts = session.scalars(select(Post).order_by(Post.created_at.desc()).limit(50)).all()
for post in posts:
    print(post.title, post.author.name)             # reads the author: one query, every time round

It is the commonest performance fault in applications built on an ORM, and it survives for understandable reasons. The code contains no SQL and reads as correct. On a developer's machine, with five posts and the database on the same computer, it takes three milliseconds. Each statement is a primary-key lookup with a perfect plan, so no slow-query log ever records one. It shows up only in Chapter 37's view, as a trivial query with tens of millions of calls, or in a request trace, as a comb of identical short queries. And it gets worse as the data grows and as templates are extended: each new attribute read inside the loop adds another N.

Time is an estimate: 0.8 ms for each statement, most of it the round trip to a database in the same data centre, plus a few microseconds for each row returned, more for wide joined rows. With the database 20 ms away in another region, multiply the statement count by twenty.

Things to notice. With 50 posts and all three relations, lazy loading sends 151 statements and takes about 124 ms, nearly all of it waiting on round trips. Select-in sends 4 and takes 7 ms, and stays at 4 statements for 200 posts, where lazy loading has grown to 601. Joined loading sends one statement, and with two collections it returns 1,600 rows to deliver 700 objects (50 posts, 50 authors, 400 comments and 200 tags), since each post comes back once for every pairing of a comment with a tag. At 200 posts that is 6,400 wide rows, and the single query takes nearly five times as long as select-in's four. The last option is the usual answer: join the author, which adds no rows, and give each collection one query of its own.

Eager loading and batching

Eager loading means telling the ORM, on the query, which related data the code is about to use, so that it can fetch it in bulk.

from sqlalchemy.orm import joinedload, selectinload, raiseload

stmt = (select(Post)
        .options(joinedload(Post.author),          # one row for each post: join it
                 selectinload(Post.comments),      # many rows for each post: a second query with IN (…)
                 raiseload("*"))                    # anything else read lazily raises an error
        .order_by(Post.created_at.desc()).limit(50))
posts = session.scalars(stmt).all()

Transactions in ORMs

An ORM also decides where transactions begin and end, and the defaults differ. A SQLAlchemy session begins a transaction at its first statement and holds it until commit() or rollback(). Django, by default, commits each statement by itself unless the code is wrapped in transaction.atomic(). Each default has a typical failure.

FailureHow it happensFix
A transaction held openA session reads something, then the code calls a payment provider for two seconds, then commits. The connection sits idle in a transaction throughout, holding its snapshot and its locks (Chapter 23, Chapter 27)Keep transactions short. Do slow outside calls before or after, never inside

Raw SQL escape hatches

An ORM is good at loading and saving objects, which is most of what an application does. It is a poor fit for some of the rest: a report with window functions and several CTEs (Chapter 6), an upsert, a queue read with FOR UPDATE SKIP LOCKED, a bulk change to a million rows. For those, write the SQL. Every ORM provides a way, and using it is ordinary practice.

from sqlalchemy import text

rows = session.execute(text("""
    SELECT author_id, title, views,
           rank() OVER (PARTITION BY author_id ORDER BY views DESC) AS r
    FROM   posts
    WHERE  created_at >= :since
"""), {"since": since}).all()                       # :since is a bound parameter, sent separately from the SQL

# Never this. The value becomes part of the statement: SQL injection.
session.execute(text(f"SELECT * FROM posts WHERE title = '{title}'"))

Two rules apply. Values always go in as bound parameters, never pasted into the string. And raw SQL bypasses what the ORM knows: objects already in the session aren't updated by a raw UPDATE, so keep the two apart or refresh afterwards. Between the ORM and raw strings there is usually a middle layer, such as SQLAlchemy's Core expressions, which builds any SQL the database supports from Python and keeps the parameter handling.

GitLab: a ceiling on queries for each request

GitLab is a large Rails application on PostgreSQL, written by hundreds of contributors, and its pages show lists of things that have other things attached: merge requests with authors, labels, approvers and pipelines. That shape produces N+1 queries constantly, and no amount of care by individual developers keeps them out. GitLab's answer, set out in its public development documentation, was to make the query count something the tooling enforces. Every controller action and API endpoint has a budget of 100 SQL statements. In the test suite a request that exceeds it raises an error, so the merge request that introduced the problem fails in continuous integration. Code that is already over the limit has to be marked with an explicit exemption that links to an issue for fixing it, which keeps the debt visible and counted. Alongside the ceiling there is a test helper that records the statements a block of code sends. The standard N+1 test uses it twice: it runs the code with one record and counts the queries, creates several more records, runs it again, and asserts that the count hasn't gone up. If loading five merge requests takes more statements than loading one, something is being loaded lazily for each of them. Reviewers working on database changes are asked to look at the query log for the pages a change touches, and the per-request query counts are recorded in production so that the worst endpoints can be ranked. None of this is sophisticated. It works because it changes when the problem is found: at the moment the code is written, by a failing test that names the endpoint, where otherwise it would be found months later, by a user, on a project large enough to make the page time out.

⚠️
Common mistakes
  • Never looking at the SQL. The statement count for a page should be a number you know.
  • Reading relations in a loop or a template with no eager loading. That is the N+1.
  • Joining several collections at once. The rows multiply, and one query becomes slower than four.
  • Read, modify in Python, write back. A lost update under concurrency. Use an expression or a row lock.
  • Slow outside calls inside a transaction, leaving a connection idle in a transaction for seconds.
  • Building raw SQL with string formatting. Use bound parameters, every time.

Interview drill

Explain it simply: What is the N+1 query problem, and how do you fix it?

How a strong answer sounds
It is when code loads a list of N objects with one query and then, for each object, triggers another query to load something related: 1 + N statements where one or two would do. It usually comes from an ORM's lazy loading: iterating over posts and reading post.author sends a SELECT for each post. Each query is fast, so nothing looks slow in isolation, but 500 round trips at a millisecond each is half a second, and it grows with the data. The fix is eager loading: tell the ORM up front what you'll need. For a single related row, a join, select_related in Django or joinedload in SQLAlchemy. For collections, a second query with WHERE parent_id IN (…), prefetch_related or selectinload, which avoids multiplying rows. To detect it, I'd log or count queries for each request, use tools such as the Django debug toolbar or Bullet, and write tests asserting that the query count doesn't grow with the number of records. Some ORMs can raise on lazy loads, which catches it in development. And sometimes the right fix is not to load objects at all: if I need a comment count, a GROUP BY does it in one query.

Deeper: When would you use a joined eager load, and when a separate IN query? What goes wrong with each?

How a strong answer sounds
A join is best for to-one relations: each parent row gains some columns and the row count doesn't change, so it is one round trip with no duplication. For to-many relations a join repeats the parent's columns once for each child, so wide parents with many children send a lot of redundant data that the ORM then has to de-duplicate. It gets much worse with two collections joined in the same query: the result is the product, comments times tags for each post, so 8 comments and 4 tags make 32 rows a post. A join also interferes with LIMIT, since the limit would apply to joined rows, not parents; ORMs work around it with a subquery, which can change the plan. A separate IN query returns each child row exactly once and leaves pagination alone, at the cost of one extra round trip for each relation, and that cost is constant, not proportional to N. Its failure modes are a very long IN list when the parent set is large, which is a sign the page is loading too much anyway, and each query getting its own snapshot under read committed, so the children can be slightly newer than the parents unless the whole thing runs in one repeatable-read transaction. My default is join for to-one, IN for to-many, and never more than one collection in a join.

🧠 Key takeaways

  • An ORM turns attribute access into SQL. Print what it sends, and know the statement count for each page.
  • N+1 is one query for a list and one more for each item. Every query is fast, and the total is not.
  • Join for a single related row. Use a separate IN query for each collection. Never join two collections together.
  • Make lazy loading an error, and test that the query count doesn't grow with the data.
  • Know where the ORM's transactions begin and end. Let the database do increments, and lock before read-then-write.
  • Write SQL by hand when the ORM is the wrong tool, always with bound parameters.

Check your understanding

A page loads 100 orders lazily and shows each order's customer and its list of items. How many statements, if every customer is different?

One for the orders, 100 for the customers and 100 for the items.

Why does N+1 seldom appear in a slow-query log?

A slow-query log has a threshold for each statement. The N+1 shows in call counts and in request traces.

A query eagerly loads 50 posts with a join to comments (10 each) and a join to tags (5 each). How many rows come back?

Two collections joined together multiply: 50 × 10 × 5. Separate IN queries would return 50 + 500 + 250.

Two requests run post.views += 1 and commit at about the same moment, starting from 42. What can the final value be?

The arithmetic happened in Python. views = views + 1 in SQL would give 44.

What does making lazy loading raise an error achieve?

The N+1 becomes a test failure, found when the code is written.
