Case Study: An Analytics Warehouse

The shop from Chapter 41 has grown. Its transactional database is healthy, and nobody is allowed to run reports on it any more, after a quarterly revenue query held a snapshot open for forty minutes and the tables bloated behind it. The questions haven't stopped: revenue by day and by category, how many visitors reach the checkout and how many of those pay, what one customer did before they rang support. They need a second system built for a different job: a few very large queries over everything that has ever happened, where the first system does many small ones over what is true now. This last case study designs that system end to end, from an event leaving a browser to a number on a dashboard. It draws on the column stores of Chapter 28, the partitioning of Chapter 26 and the materialised views of Chapter 33, and it takes a view the earlier chapters rarely needed: in a warehouse the main measure of a design is how much data each query has to read, since that sets both its speed and its price.

  • Design an ingestion pipeline for events that tolerates duplicates and late arrivals
  • Lay out fact and dimension tables for a real product, and handle dimensions that change
  • Choose a partition column and a clustering key from the queries, and predict how much each query reads
  • Build rollup tables that are cheap to maintain and safe to rebuild
  • Say which measures can be rolled up by adding, and what to do about those that can't

Event ingestion

Two kinds of data flow into the warehouse. Events are things that happened and were never rows in the shop's database: a page was viewed, a product was added to a cart, a search returned nothing. There are about 20 million a day. Entities are the rows the database does hold, orders, products and customers, and the warehouse needs copies of them and of their changes.

Four rules make the pipeline dependable, and each answers a failure that will certainly happen.

RuleThe failure it answers
Raw events are append-only and never editedA bug in a transformation. With the raw data intact, fix the SQL and rebuild everything downstream
Every event carries a unique IDDuplicates. A sender that gets no reply sends again, and a loader that crashes mid-batch reloads the batch. Delivery is at least once, so the same event will arrive twice, and the ID is how the copies are found
Record two times: when it happened and when it arrivedLate events. A phone that was offline delivers Monday's events on Wednesday. They belong to Monday, and Monday's totals have already been published
Read database changes from the log, not with queriesLoad on the transactional database, and missed changes: a nightly SELECT sees only each row's final state, and nothing of a row that was created and deleted the same day
 
-- Rebuild the last three days of the fact table with one copy of each event: the earliest to arrive.
-- The numbering pattern is Chapter 6's. Older days are left alone.
DELETE FROM analytics.fact_events
WHERE  DATE(event_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 3 DAY);

INSERT INTO analytics.fact_events
SELECT * EXCEPT (rn, received_at)
FROM  (SELECT *, ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY received_at) AS rn
       FROM   analytics.events_raw
       WHERE  DATE(event_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 3 DAY))
WHERE  rn = 1;

The SQL in this chapter is in BigQuery's dialect, since partitioning and clustering have to be written in some concrete syntax. Snowflake, Redshift and ClickHouse have the same features under their own names.

Facts and dimensions

Chapter 28 introduced the star schema: large fact tables of things that happened, surrounded by small dimension tables that describe them. Applying it starts with one decision for each fact table, its grain: what exactly one row stands for.

The order lines are easy, thanks to a decision made in Chapter 41: they already carry the price and name as they were at purchase, so the fact is a straight copy. Dimensions raise the same question that order lines did. A product is moved from "Shoes" to "Outdoor" in June. Should last March's sales now appear under "Outdoor"?

One more step is common in a column store. The attributes that nearly every query filters or groups by, the product's category and the customer's country, are copied onto the fact rows as they were at the time. That is deliberate denormalisation. A column holding a few dozen distinct values compresses to almost nothing (Chapter 28), and the commonest queries then need no join at all.

Partitioning and clustering

A column store already reads only the columns a query names. The next saving is to read only some of the rows, and a warehouse has two mechanisms for it. Partitioning divides the table into separate pieces by the value of one column, nearly always the date, and a query that filters on that column never opens the other pieces (Chapter 26). Clustering sorts the rows within each partition by another column, and keeps the minimum and maximum of that column for every block of rows. A query filtering on it skips each block whose range can't contain the value, which is the block-range idea of Chapter 15.

CREATE TABLE analytics.fact_events (
  event_id    STRING,
  event_time  TIMESTAMP,
  event_type  STRING,            -- page_view, add_to_cart, purchase, …
  customer_id INT64,
  session_id  STRING,
  product_id  INT64,
  category    STRING,            -- copied from dim_product as it was at the time
  country     STRING,
  device      STRING,
  amount      NUMERIC,
  url         STRING,
  props       JSON
)
PARTITION BY DATE(event_time)
CLUSTER BY customer_id
OPTIONS (require_partition_filter = TRUE);        -- a query with no date filter is refused

Most warehouses separate storage from computation and charge for queries by the amount of data they read. That makes the design question concrete: for each query the business runs, how many bytes does it touch, and how many times a day does it run?

Priced at £5 for each terabyte read, with a minimum of 10 MB a query, which is close to what on-demand warehouses charge. Time is a fifth of a second of overhead plus half a second for each gigabyte. Bytes are for the columns each query names, after compression. The model doesn't charge for keeping an unpartitioned table of this size sorted, which in practice is costly.

Things to notice. With no design at all, four queries cost about £41,600 a month, and the daily revenue chart alone takes over half a minute to draw. Partitioning by day cuts the bill by more than nine-tenths, since three of the four queries ask about recent days. The fourth, one customer's history over a year, hardly benefits: a year is half the table. Clustering then offers a choice. By event type, the two revenue queries become nearly free and the customer lookup stays at about £2,000 a month. By customer, the lookup drops to a few pounds and the revenue queries stay where they were. The rollups settle it. They answer the three dashboard queries from tables of a few megabytes whatever the clustering, so the clustering key is free to serve the one query the rollups can't: partition by day, cluster by customer, and the month costs about £11. The same four questions are being answered. What changed is how much data the warehouse reads to answer them.

Materialised rollups

A rollup is a table of answers worked out in advance: the facts grouped to a coarser grain, here one row for each day, category, country and device. Chapter 33 covered the idea and its central question, which is how the copy is kept in step with its source. In a warehouse the usual answer is to rebuild whole days.

-- Every night: rebuild the last three days. Late events are picked up, and a rerun can't double-count.
DELETE FROM analytics.daily_sales
WHERE  day >= DATE_SUB(CURRENT_DATE(), INTERVAL 3 DAY);

INSERT INTO analytics.daily_sales (day, category, country, device, orders, revenue, buyers_sketch)
SELECT DATE(event_time), category, country, device,
       COUNT(*), SUM(amount),
       HLL_COUNT.INIT(customer_id)                     -- a sketch of the distinct buyers, not a number
FROM   analytics.fact_events
WHERE  event_type = 'purchase'
  AND  DATE(event_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 3 DAY)
GROUP BY 1, 2, 3, 4;

-- The dashboard's query: revenue and distinct buyers by month
SELECT DATE_TRUNC(day, MONTH) AS month, SUM(revenue) AS revenue,
       HLL_COUNT.MERGE(buyers_sketch) AS buyers
FROM   analytics.daily_sales
GROUP BY 1;

Three properties of that job are worth copying. It is idempotent: delete the days, then insert them, so running it twice gives the same table as running it once, and a failed run is simply run again. It reaches back three days, so events that arrive late are counted when they turn up. And it reads only three partitions of the fact table, so it costs the same next year as today.

The sketch column is there for a reason that catches most first attempts at rollups. Some measures can be added up across rows and some can't.

MeasureCan daily rows be combined into a month?Store in the rollup
Count, sumYes: add themThe count, the sum
Minimum, maximumYes: take the minimum or maximum againThe value
AverageNot from the averages: a day with 10 orders would weigh as much as one with 10,000The sum and the count, and divide at query time
Distinct countNo: a customer who buys on two days would be counted twiceA HyperLogLog sketch, which can be merged (Chapter 4)
Median, percentilesNoA quantile sketch, or go back to the facts
Ratios, such as conversion rateNot from the ratiosThe numerator and the denominator

A rollup also fixes the questions it can answer. daily_sales knows nothing about hours, sessions or individual customers. When a question needs those, the query goes back to the fact table, which is why the facts are kept and why their partitioning and clustering still matter once the dashboards have stopped reading them.

LinkedIn: the ingestion pipeline that became Kafka

The durable log in the middle of this chapter's pipeline has a particular origin, and it is this problem. Around 2010 LinkedIn was collecting activity events, page views, searches, clicks on recommendations, and trying to deliver them to everything that wanted them: the Hadoop cluster where reports were built, the data warehouse, the search index, the monitoring system, and the features that suggest people you may know. Each of those had been connected to each source by its own pipeline. Some scraped log files from web servers in nightly batches, and some used message queues that weren't built to hold much or to be replayed. With many sources and many destinations the number of pipelines grew as the product of the two, and each was fragile in its own way. When one destination fell behind or broke, either events were dropped or the source was slowed. The data arriving in the warehouse was a day old and never quite complete, and the team responsible spent most of its time repairing pipelines. Jay Kreps, Neha Narkhede and Jun Rao built the replacement and released it as open source in 2011. Its central idea was to put one system in the middle and make it as simple as possible: an append-only log for each kind of event, stored on disk and replicated, which a producer only ever appends to and which each consumer reads at its own pace, remembering its own position. A consumer that is down for six hours loses nothing. It carries on from where it stopped. A new consumer can start from the beginning of what is retained. Producers and consumers know nothing of each other. That one change turned a tangle of pipelines into a hub, and LinkedIn has since reported carrying trillions of messages a day through it. The internals belong to the Distributed Systems course. For a warehouse the point is the property it gives the pipeline: the loader can be slow, crash or be redeployed, and no event is lost. It may deliver some events twice, which is why every event in this chapter carries an ID.

⚠️
Common mistakes
  • Running analytics on the transactional database. Long scans hold snapshots open and compete with the queries that earn the money.
  • Transforming before storing. Without the raw events, a bug in the transformation can never be put right.
  • No event ID. Duplicates are certain, and without an ID they can't be found.
  • A large table with no partitioning, or queries with no filter on the partition column.
  • Summing a distinct count or averaging an average across the rows of a rollup.
  • A rollup job that appends. Run twice, it doubles the day. Make it replace.

Interview drill

Explain it simply: What is the difference between partitioning and clustering in a data warehouse?

How a strong answer sounds
Both reduce how much of a table a query has to read, at different granularities. Partitioning splits the table into separate physical segments by the value of one column, almost always a date. A query that filters on that column reads only the matching partitions; the rest aren't opened at all. It is coarse and exact, and it also makes maintenance cheap: dropping a month of data is dropping a partition. Clustering, also called a sort key, orders the rows within each partition by one or more columns, and the engine keeps the minimum and maximum of those columns for each block of rows. A query filtering on a clustering column skips any block whose range can't contain the value. It is finer-grained and suits high-cardinality columns such as a customer ID, where partitioning would create millions of tiny partitions. So I'd partition by the time column that nearly every query filters on, and cluster by the column used for selective lookups within a time range. Since most warehouses charge by bytes read, both show up directly in cost as well as speed.

Deeper: A dashboard shows daily and monthly active users from a table of 20 million events a day, and it is slow and costly. How do you fix it?

How a strong answer sounds
I'd start by looking at what the dashboard's queries read. If each load scans the raw events for the whole date range, the cost is bytes times the number of loads, so there are two levers. First, the table: partition by event date and require a partition filter, so that a 30-day chart reads 30 partitions and not the whole history. Second, stop computing it on every load: build a rollup, one row for each day, rebuilt nightly for the last few days so that late events are included, with a job that replaces days and never appends, so that it is safe to rerun. The difficulty is that active users is a distinct count, and distinct counts aren't additive: I can't sum 30 daily counts to get the monthly figure, since most users are active on many days. There are three options. Store an exact monthly figure as its own rollup row, computed from the facts, which is exact but fixed to the periods I precompute. Store a HyperLogLog sketch for each day and merge sketches at query time, which gives any date range and any grouping I kept as a dimension, with an error of about one per cent. Or keep an intermediate table of distinct user and day pairs, which is exact and much smaller than events, and count over that. For a dashboard I'd use sketches, and say that the figures are approximate. Then I'd check the result: bytes read for each dashboard load should fall from gigabytes to megabytes, and I'd reconcile the rollup against the raw table for a sample of days.

🧠 Key takeaways

  • Keep analytics off the transactional database. Feed a warehouse from an event log and from the database's change log.
  • Raw events are append-only, carry a unique ID, and record both when they happened and when they arrived.
  • Fix the grain of each fact table first. Version the dimensions whose history reports depend on.
  • Partition by the date nearly every query filters on, and cluster by the column used for selective lookups.
  • In a warehouse, bytes read are both the response time and the bill. Design each table from the queries that run most.
  • Rollups should replace whole days, reach back for late data, and store sums, counts and sketches, never averages or distinct counts.

Check your understanding

Why does every event carry a unique ID?

Senders retry and loaders rerun batches. De-duplication by ID makes that harmless.

A table is partitioned by day and clustered by customer_id. Which query benefits least?

It filters on neither column, so every partition and every block is read. It is a job for a rollup.

A daily rollup stores the number of distinct buyers for each day. Why can't the monthly figure be found by adding the days?

Distinct counts aren't additive. Store a sketch that can be merged, or count from the facts.

Why does the nightly rollup job delete and rebuild the last three days, where it could simply append yesterday?

Replacing makes the job idempotent, and reaching back picks up stragglers.

A product moves to a different category. Finance wants last year's report to show the same figures as when it was first run. What does the product dimension need?

Overwriting restates history. Keeping versions leaves old facts attached to the old category.
