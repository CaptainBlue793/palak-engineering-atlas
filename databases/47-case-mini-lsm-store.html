Case Study: Building a Mini LSM Key-Value Store

Chapter 14 described the log-structured merge tree from the outside: a memtable, a write-ahead log, sorted files and compaction, and the trade it makes between cheap writes and dearer reads. This chapter builds one. The whole store is 125 lines of Python with no dependencies, and it is a real one in the sense that matters: it keeps its promises across a crash, including a crash halfway through writing a record, and it has been checked against a plain dictionary through tens of thousands of random operations and restarts. RocksDB, LevelDB and the storage engines inside Cassandra and CockroachDB are far larger, and nearly all of the extra is performance. The skeleton is the same five parts, and writing them out removes most of the mystery from the big ones.

  • Implement put, get and delete on a memtable backed by a write-ahead log
  • Flush the memtable to an immutable sorted file, atomically
  • Read across several files, newest first, with a sparse index and tombstones
  • Compact files with a streaming merge, and say when a tombstone may be dropped
  • Say what survives a crash at each step, and why

The API

The store maps string keys to values. It has three operations and one promise: once put or delete returns, the change survives a crash.

db = MiniLSM("data", memtable_limit=3)          # a directory. Flush after every 3 keys, to keep the example small
db.put("user:1", "Asha")
db.put("user:2", "Ben")
db.put("user:3", "Chloe")                    # the third key: the memtable is flushed to 000001.sst
db.put("user:2", "Benedict")                 # an overwrite
db.delete("user:3")

db.get("user:1")     # 'Asha'       from the file
db.get("user:2")     # 'Benedict'   from the memtable, which hides the older 'Ben' in the file
db.get("user:3")     # None         deleted, though 'Chloe' is still in the file

After those calls the directory holds two files, and their contents are the whole state of the store.

# data/000001.sst: sorted by key, never modified again
["user:1", "Asha"]
["user:2", "Ben"]
["user:3", "Chloe"]

# data/wal.log: what has happened since that flush, in order of arrival
["user:2", "Benedict"]
["user:3", null]

Nothing on disk was changed to perform the overwrite or the delete. Both were appended to the log, and null is the tombstone. The old values will stay in 000001.sst until compaction.

Memtable and WAL

A write has to be both fast and durable. Writing it into its sorted place in a file would be slow, and keeping it only in memory would lose it on a crash. So it goes to two places: appended to a log file, which is the cheapest write a disk can do, and put into an in-memory table that is quick to search.

class MiniLSM:
    def __init__(self, directory, memtable_limit=1000, max_tables=4):
        self.dir, self.memtable_limit, self.max_tables = directory, memtable_limit, max_tables
        os.makedirs(directory, exist_ok=True)
        names = sorted(n for n in os.listdir(directory) if n.endswith(".sst"))
        self.tables = [SSTable(os.path.join(directory, n)) for n in names]      # oldest first
        self.next_id = int(names[-1][:-4]) + 1 if names else 1
        self.memtable = {}
        self.wal_path = os.path.join(directory, "wal.log")
        self._recover()
        self.wal = open(self.wal_path, "a")

    def put(self, key, value):
        self.wal.write(json.dumps([key, value]) + "\n")
        self.wal.flush()
        os.fsync(self.wal.fileno())                       # on disk before we say yes
        self.memtable[key] = value
        if len(self.memtable) >= self.memtable_limit:
            self.flush()

    def delete(self, key):
        self.put(key, None)                               # a tombstone

The order inside put is the write-ahead rule of Chapter 20: log first, force the log to disk, and only then change the memtable and return. The fsync is what makes the promise true, and it is also the slowest line in the store. A production engine gathers the writes of many concurrent callers into one fsync, which this one doesn't attempt.

Starting up is the other half. The memtable is gone after a crash, and the log still holds every write that hadn't been flushed, so replaying it rebuilds the memtable exactly.

    def _recover(self):
        """Rebuild the memtable from the log, after a restart."""
        if not os.path.exists(self.wal_path):
            return
        good = 0                                          # the byte where the last whole record ends
        with open(self.wal_path, "rb") as f:
            for line in f:
                if not line.endswith(b"\n"):
                    break                                 # a torn last line: the crash came mid-write
                key, value = json.loads(line)
                self.memtable[key] = value
                good += len(line)
        os.truncate(self.wal_path, good)                  # cut the torn tail off, so new records start cleanly

The torn line deserves its three lines of code. If power fails while a record is being written, the log ends in half a record. That write was never acknowledged, so ignoring it is correct. Leaving it in the file is a bug, and it was in the first version of this code: the next record would be appended directly after the half one, the two would run together into one unreadable line, and the following recovery would stop there and lose an acknowledged write. Real engines guard each log record with a length and a checksum for the same reason.

Flushing SSTables

The memtable can't grow without limit, and the log with it. When it reaches its limit it is written out, in key order, as a sorted string table: a file that will never be modified.

class SSTable:
    """An immutable file of records sorted by key, one JSON line each."""
    EVERY = 16                                            # the sparse index holds one key in sixteen

    def __init__(self, path):
        self.path, self.keys, self.offsets, self.max_key = path, [], [], None
        with open(path, "rb") as f:
            n = 0
            while True:
                pos, line = f.tell(), f.readline()
                if not line:
                    break
                key = json.loads(line)[0]
                if n % self.EVERY == 0:
                    self.keys.append(key)
                    self.offsets.append(pos)
                self.max_key, n = key, n + 1

    @staticmethod
    def write(path, items):
        """Write (key, value) pairs, already in key order, and return the table."""
        tmp = path + ".tmp"
        with open(tmp, "w") as f:
            for key, value in items:
                f.write(json.dumps([key, value]) + "\n")
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp, path)                             # atomic: the table appears whole, or not at all
        return SSTable(path)
    # in MiniLSM
    def flush(self):
        if not self.memtable:
            return
        self.tables.append(SSTable.write(self._new_path(), sorted(self.memtable.items())))
        self.memtable = {}
        self.wal.close()
        self.wal = open(self.wal_path, "w")               # the flushed records no longer need the log
        if len(self.tables) > self.max_tables:
            self.compact()

Two things here carry the crash-safety. The table is written under a temporary name and renamed into place only after it is complete and synced, and a rename is atomic, so a crash can never leave half a table under a real name. And the log is emptied only after the table exists. A crash between those two steps leaves the same records in both the new table and the log. On restart the log is replayed into the memtable, the same values are found twice, and nothing is wrong: applying a write a second time gives the same result as applying it once.

The constructor reads the file once and remembers every sixteenth key with its byte offset. That is the sparse index: small enough to keep in memory for a very large file, and enough to bring any lookup to within sixteen records of its target.

Reads across levels

A key may now be in the memtable and in any number of tables, with a different value in each. The rule that makes this correct is to look in order of age, newest first, and stop at the first place that knows the key.

    # in MiniLSM
    def get(self, key):
        if key in self.memtable:
            return self.memtable[key]                     # None here means deleted
        for table in reversed(self.tables):               # newest first
            found, value = table.get(key)
            if found:
                return value
        return None

    # in SSTable
    def get(self, key):
        """Return (found, value). A found value of None is a tombstone."""
        if not self.keys or key < self.keys[0] or key > self.max_key:
            return False, None                            # outside this table's range: no disk read
        i = bisect.bisect_right(self.keys, key) - 1       # the last indexed key at or before ours
        with open(self.path, "rb") as f:
            f.seek(self.offsets[i])
            for _ in range(self.EVERY):
                line = f.readline()
                if not line:
                    break
                k, value = json.loads(line)
                if k == key:
                    return True, value
                if k > key:
                    break
        return False, None

The distinction between "found, and the value is None" and "not found" is the whole reason tombstones exist. A table that holds a tombstone for the key ends the search: the key is deleted, and the older tables, which may well hold a value for it, must not be consulted. Without the tombstone a deleted key would come back to life from an older file.

The cost of a read is now visible in the code. A key in the memtable costs a dictionary lookup. A key in the newest table costs one seek and a few lines. A key that doesn't exist costs a look at every table whose key range covers it, and that is the worst case. It is why real engines put a Bloom filter in front of every table (Chapter 14), and why they can't let the number of tables grow.

Each put writes a new value, v1, v2 and so on, so that versions can be told apart. A record shown as ✗ is a tombstone. After a get, the record that answered it is outlined. The memtable has a dashed border as a reminder that it is in memory only.

Things to notice. Put the same key several times: the log grows by a line each time and the memtable doesn't grow, since it keeps only the newest value. The fourth distinct key triggers a flush: a table appears and the log empties. Delete a key that is in a table, then get it: the search stops at the tombstone in the memtable and never opens the table. Now crash. The memtable is rebuilt from the log exactly as it was, and no get returns a different answer from before. Keep writing until there are four tables: they are merged into one, each key keeps only its newest value, and the tombstones vanish along with the values they were hiding. Count the records on disk before and after that merge to see how much of the data was already dead.

Compaction

Every flush adds a table, and every table is one more place a read may have to look and one more copy of keys that have since been overwritten. Compaction merges tables into one, keeping the newest value for each key. Since every input is already sorted, it is the merge step of merge sort, and it never needs more than one record from each table in memory at a time.

    def compact(self):
        """Merge every table into one, keeping the newest value of each key."""
        def tagged(table, age):                           # age 0 is the newest table
            for key, value in table:
                yield key, age, value

        streams = [tagged(t, age) for age, t in enumerate(reversed(self.tables))]

        def newest_live():
            previous = object()
            for key, _, value in heapq.merge(*streams):   # by key, and for equal keys newest first
                if key != previous:
                    previous = key
                    if value is not None:                 # every older copy is in this merge: drop the tombstone
                        yield key, value

        merged = SSTable.write(self._new_path(), newest_live())
        old, self.tables = self.tables, [merged]
        for table in old:
            os.remove(table.path)

heapq.merge takes any number of sorted streams and yields their records in order, holding one from each in a heap. Tagging each record with its table's age makes equal keys come out newest first, so the first record seen for a key is the one to keep and the rest are skipped. The tombstone rule is in one line and is easy to get wrong: a tombstone may be dropped only when every table that could hold an older value for that key is part of the same merge. Here that is always true, since the merge takes all the tables. An engine that merges a few tables at a time has to carry tombstones forward until they reach the oldest level.

Four small pieces complete the file: the imports, the iterator that compaction reads a table with, the helper that names the next table, and close.

import bisect
import heapq
import json
import os

    # in SSTable
    def __iter__(self):
        with open(self.path) as f:
            for line in f:
                yield tuple(json.loads(line))

    # in MiniLSM
    def _new_path(self):
        path = os.path.join(self.dir, f"{self.next_id:06d}.sst")
        self.next_id += 1
        return path

    def close(self):
        self.wal.close()

LevelDB: the same five parts, as a library

The engine that made this design ordinary was LevelDB, released by Google in 2011 and written by Jeff Dean and Sanjay Ghemawat, who had built the same structure years earlier as the storage layer of Bigtable. Its source is a few tens of thousands of lines of C++, and the correspondence with this chapter is close. Writes go to a log file and into a memtable, which is a skip list. When the memtable reaches its size limit, 4 MB by default, it becomes immutable and a background thread writes it out as a table file. A table is a series of blocks of about 4 kB, each compressed, followed by an index block giving the last key of each data block, which is this chapter's sparse index stored in the file where ours is rebuilt in memory. An optional Bloom filter of about ten bits for each key lets a read skip tables that can't contain it. Tables are arranged in levels. Level 0 holds freshly flushed tables, whose key ranges overlap, and four of them trigger a compaction into level 1. From level 1 down, the tables in a level have disjoint key ranges, and each level may hold ten times the data of the one above, so a read needs to look at one table in each of those levels at most. A manifest file records which tables make up each level, and is how the engine knows after a crash which files are live. Every record carries a sequence number, so that a reader can hold a snapshot while writes continue. Facebook forked LevelDB in 2012 as RocksDB, adding multi-threaded compaction and a great many tuning options for servers with fast flash storage, and RocksDB went on to become the storage engine underneath MyRocks, the first versions of CockroachDB, TiKV, Kafka's stream-processing state and a long list of others. LevelDB itself is in every copy of Chrome, where it stores IndexedDB data. The 125 lines above differ from it in almost every detail and in none of the ideas.

⚠️
Common mistakes
  • Updating the memtable before the log is synced. A crash then loses a write that was acknowledged.
  • Emptying the log before the table is safely on disk. A crash between the two loses the whole memtable.
  • Writing a table in place. Write to a temporary name and rename, or a crash leaves half a file that looks like a table.
  • Searching oldest first, or not stopping at the first hit. A stale value wins.
  • Treating a tombstone as "not found". The search carries on to an older table, and the deleted key returns.
  • Dropping tombstones in a partial compaction, while an older table still holds the value.

Interview drill

Explain it simply: Walk me through what happens on a write and on a read in an LSM-tree storage engine.

How a strong answer sounds
On a write, the engine appends the key and value to a write-ahead log and syncs it, which makes the write durable, and then inserts it into the memtable, a sorted in-memory structure. That is all: no existing file is modified, which is why writes are fast, one sequential append. When the memtable reaches a size limit it is written out in key order as an immutable file, an SSTable, and the log for it is discarded. Deletes are writes too: a tombstone marker. On a read, the engine looks in the memtable first, then in the SSTables from newest to oldest, and returns the first entry it finds for the key; if that entry is a tombstone, the key is deleted. Within an SSTable it uses a small index to find the right block, and a Bloom filter for each table lets it skip tables that definitely don't contain the key. Since tables accumulate, a background process, compaction, merges them: it combines sorted files into new ones, keeps only the newest version of each key, and drops tombstones once nothing older remains. So the trade is cheap writes in exchange for reads that may check several files and background work to keep that number small.

Deeper: Your LSM store crashes at an arbitrary moment. Convince me that no acknowledged write is lost and no half-written state is visible.

How a strong answer sounds
I'd go through each step and say what is on disk if the crash comes right after it. A put appends to the log and fsyncs before touching the memtable or returning. If the crash is before the fsync completes, the write was never acknowledged, and on restart the log either lacks it or ends in a partial record, which recovery detects, by a missing terminator here or by a checksum in a real engine, and truncates. If the crash is after the fsync, the record is in the log and replay restores it to the memtable. A flush writes the memtable to a temporary file, fsyncs it, and renames it to its final name; rename is atomic, so on restart the table either exists complete or doesn't exist, and a leftover temporary file is ignored. Only after the rename is the log truncated. A crash between the rename and the truncation leaves the same records in the table and the log; replay puts them in the memtable again with identical values, which is harmless since the operations are idempotent and the memtable is consulted first anyway. Compaction writes the merged table the same way, then removes the inputs. A crash before removal leaves inputs and output together; the output has the highest number so it is treated as newest, and any key resolves to the same value either way: live keys are found in the output, and deleted keys either have their tombstone still in an input or are absent everywhere. The invariant throughout is that every acknowledged write is in the log or in a complete table, and files only become visible when whole. Two caveats for a real system: the directory itself needs an fsync after a rename for the rename to be durable, and a manifest is the proper way to make the switch of table sets atomic.

🧠 Key takeaways

  • An LSM store is five parts: a log, a memtable, immutable sorted tables, a newest-first read path, and compaction.
  • Log, sync, then memtable. Recovery replays the log and cuts off a torn last record.
  • Tables are written whole under a temporary name and renamed. Files are never modified in place.
  • Reads go newest first and stop at the first hit. A tombstone is a hit.
  • Compaction is a streaming merge of sorted files. A tombstone can go only when every older copy is in the merge.
  • Each step is ordered so that a crash at any point leaves a correct state on disk.
