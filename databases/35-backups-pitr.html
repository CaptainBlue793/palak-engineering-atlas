Backups & Point-in-Time Recovery

Replication protects a database against a machine failing. It does nothing about a person making a mistake: a DELETE without its WHERE, a migration that drops the wrong table, a script pointed at production. Those changes are faithfully replicated to every standby within a second. The protection against them is a copy of the database as it was earlier, and a way to bring that copy forward to the moment just before the mistake. A backup is worth exactly as much as the last restore that was tested from it, and two numbers describe what it can do: how much recent work is lost, and how long the restore takes. This chapter covers the two kinds of backup, the archived log that joins them up, recovery to a chosen moment, and the testing that decides whether any of it works.

Two numbers: recovery point and recovery time

Every backup plan is judged by two figures, and it helps to have them before the mechanisms. The recovery point objective (RPO) is how much recent data may be lost: with a backup taken at 02:00 each night and nothing else, a failure at 14:37 loses twelve and a half hours of work. The recovery time objective (RTO) is how long the database may be unavailable while it is restored. They are set by different things. The recovery point depends on how recent the newest recoverable state is. The recovery time depends on how much data has to be copied back and how much log has to be replayed.

pg_dump and base backups

PostgreSQL offers two different things under the name of backup. A logical dump, made by pg_dump, is the contents of a database written out as SQL: the statements that would recreate its tables and reload its rows. A physical base backup, made by pg_basebackup, is a copy of the data files themselves, page for page.

# Logical: one database, as a compressed archive of SQL and data
pg_dump -Fc -f shop.dump shop
pg_restore -d shop -j 8 shop.dump                  # reload with 8 workers: reinserts every row, rebuilds every index
pg_restore -d shop -t orders shop.dump             # or one table only

# Physical: the whole cluster's files, plus the WAL written while copying
pg_basebackup -D /backup/base -Ft -z -X stream -P
pg_verifybackup /backup/base                       # check every file against the backup's manifest

A dump has one further cost that is easy to miss. It holds its snapshot open for as long as it runs, and a snapshot held for six hours stops VACUUM removing anything for six hours (Chapter 23). On a large, busy database that is a reason to dump from a replica.

WAL archiving

A base backup alone is no better than a dump for the recovery point: it restores the database as it was when the backup was taken. What changes that is keeping the log. Chapter 20 showed that every change is written to the WAL first, and that after a crash the database replays the log from the last checkpoint. If every WAL segment written since a base backup is kept, the same replay can carry that backup forward to any later moment.

PostgreSQL writes its log in segments of 16 MB and normally recycles them once a checkpoint has made them unnecessary. With archiving switched on, it hands each finished segment to a command first, and won't recycle the segment until that command reports success.

# postgresql.conf
archive_mode    = on
archive_command = 'pgbackrest --stanza=main archive-push %p'   # %p is the path of the finished segment
archive_timeout = 60                                          # finish a segment at least once a minute, even when quiet
-- Is archiving working? Look at this every day, and alert on it.
SELECT archived_count, last_archived_time, failed_count, last_failed_time FROM pg_stat_archiver;

 archived_count |     last_archived_time     | failed_count | last_failed_time
----------------+----------------------------+--------------+------------------
         184203 | 2026-10-07 14:36:58+00     |            0 |

Two failures are worth knowing in advance. If the archive command starts failing, the database keeps every segment it couldn't hand over, and the WAL directory grows until the disk is full and the database stops. And if a segment is lost from the archive, recovery can't pass that point: the log is a chain, and replay needs every link in order. A newer base backup is what limits the damage, since recovery needs only the WAL written after the backup it starts from.

In practice the command belongs to a backup tool such as pgBackRest, Barman or WAL-G, which compresses and encrypts the segments, sends them to object storage, takes the base backups on a schedule, and removes backups and WAL that are older than the retention period. Since version 17, PostgreSQL can also take incremental base backups, which copy only the pages changed since the previous one.

Point-in-time recovery

With a base backup and an unbroken run of WAL after it, the database can be rebuilt as it was at any moment from the end of that backup onwards. This is point-in-time recovery (PITR).

# postgresql.conf on the restored server, plus an empty file named recovery.signal in the data directory
restore_command        = 'pgbackrest --stanza=main archive-get %f "%p"'
recovery_target_time   = '2026-10-08 14:36:50+00'      # ten seconds before the DROP TABLE
recovery_target_action = 'pause'                       # stop and wait there, read-only
SELECT count(*) FROM orders;             -- is the table there, with the rows expected?
SELECT pg_wal_replay_resume();           -- yes: end recovery and open for writes

Three practical points. First, replay only goes forwards. If the target turns out to be a few seconds too late, the restore has to start again from the base backup, so it pays to aim early and pause. Second, when recovery ends, the server begins a new timeline: its WAL files carry a new number, so that the log written after the recovery can't be confused with, or overwrite, the original log that ran on past the target. The old history stays in the archive, and a second recovery to a different point is still possible. Third, a whole-database rewind is rarely what is wanted. When one table was damaged at 14:37 and everything else carried on, rewinding the lot would throw away every other table's work since then. The usual course is to recover to a separate server, and copy the lost table back into production from there with pg_dump -t.

    Things to notice. A replica alone handles the lost disk in about a minute and loses almost nothing, and against the dropped table it is no help at all, since the drop was replicated at once. The nightly dump brings the table back as it stood at 02:00, twelve hours and thirty-seven minutes out of date. Both plans with archived WAL recover everything committed before the mistake. They differ in recovery time: from Sunday's base backup there are four and a half days of log to replay, and the restore takes nearly ten hours, where from Thursday's it takes under two. The third incident shows the other reason for frequent base backups. One segment missing from Tuesday makes everything after it unreachable from Sunday's backup, and more than two days of data are lost. From a backup taken after the gap, the missing segment is never needed.

    Testing restores

    Backups fail quietly. The job reports success and writes a file of zero bytes. The archive command has been failing for a month, and its alerts go to a mailbox nobody reads. The backup is complete and the decryption key was on the server that died. None of this shows until a restore is attempted, and the only defence is to attempt restores routinely, by machine, and to treat a failed test as an incident.

    PracticeWhat it catches
    Restore the latest backup to a scratch server every day, automatically, and replay WAL to a recent timeEmpty or corrupt backups, a broken WAL chain, a tool that no longer matches the server's version
    Run checks on the restored copy: row counts, the newest timestamp in a busy table, pg_amcheckA restore that starts and has stale or damaged data in it
    Record how long it tookA recovery time that has drifted past what the business was promised, as the database grew
    Alert on pg_stat_archiver and on the age of the newest backupArchiving that stopped last Tuesday
    Keep copies in another region and another account, with deletion locked for the retention periodA lost region, a compromised account, ransomware, an engineer with a script
    Keep the keys and the runbook somewhere that survives the databaseA perfect backup that nobody can decrypt or remembers how to restore
    Have a person do a restore now and thenA procedure that only one engineer has ever run

    A useful addition for human error is a delayed replica: a standby told to apply its WAL an hour late (recovery_min_apply_delay = '1h'). For an hour after a mistake, the undamaged data is sitting on a running server, and getting it back takes minutes. It complements backups and doesn't replace them, since after the hour has passed it has the mistake too.

    🧯
    GitLab, January 2017: five kinds of backup and none that worked

    On the evening of 31 January 2017, GitLab.com's PostgreSQL primary was under heavy load from spam, and its one standby had fallen so far behind that it needed rebuilding from scratch. An engineer, late at night and after several failed attempts at the rebuild, went to clear the standby's data directory before trying again, and ran the delete in the wrong terminal, on the primary. He stopped it within a couple of seconds. Of about 300 GB of data, roughly 4.5 GB remained, and the standby had no usable copy. The team turned to the backups, and found the following, as their own account of the incident records. The nightly pg_dump to object storage had been producing files of a few bytes, because the job was running the dump program from an older PostgreSQL version than the server, and it failed with an error each night. The emails reporting those failures had been rejected by the mail system and never arrived. Disk snapshots from the cloud provider had never been switched on for the database servers. Replication, the fourth safeguard, was the thing being repaired. What saved most of the data was a filesystem snapshot that the same engineer had happened to take by hand about six hours earlier, for an unrelated test. Restoring it took around eighteen hours, with the site unavailable, and about six hours of issues, comments, merge requests and new accounts were gone for good. GitLab published the whole account and streamed the recovery live. The lessons it drew are the ones in the table above: nobody owned the backups, no restore had ever been tested, and nothing was watching whether the nightly job produced anything. A wrong command will be typed on some system sooner or later. What decided the outcome was that five mechanisms, none of them ever tested, turned out to give no protection.

    ⚠️
    Common mistakes
    • Counting a replica as a backup. It copies a mistake as faithfully as it copies everything else.
    • Never having restored. An untested backup's recovery point and recovery time are both unknown.
    • No alert on archiving. A failing archive command first breaks recovery and then fills the disk.
    • Backups in the same account, region or server as the database, where the same accident or attacker reaches both.
    • Only dumps, for a large database. No recovery between dumps, and a restore measured in hours.
    • Recovering over the damaged server. Restore beside it, and keep the evidence and the chance to try again.

    Interview drill

    Explain it simply: We have a replica in another availability zone. Why do we still need backups?

    How a strong answer sounds
    Because they protect against different things. A replica protects against losing a machine or a zone: it has the same data as the primary, a second or less behind, and can take over in under a minute. That same property makes it useless against logical damage. A dropped table, a bad UPDATE, an application bug that corrupts rows, or an attacker deleting data are all ordinary changes as far as replication is concerned, and they reach the replica almost immediately. A backup is a copy of the past: a base backup plus the archived WAL lets me rebuild the database as it was at any chosen moment, such as ten seconds before the mistake. Backups also cover cases a replica can't: corruption that replicates physically, losing the whole account, and needing last month's data for an audit. So I'd want both: replicas for availability, with a recovery time of seconds, and base backups with continuous WAL archiving for recoverability, stored in a different account and region, with restores tested automatically. A delayed replica is a useful extra between the two.

    Deeper: Design the backup and recovery plan for a 2 TB PostgreSQL database. The business wants to lose no more than five minutes of data and to be back within an hour.

    How a strong answer sounds
    I'd start by separating the failure cases, because one mechanism can't meet both targets for all of them. For hardware or zone failure: a synchronous or near-synchronous standby in another zone with automated failover, which gives a recovery point of zero to a second and a recovery time of about a minute. For logical damage and disasters: physical backups with continuous WAL archiving, using pgBackRest or similar. A full base backup weekly and incremental or differential backups daily, so recovery never replays more than a day of WAL; WAL archived continuously with archive_timeout at a minute or streamed, which gives a recovery point of about a minute, inside the five. Everything goes to object storage in a second region and a separate account, encrypted, with object lock for the retention period. The one-hour recovery time is the hard part for a full restore: 2 TB in an hour needs sustained throughput of over 500 MB/s plus WAL replay, so I'd measure it, use parallel restore, and be honest if it comes out at two or three hours. To meet an hour for human error specifically, I'd add a delayed replica an hour behind, from which a damaged table can be recovered in minutes, and note that most logical incidents need one table copied back from a side restore, not a full rewind. Then the part that makes it real: an automated daily restore to a scratch server with data checks and timing recorded, alerts on pg_stat_archiver and backup age, a written runbook, and a restore drill every quarter. I'd report the measured recovery point and time to the business, and if they don't meet the targets, that is a conversation about cost, not something to assume.

    🧠 Key takeaways

    • A replica covers a failed machine. A backup covers a mistake. A production database needs both.
    • Recovery point is how much data is lost. Recovery time is how long the restore takes. Different things set each.
    • A dump is portable, selective and slow to restore. A base backup is a fast copy of the files and the foundation for point-in-time recovery.
    • Archived WAL carries a base backup forward to any later moment. The chain must be unbroken, and it must be monitored.
    • Frequent base backups shorten the replay and limit how much depends on any one WAL segment.
    • A backup that has never been restored can't be relied on. Test restores automatically and time them.

    Check your understanding

    A table is dropped by mistake on the primary. Why doesn't the standby help?

    Replication copies what happened, mistakes included. Only a copy of the past can undo one.

    What does point-in-time recovery need?

    Recovery restores the files and then replays the log on top of them, in order, with no gaps.

    With WAL archiving in place, what does taking base backups nightly improve over taking them weekly?

    The recovery point is set by the WAL either way. A newer backup means a shorter replay and fewer segments to depend on.

    The archive command has been failing for two days. What happens on the primary?

    It won't recycle a segment that hasn't been archived. Meanwhile nothing after the failure can be recovered from the archive.

    Why does PostgreSQL start a new timeline when a point-in-time recovery finishes?

    Two different histories now follow the same point. The timeline number keeps them apart, and keeps the old one available.
