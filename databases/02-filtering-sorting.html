Filtering, Sorting & Pagination

Most queries an application sends are some version of "the rows matching this, in that order, a page at a time": an inbox, a product listing, an activity feed. Each part has a well-known trap. Filters written the wrong way silently stop using indexes; date ranges miss the last day; sorts with ties return pages in a different order every time; and OFFSET pagination gets slower with every page and shows users the same item twice. This chapter covers the predicates you'll use daily and the pagination technique that scales: keyset pagination.

  • Use comparison, IN, BETWEEN, LIKE and ILIKE correctly, including the inclusive-range trap
  • Write filters an index can use ("sargable" predicates) and recognise ones it can't
  • Make sorts deterministic with a unique tie-breaker
  • Explain why OFFSET pagination slows down and drifts, and implement keyset pagination with its index

Comparison, IN and BETWEEN

The basic predicates are the ones you'd expect: =, <> (or !=), <, <=, >, >=. Two shorthands save typing:

SELECT order_id, status, created_at
FROM   orders
WHERE  status IN ('paid', 'shipped')                         -- status = 'paid' OR status = 'shipped'
  AND  total_cents BETWEEN 5000 AND 10000;                  -- inclusive at BOTH ends

BETWEEN includes both ends, which is exactly wrong for timestamps. "Orders in September" written as created_at BETWEEN '2026-09-01' AND '2026-09-30' means up to midnight at the start of 30 September, so the whole last day is missing. Change the end to '2026-10-01' and you include orders placed at exactly midnight on 1 October. Use a half-open range instead, inclusive at the start and exclusive at the end. It's correct for any precision and composes: consecutive months never overlap or leave gaps.

WHERE created_at >= '2026-09-01'
  AND created_at <  '2026-10-01'                                 -- all of September, nothing else

Pattern matching: LIKE and ILIKE

LIKE matches a pattern where % means any sequence of characters and _ means exactly one. ILIKE is PostgreSQL's case-insensitive version. To match a literal % or _, escape it with a backslash ('50\%').

SELECT sku, name FROM products WHERE sku LIKE 'KB-%';            -- starts with KB-: an index can help
SELECT sku, name FROM products WHERE name ILIKE '%wireless%';   -- contains: a B-tree can't help

A B-tree index is sorted, so it can find everything that starts with KB- by jumping to that point and reading forward. (In PostgreSQL that needs the index to be built with text_pattern_ops or the column to use the C collation.) It can't help with "contains", because matching rows are scattered all over the sort order. Substring search needs a trigram index (pg_trgm, Chapter 15) or real full-text search (Chapter 31).

Filters an index can use

A predicate is sargable (from "search argument able") when the database can turn it into a range lookup on an index: the bare column on one side, a value on the other. Wrapping the column in a function or cast hides it from an ordinary index, so the database has to compute the expression for every row:

Not sargable (scans every row)Sargable rewrite (can use an index on the column)
WHERE created_at::date = '2026-09-30'WHERE created_at >= '2026-09-30' AND created_at < '2026-10-01'
WHERE extract(year FROM created_at) = 2026WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE total_cents / 100 > 50WHERE total_cents > 5000
WHERE lower(email) = 'ana@example.com'Keep it, but index the expression: CREATE INDEX ON users (lower(email))
WHERE coalesce(deleted_at, 'infinity') > now()WHERE deleted_at IS NULL OR deleted_at > now()

Indexes themselves are Chapter 9; the habit to build now is writing filters on bare columns.

Sorting with ties

If two rows have the same value for every ORDER BY column, their relative order is undefined, and it can differ between executions, for example when the plan changes or a parallel scan finishes in a different order. For a one-off report it doesn't matter. For pagination it does: a row can appear on two pages or on none. Always end the sort with a unique column:

ORDER BY created_at DESC, post_id DESC       -- post_id breaks ties between posts in the same microsecond

PostgreSQL also accepts the SQL-standard spelling FETCH FIRST 20 ROWS ONLY for LIMIT 20, and FETCH FIRST 3 ROWS WITH TIES returns any extra rows that tie with the last one, handy for "top 3, including joint third place".

Pagination: OFFSET vs keyset

The obvious way to page is LIMIT 20 OFFSET 40 for page 3. It has two problems. Cost: the database can't jump to row 40,000; it produces the first 40,000 rows in order and throws them away, so page n costs n times as much as page 1. Drift: if new rows arrive at the top between two page loads, everything shifts down and the next page repeats items the user has already seen; deletions make items get skipped.

Keyset pagination (also called cursor or seek pagination) fixes both. Instead of "skip n rows", the client says "rows after the last one I saw", and that's a range condition an index can jump to directly:

-- page 1
SELECT   post_id, author_id, created_at, body
FROM     posts
ORDER BY created_at DESC, post_id DESC
LIMIT    20;

-- next page: pass the (created_at, post_id) of the last row the client received
SELECT   post_id, author_id, created_at, body
FROM     posts
WHERE    (created_at, post_id) < (%(last_created_at)s, %(last_post_id)s)   -- a row-value comparison
ORDER BY created_at DESC, post_id DESC
LIMIT    20;

CREATE INDEX posts_created_id_idx ON posts (created_at, post_id);     -- scanned backwards for DESC

The row-value comparison (a, b) < (x, y) means "a < x, or a = x and b < y": exactly "comes after in this sort order". PostgreSQL can use the two-column index for it directly, so every page reads about 20 index entries no matter how deep the user scrolls.

Slack's move to cursor-based pagination

Slack's public API originally paged lists such as channel members and messages with offset-style parameters. As workspaces grew to tens of thousands of channels and members, deep pages became slow to serve and lists shifted between requests. Slack's engineering team wrote about moving its API to cursor-based pagination: each response carries an opaque next_cursor, and the client sends it back for the next page. Stripe's API (starting_after) and most modern public APIs follow the same pattern, for the same two reasons the panel shows: constant cost per page and stable results while data changes.

⚠️
Common mistakes
  • BETWEEN on timestamps. Misses most of the last day. Use >= start AND < next_start.
  • Functions on indexed columns (created_at::date = …, lower(email) = … without an expression index).
  • Pagination ordered by a non-unique column. Rows with equal values can repeat or vanish across pages; add the primary key as a tie-breaker.
  • Deep OFFSET on large tables, especially in exports and batch jobs that walk a whole table page by page: quadratic total work.
  • LIKE '%term%' on a big table expecting an index to help. It can't without a trigram index.

Interview drill

Explain it simply: Why does LIMIT 20 OFFSET 100000 get slow, and what would you use instead?

How a strong answer sounds
The database can't jump to the 100,000th row of a sorted result; it has to produce the first 100,020 rows in order and discard 100,000 of them, so cost grows linearly with the page number. I'd use keyset pagination: order by a unique key such as (created_at, id), have the client send the last key it saw, and query WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20 with an index on those columns. Every page is an index jump plus 20 rows, and it's also stable when new rows are inserted while the user scrolls.

Deeper: A nightly job exports a 200-million-row table to a warehouse in pages of 10,000 using OFFSET and has started taking 14 hours. Why, and how do you fix it?

How a strong answer sounds
Each page re-reads every row before it, so the total work is roughly the sum 10,000 + 20,000 + … + 200 million, which grows with the square of the table size: doubling the table quadruples the job. Switch to keyset iteration on the primary key (WHERE id > $last ORDER BY id LIMIT 10000), which makes the total linear. Better still, stream the whole thing with a single COPY (SELECT …) TO STDOUT or a server-side cursor, and for an incremental export, filter by an indexed updated_at watermark.

🧠 Key takeaways

  • BETWEEN is inclusive at both ends; use half-open ranges (>=, <) for time.
  • Keep filters sargable: bare column on one side, or index the exact expression you filter on.
  • LIKE 'prefix%' can use a suitable B-tree; '%contains%' needs a trigram or full-text index.
  • End every paginated sort with a unique tie-breaker.
  • OFFSET pages cost more the deeper they go and drift when data changes; keyset pagination is constant-cost and stable.

Check your understanding

Which condition selects exactly the orders placed in September 2026 (created_at is a timestamptz)?

A half-open range includes all of 30 September and excludes midnight on 1 October. BETWEEN … '2026-09-30' stops at the start of the 30th.

There is an index on orders(created_at). Which filter can't use it?

The cast wraps the column, so the planner would have to compute it for every row. Rewrite it as a range on the bare column.

A feed uses ORDER BY created_at DESC LIMIT 20 OFFSET 20. Five new posts arrive between the user loading page 1 and page 2. What do they see on page 2?

Everything shifted down by five, so offset 20 now starts five rows earlier in what the user had already seen. Keyset pagination doesn't drift.

Why add post_id after created_at in a paginated ORDER BY?

Without a unique tie-breaker the order among equal values is undefined and can change between queries.

What does keyset pagination give up compared with OFFSET?

Keyset pagination can only continue from a known position (next or previous). For infinite scroll and APIs that's fine; for "go to page 37" it isn't.
