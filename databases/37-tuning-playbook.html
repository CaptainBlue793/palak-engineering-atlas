Performance Tuning Playbook

"The database is slow" is where most tuning starts, and it says nothing about where to look. The usual first moves are to raise some memory settings found in a blog post, or to chase the one query somebody remembers taking thirty seconds. Both are guesses. A database under load is spending its time somewhere specific, and PostgreSQL will report exactly where, statement by statement. The method is the same every time: measure where the time goes, fix the largest item, measure again. In nearly every case the largest items are a handful of queries, and the fix is an index or a change to the application. Configuration comes after that, and matters less. This chapter sets out the method, the fixes in order of return, and the few settings that are worth changing from their defaults.

  • Use pg_stat_statements to find where a database spends its time
  • Rank queries by total time, and say why mean time and call count each mislead
  • Match a costly query to the kind of fix it needs: an index, a rewrite, or fewer calls
  • Set the memory parameters that matter, and explain the danger in work_mem
  • Tune autovacuum for large and busy tables

pg_stat_statements

pg_stat_statements is an extension shipped with PostgreSQL that keeps running totals for every kind of statement the server executes. It strips the constants out of each statement, so that WHERE user_id = 17 and WHERE user_id = 94 are counted as one entry, WHERE user_id = $1, and for each entry it records how often it ran and what it cost.

# postgresql.conf, then restart once
shared_preload_libraries = 'pg_stat_statements'
track_io_timing = on                            # also record time spent reading and writing blocks
CREATE EXTENSION pg_stat_statements;

SELECT left(query, 60)                                      AS query,
       calls,
       round(mean_exec_time::numeric, 2)                     AS mean_ms,
       round((total_exec_time / 1000)::numeric)               AS total_s,
       round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 1) AS pct
FROM   pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT  10;

SELECT pg_stat_statements_reset();               -- start a fresh measurement, for instance after a deploy

Top queries by total time

The view can be sorted three ways, and they give three different lists. Sorting by mean time finds the slowest statements, which tend to be reports and exports that run a few times a day. Sorting by calls finds the most frequent, which tend to be primary-key lookups that are already as fast as they can be. Sorting by total time, the mean multiplied by the calls, finds the statements the server spends the most time executing. That is the load. A query that takes 2 ms and runs forty million times a day occupies the database for twenty-two hours of every twenty-four. A query that takes three minutes and runs twice occupies it for six minutes.

Index fixes

Take each query at the top of the list and run it under EXPLAIN (ANALYZE, BUFFERS) with realistic parameters (Chapter 17). Most findings fall into a short list.

Indexes have a cost as well, paid on every write. The same statistics show which ones aren't earning it.

-- Indexes that have never been used since statistics were last reset
SELECT relname AS tbl, indexrelname AS idx, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM   pg_stat_user_indexes
WHERE  idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

Before dropping one, check that it doesn't enforce a unique constraint and that the statistics cover a full business cycle, month-end included, and look at the replicas too, since an index may be used only by queries that run there.

Memory settings

PostgreSQL's defaults are chosen so that it starts on a very small machine, and a few of them are worth changing on any real server. The list is short. Most of the three hundred other settings are best left alone until a measurement points at one.

SettingDefaultA starting point, 64 GB serverWhat it does
shared_buffers128 MB16 GB, a quarter of memoryThe buffer pool (Chapter 12). The operating system's cache holds the rest
effective_cache_size4 GB48 GBAllocates nothing. Tells the planner how much data is likely to be cached, which makes index scans look cheaper
work_mem4 MB16 to 64 MBMemory for each sort or hash, in each query
maintenance_work_mem64 MB1 to 2 GBMemory for VACUUM and index builds
random_page_cost4.01.1 on SSDThe planner's price for a random read. The default assumes a spinning disk and makes it avoid indexes
max_wal_size1 GB8 to 32 GBSpaces checkpoints out under heavy writing (Chapter 20)
max_connections100100 to 300, behind a poolerKept low on purpose (Chapter 27)

work_mem is the one that causes outages. It isn't a limit for a query or a connection. It is a limit for each sort and each hash operation, and a plan with four of them, run in parallel by three workers, may take a dozen times the setting. With work_mem at 256 MB and two hundred connections, a burst of complex queries can ask for more memory than the machine has, and the kernel's out-of-memory killer picks the database (the OS course has that incident as a case study). Keep the global value modest, and raise it for the session that runs a known large report: SET work_mem = '512MB'. The measurement that says it is too small is temp_blks_written in the statistics, or Sort Method: external merge in a plan.

Autovacuum tuning

Chapter 23 covered what VACUUM does and what holds it back. Autovacuum is the background process that runs it, and its defaults suit small tables. It vacuums a table when the dead rows exceed 20% of the table plus fifty rows. For a table of ten thousand rows that is prompt. For a table of five hundred million, a hundred million rows must die first, by which time the table and its indexes are badly bloated and the vacuum itself takes hours.

-- Vacuum the big, busy tables at 1% dead rows, not 20%
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_analyze_scale_factor = 0.005);

-- Which tables are behind?
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum
FROM   pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;
SymptomAdjustment
Large tables are vacuumed rarely, and bloat between runsLower autovacuum_vacuum_scale_factor for those tables, to 0.01 or 0.02
Autovacuum runs constantly and never catches upIt is throttled. Raise autovacuum_vacuum_cost_limit so that it does more work between pauses
Many large tables wait their turnRaise autovacuum_max_workers from 3, and the cost limit with it, since the workers share one budget
Dead rows grow although autovacuum runsNo setting helps. Something is holding the horizon back: a long transaction, an abandoned replication slot (Chapter 23)
Plans go wrong some hours after a bulk loadStatistics are stale. Run ANALYZE after the load, and lower the analyse scale factor

The instinct to turn autovacuum down when it seems to be using I/O is the wrong way round. The work doesn't go away. It accumulates as bloat, makes every query read more pages, and arrives later as a larger vacuum. A database with a vacuum problem needs autovacuum to run more often and faster.

OpenAI: one PostgreSQL primary behind ChatGPT

OpenAI's engineers have described, in a conference talk in 2025 and an article early in 2026, how the database behind ChatGPT is run, and the surprise is the architecture: one PostgreSQL primary taking all the writes, with around fifty read replicas across regions serving reads, for a service with hundreds of millions of users. They didn't get there with exotic configuration. Their account is a list of the measures in this chapter, applied strictly. Reads go to replicas wherever a slightly stale answer is acceptable, so that the primary's capacity is kept for writes. Costly queries are hunted down one at a time: one incident they describe was traced to a single statement generated by an ORM that joined a dozen tables, and the fix was to break it up and move part of the work into the application. Connections go through a pooler, since a storm of new connections had taken the service down before. Timeouts are set on statements and on sessions left idle in a transaction, so that a forgotten transaction can't hold back VACUUM. Schema changes are restricted to those that don't rewrite a table and must get their lock within a few seconds or give up, as in Chapter 34. Rate limits at several layers stop a retry storm or a newly launched feature from flooding the database. And new write-heavy workloads aren't added to this database at all: those that can be sharded go to a separate, sharded store, which keeps the primary's write load from growing with every feature. Their own conclusion is that a single well-tuned PostgreSQL primary goes much further than is generally assumed for a workload dominated by reads, provided the write load is kept under control and every query on the primary is known and watched.

⚠️
Common mistakes
  • Tuning configuration before queries. A missing index costs a factor of a thousand, and a setting rarely more than a few tens of per cent.
  • Ranking by mean time. The slowest query is seldom the one loading the server.
  • A large global work_mem. It multiplies by operations, workers and connections.
  • Adding indexes and never removing any. Each one slows every write to its table.
  • Turning autovacuum down to save I/O, and paying for it in bloat.
  • Changing several things at once, so that nobody can say which one helped.

Interview drill

Explain it simply: The database server is at 90% CPU. How do you find out why?

How a strong answer sounds
I'd look at what the database is executing, in two views. For right now, pg_stat_activity: which queries are active, how long they've been running, and what they're waiting on, which tells me whether it is CPU work or lock waits. For the pattern over time, pg_stat_statements ordered by total execution time, which is calls multiplied by mean time; the top few entries are normally most of the load. I'd order by total, not by mean, since a 2 ms query run forty million times a day costs far more than a 30-second report run twice. Then for each of the top queries I'd run EXPLAIN (ANALYZE, BUFFERS) with realistic parameters and look for a sequential scan with most rows filtered out, a sort that an index could supply, or a row estimate far from the actual count. Typical fixes are an index built concurrently, a rewrite, or refreshed statistics. If the query is already efficient and is simply called too often, the fix is in the application: an N+1 loop, missing caching, or batching. After each change I'd reset or compare the statistics to confirm the load fell. I'd also check whether something changed recently: a deploy, a dropped index, or stale statistics after a bulk load.

Deeper: Why is setting work_mem to a large value dangerous, and how would you size it?

How a strong answer sounds
Because it isn't a per-connection or per-query limit. It is the amount each sort or hash node may use before spilling to disk, and a single query can have several such nodes; with parallel query, each worker gets its own allowance for each node, and hash operations may use a multiple of it. So worst-case memory is roughly work_mem times nodes per query times parallel workers times concurrent queries. At 256 MB with 200 connections, a burst of reporting queries can demand tens of gigabytes beyond shared_buffers, and on Linux the OOM killer will terminate a backend, which makes PostgreSQL restart and drop every connection. To size it, I'd start from the memory left after shared_buffers and the OS cache I want to keep, divide by the realistic number of concurrently active queries, which with a pooler is small and known, and by two or three nodes each; that usually lands between 16 and 64 MB. Then I'd measure: temp_blks_written in pg_stat_statements and log_temp_files show which queries spill. If it is a few known heavy reports, I'd raise work_mem for those sessions or roles only, with SET or ALTER ROLE, and leave the global value conservative. And I'd keep max_connections low behind a pooler, since that is the multiplier that matters most.

🧠 Key takeaways

  • Tuning is a loop: measure, fix the largest item, measure again.
  • pg_stat_statements ordered by total time shows where the database's time goes. Mean time and call count each point at the wrong queries.
  • Most of the load is a few queries, and most fixes are an index or a change to how often the application asks.
  • Change a handful of settings from their defaults: shared_buffers, effective_cache_size, random_page_cost, max_wal_size, and a careful work_mem.
  • work_mem applies to each sort and hash in each query, so a large global value risks running out of memory.
  • On big tables, make autovacuum run sooner and faster. Turning it down stores up bloat.

Check your understanding

Query A takes 1.5 ms and runs 30 million times a day. Query B takes 40 seconds and runs 10 times a day. Which loads the server more?

Load is calls multiplied by mean time. A is over a hundred times B.

Why does pg_stat_statements replace constants with $1, $2?

Otherwise every user ID would be its own entry, and no totals would be visible.

A query does an index scan on customer_id, sorts 40,000 rows by created_at, and returns 20. What is the fix?

More memory makes the sort quicker. The right index removes it.

work_mem is set to 200 MB on a server with 300 connections. What is the risk?

The limit is for each operation. Many concurrent complex queries multiply it.

A 400-million-row table is bloated, and autovacuum reaches it about once a week. What should change?

The default threshold scales with table size. Large tables need a smaller fraction.
