Join Algorithms

SQL has one way to write a join and the database has three ways to run it. A nested loop looks up the matching rows for each row in turn. A hash join builds a lookup table from one side and passes the other side through it. A merge join sorts both sides and walks them together. All three give the same result, and for any pair of inputs one of them is right and another may be a thousand times slower. The planner chooses from its estimate of how many rows each side will produce, which is why a wrong estimate so often shows up as a bad join. This chapter covers how each algorithm works, what each costs, and how the planner decides the order in which to join several tables.

Nested loop (and index nested loop)

The simplest join is two loops. For each row of one input, the outer, look through the other, the inner, for rows that match.

def nested_loop(outer, inner, match):
    for o in outer:
        for i in inner:                 # the whole inner input, once for every outer row
            if match(o, i):
                yield o + i

def index_nested_loop(outer, inner_index):
    for o in outer:
        for i in inner_index.lookup(o.key):   # three or four pages, once for every outer row
            yield o + i

Written the first way, the cost is the product of the two sizes, which is hopeless for anything but tiny inputs. The second way is the one that matters. If the inner table has an index on the join column, each outer row costs one index lookup, and the join costs (outer rows) × (one lookup). For ten outer rows that is forty page reads, and nothing can beat it. For a million outer rows it is four million random page reads.

The nested loop has two properties the others lack. It works for any join condition at all, <, BETWEEN, a function call, where the other two need equality. And it produces its first row immediately, so it suits queries with a LIMIT.

Hash join

A hash join reads each input once. It takes the smaller input and builds a hash table in memory, keyed on the join column. Then it reads the larger input, and for each row looks its key up in the hash table.

def hash_join(small, large):
    table = {}
    for s in small:                              # build: blocking, and all of it in memory
        table.setdefault(s.key, []).append(s)
    for l in large:                              # probe: streams
        for s in table.get(l.key, ()):
            yield s + l

It needs no index and no ordering, which makes it the usual choice for joining large numbers of rows. It has three limits. It works only for equality conditions. It produces nothing until the build is finished. And the hash table has to fit in memory: if it doesn't, the join still works, by spilling batches to temporary files, and it runs several times slower. A plan line saying Batches: 16 is that case.

Merge join

If both inputs are sorted on the join column, they can be joined by walking down them together, as you would merge two sorted lists: advance whichever side has the smaller key, and emit when the keys are equal.

def merge_join(left, right):                  # both already sorted by key; keys unique on the left, for brevity
    l, r = next(left, None), next(right, None)
    while l is not None and r is not None:
        if l.key < r.key:
            l = next(left, None)
        elif l.key > r.key:
            r = next(right, None)
        else:
            yield l + r
            r = next(right, None)             # the right side may have several rows for this key

The walk itself is as cheap as a join can be: one pass over each input and no memory to speak of. The cost is in getting the inputs sorted. If they come already in order, from an index on the join column or from an earlier merge join, the merge join is the best choice for large inputs, and its output is sorted as well, which may save an ORDER BY further up. If both have to be sorted first, a hash join usually wins.

    The bars are on a logarithmic scale, so each step along is ten times the cost. The model: a nested loop without an index scans all 10,000 inner pages for each outer row. With an index, each outer row costs four random page reads. A hash join reads both inputs once, three times over if the hash table doesn't fit. A merge join reads both once and sorts whichever isn't sorted.

    Things to notice. With 1,000 outer rows and an index, the index nested loop costs 16,010 and the hash join 25,025: the planner picks the loop. At 100,000 outer rows the loop costs 1.6 million and the hash join 49,500, thirty-two times less. That is the trap of Chapter 17 in numbers: a planner that expects 1,000 rows and meets 100,000 has chosen a plan thirty-two times too slow. Remove the index and the plain nested loop is never right, not even for ten rows. At a million rows with 4 MB of memory the hash table spills and the join costs 90,000, against 50,000 when work_mem is large enough to hold it. And when both inputs arrive sorted, the merge join becomes the cheapest for large inputs, since it has nothing to build.

    Join order

    A join works on two inputs. A query over five tables is four joins, and they can be done in many orders, since joins can be rearranged freely as long as the result is the same. The order matters because every join's cost depends on the size of what flows into it.

    SELECT … FROM customers c
JOIN orders o       ON o.customer_id = c.customer_id
JOIN order_items i  ON i.order_id = o.order_id
WHERE c.country = 'IS';                       -- 40 customers in Iceland, of 2 million

-- Good:  customers (40 rows) → their orders (300) → their items (900): two index nested loops, about 5,000 units
-- Bad:   orders ⋈ order_items first (30 million rows), and only then the 40 customers

    Both orders give the same 900 rows. The first starts from the most selective condition and keeps the intermediate results small. The second builds the join of everything and throws nearly all of it away. The order in which you write the tables makes no difference: the planner considers the alternatives itself.

    Queries with many joins therefore get worse plans in two ways: the search is no longer exhaustive, and the row estimate for the result of the sixth join is built on five earlier estimates, each with its own error (Chapter 19).

    🐬
    MySQL had one join algorithm for twenty-five years

    From its first release in 1995 until 2019, MySQL joined tables by nested loop and nothing else. For the workloads it was built for, this was a sound decision and not an oversight. A web application's queries fetch a user and their twenty orders, each join follows an indexed foreign key, and an index nested loop is the best algorithm there is. MySQL's optimiser, with only one algorithm to consider, was simple and predictable. The cost fell on any query that didn't fit the pattern. A join on a column with no index became a scan of the inner table for every outer row, softened only by a variant that read the outer rows in blocks. Reporting queries that joined millions of rows to millions of rows, which a hash join does in seconds, ran for hours, and the standard advice was that analytical queries should be run somewhere else. Teams exported their data to another system to produce a monthly report. MySQL 8.0.18 added a hash join in October 2019, and from the next version it replaced the block nested loop altogether. The MySQL developers' own benchmarks showed joins without usable indexes going from minutes to seconds. A missing join algorithm doesn't make a database give wrong answers. It sets a limit on which queries are practical, and an engineer who knows the three algorithms can tell which side of that limit a query is on from its plan.

    ⚠️
    Common mistakes
    • No index on a foreign-key column. PostgreSQL doesn't create one for you. Joins from the parent, and deletes of the parent, then scan the child table.
    • Forcing a join type globally with SET enable_nestloop = off to fix one query. Every other query in the session is now planned without it. Fix the estimate.
    • Join conditions the hash and merge joins can't use: OR, inequalities, a function on one side. The planner is left with a nested loop.
    • Joining on columns of different types, such as integer to text. The cast can stop an index from being used.
    • A tiny work_mem on a server that runs large joins. Every hash join spills into batches.
    • Fifteen tables in one query, and surprise at the plan. Past the search limits, the planner is guessing at the order.
    🎤
    Interview drill

    Explain it simply: What are the three join algorithms, and when is each used?

    How a strong answer sounds
    Nested loop, hash join and merge join. A nested loop takes each row from the outer input and finds its matches in the inner input; with an index on the inner join column that is one index lookup per outer row, so it is the best choice when the outer side is small, a few rows up to a few thousand, and it is the only one that handles arbitrary join conditions. Without an index it is the product of the two sizes and only viable for tiny tables. A hash join builds an in-memory hash table on the smaller input keyed by the join column, then scans the larger input and probes; each input is read once, so cost is linear in the total size, and it needs no index or ordering, which makes it the default for joining large sets on equality. Its weaknesses are that it needs memory for the build side, spilling to disk in batches otherwise, and it returns nothing until the build completes. A merge join walks two inputs that are sorted on the join key in step; it is very cheap if the inputs are already sorted, for instance from indexes, and it preserves order, but if it has to sort both sides first, a hash join usually wins. The planner picks based on estimated row counts, available indexes and memory.

    Deeper: A query's plan shows a nested loop whose inner index scan has loops=250000. What has happened, and what do you do?

    How a strong answer sounds
    The planner chose a nested loop expecting few rows from the outer side, and got 250,000, so the inner index lookup, cheap individually, ran a quarter of a million times: a million or so random page accesses where a hash join would have read each table once. I'd confirm by comparing the outer node's estimated rows with its actual rows; I expect something like rows=5 against 250,000. So the fix is to correct the estimate, not to force the join. I'd look at why the outer estimate is wrong: stale statistics after a bulk load, so run ANALYZE; a predicate on two correlated columns whose selectivities were multiplied as if independent, so create extended statistics; a predicate wrapped in a function or involving a join the planner can't see through, so rewrite it or add an expression index, which also collects statistics; or a skewed value with too coarse a histogram, so raise the statistics target on that column. Once the estimate is in the right order of magnitude the planner will choose a hash join by itself. As a short-term measure for one query I might disable nested loops inside a transaction with SET LOCAL, to prove the diagnosis and relieve production, but I wouldn't leave that as the solution. I'd also check work_mem, so that the hash join it switches to doesn't spill.

    🧠 Key takeaways

    • An index nested loop costs one index lookup for each outer row. It is the best join for a small outer side and very bad for a large one.
    • A hash join reads each input once and needs memory for the smaller. It is the standard join for large inputs on equality.
    • A merge join walks two sorted inputs. It is cheapest when the order comes free, and it keeps the order.
    • The planner chooses by estimated row counts, so a wrong estimate tends to produce the wrong join.
    • Only the nested loop handles conditions other than equality, and only it and the merge join return rows at once.
    • Join order decides the size of intermediate results. The planner searches the orders itself, exhaustively up to about eight tables.

    A query joins 5 rows of customers to their rows in orders, which has 50 million rows and an index on customer_id. Which join is best?

    Five index lookups, about twenty page reads. A hash join would read all 50 million rows.

    Two tables of 10 million rows each are joined on equality. Neither is sorted, and no index is useful. What will the planner most likely choose?

    It reads each input once. A merge join would have to sort 20 million rows first.
