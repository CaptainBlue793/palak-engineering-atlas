Locking & Two-Phase Locking

When two transactions want to change the same row, one of them has to wait. A lock is how the database arranges the waiting: a note saying who is using what, in which way, and who is queued behind them. Locks are the oldest method of isolating transactions, and for writes they are still the one every database uses. They are also behind a familiar class of production incident, in which nothing is broken, the processors are idle, and every request hangs because one session is holding a lock that all the others need. This chapter covers the kinds of lock, the rule that makes locking give correct results, the locks that ordinary statements take without telling you, and how to see who is blocking whom.

Shared vs exclusive

A lock has an owner, a target and a mode. The two basic modes come from one observation: any number of transactions can safely read the same thing together, and a transaction that is changing it must be alone.

Another transaction holds a shared lockAnother transaction holds an exclusive lock
You ask for a shared lock, to readGrantedYou wait
You ask for an exclusive lock, to writeYou waitYou wait

A transaction that has to wait is put in a queue for that lock and sleeps until the holder releases it. From the application's side, a waiting statement simply doesn't return. It uses no processor time and raises no error, which is why lock problems look so unlike other performance problems.

Two-phase locking

Taking locks is not sufficient by itself. If a transaction locked a row, read it, unlocked it, and later locked it again to write, another transaction could change the row in between, and the lost update of Chapter 21 is back. The rule that makes locking produce serialisable results is two-phase locking, or 2PL: a transaction may acquire locks for as long as it likes, and once it has released any lock it may never acquire another. Its life has a growing phase and a shrinking phase.

Releasing everything at the end, and only then, is called strict 2PL. It has a second benefit: nobody can see or build on a change by a transaction that might yet roll back. The consequence for application code is direct. A lock taken by any statement is held until the transaction ends. A transaction that updates a row and then spends two seconds calling another service holds that row's lock for two seconds.

Under pure 2PL readers take shared locks, so readers and writers block each other. PostgreSQL, Oracle and InnoDB avoid that by letting plain reads use old row versions and take no locks (Chapter 23). Their writes still follow strict 2PL exactly as described.

Row and table locks

Locks exist at two levels, and every statement takes both: a weak lock on the table, which says "I am using this table, don't drop or restructure it", and for writes a lock on each row that is changed.

SELECTACCESS SHAREOnly statements that need the table to themselves
SELECT … FOR UPDATEROW SHARE, and locks on the rowsThe same, and other writers of those rows

Row locks are simpler: two transactions can't modify, or lock for update, the same row at once. In PostgreSQL a row lock is recorded in the row itself, in the header field that names the transaction changing it (Chapter 11), so a transaction can lock a million rows without any memory being used to remember them.

SELECT … FOR UPDATE

A plain SELECT takes no row locks, which is why the read-then-write pattern is unsafe. FOR UPDATE makes a read take the row locks an update would, so that the row can't change between your read and your write.

BEGIN;
SELECT stock FROM items WHERE item_id = 7 FOR UPDATE;      -- anyone else asking for this row now waits
-- … decide in the application …
UPDATE items SET stock = 8 WHERE item_id = 7;
COMMIT;                                                       -- the lock is released here

SELECT … FOR UPDATE NOWAIT;        -- fail at once with an error if the row is locked, without queueing
SELECT … FOR SHARE;                -- others may read and lock for share. Nobody may change the row

-- A job queue: each worker takes the next job that nobody else has claimed
SELECT job_id, payload FROM jobs
WHERE status = 'queued'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;            -- rows locked by other workers are passed over, not waited for

SKIP LOCKED deserves attention. Without it, ten workers that all ask for "the oldest queued job" queue up behind one row and work one at a time. With it, each takes a different job, and a table becomes a safe, concurrent work queue with no other machinery.

The table-lock rules are PostgreSQL's own conflict table. Two sessions also conflict if both want a lock on the same row. A lock request joins the queue behind any earlier request it conflicts with, including one that is itself still waiting, which is what decides the third session's fate.

Things to notice. A plain SELECT is blocked by almost nothing, and blocks almost nothing, since readers don't take row locks. Two updates conflict only when they touch the same row. CREATE INDEX without CONCURRENTLY stops every write to the table until it finishes. Now set session 1 to a SELECT and session 2 to an ALTER TABLE. The ALTER needs the table to itself, so it waits for session 1, which is merely an idle transaction that once read from the table. The third session's SELECT doesn't conflict with session 1 at all. It conflicts with the ALTER that is waiting ahead of it in the queue, so it waits too, and so does every query that arrives after it. One open transaction and one schema change that hasn't even begun have taken the table out of service.

Seeing and limiting waits

-- Who is waiting, and for whom?
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, state,
       now() - xact_start AS xact_age, left(query, 50) AS query
FROM pg_stat_activity WHERE datname = current_database() ORDER BY xact_start;

  pid  | blocked_by | wait_event_type |        state        | xact_age |             query
-------+------------+-----------------+---------------------+----------+-------------------------------
 20417 | {}         | Client          | idle in transaction | 00:14:09 | SELECT * FROM orders WHERE …
 20988 | {20417}    | Lock            | active              | 00:00:41 | ALTER TABLE orders ADD COLUMN …
 21002 | {20988}    | Lock            | active              | 00:00:40 | SELECT … FROM orders WHERE …

SET lock_timeout = '3s';                         -- give up waiting for a lock after 3 s, with an error
SET idle_in_transaction_session_timeout = '60s'; -- end sessions that sit in an open transaction

The first row is the cause, and it is the one row that isn't waiting for anything: a session marked idle in transaction, fourteen minutes old. Somebody's code, or somebody's console, ran BEGIN and a query and then went away. The two settings at the end are the standard protection. A schema change run with a short lock_timeout fails harmlessly if it can't get its lock at once, and can be tried again.

Lock escalation

Some databases keep every row lock as an entry in a table in memory. When one transaction has locked thousands of rows, that table grows large, and the database may swap the many row locks for a single lock on the whole page or table. This is lock escalation. It saves memory and can be a nasty surprise: a batch job that updates 6,000 rows suddenly holds a lock on the whole table, and everyone else stops.

DatabaseRow locks are keptEscalation
SQL ServerIn memoryYes. At about 5,000 locks on one table, it tries to take a table lock
PostgreSQLIn the rows themselvesNone. A transaction can lock any number of rows
MySQL InnoDBIn memory, compactly, as a bitmap for each pageNone. But it also locks the gaps between index entries at Repeatable Read, which can block inserts that touch no existing row
OracleIn the data blocksNone
🚧
GoCardless: fifteen seconds of outage from adding a foreign key

In 2015 the payments company GoCardless published an account of an outage of its API that had lasted about fifteen seconds, with a cause that surprised its own engineers. A routine migration had added a foreign key to a table. They knew the statement needed a strong lock on both tables, and they knew it would hold that lock only for a moment, since the tables were small. They had not allowed for the queue. At the instant the migration ran, some other transaction was open that had touched one of the tables. The migration's lock request conflicted with it, and waited. From then on, every ordinary query against that table, the reads and writes of the live API, was queued behind the waiting migration, although none of them conflicted with the transaction that was really in the way. Requests piled up, the application's connections were all occupied by waiting queries, and the API stopped answering. It recovered when the first transaction ended and the queue drained. The schema change had done no harm. The harm came from waiting for the lock with all the traffic behind it. Their fix became standard practice, and they released it as a library: every migration sets a short lock_timeout first. If the lock can't be had within a few seconds the migration fails, having blocked traffic only for that long, and is run again. Many teams have since had the same outage and adopted the same rule.

⚠️
Common mistakes
  • Holding a transaction open across slow work: an HTTP call, a file upload, waiting for a user. Its locks are held for the whole time.
  • Leaving a console session in a transaction. An idle in transaction session blocks schema changes and holds back VACUUM.
  • Running ALTER TABLE without a lock_timeout. While it waits, everything queues behind it.
  • CREATE INDEX on a live table without CONCURRENTLY. Writes stop for the whole build.
  • Using FOR UPDATE for a work queue without SKIP LOCKED. The workers form a single file.
  • Locking rows in different orders in different code paths. That is how deadlocks are made (Chapter 24).

Interview drill

Explain it simply: What is two-phase locking, and why does it guarantee serialisability?

How a strong answer sounds
Two-phase locking is a rule about when a transaction may take and release locks: it has a growing phase in which it only acquires locks, shared for reads and exclusive for writes, and a shrinking phase in which it only releases them; once it has released any lock it can't acquire another. That guarantees serialisability because it rules out the interleavings that cause anomalies: if transaction A accessed an item before B in a conflicting way, A held the lock until at least the point where it had all its locks, so B can't have accessed some other item before A as well; the transactions can be ordered by the moment each finished acquiring locks, and the execution is equivalent to running them serially in that order. In practice databases use strict 2PL, where all locks are held until commit or rollback, which also means nobody reads uncommitted data and aborts never cascade. The costs are blocking, since readers and writers block each other under pure 2PL, which is why most databases combine write locks with multiversion reads, and deadlocks, which the database has to detect and break. It shouldn't be confused with two-phase commit, which is about atomic commit across several databases.

Deeper: You run ALTER TABLE … ADD COLUMN on a busy table. The statement itself is instant, yet the application goes down for a minute. What happened, and how do you run migrations safely?

How a strong answer sounds
ALTER TABLE needs an ACCESS EXCLUSIVE lock on the table, which conflicts with every other lock, including the ACCESS SHARE that a plain SELECT takes. If any transaction that has touched the table is still open, a long report, or a session left idle in transaction, the ALTER can't get its lock and waits. The damage comes from the lock queue: new requests are queued behind earlier conflicting requests, so every subsequent query on that table, even a simple SELECT, now waits behind the pending ALTER. Within seconds the connection pool is full of blocked queries and the application is down, until the original transaction ends or someone cancels the ALTER. To run migrations safely: set a short lock_timeout, a couple of seconds, before any DDL, so that if the lock isn't available the statement fails fast instead of queueing, and retry it in a loop; set statement_timeout too; check pg_stat_activity for long-running and idle-in-transaction sessions before starting, and enforce idle_in_transaction_session_timeout generally. Prefer forms of DDL that need weaker locks or hold them briefly: CREATE INDEX CONCURRENTLY, adding a foreign key or check constraint as NOT VALID and validating it separately, adding a column without a volatile default. And keep each migration to one such step per transaction, so that a strong lock is never held while something slow runs.

🧠 Key takeaways

  • Shared locks are compatible with each other. An exclusive lock is compatible with nothing. A transaction that can't get a lock waits in a queue.
  • Two-phase locking: acquire, then release, never both at once. In practice every lock is held until the transaction ends.
  • Plain reads take no row locks in PostgreSQL. Writes lock the rows they change, and block other writers of those rows only.
  • Every statement also takes a table lock. Most are weak, and ALTER TABLE takes one that conflicts with everything.
  • FOR UPDATE locks rows when reading them, and SKIP LOCKED turns a table into a concurrent work queue.
  • A waiting lock request blocks later requests behind it, so set lock_timeout on schema changes and don't leave transactions open.

Check your understanding

Under strict two-phase locking, when does a transaction release the lock on a row it updated?

Every lock is held to the end of the transaction, however long that is.

In PostgreSQL, session 1 has updated row 5 and not committed. Session 2 runs a plain SELECT that reads row 5. What happens?

Plain reads take no row locks. They read an older version (Chapter 23).

Ten workers each run SELECT … FROM jobs WHERE status = 'queued' ORDER BY created_at LIMIT 1 FOR UPDATE. What happens, and what fixes it?

SKIP LOCKED passes over rows that another transaction has locked, so each worker gets the next free job.

An ALTER TABLE is waiting for its lock behind a long-running transaction. Why do new SELECTs on the table now hang?

Lock requests are served in order. A pending request for an exclusive lock holds up everything that arrives after it.

What is lock escalation, and does PostgreSQL do it?

SQL Server escalates at about 5,000 row locks. PostgreSQL has no need to.
