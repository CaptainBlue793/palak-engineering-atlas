Data-Size Arithmetic

"Will it fit?" comes up in every design review and most database interviews: will the table fit in memory, how big will the index be, how much disk do we need in three years? You can answer to within a factor of two with arithmetic you can do on a whiteboard: bytes per row, rows per page, pages per table, plus indexes and growth. This chapter gives you PostgreSQL's real overheads, including the one most people miss: alignment padding between columns.

  • Compute a row's on-disk size from its column types, headers and alignment padding
  • Turn row size into rows per page, table size and B-tree index size
  • Reorder columns to remove padding, and know when it's worth it
  • Project growth over time and compare it with memory and disk budgets

Bytes per row

A PostgreSQL row on disk (a tuple) is more than its column values:

  • Tuple header: 23 bytes, padded to 24. It records which transactions created and deleted this version of the row (Chapter 23) and where the next version is. If any column is NULL there's also a null bitmap, one bit per column, which fits inside the padding for tables of up to 8 columns.
  • Line pointer: 4 bytes in the page's slot array, pointing at the tuple (Chapter 11).
  • Column values, each at an aligned offset: an 8-byte type such as bigint or timestamptz must start at a multiple of 8, a 4-byte type at a multiple of 4. If the previous column ended elsewhere, the gap is wasted padding.
  • The whole tuple is rounded up to a multiple of 8.

Variable-length values (text, numeric, jsonb) carry a length header: 1 byte for values up to 126 bytes, and those short values need no alignment. Longer values have a 4-byte header and are aligned to 4; values over about 2 KB get compressed or moved out of line by TOAST.

Rows per page, pages per table

An 8 KB page has a 24-byte header, leaving 8,168 bytes. Each row costs its tuple size plus its 4-byte line pointer. So:

rows per page = floor(8168 / (tuple_bytes + 4))           # capped at 291 by PostgreSQL
table pages   = ceil(rows / rows_per_page)
table bytes   = table pages × 8192

A B-tree index entry is an 8-byte index tuple header (which includes the 6-byte row pointer) plus the key, aligned to 8, plus a 4-byte line pointer. Leaf pages are filled to 90% by default so that inserts don't immediately split them. For a bigint key that's 20 bytes an entry and about 365 entries a page, so roughly 21–22 MB per million rows; a uuid key costs about a third more. These are estimates for freshly built structures; real tables carry extra space from updates and deletes (bloat), so add a margin.

def table_bytes(rows: int, tuple_bytes: int) -> int:
    per_page = min(291, (8192 - 24) // (tuple_bytes + 4))
    return -(-rows // per_page) * 8192                    # ceiling division

def btree_bytes(rows: int, key_bytes: int, fill: float = 0.9) -> int:
    entry = 8 + -(-key_bytes // 8) * 8 + 4                  # header + aligned key + line pointer
    per_page = int((8192 - 24 - 16) * fill // entry)
    return -(-rows // per_page) * 8192 * 1.01              # ~1% for the inner pages

print(table_bytes(100_000_000, 152) / 1e9)    # 15.8 GB of heap
print(btree_bytes(100_000_000, 8) / 1e9)        # 2.3 GB per bigint index

Then check your arithmetic against the real thing; PostgreSQL will tell you exactly:

SELECT pg_column_size(e.*) AS row_bytes FROM events e LIMIT 5;   -- per-row data size (without the line pointer)
SELECT pg_size_pretty(pg_relation_size('events'))        AS heap,
       pg_size_pretty(pg_indexes_size('events'))         AS indexes,
       pg_size_pretty(pg_total_relation_size('events'))  AS total;  -- heap + indexes + TOAST

Column order and padding

Alignment means the same columns can take different space depending on their order. A table that alternates boolean and bigint columns pads 7 bytes after every boolean. Declaring 8-byte columns first, then 4-byte, then 2-byte, then 1-byte and variable-length ones removes nearly all of it:

-- 24 header + (1 + 7 pad + 8) × 2 + 1 + 7 pad + 8  = 72 bytes per row
CREATE TABLE flags_bad  (is_admin boolean, user_id bigint, is_beta boolean, org_id bigint, is_locked boolean, updated_at timestamptz);

-- 24 header + 8 + 8 + 8 + 1 + 1 + 1 = 51, rounded to 56 bytes per row: 22% smaller
CREATE TABLE flags_good (user_id bigint, org_id bigint, updated_at timestamptz, is_admin boolean, is_beta boolean, is_locked boolean);

It's worth doing when you create a large table, because PostgreSQL can't reorder columns afterwards without rewriting the table. For a small table it doesn't matter, and readability should win.

🦊
GitLab's rule for column order

GitLab runs one of the larger public PostgreSQL deployments, with tables of billions of rows. Its database development guidelines include a page on ordering table columns: new tables should list columns from the largest alignment to the smallest (8-byte types, then 4-byte, then 2-byte and 1-byte, with variable-length columns last) specifically to avoid padding. At a billion rows, 8 bytes of padding per row is 8 GB of heap that must be stored, backed up, replicated and, worst of all, competes for the memory that keeps hot pages cached. Reviewers check column order in migrations because fixing it later means rewriting the table.

⚠️
Common mistakes
  • Sizing from column widths alone. On narrow rows the 28 bytes of header and pointer can be half the total.
  • Forgetting the indexes. A table with five indexes often has more bytes in indexes than in the heap.
  • Assuming the table stays at its freshly loaded size. Updates and deletes leave dead space; plan for bloat.
  • Comparing total size with RAM. What must fit is the working set, the pages queries actually touch, usually recent data and index upper levels.
  • Mixing units. Disk vendors use GB (10⁹), PostgreSQL's pg_size_pretty uses binary units (1 kB = 1,024 bytes). The difference is 7% at the gigabyte scale.

Interview drill

Explain it simply: Estimate the size of a table of 1 billion rows with two bigints, a timestamptz and a 20-character text column, plus its primary key index.

How a strong answer sounds
Row: 24-byte header, 8 + 8 + 8 for the fixed columns, 21 for the short text with its 1-byte header: 69, rounded to 72, plus a 4-byte line pointer is 76 bytes. 8,168 ÷ 76 ≈ 107 rows per page, so about 9.3 million pages, roughly 76 GB of heap. A bigint primary key is about 22 MB per million rows, so about 22 GB. Call it 100 GB, and plan for 130–150 GB with bloat and free space. That won't fit in a 64 GB server's RAM, so I'd ask what the hot subset is.

Deeper: Your table is 40% larger than your estimate. What could explain it?

How a strong answer sounds
Bloat first: dead row versions from updates and deletes that VACUUM has marked reusable but that still occupy pages, which I'd check with pgstattuple or the dead-tuple counts in pg_stat_user_tables. Then a fillfactor below 100, padding from column order, NULL bitmaps on wide tables, variable-length columns larger than assumed, or long values stored in TOAST, which pg_total_relation_size counts. Finally, unit confusion between GB and GiB is worth 7%.

🧠 Key takeaways

  • Row bytes = 24 header + aligned columns, rounded to 8, plus a 4-byte line pointer.
  • Rows per page = 8,168 ÷ row bytes; table bytes = pages × 8 KB.
  • A bigint B-tree index is about 22 MB per million rows; indexes often rival the heap.
  • Order columns from largest alignment to smallest to avoid padding in big tables.
  • Add growth and a bloat margin, and compare the working set with RAM, not the whole table.

Check your understanding

What fixed overhead does every PostgreSQL row carry before any column data?

The header holds MVCC information; the line pointer lives in the page's slot array. Together about 28 bytes per row.

Columns declared as (boolean, bigint, boolean, bigint) waste space because…

Alignment padding. Declaring the bigints first and the booleans after removes it.

Rows are 76 bytes including the line pointer. Roughly how many fit on an 8 KB PostgreSQL page?

8,168 usable bytes ÷ 76 ≈ 107.

Roughly how big is a B-tree index on a bigint column for 100 million rows?

Each entry is about 20 bytes (8-byte index tuple header, 8-byte key, 4-byte line pointer), pages are 90% full: around 22 MB per million rows.

A table is 300 GB and the server has 128 GB of RAM. Does it matter?

Databases cache pages, not tables. What matters is whether the pages your queries actually touch stay cached.
