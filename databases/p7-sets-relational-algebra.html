Sets & Relational Algebra

Every SQL query, however long, is built from a handful of operations on tables: keep some rows, keep some columns, combine two tables, stack or subtract them. That small set of operations is relational algebra, and it's what the database actually works with: the planner turns your SQL into an algebra tree, rearranges it using algebraic laws, and then picks an algorithm for each node. Knowing the algebra makes joins less mysterious, explains why DISTINCT and UNION cost what they cost, and gives you the vocabulary of query processing.

  • Treat a relation as a set of tuples and say where SQL differs (it uses bags)
  • Use selection (σ), projection (π), product (×) and join (⋈), and write each in SQL
  • See a join as a product followed by a selection, and why no database computes it that way
  • Use union, intersection and difference, and choose between UNION and UNION ALL
  • Apply the rewrite rule the optimiser uses most: push selections down

Relations are sets of tuples

In Codd's relational model a table is a relation: a set of tuples that all have the same attributes. Two consequences follow from "set": there are no duplicate tuples, and there is no order. Every operator takes one or two relations and returns a new relation, so operators compose like arithmetic: the output of one is the input of the next. That closure is what lets a query be a tree.

SQL bends the first rule. SQL tables and results are bags (multisets): duplicates are allowed unless a key or DISTINCT forbids them. Removing duplicates means sorting or hashing every row, so SQL makes it opt-in. Keep this difference in mind; it's behind several of the comparisons below.

Selection is horizontal (fewer rows), projection is vertical (fewer columns). A typical query is "σ, then ⋈, then π": filter, combine, and keep what the result needs. Written as algebra, the query "names of employees in the London office" is:

πname( σcity = 'London'( employees ⋈employees.dept_id = departments.dept_id departments ) )

SELECT e.name
FROM   employees e
JOIN   departments d ON e.dept_id = d.dept_id
WHERE  d.city = 'London';

A join is a product plus a filter

The definition R ⋈p S = σp(R × S) is exact, and it's the best way to reason about what a join returns, especially the surprising cases: a row of R that matches three rows of S appears three times; a row that matches nothing disappears (that's what outer joins fix, in Chapter 3). But it's a terrible way to compute one. Two tables of a million rows have a product of 1012 pairs. Real engines produce only the matching pairs directly, with nested loops over an index, hash tables or sorted merges (Chapter 18). Watch the definition at small scale:

Union, intersection and difference

The set operators need union-compatible inputs: the same number of columns, with compatible types, matched by position. They answer "which customers ordered in both years?" (∩), "who ordered in 2025 but not 2026?" (−, a churn list), and "everyone who ordered in either year" (∪).

SELECT customer_id FROM orders WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'
EXCEPT
SELECT customer_id FROM orders WHERE created_at >= '2026-01-01';      -- churned customers, each once

The practical rule: use UNION ALL unless you need duplicates removed. Combining this month's and last month's event tables with UNION makes the database sort or hash every row just to look for duplicates that can't exist.

Rewriting the tree: push selections down

Because the operators obey algebraic laws, the planner can transform a query tree into an equivalent one that's cheaper to run. Joins are commutative and associative, so the order of joins is a choice (Chapter 19). The single most valuable rule is selection pushdown: if a predicate only mentions one input of a join, apply it to that input before joining.

σcity='London'(employees ⋈ departments)  =  employees ⋈ σcity='London'(departments)

The left side joins everything and then throws most of it away; the right side joins against the one or two London departments. Same answer, often orders of magnitude less work. Projections can be pushed down too, so that only the columns the query uses travel up the tree.

🪣
Predicate pushdown in a data lake

Engines such as Trino, Spark and DuckDB query Parquet files sitting in object storage. Each Parquet file stores per-column minimum and maximum values for every row group of (typically) many thousands of rows. When a query says WHERE event_date = '2026-09-30', the engine pushes that selection all the way down into the file reader, which skips every row group whose date range can't contain the value, without downloading it. On a table of a year's events partitioned and sorted by date, that turns a scan of terabytes into a read of a few gigabytes. It's the same σ-pushdown law as above, applied across the network instead of inside one server.

⚠️
Common mistakes
  • UNION where UNION ALL would do. An unnecessary sort or hash over the whole result.
  • Assuming SELECT col returns distinct values. SQL keeps duplicates unless you say DISTINCT.
  • Forgetting a join condition. FROM a, b with no WHERE linking them is a Cartesian product: rows(a) × rows(b).
  • Set operators on columns in a different order. They match by position, not by name, and happily combine email with name if the types agree.
  • Sprinkling DISTINCT to hide duplicate rows from a join. The duplicates usually mean the join is wrong (Chapter 3).
🎤
Interview drill

Explain it simply: What's the difference between UNION and UNION ALL, and which is faster?

How a strong answer sounds
UNION returns the distinct rows of both inputs, so the database has to sort or hash the whole combined result to find duplicates. UNION ALL just appends one result to the other and keeps every row. UNION ALL is cheaper and can stream; I use it by default and choose UNION only when duplicates are actually possible and unwanted.

Deeper: Why can a database rewrite WHERE d.city = 'London' to run before the join, and when would that rewrite be wrong?

How a strong answer sounds
For an inner join, σp(R ⋈ S) equals R ⋈ σp(S) when p only uses S's columns: a pair survives only if S's row satisfies p either way. Filtering first shrinks the join input. It's wrong for the nullable side of an outer join: with employees LEFT JOIN departments, a WHERE d.city = 'London' after the join also removes employees with no department, while the same condition inside the ON clause keeps them with NULLs. Planners know these rules and only push predicates where the result is unchanged.

🧠 Key takeaways

  • Relational algebra: σ (rows), π (columns), × and ⋈ (combine), ∪, ∩, − (stack and compare).
  • Relations are sets; SQL results are bags, so duplicates stay unless you ask for DISTINCT.
  • A join is σp(R × S) by definition, but engines never build the product.
  • UNION ALL appends; UNION, INTERSECT and EXCEPT remove duplicates, which costs a sort or hash.
  • Planners rewrite the algebra tree; pushing selections below joins is the most valuable rewrite.

Check your understanding

Which SQL corresponds to the projection πdept_id(employees) in relational algebra?

Algebraic projection returns a set, so duplicates are removed. Plain SELECT keeps duplicates (bag semantics).

employees has 1,000 rows and departments has 20. How many rows does SELECT * FROM employees, departments return with no WHERE clause?

Listing tables with commas and no join condition is R × S: every employee paired with every department.

Which query lists customers who ordered in 2025 but not in 2026?

Difference (R − S, EXCEPT in SQL) keeps rows of the first input that don't appear in the second.

Why is UNION ALL usually faster than UNION?

UNION must find and remove duplicates across the combined result. UNION ALL just concatenates.

What does "pushing a selection below a join" mean?

σp(R ⋈ S) = R ⋈ σp(S) when p mentions only S (for inner joins). Same result, smaller intermediate data.
