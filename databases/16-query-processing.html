How a Query Runs

SQL says what you want and nothing about how to get it. Between the text you send and the rows that come back, the database turns the first into the second in four stages: it checks that the text is valid SQL, works out what the names in it refer to, chooses one way of computing the answer out of many, and then runs that choice. Knowing the stages tells you where an error message comes from, why the same query can take a millisecond or a minute depending on the plan, why LIMIT 10 can stop a scan after ten rows or after ten million, and what the output of EXPLAIN is a picture of. This chapter follows one query through all four.

Parse and analyse

The parser knows the grammar of SQL and nothing about your database. It will accept SELECT nonsense FROM nowhere, because that is a well-formed statement. The analyser then opens the system catalogue, the tables in which the database describes itself, and resolves every name. It finds that orders is a table with a particular identity, that total_cents is its fourth column and of type bigint, and that > applied to a bigint and an integer literal means a specific comparison function. If it must convert a type to make an expression work, it inserts the conversion here.

SELECT o.order_id, o.total_cents
FROM orders o
WHERE o.total_cents > 10000
ORDER BY o.total_cents DESC
LIMIT 3;

After analysis this is no longer text. It is a tree which says: from the relation with this identity, take the rows for which this function of column 4 returns true, order them by column 4 descending, keep three, and output columns 1 and 4. Nothing yet says how.

Rewrite

A view is a stored query (Chapter 5). The rewriter substitutes the view's definition wherever its name appears, so that the planner sees one large query over base tables and can optimise across the boundary: a filter written against the view can be pushed down to an index on the table beneath. Row-level security works the same way, by adding each policy's condition to the query's WHERE clause. This is why a view costs nothing in itself, and why a query against a harmless-looking view can be very expensive: you are running whatever the view contains.

Plan

For the query above there are several ways to get the answer: read the whole table, filter it and sort what is left; or, if there is an index on total_cents, read the index backwards from its largest value and stop after three rows. With joins the number of possibilities multiplies, since the tables can be joined in any order and by three different algorithms (Chapter 18). The planner estimates the cost of each candidate from statistics about the data and picks the cheapest (Chapter 19). Its output is a plan: a tree of operators, each of which does one simple thing.

EXPLAIN SELECT … ;                     -- shows the plan without running it

 Limit
   ->  Sort
         Sort Key: total_cents DESC
         ->  Seq Scan on orders
               Filter: (total_cents > 10000)

Planning is work, and for a short query it can take longer than running it. A prepared statement lets a client send the text once, with placeholders, and execute it many times, so that parsing and analysis aren't repeated, and often planning isn't either. Most drivers do this for you (P6).

Execute: the iterator model

Every operator in the plan offers the same small interface: "give me your next row". This is the iterator model, also called the Volcano model after the system that introduced it. The executor asks the root of the tree for a row. The root asks its child, which asks its own child, down to a scan that reads a row from a table. The row travels back up, changed or discarded by each operator on the way. Then the executor asks for the next. Python's generators behave in exactly this way, and three operators take a dozen lines:

def seq_scan(table, predicate):
    for row in table:                       # one row is read each time someone asks
        if predicate(row):
            yield row

def sort(child, key):
    rows = sorted(child, key=key)            # has to consume ALL of its input before it can yield anything
    yield from rows

def limit(child, n):
    for i, row in enumerate(child):
        if i == n:
            return                           # stops asking: the child never produces another row
        yield row

plan = limit(sort(seq_scan(orders, lambda r: r.total_cents > 10000), key=lambda r: -r.total_cents), 3)
for row in plan:                            # the executor: keep asking the root
    send_to_client(row)

    Things to notice. Asking for any three rows over £100, the scan reads six rows and stops. The other six are never touched, because Limit stopped asking. Asking for the three largest by sorting, the first call to next() does almost all of the work: Sort has to pull every row out of the scan before it can know which is largest, so all twelve are read before one is returned, and the limit has saved nothing. With an index on the total, the same three rows come back after reading three rows. The index is already in order, so the plan needs no Sort and has no blocking operator, and Limit can stop it early. All three plans give a correct answer to their query. The cost differs fourfold on twelve rows, and on twelve million the same plans differ by a factor of millions.

    Vectorised execution

    The iterator model has a fixed cost for every row at every operator: a function call that can't be predicted, a few branches to find out what type of value it has, and a result handed back. For a query that fetches twenty rows, that cost is nothing. For an analytical query that adds up a billion values, it is nearly all of the work, since the addition is one machine instruction and the machinery round it is dozens.

    One row at a timeVectorisedCompiled
    Each call returnsOne rowA batch of about a thousand values of one columnNothing: there are no calls
    Inner loopInterpreted afresh for each rowA tight loop over an array, which the processor can run with SIMD instructionsMachine code generated for this one query
    Overhead for each valueTens of instructionsAbout oneAbout one
    Best forShort transactional queriesScans and aggregates over many rows of few columnsThe same, with more complex expressions
    Used byPostgreSQL, MySQL, SQLiteDuckDB, ClickHouse, SnowflakePostgreSQL's JIT for expressions; several research engines

    Vectorised execution keeps the same tree of operators and changes what flows between them: each call returns a batch of values, stored column by column. The overhead is then paid once for a thousand values, and the work inside an operator becomes a simple loop over an array. It goes naturally with storing tables by column (Chapter 28), and the two together are why an analytical database can aggregate a billion rows in a second on one machine.

    🧮
    When compiling a query took longer than running it

    PostgreSQL gained a just-in-time compiler in version 11, and from version 12 it was switched on by default. It attacks the overhead described above: for a query that the planner expects to be expensive, it generates machine code for the query's own expressions, the filter conditions and the column extraction, using LLVM, so that they need not be interpreted for every row. On long analytical queries this gives a real improvement. The decision to compile, though, is made from the planner's estimate of cost before the query has run, and compiling takes time itself, anything from a few milliseconds to several hundred. After upgrading, a number of teams found certain queries had become slower, and EXPLAIN ANALYZE showed why in a line they hadn't seen before: a query that executed in 20 ms was spending 400 ms being compiled first. The usual cause was a cost estimate that was far too high. A query over a table with hundreds of partitions, or one where the planner expected millions of rows and found a few, crossed the threshold and paid for compilation that could never be repaid. The remedies are to raise jit_above_cost, to fix the estimate, or, as many transactional systems do, to turn JIT off, since their queries are all short. The case shows the stages of this chapter interacting. A mistake at the planning stage, a wrong estimate, led to wasted work at the start of execution, and it could only be found because the tool reports the time spent in each stage separately.

    ⚠️
    Common mistakes
    • Assuming LIMIT makes a query cheap. It does only when nothing blocking sits beneath it. With ORDER BY and no suitable index, everything is read first.
    • Treating a view as a table. It is expanded into your query. Read its definition before you join five of them.
    • Building SQL strings with the values pasted in, so that every execution is a new statement to parse and plan, as well as an injection risk (P6).
    • Blaming "the database" for a slow query without finding the stage. It is nearly always the plan that was chosen, and occasionally the time taken to choose it.
    • Fetching a huge result into memory in the application when the database would have streamed it row by row through a cursor.
    • Expecting a transactional database to do analytics at warehouse speed. Row-at-a-time execution has a cost for every row that no index removes.

    Interview drill

    Explain it simply: What happens between sending a SQL query and getting rows back?

    How a strong answer sounds
    Four stages. The parser checks the syntax and builds a parse tree. The analyser resolves every name against the catalogue, tables, columns, functions and operators, checks types and permissions, and produces a query tree; that is where "column does not exist" comes from. The rewriter expands views into their definitions and applies row-level security. Then the planner takes that logical description and decides how to execute it: which access path to use for each table, sequential scan or an index, the join order and join algorithms, where to sort or aggregate. It enumerates alternatives, estimates the cost of each from table statistics, and picks the cheapest; its output is a tree of physical operators, which is what EXPLAIN prints. Finally the executor runs that tree using the iterator model: it repeatedly asks the root operator for the next row, each operator asks its children, and rows flow up from the scans, being filtered, joined and sorted on the way, and are sent to the client as they are produced. With prepared statements, the parse and analysis, and often the plan, are reused across executions.

    Deeper: Two queries both end in LIMIT 10. One returns in a millisecond and the other takes a minute. How can that be?

    How a strong answer sounds
    LIMIT only saves work if the plan beneath it is pipelined, meaning rows flow through one at a time, so that when Limit stops calling next() its children simply stop. In the fast query, the plan is something like Limit over an index scan that already produces rows in the required order, or over a scan with a filter and no ordering: the executor reads until ten rows have come through and stops. In the slow query there is a blocking operator between the Limit and the data: typically a Sort, because of an ORDER BY with no matching index, or a hash aggregate for GROUP BY or DISTINCT, or a window function. A blocking operator has to consume its entire input before it can emit its first row, so the full scan, join and sort all happen, and Limit then discards all but ten rows. PostgreSQL does optimise the sort into a top-N heap that keeps only ten rows in memory, but it still has to read every input row. There is a third case: a pipelined plan where matches are rare, such as an index scan in ORDER BY order with a selective filter applied afterwards, which may walk millions of index entries before finding ten that pass. I'd look at the plan with EXPLAIN ANALYZE: the node where the actual row count drops from millions to ten shows where the work was done, and the usual fix is an index that provides both the filter and the order.

    🧠 Key takeaways

    • A query is parsed, analysed, rewritten, planned and executed. The first three settle what it means, and the last two how it is done.
    • Syntax errors come from the parser, unknown names and type mismatches from the analyser, and run-time errors from the executor.
    • A view is expanded into the query before planning, so it costs whatever its definition costs.
    • A plan is a tree of operators. The executor pulls rows from the root, and each operator pulls from its children.
    • Pipelined operators pass rows on at once, and blocking ones such as Sort need all their input first. LIMIT saves work only above pipelined operators.
    • Vectorised engines pass batches of column values between operators, which removes most of the cost per row for analytical queries.

    Check your understanding

    At which stage is ERROR: column "custmer_id" does not exist raised?

    The statement is grammatical, so the parser accepts it. The analyser is the first stage that knows what columns exist.

    A query selects from a view with a WHERE clause. What does the planner see?

    The rewriter expands the view, so the filter can be pushed down to the tables and their indexes.

    In the iterator model, what does the executor do to get a result row?

    Rows are pulled on demand, one at a time, which is what lets an operator such as Limit stop the ones below it.

    SELECT … ORDER BY total DESC LIMIT 3 runs on a table with no index on total. How many rows does the scan read?

    Sort is a blocking operator, so the Limit above it can't cut the scan short.

    Why do analytical databases pass batches of column values between operators and not single rows?

    For a scan of a billion values, the interpretation overhead for each row is most of the cost.
