Case Study: Discord's Trillions of Messages

Discord is a chat service, and nearly everything in it is a message in a channel. In 2015 its messages were in a single MongoDB replica set. In 2017 the company wrote about moving them to Cassandra, by then holding billions of messages on twelve machines. In 2023 it wrote again: trillions of messages, 177 Cassandra machines that had become a constant operational burden, and a migration to ScyllaDB that left it with 72. The story covers eight years of one table, and the table's definition hardly changed in that time. It is worth studying for two reasons. It is the clearest published example of designing a wide-column table from its queries, as Chapter 30 described. And it shows what a good partition key can and can't do: the key kept partitions to a manageable size and did nothing about heat, and dealing with heat took an extra layer of software in front of the database.

The data model

Chat has one query that matters more than all the others together: show the most recent messages in this channel, and then the page before those as the user scrolls up. Writes are appends, nearly all of them to the present moment. Edits and deletions exist and are rare. Nothing joins messages to anything, and nobody asks for all messages by one author across the system.

That profile is what wide-column stores are built for (Chapter 30). In Cassandra a table's primary key has two parts. The partition key decides which machines hold a row: all rows with the same partition key form one partition, stored together on one set of replicas. The clustering key decides the order of rows inside a partition. A query that names one partition and reads a run of rows in clustering order is a single sequential read on one machine, and that is the only kind of query such a database does really well. The design task is to choose the keys so that the important query has that form.

CREATE TABLE messages (
  channel_id bigint,
  bucket     int,
  message_id bigint,
  author_id  bigint,
  content    text,
  PRIMARY KEY ((channel_id, bucket), message_id)       -- partition key in the inner brackets, then the clustering key
) WITH CLUSTERING ORDER BY (message_id DESC);

-- The query the table exists for
SELECT * FROM messages
WHERE  channel_id = 81384788765712384 AND bucket = 412
LIMIT  50;                                             -- the newest 50: the first 50 rows of the partition

The message_id is what Discord calls a snowflake: a 64-bit number whose high bits are a timestamp in milliseconds, so that sorting by ID sorts by time (Chapter 46 takes such IDs apart). With messages clustered by ID in descending order, the newest messages in a partition are physically first, and "the latest 50" reads the start of the partition and stops.

Partition keys by channel and bucket

The obvious partition key is the channel alone, and it has a flaw that takes a year to show. A partition has no upper limit, and a busy channel never stops growing. Cassandra's own guidance is to keep partitions under about 100 MB, and it logs a warning above that: a very large partition makes compaction slow, strains memory when it is read, and can't be divided between machines, since a partition is the unit of placement.

Discord's answer was to add time to the partition key. Each message belongs to a bucket, a fixed window of ten days, computed from the timestamp inside its ID.

DISCORD_EPOCH = 1420070400000                  # 1 January 2015, in milliseconds
BUCKET_SIZE   = 1000 * 60 * 60 * 24 * 10       # ten days, in milliseconds

def make_bucket(snowflake):
    timestamp = snowflake >> 22                # the top 42 bits: milliseconds since the Discord epoch
    return timestamp // BUCKET_SIZE

def recent_messages(channel_id, limit=50):
    bucket, out = make_bucket(now_as_snowflake()), []
    while len(out) < limit and bucket >= first_bucket(channel_id):
        out += query(channel_id, bucket, limit - len(out))     # one partition for each step back
        bucket -= 1
    return out

A channel is now a chain of partitions, one for each ten days, each of bounded size. The cost is in the read. A busy channel finds its 50 messages in the current bucket. A quiet one may have to step back through several buckets to collect 50, and each step is another query.

A message is taken as 250 bytes on disk. The dormant channel had 50 messages a day for some months and has been silent for 400 days. A partition over 100 MB is where Cassandra starts to warn, and one over a gigabyte is trouble. The bucket length matters only when the key includes a bucket.

Things to notice. With the channel alone as the key, every read is one partition, and the busiest channel's partition is 3.6 GB after a year and growing by 10 MB a day. With the message ID alone, the data is spread perfectly evenly and the one query that matters can't be answered without asking every machine. Channel and bucket lies between them, and the bucket length is a second trade-off. Ten days gives the busiest channel partitions of 100 MB. One day gives it 10 MB, and makes the dormant channel's reader step back through 400 empty partitions to find anything. A hundred days makes that walk short and the largest partition a gigabyte. No bucket length suits both the busiest channel and the quietest, and Discord later added a record of each channel's last message so that a reader could go straight to the right bucket.

Hot partitions

Bucketing bounds a partition's size. It does nothing about how often a partition is read. Every read of a busy channel's recent messages goes to the same partition, the current bucket, and so to the same three replicas. When a server with hundreds of thousands of members posts an announcement that notifies everyone, a large share of them open the channel within seconds, and all of those reads land on three machines.

On Cassandra that turned out to hurt much more than the busy channel. A machine under heavy read load slowed down for every partition it held. Reads in an LSM tree have to consult several files (Chapter 14), and a machine too busy serving reads to finish its compactions accumulated more files, which made each read more expensive still. Cassandra runs on the Java virtual machine, and under memory pressure its garbage collector paused the whole process, sometimes for seconds. A slow machine made the queries waiting on it queue up at their coordinators, and the latency spread through the cluster. Discord's engineers described nursing machines through this by hand, taking a struggling one out of rotation to let it compact in peace and then bringing it back, and spending a great deal of effort tuning the collector.

Deletes brought a problem of their own. In an LSM store a delete writes a marker, a tombstone, and the data is removed later at compaction (Chapter 14). Discord's 2017 article described a public channel whose owner had deleted millions of messages, leaving one. Loading it meant scanning past millions of tombstones to find a single live row, which took around twenty seconds and long enough in garbage collection to make the machine appear down. The fix was to expire tombstones sooner and to keep track of empty buckets so that readers could skip them.

Moving to ScyllaDB

ScyllaDB is a reimplementation of Cassandra: the same data model, the same query language and the same file formats, written in C++ with a different internal design. It has no garbage collector, so there are no collection pauses. It divides each machine's cores, memory and data into independent shards, one for each core, which share nothing, so that a hot shard is isolated from its neighbours and no locks are contended between cores. Its scheduler gives compaction a budget alongside queries, so that neither starves the other. For Discord the data model didn't need to change at all. What changed was how the engine behaved under the load that model produced.

Data services

Before migrating, Discord changed what talks to the database. Until then the main application queried Cassandra directly. The team put a layer of small services between them, written in Rust, each offering about one operation for each kind of query, and gave that layer two jobs that the database couldn't do for itself.

The first job is request coalescing, shown above. It differs from caching in that nothing is stored after the reply and nothing can be stale: it only merges requests that are in flight together. That is exactly the shape of a hot partition's load, where the traffic is thousands of identical reads at once. The second job is routing. Requests for a channel are sent to a particular instance of the service, chosen by consistent hashing on the channel ID, so that all the requests for one channel meet at one instance and can be coalesced there, where otherwise they would be scattered over all of them. The layer also gave the team a single place to limit how many queries run at once, and to change the database behind it, which they were about to do.

The migration that stopped at 99.9999%

Moving trillions of messages between live clusters has two parts, as Chapter 34 described for a single table. New data was handled by writing every new message to both Cassandra and ScyllaDB from a chosen moment onwards. Old data needed a backfill, and the first estimate, using ScyllaDB's standard migration tool, was three months. The team thought that too long to run two clusters side by side, and wrote a migrator of its own in Rust. It read the Cassandra cluster one range of the token ring at a time, wrote each range to ScyllaDB, and recorded its progress in a local SQLite file so that it could be stopped and resumed. By Discord's account it moved up to 3.2 million messages a second, and the new estimate was nine days. It ran for those days and then stopped with 99.9999% done. The final ranges of the token ring wouldn't finish reading: they timed out again and again. The cause was the problem from 2017 in a larger form. Those ranges held enormous runs of tombstones left by old deletions, which Cassandra's compaction had never reached, and reading through them took longer than any timeout allowed. The team forced a compaction of that range on the Cassandra side, the tombstones were cleared, and the last fraction of a per cent went through in seconds. They then checked a sample of reads against both clusters, switched reads over, and turned Cassandra off. Some months later the new cluster met its first real test, the final of the 2022 football World Cup, during which message volume leapt at each goal clearly enough that the goals could be read off the traffic graph. Discord reported that the database took it without difficulty.

⚠️
Common mistakes
  • A partition key with no bound on its size. A channel, user or device alone, for data that grows for ever.
  • Thinking a good partition key prevents hot spots. It bounds size. Popularity is a property of the traffic.
  • Buckets chosen for the busiest key only. Quiet keys then pay with many empty reads.
  • Designing the table before listing the queries. In a wide-column store the query decides the key.
  • Heavy deletion in an LSM store without a plan for tombstones. Reads have to step over them until compaction removes them.
  • Letting every application query the database directly, with nowhere to coalesce, limit or redirect requests.

Interview drill

Explain it simply: How would you choose the partition key for a table of chat messages in Cassandra?

How a strong answer sounds
I'd start from the main query, which is the most recent N messages in a channel, paged backwards. In Cassandra, an efficient query reads one partition in clustering order, so the channel has to be in the partition key and the clustering key should be a time-ordered message ID, descending, so that the newest rows come first. But channel alone is unbounded: a busy channel's partition would grow for ever, and large partitions cause slow compactions and memory pressure and can't be split across nodes. So I'd add a time bucket to the partition key, say ten days derived from the message ID's timestamp, which caps each partition's size. The trade-off is that reading recent messages in a quiet channel may need several buckets, so I'd size the bucket for the largest channels and mitigate the walk for quiet ones, for instance by storing each channel's latest message ID so that the reader starts at the right bucket. I'd also say what the key doesn't solve: a very popular channel's current bucket is still one partition on three replicas, so read heat needs caching or request coalescing in front.

Deeper: One channel in your chat system suddenly gets a hundred times the usual read traffic. What happens, and how do you protect the rest of the system?

How a strong answer sounds
All of those reads hash to the same partition, so they land on the same replica set, three nodes if the replication factor is three. Those nodes' CPU and I/O saturate. The danger is the blast radius: each node holds many partitions, so every other channel with data there slows too, coordinators queue requests waiting on them, and timeouts and retries add load. In an LSM engine it can spiral, since a node busy with reads falls behind on compaction and reads then touch more files. Protections, from the outside in. Coalesce identical in-flight requests in a service layer: a thundering herd for the same 50 messages becomes a few queries, with no staleness. Route requests for a key to the same service instance with consistent hashing so that coalescing is effective. Add a short-lived cache for the hottest reads if a second or two of staleness is acceptable. Limit concurrency per partition or per node at that layer, shedding load before the database queues it. Use timeouts and hedging carefully so that retries don't multiply the load. On the database side, an engine that isolates load for each core and schedules compaction against queries degrades more gracefully, and reading at a lower consistency level spreads reads across replicas. Structurally, if a single key is hot all the time, I'd split it further, with sub-buckets, but for bursts on the newest data coalescing and caching are the right tools.

🧠 Key takeaways

  • In a wide-column store the table is designed for one query: the partition key locates it, and the clustering key orders it.
  • Chat messages: partition by channel and a time bucket, cluster by a time-ordered ID, newest first.
  • The bucket bounds partition size. Its length trades the largest partition against the reads a quiet key needs.
  • A hot partition is a traffic problem, and it slows every other partition on the same machines.
  • Discord kept its data model and changed its engine: no garbage collector, a shard for each core, compaction scheduled against queries.
  • A data service in front of the database can coalesce identical requests, route them by key and cap concurrency.
