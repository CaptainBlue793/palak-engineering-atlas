Pages, Tuples & Heap Files

Every table you have queried so far is a file on disk, cut into 8 KB pages, with rows packed into the pages by a small set of rules. Those rules explain a good deal of behaviour that otherwise looks arbitrary: why a table doesn't shrink when you delete from it, why an update can be cheap or expensive depending on how full a page is, why a 1,900-byte column can make a table slower than a 5,000-byte one, and why you must never store a row's physical address. This chapter opens the file and looks at one page: how rows are placed in it, what happens to it under inserts, updates and deletes, and where values go when they are too large to fit.

Slotted pages

A page has to hold rows of different lengths, let them be added and removed, and give each one an address that stays valid. PostgreSQL's answer, and nearly every database's, is the slotted page. A small array of line pointers grows forward from the start of the page. The rows themselves, called tuples, are packed in from the end and grow backward. The free space is whatever is left in the middle.

A row's address is the pair (page number, line pointer number). PostgreSQL calls it a ctid, and it is what an index entry stores (Chapter 9). The address names the line pointer and not the tuple's byte offset, and that indirection is why the design works. The database can slide tuples about inside the page to close up gaps, and only the offsets in the line pointers change. Nothing outside the page needs to know.

CREATE EXTENSION pageinspect;

SELECT lower, upper, pagesize FROM page_header(get_raw_page('orders', 0));
--  lower | upper | pagesize
--    268 |   384 |     8192        61 line pointers (24 + 61 × 4), and 116 bytes free

Tuple headers

Each tuple begins with a 23-byte header (P8 counted its cost). The fields are there to answer one question for any transaction that reads the page: is this version of the row visible to me?

FieldBytesMeaning
t_xmin4The transaction that created this version
t_xmax4The transaction that deleted or replaced it, or 0 if nobody has
t_cid4Which command inside that transaction, so that a statement doesn't see its own changes
t_ctid6This version's own address, or the address of the newer version that replaced it
t_infomask, t_infomask24Flags: has NULLs, has out-of-line values, "xmin is known to have committed", number of columns
t_hoff1Where the column data begins, after the header and the optional NULL bitmap

Two of these are visible from SQL as hidden columns: SELECT ctid, xmin, xmax, * FROM orders shows them. The header exists because PostgreSQL never overwrites a row. An UPDATE writes a complete new tuple and sets t_xmax on the old one, and a DELETE only sets t_xmax. Old versions stay on the page until no transaction can still see them. Chapter 23 explains the visibility rules, and this chapter needs only the consequence: updates and deletes leave dead tuples behind, and something has to clean them up.

Heap files

A table is stored as a heap file, a sequence of pages numbered from 0. "Heap" means unordered: a row goes wherever there is room, and nothing keeps rows sorted by their key. The file is split into segments of 1 GB on disk, and two small companion files sit beside it.

SELECT pg_relation_filepath('orders');       -- base/16384/16412

$ ls -1 $PGDATA/base/16384/16412*
16412          # pages 0 to 131,071: the first gigabyte
16412.1        # the second gigabyte
16412_fsm      # free space map: roughly how much room each page has
16412_vm       # visibility map: which pages hold only rows that everyone can see

Three consequences follow from "unordered, never overwritten":

  • A table doesn't shrink when rows are deleted. Dead tuples are removed by VACUUM and their space is reused for later inserts, but the pages stay in the file. A table that once held a billion rows keeps its size until it is rewritten.
  • A row's ctid is not an identifier. It changes whenever the row is updated, and can be given to a different row after a VACUUM. Use the primary key.
  • A sequential scan reads every page, including pages that are mostly dead tuples or mostly empty. A bloated table is slow to scan whatever number of live rows it has.

The table has two indexes. An update that keeps the new version on the same page, and changes no indexed column, needs no index writes at all: PostgreSQL calls it a heap-only tuple (HOT) update. PostgreSQL also prunes a page by itself when a query visits it and finds it nearly full, which the VACUUM button stands in for here.

Things to notice. Fill the page at fillfactor 100 and eight rows fit, with 136 bytes to spare. Update one of them and the new version has nowhere to go on this page. It is written to another page, the row gets a new address, and both indexes need a new entry pointing to it. The old version stays behind as a dead tuple. Delete a row and nothing is freed either: the tuple is only marked. VACUUM is what removes dead tuples and slides the survivors together, and the line pointers it frees are reused by later inserts. Now reset, choose fillfactor 70 and fill again. Inserts stop at five rows, and the next three updates fit on the page. Each of those is a HOT update with no index writes, and after a VACUUM the row's original line pointer redirects to the new version, so its address in the indexes is still valid.

Fillfactor

The panel shows the trade exactly. Fillfactor is the percentage of each page that inserts may fill, with the remainder kept back for updates. The default for tables is 100.

ALTER TABLE sessions SET (fillfactor = 80);      -- applies to pages written from now on
VACUUM FULL sessions;                             -- or rewrite the table to apply it everywhere (takes an exclusive lock)

-- Is it working? The share of updates that were heap-only:
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0)) AS hot_pct
FROM pg_stat_user_tables WHERE relname = 'sessions';
--  sessions | 48210377 | 44836650 |  93
TableFillfactorWhy
Append-only: events, logs, an audit trail100Rows are never updated, so reserved space would be wasted for ever
Updated now and then: orders, users100, or 90Deleted and dead tuples already leave some room
Updated constantly: sessions, counters, job queues70 to 85Most updates stay on their page and skip every index

A lower fillfactor makes the table larger by the same proportion, so scans read more pages. And reserved space doesn't help at all if the update changes a column that has an index, since the index needs a new entry in any case. An index on a column such as updated_at turns every update of the row into a full one.

TOAST for large values

A tuple can't span pages, so a row has to fit in 8 KB. A text or jsonb value can be up to 1 GB. The mechanism that reconciles the two is TOAST. When a row would exceed about 2 kB, PostgreSQL takes its largest variable-length values and first tries to compress them. If the row is still too big, it moves them out of the row into a separate TOAST table, cut into chunks of about 2,000 bytes, and leaves an 18-byte pointer in their place.

Storage strategyCompress?Move out of line?Default for
PLAINNoNoFixed-length types: integer, timestamptz
MAINYesOnly as a last resortnumeric
EXTENDEDYesYestext, jsonb, bytea
EXTERNALNoYesNothing. Set it for data that is already compressed, or when you need fast substring access
 
ALTER TABLE documents ALTER COLUMN body SET STORAGE EXTERNAL;
ALTER TABLE documents ALTER COLUMN body SET COMPRESSION lz4;      -- faster than the default, pglz

SELECT pg_size_pretty(pg_relation_size('documents'))                            AS heap,
       pg_size_pretty(pg_relation_size(reltoastrelid)) AS toast
FROM pg_class WHERE relname = 'documents';
--  heap  | toast
--  41 MB | 9216 MB        the table you scan is small, and the documents are elsewhere

What this means in practice:

  • A query that doesn't touch the large column never reads it. The main table stays small and dense, and scans of it are fast.
  • SELECT * pays for every large value: a lookup in the TOAST table's index, several chunk reads and a decompression, for each row.
  • Updating other columns doesn't rewrite a TOASTed value. The new row version carries the same pointer.
  • Changing any part of a large value rewrites all of it. Setting one key in a 1 MB jsonb document writes a new megabyte.
🧻
The table that got faster when its text column got bigger

The 2 kB threshold produces a result that surprises nearly everyone who measures it, and the developer Haki Benita published a careful demonstration in 2020. He built three versions of a table that differed only in the length of one text column: short strings, strings of about 1,800 bytes, and strings of about 4,000 bytes. Then he ran a query that never referred to the text column at all, a filter on an integer. On the table with the largest values it was fast. On the one with the medium-sized values it was several times slower. The explanation is on this page. The 4,000-byte values were over the threshold, so they had been moved to the TOAST table, and the main table was left with slim rows packed a hundred or more to a page. The 1,800-byte values were just under the threshold, so they stayed in the row. Four of them filled a page, the table was dozens of times larger, and a sequential scan had to read all of it to look at one integer per row. Columns of a kilobyte or two are common in practice: descriptions, addresses kept as JSON, serialised settings. The remedies are to keep such columns out of tables that are scanned often, by moving them to a side table joined on demand, or to lower the table's toast_tuple_target so that they are moved out sooner. Either way the rows have to be measured first, and most teams never look.

⚠️
Common mistakes
  • Expecting DELETE to return disk space. It marks tuples. VACUUM makes the space reusable inside the table, and only a rewrite gives it back to the operating system.
  • Storing or exposing ctid. It is a physical address and changes on update.
  • Relying on the order of rows in a table. It is the order in which free space happened to be found.
  • Indexing a column that changes on every update, such as updated_at, on a busy table. It turns every update into a full one with index writes.
  • SELECT * on tables with large columns. Every row pays for values the code then ignores.
  • Lowering fillfactor on an append-only table. The reserved space is never used.

Interview drill

Explain it simply: How does a database store rows of different lengths on a fixed-size page?

How a strong answer sounds
With a slotted page. The page has a small header, then an array of fixed-size slots, called line pointers in PostgreSQL, growing forward from the start; the row data is packed from the end of the page growing backward, and the free space is in between. Each slot holds the offset and length of one row. A row's address is the page number plus the slot number, not a byte offset, and that is what indexes store. The indirection is the important part: rows can be variable-length, a row can be removed leaving its slot marked unused, and the page can be compacted, sliding rows together to defragment the free space, without changing any row's address, because only the offsets inside the slots change. A row that is too large for a page is handled separately: in PostgreSQL, large values are compressed and moved to a TOAST table, leaving a pointer in the row.

Deeper: A table holds 10 million rows and occupies 40 GB. You delete 9 million of them, and it still occupies 40 GB and scans are no faster. Why, and what do you do?

How a strong answer sounds
DELETE in PostgreSQL doesn't remove anything physically; it sets xmax on each tuple so that later transactions treat it as gone. The tuples stay on their pages until VACUUM removes them, once no running transaction could still need them. And VACUUM only makes that space reusable within the table: it records it in the free space map for future inserts, and it can truncate empty pages only at the very end of the file. So the file stays 40 GB, and a sequential scan still reads every page, most of them now nearly empty. First I'd check that vacuum has actually been able to run, since a long-running transaction or an abandoned replication slot would hold dead tuples in place. If the space is going to be refilled by new data, I'd leave it: the table will reuse it. If I need it back, the table has to be rewritten. VACUUM FULL does that but takes an exclusive lock for the duration, so on a live system I'd use pg_repack or a similar online tool, or, if I'd known in advance, have partitioned the table so that old data could be removed by dropping a partition, which is instant and returns the space at once.

🧠 Key takeaways

  • A page has line pointers growing from the front and tuples from the back. A row's address is (page, line pointer), so tuples can move within a page.
  • A tuple header records which transactions created and ended that version. Updates write new versions, and deletes only mark.
  • A heap file is unordered. Rows go where there is room, and the file doesn't shrink when rows are removed.
  • Dead tuples take space until VACUUM or pruning removes them and compacts the page.
  • An update that stays on its page and touches no indexed column is a HOT update with no index writes. A lower fillfactor makes room for them.
  • Values that push a row past about 2 kB are compressed and moved to a TOAST table, which keeps the main table small.
