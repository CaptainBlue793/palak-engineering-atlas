Connection Pooling

A PostgreSQL server has sixteen processor cores, and an application wants to open a thousand connections to it. The instinct is to let it, since more connections ought to mean more work done at once. They mean less. Each connection is a whole operating-system process, and a server running a thousand of them on sixteen cores spends its time switching between them and contending for locks, and gets less done than it would with fifty. A connection pool keeps a small number of connections open and shares them among many callers. This chapter covers what a connection costs, the two places a pool can live, what a pooler can and can't share, and how to choose its size.

  • Compare PgBouncer's session and transaction modes, and say what breaks in the second
  • Size a pool from the number of cores, and explain why smaller is usually better

The cost of a connection

PostgreSQL serves each connection with its own operating-system process, started when the client connects and ended when it leaves. That design is simple and robust, and it makes a connection a heavy thing.

CostWhenHow much
Network handshakesOpeningTCP, TLS and authentication: four or more round trips before the first query
Starting a processOpeningA fork, and loading the catalogue information the session will need: a few milliseconds of server processor time
MemoryFor as long as it is openSeveral megabytes for each connection, more once it has run complex queries
ContentionWhile it is activeEvery active process competes for cores, for locks on shared structures, and for the processor's caches

An application that opens a connection for each request pays the opening cost every time, which for a query of one millisecond is most of the request. An application that keeps a connection for each of its threads holds hundreds open, nearly all of them idle. The numbers above are typical: 424 connections, of which 9 are working.

Application pools

A connection pool is a small set of connections, opened once and kept. Code that needs the database borrows one, uses it for a transaction, and returns it. If all are in use, the borrower waits briefly for one to come back.

from psycopg_pool import ConnectionPool

pool = ConnectionPool(
    "host=db dbname=shop user=app",
    min_size=4, max_size=10,       # never more than 10 connections from this process
    timeout=2.0,                    # wait at most 2 s for a free connection, then raise
    max_lifetime=1800,              # replace each connection after 30 minutes
)

def get_order(order_id):
    with pool.connection() as conn:             # borrowed here …
        return conn.execute("SELECT * FROM orders WHERE order_id = %s", (order_id,)).fetchone()
                                                # … committed and returned here

A pool inside the application is the first thing to have, and for one or two application servers it is all that is needed. It stops being enough as the number of servers grows, because each process has a pool of its own and none of them knows about the others. Fifty containers with a pool of twenty each can open a thousand connections, and when an autoscaler doubles the containers during a traffic spike, the database is asked for two thousand at the moment it is busiest.

PgBouncer: session vs transaction

The answer is a second pool, outside the application and shared by all of it. PgBouncer is a small proxy that speaks PostgreSQL's protocol. Thousands of clients connect to it, which is cheap, since for PgBouncer a client is a few kilobytes of memory. It holds a few dozen real connections to the database and hands them out. The question is for how long a client keeps one.

Pool modeA client holds a server connectionSharingWhat stops working
SessionFrom connecting until disconnectingLittle. It only saves the cost of openingNothing
TransactionFrom BEGIN to COMMITGreat. A thousand mostly idle clients fit on twenty connectionsAnything that must outlive a transaction on the same connection
StatementFor one statementGreatestTransactions of more than one statement

Transaction mode is the one worth having, and the last column is its price. Consecutive transactions from one client may run on different server connections, so state that belongs to a session can't be relied on:

FeatureUnder transaction poolingDo this instead
SET for the session: search_path, statement_timeoutApplies to whichever connection ran it, and leaks to the next clientSET LOCAL inside the transaction, or set it for the role
Prepared statementsPrepared on one connection and executed on another, which doesn't know themA recent PgBouncer that tracks them, or disable them in the driver
Advisory locks held for the sessionTaken on one connection and never released by youTransaction-level advisory locks
LISTEN / NOTIFY, temporary tables, cursors held openTied to a connection you no longer haveA separate, direct connection for the code that needs them

Pool sizing

How many real connections should the pool hold? Far fewer than most people guess. A query makes progress only while it has a core, or is waiting for a disk. Connections beyond what the cores and disks can serve add no throughput. They add processes for the scheduler to rotate through, more parties contending for every lock inside the database, and more memory. A widely used starting point, from PostgreSQL's own documentation and the HikariCP project, is:

connections  ≈  (cores × 2)  +  number of independent disks

# 16 cores on SSD storage  →  about 33 connections, for the whole database, from all clients together

The factor of two allows for the time a query spends waiting for I/O, during which another can use its core. What the formula implies matters more than its exact value: the right number is tens, on a machine that will happily accept thousands.

The model: up to 16 queries can make progress at once, two for each core. With more than that active, each takes proportionally longer, and every extra active connection adds 0.4% of overhead through context switches and contention. When demand is within what the server can do, only as many connections are active as the work needs, whatever the limit.

Things to notice. In a quiet hour the pool size hardly matters: 500 queries a second keep four connections busy, and a limit of a thousand is as good as a limit of sixteen. The sizes differ under load. At 3,000 a second, more than the machine can do, a pool of 16 keeps the database at its peak of 2,000 and makes the excess wait in the pool. A pool of 256 lets all 256 run at once, and the database manages 1,020, about half. With no pool and a thousand connections it manages 405, a fifth of what it could do, during the spike when it is needed most. Each query also spends longer inside the database, 2.5 seconds against 8 ms, so locks are held longer and everything behind them is slower as well. A pool of 4 errs the other way: the machine is never stressed and is limited to 500 a second with cores sitting idle. The pool should be sized to the machine, and when more work arrives than the machine can do, the excess should wait in front of the database.

🎱
The demonstration that made smaller pools respectable

The advice in this chapter runs against intuition, and for a long time it was ignored. What changed many minds was a recorded demonstration by Oracle's Real-World Performance group, which the authors of HikariCP, a widely used Java connection pool, wrote up and put at the centre of their guidance on pool sizing. The test had a web application simulating 9,600 concurrent users against a single database server. With the connection pool set to 2,048, which the application's developers had considered generous, requests waited about 33 ms in the pool's queue and then took about 77 ms in the database, and the database's own wait statistics were dominated by contention for internal locks and for processor time. The presenters changed nothing except the pool size. At 1,024 connections the figures barely moved. At 96 connections, on the same hardware with the same load, the queue wait fell to about 1 ms and the time in the database to about 2 ms. Response time had improved by a factor of around fifty, and throughput had risen, by removing nineteen out of every twenty connections. The requests were still queuing. They now queued in the pool, where waiting uses no resources, and no longer inside the database, where 2,048 processes had been competing for a few dozen cores. The HikariCP authors' summary was that most people want a small pool, saturated with threads waiting for connections.

⚠️
Common mistakes
  • Raising max_connections to cure "too many clients". It moves the queue into the database, where it does the most harm.
  • Adding up nothing. Pool size × processes × servers is the real number, and it changes whenever the application scales.
  • Transaction pooling with session state. A SET on one transaction's connection turns up in a stranger's.
  • Holding a pooled connection across slow work: an HTTP call, a sleep, a user's think time. The pool empties while the database is idle.
  • No checkout timeout. When the pool is exhausted, callers wait for ever, where a clear error would have shed load.
  • A connection opened for each invocation of a serverless function. A burst of invocations is a burst of handshakes. Put a pooler in between.

Interview drill

Explain it simply: Why use a connection pool, and where does it go?

How a strong answer sounds
Because database connections are expensive and should be reused. Opening one costs a TCP and TLS handshake, authentication and, in PostgreSQL, a new server process; keeping one costs several megabytes and adds to contention when it is active. Without a pool, an application either pays that setup on every request or holds one connection per thread, most of them idle. A pool keeps a bounded set of connections open; code borrows one for the duration of a transaction and returns it, and callers wait when all are busy. It gives three things: no per-request setup cost, a hard cap on the load placed on the database, and a queue in a cheap place. There are two layers. An in-process pool in each application instance handles reuse. But each instance has its own, so with many instances the total can exceed what the database should take; then you add an external pooler such as PgBouncer between the applications and the database, which multiplexes thousands of client connections onto a few tens of server connections, usually in transaction mode.

Deeper: Your service gets "too many clients already" from PostgreSQL during traffic peaks. What do you do?

How a strong answer sounds
First, I wouldn't raise max_connections as the fix; that lets more backends compete for the same cores and usually lowers throughput. I'd find out where the connections come from: group pg_stat_activity by application, user and state. Typically most are idle: many application instances each holding a pool, with the total, instances times processes times pool size, growing as the autoscaler adds instances during the peak. So the first fix is arithmetic: decide the number of server connections the database should run, roughly twice its cores, and make the sum of all pools fit under it. With more than a handful of instances that can't be done with in-process pools alone, so I'd put PgBouncer in transaction mode in front, with a default pool size near that target, and let the applications connect to it freely. I'd check the application for things that break under transaction pooling, session-level SETs, session advisory locks, LISTEN, and for anything that holds a connection for a long time: transactions left open across external calls, which show as "idle in transaction", and long-running queries. I'd set a checkout timeout so that when the pool is exhausted, requests fail fast with a clear error and the service sheds load instead of hanging. Then I'd watch pool wait time and active server connections: if requests queue in the pool while the database has idle capacity, the pool is too small; if the database is saturated, the answer is query tuning or more capacity, not more connections.

🧠 Key takeaways

  • A PostgreSQL connection is a process. It costs handshakes and a fork to open, memory to keep, and contention when active.
  • An application pool reuses connections and caps them, for one process. Many processes need a shared pooler in front of the database.
  • PgBouncer in transaction mode lends a server connection for one transaction at a time, so thousands of clients fit on tens of connections.
  • Transaction pooling breaks session state: session SETs, session advisory locks, LISTEN and temporary tables.
  • The right pool size is about twice the number of cores. More connections lower throughput under load.
  • When demand exceeds capacity, let requests queue in the pool with a timeout, where waiting is free.

Check your understanding

Why is a PostgreSQL connection expensive compared with, say, an HTTP connection to a web server?

A process for each connection is robust and heavy. A few hundred of them are a real burden on the server.

Forty application containers each have a pool with a maximum of 25 connections. What is the most the database may be asked to hold?

Each pool is independent, so the limits multiply. An external pooler is the way to share one limit.

In PgBouncer's transaction mode, when is a server connection given back for other clients to use?

Between transactions the client holds no server connection, which is where the sharing comes from.

An application runs SET search_path = tenant_42 once after connecting, through PgBouncer in transaction mode. What happens?

Session state belongs to a server connection, and the client no longer has one of its own. Use SET LOCAL inside each transaction.

A database with 16 cores is overloaded, with 800 active connections. What is the likely effect of capping it at 40 with a pooler?

Only a few dozen queries can make progress at once. The rest were costing context switches and contention.
