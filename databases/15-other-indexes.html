Hash, GIN, GiST & Bitmap Indexes

A B-tree keeps values in one order and answers questions about that order: equal to, less than, between. A good many useful questions aren't about order. Does this array contain that tag? Does this JSON document have that key? Do these two date ranges overlap? Which ten shops are nearest to this point? Which rows mention this word? A B-tree can answer none of them, and PostgreSQL has a different index for each. This chapter covers the four you will meet, hash, GIN, GiST and BRIN, the kind of question each answers and what each costs to maintain, and then the bitmap scan, which is how PostgreSQL uses most of them and combines several at once.

The way to choose is to look at the operator in the WHERE clause. Each index type supports a fixed list of operators, and the planner will only consider an index for an operator on that list.

Hash indexes

A hash index applies a hash function to the key, and stores the 4-byte result with the row's address in the bucket that the hash selects. A lookup hashes the value, goes to one bucket, and checks the rows there. It can only answer equality, since hashing destroys order.

CREATE INDEX pages_url_hash ON pages USING hash (url);
SELECT page_id FROM pages WHERE url = 'https://example.com/a/very/long/path?with=parameters';

It rarely beats a B-tree, which finds an exact key in three or four cached page reads and can do everything else as well. The one real case is equality on long values such as URLs: a B-tree stores every key in full, and the hash index stores four bytes whatever the length, so it can be several times smaller. It can't enforce uniqueness, can't cover more than one column, and can't return rows in order. Don't confuse it with a hash join (Chapter 18), which builds a temporary hash table in memory and needs no index.

GIN for arrays, JSONB and text

A row in a B-tree has one key. A row with an array of five tags has five things you might search by, and so does a document with five words. A GIN index, a generalised inverted index, is built for values made of many elements. It turns the table inside out: it has one entry for each distinct element, and with it the list of all rows that contain that element, called a posting list.

-- articles(article_id, tags text[], meta jsonb, body text)
CREATE INDEX articles_tags_gin ON articles USING gin (tags);
CREATE INDEX articles_meta_gin ON articles USING gin (meta jsonb_path_ops);
CREATE INDEX articles_body_fts ON articles USING gin (to_tsvector('english', body));

SELECT article_id FROM articles WHERE tags @> ARRAY['postgres', 'indexing'];            -- has both tags
SELECT article_id FROM articles WHERE meta @> '{"status": "published"}';              -- JSON containment
SELECT article_id FROM articles WHERE to_tsvector('english', body) @@ to_tsquery('b-tree & split');

-- inside the index, roughly:
--   'indexing'  → rows 3, 17, 42, 108, …
--   'postgres'  → rows 3, 9, 42, 77, 108, …       tags @> both: intersect the two lists → 3, 42, 108

The distinct elements are themselves kept in a B-tree, so finding an element is fast, and a query for several elements intersects their lists. With the pg_trgm extension the same structure indexes every three-letter sequence in a string, which is what makes LIKE '%needle%' searchable. Chapter 31 takes inverted indexes further.

The weakness is writes. Inserting one article with 300 distinct words means 300 separate updates to the index. To soften that, GIN collects new entries in an unsorted pending list and merges them into the main structure in bulk, which makes inserts quick, and makes every search scan the pending list as well, and occasionally makes one unlucky insert wait while the list is merged.

GiST for ranges and geometry

Some values have no single position on a line: a rectangle on a map, a booking from Tuesday to Friday. Two of them can overlap, or one can contain the other, and neither is simply "less than" the other. A GiST index, a generalised search tree, is a balanced tree like a B-tree, in which each entry in an internal page is a bounding region that encloses everything beneath it: a rectangle enclosing smaller rectangles, or a range covering shorter ranges. A search descends into every child whose region could contain a match. Since regions may overlap, that can be more than one child.

-- No two bookings of the same room may overlap in time (Chapter 8)
ALTER TABLE bookings ADD CONSTRAINT no_double_booking
  EXCLUDE USING gist (room_id WITH =, during WITH &&);

-- Which bookings overlap next weekend?
SELECT * FROM bookings WHERE during && tstzrange('2026-10-17', '2026-10-19');

-- The ten shops nearest a point: the index returns rows in order of distance
CREATE INDEX shops_location_gist ON shops USING gist (location);
SELECT name FROM shops ORDER BY location <-> point(-0.1276, 51.5072) LIMIT 10;

GiST is the index behind exclusion constraints, range types, the geographic types of PostGIS, and nearest-neighbour queries, which no other index here can do. It can also index full text, and there it is smaller and quicker to update than GIN and slower to search.

BRIN

A BRIN index, a block range index, hardly stores anything. It divides the table into runs of consecutive pages, 128 pages by default, which is 1 MB, and for each run it records the smallest and largest value of the column. To answer WHERE created_at >= '2026-10-01', it looks through those summaries and skips every run whose largest value is too small. For the runs that remain, it reads all their pages and checks every row.

Whether that helps depends entirely on whether the table's physical order follows the column. In a table of events that are inserted as they happen, each megabyte covers a short stretch of time, and a query for one day touches very few runs. If the rows are in no particular order, every run contains nearly every date, no run can be skipped, and the index does nothing.

Things to notice. With the rows in order, one day's query reads one block range, 128 pages, of which the day itself is a fifth. The B-tree reads fewer pages, 35, because it goes straight to the rows. The B-tree is also 837 pages and the BRIN index is one. On a table a thousand times this size that is 6.5 GB of index to keep in memory and update on every insert, against 8 MB. With some late arrivals, a few recent ranges have summaries stretching far back in time, and every query has to read them for nothing: one day's query now reads six times as much. With the rows in no order, every summary covers almost the whole 120 days and the BRIN index reads the entire table. The B-tree still works there, at a price: the matching rows are scattered, so it reads over 1,700 pages to fetch one day.

Bitmap scans

An ordinary index scan fetches each row as it finds its address, hopping about the table. When an index matches thousands of rows, or when two indexes should be used together, PostgreSQL does something better.

EXPLAIN SELECT * FROM orders WHERE status = 'refunded' AND country = 'IN';

 Bitmap Heap Scan on orders
   Recheck Cond: ((status = 'refunded') AND (country = 'IN'))
   ->  BitmapAnd
         ->  Bitmap Index Scan on orders_status_idx     -- 2% of the rows
         ->  Bitmap Index Scan on orders_country_idx    -- 9% of the rows: together, 0.2%

Three facts are worth remembering. GIN and BRIN indexes are only ever used through bitmap scans, because they don't return rows one at a time in a useful order. If the bitmap grows beyond work_mem, it becomes lossy: it remembers whole pages and no longer individual rows, and the recheck then tests every row on those pages. And a bitmap scan returns rows in table order, so the index's ordering is lost, and an ORDER BY needs a separate sort.

A bitmap index is a different thing, and PostgreSQL doesn't have one. In Oracle and in analytical databases it is an index stored on disk as one bitmap for each distinct value of a column, with one bit for each row. It suits columns with a handful of values in tables that are rarely updated, and it reappears in Chapter 28.

⏳
The insert that waited for everyone else's index work

GIN's pending list makes a trade that goes unnoticed until a table is large and busy, and engineers at GitLab have described running into it. GitLab lets users search the titles and descriptions of issues and merge requests for any substring, and it does so with trigram GIN indexes on those text columns. Descriptions are long, so each one yields hundreds of trigrams, and without the pending list every edit would mean hundreds of index updates. With it, an edit appends to the list and returns. The list has a size limit, though, and when a write pushes it past the limit, that write has to merge the entire list into the index before it can finish. On tables with heavy traffic, this showed up as ordinary updates that normally took milliseconds occasionally taking seconds, long enough to hit statement timeouts, for no reason connected to the statement itself. Whichever session filled the list did the merging for all the others. The fixes available are all compromises. The pending list can be turned off for an index with fastupdate = off, which makes every write slower by a predictable amount and removes the stalls. The limit can be lowered, so that merges are smaller and more frequent. Or autovacuum can be made to run often enough to empty the list in the background before any foreground write has to. An index that defers its work still has to do it, and it is worth knowing which session will end up doing it.

⚠️
Common mistakes
  • A B-tree on a jsonb or array column, expecting containment queries to use it. It indexes the whole value for equality only. Use GIN.
  • A GIN index on a table with heavy writes, unmeasured. Check insert latency, and its tail, before and after.
  • BRIN on a column that isn't correlated with the table's physical order. It will be chosen, and it will read everything. Check pg_stats.correlation.
  • Using a hash index "because lookups are O(1)". A B-tree's three cached page reads are just as fast in practice, and it does ranges and ordering too.
  • One index for each column, hoping for BitmapAnd. A composite B-tree on the columns queried together is usually far better (Chapter 9).
  • A low work_mem with large bitmap scans. The bitmap turns lossy and the recheck does the work the index was meant to save.

Interview drill

Explain it simply: You have a jsonb column and need to find rows where it contains a given key and value. What index do you create, and how does it work?

How a strong answer sounds
A GIN index on the column, queried with the containment operator @>. A B-tree wouldn't help: it would index the document as one opaque value and support only whole-value equality. GIN is an inverted index: it breaks each document into its elements, the keys and values, or hashes of whole paths with the jsonb_path_ops operator class, and stores, for each distinct element, a posting list of the rows containing it. A containment query looks up the elements of the search document and intersects their posting lists, then rechecks the candidate rows. I'd use jsonb_path_ops if I only need @>, since it is smaller and faster, and the default class if I also need key-existence operators. The trade-off is write cost: each row contributes many index entries, so inserts and updates are slower and the index is large. And if I always query one specific key, an ordinary B-tree on the expression (meta->>'status') is smaller and cheaper than a GIN index on everything.

Deeper: A 2 TB table of events is queried mostly by time range. Compare a B-tree and a BRIN index on the timestamp.

How a strong answer sounds
A B-tree on the timestamp has one entry per row, so for tens of billions of rows it is hundreds of gigabytes, has to be maintained on every insert, and competes with the data for memory. It gives exact results: one descent and a walk along the leaves, reading precisely the matching rows. A BRIN index stores only the minimum and maximum timestamp per block range, 1 MB of table by default, so for 2 TB it is a few megabytes, costs almost nothing to maintain, and is always in memory. A range query scans the summaries, skips the block ranges that can't match, and reads the rest in full with a recheck, so it reads somewhat more than strictly necessary at the edges. That works only because an append-only events table is physically ordered by time: the correlation between the column and the row position is near 1. If rows arrive out of order, are updated so that new versions land elsewhere, or the table is loaded in a different order, the block ranges' min–max intervals widen and overlap, and BRIN degrades towards a full scan. So for append-only, time-ordered data queried by ranges covering many rows, BRIN is the better choice, usually combined with partitioning by time; for point lookups of individual events, or if the ordering can't be guaranteed, I'd pay for the B-tree, perhaps only on recent partitions.

🧠 Key takeaways

  • Choose an index by the operator: order and equality need a B-tree, containment needs GIN, overlap and nearest need GiST.
  • A hash index answers equality only, and is worth it only for long keys.
  • GIN maps each element to the rows that contain it. It is fast to search and costly to update, and its pending list postpones that cost.
  • GiST is a tree of bounding regions, used for ranges, geometry, exclusion constraints and nearest-neighbour ordering.
  • BRIN stores a minimum and maximum for each megabyte of table. It is tiny, and works only when the table is physically in the column's order.
  • A bitmap scan gathers row addresses first, combines indexes with AND and OR, then reads the table pages in order and rechecks.

Check your understanding

Which index supports WHERE tags @> ARRAY['sale', 'new'] on a text[] column?

GIN indexes each array element with the rows that contain it, and intersects the lists for 'sale' and 'new'.

Why is inserting into a table with a full-text GIN index slower than into one with a B-tree?

The pending list defers this work and does not remove it.

A BRIN index on created_at performs very well on one events table and uselessly on another of the same size. What is the likely difference?

BRIN can only skip a block range whose minimum and maximum exclude the value being sought.

Which index can return "the ten rows nearest to this point", already in order of distance?

GiST supports ordering by the distance operator. A B-tree on two coordinates is sorted by x first, which says little about distance.

In a plan, what does BitmapAnd over two Bitmap Index Scans do?

Each index produces a bitmap. The AND of the two is then used for one ordered pass over the table.
