The Buffer Pool

A database is much larger than the memory of the machine it runs on, and reading a page from disk takes a thousand times longer than reading it from memory. So every database keeps a set of pages in RAM and tries to make sure that the next page a query asks for is already there. That set is the buffer pool. Every read and every write of table and index data goes through it. Which pages it holds, which one it gives up when it needs room, and when a changed page is written back to disk decide whether a query takes a millisecond or a second. This chapter covers how the pool works, the eviction policies and their weaknesses, and how to size it.

Why a buffer pool

The buffer pool is an array of frames in shared memory, each the size of one page, 8 KB. Beside it are a hash table that maps "page 412 of table orders" to the frame holding it, and a small descriptor for each frame. In PostgreSQL the pool's size is the setting shared_buffers, and all the server's processes share the one pool.

No part of the database reads a table file directly. The executor, the index code and VACUUM all ask the buffer manager for a page by its identity, and get back a frame. If the page is in the pool, that is a hit and costs a hash lookup. If it isn't, it is a miss: the buffer manager must find a frame to put it in, which usually means removing another page, and then read it from the file.

A pin is a promise that the page will stay where it is while it is being read. A query pins a page, looks at the tuples it wants, and unpins it, usually within microseconds. A page that is always pinned by somebody can never be evicted, which is one reason why a cursor left open in the middle of a scan is a bad idea.

A dirty page is one that has been changed in memory. The change is already safe, because it was recorded in the WAL before COMMIT returned (Chapter 10), so there is no hurry to write the page itself. That delay is deliberate: a page that is updated a hundred times in a minute is written once. Three processes do the writing:

WriterWhenWhy
CheckpointerEvery few minutes, or after a set amount of WALWrites every dirty page, so that crash recovery need only replay the WAL from that point (Chapter 20)
Background writerContinuously, a little at a timeWrites dirty pages that are likely to be evicted soon, so that clean frames are ready
A backend, in the middle of a queryWhen it needs a frame and the victim is dirtyNobody else had written it. The query waits for the write, so this is the case to avoid

Eviction: LRU and clock sweep

When the pool is full and a page is needed, one has to go. The best page to evict is the one that won't be wanted for the longest time, which nobody can know, so every policy guesses from the past.

PolicyEvictsGoodWeakness
FIFOThe page that was loaded longest agoTrivialIgnores use altogether: the most popular page is evicted when its turn comes
LRUThe page that was used longest agoFollows recency, which predicts wellEvery access must move the page to the head of a shared list, under a lock. And one large scan pushes out everything
Clock sweep (PostgreSQL)The first page a rotating hand finds with a usage count of 0An access only adds one to a counter. Frequently used pages survive several sweepsApproximate. With a pool full of high counts, the hand may go round several times
LRU with a midpoint (InnoDB)From the tail of a list that new pages join five-eighths of the way downA page read once by a scan never reaches the protected partMore to tune

PostgreSQL's clock sweep works like this. Each access to a page adds 1 to its usage count, up to 5. When a frame is needed, a hand moves round the frames in a circle. At each one that isn't pinned, it looks at the count. If the count is above zero it subtracts 1 and moves on. If the count is zero, that frame is the victim. A page used once is evicted on the hand's next visit, and a page used constantly needs five full sweeps without a single access.

A large sequential scan is the standard test of a policy. It touches a great many pages once each, and they are precisely the pages that should not displace the working set. PostgreSQL has a second defence as well: a scan of a table larger than a quarter of shared_buffers uses a small private ring of buffers, 256 kB, and recycles them, so it passes through the pool without disturbing it. VACUUM and bulk loads do the same.

Things to notice. With 8 frames, FIFO evicts the hot pages as soon as their turn comes, however often they are used: it ends with 24 hits out of 46, evicts a hot page six times, and makes a query stop to write page 2 while it is dirty. LRU does better, 28 hits, because the hot pages that were read during the scan had been used recently. Once the scan runs for six pages without touching them, LRU gives up pages 3 and 4 as well. Clock sweep ends with 30 hits and loses no hot page. Their usage counts stood at 5 when the scan began, the scan's pages came in with 1, and the hand took the scan's own pages every time. With 16 frames there is room for everything, nothing is evicted, and all three policies give the same 30 hits. The random workload shows the limit of any policy: with no pattern to exploit, the three finish within a hit or two of each other, and only a larger pool helps.

shared_buffers and the OS cache

PostgreSQL reads and writes its files through the operating system, which has a cache of its own (P3). A page evicted from the buffer pool is very often still in the OS page cache, and a "read" of it costs a system call and a copy, a few microseconds, and no disk access. This shapes the advice on sizing:

SettingUsual valueReasoning
shared_buffersAbout 25% of RAMLarge enough for the hot working set. The rest of memory serves as the OS cache, and for sorts and connections
effective_cache_size50 to 75% of RAMIt allocates nothing. It tells the planner how much is probably cached in total, which makes index scans look cheaper
InnoDB's innodb_buffer_pool_size70 to 80% of RAMA different design: InnoDB bypasses the OS cache with direct I/O, so its own pool is the only cache
 
-- What is in the pool right now, by table and index
CREATE EXTENSION pg_buffercache;
SELECT c.relname, count(*) AS buffers, pg_size_pretty(count(*) * 8192) AS cached,
       round(100.0 * count(*) * 8192 / pg_relation_size(c.oid)) AS pct_of_relation
FROM pg_buffercache b JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
GROUP BY c.oid, c.relname ORDER BY buffers DESC LIMIT 3;
--  relname          | buffers | cached  | pct_of_relation
--  orders_pkey      |  412877 | 3226 MB |             100
--  orders           |  391204 | 3056 MB |              11     only the recent tenth of the table is hot
--  order_items_pkey |  166310 | 1299 MB |              64

-- How often a page was found in the pool
SELECT round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct
FROM pg_stat_database WHERE datname = current_database();        -- 99.31

A transactional workload should show a hit rate in the high nineties. Two cautions apply. A "read" in these statistics means "not in shared_buffers", and the page may well have come from the OS cache without touching the disk. And an average of 99% can hide one query that misses on every page. EXPLAIN (ANALYZE, BUFFERS) gives the figures for a single query (Chapter 17).

The server that was slow for an hour after every restart

A buffer pool holds nothing when the server starts. On a small database nobody notices. On a server with a hundred gigabytes of pool, it meant that after any restart, whether for an upgrade, a crash or a failover to a replica, every query missed, and the database ran at disk speed until ordinary traffic had happened to pull the working set back into memory. That could take an hour or more, during which a system that normally answered in a millisecond answered in tens, and connections piled up behind it. Operators of large MySQL installations at companies such as Facebook found that the warm-up was often the longest part of a maintenance window, and that a replica promoted after a failure was least able to cope at the moment it was needed. The fix they built, which MySQL adopted in version 5.6 in 2013, is simple. At shutdown, and periodically while running, the server writes out the list of which pages are in the pool. This is only the identifiers, a few megabytes. At start-up a background thread reads that list and loads those pages, in an order that suits the disk. PostgreSQL gained the same thing in version 11 as pg_prewarm's autoprewarm worker. A cache is part of a system's capacity, and a restart or failover plan that assumes a warm cache will fall short until the cache has been rebuilt.

⚠️
Common mistakes
  • Leaving shared_buffers at its default of 128 MB on a server with 64 GB of memory.
  • Giving PostgreSQL 80% of RAM as shared_buffers, as one would InnoDB. It leaves too little for the OS cache, sorts and connections.
  • Treating effective_cache_size as an allocation. It is a hint to the planner and reserves nothing.
  • Benchmarking with a warm cache and promising those figures for the first minutes after a restart or failover.
  • Reading a 99% hit rate as proof of health. On a busy server, 1% of a million page requests a second is 10,000 reads a second.
  • Leaving transactions or cursors open. The pages they hold pinned can't be evicted or cleaned up.

Interview drill

Explain it simply: What is a buffer pool, and why does a database have its own when the operating system already caches files?

How a strong answer sounds
The buffer pool is the database's in-memory cache of disk pages: a fixed array of page-sized frames, a hash table from page identity to frame, and per-frame metadata. All reads and writes of table and index data go through it. A database keeps its own cache, instead of relying on the OS page cache, because it needs control the OS can't give. It must enforce write ordering: a dirty page may not reach disk before the WAL records describing its changes, which requires knowing exactly when each page is written. It needs pinning, so that a page stays put while a query is reading it, and its own locks on page contents. It knows things about access patterns that the OS doesn't, such as that a sequential scan's pages shouldn't displace the working set. And a hit in its own pool avoids a system call and a copy. Some systems, like InnoDB, go further and bypass the OS cache with direct I/O; PostgreSQL uses both layers, which is why its buffer pool is typically sized at about a quarter of memory.

Deeper: Why don't databases use a plain LRU list for eviction, and what do they use instead?

How a strong answer sounds
Two reasons. First, cost and contention: strict LRU means every page access, even a read, moves that page to the head of a shared list, which requires an exclusive lock on the list. With hundreds of concurrent queries touching thousands of pages a second each, that lock becomes the bottleneck. Second, behaviour: LRU looks only at recency, so a single large table scan, or a backup, touches every page once and makes them all "most recently used", flushing the real working set from memory; afterwards the workload runs from disk until it has warmed up again. So databases approximate LRU with something cheaper and frequency-aware. PostgreSQL uses a clock sweep: each access just increments a small usage counter capped at 5, with no list manipulation, and a hand sweeping the frames decrements counters and evicts the first unpinned frame at zero, so frequently used pages survive several sweeps while a page touched once goes quickly; large scans additionally use a small ring of buffers so that they bypass the main pool. InnoDB keeps an LRU list but inserts newly read pages at a midpoint, into an "old" sublist, and promotes a page to the "young" part only if it is accessed again after a delay, which stops scans and read-ahead from polluting the hot part. Research policies such as LRU-K, 2Q and ARC address the same two problems.

🧠 Key takeaways

  • The buffer pool is a shared array of page-sized frames. Every read and write of data goes through it.
  • A pinned frame can't be evicted. A dirty frame must be written before it is reused, after its WAL.
  • Dirty pages are written by the checkpointer and the background writer, and by a waiting query only when those fall behind.
  • Plain LRU is costly under concurrency and is flushed by one large scan. Clock sweep with usage counts is cheap and protects pages that are used often.
  • PostgreSQL also relies on the OS cache, so shared_buffers is about a quarter of RAM. InnoDB bypasses the OS and takes most of it.
  • A pool is empty after a restart, and performance is poor until it has been warmed.

Check your understanding

A frame has a pin count of 2. What does that mean for eviction?

A pin promises that the page stays in its frame while someone is reading or changing it.

A transaction updates a row and commits. When is the changed table page written to its file?

The WAL makes the change durable. The page stays dirty in memory and may absorb many more changes before it is written once.

Under plain LRU, what does one scan of a very large table do to the buffer pool?

Recency alone can't tell a page read once from a page read a thousand times.

In PostgreSQL's clock sweep, the hand reaches an unpinned frame with a usage count of 3. What happens?

Only a frame found at 0 is evicted. Pages used often are passed over several times.

Why is shared_buffers usually about 25% of RAM for PostgreSQL, and not 80%?

Pages that leave the pool are often still in the OS cache. InnoDB, which bypasses that cache, is the one that takes 70 to 80%.
