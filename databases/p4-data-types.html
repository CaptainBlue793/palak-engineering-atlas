Data Types

A column's type is a promise about every value it will ever hold, and the database keeps it for you. Choose well and bad data can't get in, comparisons and sorting just work, and rows stay small. Choose badly and the failures are quiet: money that's off by a fraction of a cent, a counter that stops at 2,147,483,647, timestamps that are an hour wrong for half the year. This chapter covers the handful of PostgreSQL types that cover almost every column, and the specific way each wrong choice breaks.

  • Pick between integer, bigint, numeric and floating point, and store money correctly
  • Know that text and varchar(n) perform the same in PostgreSQL, and when a length limit is still worth it
  • Explain timestamp vs timestamptz and why the second is almost always right
  • Choose between json and jsonb
  • Estimate a row's size from its column types

Numbers: integers, numeric and floating point

TypeBytesRange or precisionUse it for
smallint2±32,767Rarely worth it; alignment often eats the saving
integer4±2,147,483,647 (about 2.1 billion)Quantities, small counters, enums stored as numbers
bigint8±9.2 × 1018Primary keys, IDs, money in cents, anything that grows
numeric(p, s)variable (~2 bytes per 4 digits + header)Exact decimal, up to 131,072 digits before the pointMoney, rates and anything a human checks to the last digit
double precision8~15 significant digits, binary fractionMeasurements, scientific values, ML features
real4~6 significant digitsAlmost never

The floating-point types store binary fractions, and most decimal fractions (0.1, 0.2, 19.99) have no exact binary form. Each value is off by a tiny amount, and sums of many values drift: add 0.1 ten times in double precision and PostgreSQL returns 0.9999999999999999. That's fine for a temperature and unacceptable for an invoice. Store money as numeric(12,2), or as a bigint count of the smallest unit (cents), which is exact and faster to sum:

SELECT sum(0.1::float8)  FROM generate_series(1, 10);   -- 0.9999999999999999
SELECT sum(0.1::numeric) FROM generate_series(1, 10);   -- 1.0

SELECT 2147483647::integer + 1;
-- ERROR:  integer out of range

The integer limit is the one that bites in production, because it arrives years after the schema was written. An integer primary key on a table that gains 1,000 rows a minute runs out in about four years. Use bigint for IDs from the start: four extra bytes per row is cheap; changing the type of a primary key on a billion-row table, and every foreign key that references it, is not (Chapter 34).

Text: text, varchar(n), char(n)

In PostgreSQL, text, varchar(n) and varchar are stored identically and perform identically; the documentation says so explicitly. varchar(n) just adds a length check. char(n) pads values with spaces to exactly n characters, which wastes space and causes comparison surprises; avoid it. (In MySQL and SQL Server the choice does matter for storage and indexing, which is where the varchar(255) habit comes from.)

CREATE TABLE users (
    user_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email        text   NOT NULL,
    display_name text   NOT NULL CHECK (char_length(display_name) BETWEEN 1 AND 80),
    country      text   NOT NULL CHECK (country ~ '^[A-Z]{2}$')     -- ISO 3166 alpha-2
);

INSERT INTO users (email, display_name, country)
VALUES ('a@example.com', repeat('x', 300), 'GB');
-- ERROR:  new row for relation "users" violates check constraint "users_display_name_check"

Use text plus a CHECK constraint when a limit is a real business rule (a display name shown in an 80-character slot); the constraint can be changed later without rewriting the table, and it can express more than a length. Lengths count characters, not bytes: char_length('naïve 🙂') is 7, while octet_length is 11 in UTF-8.

Time: timestamp vs timestamptz

This is the type choice with the worst failure mode, because it's wrong only some of the time.

  • timestamp (without time zone) stores a wall-clock reading, "1 July 2026, 09:00", with no zone. Nothing records whose 09:00 it was.
  • timestamptz (with time zone) stores an instant: on input PostgreSQL converts the value to UTC using the zone given, or the session's TimeZone setting; on output it converts back to the reader's session zone. Despite the name it doesn't store a zone, just the instant, in the same 8 bytes.

Use timestamptz for anything that happened or will happen at a moment: created, paid, shipped, expires. Use date for calendar dates with no time (a birthday, an invoice date). Plain timestamp is right only for a wall-clock time that must stay fixed regardless of zone, such as "the shop opens at 09:00 local time", and even then you usually want the zone name stored next to it.

json vs jsonb

Both store JSON documents and both validate the input. json keeps the exact text you sent: whitespace, key order, duplicate keys. jsonb parses it into a binary structure: whitespace is dropped, keys are reordered, and for duplicate keys only the last value is kept. Parsing costs a little on insert and pays back on every read: jsonb supports indexing (GIN indexes, Chapter 15), containment queries with @>, and fast field access. Use jsonb unless you have to preserve the original text byte for byte, such as storing a signed webhook payload to verify later.

SELECT '{"name": "kbd",  "id": 7, "id": 8}'::json;    -- {"name": "kbd",  "id": 7, "id": 8}
SELECT '{"name": "kbd",  "id": 7, "id": 8}'::jsonb;   -- {"id": 8, "name": "kbd"}

SELECT order_id FROM orders WHERE attributes @> '{"gift": true}';   -- can use a GIN index

A JSON column is the right tool for data whose shape genuinely varies (product attributes that differ per category, third-party payloads). It's the wrong tool for fields you filter, join or constrain on every day; those deserve real columns with real types, where the database can check them. P5 shows how to load JSON documents in bulk.

When a 32-bit ID runs out
In November 2018 Basecamp spent several hours in read-only mode because the ID column of a busy events table was a 32-bit integer and reached its maximum, 2,147,483,647. No new rows could be inserted, so any action that recorded an event failed. The fix, widening the column to a 64-bit integer, needs a rewrite of a very large table, which is exactly the job nobody wants to do under pressure. The lesson people took away is cheap to apply: bigint for every surrogate key from day one, and a monitoring query that warns when any sequence passes, say, 50% of its column's range.

Common mistakes

    
    
      
  • Money in float/double precision. Totals drift by fractions of a cent. Use numeric or integer cents.
    • 
      
  • integer primary keys on tables that grow. 2.1 billion arrives sooner than you'd think. Use bigint.
    • 
      
  • timestamp for instants. Correct in one zone, wrong by an hour twice a year everywhere else. Use timestamptz.
    • 
      
  • Numbers or dates stored as text. '10' < '9' is true as text, and nothing stops '2026-02-30'.
    • 
      
  • Everything in one jsonb blob. You lose types, constraints, foreign keys and good statistics for the planner.

Interview drill

    
Explain it simply: How would you store prices and order totals, and why not a float?

    
How a strong answer sounds
Floats are binary fractions, so values like 0.1 or 19.99 can't be represented exactly, and sums drift: ten lots of 0.1 come back as 0.9999999999999999. For money I'd use numeric(12,2), which is exact decimal arithmetic, or a bigint of minor units (cents), which is exact and faster to aggregate, with the currency in its own column because not every currency has two decimal places. I'd also round explicitly at the points the business defines, such as per line or per invoice, rather than leaving it to chance.

    
Deeper: What's the difference between timestamp and timestamptz in PostgreSQL, and what does timestamptz actually store?

    
How a strong answer sounds
timestamptz stores an absolute instant as UTC microseconds in 8 bytes; it does not store the zone. Input is interpreted using the zone in the literal or the session's TimeZone, and output is shown in the reader's session zone, so every client sees the same moment correctly. timestamp stores a bare wall-clock reading with no zone, so its meaning depends on who wrote it. I'd use timestamptz for events, and keep a separate zone-name column (e.g. Europe/London) when I also need the user's local calendar, for example to compute "the user's Monday".

What does SELECT 2147483647::integer + 1 do in PostgreSQL?

      

        
        
        
        
      

      
PostgreSQL checks integer overflow and raises an error rather than wrapping. 2,147,483,647 is the largest 32-bit signed integer.

    


    

      
Which type is best for storing order totals?

      

        
        
        
        
      

      
Both are exact. Floating-point types store binary fractions and accumulate rounding errors in sums.

    


    

      
What does a timestamptz value store?

      

        
        
        
        
      

      
The name is misleading: no zone is stored. Input is converted to UTC, and output is converted to the session's TimeZone setting.

    


    

      
In PostgreSQL, how does varchar(255) compare with text for performance?

      

        
        
        
        
      

      
The documentation states there's no performance difference between text, varchar and varchar(n), apart from char(n)'s padding.

    


    

      
What does '{"id": 7, "id": 8}'::jsonb return?

      

        
        
        
        
      

      
jsonb keeps only the last value for a duplicated key. The json type would have kept the input text exactly, duplicates included.
