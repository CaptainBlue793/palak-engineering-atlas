GROUP BY & Aggregates

Dashboards, reports and half of all interview questions ask for numbers per something: revenue per country, orders per day, active users per plan. That's GROUP BY plus aggregate functions. The mechanics are simple once you see the order things happen in: rows are filtered, sorted into groups, each group collapses to one row, and then groups are filtered. Almost every confusing error and wrong total in this area comes from mixing up those stages, or from how aggregates treat NULL.

  • Use COUNT, SUM, AVG, MIN, MAX and know exactly how each treats NULL and empty input
  • Explain the "must appear in the GROUP BY clause" error and the three correct fixes
  • Choose between WHERE and HAVING, and use FILTER for conditional aggregates
  • Distinguish COUNT(*), COUNT(col) and COUNT(DISTINCT col)
  • Produce subtotals and grand totals with GROUPING SETS and ROLLUP

Aggregate functions

An aggregate function takes a set of rows and returns one value. Without GROUP BY, the whole result is one group, so you get one row:

SELECT count(*)            AS orders,
       sum(total_cents)     AS revenue_cents,
       avg(total_cents)     AS avg_order_cents,
       min(created_at)      AS first_order,
       max(created_at)      AS last_order
FROM   orders
WHERE  status = 'paid';

The NULL rules matter more than the functions themselves. Every aggregate except COUNT(*) ignores NULL inputs. And on zero input rows, COUNT returns 0 but SUM, AVG, MIN and MAX return NULL, not 0, which then propagates through any arithmetic. Wrap sums in coalesce(sum(x), 0) when "no rows" should mean zero.

Note the AVG row: averaging a column with NULLs divides by the number of non-NULL values. If NULL really means zero (no discount), write avg(coalesce(discount, 0)); if it means unknown, the default is right. That's a business decision, so make it explicitly.

GROUP BY: one row per group

GROUP BY sorts the rows into groups that share the same values in the listed columns, then each group collapses to one output row. NULLs form a group of their own.

SELECT   country, count(*) AS orders, sum(total_cents) AS revenue_cents
FROM     orders
WHERE    status = 'paid'
GROUP BY country
ORDER BY revenue_cents DESC;

"must appear in the GROUP BY clause"

After grouping, each output row stands for a whole group. A column that's in the GROUP BY has one value per group, and so does an aggregate. Any other column could have many values within the group, so the database refuses to pick one:

SELECT   country, customer_id, count(*)
FROM     orders
GROUP BY country;
-- ERROR:  column "orders.customer_id" must appear in the GROUP BY clause or be used in an aggregate function

There are three correct fixes, and they mean different things: group by it too (GROUP BY country, customer_id: a row per country and customer); aggregate it (count(DISTINCT customer_id), max(customer_id), array_agg(customer_id)); or, if you wanted a particular row per group, such as each country's biggest order, use a window function (Chapter 6). One exception: PostgreSQL allows ungrouped columns that are functionally dependent on a grouped primary key, so GROUP BY c.customer_id lets you select c.name and c.email too. (Older MySQL versions silently returned an arbitrary value instead of an error, which is worse.)

WHERE vs HAVING, and FILTER

Use WHERE for conditions on individual rows, and HAVING only for conditions on aggregates. Putting a row condition in HAVING (HAVING country = 'GB') works when the column is grouped, but it makes the database build every group first and discard most of them; WHERE removes the rows before any grouping work.

For several conditional counts in one pass, PostgreSQL supports the SQL-standard FILTER clause, cleaner than the older sum(CASE WHEN … THEN 1 ELSE 0 END) idiom:

SELECT   date_trunc('day', created_at)                         AS day,
         count(*)                                              AS orders,
         count(*) FILTER (WHERE status = 'refunded')             AS refunds,
         sum(total_cents) FILTER (WHERE coupon IS NOT NULL)     AS coupon_revenue
FROM     orders
WHERE    created_at >= now() - interval '30 days'
GROUP BY 1
HAVING   count(*) FILTER (WHERE status = 'refunded') > 10           -- days with unusual refunds
ORDER BY 1;

GROUP BY 1 refers to the first output column; it's convenient for long expressions. date_trunc is the standard way to bucket timestamps by hour, day, week or month.

Subtotals: GROUPING SETS, ROLLUP and CUBE

Reports often want totals at several levels at once: per country and status, per country, and overall. Instead of three queries glued together with UNION ALL, ask for several groupings in one pass:

SELECT   country, status, sum(total_cents) AS revenue_cents, grouping(country, status) AS level
FROM     orders
GROUP BY ROLLUP (country, status)        -- = GROUPING SETS ((country, status), (country), ())
ORDER BY country NULLS LAST, status NULLS LAST;

Subtotal rows show NULL in the rolled-up columns. Because real data can also contain NULLs, use grouping() to tell them apart: it returns a bit mask with 1 for each column that was aggregated away in that row. CUBE (a, b) produces every combination: (a, b), (a), (b) and ().

📈
Counting distinct users without counting them

count(DISTINCT user_id) is the most expensive common aggregate: the database must remember every distinct value it has seen, which for "daily active users over a year of events" means hashing or sorting billions of IDs. Large analytics systems usually don't. They use HyperLogLog, a probabilistic sketch that estimates distinct counts to within about 1–2% using a few kilobytes per group, and whose sketches can be merged: per-day sketches combine into weekly and monthly numbers without rescanning. BigQuery's APPROX_COUNT_DISTINCT, Redis's PFCOUNT, Druid, and the hll extension for PostgreSQL all use it. Exact counts are for billing; dashboards are usually fine with an estimate (the System Design course covers the idea in its chapter on probabilistic data structures).

⚠️
Common mistakes
  • Aggregates in WHERE (WHERE count(*) > 5): an error. Groups don't exist yet; use HAVING.
  • Forgetting that SUM of nothing is NULL. coalesce(sum(x), 0) when no rows should mean zero.
  • AVG over a column with NULLs when NULL meant zero.
  • COUNT(*) after a LEFT JOIN, which counts the NULL-padded row; count a column from the right side.
  • Aggregating after a fan-out join (Chapter 3): totals multiplied.

Interview drill

Explain it simply: What's the difference between WHERE and HAVING?

How a strong answer sounds
WHERE filters individual rows before grouping, so it can't use aggregates. HAVING filters groups after aggregation, so it can: HAVING count(*) > 5. Logically it's FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY. Row conditions belong in WHERE even when they'd work in HAVING, because removing rows before grouping is less work.

Deeper: For each customer, return their number of orders and their total spend, including customers with no orders as 0 and 0.

How a strong answer sounds
SELECT c.customer_id, c.name, count(o.order_id) AS orders, coalesce(sum(o.total_cents), 0) AS spend FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id GROUP BY c.customer_id. Three details: a LEFT JOIN keeps customers without orders; count(o.order_id) rather than count(*), so they get 0, not 1; and coalesce because sum over no non-NULL values is NULL. Grouping by the primary key lets me select c.name without listing it, since it's functionally dependent.

🧠 Key takeaways

  • Logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.
  • Every aggregate except COUNT(*) ignores NULLs; SUM/AVG/MIN/MAX of nothing is NULL.
  • SELECT after GROUP BY may only use grouped columns, aggregates, or columns dependent on a grouped primary key.
  • WHERE filters rows, HAVING filters groups; FILTER (WHERE …) gives conditional aggregates.
  • ROLLUP, CUBE and GROUPING SETS compute several levels of totals in one pass.

Check your understanding

A column holds 10, NULL, 10, 30. What is AVG(col)?

Aggregates skip NULLs: the sum is 50 over 3 non-NULL values.

Why does SELECT country, customer_id, count(*) FROM orders GROUP BY country fail?

Each output row represents a group. Only grouped columns and aggregates (or columns dependent on a grouped primary key) have one value per group.

Which query finds countries with at least 100 paid orders?

The row condition (paid) goes in WHERE; the condition on the aggregate goes in HAVING.

What does SUM(amount) return when no rows match the WHERE clause?

An aggregate without GROUP BY always returns one row; SUM over zero rows is NULL. COUNT would be 0. Use coalesce(sum(amount), 0).

What does GROUP BY ROLLUP (country, status) produce?

ROLLUP(a, b) is GROUPING SETS ((a, b), (a), ()). CUBE would add (b) on its own.
