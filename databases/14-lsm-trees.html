LSM Trees

A B-tree changes data where it lies. To insert a row it finds the right page, reads it if it isn't in memory, alters it and writes it back, and for random keys that is a random read and a random write for every row. The log-structured merge tree starts from the opposite rule: never change anything on disk. New data is collected in memory and written out in sorted files, each in one sequential pass, and a background process keeps merging the files so that there aren't too many. Writes become very cheap. The price is paid by reads, which may have to look in several files, and by the merging itself. RocksDB, Cassandra, ScyllaDB, HBase and the storage layers of most distributed SQL databases are built this way, and this chapter explains the parts and the trade.

Memtable and WAL

A write does two things, and neither reads from disk. The key and value are appended to a write-ahead log, so that they survive a crash, and they are inserted into the memtable, a sorted structure in memory, usually a skip list. Then the write is acknowledged.

When the memtable is full it is frozen, a new one takes over, and the frozen one is written to disk in the background as a single sorted file. An update is just a newer entry for the same key. A delete can't remove anything, since the old value may be in a file that will never be changed, so it writes a marker called a tombstone, meaning "this key was deleted at this moment".

SSTables

The file a flush produces is a sorted string table, or SSTable. Once written it is never modified.

Part of the fileHoldsUsed for
Data blocksEntries in key order, in blocks of a few kilobytes, usually compressedThe data itself
Index blockThe first key of each data block and its offsetFinding the one block that could hold a key, by binary search
Bloom filterA compact summary of the keys in the fileAnswering "definitely not here" without reading a block
FooterThe smallest and largest key, and where the other parts areSkipping the whole file when the key is outside its range

Never modifying a file has large practical benefits. Files are written sequentially at the full speed of the disk. Readers need no locks, since what they read can't change beneath them. A consistent snapshot or backup is a list of file names. And because each file is sorted and written in one go, it compresses well and wastes no space on half-empty pages.

A read has more to do than in a B-tree. The newest value of a key could be in the memtable or in any file, so a read looks in the memtable first, then in the files from newest to oldest, and stops at the first entry it finds for the key, whether a value or a tombstone.

Bloom filters

Checking a file means reading its index and then a data block. For a key that isn't in the file that is wasted I/O, and with many files most checks are of this kind. A Bloom filter avoids nearly all of them. It is an array of bits. To add a key, hash it several ways and set the bit each hash points to. To test a key, hash it the same ways and look at those bits. If any is zero, the key was certainly never added. If all are one, it probably was.

class Bloom:
    def __init__(self, bits, hashes):
        self.bits, self.k, self.array = bits, hashes, bytearray(bits // 8 + 1)

    def _positions(self, key):
        for i in range(self.k):
            yield hash((i, key)) % self.bits

    def add(self, key):
        for p in self._positions(key):
            self.array[p // 8] |= 1 << (p % 8)

    def might_contain(self, key):                 # False is certain. True is "probably"
        return all(self.array[p // 8] & (1 << (p % 8)) for p in self._positions(key))

With 10 bits for each key and 7 hash functions, about 1% of tests for absent keys wrongly say "probably". So for 10 bits a key, held in memory, 99 of every 100 pointless file reads are avoided. A Bloom filter can't help a range query, because it can only be asked about one exact key.

Compaction strategies

Left alone, the files pile up. Reads slow down as there are more to check, and disk fills with overwritten values and tombstones. Compaction is the background work of merging several SSTables into new ones. A merge of sorted files is a sequential read and a sequential write. Where the same key appears more than once only the newest entry is kept, and a tombstone is dropped once it has reached the oldest data, where there is nothing left for it to hide.

Size-tieredLevelled
RuleWhen there are about four files of similar size, merge them into one larger fileFiles are arranged in levels, each ten times the size of the one above. Within a level no two files overlap in key range

A third strategy, time-window compaction, groups files by the period they were written in and never merges across periods. It suits time-series data, where old data is never updated and whole periods expire together (Chapter 29).

Things to notice. A put never reads anything and touches only the memtable. Every fourth new key causes a flush, and the file it writes is small and overlaps the others. Put forty keys with compaction on, then get key 16, which was never written. With Bloom filters on, no file is read at all: each filter answers "not here" from memory. With them off, every file is read and nothing is found. Now reset, switch compaction off and put forty keys. Level 0 fills with nine overlapping files, well over a third of what they hold is struck-out old versions, and without Bloom filters a get for key 16 reads all nine. Put a few more and writes are refused altogether. That is a write stall, and real LSM stores do the same thing when compaction can't keep up, because unbounded files would make reads unusable. Look at the write-amplification figure too. Without compaction each entry is written to disk about once. With it, each is written about twice here, and in a real store with more levels it is ten to thirty times.

Read, write and space amplification

Three ratios describe any storage engine, and it isn't possible to make all three small at once.

AmplificationDefinitionB-treeLSM tree, levelled
WriteBytes written to disk ÷ bytes the application wroteHigh for small random updates: a whole page is rewritten for one row, and logged10 to 30, but all sequential, and spread over time
ReadDisk reads for one lookupAbout 1, once the upper levels are cached1 or 2 with Bloom filters. More for range scans, which must merge every level
SpaceBytes on disk ÷ bytes of live dataAbout 1.5: pages are two-thirds full, and hard to compressAbout 1.1, and the files compress well
ChooseWhen
A B-treeReads dominate. Range scans and secondary indexes are important. Latency must be predictable, with no background work competing for the disk

📉
Facebook's MyRocks: an LSM tree chosen to save space

Facebook kept its social graph, the friendships, likes and comments, in MySQL with the InnoDB engine, on thousands of servers with flash storage. By the mid-2010s the database's limit was disk space. InnoDB's B-tree pages were about two-thirds full after years of random updates, and InnoDB compresses a page at a time into fixed-size slots, which leaves further gaps. Engineers measured that a large part of the expensive flash they bought was holding empty space inside pages. They had already built RocksDB, an LSM-tree library, and they wrote a MySQL storage engine on top of it, called MyRocks. An LSM tree's files are written full and in key order, with no slack, and neighbouring keys compress far better than scattered pages do. When they moved the main user database across in 2016 and 2017, it took about half the space it had under compressed InnoDB. It also wrote fewer bytes to flash for each transaction, which lengthens the life of the drives, since an InnoDB update rewrites a 16 kB page to change a few bytes. The costs were as the theory says. Range scans were somewhat slower, compaction needed tuning to keep it from disturbing queries, and some InnoDB features had no equivalent. For a workload of small random writes on costly storage, halving the number of servers was worth it. The reason for the move is the notable part: LSM trees are usually presented as a way to write faster, and Facebook adopted one to store the same data in less room.

⚠️
Common mistakes
  • "LSM trees are faster." They are faster to write to. Point reads are about equal, and range scans are slower.
  • Ignoring compaction when sizing a cluster. It needs spare disk, I/O and processor. A store running at 90% full or 100% I/O has nowhere to compact.
  • Deleting in bulk and expecting space back at once. Deletes add tombstones. Space returns only when compaction reaches them, and until then reads must step over them (Chapter 45).
  • Relying on Bloom filters for range queries. They answer only "is this exact key here?".
  • Using an LSM store as a queue. Constant inserts and deletes at the head leave a trail of tombstones that every read has to scan.
  • Benchmarking for ten minutes. An LSM tree looks its best before compaction debt has built up. Run until the levels have filled.

Interview drill

Explain it simply: How does an LSM tree handle a write, and why is that faster than a B-tree?

How a strong answer sounds
A write is appended to a write-ahead log for durability and inserted into an in-memory sorted structure, the memtable; then it is acknowledged. No data page is read or modified on disk. When the memtable reaches a size limit it is flushed to disk as an immutable sorted file, an SSTable, in one sequential write, and the corresponding log is discarded. Updates are just newer entries for the same key, and deletes are tombstones. In the background, compaction merges SSTables, keeping the newest version of each key and dropping obsolete ones. It is faster to write than a B-tree because a B-tree updates in place: for a random key it must find the leaf page, read it from disk if it isn't cached, modify it, and eventually write the whole page back, a random read and a random write per update, plus occasional page splits. The LSM tree turns all of that into sequential I/O and batches it. The cost moves to reads, which may consult several files, mitigated by Bloom filters, and to the background compaction work.

Deeper: Compare size-tiered and levelled compaction. When would you choose each?

How a strong answer sounds
They sit at different points on the trade-off between write, read and space amplification. Size-tiered compaction waits until there are several SSTables of similar size and merges them into one bigger table. Each entry is rewritten only once per tier, so write amplification is low, but tables at the same tier overlap in key range, so a read may have to check many of them, and old versions of a key can coexist across tables, so space amplification can approach two; merging the largest tier also temporarily needs about as much free space as the data itself. Levelled compaction organises tables into levels where each level is about ten times larger than the previous and, within a level, tables don't overlap. A read checks at most one table per level, and obsolete data is cleared quickly, so space overhead is around ten percent. The price is that pushing data down a level means rewriting it against the overlapping tables there, so each entry is rewritten roughly ten times per level, a write amplification of tens. I'd choose size-tiered for write-heavy, insert-mostly workloads where disk is plentiful, such as logging or ingest; levelled for read-heavy workloads or ones with many updates and deletes, where read latency and space matter; and time-window compaction for time-series data with TTLs, since whole files expire together.

🧠 Key takeaways

  • An LSM tree never changes data on disk. A write appends to a log and inserts into a memtable, which is flushed as a sorted, immutable SSTable.
  • An update is a newer entry and a delete is a tombstone. A read takes the newest entry it finds, looking from the memtable down.
  • A Bloom filter says "definitely not in this file" from memory, which removes most reads for absent keys. It can't help range scans.
  • Compaction merges files to bound read cost and reclaim space. Without it, reads degrade and writes eventually stall.
  • Size-tiered compaction writes less and reads worse. Levelled compaction reads well and uses little space, at many rewrites per entry.
  • B-trees favour reads and predictable latency. LSM trees favour writes and space.

Check your understanding

What does an LSM tree write to disk before acknowledging a put?

The log makes the write durable, and the memtable holds it in sorted order until the next flush.

How does an LSM tree delete a key whose value is in an SSTable?

SSTables are never modified. The tombstone hides older entries until a merge can drop them all.

A Bloom filter for an SSTable says a key "might be present". What do you know?

Bloom filters have false positives, at a rate of about 1% with 10 bits a key, and no false negatives.

Compaction is falling behind on a write-heavy LSM store. What happens first?

The store slows writers on purpose, to stop the read path from getting worse without bound.

Which workload suits an LSM tree better than a B-tree?

Random-key writes are a B-tree's worst case and an LSM tree's ordinary one.
