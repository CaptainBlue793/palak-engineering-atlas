Search & Inverted Indexes

A user types "indexing postgres" into a search box. They expect to find the article titled "How B-tree indexes speed up queries in PostgreSQL", although it contains neither of the words they typed, and they expect it near the top. A database can't do that with LIKE. Finding it means treating "indexing" and "indexes" as the same word, knowing that "Postgres" and "PostgreSQL" are the same thing, looking each word up in an index built for the purpose, and then putting the matches in order of how well they answer the query. This is full-text search, and at its centre is the inverted index, which is the structure behind every search engine. This chapter covers how text becomes searchable terms, how the index is laid out, how results are ranked, and when PostgreSQL's built-in search is enough.

Tokens and analysers

A search index doesn't store text. It stores terms, and the process that turns text into terms is an analyser. The quality of a search depends on this step more than on any other, and the step loses information on purpose: different spellings of one word are deliberately made identical.

Every step is specific to a language. English stemming removes "-ing" and "-es". German has compound words that must be split, and Chinese and Japanese have no spaces between words at all. An index analysed for the wrong language still works after a fashion, and gives poor results.

The inverted index

A table maps a document to the words in it. An inverted index maps the other way: each term to the list of documents that contain it, called its posting list. It is the index at the back of a book.

The cost of a query depends on the lengths of the posting lists for its terms, and hardly at all on the size of the collection. A rare word has a short list and is found at once. A very common word has a list as long as the collection, which is the practical reason for stop words. Posting lists are stored compressed, as differences between successive document ids (Chapter 29 used the same idea for timestamps).

TF-IDF and BM25

A search for two common words can match a million documents. The index has found them, and the harder problem is choosing which ten to show. A ranking function gives each matching document a score for the query. The standard one is BM25, and for each query term it combines three intuitions.

FactorIntuitionIn the formula
Term frequencyA document that mentions the term more often is more likely to be about it. But ten mentions aren't ten times better than oneRises with the count and flattens out quickly
Inverse document frequencyA term found in few documents says more than one found in most. Matching "wraparound" means more than matching "database"A weight that is high for rare terms and near zero for common ones
Length normalisationA long document contains more of every word by sheer size. One match in a short title outweighs one in a long pageThe term frequency is scaled by the document's length against the average
 
import math

def bm25(query_terms, doc, index, n_docs, avg_len, k1=1.2, b=0.75):
    score = 0.0
    for term in query_terms:
        tf = doc.count(term)                               # how often the term appears in this document
        if tf == 0:
            continue
        n = len(index[term])                               # how many documents contain the term
        idf = math.log(1 + (n_docs - n + 0.5) / (n + 0.5))     # rare terms weigh more
        norm = 1 - b + b * len(doc) / avg_len                # long documents are marked down
        score += idf * tf * (k1 + 1) / (tf + k1 * norm)      # and frequency saturates
    return score

BM25 is a refinement of an older scheme, TF-IDF, which multiplied the first two factors without the saturation. It has been the default in Lucene, and so in Elasticsearch, since 2016. Real systems add to the text score whatever else they know: how recent a document is, how popular, whether the match was in the title.

      Postgres full-text search

      PostgreSQL has all of this built in. A tsvector is an analysed document, a tsquery is an analysed query, and a GIN index (Chapter 15) is the inverted index.

      ALTER TABLE articles ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', title), 'A') ||          -- a match in the title counts for more
    setweight(to_tsvector('english', body),  'B')
  ) STORED;
CREATE INDEX articles_search_idx ON articles USING gin (search);

SELECT to_tsvector('english', 'Indexing JSON documents with GIN in Postgres');
--  'document':3 'gin':5 'index':1 'json':2 'postgr':7         stemmed, stop words gone, positions kept

SELECT title, ts_rank(search, q) AS rank
FROM articles, websearch_to_tsquery('english', 'indexing postgres -mysql') q
WHERE search @@ q
ORDER BY rank DESC LIMIT 10;

      The sensible order is the one Chapter 30 gave for any specialised store. Use PostgreSQL's search until it is the search itself that falls short: its relevance isn't good enough, users need tolerance of typos and filters by facet, or the collection outgrows one machine.

      Elasticsearch shards

      Elasticsearch is a distributed system built round Lucene, the library that implements the inverted index. Three facts about its construction explain most of its behaviour.

      • An index is written as immutable segments. New documents collect in memory and are written out as a small segment about once a second, and segments are merged in the background, as in an LSM tree (Chapter 14). A document is searchable only after its segment is written, so search is "near real time": a write is visible about a second later. A deletion is a marker until a merge removes the document.
      • An index is divided into shards, each a complete Lucene index on some machine, with replicas elsewhere. A document's id decides its shard. A search goes to every shard, each returns its best few matches, and a coordinating node merges them: scatter and gather (Chapter 26). The number of primary shards is fixed when the index is created.
      • It is not a database of record. It has no transactions, and it can lose acknowledged writes in some failures. The truth lives in the main database, and the search index is a derived copy that can be rebuilt from it.

      The third point brings an obligation: something must copy every change from the database to the search index and keep the two in step. Writing to both from the application looks simplest and goes wrong, because one of the two writes can fail and leave them different. The reliable method is to follow the database's own log of changes, through logical replication (Chapter 25), and apply each change to the index in order.

      📚
      Wikipedia's search: three hundred languages and an index that follows the edits

      Wikipedia's articles are stored in a relational database, and for most of its first decade its search ran on a system the Wikimedia engineers had built themselves on Lucene, which they found increasingly hard to maintain. In 2013 and 2014 they replaced it, one wiki at a time, with a system based on Elasticsearch which they called CirrusSearch. Two features of the problem make it a good illustration of this chapter. The first is language. There are Wikipedias in around three hundred languages, and a single analyser can't serve them. English wants stemming and a list of English stop words. German needs its long compound nouns taken apart. Chinese and Japanese have no spaces to split on, and Hebrew and Arabic attach prefixes to words. Each wiki's index is therefore built with an analysis chain for its own language, and a large part of the engineering has been in getting those chains right, since every weakness in one shows up as articles that can't be found. The second is freshness. Wikipedia is edited several times a second, and an edit should be searchable almost at once, while the database of articles remains the authority. When an article is saved, a job is queued that re-reads it and updates its document in the search index, usually within seconds. If the search cluster is unavailable, editing carries on unaffected and the jobs wait. If the index is ever damaged or its analysers are changed, it is rebuilt from the database. The database is the source of truth and the search index is a copy derived from it, which is how a search engine is normally run beside a database.

      ⚠️
      Common mistakes
      • LIKE '%term%' as a search feature. It scans every row, ignores word forms, and has no ranking.
      • Different analysers for indexing and for querying. The terms no longer meet, and documents that are plainly there can't be found.
      • Treating the search engine as the primary store. Keep the truth in the database and be able to rebuild the index from it.
      • Writing to the database and the search index separately from the application. One write fails sooner or later, and the two drift apart. Follow the database's change log.
      • Expecting to read your own write from Elasticsearch at once. A document becomes searchable when its segment is refreshed, about a second later.
      • Too many small shards. Each has a fixed overhead, and every search visits all of them.

      Interview drill

      Explain it simply: What is an inverted index, and how does a search engine use it to answer a query?

      How a strong answer sounds
      An inverted index maps each term to the list of documents that contain it, the posting list, usually with the term's frequency and positions in each document. To build it, every document is run through an analyser: tokenised into words, lowercased, stripped of stop words, and stemmed so that different forms of a word become one term. At query time the query goes through the same analyser, each resulting term is looked up in a sorted term dictionary, and the posting lists are combined: intersected for AND, merged for OR, with position checks for phrases. Because the lists are sorted by document ID, intersection is a linear merge, sped up by skip pointers, and the cost depends on the list lengths, not on the size of the collection. That gives the set of matching documents; then each is scored for relevance, typically with BM25, which rewards a term appearing often in the document, rewards rare terms more than common ones, and normalises for document length. The top results by score are returned. In PostgreSQL the same structure is a GIN index over a tsvector column.

      Deeper: Your product's search is on PostgreSQL full-text search. When would you move it to Elasticsearch, and how would you keep the two in sync?

      How a strong answer sounds
      I'd stay on PostgreSQL as long as it meets the product's needs, because it is transactionally consistent with the data, needs no extra infrastructure, and supports joins and permissions in the same query. I'd move when search-specific requirements outgrow it: relevance that needs BM25 with field boosts and tuning; typo tolerance, autocomplete, faceted counts and highlighting as first-class features; multiple languages with proper analysers; a corpus or query rate beyond what one machine handles well, since ts_rank has to visit every matching row; or search load that I want isolated from the transactional database. For synchronisation, I'd avoid dual writes from the application, since a failure between the two writes leaves them inconsistent and there is no transaction spanning both. I'd make the database the source of truth and derive the index from its change stream: logical replication or a change-data-capture tool reading the WAL, publishing changes to a queue, with a consumer that applies them to Elasticsearch idempotently, keyed by document ID and versioned so that out-of-order updates can't overwrite newer data. A simpler variant is a transactional outbox table. I'd build a full reindex job from the start, for mapping changes and recovery, using index aliases to switch atomically. And I'd design the product for the lag: after a user creates something, show it from the database rather than expecting it in search results within the same second.

      🧠 Key takeaways

      • An analyser turns text into terms by tokenising, lowercasing, removing stop words, stemming and applying synonyms. The query must go through the same one.
      • An inverted index maps each term to the documents containing it. Queries intersect or merge those lists.
      • Query cost follows the length of the posting lists, so rare words are cheap and very common ones are dropped.
      • BM25 scores a document by how often it uses the query's terms, how rare those terms are, and how long the document is.
      • PostgreSQL's tsvector with a GIN index gives search that is consistent with the data, and is enough for many applications.
      • A search engine is a derived, slightly delayed copy. The database stays the source of truth, and the index is fed from its change log.

      Check your understanding

      A document contains "Indexes" and the query is "indexing". How can they match?

      Matching happens on terms. The analyser's job is to make different forms of a word into the same term.

      In an inverted index, what is a posting list?

      Usually with the number of occurrences and their positions in each document.

      A query has two terms: one appears in 90% of documents and the other in 0.1%. Which contributes more to a document's BM25 score?

      That weighting is the inverse document frequency.

      A document is indexed into Elasticsearch, and a search run 100 ms later doesn't find it. Why?

      Elasticsearch is near real time. A read of the document by its id would have found it.

      What is the most reliable way to keep a search index in step with the database?

      Dual writes diverge the first time one of them fails. The change log has every committed change, in order.
