JSON, CSV & Loading Data

Data arrives as files: a CSV export from another system, a dump of JSON events, a spreadsheet someone emailed. Getting it into tables correctly and quickly is a skill of its own. Correctly, because CSV has quoting rules most hand-written parsers get wrong; quickly, because the naive approach, one INSERT per row, can be a thousand times slower than the right one. This chapter covers PostgreSQL's COPY, the traps in CSV and JSON files, and the staging-table pattern for loading data you don't fully trust.

  • Load and export data with COPY and \copy, and know which machine reads the file
  • Handle CSV quoting, embedded newlines, NULL versus empty string, and header rows
  • Load JSON lines into jsonb and turn documents into typed columns
  • Explain why COPY is orders of magnitude faster than row-by-row INSERT
  • Use a staging table to validate before touching real tables

COPY: the bulk path in and out

COPY moves rows between a table and a stream of text in one command. It skips the per-statement work of INSERT (parsing, planning, a round trip per row) and is the fastest way to load data into PostgreSQL.

-- server-side: the FILE is read by the database server process (needs pg_read_server_files)
COPY products (sku, name, price_cents) FROM '/var/lib/postgresql/import/products.csv'
    WITH (FORMAT csv, HEADER true);

-- client-side, in psql: the file is on YOUR machine; psql streams it over the connection
\copy products (sku, name, price_cents) FROM 'products.csv' WITH (FORMAT csv, HEADER true)

-- export a query result
\copy (SELECT order_id, total_cents FROM orders WHERE created_at >= '2026-09-01') TO 'sept.csv' WITH (FORMAT csv, HEADER true)

The difference between COPY … FROM '/path' and \copy confuses everyone once. The first is SQL executed by the server, so the path is on the database server's disk (and on a managed database you usually can't put files there). The second is a psql command that reads a file on your laptop and sends it as COPY … FROM STDIN. Application code does the same through its driver:

import csv, psycopg

with psycopg.connect(DSN) as conn, conn.cursor() as cur, open("products.csv", newline="") as f:
    reader = csv.reader(f)
    next(reader)                                          # skip the header row
    with cur.copy("COPY products (sku, name, price_cents) FROM STDIN") as copy:
        for sku, name, price in reader:
            copy.write_row((sku, name, int(price)))       # psycopg escapes each value
# leaving the "with connect" block commits

CSV is harder than it looks

CSV looks like "split each line on commas". It isn't, and code that does that corrupts data the first time a product name contains a comma. The common rules (RFC 4180, and what PostgreSQL's CSV format follows):

  • A field containing a comma, a double quote or a line break must be wrapped in double quotes: "Cable, USB-C".
  • A double quote inside a quoted field is written twice: "27"" monitor" means 27" monitor.
  • A quoted field may contain a newline, so one record can span several lines of the file. Line-by-line tools (wc -l, split, head) can cut a record in half.

Encoding is the other trap. COPY assumes the client encoding (normally UTF-8); a file exported from an older Windows tool in Windows-1252 fails with invalid byte sequence for encoding "UTF8", or worse, loads mojibake if the bytes happen to be valid. Add ENCODING 'WIN1252' to the COPY options when you know the source.

JSON documents

JSON usually arrives as JSON lines (one document per line, the format most log and event pipelines emit) or as one big array. Either way, the pattern is: land the raw documents in a jsonb column, then extract typed columns with SQL.

CREATE UNLOGGED TABLE raw_events (doc jsonb NOT NULL);

-- JSON lines. The odd QUOTE/DELIMITER characters stop COPY from interpreting the JSON's own
-- backslashes and quotes: each whole line arrives as one field.
\copy raw_events (doc) FROM 'events.jsonl' WITH (FORMAT csv, QUOTE e'\x01', DELIMITER e'\x02')

INSERT INTO events (event_id, user_id, kind, occurred_at, props)
SELECT (doc->>'id')::uuid,
       (doc->>'user_id')::bigint,
       doc->>'type',
       (doc->>'ts')::timestamptz,
       doc->'properties'                        -- the variable part stays jsonb
FROM   raw_events;

Why the odd options? COPY's text format treats backslashes as escapes, so a JSON string containing \n or \" would be altered before it reached the jsonb parser. Telling the CSV format to use control characters that never appear in JSON as its quote and delimiter makes each line one untouched field. For a single JSON array, load the file as one value and expand it with jsonb_array_elements or jsonb_to_recordset.

-> returns jsonb; ->> returns text, which you then cast. A bad value fails the cast and the whole statement, which is what you want: you find out at load time, not in a report three weeks later.

Bulk loading: why row-by-row is so slow

Each INSERT sent on its own pays three costs on top of the actual insert: a network round trip (the client waits for the reply before sending the next), parsing and planning the statement, and, in autocommit mode, a commit, which waits for the write-ahead log to be flushed to disk (Chapter 20). Multiply by a million rows. Set the round-trip time to match where your client runs and compare the four strategies:

Bulk-load calculator: 1,000,000 rows four waysInteractive
Model per row: insert work 5 µs, each index +4 µs, statement parse and plan 30 µs, COPY parsing 2 µs. Real numbers depend on row width and hardware, but the ratios between strategies hold.

The ranking barely changes with the settings: autocommit is bound by commits and round trips, one big transaction still pays a round trip per row, batching amortises the round trip, and COPY removes it. Indexes slow every strategy down equally per row, which is why very large one-off loads sometimes drop secondary indexes, load, and rebuild them afterwards. Building an index once over sorted data is cheaper than updating it a million times.

The staging-table pattern

Data from outside is never as clean as promised. Loading straight into production tables means one bad row fails the whole COPY, or a good-looking bad row gets in. The standard shape:

INSERT INTO products (sku, name, price_cents)
SELECT upper(trim(sku)), trim(name), round(price::numeric * 100)::bigint
FROM   staging_products
WHERE  price ~ '^\d+(\.\d{1,2})?$'                  -- rows that fail were logged separately
ON CONFLICT (sku) DO UPDATE
   SET name = EXCLUDED.name, price_cents = EXCLUDED.price_cents;

The genes that spreadsheets turned into dates

CSV carries no types: whatever opens the file guesses them. Spreadsheet software guessed that human gene symbols such as SEPT2 and MARCH1 were dates and silently converted them to "2-Sep" and "1-Mar". A 2016 study of published genomics papers found that around a fifth of those with gene lists in supplementary spreadsheets contained such errors. The fix that finally stuck came from the other side: in 2020 the HUGO Gene Nomenclature Committee renamed 27 genes (SEPT1 became SEPTIN1, MARCH1 became MARCHF1). The database lesson: load files as text into staging, cast deliberately with SQL, and never let a tool in the middle guess types for you.

⚠️
Common mistakes
  • Splitting CSV lines on commas. Use a real CSV parser (csv in Python) or COPY … FORMAT csv.
  • One INSERT per row in autocommit mode for bulk data. Use COPY, or at least batch in one transaction.
  • Confusing COPY FROM 'file' with \copy. The first reads the server's disk, the second yours.
  • Loading JSON with COPY's default text format. Backslash escapes in the JSON get mangled.
  • Forgetting ANALYZE after a big load. The planner keeps using statistics from when the table was small.
🎤
Interview drill

Explain it simply: A script inserts 2 million rows one INSERT at a time and takes 40 minutes. How do you make it fast?

How a strong answer sounds
Each row pays a network round trip, statement parsing, and, if autocommit is on, a commit that waits for a WAL flush. First, wrap the load in one transaction so there's one commit. Better, batch rows into multi-row INSERTs or use the driver's pipelining so round trips are amortised. Best, stream it with COPY FROM STDIN (psycopg's cursor.copy), which typically loads hundreds of thousands of rows a second. For a one-off load into a big table, consider dropping secondary indexes and rebuilding them after, and run ANALYZE at the end.

Deeper: You receive a nightly partner CSV that sometimes has bad rows. How do you load it without failing the whole batch or letting bad data in?

How a strong answer sounds
COPY it into an unlogged staging table whose columns are all text, so the load itself can't fail on types. Then validate with SQL: rows whose values don't match the expected patterns, duplicate keys, references to unknown products. Write those to a rejects table with a reason, and alert if the reject rate is unusual. Insert the valid rows into the real table with INSERT … SELECT … ON CONFLICT inside one transaction, run ANALYZE, and truncate staging. The job is rerunnable because the upsert is idempotent.

🧠 Key takeaways

  • COPY is the fast path in and out; \copy reads files on the client, COPY … FROM 'path' on the server.
  • CSV fields can contain quoted commas, doubled quotes and newlines; in PostgreSQL's CSV format an unquoted empty field is NULL.
  • Land JSON in jsonb, then extract typed columns with ->> and casts.
  • Row-by-row autocommit inserts pay a round trip, a parse and a commit per row; batching and COPY remove those costs.
  • Load untrusted files into a text staging table, validate with SQL, then upsert in one transaction and ANALYZE.

Check your understanding

In psql, what's the difference between COPY t FROM '/tmp/x.csv' and \copy t FROM '/tmp/x.csv'?

COPY with a file path is executed by the server process and needs server file access. \copy is a psql command that sends the local file as COPY FROM STDIN.

In PostgreSQL's CSV format, how is the line 7,,"" loaded into three text columns?

By default CSV format treats an unquoted empty field as NULL and a quoted empty field "" as an empty string.

What is the main reason one INSERT per row in autocommit mode is so slow?

The actual insert takes microseconds. The per-statement overheads, especially the round trip and the durable commit, dominate.

A field in a CSV file contains a line break inside double quotes. What follows?

Quoted fields may contain newlines. A proper CSV parser keeps the record whole; wc -l and split don't know about quoting.

Why load an untrusted CSV into an all-text staging table first?

One bad value makes a direct COPY fail entirely. Staging separates "get the bytes in" from "decide what's valid", and the final upsert is one atomic step.
