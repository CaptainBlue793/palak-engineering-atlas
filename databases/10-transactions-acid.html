Transactions & ACID

Moving £100 from one account to another is two writes: a debit and a credit. If the server crashes between them, or the credit fails a constraint, or another transfer runs at the same time, what's left? A transaction groups statements so the database can make strong promises about them, summarised as ACID: atomicity, consistency, isolation and durability. Each letter is a different promise kept by a different mechanism. This chapter makes each one concrete, shows the PostgreSQL behaviour that surprises people (one error aborts the whole transaction), and lets you crash a server mid-transfer.

BEGIN, COMMIT, ROLLBACK

BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 10000 WHERE account_id = 'A';
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE account_id = 'B';
COMMIT;            -- both changes become permanent and visible together; ROLLBACK would discard both

Without BEGIN, PostgreSQL runs in autocommit mode: every statement is its own transaction, committed as soon as it finishes. That's fine for single statements, and wrong for anything that must happen together. (Drivers differ: psycopg opens a transaction implicitly and waits for your commit, as P6 showed.)

One PostgreSQL behaviour surprises people coming from other databases: once any statement in a transaction fails, the whole transaction is aborted, and every later statement fails until you end it:

BEGIN;
INSERT INTO orders … ;                 -- ok
INSERT INTO order_items … quantity = -1 …;   -- ERROR: violates check constraint
INSERT INTO audit_log … ;              -- ERROR: current transaction is aborted, commands ignored until end of transaction block
COMMIT;                                -- actually performs ROLLBACK

-- to recover from an expected error without losing earlier work, use a savepoint:
SAVEPOINT before_item;
INSERT INTO order_items … ;
ROLLBACK TO SAVEPOINT before_item;    -- undo just that part; the transaction continues

The four promises

LetterPromiseHow PostgreSQL keeps itWhat still goes wrong
AtomicityAll of the transaction's changes happen, or none doChanges are only visible once the commit record is written; aborted work is simply never visible (MVCC, Ch 23)Work split across two transactions, or across a database and an external API call
ConsistencyA transaction takes the database from one valid state to anotherConstraints checked on every write (Ch 8); the rest is the application's logicRules that exist only in code, or only in someone's head
IsolationConcurrent transactions don't see each other's half-done workSnapshots and locks, at a chosen level (Ch 21)The default level, Read Committed, still allows lost updates and write skew
DurabilityOnce COMMIT returns, the change survives a crashThe WAL is flushed to disk before COMMIT returns (Ch 20)synchronous_commit = off, disks that lie about flushing, losing the whole disk without replicas or backups

Consistency is the odd one out: it's mostly your promise. The database guarantees that a committed transaction satisfies the constraints you declared, and that atomicity and isolation don't break invariants that each transaction preserves on its own. If your code moves £100 out of A and only £90 into B, the database will durably, atomically and in isolation store the wrong answer.

Durability: what COMMIT waits for

A committed change must survive a power cut, but writing every changed table page to disk at commit would be slow (they're scattered all over the files). Instead the database appends a compact description of the changes to a sequential log, the write-ahead log, and flushes only that. The pages themselves are written later, in the background. After a crash, replaying the log reconstructs anything that hadn't reached the data files.

With synchronous_commit = off, COMMIT returns before the flush, and the WAL writer flushes shortly afterwards. A crash in that window loses the last few hundred milliseconds of commits, but never leaves a half-applied transaction: atomicity and consistency are kept, only durability is relaxed. It can be set per transaction (SET LOCAL synchronous_commit = off), which makes it reasonable for, say, analytics events, and wrong for payments.

💾
"fsyncgate": when the disk said yes and meant no

Durability depends on fsync meaning what it says. In 2018 PostgreSQL developers found that on Linux, if an fsync call failed (for example after a storage error), the kernel could mark the failed pages clean and report success on the next retry, so a database that retried would believe data had reached disk when it hadn't. PostgreSQL had retried, as most software did. The fix, released in early 2019 across supported versions, was blunt: on an fsync failure, PostgreSQL now PANICs and restarts, recovering from the WAL instead of trusting the retry. The lesson for engineers is that "durable" is a chain (database, file system, kernel, controller cache, disk) and every link has to tell the truth, which is why serious deployments also replicate and back up.

⚠️
Common mistakes
  • Related writes in separate autocommit statements. A crash or error between them leaves half a change.
  • Calling external services inside a transaction and assuming they roll back with it. The email is already sent; use an outbox table (LLD Ch 26).
  • Catching an error and carrying on in the same PostgreSQL transaction: every later statement fails. Use a savepoint or roll back.
  • Long transactions. They hold locks and old snapshots, blocking DDL and VACUUM.
  • Equating ACID's C with "correct". The database enforces the constraints you declared, nothing more.

Interview drill

Explain it simply: What does ACID mean? Give an example of each letter.

How a strong answer sounds
Atomicity: a transfer's debit and credit both happen or neither does, even if the server crashes between them. Consistency: the transaction leaves the data satisfying its rules, e.g. a CHECK (balance >= 0) rejects an overdraft and aborts the whole transfer. Isolation: another transaction running at the same time doesn't see the money missing from A but not yet in B; how strictly that holds depends on the isolation level. Durability: once COMMIT returns, a power cut can't undo it, because the write-ahead log was flushed before the reply. I'd add that consistency is partly the application's job, and that the default isolation level doesn't prevent every anomaly.

Deeper: How can a database guarantee durability without writing every changed page to disk at commit?

How a strong answer sounds
Write-ahead logging. Each change is first recorded in a sequential log, and at commit only the log up to the commit record is flushed: one sequential write instead of many random ones. Data pages are modified in memory and written lazily by a checkpointer. After a crash, recovery replays the log from the last checkpoint, redoing committed changes that hadn't reached the data files; uncommitted changes are never visible. The rule that makes it work is that a page is never written to disk before the log records describing its changes.

🧠 Key takeaways

  • BEGIN … COMMIT groups statements; without it each statement autocommits on its own.
  • In PostgreSQL one error aborts the transaction; use savepoints to recover from expected errors.
  • Atomicity and isolation come from MVCC and locking; durability from flushing the WAL at commit.
  • Consistency is enforced only as far as your constraints go.
  • synchronous_commit = off can lose recent commits on a crash but never half a transaction.

Check your understanding

The debit and credit of a transfer run as two autocommit statements, and the server crashes between them. What's the state after restart?

Each autocommit statement is its own transaction. The first one committed; the second never ran. Wrap both in one transaction.

Inside a PostgreSQL transaction, an INSERT fails a CHECK constraint. You then run another INSERT. What happens?

PostgreSQL aborts the whole transaction on an error. Roll back, or use SAVEPOINT / ROLLBACK TO SAVEPOINT around statements that may fail.

What does COMMIT wait for, by default, before returning?

Flushing the sequential log is enough for durability; data pages are written later and reconstructed from the WAL after a crash.

With synchronous_commit = off, what can a crash cause?

Commits return before the WAL flush, so the last moments of acknowledged commits can be lost. Atomicity and consistency are unaffected.

Which ACID property depends most on the application rather than the database?

The database enforces declared constraints; whether a transaction preserves the business's invariants (money moved in equals money moved out) is up to its logic.
