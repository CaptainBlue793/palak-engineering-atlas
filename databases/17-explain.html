Reading EXPLAIN

When a query is slow, the database will tell you exactly what it did, and how long each part took: which tables it scanned and how, in what order it joined them, how many rows it expected at each step and how many it found. All of this comes from one command, EXPLAIN. The output is dense and looks forbidding, and most engineers never learn to read it, which leaves them guessing at indexes. It is a small notation with about six numbers on each line and a few rules, and it can be learned in an afternoon. This chapter covers the notation, the node types you will meet, and a fixed order in which to look for the one line that explains a slow query.

  • Choose between EXPLAIN and EXPLAIN ANALYZE, and run the second safely
  • Read every number on a plan line, including the ones that have to be multiplied by loops
  • Recognise the common scan, join and sort nodes and what each one suggests
  • Use the gap between estimated and actual rows to find a plan chosen on bad information
  • Read the buffer counts, and follow a checklist to the node responsible

The first bracket is the planner's forecast and the second is what happened. Four rules prevent most misreadings.

  • Read from the inside out. The most deeply indented nodes run first and feed their parents. The top line is the last step.
  • Times and rows are for one run. Multiply by loops. A node showing actual time=0.171 rows=1 loops=48210 took 8.2 seconds and returned 48,210 rows in total.
  • A node's time includes its children's. The time spent in the node itself is its own figure less those of the nodes beneath it.
  • Cost is in the planner's own units, in which reading one page sequentially costs 1. It is for comparing plans with each other. It is not milliseconds.

Chapter 18 covers how the three joins work. To read a plan it is enough to know which one multiplies work: a Nested Loop runs its inner side once for each outer row, so an error in the count of outer rows is multiplied into the inner side.

Estimated vs actual rows

The single most useful comparison on any line is rows= in the first bracket against rows= in the second, multiplied by loops. The planner chose this plan because it believed the first number. If it expected 1 row and got 48,000, then every decision made above that node, which join to use, whether to sort, how much memory to ask for, was made for a query that doesn't exist.

Estimate against actualReading
Within a factor of 2 or 3Normal. Estimates are statistical
Out by 10 or moreWorth understanding, especially low in the plan, where the error spreads upwards
Estimated 1, actual thousandsThe classic disaster. The planner picks a nested loop "because there is only one row"
Estimated millions, actual a fewLess harmful: usually a hash join or a sequential scan where an index would have done

The causes of bad estimates, stale statistics, columns that are correlated with each other, expressions the planner can't see into, are the subject of Chapter 19. This chapter is about finding them.

Buffers

With the BUFFERS option each node also reports how many pages it touched, and where they came from (Chapter 12). Time varies from run to run with whatever happens to be cached, and the page count is a steadier measure of work.

Buffers: shared hit=1021 read=2204 dirtied=12, temp read=14600 written=14600
--  hit      pages found in shared_buffers
--  read     pages that had to be requested from the operating system (its cache, or the disk)
--  dirtied  pages this query changed
--  temp     pages of temporary files: a sort or a hash that spilled out of work_mem

Multiply by 8 kB to get bytes. A query that reads 97,000 pages has pulled 760 MB through the buffer pool to produce its answer, whatever its time was today. Like time, a node's buffer counts include its children's.

A checklist for slow plans

🪤
Fast in psql, slow in the application

A team has a query that takes two seconds from their application. An engineer copies it from the logs into psql, puts in the values and runs EXPLAIN ANALYZE: three milliseconds, with a sensible index scan. This has been reported so many times, on mailing lists and in bug trackers, that PostgreSQL eventually added a setting for it. The application wasn't sending the query with its values in the text. Its driver used a prepared statement, sending the text once with placeholders and the values separately (Chapter 16). For the first five executions of a prepared statement, PostgreSQL plans it afresh each time using the actual values, as the engineer's test did. After that it also builds a generic plan, one that doesn't depend on the values, and if the generic plan's estimated cost looks no worse than the average so far, it uses that plan for every later execution and stops replanning. For most queries this is a saving. For a query on a skewed column it can be a trap. Suppose status = $1 is nearly always called with a rare value, for which an index is perfect. The generic plan can't know that $1 will be rare, estimates an average number of rows, and may choose a sequential scan. The symptom is a query that gets slow on its sixth execution on each connection. It can't be reproduced by pasting the query with literals, because that is a different statement and gets a different plan. The way to see the real plan is EXPLAIN EXECUTE on a prepared statement, or the auto_explain module, which logs the plan of any statement that runs longer than a threshold, as the server actually executed it. Since version 12 the setting plan_cache_mode = force_custom_plan switches generic plans off. The plan you examine has to be the one the application is actually running.

⚠️
Common mistakes
  • Reading cost as time. Cost is an estimate in arbitrary units. Only the "actual" bracket was measured.
  • Forgetting to multiply by loops. A node at 0.2 ms looks harmless until you see it ran 50,000 times.
  • Blaming the node with the largest time. Its time includes its children's, and a loop may be slow only because of how often it was entered.
  • Running EXPLAIN ANALYZE on a write without a transaction to roll back. It executes the statement.
  • Testing on a small or empty development database. The planner chooses by table size and statistics. Plans from toy data tell you nothing.
  • Adding an index before reading the plan. If the cause is a bad estimate or a spilling sort, an index changes nothing.
🎤
Interview drill

Explain it simply: What is the difference between EXPLAIN and EXPLAIN ANALYZE, and what do the numbers on a plan line mean?

How a strong answer sounds
EXPLAIN shows the plan the optimiser would choose without running the query: the tree of operators with estimated costs and row counts. EXPLAIN ANALYZE actually executes the query and adds what really happened, so I'd wrap a write in a transaction and roll it back. On each node, the first bracket is the estimate: cost is two numbers, the cost before the first row can be returned and the total cost, in abstract units where a sequential page read is 1; rows is the number of rows the planner expects the node to emit, and width the average row size. The second bracket is measured: actual time is milliseconds to the first row and to the last, rows is what the node really returned, and loops is how many times it was executed; time and rows are per loop, so they must be multiplied by loops, and a node's time includes its children. I'd add BUFFERS to see page hits and reads per node. The most valuable thing to compare is estimated against actual rows, because a large mismatch means the plan was chosen on wrong information.

Deeper: You are handed an EXPLAIN ANALYZE for a query that takes 8 seconds. How do you find the cause?

How a strong answer sounds
I'd go in a fixed order. First, where is the time: for each node I compute its exclusive time, its actual total time times loops minus the same for its children; usually one or two nodes account for nearly everything. Second, at that node and below it, I compare estimated and actual rows. If they differ by an order of magnitude, the real problem is the estimate: a typical case is an outer scan estimated at 1 row that returns 50,000, so the planner chose a nested loop and the inner index scan runs 50,000 times; each loop is fast, but the total is seconds. The fix is then statistics, ANALYZE, extended statistics for correlated columns, or rewriting the predicate, not an index on the inner table. Third, if estimates are fine, I look at how the node does its work: a Seq Scan or Index Scan with a huge "Rows Removed by Filter" means there is no index that matches the predicate; a Sort with "external merge Disk" or a Hash with multiple batches means work_mem is too small for this query; an Index Only Scan with large Heap Fetches means the visibility map is stale and the table needs vacuuming. Fourth, BUFFERS: a large "read" count means cold cache or simply too many pages touched for the rows returned, which can indicate bloat. I'd also check planning time, and whether the plan I'm looking at is the one the application gets, since prepared statements can use a generic plan. Then I'd change one thing and compare both time and buffers.

🧠 Key takeaways

  • EXPLAIN shows the chosen plan with estimates. EXPLAIN (ANALYZE, BUFFERS) runs the query and shows what happened.
  • Read from the innermost node outwards. Times and rows are for one run and must be multiplied by loops, and a node's time includes its children's.
  • Cost is the planner's estimate in its own units, useful only for comparing plans.
  • A large gap between estimated and actual rows means the plan was chosen on false information, and it is the first thing to fix.
  • The lines under a node hold the evidence: Rows Removed by Filter, Sort Method, Heap Fetches, Batches, Buffers.
  • Find where the time is, ask why the planner chose that, change one thing, and measure again.

Check your understanding

A node shows (actual time=0.150..0.200 rows=2 loops=30000). How long did it take, and how many rows did it return, in total?

Both figures are for one run: 0.2 ms × 30,000 is 6 s, and 2 × 30,000 is 60,000 rows.

A line reads Seq Scan on orders (… rows=98 …) (actual … rows=103 loops=1), and under it Rows Removed by Filter: 4999897. What does it tell you?

The estimate, 98 against 103, is good. The waste is in how the rows were found.

Why does a row estimate of 1 with an actual count of 50,000 so often go with a very slow query?

A nested loop is the best join for one outer row and among the worst for fifty thousand.

In Buffers: shared hit=120 read=48000, what does read=48000 mean?

Buffers are pages of 8 kB, so this is about 375 MB brought into the buffer pool.

A plan contains Sort Method: external merge Disk: 117160kB. What happened, and what is the usual remedy?

An in-memory sort is reported as quicksort or top-N heapsort, with its memory use.
