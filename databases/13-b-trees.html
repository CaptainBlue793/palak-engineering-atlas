B-Trees

When you create an index and don't say what kind, you get a B-tree. So does a primary key, a unique constraint, and in MySQL the table itself. The structure dates from 1970 and has outlasted every storage technology since, because it was designed round the one fact about storage that hasn't changed: data comes in pages, and fetching a page is the expensive step. A B-tree finds one row among a billion by reading four pages. This chapter covers how it is laid out, how a search walks down it, what happens when a page fills up, and why the order in which keys arrive decides how good the tree is.

Why a wide, shallow tree

A balanced binary tree over a billion keys is 30 levels deep. In memory that is 30 pointer hops and very fast. On disk each node would be on a different page, and 30 page reads is 30 chances of a cache miss, several milliseconds in all. What a disk-based index has to keep small is the number of pages read, and comparisons hardly matter. So instead of one key and two children, a B-tree node is a whole page, holding as many keys and child pointers as fit: several hundred.

The 367 comes from P8: an entry with a bigint key is about 20 bytes, and an 8 KB page that is 90% full holds 367 of them. Each level multiplies the reach by that factor: 367, then 135,000, then 49 million, then 18 billion. The top levels are tiny. A four-level tree over a billion rows has one root page and 367 pages below it, about 3 MB, which never leave the buffer pool. In practice a lookup costs one or two page reads that might miss the cache: the leaf, and the table page it points to.

Search

An internal page holds separator keys and pointers to child pages, arranged so that everything in a child lies between the separators on either side of its pointer. A leaf page holds the keys themselves, in order, each with the address of its row. To find a key, start at the root. In each internal page, find the child whose range covers the key, with a binary search over the page's sorted entries, and follow it. At the leaf, binary-search again.

import bisect

def search(root, key):
    page = root
    while not page.is_leaf:
        i = bisect.bisect_right(page.keys, key)      # how many separators are <= key: that child covers it
        page = read_page(page.children[i])           # one page read for each level
    i = bisect.bisect_left(page.keys, key)
    if i < len(page.keys) and page.keys[i] == key:
        return page.row_addresses[i]                  # a ctid: (table page, line pointer)
    return None

Every leaf is at the same depth, so every lookup costs the same number of page reads. That is what the "B" is usually taken to stand for, balanced, and the tree keeps the property however the data is inserted, because it grows at the root and never at the leaves.

Insert and page splits

To insert a key, search for the leaf where it belongs and put it there, in order. If the leaf has room, that is the whole operation: one page changed. If the leaf is full, it has to split.

A split is much dearer than an ordinary insert. It changes at least three pages, the old leaf, the new one and the parent, and all three changes go to the WAL. And it leaves two half-empty pages where there was one full one. Whether that space is ever used depends on where later keys land:

Keys arriveWhere inserts goSplitsPages end up
In increasing order: a serial ID, a timestampAlways the rightmost leaf, which stays in the cacheOnly at the right edge. PostgreSQL then leaves the old page 90% full, since nothing more will be added to itAbout 90% full
At random: a UUID, a hashAny leaf, so every leaf must be in memory or be fetchedEverywhere, each leaving two half-full pages that fill slowlyAbout 70% full on average, so the index is a third larger

Deletes are simpler than the textbooks suggest. PostgreSQL doesn't merge pages that have become underfull. An entry is removed when VACUUM finds that its row is dead, and a page is only reclaimed when it is completely empty. An index that has had many deletions can therefore be far larger than its contents need, a condition called bloat, and the cure is to rebuild it with REINDEX INDEX CONCURRENTLY.

Range scans

Each leaf has a link to the leaf on its right, and to the one on its left. So the leaves, read along those links, are the whole index in key order. A range query descends once, to the first key in the range, and then walks sideways from leaf to leaf until it passes the end. It never goes back up.

SELECT order_id, total_cents FROM orders
WHERE created_at >= '2026-10-01' AND created_at < '2026-10-02'
ORDER BY created_at;         -- one descent, then a walk along the leaves. No sort: the index is already in order

This is the property that makes a B-tree the default. It answers equality, ranges, ORDER BY, MIN and MAX, and a prefix of a composite key (Chapter 9), all with the one structure. A hash index can do only the first (Chapter 15).

Green pages are leaves, which hold every key. White pages are internal and hold copies of some keys as separators. A real page holds several hundred entries, so a real tree is far wider and almost never more than four levels deep. The tree stops at 60 keys.

Things to notice. Insert thirty keys in order with splits down the middle: every split leaves a half-empty page behind that no later key will ever enter, and the leaves end up 54% full, in 14 pages. Reset, choose the uneven split, and insert thirty again. Now a split at the right edge moves only the newest key to the new page, the leaves behind it stay full, and the same keys fit in 8 pages. Carry on to sixty keys and the first tree needs four levels where the second needs three. That is why PostgreSQL treats the rightmost page specially. With random keys the splits land all over the tree, and the leaves end up between two-thirds and four-fifths full under either rule. Search for a key and count the pages lit up: one for each level. Scan a range and the descent happens once, followed by a walk along the leaves.

B+ trees

The tree in the panel, and in every database, is strictly a B+ tree. The original B-tree kept row pointers in internal nodes as well as in leaves. The B+ variant keeps them in the leaves only, and internal pages hold nothing but separators and child pointers.

B-tree, as first definedB+ tree, as databases use it
Row pointersIn every nodeIn the leaves only
Internal pages holdKeys, row pointers and child pointersSeparators and child pointers, so more fit and the tree is shallower
A lookup endsAt whatever level the key is foundAlways at a leaf: the same cost every time
Range scanA traversal up and down the treeA walk along the linked leaves

Real implementations add refinements. PostgreSQL's separators are shortened to the fewest bytes that tell two pages apart, and leaves store a repeated key once with a list of row addresses, which makes indexes on low-cardinality columns several times smaller. Every page also has a link to its right-hand neighbour and a "high key", so that a search which arrives just as a page is splitting can step right and still find its key, without the tree having to be locked.

Random UUIDs as primary keys

A version-4 UUID is 122 random bits. As an identifier it is ideal: any machine can make one without asking anybody, and two will never collide. As the key of a B-tree it is about the worst case there is, and many teams have found this out as their tables grew. Each new row's key belongs at a random position in the index, so each insert lands on a random leaf. While the index fits in memory nothing seems wrong. Once it is larger than the buffer pool, nearly every insert has to fetch a leaf from disk first, change it, and leave it dirty to be written back. PostgreSQL also writes a complete image of a page to the WAL the first time the page is changed after each checkpoint (Chapter 20), and with random inserts almost every insert is the first change to its page, so the WAL grows several times over. Benchmarks published by the PostgreSQL developer Tomas Vondra showed insert throughput on a large table falling to a fraction of what sequential keys gave, with the volume of WAL many times higher. The leaves were also only about 70% full. The remedy is to keep the properties of a UUID and give up the randomness of its leading bits. Version 7 of the UUID standard, agreed in 2024, puts a millisecond timestamp in the first 48 bits and random bits after it, so that new keys arrive in nearly increasing order and go to the right-hand edge of the tree as a serial number would. PostgreSQL 18 has a built-in uuidv7() function. Chapter 46 describes an earlier answer to the same problem.

⚠️
Common mistakes
  • Random primary keys on large, insert-heavy tables. Use a sequence or a time-ordered identifier.
  • Assuming an index stays compact. After mass deletions it holds the same pages, mostly empty. Measure with pgstatindex and rebuild.
  • Thinking a bigger table means a much slower lookup. A hundred times the rows adds one level.
  • A long primary key in InnoDB. Every secondary index carries a copy of it in every entry.
  • Expecting a B-tree to help with LIKE '%word%'. The index is ordered from the first character, so only a prefix can use it (Chapter 31).
  • Rebuilding with plain REINDEX on a live system. It blocks writes. Use CONCURRENTLY.

Interview drill

Explain it simply: Why do databases use B-trees for indexes and not binary search trees or hash tables?

How a strong answer sounds
Because the cost that matters on disk is the number of pages read, and because indexes have to serve range queries. A balanced binary tree over a billion keys is thirty levels deep, and with each node on a different page that is thirty page reads. A B-tree makes each node a whole page holding hundreds of keys, so the fan-out is in the hundreds and the same billion keys need four levels; the top levels are small enough to stay cached, so a lookup costs one or two real reads. It stays balanced under inserts and deletes by splitting pages and growing at the root, so every lookup costs the same. A hash table would give one-step equality lookups but has no order: it can't answer a range predicate, ORDER BY, MIN or MAX, or a prefix match. A B+ tree keeps all the keys in sorted leaf pages linked to each other, so a range scan is one descent and then a sequential walk. One structure covers equality, ranges and ordering, which is why it is the default.

Deeper: What happens when you insert into a full B-tree page, and why does the pattern of keys matter?

How a strong answer sounds
The page splits. A new page is allocated, roughly half the entries move to it, the sibling links are updated, and a separator key pointing to the new page is inserted into the parent; if the parent is full it splits too, and if the root splits a new root is created and the tree gains a level. That touches at least three pages and writes all of them to the log, so it costs several times an ordinary insert, and it leaves two half-full pages. With monotonically increasing keys, a serial ID or a timestamp, all inserts go to the rightmost leaf, which is hot in the cache, and implementations special-case that split to leave the old page nearly full, so the index ends up around 90% dense. With random keys, such as UUIDv4, inserts hit leaves all over the index: once the index exceeds memory each insert can be a disk read, splits happen everywhere and the half-full pages fill slowly, so density sits around 70%, and in PostgreSQL the WAL volume balloons because nearly every insert triggers a full-page image after a checkpoint. So I'd prefer sequential or time-ordered keys, UUIDv7 if I need UUIDs, and in a clustered-index engine like InnoDB it matters even more, because the rows themselves are in that tree.

🧠 Key takeaways

  • A B-tree node is a page with hundreds of entries, so a billion rows need only four levels, and the upper ones stay cached.
  • A search reads one page for each level, and every leaf is at the same depth.
  • An insert into a full page splits it, changing three pages or more and leaving two half-full ones. The tree grows at the root.
  • Keys in increasing order fill pages densely. Random keys cause splits and cache misses everywhere.
  • Leaves are linked, so a range scan is one descent and a walk, and the index gives sorted output for free.
  • PostgreSQL's indexes point into a heap. InnoDB's primary key is the table, and its secondary indexes point to the primary key.

Check your understanding

An index page holds about 367 entries. Roughly how many levels does a B-tree over 1 billion rows have?

367³ is about 49 million and 367⁴ about 18 billion, so four levels are enough.

Why is a database index a tree of wide pages and not a balanced binary tree?

Thirty levels would be thirty page reads. Four levels is four, and most of those are cached.

A key is inserted into a leaf page that is full. What happens?

If the parent is full as well, it splits too, and so on up to the root.

How does a B+ tree answer WHERE created_at BETWEEN a AND b?

The leaves hold all the keys in order and are linked to their neighbours.

A large table has a random UUID as its primary key. Why are its inserts slower than with a serial key?

Serial keys all go to the rightmost leaf, which is always cached and fills densely.
