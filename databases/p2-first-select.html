Your First SELECT

Almost everything you'll do with a database starts with SELECT: name the columns you want, the table they come from, which rows to keep, what order to put them in and how many to return. This chapter gets PostgreSQL running, walks through those five clauses, and then spends real time on the one thing that trips up everyone, beginners and seniors alike: NULL, and SQL's three-valued logic.

  • Write SELECT … FROM … WHERE … ORDER BY … LIMIT and say the order the clauses are evaluated in
  • Explain why WHERE x = NULL never matches anything and what to write instead
  • Predict how NULL affects AND, OR, NOT, NOT IN and sorting

PostgreSQL and psql in two minutes

PostgreSQL is a server: a long-running process that owns the data files and accepts connections. psql is its command-line client. The quickest way to get both:

# start a PostgreSQL 17 server in a container, listening on localhost:5432
docker run --name pg -e POSTGRES_PASSWORD=secret -p 5432:5432 -d postgres:17

# connect with the client inside the same container
docker exec -it pg psql -U postgres

Inside psql, lines ending in ; are SQL sent to the server; lines starting with a backslash are commands for psql itself. These are the ones you'll use every day:

SELECT, FROM, WHERE

A query names the columns (or expressions) to return, the table they come from, and a condition each row must satisfy:

SELECT name, round(price_cents / 100.0, 2) AS price
FROM   products
WHERE  category = 'input'
  AND  price_cents < 5000;

--       name      | price
-- ----------------+-------
--  Wireless mouse | 29.99
-- (1 row)

Four details to absorb now. Strings use single quotes ('input'); double quotes are for identifiers, such as a column literally named "Order". AS gives an output column a name. Integer arithmetic stays integer: 899 / 100 is 8, which is why the query divides by 100.0. And SELECT * returns every column, which is fine at the psql prompt and a bad habit in application code, because the result changes shape whenever someone adds a column.

ORDER BY and LIMIT

ORDER BY sorts the result; LIMIT n keeps the first n rows of it. Without ORDER BY, "the first n" means whichever rows the database happened to produce first, which can differ from one run to the next.

SELECT   name, price_cents
FROM     products
ORDER BY price_cents DESC, name   -- ties on price are broken by name
LIMIT    3;

The clauses are written in one order and evaluated in another. Knowing the evaluation order explains most "why can't I use that alias here?" errors: WHERE runs before SELECT, so it can't see the alias price, while ORDER BY runs after, so it can.

NULL and three-valued logic

NULL means "unknown". Any comparison with an unknown value is itself unknown: is the mouse's discount greater than 10? We don't know. So SQL has three truth values, true, false and unknown, and WHERE keeps a row only when its condition is true. That one rule produces all of SQL's NULL surprises:

SELECT name FROM products WHERE discount_pct = NULL;      -- 0 rows: "= NULL" is always unknown
SELECT name FROM products WHERE discount_pct IS NULL;    -- Wireless mouse

SELECT count(*) FROM products WHERE discount_pct > 10;    -- 1
SELECT count(*) FROM products WHERE discount_pct <= 10;   -- 2, and 1 + 2 is not 4

The logical operators follow the rule "if the answer could go either way, it's unknown":

ExpressionResultWhy
NULL = NULLunknownTwo unknown values might or might not be equal
true AND NULLunknownDepends on the unknown side
false AND NULLfalseFalse whatever the unknown is
true OR NULLtrueTrue whatever the unknown is
false OR NULLunknownDepends on the unknown side
NOT NULL (the value)unknownThe opposite of unknown is unknown
x IS NULLtrue or falseAsks about NULL-ness itself, never unknown
x IS DISTINCT FROM ytrue or falseLike <>, but treats two NULLs as equal

Sorting needs a rule too. PostgreSQL treats NULL as larger than every value, so NULLs come last in ascending order and first in descending order. Say what you mean with NULLS FIRST or NULLS LAST; MySQL and SQL Server use the opposite default, so explicit is also portable.

The "customers who never ordered" report that came back empty

A common production bug: a marketing job looks for customers with no orders using WHERE customer_id NOT IN (SELECT customer_id FROM orders). It works for months. Then guest checkout ships, and guest orders are stored with customer_id = NULL. Overnight the report returns zero rows. x NOT IN (1, 2, NULL) means x <> 1 AND x <> 2 AND x <> NULL, and the last part is unknown for every x, so the whole condition is never true. The PostgreSQL wiki's "Don't Do This" page lists exactly this. The fix is NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id), which ignores the NULLs and is planned as an efficient anti-join (Chapter 5).

⚠️
Common mistakes
  • WHERE col = NULL. It's never true. Use IS NULL / IS NOT NULL.
  • NOT IN over a list or subquery that can contain NULL. Returns nothing. Use NOT EXISTS.
  • LIMIT without ORDER BY, or with an ORDER BY that has ties. The rows you get aren't guaranteed; add a unique column as the last sort key.
  • Integer division. price_cents / 100 drops the cents. Divide by 100.0 or cast to numeric.
  • Double quotes around strings. WHERE category = "input" looks for a column named input and fails.
🎤
Interview drill

Explain it simply: A table has 100 rows. WHERE score > 50 returns 40 and WHERE score <= 50 returns 45. Where are the other 15?

How a strong answer sounds
They have score IS NULL. Comparing NULL with anything gives unknown, not true or false, and WHERE only keeps rows where the condition is true, so those 15 rows fail both conditions. To include them I'd write WHERE score <= 50 OR score IS NULL, or coalesce(score, 0) <= 50 if treating "no score" as zero is genuinely right for the business, which is a decision, not a fix.

Deeper: Why does WHERE id NOT IN (SELECT manager_id FROM employees) return no rows, and how do you fix it?

How a strong answer sounds
The CEO has no manager, so manager_id contains a NULL. NOT IN expands to a chain of <> comparisons joined by AND, and id <> NULL is unknown, so the condition is never true for any row. NOT EXISTS (SELECT 1 FROM employees e WHERE e.manager_id = x.id) is correct because a NULL simply never matches; PostgreSQL also plans it as an anti-join. Filtering WHERE manager_id IS NOT NULL inside the subquery works too, but NOT EXISTS is the habit that doesn't depend on remembering.

🧠 Key takeaways

  • PostgreSQL is a server; psql is a client. \d table and \timing are the commands you'll use most.
  • Clauses are evaluated FROM → WHERE → SELECT → ORDER BY → LIMIT, which decides where aliases are visible.
  • Without ORDER BY, row order is undefined, and so is which rows LIMIT keeps.
  • NULL means unknown; comparisons with it are unknown, and WHERE keeps only true rows.
  • Use IS NULL, IS DISTINCT FROM and NOT EXISTS; avoid = NULL and NOT IN over nullable data.
  • PostgreSQL sorts NULLs last ascending and first descending; say NULLS FIRST/LAST when it matters.

Check your understanding

What does SELECT name FROM products WHERE discount_pct = NULL return?

Comparing anything with NULL using = yields unknown, and WHERE keeps only true rows. Use IS NULL.

Why does SELECT price_cents / 100.0 AS price FROM products WHERE price > 10 fail?

The logical order is FROM, WHERE, SELECT, ORDER BY, LIMIT. ORDER BY can use the alias; WHERE has to repeat the expression.

In PostgreSQL, where do NULLs appear with ORDER BY discount_pct DESC?

PostgreSQL treats NULL as the largest value: last when ascending, first when descending. NULLS FIRST / NULLS LAST overrides it.

x NOT IN (1, 2, NULL) is true for which values of x?

It expands to x <> 1 AND x <> 2 AND x <> NULL. The last term is always unknown, so the AND can be false or unknown but never true.

What is false AND NULL?

An AND with a false side is false whatever the other side is. Only when the answer depends on the unknown side is it unknown.
