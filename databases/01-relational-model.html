The Relational Model

In 1970 an IBM researcher, Edgar F. Codd, proposed that programs should stop navigating through stored data and instead describe the data they want. The database would work out how to fetch it. Every system in this course, from PostgreSQL to the distributed SQL engines in Chapter 36, descends from that idea. This chapter explains what problem it solved, what "declarative" buys you and what it costs, how a schema differs from the data in it, and what a database interview actually tests, with a map of where this course covers each part.

Before Codd: programs that walked pointers

The databases of the 1960s were navigational. IBM's IMS, built to track the parts list of the Apollo programme, stored records in a hierarchy: a customer record owned its order records, which owned their line items. The CODASYL "network" databases allowed more general links. Either way, a program found data by starting at an entry point and following stored pointers, record by record, along paths the database designer had built in advance:

// navigational style (pseudo-code in the spirit of IMS / CODASYL)
customer = FIND_FIRST(CUSTOMER, city = "London")
while customer:
    order = FIND_FIRST_CHILD(customer, ORDER)          // follow the owner → member pointer
    while order:
        if order.total > 100: emit(customer.name, order.id)
        order = FIND_NEXT_CHILD(order)
    customer = FIND_NEXT(CUSTOMER, city = "London")

This was fast for the questions the hierarchy was built for. It was miserable for anything else. "Which customers ordered product X?" runs against the grain of a customer → order → item hierarchy, so the program had to scan everything. Worse, the program encoded the storage structure: reorganise the records, add an access path, split a file, and the programs that walked the old paths had to be rewritten.

Codd's idea: data independence

Codd's 1970 paper, "A Relational Model of Data for Large Shared Data Banks", opened with the goal: users should be protected from having to know how data is organised in the machine. His proposal had three parts:

  • One structure for everything: data is a collection of relations (tables) of values. Relationships are expressed by matching values, such as orders.customer_id = customers.customer_id, not by stored pointers.
  • A high-level language over those relations (the algebra and calculus of P7), so a query states what is wanted.
  • The system decides how. Indexes, file layout and access paths become the database's business, invisible to the query.

The payoff is data independence, in two forms:

Physical data independenceLogical data independence
What can changeHow data is stored: indexes, file layout, partitions, compression, the disk itselfThe logical schema: tables split or merged, columns added
What stays the sameEvery query, unchangedExisting queries, through views that present the old shape
ExampleCREATE INDEX makes a report 100× faster with no code changeSplit customers into customers + addresses, keep a customers_v1 view
How well real systems deliver itVery wellPartly: views help, but writes through views and app assumptions limit it

Declarative vs imperative: what you gain and what you give up

  
SQL is declarative: a query is a description of the result. The query planner turns it into an execution plan (which indexes, which join algorithm, in what order) using statistics about the data. The same query can, and should, get a different plan when the data changes. Here is the division of labour on one query:

  
  
The trade-off is real. You gain portability across data sizes, short code, and an optimiser that knows things you don't (how many rows match, which pages are cached). You give up direct control, so when the planner misjudges, usually because its statistics are wrong, a query that ran in 5 ms can suddenly take a minute. Much of the Intermediate level is about seeing what the planner decided (EXPLAIN, Chapter 17) and giving it what it needs to decide well. That's the job; it's still a far better deal than hand-writing access paths.

From a research paper to every company's database
IBM had a successful navigational product, IMS, and was slow to bet against it. Its research lab built System R (1974–79) to test whether a relational system could be fast enough; it produced the language SEQUEL, renamed SQL, and the first cost-based optimiser, described in Patricia Selinger's 1979 paper that query planners still follow. Meanwhile a small company reading IBM's published papers shipped the first commercial SQL database in 1979: Oracle. Berkeley's Ingres project (Michael Stonebraker) led to Postgres in the 1980s, the ancestor of PostgreSQL. The pattern of an idea proven in research and adopted from published papers repeats throughout this course, from Google's Bigtable to Amazon's Dynamo.

  


  
Schema and instance

  
A schema is the description: the tables, their columns and types, keys and constraints. An instance (the database state) is the data in it at one moment. The schema changes rarely and deliberately, through DDL (data definition language: CREATE, ALTER, DROP); the instance changes constantly, through DML (data manipulation language: INSERT, UPDATE, DELETE). Changing a schema safely while the instance is live and huge is its own skill (Chapter 34).

  
One of Codd's later rules for relational systems says the database should describe itself with the same relational structures. PostgreSQL does: the schema is stored in system tables you can query like any other:


SELECT column_name, data_type, is_nullable
FROM   information_schema.columns          -- the SQL-standard view of the catalog
WHERE  table_name = 'orders'
ORDER BY ordinal_position;

SELECT relname, reltuples::bigint AS estimated_rows, relpages
FROM   pg_class                            -- PostgreSQL's own catalog, including the planner's statistics
WHERE  relname = 'orders';

  
The word "schema" has a second meaning in PostgreSQL: a namespace inside a database (public, billing, analytics), so that billing.invoices and analytics.invoices can coexist. Context tells you which meaning is intended.

Common mistakes

    
    
      
  • Thinking in loops. Fetching rows into the application and filtering or joining there throws away the planner and usually most of the speed.
    • 
      
  • Assuming a query has one plan forever. Plans change as data and statistics change, which is usually good and occasionally the cause of an incident.
    • 
      
  • Writing SQL that depends on physical order. No ORDER BY, no order: that's data independence working as designed.
    • 
      
  • Treating "relational" as "has tables". The core of the model is relationships by value and a declarative language over them.

Interview drill

    
Explain it simply: What does it mean that SQL is declarative, and why does it matter?

    
How a strong answer sounds
A SQL query describes the result, not the steps to compute it. The database's planner chooses the steps: which indexes to use, which join algorithm, in what order, based on statistics about the data. That gives data independence: I can add an index, partition a table or let it grow a thousandfold and the query text doesn't change; the planner picks a new plan. The cost is less direct control, so when estimates are wrong a plan can be bad, and I need EXPLAIN to see and fix that.

    
Deeper: What's the difference between physical and logical data independence? Give an example of each.

    
How a strong answer sounds
Physical data independence means storage changes don't affect queries: adding a B-tree index, moving to partitioned tables or changing the fillfactor leaves every query valid, and the planner adapts. Logical data independence means schema changes don't affect existing applications: if I split customers into customers and addresses, a view named like the old table can present the old shape so old queries keep working. Relational databases deliver the first very well; the second only partly, because views have limits on writes and applications often depend on the exact shape.

  


  

    
🧠 Key takeaways

    
    
      
  • Navigational databases made programs follow stored pointers, so storage changes broke code.
    • 
      
  • Codd's relational model: relations of values, relationships by matching values, a high-level language over them.
    • 
      
  • Physical data independence: storage changes, queries don't. Logical independence: views shield schema changes, partly.
    • 
      
  • SQL says what; the planner decides how, from statistics. You trade control for adaptability.
    • 
      
  • Schema = the description (DDL); instance = the data (DML); PostgreSQL stores its schema in queryable catalog tables.
    • 
      
  • Interviews test SQL, schema design, performance, concurrency, internals and scaling.

Programs walked from parent to child records along predefined paths, so they depended on how the data was stored.

    


    

      
You add an index and a report gets 100× faster with no code change. Which property is that?

      

        
        
        
        
      

      
A change to storage and access paths left the query unchanged; the planner simply chose a better plan.

    


    

      
What is the main cost of SQL being declarative?

      

        
        
        
        
      

      
The planner usually chooses well, but when its statistics mislead it you need EXPLAIN to see what it did and why.

    


    

      
Which statement is DDL?

      

        
        
        
        
      

      
DDL (CREATE, ALTER, DROP) changes the schema. UPDATE, DELETE and INSERT are DML and change the instance.

    


    

      
Where does PostgreSQL keep the definitions of your tables and columns?

      

        
        
        
        
      

      
The catalog is itself relational. information_schema is the SQL-standard view over it; pg_class also holds planner statistics like reltuples.
