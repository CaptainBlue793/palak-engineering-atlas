Python & psycopg

Most SQL isn't typed into psql; it's sent by application code. This chapter uses psycopg 3, the standard PostgreSQL driver for Python, to connect, run queries, read results and control transactions. One habit matters more than everything else here: values go to the database as parameters, never pasted into the SQL string. It's the difference between a search box and a remote control for your database.

  • Connect with a connection string and run queries with a cursor
  • Pass values as parameters and explain exactly why that stops SQL injection
  • Compose dynamic table or column names safely with psycopg.sql
  • Fetch results efficiently, including results too big for memory
  • Control transactions: psycopg's default, autocommit, and conn.transaction()

Connecting and running a query

import psycopg

DSN = "postgresql://app:secret@localhost:5432/shop"     # or set PGHOST, PGUSER... and pass ""

with psycopg.connect(DSN) as conn:                        # commits on success, rolls back on error, closes
    with conn.cursor() as cur:
        cur.execute(
            "SELECT product_id, name, price_cents FROM products WHERE category = %s ORDER BY name",
            ("input",),                                    # a tuple of parameters, even for one value
        )
        for product_id, name, price_cents in cur:          # iterate rows as tuples
            print(product_id, name, price_cents / 100)

A connection is one session on the server (one backend process, as you saw in P2). A cursor runs statements on it and holds their results. psycopg converts types both ways: integer and bigint become int, numeric becomes Decimal, timestamptz becomes a time-zone-aware datetime, jsonb becomes dict/list, and NULL becomes None.

Parameters, and why string formatting is dangerous

The placeholder %s looks like Python string formatting, but it isn't: psycopg never puts the value into the SQL text. In psycopg 3 the SQL is sent with $1-style placeholders and the values travel separately in the protocol, so the server parses the SQL before it ever sees the data. Data can't change the shape of a query that has already been parsed.

What can't be a parameter

  
Parameters stand for values. Identifiers (table and column names), keywords and ASC/DESC can't be parameters, because the server needs them to parse the statement. When those must be dynamic, such as a "sort by" dropdown, build them with psycopg.sql, which quotes identifiers correctly, and check them against an allow-list:


from psycopg import sql

SORTABLE = {"name", "price_cents", "created_at"}

def list_products(cur, category: str, sort: str):
    if sort not in SORTABLE:
        raise ValueError(f"cannot sort by {sort!r}")
    query = sql.SQL("SELECT product_id, name FROM products WHERE category = %s ORDER BY {}").format(
        sql.Identifier(sort))                          # quoted as an identifier: "price_cents"
    cur.execute(query, (category,))                       # the value is still a parameter

Fetching results


from psycopg.rows import dict_row

with conn.cursor(row_factory=dict_row) as cur:
    cur.execute("SELECT product_id, name FROM products WHERE product_id = %s", (42,))
    row = cur.fetchone()                  # {'product_id': 42, 'name': 'Trackpad'} or None

# A huge result: a named (server-side) cursor streams it in chunks instead of loading it all
with conn.cursor(name="export") as cur:
    cur.itersize = 10_000
    cur.execute("SELECT order_id, total_cents FROM orders")
    for order_id, total in cur:            # fetched 10,000 rows per round trip
        write_line(order_id, total)

  
An ordinary cursor receives the whole result into client memory when execute returns, even if you then call fetchone. For a 50-million-row export that's an out-of-memory crash. A named cursor keeps the result on the server and fetches it in batches. If you only need a few rows, say so in SQL with WHERE and LIMIT, not by fetching everything and filtering in Python.


  
Transactions from application code

  
psycopg 3 is not in autocommit mode by default: the first statement on a connection silently starts a transaction, and nothing is permanent until you commit. The with psycopg.connect(...) block commits when it ends normally and rolls back if an exception escapes. For an explicit unit of work inside a longer-lived connection, use conn.transaction():


def transfer(conn, src: int, dst: int, cents: int) -> None:
    with conn.transaction():                           # BEGIN … COMMIT, or ROLLBACK on exception
        cur = conn.execute(
            "UPDATE accounts SET balance_cents = balance_cents - %s "
            "WHERE account_id = %s AND balance_cents >= %s", (cents, src, cents))
        if cur.rowcount != 1:
            raise InsufficientFunds(src)                   # rolls back: nothing was debited
        conn.execute("UPDATE accounts SET balance_cents = balance_cents + %s WHERE account_id = %s",
                     (cents, dst))

  
  
Set autocommit=True (psycopg.connect(DSN, autocommit=True)) for scripts that run single independent statements, and for commands that refuse to run inside a transaction, such as CREATE INDEX CONCURRENTLY and VACUUM. What a transaction actually guarantees is Chapter 10.

TalkTalk, 2015: a textbook injection, a £400,000 fine
In October 2015 attackers used SQL injection against legacy web pages that UK telecoms company TalkTalk had inherited from an acquisition, and extracted personal data of about 157,000 customers, including some bank account details. The vulnerable pages built queries from request input. The UK Information Commissioner's Office fined the company a then-record £400,000, noting that the technique was well known, that the company had been warned by two earlier attacks, and that the fix was standard practice. Parameterised queries in every code path, including old ones nobody owns any more, are that standard practice.

Common mistakes

    
    
      
  • f-strings or + to build SQL with values. Injection, and broken queries for names like O'Brien.
    • 
      
  • Quoting the placeholder: WHERE email = '%s'. With parameters, write %s bare; psycopg handles types.
    • 
      
  • Passing a bare value instead of a tuple: (email) is just email; you need (email,).
    • 
      
  • Forgetting to commit. Without the with block, changes disappear when the connection closes.
    • 
      
  • Holding a transaction open across slow work. "idle in transaction" sessions block DDL and VACUUM.

Interview drill

    
Explain it simply: What is SQL injection and how do parameterised queries prevent it?

    
How a strong answer sounds
SQL injection happens when user input is pasted into SQL text, so characters in the input, like a quote, change the structure of the query; x' OR '1'='1 turns a lookup into "return every row". Parameterised queries send the SQL with placeholders and the values separately; the server parses the statement first, so a value can only ever be a value, never code. It also fixes legitimate data like O'Brien. For things that can't be parameters, like column names, I use the driver's identifier quoting plus an allow-list.

    
Deeper: Your service's database shows hundreds of connections "idle in transaction". What's happening and why does it matter?

    
How a strong answer sounds
The application started transactions and isn't finishing them: typically a driver in non-autocommit mode where code runs a SELECT and never commits, or a transaction held open while it calls another service. Each one holds a connection, possibly row locks that block other writers and DDL, and an old snapshot that stops VACUUM removing dead rows, so tables bloat. I'd find the code path from pg_stat_activity (query and application_name), scope transactions tightly with conn.transaction(), and set idle_in_transaction_session_timeout as a safety net.

Why can't you write ORDER BY %s and pass a column name as a parameter?

A script runs cur.execute("UPDATE ...") on a plain psycopg.connect() connection and then exits without committing. What happens to the update?

      

        
        
        
        
      

      
psycopg 3 isn't in autocommit mode by default. Without commit() (or leaving a with-connect block normally), the transaction is discarded.

    


    

      
You need to export 50 million rows from Python without running out of memory. What do you use?

      

        
        
        
        
      

      
An ordinary cursor receives the whole result when execute() returns, whatever fetch method you call afterwards. A named cursor keeps it on the server. COPY TO STDOUT is the other good option.

    


    

      
What does the input x' OR '1'='1 do when formatted into WHERE email = '{input}'?

      

        
        
        
        
      

      
The query becomes WHERE email = 'x' OR '1'='1', and '1'='1' is always true. With a parameter, the whole input is one string compared with email and matches nothing.
