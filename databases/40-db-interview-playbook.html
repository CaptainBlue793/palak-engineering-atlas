Database Interview Playbook

Database questions turn up in nearly every engineering interview, and in several forms: a SQL exercise, a schema to design, "how does an index work?", a system-design round where the storage choice has to be defended. The material is everything in the thirty-nine chapters before this one, and it needs a different skill from learning it: finding the right two minutes of it under pressure, in an order someone can follow, without the remark that undoes the rest. Interviewers hear the same few wrong statements many times a week and listen for them. This chapter maps the questions to the chapters, gives a shape for answers that works for almost any of them, and collects the traps.

  • Know which questions each kind of interview asks, and which chapters answer them
  • Give a two-minute explanation of an index: what it is, why it is fast, what it costs, when not to add one
  • Answer isolation questions with a concrete anomaly, not a recited table
  • Argue a choice between relational and non-relational storage from the workload
  • Recognise the trick questions, and the statements that mark a weak answer

The shape of a good answer

Conceptual questions, the kind that begin "how does" or "what is", are marked on four things, and a good answer supplies them in this order.

PartWhat it showsFor "what is an index?"
1. What it is, in one sentenceThat you can be preciseA separate sorted structure that maps a column's values to the rows that hold them
2. How it worksThat you understand the mechanism and aren't recitingA B-tree: a lookup descends three or four pages where a scan would read every row
3. What it costsThat you know nothing is free. This is the part most candidates omitEvery write to the table has to update it, and it takes space
4. When you wouldn'tJudgementSmall tables, columns with few distinct values, tables that are mostly written
5. One step deeper, chosen by youThat there is more behind it, and it steers the follow-up to ground you knowColumn order in a composite index, or covering indexes

Two minutes is the right length. Under a minute usually means a part was skipped. Past three, the interviewer has stopped listening and is waiting to interrupt. And one confidently wrong sentence costs more than everything correct around it gains, since it is the sentence the interviewer writes down.

Saying the simplified version is what marks an answer down. And the depth points are a choice, which is the useful thing about them: the one you mention is the one you will be asked about next.

Isolation questions

Isolation is asked about more than any other database topic, and the weak answer is a recited grid of levels against anomalies. A strong one names a concrete anomaly, says which level stops it, and says what it would do in practice.

QuestionThe core of the answer
"What are the isolation levels?"Each permits certain anomalies in exchange for less blocking and fewer aborts. Read committed: no dirty reads. Repeatable read: one snapshot for the whole transaction. Serialisable: the result matches some one-at-a-time order (Chapter 21)
"Repeatable read against serialisable?"Write skew. Two doctors each check that someone else is on call and each go off duty. Both read a consistent snapshot, and the outcome matches no serial order. Snapshot isolation allows it
"How do you stop two people buying the last ticket?"Make the check and the write one atomic statement: UPDATE … SET stock = stock - 1 WHERE stock > 0, and look at the row count. Or lock the row with SELECT … FOR UPDATE. Or a unique constraint on the seat (Chapter 22)
"How does MVCC work?"Writers create new row versions and readers see the versions visible to their snapshot, so reads and writes don't block each other. The cost is dead versions to clean up (Chapter 23)
"Optimistic or pessimistic locking?"Pessimistic takes the lock first, and suits frequent conflict. Optimistic reads a version number and makes the update conditional on it, retrying on failure, and suits rare conflict and long think time
"What is a deadlock, and how do you avoid one?"Two transactions each hold a lock the other wants. The database detects the cycle and aborts one. Take locks in a consistent order, keep transactions short, and retry (Chapter 24)
"Which level would you run in production?"The default, read committed, with explicit protection on the few paths that need it. Serialisable where an invariant spans several rows, with a retry loop, since it aborts transactions

One caution. The names of the levels don't mean the same in every database. PostgreSQL's repeatable read is snapshot isolation and prevents phantoms. MySQL's default is repeatable read with gap locks. Oracle's serialisable is snapshot isolation. Saying which database you are describing is a mark of experience.

SQL vs NoSQL done well

The question is nearly always posed as a choice between two labels, and the labels are the trap. "NoSQL" covers key-value stores, document stores, wide-column stores and graph databases, which have little in common (Chapter 30). The answer that works reasons from the workload.

Three sentences are worth having ready. "I'd start with PostgreSQL, since the data is relational and one server handles far more than this." "What would make me change is a write rate or data size beyond one machine with a simple key-based access pattern." "In practice it would be several stores: a relational system of record, a cache, and a search index kept up to date from it."

Trick questions

These are short questions with an obvious answer that is wrong, or right only in one database.

QuestionThe trapA good answer
count(*) or count(col)?"They're the same"count(col) skips NULLs. count(*) counts rows
Is NULL = NULL true?"Yes"It is unknown, and WHERE drops the row. Use IS NULL or IS NOT DISTINCT FROM
Does a unique constraint allow two NULLs?"No"In PostgreSQL, yes, since NULLs aren't equal to each other, unless declared NULLS NOT DISTINCT. SQL Server allows one
LIMIT 10 without ORDER BY returns the first ten?"Yes"Any ten. A table has no order
Will WHERE lower(email) = … use the index on email?"Yes"No. It needs an index on the expression
Is NOT IN (subquery) the same as NOT EXISTS?"Yes"One NULL in the subquery makes NOT IN return no rows
Is the primary key a clustered index?"Always"In MySQL's InnoDB the table is stored in primary-key order. In PostgreSQL the table is a heap and the primary key is an ordinary index
Does adding an index speed the query up?"Yes"Only if the planner judges it cheaper. For a filter matching a third of the table it will scan
DELETE or TRUNCATE?"Truncate is a fast delete"Truncate removes the table's files without visiting rows, takes an exclusive lock and fires no row triggers. In PostgreSQL it can still be rolled back
We have a replica. Do we need backups?"No"A replica copies a mistaken delete within a second (Chapter 35)
After COMMIT returns, is the data safe?"Yes"On that server's disk, yes. On an asynchronous replica, not yet, and a failover can lose it (Chapter 25)
Which is faster, a join or two queries?Picking oneIt depends on the row counts and the indexes. Look at the plan

The pattern in the right-hand column is the same throughout: say when the obvious answer holds, when it doesn't, and in which database. "It depends" is a weak answer by itself and a strong one when followed by what it depends on.

Stack Overflow: the standing answer to "relational doesn't scale"

When a candidate says that a relational database won't scale and reaches for a NoSQL store on the first whiteboard, the interviewer often has one site in mind. Stack Overflow, among the most visited sites on the web, published its architecture in detail in 2016, and the numbers were a surprise at the time. The whole Stack Exchange network, serving well over a billion page views a month, ran on nine web servers and four SQL Server machines, arranged as two clusters of a primary and a replica: one for Stack Overflow and one for every other site. The databases handled roughly half a billion queries a day, and their processors were mostly idle. Nothing in the design was exotic. The servers were large, with hundreds of gigabytes of memory, so that the working data sat in the buffer pool. The engineers treated performance as a feature and measured every page: the site displays, to its own developers, the SQL each page ran and how long it took. When they found the ORM generating poor queries on hot paths, they wrote a thin mapper of their own, Dapper, which runs hand-written SQL and only maps the results onto objects. Indexes were designed for the queries that mattered. Redis sat in front as a cache, and Elasticsearch handled search, each fed from the relational system of record. The team's own account makes the general point: a schema that fits the queries, indexes that match them, enough memory and attention to what the application sends will carry one relational primary to a scale that few products ever reach. The usual reasons to leave that design are a write volume or data size past one machine, or a need to survive the loss of a region, and they are worth naming as such when you give them.

⚠️
Common mistakes
  • Benefits with no costs. "Indexes make queries faster", and nothing about writes.
  • Reciting the isolation grid with no example of an anomaly.
  • "NoSQL scales, SQL doesn't." It is the most reliably marked-down sentence in a design round.
  • Answering before asking. In a design or SQL question, the access patterns and the edge cases come first.
  • Bluffing. "I haven't used that, and here is how I'd expect it to work" is a good answer. A confident guess that is wrong is the worst one.
  • Not saying which database. Defaults, isolation levels and index behaviour all differ between them.

Interview drill

Explain it simply: What does ACID mean?

How a strong answer sounds
It is the set of guarantees a transaction gives. Atomicity: all of the transaction's changes happen or none do, so a transfer can't debit one account without crediting the other; the database achieves it by being able to undo or ignore the work of a transaction that didn't commit. Consistency: a transaction takes the database from one valid state to another, where valid means the declared constraints hold, such as foreign keys and checks; it is partly the database's job and partly the application's. Isolation: concurrent transactions don't see each other's unfinished work, to a degree set by the isolation level, with serialisable meaning the result is as if they had run one after another. Durability: once commit returns, the change survives a crash, which is done by writing it to the write-ahead log and flushing that to disk before acknowledging. I'd add two caveats that matter in practice: most databases default to an isolation level weaker than serialisable, so anomalies such as lost updates are possible unless you guard against them, and durability on one machine is not the same as durability after a failover to an asynchronous replica.

Deeper: You're designing the storage for a chat application. SQL or NoSQL?

How a strong answer sounds
I'd first ask about scale and access patterns, since that decides it. The data has two parts with different characters. Users, channels, memberships and permissions are relational, small, read constantly and need constraints and transactions: a relational database, without much debate. Messages are different: append-mostly, enormous in volume, and read by one pattern almost exclusively, the most recent N messages in a channel, paged backwards. At small or medium scale, tens of millions of messages, I'd keep them in PostgreSQL too, in a table with an index on (channel_id, message_id), probably partitioned by time; one system is simpler to run, and it will cope. At very large scale, billions of messages and tens of thousands of writes a second, the message store is a good fit for a wide-column store such as Cassandra or ScyllaDB: partition by channel plus a time bucket, cluster by message ID descending, and the main query is a single-partition range read, with writes spread across nodes. What I'd give up is ad-hoc queries, joins and cross-partition transactions, which messages don't need; search would go to a separate search index. I'd also note the known problems: hot partitions for very busy channels, which the time bucket limits, and tombstones from deletes. So the answer is both, split by what each part of the data needs, and I'd begin with one relational database until the message volume justifies the second system.

🧠 Key takeaways

  • Database questions fall under nine headings. Know which your interview will lean on.
  • Shape every conceptual answer the same way: what it is, how it works, what it costs, when you wouldn't, and one step deeper.
  • Two minutes. Costs and limits are what separate a strong answer from a correct one.
  • Answer isolation questions with a concrete anomaly and what you would do about it.
  • For storage choices, reason from access patterns, default to relational, and name what would change your mind.
  • For a trick question, say when the obvious answer holds and when it doesn't, and in which database.

Check your understanding

Asked "what is an index?", which part of the answer do candidates most often leave out?

Everyone gives the benefit. The cost, and when not to add one, show judgement.

Which statement about serialisable isolation is correct?

It is a guarantee about results. The database gets there with locks or conflict detection, and by aborting transactions when it must.

In a design round you are asked where to store user accounts and orders for a new shop. What is the strongest opening?

Orders and accounts are relational and transactional. The reasoning from the workload matters more than the product named.

A column has a unique constraint in PostgreSQL. How many rows may have NULL in it?

NULL isn't equal to NULL, so the rows don't conflict. NULLS NOT DISTINCT changes that.

You are asked about a feature you have never used. What is the best response?

Interviewers mark reasoning. A wrong statement given confidently casts doubt on everything else you said.
