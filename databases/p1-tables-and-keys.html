Tables, Rows & Keys

A relational database stores everything in tables: named columns, and rows that each describe one thing. The single most important decision about a table is how you tell its rows apart. That's the primary key, and every other table that refers to those rows does it through a foreign key. Get the keys right and the database can stop whole classes of bugs for you; get them wrong and you find out months later, when two customers turn out to share an "unique" identifier.

  • Describe a table as a set of rows with typed columns, and say what a row represents
  • Choose a primary key that is unique, never null and stable
  • Connect two tables with a foreign key and read the error the database raises when it's broken
  • Decide between a natural key and a surrogate key, and know where each goes wrong
  • Use a composite key for a link table such as order_items

Rows and columns

A table has a fixed list of columns, each with a name and a type, and any number of rows. Each row is one fact of the same shape: one customer, one order, one login attempt. Here is a table for the customers of a small online shop:

CREATE TABLE customers (
    customer_id bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text        NOT NULL UNIQUE,
    full_name   text        NOT NULL,
    country     char(2)     NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);

Three things about tables matter from day one:

  • Rows have no inherent order. A table is a set of rows (formally a multiset, since SQL allows duplicates when there's no key). If you want them in an order, you ask for one with ORDER BY; otherwise the database returns them however is cheapest, and that can change between runs.
  • Every value in a column has the column's type. created_at can't hold 'next Tuesday'. Types are covered properly in P4.
  • A missing value is NULL, which means "unknown", not zero or empty string. NOT NULL forbids it. P2 shows why NULL behaves strangely in comparisons.

Primary keys: telling rows apart

A primary key is the column, or combination of columns, whose value identifies exactly one row. The database enforces two rules on it: every value is unique, and none is NULL. In PostgreSQL, declaring a primary key also builds a unique B-tree index on it (named customers_pkey here), which is what makes "find customer 42" fast and what checks uniqueness on every insert.

There's a third rule the database can't enforce for you: the key should be stable. Other tables, caches, URLs and log lines all store the key. If it changes, every one of those copies is now wrong or must be updated.

INSERT INTO customers (email, full_name, country)
VALUES ('priya@example.com', 'Priya Shah', 'IN')
RETURNING customer_id;              -- the database picks the next identity value: 1

INSERT INTO customers (customer_id, email, full_name, country)
OVERRIDING SYSTEM VALUE
VALUES (1, 'other@example.com', 'Someone Else', 'GB');
-- ERROR:  duplicate key value violates unique constraint "customers_pkey"
-- DETAIL:  Key (customer_id)=(1) already exists.

A table can have several column sets that are unique. Each is a candidate key: here both customer_id and email qualify. You pick one as the primary key and declare the others UNIQUE, so the database still enforces them.

Uniqueness and NOT NULL are checked by the database on every insert. Stability isn't: nothing stops an application from changing a key, which is why the key should be something that never needs to change.

The pattern you'll find: every column that means something in the real world (a name, an email, a phone number) eventually fails one of the three tests. Names repeat. Phone numbers are optional and get recycled. Emails change. Only the meaningless user_id passes all three forever, and that's the argument for surrogate keys below.

Foreign keys: rows that point at rows

Orders belong to customers. Rather than copying the customer's name and email into every order, the order stores the customer's key. A foreign key constraint tells the database that every orders.customer_id must exist as a customers.customer_id:

CREATE TABLE orders (
    order_id    bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint      NOT NULL REFERENCES customers (customer_id),
    status      text        NOT NULL DEFAULT 'pending',
    created_at  timestamptz NOT NULL DEFAULT now()
);

INSERT INTO orders (customer_id) VALUES (999);
-- ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
-- DETAIL:  Key (customer_id)=(999) is not present in table "customers".

The table holding the foreign key (orders) is the child or referencing table; the one it points at (customers) is the parent or referenced table. Natural keys vs surrogate keys

A natural key is data that already identifies the thing in the real world: an email, an ISBN, a country code, a vehicle registration. A surrogate key is an identifier the database invents, with no meaning outside it: an identity column (1, 2, 3…) or a UUID. Most production schemas use surrogate primary keys and keep natural keys as UNIQUE constraints, so they're still enforced but are free to change.

The identity column is the default answer for a table living in one database. UUIDs win when IDs must be created before the row reaches the database (an offline mobile app) or across many databases without a central counter; prefer time-ordered UUIDv7 so new keys land near each other in the index. The Social Security number 40,000 people shared

US Social Security numbers look like the perfect natural key for a person: issued by the government, one per citizen. In 1938 a wallet manufacturer put a sample card in its wallets showing a real number, 078-05-1120, belonging to an employee's secretary. Over the following decades more than 40,000 people reported it as their own. Add numbers reissued after deaths, typos at data entry, and people with none at all (visitors, newborns, non-citizens), and any system using SSN as a primary key ends up with duplicate keys, missing keys and keys that change. The fix is the standard one: a surrogate person_id as the primary key, and the SSN as an ordinary column, encrypted, possibly NULL, and deliberately not unique.

Composite keys for link tables

Some rows are identified by a combination of values. An order contains many products, and a product appears in many orders: a many-to-many relationship. It's stored as a link table whose primary key is both foreign keys together:

CREATE TABLE order_items (
    order_id    bigint  NOT NULL REFERENCES orders,
    product_id  bigint  NOT NULL REFERENCES products,
    quantity    integer NOT NULL CHECK (quantity > 0),
    unit_cents  bigint  NOT NULL,              -- the price at the time of the order
    PRIMARY KEY (order_id, product_id)       -- one line per product per order
);

The composite key says something a surrogate order_item_id alone wouldn't: the same product can't appear on two separate lines of one order. Column order matters too, because the key's index is sorted by order_id first, which is exactly what "show me the lines of order 7" needs. Chapter 9 explains why.

⚠️
Common mistakes
  • A table with no primary key. Duplicate rows become possible and impossible to tell apart; logical replication in PostgreSQL can't even replicate updates and deletes on it without extra configuration.
  • Using an email or username as the primary key. The day a user changes it, every referencing row must change too.
  • Dropping the UNIQUE constraint when adding a surrogate key. Now the database happily stores two accounts for priya@example.com.
  • Leaving out the foreign key "for speed". Orphaned rows appear and nothing notices until a report doesn't add up.
  • Relying on row order without ORDER BY. It looks stable in development and changes after the first update or vacuum in production.

Interview drill

Explain it simply: What makes a good primary key, and would you use email for a users table?

How a strong answer sounds
A primary key must be unique and never null, which the database enforces, and it should be stable and small, which it can't enforce. Email fails stability: people change addresses, and every table, cache and URL that stored the old one would need updating. I'd use a surrogate bigint identity column as the primary key, or a UUIDv7 if IDs are generated outside the database, and keep email as a UNIQUE NOT NULL column (often on lower(email)) so duplicate accounts are still rejected.

Deeper: How would you model students enrolling in courses, and what's the primary key of the link table?

How a strong answer sounds
It's many-to-many, so three tables: students, courses and enrolments(student_id REFERENCES students, course_id REFERENCES courses, enrolled_at, grade). The natural primary key of enrolments is (student_id, course_id), which also enforces "enrolled at most once". The key's index serves "courses for a student"; for "students in a course" I'd add an index on (course_id, student_id). If re-enrolling in a later term is allowed, the term becomes part of the key: (student_id, course_id, term).

🧠 Key takeaways

  • A table is a set of rows with typed columns; rows have no order unless you ask with ORDER BY.
  • A primary key is unique and not null (enforced) and should be stable and small (not enforced).
  • A foreign key makes the database reject rows that point at nothing; the check is an index lookup on the parent.
  • Surrogate keys (identity or UUIDv7) are the default; keep natural keys as UNIQUE constraints.
  • Link tables for many-to-many relationships use a composite primary key of the two foreign keys.

Check your understanding

Which two properties does PostgreSQL enforce for every primary key?

The database checks uniqueness (through the key's unique index) and rejects NULLs. Stability is a design choice nothing enforces.

INSERT INTO orders (customer_id) VALUES (999) fails with "violates foreign key constraint". What does that mean?

A foreign key requires every value in the child column to exist as a key in the parent table. The DETAIL line says exactly that: Key (customer_id)=(999) is not present in table "customers".

Why is email a poor primary key for a users table, even if every user has a unique one?

Keys get copied everywhere. A key that changes turns one update into many. Keep email as a UNIQUE column and use a surrogate key.

What is the most natural primary key for order_items(order_id, product_id, quantity, unit_cents), where a product appears at most once per order?

Neither foreign key is unique on its own: an order has many lines, and a product is in many orders. The pair is unique, and as the key it also enforces "one line per product per order".

You run SELECT * FROM customers twice and get the rows in different orders. Why?

Rows have no inherent order. Updates, VACUUM and parallel or synchronised scans can all change the order rows come back in. Only ORDER BY guarantees one.
