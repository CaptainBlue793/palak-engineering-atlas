Topological Sort

Think of getting dressed: socks before shoes, shirt before jacket. A topological order lines up the nodes of a directed graph so that every edge points forward — every “do this before that” rule is respected. Such an order exists exactly when the graph has no cycle (is acyclic). That is why topological sort and cycle detection are really the same algorithm seen from two sides. There are two ways to write it: DFS with a stack, and Kahn's algorithm with indegrees. Learn both, because each one answers different follow-up questions.

  • Write DFS toposort and explain why the answer is the order in which nodes finish, reversed
  • Write Kahn's algorithm and use the length of its output as a cycle test
  • Choose between them based on what the problem asks next
  • Produce the lexicographically smallest valid order (the one that comes first in dictionary order)
  • Solve longest path in a DAG (a directed graph with no cycles) — easy only because of this ordering

What it is, and when it exists

Why care? Any time things depend on other things, someone has to pick an order that respects the dependencies. A build tool must compile a library before the program that uses it. A package manager must install a package's dependencies first. A spreadsheet must compute cell A1 before the cell whose formula reads A1. A university must let you take Calculus I before Calculus II. All of these are the same problem, and in interviews it usually shows up as "course schedule".

You are given a directed graph. Put the nodes in a line so that for every edge u → v, u comes before v. For example, with edges 0→1, 0→2, 1→3, 2→3, the order 0, 1, 2, 3 works: 0 is before 1 and 2, and both are before 3. So does 0, 2, 1, 3. But 1, 0, 2, 3 does not, because the edge 0→1 points backwards. Three facts to know:

✅

Exists iff acyclic

“Iff” means “if and only if”. A cycle a→b→c→a would need a before b, b before c, and c before a — impossible. So a DAG (directed graph with no cycles) always has an order, and a graph with a cycle never does.

🔀

Usually not unique

Two nodes with no path between them can go in either order, so there are often many correct answers. Problems usually ask for any valid order. Asking for “the smallest” one needs a heap.

🎯

It makes DP on a DAG trivial

If you handle nodes in topological order, every node that comes before it (its predecessors) is already finished. So longest path, path counting and DAG shortest path all become one straight pass over the nodes.

Method 1: DFS with a stack

Run DFS. When a node finishes — that is, after everything reachable from it has been fully explored — push it onto a stack. At the end, pop everything off the stack. The order they come out in is a topological order.

Why "finish" and not "first visit"? A node finishes only after every node it points to has finished. So in finish order, each node appears after everything that must come after it — which is exactly the reverse of what we want. Reversing it (which popping a stack does for free) fixes that. Dry run on the example DAG 0 → [1,2], 1 → [3], 2 → [3]:

  1. DFS(0) visits 0 and goes to 1. DFS(1) goes to 3. Node 3 has no outgoing edges, so it finishes first: push 3. Stack (bottom to top): [3].
  2. Back in 1: no more neighbours, so 1 finishes: push 1. Stack: [3, 1].
  3. Back in 0: next neighbour is 2. DFS(2) sees 3 is already visited (and finished), so 2 finishes: push 2. Stack: [3, 1, 2].
  4. 0 finishes last: push 0. Stack: [3, 1, 2, 0].

Popping from the top gives 0, 2, 1, 3. Check it: every edge points left to right. The driver loop then tries nodes 1, 2, 3, but they are all visited, so nothing more happens.

toposort — DFS with a finish stackO(V + E)O(V)
// Push AFTER the loop over neighbours — that is what makes it post-order.
void DFS(unordered_map<int,vector<int>> &graph,int node,vector<bool> &visited,stack<int> &st){
	if(visited[node])return;

	visited[node]=true;
	for(auto &neighbour:graph[node]){
		if(!visited[neighbour])
		DFS(graph,neighbour,visited,st);
	}

	st.push(node);            // everything reachable from node is already on the stack
}
vector<int> toposort(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(int i=0;i<edges.size();i++){
		int u=edges[i][0];
		int v=edges[i][1];
		graph[u].push_back(v);
		// graph[v].push_back(u); -> This is for Undirected Edges
	}

	stack<int> st;
	vector<bool> visited(N,false);

	for(int i=0;i<N;i++){
		if(!visited[i]){
			DFS(graph,i,visited,st);
		}
	}

	vector<int> ans;
	while(!st.empty()){
		ans.push_back(st.top());
		st.pop();
	}

	return ans;
}
The commented-out reverse edge matters here as a reminder. Topological sort makes no sense on an undirected graph, so that line must stay commented out. If you uncomment it by accident, the code does not crash — it quietly returns a wrong answer.
🧾
Why reversed finish order is a valid topological order

Take any edge u → v. We need to show that u finishes after v. There are two cases.

  • v is unvisited when we look at the edge. We recurse into it, so v finishes before we return and finish u ✓.
  • v is already visited. In a DAG it must also be finished. If v were visited but not finished, v would be an ancestor of u on the current recursion path. Then the edge u → v would close a cycle — and a DAG has none ✓.

Either way, v is pushed before u. So u sits above v on the stack and comes out first. Notice that the proof fails exactly when there is a cycle. That is why DFS toposort quietly gives a wrong answer on a graph with a cycle, unless you add the recursion-stack check from Chapter 27.

Method 2: Kahn's algorithm

Count each node's indegree — the number of edges pointing into it, i.e. how many prerequisites it still waits on. Then repeat: take a node with indegree 0 (it waits on nothing), add it to the output, and subtract 1 from each of its neighbours' indegrees. When a neighbour's count hits 0, all its prerequisites are done and it becomes available. It is like a to-do list where a task unlocks once everything it depends on is ticked off.

toposort — Kahn's algorithmO(V + E)O(V)
vector<int> toposort(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(int i=0;i<edges.size();i++){
		int u=edges[i][0];
		int v=edges[i][1];
		graph[u].push_back(v);
		// graph[v].push_back(u); -> This is for Undirected Edges
	}

	vector<int> indegree(N,0);
	for(auto &it:graph){
		for(int node:it.second){
			indegree[node]++;
		}
	}

	queue<int> q;
	vector<int> ans;
	for(int i=0;i<N;i++){
		if(indegree[i]==0)
		q.push(i);
	}

	while(!q.empty()){
		int node=q.front();
		q.pop();
		ans.push_back(node);

		for(auto &neighbour:graph[node]){
			indegree[neighbour]--;          // this prerequisite is satisfied

			if(indegree[neighbour]==0)
			q.push(neighbour);
		}
	}

	if(ans.size()!=N)return {};      // CYCLE: some nodes never reached indegree 0

	return ans;
}
The size check gives you cycle detection for free. Nodes in a cycle block each other forever, because each one waits on another member. Their indegree never reaches zero, so they are never output. If fewer than N nodes come out, the leftover nodes are in a cycle (or come after one). That one line is why Kahn is usually the better choice for "can this schedule be completed?" problems.
✍️
My convention: build the indegree array by iterating the adjacency list, not the edge list

for(auto &it:graph) for(int node:it.second) indegree[node]++; counts each stored edge exactly once. So it stays correct even if you removed duplicate edges or filtered some out while building the graph. Re-scanning the original edges vector could disagree with what actually went into the graph. It also keeps the directed/undirected choice in one place: whatever you pushed is what gets counted. One detail: on an unordered_map this only visits nodes that have outgoing edges. That is fine, because a node with no outgoing edges adds nothing to anyone's indegree.

What "process the queue level by level" means. For "minimum number of semesters" (you can take any number of courses at once, as long as their prerequisites are done), each semester is one batch: everything currently in the queue. Record int sz=q.size();, pop exactly sz nodes, push whatever becomes ready, and add 1 to the semester count. On the example DAG that gives three batches — {0}, then {1, 2}, then {3} — so the answer is 3. This is the same trick as level-order traversal of a tree (Chapter 17).

Lexicographically smallest order

"Lexicographically smallest" means: of all valid orders, the one that is smallest when you compare them like words in a dictionary — first element as small as possible, then the second, and so on. Example: edges 2→0 and 1→3. The ready set at the start is {1, 2}. A plain queue might give 2, 1, 0, 3 or 2, 0, 1, 3, both valid. With a min-heap you take 1 first (the smallest ready node), which unlocks 3, and the heap now holds {2, 3}. Take 2, which unlocks 0; the heap holds {0, 3}. Take 0, then 3. The result 1, 2, 0, 3 is valid and is the smallest possible. Note that just sorting would give 0, 1, 2, 3, which puts 0 before 2 and breaks the edge 2→0.

Kahn with a min-heapO((V + E) log V)O(V)
// Among all currently-available nodes, always take the smallest.
// Greedy is correct: taking a larger available node first can never let
// a smaller one come earlier, since availability only grows over time.
vector<int> smallestTopo(int N,vector<vector<int>> &edges){
	vector<vector<int>> graph(N);
	vector<int> indegree(N,0);

	for(auto &e:edges){
		graph[e[0]].push_back(e[1]);
		indegree[e[1]]++;
	}

	priority_queue<int,vector<int>,greater<int>> pq;   // min-heap (Ch 15)
	for(int i=0;i<N;i++){
		if(indegree[i]==0)
		pq.push(i);
	}

	vector<int> ans;
	while(!pq.empty()){
		int node=pq.top();
		pq.pop();
		ans.push_back(node);

		for(int neighbour:graph[node]){
			indegree[neighbour]--;

			if(indegree[neighbour]==0)
			pq.push(neighbour);
		}
	}

	return ans.size()==N?ans:vector<int>{};
}
Only the container changes, and the extra log factor is the whole cost. This is not the same as "sort the output". The set of available nodes changes every time you output one, so you must pick the smallest again at every step. Sorting the result of plain Kahn breaks the dependencies and gives an invalid order.

Longest path in a DAG

In a general graph, longest path is NP-hard (no known fast algorithm). In a DAG it takes linear time, and the only reason is the ordering. Handle nodes in topological order, and every node that points into the current one already has its final answer.

Small example with edge weights: 0→1 (3), 0→2 (2), 1→3 (4), 2→3 (6). A topological order is 0, 1, 2, 3. Start with dp = [0, 0, 0, 0] (every node is a path of length 0 on its own). Process 0: dp[1] = max(0, 0+3) = 3, dp[2] = max(0, 0+2) = 2. Process 1: dp[3] = max(0, 3+4) = 7. Process 2: dp[3] = max(7, 2+6) = 8. Process 3: no outgoing edges. The longest path is 8, via 0→2→3. Improving dp[v] through one edge like this is called relaxing the edge, the word the code comment uses. When we reached node 3, both of its predecessors were already final — the topological order guaranteed that. You meet this DP-in-order idea again, in full, from Chapter 38 on.

longest path in a DAG — DP over a topological orderO(V + E)O(V)
// dp[v] = longest path ENDING at v. Because we process in topological order,
// every u with an edge u->v has already been finalised when we relax it.
int longestPath(int N,vector<vector<int>> &edges){
	vector<vector<pair<int,int>>> graph(N);      // {neighbour,weight}
	vector<int> indegree(N,0);

	for(auto &e:edges){
		graph[e[0]].push_back({e[1],e[2]});
		indegree[e[1]]++;
	}

	queue<int> q;
	for(int i=0;i<N;i++){
		if(indegree[i]==0)
		q.push(i);
	}

	vector<int> dp(N,0);
	int best=0;

	while(!q.empty()){
		int node=q.front();
		q.pop();
		best=max(best,dp[node]);

		for(auto &[neighbour,weight]:graph[node]){
			dp[neighbour]=max(dp[neighbour],dp[node]+weight);   // relax

			indegree[neighbour]--;
			if(indegree[neighbour]==0)
			q.push(neighbour);
		}
	}

	return best;
}
The same code shape solves four problems. Change max to min and you have DAG shortest path — which works with negative weights, unlike Dijkstra. Change it to dp[neighbour] += dp[node] and you are counting paths. Add a cost per node and it becomes critical-path scheduling. All of them are linear only because the topological order means one pass is enough. Without it you would have to repeat passes until nothing changes, which is exactly what Bellman-Ford does (Chapter 30).

🔤
Alien dictionary — where the hard part is building the graph

You get a list of words sorted in an unknown alphabet's order, and must work out the alphabet. The toposort is the easy half. Building the graph has two traps. First, comparing two neighbouring words gives you exactly one edge, from the first position where they differ. Nothing after that position tells you anything, so you must break after adding it. Second, if a word is a prefix of the word before it ("abc" before "ab"), the input is invalid. You must return failure instead of quietly producing an order. Then run Kahn. If the output is shorter than the alphabet, the ordering contradicts itself. Most failures on this problem are in building the graph, not in the sort — a general lesson for graph problems wrapped in a story.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 KAHN COUNTS
If Kahn emits fewer than V nodes, a cycle exists. That makes "is this schedulable?" and "give me an order" the same function with one extra check.
💡 LEX SMALLEST
Swap the queue for a priority queue and Kahn gives the lexicographically smallest topological order. A one-word change to the container.
💡 DAG DP
Longest path, path counts and critical paths are all DP in topological order — which is exactly the order that guarantees every dependency is already computed.
⚠️
Common mistakes
  • Pushing the reverse edge. Topological sort only makes sense on directed graphs. An undirected edge makes the output meaningless.
  • Forgetting the ans.size() != N check in Kahn. On a graph with a cycle you return a partial order that looks believable.
  • Using DFS toposort on a graph that might have a cycle. It quietly produces a wrong order — you need the recursion-stack check (Chapter 27).
  • Pushing in DFS before recursing. That gives preorder (nodes in the order you first reach them), which is not a topological order.
  • Not reversing the DFS order. With a stack, popping already gives the reversed finish order, which is right. But if you build a vector with push_back inside DFS and forget to reverse it, you get the exact opposite order.
  • Forgetting the driver loop over all nodes. A DAG can be in several pieces, or have several sources (nodes nothing points into).
  • Sorting plain Kahn's output to get the lexicographically smallest order. You must use a min-heap during the algorithm. Sorting afterwards breaks the dependencies.
  • Only checking indegree == 0 for the starting queue and never again. A node becomes available the moment its last prerequisite is output, so check after every decrement.
  • Building indegrees from the raw edge list when the graph was deduplicated. Count what actually went into the adjacency list.

Interview drill

Warm-up: Course schedule — can all courses be finished given prerequisites? Then: return a valid order.

How a strong answer sounds
I model each course as a node. Each prerequisite pair becomes a directed edge from the prerequisite to the course that needs it. A valid completion order is then exactly a topological order, and one exists if and only if the graph has no cycle. I would use Kahn's algorithm because it answers both parts at once. Compute every node's indegree and push all indegree-zero nodes into a queue. Then repeatedly pop a node, append it to the output, and decrement each neighbour's indegree, pushing any that reach zero. At the end, if the output has fewer than N courses, the missing ones are in a cycle or come after one. Every node in a cycle waits on another member, so none of their indegrees ever reaches zero. So ans.size() == N answers "is it possible?", and ans itself is the order — both from the same O(V + E) pass. I would mention the DFS alternative: push each node onto a stack when it finishes, then reverse. But it needs an extra recursion-stack array to detect the cycle, and it risks a stack overflow at 10⁵ nodes, so Kahn is the better default here. If the follow-up asked for the lexicographically smallest order, I would swap the queue for a min-heap. If it asked for the minimum number of semesters with unlimited parallel courses, I would process the queue one whole level at a time and count the levels.

Deeper: Why is longest path linear in a DAG but NP-hard in a general graph?

How a strong answer sounds
Because a topological order gives the DP a valid order to fill in its values, and cycles destroy that. In a DAG I define dp[v] as the longest path ending at v, and process nodes in topological order. By the time I reach v, every u with an edge u→v is already final. So dp[v] = max over predecessors of dp[u] + weight(u,v) is computed from settled values in a single pass. No node is revisited, so it is O(V + E). A general graph has no such order. A cycle means v's value depends on u's and u's depends on v's, so there is nowhere to start. Worse, the problem itself changes. With a cycle of positive weight you could go round forever, so "longest path" only makes sense if you forbid repeating vertices. "Longest simple path" (no repeated vertices) is NP-hard. In fact the Hamiltonian path problem — is there a path visiting every vertex once? — turns directly into it: such a path exists exactly when the longest simple path has V−1 edges. So having no cycles is not just convenient; it puts the problem in a different complexity class. The same idea explains why DAG shortest path handles negative weights in one pass, while general graphs need Bellman-Ford's V−1 rounds of relaxation.

🧠 Key takeaways

  • A topological order exists exactly when the graph is a DAG (no cycles), so toposort and cycle detection are one algorithm.
  • DFS pushes a node when it finishes, and popping the stack gives the answer. The proof fails exactly when a cycle exists.
  • Kahn outputs nodes whose indegree is zero. ans.size() != N gives cycle detection for free, which is why Kahn is the default.
  • Swap Kahn's queue for a min-heap to get the lexicographically smallest order. Sorting the output afterwards is wrong.
  • Running DP in topological order makes longest path, path counting and DAG shortest path (even with negative weights) all linear.

Check your understanding

In Kahn's algorithm, what does it mean if the output contains fewer than N nodes?

This is the free cycle test and the main reason Kahn is the default. A graph in several pieces is handled fine, because each piece has its own indegree-zero starting nodes.

In DFS toposort, when is a node pushed onto the stack?

This is post-order. Pushing on finish guarantees that everything reachable from the node is already on the stack below it, so popping gives a valid order. Pushing before recursing gives preorder, which is not a topological order.

You need the lexicographically smallest topological order. What changes?

The set of available nodes changes every time you output one, so you must pick the smallest again at each step. Sorting the finished output ignores the dependencies and produces an invalid order.

Why is longest path solvable in O(V + E) on a DAG but NP-hard in general?

No cycles means the DP has a valid order to compute its values in. With a cycle, v depends on u and u depends on v. The problem becomes longest simple path, and the NP-hard Hamiltonian path problem turns directly into it.

Running DFS toposort on a graph that does contain a cycle produces what?

The visited array stops the recursion, so it ends normally and outputs all N nodes. But the correctness proof needed every visited neighbour to be already finished, and a cycle breaks that. Kahn's size check catches this for free. DFS needs the instack array from Chapter 27.
