Segment Trees & Lazy Propagation

A prefix-sum array answers range questions in O(1), but changing one value costs O(n) (Chapter 6). A segment tree does both in O(log n). It also works for more than addition: minimum, maximum, GCD — any associative operation (one where the grouping does not matter). On top of that, lazy propagation lets you update a whole range in O(log n). It does this by leaving a note — a promise — on a node instead of doing the work right away. This is the first structure in the course you would really struggle to invent yourself. So the focus here is on why each piece exists.

  • Write the query and single-point update from one three-case recursion
  • Show why a range query touches only O(log n) nodes
  • Add lazy propagation, and say exactly when a pending “tag” must be pushed down to the children
  • Pick the merge function for a new problem, and know what cannot be merged

Why it exists

A typical problem: an array of 10⁵ numbers, then 10⁵ operations, each either "change a[i]" or "what is the minimum of a[l..r]?". A plain array spends up to 10⁵ steps per query, so 10¹⁰ in total: far too slow. A prefix array makes queries fast but has to be rebuilt after every change, which is just as slow. A segment tree does each operation in about 17 steps (log₂ 10⁵), so about 2 × 10⁶ in total.

The one-line justification

Use a segment tree when you have both range queries and updates, and the operation cannot be undone. (Sum can be undone by subtracting; minimum cannot.) Range minimum with updates is the classic case. There is no “subtract” for minimum, so prefix arrays and Fenwick trees both fail. If the operation is a sum, a Fenwick tree does the same job in a third of the code, and runs much faster in practice. So always ask first whether a Fenwick tree is enough.

The structure

Each node is in charge of a range of the array. It stores the combined value of that range — for example, its sum. The root covers [0, n−1]. Each inner node splits its range in half and gives one half to each child. A leaf covers a single element. Think of a company chart: each manager knows the total for their whole team, so you rarely need to ask every employee.

A concrete sum tree over a = [5, 3, 8, 6]. The leaves hold 5, 3, 8, 6. Their parents hold [0,1] = 5 + 3 = 8 and [2,3] = 8 + 6 = 14. The root holds [0,3] = 8 + 14 = 22. In the array, numbering nodes from 1: tree[1] = 22, tree[2] = 8, tree[3] = 14, and tree[4..7] = 5, 3, 8, 6. Node i's children are at 2i and 2i+1, exactly like a heap, so no pointers are needed.

  • Query the sum of [1, 3]. Root [0,3] only partly overlaps, so split. [0,1] also partly overlaps, so split again: [0,0] is outside (return 0), [1,1] is fully inside (return 3). [2,3] is fully inside, so return its stored 14 without going deeper. Total 0 + 3 + 14 = 17, which is 3 + 8 + 6.
  • Update a[2] = 1. Walk down to the leaf for index 2 and set it to 1. On the way back up, recompute each parent: [2,3] becomes 1 + 6 = 7, and the root becomes 8 + 7 = 15. Only the nodes on one root-to-leaf path change, so it costs O(log n).

// Array-based, 1-indexed nodes: node covers [lo,hi], children are 2*node and 2*node+1.
// Same index arithmetic as a heap (Chapter 15) — no pointers.
class SegTree{
	vector<long long> tree;
	int n;

	// The ONLY problem-specific line. Change it and you change the structure.
	long long merge(long long a,long long b){ return a+b; }
	long long identity(){ return 0; }        // must satisfy merge(x,identity)==x

	void build(vector<int> &a,int node,int lo,int hi){
		if(lo==hi){
			tree[node]=a[lo];
			return;
		}

		int mid=lo+(hi-lo)/2;

		build(a,2*node,lo,mid);
		build(a,2*node+1,mid+1,hi);

		tree[node]=merge(tree[2*node],tree[2*node+1]);
	}

	// THREE CASES — this shape is the whole algorithm.
	long long query(int node,int lo,int hi,int l,int r){
		if(r<lo or hi<l)return identity();       // 1. no overlap
		if(l<=lo and hi<=r)return tree[node];      // 2. fully inside

		int mid=lo+(hi-lo)/2;                       // 3. partial — split

		return merge(query(2*node,lo,mid,l,r),
		             query(2*node+1,mid+1,hi,l,r));
	}

	void update(int node,int lo,int hi,int i,int val){
		if(lo==hi){
			tree[node]=val;
			return;
		}

		int mid=lo+(hi-lo)/2;

		if(i<=mid)update(2*node,lo,mid,i,val);
		else update(2*node+1,mid+1,hi,i,val);

		tree[node]=merge(tree[2*node],tree[2*node+1]);   // recompute on the way up
	}

public:
	SegTree(vector<int> &a){
		n=a.size();
		tree.assign(4*n,identity());     // 4n is the safe size — see below
		build(a,1,0,n-1);
	}

	long long query(int l,int r){ return query(1,0,n-1,l,r); }
	void update(int i,int val){ update(1,0,n-1,i,val); }
};
Everything specific to the problem lives in two lines: merge and identity. The identity is the “does nothing” value — merging with it leaves any value unchanged, like adding 0. Change the two lines to min and LLONG_MAX, and you have a range-minimum tree with no other edits. That is why it is worth memorising once, instead of working it out again for each problem.
📐
Why 4n, not 2n

A perfect binary tree with n leaves needs 2n−1 nodes. But when n is not a power of two, the splits are uneven. The bottom level is not filled neatly from left to right. So with nodes numbered from 1, the largest index used can go past 2n. The exact bound is 2 · 2^⌈log₂ n⌉, which is under 4n for every n. The worst case is n = 2^k + 1 (just past a power of two), where that bound gets close to 4n. A tiny example: with n = 6, the right half [3,5] is node 3, it splits into [3,4] (node 6) and [5,5] (node 7), and [3,4] splits into nodes 12 and 13. Index 13 is already past 2n = 12. 4n is the standard safe size, and the extra memory is tiny, so use it and stop worrying. A too-small array does not crash. It writes past the end and silently corrupts nearby data.

🧾
Why a range query touches only O(log n) nodes

Claim: at each level of the tree, at most two nodes only partly overlap the query range. Here is why. The nodes on one level cut the array into blocks that sit side by side. A continuous range [l, r] can only cut through one block at its left end and one block at its right end. Every block strictly between them is fully inside, so it returns its stored value at once. Every block outside does not overlap at all, so it returns the identity at once. Only the two cut blocks need to recurse. There are log n levels, with at most 2 recursing nodes per level. So the query visits O(log n) nodes and merges O(log n) values. The same argument limits range updates with lazy propagation.

Choosing the merge function

The tree works for any operation that is associative: merge(merge(a,b),c) == merge(a,merge(b,c)). In plain words, it must not matter how you group the items. That matters because the tree decides the grouping, and you cannot control it. The operation does not need to be commutative (order-independent). But if it is not, you must always keep the left child on the left.

Two quick checks make this concrete. Subtraction is not associative: (5 − 3) − 1 = 1, but 5 − (3 − 1) = 3, so a tree that groups differently gives a different answer. Median cannot be merged at all: the halves [1, 2, 9] and [3, 4, 5] have medians 2 and 4, and the whole has median 3.5. The halves [1, 2, 3] and [0, 4, 5] also have medians 2 and 4, but the whole has median 2.5. Same inputs to merge, different correct outputs, so no merge function can exist.

My convention: isolate merge and identity, and test the identity law

Put the operation in a named function, even when it is one character. And check that merge(x, identity) == x for every x. That rule is what makes the "no overlap" case correct: returning the identity must not change the result. A wrong identity — say, 0 for a minimum tree — quietly breaks every query that touches a boundary, and the wrong answer still looks believable. After wrong sizing, it is the most common segment-tree bug.

🧩
The maximum-subarray segment tree, because it shows what "store more per node" buys

Take the problem "maximum subarray sum in range [l,r], with updates". Here each node stores four values, and the merge combines them:

struct Node{
	long long total;    // sum of the whole range
	long long pre;      // best sum starting at the left edge
	long long suf;      // best sum ending at the right edge
	long long best;     // best sum anywhere inside
};
Node merge(Node L,Node R){
	Node M;
	M.total=L.total+R.total;
	M.pre=max(L.pre,L.total+R.pre);
	M.suf=max(R.suf,R.total+L.suf);
	M.best=max({L.best,R.best,L.suf+R.pre});   // the crossing case

	return M;
}

The general lesson: if a value cannot be merged directly, look for a few extra helper values that can be. The key idea here: the best subarray either sits entirely in one half, or it crosses the middle. The crossing case is exactly left.suffix + right.prefix. That is the same "peaks here or passes through" split as the tree diameter in Chapter 18.

Lazy propagation: range updates in O(log n)

Say you want to “add 5 to every element in [l, r]”. With a plain segment tree, that means updating up to n leaves — O(n log n). Lazy propagation fixes this with one idea: when a node's range is entirely inside the update, do not touch its children. Write a promise on the node and stop.

The promise is only paid later, if some query or update ever goes below that node. It is like a manager holding a memo — “everyone on my team gets +5” — and only passing it on when someone actually asks a team member. Two operations handle this:

Why the plain approach is O(n log n): adding 5 to all of [0, n−1] means changing all n leaves, and each leaf change updates log n ancestors. With lazy tags, the same update touches only the root: it is fully inside, so the root records the promise and stops.

applyLazy — settle the debt here

Update this node's stored value to include the pending tag. Then copy the tag onto its children (without touching their children). For a sum tree with a "+v to all" tag, the node's value goes up by v × rangeLength. That length factor is essential, and easy to forget.

push — settle before descending

This runs at the top of every query and update, before recursing. If this node has a tag, apply it and clear it. This guarantees you never read a child while a promise above it is still unpaid.

lazy segment tree — range add, range sumO(log n) bothO(8n)
class LazySeg{
	vector<long long> tree,lazy;
	int n;

	// Settle this node's own pending tag, and hand the tag to its children.
	void applyLazy(int node,int lo,int hi){
		if(lazy[node]==0)return;

		tree[node]+=lazy[node]*(hi-lo+1);   // LENGTH FACTOR — easy to forget

		if(lo!=hi){
			lazy[2*node]+=lazy[node];         // += not =, tags ACCUMULATE
			lazy[2*node+1]+=lazy[node];
		}

		lazy[node]=0;
	}

	void rangeAdd(int node,int lo,int hi,int l,int r,long long v){
		applyLazy(node,lo,hi);              // ALWAYS settle before looking

		if(r<lo or hi<l)return;

		if(l<=lo and hi<=r){
			lazy[node]+=v;                   // the PROMISE: stop here
			applyLazy(node,lo,hi);          // pay it into this node's own value
			return;
		}

		int mid=lo+(hi-lo)/2;

		rangeAdd(2*node,lo,mid,l,r,v);
		rangeAdd(2*node+1,mid+1,hi,l,r,v);

		tree[node]=tree[2*node]+tree[2*node+1];
	}

	long long query(int node,int lo,int hi,int l,int r){
		applyLazy(node,lo,hi);              // same first line — no exceptions

		if(r<lo or hi<l)return 0;
		if(l<=lo and hi<=r)return tree[node];

		int mid=lo+(hi-lo)/2;

		return query(2*node,lo,mid,l,r)
		      +query(2*node+1,mid+1,hi,l,r);
	}

public:
	LazySeg(int size){
		n=size;
		tree.assign(4*n,0);
		lazy.assign(4*n,0);
	}

	void rangeAdd(int l,int r,long long v){ rangeAdd(1,0,n-1,l,r,v); }
	long long query(int l,int r){ return query(1,0,n-1,l,r); }
};
Three lines carry all the risk. (1) applyLazy is the first statement of every recursive function, with no exceptions — otherwise you read an out-of-date value. (2) The length factor (hi-lo+1): a tag of "+v per element" adds v × count to a sum. (3) lazy[child] += lazy[node], not =. A child may already owe something, and overwriting would lose it.

A trace with the code above. Start from the sum tree over [5, 3, 8, 6] (root 22, children 8 and 14), with every tag 0. (The class above starts from all zeros; picture it filled by a build like the one in the first codebox.)

  1. rangeAdd(0, 1, +5). The root [0,3] partly overlaps, so recurse. Node [0,1] is fully inside: set its tag to 5, then applyLazy adds 5 × 2 = 10 to its value (8 → 18), copies the tag 5 onto both leaves, and clears its own tag. Node [2,3] does not overlap. Back at the root: 18 + 14 = 32. The leaves still show 5 and 3, but each carries an unpaid +5.
  2. query(1, 1). At the root and at [0,1] there are no tags, and both partly overlap, so recurse. At leaf [0,0] the first line runs applyLazy (5 → 10), then it returns 0 because it is outside the query. At leaf [1,1], applyLazy turns 3 into 8, and it is fully inside, so it returns 8. That is correct: 3 + 5 = 8.

The promise was paid only on the path the query actually walked. If no query ever reached those leaves, the work would never be done at all.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 CHANGE ONE FUNCTION
A segment tree is generic over merge and its identity. Sum, min, max and gcd are the same tree with two lines swapped — write it once, parameterise it.
💡 LAZY = DEFERRED
Lazy propagation is just "I promise to apply this later". The hard part is never the push-down; it is composing two pending tags correctly.
⛔ SIZE 4N
Allocate 4*n, not 2*n. The recursive layout wastes slots when n is not a power of two, and the overflow is silent.
🚨
Assignment tags do not compose like addition tags

“Add v to a range” combines neatly: two pending adds are the same as one add of their sum, so += is correct. “Set a range to v” does not combine that way. The later assignment must win, and it must also cancel any pending add below it. So a tree with assignment tags needs a separate hasAssign flag. Combining a new tag with an old one becomes a set of cases. An assign on top of anything replaces it. An add on top of an assign just changes the assigned value. If a problem mixes range-assign and range-add, this combining logic is the real difficulty, not the tree itself. Get it wrong, and the bug only shows up when two updates overlap in a particular order.

Variants worth knowing about

🔎

Descend on the tree

“Find the first index ≥ l with value ≥ x” in O(log n) instead of O(log² n). Do not binary search using repeated queries. Instead, walk down the tree once, and use each node's stored maximum to decide which child can hold the answer.

📚

Merge-sort tree

Each node stores a sorted copy of its range. It answers “how many values in [l,r] are < x” in O(log² n). It uses O(n log n) space and is static — no updates.

🕰️

Persistent segment tree

Each update creates O(log n) new nodes and reuses the rest, so you can still query every past version. Used for “k-th smallest in a range” and for offline range problems (where you know all queries up front).

🌐

2D segment tree / BIT

A tree of trees, giving O(log² n) rectangle queries with updates. It is heavy, so try a 2D Fenwick tree (Chapter 24) first.

🗜️

Implicit / dynamic

When indices go up to 10⁹, you cannot allocate 4n. Create nodes only when they are first touched. Or use coordinate compression first: map the positions you actually use to 0, 1, 2, ….

🧊

Iterative (bottom-up)

A segment tree without recursion, in about 15 lines, and about twice as fast. Elegant, but it is hard to add lazy propagation to it. Learn the recursive one first.

⚠️
Common mistakes
  • Making the array size 2n. Uneven splits push indices past 2n. Use 4n — otherwise you get a silent write past the end of the array.
  • Wrong identity value. Returning 0 from a minimum tree's no-overlap case makes every query that touches a boundary wrong — in a believable way.
  • Not calling applyLazy at the top of every function. You read an out-of-date value that a pending tag was about to change.
  • Forgetting the length factor. A "+v per element" tag adds v × (hi−lo+1) to a sum node, not v.
  • Overwriting a child's lazy tag with =. Tags add up. Use += for add tags.
  • Treating assignment tags like add tags. They do not combine the same way. You need a flag and clear rules for combining them.
  • Using int for sums. A segment tree over 10⁵ values of size 10⁹ overflows at once.
  • Mixing node numbering that starts at 0 with numbering that starts at 1. Starting at 1, the children are 2n and 2n+1. Starting at 0, they are 2n+1 and 2n+2. Pick one.
  • Building a segment tree when a Fenwick tree would do. For plain prefix sums, a Fenwick tree is a third of the code and much faster.
  • Assuming any operation works. It must be associative. Median and mode are not.

Interview drill

Warm-up: Why is a segment tree query O(log n), given that a range can span most of the array?

How a strong answer sounds
Because at every level of the tree, at most two nodes partly overlap the query range, and only those nodes recurse. The nodes on any one level cut the array into side-by-side blocks. A continuous range [l, r] can only cut through one block at its left end and one at its right end. Every block strictly between them is fully inside, so the recursion returns that node's stored value at once without going deeper. Every block outside does not overlap at all, so it returns the identity at once. So at most two nodes per level are "still recursing". With log n levels, that is O(log n) nodes visited and O(log n) merges. Notice this is exactly why the operation must be associative: the tree decides how values are grouped, and I do not control that grouping. The same two-per-level argument also limits a lazy range update, since an update has the same three-case structure.

Deeper: Explain lazy propagation and the exact moment a tag must be pushed down.

How a strong answer sounds
Without lazy propagation, a range update has to reach every leaf in the range, so it is O(n) instead of O(log n). The key idea: when a node's range is entirely inside the update range, I can compute that node's new total directly. For a sum with "+v to all", it goes up by v times the range length. I do not need to touch its children at all, as long as I record that they still owe the update. That record is the lazy tag. It is a promise: the children are out of date, but the debt is written down above them. The invariant (the rule that must always hold) is: a node's stored value is correct, while its children may be out of date by exactly the tags recorded at or above them. So the push happens at one exact moment: the first statement of every query and every update, before I read tree[node] or recurse. The push applies the node's own tag to its value, gives a copy of the tag to both children, and clears it. Three details cause the bugs. First, the length factor, because a per-element tag grows with the count. Second, using += when handing the tag to a child — the child may already owe something, and = would lose it. Third, assignment tags do not combine by adding. They need a separate flag and clear rules for how a new tag combines with a pending one. That is usually the real difficulty when a problem mixes range-assign with range-add.

🧠 Key takeaways

  • Use a segment tree when you need range queries and updates for an operation you cannot undo (like min). Otherwise a Fenwick tree is smaller and faster.
  • Three cases: no overlap → identity, fully inside → stored value, partial → recurse and merge.
  • It is O(log n) because at most two nodes per level partly overlap the range, and only those recurse.
  • Size 4n, verify merge(x, identity) == x, and use long long.
  • Lazy propagation stores a promise instead of doing the work now. Push at the top of every function, multiply by the range length, and add tags together with +=.

Check your understanding

Why size the segment tree array 4n rather than 2n?

The exact bound is 2·2^⌈log₂ n⌉, which stays under 4n. An array that is too small does not crash — it writes past the end and corrupts nearby memory. So use 4n and stop worrying about it.

In a range-minimum segment tree, what must the "no overlap" case return?

The identity must satisfy merge(x, identity) == x. Returning 0 from a minimum tree makes every query that touches a boundary return 0. That is wrong, but believable enough to survive testing.

In a lazy segment tree, when must a pending tag be pushed down?

The rule is: a node's own value is correct, while its children may be out of date by the tags above them. Pushing first guarantees you never read an out-of-date child.

A lazy tag of "add v to every element" is applied to a node covering [lo, hi]. How much does that node's sum increase?

This is the length factor. Forget it, and leaves stay correct while every inner node goes wrong. You get answers that are right for single-element queries and wrong for everything else.

Which of these can a segment tree not answer for arbitrary ranges?

A segment tree needs an associative merge. But you cannot work out the median of two parts combined from just the median of each part. Maximum subarray can be merged, once each node stores total, prefix, suffix and best. Median needs a merge-sort tree or Mo's algorithm.
