Segment Trees & Lazy Propagation

A prefix-sum array gives O(1) range queries but O(n) updates (Chapter 6). A segment tree gives O(log n) for both, and it generalises past addition to minimum, maximum, GCD — anything associative. Then lazy propagation adds O(log n) range updates by storing a promise at a node instead of doing the work. This is the first structure in the course you would genuinely struggle to invent, so the emphasis is on why each piece exists.

  • Build a segment tree in an array and explain the 4n sizing
  • Write query and point update from the three-case recursion
  • Prove that a range query touches only O(log n) nodes
  • Add lazy propagation, and say exactly when a tag must be pushed down
  • Choose the merge function for a new problem, and know what cannot be merged

The one-line justification

Reach for a segment tree when you have both range queries and updates, and the operation is not invertible. Range minimum with updates is the canonical case: there is no “subtract” for minimum, so prefix arrays and Fenwick trees are both out. If the operation is a sum, a Fenwick tree does the same job in a third of the code with a much smaller constant — so always ask whether Fenwick suffices first.

The structure

Each node owns a range of the array and stores the merged value of that range. The root owns [0, n−1], and each internal node splits its range in half. A leaf owns a single element.

// Array-based, 1-indexed nodes: node covers [lo,hi], children are 2*node and 2*node+1.
// Same index arithmetic as a heap (Chapter 15) — no pointers.
class SegTree{
	vector<long long> tree;
	int n;

	// The ONLY problem-specific line. Change it and you change the structure.
	long long merge(long long a,long long b){ return a+b; }
	long long identity(){ return 0; }        // must satisfy merge(x,identity)==x

	void build(vector<int> &a,int node,int lo,int hi){
		if(lo==hi){
			tree[node]=a[lo];
			return;
		}

		int mid=lo+(hi-lo)/2;

		build(a,2*node,lo,mid);
		build(a,2*node+1,mid+1,hi);

		tree[node]=merge(tree[2*node],tree[2*node+1]);
	}

	// THREE CASES — this shape is the whole algorithm.
	long long query(int node,int lo,int hi,int l,int r){
		if(r<lo or hi<l)return identity();       // 1. no overlap
		if(l<=lo and hi<=r)return tree[node];      // 2. fully inside

		int mid=lo+(hi-lo)/2;                       // 3. partial — split

		return merge(query(2*node,lo,mid,l,r),
		             query(2*node+1,mid+1,hi,l,r));
	}

	void update(int node,int lo,int hi,int i,int val){
		if(lo==hi){
			tree[node]=val;
			return;
		}

		int mid=lo+(hi-lo)/2;

		if(i<=mid)update(2*node,lo,mid,i,val);
		else update(2*node+1,mid+1,hi,i,val);

		tree[node]=merge(tree[2*node],tree[2*node+1]);   // recompute on the way up
	}

public:
	SegTree(vector<int> &a){
		n=a.size();
		tree.assign(4*n,identity());     // 4n is the safe size — see below
		build(a,1,0,n-1);
	}

	long long query(int l,int r){ return query(1,0,n-1,l,r); }
	void update(int i,int val){ update(1,0,n-1,i,val); }
};
Everything problem-specific is in two lines — merge and identity. Change them to min and LLONG_MAX and you have a range-minimum tree with no other edits. That is why this is worth memorising once rather than re-deriving per problem.
📐
Why 4n, not 2n

A perfect binary tree over n leaves needs 2n−1 nodes. But when n is not a power of two, the recursion's splits are uneven and the deepest level is not filled left-to-right — so with 1-indexed node numbering the largest index used can exceed 2n. The tight bound is 2 · 2^⌈log₂ n⌉, which is under 4n for every n. Worst case: n = 2^k + 1, which needs just over 2n levels' worth. 4n is the standard safe size and the memory is trivial, so use it and stop thinking about it — a too-small array gives an out-of-bounds write that corrupts neighbouring data rather than crashing.

🧾
Why a range query touches only O(log n) nodes

Claim: at each level of the tree, at most two nodes are partially overlapped by the query range. Reason: the nodes at a level partition the array into consecutive blocks, and a contiguous range [l, r] can only clip a block at its left edge and a block at its right edge — every block strictly between them is fully contained (so it returns immediately) and every block outside is disjoint (so it returns the identity). Only the two clipped blocks recurse. With log n levels and at most 2 recursing nodes per level, the query visits O(log n) nodes and merges O(log n) values. The same argument bounds range updates with lazy propagation.

Choosing the merge function

The tree works for any operation that is associative — merge(merge(a,b),c) == merge(a,merge(b,c)) — because the tree groups elements in a fixed nesting you do not control. It does not need to be commutative, but if it is not, you must keep the left child on the left.

My convention: isolate merge and identity, and test the identity law

Put the operation in a named function even when it is one character, and check that merge(x, identity) == x for every x. That law is what makes the "no overlap" case correct: returning the identity must not disturb the result. A wrong identity — 0 for a minimum tree, say — silently poisons every query that touches a boundary, and the answer looks plausible. It is the single most common segment-tree bug after sizing.

🧩
The maximum-subarray segment tree, because it shows what "store more per node" buys

For "maximum subarray sum in range [l,r], with updates", each node stores four values and the merge combines them:

struct Node{
	long long total;    // sum of the whole range
	long long pre;      // best sum starting at the left edge
	long long suf;      // best sum ending at the right edge
	long long best;     // best sum anywhere inside
};
Node merge(Node L,Node R){
	Node M;
	M.total=L.total+R.total;
	M.pre=max(L.pre,L.total+R.pre);
	M.suf=max(R.suf,R.total+L.suf);
	M.best=max({L.best,R.best,L.suf+R.pre});   // the crossing case

	return M;
}

The pattern generalises: if a quantity is not directly mergeable, look for a small set of auxiliary quantities that is. Here the insight is that a best subarray either lies entirely in one half or crosses the boundary — and the crossing case is exactly left.suffix + right.prefix. That is the same "peaks here or passes through" decomposition as the tree diameter in Chapter 18.

Lazy propagation: range updates in O(log n)

“Add 5 to every element in [l, r]” with a plain segment tree means updating up to n leaves — O(n log n). Lazy propagation fixes this with one idea: when a node's range is entirely inside the update, do not touch its children. Record a promise on the node and stop.

The promise is paid later, only if someone descends past that node. Two operations manage it:

applyLazy — settle the debt here

Update this node's stored value to reflect the pending tag, then record the tag on its children (without touching their children). For a sum tree with a "+v to all" tag, the node's value increases by v × rangeLength — the length factor is essential and easy to forget.

push — settle before descending

Called at the top of every query and update before recursing. If this node has a tag, apply it and clear it. This is what guarantees a child is never read while a promise above it is unpaid.

lazy segment tree — range add, range sumO(log n) bothO(8n)
class LazySeg{
	vector<long long> tree,lazy;
	int n;

	// Settle this node's own pending tag, and hand the tag to its children.
	void applyLazy(int node,int lo,int hi){
		if(lazy[node]==0)return;

		tree[node]+=lazy[node]*(hi-lo+1);   // LENGTH FACTOR — easy to forget

		if(lo!=hi){
			lazy[2*node]+=lazy[node];         // += not =, tags ACCUMULATE
			lazy[2*node+1]+=lazy[node];
		}

		lazy[node]=0;
	}

	void rangeAdd(int node,int lo,int hi,int l,int r,long long v){
		applyLazy(node,lo,hi);              // ALWAYS settle before looking

		if(r<lo or hi<l)return;

		if(l<=lo and hi<=r){
			lazy[node]+=v;                   // the PROMISE: stop here
			applyLazy(node,lo,hi);          // pay it into this node's own value
			return;
		}

		int mid=lo+(hi-lo)/2;

		rangeAdd(2*node,lo,mid,l,r,v);
		rangeAdd(2*node+1,mid+1,hi,l,r,v);

		tree[node]=tree[2*node]+tree[2*node+1];
	}

	long long query(int node,int lo,int hi,int l,int r){
		applyLazy(node,lo,hi);              // same first line — no exceptions

		if(r<lo or hi<l)return 0;
		if(l<=lo and hi<=r)return tree[node];

		int mid=lo+(hi-lo)/2;

		return query(2*node,lo,mid,l,r)
		      +query(2*node+1,mid+1,hi,l,r);
	}

public:
	LazySeg(int size){
		n=size;
		tree.assign(4*n,0);
		lazy.assign(4*n,0);
	}

	void rangeAdd(int l,int r,long long v){ rangeAdd(1,0,n-1,l,r,v); }
	long long query(int l,int r){ return query(1,0,n-1,l,r); }
};
Three lines carry all the risk. (1) applyLazy is the first statement of every recursive function — no exceptions, or you read a stale value. (2) The length factor (hi-lo+1): a tag of "+v per element" contributes v × count to a sum. (3) lazy[child] += lazy[node], not = — a child may already owe something, and overwriting loses it.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 CHANGE ONE FUNCTION
A segment tree is generic over merge and its identity. Sum, min, max and gcd are the same tree with two lines swapped — write it once, parameterise it.
💡 LAZY = DEFERRED
Lazy propagation is just "I promise to apply this later". The hard part is never the push-down; it is composing two pending tags correctly.
⛔ SIZE 4N
Allocate 4*n, not 2*n. The recursive layout wastes slots when n is not a power of two, and the overflow is silent.
🚨
Assignment tags do not compose like addition tags

“Add v to a range” composes: two pending adds are one add of their sum, so += is correct. “Assign v to a range” does not — the later assignment must win, and it must also cancel any pending add underneath it. So an assign-lazy tree needs a separate hasAssign flag, and combining a new tag with an old one becomes a case analysis: assign-over-anything replaces; add-over-assign folds into the assign's value. If a problem mixes range-assign and range-add, that composition logic is the actual difficulty, not the tree. Get it wrong and the bug appears only when two updates overlap in a particular order.

Variants worth knowing about

🔎

Descend on the tree

“Find the first index ≥ l with value ≥ x” in O(log n) rather than O(log² n): instead of binary searching over queries, walk down the tree and use each node's stored maximum to decide which child can contain the answer.

📚

Merge-sort tree

Each node stores its range sorted. Answers “how many values in [l,r] are < x” in O(log² n). O(n log n) space, and static — no updates.

🕰️

Persistent segment tree

Every update creates O(log n) new nodes and shares the rest, so all past versions remain queryable. Used for “k-th smallest in a range” and offline range problems.

🌐

2D segment tree / BIT

A tree of trees, giving O(log² n) rectangle queries with updates. Heavy — try a 2D Fenwick tree (Chapter 24) first.

🗜️

Implicit / dynamic

When indices go up to 10⁹, do not allocate 4n. Create nodes lazily as they are touched, or coordinate-compress the queried positions first.

🧊

Iterative (bottom-up)

A non-recursive segment tree in ~15 lines with a 2× smaller constant. Elegant, but it does not extend to lazy propagation easily — learn the recursive one first.

⚠️
Common mistakes
  • Sizing the array 2n. Uneven splits push indices past 2n. Use 4n; it is a silent out-of-bounds write otherwise.
  • Wrong identity value. Returning 0 from a minimum tree's no-overlap case makes every boundary-touching query wrong, plausibly.
  • Not calling applyLazy at the top of every function. You read a stale value that a pending tag was going to change.
  • Forgetting the length factor. A "+v per element" tag adds v × (hi−lo+1) to a sum node, not v.
  • Overwriting a child's lazy tag with =. Tags accumulate; use += for additive tags.
  • Treating assignment tags like additive ones. They do not compose — you need a flag and explicit combination rules.
  • Using int for sums. A segment tree over 10⁵ values of 10⁹ overflows immediately.
  • Mixing 0-indexed and 1-indexed node numbering. With 1-indexed nodes the children are 2n and 2n+1; with 0-indexed they are 2n+1 and 2n+2. Pick one.
  • Building a segment tree when a Fenwick tree would do. For plain prefix sums, Fenwick is a third of the code and much faster.
  • Assuming any operation works. It must be associative — median and mode are not.

Interview drill

Warm-up: Why is a segment tree query O(log n), given that a range can span most of the array?

How a strong answer sounds
Because at every level of the tree, at most two nodes are partially overlapped by the query range, and only partially overlapped nodes recurse. The nodes at any given level partition the array into consecutive blocks, and a contiguous range [l, r] can only clip a block at its left end and a block at its right end — every block strictly between those is fully contained, so the recursion returns that node's stored value immediately without descending, and every block outside is disjoint, so it returns the identity immediately. So the frontier of "still recursing" nodes is at most two per level, and with log n levels that is O(log n) nodes visited and O(log n) merges. It is worth noticing that this is exactly why the operation must be associative: the tree decides the grouping, so the answer is a fixed nesting of merges I do not control. And the same two-per-level argument is what bounds a lazy range update, since an update has the identical three-case structure.

Deeper: Explain lazy propagation and the exact moment a tag must be pushed down.

How a strong answer sounds
Without lazy, a range update has to reach every leaf in the range, so it is O(n) rather than O(log n). The insight is that when a node's range is entirely inside the update range, I can compute that node's new aggregate directly — for a sum with "+v to all", it increases by v times the range length — and I do not need to touch its children at all, provided I record that they still owe the update. That record is the lazy tag, and it is a promise: the children are stale, but the debt is written down above them. The invariant I must maintain is that a node's stored value is correct, while its children may be stale by exactly the tags recorded at or above them. So the push happens at one precise moment: the first statement of every query and every update, before I look at tree[node] or recurse. That applies the node's own tag to its value, hands copies of the tag to both children, and clears it. Three details carry the bugs: the length factor, because a per-element tag scales with the count; using += when handing the tag to a child, since the child may already owe something and = would lose it; and the fact that assignment tags do not compose additively — those need a separate flag and explicit rules for how a new tag combines with a pending one, which is usually the real difficulty when a problem mixes range-assign with range-add.

🧠 Key takeaways

  • Use a segment tree when you need range queries and updates for a non-invertible operation; otherwise Fenwick is smaller and faster.
  • Three cases: no overlap → identity, fully inside → stored value, partial → recurse and merge.
  • O(log n) because at most two nodes per level are partially overlapped, and only those recurse.
  • Size 4n, verify merge(x, identity) == x, and use long long.
  • Lazy propagation stores a promise instead of doing work; push at the top of every function, scale by range length, accumulate tags with +=.

Check your understanding

Why size the segment tree array 4n rather than 2n?

The tight bound is 2·2^⌈log₂ n⌉, which stays under 4n. An undersized array is an out-of-bounds write that corrupts adjacent memory rather than crashing — so use 4n and stop thinking about it.

In a range-minimum segment tree, what must the "no overlap" case return?

The identity must satisfy merge(x, identity) == x. Returning 0 from a minimum tree makes every boundary-touching query return 0 — wrong, and plausible enough to survive testing.

In a lazy segment tree, when must a pending tag be pushed down?

The invariant is that a node's own value is correct while its children may be stale by the tags above them. Pushing first is what guarantees you never read a stale child.

A lazy tag of "add v to every element" is applied to a node covering [lo, hi]. How much does that node's sum increase?

The length factor. Forgetting it makes leaves correct and every internal node wrong, which produces answers that are right for single-element queries and wrong for everything else.

Which of these can a segment tree not answer for arbitrary ranges?

A segment tree requires an associative merge, and the median of a union is not determined by the medians of the parts. Maximum subarray is mergeable once each node stores total, prefix, suffix and best. Median needs a merge-sort tree or Mo's algorithm.
