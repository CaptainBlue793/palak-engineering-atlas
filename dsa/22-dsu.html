Union-Find (DSU)

Disjoint Set Union answers exactly two questions — “are these two in the same group?” and “merge these two groups” — in effectively constant time. It is about thirty lines of code, and it is the right answer to a surprising number of problems: Kruskal's MST, connected components that arrive one at a time, cycle detection in undirected graphs, and account merging. Two optimisations do all the work, and together they produce one of the most beautiful complexity bounds in computer science.

  • Implement find and union with path compression and union by rank
  • Explain why either optimisation alone gives O(log n) and both give O(α(n))
  • Return a boolean from union so you can detect cycles for free
  • Apply DSU to grids, to Kruskal, and to “components as edges arrive”
  • Know the variants: size tracking, weighted DSU, and rollback

The idea: a forest of pointers to representatives

Each set is a tree. Every element points at its parent, and the root points at itself — so the root is the set's representative. Two elements are in the same set exactly when they have the same root.

Note what DSU deliberately does not do: it cannot split a set, list a set's members, or tell you anything about the tree's shape. It answers one question. That narrowness is why it is so fast.

The implementation

DSU — the version used throughout this courseO(α(n)) ≈ O(1)O(n)
class DSU{
	vector<int> parent,rank;
	int components;

public:
	DSU(int n){
		parent.resize(n);
		rank.resize(n,0);
		components=n;

		for(int i=0;i<n;i++){
			parent[i]=i;          // every element starts as its own root
		}
	}

	// PATH COMPRESSION: repoint every node on the path straight at the root.
	// The assignment inside the return is the whole optimisation.
	int find(int x){
		if(x==parent[x])return x;

		return parent[x]=find(parent[x]);
	}

	// UNION BY RANK: hang the shallower tree under the deeper one.
	// Returns false if they were ALREADY connected — which is how you detect a cycle.
	bool unite(int x,int y){
		int px=find(x);
		int py=find(y);

		if(px==py)return false;      // same set already: this edge closes a cycle

		if(rank[px]>rank[py]){
			parent[py]=px;
		}else if(rank[px]<rank[py]){
			parent[px]=py;
		}else{
			parent[py]=px;
			rank[px]++;            // equal ranks: height grows by exactly one
		}

		components--;

		return true;
	}

	bool connected(int x,int y){ return find(x)==find(y); }
	int count(){ return components; }
};
return parent[x] = find(parent[x]); is the single most important line. It recurses to the root and then, on the way back out, rewrites every node on the path to point directly at it — so the next find on any of them is one step. The assignment inside the return is what does it; writing return find(parent[x]); gives you a correct but uncompressed and much slower structure.
✍️
My convention: unite returns a bool, and it is never wasted

Returning false when the two elements were already connected turns DSU into a cycle detector at zero cost. Two immediate uses:

// Kruskal's MST (Chapter 31): the boolean IS the "would this create a cycle?" test.
for(auto &[w,u,v]:edges){
	if(dsu.unite(u,v))
	total+=w;                     // added only if it connected two components
}

// Cycle detection in an undirected graph (Chapter 27):
for(auto &e:edges){
	if(!dsu.unite(e[0],e[1]))
	return true;                  // this edge joins two already-connected nodes
}

A void unite forces every caller to call connected first, which doubles the find calls and adds a line at every use site. Also note the naming: union is a C++ keyword, so the method must be called something else — unite, merge or join. That is a compile error people hit once and remember forever.

⚠️
Two naming hazards in the same class

union is a reserved word, and rank collides with std::rank if you have using namespace std; — which in a global scope can produce a genuinely confusing error. In competitive code people write rnk or sz; in a class member it is usually fine because the member name shadows. Worth knowing so the compiler message is not a mystery. Also: if you write DSU as a class rather than a struct, remember the public: — without it every member is private and the constructor is inaccessible.

Why it is effectively O(1)

🧾
Union by rank alone gives O(log n) — the clean half of the proof

Claim: a tree of rank r contains at least 2^r nodes. Proof by induction. Rank 0 is a single node, so 2⁰ = 1 ✓. Rank only increases when two trees of equal rank r merge, producing rank r+1 — and by induction each had at least 2^r nodes, so the result has at least 2^(r+1). Since the whole structure has only n nodes, no rank exceeds log₂ n, and since rank bounds height, every find is O(log n). The full O(α(n)) bound with compression added is genuinely hard — Tarjan's 1975 proof — and is not something to reproduce in an interview. Knowing the rank half, and knowing that α(n) < 5 for any n under 2^65536, is the right level of detail.

🤏
α(n) is not literally constant, and interviewers notice either way

The inverse Ackermann function grows so slowly that it is below 5 for any input you could physically store. So treat it as constant in practice, but say “effectively constant” or “O(α(n))” rather than “O(1)” — claiming true O(1) is wrong, and there is a known lower bound proving that no DSU implementation can achieve amortized O(1) for arbitrary interleaved operations. Saying "near-constant, formally inverse Ackermann" costs you three words and is precisely correct.

Where DSU is the right tool

Edges arrive one at a time and I need connectivity after each

→ DSU. BFS or DFS would be O(V+E) per query; DSU is O(α(n)) per edge. This "online" property is DSU's decisive advantage.

for(auto &e:edges) dsu.unite(e[0],e[1]);
Build an MST by adding cheapest edges

→ Kruskal with DSU (Chapter 31). The boolean return is the cycle test.

if(dsu.unite(u,v)) total+=w;
Detect a cycle in an undirected graph

→ DSU. An edge whose endpoints are already connected closes a cycle. (Directed graphs need DFS with a recursion stack — Chapter 27.)

if(!dsu.unite(u,v)) return true;
Count islands / regions in a grid

→ DSU with the cell flattened to r*cols+c, or BFS/DFS. DSU wins when cells are added incrementally.

dsu.unite(r*cols+c, nr*cols+nc);
Group things that are transitively equivalent

→ DSU. Accounts merge, equations satisfiability, similar strings, redundant connections.

dsu.unite(idOf(a), idOf(b));
I need to remove an edge, or list a set's members

→ Not DSU. It cannot split. Process the edges in reverse (offline), or use a different structure.

numIslands with DSU — the flattening patternO(rows·cols·α)O(rows·cols)
// A grid cell (r,c) becomes the integer r*cols+c — Chapter 3's flattening.
// Only check LEFT and UP: by the time we reach (r,c), right and down have
// not been processed yet, so checking them would just duplicate work.
int numIslands(vector<vector<char>> &grid){
	int rows=grid.size();
	int cols=grid[0].size();

	DSU dsu(rows*cols);
	int land=0;
	int merges=0;

	for(int r=0;r<rows;r++){
		for(int c=0;c<cols;c++){
			if(grid[r][c]!='1')continue;

			land++;

			if(r>0 and grid[r-1][c]=='1'){
				if(dsu.unite(r*cols+c,(r-1)*cols+c))merges++;
			}
			if(c>0 and grid[r][c-1]=='1'){
				if(dsu.unite(r*cols+c,r*cols+c-1))merges++;
			}
		}
	}

	return land-merges;         // each successful merge removes one island
}
land - merges instead of counting distinct roots. Every land cell starts as its own island and every successful union destroys one, so the arithmetic is exact and avoids a second pass over the grid. Note also that dsu.count() would be wrong here — it counts water cells as components too, since the DSU was sized for the whole grid.

The variants worth knowing

// Track component SIZE instead of rank. Slightly worse height bound in theory,
// same O(alpha) with compression, and you get size() for free — which many
// problems need ("largest component", "product of component sizes").
vector<int> parent,sz;

bool unite(int x,int y){
	int px=find(x);
	int py=find(y);

	if(px==py)return false;

	if(sz[px]<sz[py])swap(px,py);   // px is the bigger one

	parent[py]=px;
	sz[px]+=sz[py];

	return true;
}
int size(int x){ return sz[find(x)]; }

Use this by default. The swap makes the code shorter than the three-branch rank version, and size() is needed often enough that rank rarely earns its place.

// Store a weight on each parent edge: the value of x RELATIVE to its parent.
// Solves "a/b = 2.0, b/c = 3.0, what is a/c?" and equation-satisfiability.
vector<int> parent;
vector<double> w;      // w[x] = value(x) / value(parent[x])

// Compression must ACCUMULATE the weights along the path.
int find(int x){
	if(x==parent[x])return x;

	int root=find(parent[x]);
	w[x]*=w[parent[x]];         // fold the parent's weight into mine
	parent[x]=root;

	return root;
}
bool unite(int x,int y,double ratio){   // value(x)/value(y) = ratio
	int px=find(x);
	int py=find(y);

	if(px==py)return abs(w[x]/w[y]-ratio)<1e-9;   // consistency check

	parent[px]=py;
	w[px]=ratio*w[y]/w[x];

	return true;
}

The subtlety is in find: path compression changes each node's parent, so its stored weight — which was relative to the old parent — must be multiplied by the chain above it. Get that wrong and the answers drift silently.

// Sometimes you must UNDO unions (offline dynamic connectivity, DSU on tree).
// Rollback requires giving up path compression, because compression mutates
// nodes that were not part of this union and cannot be cheaply restored.
// So: union by size only, O(log n) per find, but every union is reversible.
vector<int> parent,sz;
vector<pair<int,int>> history;      // (child root, parent root)

int find(int x){
	while(x!=parent[x])x=parent[x];   // NO compression

	return x;
}
bool unite(int x,int y){
	int px=find(x);
	int py=find(y);

	if(px==py)return false;

	if(sz[px]<sz[py])swap(px,py);

	history.push_back({py,px});
	parent[py]=px;
	sz[px]+=sz[py];

	return true;
}
void rollback(){
	auto [child,par]=history.back();
	history.pop_back();

	sz[par]-=sz[child];
	parent[child]=child;
}

The trade is explicit: rollback costs you path compression and therefore the α(n) bound, leaving O(log n) from union by size alone. That is the right price for supporting undo, and it is used in offline dynamic connectivity and in "DSU on tree" techniques.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 BOOL FROM UNITE
Make unite return whether it actually merged. That single boolean is the cycle test in Kruskal and the redundant-edge detector, for free.
💡 GRID TO DSU
Flatten a grid cell to r*cols + c and any 2D connectivity problem becomes a 1D DSU. The same index trick works for any fixed-shape structure.
⛔ BOTH OPTIMISATIONS
Path compression and union by rank. With only one you get O(log n); with both it is effectively O(1), and the code is two extra lines.
⚠️
Common mistakes
  • Writing return find(parent[x]); without the assignment. Correct but uncompressed — you lose the entire optimisation silently.
  • Comparing x and y instead of their roots. if(x==y) tests element identity, not set membership. Always compare find(x) and find(y).
  • Naming the method union. Reserved word; use unite, merge or join.
  • Forgetting public: in a class. Everything, including the constructor, becomes inaccessible.
  • Not initialising parent[i] = i. Every element must start as its own root or find never terminates.
  • Incrementing rank on every union. It increases only when two equal ranks merge.
  • Using dsu.count() on a grid sized for every cell. It counts water cells as components too.
  • Trying to remove an edge. DSU cannot split. Process edges in reverse, or use rollback.
  • Forgetting to accumulate weights during compression in a weighted DSU. The answers drift with no error.
  • Claiming O(1). It is O(α(n)) — "effectively constant" is the accurate phrase.

Interview drill

Warm-up: Implement DSU and explain both optimisations.

How a strong answer sounds
A parent array where every element initially points at itself, so the root of a tree is the set's representative and two elements are in the same set exactly when their roots match. find walks to the root; unite finds both roots and, if they differ, hangs one under the other. Two optimisations. Path compression: return parent[x] = find(parent[x]); — the recursion reaches the root, and on the way back out every node on that path is repointed directly at it, so subsequent finds on any of them are one step. The assignment inside the return is the whole thing; omitting it leaves you with a correct but slow structure. Union by rank or size: always hang the shallower or smaller tree under the larger, so the height cannot grow unnecessarily. With rank I can prove a clean bound — rank only increases when two equal ranks merge, so a tree of rank r has at least 2^r nodes, which caps rank and therefore height at log₂ n. Together the two give amortized O(α(n)), inverse Ackermann, which is below 5 for any n you could store — so effectively constant, though I would not claim literal O(1) since a lower bound rules that out. I would also return a bool from unite, false when they were already joined, because that single boolean is the cycle test Kruskal needs.

Deeper: Islands II — land cells are added one at a time and you must report the island count after each addition. Why DSU rather than BFS?

How a strong answer sounds
Because the problem is online: I have to answer after every addition, and BFS or DFS would re-traverse the whole grid each time, giving O(k·rows·cols) for k additions. DSU handles it incrementally. I size a DSU over every cell, flattening (r,c) to r·cols+c, and keep a running island count. When a cell becomes land I increment the count, then attempt to union it with each of its four neighbours that is already land — and every union that succeeds decrements the count, because it merged two previously separate islands. Unions that return false are neighbours already in the same island, which happens often and must not be counted. The important detail is that a single new cell can merge up to four distinct islands at once, so the count can drop by three in one step — which is exactly the case a naive "increment or don't" approach gets wrong. Total cost is O(k·α) for the additions, effectively linear, and the boolean return from unite is doing all the bookkeeping. If instead the problem asked me to remove land, DSU would be the wrong tool entirely, since it cannot split a set — I would process the timeline in reverse so removals become additions, or use a rollback DSU and give up path compression.

🧠 Key takeaways

  • DSU answers only "same set?" and "merge" — and that narrowness is why it is effectively O(1).
  • return parent[x] = find(parent[x]); — the assignment inside the return is path compression.
  • Union by rank alone gives O(log n) via "a rank-r tree has ≥ 2^r nodes"; both optimisations give O(α(n)).
  • Have unite return a bool: it is Kruskal's cycle test and undirected cycle detection, for free.
  • DSU wins when edges arrive incrementally; it cannot split, so removals need reversal or rollback.

Check your understanding

What does the assignment in return parent[x] = find(parent[x]); accomplish?

The recursion reaches the root and the assignment on the way back out flattens the entire path. Writing return find(parent[x]); is correct but loses the optimisation silently.

With union by rank but no path compression, what is the amortized cost per operation?

Rank increases only when two equal ranks merge, which doubles the minimum node count — so rank, and therefore height, is bounded by log₂ n. Compression is what takes it down to inverse Ackermann.

Why should unite return a boolean?

Without it every caller must invoke connected first, doubling the find calls and adding a line at each use site. The boolean makes Kruskal a two-line loop.

Land cells are added to a grid one at a time and you must report the island count after each. Why DSU rather than BFS?

BFS is O(k·rows·cols) for k additions; DSU is O(k·α). And note a single new cell can merge up to four islands at once, so the count can drop by three in one step.

Which operation can DSU not do efficiently?

DSU only merges. For removals you either process the timeline in reverse so deletions become insertions, or use a rollback DSU — which costs you path compression and therefore the α(n) bound.
