Union-Find (DSU)

Disjoint Set Union (DSU), also called union-find, answers exactly two questions: “are these two things in the same group?” and “merge these two groups”. It answers both in effectively constant time. It is about thirty lines of code, and it solves a surprising number of problems: Kruskal's minimum spanning tree, connected components that arrive one at a time, finding cycles in undirected graphs, and merging accounts. Two small optimisations do all the work, and together they give one of the most beautiful running-time results in computer science.

  • Write find and union with path compression and union by rank
  • Explain why one optimisation alone gives O(log n), while both together give O(α(n))
  • Return a true/false value from union, so you get cycle detection for free
  • Use DSU on grids, in Kruskal's algorithm, and for “components as edges arrive”
  • Know the variants: tracking sizes, weighted DSU, and undo (rollback)

The idea: a forest of pointers to representatives

The problem it solves. Picture a social network where friendships are added one by one, and after each one someone asks "are Asha and Ben connected through any chain of friends?" You could run a BFS each time, but with 10⁵ friendships and 10⁵ questions that is about 10¹⁰ steps. DSU answers each question in a few steps, because it keeps the groups up to date as you go instead of rediscovering them.

Each group is a tree. Every element points at its parent, and the root points at itself. So the root stands for the whole group; it is the group's representative. Two elements are in the same group exactly when they have the same root.

All of it lives in one array, parent. A trace with 5 elements:

  • Start: parent = [0, 1, 2, 3, 4]. Everyone is their own root, so there are 5 groups.
  • unite(0, 1): the roots are 0 and 1, which differ. Hang 1 under 0: parent = [0, 0, 2, 3, 4]. 4 groups.
  • unite(2, 3): hang 3 under 2: parent = [0, 0, 2, 2, 4]. 3 groups.
  • unite(1, 3): find(1) walks 1 → 0, so its root is 0. find(3) walks 3 → 2, root 2. Hang 2 under 0: parent = [0, 0, 0, 2, 4]. 2 groups: {0, 1, 2, 3} and {4}.
  • connected(3, 1)? find(3) walks 3 → 2 → 0 (and, with path compression below, repoints 3 straight at 0). find(1) walks 1 → 0. Same root, so yes. connected(3, 4)? Roots 0 and 4, so no.

Notice what DSU deliberately does not do. It cannot split a group apart, list a group's members, or tell you anything about the tree's shape. It answers one question. Doing so little is exactly why it is so fast.

The implementation

DSU — the version used throughout this courseO(α(n)) ≈ O(1)O(n)
class DSU{
	vector<int> parent,rank;
	int components;

public:
	DSU(int n){
		parent.resize(n);
		rank.resize(n,0);
		components=n;

		for(int i=0;i<n;i++){
			parent[i]=i;          // every element starts as its own root
		}
	}

	// PATH COMPRESSION: repoint every node on the path straight at the root.
	// The assignment inside the return is the whole optimisation.
	int find(int x){
		if(x==parent[x])return x;

		return parent[x]=find(parent[x]);
	}

	// UNION BY RANK: hang the shallower tree under the deeper one.
	// Returns false if they were ALREADY connected — which is how you detect a cycle.
	bool unite(int x,int y){
		int px=find(x);
		int py=find(y);

		if(px==py)return false;      // same set already: this edge closes a cycle

		if(rank[px]>rank[py]){
			parent[py]=px;
		}else if(rank[px]<rank[py]){
			parent[px]=py;
		}else{
			parent[py]=px;
			rank[px]++;            // equal ranks: height grows by exactly one
		}

		components--;

		return true;
	}

	bool connected(int x,int y){ return find(x)==find(y); }
	int count(){ return components; }
};
return parent[x] = find(parent[x]); is the most important line here. The recursion goes all the way up to the root. Then, on the way back down, it rewrites every node it passed so that each one points straight at the root. After that, a find on any of them takes one step. The assignment inside the return is what does this. Writing return find(parent[x]); is still correct, but nothing gets flattened and the whole thing is much slower.

Path compression, traced. Suppose the tree has become a chain: parent = [0, 0, 1, 2], meaning 3 → 2 → 1 → 0. Call find(3). It recurses to find(2), then find(1), then find(0), which returns 0 because 0 is its own parent. On the way back out, each call stores that answer: parent[1] = 0, parent[2] = 0, parent[3] = 0. The array is now [0, 0, 0, 0]. That first find took 3 steps; every later find on 1, 2 or 3 takes one.

Union by rank, and why the direction matters. Rank is an upper bound on a tree's height. Say you merge a tree of height 3 with a single node. If the tall tree goes under the single node, every one of its nodes is now one step further from the root, and the height becomes 4. If the single node goes under the tall tree's root, the height stays 3. Always hanging the lower tree under the higher one means height only grows when both are equal, and then by exactly one.

✍️
My convention: unite returns a bool, and it is never wasted

Returning false when the two elements were already in the same group turns DSU into a cycle detector for free. Two uses right away:

// Kruskal's MST (Chapter 31): the boolean IS the "would this create a cycle?" test.
for(auto &[w,u,v]:edges){
	if(dsu.unite(u,v))
	total+=w;                     // added only if it connected two components
}

// Cycle detection in an undirected graph (Chapter 27):
for(auto &e:edges){
	if(!dsu.unite(e[0],e[1]))
	return true;                  // this edge joins two already-connected nodes
}

If unite returns nothing (void), every caller has to call connected first. That doubles the number of find calls and adds a line everywhere you use it. One note on naming: union is a C++ keyword, so the method needs another name, such as unite, merge or join. That is a compile error people hit once and never forget.

⚠️
Two naming hazards in the same class

union is a reserved word. And rank clashes with std::rank if you wrote using namespace std;, which at global scope produces a confusing error message. In contest code people write rnk or sz instead. Inside a class it is usually fine, because the member name hides the outer one. Worth knowing so the error isn't a mystery. Also, if you write DSU as a class instead of a struct, don't forget public:. Without it every member is private, including the constructor.

🧾
Union by rank alone gives O(log n) — the clean half of the proof

The claim: a tree of rank r holds at least 2^r nodes. Here is the proof, step by step. A rank-0 tree is a single node, and 2⁰ = 1 ✓. Rank only goes up when two trees of equal rank r merge into one of rank r+1. Each of those had at least 2^r nodes, so the result has at least 2^(r+1). Since there are only n nodes in total, no rank can be bigger than log₂ n. Rank is an upper bound on height, so every find is O(log n). Proving the full O(α(n)) bound, with compression included, is genuinely hard (Tarjan, 1975), and it is not something to reproduce in an interview. Knowing this rank half, plus the fact that α(n) < 5 for any n below 2^65536, is the right level of detail.

🤏
α(n) is not literally constant, and interviewers notice either way

The inverse Ackermann function grows so slowly that it stays below 5 for any input you could ever store. So treat it as constant in practice, but say “effectively constant” or “O(α(n))” rather than “O(1)”. Claiming true O(1) is wrong: there is a proven lower bound showing that no DSU can reach O(1) per operation on average when the operations are mixed freely. Saying "near-constant, formally inverse Ackermann" takes three extra words and is exactly right.

Where DSU is the right tool

Edges arrive one at a time and I need connectivity after each

→ DSU. BFS or DFS costs O(V+E) for every query. DSU costs O(α(n)) per edge. Handling data as it arrives (being "online") is DSU's big advantage.

for(auto &e:edges) dsu.unite(e[0],e[1]);
Build an MST by adding cheapest edges

→ Kruskal's algorithm with DSU (Chapter 31). The true/false return is the cycle test.

if(dsu.unite(u,v)) total+=w;
Detect a cycle in an undirected graph

→ DSU. An edge whose two ends are already in the same group closes a cycle. (Directed graphs need DFS with a recursion stack instead — Chapter 27.)

if(!dsu.unite(u,v)) return true;
Count islands / regions in a grid

→ DSU, turning each cell (r,c) into the single number r*cols+c. BFS or DFS also works. DSU wins when cells are added one at a time.

dsu.unite(r*cols+c, nr*cols+nc);
Group things that are transitively equivalent

→ DSU. (Transitive means if a matches b and b matches c, then a matches c.) Examples: merging accounts, checking equations, grouping similar strings, finding a redundant connection.

dsu.unite(idOf(a), idOf(b));
I need to remove an edge, or list a set's members

→ Not DSU. It cannot split a group. Process the edges in reverse order, once you know them all, or use a different structure.

// reverse the timeline instead

What "reverse the timeline" means. Say a network starts with some cables and then cables are cut one at a time, and after each cut you must report the number of connected groups. DSU can't cut. But if you know every cut in advance, start from the final state (all the cut cables already missing), then walk the cuts backwards, adding each cable back with unite and recording the count before each addition. Reverse that list of counts and you have the answers in the original order. This only works when all the operations are known up front (called offline).

Listing a group's members is also not built in, but it is easy once all unions are done: loop over every element and push it into a bucket keyed by find(x). That is O(n) total, and it is how "accounts merge" produces its final groups.

numIslands with DSU — the flattening patternO(rows·cols·α)O(rows·cols)
// A grid cell (r,c) becomes the integer r*cols+c — Chapter 3's flattening.
// Only check LEFT and UP: by the time we reach (r,c), right and down have
// not been processed yet, so checking them would just duplicate work.
int numIslands(vector<vector<char>> &grid){
	int rows=grid.size();
	int cols=grid[0].size();

	DSU dsu(rows*cols);
	int land=0;
	int merges=0;

	for(int r=0;r<rows;r++){
		for(int c=0;c<cols;c++){
			if(grid[r][c]!='1')continue;

			land++;

			if(r>0 and grid[r-1][c]=='1'){
				if(dsu.unite(r*cols+c,(r-1)*cols+c))merges++;
			}
			if(c>0 and grid[r][c-1]=='1'){
				if(dsu.unite(r*cols+c,r*cols+c-1))merges++;
			}
		}
	}

	return land-merges;         // each successful merge removes one island
}
Use land - merges instead of counting distinct roots. Every land cell starts as its own island, and every successful union removes one island. So the subtraction is exact and saves a second pass over the grid. Note that dsu.count() would be wrong here: the DSU covers every cell, so it counts water cells as groups too.

A small trace on the 2×3 grid 1 1 0 / 0 1 1. Cell (0,0) is land: land = 1, with no neighbour above or to the left. Cell (0,1): land = 2; its left neighbour is land, the union succeeds, merges = 1. Cell (0,2) is water. Cell (1,0) is water. Cell (1,1): land = 3; the cell above, (0,1), is land and the union succeeds, merges = 2. Cell (1,2): land = 4; the cell above is water, the left one (1,1) is land, union succeeds, merges = 3. Answer: 4 − 3 = 1 island, which is right: all four land cells touch in a chain.

The variants worth knowing

// Track component SIZE instead of rank. Slightly worse height bound in theory,
// same O(alpha) with compression, and you get size() for free — which many
// problems need ("largest component", "product of component sizes").
vector<int> parent,sz;

bool unite(int x,int y){
	int px=find(x);
	int py=find(y);

	if(px==py)return false;

	if(sz[px]<sz[py])swap(px,py);   // px is the bigger one

	parent[py]=px;
	sz[px]+=sz[py];

	return true;
}
int size(int x){ return sz[find(x)]; }

Use this version by default. The swap makes it shorter than the three-branch rank version, and you need size() often enough that rank rarely earns its place.

// Store a weight on each parent edge: the value of x RELATIVE to its parent.
// Solves "a/b = 2.0, b/c = 3.0, what is a/c?" and equation-satisfiability.
vector<int> parent;
vector<double> w;      // w[x] = value(x) / value(parent[x])

// Compression must ACCUMULATE the weights along the path.
int find(int x){
	if(x==parent[x])return x;

	int root=find(parent[x]);
	w[x]*=w[parent[x]];         // fold the parent's weight into mine
	parent[x]=root;

	return root;
}
bool unite(int x,int y,double ratio){   // value(x)/value(y) = ratio
	int px=find(x);
	int py=find(y);

	if(px==py)return abs(w[x]/w[y]-ratio)<1e-9;   // consistency check

	parent[px]=py;
	w[px]=ratio*w[y]/w[x];

	return true;
}

The tricky part is find. Path compression gives each node a new parent, but its stored weight was measured against the old parent. So you must multiply in the weights of everything above it. Get that wrong and the answers slowly drift, with no error message.

Trace: given a/b = 2 and b/c = 3, what is a/c? unite(a, b, 2) makes b the parent of a with w[a] = 2. unite(b, c, 3) makes c the parent of b with w[b] = 3. Now find(a) reaches root c, and on the way back sets w[a] = 2 × 3 = 6 and points a straight at c. Since w[c] = 1, the answer is w[a] / w[c] = 6, which matches a/c = (a/b)·(b/c).

// Sometimes you must UNDO unions (offline dynamic connectivity, DSU on tree).
// Rollback requires giving up path compression, because compression mutates
// nodes that were not part of this union and cannot be cheaply restored.
// So: union by size only, O(log n) per find, but every union is reversible.
vector<int> parent,sz;
vector<pair<int,int>> history;      // (child root, parent root)

int find(int x){
	while(x!=parent[x])x=parent[x];   // NO compression

	return x;
}
bool unite(int x,int y){
	int px=find(x);
	int py=find(y);

	if(px==py)return false;

	if(sz[px]<sz[py])swap(px,py);

	history.push_back({py,px});
	parent[py]=px;
	sz[px]+=sz[py];

	return true;
}
void rollback(){
	auto [child,par]=history.back();
	history.pop_back();

	sz[par]-=sz[child];
	parent[child]=child;
}

The trade-off is clear. Supporting undo means giving up path compression, and with it the α(n) bound. You are left with O(log n) from union by size alone. That is a fair price for undo, and it is what offline dynamic connectivity and "DSU on tree" techniques use.

Why compression and undo don't mix: one find with compression can rewrite the parent of many nodes, none of which were part of the union you want to undo. To roll back you would have to log every one of those writes. Without compression, a union changes exactly one parent entry and one sz entry, so undoing it is two assignments. Note that rollback undoes the most recent union first, like a stack; you cannot undo an arbitrary older one.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 BOOL FROM UNITE
Make unite return whether it actually merged. That single boolean is the cycle test in Kruskal and the redundant-edge detector, for free.
💡 GRID TO DSU
Flatten a grid cell to r*cols + c and any 2D connectivity problem becomes a 1D DSU. The same index trick works for any fixed-shape structure.
⛔ BOTH OPTIMISATIONS
Path compression and union by rank. With only one you get O(log n); with both it is effectively O(1), and the code is two extra lines.
⚠️
Common mistakes
  • Writing return find(parent[x]); without the assignment. It is still correct, but nothing gets flattened, so you lose the whole optimisation with no warning.
  • Comparing x and y instead of their roots. if(x==y) asks whether they are the same element, not whether they are in the same group. Always compare find(x) with find(y).
  • Naming the method union. That is a reserved word. Use unite, merge or join.
  • Forgetting public: in a class. Then nothing is usable from outside, not even the constructor.
  • Not setting parent[i] = i at the start. Every element must begin as its own root, or find never stops.
  • Increasing rank on every union. It only increases when two trees of equal rank merge.
  • Using dsu.count() when the DSU covers every grid cell. It counts water cells as groups too.
  • Trying to remove an edge. DSU cannot split a group. Process the edges in reverse order, or use a rollback DSU.
  • Forgetting to multiply in the weights during compression in a weighted DSU. The answers drift with no error.
  • Claiming O(1). It is O(α(n)). "Effectively constant" is the accurate way to say it.

Interview drill

Warm-up: Implement DSU and explain both optimisations.

How a strong answer sounds
I keep a parent array where every element starts by pointing at itself. The root of each tree represents the group, and two elements are in the same group exactly when their roots match. find walks up to the root. unite finds both roots and, if they differ, hangs one under the other. Then two optimisations. Path compression: return parent[x] = find(parent[x]);. The recursion reaches the root, and on the way back out, every node on that path is repointed straight at it. So later finds on any of them take one step. The assignment inside the return is the whole trick; leave it out and the structure is correct but slow. Union by rank or size: always hang the shallower or smaller tree under the bigger one, so the height doesn't grow for no reason. With rank there is a clean proof: rank only goes up when two equal ranks merge, so a rank-r tree has at least 2^r nodes. That caps rank, and therefore height, at log₂ n. Together the two optimisations give O(α(n)) per operation on average. That is the inverse Ackermann function, which is below 5 for any n you could store, so it is effectively constant. I wouldn't claim literal O(1), since a proven lower bound rules that out. I would also have unite return false when the two were already joined, because that one value is the cycle test Kruskal needs.

Deeper: Islands II — land cells are added one at a time and you must report the island count after each addition. Why DSU rather than BFS?

How a strong answer sounds
Because the problem is online: I have to answer after every addition. BFS or DFS would walk the whole grid again each time, which is O(k·rows·cols) for k additions. DSU updates as it goes. I build a DSU over every cell, turning (r,c) into r·cols+c, and keep a running island count. When a cell becomes land, I add one to the count, then try to union it with each of its four neighbours that is already land. Every union that succeeds subtracts one from the count, because it joined two islands that were separate before. A union that returns false means the neighbour was already in the same island; that happens often and must not change the count. The important detail is that one new cell can join up to four different islands at once, so the count can drop by three in a single step. That is exactly the case a naive "add one or don't" approach gets wrong. The total cost is O(k·α) for the additions, effectively linear, and the true/false return from unite does all the bookkeeping. If the problem asked me to remove land instead, DSU would be the wrong tool, because it cannot split a group. I would process the timeline backwards so removals become additions, or use a rollback DSU and give up path compression.

🧠 Key takeaways

  • DSU answers only "same group?" and "merge". Doing so little is why it is effectively O(1).
  • return parent[x] = find(parent[x]); — the assignment inside the return is path compression.
  • Union by rank alone gives O(log n), because a rank-r tree holds at least 2^r nodes. Both optimisations together give O(α(n)).
  • Make unite return true or false. That one value gives you Kruskal's cycle test and undirected cycle detection for free.
  • DSU wins when edges arrive one at a time. It cannot split groups, so removals need reversed order or a rollback DSU.

Check your understanding

What does the assignment in return parent[x] = find(parent[x]); accomplish?

The recursion reaches the root, and the assignment on the way back out flattens the whole path. Writing return find(parent[x]); is still correct, but it quietly loses the optimisation.

With union by rank but no path compression, what is the amortized cost per operation?

Rank only goes up when two equal ranks merge, and that doubles the smallest possible node count. So rank, and therefore height, can't exceed log₂ n. Path compression is what brings it down to inverse Ackermann.

Why should unite return a boolean?

Without it, every caller has to call connected first, which doubles the find calls and adds a line everywhere. With it, Kruskal is a two-line loop.

Land cells are added to a grid one at a time and you must report the island count after each. Why DSU rather than BFS?

BFS costs O(k·rows·cols) for k additions; DSU costs O(k·α). Note too that one new cell can join up to four islands at once, so the count can drop by three in a single step.

Which operation can DSU not do efficiently?

DSU only merges. For removals, either walk the timeline backwards so deletions become additions, or use a rollback DSU, which costs you path compression and therefore the α(n) bound.
