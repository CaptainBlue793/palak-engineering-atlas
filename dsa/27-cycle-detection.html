Cycle Detection

A cycle is a path that leads back to where it started, like a loop of one-way streets that returns you to your front door. “Does this graph have a cycle?” has two completely different answers, depending on whether the edges are one-way (directed) or two-way (undirected). Mixing them up is one of the surest ways to get a graph problem wrong. Directed cycles need a recursion stack (a record of the path you are on right now). Undirected cycles need a parent check (ignore the edge you just came along). This chapter makes the difference concrete, then covers the BFS-style alternatives and how to find the cycle itself.

  • Explain why visited alone is not enough for directed graphs
  • Sort each edge into tree, back, forward or cross — and know which one means a cycle
  • Write directed detection with instack, and undirected detection with a parent
  • Use Kahn's size check (directed) and DSU (undirected) as the non-recursive alternatives
  • Find the actual cycle, and handle self-loops and parallel (duplicate) edges

Why the two cases differ

Why this matters: a cycle is usually the thing that makes a task impossible. Courses that are each other's prerequisites can never be taken. Two threads each waiting for a lock the other holds are a deadlock, which is a cycle in the "waits for" graph. A spreadsheet reports a "circular reference" when cell formulas depend on each other in a loop. So "is there a cycle?" often is the whole question in disguise.

Here is the key point. In an undirected graph, reaching a node you have already visited almost always means a cycle. In a directed graph, it very often does not — two one-way roads can lead to the same town without any way to loop back.

Directed: not a cycle
// 0 -> 1, 0 -> 2, 1 -> 2
//
//    0
//   / \
//  v   v
//  1 -> 2
//
// DFS from 0 visits 1, then 2 (finishing it),
// then returns and sees 2 already visited via 0->2.
// Already visited, but NOT a cycle — 2 is finished,
// not an ancestor. This is a "cross/forward" edge.

So visited alone would report a cycle that is not there. You need to know whether the node is on the current path, not just whether you have ever seen it.

Undirected: not a cycle either
// 0 -- 1
//
// DFS from 0 visits 1. From 1, the adjacency list
// contains 0 — because undirected edges are stored
// twice. 0 is visited, so a naive check says "cycle".
//
// But it is just the edge we arrived on.
// Fix: skip the parent.

So visited alone would report a fake cycle here too — for a different reason. Each undirected edge is stored both ways, so every single edge looks like a 2-node cycle unless you ignore the edge you came in on.

🏷️
Edge classification — the precise statement

While DFS runs on a directed graph, every edge u → v falls into one of four kinds:

  • Tree edge — v was unvisited, and this is the edge we used to find it.
  • Back edge — v is visited and still on the recursion stack, so v is an ancestor of u (DFS passed through it on the way here). This, and only this, means a cycle.
  • Forward edge — v is a finished descendant of u (DFS already reached it from here by another route). No cycle.
  • Cross edge — v is finished and sits in a different branch of the search. No cycle.

So the whole problem comes down to telling a back edge apart from forward and cross edges. A second array — “is this node on the current path?” — gives you exactly that. A directed graph has a cycle if and only if DFS finds a back edge. In an undirected graph things are simpler: there are only tree edges and back edges. That is why the parent check alone is enough there.

Directed: DFS with a recursion stack

Two short dry runs show why both arrays are needed. instack[x] is true only while DFS is "inside" x — after entering it and before returning from it.

  • No cycle: 0→1, 0→2, 1→2. Enter 0 (instack = {0}). Enter 1 (instack = {0,1}). Enter 2 (instack = {0,1,2}). Node 2 has no edges, so leave it: instack = {0,1}. Leave 1: instack = {0}. Back in 0, check the edge 0→2: 2 is visited but instack[2] is false, so it is a forward edge and we ignore it. Result: no cycle, which is correct.
  • Cycle: 0→1, 1→2, 2→0. Enter 0, then 1, then 2 (instack = {0,1,2}). From 2, check 2→0: 0 is visited and instack[0] is true. That is a back edge, so set cycle = true. Result: cycle found, which is correct.

In the first run, a visited-only check would have wrongly reported a cycle at the edge 0→2. The only difference between the two runs is whether the node we reach is still on the current path — and that is exactly what instack records.

hasCycle — directed, DFS with instackO(V + E)O(V)
// Two arrays, and the difference between them is the whole algorithm:
//   visited[x] — x has been seen at some point
//   instack[x] — x is on the CURRENT recursion path (an ancestor of the node
//                we are at right now). This is what identifies a back edge.
void DFS(unordered_map<int,vector<int>> &graph,int node,vector<bool> &visited,
         stack<int> &st,vector<bool> &instack,bool &cycle){
	if(visited[node])return;

	visited[node]=true;
	instack[node]=true;        // entering: now on the current path

	for(auto &neighbour:graph[node]){
		if(!visited[neighbour]){
			DFS(graph,neighbour,visited,st,instack,cycle);
		}else if(instack[neighbour]){
			cycle=true;        // BACK EDGE -> neighbour is an ancestor
			return;
		}

		if(cycle)return;      // propagate the failure up immediately
	}

	instack[node]=false;       // leaving: no longer on the current path
	st.push(node);            // finish order, so this doubles as toposort
}
bool hasCycle(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(int i=0;i<edges.size();i++){
		int u=edges[i][0];
		int v=edges[i][1];
		graph[u].push_back(v);
	}

	stack<int> st;
	bool cycle=false;
	vector<bool> visited(N,false);
	vector<bool> instack(N,false);

	for(int i=0;i<N;i++){
		if(!visited[i]){
			DFS(graph,i,visited,st,instack,cycle);
			if(cycle)return true;
		}
	}

	return false;
}
instack[node]=false on the way out is the line you must not forget. Leave it out and instack becomes a second copy of visited, so every cross edge is reported as a cycle. Also notice: resetting it is correct only because we are looking for ancestors on the current path. That is what makes this array different from visited, and why you need both.
✍️
My convention: three states in one array, when you want fewer moving parts

You can merge the two boolean arrays into one vector<int> state: 0 = unvisited, 1 = in progress (on the current path), 2 = finished. It is the same algorithm with one array, and the code reads more like the edge kinds above:

// 0 = white (unvisited), 1 = grey (on the path), 2 = black (finished)
bool DFS(vector<vector<int>> &graph,int node,vector<int> &state){
	state[node]=1;               // grey: entering

	for(int neighbour:graph[node]){
		if(state[neighbour]==1)return true;        // grey -> back edge -> cycle
		if(state[neighbour]==0 and DFS(graph,neighbour,state))return true;
	}

	state[node]=2;               // black: finished

	return false;
}

Returning a bool instead of using a reference parameter also removes the if(cycle)return; line that passes the result back up. Use whichever you find clearer, but stick with it. Textbooks often call the three states white/grey/black, so it is worth recognising those names.

Undirected: DFS with a parent

The idea: when DFS walks from u to v, the edge back to u is just the same road seen from the other end, so it does not count. Any other already-visited neighbour means there are two different routes to the same node, and two routes between the same pair of nodes always join into a loop. Compare two small graphs:

  • Path 0–1–2 (no cycle). DFS(0, parent −1) goes to 1. At 1, neighbour 0 is the parent, skip; go to 2. At 2, neighbour 1 is the parent, skip. Nothing else. No cycle.
  • Triangle 0–1, 1–2, 2–0 (cycle). DFS(0) goes to 1, then 1 goes to 2 (parent 1). At 2, neighbour 1 is the parent, skip. Neighbour 0 is visited and is not the parent. Cycle found.
hasCycle — undirected, parent checkO(V + E)O(V)
// An undirected edge is stored twice, so from v the adjacency list always
// contains the parent we arrived from. Skip exactly that one edge.
bool DFS(vector<vector<int>> &graph,int node,int parent,vector<bool> &visited){
	visited[node]=true;

	for(int neighbour:graph[node]){
		if(neighbour==parent)continue;        // the edge we came in on

		if(visited[neighbour])return true;      // any OTHER visited node = cycle

		if(DFS(graph,neighbour,node,visited))return true;
	}

	return false;
}
bool hasCycleUndirected(int N,vector<vector<int>> &edges){
	vector<vector<int>> graph(N);
	for(auto &e:edges){
		graph[e[0]].push_back(e[1]);
		graph[e[1]].push_back(e[0]);      // stored both ways
	}

	vector<bool> visited(N,false);

	for(int i=0;i<N;i++){
		if(!visited[i] and DFS(graph,i,-1,visited))return true;
	}

	return false;
}
No instack is needed at all, because an undirected DFS has no cross or forward edges — every non-tree edge goes to an ancestor. But parent == neighbour is subtly wrong with parallel edges. Two separate edges between u and v do form a cycle, but comparing by node label skips both of them. The fix is to skip by edge id (which specific edge you came along) rather than by node. The same care applies to a self-loop, which is a cycle of length 1.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 DIRECTED NEEDS INSTACK
A directed cycle needs on the current path, not merely visited. Two arrays, or white/grey/black — a single visited array finds cross-edges and reports cycles that are not there.
💡 UNDIRECTED: SKIP PARENT
For undirected graphs, ignore the edge you arrived on. On a tree that single guard replaces the visited array entirely.
⛔ PARALLEL EDGES
The skip-parent trick breaks with duplicate edges or self-loops — those are cycles. Track the edge id rather than the parent node when the input allows them.

The BFS alternatives

Recursive DFS is the most natural way to find cycles, but it has one weakness: a graph shaped like a long chain makes the recursion as deep as the graph, and around 10⁵ levels the program crashes with a stack overflow. The three versions below avoid recursion entirely. The DSU version is the easiest to trace. With undirected edges 0–1, 1–2, 2–0: the first edge joins {0} and {1} into {0,1}. The second joins {0,1} and {2} into {0,1,2}. The third edge connects 2 and 0, but find(2) == find(0) — they are already in the same group. There was already a route between them, so this edge closes a loop: cycle.

// Kahn's algorithm from Chapter 26. If fewer than N nodes come out,
// the rest are in or downstream of a cycle. No recursion, so no stack risk.
bool hasCycle(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(int i=0;i<edges.size();i++){
		int u=edges[i][0];
		int v=edges[i][1];
		graph[u].push_back(v);
		// graph[v].push_back(u); -> This is for Undirected Edges
	}

	vector<int> indegree(N,0);
	for(auto &it:graph){
		for(int node:it.second){
			indegree[node]++;
		}
	}

	queue<int> q;
	vector<int> ans;
	for(int i=0;i<N;i++){
		if(indegree[i]==0)
		q.push(i);
	}

	while(!q.empty()){
		int node=q.front();
		q.pop();
		ans.push_back(node);

		for(auto &neighbour:graph[node]){
			indegree[neighbour]--;

			if(indegree[neighbour]==0)
			q.push(neighbour);
		}
	}

	if(ans.size()!=N)return true;

	return false;
}

Prefer this when the graph is directed and might be deep. It uses a loop instead of recursion, so there is no stack-overflow risk at 10⁵ nodes. When there is no cycle, it also gives you the topological order in the same pass.

// DSU from Chapter 22. An edge joining two nodes already in the same
// component closes a cycle — which is exactly what unite() returning
// false means. Four lines of logic.
bool hasCycleUndirected(int N,vector<vector<int>> &edges){
	DSU dsu(N);

	for(auto &e:edges){
		if(!dsu.unite(e[0],e[1]))
		return true;
	}

	return false;
}
// O(E * alpha(N)). Also handles the edges arriving ONE AT A TIME,
// which DFS cannot do without re-running from scratch.
// Note: this is undirected only — DSU has no notion of direction.

The cleanest undirected answer, and the only one that works online — that is, when edges arrive one at a time and you must answer after each. It is also exactly the cycle test inside Kruskal's MST (Chapter 31): the same true/false result, used for a different purpose.

// BFS version: store the parent alongside each node in the queue.
bool hasCycleBFS(vector<vector<int>> &graph,int start,vector<bool> &visited){
	queue<pair<int,int>> q;      // {node,parent}
	q.push({start,-1});
	visited[start]=true;

	while(!q.empty()){
		auto [node,parent]=q.front();
		q.pop();

		for(int neighbour:graph[node]){
			if(neighbour==parent)continue;

			if(visited[neighbour])return true;

			visited[neighbour]=true;        // neighbour, on enqueue (Ch 25)
			q.push({neighbour,node});
		}
	}

	return false;
}

The same parent logic, written with a loop instead of recursion. Useful when the graph might be a 10⁵-node chain and recursion would overflow the stack. Note visited[neighbour], not visited[node] — the Chapter 25 bug applies here too.

Recovering the cycle itself

“Is there a cycle?” is easier than “show me one”. To list the actual nodes, record each node's parent (the node you came from). When you find a back edge, follow the parents backwards until you reach the start of the cycle.

Example: edges 0→1, 1→2, 2→3, 3→1. DFS records parent[1]=0, parent[2]=1, parent[3]=2. At node 3 it finds the back edge 3→1 (1 is grey). Start at 3 and follow parents until you hit 1: collect 3, then 2, then stop at 1 and add it. That gives 3, 2, 1; reversed, the cycle is 1 → 2 → 3 → 1. Node 0 is not part of it, even though DFS passed through it — the walk stops at 1, the target of the back edge.

findCycle — return the nodes, directedO(V + E)O(V)
// When we find a back edge u -> v, the cycle is v ... u plus the edge back.
// Walk parent pointers from u up to v to recover it.
vector<int> cycleNodes;

bool DFS(vector<vector<int>> &graph,int node,vector<int> &state,vector<int> &parent){
	state[node]=1;

	for(int neighbour:graph[node]){
		if(state[neighbour]==1){
			// back edge node -> neighbour; rebuild the cycle
			cycleNodes.clear();

			int x=node;
			while(x!=neighbour){
				cycleNodes.push_back(x);
				x=parent[x];
			}
			cycleNodes.push_back(neighbour);

			reverse(cycleNodes.begin(),cycleNodes.end());

			return true;
		}

		if(state[neighbour]==0){
			parent[neighbour]=node;
			if(DFS(graph,neighbour,state,parent))return true;
		}
	}

	state[node]=2;

	return false;
}
The while(x != neighbour) loop only stops because neighbour is grey — on the current path. That means it really is an ancestor of node, so following parents will reach it. On a cross edge the loop would run off the end of the parent chain. So finding the cycle works for the same reason that detecting it works.
🕳️
Self-loops and parallel edges — ask before you code
  • Self-loop u → u: a cycle of length 1. The directed algorithm catches it automatically, because u is grey when the edge is checked. The undirected parent check, however, can skip it if parent == u. So a self-loop needs its own test: if(neighbour == node) return true;
  • Parallel edges u — v twice, undirected: a cycle of length 2. Checking the parent by label skips both copies and misses it. Fix it by skipping the specific edge id you arrived on, not the parent node.
  • Directed parallel edges u → v twice: not a cycle, and no algorithm here is confused by them.

Interviewers use exactly these cases to check whether you understood the algorithm or just memorised it. Asking “can there be self-loops or duplicate edges?” at the start earns real credit.

⚠️
Common mistakes
  • Using only visited on a directed graph. Every cross and forward edge is reported as a cycle that is not there.
  • Forgetting instack[node] = false on the way out. instack turns into a copy of visited.
  • Using instack on an undirected graph without the parent skip. Every edge looks like a 2-cycle.
  • Skipping the parent by label when parallel edges exist. A real 2-cycle is missed. Skip by edge id instead.
  • Missing the self-loop case in undirected detection. u — u is a cycle and the parent check hides it.
  • Forgetting the driver loop. The cycle may be in a separate piece of the graph you never started from.
  • Not passing the result back up. Without if(cycle) return;, the DFS keeps exploring and may reset instack entries you still needed.
  • Using DSU on a directed graph. DSU ignores direction, so it reports a "cycle" for a→b, a→c, b→c, which has none.
  • Recursive DFS on a 10⁵-node chain. The recursion overflows the stack. Use Kahn (directed) or DSU/BFS (undirected).

Interview drill

Warm-up: Detect a cycle in a directed graph. Why is a visited array not enough?

How a strong answer sounds
Because in a directed graph, "already visited" and "is an ancestor of where I am now" are different things, and only the second one means a cycle. Take 0→1, 0→2, 1→2. DFS from 0 goes to 1, then to 2, finishes 2 and returns. Then it checks the edge 0→2 and finds 2 visited. But 2 is finished, not on the current path, so that is a forward edge and there is no cycle. A visited-only check would wrongly report one. So I need a second piece of state: is this node on the current recursion path? I keep an instack array, set it true when I enter a node and false when I leave. A neighbour that is visited and instack is a back edge, which is exactly a cycle. Formally, every DFS edge is a tree, back, forward or cross edge, and a directed graph has a cycle if and only if DFS finds a back edge. I like to merge the two booleans into one three-state array — white unvisited, grey on the path, black finished — because then the code reads just like the edge kinds. The line people most often forget is the reset on exit. Without it instack becomes a copy of visited and every cross edge is a false alarm. If the graph could be 10⁵ nodes deep, I would use Kahn's algorithm instead: fewer than N output nodes means a cycle, and because it uses a loop, it cannot overflow the stack.

Deeper: Now the same question for an undirected graph. What changes, and what are the edge cases?

How a strong answer sounds
The instack array is no longer needed, because an undirected DFS has no cross or forward edges — every non-tree edge leads to an ancestor. But a new problem appears. An undirected edge is stored twice in the adjacency list, so standing at v I always see the parent u as a neighbour. u is visited, so a naive check reports a cycle for every single edge. The fix is to skip the edge I arrived on: pass the parent down and do if(neighbour == parent) continue;. After that, any other visited neighbour really does close a cycle. Two edge cases break this label-based version. A self-loop u—u is a real cycle of length one, but if the parent happens to equal u the check skips it, so I need an explicit if(neighbour == node) return true;. And parallel edges — two separate edges between u and v — form a real 2-cycle, but comparing by node label skips both copies and misses it. The robust fix is to skip the specific edge id I came along, not the parent's label. So at the start I would ask whether self-loops or duplicate edges are possible. In practice, for an undirected graph I would often just use DSU: go through the edges and return true the first time unite returns false. That is O(E·α), needs no recursion, handles parallel edges naturally, and works even when edges arrive one at a time.

🧠 Key takeaways

  • A directed graph has a cycle if and only if DFS finds a back edge — an edge to a neighbour that is on the current recursion path.
  • visited is not enough for directed graphs. You need instack (or white/grey/black), reset when you leave a node.
  • Undirected graphs need no instack, but must skip the edge they arrived on — by edge id if parallel edges can exist.
  • Kahn's size check is the non-recursive test for directed graphs. DSU's unite returning false is the cleanest test for undirected ones.
  • Self-loops and parallel edges behave differently in the two cases — ask about them before coding.

Check your understanding

In a directed graph, why is a visited array alone insufficient for cycle detection?

With 0→1, 0→2, 1→2, the edge 0→2 finds 2 visited but already finished — no cycle. You need a second state (instack, or grey in white/grey/black) to spot a real back edge.

You forget instack[node] = false when leaving a node. What happens?

The array stops meaning "on the current path" and starts meaning "ever seen". That difference is the whole point of the algorithm, so it turns back into the broken visited-only version.

In an undirected graph, why must DFS skip the parent?

graph[u] contains v, and graph[v] contains u. Standing at v, you see the parent u as a visited neighbour. Without the skip, even a two-node graph reports a cycle.

An undirected graph has two distinct edges between u and v. Your DFS skips the parent by node label. What happens?

A false negative (a real cycle missed). Skipping by node label throws away every edge back to the parent, including the second, separate one. Track and skip the specific edge id you came along instead.

You have an undirected graph and edges arriving one at a time; you must report a cycle as soon as one forms. Best approach?

DSU handles edges arriving one at a time (Chapter 22): O(E·α) in total, instead of O(E·(V+E)) for re-running DFS after each edge. Kahn is for directed graphs only, and Floyd is for linked lists and graphs where each node has exactly one outgoing edge.
