DP on Strings

Almost every DP problem on two strings has the same shape: a table dp[i][j] that holds the answer for the first i characters of one string and the first j of the other (these starting pieces are called prefixes). Each cell asks one question: do the current characters match or not? LCS, edit distance, wildcard matching and the palindrome problems all use this one table. Only the arithmetic in the "match" and "mismatch" branches changes. Once you can fill the 3×3 top-left corner by hand, the recurrence (the rule for filling each cell) almost writes itself.

  • Solve wildcard and regex matching, where the mismatch branch does the real work

The two-string template

Why do these problems matter? Comparing two strings is everywhere. diff and Git show changes between file versions using a longest-common-subsequence idea. Spell checkers suggest words with a small edit distance. Biologists align DNA with the same tables. In interviews, LCS and edit distance are two of the most common medium-to-hard DP questions.

Why a table indexed by two prefixes? The recursion for these problems always looks at the last character of each string and makes a choice that shortens one or both strings. So a subproblem is "some prefix of s against some prefix of t", and there are (n + 1)(m + 1) such pairs, counting the empty prefixes.

the shape every two-string DP takesO(n·m)O(n·m) → O(m)
// dp[i][j] = the answer for the first i characters of s and the
//            first j characters of t.
// Size (n+1) x (m+1) so row 0 and column 0 mean "empty prefix" — that
// sentinel row and column are what remove every boundary special case.
vector<vector<int>> dp(n+1,vector<int>(m+1,0));

// base cases: one string empty
for(int i=0;i<=n;i++)dp[i][0]=/* ... */;
for(int j=0;j<=m;j++)dp[0][j]=/* ... */;

for(int i=1;i<=n;i++){
	for(int j=1;j<=m;j++){
		if(s[i-1]==t[j-1]){
			dp[i][j]=/* characters MATCH: usually 1 + dp[i-1][j-1] */;
		}else{
			dp[i][j]=/* MISMATCH: combine dp[i-1][j], dp[i][j-1], dp[i-1][j-1] */;
		}
	}
}

return dp[n][m];
s[i-1], not s[i]. Row i is about the first i characters, so the i-th character sits at index i-1. The shift exists because row 0 has to mean "empty string". It causes nearly every off-by-one bug in this chapter. Write down in one sentence what a cell means, then work out the indexing from that sentence instead of guessing.

My convention: draw the 3×3 corner by hand before writing the loops

Take s = "ab", t = "ac", and fill dp[0][0] through dp[2][2] on paper. It takes thirty seconds and settles three things at once:

  • what the extra "empty" row and column (the sentinel row and column) should hold,
  • whether the match branch adds 1,
  • which of the three neighbouring cells the mismatch branch needs.

That 3×3 corner would have caught every string-DP bug I have ever written. It is much faster than debugging the full table.

The cell for "a" vs "a" is a match, so it copies the diagonal: 0 + 1 = 1 for LCS, and 0 edits. The bottom-right cell, "ab" vs "ac", is a mismatch. LCS takes the larger of its top and left neighbours, 1. Edit distance takes 1 + the smallest of its three neighbours; the diagonal is 0, meaning "replace b with c". Both answers are correct: the strings share one character, and one edit turns one into the other.

Switch between LCS and edit distance on the same strings. The table has the same shape — only the two branches differ.
Longest common subsequence
// dp[i][j] = the length of the LCS of s[0..i-1] and t[0..j-1].
int longestCommonSubsequence(string &s,string &t){
	int n=s.size();
	int m=t.size();
	vector<vector<int>> dp(n+1,vector<int>(m+1,0));
	// base: an empty prefix shares nothing -> 0, already set

	for(int i=1;i<=n;i++){
		for(int j=1;j<=m;j++){
			if(s[i-1]==t[j-1]){
				dp[i][j]=1+dp[i-1][j-1];
			}else{
				dp[i][j]=max(dp[i-1][j],dp[i][j-1]);
			}
		}
	}

	return dp[n][m];
}

Match → keep that character and step back in both strings. Mismatch → drop the last character of one string, whichever choice gives more. Notice the mismatch branch never uses the diagonal cell dp[i-1][j-1]. That is why shrinking the table to one row is easy here.

Edit distance (Levenshtein)
// dp[i][j] = the minimum operations to turn s[0..i-1] into t[0..j-1].
int minDistance(string &s,string &t){
	int n=s.size();
	int m=t.size();
	vector<vector<int>> dp(n+1,vector<int>(m+1,0));

	for(int i=0;i<=n;i++)dp[i][0]=i;   // delete every char
	for(int j=0;j<=m;j++)dp[0][j]=j;   // insert every char

	for(int i=1;i<=n;i++){
		for(int j=1;j<=m;j++){
			if(s[i-1]==t[j-1]){
				dp[i][j]=dp[i-1][j-1];       // free, no operation
			}else{
				dp[i][j]=1+min({dp[i-1][j],      // delete from s
				                  dp[i][j-1],      // insert into s
				                  dp[i-1][j-1]});  // replace
			}
		}
	}

	return dp[n][m];
}

The base cases are not zero here. Turning a string of length i into an empty one costs i deletions. Each of the three mismatch terms is one named operation (delete, insert, replace). That makes the recurrence easy to remember instead of random-looking.

Why the LCS branches are right. On a match, taking the character is always safe. Any common subsequence that does not use this pair can swap its last character for it without getting shorter. On a mismatch, s[i-1] and t[j-1] cannot both be the last character of the LCS, because they are different. So at least one of them is useless here, and you try dropping each and keep the better result.

A known example for edit distance: turning "horse" into "ros" takes 3 operations. Replace h with r ("rorse"), delete the second r ("rose"), delete e ("ros"). The table's bottom-right cell is 3, and walking back through it recovers exactly these steps. Edge cases the base cases already handle: if either string is empty, the answer is the other string's length (all inserts or all deletes), and if the strings are equal, every cell on the main path is a free match and the answer is 0.

🔗
Three problems that are LCS in disguise
  • Minimum insertions and deletions to convert s into t (no replace allowed) = (n − LCS) + (m − LCS). Every character outside the common subsequence must be deleted from one string or inserted into the other.
  • Shortest common supersequence length (the shortest string that contains both as subsequences) = n + m − LCS. The shared part is written once instead of twice.
  • Longest palindromic subsequence (LPS) of s = LCS(s, reverse(s)). A palindrome reads the same forwards and backwards, so a palindromic subsequence appears in both s and its reverse. It follows that the minimum insertions to make s a palindrome = n − LPS.

With numbers: s = "abcde", t = "ace", LCS = 3 ("ace"). Insertions plus deletions = (5 − 3) + (3 − 3) = 2: delete b and d. The shortest common supersequence has length 5 + 3 − 3 = 5, and "abcde" itself is one. For s = "bbbab", the reverse is "babbb", their LCS is "bbbb", so the LPS is 4. That means 5 − 4 = 1 insertion makes it a palindrome: add an a after the first b to get "babbab", which reads the same both ways.

Spotting these saves you writing a new recurrence. If you can compute LCS, you can answer all four. "Longest palindromic subsequence = LCS with the reverse" is exactly the kind of insight interviewers hope to hear.

The palindrome family: iterate over lengths

Now there is only one string. Here dp[i][j] means the interval (the slice) s[i..j], not a pair of prefixes. That changes the loop order: a slice's answer depends on shorter slices inside it, so you must fill shorter slices before longer ones.

A trace on "abba". Length 1: every single letter is a palindrome. Length 2: only "bb" (i = 1, j = 2) has matching ends. Length 3: "abb" and "bba" both have different ends, so both are false. Length 4: "abba" has matching ends (a and a), and its inside, "bb", was already marked true at length 2. So the whole string is a palindrome, and the answer is "abba". The length-4 cell could only be decided because the length-2 cell was already filled.

longest palindromic substring — interval DPO(n²)O(n²)
// dp[i][j] = is s[i..j] a palindrome?
// s[i..j] is a palindrome iff the ends match AND the inside is one.
// So dp[i][j] depends on dp[i+1][j-1] — a SHORTER interval. Hence we must
// iterate by increasing LENGTH, not by increasing i.
string longestPalindrome(string &s){
	int n=s.size();
	if(n<2)return s;

	vector<vector<bool>> dp(n,vector<bool>(n,false));
	int bestStart=0;
	int bestLen=1;

	for(int i=0;i<n;i++)
	dp[i][i]=true;                    // length 1

	for(int i=0;i<n-1;i++){
		if(s[i]==s[i+1]){
			dp[i][i+1]=true;            // length 2
			bestStart=i;
			bestLen=2;
		}
	}

	for(int len=3;len<=n;len++){       // LENGTH is the outer loop
		for(int i=0;i+len-1<n;i++){
			int j=i+len-1;

			if(s[i]==s[j] and dp[i+1][j-1]){
				dp[i][j]=true;
				bestStart=i;
				bestLen=len;
			}
		}
	}

	return s.substr(bestStart,bestLen);
}
Putting length in the outer loop is the whole point of this section. dp[i][j] reads dp[i+1][j-1], which is two characters shorter. Any order that fills [i][j] before that shorter slice is wrong. It gives false values with no error message. An equally good option: loop i downward and j upward from i. That also makes sure the shorter slice is already filled. Chapter 45 extends this to all interval DP.

Wildcard and regex matching

Same table again. This time the interesting logic lives in the special-character branch, because * can match any number of characters — zero, one or many.

// '?' matches exactly one character. '*' matches ANY sequence, including empty.
// dp[i][j] = does s[0..i-1] match p[0..j-1]?
bool isMatch(string &s,string &p){
	int n=s.size();
	int m=p.size();
	vector<vector<bool>> dp(n+1,vector<bool>(m+1,false));

	dp[0][0]=true;                       // empty matches empty

	// a leading run of '*' can match the empty string
	for(int j=1;j<=m;j++){
		if(p[j-1]=='*')dp[0][j]=dp[0][j-1];
	}

	for(int i=1;i<=n;i++){
		for(int j=1;j<=m;j++){
			if(p[j-1]=='*'){
				dp[i][j]=dp[i][j-1]        // '*' matches empty
				       or dp[i-1][j];     // '*' absorbs s[i-1]
			}else if(p[j-1]=='?' or p[j-1]==s[i-1]){
				dp[i][j]=dp[i-1][j-1];
			}
			// else: stays false
		}
	}

	return dp[n][m];
}

The two-way * branch is the trick. dp[i][j-1] means "let * match nothing and move past it". dp[i-1][j] means "let * swallow one more character and stay on it". Together these two options cover a match of any length, with no extra loop. You must set up the dp[0][j] row — otherwise the empty string "" fails to match "*".

Watch * absorb characters one at a time, with s = "ab" and p = "*". dp[0][1] is true (a star matches empty). dp[1][1] = dp[1][0] or dp[0][1] = false or true = true: the star took "a". dp[2][1] = dp[2][0] or dp[1][1] = true: the star took "b" as well. Each step reuses the answer for one fewer character, so a star can cover any length without an inner loop.

// '.' matches one character. 'x*' matches zero or more of x — note that
// '*' here modifies the PRECEDING character, unlike wildcard.
bool isMatch(string &s,string &p){
	int n=s.size();
	int m=p.size();
	vector<vector<bool>> dp(n+1,vector<bool>(m+1,false));

	dp[0][0]=true;

	// patterns like "a*b*c*" can match empty — the star kills its pair
	for(int j=2;j<=m;j++){
		if(p[j-1]=='*')dp[0][j]=dp[0][j-2];
	}

	for(int i=1;i<=n;i++){
		for(int j=1;j<=m;j++){
			if(p[j-1]=='*'){
				char prev=p[j-2];

				dp[i][j]=dp[i][j-2];       // zero occurrences: skip "x*"

				if(prev=='.' or prev==s[i-1])
				dp[i][j]=dp[i][j] or dp[i-1][j];   // one more occurrence
			}else if(p[j-1]=='.' or p[j-1]==s[i-1]){
				dp[i][j]=dp[i-1][j-1];
			}
		}
	}

	return dp[n][m];
}

Regex * is harder than wildcard * because it works as a pair with the character before it (a* means "zero or more a's"). So skipping it means jumping back two positions, j-2, not j-1. The "one more occurrence" branch only applies if that earlier character matches. The empty-string setup loop steps by 2 for the same reason.

Example: s = "aab" and p = "c*a*b" match. c* is used zero times (the dp[i][j-2] branch), a* is used twice (the "one more occurrence" branch, twice), and b matches b. The code reads p[j-2] when it sees a star, which assumes the pattern never starts with *. The standard problem guarantees that; if your input might break the rule, check it first.

Subsequence vs substring: one word changes the recurrence

A subsequence may have gaps. So on a mismatch you can skip a character and keep what you have — hence max(dp[i-1][j], dp[i][j-1]). A substring must be one unbroken block. So a mismatch resets to zero: dp[i][j] = 0. That one change turns LCS into longest common substring:

// dp[i][j] = length of the longest common SUBSTRING ending at s[i-1], t[j-1].
int best=0;

for(int i=1;i<=n;i++){
	for(int j=1;j<=m;j++){
		if(s[i-1]==t[j-1]){
			dp[i][j]=1+dp[i-1][j-1];
			best=max(best,dp[i][j]);   // "ending at" -> max over the table
		}
		// else dp[i][j] stays 0 — the run is broken
	}
}

Note the answer is now the largest value anywhere in the table, not dp[n][m]. That is because a cell now means "a run ending exactly here", not "the first i and j characters" (the distinction from Chapter 39).

Reconstruction

The number alone is often not enough. A diff tool must show which lines changed, and a spell checker must show the suggested word. The walk below starts at the bottom-right cell and retraces the choice each cell made. For "abcde" and "ace": e = e, so take e and move diagonally. Then d ≠ c, and the cell above is at least as big, so drop d. Then c = c, take it. Then b ≠ a, drop b. Then a = a, take it. The collected letters are e, c, a, and reversing them gives "ace". Each step moves up, left, or both, so the walk takes at most n + m steps.

recovering the LCS string and the edit scriptO(n+m)needs the full table
// Walk backwards from dp[n][m], re-deciding which branch produced each cell.
string recoverLCS(string &s,string &t,vector<vector<int>> &dp){
	string ans;
	int i=s.size();
	int j=t.size();

	while(i>0 and j>0){
		if(s[i-1]==t[j-1]){
			ans+=s[i-1];            // this character is in the LCS
			i--;
			j--;
		}else if(dp[i-1][j]>=dp[i][j-1]){
			i--;                     // the better branch came from above
		}else{
			j--;
		}
	}

	reverse(ans.begin(),ans.end());

	return ans;
}
// For edit distance the same walk yields the OPERATIONS: a diagonal move on
// equal characters is "keep", a diagonal move otherwise is "replace",
// moving up is "delete", moving left is "insert".
Rebuilding the answer is why you sometimes keep the full O(n·m) table, even though a one-row version exists (Chapter 38). The walk back needs every cell. At n = m = 1000 that is a million ints — 4 MB, which is fine. If both strings are 10⁵ long, the table is far too big. Then Hirschberg's algorithm recovers the alignment in O(n·m) time and only O(min(n,m)) space, by recursively finding the midpoint of the path. It is worth knowing the name.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 3×3 CORNER
Fill dp[0..2][0..2] by hand for two 2-character strings before writing the loops. Thirty seconds, and it settles the base cases and the indexing at once.
⛔ OFF BY ONE
Row i means "the first i characters", so the character is s[i-1]. Derive that from the state sentence rather than guessing.
💡 LCS ANSWERS FOUR

⚠️
Common mistakes
  • s[i] instead of s[i-1]. Row i is about the first i characters, so the i-th is at index i-1.
  • Zero base cases for edit distance. dp[i][0] is i, not 0 — deleting a whole prefix costs something.
  • Looping i upward for interval DP. dp[i][j] reads the shorter dp[i+1][j-1], so loop by length, or loop i downward.
  • Returning dp[n][m] for longest common substring. A cell there means "ending here", so take the largest value in the table.
  • Forgetting the dp[0][j] row in wildcard matching. A pattern made only of stars must match the empty string.
  • Using j-1 instead of j-2 for regex *. The star pairs with the character before it, so skipping it skips two pattern positions.
  • Mixing up subsequence and substring. On a mismatch, subsequence takes a max; substring resets to 0.
  • Shrinking to one row when you need to rebuild the answer. The walk back needs the whole table.
  • Using one row without saving the diagonal. Edit distance needs dp[i-1][j-1], and a single array overwrites it (Chapter 38).
  • Assuming the LCS is unique. Several subsequences can share the maximum length; the walk back returns just one of them.

Interview drill

Warm-up: Edit distance. Derive the recurrence rather than reciting it.

How a strong answer sounds
I define dp[i][j] as the minimum number of operations to turn the first i characters of s into the first j characters of t. The table is (n+1) × (m+1), so row 0 and column 0 mean "empty prefix". The base cases follow directly. dp[i][0] = i, because turning an i-character string into nothing costs i deletions. dp[0][j] = j, for j insertions. For any other cell I look at the last characters. If s[i−1] equals t[j−1], they line up for free, so dp[i][j] = dp[i−1][j−1] — no operation spent. Otherwise I must spend exactly one operation, and there are three choices: delete s[i−1] and solve dp[i−1][j]; insert t[j−1] and solve dp[i][j−1]; or replace s[i−1] with t[j−1] and solve dp[i−1][j−1]. So dp[i][j] = 1 + the min of those three. Each term is one named operation, which makes the recurrence easy to remember. It is O(n·m) time and space. A rolling row cuts space to O(min(n,m)), but I must save the diagonal value in a temporary before overwriting it, and I lose the ability to rebuild the actual list of edits. Before writing any code I would fill the 3×3 corner for "ab" and "ac" by hand. That settles the base cases and the indexing in half a minute.

Deeper: Longest palindromic subsequence. Two approaches, and why the loop order matters in one of them.

How a strong answer sounds
The quickest answer: a palindromic subsequence of s reads the same forwards and backwards, so it is a subsequence of both s and its reverse. Therefore LPS(s) = LCS(s, reverse(s)). That reuses a table I already know, needs no new recurrence, and is O(n²). A useful bonus: the minimum insertions needed to make s a palindrome is n − LPS. The direct approach is interval DP. dp[i][j] is the length of the longest palindromic subsequence inside s[i..j], with dp[i][i] = 1. If s[i] equals s[j], then dp[i][j] = 2 + dp[i+1][j−1]; otherwise it is max(dp[i+1][j], dp[i][j−1]). Here the loop order is the trap. dp[i][j] depends on dp[i+1][j−1], a shorter interval. Looping i upward from 0 reads cells that are not computed yet, and quietly gets zeros. So I either make interval length the outer loop, or loop i downward and j upward from i. Both make sure every cell I read is already filled. That is the general rule for interval DP, and it comes back in matrix chain multiplication and burst balloons (Chapter 45). I would also separate this from longest palindromic substring, which must be one unbroken block. That one is better solved by expand-around-centre in O(1) space, or by Manacher in O(n).

🧠 Key takeaways

  • Two-string DP is one table over pairs of prefixes. Each cell splits on whether the current characters match. LCS and edit distance differ only in those two branches.
  • Make the table (n+1)×(m+1) so row and column 0 mean "empty". Remember the i-th character is s[i-1].
  • LCS answers four problems: min insert/delete, shortest common supersequence, longest palindromic subsequence, and min insertions to make a palindrome.
  • Interval DP over dp[i][j] must loop by increasing length (or i downward), because each cell reads shorter intervals.
  • Subsequence takes a max on a mismatch. Substring resets to 0, and its answer is the largest value in the table.

Check your understanding

In a two-string DP with dp[i][j] over the first i and j characters, which characters do you compare?

The extra row and column for "empty prefix" force this shift. In return, they remove every special case at the edges. Getting it wrong causes an off-by-one bug that only shows up on the last character.

What are the base cases for edit distance?

Turning an i-character string into nothing costs i deletions. Leaving these at zero is the most common edit-distance bug. It gives answers that are too small.

In interval DP for palindromes, why must the outer loop be the interval length?

Looping i upward reads cells that are still false, and quietly gives wrong answers. Either fix works: length as the outer loop, or i downward with j upward. Both fill the shorter interval first.

Longest common substring differs from longest common subsequence how?

The whole difference is that a substring has no gaps, so a mismatch breaks the run. And because a cell now means "ending at i,j", the last cell is no longer the answer.

How can you compute the longest palindromic subsequence using a function you already have?

No new recurrence needed. You also get a bonus: the minimum insertions to make s a palindrome is n − LPS. (Expand-around-centre is for the substring version, which must have no gaps.)
