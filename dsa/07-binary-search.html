Binary Search (And On The Answer)

Binary search finds something in sorted data by checking the middle and throwing away the half that cannot contain it — like opening a dictionary in the middle and deciding which half your word is in. Everyone knows it, and almost everyone writes it wrong under pressure. The loop condition, the mid update and the return value all have to agree, and four common variants differ by a single character. This chapter fixes that with one invariant (a rule that stays true) you can always fall back on. Then it moves to the technique that matters far more: binary searching the answer, which turns hard “find the best value” problems into easy yes/no questions.

  • Write the classic search from an invariant instead of from memory
  • Work out lower_bound and upper_bound, and know exactly what each returns
  • Spot the “minimise the maximum” wording that means “binary search the answer”
  • Write a yes/no feasibility check and prove it only flips once, from no to yes
  • Handle rotated arrays, duplicates, and searching over real numbers

Why it is hard to get right

First, why bother at all. A linear scan checks every element, so on a million sorted numbers it may need a million checks. Binary search halves the range on each check: 1,000,000 → 500,000 → 250,000 → … → 1. That takes only about 20 halvings, because 2²⁰ is roughly a million. Twenty checks instead of a million is the whole reason this technique exists. It also turns up far beyond arrays: databases search sorted indexes this way, and git bisect finds the commit that broke your build the same way.

Binary search has three moving parts: the loop condition, how you skip past mid, and what you return. All three must fit together. Change one and you must change the others. Most people memorise one combination. Then they meet a problem that needs a different one, and they patch until the sample test passes.

The fix is to write down the invariant first. An invariant is a sentence about your variables that is true before the loop starts and stays true after every pass. Once you have it, every part follows from it.

✍️
My convention: the half-open invariant

[lo, hi) — a “half-open” range: lo is included, hi is not. The invariant is: “the answer, if it exists, is in [lo, hi)”. Everything else follows:

  • The loop runs while(lo<hi). When the range is empty, you are done.
  • hi starts at n, not n-1, because hi itself is not included.
  • To drop the left half, set lo=mid+1. To drop the right half, set hi=mid — never mid-1, because hi is already excluded.
  • When the loop ends, lo == hi, and that single index is where the answer is.

This is the convention std::lower_bound uses. It is also the one that never needs a -1 you have to explain.

classic search — is target present?O(log n)O(1)
// Invariant: if target exists, its index is in [lo,hi).
int search(vector<int> &a,int target){
	int lo=0;
	int hi=a.size();          // exclusive

	while(lo<hi){
		int mid=lo+(hi-lo)/2;   // never (lo+hi)/2 — that overflows

		if(a[mid]==target)return mid;

		if(a[mid]<target)lo=mid+1;   // mid is too small, discard it and everything left
		else hi=mid;                    // mid is too big, discard it and everything right
	}

	return -1;
}
lo+(hi-lo)/2, always. With lo = hi = 2×10⁹, (lo+hi) is too big for a signed 32-bit int. It overflows (wraps around) and becomes negative, so mid is negative and you read outside the array. This was a real bug in Java's standard binary search for nine years. Writing it safely costs nothing.

The four variants

“Find the target” is the easy case. The useful ones find a boundary — such as the first element that is at least some value. They are all the same loop with a different comparison.

Why do boundaries matter more than “is it there?”. Real questions are usually about positions: “how many scores are below 50?”, “where does the first timestamp after 9:00 start?”, “how many copies of 7 are there?”. Each one is a boundary. Here is a small example to keep in mind while reading the tabs. With a = [1, 3, 3, 3, 7] and target = 3:

  • lower_bound = 1, the first index holding something ≥ 3.
  • upper_bound = 4, the first index holding something > 3 (that is the 7).
  • last < target = 1 − 1 = 0 (the 1), and last ≤ target = 4 − 1 = 3 (the last 3).
  • count of 3 = 4 − 1 = 3.

For target = 5, which is missing, both bounds return 4, and the count is 4 − 4 = 0. For target = 9, bigger than everything, both return 5 (that is, n) — so always check the result is less than n before you read a[result].

// First index with a[i] >= target. Returns n if every element is smaller.
// Invariant: everything left of lo is < target; everything at or right of hi is >= target.
int lowerBound(vector<int> &a,int target){
	int lo=0;
	int hi=a.size();

	while(lo<hi){
		int mid=lo+(hi-lo)/2;

		if(a[mid]<target)lo=mid+1;
		else hi=mid;
	}

	return lo;
}

The most useful variant of all. It also answers “where would I insert target to keep the array sorted?” — which is why its result is called the insertion point.

// First index with a[i] > target. The ONLY change is < becoming <=.
int upperBound(vector<int> &a,int target){
	int lo=0;
	int hi=a.size();

	while(lo<hi){
		int mid=lo+(hi-lo)/2;

		if(a[mid]<=target)lo=mid+1;
		else hi=mid;
	}

	return lo;
}

Just one character different from lowerBound. That is the skeleton-reuse rule again: learn the shape, then learn where the comparison goes.

// Last index with a[i] < target. Just lowerBound minus one.
// Returns -1 if no such element exists — check for that.
int lastBelow(vector<int> &a,int target){
	return lowerBound(a,target)-1;
}

// Last index with a[i] <= target. upperBound minus one.
int lastAtMost(vector<int> &a,int target){
	return upperBound(a,target)-1;
}

Never write a separate loop for these. Build them from the two bounds you already trust. Every extra hand-written loop is another chance to get a boundary wrong.

// How many times does target appear? The two bounds sandwich it.
int countOf(vector<int> &a,int target){
	return upperBound(a,target)-lowerBound(a,target);
}

// The STL gives you both at once:
// auto [first,last]=equal_range(a.begin(),a.end(),target);
// int count=last-first;

Two O(log n) calls, no special cases, and it correctly returns 0 when the target is missing. This also solves the “find first and last position” problem.

📛
The STL names are backwards from what you expect

lower_bound returns the first element ≥ target (not <). upper_bound returns the first element > target. Both return iterators, and both return end() if nothing matches. Neither tells you whether the target was actually found — for that, check it != end() and *it == target. One more thing: on a set or map, use the member version s.lower_bound(x), not std::lower_bound(s.begin(), s.end(), x). The general function cannot jump straight to the middle of a tree, so it has to walk step by step and becomes O(n).

Binary search on the answer — the real skill

This shift unlocks a whole level of harder problems. Sometimes there is no sorted array to search at all. Instead, there is a range of possible answers, and a yes/no question you can ask about any candidate — one that only gets easier to satisfy as the candidate gets larger.

The pattern: guess an answer x and ask “is x good enough?” (is it feasible?). If the answers are monotone — no, no, no, yes, yes, yes, never flipping back — then binary search can find the point where “no” turns into “yes”.

Think of finding the lowest oven temperature that bakes a cake in an hour. Every temperature above the right one also works, every one below does not. You do not need to try them all; you can halve your way to the boundary.

A predicate is just a function that returns true or false — here, feasible(x). Notice that binary search on an array is secretly the same thing. lower_bound is “find the first index where a[i] >= target is true”, and because the array is sorted that test reads F, F, F, T, T. Searching the answer only swaps the array index for a candidate value, and the array lookup for your own check. The loop itself does not change at all.

The three questions that identify search-on-answer
  1. What range can the answer be in? A capacity is between max(single item) and sum(all items). A speed is between 1 and max(pile). Get these limits right, or you search the wrong range.
  2. Can I check one candidate cheaply? Usually with a simple greedy O(n) sweep. If one check costs more than O(n log n), the whole approach loses its advantage.
  3. Does the check only flip once? If capacity x works, does x+1 also work? Say why, in one sentence. If you cannot, the check probably is not monotone, and this is the wrong technique.

The canonical example: split an array into K parts

You are given an array and a number K. Split the array into K contiguous pieces so that the largest piece sum is as small as possible. There is no obvious greedy rule, and the DP solution is O(n²K). But the answer is a number between max(a) and sum(a). And the question “can I do it so that no piece sums to more than x?” is easy to answer with one greedy pass.

A worked example. Let a = [7, 2, 5, 10, 8] and K = 2. The answer lies between max(a) = 10 (every piece holds at least one element, so the largest piece is at least 10) and sum(a) = 32 (one piece holding everything). Now test a few candidates with the greedy check, which keeps adding elements to the current piece until the next one would push it over the cap:

  • cap = 21: 7+2+5 = 14, adding 10 gives 24 > 21, so cut. Next piece 10+8 = 18. Two pieces — feasible.
  • cap = 15: 7+2+5 = 14, cut. 10, adding 8 gives 18 > 15, cut. 8. Three pieces — not feasible.
  • cap = 18: 14, cut. 10+8 = 18, which fits exactly. Two pieces — feasible.
  • cap = 17: 14, cut. 10, then 18 > 17, cut. 8. Three pieces — not feasible.

So 17 fails and 18 works: the answer is 18, the split [7,2,5] [10,8]. The binary search reaches it in about log₂(32 − 10) ≈ 5 checks instead of trying all 23 candidates.

splitArray — minimise the largest subarray sumO(n log(sum))O(1)
// Feasibility: can we split into at most k parts with no part exceeding cap?
// Greedy is optimal here: extend the current part until it would overflow,
// then cut. Cutting later is never worse, so no part is wasted.
bool canSplit(vector<int> &a,int k,long long cap){
	int parts=1;
	long long running=0;

	for(int x:a){
		if(running+x>cap){
			parts++;
			running=x;          // start a new part with the current element

			if(parts>k)return false;
		}else{
			running+=x;
		}
	}

	return true;
}
// Monotone because a bigger cap can only ever need fewer cuts.
// Range: lo = max(a) (a single element must fit), hi = sum(a) (one part).
int splitArray(vector<int> &a,int k){
	long long lo=0;
	long long hi=0;

	for(int x:a){
		lo=max(lo,(long long)x);
		hi+=x;
	}

	while(lo<hi){
		long long mid=lo+(hi-lo)/2;

		if(canSplit(a,k,mid))hi=mid;     // feasible -> try smaller
		else lo=mid+1;                    // infeasible -> must go bigger
	}

	return lo;
}
The same twelve lines solve at least a dozen well-known problems: Koko eating bananas, capacity to ship packages in D days, minimum time to complete trips, magnetic force between balls, minimum days to make bouquets, allocate minimum pages. Only the canSplit check changes.
🗝️
The phrasings that mean “binary search the answer”
  • “Minimise the maximum …” or “maximise the minimum …”
  • “Find the smallest capacity / speed / size such that …”
  • “At least K things fit within a budget of …”
  • “Can it be done in D days? Find the smallest D.”
  • The limit on how big the answer can be (e.g. values ≤ 10⁹) is large while n is small. The log is taken over the range of values, not over n.

Rotated arrays and the duplicate problem

A rotated sorted array is a sorted array that was cut in two and had its halves swapped, like [4,5,6,1,2,3]. It is not sorted as a whole, but it is made of two sorted pieces. So whenever you split it in the middle, one half is always properly sorted — and you can tell which.

The test to use is a[mid] > a[hi]. If the middle value is bigger than the last value, the “drop” back to small numbers must happen somewhere between them, so the minimum is to the right of mid. Otherwise the stretch from mid to hi is sorted, so the minimum is mid or something to its left. Comparing with a[lo] instead does not work: in the unrotated array [1,2,3,4], a[mid] > a[lo] is true, yet the minimum is on the left, not the right.

Dry run on [4,5,6,1,2,3]: lo = 0, hi = 5, mid = 2, a[2] = 6 > a[5] = 3, so lo = 3. Then mid = 4, a[4] = 2 < 3, so hi = 4. Then mid = 3, a[3] = 1 < a[4] = 2, so hi = 3. Now lo == hi == 3 and a[3] = 1 is the minimum. Also check the edge cases in your head: an array that was not rotated at all (the test always sends you left and you end at index 0), and a single element (the loop never runs).

findMin in a rotated sorted arrayO(log n) — but see belowO(1)
// Compare mid against hi, not against lo. The minimum is the only element
// smaller than its predecessor, and comparing to the right end localises it.
int findMin(vector<int> &a){
	int lo=0;
	int hi=a.size()-1;          // inclusive here: we compare a[mid] with a[hi]

	while(lo<hi){
		int mid=lo+(hi-lo)/2;

		if(a[mid]>a[hi]){
			lo=mid+1;               // minimum is strictly right of mid
		}else if(a[mid]<a[hi]){
			hi=mid;                  // mid could BE the minimum
		}else{
			hi--;                    // equal: cannot tell. Shrink by one.
		}                            // THIS is what makes it O(n) worst case
	}

	return a[lo];
}
With duplicates, this is O(n) in the worst case, not O(log n). On [1,1,1,1,0,1,1] the a[mid]==a[hi] branch runs again and again, and you shrink one element at a time. There is no way around it: no algorithm can beat O(n) here. [1,1,…,1] and [1,…,1,0,1,…,1] can differ in just one position you have not looked at yet. Say this out loud in an interview — it is exactly the follow-up they are waiting for.

Binary search over real numbers

When the answer is a real number (like 2.718…), there is no “next” value to close in on, so you cannot loop until lo == hi. There are two options, and the second is better.

Note two small changes from the integer version. You write lo = mid rather than mid + 1, because on the real line there is no “next” number to skip to. And (lo+hi)/2 is fine for a double, because doubles do not wrap around the way ints do. A typical use: find √2 with feasible(x) = x*x >= 2, lo = 0, hi = 2. After the first halving the range is [1, 2], then [1, 1.5], then [1.25, 1.5], then [1.375, 1.5], closing in on 1.41421… Other common uses are “the largest average”, “the smallest radius that covers every point”, and physics-style questions with a real-valued answer.

Epsilon-based — fragile
while(hi-lo>1e-9){
	double mid=(lo+hi)/2;

	if(feasible(mid))hi=mid;
	else lo=mid;
}
return lo;

Choosing epsilon (the “close enough” gap) is guesswork. Too large, and your answer is not precise enough. Too small, and the loop may never end, because floating-point rounding stops the gap from shrinking.

Fixed iterations — robust
// 100 halvings shrinks any starting range by 2^-100.
// Far more precision than a double can hold, and it always terminates.
for(int iter=0;iter<100;iter++){
	double mid=(lo+hi)/2;

	if(feasible(mid))hi=mid;
	else lo=mid;
}
return lo;

Use this. It always ends, it is always precise enough, and there is one less setting to tune. 100 rounds of tiny work cost nothing.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 ONE TEMPLATE
Use while(low<high), high=mid on success, low=mid+1 otherwise, return low. It finds the first true in a monotone predicate and has no final comparison to get wrong.
💡 ON THE ANSWER
"Minimise the maximum" or "maximise the minimum" with a huge answer range means binary-search the answer, with an O(n) feasibility check. Verify monotonicity out loud before you code it.
⛔ MIDPOINT
Write low + (high-low)/2. (low+high)/2 overflows once the bounds approach INT_MAX, which is exactly where binary-search-on-answer lives.
⚠️
Common mistakes
  • mid = (lo+hi)/2. Overflows for large indices or large value ranges. Always write lo+(hi-lo)/2.
  • Mixing conventions. hi = n with while(lo<=hi) reads past the end; hi = n-1 with hi = mid can loop forever. Pick half-open and stick with it.
  • hi = mid-1 in the half-open convention. hi is already excluded, so setting it to mid removes mid. Subtracting one more skips a candidate.
  • Not checking the yes/no test only flips once before searching the answer. If it is not FFFFTTTT, binary search confidently returns a wrong number, and no test tells you why.
  • Getting the answer range wrong. If lo = 1 but a single element is already bigger than that, or hi is too small to hold the answer, the search ends at the edge of the range instead of at the answer.
  • Claiming O(log n) for rotated search with duplicates. It is O(n) in the worst case, and knowing that is the point of the question.
  • Using std::lower_bound on a set. The general function needs to jump to any position; on a tree it has to walk and becomes O(n). Use the member function.
  • Forgetting the search is over the range of values. O(n log(sum)) is not O(n log n). With values up to 10¹⁴ the log is about 47, not 17.

Interview drill

Warm-up: Koko can eat bananas at speed k per hour and has H hours to finish N piles. Find the minimum k. Talk me through it.

How a strong answer sounds
There is no formula and no obvious greedy. But the answer is a number, and I can test any candidate cheaply — that combination says “binary search the answer”. The range is 1 to max(pile). Speed 1 is the slowest sensible choice, and any speed above the largest pile still takes one hour per pile, so nothing above max(pile) can help. For a candidate k, the hours needed are the sum of ceil(pile/k) over all piles, which is O(n). k is feasible if that total is at most H. Does it only flip once? Yes: a larger k never increases any ceil(pile/k), so once a speed works, every larger speed works too. The check looks like FFFF…TTTT, and I want the first T. So I binary search on [1, max(pile)] with the half-open convention: move hi down to mid when feasible, lo up to mid+1 when not, and return lo. Total O(n log(max pile)). Two implementation notes: compute the ceiling as (pile + k − 1) / k instead of using floating point, and add up the hours in a long long, since n × max(pile) can be too big for 32 bits.

Deeper: Why is searching a rotated sorted array O(n) rather than O(log n) once duplicates are allowed?

How a strong answer sounds
Binary search works by throwing away half the range, and to do that you must know which half is sorted. Without duplicates, comparing a[mid] to a[hi] always tells you. With duplicates, you can hit a[mid] == a[hi] and learn nothing — the rotation point could be on either side. The only safe move is to shrink the range by one, which is a linear step. And this is not a flaw in this particular algorithm; it is a limit on what any algorithm can know. Compare [1,1,1,1,1,1] with the same array with a single 0 hidden somewhere. Any algorithm that has not looked at that exact position cannot tell them apart, so the worst case needs Ω(n) comparisons (at least on the order of n). In practice it stays O(log n) on typical inputs and only drops to O(n) when there are long runs of equal values. I would state both bounds rather than quote only the hopeful one.

🧠 Key takeaways

  • Write the invariant first. Then the loop condition, the mid update and the return value follow from it instead of being guessed.
  • Half-open [lo, hi) with while(lo<hi) and hi=mid never needs an unexplained -1.
  • lower_bound and upper_bound differ by one character, and every other boundary question can be built from them.
  • “Minimise the maximum” means binary search the answer: set the range, write an O(n) yes/no check, and prove it only flips once.
  • Duplicates make rotated search O(n) in the worst case. That is a hard limit for any algorithm, not a flaw in yours.

Check your understanding

Why write mid = lo + (hi-lo)/2 instead of mid = (lo+hi)/2?

With lo and hi near 2×10⁹, the sum wraps around to a negative number and you read outside the array. This was a real bug in Java's library for nine years. It matters most when you binary search a range of values rather than indices.

In the half-open convention [lo, hi), what do you do when a[mid] is too large?

hi is never part of the range, so setting it to mid already removes mid. Writing mid-1 removes one element too many and can skip the answer.

Which phrasing most strongly signals “binary search on the answer”?

“Minimise the maximum” (or “maximise the minimum”) is the giveaway. You guess a limit, check whether it is achievable with a greedy sweep, and use the fact that a looser limit is never harder to meet.

Before binary searching an answer space, what must you verify?

Monotonicity (the check flips from false to true only once) is the only thing that lets you throw away half the range. The input array does not need to be sorted at all. Without monotonicity, you get a confidently wrong answer, and no test will tell you why.

Finding the minimum in a rotated sorted array with duplicates has what worst-case complexity?

When mid and hi are equal, the rotation point could be on either side, so the only safe step is to shrink by one. And no algorithm can do better: [1,1,…,1] and the same array with one 0 hidden somewhere look identical until you check that exact position.
