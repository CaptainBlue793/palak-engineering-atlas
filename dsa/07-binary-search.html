Binary Search (And On The Answer)

Everyone knows binary search and almost everyone writes it wrong under pressure — the loop condition, the mid update and the return value have to agree, and there are four common variants that differ by a single character. This chapter fixes that with one invariant you can always fall back on, then moves to the technique that matters far more: binary searching the answer space, which converts hard optimisation problems into easy yes/no questions.

  • Write the classic search from an invariant instead of from memory
  • Derive lower_bound and upper_bound, and know exactly what each returns
  • Recognise the “minimise the maximum” phrasing that signals search-on-answer
  • Write a monotone feasibility predicate and prove it is monotone
  • Handle rotated arrays, duplicates, and search over real numbers

Why it is hard to get right

Binary search has three moving parts — the loop condition, how mid is excluded, and what you return — and they must be mutually consistent. Change one and you must change the others. Most people memorise one combination, then meet a problem that needs a different one and patch until the sample passes.

The fix is to write down the invariant first. Then every part is forced.

✍️
My convention: the half-open invariant

[lo, hi) — lo inclusive, hi exclusive. The invariant is: “the answer, if it exists, is in [lo, hi)”. From that:

  • The loop runs while(lo<hi) — an empty range means done.
  • hi starts at n, not n-1, because it is exclusive.
  • Discarding the left half is lo=mid+1; discarding the right half is hi=mid — never mid-1, because hi was never included.
  • When the loop ends, lo == hi and that single index is the answer position.

This is the convention std::lower_bound uses, and it is also the one that never needs a -1 that you have to justify.

classic search — is target present?O(log n)O(1)
// Invariant: if target exists, its index is in [lo,hi).
int search(vector<int> &a,int target){
	int lo=0;
	int hi=a.size();          // exclusive

	while(lo<hi){
		int mid=lo+(hi-lo)/2;   // never (lo+hi)/2 — that overflows

		if(a[mid]==target)return mid;

		if(a[mid]<target)lo=mid+1;   // mid is too small, discard it and everything left
		else hi=mid;                    // mid is too big, discard it and everything right
	}

	return -1;
}
lo+(hi-lo)/2, always. With lo = hi = 2×10⁹, (lo+hi) overflows a signed 32-bit int and becomes negative, so mid is negative and you index out of bounds. This was a real bug in the JDK's binary search for nine years. It costs nothing to write it safely.

The four variants

“Find the target” is the easy case. The useful cases are the boundary ones, and they are all the same loop with a different comparison.

// First index with a[i] >= target. Returns n if every element is smaller.
// Invariant: everything left of lo is < target; everything at or right of hi is >= target.
int lowerBound(vector<int> &a,int target){
	int lo=0;
	int hi=a.size();

	while(lo<hi){
		int mid=lo+(hi-lo)/2;

		if(a[mid]<target)lo=mid+1;
		else hi=mid;
	}

	return lo;
}

The single most useful variant. Also answers "where would I insert target to keep the array sorted?" — which is why it is called the insertion point.

// First index with a[i] > target. The ONLY change is < becoming <=.
int upperBound(vector<int> &a,int target){
	int lo=0;
	int hi=a.size();

	while(lo<hi){
		int mid=lo+(hi-lo)/2;

		if(a[mid]<=target)lo=mid+1;
		else hi=mid;
	}

	return lo;
}

One character apart from lowerBound. That is the skeleton-reuse rule again: learn the shape, learn where the comparison goes.

// Last index with a[i] < target. Just lowerBound minus one.
// Returns -1 if no such element exists — check for that.
int lastBelow(vector<int> &a,int target){
	return lowerBound(a,target)-1;
}

// Last index with a[i] <= target. upperBound minus one.
int lastAtMost(vector<int> &a,int target){
	return upperBound(a,target)-1;
}

Never write a separate loop for these. Derive them from the two bounds you already trust. A second hand-written loop is a second chance to get a boundary wrong.

// How many times does target appear? The two bounds sandwich it.
int countOf(vector<int> &a,int target){
	return upperBound(a,target)-lowerBound(a,target);
}

// The STL gives you both at once:
// auto [first,last]=equal_range(a.begin(),a.end(),target);
// int count=last-first;

Two O(log n) calls, no special cases, and it returns 0 correctly when the target is absent. This is also the "find first and last position" problem.

📛
The STL names are backwards from what you expect

lower_bound returns the first element ≥ target (not <). upper_bound returns the first element > target. Both return iterators, both return end() if nothing qualifies, and neither tells you whether the target was found — for that, check it != end() and *it == target. Also: on a set or map, use the member s.lower_bound(x), not std::lower_bound(s.begin(), s.end(), x) — the free function on a non-random-access iterator degrades to O(n) because it cannot jump.

Binary search on the answer — the real skill

Here is the shift that unlocks a whole difficulty tier. Sometimes there is no sorted array to search. Instead, there is a range of possible answers, and a question you can ask about any candidate that gets easier as the candidate gets larger.

The pattern: guess an answer x, ask “is x feasible?”, and if the answer to that question is monotone — false, false, false, true, true, true — then binary search finds the boundary.

The three questions that identify search-on-answer
  1. What is the answer's range? A capacity is between max(single item) and sum(all items). A speed is between 1 and max(pile). Get these bounds right or you search the wrong space.
  2. Can I check one candidate cheaply? Usually a greedy O(n) sweep. If checking costs more than O(n log n), the whole approach loses its edge.
  3. Is the check monotone? If capacity x works, does x+1 also work? Say why, in one sentence. If you cannot, the predicate probably is not monotone and this is the wrong technique.

The canonical example: split an array into K parts

Given an array and an integer K, split it into K contiguous subarrays so that the largest subarray sum is as small as possible. There is no obvious greedy and the DP is O(n²K). But the answer is a number between max(a) and sum(a), and asking “can I do it with largest sum ≤ x?” is a linear greedy.

splitArray — minimise the largest subarray sumO(n log(sum))O(1)
// Feasibility: can we split into at most k parts with no part exceeding cap?
// Greedy is optimal here: extend the current part until it would overflow,
// then cut. Cutting later is never worse, so no part is wasted.
bool canSplit(vector<int> &a,int k,long long cap){
	int parts=1;
	long long running=0;

	for(int x:a){
		if(running+x>cap){
			parts++;
			running=x;          // start a new part with the current element

			if(parts>k)return false;
		}else{
			running+=x;
		}
	}

	return true;
}
// Monotone because a bigger cap can only ever need fewer cuts.
// Range: lo = max(a) (a single element must fit), hi = sum(a) (one part).
int splitArray(vector<int> &a,int k){
	long long lo=0;
	long long hi=0;

	for(int x:a){
		lo=max(lo,(long long)x);
		hi+=x;
	}

	while(lo<hi){
		long long mid=lo+(hi-lo)/2;

		if(canSplit(a,k,mid))hi=mid;     // feasible -> try smaller
		else lo=mid+1;                    // infeasible -> must go bigger
	}

	return lo;
}
The same twelve lines solve at least a dozen named problems. Koko eating bananas, capacity to ship packages in D days, minimum time to complete trips, magnetic force between balls, minimum days to make bouquets, allocate minimum pages. Only canSplit changes.
🗝️
The phrasings that mean “binary search the answer”
  • “Minimise the maximum …” or “maximise the minimum …”
  • “Find the smallest capacity / speed / size such that …”
  • “At least K things fit within a budget of …”
  • “Can it be done in D days? Find the smallest D.”
  • The constraint on the answer's magnitude (e.g. values ≤ 10⁹) is large while n is small — the log is over the value range, not over n.

Rotated arrays and the duplicate problem

A rotated sorted array is not sorted, but it is piecewise sorted — so one half of any split is always properly sorted, and you can tell which.

findMin in a rotated sorted arrayO(log n) — but see belowO(1)
// Compare mid against hi, not against lo. The minimum is the only element
// smaller than its predecessor, and comparing to the right end localises it.
int findMin(vector<int> &a){
	int lo=0;
	int hi=a.size()-1;          // inclusive here: we compare a[mid] with a[hi]

	while(lo<hi){
		int mid=lo+(hi-lo)/2;

		if(a[mid]>a[hi]){
			lo=mid+1;               // minimum is strictly right of mid
		}else if(a[mid]<a[hi]){
			hi=mid;                  // mid could BE the minimum
		}else{
			hi--;                    // equal: cannot tell. Shrink by one.
		}                            // THIS is what makes it O(n) worst case
	}

	return a[lo];
}
With duplicates, this is O(n) in the worst case, not O(log n). On [1,1,1,1,0,1,1] the a[mid]==a[hi] branch fires repeatedly and you shrink one element at a time. That is unavoidable: no algorithm can beat O(n) here, because [1,1,…,1] and [1,…,1,0,1,…,1] can differ in one unexamined position. Say this out loud in an interview — it is exactly the follow-up they are waiting for.

Binary search over real numbers

When the answer is a real number there is no “adjacent” value to converge on, so you cannot loop until lo == hi. Two options, and the second is better.

Epsilon-based — fragile
while(hi-lo>1e-9){
	double mid=(lo+hi)/2;

	if(feasible(mid))hi=mid;
	else lo=mid;
}
return lo;

Picking epsilon is a judgement call: too large and you fail precision checks, too small and you may never terminate because of floating-point rounding.

Fixed iterations — robust
// 100 halvings shrinks any starting range by 2^-100.
// Far more precision than a double can hold, and it always terminates.
for(int iter=0;iter<100;iter++){
	double mid=(lo+hi)/2;

	if(feasible(mid))hi=mid;
	else lo=mid;
}
return lo;

Use this. Guaranteed to terminate, guaranteed precise, and one less parameter to tune. 100 iterations of trivial work costs nothing.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 ONE TEMPLATE
Use while(low<high), high=mid on success, low=mid+1 otherwise, return low. It finds the first true in a monotone predicate and has no final comparison to get wrong.
💡 ON THE ANSWER
"Minimise the maximum" or "maximise the minimum" with a huge answer range means binary-search the answer, with an O(n) feasibility check. Verify monotonicity out loud before you code it.
⛔ MIDPOINT
Write low + (high-low)/2. (low+high)/2 overflows once the bounds approach INT_MAX, which is exactly where binary-search-on-answer lives.
⚠️
Common mistakes
  • mid = (lo+hi)/2. Overflows for large indices or large value ranges. Always lo+(hi-lo)/2.
  • Mixing conventions. hi = n with while(lo<=hi) reads out of bounds; hi = n-1 with hi = mid can loop forever. Pick half-open and stay there.
  • hi = mid-1 in the half-open convention. hi is exclusive, so mid was never in the range — subtracting again skips a candidate.
  • Not proving monotonicity before searching the answer. If the predicate is not FFFFTTTT, binary search returns a confidently wrong number and no test explains why.
  • Getting the answer range wrong. lo = 1 when a single element already exceeds it, or hi too small to contain the answer, and the search converges on the boundary instead of the answer.
  • Claiming O(log n) for rotated search with duplicates. It is O(n) worst case, and knowing that is the point of the question.
  • Using std::lower_bound on a set. The free function needs random access; on a tree iterator it degrades to O(n). Use the member function.
  • Forgetting the search is over the value range. O(n log(sum)) is not O(n log n); with values up to 10¹⁴ the log is about 47, not 17.

Interview drill

Warm-up: Koko can eat bananas at speed k per hour and has H hours to finish N piles. Find the minimum k. Talk me through it.

How a strong answer sounds
There is no formula and no obvious greedy, but the answer is a number and I can test any candidate cheaply — that combination says binary search the answer. The range is 1 to max(pile): speed 1 is the slowest meaningful choice, and any speed above the largest pile finishes it in the same one hour, so nothing above max(pile) can help. For a candidate k, the time needed is the sum of ceil(pile/k) over all piles, which is O(n). Feasible means that total is at most H. Monotonicity: a larger k never increases any ceil(pile/k), so once a speed works every larger speed works — the predicate is FFFF…TTTT, and I want the first T. So I binary search on [1, max(pile)] with the half-open convention, moving hi down to mid when feasible and lo up to mid+1 when not, and return lo. Total O(n log(max pile)). Two implementation notes: compute the ceiling as (pile + k − 1) / k rather than with floating point, and accumulate the hours in a long long since n × max(pile) can exceed 32 bits.

Deeper: Why is searching a rotated sorted array O(n) rather than O(log n) once duplicates are allowed?

How a strong answer sounds
Binary search works by discarding half the range, which requires being able to tell which half is sorted. Without duplicates, comparing a[mid] to a[hi] always resolves that. With duplicates you can hit a[mid] == a[hi] and learn nothing — the pivot could be on either side. The only safe move is to shrink the boundary by one, which is a linear step. And that is not a weakness of this particular algorithm; it is information-theoretic. Consider [1,1,1,1,1,1] versus the same array with a single 0 hidden anywhere: any algorithm that has not examined that exact position cannot distinguish them, so worst case Ω(n) comparisons are required. The practical answer is that it stays O(log n) on typical inputs and degrades to O(n) only when there are long runs of equal values, and I would state both bounds rather than quote the optimistic one.

🧠 Key takeaways

  • Write the invariant first; the loop condition, the mid update and the return value are then forced rather than guessed.
  • Half-open [lo, hi) with while(lo<hi) and hi=mid never needs an unexplained -1.
  • lower_bound and upper_bound differ by one character, and every other boundary query derives from them.
  • “Minimise the maximum” means binary search the answer: define the range, write an O(n) feasibility check, prove it is monotone.
  • Duplicates make rotated search O(n) worst case, and that is a lower bound, not a defect.

Check your understanding

Why write mid = lo + (hi-lo)/2 instead of mid = (lo+hi)/2?

With lo and hi near 2×10⁹ the sum wraps negative and you index out of bounds. This was a real JDK bug for nine years. It matters especially when binary searching a value range rather than indices.

In the half-open convention [lo, hi), what do you do when a[mid] is too large?

Since hi is never part of the range, setting it to mid already excludes mid. Writing mid-1 excludes mid twice and can skip the answer.

Which phrasing most strongly signals “binary search on the answer”?

“Minimise the maximum” (or “maximise the minimum”) is the signature. You guess the bound, check feasibility with a greedy sweep, and exploit the fact that a looser bound is never harder to satisfy.

Before binary searching an answer space, what must you verify?

Monotonicity is the entire licence to discard half the range. The input array need not be sorted at all. Without monotonicity you get a confidently wrong answer and no test will tell you why.

Finding the minimum in a rotated sorted array with duplicates has what worst-case complexity?

When mid and hi are equal the pivot could be on either side, so the only safe step is linear. And it is a genuine lower bound: [1,1,…,1] and the same array with one 0 hidden somewhere are indistinguishable without examining that position.
