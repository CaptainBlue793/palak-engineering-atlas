Binary Search Trees

A BST adds one rule to a binary tree and gets O(h) search in return. The rule is stricter than most people remember — it constrains a node against its entire subtree, not just its two children — and almost every BST bug comes from forgetting that. The other thing to internalise: inorder traversal of a BST is sorted, which converts a surprising number of tree problems into array problems you already know.

  • State the BST invariant precisely, and see the tree that the naive check accepts
  • Implement search, insert and the three-case delete
  • Use inorder for validation, Kth smallest, successor and minimum difference
  • Build a balanced BST from a sorted array
  • Explain why a BST degenerates, and what Chapter 20 does about it

The invariant — and the mistake

For every node: every value in its left subtree is smaller, and every value in its right subtree is larger. Not “the left child is smaller” — the entire left subtree.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 IN-ORDER IS SORTED
Nearly every BST problem reduces to "the in-order traversal is sorted". Validate, k-th smallest, minimum difference and two-sum all fall out of that one fact.
💡 RANGE, NOT PARENT
Validate a BST by passing down (low, high) bounds, not by comparing with the parent. The parent check accepts trees that are locally fine and globally wrong.
⛔ DELETE TWO CHILDREN
Deleting a two-child node means replacing it with its in-order successor and then deleting that. Handle the zero- and one-child cases first and the third becomes short.
💥
The naive validation accepts a tree that is not a BST

Checking only left->val < root->val < right->val at each node passes this tree:

        10
       /  \
      5    15
          /  \
        6    20      // 6 < 15 ✓ locally, but 6 < 10 and it is in 10's RIGHT subtree ✗

Every parent-child pair is individually fine. But 6 sits in 10's right subtree while being smaller than 10, so a search for 6 starting at the root would go right and never find it. The correct check passes a valid range down the tree — that is a preorder pattern, which is why validation is the one BST problem that is not inorder.

isValidBST — two correct waysO(n)O(h)
// WAY 1: pass a valid (lo,hi) range down. Preorder, because the constraint
// flows from ancestors to descendants. Use long long so INT_MIN/INT_MAX
// node values do not collide with the sentinels.
bool valid(TreeNode* root,long long lo,long long hi){
	if(!root)return true;

	if(root->val<=lo or root->val>=hi)return false;

	return valid(root->left,lo,root->val)
	   and valid(root->right,root->val,hi);
}
bool isValidBST(TreeNode* root){
	return valid(root,LLONG_MIN,LLONG_MAX);
}

// WAY 2: inorder must be strictly increasing. Keep only the previous value —
// no need to build the whole vector.
bool check(TreeNode* root,TreeNode* &prev){
	if(!root)return true;

	if(!check(root->left,prev))return false;

	if(prev and prev->val>=root->val)return false;
	prev=root;

	return check(root->right,prev);
}
bool isValidBST2(TreeNode* root){
	TreeNode* prev=nullptr;

	return check(root,prev);
}
long long for the sentinels is not paranoia. If a node genuinely holds INT_MIN, then root->val <= lo with lo = INT_MIN is true and a perfectly valid tree is rejected. Widening the range type fixes it. Note also TreeNode* &prev in way 2 — a reference, because the previous node is state shared across the whole traversal, not per branch.

Search, insert, delete

search and insertO(h)O(1) iterative
// Search: the invariant tells you which way to go. No backtracking, ever.
TreeNode* searchBST(TreeNode* root,int target){
	while(root){
		if(root->val==target)return root;

		if(target<root->val)root=root->left;
		else root=root->right;
	}

	return nullptr;
}

// Insert: walk to the null slot where the value belongs, and put it there.
// A new value always becomes a LEAF — no restructuring needed.
TreeNode* insertIntoBST(TreeNode* root,int val){
	if(!root)return new TreeNode(val);

	if(val<root->val)root->left=insertIntoBST(root->left,val);
	else if(val>root->val)root->right=insertIntoBST(root->right,val);

	return root;                  // equal -> ignore (or count duplicates)
}
The root->left = insert(...) pattern — assigning the recursive result back — is how you handle "the subtree may now have a different root" without needing parent pointers. It costs nothing when the root does not change and is essential when it does, which is why the same shape appears in delete and in every rotation in Chapter 20.
deleteNode — the three casesO(h)O(h)
// Case 1: leaf           -> just remove it
// Case 2: one child      -> the child takes its place
// Case 3: two children   -> replace the VALUE with the inorder successor,
//                           then delete the successor (which has at most
//                           one child, so it reduces to case 1 or 2)
TreeNode* deleteNode(TreeNode* root,int key){
	if(!root)return nullptr;

	if(key<root->val){
		root->left=deleteNode(root->left,key);
	}else if(key>root->val){
		root->right=deleteNode(root->right,key);
	}else{
		// found it
		if(!root->left){
			TreeNode* child=root->right;
			delete root;
			return child;               // covers case 1 and 2
		}
		if(!root->right){
			TreeNode* child=root->left;
			delete root;
			return child;
		}

		// case 3: leftmost node of the right subtree = inorder successor
		TreeNode* succ=root->right;
		while(succ->left)
		succ=succ->left;

		root->val=succ->val;               // copy the VALUE up
		root->right=deleteNode(root->right,succ->val);   // then delete it
	}

	return root;
}
Why the successor works. The inorder successor is the smallest value greater than the deleted one, so it is larger than everything in the left subtree and smaller than everything else in the right — exactly the property the slot needs. It is the leftmost node of the right subtree, so it has no left child, which is why deleting it recursively cannot recurse into case 3 again. (The inorder predecessor — rightmost of the left subtree — works symmetrically.)

Inorder is the superpower

Inorder on a BST yields sorted values. That single fact converts a whole family of tree problems into array problems you have already solved.

kthSmallest and the BST iteratorO(h + k)O(h)
// Early-exit inorder. k is a reference so the countdown is shared;
// once it reaches 0 we stop descending anywhere.
void inorderKth(TreeNode* root,int &k,int &ans){
	if(!root or k==0)return;

	inorderKth(root->left,k,ans);

	k--;
	if(k==0){
		ans=root->val;
		return;
	}

	inorderKth(root->right,k,ans);
}
int kthSmallest(TreeNode* root,int k){
	int ans=-1;
	inorderKth(root,k,ans);

	return ans;
}

// BSTIterator: the iterative inorder from Chapter 16, PAUSED between calls.
// The stack holds exactly "nodes whose left subtree is done, not yet visited".
class BSTIterator{
	stack<TreeNode*> st;

	void pushLeft(TreeNode* node){
		while(node){
			st.push(node);
			node=node->left;
		}
	}

public:
	BSTIterator(TreeNode* root){ pushLeft(root); }

	bool hasNext(){ return !st.empty(); }

	int next(){
		TreeNode* node=st.top();
		st.pop();

		pushLeft(node->right);      // resume into the right subtree

		return node->val;
	}
};
// O(h) space, amortized O(1) per next() — each node is pushed and popped once.
The iterator is worth studying because it is the general technique for “turn a recursive traversal into something you can pause”. It is also the answer to “merge two BSTs in sorted order” — run two iterators and compare their fronts, exactly like merging two sorted arrays.
✍️
My convention: on a BST, ask “can I prune?” before writing the traversal

The BST invariant lets you skip whole subtrees, which turns O(n) into O(h) on many problems. Range sum is the clearest case:

int rangeSumBST(TreeNode* root,int lo,int hi){
	if(!root)return 0;

	if(root->val<lo)return rangeSumBST(root->right,lo,hi);   // skip left ENTIRELY
	if(root->val>hi)return rangeSumBST(root->left,lo,hi);    // skip right ENTIRELY

	return root->val
	      +rangeSumBST(root->left,lo,hi)
	      +rangeSumBST(root->right,lo,hi);
}

Two extra lines and the traversal visits only the nodes it needs to. A full inorder collect-then-filter is correct and wasteful — and on a large BST with a narrow range the difference is enormous. Pruning is the difference between using a BST and merely traversing one.

Balanced construction, and degeneration

sortedArrayToBST — the middle is the rootO(n)O(log n)
// Taking the middle element as the root splits the remainder evenly,
// which is exactly what makes the result height-balanced.
TreeNode* build(vector<int> &a,int lo,int hi){
	if(lo>hi)return nullptr;

	int mid=lo+(hi-lo)/2;

	TreeNode* root=new TreeNode(a[mid]);
	root->left=build(a,lo,mid-1);
	root->right=build(a,mid+1,hi);

	return root;
}
TreeNode* sortedArrayToBST(vector<int> &a){
	return build(a,0,a.size()-1);
}
Same recursion shape as binary search, which is not a coincidence — a balanced BST is a precomputed binary search. Note the O(log n) space is only the recursion stack; the tree itself is the output.
💀
Inserting sorted data destroys a BST

Insert 1, 2, 3, 4, 5 in order into an empty BST and you get a linked list of height 5. Every operation becomes O(n), and a recursive traversal on 10⁵ such nodes overflows the stack.

1

  2
   \
    3
     \
      4
       \
        5        // h = n. Search is O(n). This is not a corner case —
                 // sorted or nearly-sorted input is extremely common.

This is the reason balanced trees exist. Chapter 20 covers AVL, red-black and treaps, which rotate after each insertion to keep h = O(log n) and which is what std::map and std::set actually are. When you say "BST" in an interview, be ready for "and what if the input is sorted?" — the answer is either a self-balancing tree or, if you only need the tree once, building it from a sorted array as above.

So when do you actually want a BST?

When you need order and mutation together. A hash map is faster for pure lookup but has no order. A sorted array has order and fast range queries but O(n) insertion. A balanced BST is the only structure that gives you O(log n) insert, delete, search, predecessor, successor and ordered iteration at the same time. That is why std::map exists alongside unordered_map, and why you reach for it in problems that say “keep a running set and repeatedly ask for the nearest value”.

⚠️
Common mistakes
  • Validating only against immediate children. The invariant constrains the whole subtree; pass a range down.
  • Using INT_MIN/INT_MAX as range sentinels. A node holding those values gets rejected. Use long long.
  • Allowing equality in validation. A strict BST needs strictly increasing inorder; <= accepts duplicates the problem may forbid.
  • Forgetting to assign the recursive result back. insert(root->left, val) without root->left = loses the new node.
  • Mishandling delete case 3. Copy the successor's value, then delete the successor — do not try to splice pointers.
  • Passing k by value in kthSmallest. The countdown must be shared or every branch restarts it.
  • Collecting the entire inorder for a range query. Prune with the invariant instead — O(h + k) rather than O(n).
  • Assuming a BST is balanced. Sorted insertion gives h = n, and that input is common, not exotic.
  • Using inorder on a non-BST expecting sorted output. Only the invariant makes it monotone.

Interview drill

Warm-up: Validate a BST. Why is checking each node against its children wrong?

How a strong answer sounds
Because the invariant is about entire subtrees, not parent-child pairs. Take root 10 with left child 5 and right child 15, and give 15 a left child of 6. Every individual comparison passes — 5 < 10, 15 > 10, 6 < 15 — but 6 lives in 10's right subtree while being less than 10, so a search for 6 would descend right from the root and never reach it. The tree is broken in a way no local check can see. Two correct approaches. First, pass a valid open range down: each node must satisfy lo < val < hi, and it passes (lo, val) to its left child and (val, hi) to its right. That is a preorder pattern, which makes validation the one BST problem that is not inorder. I would use long long for the bounds, because if a node legitimately holds INT_MIN then comparing against an INT_MIN sentinel rejects a valid tree. Second approach: inorder traversal of a BST must be strictly increasing, so I track just the previously visited node and fail if it is not strictly smaller — O(n) time, O(h) space, and the prev pointer must be a reference since it is state shared across the whole traversal.

Deeper: Delete a node from a BST. Walk me through all three cases and justify the successor choice.

How a strong answer sounds
First I descend using the invariant until I find the key, assigning each recursive result back to root->left or root->right so a changed subtree root propagates without needing parent pointers. Then three cases. If the node is a leaf, remove it and return null. If it has one child, return that child — the parent's assignment splices it in, and this same code handles the leaf case since the missing child is null. The interesting case is two children: I cannot just promote a child, because it would have to absorb the other subtree. Instead I find the inorder successor, which is the leftmost node of the right subtree, copy its value into the node being deleted, and then recursively delete the successor from the right subtree. That works because the successor is by definition the smallest value greater than the deleted one, so it is larger than everything in the left subtree and smaller than everything remaining on the right — exactly what the slot requires. And the recursion terminates cleanly because the leftmost node has no left child, so deleting it falls into case one or two and cannot recurse back into case three. The inorder predecessor, the rightmost node of the left subtree, works symmetrically; alternating between them is one way to reduce the height drift that repeated deletions cause. Overall O(h), which is O(log n) only if the tree is balanced — which is the segue into why AVL and red-black trees exist.

🧠 Key takeaways

  • The invariant constrains a node against its whole subtree; validate by passing a range down, not by checking children.
  • Inorder on a BST is sorted — that converts validation, Kth smallest, minimum difference and two-sum into array problems.
  • Delete has three cases, and the two-child case copies the inorder successor's value then deletes the successor.
  • Prune with the invariant on range queries: two extra lines turn O(n) into O(h + k).
  • Sorted insertion degenerates a BST to a list with h = n — which is exactly why Chapter 20 exists.

Check your understanding

Root 10, left child 5, right child 15, and 15 has left child 6. Is this a BST?

This is the tree the naive check accepts. The invariant constrains a node against its entire subtree, so validation must pass an allowed range down from the ancestors.

Why use long long for the range bounds in isValidBST?

The sentinel must be strictly outside the value range. Widening the bound type separates "no constraint" from a real value, and this exact case appears in hidden test suites.

In BST deletion with two children, why replace the node's value with its inorder successor?

Exactly the property the vacated slot needs. It is the leftmost node of the right subtree, so it has no left child and its deletion reduces to case 1 or 2. (The predecessor works symmetrically.)

You insert 1, 2, 3, …, n into an empty BST in ascending order. What is the resulting height?

A plain BST does not rebalance. Every operation becomes O(n) and recursion on 10⁵ nodes overflows the stack. Sorted input is common, not exotic, which is precisely why AVL and red-black trees exist.

You need O(log n) insert, delete and “what is the nearest value below x?”. Which structure?

A hash map has no order, so predecessor is O(n). A sorted array has order but O(n) insertion. A heap gives you only the extreme. The balanced BST is the one structure that combines ordered queries with cheap mutation.
