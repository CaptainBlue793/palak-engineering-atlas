Binary Search Trees

A BST (binary search tree) is a binary tree with one extra rule, and that rule gives you O(h) search, where h is the tree's height. The rule is stricter than most people remember. It compares a node with its entire subtree, not just its two children, and almost every BST bug comes from forgetting that. The other thing to remember: an inorder traversal of a BST (left, node, right) visits the values in sorted order. That turns a surprising number of tree problems into array problems you already know.

  • Write search, insert, and delete with its three cases
  • Use inorder for validation, Kth smallest, successor and minimum difference
  • Build a balanced BST from a sorted array
  • Explain how a BST can collapse into a long chain, and what Chapter 20 does about it

The invariant — and the mistake

For every node: every value in its left subtree is smaller, and every value in its right subtree is larger. Not just “the left child is smaller” — the whole left subtree.

Why anyone cares. A sorted array lets you binary search in O(log n), but inserting a value means shifting everything after it, which is O(n). A plain binary tree lets you attach a new node anywhere in O(1), but finding a value means looking at every node. The BST rule gets you both: at each node, one comparison tells you which half of the remaining values the target must be in, and a new value just hangs off the bottom.

A small example. Take the BST with root 8, left child 3 (children 1, 6) and right child 10 (right child 14). To find 6: at 8, 6 is smaller, go left. At 3, 6 is larger, go right. At 6, found. Three nodes looked at out of six. The rule is what makes "go left" safe: everything on 8's right is bigger than 8, so 6 cannot be there, and you never need to come back.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 IN-ORDER IS SORTED
Nearly every BST problem reduces to "the in-order traversal is sorted". Validate, k-th smallest, minimum difference and two-sum all fall out of that one fact.
💡 RANGE, NOT PARENT
Validate a BST by passing down (low, high) bounds, not by comparing with the parent. The parent check accepts trees that are locally fine and globally wrong.
⛔ DELETE TWO CHILDREN
Deleting a two-child node means replacing it with its in-order successor and then deleting that. Handle the zero- and one-child cases first and the third becomes short.
💥
The naive validation accepts a tree that is not a BST

If you only check left->val < root->val < right->val at each node, this tree passes:

        10
       /  \
      5    15
          /  \
        6    20      // 6 < 15 ✓ locally, but 6 < 10 and it is in 10's RIGHT subtree ✗

Each parent-child pair looks fine on its own. But 6 is in 10's right subtree, and it is smaller than 10. A search for 6 starting at the root would go right and never find it. The correct check passes an allowed range down the tree. That is a preorder pattern (handle the node first, then its children), which is why validation is the one BST problem that doesn't use inorder.

isValidBST — two correct waysO(n)O(h)
// WAY 1: pass a valid (lo,hi) range down. Preorder, because the constraint
// flows from ancestors to descendants. Use long long so INT_MIN/INT_MAX
// node values do not collide with the sentinels.
bool valid(TreeNode* root,long long lo,long long hi){
	if(!root)return true;

	if(root->val<=lo or root->val>=hi)return false;

	return valid(root->left,lo,root->val)
	   and valid(root->right,root->val,hi);
}
bool isValidBST(TreeNode* root){
	return valid(root,LLONG_MIN,LLONG_MAX);
}

// WAY 2: inorder must be strictly increasing. Keep only the previous value —
// no need to build the whole vector.
bool check(TreeNode* root,TreeNode* &prev){
	if(!root)return true;

	if(!check(root->left,prev))return false;

	if(prev and prev->val>=root->val)return false;
	prev=root;

	return check(root->right,prev);
}
bool isValidBST2(TreeNode* root){
	TreeNode* prev=nullptr;

	return check(root,prev);
}
Using long long for the starting bounds is not overkill. The bounds are placeholder values meaning "no limit yet". If a node really holds INT_MIN, then root->val <= lo with lo = INT_MIN is true, and a perfectly valid tree gets rejected. A wider type puts the placeholders outside every possible int value, which fixes it. Also note TreeNode* &prev in way 2. It is a reference because the whole traversal shares one "previous node", not one per branch.

Search, insert, delete

All three operations walk one path from the root downward, so each costs O(h), where h is the height (the number of edges on the longest root-to-leaf path). How big h is depends on the shape. A well-spread tree of n nodes has h about log₂ n (1,000,000 nodes → about 20 levels), because each level can hold twice as many nodes as the one above it. A lopsided tree can have h = n − 1. Keep that in mind for every "O(h)" below.

Insert, traced. Insert 7 into the example tree (8; 3 with 1, 6; 10 with 14). At 8: 7 < 8, go left. At 3: 7 > 3, go right. At 6: 7 > 6, go right, and 6 has no right child. That empty slot is where 7 belongs, so it becomes 6's right child. Nothing else moves. Inserting 7 again would follow the same path, find 7 equal, and do nothing (the code below ignores duplicates; if a problem allows them, pick one side, usually right, and use it consistently).

search and insertO(h)O(1) iterative
// Search: the invariant tells you which way to go. No backtracking, ever.
TreeNode* searchBST(TreeNode* root,int target){
	while(root){
		if(root->val==target)return root;

		if(target<root->val)root=root->left;
		else root=root->right;
	}

	return nullptr;
}

// Insert: walk to the null slot where the value belongs, and put it there.
// A new value always becomes a LEAF — no restructuring needed.
TreeNode* insertIntoBST(TreeNode* root,int val){
	if(!root)return new TreeNode(val);

	if(val<root->val)root->left=insertIntoBST(root->left,val);
	else if(val>root->val)root->right=insertIntoBST(root->right,val);

	return root;                  // equal -> ignore (or count duplicates)
}
The root->left = insert(...) pattern assigns the recursive result back to the child pointer. It handles "this subtree may now have a different root" without needing parent pointers. It costs nothing when the root stays the same, and it is essential when the root changes. That is why the same shape shows up in delete and in every rotation in Chapter 20.

Delete is harder because removing a node can leave a hole in the middle of the tree, and the two subtrees under it still need a single parent. Here is each case on the tree 8; 3 (1, 6); 10 (—, 14):

  • Leaf — delete 1. It has no children. Set 3's left pointer to null and you are done.
  • One child — delete 10. Its only child is 14. Hook 14 directly onto 8 as its right child. This is safe because 14 was already in 8's right subtree, so it is already bigger than 8.
  • Two children — delete 3. It has 1 on the left and 6 on the right. Neither child alone can take its place and keep both subtrees. So find the smallest value in 3's right subtree: that is 6. Copy 6 into the node that held 3, then delete the original 6 (a leaf, so case 1). The tree is now 8; 6 (1, —); 10 (—, 14). Check: 1 < 6 < 8. Still a BST.
deleteNode — the three casesO(h)O(h)
// Case 1: leaf           -> just remove it
// Case 2: one child      -> the child takes its place
// Case 3: two children   -> replace the VALUE with the inorder successor,
//                           then delete the successor (which has at most
//                           one child, so it reduces to case 1 or 2)
TreeNode* deleteNode(TreeNode* root,int key){
	if(!root)return nullptr;

	if(key<root->val){
		root->left=deleteNode(root->left,key);
	}else if(key>root->val){
		root->right=deleteNode(root->right,key);
	}else{
		// found it
		if(!root->left){
			TreeNode* child=root->right;
			delete root;
			return child;               // covers case 1 and 2
		}
		if(!root->right){
			TreeNode* child=root->left;
			delete root;
			return child;
		}

		// case 3: leftmost node of the right subtree = inorder successor
		TreeNode* succ=root->right;
		while(succ->left)
		succ=succ->left;

		root->val=succ->val;               // copy the VALUE up
		root->right=deleteNode(root->right,succ->val);   // then delete it
	}

	return root;
}
Why the successor works. The inorder successor is the next value up: the smallest value bigger than the one being deleted. So it is larger than everything in the left subtree and smaller than everything else in the right. That is exactly what the empty spot needs. It is the leftmost node of the right subtree, so it has no left child. That is why deleting it can never land in case 3 again. (The inorder predecessor — the rightmost node of the left subtree — works the same way, mirrored.)

Inorder is the superpower

Inorder on a BST gives you the values in sorted order. That one fact turns a whole family of tree problems into array problems you have already solved.

Why it is sorted. Inorder visits the whole left subtree, then the node, then the whole right subtree. By the BST rule, everything in the left subtree is smaller than the node and everything in the right is larger. So the node is printed after all smaller values and before all larger ones. The same argument applies inside each subtree, all the way down. On the example tree (8; 3 with 1, 6; 10 with 14) inorder gives 1 3 6 8 10 14.

Two consequences worth spelling out. Minimum difference: in a sorted list, the closest pair is always next to each other. In 1 3 6 8 10 14 the gaps are 2, 3, 2, 2, 4, so the answer is 2, and you never need to compare 1 with 8. Kth smallest: the Kth value that inorder visits is the answer. For k = 3 you visit 1, 3, 6 and stop; the nodes 8, 10 and 14 are never touched.

// Early-exit inorder. k is a reference so the countdown is shared;
// once it reaches 0 we stop descending anywhere.
void inorderKth(TreeNode* root,int &k,int &ans){
	if(!root or k==0)return;

	inorderKth(root->left,k,ans);

	k--;
	if(k==0){
		ans=root->val;
		return;
	}

	inorderKth(root->right,k,ans);
}
int kthSmallest(TreeNode* root,int k){
	int ans=-1;
	inorderKth(root,k,ans);

	return ans;
}

// BSTIterator: the iterative inorder from Chapter 16, PAUSED between calls.
// The stack holds exactly "nodes whose left subtree is done, not yet visited".
class BSTIterator{
	stack<TreeNode*> st;

	void pushLeft(TreeNode* node){
		while(node){
			st.push(node);
			node=node->left;
		}
	}

public:
	BSTIterator(TreeNode* root){ pushLeft(root); }

	bool hasNext(){ return !st.empty(); }

	int next(){
		TreeNode* node=st.top();
		st.pop();

		pushLeft(node->right);      // resume into the right subtree

		return node->val;
	}
};
// O(h) space, amortized O(1) per next() — each node is pushed and popped once.
The iterator is worth studying because it is the general way to turn a recursive traversal into something you can pause and resume. It also solves “merge two BSTs in sorted order”: run two iterators and compare their next values, exactly like merging two sorted arrays.
✍️
My convention: on a BST, ask “can I prune?” before writing the traversal

The BST rule lets you skip whole subtrees (this is called pruning), which turns O(n) into O(h) on many problems. Range sum is the clearest example:

int rangeSumBST(TreeNode* root,int lo,int hi){
	if(!root)return 0;

	if(root->val<lo)return rangeSumBST(root->right,lo,hi);   // skip left ENTIRELY
	if(root->val>hi)return rangeSumBST(root->left,lo,hi);    // skip right ENTIRELY

	return root->val
	      +rangeSumBST(root->left,lo,hi)
	      +rangeSumBST(root->right,lo,hi);
}

Trace with range [7, 12] on the tree 8; 3 (1, 6); 10 (—, 14). At 8: inside the range, so add 8 and look both ways. At 3: 3 < 7, so everything in 3's left subtree is even smaller; skip it and only visit 3's right child. At 6: 6 < 7, skip left again, and its right is empty. At 10: inside, add it. At 14: 14 > 12, so skip its right subtree. Sum = 18, and node 1 was never visited.

With two extra lines, the traversal visits only the nodes it needs. Collecting the full inorder and then filtering is correct but wasteful. On a large BST with a narrow range, the difference is huge. Pruning is the difference between really using a BST and just walking through one.

Balanced construction, and degeneration

If you are given all the values up front, you can build the shortest possible BST directly instead of inserting them one by one. Sort them, make the middle value the root, and repeat on the left half and the right half. Each half is at most half as big, so the depth is about log₂ n.

Trace on [1, 2, 3, 4, 5, 6, 7]: the middle is 4, so 4 is the root. Left half [1, 2, 3] → middle 2, with children 1 and 3. Right half [5, 6, 7] → middle 6, with children 5 and 7. Result: a perfect tree of height 2. Inserting the same values one at a time in that order would give a chain of height 6.

sortedArrayToBST — the middle is the rootO(n)O(log n)
// Taking the middle element as the root splits the remainder evenly,
// which is exactly what makes the result height-balanced.
TreeNode* build(vector<int> &a,int lo,int hi){
	if(lo>hi)return nullptr;

	int mid=lo+(hi-lo)/2;

	TreeNode* root=new TreeNode(a[mid]);
	root->left=build(a,lo,mid-1);
	root->right=build(a,mid+1,hi);

	return root;
}
TreeNode* sortedArrayToBST(vector<int> &a){
	return build(a,0,a.size()-1);
}
This has the same recursion shape as binary search, and that is no accident: a balanced BST is a binary search worked out in advance. The O(log n) space is only the recursion stack; the tree itself is the output.
💀
Inserting sorted data destroys a BST

Insert 1, 2, 3, 4, 5 in order into an empty BST and you get a linked list of height 5. Why: 1 becomes the root. 2 is bigger, so it goes right. 3 is bigger than 1 and 2, so it goes right twice. Every new value is the biggest so far, so it always lands at the far right end. Every operation becomes O(n), and a recursive traversal over 10⁵ such nodes overflows the stack.

This is the reason balanced trees exist. Chapter 20 covers AVL trees, red-black trees and treaps. They rotate nodes after each insertion to keep h = O(log n), and they are what std::map and std::set really are underneath. When you say "BST" in an interview, be ready for "and what if the input is sorted?" The answer is either a self-balancing tree or, if you only need to build the tree once, building it from a sorted array as shown above.

So when do you actually want a BST?

When you need sorted order and changes at the same time. A hash map is faster for plain lookup, but it keeps no order. A sorted array has order and fast range queries, but inserting is O(n). A balanced BST is the only structure that gives you O(log n) insert, delete, search, predecessor (next smaller) and successor (next larger), and walking in sorted order, all at once. That is why std::map exists alongside unordered_map. Reach for it in problems that say “keep a changing set and keep asking for the nearest value”.

⚠️
Common mistakes
  • Checking a node only against its own children. The rule covers the whole subtree, so pass a range down.
  • Using INT_MIN/INT_MAX as the starting "no limit" bounds. A node holding one of those values gets rejected. Use long long.
  • Allowing equal values in validation. A strict BST needs an inorder that strictly increases. <= accepts duplicates the problem may forbid.
  • Forgetting to assign the recursive result back. Calling insert(root->left, val) without root->left = loses the new node.
  • Getting delete case 3 wrong. Copy the successor's value, then delete the successor. Don't try to rewire pointers.
  • Passing k by value in kthSmallest. The countdown must be shared, or every branch starts it over.
  • Collecting the entire inorder for a range query. Skip subtrees using the BST rule instead: O(h + k) rather than O(n).
  • Assuming a BST is balanced. Inserting sorted values gives h = n, and sorted input is common, not rare.
  • Expecting inorder on a non-BST to come out sorted. Only the BST rule makes it sorted.

Interview drill

Warm-up: Validate a BST. Why is checking each node against its children wrong?

How a strong answer sounds
Because the BST rule is about whole subtrees, not parent-child pairs. Take root 10 with left child 5 and right child 15, and give 15 a left child of 6. Every single comparison passes: 5 < 10, 15 > 10, 6 < 15. But 6 is in 10's right subtree and is less than 10. A search for 6 would go right from the root and never reach it. The tree is broken in a way no local check can see. There are two correct approaches. First, pass an allowed range down. Each node must satisfy lo < val < hi, and it passes (lo, val) to its left child and (val, hi) to its right. That is a preorder pattern, which makes validation the one BST problem that is not inorder. I would use long long for the bounds. If a node really holds INT_MIN, comparing it against an INT_MIN placeholder would reject a valid tree. Second approach: the inorder traversal of a BST must strictly increase. So I track just the previously visited node and fail if it is not strictly smaller. That is O(n) time and O(h) space. The prev pointer must be a reference, since the whole traversal shares it.

Deeper: Delete a node from a BST. Walk me through all three cases and justify the successor choice.

How a strong answer sounds
First I walk down using the BST rule until I find the key. I assign each recursive result back to root->left or root->right, so if a subtree's root changes, the parent picks it up without needing parent pointers. Then there are three cases. If the node is a leaf, remove it and return null. If it has one child, return that child; the parent's assignment links it in. The same code handles the leaf case, since the missing child is null. The interesting case is two children. I can't just move a child up, because it would have to take on the other subtree too. Instead I find the inorder successor, which is the leftmost node of the right subtree. I copy its value into the node being deleted, then recursively delete the successor from the right subtree. This works because the successor is the smallest value bigger than the deleted one. So it is larger than everything in the left subtree and smaller than everything left on the right, which is exactly what the spot needs. The recursion ends cleanly because the leftmost node has no left child. Deleting it falls into case one or two and can't go back into case three. The inorder predecessor, the rightmost node of the left subtree, works the same way, mirrored. Switching between the two is one way to slow down the height growth that many deletions cause. Overall it is O(h), which is O(log n) only if the tree is balanced. That leads straight into why AVL and red-black trees exist.

🧠 Key takeaways

  • The BST rule compares a node with its whole subtree. Validate by passing a range down, not by checking children.
  • Inorder on a BST is sorted. That turns validation, Kth smallest, minimum difference and two-sum into array problems.
  • Delete has three cases. The two-children case copies the inorder successor's value, then deletes the successor.
  • On range queries, skip subtrees using the BST rule. Two extra lines turn O(n) into O(h + k).
  • Inserting sorted values turns a BST into a list with h = n. That is exactly why Chapter 20 exists.

Check your understanding

Root 10, left child 5, right child 15, and 15 has left child 6. Is this a BST?

This is the tree the naive check accepts. The BST rule compares a node with its entire subtree, so validation must pass an allowed range down from the ancestors.

Why use long long for the range bounds in isValidBST?

The "no limit" placeholder must be outside every possible value. A wider type keeps "no limit" separate from a real value. This exact case shows up in hidden tests.

In BST deletion with two children, why replace the node's value with its inorder successor?

That is exactly what the empty spot needs. The successor is the leftmost node of the right subtree, so it has no left child, and deleting it becomes case 1 or 2. (The predecessor works the same way, mirrored.)

You insert 1, 2, 3, …, n into an empty BST in ascending order. What is the resulting height?

A plain BST does not rebalance itself. Every operation becomes O(n), and recursion over 10⁵ nodes overflows the stack. Sorted input is common, not rare, which is exactly why AVL and red-black trees exist.

You need O(log n) insert, delete and “what is the nearest value below x?”. Which structure?

A hash map has no order, so finding the next smaller value is O(n). A sorted array has order, but inserting is O(n). A heap only gives you the smallest (or largest). The balanced BST is the one structure that gives both ordered queries and cheap changes.
