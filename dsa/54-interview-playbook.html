The Interview Playbook

A coding interview is not a test of whether you can solve the problem — it is a test of how you solve problems in front of another engineer. Two candidates who both arrive at the optimal solution get very different outcomes depending on how they got there. This chapter is the minute-by-minute structure, the things worth saying out loud, and what the interviewer is actually recording.

  • Run a 45-minute round to a reliable structure
  • Ask the clarifying questions that matter, and skip the ones that do not
  • Narrate a derivation instead of announcing an answer
  • Recover gracefully when you are stuck or wrong
  • Self-score against the rubric interviewers actually use

The 45-minute structure

0:00 – 0:03 · UNDERSTAND
Restate the problem, then ask about the input

Repeat the problem in your own words — this catches misreadings immediately and costs fifteen seconds. Then ask only the questions whose answers change your code: size of the input, duplicates, negatives, empty input, whether the input may be modified, and what to return when there is no answer.

Say: "So I'm given an array of integers and a target, and I need to return the indices of two numbers that sum to it. Before I start — can the array contain duplicates or negatives? Is it sorted? Is there always exactly one answer, and what should I return if there is none? And roughly how large is n?"
0:03 – 0:06 · EXAMPLE
Work one small example by hand, including an edge case

Write out a concrete input and its expected output. Then pick one edge case — an empty input, a single element, all-equal values — and state what it should produce. This is where you catch an ambiguity the interviewer has not mentioned, and it gives you a test to trace against later.

Say: "So [2, 7, 11, 15] with target 9 gives [0, 1]. And with [3, 3] and target 6 — that should be [0, 1], using the same value twice at different indices but not the same index twice. Let me confirm that is allowed."
0:06 – 0:12 · APPROACH
Brute force out loud, then name the redundancy

State the brute force with its complexity, even when you already know the optimal answer. Then say what it recomputes, and let the fix follow from that. This is the single highest-value habit in the whole round — it demonstrates derivation rather than recall, and it is the part that survives a changed constraint.

Say: "The brute force checks every pair, O(n²). What it wastes is the lookup: for each element I re-scan the rest of the array to ask 'does target − x exist?'. That is a membership query, so a hash set makes it O(1) and the whole thing O(n) with O(n) space. Shall I code that?"
0:12 – 0:15 · AGREE
State the plan and get a nod before writing code

Say the data structures, the loop structure, and the complexity you expect. Then pause. If the interviewer wants a different direction, this is when it costs you three minutes rather than twenty — and a good interviewer will steer you here if you are heading somewhere unproductive.

Say: "The plan: one pass, a hash map from value to index, and for each element check whether the complement is already in the map. O(n) time, O(n) space, and it handles duplicates because I look up before inserting. Does that sound right to you?"
0:15 – 0:32 · CODE
Write it cleanly, narrating only the non-obvious lines

Real names, guard clauses first, helper plus driver if the logic needs state. Narrate why a line is there, not what it does — the interviewer can read i++. If you realise mid-way that the approach is wrong, say so immediately rather than pressing on; catching your own mistake reads far better than being caught.

Say: "I'm checking the map before inserting the current element — that is deliberate, so the same index can't be used twice. And I'm returning the indices rather than the values, as we agreed."
0:32 – 0:40 · VERIFY
Trace the example by hand, then the edge cases

Walk your actual code line by line on the concrete example — do not just assert that it works. Then run the edge cases you named in step 2, and volunteer any you would add. Finding your own bug during this pass is a positive signal, not a negative one.

Say: "Let me trace [2,7,11,15], target 9. i=0: complement 7, map empty, insert 2→0. i=1: complement 2, found at 0, return [0,1]. Correct. Now n=1: the loop runs once, nothing found, we fall through to the not-found return. And an empty array returns the same. I'd also want a test where the complement equals the element itself."
0:40 – 0:45 · EXTEND
State the complexity, the trade-offs, and one improvement

Give final time and space complexity, then name a trade-off you considered and rejected, and one thing you would do with more time. Finish by asking a real question about the team or the work — it is the last thing they remember, and it should not be a throwaway.

Say: "O(n) time and O(n) space. If the array were sorted I'd use two pointers for O(1) extra space instead, and if it needed to handle a stream I'd keep the map and drop the indices. With more time I'd extend it to the three-sum variant, which is the sorted-plus-two-pointers version wrapped in an outer loop."
✍️
My convention: the interviewer should never have to ask "what are you thinking?"

Silence is the most expensive thing in a coding interview. It is not that thinking quietly is wrong — it is that an unspoken derivation cannot be credited, and an interviewer who cannot see your reasoning has nothing to write down but the final code. So I narrate the structure of my thinking even when the content is incomplete: "I'm deciding between a heap and sorting here — sorting is simpler but the streaming requirement probably rules it out." That sentence is worth more than two minutes of silent correctness, because it shows a decision being made on the right criteria. And if I genuinely need to think, I say so: "Give me twenty seconds to work out the recurrence." That is a perfectly acceptable sentence, and it reads as composure rather than a stall.

    Weakest dimension first — these are trainable independently, and the lowest one is usually what loses the round.
    📊
    What each dimension actually means
    • Problem comprehension — did you restate it, and ask the questions that changed your code? Asking nothing is a weak signal even when you happen to be right.
    • Approach derivation — did the solution arrive derived or announced? A derived O(n²) often scores above an announced O(n), because the derivation is what generalises.
    • Complexity analysis — stated correctly and unprompted, for both time and space, including the space your recursion uses.
    • Code quality — real names, no duplicated logic, guard clauses, correct handling of boundaries. Would a colleague accept this in review?
    • Correctness — does it work, and did you verify it by tracing rather than by assertion?
    • Communication — could the interviewer follow your reasoning without asking? Silence costs more than a wrong turn.
    • Testing instinct — did you volunteer edge cases, or wait to be asked?
    • Coachability — when given a hint, did you take it, integrate it, and credit it? Arguing with a correct hint is the fastest way to fail a round you were otherwise passing.

    When you are stuck

    🧭
    A procedure, not a panic

    Being stuck is expected — problems are calibrated so that most candidates need help. What is scored is what you do while stuck. In order:

    • Say that you are stuck, and where. "I can see this needs DP but I can't pin down what the state should be." That is a precise, useful sentence, and it invites the hint you need. Silent struggling invites nothing.
    • Go back to a smaller case. Solve n = 1, 2, 3 by hand and write the answers down. Most recurrences are found this way, not by staring.
    • Say what you have ruled out and why. "Greedy by end time fails here — here's a counterexample." Eliminations are progress and they get credited.
    • Offer the brute force as a floor. "Let me code the O(n²) so we have something working, then optimise." A working suboptimal solution scores far above an unfinished optimal one.
    • Take the hint and run with it. Interviewers hint deliberately; using one well is a positive signal, and ignoring one is a strongly negative signal.

    What not to do: go silent, guess randomly at code, insist your wrong approach is right, or apologise repeatedly. None of it helps and the apologising actively costs you — it spends time and signals fragility.

    Tips & tricks

    The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

    💡 BRUTE FORCE ALOUD
    State the brute force even when you know the optimal answer. It proves you understand the problem, gives you a baseline to test against, and produces the optimisation.
    💡 NARRATE DECISIONS
    "I am choosing between a heap and sorting; sorting is simpler but the streaming requirement rules it out" is worth more than two minutes of silent correctness.
    ⛔ TAKE THE HINT
    Hints are given deliberately. Using one well is a positive signal; arguing with a correct one is the fastest way to fail a round you were passing.
    ⚠️
    Common mistakes
    • Coding before agreeing on the approach. Twenty wasted minutes instead of three.
    • Going silent for more than about thirty seconds. Unspoken reasoning cannot be credited.
    • Announcing a memorised optimal solution with no derivation. The follow-up will expose it.
    • Asking no clarifying questions, or asking ones whose answers change nothing.
    • Claiming it works without tracing it. Verify on the concrete example, line by line.
    • Arguing with a correct hint. The fastest way to fail a round you were passing.
    • Abandoning a working brute force to chase an optimal solution you do not finish.
    • Giving complexity only when asked, or omitting space.
    • Single-letter names everywhere, or copy-pasted logic you then have to fix twice.
    • Apologising repeatedly. It costs time and signals fragility.
    • Not asking a real question at the end. It is the last impression and it is easy to do well.
    🎤
    Interview drill

    Warm-up: Ten minutes in you realise your chosen approach cannot work. What do you do?

    How a strong answer sounds
    I say it immediately and precisely: "I've hit a problem with this approach — my greedy rule fails on this input, here's the counterexample." Naming the specific failure matters much more than the admission, because it shows I found it by reasoning rather than by guessing, and a counterexample is concrete evidence I understand the problem. Then I make the eliminated approach count: knowing that greedy-by-duration fails, and why it fails, usually points at the correct structure — in that particular case, that a locally short choice can block two better ones, which is exactly the signal that the problem needs DP or a different ordering. So the next sentence is "given that, I think this needs DP over intervals; let me work out the state." What I would not do is quietly keep coding something I know is wrong, hoping the tests are weak — that wastes the remaining time and, worse, it signals that I will do the same thing on a real project. I also would not spiral into apologising; one clear sentence is enough. If there is very little time left, I change the goal: get the brute force working and correct, state the optimal approach in words with its complexity, and say explicitly what I would implement next. A working suboptimal solution plus an accurate description of the better one scores well above an unfinished optimal attempt, and I would say that trade-off out loud so the interviewer knows it is a deliberate choice rather than a retreat.

    Deeper: You solve the problem in fifteen minutes. How do you spend the remaining thirty?

    How a strong answer sounds
    Finishing early is an opportunity, and the worst use of it is sitting back. First I make sure the solution is genuinely finished to a standard I would defend in code review: trace it line by line on the concrete example rather than asserting that it works, run the edge cases — empty, single element, duplicates, negatives, the value boundaries — and tidy the names and structure. Then I state complexity for both time and space, including the recursion stack if there is one, and I name a trade-off I considered and rejected, because that shows the choice was deliberate. After that I volunteer the extensions, since interviewers usually have follow-ups prepared and offering them first is strictly better than waiting. The good ones are: what changes if the input is a stream and cannot be stored; what changes if it must be O(1) extra space; what changes if the input is sorted, or if duplicates are allowed; how I would parallelise it; and how I would test it — which is where I'd mention writing a brute-force oracle and stress-testing against it on small random inputs. If the problem has an obvious harder sibling I say so and offer to attempt it: "two-sum extends to three-sum, which is sort plus a two-pointer scan inside an outer loop, O(n²) — want me to write it?" Finally I spend the last couple of minutes on a real question about the team — what the codebase looks like, how work is reviewed, what the hardest current problem is. That is the last thing they remember, and a specific question reads very differently from "do you like working here?".

    🧠 Key takeaways

    • Follow the structure: understand, example, approach, agree, code, verify, extend. Do not code before agreeing.
    • State the brute force and name its redundancy — a derived solution outscores an announced one.
    • Narrate the structure of your thinking; silence cannot be credited.
    • When stuck, say exactly where, shrink the case, state what you ruled out, and offer the brute force as a floor.
    • Take hints gracefully. Arguing with a correct hint fails rounds you were otherwise passing.
    • Verify by tracing, volunteer edge cases, and give both time and space complexity unprompted.

    Check your understanding

    You recognise the problem instantly and know the optimal solution. What should you do first?

    A derived solution demonstrates transferable skill; an announced one looks memorised and collapses on the follow-up. It also costs only two or three minutes.

    You are genuinely stuck, eight minutes in. The best move is…

    "I can see this needs DP but I can't pin down the state" is a precise, creditable sentence that invites exactly the hint you need. Silence invites nothing.

    The interviewer suggests an approach you had not considered. What is the right response?

    Using a hint well is a positive signal; ignoring or arguing with a correct one is strongly negative. If you genuinely disagree, do so with a concrete counterexample rather than a preference.

    With fifteen minutes left, you have a working O(n²) solution and think an O(n log n) one exists. What do you do?

    Never trade a working solution for an unfinished one. Stating the better approach and its complexity earns most of the credit even if you do not finish coding it.

    Which of these most often separates two candidates who both reach the optimal solution?

    The code is the artefact; the process is what is scored. Tracing your own code and volunteering edge cases are the two cheapest ways to move up the rubric.
