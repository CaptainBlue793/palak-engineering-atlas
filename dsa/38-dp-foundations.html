DP Foundations: The Five-Step Method

Dynamic programming (DP) means solving a big problem by solving smaller versions of it once each, saving the answers, and reusing them. It has a reputation for being hard, and that reputation is almost entirely undeserved. The code is never the problem; the state definition is — deciding exactly what dp[i] stands for. Once you can write one precise sentence defining dp[i], the rest follows step by step: the recurrence (the formula linking dp[i] to smaller entries), the base case and the loop order. So this chapter teaches a method, applied to one problem three times: as a recursion, as a memoised recursion (one that caches its answers), and as a table.

  • Recognise the two conditions that make a problem a DP problem
  • Apply the five steps: state, transition, base case, order, answer
  • Convert recursion → memoisation → tabulation (filling a table with loops) → rolling array (keeping only the last few entries)
  • Work out how to save space just by looking at which entries the recurrence reads
  • Rebuild the actual solution, not just its value

When is it DP?

Why does DP matter? Many problems ask for the best or the number of ways out of an enormous number of options. Trying every option takes exponential time: 2⁵⁰ is about 10¹⁵, which no computer finishes. DP is how you get those problems down to something like n or n² steps. It is also one of the most common topics in coding interviews.

A problem needs two conditions, and it must have both. This is the same test you saw in Chapter 11's recursion trees, just stated formally.

1 · Overlapping subproblems

The same smaller problem gets solved more than once. Draw the recursion tree for a small input. If the same function call, with the same arguments, shows up in two different places, you have overlap. Caching those answers shrinks an exponential tree down to a linear number of distinct calls.

2 · Optimal substructure

The best overall answer is built from the best answers to smaller problems. Suppose the best way to handle the first i things depends on something more than the best way to handle the first i−1. Then your state is missing information, and you need to add it.

Seeing the overlap with real numbers. Take plain recursive Fibonacci, fib(n) = fib(n−1) + fib(n−2), and expand fib(5). It calls fib(4) and fib(3). But fib(4) also calls fib(3). Count every call in the tree and you get: fib(3) twice, fib(2) three times, fib(1) five times, fib(0) three times, 15 calls in total. There are only 6 distinct arguments, 0 to 5. The waste grows fast: fib(40) makes over 300 million calls for 41 distinct values. Saving each answer the first time you compute it cuts that to 41.

Seeing optimal substructure. In house robber (below), the best total for houses 0..4 is either the best for 0..3 (skip house 4), or house 4's money plus the best for 0..2. You never need to know how the best for 0..3 was reached, only its value. That is optimal substructure: the best answer is built from best answers to smaller versions. When it fails, the fix is to add what was missing to the state. For example, if a rule said "you cannot rob house i if you robbed house i−3", knowing only the best total would not be enough, and the state would need to remember recent choices.

🔍
The signals in a problem statement
  • “Minimum / maximum number of …”, “longest / shortest …”
  • “How many ways to …” — counting, which is DP using + instead of min
  • “Can you reach / partition / make …” — a true/false DP
  • You make a choice at each step, and a choice can turn out to be a mistake later (Chapter 36's test — if it never can, use greedy)
  • The simple solution takes exponential time, and you can see the same arguments repeating

And the sign that it is not DP: if you must list every solution, rather than count them or find the best, use backtracking (Chapter 35). Every solution must be written out, so there is nothing to share or reuse.

The five steps

1
State — what does dp[...] mean?

One precise English sentence. Not "dp is the answer" — say exactly which answer, for which smaller problem, and whether index i itself is included. Write it as a comment before you write any code. If you cannot write it, nothing after this step will work.

// dp[i] = the maximum money robbable from houses 0..i inclusive
2
Transition — how does a state depend on smaller ones?

List the choices you can make at this state, then combine their results with min, max or +. The number of choices is the cost of each transition. Multiply it by the number of states to get the total running time.

// dp[i] = max(dp[i-1], dp[i-2] + nums[i])
3
Base case — the smallest states, by hand

Which states do not depend on any others? Fill those in directly. Most DP bugs live here, not in the transition. Watch for an empty input, a single element, or an index the transition would read out of bounds.

// dp[0] = nums[0]; dp[1] = max(nums[0], nums[1]);
4
Order — in which sequence do you fill the table?

Every state must be computed after everything it reads. For a 1D table, that usually means increasing i. For 2D, it depends on which neighbouring cells the transition uses. For knapsack, the direction of the capacity loop decides whether an item can be used more than once (Chapter 40).

// for(i = 2; i < n; i++) — increasing, since dp[i] reads dp[i-1], dp[i-2]
5
Answer — which cell, and is it the last one?

Often it is dp[n-1], but not always. Sometimes it is the max over the whole table (as in longest increasing subsequence), or one particular corner. And you may also need to handle n = 0 separately.

// return dp[n-1]
✍️
My convention: the state sentence goes in a comment, above the array declaration

Every DP in this course starts with // dp[i] = … in plain English. It takes ten seconds, and it is the most valuable habit in this part of the course, for two reasons. First, it forces you to decide whether index i is included or not. That is where off-by-one errors come from. Second, when the transition looks wrong, you can check it against the sentence instead of guessing. If the sentence and the code disagree, the code is wrong. This is Chapter 1's invariant rule, and DP is where it pays off most.

One problem, four implementations

The problem is called house robber. A row of houses each holds some money. You want the most money possible, but you may never rob two houses next to each other. We will write the solution four ways. The logic stays the same each time; only the mechanics change.

Why not just take every other house? Try [2, 1, 1, 9]. Houses 0 and 2 give 3, and houses 1 and 3 give 10, but the best is houses 0 and 3, for 11. The right choice at one house depends on what comes later, which is exactly the "a choice can turn out to be a mistake" signal.

A dry run of the five steps on nums = [2, 7, 9, 3, 1], using dp[i] = max(dp[i−1], dp[i−2] + nums[i]):

// Start here, always. Define the recursion from the CHOICES, not the table.
// At house i: either rob it (and skip i-1) or skip it (and take the best of i-1).
int rob(vector<int> &nums,int i){
	if(i<0)return 0;            // base: no houses left

	int take=nums[i]+rob(nums,i-2);
	int skip=rob(nums,i-1);

	return max(take,skip);
}
// O(2^n). Correct, and unusable past n = 30 — but it is the RIGHT first step,
// because the recurrence is now written down and the rest is mechanical.

Write this first, even though you know it is too slow. The recursion is where you discover the choices and the base case. Everything after that is bookkeeping. Note the guard is i < 0, not i == 0. The transition jumps to i-2, so it can skip right past zero (Chapter 11's rule).

// Three added lines. dp[i] = -1 means "not computed yet".
int rob(vector<int> &nums,int i,vector<int> &dp){
	if(i<0)return 0;

	if(dp[i]!=-1)return dp[i];        // 1. read the cache

	int take=nums[i]+rob(nums,i-2,dp);
	int skip=rob(nums,i-1,dp);

	return dp[i]=max(take,skip);         // 2. write it on the way out
}
int rob(vector<int> &nums){
	vector<int> dp(nums.size(),-1);      // 3. driver owns the cache
	return rob(nums,nums.size()-1,dp);
}
// O(n) time, O(n) space + O(n) recursion stack.

This is usually the answer to give in an interview. It is the recursion you already wrote, plus three lines, so it is quick to write and hard to get wrong. The "not computed yet" marker (the sentinel) must be a value the real answer can never be. -1 works here because house values are never negative. But if the answer could be −1, you need a separate computed[] array.

// dp[i] = the maximum money robbable from houses 0..i inclusive.
// Same recurrence, filled bottom-up in increasing i — no recursion at all.
int rob(vector<int> &nums){
	int n=nums.size();
	if(n==0)return 0;
	if(n==1)return nums[0];

	vector<int> dp(n);

	dp[0]=nums[0];                      // base cases, by hand
	dp[1]=max(nums[0],nums[1]);

	for(int i=2;i<n;i++){
		dp[i]=max(dp[i-1],nums[i]+dp[i-2]);
	}

	return dp[n-1];
}
// O(n) time, O(n) space, NO recursion stack. Safe for n = 10^6.

The base cases, written out by hand, replace the i < 0 guard. That switch is where tabulation bugs come from. The recursion's single guard quietly covered several small cases; now you must write each one out yourself. Check n = 0 and n = 1 on purpose.

// The recurrence reads only dp[i-1] and dp[i-2], so we never need the
// rest of the table. Two variables replace the whole array.
int rob(vector<int> &nums){
	int prev2=0;                       // dp[i-2]
	int prev1=0;                       // dp[i-1]

	for(int x:nums){
		int current=max(prev1,x+prev2);
		prev2=prev1;
		prev1=current;
	}

	return prev1;
}
// O(n) time, O(1) space. And the base cases vanished — starting both at 0
// handles the empty and single-element inputs automatically.

Read the space saving straight off the recurrence. If dp[i] depends only on the previous k entries, you only need k variables. Once you see this, it is routine. It is also the standard follow-up question: "can you do it in O(1) space?"

How deep is too deep? Every pending recursive call takes a frame on the call stack (Chapter 11). A typical stack is 1 to 8 MB. A depth of 10⁴ is always safe, and 10⁵ is usually fine for small frames. At 10⁶ you should expect a stack overflow, which crashes with no helpful message. So if the recursion depth is about n and n can reach 10⁶, use tabulation.

🔀
When memoisation is strictly better

When the states you can actually reach are far fewer than the full table. Coin change with a large target but few coins may only ever reach a fraction of the amounts. A DP over subsets may only visit a tiny slice of the 2ⁿ masks. Tabulation fills every cell no matter what; memoisation visits only what the recursion asks for. That is also why memoisation is the right tool when the state is not a simple range of integers — for example, a state keyed on a string, a pair, or a bitmask that needs an unordered_map instead of an array.

Space optimisation, read off the dependencies

Why bother? Memory limits are real. A 2D table for two strings of length 10⁴ has 10⁸ cells. As ints that is 400 MB, well over the usual 256 MB limit. One row of 10⁴ ints is 40 KB. The running time does not change; only the memory does.

The method is to look at which cells the transition reads. Picture the grid: dp[i][j] reads the cell above it, the cell to its left, and the cell diagonally up-left. None of those is more than one row back. So once row i is finished, row i−1 will never be read again, and you can reuse its memory.

the 2D case: one row instead of the whole gridO(n·m) → O(m)
// FULL TABLE. dp[i][j] reads dp[i-1][j] and dp[i][j-1] (and dp[i-1][j-1]).
// So it only ever looks at the PREVIOUS row and the CURRENT row.
vector<vector<int>> dp(n+1,vector<int>(m+1,0));

for(int i=1;i<=n;i++){
	for(int j=1;j<=m;j++){
		dp[i][j]=f(dp[i-1][j],dp[i][j-1],dp[i-1][j-1]);
	}
}

// TWO ROWS. Mechanical: keep prev and cur, swap at the end of each row.
vector<int> prev(m+1,0);
vector<int> cur(m+1,0);

for(int i=1;i<=n;i++){
	for(int j=1;j<=m;j++){
		cur[j]=f(prev[j],cur[j-1],prev[j-1]);
	}
	prev=cur;                  // or swap(prev,cur) to avoid the copy
}

// ONE ROW. Only possible when the diagonal term is NOT needed, because
// writing dp[j] destroys the dp[i-1][j-1] that a later j would want.
// If you do need the diagonal, save it in a temporary before overwriting.
vector<int> dp(m+1,0);

for(int i=1;i<=n;i++){
	int diag=0;                 // holds dp[i-1][j-1]

	for(int j=1;j<=m;j++){
		int saved=dp[j];         // this is dp[i-1][j], needed as next diag
		dp[j]=f(dp[j],dp[j-1],diag);
		diag=saved;
	}
}
The rule: keep as many rows as the recurrence reaches back, plus the current one. If you only read dp[i-1][*], you need two rows. If you also read dp[i-2][*], you need three. The one-row version needs care exactly when the diagonal term is used. A single array cannot hold both the old and the new value of the same index, which is why the diag temporary exists. Write the full table first, make it correct, then optimise.

Reconstructing the solution

DP gives you the value — say, the most money you can rob. When the problem wants the actual choices (which houses, which path, which items), you need one more step.

two ways to recover the choicesO(states) or O(1) extra
// WAY 1: walk the table backwards, re-deciding which branch was taken.
// No extra memory — you re-derive the choice from the stored values.
vector<int> recover(vector<int> &nums,vector<int> &dp){
	vector<int> chosen;
	int i=nums.size()-1;

	while(i>=0){
		int skip=(i>=1)?dp[i-1]:0;

		if(dp[i]==skip){
			i--;                       // house i was NOT robbed
		}else{
			chosen.push_back(i);       // it was
			i-=2;
		}
	}

	reverse(chosen.begin(),chosen.end());

	return chosen;
}

// WAY 2: store the decision as you fill the table. Costs O(states) memory
// but the recovery is trivial and cannot be got wrong.
vector<bool> took(n,false);

for(int i=2;i<n;i++){
	if(nums[i]+dp[i-2]>dp[i-1]){
		dp[i]=nums[i]+dp[i-2];
		took[i]=true;
	}else{
		dp[i]=dp[i-1];
	}
}
Way 1 does not work with a rolling array, because you threw away the table you need to walk. So if you must rebuild the solution, either keep the full table or store the decisions. That is the main reason not to save space by reflex. The O(1) version answers "how much?" but cannot answer "which?".

Way 1 on the dry run above, with dp = [2, 7, 11, 11, 12]:

  1. i = 4: skipping would give dp[3] = 11, but dp[4] = 12. They differ, so house 4 was robbed. Jump to i = 2.
  2. i = 2: skipping would give dp[1] = 7, but dp[2] = 11. House 2 was robbed. Jump to i = 0.
  3. i = 0: skipping would give 0, but dp[0] = 2. House 0 was robbed. Jump to i = −2 and stop.

Reversed, the houses are 0, 2, 4, and 2 + 9 + 1 = 12 matches the answer. When both choices give the same value, either one is a valid optimal solution; the code picks "skip". If the problem asks for a specific tie-break, such as the smallest indices, you must make that rule explicit.

🧮
Complexity is states × transition cost

Every DP's running time is (number of states) × (work per state). You can read both numbers straight off the definition. Some examples:

  • dp[i] over n values with 2 choices → O(n).
  • dp[i][j] over n × m cells with O(1) work each → O(n·m).
  • dp[i][j] where the transition loops over a split point → O(n²·n) = O(n³). This is interval DP (Chapter 45).
  • dp[mask][i] over 2ⁿ masks and n positions, with n transitions each → O(2ⁿ·n²). This is Held-Karp (Chapter 44).

So you can state the running time before writing any code. Check it against the limits table from Chapter 2. If the product is over your budget, the state is wrong, and you need to find a smaller one.

Debugging a DP

Re-read your state sentence

Nine times out of ten, the code computes something slightly different from what the comment says. Usually it is a mix-up over whether index i is included.

Print the table for a tiny input

Use n = 3 or 4. Write out by hand what you believe each cell should be, and compare. The first cell that disagrees points you to one faulty transition or base case.

Check the base cases against the empty and single-element inputs

Recursion handled these quietly; tabulation makes you write them out. n = 0 and n = 1 are where most failures happen.

Verify the loop order against the dependencies

Every state must be filled after everything it reads. If a cell reads a value that is still zero, your order is wrong.

Compare against brute force on random small inputs

Write the slow exponential version too. Run both on a hundred random arrays of size ≤ 10 and compare the outputs. This finds bugs that reading never will. It is the stress testing from Chapter 53.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 STATE SENTENCE
Write dp[i] is … as an English sentence before any code. If the sentence needs two clauses, you need two dimensions — and you have just found them.
💡 TOP-DOWN FIRST
Derive recursively and memoise; convert to a table only if you need the space optimisation. Top-down is far easier to get right and skips unreachable states for free.
⛔ KEY = STATE
The memo key must contain every parameter the answer depends on and nothing else. If two calls with the same key could legitimately differ, the key is incomplete.
⚠️
Common mistakes
  • Writing code before writing the state sentence. This causes most DP failures, and it is the easiest to fix.
  • Unclear index meaning. Is dp[i] about the first i elements, or elements 0..i? Decide in the comment and stick to it.
  • Missing base cases in tabulation. The recursion's i < 0 guard covered several cases; now each one must be written out.
  • Wrong loop order. Reading a cell that has not been filled yet gives zeros, with no error.
  • A memo sentinel the real answer could equal. -1 is unsafe if the answer can be −1. Use a separate computed array.
  • A static or global DP table. It works once, then returns stale answers on the second call (Chapter 1).
  • Saving space before the code is correct. Get the full table right first, then shrink it.
  • Saving space when you need to rebuild the solution. You cannot walk a table you threw away.
  • Overflow. Counting problems overflow fast. Use long long, or take a modulus if the problem asks for one.
  • Using DP when greedy is provably correct (Chapter 36), or when the smaller problems never overlap (Chapter 37).

Interview drill

Warm-up: House robber. Walk me through your process, not just the answer.

How a strong answer sounds
I start with the recursion, because that is where the choices become visible. At house i, I either rob it or skip it. If I rob it, I take nums[i] plus the best from i−2, since house i−1 is now off limits. If I skip it, I take the best from i−1. So rob(i) = max(nums[i] + rob(i−2), rob(i−1)), and rob of a negative index is 0. That is correct but O(2ⁿ). Drawing the recursion tree shows rob(i−2) being called from two different places — the overlapping-subproblems signal. So I memoise. I use a dp array filled with −1, return the cached value if there is one, and store the result on the way out. That is three added lines, giving O(n) time and O(n) space plus the call stack. Then I write the bottom-up version, and here I state the invariant out loud: dp[i] is the maximum money robbable from houses 0 through i inclusive. The base cases are dp[0] = nums[0] and dp[1] = max(nums[0], nums[1]). Then I fill in increasing i with the same recurrence, and the answer is dp[n−1]. That removes the recursion stack. Finally, the recurrence only reads dp[i−1] and dp[i−2], so I shrink the array to two variables for O(1) space. I would point out that this version can no longer tell you which houses were robbed. If the problem wanted the actual set, I would keep the table or record the decisions. I would also handle n = 0 and n = 1 explicitly, since the bottom-up version loses the guard that quietly covered them.

Deeper: How do you decide the state for a problem you have not seen before?

How a strong answer sounds
I work from the brute force. First I write the recursion that tries every choice, however slow. That tells me what a subproblem is, because the recursion's parameters are the state. If the recursive function needs (index, remainingCapacity), the state is dp[index][capacity]. If it needs (index, lastChoice), the state is dp[index][lastChoice]. So "what is the state?" turns into a much more concrete question: "what does the function need to know to finish the job from here?" If the function reads anything that is not a parameter, the state is incomplete. Then I check two things before writing a table. One: does the same set of parameter values come up more than once in the recursion tree? If not, it is divide and conquer, not DP. Two: does the number of distinct parameter sets, times the work for each, fit the time budget from Chapter 2? If the state implies dp[i][j] over 10⁵ × 10⁵, it carries too much, and I need a smaller one that still has enough information. Often a dimension turns out to have a much smaller range than it looks, or only the difference between two values matters, not both values. Once the state passes both checks, I write the one-sentence definition. The transition, base cases, order and answer all follow from it step by step.

🧠 Key takeaways

  • DP needs overlapping subproblems and optimal substructure. Repeated arguments in the recursion tree are the signal.
  • Five steps, in this order: state (one English sentence), transition, base case, order, answer.
  • Write the recursion first, memoise it with three lines, then turn it into a table. The recursion's parameters are the state.
  • Running time is states × work per transition, and you can work it out before writing code.
  • Shrink the table only down to what the recurrence reads back — and not at all if you need to rebuild the actual solution.

Check your understanding

What are the two conditions a problem must satisfy to be solvable by DP?

Overlap is what makes caching worth it. Optimal substructure is what makes it valid to build the answer from smaller answers. Without overlap, it is divide and conquer (Chapter 37). Without optimal substructure, your state is missing information.

What should you write before any DP code?

The state definition decides the transition, the base cases, the order and the answer. And when the code misbehaves, you can check it against the sentence instead of guessing. Most DP bugs happen when the code quietly stops matching what you meant.

dp[i] depends only on dp[i-1] and dp[i-2]. What space do you actually need?

Look at how far back the recurrence reads; that is all you need to keep. The catch: with only two variables, you can no longer walk the table to find out which choices were made.

When is memoisation preferable to tabulation?

Tabulation fills every cell, needed or not. Memoisation visits only what the recursion asks for. It also handles states keyed on strings, pairs or scattered bitmasks, which need a map instead of an array.

You space-optimise a DP to two variables, then the follow-up asks which items were chosen. What is the problem?

The O(1) version answers "how much" but not "which". Either keep the full table, or store the decision at each state as you fill it. That is why you should not save space by reflex.
