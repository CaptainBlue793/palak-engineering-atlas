DP Foundations: The Five-Step Method

Dynamic programming has a reputation for being hard, and it is almost entirely undeserved — the code is never the problem, the state definition is. Once you can write one precise sentence defining dp[i], the recurrence, the base case and the loop order all follow mechanically. So this chapter is a method, applied to one problem three times: as a recursion, as a memoised recursion, and as a table.

  • Recognise the two conditions that make a problem a DP problem
  • Apply the five steps: state, transition, base case, order, answer
  • Convert recursion → memoisation → tabulation → rolling array
  • Read the space optimisation off the recurrence's dependencies
  • Reconstruct the actual solution, not just its value

When is it DP?

Two conditions, both required. This is the same test as Chapter 11's recursion-tree observation, stated formally.

1 · Overlapping subproblems

The same subproblem is solved more than once. Draw the recursion tree for a small input; if an argument list appears at two different places, you have overlap — and caching collapses an exponential tree into a linear DAG.

2 · Optimal substructure

An optimal solution is built from optimal solutions to subproblems. If the best way to do the first i things depends on something other than the best way to do the first i−1, your state is not rich enough.

🔍
The signals in a problem statement
  • “Minimum / maximum number of …”, “longest / shortest …”
  • “How many ways to …” — counting, which is DP with + instead of min
  • “Can you reach / partition / make …” — a boolean DP
  • Choices at each step where a choice can be regretted (Chapter 36's test — if it cannot, use greedy)
  • The naive solution is exponential and you can see repeated arguments

And the anti-signal: if you must list all solutions rather than count or optimise, that is backtracking (Chapter 35), because there is nothing to collapse.

The five steps

1
State — what does dp[...] mean?

One precise English sentence. Not "dp is the answer" — specifically which answer, for which subproblem, and whether the index is inclusive. Write it as a comment before you write any code. If you cannot, nothing after this step will work.

// dp[i] = the maximum money robbable from houses 0..i inclusive
2
Transition — how does a state depend on smaller ones?

Enumerate the choices available at this state and combine their results with min, max or +. The number of choices is the transition's cost, and it multiplies the state count to give the complexity.

// dp[i] = max(dp[i-1], dp[i-2] + nums[i])
3
Base case — the smallest states, by hand

Which states have no dependencies? Fill them directly. Most DP bugs live here, not in the transition — an empty input, a single element, or an index that the transition would read out of bounds.

// dp[0] = nums[0]; dp[1] = max(nums[0], nums[1]);
4
Order — in which sequence do you fill the table?

Every state must be computed after everything it reads. For 1D that is usually increasing i; for 2D it depends on which neighbours the transition uses; for knapsack the capacity loop direction decides whether items can be reused (Chapter 40).

// for(i = 2; i < n; i++) — increasing, since dp[i] reads dp[i-1], dp[i-2]
5
Answer — which cell, and is it the last one?

Often dp[n-1], but not always. Sometimes it is max over the whole table (longest increasing subsequence), or a specific corner, or you must also handle n = 0.

// return dp[n-1]
✍️
My convention: the state sentence goes in a comment, above the array declaration

Every DP in this course opens with // dp[i] = … in plain English. It takes ten seconds and it is the single highest-leverage habit in this level, for two reasons. First, it forces you to decide whether the index is inclusive or exclusive — which is where the off-by-ones come from. Second, when the transition looks wrong you can check it against the sentence instead of guessing. If the sentence and the code disagree, the code is wrong. This is the Chapter 1 invariant rule, and DP is where it pays the most.

// Start here, always. Define the recursion from the CHOICES, not the table.
// At house i: either rob it (and skip i-1) or skip it (and take the best of i-1).
int rob(vector<int> &nums,int i){
	if(i<0)return 0;            // base: no houses left

	int take=nums[i]+rob(nums,i-2);
	int skip=rob(nums,i-1);

	return max(take,skip);
}
// O(2^n). Correct, and unusable past n = 30 — but it is the RIGHT first step,
// because the recurrence is now written down and the rest is mechanical.

Write this first even though you know it is too slow. The recursion is where you discover the choices and the base case; everything after is bookkeeping. And note the guard is i < 0, not i == 0 — the transition reaches i-2, so it can skip past zero (Chapter 11's rule).

// Three added lines. dp[i] = -1 means "not computed yet".
int rob(vector<int> &nums,int i,vector<int> &dp){
	if(i<0)return 0;

	if(dp[i]!=-1)return dp[i];        // 1. read the cache

	int take=nums[i]+rob(nums,i-2,dp);
	int skip=rob(nums,i-1,dp);

	return dp[i]=max(take,skip);         // 2. write it on the way out
}
int rob(vector<int> &nums){
	vector<int> dp(nums.size(),-1);      // 3. driver owns the cache
	return rob(nums,nums.size()-1,dp);
}
// O(n) time, O(n) space + O(n) recursion stack.

This is usually the answer to give in an interview — it is the recursion you already wrote plus three lines, so it is fast to produce and hard to get wrong. The sentinel must be a value the answer can never take: -1 works here because values are non-negative, but for a problem whose answer can be −1 you need a separate computed[] array.

// dp[i] = the maximum money robbable from houses 0..i inclusive.
// Same recurrence, filled bottom-up in increasing i — no recursion at all.
int rob(vector<int> &nums){
	int n=nums.size();
	if(n==0)return 0;
	if(n==1)return nums[0];

	vector<int> dp(n);

	dp[0]=nums[0];                      // base cases, by hand
	dp[1]=max(nums[0],nums[1]);

	for(int i=2;i<n;i++){
		dp[i]=max(dp[i-1],nums[i]+dp[i-2]);
	}

	return dp[n-1];
}
// O(n) time, O(n) space, NO recursion stack. Safe for n = 10^6.

The explicit base cases replace the i < 0 guard. That shift is where tabulation bugs come from — the recursion's guard handled several small cases implicitly, and now each must be written out. Check n = 0 and n = 1 deliberately.

// The recurrence reads only dp[i-1] and dp[i-2], so we never need the
// rest of the table. Two variables replace the whole array.
int rob(vector<int> &nums){
	int prev2=0;                       // dp[i-2]
	int prev1=0;                       // dp[i-1]

	for(int x:nums){
		int current=max(prev1,x+prev2);
		prev2=prev1;
		prev1=current;
	}

	return prev1;
}
// O(n) time, O(1) space. And the base cases vanished — starting both at 0
// handles the empty and single-element inputs automatically.

Read the optimisation off the recurrence. If dp[i] depends only on the previous k entries, you need only k variables. This is mechanical once you see it, and it is the standard follow-up question: "can you do it in O(1) space?"

🔀
When memoisation is strictly better

When the reachable state space is much smaller than the full table. Coin change with a large target but few coins may only reach a fraction of the amounts; a DP over subsets may only visit a sliver of the 2ⁿ masks. Tabulation fills everything regardless; memoisation visits only what the recursion asks for. That is also why memoisation is the right tool when the state is not a dense integer range — keyed on a string, a pair, or a bitmask that needs an unordered_map rather than an array.

Space optimisation, read off the dependencies

the 2D case: one row instead of the whole gridO(n·m) → O(m)
// FULL TABLE. dp[i][j] reads dp[i-1][j] and dp[i][j-1] (and dp[i-1][j-1]).
// So it only ever looks at the PREVIOUS row and the CURRENT row.
vector<vector<int>> dp(n+1,vector<int>(m+1,0));

for(int i=1;i<=n;i++){
	for(int j=1;j<=m;j++){
		dp[i][j]=f(dp[i-1][j],dp[i][j-1],dp[i-1][j-1]);
	}
}

// TWO ROWS. Mechanical: keep prev and cur, swap at the end of each row.
vector<int> prev(m+1,0);
vector<int> cur(m+1,0);

for(int i=1;i<=n;i++){
	for(int j=1;j<=m;j++){
		cur[j]=f(prev[j],cur[j-1],prev[j-1]);
	}
	prev=cur;                  // or swap(prev,cur) to avoid the copy
}

// ONE ROW. Only possible when the diagonal term is NOT needed, because
// writing dp[j] destroys the dp[i-1][j-1] that a later j would want.
// If you do need the diagonal, save it in a temporary before overwriting.
vector<int> dp(m+1,0);

for(int i=1;i<=n;i++){
	int diag=0;                 // holds dp[i-1][j-1]

	for(int j=1;j<=m;j++){
		int saved=dp[j];         // this is dp[i-1][j], needed as next diag
		dp[j]=f(dp[j],dp[j-1],diag);
		diag=saved;
	}
}
The rule: you need as many rows as the recurrence reaches back. Reading only dp[i-1][*] means two rows; reading dp[i-2][*] too means three. And the one-row version requires care precisely when the diagonal term is used, because a single array cannot hold both the old and new value of the same index — hence the diag temporary. Do the full table first, get it correct, then optimise.

Reconstructing the solution

DP gives you the value. When the problem wants the actual subsequence, path or item list, you need one more step.

two ways to recover the choicesO(states) or O(1) extra
// WAY 1: walk the table backwards, re-deciding which branch was taken.
// No extra memory — you re-derive the choice from the stored values.
vector<int> recover(vector<int> &nums,vector<int> &dp){
	vector<int> chosen;
	int i=nums.size()-1;

	while(i>=0){
		int skip=(i>=1)?dp[i-1]:0;

		if(dp[i]==skip){
			i--;                       // house i was NOT robbed
		}else{
			chosen.push_back(i);       // it was
			i-=2;
		}
	}

	reverse(chosen.begin(),chosen.end());

	return chosen;
}

// WAY 2: store the decision as you fill the table. Costs O(states) memory
// but the recovery is trivial and cannot be got wrong.
vector<bool> took(n,false);

for(int i=2;i<n;i++){
	if(nums[i]+dp[i-2]>dp[i-1]){
		dp[i]=nums[i]+dp[i-2];
		took[i]=true;
	}else{
		dp[i]=dp[i-1];
	}
}
Way 1 is incompatible with a rolling array — you threw away the table you need to walk. So if reconstruction is required, either keep the full table or store the decisions. That is the main reason not to space-optimise by reflex: the O(1) version answers "how much?" but cannot answer "which?".
🧮
Complexity is states × transition cost

Every DP's complexity is (number of states) × (work per state), and both factors are read straight off the definition. dp[i] over n values with 2 choices → O(n). dp[i][j] over n × m with O(1) work → O(n·m). dp[i][j] where the transition loops over a split point → O(n²·n) = O(n³), which is interval DP (Chapter 45). dp[mask][i] over 2ⁿ masks and n positions with n transitions → O(2ⁿ·n²), which is Held-Karp (Chapter 44). So you can state the complexity before writing any code, and check it against the constraints from Chapter 2 — if the product exceeds your budget, the state is wrong and you need to find a smaller one.

Debugging a DP

Re-read your state sentence

Nine times out of ten the bug is that the code computes something slightly different from what the comment says — usually an inclusive/exclusive index mismatch.

Print the table for a tiny input

n = 3 or 4, by hand, alongside what you believe it should be. The first cell that disagrees localises the bug to one transition or one base case.

Check the base cases against the empty and single-element inputs

Tabulation makes these explicit that recursion handled implicitly. n = 0 and n = 1 are where most of the failures are.

Verify the loop order against the dependencies

Every state must be filled after everything it reads. If a cell reads a value that is still zero, your order is wrong.

Compare against brute force on random small inputs

Write the exponential version and diff them on a hundred random arrays of size ≤ 10. This finds bugs that reading never will — it is Chapter 53's stress testing.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 STATE SENTENCE
Write dp[i] is … as an English sentence before any code. If the sentence needs two clauses, you need two dimensions — and you have just found them.
💡 TOP-DOWN FIRST
Derive recursively and memoise; convert to a table only if you need the space optimisation. Top-down is far easier to get right and skips unreachable states for free.
⛔ KEY = STATE
The memo key must contain every parameter the answer depends on and nothing else. If two calls with the same key could legitimately differ, the key is incomplete.
⚠️
Common mistakes
  • Writing code before writing the state sentence. The root cause of most DP failures, and the easiest to fix.
  • Ambiguous index convention. Is dp[i] about the first i elements or elements 0..i? Decide in the comment and never drift.
  • Missing base cases in tabulation. The recursion's i < 0 guard covered several; each must now be explicit.
  • Wrong loop order. Reading a cell that has not been filled yet gives silent zeros.
  • A memo sentinel the answer can legitimately take. -1 is unsafe if the answer can be −1; use a separate computed array.
  • A static or global DP table. Works once, then returns stale answers on the second call (Chapter 1).
  • Space-optimising before it is correct. Get the full table right, then collapse it.
  • Space-optimising when reconstruction is needed. You cannot walk a table you discarded.
  • Overflow. Counting problems overflow fast — long long, or take a modulus if the problem asks.
  • Using DP when greedy is provable (Chapter 36) or when the subproblems are disjoint (Chapter 37).

Interview drill

Warm-up: House robber. Walk me through your process, not just the answer.

How a strong answer sounds
I start with the recursion, because that is where the choices become visible. At house i I either rob it — taking nums[i] plus the best from i−2, since i−1 becomes unavailable — or skip it and take the best from i−1. So rob(i) = max(nums[i] + rob(i−2), rob(i−1)), with rob of a negative index being 0. That is correct and O(2ⁿ), and drawing the recursion tree shows rob(i−2) appearing from two different places, which is the overlapping-subproblems signal. So I memoise: a dp array initialised to −1, return the cached value if present, and store on the way out — three added lines, O(n) time and O(n) space plus the stack. Then I would write the bottom-up version, and here I state the invariant explicitly: dp[i] is the maximum money robbable from houses 0 through i inclusive. Base cases dp[0] = nums[0] and dp[1] = max(nums[0], nums[1]), then fill increasing i with the same recurrence, and the answer is dp[n−1]. That removes the recursion stack. Finally, since the recurrence only reads dp[i−1] and dp[i−2], I collapse the array to two variables for O(1) space — and I would mention that this version can no longer reconstruct which houses were robbed, so if the problem wanted the actual set I would keep the table or record the decisions. I would also handle n = 0 and n = 1 explicitly, since the bottom-up version loses the guard that covered them implicitly.

Deeper: How do you decide the state for a problem you have not seen before?

How a strong answer sounds
I work from the brute force. First I write the recursion that enumerates all the choices, however slow — that tells me what a subproblem is, because the recursion's parameters are the state. If the recursive function needs (index, remainingCapacity), then the state is dp[index][capacity]; if it needs (index, lastChoice), the state is dp[index][lastChoice]. So the question "what is the state?" becomes the much more concrete "what does the recursive function need to know to finish the job from here?" — and anything the function reads that is not a parameter is a sign the state is incomplete. Then I check two things before writing a table. One: does the same parameter tuple recur in the recursion tree? If not, it is divide and conquer, not DP. Two: does the number of distinct tuples times the work per tuple fit the constraint budget from Chapter 2? If dp[i][j] over 10⁵ × 10⁵ is implied, the state is too rich and I need to find a smaller sufficient one — often by noticing that a dimension is bounded much more tightly than it looks, or that only a difference matters rather than both values. Once the state passes both checks, I write the one-sentence definition, and the transition, base cases, order and answer all follow from it mechanically.

🧠 Key takeaways

  • DP needs overlapping subproblems and optimal substructure; the recursion tree's repeated arguments are the signal.
  • Five steps: state (one English sentence), transition, base case, order, answer — in that sequence.
  • Write the recursion first, memoise with three lines, then tabulate; the recursion's parameters are the state.
  • Complexity is states × transition cost, and you can state it before writing code.
  • Collapse the table only as far back as the recurrence reaches — and not at all if you need to reconstruct the answer.

Check your understanding

What are the two conditions a problem must satisfy to be solvable by DP?

Overlap is what makes caching pay; optimal substructure is what makes combining subproblem answers valid. Without overlap it is divide and conquer (Chapter 37); without optimal substructure the state is not rich enough.

What should you write before any DP code?

The state definition determines the transition, the base cases, the order and the answer. And when the code misbehaves you can check it against the sentence rather than guessing — most DP bugs are the code and the intended meaning having drifted apart.

dp[i] depends only on dp[i-1] and dp[i-2]. What space do you actually need?

Read the optimisation off the recurrence's reach. The caveat: with two variables you can no longer walk the table to reconstruct which choices were made.

When is memoisation preferable to tabulation?

Tabulation fills every cell whether or not it is needed. Memoisation visits only what the recursion asks for — and it handles states keyed on strings, pairs or sparse bitmasks that would need a map rather than an array.

You space-optimise a DP to two variables, then the follow-up asks which items were chosen. What is the problem?

The O(1) version answers "how much" but not "which". Either keep the full table, or store the decision at each state as you fill it — which is why you should not space-optimise by reflex.
