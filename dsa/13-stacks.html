Stacks & Monotonic Stacks

A stack is five operations and takes ten minutes to learn. The monotonic stack built on top of it is one of the highest-leverage patterns in the whole course: it turns “for each element, find the nearest bigger one” from O(n²) into O(n), and it is the hidden engine behind the largest-rectangle and trapping-rain-water problems that most people find genuinely hard.

  • Recognise the LIFO signature: nesting, matching, and “most recent unresolved thing”
  • Parse expressions and validate brackets with a stack
  • Write the monotonic stack template and state its invariant
  • Prove the O(n) bound even though the inner loop is a while
  • Solve next-greater, histogram and rain-water from the same skeleton

What a stack is for

Push, pop, top, empty, size — all O(1). The interesting question is not how it works but when the shape of a problem is a stack. Three signatures:

🪆

Nesting

Brackets, HTML tags, nested function calls, directory paths. The most recently opened thing must close first — which is exactly LIFO.

↩️

Undo / most recent

Undo history, browser back, the recursion call stack itself. “Give me the thing I saw most recently” is top().

⏳

Pending resolution

The monotonic stack. Hold elements whose answer is not yet known; when a new element arrives it resolves some of them. This is the powerful one.

Warm-up: brackets and expressions

isValid — matched bracketsO(n)O(n)
// Push openers; on a closer, the top MUST be its partner.
bool isValid(string &s){
	stack<char> st;
	unordered_map<char,char> pairs={{')','('},{']','['},{'}','{'}};

	for(char c:s){
		if(c=='(' or c=='[' or c=='{'){
			st.push(c);
		}else{
			if(st.empty())return false;        // closer with nothing open
			if(st.top()!=pairs[c])return false;  // wrong partner

			st.pop();
		}
	}

	return st.empty();                          // leftover openers = unmatched
}
Three failure modes, three checks. Empty stack on a closer (")"), wrong partner ("(]"), and a non-empty stack at the end ("("). Missing that last return st.empty() — writing return true instead — is the single most common bug here, and it passes every balanced test case.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 WHAT INVALIDATES
A monotonic stack is defined by one question: what makes an earlier element useless? For next-greater it is a bigger element arriving — so pop while the top is smaller.
💡 STORE INDICES
Push indices, not values. You almost always need the distance between positions, and you can still read the value with one indirection.
⚡ SENTINELS
Append a 0 to a histogram (and treat −1 as a left sentinel) and the final flush loop disappears — every bar gets popped by the sentinel.
💀
st.top() on an empty stack is undefined behaviour, not an exception

std::stack::top() and pop() on an empty stack do not throw — they read or destroy memory that is not there. Often it appears to work and returns garbage, which is far worse than crashing because the wrong answer surfaces much later. Every top() or pop() must be guarded by !st.empty(), and in the monotonic template below that guard is always the first clause of the while condition.

The monotonic stack

Here is the idea. You are scanning an array and each element has a question: “what is the nearest element to my right that is bigger than me?” The naive answer scans right from every position — O(n²). The insight is that many elements are waiting for the same answer, and when a big element arrives it answers all of them at once.

So: keep a stack of indices whose answer is still unknown, maintained in decreasing order of value. When a new element arrives, it is the answer for everything on the stack smaller than it — pop them all and record it.

the monotonic stack templateO(n)O(n)
// Invariant: the stack holds indices of elements still waiting for an answer,
// with their VALUES strictly decreasing from bottom to top.
vector<int> nextGreater(vector<int> &a){
	int n=a.size();
	vector<int> ans(n,-1);        // -1 = nothing greater to the right
	stack<int> st;                    // stores INDICES, not values

	for(int i=0;i<n;i++){
		// a[i] is the answer for every smaller element still waiting
		while(!st.empty() and a[st.top()]<a[i]){
			ans[st.top()]=a[i];
			st.pop();
		}

		st.push(i);
	}

	// whatever is left never found a greater element — already -1
	return ans;
}
Store indices, not values. You almost always need the position — to write into ans[index], or to compute a width as i - st.top() - 1. Storing values throws that away and you cannot get it back.

Why a while inside a for is still O(n)

Same amortized argument as the sliding window (Chapter 5): count pushes and pops, not loop iterations. Each index is pushed exactly once, and once popped it is never pushed again — so there are at most n pushes and n pops across the entire run. Total work ≤ 2n. The inner while may pop five elements on one iteration and zero on the next twenty; what is bounded is the sum. Watch the counters above: pushes + pops never exceeds 2n, however the array is arranged.

The four variants — one template, four comparisons

Which direction you scan and which comparison you use gives you all four “nearest” questions.

✍️
My convention: flip the comparison, not the loop

All four variants are the same twelve lines with one operator changed, and possibly the loop running backwards. Write the nextGreater skeleton once, commit it to muscle memory, and derive the others by asking “am I looking for bigger or smaller, and on which side?”. This is the skeleton-reuse rule from Chapter 1 — the same reason level order, zigzag and the two views share one loop.

One subtlety worth knowing: use < versus <= deliberately. With <, equal elements stay on the stack and each resolves to the next strictly greater element. With <=, an equal element pops the earlier one. Which you want depends on whether the problem says “greater” or “greater or equal” — and in the histogram problem below, either works, for a reason worth thinking about.

Largest rectangle in a histogram

The hard one, and it is the same template. For each bar, the largest rectangle using that bar as its full height extends left until a shorter bar and right until a shorter bar. So the width is bounded by the previous smaller and next smaller elements — and a monotonic increasing stack gives both in one pass.

largestRectangleAreaO(n)O(n)
// Invariant: the stack holds indices with strictly increasing heights.
// When we pop index p, we have just learned BOTH its boundaries:
//   next smaller is i (the bar that triggered the pop)
//   previous smaller is the new stack top after popping
// so the width is i - st.top() - 1, and the height is heights[p].
int largestRectangleArea(vector<int> &heights){
	heights.push_back(0);      // SENTINEL: forces every bar to be popped

	stack<int> st;
	int best=0;

	for(int i=0;i<heights.size();i++){
		while(!st.empty() and heights[st.top()]>=heights[i]){
			int h=heights[st.top()];
			st.pop();

			// empty stack means nothing smaller to the left: width is all of [0,i)
			int width=st.empty()?i:i-st.top()-1;

			best=max(best,h*width);
		}

		st.push(i);
	}

	heights.pop_back();          // leave the caller's vector as we found it

	return best;
}
The sentinel 0 is what makes this short. Without it, bars still on the stack at the end need a second drain loop with its own width logic — duplicated code and a second chance to get the boundary wrong. A height of 0 is smaller than everything, so it flushes the stack through the normal path. Adding a sentinel to avoid a cleanup loop is a general technique, and it appears again in rain water and in Chapter 14's deque problems.
🧠
The width = st.empty() ? i : i - st.top() - 1 line, explained

After popping index p, the new top is the nearest index to p's left with a strictly smaller height — because the stack was increasing. So the rectangle of height heights[p] can extend from st.top()+1 up to i-1 inclusive, which is i - st.top() - 1 bars. If the stack became empty, nothing to the left is smaller, so it extends all the way from index 0: that is i bars. Derive this on paper once with a three-bar example and it stops being a line to memorise.

Trapping rain water — three solutions

Worth knowing all three, because the interview follow-up is always “can you do better on space?”

// Water above bar i = min(tallest to the left, tallest to the right) - height[i].
// Two prefix sweeps (Chapter 6), then one pass. Easiest to explain and get right.
int trap(vector<int> &h){
	int n=h.size();
	if(n<3)return 0;

	vector<int> leftMax(n),rightMax(n);

	leftMax[0]=h[0];
	for(int i=1;i<n;i++)
	leftMax[i]=max(leftMax[i-1],h[i]);

	rightMax[n-1]=h[n-1];
	for(int i=n-2;i>=0;i--)
	rightMax[i]=max(rightMax[i+1],h[i]);

	int total=0;
	for(int i=0;i<n;i++)
	total+=min(leftMax[i],rightMax[i])-h[i];

	return total;
}

O(n) time, O(n) space. Start here in an interview — it is the clearest statement of why the answer is what it is, and the other two are optimisations of it.

// Decreasing stack. Popping a bar means we have found the right wall,
// and the new top is the left wall — so we can settle that basin now.
int trap(vector<int> &h){
	stack<int> st;
	int total=0;

	for(int i=0;i<h.size();i++){
		while(!st.empty() and h[st.top()]<h[i]){
			int bottom=st.top();
			st.pop();

			if(st.empty())break;        // no left wall -> water spills out

			int width=i-st.top()-1;
			int depth=min(h[st.top()],h[i])-h[bottom];

			total+=width*depth;
		}

		st.push(i);
	}

	return total;
}

O(n) time, O(n) space. Computes water layer by layer rather than column by column, which is a genuinely different mental model — the same width/left-wall arithmetic as the histogram.

// Converging two pointers (Ch 4). The shorter side is the binding constraint,
// so its water level is already known — settle it and move inward.
int trap(vector<int> &h){
	int left=0;
	int right=h.size()-1;
	int leftMax=0;
	int rightMax=0;
	int total=0;

	while(left<right){
		if(h[left]<h[right]){
			leftMax=max(leftMax,h[left]);
			total+=leftMax-h[left];
			left++;
		}else{
			rightMax=max(rightMax,h[right]);
			total+=rightMax-h[right];
			right--;
		}
	}

	return total;
}

O(n) time, O(1) space — the optimal answer. The reason it works: when h[left] < h[right], some bar at or right of right is at least h[right] > h[left], so leftMax is definitely the binding wall for left and no future information can change it. Same "move the shorter side" argument as container-with-most-water.

⚠️
Common mistakes
  • Calling top() or pop() without checking empty(). Undefined behaviour, often returning garbage instead of crashing. Put !st.empty() first in every while condition.
  • Returning true instead of st.empty() in bracket matching. Passes every balanced test and fails on "(".
  • Storing values instead of indices in a monotonic stack. You lose the positions, so you cannot compute widths or write into ans.
  • Forgetting the sentinel in the histogram. Bars left on the stack are never measured, so a monotonically increasing input returns 0 or a too-small answer.
  • Getting the width wrong after a pop. It is i - st.top() - 1, with the empty-stack case being i. Derive it once on paper.
  • Assuming the nested while makes it O(n²). Each index is pushed and popped once; total work is ≤ 2n.
  • Mutating the caller's vector and not restoring it. If you push_back a sentinel, pop_back it before returning.
  • Mixing up < and <= without deciding. It changes how equal elements resolve, and some problems care.

Interview drill

Warm-up: Explain the monotonic stack invariant and why the algorithm is O(n).

How a strong answer sounds
The stack holds indices of elements whose answer I do not know yet, kept so that their values are monotone — decreasing from bottom to top if I am hunting for the next greater element. The invariant is the key: if element x sits above element y on the stack, then x came later and x is smaller, so any future element big enough to resolve y must first resolve x. That is why popping in order is correct and why I never need to look past the top. When a new element arrives, it is the answer for every element on the stack smaller than it, so I pop those, record it, and then push the new index. For complexity I count pushes and pops rather than loop iterations: each index is pushed exactly once, and once popped it never returns, so there are at most n of each and total work is bounded by 2n. The inner while can pop five elements on one step and zero on the next twenty — what is bounded is the sum, which is the same amortized argument as vector's push_back.

Deeper: Largest rectangle in a histogram. Why does the width formula work, and what does the sentinel do?

How a strong answer sounds
For each bar I want the largest rectangle that uses that bar's full height, so I need how far left and right it can extend before hitting something shorter — that is, its previous smaller and next smaller elements. An increasing monotonic stack gives me both at the moment of the pop, which is the whole trick: the bar i that triggered the pop is the next smaller, and whatever is on the stack after popping is the previous smaller, because everything between them was taller and already popped. So the rectangle spans from st.top()+1 to i-1, which is i - st.top() - 1 bars. If the stack empties, nothing to the left is shorter, so it spans from index 0 and the width is just i. The sentinel zero appended to the end forces every remaining bar to be popped through that same code path — without it, a monotonically increasing histogram never pops anything and I would need a separate drain loop with duplicated width logic, which is a second place to get the boundary wrong. I would also mention restoring the vector with pop_back afterwards, since mutating a caller's argument is rude even when it happens to work.

🧠 Key takeaways

  • Stack signatures: nesting, most-recent/undo, and “elements pending resolution” — the third is the monotonic stack.
  • The monotonic stack holds indices whose answer is unknown, in monotone value order; a new element resolves all of them it dominates.
  • It is O(n) because each index is pushed and popped at most once — count pushes and pops, not iterations.
  • After a pop, the width is i - st.top() - 1, or i when the stack empties.
  • A sentinel value at the end replaces a duplicated drain loop; always guard top() with !empty().

Check your understanding

A monotonic stack algorithm has a while loop inside a for loop. What is its complexity?

Count pushes and pops, not iterations. An index that has been popped never returns, so both counts are capped at n. Same amortized argument as the sliding window and push_back.

Why store indices rather than values in a monotonic stack?

The value is always recoverable as a[index], but the index is not recoverable from the value. Every width-based problem — histogram, rain water, subarray minimums — needs the position.

In the histogram solution, what does appending a sentinel 0 accomplish?

Without it, an increasing histogram never pops anything and you need a second loop with duplicated width logic — a second place to get the boundary wrong. A height smaller than everything flushes the stack for free.

Your bracket validator returns true for the input "(". What did you forget?

There are three failure modes and this is the third. It passes every balanced test case, which is exactly why it survives to production.

What is the optimal space complexity for trapping rain water, and with what technique?

When h[left] < h[right], something at or right of right is taller than h[left], so leftMax is definitely the binding wall and no future information can change it. Settle and move in — O(n) time, O(1) space.
