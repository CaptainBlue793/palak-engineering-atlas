Stacks & Monotonic Stacks

A stack is a pile: you add to the top and you remove from the top, so the last thing in is the first thing out. It has five operations and takes ten minutes to learn. The monotonic stack built on top of it is one of the most useful patterns in the whole course. It turns “for each element, find the nearest bigger one” from O(n²) into O(n), and it is the hidden engine behind the largest-rectangle and trapping-rain-water problems that most people find genuinely hard.

What a stack is for

Push, pop, top, empty, size: all O(1). Here is what each one does. push(x) puts x on top. pop() removes the top item (in C++ it does not return it, so read top() first). top() looks at the top item without removing it. empty() and size() tell you how many items there are. You can only ever see or touch the top; the items below it are hidden until everything above them is gone.

A tiny example: push 1, push 2, push 3, then pop twice. The pops remove 3 and then 2, the reverse of the order they went in, and 1 is left on top. That reversal is the whole character of a stack.

In C++ you can use std::stack, or a plain vector with push_back, pop_back and back(). They behave the same. The vector version also lets you look at any element, which is handy when debugging or when a problem needs to peek below the top. The interesting question is not how a stack works, but how to recognise a problem that needs one. Three signs:

🪆

Nesting

Brackets, HTML tags, nested function calls, directory paths. Whatever opened most recently must close first. That is exactly LIFO (last in, first out).

↩️

Undo / most recent

Undo history, the browser back button, the call stack itself. “Give me the thing I saw most recently” is top().

⏳

Pending resolution

The monotonic stack. You hold elements whose answer you do not know yet. When a new element arrives, it answers some of them. This is the powerful one.

Warm-up: brackets and expressions

Why a stack fits brackets: when you meet a closing bracket, it must match the most recently opened bracket that is still open. “Most recent still open” is exactly what top() gives you. Compilers, code editors and HTML parsers all check nesting this way.

A dry run on "([)]", which looks balanced by count but is not:

  1. ( is an opener: push. Stack: (
  2. [ is an opener: push. Stack: ( [ (top is [)
  3. ) is a closer. Its partner is (, but the top is [. Wrong partner: return false.

On "([])" the same steps push ( and [, then ] matches [ and pops it, ) matches ( and pops it, and the stack ends empty: valid. Counting brackets alone would call both strings valid. Only the stack sees the order.

isValid — matched bracketsO(n)O(n)
// Push openers; on a closer, the top MUST be its partner.
bool isValid(string &s){
	stack<char> st;
	unordered_map<char,char> pairs={{')','('},{']','['},{'}','{'}};

	for(char c:s){
		if(c=='(' or c=='[' or c=='{'){
			st.push(c);
		}else{
			if(st.empty())return false;        // closer with nothing open
			if(st.top()!=pairs[c])return false;  // wrong partner

			st.pop();
		}
	}

	return st.empty();                          // leftover openers = unmatched
}
Three ways a string can be invalid, so three checks. A closing bracket with nothing open (")"), a closing bracket that does not match the top ("(]"), and brackets still open at the end ("("). Forgetting that last return st.empty() and writing return true instead is the most common bug here. It passes every balanced test case, so it hides well.

Expressions: reverse Polish notation

The same idea evaluates arithmetic. In reverse Polish notation (RPN) the operator comes after its two operands, so (2 + 1) * 3 is written 2 1 + 3 *. There are no brackets and no precedence rules to worry about. The rule: push numbers; on an operator, pop two numbers, apply the operator, and push the result.

  • 2, 1: push both. Stack: 2 1
  • +: pop 1 and 2, push 2 + 1 = 3. Stack: 3
  • 3: push. Stack: 3 3
  • *: pop 3 and 3, push 9. Stack: 9, which is the answer.

One trap: the first number you pop is the right operand. For 7 2 - you pop 2, then 7, and compute 7 − 2 = 5, not 2 − 7. Subtraction and division care about the order; addition and multiplication do not, which is why the bug hides. Normal expressions with brackets and precedence (the “basic calculator” problems) use the same push-and-pop idea, usually with a second stack for operators or saved signs.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 WHAT INVALIDATES
A monotonic stack is defined by one question: what makes an earlier element useless? For next-greater it is a bigger element arriving — so pop while the top is smaller.
💡 STORE INDICES
Push indices, not values. You almost always need the distance between positions, and you can still read the value with one indirection.
⚡ SENTINELS
Append a 0 to a histogram (and treat −1 as a left sentinel) and the final flush loop disappears — every bar gets popped by the sentinel.
💀
st.top() on an empty stack is undefined behaviour, not an exception

On an empty stack, std::stack::top() and pop() do not throw an exception. They read or destroy memory that is not there. Often the program seems to work and just returns garbage, which is worse than crashing, because the wrong answer shows up much later and far away. Every top() or pop() needs a !st.empty() check first. In the monotonic template below, that check is always the first part of the while condition.

The monotonic stack

Here is the idea. You are scanning an array, and every element has the same question: “what is the nearest element to my right that is bigger than me?” The obvious method scans rightwards from every position, which is O(n²).

The insight: many elements are waiting for the same answer. When one big element arrives, it answers all of them at once. Picture people queuing to ask “who is the next person taller than me?” One tall person walking in answers everyone shorter who is still waiting.

So keep a stack of indices whose answer is still unknown, ordered so the values decrease from the bottom to the top. When a new element arrives, it is the answer for everything on the stack that is smaller than it. Pop them all and record the answer. "Monotonic" just means the values on the stack always go one way: all decreasing, or all increasing.

the monotonic stack templateO(n)O(n)
// Invariant: the stack holds indices of elements still waiting for an answer,
// with their VALUES strictly decreasing from bottom to top.
vector<int> nextGreater(vector<int> &a){
	int n=a.size();
	vector<int> ans(n,-1);        // -1 = nothing greater to the right
	stack<int> st;                    // stores INDICES, not values

	for(int i=0;i<n;i++){
		// a[i] is the answer for every smaller element still waiting
		while(!st.empty() and a[st.top()]<a[i]){
			ans[st.top()]=a[i];
			st.pop();
		}

		st.push(i);
	}

	// whatever is left never found a greater element — already -1
	return ans;
}
Store indices, not values. You almost always need the position, either to write into ans[index] or to compute a width as i - st.top() - 1. Storing values throws the position away, and you cannot get it back. You can always get the value from the index with a[index].

A dry run on a = [2, 1, 5, 3, 4]. The stack is written bottom → top, as value@index:

ia[i]What happensStack after
02stack empty: push 02@0
112 is not smaller than 1: push 12@0 1@1
251 < 5: ans[1] = 5, pop. 2 < 5: ans[0] = 5, pop. Push 25@2
335 is not smaller than 3: push 35@2 3@3
443 < 4: ans[3] = 4, pop. 5 is not smaller: push 45@2 4@4

Result: ans = [5, 5, -1, 4, -1]. Index 2 (value 5) and index 4 (value 4) are still on the stack at the end, so nothing to their right is bigger and they keep −1. Count the work: 5 pushes and 3 pops, 8 operations for n = 5, and never more than 2n.

Why the stack stays in order by itself: before pushing i, the loop pops everything smaller than a[i]. So whatever is left underneath is at least a[i], and pushing i keeps the values going down (or staying equal) from bottom to top. And why popping from the top is safe: an element deeper in the stack is bigger than everything above it, so any new value big enough to answer the deep one has already answered all the ones above it first.

🧾
Why a while inside a for is still O(n)

This is the same averaging argument as the sliding window (Chapter 5): count pushes and pops, not loop iterations. Each index is pushed exactly once, and once it is popped it never comes back. So across the whole run there are at most n pushes and n pops. Total work is at most 2n.

The inner while might pop five elements on one step and none on the next twenty. What is limited is the total, not any single step. Watch the counters above: pushes + pops never goes above 2n, no matter how the array is arranged.

The four variants — one template, four comparisons

Change the scan direction and the comparison operator, and the same template answers all four “nearest” questions.

QuestionScanPop whileStack order (bottom→top)
Next greater to the rightleft → righta[top] < a[i]decreasing
Next smaller to the rightleft → righta[top] > a[i]increasing
Previous greater to the leftright → lefta[top] < a[i]decreasing
Previous smaller to the leftright → lefta[top] > a[i]increasing

Why scanning right → left gives the previous element: going backwards, the “next” element you meet is the one to the left in the original array. So the same code, run on the array in reverse, answers “nearest to the left”.

You can also get a previous-element answer during a normal left → right scan. After the while finishes popping, whatever is left on top is the nearest element to the left that survived. For example, pop while a[top] <= a[i]; then the top (if any) is the previous strictly greater element of i. The histogram code below uses exactly this trick to get both boundaries in one pass.

Where each one shows up: “how many days until a warmer temperature?” is next greater (daily temperatures). “How many days in a row, ending today, was the price at most today's price?” is previous greater (stock span). “How far can this bar stretch?” needs both previous smaller and next smaller (histogram).

✍️
My convention: flip the comparison, not the loop

All four variants are the same twelve lines, with one operator changed and sometimes the loop running backwards. Learn the nextGreater skeleton by heart, then work out the others by asking: “am I looking for bigger or smaller, and on which side?” This is the reuse-one-skeleton rule from Chapter 1, the same reason level order, zigzag and the two side views share one loop.

One subtlety: choose between < and <= on purpose. With <, equal elements stay on the stack, and each one waits for the next strictly greater element. With <=, an equal element pops the earlier one. Which you want depends on whether the problem says “greater” or “greater or equal”. In the histogram problem below, either works, which is worth thinking about.

Largest rectangle in a histogram

This is the hard one, and it uses the same template. Think of each bar and ask: how wide can a rectangle be if its height is exactly this bar's height? It can stretch left until it meets a shorter bar, and right until it meets a shorter bar. Any shorter bar would poke through the top.

So the width is set by the previous smaller bar and the next smaller bar. An increasing monotonic stack hands you both in a single pass.

A small example first. For heights [2, 1, 5, 6, 2, 3], take the bar of height 5 at index 2. To its left, index 1 has height 1, which is shorter, so it cannot go further left. To its right, index 3 (height 6) is fine, but index 4 (height 2) is shorter. So the rectangle of height 5 covers indices 2 and 3: width 2, area 10. That is the answer for this input. Trying every bar this way by scanning outwards is O(n²). The stack finds all those boundaries in O(n).

// Invariant: the stack holds indices with strictly increasing heights.
// When we pop index p, we have just learned BOTH its boundaries:
//   next smaller is i (the bar that triggered the pop)
//   previous smaller is the new stack top after popping
// so the width is i - st.top() - 1, and the height is heights[p].
int largestRectangleArea(vector<int> &heights){
	heights.push_back(0);      // SENTINEL: forces every bar to be popped

	stack<int> st;
	int best=0;

	for(int i=0;i<heights.size();i++){
		while(!st.empty() and heights[st.top()]>=heights[i]){
			int h=heights[st.top()];
			st.pop();

			// empty stack means nothing smaller to the left: width is all of [0,i)
			int width=st.empty()?i:i-st.top()-1;

			best=max(best,h*width);
		}

		st.push(i);
	}

	heights.pop_back();          // leave the caller's vector as we found it

	return best;
}
The sentinel 0 is what keeps this short. A sentinel is a fake value added at the end to make the loop handle the final case by itself. Without it, the bars still on the stack at the end need a second clean-up loop with its own width maths: duplicated code, and a second chance to get the boundary wrong. A height of 0 is smaller than everything, so it empties the stack through the normal path. Adding a sentinel to avoid a clean-up loop is a general technique. It comes back in rain water and in Chapter 14's deque problems.
🧠
The width = st.empty() ? i : i - st.top() - 1 line, explained

After popping index p, the new top is the nearest index to p's left with a strictly smaller height, because the stack was increasing. So a rectangle of height heights[p] can run from st.top()+1 to i-1, and that is i - st.top() - 1 bars. If the stack is now empty, nothing to the left is smaller, so the rectangle runs all the way from index 0, which is i bars. Work this out on paper once with a three-bar example, and it stops being a line you have to memorise.

The full run on [2, 1, 5, 6, 2, 3] with the sentinel 0 added at index 6. Only the pops matter, because that is when an area is measured:

The best area is 10, matching the example above. Notice the last three rows: they all come from the sentinel. Without it, bars 1, 4 and 5 would never be measured, and the bar of height 2 spanning four columns (area 8) would be lost.

Two edge cases worth knowing. Equal heights: the code pops on >=, so a second bar of the same height pops the first one. The first bar's width comes out too short, but that is harmless: the second bar has the same height and is measured later with the full width. That is why > and >= both give the right maximum. Overflow: the area is height × width. If heights can reach 10⁹ or n × max height can pass about 2.1 × 10⁹, compute it in long long.

Trapping rain water — three solutions

The problem: bars of different heights form a landscape, and rain fills the dips between taller bars. How much water is held? Learn all three solutions, because the interview follow-up is always “can you use less space?”

The key fact behind all three: the water above one column rises to the height of the shorter of the two tallest walls around it, one on the left and one on the right. Water higher than that would spill over the shorter wall. So the water on column i is min(tallest on the left, tallest on the right) − h[i], and it is never negative because both tallest values include h[i] itself.

Worked example, h = [3, 0, 2, 0, 4]. Tallest-on-the-left is [3, 3, 3, 3, 4], tallest-on-the-right is [4, 4, 4, 4, 4]. The smaller of each pair is [3, 3, 3, 3, 4]. Subtract the heights: 0 + 3 + 1 + 3 + 0 = 7 units of water. The two end columns can never hold water, since one side has no wall at all.

// Water above bar i = min(tallest to the left, tallest to the right) - height[i].
// Two prefix sweeps (Chapter 6), then one pass. Easiest to explain and get right.
int trap(vector<int> &h){
	int n=h.size();
	if(n<3)return 0;

	vector<int> leftMax(n),rightMax(n);

	leftMax[0]=h[0];
	for(int i=1;i<n;i++)
	leftMax[i]=max(leftMax[i-1],h[i]);

	rightMax[n-1]=h[n-1];
	for(int i=n-2;i>=0;i--)
	rightMax[i]=max(rightMax[i+1],h[i]);

	int total=0;
	for(int i=0;i<n;i++)
	total+=min(leftMax[i],rightMax[i])-h[i];

	return total;
}

O(n) time, O(n) space. Start here in an interview. It states most clearly why the answer is what it is, and the other two solutions are just improvements on it.

// Decreasing stack. Popping a bar means we have found the right wall,
// and the new top is the left wall — so we can settle that basin now.
int trap(vector<int> &h){
	stack<int> st;
	int total=0;

	for(int i=0;i<h.size();i++){
		while(!st.empty() and h[st.top()]<h[i]){
			int bottom=st.top();
			st.pop();

			if(st.empty())break;        // no left wall -> water spills out

			int width=i-st.top()-1;
			int depth=min(h[st.top()],h[i])-h[bottom];

			total+=width*depth;
		}

		st.push(i);
	}

	return total;
}

O(n) time, O(n) space. This one adds up the water layer by layer instead of column by column, which is a genuinely different way to picture it. The width and left-wall arithmetic is the same as in the histogram.

// Converging two pointers (Ch 4). The shorter side is the binding constraint,
// so its water level is already known — settle it and move inward.
int trap(vector<int> &h){
	int left=0;
	int right=h.size()-1;
	int leftMax=0;
	int rightMax=0;
	int total=0;

	while(left<right){
		if(h[left]<h[right]){
			leftMax=max(leftMax,h[left]);
			total+=leftMax-h[left];
			left++;
		}else{
			rightMax=max(rightMax,h[right]);
			total+=rightMax-h[right];
			right--;
		}
	}

	return total;
}

O(n) time, O(1) space: the best possible. Why it works: when h[left] < h[right], there is a bar at or to the right of right that is at least h[right], and h[right] > h[left]. So the right side is definitely tall enough, and leftMax is what limits the water above left. Nothing you learn later can change that, so you can settle this column now. It is the same "move the shorter side" argument as container-with-most-water.

Which one to write? In an interview, explain the prefix-max version first because it proves the formula, then offer two pointers when asked for less space. Reach for the stack version when the problem changes shape: it settles each basin as soon as its right wall arrives, so it adapts to variants where you must process bars as they stream in, and it is the same code shape as the histogram. Edge cases for all three: fewer than 3 bars, all bars equal, and strictly rising or falling bars all hold 0 water.

⚠️
Common mistakes
  • Calling top() or pop() without checking empty(). This is undefined behaviour, and it often returns garbage instead of crashing. Put !st.empty() first in every while condition.
  • Returning true instead of st.empty() in bracket matching. It passes every balanced test and fails on "(".
  • Storing values instead of indices in a monotonic stack. You lose the positions, so you cannot compute widths or write into ans.
  • Forgetting the sentinel in the histogram. Bars left on the stack are never measured, so an always-increasing input returns 0 or an answer that is too small.
  • Getting the width wrong after a pop. It is i - st.top() - 1, or just i when the stack is empty. Work it out once on paper.
  • Assuming the nested while makes it O(n²). Each index is pushed and popped once, so total work is at most 2n.
  • Changing the caller's vector and not putting it back. If you push_back a sentinel, pop_back it before returning.
  • Mixing up < and <= by accident. It changes how equal elements are handled, and some problems care.

Interview drill

Warm-up: Explain the monotonic stack invariant and why the algorithm is O(n).

How a strong answer sounds
The stack holds indices of elements whose answer I do not know yet, kept in order of value: decreasing from bottom to top when I am looking for the next greater element. The rule that always holds is the key. If element x sits above element y on the stack, then x arrived later and x is smaller. So any future element big enough to answer y must answer x first. That is why popping from the top in order is correct, and why I never need to look below the top. When a new element arrives, it is the answer for every element on the stack smaller than it, so I pop those, record the answer, and push the new index. For complexity, I count pushes and pops rather than loop iterations. Each index is pushed exactly once, and once popped it never comes back, so there are at most n of each and the total work is at most 2n. The inner while can pop five elements on one step and none on the next twenty. What is limited is the total, which is the same averaging argument as vector's push_back.

Deeper: Largest rectangle in a histogram. Why does the width formula work, and what does the sentinel do?

How a strong answer sounds
For each bar I want the largest rectangle that uses that bar's full height. So I need to know how far it can stretch left and right before it hits a shorter bar: its previous smaller and next smaller elements. An increasing monotonic stack gives me both at the moment I pop, and that is the whole trick. The bar i that caused the pop is the next smaller one. Whatever is left on the stack after popping is the previous smaller one, because everything in between was taller and has already been popped. So the rectangle runs from st.top()+1 to i-1, which is i - st.top() - 1 bars. If the stack becomes empty, nothing to the left is shorter, so it runs from index 0 and the width is just i. The sentinel zero at the end forces every remaining bar to be popped through that same code. Without it, an always-increasing histogram never pops anything, and I would need a separate clean-up loop with duplicate width logic: a second place to get the boundary wrong. I would also restore the vector with pop_back afterwards, since changing a caller's argument is rude even when it happens to work.

🧠 Key takeaways

  • Three signs you need a stack: nesting, most-recent/undo, and “elements still waiting for an answer”. The third is the monotonic stack.
  • A monotonic stack holds indices whose answer is unknown, kept in increasing or decreasing value order. A new element answers every one it beats.
  • It is O(n) because each index is pushed and popped at most once. Count pushes and pops, not loop iterations.
  • After a pop, the width is i - st.top() - 1, or just i when the stack is empty.
  • A sentinel at the end removes the need for a duplicate clean-up loop. Always check !empty() before top().

Check your understanding

A monotonic stack algorithm has a while loop inside a for loop. What is its complexity?

Count pushes and pops, not loop iterations. An index that has been popped never comes back, so both counts stop at n. It is the same averaging argument as the sliding window and push_back.

Why store indices rather than values in a monotonic stack?

You can always get the value back with a[index], but you cannot get the index back from a value. Every problem that measures a width, such as histogram, rain water and subarray minimums, needs the position.

In the histogram solution, what does appending a sentinel 0 accomplish?

Without it, an always-increasing histogram never pops anything, so you need a second loop with duplicate width logic: another place to get the boundary wrong. A height smaller than everything empties the stack for free.

Your bracket validator returns true for the input "(". What did you forget?

There are three ways the input can be invalid, and this is the third one. The bug passes every balanced test case, which is exactly why it reaches production.

What is the optimal space complexity for trapping rain water, and with what technique?

When h[left] < h[right], there is something at or to the right of right taller than h[left]. So leftMax is the wall that limits the water here, and nothing you learn later can change that. Settle this column and move inwards: O(n) time, O(1) space.
