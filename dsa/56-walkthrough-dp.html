Walkthrough: A Hard DP Problem

The last chapter, and the method from Chapter 38 applied under pressure to Best Time to Buy and Sell Stock IV: at most k transactions, maximise profit. It is chosen because the first correct recurrence is too slow, and fixing it requires spotting a recomputed maximum — which is the single most transferable DP optimisation there is. We will go from brute force to O(n·k) to O(k) space, and finish with the follow-ups.

  • Define a DP state precisely enough that the transition writes itself
  • Derive the natural O(n²k) recurrence and then find its redundancy
  • Reduce to O(n·k) by carrying a running best
  • Roll the table down to O(k) space, and handle the unlimited-transactions case
  • Re-derive the whole thing as a state machine and compare
📋
The problem

Best Time to Buy and Sell Stock IV. You are given an array prices where prices[i] is the price of a stock on day i, and an integer k. Find the maximum profit you can achieve with at most k transactions. A transaction is one buy followed later by one sell. You may not hold more than one share at a time — you must sell before buying again. Constraints: 1 ≤ prices.length ≤ 1000, 0 ≤ k ≤ 100, 0 ≤ prices[i] ≤ 1000.

Stage 1 — Clarify, then find the sub-structure

1
The questions that change the code

Three worth asking, and only three. "At most k, or exactly k?" — at most, which means doing nothing is always allowed and the answer is never negative. "Can I hold more than one share?" — no, which is what makes the problem sequential rather than a knapsack. "Can I buy and sell on the same day?" — it would earn zero, so it does not matter, but confirming it means the recurrence need not exclude it.

Now the sub-structure. Walking the days left to right, on each day exactly one of three things happens: I do nothing, I buy, or I sell. Whether buying is even legal depends on whether I currently hold a share, and how many transactions remain. So the decision at day i depends on two things beyond i itself — and that observation is the state.

Two sanity checks before going further. With k = 1 this is the classic single-transaction problem, answered by tracking the minimum price so far. With k = ∞ it is the "sum every upward step" greedy. A correct general solution must reduce to both, which gives two free tests.

Stage 2 — The brute force, and its complexity

2
Recursion over three choices
// solve(i, holding, remaining) = the best profit obtainable from day i onward.
int solve(int i,bool holding,int remaining,vector<int> &prices){
	if(i==prices.size() or remaining==0)return 0;

	int skip=solve(i+1,holding,remaining,prices);

	if(holding){
		// sell today: gain today's price, one transaction consumed
		int sell=prices[i]+solve(i+1,false,remaining-1,prices);

		return max(skip,sell);
	}

	// buy today: pay today's price
	int buy=-prices[i]+solve(i+1,true,remaining,prices);

	return max(skip,buy);
}

Two branches per day gives O(2ⁿ) — hopeless at n = 1000. But notice the state: (i, holding, remaining) is n × 2 × (k+1) distinct values, about 200,000 here, and the recursion revisits them enormously often. That is the definition of overlapping subproblems, so memoising on exactly those three parameters gives O(n·k) states with O(1) work each.

Worth saying explicitly: this memoised version is already the optimal complexity. Everything that follows is a bottom-up rederivation — and the reason to do it is that the obvious bottom-up formulation is the one that hides a trap. It is also why I would state this top-down version first in a real round: it is the easiest to get right, and it banks a correct answer.

🔍
Deciding the transaction counter's meaning

One small decision with real consequences: does a transaction get consumed on the buy or on the sell? Either is fine, but they must be consistent, and consuming it on the sell is better — it means a dangling buy with no matching sell can never be counted, so the "at most k" bound is automatically enforced on completed round trips. If you decrement on the buy, you must be careful that an unsold share does not waste a transaction that could have been used profitably. State which convention you chose, in a comment. Half the wrong answers on this problem are an inconsistency between the two.

Stage 3 — The bottom-up trap

3
The natural table, and why it is O(n²k)

The textbook bottom-up formulation indexes by transaction count and day: dp[t][i] = the best profit using at most t transactions within the first i+1 days. Either you make no transaction ending on day i, giving dp[t][i-1], or your t-th transaction sells on day i having bought on some earlier day j:

dp[t][i]=max(dp[t][i-1],
            max over j<i of (prices[i]-prices[j]+dp[t-1][j]))

That is correct, and it is O(n²k) — a million cells times an inner scan of a thousand times k. At n = 1000 and k = 100 that is 10⁸ per unit of k, far too slow. So name the redundancy: for each new i, the inner loop recomputes a maximum over all j < i that it already computed for i-1, changing only by one new candidate. That is a recomputed running aggregate — exactly the pattern from Chapter 6 and Chapter 39, and exactly the thing a carried variable removes.

the fix — factor prices[i] out and carry the bestO(n·k)O(n·k)
// The inner max is  max over j<i of (prices[i] - prices[j] + dp[t-1][j]).
// prices[i] does not depend on j, so pull it out:
//     prices[i] + max over j<i of (dp[t-1][j] - prices[j])
// That inner quantity does not involve i at all — so it can be carried in a
// single variable, updated once per day. The inner loop disappears.
int maxProfit(int k,vector<int> &prices){
	int n=prices.size();

	if(n<2 or k==0)return 0;

	// A transaction needs two days, so more than n/2 transactions is the same
	// as unlimited — and the unlimited case has a linear greedy answer.
	if(k>=n/2)return unlimited(prices);

	vector<vector<int>> dp(k+1,vector<int>(n,0));

	for(int t=1;t<=k;t++){
		// best = max over j seen so far of (dp[t-1][j] - prices[j])
		// Initialised at j = 0: dp[t-1][0] is 0, so this is -prices[0].
		int best=-prices[0];

		for(int i=1;i<n;i++){
			dp[t][i]=max(dp[t][i-1],prices[i]+best);

			best=max(best,dp[t-1][i]-prices[i]);
		}
	}

	return dp[k][n-1];
}

// Unlimited transactions: take every upward step. Any profitable run
// p[a] < p[b] decomposes into consecutive rises summing to the same total,
// so buying every dip and selling every peak is optimal.
int unlimited(vector<int> &prices){
	int ans=0;

	for(int i=1;i<prices.size();i++){
		if(prices[i]>prices[i-1])ans+=prices[i]-prices[i-1];
	}

	return ans;
}
The order of the two highlighted lines matters and is the subtlest point here. dp[t][i] is computed using best as it stood over j < i, and only then is j = i folded in. Swapping them would allow buying and selling on the same day — harmless in this problem, since it earns zero, but the discipline is what matters: the carried variable must reflect exactly the range the recurrence claims. Note also that the k ≥ n/2 short-circuit is not an optimisation for elegance — without it, k = 10⁹ would allocate a table with 10⁹ rows.

Stage 5 — Space, and the state-machine rederivation

Rolling to O(k) space
// Row t only ever reads row t-1 and its own previous cell. But the carried
// `best` per row makes it neater to flip the loops: iterate DAYS outside and
// TRANSACTIONS inside, keeping one buy/sell value per transaction count.
int maxProfit(int k,vector<int> &prices){
	int n=prices.size();

	if(n<2 or k==0)return 0;
	if(k>=n/2)return unlimited(prices);

	// buy[t]  = best balance while HOLDING, having begun transaction t
	// sell[t] = best balance after COMPLETING transaction t
	vector<int> buy(k+1,INT_MIN/2);
	vector<int> sell(k+1,0);

	for(auto &price:prices){
		for(int t=1;t<=k;t++){
			buy[t]=max(buy[t],sell[t-1]-price);
			sell[t]=max(sell[t],buy[t]+price);
		}
	}

	return sell[k];
}

Six lines, O(n·k) time, O(k) space. INT_MIN/2 rather than INT_MIN is deliberate — buy[t]+price must not overflow while buy[t] is still a sentinel (Chapter 53, bug 2). Updating buy[t] then immediately using it in sell[t] permits a same-day round trip, which earns zero and is therefore harmless; if the problem forbade it, you would compute both from the previous day's values.

Why this is the same thing

Read the two lines as a state machine. There are 2k states: "holding, part-way through transaction t" and "idle, having completed t". Each day you may move along an edge or stay put, and max keeps the best balance in each state.

buy[t] = max(buy[t], sell[t-1] − price) says: either I was already holding, or I was idle after t−1 completed trades and I buy today. sell[t] = max(sell[t], buy[t] + price) says: either I was already idle after t trades, or I was holding and sell today.

This formulation is the one to remember, because the entire stock-problem family is the same machine with the edges altered: a cooldown adds a "resting" state; a transaction fee subtracts it on one edge; at most 2 transactions is this with k = 2 unrolled into four named variables; unlimited is one buy and one sell state with no counter.

And it reduces correctly at the boundaries: with k = 1, buy[1] tracks the minimum price negated and sell[1] the best single profit — precisely the classic solution. That is the free test from Stage 1, passed.

The step worth internalising is row four. "An inner loop recomputing a maximum that changes by one element" is a redundancy you will meet dozens of times — in maximum subarray, in LIS with a Fenwick tree, in sliding-window maxima with a deque, and here. Factor out what does not depend on the inner index, and carry the rest.

🧪
The tests to volunteer
  • k = 0 or fewer than two prices → 0. The guard must come before any allocation.
  • Monotonically decreasing prices → 0. "At most k" means doing nothing is allowed, so the answer is never negative.
  • k = 1 → must equal the classic single-transaction answer.
  • Huge k, say 10⁹ → the short-circuit must fire, or you allocate a table with 10⁹ rows.
  • All prices equal → 0, and no negative profit from a same-day round trip.
  • k larger than the number of profitable runs → the surplus transactions must simply go unused.
  • Stress test — compare the O(k)-space version against the memoised recursion on random arrays of length 6–8 with k from 0 to 4. Every version in the table above should agree, which is the cheapest possible confirmation that the derivation held.
🔮
The follow-ups
  • "Add a one-day cooldown after selling." Insert a third state per transaction: rest[t]. Sell moves into rest, and buying may only come from rest or from an earlier idle state. The machine grows a node; the loop structure does not change.
  • "Add a fee per transaction." Subtract it on one edge — either buy[t] = max(buy[t], sell[t-1] − price − fee) or on the sell. Pick one, and only one.
  • "Return the actual buy and sell days." Store a parent per state transition, or keep the full dp table and walk back. This is the standard cost of space optimisation (Chapters 41 and 42).
  • "You may hold up to m shares at once." The state gains a dimension for shares held, giving O(n·k·m). A good moment to say that adding a dimension is the standard response to insufficient state.
  • "n is 10⁵ and k is 10⁵." O(n·k) = 10¹⁰ is too slow, but the k ≥ n/2 short-circuit makes most of that range trivial; the genuinely hard middle needs the "slope trick" / priority-queue approach in O(n log n). Naming it is enough.
  • "Exactly k transactions, not at most." Initialise the sell array to a negative sentinel instead of 0, so that having completed fewer than t transactions is not silently valid.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 FACTOR OUT
When an inner loop recomputes a maximum that changes by one element, pull out what does not depend on the inner index and carry the rest. That is O(n²k) → O(n·k).
💡 READ IT AS A MACHINE
The rolled solution is 2k states with edges between them. Cooldown adds a state, a fee subtracts on one edge, unlimited drops the counter — six problems, one framework.
⛔ SENTINEL HEADROOM
Initialise buy to INT_MIN/2, not INT_MIN, so buy + price cannot wrap. And guard k ≥ n/2 or a huge k allocates a huge table.
⚠️
Common mistakes on this problem
  • Stopping at the O(n²k) table. It is correct and too slow; the carried maximum is the point of the problem.
  • Omitting the k ≥ n/2 short-circuit, then allocating a table proportional to k when k is enormous.
  • Initialising buy to INT_MIN so that buy[t] + price overflows.
  • Initialising sell to a negative sentinel for the "at most" version, making the answer negative on decreasing prices.
  • Updating the carried best before writing the cell, so the maximum covers the wrong range of j.
  • Inconsistency about whether a transaction is consumed on buy or on sell. Choose, and comment it.
  • Iterating t in the wrong direction in the rolled version, reading an already-updated sell[t-1] from the same day.
  • Forgetting that "at most" permits zero transactions, so the answer has a floor of 0.
  • Assuming the greedy "sum every rise" works for finite k. It is correct only when transactions are unlimited.
  • Rolling the space and then being asked for the actual trades. Reconstruction needs the table or parent pointers.

Interview drill

Warm-up: Present this problem end to end, in about four minutes of speech.

How a strong answer sounds
Let me confirm three things: at most k transactions rather than exactly k, so doing nothing is allowed and the answer is never negative; I can hold at most one share, so I must sell before buying again; and a same-day buy and sell would earn zero, so it does not need special handling. Now the structure: walking the days left to right, on each day I either do nothing, buy, or sell — and which of those is legal depends on whether I am currently holding a share and how many transactions remain. So the state is (day, holding, transactions used), which is n × 2 × (k+1) — about 200,000 states here. The brute-force recursion over those three choices is O(2ⁿ), but memoising on exactly that state makes it O(n·k) time and space, and that is already the optimal complexity. I would write that first in a real round, because it is the version hardest to get wrong. Going bottom-up is where it gets interesting. The natural table is dp[t][i], the best profit using at most t transactions within the first i+1 days, and the recurrence is either dp[t][i−1], or the t-th transaction sells on day i having bought on some earlier day j — which needs a max over all j < i. That is correct and it is O(n²k), too slow. The fix is to notice what the inner max recomputes: it is max over j of (prices[i] − prices[j] + dp[t−1][j]), and prices[i] does not depend on j, so I pull it out and I am left with max over j of (dp[t−1][j] − prices[j]) — a quantity that does not involve i at all. So I carry it in a single variable, update it once per day, and the inner loop vanishes. O(n·k). One ordering detail: I write dp[t][i] using the carried value as it stood over j < i, and only then fold in j = i. Finally, the whole thing rolls to O(k) space as a state machine with buy[t] and sell[t] arrays and six lines of code. And I would add the k ≥ n/2 short-circuit, since a transaction needs two days — beyond that, transactions are effectively unlimited and the answer is the greedy sum of every upward step. That guard is not cosmetic: without it, k = 10⁹ allocates a billion rows.

Deeper: Explain the O(k)-space state machine, and why it generalises to the rest of the stock family.

How a strong answer sounds
I read the solution as a machine with 2k states: for each transaction index t, "holding a share, part-way through transaction t" and "idle, having completed t transactions". Each state stores the best balance — cash in hand, so it goes negative while holding. Each day, every state either stays put or is entered along an edge, and I keep the max. Concretely, buy[t] = max(buy[t], sell[t−1] − price) says I either was already holding, or I was idle after t−1 completed trades and I spend price to buy today. And sell[t] = max(sell[t], buy[t] + price) says I either was already idle after t trades, or I was holding and I sell today for price. The answer is sell[k], and because "at most" allows doing nothing, sell is initialised to 0 while buy starts at a negative sentinel — INT_MIN/2, not INT_MIN, so that buy[t] + price cannot overflow while the sentinel is still in place. Two things make this worth remembering over the table version. First, it is O(k) space and six lines. Second, and more importantly, the entire stock-problem family is this machine with the edges altered: a one-day cooldown adds a third "resting" state per transaction and rewires the buy edge to come from it; a transaction fee subtracts on exactly one edge, buy or sell but never both; "at most two transactions" is this with k = 2, which people usually unroll into four named variables; unlimited transactions is a single buy/sell pair with no counter at all, which collapses to the greedy. And it reduces correctly at the boundary — with k = 1, buy[1] tracks the negated minimum price and sell[1] the best single profit, which is exactly the classic one-transaction solution. I would use that as a free test, along with k = 0, monotonically decreasing prices, and a stress test comparing all my versions against the memoised recursion on small random inputs. If asked to return the actual trades rather than the profit, I would say plainly that the O(k)-space version cannot do it and I would keep the full table with parent pointers.

🧠 Key takeaways

  • Define the state as everything the decision depends on — here (day, holding, transactions) — and the transition follows.
  • Memoise the recursion first: it reaches optimal complexity with the least chance of error, and banks a correct answer.
  • The natural bottom-up table is O(n²k). Factor out what does not depend on the inner index and carry the rest.
  • Read a rolled DP as a state machine; the whole stock family is the same machine with different edges.
  • Check the boundary reductions (k = 1, k = ∞) — they are free tests of the general solution.

Check your understanding

What is the correct DP state for this problem?

The decision on each day depends on exactly those three things. Note that the accumulated profit is not state — it is the value being computed, and putting it in the key would make every state unique.

The natural bottom-up recurrence is O(n²k). Where is the redundancy?

Because prices[i] does not depend on j, it factors out and the remaining maximum can be carried in one variable. "Factor out what does not depend on the inner index" is the transferable move.

Why short-circuit when k ≥ n/2?

The unlimited case has a linear greedy answer: sum every upward step. The memory argument is the one that makes this mandatory rather than optional.

In the rolled version, why initialise buy to INT_MIN/2 rather than INT_MIN?

Classic sentinel-arithmetic bug (Chapter 53). INT_MIN + price wraps to a large positive value, which then looks like an excellent profit and propagates.

What makes the state-machine formulation worth remembering over the table?

Same O(n·k) time, but O(k) space and six lines — and, more usefully, one framework that covers six problems instead of six memorised solutions.
