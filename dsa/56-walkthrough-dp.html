Walkthrough: A Hard DP Problem

This is the last chapter. We take the method from Chapter 38 and use it under pressure on Best Time to Buy and Sell Stock IV: make at most k trades and earn the most profit. We picked this problem because the first correct recurrence is too slow. To fix it, you must spot a maximum that is being worked out again and again. Removing that repeat is the most reusable DP speed-up there is. We will go from brute force to O(n·k), then down to O(k) space, and finish with the follow-up questions.

  • Define the DP state (what you need to know at each step) so clearly that the transition (how one state leads to the next) writes itself
  • Derive the obvious O(n²k) recurrence, then find the work it repeats
  • Cut it to O(n·k) by keeping a running best in one variable
  • Shrink the table to O(k) space, and handle the unlimited-trades case
  • Rebuild the whole thing as a state machine and compare the two views
📚
What you need before this chapter
  • The five-step DP method: state, transition, base case, order, answer. Chapter 38 teaches it, and this chapter follows it step by step.
  • Memoised recursion: caching a recursive function's answer for each set of arguments. Chapter 11 covers recursion; Chapter 38 adds the cache.
  • Carrying a running best in one variable: the "lowest price so far" and maximum-subarray ideas from Chapter 39. The key speed-up here is that same trick, used inside a bigger table.
  • How big an int is: that INT_MIN is about −2.1 × 10⁹ and going past it wraps around. P2: C++ Types, Operators & Overflow has the basics; Chapter 53 shows the bug.
📋
The problem

Best Time to Buy and Sell Stock IV. You get an array prices, where prices[i] is a stock's price on day i, and an integer k. Find the most profit you can make with at most k transactions. A transaction is one buy followed later by one sell. You may not hold more than one share at a time — you must sell before you buy again. Constraints: 1 ≤ prices.length ≤ 1000, 0 ≤ k ≤ 100, 0 ≤ prices[i] ≤ 1000.

Stage 1 — Clarify, then find the sub-structure

1
The questions that change the code

Three questions are worth asking, and only three.

"At most k, or exactly k?" — At most. So doing nothing is always allowed, and the answer is never negative.
"Can I hold more than one share?" — No. That is what makes the problem a day-by-day sequence rather than a knapsack.
"Can I buy and sell on the same day?" — It would earn zero, so it does not matter. But confirming it means the recurrence does not need to rule it out.

Now the sub-structure (how the big problem breaks into smaller ones). Walk through the days from left to right. On each day, exactly one of three things happens: I do nothing, I buy, or I sell. Whether I may buy depends on whether I hold a share right now, and on how many transactions I have left. So the choice on day i depends on two things besides i itself. That observation is the state.

Two sanity checks before going further. With k = 1, this is the classic one-trade problem: track the lowest price so far. With k = ∞, it is the greedy "add up every price rise". A correct general solution must give the same answers in both cases, so you get two free tests.

One example to carry through the chapter. Take prices = [3, 2, 6, 5, 0, 3].

  • With k = 1: the lowest price before the best sell is 2 (day 1), and selling at 6 (day 2) earns 4. Buying at 0 and selling at 3 earns only 3.
  • With unlimited trades: add every rise from one day to the next. The rises are 2→6 (+4) and 0→3 (+3), so the total is 7.
  • With k = 2: buy at 2, sell at 6, buy at 0, sell at 3. That is also 7, because there are only two rising stretches to use. A third transaction would have nothing left to earn.

Work these out by hand before writing any code. They give you three known answers to check each version against.

Stage 2 — The brute force, and its complexity

2
Recursion over three choices
// solve(i, holding, remaining) = the best profit obtainable from day i onward.
int solve(int i,bool holding,int remaining,vector<int> &prices){
	if(i==prices.size() or remaining==0)return 0;

	int skip=solve(i+1,holding,remaining,prices);

	if(holding){
		// sell today: gain today's price, one transaction consumed
		int sell=prices[i]+solve(i+1,false,remaining-1,prices);

		return max(skip,sell);
	}

	// buy today: pay today's price
	int buy=-prices[i]+solve(i+1,true,remaining,prices);

	return max(skip,buy);
}

How to read it. The function returns the extra money you can still make from day i onward, so a buy subtracts today's price and a sell adds it. The base case returns 0 when the days run out or no transactions remain. If you still hold a share on the last day, the money you paid for it is simply lost. That path scores lower, so max never picks it, and the code needs no special rule for it.

Two branches per day gives O(2ⁿ) — hopeless at n = 1000. But look at the state. (i, holding, remaining) can only take n × 2 × (k+1) different values — about 200,000 here. The recursion visits the same ones over and over. That is exactly what "overlapping subproblems" means. So memoising (caching the answer for each of those three-value combinations) gives O(n·k) states with O(1) work each.

Worth saying out loud: this memoised version already has the best possible complexity. Everything after this rebuilds it bottom-up (filling a table from small cases to large). We do that because the obvious bottom-up version hides a trap. It is also why I would present this top-down version first in a real interview. It is the easiest to get right, and it puts a correct answer on the board.

🔍
Deciding the transaction counter's meaning

One small choice has real effects: do you use up a transaction when you buy, or when you sell? Either works, as long as you are consistent. Counting it on the sell is better. Then a buy with no matching sell is never counted, so the "at most k" limit only applies to finished round trips, automatically. If you count on the buy, you must make sure an unsold share does not waste a transaction that could have made money. Write down which rule you chose, in a comment. Half the wrong answers on this problem come from mixing the two.

Stage 3 — The bottom-up trap

3
The natural table, and why it is O(n²k)

The textbook bottom-up table is indexed by transaction count and day: dp[t][i] = the best profit using at most t transactions within the first i+1 days. There are two options. Either no transaction ends on day i, which gives dp[t][i-1]. Or your t-th transaction sells on day i, after buying on some earlier day j:

dp[t][i]=max(dp[t][i-1],
            max over j<i of (prices[i]-prices[j]+dp[t-1][j]))

That is correct, and it is O(n²k): for every cell, an inner loop scans all earlier days. At n = 1000 that is about 10⁶ steps for each value of t, or 10⁸ in total when k = 100 — far too slow. So name the repeated work. For each new i, the inner loop recomputes a maximum over all j < i. But it already computed nearly the same maximum for i-1 — only one new candidate has been added. That is a running total being recomputed from scratch. It is the same pattern as Chapter 6 and Chapter 39, and one variable carried along the loop removes it.

Why pulling prices[i] out is allowed. Adding the same number to every candidate does not change which candidate is biggest. So max(p + a, p + b, p + c) equals p + max(a, b, c). Here p is prices[i], which is the same for every j, so it can move outside the max. What stays inside, dp[t-1][j] − prices[j], has a plain meaning: the best cash balance you can have while holding a share you bought on day j, after t−1 finished trades.

A trace on [3, 2, 6, 5, 0, 3] with k = 2. Row t = 1 works out to [0, 0, 4, 4, 4, 4]: one trade earns at most 4. Here is row t = 2, which reads row 1:

On day 5, selling at 3 turns that into 7, which matches the answer from Stage 1. Each cell cost O(1) work instead of a scan over every earlier day.

the fix — factor prices[i] out and carry the bestO(n·k)O(n·k)
// The inner max is  max over j<i of (prices[i] - prices[j] + dp[t-1][j]).
// prices[i] does not depend on j, so pull it out:
//     prices[i] + max over j<i of (dp[t-1][j] - prices[j])
// That inner quantity does not involve i at all — so it can be carried in a
// single variable, updated once per day. The inner loop disappears.
int maxProfit(int k,vector<int> &prices){
	int n=prices.size();

	if(n<2 or k==0)return 0;

	// A transaction needs two days, so more than n/2 transactions is the same
	// as unlimited — and the unlimited case has a linear greedy answer.
	if(k>=n/2)return unlimited(prices);

	vector<vector<int>> dp(k+1,vector<int>(n,0));

	for(int t=1;t<=k;t++){
		// best = max over j seen so far of (dp[t-1][j] - prices[j])
		// Initialised at j = 0: dp[t-1][0] is 0, so this is -prices[0].
		int best=-prices[0];

		for(int i=1;i<n;i++){
			dp[t][i]=max(dp[t][i-1],prices[i]+best);

			best=max(best,dp[t-1][i]-prices[i]);
		}
	}

	return dp[k][n-1];
}

// Unlimited transactions: take every upward step. Any profitable run
// p[a] < p[b] decomposes into consecutive rises summing to the same total,
// so buying every dip and selling every peak is optimal.
int unlimited(vector<int> &prices){
	int ans=0;

	for(int i=1;i<prices.size();i++){
		if(prices[i]>prices[i-1])ans+=prices[i]-prices[i-1];
	}

	return ans;
}
The order of the two highlighted lines matters. It is the trickiest point here. dp[t][i] is computed using best as it was over j < i. Only then is day j = i added into best. Swapping them would allow buying and selling on the same day. That is harmless here, since it earns zero, but the habit is what matters: the carried variable must cover exactly the range the recurrence says it does. Also, the k ≥ n/2 early exit is not just for neatness. Without it, k = 10⁹ would create a table with 10⁹ rows.

Why n/2 is the cut-off. Every profitable trade needs a rising stretch: a day where you buy and a later day where the price is higher. Separate rising stretches cannot share a rise, and each one takes at least two days, so n days hold at most n/2 of them. Our six-day example has only two. Once k reaches that limit, the limit can never bite, and the unlimited greedy gives the same answer in O(n).

Why "add every rise" is right when trades are unlimited. Buying at 2 and selling at 6 earns 4. So does buying at 2, selling at 6 the next day, and so on through any chain of consecutive daily rises, because the in-between prices cancel out: (b − a) + (c − b) = c − a. So the sum of all daily rises is the most any set of trades can collect, and taking each rise on its own collects exactly that.

Stage 5 — Space, and the state-machine rederivation

Rolling to O(k) space
// Row t only ever reads row t-1 and its own previous cell. But the carried
// `best` per row makes it neater to flip the loops: iterate DAYS outside and
// TRANSACTIONS inside, keeping one buy/sell value per transaction count.
int maxProfit(int k,vector<int> &prices){
	int n=prices.size();

	if(n<2 or k==0)return 0;
	if(k>=n/2)return unlimited(prices);

	// buy[t]  = best balance while HOLDING, having begun transaction t
	// sell[t] = best balance after COMPLETING transaction t
	vector<int> buy(k+1,INT_MIN/2);
	vector<int> sell(k+1,0);

	for(auto &price:prices){
		for(int t=1;t<=k;t++){
			buy[t]=max(buy[t],sell[t-1]-price);
			sell[t]=max(sell[t],buy[t]+price);
		}
	}

	return sell[k];
}

Six lines, O(n·k) time, O(k) space. INT_MIN/2 instead of INT_MIN is on purpose. buy[t] starts as a placeholder meaning "impossible". Here, with non-negative prices, INT_MIN+price would actually be safe. But the moment a variant subtracts from that placeholder — a transaction fee (buy[t]+price-fee), say — INT_MIN minus anything wraps around to a huge positive number. Halving it leaves headroom so the placeholder survives that arithmetic (Chapter 53, bug 2). Updating buy[t] and then using it right away in sell[t] allows buying and selling on the same day. That earns zero, so it is harmless. If the problem banned it, you would compute both from the previous day's values.

Why this is the same thing

Read the two lines as a state machine: a set of situations you can be in, with arrows (edges) for how you move between them. There are 2k states: "holding a share, part-way through transaction t" and "not holding, having finished t". Each day you either move along an edge or stay where you are. max keeps the best cash balance for each state.

buy[t] = max(buy[t], sell[t-1] − price) says: either I was already holding, or I had finished t−1 trades and I buy today. sell[t] = max(sell[t], buy[t] + price) says: either I had already finished t trades, or I was holding and I sell today.

This is the version to remember. Every stock problem in the family is the same machine with the edges changed. A cooldown adds a "resting" state. A transaction fee is subtracted on one edge. At most 2 transactions is this with k = 2, written out as four named variables. Unlimited is one buy state and one sell state, with no counter.

It also gives the right answer at the edge cases. With k = 1, buy[1] tracks minus the lowest price so far, and sell[1] tracks the best single profit — exactly the classic solution. That is the free test from Stage 1, passed.

Watching the machine run. With k = 1 on [3, 2, 6, 5, 0, 3], there is one buy value and one sell value, updated each day:

The tests to volunteer
  • k = 0 or fewer than two prices → 0. This check must come before you create any table.
  • Prices that only go down → 0. "At most k" means doing nothing is allowed, so the answer is never negative.
  • k = 1 → must equal the classic single-transaction answer.
  • Huge k, say 10⁹ → the early exit must kick in, or you create a table with 10⁹ rows.
  • All prices equal → 0, and no negative profit from a same-day round trip.
  • k larger than the number of profitable price rises → the extra transactions must simply go unused.
  • Stress test — compare the O(k)-space version against the memoised recursion on random arrays of length 6–8, with k from 0 to 4. Every version in the table above should agree. That is the cheapest way to confirm each step of the derivation was right.
🔮
The follow-ups
  • "Add a one-day cooldown after selling." Add a third state per transaction: rest[t]. Selling moves you into rest. Buying may only come from rest or from an earlier idle state. The machine gains one state; the loop structure stays the same.
  • "Add a fee per transaction." Subtract it on one edge — either buy[t] = max(buy[t], sell[t-1] − price − fee) or on the sell. Pick one, and only one.
  • "Return the actual buy and sell days." Record where each state came from (a parent pointer), or keep the full dp table and walk back through it. This is the usual price of saving space (Chapters 41 and 42).
  • "You may hold up to m shares at once." The state gains a new dimension for how many shares you hold, giving O(n·k·m). A good moment to say: when the state is missing information, the standard fix is to add a dimension.
  • "n is 10⁵ and k is 10⁵." O(n·k) = 10¹⁰ is too slow. The k ≥ n/2 early exit makes most of that range easy. The truly hard middle needs the "slope trick" / priority-queue approach in O(n log n). Just naming it is enough.
  • "Exactly k transactions, not at most." Start the sell array at a very negative "impossible" value instead of 0. Then finishing fewer than t transactions does not quietly count as valid.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 FACTOR OUT
When an inner loop recomputes a maximum that changes by one element, pull out what does not depend on the inner index and carry the rest. That is O(n²k) → O(n·k).
💡 READ IT AS A MACHINE
The rolled solution is 2k states with edges between them. Cooldown adds a state, a fee subtracts on one edge, unlimited drops the counter — six problems, one framework.
⛔ SENTINEL HEADROOM
Initialise buy to INT_MIN/2, not INT_MIN, so arithmetic on the placeholder — especially subtracting a fee — cannot wrap. And guard k ≥ n/2 or a huge k allocates a huge table.
⚠️
Common mistakes on this problem
  • Stopping at the O(n²k) table. It is correct but too slow. The carried maximum is the whole point of the problem.
  • Leaving out the k ≥ n/2 early exit, then creating a table as big as k when k is enormous.
  • Initialising buy to INT_MIN so that buy[t] + price overflows.
  • Starting sell at a negative "impossible" value in the "at most" version. That makes the answer negative when prices only go down.
  • Updating the carried best before writing the cell, so the maximum covers the wrong range of j.
  • Mixing up whether a transaction is used up on the buy or on the sell. Choose one, and say so in a comment.
  • Looping t in the wrong direction in the O(k)-space version, so you read a sell[t-1] that was already updated today.
  • Forgetting that "at most" allows zero transactions, so the answer can never go below 0.
  • Assuming the greedy "add up every rise" works for a limited k. It is only correct when transactions are unlimited.
  • Shrinking to O(k) space and then being asked for the actual trades. Recovering the trades needs the full table or parent pointers.

Interview drill

Warm-up: Present this problem end to end, in about four minutes of speech.

How a strong answer sounds
Let me confirm three things. First, it is at most k transactions, not exactly k — so doing nothing is allowed and the answer is never negative. Second, I can hold at most one share, so I must sell before buying again. Third, a same-day buy and sell would earn zero, so it needs no special handling. Now the structure. Walking the days left to right, each day I either do nothing, buy, or sell. Which of those is allowed depends on whether I am currently holding a share, and how many transactions remain. So the state is (day, holding, transactions used). That is n × 2 × (k+1) — about 200,000 states here. The brute-force recursion over the three choices is O(2ⁿ). But memoising on exactly that state makes it O(n·k) time and space, which is already the best possible. I would write that first in a real interview, because it is the hardest version to get wrong. Going bottom-up is where it gets interesting. The obvious table is dp[t][i]: the best profit using at most t transactions within the first i+1 days. The recurrence is either dp[t][i−1], or the t-th transaction sells on day i after buying on some earlier day j — which needs a max over all j < i. That is correct, but it is O(n²k) — too slow. The fix is to look at what the inner max recomputes. It is max over j of (prices[i] − prices[j] + dp[t−1][j]). prices[i] does not depend on j, so I pull it out. What is left is max over j of (dp[t−1][j] − prices[j]), which does not involve i at all. So I keep it in a single variable, update it once per day, and the inner loop disappears. That is O(n·k). One ordering detail: I write dp[t][i] using the carried value as it was over j < i, and only then add in j = i. Finally, the whole thing shrinks to O(k) space as a state machine with buy[t] and sell[t] arrays — six lines of code. And I would add the k ≥ n/2 early exit. A transaction needs two days, so beyond that, transactions are effectively unlimited and the answer is the greedy sum of every price rise. That check is not just for show: without it, k = 10⁹ creates a billion rows.

Deeper: Explain the O(k)-space state machine, and why it generalises to the rest of the stock family.

How a strong answer sounds
I read the solution as a machine with 2k states. For each transaction number t, there are two: "holding a share, part-way through transaction t" and "not holding, having finished t transactions". Each state stores the best balance — cash in hand, so it goes negative while you hold a share. Each day, every state either stays as it is or is entered along an edge, and I keep the max. Concretely, buy[t] = max(buy[t], sell[t−1] − price) says: either I was already holding, or I had finished t−1 trades and I pay the price to buy today. And sell[t] = max(sell[t], buy[t] + price) says: either I had already finished t trades, or I was holding and I sell today for the price. The answer is sell[k]. Because "at most" allows doing nothing, sell starts at 0. buy starts at a very negative "impossible" value — INT_MIN/2, not INT_MIN, so that buy[t] + price cannot overflow while that placeholder is still there. Two things make this worth remembering over the table version. First, it is O(k) space and six lines. Second, and more important, every stock problem in the family is this machine with the edges changed. A one-day cooldown adds a third "resting" state per transaction, and the buy edge now comes from it. A transaction fee is subtracted on exactly one edge — buy or sell, never both. "At most two transactions" is this with k = 2, which people usually write out as four named variables. Unlimited transactions is a single buy/sell pair with no counter, which turns into the greedy. It also gives the right answer at the edge — with k = 1, buy[1] tracks minus the lowest price and sell[1] the best single profit, exactly the classic one-trade solution. I would use that as a free test, along with k = 0, prices that only go down, and a stress test comparing all my versions against the memoised recursion on small random inputs. If asked to return the actual trades instead of the profit, I would say plainly that the O(k)-space version cannot do it, and I would keep the full table with parent pointers.

🧠 Key takeaways

  • Make the state everything the decision depends on — here (day, holding, transactions) — and the transition follows.
  • Memoise the recursion first. It reaches the best complexity with the least chance of error, and gets a correct answer on the board.
  • The obvious bottom-up table is O(n²k). Pull out what does not depend on the inner loop's index, and carry the rest in a variable.
  • Read a space-saving DP as a state machine. The whole stock family is the same machine with different edges.
  • Check the edge cases (k = 1, k = ∞) against their known answers — they are free tests of the general solution.

Check your understanding

What is the correct DP state for this problem?

Each day's decision depends on exactly those three things. Note that the profit so far is not part of the state — it is the value being computed. Putting it in the key would make every state unique, and caching would stop helping.

The natural bottom-up recurrence is O(n²k). Where is the redundancy?

Because prices[i] does not depend on j, you can pull it out. The remaining maximum can then be carried in one variable. "Pull out what does not depend on the inner loop's index" is the move you can reuse elsewhere.

Why short-circuit when k ≥ n/2?

The unlimited case has a simple O(n) greedy answer: add up every price rise. The memory problem is what makes this check a must, not a nice-to-have.

In the rolled version, why initialise buy to INT_MIN/2 rather than INT_MIN?

A classic bug with "impossible" placeholder values (Chapter 53). Adding a non-negative price to INT_MIN is actually safe. The danger is subtracting: in a fee variant, INT_MIN + price - fee goes below the smallest int and wraps around to a huge positive value. That looks like a great profit and spreads through the table. INT_MIN/2 leaves room for that arithmetic.

What makes the state-machine formulation worth remembering over the table?

Same O(n·k) time, but O(k) space and six lines. More usefully, it is one framework that covers six problems, instead of six solutions to memorise.
