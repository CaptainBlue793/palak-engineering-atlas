Bitmask DP

Some problems need to remember which items have been used, not just how many. A set of up to about twenty items fits in a single integer, and "a set" becomes "a number you can index a DP array with". This is the technique that turns 2ⁿ·n! into 2ⁿ·n² — still exponential, but the difference between 20 cities being impossible and being instant.

  • Represent a subset as an integer and manipulate it fluently
  • Recognise the constraint signature: n ≤ 20, "each exactly once", permutations
  • Write the assignment DP and see why one index is redundant
  • Derive Held-Karp for the travelling salesman problem
  • Enumerate submasks in O(3ⁿ) and know when you need it

The constraint signature

Bitmask DP announces itself. Before deriving anything, check the bounds — n ≤ 20 or so, together with a requirement that every item is used exactly once, or that the order of a permutation matters. Those small bounds are not a courtesy; they are the problem telling you that an exponential number of states is expected.

🔢
Memory is usually the binding constraint, not time

A dp[1<<20][20] table of int is 20·2²⁰·4 bytes ≈ 84 MB — over the limit on most judges. Three standard escapes: store int rather than long long and cap with a large sentinel instead of LLONG_MAX; drop to dp[1<<n] alone when the last element is recoverable from the mask (see the assignment DP below); or iterate masks in increasing order and keep only what is still needed. Always multiply the table size out before writing it — 2ⁿ grows past a gigabyte faster than intuition expects.

Two precedence traps that bite in real code. 1<<i binds looser than comparison, so mask & 1<<i == 0 parses as mask & (1 << (i==0)) — always parenthesise. And 1<<31 overflows a signed int; for N above 30 write 1LL<<i. Chapter 47 covers the bit tricks themselves in depth; here they are just the alphabet.

The assignment problem

N people, N tasks, a cost matrix. Each person does exactly one task. The permutation-brute-force is N!, but notice: if you assign people in a fixed order — person 0 first, then person 1 — then the number of people already assigned is exactly the number of set bits in the mask. That makes one index redundant, and the state collapses to the mask alone.

minimum-cost assignmentO(2ⁿ·n)O(2ⁿ)
// dp[mask] = the minimum cost of assigning tasks in `mask` to the first
//            popcount(mask) people.
// The person index is NOT stored — it is derivable, which is the whole trick.
int minCostAssignment(vector<vector<int>> &cost){
	int N=cost.size();
	int full=(1<<N)-1;
	vector<int> dp(1<<N,INT_MAX);

	dp[0]=0;                              // nobody assigned, nothing spent

	for(int mask=0;mask<=full;mask++){
		if(dp[mask]==INT_MAX)continue;      // unreachable state, skip

		int person=__builtin_popcount(mask);   // derived, not stored

		if(person==N)continue;               // everyone already has a task

		for(int task=0;task<N;task++){
			if((mask>>task)&1)continue;        // task already taken

			int next=mask|(1<<task);

			dp[next]=min(dp[next],dp[mask]+cost[person][task]);
		}
	}

	return dp[full];
}
This is a forward, "push" DP — each state improves its successors rather than pulling from its predecessors. Both directions work; push is natural here because the successor set is easy to enumerate. Two details worth copying: skip unreachable states (dp[mask]==INT_MAX) so you never add to a sentinel and overflow, and derive person from popcount rather than adding a dimension — that alone divides the memory by N. The cost is O(2ⁿ·n) against N! for brute force: at N = 15, seven million operations versus 1.3 trillion.
✍️
My convention: N for the problem's item count, sentinel-guard before every relax

I keep N as the number of items the problem is about — cities, people, nodes — and lower-case n for an incidental local length, exactly as in the graph chapters. And the line if(dp[mask]==INT_MAX)continue; is the same discipline as if(dist[node]==INT_MAX)continue; in Bellman-Ford: never arithmetic on a sentinel. INT_MAX + cost wraps to a large negative number, which then looks like an excellent answer and propagates everywhere. It is a silent wrong answer rather than a crash, which is why the guard is a habit and not a judgement call.

Held-Karp: the travelling salesman problem

Now the case where the mask is not enough. Visit every city exactly once and return home, minimising distance. Here the next step depends on where you currently stand, not only on which cities are done — so the state needs a second index.

TSP — Held-KarpO(2ⁿ·n²)O(2ⁿ·n)
// dp[mask][i] = the cheapest way to start at city 0, visit exactly the cities
//               in `mask`, and be standing at city i right now.
// Here the mask alone is NOT enough state: the next hop's cost depends on where
// we currently stand, so the current city must be part of the state.
int tsp(vector<vector<int>> &dist){
	int N=dist.size();
	int full=(1<<N)-1;
	vector<vector<int>> dp(1<<N,vector<int>(N,INT_MAX));

	dp[1][0]=0;                           // start at home, only home visited

	for(int mask=1;mask<=full;mask++){
		if(!(mask&1))continue;              // home is always visited

		for(int at=0;at<N;at++){
			if(!((mask>>at)&1))continue;      // cannot stand outside the mask
			if(dp[mask][at]==INT_MAX)continue;  // unreachable

			for(int next=0;next<N;next++){
				if((mask>>next)&1)continue;      // already visited

				int nextMask=mask|(1<<next);

				dp[nextMask][next]=min(dp[nextMask][next],
				                       dp[mask][at]+dist[at][next]);
			}
		}
	}

	// close the tour: from every possible last city, step back home
	int ans=INT_MAX;

	for(int at=1;at<N;at++){
		if(dp[full][at]==INT_MAX)continue;

		ans=min(ans,dp[full][at]+dist[at][0]);
	}

	return ans;
}
Three loops: mask, current city, next city — hence 2ⁿ·n². The subtlety people miss is the closing step: dp[full][at] is a path that has visited everything and stopped at at, which is not yet a tour. You must add dist[at][0] and take the minimum over all at. Returning dp[full][0] instead is wrong — that state is unreachable for N > 1, since city 0 cannot be visited twice under this state definition. Held-Karp also proves the point of the chapter: TSP is NP-hard, and this does not change that, but it turns O(n!) into O(2ⁿ·n²), which is the difference between 15 cities being hopeless and 20 being routine. For a path rather than a cycle, simply skip the closing step and take min over dp[full][at].
🧩
Does the mask need a companion index?

The deciding question: does the cost of the next choice depend on which item was taken last?

  • No → dp[mask] alone. Assignment, minimum sticks/partitions, "can this set be split into k equal groups". The position is derivable from popcount.
  • Yes → dp[mask][last]. TSP, shortest superstring, arranging items where adjacency costs something, counting Hamiltonian paths.
  • The mask means "the previous row" → broken-profile DP. Tiling a grid column by column, where the mask records which cells of the boundary stick out. State is dp[column][mask].

Getting this right is worth a factor of N in both time and memory, so it is worth thirty seconds of thought before you allocate.

Submask enumeration

Some problems partition a set into groups, and the transition needs every subset of the current mask rather than a single element. Naively that is 2ⁿ·2ⁿ = 4ⁿ. The idiom below is O(3ⁿ), which is a very large saving.

minimum groups — iterate the submasks of each maskO(3ⁿ)O(2ⁿ)
// The classic loop. `sub` walks every non-empty subset of `mask`, in
// decreasing order, and never touches a bit outside mask.
// Subtracting 1 borrows through the zero bits; the &mask clears the borrow.
for(int sub=mask;sub>0;sub=(sub-1)&mask){
	int rest=mask^sub;                 // the complement WITHIN mask

	// combine an answer for `sub` with an answer for `rest`
}

// dp[mask] = the fewest groups needed to cover exactly the items in mask,
//            where ok[sub] says a single group may contain exactly `sub`.
int minGroups(int N,vector<bool> &ok){
	int full=(1<<N)-1;
	vector<int> dp(1<<N,INT_MAX);

	dp[0]=0;

	for(int mask=1;mask<=full;mask++){
		for(int sub=mask;sub>0;sub=(sub-1)&mask){
			if(!ok[sub])continue;
			if(dp[mask^sub]==INT_MAX)continue;

			dp[mask]=min(dp[mask],1+dp[mask^sub]);
		}
	}

	return dp[full];
}
Why O(3ⁿ)? Each of the n bits is independently in sub, in rest, or outside mask — three choices per bit, so 3ⁿ (mask, submask) pairs in total. At n = 16 that is 43 million, fine; at n = 20 it is 3.5 billion, too slow, so submask enumeration caps out several bits earlier than plain bitmask DP. A common fix for over-counting in partition problems: fix the lowest set bit of mask to always belong to sub, which makes each partition appear once instead of once per ordering of its groups.
🧮
Broken-profile DP, in one paragraph

Tiling problems ("count the ways to fill a 2×n or m×n board with dominoes") use the mask differently: the mask describes a boundary, not a set of used items. Process the board column by column; dp[col][mask] is the number of ways to fill everything before col such that mask records which cells of column col are already covered by a tile sticking out from the left. The transition enumerates the legal ways to place tiles in column col, producing the next column's mask. It is O(n·2ᵐ·2ᵐ) in the crude form, so keep m as the smaller dimension — for a 2×10⁵ board that is trivial, and for a 10×10 board it is fine. This is the bridge from "mask as a set" to "mask as a shape", and it is the standard technique for grid-tiling counts.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 n ≤ 20 IS THE HINT
A tiny bound plus "each item exactly once" is the bitmask signature. The bound is not a courtesy; it is telling you an exponential state is expected.
💡 DERIVE, DO NOT STORE
If items are taken in a fixed order, the position is popcount(mask) — no second dimension. That alone divides the memory by n.
⛔ PARENTHESISE
mask & 1<<i == 0 parses as mask & (1==0) and is always false. Always parenthesise, and never do arithmetic on INT_MAX.
⚠️
Common mistakes
  • Arithmetic on INT_MAX. It wraps negative and looks like a great answer. Guard with if(dp[...]==INT_MAX)continue;.
  • Missing parentheses: mask & 1<<i == 0 parses as mask & (1 << (i==0)).
  • 1<<i for i ≥ 31 overflows signed int; use 1LL<<i.
  • Returning dp[full][0] from TSP. Close the tour with min over at of dp[full][at]+dist[at][0].
  • Standing on a city outside the mask. Guard if(!((mask>>at)&1))continue;, or you build tours through unvisited cities.
  • Storing an index that popcount already gives you — an unnecessary factor of N in memory.
  • Allocating dp[1<<20][20] of long long — 168 MB. Multiply it out first.
  • Iterating masks in the wrong direction for a pull-style DP; a mask must be processed after every mask it reads.
  • Submask loop written sub = sub-1 & mask without the parentheses, or starting at sub=mask-1 and losing the full-mask case.
  • Over-counting partitions because the groups were generated in every order; pin the lowest set bit to one side.
  • Reaching for bitmask DP when n is 10⁵. Re-read the constraints — a different technique is intended.

Interview drill

Warm-up: N people, N tasks, a cost matrix, N ≤ 15. Minimise total cost.

How a strong answer sounds
The bound N ≤ 15 is the giveaway — that is far too small for anything polynomial to be needed and far too large for 15! brute force, so an exponential-in-N DP with a subset state is intended. I represent the set of already-assigned tasks as a bitmask and define dp[mask] as the minimum cost of assigning exactly the tasks in mask. The key economy is that I do not need to store which person we are up to: if people are assigned in a fixed order, the number already assigned is exactly popcount(mask), so the person index is derivable. That saves a factor of N in memory and in code. The transition, written as a push, is: for each reachable mask, let person = popcount(mask), and for each task not yet in mask, relax dp[mask | 1<<task] with dp[mask] + cost[person][task]. Answer is dp[(1<<N)−1]. That is O(2ᴺ·N) time — about half a million operations at N = 15 — and O(2ᴺ) memory. One line I would not omit is the guard that skips unreachable masks, because adding a cost to INT_MAX wraps to a negative number and silently poisons the table; that is a wrong answer rather than a crash, so it is worth being disciplined about. If asked to scale beyond about 20, I would say the exact answer needs the Hungarian algorithm, which solves assignment in O(N³) polynomial time — worth naming, because assignment is the one problem in this family that is polynomial, unlike TSP.

Deeper: TSP with N ≤ 18. Derive the DP, state the complexity, and say what you would do at N = 100.

How a strong answer sounds
I define dp[mask][i] as the cheapest way to start at city 0, visit exactly the cities in mask, and currently be standing at city i. Unlike the assignment problem, the mask alone is not sufficient state here, because the cost of the next hop depends on where I am standing right now — so the current city has to be part of the state. Base case dp[1][0] = 0: only home visited, standing at home. The transition, pushing forward: from a reachable dp[mask][at], for every city next not in mask, relax dp[mask | 1<<next][next] with dp[mask][at] + dist[at][next]. The step people get wrong is the finish: dp[full][at] is a Hamiltonian path, not a tour, so the answer is the minimum over all at of dp[full][at] + dist[at][0]. Returning dp[full][0] is wrong because that state is unreachable — city 0 cannot be visited twice under this definition. Three nested loops give O(2ᴺ·N²) time and O(2ᴺ·N) memory; at N = 18, that is about 85 million operations and a 2ᴺ·N table of ints, roughly 19 MB, which fits. I would check that memory arithmetic out loud, because at N = 20 the same table is 84 MB and typically over the limit. At N = 100 exact Held-Karp is hopeless — 2¹⁰⁰ states — and TSP is NP-hard, so I would switch goals: for a guaranteed approximation on a metric instance, the minimum-spanning-tree double-walk gives a 2-approximation and Christofides gives 1.5; in practice, nearest-neighbour construction followed by 2-opt or Or-opt local search, or Lin-Kernighan, gets within a couple of percent on thousands of cities. The important thing is to say plainly that the exact answer is out of reach and to name what replaces it, rather than pretending a DP will stretch that far.

🧠 Key takeaways

  • n ≤ 20 with "each item exactly once" or "order matters" is the bitmask-DP signature — the small bound is the hint.
  • Ask whether the mask needs a companion index: it does when the next cost depends on which item was last.
  • Derive what you can from the mask (popcount gives the position) instead of storing an extra dimension.
  • Never do arithmetic on a sentinel; guard unreachable states before every relaxation.
  • Submask enumeration with sub=(sub-1)&mask is O(3ⁿ) and caps out several bits earlier than plain 2ⁿ DP.

Check your understanding

A problem says "n ≤ 18, assign each worker exactly one job". What does that suggest?

The bound is the hint: too small to need anything polynomial, too large for n! brute force. (Assignment specifically also has a polynomial solution — the Hungarian algorithm — which is worth naming if the bound grows.)

In the assignment DP, why is dp[mask] enough, without a second index for the person?

Deriving instead of storing saves a factor of N in memory. The contrast is TSP, where the current city genuinely is not derivable from the mask and must be stored.

Why does TSP need dp[mask][i] rather than dp[mask]?

That is the deciding question for every bitmask problem: does the next choice's cost depend on the last item taken? Yes here, no in assignment.

After filling the Held-Karp table, what is the answer?

dp[full][at] has visited everything but stopped at at. dp[full][0] is unreachable for N > 1 because city 0 cannot be visited twice. (Option 3 is right for a Hamiltonian path rather than a cycle.)

The loop for(int sub=mask; sub>0; sub=(sub-1)&mask) costs how much over all masks?

Three independent choices per bit gives 3ⁿ pairs. Practically that means submask DP caps out around n = 16 rather than n = 20, which is worth knowing before you commit to it.
