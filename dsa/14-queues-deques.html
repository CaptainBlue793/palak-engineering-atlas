Queues, Deques & Monotonic Deques

A queue is a line at a shop: you join at the back and you are served from the front. It is the structure behind BFS, and BFS is behind half of the course from Chapter 25 onward, so getting it right matters more than its simplicity suggests. A deque (say "deck") lets you add and remove at both ends. The monotonic deque built on it solves sliding-window maximum in O(n), which a heap cannot do. This chapter also covers the circular-buffer version, because “design a queue” is a real interview question, and the wrap-around arithmetic is where people slip.

The queue, and the circular buffer

Why queues matter: whenever things must be handled in the order they arrived, you need a queue. Print jobs, web requests waiting for a server, messages between services, and, most importantly for this course, the “visit nearest first” order of breadth-first search (BFS). In C++, std::queue gives you push(x) (join at the back), pop() (remove the front, returns nothing), front(), back(), empty() and size().

A queue is FIFO (first in, first out): push at the back, pop from the front, both O(1). Building one on a fixed-size array is easy to get almost right. If you simply move a head index forward on every pop, the slots before it are wasted forever, and the array “runs out” even though it is mostly empty. A circular buffer fixes this by reusing the array, wrapping back to index 0 when it runs off the end, like a clock face. The wrap is done with %: in a buffer of capacity 4, the slot after index 3 is (3 + 1) % 4 = 0. The trap: a head index and a tail index on their own cannot tell a full buffer from an empty one, because both give head == tail.

// head/tail alone cannot distinguish full from empty (both give head==tail),
// so we store count. The alternative is to waste one slot and call the buffer
// full when (tail+1)%cap==head — both are standard; count is clearer.
class MyCircularQueue{
	vector<int> buf;
	int head;
	int count;
	int cap;

public:
	MyCircularQueue(int k){
		buf.resize(k);
		head=0;
		count=0;
		cap=k;
	}

	bool enQueue(int value){
		if(count==cap)return false;

		buf[(head+count)%cap]=value;   // tail is derived, not stored
		count++;

		return true;
	}

	bool deQueue(){
		if(count==0)return false;

		head=(head+1)%cap;
		count--;

		return true;
	}

	int Front(){ return count==0?-1:buf[head]; }
	int Rear(){ return count==0?-1:buf[(head+count-1)%cap]; }
	bool isEmpty(){ return count==0; }
	bool isFull(){ return count==cap; }
};
Computing tail from head + count removes a whole family of bugs. If you update two indices separately, they can drift out of sync. With one index and a count, they cannot. Note that Rear() uses head+count-1, not head+count: a classic off-by-one.

A dry run with capacity 4, so you can see the wrap happen:

OperationWrites to slotheadcountbuf

Now Front() is buf[2] = 3 and Rear() is buf[(2 + 4 − 1) % 4] = buf[1] = 6. Reading from head and wrapping gives 3, 4, 5, 6: the correct arrival order, even though the array itself reads 5, 6, 3, 4. Dequeuing never erases anything. It just moves head, and the old values are overwritten later. Edge cases to test: enqueue into a full queue (returns false), dequeue or Front() on an empty one, and capacity 1.

My convention: the BFS queue skeleton, unchanged everywhere

Every BFS in this course has exactly this shape. Recording the queue's size first is what makes it aware of levels:

queue<TreeNode*> q;
q.push(root);

while(!q.empty()){
	int n=q.size();          // capture BEFORE the inner loop

	for(int i=0;i<n;i++){
		TreeNode* node=q.front();
		q.pop();

		// ... process node ...

		if(node->left)q.push(node->left);
		if(node->right)q.push(node->right);
	}
}

Read int n=q.size() before the loop starts. At that moment, the queue holds exactly one level. If you write for(int i=0;i<q.size();i++), the size is re-read after you have pushed children, so the inner loop eats the next level too and the idea of a "level" falls apart. This one line is the whole difference between level order and plain BFS, and Chapter 17 builds six problems on it.

What a deque really is

A deque is a double-ended queue: O(1) push and pop at both ends, plus O(1) access by index. You cannot get all three from one continuous block of memory. Adding at the front would mean shifting everything. So std::deque is built from several fixed-size chunks, plus an array of pointers saying where each chunk lives. Think of a bookshelf of small boxes: you can add a box at either end without moving the others.

To find element i, the deque works out which chunk it is in and where inside that chunk, roughly by dividing i by the chunk size. That is two memory lookups instead of one, so it is still O(1), just a little slower than a vector. The operations mirror each other: push_front/push_back, pop_front/pop_back, front()/back(), and dq[i]. How to choose: use vector unless you need to add or remove at the front; then use deque.

📦
std::queue and std::stack are adapters, not containers

An adapter wraps another container and hides most of its operations. queue uses a deque underneath, and so does stack. For large stacks, stack<int,vector<int>> is measurably faster, because a vector keeps everything together in memory and a stack only ever uses one end. Neither adapter lets you loop over its contents. If you need to look at the middle, as the monotonic pattern does, use a deque directly. That is exactly why the next section uses deque and not queue.

The monotonic deque

The problem: a window of size K slides along the array, and you must report the maximum in every position. A heap gives O(n log n), but it cannot remove the element that just left the window; you would have to search for it. A monotonic deque gives O(n).

Why the plain sliding window from Chapter 5 is not enough: for a sum, you add the new element and subtract the one that leaves. A maximum cannot be “subtracted”. If the element leaving was the maximum, you have no idea what the next largest is without rescanning the window, which costs O(k) per step and O(n·k) overall. With n = 100,000 and k = 50,000, that is billions of steps. What you need is a structure that already knows the runner-up, and the one after that. That is what the deque holds.

Two rules do all the work. A rule that always holds is called an invariant:

Invariant 1 — values decrease front to back

So front() is always the largest value in the deque. Before pushing a new element, pop from the back everything smaller than it. Those can never be the maximum again, because the new element is both larger and more recent.

Invariant 2 — every index is inside the window

Before reading the front, pop from the front any index that has dropped out of the window [i-k+1, i]. This is why the deque stores indices, not values: you need the position to know when something expires.

// Invariant 1: values at dq indices strictly decrease from front to back.
// Invariant 2: every index in dq lies inside the current window.
// Together: dq.front() is always the index of the window maximum.
vector<int> maxSlidingWindow(vector<int> &a,int k){
	deque<int> dq;                   // holds INDICES
	vector<int> ans;

	for(int i=0;i<a.size();i++){
		// 1. drop indices that have left the window (invariant 2)
		while(!dq.empty() and dq.front()<=i-k)
		dq.pop_front();

		// 2. drop smaller values from the back — they can never win again (invariant 1)
		while(!dq.empty() and a[dq.back()]<=a[i])
		dq.pop_back();

		dq.push_back(i);

		// 3. once the first full window exists, the front is its maximum
		if(i>=k-1)
		ans.push_back(a[dq.front()]);
	}

	return ans;
}
Three steps, and the order matters. Remove expired indices from the front before reading the front, and remove smaller values from the back before pushing. The i >= k-1 check is there because the first k-1 steps do not have a full window yet. Using <= in step 2 instead of < keeps the deque strictly decreasing, so equal values do not pile up. Either gives the right maximum, but <= keeps the deque smaller.

A dry run on a = [1, 3, -1, -3, 5] with k = 3. The deque is written front → back as value@index:

Answers: [3, 3, 5], one per window [1,3,-1], [3,-1,-3], [-1,-3,5]. Step 4 shows both rules firing: the old maximum expires out of the front, and the new, larger value clears the back.

Variants and edge cases. For the window minimum, flip the comparison to a[dq.back()] >= a[i] so values increase from front to back. When a problem needs both the min and the max of a window (for example “longest subarray whose max − min ≤ limit”), keep two deques side by side. With k = 1, every element is its own answer; with k = n, there is exactly one answer, the overall maximum. Both fall out of the same code with no special cases.

🧾
Why dropping smaller values from the back is safe

Suppose a[j] <= a[i] with j < i. Any future window containing j must also contain i. Windows are one solid block that moves right, so if the left edge has not yet passed j, it certainly has not passed i.

So a[i] is present whenever a[j] is, and it is at least as large. That means j can never be the maximum of any window again. It is useless, and throwing it away costs nothing. This "later and larger wins" argument is the heart of every monotonic structure. It is the same reasoning as the monotonic stack in Chapter 13, and the O(n) comes from each index entering and leaving the deque exactly once.

⛰️
Why a heap is worse here

A max-heap gives you the maximum in O(1), but it cannot remove an element from the middle. When the window slides, the element leaving is at a known index, and that is almost never the top of the heap.

The usual workaround is lazy deletion: store {value, index} pairs, and whenever you look at the top, throw away anything whose index has expired. That gives O(n log n) and is a perfectly good answer.

The deque does something the heap cannot: it throws away elements that can never win, so it only ever holds real candidates. That is how it reaches O(n). The lesson: a heap keeps everything in order; a monotonic deque keeps only the candidates that still matter.

0-1 BFS: the deque's other trick

A preview of Chapter 29. When every edge costs either 0 or 1, you do not need Dijkstra's heap. Push 0-cost neighbours to the front and 1-cost neighbours to the back. A 0-cost neighbour is the same distance as the current node, so it belongs at the front; a 1-cost one belongs a layer later, at the back. The deque then stays sorted by distance on its own, which gives O(V + E) instead of O(E log V).

0-1 BFS — a preview of Chapter 29O(V + E)O(V)
// The deque holds nodes in non-decreasing distance order, with at most
// two distinct distances present at any time — which is why no heap is needed.
vector<int> zeroOneBFS(vector<vector<pair<int,int>>> &graph,int N,int src){
	vector<int> dist(N,INT_MAX);
	deque<int> dq;

	dist[src]=0;
	dq.push_back(src);

	while(!dq.empty()){
		int node=dq.front();
		dq.pop_front();

		for(auto &[neighbour,weight]:graph[node]){
			if(dist[node]+weight<dist[neighbour]){
				dist[neighbour]=dist[node]+weight;

				if(weight==0)dq.push_front(neighbour);   // same distance layer
				else dq.push_back(neighbour);                // next distance layer
			}
		}
	}

	return dist;
}
auto &[neighbour,weight] is a structured binding: it unpacks the pair into two named variables in one line. The graph chapters use it throughout. Note that each pair here is {neighbour, weight}. Stick to that order everywhere, because swapping it by accident gives a bug that is very hard to see.

Where this shows up: grid problems where following an arrow in a cell is free but changing direction costs 1, or where walking on open ground is free but breaking a wall costs 1. Any “minimum number of changes” problem with free moves in between is 0-1 BFS. One detail: a node can be pushed more than once, if a cheaper route to it is found later. That is fine. The dist[node] + weight < dist[neighbour] check makes sure only improvements are pushed, so the total work stays O(V + E).

Queue from two stacks

A classic design question. The interesting part is not the code but the cost analysis.

The idea in one sentence: pouring one stack into another reverses its order, and reversing a LIFO order gives FIFO. A short run:

  1. push 1, 2, 3 → in holds 1, 2, 3 (3 on top); out is empty.
  2. pop → out is empty, so shift: move 3, then 2, then 1. Now out holds 3, 2, 1 with 1 on top. Pop returns 1, the first element pushed.
  3. push 4 → goes onto in. out still holds 3, 2 (2 on top).
  4. pop → out is not empty, so no shift. Returns 2. The 4 waits in in until out runs dry, which keeps the order right: 3 comes out before 4.
MyQueue — amortized O(1) per operationO(1) amortizedO(n)
// Push into "in". Pop from "out". Only refill "out" when it is EMPTY —
// that condition is what makes it amortized O(1) instead of O(n) per pop.
class MyQueue{
	stack<int> in,out;

	void shift(){
		if(!out.empty())return;      // the load-bearing line

		while(!in.empty()){
			out.push(in.top());
			in.pop();
		}
	}

public:
	void push(int x){ in.push(x); }

	int pop(){
		shift();

		int v=out.top();
		out.pop();

		return v;
	}

	int peek(){
		shift();
		return out.top();
	}

	bool empty(){ return in.empty() and out.empty(); }
};
Why it is O(1) on average: each element is pushed onto in once, moved to out once, and popped once. That is three operations over its entire life, whatever order the calls come in. One single pop can cost O(n), but n operations cost O(n) in total. If you move everything whenever in is non-empty, instead of only when out is empty, it becomes O(n) per operation. That is the bug this question is really looking for.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 CAPTURE SIZE
For level-order, take int n = q.size(); before the inner loop. Reading q.size() inside a loop that pushes to q merges every level into one.
💡 DEQUE FOR EXTREMES
Sliding-window maximum keeps a deque of indices with decreasing values: pop the back while smaller, pop the front when it leaves the window. O(n), and a heap is not needed.
💡 0-1 BFS
When edges cost only 0 or 1, a deque replaces the heap — push-front for 0, push-back for 1. Dijkstra without the log factor.
⚠️
Common mistakes
  • for(int i=0;i<q.size();i++) in BFS. The size grows as you push children, so the inner loop eats the next level. Save int n=q.size() first.
  • Using head == tail to test emptiness in a circular buffer. A full buffer gives the same result. Store a count, or leave one slot unused on purpose.
  • Storing values instead of indices in a monotonic deque. Without the index, you cannot tell when an element has left the window.
  • Reading dq.front() before removing expired indices. You return a maximum from outside the window.
  • Forgetting the i >= k-1 check. The first k−1 windows are not full yet and must not be recorded.
  • Moving everything across on every pop in the two-stack queue. It turns O(1) on average into O(n) per operation.
  • Trying to loop over a std::queue or std::stack. They are adapters with no iterators; use a deque instead.
  • Using a heap for sliding-window maximum without lazy deletion. The element leaving the window is not at the top, so you cannot remove it.

Interview drill

Warm-up: Sliding window maximum. Give the heap solution, then improve it.

How a strong answer sounds
The heap version: keep a max-heap of {value, index} pairs and push each element as I go. Before reading the top, I throw away anything whose index has left the window. This is lazy deletion, and I need it because a heap cannot remove an element from the middle. That is O(n log n) time and O(n) space, and it is correct. The improvement is a monotonic deque of indices with two rules that always hold. The values at those indices strictly decrease from front to back, and every index is inside the current window. Then the front is always the window maximum, in O(1). For each element I do three things. Remove indices at or before i−k from the front. Pop from the back while the back's value is at most a[i]. Then push i. Popping from the back is safe: if a[j] ≤ a[i] with j < i, every future window containing j also contains i, because windows are one solid block moving right. So j can never be a maximum again. Each index enters and leaves the deque once, giving O(n) time and O(k) space. The general principle: a heap keeps everything in order, while the deque keeps only the candidates that can still win, which is less work.

Deeper: Implement a queue with two stacks and prove the amortized bound.

How a strong answer sounds
Two stacks, in and out. Push always goes to in. Pop and peek first call a shift. The shift does nothing unless out is empty; if it is empty, it moves everything from in to out. Moving reverses the order, which turns LIFO into FIFO. For the analysis: each element is pushed onto in once, moved to out once, and popped from out once. That is exactly three stack operations over its whole life, however the calls are mixed. So any sequence of n operations costs O(n) in total, which is O(1) amortized (on average), even though one single pop can cost O(n). The key detail is the early return if(!out.empty())return;. If I shifted whenever in was non-empty instead, alternating push and pop would move everything back and forth on every call, and the cost would become O(n) per operation. That one condition is what the question is really testing. It is the same averaging argument as vector's doubling.

🧠 Key takeaways

  • Save int n=q.size() before the inner BFS loop, or the levels run into one another.
  • A circular buffer needs a count (or one unused slot), because head == tail means both full and empty.
  • A deque is chunks plus an array of pointers to them. That gives O(1) at both ends and O(1) indexing, which one continuous block cannot.
  • The monotonic deque keeps only candidates that can still win. A later, larger element beats an earlier, smaller one, so the front is the maximum in O(1).
  • A queue from two stacks is O(1) on average only because you refill out just when it is empty.

Check your understanding

Why must BFS capture int n = q.size() before the inner loop rather than testing i < q.size()?

The saved size is exactly the number of nodes in the current level. Re-reading it also eats the children you just pushed, which breaks any per-level logic. Level order, zigzag and both side views all depend on this one line.

In a circular buffer with only head and tail, what is ambiguous?

Both states end with the two indices equal. Store a count (the clearest fix), or leave one slot unused on purpose and call the buffer full when (tail+1)%cap == head.

In a monotonic deque for window maximum, why is it safe to pop smaller values from the back?

Windows are one solid block that moves right, so a later, larger element beats an earlier, smaller one for good. Throwing away the beaten candidates is what makes this O(n) instead of O(n log n).

Why is a max-heap O(n log n) for sliding-window maximum while a deque is O(n)?

The element leaving the window is not at the top, so you need lazy deletion, and the heap can grow to size n. The deque never holds a candidate that can no longer win, so each index enters and leaves exactly once.

In the two-stack queue, what breaks amortized O(1)?

The guarantee depends on each element moving between the stacks exactly once. If you move elements too eagerly, alternating push and pop shuffles everything back and forth on every call: O(n) per operation.
