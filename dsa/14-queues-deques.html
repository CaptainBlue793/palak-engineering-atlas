Queues, Deques & Monotonic Deques

The queue is the structure behind BFS, and BFS is behind half of Chapter 25 onward — so getting it right matters more than its simplicity suggests. The deque generalises it to both ends, and the monotonic deque solves sliding-window maximum in O(n), which a heap cannot do. This chapter also covers the circular-buffer implementation, because “design a queue” is a real interview question and the wraparound arithmetic is where people slip.

The queue, and the circular buffer

FIFO: push at the back, pop from the front, both O(1). Implementing it on an array is easy to get almost right — the trap is that a head and a tail index alone cannot distinguish a full buffer from an empty one, because both give head == tail.

MyCircularQueueO(1) all opsO(capacity)
// head/tail alone cannot distinguish full from empty (both give head==tail),
// so we store count. The alternative is to waste one slot and call the buffer
// full when (tail+1)%cap==head — both are standard; count is clearer.
class MyCircularQueue{
	vector<int> buf;
	int head;
	int count;
	int cap;

public:
	MyCircularQueue(int k){
		buf.resize(k);
		head=0;
		count=0;
		cap=k;
	}

	bool enQueue(int value){
		if(count==cap)return false;

		buf[(head+count)%cap]=value;   // tail is derived, not stored
		count++;

		return true;
	}

	bool deQueue(){
		if(count==0)return false;

		head=(head+1)%cap;
		count--;

		return true;
	}

	int Front(){ return count==0?-1:buf[head]; }
	int Rear(){ return count==0?-1:buf[(head+count-1)%cap]; }
	bool isEmpty(){ return count==0; }
	bool isFull(){ return count==cap; }
};
Deriving tail from head + count removes a whole class of bug. With two independently updated indices you can get them out of sync; with one index and a count, the invariant is impossible to break. Note Rear() is head+count-1, not head+count — a classic off-by-one.
✍️
My convention: the BFS queue skeleton, unchanged everywhere

Every BFS in this course has exactly this shape, and the level-size capture is what makes it level-aware:

queue<TreeNode*> q;
q.push(root);

while(!q.empty()){
	int n=q.size();          // capture BEFORE the inner loop

	for(int i=0;i<n;i++){
		TreeNode* node=q.front();
		q.pop();

		// ... process node ...

		if(node->left)q.push(node->left);
		if(node->right)q.push(node->right);
	}
}

int n=q.size() must be read before the loop starts. Writing for(int i=0;i<q.size();i++) re-reads the size after children have been pushed, so the inner loop swallows the next level too and every notion of "level" collapses. This one line is the difference between level order and plain BFS — and Chapter 17 builds six problems on it.

What a deque really is

A double-ended queue: O(1) push and pop at both ends, plus O(1) random access. That combination is impossible with a single contiguous block, so std::deque is implemented as a map of fixed-size chunks — an array of pointers to blocks, each block holding a few elements.

std::queue and std::stack are adapters, not containers

They wrap another container and restrict its interface. queue defaults to deque; stack also defaults to deque, though stack<int,vector<int>> is measurably faster for large stacks since a vector has better locality and only needs one end. Neither adapter is iterable — if you need to inspect the middle (as the monotonic pattern does), you must use the underlying deque directly. That is exactly why the next section uses deque and not queue.

The monotonic deque

The problem: return the maximum of every window of size K. A heap gives O(n log n) but cannot remove the element that just left the window — you would have to search for it. A monotonic deque gives O(n).

Two invariants, and they do all the work:

Invariant 1 — values decrease front to back

So front() is always the maximum of whatever is in the deque. Before pushing a new element, pop from the back everything smaller than it — those can never be the maximum again, because the new element is both larger and more recent.

Invariant 2 — all indices are inside the window

Before reading the front, pop from the front any index that has fallen out of [i-k+1, i]. This is why the deque stores indices rather than values.

maxSlidingWindowO(n)O(k)
// Invariant 1: values at dq indices strictly decrease from front to back.
// Invariant 2: every index in dq lies inside the current window.
// Together: dq.front() is always the index of the window maximum.
vector<int> maxSlidingWindow(vector<int> &a,int k){
	deque<int> dq;                   // holds INDICES
	vector<int> ans;

	for(int i=0;i<a.size();i++){
		// 1. drop indices that have left the window (invariant 2)
		while(!dq.empty() and dq.front()<=i-k)
		dq.pop_front();

		// 2. drop smaller values from the back — they can never win again (invariant 1)
		while(!dq.empty() and a[dq.back()]<=a[i])
		dq.pop_back();

		dq.push_back(i);

		// 3. once the first full window exists, the front is its maximum
		if(i>=k-1)
		ans.push_back(a[dq.front()]);
	}

	return ans;
}
Three steps, and the order matters. Expire from the front before reading it, and dominate from the back before pushing. The i >= k-1 guard exists because the first k-1 iterations do not yet have a full window. And <= in step 2 rather than < keeps the deque strictly decreasing, so duplicates do not accumulate — either works for the maximum, but <= keeps it smaller.
🧾
Why dropping smaller values from the back is safe

Suppose a[j] <= a[i] with j < i. Any future window that contains j must also contain i — because windows are contiguous and move rightward, so if the left edge has not yet passed j, it certainly has not passed i. So a[i] is present whenever a[j] is, and it is at least as large: j can never be the maximum of any window again. It is dead, and removing it costs nothing. This "later and larger dominates" argument is the heart of every monotonic structure — it is the same reasoning as the monotonic stack in Chapter 13, and the O(n) follows from each index entering and leaving the deque once.

⛰️
Why a heap is worse here

A max-heap gives you the maximum in O(1), but it cannot remove an arbitrary element — and when the window slides, the element leaving is at a known index, not at the top. You can work around it with lazy deletion (push {value, index}, and on top-of-heap discard anything whose index has expired), which gives O(n log n) and is a perfectly acceptable answer. But the deque exploits something the heap cannot: it throws away elements that can never win, so it never holds more than the useful candidates. That is how it reaches O(n). The general lesson — a heap maintains an ordering, a monotonic deque maintains only the candidates that matter.

0-1 BFS: the deque's other trick

A preview of Chapter 29. When every edge weight is 0 or 1, you do not need Dijkstra's heap. Push 0-weight neighbours to the front and 1-weight neighbours to the back, and the deque stays sorted by distance automatically — giving O(V + E) instead of O(E log V).

0-1 BFS — a preview of Chapter 29O(V + E)O(V)
// The deque holds nodes in non-decreasing distance order, with at most
// two distinct distances present at any time — which is why no heap is needed.
vector<int> zeroOneBFS(vector<vector<pair<int,int>>> &graph,int N,int src){
	vector<int> dist(N,INT_MAX);
	deque<int> dq;

	dist[src]=0;
	dq.push_back(src);

	while(!dq.empty()){
		int node=dq.front();
		dq.pop_front();

		for(auto &[neighbour,weight]:graph[node]){
			if(dist[node]+weight<dist[neighbour]){
				dist[neighbour]=dist[node]+weight;

				if(weight==0)dq.push_front(neighbour);   // same distance layer
				else dq.push_back(neighbour);                // next distance layer
			}
		}
	}

	return dist;
}
Structured binding auto &[neighbour,weight] unpacks the pair in place — the same idiom used throughout the graph chapters. Note the adjacency here is {neighbour, weight}; be consistent about that order, because silently swapping it is a very hard bug to see.

Queue from two stacks

A classic design question, and the interesting part is the amortized analysis.

MyQueue — amortized O(1) per operationO(1) amortizedO(n)
// Push into "in". Pop from "out". Only refill "out" when it is EMPTY —
// that condition is what makes it amortized O(1) instead of O(n) per pop.
class MyQueue{
	stack<int> in,out;

	void shift(){
		if(!out.empty())return;      // the load-bearing line

		while(!in.empty()){
			out.push(in.top());
			in.pop();
		}
	}

public:
	void push(int x){ in.push(x); }

	int pop(){
		shift();

		int v=out.top();
		out.pop();

		return v;
	}

	int peek(){
		shift();
		return out.top();
	}

	bool empty(){ return in.empty() and out.empty(); }
};
Why amortized O(1): each element is pushed to in once, moved to out once, and popped once — three operations over its whole lifetime, regardless of the call pattern. A single pop can cost O(n), but n operations cost O(n) total. If you shift whenever in is non-empty instead of when out is empty, it becomes O(n) per operation — and that is the bug the question is really probing.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 CAPTURE SIZE
For level-order, take int n = q.size(); before the inner loop. Reading q.size() inside a loop that pushes to q merges every level into one.
💡 DEQUE FOR EXTREMES
Sliding-window maximum keeps a deque of indices with decreasing values: pop the back while smaller, pop the front when it leaves the window. O(n), and a heap is not needed.
💡 0-1 BFS
When edges cost only 0 or 1, a deque replaces the heap — push-front for 0, push-back for 1. Dijkstra without the log factor.
⚠️
Common mistakes
  • for(int i=0;i<q.size();i++) in BFS. The size grows as you push children, so the inner loop eats the next level. Capture int n=q.size() first.
  • Using head == tail to test emptiness in a circular buffer. Full gives the same condition. Store a count, or deliberately waste one slot.
  • Storing values instead of indices in a monotonic deque. You cannot expire by window position without the index.
  • Reading dq.front() before expiring stale indices. You return a maximum from outside the window.
  • Forgetting the i >= k-1 guard. The first k−1 windows are incomplete and must not be recorded.
  • Shifting on every pop in the two-stack queue. Turns amortized O(1) into O(n) per operation.
  • Trying to iterate a std::queue or std::stack. They are adapters with no iterators; use the underlying deque.
  • Using a heap for sliding-window maximum without lazy deletion. The expiring element is not at the top and cannot be removed.

Interview drill

Warm-up: Sliding window maximum. Give the heap solution, then improve it.

How a strong answer sounds
The heap version: maintain a max-heap of {value, index} pairs, push each element as I go, and before reading the top discard anything whose index has fallen out of the window — lazy deletion, because I cannot remove an arbitrary element from a heap. That is O(n log n) time and O(n) space, and it is correct. The improvement is a monotonic deque of indices with two invariants: the values at those indices strictly decrease from front to back, and every index is inside the current window. Then the front is always the window maximum in O(1). Per element I do three things: expire indices at or before i−k from the front, pop from the back while the back's value is at most a[i], then push i. Dropping from the back is safe because if a[j] ≤ a[i] with j < i, then every future window containing j also contains i — windows are contiguous and move right — so j can never be a maximum again. Each index enters and leaves the deque once, giving O(n) time and O(k) space. The general principle is that a heap maintains a full ordering while the deque keeps only the candidates that can still win, which is strictly less work.

Deeper: Implement a queue with two stacks and prove the amortized bound.

How a strong answer sounds
Two stacks, in and out. Push always goes to in. Pop and peek first call a shift, which returns immediately unless out is empty, and otherwise drains all of in into out — reversing the order, which converts LIFO into FIFO. For the analysis: each element is pushed onto in exactly once, moved to out exactly once, and popped from out exactly once, so it accounts for exactly three stack operations across its entire lifetime no matter how the calls interleave. Therefore any sequence of n operations costs O(n) total and O(1) amortized, even though one individual pop can be O(n). The critical detail is the early return if(!out.empty())return; — if instead I shifted whenever in was non-empty, an alternating push/pop pattern would move everything back and forth on every call and the cost would become O(n) per operation. That single condition is what the question is actually testing, and it is the same amortized reasoning as vector's doubling.

🧠 Key takeaways

  • Capture int n=q.size() before the inner BFS loop, or levels collapse into one another.
  • A circular buffer needs a count (or one wasted slot) because head == tail means both full and empty.
  • deque is chunks plus an index array, giving O(1) at both ends and O(1) indexing — which one contiguous block cannot.
  • The monotonic deque keeps only candidates that can still win: later-and-larger dominates, so the front is the maximum in O(1).
  • Queue from two stacks is amortized O(1) only because you refill out exclusively when it is empty.

Check your understanding

Why must BFS capture int n = q.size() before the inner loop rather than testing i < q.size()?

The captured size is exactly the current level's node count. Re-reading it swallows the children you just pushed, which destroys any per-level logic — level order, zigzag and both side views all depend on this one line.

In a circular buffer with only head and tail, what is ambiguous?

Both states collapse to the same index equality. Store a count (clearest), or deliberately leave one slot unused and define full as (tail+1)%cap == head.

In a monotonic deque for window maximum, why is it safe to pop smaller values from the back?

Windows are contiguous and move rightward, so a later, larger element dominates an earlier, smaller one permanently. Discarding dominated candidates is what makes this O(n) rather than O(n log n).

Why is a max-heap O(n log n) for sliding-window maximum while a deque is O(n)?

The element leaving the window is not at the top, so you need lazy deletion and the heap can grow to size n. The deque never holds a candidate that cannot still win, so each index enters and leaves exactly once.

In the two-stack queue, what breaks amortized O(1)?

The guarantee relies on each element moving between stacks exactly once. Shifting eagerly makes an alternating push/pop pattern move everything back and forth on every call — O(n) per operation.
