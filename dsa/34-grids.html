Grids: Flood Fill & Multi-Source BFS

A grid is a graph you never build. Each cell is a node, each adjacency is an implicit edge, and once you see that translation every algorithm from Chapters 25–33 applies unchanged. The grid-specific skills are small and worth drilling: the direction array, the bounds-plus-validity guard, and the multi-source BFS that answers “distance to the nearest anything” in one pass instead of one pass per source.

  • Translate a grid into a graph and write the four-direction loop cleanly
  • Get the bounds check right, and know why its order matters
  • Use multi-source BFS instead of running BFS from every source
  • Choose DFS, BFS, 0-1 BFS or Dijkstra from what the grid's edges cost
  • Handle in-place marking, and know when you must restore the grid

// Four orthogonal directions. Declare it once, outside the loops.
int dr[]={-1,1,0,0};
int dc[]={0,0,-1,1};

// Or as pairs, which is harder to get out of sync:
int dirs[4][2]={{-1,0},{1,0},{0,-1},{0,1}};

// Eight directions, when diagonals count:
int dr8[]={-1,-1,-1,0,0,1,1,1};
int dc8[]={-1,0,1,-1,1,-1,0,1};

// THE GUARD. Bounds first, then validity — order matters (see below).
for(int k=0;k<4;k++){
	int nr=r+dr[k];
	int nc=c+dc[k];

	if(nr<0 or nr>=rows or nc<0 or nc>=cols)continue;
	if(visited[nr][nc] or grid[nr][nc]=='0')continue;

	// ... now (nr,nc) is a safe, valid neighbour
}
Bounds before validity, always. C++ evaluates or left to right with short-circuiting, so writing if(grid[nr][nc]=='0' or nr<0) indexes out of bounds before the bounds test runs. Splitting it into two if statements, as above, makes the ordering impossible to get wrong and reads better than one long condition.
✍️
My convention: dr/dc arrays, never four copy-pasted blocks

Four hand-written neighbour blocks means four places to make the same typo, and the bug is always in the one you wrote last. One direction array plus one loop means the guard exists once. It also makes switching from 4- to 8-connectivity a one-line change, and it extends naturally to a knight's moves or to 3D. And declare the arrays outside the function or as const at file scope — re-declaring them inside a hot recursive function is pointless work.

Flood fill: count the islands

numIslands — DFS flood fillO(rows·cols)O(rows·cols) stack
// Sinking the island as we go: mark visited by overwriting the grid.
// No visited array at all — but it MUTATES the caller's grid.
void DFS(vector<vector<char>> &grid,int r,int c){
	int rows=grid.size();
	int cols=grid[0].size();

	if(r<0 or r>=rows or c<0 or c>=cols)return;
	if(grid[r][c]!='1')return;

	grid[r][c]='0';                 // sink it — this IS the visited mark

	DFS(grid,r-1,c);
	DFS(grid,r+1,c);
	DFS(grid,r,c-1);
	DFS(grid,r,c+1);
}
int numIslands(vector<vector<char>> &grid){
	if(grid.empty())return 0;

	int count=0;

	for(int r=0;r<grid.size();r++){
		for(int c=0;c<grid[0].size();c++){
			if(grid[r][c]=='1'){
				count++;             // a new island starts here
				DFS(grid,r,c);
			}
		}
	}

	return count;
}
The outer double loop is the component counter, exactly as in Chapter 25. Note this version puts the guard inside the recursive function rather than before each call — that trades four checks per cell for one, and is cleaner. Two caveats: it mutates the caller's grid, so restore it or take a copy if the caller still needs it; and on a 10⁶-cell grid that is all land, recursion depth reaches 10⁶ and overflows — use BFS or an explicit stack (Chapter 11).

Multi-source BFS — the pattern worth internalising

“What is the distance from each cell to the nearest source?” The naive approach runs BFS from every source: O(sources × cells). The trick is to put every source in the queue before the loop starts, all at distance 0. One BFS answers it for all of them.

multi-source BFS — the whole trick is the seeding loopO(rows·cols)O(rows·cols)
// "Distance to the nearest source" for every cell, in ONE pass.
vector<vector<int>> nearestSource(vector<vector<int>> &grid){
	int rows=grid.size();
	int cols=grid[0].size();

	vector<vector<int>> dist(rows,vector<int>(cols,-1));
	queue<pair<int,int>> q;

	// SEED EVERY SOURCE AT DISTANCE 0, BEFORE the loop starts.
	for(int r=0;r<rows;r++){
		for(int c=0;c<cols;c++){
			if(grid[r][c]==1){
				dist[r][c]=0;
				q.push({r,c});
			}
		}
	}

	int dr[]={-1,1,0,0};
	int dc[]={0,0,-1,1};

	while(!q.empty()){
		auto [r,c]=q.front();
		q.pop();

		for(int k=0;k<4;k++){
			int nr=r+dr[k];
			int nc=c+dc[k];

			if(nr<0 or nr>=rows or nc<0 or nc>=cols)continue;
			if(dist[nr][nc]!=-1)continue;        // already reached, so already nearest

			dist[nr][nc]=dist[r][c]+1;
			q.push({nr,nc});
		}
	}

	return dist;
}
Why it is correct: BFS processes the queue in non-decreasing distance order (Chapter 25), and seeding all sources at 0 means the frontier expands from all of them simultaneously. So the first source to reach a cell is necessarily its nearest one, and dist[nr][nc] != -1 locks that in. One pass instead of one per source — the difference between O(cells) and O(sources × cells).
🍊
The problems that are multi-source BFS
  • Rotting oranges — every rotten orange is a source; the answer is the maximum distance (and −1 if any fresh orange is unreachable).
  • 01 matrix — distance from each cell to the nearest 0. The canonical instance.
  • Walls and gates — distance from each room to the nearest gate.
  • As far from land as possible — every land cell is a source; the answer is the maximum water distance.
  • Shortest bridge — flood-fill one island to find it, then multi-source BFS from all its cells until you hit the other.
  • Map of highest peak — every water cell is a source, and the height is the BFS distance.

The tell is the word "nearest" or "any" applied to a set of starting points. If you find yourself about to loop BFS over sources, stop and seed them all instead.

Which traversal does the grid want?

Count regions, or explore a connected area

→ DFS or BFS, either is fine. Flood fill. Islands, region area, perimeter, enclosed regions.

Shortest path, all moves costing 1

→ BFS. Never DFS — it will find a path, not the shortest. Maze, knight's moves, shortest path in a binary matrix.

Moves cost 0 or 1 (free moves and paid moves)

→ 0-1 BFS with a deque (Chapter 29). Minimum obstacles to remove, minimum cost to make a valid path.

if(cost==0) dq.push_front(nb); else dq.push_back(nb);

→ Dijkstra on the implicit grid graph. Path with minimum effort, swim in rising water.

priority_queue<...,greater<...>> pq; pq.push({cost,{r,c}});

→ DP on the grid (Chapter 42), not a traversal. Unique paths, minimum path sum, maximal square.

dp[r][c] = f(dp[r-1][c], dp[r][c-1]);

dsu.unite(r*cols+c, nr*cols+nc);
🖊️
In-place marking: convenient, and sometimes wrong

Overwriting the grid to mark cells visited saves an O(rows·cols) array and is idiomatic. Three situations where it is a mistake:

  • The caller still needs the grid. Copy it, or restore it afterwards. Silently destroying an argument is rude and produces baffling bugs when the function is called twice.
  • You are backtracking, not flood-filling. In word search you must unmark on the way out (grid[r][c] = saved;) because a cell unusable on this path may be needed on another. Flood fill never revisits, so it never unmarks — the distinction is Chapter 35's.
  • There is no spare value. If every character is meaningful you have nothing safe to write. Use a separate visited array.
🔢
Why grid problems are always O(rows · cols)

A grid has V = rows·cols nodes and at most 4V edges, so it is inherently sparse and O(V + E) = O(rows·cols). That means plain BFS and DFS on a grid are linear in the number of cells, and a 10⁶-cell grid traverses in milliseconds. Dijkstra adds a log factor for the heap, giving O(rows·cols·log(rows·cols)). So if your grid solution is slower than that, the problem is usually a missing visited check causing re-expansion — or you are running a fresh BFS per source when a multi-source pass would do.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 DIRECTION ARRAYS
Keep dr[] and dc[] and loop. Four branches become one loop, and switching to 8-connectivity is then a two-element edit rather than a rewrite.
💡 MULTI-SOURCE
Push every source before the loop starts and BFS fans out from all of them at once. That converts "distance to the nearest X" from many searches into one.
💡 FLOOD FROM OUTSIDE
For "regions not touching the border", start the flood at the border and invert. Far easier than testing enclosure from the inside.
⚠️
Common mistakes
  • Checking validity before bounds. grid[nr][nc] is evaluated before nr >= 0 if you write the condition in that order. Bounds first, always.
  • dr and dc out of sync. Four copy-pasted blocks, or a mismatched pair of arrays. Use dirs[4][2] if you have ever made this mistake.
  • Running BFS once per source. Seed them all instead — O(cells) versus O(sources × cells).
  • Marking visited on dequeue instead of enqueue (Chapter 25). The queue grows to O(E) and a large grid times out.
  • Using DFS for a shortest path. It finds a path, not the shortest.
  • Forgetting to unmark in backtracking. Word search needs the restore; flood fill does not.
  • Mutating the caller's grid without saying so. Fine in a contest, a real bug in a library.
  • Recursive flood fill on a 10⁶-cell all-land grid. Depth 10⁶ overflows the stack; use BFS.
  • Assuming 4-connectivity when the problem means 8. Read the statement; "diagonally adjacent counts" changes the direction array.
  • Forgetting the unreachable case. In rotting oranges, a fresh orange never reached means return −1, not the maximum distance.

Interview drill

Warm-up: Rotting oranges — every minute, a rotten orange rots its orthogonal neighbours. How long until all are rotten?

How a strong answer sounds
This is multi-source BFS, because rot spreads from all rotten oranges simultaneously and each fresh orange is reached first by whichever rotten one is nearest. So I scan the grid once, push every initially rotten cell into the queue at distance 0, and count the fresh ones while I am there. Then one standard BFS: pop a cell, look at its four neighbours using a dr/dc array, and for any in-bounds fresh neighbour set its time to the current time plus one, decrement the fresh count, and enqueue it — marking on enqueue, so each cell enters once. The answer is the maximum time assigned, which I can track as I go or read off the last processed layer. The case people miss: if the fresh count is still positive when the queue empties, some oranges are unreachable — walled off or in a separate region — and the answer is −1, not the maximum distance. Also, if there were no fresh oranges to begin with the answer is 0, not −1. O(rows·cols) time and space, and the whole point is that seeding all sources turns what looks like "run BFS from each rotten orange" into a single linear pass.

Deeper: Shortest path in a grid where you may remove up to K walls. How do you model it?

How a strong answer sounds
The naive instinct is BFS on the cells, but that is wrong for the same reason "cheapest flight with K stops" breaks plain Dijkstra: reaching a cell cheaply having already spent all K removals may be worse than reaching it later with removals to spare. So "cell" is not a sufficient state — I widen it to (row, col, wallsUsed) and run BFS over that expanded graph, keeping visited[r][c][k]. Moving to an empty neighbour keeps k, moving through a wall goes to k+1 and is only allowed while k+1 <= K. Since every move still costs exactly one step, plain BFS is correct and it is O(rows·cols·K) time and space. The first time I dequeue the target cell at any k, that is the answer. There is a neater alternative if instead the cost is "number of walls removed" rather than "number of steps": then wall-free moves cost 0 and wall moves cost 1, which is exactly 0-1 BFS with a deque — push-front for free moves, push-back for paid ones — giving O(rows·cols) with no extra dimension. So the choice depends on whether I am minimising steps subject to a wall budget, or minimising walls removed. Naming that distinction out loud is the substance of the question; the general lesson is that a constraint belongs in the state.

🧠 Key takeaways

  • A grid is an implicit sparse graph: V = rows·cols, E ≈ 4V, so traversals are linear in the cell count.
  • One dr/dc array and one guard — bounds before validity, because or short-circuits left to right.
  • Multi-source BFS seeds every source at distance 0 before the loop: O(cells) instead of O(sources × cells).
  • Costs decide the algorithm: uniform → BFS, 0/1 → deque, arbitrary → Dijkstra, counting paths → DP.
  • In-place marking is fine for flood fill but wrong for backtracking, which must restore the cell on the way out.

Check your understanding

Why must the bounds check come before the validity check?

Writing if(grid[nr][nc]=='0' or nr<0) reads memory outside the array first. Splitting into two separate if statements makes the ordering impossible to get wrong.

You need each cell's distance to the nearest 0 in a binary matrix. Best approach?

Seeding all sources makes the frontier expand from all of them at once, so each cell is reached first by its nearest source. O(cells) instead of O(zeros × cells). (Two-pass DP also works here, but the BFS generalises to walls and to weighted moves.)

In word search (find a word by walking adjacent cells), why must you restore the cell after recursing?

Flood fill never revisits a cell, so marking is permanent. Backtracking explores alternative paths, so the mark is only valid for the current one — this is Chapter 35's choose/explore/unchoose.

Moving to an empty cell is free but breaking a wall costs 1, and you must minimise walls broken. Which algorithm?

Two distinct edge costs mean a deque keeps the frontier sorted by distance with no heap: O(cells) instead of O(cells log cells). Plain BFS would be wrong, since the free move must not increase the distance.

In rotting oranges, the queue empties but some oranges are still fresh. What do you return?

Unreachable fresh oranges mean the task is impossible. Track a fresh count while seeding and check it at the end — this is the case most first attempts miss. (And with zero fresh oranges initially, the answer is 0, not −1.)
