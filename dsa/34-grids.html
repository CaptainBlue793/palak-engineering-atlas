Grids: Flood Fill & Multi-Source BFS

A grid is a graph you never have to build. Each cell is a node. Each pair of touching cells is an edge you never store; you work it out when you need it. Once you see that, every algorithm from Chapters 25–33 works on grids unchanged. The grid-only skills are small and worth practising:

  • the direction array, which lists the moves to a cell's neighbours;
  • the guard, which checks a neighbour is inside the grid and usable;
  • multi-source BFS, which finds “distance to the nearest anything” in one pass instead of one pass per starting point.
  • Turn a grid into a graph and write the four-direction loop cleanly
  • Get the bounds check right, and know why its order matters
  • Use multi-source BFS instead of running BFS from every source
  • Pick DFS, BFS, 0-1 BFS or Dijkstra based on what each move costs
  • Mark cells in the grid itself, and know when you must restore them

The translation

Why grids get their own chapter. Grid problems are among the most common in coding interviews: mazes, islands, game boards, maps, images (every pixel is a cell). The algorithms are the graph ones you already know. What trips people up is the grid-specific plumbing: going out of bounds, forgetting a direction, or running the same search many times over. This chapter makes that plumbing automatic.

A worked example of the two ideas in the table. In a grid with 3 rows and 4 columns, cell (2, 1) becomes the single number 2·4 + 1 = 9. To go back, divide: r = 9 / 4 = 2 and c = 9 % 4 = 1. That single number is handy when an algorithm wants plain integer node ids, like DSU. And the neighbours of cell (1, 2) are (0, 2) above, (2, 2) below, (1, 1) to the left and (1, 3) to the right. Each is the cell plus one pair from the direction array below. A corner cell such as (0, 0) has only 2 real neighbours; the other two moves land at row −1 or column −1, and the guard throws them away.

the direction array and the guardwrite this the same way every time
// Four orthogonal directions. Declare it once, outside the loops.
int dr[]={-1,1,0,0};
int dc[]={0,0,-1,1};

// Or as pairs, which is harder to get out of sync:
int dirs[4][2]={{-1,0},{1,0},{0,-1},{0,1}};

// Eight directions, when diagonals count:
int dr8[]={-1,-1,-1,0,0,1,1,1};
int dc8[]={-1,0,1,-1,1,-1,0,1};

// THE GUARD. Bounds first, then validity — order matters (see below).
for(int k=0;k<4;k++){
	int nr=r+dr[k];
	int nc=c+dc[k];

	if(nr<0 or nr>=rows or nc<0 or nc>=cols)continue;
	if(visited[nr][nc] or grid[nr][nc]=='0')continue;

	// ... now (nr,nc) is a safe, valid neighbour
}
Always check bounds before validity. C++ checks or conditions left to right and stops at the first true one (short-circuiting). So if(grid[nr][nc]=='0' or nr<0) reads outside the array before the bounds test even runs. Splitting it into two if statements, as above, makes the order impossible to get wrong. It also reads better than one long condition.
✍️
My convention: dr/dc arrays, never four copy-pasted blocks

Four hand-written neighbour blocks give you four places to make the same typo. The bug is always in the one you wrote last. With one direction array and one loop, the guard exists only once. Switching from 4 directions to 8 becomes a one-line change. It also extends easily to a knight's moves or to 3D. Declare the arrays outside the function, or as const at the top of the file. Re-creating them inside a recursive function that runs millions of times is wasted work.

Flood fill: count the islands

numIslands — DFS flood fillO(rows·cols)O(rows·cols) stack
// Sinking the island as we go: mark visited by overwriting the grid.
// No visited array at all — but it MUTATES the caller's grid.
void DFS(vector<vector<char>> &grid,int r,int c){
	int rows=grid.size();
	int cols=grid[0].size();

	if(r<0 or r>=rows or c<0 or c>=cols)return;
	if(grid[r][c]!='1')return;

	grid[r][c]='0';                 // sink it — this IS the visited mark

	DFS(grid,r-1,c);
	DFS(grid,r+1,c);
	DFS(grid,r,c-1);
	DFS(grid,r,c+1);
}
int numIslands(vector<vector<char>> &grid){
	if(grid.empty())return 0;

	int count=0;

	for(int r=0;r<grid.size();r++){
		for(int c=0;c<grid[0].size();c++){
			if(grid[r][c]=='1'){
				count++;             // a new island starts here
				DFS(grid,r,c);
			}
		}
	}

	return count;
}
The outer double loop counts the islands (the connected components), exactly as in Chapter 25. This version puts the guard inside the recursive function instead of before each call. That means one check per cell instead of four, and cleaner code. Two warnings. First, it changes the caller's grid, so restore it or work on a copy if the caller still needs it. Second, on a 10⁶-cell grid that is all land, the recursion goes 10⁶ calls deep and overflows the stack. Use BFS or your own stack instead (Chapter 11).

Dry run

Take this 3 × 4 grid, where 1 is land and 0 is water:

1100
0101
0001
  1. The scan starts at (0,0), which is land. Count becomes 1. The fill sinks (0,0), then its right neighbour (0,1), then (1,1) below that. All three are now 0.
  2. The scan moves on. (0,1) and (1,1) are already water, so they are skipped. That is exactly why sinking works as the visited mark.
  3. At (1,3) the scan finds land again. Count becomes 2. The fill sinks (1,3) and (2,3).
  4. Nothing else is land. The answer is 2.

If diagonals counted as touching (8 directions), (1,1) would still not reach (1,3), so the answer would stay 2 here. On other grids the two rules give different counts, so read which one the problem wants.

A useful twist: flood from the border. "Surrounded regions" asks you to capture every region of O cells that does not touch the edge. Testing each region for "does it touch the edge?" is awkward. Instead, start a flood fill from every O on the border and mark those cells as safe. Every O not marked afterwards must be enclosed. Same algorithm, started from a smarter place.

Multi-source BFS — the pattern worth internalising

Question: “What is the distance from each cell to the nearest source?” A source is any starting cell, such as a rotten orange or an exit. The simple approach runs a separate BFS from every source. That costs O(sources × cells). The trick is to put every source in the queue before the loop starts, all at distance 0. Then one BFS answers the question for all of them.

How big the difference is. On a 1000 × 1000 grid (10⁶ cells) with 1,000 sources, one BFS per source costs about 10⁹ steps, far too slow. A single multi-source BFS costs about 10⁶ steps, because each cell enters the queue once no matter how many sources there are.

Think of dropping several stones into a pond at the same moment. The ripples spread out together, and each spot is first hit by the ripple from the closest stone.

multi-source BFS — the whole trick is the seeding loopO(rows·cols)O(rows·cols)
// "Distance to the nearest source" for every cell, in ONE pass.
vector<vector<int>> nearestSource(vector<vector<int>> &grid){
	int rows=grid.size();
	int cols=grid[0].size();

	vector<vector<int>> dist(rows,vector<int>(cols,-1));
	queue<pair<int,int>> q;

	// SEED EVERY SOURCE AT DISTANCE 0, BEFORE the loop starts.
	for(int r=0;r<rows;r++){
		for(int c=0;c<cols;c++){
			if(grid[r][c]==1){
				dist[r][c]=0;
				q.push({r,c});
			}
		}
	}

	int dr[]={-1,1,0,0};
	int dc[]={0,0,-1,1};

	while(!q.empty()){
		auto [r,c]=q.front();
		q.pop();

		for(int k=0;k<4;k++){
			int nr=r+dr[k];
			int nc=c+dc[k];

			if(nr<0 or nr>=rows or nc<0 or nc>=cols)continue;
			if(dist[nr][nc]!=-1)continue;        // already reached, so already nearest

			dist[nr][nc]=dist[r][c]+1;
			q.push({nr,nc});
		}
	}

	return dist;
}
Why it is correct: BFS handles cells in order of distance: all distance-0 cells, then all distance-1 cells, and so on (Chapter 25). Starting every source at 0 makes the frontier grow from all of them at the same time. So the first source to reach a cell must be its nearest one, and the check dist[nr][nc] != -1 locks that answer in. One pass instead of one per source. That is the difference between O(cells) and O(sources × cells).

  1. Seeding: (0,0) and (2,2) go into the queue with distance 0. Every other cell starts at −1.
  2. Layer 1: popping (0,0) sets (0,1) and (1,0) to 1. Popping (2,2) sets (1,2) and (2,1) to 1.
  3. Layer 2: popping the four distance-1 cells reaches (0,2), (1,1) and (2,0), all at distance 2. (1,1) is reached first from (1,0) (the order depends on the direction array); when (0,1), (1,2) and (2,1) look at it later, its distance is no longer −1, so they leave it alone.
  4. The queue empties. Every cell has its distance to the nearest zero.

Edge cases. If there are no sources at all, every cell stays at −1; decide what the problem wants in that case. Walls are simply cells the guard refuses to enter, so a cell sealed off by walls also keeps −1. That "still −1" is exactly how rotting oranges detects the unreachable case.

🍊
The problems that are multi-source BFS
  • Rotting oranges: every rotten orange is a source. The answer is the largest distance (or −1 if some fresh orange can never be reached).
  • 01 matrix: distance from each cell to the nearest 0. The textbook example.
  • Walls and gates: distance from each room to the nearest gate.
  • As far from land as possible: every land cell is a source. The answer is the largest distance of any water cell.
  • Shortest bridge: flood-fill one island to find all its cells. Then run multi-source BFS from all of them until you hit the other island.
  • Map of highest peak: every water cell is a source, and each cell's height is its BFS distance.

The clue is the word "nearest" or "any" applied to a set of starting points. If you are about to run BFS in a loop over the sources, stop. Put them all in the queue at the start instead.

Which traversal does the grid want?

Count regions, or explore a connected area

→ DFS or BFS, either is fine. This is flood fill. Examples: islands, region area, perimeter, enclosed regions.

for each cell: if(unvisited) { count++; fill(cell); }
Shortest path, all moves costing 1

→ BFS. Never DFS: it finds a path, not the shortest one. Examples: a maze, knight's moves, shortest path in a binary matrix.

queue<pair<int,int>> q; // dist[nr][nc]=dist[r][c]+1
Distance to the nearest of several things

→ Multi-source BFS. Start them all at distance 0.

for each source: dist=0, q.push(source);
Moves cost 0 or 1 (free moves and paid moves)

→ 0-1 BFS with a deque, a queue you can add to at either end (Chapter 29). Examples: fewest obstacles to remove, lowest cost to make a valid path.

if(cost==0) dq.push_front(nb); else dq.push_back(nb);

Example of a 0/1 grid: each cell holds an arrow, and following the arrow is free while changing it costs 1. "Fewest arrow changes to reach the corner" is then 0-1 BFS: a free move goes to the front of the deque, because it does not increase the cost, and a paid move goes to the back.

Moves have arbitrary positive costs

→ Dijkstra on the grid, treated as a graph. Examples: path with minimum effort, swim in rising water.

priority_queue<...,greater<...>> pq; pq.push({cost,{r,c}});
Count paths, or optimise over paths in one direction

→ DP on the grid (Chapter 42), not a traversal. Examples: unique paths, minimum path sum, maximal square.

dp[r][c] = f(dp[r-1][c], dp[r][c-1]);
Regions merging as cells are added over time

→ DSU (union-find, Chapter 22), with each cell turned into the number r*cols+c. Example: Islands II.

dsu.unite(r*cols+c, nr*cols+nc);
🖊️
In-place marking: convenient, and sometimes wrong

Writing over the grid to mark cells as visited saves you an O(rows·cols) array, and it is common practice. It is a mistake in three situations:

  • The caller still needs the grid. Copy it, or restore it afterwards. Quietly destroying an input is rude, and it causes confusing bugs when the function is called twice.
  • You are backtracking, not flood-filling. In word search you must unmark a cell on the way back out (grid[r][c] = saved;). A cell you cannot use on this path may be needed on another path. Flood fill never revisits cells, so it never unmarks. Chapter 35 covers this difference.
  • There is no spare value. If every character already means something, there is nothing safe to write. Use a separate visited array.
🔢
Why grid problems are always O(rows · cols)

A grid has V = rows·cols nodes and at most 4V edges. So it is always sparse, and O(V + E) = O(rows·cols). That means plain BFS and DFS on a grid take time proportional to the number of cells. A 10⁶-cell grid is explored in milliseconds. Dijkstra adds a log factor for the heap, giving O(rows·cols·log(rows·cols)). If your grid solution is slower than that, the cause is usually a missing visited check, so cells get explored again and again. Or you are running a new BFS per source when one multi-source pass would do.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 DIRECTION ARRAYS
Keep dr[] and dc[] and loop. Four branches become one loop, and switching to 8-connectivity is then a two-element edit rather than a rewrite.
💡 MULTI-SOURCE
Push every source before the loop starts and BFS fans out from all of them at once. That converts "distance to the nearest X" from many searches into one.
💡 FLOOD FROM OUTSIDE
For "regions not touching the border", start the flood at the border and invert. Far easier than testing enclosure from the inside.
⚠️
Common mistakes
  • Checking validity before bounds. If you write the condition in that order, grid[nr][nc] is read before nr >= 0 is checked. Always check bounds first.
  • dr and dc out of sync. This comes from four copy-pasted blocks, or two arrays that do not line up. Use dirs[4][2] if you have ever made this mistake.
  • Running BFS once per source. Put them all in the queue at the start instead: O(cells) versus O(sources × cells).
  • Marking a cell visited when you take it out of the queue instead of when you add it (Chapter 25). The queue grows to O(E), and a large grid times out.
  • Using DFS for a shortest path. It finds a path, not the shortest one.
  • Forgetting to unmark in backtracking. Word search needs the restore; flood fill does not.
  • Changing the caller's grid without saying so. Fine in a contest, a real bug in a library.
  • Recursive flood fill on a 10⁶-cell grid that is all land. Recursion 10⁶ calls deep overflows the stack. Use BFS.
  • Assuming 4 directions when the problem means 8. Read the statement. "Diagonal cells count as adjacent" changes the direction array.
  • Forgetting the unreachable case. In rotting oranges, if a fresh orange is never reached, return −1, not the largest distance.

Interview drill

Warm-up: Rotting oranges — every minute, a rotten orange rots its orthogonal neighbours. How long until all are rotten?

How a strong answer sounds
This is multi-source BFS. Rot spreads from all rotten oranges at the same time, and each fresh orange is reached first by the nearest rotten one. So I scan the grid once. I push every rotten cell into the queue at distance 0, and count the fresh ones while I am there. Then I run one normal BFS. Pop a cell and look at its four neighbours using a dr/dc array. For each fresh neighbour inside the grid, set its time to the current time plus one, lower the fresh count, and add it to the queue. I mark it when I add it, so each cell enters the queue only once. The answer is the largest time assigned; I can track it as I go. The case people miss: if the fresh count is still above zero when the queue empties, some oranges can never be reached. They are walled off or in a separate region, and the answer is −1, not the largest distance. Also, if there were no fresh oranges at the start, the answer is 0, not −1. This is O(rows·cols) time and space. The key point is that starting from all sources at once turns "run BFS from each rotten orange" into a single linear pass.

Deeper: Shortest path in a grid where you may remove up to K walls. How do you model it?

How a strong answer sounds
The first instinct is BFS on the cells, but that is wrong. It fails for the same reason "cheapest flight with K stops" breaks plain Dijkstra. Reaching a cell quickly after using up all K removals can be worse than reaching it later with removals still left. So "which cell" is not enough information. I widen the state (what I track at each point) to (row, col, wallsUsed) and run BFS over that bigger graph, keeping visited[r][c][k]. Moving to an empty neighbour keeps k the same. Moving through a wall goes to k+1, and is only allowed while k+1 <= K. Every move still costs exactly one step, so plain BFS is correct. It takes O(rows·cols·K) time and space. The first time I take the target cell out of the queue, at any k, that is the answer. There is a neater option if the cost is "number of walls removed" instead of "number of steps". Then moves without a wall cost 0 and moves through a wall cost 1. That is exactly 0-1 BFS with a deque: push-front for free moves, push-back for paid ones. It runs in O(rows·cols) with no extra dimension. So the choice depends on the goal: fewest steps within a wall budget, or fewest walls removed. Saying that difference out loud is the heart of the question. The general lesson: a constraint belongs in the state.

🧠 Key takeaways

  • A grid is a sparse graph you never build: V = rows·cols and E ≈ 4V, so traversals take time proportional to the number of cells.
  • Use one dr/dc array and one guard. Check bounds before validity, because or checks left to right and stops early.
  • Multi-source BFS puts every source in the queue at distance 0 before the loop: O(cells) instead of O(sources × cells).
  • Move costs decide the algorithm: all equal → BFS, 0 or 1 → deque, any positive cost → Dijkstra, counting paths → DP.
  • Marking cells in the grid itself is fine for flood fill. It is wrong for backtracking, which must restore the cell on the way out.

Check your understanding

Why must the bounds check come before the validity check?

Writing if(grid[nr][nc]=='0' or nr<0) reads memory outside the array first. Splitting it into two separate if statements makes the order impossible to get wrong.

You need each cell's distance to the nearest 0 in a binary matrix. Best approach?

Starting from all sources makes the frontier grow from all of them at once, so each cell is reached first by its nearest source. That is O(cells) instead of O(zeros × cells). (Two-pass DP also works here, but the BFS also handles walls and moves with different costs.)

In word search (find a word by walking adjacent cells), why must you restore the cell after recursing?

Flood fill never revisits a cell, so its marks are permanent. Backtracking tries different paths, so a mark only holds for the current path. This is Chapter 35's choose / explore / unchoose.

Moving to an empty cell is free but breaking a wall costs 1, and you must minimise walls broken. Which algorithm?

With only two possible move costs, a deque keeps the frontier sorted by distance without a heap: O(cells) instead of O(cells log cells). Plain BFS would be wrong, because a free move must not add to the distance.

In rotting oranges, the queue empties but some oranges are still fresh. What do you return?

If some fresh oranges can never be reached, the task is impossible. Count the fresh oranges while filling the queue, and check the count at the end. Most first attempts miss this case. (And if there are no fresh oranges at the start, the answer is 0, not −1.)
