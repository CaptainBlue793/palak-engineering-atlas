Divide & Conquer

Split the problem into pieces, solve each piece the same way, then put the answers back together. The interesting part is almost never the splitting. It is the combine step, because that is where the real work and the running time live. Merge sort's combine can count inversions for free. The closest-pair combine is an argument about geometry. And matrix exponentiation's combine turns n steps into about log n.

  • Use matrix exponentiation on any linear recurrence

The shape, and the Master Theorem

Why learn this as a separate idea? Because a lot of fast algorithms share one shape. Merge sort, binary search, quickselect, fast power and closest pair all cut the input into pieces, solve the pieces, and glue the answers together. Once you see the shape, you can reuse the same two questions on every new problem: how do I split it? and how cheaply can I combine? Interviewers also like asking you to state and justify the running time of a recursive function, and this section gives you the tool for that.

The cost of a divide-and-conquer algorithm is written as a recurrence: a formula that gives the cost for size n in terms of the cost for smaller sizes. It looks like this:

T(n) = a · T(n/b) + f(n)

You make a smaller problems, each of size n/b, and do f(n) work to split and combine. The Master Theorem compares f(n) with n^(log_b a), which is the total work at the leaves (the smallest pieces, at the bottom of the recursion). Whichever of the two is bigger decides the answer.

Where does n^(log_b a) come from? Each level multiplies the number of pieces by a and divides their size by b. You reach size 1 after log_b n levels, so the bottom level has a^(log_b n) pieces. A log identity rewrites that as n^(log_b a). For merge sort, a = b = 2, so there are n^1 = n leaves, one per element, which matches what you would draw by hand.

The ε (epsilon) in the table below just means "by a real polynomial margin", such as n^0.5 against n^1. A gap of only a log factor, like n against n log n, does not count, and the basic theorem does not cover that case.

A worked example. Take merge sort on n = 8, so T(n) = 2T(n/2) + n:

  • Level 0: one piece of size 8. Merging costs 8.
  • Level 1: two pieces of size 4. Merging costs 4 + 4 = 8.
  • Level 2: four pieces of size 2. Merging costs 2 + 2 + 2 + 2 = 8.
  • Level 3: eight pieces of size 1. Nothing to merge; these are the leaves.

Every level costs 8 = n, and there are log₂ 8 = 3 levels that do work. So the total is n · log n = 24. That is case 2. Compare binary search, T(n) = T(n/2) + 1: one piece per level, cost 1 each, log n levels, so O(log n).

My convention: draw the level sums instead of quoting the theorem

The Master Theorem is a shortcut for an argument you can always do by hand, and doing it by hand is more reliable. Ask two questions:

  • How much work is on level k? That is a^k · f(n/b^k).
  • How many levels are there? That is log_b n.

Then look at how those per-level totals change as you go down. If they stay the same, multiply one level by the number of levels. If they keep growing by a fixed factor, the bottom level decides the answer. If they keep shrinking by a fixed factor, the top level decides it. That covers all three Master cases, plus the cases where the theorem does not apply, such as T(n) = T(n−1) + n or splits into uneven pieces.

Merge sort's combine: counting inversions

Chapter 8 built merge sort. Here is the payoff. An inversion is a pair of positions that are out of order: i < j but a[i] > a[j]. The number of inversions tells you how far from sorted an array is. The merge step already has this information, and pulling it out costs one line.

For example, [3, 1, 2] has two inversions: (3, 1) and (3, 2). A sorted array has zero. A reversed array of n elements has the most possible, n(n−1)/2, because every pair is out of order. Checking every pair directly is O(n²). The point of this section is to do it in O(n log n).

A small dry run of the merge. Suppose the two sorted halves are L = [2, 5] and R = [1, 3, 4].

  1. Compare 2 and 1. Take 1 from the right. Both 2 and 5 are still in L and both are bigger than 1, so add 2. Count = 2.
  2. Compare 2 and 3. Take 2 from the left. Nothing is counted when you take from the left.
  3. Compare 5 and 3. Take 3 from the right. Only 5 is left in L, so add 1. Count = 3.
  4. Compare 5 and 4. Take 4 from the right. Add 1 for the 5. Count = 4.
  5. R is empty. Copy 5. Final: [1, 2, 3, 4, 5], with 4 cross-half inversions: (2,1), (5,1), (5,3), (5,4).

Notice that you never compared 5 with 1 directly. The sorted order of L told you that if 2 beats 1, so does everything after 2. That is where the speed comes from.

countInversions — merge sort plus one lineO(n log n)O(n)
// An INVERSION is a pair i < j with a[i] > a[j].
// Key observation: when merging and we take a[j] from the RIGHT half,
// every element still remaining in the LEFT half is greater than it —
// and each of those is an inversion. That count is (mid - i + 1).
void merge(vector<int> &a,int lo,int mid,int hi,vector<int> &temp,long long &count){
	int i=lo;
	int j=mid+1;
	int k=lo;

	while(i<=mid and j<=hi){
		if(a[i]<=a[j]){
			temp[k++]=a[i++];
		}else{
			count+=mid-i+1;      // THE one added line
			temp[k++]=a[j++];
		}
	}

	while(i<=mid)temp[k++]=a[i++];
	while(j<=hi)temp[k++]=a[j++];

	for(int x=lo;x<=hi;x++)
	a[x]=temp[x];
}
void sortCount(vector<int> &a,int lo,int hi,vector<int> &temp,long long &count){
	if(lo>=hi)return;

	int mid=lo+(hi-lo)/2;

	sortCount(a,lo,mid,temp,count);
	sortCount(a,mid+1,hi,temp,count);
	merge(a,lo,mid,hi,temp,count);
}
long long countInversions(vector<int> a){     // by value: we sort a copy
	vector<int> temp(a.size());
	long long count=0;
	sortCount(a,0,a.size()-1,temp,count);

	return count;
}
long long is not optional here. The most inversions an array can have is n(n−1)/2. For n = 10⁵ that is about 5 × 10⁹, far beyond what a 32-bit int holds. Why no inversion is missed: for any inverted pair, there is exactly one level of the recursion where its two elements land in different halves. That is the level where the merge compares them and counts the pair. So each inversion is counted once, and none is skipped.
🔢
The same trick, four problems
  • Count inversions: the version above.
  • Reverse pairs (a[i] > 2·a[j]): the same structure, but you count with a separate two-pointer scan before merging. The condition is no longer "everything still left in the left half".
  • Count of smaller numbers after self: merge indices instead of values, so each count can be credited to the right original position.
  • Count range sums in [lower, upper]: build prefix sums (Chapter 6), then use two pointers during the merge to count the pairs that qualify.

You can also solve all four with a Fenwick tree (BIT) over compressed values (Chapter 24). Merge sort is usually easier to get right. The Fenwick tree is usually faster.

Quickselect: find the Kth without sorting

Quicksort splits the array around a pivot, then works on both sides. Quickselect only needs one element, the Kth smallest, so it works on just the side that contains it and throws the other away. That single change turns O(n log n) into O(n) on average.

Why would you want this? "Find the median", "find the Kth largest" and "find the K closest points" all come up often. Sorting answers them in O(n log n), but it does far more work than needed: it puts every element in place when you only care about one position.

A tiny trace. Find the element at index k = 2 (the third smallest) in [7, 2, 9, 4, 1]. Say the random pivot is 4. After partitioning, everything ≤ 4 sits on the left: [2, 1, 4, 7, 9], and 4 lands at index 2. That equals k, so the answer is 4, after one pass of 5 elements. If k had been 4, you would drop the left part and the pivot, and keep only [7, 9] at indices 3 and 4. Partition again with pivot 7: 7 lands at index 3, which is less than 4, so keep only [9], where the next partition places 9 at index 4. The answer is 9. The left and right parts are never sorted internally. They only need to be on the correct side of the pivot.

Edge cases the code handles: k is 0-indexed, so "Kth largest" in an array of n becomes k = n − K. Duplicates are fine because the partition puts values equal to the pivot on the left. A range of one element is its own pivot and lands where it is.

quickselect — Kth smallest in expected O(n)O(n) expected, O(n²) worstO(1)
// Lomuto partition with a random pivot (Chapter 8).
int partition(vector<int> &a,int lo,int hi){
	int r=lo+rand()%(hi-lo+1);
	swap(a[r],a[hi]);

	int pivot=a[hi];
	int i=lo-1;

	for(int j=lo;j<hi;j++){
		if(a[j]<=pivot){
			i++;
			swap(a[i],a[j]);
		}
	}

	swap(a[i+1],a[hi]);

	return i+1;
}

// Iterative, so there is no recursion at all — O(1) space.
int quickselect(vector<int> &a,int k){      // k is 0-indexed
	int lo=0;
	int hi=a.size()-1;

	while(lo<=hi){
		int p=partition(a,lo,hi);

		if(p==k)return a[p];        // the pivot landed exactly on k

		if(p<k)lo=p+1;              // recurse into ONE side only
		else hi=p-1;
	}

	return -1;
}
// std::nth_element does exactly this. Use it unless asked to implement it.
Why it is O(n) on average: with a random pivot, each round throws away a steady fraction of what is left. So the work adds up to n + n/2 + n/4 + … = 2n. That is a shrinking series, unlike quicksort, which does n work on each of log n levels. The worst case is still O(n²) if the pivots are consistently terrible. Median-of-medians guarantees O(n), but its constant overhead is so large that random quickselect is faster in practice.

Matrix exponentiation: a logarithm from a recurrence

A linear recurrence is a rule where each term is a fixed combination of the previous few, like Fibonacci's F(n) = F(n−1) + F(n−2). Any such rule can be written as multiplying by a matrix. Then fast power (Chapter 48) gets you the nth term with about log n matrix multiplications, instead of n additions one at a time.

Why a matrix works. Keep the last two terms together as a pair, (F(n), F(n−1)). The next pair is (F(n) + F(n−1), F(n)). Both new values are sums of the old ones, with fixed coefficients: the first uses 1 and 1, the second uses 1 and 0. Those coefficients are the rows of the matrix [[1,1],[1,0]]. So one multiplication by that matrix moves the pair one step forward, and n multiplications move it n steps. Check it: start from (F(1), F(0)) = (1, 0). One step gives (1·1 + 1·0, 1·1 + 0·0) = (1, 1), which is (F(2), F(1)). Another gives (2, 1), which is (F(3), F(2)).

Why only log n multiplications. Matrix multiplication is associative, so M^8 can be built as M → M² → M⁴ → M⁸: three squarings instead of seven multiplications. For a power that is not a power of two, write it in binary. 13 is 1101 in binary, which is 8 + 4 + 1, so M^13 = M^8 · M^4 · M^1. The loop in matpow walks the bits of p from lowest to highest, squaring M each time and multiplying it into the result when the bit is 1. The number of loop steps is the number of bits, about log₂ p.

Fibonacci in O(log n)O(k³ log n)O(k²)
// The transition:  [F(n+1)]   [1 1] [F(n)  ]
//                  [F(n)  ] = [1 0] [F(n-1)]
// So M^n applied to the base vector gives F(n). Exponentiate by squaring.
const long long MOD=1000000007;

vector<vector<long long>> multiply(vector<vector<long long>> &A,vector<vector<long long>> &B){
	int k=A.size();
	vector<vector<long long>> C(k,vector<long long>(k,0));

	for(int i=0;i<k;i++){
		for(int j=0;j<k;j++){
			for(int x=0;x<k;x++){
				C[i][j]=(C[i][j]+A[i][x]*B[x][j])%MOD;
			}
		}
	}

	return C;
}
// Exponentiation by squaring: M^13 = M^8 * M^4 * M^1, read off the bits of 13.
vector<vector<long long>> matpow(vector<vector<long long>> M,long long p){
	int k=M.size();
	vector<vector<long long>> result(k,vector<long long>(k,0));

	for(int i=0;i<k;i++)
	result[i][i]=1;                    // identity matrix

	while(p>0){
		if(p&1)result=multiply(result,M);
		M=multiply(M,M);
		p>>=1;
	}

	return result;
}
long long fib(long long n){
	if(n<=1)return n;

	vector<vector<long long>> M={{1,1},{1,0}};
	auto R=matpow(M,n-1);

	return R[0][0];                     // F(n)
}
This is what makes "F(10¹⁸) mod p" possible at all. The simple O(n) loop would never finish. The same trick works for any rule of the form f(n) = c₁f(n−1) + … + c_k f(n−k): build the k×k matrix for it and raise it to a power. It also counts paths of length exactly n in a graph. Take the adjacency matrix to the nth power, and entry (i,j) is that count. That is a surprising and genuinely useful fact.

When to reach for it, and when not. Each multiplication of two k×k matrices costs k³ steps, which is where O(k³ log n) comes from. For Fibonacci, k = 2, so each matrix product is 8 number multiplications, and n = 10¹⁸ needs only about 60 loop steps (60 bits). If n is at most around 10⁷, the plain loop is simpler and fast enough, so use that. If k is large, say 200, then k³ is 8 × 10⁶ per product. With up to two products per bit and 60 bits, that is close to 10⁹ operations, which is too slow for a typical time limit. The signal in a problem statement is a huge n (10¹² or more) together with a rule that only looks back a small, fixed number of steps.

Closest pair of points

📐
The combine step is the whole algorithm — and it is a geometric argument

The problem: given n points, find the two that are closest together. Sort the points by x, split them at the middle, and find the closest pair in each half the same way. Let d be the smaller of those two distances. The only pairs not yet checked are those with one point on each side of the dividing line. Any such pair closer than d must sit inside a vertical strip of width 2d around the line.

You might worry that the strip could hold all n points, making the combine O(n²). It does not matter: sort the strip's points by y, and compare each one with at most the next 7. Why 7? Cover the strip with d × d squares. No square can hold two points closer than d, because both would be in the same half, where d is already the smallest distance. So a 2d × d area holds at most 8 points, counting the current one.

So the combine is O(n) once things are sorted, giving T(n) = 2T(n/2) + O(n) = O(n log n), which is Master case 2. Sort the points by y once at the start, instead of sorting the strip at every level. Otherwise the combine becomes O(n log n) and the total becomes O(n log² n).

The brute-force answer checks all n(n−1)/2 pairs, which is about 5 × 10⁹ comparisons at n = 10⁵. Divide and conquer brings that to roughly n log n ≈ 1.7 × 10⁶ steps. The same "only a few neighbours can be close" argument shows up in collision detection, clustering, and map apps that find nearby places.

Edge cases to handle:

  • Tiny ranges. When a piece has 3 or fewer points, compare every pair directly. Splitting further would leave a half with one point and no pair at all.
  • Duplicate points. Two identical points have distance 0. That is a valid answer, and the algorithm finds it, so do not skip them.
  • Many points with the same x. Split by position in the x-sorted list (the middle index), not by the x value, so both halves stay non-empty.
  • Overflow. Compare squared distances with long long. With coordinates between −10⁹ and 10⁹, dx² + dy² can reach 8 × 10¹⁸. That still fits in a signed 64-bit integer (the limit is about 9.2 × 10¹⁸), but not in 32 bits. Take the square root only once, at the end, if the problem asks for the real distance.

🪄
Karatsuba and Strassen: the trick is always "do fewer subproblems"

Multiplying two n-digit numbers the school way is O(n²). If you split each number into two halves, the school method needs four half-size products. That gives T(n) = 4T(n/2) + O(n) = O(n²): no gain.

Karatsuba gets the same result with only three products. It uses the fact that the middle term equals (a+b)(c+d) − ac − bd. Now T(n) = 3T(n/2) + O(n), which gives O(n^log₂3) = O(n^1.585). Strassen does the same kind of thing for matrices, using seven multiplications instead of eight.

A small example with 2-digit numbers: 12 × 34. Split them as a = 1, b = 2 and c = 3, d = 4, so the product is ac·100 + (ad + bc)·10 + bd. The school way computes all four of ac, ad, bc, bd. Karatsuba computes only ac = 3, bd = 8 and (a+b)(c+d) = 3 × 7 = 21. The middle term is 21 − 3 − 8 = 10. So the answer is 3·100 + 10·10 + 8 = 408, using three multiplications. The exponent comes straight from the Master Theorem: a = 3, b = 2, so the leaves cost n^(log₂3), and log₂3 ≈ 1.585.

The pattern: cutting a, the number of subproblems, changes the exponent. Cutting f(n) usually does not. That is exactly what the n^(log_b a) term in the Master Theorem is telling you.

🎯
When divide and conquer is not the right frame
  • The subproblems overlap. Then it is DP, not divide and conquer. The key difference is that D&C pieces are disjoint: they share nothing (Chapter 38).
  • The combine step is as hard as the original problem. If merging the halves costs as much as solving the whole thing, splitting gained you nothing.
  • The split is lopsided and cannot be fixed. T(n) = T(n−1) + O(n) is O(n²), which is just a loop in disguise.
  • One pass through the data is enough. Maximum subarray is the classic trap. There is a neat O(n log n) divide-and-conquer solution, but Kadane's algorithm does it in O(n) with three lines.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 WORK IN MERGE
The interesting divide-and-conquer algorithms do their real work in the combine step. If combining is trivial, you probably just have a loop.
💡 MASTER THEOREM
T(n) = 2T(n/2) + O(n) is O(n log n); + O(1) is O(n). Recognising those two shapes covers nearly every recurrence you will meet.
💡 BINARY EXPONENTIATION
Any associative operation applied n times is O(log n) by squaring — integers, matrices, even string hashes. One loop, endless reuse.
⚠️
Common mistakes
  • Using int for an inversion count. It can reach n(n−1)/2 ≈ 5 × 10⁹ at n = 10⁵.
  • Creating the merge buffer inside merge. That is an O(n) allocation on every call. Create it once in the outer function (Chapter 8).
  • Recursing into both sides in quickselect. That is quicksort: O(n log n) instead of O(n).
  • A fixed pivot in quickselect or quicksort. Already-sorted input then becomes the O(n²) worst case.
  • Re-sorting the strip by y at every level of closest pair. Sort once at the start, or you pay an extra log factor.
  • Using the Master Theorem on uneven splits such as T(n) = T(n/3) + T(2n/3) + n. Add up the work per level instead.
  • Getting the starting value wrong in matpow. Start from the identity matrix, not a zero matrix.
  • Taking the modulus too late in matrix multiplication. A[i][x] * B[x][j] with values near 10⁹ overflows even a 64-bit total if you add many of them first. Reduce inside the loop.
  • Using divide and conquer where one pass works. Maximum subarray is Kadane in O(n).
  • Not noticing overlapping subproblems. That is the sign of DP, not of D&C.

Interview drill

Warm-up: Count inversions in an array. Then explain why the counting is complete.

How a strong answer sounds
I run merge sort and add one line inside the merge. Here is the key point. When the merge takes an element from the right half because it is smaller, every element still left in the left half is bigger than it. All of those came from earlier positions in the original array, so each one forms an inversion. So at that moment I add mid - i + 1, where i is the left pointer. That is O(n log n) time and O(n) space for the buffer. I would use long long, because the count can reach n(n−1)/2, about 5 × 10⁹ at n = 10⁵, which overflows a 32-bit int. Why no inversion is missed: take any inverted pair (i, j). There is exactly one level of the recursion where those two positions first land in different halves, because the splits are nested and never overlap. At that level the merge compares them. Since a[i] > a[j], the right element is taken first and the pair is counted. At lower levels they sit in different blocks that are never merged against each other. At higher levels they are in the same block but already in sorted order relative to each other. So every inversion is counted exactly once. The same skeleton with a different counting rule solves reverse pairs, count-of-smaller-after-self and count-of-range-sums. The alternative is a Fenwick tree over compressed values: usually faster, and usually easier to get wrong.

Deeper: Why is quickselect O(n) expected while quicksort is O(n log n)?

How a strong answer sounds
Both split the array around a pivot in O(n). The difference is what happens next. Quicksort recurses into both sides, so every level of the recursion still touches all n elements. With log n levels, that is Θ(n log n). Quickselect can tell from the pivot's final position which side holds the kth element. So it throws the other side away and recurses into one. With a random pivot, on average a fixed fraction (less than all) of the elements survives each round. So the work is n + n/2 + n/4 + …, a shrinking series that adds up to about 2n. That makes it Θ(n) on average. As recurrences: T(n) = T(n/2) + O(n) instead of 2T(n/2) + O(n). The Master Theorem puts the first in case 3, where the top level dominates, and the second in case 2, where every level costs the same. The worst case is still O(n²) if the pivot is always the smallest or largest. That is why the pivot must be random: always picking the first or last element makes already-sorted input the worst case. A median-of-medians version guarantees O(n), but its overhead is large enough that random quickselect wins in practice. In real C++ I would just call std::nth_element, which does exactly this, unless the point of the question is to write it myself.

🧠 Key takeaways

  • T(n) = a·T(n/b) + f(n): compare f(n) with n^(log_b a). Or just add up the work per level and see whether it grows, shrinks or stays the same.
  • Merge sort's combine counts inversions with one line, because an element taken from the right half is out of order with everything still left on the left.
  • Quickselect recurses into one side only. That turns log n levels of n work into a shrinking series: O(n) on average.
  • Matrix exponentiation makes any linear recurrence O(log n). Powers of the adjacency matrix count paths of a fixed length.
  • Karatsuba and Strassen win by cutting the number of subproblems, which is what changes the exponent.

T(n) = 2T(n/2) + O(n) solves to what, and why?

Master case 2: n^(log₂2) = n matches f(n) = n. The work is spread evenly across levels, so you multiply by the number of levels. This is merge sort. For n = 8 the levels cost 8, 8 and 8, a total of 24 = 8 · log₂ 8.

In the counting merge, why add mid - i + 1 when taking an element from the right half?

The left half is sorted. So if a[i] > a[j], every element from i to mid is bigger than a[j]. All of them came from earlier positions, so each forms an inversion with a[j].

Why is quickselect expected O(n) while quicksort is O(n log n)?

T(n) = T(n/2) + O(n) versus 2T(n/2) + O(n). Throwing away one side each round turns log n levels of full work into a shrinking sum. Both still need a random pivot to avoid O(n²).

Karatsuba multiplication beats the schoolbook method because it…

Cutting a, the number of subproblems, is what changes the exponent, because the leaf term is n^(log_b a). Strassen does the same for matrices, using seven multiplications instead of eight.

What distinguishes divide and conquer from dynamic programming?

Merge sort's halves never share an element, so caching results would gain nothing. When the recursion tree contains the same call twice, that is the sign to use DP (Chapter 11).
