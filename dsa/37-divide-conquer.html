Divide & Conquer

Split the problem, solve the pieces recursively, combine. The interesting part is almost never the splitting — it is the combine step, because that is where the algorithm's real work and its complexity live. Merge sort's combine counts inversions for free; the closest-pair combine is an argument about geometry; and matrix exponentiation's combine turns a linear recurrence into a logarithm.

  • Use the Master Theorem to solve a recurrence in seconds
  • Count inversions and reverse pairs with one extra line inside merge
  • Write quickselect and explain its expected O(n) bound
  • Apply matrix exponentiation to any linear recurrence
  • Recognise when divide and conquer is not the right frame

The shape, and the Master Theorem

A divide-and-conquer algorithm has a recurrence of the form:

T(n) = a · T(n/b) + f(n)

with a subproblems of size n/b, plus f(n) work to split and combine. The Master Theorem compares f(n) against n^(log_b a) — the total work at the leaves — and whichever dominates wins.

CaseConditionResultIntuition
1f(n) = O(n^(log_b a − ε))T(n) = Θ(n^(log_b a))The leaves dominate — most work is at the bottom
2f(n) = Θ(n^(log_b a))T(n) = Θ(n^(log_b a) · log n)Every level costs the same, and there are log n levels
3f(n) = Ω(n^(log_b a + ε))T(n) = Θ(f(n))The root dominates — the top-level combine is the whole cost

My convention: draw the level sums instead of quoting the theorem

The Master Theorem is a shortcut for an argument you can always do by hand, and doing it by hand is more reliable. Ask two questions: how much work is on level k? (that is a^k · f(n/b^k)) and how many levels are there? (that is log_b n). Then see whether the level sums are growing, shrinking or constant. Constant → multiply by the number of levels. Growing geometrically → the last level dominates. Shrinking geometrically → the first level dominates. That covers all three Master cases and also the cases the theorem does not apply to, such as T(n) = T(n−1) + n or unequal splits.

Merge sort's combine: counting inversions

Chapter 8 built merge sort. Here is the payoff: the merge step already knows something valuable, and extracting it costs one line.

countInversions — merge sort plus one lineO(n log n)O(n)
// An INVERSION is a pair i < j with a[i] > a[j].
// Key observation: when merging and we take a[j] from the RIGHT half,
// every element still remaining in the LEFT half is greater than it —
// and each of those is an inversion. That count is (mid - i + 1).
void merge(vector<int> &a,int lo,int mid,int hi,vector<int> &temp,long long &count){
	int i=lo;
	int j=mid+1;
	int k=lo;

	while(i<=mid and j<=hi){
		if(a[i]<=a[j]){
			temp[k++]=a[i++];
		}else{
			count+=mid-i+1;      // THE one added line
			temp[k++]=a[j++];
		}
	}

	while(i<=mid)temp[k++]=a[i++];
	while(j<=hi)temp[k++]=a[j++];

	for(int x=lo;x<=hi;x++)
	a[x]=temp[x];
}
void sortCount(vector<int> &a,int lo,int hi,vector<int> &temp,long long &count){
	if(lo>=hi)return;

	int mid=lo+(hi-lo)/2;

	sortCount(a,lo,mid,temp,count);
	sortCount(a,mid+1,hi,temp,count);
	merge(a,lo,mid,hi,temp,count);
}
long long countInversions(vector<int> a){     // by value: we sort a copy
	vector<int> temp(a.size());
	long long count=0;
	sortCount(a,0,a.size()-1,temp,count);

	return count;
}
long long is not optional here. The maximum number of inversions is n(n−1)/2, which for n = 10⁵ is about 5 × 10⁹ — well past a 32-bit int. Why the counting is complete: every inversion has its two elements end up in different halves at exactly one level of the recursion, and that is the level where it gets counted. So each inversion is counted once and none is missed.
🔢
The same trick, four problems
  • Count inversions — the version above.
  • Reverse pairs (a[i] > 2·a[j]) — same structure, but the count is a separate two-pointer scan before merging, since the condition is no longer "everything remaining".
  • Count of smaller numbers after self — merge indices rather than values, so you can attribute each count to the right original position.
  • Count range sums in [lower, upper] — build prefix sums (Chapter 6), then count qualifying pairs during the merge with two pointers.

All four are also solvable with a Fenwick tree over compressed values (Chapter 24). Merge sort is usually easier to get right; the BIT is usually faster.

Quickselect: find the Kth without sorting

Quicksort partitions and recurses into both halves. Quickselect recurses into only the half containing the answer — and that single change turns O(n log n) into expected O(n).

quickselect — Kth smallest in expected O(n)O(n) expected, O(n²) worstO(1)
// Lomuto partition with a random pivot (Chapter 8).
int partition(vector<int> &a,int lo,int hi){
	int r=lo+rand()%(hi-lo+1);
	swap(a[r],a[hi]);

	int pivot=a[hi];
	int i=lo-1;

	for(int j=lo;j<hi;j++){
		if(a[j]<=pivot){
			i++;
			swap(a[i],a[j]);
		}
	}

	swap(a[i+1],a[hi]);

	return i+1;
}

// Iterative, so there is no recursion at all — O(1) space.
int quickselect(vector<int> &a,int k){      // k is 0-indexed
	int lo=0;
	int hi=a.size()-1;

	while(lo<=hi){
		int p=partition(a,lo,hi);

		if(p==k)return a[p];        // the pivot landed exactly on k

		if(p<k)lo=p+1;              // recurse into ONE side only
		else hi=p-1;
	}

	return -1;
}
// std::nth_element does exactly this. Use it unless asked to implement it.
Why expected O(n): with a random pivot the expected split discards a constant fraction each round, so the work is n + n/2 + n/4 + … = 2n — a geometric series, unlike quicksort's log n levels of n work each. The worst case is still O(n²) with adversarially bad pivots; median-of-medians gives a guaranteed O(n) but with a constant factor so large that randomised quickselect beats it in practice.

Matrix exponentiation: a logarithm from a recurrence

Any linear recurrence can be written as a matrix multiplication, and then fast power (Chapter 48) computes the nth term in O(log n) matrix multiplies instead of n additions.

Fibonacci in O(log n)O(k³ log n)O(k²)
// The transition:  [F(n+1)]   [1 1] [F(n)  ]
//                  [F(n)  ] = [1 0] [F(n-1)]
// So M^n applied to the base vector gives F(n). Exponentiate by squaring.
const long long MOD=1000000007;

vector<vector<long long>> multiply(vector<vector<long long>> &A,vector<vector<long long>> &B){
	int k=A.size();
	vector<vector<long long>> C(k,vector<long long>(k,0));

	for(int i=0;i<k;i++){
		for(int j=0;j<k;j++){
			for(int x=0;x<k;x++){
				C[i][j]=(C[i][j]+A[i][x]*B[x][j])%MOD;
			}
		}
	}

	return C;
}
// Exponentiation by squaring: M^13 = M^8 * M^4 * M^1, read off the bits of 13.
vector<vector<long long>> matpow(vector<vector<long long>> M,long long p){
	int k=M.size();
	vector<vector<long long>> result(k,vector<long long>(k,0));

	for(int i=0;i<k;i++)
	result[i][i]=1;                    // identity matrix

	while(p>0){
		if(p&1)result=multiply(result,M);
		M=multiply(M,M);
		p>>=1;
	}

	return result;
}
long long fib(long long n){
	if(n<=1)return n;

	vector<vector<long long>> M={{1,1},{1,0}};
	auto R=matpow(M,n-1);

	return R[0][0];                     // F(n)
}
This is what makes "F(10¹⁸) mod p" tractable — impossible with the O(n) iterative version. The technique generalises to any recurrence f(n) = c₁f(n−1) + … + c_k f(n−k): build the k×k companion matrix and raise it. It also counts paths of length exactly n in a graph, since the (i,j) entry of the adjacency matrix to the nth power is exactly that count — which is a genuinely surprising and useful fact.

Closest pair of points

📐
The combine step is the whole algorithm — and it is a geometric argument

Sort by x, split at the median, and recursively find the closest pair in each half. Let d be the better of the two. The only pairs not yet considered are those straddling the dividing line, and any such pair closer than d must lie within a vertical strip of width 2d around it.

The naive worry is that the strip could contain all n points, making the combine O(n²). It cannot help you: sort the strip's points by y, and each one needs to be compared with at most the next 7. Why 7? Pack the strip into d × d squares; no square can contain two points closer than d (they are within the same half, where d is already the minimum), so a 2d × d region holds at most 8 points including the current one.

So the combine is O(n) after sorting, giving T(n) = 2T(n/2) + O(n) = O(n log n) — Master case 2. Keep the points pre-sorted by y once at the start rather than sorting the strip at every level, or the combine becomes O(n log n) and the total O(n log² n).

🪄
Karatsuba and Strassen: the trick is always "do fewer subproblems"

Multiplying two n-digit numbers naively is O(n²). Split each into halves and the schoolbook method needs four products, giving T(n) = 4T(n/2) + O(n) = O(n²) — no gain. Karatsuba computes the same result with three products, using the identity that the middle term is (a+b)(c+d) − ac − bd, and T(n) = 3T(n/2) + O(n) gives O(n^log₂3) = O(n^1.585). Strassen does the analogous thing for matrices, replacing eight multiplications with seven. The pattern is that reducing a — the number of subproblems — changes the exponent, while reducing f(n) usually does not. That is exactly what the Master Theorem's n^(log_b a) term is telling you.

🎯
When divide and conquer is not the right frame
  • The subproblems overlap. Then it is DP, not divide and conquer — the defining difference is that D&C subproblems are disjoint (Chapter 38).
  • The combine step is as hard as the original problem. If you cannot merge the halves in less than the total work, the split bought nothing.
  • The split is unbalanced and cannot be fixed. T(n) = T(n−1) + O(n) is O(n²), which is just a loop in disguise.
  • A single sweep suffices. Maximum subarray is the classic trap: there is an elegant O(n log n) divide-and-conquer solution, and Kadane's algorithm does it in O(n) with three lines.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 WORK IN MERGE
The interesting divide-and-conquer algorithms do their real work in the combine step. If combining is trivial, you probably just have a loop.
💡 MASTER THEOREM
T(n) = 2T(n/2) + O(n) is O(n log n); + O(1) is O(n). Recognising those two shapes covers nearly every recurrence you will meet.
💡 BINARY EXPONENTIATION
Any associative operation applied n times is O(log n) by squaring — integers, matrices, even string hashes. One loop, endless reuse.
⚠️
Common mistakes
  • Using int for an inversion count. Up to n(n−1)/2 ≈ 5 × 10⁹ at n = 10⁵.
  • Allocating the merge buffer inside merge. An O(n) allocation per call; allocate once in the driver (Chapter 8).
  • Recursing into both sides in quickselect. That is quicksort — O(n log n) instead of O(n).
  • A fixed pivot in quickselect or quicksort. Sorted input becomes the O(n²) worst case.
  • Re-sorting the strip by y at every level of closest-pair. Pre-sort once, or you pay an extra log factor.
  • Applying the Master Theorem to unequal splits such as T(n) = T(n/3) + T(2n/3) + n. Draw the level sums instead.
  • Forgetting the base case in matpow. The identity matrix, not a zero matrix.
  • Taking the modulus too late in matrix multiplication. A[i][x] * B[x][j] with values near 10⁹ overflows a 64-bit accumulator if you sum many of them first — reduce inside the loop.
  • Using divide and conquer where a sweep works. Maximum subarray is Kadane in O(n).
  • Not noticing overlapping subproblems. That is the DP signal, not a D&C one.

Interview drill

Warm-up: Count inversions in an array. Then explain why the counting is complete.

How a strong answer sounds
I run merge sort and add one line inside the merge. The observation is that when the merge takes an element from the right half because it is smaller, every element still remaining in the left half is greater than it — and since all of those sit at earlier original indices, each forms an inversion. So I add mid - i + 1 at that moment, where i is the left pointer. That is O(n log n) time and O(n) space for the buffer, and I would use long long because the maximum inversion count is n(n−1)/2, about 5 × 10⁹ at n = 10⁵, which overflows a 32-bit int. On completeness: take any inverted pair (i, j). At some level of the recursion those two indices are first separated into different halves — there is exactly one such level, since the splits are nested and disjoint — and at that level the merge compares them, and because a[i] > a[j] the right element is taken first and the pair is counted. Below that level they are in the same half and never compared across; above it they are in the same block but already sorted relative to each other. So every inversion is counted exactly once and none is missed. The same skeleton with a different counting rule solves reverse pairs, count-of-smaller-after-self, and count-of-range-sums. A Fenwick tree over coordinate-compressed values is the alternative — usually faster, and usually easier to get wrong.

Deeper: Why is quickselect O(n) expected while quicksort is O(n log n)?

How a strong answer sounds
Both partition around a pivot in O(n). The difference is what happens next: quicksort recurses into both sides, so every level of the recursion still touches all n elements, and with log n levels that is Θ(n log n). Quickselect knows which side contains the kth element from the pivot's final index, so it discards the other side entirely and recurses into one. With a random pivot the expected surviving fraction is a constant below one, so the work is n + n/2 + n/4 + … — a geometric series summing to about 2n, hence expected Θ(n). Written out, the recurrence is T(n) = T(n/2) + O(n) rather than 2T(n/2) + O(n), and the Master Theorem puts the first in case 3 where the root dominates, and the second in case 2 where every level costs the same. The worst case is still O(n²) if the pivot is always extreme, which is why the pivot must be randomised — a fixed first-or-last pivot makes already-sorted input the worst case. There is a median-of-medians variant with a guaranteed O(n) bound, but its constant factor is large enough that randomised quickselect wins in practice. And in real C++ I would just call std::nth_element, which is exactly this, unless the point of the question is to implement it.

🧠 Key takeaways

  • T(n) = a·T(n/b) + f(n): compare f(n) with n^(log_b a) — or just sum the work per level and see whether it grows, shrinks or stays constant.
  • Merge sort's combine counts inversions with one line, because a right-half element inverts with everything remaining on the left.
  • Quickselect recurses into one side only, turning log n levels of n work into a geometric series — expected O(n).
  • Matrix exponentiation makes any linear recurrence O(log n), and adjacency-matrix powers count fixed-length paths.
  • Karatsuba and Strassen win by reducing the number of subproblems, which is what moves the exponent.

Check your understanding

T(n) = 2T(n/2) + O(n) solves to what, and why?

Master case 2: n^(log₂2) = n matches f(n) = n, so the work is spread evenly and you multiply by the number of levels. This is merge sort.

In the counting merge, why add mid - i + 1 when taking an element from the right half?

The left half is sorted, so if a[i] > a[j] then every element from i to mid exceeds a[j]. Since all of those have smaller original indices, each forms an inversion with a[j].

Why is quickselect expected O(n) while quicksort is O(n log n)?

T(n) = T(n/2) + O(n) versus 2T(n/2) + O(n). Discarding a side each round collapses log n levels of full work into a geometric sum. Both still need a random pivot to avoid O(n²).

Karatsuba multiplication beats the schoolbook method because it…

Reducing a — the number of subproblems — is what moves the exponent, since the leaf term is n^(log_b a). Strassen does the same for matrices, replacing eight multiplications with seven.

What distinguishes divide and conquer from dynamic programming?

Merge sort's halves never share an element, so memoising it would buy nothing. When the recursion tree contains the same argument twice, that is the DP signal (Chapter 11).
