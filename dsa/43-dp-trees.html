DP on Trees

Tree DP is the cleanest DP there is, because the recursion tree and the actual tree are the same object — there is no table, no loop order to get right, and no risk of reading an unfilled cell. Post-order traversal is the fill order. What makes it feel hard is a single structural habit: learning to separate what a subtree reports upward from the answer that happens to pass through this node.

  • Write the post-order DP template: children first, combine at the parent
  • Separate the return value from the running answer — the diameter pattern
  • Return multiple values from one traversal (include/exclude states)
  • Run tree DP on a general graph given as an adjacency list
  • Reroot a tree DP to get every node's answer in O(N)

The template

Every tree DP is the same three lines: recurse into the children, combine their reports into your own report, return it. Because a child is always solved before its parent, post-order is the topological order of the dependency DAG — you get the correct fill order for free, which is exactly what Chapters 41 and 42 had to arrange by hand.

the shape every tree DP takesO(N)O(h) stack
// The helper carries all mutable state by reference; the driver owns it.
// No globals — the same discipline as every other traversal in this course.
int solve(TreeNode *root,int &ans){
	if(!root)return 0;            // the empty-subtree base case

	int left=solve(root->left,ans);   // children FIRST
	int right=solve(root->right,ans);

	// 1. the answer that PASSES THROUGH this node — update the running best
	ans=max(ans,left+right+1);

	// 2. what this subtree REPORTS to its parent — usually a single chain
	return 1+max(left,right);
}

int driver(TreeNode *root){
	int ans=0;

	solve(root,ans);

	return ans;
}
Those two numbered lines are the entire chapter. They are usually different quantities, and conflating them is the one mistake that accounts for most failed tree-DP attempts. The parent cannot use "a path that bends at my child" — it can only extend a straight chain — so the bent answer must be recorded in ans and the straight one returned. Notice also that the helper takes ans by reference rather than using a member or global: the state stays visible at the call site, and the function remains safe to call twice.
✍️
My convention: helper takes state by reference, driver owns it

This is the same split I use for every traversal — solve(node, ans) plus a tiny driver that declares ans and returns it. Three reasons it matters more here than usual: a global ans silently breaks the second call on the same tree (a real failure in judge harnesses that reuse the process); passing by reference makes it obvious at the call site which quantity is accumulated rather than returned; and when the problem later wants the answer for a different root, the driver is the only thing that changes. Guard clause first, one line, unbraced: if(!root)return 0; — and get that base case right, because it is where the recursion actually terminates.

Diameter of a binary tree
// The diameter is the number of EDGES on the longest path between any two
// nodes. That path may bend at its highest node — which is exactly why the
// helper cannot simply return the answer.
int height(TreeNode *root,int &ans){
	if(!root)return 0;

	int left=height(root->left,ans);
	int right=height(root->right,ans);

	ans=max(ans,left+right);       // path BENDING here: down-left, back up, down-right

	return 1+max(left,right);      // a single chain is all the parent can extend
}

int diameterOfBinaryTree(TreeNode *root){
	int ans=0;

	height(root,ans);

	return ans;
}

Counting edges, not nodes, so left+right with no +1. If the problem asks for nodes, the bent path has left+right+1 and the base case still returns 0. Decide which you are counting before writing the line, and sanity-check on a single node — a lone node has diameter 0 in edges, 1 in nodes.

Maximum path sum
// Same skeleton, but values may be NEGATIVE — so a child that would only
// hurt us is clamped away with max(...,0), meaning "do not take that branch".
int gain(TreeNode *root,int &ans){
	if(!root)return 0;

	int left=max(gain(root->left,ans),0);
	int right=max(gain(root->right,ans),0);

	ans=max(ans,root->val+left+right);   // bending here

	return root->val+max(left,right);      // one chain upward
}

int maxPathSum(TreeNode *root){
	int ans=INT_MIN;                // NOT 0 — every value may be negative

	gain(root,ans);

	return ans;
}

Two changes that both matter. max(...,0) clamps a harmful branch — you are never forced to extend into it, since a path may stop at this node. And ans starts at INT_MIN: initialising to 0 returns 0 for a tree of all-negative values, which is wrong because a path must contain at least one node. The clamp goes on the child, the sentinel goes on the answer — mixing those up is the standard bug here.

Returning several values: the include/exclude pattern

When a node's best choice depends on whether its parent took something, one number is not enough state. Return a pair: the best if this node is used, and the best if it is not. This is the tree version of the two-state DP from Chapter 39's house robber.

house robber III — cannot rob a node and its childO(N)O(h)
// Returns {robThis, skipThis}:
//   robThis  = best total for this subtree WHEN this node is robbed
//   skipThis = best total for this subtree when it is NOT robbed
// One traversal, two numbers — no memo map needed, because each node is
// visited exactly once and reports both cases at once.
pair<int,int> solve(TreeNode *root){
	if(!root)return {0,0};

	auto [robL,skipL]=solve(root->left);
	auto [robR,skipR]=solve(root->right);

	// rob this node -> both children MUST be skipped
	int robThis=root->val+skipL+skipR;

	// skip this node -> each child is free to do whatever is best for it
	int skipThis=max(robL,skipL)+max(robR,skipR);

	return {robThis,skipThis};
}

int rob(TreeNode *root){
	auto [robRoot,skipRoot]=solve(root);

	return max(robRoot,skipRoot);
}
skipThis takes a max per child, robThis does not. Skipping a node imposes no constraint downward, so each child independently picks its better case; robbing it forbids both children, so there is no choice to make. Writing skipThis = skipL + skipR is the classic error — it silently forbids grandchildren too and quietly under-counts. The structured binding auto [robL,skipL]= keeps the two meanings named rather than .first / .second, which matters when four of them are in scope at once.
🎛️
How many values does the node need to report?

The rule is the same as choosing a DP state anywhere: report exactly what the parent cannot recompute for itself.

When the tuple grows past three or four, define a small struct with named fields instead of a tuple. Readability is a correctness feature here — a mis-ordered tuple element compiles fine and produces nonsense.

Tree DP on a general graph

Trees in graph problems arrive as an adjacency list with no parent pointers and no designated root. Two adjustments: pick any root (node 0 will do — every node of a tree is a valid root), and pass the parent down so the recursion does not walk back up the edge it came from.

subtree sizes and subtree sums on an adjacency listO(N)O(N)
// A tree with N nodes has N-1 undirected edges and no cycles, so a "visited"
// array is not needed — remembering the parent is enough to avoid going back.
void dfs(int node,int parent,unordered_map<int,vector<int>> &graph,
         vector<int> &size,vector<long long> &sum,vector<int> &value){
	size[node]=1;
	sum[node]=value[node];

	for(auto &neighbour:graph[node]){
		if(neighbour==parent)continue;   // the only guard a tree needs

		dfs(neighbour,node,graph,size,sum,value);

		size[node]+=size[neighbour];      // combine AFTER the child returns
		sum[node]+=sum[neighbour];
	}
}

void driver(int N,vector<vector<int>> &edges,vector<int> &value){
	unordered_map<int,vector<int>> graph;

	for(auto &e:edges){
		graph[e[0]].push_back(e[1]);
		graph[e[1]].push_back(e[0]);   // -> This is for Undirected Edges
	}

	vector<int> size(N,0);
	vector<long long> sum(N,0);

	dfs(0,-1,graph,size,sum,value);   // root anywhere; -1 = "no parent"
}
if(neighbour==parent)continue; replaces the visited array — acyclicity means the parent edge is the only way back. One caveat: with duplicate edges or a self-loop this is not a tree and the guard is insufficient, so if the input is merely claimed to be a tree, verify edges.size()==N-1 and connectivity first (Chapter 27). Note too that size and sum are accumulated after the recursive call returns — that ordering is the post-order, and moving the two lines above the call yields zeros.
📏
Recursion depth on a path-shaped tree

A tree DP recurses to depth h. For a balanced tree that is about log N and harmless, but a tree given as a chain of 10⁵ nodes means 10⁵ stack frames, and each frame here holds several references plus a loop iterator. That will overflow the default 1 MB stack on many judges. Options, in order of preference: raise the stack limit if the environment allows; convert to an explicit iterative post-order with your own stack (Chapter 16); or process nodes in reverse BFS order, which is a valid post-order because a node's BFS layer is always lower than its children's. The last option is usually the smallest change — one BFS to record the order, then a reverse loop doing the combine.

Rerooting: every node's answer in O(N)

The natural tree DP answers a question about the subtree of a fixed root. Some problems want the answer for every node as the root — for example, the sum of distances from each node to all others. Running the DP N times is O(N²). Rerooting gets it in two passes by observing that moving the root across one edge changes the answer by a known amount.

sum of distances in a tree — the two-pass rerootO(N)O(N)
// Pass 1 (post-order): count[node] = subtree size,
//                      ans[node]   = sum of distances WITHIN node's subtree.
void down(int node,int parent,unordered_map<int,vector<int>> &graph,
          vector<int> &count,vector<int> &ans){
	count[node]=1;

	for(auto &neighbour:graph[node]){
		if(neighbour==parent)continue;

		down(neighbour,node,graph,count,ans);

		count[node]+=count[neighbour];
		// every node in the child's subtree is one edge further from us
		ans[node]+=ans[neighbour]+count[neighbour];
	}
}

// Pass 2 (pre-order): convert each subtree answer into the WHOLE-TREE answer.
// Moving the root from `parent` to `node`:
//   count[node] nodes get one step CLOSER   -> subtract count[node]
//   N-count[node] nodes get one step FURTHER -> add N-count[node]
void up(int node,int parent,int N,unordered_map<int,vector<int>> &graph,
        vector<int> &count,vector<int> &ans){
	for(auto &neighbour:graph[node]){
		if(neighbour==parent)continue;

		ans[neighbour]=ans[node]-count[neighbour]+(N-count[neighbour]);

		up(neighbour,node,N,graph,count,ans);
	}
}

vector<int> sumOfDistancesInTree(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;

	for(auto &e:edges){
		graph[e[0]].push_back(e[1]);
		graph[e[1]].push_back(e[0]);
	}

	vector<int> count(N,0);
	vector<int> ans(N,0);

	down(0,-1,graph,count,ans);
	up(0,-1,N,graph,count,ans);

	return ans;
}
The highlighted line is the whole technique. Pass 1 is an ordinary post-order DP; pass 2 is a pre-order that pushes a correct global answer downward, because ans[node] is already global by the time we reach it (the root's subtree answer is the whole tree). Down then up, post-order then pre-order — that pairing is the rerooting signature, and it applies to any quantity where you can express the effect of shifting the root across one edge. Watch for overflow: a chain of 3·10⁴ nodes already pushes the distance sum past 32-bit range, so use long long when N is large.
🌲
The two ways to find a tree's diameter

On a general (unweighted) tree there is a second, prettier method: BFS from any node to find the farthest node u, then BFS from u — the greatest distance found is the diameter. It is O(N), needs no DP, and the endpoint u is genuinely an endpoint of some diameter. But it relies on non-negative, uniform-ish edges: it is false on graphs with cycles and false with negative weights, whereas the DP version works on any tree including weighted ones (replace 1+ with w+). Knowing both, and knowing which assumption each needs, is a good thing to say aloud — the double-BFS is the answer interviewers usually want for an unweighted tree, and the DP is what generalises.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 POST-ORDER IS FREE
On a tree the recursion order is the topological order, so there is no fill order to arrange. That is why tree DP is the easiest DP.
💡 RETURN A PAIR
When the choice depends on what the parent did, return two values — used and not-used. House robber III, max independent set and the camera problem are all this shape.
⛔ SKIP FREES CHILDREN
Skipping a node imposes nothing downward, so each child takes its own max. Writing skipL + skipR silently forbids the grandchildren too.
⚠️
Common mistakes
  • Returning the bent answer. A parent can only extend a straight chain; the bent path belongs in ans.
  • Combining before the recursive call returns. The accumulate lines must follow the call — that is the post-order.
  • Initialising max path sum's ans to 0. With all-negative values the answer is negative; start at INT_MIN.
  • Clamping the answer instead of the child. max(child,0) means "skip that branch"; clamping ans loses negative answers.
  • skipThis = skipL + skipR in house robber III — skipping a node frees the children, so each takes its own max.
  • Mixing edges and nodes in diameter. Verify on a single node: 0 edges, 1 node.
  • Forgetting if(neighbour==parent)continue; on an adjacency list, giving infinite recursion.
  • Using the parent guard when the input is not really a tree. Duplicate edges or a self-loop defeat it; check N-1 edges and connectivity.
  • Stack overflow on a path-shaped tree. h can be N; use reverse BFS order or an explicit stack.
  • Running the DP from every root when rerooting gives O(N) instead of O(N²).
  • Overflow in subtree sums and distance sums. Use long long once N passes a few thousand.

Interview drill

Warm-up: Diameter of a binary tree. Explain why the helper returns something different from the answer.

How a strong answer sounds
I would write a post-order helper returning the height of a subtree, and pass a running answer by reference. At each node, after recursing into both children, there are two distinct quantities. The first is the best path that bends at this node: it goes down into the left subtree, comes back up through this node, and descends into the right, so its edge count is left + right — and that is a candidate for the global answer, so I fold it into ans with a max. The second is what this subtree can offer its parent, which is only 1 + max(left, right), because a path passing through my parent enters my subtree once and must leave the way it came; it cannot use both of my branches. That asymmetry is exactly why the return value and the answer are different things, and conflating them is the classic failure on this problem — you get the height where you wanted the diameter. Complexity is O(N) time, since each node is visited once, and O(h) space for the recursion stack, which is O(log N) balanced but O(N) for a chain. Two details I would check explicitly: whether the problem counts edges or nodes, since a single node has diameter 0 in edges and 1 in nodes; and, on a large chain-shaped input, whether the recursion depth is safe — if not, I would do one BFS to get a layer order and iterate it in reverse, which is a valid post-order without recursion. And for an unweighted general tree I would mention the alternative: BFS from any node to find the farthest node, then BFS from there. Same O(N), no DP, but it does not survive negative or non-uniform weights the way the DP does.

Deeper: Given a tree, return for every node the sum of distances from it to all other nodes. N is 3·10⁴.

How a strong answer sounds
The naive approach is a BFS or DFS from every node, which is O(N²) — at 3·10⁴ that is around 10⁹ operations, too slow. The right technique is rerooting, in two passes. Pass one is an ordinary post-order DP from an arbitrary root, say node 0, computing count[node], the size of the subtree, and ans[node], the sum of distances from node to everything inside its own subtree. The combine is ans[node] += ans[child] + count[child], because every node in the child's subtree is exactly one edge further from me than it is from the child — that extra edge is counted once per node, hence + count[child]. After pass one, ans[0] is already the true global answer for the root, since the root's subtree is the whole tree. Pass two is a pre-order that propagates that correctness downward. Consider moving the root from a node to its child c: the count[c] nodes in c's subtree each get one step closer, and the other N − count[c] nodes each get one step further. So ans[c] = ans[node] − count[c] + (N − count[c]). Because I visit in pre-order, ans[node] is already the global value when I compute ans[c], so each node is fixed exactly once. Two passes, O(N) time and O(N) space. Two things I would watch: the distance sums need long long, since a chain of 3·10⁴ nodes gives roughly 4.5·10⁸ at the endpoint and intermediate sums exceed 32-bit range; and the recursion depth is N in the worst case, so on a chain-shaped input I would switch to an iterative order rather than risk a stack overflow. The general pattern — post-order down, then pre-order up, with a formula for the effect of shifting the root across one edge — reroots any tree DP where that per-edge effect is expressible.

🧠 Key takeaways

  • Post-order traversal is the fill order for free — the recursion tree is the dependency DAG.
  • Separate what you report upward (a straight chain) from the answer through this node (which may bend into both children).
  • Return a pair or small struct when one number is insufficient state — include/exclude, height+flag, BST bounds.
  • On an adjacency list, root anywhere and pass the parent; if(neighbour==parent)continue; replaces visited.
  • Rerooting answers "for every node as root" in O(N): post-order down, then pre-order up with a per-edge adjustment.

Check your understanding

In the diameter DP, why does the helper return 1 + max(left, right) rather than left + right?

This asymmetry between "what I report" and "the answer through me" is the core of tree DP. Returning the bent value gives you a number that no parent can legitimately extend.

In maximum path sum, what does max(gain(child), 0) accomplish?

Clamping goes on the child, never on ans — the final answer can and should be negative when every value is. That is also why ans starts at INT_MIN.

House robber III: the value reported for "this node is skipped" is…

Only robbing a node forbids its children. Writing skipL + skipR silently forbids the grandchildren as well and under-counts.

On a tree given as an adjacency list, why is a visited array unnecessary?

Correct provided the input really is a tree — a duplicate edge or self-loop defeats the parent guard, so if the shape is only claimed, check N-1 edges and connectivity first.

Rerooting: moving the root from a node to its child c changes the distance sum by…

Each of the count[c] nodes below c loses an edge and each of the other N−count[c] gains one. Because the pass is pre-order, ans[node] is already global when the child is computed — which is what makes two passes enough.
