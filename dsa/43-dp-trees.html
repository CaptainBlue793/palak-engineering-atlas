DP on Trees

Tree DP is the cleanest DP there is. The recursion follows the tree itself, so there is no table, no loop order to get right, and no risk of reading an empty cell. Post-order traversal (visit the children first, then the node) is the fill order. What makes it feel hard is one habit you have to learn: keep what a subtree reports up to its parent separate from the answer that passes through this node.

  • Write the post-order DP template: children first, combine at the parent
  • Keep the return value separate from the running answer — the diameter pattern
  • Return several values from one traversal (e.g. "this node used" / "not used")
  • Run tree DP on a tree given as an adjacency list (a list of neighbours per node)
  • Reroot a tree DP to get the answer for every node in O(N)

The template

Why learn this as its own topic? Because a large share of "hard" tree questions in interviews — diameter, maximum path sum, cameras, robbing houses on a tree, distances from every node — are one idea used again and again: each subtree hands its parent a small summary, and the parent builds its own summary from those. Once you see that, the problems stop looking different from each other.

Every tree DP is the same three steps: recurse into the children, combine their reports into your own report, and return it. A child is always solved before its parent. So post-order already visits things in dependency order (its "topological order"). You get the correct fill order for free — the thing Chapters 41 and 42 had to arrange by hand.

Compare this with the table DPs of the last chapters. There, the state was an index like dp[i][j], and you had to pick loop directions so every cell you read was already filled. Here, the state is simply "the subtree rooted at this node". The recursion cannot reach a node until it has finished both children, so the cells you read are always ready. There is also no memo table: each node is visited exactly once, so nothing is ever computed twice.

the shape every tree DP takesO(N)O(h) stack
// The helper carries all mutable state by reference; the driver owns it.
// No globals — the same discipline as every other traversal in this course.
int solve(TreeNode *root,int &ans){
	if(!root)return 0;            // the empty-subtree base case

	int left=solve(root->left,ans);   // children FIRST
	int right=solve(root->right,ans);

	// 1. the answer that PASSES THROUGH this node — update the running best
	ans=max(ans,left+right+1);

	// 2. what this subtree REPORTS to its parent — usually a single chain
	return 1+max(left,right);
}

int driver(TreeNode *root){
	int ans=0;

	solve(root,ans);

	return ans;
}
Those two numbered lines are the whole chapter. They are usually different values. Mixing them up causes most failed tree-DP attempts. The parent cannot use "a path that bends at my child" — it can only extend a straight chain. So the bent answer is recorded in ans, and the straight one is returned. Notice also that the helper takes ans by reference instead of using a member or global variable. The state stays visible where you call it, and the function is safe to call twice.
✍️
My convention: helper takes state by reference, driver owns it

I use this split for every traversal: solve(node, ans), plus a tiny driver that declares ans and returns it. It matters even more here, for three reasons:

  • A global ans quietly breaks the second call on the same tree. This really happens on online judges that reuse the process.
  • Passing by reference makes it obvious where you call it which value is collected and which is returned.
  • If the problem later wants the answer for a different root, only the driver changes.

Put the guard clause first, on one line, without braces: if(!root)return 0;. Get that base case right — it is where the recursion actually stops.

Diameter: the return value is not the answer

The diameter of a tree is the length of the longest path between any two nodes. Every such path has one highest node, where it turns from going up to going down. So if each node can say "what is the longest path that turns at me?", the diameter is the largest of those answers. That is why we check every node, and why the answer lives in a separate variable instead of being returned.

Here is a dry run on a five-node tree, counting edges. Node 1 is the root, with children 2 and 3. Node 2 has children 4 and 5.

Visit orderleft, rightThrough this node (left+right)Reports up (1+max)ans
4 (leaf)0, 0010
5 (leaf)0, 0010
21, 12 (path 4–2–5)22
3 (leaf)0, 0012
1 (root)2, 13 (path 4–2–1–3)33

Look at node 2. The two numbers happen to match (2 and 2), but they mean different things. "Through" is the bent path 4–2–5. "Reports up" is a straight chain: the edge from the parent down to 2, then one more edge down to 4. The root can only use the straight one. If node 2 had handed up the bent path, the root would attach the edge 1–2 to it — and a shape where node 2 touches 4, 5 and 1 is a fork, not a path. The final answer 3 happens to bend at the root here; in another tree the best bend could be at any node deep inside, which is why every node gets to update ans.

Diameter of a binary tree
// The diameter is the number of EDGES on the longest path between any two
// nodes. That path may bend at its highest node — which is exactly why the
// helper cannot simply return the answer.
int height(TreeNode *root,int &ans){
	if(!root)return 0;

	int left=height(root->left,ans);
	int right=height(root->right,ans);

	ans=max(ans,left+right);       // path BENDING here: down-left, back up, down-right

	return 1+max(left,right);      // a single chain is all the parent can extend
}

int diameterOfBinaryTree(TreeNode *root){
	int ans=0;

	height(root,ans);

	return ans;
}

We are counting edges, not nodes, so it is left+right with no +1. If the problem asks for nodes, the bent path has left+right+1, and the base case still returns 0. Decide which one you are counting before writing the line. Then check it on a single node: a lone node has diameter 0 in edges, 1 in nodes.

Maximum path sum
// Same skeleton, but values may be NEGATIVE — so a child that would only
// hurt us is clamped away with max(...,0), meaning "do not take that branch".
int gain(TreeNode *root,int &ans){
	if(!root)return 0;

	int left=max(gain(root->left,ans),0);
	int right=max(gain(root->right,ans),0);

	ans=max(ans,root->val+left+right);   // bending here

	return root->val+max(left,right);      // one chain upward
}

int maxPathSum(TreeNode *root){
	int ans=INT_MIN;                // NOT 0 — every value may be negative

	gain(root,ans);

	return ans;
}

Two changes, and both matter. First, max(...,0) drops a branch that would only lower the sum. You never have to extend into it, because a path may stop at this node. Second, ans starts at INT_MIN. Starting at 0 returns 0 for a tree where every value is negative. That is wrong, because a path must contain at least one node. The clamp goes on the child; the very small starting value goes on the answer. Mixing those up is the standard bug here.

Dry run: root −10 with children 9 and 20; node 20 has children 15 and 7. The leaves report 9, 15 and 7. At 20: through = 20+15+7 = 42, reports 20+max(15,7) = 35. At −10: through = −10+9+35 = 34, reports 25. So ans = 42, the path 15–20–7. It never touches the root, because adding the root would cost 10.

Returning several values: the include/exclude pattern

Sometimes a node's best choice depends on what its parent did. Then one number is not enough. Return a pair: the best total if this node is used, and the best total if it is not. This is the tree version of the two-state house robber DP from Chapter 39.

house robber III — cannot rob a node and its childO(N)O(h)
// Returns {robThis, skipThis}:
//   robThis  = best total for this subtree WHEN this node is robbed
//   skipThis = best total for this subtree when it is NOT robbed
// One traversal, two numbers — no memo map needed, because each node is
// visited exactly once and reports both cases at once.
pair<int,int> solve(TreeNode *root){
	if(!root)return {0,0};

	auto [robL,skipL]=solve(root->left);
	auto [robR,skipR]=solve(root->right);

	// rob this node -> both children MUST be skipped
	int robThis=root->val+skipL+skipR;

	// skip this node -> each child is free to do whatever is best for it
	int skipThis=max(robL,skipL)+max(robR,skipR);

	return {robThis,skipThis};
}

int rob(TreeNode *root){
	auto [robRoot,skipRoot]=solve(root);

	return max(robRoot,skipRoot);
}
skipThis takes a max per child; robThis does not. Skipping a node puts no rule on its children, so each child picks its own better case. Robbing a node forbids both children, so there is no choice to make. Writing skipThis = skipL + skipR is the classic error. It quietly forbids the grandchildren too, and the total comes out too low. The structured binding auto [robL,skipL]= gives the two values real names instead of .first / .second. That matters when four of them are around at once.

Why can't a single number work here? Suppose each node only reported "the best total for my subtree". The parent would not know whether that best total used the child itself. If it did, the parent is not allowed to rob. If it didn't, the parent is. One number hides exactly the fact the parent needs, so the child reports both versions and lets the parent choose.

Dry run on the tree [3, 2, 3, null, 3, null, 1]: root 3; its left child 2 has a right child 3; its right child 3 has a right child 1. Pairs are written {rob, skip}.

  1. Leaf 3 (under the 2): {3, 0}. Leaf 1: {1, 0}.
  2. Node 2: rob = 2 + 0 + 0 = 2 (its only child must be skipped, worth 0). Skip = max(3, 0) = 3. Report {2, 3}.
  3. Node 3 (right child): rob = 3 + 0 = 3. Skip = max(1, 0) = 1. Report {3, 1}.
  4. Root 3: rob = 3 + skipL 3 + skipR 1 = 7. Skip = max(2, 3) + max(3, 1) = 6.

The answer is max(7, 6) = 7: rob the root and the two grandchildren (3 + 3 + 1). Notice the root's "rob" line used the children's skip values, which already include the grandchildren. That is how the pair carries information two levels up without ever looking at a grandchild directly.

The rule is the same as for choosing any DP state: report exactly what the parent cannot work out for itself.

Once you need more than three or four values, define a small struct with named fields instead of a tuple. Here, easy-to-read code is also correct code — tuple elements in the wrong order still compile, and silently give nonsense.

Tree DP on a general graph

In graph problems, a tree usually arrives as an adjacency list: for each node, a list of its neighbours. There are no parent pointers and no chosen root. You need two changes. First, pick any root — node 0 will do, since any node of a tree can be the root. Second, pass the parent down, so the recursion does not walk back up the edge it came from.

subtree sizes and subtree sums on an adjacency listO(N)O(N)
// A tree with N nodes has N-1 undirected edges and no cycles, so a "visited"
// array is not needed — remembering the parent is enough to avoid going back.
void dfs(int node,int parent,unordered_map<int,vector<int>> &graph,
         vector<int> &size,vector<long long> &sum,vector<int> &value){
	size[node]=1;
	sum[node]=value[node];

	for(auto &neighbour:graph[node]){
		if(neighbour==parent)continue;   // the only guard a tree needs

		dfs(neighbour,node,graph,size,sum,value);

		size[node]+=size[neighbour];      // combine AFTER the child returns
		sum[node]+=sum[neighbour];
	}
}

void driver(int N,vector<vector<int>> &edges,vector<int> &value){
	unordered_map<int,vector<int>> graph;

	for(auto &e:edges){
		graph[e[0]].push_back(e[1]);
		graph[e[1]].push_back(e[0]);   // -> This is for Undirected Edges
	}

	vector<int> size(N,0);
	vector<long long> sum(N,0);

	dfs(0,-1,graph,size,sum,value);   // root anywhere; -1 = "no parent"
}
if(neighbour==parent)continue; replaces the visited array. A tree has no cycles, so the edge to the parent is the only way back. One warning: with duplicate edges or a self-loop, the input is not a tree, and this check is not enough. If the input is only said to be a tree, first check edges.size()==N-1 and that everything is connected (Chapter 27). Also note that size and sum are added up after the recursive call returns. That ordering is what makes it post-order. Move those two lines above the call and you get zeros.

A small check: 4 nodes with values [5, 1, 2, 4] and edges 0–1, 0–2, 1–3, rooted at 0. Node 3 is a leaf: size 1, sum 4. Node 1 adds its child 3: size 2, sum 1+4 = 5. Node 2 is a leaf: size 1, sum 2. Node 0 adds both children: size 1+2+1 = 4, sum 5+5+2 = 12, which is the total of all values, as it must be for the root. When you are unsure whether the order is right, this "root equals the whole tree" check is a quick test.

📏
Recursion depth on a path-shaped tree

A tree DP recurses as deep as the tree's height h. For a balanced tree that is about log N, which is harmless. But a tree shaped like a chain of 10⁵ nodes means 10⁵ stack frames, and each frame here holds several references plus a loop iterator. That will overflow the default 1 MB stack on many judges. Your options, best first:

  • raise the stack limit, if the environment allows it;
  • rewrite it as a loop-based post-order with your own stack (Chapter 16);
  • process nodes in reverse BFS order. This is a valid post-order, because a node's BFS layer number is always smaller than its children's.

The last option is usually the smallest change: one BFS to record the order, then a reverse loop that does the combine step.

Rerooting: every node's answer in O(N)

A normal tree DP answers a question about the tree hanging from one fixed root. Some problems want the answer with every node as the root — for example, the sum of distances from each node to all the others. Running the DP N times costs O(N²). Rerooting does it in two passes. The key fact: moving the root across one edge changes the answer by an amount you can calculate.

sum of distances in a tree — the two-pass rerootO(N)O(N)
// Pass 1 (post-order): count[node] = subtree size,
//                      ans[node]   = sum of distances WITHIN node's subtree.
void down(int node,int parent,unordered_map<int,vector<int>> &graph,
          vector<int> &count,vector<int> &ans){
	count[node]=1;

	for(auto &neighbour:graph[node]){
		if(neighbour==parent)continue;

		down(neighbour,node,graph,count,ans);

		count[node]+=count[neighbour];
		// every node in the child's subtree is one edge further from us
		ans[node]+=ans[neighbour]+count[neighbour];
	}
}

// Pass 2 (pre-order): convert each subtree answer into the WHOLE-TREE answer.
// Moving the root from `parent` to `node`:
//   count[node] nodes get one step CLOSER   -> subtract count[node]
//   N-count[node] nodes get one step FURTHER -> add N-count[node]
void up(int node,int parent,int N,unordered_map<int,vector<int>> &graph,
        vector<int> &count,vector<int> &ans){
	for(auto &neighbour:graph[node]){
		if(neighbour==parent)continue;

		ans[neighbour]=ans[node]-count[neighbour]+(N-count[neighbour]);

		up(neighbour,node,N,graph,count,ans);
	}
}

vector<int> sumOfDistancesInTree(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;

	for(auto &e:edges){
		graph[e[0]].push_back(e[1]);
		graph[e[1]].push_back(e[0]);
	}

	vector<int> count(N,0);
	vector<int> ans(N,0);

	down(0,-1,graph,count,ans);
	up(0,-1,N,graph,count,ans);

	return ans;
}
The highlighted line is the whole technique. Pass 1 is an ordinary post-order DP. Pass 2 is a pre-order (node first, then children) that pushes the correct full-tree answer downward. It works because ans[node] is already the full-tree answer by the time we reach it (the root's subtree is the whole tree). Post-order first, then pre-order — that pairing is the sign of rerooting. It works for any value where you can write down how it changes when the root moves across one edge. Watch for overflow: a chain of 3·10⁴ nodes already pushes the distance sum past the 32-bit range, so use long long when N is large.

Where does the formula come from? Take a node p and its child c. Every other node is on one side of the edge p–c or the other. The count[c] nodes on c's side reach c one step sooner than they reach p. The remaining N − count[c] nodes reach c by going through p, so they need one extra step. Nothing else changes. So ans[c] = ans[p] − count[c] + (N − count[c]).

Dry run on the path 0–1–2–3 (N = 4), rooted at 0:

NodePass 1: countPass 1: ans (inside subtree)Pass 2: full answerCheck by hand
3104 − 1 + 3 = 63+2+1 = 6
220 + 1 = 14 − 2 + 2 = 42+1+1 = 4
131 + 2 = 36 − 3 + 1 = 41+1+2 = 4
043 + 3 = 66 (already correct)1+2+3 = 6

Pass 1 fills the table bottom-up (3, 2, 1, 0). Pass 2 goes top-down (0, 1, 2, 3), and each row uses the row above it. Edge cases to keep in mind: a single node (N = 1) has answer 0 and no edges, so both passes do nothing (graph[0] is simply empty); and the root choice does not matter — rooting at node 0 only works because the labels run from 0 to N−1, so node 0 always exists.

🌲
The two ways to find a tree's diameter

On a general tree without edge weights, there is a second, neater method: BFS from any node to find the farthest node u, then BFS again from u. The largest distance found is the diameter. It is O(N), needs no DP, and u really is one end of some longest path. But it relies on edges that are not negative and roughly equal: it fails on graphs with cycles, and it fails with negative weights. The DP version works on any tree, including weighted ones (replace 1+ with w+). It is worth saying out loud that you know both, and what each one assumes. Interviewers usually want the double-BFS for an unweighted tree; the DP is the one that extends to more cases.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 POST-ORDER IS FREE
On a tree the recursion order is the topological order, so there is no fill order to arrange. That is why tree DP is the easiest DP.
💡 RETURN A PAIR
When the choice depends on what the parent did, return two values — used and not-used. House robber III, max independent set and the camera problem are all this shape.
⛔ SKIP FREES CHILDREN
Skipping a node imposes nothing downward, so each child takes its own max. Writing skipL + skipR silently forbids the grandchildren too.
⚠️
Common mistakes
  • Returning the bent answer. A parent can only extend a straight chain; the bent path belongs in ans.
  • Combining before the recursive call returns. The lines that add up results must come after the call — that is the post-order.
  • Starting max path sum's ans at 0. If every value is negative, the answer is negative; start at INT_MIN.
  • Clamping the answer instead of the child. max(child,0) means "skip that branch"; clamping ans loses negative answers.
  • skipThis = skipL + skipR in house robber III — skipping a node frees its children, so each takes its own max.
  • Mixing up edges and nodes in diameter. Check on a single node: 0 edges, 1 node.
  • Forgetting if(neighbour==parent)continue; on an adjacency list, which causes infinite recursion.
  • Relying on the parent check when the input is not really a tree. Duplicate edges or a self-loop break it; check for N-1 edges and that everything is connected.
  • Stack overflow on a chain-shaped tree. h can be N; use reverse BFS order or your own stack.
  • Running the DP from every root when rerooting gives O(N) instead of O(N²).
  • Overflow in subtree sums and distance sums. Use long long once N passes a few thousand.

Interview drill

Warm-up: Diameter of a binary tree. Explain why the helper returns something different from the answer.

How a strong answer sounds
I would write a post-order helper that returns the height of a subtree, and pass a running answer by reference. At each node, after recursing into both children, there are two different values. The first is the best path that bends at this node. It goes down into the left subtree, comes back up through this node, and goes down into the right. Its edge count is left + right. That is a candidate for the overall answer, so I fold it into ans with a max. The second is what this subtree can offer its parent, which is only 1 + max(left, right). A path through my parent enters my subtree once and must leave the way it came, so it cannot use both of my branches. That difference is exactly why the return value and the answer are different things. Mixing them up is the classic failure here — you get the height when you wanted the diameter. It is O(N) time, since each node is visited once, and O(h) space for the recursion stack: O(log N) if balanced, O(N) for a chain. I would check two details. First, does the problem count edges or nodes? A single node has diameter 0 in edges and 1 in nodes. Second, on a large chain-shaped input, is the recursion depth safe? If not, I would do one BFS to get the layer order and loop over it in reverse, which is a valid post-order without recursion. For an unweighted general tree I would mention the alternative: BFS from any node to find the farthest node, then BFS from there. Same O(N), no DP — but unlike the DP, it breaks with negative or uneven weights.

Deeper: Given a tree, return for every node the sum of distances from it to all other nodes. N is 3·10⁴.

How a strong answer sounds
The naive approach is a BFS or DFS from every node. That is O(N²) — at 3·10⁴, around 10⁹ operations, which is too slow. The right technique is rerooting, in two passes. Pass one is an ordinary post-order DP from any root, say node 0. It computes count[node], the size of the subtree, and ans[node], the sum of distances from node to everything inside its own subtree. The combine step is ans[node] += ans[child] + count[child]. Every node in the child's subtree is exactly one edge further from me than from the child, and that extra edge counts once per node — hence + count[child]. After pass one, ans[0] is already the true answer for the root, because the root's subtree is the whole tree. Pass two is a pre-order that pushes that correct answer downward. Think about moving the root from a node to its child c. The count[c] nodes in c's subtree each get one step closer. The other N − count[c] nodes each get one step further. So ans[c] = ans[node] − count[c] + (N − count[c]). Because I visit in pre-order, ans[node] is already correct when I compute ans[c], so each node is fixed exactly once. Two passes, O(N) time and O(N) space. I would watch two things. The distance sums need long long: a chain of 3·10⁴ nodes gives about 4.5·10⁸ at the end node, and sums along the way go past the 32-bit range. And the recursion depth is N in the worst case, so on a chain-shaped input I would switch to a loop-based order rather than risk a stack overflow. The general pattern — post-order first, then pre-order, with a formula for how the answer changes when the root moves across one edge — reroots any tree DP where you can write that formula.

🧠 Key takeaways

  • Post-order traversal gives you the fill order for free — children are always solved before their parent.
  • Keep what you report upward (a straight chain) separate from the answer through this node (which may bend into both children).
  • Return a pair or a small struct when one number is not enough — used/not used, height + flag, BST bounds.
  • On an adjacency list, pick any root and pass the parent down; if(neighbour==parent)continue; replaces visited.
  • Rerooting answers "for every node as the root" in O(N): a post-order pass, then a pre-order pass that adjusts the answer across each edge.

Check your understanding

In the diameter DP, why does the helper return 1 + max(left, right) rather than left + right?

This difference between "what I report" and "the answer through me" is the heart of tree DP. If you return the bent value, no parent can validly extend it.

In maximum path sum, what does max(gain(child), 0) accomplish?

The clamp goes on the child, never on ans. When every value is negative, the final answer can and should be negative. That is also why ans starts at INT_MIN.

House robber III: the value reported for "this node is skipped" is…

Only robbing a node forbids its children. Writing skipL + skipR quietly forbids the grandchildren as well, so the total comes out too low.

On a tree given as an adjacency list, why is a visited array unnecessary?

This is correct only if the input really is a tree. A duplicate edge or a self-loop breaks the parent check. If you are only told it is a tree, first check for N-1 edges and that everything is connected.

Rerooting: moving the root from a node to its child c changes the distance sum by…

Each of the count[c] nodes below c loses an edge and each of the other N−count[c] gains one. Because the pass is pre-order, ans[node] is already the full-tree answer when the child is computed. That is why two passes are enough.
