Geometry & Randomisation

This chapter covers two small topics that share one habit: both swap a long list of special cases for a single formula.

In geometry, questions like "is this point to the left or right?", "do these two segments cross?" and "is this shape convex (no dents)?" all come down to one number: the sign of a cross product. Randomised algorithms use coin flips so that no particular input can force the slow case. You plan for the average run instead of the worst one, and you get simpler code that is fast almost every time.

  • Use the cross product for orientation, area and segment intersection
  • Build a convex hull with the monotone chain
  • Apply sweep line to intervals and to closest-pair problems
  • Sample from a stream with reservoir sampling
  • Use randomised quickselect for the k-th element in expected O(n)

The cross product answers everything

Why does geometry need a special tool at all? Because the obvious way to ask "which side of this line is the point on?" is to compute slopes and compare them. Slopes mean division. Division breaks on vertical lines (you divide by zero) and brings in rounding errors. The cross product answers the same question with two multiplications and a subtraction. No division, no special cases.

Here is where the formula comes from. Treat O as the origin, so you have two arrows: a = A − O and b = B − O. The cross product is a.x·b.y − a.y·b.x. It equals |a|·|b|·sin θ, where θ is the angle you turn through to go from arrow a to arrow b (counter-clockwise counts as positive). The lengths are never negative, so the sign comes only from sin θ. That is positive for a left turn (0° to 180°), negative for a right turn, and zero when the arrows point along the same line. The size, |a|·|b|·sin θ, is the area of the parallelogram the two arrows span, and a triangle is half a parallelogram.

A worked example, with O = (0,0) and A = (4,0). The ray O→A points right along the x-axis.

  • B = (1,3): cross = 4·3 − 0·1 = 12. Positive, so B is to the left (above the ray). The triangle's area is 12 / 2 = 6.
  • B = (1,−3): cross = 4·(−3) − 0·1 = −12. Negative, so B is to the right (below).
  • B = (2,0): cross = 4·0 − 0·2 = 0. B lies on the line through O and A.
orientation, area, and why you should stay in integersO(1)
// The 2D cross product of OA and OB. Its SIGN is the orientation and its
// MAGNITUDE is twice the triangle's area — two answers from one expression.
//   > 0  -> O, A, B turn counter-clockwise (B is left of the ray O->A)
//   < 0  -> clockwise (B is right)
//   == 0 -> collinear
struct Point{
	long long x;
	long long y;
};

long long cross(Point &O,Point &A,Point &B){
	return (A.x-O.x)*(B.y-O.y)-(A.y-O.y)*(B.x-O.x);
}

// Area of any simple polygon — the shoelace formula, which is just a sum of
// cross products around the boundary. Returns TWICE the area, kept as an
// integer so there is no rounding at all.
long long twiceArea(vector<Point> &poly){
	int n=poly.size();
	long long sum=0;

	for(int i=0;i<n;i++){
		int j=(i+1)%n;

		sum+=poly[i].x*poly[j].y-poly[j].x*poly[i].y;
	}

	return llabs(sum);          // the sign tells you the winding direction
}

// Squared distance — comparing distances needs NO square root, so this stays
// exact. Only take the root when the actual length must be reported.
long long dist2(Point &a,Point &b){
	long long dx=a.x-b.x;
	long long dy=a.y-b.y;

	return dx*dx+dy*dy;
}
Doing the maths in whole numbers (integers) is the most important habit in geometry. Watch the size, though. With coordinates up to 10⁴, a cross product reaches about 8·10⁸, which is fine. With coordinates up to 10⁹, it reaches 4·10¹⁸. That is close to the largest value a long long can hold, so check the limit. The payoff: direction tests become exact. "Are these three points on one straight line (collinear)?" gets a clear yes or no. With decimals (floats) you would have to guess with a small tolerance, called an epsilon. Every float you add is a future bug in an edge case, such as points that exactly touch or line up. So stay in integers, compare squared distances, and return twice the area.

The shoelace formula on a small example. Take the square with corners (0,0), (2,0), (2,2), (0,2), listed in order around the edge. Each pair of neighbours adds x_i·y_j − x_j·y_i:

  • (0,0) → (2,0): 0·0 − 2·0 = 0
  • (2,0) → (2,2): 2·2 − 2·0 = 4
  • (2,2) → (0,2): 2·2 − 0·2 = 4
  • (0,2) → (0,0), wrapping back to the start: 0·0 − 0·2 = 0

The sum is 8, which is twice the area. The real area is 4, which is right for a 2×2 square. Each term is the cross product of two corners as seen from the origin (the signed area of a triangle with a corner at (0,0)). Triangles that fall outside the polygon get counted once positive and once negative, so they cancel. The formula only works if the corners are listed in order around the boundary. If you shuffle them, the "polygon" crosses itself and the answer is meaningless.

Do two segments cross?

This is the classic test built from the sign. Segments AB and CD cross when C and D are on opposite sides of line AB, and A and B are on opposite sides of line CD. "Opposite sides" means the two cross products have opposite signs. You need both checks. One alone is not enough, because C and D can sit on opposite sides of the line AB while the segment CD passes beyond the end of A or B.

Example: A = (0,0), B = (4,4), C = (0,4), D = (4,0). These form an X.

  • cross(A,B,C) = 4·4 − 4·0 = 16, and cross(A,B,D) = 4·0 − 4·4 = −16. The signs are opposite, so C and D straddle AB.
  • cross(C,D,A) = 4·(−4) − (−4)·0 = −16, and cross(C,D,B) = 4·0 − (−4)·4 = 16. The signs are opposite, so A and B straddle CD.

Both checks pass, so the segments cross. The edge case is a zero. If one cross product is 0, an endpoint lies on the other segment's line. You then have to check whether it lies within the segment itself. That point is on the segment when its x is between the segment's two x values and its y is between the two y values. Forgetting this case is why "do segments intersect" problems fail on the touching and collinear tests.

✍️
My convention: one cross helper, then everything is its sign

I write cross(O, A, B) once, and I write all geometry logic with it. Every question becomes a sign check:

  • "Is the point left of the line?" is cross(...) > 0.
  • "Is the turn clockwise?" is < 0.
  • "Are the points on one line (collinear)?" is == 0.
  • "Is the polygon convex?" means all the cross products have the same sign.
  • "Is the point inside a triangle?" means three cross products have the same sign.

One helper plus a sign test keeps geometry code short enough to get right. The other way is a long chain of if checks on slopes. That needs special handling for vertical lines, and it still gets the tricky edge cases wrong. It is the same instinct as reusing one BFS loop for six different views of a tree: find the step the problems share, write it once, and change only what has to change.

Convex hull: monotone chain

Why build a hull? Many questions about a cloud of points depend only on its outer boundary. Examples: the two points farthest apart, the smallest fence that encloses every tree, or whether a new point falls outside the region. Once you have the hull, the points inside it can be ignored. The hull is usually much smaller than the full set, so later work is cheaper.

The key fact: walk along a convex boundary in one direction and every turn is a left turn (counter-clockwise). If three points in a row make a right turn, or go straight, the middle one is a dent. It cannot be on the hull. The algorithm keeps the points it has so far on a stack. Whenever the newest point creates a right turn, it pops the middle point.

convex hull — O(n log n)O(n log n)O(n)
// Andrew's monotone chain. Sort by x (then y), then walk twice: once left to
// right for the lower hull, once right to left for the upper. Each walk keeps
// a stack and pops any point that makes a non-counter-clockwise turn — because
// such a point lies inside the hull built so far.
vector<Point> convexHull(vector<Point> &points){
	int n=points.size();

	if(n<3)return points;

	sort(points.begin(),points.end(),[](Point &a,Point &b){
		if(a.x!=b.x)return a.x<b.x;

		return a.y<b.y;
	});

	vector<Point> hull;

	// lower hull, then upper hull — same loop, reversed traversal
	for(int pass=0;pass<2;pass++){
		int start=hull.size();

		for(int step=0;step<n;step++){
			int i=pass==0?step:n-1-step;

			while(hull.size()>=start+2 and
			      cross(hull[hull.size()-2],hull[hull.size()-1],points[i])<=0)
			hull.pop_back();

			hull.push_back(points[i]);
		}

		hull.pop_back();      // the last point starts the next chain
	}

	return hull;
}
This is a monotonic stack (Chapter 13), but it pops on a turn direction instead of a number comparison. Each point is pushed once and popped at most once. So the two walks are O(n), and the O(n log n) sort is the slowest part. Two choices are worth saying out loud:
  • <= 0 in the pop condition leaves out points that sit on a straight edge of the hull. Use < 0 if the problem wants them kept, and check which one it asks for.
  • The pass loop only exists so the same walk is not written twice. If the two halves differed in any way, I would write them out separately instead of forcing them into one loop. Reuse should never make code harder to read.

A dry run on five points: the corners of a 2×2 square, (0,0), (2,0), (2,2), (0,2), plus the centre (1,1). Sorted by x and then y, the order is (0,0), (0,2), (1,1), (2,0), (2,2).

  1. Lower walk, left to right. Push (0,0) and (0,2). Next comes (1,1). cross((0,0),(0,2),(1,1)) = 0·1 − 2·1 = −2. That is a right turn, so pop (0,2) and push (1,1).
  2. Next is (2,0). cross((0,0),(1,1),(2,0)) = 1·0 − 1·2 = −2. Another right turn, so pop (1,1) and push (2,0).
  3. Next is (2,2). cross((0,0),(2,0),(2,2)) = 2·2 − 0·2 = 4. A left turn, so push it. The stack is (0,0), (2,0), (2,2). Pop the last point, (2,2), because the upper walk will start with it.
  4. Upper walk, right to left, visiting (2,2), (2,0), (1,1), (0,2), (0,0). The pops remove (2,0) and then (1,1), because each one causes a right turn. The walk ends with (0,0), (2,0), (2,2), (0,2), (0,0). The final pop_back removes the repeated (0,0).

The result is the four corners in counter-clockwise order. The centre (1,1) is gone. Note that (0,2) was popped from the lower walk even though it is a corner. That is fine, because the upper walk adds it back. Each walk only has to get its own half right.

Edge cases the code handles: fewer than three points are returned as they are. If all the points are on one line, every turn is 0 and gets popped, so you end up with just the two end points. Duplicate points also give a cross product of 0 and get popped under <= 0. If you switch to < 0 to keep points on the edges, remove duplicates first.

Sweep line

Imagine a vertical line sliding across the page from left to right, stopping at each interesting point. That is a sweep line. It is the go-to method for problems about intervals, rectangles and events along a timeline: sort the endpoints, then visit them in order while keeping track of a small amount of information. This turns "compare every pair", which is O(n²), into O(n log n).

Why does sorting help so much? Once the intervals are sorted by start, anything that overlaps the current one must come right after it. You never have to look back. For example, [[1,3],[8,10],[2,6],[15,18]] sorts to [1,3], [2,6], [8,10], [15,18]. Here is the merge:

  • [2,6] starts at 2, which is ≤ 3 (the current end). It overlaps, so extend: [1,6].
  • [8,10] starts at 8, which is > 6. There is a gap, so start a new interval.
  • [15,18] starts at 15, which is > 10. Start another new one.

The answer is [1,6], [8,10], [15,18]. The comparison with the last merged interval is the only state you keep. That is the "small amount of information" a sweep carries.

Merge intervals
// Sort by start, then extend or emit. The archetypal sweep.
vector<vector<int>> merge(vector<vector<int>> &intervals){
	if(intervals.empty())return {};

	sort(intervals.begin(),intervals.end());

	vector<vector<int>> ans;

	ans.push_back(intervals[0]);

	for(int i=1;i<intervals.size();i++){
		if(intervals[i][0]<=ans.back()[1]){
			ans.back()[1]=max(ans.back()[1],
			                     intervals[i][1]);
		}else{
			ans.push_back(intervals[i]);
		}
	}

	return ans;
}

You must use max when extending the end. A later interval can sit entirely inside the current one. For example, [1,10] then [2,5]. Just copying its end would shrink the merged interval to [1,5]. That is the classic bug here.

Maximum overlap (events)
// "Most meetings at once", "minimum rooms needed", "maximum guests present".
// Turn each interval into two events and sweep the timeline.
int maxOverlap(vector<vector<int>> &intervals){
	vector<pair<int,int>> events;

	for(auto &interval:intervals){
		events.push_back({interval[0],1});    // +1 on start
		events.push_back({interval[1],-1});   // -1 on end
	}

	// sorting pairs puts -1 before +1 at an equal time, so an interval that
	// ends exactly when another starts does NOT count as an overlap
	sort(events.begin(),events.end());

	int cur=0;
	int maxi=0;

	for(auto &[time,delta]:events){
		cur+=delta;
		maxi=max(maxi,cur);
	}

	return maxi;
}

How you break ties is part of the problem statement. Do [1,3] and [3,5] overlap? It depends on whether the endpoints count as "inside" the interval. In code, the whole difference is whether -1 sorts before +1 at the same time. Ask the interviewer, or say your assumption out loud.

A trace of the event sweep on [1,4], [2,5], [4,6]. The events, sorted, are (1,+1), (2,+1), (4,−1), (4,+1), (5,−1), (6,−1). The running count goes 1, 2, 1, 2, 1, 0, so the maximum overlap is 2. At time 4 the −1 is processed before the +1, so [1,4] leaves before [4,6] arrives. If the +1 came first, the count would briefly hit 3, and you would report 3. That single tie decides the answer. The same number is the minimum count of meeting rooms needed: at the busiest moment, every meeting going on needs its own room.

For closest pair, here is the key fact. Once you have a best distance d, only points inside a vertical strip of width d can beat it. Inside that strip, each point needs to be checked against only a small, fixed number of neighbours. That is why the total is O(n log n) and not O(n²). The idea "the geometry limits how many candidates you must check" comes up again and again in sweep problems.

Reservoir sampling

The goal: pick k items at random from a stream (data that arrives one item at a time) whose length you do not know. Every item must have the same chance of being picked ("uniformly at random"), and you may only use O(k) memory. Think of drawing a raffle winner while guests are still walking in, without knowing how many will come. This is the standard answer whenever a problem says "the input is too large to store" or "you may only read it once".

reservoir sampling — k = 1, and general kO(n)O(k)
// k = 1: keep the i-th item with probability 1/i.
// Proof that this is uniform: item i is kept when it arrives (probability 1/i)
// and survives every later item j > i (each replaces it with probability 1/j,
// so survives with (j-1)/j). Multiplying:
//   (1/i) * (i/(i+1)) * ((i+1)/(i+2)) * ... * ((n-1)/n) = 1/n
// Every term cancels against the next — the telescoping IS the proof.
int sampleOne(vector<int> &stream){
	int ans=0;
	int seen=0;

	for(auto &x:stream){
		seen++;

		if(rand()%seen==0)ans=x;   // probability exactly 1/seen
	}

	return ans;
}

// General k: fill the reservoir with the first k, then for the i-th item
// (0-indexed) pick a slot in [0,i) and replace only if it lands inside.
vector<int> sampleK(vector<int> &stream,int k){
	vector<int> reservoir;
	int i=0;

	for(auto &x:stream){
		if(i<k){
			reservoir.push_back(x);
		}else{
			int slot=rand()%(i+1);

			if(slot<k)reservoir[slot]=x;
		}

		i++;
	}

	return reservoir;
}
The "telescoping" product (where each fraction cancels the next) is your answer to "prove it is uniform". It is short enough to say out loud in an interview. That is the real reason to know this algorithm, not just its name. In real code, use std::mt19937 with std::uniform_int_distribution instead of rand()%n. The % adds a slight bias when n does not divide RAND_MAX+1 evenly, and RAND_MAX can be as small as 32767. The same "pick fairly without knowing the size" idea also solves random node from a linked list and random pick with a blacklist.

A check with three items, a, b, c. Here is how likely each one is to be the final answer:

  • a is kept on arrival (1/1). It survives b with probability 1/2 and survives c with probability 2/3. Total: 1 · 1/2 · 2/3 = 1/3.
  • b is kept on arrival with probability 1/2 and survives c with probability 2/3. Total: 1/3.
  • c is kept on arrival with probability 1/3, and nothing comes after it.

All three are equal, as they should be. Why the general-k version works: when the item at 0-indexed position i arrives, i+1 items have been seen, so it should be in the sample with probability k/(i+1). Picking slot uniformly in [0, i] and replacing only when slot < k happens in exactly k of the i+1 cases. It also chooses which reservoir item to throw out uniformly. So the same cancelling argument works, and every item ends up with probability k/n.

Randomised quickselect

The problem: find the k-th smallest value (the median, for example) without sorting everything. Sorting does more work than you need, because it puts every element in its place. You only care about one position. Quickselect uses quicksort's partition step: choose a pivot, then move smaller values to its left and the rest to its right. After one partition the pivot sits exactly where it would be in the sorted array. If that position is k, you are done. If not, you know which side k is on, and you can throw the other side away.

Why the total is linear. A random pivot usually lands somewhere in the middle, so each round keeps only part of the range. Even in the pessimistic case where each round keeps 3/4 of the range, the work is n + 3n/4 + 9n/16 + …, which adds up to 4n. That is still O(n). The O(n²) case needs the pivot to be the smallest or largest value round after round, and with random pivots that is extremely unlikely.

k-th smallest in expected O(n)O(n) expected, O(n²) worstO(1)
// Quicksort's partition, but recursing into ONE side only — because we know
// which side k lies in. That is what turns n log n into n:
//   n + n/2 + n/4 + ... = 2n
// A RANDOM pivot is what makes the worst case vanishingly unlikely; a fixed
// pivot is O(n^2) on already-sorted input, which is a very common test case.
int partition(vector<int> &nums,int low,int high){
	int r=low+rand()%(high-low+1);

	swap(nums[r],nums[high]);       // random pivot, moved to the end

	int pivot=nums[high];
	int i=low;

	for(int j=low;j<high;j++){
		if(nums[j]<pivot){
			swap(nums[i],nums[j]);
			i++;
		}
	}

	swap(nums[i],nums[high]);

	return i;                        // the pivot's final, sorted position
}

// k is 0-indexed: k=0 is the smallest.
int quickselect(vector<int> &nums,int k){
	int low=0;
	int high=nums.size()-1;

	while(low<=high){
		int p=partition(nums,low,high);

		if(p==k)return nums[p];

		if(p<k)low=p+1;
		else high=p-1;
	}

	return -1;
}
It uses a loop instead of recursion, because it only ever goes down one side. A recursive call as the very last step (a "tail call") is really just a loop, and a loop avoids any worry about stack depth. Compare the three ways to find the "k-th largest":
  • Sorting is O(n log n) and obviously correct.
  • A min-heap of size k is O(n log k). It is the right choice when the data streams in or k is tiny (Chapter 15).
  • Quickselect is O(n) on average, but it rearranges (mutates) the array and has an O(n²) worst case.
Mention all three, then choose on purpose. If a guaranteed O(n) is required, the answer is median of medians, which picks a pivot that is provably good. It is worth naming, but rarely worth writing.

A dry run: nums = [7,2,9,4,5], k = 2 (the third smallest; the answer is 5). Say the random pivot is the 5, already at the end. i marks where the next small value goes. Everything before i is less than the pivot.

  • j=0: 7 is not < 5, so skip it. j=1: 2 < 5, so swap it to position 0 and i becomes 1. The array is [2,7,9,4,5].
  • j=2: 9 is not < 5, so skip it. j=3: 4 < 5, so swap it to position 1 and i becomes 2. The array is [2,4,9,7,5].
  • Swap the pivot into position i: [2,4,5,7,9]. The partition returns 2, which equals k, so the answer is 5.

The two values to the left of 5 are not sorted in general. They are just all smaller. That is the only guarantee a partition makes, and it is enough. Edge cases: if the array holds many equal values, this partition puts all of them on one side. With many duplicates that slows it down, and a three-way partition (less, equal, greater) fixes it. Also turn "k-th largest" into a "k-th smallest" index yourself: it is n − k with 0-indexing.

🎲
What randomisation does and does not buy

Randomness turns adversarial worst cases (ones someone can trigger on purpose with a crafted input) into merely unlucky ones. Quickselect with a random pivot still has an O(n²) worst case. But no input can trigger it reliably, because the behaviour depends on the coin flips, not on the data. That is a real protection against sorted or hostile inputs. It is why randomisation is standard in std::sort's introsort and in hash-table seeding.

What it does not give you is a promise. If a problem demands worst-case O(n), a randomised algorithm does not meet it, however good its average. And seed the random generator properly. srand(time(0)) gives the same sequence twice within the same second. A fixed seed makes your "random" pivot completely predictable, which defeats the whole point.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 ONE CROSS HELPER
Write cross(O,A,B) once; orientation, collinearity, polygon area and point-in-triangle are all its sign. A cascade of slope comparisons is how geometry code gets long and wrong.
⛔ STAY IN INTEGERS
Compare squared distances and return twice the area. Every float you introduce is a future failure on a collinear or touching case.
💡 RESERVOIR PROOF
Keeping the i-th item with probability 1/i is uniform because the survival product telescopes to 1/n. Short enough to say out loud, which is why it is worth knowing.
⚠️
Common mistakes
  • Using decimals (floating point) for direction tests. Cross products in integers are exact. With floats, you cannot reliably tell whether three points are on one line.
  • Cross-product overflow with coordinates near 10⁹. Check the limit and use long long.
  • Taking a square root to compare distances. Compare squared distances instead and stay exact.
  • Comparing points by slope instead of by cross product, then dividing by zero on a vertical line.
  • Using the wrong rule for points on a straight edge of the convex hull. <= 0 drops them and < 0 keeps them. Know which one the problem wants.
  • Assigning instead of using max when extending a merged interval. An interval sitting inside the current one then shrinks it.
  • Getting the sweep tie-break wrong, so intervals that just touch are counted (or not counted) as overlapping, against what the problem says.
  • rand()%seen with the wrong number in reservoir sampling. It must be the count including the current item.
  • Using a fixed pivot in quickselect, which gives O(n²) on sorted input. Sorted input is an extremely common test case.
  • Forgetting that quickselect rearranges the input. Copy the array first if the caller still needs the original order.
  • Claiming worst-case O(n) for randomised quickselect. It is O(n) on average (expected). Median of medians is the worst-case version.

Interview drill

Warm-up: Pick a random element from a stream of unknown length, using O(1) memory. Then prove it is uniform.

How a strong answer sounds
I would use reservoir sampling with k = 1. I keep one candidate and a counter of how many items I have seen. When the i-th item arrives, I replace the candidate with probability exactly 1/i. That is one number of state and a single pass. Most importantly, it never needs to know the stream length.

For the proof, pick an item at position i and ask: what is the chance it ends up as the final answer? First, it must be chosen when it arrives. That happens with probability 1/i. Then it must survive every later item j. Each later item replaces it with probability 1/j, so it survives that step with probability (j−1)/j. Multiplying gives (1/i) · (i/(i+1)) · ((i+1)/(i+2)) · … · ((n−1)/n). Each top number cancels the bottom number before it, leaving 1/n. So every position has the same chance, whatever i is. That is exactly what uniform means.

I would add two practical notes. First, it extends to k items: fill the reservoir with the first k, then for the i-th item pick a slot at random in [0, i) and replace only if that slot is below k. The same cancelling argument works. Second, rand() % n is slightly biased when n does not divide RAND_MAX + 1 evenly, and RAND_MAX can be as small as 32767. So in real code I would use mt19937 with uniform_int_distribution. The same idea answers "random node from a linked list" and "random pick with a blacklist".

Deeper: Find the k-th largest element in an unsorted array. Give more than one approach.

How a strong answer sounds
There are three good answers, and the right one depends on the limits of the problem, so I would lay them all out.

Sorting and then indexing is O(n log n). It is two lines and almost impossible to get wrong. It is a perfectly good answer if n is small or the code must be obviously correct.

A min-heap of size k is O(n log k) time and O(k) space. Push each element, pop whenever the heap grows past k, and the top of the heap is the answer. I would choose this if the data streams in, or if k is much smaller than n, because it never needs the whole array in memory.

Randomised quickselect is O(n) on average. Partition as in quicksort, but only continue into the side that contains k. The work is n + n/2 + n/4 + … = 2n. I would write it as a loop, since with only one branch the recursion is just a loop anyway. The key detail is the random pivot. With a fixed pivot, already-sorted input slows to O(n²), and sorted input is one of the most common test cases. Randomising does not remove the O(n²) worst case. It makes it impossible for anyone to trigger on purpose, because the behaviour now depends on the coin flips, not on the data.

So I would be careful not to claim worst-case linear time. If that were truly required, the answer is median of medians. It picks a provably good pivot for a guaranteed O(n), but with a much larger constant factor. I would also mention that quickselect rearranges the array, so if the caller needs the original order, I copy it first.

🧠 Key takeaways

  • One cross helper tells you turn direction, area, whether points line up, and whether a point is inside a shape. Most geometry is just its sign.
  • Stay in integers: compare squared distances, return twice the area, and never use a tolerance (epsilon) where an exact test exists.
  • A convex hull is a monotonic stack that pops on turn direction. It is O(n log n), and the sort is the slowest part.
  • A sweep line turns interval and rectangle problems from O(n²) into O(n log n). How you break ties is part of the problem statement.
  • Reservoir sampling keeps the i-th item with probability 1/i. The product of fractions that cancel down to 1/n is the proof.
  • Randomness turns worst cases that someone could trigger on purpose into merely unlucky ones. It is not a worst-case guarantee.

Check your understanding

cross(O,A,B) > 0 tells you…

The sign tells you the turn direction. The size tells you twice the triangle's area. One expression gives two answers, which is why every geometry yes/no test comes down to it.

Why prefer integer coordinates and squared distances in geometry code?

Comparing distances never needs the square root, and areas can be returned doubled. Every float you add is a future failure when points line up or just touch.

The monotone-chain convex hull is essentially which earlier technique?

Each point is pushed once and popped at most once. So the two walks are O(n), and the O(n log n) sort is the slowest part.

In reservoir sampling with k = 1, why keep the i-th item with probability 1/i?

The item is chosen on arrival with probability 1/i. Then it survives each later item j with probability (j−1)/j. The fractions cancel down to 1/n. That cancelling is the proof, and it is short enough to say out loud.

Randomised quickselect is expected O(n). What does randomising the pivot actually guarantee?

The O(n²) case still exists, but now it only happens by bad luck. No one can trigger it on purpose. If worst-case linear time is truly required, use median of medians.
