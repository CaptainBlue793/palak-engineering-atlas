Geometry & Randomisation

Two small topics that share a habit of mind: both replace case analysis with a single formula. Computational geometry reduces "is this point left or right, do these segments cross, is this polygon convex" to the sign of one cross product. Randomised algorithms replace a worst-case adversary with an expectation — and get simpler code that is fast almost always.

  • Use the cross product for orientation, area and segment intersection
  • Build a convex hull with the monotone chain
  • Apply sweep line to intervals and to closest-pair problems
  • Sample from a stream with reservoir sampling
  • Use randomised quickselect for the k-th element in expected O(n)

The cross product answers everything

orientation, area, and why you should stay in integersO(1)
// The 2D cross product of OA and OB. Its SIGN is the orientation and its
// MAGNITUDE is twice the triangle's area — two answers from one expression.
//   > 0  -> O, A, B turn counter-clockwise (B is left of the ray O->A)
//   < 0  -> clockwise (B is right)
//   == 0 -> collinear
struct Point{
	long long x;
	long long y;
};

long long cross(Point &O,Point &A,Point &B){
	return (A.x-O.x)*(B.y-O.y)-(A.y-O.y)*(B.x-O.x);
}

// Area of any simple polygon — the shoelace formula, which is just a sum of
// cross products around the boundary. Returns TWICE the area, kept as an
// integer so there is no rounding at all.
long long twiceArea(vector<Point> &poly){
	int n=poly.size();
	long long sum=0;

	for(int i=0;i<n;i++){
		int j=(i+1)%n;

		sum+=poly[i].x*poly[j].y-poly[j].x*poly[i].y;
	}

	return llabs(sum);          // the sign tells you the winding direction
}

// Squared distance — comparing distances needs NO square root, so this stays
// exact. Only take the root when the actual length must be reported.
long long dist2(Point &a,Point &b){
	long long dx=a.x-b.x;
	long long dy=a.y-b.y;

	return dx*dx+dy*dy;
}
Integer arithmetic is the single most important habit in geometry. Coordinates up to 10⁴ make a cross product up to about 8·10⁸ — fine — but coordinates up to 10⁹ push it to 4·10¹⁸, which is close to the long long ceiling, so check the bound. The payoff: orientation tests become exact, and "are these three points collinear" has a definite answer instead of an epsilon comparison. Every float you introduce is a future bug in a degenerate case, so stay in integers, compare squared distances, and return twice the area.
✍️
My convention: one cross helper, then everything is its sign

I write cross(O, A, B) once and never write geometry logic any other way. "Is the point left of the line" is cross(...) > 0; "is the turn clockwise" is < 0; "collinear" is == 0; "convex polygon" is "all the crosses share a sign"; "point inside a triangle" is "three crosses share a sign". Encoding all of that as one helper plus a sign test is what keeps geometry code short enough to be correct — the alternative, a cascade of if branches over slopes, has to special-case vertical lines and then gets the degenerate inputs wrong. It is the same instinct as reusing one BFS loop for six tree views: find the operation the problems share, write it once, and vary only what must vary.

convex hull — O(n log n)O(n log n)O(n)
// Andrew's monotone chain. Sort by x (then y), then walk twice: once left to
// right for the lower hull, once right to left for the upper. Each walk keeps
// a stack and pops any point that makes a non-counter-clockwise turn — because
// such a point lies inside the hull built so far.
vector<Point> convexHull(vector<Point> &points){
	int n=points.size();

	if(n<3)return points;

	sort(points.begin(),points.end(),[](Point &a,Point &b){
		if(a.x!=b.x)return a.x<b.x;

		return a.y<b.y;
	});

	vector<Point> hull;

	// lower hull, then upper hull — same loop, reversed traversal
	for(int pass=0;pass<2;pass++){
		int start=hull.size();

		for(int step=0;step<n;step++){
			int i=pass==0?step:n-1-step;

			while(hull.size()>=start+2 and
			      cross(hull[hull.size()-2],hull[hull.size()-1],points[i])<=0)
			hull.pop_back();

			hull.push_back(points[i]);
		}

		hull.pop_back();      // the last point starts the next chain
	}

	return hull;
}
It is a monotonic stack (Chapter 14) with an orientation test instead of a comparison. Each point is pushed once and popped at most once, so the two walks are O(n) and the sort dominates. Two choices worth stating: <= 0 in the pop condition excludes collinear points from the hull — use < 0 if the problem wants them kept, and know which one is being asked for. And the pass loop exists only to avoid writing the same walk twice; if the two chains differed in any way I would write them out separately rather than force the shared shape, since reuse should never cost clarity.

Sweep line

The general technique for problems about intervals, rectangles and events on a line: sort the endpoints, then process them in order while maintaining a small amount of state. This is what turns "compare every pair", O(n²), into O(n log n).

Merge intervals
// Sort by start, then extend or emit. The archetypal sweep.
vector<vector<int>> merge(vector<vector<int>> &intervals){
	if(intervals.empty())return {};

	sort(intervals.begin(),intervals.end());

	vector<vector<int>> ans;

	ans.push_back(intervals[0]);

	for(int i=1;i<intervals.size();i++){
		if(intervals[i][0]<=ans.back()[1]){
			ans.back()[1]=max(ans.back()[1],
			                     intervals[i][1]);
		}else{
			ans.push_back(intervals[i]);
		}
	}

	return ans;
}

max on the extension is essential — a later interval can be entirely contained in the current one, and blindly assigning its end would shrink the merged interval. That is the classic bug here.

Maximum overlap (events)
// "Most meetings at once", "minimum rooms needed", "maximum guests present".
// Turn each interval into two events and sweep the timeline.
int maxOverlap(vector<vector<int>> &intervals){
	vector<pair<int,int>> events;

	for(auto &interval:intervals){
		events.push_back({interval[0],1});    // +1 on start
		events.push_back({interval[1],-1});   // -1 on end
	}

	// sorting pairs puts -1 before +1 at an equal time, so an interval that
	// ends exactly when another starts does NOT count as an overlap
	sort(events.begin(),events.end());

	int cur=0;
	int maxi=0;

	for(auto &[time,delta]:events){
		cur+=delta;
		maxi=max(maxi,cur);
	}

	return maxi;
}

The tie-breaking rule is the problem specification. Whether [1,3] and [3,5] overlap depends on whether the endpoints are inclusive — and the entire difference in code is whether -1 sorts before +1. Ask, or state your assumption.

For closest pair, the key fact is that once you have a best distance d, only points within a vertical strip of width d can beat it, and inside that strip at most a constant number of points need checking per point — which is why the total is O(n log n) rather than quadratic. That "a geometric bound limits the candidates" argument is the recurring idea in geometric sweeps.

Reservoir sampling

Choose k items uniformly at random from a stream of unknown length, using O(k) memory. This is the standard answer whenever a problem says "the input is too large to store" or "you may only read it once".

reservoir sampling — k = 1, and general kO(n)O(k)
// k = 1: keep the i-th item with probability 1/i.
// Proof that this is uniform: item i is kept when it arrives (probability 1/i)
// and survives every later item j > i (each replaces it with probability 1/j,
// so survives with (j-1)/j). Multiplying:
//   (1/i) * (i/(i+1)) * ((i+1)/(i+2)) * ... * ((n-1)/n) = 1/n
// Every term cancels against the next — the telescoping IS the proof.
int sampleOne(vector<int> &stream){
	int ans=0;
	int seen=0;

	for(auto &x:stream){
		seen++;

		if(rand()%seen==0)ans=x;   // probability exactly 1/seen
	}

	return ans;
}

// General k: fill the reservoir with the first k, then for the i-th item
// (0-indexed) pick a slot in [0,i) and replace only if it lands inside.
vector<int> sampleK(vector<int> &stream,int k){
	vector<int> reservoir;
	int i=0;

	for(auto &x:stream){
		if(i<k){
			reservoir.push_back(x);
		}else{
			int slot=rand()%(i+1);

			if(slot<k)reservoir[slot]=x;
		}

		i++;
	}

	return reservoir;
}
The telescoping product is the answer to "prove it is uniform", and it is short enough to state aloud in an interview — which is the real reason to know this algorithm rather than just recognise its name. In production code use std::mt19937 with std::uniform_int_distribution rather than rand()%n: the modulus introduces a slight bias when n does not divide RAND_MAX+1, and RAND_MAX can be as small as 32767. The same "pick uniformly without knowing the size" idea also gives you random node from a linked list and random pick with a blacklist.

Randomised quickselect

k-th smallest in expected O(n)O(n) expected, O(n²) worstO(1)
// Quicksort's partition, but recursing into ONE side only — because we know
// which side k lies in. That is what turns n log n into n:
//   n + n/2 + n/4 + ... = 2n
// A RANDOM pivot is what makes the worst case vanishingly unlikely; a fixed
// pivot is O(n^2) on already-sorted input, which is a very common test case.
int partition(vector<int> &nums,int low,int high){
	int r=low+rand()%(high-low+1);

	swap(nums[r],nums[high]);       // random pivot, moved to the end

	int pivot=nums[high];
	int i=low;

	for(int j=low;j<high;j++){
		if(nums[j]<pivot){
			swap(nums[i],nums[j]);
			i++;
		}
	}

	swap(nums[i],nums[high]);

	return i;                        // the pivot's final, sorted position
}

// k is 0-indexed: k=0 is the smallest.
int quickselect(vector<int> &nums,int k){
	int low=0;
	int high=nums.size()-1;

	while(low<=high){
		int p=partition(nums,low,high);

		if(p==k)return nums[p];

		if(p<k)low=p+1;
		else high=p-1;
	}

	return -1;
}
Iterative rather than recursive, because there is only one branch — a tail call is just a loop, and this avoids any stack-depth question. Compare the three approaches to "k-th largest": sorting is O(n log n) and trivially correct; a size-k min-heap is O(n log k) and the right answer when the data streams or k is tiny (Chapter 15); quickselect is expected O(n) but mutates the array and has an O(n²) worst case. Say all three and pick deliberately. If a guaranteed O(n) is demanded, the answer is median of medians, which chooses a provably good pivot — worth naming, rarely worth writing.
🎲
What randomisation does and does not buy

It converts adversarial worst cases into unlucky ones. Quickselect with a random pivot still has an O(n²) worst case — but no input triggers it reliably, because the behaviour depends on the coin flips rather than on the data. That is a genuine guarantee against sorted or adversarial inputs, and it is why randomisation is standard in std::sort's introsort and in hash-table seeding. What it does not buy is a bound you can promise: if a problem demands worst-case O(n), a randomised algorithm does not satisfy it no matter how good the expectation. And seed properly — srand(time(0)) gives the same sequence twice within the same second, and a fixed seed makes your "random" pivot perfectly predictable, which defeats the entire point.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 ONE CROSS HELPER
Write cross(O,A,B) once; orientation, collinearity, polygon area and point-in-triangle are all its sign. A cascade of slope comparisons is how geometry code gets long and wrong.
⛔ STAY IN INTEGERS
Compare squared distances and return twice the area. Every float you introduce is a future failure on a collinear or touching case.
💡 RESERVOIR PROOF
Keeping the i-th item with probability 1/i is uniform because the survival product telescopes to 1/n. Short enough to say out loud, which is why it is worth knowing.
⚠️
Common mistakes
  • Using floating point for orientation. Cross products in integers are exact; floats make collinearity undecidable.
  • Cross-product overflow with coordinates near 10⁹. Check the bound and use long long.
  • Taking a square root to compare distances. Compare squared distances and stay exact.
  • Comparing points by slope instead of by cross product, then dividing by zero on a vertical line.
  • The wrong collinearity convention in a convex hull — <= 0 drops collinear points, < 0 keeps them. Know which is wanted.
  • Assigning rather than max-ing when extending a merged interval, so a contained interval shrinks it.
  • Getting the sweep tie-break wrong, so touching intervals do or do not count as overlapping against the specification.
  • rand()%seen with the wrong denominator in reservoir sampling — it must be the count including the current item.
  • Using a fixed pivot in quickselect, giving O(n²) on sorted input — an extremely common test case.
  • Forgetting that quickselect mutates the input. Copy first if the caller still needs the order.
  • Claiming worst-case O(n) for randomised quickselect. It is expected O(n); median of medians is the worst-case version.

Interview drill

Warm-up: Pick a random element from a stream of unknown length, using O(1) memory. Then prove it is uniform.

How a strong answer sounds
Reservoir sampling with k = 1. I keep one candidate and a counter of how many items I have seen; when the i-th item arrives I replace the candidate with probability exactly 1/i. That is one integer of state and a single pass, and crucially it never needs the stream length. For the proof, fix an item at position i and ask for the probability it is the final answer. It must be chosen when it arrives, which happens with probability 1/i, and then it must survive every later item j — each of which replaces it with probability 1/j, so it survives that step with probability (j−1)/j. Multiplying gives (1/i) · (i/(i+1)) · ((i+1)/(i+2)) · … · ((n−1)/n), and every numerator cancels the previous denominator, leaving 1/n. So every position is equally likely, independent of i, which is exactly uniformity. Two practical notes I would add. First, the generalisation to k items: fill the reservoir with the first k, then for the i-th item pick a slot uniformly in [0, i) and replace only if that slot is below k — same telescoping argument. Second, rand() % n is slightly biased when n does not divide RAND_MAX + 1, and RAND_MAX can be as small as 32767, so in real code I would use mt19937 with uniform_int_distribution. The same idea answers "random node from a linked list" and "random pick with a blacklist".

Deeper: Find the k-th largest element in an unsorted array. Give more than one approach.

How a strong answer sounds
There are three reasonable answers and the right one depends on the constraints, so I would lay them out. Sorting and indexing is O(n log n), two lines, and impossible to get wrong — a perfectly good answer if n is small or the code needs to be obviously correct. A size-k min-heap is O(n log k) time and O(k) space: push each element, pop when the heap exceeds k, and the root is the answer. This is the one I would choose if the data streams or if k is much smaller than n, since it never needs the whole array in memory. Randomised quickselect is expected O(n): partition as in quicksort, but recurse into only the side containing k, which gives n + n/2 + n/4 + … = 2n. I would write it iteratively, since with a single branch the recursion is just a loop. The critical detail is the random pivot: with a fixed pivot, already-sorted input degrades to O(n²), and sorted input is one of the most common test cases there is. Randomising does not remove the O(n²) worst case — it makes it unreachable by an adversary, because the behaviour now depends on the coin flips rather than on the data. So I would be careful not to claim worst-case linear time; if that were actually required, the answer is median of medians, which picks a provably good pivot for a guaranteed O(n) at the cost of a much larger constant. I would also mention that quickselect mutates the array, so if the caller needs the original order I copy first.

🧠 Key takeaways

  • One cross helper gives orientation, area, collinearity and containment — geometry is its sign.
  • Stay in integers: compare squared distances, return twice the area, and never use an epsilon where an exact test exists.
  • Convex hull is a monotonic stack with an orientation test; O(n log n), dominated by the sort.
  • Sweep line turns interval and rectangle problems from O(n²) into O(n log n); the tie-break rule is part of the specification.
  • Reservoir sampling keeps the i-th item with probability 1/i, and the telescoping product is the proof.
  • Randomisation converts adversarial worst cases into unlucky ones — it is not a worst-case guarantee.

Check your understanding

cross(O,A,B) > 0 tells you…

Sign gives orientation, magnitude gives twice the area. One expression, two answers — which is why every geometry predicate reduces to it.

Why prefer integer coordinates and squared distances in geometry code?

Comparisons never need the square root, and areas can be returned doubled. Every float introduced is a future failure on a collinear or touching case.

The monotone-chain convex hull is essentially which earlier technique?

Each point is pushed once and popped at most once, so the two walks are O(n) and the sort dominates at O(n log n).

In reservoir sampling with k = 1, why keep the i-th item with probability 1/i?

Chosen on arrival with probability 1/i, then surviving each later item j with probability (j−1)/j. The cancellation is the proof, and it is short enough to say out loud.

Randomised quickselect is expected O(n). What does randomising the pivot actually guarantee?

The quadratic case still exists but becomes unlucky rather than adversarial. If worst-case linear time is genuinely required, that is median of medians.
