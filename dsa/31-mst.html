Minimum Spanning Trees: Prim & Kruskal

The goal: connect every node while paying the smallest possible total cost. Think of laying cable between towns as cheaply as possible. Two greedy algorithms (ones that always grab the best-looking choice right now) solve this. They look nothing alike, yet both are proved correct by the same one-line fact: the cut property. Kruskal is Chapter 22's DSU with a sort added in front. Prim is Chapter 29's Dijkstra with one operator changed. Spotting those two reuses is most of what this chapter is about.

  • State the cut property and use it to prove both algorithms with one argument
  • Write Kruskal as "sort, then DSU", using unite's true/false result as the cycle test
  • Write Prim as Dijkstra that pushes weight instead of dist + weight
  • Choose between them based on how dense the graph is (how many edges it has per node)
  • Know what an MST does not give you: shortest paths, or Steiner trees

The problem, and the one fact that solves it

Why anyone cares. Many real problems boil down to "link everything up as cheaply as possible". Examples: laying cable or pipes between towns, wiring a circuit board, or joining clusters in data analysis. In interviews it shows up as "minimum cost to connect all points", "connect all cities", or "supply water to every house". Whenever the answer is a set of links that must reach everyone and you pay per link, think MST.

You are given a connected, undirected graph where every edge has a weight (a cost). Pick a set of edges that links all V nodes together, with the smallest possible total weight. That set always has exactly V−1 edges and no cycles. A set like this is called a spanning tree: "spanning" because it reaches every node, "tree" because it has no loops. The cheapest one is the minimum spanning tree, or MST.

Why no cycles, and why exactly V−1 edges? If your chosen edges contained a cycle, you could delete any one edge of that cycle and every node would still be reachable (the rest of the cycle goes the long way round). With non-negative costs, deleting an edge never makes the total worse, so the cheapest answer never needs a cycle. (With negative weights, "spanning tree" is simply part of the definition of the problem, and the algorithms below still find the cheapest one.) As for the count: start with V separate nodes, which is V groups. Each edge that does not make a cycle joins two groups into one, so it lowers the group count by exactly 1. To get from V groups down to 1 you need exactly V−1 such edges. For example, 4 towns need exactly 3 cables.

✂️
The cut property — and why it proves both algorithms at once

A cut is any way of splitting the nodes into two groups, with neither group empty. An edge "crosses" the cut if it has one end in each group. The claim:

For any cut, the lightest edge crossing it belongs to some MST.

Proof (exchange argument — swap one edge for another and show nothing gets worse). Let e be a lightest crossing edge. Suppose some MST T does not contain it. Add e to T: that creates a cycle. A cycle that crosses the cut must cross back again, so it crosses an even number of times. That means the cycle holds at least one other crossing edge, f. Since e is the lightest, weight(e) ≤ weight(f). Now swap them. T − f + e still reaches every node, still has no cycle, and weighs no more. So some MST does contain e. ∎

A tiny example. Take the graph in the visualizer below and cut it into {0} versus everything else. The edges crossing that cut are 0–5 (weight 1) and 0–1 (weight 4). The cut property says the lighter one, 0–5, is safe to take. Now cut it into {0, 5} versus the rest. The crossing edges are 0–1 (4), 5–1 (6) and 5–4 (2). The lightest is 5–4, so that one is safe too. Every algorithm in this chapter is just a systematic way of picking cuts like these.

Now both algorithms follow directly. Prim grows one tree and always adds the lightest edge leaving it. That is exactly the lightest edge crossing the cut (the tree vs. the rest). Kruskal adds the lightest edge that joins two different components (separate connected groups). That is the lightest edge crossing the cut (that component vs. everything else). Two algorithms, one theorem. The mirror rule, the cycle property, says the heaviest edge on any cycle is in no MST. That is why Kruskal is allowed to reject an edge.

Kruskal: sort the edges, use DSU as the cycle test

The idea in one sentence: go through the edges from cheapest to most expensive, and take each one unless it would close a loop. At the start every node is its own little tree. Each accepted edge merges two trees into one. The only hard part is asking "are u and v already connected?" quickly, thousands of times. Walking the graph each time would cost O(V) per edge. DSU answers it in almost O(1), which is why Kruskal and DSU are always taught together.

Kruskal's MSTO(E log E)O(V)
// The DSU from Chapter 22. unite() returning false means "already connected",
// which is exactly "this edge would create a cycle" — the whole cycle test.
class DSU{
	vector<int> parent,rank;

public:
	DSU(int n){
		parent.resize(n);
		rank.resize(n,0);

		for(int i=0;i<n;i++){
			parent[i]=i;
		}
	}

	int find(int x){
		if(x==parent[x])return x;

		return parent[x]=find(parent[x]);
	}

	bool unite(int x,int y){
		int px=find(x);
		int py=find(y);

		if(px==py)return false;

		if(rank[px]>rank[py]){
			parent[py]=px;
		}else if(rank[px]<rank[py]){
			parent[px]=py;
		}else{
			parent[py]=px;
			rank[px]++;
		}

		return true;
	}
};

// {weight, {u, v}} so the built-in comparison sorts by weight (Chapter 8).
typedef pair<int,pair<int,int>> P;

int kruskal(int N,vector<vector<int>> &edges){
	vector<P> list;
	for(auto &e:edges){
		int u=e[0];
		int v=e[1];
		int w=e[2];
		list.push_back({w,{u,v}});
	}

	sort(list.begin(),list.end());        // O(E log E) — the dominant cost

	DSU dsu(N);
	int MST=0;
	int used=0;

	for(auto &it:list){
		int w=it.first;
		auto [u,v]=it.second;

		if(dsu.unite(u,v)){        // false = would form a cycle, so skip
			MST+=w;
			used++;

			if(used==N-1)break;     // a spanning tree has exactly V-1 edges
		}
	}

	if(used!=N-1)return -1;         // graph is disconnected: no spanning tree

	return MST;
}
Two checks that are easy to forget. The break at V−1 edges is just a speed-up. Once you have V−1 edges you are done, and carrying on would only reject the rest. The final used != N−1 check is about correctness. If the graph is disconnected, no spanning tree exists at all. Without this check, you quietly return the weight of a minimum spanning forest (several separate trees) as if it were one tree.

That is 5 edges, which is V−1, so the loop breaks with a total of 12. The remaining edges (3–4, 1–4, 1–5, 2–4) are never looked at. If the loop had kept going, every one of them would have been rejected, because both ends already sit in the one big group. Notice the tie at weight 2: sorting put 2–3 before 4–5, but taking them in the other order gives the same total. Ties can change which edges you pick, never the total weight.

Edge cases Kruskal must handle. A self-loop u–u is rejected automatically, since unite(u,u) returns false. Parallel edges (two edges between the same pair) are fine: the cheaper one is taken first and the other is rejected. A single node (V = 1) needs 0 edges, and used == N−1 is already true, so the answer is 0. Negative weights are also fine. Kruskal only compares weights, it never adds them along a path, so unlike Dijkstra it does not care about signs.

✍️
My convention: pair<int,pair<int,int>> with the weight first, and a typedef

Storing each edge as {weight, {u, v}} means sort needs no custom comparator. The built-in < for pair compares the weight first, then breaks ties using the endpoints. That is exactly what you want. The typedef P keeps the declarations readable, and auto [u,v] = it.second; unpacks the endpoints cleanly. It is the same idea as the {weight, node} order in Dijkstra (Chapter 29): put the sort key first and the language does the work.

Prim: grow one tree with a heap

Kruskal builds many small trees and merges them. Prim does the opposite: it keeps one tree and grows it a node at a time. Start from any node. Look at every edge that has one end inside the tree and one end outside. Take the cheapest, pull its outside node in, and repeat until every node is inside. The min-heap is how you find "the cheapest edge leaving the tree" without rescanning all edges each round.

Prim's MSTO(E log V)O(V + E)
// This is Dijkstra (Chapter 29) with ONE change: we push the edge weight
// itself rather than dist[node]+weight, because we care about the cost of
// joining the tree, not the distance from a source.
int prims(vector<vector<pair<int,int>>> &graph,int N){
	vector<bool> visited(N,false);
	priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> pq;

	pq.push({0,0});                // {weight, node} — start anywhere
	int MST=0;
	int used=0;

	while(!pq.empty()){
		int weight=pq.top().first;
		int node=pq.top().second;
		pq.pop();

		if(visited[node])continue;    // lazy deletion, same as Dijkstra

		MST+=weight;
		visited[node]=true;
		used++;

		for(auto &[neighbour,w]:graph[node]){
			if(!visited[neighbour])
			pq.push({w,neighbour});    // w, NOT weight+w — that would be Dijkstra
		}
	}

	if(used!=N)return -1;            // disconnected

	return MST;
}
Prim and Dijkstra differ by one small change. Dijkstra pushes dist[node] + weight, because it adds up the cost of a whole path. Prim pushes weight alone, because each edge's cost is paid just once, when its node joins the tree. Everything else is identical: the min-heap, the lazy if(visited) continue; skip, and the {key, node} order. If you can write one, you can write the other.

Dry run on the same graph, starting at node 0

  1. Pop {0,0}. Node 0 joins, total 0. Push its edges: {4,1} and {1,5}.
  2. Pop {1,5}, the cheapest. Node 5 joins, total 1. Push {6,1} and {2,4}.
  3. Pop {2,4}. Node 4 joins, total 3. Push {5,1}, {7,2} and {4,3}.
  4. The heap now holds {4,1}, {4,3}, {5,1}, {6,1}, {7,2}. Two entries tie at 4; the pair comparison breaks the tie by node, so {4,1} comes out. Node 1 joins, total 7. Push {3,2}.
  5. Pop {3,2}. Node 2 joins, total 10. Push {2,3}.
  6. Pop {2,3}. Node 3 joins, total 12. All 6 nodes are in.
  7. The leftover entries ({4,3}, {5,1}, {6,1}, {7,2}) are popped and skipped by the visited check.

Same total as Kruskal: 12. The edges were chosen in a different order (0–5, 5–4, 0–1, 1–2, 2–3), which is exactly what the visualizer shows when you switch modes. Step 7 is why the lazy skip is essential: without it, node 3 would be "added" again with weight 4 and the total would be wrong.

🔁
Note the adjacency order flips between the two snippets

Chapter 29's Dijkstra stored {weight, neighbour} and unpacked auto &[weight,neighbour]. This Prim stores {neighbour, weight} and unpacks auto &[neighbour,w]. Both work. Prim never sorts the adjacency list; the only sorting happens inside the heap, where the pair is built explicitly as {w, neighbour}. But pick one order per file and never mix them. If you accidentally swap a pair's two fields, you get wrong answers that look believable. It is one of the hardest graph bugs to spot just by reading. Write your chosen order in a comment above the loop that builds the adjacency list.

Why O(E log E) and O(E log V) are "about the same". A simple graph has at most V² edges, so log E ≤ log V² = 2 log V. The two differ by at most a factor of 2, which Big-O ignores. The real differences between the algorithms are the input format and the dense case.

How the O(V²) Prim works. Drop the heap. Keep an array best[v] = the cheapest edge found so far from the tree to node v (start it at infinity, and at 0 for the start node). Each round has two O(V) scans. First, scan all unvisited nodes and pick the one with the smallest best; add it to the tree and add best to the total. Second, for every unvisited node u, set best[u] = min(best[u], cost(new node, u)). There are V rounds, so the whole thing is V × O(V) = O(V²). No edge list, no sorting and no heap. For V = 10⁴ that is about 10⁸ cheap array steps, which fits comfortably in a typical time limit.

🎯
In practice

Default to Kruskal if you already have a list of edges. It is shorter, and DSU is code you will reuse anyway. Use Prim when you are given an adjacency list, when the graph is dense (the O(V²) array version needs no heap at all), or when the edges are not listed but worked out on the fly. A common case: “connect all points, where cost = Manhattan distance”. Every point can link to every other, so the graph is complete, with E = V²/2 edges. Here the O(V²) Prim is the right answer. Building and sorting a list of 5 × 10⁷ edges is not.

What an MST does not give you

🛣️

Not shortest paths

The MST path between two nodes can be much longer than their true shortest path. An MST keeps the total weight of all its edges low, not the distance between any one pair. Use Dijkstra for paths.

🎯

Not a Steiner tree

Sometimes you only need to connect some of the nodes, and may pass through others as stepping stones. That is the Steiner tree problem, and it is NP-hard (no known fast solution). An MST always connects all nodes.

🔢

Not unique

If all edge weights are different, there is exactly one MST. With ties, several MSTs can exist, all with the same total weight. "Count the MSTs" is a different, harder problem.

🏔️

But it does minimise the bottleneck

The bottleneck is the heaviest single edge on a route. The MST path between any two nodes makes that maximum edge as small as possible. So "minimise the largest weight you must cross" is an MST problem.

✂️

And it exposes critical edges

An edge that appears in every MST is critical. One that appears in no MST is useless. You can test both by running Kruskal with that edge banned or forced in.

📉

Maximum spanning tree is free

Flip the sign of every weight, or sort from largest to smallest. The cut property works the same way in reverse, so both algorithms apply unchanged.

🏔️
Why the MST minimises the bottleneck — a genuinely useful corollary

Claim: take any two nodes u and v. Of all paths between them, the one in the MST has the smallest possible heaviest edge. Why? Suppose some other path had a smaller heaviest edge, m. Look at the heaviest edge e on the MST path, where weight(e) > m. Removing e splits the MST into two parts, with u and v on opposite sides. The other path must cross between those parts, using some edge f with weight(f) ≤ m < weight(e). Swapping e for f would give a lighter spanning tree. But the MST was already the lightest, so that is impossible. ∎ So “minimise the heaviest edge you must cross” is an MST problem. That is why problems about maximum load, widest path or "swim in rising water" often have an MST solution, as well as a binary-search-plus-DSU one.

🧩
The variants worth knowing
  • Second-best MST. The cheapest spanning tree that is not the MST. For each MST edge, remove it and rerun. That costs O(V·E log E) done simply, or O(E log E) using an LCA-based query for the heaviest edge on a path (Chapter 18).
  • Critical and pseudo-critical edges. An edge is critical if banning it makes the MST heavier. It is pseudo-critical if forcing it in does not make the MST heavier. Run Kruskal V times, each time with one edge forced or banned.
  • Minimum spanning forest. Kruskal works on a disconnected graph without changes. Just do not insist on V−1 edges.
  • Directed MST (arborescence). A completely different problem that needs the Chu-Liu/Edmonds algorithm. Neither Prim nor Kruskal works here, because the cut property does not hold for one-way edges.
  • Borůvka's algorithm. A third MST algorithm. In each round, it adds the cheapest outgoing edge from every component at the same time. It is the basis of parallel and distributed MST algorithms.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 WHICH ALGORITHM
Sparse graph and an edge list you can sort: Kruskal with DSU. Dense graph or a complete graph on points: O(V²) Prim with no heap at all.
💡 MAXIMUM SPANNING
Negate the weights and the same code gives the maximum spanning tree. No new algorithm needed.
💡 BOTTLENECK
The minimum possible maximum edge between two nodes lies on the MST. That is why "minimise the largest edge" problems are MST problems in disguise.
⚠️
Common mistakes
  • No disconnection check. Without used == V−1, you return a minimum spanning forest's weight as if it were a single tree.
  • In Prim, pushing weight + w. That is Dijkstra. It computes path costs, not an MST.
  • Leaving out if(visited[node]) continue; in Prim. You add the same node, and its edge weight, more than once. The total comes out too big.
  • Adding the weight before the visited check. Order matters: skip first, then add.
  • Forgetting greater<>. A default priority_queue is a max-heap (biggest on top), so you build a maximum spanning tree.
  • Mixing {weight,node} and {node,weight} orders in one file. It compiles, it runs, and it gives the wrong answer.
  • Using an MST for shortest paths. It solves a completely different problem.
  • Using Prim or Kruskal on a directed graph. The cut property fails there; you need Chu-Liu/Edmonds.
  • Building a full edge list for a complete graph. At V = 10⁴ that is 5 × 10⁷ edges. Use the O(V²) Prim instead.
  • Assuming the MST is unique. It is only guaranteed unique when all weights are distinct.

Interview drill

Warm-up: Implement an MST and justify the greedy.

How a strong answer sounds
I would use Kruskal. Sort all edges by weight. Then add each edge whose two ends are not already connected. To test that, I use a DSU whose unite returns false when both ends share a root — that true/false result is the cycle test. Stop at V−1 edges. If fewer than V−1 were added, the graph is disconnected and there is no spanning tree. The sort costs O(E log E), which dominates, plus O(E·α) for the DSU. Correctness comes from the cut property: split the nodes into any two non-empty groups, and the lightest edge crossing between them is in some MST. The proof is an exchange argument. If an MST leaves out that lightest crossing edge e, adding e creates a cycle. That cycle must cross the cut an even number of times, so it contains another crossing edge f with weight(f) ≥ weight(e). Swapping them gives a spanning tree that is no heavier. Kruskal only ever adds the lightest edge joining two separate components. That is exactly the lightest edge across that component's cut, so every choice is safe. The same theorem proves Prim, which grows one tree and always takes the lightest edge leaving it — there the cut is (tree, everything else). And the cycle property — the heaviest edge on any cycle is in no MST — is what allows Kruskal to reject an edge.

Deeper: Prim or Kruskal — how do you choose, and how is Prim related to Dijkstra?

How a strong answer sounds
Mostly by the input format and how dense the graph is. Kruskal wants an edge list and runs in O(E log E). So it is the natural choice when the edges are given directly, or when they arrive already sorted (then it is effectively O(E·α)). It also suits a graph that may be disconnected: it produces a minimum spanning forest with no special handling. Prim wants an adjacency list and runs in O(E log V) with a heap, which is about the same for sparse graphs. But Prim has a version Kruskal does not. On a dense graph you can drop the heap entirely. Instead, keep a plain array of "cheapest known edge to each unvisited node" and scan it for the minimum each round. That is O(V²), with no log factor and no sorting. It is strictly better when E is around V². It is the right answer for problems like "connect all points where cost is Manhattan distance": the graph is complete, and building 5 × 10⁷ edges just to sort them would be absurd. As for Dijkstra: Prim is Dijkstra with one change. Both use a min-heap of {key, node}. Both skip nodes that are already finished with a lazy check. The only difference is what gets pushed. Dijkstra pushes dist[node] + weight, because it adds up a path cost from a source. Prim pushes weight alone, because each edge is paid once when its node joins the tree. Writing weight + w in Prim by accident quietly turns it into Dijkstra and gives a wrong total.

🧠 Key takeaways

  • The cut property — the lightest edge across any cut is in some MST — proves both Prim and Kruskal with one swap argument.
  • Kruskal is "sort, then DSU". unite returning false is the cycle test. Check used == V−1 to confirm the graph is connected.
  • Prim is Dijkstra that pushes weight instead of dist + weight. Everything else is identical.
  • Use Kruskal for edge lists and sparse graphs. Use the O(V²) array Prim for dense or complete graphs.
  • An MST minimises the total weight and the bottleneck (heaviest) edge. It does not give shortest paths, and it is not a Steiner tree.

Check your understanding

What is the cut property?

This one theorem proves both algorithms. Prim takes the lightest edge leaving its tree. Kruskal takes the lightest edge joining two components. Both are the lightest edge crossing some cut. (The other statements are true, but they are not the cut property.)

What single change turns Dijkstra into Prim?

Dijkstra adds up a path cost from a source. Prim pays for each edge once, when its node joins the tree. The heap, the lazy skip and the {key,node} order are all identical. That is why writing weight + w by accident quietly turns Prim into Dijkstra.

In Kruskal, why does dsu.unite(u,v) returning false mean you must skip the edge?

That true/false result is the cycle test, which is why Chapter 22 insisted on returning it. The cycle property says skipping is safe: the heaviest edge on a cycle is in no MST. Because we process edges from lightest to heaviest, this edge is the heaviest one on the cycle it would close.

You are asked to connect 10⁴ points where the cost between any two is their Manhattan distance. Which algorithm?

E ≈ V²/2. Kruskal's sort would cost 5 × 10⁷ log(5 × 10⁷). The array Prim is 10⁸ simple operations, with no extra memory and no heap, working out each distance when it needs it.

Which of these is a property an MST does guarantee?

This is the bottleneck property, proved by the same swap argument. MST paths are not shortest paths. Connecting only some nodes, using others as stepping stones, is the NP-hard Steiner tree problem. And the MST is only guaranteed unique when all weights are different.
