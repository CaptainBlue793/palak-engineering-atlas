Minimum Spanning Trees: Prim & Kruskal

Connect every node at minimum total cost. Two greedy algorithms solve it, they look nothing alike, and both are proved correct by the same one-line fact — the cut property. Kruskal is Chapter 22's DSU with a sort in front of it; Prim is Chapter 29's Dijkstra with one operator changed. Recognising those two reuses is most of what this chapter is for.

  • State the cut property and use it to prove both algorithms in one argument
  • Write Kruskal as sort-plus-DSU, using the boolean return as the cycle test
  • Write Prim as Dijkstra with weight instead of dist + weight
  • Choose between them from the graph's density
  • Know what an MST does not give you — shortest paths, and Steiner trees

The problem, and the one fact that solves it

Given a connected, undirected, weighted graph, find a subset of edges that connects all V nodes with minimum total weight. Such a subset has exactly V−1 edges and no cycles — it is a spanning tree.

✂️
The cut property — and why it proves both algorithms at once

A cut is any partition of the nodes into two non-empty sets. The claim:

For any cut, the lightest edge crossing it belongs to some MST.

Proof (exchange argument). Let e be a lightest crossing edge, and suppose an MST T does not contain it. Adding e to T creates a cycle, and that cycle must cross the cut an even number of times — so it contains at least one other crossing edge f. Since e is lightest, weight(e) ≤ weight(f). Swap them: T − f + e is still spanning, still acyclic, and weighs no more. So there is an MST containing e. ∎

Now both algorithms fall out. Prim maintains a growing tree and always adds the lightest edge leaving it — that is exactly the lightest edge crossing the cut (tree, rest). Kruskal adds the lightest edge joining two different components — which is the lightest edge crossing the cut (that component, everything else). Two algorithms, one theorem. And the mirror statement, the cycle property — the heaviest edge on any cycle is in no MST — is what justifies Kruskal rejecting an edge.

Kruskal: sort the edges, use DSU as the cycle test

Kruskal's MSTO(E log E)O(V)
// The DSU from Chapter 22. unite() returning false means "already connected",
// which is exactly "this edge would create a cycle" — the whole cycle test.
class DSU{
	vector<int> parent,rank;

public:
	DSU(int n){
		parent.resize(n);
		rank.resize(n,0);

		for(int i=0;i<n;i++){
			parent[i]=i;
		}
	}

	int find(int x){
		if(x==parent[x])return x;

		return parent[x]=find(parent[x]);
	}

	bool unite(int x,int y){
		int px=find(x);
		int py=find(y);

		if(px==py)return false;

		if(rank[px]>rank[py]){
			parent[py]=px;
		}else if(rank[px]<rank[py]){
			parent[px]=py;
		}else{
			parent[py]=px;
			rank[px]++;
		}

		return true;
	}
};

// {weight, {u, v}} so the built-in comparison sorts by weight (Chapter 8).
typedef pair<int,pair<int,int>> P;

int kruskal(int N,vector<vector<int>> &edges){
	vector<P> list;
	for(auto &e:edges){
		int u=e[0];
		int v=e[1];
		int w=e[2];
		list.push_back({w,{u,v}});
	}

	sort(list.begin(),list.end());        // O(E log E) — the dominant cost

	DSU dsu(N);
	int MST=0;
	int used=0;

	for(auto &it:list){
		int w=it.first;
		auto [u,v]=it.second;

		if(dsu.unite(u,v)){        // false = would form a cycle, so skip
			MST+=w;
			used++;

			if(used==N-1)break;     // a spanning tree has exactly V-1 edges
		}
	}

	if(used!=N-1)return -1;         // graph is disconnected: no spanning tree

	return MST;
}
Two guards that are easy to omit. The break at V−1 edges is an optimisation — you are done, and continuing just rejects the rest. The final used != N−1 check is correctness: on a disconnected graph there is no spanning tree at all, and without this you silently return the weight of a minimum spanning forest as if it were a tree.
✍️
My convention: pair<int,pair<int,int>> with the weight first, and a typedef

Packing the edge as {weight, {u, v}} means sort needs no comparator at all — pair's built-in < compares the weight first and breaks ties on the endpoints, which is exactly what you want. The typedef P keeps the declarations readable, and auto [u,v] = it.second; unpacks cleanly. Same principle as the {weight, node} ordering in Dijkstra (Chapter 29): put the sort key first and the language does the work.

Prim: grow one tree with a heap

Prim's MSTO(E log V)O(V + E)
// This is Dijkstra (Chapter 29) with ONE change: we push the edge weight
// itself rather than dist[node]+weight, because we care about the cost of
// joining the tree, not the distance from a source.
int prims(vector<vector<pair<int,int>>> &graph,int N){
	vector<bool> visited(N,false);
	priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> pq;

	pq.push({0,0});                // {weight, node} — start anywhere
	int MST=0;
	int used=0;

	while(!pq.empty()){
		int weight=pq.top().first;
		int node=pq.top().second;
		pq.pop();

		if(visited[node])continue;    // lazy deletion, same as Dijkstra

		MST+=weight;
		visited[node]=true;
		used++;

		for(auto &[neighbour,w]:graph[node]){
			if(!visited[neighbour])
			pq.push({w,neighbour});    // w, NOT weight+w — that would be Dijkstra
		}
	}

	if(used!=N)return -1;            // disconnected

	return MST;
}
Prim vs Dijkstra is one character. Dijkstra pushes dist[node] + weight because it accumulates a path cost; Prim pushes weight alone because each edge's cost is paid once when the node joins the tree. Everything else — the min-heap, the lazy if(visited) continue;, the {key, node} ordering — is identical. If you can write one, you can write the other.
🔁
Note the adjacency order flips between the two snippets

Chapter 29's Dijkstra stored {weight, neighbour} and unpacked auto &[weight,neighbour]. This Prim stores {neighbour, weight} and unpacks auto &[neighbour,w]. Both work, because Prim does not sort the adjacency list — it only sorts inside the heap, where the pair is built explicitly as {w, neighbour}. But pick one convention per file and never mix them: silently swapping a pair's fields produces plausible wrong answers, and it is one of the hardest graph bugs to spot by reading. State your convention in a comment at the top of the adjacency-building loop.

In practice

Default to Kruskal if you already have an edge list — it is shorter, and DSU is code you will reuse anyway. Use Prim when you are handed an adjacency list, when the graph is dense (the O(V²) array version has no heap at all), or when nodes are generated implicitly. A common case: “connect all points with cost = Manhattan distance” gives a complete graph with E = V²/2, so the O(V²) Prim is the right answer and building an edge list of 5 × 10⁷ entries to sort is not.

What an MST does not give you

🛣️

Not shortest paths

The MST path between two nodes can be far longer than their true shortest path. MST minimises the total edge weight, not any individual distance. Use Dijkstra for paths.

🎯

Not a Steiner tree

If you only need to connect a subset of nodes and may use others as waypoints, that is the Steiner tree problem — NP-hard. MST connects all nodes.

🔢

Not unique

Distinct edge weights give a unique MST. With ties, several MSTs exist — all of the same total weight. "Count the MSTs" is a different, harder problem.

🏔️

But it does minimise the bottleneck

The MST path between any two nodes minimises the maximum edge on the route. So "minimise the largest weight you must cross" is an MST problem.

✂️

And it exposes critical edges

An edge in every MST is critical; one in no MST is useless. Both are testable by running Kruskal with that edge excluded or forced.

📉

Maximum spanning tree is free

Negate every weight, or sort descending. The cut property works symmetrically, so the same two algorithms apply unchanged.

🏔️
Why the MST minimises the bottleneck — a genuinely useful corollary

Claim: for any two nodes u and v, the path between them in the MST minimises the maximum edge weight over all u–v paths. Suppose some other path had a smaller maximum, m. Then consider the heaviest edge e on the MST path, with weight(e) > m. Removing e splits the MST into two components with u and v on opposite sides — so the alternative path must cross that cut, using some edge f with weight(f) ≤ m < weight(e). Swapping e for f gives a lighter spanning tree, contradicting minimality. ∎ So “minimise the heaviest edge you must traverse” is an MST problem, which is why problems about maximum load, widest path or "swim in rising water" often have an MST solution as well as a binary-search-plus-DSU one.

🧩
The variants worth knowing
  • Second-best MST. For each MST edge, remove it and rerun — O(V·E log E) naively, or O(E log E) with an LCA-based maximum-edge query (Chapter 18).
  • Critical and pseudo-critical edges. An edge is critical if excluding it raises the MST weight; pseudo-critical if forcing it in does not raise the weight. Run Kruskal V times with one edge forced or banned.
  • Minimum spanning forest. Kruskal handles a disconnected graph unchanged; just do not assert V−1 edges.
  • Directed MST (arborescence). A completely different problem needing Chu-Liu/Edmonds. Neither Prim nor Kruskal applies — the cut property does not hold for directed edges.
  • Borůvka's algorithm. A third MST algorithm that adds the cheapest edge out of every component simultaneously. The basis of parallel and distributed MST.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 WHICH ALGORITHM
Sparse graph and an edge list you can sort: Kruskal with DSU. Dense graph or a complete graph on points: O(V²) Prim with no heap at all.
💡 MAXIMUM SPANNING
Negate the weights and the same code gives the maximum spanning tree. No new algorithm needed.
💡 BOTTLENECK
The minimum possible maximum edge between two nodes lies on the MST. That is why "minimise the largest edge" problems are MST problems in disguise.
⚠️
Common mistakes
  • No disconnection check. Without used == V−1 you return a minimum spanning forest's weight as if it were a tree.
  • In Prim, pushing weight + w. That is Dijkstra, and it computes path costs rather than an MST.
  • Omitting if(visited[node]) continue; in Prim. You add the same node — and its edge weight — more than once, inflating the total.
  • Adding the weight before the visited check. Order matters: skip first, then add.
  • Forgetting greater<>. A default priority_queue is a max-heap, so you build a maximum spanning tree.
  • Mixing {weight,node} and {node,weight} conventions in one file. Compiles, runs, wrong answer.
  • Using MST for shortest paths. Different objective entirely.
  • Applying Prim or Kruskal to a directed graph. The cut property fails; you need Chu-Liu/Edmonds.
  • Building an explicit edge list for a complete graph. At V = 10⁴ that is 5 × 10⁷ edges — use the O(V²) Prim instead.
  • Assuming the MST is unique. It is only guaranteed unique when all weights are distinct.

Interview drill

Warm-up: Implement an MST and justify the greedy.

How a strong answer sounds
I would use Kruskal: sort all edges by weight and add each one whose endpoints are not already connected, testing that with a DSU whose unite returns false when they share a root — that boolean is the cycle test. Stop at V−1 edges, and if fewer than V−1 were added the graph is disconnected and there is no spanning tree. O(E log E) for the sort, which dominates, plus O(E·α) for the DSU. The correctness comes from the cut property: for any partition of the nodes into two non-empty sets, the lightest edge crossing it is in some MST. The proof is an exchange argument — if an MST omits that lightest crossing edge e, adding e creates a cycle, that cycle must cross the cut an even number of times so it contains another crossing edge f with weight(f) ≥ weight(e), and swapping them gives a spanning tree no heavier. Kruskal only ever adds the lightest edge joining two distinct components, which is precisely the lightest edge across that component's cut, so every choice is safe. The same theorem proves Prim, which grows a single tree and always takes the lightest edge leaving it — the cut there being (tree, everything else). And the cycle property, the mirror statement that the heaviest edge on any cycle is in no MST, justifies Kruskal rejecting an edge.

Deeper: Prim or Kruskal — how do you choose, and how is Prim related to Dijkstra?

How a strong answer sounds
Mostly by the input form and the density. Kruskal wants an edge list and is O(E log E), so it is the natural choice when edges are given directly, when they arrive pre-sorted (then it is effectively O(E·α)), or when the graph may be disconnected — it produces a minimum spanning forest with no special handling. Prim wants an adjacency list and is O(E log V) with a heap, which is the same order for sparse graphs, but Prim has a variant Kruskal does not: on a dense graph you can drop the heap entirely and keep a plain array of "cheapest known edge to each unvisited node", scanning for the minimum each round, which is O(V²) with no log factor and no sorting. That is strictly better when E is around V², and it is the right answer for problems like "connect all points where cost is Manhattan distance", where the graph is complete and materialising 5 × 10⁷ edges to sort would be absurd. As for Dijkstra: Prim is Dijkstra with one change. Both use a min-heap of {key, node}, both skip already-finalised nodes with a lazy check, and the only difference is what gets pushed — Dijkstra pushes dist[node] + weight because it accumulates a path cost from a source, while Prim pushes weight alone because each edge is paid once when its node joins the tree. Writing weight + w in Prim by accident turns it silently into Dijkstra and produces a wrong total.

🧠 Key takeaways

  • The cut property — the lightest edge across any cut is in some MST — proves Prim and Kruskal in one exchange argument.
  • Kruskal is sort plus DSU, and unite returning false is the cycle test; check used == V−1 for connectivity.
  • Prim is Dijkstra with weight pushed instead of dist + weight; everything else is identical.
  • Kruskal for edge lists and sparse graphs; the O(V²) array Prim for dense or complete graphs.
  • An MST minimises total weight and the bottleneck edge — but not shortest paths, and it is not a Steiner tree.

Check your understanding

What is the cut property?

This single theorem proves both algorithms: Prim takes the lightest edge leaving its tree, Kruskal the lightest edge joining two components — both are lightest crossing edges for their respective cuts. (The other statements are true but are not the cut property.)

What single change turns Dijkstra into Prim?

Dijkstra accumulates a path cost from a source; Prim pays each edge once when its node joins the tree. The heap, the lazy skip and the {key,node} ordering are all identical — which is why writing weight + w by accident silently turns Prim into Dijkstra.

In Kruskal, why does dsu.unite(u,v) returning false mean you must skip the edge?

That boolean is the cycle test, which is why Chapter 22 insisted on returning it. Skipping is justified by the cycle property: the heaviest edge on a cycle is in no MST, and since we sort ascending this edge is that one.

You are asked to connect 10⁴ points where the cost between any two is their Manhattan distance. Which algorithm?

E ≈ V²/2. Kruskal's sort would be 5 × 10⁷ log(5 × 10⁷); the array Prim is 10⁸ simple operations with no allocation and no heap, computing distances on the fly.

Which of these is a property an MST does guarantee?

The bottleneck property, proved by the same exchange argument. MST paths are not shortest paths; connecting a subset with waypoints is the NP-hard Steiner tree problem; and uniqueness requires all weights to be distinct.
