Prefix Sums & Difference Arrays

One O(n) precomputation turns every range-sum query into a single subtraction. It is the cheapest trick in the book, and it is also the tool that rescues you when a sliding window fails — which, as Chapter 5 showed, happens the moment negative numbers appear. The difference array is its exact mirror image: it makes range updates O(1) instead of range queries.

  • Build a prefix-sum array with the off-by-one-proof convention and query any range in O(1)
  • Derive the 2D inclusion–exclusion formula rather than memorising it
  • Use the difference array so a range update costs two writes
  • Solve “subarray sum equals K” with negatives using prefix sums plus a hash map
  • Apply prefix XOR, prefix count and prefix min — the same idea past addition

The idea, and the convention that kills the off-by-one

Define P[i] as the sum of the first i elements — so P[0] = 0, P[1] = a[0], and P[n] is the total. That gives a size-(n+1) array, and it is worth the extra slot because the query formula becomes clean:

sum of a[l..r] (inclusive) = P[r+1] − P[l]

The alternative convention — P[i] = sum of a[0..i], size n — forces you to special-case l == 0 because P[-1] does not exist. That special case is where the bug lives. Use the sentinel zero.

prefix build + range queryO(n) build, O(1) queryO(n)
// P[i] = sum of the first i elements. P[0]=0 is the sentinel that removes
// the l==0 special case. Note the size is n+1, not n.
vector<long long> buildPrefix(vector<int> &a){
	int n=a.size();
	vector<long long> P(n+1,0);

	for(int i=0;i<n;i++)
	P[i+1]=P[i]+a[i];

	return P;
}

// Inclusive range [l,r]. No branch, no edge case.
long long rangeSum(vector<long long> &P,int l,int r){
	return P[r+1]-P[l];
}
Why long long: 10⁵ elements of magnitude 10⁹ sum to 10¹⁴, which overflows a 32-bit int at around 2 × 10⁹. Prefix sums overflow far more readily than people expect, because the whole point is to accumulate. Default to long long and only narrow it if you have checked.

2D prefix sums: derive it, do not memorise it

Same idea in two dimensions. P[i][j] is the sum of the rectangle from (0,0) to (i−1,j−1) — again with a row and column of sentinel zeros.

The build and the query are both inclusion–exclusion, and if you draw the rectangles once you never need to look the formula up again: to get the sum of a rectangle, take the big one, subtract the strip above and the strip to the left, then add back the corner you just subtracted twice.

2D prefix build + rectangle queryO(rows·cols) build, O(1) queryO(rows·cols)
// P[i][j] = sum of grid[0..i-1][0..j-1]. Row 0 and column 0 are sentinel zeros.
vector<vector<long long>> build2D(vector<vector<int>> &grid){
	int rows=grid.size();
	int cols=grid[0].size();
	vector<vector<long long>> P(rows+1,vector<long long>(cols+1,0));

	for(int i=0;i<rows;i++){
		for(int j=0;j<cols;j++){
			// current cell + strip above + strip left - the doubly counted corner
			P[i+1][j+1]=grid[i][j]+P[i][j+1]+P[i+1][j]-P[i][j];
		}
	}

	return P;
}

// Sum of the inclusive rectangle (r1,c1) to (r2,c2).
long long rectSum(vector<vector<long long>> &P,int r1,int c1,int r2,int c2){
	return P[r2+1][c2+1]
	      -P[r1][c2+1]        // strip above
	      -P[r2+1][c1]        // strip to the left
	      +P[r1][c1];         // add back the overlap
}
Build and query are the same formula with the signs flipped. If you can draw the four rectangles, you can rederive both in fifteen seconds — which is much more reliable than remembering which index gets the +1.

Difference arrays: the mirror image

Prefix sums make range queries O(1) at the cost of O(n) updates. Sometimes you need the opposite: many range updates, then read the final array once. That is a difference array.

Store D where D[i] = a[i] − a[i−1]. To add v to every element of a[l..r], you only need two writes: D[l] += v and D[r+1] -= v. A single prefix sum over D at the end reconstructs the real array.

difference array — q range updates, then one readO(1) per update, O(n) to finaliseO(n)
// Each update is 2 writes instead of (r-l+1). Total O(n+q) instead of O(n*q).
vector<long long> applyRangeUpdates(int n,vector<vector<int>> &updates){
	vector<long long> D(n+1,0);      // n+1 so D[r+1] is always writable

	for(auto &u:updates){
		int l=u[0];
		int r=u[1];
		int v=u[2];

		D[l]+=v;
		D[r+1]-=v;                  // safe: index n exists and is never read out
	}

	// one prefix sum turns the deltas back into values
	vector<long long> a(n,0);
	long long running=0;
	for(int i=0;i<n;i++){
		running+=D[i];
		a[i]=running;
	}

	return a;
}
The n+1 size is the whole trick. Without the extra slot, an update ending at the last index writes out of bounds. With it, D[n] absorbs the closing delta and is simply never read back.
✈️
This is the “car pooling” and “meeting rooms” pattern

Any problem shaped as “N intervals each add a load; find the maximum concurrent load” is a difference array. D[start] += load, D[end] -= load, prefix sum, take the maximum. That is the whole solution to car pooling, minimum number of meeting rooms, and maximum number of overlapping intervals — in O(n) after sorting, or O(max coordinate) with no sorting at all when the coordinate range is small.

Prefix sums + hash map: the pattern the window could not do

This is the payoff. “Count subarrays with sum exactly K, negatives allowed” is the problem Chapter 5 proved a sliding window cannot solve. Prefix sums solve it in one pass.

The algebra: a subarray a[j..i] has sum K exactly when P[i+1] − P[j] = K, which rearranges to:

P[j] = P[i+1] − K

So as you sweep i, you already know the current prefix. The question becomes “how many earlier prefixes equal current − K?” — which is a hash-map lookup. Every “subarray with property X” problem where X is expressible as a difference of prefixes becomes a counting problem over a hash map.

subarraySum — count subarrays summing to exactly kO(n)O(n)
// Works with negatives, which is the whole point. A sliding window cannot.
int subarraySum(vector<int> &a,int k){
	unordered_map<long long,int> seen;
	seen[0]=1;                  // the empty prefix — this is the line people forget

	long long running=0;
	int ans=0;

	for(int i=0;i<a.size();i++){
		running+=a[i];

		// every earlier prefix equal to (running-k) closes a subarray summing to k
		if(seen.count(running-k))
		ans+=seen[running-k];

		seen[running]++;
	}

	return ans;
}
seen[0]=1 is not optional. Without it you miss every subarray that starts at index 0, because no earlier prefix of value 0 was ever recorded. On a=[3], k=3 the answer silently becomes 0 instead of 1 — and it is the most common bug in this pattern by a wide margin.
✍️
My convention: look up before you insert

In the loop above, the lookup happens before seen[running]++. That ordering is what guarantees the subarray is non-empty: a prefix cannot pair with itself. Insert first and k=0 starts counting empty subarrays. Same rule in Chapter 9's two-sum: query the map, then add the current element.

“Product of array except self” is prefix-and-suffix, not division

The tempting solution is total product divided by a[i]. It breaks on a single zero and gives nonsense with two. The robust version sweeps twice:

// ans[i] = (product of everything left of i) * (product of everything right of i)
vector<int> productExceptSelf(vector<int> &a){
	int n=a.size();
	vector<int> ans(n,1);

	int running=1;
	for(int i=0;i<n;i++){
		ans[i]=running;          // product of a[0..i-1]
		running*=a[i];
	}

	running=1;
	for(int i=n-1;i>=0;i--){
		ans[i]*=running;         // times product of a[i+1..n-1]
		running*=a[i];
	}

	return ans;
}

O(n) time, O(1) auxiliary space beyond the output, and no division. The two-sweep shape — accumulate left to right into the answer, then right to left into the same answer — shows up in trapping rain water and candy distribution too.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SEEN[0] = 1
For "subarray summing to k" seed the map with {0: 1} before the loop. That single entry is what lets a prefix that is the answer be counted.
💡 MAP 0 TO −1
Equal counts of two symbols becomes "sum equals zero" the moment you map one to +1 and the other to −1. Works for 0s/1s, and for any balanced-pair problem.
⚡ DIFFERENCE ARRAY
For q range-updates and one final read, do not touch the range: add at l, subtract at r+1, then prefix-sum once at the end. O(q + n) instead of O(q·n).
⚠️
Common mistakes
  • Forgetting seen[0] = 1 in the prefix-sum-plus-hash-map pattern. Every subarray starting at index 0 is silently missed.
  • Inserting into the map before querying it. The current prefix pairs with itself and you count empty subarrays, which breaks k = 0.
  • Using int for prefix sums. 10⁵ values of 10⁹ sum to 10¹⁴. The whole point of a prefix is to accumulate, so overflow is the default, not the exception.
  • Sizing the difference array n instead of n+1. An update ending at the last index writes out of bounds.
  • Mixing the two prefix conventions mid-problem. Pick P[0]=0 with size n+1 and never deviate. Half the off-by-ones in this topic are convention drift.
  • Using division for product-except-self. One zero and it is wrong; two zeros and it is very wrong.
  • Building a prefix array for a single query. O(n) build for one O(1) query is just O(n) — the same as scanning. Prefix sums pay off when queries are repeated.

Interview drill

Warm-up: Derive the 2D rectangle-sum formula out loud, without recalling it.

How a strong answer sounds
Let P[i][j] be the sum of everything above and to the left of cell (i,j), exclusive — so P has a sentinel row and column of zeros. For the rectangle from (r1,c1) to (r2,c2) inclusive, start with the biggest prefix rectangle, P[r2+1][c2+1], which covers my target plus a strip above it and a strip to its left. Subtract the strip above, P[r1][c2+1], and the strip to the left, P[r2+1][c1]. The top-left corner region belongs to both strips, so it has now been subtracted twice — add it back once as P[r1][c1]. Four lookups, so O(1) per query. The build uses the same inclusion–exclusion with the signs flipped: P[i+1][j+1] = grid[i][j] + P[i][j+1] + P[i+1][j] − P[i][j]. I would rather draw the four rectangles than memorise which index takes the +1, because the drawing is self-checking.

Deeper: Count subarrays whose sum is divisible by K.

How a strong answer sounds
Same prefix trick, one step further. A subarray a[j..i] is divisible by K exactly when P[i+1] − P[j] ≡ 0 (mod K), which means P[i+1] and P[j] have the same remainder mod K. So I do not need to track prefix values at all — only their remainders. Sweep once keeping a running sum, take ((running % K) + K) % K to normalise negatives into [0,K), and keep a count array of size K. For each position, add the current count of that remainder to the answer, then increment it. Initialise count[0] = 1 for the empty prefix, exactly as in the sum-equals-K version, or you miss every subarray starting at index 0. That is O(n) time and O(K) space, which is better than O(n) space when K is small. The double-modulo is essential in C++ and Java because % on a negative left operand yields a negative result, so a plain running % K would index out of bounds.

🧠 Key takeaways

  • Use P[0]=0 with size n+1; then sum(a[l..r]) = P[r+1] − P[l] with no special case at l = 0.
  • 2D is inclusion–exclusion: big rectangle, minus the strip above, minus the strip left, plus the doubly-subtracted corner.
  • A difference array mirrors a prefix array: two writes per range update, one prefix sum to finalise. It is the interval-overlap pattern.
  • Prefix sums plus a hash map solve subarray-sum problems that a sliding window cannot, because they do not need monotonicity.
  • seen[0]=1, and query the map before inserting the current prefix. Both lines are load-bearing.

Check your understanding

With P[i] defined as the sum of the first i elements, what is the sum of a[l..r] inclusive?

P[r+1] covers a[0..r] and P[l] covers a[0..l−1]; the difference is exactly a[l..r]. The sentinel P[0]=0 is what makes this work at l = 0 with no branch.

In the prefix-sum-plus-hash-map solution to “subarray sum equals K”, why initialise seen[0] = 1?

A subarray starting at index 0 needs an earlier prefix of value 0 to pair with, and the only such prefix is the empty one. Omit it and a=[3], k=3 returns 0. Most common bug in the pattern.

To add v to every element of a[l..r] using a difference array, what do you write?

The increase must persist through index r and stop at r+1, so the cancelling write goes at r+1 — which is why D is sized n+1. Using D[r] -= v ends the range one element early.

Why does the 2D rectangle-sum formula add back P[r1][c1]?

Classic inclusion–exclusion. The strip above and the strip to the left overlap in that corner, so subtracting both removes it twice and one copy must be restored.

Which cannot be answered in O(1) by a prefix array?

Prefix arrays need an invertible operation, so you can subtract off the part you do not want. Sum has subtraction, XOR is its own inverse, counting is a sum. Minimum has no inverse — you need a sparse table (Chapter 24) or a segment tree (Chapter 23).
