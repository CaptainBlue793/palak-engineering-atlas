Prefix Sums & Difference Arrays

A prefix sum is a running total: for each position, the sum of everything up to that point. Doing that work once, in O(n), turns every “what is the sum from here to there?” question into a single subtraction. It is the cheapest trick in the book. It is also what rescues you when a sliding window fails — which, as Chapter 5 showed, happens as soon as negative numbers appear. The difference array is the same idea in reverse: it makes range updates O(1) instead of range queries.

  • Build a prefix-sum array using the convention that prevents off-by-one bugs, and answer any range query in O(1)
  • Work out the 2D formula from a picture instead of memorising it
  • Use a difference array so that updating a whole range costs just two writes
  • Solve “subarray sum equals K” with negative numbers, using prefix sums plus a hash map
  • Apply the same idea to XOR, counts and minimums, not just addition

The idea, and the convention that kills the off-by-one

Why bother? Suppose you get an array of 10⁵ numbers and 10⁵ questions, each asking “what is the sum from index l to index r?”. Adding up each range from scratch can take up to 10⁵ steps per question, so 10¹⁰ steps in total — far too slow. With a prefix array you spend 10⁵ steps once, and then each question costs one subtraction. This “precompute once, answer many times” idea shows up constantly: in range queries, in subarray counting, and in image processing, where 2D prefix sums (called “integral images”) let you sum any rectangle of pixels instantly.

Define P[i] as the sum of the first i elements. So P[0] = 0, P[1] = a[0], and P[n] is the total of everything. That makes the array one slot longer than the data, and that extra slot is worth it, because the query formula comes out clean:

sum of a[l..r] (inclusive) = P[r+1] − P[l]

Why that formula? P[r+1] is the sum of a[0..r]. P[l] is the sum of a[0..l−1] — exactly the part in front of your range. Subtract it, and the shared beginning cancels out, leaving only a[l..r]. With numbers: for a = [3, 1, 4, 1, 5], the prefix array is P = [0, 3, 4, 8, 9, 14]. The sum of a[1..3] is P[4] − P[1] = 9 − 3 = 6, and indeed 1 + 4 + 1 = 6. The sum of a[0..2] is P[3] − P[0] = 8 − 0 = 8, with no special case for starting at 0.

The other common convention — P[i] = sum of a[0..i], with size n — forces you to write a special case for l == 0, because P[-1] does not exist. That special case is where bugs live. Use the extra leading zero (a “sentinel”: a placeholder slot that exists only to make the formula simple).

prefix build + range queryO(n) build, O(1) queryO(n)
// P[i] = sum of the first i elements. P[0]=0 is the sentinel that removes
// the l==0 special case. Note the size is n+1, not n.
vector<long long> buildPrefix(vector<int> &a){
	int n=a.size();
	vector<long long> P(n+1,0);

	for(int i=0;i<n;i++)
	P[i+1]=P[i]+a[i];

	return P;
}

// Inclusive range [l,r]. No branch, no edge case.
long long rangeSum(vector<long long> &P,int l,int r){
	return P[r+1]-P[l];
}
Why long long: 10⁵ elements of size 10⁹ add up to 10¹⁴. A 32-bit int runs out at about 2 × 10⁹, so the value wraps around and goes wrong. Prefix sums overflow much more easily than people expect, because adding things up is the entire point. Use long long by default, and only use something smaller once you have checked the numbers.

2D prefix sums: derive it, do not memorise it

Same idea, now on a grid. P[i][j] is the sum of the rectangle from (0,0) to (i−1,j−1) — again with a row and a column of placeholder zeros along the top and left.

Both building and querying use inclusion–exclusion: add the big pieces, subtract the overlaps, then add back anything you subtracted twice. Draw the rectangles once and you will never need to look the formula up again. To get the sum of a rectangle: take the big prefix rectangle, subtract the strip above it and the strip to its left, then add back the corner that both strips covered.

2D prefix build + rectangle queryO(rows·cols) build, O(1) queryO(rows·cols)
// P[i][j] = sum of grid[0..i-1][0..j-1]. Row 0 and column 0 are sentinel zeros.
vector<vector<long long>> build2D(vector<vector<int>> &grid){
	int rows=grid.size();
	int cols=grid[0].size();
	vector<vector<long long>> P(rows+1,vector<long long>(cols+1,0));

	for(int i=0;i<rows;i++){
		for(int j=0;j<cols;j++){
			// current cell + strip above + strip left - the doubly counted corner
			P[i+1][j+1]=grid[i][j]+P[i][j+1]+P[i+1][j]-P[i][j];
		}
	}

	return P;
}

// Sum of the inclusive rectangle (r1,c1) to (r2,c2).
long long rectSum(vector<vector<long long>> &P,int r1,int c1,int r2,int c2){
	return P[r2+1][c2+1]
	      -P[r1][c2+1]        // strip above
	      -P[r2+1][c1]        // strip to the left
	      +P[r1][c1];         // add back the overlap
}
Build and query are the same formula with the plus and minus signs swapped. If you can draw the four rectangles, you can work both out in fifteen seconds. That is far more reliable than trying to remember which index gets the +1.

Check one build step: P[2][2] = grid[1][1] + P[1][2] + P[2][1] − P[1][1] = 5 + 3 + 5 − 1 = 12, which is 1 + 2 + 4 + 5. Now query the bottom-right 2 × 2 square, (1,1) to (2,2): P[3][3] − P[1][3] − P[3][1] + P[1][1] = 45 − 6 − 12 + 1 = 28. By hand, 5 + 6 + 8 + 9 = 28. The 6 removed the top row, the 12 removed the left column, and the 1 (cell (0,0)) was in both, so it is added back once.

Difference arrays: the mirror image

Prefix sums make range queries O(1), but any change to the data costs O(n) to rebuild. Sometimes you need the opposite: lots of range updates first, then read the final array once. That is what a difference array is for.

Instead of storing values, store the changes: D[i] = a[i] − a[i−1]. To add v to every element of a[l..r], you need only two writes: D[l] += v switches the increase on, and D[r+1] -= v switches it off again. At the end, one prefix sum over D rebuilds the real array.

difference array — q range updates, then one readO(1) per update, O(n) to finaliseO(n)
// Each update is 2 writes instead of (r-l+1). Total O(n+q) instead of O(n*q).
vector<long long> applyRangeUpdates(int n,vector<vector<int>> &updates){
	vector<long long> D(n+1,0);      // n+1 so D[r+1] is always writable

	for(auto &u:updates){
		int l=u[0];
		int r=u[1];
		int v=u[2];

		D[l]+=v;
		D[r+1]-=v;                  // safe: index n exists and is never read out
	}

	// one prefix sum turns the deltas back into values
	vector<long long> a(n,0);
	long long running=0;
	for(int i=0;i<n;i++){
		running+=D[i];
		a[i]=running;
	}

	return a;
}
The n+1 size is what makes this safe. Without the extra slot, an update that ends at the last index writes past the end of the array. With it, D[n] catches that final “switch off” value and is simply never read back.

Why do two writes do the job of a whole range? Because the final prefix sum carries each value forward. A +v at index l is added into every position from l onwards. The −v at index r+1 cancels it from r+1 onwards. So the net effect is +v on exactly l..r. A trace with n = 5, starting from all zeros:

  • Add 2 to [1, 3]: D[1] += 2, D[4] -= 2.
  • Add 3 to [2, 4]: D[2] += 3, D[5] -= 3 (the spare slot).
  • D is now [0, 2, 3, 0, −2, −3]. The running total over the first 5 slots gives a = [0, 2, 5, 5, 3].

Check by hand: index 1 gets only the first update (2), indices 2 and 3 get both (5), and index 4 gets only the second (3). Four writes instead of six, and the saving grows with the length of the ranges. When to choose which: many queries on data that does not change → prefix sums. Many range updates, then one read at the end → difference array. Updates and queries mixed together → neither; that needs a Fenwick or segment tree (Chapters 23–24).

✈️
This is the “car pooling” and “meeting rooms” pattern

Any problem of the form “N intervals each add some load; find the largest load at any one moment” is a difference array. Do D[start] += load, D[end] -= load, take a prefix sum, then take the maximum. That is the entire solution to car pooling, to “how many meeting rooms do I need”, and to “how many intervals overlap at once”. It is O(n) after sorting — or O(max coordinate) with no sorting at all, when the range of coordinates is small.

One edge case to read carefully in these problems: is the end point inside the interval? In car pooling, passengers get off at to, so that seat is free again at to itself. The interval is really [from, to), and you write D[to] -= load, not D[to+1]. For an inclusive range [l, r], as in the code above, it is D[r+1]. Getting this wrong shifts every “switch off” by one and over-counts the load at each drop-off point.

Prefix sums + hash map: the pattern the window could not do

This is the payoff. “Count subarrays with sum exactly K, negatives allowed” is the problem Chapter 5 showed a sliding window cannot handle. Prefix sums solve it in a single pass.

Here is the algebra. A subarray a[j..i] has sum K exactly when P[i+1] − P[j] = K. Move things around and that becomes:

P[j] = P[i+1] − K

As you sweep i along the array, you already know the current running total. So the question turns into “how many earlier running totals equal current − K?” That is just a hash-map lookup. Any “subarray with property X” problem, where X can be written as the difference of two prefixes, turns into counting with a hash map.

subarraySum — count subarrays summing to exactly kO(n)O(n)
// Works with negatives, which is the whole point. A sliding window cannot.
int subarraySum(vector<int> &a,int k){
	unordered_map<long long,int> seen;
	seen[0]=1;                  // the empty prefix — this is the line people forget

	long long running=0;
	int ans=0;

	for(int i=0;i<a.size();i++){
		running+=a[i];

		// every earlier prefix equal to (running-k) closes a subarray summing to k
		if(seen.count(running-k))
		ans+=seen[running-k];

		seen[running]++;
	}

	return ans;
}
seen[0]=1 is not optional. Without it, you miss every subarray that starts at index 0, because no earlier running total of 0 was ever recorded. On a=[3], k=3 the answer quietly becomes 0 instead of 1. This is by far the most common bug in this pattern.

A dry run with a negative number in it: a = [1, 2, -1, 2], k = 3. The map starts as {0: 1}.

The answer is 2. The hit at i = 1 came from the empty prefix seen[0] — without it, [1, 2] would be missed. The hit at i = 3 found the running total 1 from i = 0, meaning “everything after index 0 up to index 3 sums to 3”. Notice that the sum went down at i = 2 and nothing broke: the map does not care which way the running total moves. That is exactly why this works where the window failed.

✍️
My convention: look up before you insert

In the loop above, the lookup happens before seen[running]++. That order is what keeps every counted subarray non-empty: a running total cannot pair with itself. If you insert first, then k=0 starts counting empty subarrays. The same rule applies to Chapter 9's two-sum: look in the map first, then add the current element.

The same idea past addition

The prefix trick works for any operation you can undo — one with an inverse, like subtraction undoing addition. With some cleverness, it can even be stretched to a few that you cannot undo.

Why XOR works: any value XORed with itself is 0 (x ^ x = 0), and XOR with 0 changes nothing. So in P[r+1] ^ P[l], the shared part a[0..l−1] appears twice and cancels, just like subtraction cancelled it for sums. Example: a = [5, 3, 6] gives P = [0, 5, 6, 0] (5^3 = 6, 6^6 = 0). The XOR of a[1..2] is P[3] ^ P[1] = 0 ^ 5 = 5, and by hand 3 ^ 6 = 5.

Why min and max do not work: knowing that the smallest value in a[0..9] is 2 and the smallest in a[0..4] is 2 tells you nothing about the smallest in a[5..9]. There is no “minus” for minimum that removes the front part. That is why those queries need different structures.

➗
“Product of array except self” is prefix-and-suffix, not division

The tempting solution is to divide the total product by a[i]. But one zero in the array makes that impossible, and two zeros make it nonsense. The safe version sweeps the array twice:

// ans[i] = (product of everything left of i) * (product of everything right of i)
vector<int> productExceptSelf(vector<int> &a){
	int n=a.size();
	vector<int> ans(n,1);

	int running=1;
	for(int i=0;i<n;i++){
		ans[i]=running;          // product of a[0..i-1]
		running*=a[i];
	}

	running=1;
	for(int i=n-1;i>=0;i--){
		ans[i]*=running;         // times product of a[i+1..n-1]
		running*=a[i];
	}

	return ans;
}

O(n) time, no extra memory beyond the output array, and no division. This two-sweep shape — build up left to right into the answer, then right to left into the same answer — also shows up in trapping rain water and candy distribution.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SEEN[0] = 1
For "subarray summing to k" seed the map with {0: 1} before the loop. That single entry is what lets a prefix that is the answer be counted.
💡 MAP 0 TO −1
Equal counts of two symbols becomes "sum equals zero" the moment you map one to +1 and the other to −1. Works for 0s/1s, and for any balanced-pair problem.
⚡ DIFFERENCE ARRAY
For q range-updates and one final read, do not touch the range: add at l, subtract at r+1, then prefix-sum once at the end. O(q + n) instead of O(q·n).
⚠️
Common mistakes
  • Forgetting seen[0] = 1 in the prefix-sum-plus-hash-map pattern. Every subarray starting at index 0 is quietly missed.
  • Inserting into the map before looking in it. The current running total pairs with itself, so you count empty subarrays — which breaks the k = 0 case.
  • Using int for prefix sums. 10⁵ values of 10⁹ add up to 10¹⁴. Adding things up is the whole point, so overflow is the normal case, not a rare one.
  • Making the difference array size n instead of n+1. An update that ends at the last index then writes past the end.
  • Switching between the two prefix conventions mid-problem. Pick P[0]=0 with size n+1 and stick to it. Half the off-by-one bugs here come from drifting between conventions.
  • Using division for product-except-self. One zero and it is wrong; two zeros and it is very wrong.
  • Building a prefix array for a single query. An O(n) build plus one O(1) query is still O(n) — the same as just scanning. Prefix sums pay off when you query many times.

Interview drill

Warm-up: Derive the 2D rectangle-sum formula out loud, without recalling it.

How a strong answer sounds
Let P[i][j] be the sum of everything above and to the left of cell (i,j), not including that cell — so P has an extra row and column of zeros along the top and left. For the rectangle from (r1,c1) to (r2,c2) inclusive, start with the biggest prefix rectangle, P[r2+1][c2+1]. That covers my target rectangle plus a strip above it and a strip to its left. Subtract the strip above, P[r1][c2+1], and the strip to the left, P[r2+1][c1]. The top-left corner belongs to both strips, so I have now removed it twice — add it back once as P[r1][c1]. Four lookups, so O(1) per query. Building the table uses the same idea with the signs swapped: P[i+1][j+1] = grid[i][j] + P[i][j+1] + P[i+1][j] − P[i][j]. I would rather draw the four rectangles than memorise which index gets the +1, because the drawing checks itself.

Deeper: Count subarrays whose sum is divisible by K.

How a strong answer sounds
Same prefix trick, one step further. A subarray a[j..i] is divisible by K exactly when P[i+1] − P[j] ≡ 0 (mod K) — which means P[i+1] and P[j] leave the same remainder when divided by K. So I do not need the prefix values at all, only their remainders. Sweep once, keeping a running sum, and take ((running % K) + K) % K to turn negative remainders into the range [0,K). Keep a count array of size K. At each position, add the current count for that remainder to the answer, then increase that count by one. Start with count[0] = 1 for the empty prefix, exactly as in the sum-equals-K version, or you miss every subarray starting at index 0. That is O(n) time and O(K) space, which beats O(n) space when K is small. The double modulo matters in C++ and Java: % on a negative number gives a negative result, so a plain running % K would index outside the array.

🧠 Key takeaways

  • Use P[0]=0 with size n+1. Then sum(a[l..r]) = P[r+1] − P[l], with no special case when l = 0.
  • The 2D version is inclusion–exclusion: big rectangle, minus the strip above, minus the strip to the left, plus the corner you removed twice.
  • A difference array is the mirror of a prefix array: two writes per range update, then one prefix sum at the end. It is the pattern for overlapping intervals.
  • Prefix sums plus a hash map solve subarray-sum problems a sliding window cannot, because they do not need the sum to move in one direction.
  • seen[0]=1, and look in the map before inserting the current running total. Both lines matter.

Check your understanding

With P[i] defined as the sum of the first i elements, what is the sum of a[l..r] inclusive?

P[r+1] covers a[0..r] and P[l] covers a[0..l−1], so the difference is exactly a[l..r]. The extra leading P[0]=0 is what makes this work at l = 0 without an if.

In the prefix-sum-plus-hash-map solution to “subarray sum equals K”, why initialise seen[0] = 1?

A subarray starting at index 0 needs an earlier running total of 0 to pair with, and the only one is the empty prefix. Leave it out and a=[3], k=3 returns 0. This is the most common bug in the pattern.

To add v to every element of a[l..r] using a difference array, what do you write?

The increase must last through index r and stop at r+1, so the cancelling write goes at r+1. That is why D has size n+1. Writing D[r] -= v instead ends the range one element too early.

Why does the 2D rectangle-sum formula add back P[r1][c1]?

Classic inclusion–exclusion. The strip above and the strip to the left overlap in that corner, so subtracting both removes it twice. One copy has to be put back.

Which cannot be answered in O(1) by a prefix array?

Prefix arrays need an operation you can undo, so you can remove the part you do not want. Addition is undone by subtraction; XOR undoes itself; counting is just addition. Minimum cannot be undone — once a small value is gone from the range, the prefix cannot tell you the next smallest. For that you need a sparse table (Chapter 24) or a segment tree (Chapter 23).
