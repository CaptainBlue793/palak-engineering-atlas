Memory: Stack, Heap & Pointers

Why does a DSA course care where variables live? Three reasons. Recursion uses memory you can't see, and too much of it crashes the program. Linked lists and trees are built from pointers, so you need to know what a pointer is. And problems have a memory limit, so you need to estimate how much your arrays take. This chapter builds a clear picture of memory — addresses, the stack, the heap, pointers, references, and the structs that trees and lists are made of.

  • Use pointers (&, *, ->, nullptr) and references, and tell them apart
  • Define a struct node, create nodes with new, and link them
  • Estimate a program's memory against a 256 MB limit

Memory is a row of numbered boxes

Picture your program's memory as one enormously long street of boxes, each holding one byte, and each with a house number called its address. A variable occupies a few neighbouring boxes: an int takes 4, a long long 8. An array of 1,000 ints takes 4,000 boxes in a row — which is exactly why a[i] can be found by arithmetic (P4).

You can print any of these with sizeof(x), and a variable's address with &x. The addresses you'll see look like 0x7ffc2a10 — hexadecimal (base 16), the usual way to write memory addresses.

Two regions: the stack and the heap

When your program runs, it uses two main areas of memory, managed in completely different ways.

  • The stack holds each function call's local variables. It's fast and managed automatically: when a function returns, its space is freed at once. But it's small — often 1–8 MB, set by the system or the judge.
  • The heap holds memory you ask for while the program runs. Every vector, string and map keeps its elements on the heap, even when the variable itself is a local. The heap is large — as much as the memory limit allows.

An analogy: the stack is your desk. It's small, and everything on it is cleared away when you finish a task. The heap is a big storage room down the hall. A vector is a note on your desk that says which shelf in the storage room holds your data.

💥
The classic stack crash

Writing int a[1000000]; inside a function puts 4 MB on the stack, which can overflow it and crash with a Runtime Error before your code does anything. vector<int> a(1000000); puts those 4 MB on the heap and is fine. So does declaring the array globally (outside any function), since globals live in their own static region — which is why competitive programmers often put big arrays at the top of the file.

The call stack during recursion

Each time a function is called, a stack frame is pushed onto the stack. It holds that call's parameters and local variables, plus where to continue when it returns. When the call returns, its frame is popped off. Recursion is a function calling itself, so every level of recursion adds a frame. Step through this program to watch it happen.

int factorial(int n){
	if(n<=1)return 1;

	return n*factorial(n-1);
}

int main(){
	vector<int> v={4,1,3};
	int ans=factorial(3);
	cout<<ans<<"\n";          // 6
	return 0;
}
Stack frames and the heap, step by stepWalkthrough
  1. The program begins in main. Its frame holds the local variables v and ans. But v itself is small: it only stores where its elements are. The three numbers [4, 1, 3] live on the heap.
  2. A new frame is pushed with its own n = 3. main is paused, waiting at the line int ans=factorial(3);.
  3. 3 is not ≤ 1, so it needs factorial(2) before it can multiply. Another frame, with a different n, this time 2. Each call has its own copy of its local variables.
  4. Four frames are now alive at once. This is why recursion depth costs space: at the deepest point, every frame on the path is in memory together. Recursion depth n means O(n) stack space.
  5. The base case answers directly without calling again. Its frame is popped, and the value 1 goes back to the caller that was waiting.
  6. The paused frame wakes up exactly where it stopped, finishes 2*1, returns 2 and is popped.
  7. Back in main, ans becomes 6. The stack is as small as it was at the start.
  8. When main returns, its frame is popped. Because v is going away, the vector frees its heap block too. You never wrote any cleanup code — the vector does it for you.
With n = 10⁶ on a chain-shaped input, this would be a million frames — enough to overflow the stack. Chapter 11 shows how deep you can safely go.

A quick depth estimate: if each frame takes about 64 bytes and the stack is 8 MB, the limit is about 8,000,000 ÷ 64 ≈ 125,000 nested calls — fewer with bigger frames or a 1 MB stack. A recursive DFS on a balanced tree of a million nodes goes only about 20 deep and is perfectly safe; on a path-shaped graph of 10⁶ nodes it goes 10⁶ deep and crashes. The algorithm is the same; the shape of the input decides the depth. The fix, when needed, is to replace the recursion with your own explicit stack on the heap.

Pointers and references

Every variable lives at an address. A pointer is a variable that stores an address. A reference is simply another name for an existing variable.

int x=5;
int* p=&x;        // p holds the address of x
*p=7;             // "the thing p points at" = 7, so x is 7
int &r=x;         // r is another name for x
r=9;              // x is 9
int* none=nullptr; // points at nothing

An analogy: a pointer is a slip of paper with a house address written on it. You can copy the slip, change it to another address, or leave it blank (nullptr). A reference is a nickname: “Bob” and “Robert” are the same person. Everything you do to the nickname happens to the person.

SymbolIn a declarationIn an expression
*int* p — p is a pointer to int*p — the value p points at (“dereference”)
&int &r=x — r is a reference to x&x — the address of x
->—p->val — shorthand for (*p).val

Yes, * and & each mean two different things depending on where they appear. That's the single most confusing part of C++ syntax; the table is worth rereading until it's automatic. Following a nullptr crashes the program — which is why tree code in this course always starts with the guard if(!root)return;.

📌 Pointer

Can be empty (nullptr). Can be changed to point somewhere else. Needs * or -> to reach the value. Used to link structures: list nodes, tree nodes.

🏷️ Reference

Must refer to something from the start; can never be re-pointed or null. Used like the variable itself. Used to pass without copying: function parameters, range-for loops.

struct and class: building a node

A struct groups several values into one new type. It's how every linked-list node and tree node in this course is defined — and exactly how LeetCode defines ListNode and TreeNode:

a list node and a tree nodeO(1) each
struct ListNode{
	int val;
	ListNode* next;
	ListNode(int x):val(x),next(nullptr){}      // constructor: sets the fields
};

struct TreeNode{
	int val;
	TreeNode* left;
	TreeNode* right;
	TreeNode(int x):val(x),left(nullptr),right(nullptr){}
};

// build the list 1 -> 2 -> 3
ListNode* head=new ListNode(1);
head->next=new ListNode(2);
head->next->next=new ListNode(3);

// walk it: the loop every linked-list problem starts from
for(ListNode* cur=head;cur;cur=cur->next)
cout<<cur->val<<" ";                         // 1 2 3
Reading it: new ListNode(1) creates a node on the heap and returns its address. Each node's next holds the address of the following node; the last one's is nullptr. The loop condition cur means “while cur is not null”.

Because each node is created with new, it lives on the heap and survives after the function that created it returns — which is exactly what a linked structure needs. In long-running programs you'd release it with delete; in contest and interview code, memory is freed when the program ends, so you'll rarely see delete. A class is the same as a struct except its members are private by default; you'll write small classes for design problems like LRU caches (Chapter 51).

Estimating memory

Problems state a memory limit, typically 256 MB. You can check a design against it in seconds: number of elements × bytes per element. Useful anchors: 256 MB holds about 64 million ints, or 32 million long longs.

Will it fit in the memory limit?Calculator
A 5,000 × 5,000 table of ints is 100 MB — fine. Make it long long and it's 200 MB, close to the edge. 10⁴ × 10⁴ ints is 400 MB: too much, which is often the hint that a 2D DP only needs its previous row (Chapter 38).
⚠️
Common mistakes
  • Huge local arrays. int a[1000000]; inside a function can overflow the stack. Use a vector or a global.
  • Deep recursion on path-shaped inputs. 10⁶ nested calls overflow the stack even though the algorithm is O(n). Use an explicit stack.
  • Following a null pointer. root->left when root is nullptr crashes. Guard first.
  • Returning a pointer or reference to a local variable. The local's stack frame is gone once the function returns; the pointer now points at garbage.
  • Losing the head. Walking a list with head=head->next loses the start. Walk with a separate cur.
  • Confusing * and &. In a declaration they make a pointer or reference; in an expression they dereference or take an address.

Interview drill

Deeper: A recursive DFS works on every small test but gets a Runtime Error when the input is a single long chain of 10⁶ nodes. Why, and what would you do?

How a strong answer sounds
Each recursive call pushes a stack frame, and a chain of 10⁶ nodes means 10⁶ frames alive at the deepest point. The stack is small, often 1–8 MB, so even 50-byte frames overflow it and the program crashes. It is not a logic bug; the algorithm is still O(n). The fix is to keep the same algorithm but store the pending nodes in my own stack on the heap, turning the recursion into a loop. On a balanced tree I would not bother, because the depth is only about log₂ n ≈ 20.

Explain it simply: What's the difference between a pointer and a reference in C++?

How a strong answer sounds
A pointer is a variable holding an address: it can be null, can be re-pointed, and you use * or -> to reach the value. A reference is an alias for an existing object: it must be bound when created, can't be null or re-bound, and is used just like the object. I use references to pass parameters without copying, and pointers to build linked structures like lists and trees, where “no next node” must be expressible as null.

🧠 Key takeaways

  • Memory is numbered bytes; an int takes 4, a long long 8, a pointer 8. &x is x's address.
  • Locals and call frames live on the small stack (1–8 MB); container elements and new objects live on the large heap.
  • Recursion depth is stack space: depth n needs O(n) frames. Path-shaped inputs can overflow it.
  • A pointer stores an address (*p, p->f, nullptr); a reference is another name for a variable.
  • struct nodes with pointer fields, created with new, are how lists and trees are built. Always guard against null.
  • Memory estimate = elements × bytes. 256 MB ≈ 64 million ints.

Check your understanding

A recursive DFS passes every small test but gets a Runtime Error on a path-shaped graph with 10⁶ nodes. What is the most likely cause?

At the deepest point of a recursion, every frame on the path is alive at once. A chain of 10⁶ nodes means 10⁶ frames, which is far more than a stack of a few megabytes can hold. The algorithm is still O(n) time; the fix is an explicit stack (Chapter 11).

After int x=5; int* p=&x; *p=8;, what is x?

p holds x's address, and *p=8 writes 8 into the box p points at — which is x.

Where do the elements of a local vector<int> v(1000000); live?

A vector asks the heap for its element storage. The local variable itself is only about 24 bytes. That's why a million-element vector is fine where int a[1000000]; as a local might crash.

What does root->left mean when root is a TreeNode*?

p->f is shorthand for (*p).f. If root is nullptr, following it crashes — hence the guard if(!root)return;.

About how much memory does a 20,000 × 20,000 array of int need?

4 × 10⁸ elements × 4 bytes = 1.6 × 10⁹ bytes ≈ 1.6 GB, far beyond a 256 MB limit. A different approach — often keeping only one row — is needed.
