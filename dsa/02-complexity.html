Complexity: Time, Space & Amortized

Big-O is not a grade you assign to code after writing it. It is a design tool you use before writing it: a way to eliminate whole families of wrong approaches in seconds. This chapter builds it from counting operations, shows you why push_back is honestly O(1) despite sometimes copying a million elements, and teaches you to read a complexity off a loop nest without thinking.

  • Count operations, then drop constants and lower terms — and know exactly why that is legitimate
  • Read the complexity of nested, sequential and recursive code by inspection
  • Explain amortized O(1) with the doubling argument, not by hand-waving
  • Analyse space including the recursion stack, which most people forget
  • Say where Big-O lies to you, and what to do about it

What Big-O actually claims

An algorithm's running time is some function T(n) of the input size. We almost never want that function exactly — it depends on your CPU, your compiler, whether the data was in cache. What we want is the shape of its growth, because shape is what survives a change of machine and what decides whether you finish in a second or a century.

T(n) = O(f(n)) means: beyond some input size, T(n) is at most a constant multiple of f(n). Formally, there exist constants c > 0 and n₀ such that T(n) ≤ c·f(n) for all n ≥ n₀.

Two things follow from that definition, and they are the two things people get wrong:

It is an upper bound, not an equality

O(n) is technically also O(n²) — the bound is still true, just useless. When we say “this is O(n log n)” we mean the tight bound, which is properly written Θ(n log n). Everyone says O; know that they mean Θ.

It says nothing about small n

“Beyond some input size” is doing real work in that definition. An O(n²) algorithm with a tiny constant beats an O(n log n) one with a huge constant for small n — which is exactly why std::sort switches to insertion sort on small partitions.

🔤
O, Ω and Θ in one line each

O(f) — grows no faster than f (upper bound, the one you quote). Ω(f) — grows at least as fast as f (lower bound, used for proving problems hard). Θ(f) — both, so the growth is exactly f. In interviews, saying “Θ(n log n)” when you mean the tight bound is a small, cheap signal of precision.

Reading a complexity off the code

Four rules cover nearly every case you will meet. Apply them mechanically.

Sequential blocks add, so the biggest wins

An O(n) loop followed by an O(n log n) sort is O(n) + O(n log n) = O(n log n). Sum, then keep the dominant term. This is why an O(n) preprocessing pass before an O(n²) algorithm is free.

Nested loops multiply — but count the real iterations

Two independent loops to n is O(n²). But for(i..n) for(j=i..n) runs n + (n−1) + … + 1 = n(n+1)/2 times, which is still O(n²). And for(i..n) for(j=0..i*0+3) is O(n), because the inner bound does not grow.

Halving gives a log, and a log inside a loop gives n log n

Any loop whose variable is multiplied or divided by a constant runs O(log n) times. So while(n) n/=2; is O(log n), and a binary search inside a loop over n elements is O(n log n).

For recursion, count the tree

Total work = (number of calls) × (work per call), or the Master Theorem when the structure is regular. T(n) = 2T(n/2) + O(n) is O(n log n): log n levels, O(n) work per level. Chapter 37 does this properly.

The loop bound that is not what it looks like

This is O(n log n), not O(n²), and it catches almost everyone:

for(int i=1;i<=n;i++){
	for(int j=i;j<=n;j+=i){   // step is i, not 1
		// O(1) work
	}
}

The inner loop runs n/i times, so the total is n/1 + n/2 + n/3 + … + n/n = n·H(n) ≈ n·ln n. That harmonic-sum pattern is exactly the sieve of Eratosthenes, and it is why the sieve is O(n log log n) rather than O(n²).

Amortized: why push_back is honestly O(1)

A vector has a fixed capacity. When you push past it, it allocates a bigger block and copies everything across — an O(n) operation. So how can push_back be called O(1)?

Because it doubles. Growing from capacity 1 to capacity n involves copies of size 1, 2, 4, 8, …, n/2, and that sum is less than n. Total copying work across n pushes is O(n), so the average per push is O(1). That is what amortized means: not “usually fast”, but “the total over any sequence is bounded, so the average is”.

The proof in one line

With doubling, total copy work to reach n elements is 1 + 2 + 4 + … + n/2 < n (a geometric series sums to less than twice its largest term). Divide by n pushes and you get less than 1 copy per push — constant. With +1 growth, total work is 1 + 2 + 3 + … + n = n(n+1)/2, which is O(n²) total and O(n) per push. Any constant growth factor above 1 gives amortized O(1); adding a constant does not.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 DROP CONSTANTS
O(3n + 5) is O(n), but never drop the constant when comparing two solutions of the same class — a 4n pass and an n pass both being "linear" is how you lose a factor of four you needed.
💡 MEMORY FIRST
Multiply the table out before you allocate: int dp[5000][5000] is 100 MB and will not fit. Memory, not time, is what usually kills a DP.
⚡ HARMONIC
A loop that steps by i inside a loop over i is O(n log n), not O(n²) — the harmonic sum. Worth recognising so you do not over-optimise something already fast enough.
⚠️
Amortized is not the same as average-case

Amortized is a worst-case guarantee over a sequence: no adversary can make n pushes cost more than O(n) total. Average-case is a claim about a probability distribution over inputs: quicksort is O(n log n) on average, but an adversary who knows your pivot rule can hand you an O(n²) input. The first is a promise; the second is a bet. Say which one you mean.

Space complexity — and the stack you forgot

Space is counted the same way, with one thing people systematically miss: recursion depth is space. Each call frame holds parameters, locals and a return address, and they are all live simultaneously.

two traversals, same time, different spaceO(n)O(h) vs O(n)
// Recursive DFS. Time O(n) — every node once.
// Space O(h) where h is the height: h frames are live at the deepest point.
// Balanced tree -> h = log n. Degenerate (a linked list) -> h = n, and it stack-overflows.
void inorder(TreeNode* root,vector<int> &ans){
	if(!root)return;

	inorder(root->left,ans);
	ans.push_back(root->val);
	inorder(root->right,ans);
}

// BFS. Time O(n) too.
// Space O(w) where w is the widest level — and for a complete tree w = n/2, so O(n).
// A wide shallow tree is cheap to recurse and expensive to BFS. The reverse of the above.
void levelorder(TreeNode* root,vector<int> &ans){
	if(!root)return;

	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		TreeNode* node=q.front();
		q.pop();
		ans.push_back(node->val);

		if(node->left)q.push(node->left);
		if(node->right)q.push(node->right);
	}
}
The point: identical time, opposite space profiles. Which one you want depends on the tree's shape, and “O(n) either way” is the answer that shows you did not look.
✍️
My convention: state space as auxiliary space, and say what the letter means

“O(h) auxiliary, h the tree height” is a complete answer. “O(n)” is not, because it hides whether you meant the output, the recursion stack, or a hash map. The output array usually does not count as auxiliary space — but say that out loud rather than letting the interviewer wonder whether you forgot it. Every code block in this course names its letters for this reason.

Where Big-O lies to you

Big-O is the right first tool and a bad last one. Four places it misleads:

O(n) beats O(n log n)Only past the crossover. std::sort drops to insertion sort below ~16 elements because the constant wins.For small fixed n, measure. Do not out-clever a library.
Both are O(n), so both are equally fastA linked-list walk and an array walk are both O(n); the array is often 5–10× faster from cache locality alone (Chapter 3).Prefer contiguous memory when the Big-O ties.

⚠️
Common mistakes
  • Forgetting the recursion stack in space analysis. A recursive solution is never O(1) space. It is O(depth), and on a degenerate input that depth is n.
  • Calling nested loops O(n²) without checking the bounds. for(j=i;j<=n;j+=i) is O(n log n) overall, and while(j*j<=n) is O(√n).
  • Treating amortized and average-case as synonyms. One is a worst-case guarantee over a sequence; the other is a statistical claim that an adversary can break.
  • Dropping a constant that is actually a variable. A loop over the 26 letters is O(1) only if the alphabet is fixed. Over a “character set” of size k it is O(k), and interviewers ask.
  • Not multiplying out the memory. “O(n²) space with n = 10⁵” is 10¹⁰ ints — 40 GB. The complexity is fine and the program will not start.
  • Comparing complexities of different variables. O(V + E) and O(n log n) cannot be ranked until you say how V, E and n relate. Define your letters first.

Interview drill

Warm-up: Prove that push_back is amortized O(1), out loud, without hand-waving.

How a strong answer sounds
A vector holds a capacity; pushing within capacity is O(1), and pushing past it allocates a block twice the size and copies everything, which is O(current size). So the expensive pushes happen at sizes 1, 2, 4, 8 and so on, and their costs are exactly those numbers. Summing the copies performed on the way to n elements gives 1 + 2 + 4 + … + n/2, and a geometric series with ratio 2 sums to less than twice its largest term — so total copying is under n. Add the n cheap writes and total work for n pushes is O(n), hence O(1) amortized. The key detail is that this needs a multiplicative growth factor: with a fixed +1 growth every push reallocates, the total becomes 1 + 2 + … + n = Θ(n²), and the amortized cost is Θ(n).

Deeper: Your solution is O(n) and a colleague's is O(n log n), but theirs benchmarks faster on the real data. What do you do?

How a strong answer sounds
Believe the measurement and find out why, because Big-O deliberately discards exactly the information that explains this. The usual causes: my O(n) version uses a hash map, so every element costs a hash plus a random memory access and a cache miss, while theirs sorts contiguous memory and then does a linear scan with perfect locality. Or my constant factor hides an allocation per element. Or n is small enough that we are below the crossover point entirely. The move is to profile and check cache misses and allocations rather than argue from the exponent — then decide by input size. If production n is always a few thousand, ship theirs. If n might reach 10⁸, mine wins eventually, and I would find the crossover empirically and say so. Asymptotics decide what is possible; measurement decides what is fast.

🧠 Key takeaways

  • O is an upper bound that ignores constants and small n; when people say O they usually mean the tight bound Θ.
  • Sequential blocks add (keep the biggest), nested loops multiply, halving gives a log — and always check the real iteration count.
  • Amortized O(1) comes from multiplicative growth: the geometric series of copies sums to less than n.
  • Recursion depth is space, so a recursive solution is O(depth) auxiliary, never O(1).
  • Big-O ranks what is possible; cache behaviour, constants and memory limits decide what actually runs.

Check your understanding

What is the time complexity of for(int i=1;i<=n;i++) for(int j=i;j<=n;j+=i){}?

The inner loop's step is i, so it runs about n/i times. Summing over i gives n(1 + 1/2 + 1/3 + … + 1/n) = n·H(n) ≈ n·ln n. This harmonic pattern is exactly why the sieve of Eratosthenes is near-linear.

A vector grows by adding 1 to its capacity each time instead of doubling. What is the amortized cost of push_back?

Every push reallocates and copies, so total work over n pushes is n(n+1)/2 = Θ(n²), giving Θ(n) per push. Amortized O(1) requires a multiplicative growth factor; any constant above 1 works, adding a constant does not.

What is the auxiliary space complexity of a recursive inorder traversal of a binary tree?

Recursion depth is space: h frames are live at the deepest point. For a balanced tree that is O(log n), but a tree that degenerates into a chain gives h = n and a stack overflow. “O(1) because I allocated nothing” is the classic miss.

You need an O(n²) DP table of int with n = 10⁵. What happens?

Always multiply the memory out. 10⁵ × 10⁵ × 4 bytes = 4 × 10¹⁰ bytes ≈ 40 GB. The constraint n ≤ 10⁵ is itself telling you the intended solution is not O(n²) in either time or space.

What is the difference between “amortized O(1)” and “average-case O(1)”?

Amortized is a promise no input sequence can break — push_back over n pushes is O(n) total, period. Average-case is a bet about typical inputs: quicksort is O(n log n) on average, but a crafted input still gives O(n²).
