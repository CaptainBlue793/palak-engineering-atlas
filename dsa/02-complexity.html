Complexity: Time, Space & Amortized

Big-O is a way to describe how the running time of code grows as the input gets bigger. It is not a grade you give code after writing it. It is a design tool you use before writing it — a way to rule out whole groups of wrong approaches in seconds. This chapter builds Big-O up from counting operations. It shows why push_back really is O(1), even though it sometimes copies a million elements. And it teaches you to read the complexity of nested loops at a glance.

  • Count operations, then drop constants and smaller terms — and know exactly why that is allowed
  • Read the complexity of nested, back-to-back and recursive code just by looking
  • Explain amortized O(1) (cheap on average over many operations) with the doubling argument, not by hand-waving
  • Measure space including the recursion stack, which most people forget
  • Know where Big-O misleads you, and what to do about it

What Big-O actually claims

An algorithm's running time is some function T(n) of the input size n. We almost never care about that function exactly. It depends on your CPU, your compiler, and whether the data was in cache (the CPU's small, fast memory). What we care about is the shape of its growth. The shape stays the same on any machine. And the shape decides whether you finish in a second or a century.

T(n) = O(f(n)) means: once the input is big enough, T(n) is at most some fixed multiple of f(n). Formally, there exist constants c > 0 and n₀ such that T(n) ≤ c·f(n) for all n ≥ n₀.

Here is that definition on a real example. Say you counted the steps of some code and got T(n) = 3n² + 5n + 2. Is it O(n²)? Try c = 4. You need 3n² + 5n + 2 ≤ 4n², which rearranges to n² − 5n − 2 ≥ 0. At n = 5 that is 25 − 25 − 2 = −2, so it fails. At n = 6 it is 36 − 30 − 2 = 4, and from there on n² pulls further ahead. So c = 4, n₀ = 6 works, and T(n) is O(n²).

This is also why you are allowed to “drop constants and smaller terms”. The smaller terms (5n + 2) become a tiny share of the total: at n = 1000, 3n² is 3,000,000 and 5n + 2 is 5,002 — less than 0.2%. The constant 3 does not change the shape; it just picks a different c. And a constant like 3 depends on the machine and compiler anyway, so it would not mean the same thing on another computer.

Two things follow from that definition, and they are the two things people get wrong:

It is an upper bound, not an equality

O(n) is technically also O(n²). The statement is still true — just useless. When we say “this is O(n log n)”, we mean the tight bound: the growth is exactly n log n, no more and no less. The proper symbol for that is Θ(n log n). Everyone says O; know that they mean Θ.

It says nothing about small n

“Once the input is big enough” matters a lot in that definition. For small n, an O(n²) algorithm with a tiny constant can beat an O(n log n) one with a huge constant. That is exactly why std::sort switches to insertion sort on small pieces of the array.

🔤
O, Ω and Θ in one line each

O(f) — grows no faster than f (an upper bound; the one you usually quote). Ω(f) — grows at least as fast as f (a lower bound; used to prove a problem is hard). Θ(f) — both at once, so the growth is exactly f. In interviews, saying “Θ(n log n)” when you mean the tight bound is an easy way to show you are precise.

Reading a complexity off the code

Four rules cover nearly every case you will meet. Apply them step by step.

Sequential blocks add, so the biggest wins

An O(n) loop followed by an O(n log n) sort is O(n) + O(n log n) = O(n log n). Add them up, then keep only the biggest term. That is why an O(n) setup pass before an O(n²) algorithm costs you nothing extra.

Nested loops multiply — but count the real iterations

Two independent loops up to n give O(n²). But for(i..n) for(j=i..n) runs n + (n−1) + … + 1 = n(n+1)/2 times — still O(n²). And for(i..n) for(j=0..i*0+3) is O(n), because the inner loop's limit does not grow with n.

Halving gives a log, and a log inside a loop gives n log n

If a loop multiplies or divides its variable by a constant each time, it runs O(log n) times. So while(n) n/=2; is O(log n). A binary search inside a loop over n elements is O(n log n).

For recursion, count the tree

Picture the calls as a tree. Total work = (number of calls) × (work per call). When the pattern is regular, you can also use the Master Theorem (a ready-made formula for these cases). T(n) = 2T(n/2) + O(n) is O(n log n): log n levels, O(n) work per level. Chapter 37 covers this in full.

Why halving gives a log, and why the recursion tree gives n log n

Rule 3 in slow motion. Start with n = 16 and halve: 16 → 8 → 4 → 2 → 1. That is 4 halvings, and 2⁴ = 16. In general, after k halvings you have n / 2ᵏ left, and you stop when that reaches 1 — so k = log₂ n. Doubling n adds just one more step. That is why a binary search over a billion items needs only about 30 steps.

Rule 4 in slow motion, for T(n) = 2T(n/2) + O(n) (merge sort) with n = 8:

  • Level 0: one call on 8 items, doing 8 units of work.
  • Level 1: two calls on 4 items each: 4 + 4 = 8 units.
  • Level 2: four calls on 2 items each: 8 units.
  • Level 3: eight calls on 1 item each: 8 units, and the recursion stops.

Every level does n = 8 units of work in total, because the pieces always add back up to the whole array. There are log₂ 8 = 3 levels of splitting (plus the bottom one). So the total is about n × log n. Compare naive Fibonacci, T(n) = T(n−1) + T(n−2) + O(1): each call makes two calls but the input only shrinks by 1 or 2, so the tree roughly doubles at every level and has about n levels — exponential, around 1.6ⁿ calls.

One more shape to recognise: for(int i=1;i*i<=n;i++) stops when i passes √n, so it runs √n times. For n = 10⁶ that is only 1,000 iterations. This is the loop used to test whether a number is prime.

The loop bound that is not what it looks like

This is O(n log n), not O(n²). It fools almost everyone:

for(int i=1;i<=n;i++){
	for(int j=i;j<=n;j+=i){   // step is i, not 1
		// O(1) work
	}
}

The inner loop runs n/i times. So the total is n/1 + n/2 + n/3 + … + n/n = n·H(n) ≈ n·ln n. (H(n) is the harmonic sum, 1 + 1/2 + … + 1/n, which grows like ln n.) The sieve of Eratosthenes uses exactly this pattern. That is why the sieve is O(n log log n) rather than O(n²).

Amortized: why push_back is honestly O(1)

A vector has a fixed capacity — the number of slots it has reserved. When you push past it, the vector grabs a bigger block of memory and copies everything across. That is an O(n) operation. So how can push_back be called O(1)?

Because the capacity doubles each time. Growing from capacity 1 to capacity n means copies of size 1, 2, 4, 8, …, n/2. That sum is less than n. So the total copying work across n pushes is O(n), and the average per push is O(1).

Trace 8 pushes into an empty vector that starts with capacity 1 and doubles:

Total copies: 1 + 2 + 4 = 7, which is less than 8. Add the 8 writes of the new elements themselves and you get 15 units of work for 8 pushes — under 2 per push. Double the number of pushes and the total roughly doubles too, so the per-push cost stays flat.

Think of it like saving up: most pushes are cheap, and the rare expensive one is “paid for” by all the cheap ones before it. That is what amortized means. It does not mean “usually fast”. It means “the total cost over any sequence of operations is bounded, so the average is too”.

The proof in one line

With doubling, the total copy work to reach n elements is 1 + 2 + 4 + … + n/2 < n. (A geometric series — each term a fixed multiple of the last — adds up to less than twice its largest term.) Divide by n pushes and you get less than 1 copy per push: a constant. With +1 growth, the total work is 1 + 2 + 3 + … + n = n(n+1)/2. That is O(n²) in total and O(n) per push. Any growth factor above 1 (multiplying the capacity) gives amortized O(1). Adding a constant does not.

Why “any factor above 1”? With growth factor r, the copy sizes are n/r, n/r², n/r³, … going backwards from the last one. That sum is at most n × 1/(r − 1). For r = 2 it is at most n; for r = 1.5 it is at most 2n. Both are O(n) in total. A smaller factor copies a bit more often but wastes less spare memory, which is why real libraries differ: GCC's std::vector doubles, while Microsoft's grows by 1.5. Both are amortized O(1). Growing by +1 — or by +1000 — is different: the number of reallocations grows with n itself, so the total becomes quadratic.

One practical edge case: amortized O(1) says nothing about a single push. One unlucky push can still copy a million elements. That rarely matters in a contest, but in a real-time system (a game frame, an audio callback) it can. If you know the final size, call reserve(n) first and no push ever reallocates.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 DROP CONSTANTS
O(3n + 5) is O(n), but never drop the constant when comparing two solutions of the same class — a 4n pass and an n pass both being "linear" is how you lose a factor of four you needed.
💡 MEMORY FIRST
Multiply the table out before you allocate: int dp[5000][5000] is 100 MB and will not fit. Memory, not time, is what usually kills a DP.
⚡ HARMONIC
A loop that steps by i inside a loop over i is O(n log n), not O(n²) — the harmonic sum. Worth recognising so you do not over-optimise something already fast enough.
⚠️
Amortized is not the same as average-case

Amortized is a worst-case guarantee over a sequence of operations. No one, however hard they try, can make n pushes cost more than O(n) in total. Average-case is a claim about typical, random inputs. Quicksort is O(n log n) on average — but someone who knows how you pick your pivot can hand you an input that takes O(n²). The first is a promise; the second is a bet. Say which one you mean.

Space complexity — and the stack you forgot

Space is counted the same way, with one thing people almost always miss: recursion depth is space. Every function call that has not returned yet keeps a stack frame in memory — its parameters, local variables and return address. When recursion goes deep, all of those frames exist at the same time.

A quick example with numbers. A recursive function called on a tree that is really one long chain of 10⁵ nodes has 10⁵ frames alive at its deepest point. If each frame takes, say, 50–100 bytes, that is 5–10 MB of stack. Many systems give a program only 1–8 MB of stack by default, so this can crash with a stack overflow even though the algorithm is correct and fast. The same tree walked with an explicit queue or stack keeps its data on the heap (the large general-purpose memory area), which has far more room.

How to count space, in practice: add up (1) every container you create, sized by how many items it can hold at once, and (2) the maximum recursion depth. Then keep the biggest term, just like time.

two traversals, same time, different spaceO(n)O(h) vs O(n)
// Recursive DFS. Time O(n) — every node once.
// Space O(h) where h is the height: h frames are live at the deepest point.
// Balanced tree -> h = log n. Degenerate (a linked list) -> h = n, and it stack-overflows.
void inorder(TreeNode* root,vector<int> &ans){
	if(!root)return;

	inorder(root->left,ans);
	ans.push_back(root->val);
	inorder(root->right,ans);
}

// BFS. Time O(n) too.
// Space O(w) where w is the widest level — and for a complete tree w = n/2, so O(n).
// A wide shallow tree is cheap to recurse and expensive to BFS. The reverse of the above.
void levelorder(TreeNode* root,vector<int> &ans){
	if(!root)return;

	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		TreeNode* node=q.front();
		q.pop();
		ans.push_back(node->val);

		if(node->left)q.push(node->left);
		if(node->right)q.push(node->right);
	}
}
The point: same time, opposite memory use. Which one you want depends on the tree's shape. Answering “O(n) either way” shows you did not look.
✍️
My convention: state space as auxiliary space, and say what the letter means

Auxiliary space is the extra memory your algorithm uses on top of the input. “O(h) auxiliary, where h is the tree height” is a complete answer. “O(n)” is not, because it hides what you meant: the output, the recursion stack, or a hash map? The output array usually does not count as auxiliary space. But say that out loud, so the interviewer does not wonder whether you forgot it. That is why every code block in this course says what its letters mean.

The best-case, worst-case, average-case triple

Every algorithm has all three. The most common slip in interviews is quoting one of them without saying which.

Take insertion sort as an example. It walks left to right, and slides each new element leftwards until it is in place. On [1, 2, 3, 4] (already sorted), each element is compared once with its left neighbour and stays put: about n steps, O(n). On [4, 3, 2, 1] (reverse sorted), each element has to slide all the way to the front: 1 + 2 + 3 = 6 moves for n = 4, and n(n−1)/2 in general, O(n²). Same code, same n, very different cost — which is why “what is the complexity?” needs “in which case?” as a follow-up. If nobody says otherwise, quote the worst case; that is what a time limit tests.

⚠️
Common mistakes
  • Forgetting the recursion stack when measuring space. A recursive solution is never O(1) space. It is O(depth) — and on a worst-case input, like a tree that is really a straight line, that depth is n.
  • Calling nested loops O(n²) without checking the limits. for(j=i;j<=n;j+=i) is O(n log n) overall, and while(j*j<=n) is O(√n).
  • Treating amortized and average-case as the same thing. Amortized is a worst-case guarantee over a sequence. Average-case is a statistical claim that a carefully chosen input can break.
  • Dropping a constant that is really a variable. A loop over the 26 letters is O(1) only if the alphabet is fixed. Over a “character set” of size k it is O(k) — and interviewers do ask.
  • Not multiplying out the memory. “O(n²) space with n = 10⁵” is 10¹⁰ ints — 40 GB. The complexity looks fine, but the program will not even start.
  • Comparing complexities in different variables. You cannot rank O(V + E) against O(n log n) until you say how V, E and n relate. Define your letters first.

Interview drill

Warm-up: Prove that push_back is amortized O(1), out loud, without hand-waving.

How a strong answer sounds
A vector has a capacity. Pushing while there is spare capacity is O(1). Pushing past it allocates a block twice the size and copies everything, which costs O(current size). So the expensive pushes happen at sizes 1, 2, 4, 8 and so on, and each costs exactly that number. Adding up the copies on the way to n elements gives 1 + 2 + 4 + … + n/2. A geometric series with ratio 2 sums to less than twice its largest term, so the total copying is under n. Add the n cheap writes, and n pushes cost O(n) in total — O(1) amortized. The key detail: this needs the capacity to multiply. With fixed +1 growth, every push reallocates, the total becomes 1 + 2 + … + n = Θ(n²), and the amortized cost is Θ(n).

Deeper: Your solution is O(n) and a colleague's is O(n log n), but theirs benchmarks faster on the real data. What do you do?

How a strong answer sounds
Believe the measurement and find out why. Big-O throws away exactly the details that explain this on purpose. The usual causes: my O(n) version uses a hash map, so every element costs a hash, a random memory access and a cache miss. Theirs sorts memory that sits in one block, then scans it in order — which the cache loves. Or my constant factor hides a memory allocation per element. Or n is so small that we are below the crossover point entirely. The right move is to profile — check cache misses and allocations — instead of arguing from the exponent. Then decide by input size. If real-world n is always a few thousand, ship theirs. If n might reach 10⁸, mine wins eventually; I would measure where the crossover is and say so. Big-O decides what is possible; measuring decides what is fast.

🧠 Key takeaways

  • O is an upper bound that ignores constants and small n. When people say O, they usually mean the tight bound Θ.
  • Back-to-back blocks add (keep the biggest), nested loops multiply, halving gives a log — and always check the real number of iterations.
  • Amortized O(1) comes from multiplying the capacity: the copies form a geometric series that adds up to less than n.
  • Recursion depth is space, so a recursive solution uses O(depth) extra space, never O(1).
  • Big-O tells you what is possible. Cache behaviour, constants and memory limits decide what actually runs fast enough.

Check your understanding

What is the time complexity of for(int i=1;i<=n;i++) for(int j=i;j<=n;j+=i){}?

The inner loop steps by i, so it runs about n/i times. Adding that up over every i gives n(1 + 1/2 + 1/3 + … + 1/n) = n·H(n) ≈ n·ln n. This harmonic pattern is exactly why the sieve of Eratosthenes is close to linear.

A vector grows by adding 1 to its capacity each time instead of doubling. What is the amortized cost of push_back?

Every push reallocates and copies everything. So the total work over n pushes is n(n+1)/2 = Θ(n²), which is Θ(n) per push. Amortized O(1) needs the capacity to multiply: any factor above 1 works, but adding a constant does not.

What is the auxiliary space complexity of a recursive inorder traversal of a binary tree?

Recursion depth is space: at the deepest point, h calls are waiting to return, each with its own stack frame. For a balanced tree that is O(log n). But a tree that is really one long chain gives h = n — and can overflow the stack. “O(1) because I created nothing” is the classic mistake.

You need an O(n²) DP table of int with n = 10⁵. What happens?

Always multiply the memory out. 10⁵ × 10⁵ × 4 bytes = 4 × 10¹⁰ bytes ≈ 40 GB. The limit n ≤ 10⁵ is itself telling you that the intended solution is not O(n²) in time or in space.

What is the difference between “amortized O(1)” and “average-case O(1)”?

Amortized is a promise that no sequence of inputs can break: n calls to push_back cost O(n) in total, always. Average-case is a bet about typical inputs: quicksort is O(n log n) on average, but a carefully crafted input still makes it O(n²).
