Binary Trees & DFS Traversals

A tree is recursion you can see. DFS (depth-first search) walks a tree by going as deep as it can before backing up. Its three orders differ in where one line sits: where you “visit” the node compared with the two recursive calls. Once that clicks, half of all tree problems become “which order do I need?”. This chapter also builds the versions without recursion, because the interview follow-up is always “now do it without recursion”. And it covers Morris traversal, which does the job in O(1) extra space.

  • Say which order each kind of problem needs, and why
  • Rewrite each traversal with your own stack instead of recursion, including the tricky postorder
  • Explain Morris traversal and its O(1) space guarantee

The node

Why trees: a lot of real data is a hierarchy, not a line. Folders inside folders, HTML tags inside tags, a company's reporting chart, the moves in a game. A binary tree is the simplest version: every node holds a value and has at most two children, called left and right. The top node is the root, and a node with no children is a leaf. Binary trees are also the base of the fast search structures later in the course (BSTs, balanced trees, segment trees).

TreeNodeO(1) per node
struct TreeNode{
	int val;
	TreeNode* left;
	TreeNode* right;

	TreeNode(int val){
	this->val=val;
	left=nullptr;
	right=nullptr;
}
};
Both pointers are set to null in the constructor. If you leave left unset, it holds a random garbage address. The first traversal follows it into memory that is not a node. The crash usually happens somewhere far away from the real mistake. This is the same habit as ListNode in Chapter 12. And this->val=val lets the parameter have the same name as the member without mixing them up.

Building a small tree by hand shows how the pointers join up. Create the root with TreeNode* root=new TreeNode(1);, then attach children with root->left=new TreeNode(2); and root->right=new TreeNode(3);, and give node 2 two children, 4 and 5, the same way. This chapter uses that five-node tree as its running example:

  • 1 is the root. Its left child is 2 and its right child is 3.
  • 2 has children 4 (left) and 5 (right).
  • 3, 4 and 5 are leaves: both their pointers are nullptr.

A tree is only reachable through its root pointer. If you lose root, you lose the whole tree, just like losing the head of a linked list.

📐
The vocabulary, and the two numbers that matter

The height of a node is the longest path down from it to a leaf (a node with no children). Its depth is the distance up to the root. A tree with n nodes has a height somewhere between ⌊log₂ n⌋ (perfectly balanced) and n−1 (a single chain, like a linked list). Those two limits are the whole story of tree speed. Every operation you write is O(h), where h is the height. Whether that means O(log n) or O(n) depends entirely on the tree's shape. That is why balanced trees exist (Chapter 20). It is also why recursion on a tree that might be a long chain can overflow the stack (Chapter 11). One more fact: a tree with n nodes has exactly n+1 null pointers. There are 2n pointers in total, and n−1 of them are used as edges.

On the running example: the height of the root is 2, because the longest path down is 1 → 2 → 4, which has two edges. Node 4 has depth 2 and height 0, since it is a leaf. With n = 5 there are 6 null pointers, two under each of the three leaves. And the balanced-versus-chain gap is large: a million nodes need only about 20 levels when balanced, but a million levels as a chain.

The three DFS orders — one line moved

This is the clearest example of reusing one skeleton in the whole course. Here are three functions. They are identical except for where the cout line sits.

Preorder: Root → Left → Right

void preorder(TreeNode* root){
	if(!root)return;

	cout<<root->val<<" ";      // visit FIRST
	preorder(root->left);
	preorder(root->right);
}

This is the order you build or copy a tree in — you need the parent before you can attach its children. It is also the order that serialises a tree (writes it out as a list) so it can be rebuilt exactly, as long as you include markers for nulls.

Inorder: Left → Root → Right

void inorder(TreeNode* root){
	if(!root)return;

	inorder(root->left);
	cout<<root->val<<" ";      // visit BETWEEN
	inorder(root->right);
}

On a BST (binary search tree: smaller values go left, larger go right), this outputs the values in sorted order. That is why inorder shows up in every BST problem (Chapter 19): checking a BST is valid, finding the Kth smallest, finding the next value, and converting to a sorted list.

Postorder: Left → Right → Root

void postorder(TreeNode* root){
	if(!root)return;

	postorder(root->left);
	postorder(root->right);
	cout<<root->val<<" ";      // visit LAST
}

This is the order in which a node can be computed from its children. So it is the order of every bottom-up tree calculation: height, diameter, subtree sums, and all of tree DP (Chapter 43). It is also the order you must delete a tree in.

On the running example (1 at the root, 2 and 3 below it, 4 and 5 under 2):

OrderOutputWhy
Preorder1 2 4 5 31 first, then all of 2's subtree (2, then 4, 5), then 3
Inorder4 2 5 1 3everything left of 1 (4 2 5), then 1, then everything right of it (3)
Postorder4 5 2 3 12 can only come after 4 and 5; 1 comes last of all

A quick way to check yourself on paper: draw a line that walks around the outside of the tree, starting left of the root and hugging every node. Write a node down when you pass it on its left side for preorder, underneath it for inorder, and on its right side for postorder. The walk is the same each time; only the moment you write changes, exactly as in the code.

My convention: collect into a reference parameter, do not print

Printing is fine for learning, but useless for solving problems, because you almost always need the sequence afterwards. So every traversal in this course has the same shape. A helper adds values into a vector<int> &ans, and a driver function creates and returns that vector:

void inorder(TreeNode* root,vector<int> &ans){
	if(!root)return;

	inorder(root->left,ans);
	ans.push_back(root->val);
	inorder(root->right,ans);
}
vector<int> inorderTraversal(TreeNode* root){
	vector<int> ans;
	inorder(root,ans);

	return ans;
}

Helper plus driver, state in a reference parameter, no globals — the Chapter 1 rule. Here is why it matters in this case: a hidden test harness calls your function twice. A static vector ans would still hold the first tree's values, and return them mixed in with the second tree's.

Which order does a problem need?

This is the real decision, and you can make it almost by rule.

Do I need the parent's information before processing children?

→ Preorder. Examples: passing a depth down, the path so far, a running sum from the root, an allowed value range for checking a BST, or copying a tree.

visit(root); go(left); go(right);
Do I need both children's results before I can compute mine?

→ Postorder. Examples: height, diameter, subtree sum, checking if the tree is balanced, LCA (lowest common ancestor), deleting the tree, and every tree DP.

L=go(left); R=go(right); combine(L,R);
Is it a BST, and do I want sorted order?

→ Inorder. Examples: checking a BST is valid, Kth smallest, the inorder successor (next value), converting to a sorted list, finding the smallest difference between two values.

go(left); visit(root); go(right);
Do I care about level, width, or the shallowest anything?

→ Not DFS at all. Use BFS (breadth-first search, level by level) — Chapter 17.

int n=q.size(); for(...)
🔑
Postorder is the order of computation — this is the most useful realisation in tree problems

If a value depends on a node's subtrees, you can only compute it after both subtrees are done. That is postorder. Think of a manager who can only report the team's total after every sub-team has reported theirs. Height is 1 + max(leftH, rightH). A subtree sum is val + leftSum + rightSum. Checking whether a tree is balanced needs both heights. So when a problem says “for every node, something about its subtree”, you are writing a postorder function. It returns the value its parent needs. Often it also updates a reference parameter holding the overall answer at the same time. Chapter 18 solves six problems this way, and Chapter 43 turns it into tree DP. Spotting this pattern is worth more than memorising any single solution.

Iterative: the follow-up you will be asked

“Now without recursion.” To convert, you replace the function-call stack with your own explicit stack (Chapter 11). Preorder is easy. Inorder is the important one. Postorder needs a trick.

Why anyone cares, beyond the interview: each recursive call uses a frame on the call stack, and that stack is small (often a few megabytes). A tree shaped like a long chain of 100,000 nodes means 100,000 frames deep, which can crash the program with a stack overflow. Your own stack lives in the much larger heap memory, so it does not have that limit. Iterative code is also easy to pause and resume, which the BST iterator in Chapter 19 needs.

// Push right BEFORE left, so left pops first and we get Root,Left,Right.
vector<int> preorderTraversal(TreeNode* root){
	vector<int> ans;
	if(!root)return ans;

	stack<TreeNode*> st;
	st.push(root);

	while(!st.empty()){
		TreeNode* node=st.top();
		st.pop();

		ans.push_back(node->val);

		if(node->right)st.push(node->right);   // right first...
		if(node->left)st.push(node->left);     // ...so left is on top
	}

	return ans;
}

This is the simplest conversion. Preorder visits a node the moment it arrives, so there is nothing to remember for later. The only subtle part is to push right before left. That is the exact opposite of the BFS queue, where left goes in first.

// The stack holds nodes whose LEFT subtree is done but which are not visited yet.
// That is precisely what the call frames were holding.
vector<int> inorderTraversal(TreeNode* root){
	vector<int> ans;
	stack<TreeNode*> st;
	TreeNode* node=root;

	while(node or !st.empty()){
		while(node){              // dive as far left as possible
			st.push(node);
			node=node->left;
		}

		node=st.top();
		st.pop();

		ans.push_back(node->val);   // visit on the way back up

		node=node->right;         // then handle the right subtree
	}

	return ans;
}

Learn this one properly. The outer condition while(node or !st.empty()) is essential: node can be null while the stack still holds work. This skeleton is also the basis of the BST iterator (Chapter 19), where you pause it between next() calls.

// TRICK: postorder is Left,Right,Root. Reverse it and you get Root,Right,Left —
// which is a preorder with the children swapped. So run that and reverse.
vector<int> postorderTraversal(TreeNode* root){
	vector<int> ans;
	if(!root)return ans;

	stack<TreeNode*> st;
	st.push(root);

	while(!st.empty()){
		TreeNode* node=st.top();
		st.pop();

		ans.push_back(node->val);

		if(node->left)st.push(node->left);     // LEFT first this time
		if(node->right)st.push(node->right);
	}

	reverse(ans.begin(),ans.end());      // the whole trick

	return ans;
}

// TRUE single-pass postorder: track where you came from.
vector<int> postorderTrue(TreeNode* root){
	vector<int> ans;
	stack<TreeNode*> st;
	TreeNode* node=root;
	TreeNode* lastVisited=nullptr;

	while(node or !st.empty()){
		while(node){
			st.push(node);
			node=node->left;
		}

		TreeNode* peek=st.top();

		// only visit once the right subtree is also finished
		if(peek->right and lastVisited!=peek->right){
			node=peek->right;
		}else{
			ans.push_back(peek->val);
			lastVisited=peek;
			st.pop();
		}
	}

	return ans;
}

Use the reverse trick in an interview. It is only four lines longer than preorder, and clearly correct. But know that the true one-pass version exists. “Can you do it in one pass without reversing?” is a real follow-up. It is harder because a node may only be visited after both of its subtrees. So you need to remember which child you just came back from.

Iterative inorder, traced on the running example. The stack is written bottom → top:

  1. Dive left from 1: push 1, 2, 4. Stack: 1 2 4. node is now null.
  2. Pop 4, output 4. Move to 4's right child: null.
  3. Nothing to dive into. Pop 2, output 2. Move to 2's right child, 5.
  4. Dive left from 5: push 5. Pop 5, output 5. Its right child is null.
  5. Pop 1, output 1. Move to 3, push it, pop it, output 3. node is null and the stack is empty, so the loop ends.

Output 4 2 5 1 3, the same as the recursive version. Step 3 is where the outer while(node or !st.empty()) matters: node is null but the stack still holds 2 and 1. The reverse trick checks out too: preorder with children swapped gives 1 3 2 5 4, and reversing it gives 4 5 2 3 1, which is the postorder from the table above.

Morris traversal: inorder in O(1) space

Both the recursive and the stack versions use O(h) space. Morris traversal uses O(1). It borrows unused null right pointers and temporarily points them back to the node that comes next (these are called “threads”). Think of leaving a trail of breadcrumbs so you can find your way back — then picking them up as you go.

morrisInorderO(n)O(1)
// Idea: the problem with dropping the stack is that after finishing a left
// subtree you have no way back to the parent. So before descending left,
// make the left subtree's rightmost node point back at the current node.
// That thread is the return path. Remove it on the way back through.
vector<int> morrisInorder(TreeNode* root){
	vector<int> ans;
	TreeNode* cur=root;

	while(cur){
		if(!cur->left){
			ans.push_back(cur->val);   // no left subtree -> visit now
			cur=cur->right;               // follow a real edge, or a thread
		}else{
			// find the inorder predecessor: rightmost node of the left subtree
			TreeNode* pred=cur->left;
			while(pred->right and pred->right!=cur)
			pred=pred->right;

			if(!pred->right){
				pred->right=cur;          // CREATE the thread, go left
				cur=cur->left;
			}else{
				pred->right=nullptr;      // REMOVE it — left subtree is done
				ans.push_back(cur->val);
				cur=cur->right;
			}
		}
	}

	return ans;
}
Why it is still O(n) despite the inner while: each edge is walked at most three times in total — once going down, once while searching for a predecessor, and once following the thread back. So the total work is O(n). The pred->right != cur check in the search is what stops the predecessor hunt from looping forever along a thread you already made. The cost: it changes the tree while it runs. So it is unsafe if other code reads the tree at the same time, and it cannot be used on a const tree. Mention that trade-off — it is the point of the question.

Morris on the running example, step by step:

  1. cur = 1 has a left child. Its predecessor is the rightmost node of the left subtree: 2 → 5. 5's right is null, so make the thread 5 → 1 and go left to 2.
  2. cur = 2 has a left child. Its predecessor is 4. Make the thread 4 → 2 and go left to 4.
  3. cur = 4 has no left child: output 4 and follow its right pointer, which is the thread, back to 2.
  4. cur = 2 again. The predecessor search reaches 4 and finds 4->right == cur: the thread is already there, so the left side is done. Remove it, output 2, go right to 5.
  5. cur = 5 has no left child: output 5, follow the thread back to 1.
  6. cur = 1 again. The search finds the thread 5 → 1, removes it, outputs 1, and goes right to 3. 3 has no left child: output 3, and its right is null, so the loop ends.

Output 4 2 5 1 3, and both threads have been removed, so the tree is back to how it started. The trick to seeing it: a node is met twice when it has a left subtree. The first time you create the thread; the second time you find it, and that is how you know the left side is finished.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 CHOOSE THE ORDER
The traversal is the decision: in-order for BST sorted order, pre-order to copy or serialise, post-order to aggregate from children, level-order for anything about depth.
💡 PASS DOWN, RETURN UP
Information that flows from ancestors (a running max, a path, a depth) is a parameter. Information that flows from descendants (heights, sums, counts) is a return value. Mixing them up is most tree bugs.
⚡ MORRIS
O(1)-space in-order traversal exists: thread the tree through right pointers and undo them. Worth knowing the name even if you never need to write it.
⚠️
Common mistakes
  • Forgetting if(!root)return;. Every traversal needs it on line one. A null child is the base case, and the recursion reaches one below every leaf.
  • Not setting left and right in the constructor. Garbage pointers crash far away from the real mistake.
  • Using a static or global result vector. It works once. Then it adds the second tree's values onto the first's.
  • Pushing left before right in iterative preorder. A stack reverses the order, so you get Root, Right, Left.
  • Writing while(!st.empty()) for iterative inorder. You must also check node, because the stack is empty on the very first iteration.
  • Claiming recursive traversal is O(1) space. It is O(h), and O(n) for a chain.
  • Expecting sorted output from inorder on a tree that is not a BST. Inorder only gives sorted output because of the BST rule (left smaller, right larger).
  • Deleting a tree in preorder. You free the parent, then try to use it to reach the children. Deletion must be postorder.
  • Forgetting to remove the Morris thread. You leave the tree broken, with a cycle in it.

Interview drill

Warm-up: How do you decide which traversal order a tree problem needs?

How a strong answer sounds
I ask what information each node needs, and where it comes from. If a node needs something computed from its two subtrees — height, diameter, a subtree sum, whether it is balanced — I cannot process it until both children are done. That is postorder. Postorder is the order of computation, which is why every tree DP is postorder. If instead a node needs something handed down from its ancestors — the current depth, the path so far, a valid value range for checking a BST — that is preorder, because the parent must be processed first. If it is a BST and I want the values in sorted order, I use inorder. It is the only order where the BST rule makes the output always increase. And if the question mentions levels, width, or the shallowest anything, DFS is the wrong family entirely and I want BFS. In practice, most hard tree problems are postorder functions. They return one value up the tree while updating a reference parameter that holds the overall answer. Diameter is the classic example.

Deeper: Explain Morris traversal and why it is O(n) despite the nested loop.

How a strong answer sounds
Recursion and the explicit stack need O(h) space for one reason: after finishing a left subtree, you need a way back to the parent. That is what the stack frames store. Morris removes the stack by building the way back into the tree itself. Before going down into a left subtree, find that subtree's rightmost node. This is the inorder predecessor of the current node (the node that comes just before it in sorted order). Point its null right pointer at the current node. That “thread” is the way back. Later, I arrive at the current node again through the thread. I can tell, because the predecessor's right pointer already equals the current node. So I remove the thread, restore the null, visit the node, and move right. On complexity: the inner loop looks worrying, but each edge is walked at most three times in total — once going down, once while searching for a predecessor, once following a thread. So the whole traversal is O(n) amortized (on average across all steps), with O(1) extra space. The real cost is that it changes the tree temporarily. That makes it unusable on a const structure or with other code reading at the same time. And if an exception is thrown partway through, the tree is left broken with a cycle. That trade-off is what the question is really about.

🧠 Key takeaways

  • Preorder, inorder and postorder are one skeleton. Only the position of the visit line changes.
  • Postorder is the order of computation. Anything that depends on a node's subtrees is a postorder function.
  • Inorder on a BST is sorted order, which is why it appears in every BST problem.
  • Iterative preorder pushes right before left. Iterative postorder is easiest as root-right-left, then reversed.
  • Morris reuses null right pointers as temporary “threads” to get O(1) space, at the cost of changing the tree while it runs.

Check your understanding

You need each node's height, computed from its children. Which traversal?

Postorder is the order of computation. 1 + max(leftH, rightH) needs both recursive results first. Every tree DP has this shape.

In iterative preorder with a stack, why push the right child before the left?

Preorder needs Root, Left, Right. The stack reverses the push order, so to pop left first you must push it last. Note this is the opposite of the BFS queue, where left goes in first.

What is the space complexity of Morris inorder traversal, and what does it cost you?

Threads replace the stack, giving true O(1) extra space. The trade-off is real. The tree is changed temporarily, so it cannot be const. It is unsafe if other code reads the tree at the same time. And it is left broken if an exception is thrown partway through.

Iterative postorder is most easily written how?

Root-Right-Left reversed is Left-Right-Root, which is postorder. It is only four lines longer than preorder and clearly correct. Use it — and know that the true one-pass version exists, for the follow-up.

Why does the iterative inorder loop condition have to be while(node or !st.empty())?

Neither check is enough on its own. Checking only the stack exits immediately at the start. Checking only node exits after the first dive to the far left, leaving behind everything still on the stack.
