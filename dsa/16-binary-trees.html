Binary Trees & DFS Traversals

A tree is recursion made visible. The three DFS orders differ by one line's position — where you put the visit relative to the two recursive calls — and once you internalise that, half of tree problems become “which order do I need?”. This chapter also builds the iterative versions, because the interview follow-up is always “now without recursion”, and Morris traversal, which does it in O(1) space.

The node

TreeNodeO(1) per node
struct TreeNode{
	int val;
	TreeNode* left;
	TreeNode* right;

	TreeNode(int val){
	this->val=val;
	left=nullptr;
	right=nullptr;
}
};
Both pointers explicitly nulled in the constructor. An uninitialised left holds garbage, and the first traversal follows it into memory that is not a node — usually crashing somewhere unrelated to the actual mistake. This is the same discipline as ListNode in Chapter 12, and this->val=val is how you let the parameter share the member's name without shadowing confusion.
📐
The vocabulary, and the two numbers that matter

Height of a node is the longest path down to a leaf; depth is the distance up to the root. A tree with n nodes has height between ⌊log₂ n⌋ (perfectly balanced) and n−1 (a chain). Those two bounds are the whole story of tree complexity: every operation you will write is O(h), and whether that is O(log n) or O(n) depends entirely on shape. That is why balanced trees exist (Chapter 20) and why recursion on a possibly-degenerate tree is a stack-overflow risk (Chapter 11). Also: a tree with n nodes has exactly n+1 null pointers — n−1 edges used, 2n pointers total.

The three DFS orders — one line moved

This is the cleanest example of skeleton reuse in the whole course. Three functions, identical except for where the cout sits.

Preorder: Root → Left → Right

void preorder(TreeNode* root){
	if(!root)return;

	cout<<root->val<<" ";      // visit FIRST
	preorder(root->left);
	preorder(root->right);
}

The order a tree is built or copied in — you need the parent before you can attach children. Also the order that serialises a tree uniquely (with null markers).

Inorder: Left → Root → Right

void inorder(TreeNode* root){
	if(!root)return;

	inorder(root->left);
	cout<<root->val<<" ";      // visit BETWEEN
	inorder(root->right);
}

On a BST this emits values in sorted order, which is why inorder appears in every BST problem (Chapter 19) — validation, Kth smallest, successor, and converting to a sorted list.

Postorder: Left → Right → Root

void postorder(TreeNode* root){
	if(!root)return;

	postorder(root->left);
	postorder(root->right);
	cout<<root->val<<" ";      // visit LAST
}

The order in which a node can be computed from its children — so it is the order of every bottom-up tree computation: height, diameter, subtree sums, and all of tree DP (Chapter 43). Also the order you must delete a tree in.

My convention: collect into a reference parameter, do not print

Printing is fine for learning and useless for solving, because you almost always need the sequence afterwards. So every traversal in this course has the same signature shape — a helper that appends into a vector<int> &ans, plus a driver that owns it:

void inorder(TreeNode* root,vector<int> &ans){
	if(!root)return;

	inorder(root->left,ans);
	ans.push_back(root->val);
	inorder(root->right,ans);
}
vector<int> inorderTraversal(TreeNode* root){
	vector<int> ans;
	inorder(root,ans);

	return ans;
}

Helper plus driver, state in a reference parameter, no globals — the Chapter 1 rule. The reason it matters here specifically: a hidden test harness calls your function twice, and a static vector ans would return the first tree's values appended to the second's.

Which order does a problem need?

This is the actual decision, and it is nearly mechanical.

Do I need the parent's information before processing children?

→ Preorder. Passing a depth down, a path prefix, a running sum from the root, an allowed range for BST validation, or copying a tree.

visit(root); go(left); go(right);
Do I need both children's results before I can compute mine?

→ Postorder. Height, diameter, subtree sum, balanced check, LCA, deleting the tree, and every tree DP.

L=go(left); R=go(right); combine(L,R);
Is it a BST, and do I want sorted order?

→ Inorder. Validation, Kth smallest, inorder successor, converting to a sorted list, finding the minimum absolute difference.

go(left); visit(root); go(right);
Do I care about level, width, or the shallowest anything?

→ Not DFS at all. BFS — Chapter 17.

Postorder is the order of computation — this is the most useful realisation in tree problems

Any quantity defined in terms of a node's subtrees can only be computed after both subtrees are done, which is postorder. Height is 1 + max(leftH, rightH). A subtree sum is val + leftSum + rightSum. Whether a tree is balanced needs both heights. So when a problem says “for every node, something about its subtree”, you are writing a postorder function that returns the thing it needs to pass up, and often updates a reference parameter with the global answer at the same time. Chapter 18 does six problems this way, and Chapter 43 turns it into tree DP. Recognising this is worth more than memorising any individual solution.

Iterative: the follow-up you will be asked

“Now without recursion.” The conversion replaces call frames with an explicit stack (Chapter 11). Preorder is easy, inorder is the important one, postorder has a trick.

// Push right BEFORE left, so left pops first and we get Root,Left,Right.
vector<int> preorderTraversal(TreeNode* root){
	vector<int> ans;
	if(!root)return ans;

	stack<TreeNode*> st;
	st.push(root);

	while(!st.empty()){
		TreeNode* node=st.top();
		st.pop();

		ans.push_back(node->val);

		if(node->right)st.push(node->right);   // right first...
		if(node->left)st.push(node->left);     // ...so left is on top
	}

	return ans;
}

The simplest conversion, because preorder visits a node the moment it arrives — there is nothing to remember. Push right before left is the only subtlety, and it is the exact opposite of the BFS queue, where left goes first.

// The stack holds nodes whose LEFT subtree is done but which are not visited yet.
// That is precisely what the call frames were holding.
vector<int> inorderTraversal(TreeNode* root){
	vector<int> ans;
	stack<TreeNode*> st;
	TreeNode* node=root;

	while(node or !st.empty()){
		while(node){              // dive as far left as possible
			st.push(node);
			node=node->left;
		}

		node=st.top();
		st.pop();

		ans.push_back(node->val);   // visit on the way back up

		node=node->right;         // then handle the right subtree
	}

	return ans;
}

Learn this one properly. The while(node or !st.empty()) outer condition is essential — node can be null while the stack still holds work. This skeleton is also the basis of the BST iterator (Chapter 19), where you pause it between next() calls.

// TRICK: postorder is Left,Right,Root. Reverse it and you get Root,Right,Left —
// which is a preorder with the children swapped. So run that and reverse.
vector<int> postorderTraversal(TreeNode* root){
	vector<int> ans;
	if(!root)return ans;

	stack<TreeNode*> st;
	st.push(root);

	while(!st.empty()){
		TreeNode* node=st.top();
		st.pop();

		ans.push_back(node->val);

		if(node->left)st.push(node->left);     // LEFT first this time
		if(node->right)st.push(node->right);
	}

	reverse(ans.begin(),ans.end());      // the whole trick

	return ans;
}

// TRUE single-pass postorder: track where you came from.
vector<int> postorderTrue(TreeNode* root){
	vector<int> ans;
	stack<TreeNode*> st;
	TreeNode* node=root;
	TreeNode* lastVisited=nullptr;

	while(node or !st.empty()){
		while(node){
			st.push(node);
			node=node->left;
		}

		TreeNode* peek=st.top();

		// only visit once the right subtree is also finished
		if(peek->right and lastVisited!=peek->right){
			node=peek->right;
		}else{
			ans.push_back(peek->val);
			lastVisited=peek;
			st.pop();
		}
	}

	return ans;
}

Use the reverse trick in an interview — it is four lines longer than preorder and obviously correct. Know the true version exists, because “can you do it in one pass without reversing?” is a real follow-up, and the reason it is harder is that a node must be visited only after both subtrees, so you need to remember which child you just came back from.

Morris traversal: inorder in O(1) space

Both the recursive and iterative versions use O(h) space. Morris traversal uses O(1), by temporarily rewiring null right pointers into “threads” that point back to the successor — and then undoing them.

morrisInorderO(n)O(1)
// Idea: the problem with dropping the stack is that after finishing a left
// subtree you have no way back to the parent. So before descending left,
// make the left subtree's rightmost node point back at the current node.
// That thread is the return path. Remove it on the way back through.
vector<int> morrisInorder(TreeNode* root){
	vector<int> ans;
	TreeNode* cur=root;

	while(cur){
		if(!cur->left){
			ans.push_back(cur->val);   // no left subtree -> visit now
			cur=cur->right;               // follow a real edge, or a thread
		}else{
			// find the inorder predecessor: rightmost node of the left subtree
			TreeNode* pred=cur->left;
			while(pred->right and pred->right!=cur)
			pred=pred->right;

			if(!pred->right){
				pred->right=cur;          // CREATE the thread, go left
				cur=cur->left;
			}else{
				pred->right=nullptr;      // REMOVE it — left subtree is done
				ans.push_back(cur->val);
				cur=cur->right;
			}
		}
	}

	return ans;
}
Why it is still O(n) despite the inner while: each edge is traversed at most three times overall — once going down, once to find a predecessor, once following the thread back — so total work is O(n). And the pred->right != cur condition in the search is what stops the predecessor hunt from looping forever along a thread you already created. The cost: it mutates the tree during traversal, so it is unsafe with concurrent readers and unusable on a const tree. Mention that trade-off; it is the point of the question.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 CHOOSE THE ORDER
The traversal is the decision: in-order for BST sorted order, pre-order to copy or serialise, post-order to aggregate from children, level-order for anything about depth.
💡 PASS DOWN, RETURN UP
Information that flows from ancestors (a running max, a path, a depth) is a parameter. Information that flows from descendants (heights, sums, counts) is a return value. Mixing them up is most tree bugs.
⚡ MORRIS
O(1)-space in-order traversal exists: thread the tree through right pointers and undo them. Worth knowing the name even if you never need to write it.
⚠️
Common mistakes
  • Forgetting if(!root)return;. Every traversal needs it on line one — a null child is the base case, and the recursion reaches one at every leaf.
  • Not initialising left and right in the constructor. Garbage pointers crash far from the mistake.
  • Using a static or global result vector. Works once, then appends the second tree's values to the first's.
  • Pushing left before right in iterative preorder. A stack reverses, so you get Root, Right, Left.
  • Writing while(!st.empty()) for iterative inorder. You must also test node: the very first iteration has an empty stack.
  • Claiming recursive traversal is O(1) space. It is O(h), and O(n) for a chain.
  • Using inorder on a non-BST expecting sorted output. Inorder only sorts because of the BST invariant.
  • Deleting a tree in preorder. You free the parent, then dereference it to reach the children. Deletion is postorder.
  • Forgetting to remove the Morris thread. You leave the tree corrupted with a cycle.

Interview drill

Warm-up: How do you decide which traversal order a tree problem needs?

How a strong answer sounds
I ask what information each node needs and where it comes from. If a node needs something computed from its two subtrees — height, diameter, a subtree sum, whether it is balanced — then I cannot process it until both children are done, and that is postorder. Postorder is the order of computation, which is why every tree DP is postorder. If instead a node needs something handed down from its ancestors — the current depth, the path so far, a valid value range for BST checking — that is preorder, because the parent must be processed first. If it is a BST and I want values in sorted order, inorder, since that is the only order the BST invariant makes monotone. And if the question mentions levels, width, or the shallowest anything, DFS is the wrong family entirely and I want BFS. In practice most hard tree problems are postorder functions that return one value up the tree while updating a reference parameter holding the global answer — diameter is the canonical example.

Deeper: Explain Morris traversal and why it is O(n) despite the nested loop.

How a strong answer sounds
The reason recursion and the explicit stack need O(h) space is that after finishing a left subtree you need a way back to the parent, and that is what the frames store. Morris gets rid of it by building the return path into the tree itself: before descending into a left subtree, find that subtree's rightmost node — the inorder predecessor of the current node — and point its null right pointer at the current node. That thread is the way back. When I later arrive at the current node again via the thread, I recognise it because the predecessor's right pointer already equals the current node, so I remove the thread, restore the null, visit the node, and move right. For complexity: the inner loop looks alarming, but each edge of the tree is walked at most three times in total — once descending, once while searching for a predecessor, once following a thread — so the whole traversal is O(n) amortized, with O(1) extra space. The real cost is that it temporarily mutates the tree, which makes it unusable on a const structure or with concurrent readers, and means an exception thrown mid-traversal leaves the tree corrupted with a cycle. That trade-off is the actual content of the question.

🧠 Key takeaways

  • Preorder, inorder and postorder are one skeleton with the visit line in one of three positions.
  • Postorder is the order of computation — anything defined over a node's subtrees is a postorder function.
  • Inorder on a BST is sorted order, which is why it appears in every BST problem.
  • Iterative preorder pushes right before left; iterative postorder is easiest as reversed root-right-left.
  • Morris threads null right pointers to get O(1) space, at the cost of temporarily mutating the tree.

Check your understanding

You need each node's height, computed from its children. Which traversal?

Postorder is the order of computation: 1 + max(leftH, rightH) requires both recursive results. Every tree DP has this shape.

In iterative preorder with a stack, why push the right child before the left?

Preorder needs Root, Left, Right. The stack reverses the push order, so to pop left first you must push it last. Note this is the opposite of the BFS queue, where left goes in first.

What is the space complexity of Morris inorder traversal, and what does it cost you?

Threads replace the stack, giving true O(1) auxiliary space. The trade-off is real: the tree is temporarily modified, so it cannot be const, is unsafe with concurrent readers, and is left corrupted if an exception escapes mid-traversal.

Iterative postorder is most easily written how?

Reverse of Root-Right-Left is Left-Right-Root, which is postorder. Four lines longer than preorder and obviously correct — use it, and know the true single-pass version exists for the follow-up.

Why does the iterative inorder loop condition have to be while(node or !st.empty())?

Neither condition alone is sufficient. Testing only the stack exits immediately at the start; testing only node exits after the first leftmost dive, abandoning everything still on the stack.
