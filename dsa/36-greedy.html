Greedy Algorithms & Proving Them

A greedy algorithm takes the locally best option and never looks back. When it works it is the shortest, fastest solution available; when it does not, it produces a confidently wrong answer that passes every small test. So the actual skill here is not writing greedy code — it is deciding whether greedy is valid, and the tool for that is the exchange argument.

  • Write an exchange argument, and use it to prove interval scheduling
  • Recognise the two structural properties greedy needs
  • Find the counterexample that kills a plausible-looking greedy
  • Apply the standard patterns: sort by the right key, then sweep
  • Tell greedy from DP by asking whether a local choice can be regretted

What greedy needs

Two properties, and both must hold. Most wrong greedy solutions fail the first.

1 · Greedy-choice property

There is always an optimal solution that contains the greedy choice. You are not required to show the greedy choice is in every optimum — only that it is in at least one, so committing to it costs nothing.

2 · Optimal substructure

After making that choice, the remaining problem is a smaller instance of the same problem, and solving it optimally gives an overall optimum. This is what lets you commit and recurse without reconsidering.

🔄
The exchange argument — the proof template

Almost every greedy proof has this shape, and it is worth being able to produce on demand:

  1. Let G be the greedy solution and O any optimal solution.
  2. Find the first place they differ: greedy picked g, the optimum picked o.
  3. Show you can swap o for g in O without making it worse or invalid. This is the step that uses the greedy rule.
  4. The modified O' is still optimal and now agrees with G one step further.
  5. Repeat. Either G is optimal, or we have transformed an optimum into G without loss — so G is optimal. ∎

Step 3 is where the whole argument lives. If you cannot perform the swap, that failure usually is your counterexample — so attempting the proof is also the fastest way to discover that greedy is wrong.

Interval scheduling: the model case

maxNonOverlapping — sort by end, sweepO(n log n)O(1)
// Sort by END time. The intuition: finishing earliest leaves the most room
// for everything else — and the exchange argument below makes that rigorous.
bool compare(const vector<int> &a,const vector<int> &b){
	return a[1]<b[1];
}
int maxNonOverlapping(vector<vector<int>> &intervals){
	if(intervals.empty())return 0;

	sort(intervals.begin(),intervals.end(),compare);

	int count=0;
	int lastEnd=INT_MIN;

	for(auto &it:intervals){
		if(it[0]>=lastEnd){        // no overlap with what we have kept
			count++;
			lastEnd=it[1];
		}
	}

	return count;
}
>= or > depends on the problem's definition of overlap. If intervals are half-open — touching at a point is fine, like [1,3] and [3,5] — use >=. If they are closed and sharing an endpoint counts as a conflict, use >. Ask, or state your assumption. This one character is the most common source of off-by-one failures in interval problems.
🧾
Proving "sort by end time" with an exchange

Let G = g₁, g₂, … be the greedy selection in order, and O = o₁, o₂, … an optimal selection, also sorted by end time. Suppose they agree on the first k choices and differ at k+1.

Greedy picked gk+1 as the compatible interval with the earliest end time. So end(gk+1) ≤ end(ok+1). Now replace ok+1 with gk+1 in O. Is the result still valid? Yes: gk+1 is compatible with the first k choices (greedy verified that), and it finishes no later than ok+1, so it cannot conflict with anything O chose afterwards.

The swapped solution O' has the same size — still optimal — and agrees with G one step further. Repeating turns O into G with no loss, so G is optimal. ∎ Notice exactly where "earliest end" was used: it is what guarantees the replacement cannot conflict with the future. Sorting by start or by length gives no such guarantee, which is why the swap fails and the greedy is wrong.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SORT BY END
For interval scheduling, sort by end time. Sorting by duration or by start is intuitive and wrong; the exchange argument only works for end time.
⛔ PROVE IT
Most plausible greedy rules are false. Either give the exchange argument in a sentence, or stress-test against brute force on n ≤ 8 — that finds a counterexample in seconds.
💡 GREEDY + HEAP
When the greedy choice changes as you go, a heap supplies it: task scheduler, IPO, refuelling stops and connect-sticks are all "greedy, re-evaluated each step".
💰
Coin change is the canonical trap — and it is instructive why

With coins {1, 5, 10, 25} the greedy "take the largest that fits" is optimal, and it feels like a general truth. With {1, 3, 4} and target 6 it is not: greedy takes 4, then 1, then 1 for three coins, while 3 + 3 uses two.

The exchange argument fails at step 3. Swapping a 3 into the greedy solution in place of the 4 does not keep the remainder solvable in the same number of coins — the remaining subproblem changes shape, so committing to the 4 was a decision you might regret. The moment a local choice can be regretted, you need DP: dp[amount] = 1 + min over coins of dp[amount − coin], which is Chapter 40. Real currency systems are deliberately designed to be "canonical" so that greedy works, which is exactly why the intuition misleads.

The standard greedy patterns

Most greedy problems are "sort by the right key, then sweep". The skill is choosing the key.

Maximise the number of non-overlapping things

→ Sort by end time, take if compatible. Interval scheduling, non-overlapping intervals, burst balloons (minimum arrows).

sort by a[1]; if(start >= lastEnd) take;
Merge or count overlapping things

→ Sort by start time, then sweep extending the current block. Merge intervals, insert interval.

sort by a[0]; if(start <= curEnd) curEnd=max(curEnd,end);
Minimum resources for concurrent demands

→ Sort by start, and use a min-heap of end times (Chapter 15), or a difference array (Chapter 6). Meeting rooms II, car pooling.

if(pq.top() <= start) pq.pop(); pq.push(end);
Two-sided pairing to satisfy a constraint

→ Sort both sides and use two pointers (Chapter 4). Boats to save people, assign cookies, advantage shuffle.

sort both; while(l<r) match or advance;
Repeatedly combine the two smallest (or largest)

→ Heap. Huffman coding, minimum cost to connect sticks, last stone weight, reduce array size.

while(pq.size()>1){ a=pop(); b=pop(); push(a+b); }
Reach as far as possible, one step at a time

→ Track the furthest reachable index and the current jump boundary. Jump game I and II, gas station.

furthest=max(furthest,i+nums[i]);
Build a string or sequence with a constraint

→ Often a monotonic stack (Chapter 13) rather than a sort. Remove K digits, smallest subsequence, remove duplicate letters.

while(!st.empty() and st.top()>c and budget){ st.pop(); budget--; }
✍️
My convention: state the sort key and the reason in a comment, before the sort

One line — // sort by END time: finishing earliest leaves the most room for the rest — forces you to articulate the greedy rule before you rely on it, and it is the fastest way to notice you have not actually justified it. If you cannot finish that sentence, you do not yet know whether the greedy is correct, and the honest move is to try the exchange argument or look for a counterexample. This is the Chapter 1 invariant rule applied to greedy: the comment is the proof sketch.

Huffman coding: greedy with a heap

Huffman — repeatedly merge the two least frequentO(n log n)O(n)
// Build an optimal prefix code. The greedy rule: the two LEAST frequent
// symbols should be siblings at the deepest level, because the deepest
// positions cost the most bits and should hold the rarest symbols.
int huffmanCost(vector<int> &freq){
	priority_queue<int,vector<int>,greater<int>> pq;   // min-heap (Ch 15)

	for(int f:freq)
	pq.push(f);

	int total=0;

	while(pq.size()>1){
		int a=pq.top();
		pq.pop();
		int b=pq.top();
		pq.pop();

		total+=a+b;              // every merge adds one bit to both subtrees
		pq.push(a+b);
	}

	return total;               // = the total encoded length in bits
}
Why total += a+b gives the encoded length: merging two nodes pushes every symbol beneath them one level deeper, adding one bit to each of their occurrences — which is exactly a + b extra bits. Summing over all merges gives Σ(frequency × depth), the total code length. The same skeleton solves "minimum cost to connect sticks" and "reduce array size to half" — different story, identical algorithm.
🧾
Huffman's exchange argument

Let x and y be the two least frequent symbols. Claim: some optimal prefix-code tree has them as siblings at maximum depth. Take any optimal tree T and let a, b be two siblings at maximum depth. Swap x with a and y with b. Since freq(x) ≤ freq(a) and x moves to a deeper position while a moves shallower, the cost change is (freq(a) − freq(x)) × (depth(a) − depth(x)) ≥ 0 in our favour — the total cannot increase. So T' is still optimal and has x, y as deepest siblings. That establishes the greedy-choice property; merging them into one node of combined frequency then gives a strictly smaller instance of the same problem, which is the optimal substructure. ∎ This is the exchange template applied almost mechanically — worth studying as a model of the form.

🎯
The one-question test

“Could committing to this choice now ever turn out to be a mistake?” In interval scheduling, taking the earliest-finishing compatible interval is never a mistake — the exchange argument shows it. In 0/1 knapsack, taking the best-ratio item can be a mistake, because it may leave unusable capacity. That is the entire distinction. And note the interesting middle ground: fractional knapsack is greedy, because you can take a fraction of an item and never waste capacity — the same problem becomes greedy or DP depending on whether choices are divisible.

⚡
Greedy algorithms you have already met
  • Dijkstra (Ch 29) — settle the closest unsettled node. The exchange argument is the proof in that chapter, and it needs non-negative weights.
  • Prim and Kruskal (Ch 31) — take the lightest safe edge. Proved by the cut property, which is an exchange argument.
  • Kahn's algorithm (Ch 26) — emit any indegree-zero node. Correct because such a node has no unmet prerequisite.
  • The monotonic stack (Ch 13) — discard any element that a later, better one dominates. "Dominated candidates are dead" is a greedy argument.
  • The monotonic deque (Ch 14) — the same domination argument inside a window.
  • Activity selection inside binary search on the answer (Ch 7) — the feasibility check is usually a greedy sweep.

So greedy is not a niche technique — it is the engine inside several of the algorithms you already trust, and in each case a proof was available.

⚠️
Common mistakes
  • Assuming greedy works because it passes the examples. A wrong greedy is right on most inputs — that is what makes it dangerous.
  • Sorting by the wrong key. Interval scheduling sorts by end; interval merging sorts by start. They are different problems.
  • Getting > versus >= wrong on the overlap test. Decide whether touching endpoints conflict, and say so.
  • Applying the greedy coin rule to arbitrary denominations. Works for real currency, fails on {1,3,4} with target 6.
  • Using the ratio greedy on 0/1 knapsack. Correct only for the fractional version.
  • Not sorting at all before a sweep that assumes order.
  • Mutating the caller's vector with sort when it still needs the original order or indices.
  • Using a non-strict comparator. <= violates strict weak ordering and crashes std::sort (Chapter 8).
  • Reaching for DP when a proved greedy exists. O(n log n) and O(1) space beats O(n·K).

Interview drill

Warm-up: Maximum number of non-overlapping intervals. Which key, and prove it.

How a strong answer sounds
Sort by end time and sweep, taking each interval whose start is at least the last kept end. O(n log n) for the sort, O(1) space, one pass. The proof is an exchange argument. Let G be the greedy selection and O an optimal one, both listed in order of end time, and suppose they agree on the first k picks and differ at the (k+1)th. Greedy chose the compatible interval with the earliest end, so end(g) ≤ end(o). Replace o with g in O: the result is still valid, because g is compatible with the first k picks — greedy checked that — and since g finishes no later than o, it cannot conflict with anything O selected afterwards either. So O′ is the same size, still optimal, and agrees with G one step further; repeating transforms O into G with no loss, so G is optimal. The place the argument uses "earliest end" is step three, which is exactly why the other plausible keys fail: sorting by start takes [0,10] and blocks [1,2] and [3,4], and sorting by shortest takes the straddling [4,6] over [0,5] and [5,10]. Both counterexamples are two lines long, and being able to produce them quickly matters as much as the proof. I would also ask whether touching endpoints count as overlapping, since that decides >= versus >.

Deeper: Coin change. When is greedy correct, and how do you know when it is not?

How a strong answer sounds
Greedy — repeatedly take the largest coin that fits — is correct only for canonical coin systems, and real currencies are deliberately designed to be canonical, which is exactly why the intuition is so misleading. With {1, 5, 10, 25} it is optimal. With {1, 3, 4} and target 6 it fails: greedy takes 4, then 1, then 1 for three coins, while 3 + 3 uses two. I can see why by attempting the exchange argument and watching it break: swapping a 3 in for the 4 does not leave the remaining subproblem solvable in the same number of coins, so committing to the largest coin is a decision I might regret — and regret is precisely the signal that greedy is invalid. The correct general solution is DP: dp[amount] = 1 + min over coins of dp[amount − coin], with dp[0] = 0, giving O(amount × coins) time and O(amount) space, and it handles any denomination set. Deciding whether a given set is canonical is itself non-trivial — it can be checked by verifying greedy against DP for all targets up to roughly the sum of the two largest coins — so in an interview I would not assume canonicality; I would state that greedy works for standard currency, give the {1,3,4} counterexample, and write the DP.

🧠 Key takeaways

  • Greedy needs the greedy-choice property and optimal substructure; the exchange argument proves the first.
  • Interval scheduling sorts by end time — and the proof shows exactly why start and length both fail.
  • Trying the exchange argument is also how you find the counterexample: the step that will not swap is the counterexample.
  • The one-question test: can committing to this choice ever be regretted? If yes, it is DP.
  • Dijkstra, Prim, Kruskal, Kahn and the monotonic stack are all greedy with proofs — the technique is everywhere.

Check your understanding

For maximum non-overlapping intervals, which sort key is correct?

Earliest end leaves the most room for the rest, and the exchange argument uses exactly that. Earliest start fails on [0,10],[1,2],[3,4]; shortest fails on [0,5],[4,6],[5,10].

In an exchange argument, which step actually uses the greedy rule?

Step 3 is the whole argument. And when the swap cannot be performed, that failure is usually your counterexample — so attempting the proof is also the fastest way to discover greedy is wrong.

Coins {1, 3, 4}, target 6. What does the greedy "largest coin first" give, and what is optimal?

The canonical trap. Greedy is optimal for real currencies because they are deliberately designed to be canonical — which is why the intuition generalises badly. The general solution is DP.

Taking items by best value-to-weight ratio is optimal for which knapsack?

Divisibility is the whole difference. In 0/1 you may be forced to leave capacity unusable, so the ratio choice can be regretted — which makes it DP. Same problem, different answer, because of divisibility.

What single question best distinguishes a greedy problem from a DP problem?

If a choice can be regretted, you must keep options open — that is DP. If an exchange argument shows it never can, commit and sweep. Everything else is a secondary signal.
