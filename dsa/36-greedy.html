Greedy Algorithms & Proving Them

A greedy algorithm always takes the option that looks best right now, and never goes back. Think of a cashier handing out change using the biggest coin that fits, again and again. When greedy works, it is the shortest and fastest solution there is. When it does not, it gives a wrong answer that still passes every small test. So the real skill is not writing greedy code. It is deciding whether greedy is correct, and the tool for that is the exchange argument.

  • Write an exchange argument, and use it to prove interval scheduling correct
  • Recognise the two properties a problem needs for greedy to work
  • Find the counterexample that breaks a greedy rule that looks right
  • Use the standard pattern: sort by the right key, then sweep through once
  • Tell greedy from DP by asking whether a choice made now could be regretted later

What greedy needs

Why this matters. Greedy solutions are tempting because they are short: sort, loop, done. In interviews they appear constantly (meeting rooms, jump game, assigning cookies, minimum arrows). The danger is that a wrong greedy looks exactly like a right one and passes the examples in the problem statement. A quick example of greedy working: to give 30 cents with coins {1, 5, 10, 25}, take 25, then 5. Two coins, and no answer can do better. The rest of this chapter is about telling when that kind of reasoning is safe.

It needs two properties, and both must hold. Most wrong greedy solutions fail the first one.

1 · Greedy-choice property

There is always a best (optimal) solution that includes the greedy choice. You do not have to show the greedy choice is in every best solution. It only needs to be in at least one, so committing to it costs you nothing.

2 · Optimal substructure

After you make that choice, what is left is a smaller version of the same problem. Solving that smaller version as well as possible gives the best overall answer. This is what lets you commit and move on without ever reconsidering.

🔄
The exchange argument — the proof template

Almost every greedy proof has this shape. It is worth being able to write it on demand. The idea: take any best answer, and show you can change it, one step at a time, into the greedy answer without making it worse.

  1. Let G be the greedy solution and O any optimal (best) solution.
  2. Find the first place they differ: greedy picked g, the optimum picked o.
  3. Show you can swap o for g in O without making it worse or invalid. This is the step that uses the greedy rule.
  4. The changed solution O' is still optimal, and now matches G for one more step.
  5. Repeat. Either G is the optimum already, or we have turned an optimum into G without losing anything. Either way, G is optimal. ∎

Step 3 is where the whole argument lives. If you cannot make the swap, that failure usually is your counterexample. So trying the proof is also the fastest way to find out that greedy is wrong.

Interval scheduling: the model case

You are given intervals, each with a start and end time. Think of meeting requests for one room. Pick as many as you can with no two overlapping. The answer: sort by end time, then take each interval that fits.

maxNonOverlapping — sort by end, sweepO(n log n)O(1)
// Sort by END time. The intuition: finishing earliest leaves the most room
// for everything else — and the exchange argument below makes that rigorous.
bool compare(const vector<int> &a,const vector<int> &b){
	return a[1]<b[1];
}
int maxNonOverlapping(vector<vector<int>> &intervals){
	if(intervals.empty())return 0;

	sort(intervals.begin(),intervals.end(),compare);

	int count=0;
	int lastEnd=INT_MIN;

	for(auto &it:intervals){
		if(it[0]>=lastEnd){        // no overlap with what we have kept
			count++;
			lastEnd=it[1];
		}
	}

	return count;
}
Whether you use >= or > depends on what the problem calls an overlap. If touching at one point is fine, like [1,3] and [3,5], use >=. If sharing an endpoint counts as a clash, use >. Ask, or say what you are assuming. This one character is the most common cause of off-by-one bugs in interval problems.

Intervals [1,3], [2,5], [3,6], [5,7], [6,8], already sorted by end time. Touching at an endpoint is allowed, so the test is start >= lastEnd.

🧾
Proving "sort by end time" with an exchange

Let G = g₁, g₂, … be the greedy picks in order. Let O = o₁, o₂, … be an optimal set of picks, also sorted by end time. Suppose they agree on the first k picks and differ at pick k+1.

Greedy picked gk+1 because it was the fitting interval with the earliest end time. So end(gk+1) ≤ end(ok+1). Now replace ok+1 with gk+1 in O. Is the result still valid? Yes. gk+1 fits with the first k picks (greedy checked that). And it ends no later than ok+1, so it cannot clash with anything O picked after that.

The swapped solution O' has the same size, so it is still optimal. And it matches G for one more step. Repeating this turns O into G with no loss, so G is optimal. ∎ Notice exactly where "earliest end" was used. It is what guarantees the replacement cannot clash with later picks. Sorting by start or by length gives no such guarantee. That is why the swap fails and those greedy rules are wrong.

The counterexamples

Finding a counterexample (one input where the rule gives the wrong answer) is a skill in itself. These are worth remembering, because they come up again and again.

How to find a counterexample yourself. Start tiny: two or three items is usually enough. Try the cases that stress the rule: one very long item that the rule likes, ties, or an item that is good alone but blocks two others. If you cannot find one by hand, write a brute force that tries every option on small random inputs and compare it with your greedy. That is stress testing, covered in Chapter 53. A few hundred random cases of size 5 will expose most wrong greedy rules in seconds.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SORT BY END
For interval scheduling, sort by end time. Sorting by duration or by start is intuitive and wrong; the exchange argument only works for end time.
⛔ PROVE IT
Most plausible greedy rules are false. Either give the exchange argument in a sentence, or stress-test against brute force on n ≤ 8 — that finds a counterexample in seconds.
💡 GREEDY + HEAP
When the greedy choice changes as you go, a heap supplies it: task scheduler, IPO, refuelling stops and connect-sticks are all "greedy, re-evaluated each step".
💰
Coin change is the canonical trap — and it is instructive why

With coins {1, 5, 10, 25}, the greedy rule "take the largest coin that fits" is optimal. It feels like it must always be true. With {1, 3, 4} and target 6, it is not. Greedy takes 4, then 1, then 1: three coins. But 3 + 3 uses only two.

The exchange argument fails at step 3. Swapping a 3 into the greedy solution in place of the 4 does not leave the rest solvable in the same number of coins. The leftover problem changes, so taking the 4 was a choice you might regret. As soon as a choice can be regretted, you need DP: dp[amount] = 1 + min over coins of dp[amount − coin], which is Chapter 40. Real currencies are deliberately designed to be "canonical", meaning greedy works for them. That is exactly why your instinct misleads you here.

The standard greedy patterns

Most greedy problems are "sort by the right key, then sweep through once". The skill is picking the key.

Maximise the number of non-overlapping things

→ Sort by end time, and take each one that fits. Examples: interval scheduling, non-overlapping intervals, burst balloons (minimum arrows).

sort by a[1]; if(start >= lastEnd) take;
Merge or count overlapping things

→ Sort by start time, then sweep, stretching the current block as you go. Examples: merge intervals, insert interval.

sort by a[0]; if(start <= curEnd) curEnd=max(curEnd,end);
Minimum resources for concurrent demands

→ Sort by start, and keep a min-heap of end times (Chapter 15), or use a difference array (Chapter 6). Examples: meeting rooms II, car pooling.

if(pq.top() <= start) pq.pop(); pq.push(end);
Two-sided pairing to satisfy a constraint

→ Sort both sides and use two pointers (Chapter 4). Examples: boats to save people, assign cookies, advantage shuffle.

sort both; while(l<r) match or advance;
Repeatedly combine the two smallest (or largest)

→ Use a heap. Examples: Huffman coding, minimum cost to connect sticks, last stone weight, reduce array size.

while(pq.size()>1){ a=pop(); b=pop(); push(a+b); }
Reach as far as possible, one step at a time

→ Track the furthest index you can reach and the end of the current jump. Examples: jump game I and II, gas station.

furthest=max(furthest,i+nums[i]);

Jump game, worked through. Each nums[i] is the longest jump you can make from index i. For "can you reach the end?", walk left to right keeping furthest, the furthest index reachable so far. With [3,2,1,0,4], furthest becomes 3 at every one of indices 0–3, so index 4 is out of reach: answer false. The greedy is safe because you never need to decide where to jump; you only track what is reachable. For "fewest jumps", also keep curEnd, the end of the range the current number of jumps covers. With [2,3,1,1,4]: at index 0, furthest = 2, and since i == curEnd, you must jump (jumps = 1, curEnd = 2). At indices 1 and 2, furthest grows to 4. At index 2, i == curEnd again, so jump (jumps = 2, curEnd = 4), which reaches the last index. Answer: 2 jumps.

Build a string or sequence with a constraint

→ Often a monotonic stack (Chapter 13) instead of a sort. Examples: remove K digits, smallest subsequence, remove duplicate letters.

while(!st.empty() and st.top()>c and budget){ st.pop(); budget--; }
✍️
My convention: state the sort key and the reason in a comment, before the sort

Write one line, such as // sort by END time: finishing earliest leaves the most room for the rest. It forces you to say the greedy rule out loud before you rely on it. It is also the fastest way to notice you have not actually justified it. If you cannot finish that sentence, you do not yet know whether the greedy is correct. The honest next step is to try the exchange argument or look for a counterexample. This is the Chapter 1 invariant rule applied to greedy: the comment is a sketch of the proof.

Huffman coding: greedy with a heap

Huffman — repeatedly merge the two least frequentO(n log n)O(n)
// Build an optimal prefix code. The greedy rule: the two LEAST frequent
// symbols should be siblings at the deepest level, because the deepest
// positions cost the most bits and should hold the rarest symbols.
int huffmanCost(vector<int> &freq){
	priority_queue<int,vector<int>,greater<int>> pq;   // min-heap (Ch 15)

	for(int f:freq)
	pq.push(f);

	int total=0;

	while(pq.size()>1){
		int a=pq.top();
		pq.pop();
		int b=pq.top();
		pq.pop();

		total+=a+b;              // every merge adds one bit to both subtrees
		pq.push(a+b);
	}

	return total;               // = the total encoded length in bits
}
Why total += a+b gives the encoded length: Huffman builds a tree where each symbol's code length is its depth. Merging two nodes pushes every symbol under them one level deeper. That adds one bit to each time those symbols appear, which is exactly a + b extra bits. Adding this up over all merges gives Σ(frequency × depth), the total code length. The same skeleton solves "minimum cost to connect sticks" and "reduce array size to half". The story is different; the algorithm is the same.

Why anyone uses Huffman coding. Text files store every character with the same number of bits. But some characters are far more common than others. Giving common characters short codes and rare ones long codes shrinks the total. Huffman's greedy finds the best such code; it sits inside formats like ZIP (DEFLATE), gzip and JPEG.

Dry run. Four symbols with frequencies [1, 2, 3, 4]. Merge the two smallest, 1 + 2 = 3 (total 3). The heap is now [3, 3, 4]. Merge 3 + 3 = 6 (total 9). The heap is [4, 6]. Merge 4 + 6 = 10 (total 19). One node is left, so the answer is 19 bits. Check it: the symbol with frequency 4 ends at depth 1, frequency 3 at depth 2, and frequencies 1 and 2 at depth 3. So 4·1 + 3·2 + 2·3 + 1·3 = 19. A fixed 2-bit code for 4 symbols would cost (1+2+3+4) × 2 = 20 bits. Edge case: with only one symbol, the loop never runs and the function returns 0, even though a real encoder still needs 1 bit per symbol. Handle that case separately if the problem cares.

🧾
Huffman's exchange argument

Let x and y be the two least frequent symbols. Claim: some optimal code tree has them as siblings at the deepest level. (A prefix code is one where no code is the start of another, so the bits can be decoded without gaps.)

Take any optimal tree T, and let a, b be two siblings at the deepest level. Swap x with a, and y with b. We know freq(x) ≤ freq(a). And x moves deeper while a moves up. So the saving is (freq(a) − freq(x)) × (depth(a) − depth(x)) ≥ 0: the total cannot go up. So the new tree T' is still optimal, and has x, y as deepest siblings.

That proves the greedy-choice property. Merging them into one node, with their frequencies added, gives a smaller version of the same problem. That is the optimal substructure. ∎ This is the exchange template applied almost step by step. It is worth studying as a model of how these proofs look.

🎯
The one-question test

Ask: “Could taking this option now ever turn out to be a mistake?” In interval scheduling, taking the earliest-finishing interval that fits is never a mistake; the exchange argument shows it. In 0/1 knapsack, taking the best-ratio item can be a mistake, because it may leave space you cannot use. That is the whole difference. Note the interesting middle case: fractional knapsack is greedy, because you can take part of an item and never waste space. The same problem is greedy or DP depending on whether you can split the items.

⚡
Greedy algorithms you have already met
  • Dijkstra (Ch 29): settle the closest node not yet settled. The proof in that chapter is an exchange argument, and it needs weights that are never negative.
  • Prim and Kruskal (Ch 31): take the lightest edge that is safe. Proved by the cut property, which is an exchange argument.
  • Kahn's algorithm (Ch 26): output any node with no incoming edges. That works because such a node has no unmet prerequisite.
  • The monotonic stack (Ch 13): throw away any element that a later, better one beats. "Beaten candidates are dead" is a greedy argument.
  • The monotonic deque (Ch 14): the same argument, inside a sliding window.
  • Activity selection inside binary search on the answer (Ch 7): the "is this possible?" check is usually a greedy sweep.

So greedy is not a rare, special technique. It is the engine inside several algorithms you already trust, and in each case someone had a proof.

⚠️
Common mistakes
  • Assuming greedy works because it passes the examples. A wrong greedy is right on most inputs. That is what makes it dangerous.
  • Sorting by the wrong key. Interval scheduling sorts by end. Interval merging sorts by start. They are different problems.
  • Getting > versus >= wrong on the overlap test. Decide whether touching endpoints count as a clash, and say so.
  • Using the greedy coin rule on any set of coin values. It works for real currency, but fails on {1,3,4} with target 6.
  • Using the ratio greedy on 0/1 knapsack. It is correct only for the fractional version.
  • Not sorting at all before a sweep that depends on the order.
  • Changing the caller's vector with sort when it still needs the original order or indices.
  • Using a comparator that is not strict. <= breaks the ordering rules and crashes std::sort (Chapter 8).
  • Using DP when a proven greedy exists. O(n log n) time and O(1) space beats O(n·K).
🎤
Interview drill

Warm-up: Maximum number of non-overlapping intervals. Which key, and prove it.

How a strong answer sounds
Sort by end time and sweep, taking each interval whose start is at least the end of the last one I kept. That is O(n log n) for the sort, O(1) extra space, one pass. The proof is an exchange argument. Let G be the greedy picks and O an optimal set, both listed in order of end time. Suppose they agree on the first k picks and differ at the (k+1)th. Greedy chose the fitting interval with the earliest end, so end(g) ≤ end(o). Now replace o with g in O. The result is still valid: g fits with the first k picks, since greedy checked that, and g finishes no later than o, so it cannot clash with anything O picked later either. So O′ has the same size, is still optimal, and matches G for one more step. Repeating turns O into G with no loss, so G is optimal. The argument uses "earliest end" in step three, and that is exactly why the other likely-looking keys fail. Sorting by start takes [0,10], which blocks [1,2] and [3,4]. Sorting by shortest takes [4,6], which lies across [0,5] and [5,10] and blocks both. Both counterexamples are two lines long, and producing them quickly matters as much as the proof. I would also ask whether touching endpoints count as overlapping, since that decides >= versus >.

Deeper: Coin change. When is greedy correct, and how do you know when it is not?

How a strong answer sounds
Greedy here means: repeatedly take the largest coin that fits. It is correct only for canonical coin systems, meaning sets of coin values where that rule always gives the fewest coins. Real currencies are designed to be canonical, which is exactly why the intuition misleads. With {1, 5, 10, 25} greedy is optimal. With {1, 3, 4} and target 6 it fails: greedy takes 4, then 1, then 1, for three coins, while 3 + 3 uses two. I can see why by trying the exchange argument and watching it break. Swapping a 3 in for the 4 does not leave the rest solvable in the same number of coins. So taking the largest coin is a choice I might regret, and regret is exactly the signal that greedy is invalid. The correct general solution is DP: dp[amount] = 1 + min over coins of dp[amount − coin], with dp[0] = 0. That is O(amount × coins) time and O(amount) space, and it works for any set of coin values. Checking whether a given set is canonical is not easy in itself. One way is to compare greedy against DP for every target up to roughly the sum of the two largest coins. So in an interview I would not assume the coins are canonical. I would say greedy works for standard currency, give the {1,3,4} counterexample, and write the DP.

🧠 Key takeaways

  • Greedy needs two things: the greedy-choice property and optimal substructure. The exchange argument proves the first.
  • Interval scheduling sorts by end time, and the proof shows exactly why sorting by start or by length fails.
  • Trying the exchange argument is also how you find a counterexample. The swap that will not work shows you the bad case.
  • The one-question test: could taking this choice ever be regretted? If yes, it is DP.
  • Dijkstra, Prim, Kruskal, Kahn and the monotonic stack are all greedy, each with a proof. The technique is everywhere.

Check your understanding

For maximum non-overlapping intervals, which sort key is correct?

Finishing earliest leaves the most room for everything else, and the exchange argument rests on exactly that. Earliest start fails on [0,10],[1,2],[3,4]. Shortest fails on [0,5],[4,6],[5,10].

In an exchange argument, which step actually uses the greedy rule?

Step 3 is the whole argument. And when the swap cannot be made, that failure is usually your counterexample. So trying the proof is also the fastest way to find out that greedy is wrong.

Coins {1, 3, 4}, target 6. What does the greedy "largest coin first" give, and what is optimal?

This is the classic trap. Greedy is optimal for real currencies because they are designed that way on purpose, which is why the intuition does not carry over. The general solution is DP.

Taking items by best value-to-weight ratio is optimal for which knapsack?

Being able to split items is the whole difference. In 0/1 you may be left with space you cannot use, so the ratio choice can be regretted. That makes it DP. Same problem, different answer, purely because of splitting.

What single question best distinguishes a greedy problem from a DP problem?

If a choice can be regretted, you must keep your options open, and that is DP. If an exchange argument shows it never can, commit and sweep. Everything else is a weaker clue.
