Tree Problems: Height, LCA, Paths

Almost every hard tree problem uses one pattern: a postorder function that returns one thing up the tree while updating a different thing by reference. (Postorder means you handle both children first, then the node itself.) Diameter is the classic example: the function returns a height, and separately writes down a diameter. Once you see this shape, a dozen problems that looked different become one technique with different math.

  • Write the postorder pattern that returns one value and updates another by reference
  • Compute the diameter in O(n) instead of the slow O(n²) way
  • Find the LCA (lowest common ancestor) in a general tree, in a BST, and with binary lifting
  • Turn a tree into a string and back, with only one possible reading
  • Rebuild a tree from two traversals, and know which pairs are enough

The pattern: return one thing, update another

Here is the shape. The recursive function's return value is what a parent needs from its child. The reference parameter holds the overall answer, and every node gets a chance to update it. These are usually two different things. Mixing them up is the number one cause of wrong tree solutions.

the pattern, stated abstractlyO(n)O(h)
// RETURNS: what the parent needs from me (usually a height or a sum)
// UPDATES: the global answer, considering paths that PEAK at this node
int solve(TreeNode* root,int &ans){
	if(!root)return 0;

	int left=solve(root->left,ans);
	int right=solve(root->right,ans);

	ans=max(ans,/* combine left and right THROUGH this node */);

	return /* what a single downward path from me is worth */;
}
Why two different values? A parent can only use a path that goes down through one child, because it will extend that path upward. But the best answer may be a path that goes down the left side, up through this node, and down the right side. A path shaped like that bends at this node, so the parent can never extend it. You have to check it here and not pass it up. Every problem below is this pattern with different math in those two slots.

Why it is O(n): each node is visited exactly once, and at each node you do a constant amount of work with the two values its children returned. Compare the naive approach that calls a separate O(n) height() at every node: that repeats the same work over and over, and costs O(n²) on a chain. Passing the child's result up the tree is what removes the repetition.

Height, balance, diameter

// The simplest postorder: no reference parameter needed, because the
// answer IS what the parent needs.
int height(TreeNode* root){
	if(!root)return 0;

	return 1+max(height(root->left),height(root->right));
}

Returning 0 for null means a single node has height 1. Some definitions count edges instead of nodes, which gives a leaf height 0. Say which one you are using, because it changes every answer by one.

// Naive: call height() at every node -> O(n^2), because height itself is O(n).
// Better: one postorder pass. Use -1 as a sentinel meaning "already unbalanced",
// which lets the failure propagate up without a separate flag.
int check(TreeNode* root){
	if(!root)return 0;

	int left=check(root->left);
	if(left==-1)return -1;          // early exit

	int right=check(root->right);
	if(right==-1)return -1;

	if(abs(left-right)>1)return -1;

	return 1+max(left,right);
}
bool isBalanced(TreeNode* root){
	return check(root)!=-1;
}

The special return value is the trick. A height can never be −1, so we use −1 to mean "failed" (a value like this is called a sentinel). That lets one function do both jobs, with no extra bool and no second pass. O(n) instead of O(n²).

// Diameter = longest path between ANY two nodes, which need not pass the root.
// RETURNS height (what the parent can extend).
// UPDATES diameter (a path peaking here, which the parent cannot use).
int depth(TreeNode* root,int &diameter){
	if(!root)return 0;

	int left=depth(root->left,diameter);
	int right=depth(root->right,diameter);

	diameter=max(diameter,left+right);   // path THROUGH this node (in edges)

	return 1+max(left,right);           // single path DOWN from this node
}
int diameterOfBinaryTree(TreeNode* root){
	int diameter=0;
	depth(root,diameter);

	return diameter;
}

The two highlighted lines compute different things, and that is the whole lesson. left+right counts edges, so this returns the diameter in edges. Add 1 if the problem counts nodes.

// Same shape as diameter, but values can be negative — so a subtree that
// contributes a negative sum should be dropped entirely.
int gain(TreeNode* root,int &best){
	if(!root)return 0;

	// clamp at 0: a negative branch is worse than not taking it
	int left=max(0,gain(root->left,best));
	int right=max(0,gain(root->right,best));

	best=max(best,root->val+left+right);   // path peaking here

	return root->val+max(left,right);        // path continuing upward
}
int maxPathSum(TreeNode* root){
	int best=INT_MIN;                       // NOT 0 — all values may be negative
	gain(root,best);

	return best;
}

Two details break most first attempts. First, the max(0, ...) clamp lets you drop branches with a negative sum. Second, best must start at INT_MIN, because the answer can be negative. For a tree with a single node holding −3, starting at 0 would wrongly return 0.

Worked examples

Diameter on the tree with root 1, children 2 and 3, and 4 and 5 under 2. Postorder visits the leaves first:

  • Nodes 4, 5 and 3 are leaves: left = right = 0, so the diameter stays 0 and each returns height 1.
  • Node 2: left = 1, right = 1. The path bending here is 4 – 2 – 5, which is 1 + 1 = 2 edges, so diameter = 2. Returns 1 + max(1, 1) = 2.
  • Node 1: left = 2 (from node 2), right = 1 (from node 3). The path bending here is 4 – 2 – 1 – 3, 2 + 1 = 3 edges, so diameter = 3.

Now see why the root is not enough. Take a root whose only child is node A, and give A two long branches, each two nodes deep. At A, left = 2 and right = 2, so the diameter is 4. At the root, left = 3 and right = 0, only 3. The longest path bends at A and never touches the root, which is why every node gets a chance to update the answer.

Balanced: take a root with a chain of two nodes hanging on the left and nothing on the right. The left side returns height 2 and the right returns 0. Since |2 − 0| > 1, check returns −1. Every ancestor sees −1 and passes it straight up, so no more work is done.

Max path sum on root −10, with left child 9 and right child 20, and 20 having children 15 and 7:

  • gain(9) = 9, gain(15) = 15, gain(7) = 7. Best so far: 15.
  • At 20: left = 15, right = 7. The path bending here is 15 + 20 + 7 = 42, the new best. It returns 20 + max(15, 7) = 35 upward, because a parent can only extend one branch.
  • At −10: left = 9, right = 35. Bending here gives −10 + 9 + 35 = 34, which is less than 42. The answer is 42, a path that avoids the negative root entirely.

My convention: name the two slots before writing the function

Write two comments first, // RETURNS: and // UPDATES:, and fill them in with words, not code. For diameter: “returns the height below me; updates the longest path that bends at me”. If you can't fill both in plain English, you are not ready to write the body. You will likely end up returning the answer instead of the height, which is wrong on any tree whose diameter doesn't pass through the root. This is Chapter 1's rule about stating what each piece means (the invariant), applied to trees.

Lowest common ancestor

The lowest common ancestor (LCA) of two nodes is the deepest node that has both of them below it — where their paths up to the root first meet. Here are three versions, from simplest to most advanced. Which one you need depends on whether the tree is a BST and whether there will be many queries.

Why it matters: the LCA is how you measure things between two nodes. The distance between u and v is depth[u] + depth[v] − 2·depth[LCA], because both paths climb to the LCA and meet there. The same idea finds the closest shared folder of two files, or the nearest shared manager of two employees in an org chart. Note that a node counts as its own ancestor, so if p sits below q, the LCA is q itself.

// Returns: p, q, the LCA, or null — whichever it finds in this subtree.
// The insight: if p is found on the left and q on the right, THIS node is
// the LCA. If both come back from one side, the answer is already that side's.
TreeNode* LCA(TreeNode* root,TreeNode* p,TreeNode* q){
	if(!root)return nullptr;
	if(root==p or root==q)return root;    // found one; stop descending

	TreeNode* left=LCA(root->left,p,q);
	TreeNode* right=LCA(root->right,p,q);

	if(left and right)return root;        // one on each side -> split here

	return left?left:right;                // pass up whichever was found
}

O(n) time, O(h) space. This assumes both p and q are in the tree. If one might be missing, it returns the other one, which is wrong. The fix is a second pass to check both are present, or counting matches in a reference parameter. Interviewers ask about this.

// A BST tells you which way to go, so there is no need to search both sides.
// The LCA is the first node whose value lies BETWEEN p and q.
TreeNode* LCAinBST(TreeNode* root,TreeNode* p,TreeNode* q){
	while(root){
		if(p->val<root->val and q->val<root->val){
			root=root->left;           // both smaller -> go left
		}else if(p->val>root->val and q->val>root->val){
			root=root->right;          // both larger -> go right
		}else{
			return root;               // they split here (or one IS root)
		}
	}

	return nullptr;
}

O(h) time, O(1) space, and no recursion. It is always better than the general version when the tree is a BST. The BST rule (smaller values on the left, larger on the right) tells you which way to go, so you never have to search both sides.

// Binary lifting: O(n log n) preprocessing, then O(log n) per query.
// up[k][v] = the 2^k-th ancestor of v. Worth it for many queries.
const int LOG=20;                      // 2^20 > 10^6
vector<vector<int>> up;
vector<int> depth;

void dfs(vector<vector<int>> &tree,int node,int parent){
	up[0][node]=parent;

	for(int k=1;k<LOG;k++)
	up[k][node]=up[k-1][node]<0?-1:up[k-1][up[k-1][node]];

	for(int child:tree[node]){
		if(child!=parent){
			depth[child]=depth[node]+1;
			dfs(tree,child,node);
		}
	}
}
int lca(int u,int v){
	if(depth[u]<depth[v])swap(u,v);

	// 1. lift the deeper one to the same depth
	int diff=depth[u]-depth[v];
	for(int k=0;k<LOG;k++){
		if(diff&(1<<k))u=up[k][u];
	}

	if(u==v)return u;                   // v was an ancestor of u

	// 2. lift both as high as possible WITHOUT meeting
	for(int k=LOG-1;k>=0;k--){
		if(up[k][u]!=up[k][v]){
			u=up[k][u];
			v=up[k][v];
		}
	}

	return up[0][u];                     // their parent is the LCA
}

Step 2 is the clever part. You jump up as far as you can while the two ancestors are still different. Afterwards, u and v are the two children of the LCA. You must try the largest jump first and go down. It works the same way as writing a number in binary, taking the biggest power of 2 that fits each time.

Tracing the general version. Tree: root 3 with children 5 and 1. Node 5 has children 6 and 2, and node 2 has children 7 and 4. Node 1 has children 0 and 8. Find LCA(6, 4):

  • Under 5, the left call reaches 6, which is p, and returns 6 at once.
  • Under 5, the right call goes to 2. Its left (7) finds nothing and returns null; its right is 4, which is q, so 2 passes 4 up.
  • Node 5 gets 6 from the left and 4 from the right: one on each side, so 5 is returned.
  • At the root, the right subtree (1, 0, 8) returns null, so the root passes up 5. Answer: 5.

The edge case where one node is below the other: LCA(5, 4) stops at 5 the moment it is found and returns it without looking for 4 underneath. That is correct, since 5 is 4's ancestor, but only because both nodes are assumed to be in the tree.

Tracing the BST version. BST: root 6, children 2 and 8; 2 has children 0 and 4; 4 has children 3 and 5. For p = 3, q = 5: at 6, both are smaller, go left. At 2, both are larger, go right. At 4, 3 < 4 < 5: they split, so the answer is 4. Three steps, and nothing else in the tree was touched.

Why binary lifting works. The table is filled with one rule: jumping 2k steps is jumping 2k−1 steps twice, so up[k][v] = up[k-1][up[k-1][v]]. Any climb can then be split into powers of two. To lift a node 5 levels, write 5 in binary as 101 and make a jump of 1 and a jump of 4. That is at most LOG jumps for any distance, so each query is O(log n).

Serialize and deserialize

Serializing means turning a tree into a string; deserializing turns the string back into the same tree. The key point: preorder alone is not enough unless you also record the nulls. With a marker for each missing child, the string can only be read back one way.

Where this is used: saving a tree to a file, sending it over a network, or caching it, all need it as flat text. And here is why the nulls are needed. The preorder 1, 2 fits two different trees: 2 as the left child of 1, or 2 as the right child. With null markers they become different strings: 1,2,#,#,#, (2 on the left) and 1,#,2,#,#, (2 on the right).

serialize / deserialize with null markersO(n) both waysO(n)
// Preorder WITH explicit nulls. "1,2,#,#,3,#,#," is unambiguous.
void build(TreeNode* root,string &s){
	if(!root){
		s+="#,";
		return;
	}

	s+=to_string(root->val)+",";
	build(root->left,s);
	build(root->right,s);
}
string serialize(TreeNode* root){
	string s;
	build(root,s);

	return s;
}

// Read in the same preorder. The stream position is shared state, so it
// must be a reference — a copy would restart the parse in each branch.
TreeNode* parse(stringstream &ss){
	string token;
	getline(ss,token,',');

	if(token=="#" or token.empty())return nullptr;

	TreeNode* root=new TreeNode(stoi(token));

	root->left=parse(ss);        // order matters: left then right,
	root->right=parse(ss);       // matching how we wrote it

	return root;
}
TreeNode* deserialize(string data){
	stringstream ss(data);

	return parse(ss);
}
stringstream &ss — passing it by reference really matters. The stream remembers how far it has read, and every recursive call shares that position. Pass it by value and each branch gets its own copy that starts from the same place, so the tree comes out badly wrong. This is Chapter 1's reference-parameter rule, with a payoff that is easy to miss.

Reading "1,2,#,#,3,#,#," back, one token at a time:

  1. Read 1: make node 1, then build its left subtree.
  2. Read 2: make node 2 as 1's left child, then build 2's left subtree.
  3. Read #: 2's left is null. Read #: 2's right is null. Node 2 is done.
  4. Back at 1, build its right subtree. Read 3: make node 3. Read #, #: both its children are null.

Every token is used exactly once, in the same order it was written, which is why the parse needs no counting or lookahead. Edge cases: an empty tree serializes to "#," and reads back as nullptr, and negative values work because stoi handles the minus sign.

🔢
Which pairs of traversals determine a tree?
  • Preorder + inorder — yes. Preorder tells you the root. Inorder tells you how many nodes are on each side of it. Then repeat for each side.
  • Postorder + inorder — yes. Same idea, but the root is at the end of postorder.
  • Preorder + postorder — no, not for a general binary tree. Preorder [1,2] with postorder [2,1] could mean 2 is the left child of 1 or the right child, and nothing tells you which. It does work if every node has 0 or 2 children.
  • Preorder with null markers — yes, alone. The nulls fill in exactly the missing shape information. That is why serialization works.
  • Level order with null markers — yes, alone. Same reason.

The rule behind this: two traversals work when one tells you the root and the other tells you the split (where the left subtree ends and the right begins). Inorder is the only order that gives a split. That is why it appears in both working pairs.

buildTree from preorder + inorderO(n)O(n)
// Naive: search inorder linearly for the root each time -> O(n^2).
// Better: a value-to-index map makes the split lookup O(1).
TreeNode* helper(vector<int> &preorder,int &preIdx,int inLo,int inHi,
                 unordered_map<int,int> &pos){
	if(inLo>inHi)return nullptr;

	int rootVal=preorder[preIdx];
	preIdx++;                          // consumed — reference, so it advances globally

	TreeNode* root=new TreeNode(rootVal);
	int mid=pos[rootVal];              // where the root sits in inorder

	root->left=helper(preorder,preIdx,inLo,mid-1,pos);
	root->right=helper(preorder,preIdx,mid+1,inHi,pos);

	return root;
}
TreeNode* buildTree(vector<int> &preorder,vector<int> &inorder){
	unordered_map<int,int> pos;
	for(int i=0;i<inorder.size();i++)
	pos[inorder[i]]=i;

	int preIdx=0;

	return helper(preorder,preIdx,0,inorder.size()-1,pos);
}
int &preIdx is the second reference that matters. The whole recursion reads preorder strictly from left to right, so all calls must share one index. By reference, it moves forward for everyone. By value, each branch starts over and you build garbage. This assumes all values are different. With duplicates there really is more than one possible tree, and you should say so.

A dry run with preorder [3, 9, 20, 15, 7] and inorder [9, 3, 15, 20, 7]:

  1. The first preorder value, 3, is the root. It sits at inorder index 1, so inorder [9] is its left subtree and [15, 20, 7] is its right.
  2. The next preorder value, 9, is the root of the left part. Its inorder range holds only 9, so both its children are empty ranges: null.
  3. The next preorder value, 20, is the root of the right part. It sits at inorder index 3, so 15 is its left child and 7 is its right, and the last two preorder values, 15 then 7, fill those in.

Result: 3 at the root, 9 on the left, 20 on the right, and 15 and 7 under 20. The left subtree must be built before the right one, because preorder lists the whole left subtree before any of the right. Swap the two recursive calls and the values get used in the wrong places.

Path problems

Path problems are the opposite shape from diameter. The information flows down: the path so far, or the running sum from the root. So they are preorder, and they pass state down as parameters. The one catch is that when you share a single vector or map between all calls, you must undo your change before returning, so your sibling branch does not see your path. This is the same choose, explore, unchoose rhythm as backtracking (Chapter 35).

all root-to-leaf paths — and the undoO(n·h)O(h)
// Preorder, because the path is built top-down.
// The pop_back is what makes a shared vector safe — choose, explore, unchoose.
void paths(TreeNode* root,vector<int> &current,vector<vector<int>> &ans){
	if(!root)return;

	current.push_back(root->val);

	if(!root->left and !root->right){
		ans.push_back(current);        // leaf: record a copy
	}else{
		paths(root->left,current,ans);
		paths(root->right,current,ans);
	}

	current.pop_back();                 // UNDO before returning to the parent
}

// Path sum III: count paths summing to target, starting ANYWHERE.
// Prefix sums plus a hash map (Chapter 6) applied to a tree.
void count(TreeNode* root,long long running,int target,
           unordered_map<long long,int> &seen,int &ans){
	if(!root)return;

	running+=root->val;

	if(seen.count(running-target))
	ans+=seen[running-target];

	seen[running]++;

	count(root->left,running,target,seen,ans);
	count(root->right,running,target,seen,ans);

	seen[running]--;              // UNDO: this prefix is not on other branches
}
int pathSum(TreeNode* root,int target){
	unordered_map<long long,int> seen;
	seen[0]=1;                    // the empty prefix, exactly as in Chapter 6

	int ans=0;
	count(root,0,target,seen,ans);

	return ans;
}
seen[running]-- is the tree version of the backtracking undo. A prefix sum (the running total from the root down to a node) only counts along the current root-to-node path. If you leave it in the map, a node in the left subtree can pair with one in the right subtree, and that is not a real path. This is the most common bug in Path Sum III. It gives a count that is too high but still looks believable.

Why the first function is O(n·h) and not O(n): each node is visited once, but at every leaf the whole current path is copied into ans, and that copy can be up to h long.

Path Sum III on the path 10 → 5 → 3 with target = 8. The map starts as {0: 1}:

  • At 10: running = 10. Is 10 − 8 = 2 in the map? No. Add 10.
  • At 5: running = 15. Is 7 in the map? No. Add 15.
  • At 3: running = 18. Is 18 − 8 = 10 in the map? Yes, once. So one path ends here: it starts just after the node where the sum was 10, which is 5 → 3, and 5 + 3 = 8.

It is the Chapter 6 subarray trick, with the root-to-node path playing the role of the array. The running total uses long long because sums of many large node values can pass the int limit.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 RETURN ≠ ANSWER
For diameter and max-path-sum, what you report upward is a single chain; the answer that bends at this node goes into a by-reference accumulator. Conflating them is the classic failure.
💡 MINUS-ONE SENTINEL
Check balance in one traversal by returning height, or −1 to mean "already unbalanced". Two traversals become one, and the early exit is free.
⛔ INT_MIN START
Max-path-sum with negative values must start the answer at INT_MIN, not 0 — and the clamp goes on the child (max(child,0)), never on the answer.
⚠️
Common mistakes
  • Returning the answer instead of the height in diameter. A parent can only extend a single downward path. A path that bends at this node must go into the reference parameter.
  • Starting maxPathSum at 0. If every value is negative, the answer is negative. Start at INT_MIN.
  • Forgetting the max(0, ...) clamp. A negative branch should be dropped, not added.
  • Calling height() for every node. That is O(n²). One postorder pass with a −1 sentinel is O(n).
  • Passing the stringstream or preIdx by value. Both track a shared reading position. A copy starts reading from the same place in every branch.
  • Forgetting pop_back or seen[running]--. Values from one subtree leak into its sibling.
  • Assuming preorder + postorder can rebuild a tree. It can't, unless every node has 0 or 2 children.
  • Assuming both LCA targets are in the tree. If one is missing, the recursive version returns the other.
  • Using the general LCA on a BST. It costs O(n) when a simple O(h) loop would do.
  • Not saying how you count height. Nodes or edges — it changes every answer by one.

Interview drill

Warm-up: Find the diameter of a binary tree. Then explain why the naive approach is O(n²).

How a strong answer sounds
The diameter is the longest path between any two nodes, and it does not have to pass through the root. The naive approach: for every node, compute left height plus right height and take the maximum. That is correct, but each height call is O(n), so over n nodes it is O(n²). The fix is to notice that computing the height already visits every node. So I can compute both values in one postorder pass. The key is that they are different values. The function returns 1 + max(leftHeight, rightHeight), which a parent can extend upward. Separately, it updates a reference parameter with leftHeight + rightHeight. That is the longest path that bends at this node, and the parent can never use it. One traversal, O(n) time, O(h) space. I would write the two slots as comments, "RETURNS" and "UPDATES", before writing the body, because mixing them up is the classic error. Returning the diameter makes the function wrong on any tree whose longest path doesn't pass through the root. I would also say whether the answer counts edges or nodes, since left+right counts edges.

Deeper: Can you reconstruct a binary tree from its preorder and postorder traversals?

How a strong answer sounds
Not in general. Preorder puts the root first and postorder puts it last, so either one tells me the root. But neither tells me where the left subtree ends and the right one begins. For example, preorder [1,2] with postorder [2,1] fits 2 being 1's left child or its right child, and nothing in the data tells them apart. I need a traversal that gives the split, and inorder is the only one that does. Once I know the root, its position in inorder tells me exactly how many nodes are in each subtree. So preorder plus inorder works, and so does postorder plus inorder. I would build a map from value to inorder index, so each split lookup is O(1). That gives O(n) instead of the O(n²) you get from scanning inorder every time. Two caveats. First, preorder plus postorder does work if every node has zero or two children, because then the first element of the left subtree's preorder marks the boundary. Second, all of these assume distinct values, since duplicates make the split truly ambiguous. Preorder alone is also enough if you record the nulls, which is exactly why serialization works.

🧠 Key takeaways

  • The core tree pattern: a postorder function that returns what the parent can extend, and updates by reference the answer for paths that bend at this node.
  • Use an impossible return value (height −1) to mean "failed". It turns an O(n²) check into one O(n) pass.
  • LCA: recursive split for a general tree, iterative descent for a BST, binary lifting for many queries.
  • Preorder+inorder or postorder+inorder is enough to rebuild a tree. Inorder is the only order that tells you the split.
  • A shared reading position (stringstream, preIdx) must be passed by reference. Anything that collects a path as you go down needs an undo on the way back up.

Check your understanding

In the diameter solution, the recursive function returns the height but updates the diameter by reference. Why not just return the diameter?

They really are two different values. left+right is a path that bends at this node and ends here. 1+max(left,right) is what an ancestor can build on. Mixing them up is the classic error.

Which pair of traversals does not uniquely determine a general binary tree?

Preorder and postorder both tell you the root, but neither tells you where the subtrees split. Inorder is the only traversal that does, which is why it appears in both working pairs. (Preorder+postorder does work if every node has 0 or 2 children.)

Why must the stringstream in deserialize be passed by reference?

Each call reads the next token from one shared reading position. The same goes for int &preIdx in buildTree: the whole recursion reads preorder strictly from left to right.

In path sum III, why decrement seen[running] after recursing into both children?

This is the tree version of backtracking's undo. Without it you count pairs that are not real paths. The answer comes out too high but still looks believable, so the bug is hard to spot.

The tree is a BST and you need the LCA. Best approach?

The BST ordering tells you which way to go, so you never search both sides. O(h) time, O(1) space, no recursion. Binary lifting only pays off when there are many queries.
