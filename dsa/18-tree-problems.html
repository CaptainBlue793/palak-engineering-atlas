Tree Problems: Height, LCA, Paths

Nearly every hard tree problem is one pattern: a postorder function that returns one thing up the tree while updating a different thing by reference. Diameter is the canonical example — the function returns a height and writes a diameter. Once you see that shape, a dozen problems that looked distinct become one technique with different arithmetic.

  • Write the “return one value, update another by reference” postorder pattern
  • Compute diameter in O(n) rather than the naive O(n²)
  • Find the LCA in a general tree, and in a BST, and with binary lifting
  • Serialize and deserialize a tree unambiguously
  • Reconstruct a tree from two traversals, and know which pairs are sufficient

The pattern: return one thing, update another

Here is the shape. The recursive function's return value is what a parent needs from its child. The reference parameter is the global answer, updated at every node. These are usually different quantities, and conflating them is the number one source of wrong tree solutions.

the pattern, stated abstractlyO(n)O(h)
// RETURNS: what the parent needs from me (usually a height or a sum)
// UPDATES: the global answer, considering paths that PEAK at this node
int solve(TreeNode* root,int &ans){
	if(!root)return 0;

	int left=solve(root->left,ans);
	int right=solve(root->right,ans);

	ans=max(ans,/* combine left and right THROUGH this node */);

	return /* what a single downward path from me is worth */;
}
Why two different quantities. A parent can only use a path that goes down through one child — it will extend that path upward. But the global answer may be a path that goes down the left child, up through this node, and down the right child, which the parent can never extend. So you must consider that at this node and not pass it up. Every problem below is this pattern with different arithmetic in those two slots.

Height, balance, diameter

// The simplest postorder: no reference parameter needed, because the
// answer IS what the parent needs.
int height(TreeNode* root){
	if(!root)return 0;

	return 1+max(height(root->left),height(root->right));
}

Returning 0 for null means a single node has height 1. Some definitions use edges instead of nodes, giving height 0 for a leaf — state which convention you are using, because it shifts every answer by one.

// Naive: call height() at every node -> O(n^2), because height itself is O(n).
// Better: one postorder pass. Use -1 as a sentinel meaning "already unbalanced",
// which lets the failure propagate up without a separate flag.
int check(TreeNode* root){
	if(!root)return 0;

	int left=check(root->left);
	if(left==-1)return -1;          // early exit

	int right=check(root->right);
	if(right==-1)return -1;

	if(abs(left-right)>1)return -1;

	return 1+max(left,right);
}
bool isBalanced(TreeNode* root){
	return check(root)!=-1;
}

The sentinel return is the trick. Encoding "failed" as an impossible height value means one function does both jobs — no bool reference, no second traversal. O(n) instead of O(n²).

// Diameter = longest path between ANY two nodes, which need not pass the root.
// RETURNS height (what the parent can extend).
// UPDATES diameter (a path peaking here, which the parent cannot use).
int depth(TreeNode* root,int &diameter){
	if(!root)return 0;

	int left=depth(root->left,diameter);
	int right=depth(root->right,diameter);

	diameter=max(diameter,left+right);   // path THROUGH this node (in edges)

	return 1+max(left,right);           // single path DOWN from this node
}
int diameterOfBinaryTree(TreeNode* root){
	int diameter=0;
	depth(root,diameter);

	return diameter;
}

The two highlighted lines are different quantities — and that is the whole lesson. left+right counts edges, so this returns the diameter in edges; add 1 if the problem counts nodes.

// Same shape as diameter, but values can be negative — so a subtree that
// contributes a negative sum should be dropped entirely.
int gain(TreeNode* root,int &best){
	if(!root)return 0;

	// clamp at 0: a negative branch is worse than not taking it
	int left=max(0,gain(root->left,best));
	int right=max(0,gain(root->right,best));

	best=max(best,root->val+left+right);   // path peaking here

	return root->val+max(left,right);        // path continuing upward
}
int maxPathSum(TreeNode* root){
	int best=INT_MIN;                       // NOT 0 — all values may be negative
	gain(root,best);

	return best;
}

Two details that break naive attempts: the max(0, ...) clamp lets you discard negative branches, and best must start at INT_MIN because the answer can be negative — with a tree of a single node holding −3, starting at 0 returns 0.

My convention: name the two slots before writing the function

Write two comments first — // RETURNS: and // UPDATES: — and fill them in with words, not code. For diameter: “returns the height below me; updates the longest path peaking at me”. If you cannot fill both slots in plain English, you are not ready to write the body, and you will end up returning the answer instead of the height (which gives a wrong answer on any tree whose diameter avoids the root). This is the Chapter 1 invariant rule, specialised to trees.

Lowest common ancestor

Three versions, in increasing sophistication. Which one you need depends on whether it is a BST and whether there will be many queries.

// Returns: p, q, the LCA, or null — whichever it finds in this subtree.
// The insight: if p is found on the left and q on the right, THIS node is
// the LCA. If both come back from one side, the answer is already that side's.
TreeNode* LCA(TreeNode* root,TreeNode* p,TreeNode* q){
	if(!root)return nullptr;
	if(root==p or root==q)return root;    // found one; stop descending

	TreeNode* left=LCA(root->left,p,q);
	TreeNode* right=LCA(root->right,p,q);

	if(left and right)return root;        // one on each side -> split here

	return left?left:right;                // pass up whichever was found
}

O(n) time, O(h) space. Assumes both p and q exist in the tree. If one might be absent, this returns the other one, which is wrong — the fix is a second pass to verify presence, or to count matches in a reference parameter. Interviewers ask about this.

// A BST tells you which way to go, so there is no need to search both sides.
// The LCA is the first node whose value lies BETWEEN p and q.
TreeNode* LCAinBST(TreeNode* root,TreeNode* p,TreeNode* q){
	while(root){
		if(p->val<root->val and q->val<root->val){
			root=root->left;           // both smaller -> go left
		}else if(p->val>root->val and q->val>root->val){
			root=root->right;          // both larger -> go right
		}else{
			return root;               // they split here (or one IS root)
		}
	}

	return nullptr;
}

O(h) time, O(1) space, and iterative. Strictly better than the general version when the tree is a BST. Notice there is no recursion at all — the BST invariant replaces the search.

// Binary lifting: O(n log n) preprocessing, then O(log n) per query.
// up[k][v] = the 2^k-th ancestor of v. Worth it for many queries.
const int LOG=20;                      // 2^20 > 10^6
vector<vector<int>> up;
vector<int> depth;

void dfs(vector<vector<int>> &tree,int node,int parent){
	up[0][node]=parent;

	for(int k=1;k<LOG;k++)
	up[k][node]=up[k-1][node]<0?-1:up[k-1][up[k-1][node]];

	for(int child:tree[node]){
		if(child!=parent){
			depth[child]=depth[node]+1;
			dfs(tree,child,node);
		}
	}
}
int lca(int u,int v){
	if(depth[u]<depth[v])swap(u,v);

	// 1. lift the deeper one to the same depth
	int diff=depth[u]-depth[v];
	for(int k=0;k<LOG;k++){
		if(diff&(1<<k))u=up[k][u];
	}

	if(u==v)return u;                   // v was an ancestor of u

	// 2. lift both as high as possible WITHOUT meeting
	for(int k=LOG-1;k>=0;k--){
		if(up[k][u]!=up[k][v]){
			u=up[k][u];
			v=up[k][v];
		}
	}

	return up[0][u];                     // their parent is the LCA
}

Step 2 is the clever bit: you jump as far as you can while the ancestors still differ, so afterwards u and v are the two children of the LCA. Going from the largest power down is essential — it is the same greedy as binary representation.

Serialize and deserialize

Turn a tree into a string and back. The key realisation: preorder alone is insufficient unless you record the nulls. With null markers it becomes uniquely decodable.

serialize / deserialize with null markersO(n) both waysO(n)
// Preorder WITH explicit nulls. "1,2,#,#,3,#,#," is unambiguous.
void build(TreeNode* root,string &s){
	if(!root){
		s+="#,";
		return;
	}

	s+=to_string(root->val)+",";
	build(root->left,s);
	build(root->right,s);
}
string serialize(TreeNode* root){
	string s;
	build(root,s);

	return s;
}

// Read in the same preorder. The stream position is shared state, so it
// must be a reference — a copy would restart the parse in each branch.
TreeNode* parse(stringstream &ss){
	string token;
	getline(ss,token,',');

	if(token=="#" or token.empty())return nullptr;

	TreeNode* root=new TreeNode(stoi(token));

	root->left=parse(ss);        // order matters: left then right,
	root->right=parse(ss);       // matching how we wrote it

	return root;
}
TreeNode* deserialize(string data){
	stringstream ss(data);

	return parse(ss);
}
stringstream &ss — the reference is load-bearing. The stream's read position is the parse state shared by every recursive call. Pass it by value and each branch gets its own copy starting from the same place, so the tree comes out badly wrong. This is the Chapter 1 reference-parameter rule with a non-obvious payoff.
🔢
Which pairs of traversals determine a tree?
  • Preorder + inorder — yes. Preorder gives the root; inorder says how many nodes are on each side of it. Recurse.
  • Postorder + inorder — yes. Same argument, taking the root from the end of postorder.
  • Preorder + postorder — no, not for a general binary tree. [1,2] preorder with [2,1] postorder could mean 2 is either child of 1, and nothing distinguishes them. It does work if every node has 0 or 2 children.
  • Preorder with null markers — yes, alone. The nulls supply exactly the missing structural information, which is why serialisation works.
  • Level order with null markers — yes, alone. Same reason.

The underlying principle: two traversals work when one gives you the root and the other gives you the split. Inorder is the only order that supplies a split, which is why it appears in both working pairs.

buildTree from preorder + inorderO(n)O(n)
// Naive: search inorder linearly for the root each time -> O(n^2).
// Better: a value-to-index map makes the split lookup O(1).
TreeNode* helper(vector<int> &preorder,int &preIdx,int inLo,int inHi,
                 unordered_map<int,int> &pos){
	if(inLo>inHi)return nullptr;

	int rootVal=preorder[preIdx];
	preIdx++;                          // consumed — reference, so it advances globally

	TreeNode* root=new TreeNode(rootVal);
	int mid=pos[rootVal];              // where the root sits in inorder

	root->left=helper(preorder,preIdx,inLo,mid-1,pos);
	root->right=helper(preorder,preIdx,mid+1,inHi,pos);

	return root;
}
TreeNode* buildTree(vector<int> &preorder,vector<int> &inorder){
	unordered_map<int,int> pos;
	for(int i=0;i<inorder.size();i++)
	pos[inorder[i]]=i;

	int preIdx=0;

	return helper(preorder,preIdx,0,inorder.size()-1,pos);
}
int &preIdx is the second reference that matters. Preorder is consumed strictly left to right across the whole recursion, so the index is shared state — by reference it advances globally, by value each branch restarts and you build garbage. Assumes distinct values; with duplicates the reconstruction is genuinely ambiguous and you should say so.

Path problems

all root-to-leaf paths — and the undoO(n·h)O(h)
// Preorder, because the path is built top-down.
// The pop_back is what makes a shared vector safe — choose, explore, unchoose.
void paths(TreeNode* root,vector<int> &current,vector<vector<int>> &ans){
	if(!root)return;

	current.push_back(root->val);

	if(!root->left and !root->right){
		ans.push_back(current);        // leaf: record a copy
	}else{
		paths(root->left,current,ans);
		paths(root->right,current,ans);
	}

	current.pop_back();                 // UNDO before returning to the parent
}

// Path sum III: count paths summing to target, starting ANYWHERE.
// Prefix sums plus a hash map (Chapter 6) applied to a tree.
void count(TreeNode* root,long long running,int target,
           unordered_map<long long,int> &seen,int &ans){
	if(!root)return;

	running+=root->val;

	if(seen.count(running-target))
	ans+=seen[running-target];

	seen[running]++;

	count(root->left,running,target,seen,ans);
	count(root->right,running,target,seen,ans);

	seen[running]--;              // UNDO: this prefix is not on other branches
}
int pathSum(TreeNode* root,int target){
	unordered_map<long long,int> seen;
	seen[0]=1;                    // the empty prefix, exactly as in Chapter 6

	int ans=0;
	count(root,0,target,seen,ans);

	return ans;
}
seen[running]-- is the tree version of the backtracking undo. A prefix sum is only valid along the current root-to-node path; leaving it in the map lets a node in the left subtree pair with one in the right, which is not a path. This is the single most common bug in path-sum III, and it produces an overcount that looks plausible.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 RETURN ≠ ANSWER
For diameter and max-path-sum, what you report upward is a single chain; the answer that bends at this node goes into a by-reference accumulator. Conflating them is the classic failure.
💡 MINUS-ONE SENTINEL
Check balance in one traversal by returning height, or −1 to mean "already unbalanced". Two traversals become one, and the early exit is free.
⛔ INT_MIN START
Max-path-sum with negative values must start the answer at INT_MIN, not 0 — and the clamp goes on the child (max(child,0)), never on the answer.
⚠️
Common mistakes
  • Returning the answer instead of the height in diameter. A parent can only extend a single downward path; a path peaking here must go into the reference parameter.
  • Starting maxPathSum at 0. If every value is negative the answer is negative; start at INT_MIN.
  • Forgetting the max(0, ...) clamp. A negative branch should be dropped, not added.
  • Calling height() inside a loop over nodes. That is O(n²); one postorder pass with a sentinel is O(n).
  • Passing the stringstream or preIdx by value. Both are shared parse state; a copy restarts the read in every branch.
  • Forgetting pop_back or seen[running]--. Paths leak across sibling subtrees.
  • Assuming preorder + postorder reconstructs a tree. It does not, unless every node has 0 or 2 children.
  • Assuming both LCA targets exist. If one is absent the recursive version returns the other.
  • Using the general LCA on a BST. O(n) where O(h) iterative was available.
  • Not saying which height convention you use. Nodes or edges — it shifts every answer by one.

Interview drill

Warm-up: Find the diameter of a binary tree. Then explain why the naive approach is O(n²).

How a strong answer sounds
The diameter is the longest path between any two nodes, and crucially it does not have to pass through the root. The naive approach is: for every node, compute left height plus right height and take the maximum. That is correct but each height call is O(n), so over n nodes it is O(n²). The fix is to notice that the height computation already visits every node, so I can compute both quantities in one postorder pass — and the key is that they are different quantities. The function returns 1 + max(leftHeight, rightHeight), which is what a parent can extend upward, and it separately updates a reference parameter with leftHeight + rightHeight, which is the longest path peaking at this node and which the parent can never use. One traversal, O(n) time, O(h) space. I would write the two slots as comments — "RETURNS" and "UPDATES" — before writing the body, because conflating them is the classic error: returning the diameter makes the function wrong on any tree whose longest path avoids the root. Also worth stating whether the answer counts edges or nodes, since left+right counts edges.

Deeper: Can you reconstruct a binary tree from its preorder and postorder traversals?

How a strong answer sounds
Not in general. Preorder gives me the root as its first element and postorder gives me the root as its last, so I know the root from either — but neither tells me where the left subtree ends and the right begins. Concretely, preorder [1,2] with postorder [2,1] is consistent with 2 being 1's left child or its right child, and nothing in the data distinguishes them. What I need is a traversal that supplies the split, and inorder is the only one that does: once I know the root, its position in inorder tells me exactly how many nodes lie in each subtree. So preorder plus inorder works, postorder plus inorder works, and I would implement it with a value-to-index map on inorder so each split lookup is O(1), giving O(n) instead of the O(n²) you get from scanning inorder each time. Two caveats: preorder plus postorder does become sufficient if every node has either zero or two children, because then the first element of the left subtree's preorder identifies the boundary; and any of these reconstructions assumes distinct values, since duplicates make the split genuinely ambiguous. Preorder alone also suffices if nulls are recorded explicitly, which is exactly why serialisation works.

🧠 Key takeaways

  • The core tree pattern: a postorder function that returns what the parent can extend and updates by reference the answer peaking at this node.
  • Encode failure as an impossible return value (height −1) to turn an O(n²) check into one O(n) pass.
  • LCA: recursive split for a general tree, iterative descent for a BST, binary lifting for many queries.
  • A tree is determined by preorder+inorder or postorder+inorder — inorder is the only order that supplies the split.
  • Shared parse state (stringstream, preIdx) must be a reference, and every path-accumulating structure needs an undo.

Check your understanding

In the diameter solution, the recursive function returns the height but updates the diameter by reference. Why not just return the diameter?

Two genuinely different quantities. left+right is a path through this node and dead-ends here; 1+max(left,right) is what an ancestor can build on. Conflating them is the classic error.

Which pair of traversals does not uniquely determine a general binary tree?

Both preorder and postorder identify the root but neither gives the split between subtrees. Inorder is the only traversal that does — which is why it appears in both working pairs. (Preorder+postorder does work if every node has 0 or 2 children.)

Why must the stringstream in deserialize be passed by reference?

Each call consumes the next token from a single shared cursor. The same reasoning applies to int &preIdx in buildTree — preorder is consumed strictly left to right across the whole recursion.

In path sum III, why decrement seen[running] after recursing into both children?

The tree version of backtracking's undo. Without it you overcount with pairings that do not correspond to any actual path, and the answer looks plausible rather than obviously wrong.

The tree is a BST and you need the LCA. Best approach?

The BST invariant tells you which direction to go, so there is no search at all. O(h) time, O(1) space, no recursion. Binary lifting only pays off when there are many queries.
