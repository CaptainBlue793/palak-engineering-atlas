Shortest Paths I: BFS, 0-1 BFS, Dijkstra

Three algorithms, one idea: finish nodes in order of distance, nearest first. BFS uses a plain queue, because every edge costs the same. Dijkstra uses a heap (a structure that always hands you the smallest item), because edges cost different amounts. 0-1 BFS uses a deque (a queue you can push onto at either end), because when every edge costs 0 or 1 a heap is more machinery than you need. Choosing between them takes two questions, and the wrong choice is either too slow or quietly wrong.

  • Use BFS for unweighted shortest paths, and reconstruct the path with parents
  • Write Dijkstra with a min-heap, including the line that skips out-of-date heap entries
  • Prove why Dijkstra's greedy choice is safe, and see exactly where negative weights break it
  • Use the deque trick when weights are only 0 or 1, to get O(V + E)
  • Handle “shortest path with an extra rule” problems by adding to what a state remembers

The unifying idea

Shortest paths are everywhere: a maps app finding the fastest route, a network router picking the cheapest link, a game character walking around walls, or an interview question asking for the "minimum cost", "minimum time" or "fewest moves". The input is a graph where each edge has a length (a weight) and you want, for each node, the smallest total weight of any path from the start. The main tool is relaxing an edge: if dist[u] + w is smaller than the current dist[v] for an edge u → v of weight w, then going through u is a better way to reach v, so lower dist[v] to that value.

All three algorithms keep a set of settled nodes — nodes whose shortest distance is final and will never change. Each round, they settle the closest node that is not settled yet. The only difference is how they find that closest node:

The two-question decision

1. Do the edges have weights (costs)? If no, use BFS at O(V + E) and do not reach for a heap. 2. Can any weight be negative? If yes, use Bellman-Ford or Johnson (Chapter 30). With negative weights Dijkstra is wrong (or, in the lazy-heap version, can be exponentially slow). Otherwise use Dijkstra. And if every weight happens to be 0 or 1, the deque version removes the log factor for free.

Unweighted: BFS

shortest distances from a source — BFSO(V + E)O(V)
// Every edge costs 1, so BFS's layer order IS distance order (Chapter 25).
// dist doubles as the visited array: -1 means unreached.
vector<int> shortestDistances(vector<vector<int>> &graph,int N,int src){
	vector<int> dist(N,-1);
	queue<int> q;

	dist[src]=0;
	q.push(src);

	while(!q.empty()){
		int node=q.front();
		q.pop();

		for(auto &neighbour:graph[node]){
			if(dist[neighbour]==-1){           // first time reached = shortest
				dist[neighbour]=dist[node]+1;
				q.push(neighbour);
			}
		}
	}

	return dist;
}
dist[neighbour] == -1 takes the place of a separate visited array. One array does two jobs, and the two can never disagree — the same three-states-in-one-array idea as Chapter 28's colours. Also, BFS reaches every node by a shortest path the very first time (Chapter 25), so there is no need to compare distances. The first value you write is already final. That is exactly the property Dijkstra has to work hard for.

How the path comes back out of a parent array: suppose BFS from 0 set parent[1] = 0, parent[2] = 0, parent[3] = 1, parent[4] = 3. To get the path to 4, start at 4 and keep following parents: 4 → 3 → 1 → 0, and stop because parent[0] = -1. That list is backwards, so reverse it: 0, 1, 3, 4. Each node remembers only the one step before it, yet together the array holds a shortest path to every node. The four lines below are exactly this walk.

✍️
My convention: return distances, and keep a parent array only when the path is asked for

Rebuilding the actual path takes four extra lines, and they are the same four every time:

vector<int> parent(N,-1);
// ... inside the relaxation, whenever dist[neighbour] improves:
parent[neighbour]=node;

// then walk back from the target and reverse
vector<int> buildPath(vector<int> &parent,int target){
	vector<int> path;

	for(int x=target;x!=-1;x=parent[x])
	path.push_back(x);

	reverse(path.begin(),path.end());

	return path;
}

Do not store whole paths in the queue. Pushing a vector<int> for every node turns O(V) space into O(V²), and copies the whole vector on every push. This is a common mistake in word-ladder style problems. Keep one parent array and walk it at the end.

Dijkstra

Why BFS stops working once edges have different weights: with edges 0→1 (weight 10), 0→2 (1) and 2→1 (1), BFS reaches node 1 first along the single edge and records 10. But the two-edge route through 2 costs only 2. "Fewer edges" is no longer "shorter". Dijkstra fixes this by always processing the node with the smallest distance found so far, which is what the min-heap hands you.

A full dry run. Edges: 0→1 (4), 0→2 (1), 2→1 (2), 1→3 (1), 2→3 (5). Start: dist = [0, ∞, ∞, ∞], heap holds {0,0} (distance first, then node).

Two things to notice. First, node 1 was given 4, then improved to 3 before it was ever popped — a node's distance is only final when it comes off the heap, not when it goes on. Second, the two stale entries {4,1} and {6,3} are leftovers from before those improvements, and the skip line throws them away. On cost: every successful relaxation pushes one entry, so the heap receives at most E + 1 entries, and each push or pop costs O(log E), which is the same as O(log V) because E ≤ V² means log E ≤ 2 log V. That is where O((V + E) log V) comes from.

Dijkstra with a lazy min-heapO((V + E) log V)O(V + E)
// Adjacency: graph[node] holds {weight,neighbour} — weight FIRST so the
// built-in pair comparison does the right thing (Chapter 15).
vector<int> distance(vector<vector<pair<int,int>>> &graph,int N,int src){
	vector<int> dist(N,INT_MAX);
	priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> pq;

	pq.push({0,src});
	dist[src]=0;

	while(!pq.empty()){
		auto [d,node]=pq.top();
		pq.pop();

		if(d>dist[node])continue;        // LAZY DELETION: a stale entry

		for(auto &[weight,neighbour]:graph[node]){
			if(weight+dist[node]<dist[neighbour]){
				dist[neighbour]=weight+dist[node];
				pq.push({dist[neighbour],neighbour});
			}
		}
	}

	for(int i=0;i<N;i++){
		if(dist[i]==INT_MAX)
		dist[i]=-1;                     // unreachable, by this problem's convention
	}

	return dist;
}
if(d > dist[node]) continue; is the line that makes this work. A heap cannot reach in and change or delete an element in the middle (Chapter 15). So when a node's distance improves, we push a new entry and leave the old one there. The old entry is stale (out of date), and throwing it away when it pops is correct and cheaper than any scheme that updates keys in place. Without this line the algorithm still gives the right answer, but it re-explores settled nodes, and on bad input the running time slides toward O(E²).
🧾
Why the greedy is correct — and exactly where it fails

Claim: when Dijkstra pops the unsettled node u with the smallest current distance d, that d is already the true shortest distance.

Suppose it is not — some shorter path to u exists. That path has to leave the settled set somewhere, so let x be the first unsettled node on it. Then dist(x) ≤ (length of the path up to x) ≤ (length of the whole path) < d. The middle step holds because the remaining edges are non-negative, so they can only add to the total, never reduce it. But then x has a smaller current distance than u, and the heap would have popped x first. That contradicts our assumption. ∎

The whole proof rests on weights never being negative. With a negative edge, "the first part of the path is no longer than the whole path" stops being true: a negative edge further along can drag the total below the part you already walked. So a node can be settled at distance 5, while a route found later is worth only 3. Dijkstra has already marked it final and never looks again. It fails silently and returns a believable but wrong number. Try the "negative edge" mode in the visualizer above.

One precise caveat. That failure is exact for the textbook version, which keeps a "settled" set and never touches a settled node again (the visualizer works this way). The lazy-heap code above has no settled set: it pushes a node again whenever its distance improves. With negative edges but no negative cycle, it does end up with the right numbers — but a node can be re-processed so many times that the running time can grow exponentially. So either way, Dijkstra is the wrong tool for negative weights: one version is wrong, the other can be hopelessly slow. Use Bellman-Ford.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 BFS ONLY IF UNIFORM
BFS gives shortest paths only when every edge costs the same. The moment weights differ, a queue processes nodes in the wrong order — that is the single most common wrong answer in this chapter.
💡 LAZY DELETION
Do not implement decrease-key. Push duplicates and skip stale entries with if(d > dist[node]) continue; — that one line is the whole idiom.
💡 WIDEN THE STATE
When a path constraint exists (at most k stops, a key bitmask, fuel remaining), the node is not the state — (node, extra) is. Dijkstra over the widened graph, unchanged.
🚨
Three ways Dijkstra is misused
  • Negative weights. The settled-set version gives wrong answers; the lazy-heap version can take exponential time. Use Bellman-Ford (Chapter 30). And no, adding the same constant to every weight does not fix it. A path with more edges gains more, so the change can flip which path is shortest. For example, a one-edge path of weight −2 and a two-edge path of weights 1 and −4 (total −3, the shorter one). Add 4 to every edge: the first becomes 2, the second 5 + 0 = 5, and now the wrong path looks shorter. (Johnson's algorithm does reweight correctly: it runs Bellman-Ford first to work out a per-node adjustment value.)
  • Using it on an unweighted graph. The answer is right, but it costs O((V+E) log V) where BFS costs O(V+E). That is a real slowdown for no gain.
  • Marking nodes visited when you push them, instead of skipping stale entries when you pop. This is the one place where Chapter 25's "mark on enqueue" rule is deliberately reversed, because a node's distance can still improve after it is queued. Marking on push locks in the first distance, which may not be the best one.

0-1 BFS: the deque trick

When every edge costs 0 or 1, the heap earns nothing. At any moment the nodes waiting to be processed have only two different distances, d and d+1. A deque keeps those in order for free: put 0-cost neighbours at the front (same distance) and 1-cost neighbours at the back (one more).

Dry run with edges 0→1 (1), 0→2 (0), 2→1 (0), 1→3 (1):

  1. Deque [0]. Pop 0. Edge to 1 costs 1: dist[1] = 1, push to the back → [1]. Edge to 2 costs 0: dist[2] = 0, push to the front → [2, 1].
  2. Pop 2 (distance 0). Edge to 1 costs 0: 0 < 1, so dist[1] = 0, push to the front → [1, 1].
  3. Pop 1 (distance 0). Edge to 3 costs 1: dist[3] = 1, push to the back → [1, 3].
  4. Pop the old copy of 1. Its edge to 3 gives 0+1 = 1, which is not smaller than 1, so nothing changes. Pop 3. Done: dist = [0, 0, 0, 1].

The deque was always ordered by distance from front to back, which is all the heap was doing for us. A node can sit in the deque twice (node 1 did), but the < check means the second copy does no damage, and a node's distance can improve at most once after it is first set (from d+1 down to d), so it enters the deque at most twice and the total stays O(V + E).

0-1 BFSO(V + E)O(V)
// A 0-weight edge keeps you in the SAME distance layer -> push_front.
// A 1-weight edge moves you to the NEXT layer -> push_back.
// The deque therefore stays sorted by distance with no heap at all.
vector<int> zeroOneBFS(vector<vector<pair<int,int>>> &graph,int N,int src){
	vector<int> dist(N,INT_MAX);
	deque<int> dq;

	dist[src]=0;
	dq.push_back(src);

	while(!dq.empty()){
		int node=dq.front();
		dq.pop_front();

		for(auto &[weight,neighbour]:graph[node]){
			if(dist[node]+weight<dist[neighbour]){
				dist[neighbour]=dist[node]+weight;

				if(weight==0)dq.push_front(neighbour);
				else dq.push_back(neighbour);
			}
		}
	}

	return dist;
}
The classic use is “remove the fewest obstacles”: stepping into an empty cell costs 0, breaking through a wall costs 1. Another is “minimum cost to make at least one valid path in a grid”, where following an existing arrow is free and changing one costs 1. Spotting that a problem has only two edge costs saves you a log factor. A heap-based solution usually still passes, so treat this as a nice bonus rather than a must.

Extending the state: constrained shortest paths

This is the most useful idea in the chapter. When a problem adds an extra rule — at most K stops, at most K walls broken, colours must alternate — you do not need a new algorithm. You give each state more to remember. Instead of "which node am I at", a state becomes "which node am I at, and how much of my budget have I used". On that bigger graph, Dijkstra's greedy choice is safe again.

Why plain Dijkstra fails with a stop limit. Flights: 0→1 ($1), 1→2 ($1), 2→3 ($1), 0→2 ($5). Go from 0 to 3 with at most K = 1 stop (so at most 2 flights). Plain Dijkstra records the cheapest way to reach 2 as $2 via 1. Then the route 0→2 at $5 looks worse and is thrown away. But the $2 route already used one stop, so continuing to 3 would need a second stop, which is not allowed. The only legal answer, 0→2→3 for $6, was discarded. With the state (node, stops), "at 2 after 1 flight for $5" and "at 2 after 2 flights for $2" are different states, so neither overwrites the other, and the $6 route survives.

cheapest flight with at most K stops — state is (node, stopsUsed)O(E·K log(V·K))O(V·K)
// Plain Dijkstra is WRONG here: the cheapest way to reach a city may use
// too many stops, and a pricier route with fewer stops may be the only
// usable one. So "cheapest to reach node" is not a sufficient state.
// Fix: dist[node][stops], and treat (node,stops) as the real vertex.
int findCheapestPrice(int N,vector<vector<int>> &flights,int src,int dst,int K){
	vector<vector<pair<int,int>>> graph(N);
	for(auto &f:flights)
	graph[f[0]].push_back({f[2],f[1]});      // {price,to}

	// best[node][stops] = cheapest cost to reach node having used `stops` stops
	vector<vector<int>> best(N,vector<int>(K+2,INT_MAX));
	priority_queue<vector<int>,vector<vector<int>>,greater<vector<int>>> pq;

	pq.push({0,src,0});                   // {cost,node,stops}
	best[src][0]=0;

	while(!pq.empty()){
		auto top=pq.top();
		pq.pop();

		int cost=top[0];
		int node=top[1];
		int stops=top[2];

		if(node==dst)return cost;        // first pop of dst is optimal
		if(stops>K)continue;
		if(cost>best[node][stops])continue;   // stale, same as before

		for(auto &[price,neighbour]:graph[node]){
			if(cost+price<best[neighbour][stops+1]){
				best[neighbour][stops+1]=cost+price;
				pq.push({cost+price,neighbour,stops+1});
			}
		}
	}

	return -1;
}
The pattern: when the greedy choice breaks, widen the state until it works again. Here the set of nodes becomes V × (K+2) — one copy of the graph per number of stops used — and Dijkstra is correct on that bigger graph. The same move handles "at most K wall breaks" (state is (cell, breaksUsed)), "edge colours must alternate" (state is (node, lastColour)) and "you must collect keys" (state is (cell, keyBitmask)). Noticing that an extra rule belongs inside the state is the most reusable idea in this chapter.
🧩
Other Dijkstra variants worth recognising
  • Several starting points. Push every source with distance 0 before the loop starts. One run then gives each node its distance to the nearest source — the weighted version of multi-source BFS (Chapter 34).
  • Make the weakest edge as strong as possible (the widest-bottleneck path — think the heaviest lorry a route can carry). Replace dist[node] + weight with min(dist[node], weight) and use a max-heap. "Path with the highest probability" is the same shape, using multiplication.
  • Make the worst single step as small as possible ("swim in rising water", "path with minimum effort"). Replace the sum with max(dist[node], weight). Both variants work because the new operation, like addition, never improves as a path gets longer.
  • Counting how many shortest paths there are. Keep a ways[] array. When you find a strictly better distance, ways[nb] = ways[node]. When you find an equally good one, ways[nb] += ways[node].
  • Dijkstra from both ends. Search forward from the start and backward from the target, and meet in the middle. On large road networks this roughly halves the area you explore.
  • A*. Dijkstra with an estimate of the remaining distance added to each priority. It stays correct as long as that estimate never overshoots the true remaining distance.
⚠️
Common mistakes
  • Using Dijkstra with negative weights. Quietly wrong (settled-set version) or exponentially slow (lazy-heap version). And adding a constant to every weight does not fix it.
  • Leaving out if(d > dist[node]) continue;. Still correct, but settled nodes get explored again and the running time gets much worse.
  • Marking visited on push in Dijkstra. It locks in a first distance that may not be the best. This is the deliberate exception to Chapter 25's rule.
  • Pushing {node, weight} instead of {weight, node}. The heap then sorts by node id instead of distance, and the algorithm returns nonsense that looks like a real answer.
  • Forgetting greater<>. A priority_queue is a max-heap by default, so you would settle the farthest node first.
  • Overflow with INT_MAX. If dist[node] is INT_MAX, then dist[node] + weight overflows and wraps around to a negative number. Protect it with the if(d > dist[node]) continue; skip, use long long, or check the node is reachable before adding.
  • Storing whole paths in the queue. O(V²) space and a full copy on every push. Use a parent array instead.
  • Using plain Dijkstra when the problem has an extra rule. "At most K stops" needs the state widened to (node, stops).
  • Using Dijkstra on an unweighted graph. BFS is simpler and a log factor faster.

Interview drill

Warm-up: Implement Dijkstra and explain the if(d > dist[node]) continue; line.

How a strong answer sounds
I keep a dist array set to infinity, and a min-heap of {distance, node} pairs with the distance first, so the built-in pair comparison sorts by distance and I need no custom comparator. Pop the smallest, try to improve each outgoing edge, and push a new entry whenever a neighbour's distance gets better. The skip line exists because a binary heap cannot change or remove an element sitting in the middle of it. So instead of updating a key, I push a fresh entry with the better distance and leave the old one behind. That old entry is stale. By the time it reaches the top, dist[node] is already smaller than the d it carries, so exploring from it would redo work with a worse distance. The test d > dist[node] spots exactly that and drops it in O(1). This is called lazy deletion, and in practice it beats a heap with a real decrease-key operation, because the constant factors are much smaller. Leaving the line out keeps the algorithm correct — the improvement checks still prevent wrong answers — but settled nodes get explored again and the running time gets much worse on dense graphs. It also happens to prevent an INT_MAX + weight overflow, since unreachable nodes are never explored.

Deeper: Why does Dijkstra fail on negative weights, and why does adding a constant to every edge not fix it?

How a strong answer sounds
Dijkstra's correctness rests on one claim: when I pop the unsettled node with the smallest distance, that distance is final. The proof assumes a shorter path exists, takes the first unsettled node x on that path, and argues that the part of the path up to x is no longer than the whole path — so x would have been popped first, a contradiction. That step needs non-negative weights. With a negative edge further along, the whole path can be shorter than its own first part, and the contradiction disappears. Concretely, a node can be settled at distance 5 while a route through a negative edge later costs only 3. The node is already final, so Dijkstra never revisits it and returns 5. It fails silently with a believable number, which is the worst kind of failure. Adding a constant c to every edge does not fix it, because it does not add the same amount to every path: a path with k edges gains k·c. So the change punishes paths with more edges and can make a genuinely shorter route look worse. The correct fix is Johnson's algorithm. Run Bellman-Ford from an added virtual source to get a value h(v) for each node, then replace each weight with w(u,v) + h(u) − h(v). Those new weights are provably non-negative, and they keep the relative order of paths, because along any path the h terms cancel out except at the two ends. For a single source with negative edges, Bellman-Ford at O(V·E) is the direct answer, and its Vth pass also detects a negative cycle — a case where shortest paths have no meaning at all.

🧠 Key takeaways

  • All three algorithms settle nodes nearest-first; only the container used to find the closest node differs.
  • Unweighted → BFS in O(V + E). Weighted with no negatives → Dijkstra. Weights of only 0 and 1 → deque, which drops the log factor.
  • if(d > dist[node]) continue; throws away out-of-date heap entries, and it also prevents the INT_MAX + weight overflow.
  • Dijkstra's proof needs weights that are never negative. One negative edge makes it quietly wrong, and shifting all weights up does not fix it.
  • When an extra rule breaks the greedy choice, widen the state — (node, stops), (cell, keys) — and Dijkstra works again.

Check your understanding

What does if(d > dist[node]) continue; do in Dijkstra?

Because you push a new pair instead of updating the old one, out-of-date entries stay in the heap. Skipping them costs O(1) and beats a heap with a real decrease-key operation in practice. It also conveniently prevents the INT_MAX + weight overflow.

Why does Dijkstra fail with negative edge weights?

Once a node is popped, Dijkstra never looks at it again. A negative edge can make a route found later shorter, but the node is already final. You get a believable wrong number and no error.

Every edge weight is 0 or 1. What is the best approach?

Only two different distances are ever waiting at once, so a deque keeps them in order without a heap, saving the log factor. Plain BFS would be wrong, because a 0-weight edge does not increase the distance at all.

“Cheapest flight from A to B with at most K stops.” Why is plain Dijkstra insufficient?

Settling a node on price alone throws away a more expensive route that uses fewer stops — which may be the only one allowed. Widening the node set to (node, stops) makes the greedy choice safe again. That is the general fix whenever an extra rule breaks it.

You push {node, distance} instead of {distance, node} into the min-heap. What happens?

A pair is compared by .first first. With the node id in that slot, you are no longer running Dijkstra at all — and the code compiles and runs quite happily. Keeping the sort key first is exactly why this course always writes {weight, node}.
