Shortest Paths I: BFS, 0-1 BFS, Dijkstra

Three algorithms, one idea: settle nodes in increasing order of distance. BFS does it with a queue because every edge costs the same. Dijkstra does it with a heap because they do not. And 0-1 BFS does it with a deque, because when weights are only 0 or 1 a heap is overkill. Picking the right one is a two-question decision, and the wrong one is either too slow or silently incorrect.

  • Use BFS for unweighted shortest paths, and reconstruct the path with parents
  • Write Dijkstra with a min-heap and the lazy-deletion skip
  • Prove Dijkstra's greedy choice, and see exactly where negative weights break it
  • Use the deque trick for 0/1 weights to get O(V + E)
  • Handle the “shortest path with a constraint” variants by extending the state

The unifying idea

All three algorithms maintain a set of settled nodes whose shortest distance is final, and repeatedly settle the closest unsettled node. The only difference is how they find "closest":

The two-question decision

1. Are the edges weighted? No → BFS, O(V + E), and do not reach for a heap. 2. Can any weight be negative? Yes → Bellman-Ford or Johnson (Chapter 30); Dijkstra is not merely slow here, it is wrong. Otherwise Dijkstra. And if all weights happen to be 0 or 1, the deque version drops the log factor for free.

Unweighted: BFS

shortest distances from a source — BFSO(V + E)O(V)
// Every edge costs 1, so BFS's layer order IS distance order (Chapter 25).
// dist doubles as the visited array: -1 means unreached.
vector<int> shortestDistances(vector<vector<int>> &graph,int N,int src){
	vector<int> dist(N,-1);
	queue<int> q;

	dist[src]=0;
	q.push(src);

	while(!q.empty()){
		int node=q.front();
		q.pop();

		for(auto &neighbour:graph[node]){
			if(dist[neighbour]==-1){           // first time reached = shortest
				dist[neighbour]=dist[node]+1;
				q.push(neighbour);
			}
		}
	}

	return dist;
}
dist[neighbour] == -1 replaces a separate visited array — one array, two jobs, no way for them to disagree (the same three-state idea as Chapter 28's colours). And because BFS reaches every node by a shortest path the first time (Chapter 25), there is no need to compare distances: the first assignment is already final. That is precisely the property Dijkstra has to work for.
✍️
My convention: return distances, and keep a parent array only when the path is asked for

Reconstructing the path is four extra lines, and they are the same four every time:

vector<int> parent(N,-1);
// ... inside the relaxation, whenever dist[neighbour] improves:
parent[neighbour]=node;

// then walk back from the target and reverse
vector<int> buildPath(vector<int> &parent,int target){
	vector<int> path;

	for(int x=target;x!=-1;x=parent[x])
	path.push_back(x);

	reverse(path.begin(),path.end());

	return path;
}

Do not store whole paths in the queue. Pushing a vector<int> per node turns O(V) space into O(V²) and copies on every push — a real and common mistake in word-ladder style problems. One parent array, walk it at the end.

Dijkstra with a lazy min-heapO((V + E) log V)O(V + E)
// Adjacency: graph[node] holds {weight,neighbour} — weight FIRST so the
// built-in pair comparison does the right thing (Chapter 15).
vector<int> distance(vector<vector<pair<int,int>>> &graph,int N,int src){
	vector<int> dist(N,INT_MAX);
	priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> pq;

	pq.push({0,src});
	dist[src]=0;

	while(!pq.empty()){
		auto [d,node]=pq.top();
		pq.pop();

		if(d>dist[node])continue;        // LAZY DELETION: a stale entry

		for(auto &[weight,neighbour]:graph[node]){
			if(weight+dist[node]<dist[neighbour]){
				dist[neighbour]=weight+dist[node];
				pq.push({dist[neighbour],neighbour});
			}
		}
	}

	for(int i=0;i<N;i++){
		if(dist[i]==INT_MAX)
		dist[i]=-1;                     // unreachable, by this problem's convention
	}

	return dist;
}
if(d > dist[node]) continue; is the line that makes this work. A heap cannot remove an arbitrary element (Chapter 15), so when a node's distance improves we push a new entry and leave the old one. The old one is stale, and skipping it on pop is both correct and cheaper than any decrease-key scheme. Without this line the algorithm is still correct but re-expands settled nodes, degrading toward O(E²) on adversarial input.
🧾
Why the greedy is correct — and exactly where it fails

Claim: when Dijkstra pops the minimum-distance unsettled node u with tentative distance d, that d is final.

Suppose not — some shorter path to u exists. That path must leave the settled set at some point, so let x be its first unsettled node. Then dist(x) ≤ (length of the path up to x) ≤ (length of the whole path) < d, because the remaining edges are non-negative and cannot reduce the total. But then x would have a smaller tentative distance than u and the heap would have popped x first — contradiction. ∎

The non-negativity is load-bearing. With a negative edge, "the path up to x is no longer than the whole path" becomes false: a later negative edge can make the total smaller than a prefix. So a node can be settled at distance 5, and a route through it discovered later can be worth 3 — but Dijkstra has already finalised it and will never look again. It fails silently, returning a plausible wrong number. Try the "negative edge" mode in the visualizer above.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 BFS ONLY IF UNIFORM
BFS gives shortest paths only when every edge costs the same. The moment weights differ, a queue processes nodes in the wrong order — that is the single most common wrong answer in this chapter.
💡 LAZY DELETION
Do not implement decrease-key. Push duplicates and skip stale entries with if(d > dist[node]) continue; — that one line is the whole idiom.
💡 WIDEN THE STATE
When a path constraint exists (at most k stops, a key bitmask, fuel remaining), the node is not the state — (node, extra) is. Dijkstra over the widened graph, unchanged.
🚨
Three ways Dijkstra is misused
  • Negative weights. Not slow — wrong. Use Bellman-Ford (Chapter 30). And no, adding a constant to every weight does not fix it: that changes the relative cost of paths with different edge counts, so it can change which path is shortest. (Johnson's algorithm reweights correctly, using Bellman-Ford to compute a potential function first.)
  • Using it on an unweighted graph. Correct but O((V+E) log V) where BFS is O(V+E). A real slowdown for no benefit.
  • Marking nodes visited on push instead of skipping stale pops. This is the one place where Chapter 25's "mark on enqueue" rule is deliberately inverted, because a node's tentative distance can improve after it is queued. Marking on push freezes the first, possibly non-optimal, distance.

0-1 BFS: the deque trick

When every edge weighs 0 or 1, the heap is doing nothing useful. At any moment the frontier contains only two distinct distances — d and d+1 — so a deque keeps them ordered for free.

0-1 BFSO(V + E)O(V)
// A 0-weight edge keeps you in the SAME distance layer -> push_front.
// A 1-weight edge moves you to the NEXT layer -> push_back.
// The deque therefore stays sorted by distance with no heap at all.
vector<int> zeroOneBFS(vector<vector<pair<int,int>>> &graph,int N,int src){
	vector<int> dist(N,INT_MAX);
	deque<int> dq;

	dist[src]=0;
	dq.push_back(src);

	while(!dq.empty()){
		int node=dq.front();
		dq.pop_front();

		for(auto &[weight,neighbour]:graph[node]){
			if(dist[node]+weight<dist[neighbour]){
				dist[neighbour]=dist[node]+weight;

				if(weight==0)dq.push_front(neighbour);
				else dq.push_back(neighbour);
			}
		}
	}

	return dist;
}
The classic application is “minimum obstacles to remove” — moving through an empty cell costs 0, breaking a wall costs 1. Also “minimum cost to make at least one valid path in a grid”, where following an existing arrow is free and changing it costs 1. Recognising that a problem has only two edge costs is worth a log factor, and a heap-based solution will usually still pass, so this is a nice-to-have rather than a must.

Extending the state: constrained shortest paths

This is the highest-value generalisation in the chapter. When a problem adds a constraint — at most K stops, at most K wall-breaks, alternating colours — the fix is not a new algorithm. It is to make the state richer so that Dijkstra's greedy is valid again on the expanded graph.

cheapest flight with at most K stops — state is (node, stopsUsed)O(E·K log(V·K))O(V·K)
// Plain Dijkstra is WRONG here: the cheapest way to reach a city may use
// too many stops, and a pricier route with fewer stops may be the only
// usable one. So "cheapest to reach node" is not a sufficient state.
// Fix: dist[node][stops], and treat (node,stops) as the real vertex.
int findCheapestPrice(int N,vector<vector<int>> &flights,int src,int dst,int K){
	vector<vector<pair<int,int>>> graph(N);
	for(auto &f:flights)
	graph[f[0]].push_back({f[2],f[1]});      // {price,to}

	// best[node][stops] = cheapest cost to reach node having used `stops` stops
	vector<vector<int>> best(N,vector<int>(K+2,INT_MAX));
	priority_queue<vector<int>,vector<vector<int>>,greater<vector<int>>> pq;

	pq.push({0,src,0});                   // {cost,node,stops}
	best[src][0]=0;

	while(!pq.empty()){
		auto top=pq.top();
		pq.pop();

		int cost=top[0];
		int node=top[1];
		int stops=top[2];

		if(node==dst)return cost;        // first pop of dst is optimal
		if(stops>K)continue;
		if(cost>best[node][stops])continue;   // stale, same as before

		for(auto &[price,neighbour]:graph[node]){
			if(cost+price<best[neighbour][stops+1]){
				best[neighbour][stops+1]=cost+price;
				pq.push({cost+price,neighbour,stops+1});
			}
		}
	}

	return -1;
}
The pattern: when the greedy fails, widen the state until it holds again. Here the vertex set becomes V × (K+2) and Dijkstra is correct on that expanded graph. The same move handles "at most K wall breaks" (state is (cell, breaksUsed)), "alternating edge colours" (state is (node, lastColour)) and "must collect keys" (state is (cell, keyBitmask)). Recognising that a constraint belongs in the state is the single most transferable idea in this chapter.
🧩
Other Dijkstra variants worth recognising
  • Multi-source. Push every source with distance 0 before the loop. Gives "distance to the nearest source" in one run — the weighted analogue of multi-source BFS (Chapter 34).
  • Maximise the minimum edge (path of maximum bottleneck). Replace dist[node] + weight with min(dist[node], weight) and use a max-heap. "Path with maximum probability" is the same shape with multiplication.
  • Minimise the maximum edge ("swim in rising water", "path with minimum effort"). Replace the sum with max(dist[node], weight). Both of these work because the replacement operation is still monotone along a path.
  • Counting shortest paths. Keep a ways[] array: on a strict improvement, ways[nb] = ways[node]; on a tie, ways[nb] += ways[node].
  • Bidirectional Dijkstra. Search from both ends and meet in the middle. Roughly halves the explored region on large road networks.
  • A*. Dijkstra plus an admissible heuristic added to the priority. Same correctness guarantee if the heuristic never overestimates.
⚠️
Common mistakes
  • Using Dijkstra with negative weights. Silently wrong, not slow. And adding a constant to all weights does not fix it.
  • Omitting if(d > dist[node]) continue;. Still correct, but settled nodes get re-expanded and the complexity degrades badly.
  • Marking visited on push in Dijkstra. Freezes a possibly non-optimal first distance. This is the deliberate exception to Chapter 25's rule.
  • Pushing {node, weight} instead of {weight, node}. The heap then orders by node id and the algorithm returns garbage that looks like a plausible answer.
  • Forgetting greater<>. A default priority_queue is a max-heap, so you settle the farthest node first.
  • Overflow with INT_MAX. dist[node] + weight overflows when dist[node] is INT_MAX. Guard with the if(d > dist[node]) continue; skip, or use long long, or test reachability before adding.
  • Storing whole paths in the queue. O(V²) space and a copy per push. Use a parent array.
  • Using plain Dijkstra on a constrained problem. "At most K stops" needs the state widened to (node, stops).
  • Using Dijkstra on an unweighted graph. BFS is a log factor faster and simpler.

Interview drill

Warm-up: Implement Dijkstra and explain the if(d > dist[node]) continue; line.

How a strong answer sounds
I keep a dist array initialised to infinity and a min-heap of {distance, node} pairs with the distance first, so the built-in pair comparison orders by distance without a custom comparator. Pop the smallest, relax each outgoing edge, and push a new entry whenever a neighbour's tentative distance improves. The skip line exists because a binary heap cannot remove or update an arbitrary element — so instead of a decrease-key operation, I push a fresh entry with the better distance and leave the old one behind. That old entry is stale: by the time it reaches the top, dist[node] has already been improved below the d it carries, so re-expanding from it would repeat work with a worse distance. The comparison d > dist[node] detects exactly that and discards it in O(1). This is called lazy deletion, and in practice it beats a real decrease-key heap because the constant factors are far smaller. Omitting the line leaves the algorithm correct — the relaxation checks prevent wrong answers — but settled nodes get re-expanded and the running time degrades badly on dense graphs. It also happens to prevent an INT_MAX + weight overflow, since unreachable nodes never get expanded.

Deeper: Why does Dijkstra fail on negative weights, and why does adding a constant to every edge not fix it?

How a strong answer sounds
Dijkstra's correctness rests on one claim: when I pop the minimum-distance unsettled node, its distance is final. The proof supposes a shorter path exists, takes the first unsettled node x on that path, and argues that the prefix up to x is no longer than the whole path — so x would have been popped first, a contradiction. That step uses non-negativity: with a negative edge later on, the whole path can be shorter than its own prefix, so the contradiction evaporates. Concretely, a node can be settled at distance 5 while a route through a negative edge later turns out to cost 3, and since the node is already finalised Dijkstra never revisits it and returns 5. It fails silently with a plausible number, which is the worst failure mode. Adding a constant c to every edge does not repair this, because it does not add the same amount to every path — a path with k edges gains k·c, so the transformation penalises longer paths and can make a genuinely shorter route look worse. The correct reweighting is Johnson's algorithm: run Bellman-Ford from a virtual source to get a potential h(v), then replace each weight with w(u,v) + h(u) − h(v), which is provably non-negative and preserves the relative order of paths because the potentials telescope along any path. For a single source with negative edges, Bellman-Ford at O(V·E) is the direct answer, and its Vth pass also detects a negative cycle — which is a case where shortest paths are undefined altogether.

🧠 Key takeaways

  • All three algorithms settle nodes in increasing distance order; only the "find the closest" container differs.
  • Unweighted → BFS in O(V + E). Weighted non-negative → Dijkstra. Weights of 0/1 → deque, dropping the log factor.
  • if(d > dist[node]) continue; is lazy deletion, and it also prevents the INT_MAX + weight overflow.
  • Dijkstra's proof needs non-negativity; a negative edge makes it silently wrong, and shifting all weights does not fix it.
  • When a constraint breaks the greedy, widen the state — (node, stops), (cell, keys) — and Dijkstra is valid again.

Check your understanding

What does if(d > dist[node]) continue; do in Dijkstra?

Since you push a new pair instead of decreasing a key, old entries linger. Skipping them is O(1) and beats a real decrease-key heap in practice. It also conveniently prevents the INT_MAX + weight overflow.

Why does Dijkstra fail with negative edge weights?

Once a node is popped, Dijkstra never reconsiders it. A negative edge can make a later-discovered route shorter, but the node is already finalised — and it returns a plausible wrong number with no error.

Every edge weight is 0 or 1. What is the best approach?

The frontier holds only two distinct distances at a time, so a deque keeps it sorted with no heap. Drops the log factor. Plain BFS would be wrong, since a 0-weight edge does not increase the distance.

“Cheapest flight from A to B with at most K stops.” Why is plain Dijkstra insufficient?

Settling a node by cost alone discards a pricier route that uses fewer stops and may be the only usable one. Widening the vertex set to (node, stops) makes the greedy valid again — the general fix whenever a constraint breaks it.

You push {node, distance} instead of {distance, node} into the min-heap. What happens?

pair compares .first first. With the node id there, you are no longer running Dijkstra at all — and it compiles and runs happily. Keeping the sort key first is exactly why this course always writes {weight, node}.
