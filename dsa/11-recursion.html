Recursion & The Call Stack

Recursion is the foundation of the next forty chapters — trees, graphs, backtracking and every dynamic program are recursion with different bookkeeping. The reason it feels hard is that people try to trace it in their head, which does not scale past three levels. This chapter replaces tracing with two habits: trust the recursive call, and draw the recursion tree.

  • Explain what a stack frame holds, and why recursion depth is space
  • Write a correct base case and know the three ways it goes wrong
  • Use the leap of faith instead of mentally unrolling calls
  • Read complexity off a recursion tree, and spot the repeats that mean “add memoisation”
  • Convert any recursion to a loop, and know when that is worth doing

What actually happens: the call stack

Every function call pushes a stack frame holding its parameters, its local variables and the address to return to. The frame lives until the call returns. So at the deepest point of a recursion, every frame on the path is simultaneously in memory — which is why recursion depth is a space cost, and why a deep enough recursion crashes rather than merely slowing down.

How deep can you actually go?

A typical stack is 1–8 MB and a small frame is 32–64 bytes, so roughly 10⁴ to 10⁵ frames before a stack overflow — and a frame holding large local arrays reduces that sharply. So: recursing over a balanced tree of 10⁶ nodes is fine (depth ~20). Recursing over a degenerate tree or a path graph of 10⁶ nodes is not — depth 10⁶ crashes. When n can reach 10⁵ or more and the structure might be a chain, either convert to an explicit stack or say out loud that you would. Note that a stack overflow is a hard crash with no exception to catch, which is why it is worth predicting rather than discovering.

The base case, and its three failure modes

Every recursion needs a case that returns without recursing, and the recursive calls must provably move toward it. Three things go wrong:

1️⃣

Missing entirely

Infinite recursion until the stack overflows. Usually obvious, because it crashes immediately.

2️⃣

Unreachable

if(n==0) but you recurse with n-2 from an odd start — it steps straight over the base case. Use if(n<=0). This is the sneaky one.

3️⃣

Incomplete

Handles n==0 but not the negative or null case that some branch can produce. For trees this is exactly if(!root)return;.

✍️
My convention: guard with <= and !, never ==

if(n<=0), not if(n==0). if(!root), not if(root==nullptr). The inequality catches every value that has passed the boundary, not just the one you expected to land on — which makes the base case robust to a recursive step you later change.

// Fragile: steps over the base case from an odd n and never terminates.
int f(int n){
	if(n==0)return 1;
	return f(n-2);
}

// Robust: any value at or past the boundary terminates.
int f(int n){
	if(n<=0)return 1;
	return f(n-2);
}

This is the same instinct as the guard clause from Chapter 1: make the exit condition as wide as it can correctly be.

The leap of faith — how to actually write recursion

The habit that unblocks people: do not trace the recursion. Assume the recursive call already works correctly on a smaller input, and write only the one step that combines its result. Three questions, in order:

What is the smallest input, and what is its answer?

That is your base case, written first, on line one. For a tree it is almost always the null node.

If I had the answer for a smaller input, what would I do with it?

Assume it is already correct. Height of a tree: if I know the heights of both subtrees, the answer is 1 + max(left, right). You do not need to know how those heights were obtained.

Does every call get strictly closer to the base case?

n-1, n/2, root->left — each strictly shrinks the problem. If some path does not shrink, you have an infinite recursion.

the leap of faith, three timeswrite step 2, trust step 2
// "If I knew both subtree heights, the answer is 1 + the larger."
int height(TreeNode* root){
	if(!root)return 0;

	return 1+max(height(root->left),height(root->right));
}

// "If I knew the reverse of the rest of the list, I'd point the rest at me."
ListNode* reverse(ListNode* head){
	if(!head or !head->next)return head;

	ListNode* newHead=reverse(head->next);   // trust it

	head->next->next=head;      // the node after me now points back at me
	head->next=nullptr;         // and I become the new tail

	return newHead;
}

// "If I knew every subset of the rest, each is a subset with or without a[i]."
void subsets(vector<int> &a,int i,vector<int> &current,vector<vector<int>> &ans){
	if(i==a.size()){
		ans.push_back(current);
		return;
	}

	subsets(a,i+1,current,ans);        // exclude a[i]

	current.push_back(a[i]);
	subsets(a,i+1,current,ans);        // include a[i]
	current.pop_back();                // UNDO — this is backtracking (Ch 35)
}
Notice how short step 2 always is. One or two lines. If your recursive step is fifteen lines, you are probably doing work that belongs in the recursive call — which usually means the function signature is wrong, not that the logic is hard.

The recursion tree: complexity and the DP signal

To find a recursive algorithm's complexity, draw the tree of calls and count. Total work = number of nodes × work per node, or sum the work level by level when it varies.

15 calls for n = 5. The tree has ~2ⁿ nodes because each call spawns two and the depth is n. fib(2) is computed three times, fib(1) five times. Red means recomputed.

mergeSort(8) — two branches, no repeats
ms(0,7) O(n) merge ├─ ms(0,3) O(n/2) │ ├─ ms(0,1) O(n/4) │ │ ├─ ms(0,0) ✓ │ │ └─ ms(1,1) ✓ │ └─ ms(2,3) O(n/4) │ ├─ ms(2,2) ✓ │ └─ ms(3,3) ✓ └─ ms(4,7) O(n/2) ├─ ms(4,5) O(n/4) │ ├─ ms(4,4) ✓ │ └─ ms(5,5) ✓ └─ ms(6,7) O(n/4) ├─ ms(6,6) ✓ └─ ms(7,7) ✓ log n levels × O(n) per level

Every subproblem is distinct — the ranges never overlap. So there is nothing to memoise, and the complexity is simply levels × work-per-level = O(n log n).

🔑
Repeated subproblems in the tree = dynamic programming

That is the entire diagnostic. If the same argument appears at two different places in the recursion tree, you are recomputing, and caching the result collapses an exponential tree into a linear one. fib with memoisation goes from O(2ⁿ) to O(n) with three added lines. Merge sort's subproblems are all distinct, so memoisation would buy nothing. Chapter 38 turns this observation into a method — but the observation itself belongs here, because it is a property of the recursion tree, not of DP.

// Naive: every call re-solves subproblems its sibling already solved.
int fib(int n){
	if(n<=1)return n;

	return fib(n-1)+fib(n-2);
}

// Memoised: dp carried by reference, -1 means "not computed yet".
int fib(int n,vector<int> &dp){
	if(n<=1)return n;

	if(dp[n]!=-1)return dp[n];            // 1. read the cache

	return dp[n]=fib(n-1,dp)+fib(n-2,dp);  // 2. write it on the way out
}
int fib(int n){
	vector<int> dp(n+1,-1);                  // 3. driver owns the cache
	return fib(n,dp);
}
Helper plus driver again, with the cache in a reference parameter exactly as Chapter 1 prescribed. A static or global dp would work once and then silently return stale answers on a second call with different data — which is the precise reason that convention exists.

Recursion → iteration

Any recursion can be made iterative. Whether you should depends on which kind it is.

// acc carries the answer forward, so nothing
// remains to do after the call returns.
int sumTo(int n,int acc){
	if(n<=0)return acc;

	return sumTo(n-1,acc+n);
}
The same thing as a loop
// Identical arithmetic, O(1) space.
int sumTo(int n){
	int acc=0;

	while(n>0){
		acc+=n;
		n--;
	}

	return acc;
}
🚫
Do not rely on tail-call optimisation in C++

Some compilers turn a tail call into a jump at -O2, which makes it O(1) space. This is not guaranteed by the standard, it typically does not happen in a debug build, and it silently stops happening when you add a destructor-bearing local. So a deep tail recursion that works in release can crash in debug. If you need the O(1) space guarantee, write the loop.

iterative inorder — the explicit-stack conversionO(n)O(h) explicit
// The stack now holds exactly what the call frames held: "nodes whose left
// subtree I have finished but which I have not visited yet".
vector<int> inorder(TreeNode* root){
	vector<int> ans;
	stack<TreeNode*> st;
	TreeNode* node=root;

	while(node or !st.empty()){
		while(node){              // go as far left as possible
			st.push(node);
			node=node->left;
		}

		node=st.top();
		st.pop();

		ans.push_back(node->val);   // visit

		node=node->right;         // then head right
	}

	return ans;
}
Same complexity, no stack-overflow risk. The space is still O(h), but it is now heap-allocated rather than on the (much smaller) call stack — so a 10⁶-node chain works. Chapter 16 has the iterative preorder and postorder, and the O(1)-space Morris traversal.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 THREE QUESTIONS
For every recursion: what is the base case, does the argument strictly shrink, and what do I return upward? Answer those three and the body writes itself.
💡 CHOOSE / UNDO
Backtracking is push, recurse, pop — and the pop must be the exact inverse of the push. If you mutate two things going down, restore both coming up.
⛔ DEPTH
Recursion depth is O(h), and h can be n on a chain. At 10⁵ nodes the default stack overflows, so know the iterative or reverse-BFS rewrite before you need it.
⚠️
Common mistakes
  • Base case with == instead of <=. A step of n-2 from an odd n walks straight past n==0.
  • Claiming O(1) space for a recursive solution. It is O(depth), always. Interviewers listen for this.
  • Forgetting to undo state after a recursive call. The pop_back in subsets is not optional — without it, every later branch inherits your choices.
  • Passing containers by value into recursion. Correct answer, silently exponential cost. Pass by reference (Chapter 1).
  • Using a global or static cache. Works once, then returns stale answers on the second call. Own the cache in the driver.
  • Recursing on a possibly-degenerate structure with n = 10⁶. A balanced tree is depth 20; a chain is depth 10⁶ and a hard crash.
  • Tracing instead of trusting. If you are three levels deep in a mental trace, stop and use the leap of faith instead.
  • Not returning the recursive call's value. dfs(x) instead of return dfs(x) compiles fine in a non-void function and returns garbage.

Interview drill

Warm-up: What is the space complexity of a recursive DFS on a binary tree, and what is the worst case?

How a strong answer sounds
O(h) auxiliary, where h is the height of the tree, because at the deepest point exactly h call frames are live simultaneously — each holding its parameters, locals and return address. For a balanced tree h is Θ(log n), so about 20 frames at a million nodes, which is nothing. But for a degenerate tree — every node having only a right child, which is what you get from inserting sorted data into a BST — h equals n, and at n around 10⁵ to 10⁶ that overflows a typical 1–8 MB stack and hard-crashes with no catchable exception. So I would state the bound as O(h), note that h is O(n) in the worst case, and if the constraints allowed a chain of 10⁶ nodes I would convert to an explicit stack, which keeps the O(h) space but puts it on the heap where there is room. Notably BFS has the mirror profile: its space is O(w) for the widest level, which is n/2 for a complete tree — so neither is universally cheaper, it depends on the shape.

Deeper: How do you look at a recursive solution and decide it needs memoisation?

How a strong answer sounds
I sketch the recursion tree for a small input and look for the same argument list appearing at two different places. If it does, the algorithm is recomputing identical subproblems, and caching collapses the tree into a DAG — which is exactly what dynamic programming is. For fib(5) I can see fib(2) computed three times and fib(1) five times, so the tree has about 2ⁿ nodes while there are only n distinct subproblems; memoising makes it O(n). For merge sort the subproblems are disjoint index ranges that never repeat, so there is nothing to cache and memoisation would just add overhead. The practical test is to compare the number of calls against the number of distinct argument tuples: if calls far exceed distinct states, memoise. That count of distinct states is also, conveniently, your DP state space and therefore your space complexity — so the same analysis gives me the recurrence, the cache dimensions and the final complexity in one pass.

🧠 Key takeaways

  • Each call holds a live stack frame, so recursion depth is space — typically 10⁴–10⁵ frames before a hard crash.
  • Guard with <= and ! rather than ==, so no recursive step can step over the base case.
  • Do not trace: assume the recursive call is correct and write only the one-step combination.
  • Complexity = nodes in the recursion tree × work per node; repeated arguments in that tree mean memoise.
  • Any recursion converts to a loop or an explicit stack; do it when the depth could overflow, not for style.

Check your understanding

What is the auxiliary space complexity of recursive DFS on a binary tree?

At the deepest point, h frames are simultaneously live. Balanced gives O(log n); a degenerate chain gives O(n) and, at 10⁵–10⁶ nodes, a stack overflow.

Why is if(n==0) a fragile base case for a function that recurses with n-2?

The recursion steps straight over the base case and runs until the stack overflows. if(n<=0) catches every value past the boundary, which is why this course always guards with an inequality.

In the recursion tree for a function, you see the argument 7 appear at four different places. What does that tell you?

Repeated arguments are exactly the DP signal. Caching by argument turns an exponential tree into a linear DAG. Merge sort's subproblems never repeat, so caching it buys nothing.

Why does the subsets function call current.pop_back() after the “include” branch?

Because current is a single shared object, any element you add persists into every subsequent branch unless you remove it. Choose, explore, unchoose — the backtracking skeleton (Chapter 35).

You must DFS a graph that may be a single path of 10⁶ nodes. What do you do?

10⁶ frames far exceeds a typical 1–8 MB stack. An explicit stack has the same O(n) space but on the heap, where there is room. (BFS also works here, but its queue can be O(n) too — it is not automatically safe, just differently shaped.) And C++ makes no guarantee about tail-call optimisation.
