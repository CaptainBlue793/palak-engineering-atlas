Interval DP

Interval DP answers questions about an unbroken range of items. You build the answer by picking a split point, or the last operation done inside the range. The state is dp[i][j], the range from i to j. The transition tries every k in between, so the cost is O(n³). The hard part is never the loop. It is deciding what k means, and getting the fill order right so shorter ranges are always ready first.

  • Solve burst balloons by thinking backwards — k as the last balloon
  • Handle the "merge stones / cut sticks" family using prefix sums
  • Know when Knuth optimisation drops O(n³) to O(n²)

The template and the fill order

Why a separate family? Some problems cannot be solved left to right, one element at a time, because the best choice in the middle of the row depends on what happens at both ends. Bracketing a product of matrices, cutting a stick, merging piles of stones, bursting balloons: in each, a range is finished by combining two smaller ranges, and the only question is where they meet. That shape shows up in compilers (the order to evaluate expressions), in databases (the order to join tables) and in a steady stream of "hard" interview questions.

A tiny picture of the dependencies. With n = 3, the answer dp[0][2] tries k = 0 (reading dp[0][0] and dp[1][2]) and k = 1 (reading dp[0][1] and dp[2][2]). Every cell it reads has length 1 or 2, shorter than its own length 3. So if all length-2 cells are filled before any length-3 cell, every read is ready. That is the whole ordering rule.

the shape every interval DP takesO(n³)O(n²)
// dp[i][j] = the answer for the interval [i..j].
// Every transition splits the interval at some k, so dp[i][j] reads intervals
// that are strictly SHORTER. That is the only ordering requirement.
vector<vector<int>> dp(n,vector<int>(n,0));

// ORDER A — loop over increasing length (most explicit)
for(int len=2;len<=n;len++){
	for(int i=0;i+len-1<n;i++){
		int j=i+len-1;
		dp[i][j]=INT_MAX;                  // minimising: start at "worse than anything"

		for(int k=i;k<j;k++){
			dp[i][j]=min(dp[i][j],dp[i][k]+dp[k+1][j]+/* merge cost */);
		}
	}
}

// ORDER B — i downward, j upward (equivalent, fewer index gymnastics)
for(int i=n-1;i>=0;i--){
	for(int j=i+1;j<n;j++){
		dp[i][j]=INT_MAX;
		for(int k=i;k<j;k++){
			dp[i][j]=min(dp[i][j],dp[i][k]+dp[k+1][j]+/* merge cost */);
		}
	}
}

return dp[0][n-1];
Both orders are correct, for the same reason. dp[i][k] and dp[k+1][j] sit inside [i..j], so they are shorter ranges. Order A fills every shorter length before any longer one. Order B makes sure all rows below (i' > i) are finished, and within a row, smaller j comes first. Only the top-right triangle of the table is ever used, because i ≤ j. The lower half stays empty, which is useful to know when you print the table while debugging. The classic wrong order is i upward with j upward. It reads dp[k+1][j] from a row that has not been started, quietly gets the starting value, and gives a confidently wrong answer.
✍️
My convention: name what k is, in a comment, before writing the loop

Every interval DP I have got wrong was wrong because k meant something slightly different from what the loop assumed. It was the first operation instead of the last, or a split between two elements instead of on one. So I write the meaning as a comment above the loop: // k = the LAST balloon burst in [i..j]. Once that sentence exists, the bounds (k=i or k=i+1, k<j or k<=j) and the two recursive terms follow from it, instead of by trial and error. The comment is the design. The code just copies it out.

Matrix chain multiplication

This is the classic interval DP. Given the sizes dims[0..n], matrix i is dims[i-1] × dims[i]. You may bracket the product any way you like and the result is the same, but the amount of work varies enormously. Here k marks the last multiplication you perform: everything left of the split has already been reduced to one matrix, everything right of it to another, and those two are multiplied last.

How much can the bracketing matter? Take three matrices with dims = [10, 30, 5, 60]: A is 10×30, B is 30×5, C is 5×60. Multiplying a p×q matrix by a q×r one takes p·q·r scalar multiplications.

  • (AB)C: AB costs 10·30·5 = 1,500 and gives a 10×5 matrix; times C costs 10·5·60 = 3,000. Total 4,500.
  • A(BC): BC costs 30·5·60 = 9,000 and gives a 30×60 matrix; A times that costs 10·30·60 = 18,000. Total 27,000.

Same answer, six times the work. The DP finds the good bracketing without listing them all. In table form: dp[1][2] = 1,500 and dp[2][3] = 9,000. Then dp[1][3] tries k = 1 (0 + 9,000 + 10·30·60 = 27,000) and k = 2 (1,500 + 0 + 10·5·60 = 4,500), and keeps 4,500. With n matrices there are exponentially many bracketings (the Catalan numbers), but only about n²/2 ranges, which is why the DP is fast.

matrix chain multiplicationO(n³)O(n²)
// dims has n+1 entries; matrix i (1-indexed) is dims[i-1] x dims[i].
// dp[i][j] = the minimum scalar multiplications to collapse matrices i..j
//            into a single matrix.
// k = the index of the LAST matrix in the left group, so the final
//     multiplication is (i..k) x (k+1..j).
int matrixChainOrder(vector<int> &dims){
	int N=dims.size()-1;                // number of matrices
	vector<vector<int>> dp(N+1,vector<int>(N+1,0));

	// a single matrix needs no multiplication -> dp[i][i]=0, already set

	for(int len=2;len<=N;len++){
		for(int i=1;i+len-1<=N;i++){
			int j=i+len-1;

			dp[i][j]=INT_MAX;

			for(int k=i;k<j;k++){
				// left is dims[i-1] x dims[k], right is dims[k] x dims[j]
				int cost=dp[i][k]+dp[k+1][j]
				        +dims[i-1]*dims[k]*dims[j];

				dp[i][j]=min(dp[i][j],cost);
			}
		}
	}

	return dp[1][N];
}
The merge cost dims[i-1]*dims[k]*dims[j] is the whole problem. After reducing each side, the left group is a dims[i-1] × dims[k] matrix and the right is dims[k] × dims[j]. Multiplying a p×q matrix by a q×r one costs p·q·r, so this last step costs the three sizes multiplied together. Numbering the matrices from 1 is worth the small awkwardness here, because dims[i-1] then reads straight off as "the number of rows of matrix i". Since the cost multiplies three sizes, use long long once the sizes pass a few hundred. To get the actual bracketing, store the winning k in a second table and recurse on it — the same walk-back idea as Chapter 41.

Burst balloons: think about the last operation

This problem is why interval DP deserves its own chapter. Balloons sit in a row. Bursting balloon i earns nums[i-1] * nums[i] * nums[i+1], using its neighbours at that moment. Then the row closes up, so the neighbours change. Get the highest total.

A two-balloon example shows the order matters. nums = [3, 5], and a missing neighbour counts as 1. Burst 3 first: 1·3·5 = 15, then 5 has neighbours 1 and 1: 1·5·1 = 5. Total 20. Burst 5 first: 3·5·1 = 15, then 3 alone: 1·3·1 = 3. Total 18. So the answer is 20, and the choice of order is the whole problem.

🎈
Why "k = the first balloon burst" fails

The natural instinct is to let k be the first balloon burst in [i..j], then recurse on the two halves. It does not work, and the reason is worth understanding. Once k pops first, the two halves become neighbours. A later burst in the left half can then use a balloon from the right half. The two halves are no longer separate problems, so the recurrence is invalid. That separateness is exactly what DP relies on.

Turn it around: let k be the last balloon burst in the range. Then everything in [i..k-1] was burst while k was still standing, and the same for [k+1..j]. Neither half ever sees past k, so the halves really are separate. And k's own score uses the original outside neighbours i-1 and j+1, because by the time k pops, everything strictly inside the range is already gone.

burst balloonsO(n³)O(n²)
// Pad with 1s at both ends so the boundary needs no special case.
// dp[i][j] = the best score obtainable by bursting every balloon STRICTLY
//            inside the open interval (i,j) — i and j themselves survive.
// k = the LAST balloon burst inside (i,j). When it pops, its neighbours are
//     exactly i and j, because everything between them is already gone.
int maxCoins(vector<int> &nums){
	int n=nums.size();
	vector<int> a;

	a.push_back(1);

	for(auto &x:nums)
	a.push_back(x);

	a.push_back(1);

	int N=a.size();
	vector<vector<int>> dp(N,vector<int>(N,0));

	// len is the distance between the two surviving ends
	for(int len=2;len<N;len++){
		for(int i=0;i+len<N;i++){
			int j=i+len;

			for(int k=i+1;k<j;k++){
				int cost=dp[i][k]+dp[k][j]+a[i]*a[k]*a[j];

				dp[i][j]=max(dp[i][j],cost);
			}
		}
	}

	return dp[0][N-1];
}
Note dp[i][k]+dp[k][j], not dp[i][k-1]+dp[k+1][j]. The range here is open: i and j themselves survive. So k is the shared end of both halves, rather than being left out of both. That one indexing difference from matrix chain is where most attempts break, and it follows straight from the words "strictly inside". Padding the array with 1s at both ends keeps a[i]*a[k]*a[j] valid at the edges, which is why there are no special cases for boundaries at all. The same "think about the last operation" flip solves minimum cost to merge stones, remove boxes and strange printer.

Check it on [3, 5], padded to a = [1, 3, 5, 1]. The short ranges first: dp[0][2] has only balloon 1 inside, so it is 1·3·5 = 15; dp[1][3] has only balloon 2 inside, so it is 3·5·1 = 15. Then dp[0][3] tries k = 1 as the last burst: dp[0][1] + dp[1][3] + 1·3·1 = 0 + 15 + 3 = 18. And k = 2 last: dp[0][2] + dp[2][3] + 1·5·1 = 15 + 0 + 5 = 20. The maximum is 20, matching the hand count: 5 is the last balloon, so 3 went first.

Cut sticks and merge stones: the cost is the whole interval

Here is a second common shape. This time the merge cost does not depend on k at all. It is the sum or length of the whole range, which a prefix sum (running totals computed once up front) gives you in O(1). The split point only decides how the inside is arranged.

Notice that cut sticks uses the first cut as k, while burst balloons needed the last. That is not a contradiction. Once a stick is cut, the two pieces are physically separate — nothing done to one piece changes the other — so splitting on the first action keeps the halves independent. Always ask: "after I fix k, can the two sides still affect each other?" If not, k is a valid split.

minimum cost to cut a stickO(m³)O(m²)
// A stick of length L, and a list of positions where it must be cut. Cutting a
// piece costs that piece's current LENGTH; the order of cuts is ours to choose.
// Trick: sort the cuts and pad with 0 and L, then think in terms of the
// interval of cut positions rather than the stick itself.
// dp[i][j] = the minimum cost to make every cut strictly between cuts[i]
//            and cuts[j].
// k = the FIRST cut made in that range — it costs the whole piece cuts[j]-cuts[i].
int minCost(int L,vector<int> &cuts){
	cuts.push_back(0);
	cuts.push_back(L);
	sort(cuts.begin(),cuts.end());

	int m=cuts.size();
	vector<vector<int>> dp(m,vector<int>(m,0));

	for(int len=2;len<m;len++){
		for(int i=0;i+len<m;i++){
			int j=i+len;

			dp[i][j]=INT_MAX;

			for(int k=i+1;k<j;k++){
				// the cut at k splits the piece; its price is the piece length,
				// which is the same whichever k we pick
				int cost=cuts[j]-cuts[i]+dp[i][k]+dp[k][j];

				dp[i][j]=min(dp[i][j],cost);
			}
		}
	}

	return dp[0][m-1];
}
Sorting the cut positions is what makes this an interval problem. Unsorted, the smaller problems are not unbroken ranges, and the DP does not apply. Two related problems are worth knowing. Minimum cost to merge stones into one pile is the same, with prefix[j+1]-prefix[i] as the merge cost. (For the k-way version, add the condition that the range length leaves a remainder of 1 when divided by k−1.) Optimal binary search tree adds the total frequency of the subtree at each level. Whenever the merge cost is "the whole range", reach for a prefix sum first, so the innermost loop stays O(1).

Dry run: a stick of length 10 with cuts at 2 and 5. By hand, cutting at 2 first costs 10, then cutting the 8-long piece at 5 costs 8, total 18. Cutting at 5 first costs 10, then the 5-long piece at 2 costs 5, total 15. In the DP, the padded cuts are [0, 2, 5, 10]. dp[0][2] (the piece 0..5 with a cut at 2) = 5. dp[1][3] (the piece 2..10 with a cut at 5) = 8. dp[0][3] tries k = 1: 10 + 0 + 8 = 18, and k = 2: 10 + 5 + 0 = 15. It keeps 15. Note the edge case: a range with nothing strictly inside (j = i + 1) costs 0, which the zero-filled table already gives.

⚡
Knuth optimisation: O(n³) → O(n²)

Some interval DPs of the form dp[i][j] = min over k of (dp[i][k] + dp[k+1][j]) + cost(i,j) have a helpful property: the best split point only ever moves to the right as the range grows. If opt[i][j] is the best split point for [i..j], then

// opt is monotone in both arguments:
opt[i][j-1] <= opt[i][j] <= opt[i+1][j]

// so the inner loop only scans that shrinking window:
for(int k=opt[i][j-1];k<=opt[i+1][j];k++){ /* ... */ }

So you only need to search k between those two bounds. Those small search windows add up to far less work, and the total drops to O(n²). It applies when cost obeys the quadrangle inequality — for a ≤ b ≤ c ≤ d, cost(a,c) + cost(b,d) ≤ cost(a,d) + cost(b,c), meaning two overlapping ranges together never cost more than the outer range plus the inner one — and grows with the range — true for optimal binary search tree and merge-stones-style costs, and not true for burst balloons. Two honest warnings. Checking that the condition holds is harder than writing the code. And at normal interview sizes (n ≤ 500, so 1.25·10⁸ operations) plain O(n³) usually passes. Name it to show you know the faster bound exists, then write the simple version unless the limits force otherwise. The related divide-and-conquer optimisation does the same job for layered DPs of the form dp[layer][i], cutting O(k·n²) to O(k·n log n).

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 NAME k FIRST
Write a comment saying exactly what k is — the last operation, the first cut, the root — before the loop. The bounds and the two recursive terms then follow mechanically.
💡 THINK LAST
When splitting on the first operation makes the halves interact, split on the last one instead. That inversion solves burst balloons, merge stones and remove boxes.
⛔ LENGTH OUTER
Both indices increasing reads a row that has not been filled and fails silently. Iterate by increasing length, or i downward with j upward.
⚠️
Common mistakes
  • Looping i upward and j upward. dp[k+1][j] comes from a row not yet filled. Wrong answer, no crash.
  • Letting k be the first operation in burst balloons. The halves become neighbours, so they are not separate problems.
  • Using dp[i][k-1]+dp[k+1][j] for an open range (or dp[i][k]+dp[k][j] for a closed one). Match the indexing to what a cell means.
  • Forgetting to pad burst balloons with 1s, then handling the ends with special cases that are wrong.
  • Not sorting the cut positions in cut sticks, so the smaller problems are not unbroken ranges.
  • Leaving dp[i][j] at 0 when minimising instead of INT_MAX before the k loop.
  • Off-by-one in the k bounds. k<j for closed ranges, k=i+1; k<j for open ones.
  • Overflow in matrix chain — three sizes multiplied together; use long long.
  • Recomputing the range sum inside the k loop, which turns O(n³) into O(n⁴). Use a prefix sum.
  • Reaching for Knuth optimisation without checking the quadrangle inequality. It gives wrong answers when the condition fails.
  • Trying interval DP at n = 10⁵. O(n³) needs n in the hundreds. A bigger n means a different technique.

Interview drill

Warm-up: Matrix chain multiplication. Derive the recurrence and justify the loop order.

How a strong answer sounds
You can bracket a chain of matrix multiplications any way you like and the product is the same, but the work is not: multiplying a p×q matrix by a q×r one costs p·q·r scalar multiplications. I define dp[i][j] as the fewest scalar multiplications needed to reduce matrices i through j to a single matrix, with dp[i][i] = 0, since one matrix needs no work. The transition asks one question: what is the last multiplication? A split at k means the left group i..k has already been reduced to a dims[i−1] × dims[k] matrix, and the right group k+1..j to a dims[k] × dims[j] matrix. Those two are multiplied last, at a cost of dims[i−1]·dims[k]·dims[j]. So dp[i][j] is the minimum over k from i to j−1 of dp[i][k] + dp[k+1][j] + that product. Now the order. dp[i][j] reads dp[i][k] and dp[k+1][j], and both are strictly shorter ranges. So I fill by increasing length — or, just as good, loop i downward and j upward, which respects the same dependency. What does not work is the reflex double loop with both indices increasing: dp[k+1][j] would come from a row that has not been started. That gives the starting values and a confidently wrong answer, with no crash, which is why I would say the ordering argument out loud. Three nested loops over the upper triangle give O(n³) time and O(n²) space. Two practical notes. The cost multiplies three sizes, so use long long once the sizes pass a few hundred. And to print the actual bracketing, I would store the winning k in a second table and recurse on it.

Deeper: Burst balloons. Explain why the obvious recurrence is wrong.

How a strong answer sounds
The instinct is to let k be the first balloon burst in the range and recurse on the two halves. It is worth saying clearly why that fails. Once k is burst, the left and right halves become neighbours, so a later burst in the left half can use a balloon from the right half. The two halves are no longer separate problems, and that separateness is exactly what a DP recurrence needs. No amount of index fiddling saves it. The fix is to turn the question around and let k be the last balloon burst in the range. Then everything in the left part was burst while k was still standing, and the same for the right part, so neither half ever sees past k. They really are separate. And k's own score is easy: when it finally pops, everything strictly inside the range is gone, so its neighbours are exactly the two surviving ends. Concretely, I pad the array with 1s at both ends, and define dp[i][j] as the best score from bursting everything strictly inside the open range (i, j), with i and j left standing. Then dp[i][j] = max over k strictly between i and j of dp[i][k] + dp[k][j] + a[i]·a[k]·a[j]. Note that the halves share k as an endpoint — dp[i][k] and dp[k][j], not dp[i][k−1] and dp[k+1][j]. That follows from the range being open, and it is where most implementations go wrong. Filling by increasing range width, the answer is dp[0][N−1]. O(n³) time, O(n²) space. The idea you can carry elsewhere is that flip from "first operation" to "last operation". It is the same move that solves merge stones, remove boxes and strange printer.

🧠 Key takeaways

  • Interval DP is dp[i][j] plus a loop over a split point k — O(n²) states, O(n³) work.
  • Fill by increasing length, or with i downward and j upward. Both indices increasing is the classic silent bug.
  • Write down what k means before writing the loop. The bounds and the two terms then follow from it.
  • If splitting on the first operation makes the halves affect each other, split on the last one instead.
  • Compute range sums up front. Know that Knuth optimisation exists (O(n²)), but do not reach for it by default.
