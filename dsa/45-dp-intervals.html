Interval DP

Interval DP answers questions about a contiguous range whose answer is built by choosing a split point or a last operation inside it. The state is dp[i][j], the transition loops over every k between them, and the cost is the familiar O(n³). The genuine difficulty is never the loop — it is choosing what k means, and getting the fill order right so that shorter intervals are always ready.

  • Solve burst balloons by thinking backwards — k as the last balloon
  • Handle the "merge stones / cut sticks" family with prefix sums
  • Recognise when Knuth optimisation drops O(n³) to O(n²)

The template and the fill order

the shape every interval DP takesO(n³)O(n²)
// dp[i][j] = the answer for the interval [i..j].
// Every transition splits the interval at some k, so dp[i][j] reads intervals
// that are strictly SHORTER. That is the only ordering requirement.
vector<vector<int>> dp(n,vector<int>(n,0));

// ORDER A — loop over increasing length (most explicit)
for(int len=2;len<=n;len++){
	for(int i=0;i+len-1<n;i++){
		int j=i+len-1;

		for(int k=i;k<j;k++){
			dp[i][j]=min(dp[i][j],dp[i][k]+dp[k+1][j]+/* merge cost */);
		}
	}
}

// ORDER B — i downward, j upward (equivalent, fewer index gymnastics)
for(int i=n-1;i>=0;i--){
	for(int j=i+1;j<n;j++){
		for(int k=i;k<j;k++){
			dp[i][j]=min(dp[i][j],dp[i][k]+dp[k+1][j]+/* merge cost */);
		}
	}
}

return dp[0][n-1];
Both orders are correct, for the same reason. dp[i][k] and dp[k+1][j] are sub-intervals of [i..j], so they are shorter: Order A fills all shorter lengths before any longer one; Order B guarantees i' > i rows are complete and, within a row, smaller j comes first. Only the top-right triangle is ever used, since i ≤ j — the lower half stays untouched, which is a handy thing to know when you print the table to debug. The classic wrong order is i upward with j upward: it reads dp[k+1][j] from a row not yet started, silently gets the initial value, and produces confidently wrong answers.
✍️
My convention: name what k is, in a comment, before writing the loop

Every interval DP I have ever got wrong was wrong because k meant something slightly different from what the loop assumed — the first operation instead of the last, or a split between elements instead of on one. So I write the meaning as a comment above the loop: // k = the LAST balloon burst in [i..j]. Once that sentence exists, the bounds (k=i or k=i+1, k<j or k<=j) and the two recursive terms follow mechanically instead of by trial and error. That comment is the design; the code is transcription.

Matrix chain multiplication

The canonical interval DP. Given dimensions dims[0..n], matrix i is dims[i-1] × dims[i]. Multiplication is associative, so the result never changes — but the cost does, wildly. Here k is the last multiplication performed: everything left of the split has been collapsed into one matrix, everything right of it into another, and those two are multiplied last.

matrix chain multiplicationO(n³)O(n²)
// dims has n+1 entries; matrix i (1-indexed) is dims[i-1] x dims[i].
// dp[i][j] = the minimum scalar multiplications to collapse matrices i..j
//            into a single matrix.
// k = the index of the LAST matrix in the left group, so the final
//     multiplication is (i..k) x (k+1..j).
int matrixChainOrder(vector<int> &dims){
	int N=dims.size()-1;                // number of matrices
	vector<vector<int>> dp(N+1,vector<int>(N+1,0));

	// a single matrix needs no multiplication -> dp[i][i]=0, already set

	for(int len=2;len<=N;len++){
		for(int i=1;i+len-1<=N;i++){
			int j=i+len-1;

			dp[i][j]=INT_MAX;

			for(int k=i;k<j;k++){
				// left is dims[i-1] x dims[k], right is dims[k] x dims[j]
				int cost=dp[i][k]+dp[k+1][j]
				        +dims[i-1]*dims[k]*dims[j];

				dp[i][j]=min(dp[i][j],cost);
			}
		}
	}

	return dp[1][N];
}
The merge cost dims[i-1]*dims[k]*dims[j] is the whole problem. After collapsing, the left group is a dims[i-1] × dims[k] matrix and the right is dims[k] × dims[j], and multiplying those costs the product of the three dimensions. 1-indexing the matrices is worth the small awkwardness here, because dims[i-1] then reads directly as "the rows of matrix i". Costs multiply three dimensions together, so use long long once the dimensions exceed a few hundred. To recover the actual parenthesisation, store the winning k in a second table and recurse on it — the same trace-back idea as Chapter 41.

Burst balloons: think about the last operation

This problem is the reason interval DP deserves a chapter of its own. Balloons in a row; bursting balloon i earns nums[i-1] * nums[i] * nums[i+1] using its current neighbours, and then the row closes up. Maximise the total.

🎈
Why "k = the first balloon burst" fails

The natural instinct is to let k be the first balloon burst in [i..j] and recurse on the two halves. It does not work, and the reason is instructive: after bursting k first, the two halves become adjacent to each other, so a later burst in the left half can use a neighbour from the right half. The sub-problems are no longer independent, and the recurrence is invalid — the defining property of DP has been violated. Flip it: let k be the last balloon burst in the interval. Then everything in [i..k-1] was burst while k still stood, and likewise for [k+1..j], so neither half ever sees across the boundary. The halves are genuinely independent, and k's own score uses the original outside neighbours i-1 and j+1, because by the time k pops, everything strictly inside the interval is gone.

burst balloonsO(n³)O(n²)
// Pad with 1s at both ends so the boundary needs no special case.
// dp[i][j] = the best score obtainable by bursting every balloon STRICTLY
//            inside the open interval (i,j) — i and j themselves survive.
// k = the LAST balloon burst inside (i,j). When it pops, its neighbours are
//     exactly i and j, because everything between them is already gone.
int maxCoins(vector<int> &nums){
	int n=nums.size();
	vector<int> a;

	a.push_back(1);

	for(auto &x:nums)
	a.push_back(x);

	a.push_back(1);

	int N=a.size();
	vector<vector<int>> dp(N,vector<int>(N,0));

	// len is the distance between the two surviving ends
	for(int len=2;len<N;len++){
		for(int i=0;i+len<N;i++){
			int j=i+len;

			for(int k=i+1;k<j;k++){
				int cost=dp[i][k]+dp[k][j]+a[i]*a[k]*a[j];

				dp[i][j]=max(dp[i][j],cost);
			}
		}
	}

	return dp[0][N-1];
}
Note dp[i][k]+dp[k][j], not dp[i][k-1]+dp[k+1][j]. Because the interval is open — i and j survive — k is shared as an endpoint by both halves rather than excluded from both. That single indexing difference from matrix chain is where most attempts break, and it follows directly from the state sentence "strictly inside". The padding with 1s makes a[i]*a[k]*a[j]` valid even at the ends, which is why there are no boundary branches at all. The same "last operation" flip solves minimum cost to merge stones, remove boxes, and strange printer.

Cut sticks and merge stones: the cost is the whole interval

A second common shape. Here the merge cost does not depend on k at all — it is the sum or length of the entire interval, which a prefix sum gives in O(1). The split point only decides how the interior is arranged.

minimum cost to cut a stickO(m³)O(m²)
// A stick of length L, and a list of positions where it must be cut. Cutting a
// piece costs that piece's current LENGTH; the order of cuts is ours to choose.
// Trick: sort the cuts and pad with 0 and L, then think in terms of the
// interval of cut positions rather than the stick itself.
// dp[i][j] = the minimum cost to make every cut strictly between cuts[i]
//            and cuts[j].
// k = the FIRST cut made in that range — it costs the whole piece cuts[j]-cuts[i].
int minCost(int L,vector<int> &cuts){
	cuts.push_back(0);
	cuts.push_back(L);
	sort(cuts.begin(),cuts.end());

	int m=cuts.size();
	vector<vector<int>> dp(m,vector<int>(m,0));

	for(int len=2;len<m;len++){
		for(int i=0;i+len<m;i++){
			int j=i+len;

			dp[i][j]=INT_MAX;

			for(int k=i+1;k<j;k++){
				// the cut at k splits the piece; its price is the piece length,
				// which is the same whichever k we pick
				int cost=cuts[j]-cuts[i]+dp[i][k]+dp[k][j];

				dp[i][j]=min(dp[i][j],cost);
			}
		}
	}

	return dp[0][m-1];
}
Sorting the cut positions is what makes this an interval problem — unsorted, the sub-problems are not contiguous and the DP does not apply. Two relatives worth knowing: minimum cost to merge stones into one pile is the same with prefix[j+1]-prefix[i] as the merge cost (and, for the k-way version, an extra condition that the interval length be congruent to 1 modulo k−1); optimal binary search tree adds the subtree's total frequency at each level. Whenever the merge cost is "the whole interval", reach for a prefix sum first, so the innermost loop stays O(1).
⚡
Knuth optimisation: O(n³) → O(n²)

Some interval DPs of the form dp[i][j] = min over k of (dp[i][k] + dp[k+1][j]) + cost(i,j) satisfy a monotonicity property: if opt[i][j] is the best split point, then

// opt is monotone in both arguments:
opt[i][j-1] <= opt[i][j] <= opt[i+1][j]

// so the inner loop only scans that shrinking window:
for(int k=opt[i][j-1];k<=opt[i+1][j];k++){ /* ... */ }

The windows telescope, and the total work collapses to O(n²). It applies when cost satisfies the quadrangle inequality and is monotone on intervals — true for optimal binary search tree and for merge-stones-style costs, and not true for burst balloons. Two honest caveats: verifying the precondition is harder than writing the code, and at typical interview sizes (n ≤ 500, so 1.25·10⁸ operations) plain O(n³) usually passes. Name it to show you know the ceiling exists, then implement the straightforward version unless the constraints force otherwise. The related divide-and-conquer optimisation does the same job for layered DPs of the form dp[layer][i], reducing O(k·n²) to O(k·n log n).

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 NAME k FIRST
Write a comment saying exactly what k is — the last operation, the first cut, the root — before the loop. The bounds and the two recursive terms then follow mechanically.
💡 THINK LAST
When splitting on the first operation makes the halves interact, split on the last one instead. That inversion solves burst balloons, merge stones and remove boxes.
⛔ LENGTH OUTER
Both indices increasing reads a row that has not been filled and fails silently. Iterate by increasing length, or i downward with j upward.
⚠️
Common mistakes
  • Looping i upward and j upward. dp[k+1][j] comes from a row not yet filled — silently wrong, never a crash.
  • Letting k be the first operation in burst balloons. The halves become adjacent, so they are not independent.
  • Using dp[i][k-1]+dp[k+1][j] for an open interval (or dp[i][k]+dp[k][j] for a closed one). Match the indexing to the state sentence.
  • Forgetting to pad burst balloons with 1s, then special-casing the ends incorrectly.
  • Not sorting the cut positions in cut sticks, so the sub-problems are not contiguous.
  • Leaving dp[i][j] at 0 for a minimisation instead of INT_MAX before the k loop.
  • Off-by-one in the k bounds. k<j for closed intervals, k=i+1; k<j for open ones.
  • Overflow in matrix chain — three dimensions multiplied; use long long.
  • Recomputing the interval sum inside the k loop, turning O(n³) into O(n⁴). Use a prefix sum.
  • Reaching for Knuth optimisation without checking the quadrangle inequality. It gives wrong answers when the precondition fails.
  • Trying interval DP at n = 10⁵. O(n³) needs n in the hundreds; a bigger n means a different technique.

Interview drill

Warm-up: Matrix chain multiplication. Derive the recurrence and justify the loop order.

How a strong answer sounds
Matrix multiplication is associative, so the product is fixed, but the cost of computing it depends on the parenthesisation — multiplying a p×q by a q×r matrix costs p·q·r scalar multiplications. I define dp[i][j] as the minimum scalar multiplications needed to collapse matrices i through j into one matrix, with dp[i][i] = 0 since a single matrix needs no work. The transition asks: what is the last multiplication? Some split k means the left group i..k has already been collapsed to a dims[i−1] × dims[k] matrix and the right group k+1..j to a dims[k] × dims[j] matrix, and those two are multiplied last at a cost of dims[i−1]·dims[k]·dims[j]. So dp[i][j] is the minimum over k from i to j−1 of dp[i][k] + dp[k+1][j] + that product. As for order: dp[i][j] reads dp[i][k] and dp[k+1][j], both of which are strictly shorter intervals, so I must fill by increasing length — or equivalently iterate i downward and j upward, which satisfies the same dependency. What does not work is the reflex double loop with both indices increasing, because dp[k+1][j] would come from a row that has not been started; that produces the initial values and a confidently wrong answer rather than a crash, which is why I would state the ordering argument explicitly. Three nested loops over the upper triangle gives O(n³) time and O(n²) space. Two practical notes: the costs multiply three dimensions, so long long once dimensions pass a few hundred; and to output the actual parenthesisation I would store the winning k in a parallel table and recurse on it.

Deeper: Burst balloons. Explain why the obvious recurrence is wrong.

How a strong answer sounds
The instinct is to let k be the first balloon burst in the range and recurse on the two halves, and it is worth saying clearly why that fails: once k is burst, the left and right halves become adjacent to each other, so a later burst in the left half can use a neighbour that lives in the right half. The sub-problems are not independent, which is precisely the property a DP recurrence needs, so no amount of index fiddling rescues it. The fix is to invert the question and let k be the last balloon burst in the range. Then, by definition, everything in the left part was burst while k was still standing, and the same for the right part, so neither half ever sees across the boundary — they really are independent. And k's own score is easy: when it finally pops, everything strictly inside the range is already gone, so its neighbours are exactly the two surviving endpoints. Concretely, I pad the array with 1s at both ends and define dp[i][j] as the best score from bursting everything strictly inside the open interval (i, j), with i and j surviving. Then dp[i][j] = max over k strictly between i and j of dp[i][k] + dp[k][j] + a[i]·a[k]·a[j]. Note the halves share k as an endpoint — dp[i][k] and dp[k][j], not dp[i][k−1] and dp[k+1][j] — which follows directly from the interval being open, and is where most implementations go wrong. Filling by increasing interval width, the answer is dp[0][N−1]. O(n³) time, O(n²) space. That inversion from "first operation" to "last operation" is the transferable idea; it is the same move that solves merge stones, remove boxes and strange printer.

🧠 Key takeaways

  • Interval DP is dp[i][j] plus a loop over a split point k — O(n³) for O(n²) states.
  • Fill by increasing length, or i downward and j upward; both indices increasing is the classic silent bug.
  • Write down what k means before the loop; the bounds and the two terms then follow mechanically.
  • When splitting on the first operation makes the halves interact, split on the last one instead.
  • Precompute interval sums, and know Knuth optimisation exists (O(n²)) without reaching for it by default.
