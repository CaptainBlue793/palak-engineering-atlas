Strings & Character Counting

A string is an array of characters, so everything from Chapters 3 to 9 applies unchanged — and the small vocabulary of string-specific moves is worth knowing cold, because string problems are where interviewers hide off-by-ones. This chapter covers the 26-bucket count, the concatenation trap that turns an O(n) loop into O(n²), parsing, and the palindrome family.

  • Use the 26-bucket count array instead of a hash map, and know when it is not enough
  • Avoid the string-building patterns that are secretly quadratic
  • Solve anagrams, palindromes and character-window problems from the same few shapes
  • Parse with stringstream, substr and find without index errors
  • Say what a “character” is when the input is not ASCII

A string is an array — with two differences

In C++, std::string is essentially a vector<char>: contiguous, O(1) indexed, growable, with size() stored. So two pointers, sliding windows and prefix sums all work identically. Two things differ and both matter.

Characters are small integers

'c' - 'a' is 2. That turns any lowercase letter into an index in [0,26), which means the ideal container for a letter frequency is a 26-slot array, not a hash map (Chapter 9's rule, in its most common instance).

Concatenation is a trap

Building a string with s = s + c in a loop copies the whole string each time — O(n²) total. s += c is amortized O(1) and is what you always want. Same distinction as push_back versus reallocating.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 EXPAND CENTRES
For palindromic substrings, loop over 2n−1 centres and expand. O(n²) time, O(1) space, four lines — and it beats the DP table unless you need every answer.
💡 FIXED WINDOW
Anagram search is a fixed-size window plus a 26-count array. Compare counts in O(26) — constant — rather than re-sorting each window.
⛔ IN-PLACE STRINGS
Reverse-words-in-place is reverse-whole then reverse-each-word, and the hard part is collapsing runs of spaces with a write pointer. Test a string with leading, trailing and doubled spaces.

The quadratic string builders
O(n²) — copies every iteration
string ans="";
for(char c:s)
ans=ans+c;              // new string each time

// and this, which is worse:
for(int i=0;i<n;i++)
ans=ans.substr(1)+ans[0];   // O(n) per step
O(n) — appends in place
string ans;
ans.reserve(s.size());     // one allocation
for(char c:s)
ans+=c;                 // amortized O(1)

// rotation without building anything:
rotate(s.begin(),s.begin()+k,s.end());

Also watch for substr inside a loop — every call allocates and copies. When you only need to look at a slice, use indices, or a string_view, which is a pointer and a length with no allocation at all.

The 26-bucket count

isAnagram — one pass up, one pass downO(n)O(1)
// Increment for s, decrement for t. Anagram iff every bucket lands on zero.
// O(1) space because the array is 26 slots regardless of input length.
bool isAnagram(string &s,string &t){
	if(s.size()!=t.size())return false;

	vector<int> count(26,0);

	for(int i=0;i<s.size();i++){
		count[s[i]-'a']++;
		count[t[i]-'a']--;
	}

	for(int c:count){
		if(c!=0)return false;
	}

	return true;
}
The length check first is not decoration. Without it, "a" and "ab" would index t[1] out of bounds. Guard clause on line one, as always.
✍️
My convention: vector<int> count(26,0), and say the alphabet out loud

Write the 26 and then state the assumption: “assuming lowercase ASCII only”. Interviewers frequently follow up with “what if it is Unicode?”, and the honest answer — a hash map keyed on the code point, and a real discussion of what a “character” means — is a much stronger signal than a 26 you cannot defend. For mixed case or full ASCII use 128; for bytes use 256.

Palindromes

Three shapes, in increasing order of cleverness. Know all three because the follow-up questions walk up the ladder.

// Converging two pointers (Chapter 4), skipping non-alphanumerics.
bool isPalindrome(string &s){
	int left=0;
	int right=s.size()-1;

	while(left<right){
		// the two guards need left<right, or they run off the end
		while(left<right and !isalnum(s[left]))left++;
		while(left<right and !isalnum(s[right]))right--;

		if(tolower(s[left])!=tolower(s[right]))return false;

		left++;
		right--;
	}

	return true;
}

The left<right inside the skip loops is essential. On a string of only punctuation, omitting it walks left past the end. This is the classic failure case for this problem.

// On the first mismatch, try skipping ONE character from either side.
// Greedy is correct: the mismatch must be resolved here or never.
bool check(string &s,int left,int right){
	while(left<right){
		if(s[left]!=s[right])return false;

		left++;
		right--;
	}

	return true;
}
bool validPalindrome(string &s){
	int left=0;
	int right=s.size()-1;

	while(left<right){
		if(s[left]!=s[right]){
			// skip the left one OR the right one
			return check(s,left+1,right) or check(s,left,right-1);
		}

		left++;
		right--;
	}

	return true;
}

Still O(n): the outer loop runs once, and the two check calls together are at most O(n). Helper plus driver, as always.

// Expand around every centre. 2n-1 centres: n single, n-1 between pairs.
int expand(string &s,int left,int right){
	while(left>=0 and right<s.size() and s[left]==s[right]){
		left--;
		right++;
	}

	return right-left-1;       // both overshot by one
}
string longestPalindrome(string &s){
	if(s.empty())return "";

	int bestLen=0;
	int bestStart=0;

	for(int i=0;i<s.size();i++){
		int odd=expand(s,i,i);        // centre on a character
		int even=expand(s,i,i+1);    // centre between two
		int len=max(odd,even);

		if(len>bestLen){
			bestLen=len;
			bestStart=i-(len-1)/2;   // derive the start from the centre
		}
	}

	return s.substr(bestStart,bestLen);
}

O(n²) time, O(1) space. Both centre types are required — with only odd centres you miss "abba". Manacher does this in O(n) (Chapter 50), and the DP version is in Chapter 41.

Parsing without index errors

the parsing toolkitprefer stringstream to manual indexing
// Split on whitespace — by far the cleanest way.
vector<string> splitWords(string &s){
	stringstream ss(s);
	vector<string> ans;
	string word;

	while(ss>>word)          // skips runs of whitespace automatically
	ans.push_back(word);

	return ans;
}

// Split on an arbitrary delimiter.
vector<string> splitOn(string &s,char delim){
	stringstream ss(s);
	vector<string> ans;
	string part;

	while(getline(ss,part,delim))   // keeps empty fields, unlike >>
	ans.push_back(part);

	return ans;
}

// Manual scan, when you need index control (e.g. reverse words in place).
int i=0;
while(i<s.size()){
	while(i<s.size() and s[i]==' ')i++;     // skip separators

	int start=i;
	while(i<s.size() and s[i]!=' ')i++;     // consume the token

	if(i>start){
		// token is s[start..i-1], length i-start
	}
}
Note the difference: ss >> word collapses runs of whitespace and drops empty fields; getline(ss, part, ',') keeps them, so "a,,b" yields three fields including one empty. CSV parsing needs getline; word splitting wants >>. Also: s.find(x) returns string::npos when absent — compare against that, never against -1.
🌍
“Character” is not a well-defined unit outside ASCII

A char is one byte. In UTF-8, é is two bytes, → is three, an emoji is four, and a flag emoji is eight. So s.size() is a byte count, reversing a string byte by byte corrupts multi-byte characters, and s[i] may be half a letter. Worse, some visible characters are several code points combined (an e plus a combining accent), so even counting code points does not match what a user would call a character. Interview answer: for ASCII problems use a 26- or 128-slot array and say that assumption; for real text, you decode to code points first, and the correct unit depends on the question — bytes for storage, code points for most algorithms, grapheme clusters for anything a user sees.

⚠️
Common mistakes
  • s = s + c in a loop. Quadratic. Use s += c, and reserve if you know the length.
  • substr inside a loop. Each call allocates and copies. Use indices, or string_view.
  • Comparing s.find(x) against -1. It returns unsigned string::npos; compare against that.
  • i < s.size() - 1 on an empty string. size() is unsigned, so 0-1 wraps huge. Write i + 1 < s.size().
  • Missing left<right in a skip loop. A string of only punctuation walks the pointer off the end.
  • Only checking odd centres in expand-around-centre. You miss every even-length palindrome.
  • Assuming one char is one character. True for ASCII, false for UTF-8. State the assumption rather than hoping.
  • tolower on a negative char. Passing a negative value to <ctype.h> functions is undefined behaviour; cast to unsigned char first if the input might not be ASCII.

Interview drill

Warm-up: Check whether two strings are anagrams. Then: what if they can be any Unicode text?

How a strong answer sounds
For lowercase ASCII: compare lengths first as a cheap reject, then one pass incrementing a 26-slot array for the first string and decrementing it for the second, and finally check every bucket is zero. O(n) time, O(1) space since the array is fixed size — and I would say "assuming lowercase ASCII" out loud rather than leaving it implicit. Sorting both strings also works and is one line, but it is O(n log n) and mutates or copies the inputs. For Unicode the 26-slot array is gone, so I would decode to code points and count them in a hash map. But I would also flag that "anagram" becomes genuinely ambiguous: is "é" as one code point the same character as "e" plus a combining accent? Usually yes to a user, so the correct preprocessing is Unicode NFC normalisation before counting, and possibly case folding rather than tolower, which is locale-dependent. That is the kind of question where naming the ambiguity matters more than the code.

Deeper: Why is building a string with s = s + c in a loop O(n²), and what is the general lesson?

How a strong answer sounds
s + c constructs a brand-new string: it allocates a buffer of length s.size()+1, copies all of s, appends the character, and then that temporary is assigned back. So iteration i copies i characters, and the total is 1 + 2 + … + n = Θ(n²). s += c instead appends into the existing buffer, growing by doubling, which is amortized O(1) per append and O(n) overall — the same geometric argument that makes push_back O(1). The general lesson is that in any language with immutable or value-semantic strings, an operation that produces a new string inside a loop is quadratic. That is why Java has StringBuilder, why Python code joins a list instead of using += in a loop over many pieces, and why in C++ I reach for += with a reserve, or write into a preallocated buffer. The same trap applies to substr in a loop, and to any "return a modified copy" helper called n times.

🧠 Key takeaways

  • A string is a contiguous array of small integers, so c - 'a' makes a 26-slot array the right frequency container.
  • s += c is amortized O(1); s = s + c is O(n) per step and O(n²) overall.
  • Palindromes: converging pointers for checking, expand-around-centre for finding — and both centre parities are required.
  • stringstream with >> splits on whitespace runs; getline with a delimiter keeps empty fields.
  • One char is one byte, not one character — state your alphabet assumption explicitly.

Check your understanding

Why is for(char c : s) ans = ans + c; O(n²)?

Total copying is 1 + 2 + … + n = Θ(n²). ans += c appends into the existing buffer with doubling growth, making it amortized O(1) per append.

In expand-around-centre for the longest palindromic substring, why call expand twice per index?

There are 2n−1 possible centres. With only expand(s,i,i) you find "aba" but never "abba", because the latter has no single central character.

What does s.find("x") return when the substring is absent?

npos is the largest size_t. Comparing to -1 may appear to work due to conversion rules but is fragile and warns; compare to string::npos explicitly.

You need to split "a,,b" on commas and keep the empty field. Which do you use?

>> collapses runs of separators and drops empty tokens, giving two fields. getline with a delimiter emits one field per delimiter, giving the three that CSV semantics require.

Your palindrome checker crashes on the input ".,". What is wrong?

With every character skippable, while(!isalnum(s[left])) left++; never stops at a valid position and reads out of bounds. Both skip loops need the bound: while(left<right and !isalnum(s[left])) left++;
