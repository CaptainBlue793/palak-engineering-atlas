Setup, Judges & Your First Program

You will run hundreds of programs during this course. If running one takes two minutes of clicking, you will test less — and testing is where the learning actually happens. This chapter gets you from nothing to a smooth loop: write C++, compile it, feed it input, read the output, and submit it to an online judge that tests it against hidden cases. It also teaches you to read a judge's verdict as a clue that points straight at the kind of bug you have.

  • Install a C++ compiler (or use an online one), and compile and run a program
  • Read every line of a complete C++ program
  • Read input and print output in the formats judges use, quickly
  • Tell LeetCode-style problems from Codeforces-style problems
  • Read a verdict — CE, RE, TLE, MLE, WA, AC — and know what to look for
  • Test your own code on edge cases before submitting

Why C++, and what you'll set up

This course uses C++ for three reasons. It's fast, so the running time you measure reflects the algorithm, not the language. Its standard library (the STL) gives you every data structure you'll need, ready-made. And it's the most common language on competitive-programming judges and a standard choice in interviews. The ideas all transfer to Python, Java or anything else; only the spelling changes.

You need three things:

⚙️

A compiler

The program that turns your C++ source into something the computer can run. We use g++.

📝

An editor

Anywhere you can type code: VS Code, CLion, Vim, or the editor built into a judge's website.

🏛️

An online judge account

LeetCode for interview-style problems, Codeforces or AtCoder for contests. Free to join.

The compiler

C++ is a compiled language. A program called a compiler reads your source file (sol.cpp) and turns it into machine instructions saved as a program you can run. That happens once, before running. (Python, by contrast, reads and runs your code line by line every time.) The compiler almost every judge uses is g++, part of GCC, the GNU Compiler Collection.

  • Windows: install GCC through MSYS2 (MinGW-w64), or use WSL (a Linux system inside Windows). Both give you g++ in a terminal.
  • Linux: sudo apt install g++ (or your distribution's equivalent).
  • macOS: xcode-select --install gives you a g++ command, but it is really Clang, and it does not have <bits/stdc++.h>. Either install real GCC with Homebrew (brew install gcc, then run g++-14 or whichever version it installs) or include the specific headers you need.
  • No install at all: online compilers such as Compiler Explorer (godbolt.org) or the “custom input” box on Codeforces and LeetCode run your code in a browser. Perfect for starting; a local setup is faster once you're practising daily.

Then compile and run like this:

g++ -std=c++17 -O2 -Wall -o sol sol.cpp   # compile sol.cpp into a program called sol
./sol                                     # run it, type the input by hand (Windows: sol.exe)
./sol < input.txt                         # run it, reading the input from a file
./sol < input.txt > output.txt            # ...and write the output to a file

Each flag has a job. -std=c++17 turns on the C++17 language version, which is what this course uses (for things like auto and {} initialisation). -O2 tells the compiler to optimise; judges compile with it, so your timings only mean something with it too. -Wall turns on warnings, which catch real bugs such as an unused variable you meant to use. -o sol names the output program.

🧪
A debug build that catches bugs for you

While testing, compile a second way: g++ -std=c++17 -g -fsanitize=address,undefined -Wall -o sol_dbg sol.cpp. The sanitizers add checks that stop the program with a clear message the moment it reads outside an array, uses freed memory, or overflows a signed integer — bugs that otherwise just produce silent garbage. It runs slower, so use it for testing, not for timing. (Sanitizers work with GCC and Clang on Linux and macOS; on Windows, WSL is the easy route.)

Your first program, line by line

Here is a complete program in the course's house style. It reads a number n, then n numbers, and prints their sum. Save it as sol.cpp, compile it, and give it the input 3 then 10 20 30. It should print 60. Click any line on the left to see what it does.

Anatomy of sol.cppClick a line
👈 Click a line of the program.
sol.cpp — a full programO(n)O(n)
#include <bits/stdc++.h>
using namespace std;

int main(){
	ios::sync_with_stdio(false);      // faster cin/cout
	cin.tie(nullptr);

	int n;
	cin>>n;
	vector<long long> a(n);
	for(int i=0;i<n;i++)
	cin>>a[i];

	long long sum=0;
	for(auto &x:a)
	sum+=x;

	cout<<sum<<"\n";
	return 0;
}
Where the cost comes from: one pass to read, one pass to add, so O(n) time; the vector holds n numbers, so O(n) space. (O(n) means “grows in proportion to n” — P8 and Chapter 2 make this precise.)
✍️
My convention: the two-line header

Every full program in this course starts with #include <bits/stdc++.h> and using namespace std;. The first line pulls in the whole standard library at once (it is a GCC-only shortcut). The second lets you write vector instead of std::vector. Both are normal in competitive programming. In a real codebase you would include only the headers you use, and write std::.

Most code blocks in later chapters show only the function, because that is what you submit to LeetCode. Assume these two lines sit above it. The rest of the house style — no spaces around operators, braces on the same line, tabs, one-line bodies without braces — is set out in Chapter 1.

Input and output

cin reads from standard input (the keyboard, or a file redirected with <); cout writes to standard output. cin>>x skips any spaces and newlines, then reads one value into x — so numbers can be spread over lines however the input likes. cout<<x prints; chain them with more <<.

// read a grid: first r and c, then r rows of c numbers
int r,c;
cin>>r>>c;
vector<vector<int>> g(r,vector<int>(c));
for(int i=0;i<r;i++)
for(int j=0;j<c;j++)
cin>>g[i][j];

// read words until the input runs out (cin>>w becomes false at the end)
string w;
while(cin>>w)
cout<<w<<"\n";

// read a whole line, spaces included
string line;
getline(cin,line);

// print a double with exactly 6 digits after the point
cout<<fixed<<setprecision(6)<<3.14159265<<"\n";   // 3.141593

Three details that trip people up:

  • Speed. By default, cin and cout are kept in sync with C's older scanf/printf, which slows them down a lot. The two lines at the top of main switch that off. With 10⁵–10⁶ numbers of input, they can be the difference between passing and TLE. After using them, don't mix cin with scanf.
  • "\n", not endl. endl prints a newline and flushes the output buffer every time, which is slow inside a big loop. The course always uses "\n".
  • Mixing >> and getline. After cin>>n, the newline after n is still waiting. A getline right after returns an empty line. Call cin.ignore() once in between, or read everything with >>.

Two kinds of judges

An online judge is a website that runs your code against hidden tests and tells you whether it is right. You will meet two styles.

You fill in one function inside a class Solution. The site reads the input, calls your function and checks what it returns. No main, no cin. This is what interviews look like, so it is what most of this course shows.

class Solution{
public:
	int findMax(vector<int> &nums){
		int maxi=INT_MIN;
		for(auto &x:nums)
		maxi=max(maxi,x);

		return maxi;
	}
};

You never see the input format. You only see the function's parameters. To test locally, write your own small main that builds a vector and calls the function.

You write the whole program. It reads from standard input (cin) and prints to standard output (cout) in exactly the format the statement describes. Codeforces, AtCoder, CodeChef and most school contests work this way.

#include <bits/stdc++.h>
using namespace std;

int main(){
	int n;
	cin>>n;
	vector<int> nums(n);
	for(int i=0;i<n;i++)
	cin>>nums[i];

	int maxi=INT_MIN;
	for(auto &x:nums)
	maxi=max(maxi,x);

	cout<<maxi<<"\n";
	return 0;
}

Same logic. The only extra work is reading the input and printing the answer in the exact format. Many Codeforces problems also have several test cases in one input: first a number t, then t separate problems — wrap your solution in while(t--).

How a submission is judged

When you press Submit, your code goes through a short pipeline. A verdict tells you where in the pipeline your code failed, and that already tells you what kind of bug to look for.

From Submit to verdictWalkthrough
  1. On LeetCode that is just your class Solution. On Codeforces it is the whole program. Nothing has run yet: the judge has only received text.
  2. The judge runs a compiler, much like g++ -O2. If your code has a syntax error, a missing semicolon or a type mismatch, you get CE — Compilation Error. Nothing ran. Always compile locally first; a CE is the cheapest verdict to avoid.
  3. Each test runs with a time limit (often 1–2 seconds) and a memory limit (often 256 MB). Three things can go wrong here. RE — Runtime Error: the program crashed, for example by reading outside an array or dividing by zero. TLE — Time Limit Exceeded: it was too slow; the answer may even be right, but it came too late. MLE — Memory Limit Exceeded: it used too much memory.
  4. If the program finished, the judge compares what it printed (or returned) with the correct answer. Any difference gives WA — Wrong Answer. Judges usually ignore extra spaces at the end of a line, but not a missing number or a different order. Many judges tell you which test failed: “Wrong answer on test 7”.
  5. There are usually dozens of hidden tests. They include the nasty cases: n = 1, the largest allowed n, all values equal, negative numbers, an already-sorted array. Passing the examples in the statement proves very little.
  6. AC — Accepted. Only now is the problem solved. The judge often shows your running time too. If it is close to the limit, a slightly larger test could have failed, so it is still worth thinking about a faster approach.
CE: fix the syntax. RE: look for out-of-range indexes, null pointers, deep recursion. TLE: your approach is too slow (see P8). WA: your logic or an edge case is wrong (see Chapter 53).

🐢
TLE almost never means “make the code a bit faster”

It nearly always means “the approach is the wrong size”. An O(n²) solution at n = 10⁵ will not pass with any amount of tidying. Go back and choose an O(n log n) idea instead. P8 shows you how to tell before you submit.

Testing your own code

The judge's hidden tests are harsher than the examples in the statement. Get into the habit of testing like the judge does, before you submit:

Run the examples

Save each example input to a file (in1.txt) and run ./sol < in1.txt. Compare with the expected output character by character.

Try the edge cases

The smallest input (n = 1, an empty string), all values equal, all negative, already sorted, sorted backwards, the largest values allowed.

Try a big input

Generate the largest allowed n with a tiny script and time it: does it finish well under the limit?

Print to the error stream while debugging

cerr<<"i="<<i<<"\n"; writes to standard error, which judges ignore — but delete it anyway before submitting, since printing is slow.

When a bug is hard to find, the strongest technique is a stress test: write a slow but obviously correct brute-force solution, generate thousands of small random inputs, and compare the two answers until they differ. Chapter 53 teaches it step by step.

⚠️
Common mistakes
  • Submitting without compiling locally. A CE costs a penalty in contests and time everywhere.
  • Printing extra text. “The answer is 60” when the judge expects “60” is a Wrong Answer. Match the output format exactly.
  • Using endl in a big loop. It flushes every time. Use "\n".
  • Forgetting the fast-I/O lines on problems with 10⁵+ numbers of input.
  • Testing only the given examples. They are chosen to explain the problem, not to break your code.
  • Timing without -O2. Unoptimised builds can be several times slower than what the judge runs.

Interview drill

Warm-up: Your solution gets “Time Limit Exceeded on test 12”. The first 11 tests passed. What does that tell you, and what do you do?

How a strong answer sounds
The logic is probably right — earlier tests passed — but test 12 is likely the first large one, and my approach is too slow for it. I'd look at the constraints, estimate my operation count (say n = 10⁵ with an O(n²) loop is about 10¹⁰ operations, far over the ~10⁸ per second budget) and look for an idea of a smaller complexity class, like sorting plus two pointers or a hash map. I'd also quickly rule out cheap causes: slow I/O without the sync line, passing a vector by value inside a loop, or a loop that never ends on some input.

Explain it simply: What's the difference between a Runtime Error and a Wrong Answer?

How a strong answer sounds
A Runtime Error means the program crashed before finishing — typically reading outside an array, following a null pointer, dividing by zero, or overflowing the call stack with deep recursion. A Wrong Answer means it finished normally but printed or returned the wrong result — a logic bug, a missed edge case, overflow or a formatting mistake. So RE sends me looking at memory accesses; WA sends me looking at logic and edge cases.

🧠 Key takeaways

  • Compile with g++ -std=c++17 -O2 -Wall; add -g -fsanitize=address,undefined for a debug build that catches memory bugs.
  • A full program is the two-line header, main, reading input, computing, printing, return 0.
  • cin>> skips whitespace; use the two fast-I/O lines and "\n" instead of endl.
  • LeetCode wants one function in class Solution; Codeforces wants a whole program reading standard input.
  • Read the verdict as a clue: CE is syntax, RE is a crash, TLE is the wrong-sized approach, MLE is memory, WA is logic or an edge case.
  • Test the examples, the edge cases and one maximum-size input before you submit.

Check your understanding

What does the -O2 flag in g++ -std=c++17 -O2 -Wall -o sol sol.cpp do?

-O2 turns on optimisation. Judges compile with it, so your local timings only mean something with it too. -o sol names the output, -Wall enables warnings, and -std=c++17 picks the language version.

Your program crashes when the input array is empty, because it reads a[0]. What verdict will the judge give on that test?

Reading outside an array is a runtime problem — the code compiles fine, then crashes (or reads garbage) when it runs. A guard clause like if(a.empty())return 0; prevents it.

Why do many solutions start main with ios::sync_with_stdio(false); cin.tie(nullptr);?

They switch off synchronisation with C's I/O and stop cin from flushing cout before every read. That speeds up big inputs considerably. The catch is the opposite of option 3: after them, don't mix cin with scanf.

On LeetCode, what do you normally submit?

LeetCode reads the input itself and calls your function. Codeforces-style judges are the ones where you write the whole program, including input and output.

Your answer passes all the examples, then gets “Wrong answer on test 5”. Which is the best next step?

WA means the output was wrong, not slow. The hidden tests contain cases the examples don't: tiny inputs, duplicates, negatives and huge values. Reproduce them locally — overflow is a top suspect when values are large.
