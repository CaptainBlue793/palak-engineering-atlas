Balanced Trees: AVL, Red-Black, Treap

Chapter 19 ended with a BST turning into a linked list when you insert sorted values. This chapter is the fix. There is one tool: the rotation. It rewires a few pointers to change a subtree's height, while keeping its inorder (sorted) order the same. Every balanced tree is just a different rule for when to rotate. You will rarely write one yourself, but you will use one all the time, because std::map is a red-black tree.

Rotation: the only mechanism

The problem this chapter solves. A BST's speed is O(h), and h depends on the order values arrive. Sorted input, which is common (timestamps, IDs, already-sorted files), gives h = n. A balanced tree promises h = O(log n) no matter what order you insert in. For a million keys that is the difference between about 20 steps and a million steps per lookup.

A rotation takes a parent and one of its children and swaps their roles: the child moves up, the parent moves down. The key point is that it keeps the inorder sequence the same, so the tree is still a valid BST. What changes is how tall each side is. That is the whole trick, and everything in this chapter is built from it.

Smallest example: insert 3, 2, 1 into a plain BST and you get a chain leaning left (3 at the top, 2 below it, 1 at the bottom), height 2. Rotate right at 3: its left child 2 moves up to be the root, and 3 becomes 2's right child. Now 2 has children 1 and 3, height 1. Inorder was 1 2 3 before and is 1 2 3 after.

// Right rotation at y. The left child x becomes the new subtree root.
//
//        y                x
//       / \              / \
//      x   C    ->      A   y
//     / \                  / \
//    A   B                B   C
//
// Inorder before: A x B y C.  After: A x B y C.  Identical. That is the point.
TreeNode* rotateRight(TreeNode* y){
	TreeNode* x=y->left;
	TreeNode* B=x->right;

	x->right=y;
	y->left=B;              // B moves from x's right to y's left

	updateHeight(y);        // y is now LOWER, so update it first
	updateHeight(x);

	return x;               // the caller must reassign: node = rotateRight(node)
}

// Left rotation — the exact mirror image.
TreeNode* rotateLeft(TreeNode* x){
	TreeNode* y=x->right;
	TreeNode* B=y->left;

	y->left=x;
	x->right=B;

	updateHeight(x);
	updateHeight(y);

	return y;
}
Two things to get right. First, B (the "inner" subtree, in the middle) is the only subtree that gets a new parent. Forgetting to move it is the classic rotation bug, and it quietly loses a whole subtree. Second, update the height of the node that is now lower first, because the higher node's height depends on it. Also, the function returns the new root, so every caller must reassign it. That is the same pattern as BST insert in Chapter 19.

AVL: strict balance, four cases

An AVL tree keeps every node's balance factor (left height minus right height) at −1, 0 or +1: {−1, 0, +1}. After an insert or delete, walk back up toward the root. The first node that breaks this rule gets rotated. There are exactly four shapes, depending on which grandchild caused the problem.

A balance factor example: a node whose left subtree has height 3 and right subtree has height 1 has balance factor 3 − 1 = +2. That is outside {−1, 0, +1}, so it must be fixed. Why only ±2 ever shows up: before the insert every node was within ±1, and one insert raises a subtree's height by at most 1. So the worst it can become is ±2.

Two tiny traces make the cases concrete:

  • RR — insert 1, 2, 3. After 3 arrives, node 1 has an empty left side (height 0) and a right side of height 2 (2, then 3), so its balance is −2. Its right child 2 also leans right. One left rotation at 1 makes 2 the root with children 1 and 3.
  • LR — insert 3, 1, 2. Node 3 has left height 2, right height 0: balance +2. But its left child 1 leans right (2 is 1's right child). A single right rotation at 3 would give 1 at the top with 3 on its right and 2 under 3: still height 2, now leaning the other way. Instead rotate left at 1 first (giving the chain 3 → 2 → 1, an LL shape), then rotate right at 3. Result: 2 at the root with children 1 and 3.

🧾
Why the inner cases need two rotations

A single rotation moves the outer subtree up one level, while the inner subtree stays at the same depth. So when the heavy grandchild is on the outside (LL, RR), one rotation lifts it and the tree balances. When it is on the inside (LR, RL), one rotation moves the inner subtree to the other side without lifting it. You would swap a left-heavy tree for a right-heavy one of the same height. So the first rotation has one job: turn the inner case into an outer case. Then the second rotation does the real work. If you remember only one thing: rotate the child first to move the problem to the outside, then rotate the node.

AVL insert with all four casesO(log n)O(log n)
// Node carries a cached height so balance() is O(1) rather than O(n).
struct AVLNode{
	int val;
	int height;
	AVLNode* left;
	AVLNode* right;

	AVLNode(int val){
	this->val=val;
	height=1;
	left=nullptr;
	right=nullptr;
}
};

int H(AVLNode* node){ return node?node->height:0; }
int balance(AVLNode* node){ return node?H(node->left)-H(node->right):0; }
void fix(AVLNode* node){ node->height=1+max(H(node->left),H(node->right)); }

AVLNode* rotR(AVLNode* y){
	AVLNode* x=y->left;
	y->left=x->right;
	x->right=y;

	fix(y);
	fix(x);

	return x;
}
AVLNode* rotL(AVLNode* x){
	AVLNode* y=x->right;
	x->right=y->left;
	y->left=x;

	fix(x);
	fix(y);

	return y;
}

AVLNode* insert(AVLNode* node,int val){
	if(!node)return new AVLNode(val);

	if(val<node->val)node->left=insert(node->left,val);
	else if(val>node->val)node->right=insert(node->right,val);
	else return node;                  // duplicates ignored

	fix(node);

	int b=balance(node);

	// LL: left-heavy, left child leans left (or is balanced)
	if(b>1 and val<node->left->val)
	return rotR(node);

	// RR: right-heavy, right child leans right
	if(b<-1 and val>node->right->val)
	return rotL(node);

	// LR: left-heavy, left child leans right -> make it outer, then rotate
	if(b>1 and val>node->left->val){
		node->left=rotL(node->left);
		return rotR(node);
	}

	// RL: right-heavy, right child leans left
	if(b<-1 and val<node->right->val){
		node->right=rotR(node->right);
		return rotL(node);
	}

	return node;
}
Insertion needs at most one rotation (or one double rotation). A single insert raises a height by at most one, and fixing the lowest unbalanced node fixes every ancestor above it. The reason: after the rotation, that subtree's height goes back to exactly what it was before the insert. The ancestors above it therefore see no change at all, and they were balanced before. Deletion is different. It can need O(log n) rotations all the way up, because removing a node can shorten a subtree, and that can unbalance the next node up, and so on. This difference is the main reason libraries prefer red-black trees.
📐
Why AVL height is O(log n)

Let N(h) be the fewest nodes an AVL tree of height h can have. The emptiest such tree has one subtree of height h−1 and the other of height h−2. So N(h) = 1 + N(h−1) + N(h−2), which is the Fibonacci recurrence. That means N(h) ≈ φ^h, where φ ≈ 1.618. Solving for h gives h ≈ log_φ n ≈ 1.44 log₂ n. So an AVL tree is at most about 44% taller than a perfect tree. That is the tightest bound of any common balanced tree, and it is why AVL wins when most operations are lookups.

Red-black: looser balance, cheaper updates

A red-black tree colours each node red or black and keeps five rules true at all times. Its height guarantee is weaker than AVL's, but it needs far fewer rotations per update. That is why standard libraries use it.

The colours are just a bookkeeping device. Think of the black nodes as the "real" skeleton of the tree, kept perfectly balanced, and the red nodes as spare slack the tree is allowed to absorb before it has to rebalance. A new node is always inserted red (so black heights do not change). If its parent is also red, rule 4 is broken, and the fix is either recolouring a few nodes or at most two rotations.

To put numbers on the two bounds: for n = 1,000,000, a perfect tree has height about 20, an AVL tree at most about 29 (1.44 × 20), and a red-black tree at most about 40 (2 × 20). All three are tiny next to the 1,000,000 of a degenerate BST, which is why the looser red-black bound is a fine trade.

The five invariants

  1. Every node is red or black.
  2. The root is black.
  3. All null leaves count as black.
  4. No red node has a red child (no two reds in a row).
  5. Every path from a node to its descendant nulls contains the same number of black nodes (equal “black height”).

Why those give O(log n)

Rule 5 says that if you look only at the black nodes, the tree is perfectly balanced, so that part's height is at most log₂ n. Rule 4 says reds can't come two in a row, so at most half the nodes on any path are red. That means the real height is at most twice the black height: h ≤ 2 log₂(n+1). That is looser than AVL's 1.44 log₂ n, but it takes far less rebalancing to keep.

What std::map and std::set actually are

Both are red-black trees in every major implementation (libstdc++, libc++, MSVC). That is why they give you guaranteed (not just expected) O(log n), iteration in sorted order, and lower_bound/upper_bound. But they are noticeably slower in practice than unordered_map. Each lookup follows a chain of pointers to nodes scattered around memory, instead of one hash and one array read. The C++ standard doesn't require red-black, only the time bounds, but in practice you can assume it. Also worth knowing: std::map gives reference stability. Inserting never breaks references or iterators to elements already in the map. unordered_map is different (a rehash breaks its iterators), and so is vector (a resize breaks everything).

Treap: let randomness do the bookkeeping

A treap (tree + heap) is a BST ordered by key, and also a heap ordered by a random priority. To insert, add the node as in a normal BST, give it a random priority, then rotate it upward while its priority beats its parent's. No balance factors, no colours, no list of cases. The expected height is O(log n), because the tree ends up with exactly the shape you would get by inserting the keys in random order.

Why the shape is fixed by the priorities: the node with the highest priority must be the root (heap rule). Every smaller key goes to its left and every larger key to its right (BST rule). Then the same reasoning picks the root of each side. So given the keys and priorities, there is only one possible treap. Example: keys 1, 2, 3 with priorities 20, 90, 50. Key 2 has the top priority, so it is the root, with 1 on the left and 3 on the right, whatever order you inserted them in.

treap insert — 20 lines, no case analysisO(log n) expectedO(log n)
struct TreapNode{
	int val;
	int priority;
	TreapNode* left;
	TreapNode* right;

	TreapNode(int val){
	this->val=val;
	priority=rand();
	left=nullptr;
	right=nullptr;
}
};

// BST insert, then rotate up while this node's priority beats its parent's.
// The heap property on priorities is what forces a random shape.
TreapNode* insert(TreapNode* node,int val){
	if(!node)return new TreapNode(val);

	if(val<node->val){
		node->left=insert(node->left,val);

		if(node->left->priority>node->priority)
		node=rotR(node);
	}else if(val>node->val){
		node->right=insert(node->right,val);

		if(node->right->priority>node->priority)
		node=rotL(node);
	}

	return node;
}
This is the balanced tree to write from scratch in an interview or contest. The reason it works is short. A treap's shape depends only on the priorities, not on the order you insert keys. So it behaves exactly like a BST built from random input, whose expected height is 2.99 log₂ n. Someone trying to break it can't force a bad case by picking the input order; they would have to guess your random numbers. Treaps also support split and merge in O(log n). That makes them the base for balanced "arrays" where you can do things like "insert a range in the middle".

B-trees: when the memory hierarchy is the bottleneck

A B-tree of order B is a sorted tree with wide nodes. Each node stores up to B−1 keys and has up to B children. The height becomes log_B n instead of log₂ n. With B = 100, a million keys sit just three levels deep.

Where that "three" comes from: the root has up to 100 children, each of those has up to 100 children (10,000 nodes on the second level down), and each of those has up to 100 (1,000,000 on the third). Each step down multiplies the reach by B, so the number of levels is how many times you multiply by 100 to reach n: log base 100 of 10⁶ = 3. Inside a node the keys are sorted, so you binary search them to pick the child to follow. Instead of rotating, a B-tree stays balanced by splitting a node that gets too full into two and pushing the middle key up to the parent. The tree only grows taller when the root itself splits, so all leaves always stay at the same depth.

💾
Why databases and filesystems use B-trees rather than red-black trees

Because what is expensive is different. In RAM, a comparison and following a pointer cost about the same, so using as few comparisons as possible (a binary tree) is the right goal. On disk, one read costs about 100,000 times as much as a comparison. So the goal becomes using as few node reads as possible. A B-tree node is sized to fill exactly one disk page (or a group of cache lines). Each read brings back hundreds of keys and rules out hundreds of possibilities at once. A red-black tree with a million keys needs about 20 scattered reads; a B+ tree with B = 200 needs 3. This is Chapter 3's cache-locality argument (keep related data close together), taken all the way. It is why every database index, every filesystem directory and the upper layers of every LSM tree are shaped like B-trees.

Augmenting: order-statistic trees

A balanced BST becomes much more powerful when each node also stores its subtree size (how many nodes are below it, itself included). This is called augmenting the tree. You get two new O(log n) operations: “what is the k-th smallest?” and “what is x's rank?” (how many values are smaller than x).

Trace on the balanced tree holding 1 to 7 (root 4; 2 with 1, 3; 6 with 5, 7). Every leaf has size 1, nodes 2 and 6 have size 3, the root has size 7. Find the 6th smallest. At 4: the left size is 3, so the root is the 4th smallest. 6 > 4, so skip the left subtree and the root: k becomes 6 − 4 = 2, go right. At 6: its left size is 1, so 6 is the 2nd smallest in this subtree, and k = 2. Answer: 6. Two nodes visited, not six.

order statistics from a size fieldO(log n)O(1) extra per node
// Each node stores size = number of nodes in its subtree, itself included.
int S(Node* node){ return node?node->size:0; }

// k-th smallest, 1-indexed. Compare k against the left subtree's size and
// descend — the exact same decision structure as a binary search.
int kthSmallest(Node* node,int k){
	while(node){
		int leftSize=S(node->left);

		if(k==leftSize+1)return node->val;    // this node IS the k-th

		if(k<=leftSize){
			node=node->left;
		}else{
			k-=leftSize+1;                      // skip the left subtree AND this node
			node=node->right;
		}
	}

	return -1;
}

// rank(x) = how many values are strictly less than x.
int rank(Node* node,int x){
	int count=0;

	while(node){
		if(x<=node->val){
			node=node->left;
		}else{
			count+=S(node->left)+1;            // everything left of here, plus here
			node=node->right;
		}
	}

	return count;
}
Every insert, delete and rotation must keep the size field up to date. That is why rotations update it along with the height. GNU's __gnu_pbds::tree_order_statistics_node_update gives you this for free. It solves "count of smaller numbers after self" and "count inversions" in O(n log n) with no special tricks. When the values are integers in a limited range, a Fenwick tree (Chapter 24) does the same job and runs much faster in practice.
✍️
My convention: use the library, and know what to say when asked to build one

In real code and in contests, use std::map, std::set or std::multiset. Writing your own red-black tree is a mistake in every practical setting. But be able to (a) state the rules, (b) draw the four AVL cases, (c) explain why rotations keep the inorder order, and (d) write a treap, the only one short enough to write under time pressure. If an interviewer asks for a self-balancing tree from scratch, a treap plus one sentence on why its expected height is O(log n) is a far better answer than a half-finished red-black insert.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 WHY ROTATE
A rotation changes the height but never the in-order sequence. That invariant is the whole reason balancing is allowed to move nodes around at all.
💡 USE THE LIBRARY
In an interview, reach for std::map / std::set and say "this is a balanced BST". Hand-rolling AVL is almost never what is being tested.
💡 ORDER STATISTICS
Augment each node with its subtree size and you get k-th smallest and rank in O(log n) — which is what turns a BST into a tool for counting problems.
⚠️
Common mistakes
  • Forgetting to move the inner subtree in a rotation. y->left = x->right is easy to skip, and it quietly loses a whole subtree.
  • Updating heights in the wrong order. Update the node that moved down first, because the one that moved up depends on it.
  • Not reassigning the rotation's return value. rotateRight(node) without node = leaves the parent pointing at the old root.
  • Using one rotation for an LR or RL case. It turns left-heavy into right-heavy without lowering the height. Rotate the child first.
  • Assuming AVL deletion needs at most one rotation. Insertion does. Deletion can trigger rotations all the way up, O(log n) of them.
  • Recomputing height recursively inside balance(). That makes each check O(n). Store the height in the node instead.
  • Forgetting to update the size field in an augmented tree, especially inside rotations.
  • Using a BST when a hash map is enough. If you never need order or ranges, O(1) beats O(log n).
  • Hand-writing a red-black tree. Use std::map; if you must write one, write a treap.

Interview drill

Warm-up: Why does a rotation preserve the BST property?

How a strong answer sounds
Because it keeps the inorder sequence the same, and a sorted inorder sequence is the BST property. Take a right rotation at y, whose left child is x. Subtree A hangs off x's left, B off x's right, and C off y's right. Before the rotation, inorder visits A, then x, then B, then y, then C. After it, x is the root with A on its left and y on its right, and y has B on its left and C on its right. So inorder visits A, x, B, y, C again. Same sequence, so still sorted, so still a BST. What did change is the depths: A moved up a level and C moved down one. That is exactly the lever balancing uses. The detail that matters in code is B, the inner subtree. It is the only one that gets a new parent, moving from x's right to y's left. Forgetting that line is the classic rotation bug, because it drops a subtree with no obvious sign.

Deeper: AVL or red-black — which would you pick, and why do libraries pick the other one?

How a strong answer sounds
It depends on how many reads versus writes there are. AVL keeps the balance factor within one, which limits the height to about 1.44 log₂ n. That is provably the tightest of the common balanced trees, so its lookups are the fastest. The cost is on writes. A deletion can need rotations all the way up to the root, O(log n) of them, and every node has to store an integer height. Red-black loosens the guarantee to at most 2 log₂ n. It only requires that no red node has a red child, and that every root-to-null path has the same number of black nodes. That is looser, but it limits insertions to two rotations and deletions to three, and the extra data is a single bit. Libraries choose red-black because they must handle general use, where insertions and deletions are common. Limited rebalancing plus one bit per node is the better deal. std::map, std::set, Java's TreeMap and most standard libraries are all red-black. I would pick AVL only for a structure that is built once and then mostly read. And if I had to write one myself under time pressure, I would write neither. A treap is twenty lines. Its expected height is O(log n) because its shape depends only on the random priorities, not the insertion order. It also supports split and merge, which red-black does not do easily.

🧠 Key takeaways

  • A rotation keeps the inorder sequence the same while changing depths. That is what makes every balanced tree possible.
  • AVL's four cases: outer ones (LL, RR) need one rotation. Inner ones (LR, RL) need an extra first rotation to make them outer.
  • AVL height is ≤ 1.44 log₂ n (from the Fibonacci recurrence). Red-black is ≤ 2 log₂ n, but it limits the rotations per update.
  • std::map and std::set are red-black trees, which is why they guarantee O(log n) and keep references stable.
  • A treap uses randomness instead of bookkeeping, and it is the one to write by hand. A size field in each node gives k-th smallest and rank in O(log n).

Check your understanding

Why does a rotation keep the tree a valid BST?

Before and after a right rotation, inorder visits A, x, B, y, C. The sequence is the same, so it is still sorted. Only the depths change, and that is exactly the lever balancing needs.

A node is left-heavy and its left child is right-heavy (the LR case). What fixes it?

A single rotation lifts the outer subtree, but here the heavy grandchild is on the inside. One rotation would just swap left-heavy for right-heavy. The first rotation turns the inner case into an outer one; the second does the real work.

Why do libraries implement std::map as a red-black tree rather than an AVL tree?

AVL has the tighter height bound (1.44 vs 2 log₂ n), so its lookups are faster, but it pays more on updates. A general-purpose container sees many inserts and deletes, so limited rebalancing wins.

What makes a treap balanced in expectation?

The heap rule on priorities fixes the shape completely, and the priorities are random. So sorted input gives the same expected shape as shuffled input. That is why 20 lines with no list of cases is enough.

Why do databases use B-trees instead of red-black trees?

A disk read costs as much as about 100,000 comparisons. So the goal changes from fewer comparisons to fewer reads. This is Chapter 3's cache-locality argument taken to the extreme.
