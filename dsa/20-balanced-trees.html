Balanced Trees: AVL, Red-Black, Treap

Chapter 19 ended with a BST degenerating into a linked list on sorted input. This chapter is the fix. The single mechanism is the rotation — a local pointer rearrangement that changes a subtree's height while preserving its inorder order — and every balanced tree is a different policy for when to apply it. You will rarely implement one; you will constantly use one, because std::map is a red-black tree.

  • Understand a rotation as the one operation that changes height without changing order
  • Write the four AVL cases and see why LR and RL need two rotations
  • State the red-black invariants and why they give a looser but cheaper balance
  • Explain a treap, and why randomness substitutes for bookkeeping
  • Say what std::map and std::set actually are, and when to augment a tree

Rotation: the only mechanism

A rotation takes a parent and one child and swaps their roles. Crucially, it preserves the inorder sequence — so the tree is still a valid BST — while changing the height distribution. That is the whole trick, and everything in this chapter is built from it.

the two rotations — three pointer writes eachO(1)O(1)
// Right rotation at y. The left child x becomes the new subtree root.
//
//        y                x
//       / \              / \
//      x   C    ->      A   y
//     / \                  / \
//    A   B                B   C
//
// Inorder before: A x B y C.  After: A x B y C.  Identical. That is the point.
TreeNode* rotateRight(TreeNode* y){
	TreeNode* x=y->left;
	TreeNode* B=x->right;

	x->right=y;
	y->left=B;              // B moves from x's right to y's left

	updateHeight(y);        // y is now LOWER, so update it first
	updateHeight(x);

	return x;               // the caller must reassign: node = rotateRight(node)
}

// Left rotation — the exact mirror image.
TreeNode* rotateLeft(TreeNode* x){
	TreeNode* y=x->right;
	TreeNode* B=y->left;

	y->left=x;
	x->right=B;

	updateHeight(x);
	updateHeight(y);

	return y;
}
Two things to get right. First, B — the "inner" subtree — is the only child that changes parent; forgetting to move it is the classic rotation bug and it silently loses a subtree. Second, update the lower node's height before the higher one, since the higher one's height depends on it. And the function returns the new root, so every caller must reassign — the same pattern as BST insert in Chapter 19.

AVL: strict balance, four cases

An AVL tree keeps every node's balance factor — left height minus right height — in {−1, 0, +1}. After an insertion or deletion, walk back up; the first node that violates this gets rotated. There are exactly four shapes, distinguished by which grandchild caused the problem.

RRRight-heavy, and the right child is right-heavyOne left rotation at the nodeMirror of LL
LRLeft-heavy, but the left child is right-heavyLeft at the child, then right at the nodeThe problem is on the inside — one rotation just moves it to the other side
RLRight-heavy, but the right child is left-heavyRight at the child, then left at the nodeMirror of LR
🧾
Why the inner cases need two rotations

A single rotation moves the outer subtree up one level and the inner subtree stays at the same depth. So when the heavy grandchild is on the outside (LL, RR), one rotation lifts it and the tree balances. When it is on the inside (LR, RL), a single rotation would move the inner subtree to the other side without lifting it — you would trade a left-heavy tree for a right-heavy one of the same height. The first rotation therefore exists purely to convert the inner case into an outer case, and then the second rotation does the real work. If you remember only one thing: rotate the child first to make the problem outer, then rotate the node.

AVL insert with all four casesO(log n)O(log n)
// Node carries a cached height so balance() is O(1) rather than O(n).
struct AVLNode{
	int val;
	int height;
	AVLNode* left;
	AVLNode* right;

	AVLNode(int val){
	this->val=val;
	height=1;
	left=nullptr;
	right=nullptr;
}
};

int H(AVLNode* node){ return node?node->height:0; }
int balance(AVLNode* node){ return node?H(node->left)-H(node->right):0; }
void fix(AVLNode* node){ node->height=1+max(H(node->left),H(node->right)); }

AVLNode* rotR(AVLNode* y){
	AVLNode* x=y->left;
	y->left=x->right;
	x->right=y;

	fix(y);
	fix(x);

	return x;
}
AVLNode* rotL(AVLNode* x){
	AVLNode* y=x->right;
	x->right=y->left;
	y->left=x;

	fix(x);
	fix(y);

	return y;
}

AVLNode* insert(AVLNode* node,int val){
	if(!node)return new AVLNode(val);

	if(val<node->val)node->left=insert(node->left,val);
	else if(val>node->val)node->right=insert(node->right,val);
	else return node;                  // duplicates ignored

	fix(node);

	int b=balance(node);

	// LL: left-heavy, left child leans left (or is balanced)
	if(b>1 and val<node->left->val)
	return rotR(node);

	// RR: right-heavy, right child leans right
	if(b<-1 and val>node->right->val)
	return rotL(node);

	// LR: left-heavy, left child leans right -> make it outer, then rotate
	if(b>1 and val>node->left->val){
		node->left=rotL(node->left);
		return rotR(node);
	}

	// RL: right-heavy, right child leans left
	if(b<-1 and val<node->right->val){
		node->right=rotR(node->right);
		return rotL(node);
	}

	return node;
}
Insertion needs at most one rotation (or one double rotation), because a single insert changes the height by at most one and fixing the lowest unbalanced node restores every ancestor. Deletion is different — it can require O(log n) rotations all the way up, because removing a node can shorten a subtree and cascade. That asymmetry is the main reason red-black trees are preferred in libraries.
📐
Why AVL height is O(log n)

Let N(h) be the minimum number of nodes in an AVL tree of height h. The sparsest such tree has one subtree of height h−1 and the other of height h−2, so N(h) = 1 + N(h−1) + N(h−2) — the Fibonacci recurrence. Therefore N(h) ≈ φ^h where φ ≈ 1.618, and inverting gives h ≈ log_φ n ≈ 1.44 log₂ n. So an AVL tree is at most about 44% taller than a perfect tree, which is the tightest bound of any common balanced tree — and the reason AVL wins on lookup-heavy workloads.

Red-black: looser balance, cheaper updates

A red-black tree colours each node and maintains five invariants. The result is a weaker height guarantee than AVL but far fewer rotations per update — which is why it is what standard libraries ship.

The five invariants

  1. Every node is red or black.
  2. The root is black.
  3. All null leaves count as black.
  4. No red node has a red child (no two reds in a row).
  5. Every path from a node to its descendant nulls contains the same number of black nodes (equal “black height”).

Why those give O(log n)

Invariant 5 says the black-only skeleton is perfectly balanced, so its height is at most log₂ n. Invariant 4 says reds cannot cluster, so at most half the nodes on any path are red — meaning the real height is at most twice the black height: h ≤ 2 log₂(n+1). Looser than AVL's 1.44 log₂ n, and bought with far less rebalancing.

What std::map and std::set actually are

Both are red-black trees in every major implementation (libstdc++, libc++, MSVC). That is why they give you O(log n) guaranteed rather than expected, ordered iteration, and lower_bound/upper_bound — but with a constant factor noticeably worse than unordered_map, because each lookup is a chain of pointer dereferences to scattered heap nodes rather than one hash and one indexed load. The standard does not mandate red-black, only the complexity bounds, but in practice you can assume it. Also worth knowing: std::map guarantees reference stability — inserting never invalidates references or iterators to existing elements, unlike unordered_map (whose rehash invalidates iterators) and vector (which invalidates everything).

Treap: let randomness do the bookkeeping

A treap is a BST by key and a heap by a random priority. Insert as a BST, assign a random priority, then rotate upward while the priority beats the parent's. No balance factors, no colours, no case analysis — and the expected height is O(log n) because the tree's shape is exactly the shape you would get from inserting in random order.

treap insert — 20 lines, no case analysisO(log n) expectedO(log n)
struct TreapNode{
	int val;
	int priority;
	TreapNode* left;
	TreapNode* right;

	TreapNode(int val){
	this->val=val;
	priority=rand();
	left=nullptr;
	right=nullptr;
}
};

// BST insert, then rotate up while this node's priority beats its parent's.
// The heap property on priorities is what forces a random shape.
TreapNode* insert(TreapNode* node,int val){
	if(!node)return new TreapNode(val);

	if(val<node->val){
		node->left=insert(node->left,val);

		if(node->left->priority>node->priority)
		node=rotR(node);
	}else if(val>node->val){
		node->right=insert(node->right,val);

		if(node->right->priority>node->priority)
		node=rotL(node);
	}

	return node;
}
This is the balanced tree to write from scratch in an interview or contest. The correctness argument is short: a treap's shape depends only on the priorities, not the insertion order, so it is distributed exactly like a randomly-built BST — whose expected height is 2.99 log₂ n. An adversary cannot force a bad case by choosing the input order, only by guessing your random numbers. Treaps also support split and merge in O(log n), which makes them the basis of implicit-key balanced arrays for problems like "insert a range in the middle".

B-trees: when the memory hierarchy is the bottleneck

A B-tree of order B stores up to B−1 keys per node and has up to B children. Height becomes log_B n instead of log₂ n, so with B = 100 a million keys sit just three levels deep.

💾
Why databases and filesystems use B-trees rather than red-black trees

Because the cost model is different. In RAM, a comparison and a pointer dereference cost roughly the same, so minimising comparisons (a binary tree) is right. On disk, a single read costs ~100,000× a comparison, so the objective becomes minimising the number of node reads. A B-tree node is sized to exactly one disk page or cache line group, so each read brings back hundreds of keys and one read eliminates hundreds of possibilities. A red-black tree with a million keys needs ~20 scattered reads; a B+ tree with B = 200 needs 3. This is the same cache-locality argument as Chapter 3, taken to its logical conclusion — and it is why every database index, every filesystem directory and every LSM tree's upper layers are B-tree-shaped.

Augmenting: order-statistic trees

A balanced BST becomes much more powerful when each node stores its subtree size. Two new operations appear in O(log n): “what is the k-th smallest?” and “what is x's rank?”.

order statistics from a size fieldO(log n)O(1) extra per node
// Each node stores size = number of nodes in its subtree, itself included.
int S(Node* node){ return node?node->size:0; }

// k-th smallest, 1-indexed. Compare k against the left subtree's size and
// descend — the exact same decision structure as a binary search.
int kthSmallest(Node* node,int k){
	while(node){
		int leftSize=S(node->left);

		if(k==leftSize+1)return node->val;    // this node IS the k-th

		if(k<=leftSize){
			node=node->left;
		}else{
			k-=leftSize+1;                      // skip the left subtree AND this node
			node=node->right;
		}
	}

	return -1;
}

// rank(x) = how many values are strictly less than x.
int rank(Node* node,int x){
	int count=0;

	while(node){
		if(x<=node->val){
			node=node->left;
		}else{
			count+=S(node->left)+1;            // everything left of here, plus here
			node=node->right;
		}
	}

	return count;
}
The size field must be maintained by every insert, delete and rotation — which is exactly why rotations update it alongside the height. This is what GNU's __gnu_pbds::tree_order_statistics_node_update gives you for free, and it solves "count of smaller numbers after self" and "count inversions" in O(n log n) with no cleverness. A Fenwick tree (Chapter 24) does the same job with a much smaller constant when the values are bounded integers.
✍️
My convention: use the library, and know what to say when asked to build one

In real code and in contests, reach for std::map, std::set or std::multiset — hand-rolling a red-black tree is a mistake in every practical setting. But be able to (a) state the invariants, (b) draw the four AVL cases, (c) explain why rotations preserve inorder, and (d) write a treap, which is the only one short enough to produce under time pressure. If an interviewer asks for a self-balancing tree from scratch, offering a treap with a one-line justification of its expected height is a far better answer than a half-finished red-black insert.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 WHY ROTATE
A rotation changes the height but never the in-order sequence. That invariant is the whole reason balancing is allowed to move nodes around at all.
💡 USE THE LIBRARY
In an interview, reach for std::map / std::set and say "this is a balanced BST". Hand-rolling AVL is almost never what is being tested.
💡 ORDER STATISTICS
Augment each node with its subtree size and you get k-th smallest and rank in O(log n) — which is what turns a BST into a tool for counting problems.
⚠️
Common mistakes
  • Forgetting to move the inner subtree in a rotation. y->left = x->right is easy to skip and silently loses a whole subtree.
  • Updating heights in the wrong order. Fix the node that moved down first; the one that moved up depends on it.
  • Not reassigning the rotation's return value. rotateRight(node) without node = leaves the parent pointing at the old root.
  • Applying one rotation to an LR or RL case. It converts left-heavy to right-heavy without reducing height. Rotate the child first.
  • Assuming AVL deletion needs at most one rotation. Insertion does; deletion can cascade O(log n) times.
  • Recomputing height recursively inside balance(). That makes each check O(n). Cache the height in the node.
  • Forgetting to maintain the size field in an augmented tree, especially inside rotations.
  • Using a BST where a hash map suffices. If you never need order or ranges, O(1) beats O(log n).
  • Hand-writing a red-black tree. Use std::map; if you must write one, write a treap.

Interview drill

Warm-up: Why does a rotation preserve the BST property?

How a strong answer sounds
Because it preserves the inorder sequence, and the inorder sequence being sorted is the BST property. Take a right rotation at y whose left child is x, with subtrees A under x's left, B under x's right, and C under y's right. Before the rotation, inorder visits A, then x, then B, then y, then C. After it, x is the root with A on its left and y on its right, and y has B on its left and C on its right — so inorder visits A, x, B, y, C again. Identical sequence, therefore still sorted, therefore still a BST. What did change is the depth distribution: A moved up a level and C moved down one, which is exactly the lever balancing uses. The implementation detail that matters is B, the inner subtree — it is the only one that changes parent, moving from x's right to y's left, and forgetting that line is the classic rotation bug because it drops a subtree without any obvious symptom.

Deeper: AVL or red-black — which would you pick, and why do libraries pick the other one?

How a strong answer sounds
It depends on the read/write mix. AVL keeps the balance factor within one, which bounds the height at about 1.44 log₂ n — provably the tightest of the common balanced trees, so lookups are the fastest. The cost is on the write side: a deletion can require rotations cascading all the way to the root, O(log n) of them, and every node has to carry an integer height. Red-black relaxes the guarantee to at most 2 log₂ n by requiring only that no red node has a red child and that every root-to-null path has the same black count. That is looser, but it bounds insertions at two rotations and deletions at three, and the extra state is a single bit. Libraries choose red-black because they must serve a general workload where insertions and deletions are common, and bounded rebalancing plus one bit per node is the better trade — std::map, std::set, Java's TreeMap and most language standard libraries are all red-black. I would pick AVL only for a read-dominated structure that is built once and then queried heavily. And if I had to implement one myself under time pressure I would write neither — a treap is twenty lines, has expected O(log n) height because its shape depends only on the random priorities rather than the insertion order, and supports split and merge, which red-black does not do easily.

🧠 Key takeaways

  • A rotation preserves the inorder sequence while changing depths — that invariance is what makes every balanced tree possible.
  • AVL's four cases: outer imbalances (LL, RR) need one rotation; inner ones (LR, RL) need a first rotation to make them outer.
  • AVL is ≤ 1.44 log₂ n via the Fibonacci recurrence; red-black is ≤ 2 log₂ n but bounds rotations per update.
  • std::map and std::set are red-black trees, which is why they guarantee O(log n) and keep references stable.
  • A treap trades bookkeeping for randomness and is the one to write by hand; a size field adds order statistics in O(log n).

Check your understanding

Why does a rotation keep the tree a valid BST?

Both before and after a right rotation, inorder visits A, x, B, y, C. The sequence is identical, so it is still sorted. Only the depths change — which is exactly the lever balancing needs.

A node is left-heavy and its left child is right-heavy (the LR case). What fixes it?

A single rotation lifts the outer subtree, but here the heavy grandchild is inner — one rotation would just trade left-heavy for right-heavy. The first rotation converts the inner case into an outer one; the second does the real work.

Why do libraries implement std::map as a red-black tree rather than an AVL tree?

AVL has the tighter height bound (1.44 vs 2 log₂ n) and therefore faster lookups, but pays on updates. A general-purpose container sees many insertions and deletions, so bounded rebalancing wins.

What makes a treap balanced in expectation?

The heap property on priorities determines the shape uniquely, and the priorities are random — so sorted input produces the same expected shape as shuffled input. That is why 20 lines with no case analysis works.

Why do databases use B-trees instead of red-black trees?

A disk read costs about 100,000 comparisons, so the objective changes from minimising comparisons to minimising reads. This is Chapter 3's cache-locality argument taken to its extreme.
