String Algorithms

The simple way to find a pattern inside a text is O(n·m) (text length times pattern length). It is slow because, every time a character does not match, it throws away everything it just learned. Each algorithm in this chapter fixes that same waste in its own way.

KMP works out in advance how far to fall back after a mismatch. The Z-function works out in advance how far each position matches the start. Rabin-Karp compares short "fingerprints" (hashes) instead of whole strings. Manacher reuses the mirror symmetry of palindromes. Four answers to one question.

  • Build the KMP prefix function and understand what it actually stores
  • Use the Z-function, and see it is the same information in another form
  • Hash a rolling window, and know why two moduli matter
  • Find all palindromic substrings in O(n) with Manacher
  • Know what suffix arrays and LCP arrays are for

The cost of naive search

Why care? Searching for a pattern is one of the most common operations there is: find in a text editor, grep, spotting a DNA sequence in a genome, filtering logs. It is also the building block of many interview problems about periods, rotations and palindromes. With a text of 10⁵ characters and a pattern of 10⁴, the simple method can need about 10⁹ comparisons, which is too slow. The methods here need about 10⁵.

why O(n·m) happens, and where the waste isO(n·m)wasteful
// Try the pattern at every start position.
// Worst case: text "aaaa...a", pattern "aaa...ab" — every start matches m-1
// characters and then fails on the last one. n*m character comparisons.
int naiveSearch(string &text,string &pattern){
	int n=text.size();
	int m=pattern.size();

	for(int i=0;i+m<=n;i++){
		int j=0;

		while(j<m and text[i+j]==pattern[j])
		j++;

		if(j==m)return i;
		// THE WASTE: we learned that text[i..i+j-1] equals pattern[0..j-1],
		// then discarded it and restarted from i+1 with j=0.
	}

	return -1;
}
Name the waste before learning the fix. Say we matched j characters and then failed. We now know a lot about the text we just read: it equals the pattern's first j characters. KMP's big idea is that this knowledge depends only on the pattern, not the text. So it can be worked out once, in advance. Here is how it is used. A border is a start of a string that is also its end, but not the whole string (for example, "ab" in "abcab"). If the pattern's first j characters have a border of length k, we can carry on from j = k, without moving i back at all.

Counting the waste. Search for "aaab" (m = 4) in "aaaaaaaaaa" (n = 10). There are 7 start positions. At each one, three as match and then the b fails, so that is 4 comparisons per start and 28 in total. That is roughly n·m. Every start re-reads three characters it has already seen.

A border in action. Search for "ababd" in "ababcabababd", the example in the visualiser below. The first four characters, abab, match. Then the text has c where the pattern wants d. The naive method would restart at text position 1. But abab has the border ab, which is both how it starts and how it ends. So the last two text characters we read, ab, already match the pattern's first two. We keep the text position where it is and set j = 2. Now we compare c with the pattern's a. That also fails, and ab has no border, so j drops to 0 and we move on. Not one text character was read twice.

The small numbers under the pattern are the lps values ("longest prefix that is also a suffix"). Notice that i, the position in the text, never moves backwards during the search.
KMP — prefix function and searchO(n+m)O(m)
// lps[i] = the length of the longest PROPER prefix of pattern[0..i] that is
//          also a suffix of pattern[0..i]. ("Longest prefix suffix.")
// Proper means it cannot be the whole thing, so lps[0] is always 0.
//
// Why it helps: having matched j characters and then failed, the last lps[j-1]
// of them are also a prefix of the pattern — so those are already matched and
// we resume at j = lps[j-1] WITHOUT rewinding the text.
vector<int> buildLPS(string &pattern){
	int m=pattern.size();
	vector<int> lps(m,0);
	int len=0;                      // length of the current border

	for(int i=1;i<m;i++){
		while(len>0 and pattern[i]!=pattern[len])
		len=lps[len-1];            // fall back to a shorter border

		if(pattern[i]==pattern[len])len++;

		lps[i]=len;
	}

	return lps;
}

// Find every occurrence. The text index i NEVER decreases — that is the
// whole guarantee, and it is why the search is linear.
vector<int> kmpSearch(string &text,string &pattern){
	vector<int> ans;

	if(pattern.empty())return ans;

	vector<int> lps=buildLPS(pattern);
	int n=text.size();
	int m=pattern.size();
	int j=0;

	for(int i=0;i<n;i++){
		while(j>0 and text[i]!=pattern[j])
		j=lps[j-1];

		if(text[i]==pattern[j])j++;

		if(j==m){
			ans.push_back(i-m+1);
			j=lps[j-1];              // continue, allowing overlaps
		}
	}

	return ans;
}
The two loops are really the same loop. Building lps is just KMP matching the pattern against itself. That is worth noticing, because it means you only have to remember one piece of code.

The inner while costs O(1) amortised, meaning O(1) on average over the whole run. Here is why. len goes up by at most 1 per step, and each fallback makes it strictly smaller. It cannot go down more times than it went up, so the total number of fallbacks is at most the total number of increases.

After a full match, set j = lps[j-1], not 0. That is what finds matches that overlap. Searching for "aa" in "aaa" should return both 0 and 1.
✍️
My convention: lps and len, and a hand-built table before any code

I name the array lps and the current border length len. "The length of the longest prefix that is also a suffix" is a mouthful, and short names keep the two-line loop readable.

Before writing any code, I build the table by hand for "aabaaab". The answer is 0 1 0 1 2 2 3. Two minutes on paper settles the two things people get wrong. First, the prefix must be proper (not the whole string), so lps[0]=0 always. Second, the fallback goes to lps[len-1], not len-1. It is the same habit as drawing the 3×3 corner of a string-DP table in Chapter 41: work out the rule on paper, then copy it into code.

Building that table step by step. Here is buildLPS on "aabaaab" (positions 0 to 6). len is the length of the border we are trying to extend.

  • i=1 (a): it equals pattern[0], so len becomes 1. lps[1] = 1.
  • i=2 (b): it differs from pattern[1] (a), so fall back: len = lps[0] = 0. It also differs from pattern[0]. lps[2] = 0.
  • i=3 (a): it matches pattern[0], so len = 1. lps[3] = 1.
  • i=4 (a): it matches pattern[1], so len = 2. lps[4] = 2.
  • i=5 (a): it differs from pattern[2] (b), so fall back: len = lps[1] = 1. Now it matches pattern[1], so len = 2. lps[5] = 2.
  • i=6 (b): it matches pattern[2], so len = 3. lps[6] = 3. The prefix aab is also the suffix.

Step i=5 is the one to study. The border aa could not grow into aab. So we tried the next shorter border that is still valid, a, which is lps[len-1], and that one grew. Falling back to len-1 instead would try border lengths that were never checked to be borders at all.

🧠
What the prefix function is good for besides searching
  • Shortest string period (the shortest piece that repeats to build the string). For a string of length n, if n % (n − lps[n−1]) == 0, then n − lps[n−1] is the shortest period. That is how you answer "is this a repeated substring pattern?" in O(n). Example: "abcabc" has lps[5] = 3, and 6 − 3 = 3 divides 6, so "abc" repeated twice builds it. "abcab" has lps[4] = 2, and 5 − 2 = 3 does not divide 5, so it is not a whole number of repeats. One edge case: for "abc", lps[2] = 0 and the "period" is the whole string. That is one copy, not a repeat, so also require lps[n−1] > 0.
  • Longest palindromic prefix. Run the prefix function on s + '#' + reverse(s). The final value is the answer. The separator matters: without it, the border can run across the join and become too long.
  • Shortest palindrome by adding characters to the front. Use the same trick, then add the unmatched tail, reversed, to the front.
  • Count how often every prefix appears in the string, by walking the fallback chain and adding up counts.
  • Repeated substring pattern, rotation check (search b in a+a), and shortest string containing two overlapping pieces.

The # separator trick is worth remembering on its own. It shows up in about half the problems that join two strings. It must be a character that appears in neither string.

The Z-function

The Z-function asks a simpler question at every position: "starting here, how many characters match the start of the string?" Take "aabxaab". At position 1, a matches the first a, then b does not match the second a, so z[1] = 1. At position 4, aab matches the first three characters and then the string ends, so z[4] = 3. That gives 0 1 0 0 3 1 0.

Why copying from earlier is allowed. Suppose you already know that s[l..r) matches the prefix s[0..r−l). That stretch is the "Z-box". Any position i inside the box sits over the same characters as position i−l near the start. So whatever matched at i−l also matches at i, up to the edge of the box. In "aabxaab", after computing z[4] = 3 the box is [4, 7). For i = 5, the matching earlier position is 5 − 4 = 1, and z[1] = 1. So z[5] starts at min(7 − 5, 1) = 1 with no comparisons. One more comparison (a against b) fails, so z[5] = 1. The right edge r only ever moves right, so the total number of extra comparisons is O(n).

Z-function — the same information, differently arrangedO(n)O(n)
// z[i] = the length of the longest substring starting at i that is also a
//        prefix of the whole string. z[0] is left as 0 by convention.
// Example: "aabxaab" -> z = 0 1 0 0 3 1 0
//
// The trick is the "Z-box" [l,r]: the rightmost interval we know matches a
// prefix. Inside it, z values can be COPIED from the corresponding earlier
// position instead of re-compared — that is what makes this linear.
vector<int> zFunction(string &s){
	int n=s.size();
	vector<int> z(n,0);
	int l=0;
	int r=0;

	for(int i=1;i<n;i++){
		if(i<r)z[i]=min(r-i,z[i-l]);   // copy what symmetry gives us

		while(i+z[i]<n and s[z[i]]==s[i+z[i]])
		z[i]++;                        // extend past the box by comparing

		if(i+z[i]>r){
			l=i;
			r=i+z[i];                  // a new, further-right box
		}
	}

	return z;
}

// Search with it: run the Z-function on pattern + '#' + text.
// Any position where z equals the pattern length is an occurrence.
vector<int> zSearch(string &text,string &pattern){
	int m=pattern.size();
	string combined=pattern+'#'+text;
	vector<int> z=zFunction(combined);
	vector<int> ans;

	for(int i=m+1;i<combined.size();i++){
		if(z[i]==m)ans.push_back(i-m-1);
	}

	return ans;
}
Z-function or KMP? Pick whichever one you remember correctly. They solve the same problems in the same time. Z is often easier to think about, because z[i] has a direct meaning: "how far does position i agree with the start?" KMP's border length is more indirect. The only tricky line is min(r-i, z[i-l]). You may copy the earlier value, but never claim more than the box guarantees, because nothing past r has been checked yet. The separator must not appear in either string. If any character could appear, use a special marker value (a sentinel) outside the alphabet instead of a printable character.

Searching with Z, traced. Pattern "ab", text "cabab". The combined string is "ab#cabab" (positions 0 to 7). z[4] = 2, because ab matches, then a meets the # and stops. z[6] = 2 as well. Each z equal to m = 2 is a match, at text index i − m − 1: that gives 4 − 3 = 1 and 6 − 3 = 3. The # is what caps every z value at m. Without it, a z value could run on past the pattern into the text, and "equals m" would stop meaning "one full match".

Rabin-Karp: compare fingerprints

Comparing two strings of length m costs m steps. Comparing two numbers costs one. Rabin-Karp turns each window of text into a number, a hash, and compares numbers. The trick is that the next window's number can be worked out from the previous one in O(1), instead of re-reading all m characters.

Here it is with digits and base 10, so you can see it without the modulus. The text is 31415 and the pattern is 41. The first window is 31. To slide one step right, remove the leading digit's contribution (31 − 3·10 = 1), shift left (1·10 = 10), and add the new digit (10 + 4 = 14). Slide again: 14 − 1·10 = 4, then 4·10 + 1 = 41. That equals the pattern, so there is a match at index 2. Real code does the same with base B = 131 (larger than any character code), and takes % M after every step so the numbers never overflow.

rolling hashO(n+m) expectedO(1)
// Treat a window as a number in base B modulo M. Sliding the window by one
// costs O(1): drop the leading character's contribution, shift, add the new one.
const long long B=131;
const long long M=1000000007;

vector<int> rabinKarp(string &text,string &pattern){
	int n=text.size();
	int m=pattern.size();
	vector<int> ans;

	if(m>n or m==0)return ans;

	long long power=1;

	for(int i=1;i<m;i++)
	power=(power*B)%M;               // B^(m-1), the leading weight

	long long patHash=0;
	long long winHash=0;

	for(int i=0;i<m;i++){
		patHash=(patHash*B+pattern[i])%M;
		winHash=(winHash*B+text[i])%M;
	}

	for(int i=0;i+m<=n;i++){
		// A hash match is only a CANDIDATE — verify the characters.
		if(winHash==patHash and text.compare(i,m,pattern)==0)
		ans.push_back(i);

		if(i+m<n){
			winHash=(winHash-text[i]*power%M+M*M)%M;   // drop the leader
			winHash=(winHash*B+text[i+m])%M;           // shift and add
		}
	}

	return ans;
}
A hash here is a number that acts as a fingerprint for a piece of text. Two rules you must not skip:
  • (1) Check the characters when the hashes match, unless a false match is truly acceptable. Two different strings can share a hash (a collision). Problem setters write "anti-hash" tests designed to cause exactly that.
  • (2) Watch the subtraction. winHash - text[i]*power%M can go negative, and in C++ % keeps the minus sign. So add a multiple of M before the final modulus (Chapter 48).
Rabin-Karp is useful where KMP cannot help: comparing many substrings against each other (finding duplicates, or the longest repeated substring by binary searching its length), and 2D pattern search. Against hostile inputs, use a random base or two different moduli. That makes a collision astronomically unlikely.

How likely is a collision? With one modulus near 10⁹, two particular different strings share a hash with a chance of about 1 in 10⁹. That sounds safe until you compare many windows at once. Put 10⁵ window hashes into a set and there are about 5·10⁹ pairs, so you should expect around 5 false matches. This is the "birthday problem": the chance of some pair matching grows with the square of the count. Two independent moduli multiply the odds together, to about 1 in 10¹⁸ per pair, and the problem goes away.

Hashing any substring in O(1). For "compare many substrings", precompute prefix hashes: h[0] = 0 and h[i+1] = (h[i]·B + s[i]) % M, together with the powers pw[k] = B^k % M. Then the hash of s[l..r) is h[r] − h[l]·pw[r−l], taken mod M and fixed if negative. It works like the digits example. h[r] is the number for the first r characters, and subtracting the first l characters, shifted left by r−l places, leaves just the part from l to r. It is the prefix-sum idea from Chapter 6, applied to base-B numbers.

Manacher: all palindromes in O(n)

A palindrome reads the same forwards and backwards, like "racecar". The simple method tries every centre and expands outwards while both sides match. That is O(n²) when the string is something like "aaaa…a", where every expansion runs a long way. Manacher reaches O(n) by noticing that inside a big palindrome, the right half is a mirror image of the left half. So the palindromes centred on the right side are copies of ones you already measured on the left.

longest palindromic substring in linear timeO(n)O(n)
// Transform "abc" into "^#a#b#c#$" so every palindrome becomes odd-length.
// The sentinels ^ and $ remove all the bounds checks.
// p[i] = the radius of the palindrome centred at i in the transformed string,
//        which is exactly the LENGTH of the palindrome in the original.
string longestPalindrome(string &s){
	if(s.size()<2)return s;

	string t="^";

	for(auto &c:s){
		t+='#';
		t+=c;
	}

	t+="#$";

	int n=t.size();
	vector<int> p(n,0);
	int centre=0;
	int right=0;

	for(int i=1;i<n-1;i++){
		int mirror=2*centre-i;          // i reflected about `centre`

		if(i<right)p[i]=min(right-i,p[mirror]);   // reuse symmetry

		while(t[i+p[i]+1]==t[i-p[i]-1])
		p[i]++;                        // expand (sentinels stop us safely)

		if(i+p[i]>right){
			centre=i;
			right=i+p[i];
		}
	}

	int best=0;
	int bestCentre=0;

	for(int i=1;i<n-1;i++){
		if(p[i]>best){
			best=p[i];
			bestCentre=i;
		}
	}

	int start=(bestCentre-best)/2;

	return s.substr(start,best);
}
It has the same shape as the Z-function. It uses the same min(boundary, mirrored value) reuse, but it mirrors around the centre of a palindrome instead of a prefix box. Putting # between every character makes even-length palindromes odd-length too, so one case handles both. (Handling both cases is the messy part of the simpler expand-around-centre method.) The ^/$ end markers match nothing, so the while loop needs no bounds check.

Be honest about when to use it. Expand-around-centre is O(n²), but it is four lines and O(1) space, and for n ≤ 10⁴ it is the better answer. Use Manacher for n ≥ 10⁵, or when you need every p[i]. Counting all palindromic substrings is then just one sum.

Why the radius equals the original length. Take "abba". It becomes ^#a#b#b#a#$, and the centre of abba is the # between the two bs (position 5). Expanding from there matches b/b, #/#, a/a, #/#, then stops at $ against ^. So p[5] = 4, which is exactly the length of "abba". In general, the expansion always stops with a # at each end, because #s always match each other. So a palindrome of original length L covers its L letters plus L+1 #s: 2L+1 characters in all, which is a radius of exactly L. The start in the original string is (centre − p) / 2 = (5 − 4) / 2 = 0 using integer division, which is correct. An odd palindrome works the same way: in "aba", the centre b gets p = 3.

Why it is linear. Every time the inner while loop succeeds, the palindrome reaches further right than right, so right moves forward. right never moves back and stops at n. So all the expansions together cost O(n), just as the Z-function's r does.

Suffix arrays and LCP — what they buy

A suffix is an ending piece of a string: the suffixes of "banana" are "banana", "anana", "nana" and so on. The suffix array lists all n suffixes in sorted (dictionary) order, stored as their starting positions. You can build it in O(n log n) by "repeated doubling": sort by the first 2ᵏ characters, using the previous round's ranks as keys. More complex methods do it in O(n).

The LCP array ("longest common prefix") stores, for each pair of neighbours in that sorted order, how many starting characters they share. Kasai's algorithm builds it in O(n). Together they answer:

  • Longest repeated substring = the maximum LCP value.
  • Number of distinct substrings = n(n+1)/2 − sum of LCP.
  • Longest common substring of two strings. Join them with a separator, then take the maximum LCP between neighbouring suffixes that come from different strings.
  • Pattern search in O(m log n), by binary searching the sorted suffixes.
  • The k-th substring in dictionary order, and counting substrings below a bound.

In an interview, recognising the tool is nearly always enough. A complete answer sounds like: "This is longest repeated substring. A suffix array with an LCP array solves it in O(n log n). Or a binary search on the length with rolling hashes gets O(n log n) on average, with far less code." The hashing route is the one you can actually finish in the time you have. A suffix automaton or suffix tree is a heavier relative. Just know the names.

Worked example: "banana". Sorted, the suffixes are a (starts at 5), ana (3), anana (1), banana (0), na (4) and nana (2). So the suffix array is [5, 3, 1, 0, 4, 2]. The shared starts of neighbouring pairs are: a/ana 1, ana/anana 3, anana/banana 0, banana/na 0, na/nana 2. That makes the LCP array [1, 3, 0, 0, 2].

  • The largest LCP is 3, from ana and anana. So "ana" is the longest repeated substring. (The two copies overlap, which is allowed.)
  • Every substring is the start of some suffix. The suffixes have lengths 1 to 6, so there are 21 starts in total. Each LCP value counts starts that the previous suffix in sorted order already had. So there are 21 − (1+3+0+0+2) = 15 distinct substrings.

Why do neighbours in sorted order matter? Sorting groups strings with the same start together, as in a dictionary. So the suffix that shares the most with a given suffix is always right next to it.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 lps BY HAND
Build the table for "aabaaab" on paper — it is 0 1 0 1 2 2 3. That settles both traps: the prefix must be proper, and the fallback is lps[len-1], not len-1.
💡 SEPARATOR TRICK
Combining two strings as a + '#' + b and running the prefix or Z function answers a surprising number of problems. The separator must appear in neither string.
⛔ VERIFY HASHES
Equal hashes do not mean equal strings, and setters write anti-hash tests. Verify the characters on a match, or use two independent moduli.
⚠️
Common mistakes
  • Falling back to len-1 instead of lps[len-1]. The whole point is to jump along the chain of borders, not to step down by one.
  • Setting j = 0 after a full KMP match, which misses matches that overlap.
  • Forgetting that lps uses proper prefixes (never the whole string), so lps[0] must be 0.
  • Leaving out the separator in pattern + '#' + text, so a match can run across the join.
  • Using a separator that appears in the input. Pick a marker (sentinel) outside the alphabet.
  • Trusting a hash match without checking the characters, on a problem with anti-hash tests.
  • A negative rolling hash after the subtraction. Add a multiple of M first.
  • A hash base smaller than the alphabet, or a modulus so small that collisions happen all the time. Use about 10⁹, and two moduli when inputs may be hostile.
  • Claiming more than the box guarantees in Z or Manacher. It is min(r-i, z[mirror]), not z[mirror].
  • Forgetting Manacher's end markers (sentinels) and then reading out of bounds in the expand loop.
  • Reaching for a suffix array when binary search plus hashing solves it in a third of the code.

Interview drill

Warm-up: Implement strStr — find the first occurrence of a pattern in a text — in O(n+m). Explain the prefix function.

How a strong answer sounds
The simple scan is O(n·m), and I can point to exactly why. After matching j characters and then failing, it forgets that the last j characters of the text equal the pattern's first j. Then it restarts one position later. KMP keeps that knowledge. The key insight is that what to do on a mismatch depends only on the pattern, so it can be worked out in advance.

I build lps. lps[i] is the length of the longest proper prefix of pattern[0..i] that is also a suffix of it. "Proper" means it cannot be the whole thing, so lps[0] is always 0. During the search, say I have matched j characters and the next one fails. The last lps[j−1] characters I matched are also a prefix of the pattern. So they are already matched, and I carry on from j = lps[j−1] without moving the text index back at all. The text index only ever moves forward, and that is the whole reason the search is linear.

The inner while loop looks like it could be expensive, but it is O(1) amortised (on average). j goes up by at most one per text character, and every fallback makes it smaller. So the total number of fallbacks is at most the total number of increases. Building lps is the same loop, matching the pattern against itself. That is a nice saving: one piece of code, used twice.

I would call out two details. First, after a complete match I set j = lps[j−1], not 0, so overlapping matches are found. Searching "aa" in "aaa" should give both 0 and 1. Second, the fallback is lps[len−1], not len−1. That is the most common bug. I would also sketch the table for "aabaaab" by hand first (0 1 0 1 2 2 3), because two minutes on paper settles both of those.

Deeper: Longest repeated substring in a string of length 10⁵.

How a strong answer sounds
There are two good answers, and I would offer both.

The textbook one is a suffix array plus an LCP array. Sort all n suffixes in O(n log n) by repeated doubling. Then build the LCP array of neighbouring pairs in O(n) with Kasai's algorithm. The answer is simply the largest LCP value. Why? Any repeated substring is a shared start of two suffixes, and the pair that shares the most will sit next to each other in sorted order. That is O(n log n). It also gives me the number of distinct substrings: n(n+1)/2 minus the sum of the LCP array.

The answer I would actually write under time pressure is binary search on the length, plus rolling hashing. The property is monotone (it only flips once): if some substring of length L repeats, then one of length L−1 repeats too, because any prefix of it also repeats. So I can binary search L over [0, n]. For a fixed L, I compute the rolling hash of every window of that length and put them in a hash set. That finds a duplicate in O(n) on average. With precomputed prefix hashes, each window's hash costs O(1). The total is O(n log n) on average.

I would insist on checking any hash match by comparing the actual characters, or on using two independent moduli. Problem setters do write anti-hash tests. And with a single modulus around 32 bits, 10⁵ windows are well within range of the "birthday problem", where collisions become likely.

My honest reason for preferring this route: it is a third of the code, I can get it right in the time available, and it has the same complexity. I would name the suffix array so it is clear I know the standard tool, then build the one I can finish.

🧠 Key takeaways

  • Simple search throws away what it just learned. Every algorithm here reuses that knowledge in a different way.
  • lps[i] is the longest proper prefix that is also a suffix. On a mismatch, fall back to lps[j-1] and never move backwards in the text.
  • The Z-function stores the same information more directly. Both are O(n+m), and either will do.
  • Rolling hashes make comparing two substrings O(1). Check the characters on a match, and watch out for negative values after subtraction.
  • Manacher is the Z-function idea applied to palindrome centres. Expand-around-centre is the better choice when n is small.
  • A suffix array plus LCP is the standard tool for repeated-substring questions, but binary search plus hashing usually gets there with less code.

What does lps[i] store in KMP?

"Proper" (not the whole string) is why lps[0] is always 0. On a mismatch after j matches, the last lps[j-1] characters already form a prefix of the pattern, so you carry on from there.

Why is KMP's search O(n) despite the inner while loop?

j cannot go down more times than it went up. And i only ever moves forward, which is the guarantee the simple version lacks.

In Rabin-Karp, two windows have equal hashes. What must you do?

A hash match is a quick filter, not a proof. Problem setters write anti-hash tests, so check the characters or use two independent moduli.

In the Z-function, why is it z[i] = min(r-i, z[i-l]) rather than just z[i-l]?

Copying the earlier value is only safe inside the box. Manacher has the same line, but it mirrors around a palindrome's centre instead.
