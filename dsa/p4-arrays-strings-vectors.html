Arrays, Strings & Vectors

The array is the most important data structure there is: a row of values side by side in memory, where any position can be reached in one step. Almost every problem in this course starts from one, and most other structures are built on top of them. This chapter teaches C++'s arrays, the vector you'll use instead, 2D grids, and string — with the exact operations, their costs, and the index mistakes that cause most Runtime Errors.

Why arrays are the foundation

An array stores its elements in one continuous block of memory, one after another. Because every element has the same size, the computer can find element i with simple arithmetic: start address + i × element size. No searching, no following links — one step, however large the array. That's what “O(1) random access” means.

The same layout explains the weaknesses. To insert a value at the front of a million-element array, every other element must shift one place right: a million moves, O(n). Searching an unsorted array for a value means checking each element: O(n). And the block has a fixed size — growing it means finding a bigger block and copying everything over.

OperationCostWhy
Read or write a[i]O(1)Address arithmetic, one step
Add or remove at the end (vector)O(1) on averageNothing else moves (see doubling below)
Insert or erase in the middle / frontO(n)Everything after it shifts
Find a value (unsorted)O(n)Check each element
Find a value (sorted)O(log n)Binary search (Ch 7)

Contiguous memory has one more hidden advantage: reading elements in order is extremely fast, because the CPU fetches memory in chunks and predicts what you'll read next. That's why a simple loop over an array often beats fancier structures in practice. Chapter 3 shows what's really happening in memory.

Plain arrays vs vector

C++ has two kinds of array. The plain (C-style) array has a fixed size set when you write the code. A vector is an array that knows its own size, can grow and shrink, starts at zero if you ask it to, and cleans up after itself. Use vector by default.

int a[5];                               // fixed size 5; a LOCAL array starts with garbage
int b[5]={};                            // all zeros
vector<int> v(5,0);                     // five zeros: [0,0,0,0,0]
vector<int> w={3,1,4};                   // from a list of values
vector<long long> big(n);                 // n zeros, size chosen at run time
  • Indexes start at 0. A vector of size n has valid indexes 0 to n-1.
  • C++ does not check the index. v[n] reads whatever memory comes next — garbage, or a crash (Runtime Error). v.at(i) does check and throws an error, which is handy while debugging.
  • A large plain array declared inside a function can overflow the small stack and crash before your code runs. A vector keeps its elements on the heap, where there's plenty of room. P6 explains stack and heap.

Working with a vector

vector<int> v;
v.push_back(7);          // [7]         add to the end, O(1) on average
v.push_back(2);          // [7,2]
v.push_back(9);          // [7,2,9]
v.size();               // 3
v.back();               // 9           the last element
v.pop_back();           // [7,2]       remove the last, O(1)
v.empty();              // false
v.insert(v.begin(),5);  // [5,7,2]     insert at the front: O(n), everything shifts
v.erase(v.begin()+1);   // [5,2]       erase index 1: O(n)
v.assign(4,-1);          // [-1,-1,-1,-1]  refill
v.resize(6);             // [-1,-1,-1,-1,0,0]  grow (new slots are 0)
v.clear();              // []          size 0

v.begin() is an iterator — a marker for the first element — and v.end() marks one past the last. Pairs of them describe a range: sort(v.begin(),v.end()) sorts the whole vector. You'll meet iterators properly in P5.

How push_back stays fast: doubling

If a vector's memory block is full, where does the next element go? The vector allocates a bigger block — typically twice the size — copies every element across, and frees the old one. That copy is expensive, but because the size doubles each time, it happens rarely. Try it:

size vs capacitySimulator
Blue = elements in use (the size); dashed = reserved but unused (the capacity). Watch the total copies stay below 2 × the number of pushes: the copying costs 1 + 2 + 4 + … which is less than twice the final size. So each push_back is O(1) on average — called amortised O(1) (Chapter 2).

If you know the final size in advance, v.reserve(n) allocates it all at once and skips the copying. It's a small speed-up, rarely needed — but it also explains a nasty bug: a pointer or iterator to an element becomes invalid when the vector reallocates, because the element has moved.

2D vectors and grids

Many problems give you a grid: a maze, a map of islands, a game board, a DP table. In C++ that's a vector of vectors:

int R=3,C=4;
vector<vector<int>> grid(R,vector<int>(C,0));   // R rows, each with C zeros
grid[1][2]=9;                                    // row 1, column 2
for(int r=0;r<R;r++){
	for(int c=0;c<C;c++)
	cout<<grid[r][c]<<" ";
	cout<<"\n";
}

The first index is the row (going down), the second the column (going across). Mixing them up is the classic grid bug. The next most common task is visiting a cell's neighbours without writing four near-identical if blocks. The trick is a pair of direction arrays:

int dr[]={-1,1,0,0};             // up, down, left, right
int dc[]={0,0,-1,1};
for(int k=0;k<4;k++){
	int nr=r+dr[k],nc=c+dc[k];
	if(nr<0 or nr>=R or nc<0 or nc>=C)continue;   // off the grid: skip
	// (nr,nc) is a valid neighbour
}

Click a corner or an edge cell: some directions fall off the grid, and the bounds check skips them. Forgetting that check is the most common Runtime Error in grid problems. Chapter 34 builds full grid algorithms on this.

Strings

A string is a sequence of characters that behaves like a vector<char>, with extra text-specific tools. Each character is a char — a small number (P2).

string s="hello";
s.size();                 // 5
s[0];                      // 'h'
s+='!';                    // "hello!"  append one char: O(1) on average
s+=" world";               // append a string
s.substr(1,3);            // "ell"     3 characters starting at index 1: O(length)
s.find("lo");              // 3         first position, or string::npos if absent
reverse(s.begin(),s.end());  // reverse in place
sort(s.begin(),s.end());     // sort the characters: "listen" -> "eilnst"
string t=to_string(42);    // "42"
int x=stoi("123");          // 123       (stoll for long long)
bool less=("apple"<string("banana"));   // true: dictionary order

The hidden O(n²): s=s+c

s+=c appends in place, O(1) on average. But s=s+c first builds a brand-new string containing all of s plus c, then copies it back — O(length of s) every time. Build a 10⁵-character answer that way and you've done about 5 × 10⁹ character copies: TLE. Always use += (or push_back) inside loops. The same trap hides in substr inside a loop, and in passing strings by value.

Common string checks lean on character arithmetic: isdigit(ch), isalpha(ch), tolower(ch), and counting letters with a 26-slot array indexed by ch-'a'. Checking whether two words are anagrams, for example, is just comparing their two letter-count arrays. Chapter 10 is all about string techniques.

Off-by-one and out-of-range errors

Most Runtime Errors and a surprising number of Wrong Answers come from getting one index wrong by one. A few habits prevent almost all of them:

SituationWrongRight
Loop over all indexesfor(i=0;i<=n;i++)for(i=0;i<n;i++)
Compare neighbours a[i], a[i+1]i<n (reads a[n])i+1<n
Last elementa[n]a[n-1] or a.back() — after checking non-empty
Count of elements from l to r inclusiver-lr-l+1
Loop backwardsfor(unsigned i=n-1;i>=0;i--) (never ends)for(int i=n-1;i>=0;i--)

The single best defence is a dry run on a tiny input: n = 1 and n = 2. If your loop reads a[1] when n = 1, you'll see it in seconds on paper. The second-best is the sanitizer build from P1, which stops the program at the exact line that reads out of range.

⚠️
Common mistakes
  • Reading v[n] or v[-1]. No error message, just garbage or a crash. Valid indexes are 0 … n − 1.
  • Calling back(), front() or pop_back() on an empty vector. Check !v.empty() first.
  • Swapping row and column in a grid. grid[r][c]: row first. And check bounds before indexing a neighbour.
  • s=s+c in a loop. Quadratic. Use s+=c.
  • Erasing from the front of a vector in a loop. Each erase is O(n). Use an index, or a deque (Ch 14).
  • Keeping a pointer or iterator into a vector, then pushing to it. Reallocation moves the elements and the old pointer dangles.

Interview drill

Explain it simply: Why is push_back on a vector O(1) if the vector sometimes has to copy all its elements?

How a strong answer sounds
Because the capacity doubles each time it runs out. Copies happen only at sizes 1, 2, 4, 8, …, so after n pushes the total copying is 1 + 2 + 4 + … up to n, which is less than 2n. Spread over n pushes, that's under 2 copies each — constant on average. Any single push can be slow, but the average — the amortised cost — is O(1).

Spot the bug: for(int i=0;i<n;i++) if(a[i]==a[i+1]) dup=true;

How a strong answer sounds
On the last round, i = n − 1, so a[i+1] reads a[n], one past the end — undefined behaviour, garbage or a crash. The loop should run while i+1<n. I'd also add a guard for n ≤ 1, where there are no neighbouring pairs at all.

🧠 Key takeaways

  • Arrays are contiguous: a[i] is O(1); inserting or erasing in the middle is O(n); searching unsorted is O(n).
  • Use vector: it knows its size, grows with push_back, and keeps elements on the heap.
  • push_back is amortised O(1) because capacity doubles; reallocation invalidates pointers and iterators.
  • Grids are vector<vector<int>>, indexed [row][col]; visit neighbours with direction arrays and a bounds check.
  • Strings are vectors of chars: +=, substr, find, reverse, sort, stoi, to_string. Never s=s+c in a loop.
  • Valid indexes are 0 … n − 1; compare neighbours with i+1<n; dry-run n = 1 and n = 2.

Check your understanding

What is the cost of v.insert(v.begin(),x) on a vector of n elements?

Inserting at the front forces all n elements to move right by one. Adding at the end with push_back is the cheap operation.

vector<vector<int>> g(3,vector<int>(5)); — which access is valid?

There are 3 rows (indexes 0–2) and 5 columns (indexes 0–4). Only g[2][4] is inside both ranges.

What does string("dynamic").substr(2,3) return?

Indexes: d0 y1 n2 a3 m4 i5 c6. Starting at index 2, take 3 characters: n, a, m.

You build a string of length 10⁵ with ans=ans+c; inside a loop. What's the problem?

ans+c creates a temporary copy of all of ans each time: about 1 + 2 + … + n ≈ 5 × 10⁹ character copies. ans+=c appends in place, amortised O(1).

A vector grows from 0 to 1,000 elements with push_back, doubling capacity when full. Roughly how many element copies happen in total because of reallocation?

Copies happen when capacity runs out at 1, 2, 4, …, 512: 1 + 2 + 4 + … + 512 = 1,023. That's below 2 × 1,000, which is why push_back is amortised O(1).
