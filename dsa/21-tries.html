Tries & Prefix Structures

A hash map can tell you whether a word exists. It cannot tell you whether any word starts with “alg” without checking all of them. A trie makes the prefix the first-class citizen: search cost depends on the length of the query, not on how many words you stored. And the same structure over the bits of integers solves maximum-XOR problems that look impossible otherwise.

  • Build a trie with insert, search and startsWith, and know the exact space cost
  • Explain why isEnd is necessary and what breaks without it
  • Use a trie for autocomplete, word search and wildcard matching
  • Build a binary trie and solve maximum XOR pair in O(n·32)
  • Know when a trie is the wrong answer and a hash map wins

The structure

Each node represents a prefix. Its children are indexed by the next character, so walking the tree spells a word. Two consequences follow immediately: shared prefixes are stored once, and finding a prefix costs only its own length.

struct TrieNode{
	TrieNode* children[26];
	bool isEnd;

	TrieNode(){
	isEnd=false;
	for(int i=0;i<26;i++)
	children[i]=nullptr;
}
};

class Trie{
	TrieNode* root;

	// Walk as far as the string goes; return nullptr if the path breaks.
	TrieNode* walk(string &s){
		TrieNode* node=root;

		for(char c:s){
			int i=c-'a';

			if(!node->children[i])return nullptr;

			node=node->children[i];
		}

		return node;
	}

public:
	Trie(){ root=new TrieNode(); }

	void insert(string &word){
		TrieNode* node=root;

		for(char c:word){
			int i=c-'a';

			if(!node->children[i])
			node->children[i]=new TrieNode();

			node=node->children[i];
		}

		node->isEnd=true;        // THE line that distinguishes a word from a prefix
	}

	bool search(string &word){
		TrieNode* node=walk(word);

		return node and node->isEnd;   // must be an ENDPOINT, not just reachable
	}

	bool startsWith(string &prefix){
		return walk(prefix)!=nullptr;   // reachable is enough
	}
};
search and startsWith differ by exactly one condition — whether the endpoint flag matters. Without isEnd, inserting "apple" would make search("app") return true, because the path exists. That one boolean is the entire difference between "a word lives here" and "a word passes through here".
✍️
My convention: factor out the walk helper

search and startsWith share their entire body except the final check, so the walk goes in a private helper and both public methods become one line. This is the skeleton-reuse rule (Chapter 1) applied to a class: if two methods differ only in their last line, the shared part is a helper. It also means there is only one place a null check can be forgotten.

💾
The space cost is real — count it honestly

A fixed children[26] array is 26 pointers = 208 bytes per node on a 64-bit system, plus the bool. For 10⁵ words of average length 10, that is up to 10⁶ nodes and ~200 MB. Three ways to cut it:

  • unordered_map<char,TrieNode*> per node — pays only for children that exist. Better for sparse tries and for alphabets larger than 26; worse constant factor per step.
  • A compressed trie (radix tree) — collapse any chain of single-child nodes into one node holding a whole substring. Dramatic savings on real dictionaries.
  • Do not use a trie. If you only need exact lookup, a hash set is O(1) and uses a fraction of the memory. The trie earns its cost only when prefixes matter.

The one-sentence test

If the problem never says “prefix”, “starts with”, “autocomplete”, or “shared beginning”, you probably do not want a trie. Every row where the trie wins above is a prefix question. For exact membership, a hash set wins on constant factor and memory by a wide margin — and saying that out loud before building a trie is a genuine signal.

Wildcard search and word search

WordDictionary — search with a . wildcardO(26^dots × L)O(L) recursion
// A dot matches any character, so at a dot we must try every existing child.
// Helper + driver, with the index carried as a parameter.
bool match(TrieNode* node,string &word,int i){
	if(!node)return false;
	if(i==word.size())return node->isEnd;

	char c=word[i];

	if(c!='.')
	return match(node->children[c-'a'],word,i+1);

	// wildcard: branch into every child that exists
	for(int k=0;k<26;k++){
		if(node->children[k] and match(node->children[k],word,i+1))
		return true;
	}

	return false;
}
Only existing children are tried, so the real branching factor is the trie's actual density, not 26. The worst case is exponential in the number of dots, which is why problems cap them — but notice that the trie still prunes enormously compared to scanning a word list, because a failed prefix kills an entire subtree at once.
🔍
Word Search II: the trie turns an intractable grid search tractable

Given a grid and a list of 10⁴ words, find which words appear. Searching the grid once per word is 10⁴ separate DFS runs. Instead, put all the words in a trie and DFS the grid once, carrying a trie pointer alongside the grid position: at each cell, if the current character has no child in the trie, that entire branch of the search dies immediately. One grid traversal prunes against all 10⁴ words simultaneously. This is the canonical demonstration of what a trie is for — it lets you fail fast against a whole dictionary at once, and the same idea underlies Aho-Corasick below.

The binary trie: maximum XOR

A trie does not need to be over letters. Store the bits of integers, most significant first, and each node has two children. This makes a problem that looks quadratic into a linear one.

The problem: given an array, find the maximum XOR of any two elements. Brute force is O(n²). With a binary trie it is O(n·32).

findMaximumXOR with a binary trieO(n·32)O(n·32)
struct BitNode{
	BitNode* child[2];

	BitNode(){
	child[0]=nullptr;
	child[1]=nullptr;
}
};

void insert(BitNode* root,int x){
	BitNode* node=root;

	for(int b=31;b>=0;b--){          // MOST significant bit first
		int bit=(x>>b)&1;

		if(!node->child[bit])
		node->child[bit]=new BitNode();

		node=node->child[bit];
	}
}

// Greedy: at each bit, prefer the OPPOSITE branch, because setting a higher
// bit is worth more than every lower bit combined (2^b > 2^b - 1).
int bestXor(BitNode* root,int x){
	BitNode* node=root;
	int ans=0;

	for(int b=31;b>=0;b--){
		int bit=(x>>b)&1;
		int want=1-bit;                // the bit that would give us a 1 in the XOR

		if(node->child[want]){
			ans|=(1<<b);              // we got the 1
			node=node->child[want];
		}else{
			node=node->child[bit];       // forced into the same branch
		}
	}

	return ans;
}

int findMaximumXOR(vector<int> &a){
	BitNode* root=new BitNode();
	int best=0;

	for(int x:a){
		insert(root,x);                  // insert first, so x can pair with itself?
		best=max(best,bestXor(root,x));    // x^x = 0, so it never wins — safe
	}

	return best;
}
Why the greedy is optimal: a 1 at bit position b contributes 2^b, which is strictly greater than the sum of all lower bits (2^b − 1). So securing a 1 at the highest possible position always beats any combination of lower bits — there is no trade-off to consider, which is what makes a single top-down pass correct. This same "high bit dominates" argument reappears throughout Chapter 47.
🧩
The binary-trie family
  • Maximum XOR of two numbers — the version above.
  • Maximum XOR subarray — build prefix XORs (Chapter 6), then this is maximum XOR of two prefixes.
  • Count pairs with XOR less than K — descend counting, storing a subtree count per node.
  • Maximum XOR with an element ≤ limit — sort queries and insert incrementally.

All four are the same trie with a different descent rule. Once you have written insert and one query, the rest are variations.

Aho-Corasick, briefly

A trie finds one pattern at a time. Aho-Corasick adds failure links — like KMP's prefix function (Chapter 50) generalised to a whole dictionary — so a single pass over the text finds every occurrence of every pattern in O(text + total pattern length + matches).

🔗
The idea in one paragraph

Build a trie of all patterns. For each node, compute a failure link to the deepest other node whose string is a proper suffix of this node's string — computed level by level with BFS, exactly as KMP computes its table. Now scan the text one character at a time: if the current node has a child for that character, follow it; otherwise follow failure links until one does (or you reach the root). Because a failure link never loses a match that is still possible, you never re-read a character, and every pattern ending at the current position is found by walking the chain of failure links upward. It is used in spam filters, intrusion detection, DNA search and grep -F with multiple patterns — anywhere you must match thousands of fixed strings in one pass. Know what it is and what it buys; full implementation is beyond what interviews ask.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 CHILDREN AS ARRAY
For a lowercase alphabet use Node* next[26], not a map. It is faster, simpler, and the size is a constant you can afford.
💡 TRIE + GRID DFS
Word Search II is one DFS over the grid walking a trie of all words simultaneously. Searching each word separately is the trap; the trie prunes whole branches at once.
💡 BINARY TRIE FOR XOR
Maximum-XOR problems are a trie over bits, most significant first, greedily taking the opposite bit at each level. Recognising that is the entire difficulty.
⚠️
Common mistakes
  • Omitting isEnd. Then search("app") returns true after inserting only "apple", because the path exists.
  • Returning node != nullptr from search. That is startsWith. The two differ by exactly one condition.
  • Not initialising the children array. 26 garbage pointers, and the first traversal follows one.
  • Using a trie for exact membership only. A hash set is faster and far smaller. Justify the trie with a prefix requirement.
  • Ignoring the memory cost. 26 pointers per node is 208 bytes; a million nodes is 200 MB. Use a map per node or a compressed trie if it matters.
  • Iterating all 26 children at a wildcard without a null check. Dereferencing null children instead of skipping them.
  • Inserting bits least-significant-first in a binary trie. The greedy needs the most significant bit at the top, or the "higher bit dominates" argument does not apply.
  • Forgetting to un-mark the grid cell after a DFS in word search. Visited marking needs the same undo as backtracking (Chapter 35).
  • Leaking the trie. Every new TrieNode needs a recursive delete, or use smart pointers.

Interview drill

Warm-up: Why use a trie instead of a hash set of strings?

How a strong answer sounds
For exact membership, I would not — a hash set is O(L) to hash then O(1) to look up, with a much better constant factor and a fraction of the memory. The trie earns its place when prefixes matter. "Does any stored word start with 'alg'?" is O(3) in a trie and O(n·L) in a hash set, because hashing destroys the relationship between a string and its prefixes. Same for listing every word with a given prefix, finding the longest common prefix of a set, iterating in sorted order, or wildcard matching — all of those exploit the fact that a trie node is a prefix and its subtree is every word extending it. I would also mention the space trade honestly: a fixed 26-pointer array is about 208 bytes per node, so a million nodes is 200 MB, and the fixes are a hash map per node for sparse alphabets or a compressed radix tree that collapses single-child chains. The rule I use is simple: if the problem statement never mentions a prefix or a shared beginning, a trie is probably the wrong tool.

Deeper: Find the maximum XOR of any two numbers in an array, better than O(n²).

How a strong answer sounds
Build a binary trie over the 32-bit representations, most significant bit first, so each node has two children indexed by the next bit. For each number I insert it and then query for the partner that maximises the XOR. The query is greedy: at each bit from the top down, I want the XOR bit to be 1, so I try to descend into the child holding the opposite bit; if it exists I take it and set that bit in my answer, otherwise I am forced into the same-bit child and that XOR bit is 0. That greedy is optimal because a 1 at position b is worth 2^b, which strictly exceeds the sum of every lower bit, 2^b − 1 — so there is never a reason to give up a high bit to gain lower ones, which is why one top-down pass suffices with no backtracking. Each insert and each query is 32 steps, so it is O(n·32) time and O(n·32) space, effectively linear. Ordering detail: inserting before querying is fine because a number XORed with itself is 0, which can never be the maximum unless all values are equal, in which case 0 is the right answer anyway. The same trie extends to maximum XOR subarray by running it over prefix XORs, and to counting pairs below a threshold by storing subtree counts.

🧠 Key takeaways

  • A trie node is a prefix, so prefix queries cost the prefix length rather than the dictionary size.
  • isEnd is what separates "a word ends here" from "a word passes through here"; search and startsWith differ only in checking it.
  • Space is 26 pointers per node — use a map per node or a compressed trie, or use a hash set if prefixes do not matter.
  • A trie over a dictionary lets one grid DFS prune against every word simultaneously (Word Search II).
  • A binary trie over bits, most significant first, solves maximum XOR in O(n·32) because a higher bit always dominates.

Check your understanding

You insert "apple" into a trie and then call search("app"). Without an isEnd flag, what happens?

Walking "app" succeeds because those nodes exist as part of "apple". isEnd is the single boolean that distinguishes "a word ends here" from "a word passes through here".

Which problem does a trie solve that a unordered_set<string> cannot do efficiently?

O(|prefix|) in a trie versus O(n·L) in a hash set, because hashing destroys the relationship between a string and its prefixes. Every problem where a trie wins is a prefix question.

In a binary trie for maximum XOR, why insert bits from the most significant downward?

2^b > 2^b − 1, so securing a high bit can never be worth trading for any set of lower bits. That strict domination is what licenses a single top-down greedy pass.

Roughly how much memory does one trie node with TrieNode* children[26] use on a 64-bit system?

26 × 8 = 208 bytes of pointers regardless of how many children exist. A million nodes is roughly 200 MB — which is why sparse tries use a map per node or collapse chains into a compressed radix tree.

In Word Search II (a grid plus 10⁴ words), why is a trie the key optimisation?

Without it you run 10⁴ independent searches. With it, a single traversal prunes against the whole dictionary simultaneously — failing fast against many patterns at once is what a trie is for.
