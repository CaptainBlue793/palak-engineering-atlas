Tries & Prefix Structures

A hash map can tell you whether a word exists. But it cannot tell you whether any word starts with “alg” unless it checks every word. A trie (a prefix tree, said like "try") is built around the prefix: the cost of a search depends on how long your query is, not on how many words you stored. The same structure, built over the bits of integers, also solves maximum-XOR problems that look impossible otherwise.

The structure

Each node stands for a prefix (the first few letters of a word). Its children are labelled by the next character, so walking down the tree spells out a word. Two things follow right away. Words that share a beginning share those nodes, so the shared part is stored once. And finding a prefix costs only as many steps as the prefix is long.

Trace it with three words. Insert "car": the root has no c child, so create one, then a under it, then r, and mark the r node as a word end. That is 3 new nodes. Insert "cat": c and a already exist, so just follow them, and create only t. 1 new node. Insert "care": follow c, a, r, create e, mark it. 1 new node. Eleven characters were inserted, but the trie holds only 5 nodes below the root. Now startsWith("ca") takes 2 steps, whether the trie holds 3 words or 3 million.

Where this shows up: search-box autocomplete, spell checkers, IP routing tables (longest matching prefix of an address), and interview problems that mention prefixes or a dictionary of words.

Trie — insert, search, startsWithO(L) per opO(total chars × 26)
struct TrieNode{
	TrieNode* children[26];
	bool isEnd;

	TrieNode(){
	isEnd=false;
	for(int i=0;i<26;i++)
	children[i]=nullptr;
}
};

class Trie{
	TrieNode* root;

	// Walk as far as the string goes; return nullptr if the path breaks.
	TrieNode* walk(string &s){
		TrieNode* node=root;

		for(char c:s){
			int i=c-'a';

			if(!node->children[i])return nullptr;

			node=node->children[i];
		}

		return node;
	}

public:
	Trie(){ root=new TrieNode(); }

	void insert(string &word){
		TrieNode* node=root;

		for(char c:word){
			int i=c-'a';

			if(!node->children[i])
			node->children[i]=new TrieNode();

			node=node->children[i];
		}

		node->isEnd=true;        // THE line that distinguishes a word from a prefix
	}

	bool search(string &word){
		TrieNode* node=walk(word);

		return node and node->isEnd;   // must be an ENDPOINT, not just reachable
	}

	bool startsWith(string &prefix){
		return walk(prefix)!=nullptr;   // reachable is enough
	}
};
search and startsWith differ by exactly one check: whether the endpoint flag has to be set. Without isEnd, inserting "apple" would make search("app") return true, because the path down to "app" exists. That one flag is the whole difference between "a word ends here" and "a word only passes through here".
✍️
My convention: factor out the walk helper

search and startsWith have the same body except for the final check. So the walking part goes in a private helper, and both public methods become one line. This is the reuse-the-skeleton rule from Chapter 1, applied to a class: if two methods differ only in their last line, put the shared part in a helper. It also means there is only one place where you could forget a null check.

💾
The space cost is real — count it honestly

A fixed children[26] array holds 26 pointers. On a 64-bit system that is 208 bytes per node, plus the bool. For 10⁵ words averaging 10 letters, that is up to 10⁶ nodes and about 200 MB. Three ways to cut it down:

  • An unordered_map<char,TrieNode*> in each node. You only pay for children that actually exist. Better when the trie is sparse or the alphabet is bigger than 26, but each step is slower.
  • A compressed trie (radix tree). Squash any chain of nodes that each have one child into a single node holding a whole piece of text. On real dictionaries this saves a lot.
  • Don't use a trie at all. If you only need exact lookups, a hash set is O(1) and uses far less memory. A trie is worth its cost only when prefixes matter.

How autocomplete uses this. To list every word starting with P, first walk down P (|P| steps). If the walk breaks, there are no such words. Otherwise, every word with that prefix lives in the subtree under that node, so a DFS of that subtree collects them. Visiting children in order a to z even gives them alphabetically. With "car", "cat", "care" stored, the prefix "car" leads to the r node; the DFS reports "car" (it is marked as an end) and then "care". "cat" is in a different subtree and is never touched. Real autocomplete usually wants only the top 3 suggestions, so it stops the DFS early or keeps a small list of the best words at each node.

🎯
The one-sentence test

If the problem never says “prefix”, “starts with”, “autocomplete”, or “shared beginning”, you probably don't want a trie. Every row where the trie wins above is a prefix question. For plain "is this word in the set?", a hash set is much faster and much smaller. Saying that out loud before you build a trie shows you know why you are building it.

Wildcard search and word search

A wildcard . means "any one letter". Trace search("ca.") on the trie holding "car", "cat", "care". Follow c, then a. At the dot, try each child that exists: r is first. The pattern is now used up, so ask "is this node a word end?" Yes ("car"), so return true. If the pattern were "c.re", the dot would try a (the only child of c), then r, then e, and succeed on "care". A hash set would have to test the pattern against every stored word.

WordDictionary — search with a . wildcardO(26^dots × L)O(L) recursion
// A dot matches any character, so at a dot we must try every existing child.
// Helper + driver, with the index carried as a parameter.
bool match(TrieNode* node,string &word,int i){
	if(!node)return false;
	if(i==word.size())return node->isEnd;

	char c=word[i];

	if(c!='.')
	return match(node->children[c-'a'],word,i+1);

	// wildcard: branch into every child that exists
	for(int k=0;k<26;k++){
		if(node->children[k] and match(node->children[k],word,i+1))
		return true;
	}

	return false;
}
Only children that exist are tried, so in practice you branch into far fewer than 26 paths. The worst case grows exponentially with the number of dots, which is why problems limit how many there are. Even so, the trie cuts out far more work than scanning a word list, because a prefix that fails removes a whole subtree at once.
🔍
Word Search II: the trie turns an intractable grid search tractable

You are given a grid and a list of 10⁴ words, and you must find which words appear in the grid. Searching the grid once per word means 10⁴ separate DFS runs. Instead, put all the words in a trie and run one DFS over the grid, carrying a trie pointer along with your grid position. At each cell, if the letter there has no matching child in the trie, that whole branch of the search stops right away. One walk over the grid rules out all 10⁴ words at once. This is the clearest example of what a trie is for: it lets you give up early against a whole dictionary at the same time. The same idea is behind Aho-Corasick below.

The binary trie: maximum XOR

A trie doesn't have to store letters. Store the bits of integers instead, starting with the highest bit, and each node has just two children (0 and 1). That turns a problem that looks quadratic into a linear one.

The problem: given an array, find the largest XOR you can get from any two of its values. (XOR compares two numbers bit by bit and gives a 1 where the bits differ.) Checking every pair is O(n²). With a binary trie it is O(n·32).

A quick XOR example: 6 is 110 in binary and 3 is 011. Comparing bit by bit: 1 vs 0 differ (1), 1 vs 1 match (0), 0 vs 1 differ (1). So 6 XOR 3 = 101 = 5. To make an XOR big, you want the two numbers to differ in the highest bits possible.

Now a full trace with 4-bit numbers. The array is [3, 10, 5]: 3 = 0011, 10 = 1010, 5 = 0101. All three are in the trie; find the best partner for 5.

  • Bit 3 (worth 8): 5 has 0 here, so we want a 1. Only 10 starts with 1, so go that way. Answer so far 1000.
  • Bit 2 (worth 4): 5 has 1, we want 0. Down this path (only 10), bit 2 is 0. Take it. 1100.
  • Bit 1 (worth 2): 5 has 0, we want 1. 10 has 1. 1110.
  • Bit 0 (worth 1): 5 has 1, we want 0. 10 has 0. 1111 = 15.

Check: 5 XOR 10 = 15, and 5 XOR 3 = 6, so 10 really is the best partner. Notice the first step did most of the work: once bit 3 was set, no path without it could win, since 8 beats 4 + 2 + 1 = 7.

findMaximumXOR with a binary trieO(n·32)O(n·32)
struct BitNode{
	BitNode* child[2];

	BitNode(){
	child[0]=nullptr;
	child[1]=nullptr;
}
};

void insert(BitNode* root,int x){
	BitNode* node=root;

	for(int b=31;b>=0;b--){          // MOST significant bit first
		int bit=(x>>b)&1;

		if(!node->child[bit])
		node->child[bit]=new BitNode();

		node=node->child[bit];
	}
}

// Greedy: at each bit, prefer the OPPOSITE branch, because setting a higher
// bit is worth more than every lower bit combined (2^b > 2^b - 1).
int bestXor(BitNode* root,int x){
	BitNode* node=root;
	int ans=0;

	for(int b=31;b>=0;b--){
		int bit=(x>>b)&1;
		int want=1-bit;                // the bit that would give us a 1 in the XOR

		if(node->child[want]){
			ans|=(1<<b);              // we got the 1
			node=node->child[want];
		}else{
			node=node->child[bit];       // forced into the same branch
		}
	}

	return ans;
}

int findMaximumXOR(vector<int> &a){
	BitNode* root=new BitNode();
	int best=0;

	for(int x:a){
		insert(root,x);                  // insert first, so x can pair with itself?
		best=max(best,bestXor(root,x));    // x^x = 0, so it never wins — safe
	}

	return best;
}
Why grabbing the best bit first is always right: a 1 at bit position b is worth 2^b, and all the lower bits added together only reach 2^b − 1. So getting a 1 at the highest possible position always beats any mix of lower bits. There is no trade-off to weigh, which is why one pass from the top down is correct. The same "the higher bit wins" argument comes back throughout Chapter 47.

The binary-trie family
  • Maximum XOR of two numbers — the version above.
  • Maximum XOR subarray. Build prefix XORs (Chapter 6), and the problem becomes the maximum XOR of two prefixes.
  • Count pairs with XOR less than K. Store how many numbers are under each node, then count as you walk down.
  • Maximum XOR with an element ≤ some limit. Sort the queries and insert numbers into the trie as you go.

All four use the same trie with a different rule for walking down it. Once you have written insert and one query, the rest are small changes.

Aho-Corasick, briefly

A plain trie matches one pattern at a time. Aho-Corasick adds failure links: shortcuts that say where to continue when the current match breaks. It is KMP's prefix function (Chapter 50) extended to a whole dictionary. With them, one pass over the text finds every occurrence of every pattern in O(text + total pattern length + matches).

A small example. The patterns are "he", "she", "his" and "hers", and the text is "ushers". After reading "ush" then "e", you are at the trie node for "she", so "she" matches. But "he" also ends at that same position, and nothing on the current path says so. The failure link of "she" points to "he" (the longest ending of "she" that is also in the trie), and following it reports "he" too. Then reading "r" and "s" continues from "he" to "her" and "hers", a third match. One left-to-right pass found all three, without restarting at each position of the text.

🔗
The idea in one paragraph

Build a trie of all the patterns. For each node, work out its failure link: it points to the deepest other node whose string is a suffix (an ending) of this node's string. You compute these level by level with BFS, just as KMP builds its table. Now scan the text one character at a time. If the current node has a child for that character, follow it. If not, follow failure links until one does, or until you reach the root. A failure link never throws away a match that could still succeed, so you never read a character twice. Every pattern that ends at the current position is found by following the chain of failure links upward. This runs inside spam filters, intrusion detection, DNA search and grep -F with many patterns — anywhere you must match thousands of fixed strings in one pass. Know what it is and what it gives you; writing the full thing is more than interviews ask for.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 CHILDREN AS ARRAY
For a lowercase alphabet use Node* next[26], not a map. It is faster, simpler, and the size is a constant you can afford.
💡 TRIE + GRID DFS
Word Search II is one DFS over the grid walking a trie of all words simultaneously. Searching each word separately is the trap; the trie prunes whole branches at once.
💡 BINARY TRIE FOR XOR
Maximum-XOR problems are a trie over bits, most significant first, greedily taking the opposite bit at each level. Recognising that is the entire difficulty.
⚠️
Common mistakes
  • Leaving out isEnd. Then search("app") returns true after you insert only "apple", because the path exists.
  • Returning node != nullptr from search. That is what startsWith does. The two differ by exactly one check.
  • Not setting the children array to null. You get 26 junk pointers, and the first walk down the trie follows one.
  • Using a trie only to check membership. A hash set is faster and far smaller. Use a trie when the problem needs prefixes.
  • Ignoring the memory cost. 26 pointers per node is 208 bytes, so a million nodes is 200 MB. Use a map in each node, or a compressed trie, if that matters.
  • Looping over all 26 children at a wildcard without checking for null. You follow null children instead of skipping them.
  • Inserting bits lowest-first in a binary trie. The greedy needs the highest bit at the top, or the "higher bit wins" argument doesn't hold.
  • Forgetting to un-mark a grid cell after the DFS in word search. Marking cells as visited needs the same undo as backtracking (Chapter 35).
  • Leaking memory. Every new TrieNode needs a matching recursive delete, or use smart pointers.

Interview drill

Warm-up: Why use a trie instead of a hash set of strings?

How a strong answer sounds
For plain membership checks, I wouldn't. A hash set costs O(L) to hash and then O(1) to look up, it is much faster in practice, and it uses a fraction of the memory. A trie earns its place when prefixes matter. "Does any stored word start with 'alg'?" takes 3 steps in a trie and O(n·L) in a hash set, because hashing throws away any link between a string and its prefixes. The same goes for listing every word with a given prefix, finding the longest common prefix of a set, walking the words in sorted order, or wildcard matching. All of those use the fact that a trie node is a prefix, and everything in its subtree is a word that extends it. I would also be honest about space: a fixed 26-pointer array is about 208 bytes per node, so a million nodes is 200 MB. The fixes are a hash map in each node when the alphabet is sparse, or a compressed radix tree that squashes single-child chains. My rule is simple: if the problem never mentions a prefix or a shared beginning, a trie is probably the wrong tool.

Deeper: Find the maximum XOR of any two numbers in an array, better than O(n²).

How a strong answer sounds
I build a binary trie over the numbers' 32 bits, highest bit first, so each node has two children, one for bit 0 and one for bit 1. For each number, I insert it and then ask the trie for the partner that gives the biggest XOR. The query is greedy. At each bit from the top down, I want the XOR bit to be 1, so I try to go into the child holding the opposite bit. If that child exists, I take it and set that bit in my answer. If not, I am forced into the same-bit child, and that XOR bit is 0. This greedy is best possible because a 1 at position b is worth 2^b, and all the lower bits together only add up to 2^b − 1. So there is never a reason to give up a high bit to win lower ones, and one pass from the top works with no backtracking. Each insert and each query is 32 steps, so it is O(n·32) time and O(n·32) space, which is effectively linear. One ordering detail: inserting before querying is fine, because a number XORed with itself is 0, which can never be the maximum unless every value is equal, and then 0 is the right answer anyway. The same trie handles maximum XOR subarray, by running it over prefix XORs, and counting pairs below a threshold, by storing how many numbers sit under each node.

🧠 Key takeaways

  • A trie node is a prefix, so a prefix query costs the length of the prefix, not the size of the dictionary.
  • isEnd separates "a word ends here" from "a word only passes through here". search and startsWith differ only in whether they check it.
  • Each node costs 26 pointers. Use a map in each node or a compressed trie, or use a hash set if prefixes don't matter.
  • A trie of the whole dictionary lets one grid DFS rule out every word at the same time (Word Search II).
  • A binary trie over bits, highest bit first, solves maximum XOR in O(n·32), because a higher bit always outweighs the lower ones.

Check your understanding

You insert "apple" into a trie and then call search("app"). Without an isEnd flag, what happens?

Walking "app" works because those nodes exist as part of "apple". isEnd is the single flag that separates "a word ends here" from "a word only passes through here".

Which problem does a trie solve that a unordered_set<string> cannot do efficiently?

It is O(|prefix|) in a trie versus O(n·L) in a hash set, because hashing throws away the link between a string and its prefixes. Every problem where a trie wins is a prefix question.

In a binary trie for maximum XOR, why insert bits from the most significant downward?

2^b > 2^b − 1, so giving up a high bit is never worth any set of lower bits. Because a high bit always wins, one greedy pass from the top is enough.

Roughly how much memory does one trie node with TrieNode* children[26] use on a 64-bit system?

26 × 8 = 208 bytes of pointers, no matter how many children actually exist. A million nodes is roughly 200 MB. That is why sparse tries use a map in each node, or squash chains into a compressed radix tree.

In Word Search II (a grid plus 10⁴ words), why is a trie the key optimisation?

Without it, you run 10⁴ separate searches. With it, one walk of the grid rules out the whole dictionary at once. Giving up early against many patterns at the same time is what a trie is for.
