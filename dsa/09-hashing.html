Hashing: Maps, Sets & Frequency

A hash map buys you O(1) “have I seen this?” for the price of order, and that trade is the single most common optimisation in interview problems — it is what turns a nested loop into one pass. This chapter builds the table from scratch so the O(1) stops being magic, then covers the frequency-map family, the ordered-versus-unordered decision, and how to hash your own key types.

  • Explain how a hash table achieves O(1) expected lookup, and when it degrades to O(n)
  • Choose between map, unordered_map, and a plain array — and know why the array usually wins
  • Apply the four frequency-map patterns: counting, seen-before, complement, and grouping
  • Write a custom hash for a pair or a struct
  • Avoid the operator[] trap that silently inserts elements

How the O(1) actually works

A hash table is an array plus a function. The function turns a key into an index; the array holds the values. That is the whole idea, and everything else is damage control for the fact that the function is not injective.

Hash the key

h = hash(key) produces a large integer. A good hash spreads similar keys far apart, so "cat" and "cab" do not land together.

Fold it into the table

index = h % bucketCount. One modulo, O(1). This is where two different keys can collide — the table has far fewer buckets than there are possible keys.

Resolve the collision

Chaining: each bucket holds a small list; walk it comparing keys. Open addressing: probe the next slot until you find the key or an empty one. Chaining is what std::unordered_map is required to do.

Rehash when it gets crowded

When size / buckets (the load factor) exceeds ~1, allocate a larger table and re-insert everything. Amortized O(1) by the same doubling argument as push_back (Chapter 2) — and it invalidates every iterator.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 COMPLEMENT
For two-sum, look up target − x before inserting x. That ordering is what stops an element pairing with itself, and it removes the need for a second pass.
💡 COUNT-STRING KEY
For grouping anagrams, a 26-length count string is an O(L) key against O(L log L) for sorting. Same grouping, better complexity, and it generalises to larger alphabets.
⛔ ITERATION ORDER
Never rely on the order of an unordered_map. It varies between runs and compilers, and a test that depends on it will pass locally and fail on the judge.
💥
O(1) is expected, and an adversary can take it away

Try the “adversarial” mode above. If every key hashes to the same bucket, the table becomes one linked list and every lookup is O(n) — so n inserts is O(n²). This is not hypothetical: competitive programming judges have inputs specifically crafted against std::unordered_map's default integer hash (which on libstdc++ is the identity function, so multiples of the bucket count all collide). The fix is to mix the key with a random salt before hashing, or to use map, which is O(log n) guaranteed and cannot be attacked this way.

✍️
My convention: if the key is a bounded integer, use a vector

Counting characters? vector<int> count(26,0), not unordered_map<char,int>. Counting node visits in a graph with N nodes? vector<bool> visited(N,false), not a set. Same complexity, roughly 10× the speed, no hashing, no allocation, no adversarial worst case, and the code is shorter. The hash map is for when the key space is genuinely large or genuinely sparse. You will notice every graph chapter in this course uses vector<bool> visited for exactly this reason.

🪤
operator[] inserts. This is the most expensive footgun in the STL.
unordered_map<int,int> m;
m[1]=10;

if(m[5]==0){}           // m now CONTAINS key 5, value 0. size() is 2.
int x=m[7];              // and now key 7 too. size() is 3.

// Safe ways to read without inserting:
if(m.count(5)){}          // C++11 and later
if(m.contains(5)){}       // C++20, clearest
auto it=m.find(5);
if(it!=m.end()){}         // and it->second is the value

This breaks code in two ways. Obviously, when you iterate the map afterwards and find keys you never inserted. Subtly, when you are inside a loop over the map and operator[] triggers a rehash — which invalidates the iterator you are standing on. Read with count/find, write with [].

The four frequency patterns

Almost every hash-map problem is one of these. Name the pattern and the code follows.

// Count occurrences, then answer questions about the counts.
// Most frequent, majority element, k most frequent, first unique.
int majorityElement(vector<int> &a){
	unordered_map<int,int> count;

	for(int x:a){
		count[x]++;

		if(count[x]>a.size()/2)return x;
	}

	return -1;
}
// Note: Boyer-Moore voting solves this in O(1) space. Mention it as the follow-up.

The map here costs O(n) space. When the key is a character, drop to vector<int> count(26,0); when it is a bounded integer, a vector sized to the range.

// "Has this appeared already?" A set, not a map, when you need no count.
bool containsDuplicate(vector<int> &a){
	unordered_set<int> seen;

	for(int x:a){
		if(seen.count(x))return true;

		seen.insert(x);
	}

	return false;
}
// insert() returns a pair whose .second says whether it was new:
// if(!seen.insert(x).second)return true;   -- one lookup instead of two

The set version of "seen" is also how you detect a cycle in a linked list with O(n) space — worth mentioning before giving Floyd's O(1) answer from Chapter 4.

// Store what you have seen; look up what you NEED.
// This is the pattern that kills the nested loop.
vector<int> twoSum(vector<int> &a,int target){
	unordered_map<int,int> seen;      // value -> index

	for(int i=0;i<a.size();i++){
		int need=target-a[i];

		if(seen.count(need))
		return {seen[need],i};       // look up BEFORE inserting

		seen[a[i]]=i;
	}

	return {};
}

Query before you insert. Otherwise an element pairs with itself when target = 2*a[i]. Same ordering rule as the prefix-sum map in Chapter 6 — and unlike two pointers, this version keeps the original indices.

// Map a canonical key to every item sharing it.
// Group anagrams, group by remainder, group by shape.
vector<vector<string>> groupAnagrams(vector<string> &words){
	unordered_map<string,vector<string>> groups;

	for(string &w:words){
		string key=w;
		sort(key.begin(),key.end());   // canonical form: O(L log L)

		groups[key].push_back(w);
	}

	vector<vector<string>> ans;
	for(auto &it:groups)
	ans.push_back(it.second);

	return ans;
}
// Faster key: a 26-length count string. O(L) instead of O(L log L).

The skill is choosing the canonical key. Sorted letters for anagrams. value % k for remainder groups. A normalised shape string for isomorphic structures. Pick the key and the problem collapses.

Hashing your own types

unordered_map needs a hash for its key. The STL provides one for integers, strings and pointers — but not for pair or vector, which is the most common surprise in graph and grid problems.

three ways to key on a pairpick the simplest that fits
// 1. EASIEST: use map, which only needs operator< — pair already has it.
map<pair<int,int>,int> m;        // O(log n), zero extra code

// 2. BEST when coordinates are bounded: flatten to a single integer.
// A grid cell (r,c) with cols columns becomes r*cols+c. Now the key is an int.
unordered_map<int,int> flat;
flat[r*cols+c]=5;
// For unbounded ints, pack into 64 bits: ((long long)r<<32)^(unsigned)c

// 3. When you really need a pair key in an unordered container:
struct PairHash{
	size_t operator()(const pair<int,int> &p)const{
		// Do NOT write h1 ^ h2 — that collides for every (a,b) and (b,a).
		size_t h1=hash<int>{}(p.first);
		size_t h2=hash<int>{}(p.second);

		return h1^(h2+0x9e3779b9+(h1<<6)+(h1>>2));   // boost's hash_combine
	}
};
unordered_map<pair<int,int>,int,PairHash> um;
h1 ^ h2 is the classic mistake. XOR is symmetric, so (3,7) and (7,3) hash identically — and (x,x) hashes to 0 for every x. The magic constant 0x9e3779b9 is the golden ratio in fixed point; combined with the shifts it destroys that symmetry. In practice, option 2 is what you want: flattening is faster and simpler than any custom hash.
🛡️
Anti-hack hash for competitive programming
struct SafeHash{
	size_t operator()(long long x)const{
		static const long long salt=chrono::steady_clock::now().time_since_epoch().count();
		x+=salt;
		x=(x^(x>>30))*0xbf58476d1ce4e5b9;
		x=(x^(x>>27))*0x94d049bb133111eb;
		return x^(x>>31);
	}
};

Because the salt comes from the clock, nobody can precompute colliding keys for your submission. This is splitmix64, and it is what experienced competitive programmers paste in whenever they use unordered_map with integer keys.

⚠️
Common mistakes
  • Using m[key] to test membership. It inserts a default-constructed value. Use count, find or contains.
  • Inserting before querying in the complement pattern. The element pairs with itself when target = 2*a[i].
  • Holding an iterator across an insert. A rehash invalidates every iterator in the container. (References to values survive in unordered_map, but iterators do not.)
  • Erasing while iterating without using the return value. Write it = m.erase(it), not m.erase(it); ++it;.
  • Using unordered_map when you need order. Iteration order is unspecified and differs between runs, compilers and insertion histories.
  • XOR-combining hashes. Symmetric, so (a,b) and (b,a) collide and (x,x) hashes to zero.
  • Using a hash map where a vector would do. Small integer keys belong in an array: same complexity, far smaller constant, no worst case.
  • Claiming O(1) without saying “expected”. Interviewers listen for this word.

Interview drill

Warm-up: When would you choose map over unordered_map?

How a strong answer sounds
Four situations. First, when I need the keys in sorted order — iterating a map gives ascending order for free, whereas unordered_map's order is unspecified and varies between runs. Second, when I need range operations: lower_bound, upper_bound, "the largest key below x", which a hash table simply cannot do because hashing destroys adjacency. Third, when I need a worst-case guarantee — map is O(log n) always, while unordered_map is O(1) only in expectation and degrades to O(n) under adversarial or unlucky keys. Fourth, when the key type has a natural operator< but no hash, like pair or vector, where map works with no extra code at all. Otherwise I default to unordered_map for the better constant — and if the keys happen to be small bounded integers, I skip both and use a vector, which beats them on every axis.

Deeper: Your unordered_map solution times out on a judge but passes locally. Why, and what do you do?

How a strong answer sounds
Almost certainly an anti-hash test. The default hash for integers in libstdc++ is the identity function, and the bucket count is a prime the implementation picks predictably — so an adversary can generate keys that are all congruent modulo that prime, put every key in one bucket, and turn each lookup into a linear chain walk. n inserts then cost O(n²), which passes on my random local data and dies on theirs. There is also a benign version of the same symptom: rehashing plus cache-hostile pointer chasing can make a hash map several times slower than expected even without collisions. Fixes, in the order I would try them: if the keys are bounded integers, replace the map with a vector — that removes the problem entirely and is faster anyway; otherwise add a splitmix64 custom hash salted from chrono::steady_clock, so the mapping is unpredictable per run and cannot be precomputed against; failing that, switch to map and accept a guaranteed O(n log n). I would also call reserve up front to remove the rehashing, which is a cheap win regardless of the cause.

🧠 Key takeaways

  • A hash table is an array plus a function; O(1) is expected, and adversarial keys collapse it to O(n).
  • operator[] inserts on read — use count, find or contains to test membership.
  • Four patterns cover almost everything: count, seen-before, complement (query then insert), and group-by-canonical-key.
  • For a bounded integer key, a vector beats any hash map — same complexity, far better constant, no worst case.
  • Never XOR hashes together; flatten coordinates to one integer, or use map, before writing a custom hash.

Check your understanding

What does if(m[5] == 0) do to an unordered_map<int,int> that has no key 5?

operator[] default-constructs a value for a missing key and returns a reference to it. Use count, find or contains to read. This also means a read inside a loop over the map can trigger a rehash and invalidate your iterator.

You are counting the frequency of lowercase letters in a string. Best container?

The key space is 26 bounded integers, so an array is a perfect hash: one indexed load, no hashing, no allocation, no collisions, and it iterates in alphabetical order anyway. This is why every graph chapter uses vector<bool> visited rather than a set.

In the hash-map two-sum, why look up the complement before inserting the current element?

With a=[3,4] and target=6, inserting 3 first means the lookup for 6−3=3 finds the element you just added and returns [0,0]. Query, then insert — the same ordering rule as the prefix-sum map.

Why is combining two hashes with h1 ^ h2 a bad idea?

Both properties create mass collisions exactly where coordinate pairs are common. Use hash_combine with the golden-ratio constant and shifts, or better, flatten the pair into a single integer key.

Your unordered_map solution passes locally but times out on a judge. Most likely cause?

libstdc++ hashes integers with the identity function and uses a predictable bucket count, so keys congruent to that modulus all collide. Fix with a clock-salted splitmix64 hash, a vector, or map. (Missing reserve is a real but much smaller cost.)
