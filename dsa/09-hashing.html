Hashing: Maps, Sets & Frequency

A hash map answers “have I seen this before?” in O(1) time. The price is that it forgets order. That trade is the most common speed-up in interview problems: it is what turns a nested loop into a single pass. This chapter builds a hash table from scratch, so the O(1) stops feeling like magic. Then it covers the frequency-map patterns, how to choose between ordered and unordered maps, and how to hash your own key types.

  • Choose between map, unordered_map, and a plain array — and know why the array usually wins
  • Apply the four frequency-map patterns: counting, seen-before, complement, and grouping
  • Write a custom hash for a pair or a struct
  • Avoid the operator[] trap that silently inserts elements

How the O(1) actually works

Why this matters: many problems ask “does some earlier element pair up with this one?”. The naive answer is a nested loop that compares every pair — O(n²). With n = 100,000 that is 10 billion comparisons, far too slow. If you could ask “have I seen value v?” in O(1), one pass would do: 100,000 steps. The hash table is the tool that answers that question in O(1).

A hash table is just an array plus a function. The function turns a key into an index, and the array stores the values at that index. Think of a coat check: your ticket number tells the attendant exactly which hook to go to, so nobody searches the whole rack.

That is the whole idea. Everything else deals with one problem: two different keys can map to the same index (the function is not injective, meaning it is not one-to-one).

A small example by hand. Use 8 buckets and the simple hash index = key % 8. Insert 12: 12 % 8 = 4, so it goes in bucket 4. Insert 7: bucket 7. Insert 20: 20 % 8 = 4 — bucket 4 again. That is a collision, so bucket 4 now holds a short list [12, 20]. To look up 20 later, you compute 20 % 8 = 4, go straight to bucket 4, and compare against just those two keys. You never touch the other buckets. As long as the lists stay short, every lookup is a constant amount of work.

Hash the key

h = hash(key) turns the key into a large integer. A good hash sends similar keys to very different numbers, so "cat" and "cab" do not end up together.

Fold it into the table

index = h % bucketCount. One modulo, so O(1). Each slot is called a bucket. This step is where two different keys can collide (land in the same bucket), because there are far fewer buckets than possible keys.

Resolve the collision

Chaining: each bucket holds a small list, and you walk it comparing keys. Open addressing: you try the next slot, and the next, until you find the key or an empty slot. std::unordered_map is required to use chaining.

Rehash when it gets crowded

The load factor is size / buckets, the average number of keys per bucket. When it goes above about 1, the table allocates a bigger array and re-inserts everything. This is amortized O(1) (cheap on average across many inserts), by the same doubling argument as push_back in Chapter 2. The catch: a rehash invalidates every iterator, so any iterator you were holding now points at garbage.

Continuing the example: with 8 buckets, the 9th key pushes the load factor past 1. The table grows to 16 buckets and re-inserts every key using % 16. Now 12 goes to bucket 12 and 20 goes to bucket 4, so the old collision disappears. Keys must be re-placed because their bucket depends on the bucket count. The rehash costs O(n), but it happens only after the table has doubled, so spread over all the inserts it adds a constant amount per insert. If you know roughly how many keys are coming, m.reserve(n) sizes the table up front and skips the rehashes entirely.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 COMPLEMENT
For two-sum, look up target − x before inserting x. That ordering is what stops an element pairing with itself, and it removes the need for a second pass.
💡 COUNT-STRING KEY
For grouping anagrams, a 26-length count string is an O(L) key against O(L log L) for sorting. Same grouping, better complexity, and it generalises to larger alphabets.
⛔ ITERATION ORDER
Never rely on the order of an unordered_map. It varies between runs and compilers, and a test that depends on it will pass locally and fail on the judge.
💥
O(1) is expected, and an adversary can take it away

Try the “adversarial” mode above. If every key lands in the same bucket, the table turns into one long linked list. Every lookup becomes O(n), so n inserts cost O(n²).

This really happens. Competitive programming judges include inputs built to attack std::unordered_map's default integer hash. On libstdc++ (GCC's standard library) that hash is the identity function: it returns the number unchanged. So all multiples of the bucket count land in the same bucket.

There are two fixes. Mix the key with a random salt (a secret random value) before hashing. Or use map, which is O(log n) guaranteed and cannot be attacked this way.

✍️
My convention: if the key is a bounded integer, use a vector

Counting characters? Use vector<int> count(26,0), not unordered_map<char,int>. Tracking visited nodes in a graph with N nodes? Use vector<bool> visited(N,false), not a set.

The complexity is the same, but the array is roughly 10× faster. There is no hashing, no memory allocation, no adversarial worst case, and the code is shorter. Save the hash map for when the possible keys are truly huge or truly sparse (only a few of them actually appear). That is why every graph chapter in this course uses vector<bool> visited.

🪤
operator[] inserts. This is the most expensive footgun in the STL.
unordered_map<int,int> m;
m[1]=10;

if(m[5]==0){}           // m now CONTAINS key 5, value 0. size() is 2.
int x=m[7];              // and now key 7 too. size() is 3.

// Safe ways to read without inserting:
if(m.count(5)){}          // C++11 and later
if(m.contains(5)){}       // C++20, clearest
auto it=m.find(5);
if(it!=m.end()){}         // and it->second is the value

This breaks code in two ways. The obvious one: you loop over the map later and find keys you never meant to add. The sneaky one: you are inside a loop over the map, operator[] adds a key, the table rehashes, and the iterator you are using becomes invalid. Rule: read with count/find, write with [].

The four frequency patterns

Almost every hash-map problem is one of these four. Once you name the pattern, the code mostly writes itself.

  • Count — the question is about how many times something appears (“most frequent”, “first unique”).
  • Seen before — the question is yes/no: has this exact value appeared already? A set is enough.
  • Complement — you need a partner for the current element (“two values summing to target”). You look up the partner, not the element itself.
  • Group by key — items that are “the same” in some sense (anagrams, same remainder) must be collected together.
// Count occurrences, then answer questions about the counts.
// Most frequent, majority element, k most frequent, first unique.
int majorityElement(vector<int> &a){
	unordered_map<int,int> count;

	for(int x:a){
		count[x]++;

		if(count[x]>a.size()/2)return x;
	}

	return -1;
}
// Note: Boyer-Moore voting solves this in O(1) space. Mention it as the follow-up.

Why can it return early? A value that appears more than n/2 times is unique — two different values cannot both fill more than half the array. So the first count to cross n/2 is the answer. For [2, 2, 1, 2], n/2 = 2, and the count of 2 reaches 3 at index 3.

The map here uses O(n) extra space. If the key is a letter, use vector<int> count(26,0) instead. If it is an integer with a known range, use a vector sized to that range.

// "Has this appeared already?" A set, not a map, when you need no count.
bool containsDuplicate(vector<int> &a){
	unordered_set<int> seen;

	for(int x:a){
		if(seen.count(x))return true;

		seen.insert(x);
	}

	return false;
}
// insert() returns a pair whose .second says whether it was new:
// if(!seen.insert(x).second)return true;   -- one lookup instead of two

The same "seen" set also detects a cycle in a linked list, using O(n) space. In an interview, mention it first, then give Floyd's O(1)-space answer from Chapter 4.

// Store what you have seen; look up what you NEED.
// This is the pattern that kills the nested loop.
vector<int> twoSum(vector<int> &a,int target){
	unordered_map<int,int> seen;      // value -> index

	for(int i=0;i<a.size();i++){
		int need=target-a[i];

		if(seen.count(need))
		return {seen[need],i};       // look up BEFORE inserting

		seen[a[i]]=i;
	}

	return {};
}

Look up before you insert. Otherwise an element can pair with itself when target = 2*a[i]. It is the same ordering rule as the prefix-sum map in Chapter 6. And unlike the two-pointer approach, this version keeps the original indices, because it never sorts.

Dry run on a = [3, 2, 4], target = 6. i = 0: need 3, the map is empty, so store 3→0. i = 1: need 4, not there, store 2→1. i = 2: need 2, found at index 1, return {1, 2}. Now see what goes wrong if you insert first: at i = 0 you store 3→0, then look up need = 3, find it, and return {0, 0} — the 3 paired with itself.

// Map a canonical key to every item sharing it.
// Group anagrams, group by remainder, group by shape.
vector<vector<string>> groupAnagrams(vector<string> &words){
	unordered_map<string,vector<string>> groups;

	for(string &w:words){
		string key=w;
		sort(key.begin(),key.end());   // canonical form: O(L log L)

		groups[key].push_back(w);
	}

	vector<vector<string>> ans;
	for(auto &it:groups)
	ans.push_back(it.second);

	return ans;
}
// Faster key: a 26-length count string. O(L) instead of O(L log L).

The real skill is choosing the canonical key: one standard form that every item in a group shares. Sorted letters for anagrams. value % k for remainder groups. A normalised shape string for structures with the same shape. Pick the right key and the problem becomes easy.

Example: for ["eat","tea","tan","ate","nat"] the sorted keys are aet, aet, ant, aet, ant. So the map ends up as aet → [eat, tea, ate] and ant → [tan, nat]. Two words are anagrams exactly when they share a key, so the map does the grouping for you.

Hashing your own types

unordered_map needs a hash function for its key type. The STL (C++'s standard library) gives you one for integers, strings and pointers. It does not give you one for pair or vector. That surprises people all the time in graph and grid problems.

three ways to key on a pairpick the simplest that fits
// 1. EASIEST: use map, which only needs operator< — pair already has it.
map<pair<int,int>,int> m;        // O(log n), zero extra code

// 2. BEST when coordinates are bounded: flatten to a single integer.
// A grid cell (r,c) with cols columns becomes r*cols+c. Now the key is an int.
unordered_map<int,int> flat;
flat[r*cols+c]=5;
// For unbounded ints, pack into 64 bits: ((long long)r<<32)^(unsigned)c

// 3. When you really need a pair key in an unordered container:
struct PairHash{
	size_t operator()(const pair<int,int> &p)const{
		// Do NOT write h1 ^ h2 — that collides for every (a,b) and (b,a).
		size_t h1=hash<int>{}(p.first);
		size_t h2=hash<int>{}(p.second);

		return h1^(h2+0x9e3779b9+(h1<<6)+(h1>>2));   // boost's hash_combine
	}
};
unordered_map<pair<int,int>,int,PairHash> um;
h1 ^ h2 is the classic mistake. XOR gives the same result in either order, so (3,7) and (7,3) get the same hash. Worse, (x,x) hashes to 0 for every x. The magic constant 0x9e3779b9 is the golden ratio written as a fixed-point number; together with the shifts, it breaks that symmetry. In practice, option 2 is what you want: flattening is faster and simpler than any custom hash.

Why flattening is safe. In a grid with cols = 5, cell (2, 3) becomes 2×5 + 3 = 13. No other cell can give 13, because the column is always between 0 and 4: you can get the pair back with r = 13 / 5 = 2 and c = 13 % 5 = 3. A value that can be decoded back into exactly one pair is a perfect key. The one thing to check is size: with up to 10⁵ rows and 10⁵ columns, r×cols + c can reach 10¹⁰, which does not fit in an int, so use long long.

Which option to pick. Coordinates with known limits: flatten (option 2). A small number of keys, or you want sorted order anyway: map (option 1). A key you cannot flatten — say, three unbounded integers — and speed matters: write a hash (option 3).

🛡️
Anti-hack hash for competitive programming
struct SafeHash{
	size_t operator()(long long x)const{
		static const long long salt=chrono::steady_clock::now().time_since_epoch().count();
		x+=salt;
		x=(x^(x>>30))*0xbf58476d1ce4e5b9;
		x=(x^(x>>27))*0x94d049bb133111eb;
		return x^(x>>31);
	}
};

The salt comes from the clock, so it is different on every run. That means nobody can prepare colliding keys for your submission in advance. This hash is called splitmix64. Experienced competitive programmers paste it in whenever they use unordered_map with integer keys.

⚠️
Common mistakes
  • Using m[key] to test membership. It quietly inserts a default value (0 for int). Use count, find or contains.
  • Inserting before looking up in the complement pattern. The element pairs with itself when target = 2*a[i].
  • Keeping an iterator across an insert. A rehash invalidates every iterator in the container. (References to the values stay valid in unordered_map, but iterators do not.)
  • Erasing while looping without using the return value. Write it = m.erase(it), not m.erase(it); ++it;.
  • Using unordered_map when you need order. Its order is unspecified. It can change between runs, compilers and the order you inserted things.
  • Combining hashes with XOR. XOR ignores order, so (a,b) and (b,a) collide, and (x,x) hashes to zero.
  • Using a hash map where a vector would do. Small integer keys belong in an array: same complexity, much smaller constant, no worst case.
  • Saying O(1) without saying “expected”. Interviewers listen for this word.

Interview drill

Warm-up: When would you choose map over unordered_map?

How a strong answer sounds
In four situations. First, when I need the keys in sorted order. Looping over a map gives ascending order for free; unordered_map's order is unspecified and changes between runs. Second, when I need range operations like lower_bound, upper_bound, or "the largest key below x". A hash table cannot do these, because hashing scatters neighbouring keys. Third, when I need a worst-case guarantee. map is always O(log n), while unordered_map is O(1) only on average and falls to O(n) with adversarial or unlucky keys. Fourth, when the key type has an operator< but no hash, like pair or vector. Then map works with no extra code. Otherwise I default to unordered_map because it is faster in practice. And if the keys are small integers with a known range, I skip both and use a vector, which beats them in every way.

Deeper: Your unordered_map solution times out on a judge but passes locally. Why, and what do you do?

How a strong answer sounds
Almost certainly an anti-hash test. In libstdc++ the default integer hash is the identity function, and the bucket count is a prime chosen in a predictable way. So an attacker can pick keys that all leave the same remainder when divided by that prime. Every key lands in one bucket, and each lookup becomes a walk down one long chain. n inserts then cost O(n²). My random local data never triggers this; their test does. There is also an innocent version of the same symptom: rehashing, plus pointer-chasing that is unfriendly to the CPU cache, can make a hash map several times slower than expected even with no collisions. Fixes, in the order I would try them. If the keys are integers with a known range, replace the map with a vector. That removes the problem entirely and is faster anyway. Otherwise, add a splitmix64 custom hash salted from chrono::steady_clock, so the mapping changes every run and cannot be attacked in advance. Failing that, switch to map and accept a guaranteed O(n log n). I would also call reserve up front to avoid rehashing, which is a cheap win whatever the cause.

🧠 Key takeaways

  • A hash table is an array plus a function. Its O(1) is expected (on average); keys chosen by an attacker can push it to O(n).
  • operator[] inserts even when you only meant to read. Use count, find or contains to test membership.
  • Four patterns cover almost everything: count, seen-before, complement (look up, then insert), and group by a canonical key.
  • For an integer key with a known small range, a vector beats any hash map: same complexity, much faster, no worst case.
  • Never combine hashes with XOR. Before writing a custom hash, try flattening coordinates into one integer, or just use map.

Check your understanding

What does if(m[5] == 0) do to an unordered_map<int,int> that has no key 5?

For a missing key, operator[] creates a default value (0 here) and returns a reference to it. Use count, find or contains to read. It also means a "read" inside a loop over the map can trigger a rehash and invalidate your iterator.

You are counting the frequency of lowercase letters in a string. Best container?

There are only 26 possible keys, so an array works as a perfect hash. Each access is one read by index: no hashing, no allocation, no collisions. It even loops in alphabetical order. This is why every graph chapter uses vector<bool> visited instead of a set.

In the hash-map two-sum, why look up the complement before inserting the current element?

With a=[3,4] and target=6, inserting 3 first means the lookup for 6−3=3 finds the element you just added and returns [0,0]. Look up first, then insert. It is the same ordering rule as the prefix-sum map.

Why is combining two hashes with h1 ^ h2 a bad idea?

Both properties cause lots of collisions, and they hit exactly the coordinate pairs that are common in grid problems. Use hash_combine with the golden-ratio constant and shifts. Better still, flatten the pair into a single integer key.

Your unordered_map solution passes locally but times out on a judge. Most likely cause?

libstdc++ hashes integers with the identity function and picks a predictable bucket count. So keys with the same remainder modulo that count all collide. Fix it with a clock-salted splitmix64 hash, a vector, or map. (A missing reserve is a real cost, but a much smaller one.)
