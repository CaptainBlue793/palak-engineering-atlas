Bipartite Graphs & Coloring

Imagine splitting a class into two teams so that no two rivals end up on the same team. A graph is bipartite if you can split its nodes into two groups like that, with no edge inside a group. The test is a quick DFS or BFS: give each node one of two colours as you go, and fail if two neighbours end up with the same colour. What makes this chapter worth its own slot is the theorem behind it. Bipartite means exactly “has no odd-length cycle”. That fact lets you spot bipartite problems that never mention colours at all.

  • Write the two-colouring check with both DFS and BFS
  • Prove that a graph is bipartite exactly when it has no odd-length cycle
  • Use one colour array with three states, so you can tell unvisited, colour 0 and colour 1 apart
  • Recognise problem wordings that are really bipartite checks in disguise
  • Know why colouring with k colours is NP-hard in general, while k = 2 takes linear time

The definition, and the theorem

A graph is bipartite if you can paint every node one of two colours so that every edge joins two different colours. Put another way: split the nodes V into two groups A and B, so that every edge goes from one group to the other.

Two tiny examples make it concrete. A square 0–1–2–3–0 is bipartite: put A = {0, 2} and B = {1, 3}, and each of the four edges crosses between the groups. A triangle 0–1–2–0 is not: give 0 colour A, then 1 must be B, then 2 must be A (it touches 1), but 2 also touches 0, which is A. Whatever you try, one edge ends up inside a group.

Why it matters: many real questions are "can these be split into two sides?" — two shifts where certain workers cannot share a shift, two rooms for exams that clash, jobs on one side and applicants on the other. Bipartite graphs are also the setting for matching problems (Chapter 33), so being able to check the property quickly comes up again later.

🧾
Bipartite ⟺ no odd cycle

(⇒) A bipartite graph has no odd cycle. Walk around a cycle. Every edge flips the colour, so after k edges you have flipped k times. When you get back to the start, you must be on the starting colour again, and that needs an even number of flips. So every cycle has even length.

(⇐) A graph with no odd cycle is bipartite. Run BFS from any node. Colour each node by the parity of its BFS distance: even distance gets one colour, odd distance the other. Now suppose some edge u—v joined two nodes of the same colour. That means dist(u) and dist(v) are both even or both odd. Go from the start to u, cross the edge u—v, then go from v back to the start. That round trip has length dist(u) + 1 + dist(v), which is odd. A round trip of odd length always contains an odd cycle. That contradicts our assumption, so no such edge exists and the parity colouring works.

Why an odd round trip must contain an odd cycle. A round trip (a closed walk) may pass through the same node twice, so it is not always a cycle itself. If it does repeat a node, cut it at that node into two smaller round trips. Their lengths add up to the original odd length, and two numbers that add to an odd number cannot both be even — so one of the pieces is odd. Keep cutting the odd piece. It gets shorter each time, so eventually it has no repeated node, and that piece is an odd cycle.

This proof is the algorithm. Colouring by BFS parity is exactly what the code below does, and the conflict it detects is exactly this odd round trip.

DFS colouring

The algorithm is "colour one node, then every neighbour must get the other colour, and check for clashes". Dry run on the square 0–1–2–3–0 (adjacency 0 → [1,3], 1 → [0,2], 2 → [1,3], 3 → [2,0]):

  1. The driver finds node 0 uncoloured and gives it colour 0.
  2. From 0: neighbour 1 is uncoloured, so give it 1 - 0 = 1 and go there. From 1: neighbour 0 has colour 0, which differs from 1, fine. Neighbour 2 is uncoloured, give it 0.
  3. From 2: neighbour 1 has colour 1, fine. Neighbour 3 is uncoloured, give it 1. From 3: neighbour 2 has 0, fine; neighbour 0 has 0, fine.
  4. Everything returns true. Colours [0, 1, 0, 1]: bipartite.

On the triangle 0–1–2–0 the same steps give 0 → colour 0, 1 → colour 1, 2 → colour 0. Then from 2 we check neighbour 0: it already has colour 0, the same as 2. That is the conflict, and the function returns false.

bipartite — DFSO(V + E)O(V)
// colors[x] is -1 (unvisited), 0 or 1. Three states in one array, so we
// need no separate visited array — the colour IS the visited marker.
bool DFS(unordered_map<int,vector<int>> &graph,int node,vector<int> &colors){
	for(auto &neighbour:graph[node]){
		if(colors[neighbour]==-1){
			colors[neighbour]=1-colors[node];    // the opposite colour

			if(!DFS(graph,neighbour,colors))
			return false;
		}else if(colors[neighbour]==colors[node]){
			return false;                     // CONFLICT: odd cycle
		}
	}

	return true;
}
bool bipartite(unordered_map<int,vector<int>> &graph,int N){
	vector<int> colors(N,-1);

	for(int i=0;i<N;i++){
		if(colors[i]==-1){
			colors[i]=0;                      // new component: pick either colour

			if(!DFS(graph,i,colors))
			return false;
		}
	}

	return true;
}
1 - colors[node] does the whole flip. It turns 0 into 1 and 1 into 0, which is why the colours must be 0 and 1 rather than 1 and 2. Also note that the driver loop gives colour 0 to the first node of each new component. Each separate piece of the graph is coloured on its own, so a graph in several pieces is bipartite exactly when every piece is.
✍️
My convention: colors with −1 for unvisited, so one array does two jobs

Keeping a separate visited array next to colors is unnecessary, and it gives the two arrays a chance to disagree. Use -1 to mean "not coloured yet". Then colors[neighbour] == -1 answers "have I seen this?", and colors[neighbour] == colors[node] answers "is there a conflict?". One array, and nothing can get out of sync. Chapter 27 used the same three-states-in-one-array idea as white/grey/black. Reach for it whenever one boolean is about to become two.

BFS colouring

BFS makes the proof visible. It reaches nodes in layers by distance, and the colour is just "is the distance even or odd?". On a 5-cycle 0–1–2–3–4–0 starting at 0: layer 0 is {0} (colour 0), layer 1 is {1, 4} (colour 1), layer 2 is {2, 3} (colour 0). Now look at the edge 2–3: both ends are in layer 2, so both have colour 0. That clash is the odd cycle — 5 edges long — showing up as an edge inside a layer. In a bipartite graph every edge goes between neighbouring layers, never within one.

bipartite — BFSO(V + E)O(V)
// Identical logic, iterative. Colour = parity of BFS distance, which is
// literally the proof above turned into code.
bool BFS(unordered_map<int,vector<int>> &graph,int node,vector<int> &colors){
	queue<int> q;
	q.push(node);

	while(!q.empty()){
		int node=q.front();
		q.pop();

		for(auto &neighbour:graph[node]){
			if(colors[neighbour]==-1){
				colors[neighbour]=1-colors[node];
				q.push(neighbour);
			}else if(colors[neighbour]==colors[node]){
				return false;
			}
		}
	}

	return true;
}
bool bipartite(unordered_map<int,vector<int>> &graph,int N){
	vector<int> colors(N,-1);

	for(int i=0;i<N;i++){
		if(colors[i]==-1){
			colors[i]=0;

			if(!BFS(graph,i,colors))
			return false;
		}
	}

	return true;
}
Setting the colour when you enqueue is the Chapter 25 habit again, and here it does two jobs. The colour is also the visited mark, so colouring on enqueue keeps each node in the queue only once. Prefer BFS when the graph could be a 10⁵-node chain — the DFS version would overflow the stack. Otherwise the two are the same.

Recognising a bipartite problem

Problems rarely use the word “bipartite”. Instead they say something that means “split these into two groups so that…”.

“Split people into two teams so that enemies are never on the same team”

→ Build a graph where an edge means “these two must be kept apart”, then two-colour it. Possible bipartite partition.

colors[neighbour]=1-colors[node];
“Is this graph a valid two-team assignment / dislike list?”

→ Same idea. LeetCode's Possible Bipartition is exactly this, with a list of who dislikes whom.

if(colors[nb]==colors[node])return false;
“Does this graph contain an odd-length cycle?”

→ This is just the opposite of bipartite. Run the colouring: a conflict is an odd cycle.

return !bipartite(graph,N);
“Match items of type A to items of type B”

→ The graph is bipartite by design (A on one side, B on the other). The real question is maximum matching, covered in Chapter 33.

// weighted DSU, or implication graph

🎨
Why k = 2 is linear and k = 3 is NP-hard

With two colours, every choice is forced. Once you colour one node, each neighbour must get the other colour, and that ripples through the whole component with no decisions left. There is nothing to search: in one pass you either succeed or hit a contradiction. With three colours, colouring a node leaves each neighbour with two options. The choices branch, and you have to search through them. 3-colouring is NP-complete, and no polynomial-time algorithm is known. It is one of the clearest cases where "one more option makes it exponential". Be ready to say it in one line: the difference is that 2-colouring has no free choices.

➕
The variant with “same group” constraints too — DSU with parity

Suppose some rules say “these two must differ” and others say “these two must match”. Plain colouring is not enough. There are two standard tools:

  • DSU with parity (Chapter 22's weighted DSU): for each node, store whether it is the same as (0) or different from (1) its group's root. A "differ" rule joins two nodes with parity 1, a "same" rule with parity 0. A contradiction shows up when two nodes already in the same group have the wrong parity between them.
  • 2-SAT (Chapter 32): each node becomes a true/false variable, and each rule becomes "if this, then that" implications. Whether all rules can be satisfied is decided by finding strongly connected components in the graph of implications.

A quick example: the rules "a differs from b", "b differs from c", "a same as c" are consistent (a and c on one side, b on the other). Change the last rule to "a differs from c" and they contradict each other — it is the triangle again. Both tools run in roughly linear time. The point is that "two groups with a mix of same/different rules" is a different problem from bipartite colouring. Using the colouring code there gives wrong answers.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 TWO-COLOUR BFS
Bipartite is BFS assigning alternating colours; a conflict means an odd cycle. "Is it bipartite" and "does an odd cycle exist" are the same question.
💡 GRID PARITY
A grid graph is always bipartite by (r+c) % 2 — no search needed. Recognising that kills a whole class of problems instantly.
💡 DSU WITH PARITY
For mixed "same" and "different" constraints, store parity relative to the root in the DSU. It handles both kinds of edge in one structure.
⚠️
Common mistakes
  • Forgetting the driver loop over all nodes. In a graph made of separate pieces, every piece must be coloured. The piece that is not bipartite may be one you never started from.
  • Using colours 1 and 2 with 1 - color. The flip only works for 0 and 1. With 1 and 2 you need 3 - color.
  • Using a separate visited array. It is unnecessary, and it can get out of sync with colors. Let -1 mean unvisited.
  • Checking for conflicts only on unvisited neighbours. A conflict can only happen with an already coloured neighbour — that is the else if branch.
  • Returning true from the helper without passing up a child's false. Write if(!DFS(...)) return false; — not a bare DFS(...).
  • Applying it to a directed graph without care. Bipartite is an undirected idea. For a directed graph, ignore the arrow directions and check that undirected version.
  • Assuming a bipartite graph has equal halves. The two sides can be any sizes, including 1 and n−1.
  • Recursive DFS on a 10⁵-node chain. It overflows the stack. Use the BFS version.
  • Treating "must be in the same group" rules as plain colouring. That needs DSU with parity or 2-SAT.

Interview drill

Warm-up: Determine whether a graph is bipartite, and prove your approach is correct.

How a strong answer sounds
I keep a colors array set to −1 at the start, which also serves as the visited marker. For each uncoloured node I start a traversal and give it colour 0. Then for every edge: if the neighbour is uncoloured, I colour it 1 - colors[node]. If it is already coloured, I check that its colour is different. If it matches, the graph is not bipartite. The driver loops over all nodes so every separate piece is handled, because the graph is bipartite exactly when every piece is. That is O(V + E) time and O(V) space. BFS and DFS both work, though I would use BFS if the graph could be a long chain, to avoid a stack overflow. For correctness: the algorithm succeeds exactly when there is no odd cycle. If the graph is bipartite, every cycle must be even, because each edge flips the colour and getting back to the start needs an even number of flips. Going the other way: if the colouring fails, I have found an edge u—v whose endpoints have BFS distances that are both even or both odd. Then the path from the start to u, that edge, and the path from v back to the start form a round trip of odd length dist(u) + 1 + dist(v), which must contain an odd cycle. So the conflict I detect is an odd cycle. The failure is real, not an accident of the order I visited nodes in.

Deeper: Why is 2-colouring linear while 3-colouring is NP-hard?

How a strong answer sounds
Because with two colours there are no choices to make. Once I fix one node's colour, every neighbour is forced to the opposite colour, and that forcing spreads through the whole component. So the whole thing is a single pass with no branching. Either it finishes consistently or it hits a contradiction; there is nothing to search. My only freedom is which colour to give the first node of each component, and since swapping the two colours changes nothing, that choice never matters. With three colours, colouring a node leaves each neighbour with two options. The rules no longer pin down the answer, so I am searching a tree of choices. 3-colouring is NP-complete, and no polynomial-time algorithm is known. In practice I would use backtracking with pruning, trying high-degree vertices first, and accept exponential time in the worst case. It shows clearly that the jump in difficulty comes from having free choices, not from the problem "feeling" harder. Worth adding that some special cases stay easy: planar graphs (drawable with no crossing edges) can always be 4-coloured, and there is a way to construct it; interval graphs and chordal graphs can be coloured optimally by a greedy method in the right vertex order.

🧠 Key takeaways

  • Bipartite means the nodes can be painted with two colours so every edge joins different colours. That is exactly the same as having no odd-length cycle.
  • Colour with 1 - colors[node] and use -1 for unvisited, so one array is both the colour and the visited mark.
  • The conflict case is the else if branch — an already coloured neighbour matching the current colour.
  • Loop the driver over all nodes: the graph is bipartite if and only if every component is.
  • k = 2 colours is linear because every choice is forced. k ≥ 3 is NP-hard because the choices branch.

Check your understanding

A graph is bipartite if and only if it has no…

Each edge flips the colour, so getting back to the start needs an even number of flips — so every cycle must be even. The other way round: with no odd cycle, colouring by even/odd BFS distance always works. A triangle is the smallest graph that is not bipartite.

Why use colours 0 and 1 rather than 1 and 2?

The arithmetic flip keeps the line short and clear. Using 1 and 2 with 1 - color produces 0 and −1, which quietly breaks the conflict check.

Why is -1 used for "not yet coloured" instead of keeping a separate visited array?

Three states in one array — the same idea as white/grey/black in Chapter 27. Reach for it whenever one boolean is about to become two.

Your bipartite check returns true for a graph containing a triangle. What is the most likely bug?

If the triangle sits in a piece of the graph you never started a traversal from, it is never checked. (Starting the colours at 0 is also a real bug, but it would cause a false negative: every node would look already coloured.)

Why is 2-colouring O(V + E) while 3-colouring is NP-hard?

The jump in difficulty comes from free choices appearing. 2-colouring has none once the first node is fixed. 3-colouring turns into a search, and it is NP-complete.
