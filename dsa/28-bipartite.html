Bipartite Graphs & Coloring

A graph is bipartite if you can split its nodes into two groups with no edge inside a group. The test is a five-minute DFS or BFS — colour as you go, and fail on a conflict. What makes this chapter worth its own slot is the theorem behind it: bipartite is exactly “no odd cycle”, and that equivalence is what lets you recognise bipartite problems that never mention colours.

  • Write the two-colouring check with both DFS and BFS
  • Prove that bipartite is equivalent to having no odd-length cycle
  • Use a three-state colour array so unvisited, colour 0 and colour 1 are distinguishable
  • Recognise the problem phrasings that are bipartite checks in disguise
  • Know why general k-colouring is NP-hard while k = 2 is linear

The definition, and the theorem

A graph is bipartite if its nodes can be two-coloured so that every edge joins different colours. Equivalently: partition V into A and B with every edge crossing between them.

🧾
Bipartite ⟺ no odd cycle

(⇒) A bipartite graph has no odd cycle. Walk a cycle. Every edge flips the colour, so after k edges you have flipped k times. To return to the start you must be back at the starting colour, which requires an even number of flips. So every cycle has even length.

(⇐) A graph with no odd cycle is bipartite. Run a BFS from any node and colour each node by the parity of its BFS distance. Suppose some edge u—v joined two nodes of the same colour, meaning dist(u) and dist(v) have the same parity. Then the path from the source to u, plus the edge u—v, plus the path from v back to the source, forms a closed walk of length dist(u) + 1 + dist(v) — which is odd. A closed walk of odd length always contains an odd cycle. Contradiction, so no such edge exists and the parity colouring works. This proof is the algorithm: the colouring by BFS parity is exactly what the code below does, and the conflict it detects is exactly this odd closed walk.

DFS and BFS reach the conflict via different paths, but both reach it — the odd cycle cannot be coloured, however you approach it.

DFS colouring

bipartite — DFSO(V + E)O(V)
// colors[x] is -1 (unvisited), 0 or 1. Three states in one array, so we
// need no separate visited array — the colour IS the visited marker.
bool DFS(unordered_map<int,vector<int>> &graph,int node,vector<int> &colors){
	for(auto &neighbour:graph[node]){
		if(colors[neighbour]==-1){
			colors[neighbour]=1-colors[node];    // the opposite colour

			if(!DFS(graph,neighbour,colors))
			return false;
		}else if(colors[neighbour]==colors[node]){
			return false;                     // CONFLICT: odd cycle
		}
	}

	return true;
}
bool bipartite(unordered_map<int,vector<int>> &graph,int N){
	vector<int> colors(N,-1);

	for(int i=0;i<N;i++){
		if(colors[i]==-1){
			colors[i]=0;                      // new component: pick either colour

			if(!DFS(graph,i,colors))
			return false;
		}
	}

	return true;
}
1 - colors[node] is the whole flip — it maps 0 to 1 and 1 to 0, which is why the colours must be 0 and 1 rather than 1 and 2. And note the driver loop assigns colour 0 to each new component's start: each component is coloured independently, so a disconnected graph is bipartite exactly when every component is.
✍️
My convention: colors with −1 for unvisited, so one array does two jobs

A separate visited array alongside a colors array is redundant and introduces a way for them to disagree. Using -1 as "not yet coloured" means the single test colors[neighbour] == -1 answers "have I seen this?" and the single test colors[neighbour] == colors[node] answers "is there a conflict?" — no second array, no possibility of drift. The same three-state-in-one-array idea appeared in Chapter 27 as white/grey/black, and it is worth reaching for whenever a boolean is about to become two booleans.

BFS colouring

bipartite — BFSO(V + E)O(V)
// Identical logic, iterative. Colour = parity of BFS distance, which is
// literally the proof above turned into code.
bool BFS(unordered_map<int,vector<int>> &graph,int node,vector<int> &colors){
	queue<int> q;
	q.push(node);

	while(!q.empty()){
		int node=q.front();
		q.pop();

		for(auto &neighbour:graph[node]){
			if(colors[neighbour]==-1){
				colors[neighbour]=1-colors[node];
				q.push(neighbour);
			}else if(colors[neighbour]==colors[node]){
				return false;
			}
		}
	}

	return true;
}
bool bipartite(unordered_map<int,vector<int>> &graph,int N){
	vector<int> colors(N,-1);

	for(int i=0;i<N;i++){
		if(colors[i]==-1){
			colors[i]=0;

			if(!BFS(graph,i,colors))
			return false;
		}
	}

	return true;
}
Setting the colour on enqueue is the Chapter 25 discipline again, and here it does double duty: the colour is the visited mark, so marking on enqueue is what keeps each node in the queue once. Prefer BFS when the graph could be a 10⁵-node path — the DFS version would overflow the stack, and the two are otherwise identical.

Recognising a bipartite problem

The problems rarely say “bipartite”. They say something that means “split these into two groups such that…”.

“Split people into two teams so that enemies are never on the same team”

→ Build a graph where an edge means “must be separated”, then two-colour it. Possible bipartite partition.

colors[neighbour]=1-colors[node];
“Is this graph a valid two-team assignment / dislike list?”

→ Same. LeetCode's Possible Bipartition is literally this with a dislike matrix.

if(colors[nb]==colors[node])return false;
“Does this graph contain an odd-length cycle?”

→ Exactly the negation of bipartite. Run the colouring; a conflict is an odd cycle.

return !bipartite(graph,N);
“Match items of type A to items of type B”

→ The graph is bipartite by construction; the question is maximum matching, which is Chapter 33.

“Assign one of two labels consistently with pairwise constraints”

→ If all constraints are “different”, it is bipartite colouring. If some are “same” and some are “different”, it is DSU with parity or 2-SAT (Chapter 32).

// weighted DSU, or implication graph
“Colour the map with k colours”, k ≥ 3

→ Not this chapter. NP-hard in general; use backtracking with pruning (Chapter 35).

// no polynomial algorithm known
🎨
Why k = 2 is linear and k = 3 is NP-hard

With two colours, every choice is forced: once you colour one node, every neighbour's colour is determined, and the constraint propagates deterministically through the whole component. There is nothing to search — you either succeed or hit a contradiction, in one pass. With three colours, colouring a node leaves each neighbour with two options, so choices branch and you must search. 3-colouring is NP-complete, and there is no known polynomial algorithm. This is one of the cleanest "one more option makes it exponential" boundaries in complexity theory, and it is worth being able to state: the difference is that 2-colouring has no free choices.

➕
The variant with “same group” constraints too — DSU with parity

If some constraints say “these two must differ” and others say “these two must match”, plain colouring is not enough. Two standard tools:

  • DSU with parity (Chapter 22's weighted DSU): store, for each node, its parity relative to its component's root. Uniting with a "differ" constraint sets a relative parity of 1, "same" sets 0, and a contradiction appears when two nodes already in the same component have the wrong relative parity.
  • 2-SAT (Chapter 32): each node becomes a boolean, each constraint becomes implications, and satisfiability is decided by strongly connected components in the implication graph.

Both are linear-ish. The point is that "two groups with mixed same/different constraints" is a different problem from bipartite colouring, and reaching for the colouring code there gives wrong answers.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 TWO-COLOUR BFS
Bipartite is BFS assigning alternating colours; a conflict means an odd cycle. "Is it bipartite" and "does an odd cycle exist" are the same question.
💡 GRID PARITY
A grid graph is always bipartite by (r+c) % 2 — no search needed. Recognising that kills a whole class of problems instantly.
💡 DSU WITH PARITY
For mixed "same" and "different" constraints, store parity relative to the root in the DSU. It handles both kinds of edge in one structure.
⚠️
Common mistakes
  • Forgetting the driver loop over all nodes. A disconnected graph needs each component coloured, and the non-bipartite part may be one you never started from.
  • Using colours 1 and 2 with 1 - color. The flip only works for 0 and 1. With 1 and 2 you need 3 - color.
  • Using a separate visited array. Redundant, and it can drift out of sync with colors. Let -1 mean unvisited.
  • Checking the conflict only for unvisited neighbours. The conflict is precisely the already coloured case — that is the else if.
  • Returning true from the helper without propagating a child's false. if(!DFS(...)) return false; — not a bare DFS(...).
  • Applying it to a directed graph without care. Bipartiteness is an undirected notion; for a directed graph you check the underlying undirected graph.
  • Assuming a bipartite graph has equal halves. The two sides can be any sizes, including 1 and n−1.
  • Recursive DFS on a 10⁵-node path. Use the BFS version.
  • Treating "must be in the same group" constraints as colouring. That needs DSU with parity or 2-SAT.

Interview drill

Warm-up: Determine whether a graph is bipartite, and prove your approach is correct.

How a strong answer sounds
I keep a colors array initialised to −1, which does double duty as the visited marker. For each uncoloured node I start a traversal, assign it colour 0, and then for every edge either colour the neighbour with 1 - colors[node] if it is uncoloured, or — if it is already coloured — check that its colour differs; if it matches, the graph is not bipartite. I loop over all nodes in the driver so disconnected components are each handled, since the graph is bipartite exactly when every component is. That is O(V + E) time and O(V) space, and BFS and DFS are equally valid, though I would use BFS if the graph could be a long path, to avoid a stack overflow. For correctness: the algorithm succeeds exactly when there is no odd cycle. If the graph is bipartite then every cycle must be even, because each edge flips the colour and returning to the start requires an even number of flips. Conversely, if the colouring fails, I have found an edge u—v whose endpoints have the same BFS-distance parity, and then the path from the source to u, that edge, and the path from v back to the source form a closed walk of odd length dist(u) + 1 + dist(v) — which must contain an odd cycle. So the conflict I detect is an odd cycle, and the failure is genuine rather than an artefact of the traversal order.

Deeper: Why is 2-colouring linear while 3-colouring is NP-hard?

How a strong answer sounds
Because with two colours there are no choices to make. Once I fix one node's colour, every neighbour's colour is forced to the opposite, and that forcing propagates deterministically through the entire component — so the whole thing is a single constraint-propagation pass with no branching. Either it completes consistently or it hits a contradiction, and there is nothing to search. The only freedom I have is which colour to give the first node of each component, and since swapping both colours in a component is symmetric, that choice never matters. With three colours, assigning a node leaves each neighbour with two remaining options, so the constraints no longer determine the solution and I am searching a tree of choices. 3-colouring is NP-complete, and no polynomial algorithm is known — so in practice I would use backtracking with pruning, ordering vertices by degree, and accept exponential worst-case behaviour. It is a clean illustration that the complexity jump comes from the presence of free choices, not from the problem "feeling" harder. Worth adding that some structured cases stay easy: planar graphs are always 4-colourable and that is constructive, and interval graphs and chordal graphs can be optimally coloured greedily in a suitable vertex order.

🧠 Key takeaways

  • Bipartite means two-colourable, which is exactly equivalent to having no odd-length cycle.
  • Colour with 1 - colors[node] and use -1 for unvisited, so one array is both the colour and the visited mark.
  • The conflict case is the else if branch — an already coloured neighbour matching the current colour.
  • Loop the driver over all nodes: the graph is bipartite iff every component is.
  • k = 2 is linear because every choice is forced; k ≥ 3 is NP-hard because they branch.

Check your understanding

A graph is bipartite if and only if it has no…

Each edge flips the colour, so returning to the start needs an even number of flips — hence every cycle must be even. Conversely, no odd cycle means the BFS-parity colouring is consistent. A triangle is the smallest non-bipartite graph.

Why use colours 0 and 1 rather than 1 and 2?

The arithmetic flip is what makes the line short and unambiguous. Using 1 and 2 with 1 - color produces 0 and −1 and silently breaks the conflict check.

Why is -1 used for "not yet coloured" instead of keeping a separate visited array?

Three states in one array. The same idea as white/grey/black in Chapter 27 — reach for it whenever one boolean is about to become two.

Your bipartite check returns true for a graph containing a triangle. What is the most likely bug?

If the triangle sits in a component you never started a traversal from, it is never checked. (Initialising to 0 is also a real bug, but it would cause a false negative — every node would look already-coloured.)

Why is 2-colouring O(V + E) while 3-colouring is NP-hard?

The complexity jump comes from the appearance of free choices. 2-colouring has none once the first node is fixed; 3-colouring turns into a search, and it is NP-complete.
