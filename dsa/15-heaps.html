Heaps & Priority Queues

A heap answers one question fast — “what is the smallest thing left?” — and that single capability powers Dijkstra, Prim, top-K, K-way merge and the running median. The structure is unusually elegant: a tree that lives in a flat array, with no pointers at all, because the shape is so constrained that indices can encode the parent-child relationships.

  • Derive the parent and child index formulas from the complete-tree shape
  • Implement sift-up and sift-down, and explain why they are O(log n)
  • Prove that building a heap bottom-up is O(n), not O(n log n)
  • Use the min-heap-of-size-K trick for top-K, and say why it is not a max-heap
  • Solve K-way merge and the running median with two heaps

A tree with no pointers

A binary heap is a complete binary tree — every level full except possibly the last, which fills left to right — satisfying the heap property: every parent is ≤ both children (min-heap) or ≥ both (max-heap).

Because the tree is complete, there are no gaps, so you can store it in a flat array in level order and compute the relationships arithmetically:

the three index formulas — everything else followsno pointers, perfect locality
// 0-indexed:
parent(i) = (i-1)/2
left(i)   = 2*i+1
right(i)  = 2*i+2

// 1-indexed (competitive programming often prefers this — cleaner arithmetic):
parent(i) = i/2
left(i)   = 2*i
right(i)  = 2*i+1
This is why heaps are fast in practice as well as in theory. No allocation per node, no pointer chasing, and a parent and its children are close together in memory — so a sift often stays within one or two cache lines (Chapter 3). A pointer-based tree with the same O(log n) is measurably slower.
🧩
The heap property is weaker than sorted — deliberately

A heap does not sort. It only guarantees the relationship between each parent and its own children, so the array [1,3,2,7,5,4,6] is a valid min-heap while being far from sorted. That weakness is the point: maintaining a full order costs O(n log n), while maintaining only “the smallest is at the root” costs O(log n) per change. A heap gives you the minimum in O(1) and tells you nothing about the second smallest — if you need the second smallest, you must pop. That is the precise trade, and it is why a heap cannot answer range queries or do binary search.

MinHeap from scratchO(log n) push/pop, O(1) topO(n)
class MinHeap{
	vector<int> h;

	// Invariant restored upward: a new leaf may be smaller than its parent.
	void siftUp(int i){
		while(i>0){
			int p=(i-1)/2;

			if(h[p]<=h[i])break;     // property holds, nothing more to do

			swap(h[p],h[i]);
			i=p;
		}
	}

	// Invariant restored downward: the new root may be larger than a child.
	void siftDown(int i){
		int n=h.size();

		while(true){
			int small=i;
			int l=2*i+1;
			int r=2*i+2;

			if(l<n and h[l]<h[small])small=l;
			if(r<n and h[r]<h[small])small=r;

			if(small==i)break;        // parent is already the smallest

			swap(h[i],h[small]);
			i=small;                     // MUST follow the element down
		}
	}

public:
	void push(int x){
		h.push_back(x);           // append keeps the tree complete
		siftUp(h.size()-1);
	}

	int top(){ return h[0]; }

	void pop(){
		h[0]=h.back();          // move the last leaf to the root
		h.pop_back();             // the tree stays complete

		if(!h.empty())
		siftDown(0);
	}

	// Bottom-up build. This is O(n), NOT O(n log n) — see the proof below.
	void heapify(vector<int> &a){
		h=a;

		// leaves are trivially valid heaps, so start at the last internal node
		for(int i=h.size()/2-1;i>=0;i--)
		siftDown(i);
	}

	bool empty(){ return h.empty(); }
	int size(){ return h.size(); }
};
Two details people get wrong. In siftDown, you must compare against both children and swap with the smaller — swapping with the left child unconditionally breaks the property. And i=small is essential: the element has to keep moving down until it settles, so a single swap is not enough.
🧾
Why bottom-up heapify is O(n), not O(n log n)

The naive argument says: n/2 internal nodes × O(log n) per sift = O(n log n). That is a valid upper bound but it is not tight, because most nodes are near the bottom and barely sift at all.

Count properly. A node at height h above the leaves sifts at most h levels, and a complete tree has at most n/2^(h+1) nodes at height h. So the total work is:

Σh=0..log n (n / 2^(h+1)) · h = (n/2) · Σ h/2^h ≤ (n/2) · 2 = O(n)

The series Σ h/2^h converges to 2 — so the whole build is linear. The intuition: half the nodes are leaves and sift zero levels, a quarter sift at most one, an eighth at most two. The expensive nodes are rare and the common nodes are cheap. This is why std::make_heap is O(n) while n separate push calls are O(n log n) — and it matters: building a heap from a known array should always use heapify.

std::priority_queue in practice

the four forms you needmax-heap by default — this surprises people
// 1. MAX-heap. This is the DEFAULT, which is the opposite of what most
//    problems want, and the single most common heap bug in C++.
priority_queue<int> maxpq;

// 2. MIN-heap. Note you must spell out all three template arguments.
priority_queue<int,vector<int>,greater<int>> minpq;

// 3. Min-heap of pairs — compares .first, then .second. The Dijkstra idiom.
priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> pq;
pq.push({dist,node});      // distance FIRST so it is the sort key

// 4. Custom comparator. Careful: the comparator is INVERTED relative to sort().
//    "returns true if a has LOWER priority than b" -> a comes out later.
auto cmp=[](const pair<int,int> &a,const pair<int,int> &b){
	return a.second>b.second;   // SMALLER .second pops first
};
priority_queue<pair<int,int>,vector<pair<int,int>>,decltype(cmp)> custom(cmp);

// Build from an existing vector in O(n), not O(n log n):
priority_queue<int> fast(a.begin(),a.end());
The comparator inversion is worth writing on your hand. For sort, cmp(a,b) true means “a before b”. For priority_queue, cmp(a,b) true means “a has lower priority”, so it comes out later. That is why greater<> — which normally sorts descending — produces a min-heap. Getting this backwards is silent: the program runs and gives the wrong answer.
✍️
My convention: greater<pair<int,int>> with the key first

Every heap in the graph chapters is written as priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> pq; and pushed as pq.push({distance,node}) or pq.push({weight,node}) — the sort key always first. It is verbose, and it is worth it: the pair's built-in < does exactly the right thing, so there is no custom comparator to get inverted. Pop with a structured binding: auto [d,node]=pq.top();. Be strict about the ordering convention, because {node,weight} versus {weight,node} is a bug that produces plausible-looking wrong distances.

The top-K pattern

Find the K largest of n elements. Sorting is O(n log n). A heap does it in O(n log k), which matters when k is small and n is huge — and it works on a stream, where sorting is not even possible.

🔄
For the K largest, use a min-heap. This inversion catches everyone.

You keep a heap of size K holding the best candidates so far. To decide whether a new element belongs, you must compare it against the worst of your current K — and that worst element must be cheap to find and remove. In a min-heap of the K largest, the worst is exactly the root. So: if the new element beats the root, pop the root and push the new one. With a max-heap the root is the best element, which is the one thing you never need to touch.

Rule: K largest → min-heap of size K. K smallest → max-heap of size K. Always the opposite of what it first sounds like.

findKthLargest — min-heap of size KO(n log k)O(k)
// Invariant: pq holds the k largest elements seen so far, and pq.top()
// is the smallest of those k — i.e. the current kth largest.
int findKthLargest(vector<int> &a,int k){
	priority_queue<int,vector<int>,greater<int>> pq;

	for(int x:a){
		pq.push(x);

		if(pq.size()>k)
		pq.pop();             // evict the smallest — it cannot be top-k
	}

	return pq.top();
}
// O(n log k) time, O(k) space, and it works on a STREAM.
// Alternative: nth_element is O(n) expected but needs the whole array in memory
// and permutes it. Mention both and pick based on whether the input is a stream.
Push then conditionally pop is cleaner than “if full and better, replace”: one branch instead of two, and it handles the warm-up phase (fewer than k elements seen) with no special case.

// Invariant 1: every element of lower <= every element of upper.
// Invariant 2: lower.size() is either equal to upper.size() or one greater.
// Then the median is lower.top(), or the average of the two tops.
class MedianFinder{
	priority_queue<int> lower;                                  // max-heap
	priority_queue<int,vector<int>,greater<int>> upper;      // min-heap

public:
	void addNum(int num){
		// 1. always push into lower first, then move its max across.
		//    This enforces invariant 1 without needing to compare anything.
		lower.push(num);
		upper.push(lower.top());
		lower.pop();

		// 2. rebalance: lower may now be one short
		if(upper.size()>lower.size()){
			lower.push(upper.top());
			upper.pop();
		}
	}

	double findMedian(){
		if(lower.size()>upper.size())
		return lower.top();

		return (lower.top()+upper.top())/2.0;
	}
};
The push-then-transfer dance is the elegant part. Naively you would compare num against the current median and choose a heap — which needs a branch and an empty-heap special case. Pushing into lower and immediately moving its maximum into upper guarantees invariant 1 unconditionally, and then one rebalance restores invariant 2. Note /2.0, not /2 — integer division here is a classic silent bug.

K-way merge

Merge K sorted lists. A heap holding one element from each list gives the global minimum in O(log k), so the whole merge is O(N log k) where N is the total element count.

mergeKListsO(N log k)O(k)
// The heap holds at most one node per list, so its size is k, not N.
// Comparator is inverted (see the note above): "greater" makes a min-heap.
ListNode* mergeKLists(vector<ListNode*> &lists){
	auto cmp=[](ListNode* a,ListNode* b){ return a->val>b->val; };
	priority_queue<ListNode*,vector<ListNode*>,decltype(cmp)> pq(cmp);

	for(ListNode* node:lists){
		if(node)pq.push(node);      // skip empty lists — nullptr would crash cmp
	}

	ListNode dummy(0);              // dummy head from Chapter 12
	ListNode* tail=&dummy;

	while(!pq.empty()){
		ListNode* node=pq.top();
		pq.pop();

		tail->next=node;
		tail=tail->next;

		if(node->next)pq.push(node->next);   // refill from the same list
	}

	return dummy.next;
}
// Alternative: pairwise merge (divide and conquer) is also O(N log k)
// with O(1) extra space. Worth mentioning as the follow-up.
Skipping null lists matters. Pushing a nullptr means the comparator dereferences it on the next push and the program dies inside the STL, far from your code. Also note this is exactly the merge phase of an external sort (Chapter 8's interview drill) — the same pattern, with disk-backed runs instead of lists.

🔀
When you need arbitrary deletion, use multiset — or lazy deletion

A heap cannot find an arbitrary element, so “remove this specific value” is O(n). Two standard fixes. Lazy deletion: keep a set of values to ignore, and on top() discard anything marked deleted — this is exactly the pattern used in Dijkstra (Chapter 29), where a stale entry is skipped with if(d>dist[node])continue;. Or use multiset: it gives O(log n) insertion, O(1) minimum via *begin(), and O(log n) removal of a specific element via erase(find(x)) — at the cost of a larger constant factor. Note erase(x) on a multiset removes all copies, which is almost never what you want; always erase(find(x)).

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SIZE-K HEAP
For k-th largest, keep a min-heap of size k and pop when it overflows. The root is the answer, it is O(n log k), and it works on a stream.
💡 TWO HEAPS
A running median is a max-heap of the low half and a min-heap of the high half, rebalanced so the sizes differ by at most one. The same shape solves IPO and scheduling-by-two-keys.
⛔ MIN-HEAP SYNTAX
priority_queue is a max-heap by default. A min-heap needs the full greater<> template argument — and the comparator is inverted relative to sort.
⚠️
Common mistakes
  • Forgetting that priority_queue is a max-heap by default. The single most common heap bug in C++.
  • Inverting the comparator. For priority_queue, cmp(a,b) true means a comes out later — the opposite of sort.
  • Using a max-heap for “K largest”. You need cheap access to the worst of your K, which is a min-heap's root.
  • Swapping with the left child unconditionally in siftDown. Compare both children and swap with the smaller.
  • Not following the element down. Forgetting i=small makes siftDown do one swap and stop.
  • Pushing n elements instead of calling heapify. O(n log n) where O(n) was available.
  • Integer division in the median. (a+b)/2 instead of (a+b)/2.0.
  • Pushing a nullptr into a heap of pointers. The comparator dereferences it and crashes inside the STL.
  • Expecting a heap to be sorted. It guarantees only parent-versus-children; the array is not in order.
  • Trying to remove an arbitrary element. That is O(n) — use lazy deletion or multiset.

Interview drill

Warm-up: Find the K largest elements. Why a min-heap, and what are the alternatives?

How a strong answer sounds
I keep a min-heap of size K holding the best candidates so far, with the invariant that the root is the smallest of those K — that is, the current Kth largest. For each new element I push it and then pop if the size exceeds K, which evicts the weakest candidate. It has to be a min-heap because the decision I make repeatedly is "is this new element better than the worst thing I am keeping?", and the worst thing must be O(1) to inspect and O(log k) to remove. In a max-heap the root is my best element, which is the one I never need to touch. That gives O(n log k) time and O(k) space, and crucially it works on a stream where I never hold all n elements. Two alternatives: sorting the whole array is O(n log n) and simpler if n is small, and nth_element — quickselect — is O(n) expected, which is asymptotically better, but it needs the entire array in memory and permutes it. So I would pick based on whether the input is a stream and whether mutating it is allowed.

Deeper: Prove that building a heap bottom-up is O(n) rather than O(n log n).

How a strong answer sounds
The loose bound is n/2 internal nodes times O(log n) per sift, which gives O(n log n) — true but not tight, because it charges every node the maximum sift depth when almost none of them pay it. The tight count uses the tree's shape: a node sitting at height h above the leaves sifts at most h levels, and a complete tree has at most n/2^(h+1) nodes at height h. So total work is the sum over h of (n/2^(h+1))·h, which factors to (n/2)·Σ h/2^h, and that series converges to 2 — so the total is at most n. The intuition is that the distribution is heavily bottom-weighted: half the nodes are leaves and sift zero levels, a quarter sift at most one, an eighth at most two. The nodes that could be expensive are exponentially rare. Practically this is why std::make_heap and the priority_queue range constructor are O(n), and why building a heap from a known array with n separate pushes wastes a log factor for no reason.

🧠 Key takeaways

  • A complete tree in a flat array: parent=(i-1)/2, left=2i+1, right=2i+2 — no pointers, great locality.
  • The heap property is only parent-versus-children, which is why it costs O(log n) to maintain instead of O(n log n).
  • Bottom-up heapify is O(n) because Σ h/2^h converges — most nodes are leaves and sift nothing.
  • K largest needs a min-heap of size K, because you repeatedly evict the worst candidate.
  • priority_queue is a max-heap by default and its comparator is inverted relative to sort.

Check your understanding

To find the K largest elements, which heap do you keep?

The repeated decision is “is this new element better than the worst I am keeping?”, so the worst must be at the root. A max-heap puts your best element there, which is the one you never need.

Why is bottom-up heapify O(n) rather than O(n log n)?

The n log n bound is valid but loose. Half the nodes are leaves and sift nothing; a quarter sift at most one level. The expensive nodes are exponentially rare, and the series sums to a constant.

What does priority_queue<int> pq; give you in C++?

Max-heap is the default, which is usually the opposite of what a problem wants. For a min-heap you must spell out all three template arguments: priority_queue<int,vector<int>,greater<int>>.

In siftDown, you swap with the left child whenever it is smaller than the parent. What breaks?

You must compare against both children and swap with the smaller. Swapping with the left child when the right one is smaller leaves a parent greater than a child — the property is violated and top() eventually returns the wrong value.

You need to remove a specific arbitrary value from a heap in O(log n). What do you use?

A heap has no way to locate an arbitrary element, so deletion is O(n). multiset gives O(log n) removal plus O(1) minimum via *begin(). Lazy deletion — skipping stale entries at the top — is the other standard fix, and it is what Dijkstra uses.
