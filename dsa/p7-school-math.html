School Math for DSA

DSA uses very little maths, but it uses a few facts constantly: what a logarithm really counts, how big 2²⁰ is, what 1 + 2 + … + n adds up to, how remainders behave with negative numbers, how to test for primes, and how many ways there are to choose things. Each fact below comes with the question it answers in practice — usually “how fast is this?” or “will this overflow?” — and a small interactive to make it stick.

  • Use powers of two, and read and write numbers in binary
  • Read log₂ n as “how many halvings”, and know its value for 10³, 10⁶, 10⁹
  • Use the arithmetic, geometric and harmonic sums to count loop steps
  • Compute floor, ceiling and integer division, including the ceiling trick
  • Handle modulo with negative numbers, and keep answers “modulo 10⁹ + 7”
  • Find divisors and primes in O(√n), compute a GCD, and count with nCr, 2ⁿ and n!

So a set of 20 items has 2²⁰ ≈ a million subsets, which is why “n ≤ 20” in a problem hints at trying every subset (Chapter 44). In C++, 1<<k is 2ᵏ for k up to 30; for bigger k write 1LL<<k, or it overflows.

Binary writes numbers using only 0 and 1, where each position is worth twice the one to its right: 1, 2, 4, 8, 16… So 13 = 8 + 4 + 1 = 1101. Every whole number has exactly one such representation, which is why “each item in or out” (a subset) maps perfectly onto “each bit 1 or 0”. Click bits to build numbers:

Try: a number is even exactly when its last bit is 0. Shifting all bits left by one doubles the number (x<<1); shifting right halves it, rounding down (x>>1). A power of two has exactly one bit set. Chapter 47 turns these facts into tricks.

Logarithms: “how many halvings?”

Forget the textbook definition for a moment. For this course, log₂ n is the number of times you can cut n in half before you reach 1. Start at 16: 16 → 8 → 4 → 2 → 1. Four halvings, so log₂ 16 = 4. Equivalently, it's the power you raise 2 to in order to get n: 2⁴ = 16.

Why this matters: any algorithm that throws away half of what is left at each step finishes in about log₂ n steps. Binary search does that. So does walking down a balanced tree, and so does repeatedly halving a range. And log₂ n is tiny even for huge n: about 10 for a thousand, 20 for a million, 30 for a billion, 60 for 10¹⁸. That is why O(log n) feels almost free.

Each step is integer division, n/=2, exactly like the halvings loop in P3. Binary search over n items needs at most (halvings + 1) comparisons.

Two more facts complete the picture. Logs turn multiplication into addition: log(a × b) = log a + log b, so log₂(10⁶) = 6 × log₂ 10 ≈ 6 × 3.32 ≈ 20. And in Big-O, the base doesn't matter: log₂ n and log₁₀ n differ only by a constant factor (about 3.32), so we just write O(log n).

Sums that count loop steps

Three sums explain the running time of most loops you will write.

The arithmetic series: 1 + 2 + 3 + … + n = n(n + 1) / 2. Here is the picture that makes it obvious. Put two copies of the staircase together, one upside down. They make a rectangle n wide and n + 1 tall. The staircase is half of it.

Where you meet it: a loop inside a loop, where the inner one starts at i+1, compares every pair once. That is (n − 1) + (n − 2) + … + 1 = n(n − 1)/2 steps. At n = 10⁵, that is about 5 × 10⁹. Too slow. So “all pairs” means O(n²), even though it is only half of n².

for(int i=0;i<n;i++){
	for(int j=i+1;j<n;j++){
		// runs n(n-1)/2 times in total: O(n^2)
	}
}

The geometric series, where each term is double the one before: 1 + 2 + 4 + … + 2ᵏ = 2ᵏ⁺¹ − 1. For example, 1 + 2 + 4 + 8 = 15 = 16 − 1. Read it the other way round and it says: n + n/2 + n/4 + … is less than 2n. The whole sum is dominated by its biggest term. This is why a vector that doubles its size when full still costs O(1) per push_back on average (P4), and why building a heap is O(n) (Chapter 15).

The harmonic series: 1 + 1/2 + 1/3 + … + 1/n ≈ ln n (the natural log, about 0.69 × log₂ n). Multiply by n and you get the cost of a loop like “for each i, visit every multiple of i up to n”: n/1 + n/2 + n/3 + … ≈ n ln n. For n = 10⁶ that's about 1.4 × 10⁷ steps — fast. This is the running time behind the sieve of Eratosthenes and many “for each divisor” tricks (Chapter 48).

for(int i=1;i<=n;i++)
for(int j=i;j<=n;j+=i)      // visits the multiples of i: n/i of them
cnt[j]++;                     // total ≈ n ln n: cnt[j] ends as the number of divisors of j

Floor, ceiling and integer division

Floor, written ⌊x⌋, rounds down to a whole number: ⌊3.7⌋ = 3. Ceiling, ⌈x⌉, rounds up: ⌈3.2⌉ = 4. In C++, dividing two ints throws away the fractional part: 7/2 is 3. For positive numbers, that is the floor.

Two things to remember. First, for negative numbers C++ rounds toward zero, not down: -7/2 is -3, but ⌊−3.5⌋ is −4. Second, to get the ceiling of a/b for positive a and b without using decimals, write (a+b-1)/b. Example: 7 people, cars that hold 3 each, (7 + 3 − 1)/3 = 9/3 = 3 cars.

int ceilDiv(int a,int b){                // a, b positive
	return (a+b-1)/b;
}

Why it works: adding b − 1 pushes any non-zero remainder over into the next whole multiple of b, while an exact multiple stays where it is (6 + 2 = 8, and 8 / 3 is still 2). You'll use it for “how many pages / batches / trips”, and it avoids the rounding errors of ceil((double)a/b) on big numbers.

Modulo, including negative numbers

The modulo operator a % m gives the remainder after dividing a by m. 17 % 5 is 2. You use it to test divisibility (n % 2 == 0 means even), to wrap around in a circle (index (i+1) % n goes back to 0 after the last), to take the last digit (n % 10), and to keep huge numbers small.

The negative trap: in C++, the result has the same sign as a. So -7 % 3 is −1, not 2. If you then use it as an array index, you crash. The safe form is (a % m + m) % m, which always lands in 0 … m − 1.

“Output the answer modulo 10⁹ + 7” appears in many counting problems. The true answer is astronomically large, so you keep only its remainder. 10⁹ + 7 is a prime just above a billion. Any two remainders below it multiply to under 10¹⁸, which fits in a long long. The rule is simple: take the remainder after every addition and multiplication, not just at the end.

modulo helpersO(1)O(1)
const int MOD=1e9+7;

long long mulMod(long long a,long long b){
	return (a%MOD)*(b%MOD)%MOD;        // each factor < MOD, product < 10^18
}

long long subMod(long long a,long long b){
	return ((a-b)%MOD+MOD)%MOD;        // subtraction can go negative: fix it
}

int safeMod(int a,int m){
	return (a%m+m)%m;                  // -7 -> 2 when m is 3
}
Why it works: remainders can be added, subtracted and multiplied as you go, and the final remainder comes out the same as if you had worked with the full numbers. That is what lets you count to 10¹⁰⁰⁰ with a long long. (Division is the exception — it needs a modular inverse, taught in Chapter 48.)

Divisors, primes and GCD

Divisors come in pairs: if d divides n, so does n/d. For 36: (1, 36), (2, 18), (3, 12), (4, 9), (6, 6). One of each pair is always at most √n. So to find every divisor, you only need to try d from 1 up to √n — about 1,000 checks for n = 10⁶ instead of a million. The same idea tests whether n is prime (divisible only by 1 and itself): if no d from 2 to √n divides it, nothing does.

bool isPrime(long long n){
	if(n<2)return false;

	for(long long d=2;d*d<=n;d++)       // d*d<=n avoids sqrt and its rounding
	if(n%d==0)return false;

	return true;
}

long long gcd(long long a,long long b){
	return b==0?a:gcd(b,a%b);          // Euclid: gcd(48,18) -> (18,12) -> (12,6) -> (6,0) = 6
}

The greatest common divisor (GCD) is the largest number dividing both a and b. Euclid's algorithm computes it in O(log(min(a, b))) steps using one fact: gcd(a, b) = gcd(b, a mod b). C++17 also has it built in as __gcd / std::gcd. The least common multiple follows from it: lcm(a, b) = a / gcd(a, b) × b (divide first to avoid overflow). You'll use GCD for simplifying fractions, cycles and many “repeat until aligned” problems.

Many problems ask “how many ways…?”, and brute force asks “can I try them all?”. Three counts answer both:

nCr, also written C(n, r) and read “n choose r”, has the formula C(n, r) = n! / (r! · (n − r)!). Choosing 2 fruits from 5: 5! / (2! · 3!) = 120 / 12 = 10. A friendlier way to see the numbers is Pascal's triangle, where each entry is the sum of the two above it — because to choose r from n, you either take the last item (then choose r − 1 from the rest) or you don't (choose r from the rest):

Pascal's triangle: C(n, r)Interactive

The highlighted C(n, r) is the sum of the two amber entries above it: C(n−1, r−1) + C(n−1, r). That rule is also a tiny dynamic program — your first taste of Chapter 38.
nCr without overflowing on the factorialsO(r)O(1)
long long nCr(int n,int r){
	if(r<0 or r>n)return 0;

	long long ans=1;
	for(int i=1;i<=r;i++)
	ans=ans*(n-r+i)/i;                 // after step i, ans is C(n-r+i, i): always whole

	return ans;
}
Why not compute n! directly? 21! already overflows a long long. Multiplying and dividing one step at a time keeps the numbers small, and the division is always exact. For large n with a modulus you need modular inverses instead, which Chapter 48 teaches.
⚠️
Common mistakes
  • Trusting a % m to be non-negative. In C++, -7 % 3 is −1. Use (a%m+m)%m whenever a could be negative — including after a modular subtraction.
  • Taking the modulo only at the end. The intermediate values overflow long before. Reduce after every operation.
  • 1<<40. The 1 is an int; the shift overflows. Write 1LL<<40.
  • Using sqrt in loop bounds. Floating-point rounding can make it one too small. Loop while d*d<=n, with d a long long.
  • Using ceil((double)a/b) on large values. Doubles can round wrongly. Use (a+b-1)/b.
  • Computing nCr via factorials. 21! overflows. Multiply and divide step by step, or use modular arithmetic.

Interview drill

Quick maths: Roughly how many steps does binary search need on 10¹⁸ possible answers, and why?

How a strong answer sounds
About 60. Each step halves the range, so the count is log₂ 10¹⁸. Since 2¹⁰ ≈ 10³, 10¹⁸ ≈ 2⁶⁰. That's why “binary search on the answer” works even over astronomically large ranges — as long as each check is cheap.

Explain it simply: Why is checking divisors up to √n enough to decide whether n is prime?

How a strong answer sounds
Divisors come in pairs d and n/d whose product is n. If both were bigger than √n, their product would be bigger than n — impossible. So any divisor pair has one member at most √n. If nothing from 2 to √n divides n, there is no pair, and n is prime. For n near 10⁹ that's about 31,600 checks instead of a billion.

🧠 Key takeaways

  • 2¹⁰ ≈ 10³, 2²⁰ ≈ 10⁶, 2³⁰ ≈ 10⁹. n ≤ 20 means 2ⁿ subsets are affordable; use 1LL<<k for big shifts.
  • log₂ n counts halvings: ~10, 20, 30, 60 for 10³, 10⁶, 10⁹, 10¹⁸. The base doesn't matter in Big-O.
  • 1 + … + n = n(n+1)/2 (pairs are O(n²)); n + n/2 + n/4 + … < 2n; n/1 + n/2 + … + n/n ≈ n ln n.
  • C++ division truncates toward zero; ceiling of a/b is (a+b-1)/b.
  • C++ % can be negative: use (a%m+m)%m. Under “mod 10⁹ + 7”, reduce after every step.
  • Divisors pair up around √n, so primality and divisor listing are O(√n); gcd(a, b) = gcd(b, a mod b).
  • Subsets 2ⁿ, orderings n!, choices C(n, r) — with Pascal's rule C(n, r) = C(n−1, r−1) + C(n−1, r).

Check your understanding

In C++, what does -7 % 3 evaluate to?

C++ division rounds toward zero, so -7/3 is −2 and the remainder takes the sign of the left operand: −7 − (−2 × 3) = −1. To get the mathematical answer, 2, write (a%m+m)%m.

About how many times can you halve 1,000,000 before you reach 1?

That count is log₂ n, and 2²⁰ ≈ 10⁶, so the answer is about 20 (exactly 19 full halvings with integer division). This is why binary search over a million items takes only about 20 steps.

What is 1 + 2 + 3 + … + 100?

n(n + 1)/2 = 100 × 101 / 2 = 5,050. Two copies of the staircase make a 100 × 101 rectangle; the sum is half of it.

You need to split 50 items into boxes of 8. Which expression gives the number of boxes, using only integers?

(50 + 7)/8 = 57/8 = 7 boxes. Plain 50/8 = 6 would leave 2 items without a box; 50 % 8 = 2 is the leftover count.

What is C(6, 2), the number of ways to choose 2 items from 6?

C(6, 2) = 6 × 5 / 2 = 15 — the number of pairs among 6 items. 30 would count ordered pairs (6 × 5), which double-counts each pair.
