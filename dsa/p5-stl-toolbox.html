The STL Toolbox

The STL (Standard Template Library) is the set of ready-made containers and algorithms that ships with C++: hash maps, sorted sets, stacks, queues, heaps, sorting, binary search and more. You will use it in every chapter. You don't need to know how each container works inside yet — later chapters teach that. You need to know what each one is for, what each operation costs, the few lines that use it, and the traps that cost people accepted solutions.

  • Pick the right container for a job from a one-line description of each
  • Count and look things up with unordered_map, and avoid the m[key] trap
  • Keep data sorted with map/set, and use lower_bound/upper_bound
  • Use stack, queue, deque and priority_queue (max- and min-heap)
  • Read iterators, and use the algorithms library: sort with comparators and lambdas, accumulate, unique, next_permutation

pair and tuple

A pair glues two values into one: a (distance, node), an (x, y) point, a (value, index). A tuple does the same for three or more. Pairs compare lexicographically — by first, and by second only on a tie — which is exactly what makes them so handy for sorting and heaps.

pair<int,string> p={3,"cat"};
cout<<p.first<<" "<<p.second<<"\n";    // 3 cat

vector<pair<int,int>> pts={{2,5},{1,9},{2,1}};
sort(pts.begin(),pts.end());             // {1,9} {2,1} {2,5}: by first, then second

for(auto &[x,y]:pts)                      // structured binding: name both parts at once
cout<<x<<","<<y<<" ";

tuple<int,int,int> t={1,2,3};
auto [a,b,c]=t;                            // a=1, b=2, c=3

Hash containers: unordered_map and unordered_set

These answer “what's stored under this key?” and “have I seen this?” in O(1) on average, however many items they hold. They're the most-used tools in interview problems: counting, deduplicating, remembering positions, and the famous “two-sum” lookup. Inside, they're hash tables (Chapter 9), which is why there's no order: iterating gives keys in an unpredictable order.

unordered_map<string,int> freq;
for(auto &w:words)
freq[w]++;                                // a missing key starts at 0, then becomes 1

if(freq.count("apple"))                    // 1 if present, 0 if not — does NOT insert
cout<<freq["apple"]<<"\n";

auto it=freq.find("pear");                  // an iterator, or freq.end() if absent
if(it!=freq.end())
cout<<it->second<<"\n";

unordered_set<int> seen;
for(auto &x:a){
	if(seen.count(x))return true;          // a duplicate
	seen.insert(x);
}
🪤
The m[key] trap

m[key] creates the key (with value 0, or an empty string) if it was missing. So if(m[x]>0) quietly adds x to the map. That wastes memory, changes m.size(), and can break loops that iterate over the map. To only ask whether a key exists, use m.count(key) or m.find(key).

“O(1) on average” has a small print: a hash map can degrade badly if many keys collide, and a few contest problems deliberately include inputs that do this to unordered_map. If a hash-based solution mysteriously TLEs on Codeforces, switching to map (guaranteed O(log n)) is a quick fix.

Ordered containers: map and set

map and set keep their keys sorted at all times, using a balanced search tree inside (Chapter 20). Every operation is O(log n) — a little slower than hashing — but you gain order: iterate from smallest to largest, find the smallest or largest instantly, and answer “what's the first key ≥ x?”.

map<int,int> ordered;
ordered[5]=1; ordered[2]=7; ordered[9]=3;
for(auto &[k,v]:ordered)
cout<<k<<" ";                              // 2 5 9: keys come out sorted

set<int> s={10,3,7,3};                       // {3,7,10}: sorted, duplicates dropped
cout<<*s.begin()<<" "<<*s.rbegin()<<"\n";   // 3 10: smallest and largest
auto it=s.lower_bound(5);                   // first element >= 5, i.e. 7
s.erase(3);                                 // {7,10}

multiset<int> ms={4,4,4};                    // a set that keeps duplicates
ms.erase(ms.find(4));                       // removes ONE 4 → {4,4}
ms.erase(4);                                // removes EVERY 4 → {}  (a common bug!)

lower_bound and upper_bound

These two find positions in sorted data in O(log n). They work on set/map as member functions, and on a sorted vector as free functions. The definitions are worth memorising exactly:

  • lower_bound(x) — the first element ≥ x.
  • upper_bound(x) — the first element > x.

So the elements equal to x are exactly the range [lower_bound, upper_bound), and their count is the difference. If nothing qualifies, both return end(), one past the last element.

stack, queue, deque and priority_queue

These containers deliberately limit what you can do, so that the few allowed operations are fast and the code says exactly what it means.

stack<int> st;
st.push(1); st.push(2);
cout<<st.top()<<"\n";                  // 2: last in, first out
st.pop();                               // pop returns nothing: read top() first

queue<int> q;
q.push(1); q.push(2);
cout<<q.front()<<"\n";                 // 1: first in, first out — the heart of BFS
q.pop();

deque<int> dq;
dq.push_front(1); dq.push_back(2);        // [1,2]: both ends are O(1)

priority_queue<int> pq;                // max-heap: largest on top
pq.push(4); pq.push(9); pq.push(1);
cout<<pq.top()<<"\n";                  // 9

priority_queue<int,vector<int>,greater<int>> minpq;   // min-heap: smallest on top
priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> dist;  // (distance,node), smallest distance first: Dijkstra
A priority queue always serves the topInteractive
The items are shown in insertion order; the highlighted one is top(). You can't index into a priority queue or search it — it only ever gives you the best item, in O(1), and removes it in O(log n). That's all Dijkstra, scheduling and top-K problems need (Chapter 15).

Calling top(), front() or pop() on an empty container is a crash. Loops are always written while(!q.empty()).

Iterators

An iterator is a generalised position in a container — like an index, but it works for every container, including ones without indexes (sets, maps, lists). The key operations:

  • c.begin() points at the first element; c.end() points one past the last (never read it).
  • *it is the element; it->first is a field of it (for maps and pairs); ++it moves to the next.
  • For vectors and strings, it-v.begin() turns an iterator back into an index, and v.begin()+k jumps to index k.
for(auto it=s.begin();it!=s.end();++it)   // the long way to loop; range-for does this for you
cout<<*it<<" ";

auto it=max_element(v.begin(),v.end());
int idx=it-v.begin();                   // position of the maximum

Algorithms take a range as a pair of iterators [first, last) — including first, excluding last. That half-open convention is why sort(v.begin(),v.end()) means “the whole vector”, and sort(v.begin(),v.begin()+k) means “the first k elements”.

Sorting with a comparator

To sort in a different order, give sort a comparator: a function that takes two items and returns true if the first should come before the second.

sort with a comparatorO(n log n)O(log n)
// smaller .first first; on a tie, larger .second first
bool compare(const pair<int,int> &a,const pair<int,int> &b){
	if(a.first==b.first)
	return a.second>b.second;

	return a.first<b.first;
}

int main(){
	vector<pair<int,int>> v={{2,1},{1,5},{2,7}};
	sort(v.begin(),v.end(),compare);        // {1,5} {2,7} {2,1}

	vector<int> nums={3,1,2};
	sort(nums.begin(),nums.end(),[](int a,int b){
		return a>b;                         // a lambda: sorts descending -> 3 2 1
	});
	return 0;
}
Two rules. First, a comparator must use a strict comparison: < or >, never <=. With <=, sort can read past the end of the array and crash. Second, on LeetCode a comparator written inside class Solution must be marked static (or be a lambda). Chapter 8 covers sorting in depth.

⚠️
Common mistakes
  • Using m[key] to test existence. It inserts the key. Use count or find.
  • multiset::erase(x) removing every copy. To remove one, erase an iterator: ms.erase(ms.find(x)).
  • Using <= in a sort comparator. Undefined behaviour; can crash. Always strict.
  • accumulate(b,e,0) on big values. The 0 is an int, so the sum overflows. Use 0LL.
  • Calling top()/front()/pop() on an empty container. Crash. Check empty() first.
  • Forgetting that priority_queue is a max-heap. For “smallest first”, use greater<> or push negated values.
  • binary_search/lower_bound on unsorted data. The answer is meaningless. Sort first.

Interview drill

Choose and justify: When would you use map instead of unordered_map?

How a strong answer sounds
When I need order: iterating keys in sorted order, finding the smallest or largest key, or asking for the first key ≥ x with lower_bound. unordered_map is O(1) on average but has no order and can degrade with adversarial collisions; map is a balanced tree with guaranteed O(log n) per operation. If I only need exact lookups and counting, unordered_map is my default.

Code it: Return the k most frequent words in a list.

How a strong answer sounds
Count with unordered_map<string,int> in O(n). Then either sort the (count, word) pairs with a comparator — higher count first, alphabetical on ties — and take the first k, in O(m log m) for m distinct words; or keep a min-heap of size k, pushing each pair and popping when it exceeds k, in O(m log k). Watch the comparator for ties, and remember the heap gives results in reverse order, so reverse at the end.

🧠 Key takeaways

  • Default to vector; pair/tuple bundle values and compare first by first, then by second.
  • unordered_map/unordered_set: O(1) average lookups, no order. m[key] inserts; test with count/find.
  • map/set/multiset: sorted, O(log n), with begin/rbegin for min/max and lower_bound (first ≥ x) / upper_bound (first > x).
  • stack is LIFO, queue FIFO, deque both ends, priority_queue a max-heap (use greater<> for min).
  • Iterators mark positions; ranges are half-open [begin, end).
  • Reach for algorithms before loops: sort (strict comparators), accumulate with 0LL, min/max_element, unique+erase, next_permutation.

Check your understanding

You need to answer “have I seen this value before?” thousands of times, and order does not matter. Which container fits best?

An unordered_set answers membership in O(1) on average. Searching a vector is O(n) per question. A heap only gives quick access to the largest item, and a stack only to the newest. set also works, at O(log n), when you also need sorted order.

In the sorted vector {1, 3, 3, 3, 8}, where does upper_bound(3) point?

upper_bound finds the first element strictly greater than 3, which is 8 at index 4. lower_bound(3) would be index 1, and 4 − 1 = 3 is the count of 3s.

What happens after if(m["zebra"]>0) on an unordered_map<string,int> that didn't contain "zebra"?

operator[] inserts a default value (0) for a missing key before returning it. Use m.count("zebra") to test without inserting.

Which declaration gives a heap where top() is the smallest element?

The default priority_queue is a max-heap. Passing greater<int> as the comparison type turns it into a min-heap. (A set with greater would sort descending, which is a different container.)

A vector holds 10⁵ values up to 10⁹. What's wrong with long long s=accumulate(v.begin(),v.end(),0);?

accumulate adds using the type of its initial value. With 0 that's int, so the total (up to 10¹⁴) overflows before being stored. Write 0LL.
