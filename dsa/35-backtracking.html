Backtracking

Backtracking is a tidy way to try every possibility. Think of walking a maze: you pick a turn, follow it, and if it is a dead end you walk back and try the next turn. In code that is three steps: choose, explore, unchoose. Every solution in this chapter is that same three-line skeleton with different choices and different pruning (cutting off branches that cannot work). The pruning is where the real skill lies. Trying everything takes exponential time; with good pruning it is often fast enough to use.

  • Write the choose/explore/unchoose skeleton and say why the undo is required
  • Generate subsets, permutations and combinations, including when the input has duplicates
  • Handle duplicates by sorting plus a skip condition, instead of a set of results
  • Prune with O(1) conflict checks, such as N-Queens with three boolean arrays
  • Estimate the size of the search tree, and know when backtracking is the wrong tool

The skeleton

Why backtracking exists. Some problems have no clever shortcut: "list every subset", "find every way to fill this Sudoku", "place 8 queens safely". The only way is to try options. But trying them carelessly (writing nested loops, or building every full candidate and then checking it) is either impossible to write for a variable n, or wastefully slow. Backtracking builds a candidate one choice at a time and abandons it the moment it breaks a rule. In interviews it covers a whole family: subsets, permutations, combination sum, word search, N-Queens, generating valid parentheses.

choose · explore · unchooseevery problem in this chapter
void backtrack(State &current,Result &ans){
	if(isComplete(current)){
		ans.push_back(current);       // record a COPY
		return;
	}

	for(auto &choice:candidates(current)){
		if(!isValid(current,choice))continue;   // PRUNE — the whole game

		apply(current,choice);                // 1. CHOOSE
		backtrack(current,ans);                // 2. EXPLORE
		undo(current,choice);                 // 3. UNCHOOSE
	}
}
The undo is not optional, and it is where the bugs are. current is one object shared by every branch of the recursion. That is on purpose: copying it at each step would cost O(depth) per call. So anything you add on the way down must be removed on the way back up. Otherwise every later branch inherits your choices. Also, the result you record must be a copy. If you store a reference to current, all your answers point at the same object, and it ends up empty.

Reading the skeleton line by line. isComplete is the base case: the candidate is fully built, so save it. candidates lists the options for the next step (the next number, the next column, the next letter). isValid is the pruning test: can this choice still lead to a valid answer? Then come the three core lines. It helps to picture the calls as a tree: the root is the empty candidate, each edge is one choice, and each leaf is a finished candidate or a dead end. Backtracking is a DFS over that tree, and the undo is what lets one current object walk the whole tree.

✍️
My convention: the undo is the line immediately after the recursive call, always

Write apply / recurse / undo as three lines in a row with nothing between them. That way the pairing is visible, and a missing undo jumps out at you.

Avoid a return from inside the loop that skips the undo. Sometimes you do want an early exit, as in a "found it" search like Sudoku. There, return true before the undo is fine, but only because you are stopping the whole search. If the search might continue, undo first. This is the Chapter 11 rule about shared state, and breaking it is the most common cause of wrong answers in this chapter.

Subsets: the include/exclude tree

// At each index, two choices: take a[i] or do not. 2^n leaves.
void subsets(vector<int> &a,int i,vector<int> &current,vector<vector<int>> &ans){
	if(i==a.size()){
		ans.push_back(current);
		return;
	}

	subsets(a,i+1,current,ans);        // exclude a[i]

	current.push_back(a[i]);              // CHOOSE
	subsets(a,i+1,current,ans);        // EXPLORE
	current.pop_back();                  // UNCHOOSE
}

// The "for loop over remaining" form. Same 2^n outputs, but it records
// at EVERY node rather than only at leaves — which is often what you want.
void subsets2(vector<int> &a,int start,vector<int> &current,vector<vector<int>> &ans){
	ans.push_back(current);              // every node is a valid subset

	for(int i=start;i<a.size();i++){
		current.push_back(a[i]);
		subsets2(a,i+1,current,ans);     // i+1, NOT start+1
		current.pop_back();
	}
}

Use i+1, not start+1, in the recursive call. That stops you reusing an element, and stops the same subset appearing in a different order. This "loop from start" shape is the one to memorise. Change the index you recurse with, and it also handles combinations and combination sum.

Dry run of subsets2 on [1,2,3]. It records [], then pushes 1 and records [1], pushes 2 and records [1,2], pushes 3 and records [1,2,3]. Then it pops 3 and 2, pushes 3 and records [1,3]. After popping back to empty it records [2], [2,3] and finally [3]. That is 8 subsets, which is 2³. Notice that current grows and shrinks like a stack, and it is empty again when the function returns.

// SORT FIRST, then skip a value that equals its predecessor at the same level.
// Sorting is what makes duplicates adjacent, which is what makes the skip work.
void subsetsDup(vector<int> &a,int start,vector<int> &current,vector<vector<int>> &ans){
	ans.push_back(current);

	for(int i=start;i<a.size();i++){
		if(i>start and a[i]==a[i-1])continue;   // skip a duplicate SIBLING

		current.push_back(a[i]);
		subsetsDup(a,i+1,current,ans);
		current.pop_back();
	}
}
vector<vector<int>> subsetsWithDup(vector<int> &a){
	sort(a.begin(),a.end());              // mandatory

	vector<vector<int>> ans;
	vector<int> current;
	subsetsDup(a,0,current,ans);

	return ans;
}

Use i > start, not i > 0. This is the detail that matters. We want to allow [2,2], where the same value is used at different depths. But we want to forbid two branches at the same depth that both start with 2 (two "siblings"). i > start means "this is not the first choice at this level", which is exactly the sibling rule.

Dry run on [1,2,2]. At the top level (start = 0), the choices are 1 (i=0), 2 (i=1), and 2 again (i=2). The last one is skipped: i = 2 > start and a[2] == a[1]. Inside the [1] branch (start = 1), 2 at i=1 is taken, giving [1,2], and 2 at i=2 is skipped as a sibling. Inside [1,2] (start = 2), the second 2 is at i == start, so it is allowed, giving [1,2,2]. The output is [], [1], [1,2], [1,2,2], [2], [2,2]: 6 distinct subsets instead of 8 with repeats.

// No recursion at all: iterate every n-bit integer and read its bits.
// Only works when n is small (<= ~20) and there are no duplicates.
vector<vector<int>> subsetsBitmask(vector<int> &a){
	int n=a.size();
	vector<vector<int>> ans;

	for(int mask=0;mask<(1<<n);mask++){
		vector<int> current;

		for(int i=0;i<n;i++){
			if(mask&(1<<i))
			current.push_back(a[i]);
		}

		ans.push_back(current);
	}

	return ans;
}

This is shorter, needs no recursion, and makes the 2ⁿ count obvious. But it cannot prune: you go through every mask, whether it could work or not. So for any problem with constraints, the recursive version wins. Chapter 44 builds bitmask DP on this idea.

Permutations, and the duplicate rule again

permutations, with and without duplicatesO(n! · n)O(n)
// Without duplicates: a used[] array marks what is already in the prefix.
void permute(vector<int> &a,vector<bool> &used,vector<int> &current,vector<vector<int>> &ans){
	if(current.size()==a.size()){
		ans.push_back(current);
		return;
	}

	for(int i=0;i<a.size();i++){
		if(used[i])continue;

		used[i]=true;
		current.push_back(a[i]);

		permute(a,used,current,ans);

		current.pop_back();
		used[i]=false;               // BOTH must be undone
	}
}

// WITH duplicates: sort, then skip a value equal to its predecessor
// UNLESS that predecessor is currently in use (i.e. we are deeper in the
// same branch). That condition is the whole trick.
void permuteDup(vector<int> &a,vector<bool> &used,vector<int> &current,vector<vector<int>> &ans){
	if(current.size()==a.size()){
		ans.push_back(current);
		return;
	}

	for(int i=0;i<a.size();i++){
		if(used[i])continue;
		if(i>0 and a[i]==a[i-1] and !used[i-1])continue;

		used[i]=true;
		current.push_back(a[i]);

		permuteDup(a,used,current,ans);

		current.pop_back();
		used[i]=false;
	}
}
Understand !used[i-1]; do not just memorise it. Among equal values, we force one fixed order. The copy at index i may only be placed if the copy at i−1 is already placed. If a[i−1] is unused, then picking a[i] now would give exactly the same permutation as picking a[i−1]. So we skip it. Compare this with the subsets rule i > start. Both block duplicate siblings. But permutations need the used test, because the same value can rightly appear at two different depths.

A tiny example of the duplicate rule. Take [1, 1, 2] and call the two ones 1a (index 0) and 1b (index 1). Without the rule you get 3! = 6 permutations, but they come in identical pairs: 1a 1b 2 and 1b 1a 2 print the same. The rule says 1b may only be placed once 1a is already placed. So 1a always comes before 1b, and each distinct arrangement is built exactly once: [1,1,2], [1,2,1], [2,1,1]. That is 3 results, which is 3! / 2!.

Where O(n! · n) comes from. There are n choices for the first position, n−1 for the second, and so on, giving n! complete permutations. Copying each one into the answer costs O(n). For n = 8 that is 40,320 × 8, about 3 × 10⁵ steps. For n = 12 it is about 5.7 × 10⁹, which is too slow. The same reasoning gives O(2ⁿ · n) for subsets.

🚫
Do not deduplicate with a set of results

It is tempting to generate everything and drop the results into a set<vector<int>> to remove duplicates. It works, but it is the wrong answer for two reasons. First, it still does all the exponential duplicate work, only to throw it away. Second, each insert costs O(size log n), because it must compare or hash a whole vector. Sorting plus the skip condition cuts the duplicate branches before exploring them. That is faster, and it is what the interviewer is looking for. Prune at the branch, not at the leaf.

N-Queens: pruning is the whole problem

Place N queens on an N×N chessboard so that no queen attacks another. (A queen attacks along its row, its column and both diagonals.) Trying every placement would take an enormous amount of time. With the right bookkeeping, the search shrinks to something tiny.

solveNQueens — three boolean arrays, O(1) conflict checkO(n!) worst, far less in practiceO(n)
// Place one queen per row, so we only choose a COLUMN for each row.
// Three arrays make "is this square attacked?" O(1) instead of O(n):
//   cols[c]       — a queen already in column c
//   diag1[r+c]    — the anti-diagonal: r+c is constant along it
//   diag2[r-c+n-1] — the main diagonal: r-c is constant; shift to make it >= 0
void solve(int row,int n,vector<int> &pos,
           vector<bool> &cols,vector<bool> &diag1,vector<bool> &diag2,
           vector<vector<int>> &ans){
	if(row==n){
		ans.push_back(pos);
		return;
	}

	for(int c=0;c<n;c++){
		int d1=row+c;
		int d2=row-c+n-1;

		if(cols[c] or diag1[d1] or diag2[d2])continue;    // PRUNE in O(1)

		cols[c]=diag1[d1]=diag2[d2]=true;      // CHOOSE
		pos.push_back(c);

		solve(row+1,n,pos,cols,diag1,diag2,ans);   // EXPLORE

		pos.pop_back();                          // UNCHOOSE — all four
		cols[c]=diag1[d1]=diag2[d2]=false;
	}
}
vector<vector<int>> solveNQueens(int n){
	vector<vector<int>> ans;
	vector<int> pos;
	vector<bool> cols(n,false);
	vector<bool> diag1(2*n-1,false);
	vector<bool> diag2(2*n-1,false);

	solve(0,n,pos,cols,diag1,diag2,ans);

	return ans;
}
Work out the diagonal indices; do not memorise them. Along an anti-diagonal (going down-left), the row goes up as the column goes down. So r + c stays the same. It ranges from 0 to 2n−2, hence the size 2n−1. Along a main diagonal (going down-right), both go up. So r − c stays the same. It ranges from −(n−1) to n−1, so add n−1 to make it never negative. Placing one queen per row is itself a pruning choice. It removes every "two queens in one row" option before it is ever generated.

Checking the diagonal formulas with numbers. On a 4 × 4 board, cell (1, 2) has r + c = 3 and r − c + n − 1 = 1 − 2 + 3 = 2. Cell (2, 1) also has r + c = 3, so the two share an anti-diagonal, and indeed they touch diagonally. Cell (2, 3) has r − c + n − 1 = 2, the same as (1, 2), so they share a main diagonal. One array lookup answers "is this diagonal taken?" instead of scanning the board.

A short trace for N = 4. Put the row-0 queen in column 0. In row 1, columns 0 and 1 are attacked, so try column 2. In row 2, every column is now attacked: dead end, so back up and move the row-1 queen to column 3. Row 2 can then use column 1, but row 3 has no safe column: another dead end. Every branch under "row 0, column 0" dies this way, so the search moves the row-0 queen to column 1. From there it finds the first solution, columns [1, 3, 0, 2]. The only other solution is its mirror image, [2, 0, 3, 1].

Combination sum: the three variants

combinationSum — reuse allowed, then not, then with duplicatesexponential, heavily prunedO(target)
// VARIANT 1: each number may be reused. Recurse with i, not i+1.
void combo(vector<int> &a,int start,int remaining,
           vector<int> &current,vector<vector<int>> &ans){
	if(remaining==0){
		ans.push_back(current);
		return;
	}

	for(int i=start;i<a.size();i++){
		if(a[i]>remaining)break;      // SORTED, so everything after is too big

		current.push_back(a[i]);
		combo(a,i,remaining-a[i],current,ans);   // i = reuse allowed
		current.pop_back();
	}
}

// VARIANT 2: each number used at most once -> recurse with i+1.
// VARIANT 3: input has duplicates -> add the sibling skip as well:
//   if(i>start and a[i]==a[i-1])continue;
//   and recurse with i+1.
Using break instead of continue is the important pruning. The array is sorted. So once one candidate is bigger than remaining, every later one is too. We drop the whole rest of the loop instead of testing each one. That single keyword turns a slow exponential search into one that finishes instantly on typical inputs. Sorting is not just for handling duplicates; it also makes this cut possible.

Dry run: candidates [2, 3, 6, 7], target 7 (variant 1, reuse allowed).

  1. Take 2 (remaining 5), 2 (remaining 3), 2 (remaining 1). Now even the smallest candidate, 2, is bigger than 1, so break ends this level at once.
  2. Back at remaining 3, try 3: remaining 0, so record [2,2,3]. The next candidate, 6, is bigger than 3: break.
  3. Back at remaining 5, try 3 (remaining 2): 3 is bigger than 2, break. Then 6 is bigger than 5, break.
  4. At the top, try 3 (remaining 4): another 3 leaves 1, dead end. Try 6 (remaining 1): dead end. Try 7: remaining 0, record [7].

Answer: [2,2,3] and [7]. Because every branch only uses indices from i onward, [3,2,2] is never produced as a separate answer. Edge cases: a target of 0 gives one answer, the empty list, because the base case fires immediately. If the smallest candidate is bigger than the target, the answer is empty. Candidates must be positive; a 0 with reuse allowed would recurse forever, because the remaining amount never shrinks.

Looping from start is what makes order not matter. Looping from 0 with used[] is what makes order matter. This one choice decides whether you generate subsets or permutations. If your output has the wrong number of results, check this first.

When backtracking is the wrong tool

Estimating the search tree before you code. Multiply the number of choices at each level: that is the number of leaves in the worst case. Subsets have 2 choices per element, so 2ⁿ leaves; n = 20 gives about 10⁶, which is fine. Permutations have n, n−1, … choices, so n! leaves; n = 10 gives about 3.6 × 10⁶, which is fine, but n = 13 gives about 6 × 10⁹, which is not. Pruning only makes the real tree smaller than this estimate, so if the estimate already fits the time budget (about 10⁸ simple steps per second), you are safe. If it does not, you need strong pruning or a different algorithm.

📈

n is large

2ⁿ is fine up to about n = 20, and n! only up to about n = 10. If n is 100 and the problem asks for the best answer, use DP, greedy or flow, not search.

🔁

You only need the count, not the list

Counting rarely means listing every option. Count the subsets that sum to K with DP (Chapter 40) in O(n·K), not 2ⁿ.

♻️

Subproblems repeat

If the same state comes up again in different branches, memoise (save each answer the first time and reuse it). That is Chapter 38. Repeated nodes in the recursion tree are the sign that DP fits (Chapter 11).

✅

A greedy provably works

Examples: interval scheduling, Huffman coding, jump game. If you can prove the greedy choice is safe with an exchange argument (Chapter 36), searching is wasted effort.

🧩

It is an assignment problem

“Match these to those” is bipartite matching or flow, which run in polynomial time (Chapter 33). No need for an n! search.

✔️

But backtracking is right when…

you must list all solutions, n is truly small, the constraints cut off most branches, or the problem is NP-hard and nothing better is known. Examples: Sudoku, N-Queens, word search, building expressions.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SORT TO DEDUPE
Sort first, then skip i > start && a[i] == a[i-1]. That is how you avoid duplicate subsets without a set — and the condition is on the sibling, not the parent.
💡 PRUNE EARLY
Check feasibility before recursing, not at the leaf. A bound that cuts a branch at depth 2 saves more than any micro-optimisation at depth 12.
⛔ RESTORE EXACTLY
Whatever you changed going down must be undone coming up — including the grid cell you marked as visited. A missing unmark is the classic word-search bug.
⚠️
Common mistakes
  • Forgetting the undo. Every later branch inherits your choices, and the output is garbage.
  • Undoing only part of the state. N-Queens must reset all three arrays. Permutations must reset both used[i] and current.
  • Storing a reference instead of a copy in the results. All answers point at the same object and end up empty.
  • Using i > 0 instead of i > start in the subset duplicate skip. That wrongly blocks valid repeats at different depths.
  • Leaving out !used[i-1] in the permutation duplicate skip, or adding it to the subset version. The two conditions really are different.
  • Not sorting before a duplicate skip. The skip only works if equal values sit next to each other.
  • Removing duplicates with a set of results. It does the exponential work anyway, then pays extra to hash whole vectors.
  • Using continue where break works. On sorted input, going over the target means stop the loop, not skip one candidate.
  • Recursing with start+1 instead of i+1. This generates the same combination in several orders.
  • Changing a grid without restoring it in word search. This is the Chapter 34 difference between flood fill and backtracking.

Interview drill

Warm-up: Generate all subsets. Then handle duplicates in the input.

How a strong answer sounds
I use the choose/explore/unchoose skeleton with a loop that starts at a start index. At every node, I record the current vector as a valid subset. Then for each i from start to the end, I push a[i], recurse with i + 1, and pop. Recursing with i + 1, not start + 1, stops me reusing an element and stops the same subset appearing in several orders. Looping from start is exactly what makes order not matter. That gives 2ⁿ subsets in O(2ⁿ · n) time, with O(n) extra space beyond the output. For duplicates, I sort the input first so equal values sit next to each other. Then I skip a candidate when i > start and a[i] == a[i-1]. The condition is i > start, not i > 0, and the difference matters. I want to forbid two siblings at the same level that start with the same value. But I still want the same value at different depths, so that [2,2] is generated. I would avoid generating everything and removing duplicates with a set. That still does all the exponential duplicate work, then pays to hash whole vectors. Cutting the branch beats filtering at the leaf.

Deeper: Solve N-Queens. How do you make the conflict check O(1), and how much does pruning actually save?

How a strong answer sounds
First I narrow the search: exactly one queen per row, so at row r I only choose a column. That is already a pruning choice. It removes every "two queens share a row" option before generating it, cutting the space from choosing 8 of 64 squares down to 8⁸. Then three boolean arrays make the attack test constant time: cols[c], diag1[r+c] and diag2[r-c+n-1]. I work those indices out from the board rather than memorising them. Along an anti-diagonal the row goes up as the column goes down, so r+c stays fixed. Along a main diagonal both go up, so r-c stays fixed; I add n-1 to keep it from going negative. Each array needs 2n-1 slots. At each row I loop over the columns and skip any that is attacked. Otherwise I set all three flags, record the position, recurse, and then undo all four. Forgetting any one of them is the classic bug. On the savings: for N = 8 there are about 4.4 billion raw placements. With one queen per row there are 16.7 million. Adding the column rule makes it a permutation: 40,320. Pruning the diagonals as I go, the search visits roughly two thousand nodes to find all 92 solutions. That is about two million times less work, all from rejecting half-built states early. The general lesson: in backtracking the skeleton is simple, and the pruning is the real engineering problem.

🧠 Key takeaways

  • Choose, explore, unchoose: three lines in a row. The undo must restore everything you changed.
  • For combinations, loop from start and recurse with i+1. For permutations, loop from 0 with used[].
  • Handle duplicates by sorting plus a sibling skip: i > start for subsets, plus !used[i-1] for permutations.
  • Pruning is the real work. N-Queens drops from 4 × 10⁹ placements to about 2,000 nodes using three O(1) checks.
  • Backtracking is for listing solutions when n is small. If you only need a count or the best answer, use DP, greedy or flow.

Check your understanding

Why must backtracking undo its choice after the recursive call?

Sharing one changeable state is on purpose: copying it at every node would cost O(depth) per call. The price is that the undo becomes required. A missing undo is the most common bug in this chapter.

In the subsets-with-duplicates skip, why i > start rather than i > 0?

i > start means "not the first choice at this level". With i > 0 you would also block the valid use of a repeated value deeper down, and lose subsets like [2,2].

In N-Queens, why is diag2 indexed by r - c + n - 1?

Work it out from the board. Down-right diagonals keep r − c fixed. Anti-diagonals keep r + c fixed. Both need 2n−1 slots. If you only memorise the formula, you will get it wrong under pressure.

In combination sum on a sorted array, you hit a candidate larger than the remaining target. What do you do?

Sorting makes this cut possible. continue tests every remaining candidate for nothing. break cuts off the whole rest of the loop. This one keyword is often the difference between instant and hopelessly slow.

You need the number of subsets summing to K, with n = 100. Is backtracking right?

2¹⁰⁰ is far too many to list, by any margin. When you need a count or the best answer instead of the actual list, and subproblems repeat, that is the sign to use DP (Chapters 11 and 40).
