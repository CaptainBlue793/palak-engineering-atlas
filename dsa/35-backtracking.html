Backtracking

Backtracking is exhaustive search made systematic: choose, explore, unchoose. Every solution in this chapter is that same three-line skeleton with different choices and different pruning — and the interesting engineering is almost entirely in the pruning, because the naive search is exponential and the pruned one is often fast enough to be practical.

  • Write the choose/explore/unchoose skeleton and say why the undo is mandatory
  • Generate subsets, permutations and combinations, including with duplicates
  • Handle duplicates with sorting plus the skip condition, rather than a result set
  • Prune with O(1) conflict checks — N-Queens with three boolean arrays
  • Estimate the search-tree size, and know when backtracking is the wrong tool

The skeleton

choose · explore · unchooseevery problem in this chapter
void backtrack(State &current,Result &ans){
	if(isComplete(current)){
		ans.push_back(current);       // record a COPY
		return;
	}

	for(auto &choice:candidates(current)){
		if(!isValid(current,choice))continue;   // PRUNE — the whole game

		apply(current,choice);                // 1. CHOOSE
		backtrack(current,ans);                // 2. EXPLORE
		undo(current,choice);                 // 3. UNCHOOSE
	}
}
The undo is not optional, and it is where the bugs are. current is a single object shared by every branch of the recursion — that is deliberate, because copying it at each node would be O(depth) per call. So anything you add on the way down must be removed on the way up, or every later branch inherits your choices. And the recorded result must be a copy: pushing a reference to current means all your answers alias the same object, which ends up empty.
✍️
My convention: the undo is the line immediately after the recursive call, always

Write apply / recurse / undo as three consecutive lines with nothing between them, so the symmetry is visible and a missing undo is obvious on sight. Resist the temptation to return early from inside the loop without undoing — if you need an early exit (a boolean "found it" search like Sudoku), return true before the undo is correct only because you are abandoning the whole search; if you might continue, undo first. This is the Chapter 11 rule about shared state, and it is the single most common source of wrong answers in this chapter.

Subsets: the include/exclude tree

// At each index, two choices: take a[i] or do not. 2^n leaves.
void subsets(vector<int> &a,int i,vector<int> &current,vector<vector<int>> &ans){
	if(i==a.size()){
		ans.push_back(current);
		return;
	}

	subsets(a,i+1,current,ans);        // exclude a[i]

	current.push_back(a[i]);              // CHOOSE
	subsets(a,i+1,current,ans);        // EXPLORE
	current.pop_back();                  // UNCHOOSE
}

// The "for loop over remaining" form. Same 2^n outputs, but it records
// at EVERY node rather than only at leaves — which is often what you want.
void subsets2(vector<int> &a,int start,vector<int> &current,vector<vector<int>> &ans){
	ans.push_back(current);              // every node is a valid subset

	for(int i=start;i<a.size();i++){
		current.push_back(a[i]);
		subsets2(a,i+1,current,ans);     // i+1, NOT start+1
		current.pop_back();
	}
}

i+1 not start+1 in the recursive call — that is what prevents reusing an element and what stops the same subset appearing in a different order. This "for loop from start" shape is the one to memorise; it generalises to combinations and to combination-sum by changing the recursion index.

// SORT FIRST, then skip a value that equals its predecessor at the same level.
// Sorting is what makes duplicates adjacent, which is what makes the skip work.
void subsetsDup(vector<int> &a,int start,vector<int> &current,vector<vector<int>> &ans){
	ans.push_back(current);

	for(int i=start;i<a.size();i++){
		if(i>start and a[i]==a[i-1])continue;   // skip a duplicate SIBLING

		current.push_back(a[i]);
		subsetsDup(a,i+1,current,ans);
		current.pop_back();
	}
}
vector<vector<int>> subsetsWithDup(vector<int> &a){
	sort(a.begin(),a.end());              // mandatory

	vector<vector<int>> ans;
	vector<int> current;
	subsetsDup(a,0,current,ans);

	return ans;
}

i > start, not i > 0 — this is the detail that matters. We want to allow [2,2] (the same value at different depths) while forbidding two branches at the same depth that both start with 2. i > start says "this is not the first choice at this level", which is exactly the sibling condition.

// No recursion at all: iterate every n-bit integer and read its bits.
// Only works when n is small (<= ~20) and there are no duplicates.
vector<vector<int>> subsetsBitmask(vector<int> &a){
	int n=a.size();
	vector<vector<int>> ans;

	for(int mask=0;mask<(1<<n);mask++){
		vector<int> current;

		for(int i=0;i<n;i++){
			if(mask&(1<<i))
			current.push_back(a[i]);
		}

		ans.push_back(current);
	}

	return ans;
}

Shorter and stack-free, and it makes the 2ⁿ explicit. But it cannot prune — you enumerate every mask whether it is viable or not — so for any problem with constraints the recursive version wins. Chapter 44 builds bitmask DP on this representation.

Permutations, and the duplicate rule again

permutations, with and without duplicatesO(n! · n)O(n)
// Without duplicates: a used[] array marks what is already in the prefix.
void permute(vector<int> &a,vector<bool> &used,vector<int> &current,vector<vector<int>> &ans){
	if(current.size()==a.size()){
		ans.push_back(current);
		return;
	}

	for(int i=0;i<a.size();i++){
		if(used[i])continue;

		used[i]=true;
		current.push_back(a[i]);

		permute(a,used,current,ans);

		current.pop_back();
		used[i]=false;               // BOTH must be undone
	}
}

// WITH duplicates: sort, then skip a value equal to its predecessor
// UNLESS that predecessor is currently in use (i.e. we are deeper in the
// same branch). That condition is the whole trick.
void permuteDup(vector<int> &a,vector<bool> &used,vector<int> &current,vector<vector<int>> &ans){
	if(current.size()==a.size()){
		ans.push_back(current);
		return;
	}

	for(int i=0;i<a.size();i++){
		if(used[i])continue;
		if(i>0 and a[i]==a[i-1] and !used[i-1])continue;

		used[i]=true;
		current.push_back(a[i]);

		permuteDup(a,used,current,ans);

		current.pop_back();
		used[i]=false;
	}
}
!used[i-1] is the part worth understanding rather than memorising. Among equal values we force a canonical order: the copy at index i may only be placed if the copy at i−1 is already placed. If a[i−1] is unused, then choosing a[i] now would produce a permutation identical to one we get by choosing a[i−1] instead — so we skip it. Compare this with the subsets condition i > start: both suppress duplicate siblings, but permutations need the used test because the same value can legitimately appear at two different depths.
🚫
Do not deduplicate with a set of results

It is tempting to generate everything and drop the duplicates into a set<vector<int>>. It works, and it is the wrong answer in two ways: it still does all the exponential duplicate work, only to throw it away, and each insert costs O(size log n) to hash or compare a whole vector. Sorting plus the skip condition prunes the duplicate branches before exploring them, which is both faster and the thing the interviewer is checking for. Prune at the branch, not at the leaf.

N-Queens: pruning is the whole problem

Place N queens on an N×N board with none attacking another. The naive search over all placements is astronomical; with the right state the search tree collapses to something tiny.

solveNQueens — three boolean arrays, O(1) conflict checkO(n!) worst, far less in practiceO(n)
// Place one queen per row, so we only choose a COLUMN for each row.
// Three arrays make "is this square attacked?" O(1) instead of O(n):
//   cols[c]       — a queen already in column c
//   diag1[r+c]    — the anti-diagonal: r+c is constant along it
//   diag2[r-c+n-1] — the main diagonal: r-c is constant; shift to make it >= 0
void solve(int row,int n,vector<int> &pos,
           vector<bool> &cols,vector<bool> &diag1,vector<bool> &diag2,
           vector<vector<int>> &ans){
	if(row==n){
		ans.push_back(pos);
		return;
	}

	for(int c=0;c<n;c++){
		int d1=row+c;
		int d2=row-c+n-1;

		if(cols[c] or diag1[d1] or diag2[d2])continue;    // PRUNE in O(1)

		cols[c]=diag1[d1]=diag2[d2]=true;      // CHOOSE
		pos.push_back(c);

		solve(row+1,n,pos,cols,diag1,diag2,ans);   // EXPLORE

		pos.pop_back();                          // UNCHOOSE — all four
		cols[c]=diag1[d1]=diag2[d2]=false;
	}
}
vector<vector<int>> solveNQueens(int n){
	vector<vector<int>> ans;
	vector<int> pos;
	vector<bool> cols(n,false);
	vector<bool> diag1(2*n-1,false);
	vector<bool> diag2(2*n-1,false);

	solve(0,n,pos,cols,diag1,diag2,ans);

	return ans;
}
Derive the diagonal indices, do not memorise them. Along an anti-diagonal (going down-left) the row increases as the column decreases, so r + c is constant — ranging 0 to 2n−2, hence the size 2n−1. Along a main diagonal (down-right) both increase, so r − c is constant — ranging −(n−1) to n−1, so add n−1 to shift it non-negative. Placing one queen per row is itself a pruning decision: it removes the entire "two queens in one row" branch of the search space before it is ever generated.
✂️
The three levels of pruning, and what each is worth

That is a factor of two million, and every bit of it comes from rejecting a partial state early. The lesson generalises: in backtracking, the algorithm is trivial and the pruning is the engineering. Always ask “can I detect failure before the branch is fully built?”

Combination sum: the three variants

combinationSum — reuse allowed, then not, then with duplicatesexponential, heavily prunedO(target)
// VARIANT 1: each number may be reused. Recurse with i, not i+1.
void combo(vector<int> &a,int start,int remaining,
           vector<int> &current,vector<vector<int>> &ans){
	if(remaining==0){
		ans.push_back(current);
		return;
	}

	for(int i=start;i<a.size();i++){
		if(a[i]>remaining)break;      // SORTED, so everything after is too big

		current.push_back(a[i]);
		combo(a,i,remaining-a[i],current,ans);   // i = reuse allowed
		current.pop_back();
	}
}

// VARIANT 2: each number used at most once -> recurse with i+1.
// VARIANT 3: input has duplicates -> add the sibling skip as well:
//   if(i>start and a[i]==a[i-1])continue;
//   and recurse with i+1.
The break rather than continue is the important pruning. Because the array is sorted, the first candidate exceeding remaining means every later one does too — so we abandon the whole rest of the loop instead of testing each. That single keyword turns an exponential search into one that finishes instantly on typical inputs. Sorting is not just for duplicate handling; it enables this cut.

Looping from start is what makes order irrelevant; looping from 0 with used[] is what makes it matter. Getting this one choice right decides whether you generate subsets or permutations, and it is the first thing to fix when your output has the wrong count.

When backtracking is the wrong tool

📈

n is large

2ⁿ is fine to n ≈ 20 and n! only to n ≈ 10. If n is 100 and the problem still asks for an optimum, it is DP, greedy or flow — not search.

🔁

You only need the count, not the list

Counting rarely needs enumeration. Count subsets summing to K with DP (Chapter 40) in O(n·K), not 2ⁿ.

♻️

Subproblems repeat

If the same state recurs across branches, memoise — that is Chapter 38. The recursion tree having duplicate nodes is the DP signal (Chapter 11).

✅

A greedy provably works

Interval scheduling, Huffman, jump game. If you can prove an exchange argument (Chapter 36), search is wasted effort.

🧩

It is an assignment problem

“Match these to those” is bipartite matching or flow in polynomial time (Chapter 33), not n! search.

✔️

But backtracking is right when…

you must list all solutions, n is genuinely small, the constraints prune hard, or the problem is NP-hard and there is no better option — Sudoku, N-Queens, word search, expression building.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SORT TO DEDUPE
Sort first, then skip i > start && a[i] == a[i-1]. That is how you avoid duplicate subsets without a set — and the condition is on the sibling, not the parent.
💡 PRUNE EARLY
Check feasibility before recursing, not at the leaf. A bound that cuts a branch at depth 2 saves more than any micro-optimisation at depth 12.
⛔ RESTORE EXACTLY
Whatever you changed going down must be undone coming up — including the grid cell you marked as visited. A missing unmark is the classic word-search bug.
⚠️
Common mistakes
  • Forgetting the undo. Every later branch inherits your choices and the output is garbage.
  • Undoing only part of the state. N-Queens must reset all three arrays; permutations must reset both used[i] and current.
  • Pushing a reference instead of a copy into the results. All answers alias the same object and end up empty.
  • Using i > 0 instead of i > start in the subset duplicate skip. That suppresses legitimate repeats at different depths.
  • Omitting !used[i-1] in the permutation duplicate skip, or including it in the subset version. The two conditions are genuinely different.
  • Not sorting before a duplicate skip. The skip relies on equal values being adjacent.
  • Deduplicating with a result set. Does the exponential work anyway, then pays to hash whole vectors.
  • continue where break is available. On sorted input, exceeding the target means abandon the loop, not skip one candidate.
  • Recursing with start+1 instead of i+1. Generates the same combination in several orders.
  • Mutating a grid without restoring it in word search — the Chapter 34 distinction between flood fill and backtracking.

Interview drill

Warm-up: Generate all subsets. Then handle duplicates in the input.

How a strong answer sounds
I use the choose/explore/unchoose skeleton with a loop from a start index: record the current vector as a valid subset at every node, then for each i from start to the end, push a[i], recurse with i + 1, and pop. Recursing with i + 1 rather than start + 1 is what prevents reusing an element and what stops the same subset being generated in several orders — looping from start is precisely what makes order irrelevant. That gives 2ⁿ subsets in O(2ⁿ · n) time and O(n) auxiliary space beyond the output. For duplicates, I sort the input first so equal values are adjacent, then skip a candidate when i > start and a[i] == a[i-1]. The condition is i > start, not i > 0, and that distinction matters: I want to forbid two siblings at the same level starting with the same value, while still allowing the same value to appear at different depths so [2,2] is generated. What I would avoid is generating everything and deduplicating into a set — it still does all the exponential duplicate work and then pays to hash whole vectors. Pruning the branch beats filtering the leaf.

Deeper: Solve N-Queens. How do you make the conflict check O(1), and how much does pruning actually save?

How a strong answer sounds
First I restrict the search: exactly one queen per row, so at row r I only choose a column. That is itself a pruning decision — it deletes the entire "two queens share a row" region before generating it, cutting the space from choosing 8 of 64 squares down to 8⁸. Then three boolean arrays make the attack test constant time: cols[c], diag1[r+c] and diag2[r-c+n-1]. Those indices come from the geometry rather than memorisation — along an anti-diagonal the row rises as the column falls so r+c is invariant, and along a main diagonal both rise so r-c is invariant, shifted by n-1 to keep it non-negative, each needing 2n-1 slots. At each row I loop over columns, skip any that is attacked, otherwise set all three flags plus record the position, recurse, and then undo all four — forgetting any one of them is the classic bug. On the savings: for N = 8 there are about 4.4 billion raw placements, 16.7 million with one queen per row, 40,320 once the column constraint makes it a permutation, and with diagonals pruned incrementally the search visits roughly two thousand nodes to find all 92 solutions. That is a factor of about two million, all of it from rejecting partial states early — which is the general lesson: in backtracking the skeleton is trivial and the pruning is the entire engineering problem.

🧠 Key takeaways

  • Choose, explore, unchoose — three consecutive lines, and the undo must restore all mutated state.
  • Loop from start and recurse with i+1 for combinations; loop from 0 with used[] for permutations.
  • Handle duplicates by sorting plus a sibling skip — i > start for subsets, and additionally !used[i-1] for permutations.
  • Pruning is the engineering: N-Queens goes from 4 × 10⁹ placements to ~2,000 nodes on three O(1) checks.
  • Backtracking is for listing solutions at small n; if you only need a count or an optimum, reach for DP, greedy or flow.

Check your understanding

Why must backtracking undo its choice after the recursive call?

Sharing one mutable state is deliberate — copying at every node would be O(depth) per call. The price is that the undo becomes mandatory, and a missing one is the most common bug in this chapter.

In the subsets-with-duplicates skip, why i > start rather than i > 0?

i > start means "not the first choice at this level". With i > 0 you would also suppress the legitimate deeper use of a repeated value, losing subsets like [2,2].

In N-Queens, why is diag2 indexed by r - c + n - 1?

Derive it from the geometry: down-right diagonals hold r − c fixed, anti-diagonals hold r + c fixed, and both need 2n−1 slots. Memorising the formula is how you get it wrong under pressure.

In combination sum on a sorted array, you hit a candidate larger than the remaining target. What do you do?

Sorting buys this cut. continue tests each remaining candidate pointlessly; break prunes the entire tail of the loop. This one keyword is often the difference between instant and hopeless.

You need the number of subsets summing to K, with n = 100. Is backtracking right?

2¹⁰⁰ is beyond enumeration by any margin. When you need a count or an optimum rather than the actual list, and subproblems repeat, that is the DP signal (Chapters 11 and 40).
