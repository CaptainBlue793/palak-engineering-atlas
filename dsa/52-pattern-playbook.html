The Pattern Playbook

Fifty-one chapters of techniques are worth little if you cannot decide which one within the first two minutes of a problem. This chapter is the index to everything before it: a decision procedure, a table mapping constraints to complexity budgets, and twenty-four patterns each reduced to the tell that gives it away. Read it as a reference and drill the recognition, not the implementations.

  • Run the four-question decision procedure on any new problem
  • Read the constraints backwards to get a complexity budget
  • Recognise twenty-four patterns from their one-line tells
  • Distinguish the pairs that are genuinely easy to confuse
  • Know what to do when nothing matches

The decision procedure

Four questions, in this order. Most problems are pinned down by the second.

1
What is the input's shape?

Array, string, linked list, tree, graph, grid, matrix, stream, or a set of intervals. This alone eliminates most of the book. Sorted array, rooted tree, weighted graph — each qualifier is a further cut, and a stated sort order is never decoration.

2
What is the output?

One number (optimise or count), a boolean (feasibility), one arrangement (construct), all arrangements (enumerate), or a modified input (in-place). "All" means backtracking or bitmask enumeration and an exponential bound; "how many" is usually DP or combinatorics; "the best" is DP, greedy or a search.

3
What do the constraints permit?

Work backwards from roughly 10⁸ operations per second. n ≤ 20 invites exponential; n ≤ 500 invites O(n³); n ≤ 10⁵ demands O(n log n) or better; n ≤ 10⁹ means the answer cannot involve enumerating n at all — think binary search on the answer, mathematics, or digit DP.

4
What is the redundancy?

Write the brute force, then name what it recomputes. Overlapping subproblems → DP. A recomputed window aggregate → sliding window or prefix sums. A repeated search → hash map or sorting. A repeated "nearest bigger" → monotonic stack. A repeated minimum → heap. Every optimisation in this course is the removal of one specific kind of repeated work.

✍️
My convention: brute force first, out loud, always

I never skip step 4, even when I recognise the pattern instantly. Stating the brute force does four things: it proves I understand the problem, it establishes a correct baseline I can test the fast version against, it produces the optimisation by making the redundancy visible, and it gives the interviewer something to react to within two minutes. An optimal solution I cannot derive is a memorised one, and it collapses the moment the follow-up changes a constraint. The derivation is the transferable skill; the code is a consequence.

Other numbers that are telling you something
  • "values up to 10⁴" while n is 10⁵ — counting sort, or a DP indexed by value rather than position. A small value range is an invitation to use it as an array index.
  • "lowercase English letters" — a fixed 26-element array, or a 26-bit mask (Ch 47). Alphabet size becomes a constant.
  • "the answer fits in 32 bits" / "modulo 10⁹+7" — counting with overflow, so modular arithmetic (Ch 48).
  • "in O(1) extra space" — in-place pointer manipulation, XOR tricks, Floyd's cycle detection, or index-as-a-hash marking.
  • "the array is sorted" / "rotated sorted" — binary search or two pointers, essentially always.
  • "a stream" / "you cannot store the input" — one pass with O(1) or O(k) state: reservoir sampling, a size-k heap, running aggregates.
  • q queries up to 10⁵ on a static array — precompute: prefix sums, sparse table, or an offline sweep. Per-query O(n) will not do.
  • n up to 10⁵ but the answer range is huge — binary search on the answer with an O(n) feasibility check (Ch 9).

The confusable pairs

⚖️
Six distinctions worth being crisp about
  • Sliding window vs. two pointers. A window is a contiguous range whose aggregate you maintain; two pointers usually converge from the ends of a sorted array. If the answer is a subarray, think window; if it is a pair, think two pointers.
  • Greedy vs. DP. Greedy commits irrevocably and needs a proof (exchange argument or a matroid-style claim); DP keeps every option and needs no proof beyond the recurrence. If you cannot prove the greedy rule in a sentence, write the DP.
  • BFS vs. Dijkstra. BFS is correct only with uniform edge cost. The instant weights differ, a queue processes nodes in the wrong order — use a heap, or a deque for 0/1 weights.
  • DP vs. graph search on a grid. DP needs an acyclic dependency order. Right-and-down movement gives one (i+j increases); all four directions does not, and then it is BFS or Dijkstra (Ch 42).
  • Memoisation vs. tabulation. Identical complexity. Top-down is easier to derive and skips unreachable states; bottom-up avoids stack depth and permits space rolling. Derive top-down, convert if needed (Ch 38).
  • Heap vs. sorting vs. quickselect for top-k. Sorting is O(n log n) and always correct; a size-k heap is O(n log k) and handles streams; quickselect is expected O(n) but mutates the input (Ch 49). State all three, then choose.
🤷
When nothing matches

It happens, and there is a procedure for it rather than a panic.

  • Solve a smaller case by hand. n = 1, 2, 3. Write the answers down and look for the recurrence between them — this is how most DP recurrences are actually found.
  • Reduce to something known. "Can I turn this into a graph?" is the highest-yield question in the book — scheduling, currency conversion, word ladders, equation consistency and dependency resolution are all graph problems in costume.
  • Invert the question. Count the complement; find what is missing rather than present; process from the right; think about the last operation instead of the first (Ch 45's burst balloons).
  • Sort it and look again. A surprising number of problems become obvious under some ordering.
  • Loosen a constraint. Solve it without the O(1)-space requirement, then optimise space. Partial credit beats silence, and the relaxed solution often reveals the real one.
  • Ask about the input. Duplicates? Negatives? Sorted? Empty? A single clarification sometimes collapses the problem — and asking is never a mark against you.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 FOUR QUESTIONS
Shape, output, constraints, redundancy — in that order. Most problems are pinned down by the second, and the fourth hands you the technique.
💡 NAME THE WASTE
Every optimisation removes one kind of repeated work: overlapping subproblems → DP, recomputed window → sliding window, repeated "nearest bigger" → monotonic stack.
💡 MAKE IT A GRAPH
When nothing matches, ask what the nodes and edges are. Scheduling, currency conversion, word ladders and equation consistency are all graph problems in costume.
⚠️
Common mistakes in pattern selection
  • Pattern-matching on surface words rather than structure. "Subarray" does not always mean sliding window — a window needs the constraint to be monotone as it grows.
  • Ignoring the constraints. They are the strongest hint available and they are stated for a reason.
  • Jumping to the optimal solution without stating the brute force, so the derivation is invisible and the follow-up breaks you.
  • Using a greedy rule without proving it. Most plausible greedy rules are wrong; find the counterexample or write the DP.
  • BFS on a weighted graph, which returns fewest-edges rather than cheapest.
  • Reaching for a segment tree when the array is static and prefix sums suffice.
  • Sorting when the input order carries information the problem depends on.
  • DP on a state that is not sufficient — if two different histories with the same state need different answers, add a dimension.
  • Optimising before the brute force is correct. A fast wrong answer is worth nothing.
  • Forcing a remembered pattern onto a problem that does not fit, instead of going back to step 4 and naming the redundancy.

Interview drill

Warm-up: "Given an array of n ≤ 10⁵ positive integers and an integer k, split the array into k contiguous parts so as to minimise the largest part sum." Talk through your first two minutes.

How a strong answer sounds
Let me run through the shape, the output, the constraints and the redundancy. The shape is an array, with contiguity required — so the splits are k−1 cut positions. The output is a single number, and specifically it is minimise the maximum, which is a phrase that almost always signals binary search on the answer. The constraints confirm it: n is 10⁵, so I have an O(n log something) budget, and the answer's range is from the largest single element up to the total sum — around 10¹⁴ if values reach 10⁹, which is 47 binary-search steps. So the plan is: binary search the candidate maximum part sum m, and for each m test feasibility greedily in O(n) — walk the array accumulating, and start a new part whenever adding the next element would exceed m. If the number of parts needed is at most k, then m is feasible. That check is monotone in m, which is the property binary search requires and the thing I would justify explicitly: a larger allowance never increases the number of parts needed. Total O(n log(total sum)), which is about 5·10⁶ operations. Two boundary details: the search's lower bound must be max(element), not 0, since no part can be smaller than its largest member; and I would return low after the standard "find the smallest feasible value" loop shape. I would also note the alternative — an O(n²k) DP over dp[i][j], the best split of the first i elements into j parts — which is correct and is the right answer if k were tiny and n small, but is far too slow here. Naming both and choosing on the constraints is the point.

Deeper: "You are given a list of currency exchange rates between pairs. Determine whether a sequence of trades can turn 1 unit of some currency into more than 1 unit of the same currency." What pattern is this?

How a strong answer sounds
This is the "can I turn this into a graph?" question, and the answer is yes — it is negative-cycle detection, which means Bellman-Ford. The reduction is the interesting part. Currencies are nodes and each exchange rate is a directed edge. An arbitrage opportunity is a cycle whose rates multiply to more than 1, and Bellman-Ford works additively, not multiplicatively — so I transform each weight to −log(rate). Then a product of rates greater than 1 becomes a sum of logs greater than 0, which becomes a sum of negated logs less than 0: exactly a negative cycle. So I run Bellman-Ford over V−1 rounds and then do one extra relaxation pass; if any edge still improves, a negative cycle is reachable and arbitrage exists. O(V·E), which is fine because currency counts are small. Two things I would flag. First, Bellman-Ford only detects negative cycles reachable from the source, so to catch a cycle anywhere I either add a virtual source with zero-weight edges to every node, or initialise every distance to 0 — the latter is the neater trick and is worth knowing. Second, floating-point logs introduce rounding, so I would compare against a small epsilon rather than strict zero, and if exactness mattered I would say so as a limitation. The transferable lesson is that the tell here was not any keyword in the problem statement but the structure: pairwise relationships plus a multiplicative round trip. Scheduling, word ladders, equation consistency and dependency resolution all disguise themselves the same way, and asking "what are the nodes and what are the edges?" is the single highest-yield move when no pattern matches.

🧠 Key takeaways

  • Shape, output, constraints, redundancy — in that order. Most problems are pinned by the second question.
  • Constraints are a complexity budget: read them backwards from 10⁸ operations to find the intended approach.
  • Every optimisation removes one specific kind of repeated work; name the redundancy and the technique follows.
  • State the brute force aloud even when you know the answer — it is the derivation, the baseline and the proof of understanding.
  • When nothing matches: solve n = 1, 2, 3 by hand, try to make it a graph, invert the question, or relax a constraint.

Check your understanding

A problem gives n ≤ 18 and asks for the minimum cost to assign every task exactly once. What does the bound tell you?

n ≤ 20 with "each exactly once" is the bitmask signature: too small to need anything polynomial, too large for n! brute force. The bound is a hint, not a courtesy.

"Minimise the maximum load" with an answer range up to 10¹⁴ suggests…

"Minimise the maximum" or "maximise the minimum", plus a huge answer range, is the tell. The requirement to verify is that feasibility is monotone in the candidate.

You have a grid where movement is allowed in all four directions and each cell has a positive cost. Grid DP fails because…

Right-and-down movement gives an acyclic order because i+j strictly increases. Four directions destroys it, and "iterate until nothing changes" is just a slow Bellman-Ford.

What is the most reliable way to derive the right technique on an unfamiliar problem?

Overlapping subproblems → DP; a recomputed window aggregate → sliding window; a repeated "nearest bigger" → monotonic stack. Every optimisation removes one specific kind of repeated work.

When should you choose greedy over DP?

Most plausible greedy rules are wrong. If you cannot give an exchange argument in a sentence, look for the counterexample, and write the DP if you find one.
