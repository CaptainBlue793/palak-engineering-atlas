The Pattern Playbook

Fifty-one chapters of techniques are worth little if you cannot pick the right one in the first two minutes of a problem. This chapter is the index to everything before it. It gives you four questions to ask, a table that turns the input limits into a speed budget, and twenty-four patterns, each boiled down to the one clue that gives it away. Use it as a reference, and practise spotting the pattern rather than writing the code.

  • Run the four-question decision procedure on any new problem
  • Read the constraints backwards to get a complexity budget
  • Recognise twenty-four patterns from their one-line tells
  • Distinguish the pairs that are genuinely easy to confuse
  • Know what to do when nothing matches

The decision procedure

Ask these four questions, in this order. Most problems are narrowed down by the second one.

1
What is the input's shape?

Is it an array, string, linked list, tree, graph, grid, matrix, stream, or a set of intervals? This one question rules out most of the book. Then look at the extra words: a sorted array, a rooted tree, a weighted graph. Each one narrows things further. If the problem says the input is sorted, that is never just decoration.

2
What is the output?

Is it one number (a best value or a count), a yes/no answer (is it possible?), one valid arrangement, all arrangements, or the input changed in place? "All" means backtracking or bitmask enumeration, and an exponential running time. "How many" is usually DP or counting maths. "The best" is DP, greedy or a search.

3
What do the constraints permit?

Work backwards from about 10⁸ operations per second. n ≤ 20 invites an exponential solution. n ≤ 500 invites O(n³). n ≤ 10⁵ demands O(n log n) or better. n ≤ 10⁹ means you cannot even loop over n once, so think binary search on the answer, maths, or digit DP.

4
What is the redundancy?

Write the slow, obvious solution (the "brute force"), then name what it computes twice. The same subproblem solved again → DP. A window's total recomputed from scratch → sliding window or prefix sums. The same search repeated → hash map or sorting. "Next bigger element" asked repeatedly → monotonic stack. The minimum asked repeatedly → heap. Every speed-up in this course removes one specific kind of repeated work.

✍️
My convention: brute force first, out loud, always

I never skip step 4, even when I spot the pattern instantly. Saying the brute force out loud does four things:

  • It shows I understand the problem.
  • It gives me a correct baseline to test the fast version against.
  • It produces the speed-up, by making the repeated work visible.
  • It gives the interviewer something to respond to within two minutes.

A fast solution I cannot work out from scratch is a memorised one, and it falls apart the moment a follow-up question changes a constraint. Working it out is the skill that carries over. The code just follows from it.

The four questions on one problem. "Given n ≤ 10⁵ integers, which may be negative, count the subarrays that add up to k."

  1. Shape: an array, and a subarray means a block of neighbouring elements. That points to windows, prefix sums or two pointers.
  2. Output: a count, not a list. So you never have to write out the subarrays themselves, which could number about n²/2.
  3. Constraints: n = 10⁵, so O(n²) is about 10¹⁰ operations, which is too slow. You need O(n) or O(n log n).
  4. Redundancy: the brute force tries every (start, end) pair and adds up each range again from scratch. The repeated work is those sums. Prefix sums remove it: the sum of nums[l..r] is P[r+1] − P[l]. Now the question becomes "for each r, how many earlier prefixes equal P[r+1] − k?" That is a repeated search, so use a hash map of prefix counts. The total is O(n).

Check it on [1, 2, 3] with k = 3. The prefix sums are 0, 1, 3, 6. At 3, you need an earlier 0: there is one, which is the subarray [1,2]. At 6, you need an earlier 3: there is one, which is [3]. The total is 2, which is correct. Notice the word "negative" in the problem. It rules out a sliding window: with negative numbers, adding an element can make the sum smaller, so there is no reliable moment to shrink the window. One word in the constraints decided the pattern.

Where the table comes from. Take about 10⁸ simple operations per second, then put the largest n into each running time.

  • n = 10⁵: n² = 10¹⁰, which is about 100 seconds and far too slow. n log n ≈ 10⁵ × 17 ≈ 1.7·10⁶, which is instant.
  • n = 20: 2ⁿ·n ≈ 10⁶ × 20 = 2·10⁷, which is fine. At n = 30 it would be about 3·10¹⁰, which is not.
  • n = 500: n³ = 1.25·10⁸, which is about one second and on the edge. That is why O(n³) problems cap n at a few hundred.

Treat the table as a guide, not a law. Two things shift it. First, many test cases in one input. If there are up to 10⁴ tests, look for a line like "the sum of n over all tests is at most 2·10⁵". That total is what your budget is based on. Second, heavy constant factors. Hash maps, recursion and std::map are several times slower than plain array loops, so an O(n log n) with a big constant can still be too slow at the top of its range.

Meet in the middle is the one row not taught elsewhere, so here it is in brief. With n = 40, trying all 2⁴⁰ ≈ 10¹² subsets is hopeless. Split the items into two halves of 20. List every subset sum of each half, which is 2²⁰ ≈ 10⁶ sums each. Sort one list, and for each sum in the other list, binary search for the partner that makes the target. Two lists of about a million replace one list of a trillion.

🔎
Other numbers that are telling you something
  • "values up to 10⁴" while n is 10⁵. Counting sort, or a DP indexed by value instead of position. A small range of values is an invitation to use the value as an array index.
  • "lowercase English letters". A fixed 26-element array, or a 26-bit mask (Ch 47). The alphabet size becomes a constant.
  • "the answer fits in 32 bits" or "give the answer modulo 10⁹+7". The count would overflow, so use modular arithmetic (Ch 48).
  • "in O(1) extra space". Work in place with pointers, XOR tricks, Floyd's cycle detection, or marking answers in the array's own indices.
  • "the array is sorted" or "rotated sorted". Binary search or two pointers, almost every time.
  • "a stream", or "you cannot store the input". One pass with O(1) or O(k) memory: reservoir sampling, a size-k heap, or running totals.
  • Up to 10⁵ queries on an array that never changes. Precompute something: prefix sums, a sparse table, or one offline sweep. O(n) per query is too slow.
  • n up to 10⁵, but the range of possible answers is huge. Binary search on the answer, with an O(n) check of whether a candidate works (Ch 7).

The twenty-four patterns

01 Two pointers
A sorted array, and you need a pair, triple or subarray. Also: splitting an array in place, merging two sorted lists, reversing.
Ch 4 · O(n)
02 Sliding window
"Longest / shortest / how many next to each other", plus a rule that only gets harder to satisfy as the window grows.
Ch 5 · O(n)
03 Prefix sums
Many range-sum questions on an array that never changes, or "a subarray adding up to k" (pair it with a hash map).
Ch 6 · O(n) build, O(1) query
04 Binary search on an array
Sorted input, and you need a target, a boundary, or where a value would be inserted. Rotated arrays or duplicates are variations, not new patterns.
Ch 7 · O(log n)
05 Binary search on the answer
"Make the largest part as small as possible", "make the smallest part as large as possible", a huge range of answers, and a check that only flips once as the candidate grows.
Ch 7 · O(n log range)
06 Hash map / set
"Have I seen this before?", counting how often things appear, grouping by a key, or looking up "the number I still need". The default way to remove a repeated search.
Ch 9 · O(1) average
07 Sorting as a pre-step
The problem becomes easy once things are in order: intervals, grouping anagrams, greedy choices by a ratio, removing duplicates.
Ch 8 · O(n log n)
08 Monotonic stack
"Next greater / previous smaller", largest rectangle in a histogram, or how long a run lasts. Anything where a bigger element makes an earlier one useless.
Ch 13 · O(n)
09 Heap / top-k
"k largest", "k closest", merging k sorted lists, or a median that updates as data arrives. Use a heap of size k for streams.
Ch 15 · O(n log k)
10 Linked-list pointers
Cycle detection, middle node, reversal, or "in O(1) space" on a list. Fast and slow, or three-pointer reversal.
Ch 12 · O(n), O(1) space
11 Tree traversal
Anything done once per node. The real question is which order: in-order for sorted output from a BST, level-order for depth, post-order when a node needs its children's results first.
Ch 16–17 · O(n)
12 Tree DP
Each subtree's value feeds into its parent. Keep "what I report upward" separate from "the best answer passing through me".
Ch 43 · O(n)
13 BFS
Shortest path when every step costs the same, spreading out level by level, or "fewest number of steps".
Ch 25, 29 · O(V+E)
14 DFS / flood fill
Connectivity, components, islands, cycle detection, or exploring every path from a node.
Ch 25 · O(V+E)
15 Topological sort
Dependencies, prerequisites, putting a one-way graph with no cycles (a DAG) in order, or spotting a cycle in a directed graph.
Ch 26 · O(V+E)
16 Dijkstra / 0-1 BFS
Shortest path with non-negative weights. A deque instead of a heap when the only weights are 0 and 1.
Ch 29 · O(E log V)
17 Union-find
Groups that keep merging, "are these two in the same group?", Kruskal's minimum spanning tree, or merging groups of things treated as equivalent.
Ch 22 · near O(1)
18 Backtracking
"Find all" — permutations, combinations, subsets, board placements. Choose, recurse, undo. Prune early.
Ch 35 · exponential
19 Greedy
A simple step-by-step rule that you can prove gives the best overall answer: intervals sorted by end time, Huffman coding, problems solved by an exchange argument. Prove it.
Ch 36 · O(n log n)
20 1D / knapsack DP
A series of choices where the same subproblem keeps coming back; "take it or leave it"; a capacity or target to hit.
Ch 39–40 · O(n·target)
21 Two-string DP
Two sequences lined up against each other: longest common subsequence, edit distance, wildcard matching. dp[i][j] covers the first i and first j characters.
Ch 41 · O(n·m)
22 Interval DP
A range's answer is built from two neighbouring smaller ranges, with a split point you choose. Fill the table from short ranges to long ones.
Ch 45 · O(n³)
23 Bitmask DP
n ≤ 20, "use each one exactly once", or you must remember which items are used, not just how many.
Ch 44 · O(2ⁿ·n)
24 Trie / string algorithms
Questions about word beginnings, autocomplete, many patterns at once, or exact search in O(n+m) with KMP.
Ch 21, 50 · O(length)

Hard problems usually combine two cards. Medium problems often need one pattern. Harder ones join two, and seeing the join is the real skill. Some common pairings:

  • Sorting + two pointers: 3Sum. Sort, fix one number, then run two pointers on the rest for O(n²). The fix-one step works only because sorting made the rest monotone.
  • Binary search on the answer + greedy check: "ship packages within D days". The binary search guesses a capacity, and a greedy pass checks whether that capacity is enough.
  • Prefix sums + hash map: "count subarrays with sum k", worked through above.
  • BFS + bitmask: "shortest path that visits every node". The BFS state is (node, set of visited nodes), and the set is stored as an integer.
  • Heap + greedy: "meeting rooms", "task scheduler". The greedy rule says what to take next, and the heap finds it fast.

When one card gets you most of the way but one operation is still slow, ask which other card makes that operation fast.

The confusable pairs

⚖️
Six distinctions worth being crisp about
  • Sliding window vs. two pointers. A window is a block of neighbouring elements whose running total you keep updated. Two pointers usually move towards each other from the two ends of a sorted array. If the answer is a subarray, think window. If it is a pair, think two pointers.
  • Greedy vs. DP. Greedy makes a choice and never takes it back, so it needs a proof (an exchange argument, or showing the problem has the right structure). DP keeps every option open and needs no proof beyond the recurrence. If you cannot prove the greedy rule in one sentence, write the DP.
  • BFS vs. Dijkstra. BFS is only correct when every edge costs the same. As soon as costs differ, a plain queue visits nodes in the wrong order. Use a heap, or a deque when the only weights are 0 and 1.
  • DP vs. graph search on a grid. DP needs an order in which no cell depends on itself. Moving only right and down gives one, because i+j always increases. Moving in all four directions does not, and then you need BFS or Dijkstra (Ch 42).
  • Memoisation (top-down) vs. tabulation (bottom-up). Same complexity. Top-down is easier to work out and skips states you never reach. Bottom-up avoids deep recursion and lets you keep only the last row or two. Work it out top-down, then convert if you need to (Ch 38).
  • Heap vs. sorting vs. quickselect for top-k. Sorting is O(n log n) and always correct. A heap of size k is O(n log k) and handles streams. Quickselect is O(n) on average but rearranges the input (Ch 49). Say all three, then choose.

Two tiny counterexamples to keep in your head, because they show the wrong choice failing:

  • Greedy failing: coins {1, 3, 4}, target 6. Greedy takes the biggest coin first: 4 + 1 + 1, which is 3 coins. The best answer is 3 + 3, which is 2 coins. One small case like this is enough to reject a greedy rule and move to DP.
  • BFS failing on weights: an edge A→B costs 10, while A→C and C→B cost 1 each. BFS reaches B in one step and reports cost 10. Dijkstra finds A→C→B at cost 2. BFS minimises the number of edges, which is only the same as the cost when every edge costs the same.
🤷
When nothing matches

It happens. Work through this list instead of panicking.

  • Solve a tiny case by hand. Do n = 1, 2, 3. Write the answers down and look for how each one follows from the last. This is how most DP recurrences are actually found.
  • Turn it into a problem you know. "Can I make this a graph?" is the highest-value question in the book. Scheduling, currency conversion, word ladders, checking a set of equations for contradictions, and working out build order are all graph problems in disguise.
  • Flip the question round. Count the cases you do not want and subtract. Look for what is missing rather than what is there. Work from right to left. Think about the last move instead of the first (as in Ch 45's burst balloons).
  • Sort it and look again. A surprising number of problems become obvious in the right order.
  • Drop a requirement. Solve it while ignoring the O(1)-space rule, then reduce the space. Partial credit beats silence, and the easier version often shows you the real solution.
  • Ask about the input. Duplicates? Negative numbers? Sorted? Can it be empty? One question sometimes makes the problem much simpler, and asking never counts against you.

Two of those tactics on real examples. Tiny cases: "how many ways can you climb n stairs, taking 1 or 2 steps at a time?" By hand, n = 1 gives 1 way, n = 2 gives 2, n = 3 gives 3, and n = 4 gives 5. The numbers 1, 2, 3, 5 are the Fibonacci numbers. That suggests f(n) = f(n−1) + f(n−2), and the reason is easy to see once you are looking for it: your last move was either a 1-step or a 2-step. Flip the question: "how many subsets of n numbers contain at least one even number?" Counting directly is messy. Counting the opposite is easy. If there are o odd numbers, 2ᵒ subsets contain only odd numbers (including the empty one). So the answer is 2ⁿ − 2ᵒ. "At least one" is a strong hint to count the complement.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 FOUR QUESTIONS
Shape, output, constraints, redundancy — in that order. Most problems are pinned down by the second, and the fourth hands you the technique.
💡 NAME THE WASTE
Every optimisation removes one kind of repeated work: overlapping subproblems → DP, recomputed window → sliding window, repeated "nearest bigger" → monotonic stack.
💡 MAKE IT A GRAPH
When nothing matches, ask what the nodes and edges are. Scheduling, currency conversion, word ladders and equation consistency are all graph problems in costume.
⚠️
Common mistakes in pattern selection
  • Matching on words instead of structure. "Subarray" does not always mean sliding window. A window only works if the rule stays broken once it breaks as the window grows.
  • Ignoring the input limits. They are the strongest hint you get, and they are stated for a reason.
  • Jumping to the fast solution without saying the brute force. Your reasoning stays invisible, and the follow-up question catches you out.
  • Using a greedy rule without proving it. Most plausible greedy rules are wrong. Find the counterexample, or write the DP.
  • Running BFS on a weighted graph. It gives the fewest edges, not the cheapest path.
  • Reaching for a segment tree when the array never changes and prefix sums are enough.
  • Sorting when the original order carries information the problem depends on.
  • Using a DP state that does not say enough. If two different histories share a state but need different answers, add another dimension.
  • Speeding things up before the brute force is correct. A fast wrong answer is worth nothing.
  • Forcing a remembered pattern onto a problem that does not fit, instead of going back to step 4 and naming the repeated work.

Interview drill

Warm-up: "Given an array of n ≤ 10⁵ positive integers and an integer k, split the array into k contiguous parts so as to minimise the largest part sum." Talk through your first two minutes.

How a strong answer sounds
Let me run through shape, output, constraints and repeated work.

The shape is an array, and the parts must be next to each other, so I am really choosing k−1 cut positions. The output is a single number, and it is minimise the maximum. That phrase almost always signals binary search on the answer. The constraints confirm it: n is 10⁵, so I have an O(n log something) budget. The answer lies between the largest single element and the total sum, which is around 10¹⁴ if values reach 10⁹. That is only about 47 binary-search steps.

So here is the plan. Binary search on m, the largest allowed part sum. For each m, check in O(n) whether it is possible: walk the array adding up values, and start a new part whenever adding the next element would go over m. If the number of parts needed is at most k, then m works.

That check is monotone: once a value works, every larger value works too. Binary search needs exactly that, and I would justify it out loud. A bigger allowance can never force more parts. The total is O(n log(total sum)), about 5·10⁶ operations.

Two boundary details. The search's lower bound must be max(element), not 0, because no part can be smaller than its own largest member. And I would return low after the standard "find the smallest value that works" loop.

I would also mention the alternative: an O(n²k) DP over dp[i][j], the best way to split the first i elements into j parts. It is correct, and it would be the right answer if k and n were small, but it is far too slow here. Naming both and choosing based on the constraints is the point.

Deeper: "You are given a list of currency exchange rates between pairs. Determine whether a sequence of trades can turn 1 unit of some currency into more than 1 unit of the same currency." What pattern is this?

How a strong answer sounds
This is the "can I turn this into a graph?" question, and the answer is yes. It is negative-cycle detection, which means Bellman-Ford.

Turning it into a graph is the interesting part. Currencies are nodes, and each exchange rate is a one-way edge. Making a profit (arbitrage) means finding a loop whose rates multiply to more than 1. But Bellman-Ford adds weights, it does not multiply them. So I change each weight to −log(rate). A product of rates above 1 becomes a sum of logs above 0, which becomes a sum of negated logs below 0: exactly a negative cycle.

So I run Bellman-Ford for V−1 rounds, then do one extra pass. If any edge can still be improved, there is a negative cycle, and arbitrage exists. That is O(V·E), which is fine because there are not many currencies.

Two things I would flag. First, Bellman-Ford only finds negative cycles reachable from the starting node. To catch a cycle anywhere, I either add an imaginary source with zero-weight edges to every node, or simply start every distance at 0. The second is the neater trick and worth knowing. Second, logs are decimals, so rounding creeps in. I would compare against a small tolerance rather than exactly 0, and if exact answers mattered I would say so as a limitation.

The lesson that carries over: the clue here was not a keyword in the problem, it was the structure. Relationships between pairs, plus a round trip that multiplies. Scheduling, word ladders, checking equations for contradictions and working out build order all hide the same way. When no pattern matches, "what are the nodes and what are the edges?" is the single most useful question to ask.

🧠 Key takeaways

  • Shape, output, constraints, repeated work, in that order. Most problems are narrowed down by the second question.
  • The input limits are a speed budget. Work backwards from 10⁸ operations to find the intended approach.
  • Every speed-up removes one specific kind of repeated work. Name the repetition and the technique follows.
  • Say the brute force out loud even when you already know the answer. It is your reasoning, your baseline, and proof that you understood the problem.
  • When nothing matches: solve n = 1, 2, 3 by hand, try to make it a graph, flip the question round, or drop a requirement.

Check your understanding

A problem gives n ≤ 18 and asks for the minimum cost to assign every task exactly once. What does the bound tell you?

n ≤ 20 plus "each exactly once" is the bitmask signature. It is too small to need a polynomial algorithm, and too large for trying all n! orders. The limit is a hint, not a courtesy.

"Minimise the maximum load" with an answer range up to 10¹⁴ suggests…

"Minimise the maximum" or "maximise the minimum", plus a huge range of possible answers, is the clue. The thing to check is that the answer is monotone: once a candidate works, every larger one works too.

You have a grid where movement is allowed in all four directions and each cell has a positive cost. Grid DP fails because…

Moving only right and down gives a safe fill order, because i+j always increases. Allowing all four directions destroys that, and "loop until nothing changes" is just a slow Bellman-Ford.

What is the most reliable way to derive the right technique on an unfamiliar problem?

The same subproblem solved again → DP. A window total recomputed from scratch → sliding window. "Nearest bigger element" asked repeatedly → monotonic stack. Every speed-up removes one specific kind of repeated work.

When should you choose greedy over DP?

Most greedy rules that sound right are wrong. If you cannot give a one-sentence exchange argument, go looking for a counterexample, and write the DP if you find one.
