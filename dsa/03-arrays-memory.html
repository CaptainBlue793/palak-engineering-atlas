Arrays & How Memory Actually Works

The array is the only data structure the hardware truly loves, and that is not a metaphor — it is a measurable 5–10× speed difference that Big-O cannot see. This chapter explains why a[i] is one instruction, why a linked-list walk with identical O(n) can be an order of magnitude slower, and how vector really behaves under the hood.

  • Derive the address arithmetic that makes random access O(1)
  • Explain cache lines and predict which access patterns are fast
  • Distinguish size from capacity, and know what invalidates iterators
  • Choose between a 2D vector, a flattened 1D array, and a fixed array
  • Use the in-place write-pointer pattern that solves a whole family of array problems

Why a[i] costs nothing

An array is a single contiguous block of memory holding equally sized elements. That is the entire definition, and every property follows from it.

If the block starts at address base and each element takes s bytes, then element i lives at base + i·s. That is one multiply and one add — and because s is a compile-time constant power of two for most types, the multiply is a bit shift. The CPU does this as part of the load instruction itself. There is no search. That is what O(1) random access means, and it is the array's whole superpower.

🔢
Why arrays are 0-indexed

Because base + i·s is the natural formula. With 1-indexing you would need base + (i−1)·s, paying a subtraction on every single access. Zero-based indexing is not an arbitrary convention — it is the address arithmetic showing through. It is also why a[i] and *(a+i) are literally the same expression in C++.

The cost Big-O cannot see: cache

Your CPU does not read one byte from RAM. It reads a cache line — typically 64 bytes, so 16 ints — and keeps it in fast memory. Access something in a line you already have and it costs about 1 nanosecond. Miss, and you wait 100 nanoseconds for RAM.

That factor of 100 is why two O(n) traversals can differ by 10× in wall clock. A sequential array walk gets 15 free hits for every miss. A linked-list walk, whose nodes were allocated at unrelated addresses, misses on nearly every step.

The rule that follows from this

When two options have the same Big-O, pick the contiguous one. A vector<int> beats a list<int> for iteration, almost always. A flat vector<int> of size rows*cols beats a vector<vector<int>> for a hot inner loop. And an array indexed by a small integer beats an unordered_map<int,…> every time, despite both being “O(1)”.

What a vector really is

Three pointers, essentially: where the data starts, where the used part ends, and where the allocation ends. From those come size() and capacity() — and the distinction matters more than most people realise.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 READ/WRITE
Every in-place filter is one pattern: a read pointer that always advances and a write pointer that advances only on a keeper. Remove-element, move-zeroes and dedupe are the same four lines.
💡 THREE REVERSES
Rotating by k in O(1) space is reverse-all, reverse-first-k, reverse-rest. The same trick rotates a matrix: transpose, then reverse each row.
⛔ INDEX AS HASH
When a problem says values are in [1..n] and demands O(1) space, the array is your hash table — but mark by negating or swapping, and remember you have destroyed the input.
💥
Reallocation invalidates everything pointing into the vector

When a push_back exceeds capacity, the vector moves to a new block. Every pointer, reference and iterator into the old block is now dangling, and using one is undefined behaviour — often silently, which is worse than a crash.

vector<int> v={1,2,3};
int &first=v[0];     // reference into the buffer
v.push_back(4);      // may reallocate -> first is now dangling
first=99;            // undefined behaviour

The fix when you must hold on: store an index, not a pointer. Indices survive reallocation; addresses do not. This is also why removing from a vector while iterating over it needs the erase-remove idiom rather than a naive loop.

✍️
My convention: reserve() when you know the size

If you are about to push n items, call ans.reserve(n) first. It costs one line, removes every reallocation, and removes the whole class of dangling-reference bugs above. It is the cheapest optimisation in C++ and almost nobody does it.

2D arrays: three ways, and which to pick

vector<vector<int>> grid(rows,vector<int>(cols,0));

grid[r][c]=5;

Use this by default. Readable, resizable, and the syntax matches how you think about the problem. The cost: rows separate allocations that may be scattered in memory, so each row change is potentially a cache miss, plus one extra pointer dereference per access.

vector<int> grid(rows*cols,0);

grid[r*cols+c]=5;          // index by hand

Use this when the inner loop is hot or when the grid is large. One allocation, perfectly contiguous, one dereference. The whole grid walks as a single cache-friendly sweep. The cost is the manual index, which is an easy place to write c*rows+r by mistake — so write a tiny at(r,c) lambda and never index directly.

int grid[1005][1005];        // global: zero-initialised, on the data segment

grid[r][c]=5;

Use this in competitive programming when bounds are known and generous. Fastest of the three, zero allocation cost, and contiguous. But: declaring it inside a function puts ~4 MB on the stack and blows it instantly — this must be global or static. And it cannot be resized.

The in-place write-pointer pattern

A whole family of problems is “remove or rearrange elements in place, in O(1) extra space”. They all use the same two-index shape: a read index that scans everything, and a write index that advances only when something should be kept.

removeDuplicates — sorted array, in placeO(n)O(1)
// write is the index of the next slot to fill; everything before it is final.
// Invariant: a[0..write-1] holds the distinct values seen so far, in order.
int removeDuplicates(vector<int> &a){
	if(a.empty())return 0;

	int write=1;
	for(int read=1;read<a.size();read++){
		if(a[read]!=a[write-1]){
			a[write]=a[read];
			write++;
		}
	}

	return write;
}
The invariant is the whole solution. Once you have written “a[0..write-1] holds the distinct values in order”, the condition a[read]!=a[write-1] is forced — you are comparing against the last thing you kept, not the previous element you read.

🔁
O(n) insertion in the middle is not always bad

Shifting 1000 contiguous ints is a single memmove the CPU does at gigabytes per second. Walking 1000 scattered linked-list nodes to find the insertion point is 1000 cache misses. In practice, vector beats list for insertion at random positions up to surprisingly large n — the theoretical O(1) insert is worthless if finding the position is O(n) with terrible locality.

⚠️
Common mistakes
  • Holding a pointer or reference across a push_back. Reallocation invalidates it. Store an index instead.
  • Comparing i < v.size()-1 on an empty vector. size() is unsigned, so 0-1 wraps to a huge number and the loop runs forever. Write i+1 < v.size().
  • Declaring a large fixed array inside a function. int a[1000][1000] is 4 MB on a typically 1–8 MB stack. Make it global or static.
  • Expecting clear() to free memory. It sets size to 0 and keeps capacity. Use shrink_to_fit(), or swap with an empty vector, if you genuinely need the memory back.
  • Using a[i] on a map instead of find. On a map or unordered_map, [] inserts a default-constructed value when the key is absent — which silently grows the container and changes your answer.
  • Indexing a flattened 2D array as c*rows+r. It compiles, it runs, and it transposes your grid. Write a helper and never index inline.

Interview drill

Warm-up: Both an array walk and a linked-list walk are O(n). Why is the array often 10× faster?

How a strong answer sounds
Because Big-O counts operations and the hardware charges for memory locality. The CPU fetches a 64-byte cache line at a time, so walking a contiguous int array gets one miss followed by fifteen hits, and the prefetcher sees the linear pattern and loads the next line before you ask for it. A linked list's nodes were allocated separately and are at unrelated addresses, so almost every step is a cache miss — roughly 100 ns instead of 1 ns — and the prefetcher cannot help because the next address is only known after the current load completes, which serialises the whole walk. Same asymptotics, two orders of magnitude difference in the constant. The practical rule: when the Big-O ties, prefer contiguous memory.

Deeper: When would you flatten a 2D grid into a 1D vector, and what do you lose?

How a strong answer sounds
I flatten when the grid is large and the access pattern is a hot loop, because vector<vector<int>> costs one allocation per row, an extra pointer dereference per access, and rows that may be far apart in memory — so a full sweep gets no help from the prefetcher across row boundaries. Flattening gives one allocation, one dereference and a single contiguous sweep, and it also lets me memset or fill the whole grid in one call. What I lose is readability and safety: g[r*cols+c] is easy to write as g[c*rows+r], which silently transposes everything and produces a plausible wrong answer. So I always wrap it — a lambda or a small struct with at(r,c) — and never index inline. I also lose ragged rows, so if rows genuinely have different lengths, the nested version is correct and flattening is not an option.

🧠 Key takeaways

  • An array is one contiguous block, so element i is at base + i·s — that single formula gives O(1) access and explains 0-indexing.
  • The CPU fetches 64-byte cache lines, making sequential access ~100× cheaper per element than random; this is invisible to Big-O and decisive in practice.
  • size() is what you use, capacity() is what you own; reallocation invalidates every pointer and iterator, so store indices.
  • Flatten a 2D grid when the inner loop is hot, and always wrap the index arithmetic in a helper.
  • The read/write pointer pattern solves remove-duplicates, remove-element and move-zeroes with the same skeleton and O(1) space.

Check your understanding

Why is random access to an array O(1)?

Contiguity plus a fixed element size means the address is computed, not found. It is also exactly why you cannot have an O(1)-indexed array of variable-sized elements.

You hold int &r = v[0], then call v.push_back(x). What is the danger?

Exceeding capacity moves the whole buffer. Every pointer, reference and iterator into the old block dangles. Store an index if you need to refer back across a push.

for(int i=0;i<v.size()-1;i++) on an empty vector does what?

size() returns size_t, unsigned. 0 - 1 becomes about 1.8 × 10¹⁹, so the loop runs until it reads out of bounds and crashes. Write i + 1 < v.size() instead.

What does v.clear() do to capacity?

clear() destroys the elements and sets size to 0, but keeps the buffer so future pushes are cheap. To actually release it, call shrink_to_fit() after, or swap with a fresh empty vector.

You will push exactly 10⁶ elements onto a vector. What single line most improves it?

reserve allocates once up front. You skip ~20 reallocations and roughly 2 × 10⁶ element copies, and no iterator is ever invalidated. One line, and almost nobody writes it.
