Arrays & How Memory Actually Works

The array is the one data structure the hardware truly loves. That is not a figure of speech — it is a measurable 5–10× speed difference that Big-O cannot see. This chapter explains why a[i] takes a single instruction. It shows why walking a linked list can be ten times slower than walking an array, even though both are O(n). And it shows how vector really works under the hood.

  • Tell size apart from capacity, and know what breaks iterators
  • Choose between a 2D vector, a flattened 1D array, and a fixed array
  • Use the in-place write-pointer pattern, which solves a whole family of array problems

Why a[i] costs nothing

An array is one contiguous block of memory — the elements sit right next to each other, with no gaps — and every element is the same size. That is the entire definition. Everything else about arrays follows from it.

Think of houses on a street where every plot is the same width. If you know where the street starts, you can find house number 40 without walking past the first 39.

Arrays work the same way. Say the block starts at address base and each element takes s bytes. Then element i lives at base + i·s. That is one multiply and one add. For most types, s is a fixed power of two known at compile time, so the multiply becomes a cheap bit shift. The CPU even does this inside the load instruction itself. There is no search. That is what O(1) random access means, and it is the array's whole superpower.

With real numbers: an array of int (4 bytes each) starts at address 1000. Then a[0] is at 1000, a[1] at 1004, a[2] at 1008, and a[250] at 1000 + 250 × 4 = 2000. Finding a[250] takes exactly as long as finding a[0]. A linked list cannot do this: to reach its 250th node you must follow 250 “next” pointers, because each node could be anywhere.

The same fact explains the array's weakness. Since every element's position is fixed by its index, you cannot slip a new element between a[3] and a[4]. Everything from a[4] onwards has to move one slot to the right to make room. That is where the O(n) insert in the table further down comes from.

🔢
Why arrays are 0-indexed

Because base + i·s is the natural formula. With 1-indexing you would need base + (i−1)·s, which adds a subtraction to every single access. So zero-based indexing is not a random choice — it is the address maths showing through. It is also why a[i] and *(a+i) mean exactly the same thing in C++.

The cost Big-O cannot see: cache

Your CPU never reads just one byte from RAM. It reads a whole cache line — usually 64 bytes, which is 16 ints — and keeps it in a small, fast memory called the cache. It is like fetching a whole carton of eggs from the shop instead of one egg at a time.

If the next thing you need is already in the cache (a hit), it costs about 1 nanosecond. If it is not (a miss), you wait about 100 nanoseconds for RAM.

That factor of 100 is why two O(n) loops can differ by 10× in real time. Walking an array in order gets 15 free hits for every miss. A linked list's nodes were created separately and sit at unrelated addresses, so walking it misses on nearly every step.

Some rough arithmetic for a walk over 1,600 ints. In order, that is 1,600 ÷ 16 = 100 misses and 1,500 hits: about 100 × 100 + 1,500 × 1 = 11,500 ns. Jumping around at random, nearly every access misses: about 1,600 × 100 = 160,000 ns. Same number of elements, same Big-O, roughly 14× slower. (Real hardware blurs these numbers — there are several cache levels, and the prefetcher helps the in-order walk even more — but the gap is real.)

You will meet this most often with 2D grids. C++ stores a grid row by row: all of row 0, then all of row 1, and so on. So a loop with the row in the outer loop and the column in the inner loop reads memory in order. Swap the two loops, and each step jumps a whole row ahead — on a 1000-column int grid, that is 4,000 bytes per step, a new cache line every time. The code looks almost identical, but it can run several times slower.

The rule that follows from this

When two options have the same Big-O, pick the one stored in a single block. A vector<int> beats a list<int> for looping, almost always. A flat vector<int> of size rows*cols beats a vector<vector<int>> in a hot inner loop (one that runs a huge number of times). And an array indexed by a small integer beats an unordered_map<int,…> every time, even though both are “O(1)”.

What a vector really is

Under the hood, a vector is basically three pointers: where the data starts, where the used part ends, and where the reserved memory ends. From these come size() (how many elements you have) and capacity() (how many fit before it must grow). The difference matters more than most people realise.

A small example. After vector<int> v; v.reserve(4); v.push_back(7); v.push_back(8); v.push_back(9); the vector owns a block of 4 slots. Three hold 7, 8 and 9; the fourth is reserved but empty. So size() is 3 and capacity() is 4. The next push_back just writes into slot 4 — cheap. The one after that finds no room, so it allocates a bigger block (8 slots with doubling), copies the 4 values over, frees the old block, and then writes. size() tells you what is valid to read; reading v[3] while size is 3 is a bug even though the memory exists.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 READ/WRITE
Every in-place filter is one pattern: a read pointer that always advances and a write pointer that advances only on a keeper. Remove-element, move-zeroes and dedupe are the same four lines.
💡 THREE REVERSES
Rotating by k in O(1) space is reverse-all, reverse-first-k, reverse-rest. The same trick rotates a matrix: transpose, then reverse each row.
⛔ INDEX AS HASH
When a problem says values are in [1..n] and demands O(1) space, the array is your hash table — but mark by negating or swapping, and remember you have destroyed the input.
💥
Reallocation invalidates everything pointing into the vector

When a push_back goes past capacity, the vector moves to a new block of memory. Every pointer, reference and iterator into the old block is now dangling — it points at memory that is no longer yours. Using one is undefined behaviour (anything can happen). Often nothing visibly breaks, which is worse than a crash.

vector<int> v={1,2,3};
int &first=v[0];     // reference into the buffer
v.push_back(4);      // may reallocate -> first is now dangling
first=99;            // undefined behaviour

The fix, when you need to remember a position: store an index, not a pointer. Indices survive the move; addresses do not. This is also why removing items from a vector while looping over it needs the erase-remove idiom (a standard two-step recipe) rather than a simple loop.

✍️
My convention: reserve() when you know the size

If you are about to push n items, call ans.reserve(n) first. It costs one line. It removes every reallocation, and with them the whole family of dangling-reference bugs above. It is the cheapest speed-up in C++, and almost nobody does it.

2D arrays: three ways, and which to pick

vector<vector<int>> grid(rows,vector<int>(cols,0));

grid[r][c]=5;

Use this by default. It is readable, it can be resized, and the syntax matches how you think about the problem. The cost: each of the rows rows is a separate allocation, and rows may be scattered around memory. So moving to a new row can cause a cache miss, and every access follows one extra pointer.

vector<int> grid(rows*cols,0);

grid[r*cols+c]=5;          // index by hand

Use this when the inner loop is hot or the grid is large. One allocation, all in one block, one pointer to follow. You can walk the whole grid in a single cache-friendly sweep. The cost is computing the index by hand, where it is easy to write c*rows+r by mistake. So write a tiny at(r,c) lambda and never index directly.

int grid[1005][1005];        // global: zero-initialised, on the data segment

grid[r][c]=5;

Use this in competitive programming when the size limits are known and generous. It is the fastest of the three, costs nothing to allocate, and sits in one block. But if you declare it inside a function, it puts ~4 MB on the stack (the small memory area for function calls) and overflows it instantly. It must be global or static. And it cannot be resized.

Where does r*cols+c come from? Lay the rows end to end in one line. To reach row r, you skip r complete rows of cols cells each — that is r*cols cells. Then you move c more cells along the row. For a 3 × 4 grid, cell (1, 2) sits at 1 × 4 + 2 = 6:

Flat index012345678…
(row, col)(0,0)(0,1)(0,2)(0,3)(1,0)(1,1)(1,2)(1,3)(2,0)…

Going the other way, index 6 gives row 6/cols = 1 and column 6%cols = 2. That reverse trick is handy when a BFS stores grid cells as single integers. Which to pick, in short: nested vectors for interviews and most problems; flattened when profiling or a tight time limit says the grid is the bottleneck; fixed global arrays in contests with known maximum sizes.

The in-place write-pointer pattern

A whole family of problems asks you to “remove or rearrange elements in place, using O(1) extra space”. They all use the same two-index shape. A read index scans every element. A write index moves forward only when an element should be kept. Picture sorting mail: one hand picks up each letter, the other places only the keepers on the pile.

removeDuplicates — sorted array, in placeO(n)O(1)
// write is the index of the next slot to fill; everything before it is final.
// Invariant: a[0..write-1] holds the distinct values seen so far, in order.
int removeDuplicates(vector<int> &a){
	if(a.empty())return 0;

	int write=1;
	for(int read=1;read<a.size();read++){
		if(a[read]!=a[write-1]){
			a[write]=a[read];
			write++;
		}
	}

	return write;
}
The invariant (the rule that is always true) is the whole solution. Once you have written “a[0..write-1] holds the distinct values in order”, the condition a[read]!=a[write-1] follows on its own. You compare against the last value you kept, not the previous value you read.

A dry run on [1, 1, 2, 3, 3]. Both indices start at 1, because a[0] is always kept — the first value can never be a duplicate.

reada[read]a[write-1]Keep?Array afterwrite after
111no[1, 1, 2, 3, 3]1

The function returns 3, and the first 3 slots are [1, 2, 3]. Whatever sits after them does not matter — the caller only looks at the first write elements. Why is this safe to do in place? Because write never gets ahead of read, so you only ever overwrite a slot you have already read.

Edge cases to check: an empty array returns 0 from the guard. An array where every value is the same, like [5, 5, 5], never advances write and returns 1. An array with no duplicates copies each element onto itself and returns n. And the method only works because the array is sorted: equal values are next to each other, so comparing with the last kept value is enough. On an unsorted array you would need a hash set (Chapter 9).

Array operation costs, all in one place

The two O(n) rows below are worth picturing once. To insert X at index 1 of [a, b, c, d], the vector first moves d, then c, then b one slot to the right (starting from the end, so nothing gets overwritten), and only then writes X: [a, X, b, c, d]. That is 3 moves for 4 elements. Inserting at the front of n elements moves all n of them. Erasing works the same way in reverse: everything after the gap shifts left by one.

🔁
O(n) insertion in the middle is not always bad

Shifting 1000 side-by-side ints is a single memmove, which the CPU does at gigabytes per second. Walking 1000 scattered linked-list nodes to find the insert position is 1000 cache misses. In practice, vector beats list for inserting at random positions up to surprisingly large n. The list's O(1) insert is worthless if finding the position is O(n) and jumps all over memory.

⚠️
Common mistakes
  • Holding a pointer or reference across a push_back. If the vector moves, the pointer is broken. Store an index instead.
  • Comparing i < v.size()-1 on an empty vector. size() is unsigned (it cannot be negative), so 0-1 wraps around to a huge number and the loop runs forever. Write i+1 < v.size().
  • Declaring a large fixed array inside a function. int a[1000][1000] is 4 MB, and the stack is usually only 1–8 MB. Make it global or static.
  • Expecting clear() to free memory. It sets size to 0 and keeps the capacity. If you really need the memory back, use shrink_to_fit() or swap with an empty vector.
  • Using a[i] on a map instead of find. On a map or unordered_map, [] inserts a default value when the key is missing. That quietly grows the container and changes your answer.
  • Indexing a flattened 2D array as c*rows+r. It compiles, it runs, and it flips your grid on its diagonal. Write a helper and never index inline.

Interview drill

Warm-up: Both an array walk and a linked-list walk are O(n). Why is the array often 10× faster?

How a strong answer sounds
Because Big-O counts operations, but the hardware charges for where data sits in memory. The CPU fetches a 64-byte cache line at a time. So walking an int array in order gets one miss followed by fifteen hits. On top of that, the prefetcher (hardware that guesses what you will read next) spots the straight-line pattern and loads the next line before you ask. A linked list's nodes were created separately and live at unrelated addresses, so almost every step is a cache miss — about 100 ns instead of 1 ns. The prefetcher cannot help either: you only learn the next address after the current load finishes, so every step waits for the one before. Same Big-O, but a constant factor up to a hundred times bigger. The practical rule: when the Big-O ties, prefer memory in one block.

Deeper: When would you flatten a 2D grid into a 1D vector, and what do you lose?

How a strong answer sounds
I flatten when the grid is large and a hot loop walks it. vector<vector<int>> costs one allocation per row and an extra pointer hop per access. Its rows may also be far apart in memory, so the prefetcher cannot help when a sweep crosses from one row to the next. Flattening gives one allocation, one pointer hop and a single sweep through one block. It also lets me memset or fill the whole grid in one call. What I lose is readability and safety. g[r*cols+c] is easy to mistype as g[c*rows+r], which quietly flips the grid and gives a believable wrong answer. So I always wrap it — in a lambda or a small struct with at(r,c) — and never index inline. I also lose ragged rows: if rows really have different lengths, the nested version is correct and flattening is not an option.

🧠 Key takeaways

  • An array is one unbroken block, so element i is at base + i·s. That single formula gives O(1) access and explains 0-indexing.
  • The CPU fetches memory in 64-byte cache lines, so reading in order is ~100× cheaper per element than jumping around. Big-O cannot see this, but in practice it decides the winner.
  • size() is what you use; capacity() is what you have reserved. Reallocation breaks every pointer and iterator, so store indices.
  • Flatten a 2D grid when the inner loop is hot, and always wrap the index arithmetic in a helper.
  • The read/write pointer pattern solves remove-duplicates, remove-element and move-zeroes with the same skeleton and O(1) space.

Check your understanding

Why is random access to an array O(1)?

Elements side by side, all the same size, means the address is calculated, not searched for. It is also exactly why you cannot have an O(1)-indexed array whose elements have different sizes.

You hold int &r = v[0], then call v.push_back(x). What is the danger?

Going past capacity moves all the data to a new block. Every pointer, reference and iterator into the old block now points at freed memory. Store an index if you need to refer back to an element after a push.

for(int i=0;i<v.size()-1;i++) on an empty vector does what?

size() returns size_t, which is unsigned (never negative). So 0 - 1 wraps around to about 1.8 × 10¹⁹, and the loop runs until it reads outside the array and crashes. Write i + 1 < v.size() instead.

What does v.clear() do to capacity?

clear() destroys the elements and sets size to 0, but keeps the memory so future pushes are cheap. To really give it back, call shrink_to_fit() afterwards, or swap with a fresh empty vector.

You will push exactly 10⁶ elements onto a vector. What single line most improves it?

reserve allocates all the memory once, up front. You skip ~20 reallocations and roughly 2 × 10⁶ element copies, and no iterator ever breaks. One line, and almost nobody writes it.
