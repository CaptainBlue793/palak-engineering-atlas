The Knapsack Family

Knapsack is the most disguised problem in interviews. Subset sum, partition, coin change, target sum, last stone weight and rod cutting are all the same recurrence with a different combining operator and a different loop direction. Learn the one table and the six disguises stop being six problems.

  • Write the 0/1 knapsack recurrence from its take-or-leave state
  • Explain why the capacity loop direction decides whether items can be reused
  • Reduce subset sum, partition and target sum to knapsack
  • Get the two coin-change variants right — including why the loop nesting matters for counting
  • Collapse the 2D table to 1D, and know when you cannot

0/1 knapsack: the parent problem

Items with weights and values, a capacity W, each item usable at most once. Maximise the value.

0/1 knapsack — the full 2D tableO(n·W)O(n·W)
// dp[i][w] = the maximum value using only the first i items,
//            with a capacity of exactly w available.
// Two choices at item i-1: leave it, or take it (if it fits).
int knapsack(vector<int> &weight,vector<int> &value,int W){
	int n=weight.size();
	vector<vector<int>> dp(n+1,vector<int>(W+1,0));

	for(int i=1;i<=n;i++){
		for(int w=0;w<=W;w++){
			dp[i][w]=dp[i-1][w];                 // leave item i-1

			if(weight[i-1]<=w){
				dp[i][w]=max(dp[i][w],
				              value[i-1]+dp[i-1][w-weight[i-1]]);
			}
		}
	}

	return dp[n][W];
}
The i-1 in the value lookup is the whole "0/1" constraint. Reading from row i-1 means the sub-solution was built without item i-1, so it cannot be taken twice. Change that to dp[i] and you have unbounded knapsack. The i versus i-1 index shift — row i is about item i-1 — is needed because row 0 means "no items", and it is the most common source of off-by-ones here.

The loop direction: the single most important detail

Collapsing the table to one row is standard. But the direction of the capacity loop now encodes whether an item may be reused — and that one choice is the difference between 0/1 and unbounded knapsack.

0/1 — iterate capacity downward
vector<int> dp(W+1,0);

for(int i=0;i<n;i++){
	for(int w=W;w>=weight[i];w--){
		dp[w]=max(dp[w],value[i]+dp[w-weight[i]]);
	}
}

Going downward, dp[w-weight[i]] has not yet been touched on this item's pass, so it still holds the value from before item i — exactly like reading row i-1. Each item is used at most once.

Unbounded — iterate capacity upward
vector<int> dp(W+1,0);

for(int i=0;i<n;i++){
	for(int w=weight[i];w<=W;w++){
		dp[w]=max(dp[w],value[i]+dp[w-weight[i]]);
	}
}

Going upward, dp[w-weight[i]] may already include item i from earlier this pass — so the item can be taken repeatedly. That "bug" is precisely the unbounded semantics.

✍️
My convention: write the 2D version first, then collapse — and state the direction's meaning in a comment

The 1D version is four lines and completely opaque; the 2D version is eight lines and self-explanatory. Get the 2D table correct first, confirm it on a small case, and only then collapse — and when you do, put // downward: each item once or // upward: items reusable on the loop. This is the one place in DP where a loop's direction carries semantic meaning rather than being a stylistic choice, and a reader (including you, later) cannot infer it from the code.

The six disguises

// "Is there a subset summing to exactly target?"
// Knapsack with value = weight and a BOOLEAN table instead of a max.
// dp[w] = can a subset of the items seen so far sum to exactly w?
bool canPartitionSum(vector<int> &nums,int target){
	vector<bool> dp(target+1,false);
	dp[0]=true;                     // the empty subset sums to 0

	for(int x:nums){
		for(int w=target;w>=x;w--){   // downward: each number once
			dp[w]=dp[w] or dp[w-x];
		}
	}

	return dp[target];
}

dp[0] = true is the load-bearing base case — the empty subset. Omit it and the table is all false forever. Note the boolean version is often much faster in practice with a bitset: bits |= bits << x; does a whole item in one instruction (Chapter 47).

// "Can the array be split into two subsets of EQUAL sum?"
// If the total is odd, impossible. Otherwise it is subset sum for total/2 —
// because one subset summing to half forces the other to as well.
bool canPartition(vector<int> &nums){
	int total=0;
	for(int x:nums)
	total+=x;

	if(total%2!=0)return false;      // the O(1) early exit

	return canPartitionSum(nums,total/2);
}

// VARIANT: "minimum difference between two subsets" — find the achievable
// sum closest to total/2, then the answer is total - 2*thatSum.
int minimumDifference(vector<int> &nums){
	int total=0;
	for(int x:nums)
	total+=x;

	int half=total/2;
	vector<bool> dp(half+1,false);
	dp[0]=true;

	for(int x:nums){
		for(int w=half;w>=x;w--)
		dp[w]=dp[w] or dp[w-x];
	}

	for(int s=half;s>=0;s--){
		if(dp[s])return total-2*s;
	}

	return total;
}

The odd-total check is free and eliminates half the inputs instantly. "Last stone weight II" is exactly minimumDifference under a different story — smashing stones pairwise is equivalent to assigning each a sign, which is equivalent to a two-way partition.

// "Assign + or - to each number so the total equals target. How many ways?"
// Let P be the positives and N the negatives.
//   P - N = target  and  P + N = total
//   => P = (target + total) / 2
// So COUNT the subsets summing to that value. Pure subset-sum counting.
int findTargetSumWays(vector<int> &nums,int target){
	int total=0;
	for(int x:nums)
	total+=x;

	if(abs(target)>total)return 0;
	if((target+total)%2!=0)return 0;   // P must be an integer

	int P=(target+total)/2;

	vector<int> dp(P+1,0);
	dp[0]=1;                          // one way to make 0: take nothing

	for(int x:nums){
		for(int w=P;w>=x;w--)
		dp[w]+=dp[w-x];              // COUNTING, so += not max
	}

	return dp[P];
}

The algebra is the whole problem. Once you see that a sign assignment is a subset choice, it is knapsack. Watch the zeros: a 0 in the input can go in either subset, which is why dp[0] must start at 1 and the loop must handle x = 0 — the downward loop with w >= 0 handles it correctly, doubling the count as it should.

// "Fewest coins to make amount." Unbounded (coins reusable), minimising.
// dp[w] = the minimum number of coins summing to exactly w.
int coinChange(vector<int> &coins,int amount){
	vector<int> dp(amount+1,amount+1);   // amount+1 = "impossible"
	dp[0]=0;

	for(int c:coins){
		for(int w=c;w<=amount;w++)      // UPWARD: coins reusable
		dp[w]=min(dp[w],1+dp[w-c]);
	}

	return dp[amount]>amount?-1:dp[amount];
}

Use amount+1 as the infinity sentinel, not INT_MAX — because 1 + INT_MAX overflows to a negative number and silently becomes the minimum. Any value above the largest possible answer works, and amount+1 is the natural choice since you can never need more than amount coins.

// "How many ways to make amount, order irrelevant?"
// SAME table, but the LOOP NESTING is the whole problem.
int change(int amount,vector<int> &coins){
	vector<int> dp(amount+1,0);
	dp[0]=1;

	for(int c:coins){              // COIN loop OUTSIDE
		for(int w=c;w<=amount;w++)
		dp[w]+=dp[w-c];
	}

	return dp[amount];
}

// Swap the loops and you count ORDERED sequences (permutations) instead:
//   for(int w=1;w<=amount;w++)
//     for(int c:coins)
//       if(c<=w) dp[w]+=dp[w-c];
// That is "combination sum IV", a DIFFERENT problem with a bigger answer.

Coin outside = combinations; amount outside = permutations. With coins {1,2} and amount 3: coin-outside gives 2 ({1,1,1}, {1,2}), amount-outside gives 3 ({1,1,1}, {1,2}, {2,1}). This is the single most important loop-order fact in DP, and the two versions differ by nothing but nesting.

// "Cut a rod of length n into pieces to maximise total price."
// Unbounded knapsack where weight = length and value = price.
// dp[L] = the maximum revenue obtainable from a rod of length L.
int rodCutting(vector<int> &price,int n){
	vector<int> dp(n+1,0);

	for(int len=1;len<=n;len++){
		for(int cut=1;cut<=len;cut++){
			dp[len]=max(dp[len],price[cut-1]+dp[len-cut]);
		}
	}

	return dp[n];
}
// Written amount-outside here, which is fine because we are MAXIMISING,
// not counting — loop order only matters for counting.

Worth noting: the loop-nesting trap applies to counting only. For min or max both nestings give the same answer, because the optimum does not care about the order in which items were considered. That is why coin-change-minimum can be written either way but coin-change-count cannot.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 TWO LOOP RULES
In 1D knapsack, capacity descending means each item once; ascending means unlimited reuse. And coins-outer counts combinations while capacity-outer counts permutations. Memorise those two sentences.
💡 SIX DISGUISES
Subset sum, partition, target sum, coin change (min), coin change (count) and rod cutting are all one table. Learn the table, then map the problem onto it.
⛔ TARGET TOO BIG
Knapsack is O(n·target) — pseudo-polynomial. When the target is 10⁹ and n ≤ 40, it is meet-in-the-middle, not DP.

These are independent and both matter. Unbounded counting of combinations is upward + item-outside. Unbounded counting of permutations is upward + capacity-outside. 0/1 counting is downward + item-outside (and capacity-outside would be wrong there for a different reason — it would let an item be reconsidered). Say which of the four you need before writing the loops.

Reconstruction, and when you cannot

which items were chosen?needs the full 2D table
// Walk backwards from dp[n][W]. If the value differs from the row above,
// item i-1 must have been taken.
vector<int> chosenItems(vector<vector<int>> &dp,vector<int> &weight,int n,int W){
	vector<int> items;
	int w=W;

	for(int i=n;i>0;i--){
		if(dp[i][w]!=dp[i-1][w]){      // the value changed -> item was used
			items.push_back(i-1);
			w-=weight[i-1];
		}
	}

	reverse(items.begin(),items.end());

	return items;
}
This is why you do not space-optimise by reflex (Chapter 38). The 1D version answers "what is the maximum value?" but has destroyed the information needed for "which items?". If reconstruction is required, keep the O(n·W) table — and note that at n = 100 and W = 10⁴ that is a million cells, which is fine.
⏱️
O(n·W) is "pseudo-polynomial" — and that matters

Knapsack's complexity depends on the numeric value W, not on the number of bits needed to write it. So W = 10⁹ with 10 items is intractable even though the input is tiny — the table would have 10¹⁰ cells. 0/1 knapsack is NP-hard; O(n·W) is only fast when W is small. Two consequences for interviews: if the capacity or target is up to 10⁹, knapsack DP is not the intended solution — look for meet-in-the-middle (Chapter 44), a greedy if the problem is actually fractional (Chapter 36), or a different formulation entirely. And always check the constraint on the target before committing to this approach.

🗝️
Recognising a knapsack in disguise
  • “Choose a subset such that the sum is / reaches / is closest to X”
  • “Split into two groups with …” — partition
  • “Assign + or − to each number” — target sum, via the algebra above
  • “Fewest / most items to reach exactly X” — coin change
  • “How many ways to reach exactly X” — counting knapsack, and mind the nesting
  • “Fill a container / reach a total with limited or unlimited supply”
  • The tell is a bounded target and a choice per item. If the target is unbounded, it is not this.
⚠️
Common mistakes
  • Wrong capacity loop direction. Downward for 0/1, upward for unbounded — and the code looks identical either way.
  • Wrong loop nesting in a counting problem. Item outside counts combinations; capacity outside counts permutations.
  • Forgetting dp[0] = true or dp[0] = 1. The empty-subset base case; without it the whole table stays empty.
  • Using INT_MAX as the impossible sentinel in coin change. 1 + INT_MAX overflows negative and becomes the minimum.
  • Mixing the i / i-1 index convention. Row i is about item i-1, because row 0 means "no items".
  • Space-optimising when reconstruction is needed. The 1D table cannot be walked backwards.
  • Not checking the total's parity in the partition problem — a free O(1) rejection of half the inputs.
  • Assuming O(n·W) is polynomial. It is pseudo-polynomial; W = 10⁹ is intractable.
  • Mishandling zeros in target sum. A 0 can go either side, which doubles the count.
  • Using the greedy coin rule. It works only for canonical denominations (Chapter 36).

Interview drill

Warm-up: Can this array be partitioned into two subsets of equal sum?

How a strong answer sounds
First the free check: if the total is odd, no such split exists, return false immediately. Otherwise the problem reduces to subset sum for total/2, because a subset summing to half forces its complement to sum to half as well. So I define dp[w] as "can some subset of the numbers considered so far sum to exactly w", size total/2 + 1, with dp[0] = true for the empty subset — that base case is load-bearing, since without it the table stays false forever. Then for each number I iterate the capacity downward from total/2 to that number, setting dp[w] |= dp[w − x]. Downward is essential: it guarantees dp[w − x] still reflects the state before this number was considered, which is what enforces using each element at most once. Iterating upward would allow reuse and solve a different problem. Complexity is O(n · total) time and O(total) space. I would flag that this is pseudo-polynomial — if the values could sum to 10⁹ this approach is out and I would need meet-in-the-middle instead. And a nice optimisation: with a bitset the whole inner loop becomes bits |= bits << x;, one instruction per 64 capacities, which is roughly a 64× speedup for the boolean version.

Deeper: Coin change — number of ways. Why does the loop nesting change the answer?

How a strong answer sounds
Because the nesting decides whether {1,2} and {2,1} are counted as the same solution or as two. With the coin loop outside and the amount loop inside, I finish processing coin 1 entirely before I ever consider coin 2 — so every combination is built in a fixed, non-decreasing coin order and each multiset is counted exactly once. That gives combinations. With the amount loop outside and the coin loop inside, at each amount I consider every coin as the last one added, so the same multiset is reached via every ordering of its coins and each is counted separately. That gives permutations, which is the "combination sum IV" problem. Concretely with coins {1,2} and amount 3: coin-outside gives 2 — {1,1,1} and {1,2} — while amount-outside gives 3, adding {2,1}. Two important riders. First, this only matters for counting: for a min or max objective both nestings give the same answer, because the optimum is indifferent to the order items were considered in, which is why coin-change-minimum can be written either way. Second, the nesting is independent of the capacity direction, which controls reuse rather than ordering — so I decide both separately, and state which of the four combinations I need before writing the loops.

🧠 Key takeaways

  • One recurrence — take or leave — underlies subset sum, partition, target sum, coin change and rod cutting.
  • Capacity direction controls reuse: downward means each item once, upward means unlimited.
  • Loop nesting controls ordering, and only for counting: item outside = combinations, capacity outside = permutations.
  • dp[0] = 1 (or true) is the empty-subset base case, and the sentinel for "impossible" must not overflow when incremented.
  • O(n·W) is pseudo-polynomial — check the target's magnitude before committing to knapsack DP.

Check your understanding

In the 1D knapsack, why iterate the capacity downward for 0/1?

Downward is equivalent to reading row i-1 of the 2D table. Upward reads values that may already include the current item, which is exactly the unbounded semantics.

Coin change II counts the number of ways. Which loop goes outside for combinations?

Coin outside gives combinations; amount outside gives permutations (combination sum IV). With coins {1,2} and amount 3 that is 2 versus 3. This only matters for counting — for min/max both nestings agree.

Why use amount+1 rather than INT_MAX as the "impossible" sentinel in coin change?

Any sentinel above the largest possible answer works, and amount+1 is natural since you can never need more than amount coins. INT_MAX breaks the moment you add 1 to it.

"Assign + or − to each number so the total is target. How many ways?" How does this reduce to knapsack?

A sign assignment is a subset choice. The two feasibility checks are |target| <= total and (target+total) being even, and zeros in the input double the count since they can go either side.

Knapsack is O(n·W). Why is that not polynomial in the input size?

This is what "pseudo-polynomial" means, and 0/1 knapsack is NP-hard. Check the target's magnitude before committing: if it is up to 10⁹ with small n, the intended solution is meet-in-the-middle.
