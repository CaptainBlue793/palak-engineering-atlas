The Knapsack Family

Knapsack is the interview problem that wears the most disguises. The story: you have a bag with a weight limit and a pile of items, and you pick which ones to pack. Subset sum, partition, coin change, target sum, last stone weight and rod cutting all use this same recurrence (the rule that builds each answer from smaller answers). Only two things change: how you combine results, and which way a loop runs. Learn the one table, and the six disguises stop being six separate problems.

  • Write the 0/1 knapsack recurrence from one simple choice per item: take it or leave it
  • Explain why the direction of the capacity loop decides whether an item can be used more than once
  • Turn subset sum, partition and target sum into knapsack problems
  • Get both coin-change versions right — including why the order of nested loops matters when you count ways
  • Shrink the 2D table to a single row, and know when you must not

0/1 knapsack: the parent problem

You have some items. Each has a weight and a value. Your bag holds at most W weight, and you can use each item at most once (that is the "0/1": take it zero times or one time). Pack the bag to get the highest total value.

Why not just be greedy? The natural idea is to take items with the best value per unit of weight first. Try items (weight, value) = (1, 1), (3, 4), (4, 5), (5, 7) with W = 7. The best ratio is (5, 7) at 1.4 per unit. Take it, and only 2 units of room are left, so you can add just (1, 1), for a total of 8. But (3, 4) + (4, 5) fills the bag exactly and is worth 9. Taking one item changes what else fits, so an early choice can turn out to be a mistake. That is the DP signal from Chapter 38. Trying every subset would work, but n items have 2ⁿ subsets.

0/1 knapsack — the full 2D tableO(n·W)O(n·W)
// dp[i][w] = the maximum value using only the first i items,
//            with a capacity of exactly w available.
// Two choices at item i-1: leave it, or take it (if it fits).
int knapsack(vector<int> &weight,vector<int> &value,int W){
	int n=weight.size();
	vector<vector<int>> dp(n+1,vector<int>(W+1,0));

	for(int i=1;i<=n;i++){
		for(int w=0;w<=W;w++){
			dp[i][w]=dp[i-1][w];                 // leave item i-1

			if(weight[i-1]<=w){
				dp[i][w]=max(dp[i][w],
				              value[i-1]+dp[i-1][w-weight[i-1]]);
			}
		}
	}

	return dp[n][W];
}
The i-1 in the "take" lookup is what makes it "0/1". Row i-1 holds answers built without item i-1, so the item cannot be taken twice. Change it to dp[i] and you get unbounded knapsack (each item can be reused any number of times). Watch the i versus i-1 shift: row i is about item i-1, because row 0 means "no items yet". This shift is the most common cause of off-by-one bugs here.

A small table by hand. Items A = (1, 1), B = (3, 4), C = (4, 5), and W = 4. Each row adds one item; each column is a capacity.

Take the cell at row 2, w = 4. Leaving B gives the cell above, 1. Taking B gives 4 plus the best for the leftover capacity 1 without B, which is row 1, w = 1 = 1. So the cell is max(1, 5) = 5. In row 3, taking C at w = 4 gives 5 + row 2, w = 0 = 5, which only ties. The answer is 5, from A + B (C alone ties it). The table has (n + 1)(W + 1) cells and each does O(1) work, which is where O(n·W) comes from.

The loop direction: the single most important detail

Each row of the table only reads the row above it. So people usually shrink the table to a single row and overwrite it in place. But then the direction of the capacity loop decides whether an item can be reused. That one choice is the whole difference between 0/1 and unbounded knapsack.

0/1 — iterate capacity downward
vector<int> dp(W+1,0);

for(int i=0;i<n;i++){
	for(int w=W;w>=weight[i];w--){
		dp[w]=max(dp[w],value[i]+dp[w-weight[i]]);
	}
}

Going downward, dp[w-weight[i]] has not been updated yet in this item's pass. It still holds the value from before item i — just like reading row i-1. So each item is used at most once.

Unbounded — iterate capacity upward
vector<int> dp(W+1,0);

for(int i=0;i<n;i++){
	for(int w=weight[i];w<=W;w++){
		dp[w]=max(dp[w],value[i]+dp[w-weight[i]]);
	}
}

Going upward, dp[w-weight[i]] may already include item i from earlier in this same pass. So the item can be taken again and again. That looks like a bug, but it is exactly the unbounded behaviour you want.

✍️
My convention: write the 2D version first, then collapse — and state the direction's meaning in a comment

The 1D version is four lines and hard to understand. The 2D version is eight lines and explains itself. Get the 2D table right first and check it on a small case. Only then shrink it. When you do, add // downward: each item once or // upward: items reusable to the loop. This is the one place in DP where a loop's direction changes the meaning, not just the style. A reader (including future you) cannot tell that from the code alone.

With one item of weight 2 and value 3: downward gives a best of 3 (item used once). Upward gives 12 (item used four times).

The third variant: bounded knapsack. Sometimes each item has a limited supply: "item i can be used up to c[i] times". This sits between 0/1 and unbounded. The simplest fix is to treat item i as c[i] separate copies and run 0/1 knapsack (downward) on all of them. That costs O(W · total copies), which can be large. The standard speed-up is binary splitting: break c[i] copies into bundles of 1, 2, 4, 8, … plus a remainder. For c = 13 that is bundles of 1, 2, 4 and 6. A bundle of k copies acts as one item with k times the weight and k times the value. Every count from 0 to 13 can be made from some subset of those bundles, so a 0/1 knapsack over 4 bundles replaces one over 13 copies. The cost drops to O(W · Σ log c[i]).

The six disguises

// "Is there a subset summing to exactly target?"
// Knapsack with value = weight and a BOOLEAN table instead of a max.
// dp[w] = can a subset of the items seen so far sum to exactly w?
bool canPartitionSum(vector<int> &nums,int target){
	vector<bool> dp(target+1,false);
	dp[0]=true;                     // the empty subset sums to 0

	for(int x:nums){
		for(int w=target;w>=x;w--){   // downward: each number once
			dp[w]=dp[w] or dp[w-x];
		}
	}

	return dp[target];
}

dp[0] = true is the base case everything rests on. It says "the empty subset sums to 0". Leave it out and every cell stays false forever. Tip: this true/false version is often much faster with a bitset (a packed row of bits). bits |= bits << x; handles a whole item in one operation (Chapter 47).

Trace with nums = [3, 5, 2] and target = 7, listing the sums marked true: start {0}; after 3, {0, 3}; after 5, {0, 3, 5} (8 is past the target, so it is not stored); after 2, {0, 2, 3, 5, 7}. dp[7] is true, from 5 + 2.

// "Can the array be split into two subsets of EQUAL sum?"
// If the total is odd, impossible. Otherwise it is subset sum for total/2 —
// because one subset summing to half forces the other to as well.
bool canPartition(vector<int> &nums){
	int total=0;
	for(int x:nums)
	total+=x;

	if(total%2!=0)return false;      // the O(1) early exit

	return canPartitionSum(nums,total/2);
}

// VARIANT: "minimum difference between two subsets" — find the achievable
// sum closest to total/2, then the answer is total - 2*thatSum.
int minimumDifference(vector<int> &nums){
	int total=0;
	for(int x:nums)
	total+=x;

	int half=total/2;
	vector<bool> dp(half+1,false);
	dp[0]=true;

	for(int x:nums){
		for(int w=half;w>=x;w--)
		dp[w]=dp[w] or dp[w-x];
	}

	for(int s=half;s>=0;s--){
		if(dp[s])return total-2*s;
	}

	return total;
}

The odd-total check costs nothing and rejects about half of all inputs at once. "Last stone weight II" is exactly minimumDifference with a different story. Smashing stones in pairs is the same as giving each stone a + or − sign. And that is the same as splitting the stones into two groups.

// "Assign + or - to each number so the total equals target. How many ways?"
// Let P be the positives and N the negatives.
//   P - N = target  and  P + N = total
//   => P = (target + total) / 2
// So COUNT the subsets summing to that value. Pure subset-sum counting.
int findTargetSumWays(vector<int> &nums,int target){
	int total=0;
	for(int x:nums)
	total+=x;

	if(abs(target)>total)return 0;
	if((target+total)%2!=0)return 0;   // P must be an integer

	int P=(target+total)/2;

	vector<int> dp(P+1,0);
	dp[0]=1;                          // one way to make 0: take nothing

	for(int x:nums){
		for(int w=P;w>=x;w--)
		dp[w]+=dp[w-x];              // COUNTING, so += not max
	}

	return dp[P];
}

The algebra is the whole problem. Choosing signs is really choosing which numbers go in the "+" group. Once you see that, it is knapsack. Watch the zeros: a 0 can go in either group, so it doubles the number of ways. That is why dp[0] must start at 1 and the loop must handle x = 0. The downward loop with w >= 0 handles it correctly and doubles the count, as it should.

Check it on nums = [1, 1, 1, 1, 1], target = 3. The total is 5, so P = (3 + 5) / 2 = 4: you need four of the ones positive and one negative. There are 5 ways to pick which one is negative, and the DP returns 5. The two early exits matter too: if |target| > total, even all-plus or all-minus cannot reach it; if target + total is odd, P would not be a whole number.

// "Fewest coins to make amount." Unbounded (coins reusable), minimising.
// dp[w] = the minimum number of coins summing to exactly w.
int coinChange(vector<int> &coins,int amount){
	vector<int> dp(amount+1,amount+1);   // amount+1 = "impossible"
	dp[0]=0;

	for(int c:coins){
		for(int w=c;w<=amount;w++)      // UPWARD: coins reusable
		dp[w]=min(dp[w],1+dp[w-c]);
	}

	return dp[amount]>amount?-1:dp[amount];
}

Use amount+1 to mean "impossible", not INT_MAX. A special marker value like this is called a sentinel. The problem with INT_MAX: 1 + INT_MAX overflows to a negative number, and that quietly becomes the minimum. Any value bigger than the largest real answer works. amount+1 is the natural pick, because you never need more than amount coins.

Why not greedy? With coins [1, 3, 4] and amount 6, "biggest coin first" takes 4 + 1 + 1 = 3 coins. The DP fills dp[0..6] = 0, 1, 2, 1, 1, 2, 2 and finds 3 + 3 = 2 coins. If the amount cannot be made at all (coins [2], amount 3), dp[3] stays at the sentinel and the function returns −1.

// "How many ways to make amount, order irrelevant?"
// SAME table, but the LOOP NESTING is the whole problem.
int change(int amount,vector<int> &coins){
	vector<int> dp(amount+1,0);
	dp[0]=1;

	for(int c:coins){              // COIN loop OUTSIDE
		for(int w=c;w<=amount;w++)
		dp[w]+=dp[w-c];
	}

	return dp[amount];
}

// Swap the loops and you count ORDERED sequences (permutations) instead:
//   for(int w=1;w<=amount;w++)
//     for(int c:coins)
//       if(c<=w) dp[w]+=dp[w-c];
// That is "combination sum IV", a DIFFERENT problem with a bigger answer.

Coin loop outside = combinations (order does not matter). Amount loop outside = permutations (order matters). With coins {1,2} and amount 3: coin-outside gives 2 ({1,1,1}, {1,2}). Amount-outside gives 3 ({1,1,1}, {1,2}, {2,1}). This is the most important loop-order fact in DP, and the two versions differ only in which loop is on the outside.

Watch the tables. Coin loop outside: after coin 1, dp = [1, 1, 1, 1] (only 1s). Coin 2 then adds dp[0] to dp[2] and dp[1] to dp[3], giving [1, 1, 2, 2]. A 2 is only ever added on top of 1s, never before them, so {1, 2} is built once. Amount loop outside: dp[1] = 1, dp[2] = dp[1] + dp[0] = 2, dp[3] = dp[2] + dp[1] = 3. Each amount tries every coin as the last one, so "1 then 2" and "2 then 1" are both counted.

// "Cut a rod of length n into pieces to maximise total price."
// Unbounded knapsack where weight = length and value = price.
// dp[L] = the maximum revenue obtainable from a rod of length L.
int rodCutting(vector<int> &price,int n){
	vector<int> dp(n+1,0);

	for(int len=1;len<=n;len++){
		for(int cut=1;cut<=len;cut++){
			dp[len]=max(dp[len],price[cut-1]+dp[len-cut]);
		}
	}

	return dp[n];
}
// Written amount-outside here, which is fine because we are MAXIMISING,
// not counting — loop order only matters for counting.

Worth noting: the loop-order trap only matters when you are counting. For min or max, both orders give the same answer. The best value does not care in which order the items were looked at. That is why coin-change-minimum can be written either way, but coin-change-count cannot.

Trace with prices [1, 5, 8, 9] for piece lengths 1 to 4, and a rod of length 4: dp[1] = 1, dp[2] = max(1 + 1, 5) = 5, dp[3] = max(1 + 5, 5 + 1, 8) = 8, dp[4] = max(1 + 8, 5 + 5, 8 + 1, 9) = 10. Two pieces of length 2 beat selling the rod whole for 9.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 TWO LOOP RULES
In 1D knapsack, capacity descending means each item once; ascending means unlimited reuse. And coins-outer counts combinations while capacity-outer counts permutations. Memorise those two sentences.
💡 SIX DISGUISES
Subset sum, partition, target sum, coin change (min), coin change (count) and rod cutting are all one table. Learn the table, then map the problem onto it.
⛔ TARGET TOO BIG
Knapsack is O(n·target) — pseudo-polynomial. When the target is 10⁹ and n ≤ 40, it is meet-in-the-middle, not DP.

These two rules are separate, and both matter.

  • Unbounded, counting combinations: upward + item loop outside.
  • Unbounded, counting permutations: upward + capacity loop outside.
  • 0/1 counting: downward + item loop outside. (Capacity outside would be wrong here for a different reason — it would let an item be considered again.)

Say which combination you need before you write the loops.

Reconstruction, and when you cannot

Why the backward walk works: dp[i][w] is either the "leave" value dp[i-1][w] or the "take" value. If it differs from the cell above, "leave" cannot explain it, so item i-1 must have been taken, and the rest of the bag is the best answer for capacity w - weight[i-1] one row up. On the hand-built table above: row 3, w = 4 is 5, the same as row 2, so C was not taken. Row 2, w = 4 is 5, but row 1 has 1, so B was taken; move to w = 1. Row 1, w = 1 is 1, but row 0 has 0, so A was taken. The items are A and B. When the values tie, as C did here, the walk picks "not taken", which is still an optimal answer.

which items were chosen?needs the full 2D table
// Walk backwards from dp[n][W]. If the value differs from the row above,
// item i-1 must have been taken.
vector<int> chosenItems(vector<vector<int>> &dp,vector<int> &weight,int n,int W){
	vector<int> items;
	int w=W;

	for(int i=n;i>0;i--){
		if(dp[i][w]!=dp[i-1][w]){      // the value changed -> item was used
			items.push_back(i-1);
			w-=weight[i-1];
		}
	}

	reverse(items.begin(),items.end());

	return items;
}
This is why you should not shrink the table out of habit (Chapter 38). The 1D version answers "what is the best value?". But it has thrown away the information you need for "which items?". If you must list the items, keep the full O(n·W) table. At n = 100 and W = 10⁴ that is a million cells, which is fine.
⏱️
O(n·W) is "pseudo-polynomial" — and that matters

Knapsack's running time depends on the size of the number W, not on how many digits it takes to write it. So W = 10⁹ with just 10 items is far too slow, even though the input is tiny: the table would have 10¹⁰ cells. That is what pseudo-polynomial means. In fact 0/1 knapsack is NP-hard (no known fast algorithm for all inputs). O(n·W) is only fast when W is small.

What this means in interviews: if the capacity or target can be up to 10⁹, knapsack DP is not the intended solution. Look instead for meet-in-the-middle (Chapter 44), a greedy approach if items can be split into fractions (Chapter 36), or a different way of framing the problem. Always check the limit on the target before you commit to this approach.

🗝️
Recognising a knapsack in disguise
  • “Choose a subset such that the sum is / reaches / is closest to X”
  • “Split into two groups with …” — partition
  • “Assign + or − to each number” — target sum, via the algebra above
  • “Fewest / most items to reach exactly X” — coin change
  • “How many ways to reach exactly X” — counting knapsack, and mind the nesting
  • “Fill a container / reach a total with limited or unlimited supply”
  • The giveaway is a target with a small upper limit, plus a yes/no choice for each item. If the target has no small limit, it is not this.
⚠️
Common mistakes
  • Wrong capacity loop direction. Downward for 0/1, upward for unbounded — and the code looks almost the same either way.
  • Wrong loop nesting in a counting problem. Item outside counts combinations; capacity outside counts permutations.
  • Forgetting dp[0] = true or dp[0] = 1. This is the empty-subset base case. Without it, the whole table stays empty.
  • Using INT_MAX to mean "impossible" in coin change. 1 + INT_MAX overflows to a negative number and becomes the minimum.
  • Mixing the i / i-1 index convention. Row i is about item i-1, because row 0 means "no items".
  • Shrinking to 1D when you need the chosen items. The 1D table cannot be walked backwards.
  • Not checking if the total is odd in the partition problem. It is a free O(1) check that rejects half the inputs.
  • Assuming O(n·W) is always fast. It is pseudo-polynomial: W = 10⁹ is far too slow.
  • Mishandling zeros in target sum. A 0 can go either side, which doubles the count.
  • Using the greedy "biggest coin first" rule. It only works for special coin systems, like real-world currency (Chapter 36).

Interview drill

Warm-up: Can this array be partitioned into two subsets of equal sum?

How a strong answer sounds
First, the free check: if the total is odd, no such split exists, so return false right away. Otherwise this becomes subset sum for total/2. If one group sums to half, the rest must sum to half too. So I define dp[w] as "can some subset of the numbers seen so far sum to exactly w". Its size is total/2 + 1, and dp[0] = true for the empty subset. Everything depends on that base case — without it, the table stays false forever. Then, for each number, I loop the capacity downward from total/2 to that number and set dp[w] |= dp[w − x]. Downward is essential. It guarantees dp[w − x] still shows the state before this number was used, so each number is used at most once. Looping upward would allow reuse and solve a different problem. The cost is O(n · total) time and O(total) space. I would point out that this is pseudo-polynomial: if the values could sum to 10⁹, this approach is out and I would need meet-in-the-middle instead. One nice speed-up: with a bitset, the whole inner loop becomes bits |= bits << x;. That handles 64 capacities per instruction — roughly 64× faster for the true/false version.

Deeper: Coin change — number of ways. Why does the loop nesting change the answer?

How a strong answer sounds
Because the loop order decides whether {1,2} and {2,1} count as one solution or two. With the coin loop outside and the amount loop inside, I finish with coin 1 completely before I ever look at coin 2. So every combination is built in one fixed coin order, and each group of coins (a multiset) is counted exactly once. That gives combinations. With the amount loop outside and the coin loop inside, at each amount I try every coin as the last one added. So the same group of coins is reached in every possible order, and each order is counted separately. That gives permutations — the "combination sum IV" problem. Concretely, with coins {1,2} and amount 3: coin-outside gives 2 — {1,1,1} and {1,2}. Amount-outside gives 3, adding {2,1}. Two important notes. First, this only matters for counting. For a min or max goal, both orders give the same answer, because the best value does not depend on the order items were looked at. That is why coin-change-minimum can be written either way. Second, loop order is separate from the capacity direction. Direction controls reuse, not ordering. So I decide both separately, and say which of the four combinations I need before writing the loops.

🧠 Key takeaways

  • One recurrence — take the item or leave it — sits under subset sum, partition, target sum, coin change and rod cutting.
  • The capacity loop direction controls reuse: downward means each item once, upward means unlimited.
  • Which loop is outside controls ordering, and only when counting: item outside = combinations, capacity outside = permutations.
  • dp[0] = 1 (or true) is the empty-subset base case. The value you use for "impossible" must not overflow when you add 1 to it.
  • O(n·W) is pseudo-polynomial — check how big the target can be before you commit to knapsack DP.

Check your understanding

In the 1D knapsack, why iterate the capacity downward for 0/1?

Going downward is the same as reading row i-1 of the 2D table. Going upward reads values that may already include the current item — which is exactly unbounded knapsack.

Coin change II counts the number of ways. Which loop goes outside for combinations?

Coin loop outside gives combinations. Amount loop outside gives permutations (combination sum IV). With coins {1,2} and amount 3, that is 2 versus 3. This only matters for counting — for min/max, both orders agree.

Why use amount+1 rather than INT_MAX as the "impossible" sentinel in coin change?

Any "impossible" marker bigger than the largest real answer works. amount+1 is the natural choice, since you never need more than amount coins. INT_MAX breaks the moment you add 1 to it.

"Assign + or − to each number so the total is target. How many ways?" How does this reduce to knapsack?

Choosing signs is choosing a subset. Two quick checks rule out impossible cases: |target| <= total, and (target+total) must be even. Zeros in the input double the count, since they can go on either side.

Knapsack is O(n·W). Why is that not polynomial in the input size?

This is what "pseudo-polynomial" means, and 0/1 knapsack is NP-hard. Check how big the target can be before you commit. If it goes up to 10⁹ with small n, the intended solution is meet-in-the-middle.
