Designing Data Structures

"Design a class with these operations, all in O(1)" is its own type of interview question. It has one reliable method: write down every operation and how fast it must be, then combine two or three data structures so each operation is handled by whichever one is fast at it. Almost every answer in this chapter is a hash map paired with something that keeps an order.

  • Apply the composition method: list the operations, then pick structures per operation
  • Build an LRU cache from a hash map plus a doubly linked list
  • Extend to LFU, and see where the extra dimension goes
  • Design min-stack, randomised set, and an O(1) insert/delete/getRandom
  • Know what skip lists, Bloom filters and sqrt decomposition are for

The method

Why is this its own kind of question? Every standard structure is fast at some things and slow at others. A hash map finds a key in O(1) but has no order. A linked list keeps order but takes O(n) to find anything. A design question asks for a set of operations that no single structure handles well. It tests whether you can see which operation each structure is good at, and join them without the copies drifting apart. These are also the structures real systems are built from. Browser caches, database buffer pools and API rate limiters are the same designs you will meet here.

✍️
My convention: tabulate the operations before writing a single member

Design questions go wrong when you start coding from the first operation. So I first write a three-column table: operation, how fast it must be, and which structure provides it. Only then do I declare the class members. That table does three jobs at once:

  • It shows the one operation that is actually hard (there is usually exactly one).
  • It tells you how many structures you need.
  • It becomes the explanation you say out loud.

If two operations want the data laid out in conflicting ways, you need two structures that point into each other. That is the shape of nearly every answer below. Also write the invariant (the rule that must always stay true) in a comment, for example "the map's value is an iterator into the list". The bugs in these classes are almost always one structure being updated and the other not.

An LRU cache ("least recently used") keeps a fixed number of items and throws out the one untouched for longest when it is full. The head is the most recently used item. The tail is the next one to be thrown out (evicted). Every operation just relinks a node (a "splice"): no shifting, no searching.
LRU cache — O(1) get and putO(1)O(capacity)
// Operations:  get(key) O(1)   put(key,value) O(1)   evict least-recent O(1)
//
//   "find by key"          -> hash map
//   "know the order of use" -> doubly linked list, most-recent at the front
//   "move a node to the front in O(1)" -> needs the NODE, not the key,
//        which is exactly why the map stores an ITERATOR into the list.
//
// Why doubly and not singly linked: removing a node in O(1) requires its
// predecessor, and a singly linked list cannot give you that.
class LRUCache{
	int capacity;
	list<pair<int,int>> order;                          // front = most recent
	unordered_map<int,list<pair<int,int>>::iterator> position;

public:
	LRUCache(int capacity){
		this->capacity=capacity;
	}

	int get(int key){
		if(position.find(key)==position.end())return -1;

		// splice moves the node without copying or invalidating the iterator
		order.splice(order.begin(),order,position[key]);

		return position[key]->second;
	}

	void put(int key,int value){
		if(position.find(key)!=position.end()){
			position[key]->second=value;
			order.splice(order.begin(),order,position[key]);

			return;
		}

		if(order.size()==capacity){
			int victim=order.back().first;

			order.pop_back();
			position.erase(victim);        // BOTH structures, always
		}

		order.push_front({key,value});
		position[key]=order.begin();
	}
};
The one rule that must always hold: position[key] is an iterator (a pointer-like handle) to that key's node in order. Every LRU bug is this rule breaking. For example, updating the list but not the map, or erasing the wrong key from the map. std::list::splice is the right tool because it relinks nodes instead of copying them. So iterators stay valid, and the whole design depends on that.

In an interview you may be asked to write the linked list yourself. If so, use dummy head and tail nodes (sentinels), so insert and remove never need a null check. It is the same trick as Chapter 12. Also note that std::list::size() is O(1) in C++11 and later, so the capacity check is safe.

A trace with capacity 2. The list is shown front (most recent) to back.

  1. put(1), put(2): the list is [2, 1].
  2. get(1): a hit. Key 1 moves to the front, giving [1, 2]. Key 2 is now the least recently used.
  3. put(3): the cache is full, so evict the back (key 2) from the list and the map, then push 3: [3, 1].
  4. get(2): a miss, so return −1. Key 2 was evicted in step 3.
  5. put(4): evict the back (key 1): [4, 3].

Notice step 2. Reading a key counts as using it, so a get changes which item will be evicted. Edge cases to check: a put on a key that already exists updates it and moves it, and never evicts anything. A capacity of 1 evicts on every new key. If the capacity can be 0, handle it first. Otherwise order.back() is called on an empty list, which is undefined behaviour.

🔁
LFU: the same method, one more dimension

An LFU cache throws out the least frequently used item. If several items are tied, it throws out the least recently used of them. The operation table gains a row, so the class gains a member:

// keyToValue    : key -> {value, frequency}
// keyToIterator : key -> its position inside its frequency bucket
// freqToList    : frequency -> a list of keys at that frequency (LRU within it)
// minFreq       : the smallest frequency currently present
//
// On access: remove the key from bucket f, append it to bucket f+1.
// If bucket f is now empty AND f == minFreq, then minFreq becomes f+1.
// On evict: take the FRONT of bucket minFreq — least frequent, and
//           least recent among those.

Why tracking minFreq keeps it O(1): it only changes in two ways. It goes up by one when an access empties the current lowest bucket, or it resets to 1 when a new key is inserted. So you never have to search for it. That one observation is the difference between O(1) and O(n) here, and it is the thing to say out loud. LFU usually comes up as a follow-up ("can you extend your own design?") rather than as a question on its own.

A short LFU trace with capacity 2. put(1) and put(2) put both keys in bucket 1, and minFreq = 1. get(1) moves key 1 to bucket 2. Bucket 1 still holds key 2, so minFreq stays 1. put(3) is over capacity, so it evicts the front of bucket 1 (key 2) and inserts 3 into bucket 1. get(3) moves key 3 to bucket 2, which now holds [1, 3]. Bucket 1 is empty and 1 was minFreq, so minFreq becomes 2. Finally put(4) evicts the front of bucket 2. That is key 1: both keys have been used twice, and 1 was used less recently. Key 4 then goes into bucket 1, and minFreq resets to 1.

Min-stack and randomised set

Min-stack — O(1) minimum
// push, pop, top, getMin — all O(1).
// A single variable cannot work: popping the minimum must reveal the
// PREVIOUS minimum, so the history has to be stored.
// Key insight: a second stack holding "the minimum at this depth" mirrors
// the main stack exactly, so pops line up automatically.
class MinStack{
	stack<int> st;
	stack<int> mins;

public:
	void push(int val){
		st.push(val);

		if(mins.empty())mins.push(val);
		else mins.push(min(val,mins.top()));
	}

	void pop(){
		st.pop();
		mins.pop();
	}

	int top(){
		return st.top();
	}

	int getMin(){
		return mins.top();
	}
};

Pushing onto the minima stack every time, even a repeat, is on purpose. It keeps the two stacks the same height, so pop needs no comparison and the stacks can never get out of step. The "only push when smaller" version saves space, but then pop must compare. Getting that comparison wrong on equal values is the classic bug. Spending O(n) extra space for a simple, always-pop-both pop is the right call, unless space is tightly limited.

Insert / delete / getRandom in O(1)
// getRandom must be O(1) and uniform -> the elements must live in a
// CONTIGUOUS array, so a random index is a valid element.
// But delete from the middle of an array is O(n)...
// ...unless you swap the victim with the LAST element and pop the back,
// which is O(1) because order does not matter here.
class RandomizedSet{
	vector<int> values;
	unordered_map<int,int> indexOf;

public:
	bool insert(int val){
		if(indexOf.count(val))return false;

		indexOf[val]=values.size();
		values.push_back(val);

		return true;
	}

	bool remove(int val){
		if(!indexOf.count(val))return false;

		int i=indexOf[val];
		int last=values.back();

		values[i]=last;              // move the last element into the hole
		indexOf[last]=i;             // and fix ITS index — easy to forget

		values.pop_back();
		indexOf.erase(val);

		return true;
	}

	int getRandom(){
		return values[rand()%values.size()];
	}
};

"Swap with the last, then pop" is a pattern worth remembering. It makes deletion O(1) in any collection where order does not matter. The tricky line is indexOf[last]=i. Leave it out and the map keeps an out-of-date index. That only gives wrong results after some later delete, which is painful to debug. Get the order of the last two steps right, too. If val is the last element, erase after the overwrite, or you erase the entry you just wrote.

Min-stack, traced. Push 5, 3, 7, 3. The main stack is [5, 3, 7, 3], and the minima stack is [5, 3, 3, 3]. Each entry is "the smallest value at or below this depth". Pop, and getMin is still 3, because the other 3 is still there. Pop again (the 7), and getMin is 3. Pop again (the first 3), and getMin is 5. The earlier minimum comes back on its own, because it was saved at that depth all along.

Randomised set, traced. Insert 10, 20, 30. Now values = [10, 20, 30] and indexOf = {10:0, 20:1, 30:2}. To remove 10: its index is 0 and the last value is 30. Copy 30 into slot 0 and set indexOf[30] = 0. Pop the back and erase 10. The result is values = [30, 20] and indexOf = {30:0, 20:1}, and both still agree. Now remove 20, which is the last element. The code copies 20 onto itself, sets indexOf[20] = 1, pops, and then erases 20. That works only because the erase comes last.

🎯
Why "getRandom in O(1)" forces an array

This is the most often missed clue in these questions. A hash map has no idea of "the i-th element", and walking through it to find one is O(n). A tree can do it in O(log n) if each node stores its subtree size, but not in O(1). Only an array with no gaps (contiguous) lets you "pick index rand()%n" in constant time. So the moment you see getRandom, you know you need an array. The rest of the work is making insert and delete fast on top of that array. That is the swap-with-last trick, plus a map from value to index so you can find the item to delete.

The same reasoning drives Insert Delete GetRandom with duplicates (the map's value becomes a set of indices) and random pick with weight (prefix sums plus a binary search, which is O(log n), and that is the best possible there).

Three structures worth recognising

🏗️
Skip list, Bloom filter, sqrt decomposition
  • Skip list: a sorted linked list with random "express lanes", like express and local stops on a train line. Each node is promoted to the next level up with probability ½. So a search drops down through about O(log n) levels on average. It performs like a balanced binary search tree but needs no rotations. That makes it much easier to get right, and it is why Redis uses it for sorted sets. Search, insert and delete are O(log n) expected. Because it is random, that bound is an average, not a worst-case promise.
  • Bloom filter: an array of bits plus k hash functions. Inserting a key sets k bits. A lookup says "possibly present" if all k of its bits are set. It can wrongly say "present" (a false positive), but it never wrongly says "absent" (no false negatives). There is no deletion, because clearing a bit could wipe out evidence for another key. Use it as a cheap front door: it skips an expensive lookup, such as a database or network call, when the answer is almost certainly "absent". You tune the false-positive rate with the number of bits and k.
  • Sqrt decomposition: split an array into √n blocks and keep a summary (for example, the sum) for each block. A range query touches at most two partial blocks and √n whole ones. So each query is O(√n) and each single-element update is O(1). A segment tree beats it at O(log n), but sqrt decomposition is far shorter to write and easy to adapt to unusual summaries that a segment tree struggles with.
    Its famous relative, Mo's algorithm, works offline (all queries are known up front). It sorts the queries by block and answers them all in O((n+q)√n) by sliding two pointers. It is the standard tool for "many range queries, no updates, and a summary that is hard to combine", such as "count distinct values in a range".

Recognising these is usually the whole answer. Take "is this URL probably one we have already seen, with a gigabyte of memory and a billion URLs?" Naming a Bloom filter is the point. Writing one is a footnote.

Some numbers to make these concrete:

  • Skip list: why about log n levels? Half the nodes reach level 2, a quarter reach level 3, and so on. With 1,000,000 nodes, only about one node reaches level 20 (since 2²⁰ ≈ 10⁶). A search starts at the top level and moves right until the next step would overshoot, then drops down a level. On average it takes about two steps per level, so the whole search is roughly 2·20 = 40 steps.
  • Bloom filter: with about 10 bits per key and k = 7 hash functions, the false-positive rate is about 1%. For the billion-URL example, that is 10¹⁰ bits, about 1.25 GB, compared with tens of gigabytes to store the URLs themselves. A "no" is always right. A "yes" is wrong about 1 time in 100, and then you pay for the real lookup.
  • Sqrt decomposition: take n = 16 and blocks of 4 (positions 0–3, 4–7, 8–11 and 12–15). To sum positions 2 to 13, add elements 2 and 3 one by one, add the stored sums of blocks 4–7 and 8–11, then add elements 12 and 13 one by one. That is 6 additions instead of 12. With n = 10⁶ and blocks of 1,000, a query costs at most about 3,000 steps instead of up to a million.

Notice how often the answer is "a map to something ordered", and how often that ordered thing is just a plain vector with a binary search. Several of these ask for O(log n), not O(1). Read the required speed before assuming O(1) is needed.

Why "queue from two stacks" is O(1) amortised. Push onto the in-stack. To pop, take from the out-stack. If the out-stack is empty, first move everything from the in-stack onto it. That move reverses the order, so the oldest item ends up on top. A single pop can cost O(n) when it triggers a move. But each item is moved at most once in its lifetime: pushed once, moved once, popped once. So n operations cost O(n) in total, which is O(1) each on average. Example: push 1, 2, 3. The first pop moves them all, so the out-stack has 1 on top, and it returns 1. The next two pops return 2 and 3 with no moving at all.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 TABULATE FIRST
Write operation → required complexity → structure before declaring a single member. The hard operation reveals the design, and the table becomes your explanation.
💡 getRandom ⇒ ARRAY
O(1) uniform random forces a contiguous array. Deletion then becomes swap-with-last — and the line people forget is updating the moved element’s index.
⛔ UPDATE BOTH
Every bug in an LRU is one structure updated and the other not. State the invariant — the map holds a valid iterator into the list — and check it at every exit.
⚠️
Common mistakes
  • Updating one structure and not the other. On eviction, remove the item from both the list and the map.
  • Storing the key in the map when you need the node. An O(1) splice needs the node's position, not the key.
  • Using a singly linked list for LRU. Removing a node in O(1) needs the node before it, which only a doubly linked list gives you.
  • Forgetting indexOf[last]=i in the swap-with-last delete. It leaves an out-of-date index that only breaks later.
  • Erasing before overwriting when the item being removed is the last element.
  • Trying to do getRandom in O(1) with a hash map or tree. It needs a contiguous array.
  • Using a single minimum variable in min-stack. It cannot bring back the previous minimum after a pop.
  • Not tracking minFreq in LFU, which makes eviction O(n). The key fact is that it only ever goes up by one or resets to 1.
  • Expecting a Bloom filter to support deletion, or to never give false positives.
  • Promising worst-case O(log n) for a skip list. It is an average (expected) bound, because levels are chosen at random.
  • Reaching for a segment tree when sqrt decomposition or Mo's is shorter. Or the reverse when there are updates: Mo's works offline and cannot handle them.

Interview drill

Warm-up: Design an LRU cache with O(1) get and put.

How a strong answer sounds
I would start by listing the operations: get by key in O(1), put by key in O(1), and evict the least recently used item in O(1). Finding by key means a hash map. Knowing the order of use means a list with the most recent item at the front. The hard operation is moving an existing item to the front in O(1). That needs the node, not the key. So the map's value is a pointer or iterator into the list, not the value itself. The list must be doubly linked, because unlinking a node in O(1) needs the node before it, and a singly linked list cannot give you that.

So the design is: a list of (key, value) pairs with the most recent at the front, plus an unordered_map from key to an iterator into that list. get looks up the key, splices its node to the front, and returns the value. put either updates the value and splices, or inserts at the front. If that goes over capacity, it takes the key at the back, pops it, and erases it from the map.

The rule to state out loud is that the map's value is always a valid iterator to that key's node. std::list::splice is the right tool because it relinks nodes without copying, so iterators stay valid. Nearly every bug in this class is that rule breaking. The most common one: eviction removes the item from the list but not the map. The map then grows without limit, and later lookups return iterators to nodes that no longer exist.

If asked not to use the STL, I would write the list myself with dummy head and tail nodes (sentinels), so insert and remove need no null checks. Space is O(capacity). I would also mention that the usual follow-up is LFU, which adds frequency buckets and a tracked minimum frequency.

Deeper: Design a set with insert, remove and getRandom, all O(1) and the random uniform.

How a strong answer sounds
The getRandom requirement decides the design, and I would say that first. Picking uniformly at random in O(1) means I must be able to pick an index and land on a real element. That requires the elements to sit in a contiguous array (no gaps). A hash map has no idea of "the i-th element", and walking through it to find one is O(n). A tree can do it in O(log n) with subtree sizes, but not O(1). So an array is forced, and the question becomes how to make insert and remove O(1) on top of it.

Insert is easy: append to the back, and record the value's index in a hash map. Remove is the interesting one, because deleting from the middle of an array is normally O(n). But order does not matter in a set. So I can fill the hole with the last element and pop the back, which is O(1). Step by step: look up the removed value's index i, copy the last element into slot i, update the map so the moved element's index becomes i, pop the back, and erase the removed value from the map.

The line people forget is updating the moved element's index. Without it, the map holds an out-of-date entry that only gives a wrong answer on some later delete, which is unpleasant to debug. The order of steps also matters. If the removed value is the last element, the overwrite must happen before the erase, or you erase the entry you just wrote. I would test that case directly, along with removing the only element.

All operations are O(1) on average, limited by the hash map, and space is O(n). The usual follow-up allows duplicates. Then the map's value becomes a set of indices, and the same swap-with-last trick still works with a little more bookkeeping.

🧠 Key takeaways

  • Write a table of operation → required speed → structure before writing any members. The hard operation shows you the design.
  • Conflicting requirements mean two structures that point into each other, usually a map pointing into something ordered.
  • LRU is a map to list iterators. The rule is that each iterator stays valid, which is why splice is used.
  • "getRandom in O(1)" forces a contiguous array. Deletion then becomes swap-with-last.
  • When an operation must be undoable, store the history (for example, a second stack of minimums).
  • Recognise skip lists, Bloom filters, sqrt decomposition and Mo's algorithm. Naming them is usually the answer.

Check your understanding

In an LRU cache, why does the hash map store an iterator (or node pointer) rather than the value?

The list must also be doubly linked, since unlinking a node in O(1) needs the node before it. The rule "the map's value is a valid iterator" is where all the bugs live.

Which requirement forces the elements to be held in a contiguous array?

Only an array lets you "pick index rand()%n" in constant time. A map has no i-th element, and a tree needs O(log n) with subtree sizes. Deletion then becomes swap-with-last.

Min-stack pushes a value onto the minima stack on every push, even a duplicate minimum. Why?

The "only push when smaller" version saves space, but then pop must compare. Getting that comparison wrong on equal values is the classic bug here.

In LFU, why is tracking minFreq enough to keep eviction O(1)?

That observation is the whole trick, and it is the thing to say out loud. Without it, finding the lowest frequency means scanning, and eviction slows to O(n).

A Bloom filter reports that a key is present. What do you actually know?

That makes it a cheap front door: a "no" is always right, so you can skip the expensive lookup entirely. Note there is also no deletion, because clearing a bit could erase another key's evidence.
