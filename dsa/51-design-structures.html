Designing Data Structures

"Design a class with these operations, all in O(1)" is its own interview genre, and it has a single reliable method: write down every operation with its required complexity, then compose two or three structures so that each operation lands on whichever one is fast at it. Almost every answer in this chapter is a hash map paired with something ordered.

  • Apply the composition method: list the operations, then pick structures per operation
  • Build an LRU cache from a hash map plus a doubly linked list
  • Extend to LFU, and see where the extra dimension goes
  • Design min-stack, randomised set, and an O(1) insert/delete/getRandom
  • Know what skip lists, Bloom filters and sqrt decomposition are for

The method

✍️
My convention: tabulate the operations before writing a single member

Design questions go wrong when you start coding from the first operation. I write a three-column table first — operation, required complexity, which structure provides it — and only then declare the members. That table does three things at once: it exposes the operation that is actually hard (there is usually exactly one), it tells you how many structures you need, and it becomes the explanation you give aloud. If two operations want contradictory layouts, that is the signal you need two structures with cross-references, which is the shape of nearly every answer below. And keep the invariant explicit in a comment — "the map's value is an iterator into the list" — because the bugs in these classes are almost always one structure being updated and the other not.

LRU cache — O(1) get and putO(1)O(capacity)
// Operations:  get(key) O(1)   put(key,value) O(1)   evict least-recent O(1)
//
//   "find by key"          -> hash map
//   "know the order of use" -> doubly linked list, most-recent at the front
//   "move a node to the front in O(1)" -> needs the NODE, not the key,
//        which is exactly why the map stores an ITERATOR into the list.
//
// Why doubly and not singly linked: removing a node in O(1) requires its
// predecessor, and a singly linked list cannot give you that.
class LRUCache{
	int capacity;
	list<pair<int,int>> order;                          // front = most recent
	unordered_map<int,list<pair<int,int>>::iterator> position;

public:
	LRUCache(int capacity){
		this->capacity=capacity;
	}

	int get(int key){
		if(position.find(key)==position.end())return -1;

		// splice moves the node without copying or invalidating the iterator
		order.splice(order.begin(),order,position[key]);

		return position[key]->second;
	}

	void put(int key,int value){
		if(position.find(key)!=position.end()){
			position[key]->second=value;
			order.splice(order.begin(),order,position[key]);

			return;
		}

		if(order.size()==capacity){
			int victim=order.back().first;

			order.pop_back();
			position.erase(victim);        // BOTH structures, always
		}

		order.push_front({key,value});
		position[key]=order.begin();
	}
};
The one invariant: position[key] is an iterator to that key's node in order. Every bug in an LRU implementation is that invariant breaking — updating the list without the map, or erasing from the map by the wrong key. std::list::splice is the right tool because it relinks nodes rather than copying them, so iterators stay valid, which is the property the whole design rests on. In an interview you may be asked to hand-roll the linked list; if so, use dummy head and tail sentinels so insert and remove never need a null check — the same trick as Chapter 13. Note also that std::list::size() is O(1) in C++11 and later, so the capacity check is safe.
🔁
LFU: the same method, one more dimension

Least-frequently-used eviction, with ties broken by recency. The operation table gains a row, so the structure gains a member:

// keyToValue    : key -> {value, frequency}
// keyToIterator : key -> its position inside its frequency bucket
// freqToList    : frequency -> a list of keys at that frequency (LRU within it)
// minFreq       : the smallest frequency currently present
//
// On access: remove the key from bucket f, append it to bucket f+1.
// If bucket f is now empty AND f == minFreq, then minFreq becomes f+1.
// On evict: take the FRONT of bucket minFreq — least frequent, and
//           least recent among those.

Why tracking minFreq keeps it O(1): it can only ever increase by one (on an access that empties the current minimum bucket) or reset to 1 (on an insertion), so it never needs to be searched for. That single observation is the difference between O(1) and O(n) here, and it is the thing to say out loud — LFU is a "can you extend your own design" follow-up far more often than a question on its own.

Min-stack and randomised set

Min-stack — O(1) minimum
// push, pop, top, getMin — all O(1).
// A single variable cannot work: popping the minimum must reveal the
// PREVIOUS minimum, so the history has to be stored.
// Key insight: a second stack holding "the minimum at this depth" mirrors
// the main stack exactly, so pops line up automatically.
class MinStack{
	stack<int> st;
	stack<int> mins;

public:
	void push(int val){
		st.push(val);

		if(mins.empty())mins.push(val);
		else mins.push(min(val,mins.top()));
	}

	void pop(){
		st.pop();
		mins.pop();
	}

	int top(){
		return st.top();
	}

	int getMin(){
		return mins.top();
	}
};

Pushing a duplicate minimum every time is deliberate — it keeps the two stacks the same height, so pop needs no comparison and cannot desynchronise. The "only push when smaller" variant saves space but then pop must compare, and getting that comparison wrong on equal values is the classic bug. Trading O(n) extra space for an unconditional pop is the right call unless space is specifically constrained.

Insert / delete / getRandom in O(1)
// getRandom must be O(1) and uniform -> the elements must live in a
// CONTIGUOUS array, so a random index is a valid element.
// But delete from the middle of an array is O(n)...
// ...unless you swap the victim with the LAST element and pop the back,
// which is O(1) because order does not matter here.
class RandomizedSet{
	vector<int> values;
	unordered_map<int,int> indexOf;

public:
	bool insert(int val){
		if(indexOf.count(val))return false;

		indexOf[val]=values.size();
		values.push_back(val);

		return true;
	}

	bool remove(int val){
		if(!indexOf.count(val))return false;

		int i=indexOf[val];
		int last=values.back();

		values[i]=last;              // move the last element into the hole
		indexOf[last]=i;             // and fix ITS index — easy to forget

		values.pop_back();
		indexOf.erase(val);

		return true;
	}

	int getRandom(){
		return values[rand()%values.size()];
	}
};

"Swap with the last, then pop" is worth remembering as an idiom — it makes deletion O(1) in any collection where order is irrelevant. The subtle line is indexOf[last]=i; omitting it leaves a stale index that produces wrong results only after a later delete, which is painful to debug. Order the two operations carefully too: if val is the last element, erase after the overwrite, or you erase the entry you just wrote.

🎯
Why "getRandom in O(1)" forces an array

This constraint is the most frequently missed clue in the genre. A hash map has no notion of "the i-th element", and iterating to find one is O(n); a tree can do it in O(log n) with subtree sizes, but not O(1). Only a contiguous array supports "pick index rand()%n" in constant time — so the moment you see getRandom, the array is decided, and the remaining work is making insert and delete fast on top of an array. That is the swap-with-last trick, plus a map from value to index so the victim can be found. The same reasoning drives Insert Delete GetRandom with duplicates (the map's value becomes a set of indices) and random pick with weight (prefix sums plus a binary search, which is O(log n) — and that is the best possible there).

Three structures worth recognising

🏗️
Skip list, Bloom filter, sqrt decomposition
  • Skip list — a sorted linked list with randomised express lanes: each node is promoted to the next level with probability ½, so searching descends through O(log n) levels in expectation. It gives balanced-BST performance with no rotations, which is why it is much easier to implement correctly and why Redis uses it for sorted sets. Expected O(log n) search, insert and delete; randomised, so the bound is expected rather than worst-case.
  • Bloom filter — a bit array plus k hash functions. Insert sets k bits; a query returns "possibly present" if all k are set. False positives are possible; false negatives are not, and there is no deletion (clearing a bit could unset another key's evidence). Use it as a cheap front door that avoids expensive lookups — a database or network fetch — when the answer is almost certainly "absent". The false-positive rate is tunable by the bit count and k.
  • Sqrt decomposition — split an array into √n blocks and keep an aggregate per block. A range query touches at most two partial blocks and √n whole ones, so it is O(√n) per query and O(1) per point update. It is beaten by a segment tree at O(log n), but it is far shorter to write and trivially adapted to odd aggregates a segment tree struggles with. Its famous relative, Mo's algorithm, sorts offline queries by block and answers them all in O((n+q)√n) by moving two pointers — the standard tool for "many range queries, no updates, an aggregate that is hard to merge" such as "count distinct values in a range".

Recognising these is usually the whole answer. Naming a Bloom filter for "is this URL probably in our seen-set, with a gigabyte of memory and a billion URLs" is the point; implementing one is a footnote.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 TABULATE FIRST
Write operation → required complexity → structure before declaring a single member. The hard operation reveals the design, and the table becomes your explanation.
💡 getRandom ⇒ ARRAY
O(1) uniform random forces a contiguous array. Deletion then becomes swap-with-last — and the line people forget is updating the moved element’s index.
⛔ UPDATE BOTH
Every bug in an LRU is one structure updated and the other not. State the invariant — the map holds a valid iterator into the list — and check it at every exit.
⚠️
Common mistakes
  • Updating one structure and not the other. On eviction, remove from both the list and the map.
  • Storing the key in the map when you need the node. O(1) splice requires the position, not the key.
  • A singly linked list for LRU. O(1) removal needs the predecessor.
  • Forgetting indexOf[last]=i in the swap-with-last delete — a stale index that only breaks later.
  • Erasing before overwriting when the victim is the last element.
  • Trying to support getRandom over a hash map or tree in O(1). It requires a contiguous array.
  • A single minimum variable in min-stack, which cannot restore the previous minimum after a pop.
  • Not tracking minFreq in LFU, making eviction O(n) — and missing that it only ever increments or resets to 1.
  • Expecting a Bloom filter to support deletion, or to be free of false positives.
  • Promising worst-case O(log n) for a skip list. It is expected — the level promotion is random.
  • Reaching for a segment tree when sqrt decomposition or Mo's is shorter, or vice versa when updates are involved (Mo's is offline and cannot handle them).

Interview drill

Warm-up: Design an LRU cache with O(1) get and put.

How a strong answer sounds
I would start by tabulating the operations: get by key in O(1), put by key in O(1), and evict the least recently used in O(1). Finding by key says hash map. Knowing the order of use says a list with the most recent at the front. And the hard operation is moving an existing item to the front in O(1) — that needs the node, not the key, which is why the map's value is a pointer or iterator into the list rather than the value itself. The list must be doubly linked, because unlinking a node in O(1) requires access to its predecessor and a singly linked list cannot provide that. So: a list of (key, value) pairs with most-recent at the front, and an unordered_map from key to an iterator into that list. get looks the key up, splices its node to the front, and returns the value; put either updates and splices, or inserts at the front and, if the capacity is exceeded, takes the key from the back, pops it, and erases it from the map. The invariant to state explicitly is that the map's value is always a valid iterator to that key's node, and the reason std::list::splice is the right primitive is that it relinks nodes without copying, so iterators stay valid. Nearly every bug in this class is that invariant breaking — most often eviction removing from the list but not the map, so the map grows unboundedly and later lookups return dangling iterators. If asked to avoid the STL I would hand-roll the list with dummy head and tail sentinels, so insert and remove need no null checks. Space is O(capacity), and I would note that the follow-up is usually LFU, which adds frequency buckets and a tracked minimum frequency.

Deeper: Design a set with insert, remove and getRandom, all O(1) and the random uniform.

How a strong answer sounds
The getRandom requirement is the one that determines the design, and I would say that first. Uniform random selection in O(1) means I must be able to pick an index and land on a valid element, which requires the elements to occupy a contiguous array — a hash map has no notion of "the i-th element" and iterating to find one is O(n), while a tree can do it in O(log n) with subtree sizes but not O(1). So an array is forced, and the question becomes how to make insert and remove O(1) on top of one. Insert is easy: append to the back, and record the value's index in a hash map. Remove is the interesting one, since deleting from the middle of an array is normally O(n) — but order does not matter in a set, so I can overwrite the hole with the last element and pop the back, which is O(1). Concretely: look up the victim's index i, copy the last element into slot i, update the map so that moved element's index becomes i, pop the back, and erase the victim from the map. The line people forget is updating the moved element's index; omitting it leaves a stale entry that produces a wrong answer only on some later delete, which is unpleasant to debug. There is also an ordering subtlety: if the victim is the last element, the overwrite must happen before the erase, or you erase the entry you just wrote — I would test that case explicitly, along with removing the only element. All operations are O(1) average, dominated by the hash map, and space is O(n). The follow-up is usually duplicates allowed, where the map's value becomes a set of indices and the same swap-with-last trick still works, just with a little more bookkeeping.

🧠 Key takeaways

  • Tabulate operation → required complexity → structure before writing members; the hard operation reveals the design.
  • Contradictory requirements mean two structures with cross-references — usually a map pointing into something ordered.
  • LRU is a map to list iterators; the invariant is that the iterator stays valid, which is why splice is used.
  • "getRandom in O(1)" forces a contiguous array; deletion then becomes swap-with-last.
  • Store history (a parallel stack of minima) when an operation must be undoable.
  • Recognise skip lists, Bloom filters, sqrt decomposition and Mo's algorithm — naming them is usually the answer.

Check your understanding

In an LRU cache, why does the hash map store an iterator (or node pointer) rather than the value?

And the list must be doubly linked, since unlinking a node in O(1) needs its predecessor. The invariant "the map's value is a valid iterator" is where all the bugs live.

Which requirement forces the elements to be held in a contiguous array?

Only an array supports "pick index rand()%n" in constant time. A map has no i-th element; a tree needs O(log n) with subtree sizes. Deletion then becomes swap-with-last.

The conditional variant saves space but then pop must compare — and getting that comparison wrong on equal values is the classic bug here.

That observation is the whole trick, and it is the thing to say aloud. Without it, finding the minimum frequency is a scan and eviction degrades to O(n).
