Input Size, Time Limits & How to Practise

This is the most useful habit in the whole course, and it takes ten seconds: before designing anything, look at the largest input size, estimate how many basic operations your idea needs, and compare that with what a judge can do in the time limit. The numbers alone rule out most wrong ideas before you write a line. This last prerequisite teaches that estimate, gives you a first feel for Big-O, and then sets out how to practise so the skills actually stick — ending with a checklist for the whole Prerequisites level.

  • Count the steps a piece of code takes, and keep only the part that grows fastest
  • Use the rule of thumb of about 10⁸ simple operations per second
  • Turn “n ≤ …” in a problem into the complexity you need
  • Spot hidden costs: copies, slow I/O, heavy containers, recursion depth
  • Follow a repeatable method for solving problems, and a practice routine that sticks

Counting steps, and what O(…) means

How long will a piece of code take? Timing it on your laptop tells you about one input. What you really want to know is how the time grows as the input grows, because the judge's hidden tests are far bigger than the examples. So we count basic steps — comparisons, additions, array reads — as a function of the input size n.

for(int i=0;i<n;i++)             // n steps
sum+=a[i];

for(int i=0;i<n;i++)             // n × n steps
for(int j=0;j<n;j++)
cnt+=a[i]==a[j];

for(int k=n;k>1;k/=2)            // about log2 n steps
steps++;

Together that's roughly n² + n + log n steps. Now two simplifications, which are the whole idea of Big-O notation:

  • Keep only the fastest-growing term. At n = 10⁵, n² is 10¹⁰ while n is 10⁵ — the n term is a rounding error. So n² + n + log n is written O(n²).
  • Drop constant factors. 3n² and n²/2 are both O(n²). Constants matter a little in practice, but a better growth rate always wins once n is big enough.

O(n²), read “order n squared”, means “grows at most like n², up to a constant factor”. The common classes, from fastest to slowest: O(1) constant, O(log n), O(n) linear, O(n log n), O(n²), O(n³), O(2ⁿ), O(n!). Chapter 2 makes all of this precise, including recursion and “amortised” costs. For now, being able to count loops is enough.

The operation budget

The rule of thumb every competitive programmer carries: a judge's computer does about 10⁸ simple operations per second. It's rough — somewhere between 10⁸ and 10⁹ depending on the operations — but it's the right order of magnitude, and that's all you need. With a 1-second limit, aim for at most a few times 10⁸ operations.

Combine that with the largest n allowed and you get this table — worth memorising:

Largest nFastest-growing cost that still fitsTypical idea
≤ 10O(n!)Try every ordering
≤ 20O(2ⁿ · n)Try every subset
≤ 500O(n³)Three nested loops
≤ 5,000O(n²)All pairs; 2D DP
≤ 10⁵ to 10⁶O(n log n)Sort, binary search, heap
≤ 10⁸O(n)One pass
up to 10¹⁸O(log n) or O(1)A formula or binary search on the answer

Read it in both directions. Forwards: “n ≤ 10⁵, so I need O(n log n) or better — O(n²) is out”. Backwards: “n ≤ 20? That's a hint. The setter is inviting an exponential solution.” Problem constraints are chosen deliberately, so they're one of the strongest clues you get.

A worked example

Find whether any two numbers in an array add up to a target, with n ≤ 10⁵.

  • Idea 1, check every pair: n(n − 1)/2 ≈ 5 × 10⁹ operations. At 10⁸ per second that is about 50 seconds. TLE.
  • Idea 2, sort then walk two pointers inward: n log₂ n ≈ 10⁵ × 17 ≈ 1.7 × 10⁶ for the sort, plus 10⁵ for the walk. A few milliseconds. Fits easily.
  • Idea 3, one pass with a hash set of values seen so far: about 10⁵ lookups, O(n). Also fits.

Notice that you did this before writing any code. The numbers ruled out idea 1 on their own. Chapter 1 has an interactive version of this habit, and Chapter 4 teaches idea 2.

Hidden costs that break the estimate

The estimate counts your algorithm's steps. A few things add steps you didn't write — and they're behind many “but my complexity was right!” TLEs:

📑

Accidental copies

Passing a vector or string by value, s=s+c, or substr inside a loop each add an O(n) copy per step, silently turning O(n) into O(n²) (P3, P4).

⌨️

Slow input/output

Reading 10⁶ numbers without the fast-I/O lines, or printing with endl, can take longer than the algorithm (P1).

🧺

Heavy containers

map is O(log n) per operation with a large constant; unordered_map is O(1) but slower than a plain array. If keys are small integers, an array or vector of counts is fastest.

🌀

Recursion and memory

Deep recursion risks a stack overflow; huge tables risk MLE; and memory that doesn't fit in the CPU cache is slower than the count suggests (P6).

And one reminder about space: the same budgeting applies to memory. With a 256 MB limit, about 6 × 10⁷ ints fit. An O(n²) table is fine at n = 5,000 (100 MB of ints) and impossible at n = 10⁵.

How to solve a problem: the method

Reading about algorithms feels productive, but the skill only grows by solving problems — in a fixed order, the same way every time. Here is the method; Chapter 1 expands each step.

Read the constraints first

The limits on n and on the values tell you how fast you must be, and whether you need long long.

Turn n into a budget

Use the table above. n = 10⁵ means you need O(n log n) or better.

Work a small example by hand

Solve n = 4 or 5 on paper. The pattern you use without thinking is often the algorithm.

Name the pattern

“Sorted, find a pair” is two pointers. “Shortest path, equal weights” is BFS. Chapter 52 collects them all.

Say what stays true in one sentence

The invariant: a rule that holds every time round the loop. If you cannot say it, you are not ready to code.

Code it, then dry-run it

Guard clause first, then variables, then the loop. Then trace a small tricky input by hand before you submit (Chapter 53).

How to practise so it sticks

Most people who “do 300 problems” and still freeze in interviews made the same mistakes: they solved random problems, gave up or peeked too early, and never revisited anything. A routine that works better:

  • Practise by topic first, then mix. Follow the chapters: solve a handful of problems right after each one, while the pattern is fresh. Later, mix topics so you practise recognising which pattern applies — which is the real skill.
  • Struggle productively, then learn. Give a problem 20–40 minutes of honest effort. If stuck, read only a hint, try again, and only then read the full solution. After reading it, close it and write the solution yourself from memory.
  • Keep a mistakes log. One line per miss: the problem, the idea you missed, the bug you made. Patterns in your own mistakes are the fastest thing to fix.
  • Revisit on a schedule. Re-solve a problem you struggled with after a few days and again after a few weeks. If you can do it cold, you own it.
🔁
Spaced repetition: review just before you forget

Memory fades on a curve: fast at first, then slower. Each time you recall something just as it is fading, it lasts longer before the next fade. So review after one day, then three, then a week, then a month. That beats rereading the same chapter five times in one evening, and it takes far less time.

The course does the scheduling for you. Every quiz question becomes a card in the flashcard deck, which shows you each card again when it is due. Five minutes a day is enough. Once a week, try a timed problem in the mock-interview room, and look up any unfamiliar word in the glossary.

Common mistakes
  • Coding before estimating. Ten seconds with the constraints saves an hour on a solution that can never pass.
  • Thinking TLE means “optimise a bit”. It almost always means the wrong complexity class.
  • Forgetting the constant inside the count. “All pairs” is still O(n²) even though it's n²/2.
  • Ignoring hidden copies and slow I/O. They can add a whole factor of n.
  • Reading solutions too early — or never. Struggle 20–40 minutes, then learn, then re-solve from memory.
  • Never revisiting. A problem you solved once and forgot doesn't count. Review on a schedule.

Interview drill

Out loud: The problem says n ≤ 2 × 10⁵ and values up to 10⁹. What do you conclude before designing anything?

How a strong answer sounds
At about 10⁸ simple operations per second, O(n²) would be around 4 × 10¹⁰ — hundreds of seconds — so I need O(n log n) or O(n): sorting, binary search, a heap, two pointers, a hash map or prefix sums. Values up to 10⁹ mean sums or products can overflow an int, so any accumulator is long long. And with 2 × 10⁵ numbers of input, I use fast I/O. Then I'd look for which pattern fits.

Estimate: An O(n log n) solution with n = 10⁶ — will it pass in 1 second?

How a strong answer sounds
n log₂ n ≈ 10⁶ × 20 = 2 × 10⁷ operations, a fifth of the ~10⁸ budget, so yes, comfortably — provided the constant is reasonable. If the log comes from a map or set, the constant is higher and it gets closer; sorting a vector would be very safe.

🧠 Key takeaways

  • Count steps as a function of n, keep the fastest-growing term, drop constants: that's Big-O.
  • A judge does about 10⁸ simple operations per second. Divide the budget by your estimated operation count before coding.
  • n ≤ 10: n!; ≤ 20: 2ⁿ; ≤ 500: n³; ≤ 5,000: n²; ≤ 10⁶: n log n; ≤ 10⁸: n; bigger: log n or O(1).
  • Hidden costs — copies, slow I/O, heavy containers, recursion — can break a correct estimate.
  • Method: constraints → budget → small example → pattern → invariant → code → dry run.
  • Practise by topic then mixed, struggle before reading solutions, keep a mistakes log, and review on a spaced schedule.

Check your understanding

A problem allows n up to 10⁵. Which complexity is the slowest that will reliably pass in 1 second?

n log n ≈ 1.7 × 10⁶ operations — easy. n² = 10¹⁰, about 100 seconds at 10⁸ per second. n³ and 2ⁿ are hopeless.

What is the Big-O of code that runs 3n² + 5n + 100 steps?

Keep only the fastest-growing term and drop its constant: 3n² becomes n². The 5n and 100 are negligible for large n.

A problem says n ≤ 18. What does that suggest?

Constraints around 20 are a classic hint for trying every subset (often bitmask DP). 18! ≈ 6.4 × 10¹⁵, though, is still far too many orderings.

Your algorithm is O(n) with n = 10⁶, but it gets TLE. Which is the most likely hidden cause?

10⁶ steps is tiny. When a genuinely O(n) algorithm TLEs, look for hidden O(n) work per step (copies, s=s+c, substr) or unoptimised input/output.

You've been stuck on a problem for 35 minutes. According to the practice method, what's the best next move?

Productive struggle builds the skill, but only up to a point. Learning from the solution and then re-deriving it — and revisiting later — is what turns one problem into a pattern you own.
