Two Pointers

“Two pointers” means walking through data with two index variables at once instead of one. It is the cheapest way to turn an O(n²) nested loop into O(n), and it comes in exactly three shapes. The technique itself is easy. The skill is spotting which shape a problem needs — and being able to explain why the pointers move only about n steps in total. That one sentence proves both that the answer is correct and that it is fast.

  • Recognise the three shapes: converging, same-direction, and different-speed
  • State the invariant (the rule that stays true) that lets you never move a pointer backwards
  • Prove Floyd's cycle detection works — both that the pointers meet, and where the cycle starts
  • Handle duplicates correctly in the k-sum family of problems
  • Know the condition that must hold for two pointers to work, and when it fails

The three shapes

Every two-pointer solution is one of these. Learn to name the shape before you write a line.

Why care? Many problems ask about pairs: two numbers that sum to something, two walls that hold water, two ends that must match. The obvious approach checks every pair, and an array of n items has n(n−1)/2 pairs. At n = 10⁵ that is about 5 × 10⁹ checks — far over the budget. Two pointers visits each index only a few times, so it does about 10⁵ steps instead. The trick is always the same: use some property of the data (usually that it is sorted) to rule out many pairs at once, without checking them.

↔️

Converging

Start at both ends and move inward. Needs a sorted array, or a property that is the same from both ends. Each step rules out one element for good. Total movement: n.

Two-sum sorted, valid palindrome, container with most water, reverse in place.

➡️

Same direction

Both start on the left and only move right, each at a pace set by a condition. The read pointer scans; the write (or left) pointer follows behind. Total movement: 2n.

Remove duplicates, move zeroes, merge two sorted arrays, and every sliding window (Chapter 5).

🐢

Different speeds

One moves 1 step at a time, the other 2. The gap between them grows by 1 each round. That lets you detect loops and find the middle without knowing the length.

Linked-list cycle, middle node, nth from end, happy number, duplicate number.

This chapter spends most of its time on shapes 1 and 3. Shape 2 is the read/write pointer you met in Chapter 3, and its most important form, the sliding window, gets all of Chapter 5. One quick example of shape 2 so you have seen it: merging two sorted arrays. Put pointer i on [1, 4, 7] and pointer j on [2, 3, 9]. At each step, take the smaller of the two values under the pointers and move only that pointer forward: take 1 (i moves), 2 (j moves), 3 (j), 4 (i), 7 (i). Now the first array is used up, so copy what is left of the second: 9. Result [1, 2, 3, 4, 7, 9]. Both pointers only move right, and together they take 6 steps for 6 elements — O(n + m).

Shape 1: converging — and why it is correct

Take two-sum on a sorted array: find two numbers that add up to a target. The simple version checks every pair, which is O(n²). Two pointers does it in O(n). The reason is worth understanding exactly, because the same argument works for a dozen other problems.

twoSum — sorted inputO(n)O(1)
// Invariant: every pair with one index outside [left,right] has already been
// ruled out. So if the answer exists at all, it lies inside the window.
vector<int> twoSum(vector<int> &a,int target){
	int left=0;
	int right=a.size()-1;

	while(left<right){
		int sum=a[left]+a[right];

		if(sum==target)return {left,right};

		if(sum<target)left++;      // need bigger: only left can grow the sum
		else right--;              // need smaller: only right can shrink it
	}

	return {};
}
Why you can throw away a whole row of pairs: suppose a[left]+a[right] < target. The array is sorted, so a[right] is the largest value left. If even that is not enough, then a[left] paired with anything at or below right is also too small. So left can never be part of the answer. Moving it forward throws away up to n pairs in one step. That is where the factor of n disappears.

A dry run on [1, 3, 4, 6, 9] with target 13:

  1. left=0, right=4: 1 + 9 = 10, too small. Even the biggest partner (9) is not enough for 1, so 1 is out. left → 1.
  2. left=1, right=4: 3 + 9 = 12, still too small. Same reasoning: 3 is out. left → 2.
  3. left=2, right=4: 4 + 9 = 13. Found: return {2, 4}.

Three steps, while checking all pairs would have looked at up to 10. The mirror case works the same way: if the sum is too big, a[right] is too big even with the smallest value still available, so right is out. Edge cases the code already handles: if no pair exists, the pointers meet and the loop ends, returning {}. If the array has 0 or 1 elements, left<right is false from the start. And because the loop uses < and not <=, it never pairs an element with itself.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SORTED ⇒ POINTERS
The moment the input is sorted and you want a pair, two pointers from the ends is almost always the answer: too small means move left up, too big means move right down.
⛔ DUPLICATE SKIP
In 3-sum the skip goes in two places — the outer loop and after a found triplet. Forget either and you emit duplicates; the failing test is always an array of equal values.
💡 FAST/SLOW
Two pointers at different speeds finds the middle, detects a cycle, and locates the cycle entry. Same three lines, three problems.
🚨
The precondition, and what happens without it

Converging two pointers needs monotonicity — things only ever move in one direction. Moving left right must only increase the sum, and moving right left must only decrease it. On an unsorted array that is not true. The algorithm then quietly returns a wrong answer instead of crashing. If the problem does not give you a sorted array, you have two options. Sort first, which costs O(n log n) and loses the original indices. Or use a hash map instead (Chapter 9). Choosing between those two is often the real interview question in disguise.

Extending to three: the k-sum ladder

3-sum is just two-sum inside an outer loop: fix one number, then run two-sum on the rest. The same idea keeps going: k-sum is (k−1)-sum with an outer loop, which gives O(n^(k−1)). The only truly fiddly part is duplicates, and there is a standard way to handle them.

Where does O(n^(k−1)) come from? For 3-sum, the outer loop picks each of n values as the fixed first number, and for each one the two-pointer scan takes O(n). That is n × n = O(n²). Each extra number adds one more outer loop, and so one more factor of n. The sort at the start costs O(n log n), which is smaller than n², so it does not change the total.

threeSum — all unique triplets summing to zeroO(n²)O(1) auxiliary
vector<vector<int>> threeSum(vector<int> &a){
	sort(a.begin(),a.end());      // O(n log n), dominated by the O(n^2) below

	vector<vector<int>> ans;
	int n=a.size();

	for(int i=0;i<n-2;i++){
		if(i>0 and a[i]==a[i-1])continue;   // skip duplicate first elements
		if(a[i]>0)break;                        // sorted: no way back to zero

		int left=i+1;
		int right=n-1;

		while(left<right){
			int sum=a[i]+a[left]+a[right];

			if(sum<0)left++;
			else if(sum>0)right--;
			else{
				ans.push_back({a[i],a[left],a[right]});

				// skip duplicates on BOTH sides, then step both in
				while(left<right and a[left]==a[left+1])left++;
				while(left<right and a[right]==a[right-1])right--;

				left++;
				right--;
			}
		}
	}

	return ans;
}
Three duplicate skips, and you need all three. The continue stops the same triplet being found again from a repeated a[i]. The two inner while loops stop it being found again from a repeated a[left] or a[right]. Getting this right is what makes 3-sum a Medium and not an Easy.

A dry run on [-1, 0, 1, 2, -1, -4]. After sorting it is [-4, -1, -1, 0, 1, 2] (indices 0–5).

  • i=0, a[i]=−4. The other two must sum to 4. The scan tries −1+2, −1+2, 0+2, 1+2 — all too small, so left keeps moving until it meets right. Nothing found.
  • i=1, a[i]=−1. left=2 (−1), right=5 (2): −1 −1 + 2 = 0. Record [-1, -1, 2]. No neighbours to skip, so step both in: left=3 (0), right=4 (1): −1 + 0 + 1 = 0. Record [-1, 0, 1]. Step both in; they cross, so stop.
  • i=2, a[i]=−1. Same value as a[1], so the continue skips it. Without that skip you would find [-1, 0, 1] a second time.
  • i=3, a[i]=0. left=4 (1), right=5 (2): sum 3, too big, right--; they meet. Nothing. The loop ends at i < n−2.

Answer: [[-1, -1, 2], [-1, 0, 1]]. The break on a[i]>0 is a small speed-up: once the smallest of the three numbers is positive, all three are positive and cannot sum to zero.

✍️
My convention: and / or instead of && / ||

These words are standard C++, not an extension. In a long boundary condition like left<right and a[left]==a[left+1], they read more easily than symbols. That matters, because conditions like this are exactly where bugs hide. Use whichever you prefer, but be consistent — mixing both in one file is the worst option.

Shape 3: different speeds, and the proof everyone skips

This is Floyd's “tortoise and hare”. A slow pointer moves 1 step at a time; a fast pointer moves 2. Picture two runners on a track that ends in a loop: if there is a loop, the faster runner eventually laps the slower one. Two claims about this are usually stated and rarely proved, so let us prove both.

Why not just remember every node you have visited in a hash set, and stop when you see one again? That works, and it is O(n) time — but it needs O(n) extra memory. Floyd's method gets the same answer with two pointer variables, O(1) space. That difference is exactly what interviewers ask about.

First, a small example to follow along with. The list has a tail of μ = 2 nodes (A, B) and then a cycle of λ = 4 nodes: C → D → E → F → back to C. Both pointers start at A.

Claim 1 — if there is a cycle, they must meet

Wait until both pointers are inside the cycle. Now measure the gap from fast to slow, counting forward around the loop. Each step, fast gains one position on slow, so the gap shrinks by exactly 1. The gap is always one of {0, 1, …, λ−1} (λ is the cycle length). A number that drops by 1 each step in that range must hit 0 — and a gap of 0 means both are on the same node. They cannot “jump past” each other, because the gap changes by 1, never by 2. So they are guaranteed to meet within λ steps of both entering the loop.

🧾
Claim 2 — restarting one pointer at the head finds the entry

Let μ be the tail length (from the head to the start of the cycle) and λ the cycle length. When they meet, slow has taken k steps and fast has taken 2k. They are on the same node in the cycle, so fast must have gone around some whole number of extra loops:

2k − k = k ≡ 0 (mod λ), so k is a multiple of λ.

Now move one pointer back to the head, leave the other at the meeting point, and step both by 1. After μ steps, the first pointer is at the cycle entry. The second has now travelled k + μ steps from the head in total. Since k is a whole number of loops, those extra k steps bring it back round to the same place — so k + μ lands on the same node as μ. They meet exactly at the entry. That is why the second phase needs no counting and no extra memory.

detectCycle — return the entry nodeO(n)O(1)
ListNode* detectCycle(ListNode* head){
	if(!head or !head->next)return nullptr;

	ListNode* slow=head;
	ListNode* fast=head;

	// Phase 1: find a meeting point inside the cycle (if one exists)
	while(fast and fast->next){
		slow=slow->next;
		fast=fast->next->next;

		if(slow==fast)break;
	}

	if(!fast or !fast->next)return nullptr;   // ran off the end: no cycle

	// Phase 2: one pointer back to head, both step by 1, they meet at the entry
	slow=head;
	while(slow!=fast){
		slow=slow->next;
		fast=fast->next;
	}

	return slow;
}
The loop condition is what keeps this from crashing. while(fast and fast->next) checks both, because fast=fast->next->next follows two pointers in a row. Checking only fast crashes on an even-length list with no cycle; checking only fast->next crashes on an odd-length one.
🎯
The same trick, four other problems
  • Middle of a list in one pass: when fast reaches the end, slow is at the middle. No need to count the length.
  • Nth node from the end: move fast n steps ahead first, then move both until fast reaches the end. The gap between them stays n. For example, in 1 → 2 → 3 → 4 → 5 with n = 2: slow starts on node 1 and fast moves 2 ahead to node 3. Move both until fast is past the end (null): slow lands on node 4, the 2nd from the end. If you instead stop when fast is on the last node, slow stops one earlier, on node 3 — which is what you want when you need to delete the node after it. Which stopping rule you use is the off-by-one to check on paper.
  • Happy number: each number leads to exactly one next number (the sum of its digits squared). That makes a hidden “next” chain, so Floyd can detect its cycle with no list at all.
  • Find the duplicate in [1..n] with n+1 elements: treat a[i] as a “next” pointer. The duplicate is the cycle entry — O(n) time, O(1) space, and the array is not modified.

Deciding which shape, fast

Is the array sorted, or would sorting be free?

→ Converging. Pair sums, triplets, closest sum, container with most water.

left=0, right=n-1, while(left<right)
Am I filtering, compacting or merging in place?

→ Same direction. One read pointer, one write pointer. See Chapter 3.

for(read..) if(keep) a[write++]=a[read];
Is it a contiguous subarray with a condition?

→ Sliding window, which is the same-direction shape with a shrink rule. Chapter 5.

for(r..) { add(r); while(bad) remove(l++); }
Is it a linked list, or a sequence defined by "next = f(current)"?

→ Different speeds. Cycles, midpoints, nth-from-end.

slow=slow->next; fast=fast->next->next;
Is it unsorted and I need exact values, not order?

→ Not two pointers. Use a hash map. Chapter 9.

unordered_map<int,int> seen;
⚠️
Common mistakes
  • Using converging pointers on unsorted data. It quietly gives a wrong answer. The sorted (monotonic) requirement is not optional.
  • Writing while(left<=right) when you need two different indices. With <=, two-sum will happily pair an element with itself.
  • Only checking fast in the fast/slow loop. fast->next->next follows two pointers, so you must check fast and fast->next.
  • Skipping duplicates on only one side in 3-sum. You need the outer continue and both inner skips, or you output repeats.
  • Sorting when the problem wants the original indices. A two-sum that must return indices cannot sort — that is the hash-map version. Mixing up the two is the most common late-night bug.
  • Moving both pointers when it is unclear which to move. In container-with-most-water, move only the shorter wall. Moving both can skip right over the best answer.
🎤
Interview drill

Warm-up: In container-with-most-water, why do you move the pointer at the shorter wall?

How a strong answer sounds
The area is width × min(height[left], height[right]), so the shorter wall caps it. If I move the taller wall inward, the width gets smaller and the minimum cannot go up — it is still limited by the shorter wall I left in place. So every area I could get that way is worse. That means no pair using the shorter wall with any inner index can beat what I already have, and I can drop the shorter wall entirely. Moving the shorter one is the only move that could raise the minimum. If the two walls are equal, either move works: neither wall can do better with any inner partner. This argument is also the proof that the method is correct. Each step safely rules out a whole group of candidates — which is what makes the O(n) answer right, not just fast.

Deeper: Prove that Floyd's second phase lands exactly on the cycle entry.

How a strong answer sounds
Let μ be the number of nodes before the cycle entry and λ the cycle length. Say they meet after slow has taken k steps, so fast has taken 2k. They are on the same node, so their step counts differ by a whole number of loops: 2k − k = k must be a multiple of λ. Now reset one pointer to the head and step both one at a time. After exactly μ steps, the reset pointer is at the entry. The other pointer has now travelled k + μ steps from the head. Since k is a multiple of λ, walking k extra steps inside the cycle brings you back to where you started. So position k + μ is the same node as position μ — the entry. They meet there, after at most μ more steps. The neat part: you never need to know μ or λ, which is why the whole thing uses O(1) space.

🧠 Key takeaways

  • Only three shapes: converging (needs sorted data), same direction (filter, merge, window), different speeds (cycles, midpoints).
  • Converging pointers work because each step rules out a whole row of candidate pairs — that is where the factor of n goes.
  • Two pointers is O(n) because neither pointer ever moves backwards. If you need to back up, it is the wrong technique.
  • k-sum is (k−1)-sum plus an outer loop, and in 3-sum you need the duplicate skip on all three positions.
  • Floyd's second phase works because the meeting distance k is a multiple of the cycle length λ.

Check your understanding

Converging two pointers on a sorted array is O(n) rather than O(n²) because…

Together, the pointers cover the array once and never go back. That one-way movement is the whole complexity argument. It is also why “I need to move a pointer back” means two pointers is the wrong technique.

In Floyd's cycle detection, why must while(fast and fast->next) check both?

Following two pointers needs two null checks. Checking only fast crashes on an even-length list with no cycle; checking only fast->next crashes on an odd-length one. Check both, every time.

In container-with-most-water, you have walls of height 8 at left and 3 at right. Which pointer do you move?

Area is width × min(heights). Moving the taller wall shrinks the width, while the minimum stays capped by the shorter wall — so every such pair is worse. Only moving the shorter wall can raise the minimum.

A problem gives an unsorted array and asks for the indices of two numbers summing to a target. Why is sorting plus two pointers wrong?

You can still find the values, but their original positions are gone. You would have to store (index, value) pairs and sort those. At that point a one-pass hash map (Chapter 9) is simpler, and O(n). Spotting this difference is the real test.

In 3-sum, how many separate duplicate-skipping conditions do you need?

All three. A repeated value in any of the three positions can produce the same triplet again. (A set does work, but it costs hashing a whole vector on every insert, and it hides the reasoning the interviewer wants to see.)
