Two Pointers

Two pointers is the cheapest way to turn an O(n²) nested loop into O(n), and it comes in exactly three shapes. The technique is easy; the skill is recognising which shape a problem wants, and being able to say why total movement is linear — because that sentence is both the proof of correctness and the proof of complexity.

  • Recognise the three shapes: converging, same-direction, and different-speed
  • State the invariant that justifies never moving a pointer backwards
  • Prove Floyd's cycle detection — both that they meet, and where the entry is
  • Handle duplicates correctly in the k-sum family
  • Know the precondition that makes two pointers valid, and when it fails

The three shapes

Every two-pointer solution is one of these. Learn to name the shape before you write a line.

↔️

Converging

Start at both ends, move inward. Needs a sorted array or a symmetric property. Each step eliminates one candidate permanently. Total movement: n.

Two-sum sorted, valid palindrome, container with most water, reverse in place.

➡️

Same direction

Both start left and only move right, at rates set by a condition. The read pointer scans; the write or left pointer follows. Total movement: 2n.

Remove duplicates, move zeroes, merge two sorted arrays, and every sliding window (Chapter 5).

🐢

Different speeds

One advances 1 step, the other 2. The gap grows by 1 per iteration, which detects cycles and finds midpoints without knowing the length.

Linked-list cycle, middle node, nth from end, happy number, duplicate number.

Shape 1: converging — and why it is correct

Two-sum on a sorted array. The naive version checks all pairs in O(n²). Two pointers does it in O(n), and the reason is worth stating precisely because the same argument justifies a dozen other problems.

twoSum — sorted inputO(n)O(1)
// Invariant: every pair with one index outside [left,right] has already been
// ruled out. So if the answer exists at all, it lies inside the window.
vector<int> twoSum(vector<int> &a,int target){
	int left=0;
	int right=a.size()-1;

	while(left<right){
		int sum=a[left]+a[right];

		if(sum==target)return {left,right};

		if(sum<target)left++;      // need bigger: only left can grow the sum
		else right--;              // need smaller: only right can shrink it
	}

	return {};
}
Why you can discard a whole row: if a[left]+a[right] < target, then a[left] paired with anything at or below right is also too small — because the array is sorted and a[right] is the largest remaining. So left can never be part of an answer, and moving it forward discards n candidates in one step. That is where the factor of n goes.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SORTED ⇒ POINTERS
The moment the input is sorted and you want a pair, two pointers from the ends is almost always the answer: too small means move left up, too big means move right down.
⛔ DUPLICATE SKIP
In 3-sum the skip goes in two places — the outer loop and after a found triplet. Forget either and you emit duplicates; the failing test is always an array of equal values.
💡 FAST/SLOW
Two pointers at different speeds finds the middle, detects a cycle, and locates the cycle entry. Same three lines, three problems.
🚨
The precondition, and what happens without it

Converging two pointers needs monotonicity: moving left right must only increase the quantity, and moving right left must only decrease it. On an unsorted array that fails, and the algorithm silently returns a wrong answer rather than crashing. If the problem does not hand you a sorted array, you must either sort first — which costs O(n log n) and destroys the original indices — or use a hash map instead (Chapter 9). Deciding between those two is the actual interview question in disguise.

Extending to three: the k-sum ladder

3-sum is two-sum with an outer loop. That structure generalises: k-sum is (k−1)-sum with an outer loop, giving O(n^(k−1)). The only genuinely fiddly part is duplicates, and there is a standard way to handle them.

threeSum — all unique triplets summing to zeroO(n²)O(1) auxiliary
vector<vector<int>> threeSum(vector<int> &a){
	sort(a.begin(),a.end());      // O(n log n), dominated by the O(n^2) below

	vector<vector<int>> ans;
	int n=a.size();

	for(int i=0;i<n-2;i++){
		if(i>0 and a[i]==a[i-1])continue;   // skip duplicate first elements
		if(a[i]>0)break;                        // sorted: no way back to zero

		int left=i+1;
		int right=n-1;

		while(left<right){
			int sum=a[i]+a[left]+a[right];

			if(sum<0)left++;
			else if(sum>0)right--;
			else{
				ans.push_back({a[i],a[left],a[right]});

				// skip duplicates on BOTH sides, then step both in
				while(left<right and a[left]==a[left+1])left++;
				while(left<right and a[right]==a[right-1])right--;

				left++;
				right--;
			}
		}
	}

	return ans;
}
Three duplicate skips, and all three are needed. The continue stops the same triplet being found from a repeated a[i]. The two inner while loops stop it being found again from a repeated a[left] or a[right]. Getting this right is why 3-sum is a Medium and not an Easy.
✍️
My convention: and / or instead of && / ||

C++ has these as standard keyword alternatives, and in a long boundary condition like left<right and a[left]==a[left+1] they read better than punctuation — which matters because these conditions are exactly where bugs live. Use whichever you prefer, but be consistent: mixing the two in one file is the worst option.

Shape 3: different speeds, and the proof everyone skips

Floyd's tortoise and hare. A slow pointer moves 1, a fast pointer moves 2. Two claims are usually asserted and rarely proved, so let us prove both.

Claim 1 — if there is a cycle, they must meet

Once both pointers are inside the cycle, consider the gap from fast to slow measured forward around the loop. Each iteration fast gains one position on slow, so the gap shrinks by exactly 1 every step. A quantity that decreases by 1 each step and lives in {0, 1, …, λ−1} must reach 0, and gap 0 means they occupy the same node. They cannot "jump past" each other precisely because the gap changes by 1, never 2. So a meeting is guaranteed within λ steps of both being in the loop.

🧾
Claim 2 — restarting one pointer at the head finds the entry

Let μ be the tail length (head to cycle entry) and λ the cycle length. When they meet, slow has taken k steps and fast 2k. Both are in the cycle, and fast has gone exactly some whole number of extra loops:

2k − k = k ≡ 0 (mod λ), so k is a multiple of λ.

Now put one pointer at the head and leave the other at the meeting point, and step both by 1. After μ steps the first is at the entry. The second has travelled k + μ from the head in total — and since k is a whole number of loops, k + μ lands on the same node as μ does. They meet exactly at the entry. That is why the second phase needs no counting and no extra memory.

detectCycle — return the entry nodeO(n)O(1)
ListNode* detectCycle(ListNode* head){
	if(!head or !head->next)return nullptr;

	ListNode* slow=head;
	ListNode* fast=head;

	// Phase 1: find a meeting point inside the cycle (if one exists)
	while(fast and fast->next){
		slow=slow->next;
		fast=fast->next->next;

		if(slow==fast)break;
	}

	if(!fast or !fast->next)return nullptr;   // ran off the end: no cycle

	// Phase 2: one pointer back to head, both step by 1, they meet at the entry
	slow=head;
	while(slow!=fast){
		slow=slow->next;
		fast=fast->next;
	}

	return slow;
}
The loop condition is the whole safety story. while(fast and fast->next) checks both, because fast=fast->next->next dereferences twice. Checking only fast crashes on an even-length acyclic list; checking only fast->next crashes on an odd one.
🎯
The same trick, four other problems
  • Middle of a list in one pass: when fast hits the end, slow is at the middle. No length count needed.
  • Nth node from the end: advance fast by n first, then move both until fast ends. The gap is preserved.
  • Happy number: the digit-square-sum map is a functional graph, so Floyd detects its cycle with no list at all.
  • Find the duplicate in [1..n] with n+1 elements: treat a[i] as a next pointer. The duplicate is the cycle entry — O(n) time, O(1) space, and the array is not modified.

Deciding which shape, fast

Is the array sorted, or would sorting be free?

→ Converging. Pair sums, triplets, closest sum, container with most water.

left=0, right=n-1, while(left<right)
Am I filtering, compacting or merging in place?

→ Same direction. One read pointer, one write pointer. See Chapter 3.

for(read..) if(keep) a[write++]=a[read];
Is it a contiguous subarray with a condition?

→ Sliding window, which is the same-direction shape with a shrink rule. Chapter 5.

for(r..) { add(r); while(bad) remove(l++); }
Is it a linked list, or a sequence defined by "next = f(current)"?

→ Different speeds. Cycles, midpoints, nth-from-end.

slow=slow->next; fast=fast->next->next;
Is it unsorted and I need exact values, not order?

→ Not two pointers. Use a hash map. Chapter 9.

unordered_map<int,int> seen;
⚠️
Common mistakes
  • Using converging pointers on unsorted data. It produces a wrong answer silently. The monotonicity precondition is not optional.
  • Writing while(left<=right) when you need two distinct indices. With <=, two-sum will happily pair an element with itself.
  • Only checking fast in the fast/slow loop. fast->next->next dereferences twice, so you must check fast and fast->next.
  • Skipping duplicates on only one side in 3-sum. You need the outer continue and both inner skips, or you emit repeats.
  • Sorting when the problem wants original indices. Two-sum that must return indices cannot sort — that is the hash-map version, and confusing the two is the most common 3 a.m. bug.
  • Moving both pointers when the condition is ambiguous. In container-with-most-water, move only the shorter wall. Moving both can step over the optimum.
🎤
Interview drill

Warm-up: In container-with-most-water, why do you move the pointer at the shorter wall?

How a strong answer sounds
The area is width × min(height[left], height[right]), so it is capped by the shorter wall. If I move the taller wall inward, the width strictly decreases and the minimum cannot increase — it is still limited by the shorter wall I left in place — so every resulting area is worse. That means no pair involving the taller wall and any inner index can beat what I already have, and I can discard the shorter wall entirely. Moving the shorter one is the only move that can possibly improve the minimum. If the two walls are equal, either move works, because both of them are simultaneously maxed out and no inner pair can use either. That argument is also the correctness proof: each step safely eliminates a whole set of candidates, which is what makes O(n) sound rather than just fast.

Deeper: Prove that Floyd's second phase lands exactly on the cycle entry.

How a strong answer sounds
Let μ be the number of nodes before the cycle entry and λ the cycle length. Suppose they meet after slow has taken k steps; fast has taken 2k. Both are at the same node, so their positions differ by a whole number of loops: 2k − k = k must be a multiple of λ. Now reset one pointer to the head and step both one at a time. After exactly μ steps the reset pointer is at the entry. The other pointer has now travelled k + μ steps from the head; since k is a multiple of λ, walking k extra steps inside the cycle returns to where you started, so position k + μ is the same node as position μ — the entry. Hence they meet there, and it takes at most μ additional steps. The neat part is that this needs no knowledge of μ or λ, which is why the whole thing is O(1) space.

🧠 Key takeaways

  • Three shapes only: converging (needs sorted/monotone), same direction (filter, merge, window), different speeds (cycles, midpoints).
  • Converging pointers work because each step eliminates a whole row of candidates — that is where the factor of n goes.
  • Two pointers is O(n) precisely because neither pointer ever moves backwards; if you need to back up, it is the wrong technique.
  • k-sum is (k−1)-sum plus an outer loop, and the duplicate skips are needed on all three sides.
  • Floyd's second phase works because the meeting distance k is a multiple of the cycle length λ.

Check your understanding

Converging two pointers on a sorted array is O(n) rather than O(n²) because…

The pointers together cover the array once and never revisit. That monotone movement is the complexity argument — and it is also why “I need to move a pointer back” means two pointers is the wrong technique.

In Floyd's cycle detection, why must while(fast and fast->next) check both?

Two dereferences need two null checks. Checking only fast segfaults on an even-length acyclic list; checking only fast->next segfaults on an odd one. Both, every time.

In container-with-most-water, you have walls of height 8 at left and 3 at right. Which pointer do you move?

Area is width × min(heights). Moving the taller wall reduces width while the minimum stays capped by the shorter wall, so every such pair is worse. Only moving the shorter wall can improve the minimum.

A problem gives an unsorted array and asks for the indices of two numbers summing to a target. Why is sorting plus two pointers wrong?

The values are findable but the positions are gone. You would need to store index-value pairs and sort those — at which point a single-pass hash map (Chapter 9) is simpler and O(n). Recognising this distinction is the real test.

In 3-sum, how many separate duplicate-skipping conditions do you need?

All three. Each repeated value on any of the three positions can regenerate the same triplet. (A set does work, but it costs a hash of a vector per insert and hides the reasoning the interviewer is checking.)
