Linked Lists

Linked lists are rare in production code and common in interviews, and both facts have the same cause: they are the purest test of whether you can manipulate pointers without losing track of anything. There is no index to fall back on, so every operation is an exercise in ordering your assignments correctly. This chapter gives you the two habits that make that reliable — draw before you write, and use a dummy head.

  • Compare linked lists with arrays honestly, including the cache cost
  • Reverse a list iteratively with the three-pointer dance, and recursively
  • Use a dummy head to delete every special case at the head
  • Apply fast/slow pointers for midpoint, nth-from-end and cycle problems
  • Merge, partition and reorder lists without leaking or losing nodes

The node, and the honest comparison

the node typesO(1) per node + pointer overhead
struct ListNode{
	int val;
	ListNode* next;

	ListNode(int val){
	this->val=val;
	next=nullptr;
}
};

struct DListNode{
	int val;
	DListNode* prev;
	DListNode* next;

	DListNode(int val){
	this->val=val;
	prev=nullptr;
	next=nullptr;
}
};
Always initialise the pointers in the constructor. An uninitialised next holds garbage, and the first time you follow it the program dies somewhere unrelated to the actual bug. This is the same struct shape used for TreeNode in Chapter 16.

⚖️
So when is a linked list actually right?

When you already hold a pointer to the node and need O(1) removal — an LRU cache, an intrusive free list, a scheduler's run queue. Or when you need stable addresses across insertions, since a vector reallocation invalidates everything (Chapter 3). Outside those cases a vector or deque is faster, smaller and simpler. Say this in an interview: “I would use a vector here, but let us do the list version since that is the question” lands much better than pretending the list is a good choice.

Reversal: the three-pointer dance

The one you must be able to write without thinking. Three pointers, and the order of the four assignments inside the loop is the entire problem.

Reverse a list, one assignment at a timeVisualizer
Watch the order: save next first. Every other ordering loses the rest of the list.
reverseList — iterativeO(n)O(1)
// Invariant: prev heads the already-reversed part; cur heads the untouched part.
ListNode* reverseList(ListNode* head){
	ListNode* prev=nullptr;
	ListNode* cur=head;

	while(cur){
		ListNode* nxt=cur->next;   // 1. SAVE first, or the rest is lost

		cur->next=prev;              // 2. flip this node's pointer

		prev=cur;                    // 3. advance prev
		cur=nxt;                     // 4. advance cur
	}

	return prev;                     // cur is null; prev is the new head
}
Why step 1 must come first: step 2 overwrites cur->next, which was the only reference to the remainder of the list. Overwrite it before saving and everything after cur becomes unreachable — the program does not crash, it just returns a one-element list. And return prev, not cur: the loop exits when cur is null.
Recursive reversal
// Leap of faith (Ch 11): trust that the rest is reversed.
ListNode* reverseList(ListNode* head){
	if(!head or !head->next)return head;

	ListNode* newHead=reverseList(head->next);

	head->next->next=head;   // the next node points back at me
	head->next=nullptr;      // and I become the tail

	return newHead;
}

Shorter and harder to get wrong, but O(n) stack space — it overflows on a list of 10⁵ nodes. State that trade-off rather than presenting it as strictly better.

Reverse a sublist [left, right]
// Dummy head so left==1 needs no special case.
ListNode* reverseBetween(ListNode* head,int left,int right){
	ListNode dummy(0);
	dummy.next=head;

	ListNode* beforeLeft=&dummy;
	for(int i=1;i<left;i++)
	beforeLeft=beforeLeft->next;

	// head-insert each following node right after beforeLeft
	ListNode* tail=beforeLeft->next;
	for(int i=left;i<right;i++){
		ListNode* move=tail->next;

		tail->next=move->next;
		move->next=beforeLeft->next;
		beforeLeft->next=move;
	}

	return dummy.next;
}

The head-insertion trick avoids reconnecting four pointers at the end. One pass, O(1) space.

The dummy head — the single best habit in list code

Most list bugs are “what if the thing I am modifying is the head?”. A dummy node in front of the real head makes the head an ordinary node, so that case disappears entirely.

removeElements — with and without a dummyO(n)O(1)
// WITHOUT a dummy: the head needs its own loop, before the main loop.
ListNode* removeElementsUgly(ListNode* head,int val){
	while(head and head->val==val)   // must be a while, not an if:
	head=head->next;                 // several leading matches are possible

	if(!head)return nullptr;

	ListNode* cur=head;
	while(cur->next){
		if(cur->next->val==val)cur->next=cur->next->next;
		else cur=cur->next;
	}

	return head;
}

// WITH a dummy: one loop, no special cases, no separate null check.
ListNode* removeElements(ListNode* head,int val){
	ListNode dummy(0);
	dummy.next=head;

	ListNode* cur=&dummy;
	while(cur->next){
		if(cur->next->val==val)cur->next=cur->next->next;
		else cur=cur->next;
	}

	return dummy.next;               // correct even if everything was removed
}
Half the code and no edge cases. Note ListNode dummy(0) on the stack, not new ListNode(0) — no allocation, no leak, automatic cleanup. Also note that while in the ugly version: with if, the input [7,7,7] removing 7 fails.
✍️
My convention: dummy head whenever the head can change, always on the stack

If the function might remove, insert before, or reorder the head, start with ListNode dummy(0); dummy.next=head; and return dummy.next;. That covers remove-element, remove-duplicates, merge, partition, add-two-numbers, remove-nth-from-end and reverse-between — six problems, one habit. Declare it as a value (ListNode dummy(0)), not with new: a heap dummy that you forget to delete is a leak, and there is no reason to allocate it.

The fast/slow patterns

Chapter 4 proved Floyd's cycle detection. Here are the four applications you need on a list, all O(1) space and one pass.

// When fast reaches the end, slow is at the middle.
// This exact condition gives the SECOND middle for even lengths:
//   [1,2,3,4] -> 3.  For the first middle, use while(fast->next and fast->next->next).
ListNode* middleNode(ListNode* head){
	ListNode* slow=head;
	ListNode* fast=head;

	while(fast and fast->next){
		slow=slow->next;
		fast=fast->next->next;
	}

	return slow;
}

Which middle you get depends on the loop condition, and problems are specific about it. Test on [1,2,3,4] before you commit.

// Open a gap of n, then close the list. Dummy head so removing
// the first node needs no special case.
ListNode* removeNthFromEnd(ListNode* head,int n){
	ListNode dummy(0);
	dummy.next=head;

	ListNode* slow=&dummy;
	ListNode* fast=&dummy;

	for(int i=0;i<n;i++)
	fast=fast->next;              // open the gap

	while(fast->next){               // slide both until fast is last
		slow=slow->next;
		fast=fast->next;
	}

	slow->next=slow->next->next;      // slow sits just before the target

	return dummy.next;
}

Starting both at the dummy is what makes “remove the first node” work with no branch. One pass, no length count.

// Phase 1 finds a meeting point; phase 2 finds the entry.
// Chapter 4 proves why resetting to head works.
ListNode* detectCycle(ListNode* head){
	ListNode* slow=head;
	ListNode* fast=head;

	while(fast and fast->next){
		slow=slow->next;
		fast=fast->next->next;

		if(slow==fast)break;
	}

	if(!fast or !fast->next)return nullptr;

	slow=head;
	while(slow!=fast){
		slow=slow->next;
		fast=fast->next;
	}

	return slow;
}

while(fast and fast->next) — two dereferences need two null checks. The break-then-check structure is what distinguishes "met" from "ran off the end".

// Find the middle, reverse the second half, compare, (optionally restore).
bool isPalindrome(ListNode* head){
	if(!head or !head->next)return true;

	ListNode* slow=head;
	ListNode* fast=head;
	while(fast->next and fast->next->next){   // FIRST middle
		slow=slow->next;
		fast=fast->next->next;
	}

	ListNode* second=reverseList(slow->next);

	ListNode* a=head;
	ListNode* b=second;
	bool ok=true;
	while(b){                        // second half is never longer
		if(a->val!=b->val){
			ok=false;
			break;
		}
		a=a->next;
		b=b->next;
	}

	slow->next=reverseList(second);   // restore — be a good citizen

	return ok;
}

O(n) time, O(1) space. Loop on b, not a: on an odd length the first half is one longer, and looping on a dereferences a null b. Restoring the list is what a senior candidate does unprompted.

Merge and partition

mergeTwoLists and partition — the tail-pointer patternO(n+m)O(1)
// Build the result by appending to a tail pointer. Dummy head means
// "is this the first element?" never needs to be asked.
ListNode* mergeTwoLists(ListNode* a,ListNode* b){
	ListNode dummy(0);
	ListNode* tail=&dummy;

	while(a and b){
		if(a->val<=b->val){       // <= keeps it stable (Ch 8)
			tail->next=a;
			a=a->next;
		}else{
			tail->next=b;
			b=b->next;
		}

		tail=tail->next;
	}

	tail->next=a?a:b;             // splice the remainder in O(1)

	return dummy.next;
}

// Two dummies, two tails: stable partition around a pivot value.
// This is also the core of a linked-list quicksort.
ListNode* partition(ListNode* head,int x){
	ListNode lessDummy(0);
	ListNode moreDummy(0);
	ListNode* less=&lessDummy;
	ListNode* more=&moreDummy;

	while(head){
		if(head->val<x){
			less->next=head;
			less=less->next;
		}else{
			more->next=head;
			more=more->next;
		}

		head=head->next;
	}

	more->next=nullptr;          // MUST terminate, or you build a cycle
	less->next=moreDummy.next;

	return lessDummy.next;
}
more->next=nullptr is the line people forget, and forgetting it creates a cycle rather than a wrong value — so the program hangs or crashes far from the bug. Rule: whenever you split a list into pieces, explicitly terminate every piece before reconnecting.
🧩
The three list patterns that cover almost everything
  • Dummy head + tail pointer — when you are building a list. Merge, partition, add two numbers, remove duplicates.
  • Three pointers (prev, cur, next) — when you are rewiring in place. Reverse, reverse in K-groups, swap pairs, odd-even split.
  • Fast and slow — when you need a position you cannot index. Middle, nth from end, cycle, palindrome, reorder.

Name which of the three a problem needs before writing anything, and the code is mostly decided.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 DUMMY HEAD
Allocate a dummy node in front of every list you build or filter. It removes the "what if the head changes" branch entirely, and returning dummy.next is always correct.
💡 THREE POINTERS
Reversal is prev, cur, next — save next, point cur back, advance both. Write it once from memory and you own half the linked-list problems.
⛔ MIDDLE OF TWO
With an even-length list, fast && fast->next gives the second middle and fast->next && fast->next->next gives the first. The problem cares which; check on a 2-node list.
⚠️
Common mistakes
  • Overwriting cur->next before saving it. Loses the rest of the list, silently, with no crash.
  • Returning cur instead of prev from reversal. The loop ends with cur == nullptr.
  • Checking only fast in the fast/slow loop. fast->next->next dereferences twice; check fast and fast->next.
  • Not terminating a split piece with nullptr. Creates a cycle, which hangs the program somewhere else entirely.
  • Handling the head as a special case instead of using a dummy. Doubles the code and is where the bug will be.
  • Using if where a while is needed when skipping leading matches — [7,7,7] removing 7 breaks.
  • new ListNode(0) for a dummy. Leaks unless you delete it. Put it on the stack.
  • Claiming O(1) space for recursive reversal. It is O(n) stack, and overflows at 10⁵ nodes.
  • Looping on the wrong pointer in the palindrome check. On odd lengths the first half is longer; loop on the second half.

Interview drill

Warm-up: Reverse a linked list, then explain why the assignments must be in that order.

How a strong answer sounds
I keep prev starting at null and cur at the head, with the invariant that prev heads the reversed portion and cur heads the untouched portion. Inside the loop, four assignments in a fixed order: first save nxt = cur->next, then set cur->next = prev, then prev = cur, then cur = nxt. The saving must come first because step two overwrites cur->next, and that was the only reference to the rest of the list — overwrite it before saving and everything after cur becomes unreachable. What makes this bug nasty is that nothing crashes: the function returns a correctly reversed one-element list, so a test with a single node passes. At the end I return prev, not cur, because the loop terminates when cur is null and prev is sitting on the last node processed, which is the new head. O(n) time, O(1) space. The recursive version is shorter but O(n) stack, which overflows around 10⁵ nodes, so I would offer it as an alternative rather than a better answer.

Deeper: Why is a linked list usually the wrong choice in production, given its O(1) insertion?

How a strong answer sounds
Because O(1) insertion is only available once you already hold a pointer to the position, and getting there is O(n) with terrible locality. A vector insertion is O(n) too, but that O(n) is a single memmove running at gigabytes per second over contiguous memory, whereas the list's O(n) traversal is one cache miss per node at roughly a hundred nanoseconds each. So for inserting at a random found position, the vector typically wins up to surprisingly large n. Memory makes it worse: a node storing a four-byte int costs sixteen to twenty-four bytes with the pointer and allocator overhead, and those nodes are scattered, so you also lose prefetching. The cases where a list genuinely wins are narrow and specific — you already hold the node, as in an LRU cache where the hash map hands you the pointer; you need stable addresses across insertions, which a reallocating vector cannot give; or you need O(1) splicing of whole ranges. Everywhere else I would reach for vector or deque. In an interview I would say that out loud and then implement the list anyway, because the question is testing pointer manipulation rather than container choice.

🧠 Key takeaways

  • Save next before you overwrite it — the four reversal assignments have exactly one correct order.
  • A stack-allocated dummy head removes every head-is-special case; use it whenever the head can change.
  • Three patterns cover the topic: dummy+tail for building, three pointers for rewiring, fast/slow for positions.
  • Always terminate a split piece with nullptr, or you create a cycle instead of a wrong value.
  • Lists beat arrays only when you already hold the node, need stable addresses, or splice ranges — say so.

Check your understanding

In iterative reversal, what happens if you write cur->next = prev before saving nxt?

The remainder becomes unreachable with no crash, so the function quietly returns a correct-looking one-element list. Save first, always.

Why start both slow and fast at a dummy node in remove-nth-from-end?

Without the dummy, deleting the head means slow would have to sit before the head, which does not exist — forcing a separate branch. The dummy gives that position a node.

In partition, you forget more->next = nullptr. What happens?

Nodes keep their original next pointers, so the tail of one piece still points into the middle of the other. The result is a cycle — a hang or crash far from the actual bug. Always terminate every piece you split off.

Recursive list reversal versus iterative — what is the real trade-off?

Same O(n) time, but recursion holds one live frame per node. At 10⁵ nodes that overflows a typical stack. Offer the recursive version as an alternative, not as an improvement.

When does a linked list genuinely beat a vector?

O(1) insertion only helps if you did not have to walk there. Finding a position is O(n) with a cache miss per node, whereas a vector's O(n) shift is one fast memmove — and the vector uses a quarter of the memory.
