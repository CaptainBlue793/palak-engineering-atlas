Graphs: Representation, DFS & BFS

Every graph algorithm in the next twelve chapters is DFS or BFS with extra bookkeeping. Topological sort is DFS plus a stack. Cycle detection is DFS plus one more array. Dijkstra is BFS with a heap. So this chapter is the foundation: get the adjacency-list convention, the visited discipline and the helper-plus-driver split right once, and the rest of the level is variations on code you already have in your hands.

  • Choose between adjacency list and matrix from the edge density
  • Build the graph from an edge list, with the directed/undirected switch explicit
  • Write DFS and BFS with state in reference parameters and no globals
  • Say exactly where visited is set in each, and why the answer differs
  • Handle disconnected graphs by looping the driver over every node

The density rule

A graph is sparse when E ≈ V and dense when E ≈ V². Real graphs and almost all interview problems are sparse — a road network, a dependency graph, a social graph all have bounded degree. So the adjacency list is the default, and at V = 10⁵ a matrix would need 10¹⁰ entries and is not even allocatable. Use a matrix only when the algorithm genuinely wants O(1) edge lookup over a small V: Floyd-Warshall at V ≤ 500, or a bitmask DP over V ≤ 20.

vector<vector<pair<int,int>>> wgraph(N);   // {weight,neighbour}

	wgraph[e[0]].push_back({e[2],e[1]});
	wgraph[e[1]].push_back({e[2],e[0]});   // undirected

The commented-out line is a deliberate convention. Leaving // graph[v].push_back(u); -> This is for Undirected Edges in place means switching between directed and undirected is a one-character edit rather than a re-read, and it documents which kind of graph the function expects. Half the graph bugs in existence are "I forgot this was undirected".
✍️
My convention: unordered_map<int,vector<int>> when nodes are arbitrary, vector<vector<int>> when they are 0..N−1

The map version handles arbitrary labels (strings hashed to ints, sparse IDs, nodes that may have no edges) and graph[node] on a missing key harmlessly returns an empty vector — which is exactly what you want in a traversal. The vector version is faster and is right when the problem hands you N and uses 0..N−1, which most do. The one thing to avoid is mixing them mid-problem. And note the map version must be taken by reference in every helper: a recursive DFS that copies the adjacency list is still correct and catastrophically slow (Chapter 1).

DFS and BFS, side by side

Both visit every node once. The only structural difference is the container: a stack (implicit, via recursion) versus a queue. That single choice changes the order, the shortest-path property and the space profile.

DFS

DFS — helper plus driverO(V + E)O(V) + O(h) stack
// Helper: all state by reference, returns nothing.
void DFS(unordered_map<int,vector<int>> &graph,int node,vector<bool> &visited,vector<int> &dfs){
	if(visited[node])return;

	visited[node]=true;        // mark on ARRIVAL
	dfs.push_back(node);

	for(auto &neighbour:graph[node]){
		if(!visited[neighbour]){
			DFS(graph,neighbour,visited,dfs);
		}
	}
}

// Driver: owns the state, and loops over EVERY node so disconnected
// components are not missed.
vector<int> dfsOfGraph(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(int i=0;i<edges.size();i++){
		int u=edges[i][0];
		int v=edges[i][1];
		graph[u].push_back(v);
		graph[v].push_back(u);      // undirected here
	}

	vector<bool> visited(N,false);
	vector<int> dfs;

	for(int i=0;i<N;i++){
		if(!visited[i]){
			DFS(graph,i,visited,dfs);
		}
	}

	return dfs;
}
The guard if(visited[node])return; and the check if(!visited[neighbour]) are both worth keeping. The inner check avoids a wasted call; the guard makes the function safe to call on an already-visited node from anywhere. Belt and braces, and it costs one comparison — which matters because the guard is what makes the driver loop safe.

BFS

BFS — and the one line everybody gets wrongO(V + E)O(V)
void BFS(unordered_map<int,vector<int>> &graph,int start,vector<bool> &visited,vector<int> &bfs){
	queue<int> q;
	q.push(start);
	visited[start]=true;        // mark the source when you ENQUEUE it

	while(!q.empty()){
		int node=q.front();
		q.pop();
		bfs.push_back(node);

		for(auto &neighbour:graph[node]){
			if(!visited[neighbour]){
				visited[neighbour]=true;   // NOT visited[node] — see below
				q.push(neighbour);
			}
		}
	}
}
This is the single most common graph bug there is. Writing visited[node]=true inside the neighbour loop marks the node you are already standing on — which is already marked — and leaves the neighbour unmarked. The neighbour then gets enqueued again by every other node adjacent to it, the queue grows quadratically, and on a dense graph the program hangs. The output is often still correct on small tests, which is exactly why it survives.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

⛔ MARK ON PUSH
Set visited[neighbour] when you enqueue, never when you dequeue. Marking on dequeue still returns the right answer while pushing each node once per incoming edge — silent, and quadratic on dense graphs.
💡 BUILD ONCE
Build the adjacency list in the driver, pass it by reference everywhere, and add both directions for undirected edges. One missing & turns O(V+E) into O(V·(V+E)).
💡 IMPLICIT GRAPHS
Word ladder, jump games and state puzzles are graphs you never construct: the neighbour function generates edges on demand. Ask "what are the nodes and what are the edges?" before anything else.
🚨
Mark on enqueue, not on dequeue

The other half of the same bug. Consider marking a node only when you pop it:

Correct — mark when pushing
if(!visited[neighbour]){
	visited[neighbour]=true;
	q.push(neighbour);
}

Each node enters the queue exactly once. Queue size ≤ V.

Broken — mark when popping
int node=q.front(); q.pop();
if(visited[node])continue;
visited[node]=true;
for(auto &nb:graph[node])
q.push(nb);            // no check at all

A node can be pushed once per incoming edge, so the queue reaches O(E). Still correct, but on a dense graph the memory blows up.

The rule: mark a node the moment you commit to visiting it. For BFS that is when you push. The one deliberate exception is Dijkstra (Chapter 29), where a node's distance can improve after it is queued, so you must allow re-entry and instead skip stale entries on pop with if(d>dist[node])continue;.

Why BFS finds shortest paths and DFS does not

BFS processes nodes in non-decreasing order of distance from the source. Proof sketch by induction on the layers: the queue always holds nodes of distance d followed by nodes of distance d+1 and nothing else. When a node at distance d is popped, all of its unvisited neighbours are at distance exactly d+1 — they cannot be closer, since that would have made this node closer too. So the first time a node is reached, it is reached by a shortest path, and marking on enqueue locks that in. DFS has no such property: it commits to one branch entirely, so it may reach a node by a long detour and mark it, never revisiting via the short route. This is also exactly why BFS breaks on weighted graphs — "one more edge" stops meaning "one more unit of distance", and you need Dijkstra (Chapter 29).

Counting connected components

The driver loop is not boilerplate — it is the component counter. Each time it starts a fresh traversal, that is one component.

countComponentsO(V + E)O(V)
// Every iteration of the driver loop that actually starts a traversal
// discovers exactly one new component.
int countComponents(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(auto &e:edges){
		graph[e[0]].push_back(e[1]);
		graph[e[1]].push_back(e[0]);
	}

	vector<bool> visited(N,false);
	vector<int> dfs;
	int components=0;

	for(int i=0;i<N;i++){
		if(!visited[i]){
			components++;
			DFS(graph,i,visited,dfs);
		}
	}

	return components;
}
// DSU (Chapter 22) does the same in O(E*alpha) — and wins when the
// edges arrive one at a time and you must answer after each.
Forgetting the driver loop is the second most common graph mistake. Traversing only from node 0 silently reports 1 component on any disconnected graph, and gives a partial answer to every "for all nodes" question. If the problem does not promise connectivity, loop.

Graph vocabulary you will be assumed to know

↔️

Directed vs undirected

An undirected edge is stored as two directed edges. This doubles E and changes every algorithm — cycle detection especially (Chapter 27).

🔢

Degree, indegree, outdegree

Neighbours count. In a directed graph, indegree drives Kahn's topological sort (Chapter 26). Σ degree = 2E.

🧩

Connected component

A maximal mutually-reachable set. In a directed graph the right notion is a strongly connected component (Chapter 32).

🎯

DAG

Directed acyclic graph — the only kind with a topological order, and where longest path becomes easy DP.

🔁

Self-loop and multi-edge

An edge from a node to itself, and two edges between the same pair. Both break naive cycle detection — ask whether they exist.

🌳

Tree as a graph

A connected undirected graph with exactly V−1 edges and no cycles. Many "graph" problems are tree problems in disguise, and trees have no cycles to worry about.

❓
The five questions to ask before writing any graph code
  1. Directed or undirected? Decides whether you push the reverse edge, and which cycle-detection algorithm applies.
  2. Weighted or unweighted? Unweighted shortest path is BFS; weighted needs Dijkstra, or Bellman-Ford if weights can be negative.
  3. Connected, or possibly disconnected? Decides whether the driver needs the loop over all nodes.
  4. Self-loops or multi-edges? They change cycle detection and degree arithmetic.
  5. How large are V and E? V ≤ 500 permits O(V³) Floyd-Warshall and a matrix; V = 10⁵ demands a list and O((V+E) log V).

Thirty seconds, and it eliminates most of the wrong approaches — the Chapter 1 funnel applied to graphs.

⚠️
Common mistakes
  • visited[node]=true instead of visited[neighbour]=true inside the BFS neighbour loop. The single most common graph bug: nodes get enqueued repeatedly, the queue grows quadratically, and small tests still pass.
  • Marking visited on dequeue rather than enqueue. Correct but the queue reaches O(E) instead of O(V).
  • Forgetting the driver loop over all nodes. Disconnected graphs silently report one component.
  • Forgetting the reverse edge on an undirected graph. Half the graph becomes unreachable.
  • Adding the reverse edge on a directed graph. Topological sort and cycle detection both become nonsense.
  • Passing the adjacency list by value. Correct answer, silently catastrophic complexity.
  • Recursive DFS on a path graph of 10⁵ nodes. Stack overflow; use an explicit stack or BFS.
  • Using BFS for shortest paths on a weighted graph. "Fewest edges" is not "least weight".
  • Sizing visited to the edge count instead of the node count. Or forgetting that node labels may exceed N.
  • Using graph[node] on an unordered_map in a read-only loop. It inserts an empty vector for missing keys (Chapter 9) — harmless here, but it grows the map while you iterate it, which is undefined behaviour.

Interview drill

Warm-up: In BFS, why must you mark a node visited when you enqueue it rather than when you dequeue it?

How a strong answer sounds
Because otherwise a node can be pushed onto the queue once for every edge pointing at it. Suppose I only mark on dequeue: node X has five neighbours already in the queue, each of them sees X unvisited, and each pushes it — so X sits in the queue five times. The algorithm still produces the right answer, because I skip already-visited nodes when popping, but the queue grows to O(E) rather than O(V), and on a dense graph that is the difference between 10⁵ and 10¹⁰ entries. Marking on enqueue means each node enters exactly once, so the queue is bounded by V. The general rule is to mark the moment you commit to visiting, which for BFS is the push. The one deliberate exception is Dijkstra, where a node's tentative distance can improve after it has been queued, so you must allow re-entry and instead discard stale entries on pop with a check like if(d > dist[node]) continue;. And the closely related bug worth naming is writing visited[node] = true inside the neighbour loop instead of visited[neighbour] = true — that marks the node you are standing on, which is already marked, and leaves the neighbour open for repeated enqueueing.

Deeper: Adjacency list or adjacency matrix — how do you decide, and when is the matrix actually right?

How a strong answer sounds
I decide from the density and from what the algorithm needs. A list is O(V + E) memory and lets me iterate a node's neighbours in O(degree), which is what every traversal actually does — so for sparse graphs, where E is closer to V than to V², it wins on both memory and time. A matrix is O(V²) memory and iterating neighbours costs O(V) even if the node has one edge, but it answers "is there an edge u→v?" in O(1). Since almost all real and interview graphs are sparse — road networks, dependency graphs, social graphs all have bounded degree — the list is my default, and at V = 10⁵ a matrix is 10¹⁰ entries and simply not allocatable. The matrix is right in three situations: when the algorithm is inherently O(V³) and dense-oriented, like Floyd-Warshall, where V is capped around 500 anyway and the matrix is the DP table; when I need constant-time edge existence tests in a hot loop; and when V is tiny enough that I can store each row as a bitmask, which makes intersection and union of neighbour sets single machine instructions — useful for clique and bitmask-DP problems at V ≤ 64. Outside those, list.

🧠 Key takeaways

  • Adjacency list by default — O(V + E) and neighbour iteration in O(degree); matrix only for dense, small-V algorithms.
  • Keep // graph[v].push_back(u); -> This is for Undirected Edges in place so the switch is a one-character edit.
  • In BFS, mark on enqueue and mark the neighbour — both halves of the most common graph bug.
  • BFS gives shortest paths on unweighted graphs because it processes nodes in non-decreasing distance order; DFS does not.
  • The driver's loop over all nodes is the component counter, and omitting it breaks every disconnected input.

Check your understanding

Inside the BFS neighbour loop you write visited[node] = true instead of visited[neighbour] = true. What happens?

You mark the node you are already standing on, which is already marked. The output is often correct, which is exactly why this bug survives into production and then times out on a dense graph.

Why does BFS give shortest paths on an unweighted graph while DFS does not?

The queue always holds distance-d nodes followed by distance-d+1 nodes. DFS commits to one branch, so it may reach a node by a detour and mark it, never revisiting via the short route.

V = 10⁵ and E = 2×10⁵. Which representation?

E ≈ 2V, so this is sparse. The list is O(V + E) ≈ 3×10⁵ entries; the matrix is not even allocatable. Matrices are for dense graphs with small V, such as Floyd-Warshall at V ≤ 500.

Your DFS driver traverses only from node 0. On a disconnected graph, what is wrong?

DFS reaches everything reachable from its start. Without the driver's for(i=0..N-1) if(!visited[i]) loop, every disconnected input reports one component and gives a partial traversal.

Which situation genuinely requires marking a node visited after popping rather than on push?

In Dijkstra you deliberately allow a node to enter the priority queue more than once and discard outdated entries with if(d > dist[node]) continue; (Chapter 29). For plain BFS, marking on enqueue is the right discipline.
