Graphs: Representation, DFS & BFS

A graph is a set of nodes (things) joined by edges (connections between them) — cities and roads, people and friendships, tasks and "must happen before" rules. Almost every graph algorithm in the next twelve chapters is just DFS (depth-first search) or BFS (breadth-first search) with a little extra bookkeeping. Topological sort is DFS plus a stack. Cycle detection is DFS plus one more array. Dijkstra is BFS with a heap. So this chapter is the foundation. Get three habits right once — the adjacency-list convention, the visited discipline and the helper-plus-driver split — and the rest of this level is small variations on code you already know.

  • Choose between an adjacency list and a matrix by looking at how many edges there are
  • Build the graph from a list of edges, with a clear switch between one-way (directed) and two-way (undirected) edges
  • Write DFS and BFS that pass their state by reference, with no global variables
  • Say exactly where visited is set in each, and why the answer differs
  • Handle graphs made of separate pieces by having the driver loop over every node

Representation

Before any algorithm can run, the graph has to live in memory somehow. The input usually arrives as a plain list of edges, like [[0,1],[0,2],[1,3]]. That format is bad for traversal: to find the neighbours of node 1 you would have to scan every edge. So the first job in almost every graph problem is to turn that list into a structure where "give me the neighbours of u" is fast. There are three common choices.

Here is one small undirected graph with 4 nodes and edges 0–1, 0–2, 1–3, stored all three ways:

  • Adjacency list — for each node, a list of its neighbours: 0 → [1, 2], 1 → [0, 3], 2 → [0], 3 → [1]. That is 6 entries in total: each undirected edge is stored twice, once from each end.
  • Adjacency matrix — a 4×4 grid of 0/1 where mat[u][v] = 1 means there is an edge. Row 0 is 0 1 1 0. That is 16 cells, most of them 0, even though there are only 3 edges.
  • Edge list — just the input as given: (0,1), (0,2), (1,3). Compact, but you cannot jump to one node's neighbours.

The table compares what each costs. "degree" means the number of neighbours of that particular node.

The density rule

V is the number of nodes and E the number of edges. A graph is sparse (few edges) when E ≈ V and dense (nearly every pair connected) when E ≈ V². Real graphs and almost all interview problems are sparse. In a road network, a dependency graph or a social graph, each node has only a limited number of neighbours. So the adjacency list is the default. At V = 10⁵ a matrix would need 10¹⁰ entries — too much memory to even create. Use a matrix only when the algorithm really needs O(1) "is there an edge?" checks and V is small: Floyd-Warshall at V ≤ 500, or a bitmask DP over V ≤ 20.

for(int i=0;i<edges.size();i++){
	int u=edges[i][0];

// Weighted: store the pair with the WEIGHT FIRST, so the built-in pair<>
// comparison sorts by weight and no custom comparator is needed (Ch 15).
vector<vector<pair<int,int>>> wgraph(N);   // {weight,neighbour}

for(auto &e:edges){
	wgraph[e[0]].push_back({e[2],e[1]});

The commented-out line is there on purpose. Keeping // graph[v].push_back(u); -> This is for Undirected Edges in the code means you can switch between directed and undirected by deleting two characters, without re-reading anything. It also tells the reader which kind of graph the function expects. A huge share of graph bugs come down to "I forgot this graph was undirected".
✍️
My convention: unordered_map<int,vector<int>> when nodes are arbitrary, vector<vector<int>> when they are 0..N−1

The map version copes with any node labels: strings turned into ints, IDs with big gaps, or nodes that have no edges. Asking for graph[node] on a missing key just gives back an empty vector — exactly what you want in a traversal. The vector version is faster. Use it when the problem gives you N and numbers the nodes 0..N−1, which most problems do. The one thing to avoid is mixing the two in the same problem. Also, every helper must take the map by reference (with an &). A recursive DFS that copies the adjacency list on every call still gives the right answer, but it is terribly slow (Chapter 1).

DFS and BFS, side by side

Both visit every node once. The only real difference is where they keep the nodes waiting to be explored. DFS uses a stack (last in, first out — here the recursion's call stack does this for you). BFS uses a queue (first in, first out, like a line at a shop). That one choice changes the visiting order, whether you get shortest paths, and how much memory you use.

DFS

DFS means: go as deep as you can along one path, and only when you hit a dead end, back up to the last node that still has an unexplored neighbour. It is the graph version of the preorder tree traversal you already know. The one new ingredient is the visited array. A tree never leads you back to a node you have seen, but a graph can (A→B→C→A), so without visited the recursion would go round that loop forever.

A short dry run. Take the undirected graph with edges 0–1, 0–2, 1–3, 2–3, so the adjacency list is 0 → [1,2], 1 → [0,3], 2 → [0,3], 3 → [1,2].

  1. DFS(0): mark 0, record it. First neighbour is 1, unvisited, so call DFS(1).
  2. DFS(1): mark 1. Neighbour 0 is visited, skip. Neighbour 3 is unvisited, call DFS(3).
  3. DFS(3): mark 3. Neighbour 1 visited, skip. Neighbour 2 unvisited, call DFS(2).
  4. DFS(2): mark 2. Neighbours 0 and 3 are both visited. Return. Then 3 returns, 1 returns, and back in DFS(0) the next neighbour, 2, is already visited.

Visit order: 0, 1, 3, 2. The call stack was 4 frames deep at its peak. On a long chain of 10⁵ nodes it would be 10⁵ frames deep, which is where the stack-overflow risk below comes from. Each node is marked once and each adjacency list is scanned once, so the total work is O(V + E).

DFS — helper plus driverO(V + E)O(V) + O(h) stack
// Helper: all state by reference, returns nothing.
void DFS(unordered_map<int,vector<int>> &graph,int node,vector<bool> &visited,vector<int> &dfs){
	if(visited[node])return;

	visited[node]=true;        // mark on ARRIVAL
	dfs.push_back(node);

	for(auto &neighbour:graph[node]){
		if(!visited[neighbour]){
			DFS(graph,neighbour,visited,dfs);
		}
	}
}

// Driver: owns the state, and loops over EVERY node so disconnected
// components are not missed.
vector<int> dfsOfGraph(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(int i=0;i<edges.size();i++){
		int u=edges[i][0];
		int v=edges[i][1];
		graph[u].push_back(v);
		graph[v].push_back(u);      // undirected here
	}

	vector<bool> visited(N,false);
	vector<int> dfs;

	for(int i=0;i<N;i++){
		if(!visited[i]){
			DFS(graph,i,visited,dfs);
		}
	}

	return dfs;
}
Keep both the guard if(visited[node])return; and the check if(!visited[neighbour]). The inner check saves a wasted function call. The guard makes the function safe to call on an already-visited node from anywhere. Having both is a belt-and-braces safety net that costs one comparison — and the guard is what makes the driver loop safe.

BFS

BFS explores in rings: first the start node, then everything one edge away, then everything two edges away. It does this by keeping a queue of nodes that have been found but not yet processed. Same graph as the DFS dry run (0 → [1,2], 1 → [0,3], 2 → [0,3], 3 → [1,2]), starting at 0:

Visit order: 0, 1, 2, 3. Look at step 3: node 3 is a neighbour of 2, but it was already marked when 1 pushed it, so it is not pushed a second time. That is the whole point of marking on push, and the code below shows the exact line that makes it happen. Because every node is pushed and popped once, and its neighbour list is read once when it is popped, BFS also costs O(V + E) in total.

BFS — and the one line everybody gets wrongO(V + E)O(V)
void BFS(unordered_map<int,vector<int>> &graph,int start,vector<bool> &visited,vector<int> &bfs){
	queue<int> q;
	q.push(start);
	visited[start]=true;        // mark the source when you ENQUEUE it

	while(!q.empty()){
		int node=q.front();
		q.pop();
		bfs.push_back(node);

		for(auto &neighbour:graph[node]){
			if(!visited[neighbour]){
				visited[neighbour]=true;   // NOT visited[node] — see below
				q.push(neighbour);
			}
		}
	}
}
This is the most common graph bug there is. Writing visited[node]=true inside the neighbour loop marks the node you are standing on. That node is already marked, and the neighbour stays unmarked. So every other node next to that neighbour adds it to the queue again. The queue grows quadratically (roughly V² entries), and on a dense graph the program hangs. The output is often still correct on small tests — which is exactly why the bug goes unnoticed.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

⛔ MARK ON PUSH
Set visited[neighbour] when you enqueue, never when you dequeue. Marking on dequeue still returns the right answer while pushing each node once per incoming edge — silent, and quadratic on dense graphs.
💡 BUILD ONCE
Build the adjacency list in the driver, pass it by reference everywhere, and add both directions for undirected edges. One missing & turns O(V+E) into O(V·(V+E)).
💡 IMPLICIT GRAPHS
Word ladder, jump games and state puzzles are graphs you never construct: the neighbour function generates edges on demand. Ask "what are the nodes and what are the edges?" before anything else.
🚨
Mark on enqueue, not on dequeue

This is the other half of the same bug. Suppose you mark a node only when you take it off the queue:

Correct — mark when pushing
if(!visited[neighbour]){
	visited[neighbour]=true;
	q.push(neighbour);
}

Each node enters the queue exactly once. Queue size ≤ V.

Broken — mark when popping
int node=q.front(); q.pop();
if(visited[node])continue;
visited[node]=true;
for(auto &nb:graph[node])
q.push(nb);            // no check at all

A node can be pushed once for every edge pointing at it, so the queue can reach O(E) entries. The answer is still correct, but on a dense graph memory use explodes.

The rule: mark a node the moment you decide to visit it. For BFS, that is when you push it. The one deliberate exception is Dijkstra (Chapter 29). There, a node's best distance can still get better after it is queued, so you must let it enter again. Instead of marking, you skip outdated ("stale") entries when you pop them, with if(d>dist[node])continue;.

How to pick in practice:

  • The question mentions "minimum number of steps", "fewest moves" or "nearest": use BFS. Only BFS gives that answer directly on an unweighted graph.
  • The question needs information that flows back up after exploring a node (subtree sizes, "finished" times, whether a cycle was found below): use DFS. The return from the recursive call is the natural place to collect it.
  • You only need "which nodes are reachable" or "how many components": either works. Pick the one you write fastest, but prefer BFS or an explicit stack if the graph can be one long chain of 10⁵+ nodes.

The memory rows are worth a concrete picture. On a star (node 0 joined to 9,999 others) BFS pushes all 9,999 leaves at once, so the queue is huge while the DFS stack is only 2 deep. On a path (0–1–2–…–9,999) it is the reverse: the BFS queue never holds more than 1 node, but recursive DFS goes 10,000 frames deep. Both are O(V) in the worst case; they just blow up on different shapes.

🧾
Why BFS finds shortest paths and DFS does not

BFS handles nodes in order of distance from the start: all nodes 1 edge away, then all nodes 2 edges away, and so on — like ripples spreading from a stone dropped in a pond. Why this holds (a proof sketch, layer by layer): the queue only ever holds nodes at distance d followed by nodes at distance d+1, nothing else. When a node at distance d is popped, its unvisited neighbours are at distance exactly d+1. They cannot be closer, because then this node would be closer too. So the first time BFS reaches a node, it has used a shortest path, and marking on enqueue locks that in.

DFS has no such guarantee. It follows one branch all the way down first, so it may reach a node by a long detour, mark it, and never come back by the short route. This is also exactly why BFS fails on weighted graphs. Once edges have different lengths, "one more edge" no longer means "one more unit of distance", and you need Dijkstra (Chapter 29).

Counting connected components

A connected component is one separate piece of the graph: a group of nodes you can travel between, with no edges to the rest. The driver loop is not filler code — it is the component counter. Every time it starts a fresh traversal from an unvisited node, it has found one new component.

Example: N = 6 with edges 0–1, 1–2, 3–4, and node 5 on its own. The driver checks node 0: unvisited, so the count becomes 1 and DFS marks 0, 1, 2. Nodes 1 and 2 are now visited, so the loop skips them. Node 3 is unvisited: count 2, DFS marks 3 and 4. Node 4 is skipped. Node 5 is unvisited: count 3, and DFS marks just 5. Answer: 3 components. Note that node 5 has no edges at all, so it never appears in the edge list — the only reason it is counted is that the driver loops over 0..N−1, not over the edges.

countComponentsO(V + E)O(V)
// Every iteration of the driver loop that actually starts a traversal
// discovers exactly one new component.
int countComponents(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(auto &e:edges){
		graph[e[0]].push_back(e[1]);
		graph[e[1]].push_back(e[0]);
	}

	vector<bool> visited(N,false);
	vector<int> dfs;
	int components=0;

	for(int i=0;i<N;i++){
		if(!visited[i]){
			components++;
			DFS(graph,i,visited,dfs);
		}
	}

	return components;
}
// DSU (Chapter 22) does the same in O(E*alpha) — and wins when the
// edges arrive one at a time and you must answer after each.
Forgetting the driver loop is the second most common graph mistake. If you only start from node 0, a graph made of several pieces quietly reports 1 component. Every "for all nodes" question also gets only a partial answer. Unless the problem promises the graph is connected, loop over every node.

Graph vocabulary you will be assumed to know

↔️

Directed vs undirected

A directed edge is one-way (u→v); an undirected edge is two-way. An undirected edge is stored as two directed edges. This doubles E and changes every algorithm — cycle detection most of all (Chapter 27).

🔢

Degree, indegree, outdegree

Degree is how many neighbours a node has. In a directed graph, indegree counts edges coming in and outdegree counts edges going out. Indegree drives Kahn's topological sort (Chapter 26). In an undirected graph, the degrees add up to 2E (Σ degree = 2E), since each edge touches two nodes.

🧩

Connected component

The largest group of nodes that can all reach each other. In a directed graph, the matching idea is a strongly connected component (Chapter 32).

🎯

DAG

A directed acyclic graph: one-way edges and no cycles. It is the only kind of graph with a topological order (a valid "do this before that" ordering), and on it even the longest path becomes an easy DP.

🔁

Self-loop and multi-edge

A self-loop is an edge from a node to itself. A multi-edge is two edges between the same pair of nodes. Both break simple cycle detection, so ask whether the input can contain them.

🌳

Tree as a graph

A tree is a connected undirected graph with exactly V−1 edges and no cycles. Many "graph" problems are really tree problems in disguise, and trees have no cycles to worry about.

❓
The five questions to ask before writing any graph code
  1. Directed or undirected? This decides whether you add the reverse edge, and which cycle-detection method you use.
  2. Weighted or unweighted? (Do edges have costs?) Unweighted shortest path is BFS. Weighted needs Dijkstra, or Bellman-Ford if weights can be negative.
  3. Connected, or possibly in several pieces? This decides whether the driver needs the loop over all nodes.
  4. Self-loops or multi-edges? They change cycle detection and degree counts.
  5. How large are V and E? V ≤ 500 allows O(V³) Floyd-Warshall and a matrix. V = 10⁵ needs a list and an O((V+E) log V) algorithm or faster.

It takes thirty seconds and rules out most wrong approaches — the Chapter 1 funnel, applied to graphs.

⚠️
Common mistakes
  • visited[node]=true instead of visited[neighbour]=true inside the BFS neighbour loop. The most common graph bug: nodes get added to the queue again and again, the queue grows quadratically, and small tests still pass.
  • Marking visited on dequeue rather than enqueue. The answer is correct, but the queue grows to O(E) instead of O(V).
  • Forgetting the driver loop over all nodes. A graph in several pieces quietly reports one component.
  • Forgetting the reverse edge on an undirected graph. Half the graph becomes unreachable.
  • Adding the reverse edge on a directed graph. Topological sort and cycle detection both give nonsense.
  • Passing the adjacency list by value (a copy) instead of by reference. The answer is correct, but it quietly becomes far too slow.
  • Recursive DFS on a path graph of 10⁵ nodes (one long chain). The recursion goes 10⁵ calls deep and overflows the stack. Use an explicit stack or BFS.
  • Using BFS for shortest paths on a weighted graph. "Fewest edges" is not the same as "lowest total weight".
  • Sizing visited by the number of edges instead of the number of nodes. Or forgetting that node labels may be larger than N.
  • Using graph[node] on an unordered_map in a read-only loop. It inserts an empty vector for any missing key (Chapter 9). That is usually harmless, but if it happens while you are looping over the map itself, the map grows under you — which is undefined behaviour.

Interview drill

Warm-up: In BFS, why must you mark a node visited when you enqueue it rather than when you dequeue it?

How a strong answer sounds
Because otherwise a node can be pushed onto the queue once for every edge pointing at it. Say I only mark on dequeue. Node X has five neighbours already in the queue. Each of them sees X as unvisited, and each pushes it — so X sits in the queue five times. The answer is still right, because I skip already-visited nodes when popping. But the queue grows to O(E) instead of O(V). On a dense graph that is the difference between 10⁵ and 10¹⁰ entries. Marking on enqueue means each node enters exactly once, so the queue never holds more than V nodes. The general rule is to mark the moment you commit to visiting, which for BFS is the push. The one deliberate exception is Dijkstra. There a node's best-so-far distance can improve after it is queued, so you must let it re-enter, and you throw away outdated entries on pop with a check like if(d > dist[node]) continue;. A closely related bug is writing visited[node] = true inside the neighbour loop instead of visited[neighbour] = true. That marks the node you are standing on, which is already marked, and leaves the neighbour free to be enqueued again and again.

Deeper: Adjacency list or adjacency matrix — how do you decide, and when is the matrix actually right?

How a strong answer sounds
I decide from how dense the graph is and from what the algorithm needs. A list uses O(V + E) memory and lets me loop over a node's neighbours in O(degree), which is what every traversal does. So for sparse graphs, where E is closer to V than to V², the list wins on both memory and time. A matrix uses O(V²) memory, and looping over neighbours costs O(V) even if the node has one edge. Its advantage is answering "is there an edge u→v?" in O(1). Almost all real and interview graphs are sparse — in road networks, dependency graphs and social graphs each node has a limited number of neighbours. So the list is my default. At V = 10⁵ a matrix is 10¹⁰ entries, which you simply cannot allocate. The matrix is right in three situations. First, when the algorithm is O(V³) anyway and built around a table, like Floyd-Warshall: V is capped around 500 and the matrix is the DP table. Second, when I need constant-time "does this edge exist?" checks inside a hot loop. Third, when V is tiny enough (V ≤ 64) to store each row as a bitmask, so combining neighbour sets is a single machine instruction — handy for clique and bitmask-DP problems. Otherwise, list.

🧠 Key takeaways

  • Use an adjacency list by default: O(V + E) memory, and looping over a node's neighbours costs O(degree). Use a matrix only for dense graphs with small V.
  • Keep // graph[v].push_back(u); -> This is for Undirected Edges in the code so switching between directed and undirected is a tiny edit.
  • In BFS, mark on enqueue and mark the neighbour — both halves of the most common graph bug.
  • BFS gives shortest paths on unweighted graphs because it handles nodes in order of distance — nearest first. DFS does not.
  • The driver's loop over all nodes is the component counter. Leave it out and every graph made of separate pieces gives a wrong answer.

Check your understanding

Inside the BFS neighbour loop you write visited[node] = true instead of visited[neighbour] = true. What happens?

You mark the node you are standing on, which is already marked, and the neighbour stays unmarked. The output is often correct — which is exactly why this bug slips into real code and then times out on a dense graph.

Why does BFS give shortest paths on an unweighted graph while DFS does not?

The queue always holds distance-d nodes followed by distance-d+1 nodes, so nearer nodes are always handled first. DFS dives down one branch, so it may reach a node by a detour, mark it, and never come back by the short route.

V = 10⁵ and E = 2×10⁵. Which representation?

E ≈ 2V, so the graph is sparse. The list needs O(V + E) ≈ 3×10⁵ entries. The matrix would need 10¹⁰ and cannot even be allocated. Matrices are for dense graphs with small V, such as Floyd-Warshall at V ≤ 500.

Your DFS driver traverses only from node 0. On a disconnected graph, what is wrong?

DFS only reaches nodes reachable from where it starts. Without the driver's for(i=0..N-1) if(!visited[i]) loop, any graph in several pieces reports one component and only part of the traversal.

Which situation genuinely requires marking a node visited after popping rather than on push?

In Dijkstra you deliberately let a node enter the priority queue more than once, and throw away outdated entries with if(d > dist[node]) continue; (Chapter 29). For plain BFS, marking on enqueue is the right habit.
