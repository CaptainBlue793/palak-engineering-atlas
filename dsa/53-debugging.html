Debugging & Correctness

Almost every wrong answer you will write falls into about a dozen categories, and most of them are silent. The code compiles, runs, and prints a number that looks believable. This chapter gives you the full list of those categories, the habit of writing down what must always be true in a loop (an invariant), which prevents most of them, and a stress-testing trick that finds the rest in under a minute.

  • Recognise the twelve recurring bug classes by their symptom
  • State an invariant per loop, and use it to locate a fault by bisection
  • Write a stress test that finds a counterexample automatically
  • Build the edge-case checklist into a habit
  • Debug without a debugger, which is what an interview requires

Symptom → likely cause

Start from what you can see going wrong. The symptom narrows down the cause far faster than reading the code from the top.

Here is an example of reading a symptom. You add up three values of 10⁹ in an int and print -1294967296. A negative total from positive inputs can only mean one thing: the true sum, 3·10⁹, went past the int limit of about 2.1·10⁹ and wrapped around (3·10⁹ − 2³² = −1,294,967,296). Strictly, signed overflow is undefined behaviour, but wrapping around is what you will see in practice. You did not need to read a single line of code to know which row of the table to check. Overflow does not always give a negative number, though. A sum of 10¹⁰ wraps to 1,410,065,408, which is positive and looks believable. So "right on small tests, wrong on large ones" is the more reliable sign.

The twelve bug classes

1 · Marking visited at the wrong time in BFS

Symptom: the answer is right but the code is far too slow, or the output contains the same node twice. On a graph with many edges, the work blows up.

// WRONG — marks the node when it is DEQUEUED
while(!q.empty()){
	int node=q.front();

	q.pop();
	visited[node]=true;              // too late!

	for(auto &neighbour:graph[node]){
		if(!visited[neighbour])q.push(neighbour);
	}
}

Fix: mark a node when you add it to the queue, not when you take it out. Otherwise, a node that several other nodes point to looks unvisited to each of them, so it gets pushed once per pointing node before any copy is processed. The queue fills with duplicates. The rule to hold on to is "every node in the queue is already marked visited". Say that sentence and the right place for the marking is obvious. This is the most common graph bug there is, and it is silent: the answer still comes out right.

A tiny example: nodes A, B and C are all in the queue, and all three point to D. With the wrong code, D is not marked until it is popped. So A pushes D, then B pushes D, then C pushes D. D is in the queue three times. On a dense graph where every node points to many others, those extra copies add up to one per edge instead of one per node.

2 · Arithmetic on a sentinel

Symptom: a huge negative number, or an impossibly good answer that then spreads through the rest of the results. (A sentinel is a placeholder value such as INT_MAX meaning "not reached yet".)

// WRONG — dist[node] may still be INT_MAX
if(dist[node]+weight<dist[neighbour])   // INT_MAX + weight overflows
dist[neighbour]=dist[node]+weight;

// RIGHT — refuse to relax from an unreached node
if(dist[node]==INT_MAX)continue;

if(dist[node]+weight<dist[neighbour])
dist[neighbour]=dist[node]+weight;

Fix: check for the placeholder before every update, or pick a sentinel with room to spare, such as 1e18 in a long long, so adding a weight cannot wrap round. The same bug covers INT_MIN in "find the maximum" problems and INT_MAX starting values in DP tables. In C++, overflowing a signed integer is undefined behaviour, so the compiler is allowed to do anything. That includes deleting your check if you write it as a+b < a.

3 · int where the value needs 64 bits

Symptom: exactly right on small tests, wrong on large ones, and often negative.

// WRONG — the multiplication happens in int, THEN widens
long long product=a*b;            // a,b are int near 1e9 -> already wrapped

// RIGHT
long long product=1LL*a*b;

// Places this bites: sums of 1e5 values each up to 1e9 (1e14);
// products under a modulus (1e18); path counts; subtree sums;
// (low+high)/2 in binary search when both are near INT_MAX.

Fix: work out the largest value you could reach before choosing the type. An int holds about 2·10⁹, and a long long about 9·10¹⁸. When you are working under a modulus and unsure, make everything long long. And write the binary-search midpoint as low + (high-low)/2, which cannot overflow.

4 · An incomplete memo key

Symptom: the recursion is correct, but adding memoisation (caching each result) makes it wrong.

// WRONG — the state includes `remaining`, but the key does not
int solve(int i,int remaining,vector<int> &memo){
	if(memo[i]!=-1)return memo[i];      // two different `remaining`
	                                    // values collide here
	// ...
	return memo[i]=ans;
}

Fix: the memo key must include every parameter the answer depends on, and nothing else. The test is simple: if two calls with the same key could correctly return different answers, the key is missing something. The opposite mistake also exists. Including a parameter that does not affect the answer just wastes memory. But keying on the total accumulated so far, rather than on what is left to do, usually means your state is not really a state at all.

Concretely: the first call to reach i = 2 has remaining = 5, and it stores its answer in memo[2]. Later, a call with i = 2 and remaining = 3 finds memo[2] already filled and returns the answer for 5. That is the wrong subproblem. The fix is a 2D memo, memo[i][remaining], so the two calls get separate slots.

5 · Off-by-one in a loop bound or an index shift

Symptom: wrong by one, or an out-of-range access on the last element.

// The four questions to ask of every loop:
//   Does it start at 0 or 1?
//   Is the end < n or <= n?
//   Does the body read i+1 or i-1? Then the bound must shrink.
//   In a 1-indexed DP over a 0-indexed array, is it s[i-1]?

for(int i=0;i<n-1;i++)     // correct when the body reads a[i+1]
for(int i=1;i<=n;i++)      // correct for a 1-indexed dp of size n+1

Fix: walk through n = 1 and n = 2 by hand. Nearly every off-by-one shows up at those two sizes, and it takes twenty seconds. For string DP, write the meaning of the state as a sentence first ("the first i characters"). The i-1 indexing then follows from that sentence instead of from guesswork (Chapter 41).

One off-by-one deserves its own warning: v.size() is unsigned. If v is empty, v.size()-1 does not give −1. It wraps around to about 1.8·10¹⁹, so for(int i=0;i<v.size()-1;i++) runs far past the end of the array. Store the size in an int n first, as this course always does, and n-1 becomes a harmless −1.

6 · Modifying a container while iterating it

Symptom: a crash, or elements quietly skipped. It often works with one compiler and not another.

// WRONG — push_back may reallocate, invalidating the iterator
for(auto &x:values){
	if(check(x))values.push_back(x*2);
}

// WRONG — erase invalidates `it`
for(auto it=m.begin();it!=m.end();it++){
	if(it->second==0)m.erase(it);
}

// RIGHT — erase returns the next valid iterator
for(auto it=m.begin();it!=m.end();){
	if(it->second==0)it=m.erase(it);
	else it++;
}

Fix: collect the changes you want to make, then apply them after the loop. Or use the form where erase hands you the next valid iterator. In BFS this bug shows up as reading q.size() inside the same loop that pushes onto q. Save it first with int n=q.size(); before the inner loop. That is exactly why level-order traversal is written that way (Chapter 17).

7 · Copying a large object by value

Symptom: the answer is correct but the code times out, even though the complexity looks right on paper.

// WRONG — copies the whole graph at every level of the recursion
void dfs(int node,unordered_map<int,vector<int>> graph,vector<bool> visited)

// RIGHT — by reference, always
void dfs(int node,unordered_map<int,vector<int>> &graph,vector<bool> &visited)

Fix: pass every container by reference. That is exactly why the helper-plus-driver pattern in this course always uses & parameters. A missing ampersand turns an O(V+E) traversal into O(V·(V+E)). Worse, the caller never sees the visited updates, so the traversal quietly goes round in circles. One missing character causes a speed bug and a correctness bug at the same time.

8 · Wrong comparator

Symptom: a crash inside sort, or a min-heap that behaves like a max-heap.

// A comparator must be a STRICT weak ordering: comp(a,a) must be false.
// WRONG — <= on equal elements is undefined behaviour in std::sort
sort(v.begin(),v.end(),[](int a,int b){return a<=b;});

// priority_queue is a MAX-heap by default. For a min-heap:
priority_queue<pair<int,int>,vector<pair<int,int>>,
               greater<pair<int,int>>> pq;

// And the SORT KEY must come first in the pair — {distance, node},
// never {node, distance}.

Fix: use a strict <, and put the value you want to sort by first in the pair, so the default comparison (first item, then second) does what you want. For a priority_queue, remember the comparator is the other way round from sort: greater gives you a min-heap. Writing {node, distance} instead of {distance, node} in Dijkstra gives a believable but wrong shortest path.

Why is <= so dangerous? sort reads comp(a,b) as "a must come strictly before b". With <=, two equal values each claim to come before the other. Some versions of std::sort rely on that never happening, and use it to stop a scan without a bounds check. With a bad comparator the scan can run past the end of the array. So the result is not merely a wrong order. It can be a crash that only appears when the input has enough equal values.

9 · A greedy rule assumed rather than proved

Symptom: it passes every test you thought of, and fails one you did not.

// "Sort by duration and take the shortest" for interval scheduling — WRONG.
// Counterexample:  [0,10]  [9,11]  [10,20]
//   shortest-first takes [9,11] and blocks both others, total 1
//   earliest-END-first takes [0,10] and [10,20], total 2

Fix: for every greedy rule, either give the exchange argument in one sentence or find a counterexample. The fastest way to find one is a stress test against a brute force, which is the next section. If neither the proof nor the counterexample arrives within a minute, write the DP instead. It needs no proof beyond its recurrence.

10 · Unhandled edge cases

Symptom: a crash, or a nonsense result, on one hidden test.

// The usual suspects:
//   empty input; a single element; all elements equal
//   negative numbers (does your minimum start at 0?)
//   duplicates (does your set-based logic still count correctly?)
//   k larger than n; a target unreachable; a disconnected graph
//   a tree that is a single chain (recursion depth = n)
//   integer boundary values: 0, 1, -1, INT_MIN, INT_MAX

Fix: run the checklist below before calling anything finished. INT_MIN deserves a special mention. Both abs(INT_MIN) and -INT_MIN overflow, which breaks the x&-x trick and any comparison of absolute values on unrestricted input.

11 · Shadowed or reused loop variables

Symptom: an inner loop stops early, or an outer loop's index gets overwritten.

// WRONG — the inner loop destroys the outer i
for(int i=0;i<n;i++){
	while(i<n and check(i))i++;   // is this intentional?
}

// Also: a typo that compiles.
for(int j=0;j<m;i++)            // increments i, not j -> infinite loop

Fix: give the inner loop its own variable, and reread the increment part of every loop you write. This bug is boring and common. The wrong variable in the increment compiles cleanly and then hangs. People stare at the loop body instead of the header, which is why it takes so long to find.

12 · Operator precedence

Symptom: a branch is never taken, or it is always taken.

// WRONG — parses as x & (1==0), i.e. x & 0, i.e. always false
if(x&1==0)

// RIGHT
if((x&1)==0)

// Also worth parenthesising: shifts mixed with arithmetic, and any
// combination of ?: with other operators.

Fix: always put brackets around bitwise operations when you mix them with comparisons. The bitwise operators bind more loosely than ==, which is the opposite of what most people expect. The result is a branch that can never run, with no compile error to warn you.

Invariants: the technique that prevents most of this

✍️
My convention: one comment per loop, stating what is always true

Before writing a loop body, I write down what must be true at the start of every pass. Not what the loop does, but what is true:

// INVARIANT: every node in the queue is marked visited
// INVARIANT: st holds indices with strictly decreasing values
// INVARIANT: the answer, if any, lies in [low, high]
// INVARIANT: dp[0..i-1] are final and will not change
// INVARIANT: sum equals the total of nums[left..right]

Three reasons this pays off:

  • It shows you where the checks belong. "Every node in the queue is visited" tells you at once that the marking goes at the push.
  • It proves the loop finishes and is right. If [low, high] always contains the answer and always gets smaller, binary search must be correct.
  • It is easy to debug. Print the invariant, find the first pass where it is false, and that is where the bug is.

A loop whose invariant you cannot state is a loop you do not yet understand. Writing it down is usually faster than the debugging session it saves you.

An invariant at work. Find the first index whose value is at least 4 in [1, 3, 5, 7]. The invariant is "the answer is in [low, high]", starting with low = 0 and high = 4 (4 means "no such index").

  • low = 0, high = 4, mid = 2. a[2] = 5 ≥ 4, so index 2 could be the answer, but so could anything to its left. Set high = 2. The answer is still in [0, 2].
  • low = 0, high = 2, mid = 1. a[1] = 3 < 4, so index 1 and everything left of it is ruled out. Set low = 2. The answer is still in [2, 2].
  • low = high = 2. The range holds one index, so that must be the answer: index 2, value 5.

Now introduce the classic bug: write low = mid instead of low = mid + 1. With low = 1 and high = 2, mid = 1 again, low stays 1, and the loop never ends. The invariant tells you exactly what broke. "The range contains the answer" still holds, but "the range always gets smaller" does not. That is the half of the invariant to check whenever a loop hangs.

the stress-test harness — write this once, reuse foreverfinds bugs in seconds
// Three ingredients:
//   1. a brute force you are SURE is correct (slow is fine)
//   2. a random generator making SMALL inputs (n = 1..8, values -5..5)
//   3. a loop that stops at the first disagreement and prints the input
//
// Small inputs are the whole point: a failing case with n = 4 can be traced
// by hand, whereas one with n = 1000 tells you nothing.
int main(){
	srand(12345);                      // fixed seed -> reproducible failures

	for(int test=1;test<=100000;test++){
		int n=1+rand()%8;
		vector<int> nums(n);

		for(auto &x:nums)
		x=rand()%11-5;            // include negatives and zero

		int fast=mySolution(nums);
		int slow=bruteForce(nums);

		if(fast!=slow){
			cout<<"MISMATCH on test "<<test<<"\n";
			cout<<"input: ";

			for(auto &x:nums)
			cout<<x<<" ";

			cout<<"\nfast="<<fast<<" slow="<<slow<<"\n";

			return 0;               // stop at the FIRST failure
		}
	}

	cout<<"all tests passed\n";

	return 0;
}
These are the most valuable thirty lines in competitive programming. They also settle an argument about a greedy rule in ten seconds instead of ten minutes of staring. Four details matter:
  • Keep n tiny, so the counterexample is readable.
  • Include negative numbers, zeros and duplicates in the value range, because that is where the bugs hide.
  • Use a fixed seed, so the failure happens again when you rerun it.
  • Stop at the first mismatch instead of counting up failures.
If a problem has several valid answers, compare some property of the output (its length, its total, or whether it is valid) rather than the exact answer.

What a real run looks like. Say mySolution is a maximum-subarray-sum function that starts its answer at 0. The brute force tries every (start, end) pair, which is O(n³) but instant for n ≤ 8. Within a few tests the harness prints something like:

  • MISMATCH on test 3
  • input: -3 -1
  • fast=0 slow=-1

Two numbers, and the bug is obvious: when every value is negative, the best subarray is still negative, but an answer that starts at 0 can never go below 0. The fix is to start from nums[0]. You would probably never have typed "all negative" as a test by hand. The generator found it because its value range included negatives. mySolution and bruteForce are placeholders. For each problem you swap in your two functions and adjust the generator to make valid inputs, such as sorted arrays, connected graphs, or strings over a small alphabet like {a, b}.

    🔦
    Debugging without a debugger
    • Halve the search by printing. Print the state halfway through the algorithm. If it is already wrong, the bug is earlier. If it is right, the bug is later. Each print halves the area to search, which is binary search applied to your own code.
    • Print the invariant, not every variable. "sum should equal the window total" can be checked at a glance. A wall of numbers cannot.
    • Shrink the failing input. Keep removing elements while it still fails. A 3-element counterexample can be understood. A 1000-element one cannot.
    • Run the brute force on the same input and print both sets of intermediate values side by side. The first place they differ is the bug.
    • Explain the invariant out loud, even to an empty room. Half of all bugs turn up while you explain why the code should work. That is exactly why interviewers ask you to talk as you go.
    • Reread the loop headers. The wrong variable in an increment is invisible if you only study the body.
    • Check your assumptions against the problem statement. Is it really sorted? Are the values really all different? Many bugs are misreadings, not mistakes.

    When you practise at home, let the compiler help. Several of the twelve bug classes can be caught for you automatically:

    • -Wall -Wextra -Wshadow are warning flags. They catch an inner loop that declares the same name as the outer one (one form of bug 11), a comparison between signed and unsigned numbers (the v.size()-1 trap), and some precedence mistakes (bug 12).
    • -fsanitize=address,undefined checks the program while it runs. It stops with a clear message at the exact line where you read outside an array, use memory that has been freed, or overflow a signed integer (bug 3). Without it, those bugs just give quietly wrong output.
    • -D_GLIBCXX_DEBUG (with GCC) makes vector check every index and makes iterators check that they are still valid, which catches bug 6.

    These make the program slower, so use them to debug, not to submit. For debug prints, write to cerr instead of cout. Most online judges only read standard output, so a stray cerr line will not turn a correct answer into a wrong one.

    🎤
    In an interview, debugging is a visible skill

    There is no debugger and no test harness, so what is being judged is your method. Walk through your code on the sample input by hand, out loud, before saying you are done, and walk through n = 1 too. When a bug turns up, do not scan the code in silence. Say what you expected at that point and what you actually got, then narrow it down. When you finish writing, offer the edge cases you would test instead of waiting to be asked. That habit reads as engineering maturity, and it costs thirty seconds.

    Tips & tricks

    The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

    💡 ONE INVARIANT PER LOOP
    Write what is always true at the top of the loop. It settles where guards go, proves termination, and gives you one thing to print when it breaks.
    💡 STRESS TEST
    Brute force, tiny random inputs (n ≤ 8, with negatives and duplicates), fixed seed, stop at the first mismatch. Thirty lines that settle a greedy argument in seconds.
    ⛔ TRACE n = 1
    Walk your actual code on n = 1 and n = 2 before declaring it done. That catches nearly every off-by-one in twenty seconds.
    ⚠️
    Common mistakes when debugging
    • Changing code at random until the test passes. You have hidden the symptom and kept the bug.
    • Not making the failure happen reliably first. Without a repeatable failure, you cannot tell whether you fixed anything.
    • Debugging on a large input. Shrink it first. The cause is far easier to see at n = 3.
    • Assuming the library is wrong. It is your comparator, or your assumption about how the container behaves.
    • Fixing the first thing you find without checking whether it explains the whole symptom.
    • Trusting a test you never ran. Check the brute force itself against the provided sample.
    • Stress-testing with large random inputs, which produces counterexamples nobody can read.
    • Using a random generator with no seed, or one seeded from the clock, so the failure never happens again.
    • Comparing exact output when several answers are valid. Compare a property of the answer instead.
    • Forgetting to remove debug prints before submitting.
    🎤
    Interview drill

    Warm-up: "Your BFS returns the correct answer but times out on a dense graph." Diagnose it.

    How a strong answer sounds
    Correct but slow, and specifically on a graph with many edges, points almost straight at the visited marking. The classic mistake is marking a node visited when it is taken out of the queue rather than when it is put in.

    Here is what goes wrong. If several nodes point to the same node, each of them sees it as unvisited and pushes it. So that node enters the queue once per incoming edge, before any copy is processed. The answer is still right, because the first copy taken out carries the shortest distance and the later copies are then skipped. That is exactly why this bug survives testing. But the queue grows with the number of edges, and on a dense graph that means O(V²) pushes instead of O(V).

    The fix is moving one line: mark the node visited at the moment you push it. The way I keep this straight is to say the loop invariant out loud, "every node currently in the queue is already marked visited". Once that sentence exists, there is only one place the marking can go.

    While I am there I would check two related things. First, that the graph is passed by reference. A missing ampersand copies the whole adjacency structure on every call, and it also hides the visited updates from the caller. Second, if this is a level-order traversal, that q.size() is saved into a local variable before the inner loop rather than read inside it, since the loop itself pushes onto the queue.

    Deeper: "You believe your greedy solution is optimal but you are not certain. You have ten minutes." What do you do?

    How a strong answer sounds
    I would spend the first minute trying to prove it, because a proof is worth more than any amount of testing. The standard tool is an exchange argument. Assume the best possible solution differs from the greedy one. Take the first place they differ, and show you can swap the other choice for the greedy one without making the solution worse. If that works in a sentence, I am done, and I say so.

    If it does not, I stop staring at it and go looking for a counterexample. The fastest way is a stress test. I write a brute force I am sure of, usually trying every possibility, since being correct matters far more than being fast there. Then I write a generator that makes deliberately small inputs: n between 1 and 8, with values that include negatives, zero and duplicates. I loop, compare the two answers, and stop at the first disagreement, printing the input.

    Small inputs are the whole point. A failing case with four elements I can trace by hand. A thousand-element one tells me nothing. I use a fixed seed so the failure happens again when I rerun it. In practice, if a counterexample exists this finds one within a few thousand tries, which takes under a second. If it finds nothing, that at least builds confidence.

    Finding a counterexample teaches me something concrete: the greedy rule is wrong, and the failing case usually shows me why. That often points to the correct rule, or tells me to write the DP instead. If I find nothing after a hundred thousand tests, I would say honestly that I have strong evidence but not a proof, and name what still needs proving.

    One warning about the harness. If the problem allows several valid answers, compare a property of the answer (its length, its total, or whether it is valid) rather than the exact output. Otherwise you will chase mismatches that are not really bugs.

    🧠 Key takeaways

    • Most bugs are silent: the code runs and the number looks believable. Start from the symptom, not from the top of the file.
    • Mark nodes visited when you add them to the queue. Never do maths on a placeholder value. Pass containers by reference. Put brackets around bitwise operations.
    • Write one invariant per loop. It tells you where the checks go, proves the loop ends correctly, and gives you one thing to print.
    • A stress test (brute force, tiny random inputs, stop at the first mismatch) finds counterexamples in seconds.
    • Walk through n = 1 and n = 2 by hand before calling anything finished. That catches nearly every off-by-one.

    Check your understanding

    Your BFS gives the right answer but is far too slow on dense graphs. The most likely cause is…

    The answer stays correct, because the first copy taken out of the queue carries the shortest distance. That is why this bug survives testing. The invariant "every node in the queue is already visited" leaves only one place for the marking.

    Your DP is correct on small inputs and returns a large negative number on big ones. Look first at…

    Both wrap round to a negative value, which then looks like an excellent answer and spreads through the table. Check placeholder values before using them, and write 1LL*a*b.

    A recursion is correct, but becomes wrong once you add memoisation. Why?

    The test is simple: if two calls sharing a key could correctly return different answers, the key is missing something. Add the missing dimension.

    What makes a stress test effective?

    A counterexample you cannot read is nearly useless. Small inputs can be traced by hand, a fixed seed makes the failure happen again, and the first mismatch is the one to study.

    What is the practical value of writing a loop invariant as a comment?

    "Every node in the queue is visited" immediately tells you where the marking goes. And a loop whose invariant you cannot state is one you do not yet fully understand.
