Debugging & Correctness

Almost every wrong answer you will write falls into about a dozen categories, and most of them are silent — the code compiles, runs, and produces a plausible number. This chapter is the catalogue, the invariant discipline that prevents most of it, and the stress-testing technique that finds the rest in under a minute.

  • Recognise the twelve recurring bug classes by their symptom
  • State an invariant per loop, and use it to locate a fault by bisection
  • Write a stress test that finds a counterexample automatically
  • Build the edge-case checklist into a habit
  • Debug without a debugger, which is what an interview requires

Symptom → likely cause

Start from what you observe. The symptom narrows the cause far faster than reading the code from the top.

The twelve bug classes

1 · Marking visited at the wrong time in BFS

Symptom: correct answer but far too slow, or duplicate nodes in the output; on a dense graph it degenerates to exponential work.

// WRONG — marks the node when it is DEQUEUED
while(!q.empty()){
	int node=q.front();

	q.pop();
	visited[node]=true;              // too late!

	for(auto &neighbour:graph[node]){
		if(!visited[neighbour])q.push(neighbour);
	}
}

Fix: mark when you enqueue, not when you dequeue. Otherwise a node with several unvisited predecessors is pushed once per predecessor before any of those copies is processed, so the queue fills with duplicates. The invariant to hold is "every node in the queue is already marked visited" — state it, and the placement becomes obvious. This is the single most common graph bug there is, and it is silent: the answer is still right.

2 · Arithmetic on a sentinel

Symptom: a huge negative number, or an impossibly good answer that then propagates everywhere.

// WRONG — dist[node] may still be INT_MAX
if(dist[node]+weight<dist[neighbour])   // INT_MAX + weight overflows
dist[neighbour]=dist[node]+weight;

// RIGHT — refuse to relax from an unreached node
if(dist[node]==INT_MAX)continue;

if(dist[node]+weight<dist[neighbour])
dist[neighbour]=dist[node]+weight;

Fix: guard before every relaxation, or use a sentinel with headroom such as 1e18 in a long long so that adding a weight cannot wrap. The same class covers INT_MIN in maximisation problems and INT_MAX initialisers in DP tables. Signed overflow is undefined behaviour, so the compiler is entitled to do anything — including optimising your guard away if you write it as a+b < a.

3 · int where the value needs 64 bits

Symptom: exactly right on small tests, wrong on large ones, often negative.

// WRONG — the multiplication happens in int, THEN widens
long long product=a*b;            // a,b are int near 1e9 -> already wrapped

// RIGHT
long long product=1LL*a*b;

// Places this bites: sums of 1e5 values each up to 1e9 (1e14);
// products under a modulus (1e18); path counts; subtree sums;
// (low+high)/2 in binary search when both are near INT_MAX.

Fix: estimate the maximum value before choosing the type. int holds about 2·10⁹; long long about 9·10¹⁸. When in doubt under a modulus, make everything long long. And write the binary-search midpoint as low + (high-low)/2, which cannot overflow.

4 · An incomplete memo key

Symptom: the recursion is correct, adding memoisation makes it wrong.

// WRONG — the state includes `remaining`, but the key does not
int solve(int i,int remaining,vector<int> &memo){
	if(memo[i]!=-1)return memo[i];      // two different `remaining`
	                                    // values collide here
	// ...
	return memo[i]=ans;
}

Fix: the memo key must contain every parameter the answer depends on, and nothing that it does not. The test is mechanical: if two calls with the same key could legitimately return different answers, the key is incomplete. Note the reverse error too — including a parameter that does not affect the answer merely wastes memory, but including the accumulated value so far (rather than what remains) usually means the state is not a state at all.

5 · Off-by-one in a loop bound or an index shift

Symptom: wrong by one, or an out-of-range access on the last element.

// The four questions to ask of every loop:
//   Does it start at 0 or 1?
//   Is the end < n or <= n?
//   Does the body read i+1 or i-1? Then the bound must shrink.
//   In a 1-indexed DP over a 0-indexed array, is it s[i-1]?

for(int i=0;i<n-1;i++)     // correct when the body reads a[i+1]
for(int i=1;i<=n;i++)      // correct for a 1-indexed dp of size n+1

Fix: trace n = 1 and n = 2 by hand. Nearly every off-by-one reveals itself at those two sizes, and it takes twenty seconds. For string DP, write the state sentence first — "the first i characters" — and the i-1 indexing follows from it rather than from guesswork (Chapter 41).

6 · Modifying a container while iterating it

Symptom: a crash, or silently skipped elements; often works in one compiler and not another.

// WRONG — push_back may reallocate, invalidating the iterator
for(auto &x:values){
	if(check(x))values.push_back(x*2);
}

// WRONG — erase invalidates `it`
for(auto it=m.begin();it!=m.end();it++){
	if(it->second==0)m.erase(it);
}

// RIGHT — erase returns the next valid iterator
for(auto it=m.begin();it!=m.end();){
	if(it->second==0)it=m.erase(it);
	else it++;
}

Fix: collect what you intend to change, then apply it after the loop; or use the erase-returns-next-iterator form. In BFS this appears as reading q.size() inside the loop that pushes to q — capture int n=q.size(); before the inner loop, which is exactly why level-order traversal is written that way (Chapter 17).

7 · Copying a large object by value

Symptom: correct but times out; the complexity looks right on paper.

// WRONG — copies the whole graph at every level of the recursion
void dfs(int node,unordered_map<int,vector<int>> graph,vector<bool> visited)

// RIGHT — by reference, always
void dfs(int node,unordered_map<int,vector<int>> &graph,vector<bool> &visited)

Fix: pass every container by reference. This is precisely why the helper-plus-driver pattern in this course always takes & parameters: a missing ampersand turns an O(V+E) traversal into O(V·(V+E)) and, worse, makes the visited updates invisible to the caller, so the traversal silently loops. One missing character causes both a performance bug and a correctness bug at once.

8 · Wrong comparator

Symptom: a crash inside sort, or a min-heap behaving like a max-heap.

// A comparator must be a STRICT weak ordering: comp(a,a) must be false.
// WRONG — <= on equal elements is undefined behaviour in std::sort
sort(v.begin(),v.end(),[](int a,int b){return a<=b;});

// priority_queue is a MAX-heap by default. For a min-heap:
priority_queue<pair<int,int>,vector<pair<int,int>>,
               greater<pair<int,int>>> pq;

// And the SORT KEY must come first in the pair — {distance, node},
// never {node, distance}.

Fix: use strict <, and put the sort key first in a pair so the default lexicographic comparison does what you want. For a priority_queue, remember that the comparator is inverted relative to sort: greater gives a min-heap. Getting {node, distance} the wrong way round in Dijkstra produces a plausible but wrong shortest path.

9 · A greedy rule assumed rather than proved

Symptom: passes every test you thought of, fails one you did not.

// "Sort by duration and take the shortest" for interval scheduling — WRONG.
// Counterexample:  [0,10]  [9,11]  [10,20]
//   shortest-first takes [9,11] and blocks both others, total 1
//   earliest-END-first takes [0,10] and [10,20], total 2

Fix: for every greedy rule, either give the exchange argument in a sentence or find the counterexample. The fastest way to find one is a stress test against a brute force, which is the next section. If neither the proof nor the counterexample comes within a minute, write the DP — it needs no proof beyond its recurrence.

10 · Unhandled edge cases

Symptom: a crash or a nonsense result on one hidden test.

// The usual suspects:
//   empty input; a single element; all elements equal
//   negative numbers (does your minimum start at 0?)
//   duplicates (does your set-based logic still count correctly?)
//   k larger than n; a target unreachable; a disconnected graph
//   a tree that is a single chain (recursion depth = n)
//   integer boundary values: 0, 1, -1, INT_MIN, INT_MAX

Fix: run the checklist below before declaring anything finished. INT_MIN deserves special mention: abs(INT_MIN) and -INT_MIN both overflow, which breaks the x&-x idiom and any absolute-value comparison on arbitrary input.

11 · Shadowed or reused loop variables

Symptom: an inner loop terminates early, or an outer index is clobbered.

// WRONG — the inner loop destroys the outer i
for(int i=0;i<n;i++){
	while(i<n and check(i))i++;   // is this intentional?
}

// Also: a typo that compiles.
for(int j=0;j<m;i++)            // increments i, not j -> infinite loop

Fix: give the inner loop its own variable, and reread the increment of every loop you write. This class is boring and it is common — a wrong variable in the increment clause compiles cleanly and hangs, and staring at the loop body rather than the header is why it takes so long to find.

12 · Operator precedence

Symptom: a branch is never taken, or is always taken.

// WRONG — parses as x & (1==0), i.e. x & 0, i.e. always false
if(x&1==0)

// RIGHT
if((x&1)==0)

// Also worth parenthesising: shifts mixed with arithmetic, and any
// combination of ?: with other operators.

Fix: parenthesise bitwise operations mixed with comparisons, always. The bitwise operators bind looser than ==, which is the opposite of most people's intuition and produces a silently unreachable branch rather than a compile error.

Invariants: the technique that prevents most of this

✍️
My convention: one comment per loop, stating what is always true

Before writing a loop body I write what must hold at the top of every iteration. Not what the loop does — what is true:

// INVARIANT: every node in the queue is marked visited
// INVARIANT: st holds indices with strictly decreasing values
// INVARIANT: the answer, if any, lies in [low, high]
// INVARIANT: dp[0..i-1] are final and will not change
// INVARIANT: sum equals the total of nums[left..right]

Three reasons this earns its keep. It makes the guard placement obvious — "every node in the queue is visited" tells you at once that marking belongs at the push. It is the termination argument — if [low, high] always contains the answer and always shrinks, binary search must be correct. And it is debuggable: print the invariant and find the first iteration where it fails, which is precisely where the bug is. A loop whose invariant you cannot state is a loop you do not yet understand, and writing it out is usually faster than the debugging session it replaces.

the stress-test harness — write this once, reuse foreverfinds bugs in seconds
// Three ingredients:
//   1. a brute force you are SURE is correct (slow is fine)
//   2. a random generator making SMALL inputs (n = 1..8, values -5..5)
//   3. a loop that stops at the first disagreement and prints the input
//
// Small inputs are the whole point: a failing case with n = 4 can be traced
// by hand, whereas one with n = 1000 tells you nothing.
int main(){
	srand(12345);                      // fixed seed -> reproducible failures

	for(int test=1;test<=100000;test++){
		int n=1+rand()%8;
		vector<int> nums(n);

		for(auto &x:nums)
		x=rand()%11-5;            // include negatives and zero

		int fast=mySolution(nums);
		int slow=bruteForce(nums);

		if(fast!=slow){
			cout<<"MISMATCH on test "<<test<<"\n";
			cout<<"input: ";

			for(auto &x:nums)
			cout<<x<<" ";

			cout<<"\nfast="<<fast<<" slow="<<slow<<"\n";

			return 0;               // stop at the FIRST failure
		}
	}

	cout<<"all tests passed\n";

	return 0;
}
This is the highest-value thirty lines in competitive programming, and it is also how you settle a greedy argument in ten seconds instead of ten minutes of staring. Four details that matter: keep n tiny so the counterexample is readable; include negatives, zeros and duplicates in the value range, since those are where the bugs are; use a fixed seed so a failure reproduces; and stop at the first mismatch rather than counting failures. For problems with multiple valid outputs, compare a property (the length, the sum, validity) rather than the exact answer.

    🔦
    Debugging without a debugger
    • Bisect by printing. Print the state at the midpoint of the algorithm. If it is already wrong, the bug is before; if right, after. Each print halves the search space — the same logic as binary search, applied to code.
    • Print the invariant, not the variables. "sum should equal the window total" is checkable at a glance; a wall of numbers is not.
    • Shrink the failing input. Remove elements while it still fails. A 3-element counterexample is understandable; a 1000-element one is not.
    • Compare against the brute force on the same input, printing both intermediate states side by side. The first divergence is the bug.
    • Rubber-duck the invariant aloud. Half of all bugs surface while explaining why the code should work — which is exactly why interviewers ask you to narrate.
    • Reread the loop headers. A wrong variable in an increment clause is invisible when you only study the body.
    • Check your assumptions against the statement. "Sorted" — really? "Distinct" — really? Many bugs are misreadings rather than mistakes.
    🎤
    In an interview, debugging is a visible skill

    There is no debugger and no test harness, so what is being assessed is your method. Trace your code on the sample input by hand, out loud, before saying you are done — and trace n = 1 as well. When a bug appears, do not silently scan the code: say what you expect at that point and what you actually see, then narrow it down. And when you finish writing, volunteer the edge cases you would test rather than waiting to be asked. That habit reads as engineering maturity, and it costs thirty seconds.

    Tips & tricks

    The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

    💡 ONE INVARIANT PER LOOP
    Write what is always true at the top of the loop. It settles where guards go, proves termination, and gives you one thing to print when it breaks.
    💡 STRESS TEST
    Brute force, tiny random inputs (n ≤ 8, with negatives and duplicates), fixed seed, stop at the first mismatch. Thirty lines that settle a greedy argument in seconds.
    ⛔ TRACE n = 1
    Walk your actual code on n = 1 and n = 2 before declaring it done. That catches nearly every off-by-one in twenty seconds.
    ⚠️
    Common mistakes when debugging
    • Changing code randomly until the test passes. You have then fixed the symptom and kept the bug.
    • Not reproducing the failure first. Without a reliable repro you cannot know whether you fixed anything.
    • Debugging on a large input. Shrink it first; the cause is far easier to see at n = 3.
    • Assuming the library is wrong. It is your comparator, or your assumption about the container.
    • Fixing the first thing you find without checking whether it explains the whole symptom.
    • Trusting a test that never ran. Verify the brute force itself on the provided sample.
    • Stress-testing with large random inputs, producing counterexamples nobody can read.
    • Using an unseeded or time-seeded random generator, so the failure never reproduces.
    • Comparing exact output when several answers are valid — compare a property instead.
    • Forgetting to remove debug prints before submitting.
    🎤
    Interview drill

    Warm-up: "Your BFS returns the correct answer but times out on a dense graph." Diagnose it.

    How a strong answer sounds
    Correct but slow, on a dense graph specifically, points almost immediately at the visited marking. The classic error is marking a node visited when it is dequeued rather than when it is enqueued. The consequence: if a node has several unvisited predecessors, each of them sees it as unvisited and pushes it, so the same node enters the queue once per incoming edge before any copy is processed. The answer still comes out right, because the first copy to be dequeued carries the shortest distance and later copies are then skipped — which is exactly why it is such a durable bug. But the queue length blows up with the edge count, and on a dense graph that is O(V²) pushes instead of O(V). The fix is one line moved: mark visited at the moment of pushing. The way I keep this straight is to state the loop invariant explicitly — "every node currently in the queue is already marked visited" — because once that sentence exists, the correct placement of the marking is forced. I would also check two related things while I am there: that the graph is passed by reference, since a missing ampersand copies the whole adjacency structure at every call and also makes visited updates invisible to the caller; and, if this is a level-order traversal, that q.size() is captured into a local before the inner loop rather than read inside it, since the loop itself pushes to the queue.

    Deeper: "You believe your greedy solution is optimal but you are not certain. You have ten minutes." What do you do?

    How a strong answer sounds
    I would spend the first minute trying to prove it, because a proof is worth more than any amount of testing. The standard tool is an exchange argument: assume an optimal solution differs from the greedy one, take the first point of difference, and show you can swap the optimal choice for the greedy one without making the solution worse. If that goes through in a sentence, I am done and I say so. If it does not, I do not keep staring at it — I go looking for a counterexample, and the fastest way is a stress test. I write a brute force I am certain of, usually exhaustive enumeration since correctness matters far more than speed there, plus a generator producing deliberately small inputs: n between 1 and 8, values in a range that includes negatives, zero and duplicates. Then I loop, comparing the two, and stop at the first disagreement, printing the input. Small inputs are the entire point — a failing case with four elements I can trace by hand, whereas a thousand-element one tells me nothing. I use a fixed seed so the failure reproduces. In practice this finds a counterexample within a few thousand iterations if one exists, which takes under a second, and it also builds confidence if it does not. If I do find a counterexample, I have learned something concrete: the greedy rule is wrong, and usually the failing case shows me why, which often suggests the correct rule or tells me to write the DP instead. If I find nothing after a hundred thousand tests I would say honestly that I have strong empirical evidence but not a proof, and name the proof obligation. One caveat on the harness: if the problem admits several valid answers, I compare a property — the length, the total, or a validity check — rather than the exact output, or I will chase phantom mismatches.

    🧠 Key takeaways

    • Most bugs are silent: the code runs and the number looks plausible. Start from the symptom, not the top of the file.
    • Mark visited on enqueue; never do arithmetic on a sentinel; pass containers by reference; parenthesise bitwise operations.
    • State one invariant per loop. It settles guard placement, proves termination, and gives you something to print.
    • A stress test — brute force, tiny random inputs, stop at the first mismatch — finds counterexamples in seconds.
    • Trace n = 1 and n = 2 by hand before declaring anything finished; that catches nearly every off-by-one.

    Check your understanding

    Your BFS gives the right answer but is far too slow on dense graphs. The most likely cause is…

    The answer stays correct because the first copy dequeued carries the shortest distance — which is why this bug survives testing. The invariant "every node in the queue is already visited" forces the correct placement.

    Your DP is correct on small inputs and returns a large negative number on big ones. Look first at…

    Both produce a wrapped negative value that then looks like an excellent answer and propagates. Guard sentinels before use, and write 1LL*a*b.

    A recursion is correct, but becomes wrong once you add memoisation. Why?

    The mechanical test: if two calls sharing a key could legitimately return different answers, the key is incomplete. Add the missing dimension.

    What makes a stress test effective?

    A counterexample you cannot read is nearly useless. Small inputs are traceable by hand, a fixed seed makes the failure reproducible, and the first mismatch is the one to study.

    What is the practical value of writing a loop invariant as a comment?

    "Every node in the queue is visited" immediately places the marking. And a loop whose invariant you cannot state is one you do not yet fully understand.
