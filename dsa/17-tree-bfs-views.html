Level Order, ZigZag, Vertical & Views

This chapter shows the main idea of the whole course in action. Six accepted solutions, one loop. Level order, zigzag, the left view and the right view are the same BFS (breadth-first search: visit the tree one level at a time, using a queue). Only one line changes, right after the inner loop. The two vertical problems use the same loop too, with a column number attached to each node. Learn the skeleton once, learn which line changes, and you can solve six problems instead of one.

  • Write the BFS skeleton that knows where each level ends, and explain why saving the queue size first matters so much
  • Derive zigzag, left view and right view by changing one line each
  • Give each node a column number (its horizontal distance) for top view, bottom view and vertical order
  • Get the vertical-order tie-break rule right (which node comes first when two share a spot) — this is the hard part
  • Pick BFS or DFS by reading what the question asks for

The skeleton

Why a queue gives you levels: the queue is first in, first out. You put the root in, and each time you take a node out you put its children at the back. So all the nodes of one level are taken out before any node of the next level, because the next level's nodes were added behind them. That is what “breadth-first” means: finish the whole row before going deeper.

Here is one loop. Every problem in this chapter is a small change to it.

the level-order skeleton — memorise thisO(n)O(w)
void LevelOrder(TreeNode* root){
	if(!root)return;

	vector<vector<int>> ans;
	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		int n=q.size();            // THE load-bearing line
		vector<int> level;

		for(int i=0;i<n;i++){
			TreeNode* node=q.front();
			level.push_back(node->val);
			q.pop();

			if(node->left)q.push(node->left);
			if(node->right)q.push(node->right);
		}

		ans.push_back(level);      // <-- the ONLY line that varies
	}
}
int n=q.size() is the whole idea. You save the size before the inner loop starts. At that moment the queue holds this level and nothing else, so this saved number is exactly the number of nodes on this level. Every child you push inside the loop belongs to the next level, and the saved count correctly leaves it out. If you write for(int i=0;i<q.size();i++) instead, the loop keeps reading the size of a queue that is growing. It eats into the next level, the levels merge into one, and every problem in this chapter breaks without any error.

The running example for this chapter: root 1, with children 2 (left) and 3 (right). Node 2 has children 4 and 5. Node 3 has only a right child, 6. Here is the skeleton on it, round by round:

RoundQueue at startSaved nPops (and pushes)level
1111 (push 2, 3)[1]
22 322 (push 4, 5), 3 (push 6)[2, 3]
34 5 634, 5, 6 (no children)[4, 5, 6]

Now the bug, on round 2 with i < q.size(). The queue starts as 2 3. At i = 0, pop 2 and push 4, 5: size is now 3. At i = 1, pop 3 and push 6: size is still 3. At i = 2, 2 < 3, so it pops 4 as well. At i = 3 the size is 2 and the loop stops. The level comes out as [2, 3, 4]: node 4 has been pulled up a level, and no error tells you.

The four level-based variants

Save the whole level. This is the starting version.

void ZigZag(TreeNode* root){
	if(!root)return;

	vector<vector<int>> ans;
	int counter=0;
	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		int n=q.size();
		vector<int> level;
		for(int i=0;i<n;i++){
			TreeNode* node=q.front();
			level.push_back(node->val);
			q.pop();

			if(node->left)q.push(node->left);
			if(node->right)q.push(node->right);
		}
		if(counter%2!=0)
		reverse(level.begin(),level.end());
		ans.push_back(level);
		counter++;
	}
}

Reverse the odd-numbered levels before saving them. Do not try to change the direction of the traversal itself. Collect each level normally, then reverse the vector you collected. That costs O(n) in total and is hard to get wrong.

vector<int> LeftView(TreeNode* root){
	if(!root)return {};

	vector<int> result;
	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		int n=q.size();
		vector<int> level;
		for(int i=0;i<n;i++){
			TreeNode* node=q.front();
			level.push_back(node->val);
			q.pop();

			if(node->left)q.push(node->left);
			if(node->right)q.push(node->right);
		}
		result.push_back(level[0]);
	}

	return result;
}

Take the first node of each level. This is safe because level is never empty. The queue was not empty when the level started, so n ≥ 1.

vector<int> RightView(TreeNode* root){
	if(!root)return {};

	vector<int> result;
	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		int n=q.size();
		vector<int> level;
		for(int i=0;i<n;i++){
			TreeNode* node=q.front();
			level.push_back(node->val);
			q.pop();

			if(node->left)q.push(node->left);
			if(node->right)q.push(node->right);
		}
		result.push_back(level[level.size()-1]);
	}

	return result;
}

Take the last node of each level. Only the index differs from the left view. level.back() would also work.

On the running example the levels are [1], [2, 3], [4, 5, 6], so:

  • Level order: [[1], [2, 3], [4, 5, 6]].
  • ZigZag: [[1], [3, 2], [4, 5, 6]]. Only level 1 (the second level, counting from 0) is reversed.
  • Left view: [1, 2, 4], the first node of each level.
  • Right view: [1, 3, 6], the last node of each level.

An edge case that catches people: the left view is not “keep following left pointers”. Remove 4 and 5 from the example. Now level 2 is just [6], and 6 is a right child, yet it is the leftmost node you can see on that level. The left view becomes [1, 2, 6]. Following left pointers would stop at 2 and miss it. Taking level[0] handles this with no extra thought.

✍️
My convention: keep the whole level vector even when you only want one element

The left and right views only need one value per level. So you could track it with a flag inside the loop and never build level. Don't. If the body stays the same, all four functions are clearly the same code, and you remember one thing instead of four. The cost is one extra vector of size O(w) (w = the widest level), and BFS already uses that much space for its queue. Removing the shared shape saves nothing you could measure, and you lose the pattern. Code you can recognise at a glance is worth keeping.

The vertical family: attach a coordinate

Top view, bottom view and vertical order are not about levels. They are about columns. Give each node a horizontal distance (hd), which is its column number. The root gets 0. A left child gets its parent's hd−1 and a right child gets hd+1. Then the only question is what to keep for each column.

ProblemPer column, keep…So the map update is…
Top viewThe first node seen (shallowest)Insert only if the column is not in the map yet
Bottom viewThe last node seen (deepest)Always overwrite
Vertical orderAll nodes, sorted by depth then by the tie-break ruleAppend, then sort within the column

On the running example, the columns are: 1 → 0, 2 → −1, 3 → +1, 4 → −2, 5 → 0 (it is the right child of 2, so −1 + 1), and 6 → +2. Grouped left to right:

  • column −2: 4 · column −1: 2 · column 0: 1, 5 (1 at depth 0, 5 at depth 2) · column +1: 3 · column +2: 6
  • Top view keeps the shallowest per column: [4, 2, 1, 3, 6]. Node 5 is hidden behind 1.
  • Bottom view keeps the deepest per column: [4, 2, 5, 3, 6]. Now 5 hides 1.
  • Vertical order keeps everything: [[4], [2], [1, 5], [3], [6]].

Notice that nodes from different branches can share a column: 5 sits under the root even though it hangs off 2. That is why you cannot answer these questions by looking at one branch at a time.

🗺️
Why map and not unordered_map for the columns

The output must list columns from left to right, and columns on the left have negative numbers. A map<int,...> (a sorted map) always walks its keys from smallest to largest, so the final loop just goes through it in order. With unordered_map (a hash map, which has no order) you would have to collect the keys and sort them yourself. That is extra code for no gain, because there are only a few columns. This is the one place in the course where map is both clearer and less work than unordered_map. It is Chapter 9's rule from the other side: when you need order, order is what you pay for.

// BFS guarantees we meet shallower nodes first, so the FIRST node we see
// in a column is the one visible from above.
vector<int> topView(TreeNode* root){
	if(!root)return {};

	map<int,TreeNode*> colmap;
	queue<pair<int,TreeNode*>> q;
	q.push({0,root});

	while(!q.empty()){
		int level=q.front().first;      // horizontal distance
		TreeNode* node=q.front().second;
		q.pop();

		if(colmap.find(level)==colmap.end())
		colmap[level]=node;                // first only

		if(node->left)q.push({level-1,node->left});
		if(node->right)q.push({level+1,node->right});
	}

	vector<int> result;
	for(auto &it:colmap)
	result.push_back(it.second->val);

	return result;
}

This must be BFS, not DFS (depth-first search, which goes deep down one branch before trying the next). A DFS can reach a deep node on the left before a shallow node on the right in the same column, and it would save the wrong one. BFS visits shallow nodes first, and that is exactly what makes this work.

// Identical, except we always overwrite — so the LAST node seen wins,
// and BFS means the last is the deepest.
vector<int> bottomView(TreeNode* root){
	if(!root)return {};

	map<int,TreeNode*> colmap;
	queue<pair<int,TreeNode*>> q;
	q.push({0,root});

	while(!q.empty()){
		int level=q.front().first;
		TreeNode* node=q.front().second;
		q.pop();

		colmap[level]=node;                // always overwrite

		if(node->left)q.push({level-1,node->left});
		if(node->right)q.push({level+1,node->right});
	}

	vector<int> result;
	for(auto &it:colmap)
	result.push_back(it.second->val);

	return result;
}

Only one line differs from the top view. The find check is gone and we always assign. This is the same reuse-the-skeleton idea as the four level variants.

// Vertical order keeps EVERY node per column, ordered by depth,
// with ties broken by value (that is this problem's stated rule).
// Two DFS passes record the two coordinates, then we sort inside each column.
void Rows(TreeNode* root,int level,unordered_map<TreeNode*,int> &rows){
	if(!root)return;

	rows[root]=level;

	Rows(root->left,level+1,rows);
	Rows(root->right,level+1,rows);
}
void Cols(TreeNode* root,int level,map<int,vector<TreeNode*>> &cols){
	if(!root)return;

	cols[level].push_back(root);

	Cols(root->left,level-1,cols);
	Cols(root->right,level+1,cols);
}
bool compare(const pair<int,int> &a,const pair<int,int> &b){
	if(a.first==b.first)
	return a.second<b.second;   // same depth -> smaller value first

	return a.first<b.first;         // otherwise shallower first
}
vector<vector<int>> VerticalOrder(TreeNode* root){
	if(!root)return {};

	unordered_map<TreeNode*,int> rows;
	map<int,vector<TreeNode*>> cols;

	Rows(root,0,rows);
	Cols(root,0,cols);

	vector<vector<int>> ans;
	for(auto &it:cols){
		vector<pair<int,int>> temp;
		for(TreeNode* node:it.second)
		temp.push_back({rows[node],node->val});

		sort(temp.begin(),temp.end(),compare);

		vector<int> v;
		for(auto &[level,nodeval]:temp)
		v.push_back(nodeval);

		ans.push_back(v);
	}

	return ans;
}

The compare function is the whole problem. Sort by depth first, then by value. That is the multi-key comparator pattern from Chapter 8. If you get it right, your answer is correct. If you get it wrong, it passes the sample and fails on a tie.

⚖️
The vertical-order tie-break is the entire difficulty — and it varies by problem

Two nodes can be in the same column and at the same depth. Different problems decide their order in different ways, so read the problem statement:

  • Tie broken by value (the common LeetCode version). Sort by (depth, value). That is exactly the compare function above.
  • Tie broken by left-to-right BFS order. Then you don't need to sort at all, because level order already gives you that order. Just append during BFS.

The DFS-plus-sort version writes the rule down in a comparator. So it can handle either rule by changing one function. The one-pass BFS version is shorter, but it quietly assumes the second rule. When the problem states a tie-break, write it as a comparator. Don't let it depend on the order your traversal happens to visit nodes.

See the two rules disagree. Give node 3 in the running example a left child with value 0. Its column is 1 − 1 = 0 and its depth is 2, exactly the same spot as node 5. Column 0 now holds 1 (depth 0), 5 (depth 2) and 0 (depth 2). Tie broken by value: [1, 0, 5]. Tie broken by BFS order: 5 is visited before 0, because 2 comes before 3, so [1, 5, 0]. Same tree, two different correct answers, depending only on the problem statement. The same question arises for the bottom view: when two nodes share the deepest spot in a column, “always overwrite” keeps the one BFS visits last, the rightmost. Check that the problem wants that.

DFS + explicit sort

Two passes over the tree, then a sort inside each column. O(n log n) overall. The tie-break rule lives in a named compare function, so it is easy to see and easy to change. Use this when the problem states a tie-break.

One-pass BFS
// Shorter, O(n) after the map. Relies on BFS order for ties.
vector<vector<int>> verticalBFS(TreeNode* root){
	if(!root)return {};

	map<int,vector<int>> cols;
	queue<pair<int,TreeNode*>> q;
	q.push({0,root});

	while(!q.empty()){
		auto [hd,node]=q.front();
		q.pop();

		cols[hd].push_back(node->val);

		if(node->left)q.push({hd-1,node->left});
		if(node->right)q.push({hd+1,node->right});
	}

	vector<vector<int>> ans;
	for(auto &it:cols)
	ans.push_back(it.second);

	return ans;
}

BFS or DFS? The question tells you

Both visit every node in O(n), so the choice is not about speed in the worst case. It is about the order nodes come out in: BFS gives you nodes sorted by depth for free, and DFS gives you a whole root-to-leaf path at a time. Pick the one whose natural order matches what the question asks for.

Does the word “level”, “depth”, “row” or “width” appear?

→ BFS, saving the queue size before each level. Examples: level order, zigzag, average per level, largest per level, maximum width.

int n=q.size();
Does it say “shallowest”, “minimum depth”, or “nearest”?

→ BFS, and you can stop early. BFS reaches the closest answer first, so for minimum depth it stops at the first leaf it finds. DFS might explore a whole deep subtree before it finds that leaf.

if(isLeaf(node))return depth;
Does it say “deepest”, “all paths”, or “subtree”?

→ DFS (Chapter 16). You have to reach the bottom anyway, so BFS's early stop gives you nothing.

L=dfs(left); R=dfs(right);
Is it about columns or visibility from a side?

→ BFS with a column number. Top view and bottom view need BFS. Vertical order can use either, as long as the tie-break is right.

q.push({hd,node});
⚡
Space: BFS and DFS have opposite worst cases

DFS uses O(h) space, where h is the height. That is cheap on a wide, shallow tree and O(n) on a chain (a tree that is one long line). BFS uses O(w) space, where w is the widest level. That is cheap on a chain, but about n/2 on a complete tree (every level full), so O(n). Neither one always wins; it depends on the tree's shape. For example, on a nearly-complete tree of 10⁶ nodes, DFS uses about 20 stack frames while BFS queues about 500,000 pointers. On a path of 10⁶ nodes, DFS overflows the stack while BFS holds just one node. Say which tree shape you are worried about instead of quoting one number.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 ONE LOOP, SIX VIEWS
Level-order, zig-zag, left view, right view, top view and bottom view are the same BFS with one line changed. Learn the loop, then vary the one line — do not learn six functions.
💡 INDEX LIKE A HEAP
Give the root index 0 and each node 2i+1 / 2i+2, and width, verticality and position questions become arithmetic instead of traversal.
⛔ VERTICAL TIE-BREAK
Vertical order ties must break on (depth, value), not insertion order. A BFS that ignores the tie-break passes the samples and fails the hidden tests.
⚠️
Common mistakes
  • for(int i=0;i<q.size();i++). The queue grows as you push children, so the inner loop eats into the next level. All six problems in this chapter break.
  • Forgetting if(!root)return. If you push a null root, the first front()->val reads through a null pointer and crashes.
  • Pushing children without checking for null. Nulls get into the queue and crash the next time you read them. Always write if(node->left)q.push(...).
  • Using unordered_map for columns. You lose the left-to-right order and have to sort the keys yourself.
  • Using DFS for the top or bottom view. A deep node on the left can reach a column before a shallow node on the right, so you save the wrong node.
  • Ignoring the vertical-order tie-break. It passes the sample, then fails when two nodes share a column and a depth.
  • Trying to flip the traversal direction for zigzag. Collect each level normally and reverse the vector. One line, no risk.
  • Using DFS for minimum depth. It works, but it explores everything. BFS returns at the first leaf it finds.
  • Saying BFS uses O(log n) space. It uses O(w), the widest level, which is n/2 for a complete tree.

Interview drill

Warm-up: Give me the right view of a binary tree. Then the left view. Then zigzag.

How a strong answer sounds
All three are the same level-order BFS with one line different, so I'll write the skeleton once. Return early on a null root, push the root, and loop while the queue is not empty. At the top of each round I save int n = q.size(). That is the number of nodes on the current level, because right now the queue holds exactly this level and nothing else. Then an inner loop runs n times. Each time it pops a node, adds its value to a level vector, and pushes its non-null children. Those children belong to the next level, and the saved n keeps them out. After the inner loop comes the one line that changes. For level order I push the whole level. For the right view I push level.back(). For the left view I push level[0]. For zigzag I reverse level when the level index is odd, then push it. All four take O(n) time and O(w) space, where w is the widest level. The only tricky part is saving the size before the inner loop. Writing i < q.size() re-reads a growing queue and merges every level into one, which breaks all four without any error.

Deeper: Vertical order traversal. What is the tie-break, and why can you not just use DFS?

How a strong answer sounds
I give each node a horizontal distance: root 0, left child hd−1, right child hd+1. Then I group nodes in a map<int, ...> keyed by that distance, which gives me the columns in left-to-right order for free. Inside a column, nodes must come out ordered by depth. The real difficulty is that two nodes can share both a column and a depth, and the problem statement decides what happens then. The common version says the smaller value goes first. In that case I record each node's depth in one pass, group by column in another, and sort each column with a comparator on (depth, value). That is O(n log n), and the rule is written down in a named function I can change. Some versions say ties follow left-to-right order instead. Then a single BFS is enough with no sort, because level order already produces exactly that order. So I would ask which rule applies instead of guessing. Separately, top and bottom view really do need BFS, not DFS. They want the shallowest or deepest node in each column. A DFS can reach a deep node in a column before a shallow one and save the wrong value. BFS promises that shallower nodes are visited first, and that promise is what makes it correct.

🧠 Key takeaways

  • Saving int n=q.size() before the inner loop is what lets BFS know where each level ends. Without it, every problem here breaks.
  • Level order, zigzag, left view and right view are one loop. Only the line after the inner loop changes.
  • Top view, bottom view and vertical order give each node a column number (horizontal distance) and use a map, so the columns come out in order.
  • Top view keeps the first node in each column; bottom view keeps overwriting. They are one line apart.
  • DFS space is O(h) and BFS space is O(w). Their worst cases are opposite, so say which tree shape you mean.

Check your understanding

You have level order working and want the right view. What is the minimal change?

Just one line after the inner loop changes. Left view takes level[0], right view takes the last element, and zigzag reverses odd levels. One skeleton, four problems.

Why must int n = q.size() be captured before the inner loop?

At that moment the queue holds exactly the current level. Children pushed inside the loop belong to the next level and must be left out. The saved n does that for you.

Top view versus bottom view — what is the difference in code?

BFS visits shallower nodes first. So the first node seen in a column is the top one, and the last node seen is the bottom one. The find check becomes a plain assignment — one line.

Why use map rather than unordered_map for the horizontal-distance columns?

The columns must come out left to right, and column numbers are negative on the left. A sorted map gives you that order for free. A hash map would make you collect the keys and sort them.

What is the space complexity of BFS on a binary tree, and its worst case?

DFS is O(h) and BFS is O(w), and their worst cases are opposite. BFS is cheap on a chain and expensive on a complete tree. DFS is the reverse. Neither one always wins.
