Level Order, ZigZag, Vertical & Views

This is the chapter that proves the point of the whole course. Six accepted solutions, one loop. Level order, zigzag, the left view and the right view are literally the same BFS body with a single line changed after the inner loop — and the two vertical problems are the same body with a coordinate attached. Learn the skeleton once, learn where the variation goes, and you have six problems instead of one.

  • Write the level-aware BFS skeleton and explain why the size capture is load-bearing
  • Derive zigzag, left view and right view by changing one line each
  • Attach a horizontal-distance coordinate for top, bottom and vertical order
  • Get the vertical-order tie-break rule right, which is the whole difficulty
  • Choose BFS over DFS by the shape of the question

The skeleton

One loop. Everything in this chapter is this loop.

the level-order skeleton — memorise thisO(n)O(w)
void LevelOrder(TreeNode* root){
	if(!root)return;

	vector<vector<int>> ans;
	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		int n=q.size();            // THE load-bearing line
		vector<int> level;

		for(int i=0;i<n;i++){
			TreeNode* node=q.front();
			level.push_back(node->val);
			q.pop();

			if(node->left)q.push(node->left);
			if(node->right)q.push(node->right);
		}

		ans.push_back(level);      // <-- the ONLY line that varies
	}
}
int n=q.size() is the entire idea. Captured before the inner loop, it equals exactly the number of nodes on the current level — because at that moment the queue holds this level and nothing else. Every child pushed inside the loop belongs to the next level and is correctly excluded. Write for(int i=0;i<q.size();i++) instead and the inner loop keeps eating the growing queue, levels merge into one, and every problem in this chapter breaks silently.

Take the whole level. The baseline.

void ZigZag(TreeNode* root){
	if(!root)return;

	vector<vector<int>> ans;
	int counter=0;
	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		int n=q.size();
		vector<int> level;
		for(int i=0;i<n;i++){
			TreeNode* node=q.front();
			level.push_back(node->val);
			q.pop();

			if(node->left)q.push(node->left);
			if(node->right)q.push(node->right);
		}
		if(counter%2!=0)
		reverse(level.begin(),level.end());
		ans.push_back(level);
		counter++;
	}
}

Reverse odd-numbered levels before pushing. Do not try to reverse the traversal itself — collect normally and reverse the collected vector. That is O(n) total and cannot go wrong.

vector<int> LeftView(TreeNode* root){
	if(!root)return {};

	vector<int> result;
	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		int n=q.size();
		vector<int> level;
		for(int i=0;i<n;i++){
			TreeNode* node=q.front();
			level.push_back(node->val);
			q.pop();

			if(node->left)q.push(node->left);
			if(node->right)q.push(node->right);
		}
		result.push_back(level[0]);
	}

	return result;
}

The first node of each level. Safe because level is never empty — the queue was non-empty, so n ≥ 1.

vector<int> RightView(TreeNode* root){
	if(!root)return {};

	vector<int> result;
	queue<TreeNode*> q;
	q.push(root);

	while(!q.empty()){
		int n=q.size();
		vector<int> level;
		for(int i=0;i<n;i++){
			TreeNode* node=q.front();
			level.push_back(node->val);
			q.pop();

			if(node->left)q.push(node->left);
			if(node->right)q.push(node->right);
		}
		result.push_back(level[level.size()-1]);
	}

	return result;
}

The last node of each level. One index different from the left view — level.back() would also do.

✍️
My convention: keep the whole level vector even when you only want one element

The left and right views only need one value, so you could track it with a flag inside the loop and skip building level at all. Do not. Keeping the identical body means all four functions are visibly the same code, which is exactly what makes them one memory instead of four — and the cost is one O(w) vector you were already allowed by the BFS space bound. Optimising away the shared structure here would save nothing measurable and cost you the pattern. Recognisability is a feature.

The vertical family: attach a coordinate

Top view, bottom view and vertical order are not about levels — they are about columns. Give the root horizontal distance 0, a left child hd−1 and a right child hd+1, and then the question is what to keep per column.

ProblemPer column, keep…So the map update is…
Top viewThe first node seen (shallowest)Insert only if the column is absent
Bottom viewThe last node seen (deepest)Always overwrite
Vertical orderAll nodes, sorted by depth then by the tie-break ruleAppend, then sort within the column
🗺️
Why map and not unordered_map for the columns

The output must be ordered left to right by column, and horizontal distances are negative on the left. A map<int,...> iterates in ascending key order for free, so the final loop just walks it. With unordered_map you would have to collect the keys and sort them — extra code for no benefit, since the column count is small. This is the one place in the course where map beats unordered_map on both clarity and effort. It is also exactly Chapter 9's rule in reverse: when you need order, order is what you pay for.

// BFS guarantees we meet shallower nodes first, so the FIRST node we see
// in a column is the one visible from above.
vector<int> topView(TreeNode* root){
	if(!root)return {};

	map<int,TreeNode*> colmap;
	queue<pair<int,TreeNode*>> q;
	q.push({0,root});

	while(!q.empty()){
		int level=q.front().first;      // horizontal distance
		TreeNode* node=q.front().second;
		q.pop();

		if(colmap.find(level)==colmap.end())
		colmap[level]=node;                // first only

		if(node->left)q.push({level-1,node->left});
		if(node->right)q.push({level+1,node->right});
	}

	vector<int> result;
	for(auto &it:colmap)
	result.push_back(it.second->val);

	return result;
}

This must be BFS, not DFS. A DFS would reach a deep-left node before a shallow-right one in the same column and record the wrong value. The level-order property is doing real work.

// Identical, except we always overwrite — so the LAST node seen wins,
// and BFS means the last is the deepest.
vector<int> bottomView(TreeNode* root){
	if(!root)return {};

	map<int,TreeNode*> colmap;
	queue<pair<int,TreeNode*>> q;
	q.push({0,root});

	while(!q.empty()){
		int level=q.front().first;
		TreeNode* node=q.front().second;
		q.pop();

		colmap[level]=node;                // always overwrite

		if(node->left)q.push({level-1,node->left});
		if(node->right)q.push({level+1,node->right});
	}

	vector<int> result;
	for(auto &it:colmap)
	result.push_back(it.second->val);

	return result;
}

One line different from the top view. The find guard becomes an unconditional assignment. Same skeleton-reuse principle as the four level variants.

// Vertical order keeps EVERY node per column, ordered by depth,
// with ties broken by value (that is this problem's stated rule).
// Two DFS passes record the two coordinates, then we sort inside each column.
void Rows(TreeNode* root,int level,unordered_map<TreeNode*,int> &rows){
	if(!root)return;

	rows[root]=level;

	Rows(root->left,level+1,rows);
	Rows(root->right,level+1,rows);
}
void Cols(TreeNode* root,int level,map<int,vector<TreeNode*>> &cols){
	if(!root)return;

	cols[level].push_back(root);

	Cols(root->left,level-1,cols);
	Cols(root->right,level+1,cols);
}
bool compare(const pair<int,int> &a,const pair<int,int> &b){
	if(a.first==b.first)
	return a.second<b.second;   // same depth -> smaller value first

	return a.first<b.first;         // otherwise shallower first
}
vector<vector<int>> VerticalOrder(TreeNode* root){
	if(!root)return {};

	unordered_map<TreeNode*,int> rows;
	map<int,vector<TreeNode*>> cols;

	Rows(root,0,rows);
	Cols(root,0,cols);

	vector<vector<int>> ans;
	for(auto &it:cols){
		vector<pair<int,int>> temp;
		for(TreeNode* node:it.second)
		temp.push_back({rows[node],node->val});

		sort(temp.begin(),temp.end(),compare);

		vector<int> v;
		for(auto &[level,nodeval]:temp)
		v.push_back(nodeval);

		ans.push_back(v);
	}

	return ans;
}

The compare function is the whole problem. Depth first, then value — that is the multi-key comparator pattern from Chapter 8. Getting it right is what separates a correct answer from one that passes the sample and fails on a tie.

⚖️
The vertical-order tie-break is the entire difficulty — and it varies by problem

Two nodes can share a column and a depth. Different problem statements resolve that differently, so read the statement:

  • Tie broken by value (the common LeetCode variant) — sort by (depth, value), which is exactly the compare function above.
  • Tie broken by left-to-right BFS order — then no sort is needed at all, because a level-order traversal already produces that order. Just append during BFS.

Because the DFS-plus-sort version makes the rule explicit in a comparator, it adapts to either statement by editing one function. The one-pass BFS version is shorter but silently assumes the second rule. When the tie-break is stated, write it down as a comparator — do not let it be an accident of traversal order.

DFS + explicit sort

Two passes, then sort inside each column. O(n log n) overall. The tie-break rule lives in a named compare function, so it is documented and changeable. Prefer this when the statement specifies a tie-break.

One-pass BFS
// Shorter, O(n) after the map. Relies on BFS order for ties.
vector<vector<int>> verticalBFS(TreeNode* root){
	if(!root)return {};

	map<int,vector<int>> cols;
	queue<pair<int,TreeNode*>> q;
	q.push({0,root});

	while(!q.empty()){
		auto [hd,node]=q.front();
		q.pop();

		cols[hd].push_back(node->val);

		if(node->left)q.push({hd-1,node->left});
		if(node->right)q.push({hd+1,node->right});
	}

	vector<vector<int>> ans;
	for(auto &it:cols)
	ans.push_back(it.second);

	return ans;
}

BFS or DFS? The question tells you

Does the word “level”, “depth”, “row” or “width” appear?

→ BFS with the size capture. Level order, zigzag, average per level, largest per level, maximum width.

int n=q.size();
Does it say “shallowest”, “minimum depth”, or “nearest”?

→ BFS, and you can return early. BFS reaches the closest answer first, so minimum depth stops at the first leaf; DFS would explore an entire deep subtree first.

if(isLeaf(node))return depth;
Does it say “deepest”, “all paths”, or “subtree”?

→ DFS (Chapter 16). You must reach the bottom, so there is no early exit to gain.

L=dfs(left); R=dfs(right);
Is it about columns or visibility from a side?

→ BFS with a coordinate. Top view and bottom view require BFS; vertical order can use either with the right tie-break.

q.push({hd,node});
⚡
Space: BFS and DFS have opposite worst cases

DFS is O(h) — cheap on a wide shallow tree, O(n) on a chain. BFS is O(w) where w is the widest level — cheap on a chain, and n/2 on a complete tree, so O(n). Neither is universally better; it depends on the shape. The useful consequence: on a nearly-complete tree of 10⁶ nodes, DFS uses ~20 frames while BFS queues ~500,000 pointers. On a 10⁶-node path, DFS overflows the stack while BFS holds one node. Say which shape you are worried about rather than quoting one number.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 ONE LOOP, SIX VIEWS
Level-order, zig-zag, left view, right view, top view and bottom view are the same BFS with one line changed. Learn the loop, then vary the one line — do not learn six functions.
💡 INDEX LIKE A HEAP
Give the root index 0 and each node 2i+1 / 2i+2, and width, verticality and position questions become arithmetic instead of traversal.
⛔ VERTICAL TIE-BREAK
Vertical order ties must break on (depth, value), not insertion order. A BFS that ignores the tie-break passes the samples and fails the hidden tests.
⚠️
Common mistakes
  • for(int i=0;i<q.size();i++). The queue grows as children are pushed, so the inner loop consumes the next level and all six problems in this chapter break.
  • Forgetting if(!root)return. Pushing a null root means the first front()->val dereferences null.
  • Pushing children without the null check. Nulls enter the queue and crash on the next dereference. Always if(node->left)q.push(...).
  • Using unordered_map for columns. You lose left-to-right order and have to sort the keys manually.
  • Using DFS for the top or bottom view. A deep-left node reaches a column before a shallow-right one, so you record the wrong node.
  • Ignoring the vertical-order tie-break. Passes the sample, fails on two nodes sharing a column and a depth.
  • Trying to reverse the traversal direction for zigzag. Collect normally and reverse the collected vector — one line, no risk.
  • Using DFS for minimum depth. It works but explores everything; BFS returns at the first leaf found.
  • Claiming BFS is O(log n) space. It is O(w), which is n/2 for a complete tree.

Interview drill

Warm-up: Give me the right view of a binary tree. Then the left view. Then zigzag.

How a strong answer sounds
All three are the same level-order BFS with one line different, so let me write the skeleton once. Guard on a null root, push the root, and loop while the queue is non-empty. At the top of each iteration I capture int n = q.size() — that is the count of nodes on the current level, because right now the queue holds exactly this level and nothing else. Then an inner loop of n iterations pops each node, records its value into a level vector, and pushes its non-null children, which belong to the next level and are correctly excluded by the captured n. After the inner loop, the one varying line: for level order I push the whole level; for the right view I push level.back(); for the left view I push level[0]; for zigzag I reverse level when the level index is odd and then push it. All four are O(n) time and O(w) space where w is the widest level. I would emphasise that capturing the size before the inner loop is the only subtle part — using i < q.size() directly re-reads a growing queue and merges every level into one, which breaks all four silently.

Deeper: Vertical order traversal. What is the tie-break, and why can you not just use DFS?

How a strong answer sounds
I assign each node a horizontal distance — root 0, left child hd−1, right child hd+1 — and group nodes into a map<int, ...> keyed by that distance, which gives me the columns in left-to-right order for free. Within a column, nodes must come out ordered by depth. The genuine difficulty is that two nodes can share both a column and a depth, and the statement decides what happens then. The common variant says break ties by the smaller value, in which case I record each node's depth in one pass, group by column in another, and sort each column by a comparator on (depth, value) — that is O(n log n) and the rule is explicit in a named function I can change. Some variants instead say ties follow left-to-right order, and then a single BFS suffices with no sort at all, because level order already produces exactly that sequence. So I would ask which rule applies rather than guess. Separately, top and bottom view genuinely require BFS rather than DFS: they want the shallowest or deepest node per column, and a DFS can reach a deep node in a column before a shallow one, recording the wrong value — BFS's guarantee that shallower nodes are visited first is doing real work there.

🧠 Key takeaways

  • int n=q.size() captured before the inner loop is what makes BFS level-aware; without it every problem here breaks.
  • Level order, zigzag, left view and right view are one loop with one line changed after the inner loop.
  • Top, bottom and vertical order attach a horizontal distance and use a map so columns come out ordered.
  • Top view keeps the first node per column, bottom view overwrites — one line apart.
  • DFS space is O(h) and BFS space is O(w); the worst cases are opposite, so name the tree shape you care about.

Check your understanding

You have level order working and want the right view. What is the minimal change?

Exactly one line after the inner loop. Left view takes level[0], right view takes the last element, zigzag reverses on odd levels. One skeleton, four problems.

Why must int n = q.size() be captured before the inner loop?

At that instant the queue holds precisely the current level. Children pushed inside the loop belong to the next level and must be excluded — which the captured n does automatically.

Top view versus bottom view — what is the difference in code?

Since BFS visits shallower nodes first, “first seen per column” is the top and “last seen per column” is the bottom. The find guard becomes an unconditional assignment — one line.

Why use map rather than unordered_map for the horizontal-distance columns?

The columns must come out left to right, and horizontal distances go negative on the left. A tree map gives that ordering for free; a hash map would need the keys collected and sorted.

What is the space complexity of BFS on a binary tree, and its worst case?

DFS is O(h) and BFS is O(w), and their worst cases are opposite: BFS is cheap on a chain and expensive on a complete tree, while DFS is the reverse. Neither is universally better.
