Digit, Probability & Game DP

Three families that share one idea: the state is not a position in an array. Digit DP walks the decimal representation of a number and carries a "still hugging the upper bound" flag. Probability DP stores an expected value instead of a count. Game DP stores whose turn it is. Each one is short to write once you accept that anything can be a state as long as it is sufficient.

  • Count numbers in a range satisfying a property, using the tight flag
  • Reduce "count in [L, R]" to two prefix counts
  • Write expectation DP and know when the graph of states has cycles
  • Solve two-player games with minimax and the score-difference trick
  • Recognise which of the three families a problem belongs to

Digit DP: the tight flag

"How many integers in [1, 10¹⁸] have no two equal adjacent digits?" You cannot iterate the range. Instead build the number one digit at a time, left to right, and count completions. The only awkward part is the upper bound: while the prefix you have built exactly matches the bound's prefix, your next digit is capped; the moment you place something smaller, every remaining digit is free.

digit DP template — count x in [0, N] with a propertyO(digits · states · 10)O(digits · states)
// State:
//   pos   — which digit we are placing, 0 = most significant
//   tight — is the prefix built so far EXACTLY equal to N's prefix?
//           if so, this digit is capped at digits[pos]; if not, 0..9 is free
//   started — have we placed a non-zero digit yet? (handles leading zeros)
//   ...plus whatever the property needs (last digit, running sum mod m, ...)
//
// Only the NON-tight states are worth memoising: there is exactly one tight
// path per position, so caching it would be pointless and, worse, unsound —
// a tight state's answer depends on N, a free state's does not.
long long solve(int pos,bool tight,bool started,int last,
                vector<int> &digits,vector<vector<vector<long long>>> &memo){
	if(pos==digits.size())return started?1:0;   // a complete number

	if(!tight and started and memo[pos][last][1]!=-1)
	return memo[pos][last][1];

	int limit=tight?digits[pos]:9;
	long long ans=0;

	for(int d=0;d<=limit;d++){
		if(started and d==last)continue;        // the property: no equal neighbours

		bool nextTight=tight and (d==limit);   // still hugging the bound?
		bool nextStarted=started or d>0;

		ans+=solve(pos+1,nextTight,nextStarted,
		          nextStarted?d:last,digits,memo);
	}

	if(!tight and started)memo[pos][last][1]=ans;

	return ans;
}

long long countUpTo(long long N){
	if(N<0)return 0;

	vector<int> digits;
	string s=to_string(N);

	for(auto &c:s)
	digits.push_back(c-'0');

	vector<vector<vector<long long>>> memo(digits.size(),
		vector<vector<long long>>(10,vector<long long>(2,-1)));

	return solve(0,true,false,0,digits,memo);
}

// count in [L,R] = countUpTo(R) - countUpTo(L-1)
long long countRange(long long L,long long R){
	return countUpTo(R)-countUpTo(L-1);
}
Three things carry all the weight. (1) nextTight = tight and (d==limit) — you stay pinned to the bound only if you were pinned and you placed the maximum allowed digit. (2) Do not memoise tight states: their value depends on N, and there is only one such path per position anyway, so caching buys nothing and risks a wrong answer if you ever reuse the memo for a different bound. (3) The started flag exists because 007 and 7 are the same number — without it, leading zeros get counted as digits and properties like "no equal adjacent digits" reject 100 for the wrong reason. The reduction to f(R) − f(L−1) is the same prefix-difference trick as prefix sums (Chapter 6), applied to counting.
✍️
My convention: verify a digit DP against brute force before trusting it

Digit DP has an unusually high bug rate per line — the tight flag, the started flag and the memo condition all interact, and a wrong answer looks entirely plausible. So the first thing I write after the DP is a ten-line loop that checks the property on every number from 0 to a few hundred thousand, and I compare the two on every bound in that range. If they agree on 100,000 consecutive bounds, the recurrence is right; if they diverge, the smallest disagreeing bound usually points straight at the bug (a divergence at exactly a power of ten means the started flag; one that begins at the bound's own value means the tight handling). That is the stress-testing discipline from Chapter 53, and this is the family where it pays off most.

The memo has one dimension per state component, so keep them minimal — pos × tight × started × extra. With 18 digits, 10 previous-digit values and a mod-100 residue you are at 36,000 states, which is nothing. Digit DP is cheap; the expense is your attention.

Probability and expectation DP

Same machinery, different values in the table: instead of "how many ways", dp[state] holds a probability or an expected value. Two rules carry almost everything:

Probability: weight each branch
// Knight on a chessboard: k random moves, each of the 8 chosen uniformly.
// What is the probability it is still on the board?
// dp[step][r][c] = probability of standing on (r,c) after `step` moves.
double knightProbability(int N,int k,int row,int col){
	vector<vector<double>> dp(N,vector<double>(N,0.0));

	dp[row][col]=1.0;

	int dr[]={1,1,-1,-1,2,2,-2,-2};
	int dc[]={2,-2,2,-2,1,-1,1,-1};

	for(int step=0;step<k;step++){
		vector<vector<double>> next(N,vector<double>(N,0.0));

		for(int r=0;r<N;r++){
			for(int c=0;c<N;c++){
				if(dp[r][c]==0.0)continue;

				for(int m=0;m<8;m++){
					int nr=r+dr[m];
					int nc=c+dc[m];

					if(nr<0 or nr>=N or nc<0 or nc>=N)continue;

					next[nr][nc]+=dp[r][c]/8.0;
				}
			}
		}

		dp=next;
	}

	double ans=0.0;

	for(int r=0;r<N;r++)
	for(int c=0;c<N;c++)
	ans+=dp[r][c];

	return ans;
}

Each branch contributes its own probability times the branch's chance. Note that stepping off the board simply loses that mass — the totals stop summing to 1, and the answer is exactly the surviving mass. Use double and do not compare floats for equality; the dp[r][c]==0.0 skip above is safe only because those entries were never written.

Expectation: linearity
// Expected number of dice rolls to reach a total of at least `target`,
// where each roll is uniform on 1..6.
// E[s] = the expected additional rolls needed from total s.
// E[s] = 1 + (1/6) * sum over d of E[s+d]     for s < target
// E[s] = 0                                    for s >= target
// The "1 +" is the roll we are about to make — that is linearity of
// expectation: E[total] = E[this step] + E[the rest].
double expectedRolls(int target){
	vector<double> E(target+7,0.0);

	// fill BACKWARDS: E[s] depends only on larger totals
	for(int s=target-1;s>=0;s--){
		double sum=0.0;

		for(int d=1;d<=6;d++)
		sum+=E[s+d];

		E[s]=1.0+sum/6.0;
	}

	return E[0];
}

The state graph must be acyclic for this to work. Here it is: a roll strictly increases the total, so E[s] only ever reads larger s, and a single backward pass suffices. If a move could return you to the same state — "reroll on a 6" — then E appears on both sides and you must solve the equation algebraically, or set up a linear system and use Gaussian elimination.

🔁
When the states form a cycle

"Expected rolls of a die until you see a 6" cannot be filled by a DP pass, because from the state "not yet seen a 6" one outcome returns to that same state. Write the equation and solve it:

E = 1 + (5/6)·E + (1/6)·0
E - (5/6)E = 1
E = 6

The general form: self-loops with probability p multiply the expected time by 1/(1−p), because the number of attempts until success is geometric with mean 1/(1−p). For a handful of mutually dependent states, build the linear system and run Gaussian elimination — O(s³) in the number of states, which is fine for a few hundred. The tell that you need this: a transition that can leave the state unchanged, or a set of states that can reach each other in both directions.

Game DP: minimax and the score difference

Two players alternate, both play optimally. The state must include whose turn it is — or, far more neatly, you store the score difference from the perspective of whoever is about to move, which makes the turn implicit.

dp[i][j] is the best score difference the player to move can force on [i..j] — positive means that player wins the remainder.
stone game — the score-difference formulationO(n²)O(n²)
// Players alternately take a stone from either end of the row.
// dp[i][j] = the maximum score DIFFERENCE (mine minus the opponent's) that the
//            player about to move can force on the interval [i..j].
//
// Why a difference? Because it removes "whose turn" from the state. After I
// take a stone, my opponent faces the smaller interval and forces dp on it from
// THEIR perspective — which is exactly minus my perspective. Hence the minus.
bool stoneGame(vector<int> &piles){
	int n=piles.size();
	vector<vector<int>> dp(n,vector<int>(n,0));

	for(int i=0;i<n;i++)
	dp[i][i]=piles[i];              // one stone left: I take it

	for(int len=2;len<=n;len++){
		for(int i=0;i+len-1<n;i++){
			int j=i+len-1;

			int takeLeft=piles[i]-dp[i+1][j];
			int takeRight=piles[j]-dp[i][j-1];

			dp[i][j]=max(takeLeft,takeRight);
		}
	}

	return dp[0][n-1]>0;      // first player wins iff the difference is positive
}
The minus sign is the entire minimax. There is no separate "minimising player" branch, no isMaximising boolean, and no doubled state space — the opponent's best outcome is by definition the negation of mine, so subtracting it expresses optimal play by both sides in one line. This is the same idea as negamax in game-tree search. Note this is also an interval DP (Chapter 45), and it needs the same length-increasing fill order. If you need the actual scores rather than who wins, recover them from the difference and the known total: myScore = (total + diff) / 2.
♟️
Three formulations of a two-player game
  • Score difference (above) — cleanest when both players maximise the same resource. One table, no turn index.
  • Explicit turn — dp[state][turn], with a max branch and a min branch. Necessary when the players have different objectives or different move sets.
  • Win/lose (game theory) — dp[state] is a boolean. The rule is: a state is winning if any move leads to a losing state for the opponent; it is losing if every move leads to a winning state. Use this when the question is only "who wins", as in Nim-style problems and "can I reach 0". Often a pattern emerges that removes the DP entirely — the divisor game's answer is just "is n even", and Nim's is the XOR of the pile sizes being non-zero.

Try the boolean version first when the output is a winner, then look for the pattern in the small cases. Interviewers asking "who wins" are frequently hoping you will find the closed form after the DP confirms it.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 f(R) − f(L−1)
Count over a range by counting two prefixes. The same trick as prefix sums, applied to counting — and it halves the work you have to think about.
⛔ DO NOT MEMO TIGHT
A tight state’s value depends on the bound, not just the state. Memoise only the free states, and remember the started flag or leading zeros will bite.
💡 DIFFERENCE, NOT TURN
For two-player games, store the score difference from the mover’s perspective. Minimax then collapses to one minus sign and the turn leaves the state.
⚠️
Common mistakes
  • Memoising tight states in digit DP. Their value depends on the bound; only free states are reusable.
  • Forgetting the started flag, so leading zeros count as real digits and small numbers are misjudged.
  • nextTight = (d==limit) without the and tight — a free state can never become tight again.
  • Computing [L,R] as f(R) − f(L) instead of f(R) − f(L−1), dropping L itself.
  • Not stress-testing a digit DP. The bug rate per line is high and wrong answers look plausible.
  • Filling an expectation DP forwards when E[s] depends on larger s; it must go backwards.
  • Running a DP pass over a cyclic state graph. A self-loop means solving an equation, or Gaussian elimination.
  • Comparing floating-point values for equality, or accumulating error over many steps.
  • Adding an isMaximising flag when the score-difference form removes it — twice the state and twice the bugs.
  • Getting the sign wrong: piles[i] - dp[i+1][j], never +. The opponent's gain is your loss.
  • Assuming the first player always wins because they do in the standard stone game (where n is even and the total is odd). Verify it on the actual constraints.

Interview drill

Warm-up: Count the integers in [1, 10¹⁸] whose digits are non-decreasing.

How a strong answer sounds
The range is far too large to iterate, and the property depends on the decimal representation, so this is digit DP. I reduce "count in [L, R]" to f(R) − f(L−1), the same prefix-difference trick as prefix sums, and then only need f(N) = the count in [0, N]. I write N's digits into an array and build candidate numbers left to right. The state is: pos, the digit position being placed; tight, whether the prefix built so far exactly matches N's prefix, which decides whether this digit is capped at digits[pos] or free over 0–9; started, whether a non-zero digit has been placed, since 007 and 7 are the same number; and, for this property, the previous digit, since non-decreasing means each digit is at least the last. The transition loops d from 0 to the limit, skipping d < last when started, and recurses with nextTight = tight and (d == limit) — the and matters, because once you have gone strictly below the bound you can never be pinned to it again. The base case at pos == length returns 1 if started, else 0. I memoise on (pos, last) but only for non-tight, started states: a tight state's answer depends on N rather than only on the state, and there is exactly one tight path per position anyway, so caching it buys nothing and risks a wrong answer. With 19 digits and 10 previous-digit values that is fewer than 200 states, each doing ten units of work — instant. The last thing I would do, and I would say so, is stress-test it: a brute-force loop over the first hundred thousand integers, compared against the DP for every bound in that range. Digit DP is short but has an unusually high bug rate, and a wrong answer here looks entirely plausible.

Deeper: Stone game — players take from either end, both optimal. Who wins, and what is the state?

How a strong answer sounds
The naive formulation adds a boolean for whose turn it is and branches into a max for me and a min for my opponent. That works but it doubles the state and invites sign errors, so I prefer the score-difference form: dp[i][j] is the maximum value of (my score − opponent's score) that the player about to move can force on the interval [i..j]. Defining it relative to whoever moves makes the turn implicit and removes the dimension entirely. Base case dp[i][i] = piles[i], since with one stone left the mover takes it. For the transition, if I take the left stone I gain piles[i], and then my opponent faces [i+1..j] and forces dp[i+1][j] from their perspective — which is exactly minus mine — so my net is piles[i] − dp[i+1][j]. Similarly for the right end, and dp[i][j] is the max of the two. That single minus sign is the minimax; it is the same idea as negamax in game-tree search. This is an interval DP, so it needs the length-increasing fill order — dp[i][j] reads strictly shorter intervals. First player wins iff dp[0][n−1] > 0, and if the actual scores are wanted I can recover them from the total: my score is (total + diff) / 2. O(n²) time and space, reducible to O(n) with a rolling diagonal. Two follow-ups I would raise: if a player may take up to k stones from one end, the same structure holds with an extra loop over how many, and if the question is only "who wins" rather than "by how much", the boolean win/lose formulation is often enough — a state is winning if any move leaves the opponent in a losing state — and it frequently reveals a closed form, the way Nim reduces to the XOR of the pile sizes.

🧠 Key takeaways

  • Digit DP builds a number left to right; tight tracks whether you are still pinned to the bound, and only free states may be memoised.
  • Count in [L,R] as f(R) − f(L−1), and always stress-test the result against brute force.
  • Expectation DP uses linearity: one step plus the weighted average of the rest, filled in dependency order.
  • A self-loop in the state graph means solving an equation (or Gaussian elimination), not a DP pass.
  • Store the score difference from the mover's perspective and minimax collapses to one minus sign.

Check your understanding

In digit DP, what does the tight flag mean?

And nextTight = tight and (d==limit) — once you place something strictly smaller, every remaining digit is free and can never be pinned again.

Why should tight states not be memoised?

A free state's completion count is a property of the state alone and is reusable. Caching a tight state can also produce a wrong answer if the memo is reused for a different bound.

Expected number of dice rolls until you see a 6. Why can a DP pass not compute it?

A self-loop with probability p multiplies the expected time by 1/(1−p). For several mutually dependent states, build the linear system and use Gaussian elimination.

In the stone game, why is the transition piles[i] - dp[i+1][j] rather than +?

That one minus sign is the minimax — it expresses optimal play by both sides without an isMaximising flag or a doubled state space.

In the boolean win/lose formulation, a state is winning when…

One good move is all you need; it is losing only when every option hands the opponent a win. This formulation often reveals a closed form — Nim reduces to the XOR of the pile sizes being non-zero.
