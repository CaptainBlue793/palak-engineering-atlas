Digit, Probability & Game DP

Three families of problems share one idea: the state does not have to be a position in an array. Digit DP walks through a number's digits and carries a flag for "am I still matching the upper bound?". Probability DP stores an expected value instead of a count. Game DP stores whose turn it is. Each is short to write, once you accept that anything can be the state, as long as it holds everything you need.

  • Count the numbers in a range with some property, using the tight flag
  • Turn "count in [L, R]" into two counts that start from 0
  • Write expectation DP, and spot when the states form a loop
  • Solve two-player games with minimax and the score-difference trick
  • Tell which of the three families a problem belongs to

Digit DP: the tight flag

"How many whole numbers in [1, 10¹⁸] have no two equal digits next to each other?" You cannot loop over that range. Instead, build the number one digit at a time, left to right, and count how many ways each start can be finished. The only awkward part is the upper bound. While the digits you have placed still match the bound exactly, the next digit is capped at the bound's digit. The moment you place something smaller, every remaining digit is free to be 0–9.

A concrete walk with the bound N = 3254. Think of every number up to it as four digits, padded with leading zeros.

  • First digit. It can be 0, 1, 2 or 3. If it is 0, 1 or 2, the number is already smaller than 3254 no matter what follows, so the last three digits are free: 1,000 choices each. Only the choice 3 stays tight.
  • Second digit, after "3". Now it is capped at 2. Choosing 0 or 1 frees the rest (100 choices each); only "32" stays tight.
  • Third digit, after "32". Capped at 5. And so on until the last digit, where "325" allows 0 to 4.

There is exactly one tight path — the bound's own digits — and everything that leaves it is a free state. Free states depend only on how many digits remain and the extra state (such as the last digit), not on N. That is why they can be cached and reused, and why the whole count takes a few thousand steps instead of looping over 10¹⁸ numbers.

digit DP template — count x in [0, N] with a propertyO(digits · states · 10)O(digits · states)
// State:
//   pos   — which digit we are placing, 0 = most significant
//   tight — is the prefix built so far EXACTLY equal to N's prefix?
//           if so, this digit is capped at digits[pos]; if not, 0..9 is free
//   started — have we placed a non-zero digit yet? (handles leading zeros)
//   ...plus whatever the property needs (last digit, running sum mod m, ...)
//
// Only the NON-tight states are worth memoising: there is exactly one tight
// path per position, so caching it would be pointless and, worse, unsound —
// a tight state's answer depends on N, a free state's does not.
long long solve(int pos,bool tight,bool started,int last,
                vector<int> &digits,vector<vector<vector<long long>>> &memo){
	if(pos==digits.size())return started?1:0;   // a complete number

	if(!tight and started and memo[pos][last][1]!=-1)
	return memo[pos][last][1];

	int limit=tight?digits[pos]:9;
	long long ans=0;

	for(int d=0;d<=limit;d++){
		if(started and d==last)continue;        // the property: no equal neighbours

		bool nextTight=tight and (d==limit);   // still hugging the bound?
		bool nextStarted=started or d>0;

		ans+=solve(pos+1,nextTight,nextStarted,
		          nextStarted?d:last,digits,memo);
	}

	if(!tight and started)memo[pos][last][1]=ans;

	return ans;
}

long long countUpTo(long long N){
	if(N<0)return 0;

	vector<int> digits;
	string s=to_string(N);

	for(auto &c:s)
	digits.push_back(c-'0');

	vector<vector<vector<long long>>> memo(digits.size(),
		vector<vector<long long>>(10,vector<long long>(2,-1)));

	return solve(0,true,false,0,digits,memo);
}

// count in [L,R] = countUpTo(R) - countUpTo(L-1)
long long countRange(long long L,long long R){
	return countUpTo(R)-countUpTo(L-1);
}
Three things carry all the weight. (1) nextTight = tight and (d==limit). You stay pinned to the bound only if you were pinned and you placed the largest digit allowed. (2) Do not cache (memoise) tight states. Their value depends on N, and there is only one tight path per position anyway, so caching gains nothing and can give a wrong answer if the cache is reused for a different bound. (3) The started flag exists because 007 and 7 are the same number. Without it, leading zeros count as real digits, and a rule like "no two equal digits next to each other" would reject 7 — padded to 0007 — for the wrong reason, because of its two leading zeros. Turning the answer into f(R) − f(L−1) is the same subtract-the-prefix trick as prefix sums (Chapter 6), used for counting.
✍️
My convention: verify a digit DP against brute force before trusting it

A quick check of the range formula first: count every number in [10, 20]. countUpTo(20) is 20 (the numbers 1 to 20; zero never gets started), countUpTo(9) is 9, and 20 − 9 = 11, which is right: 10, 11, …, 20. Using countUpTo(10) instead would give 10 and drop the number 10 itself.

Digit DP has an unusually high bug rate per line. The tight flag, the started flag and the caching rule all interact, and a wrong answer looks completely believable. So the first thing I write after the DP is a ten-line loop that checks the property on every number from 0 up to a few hundred thousand. Then I compare the two for every bound in that range. If they agree on 100,000 bounds in a row, the recurrence is right. If they disagree, the smallest bound where they differ usually points straight at the bug: a difference at exactly a power of ten means the started flag, and one that starts at the bound's own value means the tight handling. That is the stress-testing habit from Chapter 53, and this is where it pays off most.

The cache has one dimension per piece of state, so keep the pieces to a minimum — pos × tight × started × extra. With 18 digits, 10 possible previous digits and a remainder mod 100, that is 36,000 states, which is nothing. Digit DP is cheap to run. What it costs is your attention.

Probability and expectation DP

Same machinery, different numbers in the table. Instead of "how many ways", dp[state] holds a probability, or an expected value (the long-run average). Two rules carry almost everything:

  • Probability: the chance of a result is the sum, over every way to reach it, of the chance of each way. If a step has 8 equally likely moves, each move carries 1/8 of the probability you had.
  • Expectation: the expected value of a total is the sum of the expected values of its parts. This is called linearity of expectation, and it holds even when the parts depend on each other. So "expected rolls from here" = 1 (the roll you make now) + the average of "expected rolls from wherever that roll lands you".

Where this shows up: board-game and dice puzzles, "what is the chance a random walk stays inside", expected running time of randomized algorithms, and any interview question with the words "probability" or "on average".

Probability: weight each branch
// Knight on a chessboard: k random moves, each of the 8 chosen uniformly.
// What is the probability it is still on the board?
// dp[step][r][c] = probability of standing on (r,c) after `step` moves.
double knightProbability(int N,int k,int row,int col){
	vector<vector<double>> dp(N,vector<double>(N,0.0));

	dp[row][col]=1.0;

	int dr[]={1,1,-1,-1,2,2,-2,-2};
	int dc[]={2,-2,2,-2,1,-1,1,-1};

	for(int step=0;step<k;step++){
		vector<vector<double>> next(N,vector<double>(N,0.0));

		for(int r=0;r<N;r++){
			for(int c=0;c<N;c++){
				if(dp[r][c]==0.0)continue;

				for(int m=0;m<8;m++){
					int nr=r+dr[m];
					int nc=c+dc[m];

					if(nr<0 or nr>=N or nc<0 or nc>=N)continue;

					next[nr][nc]+=dp[r][c]/8.0;
				}
			}
		}

		dp=next;
	}

	double ans=0.0;

	for(int r=0;r<N;r++)
	for(int c=0;c<N;c++)
	ans+=dp[r][c];

	return ans;
}

Each branch adds its own probability times the chance of taking that branch. Stepping off the board simply loses that share of the probability. The totals stop adding up to 1, and the answer is exactly the share that survived. Use double, and never compare floating-point numbers with ==. The dp[r][c]==0.0 skip above is only safe because those entries were never written to.

Tiny check: a 3×3 board, the knight in the corner (0,0), k = 1. Of its 8 moves, only (1,2) and (2,1) stay on the board, so the answer is 2/8 = 0.25. In the code, next gets 1/8 on each of those two cells, and the final sum is 0.25.

Expectation: linearity
// Expected number of dice rolls to reach a total of at least `target`,
// where each roll is uniform on 1..6.
// E[s] = the expected additional rolls needed from total s.
// E[s] = 1 + (1/6) * sum over d of E[s+d]     for s < target
// E[s] = 0                                    for s >= target
// The "1 +" is the roll we are about to make — that is linearity of
// expectation: E[total] = E[this step] + E[the rest].
double expectedRolls(int target){
	vector<double> E(target+7,0.0);

	// fill BACKWARDS: E[s] depends only on larger totals
	for(int s=target-1;s>=0;s--){
		double sum=0.0;

		for(int d=1;d<=6;d++)
		sum+=E[s+d];

		E[s]=1.0+sum/6.0;
	}

	return E[0];
}

This only works if the states never loop back. Here they do not: a roll always increases the total, so E[s] only ever reads a larger s, and one backward pass is enough. Check it with target = 2: from total 1, any roll finishes, so E[1] = 1. From total 0, you roll once, and only a 1 (chance 1/6) leaves you needing another roll: E[0] = 1 + (1/6)·E[1] = 1 + 1/6 ≈ 1.17. If a move could put you back in the same state — "reroll on a 6" — then E appears on both sides of the equation. Then you must solve that equation with algebra, or write out a system of equations and solve it with Gaussian elimination.

🔁
When the states form a cycle

"How many dice rolls, on average, until you see a 6?" cannot be filled in by a DP pass. From the state "no 6 yet", one outcome takes you right back to that same state. Write the equation and solve it:

E = 1 + (5/6)·E + (1/6)·0
E - (5/6)E = 1
E = 6

The general rule: if a state loops back to itself with probability p, the expected time is multiplied by 1/(1−p). The number of tries until a success follows a geometric distribution, whose average is 1/(1−p). If a few states depend on each other, write out the system of equations and run Gaussian elimination. That is O(s³) in the number of states, which is fine for a few hundred. The sign that you need this: a move that can leave the state unchanged, or a group of states that can reach each other both ways.

Game DP: minimax and the score difference

Two players take turns, and both play as well as possible. The state must include whose turn it is. Or, much more neatly, store the score difference from the point of view of whoever is about to move. Then the turn is built in and needs no separate index.

"Plays as well as possible" is the key phrase. It means you cannot just grab the biggest thing in front of you. You have to assume the opponent will answer with their best reply, and pick the move whose worst case for you is best. That is minimax: maximise your result, knowing the other player minimises it. Greedy play fails, as the dry run below shows.

stone game — the score-difference formulationO(n²)O(n²)
// Players alternately take a stone from either end of the row.
// dp[i][j] = the maximum score DIFFERENCE (mine minus the opponent's) that the
//            player about to move can force on the interval [i..j].
//
// Why a difference? Because it removes "whose turn" from the state. After I
// take a stone, my opponent faces the smaller interval and forces dp on it from
// THEIR perspective — which is exactly minus my perspective. Hence the minus.
bool stoneGame(vector<int> &piles){
	int n=piles.size();
	vector<vector<int>> dp(n,vector<int>(n,0));

	for(int i=0;i<n;i++)
	dp[i][i]=piles[i];              // one stone left: I take it

	for(int len=2;len<=n;len++){
		for(int i=0;i+len-1<n;i++){
			int j=i+len-1;

			int takeLeft=piles[i]-dp[i+1][j];
			int takeRight=piles[j]-dp[i][j-1];

			dp[i][j]=max(takeLeft,takeRight);
		}
	}

	return dp[0][n-1]>0;      // first player wins iff the difference is positive
}
That minus sign is the whole of minimax. There is no separate branch for the "minimising" player, no isMaximising boolean and no doubling of the table. The opponent's best result, measured from their side, is exactly minus mine. So subtracting it captures best play by both sides in one line. This is the same idea as negamax in game-tree search. Note this is also an interval DP (Chapter 45), so it needs the same increasing-length fill order. If you need the actual scores instead of just the winner, work them out from the difference and the known total: myScore = (total + diff) / 2.

Dry run on piles = [3, 9, 1, 2]. Single piles: dp[i][i] is the pile itself. Length 2: dp[0][1] = max(3−9, 9−3) = 6, dp[1][2] = max(9−1, 1−9) = 8, dp[2][3] = max(1−2, 2−1) = 1. Length 3: dp[0][2] = max(3−8, 1−6) = −5, dp[1][3] = max(9−1, 2−8) = 8. Length 4: dp[0][3] = max(3 − dp[1][3], 2 − dp[0][2]) = max(3−8, 2+5) = 7.

So the first player should take the 2, not the bigger 3. Taking 3 hands the opponent [9, 1, 2], where they can force +8. Taking 2 leaves [3, 9, 1], where whatever the opponent takes from an end, the 9 falls to you next. The total is 15 and the difference is 7, so the scores are (15 + 7) / 2 = 11 against 4. A greedy "take the larger end" player would have lost.

♟️
Three formulations of a two-player game
  • Score difference (above). Cleanest when both players want more of the same thing. One table, no turn index.
  • Explicit turn — dp[state][turn], with a max branch and a min branch. You need this when the players want different things, or have different moves available.
  • Win/lose (game theory) — dp[state] is just true or false. The rule: a state is winning if some move leaves the opponent in a losing state; it is losing if every move leaves them in a winning state. Use this when the question is only "who wins", as in Nim-style problems and "can I reach 0". Often a pattern appears that removes the DP entirely: the divisor game's answer is just "is n even", and Nim's is whether the XOR of the pile sizes is non-zero.

A small win/lose example: a pile of n stones, each move removes 1 or 2, and the player who cannot move loses. n = 0 is losing (no move). n = 1 and n = 2 are winning (move to 0). n = 3 is losing: both moves lead to 2 or 1, which are winning for the opponent. n = 4 and 5 win by moving to 3. The table goes lose, win, win, lose, win, win… so the pattern is "the player to move loses exactly when n is a multiple of 3". The DP found it; the formula replaces it.

When the answer is just a winner, try the true/false version first, then look for a pattern in the small cases. Interviewers who ask "who wins" often hope you will find the simple formula once the DP confirms it.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 f(R) − f(L−1)
Count over a range by counting two prefixes. The same trick as prefix sums, applied to counting — and it halves the work you have to think about.
⛔ DO NOT MEMO TIGHT
A tight state’s value depends on the bound, not just the state. Memoise only the free states, and remember the started flag or leading zeros will bite.
💡 DIFFERENCE, NOT TURN
For two-player games, store the score difference from the mover’s perspective. Minimax then collapses to one minus sign and the turn leaves the state.
⚠️
Common mistakes
  • Caching tight states in digit DP. Their value depends on the bound; only free states can be reused.
  • Forgetting the started flag, so leading zeros count as real digits and small numbers are judged wrongly.
  • nextTight = (d==limit) without the and tight — once a state is free, it can never become tight again.
  • Computing [L,R] as f(R) − f(L) instead of f(R) − f(L−1), which leaves out L itself.
  • Not stress-testing a digit DP. Bugs per line are high and wrong answers look believable.
  • Filling an expectation DP forwards when E[s] depends on larger s; it must go backwards.
  • Running a DP pass when the states loop back. A self-loop means solving an equation, or Gaussian elimination.
  • Comparing floating-point values with ==, or letting rounding error build up over many steps.
  • Adding an isMaximising flag when the score-difference form makes it unnecessary — twice the state and twice the bugs.
  • Getting the sign wrong: piles[i] - dp[i+1][j], never +. The opponent's gain is your loss.
  • Assuming the first player always wins because they do in the standard stone game (where n is even and the total is odd). Check it against the real constraints.

Interview drill

Warm-up: Count the integers in [1, 10¹⁸] whose digits are non-decreasing.

How a strong answer sounds
The range is far too large to loop over, and the property depends on the number's digits, so this is digit DP. I turn "count in [L, R]" into f(R) − f(L−1), the same subtract-the-prefix trick as prefix sums. Then I only need f(N), the count in [0, N]. I write N's digits into an array and build candidate numbers left to right. The state has four parts. pos is the digit position being placed. tight says whether the digits so far exactly match N's; it decides whether this digit is capped at digits[pos] or free to be 0–9. started says whether a non-zero digit has been placed, since 007 and 7 are the same number. And for this property, the previous digit, because non-decreasing means each digit is at least the one before. The transition loops d from 0 to the limit, skips d < last once started, and recurses with nextTight = tight and (d == limit). The and matters: once you have gone strictly below the bound, you can never be pinned to it again. The base case at pos == length returns 1 if started, else 0. I cache on (pos, last), but only for states that are not tight and have started. A tight state's answer depends on N, not just on the state, and there is exactly one tight path per position anyway, so caching it gains nothing and risks a wrong answer. With 19 digits and 10 possible previous digits, that is fewer than 200 states, each doing ten steps of work — instant. The last thing I would do, and say out loud, is stress-test it: a brute-force loop over the first hundred thousand numbers, compared with the DP for every bound in that range. Digit DP is short, but it has an unusually high bug rate, and a wrong answer here looks completely believable.

Deeper: Stone game — players take from either end, both optimal. Who wins, and what is the state?

How a strong answer sounds
The naive version adds a boolean for whose turn it is, and branches into a max for me and a min for my opponent. That works, but it doubles the state and invites sign errors. So I prefer the score-difference form. dp[i][j] is the largest value of (my score − opponent's score) that the player about to move can guarantee on the range [i..j]. Measuring it from whoever moves builds the turn in, and removes that dimension entirely. Base case: dp[i][i] = piles[i], since with one stone left the mover takes it. For the transition: if I take the left stone, I gain piles[i]. Then my opponent faces [i+1..j] and gets dp[i+1][j] measured from their side, which is exactly minus mine. So my net result is piles[i] − dp[i+1][j]. The right end works the same way, and dp[i][j] is the max of the two. That single minus sign is the minimax; it is the same idea as negamax in game-tree search. This is an interval DP, so it needs the increasing-length fill order — dp[i][j] reads strictly shorter ranges. The first player wins exactly when dp[0][n−1] > 0. If the actual scores are wanted, I get them from the total: my score is (total + diff) / 2. O(n²) time and space, which a rolling diagonal cuts to O(n) space. I would raise two follow-ups. If a player may take up to k stones from one end, the same structure holds with an extra loop over how many. And if the question is only "who wins", not "by how much", the true/false win/lose version is often enough — a state is winning if some move leaves the opponent in a losing state. It often reveals a simple formula, the way Nim comes down to the XOR of the pile sizes.

🧠 Key takeaways

  • Digit DP builds a number left to right. tight tracks whether you are still pinned to the bound, and only free states may be cached.
  • Count in [L,R] as f(R) − f(L−1), and always stress-test the result against brute force.
  • Expectation DP uses linearity: one step, plus the weighted average of what comes next, filled in dependency order.
  • A state that can loop back to itself means solving an equation (or Gaussian elimination), not a DP pass.
  • Store the score difference from the mover's point of view, and minimax shrinks to one minus sign.

Check your understanding

In digit DP, what does the tight flag mean?

And nextTight = tight and (d==limit). Once you place a strictly smaller digit, every remaining digit is free and can never be pinned again.

Why should tight states not be memoised?

The number of ways to finish a free state depends only on the state, so it can be reused. Caching a tight state can also give a wrong answer if the cache is reused for a different bound.

Expected number of dice rolls until you see a 6. Why can a DP pass not compute it?

A state that loops back to itself with probability p multiplies the expected time by 1/(1−p). If several states depend on each other, write out the system of equations and use Gaussian elimination.

In the stone game, why is the transition piles[i] - dp[i+1][j] rather than +?

That one minus sign is the minimax. It captures best play by both sides, with no isMaximising flag and no doubled table.

In the boolean win/lose formulation, a state is winning when…

One good move is all you need; it is losing only when every option hands the opponent a win. This version often reveals a simple formula — Nim comes down to whether the XOR of the pile sizes is non-zero.
