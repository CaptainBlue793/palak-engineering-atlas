The problem

Swim in Rising Water. You are given an N × N grid where grid[i][j] is the elevation of that square. Rain begins, and at time t the water level everywhere is t. You start at (0,0) and want to reach (N-1, N-1). You may move to any of the four adjacent squares, and swimming is infinitely fast — but you can only be on a square at time t if grid[i][j] ≤ t, and you can only move between two squares if both are under water. Return the least time at which you can reach the destination. Constraints: N ≤ 50, elevations are a permutation of 0 … N²−1.

Stage 1 — Read the structure, not the story

1
Strip the narrative and restate it

The rain and the swimming are decoration. What remains: a grid graph with four-directional movement, and a path whose cost is the maximum cell value along it. We want the path minimising that maximum. Everything else in the statement is flavour.

Two observations to state aloud, because both matter later. First, time never helps you wait — since swimming is instantaneous and the water only rises, if you can reach a square at all you can reach it at the moment the water covers the highest square on your route. So there is no time dimension in the state; the answer is purely a property of the path. Second, the objective is minimise the maximum, not minimise the sum. That phrase is the whole problem.

Restated: find the minimum, over all four-directionally-connected paths from (0,0) to (N-1,N-1), of the largest elevation on the path. This is sometimes called the bottleneck shortest path or the minimax path.

🚫
Why the two reflex answers fail
  • BFS is wrong. BFS finds the path with the fewest steps, and step count has nothing to do with the maximum elevation. A long detour through low ground routinely beats a short hop over a peak. (Worth saying: BFS is only correct when every edge costs the same, and here the "cost" is not even additive.)
  • Grid DP is wrong. Movement is allowed in all four directions, so the dependencies are cyclic and no fill order exists (Chapter 42). If you catch yourself wanting to run the DP loops repeatedly until nothing changes, that is Bellman-Ford and it means you have a graph problem.
  • Plain Dijkstra is almost right — and this is the interesting one. Dijkstra minimises a sum of edge weights. Here we want to minimise a maximum. The good news is that the greedy argument behind Dijkstra does not actually depend on addition; it needs only that extending a path never decreases its cost. Both sum and max have that property, so Dijkstra works with one line changed.

Stage 2 — The brute force, and the redundancy

2
State the O(N⁴) version first

The brute force writes itself once the restatement exists: for each candidate time t from 0 upward, flood-fill from (0,0) using only cells with elevation ≤ t, and stop at the first t that reaches the destination. With elevations forming a permutation of 0 … N²−1 there are N² candidates, and each flood fill is O(N²), so this is O(N⁴) — about 6 million operations at N = 50, which actually passes. Say that: the brute force is already fast enough, which means the rest of the discussion is about elegance and about what happens if N grows.

Now name the redundancy. Each flood fill re-explores the entire region it explored last time, plus a little more. Two independent ways to remove it:

  • The candidate t is monotone — if you can finish by time t, you can finish by t+1. So binary search the answer instead of scanning it: O(N² log N²).
  • Or never restart at all — add cells in increasing elevation order and maintain connectivity incrementally, which is union-find, or explore greedily in order of the lowest frontier, which is Dijkstra.

Solution A — binary search on the answer

binary search the time, flood fill to checkO(N² log N)O(N²)
// Feasibility is MONOTONE in t: if the destination is reachable using only
// cells with elevation <= t, it is also reachable for any larger t, because
// raising t only ever ADDS usable cells. That monotonicity is exactly the
// precondition binary search needs — say it out loud, do not assume it.
bool canReach(int t,vector<vector<int>> &grid){
	int N=grid.size();

	if(grid[0][0]>t)return false;   // cannot even start

	vector<vector<bool>> visited(N,vector<bool>(N,false));
	queue<pair<int,int>> q;

	q.push({0,0});
	visited[0][0]=true;            // mark on ENQUEUE, always

	int dr[]={1,-1,0,0};
	int dc[]={0,0,1,-1};

	while(!q.empty()){
		auto [r,c]=q.front();

		q.pop();

		if(r==N-1 and c==N-1)return true;

		for(int d=0;d<4;d++){
			int nr=r+dr[d];
			int nc=c+dc[d];

			if(nr<0 or nr>=N or nc<0 or nc>=N)continue;
			if(visited[nr][nc])continue;
			if(grid[nr][nc]>t)continue;     // still above water

			visited[nr][nc]=true;
			q.push({nr,nc});
		}
	}

	return false;
}

int swimInWater(vector<vector<int>> &grid){
	int N=grid.size();

	// the answer is at least the higher of the two endpoints, and at most
	// the largest elevation in the grid
	int low=max(grid[0][0],grid[N-1][N-1]);
	int high=N*N-1;

	while(low<high){                   // find the SMALLEST feasible t
		int mid=low+(high-low)/2;

		if(canReach(mid,grid))high=mid;   // feasible -> try smaller
		else low=mid+1;                  // infeasible -> must go higher
	}

	return low;
}
The loop shape is the "smallest feasible value" template from Chapter 9 — while(low<high), high=mid on success, low=mid+1 on failure, return low. It has no off-by-one because it never needs a final comparison. The tightened lower bound is a small but genuine improvement worth mentioning: no route can have a maximum below either endpoint's own elevation, since both are always on the path. Cost is O(N²) per check times log(N²) checks, so O(N² log N).

Solution B — Dijkstra with one line changed

bottleneck Dijkstra — max instead of plusO(N² log N)O(N²)
// dist[r][c] = the minimum achievable MAXIMUM elevation on any path from
//              (0,0) to (r,c).
// Dijkstra's correctness needs only that extending a path never lowers its
// cost. max(...) satisfies that just as + does, so the algorithm carries over
// unchanged — except for the relaxation itself.
int swimInWater(vector<vector<int>> &grid){
	int N=grid.size();
	vector<vector<int>> dist(N,vector<int>(N,INT_MAX));

	// min-heap of {cost so far, row, col} — SORT KEY FIRST
	priority_queue<tuple<int,int,int>,
	               vector<tuple<int,int,int>>,
	               greater<tuple<int,int,int>>> pq;

	dist[0][0]=grid[0][0];
	pq.push({grid[0][0],0,0});

	int dr[]={1,-1,0,0};
	int dc[]={0,0,1,-1};

	while(!pq.empty()){
		auto [d,r,c]=pq.top();

		pq.pop();

		if(d>dist[r][c])continue;        // a stale heap entry
		if(r==N-1 and c==N-1)return d;  // first pop of the goal is optimal

		for(int k=0;k<4;k++){
			int nr=r+dr[k];
			int nc=c+dc[k];

			if(nr<0 or nr>=N or nc<0 or nc>=N)continue;

			// the ONLY change from textbook Dijkstra:
			int cost=max(d,grid[nr][nc]);   // not d + weight

			if(cost<dist[nr][nc]){
				dist[nr][nc]=cost;
				pq.push({cost,nr,nc});
			}
		}
	}

	return -1;                          // unreachable; cannot happen on a full grid
}
This is the cleanest of the three and the one I would write. Four details carried over from Chapter 30 and worth stating: the sort key comes first in the tuple so the default comparison orders by cost; greater makes it a min-heap; the d > dist[r][c] check discards stale entries, which is the lazy-deletion idiom that avoids needing a decrease-key operation; and the first pop of the destination is already optimal, so you can return immediately rather than draining the heap. The generalisation is worth naming too: replacing + with any monotone combiner gives you "widest path", "most reliable path" (with min and multiplication of probabilities), and this bottleneck variant — all the same algorithm.

Solution C — union-find, adding cells in elevation order

incremental connectivityO(N²·α)O(N²)
// Because the elevations are a permutation of 0 .. N*N-1, "raise the water to
// t" means exactly "activate the cell whose elevation is t". So activate cells
// in increasing elevation order, union each with its already-active
// neighbours, and the answer is the first t at which start and goal are joined.
// Nothing is ever recomputed — that is the redundancy removed completely.
class DSU{
	vector<int> parent,rank;

public:
	DSU(int n){
		parent.resize(n);
		rank.assign(n,0);

		for(int i=0;i<n;i++)
		parent[i]=i;
	}

	int find(int x){
		if(parent[x]==x)return x;

		return parent[x]=find(parent[x]);   // path compression
	}

	bool unite(int a,int b){
		a=find(a);
		b=find(b);

		if(a==b)return false;

		if(rank[a]<rank[b])swap(a,b);

		parent[b]=a;

		if(rank[a]==rank[b])rank[a]++;

		return true;
	}
};

int swimInWater(vector<vector<int>> &grid){
	int N=grid.size();
	vector<int> whereIs(N*N);            // elevation -> flattened index

	for(int r=0;r<N;r++)
	for(int c=0;c<N;c++)
	whereIs[grid[r][c]]=r*N+c;

	DSU dsu(N*N);
	vector<bool> active(N*N,false);
	int dr[]={1,-1,0,0};
	int dc[]={0,0,1,-1};

	for(int t=0;t<N*N;t++){
		int id=whereIs[t];
		int r=id/N;
		int c=id%N;

		active[id]=true;

		for(int k=0;k<4;k++){
			int nr=r+dr[k];
			int nc=c+dc[k];

			if(nr<0 or nr>=N or nc<0 or nc>=N)continue;
			if(!active[nr*N+nc])continue;   // neighbour still dry

			dsu.unite(id,nr*N+nc);
		}

		if(dsu.find(0)==dsu.find(N*N-1))return t;
	}

	return -1;
}
The fastest of the three, and the one that exploits the permutation constraint. Reading "elevations are a permutation of 0 … N²−1" and realising it means "the cells activate one at a time, in a known order" is the observation being tested — without it, you would have to sort the cells by elevation first, which is O(N² log N) and lands you back with the others. Note the connectivity check is after the unions for time t, so the returned t is the first moment the two are joined. This is also the shape of Kruskal's algorithm: process edges in weight order and union — which is not a coincidence, since the bottleneck path between two nodes always lies on the minimum spanning tree.

I would write the Dijkstra. It is the shortest, it does not depend on the permutation constraint — so it survives the follow-up "what if elevations can repeat, or are arbitrary 64-bit values?" unchanged — and the one-line difference from textbook Dijkstra is a clean thing to explain. I would mention the other two: union-find as the asymptotically best given the permutation, and binary search as the fallback whose correctness is hardest to doubt.

Then verify by tracing. On a 2×2 grid [[0,2],[1,3]]: dist[0][0]=0; pop (0,0,0), relax right to max(0,2)=2 and down to max(0,1)=1; pop (1,1,0), relax right to max(1,3)=3; pop (2,0,1), relax down to max(2,3)=3, no improvement; pop (3,1,1) — that is the goal, return 3. Correct: every route must step on the destination itself, whose elevation is 3.

🧪
The tests to volunteer
  • N = 1 — the answer is grid[0][0]. Does your code return before entering any loop? (In the Dijkstra, (0,0) is the goal and is popped first, so yes.)
  • The destination is the maximum — [[0,1],[2,3]] → 3. The answer can never be below either endpoint.
  • The start is the maximum — [[3,0],[1,2]] → 3. Catches a dist[0][0]=0 initialisation bug.
  • A forced detour — a grid where the direct route crosses a peak but a longer route stays low. This is the test that fails a BFS-based attempt, and it is the one to write first.
  • Full-size N = 50 — check the timing and that no INT_MAX arithmetic occurs.
  • Stress test — compare against the O(N⁴) brute force on random 3×3 and 4×4 permutation grids. That settles it in seconds (Chapter 53).
🔮
The follow-ups you would actually get
  • "What if elevations are arbitrary, with duplicates?" Dijkstra is unchanged. Binary search must search over the sorted distinct values rather than 0…N²−1. Union-find must sort the cells first, costing O(N² log N).
  • "Eight-directional movement?" Extend the direction arrays to eight entries. Nothing else changes — which is a good argument for keeping the directions in arrays rather than writing four branches.
  • "Return the actual path, not just the time." Store a parent per cell when you relax, then walk back from the destination. In the union-find version this is harder, which is a real argument for Dijkstra.
  • "Now minimise the sum of elevations instead." Change max(d, grid[nr][nc]) back to d + grid[nr][nc] — it becomes ordinary Dijkstra. Neither binary search nor union-find adapts, because sum is not monotone in a threshold. This follow-up is the point of the whole problem.
  • "What if the water can also fall, so timing matters?" Then time enters the state: dist[r][c][t], and it becomes a layered graph. A good moment to say that adding a dimension is the standard response when the state is insufficient (Chapter 38).
  • "Many queries of the form (start, goal) on a fixed grid?" Build the minimum spanning tree once; the bottleneck between any two nodes is the maximum edge on their unique MST path, answerable in O(log N) with binary lifting. Naming this is enough.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 STRIP THE STORY
Rain and swimming are decoration; "minimise the maximum along a path" is the problem. Restate in your own words before choosing a tool.
💡 MONOTONE COMBINER
Dijkstra needs only that extending a path never lowers its cost. Swap + for max and you have bottleneck paths; min gives widest path.
💡 PICK FOR FOLLOW-UPS
Three solutions were correct; choose the one that survives "what if elevations repeat?" or "now minimise the sum". That judgement is what is actually being assessed.
⚠️
Common mistakes on this problem
  • Using BFS and expecting the fewest steps to matter. The objective is the maximum elevation, not the path length.
  • Using grid DP. Four-directional movement makes the dependencies cyclic (Chapter 42).
  • Keeping d + grid[nr][nc] in the Dijkstra. That solves a different problem and returns a larger number.
  • Initialising dist[0][0] = 0 rather than grid[0][0] — you start on a cell, and its elevation counts.
  • Putting the coordinates before the cost in the heap tuple, so it orders by row instead of by cost.
  • Forgetting greater<>, giving a max-heap and an entirely wrong traversal order.
  • Omitting the stale-entry check if(d > dist[r][c]) continue; — correct but slower, and it obscures the invariant.
  • Marking visited on dequeue in the BFS feasibility check (Chapter 53, bug 1).
  • Binary searching from low = 0 when the endpoints force a higher floor — harmless but sloppy, and worth saying you noticed.
  • Checking connectivity before the unions in the union-find version, returning t+1.
  • Not asking whether elevations are a permutation. The answer changes which solution is best.

Interview drill

Warm-up: Present this problem end to end as you would in a round, in about four minutes of speech.

How a strong answer sounds
Let me restate it: I have an N×N grid of elevations, I move four-directionally from the top-left to the bottom-right, and I can only occupy a cell once the water level reaches its elevation. Since swimming is instantaneous and the water only rises, waiting never helps — so the arrival time is just the maximum elevation along whichever path I take, and I want to minimise that maximum. Stripped of the story, this is the bottleneck shortest path on a grid graph. Two quick clarifications: are elevations a permutation of 0 to N²−1, and how large is N? Given N ≤ 50 and a permutation, that is 2,500 cells. The brute force is: for each candidate time t, flood fill from the origin using only cells at or below t, and take the first t that reaches the goal. That is O(N⁴), about 6 million operations, which actually passes — but it re-explores the same region every time, and there are two ways to remove that. First, feasibility is monotone in t, since raising the water only adds usable cells, so I can binary search t instead of scanning it: O(N² log N). Second and better, I can avoid restarting at all with a modified Dijkstra. I define dist[r][c] as the minimum achievable maximum elevation on any path to that cell, and relax with max(d, grid[nr][nc]) instead of d + weight. That is legitimate because Dijkstra's greedy argument needs only that extending a path never lowers its cost, and max satisfies that just as addition does. dist[0][0] starts at grid[0][0], not 0, because I begin standing on that cell. O(N² log N), and the first pop of the destination is already optimal so I can return immediately. There is also a union-find solution that is asymptotically better, O(N²·α): because the elevations are a permutation, "raise the water to t" means exactly "activate the cell with elevation t", so I activate cells in order, union each with its active neighbours, and return the first t at which the start and goal share a root. I would write the Dijkstra, because it is shortest and it survives the follow-up where elevations are arbitrary with duplicates, whereas union-find would then need a sort. Shall I code it?

Deeper: Justify that Dijkstra with max is actually correct. The interviewer is not satisfied by "it works".

How a strong answer sounds
Dijkstra's correctness rests on one property of the cost function, and it is not addition. The invariant is: when a node is popped from the min-heap, its recorded cost is final. The proof is by contradiction — suppose node u is popped with cost d but some cheaper path to u exists. That path must leave the settled set at some point, through a node v still in the heap. Since the heap is a min-heap and u was popped first, v's current cost is at least d. And the cheaper path continues from v to u, so its total cost is at least the cost of reaching v — which requires only that extending a path never decreases its cost. That gives cost ≥ d, contradicting the assumption that it was cheaper. Notice what the argument used: monotonicity of the combiner, and nothing about addition. So the property I need is that combining a path cost with one more edge is non-decreasing. For sums with non-negative weights, that holds — and the non-negativity is exactly why Dijkstra fails with negative edges, since there the extension can reduce the cost and the settled invariant breaks. For max, it holds unconditionally: max(d, x) ≥ d for any x whatsoever, even negative elevations. So the bottleneck version is if anything on safer ground than the additive one. That reframing also tells me what else I can plug in: min with a maximising heap gives the widest-path problem, and multiplying probabilities in [0,1] with a max-heap gives the most-reliable-path problem, because multiplying by a value at most 1 is also monotone. All the same algorithm, one line different. I would add one honest note: the argument assumes the cost of a path is determined by the sequence of cells, which it is here, and that I am comparing totals rather than anything history-dependent — if the cost depended on, say, how many times I had turned, the state would need augmenting and this would no longer be plain Dijkstra.

🧠 Key takeaways

  • Strip the story first. "Minimise the maximum along a path" is the entire problem; rain and swimming are decoration.
  • BFS needs uniform edge cost and grid DP needs an acyclic order — both fail here, and saying why is part of the answer.
  • Dijkstra's proof needs only that extending a path never lowers its cost, so max works exactly like +.
  • Monotone feasibility permits binary search on the answer; a permutation of values permits incremental union-find.
  • Choose the solution that survives the follow-up, not just the one that is asymptotically fastest.

Check your understanding

Why is plain BFS wrong for this problem?

BFS is only correct when every edge costs the same. Here the objective is not even additive, which is the deeper reason a queue cannot order the exploration correctly.

Replacing Dijkstra's d + weight with max(d, elevation) is valid because…

That is also exactly why negative edge weights break Dijkstra: there, extending a path can lower the cost, so the "popped means final" invariant fails. The max version needs no non-negativity at all.

What makes binary search on the answer applicable here?

Monotonicity is the precondition, and it should be stated rather than assumed. The check being cheap is what makes it efficient, not what makes it correct.

Which fact makes the union-find solution possible in O(N²·α) with no sorting?

Without the permutation you would have to sort the cells by elevation, which costs O(N² log N) and removes the advantage. Reading that constraint is the point.

The follow-up changes the objective to minimising the sum of elevations. What happens?

This is why Dijkstra is the choice to code: it survives the follow-up with one character changed, and being able to say that in advance is exactly the judgement being assessed.
