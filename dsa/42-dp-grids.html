DP on Grids

Grid DP is the friendliest family in dynamic programming: the state is literally a cell, and the transition is "where could I have come from?". The reason it deserves its own chapter is that grids teach three things cleanly — how the movement rules determine the loop order, how to space-optimise to a single row, and what to do when one pair of indices is no longer enough to describe the state.

  • Read the movement rules off the problem and turn them into a transition
  • Count paths, minimise path cost, and handle obstacles
  • Solve maximal square, where the state is "ending at this cell"
  • Space-optimise a grid DP to one row, and know when you cannot
  • Handle multi-agent grids (cherry pickup) by synchronising on a shared step counter

The movement rules are the recurrence

Every grid DP starts the same way. Write down which moves are legal, then reverse them: if you may move right and down, then a cell can only be reached from the left or from above. That reversal is the transition, and it also fixes the loop order — you must fill left-to-right, top-to-bottom, so the cells you depend on are already done.

🚩
The line between grid DP and grid graph search

DP requires the state dependencies to form a DAG — each state must depend only on states that are strictly "earlier" in some ordering. Right-and-down movement gives that for free, because i+j strictly increases along any path. The moment all four directions are allowed, a cell can depend on a cell that depends on it, the ordering vanishes, and no loop order can work. That is not a harder DP; it is a different tool — BFS for unweighted, Dijkstra or 0-1 BFS for weighted. If you find yourself wanting to run the DP loops "a few times until nothing changes", you have a graph problem wearing a grid costume (and what you are reinventing is Bellman-Ford).

Unique paths
// Moving only right and down, how many distinct paths from (0,0) to (n-1,m-1)?
// dp[i][j] = the number of ways to reach cell (i,j).
int uniquePaths(int n,int m){
	vector<vector<int>> dp(n,vector<int>(m,0));

	dp[0][0]=1;                       // one way to be at the start

	for(int i=0;i<n;i++){
		for(int j=0;j<m;j++){
			if(i==0 and j==0)continue;

			if(i>0)dp[i][j]+=dp[i-1][j];   // came from above
			if(j>0)dp[i][j]+=dp[i][j-1];   // came from the left
		}
	}

	return dp[n-1][m-1];
}

Counting adds; optimising takes a min or max. That is the only difference between these two columns. Note the if(i>0) guards: they replace a separate pass over the first row and column, and I prefer them because the transition then lives in exactly one place. There is also a closed form — C(n+m−2, n−1) — but the DP generalises to obstacles and costs and the closed form does not.

Minimum path sum
// Each cell has a cost; minimise the total cost of the path.
// dp[i][j] = the cheapest cost of reaching cell (i,j).
int minPathSum(vector<vector<int>> &grid){
	int n=grid.size();
	int m=grid[0].size();
	vector<vector<int>> dp(n,vector<int>(m,0));

	for(int i=0;i<n;i++){
		for(int j=0;j<m;j++){
			if(i==0 and j==0){
				dp[0][0]=grid[0][0];
				continue;
			}

			int mini=INT_MAX;

			if(i>0)mini=min(mini,dp[i-1][j]);
			if(j>0)mini=min(mini,dp[i][j-1]);

			dp[i][j]=grid[i][j]+mini;
		}
	}

	return dp[n-1][m-1];
}

Same skeleton, same guards, same loop order — += becomes min and the cell's own cost is added on. I deliberately write these two with an identical shape, the way LevelOrder and ZigZag share one loop, so that the difference between "count" and "optimise" is a single visible line rather than a whole new function.

✍️
My convention: guard the transition, do not pre-fill the borders

Many write-ups initialise row 0 and column 0 in two separate loops before the main pass. It works, but it duplicates the arithmetic in three places, and every grid-DP bug I have written was the border loops and the main loop disagreeing — usually about obstacles, where the border loop keeps filling 1s past a wall. Writing if(i>0) and if(j>0) inside the single loop keeps one source of truth. It costs two branch checks per cell and buys correctness you can see at a glance.

Obstacles

unique paths with obstacles — rolled to one rowO(n·m)O(m)
// grid[i][j]==1 means a wall. A wall has zero ways to be reached and passes
// nothing onward — so the whole cell is simply left as 0.
int uniquePathsWithObstacles(vector<vector<int>> &grid){
	int n=grid.size();
	int m=grid[0].size();

	if(grid[0][0]==1)return 0;   // the start itself is blocked

	vector<int> prev(m,0);         // one row is enough

	for(int i=0;i<n;i++){
		vector<int> cur(m,0);

		for(int j=0;j<m;j++){
			if(grid[i][j]==1){
				cur[j]=0;             // a wall: leave it at 0 and move on
				continue;
			}

			if(i==0 and j==0){
				cur[j]=1;
				continue;
			}

			int fromTop=(i>0)?prev[j]:0;
			int fromLeft=(j>0)?cur[j-1]:0;

			cur[j]=fromTop+fromLeft;
		}

		prev=cur;
	}

	return prev[m-1];
}
Note which array each dependency reads. prev[j] is the cell above (previous row); cur[j-1] is the cell to the left (this row, written earlier in this same pass). That pairing is the entire space optimisation, and mixing them up is the classic error — prev[j-1] gives you the diagonal, not the left. Also, the wall check must come before the start check, or a blocked start slips through as one way.
🪣
Space optimisation: one row, and when it is unavailable

A grid DP whose transition only reaches the previous row and the current row collapses from O(n·m) to O(m) space. Two idioms:

  • Two rows (prev and cur, as above) — always safe, and clearer. Prefer it.
  • One row in place — possible when you need only the cell above and the cell to the left, because before you write dp[j] its old value is "above". But if you also need the diagonal [i-1][j-1], it has already been overwritten; save it in a temporary first — the same trap as edit distance in Chapter 41.

You cannot space-optimise when you must reconstruct the path. Recovering the actual route needs the full table, or a parent stored per cell. Interviewers often ask for the cost first and the route as a follow-up — mention the trade-off rather than being caught by it.

Maximal square: the state is "ending at this cell"

A different flavour. Nothing travels through the grid; we are looking for a shape. The trick — the same one behind Kadane and longest common substring — is to make dp[i][j] describe the best answer whose bottom-right corner is exactly this cell, then take the maximum over the whole table.

largest square of 1sO(n·m)O(n·m) → O(m)
// dp[i][j] = the side length of the largest all-1 square whose BOTTOM-RIGHT
//            corner is (i,j).
// A square of side k ending here needs squares of side k-1 ending at the cell
// above, the cell left, and the cell diagonally up-left. The SMALLEST of those
// three is the bottleneck.
int maximalSquare(vector<vector<char>> &matrix){
	int n=matrix.size();
	int m=matrix[0].size();
	vector<vector<int>> dp(n+1,vector<int>(m+1,0));
	int maxi=0;

	for(int i=1;i<=n;i++){
		for(int j=1;j<=m;j++){
			if(matrix[i-1][j-1]=='1'){
				dp[i][j]=1+min({dp[i-1][j],dp[i][j-1],dp[i-1][j-1]});
				maxi=max(maxi,dp[i][j]);
			}
			// a 0 cell ends no square — dp stays 0
		}
	}

	return maxi*maxi;                // the AREA, not the side
}
Three neighbours, and the min is the insight. If any of the three can only support a side of 2, this cell cannot support 3 — the square would poke out of the region of ones. Here I do pad the table to (n+1)×(m+1) rather than guarding, because with three dependencies the guards start to outweigh the sentinel row. And return the area: forgetting to square is the most common wrong answer on this problem. To count all square submatrices instead, sum every dp[i][j] — a cell with dp = 3 is the corner of exactly three squares.

Two agents: cherry pickup

Now the hard case. Two paths cross the grid at once and interact — a cell picked by both counts once. A single (i,j) is no longer enough state, so we add dimensions until the state is sufficient, then look for a reason one of them is redundant.

cherry pickup II — two robots, synchronised rowsO(n·m²)O(m²)
// Two robots start at (0,0) and (0,m-1). Each moves down one row per step and
// may shift its column by -1, 0 or +1. Maximise the cherries collected, with a
// shared cell counted once.
//
// KEY: both robots move down exactly once per step, so their ROW is always the
// same. That shared row is the synchroniser — one index serves both, turning an
// apparent 4D state (i1,j1,i2,j2) into a 3D one.
// dp[i][a][b] = the best total from row i onward, robots in columns a and b.
int cherryPickup(vector<vector<int>> &grid){
	int n=grid.size();
	int m=grid[0].size();

	// front[a][b] = best from the row BELOW, robots at columns a and b
	vector<vector<int>> front(m,vector<int>(m,0));

	for(int i=n-1;i>=0;i--){
		vector<vector<int>> cur(m,vector<int>(m,0));

		for(int a=0;a<m;a++){
			for(int b=0;b<m;b++){
				int pick=grid[i][a];

				if(a!=b)pick+=grid[i][b];   // the same cell counts once

				int best=0;

				for(int da=-1;da<=1;da++){
					for(int db=-1;db<=1;db++){
						int na=a+da;
						int nb=b+db;

						if(na<0 or na>=m or nb<0 or nb>=m)continue;

						best=max(best,front[na][nb]);
					}
				}

				cur[a][b]=pick+best;
			}
		}

		front=cur;
	}

	return front[0][m-1];
}
Nine transitions per state, and a shared row that removes a dimension. The if(a!=b) line is the whole interaction between the robots; drop it and every shared cell is double-counted. This is the pattern for every two-agent grid problem: find the quantity that advances identically for both agents — here the row; in the original Cherry Pickup, where one robot goes down-right and the other returns up-left, you reverse the second path and then i+j is the clock — and index on it. Without that, the state is 4D and the cost is O(n²m²).
🧠
Grid variants worth recognising on sight
  • Triangle / falling path — movement is down plus a column shift, so three dependencies from the row above. Identical skeleton.
  • Minimum falling path with no two adjacent columns — the same, but excluding j itself; track the best and second-best of the previous row to get O(n·m) instead of O(n·m²).
  • Paths with a fixed number of moves, or a budget — add a dimension, dp[i][j][k]. The extra index is just another clause in the state sentence.
  • Dungeon game (minimum starting health) — must be filled bottom-right to top-left, because the requirement propagates backwards. The fill direction follows the dependency, not habit.
  • Maximal rectangle — not grid DP at all: build a histogram per row and reuse largest-rectangle-in-histogram with a monotonic stack (Chapter 14).
  • Count paths modulo 10⁹+7 — path counts overflow fast; unique paths on a 30×30 grid already exceeds 32-bit range.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 REVERSE THE MOVES
Legal moves right and down means a cell is entered from left or above. Reversing the movement rules gives you both the transition and the loop order.
⛔ LEFT vs DIAGONAL
Rolling one row: "above" is prev[j] and "left" is cur[j-1]. prev[j-1] is the diagonal, and using it produces plausible wrong answers.
💡 FOUR DIRECTIONS ⇒ NOT DP
If all four directions are allowed the dependencies are cyclic and no fill order exists. That is BFS, 0-1 BFS or Dijkstra — not a bigger table.
⚠️
Common mistakes
  • Using grid DP when all four directions are allowed. The dependencies become cyclic; that is BFS, 0-1 BFS or Dijkstra.
  • Border loops that disagree with the main loop — especially about obstacles. Guard the transition instead.
  • Reading prev[j-1] for "the cell to the left". Left is cur[j-1]; prev[j-1] is the diagonal.
  • Checking the start before the wall in the obstacles version, so a blocked start returns 1.
  • Returning the side instead of the area in maximal square.
  • Taking a max instead of a min of the three neighbours in maximal square — the bottleneck is the limit.
  • Forgetting if(a!=b) in cherry pickup, double-counting shared cells.
  • Initialising a min-cost DP to 0 rather than a large sentinel, so unreachable cells look free.
  • Integer overflow on path counts. Use long long, or take the modulus as you go.
  • Space-optimising and then being asked for the path. Reconstruction needs the full table or parent pointers.

Interview drill

Warm-up: Minimum path sum — then: "what if you could also move up and left?"

How a strong answer sounds
With right-and-down movement I define dp[i][j] as the minimum cost of reaching cell (i,j). Because the only legal moves are right and down, a cell can only be entered from above or from the left, so dp[i][j] = grid[i][j] + min(dp[i−1][j], dp[i][j−1]), with each term guarded for the first row and column. A plain top-to-bottom, left-to-right double loop satisfies the dependencies, giving O(n·m) time and O(m) space with a rolling row — though I would keep the full table if I also needed the route, since reconstruction requires walking back through it. Now, if up and left become legal, this stops being a DP problem, and the reason is structural rather than a matter of difficulty. DP needs the state dependencies to form a DAG, and with right-and-down the quantity i+j strictly increases along any path, which supplies that ordering for free. With all four directions a cell can lie on a cycle, so no fill order exists — and iterating the loops until the values stop changing is just a slow Bellman-Ford. The correct tool is shortest path on the grid graph: Dijkstra with a min-heap keyed on accumulated cost, O(n·m log(n·m)); plain BFS if every cell costs the same; 0-1 BFS with a deque if the costs are only 0 and 1. I would say that out loud rather than trying to patch the loops, because recognising which family a problem belongs to is the skill actually being tested here.

Deeper: Cherry pickup II. Why is the state three-dimensional and not four?

How a strong answer sounds
The naive state is both robots' positions, (i1, j1, i2, j2), which is O(n²m²) states — far too many. The saving observation is that both robots move down exactly one row per step, so after k steps both are in row k: their rows are always equal, and one index serves both. That collapses the state to dp[i][a][b] — we are in row i, robot one is in column a, robot two in column b. There are n·m² states with nine transitions each, since each robot independently shifts its column by −1, 0 or +1, so O(n·m²) overall, and O(m²) space with a rolling row because row i only ever reads row i+1. The interaction between the robots is a single line: collect grid[i][a], and add grid[i][b] only if a differs from b, because a shared cell is picked once. Forgetting that condition double-counts, and it is the first thing I would test, with a one-column grid where the robots are always on the same cell. The general lesson is that whenever two agents move through a grid together I look for a quantity that advances identically for both and index on it. In the original Cherry Pickup, where one robot walks down-right and then returns up-left, you reverse the return journey so both travel down-right, and then i+j is the synchroniser. Finding that shared clock is what turns an intractable state into a tractable one, and it is the same move as noticing that a shared row makes i1 and i2 the same variable.

🧠 Key takeaways

  • Reverse the movement rules to get the transition; the transition then fixes the loop order.
  • Right-and-down is a DAG because i+j increases; all four directions is cyclic and needs BFS, 0-1 BFS or Dijkstra.
  • Counting adds the neighbours, optimising takes a min or max of them — otherwise the same skeleton.
  • "Ending at this cell" states (maximal square) take the answer as the maximum over the whole table, and return the area.
  • Multi-agent grids need a shared clock — the same row, or i+j — to keep the state from going 4D.

Check your understanding

You may move right and down. Which cells does dp[i][j] depend on?

If a step goes right or down, then arriving at a cell means the previous cell was to the left or above. Reversing the movement rules is how every grid transition is derived — and it simultaneously tells you the loop order.

All four directions are allowed and every cell has a positive cost. What is the right tool?

DP needs a DAG of dependencies. Right-and-down supplies one because i+j increases; four directions destroys it. Iterating until stable is really just a slow Bellman-Ford.

In maximal square, why take the minimum of the three neighbouring dp values?

If any of the three supports only side 2, this cell cannot reach 3 — the square would extend outside the region of ones. And remember to return side², the area.

Rolling one row with prev and cur: which array holds "the cell to the left"?

prev[j] is the cell above and prev[j-1] is the diagonal. Mixing these up is the classic space-optimisation bug, and it produces plausible-looking wrong answers rather than a crash.

In cherry pickup II, why is the state dp[row][a][b] rather than dp[i1][j1][i2][j2]?

The shared row is a synchronising clock, so the reduction is exact rather than an approximation. Finding such a clock — the row here, i+j in the original Cherry Pickup — is the standard move for multi-agent grid problems.
