DP on Grids

Grid DP is the friendliest kind of dynamic programming. The state is simply a cell, and the transition (the rule for filling it) answers one question: "where could I have come from?". Grids still deserve their own chapter, because they teach three things clearly: how the movement rules decide the loop order, how to shrink the memory to a single row, and what to do when one cell position is no longer enough to describe the state.

  • Read the movement rules from the problem and turn them into a transition
  • Count paths, find the cheapest path, and handle obstacles
  • Solve maximal square, where each cell means "a square ending here"
  • Shrink a grid DP to one row, and know when you cannot
  • Handle two agents moving at once (cherry pickup) by giving them a shared step counter

The movement rules are the recurrence

Why learn grid DP? Robot-path, game-board and "cheapest route through a map" questions are very common, and a grid is the easiest place to see a DP table, because the table has the same shape as the input. The ideas you practise here (reading the dependency direction, rolling rows, adding a dimension when the state is incomplete) carry over to every harder DP.

Every grid DP starts the same way. Write down which moves are allowed, then turn them around. If you may move right and down, a cell can only be reached from the left or from above. That reversed rule is the transition. It also fixes the loop order: fill left-to-right, top-to-bottom, so the cells you need are already done.

Right, Down[i-1][j], [i][j-1]i up, j up — plain double loop

🚩
The line between grid DP and grid graph search

DP needs the dependencies to form a DAG (a directed acyclic graph: arrows with no loops). In plain words, each state may only depend on states that come strictly "earlier" in some order. Moving right and down gives you that for free, because i+j goes up by one on every step.

Once all four directions are allowed, a cell can depend on a cell that depends on it. The order disappears, and no loop order can work. That is not a harder DP — it needs a different tool: BFS when every step costs the same, Dijkstra or 0-1 BFS when steps have costs. If you want to run the DP loops "a few more times until nothing changes", you have a graph problem dressed up as a grid (and you are reinventing Bellman-Ford).

Unique paths
// Moving only right and down, how many distinct paths from (0,0) to (n-1,m-1)?
// dp[i][j] = the number of ways to reach cell (i,j).
int uniquePaths(int n,int m){
	vector<vector<int>> dp(n,vector<int>(m,0));

	dp[0][0]=1;                       // one way to be at the start

	for(int i=0;i<n;i++){
		for(int j=0;j<m;j++){
			if(i==0 and j==0)continue;

			if(i>0)dp[i][j]+=dp[i-1][j];   // came from above
			if(j>0)dp[i][j]+=dp[i][j-1];   // came from the left
		}
	}

	return dp[n-1][m-1];
}

Counting adds; optimising takes a min or max. That is the only difference between these two columns. Note the if(i>0) checks. They replace a separate pass over the first row and column. I prefer them because the transition then lives in exactly one place. There is also a direct formula — C(n+m−2, n−1) — but the DP also handles obstacles and costs, and the formula does not.

Minimum path sum
// Each cell has a cost; minimise the total cost of the path.
// dp[i][j] = the cheapest cost of reaching cell (i,j).
int minPathSum(vector<vector<int>> &grid){
	int n=grid.size();
	int m=grid[0].size();
	vector<vector<int>> dp(n,vector<int>(m,0));

	for(int i=0;i<n;i++){
		for(int j=0;j<m;j++){
			if(i==0 and j==0){
				dp[0][0]=grid[0][0];
				continue;
			}

			int mini=INT_MAX;

			if(i>0)mini=min(mini,dp[i-1][j]);
			if(j>0)mini=min(mini,dp[i][j-1]);

			dp[i][j]=grid[i][j]+mini;
		}
	}

	return dp[n-1][m-1];
}

Same skeleton, same checks, same loop order. += becomes min, and the cell's own cost is added on. I write these two with the same shape on purpose, the way LevelOrder and ZigZag share one loop. That way the difference between "count" and "optimise" is one visible line, not a whole new function.

Both on a 3×3 grid, by hand. Unique paths first. The top row and left column are all 1, because there is only one way to reach them (straight along the edge). Every other cell adds the cell above and the cell to the left:

There are 6 paths to the corner. The formula agrees: every path makes exactly 2 down-moves and 2 right-moves, 4 moves in all, and choosing which 2 of the 4 are "down" gives C(4, 2) = 6. For the costs, the cheapest route is 1 → 3 → 1 → 1 → 1 = 7, along the top and down the right edge. Take the centre cell: it adds its cost 5 to min(4 from above, 2 from the left) = 2, giving 7. Edge cases worth one test each: a 1×1 grid (the answer is the start cell itself: 1 path, or its cost) and a single row or column (only one path exists).

✍️
My convention: guard the transition, do not pre-fill the borders

Many write-ups fill row 0 and column 0 in two separate loops before the main pass. It works, but the same arithmetic now lives in three places. Every grid-DP bug I have written was the border loops and the main loop disagreeing. Usually it was about obstacles: the border loop keeps filling 1s past a wall. Putting if(i>0) and if(j>0) inside the single loop keeps the rule in one place. It costs two checks per cell, and you can see at a glance that it is correct.

Obstacles

A wall simply means "no path may pass through here". In DP terms, the wall cell has 0 ways to be reached, so it passes 0 on to its neighbours. Take the 3×3 grid with a wall in the centre. The counts become 1, 1, 1 on the top row; 1, 0, 1 in the middle row; and 1, 1, 2 on the bottom row. The corner gets 2: the path along the top and right edges, and the path down the left and along the bottom. The 4 paths that went through the centre are gone. Note that a wall on the top row also blocks everything to its right on that row, which is exactly the case pre-filled border loops tend to get wrong.

unique paths with obstacles — rolled to one rowO(n·m)O(m)
// grid[i][j]==1 means a wall. A wall has zero ways to be reached and passes
// nothing onward — so the whole cell is simply left as 0.
int uniquePathsWithObstacles(vector<vector<int>> &grid){
	int n=grid.size();
	int m=grid[0].size();

	if(grid[0][0]==1)return 0;   // the start itself is blocked

	vector<int> prev(m,0);         // one row is enough

	for(int i=0;i<n;i++){
		vector<int> cur(m,0);

		for(int j=0;j<m;j++){
			if(grid[i][j]==1){
				cur[j]=0;             // a wall: leave it at 0 and move on
				continue;
			}

			if(i==0 and j==0){
				cur[j]=1;
				continue;
			}

			int fromTop=(i>0)?prev[j]:0;
			int fromLeft=(j>0)?cur[j-1]:0;

			cur[j]=fromTop+fromLeft;
		}

		prev=cur;
	}

	return prev[m-1];
}
Note which array each read comes from. prev[j] is the cell above (the previous row). cur[j-1] is the cell to the left (this row, written a moment ago in the same pass). That pairing is the whole memory saving. Mixing them up is the classic error: prev[j-1] gives you the diagonal, not the left. Also, check for a wall before checking for the start, or a blocked start slips through as one way.
🪣
Space optimisation: one row, and when it is unavailable

If each cell only reads from the previous row and the current row, you do not need the whole table. Memory drops from O(n·m) to O(m). There are two ways to write it:

  • Two rows (prev and cur, as above). Always safe, and clearer. Prefer it.
  • One row, updated in place. This works when you need only the cell above and the cell to the left. Before you write dp[j], its old value is "above". But if you also need the diagonal [i-1][j-1], it has already been overwritten. Save it in a temporary variable first — the same trap as edit distance in Chapter 41.

You cannot shrink the memory if you must rebuild the path. Recovering the actual route needs the full table, or a stored "came from" pointer per cell. Interviewers often ask for the cost first and the route as a follow-up. Mention the trade-off up front instead of being caught by it.

Maximal square: the state is "ending at this cell"

A different kind of problem. Nothing travels through the grid; we are looking for a shape — the biggest square made only of 1s. The trick is the same one behind Kadane and longest common substring. Make dp[i][j] mean the best answer whose bottom-right corner is exactly this cell. Then take the largest value in the whole table.

largest square of 1sO(n·m)O(n·m) → O(m)
// dp[i][j] = the side length of the largest all-1 square whose BOTTOM-RIGHT
//            corner is (i,j).
// A square of side k ending here needs squares of side k-1 ending at the cell
// above, the cell left, and the cell diagonally up-left. The SMALLEST of those
// three is the bottleneck.
int maximalSquare(vector<vector<char>> &matrix){
	int n=matrix.size();
	int m=matrix[0].size();
	vector<vector<int>> dp(n+1,vector<int>(m+1,0));
	int maxi=0;

	for(int i=1;i<=n;i++){
		for(int j=1;j<=m;j++){
			if(matrix[i-1][j-1]=='1'){
				dp[i][j]=1+min({dp[i-1][j],dp[i][j-1],dp[i-1][j-1]});
				maxi=max(maxi,dp[i][j]);
			}
			// a 0 cell ends no square — dp stays 0
		}
	}

	return maxi*maxi;                // the AREA, not the side
}
Three neighbours, and the min is the key idea. If any of the three can only support a side of 2, this cell cannot support 3 — the square would poke out of the area of ones. Think of a chain: it is only as strong as its weakest link. Here I do pad the table to (n+1)×(m+1) instead of adding checks, because with three neighbours the checks get messier than an extra row of zeros. And return the area: forgetting to square the side is the most common wrong answer here. To count all square submatrices instead, add up every dp[i][j]. A cell with dp = 3 is the corner of exactly three squares.

A trace where the minimum matters. Take this matrix:

matrixdp
row 01 1 11 1 1
row 11 1 11 2 2
row 20 1 10 1 2

Look at the bottom-right cell. Above it is 2 and diagonally up-left is 2, but to its left is only 1, because the 0 in the bottom-left corner stops a bigger square there. So this cell gets 1 + min(2, 1, 2) = 2, not 3. The largest side is 2, so the answer is an area of 4. Taking the max instead of the min would have claimed a 3×3 square that includes the 0.

Two agents: cherry pickup

Now the hard case. Two paths cross the grid at the same time, and they affect each other: a cell picked by both only counts once. One (i,j) is no longer enough to describe the situation. So we add dimensions until the state holds everything we need, then look for a reason one of them is not needed.

cherry pickup II — two robots, synchronised rowsO(n·m²)O(m²)
// Two robots start at (0,0) and (0,m-1). Each moves down one row per step and
// may shift its column by -1, 0 or +1. Maximise the cherries collected, with a
// shared cell counted once.
//
// KEY: both robots move down exactly once per step, so their ROW is always the
// same. That shared row is the synchroniser — one index serves both, turning an
// apparent 4D state (i1,j1,i2,j2) into a 3D one.
// dp[i][a][b] = the best total from row i onward, robots in columns a and b.
int cherryPickup(vector<vector<int>> &grid){
	int n=grid.size();
	int m=grid[0].size();

	// front[a][b] = best from the row BELOW, robots at columns a and b
	vector<vector<int>> front(m,vector<int>(m,0));

	for(int i=n-1;i>=0;i--){
		vector<vector<int>> cur(m,vector<int>(m,0));

		for(int a=0;a<m;a++){
			for(int b=0;b<m;b++){
				int pick=grid[i][a];

				if(a!=b)pick+=grid[i][b];   // the same cell counts once

				int best=0;

				for(int da=-1;da<=1;da++){
					for(int db=-1;db<=1;db++){
						int na=a+da;
						int nb=b+db;

						if(na<0 or na>=m or nb<0 or nb>=m)continue;

						best=max(best,front[na][nb]);
					}
				}

				cur[a][b]=pick+best;
			}
		}

		front=cur;
	}

	return front[0][m-1];
}
Nine transitions per state, and a shared row that removes a dimension. The if(a!=b) line is the only place the robots affect each other. Drop it and every shared cell is counted twice. This is the pattern for every two-agent grid problem: find a quantity that moves forward in exactly the same way for both agents, and index on it. Here it is the row. In the original Cherry Pickup, one robot goes down-right and then returns up-left. You reverse the return trip, and then i+j is the shared clock. Without such a clock, the state is 4D and the cost is O(n²m²).

Reading the code. Why does it fill from the last row upward? Because the state is "the best total from row i onward", and that depends on the row below. The robots' starting columns are fixed (0 and m − 1), so the answer is one known cell, front[0][m-1], after the loop finishes row 0. Starting front at all zeros means "below the last row there is nothing left to collect". Why not just send the first robot on its best path, remove its cherries, then send the second? Because the first robot's best path can take cherries the second robot needed, and a slightly worse first path can give a better total. The two choices must be made together, which is why both columns are in the state.

With the problem's limits of n, m ≤ 70, the 3D version has 70 × 70 × 70 ≈ 3.4 × 10⁵ states and about 3 × 10⁶ transitions: instant. Edge cases: when m = 1 both robots share every cell, so the a != b check is what stops each cherry counting twice; moves that would leave the grid are skipped by the bounds check.

🧠
Grid variants worth recognising on sight
  • Triangle / falling path — you move down and may shift a column, so each cell reads three cells from the row above. Same skeleton.
  • Minimum falling path with no two adjacent columns — the same, but you may not reuse column j. Keep the best and second-best of the previous row to get O(n·m) instead of O(n·m²).
  • Paths with a fixed number of moves, or a budget — add a dimension, dp[i][j][k]. The extra index is just one more part of the sentence that describes a cell.
  • Dungeon game (minimum starting health) — must be filled bottom-right to top-left, because the health you need depends on what comes later. Fill in the direction of the dependency, not out of habit.
  • Maximal rectangle — not grid DP at all. Build a bar chart (histogram) for each row and reuse largest-rectangle-in-histogram with a monotonic stack (Chapter 13).
  • Count paths modulo 10⁹+7 — path counts grow very fast. Unique paths on a 30×30 grid already goes past the 32-bit range.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 REVERSE THE MOVES
Legal moves right and down means a cell is entered from left or above. Reversing the movement rules gives you both the transition and the loop order.
⛔ LEFT vs DIAGONAL
Rolling one row: "above" is prev[j] and "left" is cur[j-1]. prev[j-1] is the diagonal, and using it produces plausible wrong answers.
💡 FOUR DIRECTIONS ⇒ NOT DP
If all four directions are allowed the dependencies are cyclic and no fill order exists. That is BFS, 0-1 BFS or Dijkstra — not a bigger table.
⚠️
Common mistakes
  • Using grid DP when all four directions are allowed. The dependencies form loops; use BFS, 0-1 BFS or Dijkstra.
  • Border loops that disagree with the main loop — especially about obstacles. Put if checks in the main loop instead.
  • Reading prev[j-1] for "the cell to the left". Left is cur[j-1]; prev[j-1] is the diagonal.
  • Checking the start before the wall in the obstacles version, so a blocked start returns 1.
  • Returning the side instead of the area in maximal square.
  • Taking a max instead of a min of the three neighbours in maximal square — the smallest neighbour sets the limit.
  • Forgetting if(a!=b) in cherry pickup, so shared cells are counted twice.
  • Starting a min-cost DP at 0 instead of a large value, so unreachable cells look free.
  • Integer overflow on path counts. Use long long, or take the modulus as you go.
  • Shrinking to one row and then being asked for the path. Rebuilding the path needs the full table or "came from" pointers.

Interview drill

Warm-up: Minimum path sum — then: "what if you could also move up and left?"

How a strong answer sounds
With right-and-down movement I define dp[i][j] as the minimum cost of reaching cell (i,j). The only legal moves are right and down, so a cell can only be entered from above or from the left. That gives dp[i][j] = grid[i][j] + min(dp[i−1][j], dp[i][j−1]), with a check on each term for the first row and column. A plain top-to-bottom, left-to-right double loop fills every cell after the cells it needs. That is O(n·m) time, and O(m) space with a rolling row. If I also needed the route, I would keep the full table, because rebuilding the route means walking back through it. Now, if up and left become legal, this stops being a DP problem. The reason is about structure, not difficulty. DP needs the dependencies to form a DAG (no loops). With right-and-down, i+j goes up on every step, which gives that order for free. With all four directions, a cell can sit on a loop, so no fill order exists. Re-running the loops until the values stop changing is just a slow Bellman-Ford. The right tool is shortest path on the grid graph: Dijkstra with a min-heap keyed on total cost so far, O(n·m log(n·m)); plain BFS if every cell costs the same; 0-1 BFS with a deque if costs are only 0 and 1. I would say that out loud instead of trying to patch the loops. Recognising which family a problem belongs to is the real skill being tested.

Deeper: Cherry pickup II. Why is the state three-dimensional and not four?

How a strong answer sounds
The naive state is both robots' positions, (i1, j1, i2, j2). That is O(n²m²) states — far too many. The key observation: both robots move down exactly one row per step. After k steps, both are in row k. Their rows are always equal, so one index serves both. That shrinks the state to dp[i][a][b]: we are in row i, robot one is in column a, robot two is in column b. There are n·m² states with nine transitions each, because each robot shifts its column by −1, 0 or +1 on its own. So it is O(n·m²) overall, and O(m²) space with a rolling row, because row i only ever reads row i+1. The robots affect each other in a single line: collect grid[i][a], and add grid[i][b] only if a differs from b, because a shared cell is picked once. Forgetting that check counts cells twice. It is the first thing I would test, using a one-column grid where the robots are always on the same cell. The general lesson: whenever two agents move through a grid together, I look for a quantity that moves forward the same way for both, and index on it. In the original Cherry Pickup, one robot walks down-right and then returns up-left. You reverse the return trip so both travel down-right, and then i+j is the shared clock. Finding that shared clock is what turns an impossible state into a workable one — just as the shared row makes i1 and i2 the same variable.

🧠 Key takeaways

  • Turn the movement rules around to get the transition. The transition then fixes the loop order.
  • Right-and-down has no loops because i+j always increases. All four directions creates loops and needs BFS, 0-1 BFS or Dijkstra.
  • Counting adds the neighbours; optimising takes their min or max. Otherwise the skeleton is the same.
  • For "ending at this cell" states (maximal square), the answer is the largest value in the whole table — and return the area.
  • Grids with two agents need a shared clock — the same row, or i+j — so the state does not become 4D.

Check your understanding

You may move right and down. Which cells does dp[i][j] depend on?

If a step goes right or down, then arriving at a cell means the previous cell was to the left or above. Turning the movement rules around is how you get every grid transition. It also tells you the loop order at the same time.

All four directions are allowed and every cell has a positive cost. What is the right tool?

DP needs dependencies with no loops (a DAG). Right-and-down gives you one, because i+j always increases. Four directions breaks it. Re-running the loops until nothing changes is really just a slow Bellman-Ford.

In maximal square, why take the minimum of the three neighbouring dp values?

If any of the three supports only side 2, this cell cannot reach 3 — the square would stick out of the area of ones. And remember to return side², the area.

Rolling one row with prev and cur: which array holds "the cell to the left"?

prev[j] is the cell above and prev[j-1] is the diagonal. Mixing these up is the classic bug when you shrink to one row. It gives wrong answers that look believable, not a crash.

In cherry pickup II, why is the state dp[row][a][b] rather than dp[i1][j1][i2][j2]?

The shared row acts as a clock both robots follow, so the smaller state is exact, not an approximation. Finding such a clock — the row here, i+j in the original Cherry Pickup — is the standard move for grid problems with several agents.
