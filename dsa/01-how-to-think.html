How to Think in DSA (& My House Style)

Almost nobody fails a coding problem because they could not type a for-loop. They fail because they started typing before they knew what they were building. This chapter is the method that comes before the code — and the exact C++ conventions every one of the next 55 chapters is written in, so that by Chapter 20 the shape of a solution is something your hands already know.

  • Run the five-step funnel: constraints → complexity budget → pattern → invariant → code
  • Read a target complexity straight off the input size, before you have an idea
  • Write the guard clause, the helper-plus-driver split and the reference-parameter state
  • Reuse one skeleton across four problems instead of learning four solutions
  • Know why every code block in this course carries its time and space cost

The mistake everyone makes first

Here is the failure mode, and it is close to universal. You read a problem. You recognise a word — “subarray”, “tree”, “shortest” — and a half-remembered solution surfaces. You start typing. Twenty minutes later you have forty lines that almost work, you are patching an off-by-one with a +1 that you cannot justify, and you have no idea whether the approach was ever right.

The fix is not to know more algorithms. It is to refuse to write the first line until four questions are answered. That is what the rest of this chapter is.

⏱️
The time you “save” by skipping the thinking is borrowed at a terrible rate

Five minutes of framing routinely saves twenty minutes of debugging, because a bug in your approach looks exactly like a bug in your code — and you will look for it in the code. Every hour of your practice that goes into debugging a wrong approach is an hour that taught you nothing.

The five-step funnel

Every problem in this course is attacked in the same order. Each stage narrows what you could possibly write next, so by the time you reach “code” there is very little left to decide.

The funnel, one stage at a timeWalkthrough
  1. n ≤ 10⁵. Values up to 10⁹. Coordinates can be negative. This is the most information-dense line in any problem statement and most people skim it. It tells you the complexity you are allowed, whether you need long long, and whether your array indices can go negative. Read it first, before the prose.
  2. n = 10⁵ means O(n log n) is comfortable and O(n²) is not. Roughly 10⁸ simple operations per second is a safe assumption. So n² at n = 10⁵ is 10¹⁰ — a hundred seconds, dead. This single conversion eliminates most wrong approaches before you have had them.
  3. “Contiguous subarray with a condition” → sliding window. “Sorted, find a pair” → two pointers. “Next greater” → monotonic stack. There are about 24 patterns that cover almost everything, and Chapter 52 is the decision table. The budget from step 2 usually rules out all but two of them.
  4. “The window [l, r] always contains no repeated character.” If you cannot write this sentence, you cannot write correct code — you will be guessing at the loop condition. For DP the equivalent is “dp[i][j] is the answer for the first i of A and first j of B”. Precision here is the whole game.
  5. In that order, always. Guard clause for the empty and single cases. Declare and initialise your state with real names. Then the loop, whose body is now nearly forced by the invariant. If the body surprises you, your invariant was wrong — go back to step 4 rather than patching.
  6. Take the smallest case that exercises the tricky branch and walk every variable, line by line, on paper. This is not optional. It is the step that separates people who submit once from people who submit five times. Chapter 53 is entirely about doing it well.
Four of the six stages produce no code at all. That ratio is correct.

The house style, stated once

Every code block in this course follows the same conventions. This is deliberate and it is not about aesthetics: when the layout never changes, your brain stops spending attention on layout and spends it on logic instead. By Chapter 20 you will recognise a BFS by its shape from across the room.

Rule 1 — The guard clause is the first line, on one line

The base case goes at the top, with no braces, so your eye lands on it before anything else.

the guard clausereads in one glance
void preorder(TreeNode* root){
	if(!root)return;                 // void: bare return

	cout<<root->val<<" ";
	preorder(root->left);
	preorder(root->right);
}

vector<int> topView(TreeNode* root){
	if(!root)return {};              // value-returning: empty braces
	// ...
}
Why it matters: a missing null check is the most common crash in tree and list code. Putting it on line one, in the same place every time, means you notice when it is absent.

Rule 2 — Helper plus driver, with state in reference parameters

Recursive work goes in a helper that takes everything it needs by reference. A small public driver sets that state up and returns the answer. No global variables — they break the moment you call the function twice, which is exactly what a hidden test case does.

helper + driverO(V + E)O(V)
// helper: carries all state by reference, returns nothing
void DFS(unordered_map<int,vector<int>> &graph,int node,vector<bool> &visited,stack<int> &st){
	if(visited[node])return;

	visited[node]=true;
	for(auto &neighbour:graph[node]){
		if(!visited[neighbour])
		DFS(graph,neighbour,visited,st);
	}

	st.push(node);                    // post-order: after all children
}

// driver: owns the state, does the setup, returns the answer
vector<int> toposort(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(int i=0;i<edges.size();i++){
		int u=edges[i][0];
		int v=edges[i][1];
		graph[u].push_back(v);
		// graph[v].push_back(u); -> This is for Undirected Edges
	}

	stack<int> st;
	vector<bool> visited(N,false);

	for(int i=0;i<N;i++){
		if(!visited[i])
		DFS(graph,i,visited,st);
	}

	vector<int> ans;
	while(!st.empty()){
		ans.push_back(st.top());
		st.pop();
	}

	return ans;
}
The commented-out line is a real convention. Leaving // graph[v].push_back(u); in place documents the directed/undirected switch, so converting the algorithm is a one-character edit instead of a re-read.
✍️
My convention: always & on container parameters

Every vector, map, stack or queue parameter is taken by reference. Two reasons. First, a recursive helper that copies its adjacency list is not O(V + E) any more, it is catastrophically worse — and that bug is invisible, because the code still produces the right answer. Second, a helper that writes to a reference is declaring what it mutates, which makes the driver readable.

The one exception is a parameter you deliberately want a private copy of, such as the current path in a backtracking function — and when that happens, say so in a comment.

Rule 3 — Tight spacing, tabs, brace on the same line

No spaces around =, <, , or :. Opening brace on the same line as the statement. Tabs for indentation. Single-statement bodies unbraced on the next line.

House style
for(int i=0;i<n;i++){

    if (node->left != nullptr) {

Both compile to the same thing. The left one fits on a whiteboard, and the two symmetric if lines are visibly a pair — which is what you actually want to check when you read it back. The right one spends four lines saying something the left says in two.

🧠
My convention: names carry meaning, and they never change

ans or result for what you return. temp for a scratch container. node for the current node, neighbour for the one you are about to visit. st for a stack, q for a queue, pq for a priority queue. visited, dist, indegree, colors, parent, rank. mini and maxi for running extremes. N for the problem's node count, n for a local length.

Small vocabulary, used the same way every time. When a variable name means one thing across 56 chapters, reading your own code six months later stops being archaeology.

Rule 5 — Every block states its cost

Every code block in this course carries a time chip and a space chip, plus one sentence saying where they come from. Not as decoration — as a habit. If you cannot state the complexity of code you just wrote, you do not yet know what you wrote.

O(n log n)O(n) — the shape you will see at the top of every implementation.

What “knowing a data structure” actually means

There is a difference between having read about a heap and knowing a heap. The test is not whether you can describe it. It is whether you can answer these five questions without looking:

1️⃣

What does it make cheap?

A heap makes “give me the smallest” O(log n). A hash map makes “have I seen this” O(1). Pick the structure whose cheap operation is the one your loop does most.

2️⃣

What does it make expensive?

A heap cannot tell you the second smallest without a pop. A hash map has no order at all. The expensive operation is what rules the structure out.

3️⃣

What is its invariant?

“Every parent is ≤ both children.” Every operation must restore it. If you can state the invariant, you can derive the operations rather than memorise them.

4️⃣

Can you write it from scratch?

Not to use in a contest — to prove you understand it. Sift-down in eight lines. DSU find in two. The exercise is the understanding.

5️⃣

What is the problem phrasing that summons it?

“Top K” → heap. “Next greater” → monotonic stack. “Connected components, online” → DSU. This mapping is the actual interview skill, and Chapter 52 is the full table.

🎯

If you can answer all five

you know it. If you can only describe it, you will recognise it in a tutorial and miss it in an interview. Every chapter in this course answers these five explicitly.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 FIRST MOVE
Before anything else, write the state sentence or the invariant in one line of English. If you cannot finish that sentence, you do not yet have a solution — and no amount of typing will produce one.
💡 BUDGET
Read the constraint, divide 10⁸ by it, and you have your allowed complexity before you pick a technique. n = 10⁵ buys you a log factor; n = 20 buys you 2ⁿ.
⛔ GLOBALS
A global ans works once and then silently breaks on the second call, which is exactly what judges that reuse a process will do. Driver owns the state, helper takes it by reference.
⚠️
Common mistakes
  • Reading the prose before the constraints. The constraint line eliminates more wrong approaches than any amount of cleverness. Read it first, every time.
  • Writing code before you can state the invariant. If you cannot say in one sentence what is always true inside your loop, every boundary decision will be a guess — and you will get about half of them wrong.
  • Keeping state in globals so the helper has fewer parameters. It works once. Then a test harness calls your function twice with the same object and the leftover state silently corrupts the second answer.
  • Passing containers by value into a recursive helper. The answer stays correct and the complexity quietly explodes — the worst class of bug, because nothing looks wrong.
  • Collecting solutions instead of patterns. Two hundred memorised problems generalise worse than twenty-four understood patterns. When you finish a problem, ask “what was that an instance of?”
  • Skipping the dry run because the logic is obviously right. The logic usually is. The < that should be <= is not.

Interview drill

Warm-up: You are given a problem with n ≤ 200 and no other hints. What does that number alone tell you, and what would you try first?

How a strong answer sounds
n ≤ 200 allows roughly O(n³) — about 8 million operations, comfortable. That bound is too small for anything asking for O(n log n), so the intended solution is probably cubic or quadratic, which in practice means interval DP with a split point, Floyd-Warshall if it is a graph, or an O(n²) DP with an inner scan. It also tells me a brute force over all pairs is completely acceptable as a starting point and as a stress-test reference. So I would state the O(n³) DP candidate, confirm the problem has the overlapping-subproblem shape, and not waste a minute hunting for a linear trick that the setter clearly did not require.

Deeper: Why does an interviewer care that you state the brute force when you already know the optimal solution?

How a strong answer sounds
Three reasons, and they are all about signal rather than politeness. First, it establishes a shared, definitely-correct baseline — if we later disagree about whether the fast version is right, we have something to diff against. Second, the brute force is where the optimisation comes from: naming the wasteful part (“I recompute this sum for every window”) is what motivates the prefix array, and that reasoning is the thing being assessed. Third, it derisks the round: if I run out of time, a stated correct O(n²) plus a clear plan for O(n) scores far better than a half-finished clever attempt with nothing working. Practically, I would spend thirty seconds on it, not five minutes.

🧠 Key takeaways

  • Four of the six stages of solving a problem happen before you type: constraints, budget, pattern, invariant.
  • Input size is a lookup into a complexity budget — memorise that table and most wrong approaches die before you have them.
  • Guard clause on line one, state in reference parameters, helper plus driver, no globals.
  • Reuse the skeleton: level order, zigzag, left view and right view are the same loop with one line changed.
  • You know a structure when you can say what it makes cheap, what it makes expensive, its invariant, how to build it, and the phrasing that summons it.

Check your understanding

A problem states n ≤ 10⁵. Which complexity should you be aiming for?

At roughly 10⁸ operations per second, O(n²) at n = 10⁵ is 10¹⁰ — around a hundred seconds. O(n log n) is about 1.7 × 10⁶, which is instant. 10⁵ is the classic “n log n intended” signal.

Why does this course put recursive state in reference parameters instead of globals?

The bug is repeatability. A test harness that calls your function twice will see the first call's leftover visited array, and the second answer will be wrong with no crash to point at it. Reference parameters make the driver own the lifetime.

You want the right view of a binary tree and you already know level order. What is the minimal change?

That is the skeleton-reuse rule. Level order, zigzag, left view and right view all share one loop; only the line after the inner for changes. Learn the skeleton, then learn where the variation goes.

A constraint of n ≤ 20 most strongly suggests which family of solutions?

Nothing polynomial needs a bound that tiny. 2²⁰ is about a million, and 2²⁰ × 20² is around 400 million — right at the edge of feasible. When you see n ≤ 20, think subsets.

Passing an adjacency list by value into a recursive DFS helper causes which problem?

This is the dangerous class of bug: the output is right, so no test flags it, but every recursive call deep-copies the whole graph. It is why every container parameter in this course carries an &.
