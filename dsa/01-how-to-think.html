How to Think in DSA (& My House Style)

Almost nobody fails a coding problem because they could not type a for-loop. They fail because they started typing before they knew what they were building. This chapter teaches the method that comes before the code. It also sets out the exact C++ style that all of the next 55 chapters use. By Chapter 20, the shape of a solution will be something your hands already know.

  • Follow the five-step funnel: constraints → complexity budget → pattern → invariant (the rule that stays true) → code
  • Work out how fast your solution must be just from the input size, before you have any idea
  • Write the guard clause (the early exit for empty input), split work into a helper plus a driver, and pass state by reference
  • Reuse one code skeleton across four problems instead of learning four separate solutions
  • Know why every code block in this course states its time and space cost
📚
What you need before this chapter
  • Basic C++: variables, if, for loops, functions, and vector. If any of these feel shaky, start with P3: Control Flow & Functions.
  • What a reference (&) is: a second name for an existing variable, so a function can change the caller's data. P3: Control Flow & Functions covers it.
  • Powers of ten and logarithms: knowing that 10⁵ × 10⁵ = 10¹⁰, and that log₂ of a million is about 20. P7: School Math for DSA has the school math.
  • You do not need to know any algorithms yet. The trees and graphs in the code samples are only there to show the style; you will learn them properly later.

The mistake everyone makes first

Here is the mistake, and almost everyone makes it. You read a problem. You spot a familiar word — “subarray”, “tree”, “shortest” — and a half-remembered solution pops into your head. You start typing. Twenty minutes later you have forty lines that almost work. You are patching an off-by-one error with a +1 you cannot explain. And you have no idea whether the approach was ever right.

The fix is not to know more algorithms. It is to refuse to write the first line until you have answered four questions. The rest of this chapter is about those questions.

⏱️
The time you “save” by skipping the thinking is borrowed at a terrible rate

Five minutes of planning often saves twenty minutes of debugging. Why? A bug in your approach looks exactly like a bug in your code, so you will search for it in the code — where it isn't. Every hour you spend debugging a wrong approach is an hour that taught you nothing.

The five-step funnel

Every problem in this course is solved in the same order. Think of a funnel: each stage narrows down what you could write next. By the time you reach “code”, there is very little left to decide.

The funnel, one stage at a timeWalkthrough
  1. n ≤ 10⁵. Values up to 10⁹. Coordinates can be negative. This line packs more information than any other in the problem, and most people skim it. It tells you how fast your solution must be. It tells you whether you need long long (a 64-bit integer, for big numbers). It tells you whether indices can go negative. Read it first, before the story.
  2. n = 10⁵ means O(n log n) is comfortable and O(n²) is not. A safe rule of thumb: a computer does about 10⁸ simple operations per second. So n² at n = 10⁵ is 10¹⁰ operations — about a hundred seconds. Far too slow. This one calculation rules out most wrong approaches before you even think of them.
  3. “Contiguous subarray with a condition” → sliding window. “Sorted, find a pair” → two pointers. “Next greater” → monotonic stack. About 24 patterns cover almost every problem, and Chapter 52 has the full decision table. The budget from step 2 usually rules out all but two of them.
  4. An invariant is a rule that stays true every time the loop runs. Example: “The window [l, r] always contains no repeated character.” If you cannot write this sentence, you cannot write correct code — you will be guessing at the loop condition. For DP (dynamic programming), the same idea is the state: “dp[i][j] is the answer for the first i of A and first j of B”. Getting this sentence exactly right is the whole game.
  5. Always in this order. First, a guard clause: an early return for the empty and single-element cases. Next, declare and set up your variables with real names. Then write the loop. The invariant now almost dictates what goes inside it. If the loop body surprises you, your invariant was wrong — go back to step 4 instead of patching.
  6. Pick the smallest input that hits the tricky branch. Then trace every variable, line by line, on paper. This is not optional. It is what separates people who submit once from people who submit five times. Chapter 53 is all about doing it well.
Four of the six stages produce no code at all. That is the right balance.

One problem, taken through the whole funnel

The funnel is easier to believe once you watch it work. Here is a typical problem: “Given an array of n positive integers and a number K, return the length of the longest contiguous subarray whose sum is at most K. n ≤ 10⁵, values ≤ 10⁹, K ≤ 10¹⁴.” You do not need to know the technique yet — just follow the order.

  1. Constraints. n is up to 10⁵. A sum can reach 10⁵ × 10⁹ = 10¹⁴, far past what a 32-bit int can hold (about 2.1 × 10⁹). So the running sum must be a long long. The values are all positive — remember that, it matters in step 3.
  2. Budget. n² would be 10¹⁰ operations, which is too slow. So you need O(n log n) or O(n). That already rules out “try every start and every end”.
  3. Pattern. “Contiguous subarray” plus “a condition on it” points to a sliding window (Chapter 5). The positive values are what make it work: adding an element can only make the sum bigger, and removing one can only make it smaller.
  4. Invariant. “The window [l, r] always has sum ≤ K.” One sentence, and it tells you what the loop must do: after adding a[r], remove from the left until the sentence is true again.
  5. Code. Guard for an empty array. Set up l=0 and sum=0. Loop r over the array, add, shrink while sum>K, then record r-l+1.
  6. Dry run on [2, 1, 3, 2] with K = 4. r=0: sum 2, length 1. r=1: sum 3, length 2. r=2: sum 6 is too big, drop the 2 → sum 4, window is [1, 3], length 2. r=3: sum 6 again, drop 1 → 5, drop 3 → 2, window is [2], length 1. Answer: 2. Checking by hand, [2, 1] and [1, 3] are the longest valid pieces, so the trace agrees.

Notice where the real decisions happened: long long came from step 1, the O(n) target from step 2, and the while loop from step 4. By the time you typed, there was nothing left to guess.

Step 2 is a lookup table — memorise it

This is the most useful table in the course. Give it n, and it tells you how slow your solution is allowed to be. Use it backwards, too. The input limit is not a formality — it is a hint about the solution the problem setter had in mind.

The table is just arithmetic you can redo yourself. Take the largest n, plug it into each complexity, and compare the result with about 10⁸ — roughly what a judge runs in one second. For n = 10⁵:

  • O(n): 10⁵ operations. Instant.
  • O(n log n): log₂(10⁵) is about 17 (because 2¹⁷ ≈ 131,000). So 10⁵ × 17 ≈ 1.7 × 10⁶. Still instant.
  • O(n²): 10⁵ × 10⁵ = 10¹⁰. That is 100 times over the budget — around 100 seconds against a typical 1–2 second limit.

The 10⁸ figure is a rough rule, not a law. Simple array loops can run faster; code full of hash-map lookups or memory allocation runs slower. So treat anything within about 3× of 10⁸ as “maybe”, and anything 10× over as “no”.

The house style, stated once

Every code block in this course follows the same style. This is on purpose, and it is not about looks. When the layout never changes, your brain stops paying attention to layout and focuses on the logic instead. By Chapter 20 you will recognise a BFS (breadth-first search) by its shape from across the room.

Rule 1 — The guard clause is the first line, on one line

A guard clause handles the base case — like an empty input — and exits early. It goes at the very top, with no braces, so your eye lands on it before anything else.

The form of the return depends on what the function gives back. A void function has nothing to return, so it uses a bare return;. A function that returns a vector returns {}, which builds an empty vector. A function returning a number returns whatever the problem says the answer is for empty input — often 0 or -1. Deciding that value up front is part of the point: it forces you to ask “what should happen on empty input?” before you write the main logic.

the guard clausereads in one glance
void preorder(TreeNode* root){
	if(!root)return;                 // void: bare return

	cout<<root->val<<" ";
	preorder(root->left);
	preorder(root->right);
}

vector<int> topView(TreeNode* root){
	if(!root)return {};              // value-returning: empty braces
	// ...
}
Why it matters: a missing null check is the most common crash in tree and list code. If it always sits on line one, you will notice at once when it is missing.

Rule 2 — Helper plus driver, with state in reference parameters

Split the code into two functions. The helper does the recursive work. It takes everything it needs by reference (marked with &, so it edits the caller's data instead of a copy). The driver is a small public function that sets up that data and returns the answer. No global variables. Globals break the moment the function is called twice — and a hidden test case will do exactly that.

Here is how that goes wrong in practice. Suppose visited were a global array. The first test builds a graph with 4 nodes, and your DFS marks nodes 0–3 as visited. The judge then calls your function again, on the same object, for a second graph. Nodes 0–3 are still marked, so your DFS skips them and returns an empty or partial answer. Nothing crashes. You just get “Wrong Answer” on test 2, and your code looks correct. When the driver creates visited as a local variable, every call starts clean, so this bug cannot happen.

helper + driverO(V + E)O(V)
// helper: carries all state by reference, returns nothing
void DFS(unordered_map<int,vector<int>> &graph,int node,vector<bool> &visited,stack<int> &st){
	if(visited[node])return;

	visited[node]=true;
	for(auto &neighbour:graph[node]){
		if(!visited[neighbour])
		DFS(graph,neighbour,visited,st);
	}

	st.push(node);                    // post-order: after all children
}

// driver: owns the state, does the setup, returns the answer
vector<int> toposort(int N,vector<vector<int>> &edges){
	unordered_map<int,vector<int>> graph;
	for(int i=0;i<edges.size();i++){
		int u=edges[i][0];
		int v=edges[i][1];
		graph[u].push_back(v);
		// graph[v].push_back(u); -> This is for Undirected Edges
	}

	stack<int> st;
	vector<bool> visited(N,false);

	for(int i=0;i<N;i++){
		if(!visited[i])
		DFS(graph,i,visited,st);
	}

	vector<int> ans;
	while(!st.empty()){
		ans.push_back(st.top());
		st.pop();
	}

	return ans;
}
The commented-out line is on purpose. Leaving // graph[v].push_back(u); in place shows where the directed/undirected switch lives. To convert the algorithm, you just uncomment it — no need to re-read the whole thing.
✍️
My convention: always & on container parameters

Every vector, map, stack or queue parameter is taken by reference. There are two reasons.

First, speed. If a recursive helper copies its adjacency list (the list of each node's neighbours) on every call, it is no longer O(V + E) — it is far, far worse. And you won't see the bug, because the code still gives the right answer.

To put numbers on it: a graph with 10⁵ nodes and 10⁵ edges makes up to 10⁵ DFS calls. If each call copies all 10⁵ edges, that is about 10¹⁰ units of copying — a time-out — for code that should finish in a millisecond.

Second, clarity. A helper that writes to a reference parameter is announcing what it changes. That makes the driver easy to read.

The one exception: a parameter where you deliberately want a private copy, such as the current path in a backtracking function. When you do that, say so in a comment.

Rule 3 — Tight spacing, tabs, brace on the same line

No spaces around =, <, , or :. The opening brace goes on the same line as the statement. Indent with tabs. If a body is a single statement, skip the braces and put it on the next line.

One caution with brace-less bodies: only the first statement belongs to the if or for. If you later add a second line under it, that line runs every time, whatever the indentation suggests. So the moment a body grows to two statements, add the braces.

House style
for(int i=0;i<n;i++){
	TreeNode* node=q.front();
	q.pop();
	level.push_back(node->val);

	if(node->left)q.push(node->left);
	if(node->right)q.push(node->right);
}
Not this
for (int i = 0; i < n; i++)
{
    TreeNode *node = q.front();
    q.pop();
    level.push_back(node->val);

    if (node->left != nullptr) {
        q.push(node->left);
    }
    if (node->right != nullptr) {
        q.push(node->right);
    }
}

Both compile to the same thing. The left one fits on a whiteboard. Its two matching if lines are clearly a pair, which is exactly what you want to check when you read it back. The right one uses four lines to say what the left says in two.

Rule 4 — Reuse the skeleton

This is the most important rule. It is a way of learning, not a formatting rule. Many problems are the same loop with just one line changed. Learn the skeleton once, learn which line changes, and one memory covers four problems.

while(!q.empty()){
	int n=q.size();
	vector<int> level;
	for(int i=0;i<n;i++){
		TreeNode* node=q.front();
		level.push_back(node->val);
		q.pop();

		if(node->left)q.push(node->left);
		if(node->right)q.push(node->right);
	}
	ans.push_back(level);
}

Same loop. Take only the last of each level.

Why does this work? The skeleton's job is to hand you one full level at a time, left to right. The four problems differ only in what they do with each level: keep all of it, keep it reversed on every other level, keep the first value, or keep the last value. So the loop that produces levels never changes, and only the line that uses the level does. For a tree whose levels are [1], [2, 3], [4, 5]: level order gives [[1], [2, 3], [4, 5]], zigzag gives [[1], [3, 2], [4, 5]], left view gives [1, 2, 4], and right view gives [1, 3, 5].

Four accepted solutions. One skeleton, one highlighted line. Chapter 17 covers this in full with six problems. The point here is that the whole course works this way: learn the skeleton, then learn where the change goes.

My convention: names carry meaning, and they never change

ans or result for what you return. temp for a scratch container. node for the current node, neighbour for the one you are about to visit. st for a stack, q for a queue, pq for a priority queue. visited, dist, indegree, colors, parent, rank. mini and maxi for running extremes. N for the problem's node count, n for a local length.

A small set of names, used the same way every time. When a name means one thing across all 56 chapters, reading your own code six months later is easy instead of a puzzle.

Rule 5 — Every block states its cost

Every code block in this course shows a time label and a space label, plus one sentence explaining where they come from. They are not decoration — they build a habit. If you cannot say how fast the code you just wrote is, you do not really know what you wrote yet.

O(n log n)O(n) — the shape you will see at the top of every implementation.

How to read the two labels: the time label counts how many basic steps the code takes as the input grows. The space label counts the extra memory it allocates beyond the input itself — a new vector, a hash map, a queue, or the recursion's call stack. For example, “sort the array, then build a copy with duplicates removed” is O(n log n) time (the sort dominates) and O(n) space (the copy). Chapter 2 explains how to work these out; for now, just get used to seeing them.

What “knowing a data structure” actually means

Having read about a heap is not the same as knowing a heap. The test is not whether you can describe it. It is whether you can answer these five questions without looking:

1️⃣

What does it make cheap?

A heap makes “give me the smallest” O(log n). A hash map makes “have I seen this?” O(1). Pick the structure whose cheap operation is the one your loop does most.

2️⃣

What does it make expensive?

A heap cannot tell you the second smallest without removing the smallest first. A hash map keeps no order at all. The expensive operation is what rules a structure out.

3️⃣

What is its invariant?

For a heap: “Every parent is ≤ both children.” Every operation must put this rule back in place. If you can state the rule, you can work out the operations yourself instead of memorising them.

4️⃣

Can you write it from scratch?

Not to use in a contest — to prove you understand it. Sift-down in eight lines. DSU (disjoint set union) find in two. Doing the exercise is how you understand it.

5️⃣

What is the problem phrasing that summons it?

“Top K” → heap. “Next greater” → monotonic stack. “Connected components, online” → DSU. This mapping is the real interview skill, and Chapter 52 has the full table.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 FIRST MOVE
Before anything else, write the state sentence or the invariant in one line of English. If you cannot finish that sentence, you do not yet have a solution — and no amount of typing will produce one.
💡 BUDGET
Read the constraint, divide 10⁸ by it, and you have your allowed complexity before you pick a technique. n = 10⁵ buys you a log factor; n = 20 buys you 2ⁿ.
⛔ GLOBALS
A global ans works once and then silently breaks on the second call, which is exactly what judges that reuse a process will do. Driver owns the state, helper takes it by reference.
⚠️
Common mistakes
  • Reading the story before the constraints. The constraint line rules out more wrong approaches than any amount of cleverness. Read it first, every time.
  • Writing code before you can state the invariant. If you cannot say in one sentence what is always true inside your loop, every boundary choice is a guess. You will get about half of them wrong.
  • Keeping state in globals so the helper has fewer parameters. It works once. Then the tester calls your function twice on the same object, and the leftover values quietly spoil the second answer.
  • Passing containers by value into a recursive helper. The answer stays correct, but the running time quietly explodes. This is the worst kind of bug, because nothing looks wrong.
  • Collecting solutions instead of patterns. Two hundred memorised problems help you less than twenty-four patterns you truly understand. When you finish a problem, ask: “what was that an example of?”
  • Skipping the dry run because the logic is obviously right. The logic usually is. The < that should be <= is not.

Interview drill

Warm-up: You are given a problem with n ≤ 200 and no other hints. What does that number alone tell you, and what would you try first?

How a strong answer sounds
n ≤ 200 allows about O(n³) — roughly 8 million operations, which is comfortable. A limit that small means the setter is not asking for O(n log n). The intended solution is probably cubic or quadratic. In practice that means interval DP with a split point, Floyd-Warshall if it is a graph, or an O(n²) DP with an inner scan. It also tells me a brute force over all pairs is perfectly fine — as a starting point, and as a reference to test the fast version against. So I would propose the O(n³) DP, check that the problem has overlapping subproblems (the same smaller question asked many times), and not waste a minute hunting for a linear trick the setter clearly did not need.

Deeper: Why does an interviewer care that you state the brute force when you already know the optimal solution?

How a strong answer sounds
Three reasons, and none of them is about politeness. First, it sets up a shared answer that is definitely correct. If we later disagree about whether the fast version is right, we have something to compare against. Second, the brute force is where the speed-up comes from. Pointing at the wasteful part (“I recompute this sum for every window”) is what leads to the prefix array — and that reasoning is exactly what is being judged. Third, it makes the round safer. If I run out of time, a correct O(n²) plus a clear plan for O(n) scores far better than a half-finished clever attempt where nothing works. In practice, I would spend thirty seconds on it, not five minutes.

🧠 Key takeaways

  • Four of the six stages of solving a problem happen before you type: constraints, budget, pattern, invariant.
  • The input size tells you your complexity budget. Memorise that table and most wrong approaches are ruled out before you even try them.
  • Guard clause on line one, state in reference parameters, helper plus driver, no globals.
  • Reuse the skeleton: level order, zigzag, left view and right view are the same loop with one line changed.
  • You know a structure when you can say what it makes cheap, what it makes expensive, its invariant, how to build it, and which problem wording calls for it.

Check your understanding

A problem states n ≤ 10⁵. Which complexity should you be aiming for?

At about 10⁸ operations per second, O(n²) at n = 10⁵ is 10¹⁰ operations — around a hundred seconds. O(n log n) is about 1.7 × 10⁶, which is instant. A limit of 10⁵ is the classic sign that n log n is expected.

Why does this course put recursive state in reference parameters instead of globals?

The problem is running twice. If the tester calls your function twice, the second call sees the first call's leftover visited array. The second answer is wrong, and there is no crash to point you to it. With reference parameters, the driver creates fresh state on every call.

You want the right view of a binary tree and you already know level order. What is the minimal change?

That is the skeleton-reuse rule. Level order, zigzag, left view and right view all share one loop; only the line after the inner for changes. Learn the skeleton, then learn where the variation goes.

A constraint of n ≤ 20 most strongly suggests which family of solutions?

No polynomial solution needs a limit that tiny. 2²⁰ is about a million, and 2²⁰ × 20² is around 400 million — right at the edge of what runs in time. When you see n ≤ 20, think subsets.

Passing an adjacency list by value into a recursive DFS helper causes which problem?

This is the dangerous kind of bug. The output is right, so no test catches it. But every recursive call makes a full copy of the whole graph. That is why every container parameter in this course has an &.
