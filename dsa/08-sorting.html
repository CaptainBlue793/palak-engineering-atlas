Sorting: Every Algorithm & Comparators

You will almost never write your own sort at work. But you will be asked to explain one in nearly every interview. Why? A sort is where invariants, recursion, stability and complexity all show up at once. This chapter races six sorts side by side. It shows why no comparison-based sort can beat O(n log n). Then it spends real time on the thing you will use every day: custom comparators (the function that tells a sort which of two items comes first). That includes the subtle rule that makes them crash when you get it wrong.

  • Implement and explain bubble, insertion, selection, merge, quick and counting sort
  • Explain why sorting by comparing pairs cannot beat O(n log n), and how radix sort gets around it
  • Define stability (equal items keep their original order) and know exactly when you need it
  • Write custom comparators that follow the “strict weak ordering” rule — and know what happens when they do not
  • Pick the right sort based on what the input looks like, not by habit

Race them

Why does sorting deserve a whole chapter? Because sorted data makes other problems easy. Once an array is sorted you can binary search it (Chapter 7), walk it with two pointers (Chapter 4), find duplicates by looking only at neighbours, and merge overlapping intervals in one sweep. A huge share of “medium” problems start with the line sort(a.begin(), a.end());.

Same input, six algorithms. Each one counts its real comparisons and swaps. Try each input shape. The winner changes — and that is the whole lesson.

The O(n²) family — worth knowing, not worth using

Here are three quadratic sorts — their work grows with n², so doubling the input makes them about four times slower. Each one teaches something different, and one of them is actually useful.

// Invariant: after pass i, the last i elements are final and in place.
// The swapped flag makes it O(n) on already-sorted input — the one merit it has.
void bubbleSort(vector<int> &a){
	int n=a.size();

	for(int i=0;i<n-1;i++){
		bool swapped=false;

		for(int j=0;j<n-1-i;j++){
			if(a[j]>a[j+1]){
				swap(a[j],a[j+1]);
				swapped=true;
			}
		}

		if(!swapped)break;      // nothing moved -> already sorted
	}
}

Stable. O(n) at best, O(n²) on average and at worst. It is never the right choice. But you should be able to explain the swapped flag and the n-1-i bound. If you write j<n-1 instead, you keep re-comparing elements that are already in their final place.

// Invariant: after pass i, the first i elements are the i smallest, sorted.
// Always exactly n-1 swaps — the minimum possible. That is its one use.
void selectionSort(vector<int> &a){
	int n=a.size();

	for(int i=0;i<n-1;i++){
		int mini=i;

		for(int j=i+1;j<n;j++){
			if(a[j]<a[mini])
			mini=j;
		}

		if(mini!=i)
		swap(a[i],a[mini]);
	}
}

Not stable. Its long-distance swap can jump one element past an equal one, changing their order. It is O(n²) in every case, even on sorted input. Its one niche: when a write costs far more than a read — say, flash memory or a network round trip. Then doing only n−1 writes beats everything else.

// Invariant: a[0..i-1] is sorted. Insert a[i] into its place by shifting.
// Genuinely useful: O(n) on nearly-sorted data, tiny constant, stable, in place.
void insertionSort(vector<int> &a){
	int n=a.size();

	for(int i=1;i<n;i++){
		int key=a[i];
		int j=i-1;

		while(j>=0 and a[j]>key){   // strictly > keeps it stable
			a[j+1]=a[j];
			j--;
		}

		a[j+1]=key;
	}
}

The one quadratic sort that earns its place. std::sort switches to insertion sort for pieces smaller than about 16 elements. On tiny inputs its simple loop is faster than quicksort's recursive calls. It is also the natural choice for an online sort, where elements arrive one at a time.

Dry run of insertion sort on [5, 2, 4, 1]. It works like sorting a hand of playing cards: take the next card and slide it left until it sits in the right place.

  • i = 1, key = 2. 5 > 2, so shift 5 right. Place 2 at the front: [2, 5, 4, 1].
  • i = 2, key = 4. 5 > 4, shift it. 2 is not > 4, stop. Result: [2, 4, 5, 1].
  • i = 3, key = 1. Shift 5, 4 and 2 right, one by one. Place 1 at the front: [1, 2, 4, 5].

Count the shifts: 1 + 1 + 3 = 5, which is exactly the number of out-of-order pairs in the input. That is why insertion sort is fast on nearly sorted data — few out-of-order pairs means few shifts — and slow on reversed data, where every pair is out of order, giving about n²/2 shifts.

✍️
My convention: name the invariant, then read the loop bounds off it

Every sort above starts with a one-line invariant comment (a rule that stays true on every pass). Every loop bound follows from it. “After pass i the last i are final” gives you j<n-1-i. “a[0..i-1] is sorted” gives you i starting at 1. So you do not need to memorise the bounds. You work them out, every time, from one sentence.

Merge sort: the reliable one

Split the array in half, sort each half, then merge the two sorted halves. It is O(n log n) in every case, and it is stable. The merge step is also a useful tool on its own. Counting inversions (pairs that are out of order), finding reverse pairs, and external sorting (sorting data too big for memory) all build on it.

Why O(n log n)? Picture the splitting as a tree. The top level is the whole array of n elements. The next level is two halves, then four quarters, and so on, until every piece has one element. Halving n until you reach 1 takes about log₂ n levels. At each level, the merges together touch every element exactly once, so each level costs O(n). That gives n work per level × log n levels = O(n log n). For n = 1,000,000 that is about 20 levels of a million steps each — 20 million steps, against roughly 500 billion for an O(n²) sort.

The merge step by hand. Merge the sorted halves [2, 5, 8] and [1, 5, 9]. Compare the fronts: 1 < 2, take 1. Then 2 < 5, take 2. Then 5 vs 5 — a tie, and the rule takes the left 5 first. Then 8 vs the right 5, take 5. Then 8 < 9, take 8. The left half is empty, so copy the rest: 9. Result: [1, 2, 5, 5, 8, 9], built in one pass over both halves.

mergeSort — helper + driverO(n log n) alwaysO(n)
// temp is allocated ONCE by the driver and passed down by reference.
// Allocating inside merge() would add an O(n) allocation per call.
void merge(vector<int> &a,int lo,int mid,int hi,vector<int> &temp){
	int i=lo;
	int j=mid+1;
	int k=lo;

	while(i<=mid and j<=hi){
		if(a[i]<=a[j])temp[k++]=a[i++];   // <= is what makes it STABLE
		else temp[k++]=a[j++];
	}

	while(i<=mid)temp[k++]=a[i++];
	while(j<=hi)temp[k++]=a[j++];

	for(int x=lo;x<=hi;x++)
	a[x]=temp[x];
}
void mergeSortHelper(vector<int> &a,int lo,int hi,vector<int> &temp){
	if(lo>=hi)return;

	int mid=lo+(hi-lo)/2;

	mergeSortHelper(a,lo,mid,temp);
	mergeSortHelper(a,mid+1,hi,temp);
	merge(a,lo,mid,hi,temp);
}
void mergeSort(vector<int> &a){
	if(a.size()<2)return;

	vector<int> temp(a.size());
	mergeSortHelper(a,0,a.size()-1,temp);
}
a[i] <= a[j] matters. On a tie, it takes from the left half, where the earlier elements live. That is exactly what stability means. Change it to < and merge sort becomes unstable. The array still comes out correctly sorted, so no test catches it.
🔢
The merge step counts inversions for free

An inversion is a pair where a bigger number comes before a smaller one. When you take a[j] from the right half, every element still left in the left half is bigger than it. There are mid - i + 1 of them, and each one forms an inversion. Add that count in the else branch, and merge sort counts all inversions in O(n log n). The same idea solves “reverse pairs” and “count of smaller numbers after self”. It is one of the most valuable one-line additions in the course.

Quicksort: fast, and dangerous in the obvious case

Pick a pivot (one element to compare against). Partition the array: move smaller elements to its left and larger ones to its right. Then repeat on both sides. There is no merge step, so it sorts in place, without an extra array. In practice it is usually faster than merge sort, because it works on nearby memory, which the CPU cache likes. The catch is the worst case.

quickSort with Lomuto partition and a random pivotO(n log n) expected, O(n²) worstO(log n) stack
// Invariant: a[lo..i] are <= pivot, a[i+1..j-1] are > pivot.
int partition(vector<int> &a,int lo,int hi){
	// Random pivot: without this, sorted input gives O(n^2).
	int r=lo+rand()%(hi-lo+1);
	swap(a[r],a[hi]);

	int pivot=a[hi];
	int i=lo-1;

	for(int j=lo;j<hi;j++){
		if(a[j]<=pivot){
			i++;
			swap(a[i],a[j]);
		}
	}

	swap(a[i+1],a[hi]);      // pivot into its final position
	return i+1;
}
void quickSort(vector<int> &a,int lo,int hi){
	if(lo>=hi)return;

	int p=partition(a,lo,hi);

	quickSort(a,lo,p-1);       // p is final — never include it
	quickSort(a,p+1,hi);
}
The pivot ends up in its final position, so neither recursive call includes it. If you write quickSort(a,lo,p), it recurses forever when the pivot lands at lo. And the random pivot is not optional. With a fixed first or last pivot, already sorted input — the most common real-world case — becomes the O(n²) worst case.

Partition by hand. Take [3, 7, 1, 5, 4] and suppose the pivot is the last element, 4. i marks the end of the “≤ pivot” zone and starts at −1.

  • j = 0: 3 ≤ 4, so i = 0 and swap a[0] with itself. Array unchanged.
  • j = 1: 7 > 4, skip.
  • j = 2: 1 ≤ 4, so i = 1 and swap a[1] with a[2]: [3, 1, 7, 5, 4].
  • j = 3: 5 > 4, skip.
  • Finally swap the pivot into slot i+1 = 2: [3, 1, 4, 5, 7]. Return 2.

The 4 is now in its final place. Everything left of it is smaller and everything right is larger, though neither side is sorted yet — the two recursive calls handle that.

Why the pivot choice decides the speed. If the pivot lands near the middle, each call splits its range roughly in half, and you get about log n levels, just like merge sort. If the pivot is always the smallest or largest element, one side is empty and the other has n−1 elements. Then there are n levels, and the total work is n + (n−1) + … + 1 ≈ n²/2. A random pivot lands in the middle half of the values half the time, which is enough to keep the expected depth at O(log n) on any input.

🎨
Three-way partition when there are many duplicates

Lomuto partition puts elements equal to the pivot all on one side. So an array where every value is the same still recurses n levels deep — O(n²). A three-way (Dutch national flag) partition splits the array into three groups: <, == and > the pivot. It then recurses only on the outer two groups, so all-equal input takes O(n). This is effectively what std::sort does. It is the right answer to “what if the array is mostly duplicates?”

Beating O(n log n): counting and radix

🧾
Why no comparison sort can beat O(n log n)

Think of the game “20 questions”. A comparison sort learns only one yes/no answer per comparison: “is x < y?”. The input could be in any of n! possible orders, and the sort must tell all of them apart. Picture every run of the algorithm as a decision tree: each comparison is a fork, and each leaf is one final order. That tree needs at least n! leaves. A binary tree with n! leaves is at least log₂(n!) levels deep. By Stirling's approximation, log₂(n!) ≈ n log₂ n − 1.44n = Θ(n log n). So some input forces that many comparisons. Counting sort and radix sort escape this limit not by being cleverer, but by not comparing at all. They use the values themselves as array indices — extra information that a pure comparison sort is not allowed to use.

With real numbers: for n = 10 there are 10! = 3,628,800 possible orders, and log₂(3,628,800) ≈ 21.8. So any comparison sort needs at least 22 comparisons on some input of 10 elements, no matter how clever it is.

Counting sort works on a simple idea: if the values are small integers, you can count how many of each value there are and then write them out in order. The only subtle part is doing it stably, so that it can be used inside radix sort. A dry run on a = [2, 0, 2, 1] with k = 2:

  1. Count: count = [1, 1, 2] — one 0, one 1, two 2s.
  2. Prefix sums: count = [1, 2, 4]. Now count[v] means “values up to v fill the first count[v] slots”, so the last v goes in slot count[v] − 1.
  3. Place, walking backwards: i = 3 (value 1) goes to slot 1. i = 2 (value 2) goes to slot 3. i = 1 (value 0) goes to slot 0. i = 0 (value 2) goes to slot 2.
  4. Result: [0, 1, 2, 2]. The 2 from index 0 lands before the 2 from index 2, so equal values kept their order.
countingSort — stable, O(n+k)O(n + k)O(n + k)
// k is the value range. Only worth it when k is comparable to n:
// sorting 1000 values in [0,10^9] this way needs a 10^9 array.
void countingSort(vector<int> &a,int k){
	vector<int> count(k+1,0);
	for(int x:a)
	count[x]++;

	// prefix sums turn counts into END positions (Chapter 6)
	for(int v=1;v<=k;v++)
	count[v]+=count[v-1];

	// walk BACKWARDS to keep it stable
	vector<int> ans(a.size());
	for(int i=a.size()-1;i>=0;i--){
		count[a[i]]--;
		ans[count[a[i]]]=a[i];
	}

	a=ans;
}
The backwards loop is what makes it stable. And stability is what makes radix sort work. Radix sort is just counting sort run once per digit, from the last digit to the first. Each pass must keep the order that the previous pass set up.

Radix sort by hand. Sort [53, 21, 42, 23]. Pass 1 sorts stably by the ones digit: [21, 42, 53, 23] (1, 2, 3, 3 — and 53 stays ahead of 23 because it came first). Pass 2 sorts stably by the tens digit: [21, 23, 42, 53]. Look at 21 and 23: both have tens digit 2, so pass 2 treats them as a tie. Only stability keeps them in the order pass 1 gave them. With an unstable pass 2 you could get [23, 21, …], and the whole sort would be wrong. Each pass is O(n + 10), and with d digits the total is O(d·n).

How to choose, in practice. In an interview or contest, start from std::sort: it is fast, well tested, and guaranteed O(n log n). Move away from it only for a reason you can name. Ties must keep their input order: use stable_sort. Values are small integers such as ages or letters: use counting sort. Data is a linked list or does not fit in memory: use merge sort. You need only the top K or the median: do not sort at all, use a heap or nth_element.

Stability: what it means and when it matters

A sort is stable if equal elements keep the order they started in. This sounds like a technicality — until you sort by two keys.

A tiny example: students (Ann, 90), (Bob, 85), (Cat, 90) listed by sign-up time. Sort by score, highest first. A stable sort must give Ann, Cat, Bob, because Ann signed up before Cat and they tie on 90. An unstable sort may give Cat, Ann, Bob — still correctly sorted by score, but the sign-up order is lost.

🧩
When you need stability
  • Sorting by several keys, one pass at a time. Sort by rank, then stably by suit. You get cards grouped by suit, with ranks in order inside each suit. Radix sort is this same idea applied to digits.
  • Keeping input order for ties — for example, leaderboards where earlier submissions should rank first, or log entries with the same timestamp.
  • Reproducibility. An unstable sort may order ties differently on different runs or platforms. That turns a test into a flaky one that passes only sometimes.

In C++, std::sort is not stable. std::stable_sort is (and it slows to O(n log² n) if it cannot get extra memory). Usually the better move is to make ties impossible: add the original index as a final tiebreaker in the comparator. Then stability does not matter.

Comparators — the part you will actually use

Sorting plain integers is rare. Sorting structs by two or three keys is routine. A comparator is the function you pass to the sort to say which of two items goes first. Comparators must follow a rule, and if you break it your program can crash.

The contract is simple to say: comp(a, b) returns true when a must come strictly before b, and false otherwise — including when they are equal. The sort never asks “are they equal?” directly. It works that out when both comp(a, b) and comp(b, a) are false.

A worked example with the multi-key comparator below. Sorting {(2,5), (1,9), (2,3), (1,4)} by first ascending, then second ascending, gives {(1,4), (1,9), (2,3), (2,5)}. The two pairs starting with 1 come first, and inside that group the second value decides. With the mixed-direction version (first descending, second ascending) you get {(2,3), (2,5), (1,4), (1,9)}. The tie(…) version works because tie bundles the fields into a tuple, and tuples already compare field by field, left to right.

the comparator patterns worth memorisingstrict weak ordering
// Multi-key: ascending by first, then ascending by second on a tie.
// This is exactly the pattern from my Vertical Order solution.
bool compare(const pair<int,int> &a,const pair<int,int> &b){
	if(a.first==b.first)
	return a.second<b.second;

	return a.first<b.first;
}
sort(v.begin(),v.end(),compare);

// Same thing as a lambda, and shorter with a tuple comparison:
sort(v.begin(),v.end(),[](auto &a,auto &b){
	return tie(a.first,a.second)<tie(b.first,b.second);
});

// Descending by first, ascending by second — the mixed-direction case.
sort(v.begin(),v.end(),[](auto &a,auto &b){
	if(a.first==b.first)
	return a.second<b.second;      // ascending

	return a.first>b.first;            // descending
});

// Sort indices instead of values, when you must keep the original positions.
vector<int> idx(n);
iota(idx.begin(),idx.end(),0);
sort(idx.begin(),idx.end(),[&](int i,int j){
	return a[i]<a[j];
});

// Min-heap of pairs — the greater<> idiom used throughout the graph chapters.
priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> pq;
Note the parameter types: const T&, not T. Taking them by value copies both arguments on every one of the ~n log n comparisons. For strings or vectors, that copying can cost more than the rest of the sort.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SORT KEY FIRST
Put the value you sort by first in the pair or tuple, then the default lexicographic comparison is already correct and you need no comparator at all.
⛔ STRICT WEAK
A comparator must return false for equal elements. return a<=b is undefined behaviour in std::sort and really does crash on large inputs.
💡 MERGE COUNTS
Anything of the form "count pairs out of order" is merge sort with a counter in the merge step. Inversions, reverse pairs and count-of-smaller are one algorithm.
💥
A comparator must be a strict weak ordering, or sort will crash

std::sort requires comp(x, x) == false for every x. In other words, an item must never come “before” itself. If you return true for equal elements, the partition loop can run off the end of the array. The result is a segfault (crash) or silent memory corruption — not just a wrong answer.

Broken — uses <=
// comp(x,x) returns TRUE. Undefined behaviour.
sort(v.begin(),v.end(),[](int a,int b){
	return a<=b;
});
Correct — strict <
// comp(x,x) returns false. Well defined.
sort(v.begin(),v.end(),[](int a,int b){
	return a<b;
});

The same trap hides in multi-key comparators. if(a.first==b.first) return a.second<=b.second; is broken for exactly the same reason. It often passes small tests and fails on large input, which makes it a miserable bug to find. The comparator must also be transitive (if a comes before b and b before c, then a comes before c) and consistent (the same pair always gives the same answer). Comparing by a field that changes during the sort, or by rand(), is undefined behaviour — even if each single call looks harmless.

⚠️
Common mistakes
  • <= in a comparator. It breaks the strict weak ordering rule and crashes std::sort on large inputs. Always use a strict comparison.
  • Comparator parameters by value. This copies on every comparison. For strings or vectors, that can cost more than the sort itself.
  • Using std::sort when ties must keep their input order. It is not stable. Use stable_sort, or add the index as a final tiebreaker.
  • Always picking the first or last element as the quicksort pivot. Already-sorted input — the most common real input — becomes the O(n²) worst case.
  • Including the pivot in a recursive call. quickSort(a,lo,p) recurses forever when the pivot lands at lo.
  • Allocating the merge buffer inside merge. Correct but slow: it costs an O(n) allocation on every call. Allocate once in the driver and pass it by reference.
  • Using < instead of <= in merge. It still sorts correctly, but silently loses stability.
  • Counting sort with a huge value range. O(n+k) with k = 10⁹ is not a fast linear sort. It is an out-of-memory error.
  • Sorting everything when you only need the top K. A heap of size K takes O(n log k), and nth_element takes O(n) (Chapters 15 and 37).

Interview drill

Warm-up: Your std::sort crashes with a segfault on large inputs but works on small ones. What do you check first?

How a strong answer sounds
The comparator. std::sort requires a strict weak ordering, and that specifically means comp(x,x) must be false. Suppose I wrote return a <= b, or a multi-key version that ends in return a.second <= b.second on a tie. Then equal elements compare "true" in both directions. The introsort partition loop relies on the comparison to stop it (it has no sentinel, or stop marker). So the inner pointer walks past the end of the range and corrupts memory. It only shows up on large inputs. Small ranges go down the insertion-sort path, which happens to tolerate a bad comparator. The fix is to make every comparison strict. I would also check that the comparator is transitive and depends only on fields that do not change. Comparing on a value that changes during the sort, or on anything random, is undefined behaviour — even though each call looks fine on its own.

Deeper: You have 10⁸ 32-bit integers on disk and 100 MB of RAM. Sort them.

How a strong answer sounds
That is 400 MB of data but only 100 MB of memory. So it is an external sort — sorting data that does not fit in memory. This is the classic use of merge sort. Phase one: read the file in chunks that fit comfortably in RAM, say 20 million integers (80 MB). Sort each chunk in memory with std::sort, and write it back out as a sorted “run”. That gives me five sorted runs on disk. Phase two: a k-way merge across all five runs. I use a min-heap of size five that holds one buffered element from each run. I pop the smallest, then refill from that run's buffer. The output streams straight to the result file. Memory use is just the read buffers plus a tiny heap. I would make each buffer about a megabyte, so disk reads stay sequential instead of jumping around for every element. Total work is O(n log n) with two passes over the data. The key design point: merge sort only ever reads data in order, which is exactly what disks and network streams are good at. Quicksort jumps around in memory, which would be disastrous here. If the integers turned out to be in a small range, I would mention that a counting or radix pass avoids comparisons entirely. But the merge approach is the safe general answer.

🧠 Key takeaways

  • Insertion sort is the only quadratic sort worth using: for small n, nearly sorted data, or items arriving one at a time. std::sort switches to it below ~16 elements.
  • Merge sort is always O(n log n) and stable. Add one line to its merge step and it counts inversions for free.
  • Quicksort needs a random (or median-of-three) pivot, or sorted input becomes its worst case. A three-way partition handles duplicates.
  • No comparison sort beats O(n log n), because log₂(n!) = Θ(n log n). Counting and radix sort escape this by using values as indices instead of comparing.
  • A comparator must be strict. <= breaks strict weak ordering and crashes std::sort on large inputs.

What does a comparator returning a <= b cause in std::sort?

Strict weak ordering requires that an item never comes before itself. With <=, equal elements compare true both ways. The partition loop has no stop marker, so it runs past the end of the range. It usually only shows up on large inputs, because small ranges take the insertion-sort path.

Why is quicksort O(n²) on an already-sorted array with a fixed last-element pivot?

The pivot is always the largest value, so nothing goes to its right. That gives n levels × O(n) work = O(n²), plus O(n) stack depth. A random or median-of-three pivot makes this extremely unlikely.

What single change to merge's inner comparison silently destroys stability?

On a tie, <= takes from the left half, which holds the earlier elements — that is stability. With strict <, the right element wins ties, so equal elements swap order. The array is still correctly sorted, so no test catches it.

Why can no comparison-based sort beat O(n log n)?

Each comparison gives one yes/no answer (one bit). With n! possible orders, you need at least log₂(n!) bits, and Stirling's formula puts that at Θ(n log n). Radix sort is not a comparison sort. It uses digit values as indices, which a comparison sort is not allowed to do.
