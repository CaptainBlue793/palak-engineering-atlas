Sorting: Every Algorithm & Comparators

You will almost never implement a sort in production — and you will be asked to explain one in nearly every interview, because a sort is where invariants, recursion, stability and complexity all show up at once. This chapter races six sorts side by side, proves the O(n log n) comparison lower bound, and then spends real time on the thing you will use daily: custom comparators, including the subtle contract that makes them crash when you get it wrong.

  • Implement and explain bubble, insertion, selection, merge, quick and counting sort
  • Say why comparison sorting cannot beat O(n log n), and how radix sort sidesteps it
  • Define stability and know exactly when you need it
  • Write custom comparators that satisfy strict weak ordering — and know what happens when they do not
  • Choose the right sort from the input's shape rather than by habit

The O(n²) family — worth knowing, not worth using

Three quadratic sorts. Each teaches something different, and one of them is genuinely useful.

// Invariant: after pass i, the last i elements are final and in place.
// The swapped flag makes it O(n) on already-sorted input — the one merit it has.
void bubbleSort(vector<int> &a){
	int n=a.size();

	for(int i=0;i<n-1;i++){
		bool swapped=false;

		for(int j=0;j<n-1-i;j++){
			if(a[j]>a[j+1]){
				swap(a[j],a[j+1]);
				swapped=true;
			}
		}

		if(!swapped)break;      // nothing moved -> already sorted
	}
}

Stable. O(n) best, O(n²) average and worst. Never the right choice, but the swapped flag and the n-1-i bound are worth being able to justify. If you write j<n-1 instead, you re-compare elements already known to be final.

// Invariant: after pass i, the first i elements are the i smallest, sorted.
// Always exactly n-1 swaps — the minimum possible. That is its one use.
void selectionSort(vector<int> &a){
	int n=a.size();

	for(int i=0;i<n-1;i++){
		int mini=i;

		for(int j=i+1;j<n;j++){
			if(a[j]<a[mini])
			mini=j;
		}

		if(mini!=i)
		swap(a[i],a[mini]);
	}
}

Not stable — the long-distance swap jumps equal elements past each other. O(n²) in every case, including sorted input. Its niche: when a write is far more expensive than a read, as with flash memory or a network round trip, n−1 writes beats everything else.

// Invariant: a[0..i-1] is sorted. Insert a[i] into its place by shifting.
// Genuinely useful: O(n) on nearly-sorted data, tiny constant, stable, in place.
void insertionSort(vector<int> &a){
	int n=a.size();

	for(int i=1;i<n;i++){
		int key=a[i];
		int j=i-1;

		while(j>=0 and a[j]>key){   // strictly > keeps it stable
			a[j+1]=a[j];
			j--;
		}

		a[j+1]=key;
	}
}

The one quadratic sort that earns its place. std::sort switches to insertion sort for partitions under about 16 elements, because the constant factor beats quicksort's recursion overhead. Also the natural choice for an online sort, where elements arrive one at a time.

✍️
My convention: name the invariant, then read the loop bounds off it

Every sort above starts with a one-line invariant comment, and every loop bound follows from it. “After pass i the last i are final” gives you j<n-1-i. “a[0..i-1] is sorted” gives you i starting at 1. This is why the bounds are not something to memorise — they are derived, every time, from one sentence.

Merge sort: the reliable one

Split in half, sort each half, merge. O(n log n) in every case, stable, and the merge step is a tool in its own right — counting inversions, finding a reverse pair, and external sorting all come out of it.

mergeSort — helper + driverO(n log n) alwaysO(n)
// temp is allocated ONCE by the driver and passed down by reference.
// Allocating inside merge() would add an O(n) allocation per call.
void merge(vector<int> &a,int lo,int mid,int hi,vector<int> &temp){
	int i=lo;
	int j=mid+1;
	int k=lo;

	while(i<=mid and j<=hi){
		if(a[i]<=a[j])temp[k++]=a[i++];   // <= is what makes it STABLE
		else temp[k++]=a[j++];
	}

	while(i<=mid)temp[k++]=a[i++];
	while(j<=hi)temp[k++]=a[j++];

	for(int x=lo;x<=hi;x++)
	a[x]=temp[x];
}
void mergeSortHelper(vector<int> &a,int lo,int hi,vector<int> &temp){
	if(lo>=hi)return;

	int mid=lo+(hi-lo)/2;

	mergeSortHelper(a,lo,mid,temp);
	mergeSortHelper(a,mid+1,hi,temp);
	merge(a,lo,mid,hi,temp);
}
void mergeSort(vector<int> &a){
	if(a.size()<2)return;

	vector<int> temp(a.size());
	mergeSortHelper(a,0,a.size()-1,temp);
}
a[i] <= a[j] is load-bearing. On a tie it takes from the left half, which is where the earlier elements live — that is exactly what stability means. Change it to < and merge sort becomes unstable while still producing a correctly sorted array, so no test catches it.
🔢
The merge step counts inversions for free

When you take a[j] from the right half, every remaining element in the left half — that is mid - i + 1 of them — is greater than it, and each forms an inversion. Add that count in the else branch and merge sort counts inversions in O(n log n). The same observation solves “reverse pairs” and “count of smaller numbers after self”. It is one of the highest-value one-line additions in the course.

Quicksort: fast, and dangerous in the obvious case

Pick a pivot, partition so smaller elements are left and larger are right, recurse on both sides. No merge step, so it sorts in place — and it is usually faster than merge sort in practice because of locality. The catch is the worst case.

quickSort with Lomuto partition and a random pivotO(n log n) expected, O(n²) worstO(log n) stack
// Invariant: a[lo..i] are <= pivot, a[i+1..j-1] are > pivot.
int partition(vector<int> &a,int lo,int hi){
	// Random pivot: without this, sorted input gives O(n^2).
	int r=lo+rand()%(hi-lo+1);
	swap(a[r],a[hi]);

	int pivot=a[hi];
	int i=lo-1;

	for(int j=lo;j<hi;j++){
		if(a[j]<=pivot){
			i++;
			swap(a[i],a[j]);
		}
	}

	swap(a[i+1],a[hi]);      // pivot into its final position
	return i+1;
}
void quickSort(vector<int> &a,int lo,int hi){
	if(lo>=hi)return;

	int p=partition(a,lo,hi);

	quickSort(a,lo,p-1);       // p is final — never include it
	quickSort(a,p+1,hi);
}
The pivot ends up in its final position, so neither recursive call includes it. Writing quickSort(a,lo,p) gives infinite recursion when the pivot lands at lo. And the random pivot is not optional: with a fixed first-or-last pivot, already sorted input — the most common real-world case — is the O(n²) worst case.
🎨
Three-way partition when there are many duplicates

Lomuto puts elements equal to the pivot on one side, so an array of all-equal values still recurses n deep — O(n²). A three-way (Dutch national flag) partition splits into <, ==, > and recurses only on the outer two, making all-equal input O(n). This is what std::sort effectively does, and it is the right answer to “what if the array is mostly duplicates?”

Beating O(n log n): counting and radix

🧾
Why no comparison sort can beat O(n log n)

A comparison sort learns only one bit per comparison — “is x < y?”. There are n! possible orderings and the algorithm must distinguish all of them, so its decision tree needs at least n! leaves. A binary tree with n! leaves has depth at least log₂(n!), and by Stirling's approximation log₂(n!) ≈ n log₂ n − 1.44n = Θ(n log n). So some input forces that many comparisons. Counting and radix sort escape this not by being cleverer but by not comparing — they use the values as array indices, which is extra information the model forbids.

countingSort — stable, O(n+k)O(n + k)O(n + k)
// k is the value range. Only worth it when k is comparable to n:
// sorting 1000 values in [0,10^9] this way needs a 10^9 array.
void countingSort(vector<int> &a,int k){
	vector<int> count(k+1,0);
	for(int x:a)
	count[x]++;

	// prefix sums turn counts into END positions (Chapter 6)
	for(int v=1;v<=k;v++)
	count[v]+=count[v-1];

	// walk BACKWARDS to keep it stable
	vector<int> ans(a.size());
	for(int i=a.size()-1;i>=0;i--){
		count[a[i]]--;
		ans[count[a[i]]]=a[i];
	}

	a=ans;
}
The backwards loop is what makes it stable, and stability is what makes radix sort work — radix sort is just counting sort applied digit by digit from least significant to most, and each pass must preserve the order established by the previous one.

Stability: what it means and when it matters

A sort is stable if elements comparing equal keep their original relative order. This sounds academic until you sort by two keys.

Stability is what lets you sort by a secondary key first and a primary key second, and have both respected. Without it, the first sort is wasted.
🧩
When you need stability
  • Multi-key sorting done in passes. Sort by rank, then stably by suit, and you get suit-major with rank ordered inside. Radix sort is this idea applied to digits.
  • Preserving input order for ties — leaderboards where earlier submissions should rank first, or log entries at the same timestamp.
  • Reproducibility. An unstable sort may order ties differently between runs or platforms, which turns a test into a flake.

In C++: std::sort is not stable, std::stable_sort is (and is O(n log² n) if it cannot allocate). Usually the better move is to make ties impossible by adding the index as a tiebreaker in the comparator — then stability is irrelevant.

Comparators — the part you will actually use

Sorting integers is rare. Sorting structs by two or three keys is routine, and comparators have a contract that will crash your program if you break it.

the comparator patterns worth memorisingstrict weak ordering
// Multi-key: ascending by first, then ascending by second on a tie.
// This is exactly the pattern from my Vertical Order solution.
bool compare(const pair<int,int> &a,const pair<int,int> &b){
	if(a.first==b.first)
	return a.second<b.second;

	return a.first<b.first;
}
sort(v.begin(),v.end(),compare);

// Same thing as a lambda, and shorter with a tuple comparison:
sort(v.begin(),v.end(),[](auto &a,auto &b){
	return tie(a.first,a.second)<tie(b.first,b.second);
});

// Descending by first, ascending by second — the mixed-direction case.
sort(v.begin(),v.end(),[](auto &a,auto &b){
	if(a.first==b.first)
	return a.second<b.second;      // ascending

	return a.first>b.first;            // descending
});

// Sort indices instead of values, when you must keep the original positions.
vector<int> idx(n);
iota(idx.begin(),idx.end(),0);
sort(idx.begin(),idx.end(),[&](int i,int j){
	return a[i]<a[j];
});

// Min-heap of pairs — the greater<> idiom used throughout the graph chapters.
priority_queue<pair<int,int>,vector<pair<int,int>>,greater<pair<int,int>>> pq;
Note the parameter types: const T&, not T. Taking by value copies both arguments on every one of the ~n log n comparisons, which for a comparator over strings or vectors can dominate the entire sort.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 SORT KEY FIRST
Put the value you sort by first in the pair or tuple, then the default lexicographic comparison is already correct and you need no comparator at all.
⛔ STRICT WEAK
A comparator must return false for equal elements. return a<=b is undefined behaviour in std::sort and really does crash on large inputs.
💡 MERGE COUNTS
Anything of the form "count pairs out of order" is merge sort with a counter in the merge step. Inversions, reverse pairs and count-of-smaller are one algorithm.
💥
A comparator must be a strict weak ordering, or sort will crash

std::sort requires comp(x, x) == false for every x. Return true for equal elements and the partition loop runs off the end of the array — a segfault or silent memory corruption, not a wrong answer.

Broken — uses <=
// comp(x,x) returns TRUE. Undefined behaviour.
sort(v.begin(),v.end(),[](int a,int b){
	return a<=b;
});
Correct — strict <
// comp(x,x) returns false. Well defined.
sort(v.begin(),v.end(),[](int a,int b){
	return a<b;
});

The same trap in a multi-key comparator: if(a.first==b.first) return a.second<=b.second; is broken for exactly the same reason. It often passes small tests and fails on large input, which makes it a miserable bug to find. Also: the comparator must be transitive and consistent — comparing by a mutable field, or by rand(), is undefined behaviour even if each individual call looks harmless.

⚠️
Common mistakes
  • <= in a comparator. Violates strict weak ordering and crashes std::sort on large inputs. Always strict.
  • Comparator parameters by value. Copies on every comparison; for strings or vectors this can cost more than the sort itself.
  • Using std::sort when ties must keep input order. It is not stable. Use stable_sort, or add the index as a final tiebreaker.
  • Fixed first-or-last pivot in quicksort. Already-sorted input — the most common real input — becomes the O(n²) worst case.
  • Including the pivot in a recursive call. quickSort(a,lo,p) recurses forever when the pivot lands at lo.
  • Allocating the merge buffer inside merge. Correct but slow: an O(n) allocation per call. Allocate once in the driver and pass by reference.
  • Using < instead of <= in merge. Still sorts correctly, silently loses stability.
  • Counting sort with a huge value range. O(n+k) where k = 10⁹ is not a linear-time sort, it is an out-of-memory error.
  • Sorting when you only need the top K. A size-K heap is O(n log k), and nth_element is O(n) (Chapters 15 and 37).

Interview drill

Warm-up: Your std::sort crashes with a segfault on large inputs but works on small ones. What do you check first?

How a strong answer sounds
The comparator. std::sort requires a strict weak ordering, which specifically means comp(x,x) must be false. If I wrote return a <= b, or a multi-key version ending in return a.second <= b.second on a tie, then equal elements compare "true" in both directions and the introsort partition loop has no sentinel to stop it — so the inner pointer walks past the end of the range and corrupts memory. It only shows up on large inputs because small ranges fall into the insertion-sort path, which happens to be tolerant of a bad comparator. The fix is to make every comparison strict. I would also check that the comparator is transitive and depends only on immutable fields — comparing on a value that mutates during the sort, or anything random, is undefined behaviour even though each call looks fine in isolation.

Deeper: You have 10⁸ 32-bit integers on disk and 100 MB of RAM. Sort them.

How a strong answer sounds
That is 400 MB of data against 100 MB of memory, so it is an external sort — the classic merge-sort application. Phase one: read the file in chunks that fit comfortably in RAM, say 20 million integers (80 MB), sort each chunk in memory with std::sort, and write it back out as a sorted run. That gives me five sorted runs on disk. Phase two: a k-way merge across all five runs using a min-heap of size five, holding one buffered element from each run, popping the smallest and refilling from that run's buffer — output streams straight to the result file. Memory use is just the read buffers plus a tiny heap, and I would size the buffers to a megabyte or so each so the disk reads stay sequential rather than seeking per element. Total work is O(n log n) with two passes over the data, and the design point is that merge sort only ever needs sequential access, which is exactly what disks and network streams are good at — quicksort's random access pattern would be catastrophic here. If the integers turned out to be in a small range I would mention that a counting or radix pass avoids comparisons entirely, but the merge approach is the safe general answer.

🧠 Key takeaways

  • Insertion sort is the only quadratic sort worth using — small n, nearly sorted, or online — and std::sort falls back to it below ~16 elements.
  • Merge sort is O(n log n) always and stable; its merge step counts inversions for free with one extra line.
  • Quicksort needs a random (or median-of-three) pivot, or sorted input is its worst case; three-way partition handles duplicates.
  • No comparison sort beats O(n log n) because log₂(n!) = Θ(n log n); counting and radix escape by indexing rather than comparing.
  • A comparator must be strict: <= violates strict weak ordering and crashes std::sort on large inputs.

Check your understanding

What does a comparator returning a <= b cause in std::sort?

Strict weak ordering requires irreflexivity. With <=, equal elements compare true both ways and the partition loop has no sentinel, so it runs past the end of the range. It typically only shows up on large inputs, because small ranges take the insertion-sort path.

Why is quicksort O(n²) on an already-sorted array with a fixed last-element pivot?

The pivot is always the maximum, so nothing goes to its right. n levels × O(n) work = O(n²), plus O(n) stack depth. A random or median-of-three pivot makes this vanishingly unlikely.

What single change to merge's inner comparison silently destroys stability?

On a tie, <= takes from the left half, which holds the earlier elements — that is stability. With strict < the right element wins ties and equal elements swap order. The array is still correctly sorted, so no test catches it.

Why can no comparison-based sort beat O(n log n)?

Each comparison yields one bit. With n! possible answers you need at least log₂(n!) bits, which Stirling puts at Θ(n log n). Radix sort is not a comparison sort — it indexes by digit value, which the model does not allow.

You need to sort records by department (ascending) and, within each department, by salary (descending). What is the cleanest approach?

A single multi-key comparator is unambiguous, one pass, and does not depend on stability at all. The two-pass version only works with stable_sort for the second pass, and option A additionally has the order backwards.
