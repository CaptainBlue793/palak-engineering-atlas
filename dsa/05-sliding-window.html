Sliding Window

A sliding window is a stretch of the array, marked by a left and a right index, that you slide along instead of starting over each time. It is the highest-value pattern in interview prep: it turns “check every subarray” from O(n²) into O(n), and about one problem in eight is a hidden version of it. The mechanics take five minutes to learn. Two things take real practice: writing the shrink condition and knowing when the technique does not apply. That is where most of this chapter goes.

  • Write both templates from memory: fixed size, and variable size with a shrink loop
  • State the window's invariant (what stays true) and get the shrink condition from it
  • Explain why it is O(n) even though there is a while loop nested inside the main loop
  • Use the “at most K” subtraction trick for “exactly K” counting problems
  • Spot the cases where a window is simply wrong, and know what to use instead

The idea in one picture

Say you want to know something about every contiguous subarray — every unbroken run of elements. The brute force fixes a left end and tries every right end. That is O(n²), and it recomputes almost everything from scratch.

The window insight: going from [l, r] to [l, r+1] is one addition, not a whole new scan. It is like reading a long sentence through a cardboard slot: you slide the slot one word along instead of rereading from the start. If you can update your answer step by step like that, one pass is enough.

To see the saving, count the work for the sum of every window of size 3 in [2, 1, 5, 1, 3, 2]. The brute force adds 3 numbers for each of the 4 windows: 12 additions. The window adds the first 3 once (2 + 1 + 5 = 8), then each slide is one add and one subtract: 8 + 1 − 2 = 7, then 7 + 3 − 1 = 9, then 9 + 2 − 5 = 6. With a window of size 1,000 over 10⁵ elements, that is the difference between about 10⁸ additions and about 2 × 10⁵.

Two rules make it work, and both must hold:

Incremental update

Adding a[r] and removing a[l] must each cost O(1) — or O(log n) if you use a heap or multiset. A running sum works. A count of distinct values works, using a frequency map. A median does not, unless you add extra machinery.

Monotone shrink condition

If the window is already invalid, making it bigger on the right must not fix it. That is what lets l move forward and never back. Sums of positive numbers behave this way. Sums that can include negatives do not — and that is the most important exception in this chapter.

Which template to pick? If the problem tells you the window size (“every block of k days”, “subarrays of length k”), use the fixed-size template. If it asks for the longest or shortest stretch that satisfies a condition (“longest substring with no repeats”, “shortest subarray with sum ≥ target”), the size is what you are solving for, so use the variable-size template.

Template 1: fixed-size window

Here the window size is given to you. Fill the first window, then slide it one step at a time: add the new element on the right, remove the old one on the left.

maxSumOfSizeKO(n)O(1)
// Invariant: sum is always the total of exactly the last k elements read.
int maxSumOfSizeK(vector<int> &a,int k){
	if(a.size()<k)return 0;

	int sum=0;
	for(int i=0;i<k;i++)
	sum+=a[i];

	int maxi=sum;

	for(int r=k;r<a.size();r++){
		sum+=a[r];              // slide in
		sum-=a[r-k];            // slide out — the element leaving the window
		maxi=max(maxi,sum);
	}

	return maxi;
}
The index to get right is r-k. When r comes in, the window becomes [r-k+1, r], so the element that just dropped out is at r-k. Write the window's two ends in a comment as you code, and this stops being guesswork.

Check it with k = 3 on [2, 1, 5, 1, 3, 2]. The first loop gives sum = 8 (indices 0–2). At r = 3, add a[3]=1 and remove a[0]=2: the window is now indices 1–3 and the sum is 7. At r = 4, add 3 and remove a[1]=1: 9. At r = 5, add 2 and remove a[2]=5: 6. The best is 9, from [5, 1, 3]. Edge cases: if the array is shorter than k, no full window exists, and the guard returns 0 (check what your problem wants there). If values can be large, make sum a long long.

Template 2: variable-size window — the one that matters

This is the workhorse. The right pointer always moves forward. The left pointer moves only while the window is invalid. The whole template is four lines, and every variable-window problem you meet is just a different while condition.

the universal variable-window skeletonO(n)O(k)
int left=0;
int ans=0;

for(int right=0;right<n;right++){
	// 1. EXTEND: bring a[right] into the window
	add(a[right]);

	// 2. SHRINK: while the window violates the condition, drop from the left
	while(invalid()){
		remove(a[left]);
		left++;
	}

	// 3. RECORD: the window [left,right] is now valid — use it
	ans=max(ans,right-left+1);
}
Extend, shrink, record. Always in that order. Recording before shrinking measures a window that is still invalid. Shrinking before extending throws away an element you have not counted yet.

Here is the skeleton running on “longest substring without repeating characters” for the string "abba". The invariant is “no character appears twice in [left, right]”.

Why a nested while is still O(n)

It looks like O(n²): a while inside a for. But count the work the right way — count pointer moves, not loop rounds. right moves forward exactly n times over the whole run. left only ever moves forward, and it can never pass right, so it moves at most n times in total, added up over every run of the inner loop. Total movement is at most 2n, so the algorithm is O(n). The inner while may run many times on one round and not at all on the next; what is limited is the total. This is the same amortized argument as push_back in Chapter 2.

The window variants, and what changes

Here are four of the most common problems. Notice how little actually changes between them.

// Invariant: [left,right] has no repeated character.
int longestUnique(string &s){
	unordered_map<char,int> count;
	int left=0;
	int maxi=0;

	for(int right=0;right<s.size();right++){
		count[s[right]]++;

		while(count[s[right]]>1){
			count[s[left]]--;
			left++;
		}

		maxi=max(maxi,right-left+1);
	}

	return maxi;
}

Shrink while the character you just added appears twice. No other character can have become a duplicate, since nothing else changed.

// Invariant: [left,right] has at most k distinct characters.
int longestAtMostK(string &s,int k){
	unordered_map<char,int> count;
	int left=0;
	int maxi=0;

	for(int right=0;right<s.size();right++){
		count[s[right]]++;

		while(count.size()>k){
			count[s[left]]--;
			if(count[s[left]]==0)
			count.erase(s[left]);       // must erase, or size() lies
			left++;
		}

		maxi=max(maxi,right-left+1);
	}

	return maxi;
}

The erase is not optional. If you leave a key behind with a count of zero, count.size() still counts characters that have already left the window, and the shrink loop stops working correctly. A classic bug.

// Invariant: [left,right] covers all of t, and we shrink to make it minimal.
string minWindow(string &s,string &t){
	unordered_map<char,int> need;
	for(char c:t)need[c]++;

	int missing=t.size();       // total characters still owed
	int left=0;
	int bestLen=INT_MAX;
	int bestLeft=0;

	for(int right=0;right<s.size();right++){
		if(need[s[right]]>0)missing--;
		need[s[right]]--;

		while(missing==0){              // valid -> shrink while still valid
			if(right-left+1<bestLen){
				bestLen=right-left+1;
				bestLeft=left;
			}

			need[s[left]]++;
			if(need[s[left]]>0)missing++;
			left++;
		}
	}

	return bestLen==INT_MAX?"":s.substr(bestLeft,bestLen);
}

Looking for the shortest window flips the shape. For a longest window, you shrink while the window is invalid and record afterwards. For a shortest window, you shrink while the window is still valid and record inside the shrink loop. Notice that need is allowed to go negative — that is how it keeps track of spare copies of a character at no extra cost.

// Invariant: sum is the total of [left,right]. Needs all values POSITIVE.
int minSubArrayLen(int target,vector<int> &a){
	int left=0;
	int sum=0;
	int mini=INT_MAX;

	for(int right=0;right<a.size();right++){
		sum+=a[right];

		while(sum>=target){
			mini=min(mini,right-left+1);
			sum-=a[left];
			left++;
		}
	}

	return mini==INT_MAX?0:mini;
}

Same shortest-window shape. This is the one that breaks if the array can contain negative numbers — see the warning below.

The minimum-window tab has the least obvious bookkeeping, so here it is in words. need[c] starts as “how many copies of c the window still owes”, and missing is the total owed. For t = "AABC", need is A:2, B:1, C:1 and missing is 4. When a character enters the window, if it was still owed (need[c] > 0), one debt is paid and missing drops. Its need goes down either way; a negative value such as A:−1 means “one spare A in the window”. When a character leaves, need goes back up, and if it becomes positive again, the window owes that character once more, so missing rises. The window is valid exactly when missing == 0. That single integer replaces comparing two whole count tables on every step.

When the window is simply wrong

This section separates people who have memorised the template from people who understand it.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 GROW THEN SHRINK
Always structure it as: extend right unconditionally, then while the window is invalid move left. An if instead of a while is the bug that passes the sample and fails the rest.
💡 EXACTLY K
"Exactly K distinct" has no direct window. Compute atMost(K) − atMost(K−1) — two runs of the same helper, and the subtraction does the work.
⛔ NEGATIVES
A sliding window needs the constraint to be monotone as the window grows. With negative numbers the sum is not monotone, so the window silently fails — that is a prefix-sum-plus-deque problem instead.
🚨
Negative numbers destroy the shrink condition

Take “shortest subarray with sum ≥ target”, with a = [10, 2, -5, 20] and target = 20. The window [0,1] has sum 12, below the target, so it extends. At [0,2] the sum falls to 7. The window's whole assumption is broken: extending right no longer always helps, and shrinking once you are over the target no longer always makes sense. Adding an element can make things worse; removing one can make things better.

What to use instead: prefix sums (running totals) with a monotonic deque, or prefix sums with a hash map for the exact-sum versions. Chapter 6 covers both. The test is one question: “can adding an element to my window ever push the answer the wrong way?” If yes, it is not a window problem.

The last row deserves an example because its condition is not a plain sum. In "AABABBA" with K = 1 replacement, the window "AABA" has length 4 and its most common letter (A) appears 3 times. To make it all one letter you only change the letters that are not A: 4 − 3 = 1 change, which fits K. Extend to "AABAB" and you need 5 − 3 = 2 changes, which is too many, so the window shrinks. The condition “length − maxFreq ≤ K” is the invariant, and the while condition is its opposite.

The “exactly K” trick

Counting subarrays with exactly K distinct elements is not a window problem on its own — “exactly K” does not behave in one direction as the window grows. But there is a neat trick that turns it into two window problems:

exactly(K) = atMost(K) − atMost(K−1)

Both of those terms are window problems, because “at most K distinct” behaves in one direction. Write atMost once, call it twice, and subtract.

subarraysWithKDistinctO(n)O(k)
// Count of subarrays with AT MOST k distinct values.
// Key line: every window [left..right] contributes (right-left+1) subarrays
// ending at right, because every start in [left,right] is valid.
int atMost(vector<int> &a,int k){
	unordered_map<int,int> count;
	int left=0;
	int ans=0;

	for(int right=0;right<a.size();right++){
		count[a[right]]++;

		while(count.size()>k){
			count[a[left]]--;
			if(count[a[left]]==0)
			count.erase(a[left]);
			left++;
		}

		ans+=right-left+1;
	}

	return ans;
}
int subarraysWithKDistinct(vector<int> &a,int k){
	return atMost(a,k)-atMost(a,k-1);
}
ans += right-left+1 is the counting line worth memorising. Once the window is valid, every subarray that ends at right and starts anywhere in [left, right] is also valid. That is right-left+1 subarrays. This line shows up in dozens of counting problems.

Why does the subtraction work? Every subarray with at most K distinct values has either exactly K, or at most K−1. So the “at most K” count is (exactly K) + (at most K−1), and moving one term across gives the formula. Here it is with numbers, for a = [1, 2, 1, 2, 3] and K = 2:

  • atMost(2): the window adds 1, 2, 3, 4, 2 as right goes from 0 to 4 (at right = 4 the 3 forces the window to shrink to [2, 3]). Total 12.
  • atMost(1): neighbouring values always differ, so the window is always a single element and adds 1 each time. Total 5.
  • exactly(2) = 12 − 5 = 7. Listing them by hand confirms it: [1,2], [2,1], [1,2], [2,3], [1,2,1], [2,1,2], [1,2,1,2].

One edge case to watch: if K could be 0, the code calls atMost(a, -1). In count.size()>k, size() is unsigned, so C++ converts −1 into a huge unsigned number, the condition is never true, and the window never shrinks — a wrong answer with no warning. No non-empty subarray has 0 distinct values, so the fix is a guard: return 0 when K is 0. (Most versions of this problem promise K ≥ 1, which is why the code above leaves it out.)

🔁
The same reduction, everywhere

“Count subarrays whose sum falls in the range [lo, hi]” becomes atMost(hi) − atMost(lo−1). “Count subarrays with exactly K odd numbers” becomes atMostOdd(K) − atMostOdd(K−1). Whenever a counting problem says “exactly”, ask whether the “at most” version works as a window. Usually it does — and then you have already written the solution.

⚠️
Common mistakes
  • Using a window when values can be negative. The shrink rule no longer holds and the answer is quietly wrong. Use prefix sums instead (Ch 6).
  • Recording the answer before shrinking when looking for the longest window. You measure a window that is still invalid. The order is extend → shrink → record.
  • Forgetting to erase keys whose count hits zero when the condition uses map.size(). Leftover keys make size() count characters that have left the window.
  • Getting the fixed-window removal index wrong. After r comes in, the element leaving is a[r-k], not a[r-k+1]. Write the two ends down.
  • Using if instead of while for the shrink. One new element can force several removals — for example “at most K distinct” when a long run of new values arrives.
  • Assuming the nested while makes it O(n²). It does not, and explaining why is a real plus in an interview. Count pointer moves, not loop rounds.
  • Mixing up the shortest and longest shapes. Longest: shrink while invalid, record afterwards. Shortest: shrink while valid, record inside the loop.
🎤
Interview drill

Warm-up: Your sliding-window solution has a while inside a for. Justify the O(n).

How a strong answer sounds
Count pointer moves instead of loop rounds. The right pointer moves forward exactly n times over the whole run, once per outer round. The left pointer only ever moves forward and can never pass the right pointer, so across every run of the inner while added together it moves at most n times. Total movement is at most 2n, and each move does O(1) work, so the algorithm is O(n) — or O(n log k) if adding and removing uses an ordered structure. The inner loop might run five times on one outer round and not at all on the next twenty; what is limited is the total, not the count per round. It is the same amortized argument that makes vector's push_back O(1).

Deeper: Given an array with negative numbers, find the shortest subarray with sum ≥ K. Why not a window, and what instead?

How a strong answer sounds
A window needs the sum to move in one direction as the window grows, and with negatives it does not. Extending right can lower the sum, so both “I am below target, so extend” and “I am above target, so shrink” stop being safe. Concretely: [10, 2, −5, 20] with K = 20 gives window sums 10, 12, 7, 27, and a shrink-when-valid rule throws away a left element it may still need. The right tool is prefix sums plus a monotonic deque. Build P[i] = the sum of the first i elements. I want the smallest i − j with P[i] − P[j] ≥ K and j < i. Sweep i from left to right and keep a deque of candidate j values whose P is strictly increasing. For each i, pop from the front while P[i] − P[front] ≥ K, recording the length — a later i is only further away, so those fronts can never do better. Then, before pushing i, pop from the back while P[back] ≥ P[i], because a later index with a smaller prefix sum is better in every way. Each index enters and leaves the deque once, so it is O(n) time and O(n) space. The general lesson: when the one-direction property fails, switch from a window over values to a structure over prefix sums.

🧠 Key takeaways

  • Extend, shrink, record — always in that order. Getting the order wrong means measuring invalid windows.
  • Longest: shrink while invalid, record afterwards. Shortest: shrink while valid, record inside the shrink loop.
  • The nested while is still O(n), because what matters is total pointer movement, not loop rounds.
  • A window needs a condition that only moves one way as the window grows. Negative values break that, and prefix sums are the replacement.
  • ans += right-left+1 counts every valid subarray ending at right; exactly(K) = atMost(K) − atMost(K−1).

Check your understanding

Why is a sliding window with a nested while loop still O(n)?

Count pointer moves, not loop rounds. The inner loop may run many times on one outer step and not at all on the next. What is limited is the total: at most n moves for each pointer.

You are finding the shortest subarray satisfying a condition. Where do you record the answer?

Looking for the shortest window flips the shape. You shrink while the window is still valid, so every round of the shrink loop is a possible answer. Record inside it, then remove an element and carry on.

Your window condition tests count.size() > k. What must you do when a count reaches zero?

map::size() counts keys, not keys with a non-zero value. A leftover zero entry makes the distinct count too high, and the shrink loop misbehaves. This is the most common bug in “at most K distinct”.

Which problem is not solvable with a sliding window?

Negative values break the one-direction rule: extending the window can lower the sum, so neither the extend rule nor the shrink rule is safe. That one needs prefix sums with a hash map (Chapter 6).

In a counting problem, once the window [left, right] is valid, how many valid subarrays end at right?

For “at most” conditions, moving left forward only makes the window safer, so every start from left to right works. Adding right-left+1 at each step is the line behind exactly(K) = atMost(K) − atMost(K−1).
