Sliding Window

The sliding window is the single most productive pattern in interview prep: it turns “check every subarray” from O(n²) into O(n), and roughly one problem in eight is a disguised instance of it. The mechanics take five minutes. The two things that actually take practice are writing the shrink condition and knowing when the technique is invalid — so that is where most of this chapter goes.

  • Write both templates from memory: fixed size, and variable size with a shrink loop
  • State the window invariant and derive the shrink condition from it
  • Prove the O(n) bound even though there is a nested while
  • Use the “at most K” subtraction trick for exact-K counting problems
  • Recognise the cases where a window is simply wrong, and what to use instead

The idea in one picture

You want something about every contiguous subarray. The brute force fixes a left end and walks every right end: O(n²), and it recomputes almost everything. The window insight is that moving from [l, r] to [l, r+1] is one addition, not a fresh scan — so if you can maintain your answer incrementally, one pass suffices.

Two rules make it work, and both must hold:

Incremental update

Adding a[r] and removing a[l] must each be O(1) — or O(log n) with a heap or multiset. A sum qualifies; a “number of distinct values” qualifies with a frequency map; a median does not, without extra machinery.

Monotone shrink condition

If the window is invalid, extending it right must not fix it. That is what lets l move forward and never back. Positive sums qualify. Sums that may be negative do not — and that is the single most important exception in this chapter.

Template 1: fixed-size window

The size is given. Fill the first window, then slide one step at a time, adding on the right and removing on the left.

maxSumOfSizeKO(n)O(1)
// Invariant: sum is always the total of exactly the last k elements read.
int maxSumOfSizeK(vector<int> &a,int k){
	if(a.size()<k)return 0;

	int sum=0;
	for(int i=0;i<k;i++)
	sum+=a[i];

	int maxi=sum;

	for(int r=k;r<a.size();r++){
		sum+=a[r];              // slide in
		sum-=a[r-k];            // slide out — the element leaving the window
		maxi=max(maxi,sum);
	}

	return maxi;
}
The index to get right is r-k. When r enters, the window becomes [r-k+1, r], so the element that just left is at r-k. Write the window bounds in a comment while you code and this stops being a guess.

Template 2: variable-size window — the one that matters

This is the workhorse. The right pointer always advances; the left pointer advances only while the window is invalid. The whole template is four lines, and every variable-window problem you will meet is a different while condition.

the universal variable-window skeletonO(n)O(k)
int left=0;
int ans=0;

for(int right=0;right<n;right++){
	// 1. EXTEND: bring a[right] into the window
	add(a[right]);

	// 2. SHRINK: while the window violates the condition, drop from the left
	while(invalid()){
		remove(a[left]);
		left++;
	}

	// 3. RECORD: the window [left,right] is now valid — use it
	ans=max(ans,right-left+1);
}
Extend, shrink, record. Always that order. Recording before shrinking measures an invalid window; shrinking before extending drops an element you have not accounted for yet.
✍️
My convention: name the invariant in a comment above the loop

One line — // Invariant: [left,right] contains no repeated character — and the while condition writes itself as the negation. If you cannot phrase the invariant, you are not ready to write the loop, and every boundary decision after that is a coin flip. This is the Chapter 1 rule applied to the pattern you will use most.

Why a nested while is still O(n)

It looks like O(n²) — a while inside a for. But count the work the right way: count pointer movements, not loop iterations. right advances exactly n times over the whole run. left only ever advances, and it can never pass right, so it advances at most n times in total across all executions of the inner loop. Total movement ≤ 2n, so the algorithm is O(n). The inner while may run many times on one iteration and zero times on the next; what is bounded is the sum. This is the same amortized argument as push_back in Chapter 2.

The window variants, and what changes

Four of the most common problems. Look at how little differs.

// Invariant: [left,right] has no repeated character.
int longestUnique(string &s){
	unordered_map<char,int> count;
	int left=0;
	int maxi=0;

	for(int right=0;right<s.size();right++){
		count[s[right]]++;

		while(count[s[right]]>1){
			count[s[left]]--;
			left++;
		}

		maxi=max(maxi,right-left+1);
	}

	return maxi;
}

Shrink while the newly added character is duplicated. Nothing else can have become duplicated.

// Invariant: [left,right] has at most k distinct characters.
int longestAtMostK(string &s,int k){
	unordered_map<char,int> count;
	int left=0;
	int maxi=0;

	for(int right=0;right<s.size();right++){
		count[s[right]]++;

		while(count.size()>k){
			count[s[left]]--;
			if(count[s[left]]==0)
			count.erase(s[left]);       // must erase, or size() lies
			left++;
		}

		maxi=max(maxi,right-left+1);
	}

	return maxi;
}

The erase is mandatory. Leaving a zero-count key behind means count.size() counts characters no longer in the window, and the shrink loop never terminates correctly. Classic bug.

// Invariant: [left,right] covers all of t, and we shrink to make it minimal.
string minWindow(string &s,string &t){
	unordered_map<char,int> need;
	for(char c:t)need[c]++;

	int missing=t.size();       // total characters still owed
	int left=0;
	int bestLen=INT_MAX;
	int bestLeft=0;

	for(int right=0;right<s.size();right++){
		if(need[s[right]]>0)missing--;
		need[s[right]]--;

		while(missing==0){              // valid -> shrink while still valid
			if(right-left+1<bestLen){
				bestLen=right-left+1;
				bestLeft=left;
			}

			need[s[left]]++;
			if(need[s[left]]>0)missing++;
			left++;
		}
	}

	return bestLen==INT_MAX?"":s.substr(bestLeft,bestLen);
}

The shape inverts for minimisation. For a longest window you shrink while invalid and record after. For a shortest window you shrink while valid and record inside the shrink loop. Notice need is allowed to go negative — that is how it tracks surplus characters for free.

// Invariant: sum is the total of [left,right]. Needs all values POSITIVE.
int minSubArrayLen(int target,vector<int> &a){
	int left=0;
	int sum=0;
	int mini=INT_MAX;

	for(int right=0;right<a.size();right++){
		sum+=a[right];

		while(sum>=target){
			mini=min(mini,right-left+1);
			sum-=a[left];
			left++;
		}
	}

	return mini==INT_MAX?0:mini;
}

Same minimisation shape. This is the one that breaks with negative numbers — see the warning below.

When the window is simply wrong

This is the part that separates people who have memorised the template from people who understand it.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 GROW THEN SHRINK
Always structure it as: extend right unconditionally, then while the window is invalid move left. An if instead of a while is the bug that passes the sample and fails the rest.
💡 EXACTLY K
"Exactly K distinct" has no direct window. Compute atMost(K) − atMost(K−1) — two runs of the same helper, and the subtraction does the work.
⛔ NEGATIVES
A sliding window needs the constraint to be monotone as the window grows. With negative numbers the sum is not monotone, so the window silently fails — that is a prefix-sum-plus-deque problem instead.
🚨
Negative numbers destroy the shrink condition

“Shortest subarray with sum ≥ target”, with a = [10, 2, -5, 20] and target = 20. A sliding window at [0,1] has sum 12, which is below target, so it extends. At [0,2] the sum drops to 7. The window's core assumption — that extending right can only help, and that once you are over target you should shrink — is broken, because adding an element can make things worse and removing one can make things better.

What to use instead: prefix sums plus a monotonic deque, or prefix sums plus a hash map for the exact-sum variants. Chapter 6 covers both. The diagnostic question is one sentence: “can adding an element to my window ever move the answer in the wrong direction?” If yes, it is not a window problem.

The “exactly K” trick

Counting subarrays with exactly K distinct elements is not directly a window problem — the count is not monotone. But there is a clean reduction that turns it into two window problems:

exactly(K) = atMost(K) − atMost(K−1)

Both terms are windows, because “at most K distinct” is monotone. Write atMost once, call it twice, subtract.

subarraysWithKDistinctO(n)O(k)
// Count of subarrays with AT MOST k distinct values.
// Key line: every window [left..right] contributes (right-left+1) subarrays
// ending at right, because every start in [left,right] is valid.
int atMost(vector<int> &a,int k){
	unordered_map<int,int> count;
	int left=0;
	int ans=0;

	for(int right=0;right<a.size();right++){
		count[a[right]]++;

		while(count.size()>k){
			count[a[left]]--;
			if(count[a[left]]==0)
			count.erase(a[left]);
			left++;
		}

		ans+=right-left+1;
	}

	return ans;
}
int subarraysWithKDistinct(vector<int> &a,int k){
	return atMost(a,k)-atMost(a,k-1);
}
ans += right-left+1 is the counting line worth memorising. Once the window is valid, every subarray ending at right and starting anywhere in [left, right] is also valid — that is right-left+1 of them. It appears in dozens of counting problems.
🔁
The same reduction, everywhere

“Count subarrays with sum exactly in [lo, hi]” becomes atMost(hi) − atMost(lo−1). “Count subarrays with exactly K odd numbers” becomes atMostOdd(K) − atMostOdd(K−1). Whenever a counting problem says “exactly”, ask whether “at most” is monotone. Usually it is, and then you have written the solution.

⚠️
Common mistakes
  • Using a window when values can be negative. The shrink condition stops being monotone and the answer is silently wrong. Prefix sums instead (Ch 6).
  • Recording the answer before shrinking in a maximisation problem. You measure an invalid window. Order is extend → shrink → record.
  • Forgetting to erase zero-count keys when the condition depends on map.size(). Stale keys make size() report characters that left the window.
  • Getting the fixed-window removal index wrong. After r enters, the element leaving is a[r-k], not a[r-k+1]. Write the bounds down.
  • Using if instead of while for the shrink. One added element can require several removals — “at most K distinct” with a long run of new values, for instance.
  • Assuming the nested while makes it O(n²). It does not, and being able to explain why is a real interview signal. Count pointer movements, not iterations.
  • Mixing up the minimisation and maximisation shapes. Longest: shrink while invalid, record after. Shortest: shrink while valid, record inside.
🎤
Interview drill

Warm-up: Your sliding-window solution has a while inside a for. Justify the O(n).

How a strong answer sounds
Count pointer movements instead of loop iterations. The right pointer advances exactly n times over the whole run, once per outer iteration. The left pointer only ever increases and can never exceed the right pointer, so across every execution of the inner while combined it advances at most n times. Total movement is bounded by 2n, and each movement does O(1) work, so the algorithm is O(n) — or O(n log k) if the add/remove uses an ordered structure. The inner loop might run five times on one outer iteration and zero times on the next twenty; what is bounded is the sum, not the per-iteration count. It is the same amortized argument that makes vector's push_back O(1).

Deeper: Given an array with negative numbers, find the shortest subarray with sum ≥ K. Why not a window, and what instead?

How a strong answer sounds
A window needs the sum to move monotonically as the window grows, and with negatives it does not — extending right can lower the sum, so "I am below target, extend" and "I am above target, shrink" are both unsound. Concretely, [10, 2, −5, 20] with K = 20: the window sum goes 10, 12, 7, 27, and a shrink-when-valid rule discards a left element it may need later. The right tool is prefix sums plus a monotonic deque. Build P[i] = sum of the first i elements; I want the shortest i − j with P[i] − P[j] ≥ K and j < i. Sweep i and keep a deque of candidate j indices with strictly increasing P. For each i, pop from the front while P[i] − P[front] ≥ K, recording the length — those fronts can never be beaten by a later i, since a later i is further away. Then pop from the back while P[back] ≥ P[i] before pushing i, because a later index with a smaller prefix dominates. Each index enters and leaves once, so it is O(n) time and O(n) space. The general lesson: when monotonicity fails, move from a window over values to a structure over prefix sums.

🧠 Key takeaways

  • Extend, shrink, record — in that order, always. Getting the order wrong measures invalid windows.
  • Longest: shrink while invalid and record after. Shortest: shrink while valid and record inside the shrink loop.
  • The nested while is still O(n) because you count pointer movements, not loop iterations.
  • A window needs a monotone condition — negative values break it, and prefix sums are the replacement.
  • ans += right-left+1 counts every valid subarray ending at right; exactly(K) = atMost(K) − atMost(K−1).

Check your understanding

Why is a sliding window with a nested while loop still O(n)?

Count movements, not iterations. The inner loop may run many times on one outer step and zero times on the next; what is bounded is the total, at n moves for each pointer.

You are finding the shortest subarray satisfying a condition. Where do you record the answer?

Minimisation inverts the shape. You shrink while valid, so every iteration of the shrink loop is a candidate answer — record inside it, then remove and continue.

Your window condition tests count.size() > k. What must you do when a count reaches zero?

map::size() counts keys, not non-zero values. A leftover zero entry inflates the distinct count and the shrink loop stops behaving. This is the single most common bug in “at most K distinct”.

Which problem is not solvable with a sliding window?

Negative values break monotonicity: extending the window can lower the sum, so neither the extend nor the shrink rule is sound. That one needs prefix sums with a hash map (Chapter 6).

In a counting problem, once the window [left, right] is valid, how many valid subarrays end at right?

Shrinking left only ever makes the window more valid for “at most” conditions, so every start from left to right works. Adding right-left+1 each step is the line behind exactly(K) = atMost(K) − atMost(K−1).
