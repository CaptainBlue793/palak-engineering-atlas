Bit Manipulation

Bit tricks are a small vocabulary — perhaps a dozen idioms — that recur constantly: in bitmask DP, in hash sets of small alphabets, in tries, in sign handling, and in a family of interview problems that are only solvable in O(1) space because XOR happens to be a group operation. This chapter is the vocabulary, the three properties of XOR worth internalising, and the undefined-behaviour landmines in C++.

  • Use the core idioms fluently, and know their precedence traps
  • Internalise the three XOR properties that make the single-number family work
  • Split a set by a distinguishing bit — the two-single-numbers technique
  • Count bits, enumerate subsets, and use bits as a tiny hash set
  • Avoid the undefined behaviour around shifts, signed types and overflow

// ---- single bits ----
bool isSet=(x>>i)&1;               // read bit i
x|=(1<<i);                           // set bit i
x&=~(1<<i);                          // clear bit i

// ---- lowest set bit ----
int low=x&-x;                        // isolate it (two's complement magic)
x&=(x-1);                           // clear it  — the Kernighan step
int idx=__builtin_ctz(x);            // its index (undefined if x==0!)

// ---- whole-number facts ----
bool isPow2=x>0 and (x&(x-1))==0;   // exactly one bit set
int bits=__builtin_popcount(x);       // how many 1s
int high=31-__builtin_clz(x);          // index of the highest set bit = floor(log2 x)
bool sameSign=(x^y)>=0;             // the sign bit agrees

// ---- arithmetic in disguise ----
int twice=x<<1;                      // x*2
int half=x>>1;                       // x/2, for NON-NEGATIVE x
int mod8=x&7;                        // x%8, for non-negative x (8 = 1<<3)
int roundDown=x&~7;                  // round down to a multiple of 8

// ---- the safe midpoint ----
int mid=low+((high-low)>>1);        // no overflow, unlike (low+high)/2
Why does x&-x isolate the lowest set bit? In two's complement, -x is ~x+1. Adding 1 to the flipped value propagates a carry through the trailing 1s of ~x — exactly the positions where x had trailing 0s — until it lands on x's lowest 1. So -x agrees with x at that one bit and disagrees everywhere below and above it, and the AND leaves precisely that bit. Two landmines in this block: __builtin_ctz(0) and __builtin_clz(0) are undefined, so guard for zero; and x>>1 is not x/2 for negative x (it rounds towards negative infinity, while division truncates towards zero), so -7>>1 is −4 while -7/2 is −3.
💣
Precedence and undefined behaviour — the five real hazards
  • &, |, ^ bind looser than == and !=. So x & 1 == 0 parses as x & (1==0), which is x & 0, which is 0 — always false. Parenthesise every comparison: (x & 1) == 0.
  • They also bind looser than + and -, so x & y - 1 is x & (y-1). That one happens to be what you usually want, which is precisely why it is dangerous to rely on.
  • 1<<31 overflows a signed 32-bit int — undefined behaviour. For bit 31 or beyond, write 1u<<31 or 1LL<<i.
  • Shifting by ≥ the type's width is undefined, not zero. x << 32 on a 32-bit int is not 0; it is whatever the hardware does.
  • Shifting a negative number left is undefined, and right-shifting one is implementation-defined (in practice arithmetic). Use unsigned types when you are treating a value as a bag of bits rather than a number.

The habit that prevents all five: parenthesise generously, and use unsigned or long long whenever the value is a bitmask rather than a quantity.

XOR: three properties, one family of problems

⊕
Everything about XOR follows from these
  • Self-inverse: a ^ a == 0. A value XORed in twice vanishes.
  • Identity: a ^ 0 == a.
  • Commutative and associative: the order of a XOR chain is irrelevant.

Together they make XOR an abelian group operation where every element is its own inverse. The practical consequence: XORing a whole array cancels every value appearing an even number of times and leaves the XOR of the odd-count ones. That is why the entire "find the element appearing once" family is solvable in one pass and O(1) space — no hash set required. It is also why XOR is not usable when you need to know how many times something appeared; cancellation destroys that information.

Pairs annihilate in any order — which is exactly why a single pass with one integer suffices.
One element appears once
// Every element appears twice except one. Find it.
// The pairs cancel; only the loner survives.
int singleNumber(vector<int> &nums){
	int ans=0;

	for(auto &x:nums)
	ans^=x;

	return ans;
}

// Missing number from 0..N — the same idea, XORing the
// expected values against the present ones.
int missingNumber(vector<int> &nums){
	int N=nums.size();
	int ans=0;

	for(int i=0;i<=N;i++)
	ans^=i;

	for(auto &x:nums)
	ans^=x;

	return ans;
}

O(1) space, one pass, no hash set. Compare with the sum-based trick for the missing number (N(N+1)/2 − sum), which is equally valid but can overflow where XOR never does — XOR never grows beyond the width of its operands.

Two elements appear once
// Every element appears twice except TWO. Find both.
// Step 1: XOR everything -> a^b, where a and b are the two loners.
// Step 2: any set bit of a^b is a bit where a and b DIFFER, so it splits
//         the array into two groups, each containing exactly one loner.
vector<int> singleNumberIII(vector<int> &nums){
	long long xorAll=0;

	for(auto &x:nums)
	xorAll^=x;

	// pick the lowest bit where they differ
	long long diff=xorAll&-xorAll;

	int a=0;
	int b=0;

	for(auto &x:nums){
		if(x&diff)a^=x;         // group where that bit is 1
		else b^=x;              // group where it is 0
	}

	return {a,b};
}

"Split by a distinguishing bit" is the transferable idea. Every duplicated pair lands in the same group (equal values have equal bits), so each group reduces to the one-single problem. Using long long for xorAll avoids the INT_MIN edge case where -x overflows.

✍️
My convention: ans as the accumulator, range-for by reference

Every one of these is int ans=0; followed by for(auto &x:nums) ans^=x; — the same two-line shape, which is why I keep the accumulator named ans across the whole family. It makes the variation visible: single number is one accumulator, two singles is the same loop run twice with a filter, and the three-times variant below replaces ^ with a pair of counters. When four problems share a skeleton, keeping the names identical is what turns them into one thing you know rather than four things you memorised — the same reason LevelOrder, ZigZag, LeftView and RightView are written with one loop in Chapter 17.

every element appears three times except oneO(32n) or O(n)O(1)
// XOR no longer works: three copies leave one behind rather than cancelling.
// Approach A — count each bit position mod 3. Clear, and easy to generalise
// to "appears k times" by changing the 3.
int singleNumberII(vector<int> &nums){
	int ans=0;

	for(int bit=0;bit<32;bit++){
		int count=0;

		for(auto &x:nums){
			if((x>>bit)&1)count++;
		}

		if(count%3)ans|=(1<<bit);   // the loner contributed this bit
	}

	return ans;
}

// Approach B — two accumulators acting as a mod-3 counter in parallel across
// all 32 bits. `ones` holds bits seen 1 mod 3 times, `twos` bits seen 2 mod 3.
int singleNumberII_fast(vector<int> &nums){
	int ones=0;
	int twos=0;

	for(auto &x:nums){
		ones=(ones^x)&~twos;
		twos=(twos^x)&~ones;
	}

	return ones;
}
Prefer Approach A in an interview. It is obviously correct, it generalises in one character ("appears k times, one appears once" — change the 3), and you can explain it in a sentence: each bit position is counted independently, and a count not divisible by 3 must include the loner's contribution. Approach B is clever and fast but essentially unexplainable under pressure, and a solution you cannot justify is worth less than one you can. One caveat for A: with negative numbers, bit 31 is the sign bit and building ans by OR-ing 1<<31 is technically UB on signed int — use unsigned internally and cast at the end.

Counting bits and enumerating subsets

popcount three ways, and the subset loopsee notes
// (1) naive — 32 iterations regardless of the value
int popcountNaive(int x){
	int count=0;

	for(int bit=0;bit<32;bit++){
		if((x>>bit)&1)count++;
	}

	return count;
}

// (2) Kernighan — one iteration per SET bit. Much better for sparse values.
int popcountKernighan(int x){
	int count=0;

	while(x){
		x&=(x-1);                  // clears the lowest set bit
		count++;
	}

	return count;
}

// (3) the DP — popcount for EVERY value 0..N in O(N).
// x has the same bits as x>>1, plus its own lowest bit.
vector<int> countBits(int N){
	vector<int> dp(N+1,0);

	for(int x=1;x<=N;x++)
	dp[x]=dp[x>>1]+(x&1);

	return dp;
}

// Enumerate every subset of an n-element array.
void allSubsets(vector<int> &nums){
	int n=nums.size();

	for(int mask=0;mask<(1<<n);mask++){
		vector<int> temp;

		for(int i=0;i<n;i++){
			if((mask>>i)&1)temp.push_back(nums[i]);
		}

		// temp is one subset
	}
}
Kernighan's x&=(x-1) is worth genuinely understanding, because it appears everywhere: subtracting 1 flips the lowest set bit to 0 and turns every 0 below it into 1, so the AND keeps the bits above and clears the lowest 1 along with everything under it. That also gives the power-of-two test for free, and it is how you iterate the set bits of a mask without scanning all 32 positions. In practice, use __builtin_popcount (or C++20's std::popcount) — it compiles to a single instruction on modern hardware. The subset loop is the iterative alternative to backtracking from Chapter 34; it is clearer for a fixed small n, while backtracking is better when you need pruning.
🎒
Bits as a tiny hash set

For a 26-letter alphabet, a single int replaces a whole set — and the operations become arithmetic:

// mask of the distinct letters in a lowercase word
int signature(string &s){
	int mask=0;

	for(auto &c:s)
	mask|=(1<<(c-'a'));

	return mask;
}

// two words share no letter  <->  their masks AND to zero
bool disjoint=(signature(a)&signature(b))==0;

// all 26 letters present (a pangram)
bool pangram=mask==(1<<26)-1;

// at most one odd count -> can be rearranged into a palindrome
// (use ^= instead of |= to track PARITY rather than presence)
bool canPalindrome=(parity&(parity-1))==0;

This turns "maximum product of two words with no common letters" from O(n²·L) into O(n² ) after an O(n·L) preprocessing pass, and it is why the "words with no shared letters" problem is a bit problem in disguise. The |= versus ^= distinction is the useful one to remember: OR records presence, XOR records parity, and the palindrome-permutation family needs parity.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 TWELVE IDIOMS
x&-x isolates the lowest set bit, x&(x-1) clears it, and that pair gives you popcount, power-of-two and set iteration. Learn them as vocabulary.
💡 XOR CANCELS PAIRS
XOR is self-inverse, so it deletes everything appearing an even number of times. That is the whole single-number family, in O(1) space and one pass.
⛔ PARITY BREAKS AT 3
With three copies XOR no longer cancels. Count each bit position mod 3 instead — and that version generalises to any k by changing one character.
⚠️
Common mistakes
  • x & 1 == 0 parses as x & (1==0) — always false. Parenthesise the comparison.
  • 1<<31 on a signed int is undefined behaviour; use 1u<<31 or 1LL<<i.
  • Shifting by ≥ the type width is undefined, not zero.
  • __builtin_ctz(0) / __builtin_clz(0) are undefined. Guard for zero first.
  • Assuming x>>1 == x/2 for negatives. Shifts round towards −∞; division truncates towards zero.
  • Using XOR when elements appear three times. Odd counts do not cancel; count bits mod 3 instead.
  • -x when x is INT_MIN overflows. Use long long for the x&-x trick on arbitrary input.
  • Forgetting that XOR loses count information. It tells you what survived, never how many times anything appeared.
  • Using |= when you needed parity (or ^= when you needed presence).
  • Hand-rolling popcount in a hot loop instead of __builtin_popcount, which is one instruction.
  • Using the sum trick for the missing number on large N without long long — XOR has no overflow.

Interview drill

Warm-up: Every element appears twice except two. Find both, in O(n) time and O(1) space.

How a strong answer sounds
XOR is self-inverse and commutative, so XORing the whole array cancels every pair and leaves a ^ b, where a and b are the two loners. That alone is not enough — I need to separate them. The observation is that since a and b are different, a ^ b has at least one set bit, and every set bit is a position where a and b differ. So I pick any one of them — the lowest is convenient, via the idiom diff = xorAll & -xorAll — and use it to partition the array into the elements with that bit set and those without. That partition has two useful properties: a and b land in different groups by construction, and every duplicated pair lands in the same group, because equal values have identical bits. So each group is now an instance of the single-number problem, and one more XOR pass over the array with a filter produces both answers. Two passes, O(n) time, two integers of space. One detail I would mention: I would accumulate into a long long, because if the array can contain INT_MIN then negating it in x & -x overflows signed int. The transferable idea here is "split the input by a distinguishing bit" — it also shows up when you need to find a pair with a particular XOR, and in binary-trie solutions to maximum-XOR problems.

Deeper: Now every element appears three times except one. Why does XOR fail, and what replaces it?

How a strong answer sounds
XOR fails because it is a parity operation: it cancels values appearing an even number of times, and three is odd, so every triple leaves one copy of itself behind and the accumulator ends up as the XOR of every distinct value rather than the loner. The fix is to stop thinking in parity and count properly. I work bit position by bit position: for each of the 32 positions, count how many array elements have that bit set. Every triple contributes either 0 or 3 to that count, so the count is divisible by 3 unless the loner also has that bit set. So the answer is built by setting exactly those bits whose count is not divisible by 3. That is O(32n) time — linear — and O(1) space, and I like it because it is obviously correct and it generalises by changing one character: for "every element appears k times except one", take the count modulo k. There is a faster variant using two accumulators, ones and twos, that implements a mod-3 counter in parallel across all bits with a couple of masked XORs, and I would mention it exists — but I would write the bit-counting version, because I can justify every line of it under pressure and the clever one is essentially unexplainable. One implementation detail: with negative inputs, bit 31 is the sign bit, and OR-ing 1<<31 into a signed int is technically undefined, so I would accumulate into an unsigned value and cast at the end.

🧠 Key takeaways

  • A dozen idioms cover almost everything: read/set/clear/flip, x&-x, x&(x-1), popcount, and the safe midpoint.
  • XOR is self-inverse, so it cancels even-count values — that is the whole single-number family, in O(1) space.
  • Split by a distinguishing bit to separate two unknowns; every duplicate pair stays together.
  • Parity breaks at three copies: count each bit position mod k instead, which generalises in one character.
  • Parenthesise everything, and use unsigned or long long when a value is a bitmask rather than a number.

Check your understanding

What does if(x & 1 == 0) actually test?

& binds looser than ==. Write (x & 1) == 0. This silently makes a branch unreachable rather than failing to compile, which is what makes it dangerous.

Why does x & -x isolate the lowest set bit?

Worth knowing the mechanism, since it explains the INT_MIN caveat: negating it overflows, so use long long when the input is arbitrary.

Every element appears three times except one. Why does XORing everything fail?

You end up with the XOR of every distinct value. The fix is to count each bit position mod 3 — which generalises to any k by changing the 3.

What does x &= (x-1) do, and why is it useful?

Kernighan's step. Subtracting 1 flips the lowest 1 to 0 and everything below it to 1, so the AND keeps only the bits above it — one iteration per set bit rather than 32.
