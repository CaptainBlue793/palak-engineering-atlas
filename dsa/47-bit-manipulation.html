Bit Manipulation

Bit tricks are a small set of patterns — about a dozen — that keep coming back. You will see them in bitmask DP, in tiny sets of letters, in tries, in sign handling, and in a group of interview problems that can only be solved in O(1) space thanks to how XOR behaves. This chapter covers those patterns, the three XOR rules worth knowing by heart, and the C++ traps where the behaviour is undefined (the language makes no promise about what happens).

  • Use the core patterns comfortably, and know their operator-precedence traps
  • Learn the three XOR rules that make the "single number" problems work
  • Split a set using one bit where two values differ — the two-single-numbers technique
  • Count bits, list every subset, and use bits as a tiny set
  • Avoid undefined behaviour with shifts, signed types and overflow

The vocabulary

Why bother with bits at all? Because an int is really 32 on/off switches, and the processor can flip, test or combine all 32 in a single step. That gives you three things: a very small, very fast set (one bit per item), arithmetic shortcuts (doubling, halving, "is it a power of two?"), and a few problems — like finding the one number without a partner — that have an O(1)-space answer only through bits.

~x flips every bit. x<<k slides the bits k places left, filling with zeros (multiplying by 2ᵏ), and x>>k slides them right, dropping the lowest k bits (dividing by 2ᵏ for non-negative x). Bit positions are counted from the right, starting at 0, and bit i is worth 2ⁱ.

the idioms worth knowing by heartO(1) each
// ---- single bits ----
bool isSet=(x>>i)&1;               // read bit i
x|=(1<<i);                           // set bit i
x&=~(1<<i);                          // clear bit i
x^=(1<<i);                           // flip bit i

// ---- lowest set bit ----
int low=x&-x;                        // isolate it (two's complement magic)
x&=(x-1);                           // clear it  — the Kernighan step
int idx=__builtin_ctz(x);            // its index (undefined if x==0!)

// ---- whole-number facts ----
bool isPow2=x>0 and (x&(x-1))==0;   // exactly one bit set
int bits=__builtin_popcount(x);       // how many 1s
int high=31-__builtin_clz(x);          // index of the highest set bit = floor(log2 x)
bool sameSign=(x^y)>=0;             // the sign bit agrees

// ---- arithmetic in disguise ----
int twice=x<<1;                      // x*2
int half=x>>1;                       // x/2, for NON-NEGATIVE x
int mod8=x&7;                        // x%8, for non-negative x (8 = 1<<3)
int roundDown=x&~7;                  // round down to a multiple of 8

// ---- the safe midpoint ----
int mid=low+((high-low)>>1);        // no overflow, unlike (low+high)/2
Why does x&-x keep only the lowest 1-bit? Computers store negative numbers in two's complement, where -x is ~x+1 (flip every bit, then add 1). Take x = 12 = 1100. Flipped, that is …0011. Adding 1 carries through the trailing 1s and gives …0100. The carry stops exactly at x's lowest 1-bit. So -x matches x at that one bit and differs everywhere else, and the AND leaves just that bit: 0100 = 4. Two traps in this block. First, __builtin_ctz(0) and __builtin_clz(0) are undefined, so check for zero first. Second, x>>1 is not x/2 for negative x. A shift rounds towards negative infinity, while division rounds towards zero, so -7>>1 is −4 but -7/2 is −3.
💣
Precedence and undefined behaviour — the five real hazards
  • &, | and ^ are evaluated after == and !=. So x & 1 == 0 is read as x & (1==0), which is x & 0, which is 0 — always false. Put brackets around every comparison: (x & 1) == 0.
  • They are also evaluated after + and -, so x & y - 1 means x & (y-1). That one happens to be what you usually want — which is exactly why it is dangerous to rely on.
  • 1<<31 overflows a signed 32-bit int — undefined behaviour. For bit 31 or higher, write 1u<<31 or 1LL<<i.
  • Shifting by the type's width or more is undefined, not zero. x << 32 on a 32-bit int is not 0; it is whatever the hardware happens to do.
  • Shifting a negative number left is undefined, and shifting one right depends on the compiler (in practice it keeps the sign). Use unsigned types when you treat a value as a bag of bits rather than a number.

The habit that prevents all five: use plenty of brackets, and use unsigned or long long whenever the value is a bitmask rather than an amount.

Try the idioms on x = 180, which is 10110100 (128 + 32 + 16 + 4), with i = 3:

  • Read bit 3: (180>>3)&1 — shifting gives 10110, whose last bit is 0. So bit 3 is off.
  • Set it: 180|8 = 10111100 = 188. Flip it also gives 188; clear it leaves 180 unchanged.
  • Lowest set bit: 180&-180 = 4 (bit 2), and __builtin_ctz(180) = 2. Clearing it: 180&179 = 176.
  • Counts: __builtin_popcount(180) = 4 ones; the highest set bit is bit 7, since 2⁷ = 128 ≤ 180 < 256.
  • Arithmetic: 180&7 = 4, the same as 180 % 8; 180&~7 = 176, the largest multiple of 8 not above 180.

XOR: three properties, one family of problems

⊕
Everything about XOR follows from these
  • Self-inverse: a ^ a == 0. A value XORed in twice disappears.
  • Identity: a ^ 0 == a. XOR with 0 changes nothing.
  • Commutative and associative: the order of a chain of XORs does not matter.

Mathematicians call this an abelian group in which every value is its own inverse. Think of a light switch: flip it twice and you are back where you started. In practice, XORing a whole array cancels every value that appears an even number of times, and leaves the XOR of the ones that appear an odd number of times. For example, 4 ^ 7 ^ 4 = 7. That is why the whole "find the element that appears once" family takes one pass and O(1) space, with no hash set. It is also why XOR is no use when you need to know how many times something appeared: the cancelling throws that information away.

Trace it on [4, 1, 2, 1, 2], where every value but one appears twice. Start with 0. Then 0^4 = 4 (100), 4^1 = 5 (101), 5^2 = 7 (111), 7^1 = 6 (110), 6^2 = 4 (100). The running value wanders, but the two 1s and the two 2s each switch their bits on and back off, and only the 4 is left. Order does not matter: any shuffle of the array ends at the same 4.

Pairs cancel out in any order. That is exactly why one pass with one integer is enough.
One element appears once
// Every element appears twice except one. Find it.
// The pairs cancel; only the loner survives.
int singleNumber(vector<int> &nums){
	int ans=0;

	for(auto &x:nums)
	ans^=x;

	return ans;
}

// Missing number from 0..N — the same idea, XORing the
// expected values against the present ones.
int missingNumber(vector<int> &nums){
	int N=nums.size();
	int ans=0;

	for(int i=0;i<=N;i++)
	ans^=i;

	for(auto &x:nums)
	ans^=x;

	return ans;
}

O(1) space, one pass, no hash set. Compare the sum trick for the missing number (N(N+1)/2 − sum). It is just as valid, but it can overflow. XOR never can, because its result never has more bits than its inputs.

Missing number on [3, 0, 1] (N = 3): XOR of 0..3 is 0^1^2^3 = 0, and XOR of the array is 3^0^1 = 2. Together, every present value appears twice and cancels, so the result 0^2 = 2 is the missing one.

Two elements appear once
// Every element appears twice except TWO. Find both.
// Step 1: XOR everything -> a^b, where a and b are the two loners.
// Step 2: any set bit of a^b is a bit where a and b DIFFER, so it splits
//         the array into two groups, each containing exactly one loner.
vector<int> singleNumberIII(vector<int> &nums){
	long long xorAll=0;

	for(auto &x:nums)
	xorAll^=x;

	// pick the lowest bit where they differ
	long long diff=xorAll&-xorAll;

	int a=0;
	int b=0;

	for(auto &x:nums){
		if(x&diff)a^=x;         // group where that bit is 1
		else b^=x;              // group where it is 0
	}

	return {a,b};
}

"Split by a bit where the two answers differ" is the idea to take with you. Every duplicated pair lands in the same group, because equal values have equal bits. So each group becomes the one-single-number problem. Using long long for xorAll avoids the INT_MIN edge case, where -x overflows.

Trace on [1, 2, 1, 3, 2, 5]: xorAll = 3^5 = 6 (110), since the pairs cancel. Its lowest set bit is 2 (010), and indeed 3 = 011 and 5 = 101 differ there. Values with that bit on: 2, 3, 2, which XOR to 3. The rest: 1, 1, 5, which XOR to 5. Why is xorAll never 0 here? Because the two loners are different, so they differ in at least one bit.

✍️
My convention: ans as the accumulator, range-for by reference

Every one of these is int ans=0; followed by for(auto &x:nums) ans^=x; — the same two-line shape. That is why I call the running total ans across the whole family. It makes the differences easy to see. Single number is one running total. Two singles is the same loop run twice with a filter. The three-times version below swaps ^ for a pair of counters. When four problems share a skeleton, keeping the names the same turns them into one thing you understand, instead of four things you memorised. It is the same reason LevelOrder, ZigZag, LeftView and RightView share one loop in Chapter 17.

every element appears three times except oneO(32n) or O(n)O(1)
// XOR no longer works: three copies leave one behind rather than cancelling.
// Approach A — count each bit position mod 3. Clear, and easy to generalise
// to "appears k times" by changing the 3.
int singleNumberII(vector<int> &nums){
	int ans=0;

	for(int bit=0;bit<32;bit++){
		int count=0;

		for(auto &x:nums){
			if((x>>bit)&1)count++;
		}

		if(count%3)ans|=(1<<bit);   // the loner contributed this bit
	}

	return ans;
}

// Approach B — two accumulators acting as a mod-3 counter in parallel across
// all 32 bits. `ones` holds bits seen 1 mod 3 times, `twos` bits seen 2 mod 3.
int singleNumberII_fast(vector<int> &nums){
	int ones=0;
	int twos=0;

	for(auto &x:nums){
		ones=(ones^x)&~twos;
		twos=(twos^x)&~ones;
	}

	return ones;
}
Prefer Approach A in an interview. It is clearly correct. It extends by changing one character: for "everything appears k times except one", change the 3. And you can explain it in one sentence: each bit position is counted on its own, and a count not divisible by 3 must include the loner. Approach B is clever and fast, but almost impossible to explain under pressure — and a solution you cannot justify is worth less than one you can. One warning for A: with negative numbers, bit 31 is the sign bit, and setting it by OR-ing 1<<31 into a signed int is technically undefined behaviour. Use unsigned inside the function and convert at the end.

Approach A on [2, 2, 3, 2]: in binary that is 10, 10, 11, 10. Bit 0 is on only in the 3, so its count is 1, and 1 % 3 ≠ 0 means the loner has bit 0. Bit 1 is on in all four numbers, count 4, and 4 % 3 = 1, so the loner has bit 1 too. The answer is 11 = 3. The three copies of 2 add 3 to every count they touch, which is exactly what % 3 removes.

Counting bits and enumerating subsets

popcount three ways, and the subset loopsee notes
// (1) naive — 32 iterations regardless of the value
int popcountNaive(int x){
	int count=0;

	for(int bit=0;bit<32;bit++){
		if((x>>bit)&1)count++;
	}

	return count;
}

// (2) Kernighan — one iteration per SET bit. Much better for sparse values.
int popcountKernighan(int x){
	int count=0;

	while(x){
		x&=(x-1);                  // clears the lowest set bit
		count++;
	}

	return count;
}

// (3) the DP — popcount for EVERY value 0..N in O(N).
// x has the same bits as x>>1, plus its own lowest bit.
vector<int> countBits(int N){
	vector<int> dp(N+1,0);

	for(int x=1;x<=N;x++)
	dp[x]=dp[x>>1]+(x&1);

	return dp;
}

// Enumerate every subset of an n-element array.
void allSubsets(vector<int> &nums){
	int n=nums.size();

	for(int mask=0;mask<(1<<n);mask++){
		vector<int> temp;

		for(int i=0;i<n;i++){
			if((mask>>i)&1)temp.push_back(nums[i]);
		}

		// temp is one subset
	}
}
Kernighan's x&=(x-1) is worth truly understanding, because it shows up everywhere. Subtracting 1 turns the lowest 1-bit into 0, and every 0 below it into 1. For example, 12 = 1100 and 11 = 1011. So the AND keeps the bits above and clears the lowest 1: 1100 & 1011 = 1000. It also gives you the power-of-two test for free, and it is how you visit just the 1-bits of a mask without checking all 32 positions. In practice, use __builtin_popcount (or C++20's std::popcount) — it becomes a single instruction on modern hardware. The subset loop is the loop-based alternative to backtracking from Chapter 35. It is clearer for a small fixed n; backtracking is better when you want to cut off branches early (pruning).

Two quick checks. The DP line dp[x] = dp[x>>1] + (x&1) works because x>>1 is x with its last bit dropped, and that smaller number has already been computed: dp[7] = dp[3] + 1 = 2 + 1 = 3, and dp[6] = dp[3] + 0 = 2. For the subset loop with nums = [a, b, c], the masks 0 to 7 give each subset exactly once: mask 5 = 101 is {a, c}, mask 6 = 110 is {b, c}, mask 0 is the empty set. Keep n below about 20, since 2ⁿ subsets each cost O(n) to build.

Bits as a tiny hash set

For a 26-letter alphabet, one int can replace a whole set: bit 0 for 'a', bit 1 for 'b', and so on. Set operations then become single bit operations:

// mask of the distinct letters in a lowercase word
int signature(string &s){
	int mask=0;

	for(auto &c:s)
	mask|=(1<<(c-'a'));

	return mask;
}

// two words share no letter  <->  their masks AND to zero
bool disjoint=(signature(a)&signature(b))==0;

// all 26 letters present (a pangram)
bool pangram=mask==(1<<26)-1;

// at most one odd count -> can be rearranged into a palindrome
// (use ^= instead of |= to track PARITY rather than presence)
bool canPalindrome=(parity&(parity-1))==0;

Example: "abc" has mask 111 = 7 and "de" has mask 11000 = 24. 7 & 24 = 0, so they share no letter. "cab" also gives 7 — the mask ignores order and repeats, which is exactly what a set does.

This turns "maximum product of two words with no common letters" from O(n²·L) into O(n² ), after one O(n·L) pass to build the masks. That is why the "words with no shared letters" problem is really a bit problem. The difference worth remembering is |= versus ^=. OR records whether a letter is present. XOR records whether it appears an odd or even number of times (its parity). The palindrome-permutation problems need parity.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 TWELVE IDIOMS
x&-x isolates the lowest set bit, x&(x-1) clears it, and that pair gives you popcount, power-of-two and set iteration. Learn them as vocabulary.
💡 XOR CANCELS PAIRS
XOR is self-inverse, so it deletes everything appearing an even number of times. That is the whole single-number family, in O(1) space and one pass.
⛔ PARITY BREAKS AT 3
With three copies XOR no longer cancels. Count each bit position mod 3 instead — and that version generalises to any k by changing one character.
⚠️
Common mistakes
  • x & 1 == 0 is read as x & (1==0) — always false. Put brackets around the comparison.
  • 1<<31 on a signed int is undefined behaviour; use 1u<<31 or 1LL<<i.
  • Shifting by the type's width or more is undefined, not zero.
  • __builtin_ctz(0) / __builtin_clz(0) are undefined. Check for zero first.
  • Assuming x>>1 == x/2 for negatives. Shifts round towards −∞; division rounds towards zero.
  • Using XOR when elements appear three times. Odd counts do not cancel; count bits mod 3 instead.
  • -x when x is INT_MIN overflows. Use long long for the x&-x trick on any input.
  • Forgetting that XOR loses count information. It tells you what is left, never how many times anything appeared.
  • Using |= when you needed parity (or ^= when you needed presence).
  • Writing your own popcount in a hot loop instead of __builtin_popcount, which is one instruction.
  • Using the sum trick for the missing number on large N without long long — XOR has no overflow.

Interview drill

Warm-up: Every element appears twice except two. Find both, in O(n) time and O(1) space.

How a strong answer sounds
XOR cancels itself and ignores order, so XORing the whole array cancels every pair and leaves a ^ b, where a and b are the two loners. That alone is not enough — I need to separate them. The key observation: a and b are different, so a ^ b has at least one 1-bit, and every 1-bit marks a position where a and b differ. I pick one of those bits — the lowest is convenient, using diff = xorAll & -xorAll — and use it to split the array into elements with that bit set and elements without. That split has two useful properties. a and b land in different groups, by design. And every duplicated pair lands in the same group, because equal values have identical bits. So each group is now a single-number problem, and one more XOR pass with a filter gives both answers. Two passes, O(n) time, two integers of space. One detail I would mention: I would collect into a long long, because if the array can contain INT_MIN, negating it in x & -x overflows a signed int. The idea to carry elsewhere is "split the input by a bit where the answers differ". It also appears when finding a pair with a given XOR, and in binary-trie solutions to maximum-XOR problems.

Deeper: Now every element appears three times except one. Why does XOR fail, and what replaces it?

How a strong answer sounds
XOR fails because it only tracks odd versus even. It cancels values that appear an even number of times. Three is odd, so every triple leaves one copy behind, and the result is the XOR of every distinct value, not the loner. The fix is to stop thinking odd/even and actually count. I work one bit position at a time: for each of the 32 positions, count how many elements have that bit set. Every triple adds either 0 or 3 to that count. So the count is divisible by 3 unless the loner also has that bit set. The answer is built by setting exactly the bits whose count is not divisible by 3. That is O(32n) time — linear — and O(1) space. I like it because it is clearly correct and it extends by changing one character: for "every element appears k times except one", take the count mod k. There is a faster version with two running values, ones and twos, that counts mod 3 for all bits at once using a few masked XORs. I would mention it exists, but I would write the bit-counting version, because I can justify every line of it under pressure and the clever one is almost impossible to explain. One implementation detail: with negative inputs, bit 31 is the sign bit, and OR-ing 1<<31 into a signed int is technically undefined. So I would collect into an unsigned value and convert at the end.

🧠 Key takeaways

  • About a dozen patterns cover almost everything: read/set/clear/flip, x&-x, x&(x-1), popcount, and the safe midpoint.
  • XOR cancels itself, so values that appear an even number of times vanish — that is the whole single-number family, in O(1) space.
  • To separate two unknowns, split by a bit where they differ; every duplicate pair stays together.
  • Odd/even tricks break at three copies: count each bit position mod k instead, which extends by changing one character.
  • Use brackets everywhere, and use unsigned or long long when a value is a bitmask rather than a number.

Check your understanding

What does if(x & 1 == 0) actually test?

& is evaluated after ==. Write (x & 1) == 0. The mistake still compiles and quietly makes a branch unreachable, which is what makes it dangerous.

Why does x & -x isolate the lowest set bit?

It is worth knowing how it works, because it explains the INT_MIN warning: negating INT_MIN overflows, so use long long when the input could be anything.

Every element appears three times except one. Why does XORing everything fail?

You end up with the XOR of every distinct value. The fix is to count each bit position mod 3 — which works for any k if you change the 3.

What does x &= (x-1) do, and why is it useful?

This is Kernighan's step. Subtracting 1 turns the lowest 1 into 0 and every bit below it into 1, so the AND keeps only the bits above it. The loop runs once per 1-bit instead of 32 times.
