Max Flow & Bipartite Matching

Picture water pipes: how much water per second can you get from one point to another? That is max flow. It is one of the most useful modelling tools in graph algorithms. Many problems that look nothing like plumbing turn out to be max flow once you build the right network: assigning tasks, cutting an image into regions, picking projects, scheduling. The algorithm rests on one surprising idea, the residual edge. It lets the algorithm undo its own earlier decisions.

The problem

You have a directed graph (edges have a direction). One node is the source s, where flow starts. One node is the sink t, where flow ends. Every edge has a capacity: the most it can carry, like the width of a pipe. Your job is to push as much flow as possible from s to t, following two rules:

Why you would care. The pipes are a picture, not the point. "Flow" can be data through a network, trucks along roads, or, most often in interviews, assignments: one unit of flow from a worker to a task means "this worker does this task". The capacities then encode the rules ("each worker at most 3 tasks"). Once a problem is written as a network, one standard algorithm solves it.

Capacity constraint

The flow on an edge can never be more than its capacity: 0 ≤ f(u,v) ≤ c(u,v).

Conservation

For every node except s and t, flow in equals flow out. Nothing is created or stored along the way.

↩️
The residual edge — the idea that makes it work

The simple greedy idea fails. Say you find any path, push as much as it can take until some edge is full (saturated), and repeat. You can get stuck. An early path can block a better arrangement, and you have no way to take it back.

The fix: when you push f units along u → v, you also add f units of reverse capacity on v → u.

That reverse edge is not a real pipe. Sending flow "backwards" along it means cancelling some flow you sent forwards earlier, so it can be sent somewhere else. An augmenting path is a path from s to t that can still carry more flow. When a later augmenting path uses a residual edge, the algorithm is undoing an earlier decision. That is exactly what greedy could not do.

This is why the algorithm gives the correct answer instead of just a greedy guess. It is the core idea of max flow. The classic example: the first path fills the middle edge and blocks everything else. Then a residual edge lets the flow reroute around it.

The classic example, step by step

Four nodes: s, a, b, t. Five edges, each with capacity 1: s→a, s→b, a→b, a→t, b→t. The best answer is clearly 2: send one unit along s→a→t and one along s→b→t.

  1. An unlucky first path: s→a→b→t, carrying 1. Now s→a, a→b and b→t are full.
  2. Plain greedy is stuck. From s the only edge with room is s→b, and from b the only real edge, b→t, is full. Greedy stops at 1, which is wrong.
  3. With residual edges, step 1 also created the reverse edge b→a with capacity 1. So there is a new path: s→b, then b→a (residual), then a→t. It carries 1 more unit. Total: 2.
  4. What really happened: the unit on a→b was cancelled. The final flow is s→a→t plus s→b→t, the optimal answer, even though the algorithm never "planned" it.

The bottleneck of a path is its smallest remaining capacity along the way; that is how much the path can carry. In this example every bottleneck is 1. On a path whose edges have room 5, 2 and 7, the bottleneck is 2.

Edmonds-Karp — Ford-Fulkerson with BFSO(V·E²)O(V²)
// Capacity matrix, because we need O(1) lookup of both cap[u][v] and cap[v][u].
// Only viable for V up to a few hundred; use an edge-list residual graph beyond that.
int maxflow(vector<vector<int>> cap,int N,int s,int t){
	int total=0;

	while(true){
		// BFS for an augmenting path in the RESIDUAL graph.
		// BFS (not DFS) is what makes this Edmonds-Karp and bounds the iterations.
		vector<int> parent(N,-1);
		parent[s]=s;

		queue<int> q;
		q.push(s);

		while(!q.empty() and parent[t]==-1){
			int node=q.front();
			q.pop();

			for(int next=0;next<N;next++){
				// residual capacity > 0 covers BOTH forward and reverse edges
				if(parent[next]==-1 and cap[node][next]>0){
					parent[next]=node;
					q.push(next);
				}
			}
		}

		if(parent[t]==-1)break;        // no path left: flow is maximum

		// bottleneck = the smallest residual capacity on the path
		int bottleneck=INT_MAX;
		for(int v=t;v!=s;v=parent[v]){
			int u=parent[v];
			bottleneck=min(bottleneck,cap[u][v]);
		}

		// push it, and create the residual capacity going back
		for(int v=t;v!=s;v=parent[v]){
			int u=parent[v];
			cap[u][v]-=bottleneck;
			cap[v][u]+=bottleneck;      // THE residual edge
		}

		total+=bottleneck;
	}

	return total;
}
cap is passed by value (copied) on purpose. The function changes it as it works, and the caller almost always still wants the original. The line cap[v][u] += bottleneck is the whole trick. One matrix holds both the forward capacity and the residual capacity. So the BFS needs only one check, cap[node][next] > 0, and it walks both kinds of edge with no special case.

Edge cases the code must handle. If s == t, the question does not make sense; decide on an answer before calling. If the input lists two edges u→v, add their capacities into cap[u][v] rather than overwriting. If it has both u→v and v→u, the matrix still works: each real capacity just starts its cell above zero, and residual capacity adds on top. The O(V²) matrix is fine for a few hundred nodes. Beyond that, use an adjacency list of edges where each edge stores the index of its reverse edge.

⏱️
Why BFS, and why the bound is what it is
  • Plain Ford-Fulkerson can be very slow. If it picks paths in any order, it is not polynomial (its time is not bounded by a power of the input size). The famous bad case has a middle edge of capacity 1. DFS keeps zig-zagging through it, one unit at a time. That takes O(max flow) rounds, which is huge when capacities are large.
  • Edmonds-Karp uses BFS, so it always picks a shortest augmenting path. You can prove the distance from s to t never shrinks, and grows at least once every E augmentations. That gives O(V·E) augmentations and O(V·E²) time in total.
  • Dinic's algorithm does better: O(V²E). In each phase it builds a level graph (nodes grouped by BFS distance) once, then pushes many paths through it. On networks where every capacity is 1, it runs in O(E√V). That is why Dinic is what you use for large bipartite matching.

Max-flow min-cut

An s-t cut splits the nodes into two groups: s on one side, t on the other. Its capacity is the total capacity of the edges that cross from the s side to the t side. Think of it as the pipes you would have to cut to stop all flow. The theorem says:

For example, in the four-node graph above, the cut {s} vs {a, b, t} crosses s→a and s→b: capacity 1 + 1 = 2. The cut {s, a} vs {b, t} crosses s→b, a→b and a→t: capacity 3. Only edges going from the s side to the t side count; an edge pointing back is ignored. The smallest cut here is 2, the same as the max flow.

max flow = min cut

🧾
Both directions, and how to find the cut

(≤) No flow can be bigger than any cut. To get from s to t, all flow must cross every s-t cut. By the capacity rule, it cannot carry more than the crossing edges allow. So max flow ≤ min cut.

(≥) Some cut is exactly equal to the max flow. When the algorithm stops, no augmenting path is left. Let S be the nodes you can still reach from s in the residual graph (the graph of edges with capacity left, including reverse edges). Let T be all the other nodes. Note that t is in T; if it were reachable, a path would still exist.

  • Every edge from S to T must be saturated (full). If it had room left, its far end would be reachable, so it would be in S.
  • Every edge from T back to S must carry zero flow. If it carried flow, its reverse edge would have room, and its start node would be in S.

So the flow across this cut equals the cut's full capacity. ∎

That proof also tells you how to find the cut. Run max flow, then BFS from s in the residual graph. The nodes you reach form S. The saturated edges from S to T are the min cut. Press the button in the visualizer above to see it.

Why the min cut is useful on its own. Many questions ask for the cheapest way to separate things, not to send anything: "fewest roads to close so the two cities are cut off", or "cheapest set of pixels to relabel so foreground and background split". You never search for cuts directly. You compute a max flow, and the theorem hands you the cut.

Bipartite matching as max flow

A bipartite graph has two groups of nodes (left and right), and edges only go between the groups. Think of job seekers on the left and jobs on the right. A matching is a set of edges where no node is used twice, so each person gets at most one job. You want the largest matching. Turning it into max flow is direct:

Add a source and a sink

Add a new s and t that sit outside the original graph.

Connect s to every left node with capacity 1

The capacity of 1 is what makes sure each left node is matched at most once.

Keep every original edge, capacity 1

Point each one from left to right.

Connect every right node to t with capacity 1

This makes sure each right node is matched at most once.

Max flow = maximum matching

All capacities are whole numbers, so there is a max flow that uses only whole units. Each unit of flow goes through exactly one left–right edge. The full middle edges are the matching.

A tiny example. Left nodes L1, L2; right nodes R1, R2. L1 can take R1 or R2; L2 can only take R1. Kuhn's algorithm (below) tries L1 first: R1 is free, so L1–R1. Then L2 tries R1, which is taken. Instead of giving up, it asks L1: "can you move?" L1 tries its other option, R2, which is free. So the result is L1–R2 and L2–R1, size 2. That "ask the current partner to move" step is the matching version of pushing flow back along a residual edge.

Kuhn's algorithm — bipartite matching without building a flow networkO(V·E)O(V)
// For each left node, try to find an augmenting path. The recursion IS the
// residual-edge idea specialised to matching: if a right node is taken, ask
// its current partner to move elsewhere.
bool tryMatch(vector<vector<int>> &graph,int u,vector<bool> &used,vector<int> &matchOf){
	for(int v:graph[u]){
		if(used[v])continue;        // already explored v in THIS attempt

		used[v]=true;

		// v is free, or v's partner can be rehoused
		if(matchOf[v]==-1 or tryMatch(graph,matchOf[v],used,matchOf)){
			matchOf[v]=u;
			return true;
		}
	}

	return false;
}
int maxMatching(vector<vector<int>> &graph,int leftN,int rightN){
	vector<int> matchOf(rightN,-1);   // matchOf[v] = the left node matched to v
	int size=0;

	for(int u=0;u<leftN;u++){
		vector<bool> used(rightN,false);   // FRESH for every left node

		if(tryMatch(graph,u,used,matchOf))
		size++;
	}

	return size;
}
Reset the used array for every left node. It stops you visiting the same right node twice within one attempt. If you kept it across attempts, it would block valid matches and you would get too small an answer. Kuhn runs in O(V·E) and is about fifteen lines. That is why it is the practical choice for matching, instead of building a full flow network. Hopcroft-Karp speeds it up to O(E√V) by finding many shortest augmenting paths per phase. That matters once V is above about 10⁴.

Where O(V·E) comes from. Kuhn makes one attempt per left node, so at most V attempts. Each attempt is one DFS that marks right nodes as used, so it looks at each edge at most once: O(E). V attempts × O(E) each = O(V·E). With 1,000 nodes per side and 10,000 edges, that is about 10⁷ steps, which runs almost instantly.

✍️
My convention: use Kuhn for matching, reach for full max flow only when capacities are not 1

If the problem is "match As to Bs, each used once", Kuhn is fifteen lines. It needs no source, sink or capacity matrix. Build the flow network only when you really need capacities other than 1: a worker who can take three tasks, a warehouse with limited stock, a node that can only pass so much through. The clue is the phrase “at most k” instead of “at most one”.

👑
König's theorem — and why it makes matching so useful

In a bipartite graph, maximum matching = minimum vertex cover. A vertex cover is a set of nodes that touches every edge. Take everything outside that cover and you get the opposite result: maximum independent set = V − maximum matching. An independent set is a set of nodes with no edge between any two of them.

These links are why matching answers questions that never mention matching at all. Examples: "fewest rows and columns that cover all the marked cells", "most rooks with none attacking another", "fewest machines to process all jobs", "most items I can pick with no conflicts".

When a problem on a bipartite structure asks for "fewest nodes to cover all edges" or "most items with no two in conflict", compute a matching. Both results fail on general graphs. There, minimum vertex cover is NP-hard (no known fast algorithm). That gap is exactly what makes bipartite graphs special.

König on the small example. In the L1, L2, R1, R2 graph the maximum matching has size 2. A vertex cover of size 2 is {L1, R1}: edge L1–R1 touches both, L1–R2 touches L1, and L2–R1 touches R1. No single node touches all three edges, so 2 is the minimum, as König promises. The other two nodes, {L2, R2}, have no edge between them, so they form an independent set of size 4 − 2 = 2.

The modelling patterns

The algorithm itself is standard. The real skill is building the network. These patterns cover most cases.

A node has a capacity, not just its edges

→ Split the node. Replace v with two nodes, v_in → v_out, joined by one edge with the node's capacity. Send all incoming edges into v_in, and all outgoing edges out of v_out.

cap[v_in][v_out] = nodeCapacity;
Several sources or several sinks

→ Add a super-source and a super-sink. Add edges with infinite capacity from the super-source to each real source, and from each real sink to the super-sink.

cap[S][src_i] = INF;
“Assign each A to at most one B”

→ Bipartite matching. Capacity 1 on the source and sink edges is what enforces "at most one".

cap[s][a] = 1; cap[b][t] = 1;
“Each worker can take up to k tasks”

→ Same network, but with cap[s][worker] = k. This is a flow problem, not a matching one, so Kuhn no longer works.

cap[s][worker] = k;
“Select projects with profits, but prerequisites cost money”

→ Project selection (also called max closure). Add an edge from the source to each profitable item, with its profit as capacity. Add an edge from each costly item to the sink, with its cost as capacity. Use infinite-capacity edges for the dependencies. Answer = total profit − min cut.

answer = totalProfit - maxflow(s,t);

Project selection with numbers. Project A earns 10 and needs tools X (cost 4) and Y (cost 3). Project B earns 5 and needs only Y. Edges: s→A 10, s→B 5; A→X, A→Y and B→Y infinite; X→t 4, Y→t 3. The max flow is 7 (4 through X, 3 through Y), so the min cut is 7 and the answer is 15 − 7 = 8. Check by hand: both projects earn 15 and cost 4 + 3 = 7, profit 8. Only A gives 10 − 7 = 3. Only B gives 5 − 3 = 2. The idea behind it: in the cut, every item is either "given up" (you lose its profit) or "bought" (you pay its cost), and the infinite edges make it impossible to take a project without its prerequisites.

“Minimum edges/nodes to disconnect X from Y”

→ This is the min cut directly, which equals the max flow. If you must remove nodes instead of edges, split the nodes first.

minCut = maxflow(s,t);
🎯
When to suspect max flow at all

Flow is a heavy hammer, and most problems do not need it. Look for these signals:

  • Two groups with a one-to-one or limited assignment between them (a bipartite structure).
  • The words “minimum cut”, “disconnect”, “bottleneck” or “capacity”.
  • A selection problem with dependencies, where taking one thing forces you to take another.
  • A greedy that clearly fails because early choices block later ones, so you need a way to undo.

If the problem is an assignment where you must keep total cost low, that is min-cost max flow or the Hungarian algorithm. Those are related, but different tools. In an interview, flow is usually about spotting and modelling it, not coding it. Say "this is max flow, here is the network, and I would use Dinic". Then talk through how you build the network.

Tips & tricks

The things that are muscle memory rather than theory — what to check first, and the line that is wrong the first time you write it.

💡 MODEL, DO NOT IMPLEMENT
The skill being tested is the reduction: what are the two sides, what is the capacity, what does a unit of flow mean. Naming max-flow and describing the graph is usually the whole answer.
💡 MATCHING = FLOW
Bipartite matching is max-flow with unit capacities. Kőnig then gives minimum vertex cover, and the complement gives maximum independent set — three answers from one run.
💡 NODE CAPACITY
To cap a node rather than an edge, split it into in- and out-halves joined by one edge of that capacity. A standard trick worth remembering.
⚠️
Common mistakes
  • Forgetting to add the residual edge. Without cap[v][u] += bottleneck the algorithm is just greedy, and it returns a wrong, smaller answer.
  • Using DFS for the augmenting path and calling it Edmonds-Karp. BFS is what guarantees the polynomial running time.
  • Changing the caller's capacity matrix. Pass it by value, or copy it first.
  • Not resetting used for each left node in Kuhn. It blocks valid augmenting paths, so the matching comes out too small.
  • Using capacity 1 when the problem says “up to k”. That quietly solves a different problem.
  • Forgetting to split nodes when the node has a capacity. Edge capacities alone cannot limit how much passes through a node.
  • Reporting every saturated edge as the min cut. Only the saturated edges from S to T count, where S is the set reachable in the residual graph.
  • Using INT_MAX for infinite capacity and then adding. Two "infinite" edges added together overflow. Use a large finite value like 1e9.
  • Using König's theorem on a graph that is not bipartite. In general graphs, minimum vertex cover is NP-hard.
  • Reaching for flow when a greedy is proven to work. Interval scheduling and many assignment problems have simple greedy solutions (Chapter 36).

Interview drill

Warm-up: Why does max flow need residual (back) edges?

How a strong answer sounds
Because without them the algorithm is a plain greedy, and it gets stuck. Pushing flow along a path fills its bottleneck edge. An unlucky early choice can block an arrangement that would carry more flow in total, and there is no way to reconsider. The residual edge fixes that. When I push f units along u → v, I add f units of capacity on v → u. That reverse edge is not a real pipe. Sending flow along it means cancelling flow I already sent on u → v, which frees those units to go somewhere else. So an augmenting path that uses a residual edge is the algorithm undoing an earlier decision. That ability to undo is exactly what turns a greedy into a correct algorithm. The code is neat, too: one capacity matrix holds both real and residual capacity. The path search just asks "is cap[u][v] > 0?" and walks both kinds of edge with no special case. It is also what makes the min-cut proof work. When no augmenting path is left, the nodes reachable from the source in the residual graph define a cut whose crossing edges are all full, so its capacity equals the flow.

Deeper: Model this: N workers, M tasks, each worker qualified for some tasks and able to take at most 3, each task needing exactly one worker. Maximise assigned tasks.

How a strong answer sounds
This is max flow, not plain matching, because of the "at most 3". Kuhn's algorithm allows at most one partner per node, and it cannot express a bigger limit. I build a network with a super-source s, the N workers, the M tasks, and a super-sink t. From s to each worker I put capacity 3; that is the workload limit. From each worker to each task they are qualified for, capacity 1. That stops the same worker being counted twice for one task. From each task to t, capacity 1, meaning "exactly one worker per task". The max flow is then the maximum number of assigned tasks. All capacities are whole numbers, so there is a max flow using whole units only. The full worker-to-task edges therefore give a real, valid assignment, not a fractional one. I would use Dinic: O(V²E) in general and O(E√V) when all capacities are 1, so it handles this size easily. Edmonds-Karp would also work and is easier to write if V is small. Two follow-ups worth answering early. If a task needed up to k workers, that capacity moves to the task-to-t edge. If each worker had a cost per task and I had to keep total cost as low as possible, this becomes min-cost max flow or the Hungarian algorithm, which are different tools.

🧠 Key takeaways

  • The residual edge lets the algorithm cancel earlier flow. That is what makes max flow correct instead of just greedy.
  • Edmonds-Karp uses BFS to find each augmenting path, giving O(V·E²). Dinic is the practical choice: O(V²E), or O(E√V) when all capacities are 1.
  • Max flow equals min cut. To find the cut, BFS from the source in the residual graph after the algorithm finishes.
  • Bipartite matching is max flow with every capacity set to 1. But Kuhn's 15 lines are usually the better answer.
  • Modelling is the real skill. Split nodes for node capacities. Add a super-source/sink for several endpoints. Use König to turn cover and independent-set questions into matchings.

Check your understanding

What does a residual (reverse) edge represent?

This is the core idea of max flow. Sending flow "backwards" undoes an earlier choice, which plain greedy cannot do. It is also what makes the min-cut proof work.

Why does Edmonds-Karp specifically use BFS for the augmenting path?

If it picks any path, Ford-Fulkerson can take O(maxflow) rounds, which is not polynomial in the input size. With BFS, the s–t distance never shrinks and is forced to grow. That puts a limit on the number of rounds.

After max flow terminates, how do you find the min cut?

Every S→T edge must be full (or its far end would be reachable). Every T→S edge must carry zero flow. So the cut's capacity equals the flow. Not every full edge is part of the cut.

A problem says each worker can take up to 3 tasks. Why can Kuhn's algorithm not be used?

The matchOf array holds one partner per node, so there is no way to allow more. The clue in a problem statement is "at most k" instead of "at most one".

This is why matching answers questions that never mention matching, like "fewest rows and columns to cover all marks" or "most picks with no conflicts". Both results fail on general graphs, where minimum vertex cover is NP-hard.
