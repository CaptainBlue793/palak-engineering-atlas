Case Study: Chrome’s Multi-Process Sandbox

A web browser downloads programs from strangers and runs them, thousands of times a day, on the machine where you do your banking. It parses formats nobody fully understands, in millions of lines of C++, and it will always contain memory bugs. Chrome's answer, from its first release in 2008, was to stop trying to make that code safe and to make it powerless instead: run it in a process that can't open a file, can't make a network connection and can't see any other process, and have it ask a small trusted process for everything. This case study looks at that design as an exercise in using the operating system's own boundaries, and at what happened in 2018 when a hardware flaw moved the boundary.

Why multiple processes

Until 2008 a browser was one process. Every tab, every plug-in and the user interface shared one address space, which had two consequences. A crash anywhere closed everything. And a memory-corruption bug in the code handling one page (Chapter 36) gave an attacker the whole browser: every other page, every stored password, and all the user's files, because the process ran with the user's full rights.

The split buys three things at once. Stability: a renderer that crashes takes down one page, and the browser shows a sad-tab message. Responsiveness: a page stuck in a loop is just a busy process, and the kernel's scheduler takes the CPU away from it. Security: the code most likely to be exploited can be run with almost no privileges, which is least privilege applied to a single program. The third is why the design spread to every other browser.

Site isolation

For its first ten years Chrome used roughly one renderer per tab. A page from one site and a frame it embedded from another, such as an advert, shared a process. That was thought to be safe, because the rule that keeps sites apart, the same-origin policy, was enforced by checks inside the renderer: script from one site simply wasn't given references to another site's data.

⚖️
Spectre moves the boundary

In January 2018 the Spectre attacks were published. They showed that on almost every modern processor, code can read any memory in its own address space, whatever checks the software makes, by steering the CPU's speculative execution and measuring its effect on the cache (Chapter 32). JavaScript was enough to do it. For browsers that was the end of an assumption. If an advert's script shares a process with your webmail, no check written in C++ keeps the mail from it. There is only one boundary the hardware still enforces: the one between address spaces. The Chrome team had been building a stricter process model for several years, mainly as a defence against compromised renderers, and Spectre turned it from an improvement into a necessity. Site Isolation was switched on for all desktop users in Chrome 67, in May 2018. Every site now gets its own renderer process, a frame from another site is drawn by a different process from the page around it, and the browser refuses to deliver another site's HTML or JSON into a renderer that didn't ask for it as a page. Google put the cost at 10 to 13% more memory in real use, and paid it. Firefox followed with its own version in 2021.

The change also closed an older hole. Before it, a renderer wasn't tied to a site, so a compromised renderer could tell the browser process "I am showing bank.example, send me its cookies" and be believed. With site isolation each renderer is locked to one site. The browser process knows which, and treats a request for anything else as proof of compromise and kills the renderer.

One page, three browsers

Three tabs are open: your mail, your bank and a news article. The article contains an advert in a frame from ads.evil, and the advert is hostile. Choose how the browser is built, then choose what the advert does.

Memory figures are a rough model: 180 MB for the browser process, 80 MB for a GPU process, 45 MB of overhead for each renderer, plus the pages themselves. Real pages carry many more cross-site frames than this one, which is how the real overhead of site isolation reaches 10 to 13%.

Things to notice. In the single process, every attack reaches everything: a crash closes all three tabs, and an exploit owns your files. With a sandboxed process per tab, the exploit can no longer touch the file system, which is the 2008 design doing its job. But the advert shares a process with the news page, Spectre reads whatever is in that process, and the advert can pull other sites' data into it by requesting, say, a bank URL as if it were an image. A full exploit can also lie to the browser about which site it is. With site isolation the advert is alone in a process locked to ads.evil, and all three attacks reach nothing but the advert itself. The stats show the price: one more process and more memory, for the same three tabs.

IPC between processes

A process that can't open files or sockets still has to load pages and read the file you chose to upload. It does so by asking. Chrome's processes are connected by message pipes (its IPC system is called Mojo), which on Linux are Unix domain sockets created before the sandbox closes, with shared memory for bulky data such as bitmaps (Chapter 9). The important trick is one from Chapter 10: an open file descriptor can be sent across a Unix socket.

This rearranges the security problem; it doesn't remove it. The renderer is assumed hostile, so every message it sends is untrusted input to the browser process, and every handler in the browser must check it: is this renderer allowed that origin, that file, that size? A mistake in one of those checks is a sandbox escape. That is why real attacks on Chrome come as chains. In March 2019 Google caught attackers using a memory bug in the renderer together with a second bug in the Windows 7 kernel. The first gave them code execution in a process that could do nothing, and they needed the second purely to get out.

The Linux sandbox: namespaces and seccomp

On Linux the renderer's powerlessness is built from two mechanisms you have already met, applied one after the other.

/* What the zygote does before any web content is loaded (simplified) */
unshare(CLONE_NEWUSER | CLONE_NEWPID | CLONE_NEWNET);   /* layer 1: no other processes, no network devices */
chroot(empty_dir);  chdir("/");                         /*          and a root directory with nothing in it */

/* ... and in each renderer, after fork() and before it touches a page: */
prctl(PR_SET_NO_NEW_PRIVS, 1);
prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &renderer_policy);    /* layer 2: most system calls now fail */
Layer 1: namespaces and an empty rootLayer 2: a seccomp filter
FromChapter 34Chapter 36
Takes awayThings to name: there are no files, no other PIDs and no network interfaces in the renderer's viewThings to call: open, socket, connect, execve, ptrace and many more are refused
Still allowedAny system callMemory management, futex, reading and writing descriptors it already holds, sending messages on its sockets
Weak atProtecting the kernel: every system call is still reachable, and so is every kernel bug behind oneDecisions about paths: a filter sees a pointer to a file name, not the name

Each covers the other's weakness. The filter can't judge which file a path refers to, so the file system is removed altogether and files arrive only as descriptors. Namespaces can't stop a process attacking the kernel through an obscure system call, so the filter leaves only a few dozen reachable. An attacker who escapes through the kernel has to find a bug in that small set.

Other systems give the same result with different parts: restricted tokens and job objects on Windows, sandbox profiles on macOS, and on Android a separate user ID for each renderer. The architecture, a broker with rights and workers with none, is the portable part.

Memory cost trade-offs

Isolation is bought with memory. Each renderer has its own JavaScript heap, its own copy of the engine's data structures and its own allocator arenas, tens of megabytes before a page is loaded. Program code is shared between processes through the page cache, and the zygote lets renderers share whatever was initialised before the fork, but a hundred tabs from a hundred sites are still a hundred processes.

The Android row is the trade-off stated openly: on a phone with little memory, more processes mean other apps are killed sooner, so isolation is spent where the data is most valuable. On desktop, Chrome also caps the number of renderers according to installed RAM. Past the cap, tabs from the same site share a process, but different sites are never merged. And when you look at the numbers yourself, remember Chapter 43: adding up the RSS of every Chrome process counts the shared pages many times over. The browser's own task manager reports each process's private memory for that reason.

⚠️
Common mistakes
  • Thinking the sandbox makes renderer bugs harmless. A compromised renderer still holds everything in its own process: with site isolation, one site's data.
  • Trusting messages from the sandboxed process. The broker must validate every one. Most sandbox escapes are missing checks in the trusted side.
  • Relying on one layer. Namespaces leave the kernel exposed, and a system-call filter can't reason about file names. Use both.
  • Running with --no-sandbox to make something work. Common in containers and test scripts, and it turns every renderer bug into full access as that user.
  • Believing in-process checks survive Spectre. Secrets and untrusted code must not share an address space.
  • Summing RSS to measure a multi-process program. Shared pages are counted once per process.

Interview drill

Explain it simply: Why does Chrome run so many processes?

How a strong answer sounds
For stability, responsiveness and above all security. A browser constantly parses and executes untrusted content with a huge C++ code base, so memory-safety bugs are inevitable. Chrome separates the code that handles web content, the renderer, from the part that holds the user's privileges. A browser process owns the UI, cookies, files and network policy; each renderer runs in a sandbox with almost no privileges and talks to the browser over IPC. If a renderer crashes, one tab or frame is lost. If it hangs, the OS still schedules the others. If it is exploited, the attacker is inside a process that can't open files, create sockets or see other processes. Since 2018 renderers are also split by site, so that one site's data never shares an address space with another site's code, which is the defence against Spectre-style attacks. The cost is memory, because every process has its own heap and runtime.

Deeper: An attacker gets arbitrary code execution inside a renderer on Linux. What stands between them and your files or your bank session?

How a strong answer sounds
Several layers. The renderer runs in its own user, PID and network namespaces with an empty root directory, so there are no file paths to open, no other processes to signal or trace, and no network interfaces. On top of that a seccomp-BPF filter refuses most system calls, including open, socket and execve, which also shrinks the kernel attack surface to a small set of calls. So the attacker can compute and can use the descriptors the process already holds, mainly its IPC channel to the browser. Over that channel they can ask for things, but with site isolation the browser has locked that renderer to one site and will refuse, and kill it, if it asks for another site's cookies or data. My bank session lives in a different renderer process and in the browser process, neither of which shares memory with the compromised one. To go further the attacker needs a second vulnerability: a logic or memory bug in a browser-side IPC handler, a bug in the GPU process, or a kernel bug reachable through the few permitted system calls. That is why real attacks are chains of two or more exploits.

🧠 Key takeaways

  • Chrome puts the code that handles untrusted content in renderer processes with no privileges, and keeps privileges in one browser process.
  • Separate processes give crash containment, scheduling by the kernel, and a hardware-enforced security boundary.
  • Spectre showed that code can read its whole address space, so since 2018 each site gets its own process, locked to that site.
  • A sandboxed process works by asking a broker over IPC and receiving descriptors. Every such message is untrusted input.
  • The Linux sandbox layers namespaces and an empty root (nothing to name) with a seccomp filter (little to call).
  • The price is memory, about 10–13% for site isolation, and escaping still needs a second bug.

Check your understanding

Why is the renderer, and not the browser process, the one that is sandboxed?

Least privilege: the code most exposed to attack gets the fewest rights, and the rights live elsewhere.

What did Spectre change for browsers?

Checks inside a process no longer protect secrets in that process. The address-space boundary still does.

A sandboxed renderer can't call open. How does it read a file the user chose to upload?

The broker decides which file; the renderer only receives a handle to that one file.

Why does the Linux sandbox use both namespaces and a seccomp filter?

Remove what can be named, then restrict what can be called. Each covers the other's gap.

With site isolation, a compromised renderer for ads.evil asks the browser for bank.example's cookies. What happens?

The enforcement is in the browser process, which knows which site each renderer belongs to.
