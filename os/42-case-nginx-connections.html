Case Study: How nginx Handles 10,000 Connections

nginx was written in the early 2000s to answer one question: how does a single machine hold ten thousand client connections at once? Its answer is now the standard shape of a network server. A few processes, one per core. Each runs one thread in one loop, never blocks, and treats every connection as a small record of state instead of a thread with a stack. Static files leave through the kernel without ever being copied into the server. Almost every design decision in it is a chapter of this course applied on purpose: fork, epoll, the event loop, the page cache, privilege dropping. This case study walks through a running nginx and shows which mechanism is doing what.

The split is least privilege at work (Chapter 36). Binding a port below 1024 needs privilege, so the master does that, and only that, as root. The workers are created by fork, so they inherit the listening sockets as open descriptors (Chapter 10), and then drop to an ordinary user before reading a byte from the network. A bug in request parsing is a bug in an unprivileged process.

The master also makes configuration changes painless. On nginx -s reload it reads the new configuration, forks a new set of workers, and tells the old ones to stop accepting and exit once their current requests finish. No connection is dropped, and the listening sockets never close.

One event loop per worker

Each worker is the loop of Chapter 29: wait in epoll_wait, handle whatever is ready, repeat. A connection is not a thread. It is a small structure holding the socket, a buffer and a position in a state machine, and nginx's own figure is about 2.5 MB of memory for ten thousand idle keep-alive connections.

# /etc/nginx/nginx.conf: the lines that set this up
worker_processes  auto;                 # one worker per core
events {
    worker_connections  4096;           # per worker
}
http {
    sendfile        on;                 # files go from the page cache straight to the socket
    tcp_nopush      on;                 # send the headers and the start of the file in one packet
    keepalive_timeout  65;
}

Because a worker has one thread, it has no locks round its own data, and one worker per core means the kernel has no reason to move it: its caches stay warm (Chapter 32). The price is the rule from Chapter 29. A worker must never block. Disk reads are the awkward case, since a file that isn't in the page cache blocks whoever reads it, so nginx can hand those reads to a small thread pool and collect the result as another event.

Who accepts? The thundering herd

All four workers inherited the same listening socket, and each has it in its epoll set. When a connection arrives, the socket becomes readable for all of them. The naive result is that every worker wakes, they all call accept, one gets the connection, and the rest get EAGAIN and go back to sleep, having achieved nothing but context switches. This is the thundering herd. nginx has used three remedies over the years:

  • An accept mutex. Workers take turns holding a lock, and only the holder has the listening socket in its epoll set. One worker wakes. It was nginx's default for many years.
  • EPOLLEXCLUSIVE (Linux 4.5, 2016). A flag asking the kernel to wake just one of the waiters on a shared socket. No lock is needed in user space; modern nginx uses it and has the mutex off by default.
  • SO_REUSEPORT (listen 80 reuseport;). Each worker opens its own listening socket on the same port, and the kernel shares incoming connections among the sockets by hashing the client's address. No shared socket, no herd, and no contention on one accept queue.

Deliver some connections

Four workers, one port. Send connections one at a time to see who wakes, then send a thousand and compare how the work is shared out.

Four workers and a listening portInteractive
A model of a lightly loaded server: each connection keeps a worker busy for a fraction of the gap before the next one. With EPOLLEXCLUSIVE the kernel goes through the workers in a fixed order and wakes the first that is idle. With SO_REUSEPORT it picks a socket by hashing the client's address and port. Amber means a worker was woken for nothing.

Things to notice. With no protection, a thousand connections cause four thousand wake-ups, three quarters of them wasted. The other three modes wake one worker each time, but they share the work very differently. The mutex passes round, so the split is even. EPOLLEXCLUSIVE wakes the first idle worker in a fixed order, which under light load is nearly always the same one, so one worker ends up doing most of the work while the others idle. SO_REUSEPORT spreads connections evenly by hash, whether or not the chosen worker is free.

⚖️
"Why does one NGINX worker take all the load?"

Engineers at Cloudflare noticed exactly what the panel shows: on their servers one nginx worker was far busier than the rest, and they published an investigation under that title in 2017. The cause was the order in which the kernel wakes waiters on a shared socket. It isn't round-robin. The kernel's choice favours the same worker whenever that worker is free, so a worker that has just finished a request is given the next one too, and the busiest worker stays busiest. Their first instinct was that this must be bad, and they tested SO_REUSEPORT, which gave a beautifully even spread. Then they measured latency, and it was worse, especially in the tail. With one socket per worker, a connection is assigned by hash to a particular worker's queue, and if that worker happens to be busy with a slow request the connection waits, even though three other workers are idle. With a shared socket, any idle worker can take it. The uneven load had been keeping one worker's caches hot and costing nothing. The conclusion, that balanced isn't the same as fast, is the kind you only reach by measuring: the three accept strategies are still all in nginx because each wins on some workload.

sendfile: the file never visits user space

Serving a static file the obvious way moves every byte across the user–kernel boundary twice:

/* The obvious way: two system calls and two copies per chunk */
while ((n = read(file_fd, buf, sizeof buf)) > 0)     /* page cache -> buf  (copy 1) */
    write(sock_fd, buf, n);                          /* buf -> socket buffer  (copy 2) */

/* sendfile: one system call, and the data stays in the kernel */
off_t off = 0;
sendfile(sock_fd, file_fd, &off, file_size);         /* page cache -> socket, by reference */

LimitsNoneThe data can't be changed on the way: no compression on the fly, and encryption only if the kernel does the TLS

This is zero-copy I/O, and it rests on Chapter 31: the file's pages are already in memory in the page cache, and the kernel's network stack can transmit straight from them. A worker serving a thousand large downloads is doing almost no work per byte. It is telling the kernel which file goes to which socket.

Common mistakes
  • Setting far more workers than cores. Workers don't block, so extra ones only add context switches and cold caches.
  • Blocking inside a worker. A slow disk, a synchronous lookup or a heavy script in the worker stalls every connection it holds.
  • Forgetting the descriptor limit. Each connection is a descriptor, and a proxied one is two. Raise the limit to match worker_connections.
  • Assuming even load across workers is the goal. Measure latency. A shared socket with uneven load can beat a perfectly balanced one.
  • Expecting sendfile to apply to everything. Compressed or transformed responses must pass through user space.
  • Running the workers as root. Only the master needs it, and only to bind the ports.

Interview drill

Explain it simply: How does nginx handle thousands of concurrent connections with only a few processes?

How a strong answer sounds
It uses an event-driven design instead of a thread per connection. A master process, running as root, binds the listening ports and forks one worker per CPU core; the workers inherit the listening sockets and drop privileges. Each worker is single-threaded and runs an event loop on epoll. All its sockets are non-blocking and registered with epoll; the worker sleeps in epoll_wait, wakes when some sockets are ready, does a small amount of work on each, such as reading part of a request or writing part of a response, and goes back to waiting. A connection is just a small state structure, a few kilobytes, so tens of thousands cost little memory and no context switches, and idle or slow clients cost almost nothing. Static files are sent with sendfile, directly from the page cache to the socket. The constraint is that a worker must never block, so blocking work is pushed to thread pools or to upstream application servers.

Deeper: What is the thundering herd problem in this design, and how is it avoided?

How a strong answer sounds
All workers share one listening socket, inherited through fork, and each waits on it with epoll. When a connection arrives the socket becomes readable for all of them, so every worker is woken, they all call accept, one succeeds and the rest get EAGAIN: wasted wake-ups and context switches on every connection. There are three fixes. An accept mutex in user space, so that only the worker holding it listens for new connections at any moment. The EPOLLEXCLUSIVE flag, which asks the kernel to wake only one waiter per event; it prefers the same worker whenever that worker is idle, so load concentrates on a few workers under light traffic. Or SO_REUSEPORT, where each worker has its own listening socket on the same port and the kernel distributes connections by hashing the client address; that removes contention and balances evenly, but a connection is bound to one worker's queue and waits if that worker is busy, which can hurt tail latency. Which is best depends on the workload, so I'd measure latency, not just the distribution.

🧠 Key takeaways

  • A root master binds ports and forks workers; unprivileged workers, one per core, do all the serving.
  • Each worker is one thread running an epoll event loop over non-blocking sockets. A connection is a few kilobytes of state.
  • Workers share the listening socket through fork, which invites a thundering herd on accept.
  • An accept mutex, EPOLLEXCLUSIVE or SO_REUSEPORT each wake one worker; they differ in how evenly, and how quickly, connections are picked up.
  • sendfile sends file data from the page cache to the socket inside the kernel, with no copies through user space.
  • The model excels at many slow connections and fails if a worker blocks, which is why it is paired with separate application servers.

Check your understanding

Why does the nginx master process run as root while the workers don't?

The master does the one privileged job and forks; the workers inherit the sockets and drop to an ordinary user. Least privilege.

How do the worker processes come to share one listening socket?

fork copies the descriptor table, so every worker has a descriptor for the same socket.

Four workers wait on a shared listening socket with no protection. One connection arrives. What happens?

The thundering herd: every waiter is told the socket is readable, though there is work for only one.

What does sendfile avoid, compared with a loop of read and write?

The data goes from the page cache to the socket inside the kernel. The application never sees the bytes.

A module run inside an nginx worker makes a blocking database call that takes 200 ms. What is the effect?

A worker has one thread. While it is blocked it isn't in epoll_wait, so none of its other connections make progress.
