Booting, Kernel Modules & Drivers

Every chapter so far has assumed a running kernel. This one asks how it gets there, and how it comes to know about the particular disks, network cards and keyboards attached to this particular machine. The answer to the first is a relay race: firmware, boot loader, kernel, a temporary file system in memory, and finally the first process, each stage doing just enough to load the next. The answer to the second is drivers, code that plugs into the kernel and runs with all of its privileges, usually loaded on demand as modules. That privilege is why one faulty driver can take down a machine, or eight million of them, and why Linux now has a safer way to extend the kernel as well.

From the power button to a login prompt

A CPU that has just been powered on knows nothing: no file systems, no drivers, not even how much memory it has. It starts executing at a fixed address in a chip on the motherboard. Each stage of the boot knows a little more than the last and uses it to find, load and start the next. That is the "bootstrap" the word booting comes from.

$ cat /proc/cmdline                         # what the boot loader told the kernel
BOOT_IMAGE=/vmlinuz-6.8.0-45-generic root=UUID=3f1c2a9e-7b1d-4c55-9a0e-5d2f8c1e6b74 ro quiet
$ systemd-analyze                           # where the time went
Startup finished in 3.1s (firmware) + 1.2s (loader) + 1.4s (kernel) + 4.9s (userspace) = 10.6s
$ systemd-analyze blame | head -3           # the slowest units

Boot a machine, and break it

Step through a boot. Then choose a fault and boot again: each one stops the machine at a different stage, with the message you would really see on the console.

Seven stages and five ways to failInteractive
Console output is shortened but uses the real wording. Times are typical for a server with an SSD. A fault takes effect at the stage that first depends on the broken thing, which is often several stages after the mistake was made.

Things to notice. Where a boot stops tells you what to look at. A grub rescue> prompt means the kernel was never loaded. A kernel panic about unknown-block(0,0) means the kernel is running but has no driver for the root disk. An (initramfs) prompt means the drivers loaded and the disk they were told to find isn't there. "Emergency mode" means the kernel and the root file system are fine and systemd couldn't finish mounting things. And a failed service doesn't stop the boot at all: the machine comes up, without the one thing you wanted it for.

Kernel modules

A kernel containing a driver for every device ever made would be enormous. Most drivers, file systems and network protocols are built as modules: object files (.ko) that can be linked into the running kernel when needed and removed when not. The device manager does this automatically, matching the identifiers each device reports against a table of which module handles what.

$ lsmod | head -4                         # what is loaded now
Module                  Size  Used by
nvme                   61440  3
nvme_core             212992  5 nvme
ext4                 1118208  2
$ modinfo nvme | grep -E '^(description|license|alias)' | head -3
description:    NVM Express device driver
license:        GPL
alias:          pci:v*d*sv*sd*bc01sc08i02*      # "any PCI device of class NVMe is mine"
# modprobe wireguard                        # load a module and whatever it depends on
/* The smallest possible module. */
#include <linux/module.h>
#include <linux/init.h>

static int __init hello_init(void)
{
    pr_info("hello: loaded\n");             /* goes to the kernel log: read it with dmesg */
    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("hello: unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");

Once loaded, a module is part of the kernel in every sense. It runs in kernel mode, can read and write any memory, and nothing stands between its bugs and the machine. A stray pointer in a module is not a segmentation fault in one process. It is a corrupted kernel, and usually a panic.

Device drivers

A driver is the code that knows how to operate one kind of device and presents it to the rest of the kernel through a standard interface. Linux sorts devices into three families.

$ ls -l /dev/null /dev/nvme0n1
crw-rw-rw- 1 root root   1,  3 Oct  6 09:12 /dev/null        # c = character; major 1, minor 3
brw-rw---- 1 root disk 259,  0 Oct  6 09:12 /dev/nvme0n1     # b = block;     major 259, minor 0

The two numbers are how the kernel routes a call. The major number selects the driver, and the minor number tells that driver which of its devices is meant. This is the machinery behind "everything is a file" in Chapter 10: opening /dev/nvme0n1 gives you a descriptor whose operations are the NVMe driver's functions.

How a driver talks to hardware: interrupts and DMA

A device exposes a few registers, mapped at fixed addresses in memory, that the driver reads and writes to command it. Two mechanisms keep the CPU from wasting its time on slow hardware. Interrupts let the device announce that it has finished, so nothing has to poll it. Direct memory access (DMA) lets the device copy data to and from RAM by itself, so the CPU doesn't move it a word at a time.

$ head -4 /proc/interrupts
            CPU0       CPU1       CPU2       CPU3
  24:    1840221          0          0          0  PCI-MSI  nvme0q0
  25:     611204          0          0          0  PCI-MSI  nvme0q1     # one queue, and one interrupt, per core
  26:          0     598877          0          0  PCI-MSI  nvme0q2
💥
19 July 2024: one driver, 8.5 million machines

CrowdStrike's Falcon is security software that runs inside the Windows kernel as a driver, loaded early in boot so that nothing can start before it. On 19 July 2024 the company pushed a routine update to one of the data files the driver reads. The file's contents led the driver to read memory outside a buffer. In an ordinary program that is a crash of that program. In a kernel driver it is a crash of Windows: a blue screen. And because the driver loads at boot and read the same file again, every affected machine crashed again on restart, and again, indefinitely. Microsoft estimated that 8.5 million machines were caught in the loop. Airlines grounded flights, hospitals postponed operations, and banks and broadcasters went dark. No remote fix was possible, since a machine that can't boot can't download one: someone had to start each computer in a recovery mode and delete the file by hand. The update was withdrawn within 78 minutes; the recovery took days. Nothing about this was peculiar to Windows or to that vendor. It is the property this chapter keeps returning to: code in the kernel has no supervisor. The lasting consequence was renewed pressure, from Microsoft among others, to move such software out of the kernel or into a restricted environment where a mistake can be contained.

eBPF: extending the kernel safely

Linux's restricted environment is eBPF. It lets you load a small program into the running kernel and attach it to an event: a system call, a function inside the kernel, a network packet arriving. Before the kernel accepts it, a verifier examines every path through the program and proves that it terminates, never reads memory it shouldn't, and only calls a fixed list of approved helper functions. A program that passes is compiled to native code and runs at nearly full speed; one that doesn't is refused.

# Print every file any process opens, live, on a production machine, without restarting anything:
# bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
nginx /var/www/index.html
postgres base/16384/2619

eBPF can't replace a disk driver, which genuinely needs the freedom a module has. What it has replaced is a great deal of code that only needed to observe the kernel or make small decisions inside it, and used to need a module, with a module's risks, to do so.

⚠️
Common mistakes
  • Forgetting to rebuild the initramfs. After changing storage drivers, encryption or the root device, the copy in the initramfs is stale and the next boot can't find its disk.
  • Naming disks by device path in /etc/fstab. /dev/sdb1 can become /dev/sdc1 when a disk is added. Use UUIDs, and nofail for disks the machine can live without.
  • Treating a module like a program. There is no memory protection and no clean way to kill it. Test in a virtual machine.
  • Reading boot failures from the last line only. The message that matters is the first error, often many lines above the panic.
  • Assuming a slow boot is the kernel's fault. It is usually firmware, or one service waiting on a timeout. systemd-analyze blame shows which.
  • Loading modules from untrusted sources. A module is the most privileged code on the machine.

Interview drill

Explain it simply: What happens between pressing the power button and seeing a login prompt on Linux?

How a strong answer sounds
The CPU starts executing firmware from a chip on the board. UEFI initialises the hardware, finds a boot loader on a special partition, and runs it. The boot loader, usually GRUB, loads the compressed kernel image and an initramfs into memory and passes the kernel a command line that includes the root device. The kernel decompresses itself, sets up memory management, scheduling and interrupts, and initialises built-in drivers. It then unpacks the initramfs, a small root file system in RAM whose scripts load the modules needed to reach the real root, for example NVMe, RAID or disk encryption, and locate it. The kernel mounts the real root and executes init from it as PID 1, which on most systems is systemd. systemd mounts the remaining file systems, starts udev to load drivers for detected hardware, and starts services according to their dependencies until it reaches the target state, at which point you get a login prompt.

Deeper: A server fails to boot after a kernel upgrade, stopping at "VFS: Unable to mount root fs on unknown-block(0,0)". What does that tell you?

How a strong answer sounds
It tells me how far the boot got and what is missing. The firmware and boot loader worked, because the kernel is running and printing. The kernel reached the point of mounting the root file system and failed, and "unknown-block(0,0)" means it has no block device at all for it: it never found a driver for the disk controller. Almost always that means the initramfs is absent or wrong. After a kernel upgrade, the likely causes are that the initramfs for the new version wasn't generated, wasn't copied to the boot partition, or the boot loader entry doesn't reference it, so the storage and file-system modules, which aren't built into the kernel, were never loaded. To recover I'd boot the previous kernel from the boot loader's menu, which is why old kernels are kept, then regenerate the initramfs for the new kernel, check that the boot entry lists it, and reboot. If it had instead stopped at an initramfs shell saying the UUID doesn't exist, the drivers would be fine and the root device named on the command line would be the thing to check.

🧠 Key takeaways

  • Booting is a relay: firmware, boot loader, kernel, initramfs, real root, PID 1. Each loads the next.
  • The initramfs carries the drivers needed to reach the disk that holds all the other drivers.
  • Where a boot stops identifies the failed stage: the loader, the kernel's root mount, the initramfs, or systemd.
  • Modules are kernel code loaded on demand. They run with full privilege, so their bugs are the kernel's bugs.
  • Drivers present devices as character, block or network devices, and use interrupts and DMA to avoid polling and copying.
  • eBPF runs verified programs inside the kernel: far safer than a module, for observing and filtering.

Check your understanding

What is the initramfs for?

The disk's driver lives on the disk. The initramfs, loaded by the boot loader, carries the few modules needed to get there.

A machine stops at a grub rescue> prompt. Which stage failed?

GRUB is still in control, so no kernel has been loaded yet. The fault is with the loader's own files or the partition they are on.

Why is a bug in a kernel module more serious than the same bug in an ordinary program?

A bad pointer in a process is caught by the MMU and kills that process. In the kernel there is nothing above it to catch the error.

What does DMA let a device do?

The driver tells the device where in memory to put the data; the device does the copy and then raises an interrupt.

What makes loading an eBPF program safer than loading a kernel module?

They run inside the kernel at native speed, but only after static checks that rule out the bugs which make modules dangerous.
