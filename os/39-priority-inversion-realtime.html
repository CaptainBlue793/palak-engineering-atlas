Priority Inversion & Real-Time Scheduling

Some software has deadlines that are part of its correctness. An engine controller, a pacemaker, an audio driver, a spacecraft's attitude control: a right answer that arrives late is a wrong answer. Such systems are built on a simple promise from the scheduler, that the most urgent runnable task always runs. Locks can quietly break that promise. In 1997 they did so on the surface of Mars, where a spacecraft kept rebooting itself because its most important task was being kept off the CPU by one of its least important. The cause has a name, priority inversion, a standard fix, and a place in every interview about real-time systems. This chapter covers both, and how Linux schedules tasks that can't be late.

The promise, and how a lock breaks it

In a fixed-priority preemptive scheduler, every task has a priority and the rule is absolute: the highest-priority task that is ready runs, at once, preempting whatever was running. Designers rely on that to reason about deadlines. The urgent task can be delayed only by things more urgent than itself.

Now add a mutex shared between a high-priority task H and a low-priority task L. If L holds the mutex when H wants it, H has to wait for L to finish its critical section. That is unavoidable and acceptable: it is short, and its length is known. It is called bounded priority inversion.

The trouble comes from a third task, M, of medium priority, which doesn't use the mutex at all. While H waits for L, M becomes ready. M outranks L, so M preempts L, and runs for as long as it likes. L can't finish its critical section, so it can't release the mutex, so H can't run. The highest-priority task in the system is waiting for a medium-priority task it has nothing to do with, for an unlimited time. That is unbounded priority inversion.

Watch it happen, then fix it

One CPU, three tasks. L and H share a mutex; M just computes. H must finish within 12 ms of arriving. Start with no protocol and lengthen M's work. Then switch on each fix.

L arrives at 0 and needs the mutex for 6 ms of its 10 ms of work. H arrives at 4 ms and needs it for 2 ms of its 4 ms. M arrives at 5 ms and never touches the mutex. The scheduler always runs the ready task with the highest current priority.

Things to notice. With a plain mutex, H's response time is M's running time plus 8 ms: the more work the medium task has, the later the high-priority one finishes, and it misses its deadline as soon as M runs longer than 4 ms. With priority inheritance, L is boosted to H's priority the moment H blocks, so M can't get in; H finishes after 8 ms whatever M does. The priority ceiling gives the same answer by a different route: L is boosted as soon as it takes the mutex, so H never even has to block on it. With M's work set to zero the plain mutex is fine, which is why the bug survives testing.

Mars Pathfinder, July 1997

A few days after landing, the Pathfinder spacecraft began resetting itself, losing a day's science each time. Its computer ran the VxWorks real-time operating system with fixed-priority preemptive scheduling. A high-priority task managed the spacecraft's internal "information bus", a shared memory area, and ran frequently. A low-priority task collecting meteorological data occasionally published results to the bus, taking the mutex that protected it. Between them in priority sat a long-running communications task. Now and then, the bus task woke while the weather task held the mutex and blocked, as designed. Before the weather task could finish, the communications task became ready and preempted it. The bus task stayed blocked, and blocked, until a watchdog timer noticed that the most important task on the spacecraft had not run for too long, declared the system broken, and rebooted it. Engineers at the Jet Propulsion Laboratory reproduced the fault overnight on an identical computer on Earth, with tracing switched on. The mutex had been created with priority inheritance switched off. VxWorks kept that choice in a global variable, and the flight software still included a small command interpreter for debugging, so the fix was to upload a short script that changed one flag from false to true, 190 million kilometres away. The resets stopped. Two details are worth remembering: the fault had been seen once or twice in testing and put down as a glitch, and it was fixable only because the debugging tools had been left on board.

Neither protocol is free, and neither removes the need for short critical sections. They guarantee that a high-priority task waits only for the code that actually holds the resource it needs. The same shape of problem turns up without real-time priorities too: a thread holding a lock is preempted, or throttled by its container's CPU limit (Chapter 38), and everyone who wants that lock waits for a thread that isn't allowed to run.

Real-time scheduling on Linux

The scheduler of Chapter 8 aims at fairness: every task gets a share, and priorities (nice values) only tilt the shares. That is the wrong goal for a task with a deadline. Linux therefore has several scheduling classes, consulted in strict order. A runnable task in a higher class always beats every task in a lower one.

PolicyRuleTypical use
SCHED_DEADLINEEach task declares "I need runtime every period, by this deadline". The earliest deadline runs first. The kernel refuses tasks whose demands don't fitPeriodic control loops, media pipelines
SCHED_FIFOFixed priority 1 to 99. Runs until it blocks, yields, or a higher priority arrives. No time slicesClassic real-time tasks
SCHED_RRAs FIFO, but tasks of equal priority take turns on a time sliceSeveral equally urgent tasks
SCHED_OTHER (default)The fair scheduler of Chapter 8, weighted by nice valueEverything else
SCHED_IDLERuns only when nothing else wants the CPUBackground indexing and the like
 
# chrt -f 50 ./motor-control                  # start under SCHED_FIFO at priority 50
$ chrt -p 4120
pid 4120's current scheduling policy: SCHED_FIFO
pid 4120's current scheduling priority: 50
$ cat /proc/sys/kernel/sched_rt_runtime_us
950000                                         # real-time tasks may use at most 0.95 s of every second
struct sched_param sp = { .sched_priority = 50 };
sched_setscheduler(0, SCHED_FIFO, &sp);           /* needs privilege: CAP_SYS_NICE */
mlockall(MCL_CURRENT | MCL_FUTURE);              /* no page faults: a fault is an unbounded delay */

A SCHED_FIFO task that spins in a loop takes its core completely: nothing in the ordinary class will ever run there, including your shell. The 95% limit in the listing above is a safety net for exactly that mistake. Real-time priority is a promise the program makes to block regularly, not a way to make ordinary code faster.

Hard, soft, and PREEMPT_RT

Real-time doesn't mean fast. It means predictable: the worst case is known and bounded.

  • Hard real-time: a missed deadline is a failure of the system. Anti-lock brakes, flight control, industrial robots.
  • Soft real-time: a missed deadline degrades quality. A dropped video frame, a click in audio.

A normal Linux kernel is good at soft real-time and not suitable for hard. A real-time task can be the highest priority on the machine and still wait while the kernel itself runs with preemption disabled: inside a spinlock-protected section, or an interrupt handler. Those sections are usually microseconds long, and occasionally much longer. The PREEMPT_RT work makes the kernel itself preemptible nearly everywhere. Most kernel spinlocks become sleeping locks with priority inheritance, and interrupt handlers run as ordinary threads with priorities, so a high-priority task can preempt them. After about twenty years as a separate patch set, it was merged into the mainline kernel in version 6.12, in 2024. With it, worst-case scheduling delays drop from milliseconds to tens of microseconds, at some cost in throughput.

⚠️
Common mistakes
  • Sharing a plain mutex between tasks of very different priority. Use a priority-inheritance mutex, or avoid sharing.
  • Thinking real-time means fast. It means bounded worst case. Real-time kernels usually have lower throughput.
  • Giving a busy loop a real-time priority. It starves everything below it, possibly including the tools you need to stop it.
  • Forgetting memory. A page fault or a malloc that needs the kernel is an unbounded delay. Lock memory and allocate up front.
  • Dismissing a rare reset or stall in testing as a glitch. Timing bugs are rare by nature. Pathfinder's had been seen before launch.
  • Assuming inheritance makes long critical sections harmless. The high-priority task still waits for the whole of the section it needs.

Interview drill

Explain it simply: What is priority inversion, and how is it solved?

How a strong answer sounds
Priority inversion is when a high-priority task is made to wait by a lower-priority one. The damaging form needs three tasks. A low-priority task takes a lock. A high-priority task then needs the same lock and blocks. Before the low task can release it, a medium-priority task that doesn't use the lock at all becomes ready and preempts the low one, because it outranks it. Now the high-priority task is effectively waiting for the medium one, for as long as that chooses to run. That is unbounded inversion, and it is what reset Mars Pathfinder. The standard solution is priority inheritance: while a task holds a lock that a higher-priority task is blocked on, it temporarily runs at that higher priority, so medium-priority work can't preempt it, and it drops back when it unlocks. An alternative is the priority-ceiling protocol, which raises a task to the lock's preassigned ceiling as soon as it locks. On POSIX systems both are mutex attributes.

Deeper: What is the difference between SCHED_FIFO and the default Linux scheduler, and what do you have to be careful about when using it?

How a strong answer sounds
The default policy shares CPU time fairly among tasks, with nice values as weights; no task is starved, and none is guaranteed to run at a particular moment. SCHED_FIFO is a fixed-priority real-time class that sits above it: a FIFO task with priority 1 to 99 preempts any normal task immediately, and keeps the CPU until it blocks, yields, or a higher-priority real-time task becomes runnable. There is no time slice. That gives low, predictable latency for a task that must react to an event, such as an audio or control loop. The care needed follows from the power. A FIFO task that doesn't block will monopolise its core, so it must be written to sleep between events; Linux's real-time throttling, 95% by default, is a backstop. Any lock it shares with lower-priority code needs priority inheritance, or it suffers inversion. It should lock its memory and avoid allocation in the critical path, since a page fault is an unbounded delay. And for hard guarantees the kernel itself must be preemptible, which is what PREEMPT_RT provides; latency should be measured with something like cyclictest, looking at the maximum.

🧠 Key takeaways

  • Priority inversion: a high-priority task waits on a lock held by a low-priority task, which is itself kept off the CPU by medium-priority work.
  • Without a protocol the wait is unbounded. It reset Mars Pathfinder until priority inheritance was switched on.
  • Priority inheritance boosts the lock holder to its highest waiter's priority; the priority ceiling boosts on every lock.
  • Linux's real-time classes, SCHED_DEADLINE, SCHED_FIFO and SCHED_RR, always run before normal tasks.
  • Real-time means a bounded worst case, not speed. Lock memory, keep critical sections short, and block regularly.
  • PREEMPT_RT makes the kernel preemptible so that worst-case delays are tens of microseconds.

Check your understanding

In the classic priority-inversion scenario, which task is actually keeping the high-priority task from running?

The low task would release the lock promptly if it could run. The medium task, which outranks it, is what stretches the wait without limit.

How does priority inheritance fix the problem?

With the boost, medium-priority work can't preempt the holder, so the critical section finishes and the lock is released quickly.

What made the Mars Pathfinder computer reset?

The bus-management task was blocked on a mutex held by a low-priority task that a medium-priority task kept preempting. The watchdog did its job.

A SCHED_FIFO task with priority 50 enters an infinite loop that never blocks. What happens on its core?

FIFO tasks have no time slice and outrank every normal task. Only the 5% reserved by default keeps the machine reachable.

What does "hard real-time" require of a system?

Real-time is about the worst case being known and bounded, not about the average being small.
