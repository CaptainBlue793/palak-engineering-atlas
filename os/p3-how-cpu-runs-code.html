How a CPU Runs Your Code

An operating system is, in the end, a program that decides what the CPU runs next. To understand how it switches between programs, takes interrupts and enters the kernel, you need a working picture of the CPU itself: a handful of registers, a program counter that walks through instructions, and a stack pointer that makes function calls possible. This chapter builds that picture from a two-line C function down to the bytes the CPU fetches, and ends with the pipeline tricks that make modern CPUs fast and occasionally insecure.

Registers and the program counter

A CPU core works on a small set of registers: named storage slots inside the core, each 64 bits wide on x86-64, readable in a fraction of a nanosecond. Instructions mostly move data between memory and registers and do arithmetic on registers. Two registers are special. The program counter (called rip, the instruction pointer, on x86-64) holds the address of the next instruction. The stack pointer (rsp) holds the address of the top of the current thread's stack.

The 32-bit names (eax, edi, ecx) are the low halves of the same registers; an int in C is 32 bits, so compiled code uses them a lot.

The stack pointer and function calls

Each thread has its own stack and therefore its own chain of return addresses: that chain is the thread's position in the program. When the kernel switches threads it saves rip, rsp and the other registers into the thread's kernel record and loads another thread's saved set. To the thread, nothing happened.

Pipelines, and why branches cost

Real cores don't finish one instruction before starting the next. They are pipelined: while one instruction executes, the next is being decoded and the one after is being fetched, across 14 to 20 stages on recent x86 cores, and several instructions can be in each stage at once. That works only if the CPU knows which instruction comes next. At a conditional branch (jge above) it doesn't, so it predicts, starts executing down the predicted path speculatively, and if it guessed wrong it throws that work away. A misprediction costs roughly 15–20 cycles.

EventApproximate costAt 3 GHz
Simple ALU instruction (add, compare)1 cycle, several per cycle in parallel< 0.3 ns

A loop over an array with an unpredictable if (x >= 128) inside can run several times slower on random data than on sorted data, purely because the predictor guesses right on sorted input. Branch-free code (conditional moves, arithmetic masks) is a standard fix in hot loops.

👻
Spectre and Meltdown: when speculation leaked secrets

In January 2018 researchers disclosed Meltdown and Spectre. Speculative execution is supposed to be invisible: wrong-path work is discarded. But it leaves traces in the caches, and timing a later memory access reveals which cache line the discarded work touched. Meltdown let a user program speculatively read kernel memory on many Intel CPUs. Operating systems patched it with kernel page-table isolation (KPTI): the kernel is unmapped from a process's page tables while user code runs, so every system call and interrupt now switches page tables. That made syscall-heavy workloads measurably slower, and is part of why Chapter 2 cares so much about syscall cost and Chapter 13 about TLB flushes. A CPU detail, invisible in C, reshaped kernel design overnight.

Reading a few lines of assembly

You won't write assembly in this course, but you'll read it when profiling (Chapter 37) and when looking at what a lock or an atomic really compiles to. Two commands are enough:

$ gcc -O1 -S square.c -o -          # compiler output as assembly text
$ gcc -O1 -c square.c && objdump -d -M intel square.o
0000000000000000 <square>:
   0:	89 f8                	mov    eax,edi
   2:	0f af c7             	imul   eax,edi
   5:	c3                   	ret

Read each line as: address (offset in the file), the instruction's bytes, then the mnemonic and operands, destination first in Intel syntax. The Compiler Explorer website (godbolt.org) shows the same thing side by side with your C, which is the fastest way to answer "what does this line really cost?".

⚠️
Common mistakes
  • Thinking each C line is one instruction. count++ on a variable in memory is a load, an add and a store, which is exactly why it races between threads (Chapter 17).
  • Mixing up AT&T and Intel syntax. GCC's default (AT&T) puts the destination last and prefixes registers with %; Intel puts it first.
  • Believing the CPU runs instructions strictly in order. It overlaps, reorders and speculates; it only appears in-order to a single thread. Other threads can see the difference (Chapter 25).
  • Benchmarking with -O0. Unoptimised code keeps every variable in memory and tells you little about real cost.
  • Forgetting the stack is per thread. Two threads never share rsp or a call chain, even though they share the heap.

Interview drill

Explain it simply: What happens at the CPU level when one C function calls another?

How a strong answer sounds
The caller puts the first arguments in registers (rdi, rsi, … on Linux x86-64) and executes call, which pushes the address of the next instruction onto the stack (decrementing rsp by 8) and sets rip to the callee. The callee may push saved registers and reserve space for locals by moving rsp down, computes the result into rax, restores what it saved, and executes ret, which pops the return address back into rip. Execution continues in the caller with the result in rax.

Deeper: Why can sorting an array make a loop over it run faster, even though the loop does the same work?

How a strong answer sounds
Because of branch prediction. Modern CPUs are deeply pipelined and speculate past conditional branches. If the loop contains a data-dependent if, random data makes the branch unpredictable, so roughly half the predictions are wrong and each costs 15–20 cycles of flushed work. Sorted data makes the branch go one way for a long run and then the other, so the predictor is almost always right. Making the loop branch-free, for example with a conditional move or a mask, removes the dependence on data order.

🧠 Key takeaways

  • A core is a set of registers plus a loop: fetch at rip, decode, execute, check for interrupts, repeat.
  • Arguments go in rdi, rsi, rdx…; results come back in rax.
  • call pushes a return address and jumps; ret pops it into rip. The stack of return addresses is a thread's position.
  • Saving and restoring registers, including rip and rsp, is all a context switch needs to pause and resume a thread.
  • Pipelines and speculation make CPUs fast; mispredicted branches cost ~15–20 cycles, and Spectre/Meltdown turned speculation into a security problem.
  • objdump -d and gcc -S show what your C really became.

Check your understanding

What does the x86-64 call instruction do?

call pushes the return address (rsp −= 8) and jumps. ret pops it back into rip. Saving other registers is the compiled function's job.

On Linux x86-64, where does a function find its first integer argument?

The System V calling convention passes the first six integer or pointer arguments in rdi, rsi, rdx, rcx, r8 and r9; the return value comes back in rax.

What must the kernel save so that a paused thread can later continue exactly where it stopped?

The stack stays in memory where it is. The register values, especially the program counter and stack pointer, are what define "where it was", and a context switch saves and restores them.

Roughly what does a mispredicted branch cost on a modern x86 core?

The pipeline has to be flushed and refilled from the correct path. That's cheap in absolute terms but adds up quickly in a hot loop.

How did operating systems mitigate Meltdown?

KPTI keeps kernel memory out of the address space while user code runs, so speculative reads have nothing to read, at the cost of extra work on every kernel entry and exit.
