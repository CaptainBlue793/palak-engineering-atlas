mmap & Copy-on-Write

Two of the most useful tricks in the kernel are the same trick: point page-table entries at memory that is shared, and sort out the details only if someone writes. mmap uses it to make a file appear as an array in your address space, with no reads and no copies. fork uses it to "duplicate" a ten-gigabyte process in milliseconds by duplicating nothing. Both rest on the page fault from Chapter 14, used as a hook: mark a page read-only, wait for a write to trap, and do the expensive part then, for that one page only. This is copy-on-write, and it is behind program loading, shared libraries, Redis snapshots and container images.

mmap: a file as memory

mmap asks the kernel to make a range of your address space stand for a range of a file. After the call you read the file by reading memory.

#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>

int fd = open("access.log", O_RDONLY);
struct stat st;
fstat(fd, &st);

char *p = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
close(fd);                                  /* the mapping keeps the file open by itself */

long lines = 0;
for (off_t i = 0; i < st.st_size; i++)       /* no read() calls: just memory accesses */
    lines += (p[i] == '\n');

munmap(p, st.st_size);

The mmap call itself does almost nothing: it creates a VMA saying "these addresses are that file" and returns. No data is read. The first touch of each page faults, and the kernel maps in the page that holds that part of the file from its page cache (Chapter 31), reading it from disk first if necessary. Your process and the kernel's cache then share the same physical frame: nothing is copied into a buffer of yours, because there is no buffer.

Shared or private, file or anonymous

Two choices define a mapping. Is it backed by a file, or by nothing (anonymous, starting as zeros)? And what happens to writes: are they shared with everyone else who maps the same thing, or private to this process?

MAP_SHAREDMAP_PRIVATE
File-backedWrites go into the page cache: other processes mapping the file see them at once, and the kernel writes them back to the file. Used for: memory-mapped databases, shared data filesReads come from the file; a write gets a private copy of that page, and the file is never changed. Used for: loading programs and libraries
AnonymousMemory shared between a process and the children it forks. Used for: shared memory between related processes (Chapter 9)Ordinary private memory, zero-filled on first touch. Used for: the heap, stacks, large malloc blocks (Chapter 16)

The top-right cell is how every program on the machine is loaded. The dynamic loader maps the C library's file privately into each process. The code pages are never written, so all three hundred processes that use the library share one copy of them in RAM. The library's data pages start out shared too, and a process gets its own copy of one only when it first writes to it. This is why the "shared" column in top is so large, and why starting the hundredth copy of a program costs so little memory.

Copy-on-write after fork

fork must give the child a copy of the parent's entire address space. Early Unix really copied it. That is wasteful in the usual case, where the child calls exec a moment later and throws the copy away (Chapter 3), and intolerable for a large process. Modern kernels copy only the page tables:

  • the child's page tables point at the same physical frames as the parent's;
  • every writable private page is marked read-only in both processes;
  • each frame's reference count goes up by one.

Reads work as before, for both. The first write to a page, by either process, hits the read-only bit and faults:

The kernel tells this fault apart from an illegal write by looking at the VMA (Chapter 14): the mapping is writable, only the page-table entry says otherwise. If the reference count has already dropped to one, because the other process exited or copied its own, there is nothing to copy: the kernel just makes the page writable again.

Fork is therefore cheap but not free. The page tables themselves are copied, about 2 MiB of them per gigabyte of memory, so forking a process with tens of gigabytes takes tens of milliseconds, during which the parent is paused. Programs that only want to start another program can skip even that with posix_spawn or vfork.

The letter and number in each page are its contents: the number goes up each time that page is written, so you can see when parent and child have different data. "ro" means the page-table entry is read-only although the memory is writable: a write will fault. Blue pages share their frame with the other process.

Things to notice. Straight after fork there are sixteen pages and still eight frames. Each first write to a shared page costs one copy, whichever side writes. If the child calls exec or exits before any write, nothing was ever copied, which is the common case fork was optimised for. The parent's pages are left read-only, and its next write to each one faults once more but copies nothing, because it is the only user. Now press Parent rewrites every page while a child exists: memory use doubles. That is exactly what happens to a database that snapshots itself with fork while under heavy write load. With MAP_SHARED memory there are no copies at all, and each side sees the other's writes.

mmap or read()?

Reading a file with read() copies data from the page cache into your buffer, one system call at a time. A mapping gives you the page cache's own pages. Which is better depends on the access pattern more than on any general rule.

Mappings suit read-mostly data that several processes share, lookups scattered across a large file, and loading code. Plain reads and writes suit streaming through a file, anything that needs precise control of durability, and code that must handle disk errors gracefully. You can tell the kernel what to expect with madvise: MADV_SEQUENTIAL, MADV_RANDOM, MADV_WILLNEED, or MADV_DONTNEED to hand pages back.

Why databases keep giving up on mmap

Memory-mapping the data files looks like the perfect way to build a database: the operating system already has a cache, already decides what to keep in RAM and already writes dirty pages back, so the database need not have a buffer pool of its own. MongoDB's original storage engine did exactly this, and was named MMAPv1 after it. In practice the engine could never control what mattered. It couldn't decide which pages stayed in memory, couldn't know whether touching a record would take a nanosecond or block the thread on a disk read, and couldn't guarantee the order in which changes reached the disk, which a database needs in order to recover correctly after a crash. MongoDB made the WiredTiger engine, with its own cache, the default in 2015 and later removed MMAPv1 altogether. In 2022 a paper by Andrew Crotty, Viktor Leis and Andy Pavlo, "Are You Sure You Want to Use MMAP in Your Database Management System?", collected the same story from several systems and measured the rest: with fast disks and many cores, the kernel's page eviction and the TLB shootdowns that go with it stop scaling long before a purpose-built buffer pool does. Some stores, LMDB among them, use mmap deliberately and well, for read-heavy workloads that fit in memory. The general lesson is about control: mmap is at its best when the kernel's own choices are good enough for you.

⚠️
Common mistakes
  • Thinking mmap reads the file. It sets up a mapping. Pages arrive by page fault as you touch them, possibly blocking on disk each time.
  • Expecting writes to a MAP_PRIVATE mapping to reach the file. They go to private copies and vanish when the process exits.
  • Assuming fork is free for large processes. The page tables are copied, and every page written afterwards is copied too.
  • Forking a multithreaded program and carrying on. Only the calling thread exists in the child, while locks held by the others stay locked. Call exec promptly, or don't fork.
  • Ignoring SIGBUS. If a mapped file is truncated by someone else, or the disk fails, the access kills the process unless you handle the signal.
  • Mapping and unmapping in a hot loop. Each munmap interrupts every core running the process. Map once and keep it.

Interview drill

Explain it simply: What is copy-on-write, and how does fork use it?

How a strong answer sounds
Copy-on-write means sharing a resource until someone modifies it, and copying only then. When a process forks, the kernel doesn't duplicate its memory. It copies the page tables so the child's entries point at the same physical frames, marks the writable private pages read-only in both processes, and increments each frame's reference count. Both can read freely. When either writes to such a page, the CPU raises a protection fault; the kernel sees that the mapping is meant to be writable and the frame is shared, so it allocates a new frame, copies that one page, points the writer's page-table entry at the copy with write permission, and restarts the instruction. Pages that are never written are never copied. That makes fork fast even for large processes, and nearly free in the common fork-then-exec case, where the child replaces its address space before writing much at all.

Deeper: A 20 GB in-memory database forks to write a snapshot to disk. What does that cost in time and memory?

How a strong answer sounds
The fork itself copies page tables, not data: about 2 MB of page tables per gigabyte, so tens of megabytes, which takes tens of milliseconds during which the parent can't serve requests. That is a latency spike proportional to the process's size. After the fork the child reads a frozen view of memory and writes it out, while the parent keeps serving. Every page the parent modifies during the snapshot triggers a copy-on-write fault and a 4 KB copy, so extra memory use equals the amount of data written while the child is alive. A read-mostly workload costs almost nothing; a write-heavy one can approach double the memory, 40 GB, and if that isn't available the machine swaps or the OOM killer steps in. Transparent huge pages make it worse, because one write then copies 2 MB instead of 4 KB. So I'd plan for headroom, disable huge pages for that process, set overcommit so the fork isn't refused, and schedule snapshots when the write rate is low.

🧠 Key takeaways

  • mmap makes a file, or fresh zeroed memory, appear at an address; pages arrive on demand by page fault.
  • A file mapping shares the page cache's frames with your process: no copy into a buffer.
  • Shared mappings write through to the file and to other mappers; private mappings copy on write and never change the file.
  • fork copies page tables only, marks pages read-only, and copies a page on the first write to it.
  • A forked process costs memory in proportion to what is written while both copies exist.
  • mmap trades copies and system calls for page faults, SIGBUS on errors and less control over writeback.

Check your understanding

A process using 4 GB of memory calls fork(). Immediately afterwards, before either process writes anything, how much extra physical memory is in use?

Parent and child share every frame, marked read-only. Only the page tables, about 2 MB per gigabyte, are duplicated.

After a fork, the child writes one byte to a page it shares with the parent. What does the kernel do?

The write faults on the read-only entry. The kernel recognises a copy-on-write page and copies just that 4 KiB.

A program maps a file with MAP_PRIVATE and PROT_READ | PROT_WRITE, then modifies the mapped memory. What happens to the file on disk?

Private mappings are copy-on-write. To change the file through a mapping you need MAP_SHARED.

Three hundred processes use the same shared library. Why is its code in physical memory only once?

A file-backed mapping shares the page cache's frames. Code is never written, so no process ever gets a private copy.

A program reads a memory-mapped file while the disk develops a bad sector under one of its pages. How does the program find out?

A memory access has no return value to carry an error, so the kernel can only signal. This is one of mmap's real drawbacks.
