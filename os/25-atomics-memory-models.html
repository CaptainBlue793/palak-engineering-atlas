Atomics & Memory Models

Chapter 17 said that to reason about threads you must consider every interleaving of their instructions. That was a simplification. Real machines don't even run one thread's instructions in the order you wrote them: the compiler rearranges and removes memory accesses, and the CPU holds stores back in a private buffer where other cores can't see them. Single-threaded code never notices. Code that shares memory without locks can see results that no interleaving of the source lines could produce. A memory model is the contract that says what you may rely on, and atomics are how you ask for more. This is the ground that lock-free programming stands on.

The compiler reorders first

A C compiler is bound by the "as-if" rule: it may transform the program in any way, as long as a single thread can't tell the difference. It is allowed to assume no other thread changes a variable behind its back, because doing so without synchronisation is a data race, and a data race is undefined behaviour. So this program hangs:

static bool done;                          /* an ordinary variable */

void *worker(void *arg) {
    while (!done) { }                       /* wait for the main thread */
    return NULL;
}

int main(void) {
    pthread_t t;
    pthread_create(&t, NULL, worker, NULL);
    sleep(1);
    done = true;
    pthread_join(t, NULL);                  /* at -O2: never returns */
}
; what gcc -O2 makes of worker(): the load is done once, outside the loop
        movzx   eax, BYTE PTR done[rip]
        test    al, al
        jne     .L1
.L2:    jmp     .L2                         ; an infinite loop that never looks at done again
.L1:    ret

Nothing in the loop writes done, so within this thread its value can't change, so reading it once is "the same". The compiler isn't wrong; the program is, because it has a data race. The same reasoning lets a compiler swap the order of two stores, merge them, or keep a value in a register for a whole function.

Then the CPU reorders: store buffers

Suppose the compiler leaves your accesses alone. The processor still changes their visible order. A store can't complete until the core owns the cache line it writes to, which may mean fetching it from another core and can take tens of nanoseconds (Chapter 32). Stalling for that on every store would be ruinous, so each core has a store buffer: a queue of a few dozen pending stores. The instruction "completes" as soon as its value is in the buffer, and the buffer drains to the cache in the background.

The core's own later loads check the buffer first, so the thread always sees its own writes. Other cores see nothing until the store drains. For a short while the thread that wrote and everybody else disagree about what memory contains. This small program exposes it:

int x = 0, y = 0;

/* Thread A */                 /* Thread B */
x = 1;                         y = 1;
r1 = y;                        r2 = x;

/* Can both r1 and r2 be 0 at the end? */

Try every interleaving of those four lines: whichever store runs first, the other thread's load comes after it and reads 1. At least one of r1 and r2 must be 1. On every mainstream processor, including x86, both can be 0:

How weak is your CPU?

What a processor may reorder is fixed by its architecture's memory model. x86 is among the strictest, and it is not typical.

x86's model is called total store order: stores become visible to others in the order they were issued, just later than you might think. The weak models promise almost nothing between independent accesses. This is the source of a whole class of bug: lock-free code written and tested on Intel machines, relying without knowing it on an ordering that only x86 gives, which then fails rarely and mysteriously on an ARM server or an Apple laptop.

C11 atomics: saying what you need

Since 2011, C and C++ define what multithreaded programs mean, and give you a way to make shared accesses legal: declare the variable atomic. An atomic access can't be torn, isn't a data race, and may not be optimised away or hoisted. Each one also takes a memory order saying how much ordering you need around it. From weakest to strongest:

#include <stdatomic.h>

/* 1. The flag from the top of the chapter, fixed. The default order is seq_cst. */
static atomic_bool done;
while (!atomic_load(&done)) { }            /* really reads it every time round */
atomic_store(&done, true);

/* 2. A counter: only atomicity matters, so relaxed is enough. */
static atomic_long requests;
atomic_fetch_add_explicit(&requests, 1, memory_order_relaxed);

/* 3. Publishing an object: release on the store, acquire on the load. */
static struct config *_Atomic current;

void publish(struct config *c) {
    c->timeout = 30; c->retries = 3;                               /* fill it in first ... */
    atomic_store_explicit(&current, c, memory_order_release);   /* ... then make it visible */
}
struct config *get(void) {
    return atomic_load_explicit(&current, memory_order_acquire);  /* sees a fully initialised object */
}

The third pattern is the important one. Without the release and acquire pair, a weakly ordered CPU or an optimising compiler could let the pointer become visible before the fields it points to, and a reader would follow a valid pointer to an object full of garbage. Release and acquire create a happens-before edge between the two threads: what came before the store in the writer is guaranteed to be seen by what comes after the load in the reader.

Run the store-buffer test

Two threads, two stores, two loads. You decide when each thread runs a line and when each store buffer drains. Find a schedule that leaves both registers at 0. Then try the other two models.

"No store buffers" is the machine Chapter 17 imagined: a store is visible to everyone at once. "Store buffers" is x86. "seq_cst stores" is x86 running atomic_store: the compiler emits an instruction that doesn't finish until the store has reached memory, so the thread can't load until its buffer is empty. On a weaker CPU even more outcomes are possible than this panel shows.

Things to notice. Without store buffers there are 6 schedules and none gives (0, 0). With them, run both stores, then both loads, then drain: (0, 0), an outcome the source code can't explain. With seq_cst stores it is impossible again. The cost of that guarantee is the wait for the buffer to drain, on every store, which is why it is a choice and not the hardware's default behaviour.

Memory barriers

Underneath the atomics are memory barriers (or fences): instructions that forbid the CPU from reordering across them. You rarely write them, but you will meet them in kernel code and in disassembly.

The x86 column explains the bug pattern from earlier. On x86, release, acquire and even relaxed all compile to the same plain instructions, so code that asks for too little still behaves as if it had asked for more. Move the same binary's source to ARM and each order becomes a different instruction with different guarantees. One more trap from other languages: in C, volatile only stops the compiler caching a value in a register. It gives no atomicity and no ordering. Java's volatile is a different thing, equivalent to seq_cst.

🔒
Double-checked locking: broken for a decade

Lazy initialisation with a lock is safe but takes the lock on every call. An "optimisation" spread through C++ and Java code in the 1990s: check the pointer without the lock first; only if it is null, take the lock, check again and create the object. It looks obviously right, and it was wrong. The assignment instance = new Thing() is several steps: allocate memory, run the constructor, store the pointer. Nothing obliged the compiler or the CPU to do them in that order, so the pointer could be stored first. A second thread making the unlocked check would then see a non-null pointer and use an object whose constructor hadn't finished. It failed rarely enough to pass every test. In 2004 Scott Meyers and Andrei Alexandrescu showed in detail that it could not be written correctly in the C++ of the day, and the same year Java 5 changed the meaning of volatile largely so that the idiom could be made to work. The correct version is the publish pattern of this chapter: the pointer must be atomic, stored with release and loaded with acquire. In modern C++ and C you don't write it at all: a function-local static and call_once do it for you, correctly.

What to do in practice

  • Use a mutex. Locking and unlocking are full barriers. Code that touches shared data only under a lock never has to think about any of this, on any CPU.
  • If you use atomics, use the default order. seq_cst behaves the way the interleaving model says. Weaken it only where a profile shows the cost, and write down the argument for why the weaker order is enough.
  • Test on a weakly ordered machine. An ARM server or laptop will show bugs x86 hides. Run ThreadSanitizer everywhere; it checks the language's rules, not what the hardware happens to do.
  • Prefer structures someone else has proved. The next chapter uses these tools to build lock-free data structures, and shows how much care each one takes.
⚠️
Common mistakes
  • Sharing a plain flag between threads. The compiler may read it once and never again. Make it atomic.
  • Using volatile as if it were atomic. In C and C++ it is neither atomic nor ordered.
  • "It works on my machine." If your machine is x86, you have tested the most forgiving model there is.
  • Sprinkling memory_order_relaxed for speed. On x86 it buys nothing for loads and plain stores, and on ARM it removes guarantees you were relying on.
  • Publishing a pointer before the object is ready. Fill in the object, then store the pointer with release.
  • Reasoning by interleaving alone. With weak ordering, outcomes exist that no interleaving of the source produces. Reason with happens-before.

Interview drill

Explain it simply: Why isn't it safe for two threads to share an ordinary variable as a "stop" flag?

How a strong answer sounds
Because unsynchronised access from two threads where one writes is a data race, and in C and C++ that is undefined behaviour, which gives the compiler freedom that breaks the code. In a loop like while (!done), nothing in the loop modifies done, so the optimiser may load it once before the loop and never again, producing an infinite loop. Even if it does reload, the CPU may delay making the writer's store visible, and on weakly ordered hardware other accesses may be reordered around it. The fix is to make the flag atomic, atomic_bool in C, or protect it with a mutex. An atomic load can't be hoisted, and with the default sequentially consistent ordering the reader is guaranteed to see the store.

Deeper: Explain memory_order_acquire and memory_order_release. When are they enough?

How a strong answer sounds
They form a pair that orders one thread's work before another's. A store with release ordering guarantees that all memory writes the thread made before it are visible to any thread that later does an acquire load of the same atomic and sees that stored value. So they create a happens-before edge from the writer to the reader through that variable. That is exactly what is needed to publish data: initialise an object completely, then release-store a pointer or a "ready" flag; a reader acquire-loads it and, if it sees the new value, may safely use the object. It is also what a lock does: unlock is a release, lock is an acquire. They are not enough when the algorithm needs a single global order across different variables, as in the store-buffering pattern where each thread writes one variable and reads another: there, release and acquire still allow both threads to read the old values, and you need seq_cst. On x86 acquire and release cost nothing extra; on ARM they select specific load and store instructions.

🧠 Key takeaways

  • Compilers may reorder, merge and remove accesses to ordinary variables, because a data race is undefined behaviour.
  • CPUs delay stores in a store buffer; other cores can read stale values, giving results no interleaving of the source allows.
  • x86 only lets loads pass earlier stores. ARM, RISC-V and POWER allow much more, so x86-tested code can break elsewhere.
  • Atomics make shared access legal. relaxed gives atomicity only; release with acquire publishes data safely; seq_cst gives one global order.
  • Memory barriers are the instructions that enforce this; locks and seq_cst operations include them.
  • Default to a mutex, then to seq_cst atomics. Weaker orders need a proof and a measurement.

It is not a data race and can't be torn, which is enough for a counter. It gives no happens-before relationship.
