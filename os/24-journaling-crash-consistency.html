Journaling & Crash Consistency

Adding one block to a file changes three separate places on the disk, and a disk writes them one at a time. Machines lose power, kernels panic and cables are pulled, at any moment, including between the second write and the third. What is on the disk then? A file system has to be able to answer "something sensible", after every possible interruption, and to get back to a usable state quickly. This chapter looks at the problem exactly, at the old answer (check the whole disk afterwards), at the answer nearly every file system uses now (write down what you are about to do first), and at a third design that avoids overwriting anything at all.

The crash-consistency problem

A program appends 4 KiB to a file that already has one block. To make that true on disk the file system must write three blocks:

  • the data block: the new contents, in a block that was free (say block 5);
  • the inode: the size goes from 4,096 to 8,192, and block 5 is added to the file's block list;
  • the block bitmap: block 5 is marked as in use.

These are in different places, and a disk can't write three scattered blocks as one indivisible operation. If the machine dies part-way, any subset may have reached the disk. Two of the eight combinations are clean: nothing written, or everything. The other six are these:

Reached the diskWhat the disk now saysConsequence
Data onlyBlock 5 has the new bytes, but nothing refers to it and it is marked freeHarmless. It is as if the append never happened
Bitmap onlyBlock 5 is marked used, and no file owns itA leaked block: space lost until something notices
Inode onlyThe file claims block 5, which holds old rubbish and is marked freeThe file ends in garbage, possibly another user's old data. Worse, the allocator can give block 5 to a second file
Inode + bitmapMetadata is perfectly consistent; block 5 was never writtenThe file ends in garbage, and no check can tell
Inode + dataThe file is right, but block 5 is marked freeThe block will be handed to another file: two files sharing one block
Bitmap + dataBlock 5 is used and written, and no inode points to itLeaked block; the append is lost

The goal is modest: after a crash the file system should look as if each operation either happened completely or didn't happen at all. Losing the last second of work is acceptable. Structures that contradict each other are not.

The old answer: fsck

Early file systems let the inconsistencies happen and repaired them on the next boot. fsck (file system check) reads all the metadata and cross-checks it: every inode's block list against the bitmaps, every directory entry against the inode table, every link count against the number of names actually found.

# e2fsck -f /dev/sdb1
Pass 1: Checking inodes, blocks, and sizes
Pass 2: Checking directory structure
Pass 3: Checking directory connectivity
Pass 4: Checking reference counts
Pass 5: Checking group summary information
Block bitmap differences:  +524312                  # an inode uses a block the bitmap calls free
Fix<y>? yes
Free blocks count wrong for group #16 (1024, counted=1023).
Fix<y>? yes
/dev/sdb1: ***** FILE SYSTEM WAS MODIFIED *****

It has two weaknesses that got worse every year. It has to scan the whole disk to find a problem that involves three blocks, so the time grows with the size of the disk, not the size of the damage: minutes in the 1990s, hours on a multi-terabyte volume, with the server down throughout. And it can only make the metadata agree with itself. In the "inode + bitmap" case there is nothing inconsistent to find, so the garbage stays. Orphaned files with no name are moved to lost+found for a human to sort out.

Journaling: write it down first

The idea that replaced it comes from databases, where it is called write-ahead logging. Before changing any structure in place, the file system first writes a note describing the whole change to a reserved area of the disk, the journal. Only once the note is safely stored does it make the real changes.

After a crash, recovery reads the journal and nothing else:

  • A transaction with no commit record is ignored. Its real locations were never touched, so the file system is in its old, consistent state.
  • A committed transaction is replayed: its logged blocks are copied to their real places. If some had already been written before the crash, they are simply written again with the same contents.

Either way the operation is all or nothing, and recovery takes time proportional to the journal, a second or two, however large the disk is.

$ dmesg | grep EXT4
EXT4-fs (nvme0n1p2): recovery complete
EXT4-fs (nvme0n1p2): mounted filesystem with ordered data mode

What goes in the journal: three modes

Journaling everything means every block is written twice, once to the journal and once to its place. For file contents, which are most of the bytes, that halves write throughput. So file systems offer a cheaper arrangement: journal only the metadata and write data blocks directly. That raises a question of order. If the metadata transaction commits before the data block has been written, a crash leaves a committed inode pointing at garbage. Ordered mode closes that hole by always writing the data blocks to their final place first, and only then committing the metadata that refers to them.

ext4 mount optionIn the journalAfter a crashCost
data=journalMetadata and file dataMetadata consistent; file contents are old or new, never garbageAll data written twice
data=ordered (default)Metadata only; data is written to its place before the metadata commitsMetadata consistent; files never expose blocks that weren't writtenClose to no journal
data=writebackMetadata only; data is written whenever convenientMetadata consistent, but a recently extended file can contain stale garbageFastest

Two practical points. The journal protects the file system's structure, not your last few seconds of work: ext4 commits about every five seconds, and whatever hadn't been committed is simply gone after a crash. And a journal is no defence against a disk that returns wrong data or loses blocks it claimed to have written.

The boxes show what is on the disk. The complete update exists in memory from the start and is lost when the power goes. Green means the new version has reached its final location. Real journals batch many operations into one transaction; this one holds a single append.

Things to notice. Without a journal, five of the eight places to stop leave something wrong, and the most dangerous are the ones where the inode gets ahead of the other two. Recovery by fsck repairs the bookkeeping but can't bring back the append or turn garbage into data. With either journal there is no bad moment: before the commit record the old state survives untouched, and after it the new state can always be rebuilt from the journal. In ordered mode, notice that the data block goes out first, so the commit never describes a file whose contents haven't been written.

Copy-on-write file systems

ZFS, btrfs and APFS take a different route: never overwrite live data at all. A change is written to free blocks. That changes the block that pointed to the old version, so a new copy of that block is written too, and so on up the tree of metadata to the root. Last of all, one write switches the file system's root pointer from the old tree to the new one.

Copy-on-write file systems usually add a checksum for every block, stored in the block above it. That lets them detect a disk silently returning the wrong contents, and repair it from a mirror copy if there is one, which neither fsck nor a journal can do.

What the file system doesn't do for you

A consistent file system is not the same as a safe file. All of the above keeps the file system's structures sane. Whether your data survives is up to you, because write() only copies bytes into the kernel's memory and returns. To make a file durable you must ask, with fsync, and to replace a file safely you combine it with the atomic rename from Chapter 23:

int fd = open("config.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(fd, buf, len);
fsync(fd);                              /* 1. the new contents are on the disk */
close(fd);
rename("config.tmp", "config");         /* 2. switch the name, atomically */
int dir = open(".", O_RDONLY);
fsync(dir);                             /* 3. the rename itself is on the disk */
close(dir);

After a crash at any point, config is the complete old file or the complete new one. Leave out step 1 and it can be an empty file. Chapter 31 covers what fsync does and what it costs.

📄
The ext4 zero-length file bug of 2009

When ext4 became the default in Linux distributions in 2009, users began reporting that after a crash, configuration files they had just saved were present and empty. Desktop programs were saving settings the usual way: write a new file, then rename it over the old one, without an fsync. On ext3 that had been safe in practice, because ordered mode pushed the data out within five seconds, before the rename committed. ext4 had added delayed allocation: it didn't even choose blocks for new data until writeback, up to half a minute later, to lay files out better. Until then there were no data blocks for ordered mode to write first. So the journal could commit the rename, making the new name point at a file with no contents yet, and a crash in that window kept the committed, empty file and lost the old one. The file system was perfectly consistent; the users' data was gone. Both sides had a point: POSIX had never promised the old behaviour, and thousands of programs depended on it. ext4 changed, and now forces a file's data out when it is renamed over an existing file, and well-written programs call fsync before the rename, as above. It is the clearest demonstration that "crash-consistent" describes the file system, not the application.

⚠️
Common mistakes
  • Thinking a journal means no data loss. It means no structural corruption. Recent writes that weren't committed or synced are lost.
  • Assuming write() returning means the data is on disk. It is in memory. Only fsync asks for it to be made durable.
  • Replacing a file by truncating and rewriting it. A crash in between leaves an empty or half-written file. Write a new one and rename.
  • Renaming without syncing the data first. The name can become durable before the contents do.
  • Believing fsck makes data correct. It makes metadata agree with itself. It can't know what your file should contain.
  • Mounting with data=writeback for speed without understanding it. After a crash, files can contain stale blocks, including other users' deleted data.

Interview drill

Explain it simply: What is journaling in a file system and what problem does it solve?

How a strong answer sounds
A single file operation updates several on-disk structures, for an append the data block, the inode and the allocation bitmap, and the disk can't write them atomically. A crash in between leaves them contradicting each other: an inode pointing at an unwritten block, or a block that is in use but marked free. Journaling solves this with write-ahead logging. The file system first writes a description of the whole update to a journal area, then a commit record, and only then writes the blocks to their real locations. On reboot it scans the journal: transactions without a commit record are discarded, because nothing was changed in place, and committed ones are replayed. So every operation is all or nothing, and recovery takes seconds instead of the hours a full fsck needs. Most file systems journal only metadata for speed; ext4's default ordered mode also writes data blocks before committing the metadata that points to them, so files never expose garbage.

Deeper: How would you update a configuration file so that a crash can never leave it corrupted or empty?

How a strong answer sounds
Never modify it in place. Write the complete new contents to a temporary file in the same directory, so it is on the same file system. Call fsync on that file, so its data and inode are on stable storage. Then rename it over the real name: rename is atomic, so any reader or any crash sees either the whole old file or the whole new one. Finally fsync the directory, because the rename is a change to the directory and isn't durable until that is flushed. I'd check the return value of every call, fsync especially, since a failed sync means the data may not be there. If I skipped the first fsync, a journaling file system could commit the rename before the data blocks were written, and a crash would leave a zero-length file, which is exactly what happened to many applications when ext4 introduced delayed allocation.

🧠 Key takeaways

  • One logical operation is several disk writes, and a crash can land between any two of them.
  • fsck repairs metadata by scanning the whole disk: slow, and unable to restore data.
  • A journal records the change, then a commit record, then checkpoints it; recovery replays committed transactions and ignores the rest.
  • Metadata journaling is the usual compromise; ordered mode writes data before committing the metadata that points to it.
  • Copy-on-write file systems write new blocks and switch a root pointer, so the disk is always consistent, and snapshots come nearly free.
  • None of this makes your own writes durable. That takes fsync, and write-then-rename for safe replacement.

Check your understanding

A file is being extended by one block. The machine crashes after the inode has been written but before the data block or the bitmap. What is on the disk?

The inode got ahead. Reading the file returns whatever was in that block before, and the allocator may hand the same block to another file.

Why did journaling replace fsck as the normal way to recover from a crash?

fsck's cost is proportional to the disk, not to the damage. Journal recovery reads only the journal.

During recovery, the journal contains a transaction with its blocks logged but no commit record. What happens?

Nothing is written in place until after the commit. Without a commit record the transaction never happened.

What does ext4's default data=ordered mode guarantee?

Only metadata is journaled, but data goes out first, so a committed inode never points at blocks that were not written.

How does a copy-on-write file system such as ZFS or btrfs stay consistent without a journal?

The old tree is valid until the root switches and the new one is valid after. There is no moment at which the disk holds a half-updated structure.
