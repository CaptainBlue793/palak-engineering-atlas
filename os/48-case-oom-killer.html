Case Study: An OOM-Killer Incident

At twelve minutes past three in the morning an API stops answering. Its log ends in the middle of an ordinary request. There's no exception, no stack trace and no crash dump, and the process is simply gone. Nothing was wrong with the API. This last case study is an incident of the most common kind there is on Linux, followed the way you would follow it on call: from the symptom, to the one line in the kernel log that explains it, to why the kernel chose that process, and to the changes that stop it happening again. On the way it uses most of what this course has said about memory.

  • Recognise an out-of-memory kill from its symptoms and find the evidence
  • Explain why memory runs out long after the allocations succeeded
  • Work out which process the kernel will choose, and how to change the choice
  • Tell a kill at a container's limit from a kill on a full host
  • Write the fixes: limits, priorities, early warning, and the real root cause

The symptoms

The host is one 16 GB machine running a database, a Java API, a cache and a nightly reporting job. This is what the person on call sees first:

$ systemctl status api
× api.service - Orders API
     Active: failed (Result: oom-kill) since Mon 2026-03-02 03:12:41 UTC; 14min ago
   Main PID: 3310 (code=killed, signal=KILL)

$ tail -n 2 /var/log/api/app.log
03:12:40.981 INFO  GET /orders/88213 200 12ms
03:12:41.007 INFO  GET /orders/88               # the log stops in the middle of a line

Three things together are the signature of an out-of-memory kill: the process died from SIGKILL (signal 9, or exit status 137 from a container), it left nothing in its own log, and nobody sent the signal. SIGKILL can't be caught (Chapter 9), so the program gets no chance to print an error, flush a buffer or write a heap dump. The evidence is in the kernel's log instead.

Read the first and last lines together. python3 invoked the OOM killer: it was the process asking for a page at the moment none could be found. java was killed. The process that triggers the kill and the process that dies are chosen by completely different rules, and neither has to be the one at fault. The table in between is the kernel showing its working, and the rss column, in 4 KiB pages, already suggests why Java was picked: 1,572,864 pages is 6 GB, the largest figure there.

Overcommit and RSS

Why did memory run out at 03:12 and not when it was allocated? Because allocating memory and using it are different events (Chapter 14). malloc and mmap hand out address space, and the kernel agrees to far more of it than there is RAM. A physical frame is needed only when a page is first touched, in a page fault. So the failure comes late, at an ordinary instruction that writes to memory, with no return value in which to report an error. Every measure of "memory used" comes from that distinction:

MeasureWhat it countsUse it for
VSZ (virtual size)All address space the process has mapped, touched or notVery little. A JVM can show 10 GB here and use 1
RSS (resident set size)Pages actually in RAM for this process, including pages it shares with othersWhat the OOM killer looks at. Over-counts shared memory when summed across processes
PSS (proportional set size)RSS with each shared page divided among the processes sharing itAdding up a multi-process program such as PostgreSQL or Chrome
Anonymous memoryHeap and stack: pages with no file behind themThe part that can't be dropped, only swapped. Leaks show up here
Page cacheCached file contents, owned by the kernelMostly reclaimable. A machine with almost no "free" memory and a large cache is healthy

How the OOM killer picks a victim

The aim is to free the most memory by killing the fewest processes, so the score is mostly size. For each process the kernel adds its resident pages, its swapped pages and its page tables, and expresses that as parts per thousand of the machine's memory. Then it adds one number that you control:

/* mm/oom_kill.c, in outline */
points  = rss + swap_entries + page_table_pages;          /* how much killing this would free */
points += oom_score_adj * total_pages / 1000;             /* the administrator's thumb on the scale */
if (oom_score_adj == -1000) return NEVER;                 /* this process is not a candidate at all */
$ cat /proc/3310/oom_score /proc/3310/oom_score_adj       # java: 6 GB of 16 GB
375
0
$ echo 500 > /proc/9917/oom_score_adj                       # "if someone must die, prefer this one"
# for a systemd service, in the unit file:  OOMScoreAdjust=-900

oom_score_adj runs from −1000 to +1000 and is inherited by child processes. Each step of 100 is worth a tenth of the machine's RAM in the comparison. System services that must survive, such as sshd, are started at −1000, and Kubernetes sets the value on every container from its quality-of-service class: about −997 for pods with guaranteed resources, +1000 for pods that declared none.

Things to notice. With everything at the default, the first kill takes the API. It scores 375 because it is the biggest process, while the leaking job is at 156 and carries on growing into the space that was freed. Only on the second round, at 8.5 GB and a score of 531, is the job itself the largest. Two kills, and the first one hit a bystander. Now reset and set the job's adjustment to +500: it scores 656 and dies first, and nothing else is touched. Try protecting the API instead, with −500. The kernel still has to kill something, so it takes the database, which is worse. Protection moves the damage along; it doesn't remove it. Give the job −1000 and it outlives everything, up to a kernel panic. Finally switch on the 2 GB limit. The job is killed at 2 GB, inside its own cgroup, the scores of the other processes never come into it, and the host doesn't run out at all.

cgroup memory limits in containers

That last setting is the important one, and it changes what kind of event the kill is. There are two different out-of-memory situations, and they are often confused:

A limit turns an unpredictable failure of the whole machine into a predictable failure of one service, which is the entire reason to set one. Two details catch people out.

  • More than the heap counts. The cgroup is charged for the process's anonymous memory, for page cache its files occupy, for kernel memory used on its behalf, and for files in memory-backed file systems such as /dev/shm. A JVM with a 2 GB heap needs a limit comfortably above 2 GB, because thread stacks, compiled code, class metadata and buffers outside the heap are all extra.
  • The runtime has to know about the limit. For years a JVM in a container sized its heap from the host's RAM, since that is what /proc/meminfo reports inside a container, and was killed as soon as it grew into a heap its cgroup didn't allow. Java has read the cgroup limit since 2017–18, and Go has had GOMEMLIMIT since 1.19. A runtime that respects the limit collects garbage harder as it approaches, and fails with its own out-of-memory error, which can be caught, logged and dumped.

Fixes and prevention

Back to the incident. Put together from the kernel log and the job scheduler, the night looked like this:

TimeWhat was seenWhat was happening
02:00NothingThe nightly report starts. A change released the day before makes it load a whole table into memory
02:50API latency creeping upFree memory is gone. The kernel is evicting page cache, including the code of running programs, and reading it back from disk
03:12API down. Alert firesFirst OOM kill: java, the largest process at 6 GB. The report, at 2.5 GB, continues
03:19Report job "failed"Second OOM kill: python3, now 8.5 GB and the largest
03:31API restarted by hand; all wellThe cause had already removed itself. Without the kernel log, the incident reads as "the API crashed for no reason"

The root cause is the leak in the report. But a postmortem that stops there has fixed one bug and left the machine exactly as fragile, so the useful findings are the contributing ones:

⚖️
Facebook's oomd: the kernel's killer arrives too late

Engineers running Facebook's fleet kept meeting the 02:50 line of that timeline, at scale. The kernel's OOM killer is a last resort by design. It acts only when reclaim has completely failed, and before that point a machine can spend minutes barely alive, evicting and re-reading the pages of the programs it is trying to run. Servers were effectively down long before anything was killed, and when the kill came it followed the kernel's size-based rule and not what the operators would have chosen. Their answer had two parts. They added pressure stall information to the kernel, merged in Linux 4.20 in 2018, which reports the share of time tasks are stalled waiting for memory. That finally gave a direct measure of "this machine is suffering" in place of guesses based on free memory. And they wrote oomd, a daemon in user space that watches those numbers per cgroup and kills a whole cgroup, chosen by policy, when pressure stays high, well before the kernel would act. The idea is now ordinary. systemd ships a version of it, systemd-oomd, and desktop distributions such as Fedora enable it by default, so that a runaway browser tab is killed in seconds and the whole machine doesn't freeze for minutes.

⚠️
Common mistakes
  • Blaming the victim. The process that was killed is the largest, or the one at its limit. The cause is whichever one grew.
  • Looking for the error in the application log. SIGKILL leaves nothing there. Look in the kernel log and in memory.events.
  • Treating low "free" memory as the alarm. Free is low on every healthy machine, because of the page cache. Watch available memory and pressure.
  • Setting the limit equal to the heap size. The runtime's other memory, and page cache, count too.
  • Protecting everything with −1000. Something must be killable. Protect the few things that are irreplaceable, and choose what is sacrificed.
  • Fixing only the leak. The next one will come from a different program. Limits and alerts are the lasting fix.

Interview drill

Explain it simply: What is the OOM killer, and how does it decide what to kill?

How a strong answer sounds
Linux overcommits memory: allocations succeed as address space, and physical pages are assigned only when touched. So the system can find itself needing a page for a fault when none is free. It first tries to reclaim, by dropping page cache, writing out dirty pages and swapping. If that fails, the out-of-memory killer picks a process and sends it SIGKILL to free memory. The choice is by a badness score: essentially the process's resident memory plus swap plus page tables, as a fraction of total memory, adjusted by oom_score_adj, which ranges from −1000, meaning never kill, to +1000, meaning kill first. The highest score dies. So by default it's the biggest process, which is not necessarily the one that caused the shortage. You can see the scores in /proc/PID/oom_score and the kill in the kernel log as "Out of memory: Killed process". Inside a cgroup with a memory limit the same thing happens locally: when the group hits its limit, a process in that group is chosen.

Deeper: A container keeps being OOMKilled, but the node has gigabytes free and the application's heap metrics look fine. What is going on?

How a strong answer sounds
The node's free memory isn't relevant. The container has its own limit, memory.max on its cgroup, and it's being killed for reaching that. I'd confirm with kubectl describe pod showing OOMKilled and exit code 137, the kernel message "Memory cgroup out of memory", and the oom_kill count in the cgroup's memory.events. The heap looking fine means the memory is elsewhere. The cgroup is charged for everything: the heap, but also thread stacks, native allocations, direct or off-heap buffers, the JIT's code cache and class metadata in a JVM, memory-mapped files and page cache the container generates, and any tmpfs such as /dev/shm. Common causes are a heap limit set equal to the container limit so there's no room for the rest, a runtime that isn't aware of the cgroup limit and sizes itself from the host, a native memory leak, or many threads. I'd compare RSS with the heap size, look at memory.stat for the breakdown between anonymous, file and kernel memory, and then either raise the limit, lower the heap to perhaps 70–75% of it, or find the off-heap growth.

🧠 Key takeaways

  • An OOM kill looks like a process vanishing: SIGKILL, exit status 137, nothing in its own log. The evidence is in the kernel log.
  • Memory runs out when pages are touched, not when they are allocated, and only after reclaim has failed.
  • The victim is the process with the highest score: its share of RAM plus oom_score_adj. That is the largest process, not the guilty one.
  • A cgroup limit makes the kill local: only that group's processes are candidates, whatever the host has free.
  • Everything the cgroup uses counts towards its limit, and a runtime must be told about it.
  • Prevent it with per-service limits, chosen priorities, alerts on memory pressure, and kernel logs someone reads.

A service is found dead with status "killed, signal 9" and its log stops mid-line. Where is the explanation most likely to be?

SIGKILL can't be caught, so the process records nothing. The kernel logs its own decision.

A program allocated 8 GB an hour ago without error. Why is the machine only running out of memory now?

Overcommit and demand paging: the bill arrives at the page fault, not at malloc.

On a full 16 GB host, process A uses 6 GB and has oom_score_adj 0. Process B uses 2.5 GB, is leaking, and has oom_score_adj 0. Which is killed?

375 against 156. The kernel doesn't know which process is at fault, only which is biggest.

What does setting a process's oom_score_adj to −1000 do?

It is never chosen. Use it sparingly: something else will be killed in its place.

A container with a 1 GB limit is OOMKilled while its node has 20 GB free. Why?

A cgroup OOM is local: the trigger is the group's limit and the candidates are the group's processes.
