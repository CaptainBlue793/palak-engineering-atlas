CPU Scheduling II: Priorities, MLFQ & Linux CFS

Chapter 7 left a puzzle: shortest-job-first gives the best response times, but the kernel can't know how long a job will run. Real schedulers solve it by watching. A task that keeps blocking after a millisecond of work behaves like a short, interactive job; a task that burns every slice behaves like a long batch job. This chapter covers the three ideas that turn that observation into a scheduler: priorities (and the starvation they cause), the multi-level feedback queue, and the approach Linux took instead from 2007, the Completely Fair Scheduler, with its successor EEVDF.

Priorities, starvation and aging

The simplest improvement over round robin is to give each task a priority and always run the highest-priority ready task, round robin among equals. That lets an audio thread or a request handler beat a log compressor. The danger is starvation: if high-priority work never runs out, low-priority tasks never run at all. The classic fix is aging: the longer a task waits, the more its effective priority rises, until it's guaranteed a turn. Every scheduler below is, one way or another, a way of setting priorities automatically and preventing starvation.

The multi-level feedback queue

The MLFQ, first described by Corbató's team for MIT's CTSS in 1962 and still the basis of several schedulers (it shaped those of the BSDs, Solaris and Windows), keeps several round-robin queues of decreasing priority, with longer quanta lower down, and moves tasks between them based on how they behave. In the form used by the OSTEP textbook:

  1. If A's priority is higher than B's, A runs.
  2. Equal priorities run round robin.
  3. A new task starts in the top queue: assume it's short and interactive until it proves otherwise.
  4. Once a task uses up its time allotment at a level, however many times it gave up the CPU along the way, it moves down one level.
  5. Every period S, move all tasks back to the top queue (a priority boost).

Rule 3 approximates SJF without knowing lengths: short jobs finish while still at the top. Rule 5 is aging: CPU-bound tasks can't starve, and a task that turns interactive gets a fresh chance. Rule 4's wording matters. An earlier version said "if a task gives up the CPU before its quantum ends, it stays at its level", which a crafty program could game by sleeping for a moment just before each quantum expired, staying at top priority forever. Counting the total time used at a level closes that hole. Try both in the simulator below.

Linux's Completely Fair Scheduler

From 2007 (Linux 2.6.23) until 2023, Linux's default scheduler was CFS, written by Ingo Molnár. It drops queues and quanta altogether in favour of one idea: on an ideal multitasking CPU, n runnable tasks would each get exactly 1/n of the CPU at every instant. CFS tracks how far each task is from that ideal with its virtual runtime, vruntime, the CPU time it has received, scaled by its weight, and always runs the task with the smallest vruntime. Runnable tasks are kept in a red-black tree ordered by vruntime, so the next task is the leftmost node.

/* The heart of CFS, simplified from kernel/sched/fair.c */
#define NICE_0_LOAD 1024

static void update_curr(struct cfs_rq *rq, struct sched_entity *curr, u64 delta_ns) {
	curr->sum_exec_runtime += delta_ns;                               /* real CPU time */
	curr->vruntime += delta_ns * NICE_0_LOAD / curr->load.weight;    /* weighted: heavy tasks age slowly */
	rq->min_vruntime = max(rq->min_vruntime, leftmost_vruntime(rq));
}

static struct sched_entity *pick_next_entity(struct cfs_rq *rq) {
	return rb_entry(rb_first_cached(&rq->tasks_timeline), struct sched_entity, run_node);  /* O(1): cached leftmost */
}

/* A task waking from sleep is placed near min_vruntime, not where it left off,
   so it can't bank hours of "credit" by sleeping, but does get to run soon. */
static void place_entity(struct cfs_rq *rq, struct sched_entity *se) {
	se->vruntime = max(se->vruntime, rq->min_vruntime - sysctl_sched_latency / 2);
}

Interactive tasks get good latency for free: they sleep most of the time, so their vruntime stays low and they're at the left of the tree the moment they wake. Nice values (−20 to 19) set the weight: nice 0 is 1,024, and each step multiplies or divides it by about 1.25, so each nice level is worth roughly 10% of CPU relative to a competing task. A nice −5 task runs about three times as much as a nice 0 one; nice 19 gets a weight of just 15.

EEVDF: Linux 6.6 and later

In Linux 6.6 (October 2023), Peter Zijlstra replaced CFS's pick rule with EEVDF, Earliest Eligible Virtual Deadline First, an algorithm from a 1995 paper by Stoica and Abdel-Wahab. Weights and virtual time stay. What changes: a task is eligible only if it hasn't received more than its fair share (its "lag" is non-negative), and among eligible tasks the one with the earliest virtual deadline (roughly, vruntime plus its requested slice divided by its weight) runs. Tasks asking for shorter slices get earlier deadlines, so latency-sensitive work can be favoured explicitly instead of through CFS's pile of wake-up heuristics. For most workloads the behaviour is similar to CFS; the code is simpler and latency is more predictable.

Kubernetes CPU requests are CFS weights

When you give a container resources.requests.cpu: 500m, Kubernetes doesn't reserve half a core anywhere. It sets the weight of the container's cgroup (cpu.shares = 512 under cgroup v1, the equivalent cpu.weight under v2), and Linux's fair scheduler does the rest: it schedules groups by weight the same way it schedules tasks by nice value. Under contention, a pod requesting 1000m gets twice the CPU of one requesting 500m; when the node is idle, either can use more. CPU limits are a different mechanism, a quota per period that pauses the group when used up, and they're a common hidden source of tail latency (Chapter 38). On a single machine, nice -n 19 ./backup.sh uses the same machinery to keep a backup out of a web server's way.

⚠️
Common mistakes
  • Thinking a lower nice value makes a task faster. It changes its share under contention only; on an idle machine nice does nothing.
  • Expecting nice 19 to mean "never runs while anything else wants the CPU". It still gets about 1.5% against a nice 0 task; use SCHED_IDLE for truly background work.
  • Saying CFS has a fixed time slice. The slice depends on how many tasks are runnable and their weights.
  • Saying MLFQ needs to know job lengths. It infers them from how tasks use their quanta.
  • Forgetting the boost. An MLFQ without it starves CPU-bound tasks whenever interactive load is high.

Interview drill

Explain it simply: How does Linux's CFS decide which task to run?

How a strong answer sounds
Each task has a virtual runtime: the CPU time it has used, scaled down for heavier (lower nice) tasks and up for lighter ones. Runnable tasks sit in a red-black tree ordered by vruntime, and CFS always runs the leftmost, the one that has had the least weighted CPU so far. The running task is charged as it runs and preempted when it has had its share of the target latency or when a woken task is sufficiently behind it. Tasks that sleep a lot keep low vruntimes and so run promptly when they wake, which gives interactive tasks good latency without special cases. Since Linux 6.6 the pick rule is EEVDF, which adds eligibility and virtual deadlines on top of the same weights.

Deeper: How can a task game an MLFQ, and how do you stop it?

How a strong answer sounds
If the rule is "a task that gives up the CPU before its quantum expires keeps its priority", a CPU-hungry program can run for 99% of its quantum, do a tiny sleep or I/O, and repeat, staying in the top queue and taking far more than its share. The fix is to account for total CPU time used at a level, across yields: once its allotment is used up, it's demoted regardless of how it got there. Separately, periodic priority boosts prevent the opposite problem, CPU-bound tasks starving under a flood of interactive ones.

🧠 Key takeaways

  • Priority scheduling needs aging, or low-priority work starves.
  • MLFQ: start at the top, demote tasks that use their allotment, boost everyone periodically; account total time at a level so it can't be gamed.
  • CFS runs the task with the smallest weighted virtual runtime, kept in a red-black tree.
  • Each nice step is about 1.25× weight, roughly 10% of CPU against a competitor; nice matters only under contention.
  • Linux 6.6 switched to EEVDF: same weights, plus eligibility and virtual deadlines for more predictable latency.

Check your understanding

What is aging in a priority scheduler?

Waiting earns priority. MLFQ's periodic boost is a blunt form of the same idea.

In an MLFQ, where does a brand-new task start, and why?

Starting high approximates SJF: short jobs finish before they're ever demoted, and long ones sink.

Two CPU-bound tasks compete on one core under CFS: one at nice 0 (weight 1024), one at nice 5 (weight 335). Roughly what share does the nice 0 task get?

1024 / (1024 + 335) ≈ 0.75. Shares are proportional to weights.

Why do interactive tasks get the CPU quickly under CFS?

Low vruntime means "owed CPU". On wake-up CFS places them near the minimum vruntime, so they're picked almost at once.

What did Linux 6.6 change about the default scheduler?

EEVDF keeps virtual time and weights but uses lag-based eligibility and virtual deadlines, which makes latency more predictable.
