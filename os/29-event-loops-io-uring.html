Event Loops & io_uring

Chapter 28 gave one thread the ability to watch thousands of sockets. The program built on top of that is an event loop: wait for something to be ready, run the small piece of code that deals with it, go back to waiting. Node.js, nginx, Redis, browsers and every async/await runtime are this loop. It buys enormous concurrency from a single thread, at the price of one iron rule, which is that no piece of code may hold the thread for long. This chapter builds the loop, shows what breaking the rule does, and then looks at io_uring, the newer Linux interface that changes the question from "what is ready?" to "what has finished?".

The reactor loop

Attach a small object to each descriptor saying what to do when it is ready, and the epoll loop of Chapter 28 becomes a general-purpose engine. This structure is called a reactor: it reacts to readiness events by dispatching to handlers.

struct handler {
    int fd;
    void (*on_ready)(struct handler *self, uint32_t events);
    void *state;                                  /* whatever this connection needs to remember */
};

void loop_run(int ep)
{
    for (;;) {
        struct epoll_event ev[64];
        int n = epoll_wait(ep, ev, 64, ms_until_next_timer());   /* the only place the thread sleeps */
        for (int i = 0; i < n; i++) {
            struct handler *h = ev[i].data.ptr;
            h->on_ready(h, ev[i].events);            /* must return quickly and must never block */
        }
        run_expired_timers();
    }
}

Everything happens in turn on one thread. Two consequences follow, one welcome and one not. Handlers never run at the same time, so they can share data with no locks and none of the races of Chapter 17. And while one handler is running, nothing else is: the loop is only as responsive as its slowest handler.

Where does the state go? Callbacks and async/await

A thread serving one connection keeps its place in local variables: it calls read(), sleeps, and wakes up on the next line with its stack intact. A handler in an event loop can't do that. When there is nothing more to read it has to return to the loop, and its stack frame is gone. Whatever it needs to remember must be saved in an object on the heap, and the handler becomes a state machine that picks up where it left off.

enum phase { READING, WRITING };
struct conn { int fd; enum phase phase; char buf[4096]; size_t have, sent; };

void conn_ready(struct conn *c)                  /* called each time the socket is ready */
{
    if (c->phase == READING) {
        ssize_t n = read(c->fd, c->buf + c->have, sizeof c->buf - c->have);
        if (n < 0 && errno == EAGAIN) return;   /* back to the loop; c remembers where we are */
        c->have += n;
        if (!request_complete(c)) return;
        build_response(c);
        c->phase = WRITING;
    }
    if (c->phase == WRITING) {
        ssize_t n = write(c->fd, c->buf + c->sent, c->have - c->sent);
        if (n < 0 && errno == EAGAIN) return;
        c->sent += n;
        if (c->sent == c->have) conn_close(c);
    }
}

Writing every piece of logic inside out like this is tedious and error-prone. The first relief was callbacks ("when the read finishes, call this function"), which nest badly. The second was promises and futures, objects standing for a result that isn't there yet. The third, now nearly universal, is async/await, which lets you write the sequential version and has the compiler produce the state machine:

// What you write (Rust-like pseudocode):
async fn handle(conn) {
    let request = conn.read_request().await;     // may pause here ...
    let reply   = build_response(request);
    conn.write_all(reply).await;                 // ... and here
}

Don't block the loop

The second-to-last row is the rule that governs everything written for an event loop. Tasks are scheduled cooperatively: each runs until it awaits or returns. There is no timer interrupt to rescue the others. If one handler spends 200 ms without yielding, every one of the other ten thousand connections waits 200 ms. The usual culprits:

  • Blocking system calls: reading a file, a synchronous DNS lookup, a blocking database driver, sleep.
  • CPU work: parsing a huge JSON document, compressing, hashing a password, resizing an image, a regular expression with catastrophic backtracking.
  • Waiting for a lock that some other thread holds.

There are three ways out. Offload the work to a thread pool and have its completion posted back to the loop as an event; this is what libuv does for file I/O and what spawn_blocking and similar calls are for. Chunk long computations and yield to the loop between pieces. Or run several loops, one per core, so that one stall affects only a fraction of the connections.

Block a loop

One event loop for one second. Five hundred small requests arrive, one every 2 ms, each needing 0.2 ms. Four times in that second a heavy request arrives too. Choose how heavy it is and how the server deals with it, and watch what happens to everybody else.

A model: events are handled strictly in arrival order; a chunked task goes to the back of the queue after each 5 ms piece; the thread pool always has a free thread, and handing over and collecting the result cost the loop 0.05 ms each. Things to notice. A 5 ms task on the loop barely shows. A 200 ms task turns the loop red for three quarters of the second: the median small request, which needs 0.2 ms, takes about 90 ms, because most of them arrive while the loop is busy. Chunking caps the damage at about one chunk, 5 ms, at the price of the heavy task itself taking longer to finish. Handing it to a pool leaves the small requests untouched, and the heavy task takes exactly as long as before: its cost hasn't gone away, it has moved to a thread where it holds nobody up.

☁️
One regular expression, every core, 27 minutes

On 2 July 2019 Cloudflare deployed a new rule to its web application firewall, the component that inspects every HTTP request passing through its network. The rule contained a regular expression which, for certain inputs, made the matching engine backtrack through an enormous number of possibilities. The firewall runs inside the same event-driven worker processes that serve the traffic. Within seconds of the rule going live worldwide, each worker that received a request was stuck evaluating the expression, its event loop unable to return to epoll_wait, and every CPU core that handled web traffic sat at 100%. Requests that were perfectly ordinary queued behind the stuck ones and failed. Cloudflare's traffic fell by about 80% for 27 minutes, until the rule was withdrawn. Nothing blocked in the system-call sense; the handlers were simply computing. On an event loop that is the same thing. The fixes included switching to a regular-expression engine that guarantees running time proportional to its input, and CPU limits for rules: both ways of making sure no single handler can hold the loop.

io_uring: ask for the work, not for readiness

The readiness model has two limits. It doesn't cover disk files, which are always "ready" and then block (Chapter 28). And every operation still costs a system call: wait, then one read or write per ready descriptor. At a million operations a second, crossing into the kernel is the main expense.

io_uring, added to Linux in 2019, replaces "tell me when I can try" with "do this for me and tell me when it is done". The program and the kernel share two ring buffers, mapped into both address spaces:

  • the submission queue: the program writes entries describing operations: read this file at this offset into this buffer, accept on this socket, send these bytes;
  • the completion queue: the kernel writes an entry for each finished operation, with its result.
#include <liburing.h>

struct io_uring ring;
io_uring_queue_init(256, &ring, 0);

struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);       /* a free slot in the submission ring */
io_uring_prep_read(sqe, fd, buf, sizeof buf, offset);     /* describe the operation: it works for files too */
io_uring_sqe_set_data(sqe, req);                          /* a tag, to recognise the completion later */
io_uring_submit(&ring);                                   /* one system call, however many entries are queued */

struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);                           /* something has finished */
struct request *done = io_uring_cqe_get_data(cqe);
int result = cqe->res;                                    /* bytes transferred, or a negative errno */
io_uring_cqe_seen(&ring, cqe);

This is the proactor pattern, or completion-based I/O. Windows has had it for decades as I/O completion ports.

io_uring is used by newer storage engines and network servers, and by runtimes built around it. It is also a large new surface inside the kernel. Google reported in 2023 that most of the kernel exploits submitted to its bug-bounty programme in the previous year had targeted io_uring, and restricted it on its own systems; some container setups block it by default. For most services epoll is still the right default, and io_uring is what you reach for when measurement shows that system calls or disk I/O are the limit.

⚠️
Common mistakes
  • Calling blocking code from a handler. A synchronous file read, DNS lookup or database call stops every connection on the loop for its duration.
  • Forgetting that computation blocks too. No system call is needed. A 100 ms loop over data is a 100 ms outage for everyone else.
  • Assuming async means parallel. A single loop uses one core. More throughput needs more loops or a pool.
  • Offloading without a limit. Sending every request to a pool rebuilds thread-per-request. Bound the pool and its queue (Chapter 27).
  • Freeing a buffer before its io_uring operation completes. The kernel writes into it later. It must outlive the operation.
  • Not measuring loop lag. The time between a timer being due and running is the loop's health in one number. Export it.

Interview drill

Explain it simply: How does a single-threaded server such as Node.js or Redis handle thousands of connections?

How a strong answer sounds
With an event loop over non-blocking sockets. All connections are registered with the kernel's readiness mechanism, epoll on Linux. The single thread calls epoll_wait, which sleeps until some sockets are ready, then runs a short handler for each one: read what has arrived, do a little work, write what can be written, and return. No handler ever waits for I/O; if a socket isn't ready, the handler saves its state and goes back to the loop. Because connections spend nearly all their time idle or waiting on the network, one thread can interleave thousands of them, with no stack per connection and no locks, since only one handler runs at a time. The condition is that every handler is quick. Anything slow, such as a blocking call or heavy computation, has to be moved to a thread pool or broken up, because while it runs nothing else does.

Deeper: How does io_uring differ from epoll, and when would you choose it?

How a strong answer sounds
epoll is readiness-based: it tells you a descriptor can be read or written, and you then make the system call yourself. io_uring is completion-based: you describe the operation, the kernel carries it out, and you are told the result. Its interface is two ring buffers shared between user space and the kernel, a submission queue you fill with requests and a completion queue the kernel fills with results, so many operations can be submitted and reaped with one system call, or with none in polling mode. Two things follow. It handles regular files asynchronously, which epoll can't, because files always look ready and then block. And it cuts system-call overhead for high-rate network I/O. I'd choose it for storage-heavy systems such as databases and object stores, or for servers where profiling shows time going to system-call entry and exit. I'd stay with epoll when portability matters, when the workload is ordinary network serving, or where io_uring is restricted for security reasons, since it has been a frequent source of kernel vulnerabilities.

🧠 Key takeaways

  • An event loop waits for readiness and dispatches short handlers, one at a time, on one thread.
  • State that a thread would keep on its stack lives in a heap object; async/await has the compiler build that state machine.
  • Tasks on a loop yield only when they choose to. One slow handler, blocking or just computing, delays all the others.
  • Fixes: offload to a bounded thread pool, chunk and yield, or run a loop per core.
  • io_uring is completion-based: shared submission and completion rings, batching, and real asynchronous file I/O.
  • Reactor: "it is ready, you do it". Proactor: "it is done, here is the result".

Check your understanding

An event-loop server calls a function that hashes a password for 150 ms of CPU time inside a request handler. What do the other connections experience?

Handlers on a loop are not preempted in favour of each other. Until this one returns, the loop can't get back to epoll_wait.

What does a compiler turn an async function into?

The state a thread would keep on its stack is stored in the object, so the function can return to the loop and continue later.

Why can handlers on a single-threaded event loop usually share data structures without locks?

There is no interleaving between awaits. The care needed is across an await, where other handlers may run.

In io_uring, how does a program submit operations and learn their results?

Shared rings let a batch of requests be submitted, and results collected, with one system call or none.

Which statement describes the proactor (completion) model, as opposed to the reactor (readiness) model?

A proactor is told about finished operations. A reactor is told that an operation could now be attempted.
