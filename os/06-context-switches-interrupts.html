Context Switches & Interrupts

A CPU core runs one thread at a time. To make 300 threads look like they run together, the kernel has to stop one, save everything about where it was, and start another, thousands of times a second. The trigger is usually an interrupt: a timer firing, a packet arriving, a disk finishing. This chapter shows how an interrupt takes the CPU away from whatever is running, what a context switch actually saves and restores, what it costs (the direct part is small; the cache damage often isn't), and how the kernel keeps interrupt handlers short.

Interrupts: the hardware taps the CPU on the shoulder

Devices don't wait to be asked. When a network card has received packets, a disk has finished a read or the local timer has counted down, it raises an interrupt. Between two instructions the CPU checks for pending interrupts (the last step of the cycle in P3), and if one is pending and interrupts are enabled, it saves the current rip, rsp and flags on the kernel stack, switches to kernel mode if needed, and jumps to the handler for that interrupt's vector, looked up in the interrupt descriptor table the kernel set up at boot.

The timer interrupt is the one that makes multitasking work. Each core's local APIC timer fires periodically (Linux's CONFIG_HZ is commonly 250 or 1,000 times a second), and on each tick the kernel updates the running task's CPU time and asks the scheduler whether someone else should run. Idle cores turn the periodic tick off ("tickless", NO_HZ) to save power, and dedicated cores can even run with almost no ticks for latency-sensitive work.

What a context switch saves and restores

A context switch is the kernel stopping one task and resuming another on the same CPU. It happens for two reasons: the running task blocks (a voluntary switch: it called read() and there was nothing to read) or it is preempted (an involuntary switch: the timer says its turn is over, or a higher-priority task woke up). Either way, by the time the switch happens the task is already in kernel mode with its user registers saved on its kernel stack, so the switch itself is surprisingly small:

/* The shape of Linux's schedule() → context_switch(), heavily simplified. */
void context_switch(struct task_struct *prev, struct task_struct *next) {
	if (prev->mm != next->mm)
		switch_mm(prev->mm, next->mm);   /* different process: load next's page tables (write CR3) */
	switch_to(prev, next);               /* save prev's callee-saved registers and stack pointer
	                                        into prev->thread, load next's, jump into next */
	/* ... when prev is eventually switched back in, it resumes HERE */
}

The floating-point and vector registers (which can be hundreds of bytes with AVX-512) are also saved and restored, and switching to a task of a different process changes the page tables. Older CPUs had to flush the whole TLB on that page-table change; x86 PCIDs and ARM ASIDs tag TLB entries by address space so they can survive (Chapter 13).

What switching costs

OperationRough costWhere the time goes
Function call~1 nsA call and a ret
System call (no switch)~0.1–0.3 µsMode change, mitigations (Chapter 2)
Thread switch, same process~1–2 µs directScheduler decision, register save/restore, FPU state
Process switch~2–4 µs directAll of the above plus loading new page tables
Indirect cost afterwards~0 to hundreds of µsThe new task finds L1/L2 and TLB full of the old task's data and refills them from L3 or DRAM

The direct cost is small enough that a few thousand switches per second per core are noise. The indirect cost is the one that bites, and it depends on how much data each task touches: a task with a 1 MiB working set that gets switched out finds most of it gone from L2 when it comes back. Shorter time slices mean more switches and more refills; that's the trade-off between responsiveness and throughput every scheduler makes (Chapter 7). Explore it:

$ grep ctxt /proc/4120/status    # lifetime totals, as in Chapter 4

Read the two kinds separately. Many voluntary switches (cswch/s) mean the task blocks a lot: normal for an I/O-heavy server, suspicious if it's lock contention. Many involuntary switches (nvcswch/s) mean it's being preempted while it still wants the CPU: too many runnable threads for the cores, or a CPU limit throttling it (Chapter 38). vmstat's r column, runnable tasks, consistently above the core count is the same story from the machine's side.

Top halves and bottom halves

While an interrupt handler runs, further interrupts on that core are usually held off, and whatever task was running is stuck. So Linux splits interrupt work in two. The top half, the handler itself, does the bare minimum: acknowledge the device, grab the data or note that it's ready, and schedule the rest. The bottom half does the real processing a little later with interrupts enabled: as a softirq (used by networking and block I/O), a tasklet, or a workqueue item or threaded handler running in a kernel thread, which is even allowed to sleep.

🌊
Receive livelock, and why Linux polls the network card

In the 1990s, researchers (Mogul and Ramakrishnan, 1996) documented receive livelock: under a flood of packets, a machine spent all its time in interrupt handlers accepting packets and none processing them, so throughput collapsed to zero exactly when load was highest. Each interrupt was cheap; a hundred thousand a second was not. Linux's answer, NAPI, merged in the early 2000s, is the flow above: the first packet's interrupt switches the driver to polling mode, the softirq drains the receive ring in batches with a budget per round, and interrupts come back only when the ring is empty. Modern NICs add interrupt coalescing (one interrupt per batch or per few microseconds) and multiple queues with a separate interrupt per core. It's the same lesson as batching system calls: per-event overhead must not grow with load.

⚠️
Common mistakes
  • Equating a system call with a context switch. A syscall changes mode on the same thread; a switch changes which thread runs. A non-blocking syscall involves no switch.
  • Ignoring the indirect cost. Microbenchmarks of switching measure the direct microseconds; real services pay in cache and TLB misses afterwards.
  • Running thousands of busy threads on a few cores. Involuntary switches and cache thrash grow; use a pool sized to the cores for CPU work (Chapter 27).
  • Doing slow work in an interrupt handler (in a driver): it delays everything on that core. Defer it to a bottom half.
  • Reading high cs alone as a problem. 50,000 voluntary switches per second can be a healthy, busy I/O server; check involuntary switches and run-queue length too.

Interview drill

Explain it simply: What happens during a context switch?

How a strong answer sounds
The current task is already in the kernel, either because it blocked in a system call or because a timer interrupt arrived, so its user registers are saved on its kernel stack. The scheduler picks the next task. If that task belongs to a different process, the kernel loads its page tables. Then switch_to saves the current task's callee-saved registers and kernel stack pointer into its task_struct and loads the next task's, so returning now unwinds the next task's kernel stack, restores its user registers and drops back to user mode where it left off. FPU and vector state are saved and restored too.

Deeper: Why is switching between threads of one process cheaper than between processes, and is it always?

How a strong answer sounds
Threads share an address space, so the kernel skips loading new page tables, and the TLB entries and much of the cache content (shared code and data) stay useful. A process switch loads new page tables, and without PCIDs that flushed the TLB; with PCIDs entries survive, but the new process still touches entirely different memory, so it misses more in caches and the TLB. It isn't always a big difference: if two threads of the same process work on completely different data, the cache refill dominates either way, and that indirect cost is usually larger than the direct microseconds of the switch.

🧠 Key takeaways

  • Interrupts let devices and the timer take the CPU between any two instructions; the timer tick drives preemptive scheduling.
  • A switch saves the old task's registers and kernel stack pointer in its PCB and loads the next task's; a process switch also loads page tables.
  • Direct cost is a few microseconds; the indirect cost of cold caches and TLBs is often larger.
  • Voluntary switches mean blocking; involuntary ones mean preemption. vmstat, pidstat -w and /proc show both.
  • Interrupt handlers do the minimum (top half) and defer the rest (softirqs, workqueues); NAPI polls under load to avoid livelock.

Check your understanding

What lets the kernel take the CPU away from a thread that never makes a system call?

The timer fires regardless of what the thread is doing, so the kernel always regains control.

What is the extra step when switching to a thread of a different process?

Threads of one process share an address space; a different process needs its own page tables, which also affects the TLB.

pidstat -w shows a CPU-heavy service with a high nvcswch/s. What does that suggest?

Non-voluntary switches happen when the task wanted to keep running. Voluntary ones (cswch) come from blocking.

Why does Linux split interrupt handling into a top half and a bottom half?

Long top halves delay other interrupts and the interrupted task. Softirqs, tasklets and workqueues carry the rest.

Halving the time slice on a busy core with large working sets usually…

More, shorter turns mean each task waits less for its next turn but pays the switch and refill cost more often.
