OS Security: Privileges, ASLR & Sandboxing

Chapter 1 gave the operating system three jobs, and the third was protection: keeping programs, and the people running them, from interfering with each other. So far that has mostly meant the memory isolation of virtual addresses. This chapter is about the rest. Who is a process acting for, and what is it allowed to do? What happens when a bug lets an attacker steer a program that has more privilege than they do? And since such bugs keep being found, how do you arrange things so that one of them isn't the end of the machine? The answers come in layers: identities and capabilities, defences that make bugs hard to exploit, and sandboxes that limit the damage when one is exploited anyway.

Who is asking? Users, root and capabilities

Every process carries credentials: a user ID and a set of group IDs. Every file has an owner, a group and permission bits. Each time a process opens a file, sends a signal or binds a port, the kernel compares the two. One user ID is special: UID 0, root, for which nearly every check is skipped.

All-or-nothing is a poor design. A web server needs exactly one privileged thing, to listen on port 80, and to get it traditionally had to be given the power to read every file and load kernel modules too. Linux therefore splits root's power into about forty capabilities that can be granted and removed one at a time.

CapabilityAllowsTypical holder
CAP_NET_BIND_SERVICEBinding to ports below 1024A web server that otherwise runs unprivileged
CAP_NET_RAWSending hand-crafted packetsping

CAP_SYS_PTRACEInspecting and controlling other users' processesDebuggers and profilers
CAP_SYS_ADMINMounting, namespaces and a long list of other thingsSo broad it is nearly root again: grant it reluctantly
 
$ id
uid=1000(ana) gid=1000(ana) groups=1000(ana),27(sudo),999(docker)
$ getcap /usr/bin/ping
/usr/bin/ping cap_net_raw=ep                 # one capability instead of full root
$ grep Cap /proc/4120/status                 # a process's capability sets, as bit masks
CapEff: 0000000000000400                     # only CAP_NET_BIND_SERVICE

Containers start with most capabilities removed, which is a large part of why "root in a container" is less than root (Chapter 34).

setuid, and privilege escalation

An ordinary user must be able to change their own password, and the password file is writable only by root. Unix's answer is the setuid bit: a program marked with it runs with the user ID of the file's owner, not of the person who started it.

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 64152 /usr/bin/passwd      # the s: runs as root, whoever starts it
$ find / -perm -4000 -type f 2>/dev/null           # every setuid program on the machine
/usr/bin/sudo
/usr/bin/passwd
/usr/bin/su
/usr/bin/mount

A setuid-root program is a door in the wall between users and root, guarded only by the correctness of its code. Its input, arguments, environment variables and files are all chosen by an unprivileged and possibly hostile user. Any bug that lets that user redirect what it does is a local privilege escalation: from ordinary account to root. That makes these programs the most carefully audited on the system, and still a regular source of serious vulnerabilities.

The defensive habit runs the other way: start with privilege only if you must, and drop it as soon as the privileged step is done. A server binds port 80 as root and then permanently switches to an unprivileged user before reading a single byte from the network.

When a bug becomes control: memory attacks and their defences

The classic way to take over a C program is the stack overflow from P2. A function copies input into a fixed-size buffer on the stack without checking its length. Just above the buffer sits the function's return address. Input longer than the buffer overwrites it, and when the function returns, the CPU jumps wherever the attacker wrote.

void greet(const char *name)
{
    char buf[16];
    strcpy(buf, name);          /* no length check: a 40-byte name runs past buf, over the return address */
    printf("hello, %s\n", buf);
}

Compilers, kernels and CPUs now add defences that don't fix the bug but make it hard to turn into control. Each one answers a particular technique, and attackers have an answer to each, which is why they are used together.

DefenceWhat it doesStopsThe attacker's reply
Stack canaryThe compiler puts a random value between the buffers and the return address, and checks it before returningOverflows that run straight from a buffer into the return addressLearn the canary through another bug, or overwrite something other than the return address
NX (no-execute)Stack and heap pages are marked non-executable in the page table (Chapter 12)Running code the attacker injected as dataReuse code that is already there: return into the C library, or chain existing fragments ("return-oriented programming")
ASLRThe stack, heap, libraries and program are loaded at random addresses on every runAttacks that need to know where anything isFind an information leak that reveals one address
Control-flow integrityThe CPU keeps a protected second copy of return addresses (a shadow stack), or checks that indirect jumps land on valid targetsMost code-reuse attacksAttack data instead of control flow

Real attacks on modern systems first need a second bug that leaks addresses or the canary, and then chain many small steps; the logic of what each defence blocks is the same. The sandbox here means running as an unprivileged user with a seccomp filter that doesn't allow execve.

Things to notice. With no defences, injected code runs and the attacker owns whatever the service could do. The canary stops every overflow that reaches the return address, by turning it into a clean abort. NX stops injected code and does nothing against returning into the library, since that code is supposed to be executable. ASLR stops both by making the addresses a guess. And the sandbox stops none of the attacks: it changes what winning is worth. The program is hijacked, tries to start a shell, and is killed by the kernel for making a system call it had promised never to make.

Sandboxing with seccomp

A compromised process can only affect the world through system calls. Most programs need a few dozen of the roughly 350 that Linux has. seccomp lets a process hand the kernel a filter listing the calls it will use from now on. The filter can't be removed, and it is inherited by children. Anything outside it fails or kills the process, however completely an attacker controls the code.

#include <seccomp.h>

scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_KILL_PROCESS);       /* anything not listed: die */
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(epoll_wait), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit_group), 0);
seccomp_load(ctx);                                              /* in force from here, for good */
/* open(), execve(), socket(), ptrace() ... are now fatal for this process */

Docker applies a seccomp profile to every container by default. Chrome puts each page's renderer under a very strict one (Chapter 47). OpenSSH filters the process that parses untrusted network data before login. systemd can apply one to any service with a line of configuration.

Least privilege, in layers

The principle behind all of this is old and plain: give every piece of software only the access it needs for its job. No single mechanism achieves it, and none is unbreakable, so they are stacked, each limiting the damage if the one before it fails.

# A systemd service with the layers switched on
[Service]
User=app                                     # 1. not root
NoNewPrivileges=yes                          # 2. setuid programs can't raise it
CapabilityBoundingSet=CAP_NET_BIND_SERVICE   # 3. one capability, and no way to get more
ProtectSystem=strict                         # 4. the file system is read-only to it ...
ReadWritePaths=/var/lib/app                  #    ... except its own data
PrivateTmp=yes                               # 5. its own /tmp (a mount namespace)
SystemCallFilter=@system-service             # 6. seccomp: only the usual service calls

PwnKit: twelve years of root for anyone

In January 2022 researchers at Qualys published a bug in pkexec, a small setuid-root program installed by default on nearly every Linux distribution since 2009. Its job is to run a command as another user after checking a policy. The bug was in the first lines of main. The code assumed that the argument list always has at least one entry, the program's own name. It doesn't have to: a caller can start a program with an empty list. With no arguments, the loop that processed them read one slot past the end, and what lies just past the argument array in memory is the first environment variable. pkexec then wrote a value back to that slot. That let an attacker smuggle in an environment variable that setuid programs are specifically protected against, one that tells the C library to load a shared library of the attacker's choosing, which then ran as root. The exploit was a few dozen lines, worked every time, and needed no knowledge of addresses, so canaries, NX and ASLR were all beside the point: no memory layout was being guessed. Any local user on an unpatched machine was root. It is the case for everything in this chapter: privileged code handles hostile input, even tiny and old code has bugs, and the dependable defences are having fewer privileged programs and giving each as little power as possible.

⚠️
Common mistakes
  • Running services as root "to avoid permission problems". Every bug in the service is then a root compromise. Grant the one capability it needs.
  • Treating ASLR, NX and canaries as fixes. They raise the cost of exploiting a bug. The bug is still there.
  • Thinking a container is a sandbox by itself. Without dropped capabilities, seccomp and a non-root user, a kernel bug or a careless mount is a way out.
  • Adding setuid programs or wide sudo rules for convenience. Each is a new door to root that must be perfect.
  • Checking permissions and then using the name again. Between the check and the use, the file can be swapped. Open it once and work on the descriptor.
  • Trusting input because it is local. Arguments, environment variables and file contents are attacker-controlled whenever privilege is higher than the caller's.

Interview drill

Explain it simply: What do ASLR, NX and stack canaries each protect against?

How a strong answer sounds
They are three defences against memory-corruption exploits, each breaking a different step. A stack canary is a random value the compiler places between a function's local buffers and its saved return address, and checks before the function returns. A linear overflow that reaches the return address must overwrite the canary first, so the check fails and the program aborts instead of jumping where the attacker chose. NX, or data execution prevention, marks the stack and heap as non-executable in the page tables, so even if an attacker gets code into a buffer and redirects execution there, the CPU faults. Attackers answer with code reuse: returning into existing library functions or chaining small instruction sequences. ASLR counters that by loading the stack, heap, libraries and the executable at random addresses each run, so the attacker doesn't know where the code they want to reuse is. It is defeated by an information leak. None of them fixes the bug; together they make it much harder to exploit.

Deeper: How would you harden a network-facing service so that a remote code execution bug in it does as little harm as possible?

How a strong answer sounds
By assuming the bug exists and limiting what the compromised process can reach, in layers. Identity first: run as a dedicated unprivileged user, never root; if it needs a low port, grant only CAP_NET_BIND_SERVICE or bind before dropping privileges, and set no-new-privileges so setuid binaries can't be used to climb back. Then the file system: read-only except for the directories it truly writes, no access to home directories or secrets it doesn't use, a private /tmp. Then the kernel interface: a seccomp filter allowing only the system calls it needs, which blocks things like execve, ptrace and module loading and puts most kernel bugs out of reach. Then the surroundings: its own namespaces or container, cgroup limits so it can't exhaust the host, and network policy so it can talk only to the services it depends on. In the build, keep the standard mitigations on: canaries, position-independent code for ASLR, non-executable stack. And split the design if possible, so the code that parses untrusted input runs in the most restricted process. With systemd or a container runtime most of this is configuration, not code.

🧠 Key takeaways

  • Processes act with a user ID; root bypasses checks, and capabilities split root's power into separate grants.
  • A setuid program runs as its owner. Every bug in one is a potential path from user to root.
  • Stack canaries, NX and ASLR don't fix memory bugs; each blocks a technique for exploiting them, and they are strongest together.
  • seccomp limits the system calls a process may ever make, shrinking what a hijacked process can do.
  • Least privilege is applied in layers: unprivileged user, few capabilities, restricted file system, filtered system calls, isolation.
  • Assume a bug will be found, and design so that it isn't enough.

Check your understanding

What do Linux capabilities do?

A process can hold, say, only the ability to bind low ports, without the rest of what root can do.

A program owned by root has the setuid bit set. An ordinary user runs it. With whose privileges does it run?

setuid makes the effective user ID that of the file's owner. That is why bugs in such programs lead to privilege escalation.

An attacker overflows a stack buffer and overwrites the return address so that it points at code they placed in the buffer. Which defence stops this by faulting when the CPU tries to run that code?

The no-execute bit in the page-table entry makes an instruction fetch from the stack fault. It doesn't stop reuse of code that is already executable.

Why does ASLR make "return into the C library" attacks harder?

Code reuse needs addresses. Randomisation forces the attacker to find a separate leak first.

A service has a seccomp filter that allows only read, write, epoll_wait and exit_group. An attacker gains full control of its code and tries to start a shell. What happens?

The filter is enforced in the kernel on every system call and can't be undone by the process, whoever is steering it.
