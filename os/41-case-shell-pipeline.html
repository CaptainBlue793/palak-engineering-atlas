Case Study: How the Shell Runs ls | grep

You type ls | grep txt and press Enter. Two programs start, the output of one becomes the input of the other, the matching names appear, and the prompt comes back. Neither program contains a line of code about the other. ls writes to its standard output as it always does; grep reads its standard input as it always does. Everything that joins them is done by the shell, in about fifteen system calls, using only pieces from the first ten chapters: pipe, fork, dup2, close, exec and wait. This case study follows every one of those calls, and shows why forgetting a single close leaves the command hanging for ever.

Before anything runs: parsing

The shell is an ordinary program in a loop: print a prompt, read a line, work out what it means, make it happen. Working out what it means is all done inside the shell, before any other program exists.

  • Splitting. The line becomes words: ls, |, grep, txt. The | marks the boundary between two commands whose output and input are to be joined.
  • Expansion. Variables, wildcards and quotes are resolved now. If you type ls *.c, it is the shell that reads the directory and replaces *.c with the matching names. ls never sees a star.
  • Finding the programs. ls isn't a path, so the shell looks through the directories in $PATH until it finds /usr/bin/ls.
  • Built-ins. A few commands, cd and exit among them, must be done by the shell itself, because they change the shell's own state. A child process that changed its directory would help nobody.

What comes out is a plan: run /usr/bin/ls with its standard output going into a pipe, and /usr/bin/grep txt with its standard input coming from the same pipe.

The plan as code

This is the whole of it, with error handling removed. A real shell does exactly this.

int pfd[2];
pipe(pfd);                              /* pfd[0] = read end, pfd[1] = write end */

pid_t a = fork();
if (a == 0) {                           /* child A: will become ls */
    dup2(pfd[1], STDOUT_FILENO);        /* descriptor 1 now refers to the pipe's write end */
    close(pfd[0]); close(pfd[1]);       /* the two spare references are no longer needed */
    execlp("ls", "ls", NULL);           /* same descriptors, new program */
    _exit(127);                         /* only reached if exec failed */
}

pid_t b = fork();
if (b == 0) {                           /* child B: will become grep */
    dup2(pfd[0], STDIN_FILENO);         /* descriptor 0 now refers to the pipe's read end */
    close(pfd[0]); close(pfd[1]);
    execlp("grep", "grep", "txt", NULL);
    _exit(127);
}

close(pfd[0]); close(pfd[1]);           /* the parent must close its copies too: see below */
int status;
waitpid(a, NULL, 0);
waitpid(b, &status, 0);                 /* the pipeline's exit status is the last command's */

Three facts from Chapter 10 carry the design. fork copies the descriptor table, so each child starts with the pipe's ends already open. dup2(old, new) makes descriptor new refer to whatever old refers to. And exec replaces the program but keeps the descriptor table. So the shell arranges descriptors 0 and 1 between fork and exec, and the new program simply finds its standard input or output already connected.

Each box is a process and its descriptor table. Green descriptors refer to the pipe's write end, blue ones to its read end. The pipe's two counts are how many open descriptors, in all processes together, refer to each end.

Things to notice. Straight after the second fork the pipe has three open write ends, in three different processes. Once both programs are running and the shell has closed its copies, exactly one write end and one read end remain. grep finishes because its read returns 0, and the kernel returns 0 only when the pipe is empty and no descriptor anywhere refers to the write end. In the buggy version the shell still holds one. ls has exited, the pipe is empty, grep waits for more data that can never come, and the shell waits for grep. Nothing is wrong with either program.

Why every close matters

A pipe has no "end of file" marker in it. End of file is a fact about the writers: there are none left. That makes the bookkeeping of open ends part of the protocol.

If this is left openWhat happens
The write end in the shellgrep never sees end of file. The pipeline hangs after ls finishes
The write end in the grep childThe same, and harder to spot: grep is waiting for a writer that is itself
The read end in the shell or in lsIf grep exits early, ls isn't told. It should get SIGPIPE on its next write; with a reader still open it fills the 64 KiB pipe and blocks
Nothing: every spare end is closedls exits → writers 0 → grep reads end of file → exits → the shell's wait returns

The third row is what makes yes | head -1 stop. head exits after one line, the read end's count drops to zero, and the next write by yes raises SIGPIPE, which kills it. A pipeline shuts down from the consumer's end backwards.

wait, exit status and job control

The shell collects both children with wait, which also removes their zombie entries (Chapter 3). By convention the status of a pipeline is the status of its last command, so false | true succeeds, and a failed ls is invisible if grep was happy. In scripts, set -o pipefail changes that: the pipeline fails if any command in it did.

One more thing happens between the forks and the waits. An interactive shell puts both children in a new process group, a "job", and tells the terminal that this group is now in the foreground. That is how keys become signals for the right processes:

cmd &NothingThe shell simply doesn't wait, and doesn't give the job the terminal

The deploy script that never returns

A script logs in to a server and starts a long-running program in the background: ssh web1 'nohup ./server &'. The server starts, and the ssh command never comes back. People add sleep, try disown, and eventually kill the terminal. It is this chapter's bug in another setting. On the remote machine, sshd runs your command with its standard output and standard error connected to pipes, and copies whatever comes out of them back over the network. It decides the command has finished when those pipes reach end of file, which, as you now know, means when nobody holds their write ends any more. The background server inherited descriptors 1 and 2 from the shell that started it, and it is still running. The shell has exited and the server holds the pipe open, so sshd waits, and so does your script. nohup doesn't help, because it is about a signal, not about descriptors. The fix is to give the server descriptors of its own: ssh web1 'nohup ./server > server.log 2>&1 < /dev/null &'. The same leak hangs CI jobs that start a helper daemon, command substitutions such as $(start-service), and any program that waits for a child's output to end. When a command hangs after its work is plainly done, ask who still has the pipe.

⚠️
Common mistakes
  • Forgetting to close the pipe in the parent. The reader never sees end of file. The most common pipeline bug there is.
  • Calling dup2 and not closing the original. The child then holds two references to the same end, and one of them is the leak.
  • Creating the pipe after the fork. Each process then has its own, unconnected pipe. The pipe must exist before the processes that share it.
  • Waiting for the first child before starting the second. If the first writes more than 64 KiB it blocks on a full pipe that nobody is reading: a deadlock.
  • Expecting the program to expand * or $HOME. The shell does that. A program started with exec directly gets the characters as they are.
  • Trusting a pipeline's exit status. It is the last command's. Use pipefail where failures earlier in the pipe matter.

Interview drill

Explain it simply: What does a shell do to run ls | grep txt?

How a strong answer sounds
It parses the line into two commands joined by a pipe, then creates the pipe with pipe(), which gives it a read descriptor and a write descriptor. It forks once for ls: in that child it calls dup2 to make descriptor 1, standard output, refer to the pipe's write end, closes both original pipe descriptors, and calls exec to become ls. It forks again for grep: that child uses dup2 to make descriptor 0 the pipe's read end, closes the originals, and execs grep. The parent closes both of its own pipe descriptors and waits for both children. This works because fork copies the descriptor table and exec preserves it, so the programs find their standard streams already connected and need no knowledge of pipes. The closes are essential: grep gets end of file only when every write end is closed, so if the shell kept its copy open, grep would wait for ever after ls exited.

Deeper: Why can't cd be an external program like ls?

How a strong answer sounds
Because the current working directory is an attribute of a process, and a process can only change its own. If cd were a separate program, the shell would fork a child, the child would call chdir successfully, and then exit, leaving the shell's directory exactly where it was. So cd has to be a built-in that the shell executes in its own process with a direct chdir call. The same reasoning applies to anything that must alter the shell's own state: exit, export and umask, setting variables, exec itself, and ulimit. It is a consequence of process isolation: a child inherits copies of the parent's environment, directory and descriptors at fork time, and nothing it does to them flows back.

🧠 Key takeaways

  • The shell parses, expands wildcards and finds programs itself; then it is all pipe, fork, dup2, close, exec, wait.
  • Redirection is done between fork and exec, by rearranging descriptors 0, 1 and 2 in the child.
  • Programs in a pipeline don't know about each other; they just use their standard streams.
  • A reader sees end of file only when every descriptor for the write end is closed, in every process.
  • A writer gets SIGPIPE when no reader is left, which is how pipelines stop early.
  • The pipeline is one job: a process group that the terminal's Ctrl-C and Ctrl-Z are delivered to.

Check your understanding

In ls *.c | wc -l, which program turns *.c into a list of file names?

Wildcard expansion is done by the shell during parsing. ls receives the names as separate arguments.

What does dup2(pfd[1], 1) do in the child that will become ls?

Descriptor 1 is closed if open and then made a duplicate of pfd[1]. ls keeps writing to 1 as usual.

The shell forgets to close its copy of the pipe's write end. ls finishes and exits. What does grep do?

End of file on a pipe means "no writers remain". The shell is still a potential writer, so the kernel keeps grep waiting.

Why does yes | head -1 terminate, although yes prints for ever?

Writing to a pipe with no readers sends the writer SIGPIPE, whose default action is to terminate it.

You press Ctrl-C while ls -R / | grep txt is running. Which processes receive SIGINT?

The shell placed the pipeline in its own process group and made it the terminal's foreground group. The signal goes to that group, not to the shell.
