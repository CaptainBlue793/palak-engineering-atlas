The Page Cache & fsync

When write() returns successfully, where is your data? Not on the disk. It is in the kernel's memory, in the page cache, and it will reach the disk at some point in the next half a minute, unless the power fails first. This arrangement is what makes file I/O fast: reads are served from RAM and writes return in microseconds. It is also why "the program wrote it" and "it is saved" are different statements, and why a single call, fsync, carries the whole weight of durability in every database and every program that must not lose data.

The page cache

Disks are thousands of times slower than memory (P4), so the kernel keeps copies of file contents in RAM. Every ordinary read and write goes through this page cache, a collection of 4 KiB pages indexed by file and offset.

  • Read, page in the cache: copy from RAM to your buffer. Microseconds, and no disk involved.
  • Read, page not cached: the kernel reads it from disk into the cache, then copies. When it sees you reading sequentially it reads ahead, fetching the next blocks before you ask.
  • Write: copy from your buffer into the cached page and mark the page dirty. Return. The disk has not been touched.

The cache has no fixed size. It grows to use whatever memory nothing else wants, and shrinks instantly when a program needs memory, because a clean page can simply be dropped (Chapter 15). That is why a healthy Linux machine shows almost no "free" memory:

$ free -h
               total        used        free      shared  buff/cache   available
Mem:            31Gi       6.2Gi       412Mi       310Mi        24Gi        24Gi
#                                    ^ nearly nothing "free"     ^ the page cache      ^ but 24 GiB can be had at once
$ fincore access.log                   # how much of one file is in the cache right now
  RES PAGES  SIZE FILE
 1.2G 314573  4.8G access.log

Read available, not free. Memory used for cache isn't wasted; unused memory is.

Dirty pages and writeback

A dirty page is one whose contents in memory are newer than on disk. Kernel flusher threads write dirty pages back in the background, a process called writeback. Three things set it off:

Age: a page has been dirty for too long30 seconds, checked every 5vm.dirty_expire_centisecs, vm.dirty_writeback_centisecs

Delaying is good for speed: a file written and deleted within seconds never touches the disk at all, repeated writes to one page become a single disk write, and blocks can be written in an efficient order. The third row of the table is the catch. If a program writes faster than the disk can absorb for long enough, its write() calls suddenly block, sometimes for seconds, which looks from outside like the application freezing for no reason.

Writeback:          8192 kB        # being written at this moment

Making data durable

A program that needs its data to survive must say so.

Call or flagWhat it doesUse
fsync(fd)Writes this file's dirty pages and metadata, tells the drive to empty its own write cache, and returns only when all of that is doneThe standard way to make a file durable
fdatasync(fd)The same, but skips metadata that isn't needed to read the data back, such as the modification timeSlightly cheaper; what databases usually call
O_SYNC / O_DSYNC on openEvery write behaves as if followed by fsync or fdatasyncSimple and slow

An fsync costs what the disk costs: a fraction of a millisecond on a good SSD, around ten on a spinning disk, because it waits for a real device to confirm. It is the one call in ordinary file I/O that is as slow as hardware. Two things follow from the layers data passes through:

Where the data isProcess crashesKernel crashesPower fails
In a user-space buffer (printf, fwrite before fflush)LostLostLost
In the page cache (after write)Safe: the kernel still has itLostLost
In the drive's write cacheSafeSafeLost, unless the drive has power-loss protection
On stable storage (after fsync returns)SafeSafeSafe

The first row catches people out: the C library has its own buffer in front of the kernel's. And the second explains a common surprise in the other direction. A program killed with kill -9 loses nothing it had already handed to write(), because the page cache belongs to the kernel, not to the process.

A model: a write() costs 2 microseconds and an fsync 2 milliseconds, roughly an SSD. Each record's number is the order in which the program was told its write had succeeded. Amber records are in the page cache only; green ones are on the disk.

Things to notice. With no fsync, ten records take 20 microseconds and all of them are lost in a power cut, but none in a kill -9: the kernel writes them out a little later as if nothing had happened. Syncing every record makes each one safe the moment the program hears "ok", and costs a thousand times more time. Syncing every four sits in between: at most three acknowledged records are ever at risk, for a quarter of the cost. That middle position, deliberately chosen, is how most databases run.

When fsync says no

🐘
fsyncgate: twenty years of a wrong assumption

In 2018 a PostgreSQL user, Craig Ringer, investigated a case of silent data corruption on a storage system that had briefly returned errors. The cause shook every database team. PostgreSQL, like most software, assumed that if fsync failed it could try again later, and that a later success meant the data was now safe. Linux didn't work that way. When writeback of a dirty page failed, the kernel reported the error to one fsync call and then marked the page clean, since keeping unwritable pages for ever would exhaust memory. The data existed only in a page that could now be dropped at any time. The next fsync found nothing dirty and returned success. The database concluded a checkpoint was complete and discarded the log records that could have rebuilt the lost pages. On older kernels the single error report could even be delivered to a different process, or to nobody. PostgreSQL's fix was blunt and correct: since version 12, and in the older versions through updates, a failed fsync makes the server crash on purpose and recover from its write-ahead log, which it knows is good. MySQL, MongoDB and others made the same change, and Linux improved how reliably the error is reported. The rule to take away: a failed fsync means that data is gone from the kernel's hands. Never retry it. Treat everything written since the last successful sync as lost.

Durability in databases

A database can't call fsync on its data files for every change: the changed pages are scattered and each sync costs milliseconds. It uses the journal idea of Chapter 24 instead. Every change is first appended to a sequential write-ahead log, and a transaction is acknowledged once the log record is synced. The data files are updated later, at leisure, through the page cache or the database's own. After a crash the log is replayed.

The remaining cost is one sync per commit, and group commit removes most of that: transactions that arrive while a sync is in progress wait together and share the next one, so a hundred commits may cost a single fsync. Databases expose the trade-off the panel showed as a setting:

SystemSettingSafest valueFaster value, and what it risks

None of these choices is wrong. What is wrong is not knowing which one you have.

⚠️
Common mistakes
  • Treating a successful write() as "saved". It means "in the kernel's memory". Only a successful fsync means "on the disk".
  • Ignoring the return value of fsync or close. Errors from delayed writes are reported there and nowhere else.
  • Retrying a failed fsync. The pages may already have been marked clean. A later success doesn't mean the data was written.
  • Forgetting the directory. A new file's name lives in its directory. Sync the directory too, or the file can be durable and unreachable.
  • Benchmarking writes without syncing. You are timing a copy into RAM. Include fsync, or the numbers describe nothing real.
  • Reading "used" memory as a shortage. Page cache is counted there and is given up on demand. Look at available.
🎤
Interview drill

Explain it simply: What happens when a program calls write(), and when is the data safe?

How a strong answer sounds
write() copies the bytes from the program's buffer into the kernel's page cache and marks those pages dirty, then returns. No disk I/O has happened. Kernel flusher threads write dirty pages to the device later: by default within about 30 seconds, or sooner if a lot of memory is dirty. So after write() the data survives the process crashing, because the kernel holds it, but not a kernel panic or a power failure. To make it durable the program calls fsync or fdatasync, which write that file's dirty pages, ask the drive to flush its own cache, and return only when the device confirms. That costs milliseconds, so programs sync at the points where they promise durability, such as a database commit, not after every write. And for a new file you also sync its directory, so the name is durable as well as the contents.

Deeper: How can a database be both durable and fast when fsync is so slow?

How a strong answer sounds
By syncing less, and syncing something cheap. Changes go first to a write-ahead log, which is append-only, so making a transaction durable means syncing a small sequential write instead of many scattered data pages. The data pages are modified in memory and written back in the background; if the machine crashes, the log is replayed. Then group commit: many concurrent transactions share one fsync, because while one sync is in flight the commits that arrive queue up and are covered by the next, so throughput can be far higher than one over the sync time. Beyond that it is hardware and policy: drives with power-loss protection make sync cheap, and the database can be told to acknowledge before syncing, accepting the loss of the last few hundred milliseconds of commits in a crash in exchange for latency. What a database must not do is ignore sync errors: a failed fsync has to be treated as fatal for that data and recovered from the log.

🧠 Key takeaways

  • All ordinary file I/O goes through the page cache; reads are served from RAM and writes land in RAM.
  • write() returns once the data is in the cache. Dirty pages reach the disk by background writeback, up to about 30 seconds later.
  • fsync and fdatasync force a file to stable storage and wait; they cost what the device costs.
  • Data in the page cache survives a process crash but not a kernel crash or a power cut.
  • A failed fsync must be treated as data loss, never retried.
  • Databases get durability from a sequential write-ahead log and share each sync among many commits.

Check your understanding

A program's write() call returns successfully. Where is the data guaranteed to be?

write copies into kernel memory and returns. Writeback to the device happens later, or when the program asks with fsync.

A program writes 100 records with write(), never calls fsync, and is then killed with kill -9. The machine keeps running. What happens to the records?

The page cache belongs to the kernel and outlives the process. A power cut or kernel crash would be a different story.

What does fsync(fd) guarantee when it returns successfully?

It covers one file and waits for the device. Syncing everything is sync().

An fsync call returns an error. What should a program that cares about its data do?

After a failed writeback the kernel may mark the pages clean, so a retry can report success with the data never written.

What is group commit?

While one sync is in progress, later commits queue up and are all made durable by the next sync, dividing its cost among them.
