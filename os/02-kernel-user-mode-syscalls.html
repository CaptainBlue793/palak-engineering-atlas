Kernel Mode, User Mode & System Calls

Your program cannot read a disk, send a packet or even find out the time on most clocks by itself. The CPU won't let it. Every one of those actions needs a privileged instruction or memory the program can't touch, so the program must ask the kernel, through a system call. This chapter follows one read() from a line of C, through the syscall instruction and the kernel's dispatch table, down to the page cache or the disk and back, and explains what that round trip costs and how Linux avoids it when it can.

Two modes, and why

x86 CPUs have four privilege levels called rings; operating systems use two of them. Ring 0, kernel mode, can execute every instruction and touch all memory. Ring 3, user mode, cannot execute privileged instructions (talking to I/O ports, loading page tables, disabling interrupts, halting the CPU) and can only access pages the page table marks as user-accessible. ARM has the same split under different names (EL1 and EL0). The current level is part of the CPU's state, and the only ways from user mode up to kernel mode are controlled entry points the kernel registered at boot:

The important property is that a program can't choose where in the kernel it lands. The CPU jumps to an address the kernel stored in a special register at boot, so user code can request services but can't run arbitrary kernel code. That one restriction is what makes the protection in Chapter 1 real.

Making a system call

On Linux x86-64 a system call is just a register convention plus one instruction. The system-call number goes in rax (read is 0, write is 1, openat is 257), the arguments in rdi, rsi, rdx, r10, r8 and r9, and then syscall. This is all the C library's write() wrapper really does:

#include <stddef.h>

/* A write() without libc: Linux x86-64 system call 1. Returns bytes written or -errno. */
static long raw_write(int fd, const void *buf, size_t n) {
	long ret;
	__asm__ volatile ("syscall"
		: "=a"(ret)                                  /* result comes back in rax */
		: "a"(1L), "D"((long)fd), "S"(buf), "d"(n)   /* rax=1 (write), rdi, rsi, rdx */
		: "rcx", "r11", "memory");                   /* syscall overwrites rcx and r11 */
	return ret;
}

int main(void) {
	long r = raw_write(1, "hello from ring 3\n", 18);
	return r < 0 ? 1 : 0;   /* the kernel returns -EBADF etc.; libc would turn it into -1 + errno */
}

When the CPU executes syscall it does four things in hardware: saves the return address (rip) in rcx and the flags in r11, switches to ring 0, and jumps to the kernel's entry point, entry_SYSCALL_64. The kernel's entry code switches to this thread's kernel stack (every thread has a small one, 16 KiB on x86-64), saves the user registers, and indexes sys_call_table[rax] to find the handler. When the handler finishes, sysret reverses the steps. The kernel returns small negative numbers for errors (−2 for ENOENT); the libc wrapper turns those into −1 and sets errno.

What a system call costs

A system call that does almost nothing, like getppid(), takes very roughly 100 to a few hundred nanoseconds round trip on current x86 servers: hundreds of times more than a function call. The cost comes from the mode switch itself, saving and restoring registers, security mitigations added after Spectre and Meltdown (switching page tables with KPTI, flushing branch predictors), and the caches and TLB entries the kernel's code and data displace. That's why high-performance code batches: one read of 64 KiB instead of 65,536 reads of one byte, writev to send several buffers in one call, sendfile and io_uring (Chapter 29) to submit many operations at once.

The vDSO (virtual dynamic shared object) removes the cost entirely for a few calls that only read kernel data. The kernel maps a tiny library and a read-only page of data (the current time, kept up to date by the kernel) into every process. clock_gettime() and gettimeofday() in glibc call into it and read the time from that page in user mode, in about 20 ns. You saw linux-vdso.so.1 in ldd's output in P6; this is what it is for.

⏱️
The clock source that quietly burned CPU

Services call the clock constantly: every log line, every metric, every timeout check. On older Xen-based EC2 instances, the default clock source was xen, which the vDSO could not read from user space, so every clock_gettime() quietly became a full system call. Engineers at Netflix noticed time functions near the top of CPU flame graphs (Chapter 37), switched the instances' clock source to tsc, which the vDSO can read, and reported CPU savings of around 30% on an affected workload (Brendan Gregg described it in his 2017 AWS re:Invent talk). AWS's own documentation later recommended the same setting. Nothing in the application changed: the same call simply stopped crossing into the kernel.

⚠️
Common mistakes
  • Thinking a system call is "a call into another process". The kernel runs on the same thread, on that thread's kernel stack; the CPU just changes mode.
  • Unbuffered I/O in a loop. read(fd, &c, 1) per byte costs a mode switch per byte. Use a buffer or stdio.
  • Assuming a blocked thread uses CPU. A thread waiting in read() is asleep in a wait queue; it costs memory, not cycles.
  • Ignoring EINTR. A signal can interrupt a blocking call; the call returns −1 with errno = EINTR and must usually be retried.
  • Expecting the kernel to crash on a bad pointer you pass it. It validates and returns EFAULT; your bug shows up as a failed call, not a segfault.

Interview drill

Explain it simply: What happens when a program calls read()?

How a strong answer sounds
The libc wrapper puts the system-call number (0) in rax and the fd, buffer pointer and length in rdi, rsi, rdx, then executes syscall. The CPU switches to kernel mode and jumps to the kernel's registered entry point, which switches to the thread's kernel stack, saves registers and dispatches through the system-call table to the read handler. The kernel looks up the fd in the process's file table, calls the file type's read function, and, for a regular file, finds the data in the page cache, or starts a disk read and puts the thread to sleep until the I/O completes. It copies the bytes into the user buffer after checking the pointer, puts the byte count in rax and returns to user mode with sysret. On error the wrapper sets errno and returns −1.

Deeper: Why is gettimeofday() so much faster than getpid() on modern Linux, when both just return a number?

How a strong answer sounds
Because gettimeofday (and clock_gettime) are served by the vDSO: the kernel maps a small shared library plus a read-only data page containing timekeeping data into every process, and glibc computes the time from that page and the CPU's timestamp counter entirely in user mode, around 20 ns. getpid is a real system call with a full mode switch (glibc stopped caching the PID years ago because caching broke with some uses of clone). The vDSO only works for read-only data the kernel can safely publish, and only with a clock source user space can read, like TSC.

🧠 Key takeaways

  • Ring 0 (kernel) may do anything; ring 3 (user) can't run privileged instructions or touch kernel pages.
  • Entering the kernel happens only through fixed doors: system calls, faults, traps and interrupts.
  • On x86-64 Linux: number in rax, arguments in rdi rsi rdx r10 r8 r9, then syscall; the result comes back in rax.
  • A blocking call puts the thread to sleep in a wait queue; the CPU runs other work until an interrupt wakes it.
  • A system call costs roughly 100 ns to a few hundred; batch work, and let the vDSO handle the clock.
  • The kernel validates every user pointer and returns EFAULT instead of crashing.

Check your understanding

On Linux x86-64, where does the kernel find which system call a program wants?

The number goes in rax (read = 0, write = 1); arguments in rdi, rsi, rdx, r10, r8, r9. The entry code indexes sys_call_table with it.

A thread calls read() on a file whose data isn't in memory. What does it do while the SSD works for 80 µs?

Blocking means sleeping, not spinning: the thread is taken off the run queue and costs no CPU until the device's interrupt marks it runnable again.

Why can't a user program simply jump to the kernel's file-reading code?

The page tables mark kernel memory supervisor-only, and syscall always lands at the kernel's chosen entry point, so user code can request but never steer.

A program passes an invalid pointer as read()'s buffer. What happens?

copy_to_user detects the bad address and the call fails with EFAULT. The kernel never trusts a user pointer.

What is the vDSO for?

The kernel publishes timekeeping data on a read-only page; the vDSO code reads it in ~20 ns, avoiding a mode switch.
