Mutexes & Spinlocks

Chapter 17 ended on a circle: a lock made from ordinary reads and writes has the same race as the code it protects. The way out is hardware. Every CPU has an instruction that reads a value and writes a new one as a single indivisible step, and a lock is a small amount of code wrapped around it. What that code does when the lock is already taken is the interesting part. It can spin, burning CPU until the lock is free, or sleep, and pay for a trip through the kernel. This chapter builds both, shows how Linux's pthread_mutex gets the best of each, and looks at what locks cost once many threads want them.

The instruction that breaks the circle

The broken lock was while (busy) ; busy = 1;. Two threads could both read 0 before either wrote 1. What is needed is a way to read the old value and write the new one with nothing able to come between. CPUs provide two such operations, and C11 exposes both in <stdatomic.h>.

OperationWhat it does, atomicallyx86 instructionC11
Test-and-set (exchange)Write a new value; return the old onexchgatomic_flag_test_and_set, atomic_exchange
Compare-and-swap (CAS)If the value equals expected, write new; report whether it didlock cmpxchgatomic_compare_exchange_strong
Fetch-and-addAdd to the value; return the old onelock xaddatomic_fetch_add

The core makes the step indivisible by holding the cache line that contains the variable exclusively for the duration of the instruction, so no other core can read or write it in between (Chapter 32). With test-and-set, the lock is four lines:

#include <stdatomic.h>

typedef struct { atomic_flag held; } spinlock_t;      /* initialise with { ATOMIC_FLAG_INIT } */

void spin_lock(spinlock_t *l)
{
    while (atomic_flag_test_and_set(&l->held))    /* set it to 1 and learn what it was, in one step */
        __builtin_ia32_pause();                   /* it was already 1: someone else has it. Try again. */
}

void spin_unlock(spinlock_t *l)
{
    atomic_flag_clear(&l->held);
}

If two threads call spin_lock at the same instant, the hardware orders their two exchanges. One of them gets back 0 and owns the lock; the other gets back 1 and loops. Mutual exclusion holds. The pause instruction changes nothing logically; it tells the core this is a wait loop, which saves power and lets a hyperthread sharing the core get more done.

For something as small as the counter of Chapter 17 you don't need a lock at all: atomic_fetch_add(&counter, 1) compiles to one lock add instruction and is correct from any number of threads. Locks are for critical sections longer than one instruction.

Spinlocks

A thread waiting for a spinlock stays on its core, running the loop until the lock is free. That is the right thing to do in exactly one situation: the lock will be released very soon by a thread that is running right now on another core. Then the wait is a few dozen nanoseconds, far less than any alternative.

It goes wrong in three ways:

  • Long critical sections. Every waiter burns a whole core for the entire wait. Four threads and a 1 ms critical section turn three cores into heaters.
  • The holder isn't running. If the thread holding the lock is preempted, the waiters spin for its whole absence, perhaps several time slices, and their spinning is what keeps it off the CPU. This is lock-holder preemption. On a single core it is the normal case: if you are spinning, the holder can't be running.
  • No fairness. Whoever executes the exchange at the lucky moment wins. A thread can lose again and again, so bounded waiting isn't met.

The kernel uses spinlocks heavily, because it can rule those problems out: it disables preemption while one is held, keeps the protected sections to a handful of instructions, and uses a queued design that hands the lock over in arrival order. It also has no choice in interrupt handlers, which can't sleep. User programs have none of those guarantees, since the scheduler can preempt them at any instruction, so a pure spinlock in application code is almost always a mistake.

Sleeping locks and the futex

A mutex does the other thing: if the lock is taken, the thread asks the kernel to put it to sleep until the lock is released. The waiting costs no CPU, and the core runs something else. The obvious implementation makes every lock and unlock a system call, which would add hundreds of nanoseconds to operations that mostly don't contend at all.

Linux's answer is the futex, "fast user-space mutex" (2003). The lock's state is a plain integer in the program's own memory. Taking a free lock and releasing a lock nobody is waiting for are each a single atomic instruction, with no kernel involved. Only when there is contention does a thread call into the kernel:

  • futex(addr, FUTEX_WAIT, val): "put me to sleep, but only if *addr still equals val".
  • futex(addr, FUTEX_WAKE, n): "wake up to n threads sleeping on addr".
/* A futex mutex, after Ulrich Drepper's "Futexes Are Tricky".
   *m is 0 = free, 1 = locked, 2 = locked and someone may be sleeping.
   futex() is a thin wrapper around syscall(SYS_futex, ...). */
void mutex_lock(atomic_int *m)
{
    int c = 0;
    if (atomic_compare_exchange_strong(m, &c, 1))    /* fast path: 0 -> 1, no system call */
        return;
    if (c != 2)
        c = atomic_exchange(m, 2);                   /* announce that someone is waiting */
    while (c != 0) {
        futex(m, FUTEX_WAIT, 2);                     /* sleep, unless *m is no longer 2 */
        c = atomic_exchange(m, 2);                   /* woken: try to take it */
    }
}

void mutex_unlock(atomic_int *m)
{
    if (atomic_fetch_sub(m, 1) != 1) {               /* it was 2: there may be sleepers */
        atomic_store(m, 0);
        futex(m, FUTEX_WAKE, 1);                     /* wake one */
    }
}

The value passed to FUTEX_WAIT closes a gap. Between B deciding to sleep and B actually sleeping, A might unlock and send its wake-up to nobody. The kernel checks the word and queues the thread as one atomic step: if the word has changed, the call returns at once instead of sleeping. Chapter 19 calls this the lost wake-up problem.

pthread_mutex_lock in glibc is built this way: about 20 ns when uncontended, a system call only under contention. Most modern mutexes add one refinement and spin briefly before sleeping, on the bet that the holder is about to finish. Go's, Java's and Rust's standard mutexes all do it, and glibc offers it as PTHREAD_MUTEX_ADAPTIVE_NP.

Spin, sleep or both?

Each thread repeats: 4 µs of its own work, then a critical section under one shared lock. Change the lock, the number of threads and cores, and the length of the critical section. The table underneath compares all three locks for the current setting.

A model: one tick is a microsecond; a sleeping thread costs 1 µs to block and 8 µs to wake and get back on a core; the time slice is 50 µs (real ones are milliseconds, so real lock-holder preemption is far worse); "spin, then sleep" spins for at most 4 µs. A released lock is free for any running thread to take, as with a real futex mutex. Letters mark which thread a long stretch belongs to.

Things to notice. With a 2 µs critical section on 4 cores, the spinlock finishes the most sections (198) and the sleeping mutex the fewest (185): it spends about a quarter of the CPU on going to sleep and waking, for waits that were shorter than the wake-up itself. With a 40 µs critical section all three complete the same work, but the spinlock burns over 70% of four cores doing it, while the mutex leaves them idle for someone else. Now set 1 core: the spinlock collapses to 2 sections against the mutex's 7, because the holder is preempted inside the critical section and each waiter spins away a full time slice. "Spin, then sleep" is never the best lock in this model and never far from it. That is why it is the default almost everywhere: it doesn't have to know in advance which case it is in.

Contention and granularity

A lock makes part of the program run one thread at a time, and that part limits everything. If 5% of each request's work is inside one shared lock, then no matter how many cores you add, throughput can't exceed 20 times a single core's (Amdahl's law), and long before that limit, threads are queuing. A lock is contended when threads often find it taken; contended locks are where multithreaded programs lose their scaling.

The main design choice is granularity: how much data one lock covers.

Coarse: one big lockFine: many small locks
ExampleOne mutex around a whole hash tableOne mutex per bucket, or per group of buckets
CorrectnessEasy to reason aboutHarder: operations that touch two parts need two locks, in a consistent order (Chapter 22)
ScalingPoor: all threads queue on itGood: threads working on different parts don't meet
OverheadOne lock, taken once per operationMore memory and more lock operations per request
Use whenThe lock is held briefly and contention is low. Start hereProfiling shows that one lock is the bottleneck

Before splitting a lock, shorten what it protects. Three habits remove most contention: do the expensive work (allocation, formatting, hashing) outside the lock and only publish the result inside; never hold a lock across I/O or anything else that can block; and don't call code you don't control, such as a callback, while holding one. To find out whether a lock is the problem, look at where threads are waiting, not where they are computing:

The Big Kernel Lock: fifteen years of making one lock smaller

When Linux first supported multiprocessor machines, in version 2.0 (1996), it did so in the simplest way that could be correct: a single spinlock, the Big Kernel Lock, taken on every entry to the kernel. Only one CPU could execute kernel code at a time. A two-processor machine ran user programs in parallel, but as soon as they made system calls they queued. It was the coarsest granularity possible, and it was the right first step, because nothing in the kernel had been written with concurrency in mind. Then the work of splitting it began: separate locks for the scheduler, for each file system, for each inode, for each network socket, release after release, each change exposing code that had quietly depended on the big lock. The last users were removed and the lock deleted in version 2.6.39, in 2011. Python's Global Interpreter Lock is the same design with the same history: one lock that makes a single-threaded runtime safe, simple and fast on one core, which took decades to make optional (the free-threaded build arrived in Python 3.13). The lesson both teach: a coarse lock is cheap to add and very expensive to remove, because everything written under it comes to rely on it.

Reader–writer locks

Many threads reading the same data don't conflict; only writing does. A reader–writer lock allows either any number of readers or exactly one writer.

pthread_rwlock_t rw = PTHREAD_RWLOCK_INITIALIZER;

int lookup(const char *key) {
    pthread_rwlock_rdlock(&rw);           /* shared: other readers may hold it too */
    int v = table_get(key);
    pthread_rwlock_unlock(&rw);
    return v;
}

void update(const char *key, int v) {
    pthread_rwlock_wrlock(&rw);           /* exclusive: waits for every reader to leave */
    table_put(key, v);
    pthread_rwlock_unlock(&rw);
}

It helps when reads are much more common than writes and the read sections are long enough to overlap. It is not a free upgrade. Taking the lock for reading still writes to shared memory, to count the readers, so every reader drags the lock's cache line between cores; for short sections a plain mutex is often faster. And the policy matters: if readers are always admitted while other readers hold the lock, a steady stream of them can keep a writer waiting for ever (Chapter 21). Data that is read constantly and changed rarely is often better served by schemes where readers take no lock at all (Chapter 26).

⚠️
Common mistakes
  • Writing your own spinlock in application code. One preempted holder and every waiter burns a time slice. Use the mutex your platform provides; it already spins when that pays.
  • Holding a lock across I/O or a blocking call. A 10 ms disk read under a lock makes it a 10 ms lock for everyone.
  • Unlocking on only some paths. An early return or error branch that skips the unlock hangs the next caller for ever.
  • Assuming a mutex is slow. Uncontended, it is one atomic instruction each way. Contention is what costs, so measure before redesigning.
  • Reaching for a reader–writer lock by default. With short critical sections it usually loses to a plain mutex.
  • Protecting data with the wrong lock, or two different ones. Decide which lock guards which data, write it down next to the data, and keep to it.

Interview drill

Explain it simply: What is the difference between a spinlock and a mutex, and when would you use each?

How a strong answer sounds
Both give mutual exclusion; they differ in what a thread does when the lock is already held. With a spinlock it loops on an atomic test-and-set until it gets the lock, staying on the CPU. With a mutex it asks the kernel to put it to sleep and is woken when the lock is released. Spinning is cheaper when the wait is shorter than a sleep and wake-up, which cost microseconds, and when the holder is running on another core, so it is used inside the kernel for very short sections and in interrupt context, where sleeping isn't allowed. A mutex is right for anything longer, for anything that might block while holding the lock, and in user space generally, where the holder can be preempted and spinners would waste whole time slices. In practice a modern mutex is a hybrid: an atomic instruction when uncontended, a short spin, then a futex sleep.

Deeper: How does pthread_mutex_lock avoid a system call in the common case?

How a strong answer sounds
It is built on futexes. The mutex's state is an integer in user memory. Locking does a compare-and-swap from 0 to 1; if that succeeds the thread owns the lock, and no kernel call was made. Unlocking decrements it, and if no waiter was recorded that is also the end. Only when the CAS fails does the thread mark the lock as contended and call futex with FUTEX_WAIT, passing the value it expects to find. The kernel checks that the word still has that value and puts the thread on a wait queue keyed by the address, atomically, so a wake-up that happens in between isn't lost. The unlocking thread sees the contended state and calls FUTEX_WAKE to wake one sleeper. So the kernel is only involved when a thread really has to wait, and since most acquisitions in a well-designed program are uncontended, the average cost is tens of nanoseconds.

🧠 Key takeaways

  • Locks are built on atomic instructions: exchange (test-and-set) and compare-and-swap.
  • A spinlock waits by looping. It suits very short sections whose holder is running on another core, which the kernel can guarantee and applications can't.
  • A mutex waits by sleeping. A futex keeps the lock word in user memory, so only contended operations make a system call.
  • Real mutexes spin briefly and then sleep, getting most of the benefit of both.
  • Contention, not locking itself, is what hurts. Shorten critical sections first; split locks when profiling says so.
  • Reader–writer locks help read-mostly data with long read sections; elsewhere a plain mutex is usually as good or better.

Check your understanding

Why can a lock be built from test-and-set but not from a plain read followed by a plain write?

With separate read and write, two threads can both read 0 before either writes. An atomic exchange gives exactly one of them the old value 0.

Two threads share one core. Thread A holds a spinlock and is preempted; thread B then tries to take the lock. What happens?

Lock-holder preemption. B's spinning uses the only core, which is what keeps A from finishing. It resolves only when B's slice ends.

A thread locks and unlocks a futex-based mutex that no other thread is using. How many system calls does that take?

The kernel is called only to sleep (FUTEX_WAIT) or to wake a sleeper (FUTEX_WAKE). Without contention neither is needed.

When is spinning a better choice than sleeping?

A sleep and wake-up cost microseconds. If the lock will be free in nanoseconds, waiting on the CPU is cheaper. Otherwise spinning only wastes it.

Which combination does a reader–writer lock allow at the same time?

Readers don't conflict with each other, so they share the lock. A writer needs it exclusively: no readers and no other writer.
