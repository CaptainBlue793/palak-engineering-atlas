Threads

A process is a container: an address space, a table of open files, a set of credentials. A thread is a flow of execution inside that container, with its own registers and stack. One process can hold many threads, and they all see the same memory and the same files. That makes threads the cheap, fast way to use several cores at once, and it is also exactly why concurrency is hard: when everything is shared, every shared write is a potential bug. This chapter is about what threads share, how they're created, and when you'd pick them over processes. Chapters 17 to 22 deal with the bugs.

What threads share, and what they don't

Think of a web server process handling 50 requests at once with 50 threads. They all run the same code, use the same in-memory cache, write to the same log file descriptor and listen on the same socket. But each is at a different point in its own request, so each needs its own program counter, its own registers and its own stack of function calls.

Shared by all threads of a processPrivate to each thread
Code (.text) and read-only dataRegisters, including rip and rsp
Global and static variables (.data, .bss)The stack: local variables, return addresses
The heap: everything malloc'dThread-local storage, including errno
Open file descriptors and their offsetsSignal mask (which signals it blocks)
Current directory, user and group IDs, PIDThread ID (TID) and scheduling state
Signal handlers; the address space as a wholeCPU time used; its own task_struct

"Private" stacks are private by convention, not by protection: all stacks live in the one shared address space, so a thread that gets a pointer to another thread's local variable can read and write it. The only real isolation boundary is between processes.

Creating and joining threads

POSIX threads (pthreads) is the standard C API. pthread_create starts a new thread running a function you give it, with one void * argument; pthread_join waits for a thread to finish and collects its return value, like waitpid for threads. Here four threads sum quarters of an array in parallel:

#include <pthread.h>
#include <stdio.h>
#include <stdint.h>

#define N        (1u << 24)
#define NTHREADS 4

static uint32_t data[N];                   /* shared: every thread can see it */

struct slice { size_t lo, hi; uint64_t sum; };   /* one per thread: no sharing of results */

static void *sum_slice(void *arg) {
	struct slice *s = arg;
	uint64_t total = 0;                        /* local: on this thread's own stack */
	for (size_t i = s->lo; i < s->hi; i++) total += data[i];
	s->sum = total;                            /* each thread writes only its own slot */
	return NULL;
}

int main(void) {
	for (size_t i = 0; i < N; i++) data[i] = (uint32_t)(i % 7);
	pthread_t tid[NTHREADS];
	struct slice sl[NTHREADS];
	for (int t = 0; t < NTHREADS; t++) {
		sl[t] = (struct slice){ .lo = (size_t)t * N / NTHREADS, .hi = (size_t)(t + 1) * N / NTHREADS };
		int rc = pthread_create(&tid[t], NULL, sum_slice, &sl[t]);
		if (rc != 0) { fprintf(stderr, "pthread_create: error %d\n", rc); return 1; }   /* returns the error, not -1 */
	}
	uint64_t total = 0;
	for (int t = 0; t < NTHREADS; t++) {
		pthread_join(tid[t], NULL);            /* wait, then it's safe to read sl[t].sum */
		total += sl[t].sum;
	}
	printf("total = %llu\n", (unsigned long long)total);
	return 0;
}
$ gcc -O2 -pthread sum.c -o sum && ./sum
total = 50331645

Two design choices keep this correct without any locks: the shared array is only read, and each thread writes only its own struct slice. Results are combined after pthread_join, which guarantees the thread's writes are visible. The moment two threads write the same variable, you need the tools from Chapter 17 onwards. Note also that pthread functions return an error number instead of setting errno.

How Linux makes a thread

Linux has no separate "thread" object. A thread is a task (a task_struct, Chapter 4) created by the clone() system call with flags saying what to share with its creator. fork() is clone() sharing nothing; pthread_create is clone() sharing nearly everything:

$ ps -eLo pid,lwp,nlwp,stat,cmd | grep '[j]ava'
   4120    4120   58 Sl   java -jar api.jar     # PID 4120, 58 threads ("lightweight processes")
   4120    4121   58 Sl   java -jar api.jar     # LWP = the thread's own ID (TID)
$ ls /proc/4120/task | wc -l
58

Because every thread is a full kernel task, the kernel schedules threads, not processes: a process with eight runnable threads can use eight cores. Creating a thread costs roughly tens of microseconds (mostly the stack mapping and the kernel task), less than a fork of a big process but far from free, which is why servers use thread pools (Chapter 27).

Kernel threads, user threads and M:N

"Thread" can mean two things: a kernel-scheduled task, or a lighter flow of control scheduled by a language runtime in user space (a goroutine, a Java virtual thread, a coroutine). How the two map onto each other is a classic design choice:

ModelMappingStrengthsWeaknessesExamples
1:1Each user thread is one kernel taskSimple; true parallelism; blocking calls block only that threadEach thread costs a kernel task and a large stack; tens of thousands get heavypthreads on Linux, Java platform threads, Rust std::thread
N:1Many user threads on one kernel taskVery cheap switches, no kernel involvementNo parallelism; one blocking syscall stalls all of themEarly "green threads" in Java (1990s), Python's asyncio on one thread
M:NMany user threads on a pool of kernel threadsMillions of cheap threads and all cores usedComplex runtime scheduler; must handle blocking calls speciallyGo goroutines, Java 21 virtual threads, Erlang processes

Chapter 45 opens up Go's and Java's M:N schedulers. Underneath both, the kernel still sees ordinary 1:1 threads, one per core or so.

PostgreSQL vs MySQL: one connection, one process or one thread?

PostgreSQL forks a backend process for every client connection; MySQL serves each connection with a thread in one big process. PostgreSQL's choice dates from the 1990s, when threads were less portable, and it gives isolation: a backend that crashes on a bad query can't scribble over another session's memory, and the postmaster restarts cleanly. The cost is memory and setup time per connection, which is why PostgreSQL deployments put a connection pooler like PgBouncer in front and keep connections in the hundreds, not thousands. MySQL's threads make connections cheaper but share one address space. The trade-off is live: in 2023 PostgreSQL developers started discussing a long-term move to a threaded model to cut that per-connection overhead. Chapter 43 looks at the process model in depth.

⚠️
Common mistakes
  • Passing a pointer to a loop variable to pthread_create. By the time the thread reads it, the loop has changed it. Give each thread its own argument, as the listing does.
  • Returning a pointer to the thread's stack from the thread function. The stack is freed when the thread ends.
  • Forgetting to join or detach. An unjoined, undetached thread is a "zombie thread": its stack and record stay allocated.
  • Checking errno after pthread calls. They return the error number directly.
  • Assuming more threads means more speed. Beyond the number of cores, CPU-bound threads just take turns and add switching.
  • Calling exit() from a worker thread. It ends the whole process; use return or pthread_exit.

Interview drill

Explain it simply: What's the difference between a process and a thread?

How a strong answer sounds
A process is a unit of resource ownership: its own address space, file-descriptor table, credentials. A thread is a unit of execution inside a process: its own registers, program counter and stack, but sharing the process's memory, open files and identity with the other threads. So threads communicate through shared memory cheaply but can corrupt each other and die together; processes are isolated and survive each other's crashes but need IPC to share data. On Linux both are tasks created by clone(); a thread is a task that shares its creator's address space and fd table.

Deeper: If threads are so much cheaper to share data between, why do Chrome and PostgreSQL use processes?

How a strong answer sounds
Isolation. A process is the boundary the hardware and kernel enforce: separate page tables, separate privileges. Chrome runs each site's renderer in its own sandboxed process, so a compromised or crashed renderer can't read another site's memory or take the browser down, and it can drop privileges with seccomp. PostgreSQL's process per connection means a backend that crashes can't corrupt other sessions' memory, and the postmaster can recover. Both pay with memory and IPC complexity, and both mitigate it: Chrome shares rendering processes under memory pressure, PostgreSQL deployments pool connections.

🧠 Key takeaways

  • Threads share code, globals, the heap, file descriptors and identity; each has its own registers, stack and TLS (errno).
  • pthread_create starts a thread; pthread_join waits for it and makes its writes visible.
  • On Linux a thread is a task made with clone(CLONE_VM | CLONE_FILES | CLONE_THREAD …); the kernel schedules threads.
  • 1:1 is simple and parallel; M:N (Go, virtual threads) gives millions of cheap threads on a few kernel threads.
  • Threads: cheap sharing, shared fate. Processes: isolation, at the cost of IPC and memory.

Check your understanding

Which of these is private to each thread of a process?

Each thread needs its own call stack and CPU state; everything in the address space and the fd table is shared.

One thread of a 40-thread server dereferences a NULL pointer. What happens?

Signals like SIGSEGV act on the process. Threads share fate, which is why crash isolation needs processes.

How does Linux create a thread?

Threads are tasks that share. fork() is clone() that shares nothing; pthread_create uses clone() with CLONE_VM, CLONE_FILES, CLONE_SIGHAND, CLONE_THREAD and more.

In an N:1 threading model, a user thread calls a blocking read() on a slow disk. What happens to the other user threads?

That's N:1's big weakness, and why M:N runtimes like Go hand off blocked kernel threads and start others.

Why do PostgreSQL deployments typically run a connection pooler such as PgBouncer?

Process-per-connection buys isolation at a per-connection cost; a pooler multiplexes many clients onto a few backends.
