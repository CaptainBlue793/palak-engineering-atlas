Thread Pools & Work Stealing

A server that starts a new thread for every request works well in a demo and falls over in production: ten thousand requests become ten thousand threads, each with its own stack, all fighting for eight cores. A thread pool turns that round. A fixed crew of worker threads takes tasks from a queue, so threads are reused, the amount of work in progress has a limit, and there is one obvious place to say "too busy". Almost every server, runtime and database you use is built on one. The design questions are few and they matter: how many workers, what kind of queue, and how to share work among cores without the queue itself becoming the bottleneck.

Why pool threads?

Creating a thread per task has three costs. Creation and teardown take tens of microseconds each, which is more than many tasks need to run. Each thread reserves a stack, 8 MiB of address space by default on Linux, and occupies kernel memory. And nothing limits the number: a burst of load creates a burst of threads, which makes every one of them slower (Chapter 6), which makes the backlog grow, which creates more threads.

A pool is a bounded buffer with the consumers built in. This is all of it:

typedef struct { void (*fn)(void *); void *arg; } task_t;
static queue_t q;                          /* the bounded queue of Chapter 21 */

static void *worker(void *unused)
{
    for (;;) {
        task_t t = queue_get(&q);           /* sleeps while there is nothing to do */
        if (!t.fn) break;                  /* an empty task means "shut down" */
        t.fn(t.arg);
    }
    return NULL;
}

void pool_start(int n) {
    for (int i = 0; i < n; i++) { pthread_t t; pthread_create(&t, NULL, worker, NULL); }
}

bool pool_submit(void (*fn)(void *), void *arg) {
    return queue_try_put(&q, (task_t){ fn, arg });   /* false when full: the caller must cope */
}

Two numbers define its behaviour: the number of workers and the capacity of the queue.

How many threads?

It depends on what a task spends its time doing.

  • CPU-bound tasks (compressing, encoding, parsing, computing) run until they finish. A core can run one at a time, so the right number of threads is the number of cores. More than that adds context switches and cold caches and no throughput.
  • I/O-bound tasks (a database query, an HTTP call, a disk read) spend most of their time blocked, using no CPU. While one waits, its core is free, so you need more threads than cores to keep the cores busy.
threads ≈ cores × (1 + wait time / compute time)

8 cores, tasks that compute for 10 ms and never wait        8 × (1 + 0/10)   =   8 threads
8 cores, tasks that compute for 2 ms and wait for 18 ms     8 × (1 + 18/2)   =  80 threads

The formula gives the size at which the CPUs are just saturated. Below it, cores sit idle while tasks queue. Above it, threads queue for cores instead, which is the same waiting with extra overhead. Two cautions. First, measure the ratio; don't guess it. Second, the pool's size is also the number of simultaneous calls it can make to whatever the tasks wait on, and that system may have a much lower limit than your CPUs do.

When a program has both kinds of work, give each its own pool. If slow I/O tasks share a pool with quick CPU tasks, a few stuck calls occupy every worker and the quick tasks wait behind them. Separate pools, sometimes called bulkheads, keep one kind of trouble from sinking everything.

A steady-state model, not a measurement: tasks are identical, queueing delay uses a standard approximation, and each ready thread beyond the four cores costs a little throughput in switching. "Latency" is the average time from submitting a task to its completion.

Things to notice. For the I/O-bound task, each thread handles 50 tasks a second, so 8 threads manage 400 while the CPUs sit at 20%; you need about 30 threads for 1,500 a second, and throughput stops rising at 40, where all four cores are busy. For CPU-bound work the limit is 400 a second at 4 threads, and more threads make it slightly worse, never better. Push the arrival rate past capacity: with a queue of 100 the latency settles at a high but fixed value and the excess is rejected; with an unbounded queue nothing is rejected and the wait grows every second without limit.

The queue, and what to do when it is full

The queue absorbs short bursts. It can't absorb a sustained overload: if tasks arrive faster than the pool finishes them, any queue only delays the moment of truth, and an unbounded one hides it until memory runs out. Chapter 21's rule applies: bound the queue, and decide in advance what happens at the limit.

When the queue is fullEffectSuits
Block the submitterBackpressure: the producer slows to the pool's pacePipelines, batch jobs
Reject with an errorThe caller can retry later, try elsewhere, or tell the user "busy" (HTTP 503)Request-serving systems. Fast failure beats a slow timeout
Run it in the caller's threadThe submitter is kept busy doing the task, so it submits lessA simple self-regulating fallback
Drop the new task, or the oldest queued oneWork is lost on purposeMetrics, sampling, anything where fresh matters more than complete

These four are the built-in rejection policies of Java's ThreadPoolExecutor, and every pool has some equivalent. Watch the queue's length in production. A queue that is usually empty means the pool has headroom; one that is usually full means every task is paying the maximum wait, and the pool or what it calls is the bottleneck.

🐘
A smaller database connection pool can be fifty times faster

A database connection pool is a thread pool seen from the other side: its size is the number of queries the database is asked to run at once. The instinct under load is to raise it. The documentation for HikariCP, a widely used Java connection pool, describes a demonstration by Oracle's performance group that shows why that is wrong. An application was driven by thousands of concurrent users against a pool of 2,048 connections. The database was swamped: far more active sessions than cores, all contending for CPU, locks and disk, with response times around 100 ms. Reducing the pool to 96 connections, with nothing else changed, cut response times to about 2 ms. Requests now waited briefly in the application's queue for a connection, and then ran on a database that wasn't thrashing. It is this chapter's formula applied to someone else's CPUs: the useful number of concurrent queries is set by the database's cores and disks, and HikariCP's guide suggests starting near twice the core count plus the number of disks. Beyond that, threads don't add capacity. They only move the queue to a place where waiting is more expensive.

Work stealing

One shared queue has two problems on a many-core machine. Every worker locks it for every task, so the queue becomes the contended lock of Chapter 18. And tasks land on whichever core is free, far from the data they need.

Work stealing gives each worker its own double-ended queue (a deque). A worker pushes the tasks it creates onto the bottom of its own deque and takes its next task from the bottom as well: last in, first out, so it works on what it touched most recently, with the data still in its cache. Only when its deque is empty does it become a thief, and takes a task from the top of another worker's deque, the oldest task there.

The design suits tasks that split into subtasks, which is how parallel sorts, searches and build systems are written. Old tasks near the top tend to be large pieces of the problem, so one steal moves a lot of work and steals are rare. Idle workers do the balancing; busy ones pay almost nothing. The idea comes from the Cilk language of the 1990s and now runs underneath Java's ForkJoinPool and parallel streams, the Go scheduler, Rust's Tokio and Rayon, and .NET's task library.

⚠️
Common mistakes
  • An unbounded queue. Overload becomes rising latency and then an out-of-memory kill, instead of a clear "busy" signal.
  • Sizing by guesswork. "200 threads to be safe" for CPU-bound work is 200 threads sharing 8 cores. Measure wait and compute time.
  • Blocking inside a pool sized for CPU work. A few blocked workers and the pool has no threads left. Give blocking work its own pool.
  • A task that waits for another task in the same pool. If all workers are waiting for subtasks that are stuck in the queue behind them, the pool has deadlocked itself.
  • Ignoring what the pool calls. A pool of 500 makes 500 simultaneous calls to a database that copes with 50.
  • Losing errors. An exception or failure in a pooled task has no caller waiting for it. Make sure results and errors go somewhere.

Interview drill

Explain it simply: How do you decide the size of a thread pool?

How a strong answer sounds
By what the tasks do. For CPU-bound tasks the right size is about the number of cores, because a core runs one thread at a time and extra threads only add context switches and cache misses. For tasks that block on I/O, each thread is idle most of the time, so I need more threads than cores to keep the CPUs busy: roughly cores times one plus the ratio of wait time to compute time. A task that computes for 2 ms and waits 18 ms on a database gives a factor of ten, so 80 threads on 8 cores. I'd get that ratio from measurement, not a guess. Then I'd check the other limits: memory for the stacks, and above all the capacity of what the tasks call, since the pool size is also the number of concurrent requests sent downstream. Finally I'd bound the queue and choose a rejection policy, then tune under realistic load while watching throughput, latency and queue depth.

Deeper: What is work stealing, and why does the owner take from one end of its deque and thieves from the other?

How a strong answer sounds
Work stealing is a scheduling scheme in which each worker thread has its own deque of tasks instead of all workers sharing one queue. A worker pushes new tasks to the bottom of its own deque and pops from the bottom, so it runs the most recently created task, whose data is likely still in its cache, and it does so with no contention, since no other thread normally touches that end. When its deque is empty it steals from the top of a randomly chosen victim's deque. Taking from the opposite end means the owner and a thief interfere only when the deque is down to its last item, so the common path needs no lock, and implementations such as the Chase–Lev deque use a single CAS for steals. Stealing the oldest task also tends to take the largest piece of work in a divide-and-conquer computation, so one steal keeps the thief busy for a while and the number of steals stays small. The result is good locality, low contention and automatic load balancing driven by idle threads.

🧠 Key takeaways

  • A thread pool reuses a fixed set of workers fed by a queue; it limits concurrency and gives a place to apply backpressure.
  • CPU-bound work: threads ≈ cores. I/O-bound work: threads ≈ cores × (1 + wait/compute).
  • More threads than that add switching, memory and downstream load, not throughput.
  • Bound the queue and choose what happens when it is full: block, reject, run in the caller, or drop.
  • Work stealing gives each worker its own deque: owners work LIFO at one end, idle workers steal the oldest task from the other.
  • Keep blocking work and CPU work in separate pools.

Check your understanding

A service on an 8-core machine runs CPU-bound image resizing in a pool of 200 threads. What is the likely effect compared with a pool of 8?

Eight cores run eight CPU-bound threads at a time. The other 192 only wait for a core and make every switch more expensive.

On 4 cores, each task computes for 5 ms and waits on the network for 45 ms. Roughly what pool size keeps the CPUs busy?

cores × (1 + wait/compute) = 4 × (1 + 45/5) = 40. Each thread uses a core only a tenth of the time.

Tasks arrive at a pool faster than it can complete them, and the queue is unbounded. What happens?

An unbounded queue can't fix sustained overload. It hides it until latency is unusable or memory runs out.

In a work-stealing pool, where does a worker get its next task when its own deque is not empty?

Owners work last-in, first-out at the bottom, which keeps data cache-warm. Thieves take the oldest task from the top.

Why can raising a database connection pool from 100 to 2,000 make an overloaded application slower?

Useful concurrency is set by the database's hardware. Past that point, extra connections only add contention inside the database.
