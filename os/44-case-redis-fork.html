Case Study: Redis — One Thread and fork() Snapshots

Redis answers a hundred thousand requests a second from a single thread, and it saves a consistent copy of tens of gigabytes of changing data to disk without taking a lock. Both are operating-system ideas from earlier chapters, used very directly: an event loop on epoll for the first, and fork with copy-on-write for the second. The second also explains the failures Redis is best known for in production: the server that freezes for a moment whenever a snapshot starts, the one that suddenly refuses every write, and the one whose memory doubles until the kernel kills it. This case study covers how the design works and where its costs appear.

Why one thread is enough

Redis keeps all its data in memory, in ordinary data structures: a hash table of keys whose values are strings, lists, sets and so on. Looking up a key costs well under a microsecond of CPU time. Almost everything else spent on a request goes on reading it from a socket and writing the reply, which is system calls and the kernel's network stack. So the commands themselves are never the bottleneck, and running them one at a time on a single thread gives something valuable for free:

One thread runs every command (Redis)Many threads share the data (memcached and others)
LocksNone on the dataA lock, or lock-free code, round every structure
AtomicityEvery command is atomic, and so is a whole script or transaction. INCR can't lose an updatePer operation only, and only where the locking provides it

"Single-threaded" means one thread executes commands. There have always been a few helpers for jobs that would block, such as closing files, syncing the log and freeing large values, and they never touch the data set the main thread is using.

The event loop

The main thread is the loop of Chapter 29. In outline the whole server is this:

/* ae.c and server.c, much simplified */
while (!stop) {
    beforeSleep();                                   /* send replies that are ready; sync the log if due */
    int n = epoll_wait(epfd, events, MAX, ms_until_next_timer);
    for (int i = 0; i < n; i++) {
        if (events[i].events & EPOLLIN)
            readQueryFromClient(conn);               /* read, parse, RUN THE COMMAND, queue the reply */
        if (events[i].events & EPOLLOUT)
            sendReplyToClient(conn);
    }
    processTimeEvents();                             /* 10 times a second: expire keys, check on a snapshot child */
}

The command runs to completion inside the loop, between one epoll_wait and the next. That is the source of the atomicity, and of the one rule every Redis user learns sooner or later: a command that takes a second stops the server for a second.

BGSAVE: fork and copy-on-write

Data in memory is lost when the process stops, so Redis periodically writes all of it to a file, dump.rdb. That poses a hard problem. Writing 24 GB takes minutes. The file must be a consistent picture of one instant, the server has to keep accepting writes the whole time, and there's only one thread and no locks.

The answer is one system call. fork creates a child whose memory is, logically, a copy of the parent's at that instant. Physically nothing is copied except the page tables (Chapter 30): both processes point at the same frames, now marked read-only. The child walks the data set and writes the file, seeing a frozen world. The parent goes on serving clients, and whenever it writes to a page for the first time, the kernel copies that one page for it. The operating system's virtual memory is being used as a snapshot mechanism.

/* rdb.c, simplified */
int rdbSaveBackground(char *filename) {
    pid_t child = fork();
    if (child == 0) {                        /* child: a frozen copy of everything */
        closeListeningSockets();
        int ok = rdbSave(filename);           /* write temp file, fsync, rename */
        _exit(ok ? 0 : 1);
    }
    if (child == -1) return C_ERR;            /* "Can't save in background: fork: Cannot allocate memory" */
    server.child_pid = child;                /* parent: carry on; the timer will call wait later */
    return C_OK;
}

Memory spikes and overcommit

The fork is cheap, and it has three costs, each controlled by something in the kernel.

  • The pause. Copying the page tables happens inside fork, on the main thread. A 24 GB process has about 48 MB of page-table entries, and copying them takes roughly 10 to 15 ms per gigabyte of data. Nothing is served during it.
  • The copies. Every page the parent writes to during the snapshot is duplicated. How much that comes to depends on how many different pages are touched before the child finishes.
  • The promise. At the moment of the fork the kernel has, in principle, promised both processes their own copy of everything. Whether it is willing to make that promise is the overcommit setting (Chapter 14).

A model: the child needs 10 s per gigabyte to write the file, each write lands on a random page, and 2 GB of the machine is kept for everything else. The overcommit heuristic here is the classic one, which refuses a fork when free memory is less than the parent's size. Recent kernels are more lenient, but Redis still asks for the setting to be 1.

Things to notice. At 24 GB and 2,000 writes a second the snapshot costs 1.8 GB of copies, 7% of the data, and a pause of about 0.3 s. Raise the writes tenfold and over half the data is copied. Now switch huge pages on at the lowest write rate: nearly the whole data set is copied, because a one-byte change to any key now duplicates 2 MiB instead of 4 KiB, and there are only 12,288 huge pages to hit. The fork itself gets much quicker, since the page tables are tiny, which is exactly why this trap is easy to walk into. Then try 44 GB. With the heuristic overcommit setting the fork is refused outright, and with it allowed, a heavy write load runs the machine out of memory part-way through. A write-heavy instance needs its data set to be well under half of RAM.

Compare the overcommit advice with Chapter 43. PostgreSQL asks for mode 2, strict accounting, because it would rather have an allocation fail cleanly than be killed. Redis asks for mode 1, because its design depends on the kernel agreeing to a fork whose worst case it could never honour. Neither is wrong. The right setting follows from how the program uses memory, which is a good reason to give each its own machine or container. Since version 6.2 Redis also switches transparent huge pages off for its own process where the system-wide setting is always.

When the fork does fail, the effect on clients is more dramatic than a missing backup. By default Redis then refuses all writes, on the reasoning that silently running without persistence is worse than stopping:

The same fork, twenty times slower

Redis's documentation on latency includes measurements of fork on different machines, and they explain a problem that plagued Redis on cloud servers in its early years. On physical hardware, and on VMware, forking took about 13 ms per gigabyte of data. On the Xen-based virtual machines that Amazon EC2 used at the time, the same call took 239 ms per gigabyte. Page-table updates on those instances had to go through the hypervisor (Chapter 33), and fork is millions of page-table updates. By those figures a 24 GB instance stops for a third of a second on bare metal and for nearly six seconds on such a VM, every time a snapshot begins, with every client timing out together. Nothing in Redis was different. The remedies people used were all about the fork: moving to instance types with hardware support for nested page tables, where the cost fell back to about 10 ms per gigabyte; splitting the data over several smaller instances so each fork was short; and taking snapshots only on a replica, so that the server answering clients never forks at all. That last arrangement is still common.

I/O threads in Redis 6 and later

If commands cost a microsecond and the socket work costs ten, the socket work is the place to add cores. Redis 6 (2020) added optional I/O threads that do exactly that and nothing more:

WorkWho does it
Waiting for ready sockets (epoll_wait)Main thread
Reading requests and parsing themI/O threads, in parallel, if io-threads-do-reads yes
Executing the commandsMain thread, one at a time, as before
Writing replies to socketsI/O threads, in parallel
Closing files, syncing the log, freeing big valuesBackground helper threads
Snapshots and log rewritesA forked child process

In each turn of the loop the main thread hands the ready sockets out to the I/O threads, waits for them to finish reading and parsing, runs every command itself, and then hands the replies back for writing. The data set is still touched by exactly one thread, so nothing about atomicity or locking changed. The gain is up to about double the throughput on a machine with spare cores, and it only helps when the network work really is the limit. A workload of slow commands gains nothing.

# redis.conf
io-threads 4                  # total, including the main thread; leave cores free for the kernel's network work
io-threads-do-reads yes       # reads and parsing too, not only writes

Projects that wanted more than that took other routes: KeyDB and Dragonfly run commands on many threads and pay for it with locking or with partitioned data, and Redis Cluster stays single-threaded and runs many processes with the keys divided among them.

⚠️
Common mistakes
  • Running slow commands on a live server. KEYS, huge range reads, deleting an enormous key, long scripts: each stops every client for its whole duration.
  • Sizing the machine to the data set. A snapshot can need a large fraction of the data again. Leave that headroom, or snapshot on a replica.
  • Leaving transparent huge pages on always. Faster forks, but each first write copies 2 MiB and memory can double.
  • Ignoring the overcommit warning. The first sign is usually the MISCONF error, with all writes refused.
  • Expecting I/O threads to speed up commands. They parallelise socket reads and writes only.
  • Treating Redis as durable by default. With snapshots alone, a crash loses everything since the last one.

Interview drill

Explain it simply: Redis is single-threaded. Why is it still fast, and what is the downside?

How a strong answer sounds
All the data is in memory, so a command is a few memory accesses, well under a microsecond. Most of the time per request is network I/O, and Redis handles that with an event loop on epoll: one thread waits for whichever sockets are ready, reads the requests, runs each command to completion and writes the replies. With one thread running commands there are no locks on the data and no context switches between workers, and every command is atomic, which keeps the code simple and the per-request overhead very low. A single thread manages on the order of a hundred thousand simple requests a second, more with pipelining. The downsides are that it can use only one core for command execution, so you scale by running several instances and sharding, and that any slow command blocks every other client for its whole duration. Since Redis 6, extra threads can do the socket reading and writing, but commands still run on the main thread.

Deeper: How does Redis write a consistent snapshot while still accepting writes, and what can go wrong on a large instance?

How a strong answer sounds
It calls fork. The child gets a copy-on-write view of the parent's memory as it was at that instant, iterates over the data set and writes it to a temporary file, syncs it and renames it over the old snapshot. The parent keeps serving; when it modifies a page, the kernel copies that page first, so the child's view never changes. Three things go wrong at scale. First, fork copies the page tables on the main thread, roughly 10 ms per gigabyte, so a large instance pauses for hundreds of milliseconds, and much longer on some virtual machines. Second, memory: every page written during the snapshot is duplicated, so a write-heavy instance can need a large part of its data set again, and with transparent huge pages each write copies 2 MiB so usage can double. If the machine has no headroom the OOM killer steps in. Third, with vm.overcommit_memory at 0 the kernel may refuse the fork, and Redis then rejects writes with a MISCONF error. The mitigations are to set overcommit to 1, disable THP, keep the data set well under half of RAM for write-heavy loads, use smaller shards, and take snapshots on a replica.

🧠 Key takeaways

  • One thread runs every Redis command, so there are no locks on the data and every command is atomic. The limit is one core.
  • That thread is an epoll event loop. A slow command stops every client until it finishes.
  • A snapshot is a fork: the child sees a frozen copy-on-write image and writes it to disk while the parent keeps serving.
  • The costs are a pause while page tables are copied, and one copied page for each page the parent writes to during the snapshot.
  • Transparent huge pages make each of those copies 2 MiB, and the wrong overcommit setting makes the fork fail and Redis refuse writes.
  • I/O threads parallelise reading and writing sockets only. Commands still run on the main thread.

Check your understanding

Why can Redis run INCR counter from thousands of clients without a lock and never lose an update?

A command runs between one epoll_wait and the next with nothing else touching the data.

A client runs a command that takes two seconds on a production Redis. What do the other clients see?

The loop is not in epoll_wait while a command runs, so no other socket is read or written.

During a background save, the parent overwrites a value. Why doesn't the child's snapshot include the change?

Nothing is copied at fork time except page tables. Pages are copied one at a time, when the parent first writes to them.

Why can transparent huge pages make a snapshot use far more memory?

Copy-on-write works a page at a time. Bigger pages mean bigger copies and far fewer pages to hit.

With io-threads 4, which work is done in parallel?

The I/O threads take the socket work. The data set is still touched by one thread only.
