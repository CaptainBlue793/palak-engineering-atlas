The Heap: How malloc Works

The kernel hands out memory a page at a time, and getting it costs a system call. Programs want 24 bytes for a list node, a million times a second. malloc sits between the two: a library that takes big pieces from the kernel and deals them out in small ones, and takes them back with free. How it finds a block, what it writes next to your data, and why a server's memory use creeps upwards for days without a leak all come from a handful of ideas: chunk headers, free lists, fragmentation and size classes.

malloc is a library, not a system call

The kernel offers two ways to get memory, both in whole pages. brk moves the program break, the end of the heap region, up or down. mmap creates a fresh anonymous mapping anywhere in the address space. Neither is suitable for a 24-byte request: a system call costs hundreds of nanoseconds and the smallest unit is 4 KiB.

So the allocator, which is ordinary user-space code inside the C library, asks for memory in large pieces and manages it itself. Most malloc calls never enter the kernel. Watching glibc's allocator with strace shows the two sources:

$ strace -e trace=brk,mmap,munmap ./demo        # output trimmed to the calls malloc made
brk(NULL)                         = 0x55d0c8a4b000     # where does the heap end?
brk(0x55d0c8a6c000)               = 0x55d0c8a6c000     # first malloc(100): grow the heap by 132 KiB
                                                       # the next thousand small mallocs: no system calls
mmap(NULL, 1052672, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0x7f3a1c0ff000
                                                       # malloc(1 MiB): too big for the heap, gets its own mapping
munmap(0x7f3a1c0ff000, 1052672)   = 0                  # free() of that block returns it at once

glibc sends requests of 128 KiB and above straight to mmap (the threshold adapts upwards as the program runs) and serves everything smaller from the heap. The difference matters when memory is freed. A mapped block goes back to the kernel immediately. Heap memory mostly doesn't: free puts the block on a list for reuse, and the heap can only shrink from its top, by moving the break down. One long-lived allocation near the top keeps everything below it, however empty.

Inside a chunk

free(p) takes a pointer and no size. It knows how much to free because the allocator wrote the size just before the address it gave you. Every allocation is a chunk: a small header, then your bytes.

        chunk start            the pointer malloc returned
        ↓                      ↓
        ┌──────────────────────┬─────────────────────────────────────┐
        │ header: size + flags │ your data (at least what you asked) │  next chunk's header …
        └──────────────────────┴─────────────────────────────────────┘
          8–16 bytes             rounded up to a multiple of 16

Sizes are rounded up so that every pointer is aligned to 16 bytes, and there is a minimum chunk size. In glibc on 64-bit Linux, malloc(24) occupies a 32-byte chunk and malloc(25) a 48-byte one. When a chunk is free, the allocator reuses its data area for its own bookkeeping: the pointers that link it into a free list.

This is a complete allocator in forty lines. It is first fit with splitting, and it is the one the simulator below runs:

#include <stddef.h>
#include <unistd.h>

struct chunk {
    size_t size;              /* size of the whole chunk; the low bit means "in use" */
    size_t pad;               /* keeps the data 16-byte aligned */
    struct chunk *next;       /* next free chunk: lives in the data area, valid only while free */
};
#define HDR   16
#define MIN   32
#define ALIGN(n) (((n) + 15) & ~(size_t)15)

static struct chunk *free_list;

void *my_malloc(size_t n)
{
    size_t need = ALIGN(n + HDR);
    if (need < MIN) need = MIN;

    for (struct chunk **p = &free_list; *p; p = &(*p)->next) {    /* first fit */
        struct chunk *c = *p;
        if (c->size < need) continue;
        if (c->size - need >= MIN) {                 /* split: the tail stays on the list */
            struct chunk *rest = (struct chunk *)((char *)c + need);
            rest->size = c->size - need;
            rest->next = c->next;
            *p = rest;
            c->size = need;
        } else {
            *p = c->next;                            /* too little left to split: hand over all of it */
        }
        c->size |= 1;
        return (char *)c + HDR;                      /* the caller's pointer starts after the header */
    }

    struct chunk *c = sbrk(need);                    /* nothing fits: grow the heap */
    if (c == (void *)-1) return NULL;
    c->size = need | 1;
    return (char *)c + HDR;
}

void my_free(void *ptr)
{
    if (!ptr) return;
    struct chunk *c = (struct chunk *)((char *)ptr - HDR);   /* step back to the header */
    c->size &= ~(size_t)1;
    c->next = free_list;                             /* push on the free list */
    free_list = c;
}

It works, and it shows the two weaknesses that the rest of the chapter is about. Every malloc walks a list, which is slow. And my_free never joins neighbouring free chunks back together, so the heap gradually turns into crumbs.

Fragmentation

Memory is wasted in two different ways, and the fixes are different.

  • Internal fragmentation is waste inside a chunk: the header, and the padding between what you asked for and what you got. A program making millions of 17-byte allocations pays for 32 bytes each.
  • External fragmentation is waste between chunks: free memory split into holes that are each too small. The total is enough for a request and yet no single hole is.

The first defence against external fragmentation is coalescing: when a chunk is freed, merge it with a free neighbour on either side, so holes grow back together. Real allocators keep a size tag at both ends of a chunk so that free can find its neighbours in constant time.

The defence a C allocator can't use is compaction, sliding the live chunks together to squeeze the holes out. The program holds raw addresses to its blocks, in variables, in other heap objects and in registers, and the allocator can't find and update them. A chunk stays where it was put until it is freed. Runtimes with managed references, such as the JVM, Go's and .NET's, know where every pointer is, and several of their collectors do compact.

The allocator from the listing, plus optional coalescing: a 16-byte header, sizes rounded up to 16, a 32-byte minimum chunk. The number in each chunk is its full size, header included. "Internal waste" is headers plus padding. External fragmentation is the share of free memory that is not in the largest hole. The heap can grow to 1,024 bytes.

Things to notice. After Fragment it, 256 bytes are free and malloc(100) still fails: it needs 128 in one piece and the largest hole is 64. Coalescing can't help, because no two holes touch. With coalescing off, free two neighbouring chunks and the heap keeps two 64-byte holes where there should be one of 128, so the same request fails for no good reason. Best fit and worst fit differ most when holes of several sizes exist: free a few chunks of different sizes and allocate 16 bytes with each policy.

Size classes, thread caches and arenas

Production allocators avoid searching altogether. They round every small request up to one of a fixed set of size classes (16, 32, 48, 64 … bytes, getting sparser as they grow) and keep a separate free list, or bin, per class. Allocation is "take the first chunk from the right bin"; freeing is "put it back". Any chunk in a bin fits any request for that class, so there is no search and no splitting. The price is internal fragmentation, bounded by the gap between classes.

The second problem is threads. One heap shared by 64 threads needs a lock, and malloc is called so often that the lock becomes the bottleneck (Chapter 18). The fix is to give each thread memory of its own:

Behind the thread caches glibc keeps several arenas, independent heaps each with its own lock, up to eight per core, so threads rarely wait for one another. Google's tcmalloc and jemalloc (from FreeBSD, developed further at Facebook, and used by Redis and Firefox) are built on the same three layers: thread or per-CPU caches, shared structures per size class, and a page-level allocator underneath. They differ in how tightly they pack memory and how readily they return it to the kernel, and they are the usual choice for large multithreaded servers. The kernel uses the same ideas for its own objects: the slab allocator keeps caches of fixed-size objects such as task_struct on top of a page allocator.

The Ruby "memory leak" that was really arenas

Around 2017, many teams running multithreaded Ruby servers such as Puma and Sidekiq on Linux saw memory use climb to two or three times what the application needed. Heap profilers found no leak, and the Ruby objects were being freed. The cause was in glibc. With many threads allocating, glibc had created many arenas. Each arena keeps its own free chunks and can't lend them to the others, and each fragments separately, so memory freed in one sat unused while another grew. Two fixes spread through the community. Setting the environment variable MALLOC_ARENA_MAX=2 limits glibc to two arenas, trading some lock contention for much less waste; Heroku made that the default for new Ruby applications. The other was replacing the allocator with jemalloc, which needs no code change: LD_PRELOAD loads it in front of the C library. The same symptom, RSS that grows with no leak, is why Redis reports a fragmentation ratio and why "try another allocator" is a standard step when a long-running service's memory won't come down.

Heap bugs, seen from the allocator

P1 covered these mistakes from the programmer's side. Knowing the chunk layout explains why they fail so strangely: the allocator's bookkeeping lives in the same memory as your data, right next to it.

char *a = malloc(24);
char *b = malloc(24);
strcpy(a, "a string that is longer than 24 bytes");   /* overflow: runs into b's header */
free(b);                                           /* glibc reads a nonsense size and aborts here */

char *c = malloc(64);
free(c);
free(c);                                           /* double free: c is on the free list twice */
char *x = malloc(64), *y = malloc(64);              /* without checks, x == y: two owners of one chunk */
  • Overflow. Writing past the end of a overwrites the header of the next chunk. Nothing fails at the bad write. The crash comes later, inside some unrelated malloc or free that trusts the damaged size, with a message such as free(): invalid size or malloc(): corrupted top size.
  • Double free. The chunk is linked into a free list twice, so two later allocations return the same address and silently overwrite each other. Modern glibc catches the simple cases and aborts with free(): double free detected in tcache 2.
  • Use after free. A freed chunk's first bytes now hold the allocator's list pointers, and soon the chunk belongs to someone else. Reads return rubbish; writes corrupt the free list or another object.

These are also the raw material of many security exploits, which Chapter 36 returns to. In development, don't debug them by reading crashes. Build with AddressSanitizer, which surrounds every allocation with poisoned bytes and reports the faulty access itself:

$ gcc -g -fsanitize=address overflow.c -o overflow && ./overflow

Common mistakes
  • Calling malloc a system call. It is a library function. It makes a system call only when it needs more memory from the kernel.
  • Expecting free to lower RSS. Freed heap memory goes back to the allocator for reuse, not to the kernel, unless it was a large mapped block or sits at the very top of the heap.
  • Diagnosing a leak from RSS alone. Growth with no leaked objects is usually fragmentation or allocator caching. Compare the allocator's own statistics with RSS.
  • Assuming the crash is where the bug is. Heap corruption is detected long after the bad write, in innocent code. Use AddressSanitizer or Valgrind to find the write.
  • Ignoring allocation size. Millions of tiny allocations pay a header and rounding each. One array of structs is smaller and faster than a million nodes.
  • Forgetting the lock. Allocation-heavy code that scales badly across threads is often queuing on the allocator. Reuse buffers, or use an allocator built for threads.

Interview drill

Explain it simply: What happens when you call malloc(100)?

How a strong answer sounds
malloc is a user-space library function. It rounds the request up to a chunk size that includes a small header and alignment padding, here 112 bytes in glibc. It first looks in a per-thread cache of free chunks of that size, with no locking; if that is empty it takes a lock on an arena and looks in that arena's bins, splitting a larger free chunk if necessary. Only if nothing is available does it go to the kernel, extending the heap with brk, or using mmap for very large requests. It returns a pointer just past the header, which is how free later finds the size. The memory isn't physically allocated until I touch it: the kernel maps pages on first write, through page faults.

Deeper: A service's RSS grows for days, but heap profiling shows no leak. What could explain it and what would you check?

How a strong answer sounds
Fragmentation or allocator retention. The live data may be constant while the heap holds more and more free memory in pieces that can't be reused or returned: external fragmentation when allocation sizes vary over time, a long-lived chunk pinning the top of the heap so it can't shrink, or, with glibc and many threads, many arenas each keeping its own free memory. I'd compare the allocator's view with the kernel's: malloc_stats or mallinfo2 for bytes in use against bytes held, and RSS from /proc/PID/smaps. A big gap confirms it. Then I'd try limiting arenas with MALLOC_ARENA_MAX, calling malloc_trim to see how much is releasable, or running under jemalloc or tcmalloc, which keep size classes in separate regions and return unused pages on a timer. Longer term, reducing allocation churn with pooled or reused buffers treats the cause.

🧠 Key takeaways

  • malloc is a library that buys memory wholesale from the kernel (brk, mmap) and retails it in chunks.
  • Each chunk has a header with its size, which is how free works without being told a size.
  • Internal fragmentation is waste inside chunks; external fragmentation is free memory in holes too small to use.
  • Coalescing merges free neighbours. Compaction is impossible in C because blocks can't be moved.
  • Real allocators use size classes, per-thread caches and multiple arenas to be fast and to scale across threads.
  • Heap bugs corrupt the allocator's own data, so the crash arrives later and elsewhere; use AddressSanitizer.

Check your understanding

A program calls malloc(32) ten thousand times in a loop. About how many system calls does that cause?

malloc is a library function. It calls brk only when its heap runs out, typically in steps of 132 KiB or more.

A heap has 256 bytes free in four separate 64-byte holes. A request needing a 128-byte chunk fails. What is this called?

Enough memory is free in total, but not in one piece. Internal fragmentation is waste inside allocated chunks.

How does free(p) know how many bytes to release?

Each chunk begins with a header holding its size. That is also why overflowing a buffer into the next chunk's header breaks later calls.

Why can't a C allocator fix fragmentation by moving the live chunks together?

Compaction needs every pointer to a moved block to be updated. Managed runtimes know where their references are; C does not.

What is the main reason modern allocators give each thread its own cache of free chunks?

A single locked heap becomes a bottleneck with many threads. A thread-local cache serves the common case with no synchronisation at all.
