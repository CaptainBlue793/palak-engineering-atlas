Address Spaces & Virtual Memory

Print the address of a variable in two copies of the same program running side by side, and you may well see the same number in both, yet they hold different values. Each process lives in its own address space: a private range of addresses that the hardware translates, on every single memory access, to wherever the data really is in RAM. This chapter shows what a process's address space contains, why addresses are virtual at all, and the two simplest ways hardware has done the translation, base-and-bounds and segmentation, along with the fragmentation problem that pushed every modern OS to paging.

This is the shape of every 64-bit Linux process. The program's own code and globals come from the ELF file (P6), placed at a random base because of ASLR (Chapter 36). The heap grows upward from just above them. Shared libraries and large allocations are mapped in a separate region below the stack, which grows downward from near the top of user space. The upper half of the 64-bit space belongs to the kernel and is off limits in user mode.

Most of the space is unmapped. On x86-64 a process has 128 TiB of user addresses; a typical server touches a few hundred megabytes. Unmapped addresses aren't wasted RAM, they're just numbers that translate to nothing, and touching one causes a fault.

Why addresses are virtual

A virtual address is the number your program uses. A physical address is a location in the RAM chips. Between them sits the CPU's memory management unit (MMU), translating every instruction fetch, load and store. That indirection buys four things:

  • Isolation. A process can only reach what its own translation maps, so it can't read or corrupt another's memory or the kernel's (Chapter 1's panel, with protection switched off, showed the alternative).
  • Relocation. Every program can be linked as if it owned the address space; the OS places it wherever RAM is free, and can move it.
  • More than fits. Virtual memory can exceed RAM: pages can be fetched lazily or swapped out (Chapter 14).
  • Sharing. Two virtual addresses in two processes can map the same physical memory: one copy of libc's code for everyone, shared memory for IPC.

Base and bounds

The simplest MMU has two registers. Base holds where the process's memory starts in RAM; bounds holds its size. Every address is checked against bounds, then added to base: physical = base + virtual, provided virtual < bounds, otherwise fault. A context switch saves and reloads the two registers, and only the kernel may change them. It's fast and simple, and it has two serious problems. The whole address space must sit in one contiguous block of RAM, including the empty gap between heap and stack (internal fragmentation: reserved but unused). And as processes come and go, free RAM is chopped into holes, so a process that needs a big block may find no single hole large enough even though plenty is free in total (external fragmentation).

Segmentation

Segmentation generalises base-and-bounds to one pair per logical region: a segment for code, one for the heap, one for the stack. The top bits of a virtual address pick the segment, the rest is the offset within it. Now the empty gap between heap and stack costs nothing, segments can grow independently, and a code segment can be shared read-only between processes. The stack segment grows downward, so its offsets are counted back from the top. External fragmentation remains, because each segment still needs contiguous RAM.

The 32-bit wall: out of addresses, not out of RAM

A 32-bit process has 4 GiB of virtual addresses in total, and on classic 32-bit Linux the kernel kept the top 1 GiB, leaving 3 GiB for the program. Servers hit this wall long before running out of RAM. A 32-bit JVM needs its heap to be one contiguous range of virtual addresses, and once code, libraries, thread stacks and the native heap were placed, the largest free range was often only around 1.5 to 2.5 GB, so -Xmx3g simply failed to start, on machines with 16 GB of RAM. Memory-hungry databases on 32-bit systems resorted to tricks like mapping windows of a large buffer in and out. The move to 64-bit gave each process 128 TiB of user space, which is why virtual address space is almost never the limit today and physical memory is. Keep the two apart: "out of memory" can mean either.

⚠️
Common mistakes
  • Treating a printed pointer as a physical address. Every address a user program sees is virtual.
  • Equating virtual size with memory use. VSZ in ps counts reserved address space; RSS counts what's actually in RAM.
  • Thinking virtual memory means swapping. Translation and protection are the main point; swap is one optional feature built on it.
  • Mixing up internal and external fragmentation. Internal: waste inside an allocated block. External: free space split into holes too small to use.
  • Forgetting the stack grows down when computing addresses or reading /proc/<pid>/maps.

Interview drill

Explain it simply: Why do operating systems use virtual memory?

How a strong answer sounds
So every process gets its own private address space that the hardware translates to physical memory on each access. That gives isolation (a process can only reach memory its own mapping allows, so bugs and attacks can't cross between processes or into the kernel), relocation (programs are linked as if they own the address space and the OS places them anywhere in RAM), sharing (the same physical pages, like library code, can appear in many processes), and the ability to use more virtual memory than physical RAM by loading pages lazily or swapping. The cost is the translation itself, which the TLB makes cheap.

Deeper: Why did segmentation lose to paging?

How a strong answer sounds
Segments are variable-sized and each must be contiguous in physical memory, so as segments are created, grown and freed, physical memory fragments into holes; a segment that needs to grow may have to be copied elsewhere, and allocation needs a best-fit search with compaction now and then. Paging splits everything into fixed-size pages that can go in any free frame, which eliminates external fragmentation, makes growth trivial, and allows fine-grained sharing and protection per page. The price, page tables and translation lookups, became acceptable with multi-level tables and TLBs. On x86-64, segmentation survives only vestigially, mainly the FS and GS bases used for thread-local storage.

🧠 Key takeaways

  • A process sees code, data, heap (up), mmap region, stack (down) and a kernel half it can't touch; most of the space is unmapped.
  • The MMU translates every virtual address; the mapping changes on each context switch between processes.
  • Virtual addresses give isolation, relocation, sharing and the option of using more than RAM.
  • Base and bounds: physical = base + virtual if virtual < bounds. Simple, but wastes the heap–stack gap and fragments RAM.
  • Segmentation: a base/limit per region; cheaper gaps and sharing, still external fragmentation. Paging fixes that.

Check your understanding

With base = 0x4000 and bounds = 0x4000, what physical address does virtual 0x1234 map to?

0x1234 < 0x4000, so it's in bounds; physical = 0x4000 + 0x1234 = 0x5234.

Two processes print the address of the same global variable and see the same number. Why don't they share the variable?

Identical virtual addresses in different address spaces are unrelated unless the OS deliberately maps them to the same frame.

Total free RAM is 28 KiB, but a request for one contiguous 20 KiB block fails. What is this called?

Variable-sized contiguous allocation (base-and-bounds, segmentation) suffers it. Paging avoids it.

What does ps's RSS column measure, as opposed to VSZ?

VSZ counts every mapped virtual range; RSS counts resident pages. A process can have a huge VSZ and a small RSS.

What problem does segmentation solve that base-and-bounds doesn't?

With a base/limit per region, only the regions themselves need RAM. Each still needs contiguous memory, so external fragmentation remains.
