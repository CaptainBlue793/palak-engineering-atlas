IPC: Pipes, Signals & Shared Memory

Processes are isolated by design (Chapter 1), so when they need to cooperate the kernel has to provide the channel. A shell pipeline streams bytes through a pipe. systemd and Kubernetes tell a server to shut down with a signal. PostgreSQL's backends share their buffer cache through shared memory. The Docker CLI talks to its daemon over a Unix domain socket. Each mechanism makes a different trade between simplicity, speed and safety, and each has a way of failing that catches people out: a pipe that blocks forever, a signal handler that deadlocks, shared memory with no lock.

  • Use pipes and FIFOs, and predict when readers and writers block, see end-of-file, or get SIGPIPE
  • Install a signal handler safely and explain what may run inside one
  • Share memory between processes with shm_open and mmap, and say what extra it needs
  • Explain what Unix domain sockets add, including passing file descriptors
  • Choose an IPC mechanism for a given job

Pipes and FIFOs

A pipe is a one-way byte stream through a buffer in the kernel. pipe(fds) returns two file descriptors: fds[0] to read from and fds[1] to write to. On its own that's useless (one process talking to itself), but descriptors survive fork(), so a parent creates the pipe, forks, and each side closes the end it doesn't use:

#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
	int fds[2];
	if (pipe(fds) < 0) { perror("pipe"); return 1; }
	pid_t pid = fork();
	if (pid < 0) { perror("fork"); return 1; }
	if (pid == 0) {                         /* child: the reader */
		close(fds[1]);                      /* MUST close the write end, or it never sees EOF */
		char buf[256];
		ssize_t n;
		while ((n = read(fds[0], buf, sizeof buf)) > 0)
			fwrite(buf, 1, (size_t)n, stdout);
		_exit(n < 0 ? 1 : 0);                 /* n == 0: every write end is closed: end of file */
	}
	close(fds[0]);                          /* parent: the writer */
	const char *msg = "job 17 done\njob 18 done\n";
	if (write(fds[1], msg, strlen(msg)) < 0) perror("write");
	close(fds[1]);                          /* signals EOF to the reader */
	waitpid(pid, NULL, 0);
	return 0;
}

Four rules cover almost every pipe bug. A read on an empty pipe blocks while any write end is open. A read returns 0 (end of file) only once every write end, in every process, is closed, which is why forgetting close(fds[1]) in the reader hangs it forever. A write to a full pipe (Linux's default capacity is 64 KiB) blocks until the reader makes room. And a write when no read end is open raises SIGPIPE, killing the writer by default; that's how yes | head -1 stops. A FIFO (mkfifo /tmp/jobs) is the same thing with a name in the file system, so unrelated processes can open it.

Signals

A signal is a tiny asynchronous message: just a number, delivered to a process by the kernel, another process (kill()) or the terminal. Each signal has a default action (terminate, terminate with a core dump, ignore, stop or continue), which a program can replace with a handler for all but two: SIGKILL and SIGSTOP can never be caught.

The danger is that a handler can run between any two instructions of your program, even in the middle of malloc while it holds the heap lock. If the handler then calls malloc or printf, it can deadlock or corrupt state. So a handler may only call async-signal-safe functions (a short list in man 7 signal-safety: write, _exit and a few dozen more). The robust pattern is to do nothing in the handler but set a flag, and let the main loop act on it:

#include <signal.h>

static volatile sig_atomic_t stopping = 0;          /* the only thing the handler touches */

static void on_term(int sig) { (void)sig; stopping = 1; }

int main(void) {
	struct sigaction sa = { .sa_handler = on_term };    /* sigaction, not signal(): portable semantics */
	sigemptyset(&sa.sa_mask);
	if (sigaction(SIGTERM, &sa, NULL) < 0) { perror("sigaction"); return 1; }
	signal(SIGPIPE, SIG_IGN);                           /* get EPIPE from write() instead of dying */

	while (!stopping) {
		serve_one_request();                            /* blocking calls return EINTR when a signal lands */
	}
	drain_and_close();                                  /* graceful: finish in-flight work */
	return 0;
}

Shared memory

Pipes and sockets copy every byte twice: from the writer's buffer into the kernel, then out to the reader's. Shared memory avoids that: the same physical pages are mapped into both processes' address spaces, so a write by one is immediately visible to the other, with no system call per message. It's the fastest IPC there is, and the least safe, because the kernel no longer orders anything for you.

#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>

struct ring { _Atomic unsigned head, tail; char slots[1024][256]; };   /* a shared queue layout */

int fd = shm_open("/metrics-ring", O_CREAT | O_RDWR, 0600);   /* a named object in /dev/shm */
if (fd < 0) { perror("shm_open"); return 1; }
if (ftruncate(fd, sizeof(struct ring)) < 0) { perror("ftruncate"); return 1; }
struct ring *r = mmap(NULL, sizeof *r, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
if (r == MAP_FAILED) { perror("mmap"); return 1; }
close(fd);                     /* the mapping stays valid */
/* Another process does the same shm_open + mmap and sees the same bytes.
   Coordination (atomics, a futex or a process-shared mutex) is entirely up to you. */

Chapter 30 explains mmap and MAP_SHARED properly; Chapters 17 to 26 cover the synchronisation shared memory needs. PostgreSQL is the classic user: all backend processes map one shared buffer pool (Chapter 43).

Unix domain sockets

A Unix domain socket is a socket whose address is a path in the file system (or an abstract name) instead of an IP and port. It uses the familiar socket API, socket(AF_UNIX, SOCK_STREAM, 0), bind, listen, connect, but never touches the network stack, so it's faster than TCP on localhost. It is two-way, connection-oriented, and has two features no other IPC has: the server can ask the kernel who the client really is (SO_PEERCRED gives its PID, UID and GID), and processes can send open file descriptors to each other (SCM_RIGHTS). /var/run/docker.sock, PostgreSQL's local connections and systemd's socket activation all use them.

☸️
Kubernetes shutdown is a signal and a timer

When Kubernetes stops a pod, during a deploy or a node drain, the container runtime sends SIGTERM to the container's PID 1 and starts a clock: terminationGracePeriodSeconds, 30 seconds by default. If the process is still alive when it runs out, it gets SIGKILL. Services that handle SIGTERM properly stop accepting new work, finish in-flight requests and close their connection pools, so deploys cause no errors. Services that don't (or that run under a shell script as PID 1 that never forwards the signal, Chapter 3's PID 1 problem) are killed mid-request every single deploy, and users see a burst of 502s. The entire graceful-shutdown story of cloud platforms rests on the 1970s signal mechanism in this chapter.

⚠️
Common mistakes
  • Not closing unused pipe ends. A reader that still holds the write end never sees EOF; a writer holding the read end never gets SIGPIPE.
  • Calling printf, malloc or locks in a signal handler. Set a volatile sig_atomic_t flag instead.
  • Assuming every signal is delivered once. Two SIGCHLDs arriving together can merge into one; reap in a loop.
  • Dying on SIGPIPE in a server. A client that disconnects shouldn't kill the process: ignore the signal and handle EPIPE.
  • Shared memory without synchronisation. Two processes writing the same region need atomics or a process-shared lock, exactly like threads.
  • Forgetting EINTR. A handled signal interrupts blocking calls; retry them, or use SA_RESTART.
🎤
Interview drill

Explain it simply: A parent writes to a pipe and its child reads until end-of-file, but the child hangs forever after the last message. Why?

How a strong answer sounds
The child never closed its own copy of the write end. After fork() both processes hold both ends, and read returns 0 only when every write end in every process is closed. The parent closed its write end, but the child's inherited one keeps the pipe "open for writing", so the child's read blocks waiting for data that it would have to write itself. The fix is for each process to close the end it doesn't use immediately after the fork.

Deeper: When would you choose shared memory over a Unix domain socket, and what does it cost you?

How a strong answer sounds
When the data volume or message rate is high enough that copying through the kernel and a system call per message dominate: a buffer pool shared by database backends, a ring buffer of telemetry, video frames between processes. Shared memory gives zero copies and no syscalls on the fast path. The cost is that the kernel no longer provides ordering, boundaries or wake-ups: I have to design the data layout, use atomics or a process-shared mutex, handle a crashed peer leaving a lock held, and usually still use a socket, eventfd or futex to wake the other side instead of spinning. For control messages or moderate rates, a Unix socket is simpler and safer, and it can also check peer credentials and pass file descriptors.

🧠 Key takeaways

  • A pipe is a one-way kernel buffer (64 KiB by default): readers block when empty, writers when full.
  • EOF needs every write end closed; writing with no reader raises SIGPIPE (or EPIPE if ignored).
  • Signals are asynchronous numbers; handlers may only use async-signal-safe calls, so set a flag and act in the main loop.
  • SIGTERM asks politely, SIGKILL can't be caught; graceful shutdown depends on handling TERM.
  • Shared memory is zero-copy but needs your own synchronisation; Unix sockets add two-way streams, peer credentials and fd passing.

Check your understanding

A process writes 100 KiB into a pipe that nobody is reading yet. What happens on Linux with default settings?

Pipes provide backpressure: a full buffer blocks the writer (or returns EAGAIN with O_NONBLOCK).

When does read() on a pipe return 0?

An empty pipe with a writer still open blocks; only when no writer remains does read report end of file.

What is the safe thing to do inside a SIGTERM handler?

Handlers can interrupt non-reentrant code like malloc or printf. Do the real work in the main loop.

Which IPC mechanism avoids copying data through the kernel for every message?

With shared memory both processes access the same physical pages. Pipes and sockets copy in and out of a kernel buffer.

What can a Unix domain socket do that a pipe can't?

SCM_RIGHTS passes fds; SO_PEERCRED gives credentials. It's also two-way, unlike a pipe.
