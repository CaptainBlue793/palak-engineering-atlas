Lock-Free Data Structures (CAS, ABA)

A lock has one weakness that no tuning removes: if the thread holding it stops, everyone waiting stops too. It may have been preempted, or page-faulted, or killed. A lock-free data structure has no holder to wait for. Every thread works on its own copy of a small change and tries to install it with a single compare-and-swap; if another thread got there first, it tries again. Twelve lines give you a stack that many threads can use with no lock at all. They also contain one of the most famous bugs in concurrent programming, and fixing it leads to the real difficulty of the subject, which is not updating shared memory but knowing when it is safe to free it.

What "lock-free" promises

The terms describe progress guarantees, not implementation techniques. They say what is certain even if the scheduler behaves as badly as possible.

GuaranteePromiseCan one stalled thread block the rest?Example
BlockingNone, if a lock holder stopsYesAnything built on a mutex
Lock-freeAt every moment, some thread completes its operation in a bounded number of stepsNo. But one unlucky thread may retry for a long timeThe stack and counters in this chapter
Wait-freeEvery thread completes in a bounded number of stepsNo, and nobody starvesatomic_fetch_add on x86; reading under RCU

Notice what is absent: speed. Lock-free code is not automatically faster than a well-used mutex, and under heavy contention it is often slower, since every failed attempt is wasted work. People use it for the guarantee: no deadlock, no thread able to stall the others, safe in places where sleeping is forbidden, such as interrupt and signal handlers.

The CAS retry loop

Every lock-free update has the same shape. Read the current value. Work out the new value privately. Then compare-and-swap: "if it is still what I read, replace it". If the CAS fails, another thread changed it in between, so start again from the fresh value.

#include <stdatomic.h>

/* Raise *m to v if v is larger. There is no "atomic max" instruction, so build one. */
void store_max(atomic_long *m, long v)
{
    long cur = atomic_load(m);
    while (cur < v && !atomic_compare_exchange_weak(m, &cur, v))
        ;       /* a failed CAS writes the value it found into cur, so the loop re-tests with fresh data */
}

If the loop goes round again, it is because some other thread's CAS succeeded. That is the lock-free guarantee in miniature: one thread's failure is always another thread's progress. (_weak may fail occasionally for no reason on some CPUs, which is harmless inside a loop and cheaper than _strong.)

A lock-free stack

The simplest lock-free structure is a linked stack, published by R. Kent Treiber in 1986. The only shared variable is the pointer to the top node.

struct node { struct node *next; int value; };
static _Atomic(struct node *) top;

void push(struct node *n)
{
    n->next = atomic_load(&top);                            /* link the new node in front, privately */
    while (!atomic_compare_exchange_weak(&top, &n->next, n))
        ;                                                    /* top moved: n->next now holds the new top */
}

struct node *pop(void)
{
    struct node *old = atomic_load(&top);
    while (old && !atomic_compare_exchange_weak(&top, &old, old->next))
        ;                                                    /* "if top is still old, make it old->next" */
    return old;
}

push is correct. pop looks just as innocent and is broken in two ways, both hiding in the expression old->next:

  • It reads a node it doesn't own. Between loading old and reading old->next, another thread may have popped that node and freed it. This thread then reads freed memory.
  • The CAS checks the wrong thing. It verifies that top holds the same address as before. It concludes that nothing has changed. Those are not the same statement.

The ABA problem

A thread reads the value A from a shared variable and is interrupted. While it is away, other threads change the variable to B and then back to A. The first thread resumes, its CAS finds A as expected, and succeeds, although everything it worked out from the earlier state is now out of date. With pointers this happens naturally, because allocators hand out recently freed addresses again (Chapter 16): a different node, or the same node pushed back, at the same address.

Cause it yourself

The stack holds A, B and C. Thread 1 pops in three separate steps, and thread 2 can run whole operations in between. Use Play the ABA schedule, then let thread 1 finish. Then turn on version tags and do the same.

Thread 2's buttons each run a complete, correct operation. "Push back" pushes the node thread 2 has held longest; "free" releases the one it popped most recently. With version tags, every successful change to top also adds 1 to a counter stored beside the pointer, and the CAS compares both.

Things to notice. With a plain CAS the final step succeeds and leaves top pointing at freed memory: no crash, no error, a corrupted stack that fails later somewhere else. With a version tag the same CAS fails, because although the pointer is A again the version has moved on by three; thread 1 retries and pops correctly. Also try freeing A itself before thread 1's second step: thread 1 then reads next out of freed memory, and no tag can fix that.

Fix one: version tags

The CAS should fail whenever top has been modified, not merely when it holds a different address. So keep a counter next to the pointer, add one on every update, and compare-and-swap the pair as a unit.

struct tagged { struct node *ptr; uintptr_t version; };
static _Atomic(struct tagged) top;                 /* 16 bytes: needs a double-width CAS (cmpxchg16b) */

struct node *pop(void)
{
    struct tagged old = atomic_load(&top), new;
    do {
        if (!old.ptr) return NULL;
        new.ptr = old.ptr->next;                     /* still reads a node we don't own: see below */
        new.version = old.version + 1;
    } while (!atomic_compare_exchange_weak(&top, &old, new));
    return old.ptr;
}

On x86-64 the pair is swapped with lock cmpxchg16b. Where no double-width CAS exists, the tag is squeezed into bits of the pointer that are unused: the low bits, which alignment keeps at zero, or the top 16 bits of a 64-bit address. Storing array indexes with a counter instead of pointers is another common form.

Fix two, the hard one: when may a node be freed?

Tags stop the bad CAS. They do nothing about the other bug: a thread still dereferences old.ptr after another thread may have freed it. With a lock this can't happen, since nobody frees a node while someone is in the critical section. Without one, "is anyone still looking at this?" is a real question, called safe memory reclamation, and it is the hardest part of lock-free programming in a language without garbage collection.

ApproachIdeaCost
Never freeNodes go back to a private pool and are only ever reused as nodes, so a stale read sees a valid node, not garbage. Tags handle the ABAMemory is never returned; fine for fixed-size pools
Hazard pointersBefore dereferencing a node, a thread publishes its address in a per-thread "hazard" slot. Before freeing a node, a thread checks every slot, and defers the free if the node is listedA store and a barrier on every access; bounded garbage
Epochs / RCUReaders announce "I am reading" cheaply. A removed node is freed only after every reader that could have seen it has finishedAlmost free for readers; garbage can pile up if a reader stalls

RCU: how the Linux kernel reads without locking

The most widely used lock-free technique in practice is read-copy-update, added to Linux in 2002 by Paul McKenney and others and now used in well over ten thousand places in the kernel: the routing tables, the list of processes, the dentry cache that speeds up every path lookup. It suits data that is read constantly and changed rarely. A reader does no atomic operation on the data at all. It marks the start and end of its read, which in the kernel costs about as much as nothing, and follows pointers freely in between. A writer never modifies a structure that readers can see. It makes a copy, changes the copy, and swings one pointer to it with an atomic store, exactly the publish pattern of Chapter 25, so a reader sees the complete old version or the complete new one. The writer then waits for a grace period, the time it takes for every reader that was already running to finish, and only then frees the old version. No reader ever waits or retries, and reads scale perfectly with the number of cores, because readers write nothing shared. The price is paid by writers, who must copy and wait, and by memory, which holds two versions for a while.

/* Linux kernel style. Readers: */
rcu_read_lock();                                 /* not a lock: it marks "a reader is active here" */
struct config *c = rcu_dereference(current_config);
timeout = c->timeout;                            /* c stays valid until rcu_read_unlock() */
rcu_read_unlock();

/* A writer (writers still exclude each other with an ordinary lock): */
struct config *new = kmalloc(sizeof *new, GFP_KERNEL);
*new = *old;                                     /* read-copy ... */
new->timeout = 60;                               /* ... update the copy ... */
rcu_assign_pointer(current_config, new);         /* ... publish it atomically */
synchronize_rcu();                               /* wait until no reader can still hold old */
kfree(old);

Should you write lock-free code?

Usually not. The stack above is the easiest lock-free structure there is, and it took two subtle fixes to make correct. A queue is much harder, and a hash table harder again. Use the proven implementations: the concurrent collections of your language, a library such as liburcu or Folly, the kernel's primitives. Reach for them when you have measured lock contention you can't design away, or when you need the guarantee itself. And measure afterwards too: under heavy contention a lock-free structure's cache line bounces between cores just as a lock's would (Chapter 32), and the retries are pure waste.

⚠️
Common mistakes
  • Assuming lock-free means faster. It means no thread can block the others. Uncontended mutexes are often quicker and always simpler.
  • Treating "same pointer" as "nothing changed". That assumption is the ABA problem. Compare a version too, or make address reuse impossible.
  • Freeing a node as soon as it is unlinked. Another thread may be about to dereference it. You need a reclamation scheme.
  • Updating two variables with two CASes. Other threads can see the state between them. Either the invariant must hold at every step or both must be one atomic unit.
  • Testing only on x86 and only lightly loaded. These bugs need a preemption at one precise instruction. Use stress tests, ThreadSanitizer and a weakly ordered CPU.
  • Writing your own when a library exists. Published lock-free algorithms have had errors found in them years later.

Interview drill

Explain it simply: What is the ABA problem?

How a strong answer sounds
It is a flaw in using compare-and-swap to detect change. A thread reads a shared value A, computes something from the state it saw, and plans to CAS from A to a new value. Before it does, other threads change the value to B and then back to A. The CAS succeeds because the value matches, but the state the thread reasoned about is gone. The classic case is a lock-free stack: a thread reads top = A and A's next = B, then is preempted; others pop A and B, free B, and push A back. The CAS from A to B succeeds and installs a pointer to freed memory. It arises with pointers because allocators reuse addresses. Fixes are to pair the pointer with a version counter and CAS both, so any intervening update makes the CAS fail, or to prevent reuse while anyone may hold a reference, with hazard pointers, epoch-based reclamation or a garbage collector.

Deeper: When would you choose a lock-free structure over a mutex, and what would make you hesitate?

How a strong answer sounds
I'd choose it when I need the progress guarantee or when a measured lock is the bottleneck. The guarantee matters where a stalled lock holder is unacceptable: code that runs in signal or interrupt context and can't sleep, real-time paths that can't tolerate priority inversion, or systems where threads can be descheduled for long periods while others must keep going. For performance, read-mostly data is the strong case: RCU-style schemes let readers proceed with no shared writes at all, which scales across cores in a way a reader–writer lock can't. I'd hesitate for three reasons. Correctness is hard: ABA, memory reclamation and memory ordering all have to be right, and bugs appear only under rare interleavings. It is often not faster: with write contention, failed CAS attempts are wasted work and the cache line still bounces between cores. And maintenance: few engineers can review it. So my order is a mutex with short critical sections first, then partitioning or sharding to cut contention, then an existing, well-tested concurrent structure, and only then something written by hand.

🧠 Key takeaways

  • Lock-free means some thread always makes progress; wait-free means every thread does. Neither means fast.
  • The basic tool is the CAS retry loop: read, compute privately, swap if unchanged, otherwise retry.
  • A CAS checks that a value is the same, not that it was never changed. A to B to A fools it: the ABA problem.
  • A version tag swapped together with the pointer makes any intervening update visible.
  • The harder problem is reclamation: a node can't be freed while another thread might still dereference it.
  • Hazard pointers, epochs and RCU, or a garbage collector, solve reclamation. Use proven implementations.

Check your understanding

What does it mean for a data structure to be lock-free?

Lock-free guarantees system-wide progress. "Every thread" is the stronger wait-free guarantee, and speed is not part of either definition.

In a CAS retry loop, a thread's compare-and-swap fails. What does that tell it?

A failure means someone else succeeded. The loop reloads the current value and tries again.

Thread 1 reads top = A and A->next = B. Thread 2 then pops A, pops and frees B, and pushes A back. What does thread 1's CAS(top, A, B) do?

The CAS only compares addresses, and top holds A again. This is the ABA problem.

How does a version tag fix the ABA problem?

The pointer may return to A, but the version can't return to its old value, so the pair no longer matches.

In RCU, when is the old version of an updated structure freed?

Readers take no lock and hold no count, so the writer waits until all readers that were in progress have left their read sections.
