Classic Problems: Producer–Consumer, Readers–Writers, Dining Philosophers

Three small puzzles have been used to teach and test synchronisation for sixty years, and they survive because each one is the stripped-down form of something real. Producer–consumer is every queue between two stages of a program. Readers–writers is every shared structure that is read far more often than it changes. Dining philosophers is every operation that needs two locks. This chapter solves all three with the tools of Chapters 18 to 20, and spends as much time on the plausible solutions that fail as on the ones that work.

Producer–consumer: the bounded buffer

Some threads produce items and others consume them, at different and varying speeds. Between them sits a buffer of fixed capacity. Two rules: a consumer must wait when the buffer is empty, and a producer must wait when it is full. You have met this already without the name: a pipe (Chapter 9), a thread pool's job queue, a socket's send buffer.

#define CAP 8
static item_t buf[CAP];
static int head, tail, count;                    /* a ring buffer and how full it is */
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t not_full  = PTHREAD_COND_INITIALIZER;
static pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;

void put(item_t x)
{
    pthread_mutex_lock(&m);
    while (count == CAP)                         /* full: the producer is made to wait */
        pthread_cond_wait(&not_full, &m);
    buf[tail] = x; tail = (tail + 1) % CAP; count++;
    pthread_cond_signal(&not_empty);             /* a consumer may now proceed */
    pthread_mutex_unlock(&m);
}

item_t get(void)
{
    pthread_mutex_lock(&m);
    while (count == 0)                           /* empty: the consumer is made to wait */
        pthread_cond_wait(&not_empty, &m);
    item_t x = buf[head]; head = (head + 1) % CAP; count--;
    pthread_cond_signal(&not_full);              /* a producer may now proceed */
    pthread_mutex_unlock(&m);
    return x;
}

Every line is a rule from Chapter 19: state changed only under the mutex, waits in while, and one condition variable per condition so that a consumer's signal can only wake a producer and the other way round. Chapter 20 gave the same buffer with three semaphores.

The capacity is the important design decision. It is tempting to make the queue unbounded so that put never blocks. Then a producer that is faster than its consumer, even slightly, fills memory without limit, latency grows with the queue, and the process is eventually killed for it (Chapter 48). A bounded queue turns overload into something visible and controllable: the producer waits, or is told "busy" and can drop or reject the work. That is backpressure, and it is why queues in production systems have limits.

🚰
A Unix pipe is a bounded buffer in the kernel

When you run zcat access.log.gz | grep ERROR | head -5, each | is a bounded buffer with a producer on one side and a consumer on the other. On Linux a pipe holds 64 KiB by default. If zcat decompresses faster than grep can scan, its write() blocks as soon as the pipe is full, and it is put to sleep until grep has read some. If grep is the faster one, its read() blocks on an empty pipe. Neither program contains a line of synchronisation code; the kernel's pipe implementation is the put and get above. This is why a pipeline over a 50 GB file uses a few megabytes of memory: no stage can get more than 64 KiB ahead of the next. And when head has its five lines and exits, the next write into its pipe fails with SIGPIPE and the whole pipeline shuts down from the consumer's end backwards. TCP does the same between machines: the receive window is the free space in the receiver's buffer, and a sender that fills it must wait.

Readers–writers

Many threads read a shared structure and a few change it: a routing table, a configuration, a cache. Readers may share; a writer must be alone. Chapter 18 used a ready-made pthread_rwlock. Building one shows that the hard part isn't exclusion, it is policy: who goes next when both readers and a writer are waiting?

/* Readers–writers, version 1: readers are let in whenever readers are inside. */
static sem_t room;          /* starts at 1: held by one writer, or by the readers as a group */
static sem_t guard;         /* starts at 1: protects the reader count */
static int readers;

void read_lock(void) {
    sem_wait(&guard);
    if (++readers == 1) sem_wait(&room);      /* the first reader in takes the room */
    sem_post(&guard);
}
void read_unlock(void) {
    sem_wait(&guard);
    if (--readers == 0) sem_post(&room);      /* the last reader out gives it up */
    sem_post(&guard);
}
void write_lock(void)   { sem_wait(&room); }
void write_unlock(void) { sem_post(&room); }

This is correct and has a flaw you can see by reading it. A waiting writer needs readers to reach zero. If readers keep arriving so that there is always at least one inside, it never does, and the writer waits for ever. That is starvation: nothing is deadlocked, work is being done, and one thread makes no progress.

The fix is a "turnstile" that every thread passes through on the way in. A writer holds it while it waits, which stops new readers from entering. The readers already inside drain out, and the writer gets its turn.

/* Version 2: a waiting writer blocks new readers. Add: static sem_t turnstile, starting at 1. */
void read_lock(void) {
    sem_wait(&turnstile); sem_post(&turnstile);   /* pass through, unless a writer is holding it */
    sem_wait(&guard);
    if (++readers == 1) sem_wait(&room);
    sem_post(&guard);
}
void write_lock(void)   { sem_wait(&turnstile); sem_wait(&room); }
void write_unlock(void) { sem_post(&room); sem_post(&turnstile); }

Fairness has a price: readers that could have run together are made to queue behind a writer, so throughput drops. Which policy is right depends on the workload, which is why the libraries differ and why you should know which one yours implements.

Dining philosophers

Five philosophers sit round a table. Between each pair of neighbours lies one fork, five in all. A philosopher alternates between thinking and eating, and needs both the fork on the left and the fork on the right to eat. Dijkstra set the problem in 1965 as an exercise; it is the smallest example of threads that each need more than one lock.

#define N 5
static pthread_mutex_t fork_[N];

void *philosopher(void *arg)                /* the obvious solution, and it is wrong */
{
    int i = *(int *)arg, left = i, right = (i + 1) % N;
    for (;;) {
        think();
        pthread_mutex_lock(&fork_[left]);
        pthread_mutex_lock(&fork_[right]);   /* if all five are here at once, nobody ever gets past */
        eat();
        pthread_mutex_unlock(&fork_[right]);
        pthread_mutex_unlock(&fork_[left]);
    }
}

Mutual exclusion is fine: no fork is ever held by two philosophers. The failure is elsewhere. If all five pick up their left fork at about the same time, every fork is taken, and each philosopher waits for the right fork, which its neighbour holds and won't release until it has eaten. Each waits for the next, all the way round the table. Nobody can proceed, and nothing will ever change. That is a deadlock, and Chapter 22 studies it in general. Three fixes are standard:

/* Fix 1 in code: the only change is which fork is locked first. */
int first  = left < right ? left : right;
int second = left < right ? right : left;
pthread_mutex_lock(&fork_[first]);
pthread_mutex_lock(&fork_[second]);

Seat the philosophers

Click a philosopher to let it take its next step, or step all five together, which is the worst case. Deadlock the naive version first. Then try the same moves with each fix.

Five philosophers, five forks, four strategiesInteractive
Philosopher i's left fork is fork i; its right fork is fork i + 1, and philosopher 4's right fork is fork 0. A fork is drawn next to whoever holds it. Each step is one action: get hungry, pick up one fork, eat, or put the forks down. The random run uses a fixed sequence, so it is repeatable.

Things to notice. With "left, then right", two presses of Everyone steps at once deadlock the table: all hungry, then all holding a left fork and waiting for the right. With "lower fork first" the same presses leave philosopher 4 holding nothing, because its first fork is fork 0, so philosopher 3 gets both of its forks and the table keeps moving. With "four seats" one philosopher is kept back and the same thing happens. "Try, then back off" never blocks, but press Everyone steps at once repeatedly and watch the meal count stay at zero: that is livelock. Stepping philosophers one at a time breaks the symmetry, which is what a random delay does in real code.

⚠️
Common mistakes
  • An unbounded queue "to be safe". It hides overload until memory runs out. Bound it and decide what happens when it is full.
  • One condition variable for both "not full" and "not empty". A signal can wake the wrong side and stall everything.
  • Assuming a reader–writer lock is fair. Check the policy. The default on Linux can starve writers.
  • Taking two locks in whatever order is convenient. Two code paths that take the same pair in opposite orders will deadlock one day.
  • Fixing a deadlock with try-and-retry and no delay. Threads can retry in step for ever. Add randomised back-off.
  • Confusing starvation, deadlock and livelock. Starved: others progress, one doesn't. Deadlocked: none can move. Livelocked: all are busy and none progresses.

Interview drill

Explain it simply: Describe the dining philosophers problem and one way to solve it.

How a strong answer sounds
Five philosophers sit at a round table with one fork between each pair, and each needs both neighbouring forks to eat. If every philosopher picks up the left fork and then waits for the right one, they can all end up holding one fork and waiting for a neighbour, in a cycle, and nobody ever eats: a deadlock. It models threads that each need two locks. The simplest fix is to impose a global order on the forks and always take the lower-numbered one first. Four philosophers still go left then right, but the fifth, sitting between fork 4 and fork 0, reaches for fork 0 first, so it competes for a fork instead of holding one that someone else needs, and the cycle can't form. Alternatives are to let at most four philosophers try at once using a semaphore, or to use try-lock and release everything on failure, with random back-off to avoid livelock.

Deeper: Implement a bounded blocking queue. What would you change for production use?

How a strong answer sounds
A ring buffer with a count, one mutex, and two condition variables, not_full and not_empty. put locks, waits in a while loop while the count equals the capacity, stores the item, signals not_empty and unlocks; get is the mirror image and signals not_full. Two condition variables mean a signal always goes to a thread that can use it. For production I'd add three things. Timeouts or try variants, so a caller can give up and shed load instead of blocking indefinitely. A shutdown path: a closed flag checked in both loops, set under the mutex and followed by a broadcast on both conditions, so blocked threads wake and exit cleanly. And metrics on queue depth and wait time, because a queue that is always full or always empty says which side is the bottleneck. If profiling showed the single mutex was contended I'd look at a two-lock queue or a lock-free ring, but only then.

🧠 Key takeaways

  • A bounded buffer blocks producers when full and consumers when empty: a mutex, two condition variables, waits in while loops.
  • Bounding the queue gives backpressure; an unbounded one turns overload into memory exhaustion.
  • A readers–writers lock is easy to make exclusive and hard to make fair: reader preference starves writers, writer preference starves readers.
  • The naive dining philosophers deadlocks when everyone holds one fork and waits for the next.
  • Taking locks in one global order prevents that deadlock at no run-time cost.
  • Try-and-back-off avoids deadlock but can livelock without a random delay.

Check your understanding

A producer calls put on a bounded buffer that is full. What should happen?

Blocking the producer is backpressure: it can't get ahead of the consumer by more than the buffer's capacity.

Why does the bounded buffer use two condition variables instead of one?

With one shared condition variable, signal may wake a thread that can't proceed while the one that could stays asleep.

A readers–writers lock admits a new reader whenever other readers are already inside. Under a constant stream of readers, what happens to a waiting writer?

Starvation, not deadlock: the readers are all making progress. Blocking new readers while a writer waits fixes it.

In the naive dining philosophers, every philosopher has picked up its left fork. Why can't anyone eat?

Every fork is held and every holder is waiting for another. Nothing can change that, so it is a deadlock.

Which change prevents that deadlock without adding any new lock or semaphore?

A single global order means the circle can't close. "Right first" for everyone is just the mirror image and deadlocks the same way.
