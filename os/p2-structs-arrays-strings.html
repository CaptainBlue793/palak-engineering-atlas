Structs, Arrays & Strings in C

The kernel describes everything with structs: a process is a struct task_struct, an open file is a struct file, a network address is a struct sockaddr_in. Buffers are arrays, and every path and command line is a C string. This chapter shows how those three things sit in memory, byte by byte, because that layout explains real behaviour: why reordering two fields can save gigabytes, why an array "forgets" its length when you pass it, and why one missing zero byte has caused some of the worst security bugs on record.

Structs group fields at fixed offsets

A struct is a block of memory with named fields at fixed offsets from its start. Here is a simplified record a server might keep per connection:

#include <stdint.h>
#include <stddef.h>

struct conn {
	int      fd;          /* socket file descriptor */
	char     state;       /* 'R' reading, 'W' writing, 'C' closing */
	uint64_t bytes_in;    /* fixed-width: exactly 64 bits everywhere */
	char     tls;         /* 1 if encrypted */
};

struct conn c = { .fd = 7, .state = 'R' };   /* designated initialisers; the rest is zeroed */
c.bytes_in += 512;                            /* "." on a struct */

struct conn *p = &c;
p->bytes_in += 512;                           /* "->" on a pointer: same as (*p).bytes_in */

printf("sizeof=%zu offsetof(bytes_in)=%zu\n", sizeof(struct conn), offsetof(struct conn, bytes_in));
/* prints: sizeof=24 offsetof(bytes_in)=8 */

The fields add up to 4 + 1 + 8 + 1 = 14 bytes, yet the struct is 24. The other 10 bytes are padding, and they are there because of a hardware rule.

Padding and alignment

CPUs load data fastest when a value of size n sits at an address that is a multiple of n: an 8-byte integer at an address divisible by 8 can never straddle two cache lines (P4). Some architectures fault on misaligned loads; x86 tolerates them but may be slower, and atomic operations need alignment everywhere. So the C compiler follows two rules on x86-64 Linux:

  1. Each field starts at an offset that is a multiple of its alignment (for the basic types, equal to its size: char 1, short 2, int 4, long, pointers and double 8). If the next free offset isn't, it inserts padding bytes.
  2. The whole struct's size is rounded up to a multiple of its largest field alignment, so that every element of an array of these structs is aligned too.

For struct conn: fd at 0–3, state at 4, then 3 bytes of padding so bytes_in can start at 8, then tls at 16, then 7 bytes of tail padding to reach 24. Put the big fields first and the same data fits in 16 bytes. Try it:

Padding is invisible in source code but very visible in memory bills. The Linux kernel keeps one struct page (64 bytes) for every 4 KiB page of RAM, about 1.6% of memory, and kernel developers fight over single bytes in it for exactly this reason. Tools like pahole print every hole in a struct. When the layout must match an external format byte for byte (a network header, a file format) you can ask for no padding with __attribute__((packed)), at the cost of slower or even faulting misaligned access on some CPUs.

Arrays and pointer arithmetic

An array is a run of elements of the same type, back to back with no gaps between them. The name of an array, used in an expression, turns into a pointer to its first element, and indexing is defined as pointer arithmetic: a[i] means *(a + i). Adding 1 to a pointer advances it by the size of what it points to, not by one byte:

uint32_t ports[4] = { 80, 443, 8080, 9090 };
uint32_t *p = ports;            /* same as &ports[0] */
printf("%u\n", *(p + 2));       /* 8080: p + 2 is 8 bytes past ports, not 2 */
printf("%u\n", p[3]);           /* 9090: p[3] is *(p + 3) */

void dump(uint32_t *a, size_t n) {   /* the array "decays": dump only gets a pointer */
	printf("%zu\n", sizeof a);           /* 8, the size of a pointer, NOT 16 */
	for (size_t i = 0; i < n; i++) printf("%u ", a[i]);
}
dump(ports, sizeof ports / sizeof ports[0]);   /* so the length travels separately */

Strings end in a zero byte

C has no string type. A string is a char array whose end is marked by a byte with value 0 (written '\0' and called NUL). "GET" occupies four bytes: 'G' 'E' 'T' '\0'. Every string function walks until it finds that zero, so strlen is O(n), and a missing terminator makes functions read on into whatever memory follows.

char path[16];
strcpy(path, user_input);                       /* BUG: no length limit at all */strncpy(path, user_input, sizeof path);         /* BUG: no '\0' if input is 16+ chars */snprintf(path, sizeof path, "%s", user_input);  /* OK: always terminates, truncates if needed */

size_t n = strlen(user_input);
if (n >= sizeof path) { errno = ENAMETOOLONG; return -1; }   /* better: reject, don't truncate */
memcpy(path, user_input, n + 1);                              /* copies the '\0' too */

Writing past the end of an array is a buffer overflow. On the stack, the bytes after a local buffer include saved registers and the function's return address, so an overflow can redirect execution when the function returns. That is how the 1988 Morris worm spread (through gets() in the fingerd daemon), and why gets was removed from the C standard in C11.

🩸
Heartbleed: trusting a length field

In 2014, OpenSSL's TLS heartbeat feature (CVE-2014-0160) received a small message containing a payload and a length field saying how long that payload was. The code allocated a reply and memcpy'd length bytes from the request without checking that the request was really that long. Send a 1-byte payload claiming to be 64 KiB, and the server copied back 64 KiB of whatever sat next to it in its heap: session cookies, passwords, sometimes private keys. It is an over-read rather than an overflow, but the root cause is the one this chapter keeps returning to: C buffers don't know their own length, so every length that crosses a trust boundary must be checked against the real buffer size. The fix was one bounds check.

Function pointers: how C does interfaces

A function's code lives at an address too, and a function pointer stores it. A struct full of function pointers is C's version of an interface: different implementations fill in the same slots. The kernel's struct file_operations is the famous example. When you call read() on a file descriptor, the kernel neither knows nor cares whether it is an ext4 file, a pipe or a socket; it calls whatever function that file's operations table holds:

/* Simplified from include/linux/fs.h */
struct file_operations {
	ssize_t (*read)(struct file *f, char *buf, size_t len, loff_t *pos);
	ssize_t (*write)(struct file *f, const char *buf, size_t len, loff_t *pos);
	int     (*release)(struct inode *ino, struct file *f);
};

static const struct file_operations pipe_fops = {
	.read    = pipe_read,      /* each kind of file fills in its own functions */
	.write   = pipe_write,
	.release = pipe_release,
};

/* Somewhere inside the read() system call: */
ssize_t n = f->f_op->read(f, buf, len, &f->f_pos);   /* one indirect call, any file type */

You use the same idea in user space with qsort, which takes a comparison function pointer, and with callbacks passed to event loops (Chapter 29).

⚠️
Common mistakes
  • Assuming sizeof(struct) is the sum of the fields. Padding makes it larger; use sizeof and offsetof, never hand-computed numbers.
  • Using sizeof on an array parameter. Inside the function it is a pointer, so you get 8. Pass the length.
  • Forgetting the byte for '\0'. A 16-character name needs 17 bytes.
  • strcpy, strcat, sprintf, gets. No bounds. Use snprintf or memcpy with a checked length.
  • Trusting strncpy to terminate. It doesn't when the source is too long.
  • memcpying a struct to disk or the network. Padding bytes and byte order (P5) differ between machines; serialise field by field.

Interview drill

Explain it simply: What is sizeof(struct { char a; int b; char c; }) on x86-64, and how would you make it smaller?

How a strong answer sounds
12 bytes. a is at offset 0, then 3 bytes of padding so the 4-byte int b starts at offset 4, then c at 8, then 3 bytes of tail padding so the size is a multiple of the largest alignment, 4. Reordering to int b; char a; char c; gives 4 + 1 + 1 + 2 tail padding = 8 bytes. In general, ordering fields from largest alignment to smallest minimises padding. packed would give 6 but makes b misaligned, which is slower or illegal on some CPUs.

Deeper: How does the Linux kernel let read() work the same way on files, pipes and sockets?

How a strong answer sounds
Every open file is a struct file that points to a struct file_operations, a table of function pointers chosen when the file was opened: ext4 fills it with its file functions, the pipe code with pipe_read/pipe_write, the socket layer with its own. The read() system call looks up the descriptor in the process's fd table and calls f->f_op->read(...), an indirect call. It's runtime polymorphism built from a struct of function pointers, which is how C code expresses interfaces.

🧠 Key takeaways

  • A struct is fields at fixed offsets; . accesses a struct, -> a struct through a pointer.
  • Each field is aligned to its size and the struct is padded to its largest alignment; order fields large to small to save space.
  • a[i] is *(a + i); pointer arithmetic moves in units of the pointed-to type.
  • Arrays decay to pointers when passed, so C APIs take a pointer and a length.
  • C strings end in '\0'; unbounded copies cause overflows and over-reads like Heartbleed.
  • A struct of function pointers is an interface; the kernel's file_operations makes "everything is a file" work.

Check your understanding

On x86-64, what is sizeof(struct { char a; double d; char b; })?

a at 0, 7 bytes padding, d at 8–15, b at 16, then 7 bytes of tail padding to a multiple of 8: 24. Putting d first gives 16.

With uint32_t *p holding address 0x1000, what address does p + 3 hold?

Adding n to a pointer advances it by n elements, each 4 bytes here: 0x1000 + 12 = 0x100C.

Inside void f(char buf[64]), what is sizeof buf?

Array parameters decay to pointers; the 64 is ignored. That's why C functions take an explicit length.

What made Heartbleed possible?

The heartbeat handler trusted the peer's length field and copied up to 64 KiB of adjacent heap memory into the reply. One bounds check fixed it.

How does the kernel's read() system call reach the right code for a pipe versus an ext4 file?

f->f_op->read(...) is an indirect call through a struct of function pointers: the kernel's way of expressing an interface in C.
