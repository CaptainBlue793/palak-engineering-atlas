Containers: Namespaces & cgroups

The Linux kernel has no object called a container. Search its source and you won't find one. What it has is ordinary processes, plus two families of features that can be switched on for any process. Namespaces change what a process can see: its own process list, its own network interfaces, its own file tree. Control groups limit what it can use: this much memory, this much CPU. A container is the name we give to a process with most of those switched on, started from a packaged file system. Because that is all it is, you can build one by hand in a few commands, and knowing how explains how containers start in milliseconds, why they aren't virtual machines, and what happens when one hits its limit.

A container is a process

Start a container and look at the host:

$ docker run -d --name web nginx
$ ps -ef | grep nginx                        # on the host, not in the container
root      41872  41851  nginx: master process nginx -g daemon off;
systemd+  41925  41872  nginx: worker process
$ docker exec web ps -ef                     # the same processes, seen from inside
root          1      0  nginx: master process nginx -g daemon off;
nginx        29      1  nginx: worker process

They are the same two processes, running on the host's kernel, scheduled by the host's scheduler, making system calls to the host's kernel. Inside, the master believes it is PID 1 and that nothing else exists. Nothing has been virtualized. The kernel is simply giving this process different answers to the questions it asks.

Namespaces: what a process can see

Each kind of global resource the kernel manages can be split into separate instances called namespaces. A process belongs to one namespace of each kind and sees only what is in it.

NamespaceGives the process its own…So that…
PIDProcess numbers, starting again from 1It can't see, signal or inspect processes outside
MountTable of mounted file systemsIt can have a completely different /
NetworkInterfaces, addresses, routing table, firewall rules, portsTwo containers can both listen on port 80
UTSHostnameIt can be called web-1 whatever the host is called
IPCShared memory segments and message queuesIt can't attach to another container's shared memory
UserMapping of user and group IDsIt can be root (UID 0) inside while being an unprivileged user outside
CgroupView of the cgroup treeIt can't see how the host has organised its limits

Three system calls manage them: clone with CLONE_NEW… flags creates a child in new namespaces, unshare moves the calling process into new ones, and setns joins existing ones, which is how docker exec gets a shell "into" a running container. Here is a complete, if crude, container runtime:

#define _GNU_SOURCE
#include <sched.h>
#include <signal.h>
#include <unistd.h>
#include <sys/mount.h>
#include <sys/wait.h>

static int child(void *arg)
{
    sethostname("mybox", 5);                    /* UTS namespace: only we see this name */
    chroot("/srv/alpine"); chdir("/");           /* an unpacked image as our root (real runtimes use pivot_root) */
    mount("proc", "/proc", "proc", 0, NULL);    /* a /proc that describes our PID namespace */
    execl("/bin/sh", "sh", NULL);               /* this shell is PID 1 in here */
    return 1;
}

int main(void)
{
    static char stack[1 << 20];
    int flags = CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWNET | CLONE_NEWIPC | SIGCHLD;
    pid_t pid = clone(child, stack + sizeof stack, flags, NULL);    /* fork, into fresh namespaces */
    waitpid(pid, NULL, 0);
}
# The same thing from a shell:
# unshare --pid --fork --mount-proc --uts --net --ipc --mount chroot /srv/alpine /bin/sh
$ lsns -p 41872                               # which namespaces is a process in?

cgroups: what a process can use

A process in its own namespaces can still use every core and all the memory in the machine. Control groups put a budget on a group of processes. In cgroups v2 the interface is a file system: a directory is a group, files in it are settings and counters, and writing a PID into one file moves a process in.

# mkdir /sys/fs/cgroup/demo
# echo 100M           > /sys/fs/cgroup/demo/memory.max    # a hard ceiling on memory
# echo "50000 100000" > /sys/fs/cgroup/demo/cpu.max       # 50 ms of CPU in every 100 ms: half a core
# echo 64             > /sys/fs/cgroup/demo/pids.max      # at most 64 processes: no fork bombs
# echo $$             > /sys/fs/cgroup/demo/cgroup.procs  # put this shell, and its future children, inside
# cat /sys/fs/cgroup/demo/memory.current
2191360
ControllerMain settingsWhat happens at the limit
memorymemory.max (hard), memory.high (soft)The kernel reclaims pages belonging to the group, including its page cache. If that isn't enough, the OOM killer kills a process in that group (Chapter 48)
cpucpu.max (quota per period), cpu.weight (share under contention)The group is throttled: its threads aren't run again until the next period. Nothing is killed; requests just stall (Chapter 38)
pidspids.maxfork fails with EAGAIN
ioio.max (bytes or operations per second, per device)Reads and writes are delayed

docker run --memory 100m --cpus 0.5 and a Kubernetes pod's resources.limits do exactly this: they write those numbers into files like these.

The host has 16 GiB of RAM and 8 cores. The memory limit is 100 MiB and the CPU limit is half a core. The outputs are what the real commands would print, shortened.

Things to notice. Each switch changes the answer to one question and nothing else. Switch on the PID namespace alone and ps still lists every process on the host: ps reads /proc, and without a mount namespace that is still the host's /proc. A new network namespace has only a loopback interface, and it is down: connectivity has to be added. In a user namespace id says root, and the host sees an ordinary unprivileged user. Without the memory limit the process can take the whole machine; with it, the third allocation gets it killed, and nothing else on the host notices.

The file system: layers and overlays

A container needs a root file system with the program and its libraries: an image. Images are stacks of read-only layers, each a set of files added or changed by one build step. Copying an image for every container would be slow and wasteful, so the runtime uses a union file system, on Linux usually overlayfs, to present several directories as one.

# lowerdir: the read-only image layers, top first.  upperdir: this container's own changes.
# The last argument is the merged view, which the container sees as /.
# mount -t overlay overlay \
    -o lowerdir=/layers/app:/layers/python:/layers/debian,upperdir=/containers/c1/diff,workdir=/containers/c1/work \
    /containers/c1/merged
  • Reading a file finds it in the topmost layer that has it.
  • Writing to a file from a lower layer first copies the whole file up into the container's own layer. This is copy-on-write (Chapter 30) at the granularity of a file.
  • Deleting a lower-layer file puts a marker in the upper layer that hides it.

A hundred containers from one image share the same lower layers on disk and in the page cache. Starting a container creates an empty directory and makes one mount call, which is a large part of why it takes milliseconds. It is also why writes inside a container are slower than writes to a mounted volume, and why data in a container's own layer disappears with the container.

The security row is the one that matters most. A bug in the shared kernel is a way out of every container on the machine, so untrusted code is usually given something stronger: a microVM per container, as in Firecracker and Kata Containers (Chapter 33), or a user-space kernel that intercepts system calls, as in gVisor. ☕
The JVM that thought it had the whole machine

When Java services first moved into containers, many were killed within minutes of starting, with exit code 137 and nothing in their own logs. The limits were in cgroups, and the JVM had never heard of cgroups. On start-up it asked the kernel how much memory the machine had, through the usual interfaces, and those describe the host, because there is no memory namespace. On a 64 GB host with a 1 GB container limit, the JVM chose a default maximum heap of a quarter of 64 GB. The heap grew past 1 GB, the cgroup's limit was reached, and the kernel's OOM killer removed the process. CPU went wrong the same way: the JVM saw 32 cores and sized its garbage-collection and compiler thread pools for 32, inside a container allowed half a core, so those threads used up the quota and the application was throttled (Chapter 27). Java learned to read its cgroup limits in version 10 and in an update to Java 8, and other runtimes followed. The lesson stands for any software: /proc/meminfo and the CPU count describe the host. A program in a container has to read its limits from /sys/fs/cgroup, or be told them.

⚠️
Common mistakes
  • Calling a container a lightweight VM. There is no second kernel. It is a host process with a restricted view.
  • Trusting free or nproc inside a container. They report the host. Read the cgroup files.
  • Setting a memory limit below what the process plus its page cache needs. File I/O counts towards memory.max.
  • Assuming a CPU limit only slows things evenly. Throttling stops the whole group until the next period: latency spikes, not a gentle slowdown.
  • Running as root in a container without a user namespace. That UID 0 is the host's UID 0, held back only by other restrictions.
  • Storing data in the container's writable layer. It is slow, and it is deleted with the container. Use a volume.

Interview drill

Explain it simply: What is a container, at the level of the operating system?

How a strong answer sounds
A container is one or more ordinary Linux processes that the kernel has been told to isolate and limit. Isolation comes from namespaces: the process gets its own PID namespace, so it sees itself as PID 1 and can't see other processes; its own mount namespace with an image as its root file system; its own network namespace with separate interfaces and ports; and UTS, IPC and often user namespaces. Limits come from cgroups, which cap the memory, CPU, I/O and number of processes for the group. The root file system is typically an overlay of read-only image layers with a writable layer on top. There is no guest kernel and no hypervisor: the processes make system calls directly to the host kernel, which is why containers start in milliseconds and add almost no overhead, and also why their isolation is weaker than a VM's, since the shared kernel is the security boundary.

Deeper: A container has a memory limit of 512 MB and keeps being killed. How do you investigate?

How a strong answer sounds
First confirm it is the cgroup OOM killer: exit code 137, meaning SIGKILL, and a line in the host's kernel log saying "Memory cgroup out of memory: Killed process …", plus the oom_kill counter in the cgroup's memory.events. Then find out what the memory is: memory.stat in the cgroup splits it into anonymous memory, page cache, kernel memory and so on. If it is anonymous memory growing steadily, it is the application: a leak, or a runtime sized for the host instead of the limit, which is common with a JVM or anything that reads /proc/meminfo, so I'd set the heap explicitly or enable container awareness. If it is mostly file cache, the workload does heavy file I/O and the kernel should reclaim that before killing; a kill then suggests the cache is dirty or pinned, or the limit is simply too tight. I'd also check for many threads, each with its own stack and allocator arena. The fix is either to make the process fit, by capping its heap, caches and thread counts, or to raise the limit to what it really needs, with headroom, and alert on memory.current approaching it.

🧠 Key takeaways

  • A container is a normal process on the host kernel. Nothing is emulated or virtualized.
  • Namespaces restrict what it sees: PID, mount, network, UTS, IPC, user, cgroup.
  • cgroups limit what it uses. Exceeding memory gets a process in the group killed; exceeding CPU gets it throttled.
  • Images are read-only layers joined by an overlay file system, with a copy-on-write layer per container.
  • Containers share the host kernel, so they are lighter and less isolated than virtual machines.
  • Tools that read host-wide information see the host. Limits live in /sys/fs/cgroup.

Check your understanding

What is a Linux container, from the kernel's point of view?

The kernel knows only processes, namespaces and cgroups. "Container" is the name for a useful combination of them.

Two containers on one host both run a web server listening on port 80. Why don't they conflict?

A network namespace has its own addresses, routing table and ports. The host maps or routes traffic to each one.

A container with memory.max set to 256 MB tries to use 300 MB of anonymous memory. What happens?

Allocation succeeds as usual (overcommit). The limit is enforced when pages are touched, and the OOM killer acts inside the cgroup.

What does a CPU limit of half a core (cpu.max of "50000 100000") do to a container that wants more?

This is throttling. Work stalls completely for the rest of the period, which shows up as latency spikes.

Why is a container's isolation generally considered weaker than a virtual machine's?

A VM's boundary is a narrow virtual-hardware interface with its own kernel inside. A container's boundary is the entire system-call surface of a shared kernel.
