File Systems: Inodes, Directories & Blocks

A disk is a long row of numbered blocks, with no idea what a file is. A file system is the data structure that turns those blocks into named files in a tree of directories. Its central design decision surprises most people the first time: a file's name is not part of the file. The file is an inode, a small record of who owns it and where its data lives. Names sit in directories and merely point at inodes. Once you see that split, hard links, instant renames, "deleted" files that still fill the disk, and a disk that is "full" with gigabytes free all stop being mysteries.

A file is an inode plus data blocks

A file system divides the disk into fixed-size blocks, usually 4 KiB, and sets aside a few areas for its own bookkeeping. The layout of a classic Unix file system, which ext4 still follows in outline:

┌────────────┬──────────────┬──────────────┬─────────────────┬──────────────────────────────────┐
│ superblock │ block bitmap │ inode bitmap │   inode table   │           data blocks            │
└────────────┴──────────────┴──────────────┴─────────────────┴──────────────────────────────────┘
  sizes and    one bit per     one bit per    one fixed-size     file contents, and the contents
  counts for   data block:     inode:         record per file    of directories
  the whole    free or used    free or used
  file system

Every file, directory and symbolic link has exactly one inode (index node), identified by its number. The inode is the file's metadata:

$ stat notes.txt
  File: notes.txt
  Size: 9214          Blocks: 24         IO Block: 4096   regular file
Device: 259,2       Inode: 1311842     Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/     ana)   Gid: ( 1000/     ana)
Modify: 2026-10-06 09:12:40.730118826 +0530
Change: 2026-10-06 09:12:40.730118826 +0530

Type, size, owner, permissions, timestamps, a link count, and the location of the data blocks. Look for what is missing: the name. stat printed notes.txt because you typed it, not because the inode knows it. An inode can have several names, or, for a moment, none.

Finding the blocks: pointers and extents

The inode has to say which blocks hold the file's data, and it is a small fixed-size record (256 bytes in ext4), so it can't list a million block numbers. Two schemes are in use.

The classic scheme, from the original Unix through ext3, stores block pointers. The inode holds 12 direct pointers. If the file needs more, a 13th points to a block that is itself full of pointers (single indirect), a 14th to a block of pointers to such blocks (double indirect), and a 15th adds a third level.

4 KiB blocks, 4-byte block numbers: 1,024 pointers fit in one block

12 direct pointers              12 × 4 KiB        =  48 KiB      small files: no extra reads
 1 single indirect           1,024 × 4 KiB        =   4 MiB
 1 double indirect          1,024² × 4 KiB        =   4 GiB
 1 triple indirect          1,024³ × 4 KiB        =   4 TiB      four extra block reads to reach the data

That is simple and handles any size, but a 1 GiB file needs 262,144 pointers, and they are almost all consecutive numbers. Modern file systems (ext4, XFS, NTFS, APFS, btrfs) record extents instead: "starting at block 81,920, the next 25,600 blocks". One extent in ext4 can describe up to 128 MiB, and four fit inside the inode; bigger or more fragmented files get a small tree of them.

Block pointersExtents
RecordsOne number per blockOne (start, length) pair per contiguous run
Metadata for a 1 GiB contiguous fileAbout 1 MiB of pointer blocksEight extents: under 100 bytes
Deleting a large fileSlow: every pointer block must be read to free the blocksFast
Fragmented fileNo worse than usualNeeds many extents, and loses the advantage
Used byext2, ext3, classic UFSext4, XFS, btrfs, NTFS, APFS

Extents only pay off if files really are laid out in long runs, so allocators work for that. ext4 delays choosing blocks until the data is about to be written, when it knows how much there is, and it tries to keep a file's blocks, its inode and its directory close together on the disk. You can see a file's extents with filefrag -v.

Directories are files

A directory is a file whose contents the file system itself maintains: a list of directory entries, each a name and an inode number. Nothing more. All the other facts about a file are in the inode the entry points to.

$ ls -ia /home/ana
1310722 .              # this directory itself
1310721 ..             # its parent
1311842 notes.txt
1311907 projects

Several familiar behaviours follow directly. Renaming or moving a file within one file system changes directory entries and never touches the data, so mv of a 50 GB file is instant. Moving it to a different file system has to copy every byte, because an entry can only name an inode in its own file system. And listing a directory with ls is cheap while ls -l is not: the first reads one directory, the second must also read every file's inode.

Hard links and symbolic links

Since names are just entries pointing at inodes, nothing stops two entries from pointing at the same one.

Hard link (ln a b)Symbolic link (ln -s a b)
What it isAnother directory entry for the same inodeA new inode whose content is a path, as text
Are the two names equal?Yes. Neither is "the original"No. One is the file, the other points to its name
If the first name is removedThe file lives on under the other nameThe link dangles: it names something that isn't there
Across file systemsImpossible: inode numbers are per file systemFine: a path can lead anywhere
To a directoryNot allowed (it could create loops in the tree)Fine
CostOne directory entryOne inode, and one more lookup each time it is followed

This explains what rm really does. The system call is named unlink: it removes one directory entry and subtracts one from the inode's link count. The inode and its blocks are freed only when the link count reaches zero and no process still has the file open. That second condition is why deleting a large log file that a server is still writing to frees no space until the server is restarted.

#include <unistd.h>
#include <stdio.h>

link("a.txt", "b.txt");               /* a second name for the same inode */
symlink("a.txt", "c.txt");            /* a new inode containing the text "a.txt" */
unlink("a.txt");                      /* one name fewer; the data survives while b.txt exists */
rename("config.tmp", "config.json");  /* atomic: readers see the old file or the new one, never half */

The last line matters more than it looks. rename replaces the destination in a single step, so the standard way to update a file safely is to write a complete new copy under a temporary name and rename it over the old one. Chapter 24 and Chapter 31 add what is needed to make that survive a power cut.

Commands: touch NAME, write NAME [N] (append N blocks, creating the file if needed), ln A B, ln -s A B, mv A B, rm NAME, cat NAME, ls. Everything lives in the root directory. A symbolic link's target is short enough to be stored inside its inode, as real file systems do.

Things to notice, following the examples in order. ln uses no inode and no block: only the directory grows, and the link count becomes 2. ln -s does use an inode. After mv a.txt d.txt the inode and its blocks haven't moved, b.txt still reads the data, and c.txt is broken, because it pointed at a name that no longer exists. rm d.txt frees nothing; rm b.txt removes the last name and only then are the inode and blocks released. Finally, keep running touch with new names: you run out of inodes with most of the blocks still free.

Two ways to be full

That last experiment happens on real servers. A file system can run out of blocks or out of inodes, and the error is the same: No space left on device. ext4 creates a fixed number of inodes when the file system is made, by default one for every 16 KiB of space. A directory of millions of tiny files, such as session files, a mail queue or a build cache, can use them all with the disk half empty.

$ df -h /var                 # blocks: plenty left
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p3   98G   41G   52G  45% /var
$ df -i /var                 # inodes: none left
Filesystem       Inodes   IUsed IFree IUse% Mounted on
/dev/nvme0n1p3  6553600 6553600     0  100% /var

XFS and btrfs allocate inodes as needed and don't have this limit. On ext4 the cures are to delete the small files or to rebuild the file system with more inodes.

The VFS: one interface, many file systems

A Linux machine usually has several file systems mounted at once: ext4 on the disk, tmpfs in memory, /proc generated by the kernel on the fly, perhaps NFS over the network. Programs don't care. open, read and write work the same on all of them, because they call into the virtual file system (VFS), a layer that defines what every file system must provide and dispatches to whichever one owns the file.

/* Linux, simplified: every open file carries a table of functions supplied by its file system. */
struct file_operations {
    ssize_t (*read) (struct file *, char *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char *, size_t, loff_t *);
    int     (*mmap) (struct file *, struct vm_area_struct *);
    int     (*fsync)(struct file *, loff_t, loff_t, int);
    /* ... */
};

/* What read() does once it has the struct file for the descriptor: */
return file->f_op->read(file, buf, count, &file->f_pos);     /* ext4's, tmpfs's or procfs's version */

This is an interface built from function pointers, the C equivalent of a virtual method table. The VFS defines four main objects: the superblock (one mounted file system), the inode (one file), the dentry (one name-to-inode link, cached) and the file (one open instance, with its offset). A file system is a set of functions that fill these in. That is how /proc/4120/status can be a "file" with no disk behind it: procfs's read generates the text when asked. It is also what Chapter 10 meant by "everything is a file".

$ findmnt -o TARGET,SOURCE,FSTYPE | head -6
TARGET        SOURCE          FSTYPE
/             /dev/nvme0n1p2  ext4
├─/proc       proc            proc
├─/sys        sysfs           sysfs
├─/dev/shm    tmpfs           tmpfs
└─/var        /dev/nvme0n1p3  ext4

Deploying a website by swapping one symbolic link

A long-standing way to release a new version of a web application, used by tools such as Capistrano and by many hand-written deploy scripts, depends on nothing but this chapter. Each release is unpacked into its own directory, releases/2026-10-06-1412/, next to the previous ones. The web server is configured to serve from a path called current, which is a symbolic link to one of those directories. Preparing a release can take minutes and touches nothing live. Going live is two calls: create a new symbolic link under a temporary name pointing at the new directory, then rename it over current. Because rename replaces the destination atomically, every request resolves current to either the complete old release or the complete new one, never a mixture of files from both. Rolling back is the same operation pointed at the previous directory, and takes a millisecond. The one thing to get right is the rename: deleting current and then re-creating it leaves a moment with no site at all.

⚠️
Common mistakes
  • Thinking the name is stored in the file. It is in the directory. The inode has no name, and may have several.
  • Expecting rm to free space at once. It removes a name. Space returns when the last name is gone and the last process has closed the file.
  • Treating hard links and symbolic links as the same. A hard link is the file. A symbolic link is a pointer to a name, and breaks if the name goes.
  • Checking only df -h when the disk is "full". Check df -i too.
  • Assuming mv is always instant or atomic. Only within one file system. Across two it is a copy followed by a delete.
  • Putting millions of files in one directory. Lookups are indexed in modern file systems, but listing, backing up and deleting such a directory are painfully slow. Spread them over subdirectories.

Interview drill

Explain it simply: What is an inode, and what is the difference between a hard link and a symbolic link?

How a strong answer sounds
An inode is the on-disk record that represents a file: its type, size, owner, permissions, timestamps, link count and the location of its data blocks. It doesn't contain the file's name. Names live in directories, which are files containing entries that map a name to an inode number. A hard link is simply another directory entry pointing at the same inode, so the two names are equal, the link count goes up, and the data stays until the last name is removed. It can't cross file systems, because inode numbers are only meaningful within one. A symbolic link is a separate inode whose content is a path. The kernel follows that path at lookup time, so it can point across file systems and at directories, but if the target is renamed or removed the link dangles.

Deeper: A server reports "No space left on device", but df -h shows 50% free. What do you check?

How a strong answer sounds
First inodes: df -i. On ext4 the inode count is fixed when the file system is created, so a huge number of small files can exhaust inodes while blocks remain; I'd find the directory responsible with something like find /var -xdev -type f | cut -d/ -f1-4 | sort | uniq -c | sort -n and clean it up. If inodes are fine, I'd look for space held by deleted files that are still open: lsof +L1 lists files with a link count of zero, and the space only returns when the owning process closes them or is restarted, though truncating the file through /proc/PID/fd/N frees it at once. Other possibilities are the blocks reserved for root, which ordinary users can't use, a per-user or per-project quota, or the write going to a different file system from the one I checked, so I'd confirm the mount with df on the exact path.

🧠 Key takeaways

  • An inode holds a file's metadata and the location of its data, but not its name.
  • Blocks are found through direct and indirect pointers in older file systems, and through extents, (start, length) runs, in modern ones.
  • A directory is a file of (name, inode number) entries; a path is resolved one component at a time.
  • A hard link is a second name for one inode; a symbolic link is a separate inode holding a path, and can dangle.
  • rm unlinks a name; data is freed at link count zero with no open descriptors. rename within a file system is atomic.
  • The VFS gives every file system the same interface through tables of function pointers, which is why /proc, tmpfs and ext4 all look like files.

Check your understanding

Which of these is not stored in a file's inode?

Names are in directory entries, which map a name to an inode number. That is what makes several names for one file possible.

You run ln report.txt copy.txt and then rm report.txt. What happens to the data?

A hard link is another name for the same inode. Removing one name leaves the inode and its blocks untouched while any name remains.

You run ln -s report.txt latest and then mv report.txt old.txt. What does cat latest do?

A symbolic link holds a path, not an inode number. It is resolved each time it is used, and the name it holds is gone.

Why is moving a 50 GB file to another directory on the same file system almost instant?

A rename removes one directory entry and adds another, both naming the same inode. No data is read or written.

What does the VFS layer provide?

Each file system supplies its own implementations of read, write, lookup and so on; the VFS calls them through function pointers.
