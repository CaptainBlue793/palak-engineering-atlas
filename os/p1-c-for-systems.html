C for Systems: Pointers & Memory

Every operating system you are likely to meet (Linux, the BSDs, the core of Windows and macOS) is written mostly in C, and so are the interfaces it offers to programs: read(), mmap(), pthread_create(). Those interfaces talk in addresses. You pass a pointer to a buffer and the kernel fills it; you get a pointer back from malloc and you decide when it dies. This chapter is the C you need to read systems code calmly: what an address is, what & and * do, where the stack and the heap are, and the four pointer bugs behind most crashes and security holes.

  • Tell stack memory from heap memory, and say who frees each
  • Recognise dangling pointers, leaks, double frees and use-after-free, and the tools that catch them

Variables live at addresses

To the CPU, memory is one long array of bytes, and an address is an index into it. When you write int port = 8080; inside a function, the compiler reserves four bytes somewhere (on x86-64 Linux an int is 4 bytes) and every use of port becomes "the four bytes at that address". C lets you see the address with the & operator:

#include <stdio.h>

int main(void) {
	int port = 8080;
	double load = 0.75;
	printf("port lives at %p and holds %d\n", (void *)&port, port);
	printf("load lives at %p and holds %.2f\n", (void *)&load, load);
	printf("sizes: int=%zu double=%zu pointer=%zu\n", sizeof port, sizeof load, sizeof &port);
	return 0;
}
$ gcc -Wall -g addr.c -o addr && ./addr
port lives at 0x7ffd4f1ca3c4 and holds 8080
load lives at 0x7ffd4f1ca3c8 and holds 0.75
sizes: int=4 double=8 pointer=8

Three things to notice. The addresses are large numbers starting 0x7ff…: that is the stack region, near the top of the process's address space (Chapter 11 explains the layout). They change every run, because Linux randomises where the stack goes as a security measure (ASLR, Chapter 36). And a pointer on a 64-bit machine is 8 bytes whatever it points to, because it is just an address.

Pointers: & takes an address, * follows one

A pointer is a variable whose value is an address. The type says what lives at that address, so the compiler knows how many bytes to read when you follow it:

int port = 8080;
int *p = &port;      /* p holds the address of port: "p points to port" */
printf("%d\n", *p);  /* *p follows the pointer: reads the int at that address -> 8080 */
*p = 9090;           /* writes through the pointer: port is now 9090 */
int **pp = &p;       /* a pointer to a pointer: **pp is port again */
int *nothing = NULL; /* points nowhere; following it crashes with SIGSEGV */

Read declarations from the name outwards: int *p is "p is a pointer to int". In an expression, &x means "address of x" and *p means "the thing at the address in p". That is the whole notation.

Why systems code is full of pointers: C passes arguments by value, copying them. If a function must fill in or change something the caller owns, the caller passes its address. That is exactly how the system-call interface works. read(fd, buf, n) cannot return 4 KiB of file data as a return value; you hand it the address of your buffer and it writes into your memory. pipe(fds) fills a two-element array you own. strtol(text, &end, 10) returns the number and, through a pointer to your pointer, where parsing stopped.

/* The caller owns buf; read() writes up to sizeof buf bytes into it. */
char buf[4096];
ssize_t got = read(fd, buf, sizeof buf);
if (got < 0) { perror("read"); return -1; }   /* always check: -1 means failure, errno says why */

The stack and the heap

A C program gets memory in two everyday ways. Local variables live in the function's stack frame: the compiler moves the stack pointer down on entry and back up on return, so allocation and freeing cost one instruction each and happen automatically. Heap memory comes from malloc and stays until you free it, so it can outlive the function, and its size can be decided at run time.

The house rule this course follows: name the owner of every allocation. Whoever calls malloc (or open) is responsible for the matching free (or close), unless a comment says the responsibility moves to the caller, as in make_greeting in the stepper.

Four pointer bugs

C trusts you completely. It never checks that a pointer is valid before following it, so a wrong pointer silently reads or writes the wrong bytes. Nearly every crash in C code, and most of its security holes, is one of these:

char *name = malloc(32);
free(name);
name[0] = 'x';          /* 1. use-after-free: the block may already belong to someone else */free(name);             /* 2. double free: corrupts the allocator's free list */
char *line = malloc(1024);
line = malloc(2048);    /* 3. leak: the first block is now unreachable, never freed */
int *count_ptr(void) { int c = 0; return &c; }   /* 4. dangling: c dies on return */

A useful habit from the table's last row: set a pointer to NULL right after freeing it. A second free(NULL) is defined to do nothing, and a stray use crashes at once instead of corrupting memory quietly.

Why 70% of Chrome's serious security bugs are memory bugs

In 2020 the Chromium security team reported that around 70% of their high-severity security bugs were memory-safety problems, and Microsoft had reported the same proportion for the CVEs it fixes each year. Most were use-after-free and out-of-bounds accesses in C and C++ code. That is why Chrome splits itself into sandboxed processes (Chapter 47), why sanitizers run on every test build at large companies, and why the Linux kernel accepted Rust as a second language in version 6.1 (December 2022), starting with drivers. The C stays, because decades of kernels, databases and runtimes are written in it, so reading it, and knowing these four bugs on sight, remains a core systems skill.

Why the OS is written in C

Kernels, allocators, language runtimes (CPython, the JVM's core, Go's early runtime) and databases like PostgreSQL and Redis are C, or C++ used in a C-like way. The reasons are the same ones that make C dangerous:

⚠️
Common mistakes
  • Not checking malloc's result. It returns NULL on failure; check before use, as every listing here does.
  • Returning the address of a local variable. The frame is gone after return. Return the value, or malloc and document that the caller frees.
  • Confusing sizeof p with the size of what it points to. For a pointer it is 8 on x86-64, whatever the buffer size. Pass lengths explicitly.
  • Freeing something you don't own, such as a string literal or a pointer into the middle of a block. Only pass free exactly what malloc returned.
  • Putting a large array on the stack (char buf[16 << 20];). 16 MiB is more than the default 8 MiB stack: instant SIGSEGV.
  • Printing a pointer with %d or %x. Use %p with a (void *) cast; addresses are 64-bit.

Interview drill

Explain it simply: What is the difference between stack and heap memory, and when would you use each?

How a strong answer sounds
Stack memory belongs to a function call: locals are carved out by moving the stack pointer on entry and released automatically on return, so it is nearly free but limited (8 MiB by default for the main thread) and dies with the call. Heap memory comes from malloc, lives until free, can be sized at run time and outlives the function, but costs more, can fragment, and leaks if you forget it. I'd use the stack for small, fixed-size, short-lived data and the heap for anything large, variable-sized, or returned to the caller, with one clear owner responsible for freeing it.

Deeper: A server's memory use grows slowly for days and then it is killed. Another one crashes at random places with corrupted data. What would you suspect for each, and how would you find it?

How a strong answer sounds
Slow growth until death is a classic leak: something allocated per request is never freed. I'd confirm with a heap profiler or Valgrind/LeakSanitizer on a test run, look at which call sites own the growing allocations, and check the error paths, where frees are often skipped. Random crashes with corrupted data far from the bug suggest use-after-free, a double free or a buffer overflow; I'd rebuild with -fsanitize=address and run the test suite or replay traffic, since ASan reports the bad access at the moment it happens, with the stacks of the allocation and the free.

🧠 Key takeaways

  • Memory is an array of bytes; every variable lives at an address, and a pointer is a variable holding one.
  • &x gives an address, *p follows one; C passes by value, so functions that fill your data take pointers, like read(fd, buf, n).
  • Stack frames are created and destroyed with each call; heap blocks live from malloc until free.
  • Every allocation and file descriptor has one named owner responsible for releasing it.
  • Use-after-free, double free, leaks and dangling stack pointers cause most C crashes and many security holes; sanitizers find them.
  • Kernels are written in C because it needs no runtime, controls layout exactly and treats addresses as numbers.

Check your understanding

After int x = 5; int *p = &x; *p = 7;, what is the value of x?

p holds the address of x, so *p = 7 writes 7 into x's four bytes.

Why does read(fd, buf, n) take a pointer to a buffer instead of returning the data?

The caller owns the buffer and passes its address; the kernel copies file data into it and returns only the byte count (or −1 with errno).

A function declares char buf[64];, fills it and returns buf. What goes wrong?

Locals die with their frame. The next function call reuses those bytes, so the caller's "string" changes under it. Return heap memory (and document who frees it) or let the caller pass a buffer in.

What is sizeof p when char *p = malloc(1000); on x86-64 Linux?

A pointer is an 8-byte address on a 64-bit machine. C does not remember the size of the block; you must carry the length yourself.

A program frees a block and later writes to it through the old pointer. Why is this so dangerous?

Use-after-free rarely crashes at once; it corrupts whatever now lives in the block, often far from the bug, and attackers can arrange for useful objects to land there.
