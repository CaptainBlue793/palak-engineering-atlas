Page Replacement: FIFO, LRU & Clock

Chapter 14 kept saying "the kernel evicts a page" without saying which one. The choice matters more than almost any other in memory management: evict a page that is needed again in a millisecond and you pay for a disk read; evict one that is never touched again and you pay nothing. This chapter works through the classic policies in order: the optimal one that can't be built, FIFO and its famous anomaly, LRU and why no kernel implements it exactly, and the clock algorithm that approximates it with one bit per page. Then it shows what Linux really does.

The problem, and why it deserves a chapter

RAM is full, a page fault needs a frame, and some page must give one up. If that page is used again, the result is a major fault. Take a memory access as 100 ns and a major fault on a hard disk as 8 ms. If just one access in a thousand faults:

average access = 0.999 × 100 ns + 0.001 × 8,000,000 ns ≈ 8,100 ns      (81 times slower)

To stay within 10% of full speed, fewer than 1 access in 800,000 may fault.

So the goal of a replacement policy is simple to state: cause as few faults as possible. Policies are compared on a reference string, the sequence of page numbers a program touches, with a fixed number of frames. Offsets within a page don't matter, and neither do repeated accesses to the same page in a row.

Optimal: evict the page needed furthest in the future

The best possible policy was described by László Bélády in 1966: when a frame is needed, evict the page whose next use is furthest away, or that is never used again. No policy can cause fewer faults on the same string.

It can't be built, because the kernel doesn't know what a program will touch next. It is still essential, as a yardstick. If LRU causes 12 faults where optimal causes 9, you know how much room is left; if a clever new policy is within a few per cent of optimal on your traces, there is nothing more to gain.

FIFO and Belady's anomaly

First in, first out evicts the page that was loaded longest ago. It needs only a queue and no information about use. That is also its flaw. The oldest pages in a process are often the busiest: the code of its main loop and the C library were loaded at start-up and are used constantly. FIFO throws them out on schedule, however hot they are.

FIFO also does something no sensible policy should. Give it more memory and it can fault more:

reference string: 1 2 3 4 1 2 5 1 2 3 4 5          FIFO

3 frames:   1 2 3 4 1 2 5 1 2 3 4 5       4 frames:   1 2 3 4 1 2 5 1 2 3 4 5
            F F F F F F F · · F F ·                   F F F F · · F F F F F F
            9 faults                                  10 faults

This is Belady's anomaly. The cause is that under FIFO, the pages held with 4 frames are not always a superset of the pages held with 3, so the larger memory can be missing a page the smaller one has. LRU and optimal can't behave this way. With either of them, the pages in memory with n frames are always among the pages in memory with n + 1 (they are called stack algorithms), so adding a frame never adds a fault.

LRU: the recent past predicts the near future

Least recently used evicts the page that has gone longest without being touched. It is optimal run backwards: it can't see the future, so it assumes the future looks like the recent past. Because of locality that guess is usually good, and LRU is typically close to optimal. Its bad case is a loop over slightly more pages than there are frames: the page it evicts is always the one needed next.

The trouble is the bookkeeping. To know the true least recently used page, something must be recorded on every memory reference:

/* Exact LRU: what would have to run on every load and store. */
struct frame { int page; uint64_t last_used; };
static uint64_t now;

void on_every_access(struct frame *f) { f->last_used = ++now; }   /* billions of times a second */

int lru_pick_victim(struct frame *f, int nframes)                 /* and a scan of every frame per eviction */
{
    int victim = 0;
    for (int i = 1; i < nframes; i++)
        if (f[i].last_used < f[victim].last_used)
            victim = i;
    return victim;
}

A memory access takes nanoseconds and happens without the kernel being involved at all. Trapping into the kernel on each one would slow programs down a thousand times, and no CPU writes a timestamp to a page table on every access. What hardware does provide, cheaply, is one bit: the MMU sets the Accessed bit in the page-table entry the first time a page is touched, and the kernel can clear it and look again later.

Clock: LRU from a single bit

The clock algorithm (also called second chance) turns that bit into a workable policy. Arrange the frames in a circle with a hand pointing at one of them. When a victim is needed, look at the page under the hand:

  • Accessed bit is 1: the page has been used since the hand last came by. Clear the bit, give it a second chance, and move the hand on.
  • Accessed bit is 0: it has not been touched for a whole revolution. Evict it.
struct frame { int page; bool accessed; bool dirty; };

int clock_pick_victim(struct frame *f, int nframes, int *hand)
{
    for (;;) {
        int here = *hand;
        *hand = (*hand + 1) % nframes;
        if (f[here].accessed) {
            f[here].accessed = false;       /* used recently: second chance */
            continue;
        }
        return here;                        /* untouched since the hand's last visit */
    }
}

The loop always ends: in the worst case the hand clears every bit on one revolution and evicts the page it started at on the next. Nothing runs per memory access, only per eviction. The result is a coarse LRU: it can't rank pages by age, but it separates "used lately" from "not used lately", which is most of what matters. A common refinement also reads the Dirty bit and prefers victims that are clean, since a dirty page must be written out before its frame can be reused.

Things to notice. On the textbook string with 3 frames the order is the one you would hope for: FIFO 15 faults, Clock 14, LRU 12, Optimal 9. On Belady's string, FIFO goes from 9 faults with 3 frames to 10 with 4, and so does Clock, which is FIFO whenever every page has been touched; LRU and Optimal never show a red bar. On the loop of 5 with 4 frames, FIFO, LRU and Clock fault on every single reference while Optimal manages with 7: no policy based on the past can handle a cycle one page larger than memory. On "hot and cold" with 3 frames, LRU matches Optimal at 8 because it keeps the two hot pages, while FIFO takes 12.

Working sets

Peter Denning's working set (1968) is the set of pages a process has referenced in its most recent window of time. It changes as the program moves between phases, but at any moment it is usually much smaller than the whole process. It gives replacement a goal that isn't tied to one algorithm: keep every running process's working set in memory. If the working sets together fit, faults are rare. If they don't, no replacement policy can help: this is the thrashing of Chapter 14, and the remedy is to run less or add RAM.

RSS is not the working set. RSS counts every page that happens to be resident, including pages touched once an hour ago that nothing has needed to evict. You can estimate a real process's working set on Linux by clearing its Accessed bits and seeing which ones are set again:

# echo 1 > /proc/4120/clear_refs                    # clear the Accessed bits of process 4120
# sleep 10
# awk '/^Referenced/ { kb += $2 } END { print kb " kB" }' /proc/4120/smaps
412664 kB                                           # touched in the last 10 s; its RSS is 2.4 GB

That gap is how much memory the machine could take back from this process without it noticing, and it is the number that matters when you size a container.

What Linux does

Linux doesn't run a single clock over all of memory. It keeps pages on lists, and the important pair is the inactive list and the active list (kept separately for file-backed and anonymous pages):

Two lists solve a problem plain LRU has. A backup job or grep -r reads gigabytes of files exactly once. Under plain LRU those pages are the most recently used, so they would push out the database's and the web server's hot pages. With two lists, use-once pages enter the inactive list, are never promoted, and are the first to go.

Who does the reclaiming matters for latency. A kernel thread, kswapd, wakes when free memory drops below a low watermark and frees pages in the background. If allocations outrun it and free memory hits the minimum, the allocating process has to stop and reclaim pages itself. That is direct reclaim, and it shows up as stalls in the middle of a malloc or a page fault (Chapter 38).

$ grep -E '^(Active|Inactive)' /proc/meminfo
Active(anon):    2811340 kB
Inactive(anon):   402116 kB
Active(file):    1920448 kB
Inactive(file):  3377012 kB
$ grep -E 'pgscan_(kswapd|direct)|pgsteal_(kswapd|direct)' /proc/vmstat
pgscan_kswapd 88213044        # pages examined by background reclaim
pgscan_direct 412877          # pages examined while a process waited: should stay small
pgsteal_kswapd 61120933       # pages actually freed
pgsteal_direct 305112

Since Linux 6.1 (2022) there is a second design, the multi-generational LRU, which sorts pages into several generations by age instead of two lists. It came from Google and is used on Android and ChromeOS; it is the same idea with finer steps.

🟥
Redis makes the same trade: approximate LRU by sampling

Redis can be told to evict keys when it reaches a memory limit, with maxmemory-policy allkeys-lru. A textbook LRU would keep every key on a linked list and move a key to the front on each access: two extra pointers per key, and a list update on every read, in a server whose whole selling point is small, fast operations. Redis doesn't do that. Each object stores a 24-bit timestamp of its last access. When memory is needed, Redis picks a few keys at random (five by default, set by maxmemory-samples), evicts the one that has been idle longest, and keeps the best remaining candidates in a small pool for the next round. Its own measurements show that with 10 samples the result is hard to tell apart from true LRU. This is the kernel's reasoning in another setting: exact recency costs something on every access, approximate recency costs something only on eviction, and the approximation is nearly as good. Redis later added an LFU policy (least frequently used) for workloads where a key touched once recently shouldn't outrank one touched a thousand times.

⚠️
Common mistakes
  • Mixing up FIFO and LRU. FIFO looks at when a page was loaded; LRU at when it was last used. On a hit, FIFO changes nothing and LRU updates the page's position.
  • Saying "more memory always means fewer faults". True for LRU and optimal, false for FIFO. Belady's anomaly is the counter-example.
  • Claiming Linux uses LRU. It uses an approximation built from Accessed bits and two lists (or generations). The lists are often called "the LRU", which adds to the confusion.
  • Forgetting to count the first loads. Filling an empty frame is a fault too. An exam answer that is off by the number of frames has usually missed these.
  • Treating RSS as what a process needs. The working set is usually smaller. Sizing by RSS wastes memory; sizing below the working set causes thrashing.
  • Ignoring dirty pages. Evicting a clean page is free; a dirty one costs a write first. Real policies weigh that.
🎤
Interview drill

Explain it simply: Compare FIFO, LRU and Clock page replacement.

How a strong answer sounds
All three decide which page to evict when memory is full. FIFO evicts the page that was loaded earliest. It is trivial to implement but ignores usage, so it throws out hot pages, and it suffers from Belady's anomaly, where adding frames can increase faults. LRU evicts the page that hasn't been used for longest, on the assumption that recent use predicts future use; it is usually close to optimal and can't show the anomaly, but exact LRU needs bookkeeping on every memory access, which is far too expensive. Clock approximates LRU using the Accessed bit the MMU sets: frames sit in a circle, and the hand clears set bits as it passes and evicts the first page whose bit is already clear, meaning it hasn't been used for a full revolution. It costs nothing per access and only a little per eviction, which is why real kernels build on it.

Deeper: How would you design an LRU cache, and why doesn't the kernel use that design for pages?

How a strong answer sounds
A hash map from key to node, plus a doubly linked list ordered by recency. A get finds the node through the map and moves it to the head; a put inserts at the head and, if the cache is over capacity, removes the tail and its map entry. Both are O(1). That works for an application cache because every access already goes through my code, so the move-to-front is a few pointer writes on a path I control. Page accesses don't go through the kernel: a load or store is one instruction handled entirely by the MMU. To maintain the list the kernel would have to trap on every access, turning nanoseconds into microseconds. A shared list would also need a lock, which would be contended on every core. So the kernel settles for what the hardware gives it for free, the Accessed bit, and samples it during reclaim with clock-style scanning and active and inactive lists.

🧠 Key takeaways

  • A replacement policy's job is to minimise faults; a fault costs thousands to tens of thousands of times more than a hit.
  • Optimal evicts the page needed furthest in the future. It can't be built, and it is the yardstick for everything else.
  • FIFO evicts the oldest-loaded page and can fault more with more memory: Belady's anomaly.
  • LRU evicts the least recently used page and is close to optimal, but exact LRU needs work on every access.
  • Clock approximates LRU with the Accessed bit: clear it and move on if set, evict if clear.
  • Linux uses active and inactive lists, with kswapd reclaiming in the background and direct reclaim as the slow fallback.

Check your understanding

Memory has 3 frames and the reference string so far is 1, 2, 3, 1. Page 4 is referenced next. Which page does LRU evict, and which does FIFO?

Page 1 was loaded first, so FIFO evicts it. But 1 was just used again, so for LRU the least recently used page is 2.

What is Belady's anomaly?

With the string 1 2 3 4 1 2 5 1 2 3 4 5, FIFO takes 9 faults with 3 frames and 10 with 4. LRU and optimal can never do this.

Why don't kernels implement exact LRU for memory pages?

Accesses are handled by the MMU in about a nanosecond. Recording each one would cost far more than the faults it saves.

In the clock algorithm, the hand reaches a page whose Accessed bit is 1. What happens?

Only a page whose bit is still 0 when the hand comes round again, meaning it wasn't used in between, is evicted.

A nightly backup reads 50 GB of files once. Why doesn't this push a database's hot pages out of memory on Linux?

A page must be used again while inactive to be promoted. Use-once pages never are, so they are the cheapest victims.
