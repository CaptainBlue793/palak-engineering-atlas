Performance Tools: perf, strace & /proc

"The server is slow." Thirty-six chapters have described the things that can make it so: too many runnable threads, page faults, lock contention, a full disk queue, a stalled event loop. This chapter is about telling them apart on a live machine in the first few minutes, with the tools every Linux system already has. There are a lot of tools, and the skill is not knowing all their options. It is having a method that tells you what to look at next, and being able to read a handful of numbers for what they say about the kernel mechanisms underneath. Each one is a window onto something you now understand.

  • Apply the USE method: utilisation, saturation and errors for each resource
  • Read uptime, vmstat, mpstat, iostat, free and top, and say what each number means
  • Use strace to see what a process asks of the kernel, and know what it costs
  • Profile CPU use with perf and read a flame graph
  • Explain off-CPU analysis and when a CPU profile can't help

A method before any tool: USE

The usual way to investigate is to run a familiar tool and stare at it until something looks odd. Brendan Gregg's USE method replaces that with a checklist. For every resource the machine has, ask three questions:

  • Utilisation: how busy is it? (Percentage of time in use, or of capacity used.)
  • Saturation: is work queuing for it? (A queue is where latency comes from.)
  • Errors: is it failing?

Saturation matters most. A CPU at 100% with nothing waiting is fully used and healthy. A CPU at 100% with twenty threads queued behind it is the reason requests are slow.

Almost every number these tools print is read from /proc and /sys, plain files the kernel generates on demand (Chapter 23). /proc/loadavg, /proc/meminfo, /proc/stat, /proc/<pid>/status: when no tool is installed, you can still read them.

strace: what is it asking the kernel?

strace prints every system call a process makes. Since everything a program does to the outside world is a system call, it answers a great many "what is it doing?" questions without the source code.

$ strace -f -T -e trace=openat,read,connect -p 4120     # chosen calls, with the time each took
[pid 4131] openat(AT_FDCWD, "/etc/app/config.yaml", O_RDONLY) = 9 <0.000031>
[pid 4131] connect(12, {sa_family=AF_INET, sin_port=htons(5432), ...}, 16) = -1 ETIMEDOUT <30.001240>
#                                                              ^ the answer: 30 s waiting for a database
$ strace -c -f -p 4120                                   # or a summary: which calls, how often, how long
% time     seconds  usecs/call     calls    errors syscall
 96.12   41.208133          85    480377    131020 futex
  2.01    0.861002          12     71200           epoll_wait

It has a cost you must know about. strace works through ptrace, which stops the traced process twice per system call and switches to the tracer each time. A system-call-heavy program can run tens of times slower under it. Use it freely on a development machine and on processes that are already stuck; on a busy production process, prefer perf trace or an eBPF tool, which observe from inside the kernel (Chapter 35). ltrace does the same for calls into shared libraries.

perf: where is the CPU time going?

perf is a sampling profiler. Many times a second, on every core, a timer interrupt records what was running and the chain of function calls that led there. After thousands of samples, the functions that appear most are where the time goes. Because it only samples, the overhead is small enough for production.

$ perf top                                  # live: the hottest functions on the whole machine
  38.20%  [kernel]        [k] native_queued_spin_lock_slowpath
  11.04%  libc.so.6       [.] __lll_lock_wait
$ perf record -F 99 -g -p 4120 -- sleep 30   # record stacks from one process, 99 times a second, for 30 s
$ perf report                               # browse them
$ perf stat -p 4120 -- sleep 10             # or count hardware events instead of sampling
    41,203,118,442      cycles
    22,884,170,019      instructions          #  0.56 insn per cycle: stalled on memory, not busy computing
       912,440,871      cache-misses

Thousands of stack samples are unreadable as text. A flame graph draws them as one picture. Each box is a function. A box sits on top of the function that called it, so the height is the depth of the call stack. The width of a box is the share of samples in which that function was on the stack. The x-axis is not time; boxes are sorted alphabetically so that identical stacks merge. To read one, look for the widest boxes that have nothing on top of them: those are the functions actually burning CPU.

$ perf script | stackcollapse-perf.pl | flamegraph.pl > cpu.svg

      ┌─────────────────────────────────────┐┌──────────┐
      │            json_parse               ││ gzip     │         ← wide and on top: the CPU is here
      ├─────────────────────────────────────┴┴──────────┤┌───────┐
      │                 handle_request                  ││ log   │
      ├─────────────────────────────────────────────────┴┴───────┤
      │                       worker_loop                        │
      └───────────────────────────────────────────────────────────┘

Where flame graphs came from

In 2011 Brendan Gregg, then at the cloud provider Joyent, was investigating a MySQL database that was using far more CPU than it should. He profiled it in the standard way, sampling stack traces, and got what such profiles always produce on a real system: output that ran to many thousands of lines, with the same few call paths repeated in slightly different forms. The answer was in there and nobody could see it. He wrote a script to merge identical stacks and draw them as stacked rectangles whose widths were sample counts. The cause of the MySQL problem was visible at once as one wide tower. The picture looked like flames in the colours he happened to choose, and the name stuck. The technique needed no new measurement at all, only a better way to look at data everyone already collected. Flame graphs are now built into browsers' developer tools, language runtimes and every commercial profiler, and the same idea is applied to memory allocation, to disk I/O, and to time spent waiting. It is a fair summary of performance work in general: the data is usually there; the skill is in knowing what to draw.

Off-CPU: the time a CPU profile can't see

A CPU profiler samples threads that are running. A request that takes 900 ms because it spends 890 ms waiting, for a lock, a disk, a database, a full queue, contributes almost nothing to a CPU profile. The flame graph will show you the 10 ms and look perfectly healthy.

A quick first check needs no special tool. If a thread's voluntary context switches are climbing fast, it keeps going to sleep waiting for something. If its involuntary ones are, it is being pushed off the CPU (Chapter 6). Either way the next chapter's subject, the slowest few requests, usually lives in off-CPU time.

⚠️
Common mistakes
  • Reading load average as CPU load. On Linux it includes threads blocked on disk. Check vmstat before concluding anything.
  • Trusting averages over all cores. 12% CPU on 8 cores can be one core at 100%. Look per core, and per thread.
  • Running strace on a busy production process. It can slow it many times over. Know the cost, or use a kernel-side tracer.
  • Reading a flame graph left to right as time. The x-axis is alphabetical. Only width means anything.
  • Profiling CPU when the problem is waiting. If the CPU is mostly idle, a CPU profile explains the wrong 2%.
  • Changing something before measuring. Without a baseline you can't tell whether the fix worked, or what it broke.

Interview drill

Explain it simply: A Linux server is slow. What do you check in the first minute?

How a strong answer sounds
I'd go resource by resource, looking at utilisation, saturation and errors. uptime for the load averages and whether they are rising. dmesg | tail for kernel errors such as OOM kills. Then vmstat 1, which shows most of it at once: the r column against the core count for CPU saturation, si and so for swapping, us versus sy for where CPU time goes, wa and b for threads stuck on disk, cs for context switches. mpstat -P ALL to see whether one core is pinned while others idle. iostat -xz 1 for each disk's utilisation, queue depth and await. free -h for available memory. And top or pidstat to attach the problem to a process. That narrows it to CPU, memory, disk or "none of those", and each of those leads to a specific next tool: perf for CPU, off-CPU tracing or strace for waiting.

Deeper: A service's p99 latency doubled, but CPU usage is unchanged at 30%. How do you find the cause?

How a strong answer sounds
Unchanged, low CPU with worse latency says the extra time is spent waiting, not computing, so a CPU profile won't show it. I'd look at off-CPU time. First the cheap signals: per-thread voluntary and involuntary context switches from pidstat -w, run-queue latency with runqlat in case threads are waiting for a core because of bursts or a cgroup CPU limit, and iostat and block-I/O latency in case the disk has slowed. Then where the threads block: an off-CPU flame graph from offcputime shows the stacks that sleep and for how long, which separates lock waits, futex in the stack, from I/O waits and from network waits on a dependency. strace -T on one thread, briefly, shows slow individual system calls. I'd also check what changed: a dependency's latency, a new lock, memory pressure causing major faults, throttling counters in the cgroup. p99 problems are usually queues, so I'd look for whatever resource has a queue building at the times the slow requests occur.

🧠 Key takeaways

  • Work by method: for each resource, check utilisation, saturation and errors. Saturation is where latency comes from.
  • vmstat 1 covers CPU, memory and I/O in one line; mpstat, iostat -x, free and top fill in the detail.
  • Linux's load average counts threads waiting for disk as well as for CPU. Averages across cores hide a single pinned thread.
  • strace shows a process's system calls and their timing; it is expensive for the process being traced.
  • perf samples stacks cheaply; in a flame graph, width is the share of CPU and the x-axis is not time.
  • If the CPU is idle and things are slow, the time is off-CPU: locks, I/O, queues. Use tools that measure waiting.

Check your understanding

In the USE method, what does "saturation" mean?

Utilisation says how busy a resource is. Saturation says there is more demand than it can serve, so requests wait.

A server with 8 cores shows a load average of 9 and CPU usage of 5%. What is the most likely explanation?

Linux's load average includes uninterruptible waits. Low CPU with high load points at I/O; vmstat's b and wa confirm it.

vmstat shows us 22, sy 61 and 412,000 context switches a second. What should you suspect?

High system time with a very high switch rate means the kernel is busy arbitrating. strace -c showing mostly futex would confirm it.

In a CPU flame graph, what does the width of a box represent?

Width is proportional to sample count. The horizontal order is alphabetical, chosen so that identical stacks merge.

Requests are slow, CPU usage is low, and a CPU profile shows nothing unusual. Why is the profile unhelpful?

Waiting for locks, I/O or other services uses no CPU, so it doesn't appear. Off-CPU tools record where threads sleep and for how long.
