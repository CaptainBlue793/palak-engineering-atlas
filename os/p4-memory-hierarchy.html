The Memory Hierarchy

A CPU core can do several additions per nanosecond, but fetching one value from main memory takes around 100 nanoseconds, a disk read can take 10 milliseconds, and a request to another continent 150. Almost every design decision in an operating system (caching file data in RAM, keeping page tables small, putting threads near their memory, batching writes) is about hiding those gaps. This chapter gives you the numbers and the two ideas that make caches work: cache lines and locality.

The figures below are typical for a recent server; exact values vary by a factor of two between machines, and that doesn't matter. What matters is the ratios: each step down the hierarchy is roughly 3 to 1,000 times slower than the one above it. Three consequences run through this course. A page fault that has to read from disk (Chapter 14) costs as much as hundreds of thousands of instructions, so the OS works hard to avoid them. The kernel keeps recently used file data in RAM, the page cache (Chapter 31), because RAM is a thousand times faster than an SSD. And a context switch (Chapter 6) costs more than its few microseconds of direct work because the next thread finds the caches full of someone else's data.

Cache lines: the unit of transfer

Caches never move single bytes. They move cache lines, 64 bytes on x86-64 and most ARM server chips. Read one int from DRAM and the 64-byte block around it is copied into L1, L2 and L3. The next fifteen ints are then nearly free. A load works its way down until some level has the line:

Caches work because programs have locality. Temporal locality: data used recently is likely to be used again soon (a loop counter, the top of the stack, a hot hash bucket). Spatial locality: data near recently used data is likely to be used soon (the next array element, the next field of a struct). Code with good locality runs at cache speed; code without it runs at DRAM speed, up to 100 times slower, while doing exactly the same arithmetic.

#define N 4096
static int m[N][N];            /* 64 MiB; C stores it row by row */

long sum_rows(void) {          /* walks memory in order: 1 miss per 16 ints */
	long s = 0;
	for (size_t r = 0; r < N; r++)
		for (size_t c = 0; c < N; c++) s += m[r][c];
	return s;
}

long sum_cols(void) {          /* jumps 16 KiB per step: a miss on nearly every access */
	long s = 0;
	for (size_t c = 0; c < N; c++)
		for (size_t r = 0; r < N; r++) s += m[r][c];
	return s;
}

Both functions add the same 16.7 million numbers. On a typical machine sum_cols is several times slower, sometimes ten times or more. Watch why:

Row order misses once per line and then hits fifteen times: a 94% hit rate. Column order touches 32 different lines before coming back to any of them, so with fewer than 32 lines of cache every single access misses: the line it loaded is evicted before its neighbours are used. Give the cache 32 lines and column order recovers, which is the general rule: locality matters when the data is bigger than the cache, and real data almost always is.

Sequential beats random, at every level

The same pattern repeats all the way down. Hardware prefetchers make sequential memory reads nearly free. SSDs read large sequential blocks far more efficiently than scattered 4 KiB reads. Hard disks are extreme: a sequential read streams at around 200 MB/s, while random 4 KiB reads manage about 100–200 per second (well under 1 MB/s) because each one waits for the head to seek and the platter to rotate.

That table also separates two words people mix up. Latency is how long one access takes. Throughput (or bandwidth) is how much data per second you can move when many accesses overlap. An SSD has 1,000 times DRAM's latency but only about 10 times less bandwidth, because it can work on many requests at once. Systems get throughput by keeping many operations in flight (deep I/O queues, io_uring in Chapter 29) and get low latency by not waiting at all (caching).

📜
Kafka: built on "the disk is fast if you read it in order"

Apache Kafka stores every topic as an append-only log on disk and serves consumers by reading those files front to back. Its design documentation makes the hierarchy argument explicitly: sequential disk access can outrun random memory access, and the operating system's page cache already keeps recently written data in RAM. So Kafka doesn't build its own in-memory cache; it writes sequentially, lets the kernel cache the tail of the log, and sends file data to sockets with sendfile() so it never passes through user space (Chapter 42 uses the same trick). A design choice that looks like "using disks" is really a design choice about access patterns.

⚠️
Common mistakes
  • Counting operations instead of cache misses. Two loops with the same Big-O can differ tenfold in speed because of their access pattern.
  • Linked lists and pointer-chasing for hot data. Every hop can be a cache miss; arrays and B-trees pack many items per line.
  • Iterating a 2-D C array column by column. C is row-major: the last index should vary fastest in the inner loop.
  • Confusing latency with throughput. "Our SSD does 5 GB/s" says nothing about how long one 4 KiB read takes.
  • Benchmarking on a warm cache only. The first request after a deploy, or after the data falls out of cache, can be 100 times slower.

Interview drill

Explain it simply: Roughly how long does it take to read from L1, from RAM, from an SSD and from another data centre?

How a strong answer sounds
L1 is about a nanosecond, RAM about 100 nanoseconds, an NVMe SSD random read tens of microseconds to about 100, a round trip within a data centre a few hundred microseconds, and across continents around 100–150 milliseconds. Each step is roughly two or three orders of magnitude, which is why caches exist at every level: the CPU caches RAM, the OS page cache holds disk data in RAM, and services cache remote results locally.

Deeper: Two nested loops sum a large 2-D array. Swapping the loop order makes it eight times slower. Why?

How a strong answer sounds
C stores 2-D arrays row by row, and caches move 64-byte lines. With the column index in the inner loop, consecutive accesses are adjacent in memory: one miss brings in sixteen ints, and the prefetcher streams the next lines. With the row index inner, each access jumps a whole row ahead, so every access touches a different line; once the column is longer than the cache can hold, lines are evicted before their neighbours are used, and nearly every access is a miss costing ~100 ns instead of ~1 ns. The arithmetic is identical; the locality is not.

🧠 Key takeaways

  • Registers < 1 ns, L1 ~1 ns, DRAM ~100 ns, SSD ~20–100 µs, disk seek ~10 ms, cross-continent ~150 ms.
  • Caches move 64-byte lines; touching one byte loads the whole line.
  • Temporal and spatial locality decide whether code runs at cache speed or memory speed.
  • Sequential access beats random access in caches, SSDs, disks and networks alike.
  • Latency is the time for one access; throughput is data per second with many in flight.
  • The OS's caches (page cache, TLB) exist to hide these gaps.

Check your understanding

Roughly how long does a read from main memory (DRAM) take when it misses every cache?

Around 80–100 ns: a hundred times an L1 hit, and hundreds of simple instructions' worth of time.

Your code reads one 4-byte int that is not in any cache. How much data moves from DRAM into the cache?

Caches transfer whole lines, 64 bytes on x86-64. The neighbouring 60 bytes come along, which is why spatial locality pays.

Which access pattern makes the best use of the cache for a large C array int m[R][C]?

C is row-major, so m[r][c] and m[r][c+1] are adjacent. Varying the last index fastest walks memory in order.

An NVMe SSD streams 5 GB/s, yet one random 4 KiB read takes ~80 µs. How can both be true?

Latency and throughput are different measures. With dozens of overlapping requests, each still taking ~80 µs, the device moves gigabytes per second.

Why does Kafka rely on the OS page cache and sequential disk writes instead of a big in-process cache?

Kafka's design leans on access patterns: append and read logs in order, and let the kernel's page cache hold the hot tail. The page cache is not durable; that's what fsync is for (Chapter 31).
