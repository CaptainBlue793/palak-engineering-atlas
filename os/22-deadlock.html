Deadlock: Conditions, Detection & Prevention

The philosophers of Chapter 21 each held one fork and waited for another, for ever. That was a deadlock: a set of threads in which every one is waiting for something that only another one of them can provide. It doesn't crash and it doesn't use CPU. The service simply stops answering, and the only evidence is threads asleep inside lock calls. This chapter gives the general theory, which is short: four conditions must all hold for a deadlock to exist, and every technique for dealing with deadlock removes one of them, steers around the danger, or cleans up afterwards.

  • Run the banker's algorithm to decide whether a state is safe
  • Compare prevention, avoidance, detection and ignoring the problem

The smallest deadlock

It takes two threads and two locks. This function moves money between accounts and locks both while it does:

struct account { int id; long balance; pthread_mutex_t lock; };

void transfer(struct account *from, struct account *to, long amount)
{
    pthread_mutex_lock(&from->lock);
    pthread_mutex_lock(&to->lock);
    from->balance -= amount;
    to->balance   += amount;
    pthread_mutex_unlock(&to->lock);
    pthread_mutex_unlock(&from->lock);
}

/* Thread 1: transfer(&a, &b, 10);      Thread 2: transfer(&b, &a, 20); */

The four conditions

In 1971 Edward Coffman and colleagues showed that a deadlock can exist only if four conditions hold at the same time. All four are true in the example above.

ConditionMeaningIn the transfer example
Mutual exclusionA resource can be held by only one thread at a timeAn account's mutex has one owner
Hold and waitA thread holds one resource while waiting for anotherThread 1 keeps A while it waits for B
No preemptionA resource can't be taken away; only its holder can release itNobody can make thread 2 give up B
Circular waitThere is a cycle of threads, each waiting for a resource the next one holds1 waits for 2, and 2 waits for 1

The value of the list is the other direction: remove any one condition and deadlock becomes impossible. Every prevention technique below is aimed at exactly one of them.

Seeing a deadlock: the wait-for graph

Draw a node for each thread and an arrow from each waiting thread to the thread that holds what it wants. That is a wait-for graph. (A resource-allocation graph is the same picture with the resources drawn as nodes too.) When every resource has a single unit, as a mutex does, the rule is exact: there is a deadlock if and only if the graph has a cycle.

You can build that graph from a hung process. Every thread's stack shows what it is waiting for:

$ gdb -p 4120 -batch -ex "thread apply all bt"
Thread 2 (LWP 4122):
#0  __lll_lock_wait ()                     # asleep, waiting for a mutex ...
#1  pthread_mutex_lock ()
#2  transfer (from=0x55d0c8a4b2a0, to=0x55d0c8a4b260, amount=20) at bank.c:9     # ... its second one
Thread 1 (LWP 4121):
#0  __lll_lock_wait ()
#1  pthread_mutex_lock ()
#2  transfer (from=0x55d0c8a4b260, to=0x55d0c8a4b2a0, amount=10) at bank.c:9     # same line, arguments swapped
(gdb) print ((pthread_mutex_t *) 0x55d0c8a4b270)->__data.__owner
$1 = 4121                                   # the mutex thread 2 wants is owned by thread 1

Two threads blocked at line 9 with mirrored arguments is the cycle. Higher-level runtimes do this for you: Java's jstack prints Found one Java-level deadlock with the threads and locks involved, and Go's runtime aborts with all goroutines are asleep - deadlock! when nothing at all can run.

Prevention: break one condition

BreakHowVerdict
Mutual exclusionDon't share, or share without locks: immutable data, per-thread data, atomic operationsThe best cure where it applies, but many resources really are exclusive
Hold and waitTake everything you need in one step, or hold nothing while you wait: one coarse lock, or a helper that locks a set togetherWorks, at a cost in concurrency. You must know what you need in advance
No preemptionUse try-lock or a timeout; on failure, release what you hold and retryWorks, but can livelock, and the retry path has to undo partial work
Circular waitGive all locks one global order and always take them in that orderThe standard technique. No run-time cost; needs discipline

Lock ordering is the one to know thoroughly. If every thread takes locks in increasing order, a cycle would need some thread to hold a higher lock while waiting for a lower one, and nobody does that. Any consistent order works: an ID, a level in a hierarchy, or the memory address of the lock.

void transfer(struct account *from, struct account *to, long amount)
{
    if (from == to) return;                              /* locking one mutex twice would deadlock with ourselves */
    struct account *first  = from->id < to->id ? from : to;   /* always the lower id first */
    struct account *second = from->id < to->id ? to : from;

    pthread_mutex_lock(&first->lock);
    pthread_mutex_lock(&second->lock);
    from->balance -= amount;
    to->balance   += amount;
    pthread_mutex_unlock(&second->lock);
    pthread_mutex_unlock(&first->lock);
}

In a large program the order is usually a documented hierarchy: "the table lock before any row lock; never take the table lock while holding a row lock". The Linux kernel goes further and checks it by machine. Its lockdep validator records, in a debug build, every pair of lock classes taken one inside the other, and reports as soon as it sees the same two taken in the opposite order anywhere in the kernel, even if the two code paths never ran at the same time and no deadlock happened.

Avoidance: the banker's algorithm

Prevention restricts how programs are written. Avoidance lets them ask for anything and has the system say "not yet" when granting a request could lead to deadlock later. Dijkstra's banker's algorithm (1965) is the classic. Each process declares in advance the maximum of each resource type it may ever need. The system then keeps itself in a safe state: one in which there is some order for the processes to finish, each getting its full maximum in turn from what is free plus what earlier finishers return.

Safety check:
    Work = Available                              what is free now
    repeat:
        find an unfinished process P with  Need[P] ≤ Work      it could run to completion
        if none exists: stop
        Work = Work + Allocation[P]               it finishes and returns everything it holds
        mark P finished
    the state is safe if and only if every process got marked

Request from P:
    if Request > Need[P]:       error             it is asking for more than it declared
    if Request > Available:     P must wait
    otherwise pretend to grant it, then run the safety check:
        safe   -> grant it
        unsafe -> undo, and P waits

An unsafe state is not a deadlock. It is a state from which the system can no longer guarantee to avoid one, because if every process then asked for its maximum, some could never be satisfied. The banker refuses to enter such states at all.

Be the banker

asks for A B C
Each triple is (A, B, C). Need = Max − Allocation. The check scans the processes in order, repeatedly, and takes the first that can finish; other valid orders may exist. A granted request stays granted, so the three presets build on each other.

Things to notice. The starting state is safe: P1, P3, P4, P0 and P2 can finish in that order. P1's request for (1,0,2) is granted, because a safe order still exists afterwards. P4's request for (3,3,0) has to wait for a plain reason: only 2 units of A are free. P0's request for (0,2,0) is the interesting one. The units are available, and granting it would cause no deadlock today, but it would leave (2,1,0) free and no process could then be guaranteed to finish, so the banker says no.

The algorithm is rarely used as written. Real processes don't know their maximum needs in advance, the set of processes keeps changing, and running the check on every allocation is expensive. The idea survives in admission control: a system that takes on new work only if it can guarantee to finish what it has already accepted is doing what the banker does.

Detection, recovery, or nothing at all

The third strategy is to let deadlocks happen and deal with them. The system keeps the wait-for graph, looks for cycles, and breaks one by choosing a victim and forcing it to release what it holds. That is only practical where the victim's work can be undone cleanly, which is exactly what a database transaction is.

🐘
Databases detect deadlocks and shoot a transaction

Two transactions update the same two rows in opposite orders: one runs UPDATE accounts ... WHERE id = 1 and then id = 2; the other does id = 2 and then id = 1. Each takes a row lock on its first row and waits for the other's. A database can't impose a lock order on arbitrary SQL, so it does the other thing. PostgreSQL lets a lock wait run for deadlock_timeout (one second by default), then builds the wait-for graph and, if it finds a cycle, aborts one of the transactions with ERROR: deadlock detected and a detail line such as Process 18123 waits for ShareLock on transaction 9031; blocked by process 18140. The other transaction proceeds at once. MySQL's InnoDB checks as soon as a transaction has to wait, and rolls back the one that has changed the fewest rows. The application is expected to catch the error and retry, which is safe because the rollback undid everything. And the cure on the application side is this chapter's main technique: make every transaction touch rows in the same order, for instance sorted by primary key, and the cycle can't form.

The last row is not a joke. An operating system can't know which user-level waits are deadlocks and which are just slow, so it leaves user programs to prevent their own, and operators rely on timeouts, health checks and restarts to recover from the ones that slip through.

Relatives of deadlock

  • Livelock. The threads aren't blocked. They keep reacting to each other, each backing off and retrying in step, and none makes progress, like the philosophers in Chapter 21 who all put their forks down together. It burns CPU, which at least makes it visible. Randomised back-off breaks it.
  • Starvation. The system as a whole makes progress but one thread never gets its turn, like the writer behind an endless stream of readers. Fair queues fix it.
  • Self-deadlock. One thread locks a non-recursive mutex it already holds, usually by calling a function that takes the same lock. A cycle of length one.
  • Priority inversion. A high-priority thread waits for a lock held by a low-priority one that isn't getting to run. Not a deadlock, but it can look like one (Chapter 39).
⚠️
Common mistakes
  • Taking locks in argument order. transfer(a, b) and transfer(b, a) then lock in opposite orders. Order by something intrinsic to the objects.
  • Calling unknown code while holding a lock. A callback or virtual method may take other locks, and you have just created an ordering you don't control.
  • Waiting for something else while holding a lock. A join, a blocking queue operation or a network call under a lock is hold-and-wait with a longer name.
  • Thinking a timeout is a fix. It turns a hang into an error and a retry. Useful, but the ordering bug is still there.
  • Saying "unsafe" when you mean "deadlocked". An unsafe state may never deadlock. It only lacks the guarantee.
  • Assuming a cycle always means deadlock. With several units of a resource, a cycle is necessary but not sufficient.

Interview drill

Explain it simply: What is a deadlock, what conditions does it need, and how do you prevent one?

How a strong answer sounds
A deadlock is a set of threads each waiting for a resource held by another in the set, so none can ever proceed. It needs four conditions together: mutual exclusion, meaning the resource can't be shared; hold and wait, meaning a thread keeps one resource while waiting for another; no preemption, meaning a resource can't be taken from its holder; and circular wait, a cycle of threads each waiting on the next. Breaking any one prevents it. In practice the one to break is circular wait, by defining a global order for locks and always acquiring them in that order: for example, when transferring between two accounts, lock the one with the lower ID first. Then no thread ever holds a higher lock while waiting for a lower one, so a cycle can't form. Where ordering isn't possible I'd use try-lock with back-off, or a single coarser lock.

Deeper: A production service has stopped responding but is using no CPU. How do you find out whether it is deadlocked, and where?

How a strong answer sounds
No CPU with no progress suggests every thread is blocked. I'd capture all thread stacks without killing the process: gdb -p PID -batch -ex "thread apply all bt" or pstack for native code, jstack for the JVM, a goroutine dump for Go. Then I'd look for threads parked in a lock acquisition, such as __lll_lock_wait under pthread_mutex_lock, and for each one identify the lock it wants and who owns it; for a pthread mutex the owner's thread ID is in the mutex structure. That gives a wait-for graph, and a cycle in it is the deadlock: typically two code paths taking the same two locks in opposite orders. If the threads are instead blocked on I/O or a condition variable it is a different problem, such as a dependency that has stopped answering or a lost wake-up. To restore service I'd restart the instance after saving the dump, and the fix is to impose one acquisition order on those locks, or to stop holding one while taking the other.

🧠 Key takeaways

  • Deadlock: a cycle of threads each waiting for a resource the next one holds. No crash, no CPU use, no progress.
  • It needs all four Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait.
  • With single-unit resources, a cycle in the wait-for graph is a deadlock. Thread stacks let you draw that graph.
  • Lock ordering breaks circular wait and is the standard prevention technique.
  • The banker's algorithm grants a request only if some order still lets every process finish: a safe state.
  • Databases detect cycles and abort a victim; operating systems mostly leave user programs to prevent their own.
