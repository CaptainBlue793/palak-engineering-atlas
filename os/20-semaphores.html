Semaphores

A semaphore is the oldest synchronisation tool still in daily use: Edsger Dijkstra described it in 1965. It is an integer with two atomic operations. One takes a unit and waits if there are none; the other puts a unit back and wakes a waiter. That is all, and depending on the number it starts with, the same object is a lock, a limit on how many threads may do something at once, or a signal from one thread to another. A semaphore is what you get if you give a condition variable a memory.

Two operations on a counter

A semaphore holds a non-negative integer, which you can read as "how many units are available". The two operations have several names: Dijkstra called them P and V, from Dutch; textbooks say wait and signal, or down and up; POSIX calls them sem_wait and sem_post.

OperationNamesWhat it does, atomically
TakeP, wait, down, sem_waitIf the value is above 0, subtract 1 and continue. If it is 0, sleep until someone posts
GiveV, signal, up, sem_postIf threads are waiting, wake one of them. Otherwise add 1 to the value. Never blocks

You already know everything needed to build one. This is a semaphore made from Chapter 19's parts:

typedef struct {
    int value;
    pthread_mutex_t m;
    pthread_cond_t nonzero;
} semaphore;

void sem_take(semaphore *s)
{
    pthread_mutex_lock(&s->m);
    while (s->value == 0)                       /* nothing available: wait */
        pthread_cond_wait(&s->nonzero, &s->m);
    s->value--;
    pthread_mutex_unlock(&s->m);
}

void sem_give(semaphore *s)
{
    pthread_mutex_lock(&s->m);
    s->value++;                                  /* the count remembers this, even if nobody is waiting */
    pthread_cond_signal(&s->nonzero);
    pthread_mutex_unlock(&s->m);
}

Compare it with a bare condition variable. A signal sent when nobody is waiting is lost; a post made when nobody is waiting is counted, and the next thread to call wait goes straight through. That one integer is the whole difference, and it is why a semaphore needs no separate mutex and no while loop in the code that uses it: the predicate, "value above zero", is built in.

Three tools, chosen by the starting value

Start at 1: a lock

With one unit, at most one thread can be between its wait and its post. A binary semaphore gives mutual exclusion:

sem_t s;
sem_init(&s, 0, 1);        /* second argument 0: shared between threads, not processes */

sem_wait(&s);
counter++;                 /* critical section */
sem_post(&s);

It is not quite a mutex, though. A mutex has an owner: the thread that locked it is the one that must unlock it, and the library can check that. A semaphore has no owner. Any thread may post, whether or not it ever waited, and nothing notices if one posts twice. That freedom is what makes the other two uses possible, and it is also why a mutex is the better tool when all you want is a lock.

Start at N: a limit

With N units, at most N threads can be inside at once. A counting semaphore is the natural way to guard a pool of identical resources: eight database connections, four GPU slots, a hundred requests in flight to a service that falls over at a hundred and one.

#define POOL 8
static sem_t slots;                         /* sem_init(&slots, 0, POOL) at start-up */

int run_query(const char *sql)
{
    sem_wait(&slots);                       /* the ninth caller sleeps here until a slot is free */
    struct conn *c = pool_take();            /* the pool's own list still needs its own mutex */
    int rc = conn_exec(c, sql);
    pool_return(c);
    sem_post(&slots);                       /* must run on every path out, including errors */
    return rc;
}

The semaphore counts how many may enter. It doesn't say which connection each thread gets, so the pool's list is still shared data and still needs a lock.

Start at 0: a signal

With no units, the first wait blocks until some other thread posts. That makes one thread's progress depend on another's: "don't continue until that has happened".

static sem_t loaded;                        /* sem_init(&loaded, 0, 0) */

void *loader(void *arg) {
    load_config();
    sem_post(&loaded);                      /* "the config is ready" */
    return NULL;
}

void serve(void) {
    sem_wait(&loaded);                      /* blocks until the loader has posted */
    start_accepting();
}

Waiters are woken in arrival order here; POSIX doesn't promise that. A "stray" post comes from a thread that never called wait. That is exactly what a signalling semaphore needs when it starts at 0, and a bug when the semaphore is meant to be a lock or a limit.

Things to notice. Starting at 3, the fourth and fifth threads sleep, and each post lets exactly one of them in while the value stays at 0. Let threads return early without posting and the limit shrinks by one each time, until every new arrival sleeps for ever: nothing crashes, the program just stops. A stray post does the opposite and lets one thread too many inside. Starting at 0, a wait blocks until a post arrives from another thread, and a post that comes first is kept.

Semaphores for ordering

Several semaphores together can express a small protocol. The best-known is the bounded buffer, which uses three: empty counts free slots and starts at the buffer's size, full counts filled slots and starts at 0, and a binary mutex protects the buffer itself.

void produce(item_t x) {                  item_t consume(void) {
    sem_wait(&empty);   /* a free slot */        sem_wait(&full);    /* an item */
    sem_wait(&mutex);                            sem_wait(&mutex);
    buffer_put(x);                               item_t x = buffer_get();
    sem_post(&mutex);                            sem_post(&mutex);
    sem_post(&full);    /* one more item */      sem_post(&empty);   /* one more free slot */
}                                            return x; }

The order of the two waits matters. Swap them in produce, so it takes mutex first and then waits on empty, and a producer that finds the buffer full goes to sleep holding the mutex. No consumer can ever get in to make room, and everything stops. Sleeping while holding a lock is the root of most deadlocks, and Chapter 21 and Chapter 22 take it further.

Semaphore, or mutex and condition variable?

SemaphoreMutex + condition variable
StateA count, kept by the semaphoreAny shared data you like; the condition variable itself has none

A wake-up with no waiterIs remembered in the countIs lost; the shared state must record it
OwnershipNone: any thread may postThe mutex has an owner, which can be checked
Typical bugA missing or extra post, silently changing the countWaiting in an if, or touching the state without the mutex
Best forLimits on concurrency, pools, one-off signals between threadsEverything else, and plain mutual exclusion

The two are equally powerful: each can be built from the other. The choice is about clarity. If what you are protecting really is a number of interchangeable units, a semaphore says so in one line. If the condition is anything richer, such as "the queue has an item and we are not shutting down", a mutex and condition variable keep the logic visible where a set of semaphores would hide it. One practical point in the semaphore's favour: sem_post is one of the few synchronisation calls that POSIX allows inside a signal handler, which makes it the standard way for a handler to wake the main program.

🐧
Why the Linux kernel replaced its semaphores with mutexes

For most of its early history the Linux kernel had one sleeping lock, the semaphore, and used it everywhere. By 2005 the great majority of the kernel's semaphores were initialised to 1 and used purely as locks: taken and released by the same code, never counted, never used to signal. So Ingo Molnar added a dedicated struct mutex, merged in version 2.6.16 in 2006, and those semaphores were converted over the following releases. The gain came from the restriction. Because a mutex has exactly one owner, and only the owner may unlock it, the kernel could add debugging that catches a lock released by the wrong task, released twice or still held when a task exits. It could make the structure smaller and the fast path shorter. And later it could let a waiter spin for a moment when the owner is running on another CPU, which requires knowing who the owner is. None of that is possible with a semaphore, whose count can be raised by anyone. Semaphores remain in the kernel for the cases that need a count. It is the general rule in one story: use the most restricted tool that expresses what you mean.

⚠️
Common mistakes
  • Skipping the post on an error path. Each early return between wait and post leaks a unit. The pool shrinks until the program hangs.
  • Posting more times than you waited. The count rises above its intended maximum and the limit silently stops limiting.
  • Starting with the wrong value. 1 for a lock, N for a pool, 0 for a signal. A lock that starts at 0 blocks its first user for ever.
  • Using a binary semaphore where a mutex would do. You lose ownership checks and gain nothing.
  • Waiting on a counting semaphore while holding a lock. If the wait blocks, the lock is held for the whole sleep. Take the semaphore first.
  • Thinking the semaphore protects the resource itself. It limits how many threads enter. Shared data inside still needs its own lock.

Interview drill

Explain it simply: What is a semaphore, and how does a binary semaphore differ from a mutex?

How a strong answer sounds
A semaphore is a non-negative counter with two atomic operations. Wait decrements it, or blocks if it is zero; post increments it, or wakes a waiter if there is one. Initialised to N it lets at most N threads into a region, which suits resource pools; initialised to 0 it lets one thread wait for an event from another. A binary semaphore, initialised to 1, gives mutual exclusion like a mutex, but with one important difference: it has no owner. Any thread can post it, so it can't detect an unlock by the wrong thread or a double unlock, and it can't support features that depend on knowing the holder, such as priority inheritance or recursive locking. So I'd use a mutex for locking, and a semaphore when I need counting or signalling across threads.

Deeper: You have a service that must never make more than 10 concurrent calls to a downstream API. How do you enforce it, and what can go wrong?

How a strong answer sounds
A counting semaphore initialised to 10: wait before the call, post after it. The eleventh caller blocks until one returns. The main risk is a leaked permit: if any path between the wait and the post exits early, by an error return, an exception or a timeout, the permit is never returned and the effective limit drops, until eventually every caller blocks. So the post has to be in a cleanup construct that runs on every path: goto out in C, finally, defer or a guard object elsewhere. Next, blocking for ever is rarely what I want under overload, so I'd use a timed or try variant and shed load or return an error when no permit is free. I'd also avoid holding any other lock while waiting for a permit, and export the number of waiters as a metric, since a queue building up at the semaphore is the earliest sign the downstream is slow.

🧠 Key takeaways

  • A semaphore is a counter with atomic wait (take one, or sleep at zero) and post (give one, or wake a waiter).
  • Start at 1 for a lock, at N to admit at most N threads, at 0 to make one thread wait for another.
  • Unlike a condition variable, a semaphore remembers a post made before anyone waits.
  • A semaphore has no owner. That enables signalling between threads and removes the safety checks a mutex has.
  • Every wait needs exactly one matching post on every path. A missing one leaks a unit; an extra one breaks the limit.
  • Use a semaphore when the state really is a count of units; use a mutex and condition variable for anything richer.

Check your understanding

A semaphore starts at 3. Five threads call sem_wait and none has called sem_post yet. What is the state?

The first three each take a unit, leaving 0. The fourth and fifth find 0 and sleep until someone posts.

A semaphore starts at 0. Thread A calls sem_post. Later, thread B calls sem_wait. What happens to B?

The count remembers the post. This is the difference from a condition variable, where an early signal would be lost.

What can a mutex check that a binary semaphore can't?

A mutex has an owner. A semaphore's count can be raised by any thread, so it has no notion of who holds it.

A pool is guarded by a semaphore that starts at 8. One code path returns after sem_wait without calling sem_post. What is the long-term effect?

Nothing returns a unit automatically. The limit shrinks with every leak and the program eventually stops making progress.

Which problem is a counting semaphore the most natural tool for?

Interchangeable units and a limit: that is what the count represents. Compound conditions suit a mutex and condition variable; a single counter suits a mutex or an atomic.
