Case Study: Goroutines vs JVM Threads (M:N Scheduling)

The last three case studies each chose between two ways of handling many connections: a thread per connection, which is simple to write and expensive to run, or an event loop, which is cheap to run and awkward to write. Go's goroutines and Java's virtual threads are an attempt to have both. You write ordinary blocking code, one task per connection, and a scheduler inside the language runtime runs millions of those tasks on a handful of kernel threads, with an event loop hidden underneath. This case study looks at how the two runtimes do it, and at the places where the kernel thread underneath shows through.

  • Explain what happens to the kernel thread when a goroutine waits for the network or blocks in a system call
  • Explain Java virtual threads, carrier threads and pinning
  • Choose between platform threads, virtual threads and goroutines for a workload

1:1 and M:N threading

A pthread, and a classic Java thread, is a kernel thread: the kernel creates it, gives it a stack, and schedules it. One thread in the language is one thread in the kernel, which is called 1:1 threading. It's simple and it uses every core, but each thread costs enough that a server can afford thousands, not millions.

M:N threading puts a second scheduler in user space. The program creates M lightweight tasks, and the runtime runs them on N kernel threads, with N about the number of cores. Switching between two tasks on the same kernel thread is a function call that saves a few registers and changes the stack pointer. The kernel isn't involved and doesn't know the tasks exist.

The hard part of M:N has always been blocking. If a task makes a system call that blocks, the kernel puts the kernel thread to sleep, and every other task that was due to run on it waits too. Both runtimes are best understood as a set of answers to that one problem.

Go: G, M and P

// A server written as if threads were free
func handle(conn net.Conn) {
    defer conn.Close()
    buf := make([]byte, 4096)
    n, _ := conn.Read(buf)          // looks blocking. Parks the goroutine, not the thread
    conn.Write(reply(buf[:n]))
}

for {
    conn, _ := ln.Accept()
    go handle(conn)                 // one goroutine per connection, 100,000 of them if need be
}

The Go scheduler has three kinds of object, and their one-letter names are used everywhere, including in its own trace output:

What it isHow many
G: goroutineA task: a small stack, saved registers and a state (running, runnable, waiting)As many as the program starts
M: machineA kernel threadAs many as needed. Most are asleep
P: processorPermission to run Go code, together with a local queue of up to 256 runnable goroutinesExactly GOMAXPROCS, by default the number of cores

An M must hold a P to run a goroutine. That one rule is the design. It caps the number of threads running Go code at the number of cores, however many threads exist, and it gives each running thread a private queue that it can use without taking a lock. The P was added in Go 1.1, in 2013. Before it there was one global queue behind one lock, and that lock was where busy programs spent their time, which is the lesson of Chapter 27 over again.

When the goroutine an M is running blocks or finishes, the M looks for another, in a fixed order:

The fourth step is the hidden event loop. Every socket Go opens is non-blocking. When conn.Read finds no data, the runtime registers the socket with epoll, marks the goroutine as waiting, and switches to another goroutine on the same thread. No kernel thread is waiting for that socket. When the data arrives, the poller hands the goroutine back to a run queue. It is the nginx architecture of Chapter 42, with the state machine replaced by a parked stack.

That only works for calls the runtime can turn into "try, and wait for readiness". A read from a regular file, a call into C code, or any other system call that really blocks leaves the kernel thread stuck. For those, Go does something different:

  • Before the system call, the M marks its P as "in a system call".
  • A monitoring thread called sysmon runs without a P and checks every few tens of microseconds. If a P has been stuck that long and other goroutines are waiting, sysmon takes the P away and gives it to another M, waking an idle one or creating a new kernel thread.
  • When the call returns, the first M has no P. It puts its goroutine on a run queue and goes to sleep.

So other goroutines keep running, at the price of an extra kernel thread for every call that is blocked at once. For the duration of a blocking call, M:N quietly becomes 1:1. sysmon has a second job: it marks any goroutine that has run for 10 ms without yielding, and since Go 1.14 it sends that thread a signal to force the switch. Before that, a loop with no function calls in it could hold a P for ever.

Java virtual threads and pinning

Java went the other way round. Its threads have been kernel threads since the 1990s, now called platform threads, and a large server is built from pools of a few hundred of them. Virtual threads, final in JDK 21 (2023), add M:N scheduling without changing the API: a virtual thread is a java.lang.Thread, and existing blocking code runs on one unchanged.

// One virtual thread per task. No pool: they are cheap enough to create and throw away
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var request : requests)
        executor.submit(() -> handle(request));     // handle() may block on sockets freely
}

A virtual thread runs by being mounted on a carrier, a platform thread from a small pool with one carrier per core. When it blocks on a socket or a java.util.concurrent lock, the JDK unmounts it: its stack frames are copied to the heap, and the carrier takes another virtual thread.

Sometimes the unmount isn't possible, and the virtual thread is pinned: it stays on its carrier, and if it blocks, the carrier blocks with it. In JDK 21 that happened in two cases.

// 1. Blocking inside synchronized (JDK 21 to 23). The monitor was tied to the carrier thread
synchronized (connection) {
    connection.send(request);        // blocks: the carrier is stuck with it
}

// The workaround at the time: a java.util.concurrent lock, which can unmount
lock.lock();
try { connection.send(request); } finally { lock.unlock(); }

// 2. Blocking with a native frame on the stack (still true): the JDK can't copy a C stack frame

With four carriers, four pinned virtual threads are enough to stop every other virtual thread in the process, however many thousands are ready to run. JDK 24 (2025) removed the first case: a virtual thread can now unmount while holding a monitor. The second remains. One more difference from Go matters in practice: virtual threads are never preempted. One that computes without blocking keeps its carrier until it finishes.

A model with round numbers: 1 MB of stack reserved per platform thread, about 4 KB per parked goroutine and 2 KB per parked virtual thread, and a default thread limit of 10,000 in the Go runtime. "Holding a monitor" means inside a synchronized block on the request's own object, so the requests don't contend with each other.

Things to notice. Waiting for the network is the case M:N was built for: the pool of 200 platform threads takes 5 seconds because only 200 requests can wait at once, while goroutines and virtual threads finish in about a tenth of a second on four kernel threads. Now hold a monitor while waiting. On JDK 21 each waiting request pins a carrier, only four can wait at a time, and the burst takes over four minutes; the identical code on JDK 24 is back to a tenth of a second. Native code is the case where the old model wins. Virtual threads are pinned, Go tries to start a kernel thread per call and hits its limit of 10,000, and the plain pool of 200 finishes in 5 seconds. For pure computation the four cards agree, because no scheduler can add cores. Last, drop to 100 requests. Nothing crashes and the worst figure is 2.5 seconds, which is why these problems are found in production and not in testing.

⚖️
Netflix: "Dude, where's my lock?"

In 2024 Netflix engineers described a failure that appeared after services moved to Java 21 with virtual threads handling requests. Instances would stop answering. They weren't using CPU, and they weren't out of memory. The number of sockets waiting to be closed climbed steadily, and the health checks failed. The usual thread dump was no help, because it listed platform threads and the work was on virtual ones. A fuller dump showed thousands of virtual threads that had been created and had never run. The instances had four vCPUs, so four carriers. Each of the four was occupied by a virtual thread that was pinned: inside a synchronized block in a tracing library, it had gone on to wait for a lock. The lock was actually free. Its previous holder had released it, and the next thread in line to take it was another virtual thread, which had been made runnable and needed a carrier to run on. There were none. Nothing was deadlocked in the textbook sense of Chapter 22, since no cycle of locks existed, yet nothing could ever move. The resource that had run out was kernel threads, hidden one layer below the code anyone was reading. The fix at the time was to replace synchronized with a lock that can unmount, and the JDK 24 change removed the cause.

Choosing

The workloadWhat fitsWhy
Many connections, mostly waiting on the networkGoroutines, or virtual threadsA waiting task costs kilobytes and no kernel thread
CPU-bound workA fixed pool of platform threads, one per core, or goroutinesCores are the limit. Lightweight tasks add nothing, and virtual threads aren't time-sliced
Calls into blocking native librariesA bounded pool of platform threads, or goroutines behind a semaphoreEach blocked call needs a real kernel thread whatever the runtime, so bound the number yourself
A mix of short requests and long computationsGoroutines, or separate pools for the twoGo preempts every 10 ms. A computing virtual thread holds its carrier
Limiting load on a database or downstream serviceA semaphoreWith cheap tasks, the pool size no longer limits concurrency for you

The last row is the change of habit that M:N asks for. A pool of 200 threads was also, without anyone designing it, a limit of 200 concurrent calls on whatever sat behind it. A million goroutines have no such limit, and the first thing they exhaust is someone else's connection pool.

⚠️
Common mistakes
  • Pooling virtual threads or goroutines. They are cheap to create. A pool only brings back the limit you were avoiding.
  • Expecting M:N to speed up computation. It makes waiting cheap. Running still needs a core.
  • Starting unbounded numbers of tasks. Without back-pressure, memory and downstream services absorb the load. Goroutines blocked for ever on a channel are a leak.
  • Thousands of concurrent blocking native calls. In Go that is thousands of kernel threads; in Java it is pinned carriers.
  • Ignoring the CPU limit of a container. A runtime that sizes itself to the host's 64 cores inside a 2-CPU cgroup gets throttled (Chapter 34). Go respects the limit by default only since 1.25.
  • Reading a normal thread dump and seeing nothing. Parked virtual threads and goroutines aren't kernel threads. Use the runtime's own dump.

Interview drill

Explain it simply: What is the difference between a goroutine and an operating-system thread?

How a strong answer sounds
An OS thread is created and scheduled by the kernel, has a fixed stack reservation of a megabyte or more, and costs a system call to create and a trip through the kernel to switch. A goroutine is a task managed by the Go runtime in user space. It starts with a stack of about 2 KB that grows on demand, creating one is a small allocation, and switching between two of them is a few hundred nanoseconds with no kernel involvement. The runtime multiplexes many goroutines onto a small number of OS threads, roughly one running per core, which is M:N scheduling. When a goroutine waits for a channel, a mutex or the network, the runtime parks it and runs another on the same thread; network waits are handled by an epoll-based poller underneath. So a program can have hundreds of thousands of goroutines where it could afford only thousands of threads, while the code still reads as straightforward blocking code.

Deeper: What happens when one of those lightweight tasks makes a blocking system call, in Go and in Java?

How a strong answer sounds
It depends on whether the runtime can avoid the block. For sockets, both runtimes use non-blocking I/O with a poller: the task is parked and the kernel thread carries on with other tasks. For a call that truly blocks the kernel thread, such as file I/O or a call into C, the thread is stuck. In Go, the thread, an M, was holding a P, the token needed to run Go code. A monitor thread notices the P has been in a system call too long and hands it to another M, starting a new OS thread if none is idle, so the other goroutines keep running. When the call returns, the original goroutine queues to get a P again. The cost is one OS thread per concurrently blocked call. In Java, a virtual thread that blocks in native code, or inside synchronized before JDK 24, is pinned to its carrier thread: it can't be unmounted, so the carrier blocks. The JDK adds temporary carriers for some operations such as file I/O, but in general pinned threads reduce the carrier pool, and with one carrier per core a few pinned threads can stall the whole application. In both, the practical advice is to bound the number of concurrent truly blocking calls.

🧠 Key takeaways

  • 1:1 threading maps each task to a kernel thread. M:N runs many cheap tasks on a few kernel threads with a scheduler in user space.
  • In Go, a kernel thread (M) needs a P to run a goroutine (G). There are as many Ps as cores, each with a local run queue, and idle Ps steal work.
  • Network waits park the task and use epoll underneath, so no kernel thread waits. This is an event loop presented as blocking code.
  • A truly blocking call still blocks a kernel thread. Go hands the P to another thread; Java pins the carrier.
  • Pinning inside synchronized could stall a JDK 21 application on a few carriers. JDK 24 removed it; native frames still pin.
  • M:N makes waiting cheap, not computing. With cheap tasks, limit concurrency with a semaphore, not a pool.

Check your understanding

In the Go scheduler, what is a P?

There are GOMAXPROCS of them, so at most that many threads run Go code at once.

A goroutine calls conn.Read on a socket with no data waiting. What happens to the kernel thread it was running on?

The socket is non-blocking. The goroutine is parked and made runnable again when epoll reports data.

A goroutine makes a call into a C library that blocks for a second. How do the other goroutines on its P keep running?

The blocked thread keeps the goroutine but loses the P. The cost is an extra kernel thread per blocked call.

On JDK 21, a virtual thread blocks on I/O inside a synchronized block. What is the effect?

With one carrier per core, a handful of pinned threads can stall everything. JDK 24 lifted this restriction.

A service does 100 ms of pure computation per request on 4 cores. It is moved from a pool of 200 platform threads to virtual threads. What changes?

Lightweight threads make waiting cheap. Computation is limited by cores under any scheduler.
