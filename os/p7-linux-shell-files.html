The Linux Shell & Files

This course explains what happens underneath the commands you type, so it helps to be fluent with the commands themselves: moving around the file tree, reading permissions, listing and killing processes, wiring programs together with pipes and redirection, and setting environment variables. Everything here is the user's view. Each later chapter takes one piece of it (a pipe, a file descriptor, a signal, fork) and opens it up.

Paths and the tree

Linux has one directory tree, rooted at /. Disks, USB sticks and even kernel interfaces are attached ("mounted") somewhere inside it. An absolute path starts at the root (/var/log/syslog); a relative path starts at the process's current working directory (logs/app.log), which every process has and which cd changes for the shell. . means the current directory and .. its parent.

Permissions: who may do what

Every file has an owner, a group and nine permission bits: read, write and execute for the owner, the group and everyone else. ls -l shows them as a string:

$ ls -l /home/ada/scripts/deploy.sh /etc/shadow
-rw-r--r-- 1 ada  ada   212 Oct  1 09:12 /home/ada/scripts/deploy.sh
-rw-r----- 1 root shadow 1203 Sep 30 18:40 /etc/shadow
$ chmod 755 /home/ada/scripts/deploy.sh      # rwxr-xr-x: owner all, others read+execute
$ chmod u+x,g-w notes.txt                    # symbolic form: add x for user, remove w for group

Read the first string as: file type (- regular file, d directory, l symlink), then rw- for the owner, r-- for the group, r-- for others. The octal form is the same nine bits in three-bit groups (P5): 7 = rwx, 5 = r-x, 4 = r--. On a directory, r lets you list names, w lets you create and delete entries, and x lets you pass through it to reach what's inside. The kernel checks these bits on every open(); user root (UID 0) bypasses most of them, which is why Chapter 36 is about not running as root.

Processes from the outside

Every running program is a process with a numeric PID, a parent (PPID), an owner and a state. ps lists them once; top refreshes the list live, sorted by CPU use.

$ ps -eo pid,ppid,user,stat,%cpu,rss,cmd | head -5
    PID    PPID USER     STAT %CPU   RSS CMD
      1       0 root     Ss    0.0 12840 /sbin/init
    812       1 root     Ss    0.0  9020 sshd: /usr/sbin/sshd -D
   1734       1 www-data S     2.1 48212 nginx: worker process
   2210    2190 ada      R+   98.7  3184 ./crunch
$ kill 2210          # sends SIGTERM (15): "please exit", the program can clean up
$ kill -9 2210       # sends SIGKILL (9): the kernel ends it; no clean-up possible

kill doesn't really kill: it sends a signal, a small numbered notification (Chapter 9). SIGTERM lets a well-written server finish in-flight requests and flush logs; SIGKILL can't be caught, so the process gets no chance to tidy up. Always try TERM first. Ctrl+C in the terminal sends SIGINT to the foreground program. The STAT column's first letter is the process state: R running or runnable, S sleeping (waiting for something), D uninterruptible disk wait, Z zombie; Chapter 4 explains each.

Pipes and redirection

Every process starts with three open streams: standard input (0), standard output (1) and standard error (2). By default all three are the terminal. The shell can point them elsewhere before starting a program, and the program never knows:

You typeEffectTypical use
cmd > out.txtstdout to a file, truncating it firstSave a report

cmd 2> err.txtstderr (stream 2) to a fileSeparate errors from data
cmd > all.txt 2>&1stdout to the file, then stderr to wherever stdout now goesCapture everything from a cron job

a | ba's stdout connected to b's stdin through a pipe; both run at onceps aux | grep nginx
cmd > /dev/nullOutput discardedSilence a noisy command

Environment variables

Every process carries an environment: a list of NAME=value strings. A child process gets a copy of its parent's environment when it is created, so export in your shell affects programs you start afterwards, never your parent or programs already running. The most important variable is PATH: when you type grep, the shell tries each directory in PATH in order until it finds an executable file named grep.

$ echo $PATH
/usr/local/bin:/usr/bin:/bin
$ export LOG_LEVEL=debug        # set and export to future children
$ ./server                      # server sees LOG_LEVEL=debug via getenv("LOG_LEVEL")
$ LOG_LEVEL=warn ./server       # set for this one command only
$ which python3                 # which PATH entry wins?
/usr/bin/python3

The shell script that deleted home directories

In January 2015, users of Valve's Steam client for Linux reported that it had deleted every file they owned. The uninstall script contained rm -rf "$STEAMROOT/"*. When the script was run in a way that left STEAMROOT empty, the command became rm -rf "/"*, and it removed everything the user had permission to delete, including mounted backup drives. Three habits from this chapter would have stopped it: start scripts with set -u so an unset variable is an error, use ${STEAMROOT:?} to abort when a variable is empty, and remember that permissions, not caution, are what limit the damage a command can do, which is the argument for running things as an unprivileged user.

⚠️
Common mistakes
  • Reaching for kill -9 first. The process can't flush buffers, release lock files or finish requests. Send SIGTERM, wait, then escalate.
  • chmod 777 to "fix" a permission error. It lets every user modify the file. Find out which user needs which access.
  • Writing cmd 2>&1 > file. Order matters: this sends stderr to the old stdout (the terminal). Write > file 2>&1.
  • Unquoted variables in scripts. rm $f breaks on spaces and empties; write rm -- "$f" and use set -u.
  • Expecting export in a script to change your shell. The script runs as a child with a copy of the environment; use source script.sh to run it in the current shell.

Interview drill

Explain it simply: What is the difference between kill and kill -9?

How a strong answer sounds
kill sends SIGTERM, a request to exit that the program can catch to finish in-flight work, flush buffers and remove lock or PID files. kill -9 sends SIGKILL, which cannot be caught or ignored: the kernel stops the process immediately with no clean-up. Use TERM first and give it a timeout, as systemd and Kubernetes do; KILL is the last resort. Even KILL won't take effect until a process stuck in uninterruptible disk wait (state D) returns from the kernel.

Deeper: You run ./deploy.sh and get "Permission denied", but bash deploy.sh works. Why?

How a strong answer sounds
Running ./deploy.sh asks the kernel to execve the file itself, which requires the execute bit for your user; the file is probably rw-r--r--. Running bash deploy.sh executes /bin/bash, which is executable, and bash merely reads the script, which only needs read permission. The fix is chmod u+x deploy.sh (and a #!/bin/bash first line so the kernel knows which interpreter to start). Other causes are a filesystem mounted noexec, or a missing execute bit on a directory in the path.

🧠 Key takeaways

  • One tree from /; relative paths start at the process's current working directory.
  • Nine permission bits (owner, group, others × rwx), written in octal like 0755; the kernel checks them on every open and exec.
  • ps and top show processes; kill sends signals: TERM to ask, KILL to force.
  • Every process has stdin, stdout and stderr; the shell redirects them with >, >>, 2>, < and connects them with |.
  • Children get a copy of the environment; PATH decides which program a bare command name runs.

Check your understanding

What does -rwxr-x--- mean for a file?

After the type character come three triples: owner rwx, group r-x, others ---. In octal, 0750.

Which command captures both normal output and error messages of backup.sh into run.log?

Redirections apply left to right: first stdout goes to the file, then stderr is pointed at wherever stdout now points. The reverse order sends stderr to the terminal.

A server ignores kill 4120. What does kill -9 4120 do differently?

kill defaults to SIGTERM (15), which programs may handle or ignore. SIGKILL (9) is enforced by the kernel.

You run export API_KEY=abc in a terminal. Which processes see the new variable?

The environment is copied into a child when it's created. Existing processes keep the copy they got at their start.

In ps aux | grep nginx, how is ps's output delivered to grep?

The shell creates a pipe, then starts both programs with their standard streams pointed at its two ends. Chapters 9, 10 and 41 show the system calls.
