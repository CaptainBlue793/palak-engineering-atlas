Reading Syscalls & Man Pages

Every program, in every language, talks to the operating system through one narrow door: system calls. Python's open(), Java's FileInputStream and Go's net.Listen all end up as openat, read, socket and bind. Two skills follow from that. You can look any of them up in the manual and know exactly how it fails, and you can watch any program's system calls live with strace, which turns "it just hangs" or "it says permission denied" into a specific line with a specific error. This chapter teaches both.

  • Read a man page's SYNOPSIS, RETURN VALUE and ERRORS sections
  • Check return values and use errno correctly
  • Run strace with the five options that matter
  • Read a trace and find the failing or slow call

Library calls vs system calls

A system call is a request to the kernel: the program executes a special instruction, the CPU switches to kernel mode, and the kernel does something only it is allowed to do (Chapter 2 shows the mechanism). A library function is ordinary code in your process, usually from the C library (libc). Many library functions are thin wrappers around one system call; others do a lot of work in user space and call the kernel rarely or never.

You callKindWhat reaches the kernelManual

The number after man is the section: 1 is commands (man 1 ls), 2 is system calls, 3 is library functions, 5 is file formats (man 5 passwd), 7 is overviews (man 7 signal, man 7 epoll) and 8 is admin commands. When a name exists in two sections, like printf (a shell command and a C function), the section number picks the one you mean.

Reading a man page

Every section-2 page has the same shape. Here is the part of man 2 read you'll consult most:

SYNOPSIS
       #include <unistd.h>
       ssize_t read(int fd, void buf[.count], size_t count);

RETURN VALUE
       On success, the number of bytes read is returned (zero indicates end of
       file), and the file position is advanced by this number.  It is not an
       error if this number is smaller than the number of bytes requested ...
       On error, -1 is returned, and errno is set to indicate the error.

ERRORS
       EAGAIN The file descriptor fd refers to a file other than a socket and has
              been marked nonblocking (O_NONBLOCK), and the read would block.
       EBADF  fd is not a valid file descriptor or is not open for reading.
       EINTR  The call was interrupted by a signal before any data was read.
       ...

Read it in that order. SYNOPSIS gives the header to include and the exact types. RETURN VALUE tells you what success and failure look like, and here hides the most-missed sentence in Unix: a short read is not an error. ERRORS lists every errno value the call can produce and what each means, which is your checklist for error handling. The DESCRIPTION, NOTES and BUGS sections fill in the details when you need them.

Return values and errno

The convention almost every system call follows: return −1 on failure and store a reason code in the thread-local variable errno. A few return a pointer and signal failure with NULL or MAP_FAILED. errno is only meaningful immediately after a call that failed; a successful call may leave any old value in it.

#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>

int fd = open("/etc/server/server.conf", O_RDONLY);
if (fd < 0) {
	if (errno == ENOENT) {                     /* expected: fall back to defaults */
		fd = open(fallback_path, O_RDONLY);
	} else {                                   /* unexpected: report and stop */
		fprintf(stderr, "open %s: %s\n", path, strerror(errno));
		return -1;
	}
}

Four errno values come up constantly in this course. ENOENT: no such file. EACCES/EPERM: permission denied (file mode, or a missing privilege). EINTR: a signal interrupted a blocking call, so retry it. EAGAIN (same value as EWOULDBLOCK): a non-blocking call would have had to wait, the basis of event loops in Chapter 28.

strace in five minutes

strace runs a program (or attaches to a running one) and prints every system call it makes, with decoded arguments, the return value and the error name. It works through ptrace, the same kernel interface debuggers use: the kernel stops the traced process at every system call entry and exit and lets strace look at its registers.

$ strace ./server                     # trace from the start
$ strace -f ./server                  # follow children and threads too (almost always wanted)
$ strace -e trace=openat,connect ./app   # only these calls (also: trace=file, trace=network, trace=%process)
$ strace -T -tt ./app                 # time spent in each call, and a timestamp per line
$ strace -c ./app                     # no per-call output: a summary table of counts, errors and time
$ strace -p 4120 -f -o trace.txt      # attach to a running process, write to a file

The five-second DNS delay in Kubernetes

A well-known problem from around 2018: some requests from pods on Kubernetes took exactly five seconds longer than they should. Application logs showed nothing. strace -T on the slow process showed it immediately: a poll() on the DNS socket returning 0 (Timeout) after 5.00 seconds, then a retry that answered in a millisecond. Five seconds is glibc's default resolver timeout. The root cause was a race in the kernel's connection tracking: glibc sends the A and AAAA lookups in parallel from the same UDP socket, and under some network setups the second packet was dropped. Fixes included the resolver option single-request-reopen and node-local DNS caches. The diagnosis took one command, because a round number like 5.00 in a -T column is almost always a timeout someone configured.

⚠️
Common mistakes
  • Checking errno without checking the return value. errno is only set on failure; after success it holds whatever an earlier call left there.
  • Calling another function before reading errno. Even printf may change it. Save it, or use it at once in strerror(errno).
  • Treating every −1 in a trace as the bug. ENOENT on a config search path or EAGAIN in an event loop are normal. Look for the error that the program acted on, usually just before it writes an error message or exits.
  • Forgetting -f. Without it you trace only the first thread or process and miss what the workers do.
  • Leaving strace attached to a busy production process. It can slow it down dramatically. Use -c briefly, or eBPF-based tools (Chapter 37).

Interview drill

Explain it simply: Is printf a system call?

How a strong answer sounds
No. printf is a C library function (section 3 of the manual). It formats the text into a buffer in the process's own memory, and only when the buffer is flushed (when it fills, at a newline if stdout is a terminal, on fflush, or at exit) does the library make the actual system call, write(1, buf, n). That buffering is why a program that crashes can lose output it "printed", and why strace may show one write for many printf calls.

Deeper: A service fails to start with a vague "initialisation failed". How would you find out why without reading its source?

How a strong answer sounds
Run it under strace -f -o trace.txt, then search the trace for failing calls (= -1) and read backwards from the end, where the program wrote its error message and exited. Most start-up failures show up as a specific call and errno: openat ... ENOENT for a missing file, EACCES for permissions, bind ... EADDRINUSE or EACCES for a port, connect ... ECONNREFUSED for a dependency that's down. I'd ignore expected failures like probing several config paths and focus on the last error before the exit. If it hangs instead, -T or attaching with -p shows which call it is blocked in.

🧠 Key takeaways

  • System calls are requests to the kernel (man section 2); library functions run in your process (section 3) and may or may not make system calls.
  • Read man pages via SYNOPSIS, RETURN VALUE and ERRORS: the ERRORS list is your error-handling checklist.
  • System calls return −1 and set errno on failure; check the return value first, read errno immediately.
  • strace -f shows every call with arguments, results and errors; -T times them, -c summarises, -p attaches.
  • In a trace, find the error the program acted on, or the call it spent its time in.

Check your understanding

Which manual section documents openat, and which documents fopen?

Section 2 is system calls, section 3 library functions. fopen calls openat internally and adds a user-space buffer.

read(fd, buf, 4096) returns 1200. What does that mean?

A short read is normal, especially on pipes and sockets. Only 0 (end of file) and −1 (error) are special.

When is the value of errno meaningful?

Successful calls don't reset errno, so it can hold a stale value. Check the return value first.

Your program forks worker processes, and the error happens in a worker. Which strace option do you need?

Without -f, strace traces only the process it started; children created by fork or clone are invisible.

In an strace -T output, one line reads poll([{fd=3, events=POLLIN}], 1, 5000) = 0 (Timeout) <5.005112>. What happened?

The third argument is the timeout in milliseconds, a return of 0 means no fd became ready, and the time in angle brackets confirms the 5-second wait.
