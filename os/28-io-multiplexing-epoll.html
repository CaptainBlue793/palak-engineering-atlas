I/O Multiplexing: select, poll, epoll

A chat server holds 50,000 open connections. At any instant perhaps twenty of them have something to say; the rest are idle. Giving each connection its own thread means 50,000 threads asleep in read(). The alternative is to turn the question round. Instead of each thread asking "is there data on my socket?", one thread asks the kernel "which of my 50,000 sockets have data?" and handles only those. That is I/O multiplexing, and how well the kernel can answer that question decides how many connections one machine can hold. It is the mechanism under nginx, Redis, Node.js, HAProxy and every async runtime.

Blocking I/O, and one thread per connection

By default a descriptor is blocking: read() on a socket with nothing to read puts the thread to sleep until bytes arrive. That makes simple code, one thread per connection, each written as if it were the only one:

for (;;) {
    ssize_t n = read(conn, buf, sizeof buf);     /* sleeps here, perhaps for minutes */
    if (n <= 0) break;
    handle(conn, buf, n);
}

It works well up to a few thousand connections. Past that, the costs of Chapter 27 take over: a stack and kernel structures per thread, and a scheduler juggling thousands of threads when a burst of traffic wakes them. In 1999 Dan Kegel named this the C10K problem: how should a server handle ten thousand clients at once? The answer was to stop dedicating a thread to each.

Non-blocking descriptors

A descriptor can be switched to non-blocking mode. Then a read() with nothing to read returns at once with the error EAGAIN ("try again later") instead of sleeping.

int flags = fcntl(fd, F_GETFL);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);

ssize_t n = read(fd, buf, sizeof buf);
if (n < 0 && errno == EAGAIN) {
    /* nothing there right now: go and do something else */
}

Now one thread can serve many connections, by trying each in turn. But a loop that keeps trying 50,000 sockets, nearly all of which answer EAGAIN, is the busy-wait of Chapter 19 with a system call in it. The thread needs to sleep until any of its descriptors is ready, and then be told which. That service is called readiness notification.

select and poll: ask about everything, every time

The original interfaces are select (1983) and poll. You hand the kernel the complete list of descriptors you care about; it sleeps until at least one is ready, and marks which.

struct pollfd fds[MAX];                         /* fd and events wanted, for every connection */

for (;;) {
    int n = poll(fds, nfds, -1);                 /* the whole array goes into the kernel, every call */
    for (int i = 0; i < nfds; i++)               /* and you scan the whole array to find the ready ones */
        if (fds[i].revents & POLLIN)
            handle(fds[i].fd);
}

It works, and it is still fine for a handful of descriptors. The flaw is in the shape of the interface. The kernel keeps nothing between calls, so on every call the full list is copied in, every descriptor on it is checked, and the program then walks the full list again to find the few that were marked. With 50,000 connections and 20 active, each trip does 50,000 units of work to deliver 20 results, and a busy server makes that trip thousands of times a second. select has a further limit: its bitmap is fixed at 1,024 descriptors.

epoll: tell the kernel once

Linux's epoll (2002) splits the job into two. You register interest in a descriptor once, and the kernel remembers. Later you ask only for what has become ready.

  • epoll_create1() makes an epoll instance, itself a descriptor.
  • epoll_ctl() adds, changes or removes one descriptor in its interest list.
  • epoll_wait() sleeps until the ready list is non-empty, then returns its contents.
int ep = epoll_create1(0);
struct epoll_event ev = { .events = EPOLLIN, .data.fd = listen_fd };
epoll_ctl(ep, EPOLL_CTL_ADD, listen_fd, &ev);

for (;;) {
    struct epoll_event ready[64];
    int n = epoll_wait(ep, ready, 64, -1);            /* sleep until something is ready */

    for (int i = 0; i < n; i++) {                    /* only the ready ones: no scan */
        int fd = ready[i].data.fd;
        if (fd == listen_fd) {                        /* a new client */
            int c = accept4(listen_fd, NULL, NULL, SOCK_NONBLOCK);
            ev.events = EPOLLIN; ev.data.fd = c;
            epoll_ctl(ep, EPOLL_CTL_ADD, c, &ev);     /* registered once, for its whole life */
        } else {                                      /* data from an existing client */
            char buf[4096];
            ssize_t len = read(fd, buf, sizeof buf);
            if (len <= 0) { close(fd); continue; }   /* closing also removes it from the epoll set */
            write(fd, buf, len);                      /* echo it back */
        }
    }
}

Level-triggered and edge-triggered

There are two meanings "ready" can have, and epoll offers both.

  • Level-triggered (the default): a descriptor is reported for as long as it has data. If you read only part of what is there, the next epoll_wait reports it again. Forgiving, and exactly how select and poll behave.
  • Edge-triggered (EPOLLET): a descriptor is reported when it becomes ready, once. The kernel won't mention it again until more data arrives.

Edge-triggered mode produces fewer wake-ups, which matters when several threads share one epoll instance. It comes with a strict rule: when a descriptor is reported, read until you get EAGAIN. If you take one buffer's worth and go back to waiting, the rest of the data stays in the kernel, the edge has already passed, and the connection stalls, possibly for ever if the client is itself waiting for your reply.

/* Edge-triggered: drain the socket completely each time it is reported. */
for (;;) {
    ssize_t len = read(fd, buf, sizeof buf);
    if (len > 0) { consume(fd, buf, len); continue; }
    if (len < 0 && errno == EAGAIN) break;        /* empty: safe to wait again */
    close(fd); break;                             /* 0 = the peer closed; otherwise a real error */
}

Things to notice. With 100,000 idle connections, each select call examines 100,008 descriptors to find the one or two you clicked, and epoll examines one or two. In level-triggered mode, reading once is safe: whatever is left is reported again on the next call. In edge-triggered mode, read once and call wait again: the connection turns red, with 100 bytes that nobody will ever be told about unless the client happens to send more. Switch to "read until EAGAIN" and the problem can't occur.

C10K: the web page that changed how servers are built

In 1999 a typical web server ran a process or a thread per connection, and hardware had just become able to serve far more clients than that design could hold. Dan Kegel collected the options on a page titled "The C10K problem", and laid out the argument that the limit was the operating system's interface, not the machine: select and poll spent their time re-examining idle connections. The page became a reference point for kernel and server developers. Within three years FreeBSD had kqueue and Linux had epoll, both built on the idea in this chapter, that the kernel should remember what you are interested in and report only changes. A generation of servers followed that used one event loop per core instead of a thread per client: nginx, written by Igor Sysoev for a busy Russian web portal and released in 2004, then lighttpd, HAProxy, memcached, Redis and Node.js. Today a single ordinary server holding a million idle connections is unremarkable, and what limits it is memory per connection, not the cost of finding out who is ready.

What readiness can't do

  • Regular files are always "ready". Readiness is about whether a call would have to wait for the other side. A disk file has no other side, so epoll reports it readable at once, and the read() then blocks for a disk seek all the same. Event-driven servers hand file I/O to a thread pool (Chapter 27) or use io_uring (Chapter 29).
  • It doesn't do the I/O. You are told a socket is readable; you still make a read system call for each one. At very high rates those calls are the cost, which io_uring also addresses.
  • One slow handler stalls everyone. While the loop's thread is computing for one connection, the other 49,999 wait. The next chapter is about living with that.
⚠️
Common mistakes
  • Edge-triggered without draining. Read (or accept, or write) until EAGAIN, every time, or connections will stall.
  • Blocking descriptors under an event loop. A readiness report can be out of date by the time you read. With a blocking socket, that hangs the whole loop. Always use O_NONBLOCK.
  • Asking for writability all the time. A socket is nearly always writable, so a level-triggered loop spins at 100% CPU. Register for EPOLLOUT only while you have data waiting to go.
  • Assuming one read is one message. TCP delivers a byte stream. A request may arrive in pieces or several may arrive together; buffer and parse.
  • Using select in new code with many descriptors. A descriptor number above 1,023 overflows its bitmap.
  • Expecting epoll to make file reads asynchronous. It doesn't. Disk I/O still blocks.

Interview drill

Explain it simply: Why is epoll faster than select for a server with many connections?

How a strong answer sounds
Because of how much work each call does. With select or poll the kernel has no memory of your descriptors, so every call passes the entire set in, the kernel checks every one, and then the program scans the entire set again to find which were marked ready. That is proportional to the total number of connections, on every call, even if only one is active. With epoll you register each descriptor once using epoll_ctl, and the kernel keeps that interest list. When data arrives on a socket, the socket adds itself to the epoll instance's ready list through a callback. epoll_wait just returns that list, so the work is proportional to the number of ready descriptors. For ten thousand mostly idle connections that is the difference between examining ten thousand entries and examining a handful, thousands of times a second. select also has a hard limit of 1,024 descriptors.

Deeper: What is the difference between level-triggered and edge-triggered epoll, and what must an edge-triggered program do?

How a strong answer sounds
Level-triggered reports a descriptor whenever its condition holds: while unread data remains, every epoll_wait returns it. Edge-triggered reports only the transition: when new data arrives on a socket, you are told once, and not again until more arrives. So with edge-triggering the program must consume everything available when notified: use non-blocking descriptors and loop on read, or accept, or write, until it returns EAGAIN. If it reads only part and returns to epoll_wait, the remaining bytes sit in the kernel buffer with no further notification, and the connection hangs. Edge-triggering reduces redundant wake-ups, which helps when several threads wait on one epoll instance, usually together with EPOLLONESHOT or EPOLLEXCLUSIVE so only one thread handles a given event. The price is that draining loop, and care that one very busy connection doesn't starve the others while it is being drained.

🧠 Key takeaways

  • One thread per connection stops scaling at thousands of connections; the alternative is one thread watching many descriptors.
  • Non-blocking descriptors return EAGAIN instead of sleeping; readiness notification says which descriptors are worth trying.
  • select and poll re-examine every descriptor on every call: work proportional to the total.
  • epoll keeps an interest list in the kernel and returns a ready list: work proportional to the active connections.
  • Level-triggered repeats while data remains; edge-triggered reports once, so you must read until EAGAIN.
  • Readiness doesn't cover disk files or CPU-heavy handlers; both still block the loop.

The edge, "became readable", has already been reported. Edge-triggered code must read until EAGAIN.

Readiness describes waiting for a peer. Disk I/O needs a thread pool or a true asynchronous interface such as io_uring.
