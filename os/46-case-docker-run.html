Case Study: What docker run Really Does

Chapter 34 showed that a container is an ordinary process with a restricted view and a budget, and built one from namespaces and cgroups by hand. This case study follows the real command. Between pressing Enter on docker run and the first instruction of your program, five other programs take part, an image is fetched and stacked into a file system, one system call creates a process that can see almost nothing, and a handful of files set its limits. Then your program starts as process number 1, a position with rules of its own, and those rules are behind the most common container complaint there is: "why does it take ten seconds to stop?"

Two things in that listing are worth a second look. nginx is a normal process on the host with a normal host PID, 4431, as Chapter 34 said it would be. Since no container is a child of dockerd, the daemon can be upgraded or can crash without taking the containers with it.

Image layers and overlayfs

An image name such as nginx:1.27 resolves to a manifest: a small JSON document listing the image's layers by the SHA-256 hash of their contents. Each layer is a compressed tar archive of the files one build step added or changed.

Because a layer is named by its hash, identical layers are downloaded once and stored once, however many images use them. To make a root file system, containerd unpacks each layer into its own directory, and the kernel stacks them with one mount call:

So starting a container copies no files at all, which is why it takes a fraction of a second where booting a virtual machine takes many. A hundred containers from one image share one copy of its files on disk, and one copy in the page cache (Chapter 31), since they are reading the same files.

clone() with namespaces

containerd hands runc a directory holding that root file system and a file, config.json, written to an open standard, the OCI runtime specification. Everything about the container is in it:

{
  "process": { "args": ["nginx", "-g", "daemon off;"], "user": { "uid": 0 },
               "capabilities": { "bounding": ["CAP_CHOWN", "CAP_NET_BIND_SERVICE", "…"] }, "noNewPrivileges": false },
  "root":    { "path": "rootfs" },
  "hostname": "3f2a9c81d0b2",
  "linux": {
    "namespaces": [ {"type": "pid"}, {"type": "mount"}, {"type": "ipc"}, {"type": "uts"}, {"type": "cgroup"},
                    {"type": "network", "path": "/var/run/docker/netns/5d1c0a7e9b21"} ],
    "resources":  { "memory": { "limit": 268435456 }, "cpu": { "quota": 150000, "period": 100000 } },
    "seccomp":    { "defaultAction": "SCMP_ACT_ERRNO", "syscalls": [ "…" ] }
  }
}

runc turns that file into system calls, in an order that matters:

/* What runc does, in outline */
pid = clone(child, stack, CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWCGROUP | SIGCHLD, arg);
write(cgroup_procs_fd, pid_string, len);       /* parent: put the child in its cgroup before it runs anything */

/* in the child, which is already PID 1 of a new PID namespace: */
setns(netns_fd, CLONE_NEWNET);                 /* join the network namespace dockerd prepared */
sethostname("3f2a9c81d0b2", 12);
mount("overlay", rootfs, "overlay", 0, layers);  /* the stacked image */
mount("proc", "rootfs/proc", "proc", 0, NULL);  /* a /proc that shows only this PID namespace */
pivot_root(rootfs, old_root);                  /* swap the root; then unmount the old one so the host isn't reachable */
umount2(old_root, MNT_DETACH);
/* privileges go last, because the steps above needed them: */
drop_capabilities();                           /* keep 14 of about 40 */
load_seccomp_filter();                         /* refuse about 44 system calls */
execve("/usr/sbin/nginx", argv, envp);          /* the container's program replaces runc's code */

The last line is the reason runc disappears: your program doesn't run under the runtime, it replaces it, keeping the namespaces, the cgroup and the reduced privileges that were set up around it (Chapter 3). The network is prepared by dockerd beforehand: a virtual cable with one end inside the new network namespace as eth0 and the other on a bridge on the host, and for -p 8080:80 a rule sending the host's port 8080 to the container's port 80.

Because runc enters the container before handing over, it has to assume the container is hostile. In 2019 a flaw, CVE-2019-5736, let a malicious image overwrite the host's runc binary through /proc/self/exe at that moment and so gain root on the host. The fix has runc run from a sealed copy of itself held in memory, so there's no file on the host for a container to reach.

PID 1 and signals

Inside its new PID namespace, the program runc started is process 1. On a normal system PID 1 is init, and the kernel gives that position three special rules. They apply to your program now.

  • Signals without a handler are discarded. For any other process, SIGTERM with no handler means "terminate". For PID 1 the kernel doesn't apply default actions, so a signal the program hasn't asked to handle does nothing. (SIGKILL sent from the host still works.)
  • Orphans arrive. A process whose parent dies is re-parented to PID 1, which is expected to call wait for it. If it doesn't, each one stays behind as a zombie.
  • When PID 1 exits, the namespace ends. The kernel kills every other process in it at once, with SIGKILL.

docker stop sends SIGTERM to PID 1, waits ten seconds, and then sends SIGKILL. What happens in those ten seconds depends entirely on which program is PID 1, and that is decided by how the image starts your application.

What happened
    The app is a web server with 12 requests in flight, each needing up to 2 seconds more. The script is a shell script whose last line is node server.js, without exec. --init puts a tiny init program, tini, at PID 1 with the app as its child.

    Things to notice. With the app as PID 1 and no handler, the stop takes the full ten seconds and ends in a kill, with status 137 and twelve requests cut off. The program did nothing wrong by ordinary standards, since the default action would have ended it immediately anywhere else. Add a handler and the same container stops in two seconds with status 0. Now put the script in front. The handler makes no difference, because the shell is PID 1, discards the signal and doesn't pass it on. The app never learns that it was asked to stop. With --init, tini forwards the signal, and the app, no longer PID 1, gets ordinary behaviour: instant death by default, or a clean shutdown with a handler. The orphan button shows the other duty. A shell or tini collects orphans, and an application at PID 1 usually doesn't, so its zombies pile up.

    # The two fixes, in a Dockerfile and a start script
ENTRYPOINT ["node", "server.js"]        # exec form: no shell in between. (ENTRYPOINT node server.js would add one)

#!/bin/sh
export DB_URL="$(cat /run/secrets/db_url)"
exec node server.js                       # exec: node replaces the shell and becomes PID 1

$ docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' web
137 false                                 # 128 + 9: killed by SIGKILL, and not for memory. A stop that timed out
    ⚖️
    The zombie reaping problem, and a flag added to fix it

    In 2015 the makers of a popular base image, Phusion, published an article titled "Docker and the PID 1 zombie reaping problem". Their point was that almost every image of the time ran its application directly as PID 1, and almost no application was written to do an init system's job. Applications that started helper programs, and many do, for image conversion, health checks or shell commands, left zombies behind whenever a helper outlived the process that started it. Each zombie holds a slot in the process table, and a long-running container could collect thousands and finally fail to start new processes at all. The same images ignored SIGTERM, so every deployment waited out a ten-second timeout per container and then killed it mid-request. The article was widely read, and the ecosystem's response was a very small program: tini, a few hundred lines of C that starts one child, forwards signals to it and reaps every orphan. It was so widely added to images that Docker built it in, as docker run --init, in version 1.13 in 2017. The same rules now sit behind Kubernetes rolling updates. A pod is sent SIGTERM and given 30 seconds, and a service whose PID 1 never passes the signal on drops requests on every deployment.

    ⚠️
    Common mistakes
    • Shell-form or wrapper-script entrypoints without exec. A shell becomes PID 1 and your app never receives the stop signal.
    • No SIGTERM handler in a program that runs as PID 1. The default action doesn't apply there. Every stop becomes a ten-second wait and a kill.
    • Reading exit status 137 as "out of memory". It means SIGKILL. Check OOMKilled to tell a memory kill from a stop that timed out.
    • Writing data into the container layer. It is slow for large files, because of the copy-up, and it is deleted with the container.
    • Thinking the daemon runs the container. The kernel does. The daemon only set it up, which is why containers outlive it.
    • Treating root in a container as harmless, or as the same as root on the host. It is root with fewer capabilities and a system-call filter, sharing the host's kernel.
    🎤
    Interview drill

    Explain it simply: What happens when you run docker run nginx?

    How a strong answer sounds
    The docker CLI sends an API request over a Unix socket to the Docker daemon. If the image isn't present, it is pulled: a manifest lists layers by content hash, and each missing layer is downloaded and unpacked. The daemon asks containerd to create the container; containerd prepares a root file system by stacking the read-only image layers with a new empty writable layer using overlayfs, and writes an OCI configuration describing the process, namespaces, limits and security settings. It starts a shim process, which invokes runc. runc creates a new process with clone in new PID, mount, network, UTS and IPC namespaces, places it in a new cgroup with the memory and CPU limits, switches its root to the overlay mount with pivot_root, drops capabilities and installs a seccomp filter, and finally calls exec on nginx. runc exits and the shim remains as the parent, so the container doesn't depend on the daemon staying up. The result is an ordinary host process that sees itself as PID 1 in an isolated environment.

    Deeper: A container takes exactly ten seconds to stop and exits with status 137. Why, and how do you fix it?

    How a strong answer sounds
    docker stop sends SIGTERM to the container's PID 1, waits for a grace period, ten seconds by default, and then sends SIGKILL; 137 is 128 plus 9, so the process was killed after ignoring the SIGTERM. There are two usual causes. One is that the application is PID 1 and has no SIGTERM handler: the kernel doesn't apply default signal actions to PID 1 of a namespace, so the signal is dropped. The other is that PID 1 isn't the application at all but a shell, from a shell-form entrypoint or a wrapper script that doesn't use exec, and shells don't forward signals to their children. The fixes are to use the exec form of ENTRYPOINT, to end wrapper scripts with exec, to add a SIGTERM handler that stops accepting work and finishes what is in flight, or to run a minimal init such as tini with --init, which forwards signals and also reaps orphaned zombies. I'd also check OOMKilled in docker inspect, because 137 from the memory limit looks the same but wouldn't take ten seconds.

    🧠 Key takeaways

    • docker run passes through the CLI, dockerd, containerd, a shim and runc. Only the kernel enforces anything, and the container's parent is the shim.
    • An image is a list of content-addressed layers. A container's root is those layers stacked read-only under one empty writable layer, with nothing copied.
    • runc clones a process into new namespaces, puts it in a cgroup, pivots the root, drops privileges and then execs your program in its own place.
    • Resource flags are values in cgroup files: exceed memory and a process is killed, exceed CPU and it is throttled.
    • Your program is PID 1: unhandled signals are discarded, orphans are its to reap, and its exit ends the container.
    • Use exec-form entrypoints, exec in scripts, a SIGTERM handler, or --init. Status 137 means SIGKILL.

    Check your understanding

    Once a container is running, which process is its parent on the host?

    runc exits after starting the program, and the shim stays. That is why restarting the daemon doesn't kill containers.

    Fifty containers are started from one 800 MB image. Roughly how much extra disk do they use at the start?

    Starting a container is a mount, not a copy. A file is copied only when a container first writes to it.

    Why does runc drop capabilities and install the seccomp filter last, just before exec?

    Set up the environment with full privilege, reduce privilege, then hand over to the untrusted program.

    An application with no signal handlers runs as PID 1 in a container. What does docker stop do?

    The kernel applies no default action to PID 1's signals. Only the SIGKILL from outside the namespace ends it.

    A start script ends with node server.js, and node has a careful SIGTERM handler. On docker stop the handler never runs. Why?

    With exec, node replaces the shell and is PID 1 itself, so it receives the signal directly.
