Processes: fork, exec, wait

Every process on a Linux machine, apart from the very first, was created by another process with the same three-step dance. fork() makes a copy of the caller. exec() replaces the copy's program with a new one. wait() lets the parent collect the child's exit status when it finishes. Your shell does it for every command you type, systemd does it for every service, and nginx, PostgreSQL and Redis all do it while they run. Get the dance slightly wrong and you get zombie processes, orphaned workers and the classic container bug where nothing ever gets cleaned up.

fork() returns twice

fork() creates a new process, the child, that is an almost exact copy of the caller, the parent: same code, same memory contents, same open files, same position in the program. Both continue from the instruction after fork(). The only difference is the return value: the parent gets the child's PID, the child gets 0. That one number is how each copy finds out which one it is:

#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
	int counter = 10;
	pid_t pid = fork();
	if (pid < 0) { perror("fork"); return 1; }          /* no child created: out of PIDs or memory */
	if (pid == 0) {                                     /* child */
		counter++;
		printf("child  pid=%d parent=%d counter=%d\n", getpid(), getppid(), counter);
		_exit(0);                                       /* _exit: don't flush the parent's copied stdio buffers twice */
	}
	waitpid(pid, NULL, 0);                              /* parent: wait for the child to finish */
	printf("parent pid=%d child=%d counter=%d\n", getpid(), pid, counter);
	return 0;
}
$ ./forkdemo
child  pid=4102 parent=4101 counter=11
parent pid=4101 child=4102 counter=10      # the child changed its own copy, not the parent's

The child's memory is a copy, so its counter++ is invisible to the parent. Copying a large process's memory would be slow, so Linux doesn't: parent and child share the physical pages read-only after fork(), and a page is copied only when one of them writes to it. That's copy-on-write, and Chapter 30 shows how the page tables make it work.

exec() replaces the program

A copy of the shell isn't very useful by itself. The exec family (execve is the system call; execlp, execvp and friends are library wrappers that search PATH and build the argument array) throws away the calling process's program and loads a new one from an executable file, using the ELF segments from P6. On success exec never returns, because the code that called it no longer exists. The process, though, is the same one:

After a successful exec…KeptReplaced or reset
IdentityPID, parent PID, user and group IDs (unless the file is setuid)
MemoryCode, data, heap, stack and all mappings: a fresh address space from the new ELF file
Open filesEvery file descriptor without the close-on-exec flagDescriptors opened with O_CLOEXEC are closed
SignalsIgnored signals stay ignored; the signal maskInstalled handlers reset to default (the handler code is gone)
EnvironmentWhatever you pass as envp (usually the current one)
OtherCurrent directory, resource limits, cgroup membershipThreads: all but the calling one are destroyed

The "open files are kept" row is the trick behind redirection and pipes. The shell forks, rearranges the child's file descriptors (point stdout at a file, say), then execs the command, which inherits the arrangement without knowing (Chapter 10).

wait() and exit status

When a process ends, by returning from main, calling exit(), or being killed by a signal, the kernel frees almost everything it owned but keeps a small record: its PID and how it ended. The parent collects that record with wait() or waitpid(), and decodes it with macros:

int status;
pid_t done = waitpid(pid, &status, 0);       /* blocks until that child changes state */
if (done < 0) { perror("waitpid"); return -1; }
if (WIFEXITED(status))
	printf("exited with code %d\n", WEXITSTATUS(status));     /* exit(3) -> 3 */
else if (WIFSIGNALED(status))
	printf("killed by signal %d\n", WTERMSIG(status));        /* SIGKILL -> 9, SIGSEGV -> 11 */

Shells report a process killed by signal n as exit code 128 + n. That's why a container killed by the out-of-memory killer shows exit code 137 (128 + 9, SIGKILL), and a segfault shows 139 (128 + 11), which you'll meet again in Chapter 48.

Zombies and orphans

A zombie is a process that has exited but whose parent hasn't called wait() yet. It has no memory, no open files and runs no code: it is just a process-table entry holding a PID and an exit status, shown by ps as Z or <defunct>. Every process is briefly a zombie; it's only a problem when a parent never reaps, because zombies pile up and hold PIDs, and when PIDs run out fork() fails for everyone. You can't kill a zombie (it's already dead); you fix or kill its parent.

An orphan is a running process whose parent has exited. Linux re-parents it to PID 1 (systemd, or a designated "subreaper"), which waits for it when it ends, so orphans are harmless and sometimes deliberate: classic daemons fork and let the parent exit so the child is detached from the terminal.

How a shell runs a command

Forking a large process just to exec something else wastes work, even with copy-on-write (the page tables still have to be copied). posix_spawn(), built on Linux's clone() with the CLONE_VM | CLONE_VFORK flags, creates the child without copying the address space, which is why programs with huge heaps, like JVMs, use it to launch subprocesses.

The PID 1 problem in containers

Inside a container, the first process gets PID 1 in its own PID namespace (Chapter 34), and so inherits init's job: adopting orphans and reaping them. A Node.js or Python app started as PID 1 doesn't know it has that job. If it spawns helper processes (a headless browser, shell scripts, health checks) whose own children get orphaned, those grandchildren end up re-parented to the app, which never calls wait() on them. The container slowly fills with zombies until it hits its PID limit and every fork() fails. PID 1 also gets no default signal handling, so a SIGTERM that would kill a normal process is ignored unless the app installs a handler. The standard fix is a tiny init like tini as PID 1 (docker run --init adds it), which reaps zombies and forwards signals. Chapter 46 covers it in context.

⚠️
Common mistakes
  • Not checking fork() for −1. Then pid is −1, the parent thinks it's the parent, and kill(pid, …) with −1 signals every process you're allowed to.
  • Code after exec without an error path. If exec fails, the child keeps running your program's code. Always perror and _exit(127) after it.
  • Calling exit() in a forked child. It flushes stdio buffers copied from the parent, so output appears twice. Children use _exit().
  • Never reaping children in long-running servers: zombies accumulate. Handle SIGCHLD and loop over waitpid(-1, …, WNOHANG).
  • Leaking file descriptors into children. Open files with O_CLOEXEC so exec'd programs don't inherit sockets and files they shouldn't hold.
  • Forking in a multi-threaded program. Only the calling thread is copied; locks held by other threads stay locked forever in the child. Exec soon after, or use posix_spawn.

Interview drill

Explain it simply: How many processes does fork(); fork(); fork(); create, and why?

How a strong answer sounds
Eight processes in total, seven of them new. Each fork() doubles the number of processes, because every process alive at that line executes it: one becomes two, two become four, four become eight. In general n sequential forks give 2n processes. The tree isn't balanced: the original process has three children, its first child has two, and so on, since later forks are executed by more processes.

Deeper: What's a zombie process, why does it exist, and how do you get rid of thousands of them?

How a strong answer sounds
A zombie is a process that has exited but hasn't been reaped: the kernel freed its memory and files but keeps its PID and exit status so the parent can retrieve them with wait(). That design lets a parent find out how its child ended at any time later. Thousands of zombies mean a parent that never waits. Killing the zombies does nothing; you fix the parent to reap (a SIGCHLD handler looping on waitpid(-1, &st, WNOHANG), or SIG_IGN on SIGCHLD so the kernel auto-reaps), or kill the parent, after which PID 1 adopts the zombies and reaps them. In containers, run a real init like tini as PID 1.

🧠 Key takeaways

  • fork() copies the caller and returns twice: the child's PID to the parent, 0 to the child, −1 on failure.
  • Memory after fork is copy-on-write: shared until someone writes.
  • exec() replaces the program but keeps the PID and open file descriptors (except O_CLOEXEC ones).
  • waitpid() collects the exit status; shells show death by signal n as 128 + n (137 = SIGKILL).
  • Zombies are exited but unreaped; orphans are running with a dead parent and get adopted by PID 1.
  • A shell is a loop: parse, fork, set up fds in the child, exec, wait in the parent.

Check your understanding

In the child process, what does fork() return?

0 in the child, the child's PID in the parent, −1 (in the parent, with no child created) on failure. The child can call getppid() for its parent's PID.

A process with PID 4102 calls execvp("python3", argv) successfully. What is its PID afterwards?

exec keeps the process (PID, parent, open fds) and replaces its code and memory. Creating a new process is fork's job.

How many lines does this print? for (int i = 0; i < 2; i++) fork(); printf("x\n");

Two forks give 2² = 4 processes, and each prints once.

ps shows hundreds of <defunct> children of your server. What's the fix?

Zombies are already dead, so signals do nothing. Only a wait() by the parent (or by PID 1 after the parent dies) removes them.

A container's main process exits with code 137. What most likely happened?

Shells and container runtimes report death by signal n as 128 + n. 137 is SIGKILL; 139 is SIGSEGV; 127 is "command not found".
