Virtualization & Hypervisors

An operating system believes it owns the machine: it loads its own page tables, handles its own interrupts and talks to its own disks. A virtual machine lets several operating systems hold that belief at once on the same hardware, each unaware of the others. The piece of software that maintains the illusion is the hypervisor. It has to let a guest kernel run at nearly full speed while never letting it actually take control, which sounds contradictory and for years on x86 nearly was. How that was solved, in software and then in hardware, is the foundation of every cloud: an "instance" you rent is a virtual machine, and so, underneath, are most serverless functions.

What a virtual machine is

A hypervisor, or virtual machine monitor, gives each guest a set of virtual CPUs, a block of what the guest takes to be physical memory, and some devices. The guest operating system is unmodified and boots as it would on real hardware. In 1974 Gerald Popek and Robert Goldberg set out what a real hypervisor must achieve, and the list still stands:

  • Equivalence: software behaves in the VM as it would on a real machine.
  • Resource control: the hypervisor stays in charge of the hardware. A guest can't take a resource it wasn't given or interfere with another guest.
  • Efficiency: the great majority of the guest's instructions run directly on the real CPU, with no intervention.

The third is what separates virtualization from emulation. An emulator interprets every instruction and can imitate any CPU on any other, slowly. A hypervisor runs the guest's code on the real processor and steps in only for the few operations that would break the illusion.

KVM sits between: it is a module that turns the Linux kernel itself into the hypervisor. Each VM is an ordinary Linux process and each virtual CPU an ordinary thread, scheduled like any other. Google Cloud and AWS's current instances are built on it.

Trap-and-emulate

The classic way to stay in control is to run the guest kernel without real privilege. Ordinary instructions run at full speed. Whenever the guest kernel executes a privileged instruction, such as loading a page-table base or disabling interrupts, the CPU traps, because the guest isn't really in kernel mode. The trap lands in the hypervisor, which works out what the guest was trying to do, applies it to that VM's virtual state, and resumes the guest. This is trap-and-emulate.

It only works if every instruction that touches privileged state traps when run without privilege. On x86 that wasn't true. A handful of instructions, 17 by one well-known count, behaved differently in user mode without trapping: popf, for example, silently ignored an attempt to change the interrupt flag. A guest kernel using them would simply go wrong. For years x86 was considered impractical to virtualize.

  • Binary translation (VMware, 1998): scan the guest kernel's code just before it runs and rewrite the awkward instructions into calls to the hypervisor. Clever, complex and fast enough to found an industry.
  • Paravirtualization (Xen, 2003): change the guest kernel's source so that it asks the hypervisor explicitly, with hypercalls, instead of using the awkward instructions. Fast, but the guest has to be modified.
  • Hardware support (Intel VT-x in 2005, AMD-V in 2006): fix the processor. This is what everything uses now.

VT-x: a second dimension of privilege

The hardware extensions add a mode switch that is separate from the user/kernel rings: root mode, for the hypervisor, and non-root mode, for guests. A guest in non-root mode has its own full set of rings, so the guest kernel really does run in ring 0 and its system calls, interrupts-off sections and most privileged instructions work natively with no hypervisor involved. The hypervisor fills in a control structure saying which events it wants to intercept. When one happens, the CPU performs a VM exit: it saves the guest's state, loads the hypervisor's, and jumps to it.

Memory: translating twice

A guest kernel builds page tables that map its processes' virtual addresses to what it believes are physical addresses. Those are really guest-physical addresses, and the hypervisor has placed them somewhere of its choosing in real, host-physical memory. Every guest memory access therefore needs two translations.

Nested paging removed the largest remaining source of exits, at the price of a more expensive TLB miss: each of the guest's four table reads is itself a guest-physical address that needs a four-step translation. That is why huge pages (Chapter 13) matter even more inside virtual machines, and why hypervisors back guest memory with 2 MiB pages when they can.

A model: an operation that runs directly is counted as 1 ns of overhead-free work and a VM exit as 1.5 µs. The first mode stands for pure trap-and-emulate; real software hypervisors used binary translation to avoid many of these traps. "A second of web serving" is 200,000 system calls, 20,000 process switches, 100,000 page-table updates, 50,000 guest page faults, 50,000 packets and 1,000 idle waits.

Things to notice. Ordinary instructions never exit in any mode: that is the efficiency requirement. A system call exits only in the first mode, because with VT-x the guest kernel has a real ring 0 of its own. Page-table work exits until EPT arrives. A packet through an emulated network card costs several exits; with virtio a whole batch costs one. Halting always exits, and should: an idle guest hands its core back. Over a second of web serving, the first mode spends most of the second in the hypervisor, and the last well under one per cent.

Firecracker: a virtual machine that starts in an eighth of a second

AWS Lambda runs strangers' code side by side on shared machines, so it needs the strong isolation of a virtual machine. A traditional VM takes seconds to boot and hundreds of megabytes of overhead, far too much for a function that runs for 50 ms. In 2018 AWS released Firecracker, the hypervisor it wrote for the job. It uses KVM for the CPU and memory work described in this chapter and discards almost everything else. There is no emulated BIOS, no PCI bus, no graphics, no USB: the guest gets a virtio network device, a virtio block device, a serial console and a one-button keyboard whose only purpose is to request a shutdown. With so little to set up, a microVM boots in about 125 ms and costs under 5 MiB of memory beyond what the guest itself uses, so a single server can hold thousands and create them at well over a hundred per second. The small device model is also the security argument: most escapes from virtual machines have gone through bugs in emulated devices, so the fewer there are, the less there is to attack. Lambda and Fargate both run on it. It shows that "a VM is heavy" was never about virtualization itself, which costs a few per cent, but about everything that used to be packed in with it.

⚠️
Common mistakes
  • Confusing virtualization with emulation. A VM runs guest instructions on the real CPU. Emulating a different CPU is another technique, and orders of magnitude slower.
  • Assuming a VM is slow. CPU-bound code runs at near-native speed. The costs are in exits, I/O and TLB misses.
  • Using emulated devices in production. An emulated network card or disk controller can cost half a core. Use virtio or passthrough.
  • Ignoring steal time. Unexplained slowness with low CPU use inside a VM may be the hypervisor running someone else.
  • Forgetting the double translation. Memory-heavy workloads pay more per TLB miss in a VM. Huge pages help at both levels.
  • Treating a VM boundary as absolute. It is far stronger than a process boundary, and it has still been crossed, usually through device emulation.

Interview drill

Explain it simply: How does a hypervisor run a guest operating system that thinks it controls the hardware?

How a strong answer sounds
It lets the guest's code run directly on the real CPU, but in a mode where the operations that would really take control are intercepted. With hardware virtualization, Intel VT-x or AMD-V, the CPU has a root mode for the hypervisor and a non-root mode for guests. In non-root mode the guest has its own user and kernel rings, so ordinary code, system calls and most kernel work run at native speed. When the guest does something the hypervisor has chosen to intercept, such as touching a device or halting, the CPU does a VM exit: it saves the guest's state and jumps to the hypervisor, which emulates the effect on that VM's virtual hardware and resumes it. Memory is handled by a second level of page tables, EPT, that maps the guest's idea of physical memory to real memory, so the guest can manage its own page tables freely. Devices are either emulated, paravirtual with shared queues, or passed through.

Deeper: What are shadow page tables and nested page tables, and what is the trade-off?

How a strong answer sounds
Both solve the same problem: a guest's page tables map guest-virtual to guest-physical addresses, and guest-physical still has to be mapped to host-physical. With shadow paging, the hypervisor builds, for each guest address space, a hidden table that maps guest-virtual directly to host-physical and points the real CPU at that. To keep it correct it must see every change the guest makes, so it write-protects the guest's page tables and takes a VM exit on each update and on each address-space switch. That makes page-table-heavy workloads, such as process creation, very slow. Nested paging, EPT on Intel and NPT on AMD, puts the second mapping in hardware: the MMU walks the guest's tables and translates each guest-physical address it meets through the hypervisor's tables. The guest updates its page tables with no exits at all. The cost moves to TLB misses: a four-level walk inside a four-level walk can take up to 24 memory accesses instead of 4. So nested paging wins almost everywhere, and you reduce the miss cost with huge pages in the guest and in the host.

🧠 Key takeaways

  • A hypervisor runs guest code directly on the CPU and intercepts only what would let the guest take control.
  • Type 1 hypervisors run on bare metal, type 2 on a host OS; KVM makes Linux itself the hypervisor.
  • x86 couldn't be virtualized by classic trap-and-emulate; binary translation and paravirtualization worked round it until VT-x and AMD-V fixed the CPU.
  • A VM exit costs about a microsecond. Performance comes from avoiding them.
  • Guest memory is translated twice. Nested page tables do it in hardware: no exits, but TLB misses of up to 24 reads.
  • Emulated devices exit on every access; virtio batches through shared rings; passthrough gives the guest the device.

Check your understanding

What distinguishes virtualization from emulation?

Direct execution is the efficiency requirement. An emulator interprets or translates every instruction, which is what lets it imitate a different CPU, slowly.

With VT-x, a process inside a guest makes a system call to its guest kernel. What happens?

Non-root mode has its own user and kernel rings, so guest system calls are ordinary ring transitions.

Why was x86 difficult to virtualize before hardware extensions?

Trap-and-emulate needs every sensitive instruction to trap. Instructions such as popf didn't, so a deprivileged guest kernel misbehaved.

What is the main cost of nested page tables (EPT) compared with shadow page tables?

Each step of the guest's walk yields a guest-physical address that must itself be translated. The exits disappear; the miss cost grows.

Why is a virtio network device much faster than an emulated e1000 card?

Emulating real hardware means trapping each register read and write. A paravirtual device is designed to cross the boundary rarely.
