Process States & the Process Control Block

A machine with 8 cores and 600 processes has at most 8 of them running at any instant. The rest are waiting: for a turn on a CPU, for a disk read, for a network packet, for a timer, or for their parent to collect their exit status. The kernel tracks every one of them in a record called the process control block, and moves it between a handful of states and queues as events happen. Knowing that state machine is what lets you read ps and top properly, and explain why a machine can have a load average of 200 while its CPUs sit idle.

The five-state model

Textbooks describe a process's life with five states. A process is new while the kernel is building it; ready when it could run but no CPU is free; running on a CPU; blocked (also called waiting or sleeping) when it can't continue until some event happens; and terminated once it has exited. The process control block

The process control block (PCB) is the kernel's record of one process: everything it needs to pause the process and resume it later, and to manage its resources. In Linux the PCB is struct task_struct, and there is one per thread; threads of the same process point at shared sub-structures for memory and files (Chapter 5). It is large (several kilobytes), so here is the shape, heavily simplified:

/* Simplified from include/linux/sched.h: the fields this course keeps coming back to. */
struct task_struct {
	unsigned int          __state;        /* TASK_RUNNING, TASK_INTERRUPTIBLE, ... */
	pid_t                 pid, tgid;      /* thread ID; thread-group (process) ID */
	struct task_struct   *real_parent;    /* who gets SIGCHLD and reaps us */
	struct list_head      children;

	int                   prio;           /* scheduling priority (Chapter 8) */
	struct sched_entity   se;             /* run-queue node, virtual runtime */
	int                   on_cpu;

	struct mm_struct     *mm;             /* address space: page tables, mappings (Chapter 11) */
	struct files_struct  *files;          /* the file-descriptor table (Chapter 10) */
	struct fs_struct     *fs;             /* current directory, root */
	struct signal_struct *signal;         /* pending signals, handlers (Chapter 9) */
	const struct cred    *cred;           /* user and group IDs, capabilities (Chapter 36) */
	struct nsproxy       *nsproxy;        /* namespaces (Chapter 34) */

	struct thread_struct  thread;         /* saved CPU state: rsp, registers (Chapter 6) */
	void                 *stack;          /* this thread's kernel stack */
};

Notice how many fields are pointers to separate structures. That's what makes fork and threads cheap to express: a new thread is a new task_struct sharing the same mm and files; a new process gets copies. The table of contents of this course is, more or less, a tour of those pointers.

Run queues and wait queues

States are implemented as membership in queues. Each CPU has a run queue holding its runnable tasks (in Linux's fair scheduler, a red-black tree ordered by how much CPU time each has had, Chapter 8). Every thing a task can wait for has a wait queue: each socket, each pipe, each locked page under I/O, each child-exit event. Blocking means taking the task off the run queue and putting it on a wait queue; waking means the reverse.

Reading state from /proc

Linux exposes each task's PCB, read-only, under /proc/<pid>/. The status file is the readable summary:

$ grep -E 'Name|State|Pid|PPid|Threads|VmRSS|ctxt' /proc/1734/status
Name:	nginx
State:	S (sleeping)                 # blocked in epoll_wait, waiting for connections
Pid:	1734
PPid:	1730
Threads:	1
VmRSS:	   48212 kB                  # physical memory in use (Chapter 14)
voluntary_ctxt_switches:	  913442  # times it blocked and gave up the CPU
nonvoluntary_ctxt_switches:	    2104  # times it was preempted while still runnable
$ cat /proc/1734/wchan; echo          # the kernel function it is sleeping in
do_epoll_wait

The two context-switch counters are a quick diagnostic. A process with many voluntary switches spends its life blocking on I/O; one with many non-voluntary switches is CPU-bound and being preempted, often because there are more runnable tasks than cores.

📈
Load average 200, CPUs idle: the D state

Linux's load average counts tasks that are runnable or in uninterruptible sleep (D). That second part, a Linux choice dating from 1993, means load reflects demand for disk as well as CPU. It also produces a classic incident: an NFS server stops responding, every process that touches the mounted directory blocks in D state, and load average climbs into the hundreds while top shows the CPUs almost idle. Those processes can't be killed, not even with kill -9, until the I/O completes or times out, because D-state waits deliberately ignore signals. The diagnosis is ps -eo pid,stat,wchan:30,cmd | awk '$2 ~ /D/': every stuck task, and the kernel function it's stuck in. Brendan Gregg's 2017 article "Linux Load Averages: Solving the Mystery" traces the history.

⚠️
Common mistakes
  • Reading R as "running right now". It means running or ready; with more R tasks than cores, some are waiting in line.
  • Thinking a woken task runs immediately. Waking moves it to a run queue; the scheduler decides when it gets a CPU.
  • Reading high load as high CPU. On Linux, load includes D-state tasks; check CPU utilisation and I/O wait separately.
  • Expecting kill -9 to clear D-state processes. They die only when the uninterruptible wait ends.
  • Assuming one PCB per process. Linux has one task_struct per thread; ps -L or /proc/<pid>/task/ shows them.

Interview drill

Explain it simply: What states can a process be in, and what moves it between them?

How a strong answer sounds
New while it's being created; ready when it can run but has no CPU; running on a CPU; blocked when it's waiting for an event like I/O; terminated after exit until its parent reaps it. The scheduler moves ready to running; a timer interrupt ending its time slice moves running back to ready; a blocking call moves running to blocked; the event's interrupt or a wake-up moves blocked to ready, never directly to running; and exit moves running to terminated. Linux shows these as R (ready or running), S and D (interruptible and uninterruptible sleep), T (stopped) and Z (zombie).

Deeper: What's in a PCB, and why does a context switch need it?

How a strong answer sounds
The PCB, Linux's task_struct, holds the task's identity (PID, parent), its state and scheduling data (priority, run-queue node, CPU time used), pointers to its resources (address space and page tables, file-descriptor table, signal handlers, credentials, namespaces), and the saved CPU context: the kernel stack pointer and registers. A context switch saves the outgoing task's registers into its PCB and kernel stack, switches page tables if the next task is in a different process, and restores the incoming task's saved state, so it resumes exactly where it stopped. Without the PCB there'd be nowhere to keep a paused task.

🧠 Key takeaways

  • Five states: new, ready, running, blocked, terminated; every transition is triggered by an event.
  • Linux letters: R (ready or running), S (interruptible sleep), D (uninterruptible), T (stopped), Z (zombie).
  • The PCB (task_struct, one per thread) holds identity, state, scheduling data, resource pointers and saved registers.
  • Ready tasks sit in per-CPU run queues; blocked tasks sit in per-event wait queues; waking moves them back.
  • Linux load average counts R and D tasks, so it can be high with idle CPUs.

Check your understanding

A blocked process's disk read completes. Which state does it move to?

Waking makes a task runnable, not running. Another task may hold the CPU, and the scheduler chooses.

What causes a running process to go back to ready without doing anything wrong?

Preemption: still runnable, but its turn is over. A blocking call would move it to blocked instead.

ps shows a process in state D that ignores kill -9. Why?

D-state sleeps don't wake for signals. The kill is queued and takes effect once the I/O finishes or fails.

Which of these is NOT something the PCB (task_struct) points to?

The kernel knows nothing about source code. It tracks resources and saved CPU state.

A 16-core server shows load average 180 and 3% CPU utilisation. What's the most likely explanation?

Linux load counts R and D tasks. Spinning threads would show high CPU; zombies aren't counted.
