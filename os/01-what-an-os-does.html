What an Operating System Does

A production server runs nginx, PostgreSQL, a few Python workers, a log shipper and cron jobs, all on one machine with a handful of cores, one pool of RAM and one disk. None of those programs was written with the others in mind; each assumes it has the computer to itself. The operating system is what makes that assumption safe. It does three jobs: it shares the hardware between programs, it hides the hardware's messy details behind clean abstractions, and it protects programs (and itself) from each other. Every chapter in this course is one of those three jobs, seen up close.

Job 1: share the hardware (virtualisation)

The OS gives each program the illusion of its own machine, a technique called virtualisation. A 4-core server can run 300 threads because the kernel switches cores between them every few milliseconds, faster than anyone notices. Each of 40 processes believes it owns a private 128 TiB address space, though the machine has 64 GiB of RAM, because the kernel and the MMU translate every address. And a dozen programs write to "their" files at once, while the kernel decides where on one shared disk the bytes go.

Job 2: hide the details (abstraction)

Hardware is awkward: disks deal in sectors and need commands sent through device registers, network cards fill rings of descriptors, RAM is just numbered bytes. The OS replaces those with a handful of abstractions that every program uses the same way:

  • Process: a running program, with its own state, owner and resources. Created with fork/exec (Chapter 3); contains one or more threads (Chapter 5).
  • Address space: the process's private view of memory (Chapter 11).
  • File: a named sequence of bytes. Unix stretches the idea so that pipes, sockets, terminals and devices are all used through the same read/write calls on a file descriptor (Chapter 10).

That's why the same cat program works on a file on an NVMe drive, a file on a network share and /proc/cpuinfo, which isn't stored anywhere at all: it only ever sees the file abstraction.

Job 3: protect (isolation)

Sharing is only safe if one program can't damage another. Two hardware features make that enforceable rather than polite. The CPU has a privileged mode (Chapter 2): only the kernel can talk to devices, change page tables or disable interrupts, and programs must ask it through system calls. And the MMU checks every memory access against the current process's page tables, so a stray pointer in one program faults instead of scribbling on another's memory. On top of those, the kernel checks permissions on every file, signal and network port. The panel below lets you switch these protections off and see the machine fall apart.

Every failure in that panel happened for real before modern protection was standard. Cooperative multitasking in Windows 3.1 and classic Mac OS relied on each program giving the CPU back voluntarily, so one hung program froze the whole machine. MS-DOS had no memory protection, so a bad pointer in one program could crash everything. Those systems weren't badly written; the hardware features, or the willingness to use them, came later.

Monolithic kernels and microkernels

How much code should run in privileged mode? A monolithic kernel (Linux, the BSDs) puts the scheduler, memory manager, file systems, network stack and device drivers all in kernel mode, in one address space, calling each other directly. A microkernel (seL4, QNX, MINIX 3) keeps only the minimum in kernel mode: address spaces, threads, scheduling and message passing. File systems and drivers run as ordinary user-space processes, and a read() becomes a series of messages:

Monolithic (Linux)Microkernel (seL4, QNX)Hybrid (Windows NT, macOS XNU)

Linux claws back some microkernel benefits without changing its design: loadable modules keep drivers separate at build time, FUSE runs file systems in user space, and eBPF lets verified programs run inside the kernel safely (Chapter 35).

🟦
CrowdStrike, July 2024: when kernel code fails, everything fails

On 19 July 2024 a faulty content update for CrowdStrike's Falcon security sensor caused its Windows kernel-mode driver to read memory out of bounds. In user space that would have been one crashed process. In kernel mode there is no one above the kernel to catch the fault, so Windows stopped with a blue screen, on about 8.5 million machines by Microsoft's estimate, grounding flights and closing hospitals' systems. Security products run in the kernel because they want to see everything; this incident is the cost side of that same choice, and it pushed Microsoft to start moving such tools out of the kernel. The protection boundary from this chapter is the line that decides whether a bug is an error message or an outage. The Cloud & DevOps course (course home) looks at the incident response.

What an OS interview asks

OS questions in interviews cluster around the same handful of ideas, and they map onto this course's levels: processes vs threads and what fork does (Chapters 3–5); scheduling and context switches (6–8); virtual memory, paging, page faults and the TLB (11–15); race conditions, locks, condition variables, semaphores and deadlock (17–22); and, for systems roles, I/O models, the page cache, fsync and containers (28–34). ⚠️
Common mistakes
  • Thinking "the OS" means the desktop or the shell. Those are programs. The OS, in this course, is the kernel: the code running in privileged mode.
  • Thinking the kernel is a process that "runs in the background". It mostly runs only when something enters it: a system call, an interrupt or a fault. (Linux does have kernel threads for background work.)
  • Equating virtual memory with swap. Virtualisation of memory is about private address spaces and protection; swapping to disk is one optional use of it.
  • Assuming microkernels are "better". They trade speed for isolation; the right choice depends on what a failure costs.
🎤
Interview drill

Explain it simply: What does an operating system do?

How a strong answer sounds
Three things. It shares the hardware among programs by virtualising it: time-slicing the CPU with a scheduler driven by timer interrupts, giving each process a private address space with page tables, and multiplexing storage and the network. It provides abstractions so programs don't drive hardware directly: processes and threads, address spaces, files and sockets behind system calls. And it protects programs from each other and from themselves, using the CPU's privileged mode and the MMU so only the kernel touches devices and page tables, and checking permissions on every access.

Deeper: Why is Linux monolithic when microkernels isolate failures better?

How a strong answer sounds
Performance and pragmatism. In a monolithic kernel a system call reaches the file system and driver through function calls in one address space; in a microkernel it becomes several messages and context switches, which historically cost a lot (newer microkernels like seL4 made IPC much cheaper). Linux also grew from a single developer's working system into a huge shared codebase where in-kernel drivers were the fastest way to support hardware. It mitigates the downsides with loadable modules, FUSE for user-space file systems, and eBPF for safe extensions. Microkernels win where isolation and verifiability matter more than peak throughput, like QNX in cars and seL4 in high-assurance systems.

🧠 Key takeaways

  • The OS virtualises the CPU (scheduling), memory (address spaces) and storage (file systems).
  • It offers abstractions (processes, address spaces, files) so programs never drive hardware directly.
  • Protection rests on hardware: privileged mode and the MMU; without them, one bad program takes down the rest.
  • Preemption via timer interrupts is what stops one looping program from freezing the machine.
  • Monolithic kernels are fast but a driver bug is fatal; microkernels isolate services at the cost of messaging.

Check your understanding

A one-core machine runs a program stuck in an infinite loop, yet the web server on the same machine keeps answering. What makes that possible?

Preemptive scheduling doesn't need the program's cooperation: the hardware timer interrupts it and the kernel decides who runs next.

Which hardware feature stops a bad pointer in one process from corrupting another process's memory?

Each process's page tables map only its own memory. An access outside it causes a fault, and the kernel typically kills the process with SIGSEGV.

Which of these is an OS abstraction rather than a piece of hardware?

Files are an illusion the kernel builds out of disk blocks (and sometimes nothing at all, like /proc files).

In a microkernel, where does a file system usually run?

Microkernels keep only IPC, threads and address spaces privileged; file systems and drivers are ordinary processes.

Why did the July 2024 CrowdStrike fault crash whole machines rather than one application?

In user mode the same bug would have killed one process. In kernel mode, the OS itself fails, so the system stops.
