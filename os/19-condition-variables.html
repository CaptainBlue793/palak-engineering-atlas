Condition Variables

A mutex answers "may I touch this data now?". It can't answer "tell me when the data is in the state I need". A worker thread wants a job from a queue that happens to be empty; a producer wants to add to a buffer that happens to be full. Each needs to wait for something another thread will do, without burning CPU and without missing the moment. A condition variable is the tool: a place to sleep until someone signals that the shared state has changed. The interface is three calls. The rules for using them correctly are short, and each one exists because of a specific bug that this chapter lets you cause.

Why a mutex isn't enough

A worker takes jobs from a shared queue. The queue is protected by a mutex, so adding and removing are safe. But what should the worker do when the queue is empty? With only a mutex, it can poll:

for (;;) {
    pthread_mutex_lock(&m);
    if (count > 0) { job = dequeue(); count--; pthread_mutex_unlock(&m); break; }
    pthread_mutex_unlock(&m);
    /* nothing yet: go round again */
}

This is correct and terrible. An idle worker uses 100% of a core and takes the lock millions of times a second, getting in the way of the thread trying to add a job. Adding a usleep(1000) to the loop trades the CPU for latency: every job now waits up to a millisecond for no reason. What the worker wants is to sleep until the exact moment the queue stops being empty, and that means the thread that adds a job has to wake it.

wait, signal, broadcast

A condition variable is a queue of sleeping threads. It holds no data and no state of its own. It is always used together with a mutex and with some condition on shared data (also called a predicate), such as count > 0.

CallWhat it does
pthread_cond_wait(&cv, &m)Releases m and puts the caller to sleep on cv, as one atomic step. When woken, takes m again before returning
pthread_cond_signal(&cv)Wakes one thread sleeping on cv, if there is one. If nobody is waiting, nothing happens and nothing is remembered
pthread_cond_broadcast(&cv)Wakes every thread sleeping on cv

The whole of correct usage fits in one pattern. Learn it as a unit:

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;
int count;                                      /* jobs in the queue: the shared state */

void put(job_t j)
{
    pthread_mutex_lock(&m);
    enqueue(j); count++;                        /* 1. change the state, holding the mutex */
    pthread_cond_signal(&not_empty);            /* 2. tell a waiter that it changed */
    pthread_mutex_unlock(&m);
}

job_t get(void)
{
    pthread_mutex_lock(&m);
    while (count == 0)                          /* check the condition, holding the mutex, in a loop */
        pthread_cond_wait(&not_empty, &m);      /* unlocks m, sleeps, relocks m */
    job_t j = dequeue(); count--;               /* here the condition is true and we hold the mutex */
    pthread_mutex_unlock(&m);
    return j;
}

Why wait takes the mutex: the lost wake-up

It seems odd that wait needs to know about the mutex. The reason is one particular interleaving. Suppose releasing the lock and going to sleep were two separate steps:

Worker                                   Producer
lock; count == 0, so decide to sleep
unlock
                                         lock; enqueue; count = 1
                                         signal            <- nobody is asleep yet: does nothing
                                         unlock
sleep                                    <- sleeps for ever, with a job in the queue

The signal arrived in the gap between "decided to sleep" and "asleep", and since a condition variable remembers nothing, it was lost. This is the lost wake-up, the same check-then-act shape as every race in Chapter 17. pthread_cond_wait closes the gap by doing the unlock and the sleep atomically: the caller is on the wait queue before any other thread can take the mutex, so a producer that changes the state afterwards is certain to find it there. It is also why the signaller must change the state while holding the mutex.

Always wait in a while loop

When wait returns, the condition is probably true. It isn't guaranteed, for three reasons:

  • Another thread got there first. A signalled thread doesn't run at once. It becomes runnable and then has to take the mutex like anyone else. In between, a third thread can lock the mutex, find a job and take it. When the woken thread finally runs, the queue is empty again.
  • Spurious wake-ups. POSIX allows pthread_cond_wait to return even though nobody signalled. Implementations are allowed this slack because ruling it out would make every wait slower.
  • Broadcasts. A broadcast wakes every waiter although there may be work for only one.

One rule covers all three: recheck the condition after waking, by putting the wait inside a while. Then a wake-up is only ever a hint to look again, and an unnecessary one costs a little time but can't cause a wrong result. With an if, the thread carries on with a condition that no longer holds.

Cause the bugs

Two workers each take one job; a producer adds two. You choose who runs. In the first variant, try to strand a worker asleep with jobs in the queue. In the second, make a worker take a job from an empty queue. Then check that you can't break the third, and press Try every schedule on each.

Two workers, one producer: three ways to waitInteractive
The queue is shown only as its count, which starts at 0. The producer runs its loop twice. A run is correct if both workers finish with one job each and count ends at 0. Spurious wake-ups aren't modelled; the bugs here need none. "Try every schedule" follows every choice the scheduler could make.

Things to notice. In the first variant the fatal order is: a worker tests count, the producer does all its work, and only then does the worker sleep. Both signals have gone and nobody will send another. In the second, let worker 1 wait, let the producer add one job and signal, then run worker 2 through before worker 1 gets the mutex back: worker 1 returns from wait and decrements a count of zero. The third variant is correct on every schedule, and the only change is one word: if became while.

Mesa and Hoare semantics

The need for while comes from a design decision about what signal means. There are two classic answers.

Hoare semantics (1974)Mesa semantics (1980)
On signalThe signaller stops; the lock and the CPU pass straight to the waiterThe waiter is made runnable; the signaller carries on
When the waiter resumesThe condition is guaranteed to be trueThe condition may have changed: the signal was a hint
Waiting codeif (!cond) wait(); is enoughwhile (!cond) wait(); is required
CostTwo forced context switches per signal; awkward to implementNone beyond the wake-up
Used byTextbooks and a few research systemsEssentially everything: pthreads, Java, C++, Go, Rust, the Linux kernel

Tony Hoare's version is easier to reason about on paper. The version built by Butler Lampson and David Redell for the Mesa language at Xerox is easier to implement efficiently and more forgiving: since every waiter rechecks, extra or early wake-ups are harmless. Every system you are likely to use is Mesa-style, so treat the loop as part of the syntax.

signal or broadcast?

signalbroadcast
WakesOne waiterAll waiters
Safe whenEvery waiter is waiting for the same condition, and one state change can satisfy only one of themAlways, provided waiters use while
RiskWaking a thread that can't use the change, while the one that could stays asleepA "thundering herd": all wake, all fight for the mutex, all but one go back to sleep
Typical useOne job added to a queueShutdown flags, configuration reloads, a pool's capacity changing

The classic way to get signal wrong is to use one condition variable for two conditions. In a bounded buffer, producers wait for "not full" and consumers for "not empty". If both sleep on the same condition variable, a consumer that removes an item may signal and wake another consumer, which finds nothing and sleeps again, while the producer that could have used the free slot is never woken. Everything stops. The fix is one condition variable per condition, not_full and not_empty, or, failing that, broadcast. Chapter 21 builds that buffer in full.

☕
Java's ArrayBlockingQueue: one lock, two conditions

The bounded queue behind many Java thread pools is this chapter in about thirty lines. ArrayBlockingQueue has a single ReentrantLock and two condition objects created from it, named notEmpty and notFull. Its put method locks, runs while (count == items.length) notFull.await();, stores the element and calls notEmpty.signal(). Its take method is the mirror image: while (count == 0) notEmpty.await();, remove, then notFull.signal(). Every rule is visible: the state is only read and changed under the lock, each wait is in a while, and there is one condition per predicate so that signal can never wake the wrong kind of thread. Java's documentation for the older Object.wait() says in so many words that waits "should always occur in loops". Go's sync.Cond, C++'s std::condition_variable (whose wait can take the predicate and do the loop for you) and Rust's Condvar all have the same shape, because all are Mesa-style.

⚠️
Common mistakes
  • Waiting in an if. After waking, the condition may be false again. Always while.
  • Checking the condition without the mutex. The check and the sleep must be one critical section, or a signal can fall in between and be lost.
  • Changing the state without the mutex. For the same reason: the waiter must not be able to miss the change.
  • Treating a signal as a message. It carries no information and isn't stored. The truth is in the shared state; the signal only says "look again".
  • One condition variable for two different conditions. signal may wake a thread that can't proceed. Use one per condition.
  • Forgetting to signal on every path. Each code path that could make the condition true must signal, including error paths and shutdown.

Interview drill

Explain it simply: Why must pthread_cond_wait be called in a while loop?

How a strong answer sounds
Because returning from wait doesn't guarantee the condition is true. Pthreads uses Mesa semantics: signal only makes the waiter runnable, and it then has to reacquire the mutex. Between the signal and that moment another thread can take the mutex and consume whatever the signal was about, so the woken thread finds the queue empty again. POSIX also permits spurious wake-ups, where wait returns with no signal at all, and a broadcast wakes all waiters when only some can proceed. Rechecking in a while handles all of these: a wake-up becomes a hint to re-test, and if the condition is false the thread simply waits again. With an if, it would continue on a false assumption, for example dequeuing from an empty queue.

Deeper: Why does pthread_cond_wait take a mutex, and what goes wrong without it?

How a strong answer sounds
To prevent a lost wake-up. The waiter checks a condition on shared state and, if it is false, sleeps. If checking and sleeping aren't atomic with respect to the thread that changes the state, this can happen: the waiter sees the queue empty and decides to sleep; before it is actually asleep, a producer adds an item and signals; the signal finds no sleeper and is discarded, because condition variables keep no memory; then the waiter goes to sleep and never wakes, though the queue has an item. pthread_cond_wait avoids it by requiring the caller to hold the mutex while checking, and by releasing the mutex and enqueuing the thread as a sleeper in one atomic step. The producer must hold the same mutex to change the state, so it can only run either before the check, in which case the waiter sees the item, or after the waiter is on the queue, in which case the signal wakes it.

🧠 Key takeaways

  • A condition variable lets a thread sleep until another thread says the shared state has changed.
  • wait atomically releases the mutex and sleeps, and retakes the mutex before returning.
  • The pattern: lock; while (!condition) wait; use the state; unlock. The signaller changes the state under the same lock, then signals.
  • A signal isn't stored. Checking or changing the state outside the mutex allows lost wake-ups.
  • Real systems use Mesa semantics: a wake-up is a hint, so the condition must be rechecked in a loop.
  • Use one condition variable per condition; use broadcast when a change may matter to several waiters.

Check your understanding

What does pthread_cond_wait(&cv, &m) do with the mutex?

If the sleeper kept the mutex, no other thread could change the state it is waiting for. Releasing and sleeping atomically prevents a lost wake-up.

A thread calls pthread_cond_signal on a condition variable that no thread is waiting on. What happens?

Condition variables have no memory. That is the key difference from a semaphore, and why the shared state, not the signal, must carry the information.

With Mesa semantics, which statement about a thread that has just returned from wait is true?

Between the signal and the waiter reacquiring the mutex, other threads can run and change the state. Hence the while loop.

A worker checks count == 0 without holding the mutex, then calls a function that sleeps. What bug is possible?

The signal finds nobody asleep and vanishes; the worker then sleeps for ever although the queue isn't empty.

In a bounded buffer, producers and consumers all wait on a single condition variable, and the code uses signal. What can go wrong?

The woken thread can't use the change and waits again; the one that could is never woken. Use separate condition variables, or broadcast.
