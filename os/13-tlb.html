The TLB

Chapter 12 ended with a problem: one load from memory needs four more memory reads just to find out where the memory is. The translation lookaside buffer (TLB) is the cache that makes paging affordable: a few dozen to a few thousand recent page-to-frame translations kept inside the CPU and checked on every access. When it hits, translation costs nothing. When it misses, you pay for the page walk. How big it is, what empties it, and what it costs to keep correct across cores explain why huge pages exist, why switching processes costs more than switching threads, and why a busy munmap can slow down a 64-core server.

Why translation needs a cache

Every instruction fetch, every load and every store uses a virtual address, and each one has to be translated. A four-level walk turns one memory access into five. Programs would run several times slower if the MMU really did that each time.

It doesn't have to, because programs have locality. A loop runs the same few pages of code, pushes and pops on the same stack page, and works through an array one page at a time. So the MMU keeps the translations it used most recently in a small, very fast lookup table: the TLB. Each entry holds a virtual page number, the frame number it maps to, the permission bits copied from the page-table entry, and a tag saying which address space it belongs to. The lookup compares the page number against many entries at once, in hardware, in well under a nanosecond.

Here is what the MMU does on every access, written as C. On x86, ARM and RISC-V this is a circuit, not code:

/* One memory access, as the MMU sees it. PTE_* and pte_frame() are from Chapter 12. */
uint64_t translate(uint64_t va, int access)
{
    uint64_t vpn = va >> 12;
    struct tlb_entry *e = tlb_lookup(vpn, current_asid);   /* compared against all candidates in parallel */

    if (e) {                                             /* TLB hit: no memory reads at all */
        if (!allowed(e->flags, access))
            page_fault(va);                              /* e.g. a write to a read-only page */
        return (e->pfn << 12) | (va & 0xfff);
    }

    uint64_t pte = page_walk(cr3, va);                   /* TLB miss: up to four reads */
    if (!(pte & PTE_PRESENT) || !allowed(pte, access))
        page_fault(va);                                  /* trap to the kernel; nothing is cached */

    tlb_insert(vpn, current_asid, pte);                  /* may evict an older entry */
    return pte_frame(pte) | (va & 0xfff);
}

Some older architectures, such as MIPS and early SPARC, had a software-managed TLB: a miss trapped to the kernel, which did the lookup itself and loaded the entry. That let the OS use any page-table format it liked, but every miss cost a trap. Modern x86, ARM and RISC-V CPUs walk the tables in hardware.

Hit rate and effective access time

The standard way to measure a TLB is the effective access time (EAT): the average cost of one memory access once translation is included. If h is the hit rate:

EAT = t_tlb + t_mem + (1 − h) × t_walk

Textbook numbers: t_tlb = 1 ns, t_mem = 100 ns, t_walk = 4 × 100 ns (four levels, nothing cached)

h = 0      (no TLB)    1 + 100 + 1.000 × 400 = 501 ns
h = 0.90               1 + 100 + 0.100 × 400 = 141 ns
h = 0.99               1 + 100 + 0.010 × 400 = 105 ns
h = 0.999              1 + 100 + 0.001 × 400 = 101.4 ns

Two things to take from the arithmetic. A TLB turns a 5× slowdown into a few per cent. And the last per cent of hit rate matters: going from 99% to 90% costs a third more time per access.

Those numbers are for exams and interviews. Real CPUs do better in three ways, and you should know them:

  • The lookup is free on a hit. The first-level TLB is searched at the same time as the L1 data cache, so a hit adds no delay.
  • Page-table entries are ordinary memory. They sit in the same L1, L2 and L3 caches as your data, so a walk's reads usually cost a few nanoseconds each, not 100.
  • Paging-structure caches. The MMU also remembers recent upper-level entries (PML4, PDPT and PD), so most walks skip straight to the last level: one read instead of four.

A typical walk therefore costs tens of CPU cycles. It becomes expensive when the page-table entries themselves have fallen out of the caches, which is exactly what happens to programs that touch a lot of memory at random. A study of database, key-value cache and graph workloads (Basu et al., ISCA 2013) found they spent as much as 10% of their execution cycles on TLB misses, even with large pages.

TLB reach and huge pages

TLB reach is how much memory the TLB can cover at once: the number of entries times the page size. If your program's working set fits inside the reach, almost every access hits. If it doesn't, misses are guaranteed however much RAM the machine has.

Real TLBs are split and layered like the data caches: a first level for instructions (iTLB), a first level for data (dTLB), and a larger, slower second level shared by both (often called the STLB). Entries for different page sizes are kept separately. These are the sizes for an Intel Skylake core; newer Intel and AMD cores have 2,000 to 3,000 second-level entries.

Page sizeL1 data TLBL1 reachL2 TLBL2 reach
4 KiB64 entries256 KiB1,536 entries6 MiB
2 MiB32 entries64 MiB1,536 entries (the same ones)3 GiB
1 GiB4 entries4 GiB16 entries16 GiB

Read the first row again. With 4 KiB pages, the whole second-level TLB covers 6 MiB. A PostgreSQL server with a 32 GiB buffer pool, a JVM with a 16 GiB heap or a Redis instance holding 50 GiB of keys can keep only a tiny fraction of its memory translated at any moment. That is the real case for huge pages, and the reason Chapter 12 called the TLB their most important benefit: the same 1,536 entries cover 3 GiB when each one maps 2 MiB.

Access pattern matters as much as size. Each row of this grid is exactly one page, so reading along a row stays on one page for 4,096 accesses, and reading down a column lands on a new page every time:

#define ROWS 4096
#define COLS 4096                     /* one row = 4096 bytes = one 4 KiB page */
static char grid[ROWS][COLS];        /* 16 MiB, filled by main() before timing */

long by_row(void) {                   /* 4,096 pages touched, one after another */
    long sum = 0;
    for (int r = 0; r < ROWS; r++)
        for (int c = 0; c < COLS; c++)
            sum += grid[r][c];
    return sum;
}

long by_col(void) {                   /* same bytes, but a different page on every access */
    long sum = 0;
    for (int c = 0; c < COLS; c++)
        for (int r = 0; r < ROWS; r++)
            sum += grid[r][c];
    return sum;
}
$ gcc -O1 grid.c -o grid               # -O1: higher levels may swap the loops for you
$ perf stat -e dTLB-loads,dTLB-load-misses ./grid row
        16,912,347      dTLB-loads
             5,216      dTLB-load-misses          #  0.03% of all dTLB cache accesses
$ perf stat -e dTLB-loads,dTLB-load-misses ./grid col
        16,931,102      dTLB-loads
        16,204,881      dTLB-load-misses          # 95.71% of all dTLB cache accesses

The counts above are illustrative, for a core like the one in the table with 4 KiB pages; yours will differ. The shape won't: by_col cycles through 4,096 pages, more than the 1,536 second-level entries, so nearly every access needs a page walk. It also runs many times slower, though most of that is data-cache misses, with the page walks adding to it. Now back the array with 2 MiB pages (set transparent huge pages to always, or ask with madvise(MADV_HUGEPAGE)): the 16 MiB grid needs eight TLB entries and the misses nearly vanish.

A model, not a real CPU: eight fully associative entries with least-recently-used replacement, and frame numbers that are invented. The array scan reads every 1,024 bytes; the column walk reads down a grid of 12 rows of 4,096 bytes; random lookups probe a 64 MiB hash table; the hot loop touches four pages. Both processes run the same program, so they use the same virtual addresses with different frames.

Things to notice. The column walk gets a 0% hit rate with 4 KiB pages, because 12 pages rotate through 8 slots and each one is evicted just before it is needed again. With 2 MiB pages all 12 rows share one entry. Random lookups over 64 MiB improve with 2 MiB pages but only to about one hit in four, because the reach is 16 MiB: huge pages raise the reach, they don't remove the limit.

Context switches: flushes, ASIDs and PCIDs

A TLB entry says "page 0x7f3a00003 is in frame 0x1a2f4". That is true in one address space only. Another process has its own page 0x7f3a00003 in a different frame. So when the kernel loads another process's page tables into CR3, the old entries must not be used. There are three ways to make sure of that.

  • Flush. This was x86's only behaviour for decades: writing CR3 discards every entry except those marked global (a page-table entry bit for kernel mappings that are identical in every address space). It is simple and safe, but the incoming process starts with an empty TLB and misses on everything it touches, and so does the outgoing one when it returns. This is a large part of the "indirect cost" of a process switch in Chapter 6.
  • Tag. Each entry also stores an address-space number, and a lookup must match both the page number and the current number. ARM calls it an ASID (8 or 16 bits); x86 calls it a PCID, process-context identifier (12 bits, stored in the low bits of CR3). With tags, nothing is flushed on a switch. The old process's entries stay, can't match the new process's lookups, and are still valid when the old process runs again, unless they were evicted in the meantime.
  • Don't switch at all. Threads of one process share their page tables (Chapter 5). Switching between them leaves CR3 alone and the TLB untouched. Kernel threads have no user address space, so Linux lets them borrow the previous task's page tables instead of switching ("lazy TLB").
$ grep -o -w -E 'pcid|invpcid|pge' /proc/cpuinfo | sort -u    # what this CPU supports
invpcid          # an instruction to invalidate entries of one PCID
pcid             # tagged TLB entries
pge              # global pages

PCIDs arrived in Intel CPUs in 2010, but Linux only began using them for user processes in version 4.14 (2017). It keeps things cheap: each core remembers just six recently used address spaces and recycles their PCIDs, because the kernel has to track which cores may still hold entries for which address space.

Meltdown, KPTI, and the week PCIDs started to matter

Until 2018 the kernel was mapped into every process's page tables, protected only by the User bit (Chapter 2). That made system calls cheap: entering the kernel changed the privilege level, not the page tables, and the kernel's global TLB entries stayed warm. The Meltdown attack, made public in January 2018, showed that speculative execution on many Intel CPUs let user code read that kernel memory anyway. The fix, kernel page-table isolation (KPTI, merged in Linux 4.15), gives each process two sets of page tables: a full one used in kernel mode, and one for user mode with almost none of the kernel mapped. Now every system call and interrupt switches page tables twice. Without PCIDs that means two TLB flushes per system call. With PCIDs, the kernel gives the two views separate tags and nothing is flushed. Brendan Gregg at Netflix measured the result: between 0.1% and 6% overhead on their cloud workloads, depending mostly on the system-call rate, and noticeably more on kernels or CPUs without PCID support. A hardware feature that had sat almost unused for seven years became essential in a week. Chapter 36 returns to the attack itself.

TLB shootdowns

Every core has its own TLB, and the hardware does not keep them in step with the page tables. If a process has threads running on eight cores, a translation for one of its pages may be cached in eight places. When the kernel changes or removes that mapping, clearing the page-table entry isn't enough: the other cores would go on using their cached copies.

So the kernel does a TLB shootdown. It updates the page tables, invalidates the entries on its own core, then sends an inter-processor interrupt (IPI) to every other core that might be running that address space and waits for each to invalidate its entries too. Only then is it safe to reuse the frames.

One shootdown costs a few microseconds and interrupts whatever each target core was doing. That is nothing once, and a real bottleneck at thousands per second on a machine with dozens of cores, because each call disturbs every core the process is using. The usual causes are frequent munmap, mprotect or madvise(MADV_DONTNEED) calls in a multithreaded program: a memory allocator returning memory to the kernel too eagerly (Chapter 16), a garbage collector changing page protections, or the kernel itself migrating and reclaiming pages. Linux softens it by batching the pages of one operation into a single IPI, and by flushing the whole TLB instead when more than 33 pages are involved. arm64 CPUs can broadcast an invalidation to all cores in hardware, with no interrupt, and AMD's Zen 3 and later add a similar instruction.

$ grep TLB /proc/interrupts                       # shootdown interrupts per core since boot
 TLB:     184211     179902     201338     176455   TLB shootdowns
$ perf stat -e tlb:tlb_flush -a sleep 5           # TLB flushes on the whole machine for 5 s
$ perf stat -e dTLB-load-misses,iTLB-load-misses -p 4120 sleep 5    # misses in one process

If perf shows a service spending its time in flush_tlb_mm_range and smp_call_function_many_cond, it is paying for shootdowns. The fixes are on the program's side: reuse memory instead of unmapping it, make the allocator hold on to freed memory for longer, or change protections less often. Chapter 38 shows what this does to tail latency.

⚠️
Common mistakes
  • Thinking the TLB caches data. It caches translations: page number to frame number plus permissions. The data caches (L1, L2, L3) are separate.
  • Calling a TLB miss a page fault. A miss is resolved by the hardware walk in nanoseconds and the kernel never hears of it. A fault traps to the kernel.
  • Saying every context switch flushes the TLB. Thread switches within a process never do, and with PCIDs or ASIDs process switches don't either.
  • Expecting more RAM to fix TLB misses. Reach is entries times page size. Only bigger pages or a smaller, more local working set help.
  • Forgetting the TLB is per core. Changing a mapping in a multithreaded process costs an interrupt on every core running it.
  • Quoting the textbook 100 ns walk as a real number. Use it for the formula; say that cached page-table entries make real walks much cheaper.

Interview drill

Explain it simply: What is the TLB, and what happens on a miss?

How a strong answer sounds
The TLB is a small cache inside the CPU that maps virtual page numbers to physical frame numbers, together with the permission bits. It exists because translating an address through four levels of page tables would add four memory reads to every access. On a hit the frame comes straight from the TLB. On a miss the MMU walks the page tables itself, starting at CR3, and if it finds a valid entry it caches the translation and the access continues; the program only notices the delay. If the walk finds the page isn't present or the access isn't allowed, that is a page fault and the kernel takes over. A TLB has tens of first-level entries and a couple of thousand second-level ones, so with 4 KiB pages it covers only a few megabytes; huge pages are the main way to cover more.

Deeper: A 64-core service got slower after a change that frees memory more aggressively. The profile shows time in flush_tlb_mm_range. What is happening?

How a strong answer sounds
TLB shootdowns. Each core has its own TLB, so when one thread unmaps memory the kernel has to make every other core running that process drop its cached translations before the frames can be reused. It does that with inter-processor interrupts and waits for them to be acknowledged. One is a few microseconds; thousands per second across 64 cores interrupt every thread constantly, and the cost grows with core count. I'd confirm it with the TLB line in /proc/interrupts and the rate of munmap or madvise calls from strace -c or perf. The fix is to free less often: make the allocator retain and reuse memory, batch the frees, or pool the buffers so the mappings never change.

🧠 Key takeaways

  • The TLB caches page-to-frame translations and permissions; a hit avoids the page walk entirely.
  • EAT = TLB time + memory time + miss rate × walk time. A miss is not a page fault.
  • Reach = entries × page size: about 6 MiB with 4 KiB pages, about 3 GiB with 2 MiB pages on a typical core.
  • Entries belong to one address space. A process switch flushes them unless they are tagged with a PCID or ASID; a thread switch never does.
  • TLBs are per core, so changing a mapping in a multithreaded process needs a shootdown: an interrupt to every core running it.
  • KPTI switches page tables on every system call; PCIDs are what keep that affordable.

Check your understanding

A memory access takes 100 ns, a page walk adds 400 ns, and the TLB lookup time is negligible. With a 98% hit rate, what is the effective access time?

100 + (1 − 0.98) × 400 = 100 + 8 = 108 ns. Only the 2% of accesses that miss pay for the walk.

A TLB has 1,536 entries. What is its reach with 4 KiB pages, and with 2 MiB pages?

Reach = entries × page size. 1,536 × 4 KiB = 6 MiB; 1,536 × 2 MiB = 3,072 MiB = 3 GiB. RAM size doesn't come into it.

Which of these needs no TLB flush at all, even on a CPU without PCIDs?

Threads share one set of page tables, so every cached translation is still correct. The other three change which translations are valid.

What does a PCID (or an ASID on ARM) do?

A lookup matches the page number and the current tag, so stale entries can't be used and nothing needs flushing on a switch.

Why does unmapping memory in a process with threads on several cores require inter-processor interrupts?

Page tables are shared, but cached translations are per core. The kernel must tell each core to invalidate them before the frames are reused.
