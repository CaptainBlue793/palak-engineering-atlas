OS Interview Playbook

You now know more about operating systems than most interviews will ask for. That is a different thing from answering well. Operating-systems questions are rarely about recalling a definition. They are a way for an interviewer to find out whether you understand the machine your code runs on: whether you can explain a mechanism in order, say what it costs, and connect it to something real. This chapter maps the questions that actually come up to the chapters behind them, gives a structure that works for any of them, rehearses the two most common ones, and then drills the traps: statements that sound right, and that strong candidates learn to stop and correct.

  • Recognise the common question families and what each is really testing
  • Structure an answer: definition, problem, mechanism, cost, example
  • Give a strong answer on processes and threads, and on virtual memory
  • Read concurrent code for the standard bugs
  • Spot and correct the classic false statements

A structure that fits any answer

Weak answers are usually a correct definition followed by silence, or a pile of true facts in no order. Strong answers have a shape, and the same shape works for nearly every question in the table.

Process versus thread, done well

This is the most common opening question, so the difference between an adequate answer and a strong one is worth seeing side by side.

An adequate answerA strong answer adds
"A process is a running program with its own memory. A thread is a lightweight process that shares memory."Exactly what is shared: threads of a process share the address space (code, heap, globals), open files and signal handlers. Each thread has its own stack, registers and program counter
"Threads are faster."Why, and how much: creating a thread skips copying page tables; switching between threads of one process keeps the same page tables, so no TLB flush. Microseconds either way, with the indirect cache cost often larger
"Processes are safer."The trade-off: a wild pointer in one thread corrupts all of them and a crash kills the process. Separate processes are isolated by the MMU, and pay for it with explicit IPC
(nothing)Real systems: Chrome and PostgreSQL choose processes for isolation; nginx and Redis choose few threads and event loops; and on Linux both are tasks created by clone, differing only in which resources they share

Expected follow-ups, each with a one-line answer you should have ready. What does a context switch save? Registers, program counter, stack pointer, and if the address space changes, the page-table base. What is a zombie? A process that has exited but whose parent hasn't collected its status with wait; only its table entry remains. When would you use processes? When a fault or a compromise in one must not reach the others.

Virtual memory in two minutes

The second most common question, and the easiest to answer badly, because there is so much one could say. Use the structure and keep to six beats:

  1. Definition. Every process gets its own address space. The addresses it uses are virtual, and the hardware translates each one to a physical address.
  2. Problem. Isolation, so one process can't read or corrupt another; simplicity, so every program can be laid out as if it had the machine to itself; and flexibility, so memory can be allocated lazily, shared or moved to disk.
  3. Mechanism. Memory is divided into 4 KiB pages. A per-process page table maps virtual pages to physical frames, with permission bits. The MMU walks it on every access, and caches results in the TLB.
  4. When a translation fails. A page fault traps to the kernel, which either supplies the page, from a zeroed frame, a file or swap, or kills the process with SIGSEGV.
  5. Cost. TLB misses and page walks; page-table memory; a major fault costs a disk read.
  6. Example. "It is why malloc of a gigabyte returns instantly, and why fork of a large process is fast: copy-on-write."

Then stop. Likely follow-ups: the TLB and what flushes it, multi-level page tables and why, minor versus major faults, thrashing, huge pages. Each is a chapter you can summarise in three sentences.

Synchronisation questions, and reading code

Concurrency questions often arrive as code to review or write. Before saying anything about a piece of threaded code, run this checklist over it:

  • Is every read and write of shared state inside the lock, including the "obvious" ones?
  • Is every condition-variable wait inside a while, and does every state change that could satisfy a waiter signal?
  • Are a check and the action that depends on it in the same critical section?
  • If two locks are ever held together, are they always taken in the same order?
  • Does anything block, or call unknown code, while holding a lock?
  • Is the lock released on every path, including errors?
/* Interview exercise: find the bugs. There are three. */
void *consumer(void *arg)
{
    pthread_mutex_lock(&m);
    if (count == 0)
        pthread_cond_wait(&not_empty, &m);
    item_t x = dequeue(); count--;
    process(x);                            /* may take 200 ms */
    pthread_mutex_unlock(&m);
    return NULL;
}

void producer(item_t x)
{
    enqueue(x); count++;
    pthread_cond_signal(&not_empty);
}
The three bugs
1. The wait is in an if. After waking, another consumer may have taken the item, or the wake-up may be spurious; it must be a while (Chapter 19). 2. The producer changes count and the queue without the mutex: a data race, and a lost wake-up if it runs between a consumer's check and its wait. 3. The consumer calls process while holding the mutex, so for 200 ms nobody can add or remove anything; unlock first. Saying "and I'd make it a bounded queue with a not_full condition" earns the extra mark (Chapter 21).

Catch the trap

Interviewers like statements that are nearly true, and so do tired engineers. Decide whether each is true, false, or true only sometimes, before you look at the answer. The wording of the correction is the part to practise saying.

"What happens when…"

The open-ended question is where the whole course is tested at once. There is no single right answer. What is being judged is whether you can tell the story in order, at a sensible level of detail, and go deeper wherever you are asked.

▶️
"What happens when you run ./server?"

A strong answer, in about two minutes. The shell reads the line and calls fork, which creates a child sharing the parent's memory copy-on-write. The child calls execve. The kernel checks permissions and the file's format, discards the child's old address space and sets up a new one: it maps the executable's code and data from the file, sets up a stack with the arguments and environment, and, for a dynamically linked program, maps the dynamic loader, which in turn maps the shared libraries. Nothing has been read from disk yet beyond headers. The kernel returns to user mode at the entry point. The first instruction faults, since its page isn't in memory; the kernel reads it into the page cache and maps it, and so on, page by page, as the program touches code and data. The C runtime initialises and calls main. The server asks for memory with malloc, which grows the heap with brk or mmap; opens a socket, getting a file descriptor; and blocks in accept or epoll_wait, at which point the scheduler runs something else. Meanwhile the shell is waiting in wait for its child. From there you can go wherever the interviewer points: how the scheduler picks the next task, what a context switch saves, how the page fault is handled, how a packet wakes the server. Chapters 41 to 48 are eight such stories told in full.

⚠️
Common mistakes
  • Reciting a definition and stopping. Add why it exists and what it costs. That is where understanding shows.
  • Agreeing with a false premise. "Since a thread switch flushes the TLB…" Stop and correct it politely. That is often the test.
  • Speaking in absolutes. "Threads are faster", "spinlocks are bad". Say when, and compared with what.
  • Hiding what you don't know. "I'm not sure how Linux does it today; the classic approach is…" is a good answer. A confident invention is not.
  • Jumping to code. For a design or concurrency problem, state the shared data and the invariant first, then the locking.
  • Never naming a real system. One concrete example, a command or a number, is worth five sentences of theory.

Interview drill

Explain it simply: What is the difference between a process and a thread?

How a strong answer sounds
A process is an instance of a running program with its own virtual address space and resources such as open files. A thread is a flow of execution inside a process. Threads of the same process share its address space, so code, heap and globals, along with its open files, while each thread has its own stack, registers and program counter. Processes exist to isolate programs from one another: the MMU stops one from touching another's memory, and a crash is contained. Threads exist to do several things at once within one program, cheaply: creating one doesn't copy page tables, and switching between threads of the same process keeps the address space, so it avoids a TLB flush. The price is that threads have no protection from each other; shared data needs synchronisation, and a bug in one can corrupt all. So I'd use processes where I want fault or security isolation, as browsers and PostgreSQL do, and threads where tasks cooperate closely on shared data. On Linux both are created by clone; the difference is simply which resources are shared.

Deeper: You are asked a question you only half know: "How does the Linux scheduler decide what runs next?" How do you answer?

How a strong answer sounds
I'd say what I'm sure of, mark the boundary, and reason from principles for the rest. "For ordinary tasks Linux aims for fairness. Each runnable task accumulates virtual runtime, which is its actual CPU time scaled by its weight, set by the nice value. The scheduler keeps runnable tasks ordered by that, in a red-black tree, and picks the one that has had least, so everyone converges on a fair share and interactive tasks that sleep a lot are favoured when they wake. That is the CFS design. I know newer kernels replaced it with EEVDF, which adds a notion of deadlines to improve latency, and I couldn't give you its details. Above that there are real-time classes, FIFO and round robin with fixed priorities, and a deadline class, which always preempt normal tasks. And per-CPU run queues with periodic load balancing between cores." That shows the model, a real implementation, honest limits, and the surrounding context. What I wouldn't do is guess at specifics and present them as fact, since the follow-up question will find the guess.

🧠 Key takeaways

  • Most OS questions fall into seven families; know what each is really probing.
  • Shape every answer: definition, the problem it solves, mechanism in order, cost, a real example. Then stop.
  • Process versus thread is about what is shared, what a switch costs, and isolation against convenience.
  • Virtual memory in six beats: private address space, why, pages and page tables with a TLB, page faults, cost, example.
  • Read concurrent code with a checklist: locked state, while loops, signals, check-and-act together, lock order, nothing slow under a lock.
  • Correct false premises, avoid absolutes, and say plainly where your knowledge ends.

Check your understanding

Which answer to "what is virtual memory?" is strongest?

It defines the idea, gives the reason, names the mechanism and the cost. The first option describes swap, which is one use of virtual memory.

Which of these do threads of the same process not share?

Each thread has its own stack, registers and program counter. Everything in the address space, and the open files, is shared.

An interviewer says: "Since switching between two threads of the same process flushes the TLB, how would you reduce that cost?" What is the best response?

The premise is false. Correcting it politely and then answering the real question is what the interviewer is looking for.

You are reviewing code in which a thread calls pthread_cond_wait inside an if. What is the problem?

Another thread may have consumed the item, or the wake-up may be spurious. A while loop re-tests the condition every time.

You don't know the answer to a detailed question about a kernel internals. What is the best approach?

Interviewers value sound reasoning and honesty about limits. A confident guess usually collapses at the first follow-up.
