Case Study: How PostgreSQL Relies on the OS

PostgreSQL leans on the operating system harder than almost any other database, which makes it a good one to take apart. It forks a process for every client connection. Its cache is one region of shared memory mapped by all of those processes. It reads and writes its files through the kernel's page cache instead of going round it, and its promise that a committed transaction survives a power cut comes down to one system call returning an honest answer. In 2018 its developers discovered that the call had not meant what they had assumed for twenty years. This case study follows one UPDATE from the client to the disk and looks at every place the kernel is involved on the way.

  • Explain shared buffers, and why a page is often in memory twice
  • Follow a commit through the write-ahead log to the disk, and say when it becomes durable
  • Explain what went wrong with fsync errors in 2018 and how it was fixed
  • Explain why huge pages and overcommit settings matter to a database server

Look at the RSS column before moving on. Three processes appear to be using 3 to 4 GB each on a machine that may only have 8. They aren't. This server has a 4 GB cache in shared memory, and RSS counts every shared page a process has touched. Adding up the RSS of PostgreSQL's processes counts the same memory over and over, a point that comes back in Chapter 48.

A process per connection

The postmaster's main loop is the oldest server design there is, the one from Chapter 3:

/* The shape of the postmaster's loop, much simplified */
for (;;) {
    int client = accept(listen_fd, NULL, NULL);
    pid_t pid = fork();
    if (pid == 0) {                 /* child: the backend for this client */
        close(listen_fd);
        backend_main(client);       /* log the client in, then run its queries until it leaves */
        _exit(0);
    }
    close(client);                  /* parent: straight back to accept */
}

This is the opposite choice to nginx in Chapter 42, and it suits a database for the same reason it didn't suit a web server. A query is allowed to block: on the disk, on a lock held by another transaction, on a sort that takes a minute. With a process each, a backend's code can simply wait, and the kernel's scheduler shares the cores out. Separate address spaces also contain damage. A backend that follows a bad pointer can't scribble on another backend's private memory.

It can still scribble on the shared memory, though, and that decides what happens when a backend dies:

LOG:  server process (PID 4313) was terminated by signal 9: Killed
LOG:  terminating any other active server processes
LOG:  all server processes terminated; reinitializing
LOG:  database system was interrupted; last known up at 2026-03-02 09:14:07 UTC
LOG:  redo starts at 2/3A000028
LOG:  database system is ready to accept connections

One backend was killed, and the postmaster responded by stopping every backend, throwing the shared memory away and recovering from the log. It has no way to know whether the dead process was halfway through changing a shared structure, so it trusts none of it. Every client is disconnected because of one process's death. Keep that in mind for the section on the OOM killer.

What a process per connection costs
Opening a connectionA fork, a login, and filling the new backend's private caches of table definitions: a few milliseconds, which can be longer than the query that follows
Memory per connectionA few megabytes of private memory at first, growing to tens or hundreds as the backend caches metadata and plans
Thousands of connectionsThousands of processes for the scheduler, and contention on the shared structures. Throughput falls well before the limit
The usual answermax_connections stays low (the default is 100), and a connection pooler such as PgBouncer holds the thousands of client connections and shares a few dozen real backends among them

A pooler in front of PostgreSQL is the same arrangement as nginx in front of an application server: an event loop holds the many idle connections, and a small set of processes that are allowed to block does the work.

Shared buffers and the page cache

Tables and indexes are files made of 8 kB pages. Before forking anything, the postmaster asks the kernel for one large region of shared memory with mmap(MAP_SHARED | MAP_ANONYMOUS). Children inherit the mapping, so every backend sees the same memory at the same address. Most of it is the shared buffers: PostgreSQL's own cache of pages, with its own locks and its own eviction policy (a clock sweep, as in Chapter 15).

When a backend needs a page that isn't in shared buffers, it calls pread on the file. That is ordinary buffered I/O, so the kernel reads the page from disk into the page cache, and then copies it into the shared buffer. The page is now in RAM twice. This is double buffering, and it's the direct result of running a cache on top of a cache.

Shared buffersKernel page cache
Owned byPostgreSQLThe kernel
SizeFixed at start-up by shared_buffers (default 128 MB)Whatever RAM is free; shrinks under pressure
A hit costsA lookup in a hash table, no system callA system call and an 8 kB copy
Knows aboutTransactions, which pages are dirty and which log records cover themFiles and offsets only
Survives a PostgreSQL restartNoYes: a restarted server finds its files still warm

This is why the usual advice is to give shared buffers about a quarter of the machine's RAM and leave the rest to the kernel, and not the 70 to 80% that a database doing direct I/O would take. MySQL's InnoDB is normally run with O_DIRECT, bypassing the page cache, so its buffer pool is the only cache and should be as big as possible. PostgreSQL has always relied on the kernel for read-ahead and for writing dirty pages back, and that reliance is what the rest of this chapter is about. (PostgreSQL 18, in 2025, added asynchronous reads, with io_uring from Chapter 29 as one method, but its I/O is still buffered by default.)

# postgresql.conf on a machine with 64 GB of RAM
shared_buffers        = 16GB     # PostgreSQL's cache: about a quarter
effective_cache_size  = 48GB     # a hint to the planner: shared buffers + the page cache it can expect
max_connections       = 200      # and a pooler in front

WAL and fsync: what COMMIT waits for

Writing a changed 8 kB page to its place in a data file on every commit would be slow, and a crash halfway through several pages would leave the tables inconsistent. So PostgreSQL uses a write-ahead log (Chapter 24). Every change is first described in a compact record appended to the WAL. The rule is that the log record must be on disk before the changed page may be, and a transaction is committed at the moment its commit record is on disk. The data files catch up minutes later.

$ strace -p 4313 -e trace=recvfrom,pwrite64,fdatasync,sendto      # the same commit, as the kernel sees it
recvfrom(9, "Q\0\0\0\vCOMMIT\0", 8192, 0, NULL, NULL) = 12
pwrite64(5, "\x13\xd1\x05\0\x01\0\0\0\0\x40\x3a\0"..., 8192, 2318336) = 8192
fdatasync(5)                            = 0
sendto(9, "C\0\0\0\vCOMMIT\0Z\0\0\0\5I", 18, 0, NULL, 0) = 18

Three details make this fast enough to live with. Appending to a log is sequential I/O, the cheapest kind. Many backends committing at the same moment share one fdatasync (group commit, from Chapter 31). And the expensive random writes to the data files are deferred to the checkpoint, which runs every five minutes by default, writes every dirty page with ordinary write calls, and then calls fsync on each data file. Once a checkpoint finishes, the log before it is no longer needed and its files are recycled.

One transaction changes a balance from 100 to 70 on page 7 of a table. The page was read earlier, so at the start it is already in shared buffers and in the page cache. "Disk error, fsync retried" is how PostgreSQL 11 and earlier behaved; "PANIC" is the behaviour since 2019.

Things to notice. With the default settings there are two system calls between the client and safety: after the write, the change survives PostgreSQL crashing, and after the fdatasync it survives a power cut. From that moment nothing you can do loses it, although the table's file on disk still says 100 until the checkpoint. With synchronous_commit = off the client is told first, and for a short time a crash loses a transaction the client believes is committed. The database is still consistent, just a fraction of a second behind, and for some workloads that is a fair trade. The third scenario is the alarming one: a committed change disappears with no crash at all. The next section explains it. Last, count the copies of page 7 in RAM. There are two almost the whole time.

The 2018 fsync bug

⚖️
"fsyncgate": twenty years of a wrong assumption

In March 2018 Craig Ringer, a PostgreSQL developer, reported a case of corruption on a server whose storage had briefly returned errors. Tracing it led to an assumption built into the checkpointer since the 1990s: if fsync fails, call it again later, and when it succeeds the data is safe. On Linux that isn't true. When the kernel fails to write a dirty page, it reports the error from fsync once, and then marks the page clean, because a kernel that kept every unwritable page dirty would run out of memory when a disk was unplugged. So the retry had nothing left to write. It returned 0. PostgreSQL concluded the checkpoint was complete and recycled the WAL that could have repaired the page. The database now had a committed change that existed only in memory, marked clean, to be silently dropped whenever the kernel wanted the space. It was worse on older kernels, where the error could be delivered to a different process that happened to have the file open, or to nobody. The kernel developers pointed out that POSIX allows this behaviour, and it does. The fix, in PostgreSQL 12 and in updates to every supported version in February 2019, was to stop trusting a retry: any fsync failure on a data file is now a PANIC. The server crashes itself on purpose and replays the WAL, which rewrites the affected pages from a source that is known to be on disk. Linux, for its part, improved its error tracking from 4.13 so that every process with the file open sees the error once. Other storage engines, MongoDB's WiredTiger among them, made the same change after reading the thread.

# PostgreSQL 11.1 and earlier: logged, retried, and believed
ERROR:  could not fsync file "base/16384/16397": Input/output error
LOG:    checkpoint complete: wrote 3170 buffers (2.4%) ...

# Since 11.2 / 12: the server stops and recovers from the WAL
PANIC:  could not fsync file "base/16384/16397": Input/output error
LOG:    checkpointer process (PID 2140) was terminated by signal 6: Aborted
LOG:    all server processes terminated; reinitializing
LOG:    redo starts at 2/3A000028

The general lesson goes beyond databases: after a failed fsync you don't know what is on disk, and calling it again tells you nothing. The only safe responses are to rebuild the data from another durable copy or to stop. A 2020 study of this exact question (Rebello and others, "Can Applications Recover from fsync Failures?") found that file systems disagree about what a failed write leaves in memory, and that most of the applications tested got it wrong on at least one of them.

Huge pages and the OOM killer

Two pieces of kernel tuning follow from the design, and both matter on a large server.

Huge pages. Shared memory is mapped by every backend, and each process has its own page tables for it (Chapter 12). With 4 KiB pages the arithmetic is unkind:

32 GB of shared buffers4 KiB pages2 MiB huge pages
Mappings needed8,388,60816,384
Page-table memory per backend (8 bytes per entry)64 MiB128 KiB
For 300 backends that have each touched the whole cacheAbout 19 GiB of page tablesAbout 38 MiB
Memory one TLB entry covers4 KiB2 MiB

Nineteen gigabytes of RAM spent describing where 32 gigabytes are is a real failure seen on busy servers: memory "disappears", and the PageTables line of /proc/meminfo is where it went. Huge pages remove it, and cut TLB misses as well (Chapter 13). They have to be reserved from the kernel in advance:

$ grep PageTables /proc/meminfo
PageTables:     18734080 kB                          # the symptom

$ sysctl -w vm.nr_hugepages=16800                    # 16,384 for the buffers, plus a margin
$ grep -E '^huge_pages' postgresql.conf
huge_pages = on                                      # 'try' (the default) silently falls back to 4 KiB pages

The OOM killer. You saw what one SIGKILL does: every connection is dropped and the server goes through recovery. The kernel's out-of-memory killer (Chapter 48) sends exactly that signal, and it picks victims partly by RSS, which for PostgreSQL's processes is inflated by the shared buffers. PostgreSQL's documentation recommends two defences:

# 1. Don't promise memory that doesn't exist: allocations fail cleanly with ENOMEM instead
vm.overcommit_memory = 2

# 2. In the service unit: never kill the postmaster, but leave the backends killable
[Service]
OOMScoreAdjust=-1000
Environment=PG_OOM_ADJUST_FILE=/proc/self/oom_score_adj
Environment=PG_OOM_ADJUST_VALUE=0

With strict overcommit (Chapter 14), a query that asks for too much gets an error from malloc, and PostgreSQL turns that into an ordinary "out of memory" failure of one query. The second setting protects the one process that can't be replaced. If the postmaster itself were killed, nothing would be left to restart the others. Each backend resets its own score to 0 after the fork, so that if something must die, it is a backend.

⚠️
Common mistakes
  • Adding up RSS to find PostgreSQL's memory use. Every backend's RSS includes the shared buffers it has touched. Use Pss from /proc/PID/smaps_rollup, or count shared memory once.
  • Giving shared buffers most of the RAM. With buffered I/O that starves the page cache and leaves no room for the backends' own memory.
  • Raising max_connections into the thousands. Each connection is a process. Put a pooler in front instead.
  • Turning fsync = off for speed. A crash can then corrupt the database beyond repair. synchronous_commit = off gets most of the speed and only risks the last moments of commits.
  • Retrying a failed fsync. In your own code too. Success on the second call doesn't mean the first write happened.
  • Leaving huge_pages = try on a big server and never checking. If the kernel has no huge pages reserved, PostgreSQL starts anyway, on 4 KiB pages.

Interview drill

Explain it simply: What happens inside PostgreSQL and the kernel when a client sends COMMIT?

How a strong answer sounds
By the time of the commit, the transaction's changes have already been made to pages in shared buffers, which is PostgreSQL's cache in shared memory, and a record of each change has been appended to the WAL buffers. On COMMIT the backend adds a commit record, writes the WAL buffers to the log file with write, which puts them in the kernel's page cache, and then calls fdatasync, which makes the kernel push those blocks to the disk and flush the drive's cache. Only when that returns does the backend reply to the client. The modified data pages are not written at this point. They go to the data files later, written by the background writer or the checkpointer, and the checkpoint calls fsync on the data files. If the server crashes in between, recovery replays the WAL from the last checkpoint and reapplies the changes. So durability depends on one sequential write and one sync of the log, and several concurrent commits can share that sync.

Deeper: Why does PostgreSQL crash itself when fsync on a data file fails, instead of retrying?

How a strong answer sounds
Because on Linux a retry gives a false answer. When writeback of a dirty page fails, the kernel reports the error to fsync once and then marks the page clean, so it won't hold unwritable pages in memory for ever. A second fsync finds nothing dirty and returns success, although the data never reached the disk. Before 2019 PostgreSQL retried the checkpoint, saw success, and recycled the WAL covering those pages, so the only durable record of committed changes was deleted while the data files were stale. That was the 2018 fsync bug. Now a failed fsync causes a PANIC. All processes exit, shared memory is discarded, and recovery replays the WAL from the last checkpoint that really completed, which marks the pages dirty again so they are written and synced again. If the disk is still failing, the server fails again visibly, which is the right outcome: the choice is between stopping and silently losing committed data.

🧠 Key takeaways

  • PostgreSQL forks one process per connection. It makes blocking simple and isolates private memory, but connections are expensive, so a pooler sits in front.
  • All processes map one shared memory region. If any backend dies abnormally, the postmaster restarts everything and recovers from the log.
  • Its I/O is buffered, so pages live in shared buffers and in the page cache: double buffering. Shared buffers get about a quarter of RAM.
  • A commit is durable when its WAL record has been written and synced. Data files are updated later and synced at checkpoints.
  • After a failed fsync the kernel may have marked the pages clean. Retrying proves nothing; PostgreSQL now panics and replays the WAL.
  • Huge pages keep per-process page tables for shared memory small, and overcommit and OOM settings keep the kernel from killing a backend.

Check your understanding

With default settings, at what point does PostgreSQL tell the client that its transaction is committed?

The log is the durable copy. The data file may not be updated for minutes.

Why is a table page often held in RAM twice on a PostgreSQL server?

Double buffering: a cache on top of a cache. It is why shared buffers are sized at about a quarter of RAM.

A backend process is killed with SIGKILL. What does the postmaster do?

The dead process might have left shared memory half-changed, so none of it is trusted. Every client is disconnected.

A checkpoint's fsync on a data file returns EIO. A second call returns 0. What can you conclude?

This was the 2018 bug. The safe response is to recover from the WAL, not to retry.

A server has 32 GB of shared buffers and 300 connections, and tens of gigabytes show up as PageTables. What is the fix?

Each process has its own page tables for the shared region. 2 MiB pages make them about 500 times smaller.
