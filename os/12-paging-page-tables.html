Paging & Page Tables

Segmentation's trouble was variable-sized chunks of memory. Paging fixes it by making every chunk the same size: the address space is cut into 4 KiB pages, physical memory into 4 KiB frames, and any page can live in any frame. A per-process page table records where each page is and what you may do with it. It's how every mainstream OS manages memory today, and it explains a long list of things you'll meet later: page faults, copy-on-write, mmap, huge pages, the TLB, and why a container's memory limit counts what it does.

Pages, frames and offsets

With 4 KiB pages, the low 12 bits of a virtual address are the offset within the page (212 = 4096) and the bits above are the virtual page number (VPN). Translation replaces the VPN with a physical frame number (PFN) and keeps the offset unchanged. A worked example on a 32-bit machine:

virtual address   0x00403A7C
                  = VPN 0x00403   |  offset 0xA7C        (top 20 bits | low 12 bits)
page table[0x403] = frame 0x1A2, present, writable, user
physical address  = (0x1A2 << 12) | 0xA7C = 0x001A2A7C

Because every page and frame is the same size, any free frame can hold any page: no holes too small to use, no compaction, no external fragmentation. The cost moves elsewhere: a little internal fragmentation (on average half a page wasted at the end of each region) and the memory and time spent on page tables, which the rest of this chapter and the next are about.

Page-table entries

Each page-table entry (PTE) on x86-64 is 64 bits: the frame number plus flag bits the MMU checks on every access and updates itself as a side effect.

/* x86-64 page-table entry bits (the same layout at every level) */
#define PTE_PRESENT  (1ULL << 0)    /* P:  mapping is valid; if 0, any access faults */
#define PTE_WRITE    (1ULL << 1)    /* RW: writes allowed */
#define PTE_USER     (1ULL << 2)    /* US: user mode may access (0 = kernel only) */
#define PTE_ACCESSED (1ULL << 5)    /* A:  set by hardware on any access (used by page replacement) */
#define PTE_DIRTY    (1ULL << 6)    /* D:  set by hardware on a write (page must be written back) */
#define PTE_HUGE     (1ULL << 7)    /* PS: at a middle level, this entry maps a 2 MiB or 1 GiB page */
#define PTE_NX       (1ULL << 63)   /* XD: instruction fetches fault (no-execute) */
#define PTE_PFN_MASK 0x000ffffffffff000ULL   /* bits 12..51: physical frame address */

static inline uint64_t pte_frame(uint64_t pte) { return pte & PTE_PFN_MASK; }

Why page tables have levels

A flat page table for a 48-bit address space with 4 KiB pages would need 236 entries of 8 bytes: 512 GiB, per process. Almost all of it would describe unmapped addresses. So the table is a tree. On x86-64 the 36 bits of page number are split into four 9-bit indexes, each selecting one of 512 entries in a 4 KiB table at that level. The top table (PML4) is always present; lower tables exist only for regions actually in use. A process using a few hundred megabytes needs a few hundred kilobytes of page tables.

Walk the tables

Pick an address from a real process's layout and an access type, then step through the walk. Each level uses 9 bits of the address as an index; the last step adds the offset. Faults stop the walk where the hardware would.

x86-64 page walk: CR3 → PML4 → PDPT → PD → PT → frameInteractive
Frame numbers are invented but the bit positions, flags and checks are x86-64's. The access is made from user mode. A real walk also sets the Accessed bit (and Dirty, on writes) in the final entry.

Huge pages

If a page-directory entry has its PS bit set, the walk stops there and the entry maps a whole 2 MiB page, with the low 21 bits as the offset (a PDPT entry can likewise map 1 GiB). One entry then covers 512 times as much memory, so the page tables are smaller, walks are one level shorter, and, most importantly, one TLB entry covers 2 MiB instead of 4 KiB (Chapter 13). Databases, JVMs and VMs with large heaps benefit most. Linux offers them two ways: explicitly reserved hugetlbfs pages, and transparent huge pages (THP), where the kernel promotes regions automatically when it can find 2 MiB of contiguous physical memory.

🐘
Why Redis and many databases say "disable transparent huge pages"

THP sounds like free speed, and for many workloads it is. But Redis prints a warning at start-up if THP is set to always, and MongoDB, Oracle and others have long recommended turning it off or using madvise mode. The reasons are all in this chapter. To create a huge page the kernel may need to compact memory, moving pages around to free a contiguous 2 MiB, and that work can stall the allocating thread for milliseconds: latency spikes. And after fork(), copy-on-write happens per page: one write to a 2 MiB huge page copies all 2 MiB instead of 4 KiB, so Redis's background snapshot (Chapter 44) can balloon memory use. The page size is a trade-off between translation cost and the granularity of everything else the kernel does per page.

⚠️
Common mistakes
  • Translating the offset. The offset passes through unchanged; only the page number is looked up.
  • Assuming contiguous virtual pages are contiguous in RAM. Neighbouring pages can be in any frames; that's the point.
  • Forgetting page tables cost memory. A process mapping a huge sparse range, or thousands of processes, can spend gigabytes on page tables.
  • Confusing a page fault with an error. Most faults are normal (lazy allocation, copy-on-write); only unfixable ones become SIGSEGV.
  • Turning on huge pages without measuring. Compaction stalls and per-page copy-on-write can make latency or memory worse.

Interview drill

Explain it simply: How is a virtual address translated to a physical one on x86-64?

How a strong answer sounds
The MMU first checks the TLB. On a miss it walks a four-level tree of page tables rooted at the physical address in CR3: bits 47–39 index the top table, 38–30 the next, 29–21 the next and 20–12 the last, each index selecting one of 512 eight-byte entries that points to the next table. The final entry holds the physical frame number plus permission flags; the frame plus the low 12 offset bits is the physical address. At each level it checks the present bit, and at the end the write, user and no-execute bits against the access; any failure raises a page fault for the kernel to handle. If a middle-level entry is marked as a huge page, the walk stops early and maps 2 MiB or 1 GiB.

Deeper: Why multi-level page tables instead of one big table?

How a strong answer sounds
Size. A single table indexed by every possible page number of a 48-bit space with 4 KiB pages has 236 entries, 512 GiB per process, almost all describing unmapped addresses. A tree only allocates lower-level tables for regions actually in use, so page-table memory is proportional to the memory used, plus some overhead per sparse region. The cost is more memory reads per walk, which the TLB and the CPU's paging-structure caches hide in the common case.

🧠 Key takeaways

  • Pages (virtual) and frames (physical) are both 4 KiB; any page can go in any frame, so there's no external fragmentation.
  • Address = page number | offset; translation swaps the page number for a frame number and keeps the offset.
  • PTEs hold the frame plus flags: present, writable, user, accessed, dirty, huge, no-execute.
  • x86-64 walks four 9-bit-indexed levels from CR3; tables exist only where memory is mapped.
  • Huge pages (2 MiB, 1 GiB) cut walks and TLB pressure but cost compaction and coarse copy-on-write.

Check your understanding

With 4 KiB pages, page 0x2F of a process is in frame 0x91. What physical address does virtual 0x2F0C4 map to?

VPN = 0x2F, offset = 0x0C4. Frame 0x91 shifted left 12 bits is 0x91000; add the offset: 0x910C4.

How many bits of a virtual address index each level of the x86-64 page tables, and why that number?

Each table is exactly one page. 4096 / 8 = 512 entries, so 9 bits pick an entry.

Which bit does the hardware set when a page is written, telling the kernel it must be saved before the frame is reused?

Dirty is set on writes. Accessed is set on any access and drives LRU approximations.

Why would a flat (single-level) page table be impractical on x86-64?

Multi-level tables only allocate the parts of the tree covering memory that's actually mapped.

What is the main performance benefit of a 2 MiB huge page?

Fewer translations to cache and shorter walks. It can actually waste memory, and has costs like compaction.
