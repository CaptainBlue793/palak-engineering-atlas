Compiling & Linking

When you type gcc main.c util.c -o app, four separate programs run, and the file that comes out is not "your code" but an ELF file that tells the kernel how to build a process: which bytes to map where, which are code and which are data, and which shared libraries to load before main starts. Knowing that pipeline turns cryptic errors ("undefined reference", "cannot open shared object file") into obvious ones, and it is the starting point for Chapter 3, where exec loads exactly this file.

The four stages

gcc is a driver. It runs a pipeline, and you can stop it after any stage to look at the intermediate file:

The key fact is in the last line of that caption. While compiling main.c, the compiler sees only the declaration int clamp(int, int, int); from a header. It trusts that a definition exists somewhere and leaves a placeholder, a relocation, saying "put the address of clamp here". The linker resolves those placeholders. If no file defines clamp, compiling succeeds and linking fails.

Object files and symbols

Every object file carries a symbol table: the names it defines and the names it needs. nm prints it, one letter per symbol:

$ nm main.o
                 U clamp          # U: used here, defined elsewhere
0000000000000000 T main           # T: defined here, in the text (code) section
                 U printf
$ nm util.o
0000000000000000 T clamp
0000000000000000 B clamp_calls    # B: zero-initialised global, lives in .bss
0000000000000000 D clamp_name     # D: initialised global, lives in .data

Lower-case letters mean the symbol is local to that file: a static function or variable, invisible to the linker's matching. That's how C does privacy: static at file scope means "not exported".

The ELF layout

Linux executables, object files and shared libraries all use ELF (Executable and Linkable Format). An ELF file is divided into sections for the linker and grouped into segments for the loader, each with permissions:

SectionHoldsMapped asTakes file space?
.textMachine coderead + executeYes
.rodataString literals, const tablesread onlyYes
.dataGlobals with non-zero initial values: int limit = 10;read + writeYes
.bssGlobals that start at zero: static char buf[1 << 20];read + writeNo: only its size is recorded; the kernel hands out zeroed pages
.symtab, .debug_*Symbols and debug infonot loadedYes (removed by strip)
.dynamic, .plt, .gotWhat the dynamic loader needs: libraries to load, call stubs, address tablesmixedYes
 
$ size server
   text    data     bss     dec     hex filename
   1418     600 1048608 1050626  1008c2 server   # its 1 MiB zeroed buffer costs no disk space
$ readelf -l server | grep LOAD
  LOAD  0x000000 0x0000000000400000 ... R    0x1000
  LOAD  0x001000 0x0000000000401000 ... R E  0x1000
  LOAD  0x002000 0x0000000000402000 ... R    0x1000
  LOAD  0x002e10 0x0000000000403e10 ... RW   0x1000

Those LOAD lines are instructions to the kernel: map this range of the file at this address with these permissions. They become the code and data regions of the process's address space (Chapter 11), mapped lazily, page by page (Chapter 14). Keeping code non-writable and data non-executable is a security feature (Chapter 36).

Static vs dynamic linking

Library code like printf can reach your program two ways. Static linking copies the needed object code from libc.a into the executable. Dynamic linking records only "needs libc.so.6", and the code is mapped in at start-up by the dynamic loader, ld-linux-x86-64.so.2, whose path is written in the executable's .interp section.

StaticDynamic
Executable sizeLarge (hundreds of KiB to MiB)Small (KiB)
Start-upFastest: nothing to load or patchLoader maps and relocates libraries first
RAM across processesEach binary has its own copy of library codeOne copy of libc.so's code pages shared by every process
Security fixesRebuild and redeploy every binaryUpdate the library once; restart processes
DeployingCopy one file; runs anywhere with the same kernel ABINeeds compatible library versions on the target
Typical failureLink-time: undefined referenceRun-time: error while loading shared libraries
Who uses itGo binaries, minimal containers, rescue toolsAlmost every Linux distribution package
🕳️
The xz backdoor travelled through dynamic linking

In March 2024 a Microsoft engineer noticed SSH logins taking about half a second longer than they should and traced it to a backdoor planted in the xz/liblzma compression library (CVE-2024-3094). OpenSSH doesn't use liblzma at all. But several distributions patch sshd to link libsystemd, which depends on liblzma, so the dynamic loader mapped the compromised library into every sshd process. The malicious code then used a glibc feature that runs resolver functions while the loader is still filling in the address table, and redirected one of OpenSSH's functions to its own. It was caught before reaching most stable releases. The lesson for this chapter: every shared library in ldd's output runs inside your process with your privileges, whether or not your code ever calls it.

⚠️
Common mistakes
  • Putting definitions in headers. A non-static function or global defined in a header included by two files gives "multiple definition". Headers declare; one .c file defines.
  • Ignoring "implicit declaration" warnings. Without the prototype, pre-C99 compilers guessed int f(); gcc 14 now rejects it by default. Always include the header.
  • Wrong library order on the command line. The traditional linker resolves left to right: gcc -lm main.o can fail where gcc main.o -lm works.
  • Assuming a binary that runs here runs there. A dynamically linked program needs the same (or newer) library versions on the target; ldd tells you which.
  • Shipping debug symbols you didn't mean to, or stripping the ones you'll need for a crash dump. Keep a separate debug file.

Interview drill

Explain it simply: What is the difference between a compile error and a link error?

How a strong answer sounds
Each .c file is compiled on its own into an object file. Compile errors are problems inside one file: bad syntax, wrong types, an undeclared name. The linker then combines object files and libraries and must match every used symbol with exactly one definition. Link errors are about the whole program: "undefined reference" means something was declared and used but no file or library defined it (often a missing .o or -l flag), and "multiple definition" means two files both defined it (often a definition in a header).

Deeper: Why would you choose static linking for a container image, and what do you give up?

How a strong answer sounds
A static binary has no run-time library dependencies, so it can run in an image with nothing else in it (FROM scratch): smaller attack surface, no library version mismatches, faster start-up. Go does this by default. You give up sharing library code pages in RAM across processes, you must rebuild and redeploy to pick up a security fix in a library, and some glibc features (name-service lookups, locales) don't work well statically, which is why static C binaries often use musl instead.

🧠 Key takeaways

  • gcc runs preprocess → compile → assemble → link; -E, -S and -c stop after each stage.
  • Files are compiled separately; references to other files' symbols are left as relocations for the linker.
  • nm shows symbols: T code, D data, B bss, U undefined; static keeps a name local.
  • ELF sections: .text (code), .rodata, .data, and .bss, which costs no file space.
  • Dynamic linking defers library loading to ld-linux.so at start-up and shares library pages in RAM; static linking bakes everything in.
  • Undefined reference = no definition at link time; "cannot open shared object file" = missing library at run time.

Check your understanding

Which stage turns #include <stdio.h> into actual declarations?

The preprocessor pastes the header's text in; gcc -E shows the result.

nm main.o shows U clamp. What does that mean?

U means undefined in this object file: a relocation the linker will fill in with clamp's address.

A program declares static char buf[1 << 20]; at file scope. How much does it add to the executable file's size?

Zero-initialised globals go in .bss, which takes no file space. Only non-zero initial values need to be stored.

A program built on one machine fails on another with "error while loading shared libraries: libssl.so.3: cannot open shared object file". When did this fail?

The executable records that it needs libssl.so.3; the loader looks for it before main runs. Install the library or link it statically.

Why does dynamic linking save RAM on a server running 200 processes that all use libc?

Read-only file mappings are backed by the same page-cache pages in every process (Chapter 30). A static libc would be a separate copy inside each binary.
