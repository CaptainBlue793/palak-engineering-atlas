Page Faults & Demand Paging

A page fault sounds like an error. Almost always it is the kernel doing its job as late as possible. malloc hands out address space without memory behind it; exec starts a program without reading it from disk; a 200 MB binary runs on a machine with 100 MB free. Each works because the kernel waits for the first access to a page, catches the fault, and only then finds a frame for it. This chapter follows what happens between the fault and the retry, when it is cheap, when it costs a disk read, and what goes wrong when there isn't enough RAM to go round.

A fault is a question for the kernel

When the MMU can't complete a translation, because the Present bit is clear or the access breaks a permission bit, it stops the instruction before it has any effect. On x86-64 it stores the address in the CR2 register, pushes an error code saying what was attempted (read or write, user or kernel mode, data access or instruction fetch, page missing or permission denied), and traps into the kernel's page-fault handler.

The kernel then has to answer one question: should this access have worked? The page tables can't tell it, since they only say what is mapped right now. So the kernel keeps its own record of what each process is entitled to: a list of virtual memory areas (VMAs). Each line of /proc/<pid>/maps from Chapter 11 is one VMA: an address range, its permissions, and what backs it (a file, or nothing, for anonymous memory such as the heap and stack).

Demand paging and lazy allocation

Demand paging means a page gets a frame only when it is first used. The kernel applies it everywhere:

  • Heap and stack. malloc of a large block, or mmap of anonymous memory, creates a VMA and returns. No frames are allocated. The first write to each page faults, and the kernel supplies a frame filled with zeros (zeroed so one process can never see another's old data). A first read is cheaper still: the kernel maps one shared, read-only zero page and uses no memory at all.
  • Program code. exec maps the executable and its libraries but reads none of them. Pages are loaded as the program runs into them. Code that never runs, such as error paths and unused features, never costs RAM.
  • The stack. It starts small and grows a page at a time as faults arrive below it, up to the limit in ulimit -s (usually 8 MiB).

That is why VSZ and RSS differ. This program asks for 1 GiB and watches both:

#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>

static void show(const char *when)
{
    struct rusage ru;
    long size, resident;                              /* both in 4 KiB pages */
    FILE *f = fopen("/proc/self/statm", "r");
    fscanf(f, "%ld %ld", &size, &resident);
    fclose(f);
    getrusage(RUSAGE_SELF, &ru);
    printf("%-14s VSZ %5ld MiB  RSS %5ld MiB  minor %7ld  major %ld\n",
           when, size / 256, resident / 256, ru.ru_minflt, ru.ru_majflt);
}

int main(void)
{
    size_t len = 1UL << 30;                          /* 1 GiB */
    long sum = 0;

    show("start");
    char *p = malloc(len);                           /* address space only */
    show("after malloc");
    for (size_t i = 0; i < len; i += 4096) sum += p[i];   /* read one byte per page */
    show("after reads");
    for (size_t i = 0; i < len; i += 4096) p[i] = 1;      /* write one byte per page */
    show("after writes");
    return (int)sum;
}
$ gcc -O1 lazy.c -o lazy && ./lazy
start          VSZ     2 MiB  RSS     1 MiB  minor      71  major 0
after malloc   VSZ  1026 MiB  RSS     1 MiB  minor      72  major 0
after reads    VSZ  1026 MiB  RSS     1 MiB  minor  262216  major 0
after writes   VSZ  1026 MiB  RSS  1025 MiB  minor  524360  major 0

The numbers are typical for 4 KiB pages; yours will differ slightly. malloc changed VSZ and nothing else. Reading every page took 262,144 faults (1 GiB ÷ 4 KiB) and still used no memory, because every page was mapped to the zero page. Only the writes made the kernel hand over a gigabyte of frames, with one more fault per page. If transparent huge pages are on for this region (Chapter 12), one fault maps 2 MiB and you will see about 512 faults per pass instead.

Each of those faults costs around a microsecond, so touching a fresh gigabyte takes a noticeable fraction of a second. Programs that can't afford faults later ask for the memory up front: mmap with MAP_POPULATE fills the mapping at once, and mlock both loads pages and forbids the kernel from taking them away.

A major fault is tens of thousands of times slower than an ordinary memory access, and the time is spent asleep, not computing:

$ ps -o pid,min_flt,maj_flt,vsz,rss,comm -p 4120     # lifetime fault counts for one process
    PID  MINFLT  MAJFLT     VSZ    RSS COMMAND
   4120  918244     137 9731204 2411660 java
$ /usr/bin/time -v ./lazy 2>&1 | grep -i faults
        Major (requiring I/O) page faults: 0
        Minor (reclaiming a frame) page faults: 524417
$ perf stat -e minor-faults,major-faults -p 4120 sleep 10    # fault rate right now

Minor faults in the hundreds of thousands are normal for a process that has just started or just allocated memory. A steady stream of major faults in a running service means it keeps waiting for the disk to get its own memory back, and its latency will show it.

A model: each access stands for 10 µs of work on that page, and "useful work" is the share of time the last 12 accesses spent working and not waiting; a minor fault costs 1 µs and a major fault one disk read (100 µs on the SSD, 8 ms on the hard disk). The victim is the least recently used page; Chapter 15 covers what real kernels do. Swap-out writes happen in the background and aren't counted in the wait. A sweep writes the heap pages and reads the code pages. Real kernels also read neighbouring file pages ahead, which this model leaves out.

Things to notice. With 12 frames the second sweep causes no faults at all: once the working set is in RAM, demand paging costs nothing. With 6 frames every access in the second sweep is a major fault, and the share of time spent on useful work collapses even though the program is doing exactly the same thing. Read a heap page before writing it and it costs no frame. Evict a heap page that came back from swap and was only read: nothing is written, because its copy in swap is still good.

Swap and the swap cache

When RAM runs short the kernel must take frames back. For a file-backed page that is easy: if it is clean, drop it and read it from the file again later; if it is dirty, write it to the file first. An anonymous page (heap, stack) has no file. It can only be evicted if there is somewhere to put it, and that place is swap: a partition or file the kernel uses as a holding area for anonymous pages.

  • Swap out. The kernel writes the page to a free slot in swap and clears the Present bit. With Present clear the MMU ignores the rest of the entry, so the kernel uses those bits to record which swap slot holds the page.
  • Swap in. The next access faults, the kernel finds a swap location in the entry, reads the page into a new frame and maps it. That is a major fault.
  • The swap cache. After a swap-in, the page is in RAM and still in its swap slot. The kernel remembers the pairing. If the page is evicted again without having been written to, there is nothing to write: the copy in swap is still correct.
$ swapon --show
NAME      TYPE      SIZE  USED PRIO
/dev/dm-1 partition   8G  1.2G   -2
$ grep -E 'VmRSS|VmSwap' /proc/4120/status       # how much of one process is in swap
VmRSS:   2411660 kB
VmSwap:   318204 kB
$ sysctl vm.swappiness                              # 0–200; higher = more willing to swap anonymous pages
vm.swappiness = 60

Without swap, anonymous pages can never be evicted, so all the pressure falls on file-backed pages: the page cache and program code. That is a trade, not a cure, as the last section shows. Many systems now put swap in RAM itself, compressed (zram on Android, ChromeOS and Fedora; zswap as a compressed cache in front of a disk): swapping in then costs a decompression instead of a disk read.

Overcommit

Lazy allocation has a consequence. Since malloc gives out address space and not memory, the kernel can promise more than it has, and it does. This is overcommit, and it is on by default in Linux, because most programs never touch everything they allocate and fork would otherwise need room for a full copy of the parent.

CommitLimit:    24512368 kB      # the ceiling, enforced only in mode 2
Committed_AS:   31877120 kB      # what has been promised: already more than the limit

The price is where failure shows up. On Linux, checking malloc for NULL catches very little. If memory really runs out, it happens during a page fault, when the kernel needs a frame and can't free one. No function is there to return an error, so the kernel's OOM killer picks a process and kills it. Chapter 48 works through a real incident.

🔎
Elasticsearch: touch every page at start-up, and never swap

Elasticsearch runs on the JVM, usually with a heap of many gigabytes, and its default configuration makes two choices that come straight from this chapter. First, it starts the JVM with -XX:+AlwaysPreTouch, which writes to every page of the heap during start-up. Start-up gets slower, but all those minor faults are paid before the node takes traffic instead of during the first searches, and a machine without enough RAM fails at once and not at 3 a.m. Second, its documentation tells operators to disable swap or set bootstrap.memory_lock: true, which calls mlockall to pin the process in RAM. The reason is garbage collection: a collector walks the whole heap, so if part of the heap is in swap, a pause that should take milliseconds turns into thousands of major faults and can last minutes. The node stops answering, the cluster decides it has died, and starts moving its data elsewhere. A slow node is often worse than a dead one. Cassandra, Kafka and most databases give the same advice.

Thrashing

Demand paging works when each process's working set, the pages it is actively using, fits in RAM. When the working sets together are bigger than RAM, every fault has to evict a page that some process will need again almost at once. That page faults back in and evicts another. The machine spends its time moving pages and almost none running programs. This is thrashing.

You can recognise it from the outside. CPU utilisation is low, because every process is blocked on a major fault, while the disk is saturated and the load average climbs. Early time-sharing systems made it worse: they saw an idle CPU, admitted more jobs, and deepened the shortage.

$ vmstat 1

#  ^ 14 tasks blocked            ^ pages swapped in and out every second          ^ 91% waiting for I/O
$ cat /proc/pressure/memory        # share of time tasks were stalled waiting for memory
some avg10=78.21 avg60=64.90 avg300=31.07 total=184220931
full avg10=61.45 avg60=49.12 avg300=22.80 total=139881204

Turning swap off does not prevent thrashing. With no swap the kernel can't evict anonymous pages, so it evicts the only thing left: file-backed pages, including the code of running programs. Every function call into an evicted page becomes a major fault that reads the executable from disk again, and the machine freezes just as thoroughly. The real remedies are less demand or more supply: more RAM, fewer or smaller processes, a memory limit on each service so one can't starve the rest (Chapter 34), or a daemon such as systemd-oomd that watches the pressure numbers above and kills something before the whole machine stalls. Which page the kernel chooses to evict is the subject of Chapter 15.

⚠️
Common mistakes
  • Treating every page fault as a bug. Most are minor faults doing lazy allocation. Only invalid faults are errors.
  • Reading VSZ as memory use. It counts promises. RSS counts frames, and even RSS double-counts pages shared between processes.
  • Trusting malloc's return value to tell you memory exists. With overcommit, success means address space. The frames are found, or not, when you touch the pages.
  • Benchmarking the first pass over fresh memory. It measures page faults, not your code. Touch the memory first, then time it.
  • Thinking no swap means no paging. Code and file data are still evicted and re-read from their files.
  • Forgetting a memory access can block. A thread that takes a major fault while holding a lock makes every waiter pay for the disk read.

Interview drill

Explain it simply: What happens on a page fault?

How a strong answer sounds
The MMU can't translate an address, either because the page isn't present or the access isn't permitted, so the CPU saves the faulting address and traps into the kernel. The kernel looks the address up in the process's list of memory areas. If nothing is mapped there, or the access breaks the area's permissions, the process gets SIGSEGV. Otherwise the fault is legitimate and the kernel supplies the page: a zero-filled frame for fresh heap or stack, a page from the page cache for a file mapping, or a read from disk or swap if the data isn't in memory. It updates the page-table entry and returns, and the CPU re-executes the same instruction. If no I/O was needed it is a minor fault costing about a microsecond; if the kernel had to read from storage it is a major fault, and the process sleeps for the duration.

Deeper: A process calls malloc(8 GiB) on a machine with 4 GiB of RAM and no swap, and it succeeds. How, and what happens next?

How a strong answer sounds
It succeeds because Linux overcommits by default. malloc gets address space from mmap: the kernel records a new memory area and allocates no frames. Nothing physical happens until the pages are touched. Reads map the shared zero page and still use no memory. Each first write takes a minor fault and a real frame. As the process writes its way towards 4 GiB the kernel reclaims what it can, which without swap means dropping page-cache and code pages, so the machine gets slow. When it can't free a frame for the next fault, the OOM killer chooses a process, most likely this one since it is the largest, and kills it with SIGKILL. The program never sees a NULL from malloc. To get an error instead you would run in strict overcommit mode, or put the process under a memory limit and handle the failure there.

🧠 Key takeaways

  • A page fault traps to the kernel, which checks the address against the process's VMAs, fixes the page table and restarts the instruction.
  • Demand paging gives a page a frame on first use: zeros for anonymous memory, file contents for mappings.
  • Minor faults need no I/O (about a microsecond); major faults read from disk and block the process (100 µs to milliseconds).
  • Swap gives anonymous pages somewhere to go; file-backed pages are dropped or written back to their files.
  • Overcommit lets allocations succeed without memory behind them; running out shows up later as the OOM killer, not a NULL.
  • When working sets exceed RAM the system thrashes: low CPU use, a saturated disk, almost no progress.

Check your understanding

A process calls malloc(1 GiB) and never touches the memory. Roughly how much physical RAM does that use?

The kernel records the mapping and allocates frames only when pages are first written. VSZ grows by 1 GiB; RSS does not.

A program writes for the first time to a page of freshly allocated heap. What kind of fault is this?

Nothing has to be read from storage, so it is minor. Major means the kernel had to do I/O to get the page's contents.

After the kernel has handled a valid page fault, what does the CPU do?

The faulting instruction had no effect, so it is run again with the page now mapped. The program never notices.

A server is very slow. vmstat shows 2% user CPU, 91% I/O wait, and thousands of pages swapped in and out per second. What is happening?

Low CPU use with heavy paging is the signature of thrashing. Adding more work makes it worse; it needs more RAM or less demand.

With Linux's default overcommit setting, what usually happens when the system truly runs out of memory?

Allocations were already granted. The shortage is discovered when pages are touched, where no error can be returned, so a process is killed instead.
