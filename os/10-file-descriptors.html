File Descriptors & "Everything Is a File"

A file descriptor is just a small integer, 0, 1, 2, 3…, but almost everything a Unix program does with the outside world goes through one: files, pipes, terminals, network sockets, timers, even other processes. Behind that integer sit three kernel tables, and how they point at each other explains a surprising number of real behaviours: why 2>&1 works, why a child process's log lines don't overwrite its parent's, why a deleted log file can keep filling the disk, and why a busy server suddenly fails with "Too many open files".

Three tables behind one integer

When a process calls open("app.log", O_WRONLY) and gets back 3, the kernel has set up a chain of three objects:

TableOne perHoldsShared by
File-descriptor tableProcess (threads share it)Slots 0, 1, 2…, each pointing at an open file description, plus the close-on-exec flagNobody; but fork copies it
Open file description (struct file)Each call to open()The current offset, the access mode and status flags (O_APPEND, O_NONBLOCK), a reference count, a pointer to the inode and to its file_operationsEvery fd that came from the same open: via dup, dup2, fork or fd passing
Inode (in-memory struct inode)Each file on disk, pipe, socket…Size, owner, permissions, where the data lives (Chapter 23)Every open of the same file, by any process

The middle layer is the one people forget, and it's the key to everything below. The offset lives in the open file description, not in the fd and not in the file. Two descriptors that share a description share a position; two separate opens of the same file have independent positions.

open, read, write, close

#include <errno.h>
#include <fcntl.h>
#include <unistd.h>

/* Copy one file to another. Both fds are owned (and closed) by this function. */
int copy_file(const char *src, const char *dst) {
	int in = open(src, O_RDONLY | O_CLOEXEC);
	if (in < 0) return -1;
	int out = open(dst, O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
	if (out < 0) { int e = errno; close(in); errno = e; return -1; }

	char buf[64 * 1024];
	for (;;) {
		ssize_t n = read(in, buf, sizeof buf);
		if (n == 0) break;                                   /* end of file */
		if (n < 0) { if (errno == EINTR) continue; goto fail; }
		for (ssize_t done = 0; done < n; ) {                  /* write() may be short too */
			ssize_t w = write(out, buf + done, (size_t)(n - done));
			if (w < 0) { if (errno == EINTR) continue; goto fail; }
			done += w;
		}
	}
	close(in);
	return close(out);            /* close can report a delayed write error: check it */
fail:
	close(in); close(out);
	return -1;
}

open always returns the lowest free descriptor number. That rule sounds trivial, and it is exactly what old shells relied on to redirect output: close(1); open("out.txt", …) made the new file land on slot 1. It's also why a use-after-close bug is dangerous: after you close fd 7, the next open or accept anywhere in the process may get 7, and a stale write goes to the wrong file or the wrong client.

Each write is 100 bytes. Offsets and sizes are in bytes. "refs" counts how many descriptors (in any process) point at an open file description; it is freed when that reaches 0. The inode stays while any description, or a directory entry, refers to it.

dup2 and redirection

dup2(oldfd, newfd) makes newfd point at the same open file description as oldfd, closing whatever newfd pointed at first. That one call is how shells redirect. For ./server > out.log 2>&1, the shell does this in the child, between fork and exec:

int fd = open("out.log", O_WRONLY | O_CREAT | O_TRUNC, 0644);   /* say it returns 3 */
if (fd < 0) { perror("out.log"); _exit(1); }
dup2(fd, 1);          /* "> out.log":  fd 1 now shares fd 3's description */
dup2(1, 2);           /* "2>&1":       fd 2 now shares whatever fd 1 points at, the same description */
close(fd);            /* fd 3 isn't needed any more; 1 and 2 keep the description alive */
execvp("./server", argv);

Descriptors across fork and exec

fork() copies the fd table, so parent and child have the same numbers pointing at the same open file descriptions, with shared offsets. That's why a parent and child both writing to an inherited log file append after each other rather than overwriting. exec() keeps the fd table too, except descriptors flagged close-on-exec. Forgetting O_CLOEXEC is a real leak: a server that forks helper programs hands them its listening socket and database connections, the helpers hold them open, and a port stays "in use" after the server dies. Modern code opens everything with O_CLOEXEC (or SOCK_CLOEXEC, pipe2(fds, O_CLOEXEC)).

"Everything is a file"

Because read and write dispatch through the description's file_operations table (P2), the kernel can put anything behind a descriptor. Sockets, pipes, terminals and devices are the classic cases, and Linux keeps adding more: eventfd (a counter you can wait on), timerfd (a timer that becomes readable when it fires), signalfd (signals delivered as reads), pidfd (a handle to a process that can't be confused by PID reuse), epoll itself. One mechanism, epoll (Chapter 28), can then wait on all of them at once.

The deleted log file that kept filling the disk

An on-call engineer sees a disk 98% full, finds a 40 GB app.log, deletes it with rm, and… df still says 98%, while du says the directory is tiny. The application still has the file open. rm only removes the directory entry; the inode, and its blocks, live on until the last open file description pointing at it is closed. The process keeps writing into a file nobody can see. lsof +L1 (or ls -l /proc/*/fd | grep deleted) finds it. The fixes are to make the application reopen its log (most daemons do it on SIGHUP, which is what logrotate's postrotate step sends), to truncate it in place with : > app.log instead of deleting it, or, in an emergency, : > /proc/<pid>/fd/<n>. It's the three tables, showing up as a production incident.

⚠️
Common mistakes
  • Leaking descriptors on error paths. Every open, socket and accept needs a close on every path; leaks end in EMFILE: Too many open files.
  • Opening the same file twice and expecting a shared position. Two opens mean two offsets; use dup, or O_APPEND for logs.
  • Using an fd after closing it. The number is reused by the next open; the stale write goes somewhere else.
  • Forgetting O_CLOEXEC before exec'ing helpers: they inherit sockets and files they shouldn't hold.
  • Ignoring short reads and writes, and the return value of close.
  • Raising ulimit -n to hide a leak. Raise it for genuine load (servers commonly need tens of thousands), but find the leak too.

Interview drill

Explain it simply: What is a file descriptor, really?

How a strong answer sounds
An index into the process's file-descriptor table. Each slot points to an open file description, the kernel object created by an open call, which holds the current offset, the open flags and a reference count, and points to the inode (or socket, or pipe) plus the function table that implements read and write for that type. Several descriptors, even in different processes after fork or dup, can share one description and therefore one offset. Because every kind of object sits behind the same interface, the same read, write, close and epoll work on files, sockets, pipes, timers and devices.

Deeper: Why does cmd > out 2>&1 work while cmd 2>&1 > out sends errors to the terminal?

How a strong answer sounds
Redirections are applied left to right, each as a dup2. In the first, > out points fd 1 at the file, then 2>&1 makes fd 2 a copy of fd 1, so both share the file's description. In the second, 2>&1 runs first and copies fd 1 while it still points at the terminal, then > out repoints only fd 1. 2>&1 copies where fd 1 points at that moment; it isn't a lasting link.

🧠 Key takeaways

  • fd → open file description → inode: the offset and flags live in the middle object.
  • open returns the lowest free number; closed numbers are reused immediately.
  • dup2 makes two fds share a description; shells build redirection from it, applied left to right.
  • fork shares descriptions (and offsets) with the child; exec keeps fds unless O_CLOEXEC.
  • Sockets, pipes, timers and devices are all fds, so one API and one epoll cover them.
  • Deleted-but-open files keep their space; fd leaks end in EMFILE.
