Race Conditions & Critical Sections

Two threads each add one to a shared counter a million times, and the total comes out as 1,143,209. Run it again and it is a different wrong number. Nothing crashed and no line of the program is wrong when read alone. This is a race condition: the result depends on how the threads' instructions happen to be interleaved. It is the central problem of concurrent programming, and every tool in the next eight chapters, from mutexes to lock-free structures, exists to control it. This chapter makes the problem exact before any of them try to solve it.

  • Show, instruction by instruction, how a shared counter loses updates
  • Count interleavings and explain why testing rarely finds races
  • Identify critical sections in code, including check-then-act and pointer updates
  • State the three requirements for a solution: mutual exclusion, progress, bounded waiting
  • Tell a data race from a race condition, and find data races with a tool

counter++ is three instructions

#include <pthread.h>
#include <stdio.h>

static long counter;                          /* one variable, visible to both threads */

static void *work(void *arg)
{
    for (int i = 0; i < 1000000; i++)
        counter++;
    return NULL;
}

int main(void)
{
    pthread_t a, b;
    pthread_create(&a, NULL, work, NULL);
    pthread_create(&b, NULL, work, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("counter = %ld (expected 2000000)\n", counter);
}
$ gcc -O0 -pthread race.c -o race
$ ./race
counter = 1143209 (expected 2000000)
$ ./race
counter = 1032574 (expected 2000000)
$ ./race
counter = 1287660 (expected 2000000)

Your numbers will differ, and that is the point. The cause is that counter++ looks like one step and is three. The CPU can't add to a value in memory directly: it has to bring it into a register, change it there, and write it back.

mov  rax, QWORD PTR counter[rip]     ; load   the value from memory into a register
add  rax, 1                         ; add    one, in the register
mov  QWORD PTR counter[rip], rax     ; store  the register back to memory

Each thread has its own rax (Chapter 5) but there is one counter. If both threads load before either stores, both compute the same new value, and one increment disappears:

Two details are worth knowing. On one core, this needs a timer interrupt to land between the load and the store (Chapter 6). On several cores the threads really do run at once, so it happens far more often. And compiling the single instruction add QWORD PTR counter[rip], 1 doesn't save you: inside the CPU it is still a read, an add and a write, and another core can slip in between unless the instruction carries a lock prefix (Chapter 18).

Interleavings

An interleaving (or schedule) is one particular order in which the threads' instructions are executed. The scheduler chooses it, and it changes from run to run with interrupts, cache misses and whatever else the machine is doing. Two threads of three instructions each can be interleaved in 20 ways. Only 2 of them give the right answer: the ones where one thread finishes all three steps before the other starts.

In practice the wrong ones are rare, because a thread usually runs for millions of instructions before it is switched out, so the window between a load and its store is tiny. That is what makes races dangerous. A program can pass every test for months and fail once a week in production under load, on a machine with more cores, or when a debugging printf is removed and the timing shifts. You can't establish correctness by running the program. You have to reason about every interleaving the scheduler is allowed to choose.

Be the scheduler

Two threads are about to run counter++ once each. You decide whose instruction runs next. First find a schedule that ends with 1, then one that ends with 2. Then press Try every schedule, and repeat with the mutex on.

Two threads, one counter: choose the interleavingInteractive
Each thread has its own rax register; counter is shared and starts at 0. The correct final value is 2. With the mutex on, a thread that reaches lock while the other holds it is blocked and can't be stepped.

Things to notice. Without a lock, 18 of the 20 schedules lose an update. With the mutex only 2 schedules remain, and they are the two correct ones: one thread's whole critical section, then the other's. The 18 bad interleavings haven't become unlikely. They have become impossible, because a thread that reaches lock while the other holds it has to wait, so the load–add–store of one thread can't overlap the other's.

Critical sections

A critical section is a piece of code that reads or writes shared state and gives wrong results if another thread runs a conflicting piece at the same time. The three instructions of counter++ are one. Most real ones don't look like arithmetic.

/* 1. Pointer update: two pushes at once lose a node. */
struct node { int value; struct node *next; };
static struct node *head;

void push(struct node *n)
{
    n->next = head;        /* A and B both read the same head ...                   */
    head = n;              /* ... both write it. The second write unlinks the first. */
}

/* 2. Check-then-act: the check is stale by the time of the act. */
int withdraw(long amount)
{
    if (balance < amount)  /* both threads see 100 and pass the check for 80 */
        return -1;
    balance -= amount;     /* both subtract: balance is -60 */
    return 0;
}

/* 3. Lazy initialisation: two threads both find NULL and both create. */
struct config *get_config(void)
{
    if (!cfg)
        cfg = load_config();
    return cfg;
}

The pattern is always the same: a thread reads shared state, decides or computes something from it, and writes, on the assumption that nothing changed in between. To find critical sections, don't look for ++. Look for shared, mutable state and ask what each piece of code assumes stays true from its first access to its last. Data that isn't shared (locals, thread-local variables) or isn't mutable (constants, data that is fully built before other threads can see it) needs no protection, and designs that maximise those are the easiest to get right.

What a solution must guarantee

A mechanism that protects critical sections has to satisfy three requirements. They are worth learning by name, because each failed attempt in the table breaks a different one.

  • Mutual exclusion. At most one thread is inside the critical section at a time. This is the safety property.
  • Progress. If no thread is inside and some want to enter, one of them gets in, and the decision can't be postponed for ever. Threads that aren't interested must not block those that are.
  • Bounded waiting. Once a thread has asked to enter, there is a limit on how many times others can enter before it. No thread starves.

Disable interruptsNo timer interrupt, no switch, so nobody can interleaveWorks for short kernel code on one core. Useless on multicore, where the other thread is already running, and far too dangerous to allow user programs

The flag attempt is the one to remember. A lock built from ordinary reads and writes has the same race as the code it is meant to protect. Software alone can't get out of that circle; the way out is an instruction the hardware guarantees to be atomic.

Data races and race conditions are not the same thing

The two terms are used loosely, and interviewers like to ask for the difference.

Data raceRace condition
DefinitionTwo threads access the same memory location at the same time, at least one of them writes, and nothing synchronises themThe program's correctness depends on the relative timing or order of events
LevelMemory accesses: a precise, mechanical propertyProgram logic: depends on what "correct" means
In C and C++Undefined behaviour: the compiler may assume it never happensNot a language concept
Found by tools?Yes: ThreadSanitizer, HelgrindOnly by reasoning, review and stress testing
Examplecounter++ from two threadsTwo bank transfers that each lock correctly but check the balance in one step and withdraw in another

You can have either without the other. If every access to balance takes a lock, but withdraw releases it between the check and the subtraction, there is no data race and the account can still go negative. In the other direction, a statistics counter that tolerates being slightly off has a data race but arguably no logical race condition, though in C it is still undefined behaviour, and at -O2 the compiler is entitled to do surprising things with it. Fix data races always; then go looking for the logical ones.

$ gcc -g -fsanitize=thread -pthread race.c -o race && ./race

ThreadSanitizer watches every memory access and the locks held at the time, and reports a race even on a run where the interleaving happened to be harmless. Run your tests under it; it costs a 5–15× slowdown and finds bugs that would otherwise take a year to show up.

Dirty COW: a race in the kernel that lasted nine years

In October 2016 a bug was disclosed in the Linux kernel's memory code, CVE-2016-5195, quickly named Dirty COW. It had been there since 2007. When a process writes to a private, read-only mapping of a file, the kernel is supposed to give it a private copy of the page (copy-on-write, Chapter 30) and send the write there. The code did this in steps: fault in a copy, then retry the write. An attacker ran two threads in a loop. One wrote to the mapping through /proc/self/mem. The other called madvise(MADV_DONTNEED) on the same range, telling the kernel to throw the private copy away. Now and then the second thread's call landed exactly between the first thread's two steps, and the retried write went to the original page: the kernel's cached copy of a file the user had no permission to change. With that, an unprivileged user could modify a root-owned program and take over the machine, and it was used in real attacks, including on Android phones. The fix was a few lines that made the second step remember what the first had decided. It is check-then-act, the same shape as withdraw above, in some of the most reviewed C code in the world.

⚠️
Common mistakes
  • "It passed a million test runs, so it's correct." A race is about what the scheduler may do, not what it usually does. Tests sample a tiny fraction of interleavings.
  • Thinking one line of C is one step. x++, x += n, if (p) use(p) and list->tail->next = n are all several reads and writes.
  • Protecting the write but not the read. A reader that sees data halfway through an update is racing too.
  • Locking each step but not the sequence. Check-then-act is only safe if the check and the act are in the same critical section.
  • Calling a data race "benign". In C it is undefined behaviour, and optimisers do exploit it.
  • Debugging with printf. Output is slow and takes locks itself, so it changes the timing and often hides the race.

Interview drill

Explain it simply: What is a race condition? Give an example.

How a strong answer sounds
A race condition is a bug where the result depends on the timing or interleaving of concurrent operations. The standard example is two threads doing counter++ on a shared variable. The increment isn't atomic: it is a load into a register, an add, and a store back. If both threads load the same value before either stores, both write the same result and one increment is lost. Whether it happens depends on where the scheduler switches threads, or on both cores executing at once, so it is rare, non-deterministic and hard to reproduce. The fix is to make the three steps a critical section, with a mutex or an atomic increment, so no other thread can run conflicting code in between.

Deeper: What is the difference between a data race and a race condition? Can code have one without the other?

How a strong answer sounds
A data race is a low-level, precisely defined thing: two threads access the same memory location concurrently, at least one access is a write, and there is no synchronisation between them. In C and C++ it is undefined behaviour, and tools like ThreadSanitizer detect it mechanically. A race condition is a flaw in the logic: correctness depends on event ordering. They overlap but neither implies the other. A bank account where each read and write of the balance takes a lock, but the "enough funds?" check and the withdrawal are separate lock acquisitions, has no data race and a real race condition: two withdrawals can both pass the check. Conversely, an approximate hit counter updated without a lock has a data race, though you might accept the imprecision. I fix data races unconditionally, because the compiler can miscompile them, and then look for check-then-act sequences that need to be made atomic as a whole.

🧠 Key takeaways

  • counter++ is load, add, store; two threads interleaving those steps lose updates.
  • Of the 20 interleavings of two three-step threads, 18 are wrong. They are rare in practice, which is why testing misses them.
  • A critical section is code whose reads and writes of shared mutable state must not overlap with another thread's.
  • A solution needs mutual exclusion, progress and bounded waiting. A lock made of ordinary reads and writes fails the first.
  • A data race is unsynchronised conflicting memory access; a race condition is timing-dependent logic. Each can exist without the other.
  • Use ThreadSanitizer to find data races; use reasoning about every interleaving to find the rest.

Check your understanding

Two threads each run counter++ once on a shared counter that starts at 0, with no locking. What are the possible final values?

If both load 0 before either stores, both store 1. If one finishes before the other loads, the result is 2. It can't stay 0: each thread stores at least 1.

Why is counter++ not atomic?

The value is read into a register, changed there, and written back. A second thread can read the old value in the gap.

A lock is implemented as while (busy) ; busy = 1; using an ordinary shared variable. Which requirement does it break?

Testing and setting the flag are separate steps, so the lock has the same check-then-act race it was meant to prevent.

Every read and write of balance is protected by a lock, but withdraw releases the lock between checking the balance and subtracting. What does the code have?

No two accesses are unsynchronised, so there is no data race. But two withdrawals can both pass the check before either subtracts.

A multithreaded program has passed its test suite thousands of times. What does that tell you about race conditions?

Harmful interleavings can be extremely rare under test conditions and common under production load or on different hardware.
