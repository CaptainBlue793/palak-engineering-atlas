Text, Unicode & Normalisation

Every NLP pipeline starts with a string, and a string is less simple than it looks. The “é” in café can be stored as one character or as two; “ﬁle” can be four letters or three; a password field can contain a character you cannot see. Two strings that look identical on screen can compare unequal, hash differently, and be split into different tokens by a model.

This prerequisite takes eleven strings apart character by character, runs them through three real tokenisers (BERT uncased, BERT cased and XLM-RoBERTa), and measures what normalisation does to 171,018 lines of real web text from C4. The browser you are reading this in has the same Unicode functions, so the panel lets you type your own.

Characters, code points and bytes

Unicode gives every character a number, its code point, written U+ followed by hexadecimal: U+0065 is “e”, U+00E9 is “é”, U+1F468 is “👨”. Python strings are sequences of code points, and len() counts them. Storing or sending text needs an encoding that turns code points into bytes; UTF-8, used by almost every web page and file today, takes 1 byte for ASCII, 2 for most European accents, 3 for most Asian scripts and 4 for emoji. Neither count is what a reader calls a character: a grapheme is what you see as one symbol, and it can be several code points.

s = "café"                         # "cafe" + COMBINING ACUTE ACCENT: shows as café
len(s), len(s.encode("utf-8"))          # (5, 6): 5 code points, 6 bytes, 4 graphemes
s == "café"                       # False: the one-character é is a different sequence
import unicodedata
unicodedata.normalize("NFC", s) == "café"   # True after normalisation
[f"U+{ord(c):04X}" for c in "👨‍👩‍👧"]        # 5 code points: man, ZWJ, woman, ZWJ, girl

Four normal forms

Unicode defines when two sequences mean the same thing and four normal forms that make equivalent strings identical. Canonical equivalence covers sequences that are genuinely the same character, such as precomposed é and e + combining accent. Compatibility equivalence goes further and folds characters that are only variants of another: the ligature ﬁ becomes “fi”, full-width １ becomes “1”, superscript ² becomes “2”, ™ becomes “TM”. Each kind comes composed (C) or decomposed (D).

NFC is always safe: it never changes what the text means. NFKC is the usual choice before matching or tokenising, but it is lossy, so keep the original text alongside it if you ever need to display or reproduce it.

Case folding is not lower-casing

str.lower() is meant for display; str.casefold() is meant for comparison and is more aggressive. German ß lower-cases to itself but case-folds to “ss”, so “Straße”.lower() and “STRASSE”.lower() differ while their case folds match. Some letters have no simple answer: the Turkish capital İ (dotted I) lower-cases in Python to “i” plus a combining dot, two code points, because the right answer depends on the language. Case-insensitive matching should case-fold after NFKC; a model input should usually keep case, unless the model was trained without it.

Characters you cannot see

Some code points have no visible glyph: the zero-width space U+200B, the zero-width joiner U+200D that glues emoji into one picture, the byte-order mark U+FEFF that some editors leave at the start of files, and the combining marks that sit on top of a previous letter. They break exact matching (“pass​word” with a hidden U+200B is not “password”), sneak past keyword filters, and are tokenised inconsistently. A cleaning step should remove zero-width spaces and BOMs explicitly; the joiner should be kept inside emoji sequences, where it is meaningful.

What tokenisers do with it

Every pretrained tokeniser applies its own normalisation before splitting, and they disagree. Three widely used ones, on strings from the panel:

Four lessons in one table. The cased BERT tokeniser does not normalise, so the two spellings of café, identical on screen, became different tokens. The uncased one strips accents, so “résumé” and “resume” become the same token, which is usually what you want for English and quietly destructive elsewhere: on Hindi it removed the vowel signs and the virama, which are combining marks, leaving “नमसत”, not a word. XLM-RoBERTa’s SentencePiece model applies NFKC first, so full-width digits became “123” where both BERTs gave up with [UNK], but it treated the zero-width space as a word boundary and split the family emoji into three people. Pick the tokeniser for your languages and check it on your own text; Chapter 2 measures what these choices do to accuracy.

Measured on real web text

In the first 20,000 documents of C4’s English validation set, 54.6% of documents, and 28.1% of their 171,018 non-empty lines, contain at least one non-ASCII character. Most of it is typography, not foreign words: the commonest non-ASCII categories were closing quotes and apostrophes (65,247 occurrences of ’ and friends), opening quotes and dashes, then accented letters and other scripts. NFC changed only 0.01% of lines, because web text is almost all NFC already. NFKC changed 1.64%, and the list of what it changed is a good warning: the ellipsis … became three full stops in 1,956 lines, ™ became “TM”, ½ became “1⁄2” (with a fraction slash, not “/”), and ideographic, thin and en spaces became ordinary spaces. 1.06% of lines contained a symbol such as an emoji, © or ™, and 0.094% a zero-width character. There were no exact duplicate lines to begin with, because C4’s builders had already deduplicated it, and normalisation exposed only 6 more. The full pipeline above (NFKC, case folding, invisible characters, whitespace) cost about 60 ms per 10,000 lines in plain Python. For contrast, the copy of the tweet_eval sentiment dataset on the Hugging Face hub contains no non-ASCII characters at all in 45,615 tweets: its publisher had already folded or removed emoji and accents. Find out what was done to a corpus before you build on it.

Use case: the duplicate account and the filter that missed

A sign-up service checks whether a username is taken with an exact string comparison. A user registers “café” typed on a Mac keyboard, which produces the decomposed form, and another registers “café” from a phone, which produces the composed form: two accounts that look identical in every list, a classic impersonation route. The same gap lets a content filter that blocks a word miss it written with a zero-width space or full-width letters. The fix is the pipeline above: store NFC, compare on an NFKC + case-folded key with invisible characters removed, and apply the identical function everywhere, including the search index and the model’s training data.

⚠️
Common mistakes
  • Comparing user text without normalising: composed and decomposed é are different strings.
  • Using lower() for case-insensitive matching: “Straße” and “STRASSE” only match after casefold().
  • Applying NFKC to text you must reproduce: it turns x² into x2 and ½ into 1⁄2. Keep the original.
  • Using an uncased, accent-stripping tokeniser on non-English text: it removed Hindi vowel signs here.
  • Assuming len() is what a user sees: the family emoji is 5 code points, 18 bytes and one picture.
  • Normalising differently in training and serving: the model sees different tokens for the same text.

Interview drill

Explain it simply: Why can two strings that look identical compare unequal, and how do you fix it?

How a strong answer sounds
Unicode often has more than one way to encode the same visible text: é can be one precomposed code point or an e followed by a combining accent, and there are compatibility variants such as ligatures and full-width digits. String comparison works on code points, so different encodings compare unequal and hash differently. The fix is to normalise: NFC for storage and display, because it is lossless, and for matching a key built with NFKC plus case folding with zero-width characters removed, kept alongside the original because NFKC is lossy. I measured the practical effect on tokenisers: cased BERT split the decomposed café into different tokens from the composed one, while XLM-RoBERTa normalised them to the same token.

Deeper: You are building a multilingual classifier. What normalisation do you apply, and where?

How a strong answer sounds
Decode bytes as UTF-8 with errors reported, then apply one normalisation function in a shared library used by training, evaluation and serving, so they can never drift. NFC always; NFKC only if the tokeniser does not already do it and the compatibility distinctions do not matter for the task; remove zero-width spaces and BOMs; collapse unusual whitespace. Do not lower-case or strip accents for a multilingual model: accent stripping deletes meaning in many languages, and on Hindi an uncased BERT tokeniser removed vowel signs entirely. Pick a tokeniser trained on the target languages, check its unknown-token rate and tokens per word on a sample of real input per language, and log the normalised text the model actually saw, so mismatches can be found later. On 171,018 lines of C4 web text, NFKC changed 1.6% of lines, mostly ellipses, trademark signs and odd spaces, which is small but enough to split a matching key in two.

🧠 Key takeaways

  • Code points, UTF-8 bytes and visible characters are three different counts.
  • NFC is lossless and safe for storage; NFKC also folds compatibility variants and is lossy.
  • Use case folding, not lower-casing, for comparison; ß and İ have no simple lower case.
  • Zero-width characters and combining marks are invisible and break matching and tokenising.
  • Tokenisers normalise differently: cased BERT kept two cafés apart, uncased BERT stripped Hindi vowel signs, XLM-R applied NFKC.
  • Measured on C4 web text: 28% of lines had non-ASCII characters, NFC changed 0.01%, NFKC 1.6%; one public tweet dataset had been ASCII-folded entirely.

Check your understanding

What does len("café") return in Python?

c, a, f, e and a combining acute accent: five code points that display as four letters and take six bytes in UTF-8.

Which normal form is lossless and the safe default for storing text?

NFC only merges canonically equivalent sequences; the K forms fold compatibility variants and change meaning (x² becomes x2).

Why use casefold() rather than lower() for case-insensitive matching?

“Straße”.lower() keeps ß; casefold() turns it into “ss”, so it matches “STRASSE”.

What did the uncased BERT tokeniser do to the Hindi word नमस्ते?

Accent stripping removes every combining mark, and in Devanagari those marks are vowels.

Why is a zero-width space a problem in a text pipeline?

“pass” + U+200B + “word” looks like password but is a different string; XLM-R split it into two words.
