Datasets, Splits & Hugging Face

Almost every experiment in this course starts with one line, load_dataset(…), and one more, AutoTokenizer.from_pretrained(…). Those lines hide a download, a cache, a file format, a tokenisation pass and a set of train, validation and test splits that someone else decided. Each can quietly cost hours, memory or the meaning of your result.

This prerequisite measures what they do. A 127 MB dataset loads without using any extra memory. Tokenising 25,000 reviews took 9.7 seconds one at a time, 2.5 batched and 0.05 the second time. Asking for four worker processes made it slower. And in four of five standard benchmarks, duplicates turn up inside the training data; in two of them, test examples appear in the training set itself.

  • Load, cache, slice and stream datasets with the datasets library
  • Tokenise a whole dataset efficiently with map
  • Make honest train, validation and test splits, and check them for leakage
  • Load tokenisers and models from the hub reproducibly
  • Read a dataset card, including its licence

The datasets library

The Hugging Face hub hosts hundreds of thousands of datasets, each a repository of data files plus a dataset card (a README with metadata). load_dataset downloads the files once, converts them to Apache Arrow, a columnar format, and caches the result on disk. A Dataset then behaves like a list of dictionaries that you can index, slice, filter and shuffle; a DatasetDict holds the named splits.

from datasets import load_dataset
ds = load_dataset("stanfordnlp/imdb")                 # DatasetDict: train 25,000, test 25,000, unsupervised 50,000
ds["train"][0]                                       # {'text': 'I rented I AM CURIOUS-YELLOW ...', 'label': 0}
ds["train"].features["label"].names                # ['neg', 'pos']
small = ds["train"].shuffle(seed=0).select(range(2000))  # a reproducible subset
texts = list(small["text"])                            # a column; wrap in list() before passing it to a tokeniser

Loading AG News (127,600 headlines) into an empty cache took 2.9 seconds, and loading it again 1.5 seconds; the cache was 30 MB. The Arrow files are memory-mapped: the operating system pages them in as they are read, rather than the program copying them into memory. Loading IMDB, whose Arrow files are 127 MB, changed the Python process’s memory by 0 MB. Only reading the 66.5 million characters of its unsupervised split into Python strings added 64 MB. That is why a laptop can open a dataset larger than its RAM.

Tokenising with map

Dataset.map applies a function to every example and stores the new columns in a cached Arrow file. With batched=True the function receives 1,000 examples at a time, which a fast (Rust) tokeniser processes far more efficiently.

tok = AutoTokenizer.from_pretrained("bert-base-uncased")
def encode(batch): return tok(batch["text"], truncation=True, max_length=512)
enc = ds["train"].map(encode, batched=True, remove_columns=["text"])   # adds input_ids, attention_mask
# define encode and tok at module level: with num_proc on Windows, worker processes cannot see names inside if __name__ == "__main__"

One example per call9.73
Batched, 1,000 per call2.54

Batching was 3.8 times faster. The cache made the second run almost free, which is a gift and a trap: map recognises a rerun by fingerprinting the function, and if you change something the fingerprint cannot see, such as a global setting the function reads, you get yesterday’s result. Pass load_from_cache_file=False when in doubt. The surprise is num_proc=4, which was 7.5 times slower than one process. On Windows each worker is a fresh Python process that re-imports everything and receives the data through pipes, and the fast tokeniser already spreads a batch across CPU cores by itself, so the workers mostly competed with it. On Linux, with cheaper process start-up and a slower Python tokenising function, extra processes often do help; measure before assuming.

Caching and streaming

Some corpora are too large to download. The English C4 is about 305 GB of JSON. With streaming=True, load_dataset returns an iterable that reads records over the network as you consume them, with nothing cached. On this connection the first C4 document arrived after 10.3 seconds (resolving the file list and opening the first shard), after which documents arrived at about 5,500 per second. Every corpus statistic in P1 and P4 was computed this way from the first 20,000 documents. A streamed dataset cannot be indexed or shuffled globally; .shuffle(buffer_size=…) shuffles within a sliding buffer, which is approximate.

c4 = load_dataset("allenai/c4", "en", split="validation", streaming=True)
for doc in itertools.islice(c4, 20000): ...                # reads as it goes; nothing is stored

Train, validation and test splits

The training split fits the model, the validation split chooses hyperparameters and when to stop, and the test split is looked at once, at the end, to report a number. Every look at the test set while making choices leaks a little of it into the model. Many datasets ship without a validation split (IMDB has only train and test), so you carve one out of the training data, with a fixed seed and, for classification, stratified by label:

sp = ds["train"].train_test_split(test_size=0.1, seed=0, stratify_by_column="label")
train, valid = sp["train"], sp["test"]                          # 22,500 / 2,500, same label balance

A random split is honest only if examples are independent. Text rarely is. Several reviews of the same film share names and plot words; P5 found that a review’s nearest neighbours were reviews of the same film. A random split puts reviews of each film on both sides, so the test measures how well the model remembers films, not how well it reads opinions. IMDB’s authors avoided this by putting disjoint sets of films in train and test. Split by the unit you will meet new examples of: by film, by author, by customer, by time.

None of this is large, and none of it is zero. 123 IMDB test reviews also appear word for word in the training set, so a model that memorised its training data gets those for free; at 0.49% of the test set, that could move a reported accuracy by up to half a point, which is about the size of many claimed improvements. AG News has no exact overlap but 15 headlines that differ only in punctuation or case, which is why the normalised check matters. On a dataset you assemble yourself, from scraped reviews, support tickets or forum posts, expect much more: copied templates, reposts and quoted replies are everywhere in real text. Tokenizers, models and the hub

A model on the hub is a repository too: weights, a config, and the tokeniser files it was trained with. Always load the tokeniser from the same repository as the model; a different tokeniser produces IDs that mean different words to the model, and nothing raises an error. Hub repositories can change, so for anything you need to reproduce, pin a revision (a commit hash), as P7 did to load a converted copy of CoNLL-2003.

name = "distilbert/distilbert-base-uncased-finetuned-sst-2-english"
tok = AutoTokenizer.from_pretrained(name)                      # the tokeniser it was trained with
model = AutoModelForSequenceClassification.from_pretrained(name, revision="<commit hash>")   # pin for reproducibility

Licences and data cards

A dataset card should say where the data came from, how it was labelled, what it is for and under what licence it may be used. Many say less. The license field of the seven dataset cards used so far reads: C4, odc-by; GoEmotions, apache-2.0; IMDB, CoNLL-2003 and GLUE, other; AG News and tweet_eval, unknown. “Other” means read the card and the original paper; “unknown” means the uploader did not say. That is normal for research datasets and fine for learning, but before training a model you will ship, find the original source’s terms. The data in tweet_eval, for example, comes from Twitter, whose terms govern redistribution, whatever the hub field says.

Use case: the product-review classifier that scored too well

A team scrapes 200,000 product reviews, splits them randomly, and gets 96% accuracy on a defect-detection task, well above what a pilot suggested. A leakage check like the one above finds 8% of test reviews have an exact or normalised twin in training: the same customers posting the same text on several listings, and sellers pasting template reviews. A second problem is quieter: reviews of the same product share its name and its specific faults, so a random split lets the model recognise products rather than read reviews. They deduplicate, split by product so no product appears on both sides, and re-run. Accuracy is 89%, and that is the number that held up in production.

⚠️
Common mistakes
  • Splitting at random when examples are grouped: reviews of the same film, posts by the same author or tickets from the same customer end up on both sides.
  • Never checking for duplicates: 123 IMDB test reviews are in its training set word for word.
  • Tuning on the test set: carve a validation split from train, with a seed and stratification.
  • Mapping one example at a time: batched tokenising was 3.8× faster; num_proc was slower on Windows.
  • Trusting a stale map cache after changing something its fingerprint cannot see.
  • Loading a tokeniser from a different repository than the model, or not pinning a revision.
  • Assuming a licence: two of seven cards here say “unknown”.

Interview drill

Explain it simply: How would you split a text dataset for a model you intend to ship?

How a strong answer sounds
Three splits: train to fit, validation to choose hyperparameters and stop, and test, used once at the end. But how you split matters more than the ratios. I would split by the unit the model will meet new examples of: new customers, new products, or future dates, so that no group appears on both sides; a random split of reviews puts reviews of the same film or product in train and test and measures memory. Before splitting, deduplicate, exactly and after normalising case and punctuation, and after splitting, check that no test text appears in training. Stratify by label if classes are imbalanced, fix the seed, and record all of it so the split can be rebuilt.

Deeper: Your test accuracy is suspiciously high. How do you check for leakage?

How a strong answer sounds
Start with the data: count test examples whose text, exactly or after normalisation, appears in training; even IMDB has 123. Then near-duplicates, with TF-IDF cosine or MinHash above a threshold. Then group leakage: do the same authors, products or sessions appear on both sides? Then feature leakage: read the model’s strongest features or attributions, looking for things like ratings typed into reviews, signatures or source names, which a linear model will happily use. Finally, re-split by group or by time and re-measure. The size of the drop tells you how much of the score was leakage.

🧠 Key takeaways

  • load_dataset downloads once, converts to memory-mapped Arrow and caches: loading 127 MB of IMDB used no extra memory.
  • Tokenise with map(batched=True): 3.8× faster than one at a time, and cached for the next run; measure num_proc before using it.
  • Stream corpora too large to download; streaming C4 delivered about 5,500 documents a second.
  • Split by group or time, deduplicate, and check for leakage: standard datasets contain duplicates, and IMDB has 123 test reviews in train.
  • Load the tokeniser with its model, pin revisions, and read the card’s licence before you ship.

Check your understanding

Loading 127 MB of IMDB Arrow files changed the Python process’s memory by 0 MB. Why?

Arrow files are mapped into memory by the operating system; reading the text into Python strings is what used 64 MB.

You rerun a map that took 2.5 seconds and it finishes in 0.05 seconds. What happened, and what is the risk?

Use load_from_cache_file=False when a change might not be detected.

Why can a random split of movie reviews overstate accuracy, even with no duplicate texts?

Split by film (as IMDB did), by author or by time, so test groups are new to the model.

When should you use streaming=True?

Streaming reads records as you iterate and stores nothing; you lose indexing and exact global shuffling.

A dataset card’s licence field says “unknown”. What should you do before shipping a model trained on it?

The hub field is the uploader’s declaration; the source’s terms are what apply.
