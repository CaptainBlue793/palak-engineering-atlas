Serving NLP Models

A model that takes 20 ms per text is fine in a notebook and a problem at 2,000 requests a second. Serving is where the cheap wins live: a smaller distilled model, batching, padding only as much as each batch needs, int8 weights, an optimised runtime. Each one is a few lines of code; each needs its accuracy cost measured, because occasionally it is not zero.

This chapter measures them all on one sentiment model, on one machine. One sentence through DistilBERT took 1.95 ms on the GPU and 23.26 ms on 8 CPU threads at 128 tokens. Batching raised GPU throughput 27-fold, dynamic padding made a pass over SST-2 8.3× faster than padding to 512, and ONNX Runtime with int8 weights cut CPU latency from 7.26 ms to 1.28 ms for 0.92 points of accuracy.

  • Measure latency and throughput properly: warm-up, synchronisation, medians
  • Use batching and dynamic padding to raise throughput
  • Quantise to int8 and export to ONNX Runtime, checking accuracy
  • Find the tokeniser’s share of end-to-end latency
  • Choose CPU or GPU serving from measured numbers

Measuring correctly

GPU calls return before the work finishes, so a timer without torch.cuda.synchronize() measures nothing. The first calls are slow (kernel selection, memory allocation), so warm up first. Latency varies, so report the median of many runs, and in production the 95th or 99th percentile. All numbers here follow that recipe.

Batching and padding

A GPU processing one sentence is mostly idle; processing 64 at once costs little more. Batching raises throughput (texts per second) at the price of latency (each request waits for its batch). Inside a batch, every sequence is padded to the same length. Padding everything to 512 wastes most of the compute on SST-2’s short sentences; dynamic padding pads only to the longest sequence in each batch, and sorting requests by length before batching wastes even less. Measured: latency and throughput

At batch 1, DistilBERT took 1.6–4.17 ms on the GPU from 32 to 512 tokens and BERT-base about twice that (3.11–8.12 ms), as the halved layer count predicts. On 8 CPU threads the same sentence took 9.4, 23.26 and 78.28 ms for DistilBERT and 18.45, 46.06 and 162.92 ms for BERT-base: on a CPU, length and depth both cost roughly in proportion. bf16 on the GPU made no difference for short inputs, where a single sequence leaves the GPU mostly idle, and was 2.6× faster at 512 tokens.

Throughput is a different number. With 64-token inputs on the GPU, batch 1 processed 405 texts a second; batch 64 processed 11,015, 27 times as many, while each batch took 5.81 ms instead of 2.47. Beyond 64 the GPU was saturated: batch 256 gave 10,889 a second and four times the wait. A server that collects requests for a few milliseconds and sends them as one batch gets most of that throughput at a small cost in latency.

Measured: padding

SST-2 validation sentences are short (median 24 word pieces, longest 55). Classifying all 872 in batches of 32 processed 42,208 token positions with dynamic padding, 111,616 when every batch was padded to 128 and 446,464 when padded to 512, and took 0.089 s, 0.164 s and 0.743 s respectively. Padding to the model’s maximum made the job 8.3× slower to compute nothing extra. Dynamic padding is one argument to the tokeniser or collator, and there is no reason to serve without it.

Measured: quantisation and runtimes

Dynamic int8 quantisation stores linear-layer weights as 8-bit integers and quantises activations on the fly: a quarter of the memory for those weights and faster integer matrix multiplication on CPU. ONNX Runtime runs an exported graph with fused operators. Both are a few lines; both can change predictions slightly.

Exporting to ONNX Runtime alone, with no change to the weights, cut single-sentence CPU latency from 7.26 to 3.97 ms with identical predictions (91.06%). Quantising to int8 roughly halved latency again in each runtime (7.26 → 3.57 ms in PyTorch, 3.97 → 1.28 ms in ONNX Runtime) and cost about a point of accuracy (90.02% and 90.14% against 91.06%). The ONNX int8 model is 4.0× smaller on disk (64.2 MB), because the embeddings are quantised too; PyTorch’s dynamic quantisation only converts the linear layers (132.3 MB). fp16 on the GPU changed no prediction. A point of accuracy for a 5.7× speed-up is usually a good trade, but it is a trade, and it must be measured on your own data.

The tokeniser

Tokenising a batch of 32 sentences took 0.8 ms; running DistilBERT on them on the CPU took 198.97 ms. The tokeniser was 0.4% of the work, negligible here. The “slow” comparison did not measure what it was meant to: in transformers 5 the class still called BertTokenizer appears to use the same fast implementation (the two took similar times (1.86 and 2.12 ms per 256 sentences), since version 5 reworked the tokeniser classes. The old pure-Python tokenisers, still found in older code and some custom pipelines, were typically ten or more times slower and could dominate CPU latency; check which one a deployment actually loads.

Use case: moving a classifier off the GPU

A team serves a BERT-base intent classifier on a GPU instance that is busy 6% of the time. They switch to DistilBERT, export to ONNX, quantise to int8, and benchmark on the CPU machines they already run: batch-1 latency well inside their 30 ms budget, accuracy within 0.3 points on their own test set, and the GPU instance switched off. The benchmark script, with warm-up, medians and an accuracy check, goes into CI so that a future model or library upgrade cannot quietly slow the service or shift its predictions.

⚠️
Common mistakes
  • Padding every request to 512: it processed 10.6× the token positions of dynamic padding on SST-2 and took 8.3× as long.
  • Serving at batch 1 on a GPU: 405 texts a second against 11,015 at batch 64.
  • Shipping a quantised model without its accuracy check: int8 cost about a point here (91.06 → 90.14).
  • Timing GPU code without synchronising: you measure how fast work is queued, not done.
  • Quantising without re-measuring accuracy on your own data, not just a benchmark.

Interview drill

Explain it simply: How would you make a BERT classifier faster in production?

How a strong answer sounds
In rough order of effort: use a distilled model (DistilBERT was about twice as fast as BERT-base here: 23.26 against 46.06 ms per sentence on CPU); pad dynamically and bucket by length (8.3× faster than padding to 512 on SST-2); batch requests on a GPU (405 → 11,015 texts a second from batch 1 to 64); use bf16 on GPU; and on CPU export to ONNX Runtime and quantise to int8, which took single-sentence latency from 7.26 to 1.28 ms for about a point of accuracy. Truncate to the length the task needs, and measure every step on the real traffic, with warm-up and percentiles, and check accuracy after each change.

Deeper: Design serving for 5,000 requests a second with a 50 ms p99 budget.

How a strong answer sounds
First, measure the model: latency at batch 1 and throughput against batch size, at the real length distribution, for p50 and p99. With the numbers here, an int8 ONNX DistilBERT does one sentence in about 1.28 ms on 8 CPU threads, so a CPU fleet is plausible: 5,000 requests a second at batch 1 needs on the order of 6 concurrent workers. On GPU, batching does the work: a server that collects requests for up to 5–10 ms and sends batches of up to 64 reached about 11,015 texts a second per GPU here, so one or two GPUs with headroom. Either way: dynamic padding and length bucketing; a max-length cap; autoscaling on queue depth; timeouts so a slow batch cannot blow the p99; a cheaper fallback model under overload; and load tests at peak with realistic text before launch, measuring p99 end to end including tokenisation and network.

🧠 Key takeaways

  • Measured: batching took GPU throughput from 405 to 11,015 texts a second (batch 1 → 64); dynamic padding was 8.3× faster than padding to 512.
  • Measured: ONNX Runtime int8 cut CPU latency from 7.26 to 1.28 ms and size from 255.5 to 64.2 MB, for 0.92 points of accuracy.
  • Measured: DistilBERT was about twice as fast as BERT-base on CPU at every length; bf16 helped on GPU only for long inputs.
  • Warm up, synchronise and take medians, or the numbers mean nothing.
  • Every speed-up is checked for accuracy on your own test set.
