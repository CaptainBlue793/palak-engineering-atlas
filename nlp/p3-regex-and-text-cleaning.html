Regular Expressions & Text Cleaning

Before any model sees text, someone writes a few regular expressions: to pull out emails and dates, to strip HTML, to lower-case and remove punctuation. These lines are short, rarely tested and run on every document. This prerequisite measures what they actually do.

On 171,018 lines of C4 web text, the obvious email pattern returned a trailing full stop or comma with almost half its matches, and 12% of its matches contained no valid address at all. A two-character change to a pattern made matching 1.2 seconds slower per 26-character string, doubling with each extra character. And on 25,000 IMDB reviews, the usual cleaning steps moved a sentiment classifier’s accuracy by less than half a point, except removing stop words, which cost 1.2 points because the standard list contains “not”.

  • Read and write the regex syntax that text work needs
  • Extract emails, URLs and dates, and measure what a pattern gets wrong
  • Recognise and avoid catastrophic backtracking
  • Strip HTML and boilerplate
  • Decide which cleaning steps a model needs, by measuring them

The regex syntax that matters

A regular expression describes a set of strings. Text work uses a small part of the language:

SyntaxMeansExample
\d \w \sa digit, a word character (letter, digit, underscore), whitespace\d+ matches 2019
\S \W \Dthe opposite of each\S+ matches any run of non-spaces, punctuation included
[A-Za-z0-9._-]one character from a set; [^…] is “not in the set”[^\s<>]
+ * ? {2,}one or more, zero or more, optional, at least two[A-Za-z]{2,} for a top-level domain
\ba word boundary, a zero-width position between \w and \W\bcat\b skips “concatenate”
(…) (?:…)a capturing group, a non-capturing group(?:\.[a-z]+)*
^ $start and end of the string (or line, with re.M)^\s*$ is a blank line
 
import re
EMAIL = re.compile(r"\b[A-Za-z0-9._%+-]+@[A-Za-z0-9-]+(?:\.[A-Za-z0-9-]+)*\.[A-Za-z]{2,}\b")   # compile once, reuse
EMAIL.findall("Write to (nmarti20@gmu.edu), or office@example.com.")
# ['nmarti20@gmu.edu', 'office@example.com']: no bracket, no comma, no full stop
re.sub(r"<[^>]+>", " ", "Loved it.<br /><br />Ten out of ten.")   # 'Loved it.  Ten out of ten.'

Extraction: what a pattern gets wrong

Every extraction pattern makes two kinds of error: it matches things that are not what you want (false positives, or matches with junk attached), and it misses things that are. The only way to know which is to run it on real text and read the matches. Here are a naive and a stricter pattern for each of three things, run over the 171,018 non-blank lines of the first 20,000 documents of C4’s validation split:

Date, stricter (day/month 1–31, year 19xx or 20xx)31291 (29%) are still ambiguous: 10/03/2015 is 10 March or 3 October35.2

The stricter patterns are better, not correct. The stricter date pattern drops every two-digit year, so 5/4/16 is now a miss, and it cannot know whether a page is American or British: almost a third of the dates it finds could be read either way. No pattern can fix that; only metadata about the source can. Stricter is also not always slower or faster: the stricter URL pattern was nine times slower than http\S+, the stricter email pattern slightly faster than \S+@\S+, because it fails sooner on lines without an @. All of them process 10,000 lines in under 40 ms.

Catastrophic backtracking

Python’s re, like the regex engines in JavaScript, Java, .NET and PCRE, is a backtracking engine: when part of a pattern can match a string in several ways, it tries them one at a time until one works or all fail. Usually that is fast. With nested quantifiers such as (a+)+, the number of ways to split a run of as between the inner and outer + is 2n−1, and if the match eventually fails, the engine tries every one.

Timed on one string of each length, ^(a+)+$ took 18.5 ms on 20 a’s and a b, 303 ms on 24 and 1.21 seconds on 26, multiplying by about four for every two characters added. ^a+$ took under 0.005 ms on all of them. Extrapolating the doubling, a 40-character line would take over five hours. Real incidents look less obvious than (a+)+: (\s*,?\s*)* for a comma-separated list, or (\w+\s?)+$ for “words followed by an end”. Cloudflare’s global outage of July 2019 was one regex with this flaw in a firewall rule, using all the CPU on its edge servers.

# fixes, in order of preference
re.compile(r"^a+$")                  # 1. write a pattern with only one way to match
re.compile(r"^(?>a+)+$")              # 2. atomic group (Python 3.11+): never gives characters back
re.compile(r"^(a++)+$")               #    possessive quantifier (Python 3.11+), same idea
import re2; re2.compile(r"^(a+)+$")    # 3. google-re2: a linear-time engine, no backreferences
# 4. cap input length before matching untrusted text

HTML and boilerplate

Text scraped from the web or exported from a system arrives with markup. 58.7% of IMDB training reviews contain an HTML tag, nearly all of them <br /> line breaks. A regex such as <[^>]+> removes simple tags and is fine for that. For real web pages use a parser: BeautifulSoup(html, "html.parser").get_text(" ") handles comments, scripts, entities like &amp; and a > inside an attribute, which a regex does not, and boilerplate removers such as trafilatura drop menus, cookie banners and footers, which no tag-level rule can identify. Corpora like C4 were built with exactly such rules: keep lines that end in punctuation, drop pages with a “lorem ipsum” or a curly brace, drop lines with “JavaScript”.

Measured: what cleaning steps do to a classifier

Cleaning tutorials recommend a fixed recipe: lower-case, remove punctuation, remove numbers, remove stop words. Each step was added in turn to a TF-IDF and logistic-regression sentiment classifier, trained on 25,000 IMDB reviews and tested on another 25,000:

Cleaning applied before TF-IDF (unigrams + bigrams)Test accuracyChange
Raw text90.56%
Remove HTML tags90.49%−0.07
+ lower-case90.74%+0.25
+ remove punctuation (including ! and ?)90.89%+0.15
+ remove numbers90.66%−0.23
Lower-cased + scikit-learn’s English stop words removed89.53%−1.21 vs lower-cased
Lower-cased + stop words removed, negations kept89.89%−0.85 vs lower-cased
Lower-cased, unigrams only (no cleaning change, for scale)88.99%−1.75 vs lower-cased

The first four steps moved accuracy by at most a quarter of a point each way. With 25,000 test reviews the standard error of an accuracy near 90% is about 0.19 points, so none of those changes is clearly real. Removing HTML did not help because br simply became one more feature the classifier learned to ignore. Removing punctuation did not hurt, even though it removed ! and ?, which the tokeniser here counted as tokens.

Removing stop words did hurt, by 1.2 points. scikit-learn’s 318-word English list contains not, no, never, nor, nothing, none, nobody, neither, nowhere and cannot, so “not good” and “good” become the same feature. Keeping those ten words recovered 0.36 of the 1.21 points; the rest came from words like but, too, very and off, also on the list. And the largest effect in the table is not a cleaning step at all: dropping bigrams cost 1.75 points. Feature choice mattered more than any cleaning step. The rule that follows is to clean data errors always, and to treat model-specific cleaning as a hypothesis you test. For pretrained transformers (from Chapter 15) the answer is usually to do none of it, because their tokenisers were trained on cased, punctuated text and expect it.

Use case: the support-ticket parser that froze

A team routes support tickets by pulling order IDs, emails and dates out of the body with a dozen regexes. One day ingestion stops: a worker is at 100% CPU on a single ticket, a 3,000-character pasted log with a long run of spaces. The culprit is (\s*\w+\s*)+:, written to find “Field name:” labels. The fix has three parts: rewrite the pattern so there is one way to match (\w+(?:\s+\w+)*\s*:), cap input at 10,000 characters before any regex runs, and add a test that times every pattern on a 5,000-character adversarial string. While they are there, they find the email pattern has been storing alice@example.com. with the full stop, so replies bounce, and switch to the stricter pattern above.

⚠️
Common mistakes
  • Trusting \S+ around an anchor: half the naive email and URL matches on C4 carried trailing punctuation, and 12% of “emails” were not addresses.
  • Nested quantifiers such as (a+)+ or (\s*x\s*)*: 26 characters took 1.2 seconds, doubling per character.
  • Parsing HTML with a regex beyond stripping simple tags; use a parser.
  • Removing stop words by default: the standard list contains “not”, and it cost a sentiment classifier 1.2 points.
  • Applying a cleaning recipe without measuring it: four common steps here changed accuracy by less than the noise.
  • Assuming a date’s order: 29% of the dates found could be day-first or month-first.
  • Lower-casing text for a cased pretrained model, which then sees text unlike its training data.

Interview drill

Explain it simply: Should you lower-case text and remove stop words before training a classifier?

How a strong answer sounds
It depends on the model, so measure it. For a bag-of-words model, lower-casing usually helps a little because it merges counts of the same word. Removing stop words often hurts sentiment, because standard lists include negations: on IMDB with TF-IDF and logistic regression, removing scikit-learn’s stop words cost 1.2 points, and keeping the ten negation words won back only about a third of that. Lower-casing, punctuation and number removal each changed accuracy by under 0.3 points, inside the noise. For a pretrained transformer, do neither: its tokeniser expects natural text. What you should always do is fix data errors: markup, encoding, normalisation.

Deeper: An ingestion worker hangs at 100% CPU on one document. You suspect a regex. What is happening, and how do you fix and prevent it?

How a strong answer sounds
Most likely catastrophic backtracking: a pattern with nested or overlapping quantifiers, like (\s*\w+\s*)+, has exponentially many ways to match a long run, and when the overall match fails the backtracking engine tries them all. ^(a+)+$ takes over a second on 26 characters and doubles with each one. Fix: rewrite so each character can be matched only one way, or use an atomic group or possessive quantifier (Python 3.11+), or a linear-time engine such as RE2. Prevent: cap input length, run untrusted input with a timeout, and add tests that time each pattern on long adversarial strings.

🧠 Key takeaways

  • A regex is only as good as its measured matches: read a sample of what it returns on real text.
  • Measured on C4: \S+@\S+ carried trailing punctuation in 49% of matches and 12% were not addresses; a stricter pattern fixed both.
  • Nested quantifiers backtrack exponentially: ^(a+)+$ took 1.2 s on 26 characters; write one-way patterns, use atomic groups or RE2, cap input length.
  • Strip markup with a parser; normalise Unicode before matching.
  • Measured on IMDB: removing stop words cost 1.2 points (the list contains “not”); other common cleaning steps changed accuracy by less than the noise.
