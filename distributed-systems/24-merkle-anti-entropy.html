Merkle Trees & Anti-Entropy

Two replicas each hold a billion rows that are supposed to be identical. Replicas drift: a node was down for an hour, a message was dropped, a disk returned a wrong block. Chapter 23 ended with anti-entropy, the background process that compares replicas and repairs any difference, and left open how it could be affordable. Sending a billion rows across the network to check them is out of the question, and so is sending a billion hashes when the usual answer is "no difference". The tool that makes it cheap was invented by Ralph Merkle in 1979 for a different purpose, digital signatures. Hash the rows in groups, then hash the hashes in pairs, and again, up to a single value at the top. If two replicas' top values are equal, everything beneath is equal, and the check has cost one comparison. If they differ, the two children show which half to look in. This chapter covers how the tree is built and walked, what it costs, and where else it appears, from Cassandra's repair to every Git repository.

  • Estimate what a comparison costs, and say what decides how much data is streamed
  • Prove that one item belongs to a tree using a logarithmic number of hashes
  • Recognise the same structure in Cassandra, Dynamo, Git and certificate logs

Hash trees

Divide the data into ranges that both replicas agree on. In a partitioned store these are slices of the token range (Chapter 19). Each range becomes a leaf, whose value is a hash of all the rows in it, taken in a fixed order. Each internal node's value is the hash of its two children's values joined together. The value at the top is the root.

record Node(byte[] hash, Node left, Node right, Range range) {
	boolean isLeaf() { return left == null; }
}

Node build(List<Range> leaves, int from, int to) {                 // leaves in token order; to is exclusive
	if (to - from == 1) {
		Range r = leaves.get(from);
		return new Node(sha256(LEAF, rowsInOrder(r)), null, null, r);    // reads every row in the range
	}
	int mid = (from + to) >>> 1;
	Node l = build(leaves, from, mid), r = build(leaves, mid, to);
	return new Node(sha256(INNER, l.hash(), r.hash()), l, r, l.range().union(r.range()));
}

The property that everything rests on: a node's hash depends on every row beneath it. Change one byte of one row and its leaf's hash changes, so its parent's does, and so on up to the root. With a collision-resistant hash (P6), two trees with equal roots hold equal data, for all practical purposes. The root is said to commit to the whole dataset.

The two constants LEAF and INNER are a one-byte prefix that makes a leaf's hash and an internal node's hash come from different inputs. Without it, an internal node can be passed off as a leaf whose "data" happens to be two hashes joined together.

Finding the differences

Two replicas build trees over the same ranges and compare from the top.

void diff(Node mine, Node theirs, List<Range> out) {
	if (Arrays.equals(mine.hash(), theirs.hash())) return;        // identical subtree: skip everything under it
	if (mine.isLeaf()) { out.add(mine.range()); return; }         // as far down as the tree can see
	diff(mine.left(), theirs.left(), out);
	diff(mine.right(), theirs.right(), out);
}

Each equal pair of hashes removes a whole subtree from the search. One differing row leaves a single path of unequal hashes from the root to one leaf, and the walk compares two children at each level along it: about 2 log2 L hashes for a tree of L leaves. With d scattered differences the cost is at most d times that.

Two points about the last step. The tree finds ranges, and it can't see inside a leaf: if a leaf covers a thousand rows and one differs, all thousand are sent. And the comparison is symmetric. Neither replica is "the good one", and each may hold rows the other lacks, so data usually flows in both directions.

The top row is the root and the bottom row is the leaves, each covering an equal slice of the token range. Keys are placed by hashing, so a leaf holds about 1,024 ÷ leaves of them, and not exactly that. The panel uses a 32-bit hash to keep the values short. Real systems use 128 bits or more.

Things to notice. Start as it opens, with 64 leaves and one stale key. The roots differ. At each level below, two hashes are compared and one differs, and the equal one removes half of what was left: 512 keys, then 256, then 128. After six levels and 13 hashes the walk arrives at one leaf, number 18, which holds 24 keys. All 24 are sent to repair one. Choose "nothing" and the whole comparison is a single hash. A hash for every key would have been 1,024.

Now change the number of leaves, keeping the one stale key. With 16 leaves the walk needs 9 hashes and sends 68 keys. With 256 it needs 17 hashes and sends 5. Eight more hashes save 63 keys, and with rows of a kilobyte or more each, that is the better side of the trade. The price of more leaves is a larger tree to build and hold in memory.

Where the differences fall matters as much as how many there are. Eight scattered keys with 64 leaves cost 55 hashes and reach 7 leaves, two of the eight having landed in the same one, and 124 keys are sent. Eight keys next to each other share a single path: 13 hashes and 24 keys, the same as for one. With 100 scattered keys the tree stops helping. At 64 leaves, 51 of them differ and 842 of the 1,024 keys are sent. A hash tree pays when differences are rare, which is the normal condition of replicas in good health.

Anti-entropy repair in practice

The walk is the cheap part. The work is in building the trees and in what follows.

  • Building reads everything. A leaf's hash needs every row in its range, so a tree built from scratch costs a full scan of the data on every replica involved: heavy disk I/O that competes with live traffic. The alternative is to keep the tree up to date as writes arrive, which costs a little on every write and nothing extra at repair time.
  • Both sides must hash the same thing. A write that has reached one replica and not yet the other shows up as a difference. It is a harmless one, repaired by sending data that was about to arrive anyway, and it wastes work. So does any disagreement about what to include: if one replica has already purged an expired row and the other hasn't, their hashes differ though nothing is wrong.
  • Leaf size sets the waste. Fewer leaves make a smaller tree and send more rows per difference. More leaves send less and cost memory. The panel shows the trade directly.
  • The ranges must match. Two trees can be compared only if their leaves cover the same slices. When ownership of ranges changes, as nodes join or leave, the trees for the affected ranges are rebuilt.
  • Repair doesn't decide who is right. It delivers each replica's rows to the other, and the store's usual conflict rule merges them: latest timestamp, version vectors, or a merge function (Chapter 25).

Anti-entropy is the slowest of the three repair mechanisms from Chapter 12, and the only complete one. Hinted handoff covers writes that a node is known to have missed. Read repair covers rows that happen to be read. Only a full comparison reaches data that is never read and was lost without anyone noticing.

Proving membership

A hash tree does one more thing, used less in databases and heavily elsewhere. Suppose a client trusts a root and wants to check that one particular item is in the tree, without downloading the tree. The server sends the item and the hash of the sibling at each level on the way up. The client hashes its way to the top and compares the result with the root it trusts.

boolean verify(byte[] item, List<Sibling> path, byte[] trustedRoot) {
	byte[] h = sha256(LEAF, item);
	for (Sibling s : path)                                       // from the leaf's level up to just below the root
		h = s.isOnLeft() ? sha256(INNER, s.hash(), h) : sha256(INNER, h, s.hash());
	return Arrays.equals(h, trustedRoot);
}

For a tree of a billion leaves the proof is thirty hashes, under a kilobyte. A server can't forge one without finding a hash collision. This is how a lightweight Bitcoin client checks that a payment is in a block (Chapter 34), and it is the basis of the use case below.

Cassandra. The command nodetool repair asks each replica of a range to build a tree, a step called a validation compaction, since it reads the SSTables as a compaction does (Databases, LSM trees). The trees go to the node coordinating the repair, which compares them and tells replicas which ranges to stream to each other. The tree's depth is capped to bound memory, so on a large table one leaf covers many partitions, and a single stale row can cause megabytes to be streamed. This is known as overstreaming, and it is the bottom-left corner of the panel at scale. Running repair on smaller sub-ranges, each with its own full-depth tree, reduces it. Chapter 45 covers why repair has a deadline.

Git. Every object in a repository is named by the hash of its content. A file is a blob. A directory is a tree object listing each entry's name and hash. A commit names one tree and its parent commits. So a commit's 40-character ID commits to every byte of every file in that version and to the entire history before it. Two consequences are the same as in a database. If two commits share a directory's hash, the directories are identical and Git doesn't look inside, which is why comparing two versions of a huge repository is fast. And when you fetch, your client and the server exchange commit IDs each side has, find the common ones, and transfer only the objects beneath the commits you lack. A structure where a node can have several parents is strictly a hash graph, and the principle is unchanged.

Use case: Certificate Transparency, a hash tree the public audits

In 2011 the Dutch certificate authority DigiNotar was breached, and the attackers issued themselves a valid certificate for google.com, which was then used to intercept the email of users in Iran. The certificate was technically genuine, and nobody outside could have known it existed: a certificate authority could sign anything, and only the party it was shown to would ever see it. Engineers at Google proposed a remedy that became RFC 6962 in 2013. Every certificate must be submitted to public logs, and each log is an append-only Merkle tree whose leaves are certificates. The log periodically signs its current root and size, the signed tree head. Two kinds of proof make the log checkable by people who don't trust its operator. An inclusion proof is the sibling path described above: it shows that a given certificate is under a given root, in about log2 n hashes. A consistency proof shows that a later root's tree contains an earlier root's tree as its prefix, so the log has only appended and has never removed or rewritten an entry. Monitors run by companies and researchers fetch every new entry and watch for certificates issued for their own domain names. Auditors compare the tree heads that different parties were shown, since a log that presented different trees to different clients would be caught the moment two of them compared notes. Since April 2018 Chrome has refused certificates that don't carry signed promises of inclusion from such logs. The logs now hold billions of certificates, and mis-issuance that once went unseen for months is typically noticed within hours. The data structure does the work: one small signed hash commits a log operator to an exact, ordered set of billions of entries, and any change to that set is detectable by anyone holding an older hash.

⚠️
Common mistakes
  • Assuming the tree finds rows. It finds leaves. Everything in a differing leaf is sent.
  • Building trees over different ranges or different snapshots. The comparison reports differences that aren't real.
  • Hashing rows in whatever order they are stored. The same data in a different order gives a different hash. Use a fixed order and a canonical encoding (P3).
  • Forgetting what a build costs. A full repair reads all the data on every replica. Run it in small pieces, off-peak.
  • Never running anti-entropy. Read repair and hints miss rows that are never read.
  • Hashing leaves and internal nodes the same way. It lets an internal node be presented as a leaf. Prefix them differently.

Interview drill

Explain it simply: What is a Merkle tree, and why do distributed databases use one?

How a strong answer sounds
It is a tree of hashes. The leaves are hashes of blocks of data, for a database, ranges of keys, and each internal node is the hash of its children, up to a single root hash. Because every node's hash depends on everything below it, the root summarises the whole dataset: if two replicas have the same root, their data is identical. Databases use it for anti-entropy, the background repair of replicas that have drifted apart. Instead of shipping all the data, or a hash per row, the replicas compare roots. If they match, done, at the cost of one hash. If not, they compare the children and recurse only into subtrees whose hashes differ, so they locate the differing ranges with a number of comparisons proportional to the number of differences times the tree height, not to the data size. Then they exchange only the rows in those ranges. Cassandra, Dynamo and Riak do this. The costs are building the tree, which requires reading the data, and granularity: the tree identifies a leaf range, not a row, so everything in a differing leaf is transferred.

Deeper: Repair on a large Cassandra cluster is slow and floods the network. What is going on, and what would you change?

How a strong answer sounds
Three costs. First, validation: every replica scans its SSTables for the range to build the tree, which is heavy disk I/O and competes with reads and compaction. Second, overstreaming: the tree has a bounded number of leaves, so on a big table each leaf covers many partitions; a one-row difference marks the whole leaf, and all of it is streamed, then has to be compacted on the receiving side, which creates more I/O. Third, false differences: replicas build their trees at slightly different moments, so in-flight writes look like mismatches. What I would change: repair in small token sub-ranges rather than whole ranges, so each tree's leaves cover few partitions; that is what tools like Reaper automate, scheduling segments one at a time and backing off when a node has pending compactions. Repair one replica set at a time, off-peak, with stream throughput throttled. Use incremental repair where it is reliable, so already-repaired SSTables aren't re-validated. Make sure hinted handoff and read repair are working, so there are fewer differences to find. And keep the whole cycle shorter than the tombstone grace period, because a replica that misses a delete and isn't repaired before the tombstone is purged will bring the deleted data back. I'd monitor the time since each range was last repaired as the key health metric.

🧠 Key takeaways

  • A hash tree: leaves hash ranges of data, each parent hashes its children, and the root commits to everything.
  • Equal roots mean equal data, for one comparison. Unequal roots are followed down only where hashes differ.
  • Finding a difference costs about 2 log2 L hashes. Building the tree costs a read of all the data.
  • The tree sees leaves and not rows, so leaf size sets how much is streamed for each difference.
  • Anti-entropy is the complete repair: it reaches data that hints and read repair never touch.
  • A sibling path proves one item is under a root. Git, certificate logs and blockchains rest on the same structure.

Why is anti-entropy needed when a system already has read repair and hinted handoff?

Hints cover known misses, and read repair covers what is read. A full comparison covers the rest.

In Git, what does a commit's hash commit to?

A commit names a tree and its parents by hash, and each of those names what is beneath it.
