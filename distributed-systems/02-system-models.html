System Models

"Is this protocol correct?" has no answer until you say correct under which assumptions. How long can a message take? Can a crashed node come back, and does it remember anything? Can a node lie? A system model is the precise list of those assumptions. It decides what is possible at all: the same problem can be easy in one model and provably unsolvable in another. This chapter introduces the timing and failure models that every protocol paper states, shows what each makes possible, and names the model that production systems like etcd, ZooKeeper and Kafka actually assume.

Timing models: how slow can things be?

A timing model says what bounds exist on message delays, processing time and clock drift.

  • Synchronous: every message arrives within a known bound Δ, every step takes a bounded time, and clocks drift at a bounded rate. A node that hasn't heard from a peer within the bound knows the peer has crashed. Very convenient; almost never true of real networks, where a congested switch or a GC pause can delay anything.
  • Asynchronous: no bounds at all. Messages arrive eventually, but "eventually" can be arbitrarily long. A silent peer might be dead or just slow, and no amount of waiting tells you which. Algorithms that work here work everywhere, but some problems become impossible.
  • Partially synchronous: bounds exist but are unknown, or hold only after some unknown global stabilisation time (GST). Dwork, Lynch and Stockmeyer introduced it in 1988. It models the real world well: the network usually behaves, sometimes doesn't for a while, and recovers.

Failure models: how do things break?

  • Crash-stop: a node works correctly until it halts, and never returns. Simple to reason about; unrealistic for servers that reboot.
  • Crash-recovery: a node can halt and later restart. It loses its memory but keeps whatever it wrote to stable storage (an fsync'd disk). Messages sent to it while down are lost. This is the model for real servers.
  • Omission: a node or link silently drops some messages but is otherwise correct. Networks do this all the time.
  • Byzantine: a node can do anything: send wrong or contradictory messages, to different peers, possibly on purpose. Covers bugs, corrupted memory and attackers (Chapter 33).

Links get their own model too. A fair-loss link may drop, delay, duplicate or reorder messages, but if you keep resending, a message eventually gets through. Adding retransmission and deduplication on top (which TCP does within one connection) gives a reliable link: every message sent between correct nodes is delivered exactly once.

The model real systems assume

Almost every production coordination system assumes partial synchrony with crash-recovery nodes and fair-loss links. That choice shapes their designs in three visible ways:

  • Majorities. With crash failures and no reliable failure detector, a protocol can only wait for a majority: any two majorities overlap in at least one node, which carries the information forward. That's why clusters have 3 or 5 nodes (P4).
  • Timeouts only for liveness. Timeouts are used to suspect a leader and start an election, never to decide what's safe. If the network misbehaves, the cluster may stall, but it won't diverge.
  • Durable state before acknowledging. Crash-recovery lets a node forget everything that wasn't on disk. Any promise the node made to others, such as a vote or an accepted log entry, must reach stable storage before the reply leaves, or the restarted node may contradict itself.
/** Crash-recovery model: make the vote durable BEFORE replying. */
void persistVote(long term, String votedFor) throws IOException {
	byte[] bytes = (term + "\n" + (votedFor == null ? "" : votedFor)).getBytes(UTF_8);
	Path tmp = dir.resolve("vote.tmp"), file = dir.resolve("vote");
	try (FileChannel ch = FileChannel.open(tmp, CREATE, WRITE, TRUNCATE_EXISTING)) {
		ch.write(ByteBuffer.wrap(bytes));
		ch.force(true);                                     // fsync the data
	}
	Files.move(tmp, file, ATOMIC_MOVE, REPLACE_EXISTING);     // all-or-nothing replace
	try (FileChannel d = FileChannel.open(dir, READ)) { d.force(true); }   // fsync the rename (Linux)
}

The last line matters on Linux: a rename is durable only once the directory itself is synced. It is easy to miss, and the OS course covers why (page cache and fsync). The cost is real, too: every vote and every log append waits for the disk, which is why consensus systems care so much about disk latency.

Use case: when reality leaves the model

In November 2020 Cloudflare's control plane had a multi-hour outage that their engineers titled "A Byzantine failure in the real world". A network switch failed partially: some nodes could talk to each other and others couldn't, in a pattern that didn't match any clean partition. Their etcd cluster, which assumes crash-recovery nodes and a network that either delivers or doesn't, kept electing new leaders as different nodes saw different views. The database cluster manager that depended on etcd then couldn't make reliable decisions, and failover of their PostgreSQL clusters stalled. No component was malicious; the failure simply sat outside the model the software was built for. Knowing your system's model tells you which failures it handles by design, and which ones you need monitoring and runbooks for.

⚠️
Common mistakes
  • Designing as if the network were synchronous, e.g. treating a timeout as proof that a node is dead and acting on it irreversibly.
  • Acknowledging before persisting in a crash-recovery system, so a restart forgets promises made to other nodes.
  • Using a crash-fault protocol where nodes can be compromised: Raft assumes nobody lies.
  • Forgetting omission and partial network failures: links that work in one direction only, or between some pairs of nodes.
  • Not fsyncing the directory after a rename, losing the "atomic" update after a power cut.
  • Never stating the model in a design document, so nobody can check whether a failure is handled.

Interview drill

Explain it simply: What is partial synchrony, and why do Raft and Paxos assume it rather than synchrony or asynchrony?

How a strong answer sounds
Partial synchrony means the network and nodes have timing bounds, but we don't know them, or they only hold after some unknown point; the system can be badly behaved for a while and then settle. Synchrony is unrealistic: real networks and GC pauses break any fixed bound. Pure asynchrony is too weak: FLP shows deterministic consensus is impossible there with even one crash. Under partial synchrony, Raft and Paxos are always safe, because they never use timing to decide correctness, and they make progress once the network behaves well enough for a leader to stay in contact with a majority.

Deeper: Why does crash-recovery force a consensus implementation to fsync before replying, and what does that cost?

How a strong answer sounds
In crash-recovery, a node may restart and lose everything not on stable storage. Votes and accepted log entries are promises other nodes rely on: a candidate counts the vote, a leader counts the acknowledgement towards a majority. If the node replies, crashes, and comes back without that state, it can vote twice in one term or lose an entry the leader already counted as committed, breaking safety. So the write must be durable, including an fsync and, for renames, a directory sync, before the reply. The cost is that every write's latency includes a disk flush, which is why etcd recommends fast SSDs and batches many entries into one fsync.

🧠 Key takeaways

  • A system model states timing assumptions and failure assumptions; correctness is always relative to one.
  • Synchronous: known bounds, perfect failure detection. Asynchronous: no bounds, slow and dead are indistinguishable. Partially synchronous: bounds hold eventually.
  • Failures: crash-stop, crash-recovery (with stable storage), omission, and Byzantine (arbitrary).
  • Consensus is impossible deterministically in pure asynchrony, and possible under partial synchrony with f < n/2 crash faults or f < n/3 Byzantine faults.
  • Production systems assume partial synchrony and crash-recovery: majorities, timeouts only for liveness, durable state before replies.
  • Real failures sometimes fall outside the model; know which ones and watch for them.

Check your understanding

In which timing model can a node be certain that a silent peer has crashed?

Only known bounds let silence prove a crash. In the other two models, a silent node might just be slow (or, under partial synchrony, the bound may not hold yet).

What does the crash-recovery model require of a node that replies "vote granted"?

Crash-recovery nodes lose memory on restart but keep what was fsync'd. Promises to other nodes must be durable before they are sent.

Under partial synchrony with crash failures, how many failed nodes can a 5-node consensus cluster tolerate?

Crash-tolerant consensus without a perfect failure detector needs f < n/2. With n = 5, f = 2.

How do Raft and Paxos stay safe even though their timeouts can be wrong?

A wrong timeout can cause an unnecessary election and a pause, never two conflicting committed values.

Which failure model allows a node to send different, contradictory messages to different peers?

Byzantine nodes can behave arbitrarily, including equivocating. Tolerating f of them needs at least 3f + 1 nodes.
