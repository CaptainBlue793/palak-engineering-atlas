Distributed Logs: Kafka Internals

The replicated log has been at the centre of this course since Chapter 15: an ordered, append-only sequence of records that several machines agree on. Raft uses one internally, to keep a state machine's replicas in step. Apache Kafka takes the same structure and makes it the product. Applications append records to a log and other applications read from it, each at its own pace and from its own position, and the log keeps everything for days whether or not it has been read. That design carries a large share of the world's event data, and a single cluster may handle millions of records a second. This chapter is about how: how a topic is split so that it can exceed one machine, how each piece is replicated and what "committed" means, which settings decide whether an acknowledged record can be lost, how a group of consumers divides the work, and how the cluster keeps track of itself. Chapter 28 covered the delivery guarantees built on top, and Chapter 43 tells the story of the design.

Topics and partitions

A topic is a named stream of records: payments, page-views. A topic is divided into partitions, and the partition is the real unit of everything that follows. Each partition is one append-only log. A record appended to it gets the next offset, a number that never changes and is never reused. Readers ask for "partition 3 from offset 1,205,117" and receive records in offset order.

The producer chooses the partition. With a key, the default is a hash of the key modulo the number of partitions, so every record with the same key lands in the same partition, in the order sent. Without a key, records are spread evenly. Three consequences follow, and most Kafka design questions come back to them.

  • Order is per partition. All events for account 77 are in order, if the account number is the key. There is no order between partitions, and so none across a whole topic.
  • The partition count is the limit on parallelism. Within a group, one partition is read by one consumer, so a topic with 12 partitions supports at most 12 consumers working at once.
  • Changing the count remaps keys. It is hash-mod-N from Chapter 19: add partitions and existing keys move, and their order across the change is lost. So the count is chosen generously at the start.

On disk a partition is a directory of segment files, a gigabyte each by default, with a small index beside each mapping offsets to file positions. Only the newest segment is written, always at the end. Old segments are deleted whole when they pass the retention limit, seven days by default, or are compacted, which keeps the latest record for each key and discards the rest. Appending to the end of a file and reading it forwards are the two things disks and operating systems do fastest: the kernel's page cache holds recent data, and records go from cache to network socket without being copied through the broker's own memory. Together with batching and compressing records at the producer, that is where the throughput comes from. Nothing in the read path depends on whether a record has been consumed, and that is why a new consumer can start a week back and replay.

Replication and ISR

Each partition is stored on several brokers, the replication factor, usually three. One replica is the leader and takes every write. The others are followers, which fetch from the leader continually, exactly as a consumer would, and append what they receive.

Two positions are tracked for each partition. The log end offset is where a replica's own log ends. The high watermark is the offset up to which every in-sync replica has the data. Records below the high watermark are committed. Consumers are only ever shown committed records, so a consumer never reads something that a leader failure could take away.

"Every in-sync replica" is where Kafka differs from Raft. The leader maintains a list, the in-sync replica set or ISR, of the replicas that are keeping up, itself included. A follower that hasn't caught up to the end of the leader's log within replica.lag.time.max.ms, thirty seconds by default, is removed from the list. When it catches up it is put back. A record is committed when all current members of the ISR have it, and on a leader's failure the new leader is chosen from the ISR, any member of which is certain to have every committed record.

Majority quorum (Raft, Paxos)In-sync replica set (Kafka)

The bargain is fewer copies for the same tolerance, three replicas surviving two failures where Raft would need five, in exchange for depending on a separate consensus system to hold the membership. It has one sharp edge. The ISR can shrink all the way to the leader alone, at which point "all in-sync replicas have it" means "one machine has it".

acks and durability

Whether an acknowledged record can be lost depends on three settings, in three different places, and they only work together.

SettingWhereValuesWhat it decides
acksProducer0: don't wait. 1: the leader has written it. all: every in-sync replica has itWhat "acknowledged" means
min.insync.replicasTopicUsually 2 with three replicasThe smallest ISR at which an acks=all write is accepted. Below it the producer gets an error
unclean.leader.election.enableTopicfalse by defaultWhether a replica outside the ISR may become leader when no member of it is alive

With acks=1 the leader acknowledges as soon as it has the record. If it fails before a follower has fetched it, the new leader never had it, and the record is gone after the producer was told it was safe. With acks=all alone the edge above applies: if the ISR has shrunk to one, the write is acknowledged on one copy. min.insync.replicas=2 closes that, by refusing the write. The standard durable set-up is therefore a replication factor of 3, min.insync.replicas=2 and acks=all, which survives the loss of any one broker with no acknowledged record lost and no interruption to writes.

// The topic: three copies, at least two of them in sync for a write to be accepted.
admin.createTopics(List.of(new NewTopic("payments", 12, (short) 3).configs(Map.of(
		"min.insync.replicas", "2",
		"unclean.leader.election.enable", "false"))));

// The producer: wait for every in-sync replica, and let retries be safe (Chapter 28).
props.put("acks", "all");
props.put("enable.idempotence", "true");
props.put("delivery.timeout.ms", "120000");                     // keep retrying for two minutes before giving up
producer.send(new ProducerRecord<>("payments", accountId, json), (meta, err) -> {
	if (err != null) alertAndPark(accountId, json, err);        // NotEnoughReplicas after two minutes: not written
});

One more fact belongs here. By default a broker does not force each record to disk before acknowledging. It writes to the page cache and leaves flushing to the operating system. Kafka's durability comes from the record being on several machines, on the reasoning that they won't all lose power in the same second. A whole datacentre losing power at once is the case that reasoning doesn't cover.

Things to notice. Play Case 1 under each setting of acks. Three records are replicated, two more are produced, and the leader dies before any follower has fetched them. With acks=1 both had been acknowledged, the new leader doesn't have them, and they are lost. The other two settings make no difference to that. With acks=all the same two records had not yet been acknowledged when the leader died. The producer gets an error and sends them again, and nothing that was promised is missing.

Case 2 is the one that acks=all doesn't cover alone. The followers stop fetching and are dropped, so the in-sync set is the leader. With min.insync.replicas at 1, the next two records are acknowledged on that one machine, and then it dies. If unclean election is off, the partition goes offline: no reads, no writes, and no loss, since restarting broker 1 brings every record back. If it is on, broker 2 takes over and m3 and m4 are gone, though each was acknowledged under acks=all. Now set min.insync.replicas to 2 and play it again. The two records are refused when they are sent, and there is nothing to lose.

Then use the buttons freely with acks=all, a minimum of 2 and unclean election off. Stop one follower and writes continue. Stop two and they are refused. In a test of 150 random sequences of 40 actions under those settings, no acknowledged record was lost. The same test lost acknowledged records in 115 of the 150 runs with acks=1, in 88 with acks=all, a minimum of 1 and unclean election on, and in 44 with the minimum at 2 and unclean election still on. Each of those 44 was a case where two brokers had failed and a stale third was allowed to lead.

Consumer groups and rebalancing

Consumers that share a group.id form a consumer group, and Kafka divides the topic's partitions among them so that each partition has exactly one reader in the group. That gives parallelism, and keeps per-key order, since one key is one partition is one consumer. Two different groups each receive every record, which is how one topic feeds billing, analytics and search without their knowing of each other. Each group's position in each partition, its committed offset, is itself stored in a Kafka topic, __consumer_offsets.

One broker acts as the group's coordinator. Members send it heartbeats, and it changes the assignment when membership changes: a consumer joins, leaves, or stops heartbeating for session.timeout.ms. There is a second, less obvious trigger. A consumer that goes longer than max.poll.interval.ms, five minutes by default, between calls to poll is presumed stuck and removed, even though its heartbeat thread is alive. Redistributing partitions is called a rebalance.

Eager rebalanceCooperative rebalance
What happensEvery member gives up all its partitions, then all are reassignedOnly the partitions that must move are given up. The rest keep flowing
EffectThe whole group stops, for seconds to minutesA short pause on the moved partitions
Chosen byThe older assignorsCooperativeStickyAssignor, and the newer server-side protocol
 
props.put("group.id", "billing");
props.put("enable.auto.commit", "false");                          // commit after the work, not on a timer
props.put("partition.assignment.strategy", CooperativeStickyAssignor.class.getName());
props.put("group.instance.id", hostName);                        // static membership: a quick restart isn't a rebalance

consumer.subscribe(List.of("payments"), new ConsumerRebalanceListener() {
	public void onPartitionsRevoked(Collection<TopicPartition> lost) {
		consumer.commitSync(offsetsFor(lost));                 // last chance to record progress on these
	}
	public void onPartitionsAssigned(Collection<TopicPartition> gained) { }
});
while (running) {
	for (ConsumerRecord<String, String> r : consumer.poll(Duration.ofMillis(500))) handle(r);
	consumer.commitSync();                                     // at-least-once: handle() must be idempotent
}

Rebalances are the commonest source of trouble in consuming applications. A partition that changes hands is re-read from its last committed offset, so whatever the old owner had processed and not committed is processed again. And a group can fall into a loop: a batch takes longer than max.poll.interval.ms to handle, the consumer is removed, its partitions go to another member, which gets the same slow batch and is removed in turn. The remedies are smaller batches (max.poll.records), a longer interval, and moving slow work off the polling thread.

KRaft

Something has to hold the facts that the brokers themselves rely on: which topics exist, which broker leads each partition, who is in each ISR. That is the controller's job, and since the ISR mechanism is only as safe as the record of who is in it, this metadata must be kept by real consensus.

For its first decade Kafka kept it in ZooKeeper, a separate coordination service (Chapter 31), with one broker elected as controller to read and write it. That meant a second distributed system to run, and a slow failover: a new controller had to load the whole cluster's metadata from ZooKeeper before it could act, which on a cluster with hundreds of thousands of partitions took minutes during which no leader could be elected anywhere.

KRaft replaces this with a Raft implementation inside Kafka. A small group of nodes, three or five, form a controller quorum. The cluster's metadata is a log, replicated among them by Raft as in Chapters 17 and 18, and each change to the cluster is a record appended to it. Brokers follow that log too, as learners, so every broker holds the current metadata in memory, and a standby controller already has it all and takes over within seconds. KRaft was declared ready for production in Kafka 3.3 in 2022, and ZooKeeper support was removed in 4.0. So one Kafka cluster now runs two replication protocols on purpose: a majority quorum for the small, critical metadata, and the cheaper ISR scheme, which depends on it, for the data.

Use case: the Jepsen test that gave Kafka min.insync.replicas

In September 2013 Kyle Kingsbury published a test of Kafka 0.8, then in beta, in his Jepsen series, which subjects databases to network partitions and checks what they did against what they promised. The scenario he found is the panel's second case. A partition has three replicas. The network cuts the leader off from its two followers. The followers stop fetching, and after the lag timeout the leader removes them from the in-sync set, which now contains only itself. The leader is still reachable by clients and keeps accepting writes. Those writes were sent with the strongest setting available, acknowledgement from all in-sync replicas, and since the leader was the only one, each was acknowledged at once. Then the leader itself is cut off, or dies. No member of the in-sync set is left alive, and Kafka at the time did what kept the partition available: it elected one of the stale followers. Every record written since the followers fell behind was gone, although each had been acknowledged under the strongest guarantee on offer. In the published run a large share of the acknowledged writes were lost. The point of the analysis was that the ISR design lets the number of copies behind "committed" fall silently to one, and that a user had no way to forbid it. Kafka's developers had been frank that this was a known trade-off for availability, and the outcome was two settings. min.insync.replicas, added in version 0.8.2, lets a topic refuse writes when the in-sync set is too small, turning silent loss into a visible error. unclean.leader.election.enable lets a topic refuse to elect a stale replica, choosing to be unavailable instead, and from version 0.11 its default is off. Both are in the panel, and the test is why every guide to running Kafka gives the same three settings together.

⚠️
Common mistakes
  • acks=all with min.insync.replicas left at 1. "All" can mean one broker.
  • Setting min.insync.replicas equal to the replication factor. One broker restart then stops all writes.
  • Expecting order across a topic. Order exists within a partition only. Key by the thing whose order matters.
  • Too few partitions, then adding more. Keys move to different partitions, and per-key order breaks across the change.
  • Slow work inside the poll loop. The consumer is removed for being idle, and the group rebalances in a loop.
  • Turning on unclean leader election to "improve availability". It trades acknowledged data for uptime.
  • Treating Kafka as a queue where a message is removed when read. Nothing is removed by reading. Retention removes it.

Interview drill

Explain it simply: How does Kafka store and replicate data?

How a strong answer sounds
Data is organised into topics, and each topic is split into partitions. A partition is an append-only log on disk: producers append records to the end, each record gets a sequential offset, and consumers read forward from an offset they track themselves. Records with the same key go to the same partition, so ordering is guaranteed within a partition but not across the topic. Partitions are what let a topic scale past one machine and let consumers work in parallel. Each partition is replicated to several brokers. One replica is the leader and handles all writes; followers fetch from it. The leader tracks the in-sync replica set, the followers that are fully caught up. A record is committed once all in-sync replicas have it, and the high watermark marks that point; consumers only see committed records. If the leader fails, a new one is elected from the in-sync set, so no committed record is lost. Producers choose their durability with acks: zero for none, one for the leader only, or all for every in-sync replica, and min.insync.replicas sets the fewest replicas that "all" may mean.

Deeper: You must not lose a single acknowledged payment event. How do you configure Kafka, and what can still go wrong?

How a strong answer sounds
Topic: replication factor 3 across three racks or zones, min.insync.replicas 2, unclean leader election disabled. Producer: acks=all, idempotence enabled so retries don't duplicate or reorder, a generous delivery timeout, and the send callback checked, with failed records parked somewhere durable rather than dropped. That means a record is acknowledged only when at least two brokers have it, one broker can fail without losing anything or blocking writes, and a stale replica can never be elected. If two brokers are down, writes are rejected with NotEnoughReplicas, which is the correct behaviour: unavailable, not lossy. What can still go wrong. Kafka acknowledges after writing to the page cache, not after fsync, so a correlated power loss across all in-sync replicas could lose data; spreading replicas across zones addresses it, or forcing flushes at a large throughput cost. The producer side: if the application crashes before send completes, or ignores the callback, the event was never in Kafka, so the producing service needs a transactional outbox. The consumer side: committing offsets before processing loses events on a crash, so commit after, and make processing idempotent. Retention: an event not consumed within the retention period is deleted, so lag must be monitored. And operator error, deleting a topic or shrinking retention, which no replication setting prevents; for payments I would also mirror to a second cluster or archive to object storage.

🧠 Key takeaways

  • A topic is a set of partitions. A partition is an append-only log with permanent offsets, and the unit of order, parallelism and replication.
  • Each partition has a leader and followers. The in-sync replica set is the followers that are caught up.
  • A record is committed when every in-sync replica has it. The high watermark marks that point, and consumers read only below it.
  • Durability needs three settings together: acks=all, min.insync.replicas=2, and unclean election off.
  • A consumer group gives each partition one reader. Rebalances move partitions and cause reprocessing.
  • The controller holds cluster metadata. KRaft keeps it in a Raft log inside Kafka, where ZooKeeper once did.

What ordering does Kafka guarantee?

Order is per partition. Records with the same key share a partition, so per-key order follows.

A producer uses acks=1. The leader writes the record, acknowledges, and crashes before any follower fetches it. What happens to the record?

With acks=1 "acknowledged" means one copy. The producer was told it was safe, and has no reason to resend.

Replication factor 3, acks=all, min.insync.replicas=2. Two followers fall out of the in-sync set. What happens to a new write?

The in-sync set has one member, below the minimum. Refusing is what stops "all" from meaning one copy.

Why can a consumer only read up to the high watermark?

Showing only committed records means a consumer never acts on something a failover could erase.

A consumer takes six minutes to process one batch, with max.poll.interval.ms at five minutes. What happens?

Heartbeats show the process is alive. The poll interval shows it is making progress. Failing either causes a rebalance.
