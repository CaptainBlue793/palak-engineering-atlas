Coordination Services: ZooKeeper & etcd

Most distributed systems contain a few small questions on which everyone must agree. Which node is the leader at present? Which nodes are alive? Who may run the nightly job? What is the current configuration? Each is a few bytes of data, and each needs the full strength of consensus behind it, since two nodes that disagree about who leads is the split brain of Chapter 13. Implementing Paxos or Raft inside every application that has such a question would be a poor use of anyone's time, and a rich source of bugs. So the industry settled on doing it once: a small, separate service, replicated across three or five machines by a consensus protocol, that stores tiny pieces of data with strong guarantees and offers a few building blocks on top. Google's Chubby was the first to be described, in 2006. ZooKeeper followed from Yahoo, and etcd from CoreOS, and one or the other now sits beneath Kafka, HBase, Kubernetes and a great many systems that never mention it. This chapter covers what such a service stores, the three ideas it adds to a key–value store, the recipes built from them, and why it should be used sparingly.

What they store

Both are small databases, held in memory and logged to disk on every node, in which every write passes through a consensus protocol: ZooKeeper's own, called Zab, or Raft in etcd. A write is acknowledged once a majority has it, so the service survives the loss of a minority of its nodes and never returns two different answers about the same write. The data is meant to be small: configuration, names, pointers, a few kilobytes per entry and at most a few gigabytes in all.

A consistent key–value store alone would not be worth a chapter. What makes these services useful for coordination is three additions, each of which turns up in both: a write that succeeds only if nobody else got there first, a way to be told when something changes, and data that exists only while its owner is alive.

The first is the smallest and the most important. "Create this key, failing if it exists" is an election in one call: many clients try, the service orders the attempts through its log, and exactly one succeeds. Everything else in this chapter is a refinement of that.

Watches

A client that needs to know when the leader changes could ask every second. That is slow to notice and wasteful with ten thousand clients. A watch reverses it: the client reads a value and asks, in the same call, to be told when it next changes. The service keeps the request and pushes a notification.

The two services differ here, in a way that shapes how clients are written.

  • ZooKeeper's classic watch fires once. It says "this znode changed" and no more: not the new value, and nothing about any later change. The client reads again and, in the same call, sets a new watch. Changes between the notification and the re-read are folded together, so the client always ends with the latest state and isn't told of every state in between. That suits "who is the leader now" exactly, and doesn't suit keeping a full history.
  • etcd's watch is a stream. The client names a revision and receives every change after it, in order, each with its new value. If the connection breaks it resumes from the last revision it saw, and misses nothing, provided that revision hasn't been compacted away. Kubernetes is built on this, as Chapter 44 describes.

Both give one ordering promise that the recipes rely on: a client is told of a change before it can read the changed data. It never sees the new state and then hears that it is about to arrive.

Ephemeral nodes and leases

The third addition answers "who is alive?" without a separate failure detector. A ZooKeeper client holds a session with the service, kept open by heartbeats. A znode created as ephemeral belongs to that session. If the client exits, or crashes, or is cut off for longer than the session timeout, the service ends the session and deletes every ephemeral node it owned, through the consensus log like any other write, so all observers see the deletion at the same point in the order of events.

So the existence of a node means "its creator was alive within the last session timeout". A worker registers by creating /workers/worker-17 as ephemeral. The list of live workers is the list of children, and anyone watching the parent learns of a death without asking. etcd does the same with a lease: a client is granted one with a time to live, attaches keys to it, and renews it periodically. When renewals stop, the lease expires and its keys go.

The timeout is a choice between two errors, as in Chapter 5. Short, and a long garbage-collection pause is taken for a death. Long, and a real death goes unnoticed for that long while its lock is held by nobody. And one limit can't be tuned away: the service decides that a session has expired, on its own clock, and the client may not know. A client that was merely paused wakes up still believing that it holds whatever its ephemeral node stood for. The panel below produces this, and Chapter 32 is about what to do.

Lock and election recipes

A recipe is a known-good way of combining these parts. The lock and the leader election are the same recipe: the leader is whoever holds a lock that is never released voluntarily.

The obvious version. Every contender tries to create the same ephemeral node, /lock. One succeeds and holds the lock. The rest watch that node, and when it is deleted they all try again. It is correct, and it has the herd effect: with a thousand waiters, each release sends a thousand notifications and causes a thousand create attempts, of which 999 fail.

The standard version forms a queue. ZooKeeper can append an increasing number to a new node's name, a sequential node.

// The recipe written out, with the Curator client.
String me = zk.create().withMode(CreateMode.EPHEMERAL_SEQUENTIAL).forPath("/locks/report/n-");
while (true) {
	List<String> queue = sorted(zk.getChildren().forPath("/locks/report"));
	int i = queue.indexOf(nameOf(me));
	if (i == 0) break;                                          // lowest number: the lock is mine
	CountDownLatch gone = new CountDownLatch(1);
	Stat ahead = zk.checkExists()
			.usingWatcher((CuratorWatcher) event -> gone.countDown())
			.forPath("/locks/report/" + queue.get(i - 1));          // watch my predecessor only
	if (ahead != null) gone.await();                           // if it vanished already, go round again at once
}

// In practice, use the library's tested version, and listen for the connection being lost.
LeaderLatch latch = new LeaderLatch(zk, "/election/scheduler", myId);
latch.addListener(new LeaderLatchListener() {
	public void isLeader() { startScheduling(); }
	public void notLeader() { stopScheduling(); }
});
latch.start();
zk.getConnectionStateListenable().addListener((client, state) -> {
	if (state == ConnectionState.SUSPENDED || state == ConnectionState.LOST) stopScheduling();   // can't prove I still lead
});

The check-then-watch in the loop is safe only because of the ordering promise above and because checkExists sets the watch and reports existence in one step. etcd's version is the same idea in its own terms: each contender writes a key under a prefix, attached to its lease, the holder is the key with the lowest creation revision, and each waiter watches the key created just before its own.

The dashed box is what the service stores: the lock's children, lowest number first. A crashed or frozen client's node stays until its session times out, as it would in a real deployment. "Believes it holds the lock" is the client's own view, and it can differ from the service's.

Things to notice. Press the first preset under each setting. Five clients join, and A, the holder, releases. When every waiter watches the holder's node, the service sends four notifications. B takes the lock, and C, D and E wake, list the children, find they aren't first, and set new watches: three wake-ups of the four did nothing. When each watches only the node ahead of its own there is one notification, to B. Now crash C, in the middle of the queue, and let its session time out. Under the queue recipe D is told, since C's node was the one it watched. D looks again, finds B's node ahead of it, and watches that. The lock doesn't move.

Crash a holder and look at the gap that follows. The service still lists its node, and the lock belongs to a client that no longer exists, until you press "Session timeout passes". That wait is the session timeout, and every failover built this way pays it.

The second preset is the important one. A holds the lock and freezes. Its session expires, its node is deleted, and B is notified and takes the lock, all correctly. Then A unfreezes and carries on, since nothing has told it otherwise. The service says B holds the lock. A and B each believe they do. Both followed the recipe exactly and the service made no mistake. It happens under either watch setting. In a test of 8,000 random actions on each, an expired session was the only way a client ever came to be wrong about holding the lock.

When not to use them

A coordination service is consistent, and available as long as a majority of its nodes can talk. The price is that every write is a consensus round forced to disk on several machines, and the whole dataset is kept in memory. That fits its purpose and little else.

  • Not a database. etcd's default storage limit is 2 GB, and ZooKeeper holds its entire tree in each server's heap. Application data belongs elsewhere, with a pointer to it here if needed.
  • Not for frequent writes. Thousands of writes a second is the ceiling, shared by everything that uses the service. Counters, metrics, per-request state and heartbeats written as data will exhaust it.
  • Not a queue. Queues built on znodes were once a published recipe. They degrade badly with length, since listing the children of one node returns all of them.
  • Not on the request path. If serving a user requires a call to the coordination service, its latency is in every request and its outage is yours. Read configuration and membership into memory, keep them current with a watch, and carry on with the last known copy when the service can't be reached.
  • Not as proof. A lock from one of these services tells a client that it was the holder when it last heard. It doesn't stop a paused client acting after its session has gone. Any resource the lock protects must check for itself, with a fencing token (Chapter 32).
  • Not shared carelessly. When many systems depend on one cluster, one misbehaving client can take all of them down together, as the use case shows.

Use case: Roblox, 73 hours, and one Consul cluster

On 28 October 2021 the game platform Roblox, with about fifty million daily players, went down and stayed down for 73 hours. The company's account of it is a study in what this chapter's last section means. Roblox ran its services on its own machines, scheduled by Nomad, with secrets from Vault and service discovery from Consul, HashiCorp's coordination service, which like etcd keeps a Raft-replicated key–value store with sessions, locks and health checks. Nomad and Vault kept their own state in Consul as well. So one Consul cluster was beneath everything: without it no service could find another, nothing could be scheduled and no secret could be read. That afternoon the cluster's leader began taking seconds to commit a write that normally took milliseconds. Two causes were eventually found. Some months earlier the team had turned on a newer Consul feature, streaming, a more efficient way of serving watches. Under Roblox's unusually heavy mix of reads and writes it concentrated contention on a single internal channel and blocked writes on the leader. Separately, the embedded store holding Consul's Raft log, BoltDB, kept a list of free pages in a way that became very slow to maintain once the log file had grown to several gigabytes with most of its pages free, so that each write to the log took far longer than it should. Finding either was slow for a reason worth remembering: Roblox's monitoring and dashboards located their own backends through Consul, so the tools for seeing the problem were casualties of it. Replacing the machines with faster ones and restoring from a snapshot each failed to help, since the cause was in the software's behaviour under that load. Once streaming was turned off and the cluster was stable, a further day went on bringing the site back gradually, since caches were empty and letting every player in at once would have overloaded it again. The changes Roblox listed afterwards are the advice above made concrete: split what had been one cluster into several by purpose, remove the monitoring system's dependence on the system it monitors, and make services able to keep running on what they already know when coordination is unavailable.

⚠️
Common mistakes
  • Every waiter watching the same node. One change wakes them all. Watch your predecessor.
  • Assuming a watch delivers every change. A one-shot watch tells you to look again. You see the latest state, not the history.
  • Acting as leader after the connection is suspended. You can no longer tell whether your session, and your node, still exist.
  • Treating a lock from the service as mutual exclusion on something else. A paused holder still acts. The protected resource must check a token.
  • Storing application data or writing per request. The service is small and every write is a consensus round.
  • An even number of servers, or spreading them over two sites. Four tolerate one failure, as three do, and the site with the minority stops.
  • Failing hard when the service is briefly unreachable. Serve from the last known state where that is safe.

Interview drill

Explain it simply: What is ZooKeeper, or etcd, and what is it used for?

How a strong answer sounds
It is a small, strongly consistent, highly available data store that other distributed systems use for coordination. It runs on three or five servers that replicate every write through a consensus protocol, Zab for ZooKeeper, Raft for etcd, so it keeps working if a minority fail and never gives conflicting answers. On top of a key–value store it adds three things. Conditional writes, such as create-if-absent or compare-and-set, so exactly one of several competing clients wins. Watches, so clients are notified of changes instead of polling. And data tied to a client's liveness: ephemeral nodes in ZooKeeper or keys attached to a lease in etcd, which disappear automatically when the client's session expires. With those you build leader election, distributed locks, group membership, service discovery and shared configuration. Kafka used ZooKeeper for controller election and metadata; Kubernetes stores all cluster state in etcd. It is for small amounts of critical metadata, not for application data or high write rates.

Deeper: Implement leader election with ZooKeeper. What can go wrong?

How a strong answer sounds
Each candidate creates an ephemeral sequential znode under an election path, getting a name with an increasing sequence number. Each then lists the children; the one with the lowest number is the leader. A candidate that isn't lowest sets a watch on the node immediately before its own, not on the leader's node, and waits. When that predecessor disappears, it re-lists: if it is now lowest, it leads; otherwise it watches its new predecessor. Because nodes are ephemeral, a leader that crashes or is partitioned loses its node when its session times out, and the next in line is notified. Watching only the predecessor avoids the herd effect, where every candidate is woken on every change. What can go wrong. First, detection delay: the old leader's node persists for the session timeout, so there is a window with no working leader; a short timeout shrinks it but causes false failovers on GC pauses. Second, and more serious, two leaders: if the leader's process is paused, by GC or a VM stall, longer than the session timeout, ZooKeeper expires the session and a new leader is elected, but the old one resumes still believing it is leader until it next hears from ZooKeeper. So leadership from ZooKeeper is not enough to guarantee mutual exclusion; the resources the leader writes to must reject stale leaders, using a fencing token such as the znode's creation zxid or an epoch number. Third, connection state: on a SUSPENDED event the client doesn't know whether its session will survive, so a careful leader stops acting until reconnected. Fourth, operational: the election path is on a shared cluster, so load from other users affects failover. I would use Curator's LeaderLatch or LeaderSelector rather than write it myself.

🧠 Key takeaways

  • A coordination service is a small, consensus-replicated store for the facts a cluster must agree on.
  • ZooKeeper offers a tree of versioned znodes. etcd offers a flat key space with one global revision and transactions.
  • Three additions do the work: conditional writes, watches, and data that lives only while its owner's session or lease does.
  • A one-shot watch means "look again". A revision-based watch stream delivers every change in order.
  • Lock and election: ephemeral sequential nodes, lowest wins, each waiter watching only its predecessor.
  • A client can outlive its session without knowing. The lock alone is not mutual exclusion.
  • Keep it small, off the request path, and not shared by everything.

Check your understanding

What happens to an ephemeral znode when the client that created it crashes?

The service can't tell a crash from silence, so it waits for the session timeout. Until then the node still exists.

In the lock recipe, why does each waiter watch the node just ahead of its own, and not the holder's?

Watching the holder causes the herd effect: every waiter wakes, re-reads, and all but one go back to waiting.

A ZooKeeper one-shot watch fires. What does the client know?

Further changes before the re-read aren't reported separately. The client ends up with the latest state.

A lock holder is frozen by a garbage-collection pause for longer than its session timeout. What is true when it wakes?

Expiry is decided by the service. Two clients can briefly both believe they hold the lock, which is why resources need fencing.

Which workload is a poor fit for ZooKeeper or etcd?

Every write is a consensus round and all data is held in memory. High-volume data belongs in a log or a database.
