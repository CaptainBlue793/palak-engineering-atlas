One code style, all the way through

Every listing in this course is Java written the same way, so the shape of the code becomes a memory aid instead of noise. Distributed code fails in ways local code never does, and these five rules are how the listings deal with it.

  • Every remote call has a deadline. No call waits forever, and the deadline is passed down to the next hop instead of being reset at each one.
  • Three outcomes, not two. A call can succeed, fail, or time out, and a timeout means unknown: the write may have happened.
  • Retries carry an idempotency key. The server remembers request IDs, so sending the same request twice changes state once.
  • Durations use System.nanoTime(). The wall clock can jump backwards; it is never used for timeouts, and never for ordering events.
  • Messages are immutable records. A node's state changes in one place, one message at a time, so a run can be replayed.
public record PutRequest(String requestId, String key, String value) {}

// Retry until the deadline. Safe only because the server dedups on requestId.
PutResult put(PutRequest req, Duration budget) throws InterruptedException {
	long deadline = System.nanoTime() + budget.toNanos();   // monotonic
	long backoffMs = 20;
	while (true) {
		long left = deadline - System.nanoTime();
		if (left <= 0) return PutResult.unknown();   // may or may not have applied
		try {
			return client.put(req, Duration.ofNanos(left));
		} catch (UnavailableException e) {
			Thread.sleep(ThreadLocalRandom.current().nextLong(backoffMs + 1)); // full jitter
			backoffMs = Math.min(backoffMs * 2, 1_000);
		}
	}
}

A deadline, jittered backoff, and an honest "unknown" at the end. Chapter 4 builds this up one line at a time, and shows the outage you get without each line.
