Leases, Locks & Fencing Tokens

A lock inside one program is simple and absolute. While a thread holds a mutex, no other thread is in the critical section, and if the holder dies the whole process dies with it. A lock between machines keeps the name and loses both properties. The holder can crash while holding it, and then nobody can ever enter again, so every practical distributed lock comes with an expiry: it is a lease. And once a lock can expire, the holder can outlive it. The last chapter ended with that picture: a client frozen for a few seconds, its lease gone, another client holding the lock, and the first one waking up with no knowledge of any of it and carrying on. No lock service can prevent this, however well built, since the problem is in the client and not in the service. This chapter covers why, and the one technique that makes it harmless: have the thing being protected check for itself, using a number called a fencing token.

Leases

A lease is a lock with a time limit, granted by a service to a holder: "this is yours for the next ten seconds". The holder may renew it before it runs out. If the holder crashes or is cut off, renewals stop, the time passes, and the service is free to grant the lease to someone else. No failure detector is involved and no one has to decide that the old holder is dead. Time decides. The idea was set out by Cary Gray and David Cheriton in 1989 for file caches, and it is now everywhere: a ZooKeeper session, an etcd lease, a leader's term of office in Chapter 13, an IP address from DHCP.

A lease replaces "is the holder alive?", which can't be answered, with "has the time run out?", which can, at the price of a new assumption. Grantor and holder each measure the ten seconds on their own clock. They needn't agree on the time of day. They do need their clocks to run at nearly the same rate, and each must lean the safe way:

  • The holder is pessimistic. It starts counting from the moment it sent the request, not when the reply arrived, and it stops using the lease a margin early.
  • The grantor is patient. It waits the full term, and a margin more, before granting to anyone else.
  • Both use a monotonic clock (P5). A wall clock stepped forward by NTP would expire a lease early on one side.

With bounded clock drift and those margins, the two views never overlap: the holder believes its lease has ended before the grantor does. That is the theory, and it holds until the holder stops running.

The GC-pause problem

Code that uses a lease looks like this, in any language.

if (lease.isStillValid()) {          // 1. check: nine seconds left
	                                    // ← the process stops here for fifteen seconds
	storage.write(key, newValue);      // 2. act: believing it holds the lease
}

Between the check and the write, the thread can be stopped for an arbitrary length of time, and it will not know. When it resumes, the next instruction runs as though nothing happened. The causes are ordinary:

  • A stop-the-world garbage collection. Modern collectors pause for milliseconds. Older ones on large heaps paused for many seconds, and a badly tuned one still can.
  • The machine itself is paused. A virtual machine is frozen for live migration, or its hypervisor gives the CPU to another tenant.
  • The operating system. The process is swapped out, blocked on a slow disk, or stopped by a signal.
  • The network. The process runs on time and its write request sits in a queue or a retransmission, arriving seconds after it was sent.

The last one shows that no amount of care inside the client is enough. Even a client that checks its lease on the very line before the write, and is never paused, has only shown that the lease was valid when the request left. Checking and acting are two moments, and time passes between them. A check in the client narrows the window and can't close it.

Fencing tokens

The remedy moves the check to the only place where it can be atomic with the write: the resource being written. The lock service hands out, with every grant, a number that is larger than any it has handed out before. That number is the fencing token. The client sends its token with every write. The resource remembers the highest token it has seen and refuses anything lower.

The lock is now advisory, a way of making conflict rare, and the token is what makes it safe. Three points on doing it properly.

  • The token must come from the lock service and only go up. Services built on consensus have a suitable number already: ZooKeeper's transaction ID or a node's version, etcd's revision, a Raft term, an epoch in Kafka (Chapter 28 met one as the producer epoch). A random value identifies a holder, and can't say which of two holders is the later.
  • The resource must check and write in one atomic step. A conditional update in a database, a compare-and-set in a store, or a service that serialises its writes. A resource that can't compare a number can't be fenced, which rules out many third-party APIs.
  • A new holder should write early. The resource refuses tokens lower than the highest it has seen. Until the new holder's first write arrives, a straggler from the old one still gets in.

It catches one of the four: the pause that ends before the check, when the client looks at its clock and sees that the lease has gone. It misses a pause after the check. It misses a slow clock, on which 12.5 real seconds read as 6.3. And it misses a request sent in good time and held up for 14 seconds on the way, a case in which the client did nothing wrong at all. The token check stops all four, whether or not the client checks. Over the four faults the stored data is corrupted four times with no defence, three times with the client's check alone, and never with fencing.

    Two kinds of lock

    Before choosing a lock, ask what happens if two clients hold it at once for a moment. There are only two answers.

    A lock for efficiencyA lock for correctness
    It exists toAvoid doing the same work twiceStop two writers damaging shared state
    If it fails brieflySome wasted work: a report generated twice, an email sent twiceCorrupt data, money moved twice, an inconsistency that stays
    Examples"Only one node should run the nightly export""Only one node may write this file", "one leader per shard"
    EnoughAny lock with an expiry. One Redis server is fineA lock from a consensus service, and a fencing token checked by the resource
    FencingNot neededRequired. Without it the lock is an efficiency lock, whatever it is built on

    Most locks in practice are for efficiency, and are better kept simple. The mistakes happen when a lock that is good enough for the first purpose is trusted with the second.

    The Redlock debate

    The plainest distributed lock is one command against a single Redis server: SET resource <random-value> NX PX 30000, which sets the key only if it doesn't exist, with a thirty-second expiry. Release is a small script that deletes the key only if it still holds the caller's random value, so a client can't release a lock that has since passed to another. It is an efficiency lock, and its weak point is plain: if that Redis server fails, and a replica that hadn't yet received the key is promoted, the lock is granted twice.

    Redlock, proposed by Redis's author Salvatore Sanfilippo, aims to remove that weak point without a consensus system. Run five independent Redis servers. To acquire, a client notes the time, tries the same SET NX PX on all five in turn with a short timeout on each, and notes the time again. It holds the lock if it succeeded on at least three and the whole attempt took well under the expiry time. Its lease is then the expiry less the time taken, less an allowance for clock drift.

    In 2016 Martin Kleppmann published a critique, Sanfilippo replied, and the exchange is still the clearest treatment of what a lock can promise. The two main objections were these.

    • There is no fencing token. Redlock's random value isn't ordered, so nothing lets a resource reject a holder whose lease expired during a pause. That is this chapter's panel, and it applies to Redlock exactly as to a single server.
    • Its safety rests on timing. The algorithm is correct if clocks on the five servers advance at about the same rate, and pauses and network delays are short compared with the lease. If one server's clock jumps forward, its copy of the key expires early, and a second client can then gather three servers while the first still holds its lease. Consensus protocols such as Raft are built so that bad timing costs availability and never safety (Chapter 2). Redlock can lose safety.

    Sanfilippo's reply made points that also stand. Clock jumps can largely be prevented by operating the servers properly and using monotonic clocks. And a resource able to check fencing tokens atomically is already a store with conditional writes, in which case one might ask what the lock is adding. The practical conclusion, on which both sides more or less agree, is the table above. For an efficiency lock, a single Redis server does the job and five add complexity for little gain. For a correctness lock, use a system built on consensus, and fence. Redlock sits between the two: more machinery than the first needs, and weaker guarantees than the second requires.

    Lock built onSurvives the lock server failingSafety depends on timingGives an ordered token
    One Redis server, SET NX PXNo. A failover can grant it twiceYesNo
    Redlock, five Redis serversYes, up to twoYes: clock rates and pausesNo
    ZooKeeper or etcdYes, a minorityOnly the holder's own view of its leaseYes: transaction ID or revision
    A row in the database being protectedIt is the same systemNo: the lock and the data commit togetherNot needed

    The last row is often the right answer and often overlooked. If the thing being protected lives in one database, a transaction there, a SELECT … FOR UPDATE or a conditional update (Databases, Locks), needs no lease, no clock and no token, since holding the lock and making the change are one atomic act.

    Safe locking in Java

    Four habits, in code.

    // 1. A lease is timed on the monotonic clock, from before the request was sent, with a margin.
record Lease(long token, long deadlineNanos) {
	static Lease acquire(LockClient locks, String name, Duration ttl) {
		long sentAt = System.nanoTime();                         // not currentTimeMillis: that clock can jump
		long token = locks.acquire(name, ttl);                   // the service returns an increasing number
		return new Lease(token, sentAt + ttl.toNanos() - MARGIN_NANOS);
	}
	boolean looksValid() { return System.nanoTime() < deadlineNanos; }   // a hint to stop early, never a proof
}

// 2. The resource checks the token in the same statement as the write.
void save(Lease lease, long id, String payload) {
	int rows = jdbc.update("""
			UPDATE report_state SET payload = ?, fence = ?
			WHERE id = ? AND fence <= ?""", payload, lease.token(), id, lease.token());
	if (rows == 0) throw new LockLostException(lease.token());      // a newer holder has written: stop everything
}

// 3. If the data lives in the lock service's own store, check the lock in the transaction that writes.
kv.txn()
	.If(new Cmp(lockKey, Cmp.Op.EQUAL, CmpTarget.createRevision(myLockRevision)))   // my lock key still exists, unchanged
	.Then(Op.put(dataKey, value, PutOption.DEFAULT))
	.commit();

// 4. Do the work in short steps, and treat a refusal as the signal to stop.
for (Batch batch : work) {
	if (!lease.looksValid()) break;                              // polite: don't start what can't be finished
	save(lease, batch.id(), process(batch));                       // safe: the database has the last word
}

    Two further points. A background thread that renews the lease is useful and proves nothing, since a pause stops every thread in the process together, the renewer and the worker alike. And the work done under the lock should be idempotent (Chapter 4), since a holder that loses its lease part-way leaves the next one to start again.

    🧟
    Use case: HBase, and the server that didn't know it was dead

    HBase stores tables as regions, each served by one region server, and each region server writes its changes first to a log file in HDFS. A region must have exactly one server writing to it: this is a correctness lock. Every region server holds an ephemeral node in ZooKeeper, and the HBase master watches them. If a node disappears, the master takes that server for dead, replays its log, and assigns its regions to others. In HBase's early years this met the Java garbage collectors of the time. Region servers ran with heaps of many gigabytes, and a full collection on a fragmented heap could stop the whole process for tens of seconds, sometimes minutes, far longer than the ZooKeeper session timeout. The sequence that followed is the panel's. The server freezes mid-request. ZooKeeper expires its session, the master reassigns its regions, and other servers begin accepting writes for them. Then the collection ends, and the original server resumes exactly where it was, with clients' writes in hand and every reason to believe the regions are still its own. HBase's developers called it a Juliet pause, after the heroine who wakes to find that everyone has acted on the belief she was dead. Two defences were built, and both are fencing. When a revived server next contacts the master, it is answered with an exception named YouAreDeadException, and shuts itself down. That one depends on the stale server asking. The one that doesn't is in the storage. Before the master replays a dead server's log, it tells HDFS to recover the lease on that log file. HDFS allows one writer per file, and recovering the lease closes the file to its old writer. From that moment any append from the old region server is refused by HDFS itself, so it can't acknowledge a single further write, whatever it believes. HBase also attacked the pauses, with an allocator designed to stop the heap fragmenting, and later collectors made them rare. The fence stayed, since rare is not never.

    ⚠️
    Common mistakes
    • Trusting "I hold the lock" at the moment of writing. You held it when you last checked.
    • A lock without an expiry. One crashed holder blocks everyone for ever.
    • A lease shorter than the work. It expires mid-task in normal operation, with no failure at all.
    • A random value used as a fencing token. It can't be compared. The token must increase.
    • Releasing without checking ownership. A late release deletes the lock that now belongs to someone else.
    • Timing a lease with the wall clock. A clock adjustment shortens or lengthens it.
    • A correctness lock on a resource that can't check a token. There is then no safe design with a lock. Use a transaction or make the operation idempotent.
    🎤
    Interview drill

    Explain it simply: What is a fencing token, and what problem does it solve?

    How a strong answer sounds
    Distributed locks have to expire, otherwise a crashed holder would block everyone for ever. But that means a client can still be running after its lock has expired without knowing it. The classic case is a long garbage-collection pause: the client acquires the lock, pauses for longer than the lease, the lock is given to a second client, and then the first wakes up and writes to the shared resource, believing it still holds the lock. Now two clients are writing and data can be corrupted. A fencing token fixes this at the resource. Every time the lock service grants the lock, it also returns a number that increases with each grant. Clients include their token with every write. The resource remembers the highest token it has seen and rejects any write with a lower one. So when the paused client wakes and writes with token 33, the storage has already seen 34 from the new holder and refuses it. The lock service cannot prevent the stale client from trying; only the resource can stop it, because only there are the check and the write atomic.

    Deeper: Is Redlock safe to use? When would you use a Redis lock, and when not?

    How a strong answer sounds
    It depends what the lock is for. Redlock acquires a key with SET NX PX on a majority of five independent Redis nodes and considers the lock held if that completes quickly relative to the TTL. Kleppmann's critique had two parts. First, it provides no fencing token, only a random value, so it can't protect against a client that pauses, or whose request is delayed, beyond the lease; the stale client's write will be accepted. Second, its safety depends on timing assumptions: bounded clock drift between nodes, bounded process pauses and network delay. If a node's clock jumps forward, its key expires early and another client can obtain a majority while the first still thinks it holds the lock. Consensus algorithms avoid that by never depending on timing for safety. Antirez's response was that clock jumps are an operational problem that can be controlled, and that if the resource can check a token atomically you already have a linearizable store. My position: if the lock is for efficiency, avoiding duplicate work where an occasional double execution is tolerable, a single Redis instance with SET NX PX and a compare-and-delete release is perfectly good and simpler than Redlock. If the lock is for correctness, where two holders would corrupt data, I would not use Redis at all; I would use ZooKeeper or etcd, which give a monotonically increasing number such as the zxid or revision, and have the resource enforce it as a fencing token, or better, put the mutual exclusion in the database itself with a transaction or conditional write. And I would point out that even with ZooKeeper, without fencing the lock is still only an efficiency lock.

    🧠 Key takeaways

    • A distributed lock must expire, so it is a lease. A lease assumes clocks tick at similar rates, and each side leans the safe way.
    • A holder can act after its lease has gone: a pause, a slow clock, or a delayed request. It can't detect this itself.
    • Checking the lease before writing narrows the window. It can't close it, since check and write are two moments.
    • A fencing token is a number that rises with each grant. The resource refuses any write carrying a lower one than it has seen.
    • Decide whether a lock is for efficiency or correctness. The second needs consensus behind it and fencing in front of the resource.
    • Redlock has no ordered token and depends on timing: fine as an efficiency lock, where one Redis server would also do.
    • If the data is in one database, a transaction there is a better lock than any lock service.

    Check your understanding

    Why must a distributed lock have an expiry?

    An expiry lets time decide, where "is the holder dead?" can't be answered. It also creates the problem this chapter is about.

    A client checks that its lease has nine seconds left, then writes on the next line. Why isn't that safe?

    Check and act are two moments in the client. Only the resource can check and write in one step.

    Storage has accepted a write with token 34. A write arrives with token 33. What should it do?

    Tokens rise with each grant, so a lower one can only be from an earlier holder.

    What was the central objection to using Redlock for correctness?

    A paused holder isn't stopped, and a clock jump on one node can let two clients each gather a majority.

    A nightly export should run on only one of three nodes. Occasionally running it twice would waste a few minutes and do no harm. What is appropriate?

    It is a lock for efficiency. A brief double grant costs little, so the simplest lock that expires is the right tool.
