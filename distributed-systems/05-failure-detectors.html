Failure Detectors & Heartbeats

Almost every mechanism in this course starts with one node deciding that another has failed: a load balancer removes a backend, a Raft follower starts an election, a Cassandra node routes around a peer, a lock service revokes a lease. That decision is made by a failure detector, and it is always a guess, because a crashed node and a slow one look the same from outside (Chapter 2). This chapter builds detectors from heartbeats and timeouts, shows why fixed timeouts are hard to tune, implements the adaptive phi accrual detector used by Cassandra and Akka, and introduces SWIM's probing scheme for large clusters.

What a failure detector promises

Chandra and Toueg (1996) described failure detectors by two properties:

  • Completeness: every node that has crashed is eventually suspected. Missing this means waiting forever on a dead node.
  • Accuracy: nodes that are alive are not suspected. Missing this means false alarms: failovers, elections and data movement for nothing.

In an asynchronous network you can't have both perfectly: to be sure a node is dead you'd have to wait forever, and if you never wait forever you'll sometimes suspect a slow node. Every real detector picks a point on that trade-off, usually through one number: how long to wait. Fast detection means more false positives; fewer false positives means slower detection. The best you can promise, under partial synchrony, is a detector that is eventually accurate: it may make mistakes during bad periods, but it stops making them once the network settles, which is exactly what consensus protocols need.

Heartbeats and a fixed timeout

The simplest detector: each node sends a small heartbeat every interval (say 1 s), and a monitor suspects a node once no heartbeat has arrived for T. Choosing T is the whole problem. Set it just above the heartbeat interval and one late packet triggers a false alarm; set it to 30 s and a crashed leader stalls the cluster for 30 s. And the right value depends on the environment: a value that works in one data centre causes constant false alarms across regions, or during the occasional 2-second garbage-collection pause. TCP faced the same problem for retransmission and solved it adaptively, setting its timeout from a smoothed average of measured round-trip times plus four times their variation. The phi accrual detector applies the same idea to heartbeats.

Phi accrual: suspicion as a number

Hayashibara and colleagues (2004) proposed that a detector should output not "alive" or "dead" but a continuous suspicion level, φ (phi). The detector keeps a sliding window of recent heartbeat inter-arrival times and models them as a normal distribution. When the next heartbeat is late, it asks: if heartbeats really follow this distribution, how unlikely is it that we would still be waiting? φ is that probability on a logarithmic scale:

φ = −log10( P(a heartbeat arrives later than now) )

φ = 1 means about a 10% chance the node is fine; φ = 8 means about one chance in 108. Applications pick a threshold; Cassandra and Akka both default to 8. Because the distribution is learned, the same threshold adapts automatically: on a jittery network the spread is wider, so φ rises more slowly, and the detector waits longer before suspecting.

public final class PhiAccrualDetector {
	private final ArrayDeque<Double> intervalsMs = new ArrayDeque<>();
	private final int window;                     // e.g. the last 100 intervals
	private final double minStdMs;                 // floor, so a very regular sender doesn't make φ explode
	private long lastNanos = -1;

	public synchronized void heartbeat(long nowNanos) {
		if (lastNanos >= 0) {
			intervalsMs.addLast((nowNanos - lastNanos) / 1e6);
			if (intervalsMs.size() > window) intervalsMs.removeFirst();
		}
		lastNanos = nowNanos;
	}

	public synchronized double phi(long nowNanos) {
		if (intervalsMs.isEmpty()) return 0;
		double mean = intervalsMs.stream().mapToDouble(Double::doubleValue).average().orElse(0);
		double var = intervalsMs.stream().mapToDouble(x -> (x - mean) * (x - mean)).average().orElse(0);
		double std = Math.max(Math.sqrt(var), minStdMs);
		double sinceMs = (nowNanos - lastNanos) / 1e6;
		double y = (sinceMs - mean) / std;
		double e = Math.exp(-y * (1.5976 + 0.070566 * y * y));   // logistic approximation of the normal CDF
		return sinceMs > mean ? -Math.log10(e / (1 + e)) : -Math.log10(1 - 1 / (1 + e));
	}

	public boolean isAvailable(long nowNanos, double threshold) { return phi(nowNanos) < threshold; }
}

This is the formula Akka uses. Cassandra's implementation simplifies it by assuming exponentially distributed intervals, which makes φ grow linearly with the time since the last heartbeat, but the idea is the same. Compare the two kinds of detector on three kinds of network:

SWIM: probing at scale

All-to-all heartbeats don't scale: 1,000 nodes each heartbeating every other node is a million messages a second, and every node's view depends on every link. SWIM (Das, Gupta and Motivala, 2002) replaces them with random probing. Every protocol period, each node picks one random member and pings it. If no ack arrives in time, it doesn't conclude anything yet: it asks k other members to ping the target on its behalf (ping-req). Only if none of them gets through is the target marked suspect, and only if it stays suspect for a while, without refuting the suspicion, is it declared dead.

The cost per node is constant, one probe per period whatever the cluster size, and the expected time to detect a crash doesn't grow with the cluster either. The suspect state lets a slow node clear its name before it's removed: if it hears it is suspected, it broadcasts "I'm alive" with a higher incarnation number. How SWIM spreads these updates through the cluster by gossip is the subject of Chapter 23. HashiCorp's memberlist library, used by Consul, implements SWIM with extensions.

Make false positives cheap

Since mistakes are unavoidable, the design question is what a suspicion triggers. A load balancer that stops sending traffic to a slow backend loses little if it's wrong. A database that promotes a replica on suspicion risks two primaries (Chapter 13). Good systems separate the two: suspicion causes cheap, reversible actions (route around, stop sending new work), and expensive, irreversible actions (failover, re-replicating terabytes, evicting pods) wait longer or require stronger evidence such as a lease expiring. Kubernetes follows this pattern: a node that stops reporting is first marked NotReady and taints are added, and its pods are evicted only after a separate, longer toleration period.

👁️
Use case: Cassandra in the cloud

Cassandra uses phi accrual over gossip heartbeats, with phi_convict_threshold defaulting to 8. On early EC2 deployments, network jitter between availability zones was high enough that nodes were frequently marked down and up again ("flapping"), and every false conviction caused hints to be stored and requests to be rerouted. The common operational advice, repeated in vendor documentation, was to raise the threshold to around 12 in such environments: slower detection of real failures, in exchange for far fewer false ones. The panel's jittery setting shows why one threshold doesn't fit every network even with an adaptive detector.

⚠️
Common mistakes
  • Treating a suspicion as a fact and acting irreversibly on it, such as promoting a new primary without fencing the old one.
  • Timeouts barely above the heartbeat interval, so one delayed packet or GC pause triggers a false alarm.
  • Measuring heartbeat gaps with the wall clock (P5): one NTP step marks every peer dead.
  • Sending heartbeats from a thread that can be starved, so a busy but healthy node looks dead, or from a separate thread while the main work is stuck, so a hung node looks alive.
  • All-to-all heartbeats in large clusters, which cost O(n²) messages; use SWIM-style probing.
  • One threshold for every environment. Cross-region and noisy cloud networks need more tolerance than a single rack.

Interview drill

Explain it simply: Why can't a failure detector be both fast and always right?

How a strong answer sounds
Because from the outside, a crashed node and a slow node look identical: both are silent. The only way to tell them apart is to wait, and in a real network there's no upper bound on how long a slow node might take, because of GC pauses, congestion or overload. So any detector that answers in finite time will sometimes suspect a node that's actually alive, and making it wait longer to avoid that makes it slower to detect real crashes. You pick a point on that trade-off and design the system so that wrong suspicions are cheap.

Deeper: How does phi accrual improve on a fixed timeout, and how would you choose its threshold?

How a strong answer sounds
Instead of a fixed cutoff, it learns the distribution of heartbeat inter-arrival times over a sliding window and reports φ, minus log10 of the probability that a heartbeat would be this late if the node were healthy. On a steady network the distribution is narrow and φ rises quickly once a heartbeat is late; on a jittery one it's wide and φ rises slowly, so one threshold adapts to both. To choose the threshold, I'd look at the cost of a false positive versus slow detection for what the suspicion triggers: around 8 is a common default, higher for noisy cloud or cross-region links, and I'd validate it by replaying recorded heartbeat timings and counting false convictions and detection latency. I'd also set a minimum standard deviation and an acceptable pause, so a perfectly regular sender doesn't make φ explode on the first late heartbeat.

🧠 Key takeaways

  • A failure detector trades completeness (catching crashes) against accuracy (no false alarms); it can't be perfect.
  • Fixed timeouts are simple but hard to tune; every network and every GC pause needs a different value.
  • Phi accrual learns the heartbeat distribution and outputs a suspicion level; a threshold around 8 is common.
  • SWIM probes one random member per period and uses indirect probes and a suspect state to avoid false positives from bad links.
  • Measure intervals on the monotonic clock, and send heartbeats from where real work happens.
  • Make suspicion trigger cheap, reversible actions; save irreversible ones for stronger evidence.

Check your understanding

What does "completeness" mean for a failure detector?

Completeness is about catching real failures; accuracy is about not suspecting live nodes. No detector achieves both perfectly in an asynchronous network.

A phi accrual detector reports φ = 8 for a node. What does that mean?

φ is minus log10 of the probability that a heartbeat would arrive this late if the node were fine. Higher φ means stronger suspicion.

Why does SWIM send ping-req messages through other members before suspecting a node?

Indirect probes test other network paths. A target is suspected only if none of them reach it.

On a jittery cross-region network, a fixed 1.5 s timeout flags healthy nodes several times an hour. What does phi accrual do differently?

The detector models recent inter-arrival times. A wider distribution means a late heartbeat is less surprising, so suspicion grows more slowly.

What is a good response to a node being suspected by a failure detector?

Suspicions are sometimes wrong. Designing so that a false positive costs little is the main defence.
