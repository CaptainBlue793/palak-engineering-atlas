Serialization: JSON & Protobuf

Objects can't cross a network; bytes can. Every message between nodes, every entry in a replicated log and every record in Kafka is a Java object turned into bytes on one machine and back into an object on another, often by a different version of the code. This chapter covers how JSON and Protocol Buffers do that, what the bytes actually look like, and the rules that let a cluster run old and new versions side by side during a rolling upgrade without corrupting data.

Why not just send the object?

A Java object is a set of fields in one JVM's heap, full of references to other objects at addresses that mean nothing anywhere else. To send it, you serialize it into a self-contained sequence of bytes, and the receiver deserializes those bytes into its own objects. Four things decide whether a format is a good choice between services:

  • Size and speed: bytes on the wire and CPU spent encoding. It matters for a replication log that writes every entry several times.
  • Schema: whether the structure is written down and checked, or implied by whatever the sender happened to send.
  • Evolution: whether version 2 of a service can talk to version 1, in both directions.
  • Safety: whether decoding untrusted bytes can do anything except produce data.

The last point rules out Java's built-in Serializable between services. Deserializing a Java object stream can instantiate arbitrary classes on the classpath, and chains of ordinary library classes ("gadgets") have been used for remote code execution; the 2015 Apache Commons Collections exploits hit WebLogic, JBoss and Jenkins this way. It is also tied to Java and fragile across class changes. Use a data format, not an object-graph format.

JSON: readable, schemaless, verbose

JSON is the default for public APIs because anyone can read it and every language can parse it. Between your own services it has costs: field names are repeated in every message, numbers have no fixed type, and nothing checks the structure.

public record OrderJson(long id, String sku, int qty) {}

ObjectMapper json = new ObjectMapper()
	.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);   // see below

String text = json.writeValueAsString(new OrderJson(150, "A-17", 2));
// {"id":150,"sku":"A-17","qty":2}   → 31 bytes
OrderJson back = json.readValue(text, OrderJson.class);

Two JSON traps show up in distributed systems. First, Jackson's default is to fail on unknown properties, so the moment a new version of a service adds a field, every old reader starts throwing. Turning that off (as above) is what makes JSON forward compatible. Second, JSON numbers become IEEE doubles in JavaScript, which represent integers exactly only up to 253. 64-bit IDs from Snowflake-style generators exceed that, which is why Twitter's API returned every ID twice, as id and as the string id_str. Send large IDs as strings.

Protocol Buffers: a schema and compact bytes

Protobuf starts from a schema file. Each field has a type and, crucially, a field number; the number, not the name, is what goes on the wire.

syntax = "proto3";
package shop.v1;
option java_package = "com.example.shop.v1";
option java_multiple_files = true;

message Order {
  int64  id     = 1;
  string sku    = 2;
  int32  qty    = 3;
  string coupon = 4;      // added in v2
  reserved 5;              // was bool gift; never reuse the number
  reserved "gift";
}
Order order = Order.newBuilder().setId(150).setSku("A-17").setQty(2).build();   // immutable
byte[] bytes = order.toByteArray();                                       // 11 bytes
Order back = Order.parseFrom(bytes);

The encoding is a sequence of fields, each starting with a tag: the field number shifted left three bits, combined with a three-bit wire type that tells the parser how to find the end of the value. Wire type 0 is a varint: an integer in 7-bit groups, least significant first, with the top bit of each byte meaning "more bytes follow". Wire type 2 is length-delimited: a varint length, then that many bytes (strings, bytes, nested messages). So id = 150 becomes 08 96 01: tag 08 is field 1, wire type 0; then 150 is 0010110 + 0000001 in 7-bit groups, written as 96 01. Compatibility: two directions, both needed

In a cluster, you never upgrade every machine at once. During a rolling upgrade, v1 and v2 nodes run side by side for minutes or hours, and data written by either can sit in a log or a database for years. That needs both directions of compatibility:

  • Backward compatibility: new code can read data written by old code. Needed as soon as v2 reads anything v1 wrote, including old log entries.
  • Forward compatibility: old code can read data written by new code. Needed because a v1 node will receive messages from an already-upgraded v2 node, and because you may have to roll back.

Protobuf gives you both, if you follow its rules. An old reader skips a field number it doesn't know, using the wire type to find where it ends. And it keeps those bytes: since protobuf 3.5, unknown fields are preserved, so a v1 node that reads a v2 record, changes the quantity and writes it back doesn't silently delete the coupon.

The rules that keep this working are short, and every one of them comes from a real outage:

  • Never change a field's number. The number is the field's identity on the wire.
  • Never reuse a number or a name after deleting a field. Mark it reserved so the compiler refuses. Old data and old writers still use it.
  • Add fields with new numbers, and make sure code works when they are missing (the default value).
  • Don't change a field's type except between compatible types (for example int32 ↔ int64, which can truncate), and never between a number and a string.
  • Renaming is safe on the wire but breaks the JSON mapping and anything that reflects on names.

Avro takes the opposite approach to Protobuf: no field numbers on the wire at all, just values in schema order. A reader can decode the bytes only with the writer's schema, which is why Kafka deployments pair Avro with a schema registry and put a schema ID in front of every message.

Use case: the reused field number

A team removes int32 qty = 3 from Order because quantities moved to line items. Months later someone adds int32 discount_pct = 3; the number looked free. Nothing fails. But order records written before the change are still in the database and in a Kafka topic retained for 30 days, and a billing job replaying the topic now reads every old quantity as a discount: an order for 20 items gets 20% off. There is no error to alert on, because the bytes are perfectly valid. The one-line fix would have been reserved 3; when qty was deleted, which makes the compiler reject the reuse. ⚠️
Common mistakes
  • Java serialization between services: unsafe on untrusted input and brittle across versions.
  • Reusing a deleted field number. Old data is reinterpreted silently. Always reserve deleted numbers and names.
  • JSON readers that fail on unknown fields (Jackson's default), so every additive change breaks old nodes.
  • 64-bit IDs as JSON numbers, silently rounded by JavaScript clients past 253.
  • Assuming a missing field means "not set" in proto3. A zero, an empty string and an absent field look the same unless you use optional or a wrapper.
  • Upgrading readers and writers in the wrong order. Deploy code that can read a new field before any code writes it.

Interview drill

Explain it simply: What do backward and forward compatibility mean, and why does a rolling upgrade need both?

How a strong answer sounds
Backward compatibility means new code can read old data; forward compatibility means old code can read new data. During a rolling upgrade, some nodes run v1 and some v2 at the same time, so v2 nodes read messages and stored records from v1 (backward), and v1 nodes receive messages from v2 nodes (forward). If you need to roll back, v1 code also has to read anything v2 already wrote. Protobuf gets both by identifying fields by number, skipping unknown numbers, and preserving them when re-serializing.

Deeper: Why is reusing a Protobuf field number dangerous, when the build passes and no errors appear?

How a strong answer sounds
Because the field number is the field's identity on the wire. Old bytes, in databases, logs, caches or from not-yet-upgraded writers, still carry the old meaning under that number. If the new field has a compatible wire type, the parser accepts those bytes and assigns them to the new field, so data is silently misread: no exception, no failed request, just wrong values. If the wire type differs, the value lands in unknown fields and the new field reads as its default, which is also silent. The prevention is reserved for every deleted number and name, plus a schema-compatibility check in CI, such as buf breaking.

🧠 Key takeaways

  • Serialization turns objects into self-contained bytes; never use Java's object serialization between services.
  • JSON is readable and flexible but verbose; make readers ignore unknown fields and send big IDs as strings.
  • Protobuf writes a tag (field number and wire type) and then the value: varints for integers, a length prefix for strings and messages.
  • Rolling upgrades need backward and forward compatibility at the same time.
  • Never change or reuse field numbers; reserve deleted ones; add new fields with new numbers.
  • Old readers skip and preserve unknown fields, so data passes safely through code that doesn't understand it.

Check your understanding

In Protobuf, what identifies a field in the encoded bytes?

The tag is (field number << 3) | wire type. Names never appear on the wire, which is why renaming is safe and renumbering is not.

During a rolling upgrade, a v1 node receives a message from a v2 node that contains a new field. Which property makes this work?

Old reading new is forward compatibility. New reading old (v2 reading v1 data) is backward compatibility. A rolling upgrade needs both.

A team deletes int32 qty = 3, then later adds int32 discount_pct = 3. What happens when the new code reads old records?

Same number, same wire type: the bytes are valid, so they are assigned to the new field. Marking 3 as reserved would have prevented the reuse at compile time.

How is the integer 150 encoded as a Protobuf varint?

150 = 1·128 + 22. The first byte carries the low 7 bits (22 = 0x16) with the top bit set: 0x96. The second byte carries 1 without the top bit: 0x01.

Why do Kafka setups that use Avro usually run a schema registry?

Avro values are written in schema order with no tags. The message carries a schema ID; the reader fetches that writer schema and resolves it against its own by field name.
