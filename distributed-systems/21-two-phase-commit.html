Two-Phase Commit

Once data is partitioned (Chapter 20), an ordinary operation can touch two machines. A transfer debits an account on one shard and credits an account on another. An order reduces stock in one database and records a payment in a second. Each machine can commit its own part atomically, as any database can. What is needed is for the parts to stand or fall together: if either commits, both must, and if either can't, neither may. That is the atomic commit problem, and two-phase commit is the classic answer, in use since the 1970s. It is simple and it is correct, and it has one notorious property: if the wrong machine fails at the wrong moment, the others are left holding locks, unable to go forward or back, for as long as that machine stays down. This chapter covers the protocol, each way it can fail, and how modern systems keep the idea and remove the wait.

The problem

A transaction has done work at several nodes, the participants. Now it wants to commit. Atomic commit requires that every participant reaches the same outcome, commit or abort, that the outcome is commit only if every participant was able to commit, and that once a participant has decided, it never changes its mind.

This sounds like consensus, and it differs in the detail that causes all the trouble. In consensus, any proposed value may win, and a majority is enough to choose it, so a failed machine can be outvoted. In atomic commit every participant has a veto. A node that has run out of disk space, or found a constraint violated, must be able to force an abort. So the protocol needs an answer from every one of them, and a participant that can't be reached can't simply be ignored.

The protocol

One node acts as coordinator. It may be one of the participants or a separate service. The two phases are a vote and a decision.

A participant that votes YES is making a promise with two halves. It will commit if told to, whatever happens to it in the meantime, a crash included, which is why it writes "prepared" to disk before the vote leaves. And it will not decide for itself: having said yes, it can no longer abort on its own, since the others may be committing. Until it hears the outcome it is in doubt, and it keeps every lock the transaction holds.

// Coordinator
Outcome commit(TxnId id, List<Participant> participants) {
	log.force(new Begin(id, participants));
	boolean allYes = participants.parallelStream()
			.allMatch(p -> p.prepare(id, TIMEOUT) == Vote.YES);       // no answer in time counts as NO
	Outcome outcome = allYes ? Outcome.COMMIT : Outcome.ABORT;
	log.force(new Decision(id, outcome));                          // the commit point
	participants.forEach(p -> retryUntilAcknowledged(() -> p.finish(id, outcome)));
	log.append(new End(id));                                      // everyone knows: the record can be forgotten
	return outcome;
}

// Participant
Vote prepare(TxnId id) {
	if (!ableToCommit(id)) { rollback(id); return Vote.NO; }        // free to abort alone: no promise was made
	log.force(new Prepared(id, coordinator));                       // the promise must survive a crash
	return Vote.YES;                                               // locks stay held
}

void finish(TxnId id, Outcome outcome) {                          // may be called more than once: must be idempotent
	if (outcome == Outcome.COMMIT) commitLocally(id); else rollback(id);
	log.force(new Done(id, outcome));
	releaseLocks(id);
}

When the coordinator crashes after deciding and before telling anyone, the three participants are all prepared, all holding locks, and none of them knows the decision that is sitting on the coordinator's disk. They can ask each other, and each can only say "I voted yes too". They wait until the coordinator returns. In the last scenario one participant did hear before the crash, and that is enough: the others ask it, and finish.

Blocking

The panel's fifth scenario is the defect two-phase commit is known for. Between voting yes and learning the outcome, a participant is in doubt, and for that period its fate is in someone else's hands. If the coordinator is unreachable, the participant can't commit, since the decision may have been to abort. It can't abort, since the decision may have been to commit and another participant may already have acted on it. It can't release its locks, since either outcome needs them. A timeout doesn't help, since no amount of waiting tells it which.

Asking the other participants, called cooperative termination, resolves some cases. If any of them has already committed or aborted, that is the outcome. If any of them hasn't yet voted, it can refuse to, and everyone can abort. If all of them are prepared and none has heard, nothing can be concluded: the coordinator alone knows.

The cost is larger than the stuck transaction. Its locks block every other transaction that needs those rows, those block others, and in a busy database a single in-doubt transaction can stall a large share of the workload within seconds. The availability arithmetic is poor too. A transaction across five nodes needs all five and the coordinator to be working, so its availability is the product of theirs (P4), and its latency is that of the slowest.

Three-phase commit

The blocking arises from one state. A prepared participant is one message away from committing and one message away from aborting, and can't tell which. Three-phase commit puts an extra round between the vote and the commit. After every participant has voted yes, the coordinator first sends PRE-COMMIT, which says "everyone agreed, and I am about to commit", and waits for acknowledgements. Only then does it send COMMIT. Now a participant that times out can reason from its own state: if it never received PRE-COMMIT, no participant can have committed yet, so aborting is safe. If it did, everyone voted yes, so committing is safe.

The reasoning holds if a node that doesn't answer has certainly crashed. It fails in a real network, where silence may mean a partition (Chapter 2). Cut the participants into two groups after some have received PRE-COMMIT and some haven't, and one group times out and commits while the other times out and aborts. Three-phase commit removes blocking by assuming away the failure that matters most, and it costs a third round trip, so it is rarely used.

2PC over Paxos and Raft

Two-phase commit blocks since each piece of critical knowledge lives on one machine: the decision on the coordinator's disk, and each participant's promise on its own. The remedy that works is to keep the protocol and remove the single machines. Make each participant a consensus group, a few replicas kept identical by Raft or Paxos, as Chapters 15 to 18 described. "Prepared" then isn't a record on one disk. It is an entry in a replicated log, and if the group's leader dies, the new leader has it and carries on. Do the same for the coordinator's decision: record it as an entry in a replicated log, and any replica can answer the question "what happened to transaction 91?".

The protocol's messages are unchanged, and every failure in the table above now ends with "a new leader is elected, reads the log and continues", a pause of seconds where there was an outage of unknown length. Participants still hold locks while in doubt, and the doubt is brief. This is how Spanner and CockroachDB commit transactions that span ranges, and the Databases course follows one through in Distributed SQL. Jim Gray and Leslie Lamport showed in 2004 that the two ideas fit together exactly: ordinary two-phase commit is the special case of their combined protocol in which each group has a single member.

When the participants are independent services, with no shared protocol and no willingness to hold locks for each other, even this is the wrong tool. Chapter 22 covers what is used there.

Use case: the prepared transaction nobody finished

PostgreSQL implements the participant's half of two-phase commit, and its documentation carries an unusual warning about its own feature. An external coordinator runs PREPARE TRANSACTION 'order-8812' on each database involved, which is the vote: the transaction's state is written to disk, detached from the session that created it, and from then on it survives a restart of the server. Later the coordinator runs COMMIT PREPARED 'order-8812', or ROLLBACK PREPARED. In between, the transaction is in doubt in exactly this chapter's sense, and PostgreSQL shows what that means for one machine. Every row lock the transaction took is still held, so other sessions that touch those rows wait. Its snapshot is still open, so VACUUM can't remove dead rows newer than it, anywhere in the database, and tables bloat (Databases, MVCC). Neither effect ends when the client disconnects or the server restarts, since surviving both is the purpose of the feature. If the coordinator crashes and loses its own record, or the application has a bug, the prepared transaction stays indefinitely. For that reason the setting that permits the feature, max_prepared_transactions, defaults to zero, and the documentation advises leaving it there unless a transaction manager is in use that is known to resolve its transactions. Operators who do use it monitor the view pg_prepared_xacts for entries older than a few minutes. When one is found, a person has to decide by hand whether to commit it or roll it back, without knowing what the other databases did. The standard that coordinators and databases speak, XA, has a name for a participant resolving a transaction on its own in this way: a heuristic decision. When it differs from the coordinator's, the result is the inconsistency the protocol existed to prevent.

⚠️
Common mistakes
  • A participant voting yes before "prepared" is on disk. After a crash it has forgotten a promise the others are relying on.
  • A prepared participant aborting on a timeout. Another participant may already have committed.
  • A coordinator that keeps its decision in memory. If it crashes, nobody can ever find out what was decided.
  • Calling it "distributed consensus". Atomic commit needs every participant, where consensus needs a majority.
  • Two-phase commit across services owned by different teams. Each holds locks at the mercy of the others' uptime.
  • No monitoring of in-doubt transactions. One forgotten prepare can hold locks for days.

Interview drill

Explain it simply: How does two-phase commit work, and what is its main weakness?

How a strong answer sounds
It makes a transaction that spans several nodes commit on all of them or none. A coordinator runs two phases. In the prepare phase it asks every participant whether it can commit. A participant that can writes a durable "prepared" record, keeps its locks, and votes yes; one that can't votes no and rolls back. In the commit phase, if every vote was yes the coordinator durably records "commit", which is the point of no return, and tells everyone to commit; otherwise it records and sends "abort". Participants apply the outcome, release their locks and acknowledge. The weakness is blocking. Once a participant has voted yes, it can neither commit nor abort on its own: it must wait to hear the outcome. If the coordinator crashes after participants have voted and before they hear, they are stuck in doubt, holding locks, until the coordinator recovers, and those locks block other transactions. So a single machine failure can stall a large part of the system for an unbounded time. It also costs two round trips and several forced disk writes for each transaction, and needs every participant to be up.

Deeper: How do systems like Spanner run distributed transactions without suffering from 2PC's blocking?

How a strong answer sounds
They still use two-phase commit, but none of the parties is a single machine. Each participant is a replicated group, a Paxos or Raft group holding one range of the data, and the prepare record is written through that group's consensus log, so it survives the loss of any minority of its replicas. One participant group acts as coordinator, and its commit decision is likewise a replicated log entry. So the failures that block classic 2PC, the coordinator dying with the only copy of the decision, or a participant dying with the only copy of its promise, become leader failovers: a new leader is elected in seconds, finds the prepare or commit record in its log, and continues the protocol. Blocking isn't eliminated in theory, a group that loses its majority is stuck, but it is reduced to the availability of a quorum rather than of one node. The costs are that each phase is now a consensus round trip, so cross-range transactions are noticeably slower than single-range ones, which commit with one round and skip 2PC altogether; and participants still hold locks or write intents while prepared, so contention is still a concern. Systems reduce the latency with optimisations such as committing in parallel with the prepare when all participants are known, and they design schemas so that most transactions touch one range. Gray and Lamport's Paxos Commit paper is the formal version of this: 2PC is the special case with one acceptor.

🧠 Key takeaways

  • Atomic commit: all participants commit or all abort, and every one has a veto. That is why it needs an answer from each.
  • Two-phase commit: participants vote and promise, then the coordinator decides. Its forced log record is the commit point.
  • A yes vote is durable and binding. The participant can't decide alone afterwards, and keeps its locks.
  • Recovery is read off the log: no "prepared" means abort, "prepared" with no outcome means ask.
  • If the coordinator fails while participants are prepared, they block. Three-phase commit avoids that only by ruling out partitions.
  • Running each participant and the coordinator as a consensus group keeps 2PC and turns blocking into a short failover.

Check your understanding

At what moment is a two-phase commit transaction's outcome decided?

Before that record, a coordinator crash leads to abort. After it, recovery will always find "commit" and carry it out.

A participant restarts and finds a "prepared" record for a transaction, with no outcome. What must it do?

It promised to follow the decision, and doesn't know it. Guessing either way could contradict the others.

The coordinator crashes after all three participants have voted yes and before any has heard the outcome. They ask each other. What do they learn?

The decision exists only on the coordinator. If one of them had heard, or hadn't voted, they could finish.

Why is three-phase commit rarely used?

It trades blocking for possible inconsistency in a real network, and adds a round trip.

How does running each participant as a Raft group change two-phase commit?

The protocol is the same. What changes is that no promise or decision lives on a single disk.
