Stream Processing: Time & Watermarks

"How many people clicked this advert between 12:00 and 12:01?" is easy to answer the next day, from a file. A stream processor is asked to answer it at about 12:01, while the clicks are still arriving, and that raises a question a batch job never faces: when is the minute over? The clock on the wall says 12:01 at one moment. The data says otherwise. A phone in a tunnel reports its 12:00 clicks at 12:07. A server retries a failed upload at 12:03. A consumer that fell behind is reading 11:40's records now. If the processor counts each click when it happens to see it, the totals describe the delivery network and not the users. If it waits until every click for the minute has certainly arrived, it waits for ever, since nothing announces the last one. This chapter covers the working answer: reason in the time the events occurred, and carry through the pipeline a running estimate, the watermark, of how far that time has progressed. It is a guess, and the craft lies in choosing how to be wrong.

Event time vs processing time

Every event has two times. Event time is when it happened, recorded by the device or service that produced it and carried inside the event. Processing time is when a particular operator in the pipeline handles it, read from that machine's clock. The gap between them, the skew, is never zero and never constant. It is a few milliseconds for a healthy path, minutes for a device that was offline, and hours when a pipeline is restarted and works through a backlog.

The fifth row decides it for most pipelines. Sooner or later a job is restarted from an old offset, after a bug fix or a failure, and it then reads hours of history in minutes. With processing time, that entire backlog is counted as happening now. With event time, each record goes to the window it belonged to all along, and the corrected results match what a batch job over the same data would give.

Windows

A stream has no end, so an aggregate such as a count or an average is always taken over a window: a bounded slice.

WindowShapeAn event belongs toTypical use
TumblingFixed size, end to end: 12:00–12:01, 12:01–12:02Exactly oneCounts per minute, hourly billing totals
SlidingFixed size, starting more often than its length: five minutes, every minuteSeveral: size ÷ slideMoving averages, "errors in the last five minutes"
SessionPer key, as long as events keep coming, closed by a gap of inactivityOne, whose bounds aren't known in advanceA user's visit, a trip, a burst of activity

Windows are computed per key: clicks per advert, per minute. Each open window for each key is a piece of state held by the processor, a running count or a list of events, which exists from the window's first event until the window is closed and cleared. Session windows are the awkward kind, since a late event can arrive in the gap between two sessions and join them into one.

Watermarks

A watermark is a statement carried in the stream alongside the data: "event time has reached T. I don't expect any more events with a timestamp at or before T." When the watermark passes the end of a window, the operator treats the window as complete, emits its result and, unless told otherwise, discards its state.

Nothing can know T for certain, so a watermark is generated by a rule of thumb at the source. The usual one is bounded out-of-orderness: assume no event is more than some fixed delay behind the latest one seen. The watermark is then the highest timestamp seen so far, minus that delay. It only moves forward. The delay is the dial:

  • Too small, and the watermark runs ahead of the data. Windows close before all their events have arrived, and results are early and incomplete.
  • Too large, and the watermark trails. Results are complete and late, and every open window is held in memory for longer.

The "lowest of the inputs" rule has a well-known trap. If one input goes quiet, a partition with no traffic overnight, its watermark stops advancing, the minimum stops with it, and no window anywhere downstream ever fires. Sources therefore need a rule for marking an input idle and leaving it out of the minimum.

DataStream<Click> clicks = env.fromSource(kafkaSource,
		WatermarkStrategy.<Click>forBoundedOutOfOrderness(Duration.ofSeconds(5))   // the dial
				.withTimestampAssigner((click, ts) -> click.eventTimeMillis())  // event time, from the record
				.withIdleness(Duration.ofMinutes(1)),                          // a silent partition stops holding everyone back
		"clicks");

OutputTag<Click> tooLate = new OutputTag<>("too-late") {};

SingleOutputStreamOperator<PageCount> counts = clicks
		.keyBy(Click::page)
		.window(TumblingEventTimeWindows.of(Time.minutes(1)))
		.allowedLateness(Time.minutes(10))            // keep each window's state this long after it fires
		.sideOutputLateData(tooLate)                 // and send anything later than that here
		.aggregate(new CountAggregate(), new ToPageCount());

counts.getSideOutput(tooLate).sinkTo(lateArchive);    // never silently discarded

Late data

However the delay is set, some event will arrive after its window has fired. There are three things to do with it, and a pipeline usually combines them.

  • Drop it, and count how many. Acceptable for a dashboard. The count of dropped events is itself a metric to watch, and the events should go to a side output and not into the void.
  • Revise the result. Keep the window's state for an allowed lateness after it fires. A late event within that period updates the aggregate and the window fires again with a corrected figure. This moves the difficulty downstream: whatever receives the results must accept a second value for the same window and replace the first, an upsert keyed by window (Chapter 28), and must not add them together.
  • Correct it later in batch. Publish the stream's figures as provisional and recompute the day from the complete data overnight.

The same machinery runs in the other direction. A window can be made to fire before the watermark arrives, every few seconds say, giving early approximate results that are refined as data comes in. So a window may produce a series of results: early and speculative, then on time when the watermark passes, then late corrections. Google's Dataflow model, published in 2015 and the basis of Apache Beam, frames a pipeline as four questions: what is computed, where in event time (the windows), when in processing time results are emitted (the triggers), and how successive results for one window relate.

Change to event time, with the watermark trailing by 2 seconds. It fired at 23.1 s with a count of 23, and the phone's three events arrived at 31 s to find it closed. They are the red dots, dropped. Try to fix that with the watermark alone. At 5 seconds they are still dropped, and every result now waits 7.2 seconds. A watermark sized for the rarest straggler makes every result wait for it.

Put the watermark back to 2 seconds and set the allowed lateness to 30. The first results are as prompt as before, and the phone's dots turn amber: the window from 10 to 20 seconds is issued a second time, with 26. Every final figure is right. The price is each window's state held for half a minute longer, and a consumer that must accept corrections. Last, try a watermark delay of 0. Two windows are incomplete when first issued and five events are late, since an ordinary delay of a second or two now counts as lateness.

State and checkpoints

A windowed job is a stateful one. For every key and every window that hasn't been cleared, the operator holds an aggregate or a buffer of events, and a timer set for the moment the watermark should close it. The amount of state is roughly the number of active keys, times the number of windows open at once for each, times the size of one aggregate. Three settings from this chapter enter that product directly: the window's length, the watermark's delay, and the allowed lateness, which keeps every window alive for that much longer. A count per minute for a million adverts with ten minutes of allowed lateness is about eleven million counters. Keeping whole events where an incremental aggregate would do multiplies it by the event rate.

That state lives in the operator, on its heap or, when it is larger than memory, in an embedded store such as RocksDB on local disk (Databases, LSM trees). It is made safe against failure by the checkpoints of Chapter 27: barriers flow through the job, each operator saves its state to durable storage as the barrier passes, and after a crash every operator is restored and the sources rewind. The watermark is restored along with everything else, since each source's highest timestamp is part of its state. This is the reason event time and checkpoints fit together: on replay the events carry the same timestamps, go to the same windows and produce the same results, which could not be said if windows depended on the clock at the time of the rerun.

State that is never cleared grows until the job fails. Every piece of keyed state outside a window needs an expiry, a time-to-live, and a session window on a key that never falls silent never closes.

Use case: Google Zeitgeist, and the question a watermark answers

The idea of the watermark comes from MillWheel, a stream processor built at Google and described in a paper in 2013. Its worked example was Zeitgeist, the system that detected which search queries were suddenly rising or falling. The pipeline counted each query in one-second buckets and compared each bucket with a model of what was expected for that query at that time of day, flagging a spike when the count was far above the prediction and a dip when it was far below. The spike was the easy half. If a bucket's count already exceeds the prediction, more data arriving can only make it larger, so the alert can go out at once. The dip was the hard half, and it shows exactly what a watermark is for. A bucket with few queries in it has two possible explanations: people have stopped searching for that term, or the records for that second haven't arrived yet, held up somewhere between the search front ends and the pipeline. A count can't tell those apart. Reporting every thin bucket as a dip would raise an alarm whenever an upstream system was slow. The pipeline needed some way to know that a given second was finished. MillWheel's answer was the low watermark: a bound, computed by the system and passed from stage to stage, on the timestamp of the oldest record that might still be on its way. Zeitgeist declared a dip only for buckets the low watermark had passed. A delay upstream then held the watermark back, and with it the verdict, where before it would have produced a false alarm. The paper was frank that the watermark was a heuristic and that some data would arrive behind it. Its successors, the Dataflow model in 2015 and Apache Beam and Flink after it, kept the watermark and added the triggers and allowed lateness of this chapter to deal with what it misses.

⚠️
Common mistakes
  • Windowing on processing time for a question about the world. A backlog or a restart corrupts the figures with no error.
  • Treating the watermark as a guarantee. It is an estimate. Decide what happens to events behind it.
  • Dropping late data silently. Send it to a side output and count it.
  • Allowed lateness with a sink that appends. Each correction is added to the earlier result. Sinks must replace by window.
  • An idle partition with no idleness setting. The watermark stops, and every window waits for ever.
  • Trusting device clocks. An event stamped next year pushes the watermark past everything. Reject timestamps far in the future.
  • State with no expiry. Per-key state for keys that never return fills the disk.

Interview drill

Explain it simply: What is the difference between event time and processing time, and what is a watermark?

How a strong answer sounds
Event time is when something actually happened, a timestamp carried in the event. Processing time is when the stream processor sees it. They differ because of network delay, retries, offline devices and backlogs, and the difference varies from event to event, so events arrive out of order. If I want "clicks per minute", the minute should be the minute the click happened, so I window on event time; otherwise a delay or a replay moves events into the wrong windows. But with event time the processor needs to know when a window is complete, since events can arrive late. A watermark is the mechanism: it is a marker flowing with the data that says "I believe all events with timestamps up to T have now arrived". When the watermark passes the end of a window, the window fires and emits its result. Watermarks are heuristic, typically the maximum timestamp seen minus an allowed out-of-orderness, so they trade latency against completeness. Events that arrive after their window has fired are late, and can be dropped, sent to a side output, or used to update the result if the window is kept for an allowed-lateness period.

Deeper: Design a pipeline that counts advert clicks per minute for billing, with mobile clients that may be offline for hours.

How a strong answer sounds
Clicks go to Kafka keyed by advert ID, each carrying an event-time timestamp and a unique click ID generated on the device. A Flink job reads them with event-time semantics. First, deduplicate by click ID using keyed state with a TTL longer than the client retry horizon, because mobile clients retry. Then tumbling one-minute event-time windows per advert with an incremental count aggregate. Watermarks: bounded out-of-orderness of perhaps ten to thirty seconds, chosen from the observed delay distribution so that the great majority of events are on time, with idleness handling so a quiet partition doesn't stall progress. That gives a first result within about half a minute of the window closing. For late events, I set an allowed lateness of some hours; each late click re-fires its window with an updated count. The sink is an upsert keyed by advert and window start, so a later firing replaces the earlier figure rather than adding to it, and I run checkpoints with a transactional or idempotent sink for exactly-once results. Anything later than the allowed lateness goes to a side output, landed in storage. Because this is billing, the streaming numbers are provisional: a daily batch job recomputes from the raw click log, including the very-late data, and is the source of truth for invoices; the stream is for dashboards and pacing. I would also guard against bad device clocks by clamping or rejecting timestamps far in the future, since one such event would advance the watermark and make everything else late. State size is adverts times open windows, which the allowed lateness multiplies, so I would use RocksDB state with incremental checkpoints and monitor late-drop counts and watermark lag.

🧠 Key takeaways

  • Event time is when it happened, and processing time is when it was seen. Questions about the world need event time.
  • Event-time results are the same on replay. Processing-time results depend on when the job ran.
  • Windows bound an endless stream: tumbling, sliding, or sessions closed by a gap.
  • A watermark estimates that event time has reached T. It closes windows, and it is a trade between early and complete.
  • Late events are dropped and counted, used to revise the result, or picked up by a later batch. Revisions need a sink that replaces.
  • Open windows are state. Window length, watermark delay and allowed lateness all multiply it, and checkpoints protect it.

Check your understanding

A pipeline that windows on processing time is restarted and reads six hours of backlog in ten minutes. What happens to its per-minute counts?

Processing time assigns events by when they are seen. Event time would put each in the minute it happened.

What does a watermark with value T assert?

It is a statement about event time, and an estimate. Windows ending at or before T can fire.

The watermark's delay is raised from 2 seconds to 30. What changes?

The delay trades latency and memory for completeness. It doesn't change which window an event belongs to.

An operator reads from four partitions. One receives no events for an hour. With no idleness setting, what happens?

The minimum can't pass the silent input's last watermark. Marking it idle removes it from the minimum.

A window fires with a count of 40. Within its allowed lateness two more events arrive and it fires again with 42. What must the sink do?

A later firing is a corrected total, not an increment. The sink needs an upsert by key and window.
