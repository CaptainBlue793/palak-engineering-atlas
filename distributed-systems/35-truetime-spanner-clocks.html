TrueTime & Clock-Based Consistency

This course has said one thing about clocks since Chapter 6: don't trust them to order events. Two machines' clocks differ by an amount nobody knows, so a timestamp from one can't be compared with a timestamp from another, and the remedy was logical clocks, which count events and ignore the time of day. In 2012 Google described a database, Spanner, that goes back to physical time and orders transactions across continents by timestamp, correctly. Nothing in it contradicts Chapter 6. The clocks in Spanner are still wrong. The change is that each one knows how wrong it might be and says so: asked the time, it answers with a range, "somewhere between 12:00:00.003 and 12:00:00.011", that is guaranteed to contain the truth. Uncertainty that is known and bounded can be designed round, and the design is short enough to state in a sentence: after choosing a timestamp, wait until it is certainly in the past everywhere before telling anyone. This chapter covers that idea, what it guarantees, and how databases without Google's hardware get most of the benefit by a different route.

External consistency

A multi-version database gives every transaction a timestamp, keeps each row's versions labelled with the timestamp that wrote them, and lets a reader at timestamp s see exactly the versions at or below s (Databases, MVCC). Readers never block writers, and a read at one timestamp is a consistent picture of the whole database. On one machine a counter supplies the timestamps. Across many machines the property to preserve is this:

If transaction T1 has finished before transaction T2 begins, then T1's timestamp is lower than T2's.

Google called it external consistency: the order of timestamps agrees with the order a person outside the system would observe with a watch. It is linearizability (Chapter 11) for whole transactions, also called strict serializability. Without it a database can be perfectly serializable and still show this: a customer pays, sees "payment confirmed", refreshes the page, and is told there is no payment. The read began after the write finished, and was served by a machine whose clock was behind, so it was given a lower timestamp and looked into the past.

Plain machine clocks produce exactly that. If the node handling T1 runs 100 ms fast and the node handling T2 runs true, then a T2 that starts 50 ms after T1 finishes gets the lower timestamp. A single shared counter, a timestamp oracle, fixes it and puts a round trip to one place in front of every transaction on Earth.

Uncertainty intervals

Spanner's clock service, TrueTime, has an interface that differs from an ordinary clock in one respect.

interface TrueTime {
	Interval now();                         // guaranteed: earliest ≤ the true time ≤ latest
	default boolean after(long t)  { return now().earliest() > t; }   // t has definitely passed
	default boolean before(long t) { return now().latest() < t; }     // t has definitely not arrived
}
record Interval(long earliest, long latest) {}

The half-width of the interval is written ε. The guarantee is that the true time lies inside, on every machine, always. Two things keep ε small and honest.

  • Good references, of two kinds. Each datacentre has time masters, some with GPS receivers and some with atomic clocks. The two fail in unrelated ways, an aerial fault or interference on one side, slow drift on the other, so a fault in one kind is caught by disagreement with the other.
  • Assuming the worst between synchronisations. Every machine checks against several masters about every thirty seconds. Between checks its own quartz clock is assumed to drift at a pessimistic rate, and ε is widened continuously to cover it. So ε is a sawtooth: small just after a sync, growing until the next. As first published it ran from about 1 ms to 7 ms and averaged 4. Today it is under a millisecond.

The step from Chapter 6 is one of attitude. NTP gives a best guess and no promise. TrueTime gives a worse-looking answer, a range, with a promise attached, and a promise is something a protocol can be built on.

Commit wait

With such a clock, external consistency takes two rules.

  1. Choose the timestamp from the top of the interval. A committing transaction takes s = now().latest. Whatever the true time is, s is not before it.
  2. Wait it out. Before releasing its locks or replying to the client, the transaction waits until after(s) is true: until even the bottom of the interval has passed s.

The argument is three lines. When T1's client gets its reply, the true time is later than s₁, by rule 2. T2 begins after that, so the true time when T2 picks its timestamp is later still. T2 takes the top of an interval that contains the true time, so s₂ is at least the true time, and therefore greater than s₁. Nothing in it mentions which machines were involved or how far apart they are.

long commit(Transaction txn) throws Exception {
	long s = clock.now().latest();                       // rule 1
	Future<?> replicated = group.replicate(txn, s);       // consensus among the replicas starts at once
	while (!clock.after(s)) Thread.sleep(0, 100_000);     // rule 2: the commit wait runs alongside it
	replicated.get();
	return s;                                            // only now release locks and answer the client
}

The wait is about 2ε: the timestamp was up to ε ahead of the clock's reading, and the bottom of the interval is ε behind it. It overlaps with the replication round the transaction needs in any case, so when 2ε is shorter than that round trip, as it now is, the wait costs nothing extra. When it is longer, every write pays the difference. This is the reason for the hardware: money spent on clocks is latency removed from every transaction.

What the guarantee buys goes beyond the refreshed page. Any timestamp now names one consistent state of the entire database, the same on every replica in every region. A read-only transaction can pick a timestamp and be served by whichever replica is nearest, without locks and without talking to a leader, provided that replica has caught up to that timestamp. Backups, analytics and long reports run at a timestamp and never block a write. Chapter 41 follows these through the real system.

Try it: one write, then one read

T1 commits a write through node A at true time 1,000 ms. Replicating it takes 5 ms. One millisecond after T1's client is told "committed", T2 begins at node B and reads the same row. If T2 doesn't see T1's write, external consistency has failed. The clocks on A and B are wrong by the amounts you choose.

Hybrid logical clocks in CockroachDB

CockroachDB, YugabyteDB and others set out to offer Spanner's model on ordinary servers, synchronised by NTP, where the honest bound on clock error is hundreds of milliseconds. A commit wait of half a second on every write is out of the question. Their design keeps the bound and moves the waiting to the rare case where it matters.

Timestamps come from a hybrid logical clock (Chapter 8): wall-clock time, with a counter to keep it moving forwards and to carry causality between nodes that exchange messages. The cluster is configured with a maximum clock offset, 500 ms by default in CockroachDB, which every pair of nodes is assumed to stay within. A write commits at its node's current timestamp, with no wait.

The care is taken on the read side. A transaction reading at timestamp s treats the stretch from s to s + the maximum offset as its uncertainty interval. A version stamped at or below s is visible, as usual. A version stamped above the interval was certainly written after this transaction began, and is ignored. A version stamped inside the interval is the problem case: its writer's clock may have been ahead, and it may have committed before this transaction started. The reader can't tell. So it does the safe thing, and restarts with its timestamp moved up to just above that version, which it will now see.

Value read(Key key, long readAt, long maxOffset) {
	Version v = store.newestAtOrBelow(key, readAt + maxOffset);
	if (v != null && v.timestamp() > readAt)                   // inside the uncertainty interval
		throw new ReadWithinUncertaintyInterval(v.timestamp());   // retry the read just above it
	return v == null ? null : v.value();
}

The cost has moved from every write to the occasional read: a restart only when a read meets a value written in the last half-second or so by another node, which for most workloads is uncommon. Where Spanner waits out the uncertainty in advance, these systems resolve it on demand.

The fourth row is the difference that remains. With uncertainty restarts, a read never misses a completed write to the data it reads. Two transactions on unrelated rows can still receive timestamps in the opposite order to the one in which they really happened, if they ran on nodes with different clocks and never touched a common key. A third transaction reading both rows could then see the later one's effect without the earlier one's. CockroachDB's documentation names this a causal reverse. So its guarantee is serializability with no stale reads, which is slightly less than Spanner's, and for nearly all applications the gap is never observed.

Both designs rest everything on the bound, so both police it. A CockroachDB node measures its offset from its peers continually, and one that finds itself too far from the majority shuts itself down, on the principle that a stopped node is a crash fault and a node with a wrong clock is something worse.

🛰️
Use case: the clock with error bars becomes something you can rent

For about a decade the interval clock was a Google speciality. The paper described it in 2012, and anyone else wanting the same guarantees had to choose between an oracle and a half-second NTP bound, since building a fleet of GPS receivers and atomic clocks was out of reach. That has changed, and the route by which it changed shows what the idea really consists of. Amazon had run a time service for its cloud since 2017, with satellite-connected and atomic reference clocks in each of its regions. In 2021 it published ClockBound, an open-source daemon and library which, on a virtual machine using that service, answers the TrueTime question: the current time as an earliest and a latest bound, with the promise that the truth lies between. In late 2023 the service began delivering time to supported machines through hardware in the network card, which stamps packets as they pass and removes most of the variable delay that limits NTP, and the bound fell from about a millisecond to tens of microseconds. An interval that narrow makes commit wait almost free. The following year Amazon announced a distributed SQL database of its own, Aurora DSQL, whose design uses those bounded clocks to choose transaction timestamps, so that a read in one region can be served locally at a timestamp known to be valid everywhere, with no call to a central service and no coordination across regions before commit. Other providers now offer comparable precision time. The lesson is about where the difficulty lay. The algorithm in this chapter is two rules and a three-line proof. What took the decade was the engineering that lets a machine state an error bound and never be wrong about it, and once that is available as a service, the algorithm comes with it.

⚠️
Common mistakes
  • "Spanner has perfectly synchronised clocks." It has clocks with a known error, and waits out the error.
  • Comparing raw timestamps from two machines. Without a bound and a rule for using it, the order means nothing.
  • Setting the maximum offset low to cut restarts. If real skew exceeds it, the database returns stale reads with no error at all.
  • Ignoring clock health. In these systems a bad clock is a correctness fault. Monitor offsets and let nodes remove themselves.
  • Assuming a hybrid-clock database is strictly serializable. It prevents stale reads. Unrelated transactions can still be ordered against real time.
  • Trying commit wait over NTP. With an honest bound of hundreds of milliseconds, every write would take that long.

Interview drill

Explain it simply: What is TrueTime, and how does Spanner use it?

How a strong answer sounds
TrueTime is Google's clock API. Instead of returning a single timestamp, it returns an interval, earliest and latest, that is guaranteed to contain the true time. The width of the interval, a few milliseconds originally and under a millisecond now, reflects the clock's uncertainty, and it is kept small using GPS receivers and atomic clocks in every datacentre, with each machine assuming worst-case drift between synchronisations. Spanner uses it to assign commit timestamps that respect real-time order across the whole globe, a property called external consistency. A transaction picks its commit timestamp as the latest bound of the interval and then performs a commit wait: it holds its locks and delays replying until the earliest bound has passed that timestamp, so the timestamp is definitely in the past everywhere. Any transaction that starts after that must get a higher timestamp. The result is that timestamp order matches the order an outside observer would see, without nodes having to coordinate on time, and it allows consistent, lock-free snapshot reads at any timestamp from any sufficiently up-to-date replica. The cost is a wait of roughly twice the uncertainty per write, which is why Google invested in accurate clocks.

Deeper: CockroachDB has no atomic clocks. How does it stay consistent, and what does it give up?

How a strong answer sounds
It uses hybrid logical clocks, which combine NTP-synchronised physical time with a logical counter, and a configured maximum clock offset between nodes, 500 milliseconds by default. Rather than waiting out the uncertainty on every commit, which would be far too slow at that bound, it handles uncertainty on reads. A transaction reading at timestamp t considers the range from t to t plus the max offset as uncertain: if it finds a value with a timestamp in that range, it can't know whether that write actually happened before the transaction started, since the writer's clock could be ahead. So it restarts the read at a timestamp just above that value, guaranteeing it sees it. That prevents stale reads, and since hybrid clocks advance when nodes exchange messages, causally related transactions are ordered correctly. The trade-offs. Occasional transaction restarts, which are usually cheap and are reduced by tracking per-node observed timestamps. A weaker guarantee than Spanner: it is serializable with no stale reads on the keys you touch, but not strictly serializable, because two transactions on disjoint keys handled by nodes with skewed clocks can get timestamps in the reverse of their real-time order, the causal reverse anomaly. And correctness depends on clocks staying within the configured offset: if skew exceeds it, stale reads become possible without any error, so nodes continuously check their offset against peers and a node that drifts too far shuts itself down. Operationally that means good NTP, or better PTP or a cloud time service, is a hard requirement.

🧠 Key takeaways

  • External consistency: if one transaction finishes before another starts, it has the lower timestamp. Raw clocks can't give this.
  • An interval clock returns earliest and latest bounds that are guaranteed to contain the true time. The half-width is ε.
  • Commit wait: stamp with the latest bound, then wait until the earliest bound has passed the stamp. The cost is about 2ε for each write.
  • With that, every timestamp names one consistent state of the whole database, and reads at a timestamp need no locks.
  • On ordinary clocks, a hybrid clock plus an uncertainty window moves the cost to reads that meet a recent value, by restarting them.
  • Both depend on the clock bound holding. A clock outside it gives stale reads silently, so nodes watch their own clocks and stop if in doubt.
