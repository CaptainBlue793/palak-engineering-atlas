Distributed Tracing & Debugging

"Checkout is slow." On one machine that sentence leads to a profiler and, an hour later, to a line of code. In a system of services it leads to a meeting. A checkout request enters at a gateway, which calls an authentication service, a cart service, a pricing service and a payment service, each of which calls a cache, a database or a bank. Fifteen processes on a dozen machines took part in one click. Every one of them has logs, in fifteen places, with timestamps from fifteen clocks, none of which says which line belongs to which user's request. Every one has a dashboard, showing averages, on which nothing looks wrong. The question "where did this request's two seconds go?" has an exact answer, and nothing in those tools holds it. Distributed tracing is the technique that does. Each request carries an identifier through every service it touches, each service records what it did under that identifier and for how long, and the records are joined afterwards into one picture of the request's whole life. This chapter covers how that picture is made, what it costs, and how to read one.

Traces and spans

A span is one timed operation in one process: handling an HTTP request, making a call to another service, running a database query. It records a name, a start time and a duration, whether it succeeded, and a set of key–value attributes such as the URL, the SQL statement or the user's tier. A span also records the ID of its parent, the operation that caused it.

A trace is all the spans of one request, which the parent links arrange into a tree. The root is the first span, where the request entered the system. A call from one service to another usually appears twice: a client span in the caller, timing the whole round trip, with a server span beneath it in the callee, timing the work. The difference between the two is the network and any queueing.

The three are used together, and the thing that joins them is the trace ID. An alert on a metric says that checkout's 99th percentile has risen. A trace of one slow checkout shows which hop. That span's trace ID, written into every log line the service produced while handling the request, finds the lines that say why.

Context propagation

A trace only exists if every process agrees which request it is working on. That agreement is carried by the trace context: the trace ID, shared by every span of the request, and the ID of the current span, which will be the parent of whatever comes next. Within a process the context is kept in thread-local storage or its equivalent. Between processes it has to be written into the outgoing request and read out at the other end. For HTTP there is a standard header.

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └─ flags: 01 = this trace is sampled
             │  │                                └─ the caller's span ID, 16 hex digits: the new span's parent
             │  └─ the trace ID, 32 hex digits, generated once at the edge
             └─ version

Propagation is where tracing breaks, and it breaks in the same few places.

  • One service that doesn't forward the header. Everything downstream of it starts a fresh trace. The original shows a call into that service and then nothing, and the missing half exists under an ID nobody is looking for.
  • Asynchronous hops. A message put on a queue is processed later by another process on another thread. The context has to be written into the message's headers by the producer and restored by the consumer.
  • Thread pools. Work handed to an executor runs on a thread whose thread-local context belongs to something else, unless the task is wrapped to carry the submitter's.
  • Things that aren't your code. Proxies, gateways and third-party services that strip unknown headers.

Sampling

Recording every span of every request is rarely affordable. A service handling ten thousand requests a second, each producing thirty spans, emits three hundred thousand spans a second, and most describe requests exactly like the one before. So a trace is kept or dropped as a whole, and the question is when to decide.

Head-based samplingTail-based sampling
DecidedAt the first span, before anything is known. The decision travels in the flags of the headerAfter the trace is complete, by a collector that has seen all of it
RuleA fixed fraction: keep 1 in 100Keep every error and every slow trace, and a small fraction of the rest
CostAlmost none. Unsampled requests record nothingEvery span is produced and shipped, and held in memory until its trace ends
Of 100 failed requests in a millionAbout 1 is keptAll 100 are kept
DifficultyThe interesting traces are the rare ones, and they are mostly thrown awayAll spans of a trace must reach the same collector, which has to guess when a trace is finished

Whichever is used, the decision must be made once for the whole trace. If each service sampled independently at 10%, a request crossing five services would be recorded complete once in a hundred thousand times, and the rest would be fragments. That is why the sampled flag is part of the propagated context, and why a service that receives it obeys it.

OpenTelemetry in Java

Tracing began inside large companies. Google's system, Dapper, was described in 2010, and Twitter's Zipkin and Uber's Jaeger followed its design in the open. OpenTelemetry, formed in 2019 by merging two earlier projects, is now the common standard: one API for producing spans, metrics and logs, one wire protocol, OTLP, for shipping them, and a collector process that receives, samples and forwards them to whatever stores and displays traces.

For a Java service most of the work is done without touching the code. An agent attached at start-up rewrites the bytecode of well-known libraries, HTTP servers and clients, gRPC, JDBC drivers, Kafka clients, so that each creates spans and propagates context.

# Start the service with the agent. No code changes.
OTEL_SERVICE_NAME=cart-service \
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317 \
OTEL_TRACES_SAMPLER=parentbased_traceidratio OTEL_TRACES_SAMPLER_ARG=0.01 \
java -javaagent:opentelemetry-javaagent.jar -jar cart-service.jar

The sampler named there keeps 1% of traces that start at this service, and for any request arriving with a traceparent, does whatever the caller decided. What the agent can't know is which parts of your own logic matter. Those get spans by hand.

private static final Tracer tracer = GlobalOpenTelemetry.getTracer("checkout");

Receipt priceAndCharge(Cart cart) {
	Span span = tracer.spanBuilder("checkout.price-and-charge").startSpan();
	try (Scope scope = span.makeCurrent()) {              // spans started on this thread are now its children
		span.setAttribute("cart.items", cart.size());           // low-cardinality facts worth filtering by
		Price price = pricing.quote(cart);                   // the instrumented client adds traceparent
		return payments.charge(cart.userId(), price);
	} catch (RuntimeException e) {
		span.recordException(e);
		span.setStatus(StatusCode.ERROR);
		throw e;
	} finally {
		span.end();                                         // a span that is never ended is never exported
	}
}

// Crossing a thread pool: carry the submitter's context into the task.
ExecutorService pool = Context.taskWrapping(Executors.newFixedThreadPool(8));

// Putting the trace ID in every log line, so that a span leads to its logs.
MDC.put("trace_id", Span.current().getSpanContext().getTraceId());

Spans are queued in memory and exported in batches by a background thread, so tracing adds microseconds to a request and never a network call. If the collector is unreachable, spans are dropped. Losing telemetry is the correct failure: a tracing system must never be able to take down the service it observes.

Finding the slow hop

A method that works on almost any trace:

  1. Start at the root and note the total. That is what the user experienced.
  2. Follow the critical path. At each span, find the child that finished last, and step into it. Spans off this path, however slow, did not delay the request.
  3. Look for the largest self time. A span that is long and has long children is only reporting on them. A span that is long with nothing beneath it is the place, or is the point at which instrumentation ends.
  4. Look at the shape. Many short identical spans in a row are a loop making one call per item. Two identical spans, the first failed, are a retry. Children that run one after another and don't depend on each other could run together.
  5. Look at the gaps. Time between a client span starting and its server span starting is network, connection set-up or a queue. Time inside a server span before its first child is often waiting for a thread or a connection from a pool.
  6. Compare with normal. One trace shows where the time went. Whether that is unusual needs the same span's usual duration, which is a metric.

One caution about what is being read. Each span's start time comes from the clock of the machine that recorded it, and those clocks differ (Chapter 6). Durations are measured on one machine and can be trusted. The alignment of a span against its parent on another machine can be off by milliseconds, and a child drawn as starting before the call that caused it is a skewed clock, not a paradox.

Use case: Dapper, and tracing one request in a thousand

The design that nearly every tracing system now follows was set out by Google in a 2010 paper on Dapper, which had by then been running in production for two years. Its authors started from three requirements, and the way they met them explains the shape of this chapter. The first was that tracing be everywhere, since a trace with a hole in it is of little use, and that it stay on at all times, since the problem worth diagnosing has usually already happened. That ruled out asking each team to instrument its code. Google's services almost all used the same few libraries for remote calls, threading and control flow, so Dapper was built into those. Trace context was carried in thread-local storage and added to every outgoing call by the RPC library, and an application developer got traces by doing nothing. The second requirement was low overhead, as a service team will turn off anything that costs it measurable latency. Spans were written to local files and collected later, off the request's path. The decisive saving was sampling. The paper reports that recording one trace in 1,024 was enough for high-traffic services: at that volume even a rare event recurs often enough to be caught, and the cost fell below what could be measured. Lower-traffic services needed a higher rate, and the system later adjusted it automatically. The third requirement, which the authors came to value most, was that the data be available within about a minute and be searchable. The paper's examples of use are instructive for being mundane. One team found, from the picture of a single request, that calls it had assumed were being made in parallel were issued one after another along the critical path, and fixed a latency problem by restructuring them. Others used traces to learn which services their own service really depended on, which nobody had written down. The paper is open about the limit: sampling at the head keeps a representative set and discards most of the exceptions, the weakness that tail-based sampling was later designed to address.

⚠️
Common mistakes
  • Sampling independently in each service. Traces arrive in pieces. Decide once, at the edge, and propagate the decision.
  • One service that drops the header. Every trace through it is cut in two. Check propagation at each hop, queues and thread pools included.
  • Optimising the longest bar. If it isn't on the critical path, the request gets no faster.
  • Putting user IDs or request bodies in span names. Names should be few. Put variable detail in attributes, and keep secrets out of both.
  • Exporting spans synchronously. The tracing backend's bad day becomes the service's outage.
  • Trusting the alignment of spans across hosts to the millisecond. The clocks differ. Trust durations.
  • Tracing without trace IDs in the logs. The trace shows where and can't show why.

Interview drill

Explain it simply: What is distributed tracing, and how does a trace get assembled across services?

How a strong answer sounds
Distributed tracing records the path of a single request through all the services it touches, so you can see where time was spent and where an error originated. The unit is a span: one timed operation in one process, with a name, start time, duration, status and attributes. A trace is the tree of all spans for one request. To assemble it, the first service generates a trace ID and a span ID. On every outgoing call it adds a header, in the W3C standard called traceparent, containing the trace ID, its own span ID as the parent, and a flag saying whether the trace is sampled. The receiving service reads the header, creates its own span with the same trace ID and the caller's span as parent, and passes the context on to its own downstream calls. Each service exports its finished spans asynchronously to a collector. The backend groups spans by trace ID and links them by parent ID to rebuild the tree, usually shown as a waterfall. Because full tracing is expensive, systems sample: either at the start of the request, keeping a fixed percentage, or at the end, keeping slow and failed traces.

Deeper: The p99 latency of an endpoint has doubled. How do you use traces to find out why, and what could mislead you?

How a strong answer sounds
First I'd confirm with metrics when it started and whether it correlates with a deploy, traffic change or a dependency's metrics. Then I'd pull traces for that endpoint in the slow range, above the old p99, and compare them with typical ones. In a slow trace I follow the critical path from the root: at each level the child that finishes last. I look for the span with the largest self time, meaning duration not explained by its children, because a parent is long simply when its child is. I also look at shape: a long run of identical short database spans suggests an N+1 query; duplicate spans with an error on the first suggests retries or timeouts; gaps between a client span and the matching server span suggest queueing, connection pool exhaustion or network; a gap before the first child inside a server span suggests thread or pool starvation or garbage collection. I'd check whether the slow traces share an attribute: one host, one availability zone, one tenant, one downstream shard. What could mislead me. Sampling: with head sampling at one percent I may have few slow traces and they may not be representative, so I'd raise sampling for this endpoint or use tail sampling. Missing instrumentation: a big self time may just mean an untraced call inside. Broken propagation: a client span with no children looks like network time when the callee's spans are in another trace. Clock skew between hosts can make spans appear misaligned, so I trust durations over offsets. Parallel calls: the longest sibling isn't necessarily the problem unless it is on the critical path. And one trace is an anecdote, so I would aggregate: compare the distribution of each span's duration before and after.

🧠 Key takeaways

  • A span is one timed operation in one process. A trace is the tree of a request's spans, joined by trace ID and parent ID.
  • Context travels in a request header and must be forwarded at every hop, across queues and thread pools too.
  • Sampling keeps whole traces. Head-based is cheap and misses the rare cases, and tail-based keeps them at a cost.
  • OpenTelemetry's Java agent instruments common libraries. Add spans by hand for your own logic, and put the trace ID in logs.
  • To read a trace: follow the critical path, find the largest self time, and look at the shape and the gaps.
  • Metrics say that something is wrong, traces say where, and logs say why.

Check your understanding

What links the spans recorded by different services into one trace?

Each service reports alone. The trace ID groups the spans and the parent IDs arrange them into a tree.

Service C in the chain A → B → C → D doesn't forward the traceparent header. What does the trace for A's request show?

D sees no context and starts a new trace. The original ends at C's outgoing call, which looks like unexplained time.

One request in ten thousand fails. Head-based sampling keeps 1% of traces. How many failed traces are kept, of a hundred failures?

A head sampler can't favour interesting traces. Tail-based sampling decides after the trace is complete and can keep every error.

A span lasts 400 ms and its children, run one after another, last 390 ms in total. What is its self time, and what does that suggest?

Self time is duration less the time covered by children. Look further down the tree.

A request calls three services in parallel, taking 30, 40 and 300 ms. The 40 ms call is made twice as fast. What happens to the request's latency?

Only spans on the critical path affect the total. The others finished long before they were needed.
