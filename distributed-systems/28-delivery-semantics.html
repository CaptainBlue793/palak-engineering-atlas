Delivery Semantics & Exactly-Once

A service puts a message on a queue: "payment received, £10, account 77". Another service takes it off and adds £10 to a balance. Between those two sentences are three networks and two processes, any of which can fail at any moment, and the sender's only evidence of success is an acknowledgement that can itself be lost. So after any failure the sender faces a choice it can't escape: send again and risk the message arriving twice, or don't and risk it never arriving. Those are the two honest guarantees, at-least-once and at-most-once. The third, exactly-once, is what everyone wants, and as a statement about delivery it can't be had. What can be had is its effect: a system in which a message may be delivered several times and changes the result only once. This chapter covers how that is built, at each hop, from the two ingredients that make it possible, and what Kafka's "exactly-once" does and doesn't include.

Exactly-once delivery is impossible for the reason given in Chapter 4: a sender that hears nothing can't tell "the message was lost" from "the acknowledgement was lost", and no number of extra acknowledgements changes that (Chapter 39 has the proof). So every system that claims exactly-once is doing the same thing underneath: delivering at least once, and making the second delivery harmless. The accurate names are effectively-once or exactly-once processing.

Where it goes wrong

A message crosses two hops, and each has its own window.

Producer to broker. The producer sends and waits for an acknowledgement. If none comes and it doesn't retry, a lost request is a lost message. If it does retry, a lost acknowledgement is a duplicate: the broker stored the first copy and stores the second.

Broker to consumer. The consumer does two things with each message: it performs the work, and it records that it has done so by committing its offset. A crash can fall between the two, and the order decides what the crash costs.

There is no third ordering. The work and the offset live in two different systems, a database and a broker, and no arrangement of two separate writes is atomic. The ways out are to make the repeat harmless, or to put the two writes in one system so that they become one.

Deduplication

To recognise a repeat, a receiver needs something that is the same on both copies and different on every other message: an identity. There are three sources.

  • An ID assigned by the producer when the message is first created, and reused on every resend. A random UUID works. The ID must be created before the first attempt and stored with the message, since an ID generated per attempt identifies nothing.
  • A natural key from the business: the payment provider's transaction reference, an order number with a line number.
  • A sequence number per producer. Each producer numbers its messages 1, 2, 3. The receiver keeps only the highest number seen from each producer, and drops anything at or below it. This needs constant space, where remembering every ID grows without limit.

The second question is how long to remember. A set of every ID ever seen grows for ever, so real systems keep a window: a time limit, or the last few sequence numbers per producer. A duplicate that arrives after the window has closed gets through, so the window must be longer than the longest retry any sender will attempt. Mobile clients that have been offline for a week are why some windows are measured in weeks.

Idempotent consumers

A consumer is idempotent if handling the same message twice leaves the same state as handling it once. There are three ways to build one, in rising order of generality.

Make the operation itself idempotent. "Set order 8812 to PAID" can be repeated safely. "Add £10 to the balance" can't. Many handlers can be rewritten from the second form to the first: store the payment as a row keyed by its ID, an upsert, and compute the balance from the rows.

Keep a table of processed IDs, in the same transaction as the work. This is the inbox, the mirror of Chapter 22's outbox.

@Transactional
void handle(PaymentReceived event) {
	int inserted = jdbc.update(
			"INSERT INTO processed_events (event_id) VALUES (?) ON CONFLICT DO NOTHING", event.id());
	if (inserted == 0) return;                                  // seen before: do nothing, and let it be acknowledged
	jdbc.update("UPDATE accounts SET balance = balance + ? WHERE id = ?", event.amount(), event.accountId());
}                                                              // one commit: the ID and the money, or neither

The insert and the update commit together. If the consumer crashes before the commit, neither happened and the redelivery does both. If it crashes after, the redelivery finds the ID and does nothing. The primary key on event_id also settles two consumers handling the same message at once: one insert wins and the other sees zero rows.

Store the offset with the data. If messages come from a log with offsets, the consumer can write its new offset into the same database, in the same transaction as the work, and ignore the broker's copy of the offset. On restart it reads its position from the database. Work and position are now one atomic write, and the crash window is gone. This protects against the consumer's own crashes. It does nothing about a duplicate that is already in the log as a separate entry, which has its own offset.

    Things to notice. With no faults, every design gives £60. Start with the producer. Lose m3's acknowledgement with a producer that retries: the log holds m3 twice, seven entries for six messages, and the balance is £70. Change the producer to "no retries" and that fault does no harm, and losing m3's request loses m3 for good: £50. The producer can't tell which of the two has happened, so neither setting is safe against both. Sequence numbers are. The producer still sends m3 twice, and the broker stores it once.

    Now the consumer, with the sending fault set back to none. Crash on m5 under "commit, then process" and m5 is never applied: £50. Under "process, then commit" it is applied twice: £70. The same crash between the same two steps gives opposite errors. The ID table and the single transaction both give £60.

    Those last two designs differ in one case, and it is why this chapter takes each hop separately. Use a producer that retries without sequence numbers, lose m3's acknowledgement, and compare them. The consumer with an ID table gives £60: the second m3 carries the same ID and is skipped. The consumer that stores its offset in the transaction gives £70. It handled every log entry exactly once, and the log had m3 in it twice. Across all 72 combinations, three pairings are correct under every fault: the ID table with either retrying producer, and the transactional offset with sequence numbers.

    One more. Choose no retries, lose m3's request, process then commit, and crash on m5. One message is lost and one is doubled, and the balance is £60. A total that looks right is not evidence that the pipeline is.

    Transactional outbox

    The same gap exists on the sending side, and Chapter 22 closed it: a service that must change its database and publish a message writes the message as a row in an outbox table, in the same local transaction, and a relay publishes it afterwards. The relay can crash after publishing and before marking the row as sent, so the outbox is an at-least-once producer by construction.

    Put the two halves together and the chain is complete. An outbox at each sender guarantees the message is published if and only if the change committed, perhaps twice. An inbox at each receiver guarantees a repeated message changes nothing. Between them the transport needs only to be at-least-once, which every broker can manage. No distributed transaction is involved at any point: each service does one local transaction, twice over.

    Exactly-once in Kafka

    Kafka added two features in 2017, in version 0.11, that together carry its exactly-once claim. Each closes one of the two windows.

    The idempotent producer closes the producer hop, and is the sequence-number scheme from the deduplication section. When a producer starts, the broker gives it a producer ID. The producer numbers the batches it sends to each partition, and the broker remembers the last few sequence numbers for each producer and partition. A batch that arrives with a number already seen is acknowledged and not appended. A batch that arrives with a gap is rejected, so order is kept as well. It is on by default from Kafka 3.0. Its limit is in the name of the thing it tracks: the producer ID lasts for one run of the producer, so a producer that crashes and restarts gets a new ID, and anything it resends from before the crash is not recognised.

    Transactions extend this across restarts and across several writes. A producer is given a stable transactional.id by its configuration. It can then begin a transaction, send messages to any number of partitions, and commit or abort, and consumers that ask for isolation.level=read_committed see either all of the transaction's messages or none. The feature that makes this more than batching is that a consumer's offsets are themselves stored in a Kafka topic. So a program that reads from one topic and writes to another can put its outputs and its new input position into one transaction.

    props.put("transactional.id", "enricher-" + instance);         // the same id every time this instance starts
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();                                     // also shuts out any older process using this id

while (running) {
	ConsumerRecords<String, String> batch = consumer.poll(Duration.ofMillis(200));
	if (batch.isEmpty()) continue;
	producer.beginTransaction();
	try {
		for (ConsumerRecord<String, String> r : batch)
			producer.send(new ProducerRecord<>("enriched", r.key(), enrich(r.value())));
		producer.sendOffsetsToTransaction(nextOffsets(batch), consumer.groupMetadata());   // the input position, in the same transaction
		producer.commitTransaction();
	} catch (ProducerFencedException e) {
		throw e;                                                 // a newer instance has taken over: stop at once
	} catch (KafkaException e) {
		producer.abortTransaction();                             // outputs and offsets are both discarded
		rewindToLastCommitted(consumer);                         // and the batch will be read again
	}
}

    If the program crashes anywhere in the loop, the open transaction is aborted. Its outputs are never shown to read-committed consumers and its offsets were never advanced, so the replacement instance reads the same batch and produces the same outputs, once. Inside the brokers this is a two-phase commit (Chapter 21) run by a transaction coordinator whose own state is a replicated log, which is what keeps it from blocking. The call to initTransactions raises an epoch number for the transactional ID, and brokers refuse writes carrying an older epoch. That is a fencing token, the subject of Chapter 32, and it deals with an old instance that was only paused and wakes up believing it is still in charge.

    The boundary. The guarantee covers three things: records read from Kafka, records written to Kafka, and offsets. Everything else the loop does is outside it. If enrich calls a payment API, sends an email or writes to a database, that happens on every attempt, and an aborted transaction doesn't undo it. For effects outside Kafka the earlier sections still apply: an idempotent sink, or a sink that takes part in a two-phase commit tied to the processor's checkpoints, as Flink's does (Chapter 27). Kafka Streams turns the whole pattern on with one setting, processing.guarantee=exactly_once_v2, and has the same boundary.

    Use case: Segment, and remembering sixty billion message IDs

    Segment collects analytics events from its customers' websites and mobile apps and passes them on to hundreds of other tools. The senders are browsers and phones on unreliable networks, built to retry: an app that sends a batch and loses its connection before the reply sends the batch again when the connection returns, which may be a second later or a week. In 2017 Segment's engineers wrote that about 0.6% of what they received was a repeat of something already received, and for customers billed by event count, or counting purchases, that was not acceptable. Every event carries a message ID generated on the device when the event is created, so the repeats were identifiable. The difficulty was scale: to catch a retry a week late, the system had to remember every ID for weeks, and they chose a window of four weeks, which meant about sixty billion IDs, a terabyte and a half on disk. Their design follows this chapter's rules closely. Incoming events go to a Kafka topic partitioned by message ID, so both copies of a duplicate always reach the same worker and no two workers need to coordinate. Each worker keeps its seen IDs in RocksDB, an embedded LSM store, chosen in part since nearly every lookup is for an ID that has not been seen, and its bloom filters answer "definitely absent" without reading the disk (Databases, LSM trees). The awkward step is the usual one: a worker must record the ID and publish the event to the output topic, in two systems, and may crash between. They made the output topic the single source of truth. An ID counts as seen only if its event is in the output, and a worker that restarts first reads the tail of the output topic and brings its local store into line with it before taking new input. One system holds the truth and the other is a cache of it, which is the "store the offset with the data" idea turned around.

    ⚠️
    Common mistakes
    • Believing a broker's "exactly-once" covers your database or your HTTP calls. It covers the broker.
    • Auto-committing offsets on a timer. The commit is unrelated to whether the work finished, so a crash can lose or repeat.
    • Generating the message ID at send time. Each retry gets a fresh ID and nothing can be matched.
    • Writing the processed-ID row in a separate transaction from the work. The gap is back.
    • A deduplication window shorter than the longest retry. Late duplicates pass straight through.
    • Choosing at-most-once by accident. Acknowledging on receipt, before the work, is the default in many client libraries.
    • Assuming redelivery keeps the order. A retried message can arrive after its successors.

    Interview drill

    Explain it simply: What are at-most-once, at-least-once and exactly-once delivery? Is exactly-once really possible?

    How a strong answer sounds
    At-most-once means a message is delivered zero or one times: the sender doesn't retry, or the consumer acknowledges before processing, so a failure loses the message but never duplicates it. At-least-once means one or more times: the sender retries until acknowledged and the consumer acknowledges only after processing, so nothing is lost but a failure can cause a duplicate. Exactly-once means the effect happens once. As pure delivery it is not possible, because when an acknowledgement is lost the sender cannot tell whether the message arrived, so it must either risk a duplicate or risk a loss. What is achievable is exactly-once processing, sometimes called effectively-once: at-least-once delivery combined with idempotent handling, so duplicates have no additional effect. That is done by making the operation naturally idempotent, by recording processed message IDs in the same transaction as the work, or by committing the consumer's position atomically with its output. So in practice I design for at-least-once and make consumers idempotent.

    Deeper: How does Kafka provide exactly-once semantics, and where does it stop?

    How a strong answer sounds
    Two mechanisms. The idempotent producer: each producer gets a producer ID and attaches a per-partition sequence number to every batch; the broker keeps the latest sequence numbers per producer and partition, and discards a batch it has already appended, so a retry after a lost acknowledgement doesn't create a duplicate, and ordering is preserved. That handles the producer-to-broker hop within one producer session. Transactions extend it: a producer with a configured transactional ID can write to several partitions atomically, and because consumer offsets are stored in an internal Kafka topic, it can include the offsets of the input it consumed in the same transaction, using sendOffsetsToTransaction. A transaction coordinator runs a two-phase commit and writes commit or abort markers into the partitions; consumers with isolation level read_committed only see committed data. So in a consume-transform-produce loop, the outputs and the advance of the input position either both happen or neither does, and a crash just means the batch is reprocessed with the earlier attempt's output invisible. The transactional ID also provides fencing: when a new instance calls initTransactions the epoch is bumped and a zombie old instance is rejected. Where it stops: the guarantee is only for state inside Kafka. Any side effect to an external system during processing, a database write, an API call, is still at-least-once, so the sink must be idempotent or participate in a two-phase commit, which is what Flink's transactional sinks do with checkpoints. It also costs latency, since read_committed consumers wait for commit markers, so the commit interval sets a floor on end-to-end delay.

    🧠 Key takeaways

    • After a timeout a sender must risk a loss or a duplicate. At-most-once and at-least-once are the two honest choices.
    • Exactly-once delivery is impossible. Exactly-once effect is at-least-once delivery plus a harmless repeat.
    • The consumer's crash window is between doing the work and recording its position. Order decides whether it loses or repeats.
    • Close it with an idempotent operation, a processed-ID table in the same transaction, or the offset stored with the data.
    • Outbox at the sender and inbox at the receiver give effectively-once across services with only local transactions.
    • Kafka: sequence numbers remove producer duplicates, and transactions commit outputs with input offsets. Outside Kafka, you are back to idempotence.

    Check your understanding

    A consumer commits its offset and then processes the message. It crashes between the two. What happens to that message?

    Commit-then-process is at-most-once. The reverse order turns the same crash into a duplicate.

    Why can't a messaging system guarantee exactly-once delivery?

    Resending risks a duplicate and not resending risks a loss. Only the receiver can make the repeat harmless.

    In the inbox pattern, why must the processed-ID row and the business change be in the same transaction?

    One commit makes "seen" and "done" the same fact. Two commits bring the crash window back.

    What does Kafka's idempotent producer use to discard a retried batch?

    A batch whose number the broker has already stored is acknowledged without being appended again.

    A Kafka transactional loop reads a record, calls an external email API, writes an output record and commits. The transaction aborts and the batch is retried. What is true?

    Kafka's guarantee covers Kafka. The email call needs its own idempotency key.
