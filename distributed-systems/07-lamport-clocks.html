Lamport Clocks & Happens-Before

Chapter 6 ended on a problem: physical clocks on different machines disagree, so their timestamps can't say which of two events came first. In 1978 Leslie Lamport published a paper that changed the question. For most purposes a system doesn't need to know what time an event happened. It needs to know which events could have influenced which, and that can be worked out exactly, with no clock at all, from the messages the processes send each other. The paper defined that relation, happens-before, and gave a counter of a few lines, the Lamport clock, whose values respect it. Both ideas run through the rest of this course: Paxos ballots, Raft terms, version numbers and fencing tokens are all descendants of that counter.

Happens-before

Picture a system as a set of processes, each doing one thing after another. Three kinds of thing can happen at a process: a local step, the sending of a message, and the receipt of a message. Each is an event. Lamport defined a relation between events, written a → b and read "a happened before b", by three rules.

  • Same process: if a and b are events at one process and a comes first there, then a → b.
  • Message: if a is the sending of a message and b is the receipt of that same message, then a → b.
  • Chains: if a → b and b → c, then a → c.

That is the whole definition, and it uses no clock. a → b means there is a path from a to b made of steps within a process and messages between processes. Put another way, information from a could have reached b, so a could have caused or influenced b.

When there is no path in either direction, the two events are concurrent, written a ∥ b. Concurrent doesn't mean simultaneous. It means neither could have known about the other. A write in London at noon and a write in Tokyo ten minutes later are concurrent if no message travelled between the two machines in those ten minutes, and nothing in the system could tell which came first, since nothing in the system observed both. Happens-before is therefore a partial order: some pairs of events are ordered and some aren't.

Lamport timestamps

A Lamport clock is a counter kept by each process, with two rules.

  • Before each local event, and before sending a message, add one. A message carries the sender's counter with it.
  • On receiving a message, set the counter to the larger of its own value and the message's, and then add one.
public final class LamportClock {
	private final AtomicLong time = new AtomicLong();

	/** A local event, or the sending of a message. The result goes into the message. */
	public long tick() { return time.incrementAndGet(); }

	/** A message arrived carrying the sender's timestamp. */
	public long onReceive(long messageTime) {
		return time.updateAndGet(local -> Math.max(local, messageTime) + 1);
	}
}

Write L(a) for the counter's value at event a. The rules guarantee one thing, called the clock condition:

if a → b, then L(a) < L(b)

It holds for each of the three rules of happens-before. Along one process the counter only goes up. Across a message the receiver takes at least the sender's value plus one. And a chain of smaller-than steps is smaller-than from end to end. So Lamport timestamps never contradict causality: an effect always carries a larger number than anything that led to it.

Total order with tie-breaks

Happens-before leaves concurrent events unordered, and many algorithms want every event in one definite sequence that all processes agree on. Lamport timestamps give one almost for nothing. Sort events by timestamp, and where two timestamps are equal, break the tie by a fixed rule such as the lower process number.

record Stamp(long time, int nodeId) implements Comparable<Stamp> {
	public int compareTo(Stamp o) {
		int byTime = Long.compare(time, o.time);
		return byTime != 0 ? byTime : Integer.compare(nodeId, o.nodeId);   // the tie-break: arbitrary, and the same everywhere
	}
}

The result is a total order: any two events can be compared, and every process that holds the same stamps sorts them the same way. It is consistent with happens-before, since a cause always has the smaller time. Among concurrent events the order is arbitrary. It reflects nothing real, and that doesn't matter for its purpose, which is agreement. If every replica applies the same operations in the same order, every replica ends in the same state, whichever order it was.

Lamport's paper used this to build a mutual-exclusion algorithm: processes broadcast timestamped requests for a resource, and the request with the smallest stamp goes first. It also shows the limit of the technique. Before acting on the request stamped (5, P2), a process has to be sure that no request stamped 4 is still on its way from someone, and it can only be sure once it has heard something later from every other process. One silent process blocks everyone. Ordering events is half of a replicated system, and the other half is making progress when a participant has failed. That half is consensus, from Chapter 15 onwards.

What Lamport clocks can't tell you

The clock condition runs in one direction only, and reading it backwards is the commonest mistake made with logical clocks.

StatementTrue?Why
If a → b, then L(a) < L(b)AlwaysThe clock condition
If L(a) < L(b), then a → bNoThey may be concurrent, as with b and d in the panel
If L(a) < L(b), then b did not happen before aAlwaysThe clock condition, turned round: this is all a comparison can rule out
If L(a) = L(b), then a and b are concurrentAlwaysOrdered events have different timestamps
If a and b are concurrent, then L(a) = L(b)NoConcurrent events can have any timestamps at all

So, given two Lamport timestamps and nothing else, you can't tell whether one event caused the other or whether they were independent. For a replicated store that is the question that matters: when two replicas hold different values for a key, did one writer see the other's value and replace it, or did two writers update it independently, in which case there is a conflict that something has to resolve? A single number can't hold enough to answer that. Chapter 8 replaces it with one number for each process, which can.

Use case: a Raft term is a Lamport clock

Lamport clocks are seldom seen under that name in production systems, and their rule is in most of them. Take Raft, the consensus algorithm behind etcd, Consul and CockroachDB, which Chapter 17 covers in full. Every Raft node keeps a number called the current term. A node that starts an election adds one to its term. Every message between nodes carries the sender's term. A node that receives a message with a term larger than its own adopts the larger term at once, and if it believed itself leader it steps down. A node that receives a message with a smaller term rejects it. Compare that with this chapter's two rules: increment on a local event, and on receipt take the maximum. The Raft paper says so directly, that terms act as a logical clock. The term solves the problem this chapter started with. A leader that has been cut off from the cluster for a minute may still believe it leads, and no wall clock can be trusted to tell it otherwise. Its term can: the rest of the cluster has held an election and moved to a higher term, so the first message the old leader exchanges with anyone shows that it is behind, and its writes are refused. The same device appears as the ballot number in Paxos, the leader epoch in Kafka, the configuration epoch in Redis Cluster and the fencing token of Chapter 32. In each, a counter that only moves forward, and is taken as a maximum on every message, tells stale participants apart from current ones without reference to time.

⚠️
Common mistakes
  • Reading L(a) < L(b) as "a happened before b". It only rules out the reverse.
  • Treating "concurrent" as "at the same moment". It means causally unrelated, however far apart in time.
  • Forgetting the "+1" after taking the maximum on receipt, which lets a receipt share its send's timestamp.
  • Not sending the timestamp with every message. The clocks only stay consistent through what messages carry.
  • Using the tie-broken total order to detect conflicts. It orders concurrent writes arbitrarily and reports nothing.
  • Expecting a Lamport timestamp to mean anything in seconds. It has no relation to real time.

Interview drill

Explain it simply: What is a Lamport clock, and what does it guarantee?

How a strong answer sounds
It is a counter each process keeps to timestamp events without relying on physical time. There are two rules: increment the counter before every local event and every send, attaching the value to the message; and on receiving a message, set the counter to the maximum of the local value and the message's value, plus one. The guarantee is that if event a could have influenced event b, meaning a happened before b through a chain of local steps and messages, then a's timestamp is smaller than b's. So causes always get smaller numbers than their effects. What it doesn't guarantee is the converse: a smaller timestamp doesn't mean the event happened first, since two unrelated events on different machines can have any timestamps. Adding a tie-break by process ID turns the timestamps into a total order that every node agrees on, which is useful for applying operations in the same sequence everywhere.

Deeper: Two replicas each hold a value for the same key, with Lamport timestamps 7 and 9. What can you conclude, and what can't you?

How a strong answer sounds
I can conclude one thing for certain: the write stamped 9 did not happen before the write stamped 7, since that would violate the clock condition. I can't conclude that 7 happened before 9. There are two possibilities the timestamps don't distinguish. Either the writer of 9 had seen the value stamped 7, directly or through a chain of messages, and replaced it, in which case 9 supersedes 7 and keeping 9 is right. Or the two writes were concurrent: two clients updated the key through different replicas with no communication between them, and the numbers differ only because one replica's counter had been pushed higher by unrelated traffic. In that case there is a real conflict, and picking 9 throws away an update nobody decided to discard. If I use the Lamport order with a node-ID tie-break, I get a deterministic winner, so all replicas converge, and that is last-write-wins with a logical clock: convergent, but it loses concurrent updates silently. To detect the conflict I need more information than one integer: a version vector, which records what each writer had seen, lets me tell whether one version descends from the other or whether they are siblings to be merged.

🧠 Key takeaways

  • Happens-before orders events by possible influence: steps in one process, a send before its receipt, and chains of these.
  • Events with no such path either way are concurrent, whatever the wall clocks said.
  • A Lamport clock increments on every event and takes the maximum, plus one, on receipt.
  • Its guarantee is one-directional: if a → b then L(a) < L(b). A smaller timestamp proves nothing by itself.
  • Timestamps with a tie-break give a total order all processes agree on, which is what replicating a state machine needs.
  • Terms, epochs, ballots and fencing tokens are the same counter, used to tell stale from current.

Check your understanding

Two events are "concurrent" in Lamport's sense when:

Concurrency is about causality. Two events at one process are always ordered, and concurrent events can be hours apart.

A process whose clock reads 4 receives a message stamped 9. What is its clock after the receipt?

max(4, 9) + 1. The receipt must have a larger timestamp than the send that caused it.

Event a has Lamport timestamp 3 and event b has 8, on different processes. What can you conclude?

The clock condition says causes have smaller timestamps. It doesn't say that smaller timestamps are causes.

Why is a tie-break by process ID added to Lamport timestamps?

Equal timestamps would otherwise be unordered. The tie-break is arbitrary, and its value is that everyone applies the same one.

A Raft node in term 5 receives a message from a node in term 7. Following the Lamport rule, what does it do?

Terms act as a logical clock: on receipt, take the maximum. A larger term shows the node's own view is out of date.
