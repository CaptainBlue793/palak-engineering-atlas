Consistency Models

"Is it consistent?" is a question without an answer until somebody says consistent how. A replicated system can't behave exactly as one machine would at no cost, as Chapter 10 showed, so every system promises something less, and the promises differ a great deal. A consistency model is such a promise stated exactly: a rule that says, of any record of operations and their results, whether the system was permitted to produce it. A strong model permits few such records. It is easy to program against, and costs latency and availability. A weak model permits many, costs little, and leaves the application to cope with what it sees. This chapter defines the five models that matter in practice, from linearizability down to eventual consistency, and gives each one as a test you can apply to a history of reads and writes.

Histories

All of these models are judged on the same evidence. Clients send operations to the system and get results back. Each operation has a moment when it was sent and a moment when its result arrived, and between those two moments nobody outside the system knows what happened. A list of operations with their start times, end times and results is a history. Throughout the chapter the data is one register, x, starting at 0, with two operations: write a value, and read the value.

If two operations overlap in time, each started before the other finished, they are concurrent, and the system may treat them in either order. If one finished before the other started, a client could have used the result of the first to decide to send the second, and the stronger models require the system to respect that.

Linearizability

A history is linearizable if every operation can be assigned a single instant, somewhere between its start and its end, at which it appears to take effect, such that reading the operations off in order of those instants gives a correct history for one copy of the data. Each read returns the value of the most recent write before it.

That is the precise form of "behaves like a single machine". Two consequences follow. Once a write has completed, every read that starts afterwards must return it or something newer: there are no stale reads. And once any read has returned a new value, no later read may return the old one, even while the write is still in progress: the system can't appear to go back.

The figure shows why the real-time requirement matters: clients talk to each other outside the system. Linearizability is what a lock service, a leader election or a "this username is free" check needs, and it is expensive. Every operation has to be coordinated with a majority of replicas, which costs a round trip, and Chapter 10 showed that a replica cut off from the majority can't provide it at all.

Sequential consistency

Sequential consistency keeps the single order and drops the clock. A history is sequentially consistent if all its operations can be arranged in one sequence that is correct for one copy of the data and that keeps each client's own operations in the order that client issued them. Operations by different clients may be arranged in any order that works, regardless of when they really happened.

The history in the figure is sequentially consistent: put Bob's read first, then the write, then Alice's read. Each person's operations are in their own order, and the sequence is valid. It disagrees with the wall clock, and the model doesn't care. A sequentially consistent system never shows any one client something impossible, and never shows two clients views that contradict each other in a way they could detect through the system. They detect it only by comparing notes outside. A system in which each client reads from one fixed replica, and replicas apply the same writes in the same order, gives roughly this. ZooKeeper's reads are the standard example.

Causal consistency

The next step down drops the single order as well. Under causal consistency every client must see operations in an order that respects cause and effect: if one operation could have influenced another, in the happens-before sense of Chapter 7, nobody sees the effect without the cause. Operations that are concurrent, with no causal link, may be seen in different orders by different clients.

The usual illustration is a comment thread. Someone posts "Has anyone seen my keys?" and a reply appears: "Found them, on the hall table." The reply was written by someone who had read the question, so the question is its cause. A reader must never be shown the reply without the question above it. Two unrelated comments posted at the same moment, on the other hand, may appear in either order to different readers, and no one is harmed.

Causal consistency matters for a specific reason. It can be provided by a system that stays available during a partition: each replica only has to hold back an operation until it has the operations that one depends on, which it can do with version vectors and no help from other replicas. It has been shown to be, in essence, the strongest model for which that is true. Anything stronger needs replicas to coordinate, and so must sometimes refuse.

Session guarantees

Causal consistency is a property of the whole system. Often what an application needs is narrower: that one user's own sequence of requests makes sense. In 1994 the designers of a system called Bayou named four such properties, each about a single client's session.

GuaranteePromise to one clientWithout it
Read your writesAfter you write a value, your reads return it, or something newerYou save your profile and the page shows the old one
Monotonic readsOnce you have seen a value, you never afterwards see an older oneYou refresh, and a comment you have just read has vanished
Monotonic writesYour writes are applied in the order you made themYou edit a document twice and the first edit lands on top of the second
Writes follow readsA write you make after reading something is ordered after what you read, on every replicaYour reply is shown on a replica that doesn't yet have the post it answers

They are cheap to provide, since each concerns only what one client has already seen. The client carries a token, the version of the newest data it has written or read, and presents it with every request. A replica that hasn't reached that version waits until it has, or passes the request to one that has.

final class Session {
	private long lastSeen;                                  // the newest version this client has written or read

	Value read(Replica replica, String key) {
		Versioned v = replica.readAtLeast(key, lastSeen);   // the replica waits, or refuses, until it has applied this version
		lastSeen = Math.max(lastSeen, v.version());          // monotonic reads: never accept anything older again
		return v.value();
	}

	void write(Leader leader, String key, Value value) {
		lastSeen = Math.max(lastSeen, leader.write(key, value));   // read your writes: later reads must reach this version
	}
}

Eventual consistency

At the bottom is the weakest promise in common use. Eventual consistency says that if writes stop, all replicas will, after some unstated time, hold the same value. That is all. It says nothing about what a read returns in the meantime: a stale value, values that go backwards, your own write missing. It doesn't even say which value the replicas will agree on, only that they will agree, so a system that settles conflicts by discarding writes satisfies it.

It is a statement about the future, where the other models are statements about every read. That makes it weak as a guarantee and cheap as a design: any replica can answer any request at once, alone, which is why the systems that favour availability and latency are built on it. They are seldom used bare. Session guarantees are usually added on top, and conflict handling is chosen with care, so that "eventually the same" also means "eventually right".

Each model in the table permits every history permitted by the one above it. One term from the Databases course belongs beside these. Serializability says that transactions, groups of operations on several items, behave as if run one at a time in some order. It says nothing of real time. A system that is both serializable and linearizable, so that the order of transactions agrees with the clock, is called strictly serializable, and it is the strongest guarantee a database offers.

🎚️
Use case: five settings on one database

Most databases offer two consistency settings, a strong one and a weak one. Microsoft's Azure Cosmos DB, a globally replicated store, offers five, chosen for each account and adjustable for each request, and its documentation describes them in the terms of this chapter. Strong is linearizability: a write isn't acknowledged until it has been committed durably across the account's regions, and reads never return anything stale. It costs the most in latency and can't be combined with accepting writes in several regions. Bounded staleness lets reads lag, by no more than a set number of versions or a set time. Session gives a client read-your-writes and monotonic reads within its own session, by means of a token the client library passes back with each request, as in the code above. Consistent prefix promises that a reader never sees writes out of order, though it may be behind. Eventual promises convergence and nothing more, and is the cheapest and fastest. Two facts about how the product is used are instructive. The default is session, not strong and not eventual, and Microsoft has said that most of its customers stay on it. That fits experience elsewhere: what applications mostly need is for each user's own actions to be reflected back to them, and that is far cheaper than a global order. And the service prices the levels differently, with a strong read costing about twice an eventual one in its accounting units, which makes the trade-off of Chapter 10 a line on an invoice.

⚠️
Common mistakes
  • Saying "strong" or "consistent" without naming a model. Vendors use both words for at least three different guarantees.
  • Confusing linearizability with serializability. One is about single operations and real time, the other about multi-item transactions and no particular time.
  • Assuming eventual consistency includes read-your-writes. It doesn't, and users notice at once.
  • Paying for linearizability everywhere when one operation, a lock or a uniqueness check, is the only one that needs it.
  • Testing consistency with one client. Most violations need two clients, or one client talking to two replicas.
  • Forgetting the channel outside the system. Users phone each other. Services call each other. Real time matters when they do.

Interview drill

Explain it simply: What is linearizability?

How a strong answer sounds
It is the guarantee that a replicated system behaves as if there were a single copy of the data and every operation happened at one instant, somewhere between when the client sent it and when it got the response. Concretely: once a write has completed, any read that starts afterwards sees that write or a later one; and once any client has read a new value, no later read by anyone returns an older one. So there are no stale reads, and time never appears to go backwards, even across different clients and replicas. It matters whenever clients coordinate through the data or outside it: locks, leader election, uniqueness constraints, "did my payment go through?". The cost is that every operation has to be coordinated with a majority of replicas, which adds latency, and by the CAP theorem a replica that is partitioned from the majority can't serve linearizable operations at all.

Deeper: A user changes their display name, and the next page load still shows the old one. Which guarantee is missing, and how would you add it without making the whole system linearizable?

How a strong answer sounds
That is a violation of read-your-writes, one of the session guarantees: the write went to the leader, and the next read was served by a replica that hadn't applied it yet. It doesn't need linearizability, since only this user's view of their own write is at stake. There are several ways to provide it, in increasing order of generality. Route the user's reads to the leader for a short period after they write, say a few seconds, or always read the user's own profile from the leader, since only they edit it. Pin a session to one replica, which also gives monotonic reads, though a failover of that replica breaks it. Or, most robustly, use a version token: the write returns the log position or timestamp at which it was applied; the client, or the session store, sends that token with later reads; and a replica that hasn't reached that position either waits briefly until it has, or the request is forwarded to one that has. That is how session consistency in systems such as Cosmos DB and causal sessions in MongoDB work. I'd also keep the highest version the client has read, to get monotonic reads from the same mechanism. The things to watch are users on several devices, where the token has to travel with the user and not the device if that matters, and the latency of waiting, which should be bounded by a timeout with a fallback to the leader.

🧠 Key takeaways

  • A consistency model is a rule about which histories of operations and results a system may produce.
  • Linearizable: one order of operations that agrees with real time. No stale reads, and no going back.
  • Sequential: one order that agrees with each client's own sequence, and not necessarily with the clock.
  • Causal: effects never appear without their causes. It is the strongest model that stays available under partition.
  • Session guarantees make one client's view coherent, and a version token is enough to provide them.
  • Eventual consistency promises only convergence. Say which model you mean, and pay for strength only where it is needed.

A write of x = 1 completes. A read that starts afterwards returns the old value, 0. Which is the strongest model this history can still satisfy?

Ordering the read before the write explains the values, and the reader was a different client. Real time is violated, so it isn't linearizable.

What does linearizability require that sequential consistency doesn't?

Both demand one order. Linearizability also ties it to the clock.

Two unrelated comments are posted at the same moment, and two readers see them in opposite orders. Which model does that violate?

No single order suits both readers. The comments are concurrent, so no cause was shown after its effect.

A user reads a comment, refreshes, and the comment is gone, then reappears on the next refresh. Which guarantee was broken?

The second read came from a replica further behind than the first. A client should never see an older state after a newer one.

What does eventual consistency guarantee about a read made one second after a write?

The promise is convergence at some later time if writes stop. No particular read is covered.
