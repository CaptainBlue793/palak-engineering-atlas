Case Study: Google Spanner

For a decade the accepted view was that a database could scale across datacentres or offer transactions, and that a designer had to pick. Google's own systems said as much: Bigtable scaled without limit and had no transactions across rows, and the advertising business, which needed them, ran on MySQL split by hand into shards, the last re-splitting of which took over two years. Spanner, described in a paper in 2012, declined the choice. It is a database of SQL tables, spread over thousands of machines on several continents, synchronously replicated, in which a transaction may touch any rows anywhere and the result is as though every transaction in the world had run one at a time, in the order a bystander would have seen them. It was built with parts from nearly every section of this course. Partitioning into ranges. A Paxos group for each range. Two-phase commit across groups, with the groups making it non-blocking. Leases. Multi-version storage. And a clock that admits its error. Seeing them fitted together, with the reasons, is the best single review of the course there is.

Architecture

A Spanner deployment is called a universe. It is divided into zones, each roughly a datacentre's worth of machines and the unit that can be lost in one accident. Inside a zone are hundreds to thousands of spanservers, which hold the data and serve it, with a few helper services to tell clients which server has which data and to move data about.

The data itself is rows in tables, sorted by primary key and cut into contiguous key ranges. The paper calls the unit a tablet and Google's cloud product calls it a split. Each split is replicated in several zones, and the set of replicas of one split forms a Paxos group. Everything else is built on that.

The data model is relational, with one addition aimed at locality. A child table can be declared interleaved in its parent, which stores each child row physically next to its parent row, in the same split. A customer and that customer's orders then sit together, and a transaction on one customer's data touches one Paxos group.

CREATE TABLE Customers (
  CustomerId STRING(36) NOT NULL,                  -- a UUID: a rising counter would send every insert to the last split
  Name       STRING(MAX)
) PRIMARY KEY (CustomerId);

CREATE TABLE Orders (
  CustomerId STRING(36) NOT NULL,
  OrderId    STRING(36) NOT NULL,
  Total      NUMERIC
) PRIMARY KEY (CustomerId, OrderId),
  INTERLEAVE IN PARENT Customers ON DELETE CASCADE;   -- stored inside the customer's row range

Paxos groups and splits

Each split's replicas run Paxos with a long-lived leader, much as Raft does. A write to the split goes to the leader, is appended to the group's log, and is applied once a majority of the replicas has it. So a write is durable in several zones before the client hears of it, and a zone can be lost without losing a committed write.

The leader holds a lease of about ten seconds, granted by a majority and renewed as it goes. While the lease runs no other replica can lead. Lease intervals are measured with TrueTime, so that one leader's lease is certainly over before the next begins, and that is what allows a leader to answer some reads without a round of Paxos. In Google's cloud product a group's replicas come in three kinds: read-write replicas, which vote and can lead; read-only replicas, which follow the log and serve reads without voting; and witnesses, which vote and hold no data, there to complete a quorum. An instance's configuration fixes where each kind lives and which region the leaders prefer.

Splits aren't fixed. When one grows too large, or takes too much load, it is cut in two, and a busy split can be moved to other servers. The application never sees this. What it does see is the consequence of its key design: a primary key that rises steadily, a timestamp or a sequence, sends every insert to the last split and makes one Paxos group carry the whole write load (Chapter 20).

TrueTime

Chapter 35 covered the clock: TT.now() returns an interval certain to contain the true time, a commit takes its timestamp from the top of the interval and then waits until that timestamp has certainly passed. The result is that if one transaction finishes before another starts, it has the lower timestamp, anywhere in the world. Here it is enough to note what Spanner uses that property for: to order transactions, to let any replica serve a read at a timestamp, to keep leader leases from overlapping, and to make schema changes take effect at one agreed instant across thousands of servers with no pause in service.

Read-write and read-only transactions

Spanner has two quite different kinds of transaction, and most of its performance comes from keeping reads out of the expensive one.

A read-write transaction is pessimistic. Reads go to the leader of each split concerned and take shared locks there. Writes are held at the client until commit. If every row is in one split, commit is one Paxos write. If several splits are involved, their leaders run two-phase commit, and one of them acts as coordinator.

Deadlocks between transactions are prevented by letting an older transaction force a younger one to abort and retry, which is why a transaction's body may be run more than once.

A read-only transaction takes no locks and writes nothing. It picks a timestamp, normally TT.now().latest, and reads every row as of that timestamp. Since timestamps are globally meaningful, any replica of a split can answer, provided it has applied everything up to the chosen timestamp. Each replica tracks a safe time, the latest timestamp up to which it is known to be complete, and a replica asked for a later one either waits or checks with its leader. A stale read goes further: the client asks for the data as it was a few seconds ago, and the nearest replica almost always answers at once, with no contact with the leader at all.

DatabaseClient db = spanner.getDatabaseClient(DatabaseId.of(project, instance, "shop"));

// Read-write. The body can be run again after an abort, so it must change nothing outside the database.
db.readWriteTransaction().run(tx -> {
	long balance = tx.readRow("Accounts", Key.of(from), List.of("Balance")).getLong("Balance");   // locks the row at its leader
	if (balance < amount) throw new IllegalStateException("insufficient funds");
	tx.buffer(Mutation.newUpdateBuilder("Accounts").set("AccountId").to(from).set("Balance").to(balance - amount).build());
	tx.buffer(creditFor(to, amount));                          // writes wait at the client until commit
	return null;
});

// Read-only and strong: no locks, served by an up-to-date replica.
try (ResultSet rs = db.singleUse().executeQuery(query)) { render(rs); }

// Read-only and up to 15 seconds stale: the nearest replica answers without asking anyone.
try (ResultSet rs = db.singleUse(TimestampBound.ofMaxStaleness(15, TimeUnit.SECONDS)).executeQuery(query)) { render(rs); }

    Things to notice. As it opens, the client is in Virginia beside the leaders, the replicas are in three regions, and the transaction spans two splits: 63 ms. Two milliseconds of that are the client's round trips. The rest is two Paxos rounds of 30 ms, one for the other group's "prepared" and one for the commit, each waiting on a replica in Iowa. Keep the transaction inside one split and it is 32 ms, one round. That difference is the argument for interleaved tables.

    Now put all the replicas in one region. The same two transactions take 6 and 8 ms, and the database no longer survives the loss of Virginia. The 30 ms was the price of that insurance, paid on every write. Go back to three regions and move the client to Belgium: 210 ms for a one-split transaction, of which 180 is two round trips to the leaders. Code that runs read-write transactions belongs near the leaders.

    Then the reads. A strong read from Iowa costs 30 ms, since being certain of the latest data means consulting the leader. A read that accepts data up to fifteen seconds old costs 1 ms from Iowa, answered by a replica in the same region. From Belgium even the stale read costs 90 ms, as Belgium has only a witness, which votes and stores nothing. Where the data-holding replicas are, and whether a read may be stale, decide more than anything in the query.

    Where Spanner sits in CAP

    By the definitions of Chapter 10, Spanner chooses consistency. A split whose replicas can't form a majority stops accepting writes, and a replica cut off from its leader can't serve strong reads. Yet Google sells it with an availability target of 99.999% for multi-region instances, about five minutes of downtime a year. Eric Brewer, who formulated CAP and later worked at Google, addressed the apparent conflict directly in 2017. Spanner is a CP system, he wrote, and it is also so rarely partitioned that its users may treat it as available. Google runs its own fibre between its datacentres with several independent paths, so the network splits far less often than the public internet does, and in practice outages came more often from software and operator error than from partitions. CAP says what must be given up when a partition happens. It is silent on how often that is, and a great deal of money can be spent on making it seldom.

    The cost that doesn't go away is the other half of PACELC: latency. Every write waits for a majority across zones, and in a multi-region instance, across regions. The panel's figures are that cost.

    📣
    Use case: F1, and moving AdWords off sharded MySQL

    Spanner's first large customer was Google's own advertising system, and the account of that move, published in 2013 as the F1 paper, is frank about the price. AdWords had run on MySQL, with the data divided among shards by customer. As it grew, the shards had to be re-divided, a manual job whose last instance took over two years and which the team was determined never to repeat. Transactions across shards didn't exist, so application code carried the burden of keeping related rows consistent. The team built F1, a SQL layer, on Spanner, and moved the whole advertising database onto it in 2012 without stopping the business. They chose five replicas spread across the United States, so that the loss of a whole datacentre region still left a majority, and they paid for it in exactly the way this chapter predicts: the paper reports commit latencies of 50 to 150 milliseconds, far above the few milliseconds of the MySQL it replaced. The system as a whole was nonetheless no slower for users, and the reasons are a guide to using any database of this kind. The schema was made hierarchical, each customer's campaigns and adverts interleaved under the customer row, so that most transactions touched one Paxos group and avoided two-phase commit. Code written as a loop of small reads and writes, each a round trip, was rewritten to read in bulk and in parallel and to write once. Work that needed no fresh data used stale reads, served by the nearest replica. And the team stated the design choice outright: they would take higher latency for each operation in return for never again writing application code to compensate for missing transactions, on the grounds that the first can be engineered round and the second produces bugs for ever.

    ⚠️
    Common mistakes
    • A primary key that only rises. Every insert lands on the last split, and one Paxos group carries the write load.
    • Using a read-write transaction to read. It takes locks at the leaders. A read-only transaction takes none and can use any replica.
    • Side effects inside a transaction body. The body is re-run after an abort. An email sent from it is sent twice.
    • Many small round trips. With leaders in another region each one costs tens of milliseconds. Batch, and read in parallel.
    • Unrelated rows in one transaction. Spanning splits means two-phase commit. Keep rows that change together under one parent.
    • Never using stale reads. A dashboard that could tolerate ten-second-old data is paying for strong consistency it doesn't need.
    • "Spanner beats CAP." It chooses consistency, and is engineered so that the choice rarely costs anything.

    Interview drill

    Explain it simply: How does Spanner provide transactions across a globally distributed database?

    How a strong answer sounds
    Spanner splits data into key ranges and replicates each range across several zones using Paxos, so each range is a consensus group with a leader. Writes go through the leader and are committed when a majority of replicas have them. A transaction that touches a single range is just a Paxos write. A transaction that spans ranges uses two-phase commit between the leaders of the groups involved; because each participant's state is itself replicated by Paxos, a machine failure doesn't block the protocol the way it would in classic 2PC. For isolation, read-write transactions use two-phase locking at the leaders. The distinctive part is timestamps: every transaction gets a commit timestamp from TrueTime, a clock API that returns an interval guaranteed to contain the true time. The coordinator picks a timestamp at the top of the interval and waits until that time has definitely passed before acknowledging, the commit wait. That makes timestamp order match real-time order globally, which is called external consistency. Data is stored multi-versioned by timestamp, so read-only transactions can read a consistent snapshot at a timestamp from any sufficiently up-to-date replica without taking locks.

    Deeper: Your service on a multi-region Spanner instance has slow writes. How do you reason about it and what do you change?

    How a strong answer sounds
    I'd start from where the time goes. A write's latency is the round trip from the client to the split's leader, plus the Paxos round from the leader to a majority of voting replicas, which in a multi-region configuration includes at least one other region, plus commit wait, which is small. If the transaction spans splits there is also a prepare round at each other participant. So first: where are the leaders relative to the clients? If the application servers are in one region and the default leader region is another, every read in a read-write transaction and every commit crosses regions; moving the leader region next to the writers is often the biggest single fix. Second: how many round trips per transaction? Sequential reads inside a read-write transaction each go to the leader; I'd batch them, issue them in parallel, or read what I can in a preceding read-only transaction. Third: is it using two-phase commit unnecessarily? I'd check whether rows that are written together live in the same split, using interleaved tables under a common parent key, so most transactions are single-group. Fourth: contention. Lock waits and aborted-and-retried transactions look like latency; the lock statistics tables show hot rows, and a monotonically increasing key creates a hot split at the end of the range, fixed by a hashed or UUID key. Fifth: are reads using the right mode? Anything that tolerates staleness should use a bounded-staleness read from the local replica instead of a strong read or, worse, a read-write transaction. I'd confirm with traces and the transaction statistics rather than guess, and I'd set expectations: a multi-region synchronous write can't be faster than a round trip to the nearest region that completes the quorum.

    🧠 Key takeaways

    • Spanner is range-partitioned SQL data, each split replicated by a Paxos group with a leased leader.
    • A write is one Paxos round in its group. A transaction across groups is two-phase commit between leaders, made non-blocking by replication.
    • Read-write transactions lock at leaders. Commit timestamps come from TrueTime, with commit wait, giving external consistency.
    • Read-only transactions read at a timestamp from any up-to-date replica without locks. Stale reads need no leader at all.
    • Cost follows geography: distance to the leader, distance to a quorum, and whether the transaction stays in one split.
    • It is a CP system made highly available by engineering the network, and it pays for consistency in write latency.

    Check your understanding

    In Spanner, what is replicated by one Paxos group?

    Each split has its own group, leader and log. A database is many thousands of them.

    A transaction updates rows in two different splits. What does commit involve?

    Groups don't share a log, so atomicity across them needs 2PC. Recording prepare and commit in Paxos is what stops it blocking.

    Why can a read-only transaction be served by a replica that isn't the leader?

    Multi-version storage plus globally meaningful timestamps make "the data as of s" the same on every replica that is caught up to s.

    Why does Spanner's documentation warn against a primary key that increases monotonically?

    Data is range-partitioned by key. New keys that are always the largest all land in the same place.

    Which statement about Spanner and the CAP theorem is accurate?

    A minority side stops accepting writes. High availability comes from making that situation uncommon, not from escaping the theorem.
