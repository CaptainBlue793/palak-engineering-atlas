Quorums

Chapter 9 described leaderless replication in a sentence: write to several replicas, read from several, and choose the numbers so that the two sets must overlap. This chapter is about those numbers. With N replicas, a write that waits for W acknowledgements and a read that asks R replicas give a simple dial. Turn it one way and reads are fast, writes are slow and a single failure stops them. Turn it the other and writes always succeed, and a read may miss them. The rule R + W > N marks the settings where a read is certain to reach a replica holding the latest write. It is a useful guarantee and a narrower one than it sounds, and the end of the chapter covers what it doesn't promise.

Read and write quorums

Each key is stored on N replicas. Every stored value carries a version, so that two copies can be compared. A request is handled by a coordinator, which may be the client's library or whichever node received the request.

  • To write, the coordinator sends the new value to all N replicas and waits for W of them to acknowledge. Then it reports success. The remaining replicas usually receive the write a moment later, and may not receive it at all if they are down or the message is lost.
  • To read, the coordinator asks all N replicas and waits for R replies. It returns the reply with the newest version.
CompletableFuture<Void> put(String key, Versioned value) {
	var acks = replicasFor(key).stream().map(r -> r.store(key, value)).toList();    // sent to all N
	return firstK(acks, W).thenApply(done -> null);                                 // success once W have it
}

CompletableFuture<Versioned> get(String key) {
	var replies = replicasFor(key).stream().map(r -> r.fetch(key)).toList();        // asked of all N
	return firstK(replies, R).thenApply(found -> {
		Versioned newest = Collections.max(found, BY_VERSION);
		found.stream().filter(v -> BY_VERSION.compare(v, newest) < 0)
				.forEach(stale -> stale.replica().store(key, newest));               // read repair, in the background
		return newest;
	});
}

firstK is the helper from P1: it completes when k of the calls have succeeded and fails if that can no longer happen. Nothing in this code elects anybody. A replica that is down is a reply that doesn't arrive, and as long as enough others answer, the request succeeds.

R + W > N

Suppose a write was acknowledged by W replicas, and a later read hears from R replicas. If R + W is greater than N, the two groups can't be disjoint: there aren't enough replicas for them to avoid each other. At least one replica in the read group acknowledged the write, its reply carries the new version, and the coordinator, taking the newest, returns it. With N = 3, W = 2 and R = 2, any two replicas share at least one member with any other two.

When R + W is N or less, the groups can miss each other, and a read can return a value older than one already acknowledged. How often depends on how quickly the remaining replicas catch up. The setting is still legitimate, and many systems run on it, for speed.

NWROverlap?Writes surviveReads surviveSuits

One more inequality is worth knowing. If W is greater than N/2, any two write quorums overlap as well, so two writers can't both succeed on completely separate sets of replicas, and at least one replica sees both writes and can tell that they conflict.

Things to notice. With three replicas and W = R = 2, write a version and read a hundred times: no read is stale, although one replica never received the write. Lower R to 1 and read a hundred times more. About a third of the reads now return the old version, the fraction that happen to ask the one replica left behind. Put R back to 2, turn read repair on and read: the read notices that one of its two replies is older and brings that replica up to date, so the gap closes for every key that is read. Now fail two replicas. Writes are refused, correctly, since one replica isn't a quorum. Turn sloppy quorums on and write again: the write succeeds, with a stand-in holding the value and a note of whom it is for. Now bring the two failed replicas back, fail the third, and read before pressing "Hand over hints". The read reaches two of the key's replicas, R + W exceeds N, and the answer is stale. The one home replica that took the write isn't in the read set, and a stand-in is never a place that reads look.

Sloppy quorums and hinted handoff

A strict quorum counts only the N replicas that are responsible for the key. If too many of those are unreachable, the write fails, even when the cluster has dozens of other healthy machines. Dynamo's designers judged that unacceptable for a shopping cart, and loosened the rule: when a home replica can't be reached, the write goes to the next healthy node in the cluster, which stores it with a hint naming the replica it was meant for. The acknowledgements from stand-ins count towards W. When the intended replica returns, the stand-in sends it the write and deletes its copy. The arrangement is a sloppy quorum, and the delivery is hinted handoff.

It buys write availability: a write succeeds whenever any W nodes in the cluster are reachable. It costs the guarantee. The W nodes that took the write may include none of the key's home replicas, so a read of R home replicas can miss it entirely, with R + W > N satisfied on paper. A sloppy quorum is a durability device, a promise that W machines somewhere hold the data, and gives no assurance about what the next read sees. Systems differ here, and the difference matters when reading their documentation. Riak counts stand-ins towards the quorum by default. Cassandra stores hints too, but doesn't count them towards a requested consistency level, except at its weakest setting, which accepts a write if a hint alone was stored.

Read repair

A replica that missed a write stays stale until something tells it. The cheapest mechanism uses reads that are happening anyway. A coordinator that has collected R replies can see which of them are behind the newest, and sends those replicas the newer value. That is read repair, and it is the last three lines of the get method above.

It keeps frequently read keys in good shape at almost no cost. It does nothing for a key that isn't read: a value written once and left for a year can sit on fewer replicas than intended for the whole year, and be lost if those fail. So read repair is paired with a background process, anti-entropy, in which replicas compare their contents with each other and exchange what differs. Doing that comparison without shipping all the data is the subject of Chapter 24.

Quorums are not linearizable

It is tempting to read R + W > N as "strong consistency", and vendors have encouraged it. The overlap rule guarantees one thing: a read that begins after a write has completed successfully contacts at least one replica that has it. Linearizability (Chapter 11) asks for more, and strict quorums fall short in several ways.

What goes wrongWhy the overlap rule doesn't help
A read during a write, as in the figureThe write hasn't completed, so different readers may or may not see it, in any order
A write that failed part-wayIt reached one replica and was reported as failed. Nothing rolls that replica back, and a later read may return the value of a write the client was told didn't happen
Two concurrent writesDifferent replicas receive them in different orders. Whichever is kept, by timestamp or as siblings, there was never one agreed order
Sloppy quorumsThe write quorum may contain no home replica at all
A replica restored from an old backupIt rejoins with old data, and the number of replicas really holding a write falls below W

The first of these can be fixed within the quorum scheme: have every read write the newest value back to a quorum and wait for the acknowledgements before it returns, so that no later read can see anything older. Operations that depend on the current value, such as "set this only if it is still 5", can't be fixed that way. They need the replicas to agree on a single order of operations, which is consensus, and that is why Cassandra runs a Paxos round for its conditional writes while leaving ordinary ones to quorums. Chapters 15 to 18 build that machinery.

🎛️
Use case: a consistency level on every Cassandra query

Cassandra exposes the dial of this chapter directly, and for each statement. A keyspace is created with a replication factor, N, commonly three in each data centre. Every read and write then names a consistency level, which is R or W for that one request. ONE waits for a single replica. QUORUM waits for a majority of all replicas across every data centre. LOCAL_QUORUM waits for a majority of the replicas in the coordinator's own data centre, two of three, and lets the other data centres receive the write asynchronously. ALL waits for every replica and fails if any is down. The combination most production clusters settle on is LOCAL_QUORUM for both reads and writes: within a data centre, 2 + 2 exceeds 3, so a read sees every write acknowledged there, one replica can be lost without affecting either, and no request waits on a link between continents. Readers in another data centre get the data a little later, which is the "else, latency" half of Chapter 10, chosen deliberately. Teams then lower the level for particular queries where staleness is harmless, a product page's view count at ONE, say, and raise it for the few that can't tolerate it. For the operations that need more than any quorum gives, such as claiming a unique username, Cassandra offers a separate mechanism, the lightweight transaction, written INSERT … IF NOT EXISTS, which runs a consensus protocol among the replicas and costs several round trips. The documentation is plain that the two are different tools, which is this chapter's last section put into practice.

⚠️
Common mistakes
  • Calling R + W > N "strong consistency". It prevents stale reads after completed writes, and it isn't linearizable.
  • W = N for safety. One slow or failed replica then blocks every write.
  • Assuming a failed write left nothing behind. It may be on some replicas, and may be read later.
  • Relying on read repair alone. Keys that are never read are never repaired.
  • Forgetting that sloppy quorums count stand-ins. The arithmetic holds and the overlap doesn't.
  • Using a quorum read to guard a compare-and-set. Two clients can both read the old value and both write. That needs consensus.

Interview drill

Explain it simply: What does R + W > N mean, and why does it matter?

How a strong answer sounds
N is the number of replicas of each key, W is how many must acknowledge a write before it is considered successful, and R is how many must respond to a read. If R + W is greater than N, any set of W replicas and any set of R replicas share at least one member, simply because there aren't enough replicas for them to be disjoint. So a read that starts after a write has succeeded is guaranteed to hear from at least one replica that has that write, and by returning the reply with the highest version it returns the latest value. With N = 3 the usual choice is W = 2, R = 2: reads see completed writes, and either operation tolerates one replica being down. You can shift the balance: W = 3, R = 1 gives fast reads but writes that fail if any replica is down; W = 1, R = 1 is fastest and most available but reads can be stale. I'd add that the guarantee is narrower than linearizability: it says nothing about reads concurrent with a write, about partially failed writes, or about conflicting concurrent writes.

Deeper: A Dynamo-style store is configured with N = 3, W = 2, R = 2, and a client still reads a stale value after its write was acknowledged. How can that happen?

How a strong answer sounds
Several ways, and I'd go through them in order of likelihood. First, sloppy quorums: if two of the three home replicas were unreachable when the write was made, the write may have been acknowledged by one home replica plus a stand-in holding a hint. A later read from two home replicas can then miss it until hinted handoff delivers it. Second, the read might have been concurrent with the write or with read repair, in which case the guarantee doesn't apply. Third, clocks: if conflicts are resolved by last-write-wins and the writing coordinator's clock was behind, the new write may carry a smaller timestamp than the existing value, so every replica keeps the old one, and the acknowledged write is effectively discarded. Fourth, the consistency level may differ from what is assumed: a driver default of ONE, or LOCAL_QUORUM with the reader in a different data centre from the writer. Fifth, a replica may have lost data, by being restored from an older snapshot or wiped and rejoined, so the write is on fewer than W replicas. And sixth, an earlier write that partially failed may have left a value with a higher version on one replica, which then wins. To diagnose it I'd check the consistency levels used for both operations, whether hints were stored at the time, clock offsets on the nodes involved, and the timestamps of the versions on each replica. To prevent it I'd use strict quorums for this data if the store allows, monitor clock skew, and run regular anti-entropy repair.

🧠 Key takeaways

  • With N replicas, a write waits for W acknowledgements and a read for R replies, taking the newest.
  • R + W > N forces the read set and the write set to share a replica, so a read sees every completed write.
  • Writes survive N − W failures and reads N − R. Moving the dial trades one for the other, and trades both against latency.
  • Sloppy quorums with hinted handoff keep writes available by using stand-ins, and give up the overlap.
  • Read repair fixes the keys that are read. Anti-entropy fixes the rest.
  • Quorums aren't linearizable: concurrent reads, partial writes and concurrent writes all break it. Compare-and-set needs consensus.

Check your understanding

N = 5. Which setting guarantees that a read sees the latest completed write?

3 + 3 = 6 exceeds 5. The others sum to 5 or less, so a read set can avoid the write set.

N = 3, W = 2, R = 2. How many replicas can be down with both reads and writes still succeeding?

Each operation needs two of the three. With two down, neither quorum can be reached.

What does a sloppy quorum give up?

The data is on W machines, and they may not be the key's home replicas, which is where reads look.

Why isn't read repair enough to keep replicas in step?

A background anti-entropy process is needed for everything that reads don't touch.

With strict quorums and R + W > N, which of these can still happen?

The rule covers completed writes. During a write, readers can see it or not, in either order, which linearizability forbids.
