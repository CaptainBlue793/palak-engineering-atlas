RPC & Timeouts

A remote procedure call looks like a method call: inventory.reserve(sku, 2). It isn't one. It crosses a network that can lose, delay or duplicate the request, to a process that can be slow, overloaded or dead, and it can come back with no answer at all. This chapter covers the mental model the rest of the course depends on: where an RPC can fail, why every call needs a timeout, how to choose that timeout from real latency data, why deadlines beat per-hop timeouts, and the uncomfortable third outcome every distributed program has to handle: "I don't know if it happened."

  • List the places an RPC can fail and what the caller sees in each case
  • Explain why a timeout leaves the outcome unknown, not failed
  • Choose a timeout from a latency distribution and a target false-timeout rate
  • Propagate a deadline across several hops instead of resetting timeouts
  • Model success, failure and unknown as three types in Java

A remote call is not a local call

RPC frameworks work hard to make a remote call look local: you call a method on a generated stub, it serializes the arguments, sends them, waits, and deserializes the reply. That convenience hides every difference that matters. The table lists them; the rest of this course is largely about the last three rows.

PropertyLocal method callRemote procedure call
LatencyNanoseconds, very predictable0.1–1 ms in one data centre, 50–200 ms across continents, with a long tail
ArgumentsPassed by reference, nothing copiedSerialized to bytes and copied; no shared objects (P3)
VersionsCaller and callee compiled togetherDeployed separately; old and new versions talk to each other
FailureThe whole process fails togetherPartial failure: the callee can die while the caller lives
OutcomeReturns or throws, alwaysReturns, throws, or never answers
DuplicatesEach call runs exactly onceA retried request may run twice (Chapter 4)

Where an RPC can fail

Follow one call, a client asking a payment service to charge a card, and list everything that can go wrong. The request can be lost on the way. The server can crash before doing the work, or after doing it but before replying. The reply can be lost on the way back. Or nothing is lost at all, and the server is just slow: a garbage-collection pause, a queue behind a burst of traffic, a slow disk.

From the client's side, all of these failures look the same: no reply arrived in time. That is the central fact of distributed computing, and it's why the next chapters spend so long on retries, idempotency and failure detection. A call has three outcomes, not two:

  • Success: a reply arrived saying the work was done.
  • Known failure: a reply arrived saying it was not done: validation error, "not leader", "overloaded, try later". The server tells you it rejected the request before acting.
  • Unknown: no reply. The work may have happened completely, partly, or not at all, and it may still be happening.

Code that treats a timeout as a failure ("the charge didn't go through, show an error") is wrong in the case that costs the most money. Make the third outcome a type, so the compiler forces every caller to deal with it:

public sealed interface Outcome<T> {
	record Ok<T>(T value) implements Outcome<T> {}
	record Rejected<T>(String reason) implements Outcome<T> {}   // definitely not applied
	record Unknown<T>(Throwable cause) implements Outcome<T> {}  // may or may not have applied
}

Outcome<Receipt> charge(ChargeRequest req) {
	try {
		HttpResponse<String> res = http.send(post(req).timeout(Duration.ofMillis(300)).build(), ofString());
		return switch (res.statusCode()) {
			case 200 -> new Outcome.Ok<>(Receipt.parse(res.body()));
			case 400, 402, 409 -> new Outcome.Rejected<>(res.body());   // server says: not done
			default -> new Outcome.Unknown<>(new IOException("HTTP " + res.statusCode()));
		};
	} catch (HttpTimeoutException e) {
		return new Outcome.Unknown<>(e);                                 // NOT a failure
	} catch (IOException | InterruptedException e) {
		return new Outcome.Unknown<>(e);                                 // connection reset mid-call: also unknown
	}
}

Notice that a 500 or 503 is filed as Unknown too. Unless the service documents that an error status means "nothing was done", you can't assume it. A load balancer can return 502 after the backend has already committed.

Every call needs a timeout

Without a timeout, a call to a hung server waits forever, and so does the thread making it, and the request that thread was serving. A few hundred of those and your service is down because a dependency is slow. Java's defaults won't save you: java.net.http.HttpClient has no request timeout unless you set one, and the old URLConnection defaults its connect and read timeouts to 0, meaning infinite.

Choosing the number is a trade-off. Too long, and callers pile up behind a sick dependency. Too short, and you time out calls that were about to succeed: each one is wasted work, and if you retry it, extra load on a service that was merely busy. Drag the timeout and see both effects:

Latencies are simulated: a log-normal body (median about 40 ms when healthy) plus a few lost packets. GC pauses adds a 750 ms stall to 0.5% of calls; Overloaded slows every call. A call that times out was usually still processed by the server, so its outcome is unknown to the client.

The useful rule, from Amazon's Builders' Library: decide what rate of false timeouts you can accept, then read that percentile off the dependency's latency distribution. If 0.1% false timeouts is acceptable, set the timeout near the dependency's p99.9 latency, plus a little margin. That ties the number to measurements instead of a guess, and it makes clear that the timeout must be revisited when the dependency's latency changes. In the GC-pause setting you can see the trap: the p99 is fast, but 0.5% of calls stall, so a timeout set from the p99 times out on every stall.

Deadlines, not per-hop timeouts

A user request rarely makes one call. The API gateway calls the order service, which calls inventory, which calls the database. If each hop has its own fresh 1-second timeout, the user can wait far longer than a second, and worse, the inner services keep working on a request whose caller gave up long ago. A deadline fixes both: the edge sets an absolute time by which the whole request must finish, every hop passes it on, and each hop gives its own calls only the time that is left.

/** An absolute deadline on the monotonic clock. Pass it down; never reset it. */
public record Deadline(long atNanos) {
	public static Deadline in(Duration d) { return new Deadline(System.nanoTime() + d.toNanos()); }
	public Duration remaining() { return Duration.ofNanos(Math.max(0, atNanos - System.nanoTime())); }
	public boolean expired() { return remaining().isZero(); }
}

Outcome<Stock> reserve(Sku sku, int qty, Deadline deadline) {
	if (deadline.remaining().toMillis() < 5) return new Outcome.Rejected<>("deadline exceeded");   // don't start
	return inventoryClient.reserve(sku, qty, deadline.remaining());                 // budget shrinks per hop
}

The deadline is measured with System.nanoTime(), the monotonic clock, because the wall clock can jump (P5). Between machines you send the remaining duration, never an absolute wall-clock time, since the two machines' clocks disagree.

Living with "unknown"

Once a call can end in Unknown, the caller needs a plan for it. There are only a few, and every chapter that follows uses one of them:

  • Make it safe to retry. Send an idempotency key so a second attempt returns the first result instead of charging again. This is the default for writes (Chapter 4).
  • Ask. Look the result up by a client-chosen ID: "what happened to order 81's charge?" This only works if the ID was chosen before the first attempt.
  • Reconcile later. Record the attempt, show "processing" to the user, and let a background job compare your records with the other side's. Payment systems do this every night.
  • Make the operation naturally idempotent. "Set the price to £40" can be repeated safely; "add £40" cannot.
💳
Use case: the double charge

A mobile app calls POST /charges with a 10-second timeout on a train. The request reaches the server and the card is charged, but the reply is lost when the train enters a tunnel. The app shows "Payment failed, try again", the user taps again, and is charged twice. Stripe's API is designed around exactly this: clients send an Idempotency-Key header, the server stores the result of the first request under that key, and a retry with the same key gets the stored result instead of a second charge. The fix lives on both sides: the client must treat the timeout as "unknown" and retry with the same key, and the server must remember keys.

⚠️
Common mistakes
  • No timeout at all, often because the HTTP or database client's default is infinite. Set connect and request timeouts on every client.
  • Treating a timeout as a failure and telling the user "not done" when it may have been done.
  • Choosing timeouts by gut feel ("5 seconds seems safe") instead of from the dependency's latency percentiles.
  • Resetting the timeout at every hop, so the user waits for the sum, and inner services work on abandoned requests.
  • Sending wall-clock deadlines between machines. Send the remaining duration; clocks disagree.
  • Assuming a 5xx means nothing happened. Unless the API promises it, a server error is also an unknown outcome.

Interview drill

Explain it simply: Your service called another service and got a timeout. Did the operation happen?

How a strong answer sounds
I can't know from the timeout alone. The request might have been lost, the server might have crashed before or after doing the work, the reply might have been lost, or the server might still be working on it. So a timeout is an unknown outcome, not a failure. What I do next depends on the operation: if it's idempotent or I sent an idempotency key, I retry with the same key; if I chose a request ID up front, I can query for the result; otherwise I record it as pending and reconcile later. What I must not do is tell the user it failed.

Deeper: How would you choose the timeout for calls from your checkout service to the inventory service?

How a strong answer sounds
Start from data: look at inventory's latency distribution as seen by the client, including the network, and pick an acceptable false-timeout rate. If 0.1% is acceptable, the timeout sits around inventory's p99.9 plus a margin. Then check it against the caller's own budget: if checkout must answer in 800 ms and inventory is one of three sequential calls, inventory gets whatever part of the remaining deadline is left, and I'd propagate a deadline rather than set independent timeouts. I'd watch for bimodal latency, like GC pauses, where p99 is fast but a few percent of calls stall, and I'd monitor the timeout rate as its own alert, because a rising timeout rate is often the first sign the dependency is in trouble.

🧠 Key takeaways

  • An RPC adds latency, serialization, version skew and partial failure to a method call.
  • Lost request, crash before, crash after, lost reply and slow server all look identical to the caller: no reply.
  • A call has three outcomes: success, known failure, and unknown. Model unknown as its own type.
  • Every call needs a timeout; choose it from the dependency's latency percentiles and an acceptable false-timeout rate.
  • Propagate one deadline through every hop, measured on the monotonic clock and sent as a remaining duration.
  • Handle unknown with idempotent retries, lookups by client-chosen ID, or reconciliation.

Check your understanding

A client's call to a payment service times out. What does the client know about the charge?

A lost request, a crash before or after the charge, a lost reply and a slow server all look the same from the client: no reply in time.

A dependency's latency is p50 = 30 ms, p99 = 120 ms, p99.9 = 400 ms. You can accept about 0.1% of calls timing out falsely. Which timeout fits?

Pick the percentile that matches the false-timeout rate you accept (0.1% means p99.9) and add margin. The p99 would time out 1% of calls that would have succeeded.

A request passes through three services, each with its own 1-second timeout on the next call. What is the problem?

Per-hop timeouts don't share a budget. A propagated deadline gives each hop only the time left, so the chain gives up together.

Why should a deadline be sent between machines as a remaining duration rather than an absolute wall-clock time?

Clock skew between machines can be milliseconds or seconds. A remaining duration, measured locally on each side's monotonic clock, avoids it.

Which reply can a client safely treat as "definitely not applied"?

Only an explicit rejection that the server promises happens before acting is a known failure. Gateway errors, resets and timeouts are all unknown outcomes.
