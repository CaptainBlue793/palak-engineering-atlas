State Machine Replication

Suppose three machines each run a copy of the same program. Start them all in the same state, feed each of them the same commands in the same order, and make sure the program's behaviour depends on nothing except its state and the command in front of it. Then the three copies will pass through the same states and give the same answers, for ever, with no further effort. That observation is state machine replication, and it is the idea underneath every consensus-based system: etcd, ZooKeeper, Spanner, CockroachDB, Kafka's controller, every blockchain. It turns the problem of replicating an arbitrary service into the narrower problem of getting a group of machines to agree on one list. Chapters 16 to 18 are about reaching that agreement. This chapter is about what the list is, what can be put in it, and why its order is the only thing that matters.

Deterministic state machines

A state machine, in this sense, is anything that holds some state and changes it only by processing commands one at a time: a key-value store handling put and delete, a lock table handling acquire and release, a bank ledger handling transfers. It is deterministic if the new state and the output depend only on the old state and the command. Run it twice from the same start on the same commands and it does the same thing.

interface StateMachine {
	Result apply(Command command);          // must depend on nothing but this.state and command
}

The principle then has three conditions: the same initial state, the same commands, in the same order. Given those, the copies never differ. The first is easy, and the third is the work of consensus. The second hides a trap, since a great deal of ordinary code isn't deterministic, in ways that never matter on one machine.

case SetWithTtl c -> store.put(c.key(), new Entry(c.value(), Instant.now().plus(c.ttl())));

// Right: the leader decided the expiry when it accepted the command. Every replica stores the same instant.
case SetWithExpiry c -> store.put(c.key(), new Entry(c.value(), c.expiresAt()));

The replicated log

The commands are kept in a log: a numbered list to which entries are only ever added at the end. Entry 1, entry 2, entry 3, and so on. Each replica has a copy of the log and a state machine, and applies the entries to the machine strictly in order of their numbers.

The job of the consensus protocol is exactly one guarantee about this log: every replica that has an entry at position n has the same entry there, and once an entry is committed it never changes. Everything else is built on top. A replica that was down for an hour comes back, fetches the entries it missed, applies them in order and arrives at the same state as the others. A replica that is slow is behind and never different.

void applyCommitted() {                            // runs on one thread, on every replica
	while (lastApplied < commitIndex) {
		Entry entry = log.get(++lastApplied);
		Result result = machine.apply(entry.command());
		waiting.complete(entry.index(), result);       // on the leader, this answers the client
	}
}

One practical addition belongs to the state machine itself. A client that gets no reply will send its command again (Chapter 4), and the first attempt may already be in the log. So each command carries a client ID and a sequence number, and the state machine keeps, as part of its state, the last sequence number it applied for each client together with the result. A repeat is recognised when it is applied and answered from that table without being executed again. Since the table is part of the replicated state, every replica makes the same decision.

Why order is everything

If commands commuted, so that applying them in any order gave the same result, replication would be easy, and Chapter 25 shows how far that idea can be pushed. Most commands don't. "Add 50" and "double it" give different balances depending on which comes first. "Withdraw 120" succeeds after a deposit and fails before one. Two put operations on the same key leave whichever came second. So the replicas must agree on the order, and agreement on the set of commands isn't enough.

The bonus stands for any command that isn't deterministic: when each replica computes it, the first adds 1, the second 2 and the third 3, as if each had read its own clock. In "whatever order reached them", the second replica receives each pair of commands swapped and the third receives the first command last, as an unordered network might deliver them. The fee is a tenth of the balance, rounded down. The log holds 12 commands.

Things to notice. Add a deposit, a doubling and a fee, with both conditions satisfied: the three balances agree after every command. Switch to "whatever order reached them". The same three commands are on every replica, nothing was lost or duplicated, and the balances are three different numbers, since doubling 150 isn't the same as adding 50 to 200. Switch back, add a bonus, and set it to be computed by each replica: now the logs are identical, entry for entry and in order, and the balances still drift apart, by a little more with every bonus. The first failure is what consensus prevents, and the second is what the programmer has to prevent. Then take a snapshot, and look at the log: everything up to that point is replaced by one entry holding the balance, and a new replica joining would load it and replay only what came after.

Snapshots

A log that is only ever added to grows without limit, and a replica that restarts, or a new one that joins, would have to replay it from the first entry. After a year that could mean billions of commands to rebuild a state of a few megabytes.

The remedy is to save the state itself now and then. A snapshot is a copy of the state machine's whole state as it stood immediately after applying some entry n. Once it is safely stored, entries 1 to n are no longer needed and can be deleted. A replica that restarts loads the snapshot and replays the entries after n. A replica that has fallen so far behind that the leader has already discarded the entries it needs is sent the snapshot.

A snapshot mustBecause
Record the index of the last entry it includesReplay has to start at exactly the next one. One entry applied twice or skipped, and the replica has diverged
Include everything apply reads, the table of client sequence numbers among itOtherwise a replica restored from it would execute a retried command a second time
Be taken at one point in the log, though the machine goes on applying meanwhileA copy that mixes the state before and after entry n + 1 corresponds to no log position at all
Be written completely before any log is discardedA crash halfway through must leave either the old snapshot and the full log, or the new snapshot

The third row is the hard one in practice. Stopping the state machine while gigabytes are written out would stall the service, so implementations take a consistent view some other way: by forking the process, so that the operating system's copy-on-write keeps the child's memory frozen while the parent carries on, which is how Redis saves to disk (the OS course covers the mechanism), or by keeping the state in a structure that supports cheap point-in-time views, such as an LSM tree or a copy-on-write B-tree.

Snapshots also show that there are two things one can replicate. State machine replication ships the commands, and every replica executes them. Chapter 14's alternative ships the resulting state: the primary executes, and sends the backup the new values. Shipping commands is compact and needs determinism. Shipping state tolerates any non-determinism, since only one machine computes, and can be much larger. Many systems mix the two: the log carries commands whose non-deterministic parts have already been resolved by the leader, which is shipping a little state inside each command.

Use case: "Paxos Made Live", and what the principle leaves out

In 2007 three Google engineers published an account of rebuilding Chubby, the company's lock service, on a replicated state machine of their own making. The paper is called "Paxos Made Live", and its theme is the distance between the principle, which fits in a paragraph, and a system that can be trusted with production data. They reported that the consensus algorithm, the part the literature is about, was the smaller share of the work. Snapshots were among the hardest parts. The consensus layer knew about the log and nothing about the application's state, and the application knew about its state and nothing about the log, so the two had to be made to cooperate: the application takes a snapshot that corresponds to a precise log position while continuing to serve requests, tells the log which position that was, and only then may the log be truncated, with every step safe against a crash in the middle. A replica that fell too far behind had to be brought back with a snapshot and the log that followed it, fetched from different places. Determinism got the same treatment. Since nothing in the principle detects a replica that has quietly diverged, they added a check: the leader periodically computes a checksum of its state and has the replicas compare theirs. The check found real divergences, and the causes they list are instructive: an operator's mistake during an upgrade, and what looked like faulty hardware corrupting memory. Neither is in any model of the algorithm. They also describe the disk of a replica being wiped and the replica rejoining as though it had forgotten promises it had made, which the protocol's proof assumes never happens. The paper's conclusion is one the rest of this course bears out: the algorithm gives you agreement on a log, and a production replicated state machine is that plus snapshots, membership changes, corruption checks and a great deal of testing.

⚠️
Common mistakes
  • Reading the clock, or generating a random value, inside apply. Each replica gets its own answer.
  • Applying an entry before it is committed. If the entry is later replaced, the state machine can't be un-applied.
  • Applying committed entries on several threads without proving the commands independent.
  • No de-duplication of client retries, or a de-duplication table kept outside the replicated state.
  • A snapshot that leaves out part of the state, or doesn't record the log position it corresponds to.
  • Never comparing replicas. Divergence is silent, and a periodic checksum is the only thing that finds it.

Interview drill

Explain it simply: What is state machine replication?

How a strong answer sounds
It is a way of replicating any deterministic service. You model the service as a state machine: it has state, and it changes only by applying commands one at a time. If several replicas start in the same state and apply the same sequence of commands in the same order, and the machine is deterministic, they end up in identical states and produce identical outputs. So the replication problem reduces to getting the replicas to agree on one ordered log of commands, which is what a consensus protocol such as Raft or Paxos does. A client's command goes to the leader, is appended to the log, replicated to a majority, and only once it is committed is it applied to the state machine and the result returned. A replica that falls behind just replays the log. The two things you have to take care of yourself are determinism, so nothing in apply may depend on local clocks, randomness, thread timing or iteration order, and log growth, which is handled by taking snapshots of the state and discarding the log before them.

Deeper: Two replicas of your replicated key-value store are found to hold different values for a key, though their logs are identical. How could that happen, and how would you find the cause?

How a strong answer sounds
If the logs are identical and the states differ, either the state machine isn't deterministic or the state was damaged outside the log. I'd go through the candidates. Non-determinism in apply: a time-to-live computed from the local clock, an ID or tie-break from a random generator, iteration over an unordered map when a command touches many keys, floating-point results that differ between CPU types or compiler versions, or commands applied on multiple threads. Version skew: the replicas ran different releases at some point, and the two releases handle some command differently, so the same entry produced different states. Snapshot problems: a snapshot that omitted part of the state, or was taken while applies were in progress so that it matches no log index, or replay that started from the wrong index after loading one, so an entry was applied twice or skipped. Duplicate handling: a retried command executed twice on a replica whose de-duplication table wasn't in its snapshot. And outside the model entirely: disk or memory corruption, or someone modifying a replica's data directly. To find it, I'd first establish when they diverged, by replaying the log from the last known-good snapshot on a test machine and comparing state checksums at intervals, a bisection over the log index. Once I have the first entry after which they differ, the command type usually points at the code path. To prevent a recurrence I'd add a periodic checksum comparison between replicas, as Chubby did, and a test that replays recorded logs through the state machine twice, in different processes and on different builds, and asserts identical results.

🧠 Key takeaways

  • Same start, same deterministic commands, same order: the replicas stay identical. Replication reduces to agreeing on a log.
  • Determinism has to be engineered: no clocks, randomness, unordered iteration, thread races or outside calls inside apply.
  • An entry is applied only after it is committed, in index order, on every replica.
  • Most commands don't commute, so agreeing on the set of commands isn't enough. The order is the state.
  • Client retries are de-duplicated by a table that is itself part of the replicated state.
  • Snapshots bound the log. Each records the index it covers and everything apply depends on.

Check your understanding

Which three conditions make replicas of a state machine stay identical?

Nothing else is needed, and losing any one of the three lets the copies diverge.

A command sets a key to expire "in 60 seconds". How should a replicated state machine handle it?

Replicas apply the entry at different moments, on different clocks. The value has to be decided once and carried in the command.

Why isn't it enough for replicas to agree on the set of commands?

"Add 50, then double" and "double, then add 50" start and end in different places.

Why is an entry applied to the state machine only after it has been committed?

Commitment is the promise that the entry will stay at that index. Before it, the result could turn out to belong to a history that never happened.

A snapshot is taken after applying entry 5,000. What must it record besides the data?

Replay must resume at exactly entry 5,001, with everything in place that later commands depend on.
