Paxos

Chapter 15 reduced replication to one requirement: the replicas must agree on what goes in each position of a log. Chapter 14 got agreement by appointing a view service to decide, which only moved the problem. Paxos is the algorithm that solves it outright. A group of machines, any of which may crash or be slow, with messages that may be delayed, lost or repeated, and with no outside authority, settles on a single value, and once it has, nothing that happens afterwards can change the choice. Leslie Lamport devised it in 1989. It is two rounds of messages and two rules for the machines that vote, and it has a reputation for being hard to understand that comes mostly from how it was first explained. This chapter covers the basic algorithm, which decides one value, and then how it is extended to decide a whole log.

The problem

Several machines each may propose a value. Consensus means choosing one of them, with three properties.

  • Agreement: only one value is ever chosen.
  • Validity: the chosen value is one that somebody proposed.
  • Termination: eventually a value is chosen.

Paxos guarantees the first two under all conditions: any number of crashes, any delays, any lost or duplicated messages. It guarantees the third only when things are calm enough, for long enough, that a majority of the machines can exchange a few messages without interruption. That division isn't a weakness of Paxos in particular. Chapter 39 shows that no algorithm can promise all three in a network with unbounded delays, and the sound response is the one Paxos makes: never be wrong, and make progress whenever conditions allow.

Roles

The algorithm is described in terms of three roles. A real server usually plays all of them at once.

RoleWhat it doesWhat it must remember across a crash
ProposerTries to get a value chosen, by running the two phases belowNothing. It can start again with a higher number
AcceptorVotes. A value is chosen when a majority of the acceptors have accepted it in the same proposalThe highest number it has promised, and the last proposal it accepted. Both go to disk before it replies
LearnerFinds out what was chosen, and acts on itNothing

Every attempt by a proposer carries a proposal number, also called a ballot. The numbers must be unique and totally ordered, which is arranged by pairing a counter with the proposer's ID, exactly the tie-broken timestamp of Chapter 7. A higher number means a later attempt, and the acceptors use the numbers to ignore proposers that are out of date.

Phase 1: prepare and promise

A proposer doesn't begin by proposing its value. It begins by asking permission, and by finding out what has already happened.

  • The proposer picks a number n, higher than any it has used or seen, and sends Prepare(n) to the acceptors.
  • An acceptor that has made no promise to a higher number replies with a promise: it will accept nothing numbered below n from now on. With the promise it reports the highest-numbered proposal it has already accepted, if there is one. An acceptor that has promised a higher number refuses.

If a majority promise, the proposer goes on. Phase 1 has done two things for it. It has shut out every lower-numbered proposal at a majority of acceptors, and it has shown the proposer any value that might already have been chosen.

Phase 2: accept and accepted

  • The proposer now decides what value to put forward, and it isn't free to choose. If any promise reported an accepted proposal, it must use the value of the highest-numbered one. Only if none did may it use its own value. It sends Accept(n, v) to the acceptors.
  • An acceptor accepts the proposal unless it has since promised a higher number. It records (n, v) as its accepted proposal and says so.

When a majority of acceptors have accepted proposal n, its value is chosen.

final class Acceptor {
	private long promised = -1;           // the highest number promised
	private Proposal accepted;             // the last proposal accepted, or null

	synchronized Promise onPrepare(long n) {
		if (n <= promised) return Promise.refused(promised);
		promised = n;
		persist();                          // on disk before the reply leaves: a promise forgotten is a promise broken
		return Promise.granted(accepted);
	}

	synchronized boolean onAccept(long n, Value v) {
		if (n < promised) return false;
		promised = n;
		accepted = new Proposal(n, v);
		persist();
		return true;
	}
}

// The proposer's one rule, applied to the promises of a majority
Value valueToPropose(List<Promise> promises, Value mine) {
	return promises.stream().map(Promise::accepted).filter(Objects::nonNull)
			.max(Comparator.comparingLong(Proposal::number))
			.map(Proposal::value)
			.orElse(mine);
}

The chosen value has survived. Then try for a livelock: let the proposers prepare alternately, each one's prepare making the other's accept fail. No value is chosen and nothing has gone wrong, which is the safe way for consensus to fail.

    Why it's safe

    The claim is that once a value is chosen, every later proposal carries that same value, so no other can ever be chosen. The argument is short.

    Suppose value v was chosen by proposal number n: a majority of acceptors accepted (n, v). Take the next higher-numbered proposal that gets as far as phase 2, say number m. Its proposer collected promises from a majority. Two majorities share at least one acceptor (Chapter 12), so at least one of those promises came from an acceptor that had accepted (n, v). It must have accepted before promising m, since after promising m it would have refused the lower number n. So its promise reported (n, v). No promise can have reported anything numbered between n and m, since m is the next proposal to reach phase 2. The highest-numbered proposal the proposer saw was therefore (n, v), and the rule forced it to propose v. The same reasoning then applies to the proposal after m, and to every one after that.

    Part of the algorithmWhat would break without it
    Majorities, in both phasesTwo proposers could each complete with separate groups of acceptors, and choose different values
    The promise not to accept lower numbersAn old proposal could complete after a newer one had looked and seen nothing
    Reporting the accepted proposal with the promiseA new proposer couldn't know that a value might already be chosen
    Adopting the highest-numbered value seenA new proposer would overwrite a chosen value with its own
    Writing to disk before replyingAn acceptor that crashed and restarted would forget its promise, and act as a second, different voter

    Termination is the property that can fail. Two proposers can keep outbidding each other for ever, each new prepare invalidating the other's accept, as the panel shows. Real systems avoid it by having proposers wait a random time before retrying, or, better, by arranging that only one machine proposes at a time. That arrangement is the step from Paxos to something usable.

    Multi-Paxos

    The algorithm above chooses one value. A replicated log needs a value chosen for position 1, another for position 2, and so on without end. The direct approach runs a separate instance of Paxos for each position, at two round trips each. Multi-Paxos removes most of that cost with one observation: phase 1 doesn't mention any value. It only establishes a proposer's right to propose.

    So a proposer can run phase 1 once, with one number, for every position from here on. If a majority promise, it is the leader. From then on each client command needs only phase 2: one Accept to the acceptors, one round trip, and the command is chosen for the next position. The leader keeps this up until another machine suspects it has failed and runs phase 1 with a higher number. The acceptors' promises to the newcomer cut the old leader off: its next Accept is refused, and it learns that it has been replaced.

    A new leader's phase 1 has one more duty. The promises it receives report, for every position, anything the acceptors had accepted. Where a position has an accepted value, the new leader must re-propose that value, by the usual rule, since the old leader may have got it chosen. Where there is a gap, with later positions filled, it proposes a command that does nothing, so that the log has no holes and can be applied in order.

    Basic PaxosMulti-Paxos
    DecidesOne valueA value for each position of a log
    Round trips for each valueTwoOne, while the leader is stable
    Who proposesAnyone, at any timeThe leader. Others forward to it

    The combination, a leader chosen by phase 1 with a proposal number acting as its term, followed by a stream of phase 2 messages, should look familiar from Chapter 13 and Chapter 14. It is a primary with backups, in which the view change is done by the replicas themselves and is safe by the argument above. The papers left a great deal of Multi-Paxos unspecified, and every implementation filled the gaps in its own way. Raft, the subject of the next two chapters, is the same idea written down completely, with the leader at the centre from the start.

    🪶
    Use case: Cassandra runs a Paxos round for one statement

    Cassandra is a leaderless store built on quorums (Chapter 12), and quorums can't do a compare-and-set: two clients that both read "this username is free" will both write it. In version 2.0, in 2013, Cassandra added what it calls lightweight transactions, statements such as INSERT … IF NOT EXISTS and UPDATE … IF balance = 100, and implemented them with single-decree Paxos, run among the replicas of the one partition involved, with no leader. The node that receives the statement acts as proposer. It sends a prepare to the replicas with a timestamp-based proposal number and waits for promises from a quorum. If the promises show a proposal that an earlier coordinator left half finished, it first completes that one, which is the adopt-the-highest rule at work. It then reads the current row from a quorum to evaluate the condition. If the condition holds, it sends the accept with the new values, and when a quorum has accepted, a final commit message makes the write visible. That is four round trips where an ordinary write takes one, and Cassandra's documentation is direct about the cost and tells users to keep such statements for the few operations that need them. Under contention the livelock from this chapter is visible too: competing coordinators for the same partition invalidate one another's proposals, and the client sees timeouts, which Cassandra mitigates with randomised back-off. Later versions reworked the protocol to save round trips. Running Paxos without a leader suits Cassandra's design, where any node can coordinate any request, and the price shows why the systems of the next two chapters elect one.

    ⚠️
    Common mistakes
    • A proposer sending its own value in phase 2 when a promise reported an accepted one. That is the bug that loses chosen values.
    • An acceptor replying before its state is on disk. After a crash it votes again as if it had never promised.
    • Proposal numbers that can collide, such as a bare counter kept by each proposer.
    • Treating "accepted by one acceptor" as "chosen". Only a majority on the same proposal chooses.
    • Retrying at once after a refusal. Two proposers doing so can block each other indefinitely. Back off by a random time.
    • Changing the set of acceptors casually. Majorities are counted over a fixed membership, and changing it is a protocol in itself.

    Interview drill

    Explain it simply: How does Paxos reach agreement on a value?

    How a strong answer sounds
    In two phases, each needing a majority of the acceptors. In phase one, a proposer picks a proposal number higher than any it has seen and sends a prepare to the acceptors. Each acceptor that hasn't promised a higher number promises not to accept anything lower, and reports the highest-numbered proposal it has already accepted, if any. If the proposer gets promises from a majority, it moves to phase two: it must propose the value from the highest-numbered accepted proposal that was reported to it, and only if none was reported may it propose its own value. It sends an accept with that number and value, and each acceptor accepts unless it has since promised a higher number. Once a majority has accepted the same proposal, the value is chosen. It is safe because any two majorities overlap: a later proposer's phase one must reach at least one acceptor that accepted the chosen value, so the later proposer is forced to re-propose that value. So once chosen, the value can't change. What Paxos doesn't guarantee is progress under contention, since competing proposers can keep pre-empting each other, which is why practical systems elect a stable leader.

    Deeper: Why must a proposer adopt a value it sees in a promise, even if that value was accepted by only one acceptor and so was never chosen?

    How a strong answer sounds
    Because the proposer can't tell the difference between "accepted by one acceptor and not chosen" and "accepted by a majority and chosen". It hears from a majority, not from everyone. Say there are five acceptors and the proposer hears from three. One of them reports having accepted value X at proposal 4. The two acceptors it didn't hear from might both have accepted X at proposal 4 as well, which would make three, a majority, so X might be chosen. Or they might not. From the proposer's position both situations look identical, and if it proposed its own value in the case where X was in fact chosen, it could get a different value chosen and break agreement. So the rule is conservative: any accepted value it sees might be chosen, so adopt it, and if several are reported, take the highest-numbered, since by the invariant any proposal numbered above a chosen one carries the chosen value. The cost of the rule is only that sometimes a value that wasn't chosen gets carried forward, and the proposer's own value loses. That is perfectly acceptable: validity only requires that the chosen value was proposed by somebody. The original proposer simply tries again in the next instance, which in Multi-Paxos means the next log position.

    🧠 Key takeaways

    • Consensus means one value chosen, from those proposed, eventually. Paxos never breaks the first two, and achieves the third when the network is calm.
    • Phase 1: a proposer's numbered prepare wins promises from a majority, each reporting what that acceptor has already accepted.
    • Phase 2: the proposer must propose the highest-numbered value reported, or its own if there was none. A majority accepting it chooses it.
    • Safety comes from overlapping majorities: any later proposer is bound to see a chosen value and carry it forward.
    • Acceptors must persist their promises and acceptances before replying.
    • Multi-Paxos runs phase 1 once to establish a leader, then one round trip for each log entry.

    An acceptor has promised proposal number 7. It receives Prepare(5). What does it do?

    A promise for 7 is a promise to ignore everything lower. The proposer learns that it is out of date and must use a higher number.

    A proposer wanting value B receives three promises. Two report nothing accepted, and one reports the accepted proposal (4, "A"). What must it send in phase 2?

    A might already be chosen by acceptors it didn't hear from. It has to carry A forward.

    When is a value "chosen" in Paxos?

    Promises grant the right to propose. Only acceptances by a majority, for one proposal, choose.

    Two proposers keep sending prepares with ever higher numbers, each causing the other's accept to be refused. Which property is being violated?

    Paxos stays safe and stops making progress. A random back-off, or a single leader, restores it.

    What does Multi-Paxos save, compared with running basic Paxos for every log entry?

    Phase 1 carries no value, so one prepare can cover every later position, until the leader changes.
