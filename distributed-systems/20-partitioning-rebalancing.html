Partitioning & Rebalancing

Replication copies the same data to several machines. Partitioning does the opposite job: it divides the data, so that each machine holds only a part and the whole can be larger than any one of them. The two are nearly always used together, each partition being replicated on a few nodes by one of the methods of the last ten chapters. Chapter 19 covered one way of deciding which key goes where. This chapter looks at the system around that decision. How are the partitions cut, by ranges of keys or by hash? What happens when one of them receives far more traffic than the rest? How does a cluster move partitions between machines as it grows, without stopping? And how does a request find the right machine, when the answer changed a minute ago?

Range partitioning

Sort all the keys, and cut the sorted sequence into contiguous pieces: keys from A to F in one partition, G to M in the next, and so on. The system keeps a small table of the boundaries. Different products call the pieces tablets, regions, ranges or shards, and they are the same thing.

The great advantage is that keys which are close in order are stored together. A query for "all orders of customer 5512 in March", with a key that begins with the customer and continues with the date, reads one run of adjacent rows from one partition. Boundaries don't have to be evenly spaced: a partition that grows too big is split in two at a middle key, and the table gains a row.

The weakness comes from the same property. If the keys being written are close together, the writes are too. The classic case is a key that begins with a timestamp. Every new record has a key larger than every existing one, so every write goes to the last partition, and one machine does all the work while the rest are idle.

Hash partitioning

Hash each key, and partition on the hash: by ranges of the hash value, or by a ring (Chapter 19). A good hash scatters similar keys across the whole space, so sequential keys, and almost any other pattern, are spread evenly over the partitions.

The cost is the mirror image of range partitioning's benefit. Adjacent keys are now nowhere near each other, and a range query has to be sent to every partition and the results merged. Many stores offer a compromise: a key in two parts, of which the first is hashed to choose the partition and the second orders the rows inside it. All of one customer's orders are then in one partition, sorted by date, and different customers are scattered.

Hot spots

A partition that receives much more load than the others is a hot spot, and it limits the whole system: the cluster's capacity is that of its busiest partition's machine, whatever the total. Partitioning aims to spread load, and there are three ways it fails to.

CauseExampleRemedy
Keys that arrive in order, under range partitioningTimestamps, auto-increment IDsPut something well spread in front: a hash of part of the key, a tenant ID, or a small "bucket" number. Range scans over time then need one query for each bucket
One key far more popular than the rest, under any schemeA celebrity's account, a viral post, a default value everyone sharesNo hash helps, since one key lives in one place. Split the key by adding a suffix, cache it in front, or treat it specially in the application
A partition that has grown too largeOne tenant with a thousand times the data of the othersSplit by size, and place the halves on different machines. Some systems split by load as well

Rebalancing strategies

Data grows and machines are added, so the assignment of partitions to nodes has to change over time. Rebalancing is that change, and it has three requirements: afterwards the load should be shared fairly, the system should keep serving reads and writes during it, and no more data should move than is necessary. P6 showed what violating the third looks like. The three strategies in real use differ in what a "partition" is to begin with.

Things to notice. With 24 fixed partitions, adding a node moves a few whole partitions, close to the minimum, and each batch of writes simply makes every partition larger: write several batches and they pass 10 GB with no way of splitting them. With eight partitions for each node, a new node cuts existing partitions in half and takes a half of each, so the partitions get smaller as the cluster grows. With key ranges and evenly spread keys, partitions split as they pass 10 GB and stay near that size however much is written. Now choose timestamps as the key and write: the whole batch lands in the last partition, on one node. That partition splits into pieces, most of the pieces are then moved to other nodes, and the next batch does it all again. All the writes go to one machine, and a good part of them is then written a second time by the rebalancer. Adding nodes doesn't help in the slightest.

Moving a partition

Whatever the strategy, rebalancing comes down to moving one partition from one node to another while clients go on using it. The steps are the same in almost every system, and the same as those an online schema change uses within one database.

One question divides operators: should rebalancing start automatically? Automatic is convenient, and combined with automatic failure detection it can turn a small problem into a large one. A node that is slow under load looks dead (Chapter 5). The cluster starts copying its partitions elsewhere, the copying adds load to the remaining nodes, one of those now looks dead, and so on. Many systems therefore compute the plan automatically and wait for a person to approve it, or limit sharply how much may move at once.

Request routing

A client has a key. Which machine should it talk to? The mapping from partitions to nodes changes with every rebalance and every failover, so the answer has to be looked up, and there are three places to put the lookup.

ApproachHow a request finds its nodeExtra hop?Examples
Ask any nodeEvery node knows the whole map. The one contacted handles the request or forwards itSometimesCassandra, Riak, with the map spread by gossip
A routing tierClients talk to a proxy that knows the map and forwards each requestAlwaysMongoDB's mongos, most sharding proxies
A partition-aware clientThe client library fetches the map, caches it, and connects straight to the right nodeNoKafka, HBase, Redis Cluster clients

The map itself has to live somewhere authoritative. Systems that favour consistency keep it in a small consensus-backed store, ZooKeeper or etcd or a Raft group of their own (Chapter 31), and everyone else reads it from there. Systems that favour availability spread it by gossip (Chapter 23) and accept that nodes may briefly disagree.

Either way, any cached copy of the map can be out of date, and the design has to expect that. The rule is that the node receiving a request checks that it really owns the partition, and if it doesn't, says so. The sender refreshes its map and tries again.

Response send(Request request) {
	for (int attempt = 0; attempt < 3; attempt++) {
		Partition p = map.partitionFor(request.key());          // from our cached copy of the map
		Response r = p.owner().call(request, p.epoch());
		if (!r.wrongNode()) return r;
		map = metadata.fetch();                                // the partition has moved: our copy was stale
	}
	throw new RoutingException(request.key());
}

// On every node, before doing any work for a request
if (!owned.contains(request.partition()) || request.epoch() < epochOf(request.partition()))
	return Response.wrongNode(currentOwnerHint(request.partition()));

Use case: Redis Cluster's 16,384 slots

Redis Cluster is a compact example of the fixed-partition strategy and of client-side routing, with every part visible in its protocol. The key space is divided into exactly 16,384 hash slots, a number fixed in the design and independent of how many machines there are. A key's slot is a 16-bit checksum of the key, CRC16, taken modulo 16,384. Each primary node is assigned a set of slots: with three nodes, roughly 5,500 each. To add a node, an operator moves some slots to it, and to remove one, moves its slots away. Nothing is ever re-hashed, since a key's slot never changes, only the slot's owner. Clients are partition-aware. A client fetches the table of slots and nodes from any node, caches it, and sends each command straight to the owner. When its table is stale, the node it contacts replies with a redirection that names the slot and the right address, MOVED 3999 127.0.0.1:6381, and the client updates its table and retries. While a slot is partway through being moved, some of its keys are on the old node and some on the new. A request for a key that has already gone gets a different redirection, ASK, which means "try there for this one request, and don't update your table yet". Since commands touching several keys only work if all the keys are in one slot, Redis lets the application control placement: if a key contains a part in braces, as in {user1000}.cart and {user1000}.profile, only that part is hashed, so related keys can be forced into the same slot. That is the two-part key of this chapter in another form: one part decides the partition, and the application chooses what goes in it.

⚠️
Common mistakes
  • Range partitioning on a key that only increases. Every write goes to the last partition.
  • Too few fixed partitions. They can't be split later, and each grows with the data. Choose the count for the cluster you expect in several years.
  • Assuming a hash removes hot keys. It spreads different keys. One popular key is still in one place.
  • Fully automatic rebalancing on top of automatic failure detection, so that a slow node sets off a cascade of copying.
  • Trusting a cached routing table. The receiving node must verify ownership and the epoch on every request.
  • Forgetting that queries across partitions are expensive. A scan or a join that touches every partition is as slow as the slowest of them.

Interview drill

Explain it simply: What is the difference between range partitioning and hash partitioning?

How a strong answer sounds
Range partitioning keeps keys in sorted order and assigns contiguous ranges of them to partitions, with a table of the boundaries. Keys that are close together are stored together, so range scans, such as all events for a user in a time window, hit one partition or a few adjacent ones, and a partition that grows too big can be split at a middle key. The danger is skew: if writes use sequential keys such as timestamps, they all go to the last partition and one node takes the entire write load. Hash partitioning applies a hash function to the key and partitions on the hash, so even sequential or clustered keys are spread uniformly. That fixes the skew from key ordering but destroys locality: a range query has to go to every partition. A common compromise is a compound key, where the first part is hashed to pick the partition and the remaining columns sort the rows inside it, which gives efficient scans within one partition key. Neither helps with a single extremely hot key, which lives in one partition under either scheme.

Deeper: How would you move a partition from one node to another with no downtime and no lost writes?

How a strong answer sounds
In phases, keeping the source authoritative until a short, well-defined hand-over. First, the destination is given a snapshot of the partition, copied in the background while the source carries on serving reads and writes. Second, since writes continued during the copy, the destination catches up by applying the source's log of changes from the snapshot's position onwards; if the partition is replicated with Raft or similar, this is simply adding the destination as a learner replica. Third, when the destination is close to current, comes the cut-over: the source stops accepting writes for that partition for a moment, ships the final entries, and ownership transfers. That transfer must be a single atomic decision in an authoritative place: a metadata update in a consensus store, or a membership change in the partition's own consensus group, with the partition's epoch incremented. Fourth, routing is updated: clients and proxies learn the new location, and because some will have stale maps, the old owner must reject requests for the partition, carrying the old epoch, with a redirect, and clients retry after refreshing. Finally the old copy is deleted, after a delay. The things that go wrong are a source that keeps accepting writes after the hand-over, which the epoch check prevents; a hand-over started when the destination is too far behind, making the write pause long, so I'd gate it on lag; and the copy itself overloading the source, so I'd throttle it.

🧠 Key takeaways

  • Partitioning divides data so that the whole can exceed one machine. Each partition is usually replicated as well.
  • Range partitioning keeps neighbours together and suits scans. Hash partitioning spreads keys and loses the order.
  • Hot spots come from keys written in order, from single popular keys, and from oversized partitions. Each needs its own remedy.
  • Rebalance by moving whole partitions: a fixed number of them, ones that split as they grow, or a fixed number for each node.
  • A partition moves by snapshot, catch-up and a brief hand-over under a new epoch.
  • Requests are routed by any node, a proxy or the client. Every routing table can be stale, so the receiving node checks and redirects.

Check your understanding

A table is range-partitioned on a key that starts with the event's timestamp. What happens under heavy writing?

New keys are always the largest. Put a hashed or bucketed prefix in front to spread them.

What does hash partitioning give up, compared with range partitioning?

The hash that spreads keys evenly also destroys their order.

In the fixed-number-of-partitions strategy, what happens when a node is added?

The mapping from key to partition is permanent. Only the mapping from partition to node changes.

A client's cached routing table says partition 7 is on node A, and it has just moved to node C. What should happen when the client sends a request to A?

The owner check, with the partition's epoch, is what makes stale routing harmless.

Why is fully automatic rebalancing risky when combined with automatic failure detection?

The response to a suspected failure adds load, which produces more suspected failures.
