Primary–Backup Replication

Chapter 9 introduced the single leader in outline, and Chapter 13 showed how hard it is to be sure there is only one. This chapter puts the two together into a complete protocol, the oldest and simplest design for a replicated service that never loses an acknowledged write. One server, the primary, handles every request, and sends each to a backup before answering. A separate, small service decides who is primary, and announces every change as a numbered view. The rules are few, and each exists to close a specific hole: a backup promoted without the data, a primary that doesn't know it has been replaced, a client that is told "done" for an operation only one machine has. Working through them is the best preparation for Paxos and Raft, which solve the same problems without needing the separate service.

The protocol

There are three kinds of participant. Clients send operations. Servers hold the state, and at any moment one is the primary, one is the backup, and any others are idle spares holding nothing. A view service watches the servers and decides which is which.

The handling of one operation is four steps, and their order is the protocol.

// On the primary
synchronized Reply handle(ClientOp op) {
	if (!view.isPrimary(me)) return Reply.wrongServer(view.primary());
	if (view.hasBackup()) {
		Ack ack = backupOf(view).forward(view.number(), nextIndex, op);    // blocks: no reply to the client without it
		if (ack.staleView()) {                                           // the backup knows a newer view than we do
			view = viewService.current();
			return Reply.wrongServer(view.primary());
		}
	}
	Result result = state.apply(op);
	nextIndex++;
	return Reply.ok(result);
}

// On the backup
synchronized Ack onForward(long viewNumber, long index, ClientOp op) {
	if (viewNumber != view.number() || !view.isBackup(me)) return Ack.staleView();
	if (index == nextIndex) { state.apply(op); nextIndex++; }        // a repeat of the last operation is simply acknowledged again
	return Ack.ok();
}

Three properties follow from that order. An acknowledged operation is on both servers, so losing either loses nothing. The two servers apply the same operations in the same order, since the primary chooses the order and handles one operation at a time. And a server that isn't the primary answers no client, which makes reads as well as writes linearizable: there is one place that answers, and it has everything.

Operations must be deterministic for this to work. If applying "set the expiry to now plus an hour" reads each machine's own clock, the two copies drift apart. Either the primary resolves such values first and forwards the result, or it forwards the resulting state in place of the operation. Chapter 15 takes that up.

Failover

Each server sends the view service a short message, a ping, several times a second. A server that misses several in a row is taken to be dead, with all the uncertainty Chapter 5 attached to that judgement.

What the view service seesWhat it doesWhy
The backup is goneMakes an idle server the new backup. The primary copies its whole state to itWithout a backup, one more failure loses everything
The primary is gonePromotes the backup to primary, and makes an idle server the new backupThe backup is the only other server with the state
Both are gone at onceNothing. The service is unavailable until one of them returns with its stateAn idle server has no data. Promoting it would silently replace the service's contents with nothing
A server has restartedTreats it as idle, whatever it was beforeIts memory is gone, or out of date

The second row holds the rule that keeps the data safe: only the backup of the current view may become the next primary. The third row is the price of that rule, and of the design. With two copies of the state the service survives one failure at a time, with a pause in between to copy the state to a new backup. Two failures in quick succession stop it.

Views and view changes

Each arrangement of primary and backup is a view, and views are numbered: view 1 has S1 as primary and S2 as backup, view 2 has S2 as primary and S3 as backup, and so on. The number is a logical clock in the sense of Chapter 7. Every forwarded operation carries it, and it is how a server recognises that the sender is out of date, or that it is itself.

The view service obeys one more rule, which looks fussy and matters a great deal: it doesn't move to a new view until the primary of the current view has acknowledged that view. Suppose it didn't wait. View 2 makes S2 primary with S3 as its fresh backup, and S2 begins copying the state across. Before the copy is finished, the view service loses sight of S2 and moves on to view 3, promoting S3. S3 is now primary with half the data, or none. Waiting for the primary's acknowledgement, which the primary gives only once its backup is ready, makes every view hand a complete copy of the state to the next.

The view number also deals with the stale primary of Chapter 13. A primary that is cut off from the view service may be replaced without knowing. It still receives requests from clients that haven't heard either. Follow what happens when it tries to serve one: it must forward the operation to its backup and wait. Its backup is the server that has just been promoted, which knows the new view number, sees the old one on the forwarded message, and refuses. The old primary can't finish the operation, learns from the refusal that the view has changed, and sends the client elsewhere. It was stopped by the protocol's first rule, and no timing assumption was needed: a primary can't act alone.

"A client writes" goes to whichever server the view service currently names as primary. "A client with an old view" goes to a server that still believes it is primary after being replaced. A server cut off from the view service can still exchange messages with clients and with the other servers. A restarted server has lost its memory and comes back idle.

Things to notice. Write twice and both operations appear on S1 and S2. Crash S1 and write again: there is no answer, since the view service hasn't noticed yet. Let it check its pings, and it moves to view 2, with S2 as primary and S3 as backup, and S3 receives a copy of everything S2 has. Now cut the primary off from the view service and let the service check again. It promotes the backup, and for a while two servers believe they are primary, which is the situation Chapter 13 warned about. Send a write from a client with the old view. The old primary forwards it to the server it thinks is its backup, that server refuses, and the write fails cleanly with nothing changed. Finally, reset, crash the backup and the primary one after the other without letting the view service react in between. It has nobody to promote, and says so. The idle server is healthy and is no use, since it holds nothing.

Chain replication

Primary–backup with one backup tolerates one failure. More backups tolerate more, and the primary then has to forward to all of them and collect all their answers. Chain replication, published in 2004, arranges the servers differently: in a line.

  • Writes go to the first server, the head. It applies the write and passes it to the next server, which does the same, until it reaches the last, the tail. The tail sends the reply to the client.
  • Reads go to the tail alone, which answers from its own state.

The tail has seen a write only when every server before it has, so anything the tail returns is on every replica, and reads are linearizable without the tail consulting anyone. Each server talks to one neighbour, where a primary would talk to all its backups. Failures are handled by a separate master, playing the part of the view service: if the head fails its successor becomes head, if the tail fails its predecessor becomes tail, and if a middle server fails its two neighbours are joined, with the earlier one resending whatever the later one hadn't yet received.

The fifth row is the catch in both of the simpler designs. The view service, or the master, is itself a single point of failure, and if it is replicated its copies have to agree on the current view, which is the very problem it was introduced to solve. In practice it is a small consensus-based store such as ZooKeeper or etcd (Chapter 31). Primary–backup and chain replication don't remove the need for consensus. They confine it to one small service that changes rarely, and let the bulk of the data be replicated by a cheaper method. Many large storage systems are built in exactly that way.

🖥️
Use case: VMware FT, a backup for an entire machine

VMware's Fault Tolerance feature, described in a paper its engineers published in 2010, applies primary–backup replication to a whole virtual machine, with any operating system and any applications running inside it unmodified. A primary VM runs on one physical host and a backup VM on another. The hypervisor under the primary records everything that could make the two diverge, the exact instruction at which each interrupt arrives, every incoming network packet, the result of each read of the clock, and streams these over a dedicated network link to the hypervisor under the backup, which replays them at the same points. The backup therefore executes the same instructions on the same inputs and stays in the same state, a few milliseconds behind. Only the primary's outputs reach the outside world. The paper's central rule is the one this chapter began with, in a different setting. Before the primary may send a network packet out, the backup must have acknowledged receiving the log entry for the operation that produced it. Otherwise the primary could show a client a result, fail, and be replaced by a backup that had never reached that point and might then act differently. The output is held back until the backup has confirmed. The computation itself runs ahead without waiting, which is why the overhead was tolerable. Split brain is prevented without a view service. The two hosts share a disk, and before a backup goes live, or a primary carries on alone after losing contact, it must win an atomic test-and-set operation on that shared storage. Whichever loses halts itself. The shared disk is serving as the arbiter that both sides can reach, and the test-and-set as the view change.

⚠️
Common mistakes
  • Replying to the client before the backup has acknowledged. The reply promises something only one machine knows.
  • Promoting a server that wasn't the backup. It doesn't have the state, however healthy it is.
  • Changing the view before the primary has confirmed the last one, while a state transfer may be half done.
  • Letting a backup answer reads. It may be an operation behind, or belong to an old view.
  • Forwarding non-deterministic operations, such as "now" or a random number, to be evaluated separately on each server.
  • A single, unreplicated view service. The design's availability is then that of one machine.

Interview drill

Explain it simply: How does primary–backup replication work, and how does it avoid losing data on failover?

How a strong answer sounds
One server, the primary, receives all client requests. For each one it forwards the operation to the backup, waits for the backup to acknowledge it, applies it locally, and only then replies to the client. So any operation a client has been told succeeded exists on both servers. A separate view service monitors both with heartbeats and defines numbered views saying who is primary and who is backup. If the primary dies, the view service promotes the backup, which by construction has every acknowledged operation, and recruits a spare as the new backup, to which the new primary transfers its full state. If the backup dies, the primary gets a new one the same way. Two rules make it safe. Only the current backup may be promoted, never an idle server, since only it has the data. And the view service won't move to another view until the current primary has acknowledged the present one, which guarantees that state transfer has finished. The limits are that it tolerates one failure at a time, and that the view service itself must be made reliable, usually with a consensus system.

Deeper: The old primary is partitioned from the view service but still reachable by some clients. Why doesn't that cause split brain, and where could it still go wrong?

How a strong answer sounds
Because the primary can't complete any operation alone. It must forward each operation to its backup, tagged with its view number, and wait for the acknowledgement before applying or replying. If the view service has moved on, the server the old primary believes is its backup is now the primary of a newer view. It sees a forwarded operation with an old view number and rejects it. The old primary therefore can't acknowledge anything to a client, and the rejection tells it the view has changed, so it steps down and redirects clients. No clock or lease is involved: the safety comes from requiring the backup's cooperation, and the backup always knows about a view change that promotes it. It can still go wrong in a few places. Reads: if the primary answers reads from local state without contacting the backup, a stale primary can return stale data, so reads either go through the same forwarding step or the primary must hold a lease. A view with no backup: a primary running alone has nobody to refuse it, so the view service must never promote someone else while such a primary might be alive, which means it can't make progress and the system is unavailable instead of unsafe. And the rule that views advance only after the primary's acknowledgement has to be enforced, or a new primary could be chosen that never received the state. Finally, clients must handle the ambiguity of a request that timed out during the change by retrying with a request ID so that the operation isn't applied twice.

🧠 Key takeaways

  • The primary forwards each operation to the backup and waits for its acknowledgement before applying and replying.
  • An acknowledged operation is therefore on two servers, and only the primary answers clients.
  • A view service numbers each arrangement as a view. Only the current backup can become the next primary.
  • A view doesn't change until its primary has acknowledged it, so state transfer is always complete.
  • A stale primary can't act: its former backup refuses anything carrying an old view number.
  • Chain replication writes down a line and reads at the tail. Both designs lean on a small consensus service to decide the configuration.

Check your understanding

Why does the primary wait for the backup's acknowledgement before replying to the client?

A reply is a promise. Without the wait, a crash of the primary right after replying would break it.

The primary and the backup both fail, and an idle server is healthy. What should the view service do?

The idle server has no data. Promoting it would replace the service's contents with an empty state.

Why must the view service wait for the primary to acknowledge the current view before moving to the next?

The acknowledgement says "my backup is ready". Without it, a chain of quick view changes could end at an empty server.

A primary that has been replaced, without knowing it, receives a client's write. What happens?

A primary never acts alone, and the server it depends on already knows about the new view.

In chain replication, why can the tail answer reads without consulting any other server?

The tail is the last to see each write, so it never returns anything that a failure could take away.
