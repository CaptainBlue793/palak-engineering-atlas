Retries, Backoff & Idempotency

Retrying is the first fix everyone reaches for, and it's usually right: most failures in a healthy system are brief, and a second attempt succeeds. But retries have two side effects that cause some of the worst outages in the industry. A retried request can be applied twice, and a fleet of clients retrying at once can keep a recovering service down long after the original problem is gone. This chapter covers when to retry, how to space retries out with exponential backoff and jitter, how to cap them with a budget, and how idempotency keys make retries safe.

When to retry

Retry a failure only if a second attempt might succeed and repeating the request is safe:

  • Retry transient failures: connection refused or reset, UNAVAILABLE, HTTP 503 (respecting any Retry-After), 429 after the indicated wait, and ABORTED transaction conflicts (by retrying the whole transaction).
  • Retry timeouts only if the operation is idempotent, or made idempotent with a key. A timeout is an unknown outcome (P2).
  • Never retry permanent failures: 400, 401, 403, 404, INVALID_ARGUMENT. They will fail the same way every time, and retrying just adds load.

And retry at one layer. If a browser retries 3 times, the API gateway retries each of those 3 times, and the service behind it retries its database call 3 times, one user click can become 4 × 4 × 4 = 64 database queries when the database is struggling, exactly when it can least afford them. The usual rule: retry at the layer closest to the failure that knows whether the operation is safe to repeat, and have the others fail fast.

Exponential backoff with jitter

Retrying immediately hits a service while it's still failing. Exponential backoff waits longer after each failure: 50 ms, 100 ms, 200 ms, up to a cap. That gives a struggling service room to recover. But if a thousand clients failed at the same moment, they all back off by the same amounts and return together in synchronized waves. Jitter breaks the synchronization by randomising each wait. The variant usually recommended, called full jitter in Marc Brooker's 2015 AWS analysis, sleeps for a random time between zero and the exponential value:

sleep = random(0, min(cap, base × 2attempt))

public final class Retrier {
	private final int maxAttempts;
	private final long baseMs, capMs;
	private final RetryBudget budget;

	public <T> T call(Supplier<T> op, Predicate<RuntimeException> retryable, Deadline deadline)
			throws InterruptedException {
		for (int attempt = 1; ; attempt++) {
			try {
				T value = op.get();
				budget.onSuccess();
				return value;
			} catch (RuntimeException e) {
				if (!retryable.test(e) || attempt == maxAttempts || !budget.tryAcquire()) throw e;
				long ceiling = Math.min(capMs, baseMs << attempt);           // exponential, capped
				long sleep = ThreadLocalRandom.current().nextLong(ceiling + 1);   // full jitter
				if (sleep >= deadline.remaining().toMillis()) throw e;       // no time left: give up now
				Thread.sleep(sleep);
			}
		}
	}
}

Three details matter. The loop respects the request's deadline, so retries never outlive the caller. Only errors the predicate marks as retryable are retried. And every retry must get a token from a budget, which is what the next section is about.

Retry storms and metastable failure

Here's the trap. When a service is overloaded, requests queue up and time out. Clients retry the timed-out requests, adding load to the overloaded service, which makes more requests time out. Worse, the server still processes the original attempts sitting in its queue, even though their clients have already given up, so its capacity goes on work nobody will read. The system can stay in this state after the original trigger is gone. Bronson and colleagues named this a metastable failure (HotOS 2021): the system has a good stable state and a bad stable state, and a brief shock can push it from one to the other.

The panel's lesson is uncomfortable: backoff and jitter alone don't save you from sustained overload, because each failing request still makes the same number of attempts; they're only spread out. What fixes it is limiting the total. A retry budget allows retries only up to a fraction of recent successful requests. gRPC's built-in retry throttling works this way: every failure costs a token, every success refunds a fraction of one, and retries stop when the bucket is half empty. On the server side, dropping requests whose deadline has already passed (the deadline from Chapter 3) stops it wasting capacity on clients who left.

/** Token bucket: retries are allowed while recent successes keep it topped up. */
final class RetryBudget {
	private static final double MAX = 10, REFUND = 0.1;   // ~1 retry per 10 successes, burst of 10
	private double tokens = MAX;
	synchronized void onSuccess() { tokens = Math.min(MAX, tokens + REFUND); }
	synchronized boolean tryAcquire() {
		if (tokens < 1) return false;
		tokens -= 1;
		return true;
	}
}

Idempotency keys: making retries safe

An operation is idempotent if doing it twice has the same effect as doing it once. "Set the price to £40" is; "charge £40" isn't. To make a non-idempotent operation safe to retry, the client generates a unique idempotency key for each logical operation, before the first attempt, and sends the same key with every retry. The server records the key with the result, and when a retry arrives with a key it has seen, it returns the stored result instead of acting again.

public Receipt charge(ChargeRequest req) {
	Claim c = keys.claim(req.idempotencyKey(), fingerprint(req));   // unique index on the key
	return switch (c) {
		case Claim.First f        -> {
			Receipt r = cards.charge(req.card(), req.amount(), req.idempotencyKey());   // pass it on
			keys.complete(req.idempotencyKey(), r);
			yield r;
		}
		case Claim.Done d         -> d.receipt();                                // a retry: same result
		case Claim.InProgress p   -> throw new ConflictException("retry later");       // concurrent duplicate
		case Claim.Mismatch m     -> throw new BadRequest("key reused with a different request");
	};
}

The details are where implementations go wrong:

  • Claim atomically. Two retries can arrive at once. A unique index (or a conditional put) ensures exactly one wins; the other sees InProgress.
  • Fingerprint the request. Reusing a key with different parameters is a client bug; reject it rather than returning an unrelated result. Stripe does exactly this.
  • Handle a crash between claim and complete. The key is stuck "in progress". Either ask the downstream system (here, by passing the same key on to the card network, so its retry is safe too), or let the claim expire so a later retry can proceed.
  • Keep keys long enough. At least as long as any client might retry. Stripe keeps them for 24 hours.

At-least-once delivery

A client that retries until it hears back has made the request at-least-once: it will be delivered once or more, never zero times (within the deadline). Combined with an idempotent receiver, at-least-once delivery produces an exactly-once effect, which is the only practical meaning of "exactly once" in distributed systems. Message queues, Kafka consumers and payment flows all use this pattern; Chapter 28 generalises it.

🗃️
Use case: DynamoDB, 20 September 2015

Amazon's postmortem for a multi-hour DynamoDB disruption in us-east-1 reads like the panel above. A brief network problem made many storage servers re-request their membership data from an internal metadata service at the same time. That service was already running near capacity because a new feature (global secondary indexes) had made the membership data much larger, so requests took longer than the storage servers' timeout. The servers timed out and retried, keeping the metadata service overloaded, and storage servers that couldn't get their data took themselves out of service, so customer requests failed. The retry load didn't stop on its own: engineers had to pause the metadata requests to add capacity before the system could recover. Afterwards Amazon increased the service's capacity, lengthened timeouts and changed how the requests were made. The trigger lasted minutes; the retries made it hours.

⚠️
Common mistakes
  • Retrying non-idempotent operations (charges, inserts, "add 1") without a key.
  • Retrying at every layer, so attempts multiply: 4 attempts at 3 layers is 64 calls at the bottom.
  • Backoff without jitter, so clients that failed together retry together.
  • No cap on total retries, assuming backoff alone prevents storms. Use a retry budget or circuit breaker.
  • Retrying permanent errors such as 400 or INVALID_ARGUMENT.
  • Generating a new idempotency key per attempt instead of per logical operation, which makes the key useless.
  • Servers that process requests whose client has already timed out, wasting capacity exactly when it's scarce.

Interview drill

Explain it simply: Why add jitter to exponential backoff?

How a strong answer sounds
Because failures are often correlated: many clients fail at the same moment, for example when a server restarts. With plain exponential backoff, they all wait 100 ms, then 200 ms, then 400 ms, and hit the server in synchronized waves that can knock it over again. Jitter randomises each wait, typically a uniform value between zero and the exponential ceiling, so retries spread out evenly and the server sees a smooth load it can absorb.

Deeper: Design idempotency for a "create payment" API that clients retry on timeout.

How a strong answer sounds
Clients generate a unique idempotency key per logical payment, before the first attempt, and send it in a header on every retry. The server claims the key atomically, with a unique index or a conditional insert, along with a fingerprint of the request. If the claim succeeds, it processes the payment, passing the key down to the payment processor so that hop is idempotent too, then stores the response under the key. A retry with a completed key gets the stored response; one with an in-progress key gets a 409 "retry later"; a key with a different fingerprint gets a 400. For crashes between claim and completion, a recovery job checks with the processor by key and completes or releases the claim. Keys are kept at least as long as clients might retry, say 24 hours. Combined with client retries, that gives at-least-once delivery with an exactly-once effect.

🧠 Key takeaways

  • Retry transient failures; retry timeouts only when the operation is idempotent; never retry permanent errors.
  • Retry at one layer; attempts multiply across layers.
  • Use exponential backoff with full jitter, inside the request's overall deadline.
  • Backoff spreads retries but doesn't cap them; a retry budget (or throttling) does, and deadline-aware servers stop wasted work.
  • Idempotency keys, claimed atomically and stored with the result, make retries safe.
  • At-least-once delivery plus an idempotent receiver gives an exactly-once effect.

Check your understanding

A browser, an API gateway and a backend service each retry a failed call up to 3 times (4 attempts each). How many database calls can one click cause in the worst case?

Attempts multiply across layers: 4 × 4 × 4 = 64. Retry at one layer and fail fast elsewhere.

What does full jitter compute for the wait before retry number n?

Full jitter picks uniformly from zero up to the capped exponential value, which spreads synchronized clients evenly.

A service recovers from a 3-second outage, but stays overloaded for an hour while clients keep retrying with backoff and jitter. What would most directly let it recover?

This is a metastable failure: retries keep the load above capacity. Capping total retries and not wasting work on abandoned requests break the loop.

When should a client generate the idempotency key for a payment?

The key identifies the logical operation. A new key per attempt makes every retry look like a new payment.

Two retries with the same idempotency key arrive at the server at the same moment. What should happen?

The claim must be atomic, for example a unique index or conditional insert, so concurrent duplicates can't both act.
