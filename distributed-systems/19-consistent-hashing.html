Consistent Hashing

A cluster that stores more data than one machine can hold has to decide which machine each key lives on, and it has to make that decision the same way everywhere, quickly, with no table of every key. A hash function does that. P6 showed the obvious scheme, hash(key) mod N, and its fatal property: change N by one and nearly every key moves to a different machine. Consistent hashing is the family of schemes in which changing the set of machines moves only the keys that have to move, about one in N. It is how Dynamo, Cassandra, memcached clients, content delivery networks and many load balancers place data. This chapter builds the hash ring properly, adds the virtual nodes that make it usable, and then covers two alternatives that have no ring at all.

The ring

Take the output range of a hash function, say 0 to 232 − 1, and bend it into a circle, so that the largest value is followed by 0. Hash each node's name to get its position on the circle. Hash each key the same way. A key belongs to the first node at or after its position, going clockwise. Each node therefore owns the arc of the circle that ends at its position and begins just after the previous node's.

The ring is a sorted map from position to node, and the lookup is "the smallest entry at or above this hash, or the first entry if there is none".

final class HashRing {
	private final TreeMap<Long, String> ring = new TreeMap<>();
	private final int vnodes;                                 // positions for each node: see the next section

	void add(String node)    { for (int i = 0; i < vnodes; i++) ring.put(hash(node + "#" + i), node); }
	void remove(String node) { for (int i = 0; i < vnodes; i++) ring.remove(hash(node + "#" + i)); }

	String nodeFor(String key) {
		var e = ring.ceilingEntry(hash(key));               // first position at or after the key's
		return (e != null ? e : ring.firstEntry()).getValue();   // past the end: wrap round to the start
	}

	/** The n distinct nodes that hold a key: keep walking clockwise, skipping repeats. */
	List<String> replicasFor(String key, int n) {
		var found = new LinkedHashSet<String>();
		var tail = ring.tailMap(hash(key), true).values();
		for (String node : Iterables.concat(tail, ring.values())) {
			found.add(node);
			if (found.size() == n) break;
		}
		return List.copyOf(found);
	}
}

Why this moves so little is easy to see on the circle. Adding a node places one new point. The keys between that point and the previous one, which belonged to the next node along, now belong to the new node. No other key is affected. Removing a node hands its arc to its successor and touches nothing else. With N nodes, a change moves about 1/N of the keys, where mod N moved nearly all of them.

The second method is what a replicated store uses. The N replicas of a key are the next N distinct nodes clockwise from it, which Dynamo called the key's preference list, and the quorum arithmetic of Chapter 12 is done over that list.

Virtual nodes

The ring as described has a practical flaw. Node positions are random, and a handful of random points cut a circle very unevenly. With five nodes, one will routinely own a third of the ring and another a twentieth. There is a second problem too: when a node leaves, its whole arc lands on a single neighbour, which may then be overloaded and fail in its turn.

The fix is to give each physical node many positions. Hash "A#0", "A#1", up to "A#127", and place node A at all 128 points. Each is a virtual node, or token. A's share of the ring is now the sum of 128 small arcs scattered around the circle, and the sum of many random pieces is close to its average.

The last row is why the count isn't simply set as high as possible. Cassandra's default was 256 virtual nodes for each machine for some years. With hundreds of machines that meant tens of thousands of ranges for every repair and every topology change to work through, and the default was later reduced to 16, with the positions chosen deliberately to be even where they had been purely random.

Things to notice. On the ring with one position for each node, the shares are badly uneven, and with 16 they are tolerable, and with 128 nearly level. Add a node on the ring: about a fifth of the keys move, which is all that had to, and with many virtual nodes they come a little from every other node. Now switch to hash mod N and add a node: about four keys in five move. Rendezvous hashing is level without any virtual nodes and moves the minimum in every case. Jump hash is as level as rendezvous, using no table at all, and moves the minimum when a node is added or the newest one is removed. Remove the oldest node under jump hash, though, and most keys move: it knows the nodes only as numbers 0 to N − 1, and taking one out of the middle renumbers the rest.

Adding and removing nodes

In a cache, a key that moves is merely a miss: the new node fetches the value from the origin. In a store, the data has to move too, and that is the expensive part of any change.

Two cases should be kept apart. A planned change, adding capacity or retiring a machine, goes through the steps above and changes ownership for good. An unplanned one, a node that has crashed and may well be back in ten minutes, shouldn't. Re-replicating a terabyte for an outage that ends before the copying does is wasted work, and the copying itself loads the survivors. So stores leave the ring alone at first: requests for the dead node's ranges are served by its fellow replicas, with hinted handoff covering the writes it misses (Chapter 12), and ownership changes only when an operator, or a long timeout, decides the node isn't coming back.

Rendezvous hashing

Rendezvous hashing, also called highest random weight, reaches the same goal with no ring. For a given key, compute a score for every node by hashing the key and the node's name together. The key belongs to the node with the highest score.

String nodeFor(String key, Collection<String> nodes) {
	return nodes.stream()
			.max(Comparator.comparingLong(node -> hash(key + "|" + node)))
			.orElseThrow();
}

If a node is removed, the only keys affected are those for which it had the top score, and each of them falls to its own second choice, which is a different node for different keys, so the load is spread evenly over the survivors. If a node is added, it takes exactly the keys for which its score is now the highest. Balance is as good as the hash function, with no virtual nodes, and the top k scores give k replicas. The price is that every lookup computes a hash for every node. For ten or fifty nodes that is negligible. For ten thousand it isn't, and a ring's logarithmic lookup wins.

Jump hash

Jump consistent hash, published by two Google engineers in 2014, is the smallest of the three: a function of a few lines, using no memory at all, that maps a key to a bucket number from 0 to N − 1.

static int jumpHash(long key, int buckets) {
	long b = -1, j = 0;
	while (j < buckets) {
		b = j;
		key = key * 2862933555777941757L + 1;                        // a pseudo-random sequence seeded by the key
		j = (long) ((b + 1) * ((double) (1L << 31) / (double) ((key >>> 33) + 1)));
	}
	return (int) b;
}

The idea behind it: imagine the number of buckets growing from 1 upwards. Each time a bucket is added, a key should jump to the new bucket with probability 1/n, and otherwise stay. The function simulates those jumps directly, skipping ahead from one jump to the next, so it runs in time proportional to the logarithm of the bucket count. The distribution is almost perfectly even, better than a ring with any practical number of virtual nodes.

Its limitation is in its signature. It knows a count of buckets and nothing about their identities, so buckets can only be added and removed at the end. That suits storage shards, which are numbered, are never removed from the middle, and are each a replicated group that doesn't vanish when one machine fails. It doesn't suit a pool of cache servers, any of which may disappear.

Use case: Vimeo, and a ring that knows when a node is full

Consistent hashing balances keys, and P6 pointed out that keys aren't load. Vimeo met the difference in 2016 in the service that packages video for streaming. Each video's index is expensive to compute and is cached in the memory of whichever server handled it, so requests for the same video should always go to the same server, and the load balancer chose servers by consistent hashing on the video's ID. That worked until a video became popular. All its requests went to one server, by design, and that server was overwhelmed while others sat idle. The alternative, sending each request to the least busy server, spread the load evenly and ruined the caching, since every server ended up computing every popular index for itself. Vimeo's engineers found a recent paper from Google researchers, "Consistent Hashing with Bounded Loads", which combines the two. Each server is given a cap, a fixed fraction above the current average load, 25% in Vimeo's configuration. A request goes to the server the ring chooses, as before, unless that server is at its cap, in which case it goes on round the ring to the next server that isn't. Most requests land where consistent hashing would have put them, so the caches stay effective, and no server can exceed the cap, however popular one key becomes. One of the engineers implemented the algorithm in HAProxy, the open-source load balancer, where it became a standard option, and Vimeo reported both the overload and most of the cache duplication gone. The original ring assumes that every key costs the same. Where that is false, the placement scheme has to be told about load as well as about keys.

⚠️
Common mistakes
  • A ring with one position for each node. The load is badly uneven, and a failure dumps everything on one neighbour.
  • A weak hash function. Java's String.hashCode clusters similar names. Use a mixing hash such as Murmur3 or xxHash.
  • Taking the next N positions as replicas. With virtual nodes several may be the same machine. Take the next N distinct nodes, and for real safety distinct racks.
  • Rebalancing the moment a node is unreachable. Most outages are short, and moving data loads the survivors.
  • Jump hash for servers that can fail individually. Removing a bucket from the middle renumbers the rest.
  • Assuming even keys means even load. One hot key defeats any hash. Cap the load, or split the key.

Interview drill

Explain it simply: What is consistent hashing, and why not just use hash(key) % N?

How a strong answer sounds
With hash mod N, the node for a key depends on N, so when a node is added or removed nearly every key maps to a different node. For a cache that is a storm of misses, and for a store it means moving almost all the data. Consistent hashing makes placement depend on positions rather than on a count. You hash each node to a point on a circle and each key to a point on the same circle, and a key belongs to the first node clockwise from it. Adding a node only takes over the arc between it and its predecessor, and removing one only hands its arc to its successor, so on average only about one Nth of the keys move, which is the minimum possible. In practice each physical node is placed at many points, virtual nodes, since a few random points divide the circle unevenly; with a hundred or so for each node, load evens out and a departing node's keys are spread across all the others. For replication you take the next N distinct nodes clockwise. I'd mention that there are ring-free alternatives: rendezvous hashing, which scores every node for each key and takes the highest, and jump hash, which is tiny and perfectly even but only supports adding and removing buckets at the end.

Deeper: You run a consistent-hash ring of cache servers. One key becomes extremely hot and its server falls over. What are your options?

How a strong answer sounds
The ring is doing its job, sending one key to one node, and that is the problem, so more virtual nodes won't help: they balance the number of keys, not the traffic to a single key. Options, roughly from least to most invasive. Bounded loads: cap each server at some factor above the mean load, say 1.25, and when the chosen server is at its cap, spill to the next one on the ring. Most requests still hit the intended server, so cache locality is largely kept, and no server can be overwhelmed. Replicating the hot key: hash it to the top two or three servers, by rendezvous score or the next positions on the ring, and spread reads across them; that needs a way of identifying hot keys, either a static list or a counter in the client or proxy. Splitting the key: append a small random suffix on reads so that copies land on several servers, with the writer fanning out to all the suffixes. A local in-process cache in front for the hottest few keys, with a short lifetime, which removes the network hop entirely. And, on the server side, coalescing concurrent misses so that a thundering herd for the same key triggers one recomputation. I'd also look at why the server fell over rather than degraded: a concurrency limit and load shedding would have turned an outage into some slow requests. If the store behind the cache is the real bottleneck, the fix belongs there. For most cases I'd start with bounded loads in the proxy, since it needs no knowledge of which keys are hot.

🧠 Key takeaways

  • On a hash ring a key belongs to the first node clockwise from its hash. Changing the nodes moves about one key in N.
  • Virtual nodes give each machine many positions, which evens out the load and shares a departing node's keys among all the others.
  • Replicas are the next N distinct nodes round the ring.
  • In a store, placement changes in an instant and the data takes hours to move. Don't rebalance for a short outage.
  • Rendezvous hashing needs no ring and balances well, at a cost linear in the number of nodes for each lookup.
  • Jump hash is tiny and almost perfectly even, and only adds or removes at the end. No hash balances a hot key.

Check your understanding

A hash ring has 10 nodes. An eleventh is added. Roughly what share of the keys move?

Only the keys in the arcs the new node takes over move to it. That is the least any scheme could move.

What do virtual nodes fix?

Many small arcs average out. They also spread a departing node's keys across everyone.

On a ring with virtual nodes, how are the three replicas of a key chosen?

Adjacent positions may belong to the same machine, which would put two "replicas" on one disk.

What is the main cost of rendezvous hashing?

Excellent for tens of nodes. With thousands, a ring's sorted lookup is cheaper.

Why is jump hash a poor fit for a pool of cache servers?

It suits numbered shards that are only ever added at the end. Cache servers fail in any order.
