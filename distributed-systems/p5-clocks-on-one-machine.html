Clocks on One Machine

Before two machines can disagree about the time, one machine has to disagree with itself. Every server has two clocks that answer different questions: "what time is it?" and "how long has it been?". They behave differently when NTP corrects the time, when a leap second arrives, or when someone fixes a wrong clock by hand, and code that asks the first clock the second question breaks in exactly those moments. This chapter sorts out which clock to use for what, in Java, before Chapter 6 adds the network.

Two clocks in every machine

The wall clock (time of day) tells you what time it is in the world: 2026-10-01T14:03:22Z. It is what you put in a log line or show a user. Because it is supposed to match real time, the operating system adjusts it: NTP corrects it, an administrator can set it, a virtual machine restored from a snapshot can wake up hours in the past. So it can jump forwards or backwards.

The monotonic clock tells you how much time has passed since some arbitrary point, usually boot. Its absolute value means nothing, and you can't compare it between machines or even across a reboot. What it promises is the one thing the wall clock can't: it never goes backwards. That makes it the only correct clock for measuring durations.

How the wall clock moves

A quartz oscillator drifts: a typical server clock gains or loses tens of microseconds per second, a few seconds a day if nothing corrects it. NTP measures the offset against time servers and corrects it in one of two ways:

  • Slewing for small offsets: the kernel runs the clock slightly fast or slow, by at most 500 parts per million (0.5 ms per second), until the offset is gone. Time never jumps, but correcting a 400 ms error takes over 13 minutes.
  • Stepping for large offsets: the clock is set to the right value at once. Classic ntpd steps when the offset exceeds 128 ms; chrony steps only when configured (makestep), typically at boot. A step can move the time backwards.

Then there are the steps nobody planned: an operator running date -s, a VM resumed after a pause or migrated to a host with a different clock, a container restored from a checkpoint. Any code that subtracts two wall-clock readings is exposed to all of them.

Leap seconds

The Earth's rotation is slightly irregular, so UTC has occasionally inserted a leap second, 23:59:60, to stay within 0.9 s of solar time; 27 have been added since 1972. Unix time pretends every day has exactly 86,400 seconds, so on most systems the leap second shows up as one second being repeated: the wall clock goes backwards by a second at midnight. Code that assumed time only moves forward broke in famous ways (see the use case below). Large operators now smear the leap second instead: Google and AWS run their clocks very slightly slow over the 24 hours around it, so there is no repeated second, at the cost of being up to half a second off from strict UTC during the smear. In 2022 the General Conference on Weights and Measures voted to stop inserting leap seconds by 2035, but the code that mishandles them will be around for a long time.

Measuring time correctly in Java

// WRONG: a duration from the wall clock. An NTP step makes it negative or huge.
long start = System.currentTimeMillis();
replicateBatch();
long tookMs = System.currentTimeMillis() - start;

// RIGHT: durations from the monotonic clock.
long t0 = System.nanoTime();
replicateBatch();
Duration took = Duration.ofNanos(System.nanoTime() - t0);

// Comparing two nanoTime readings: subtract, don't compare directly (the value may overflow).
boolean expired = System.nanoTime() - leaseExpiresAtNanos >= 0;   // not: now >= expiresAt

The last line follows the nanoTime Javadoc: the value can be negative and can wrap around after about 292 years of uptime, so the only meaningful operation is subtracting two readings taken in the same JVM. It's a habit worth having even if the wrap never happens.

For code you want to test, don't call either clock directly. Inject one. Java's java.time.Clock covers the wall clock; for the monotonic clock, a one-method interface is enough, and a fake implementation lets a test advance time by an hour instantly:

public interface Ticker { long nanos(); }                      // monotonic time source

public final class Lease {
	private final Ticker ticker;
	private final long expiresAt;

	Lease(Ticker ticker, Duration ttl) {
		this.ticker = ticker;
		this.expiresAt = ticker.nanos() + ttl.toNanos();
	}
	boolean valid() { return ticker.nanos() - expiresAt < 0; }
}

Ticker real = System::nanoTime;                            // production
var fake = new AtomicLong(); Ticker test = fake::get;       // tests: fake.addAndGet(...)

Use case: the leap second that took down DNS

At midnight UTC on 1 January 2017, a leap second was inserted. Cloudflare's DNS server, written in Go, measured how long upstream resolvers took to answer by subtracting two wall-clock times. During the repeated second, some of those durations came out negative. The value was passed to a random-number function that panics on a negative argument, and DNS resolution failed for a portion of Cloudflare's customers until the code was patched. Go itself changed afterwards: since Go 1.9, time.Now() carries a monotonic reading, and subtracting two such times uses it. Five years earlier, the 30 June 2012 leap second had triggered a Linux kernel timer bug that sent many Java servers to 100% CPU at once, among them Cassandra and Hadoop clusters at several large sites. Both incidents happened on every affected machine at the same instant: a textbook correlated failure (P4).

⚠️
Common mistakes
  • Measuring durations with currentTimeMillis or Instant.now(). Use nanoTime.
  • Timeouts, leases and rate limiters on the wall clock. A step forward expires them all at once; a step back extends them.
  • Comparing nanoTime values with < or > instead of subtracting, or comparing them between JVMs or machines.
  • Assuming time never repeats. Leap seconds and backward steps make two events seconds apart look out of order.
  • Calling the clock directly in logic you want to test. Inject a Clock or Ticker.
  • Turning off NTP to "avoid jumps". The clock then drifts by seconds a day; fix the code, not the clock.

Interview drill

Explain it simply: What's the difference between System.currentTimeMillis() and System.nanoTime(), and when do you use each?

How a strong answer sounds
currentTimeMillis reads the wall clock: milliseconds since the Unix epoch, meaningful to people and roughly comparable across machines, but it can jump when NTP steps the clock, an operator sets it, or a leap second is inserted. nanoTime reads a monotonic clock: the absolute value is meaningless, it can't be compared across JVMs, but it never goes backwards. I use the wall clock for timestamps I record or show, and the monotonic clock for anything that measures elapsed time: latencies, timeouts, deadlines, leases, rate limiters.

Deeper: A failure detector marks a peer dead if no heartbeat arrived for 3 seconds. One night every node in the cluster declares every other node dead at the same moment. What could cause that?

How a strong answer sounds
The detector is probably measuring "time since last heartbeat" with the wall clock, and the wall clock jumped forward on every node at once, for example NTP stepping all clocks after a time-server problem was fixed, or a VM host resuming guests. A forward step makes every "last heartbeat" look older than 3 seconds instantly, so every peer is suspected together, which can trigger mass failovers or elections. The fix is to measure intervals with the monotonic clock (nanoTime), and to treat simultaneous suspicion of many peers as a sign the detector, not the peers, has a problem.

🧠 Key takeaways

  • The wall clock answers "what time is it?" and can jump; the monotonic clock answers "how long has it been?" and never goes backwards.
  • NTP slews small errors (at most 0.5 ms per second) and steps large ones, possibly backwards.
  • Leap seconds repeat a second on most systems; smearing avoids the repeat; they caused real, fleet-wide outages.
  • Measure durations, timeouts, deadlines and leases with System.nanoTime(), by subtracting readings.
  • Use the wall clock only for timestamps people or other systems read.
  • Inject a clock so time-dependent logic can be tested without waiting.

Check your understanding

Which Java call should a heartbeat-based failure detector use to measure time since the last heartbeat?

Elapsed time needs the monotonic clock. The other three read the wall clock, which can jump when NTP or an operator changes it.

NTP finds the local clock 50 ms fast. What does a typical NTP daemon do?

Small offsets are slewed (at most 500 ppm). ntpd steps only above 128 ms by default; chrony steps only when configured to.

Why did some programs compute negative durations during the leap second of 31 December 2016?

Unix time has no 23:59:60, so most systems repeat 23:59:59. A duration measured across that repeat on the wall clock can come out negative.

How should two System.nanoTime() readings, a and b, be compared to ask "is b later than a"?

nanoTime values can be negative and can wrap, so the Javadoc says to subtract and compare the difference with zero. Readings from different JVMs are not comparable at all.

A leader holds a lease measured on the wall clock. NTP steps its clock back 2 seconds just before the lease ends. What happens?

Stepping back makes the wall clock read earlier, so the lease's end appears further away. Lease timers belong on the monotonic clock.
