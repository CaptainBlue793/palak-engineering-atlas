Case Study: Apache Cassandra

In 2008 two engineers at Facebook needed a store for a feature that let people search their inbox, with a volume of writes that no database of the time took comfortably. One of them had been an author of Amazon's Dynamo paper the year before. They took Dynamo's way of spreading and replicating data, a ring of equal nodes with no leader, and joined it to the storage design of Google's Bigtable, in which a write is an append and files are never changed in place. The result, Cassandra, was open-sourced that year and has since run some of the largest databases anywhere: Apple has spoken of well over a hundred thousand nodes, and Netflix keeps most of what it knows about its members' viewing in it. Earlier chapters used Cassandra for examples of consistent hashing, quorums, gossip, failure detection and repair. This chapter puts it together as one system and follows a write and a read through a node. It then spends its time on the part that most often surprises the people who run it, and that every earlier chapter has postponed to here: what it means to delete something from a database in which no node can be sure it has heard everything.

  • Show how deleted data comes back when repair is late, and state the rule that prevents it

The ring

A Cassandra cluster is a set of identical nodes. There is no leader, no configuration server and no special role, and a client may send any request to any node. Each node owns a number of positions, tokens, on a ring of 64-bit hash values, and a row is placed by hashing its partition key and walking clockwise to find the nodes that own the next positions (Chapter 19). How many, and where, is set for each keyspace: typically three replicas in each datacentre, on separate racks. Nodes learn of one another, and of each other's tokens and health, by gossip (Chapter 23).

The data model is shaped by this placement, and learning Cassandra is mostly learning to design with it and not against it.

CREATE TABLE messages_by_channel (
  channel_id  bigint,
  bucket      int,                       -- which ten-day window: keeps any one partition from growing for ever
  message_id  timeuuid,
  author_id   bigint,
  body        text,
  PRIMARY KEY ((channel_id, bucket), message_id)   -- (partition key), clustering column
) WITH CLUSTERING ORDER BY (message_id DESC)
  AND gc_grace_seconds = 864000;              -- ten days: see "Repair and tombstones"
  • The partition key decides the nodes. All rows with the same partition key form one partition, stored together on the same replicas. A query that gives the partition key goes to those replicas and nowhere else. A query that doesn't must ask every node, and Cassandra refuses it by default.
  • Clustering columns sort rows inside a partition. Here a channel's messages for one window lie on disk newest first, so "the latest fifty" is one short sequential read.
  • Tables are designed for queries. There are no joins. If the same data must be found two ways, it is written to two tables, each with a key that suits one question.
  • Partitions must stay bounded. A partition lives whole on each of its replicas and can't be split, which is the reason for the bucket in the key.

Consistency is chosen for each request, as Chapters 12 and 26 described: with three replicas, QUORUM for both reads and writes gives overlap, and LOCAL_QUORUM gives it within a datacentre. Conflicting writes to a cell are settled by timestamp, last write wins, and an operation that needs compare-and-set uses a lightweight transaction, a round of Paxos among the replicas (Chapter 16).

Write and read paths

Inside a node Cassandra is a log-structured merge tree (Databases, LSM trees), and the two halves of its behaviour follow from that structure.

WriteRead
Disk workOne sequential appendSeveral lookups, in as many SSTables as hold part of the row
Looks at existing dataNever. There is no check that a row exists, or for a conflictAll versions, to find the newest of each cell
Cost grows withAlmost nothingThe number of SSTables, the partition's size, and the tombstones passed over
ConsequenceINSERT and UPDATE are the same operation, an upsertCompaction strategy is a read-performance decision

That a write never reads is the source of Cassandra's write throughput, and of a habit of mind it demands. An update doesn't know what it is updating. Two writes to the same row from two clients are both accepted without comment, and the later timestamp wins when the row is next merged. Anything that needs "only if" must say so, and pay for a lightweight transaction.

PreparedStatement insert = session.prepare("""
		INSERT INTO messages_by_channel (channel_id, bucket, message_id, author_id, body)
		VALUES (?, ?, now(), ?, ?) USING TTL ?""");
session.execute(insert.bind(channel, bucketOf(Instant.now()), author, body, 90 * 86_400));   // expires in ninety days

// A delete is also a write: it stores a marker, and reads nothing.
session.execute(SimpleStatement.newInstance(
		"DELETE FROM messages_by_channel WHERE channel_id = ? AND bucket = ? AND message_id = ?",
		channel, bucket, messageId));

Repair and tombstones

How do you delete a row from a store built this way? The SSTables that hold it can't be edited. And with replicas that may each have missed some writes, removing the row from the replicas you can reach leaves a problem: a replica that was down still has it, and from outside, "this replica has a row the others lack" looks exactly like "the others missed a write". The usual machinery, read repair and anti-entropy (Chapter 24), would dutifully copy the row back.

So a delete is a write. It stores a tombstone: a marker with a timestamp, saying that everything older than this in this cell, row, range or partition is deleted. Tombstones replicate, merge and win conflicts like any other write. A replica that missed the delete receives the tombstone later, and its newer timestamp covers the old data.

A tombstone can't be kept for ever, since the store would never shrink. But it must be kept until every replica has it. Cassandra has no way to know when that is, and uses a rule in its place:

  • A tombstone is kept for at least gc_grace_seconds, ten days by default. After that, the next compaction that touches it may drop it, with the data it covers.
  • In return, the operator must make sure that every replica receives every tombstone within that time, which means completing a repair of every table on every node at least once every gc_grace_seconds.

The other two delivery mechanisms don't meet that obligation alone. A hint for a node that is down is kept for three hours by default and then abandoned. Read repair reaches only what is read. If a node misses a delete, isn't repaired within the grace period, and the other replicas then purge their tombstones, the cluster holds one copy of the row and no record that it was ever deleted. The next repair spreads it back to every replica. Operators call this zombie data, and the panel below produces it.

How a missed delete reaches a replicaCoversLimit
Hinted handoffA node that was down brieflyHints are dropped after three hours by default
Read repairRows that are read, at a level that consults the stale replicaNothing that isn't read
Anti-entropy repairEverythingMust be run, on every node, inside the grace period

Tombstones also cost something while they live. A read that scans a range must step over every tombstone in it to be sure which rows are dead, and they are invisible in the result. A query that returns ten rows may have read a hundred thousand markers. Cassandra warns when one query passes a thousand tombstones and aborts it at a hundred thousand. The workloads that get there are predictable: a table used as a queue, with rows inserted and deleted at the head; data with a time-to-live, since each expiry becomes a tombstone; and inserting explicit nulls, each of which is a tombstone for that column.

Try it: delete a row, and keep it deleted

One row on three replicas, with a grace period of ten days. Write it, take a node down, delete it, and let time pass. The question at every step is what a client would be told.

Tombstones and the grace periodInteractive
Each card is one replica's copy of the row: the data, a tombstone, or nothing. The amber bar is the grace period, starting at the delete. Compaction runs as time passes and drops any tombstone older than the grace period. Hints are kept for three hours. A read at QUORUM asks two of the replicas that are up and returns whichever version has the newer timestamp, and the panel reports the answer for every pair.

Things to notice. Play the three presets. If C is back within the hour, the hint is still waiting, delivers the tombstone, and that is the end of it. If C is away for two days, the hint expired after three hours and C returns holding the row. Repair then finds that A and B have a tombstone newer than C's data, and C receives it. If C is away for twelve days, the grace period ended on day 10 and compaction on A and B dropped their tombstones. Repair finds the row on C and nothing anywhere else, concludes that A and B missed a write, and copies it to them. The row is back on all three.

Walk that last case by hand to find the moment it goes wrong. After the delete, A and B hold tombstones and a client sees nothing. On day 10 they hold nothing at all, and a client still sees nothing, so every check that could be run passes. The fault shows only when C returns, and by then no replica holds the evidence. In a test of 400 random sequences of these actions the row came back in 184. In the 120 where a repair ran with C present before the grace period ended, it never did.

Running it

The rule in the last section turns into a routine. Every node runs repair on a schedule, in small pieces so that no one run streams too much (Chapter 24), and the thing to monitor is the age of the oldest unrepaired range against the grace period. A node that has been down for longer than the grace period must not simply be started again: it is wiped and rebuilt from its neighbours, since anything on it may be a row the rest of the cluster has deleted and forgotten. For data that only ever expires, time-series and logs with a time-to-live, a compaction strategy that groups SSTables by time window lets a whole file be dropped once everything in it has expired, with no tombstones scanned at all. And the grace period can be shortened for a table, as Discord did (Chapter 26), by anyone who is certain that their repairs finish inside the shorter time.

Use case: Netflix, and a million writes a second by adding machines

In 2011 Netflix, then partway through moving off its own datacentres and its Oracle databases on to Amazon's cloud, published a benchmark that did a good deal to establish Cassandra's reputation. The company had chosen Cassandra for its member data on two grounds from this chapter: every node is the same, so a node lost in the cloud is replaced without ceremony, and writes are appends, so throughput is limited by machines and not by coordination. The test was meant to check the second claim. Engineers built clusters of 48, 96, 144 and 288 nodes on ordinary cloud instances, with three replicas of the data spread over three availability zones, and drove writes at them from separate client machines. Throughput rose in proportion to the number of nodes at every step: doubling the machines doubled the writes. At 288 nodes the cluster took just over a million client writes a second, which with three replicas is more than three million stored. Latency stayed flat as the cluster grew. The whole exercise, clusters and clients, ran for a few hours and cost a few hundred dollars. The figures have long since been passed, and what lasts is the shape of the result. A leaderless ring with an append-only write path has no component whose load grows with the size of the cluster, so it scales in a straight line, where a system with a leader or a coordinator bends. Netflix's later writing about Cassandra is the other half of the picture, and is mostly about what this chapter's last sections describe: it built tools to schedule repairs across thousands of nodes, to replace nodes automatically, and to take backups of immutable SSTables as they are written. The throughput came from the design. The work, for a company running it at that scale, went into keeping replicas the same.

⚠️
Common mistakes
  • Repair that doesn't complete within gc_grace_seconds. Deleted rows return, and nothing says so.
  • Restarting a node that has been down longer than the grace period. It carries data the cluster has deleted. Replace it.
  • Using a table as a queue. The head of the partition is tombstones, and every read wades through them.
  • Inserting nulls. Each null column is a tombstone. Leave unset columns out.
  • Unbounded partitions. A partition key such as a user ID alone grows for ever on three nodes. Add a time bucket.
  • Modelling tables first and queries later. A query without the partition key scans the cluster. Start from the queries.
  • Expecting an UPDATE to fail when the row doesn't exist. It creates it. Writes never read.

Interview drill

Explain it simply: Why are writes so fast in Cassandra, and what is the cost?

How a strong answer sounds
Two reasons, one per layer. Across the cluster there is no leader: any node can coordinate a write, it sends the write to the replicas that own the partition's token and waits only for the number of acknowledgements the consistency level asks for, so there is no single bottleneck and capacity grows with the number of nodes. Within a node the storage engine is a log-structured merge tree: a write is appended to the commit log for durability and inserted into an in-memory memtable, and that is all. Nothing is read from disk, there is no check for an existing row and no in-place update, so an insert and an update are the same operation. Memtables are flushed later to immutable SSTable files, which are merged by compaction in the background. The costs: reads are more expensive, because a row may be spread across the memtable and several SSTables and must be merged by timestamp, using bloom filters and indexes to limit the work; compaction consumes I/O and disk space; conflicts are resolved by last-write-wins timestamps, so concurrent updates silently overwrite and clock accuracy matters; and deletes can't remove data in place, so they are written as tombstones, which have their own costs.

Deeper: Deleted data has reappeared in a Cassandra table. What happened, and how do you prevent it?

How a strong answer sounds
Almost certainly a tombstone was purged before every replica had received it. In Cassandra a delete writes a tombstone, a timestamped marker that shadows older data, because replicas can miss writes and the absence of a row can't be distinguished from never having received it. Tombstones are kept for gc_grace_seconds, ten days by default, and after that compaction can discard them along with the data they cover. The sequence for resurrection: a replica was down or partitioned when the delete happened, so it kept the live row. Hinted handoff didn't cover it, because hints are only kept for about three hours. The row wasn't read at a level that would trigger read repair on that replica. No repair completed for that range within gc_grace_seconds. The other replicas compacted away their tombstones. Now one replica has the row and the others have nothing, and to repair or read repair that looks like a write the others missed, so the row is copied back everywhere. Prevention: run repair on every node so that every range is repaired within gc_grace_seconds, with margin, and monitor the time since last successful repair per table as a hard alert. Never bring back a node that has been down longer than gc_grace; wipe and replace it. Don't lower gc_grace unless repairs reliably complete within the new value. Other causes I'd check: clients supplying their own timestamps with skewed clocks, so a delete has an older timestamp than the write it was meant to remove; restoring old SSTables from backup; and for TTL data, a mix of TTLs meaning some cells outlive the tombstones of others. To clean up, I'd delete again and repair promptly.

🧠 Key takeaways

  • Cassandra is Dynamo's leaderless ring with Bigtable's log-structured storage: every node equal, every write an append.
  • The partition key decides which replicas hold a row. Tables are designed query by query, and partitions kept bounded.
  • A write appends to the commit log and the memtable and reads nothing. A read merges the memtable and several SSTables by timestamp.
  • A delete is a tombstone, kept for gc_grace_seconds so that every replica can receive it.
  • Repair must complete on every node within the grace period, or deleted data returns as zombies.
  • Tombstones slow reads. Queues, expiring data and null inserts create them in bulk.

Check your understanding

What decides which nodes store a row in Cassandra?

The partition key is hashed to a token, and the replicas are the nodes that own the next positions clockwise.

What does a replica do on disk to handle a write?

Nothing is read. SSTables are written later, in bulk, and never changed.

Why is a delete stored as a tombstone?

Absence carries no information. The marker has a timestamp, and wins against the older data on any replica it reaches.

gc_grace_seconds is ten days. What must an operator ensure?

After the grace period tombstones may be dropped. Every replica must have received them by then.

A node has been down for three weeks, with the default grace period. What should be done with it?

It may hold rows whose tombstones the cluster has already purged. Repair would copy them back to everyone.
