Formal Methods: TLA+ in Practice

Chapter 37 hunted bugs in code by trying many executions, thousands of random ones a second. There is an earlier point at which a bug can be caught, and a more thorough way to look. Before a protocol is code it is a design: a page of prose, a diagram on a whiteboard, an argument that sounded right in a meeting. Design errors in distributed protocols are subtle, since the faulty case needs several unlikely things to happen in one order, and they are the most expensive kind, since by the time one surfaces a whole system has been built on it. Formal specification means writing the design down in a language precise enough for a machine to read. Model checking means having the machine examine every state the design can reach, for a small configuration, and report any state that breaks a rule you have stated, together with the shortest sequence of steps that leads there. The language most used for this in industry is TLA+, devised by Leslie Lamport. It is mathematics, of the kind met in a first course on logic, and engineers with no background in formal methods learn enough to be useful in two or three weeks. This chapter covers what a specification is, reads a real one, runs a model checker over it, and looks at what companies have found this way.

  • Describe a system as a state machine: variables, initial states and a next-state relation
  • Distinguish safety properties from liveness properties, and write an invariant
  • Read a short TLA+ specification
  • Explain what a model checker does, what a counterexample is, and why models are kept small

Specs and invariants

A specification in TLA+ describes a system as a state machine, in three parts.

  • Variables. A state is one assignment of values to all of them. The variables describe the whole system at once: every node's memory and every message in the network.
  • An initial condition, saying which states the system may start in.
  • A next-state relation, saying which states may follow which. It is written as a set of actions, each with a condition for when it can happen and a description of what it changes.

A behaviour is any sequence of states that starts in an initial state and moves by actions. The specification is the set of all behaviours it allows. Nothing in it says which action happens when several could. That is the point: every possible interleaving, every order of message delivery, a crash at any moment, are all simply behaviours, and all are covered.

What you then ask of a specification is whether a property holds for all of its behaviours. There are two kinds.

SafetyLiveness
SaysNothing bad ever happensSomething good eventually happens
ExamplesNo two leaders in one term. No committed entry is lost. No participant commits while another abortsEvery request is eventually answered. A leader is eventually elected
Usual formAn invariant: a condition true in every reachable stateA temporal formula about whole behaviours
A violation isA finite sequence of steps ending in a bad stateAn infinite behaviour in which the good thing never comes
To checkVisit every reachable stateHarder: needs assumptions about fairness, and a search for cycles

Most of the value in practice comes from invariants, and writing one is half the benefit. To state "no acknowledged write is ever lost" precisely, you must say what "acknowledged" and "lost" mean in terms of the variables, and designs often turn out to be undecided on exactly that.

A specification is not the program. It leaves out everything that doesn't bear on the property: data formats, performance, most error handling. A whole replication protocol is typically a few hundred lines. The skill is in choosing what to leave out.

A small TLA+ spec

Here is two-phase commit from Chapter 21, closely following the specification Lamport uses to teach the language. RM is the set of participants, called resource managers, and the transaction manager, TM, is the coordinator.

---------------------------- MODULE TwoPhase ----------------------------
CONSTANT RM                              \* the participants, for example {"r1", "r2", "r3"}
VARIABLES rmState, tmState, tmPrepared, msgs

Init == /\ rmState = [r \in RM |-> "working"]
        /\ tmState = "init"
        /\ tmPrepared = {}                \* participants the coordinator has heard "prepared" from
        /\ msgs = {}                      \* every message ever sent

RMPrepare(r) == /\ rmState[r] = "working"
                /\ rmState' = [rmState EXCEPT ![r] = "prepared"]
                /\ msgs' = msgs \cup {[type |-> "Prepared", rm |-> r]}
                /\ UNCHANGED <<tmState, tmPrepared>>

RMChooseToAbort(r) == /\ rmState[r] = "working"
                      /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
                      /\ UNCHANGED <<tmState, tmPrepared, msgs>>

TMRcvPrepared(r) == /\ tmState = "init"
                    /\ [type |-> "Prepared", rm |-> r] \in msgs
                    /\ tmPrepared' = tmPrepared \cup {r}
                    /\ UNCHANGED <<rmState, tmState, msgs>>

TMCommit == /\ tmState = "init"
            /\ tmPrepared = RM            \* every participant has said "prepared"
            /\ tmState' = "committed"
            /\ msgs' = msgs \cup {[type |-> "Commit"]}
            /\ UNCHANGED <<rmState, tmPrepared>>

TMAbort == /\ tmState = "init"
           /\ tmState' = "aborted"
           /\ msgs' = msgs \cup {[type |-> "Abort"]}
           /\ UNCHANGED <<rmState, tmPrepared>>

RMRcvCommitMsg(r) == /\ [type |-> "Commit"] \in msgs
                     /\ rmState' = [rmState EXCEPT ![r] = "committed"]
                     /\ UNCHANGED <<tmState, tmPrepared, msgs>>

RMRcvAbortMsg(r) == /\ [type |-> "Abort"] \in msgs
                    /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
                    /\ UNCHANGED <<tmState, tmPrepared, msgs>>

Next == \/ TMCommit \/ TMAbort
        \/ \E r \in RM : TMRcvPrepared(r) \/ RMPrepare(r) \/ RMChooseToAbort(r)
                          \/ RMRcvCommitMsg(r) \/ RMRcvAbortMsg(r)

Consistent == \A r1, r2 \in RM : ~ (rmState[r1] = "aborted" /\ rmState[r2] = "committed")
=========================================================================

How to read it:

  • /\ is "and", \/ is "or", ~ is "not", \in is "is a member of", \cup is union, \A is "for all" and \E is "there exists".
  • A plain variable is its value in the current state, and a primed one, rmState', is its value in the next. So each action is a formula relating two states. The lines without primes are the action's guard and the lines with them are its effect.
  • [rmState EXCEPT ![r] = "prepared"] is the function rmState with one entry changed. UNCHANGED lists the variables that stay as they are, and every action must account for every variable.
  • Next says that a step is any one of the actions, for any participant. Consistent is the invariant to check.

Two modelling choices are worth noticing, as they recur in almost every specification of a distributed protocol. Messages are a set that only grows. An action that needs a message checks that it is in the set and doesn't remove it. So a message can be received at any later time, more than once, or never, which covers delay, duplication, reordering and loss in a single stroke. And failures need no special machinery: a participant that crashes is one whose actions simply don't happen, which the specification already allows.

Many engineers write in PlusCal instead, a notation that looks like pseudocode with labels marking atomic steps, and is translated automatically into TLA+.

Model checking

TLA+ comes with a model checker, TLC. Given a specification, values for its constants and a list of invariants, it does what the name of the technique says.

// What an explicit-state model checker does, in Java. A state must be a value: a record with equals and hashCode.
<S> Optional<List<S>> check(S init, Function<S, List<S>> next, Predicate<S> invariant) {
	Map<S, S> cameFrom = new HashMap<>();                    // doubles as the set of states already seen
	Deque<S> queue = new ArrayDeque<>(List.of(init));
	cameFrom.put(init, init);
	while (!queue.isEmpty()) {
		S s = queue.poll();
		if (!invariant.test(s)) return Optional.of(pathTo(s, cameFrom));   // breadth-first: no shorter path exists
		for (S t : next.apply(s))                              // every action that is enabled in s
			if (cameFrom.putIfAbsent(t, s) == null) queue.add(t);
	}
	return Optional.empty();                                   // every reachable state satisfies the invariant
}

It differs from the testing of Chapter 37 in three ways. It is exhaustive for the model it is given: when it reports no violation, there is none in that model, where a random test can only say it found none. A failure comes as a shortest counterexample, since the search is breadth-first, and a short trace is one that can be understood. And it examines the design, weeks or months before there is code to test.

The limit is the number of states. Each participant, each message and each possible value multiplies it, a growth known as state explosion. So models are kept small on purpose: three nodes, two values, two or three client requests. This is less of a restriction than it sounds. Experience bears out what is called the small-scope hypothesis: nearly every design error shows itself in a small configuration, since it needs only the few participants involved in the bad interleaving. A model that explores every behaviour of three nodes finds more than a test that samples the behaviours of fifty.

    Things to notice. With the design as specified and three participants, the checker visits 288 distinct states and finds none that breaks the invariant. The furthest is ten steps from the start. Look at the bars: 56 states for two participants, 288 for three, 1,568 for four, 8,832 for five and 50,816 for six, each one between five and six times the last. That is state explosion, and it is the reason three is the usual number.

    Now let a prepared participant give up. The checker stops after 436 states with a nine-step trace. r1 says "prepared" and the coordinator records it. r1 then times out and aborts. r2 and r3 prepare, and the coordinator, holding three "prepared" messages, commits. r2 commits. One participant has committed and one has aborted. It is Chapter 21's argument for why a prepared participant must wait, found by a machine, and by a route that few people would think of first.

    The third design commits on a majority. With three participants it fails in seven steps: two prepare, the coordinator commits, one of the two acts on it, and the third, which never promised anything, chooses to abort. Set the participants to 2 and that design passes, since a majority of two is both of them. A model that is too small can hide an error, as surely as one that is too large never finishes, and that is a reason to check more than one size.

    Industry use

    Formal methods had a reputation as an academic pursuit until a group of engineers at Amazon Web Services described, in 2014, how they had been using TLA+ since 2011 on the designs of their core services. Their account changed the general view, mostly by being practical. The engineers were not specialists and learned the language in a few weeks. The specifications were a few hundred lines. And they found errors that had passed design review, code review and extensive testing, in systems already carrying a great deal of traffic.

    The practice has since spread through the companies that build this course's subject matter. Microsoft's Azure Cosmos DB published specifications of its consistency levels. MongoDB specified its replication protocol and checked proposed changes against it. Elasticsearch redesigned its cluster coordination with a TLA+ model after years of split-brain reports. CockroachDB specified its parallel-commit protocol before implementing it. The Raft dissertation includes a TLA+ specification, and Kafka's replication protocol and its Raft-based controller have published ones. The pattern in each is the same: specify a protocol when it is new or being changed, and when an error in it would lose data.

    The honest limits. A specification verified correct says nothing directly about the code, which may not implement it. That gap is closed by other means: the simulation of Chapter 37, with the specification's invariants as its assertions, or checking recorded traces of the real system against the model. The checker proves the property for the sizes it ran, and for all sizes only by argument or a separate proof tool. And the specification models the failures you thought to include: if disks in the model never lose data, the result assumes that they don't.

    📐
    Use case: thirty-five steps to lose data in DynamoDB

    The paper that made the case for TLA+ in industry, "How Amazon Web Services Uses Formal Methods", was written by seven AWS engineers and gives several examples in enough detail to judge. The best known concerns DynamoDB. The service's replication and fault-tolerance design had been through the company's usual process: design documents, reviews by senior engineers, code review, and a large programme of testing that included fault injection of the kind in Chapter 37. An engineer wrote the design as a TLA+ specification and ran the model checker over it on a cluster of machines. It found a sequence of events, a particular interleaving of failures and recovery steps with ordinary processing, that led to data being lost. The shortest trace exhibiting the bug was thirty-five steps long. The authors' comment is the argument of this chapter in a sentence: the chance of a human reviewer, or a test, arriving at that exact sequence was negligible, and yet in a service handling that volume of requests, rare sequences occur. The paper lists other finds, in S3, in the storage system behind EC2's disks and in an internal lock manager, some in designs and some in optimisations that engineers had proposed and wanted to know were safe. That second use is the one the authors stress. With a checked specification in hand, a team can make an aggressive change to a subtle protocol and learn within hours whether it is sound, where before the choice was between leaving the performance on the table and taking a risk nobody could measure. They also report what didn't work, which lends the rest credibility: the notation was unfamiliar at first, the tools could not check everything they wanted, and performance problems, as opposed to correctness, were outside what the method addresses.

    ⚠️
    Common mistakes
    • Specifying the code. A specification with every field and every error path is unreadable and uncheckable. Model the protocol.
    • Checking an invariant on a model that can't do anything. A guard that is never true makes every property hold. Confirm the good outcome is reachable.
    • A large model. Five nodes and ten values will not finish. Three and two find almost everything.
    • Assuming a checked specification means correct code. The implementation still has to match it, and that needs testing.
    • Modelling a kinder world. If messages in the model are never lost or repeated, the result holds only for a network like that.
    • Only safety. A protocol that never does anything is perfectly safe. State at least one liveness property, or check reachability.

    Interview drill

    Explain it simply: What is TLA+, and why would an engineering team use it?

    How a strong answer sounds
    TLA+ is a language for writing precise specifications of concurrent and distributed systems, created by Leslie Lamport. You describe the system as a state machine: a set of variables, the initial states, and the actions that can change the state. You then state properties, most often invariants, conditions that must hold in every reachable state, such as "there is never more than one leader per term" or "a committed entry is never lost". A model checker called TLC explores every reachable state of a small instance of the model, say three nodes, and either confirms the invariant holds or gives the shortest sequence of steps that violates it. Teams use it because the hardest bugs in distributed systems are design bugs that depend on rare interleavings of messages and failures. Those are almost impossible to find by reasoning or testing, but a model checker tries every interleaving. It is applied at design time, before code exists, when fixing a flaw is cheap. AWS, Microsoft, MongoDB, Elastic and others use it for replication, consensus and transaction protocols. It verifies the design, not the implementation, so it complements testing rather than replacing it.

    Deeper: The model checker reports no errors for three nodes. What have you actually learned, and what haven't you?

    How a strong answer sounds
    I've learned that for that specific model, three nodes, the chosen sets of values and any bounds I set, every reachable state satisfies the invariants I wrote, under the failure behaviours the specification allows. That is exhaustive for that configuration, which is far stronger than any amount of random testing of it. What I haven't learned. First, nothing about larger configurations in a strict sense. In practice the small-scope hypothesis says most protocol bugs appear with very few nodes and values, so I get high confidence, and I can raise it by running four or five nodes with symmetry reduction, or by writing an inductive invariant and proving it for all sizes with a proof system. Second, I have only checked the properties I stated. If my invariant is weaker than the real requirement, or I forgot one, the checker is silent. I'd sanity-check by confirming that desirable states are reachable, so the spec isn't vacuous, and by deliberately breaking the spec to see the checker catch it. Third, the model's fault assumptions: if I modelled message loss but not duplication, or crashes but not disk corruption, the result holds only under those assumptions. Fourth, liveness: an invariant check says nothing about whether the system makes progress; that needs temporal properties and fairness assumptions. And fifth, the big one: the implementation. The code may diverge from the spec. To bridge that I would turn the spec's invariants into runtime assertions, use deterministic simulation or Jepsen-style tests against the implementation, and where possible check traces from the real system against the model.

    🧠 Key takeaways

    • A specification describes a design as a state machine: variables, initial states, and actions with guards and effects.
    • Safety says nothing bad happens, usually as an invariant over every reachable state. Liveness says something good eventually does.
    • In TLA+ an action relates the current state to the next, written with primed variables. Messages as a growing set model loss, delay and duplication.
    • A model checker visits every reachable state of a small model and returns a shortest counterexample.
    • State counts explode, so models are small, and small models find nearly all design errors.
    • A checked specification verifies the design. Matching the code to it is a separate job, for testing.

    Check your understanding

    Which of these is a safety property?

    It says a bad thing never happens, and a violation is a finite trace ending in a bad state. The other three are liveness properties.

    In a TLA+ action, what does a primed variable such as tmState' stand for?

    An action is a formula over two states. Unprimed variables are the current state and primed ones the state after the step.

    The specification models the network as a set of messages that is only ever added to. What does that capture?

    A receive action only requires the message to be in the set, so it can fire at any time, repeatedly, or not at all.

    Why does a model checker's counterexample tend to be short?

    Every state at depth k is examined before any at depth k + 1. Random testing has no such guarantee and usually needs separate shrinking.

    A specification passes the model checker. Which statement is justified?

    The result covers that model, those invariants and those assumptions. Larger sizes, liveness and the code each need something more.
