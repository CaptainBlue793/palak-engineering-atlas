Testing: Jepsen & Deterministic Simulation

Every protocol in this course came with an argument for why it is correct. An argument covers the algorithm, and what runs in production is ten or a hundred thousand lines of code that someone typed. The bugs that matter in that code share a description: they need a particular message to be delayed past a particular timeout while a particular node restarts. A unit test doesn't arrange that. An integration test on a healthy cluster doesn't either, and a week of load testing may well not. Then it happens in production on some Tuesday, loses data, and can't be reproduced. For a long time the industry's answer was to be careful and wait for the reports. Two practices changed that. One attacks a real cluster from outside, cutting its network and killing its processes while clients record everything they are told, and then checks the record against the guarantee the system claims. The other runs the entire cluster inside a simulator in which the network, the disks and the passage of time are all controlled by one random seed, so that years of bad luck fit into an afternoon and any failure can be replayed exactly. This chapter covers both, and the testing of the one thing neither can reach: the production system and the people who run it.

Why unit tests miss it

A distributed system's behaviour is a function of its inputs and also of everything it doesn't control: the order in which messages arrive, how long each takes, which are lost, when each process pauses or dies, what each clock reads. A test that exercises the code with one such schedule, the fast and orderly one of a developer's laptop, has examined one path through a space of billions.

A study published in 2014 looked at how such systems really fail. Its authors took 198 failures reported by users of Cassandra, HBase, HDFS, MapReduce and Redis, and traced each to its cause. Almost all of the catastrophic ones, 92%, came from mishandling an error the software had itself detected: an exception caught and ignored, a handler that logged and carried on, a "this can't happen" that did. Nearly all could be reproduced on three nodes or fewer. The bugs were neither exotic nor confined to enormous clusters. They sat in error-handling code that had never once been run, since nothing in testing ever made the error occur.

So the missing ingredient is the faults, applied to the real code, in great variety, together with a way to tell afterwards whether the system kept its word.

Jepsen

Jepsen is a testing library, and a long series of published analyses, by Kyle Kingsbury, begun in 2013. Its stance is that of a sceptical customer. It takes a database as shipped, reads what the documentation promises, and tries to catch the database breaking the promise. It needs no access to the source.

The third kind of completion is where the care goes. A write that timed out may have taken effect, may yet take effect later, or may never do so (Chapter 4). The checker has to allow for all three, or it will accuse a correct system or excuse a broken one. In practice the plainest findings need no subtle checking: add a thousand distinct elements to a set, acknowledge each one, partition and heal, and read the set back. An acknowledged element that is missing is lost data, with no room for argument.

The published analyses found acknowledged writes lost, stale reads and broken isolation in a large share of the well-known databases and queues, often in the default configuration, and in several cases in behaviour the documentation said couldn't happen. Many vendors now commission the tests before a release. Two limits apply. A test that passes shows that no violation was found in a few hours of random faults, not that none exists. And when one is found, reproducing it is hard, since the timing came from real clocks and real networks.

Linearizability checking

For a store that claims linearizability, the checker's question is the one from Chapter 11: is there some order of the operations, one that respects real time, in which a single correct copy of the data would have given every client the answer it received? The standard algorithm, due to Wing and Gong, searches for such an order.

// Can the remaining operations be put in an order the model accepts?
boolean linearizable(Set<Op> remaining, Model state) {
	if (remaining.isEmpty()) return true;
	for (Op op : couldBeNext(remaining)) {                     // those that no other remaining op finished before
		Optional<Model> after = state.apply(op);               // would one copy of the data have given this result?
		if (after.isPresent() && linearizable(without(remaining, op), after.get())) return true;
	}
	return false;                                               // no order explains what the clients saw
}

The search is exponential in the worst case, and the problem is known to be NP-complete. Operations that overlap in time can be ordered either way, so the cost grows with how many are in flight at once, and an operation that timed out overlaps everything after it for the rest of the test. Real checkers remember states they have already ruled out, and split the history by key, since a history is linearizable exactly when each key's is. Even so, tests are designed round the checker: few clients, short histories, many independent keys.

For transactions the approach is different. Jepsen's Elle checker has clients append unique values to lists. From the lists read back, it can tell which transaction saw which other's effects, builds a graph of who must have preceded whom, and looks for cycles. A cycle is an isolation anomaly of the kinds catalogued in Databases, Isolation Anomalies. This takes time roughly proportional to the size of the history, where the search above takes exponential time, and it returns the offending transactions as a counterexample.

Deterministic simulation

Jepsen's weakness is that the real world supplies the timing. The alternative is to supply it yourself. In deterministic simulation testing the whole cluster, every node, runs as one single-threaded program. The code under test is the real code, and everything through which the outside world reaches it has been replaced:

  • The network is a queue in memory. The simulator decides when each message is delivered, or that it never is.
  • The clock is a variable. Time passes when the simulator advances it, so a thirty-second timeout takes no real time at all.
  • The disk is a structure in memory that can be slow, fail a write, or lose whatever wasn't flushed when a "machine" loses power.
  • Scheduling is the simulator's event loop. There are no real threads, so there is no interleaving that the simulator didn't choose.
  • Randomness comes from one generator with one seed, and every choice above is drawn from it.

With nothing left to chance, the seed determines the run completely. Three things follow. A failure found on seed 81,422 happens again on seed 81,422, on anyone's machine, with a debugger attached and extra logging added. Faults can be injected at rates no real cluster would survive, a partition every few seconds for a simulated month, so that the rare combination comes up in minutes. And since simulated time costs nothing, one core tests many simulated hours each second, and a few hundred cores running overnight cover more failure scenarios than the software will meet in years of production.

// The code under test may touch the world only through this.
interface Env {
	long now();
	long random();
	void send(NodeId to, Message m);
	void schedule(Duration after, Runnable task);
}

final class SimEnv implements Env {                          // production has a second implementation, on real sockets and clocks
	private final SplittableRandom rng;                         // the seed is the whole run
	private final PriorityQueue<Event> queue = new PriorityQueue<>(comparing(Event::at).thenComparing(Event::seq));
	private long clock, seq;

	public void send(NodeId to, Message m) {
		if (partitioned.contains(to) || rng.nextInt(100) < dropPercent) return;        // lost
		schedule(Duration.ofMillis(1 + rng.nextInt(500)), () -> nodes.get(to).onMessage(m));   // delayed, so reordered
	}
	public void schedule(Duration after, Runnable task) { queue.add(new Event(clock + after.toMillis(), seq++, task)); }

	void run(int events) {
		for (int i = 0; i < events && !queue.isEmpty(); i++) {
			Event e = queue.poll();
			clock = e.at();                                   // time jumps to the next thing that happens
			e.task().run();
			maybeInjectFault();                              // crash, restart, partition, heal: all drawn from rng
			checkInvariants();                               // after every single step
		}
	}
}

The price is discipline, and it must be paid from the first day. One call to the system clock, one real thread, one iteration over a hash map whose order depends on memory addresses, and the run is no longer repeatable. So the technique suits software designed for it from the start, and is hard to add to a codebase that grew without it. A newer line of work moves the determinism beneath the software, into a hypervisor that makes a whole virtual machine repeatable, so that existing systems can be tested the same way unmodified.

C, which has heard nothing, calls an election, and A and B both vote for it without comparing logs. C is leader with an empty log. Now press "Replay" a few times. The fingerprint doesn't change: the same five events, in the same order, every time. A test on real machines can't offer that, and it is what lets an engineer put a breakpoint on the fourth event.

    Consider what kind of test would have missed this. Every operation in the run succeeded and nothing returned an error. If C had received A's log before calling its election, as it would on a quiet network, its victory would have been harmless. Then change to the correct rule and run a thousand seeds, and more. In a test of 40,000 seeds, about 746,000 events, the invariant never broke. The message under the panel words that result with care, and so should anyone reporting one.

    Chaos in production

    Simulation tests the software. It can't test what the software runs inside: the load balancer's health checks, a timeout set in a configuration file two years ago, a dependency nobody listed, a dashboard that will or won't show the problem, an alert that will or won't fire, a runbook that was last correct before the migration, and the engineer who will be woken. Those are tested by the production system or not at all.

    Chaos engineering is the practice of causing failures there on purpose, as experiments. It grew out of Netflix's move to the cloud around 2010, when the company wrote a tool, Chaos Monkey, that terminated production servers at random during working hours. The reasoning was that instances in the cloud would disappear without warning in any case, and a team whose service met that every day would build it to cope, and would find out on a weekday afternoon with everyone at their desks. Larger exercises followed, up to routing all traffic away from an entire region to prove that it could be done. An experiment has a fixed form:

    1. Define steady state in terms of something users feel: orders per minute, successful playbacks.
    2. State a hypothesis: "if one cache node dies, steady state holds".
    3. Inject the fault with a limited blast radius: one instance, one percent of traffic, one zone, and a tested way to stop.
    4. Compare with a control group. If steady state held, confidence has been earned. If it didn't, a weakness was found at a chosen time, with the people who can fix it watching.

    The methods are complements. Simulation and Jepsen search for wrong answers. Chaos experiments search for wrong assumptions about the system as it is deployed. A team that has neither a tested failover nor a rehearsed response has no evidence that either works.

    🧪
    Use case: FoundationDB, the database that was built inside its simulator

    FoundationDB is a distributed, transactional key–value store, begun as a company in 2009, bought by Apple in 2015 and open-sourced in 2018. It is the reference example of deterministic simulation because of the order in which it was built. Before writing the database, its founders spent their first years on the tools for testing one. They created an extension to C++, called Flow, that let them write all concurrent code as single-threaded actors, with every use of the network, the disk and the clock passing through interfaces. Those interfaces had two implementations from the beginning: the real one, and a simulator that could run an entire cluster in one process, deterministically, from a seed. The database was then developed inside it. The simulator did more than reproduce ordinary faults. It was made actively hostile: machines rebooting together, disks filling, networks dropping and reordering, clocks drifting, and at chosen points in the code a facility the developers called "buggify", which makes a correct program behave in unusual and permitted ways, a slow reply here, a retry there, to push it down paths it would rarely take. Each night the company ran simulated clusters by the thousand, with an estimated accumulation, over the years, of the equivalent of a trillion hours of machine time. The claim made for this is specific: for long stretches the engineers found their bugs in simulation and their customers found almost none. It had a notable endorsement. Asked why Jepsen had not analysed FoundationDB, Kyle Kingsbury replied that their own testing appeared to be far more rigorous than his. The approach has since spread, to the financial database TigerBeetle, whose simulator runs continuously and publicly, and through a company founded by FoundationDB's former engineers that sells deterministic simulation as a service for software that wasn't built for it.

    ⚠️
    Common mistakes
    • Treating a passing test as proof. Random testing shows the presence of bugs. State how many seeds, or hours, and what faults.
    • Counting a timed-out operation as failed. It may have happened. A checker that assumes otherwise reports nonsense.
    • Testing only the paths that work. Most catastrophic failures start in an error handler nobody ran.
    • One source of real time or real randomness in a simulated system. The failing seed stops failing, and the bug is lost.
    • A simulator kinder than reality. If simulated disks never lose unflushed writes, the recovery code is untested.
    • Checking only at the end. Check invariants after every step, so that the failure is reported where it occurs.
    • Chaos experiments with no hypothesis and no stop button. That is an outage with extra steps.

    Interview drill

    Explain it simply: What is Jepsen, and how does it find bugs in distributed databases?

    How a strong answer sounds
    Jepsen is a framework for testing whether a distributed system actually provides the consistency guarantees it claims. It sets up a real cluster, usually five nodes, and runs concurrent clients performing operations such as reads, writes and compare-and-set, recording for each when it was invoked and how it completed: success, definite failure, or indeterminate, for example a timeout. While this runs, a component called the nemesis injects faults: network partitions, process crashes and pauses, clock skew. Afterwards the faults are healed and a checker analyses the recorded history against a model. For a system claiming linearizability, it searches for a sequential ordering of the operations, consistent with real-time order, that explains every result; if none exists, the system violated linearizability. For transactional systems it looks for dependency cycles that indicate isolation anomalies. It treats the database as a black box, so it finds bugs in the real binary, configuration and defaults. It has found lost acknowledged writes, stale reads and split-brain in many well-known systems. Its limits are that passing doesn't prove correctness, and failures can be hard to reproduce because timing is non-deterministic.

    Deeper: What is deterministic simulation testing, and what does it take to make a system testable that way?

    How a strong answer sounds
    It means running an entire distributed system, all nodes, inside a single-threaded simulator in which every source of non-determinism is controlled by one pseudo-random seed. The real application code runs, but the network, disk, clock and scheduler are simulated implementations behind interfaces. The simulator decides message delivery order and delay, drops messages, partitions the network, crashes and restarts nodes, corrupts or delays disk writes, and advances time, all from the seed. After each step it checks invariants. The benefits: perfect reproducibility, since the same seed gives the same execution, so a failure that occurs once in a million runs can be replayed and debugged; time compression, because simulated time advances instantly, so timeouts and long scenarios run in milliseconds; and far more aggressive fault injection than real hardware would produce, so rare interleavings are explored quickly. FoundationDB pioneered it and TigerBeetle and others use it. What it takes: the system must be written so that all I/O, time, randomness and concurrency go through abstractions. No direct calls to the system clock, no real threads or thread pools, no real sockets, no unseeded randomness, and no dependence on things like hash map iteration order or memory addresses. That is easy if designed in from the start and very hard to retrofit, which is why hypervisor-level approaches now exist. The simulator must also model failure realistically, especially disks losing unsynced writes. And it only tests what is inside the simulation: real kernels, real networks and operational issues still need Jepsen-style tests and chaos experiments.

    🧠 Key takeaways

    • Distributed bugs live in schedules and faults that ordinary tests never produce, and very often in error handlers that never ran.
    • Jepsen: real cluster, concurrent clients, a nemesis injecting faults, a recorded history, and a checker that compares it with the claimed guarantee.
    • A timed-out operation is unknown, not failed. Checkers must allow for both.
    • Linearizability checking searches for a valid order and is exponential in the worst case, so tests keep histories small and split them by key.
    • Deterministic simulation puts the network, disk, clock and scheduler under one seed: failures replay exactly and time costs nothing.
    • Chaos experiments test what the others can't: the deployed system, its configuration, its monitoring and its people.

    Check your understanding

    In a Jepsen history, a write is recorded as "info" after a timeout. How must the checker treat it?

    The outcome is unknown. Assuming either way would make the checker wrong about some correct or incorrect system.

    What does the nemesis do in a Jepsen test?

    The generator chooses operations, the nemesis breaks things, and the checker judges the recorded result.

    Why can a failure found by deterministic simulation be replayed exactly?

    With nothing left to chance, the seed fixes the whole execution. One uncontrolled clock or thread would break it.

    Why are linearizability tests kept to short histories on many independent keys?

    The search grows with the number of overlapping operations. Splitting by key keeps each search small.

    Which of these is a chaos experiment in production best placed to find?

    Configuration, monitoring and operational assumptions exist only in the deployed system. The others are better hunted by simulation and Jepsen.
