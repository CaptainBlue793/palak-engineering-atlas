Hashing for Distribution

When data doesn't fit on one machine, every key needs a home, and every client needs to find that home without asking a central directory. The standard trick is to hash the key and let the hash pick the server. This chapter covers what makes a hash function fit for that job, the simple hash mod N placement and the subtle ways it goes wrong, and the problem that motivates a whole later chapter: add one server to a mod N cluster and almost every key moves.

What a placement hash needs

Inside one JVM, a HashMap only needs a hash that is consistent for the life of the process. Across a cluster, the bar is higher. Every client, every server and every future version of the code must compute the same hash for the same key, or they will look for the data in different places. A placement hash needs to be:

  • Stable everywhere: defined only by the key's bytes, identical on every machine, JVM version and language. Object.hashCode() fails this outright: for objects that don't override it, the value differs between runs. String.hashCode() is specified by the Java language, so it is stable, but other languages won't compute it unless you copy the formula.
  • Uniform: keys spread evenly over the output range, including keys that are very similar, like user:1001 and user:1002.
  • Avalanching: changing one input bit flips about half of the output bits, so patterns in keys don't survive into the hash.
  • Fast: it runs on every request. Cryptographic hashes like SHA-256 are uniform but slower than needed; their extra property, resistance to deliberate collisions, matters only when attackers choose your keys.

hash mod N

The simplest placement takes the hash modulo the number of servers. It has one classic Java bug: Math.abs(h) % n. A hash can be Integer.MIN_VALUE, whose absolute value is itself (still negative), so about one key in four billion maps to a negative shard number and throws, rarely enough to pass every test. Math.floorMod always returns a value in [0, n):

import static java.nio.charset.StandardCharsets.UTF_8;

public final class ModPlacement {
	private static final HashFunction MURMUR = Hashing.murmur3_32_fixed();   // Guava
	private final List<String> servers;                                     // same order on every client!

	ModPlacement(List<String> servers) { this.servers = List.copyOf(servers); }

	String serverFor(String key) {
		int h = MURMUR.hashString(key, UTF_8).asInt();               // stable: bytes in, bits out
		return servers.get(Math.floorMod(h, servers.size()));        // never negative
	}
}

Note the comment on the server list. If two clients list the same servers in different orders, they disagree about every key. Placement depends on the hash function, the encoding, and the membership list, and all three must match everywhere. Try it with 1,000 keys:

Two lessons hide in the panel. First, similar keys and a structured hash interact with N. String.hashCode computes s[0]·31n−1 + … + s[n−1] in 32-bit arithmetic. For keys of the same length that share a prefix, like order-000001 to order-001000, the prefix adds the same constant to every hash and the other digits add multiples of 31, so modulo 31 only the last character varies: with 31 servers, those 1,000 orders land on just 10 servers, one per final digit. MurmurHash3 mixes every bit and doesn't care. Second, even a perfect hash gives only statistical balance: with 1,000 keys on 32 servers, the busiest server routinely has 50% more keys than the average. Real systems put many more keys, or many virtual nodes, on each server to smooth that out.

The reshuffle problem

Now add a server. With mod N, a key stays put only if h mod N equals h mod (N+1), which holds for about 1 in N+1 keys. Going from 4 to 5 servers moves about 80% of all keys; from 10 to 11, about 91%. For a cache cluster, a moved key is a miss. For a database, it's data that must be copied over the network before it can be served.

The fix is a placement where adding a server moves only that server's fair share, about 1/(N+1) of the keys, and removing one moves only the keys it held. Two families of algorithms do this, both covered properly in Chapter 19:

  • Consistent hashing: hash servers and keys onto the same circle; each key belongs to the next server clockwise. A new server takes over one arc and nothing else moves. Each server is placed at many points ("virtual nodes") to even out the arcs.
  • Rendezvous (highest-random-weight) hashing: for each key, compute hash(key, server) for every server and pick the highest. A new server wins only the keys where it scores highest.

Hashing balances keys, not load

Even perfect placement assumes every key costs the same. They don't. One celebrity's profile, one viral product, one tenant with a million users: a single hot key lands on one server whatever the hash function, and that server melts while the others idle. Hashing can't fix that, because all requests for the key must find the same server. The fixes live a level up: cache the hot key at many places, split it into sub-keys (counter#1 … counter#16) and combine on read, or route it specially. Chapter 20 covers them.

🎵
Use case: memcached and ketama

Early memcached client libraries placed keys with hash mod N. Every time an operator added or replaced a cache server, most of the cache effectively emptied, and the databases behind it took the load. In 2007 Last.fm released ketama, a client library that placed memcached servers on a hash ring with many points per server, so adding one server remapped only a small fraction of keys. Ketama-compatible hashing became an option in most memcached clients, and the same idea sits inside Dynamo, Cassandra and many load balancers today.

⚠️
Common mistakes
  • Placing data with Object.hashCode() or anything else that isn't defined purely by the key's bytes.
  • Math.abs(h) % n: negative for Integer.MIN_VALUE. Use Math.floorMod(h, n).
  • Different encodings or server orders on different clients, so they disagree about where keys live.
  • Using mod N for a cluster that grows, then discovering that every resize moves almost everything.
  • Trusting a weak hash with structured keys, especially when N shares factors with the hash's internals.
  • Assuming even keys means even load. One hot key can overload a server no matter how good the hash is.

Interview drill

Explain it simply: Why is hash(key) % N a poor way to spread keys across cache servers?

How a strong answer sounds
Because N changes. When you add or remove a server, a key keeps its server only if hash mod N happens to equal hash mod the new N, which is true for about one key in N+1. Going from 4 to 5 servers moves about 80% of the keys, so most cache lookups miss at once and the database behind the cache gets hammered. Consistent hashing or rendezvous hashing fix this: adding a server moves only about 1/(N+1) of the keys, the new server's fair share.

Deeper: A team shards by Math.abs(userId.hashCode()) % 31. What can go wrong?

How a strong answer sounds
Three things. Math.abs(Integer.MIN_VALUE) is still negative, so a rare key produces a negative shard and an exception; use Math.floorMod. String.hashCode is a polynomial in 31, so for IDs that share a prefix and length, modulo 31 it reduces to the last character: fixed-width numeric IDs land on only ten of the 31 shards. And mod-31 placement can't grow: moving to 32 shards relocates almost all data. I'd use a well-mixed hash like MurmurHash3 over the UTF-8 bytes and a placement that tolerates resizing, such as many fixed logical partitions mapped to physical shards.

🧠 Key takeaways

  • A placement hash must be defined by the key's bytes alone, identical on every machine and version.
  • Use a well-mixed non-cryptographic hash (MurmurHash3, xxHash); String.hashCode keeps structure from similar keys.
  • Use Math.floorMod, never Math.abs(h) % n.
  • hash mod N moves about N/(N+1) of all keys when one server is added.
  • Consistent and rendezvous hashing move only about 1/(N+1) of the keys (Chapter 19).
  • Hashing evens out keys, not load: hot keys need caching, splitting or special routing.

Check your understanding

A cache cluster using hash mod N grows from 4 to 5 servers. Roughly what fraction of keys now map to a different server?

A key stays only if h mod 4 equals h mod 5, about 1 key in 5. So about 4/5 = 80% move. Consistent hashing would move about 20%.

Why is Math.abs(hash) % n a bug?

Integer.MIN_VALUE has no positive counterpart in 32-bit two's complement. Math.floorMod(h, n) always returns a value in [0, n).

Why can't Object.hashCode() be used to choose which server stores a key?

Placement must be computed identically by every client and server. Identity hash codes are per-process. Hash the key's bytes with a fixed function.

With String.hashCode and N = 31 servers, the keys order-000001 to order-001000 land on only 10 servers. Why?

The prefix contributes one constant to all the keys, and every other digit term s[i]·31^k with k ≥ 1 is a multiple of 31. So the remainder mod 31 is set by the last character. A well-mixed hash removes such structure.

A perfectly uniform hash spreads keys evenly, yet one server is at 100% CPU while others idle. What is the most likely cause?

Hashing balances the number of keys, not the traffic per key. Hot keys need caching, splitting into sub-keys, or special routing.
