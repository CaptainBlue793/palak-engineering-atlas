System Design Building Blocks, Recapped

The System Design course treats load balancers, caches, databases and queues as boxes you connect. This course opens the boxes. Each one hides at least one hard distributed-systems problem: a load balancer is a failure detector, a replicated database is a consensus protocol, a queue is a promise about delivery. This chapter recaps the blocks in a page, sorts them by where the state lives, and maps every hidden problem to the chapter that solves it, so the rest of the course has an obvious place in the systems you already know how to draw.

Where state lives

The single most useful way to look at an architecture diagram is to ask of every box: if this machine vanished, what would be lost? A stateless tier (API servers, most load balancers) loses nothing: any copy can serve any request, so you add copies and put a load balancer in front. A stateful tier (databases, queues, coordination services) holds data that exists nowhere else, or exists in several places that must agree. Every hard problem in this course lives in the stateful tiers, which is why good designs push state into a small number of well-understood stateful systems and keep everything else stateless.

Even a few lines of ordinary application code lean on those stateful systems in ways that hide whole chapters:

Optional<Product> product(String id) {
	Product cached = cache.get(id);                       // which cache node owns id? (P6, Ch 19)
	if (cached != null) return Optional.of(cached);
	Product p = db.readReplica().find(id);              // how stale can a replica be? (Ch 9, 11)
	if (p != null) cache.set(id, p, Duration.ofMinutes(5));  // can this overwrite a newer value? (Ch 11)
	return Optional.ofNullable(p);
}

void placeOrder(Order o) {
	db.primary().insert(o);                                // what if the primary fails over mid-call? (P2, Ch 13)
	queue.publish(new OrderPlaced(o.id()));                  // what if we crash between the two lines? (Ch 22, 28)
}

The last comment is the dual-write problem, and it's a good example of how this course differs from System Design. There, "write to the database, then publish an event" is a fine box-and-arrow answer. Here, we ask what happens if the process dies between the two lines (the event is lost), or if the publish times out (unknown outcome, so maybe a duplicate), and we fix it with a transactional outbox and idempotent consumers.

Use case: GitHub, 21 October 2018

During routine maintenance to replace failing optical networking equipment, GitHub's US East Coast network hub lost connectivity to its main East Coast data centre for 43 seconds. Their database failover tool, Orchestrator, saw the primary MySQL servers as unreachable and promoted replicas in the West Coast data centre. When the network came back, both sides had accepted writes the other didn't have, and application traffic now crossed the continent to reach the new primaries, adding latency to every query. Reconciling the writes and restoring the original topology while preserving user data took 24 hours and 11 minutes of degraded service. Every block on this page was involved: a failure detector that fired on a short partition, a database failover across regions, replication that couldn't merge divergent writes, and queued background jobs held back until the data was consistent again. Chapters 5, 9, 13 and 32 each describe a piece of it.

What this course adds

System Design asks which blocks to use and how to connect them, at the level of a 45-minute whiteboard. This course asks how a block keeps its promise when machines fail and messages arrive late, at the level of protocols and code. Where the two courses meet, they link to each other: when you read about Raft here, System Design's distributed theory chapter shows where it sits in an architecture; when you design a key-value store there (case study), the quorum and anti-entropy chapters here show what's inside.

⚠️
Common mistakes
  • Drawing a box and assuming its guarantees. "Replicated database" says nothing about lag, failover or lost writes until you ask.
  • Keeping state in "stateless" servers: in-memory sessions or local files that vanish when the instance is replaced.
  • Dual writes to a database and a queue without an outbox; a crash between them loses or duplicates events.
  • Treating a cache as a database. If losing the cache loses data, it isn't a cache.
  • Automatic failover tuned shorter than real network blips, so a few seconds of partition triggers a cross-region promotion.
  • Forgetting the coordination service is a dependency. When etcd or ZooKeeper loses its majority, everything that needs a leader or a lock stalls.

Interview drill

Explain it simply: Why are stateless services easy to scale and make highly available, while databases are hard?

How a strong answer sounds
A stateless server holds nothing that isn't somewhere else, so any copy can handle any request: you add copies behind a load balancer, and if one dies, you lose only its in-flight requests, which clients retry. A database holds the only copy of data, or several copies that must agree. Scaling it means splitting data (and then handling cross-partition operations) or adding replicas (and then dealing with lag and conflicting writes). Making it available means failing over to a replica without losing acknowledged writes and without two primaries accepting writes at once, which is a consensus problem.

Deeper: Your design writes an order to the database and then publishes an "order placed" event to Kafka. What can go wrong, and how do you fix it?

How a strong answer sounds
It's a dual write with no atomicity. If the service crashes after the insert but before the publish, the event is lost and downstream services never learn about the order. If the publish times out, the outcome is unknown; retrying may publish it twice. If you publish first and the insert fails, consumers act on an order that doesn't exist. The usual fix is a transactional outbox: insert the order and an outbox row in one database transaction, then a relay (or change data capture) publishes outbox rows to Kafka with at-least-once delivery, and consumers deduplicate by event ID. That turns "exactly once" into "at least once plus idempotence".

🧠 Key takeaways

  • Every System Design building block hides a distributed-systems problem; this course opens the boxes.
  • Ask of every box: if this machine vanished, what would be lost?
  • Stateless tiers scale by adding copies; stateful tiers need replication, partitioning and agreement.
  • Load balancers are failure detectors; replicated databases are consensus or replication protocols; queues are delivery promises.
  • Ordinary code like "write then publish" hides real failure modes: dual writes, unknown outcomes, stale reads.
  • A short network partition can travel through every block, as GitHub's 2018 outage showed.

Check your understanding

Which question best separates the easy parts of an architecture from the hard ones?

Stateless components can simply be replicated. Components holding state need replication, consensus, partitioning and recovery, which is where distributed systems get hard.

A load balancer stops sending traffic to a server that missed three health checks. Which distributed-systems problem is it solving?

Health checks are heartbeats with a timeout. Chapter 5 covers how to tune them and why false positives are unavoidable.

A service inserts an order into its database and then publishes an event, as two separate calls. What failure is NOT handled?

Two independent writes aren't atomic. A transactional outbox writes the event in the same transaction as the order and publishes it afterwards.

In GitHub's October 2018 incident, why did a 43-second network partition cause about 24 hours of degraded service?

The partition was short; the failover it triggered created divergent writes on two sides, and reconciling them safely took most of a day.

The etcd cluster behind a Kubernetes control plane loses its majority. What is the most likely effect?

Without a majority, etcd can't commit writes. Existing pods keep running, but the control plane is frozen. Chapter 44 looks at this in detail.
