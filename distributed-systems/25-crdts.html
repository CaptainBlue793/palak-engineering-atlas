CRDTs: Data That Merges Itself

Any system that accepts writes in more than one place at once has to say what happens when two of them touch the same thing: two datacentres each taking orders, three Dynamo-style replicas on either side of a partition, a phone editing a document on a train. Chapter 8 showed how to detect that two versions are concurrent, and left the application holding both and a problem. The easy way out, keeping the one with the later timestamp, silently discards the other. A conflict-free replicated data type takes a different route. It is a counter, a set, a map or a text sequence whose merge operation is designed, with a little algebra, so that any two replicas can always be combined, in any order, any number of times, and reach the same result. Replicas need no coordination to accept a write and no arbitration to reconcile. This chapter covers the rule that makes that work, the standard types and what each costs, and the things a CRDT cannot do.

The rule that makes merging safe

Replicas exchange state over a network that delays, reorders and duplicates (Chapter 2). So a merge function, written here as ⊔, will be applied in unpredictable orders and sometimes twice to the same input. Three properties make that harmless.

PropertyIn symbolsWhat it protects against
Commutativea ⊔ b = b ⊔ aTwo replicas merging in opposite directions
Associative(a ⊔ b) ⊔ c = a ⊔ (b ⊔ c)Updates arriving grouped or relayed in different ways
Idempotenta ⊔ a = aThe same state delivered twice

Taking the larger of two numbers has all three: max(3, 5) is max(5, 3), grouping doesn't matter, and max(5, 5) is 5. So does set union. Addition fails the third, since 5 + 5 isn't 5, which is why a counter can't simply be merged by adding. The whole craft of CRDTs is to express a useful data type so that its merge is a maximum or a union underneath.

The second requirement is on updates: an update may only move the state upwards in the order that merge defines. A set grows. A per-replica count rises. Nothing is ever taken back, since a merge with a peer that hadn't heard would bring it back anyway. Deleting therefore has to be represented as adding something: a record that the deletion happened.

With both in place the type gives strong eventual consistency: any two replicas that have received the same set of updates are in the same state, whatever order they arrived in, with no conflicts to resolve and nothing to roll back. The name and the framework come from a 2011 paper by Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski.

G-Counter and PN-Counter

A counter of likes or page views, incremented at three replicas. If each stored a single number and merged by taking the larger, concurrent increments would be lost: 5 and 5, each having added one to 4, merge to 5 and not 6. The fix is to stop sharing a number. Each replica counts its own increments in its own slot, and no replica ever writes another's slot.

final class GCounter {                                           // grow-only
	private final Map<String, Long> counts = new HashMap<>();   // replica → how many it has added

	void increment(String me) { counts.merge(me, 1L, Long::sum); }   // only ever my own entry
	long value() { return counts.values().stream().mapToLong(Long::longValue).sum(); }
	void merge(GCounter other) { other.counts.forEach((replica, n) -> counts.merge(replica, n, Math::max)); }
}

final class PNCounter {                                          // can go down as well
	private final GCounter added = new GCounter(), removed = new GCounter();

	void increment(String me) { added.increment(me); }
	void decrement(String me) { removed.increment(me); }          // a decrement is an increment of the other counter
	long value() { return added.value() - removed.value(); }
	void merge(PNCounter other) { added.merge(other.added); removed.merge(other.removed); }
}

The value is the sum of the slots, and merge takes the maximum slot by slot. A slot only ever rises, and only its owner raises it, so the larger of two copies of a slot is always the more recent, and the maximum loses nothing and counts nothing twice. It is the vector of Chapter 8 put to a different use. A counter that must also go down can't lower a slot, since the maximum would restore it. So a PN-Counter keeps two grow-only counters, one of increments and one of decrements, and reports the difference.

Registers and sets

A register holds one value. The LWW register of Chapter 6 is a CRDT: its state is a value with a timestamp, and merge keeps the higher timestamp, which is a maximum. It converges, and it does so by discarding every concurrent write but one. The multi-value register keeps all concurrent values, the siblings of Chapter 8, and hands them to the reader.

Sets show the design problem most clearly. A grow-only set merges by union and can't remove. A two-phase set adds a second set of removed elements, called tombstones, and reports "added and not removed". It converges, and an element once removed can never be added again, since the tombstone is permanent and always wins.

The useful one is the observed-remove set, the OR-Set. Each add attaches a fresh unique tag to the element. A remove cancels exactly the tags that the removing replica has seen. An add that happens concurrently elsewhere has a tag the remover never saw, and survives. So if one replica removes "milk" while another adds it, the result contains milk: add wins, and an element can be removed and added again freely.

final class ORSet<E> {
	private final Map<E, Set<UUID>> tags = new HashMap<>();     // every add gets its own tag
	private final Set<UUID> removed = new HashSet<>();          // tags cancelled by a remove

	void add(E e) { tags.computeIfAbsent(e, k -> new HashSet<>()).add(UUID.randomUUID()); }
	void remove(E e) { removed.addAll(tags.getOrDefault(e, Set.of())); }   // only the adds seen here
	boolean contains(E e) {
		return tags.getOrDefault(e, Set.of()).stream().anyMatch(tag -> !removed.contains(tag));
	}
	void merge(ORSet<E> other) {                                 // two unions
		other.tags.forEach((e, ts) -> tags.computeIfAbsent(e, k -> new HashSet<>()).addAll(ts));
		removed.addAll(other.removed);
	}
}

This version keeps every tag for ever. Production implementations replace the tombstones with a version vector that summarises which tags each replica has seen, so that a removed tag can be dropped, at the price of a subtler merge. Maps are built from the same parts: a map whose keys form an OR-Set and whose values are themselves CRDTs, merged key by key.

Things to notice. Press "Play the awkward case" under each type. For the counters it makes four increments with no sync between them: one at A, one at B, two at C. Under last-write-wins all three replicas agree afterwards, on 2. The copy with the highest stamp replaced the others whole, and two increments are gone with no error anywhere. The PN-Counter gives 4: its state after merging is P [1, 1, 2].

For the sets the awkward case is a removal racing an add. All three have milk. A removes it, and at the same moment B adds it. The two-phase set ends with milk removed, permanently: press "+ milk" on any replica afterwards and nothing changes. The OR-Set ends with milk present. Look at its tags: A1 is struck through, and B1, which A never saw, is live. Then try your own sequences. Sync in any order, or the same pair five times running, and the replicas always end in agreement.

Sequence CRDTs

Text is the hardest case, and the one behind collaborative editors. A document is a sequence of characters, and "insert at position 5" means different things on two replicas once one of them has inserted at position 2. Positions are not stable, so a sequence CRDT doesn't use them.

Each character gets a permanent unique ID when it is typed, a pair of a counter and the replica's name, as in a Lamport timestamp (Chapter 7). An insert is recorded as "new character X, with this ID, placed after the character with that ID". A delete marks a character as a tombstone and leaves it in the structure, since other replicas may still be inserting after it. When two replicas insert after the same character concurrently, the tie is broken by comparing IDs, the same way everywhere.

ReplicaStarts withOperationSees locallyAfter merging
AliceC A Tinsert H, ID 4.alice, after CC H A TC R H A T on both: two inserts after C, ordered by ID, and "4.bob" sorts above "4.alice"
BobC A Tinsert R, ID 4.bob, after CC R A T

Both replicas reach the same text and neither edit is lost. Whether "CRHAT" is what either person meant is another matter: a CRDT guarantees agreement, not intent. This design is known as RGA, a replicated growable array, and it is the basis of the Automerge library. Yjs uses a close relative. Their practical difficulty is size, since every character ever typed carries an ID and deleted ones stay as tombstones, and much of the engineering in those libraries is compact encoding. The older technique, operational transformation, which Google Docs uses, rewrites incoming operations against concurrent ones and needs a central server to order them.

What a CRDT can't do

  • Enforce a rule that spans replicas. A PN-Counter holding a stock level of 1 lets two replicas each sell one unit, and merges to −1. "Never below zero", "usernames are unique" and "at most one leader" all need replicas to agree before acting, which is coordination (Chapters 16 to 18). A CRDT can't provide it.
  • Forget cheaply. Tombstones and per-replica slots accumulate. Removing them safely needs to know that every replica has seen them, which is itself a coordination problem. A replica that leaves the cluster for good leaves its slot behind.
  • Read your intent. The merge is fixed when the type is chosen: add wins, or remove wins, or the last writer wins. If none of those is what the business means, the type is the wrong one.
  • Give a current answer. A read returns what this replica has heard so far. The model is eventual consistency, with the guarantee that it is also conflict-free.

Use case: Figma, CRDT ideas with a server in the middle

Figma lets many people edit one design file at once, and its engineers described the design in 2019. They studied CRDTs and operational transformation and took a deliberately simpler path, which is instructive about what the theory is for. A Figma document is a tree of objects, and each object is a set of properties: position, colour, parent. A change is a triple of object, property and new value. Two changes to different properties, or different objects, never conflict. Two changes to the same property of the same object are settled as a last-writer-wins register, with one difference from the textbook: Figma has a central server that every client talks to, so "last" is simply the order in which changes reach the server, and no timestamps or clock comparisons are needed. That is not strictly a CRDT, which would need no central authority, and the team said so. What they kept from CRDTs was the shape: every value is a small register with a deterministic merge, so there is no general conflict-resolution step at all. The harder cases got specific answers. New objects take IDs generated by the client, a client number plus a counter, so two people creating objects never collide. The order of children under a parent uses a fractional position between its neighbours, so inserting between two objects never renumbers the others. Moving an object is a change to its parent property, and the server rejects any move that would create a cycle, a rule spanning objects that no merge function could enforce. Text was at first a single property, so two people typing in the same text box got last-writer-wins on the whole string. The lesson is the one from the previous section, applied well: use self-merging types where concurrent edits are independent, and use the coordinator you already have for the invariants.

⚠️
Common mistakes
  • Calling last-write-wins "conflict resolution". It resolves a conflict by deleting one side of it.
  • Merging counters by adding or by taking the maximum of a single number. One double-counts on a repeat, the other loses concurrent increments.
  • Using a CRDT for something with an invariant. Balances, stock and uniqueness need coordination.
  • Ignoring metadata growth. Tombstones and slots for long-gone replicas can outweigh the data.
  • Op-based CRDTs over a channel that can drop or repeat. They assume exactly-once, causal delivery.
  • Sharing a replica ID between two devices or processes. Both write the same slot, and the maximum then loses updates.

Interview drill

Explain it simply: What is a CRDT, and how does a counter CRDT avoid losing increments?

How a strong answer sounds
A CRDT is a data type designed so that replicas can be updated independently, without coordinating, and can always be merged automatically to the same result. The trick is that the merge function is commutative, associative and idempotent, so it doesn't matter in what order replicas exchange state or whether they receive the same state twice; any replicas that have seen the same updates end up identical. That is called strong eventual consistency. For a counter: a single shared number doesn't work, because if two replicas both go from 4 to 5 there is no way to merge 5 and 5 into 6. A G-Counter instead keeps one count per replica. Each replica increments only its own entry, the value is the sum of the entries, and merge takes the element-wise maximum. Since each entry only grows and has a single writer, the max is always the latest value of that entry, so no increment is lost or double-counted. For decrements, a PN-Counter keeps two G-Counters, one for increments and one for decrements, and the value is the difference.

Deeper: You are building a shopping cart that works offline on two devices. Which CRDT, and what are its limits?

How a strong answer sounds
The cart is a map from item to quantity, so I would use an OR-Map: the keys are an observed-remove set and each value is a PN-Counter for the quantity. With an OR-Set, each add creates a unique tag and a remove only cancels the tags it has observed. So if one device removes an item while the other, offline, adds it, the add wins and the item is kept; that is the safer default for a cart, and it avoids the two-phase set's problem that a removed item can never be re-added. Quantities merge as counters, so "plus one" on both devices gives plus two rather than last-write-wins. Each device needs a stable unique replica ID, since two devices sharing an ID would corrupt the counters. Limits. First, add-wins has an anomaly: an item deleted on one device can reappear after sync if the other device touched it, which the Dynamo paper noted for its cart; I would show it and let the user remove it again. Second, metadata: tags and tombstones accumulate, so I would use an optimised OR-Set with dots and a version vector rather than explicit tombstones, and reset the state at checkout, which is a natural point to coordinate. Third, no invariants: the cart can't enforce "at most five per customer" or stock availability while offline; those are checked when the order is placed, on the server, as an ordinary transaction. Fourth, I would send deltas rather than full state to keep sync small. And I'd avoid LWW for the cart as a whole, because it would silently drop one device's changes.

🧠 Key takeaways

  • A CRDT's merge is commutative, associative and idempotent, so order and duplication don't matter and replicas converge.
  • Updates only move state upwards. A delete is recorded as an addition: a tombstone or a second counter.
  • State-based CRDTs ship state and tolerate any network. Op-based ones ship operations and need reliable causal delivery.
  • G-Counter: one slot per replica, merged by maximum. PN-Counter: two of them.
  • OR-Set: every add has a unique tag, and a remove cancels only the tags it has seen, so a concurrent add survives.
  • Sequence CRDTs give each character a permanent ID and position it relative to another ID.
  • CRDTs can't enforce invariants across replicas, and their metadata grows. LWW is a CRDT that discards data.

Check your understanding

Why must a state-based CRDT's merge be idempotent?

Networks and gossip repeat messages. A merge that added, say, would count the repeat.

Two replicas hold G-Counter states [3, 1] and [2, 4]. What is the merged state and its value?

Merge takes the maximum of each replica's entry, and the value is their sum.

Replica A removes "milk" from an OR-Set while replica B, concurrently, adds "milk". After they merge, is milk in the set?

A remove cancels only the tags it saw. This is the "add wins" behaviour.

Which of these can a CRDT not guarantee without help?

An invariant across replicas needs them to agree before acting. Two concurrent withdrawals each look fine locally.

Why doesn't a sequence CRDT record an insert as "at position 5"?

A permanent ID for each character, and "insert after ID X", mean the same thing everywhere.
