Case Study: etcd & Kubernetes

Kubernetes runs a large share of the world's server software, and it is built on a deliberately narrow foundation. Every fact about a cluster, each machine, each container that should be running, each secret, each piece of configuration, is a small document in one database, etcd, three or five machines replicated by Raft. Everything else in Kubernetes is a program that reads those documents, watches them for changes and writes documents back. No component gives another an order. The scheduler doesn't tell a machine to start a container: it writes a machine's name into a document, and a program on that machine, which has been watching, sees it. The whole system is a set of independent loops arranged round a consistent store with a change feed, and that structure is why a cluster keeps its balance through the loss of machines, of network links, and of its own control components. It is also why the store's health is the cluster's. This chapter looks at what Kubernetes needs from etcd, how the watch mechanism of Chapter 31 becomes an architecture, what keeping history costs, and what fails, and what doesn't, when the store does.

A cluster built on one store

A Kubernetes user doesn't issue commands. They submit a description of what should exist, "three copies of this container, reachable on port 80", and the cluster makes it so and keeps it so. The description is stored as an object. Separate programs called controllers each watch some kind of object and work to make the world match it. Only one component, the API server, talks to etcd. Everything else, the controllers, the scheduler, the agent on each machine (the kubelet) and the user's own tools, talks to the API server.

This shape is a choice with consequences. Any component can crash and restart without anyone needing to know, since its instructions are in the store and it will read them again. Components can be added without changing the others. And every interaction is recorded as a change to an object, which makes the system observable with one tool. The cost is that everything depends on one store and one change feed being correct and available.

etcd's Raft

etcd is a key–value store replicated by Raft across an odd number of members, three in most clusters and five in large ones. Every write goes to the leader, is appended to its log and forced to disk, and is acknowledged once a majority has done the same. Reads are linearizable by default: the leader confirms with a majority that it still leads before answering. So the API server is given the guarantees a single correct machine would give, by a group that survives one failure in three.

Two properties of that design explain most of etcd's operational advice. The first is that the disk is in the path of every write. Each member forces each log entry to disk before acknowledging it, and a leader whose disk stalls for a second also stalls its heartbeats, which followers read as a dead leader. A slow disk therefore shows up as leader elections. The guidance is a dedicated SSD, and an alert when the 99th percentile of log sync time passes about ten milliseconds. The second is that the whole dataset is in one replicated log, with no partitioning. etcd doesn't scale out, and isn't meant to. A cluster's entire state must fit in a few gigabytes.

Kubernetes' API is, to a close approximation, etcd's features with access control and validation in front.

The Kubernetes watch model

A controller needs the current state of the objects it cares about, and to hear of every change. It gets both with a pattern used by every Kubernetes component, list, then watch.

  1. List the objects. The reply carries them and the resourceVersion at which the list was taken.
  2. Watch from that resourceVersion. The API server streams every later change: added, modified, deleted.
  3. Keep a local copy, the cache, updated from the stream, and note the resourceVersion of the last event seen.
  4. If the connection breaks, watch again from the last resourceVersion. Nothing is missed.
  5. If the API server answers 410 Gone, that point in history no longer exists. List again, and start over from step 2.

Client libraries package this as an informer. The API server helps by keeping its own recent window of changes in memory, so that ten thousand watchers are served from that and not by ten thousand watches on etcd.

What a controller does with the events matters as much as how it gets them. The obvious design reacts to each event: "a pod was deleted, so create one". That is edge-triggered, and it is fragile, since it is correct only if no event is ever lost and none is ever handled twice. Kubernetes controllers are level-triggered. An event is used only as a hint that something about an object may have changed. The controller then looks at the object's desired state and its actual state, in its cache, and does whatever closes the gap. This is called reconciliation, and it is idempotent: run it once, twice, or after missing an hour of events, and it arrives at the same place.

// With the fabric8 client. The informer does list-then-watch and keeps the cache current.
SharedIndexInformer<Pod> pods = client.pods().inNamespace("shop").inform(new ResourceEventHandler<>() {
	public void onAdd(Pod pod) { queue.add(ownerOf(pod)); }                    // an event says only "look at this owner again"
	public void onUpdate(Pod before, Pod after) { queue.add(ownerOf(after)); }
	public void onDelete(Pod pod, boolean stateUnknown) { queue.add(ownerOf(pod)); }
}, 10 * 60 * 1000L);                                                    // and every ten minutes, look at everything anyway

// Level-triggered: compares what is wanted with what exists. It never asks what changed.
void reconcile(String key) {
	Deployment wanted = deployments.getStore().getByKey(key);
	if (wanted == null) return;                                           // deleted: its pods are removed by garbage collection
	List<Pod> existing = podsOwnedBy(wanted);                               // read from the cache, not from the server
	int missing = wanted.getSpec().getReplicas() - existing.size();
	if (missing > 0) createPods(wanted, missing);
	else if (missing < 0) deletePods(existing, -missing);
}

// Writing back: the update carries the resourceVersion that was read, and loses if anyone wrote since.
try {
	client.resource(changed).update();
} catch (KubernetesClientException e) {
	if (e.getCode() == 409) queue.add(key); else throw e;                 // conflict: reconcile again from fresh state
}

Compaction and defrag

To serve a watch from an old revision, or a paged list at a fixed one, etcd must keep old versions of every key. It is a multi-version store, and every update to an object adds a version. A cluster whose objects are updated constantly, and node heartbeats and status changes see to that, would grow without limit. Three separate operations deal with this, and confusing them is a common source of trouble.

CompactionDefragmentationSnapshot
What it doesDiscards every version older than a chosen revisionRewrites the database file without its empty spaceCopies the database to a file
Why it is neededHistory otherwise grows for everCompaction frees space inside the file, for reuse. The file doesn't shrinkThe only protection against losing a majority, or against a mistake
Effect on clientsA watch or list at a discarded revision now fails: 410 GoneThat member stalls while it runs. Do one member at a timeNone
Who runs itThe API server, every five minutes by defaultAn operator or a scheduled jobAn operator or a scheduled job

The database has a size quota, 2 GB by default and at most about 8 GB by recommendation. When the file reaches it, etcd raises an alarm and refuses further writes, and the cluster's control plane becomes read-only: nothing can be scheduled, scaled or healed. Recovery is to compact, defragment each member in turn, and clear the alarm. The quota is measured on the file, so a cluster can hit it while holding very little live data, if compaction has run and defragmentation hasn't.

Compaction is also what gives step 5 of the watch pattern its work. A component that was disconnected for longer than the retained history comes back to find its place gone, and must list everything again. One component doing that is routine. A thousand doing it at the same moment, after a network fault, is a load spike on the API server and etcd, which is one way a brief interruption becomes a long one.

Things to notice. With the level-triggered controller connected, press "A pod crashes": it is told at once and creates a replacement. Now the first preset. The controller is cut off, two pods crash and the Deployment is scaled to 4. On reconnecting it asks for everything after the last revision it saw, is sent the three changes in order, and creates three pods. Nothing was missed, since the store had kept the history.

The second preset is the same with one addition: the history is compacted before the controller returns. It asks to resume and is refused with 410 Gone. It lists again and learns only the present: 4 wanted, 1 running. For the level-triggered controller that is all it needs. It compares the two numbers and creates three pods, without ever learning what happened in between. Change to the edge-triggered controller and play the second preset again. It too lists again, and then does nothing, since no event arrives for it to react to. The cluster stays at 1 pod of 4, with a controller that is connected, up to date and idle.

In a test of 300 random sequences of 30 actions, the level-triggered controller was never found connected with the wrong number of pods running. The edge-triggered one was, in 102 of the 300.

Failure scenarios

The most useful fact about Kubernetes under failure is the separation between the control plane, which decides, and the data plane, which runs. Containers that are running need nothing from etcd in order to keep running.

What failsWhat etcd doesWhat stopsWhat carries on
One member of threeTwo remain, a majority. If the leader was lost, an election takes about a secondNothing, beyond a brief pauseEverything. There is now no margin: replace the member before another fails
Two members of three: quorum lostThe survivor refuses writes and linearizable readsEvery change: deploying, scaling, scheduling, replacing failed pods, updating which pods a service routes toRunning containers, and traffic to them over the routes already programmed on each node
A slow disk under the leaderWrites stall, heartbeats are late, followers call electionsAPI requests time out or fail with "leader changed", intermittentlyWorkloads. Controllers retry
The database reaches its quotaRaises an alarm and rejects writesEvery change, as for lost quorumReads, and running workloads
All API servers down, etcd healthyNothing: it has no clientsEvery change, and all visibilityRunning workloads. Kubelets restart crashed containers on their own node from what they last knew
Restore from an old snapshotRevisions go back to an earlier numberComponents holding newer resourceVersions are confused until restarted. Objects created since the snapshot are forgottenContainers started since the snapshot keep running, unknown to the cluster, until cleaned up

The second row is the design's strength and its trap. A control-plane outage degrades a cluster to "frozen as it was", which is a far better failure than "down". That holds only as long as the data plane has no hidden dependence on the control plane, and such dependencies creep in: a service that looks up addresses through the cluster's DNS, a sidecar that fetches configuration at start-up, an autoscaler that must act for the service to survive a traffic peak. The frozen state is also only as good as the moment it froze. Pods that crash during the outage on a node that also fails aren't replaced.

Use case: OpenAI, December 2024, and a control plane that locked its own door

On 11 December 2024 OpenAI's services, ChatGPT and its API among them, were unavailable for more than four hours. The company's account of it is a clear modern instance of the last paragraph. OpenAI ran very large Kubernetes clusters, and that afternoon deployed a new telemetry service to them, to improve its visibility into the clusters' own control planes. The service's configuration caused the agent on every node to make expensive requests to the Kubernetes API, and the cost of those requests grew with the size of the cluster. In the largest clusters, thousands of nodes did so at once, and the API servers were overwhelmed. That took down the control plane. By the reasoning of this chapter the running workloads should have carried on. For a few minutes they did. But services found each other through the cluster's DNS, and the DNS service kept its records current from the Kubernetes API. Cached answers hid the problem at first, which let the rollout proceed to more clusters before anyone saw harm. As the cached records expired over the following twenty minutes, lookups began to fail, and with them the data plane. The change had been tested in a staging cluster, which was too small to show a load that scales with size. Recovery was slow for a reason worth dwelling on. The remedy was to remove the offending service, and removing a service is done through the Kubernetes API, which was the thing that was down. The engineers were locked out by the failure they needed to fix. They got back in by reducing the load from several directions at once: shrinking the clusters, blocking network access to the API from everything except themselves, and adding API server capacity, until one request to delete the service could get through. The changes OpenAI listed afterwards are this chapter's advice. Remove the data plane's dependence on the control plane for service discovery. Roll out infrastructure changes in stages with enough time between them to see slow-acting effects. And keep a way to reach the control plane that doesn't depend on the control plane being healthy.

⚠️
Common mistakes
  • Controllers that act on events alone. One missed or repeated event leaves the world wrong for good. Reconcile from state.
  • Updating an object without its resourceVersion, or ignoring a 409. Another writer's change is overwritten. Read again and retry.
  • etcd on a shared or slow disk. Sync latency becomes leader elections and API errors.
  • Compacting and never defragmenting. The file stays at its largest size and reaches the quota while nearly empty.
  • Using the cluster's etcd as an application database, or storing large or fast-changing objects in the API. Everything is in one unpartitioned log.
  • Two or four etcd members. Both tolerate one failure fewer than they appear to. Use three or five.
  • A data plane that needs the control plane to serve traffic. A frozen cluster then becomes a down one.
  • No tested restore. A snapshot nobody has restored from is a hope.

Interview drill

Explain it simply: What role does etcd play in Kubernetes, and what happens to a cluster if etcd goes down?

How a strong answer sounds
etcd is the single source of truth for a Kubernetes cluster. Every object, pods, deployments, services, secrets, config maps, node records, is stored there as a key and value, and only the API server reads and writes it. It is a strongly consistent key–value store replicated with Raft, typically three or five members, so it tolerates the loss of a minority and gives linearizable reads and writes. It also provides the features Kubernetes' design depends on: a global revision number that becomes each object's resourceVersion, conditional writes for optimistic concurrency, and watches that stream changes from a given revision, which is how controllers, the scheduler and kubelets learn what to do. If etcd loses quorum, the API server can't write, so nothing can be created, updated, scheduled or healed, and most reads fail. But the data plane keeps running: containers already started stay up, kubelets keep them alive, and existing network rules keep routing traffic. The cluster is frozen rather than dead. When quorum returns, controllers reconcile and catch up. If etcd's data is lost entirely, the cluster's state is gone and you restore from a snapshot.

Deeper: How does a Kubernetes controller stay correct if it misses events or restarts?

How a strong answer sounds
Two mechanisms. First, how it gets data: list-then-watch. On start it lists the objects it manages, receiving them with a resourceVersion, then opens a watch from that version, so it gets every subsequent change in order. It keeps a local cache and remembers the last resourceVersion seen. If the watch drops, it re-watches from that version and receives exactly what it missed, because the API server, backed by etcd's multi-version store, retains recent history. If it was away so long that the history has been compacted, the server returns 410 Gone, and it relists to get the full current state and starts watching again. Informers in the client libraries implement this, with periodic resyncs as a further safety net. Second, and more important, what it does with events: controllers are level-triggered, not edge-triggered. An event only enqueues the key of the affected object. The reconcile function then reads the desired state and the observed state from the cache and computes the actions needed to converge, for example "five replicas wanted, three exist, create two". It does not depend on which events occurred or how many. So if events are missed, duplicated, coalesced or replayed after a restart, the outcome is the same, because reconcile is idempotent and based on current state. Writes back use optimistic concurrency: an update carries the resourceVersion read, and if someone else changed the object the server returns a conflict and the controller requeues and reconciles again. And where several replicas of a controller run for availability, they use a Lease object for leader election so only one acts, though correctness doesn't depend on that because actions are idempotent and conflict-checked.

🧠 Key takeaways

  • Kubernetes is independent control loops round one consistent store. Components communicate only by reading and writing objects.
  • etcd supplies what that needs: Raft-replicated, linearizable storage, a global revision, conditional writes and watch streams.
  • List, then watch from the list's revision. Resume from the last revision seen, and list again on 410 Gone.
  • Controllers reconcile desired state against actual state. Events are hints, so missed or repeated ones do no harm.
  • History must be compacted, and the file defragmented. A full database makes the control plane read-only.
  • Losing the control plane freezes the cluster, and running workloads continue, provided the data plane doesn't secretly depend on it.

A controller's watch reconnects and receives 410 Gone. What does that mean, and what should it do?

History is kept only for a while. A watcher that falls behind the compaction point can't be given what it missed, so it starts from current state.

Why are Kubernetes controllers level-triggered?

Reconciliation is idempotent and depends only on current state. An event-driven controller is wrong for ever after one lost event.

etcd has been compacted regularly, and its database file still reaches the size quota. What was missing?

The quota is measured on the file. Defragmenting each member in turn returns the freed space.

A three-member etcd cluster loses two members. What is the state of the Kubernetes cluster?

Without a majority etcd accepts no writes, so the control plane is frozen. The data plane needs no writes to keep going.
