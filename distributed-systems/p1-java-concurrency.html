Java Concurrency Refresher

Every node in a distributed system is first a concurrent program. A Raft server answers votes from peers, appends entries from the leader, fires election timers and serves clients, all at once, all touching the same few fields. Before we worry about two machines disagreeing, we have to make sure one machine never disagrees with itself. This chapter recaps the Java you need for that: executors, CompletableFuture, the three ways to share state safely, the memory model's happens-before rule, and the single-threaded event loop that most consensus code is built on.

  • Pick the right executor for request handlers, timers and blocking I/O, including virtual threads
  • Fan a call out to several replicas with CompletableFuture and finish when a majority answers
  • Find a check-then-act race in node state and fix it with a lock or a single owner thread
  • Explain happens-before and the visibility bugs it prevents
  • Describe the event-loop design that etcd, Kafka's controller and most Raft libraries use

A node is a concurrent program

Take one replica of a replicated key-value store. At any instant it may be doing four unrelated things: handling a PUT from a client, answering a vote request from a peer, receiving a batch of log entries from the leader, and noticing that its election timer has expired. Each arrives on its own thread, and every one of them reads or writes the same fields: the current term, who it voted for, the log. In Java those threads come from executors, and each kind of work wants a different one:

// RPC handlers: lots of short tasks that mostly wait on the network.
ExecutorService rpc = Executors.newVirtualThreadPerTaskExecutor();   // Java 21+

// Timers: heartbeats every 50 ms, election timeouts, lease renewals.
ScheduledExecutorService timers = Executors.newSingleThreadScheduledExecutor();
timers.scheduleAtFixedRate(this::sendHeartbeats, 0, 50, TimeUnit.MILLISECONDS);

// Disk: fsync is slow and blocking; give it its own small, bounded pool.
ExecutorService disk = new ThreadPoolExecutor(2, 2, 0, TimeUnit.SECONDS,
		new ArrayBlockingQueue<>(1_000), new ThreadPoolExecutor.AbortPolicy());

Virtual threads (Java 21) make "one thread per request" cheap again: a blocked virtual thread parks without holding an operating-system thread, so a node can have tens of thousands of RPCs in flight. They don't make shared state any safer, and they don't remove the need for limits; a slow disk still needs a bounded queue in front of it. One detail to know: before Java 24, a virtual thread that blocked inside a synchronized block pinned its carrier thread (JEP 491 removed that), which is why older code prefers ReentrantLock around blocking calls.

Notice that the scheduled executor has one thread. If a heartbeat send blocks, the election timer behind it is late too. Timer tasks should only enqueue work or send asynchronously; they should never block.

Fan out, finish at a majority

The single most common shape in this course is "send the same request to every replica and continue once k of them answer". A leader commits an entry when a majority has stored it; a quorum read returns once R replicas reply. CompletableFuture.allOf is the wrong tool, because it waits for every call, including the replica that is down. You want the first k successes, or a failure as soon as success has become impossible:

/** Completes with k results as soon as k calls succeed, or fails once more than n - k have failed. */
static <T> CompletableFuture<List<T>> firstK(List<CompletableFuture<T>> calls, int k) {
	var result = new CompletableFuture<List<T>>();
	var oks = new ArrayList<T>();
	var failures = new AtomicInteger();
	for (var call : calls) {
		call.whenComplete((value, err) -> {
			if (err == null) {
				synchronized (oks) {                                     // callbacks run on many threads
					oks.add(value);
					if (oks.size() == k) result.complete(List.copyOf(oks));
				}
			} else if (failures.incrementAndGet() == calls.size() - k + 1) {
				result.completeExceptionally(new QuorumUnavailable(k, calls.size(), err));
			}
		});
	}
	return result;
}

// Usage: a leader replicating one entry to 4 followers needs 2 acks (plus itself = 3 of 5).
var acks = followers.stream()
	.map(f -> f.appendEntries(req).orTimeout(200, TimeUnit.MILLISECONDS))
	.toList();
firstK(acks, 2).thenRun(() -> advanceCommitIndex(req.lastIndex()));

Three details carry over to every later chapter. Each call has its own timeout (orTimeout), so a hung replica counts as a failure instead of hanging the request. The callbacks run on whichever thread completed each future, so the shared list needs a lock. And the failure condition is "more than n − k failed", not "any failed": with 5 replicas and a majority of 3, you can lose 2.

Shared state: the check-then-act race

Raft's vote rule is one sentence: in a given term, vote for at most one candidate. The obvious code is a check followed by an act:

// BROKEN: called concurrently from RPC threads
VoteReply onRequestVote(VoteRequest req) {
	if (req.term() == currentTerm && (votedFor == null || votedFor.equals(req.candidate()))) {
		votedFor = req.candidate();                                  // two threads can both get here
		return new VoteReply(currentTerm, true);
	}
	return new VoteReply(currentTerm, false);
}

If two candidates' requests arrive at the same moment, both threads can read votedFor == null before either writes it. The node then votes for both, each candidate counts that vote towards a majority, and the cluster can end up with two leaders in the same term, the exact situation Raft exists to prevent. The protocol was correct; the node implementing it was not. Try it:

Two fixes are common. The first is a lock around the whole decision: make the handler synchronized (or hold a ReentrantLock), so the read, the check and the write happen as one step. Real Raft adds a second requirement inside that critical section: currentTerm and votedFor must be written to disk before the reply leaves, or a crash and restart could make the node forget its vote and vote again.

private final ReentrantLock lock = new ReentrantLock();

VoteReply onRequestVote(VoteRequest req) {
	lock.lock();
	try {
		if (req.term() > currentTerm) becomeFollower(req.term());       // clears votedFor
		boolean grant = req.term() == currentTerm
				&& (votedFor == null || votedFor.equals(req.candidate()))
				&& logIsAtLeastAsUpToDate(req);
		if (grant) {
			votedFor = req.candidate();
			storage.persist(currentTerm, votedFor);                     // fsync before replying
		}
		return new VoteReply(currentTerm, grant);
	} finally {
		lock.unlock();
	}
}

The second fix removes sharing altogether, and it is the one most production consensus code uses. We'll get to it after the memory model.

Visibility and happens-before

Races aren't the only problem. Without synchronisation, one thread may never see another thread's write at all. The Java Memory Model only promises that a write is visible to a read if the write happens-before the read. These are the edges you will use:

  • Program order: within one thread, each action happens-before the next.
  • Monitor lock: unlocking a lock happens-before every later lock of the same lock.
  • volatile: a write to a volatile field happens-before every later read of that field.
  • Thread start and join: start() happens-before the new thread's first action; a thread's last action happens-before another thread's return from join().
  • java.util.concurrent: putting an object in a concurrent collection or queue, or submitting a task, happens-before the other thread takes it out or runs it. Completing a CompletableFuture happens-before its dependent stages run.
  • Transitivity: if a happens-before b and b happens-before c, then a happens-before c.

The classic bug is a stop flag. The JIT compiler is allowed to read a plain field once and keep using the cached value, because nothing told it another thread might change it:

private boolean running = true;                 // BUG: needs volatile

void heartbeatLoop() {
	while (running) { sendHeartbeats(); sleepQuietly(50); }
}
void stepDown() { running = false; }           // the loop may never notice

A deposed leader that keeps sending heartbeats is not a harmless bug: followers reset their election timers on each heartbeat and never elect the replacement. Declaring the field volatile fixes visibility. It does not make compound actions like votedFor == null ? set : skip atomic; for those you need a lock, an atomic class (compareAndSet), or a single owner.

The cheapest way to stay safe is to share only things that can't change. A Java record with immutable fields, built completely before it is published through a queue or a future, is safe to read from any thread. That's why every message in this course is a record.

The single-threaded event loop

Locks work, but every handler that touches node state needs the right lock, every time, forever. Most consensus implementations take a different path: one thread owns all of the node's state, and everything else talks to it through a queue. Network threads decode messages and enqueue them; timers enqueue "election timeout" events; the state-machine thread takes one event at a time, updates state, and enqueues outgoing messages and disk writes for other threads to perform.

sealed interface Event permits VoteRequest, AppendRequest, ClientPut, ElectionTimeout {}

final class NodeLoop implements Runnable {
	private final BlockingQueue<Event> inbox = new LinkedBlockingQueue<>();
	private final RaftState state;                  // touched ONLY by the loop thread

	void submit(Event e) { inbox.add(e); }          // called from any thread

	public void run() {
		try {
			while (true) {
				Event e = inbox.take();
				switch (e) {                              // pattern matching, Java 21
					case VoteRequest v      -> state.onRequestVote(v);
					case AppendRequest a    -> state.onAppendEntries(a);
					case ClientPut p        -> state.onClientPut(p);
					case ElectionTimeout t  -> state.startElection();
				}
			}
		} catch (InterruptedException stop) {
			Thread.currentThread().interrupt();
		}
	}
}

The payoff goes beyond safety. A node whose state changes only through onX(event) calls is deterministic: feed it the same events in the same order and it ends in the same state. That property is what makes deterministic simulation testing possible (Chapter 37), and it's the same idea as state machine replication (Chapter 15) applied inside one process.

Where you'll meet this design

etcd's Raft library is a pure state machine: the application calls Step(message) and Tick() from one goroutine and reads back a Ready batch of messages to send and entries to persist, doing the I/O itself. Kafka's controller, which assigns partition leaders, was rebuilt around a single event queue in Kafka 1.1 (2018) after years of race-condition bugs between ZooKeeper callbacks and request threads. Redis serves all commands from one thread for the same reason: no locks on the data, and an order everyone can reason about.

⚠️
Common mistakes
  • Check-then-act on node state without a lock, like the double-vote above. Every rule of the form "at most one X per term" is a compound action.
  • Using volatile for compound updates. It makes each read and write visible, not the sequence atomic.
  • Holding a lock across a network call or an fsync. Every other handler stalls behind one slow peer. Decide under the lock, do I/O outside it (or on another thread).
  • allOf(...).join() to wait for replicas. It waits for the slowest or deadest one. Wait for the first k successes instead.
  • Blocking inside a timer task. With a single-threaded scheduler, one blocked heartbeat delays every election timeout behind it.
  • Sharing mutable messages. Use records with immutable fields, and copy collections (List.copyOf) before publishing.

Interview drill

Explain it simply: A Raft node is a correct implementation of the protocol, yet the cluster elected two leaders in one term. What's a likely cause inside one node?

How a strong answer sounds
A local concurrency bug in the vote handler. Two RequestVote RPCs for the same term arrived on different threads, both read votedFor == null, and both granted, so the node voted twice and each candidate counted it towards a majority. The protocol assumes each node's decision is atomic and durable. Fix it by making the check and the write one critical section (a lock, or a single event-loop thread that owns the state) and by persisting currentTerm and votedFor before replying, so a restart can't forget the vote either.

Deeper: Why do so many consensus implementations run the protocol on a single thread instead of using fine-grained locks?

How a strong answer sounds
Because the protocol's state (term, vote, log, commit index) has invariants that span several fields, so fine-grained locks rarely help and are easy to get wrong. One owner thread processing events from a queue serializes every change without locks, makes the node deterministic for a given input order, and makes it replayable for simulation testing. The cost is that the loop must never block: network sends and fsyncs go to other threads, and results come back as events. Throughput is fine because the protocol logic is cheap compared to disk and network I/O, which are batched.

🧠 Key takeaways

  • A node runs RPC handlers, timers and I/O concurrently; give each kind of work the right executor, and never block timer threads.
  • Fan requests out with CompletableFuture and finish at the first k successes, with a timeout on every call.
  • "At most one per term" rules are check-then-act: they need one critical section, plus a durable write before the reply.
  • Visibility needs a happens-before edge: a lock, a volatile, a concurrent queue or a completed future.
  • Immutable records are safe to share; mutable state should have exactly one owner.
  • Most consensus code uses a single-threaded event loop: no locks on protocol state, deterministic, replayable.

Check your understanding

Two RequestVote handlers for the same term run on different threads with no lock. What is the dangerous outcome?

Check-then-act without atomicity: both threads pass the check before either writes. Each candidate counts the vote, which can give both a majority.

Which of these creates a happens-before edge between thread A's write and thread B's read?

A volatile write happens-before every subsequent read of that variable. Sleeping or timing proves nothing to the memory model.

A leader replicates each entry to 4 followers and commits at a majority of 5. Why not wait with CompletableFuture.allOf(calls).join()?

Commit latency should be the second-fastest follower here (2 acks plus the leader itself). Waiting for all turns one bad replica into an outage.

A stop flag boolean running is set to false by one thread, but the heartbeat loop in another thread keeps running. What's the fix, and why?

Visibility is only guaranteed through happens-before. A volatile write is seen by later volatile reads; a plain field may never be re-read.

What is the main benefit of having one event-loop thread own all of a node's consensus state?

One owner means no data races on protocol state and a single, replayable order of events. Slow I/O still has to happen on other threads.
