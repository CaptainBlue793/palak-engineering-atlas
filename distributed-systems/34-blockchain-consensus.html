Blockchain Consensus

Every consensus protocol so far begins with a list. Raft has its five servers, and PBFT in Chapter 33 its 3f + 1 replicas, each with a known key. A quorum is a count against that list. In 2008 a paper signed Satoshi Nakamoto asked for agreement with no list at all: a ledger that anyone on the internet may help to maintain, without permission and without identifying themselves. Counting votes is then meaningless, since one party can appear as a million. The paper's answer was to replace "one node, one vote" with "one unit of computing work, one vote", and with it came a kind of consensus unlike anything earlier in this course: no fixed membership, no rounds of messages, and no moment at which a decision is final, only one at which reversing it has become too expensive to attempt. This chapter treats blockchains as what they are for our purposes, consensus protocols under an unusual set of assumptions. It covers how Nakamoto's works, how proof of stake replaces the electricity, what finality means in each, and where all of them stand beside Raft.

The problem of open membership

A blockchain is state machine replication (Chapter 15): an ordered log of transactions that every participant applies in the same order to reach the same state. The log is grouped into blocks, and each block contains the hash of the one before, so that the latest block's hash commits to the whole history, as a Git commit does (Chapter 24). None of that is consensus. Consensus is the question of who decides what the next block is.

With a known set of replicas, PBFT answers it. With an open network it can't be used, for one reason: identities are free. An attacker can start a million nodes on one machine, and in any protocol that counts nodes those million are a quorum. This is a Sybil attack, and it defeats every scheme where a vote costs nothing to cast. The way out is to attach votes to something that can't be created at will. There are two candidates in use: computation that has been spent, and money that has been put at risk.

Nakamoto consensus

In Bitcoin, the right to add the next block is won by lottery, and tickets cost electricity. A node that wants to add a block, a miner, gathers pending transactions into a candidate and then searches for a number, the nonce, which makes the hash of the block's header fall below a target value. A cryptographic hash can't be steered, so the only method is to try nonces one after another. Checking a claimed solution takes one hash. This is proof of work.

Header mine(Header template, BigInteger target) throws Exception {
	MessageDigest sha = MessageDigest.getInstance("SHA-256");
	for (long nonce = 0; ; nonce++) {
		Header candidate = template.withNonce(nonce);            // previous block's hash, Merkle root of the transactions, time, nonce
		byte[] hash = sha.digest(sha.digest(candidate.bytes()));    // SHA-256, twice
		if (new BigInteger(1, hash).compareTo(target) < 0) return candidate;   // roughly one try in 10²³ on today's network
	}
}

// Fork choice: among valid chains, follow the one with the most total work in it.
Chain best(Collection<Chain> tips) {
	return tips.stream().filter(Chain::isValid).max(Comparator.comparing(Chain::totalWork)).orElseThrow();
}

The target is adjusted every 2,016 blocks so that, whatever the total computing power of the network, a block is found about every ten minutes. A miner's chance of finding the next block is its share of that total power. So the lottery is weighted by work, and pretending to be a million nodes buys nothing: the million share the same machines.

The fork-choice rule, follow the chain with the most work, is the whole protocol. Honest miners extend the heaviest chain, so the heaviest chain grows fastest, as long as honest miners hold most of the computing power. A transaction buried under several blocks can be removed only by someone who builds a competing chain from below it and overtakes the honest network, a race against everyone else's hardware. That is why merchants wait for confirmations: the number of blocks on top. Each one makes a reversal less likely, and none makes it impossible.

The design tolerates Byzantine behaviour by any coalition with less than half the computing power, where PBFT's limit is a third, and it needs no list of members. The costs are as distinctive. A block every ten minutes holding a few thousand transactions is about seven a second for the whole world. The electricity consumed is the security: it is what an attacker would have to match. And the protocol assumes blocks travel across the network much faster than they are produced, since otherwise forks would be the normal state.

Try it: a double-spend race

An attacker pays a merchant, and at the same moment starts mining a secret chain in which that payment doesn't exist. The merchant waits for some confirmations and hands over the goods. If the attacker's secret chain ever becomes longer than the public one, the attacker publishes it, every node switches to it, and the payment has never happened.

Proof of stake

Proof of work makes a vote expensive by burning energy outside the system. Proof of stake makes it expensive with money inside the system. A participant becomes a validator by locking up a deposit of the chain's own currency. The protocol picks the proposer of each block pseudo-randomly, with chances in proportion to deposits, and the other validators vote on it by signing. Creating a million identities is again useless: the stake is divided among them.

Stake has a property that work lacks, and the design turns on it. Signing costs nothing. A validator facing a fork could vote for both branches to be sure of backing the winner, which in proof of work would mean splitting its hardware. Unchecked, this "nothing at stake" behaviour would stop forks resolving. The remedy is that signatures are evidence. Two signed votes for conflicting blocks at the same height are an undeniable proof of misbehaviour, which anyone can submit, and the protocol then destroys part or all of the offender's deposit. This is slashing. It converts equivocation, the Byzantine behaviour of Chapter 33, from undetectable to provable and costly.

Proof of stake also restores what proof of work gave up: a known set of voters. The validators are listed on the chain itself, each with a key and a weight. With a list, the Byzantine agreement protocols of the last chapter become usable again, with "2f + 1 of 3f + 1 nodes" read as "more than two-thirds of the stake".

Finality

Finality is the point after which a transaction can't be undone. The two families give different kinds.

The last two rows are Chapter 10 applied. A longest-chain protocol never stops, and pays with reorganisations. A BFT protocol never reorganises, and pays by halting when too many validators are unreachable. Ethereum since 2022 runs one of each together: a fork-choice rule that keeps producing a block every twelve seconds come what may, and a voting layer on top that marks blocks final about every thirteen minutes. Applications can act on the latest block and accept a small risk, or wait for finality.

Tendermint and HotStuff

Given a list of validators weighted by stake, a chain can run Byzantine agreement on each block directly, and get finality at once.

Tendermint, designed in 2014 and used by the Cosmos family of chains, is PBFT rearranged for blocks. Validators take turns as proposer. In each round the proposer broadcasts a block, every validator broadcasts a prevote for it, and on seeing prevotes from more than two-thirds of the stake, a precommit. A block with precommits from more than two-thirds is committed and final, and the next height begins. The two steps are PBFT's prepare and commit. A validator that has precommitted is locked on that block in later rounds, which is what keeps a decision safe when a proposer fails and another takes over. There are no forks to choose between: every committed block is final. If more than a third of the stake is offline, the chain stops and waits.

HotStuff, published in 2019, addressed what kept PBFT small. In PBFT and Tendermint every validator sends its vote to every other, n² messages a round. In HotStuff validators send votes to the leader only, and the leader combines them into a quorum certificate: a compact proof, using aggregated signatures, that two-thirds signed. The certificate travels with the next proposal. Messages per round fall from n² to n, and replacing a failed leader, the costly case in PBFT, becomes equally cheap. The phases are also chained: the vote on each new block doubles as the next phase for the blocks before it, so one round of voting does the work of three. Protocols derived from HotStuff run chains with hundreds of validators.

Read from left to right, each column trusts its participants less and pays more for the privilege. So the engineering question about a blockchain is the same as for Byzantine tolerance in general: is there truly no party that all the participants would accept as operator? Where there is one, a replicated database with a signed, hash-chained audit log, in the manner of the certificate logs of Chapter 24, gives the tamper-evidence at a ten-thousandth of the cost.

Use case: the day Ethereum stopped finalising, and kept going

On 11 May 2023, and again the next day, Ethereum's finality layer stalled: for about twenty-five minutes the first time and over an hour the second, no block was marked final. The episode shows the two-layer design of the Finality section working as intended, and a lesson from Chapter 33 as well. Ethereum's validators run software from several independent teams, called consensus clients. Under an unusual pattern of votes on the network, votes that referred to old checkpoints, two of those clients did a large amount of unnecessary work reconstructing old states in order to check each one, and ran short of memory and processor time. Validators running them fell behind and missed their own votes. Finality needs votes from more than two-thirds of the stake, and with a large share of validators struggling, participation fell below that line. Finality stopped. Block production did not. The fork-choice layer went on producing a block nearly every twelve seconds, transactions continued to be included, and users of ordinary applications noticed little. What was missing was the guarantee: for that hour, recent blocks were only probably permanent, as on a proof-of-work chain. Exchanges and bridges that wait for finality before crediting a deposit correctly paused. The protocol has a designed response to a prolonged loss, which drains the deposits of validators who aren't voting until those who are make up two-thirds again, and it had begun to apply. The affected teams shipped fixes within a day and finality resumed without anyone's intervention on the chain itself. The reason the stall was partial is that the other clients, written separately by other teams in other languages, didn't share the flaw and carried on. That is the independence assumption made real. A Byzantine protocol tolerates a third of its voters failing, and if every validator had run the same software, the same bug would have taken all of them at once.

⚠️
Common mistakes
  • Treating one confirmation as final on a proof-of-work chain. It is a block that might yet be replaced. Wait in proportion to the amount.
  • "The blockchain is immutable." A longest-chain ledger is expensive to rewrite, by an amount that depends on depth and on who is trying.
  • Assuming 51% is the only threshold. A miner with a smaller share can still double-spend sometimes, as the panel shows, and can profit by withholding blocks.
  • Using a blockchain where the participants trust an operator. A database with an audit log is faster by orders of magnitude.
  • Forgetting that BFT chains halt. With a third of the stake offline they stop, by design.
  • Confusing the hash chain with consensus. Linking blocks by hash makes tampering evident. Deciding which block is next is the hard part.

Interview drill

Explain it simply: How does Bitcoin reach consensus without knowing who the participants are?

How a strong answer sounds
Classical consensus counts votes from a known set of nodes, which doesn't work in an open network because anyone can create unlimited identities, a Sybil attack. Bitcoin ties voting power to computation instead. To add a block of transactions, a miner must find a nonce that makes the block's hash fall below a target, which takes an enormous number of attempts but is trivial to verify; that is proof of work. The difficulty adjusts so a block is found about every ten minutes across the whole network, and a miner's chance of finding the next one is proportional to its share of total hash power. Each block includes the hash of the previous one, forming a chain. Nodes follow the valid chain with the most accumulated work. Occasionally two miners find blocks at the same time and the chain forks briefly; whichever branch gets extended first becomes longer, and everyone converges on it. A transaction becomes harder to reverse with each block built on top, because an attacker would need to redo all that work and outpace the honest network, which requires a majority of the hash power. So finality is probabilistic, and by convention six confirmations, about an hour, is treated as settled.

Deeper: Compare proof-of-work consensus with a BFT proof-of-stake protocol such as Tendermint. What are the trade-offs?

How a strong answer sounds
They differ in membership, finality and what happens under partition. Proof of work is permissionless and has no notion of a validator set; the leader for each block is whoever solves the puzzle, and the fork-choice rule is most accumulated work. It tolerates an adversary with under half the hash power, but finality is only probabilistic, blocks are slow, throughput is low, and security costs continuous energy. Under a network partition both sides keep extending their own chain and when it heals the shorter side is reorganised away, so it favours availability over consistency. Tendermint has a known validator set weighted by staked deposits, with a rotating proposer and two voting steps, prevote and precommit, each needing more than two-thirds of the stake, essentially PBFT's prepare and commit. A block that gets two-thirds precommits is final immediately, with no forks, and block times are seconds. It tolerates under one-third Byzantine stake rather than one-half, and if more than a third of validators are offline the chain halts, choosing consistency over availability. Misbehaviour such as signing two conflicting blocks is cryptographically provable and punished by slashing the deposit, which is how proof of stake handles the nothing-at-stake problem. Communication is quadratic in validators, which limits the set to a few hundred; HotStuff-style protocols make it linear with aggregated signatures. Proof of stake also needs additional mechanisms that proof of work doesn't, such as defences against long-range attacks using old keys. Ethereum combines the two ideas: an always-available fork-choice rule for block production with a BFT finality gadget on top.

🧠 Key takeaways

  • With open membership, identities are free, so votes must be tied to something scarce: work done, or stake at risk.
  • Nakamoto consensus: a proof-of-work lottery picks each block's author, and nodes follow the chain with the most work.
  • Its finality is probabilistic. Each confirmation makes reversal less likely, at a rate set by the attacker's share of the power.
  • Proof of stake weights votes by locked deposits, and slashing makes equivocation provable and costly.
  • A known validator set allows BFT agreement with immediate finality: Tendermint, and HotStuff with linear messages.
  • Longest-chain protocols stay available and reorganise. BFT protocols stay consistent and halt.
  • From Raft to BFT to proof of work, each trusts less and costs more. Use the cheapest that the trust model allows.

Check your understanding

Why can't an open network simply count one vote per node?

This is the Sybil attack. Proof of work and proof of stake both weight votes by something that can't be multiplied for free.

Two miners find valid blocks at the same height at almost the same time. What happens?

Forks are normal and resolve with the next block. The losing block's transactions go back to the pending pool.

Why does waiting for more confirmations make a Bitcoin payment safer?

Six is a convention and not a rule in the protocol. The risk falls with depth and never reaches zero.

What is slashing for?

Signing is free, so without a penalty a validator could back every fork. Two conflicting signatures are proof anyone can present.

A network partition leaves 40% of the validators on one side and 60% on the other. What does a Tendermint chain do?

Committing needs more than two-thirds of the stake. It halts and loses nothing, where a longest-chain protocol would continue and reorganise.
