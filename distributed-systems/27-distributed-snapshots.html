Distributed Snapshots

A bank has three branches, each with its own ledger, sending transfers to one another all day. An auditor asks one question: how much money is in the bank? Every branch can state its balance, and no two can state it at the same instant, since there is no shared clock to say "now" (Chapter 6). Ask them one after another and the answers describe three different moments. A transfer that left the first branch before it answered and reached the second after it answered is in neither figure. One that left after and arrived before is in both. Stopping every branch while the count is made would work, and stopping a running system is the thing to avoid. In 1985 Mani Chandy and Leslie Lamport showed how to record a state of the whole system that is guaranteed to make sense, using one extra kind of message and without pausing anything. The same algorithm, a little adapted, is how stream processors such as Flink checkpoint a pipeline handling millions of events a second.

Consistent cuts

Draw each process as a timeline of events, as in Chapter 7. A cut is one point chosen on each timeline: everything before the point is "in" the recorded state and everything after is not. A snapshot is a cut, plus what each process's state was at its point. The question is which cuts describe a state that makes sense.

Consider one message and where its two ends fall.

SendReceiveThe cut isIn the bank
Before the cutBefore the cutConsistentThe transfer has left one balance and joined the other
AfterAfterConsistentThe transfer hasn't happened yet
BeforeAfterConsistent, if the message is recorded as in the channelThe money is on its way. Ignore the channel and it has vanished
AfterBeforeInconsistentThe receiver has money the sender hasn't yet parted with. It is counted twice

A cut is consistent when no message crosses it backwards: for every receive inside the cut, the matching send is inside too. Put in the language of Chapter 7, if an event is in the cut, so is everything that happened before it. An effect is never recorded without its cause.

A consistent cut need not be a state the system was ever actually in at one instant. It is a state the system could have been in: one that is reachable from where the system started and from which the real present is reachable. For checking an invariant, restarting after a failure, or detecting a deadlock, that is exactly as good.

The marker algorithm

The setting: processes joined by one-way channels, each reliable and first-in-first-out. Any process may start a snapshot. The algorithm adds a single special message, the marker, and two rules.

Why it gives a consistent cut. Take the bad case from the table, a message sent after the sender's recording and received before the receiver's. The sender sent a marker on that channel immediately after recording, so the marker is ahead of the message in a FIFO channel and arrives first. On receiving the marker the receiver records, if it hasn't already. So the receiver has recorded before the message arrives, and the bad case can't occur. The marker is the cut made visible on each channel: what travelled ahead of it was sent before the sender's point, and what follows was sent after.

Channel state

The third row of the table is the reason for the recording rule. A message sent before the sender's point and not yet received at the receiver's point belongs to neither process's state. It is in the channel, and the snapshot is wrong without it.

A process can't look inside a channel. It can do something equivalent: after recording its own state, it notes every message that arrives on an incoming channel until the marker for that channel comes. Those messages arrived after the receiver's point, so the receiver's recorded state doesn't include them. They were ahead of the marker, so they were sent before the sender's point. They are exactly the messages that were in flight across the cut.

final class SnapshotParticipant {                               // one thread per process: no locking needed
	private long balance;
	private Long recorded;                                       // null until this process has recorded
	private final Map<Channel, List<Message>> recording = new HashMap<>();     // incoming channels still open
	private final Map<Channel, List<Message>> channelState = new HashMap<>();

	void startSnapshot() { recordAndSendMarkers(); }

	void onMessage(Channel from, Message m) {
		if (m.isMarker()) {
			if (recorded == null) recordAndSendMarkers();          // first marker seen: record now
			channelState.put(from, recording.remove(from));         // close this channel with what it collected
			if (recording.isEmpty()) report(recorded, channelState);
			return;
		}
		balance += m.amount();                                    // ordinary work never pauses
		List<Message> open = recording.get(from);
		if (open != null) open.add(m);                            // in flight across the cut
	}

	private void recordAndSendMarkers() {
		recorded = balance;
		for (Channel in : incoming) recording.put(in, new ArrayList<>());
		for (Channel out : outgoing) out.send(Message.marker());   // before anything else on that channel
	}
}

The cost is one marker per channel and the storage for whatever was in flight. The assumptions are worth stating, since each is a place where a real system needs extra work: channels don't lose or reorder messages, every process can be reached by markers from the initiator, and no process fails while the snapshot is being taken. A real implementation also tags each marker with a snapshot number, so that two snapshots can be in progress without being confused.

Try it: audit a running bank

Three branches with £100 each, so £300 in all, joined by six FIFO channels. Send transfers, deliver messages in any order you like, and take a snapshot part-way through. A snapshot is right if its total is £300.

A snapshot of three branchesInteractive
Method
In each channel the message on the left is the next to arrive. A blue pill is a marker. A channel with a solid border is being recorded by its receiver. In the naive method there are no markers: you choose the moment each branch writes down its balance, as a coordinator asking them one by one would.

Things to notice. Press "Case 1" with markers. Q sends £10 to R, and P starts a snapshot while the money is in the air. The result is P £100, Q £90, R £100, and £10 in the channel from Q to R: £300. Change the method to naive and press it again. The three balances are the same, there is no channel, and the total is £290. Ten pounds is missing from a bank that never lost it. "Case 2" is the opposite error. P records, and then sends £10 to Q. With markers, P's marker is ahead of the money in the channel, so Q records £100 before the £10 arrives, and the total is £300. In the naive method Q is asked after the money has arrived and says £110: £310, with the same ten pounds counted at both ends.

Then work it by hand. Start again, send a few transfers, begin a snapshot at any branch, and deliver messages in whatever order you choose, leaving a marker undelivered while money flows round it if you like. You can make the snapshot take as long as you want. You can't make it wrong. In a test of 400 random runs, with the snapshot started at a random moment in each, the marker method's total was £300 every time, and in 381 of them part of that total was in a channel. The naive method, recording the three branches at three random moments, was right in 15 runs of the 400.

What a snapshot is for

  • Checkpoint and recovery. Save a consistent state periodically. After a failure, restore every process to it and resume. The next section is this, at scale.
  • Detecting stable properties. Some conditions, once true, stay true: a deadlock, a computation that has terminated, an object that nothing refers to any more. If a consistent snapshot shows such a condition, it holds now. The original paper was written with these in mind.
  • Checking invariants. "The total is £300", "every lock has at most one holder". A check against states taken at different moments reports violations that never occurred, and misses ones that did.
  • Debugging. A view of the whole system that some execution could really have produced.

Databases meet the same need differently. A multi-version store reads "as of" a timestamp (Databases, MVCC), and a distributed one needs clocks good enough to make that timestamp mean one thing on every node, which is the subject of Chapter 35.

Snapshots in Flink

A stream processor is a graph of operators, connected by channels, through which records flow from sources to sinks. Many operators hold state: a count per user, the contents of an open window. If a machine fails, that state is gone, and the job must restart from a point at which every operator's state and the position in every input agree with each other. That point is a consistent snapshot, and Apache Flink's checkpointing is the marker algorithm adapted to a dataflow graph.

Chandy–LamportFlink checkpoints
The markerA marker messageA checkpoint barrier, carrying the checkpoint's number, flowing in line with the records
Who startsAny processA coordinator tells every source to emit a barrier, on a timer
Process stateRecorded on the first markerEach operator's state, written to durable storage such as S3, off the processing thread. Sources record their read positions, for example Kafka offsets
Channel stateMessages recorded until the marker arrives on each channelAvoided, by alignment. Or recorded, with unaligned checkpoints
RecoveryOutside the algorithmRestore every operator from the last complete checkpoint, and rewind each source to its recorded position

Alignment is Flink's main change. An operator with two inputs receives a barrier on one of them first. If it kept processing records from that input, they would be records from after the cut mixed into a state that is about to be recorded as at the cut. So it stops reading that input and buffers it, carries on with the other until its barrier arrives too, then records its state and passes the barrier on. At that moment nothing is in flight on its inputs that belongs before the cut, so there is no channel state to save. The snapshot is the operators' states and the sources' offsets, and nothing else. Since the sources can replay from an offset, restoring both gives the effect of each record having been applied to the state exactly once, though after a failure some records are physically processed twice. Making that hold at the sink, in the outside world, takes a further step, covered in Chapter 28.

StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.enableCheckpointing(60_000, CheckpointingMode.EXACTLY_ONCE);       // a barrier from every source each minute
CheckpointConfig cfg = env.getCheckpointConfig();
cfg.setMinPauseBetweenCheckpoints(30_000);                            // leave time to do real work between them
cfg.setCheckpointTimeout(600_000);                                    // abandon one that takes over ten minutes
cfg.setTolerableCheckpointFailureNumber(3);
cfg.enableUnalignedCheckpoints();                                      // see the use case

The interval is a trade. Checkpoints cost I/O and, during alignment, latency. A longer interval means more records to reprocess after a failure. Chapter 30 returns to operator state and what is kept in it.

🚧
Use case: when Flink's barriers got stuck in traffic

Aligned checkpoints have a weakness that large Flink users ran into repeatedly, and its fix is a return to the original algorithm. A barrier travels in line with the records. When a pipeline is under backpressure, a slow operator or a slow sink causing every buffer upstream of it to fill, records move slowly, and so do the barriers queued behind them. A checkpoint that normally completed in seconds would take many minutes, or exceed its timeout and be abandoned. The timing was the worst possible. Backpressure is a sign of a job in trouble, a job in trouble is the one most likely to fail, and a job whose checkpoints had been timing out for an hour would restart from a state an hour old, with an hour of input to reprocess, under the same load that caused the trouble. Some jobs never caught up. Alignment added to it: an operator that had stopped reading one input to wait for the other input's barrier was itself a new source of backpressure. Flink 1.11, released in July 2020, added unaligned checkpoints. A barrier arriving at an operator no longer waits its turn. It jumps the queue of buffered records, the operator records its state immediately and forwards the barrier at once, and the records the barrier overtook, in the input and output buffers, are written into the checkpoint as well. Those overtaken records are precisely Chandy and Lamport's channel state: messages sent before the cut and not yet received at it. The checkpoint's duration no longer depends on how fast data is flowing, at the price of larger checkpoints and more I/O at the moment the job is already struggling. Later releases added a middle course, in which a checkpoint starts aligned and switches to unaligned only if alignment takes longer than a set time. The design choice in 2015 had been to avoid storing channel state by making sure there was none. Five years of production use showed when that bargain fails.

⚠️
Common mistakes
  • Collecting each node's state in turn and calling it a snapshot. The states are from different moments, and the sum can be wrong in either direction.
  • Forgetting what is in flight. Messages sent and not yet received are part of the state.
  • Running the marker algorithm over channels that reorder. The proof rests on the marker arriving before anything sent after it.
  • Reading a snapshot as "the state at time T". It is a possible state, not necessarily one that existed.
  • Assuming checkpoints make outputs exactly-once. They make state exactly-once. A sink can still see a record twice after a restart.
  • Checkpoint intervals shorter than checkpoints take. The job spends its time snapshotting.

Interview drill

Explain it simply: How do you take a consistent snapshot of a distributed system without stopping it?

How a strong answer sounds
The problem is that there is no global clock, so you can't ask every node for its state "at the same time", and if you ask them one by one you can get a state that never could have existed, for example one where a message has been received but not yet sent. The Chandy–Lamport algorithm solves it with marker messages, assuming reliable FIFO channels. The initiator records its own state and immediately sends a marker on every outgoing channel. When a process receives a marker for the first time, it records its state, sends markers on all its outgoing channels, and starts recording the messages arriving on its other incoming channels. When it receives a marker on a channel it is recording, it stops; the messages recorded in between are that channel's state, the messages that were in flight. The snapshot is all the process states plus all the channel states. It is consistent because the marker separates, on each channel, what was sent before the sender's recording from what was sent after, and FIFO delivery means a receiver always records before it sees anything from after. Normal processing continues throughout; the only overhead is one marker per channel.

Deeper: How does Flink checkpoint a streaming job, and what happens to checkpoints under backpressure?

How a strong answer sounds
Flink uses a variant of Chandy–Lamport called asynchronous barrier snapshotting. The checkpoint coordinator periodically tells the sources to inject a barrier into their output; each source also records its position, such as its Kafka offsets. Barriers flow downstream with the data. An operator with one input snapshots its state when the barrier arrives and forwards the barrier. An operator with several inputs aligns: when a barrier arrives on one input it stops consuming from that input and buffers it until the barriers have arrived on all inputs, then snapshots and forwards. Alignment means no pre-barrier records are still in flight when the state is taken, so no channel state needs saving. The state itself is written asynchronously, often incrementally with RocksDB, to durable storage. When every operator has acknowledged, the checkpoint is complete. On failure, all operators are restored from the latest complete checkpoint and sources rewind to the saved offsets, which gives exactly-once semantics for state. Under backpressure, barriers are stuck behind queued records, so checkpoints take a long time or time out, exactly when the job is most likely to fail, and alignment itself blocks inputs and worsens it. Unaligned checkpoints, since 1.11, let the barrier overtake buffered records; the operator snapshots immediately and the overtaken in-flight buffers are persisted as channel state. Checkpoint time becomes independent of throughput, at the cost of bigger checkpoints and extra I/O. I would also mention that end-to-end exactly-once needs the sink to take part, with idempotent writes or a two-phase commit tied to the checkpoint.

🧠 Key takeaways

  • A global state is a cut across the processes' timelines. It is consistent if no message is received inside it and sent outside.
  • A consistent snapshot is a state the system could have been in. That is enough for recovery and for checking invariants.
  • Chandy–Lamport: record, send a marker on every outgoing channel at once, and record on the first marker received.
  • Messages in flight are part of the state. A receiver captures them by recording each channel until its marker arrives.
  • It needs FIFO, reliable channels, and costs one marker per channel without pausing any work.
  • Flink's checkpoints are the same idea with barriers. Alignment avoids channel state, and unaligned checkpoints store it.
