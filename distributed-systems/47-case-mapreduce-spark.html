Case Study: MapReduce to Spark

The file system of Chapter 46 gave Google a place to keep a copy of the web. Doing anything with it was another matter. Counting links, building an index or grouping log records by user each meant a program running on thousands of machines for hours, and every such program had to solve the same problems again: divide the input, hand out the pieces, notice the machines that died part-way, redo their work, and bring the results together. In 2004 two engineers, Jeff Dean and Sanjay Ghemawat, published the library that had taken those problems off everyone's hands. A programmer supplied two small functions with no side effects, and the library ran them over any amount of data on any number of machines, treating failure as routine. It worked by being restrictive: because the two functions are deterministic, any piece of work can be thrown away and done again. Ten years later a successor, Spark, kept that one idea and dropped nearly everything else. This chapter covers how MapReduce runs a job, the step in the middle that costs the most, the problem of machines that are slow without being dead, and how Spark generalised the recovery trick into a record of how every dataset was made.

MapReduce

The programmer writes two functions. Map takes one input record and emits any number of key–value pairs. Reduce takes one key and all the values emitted for it, and emits a result. Counting words is the standard example: map emits (word, 1) for each word in a line, and reduce adds up the ones.

public static class TokenMapper extends Mapper<LongWritable, Text, Text, IntWritable> {
	private static final IntWritable ONE = new IntWritable(1);
	private final Text word = new Text();

	@Override protected void map(LongWritable offset, Text line, Context out) throws IOException, InterruptedException {
		for (String w : line.toString().toLowerCase().split("\\W+")) {
			if (w.isEmpty()) continue;
			word.set(w);
			out.write(word, ONE);                                   // (word, 1)
		}
	}
}

public static class SumReducer extends Reducer<Text, IntWritable, Text, IntWritable> {
	@Override protected void reduce(Text word, Iterable<IntWritable> ones, Context out) throws IOException, InterruptedException {
		int sum = 0;
		for (IntWritable one : ones) sum += one.get();
		out.write(word, new IntWritable(sum));                       // (word, total)
	}
}

Everything else belongs to the library.

The design's central property is that any task can be run again. Map and reduce are required to be deterministic functions of their input, with no effects elsewhere. A task that is re-run reads the same input and produces the same output, and the atomic rename means that two copies of a reduce task finishing at once leave exactly one output file. So the master's whole treatment of failure is one rule. It pings each worker. If a worker stops answering, every task that worker was running is given to another. Its completed map tasks are re-run as well, since their output was on the dead machine's local disk, and completed reduce tasks are not, since their output is safe in the file system. The paper reports a job that lost 1,600 of 1,800 machines for some minutes to a network change, and finished correctly.

This is fault tolerance without replication, consensus or checkpoints, bought with a restriction on what the programmer may write. The master itself is a single process, and if it dies the job is simply started again. With thousands of workers and one master, the master's failure is the one unlikely enough to be handled by a retry.

The shuffle

Map tasks are independent of each other, and so are reduce tasks. All the coordination in a job is in the step between them: every pair with the same key, emitted anywhere on any machine, must end up at the same reduce task. With M map tasks and R reduce tasks, each of the M writes R sorted runs, and each of the R fetches from all M. That is M × R transfers, and for a large job, most of the data crossing most of the network.

Three facts about the shuffle shape how such jobs are written and tuned.

  • It is where the time goes. Sorting, writing to local disk, fetching over the network and merging usually cost more than the map and reduce functions themselves. A job with no reduce phase is many times cheaper.
  • It can often be shrunk before it happens. A combiner runs the reduce logic on each map task's own output before anything is sent. For word counting, a map task that saw "the" ten thousand times sends one pair, (the, 10000), where it would have sent ten thousand.
  • Skew hurts it. Keys are spread over reduce tasks by hash, which balances the number of keys and not the number of values. One very common key, a default value, a null, a celebrity's ID, sends a large share of the data to one reduce task, which runs long after the others have finished. It is the hot-key problem of Chapter 20, and no amount of extra machines helps.

Stragglers

A machine that dies is easy: its tasks are re-run. The awkward machine is the one that is alive and slow. The paper lists what its authors had met: a disk with correctable errors that slows reads from 30 megabytes a second to 1, other jobs competing for the same machine, and a bug in start-up code that left the processor caches switched off. A job of thousands of tasks waits for its slowest, so one such machine can double the time the whole job takes. The paper's name for the slow task is a straggler.

The remedy uses the same property as failure recovery. When a job is nearly done, the master starts a second copy of each task still running, a backup task, on another machine. Whichever copy finishes first wins and the other is discarded. Since tasks are deterministic it makes no difference which. The cost is a few per cent of extra work. The paper's measurement, sorting a terabyte on 1,800 machines, took 891 seconds with backup tasks and 1,283 seconds without, 44% longer.

The job is simulated event by event: a scheduler hands each free worker the next task, and a task takes its own length of work divided by its worker's speed. With backup tasks on, once nothing is left to hand out, a free worker is given a second copy of any task that has been running for more than one and a half times the median, and the first copy to finish counts. Each bar is four tasks, in the order they finished, and its height is when they did. The scheduler isn't told which machines are slow.

Things to notice. With no slow machines the job takes 30.7 seconds: four hundred ten-second tasks on a hundred workers. Now let 3 machines in 100 run at a tenth of normal speed, without backup tasks. The job takes 119.4 seconds, nearly four times as long. Ninety-five per cent of the tasks were done at 29.4 seconds, and the rest of the time went on three tasks that happened to be handed to the slow machines. Make those machines slower still, a thirtieth of normal speed, and the job takes 358 seconds. A job is as slow as its slowest task.

Turn on backup tasks. The same job takes 32.3 seconds. Three second copies were started, all three finished before the originals, and the work thrown away came to 2.4% of the total. With ten slow machines in a hundred it is 32.6 seconds for 7.8% of extra work, against 119.8 without. When the slow machines are only three times slower the gain is small, from 35.8 seconds to 32.3, and one of the three copies lost its race. Backup tasks pay in proportion to how bad the tail is, and they rest on the same property as recovery from failure: running a task twice does no harm.

Spark RDDs and lineage

MapReduce's strength was also a strait-jacket. A job is one map and one reduce. Anything more involved is a chain of jobs, each reading its input from the distributed file system and writing its output there, three copies of it, for the next to read. An algorithm that makes fifty passes over the same data, as most machine-learning methods do, reads and writes it from disk fifty times. An analyst trying one query after another waits minutes for each.

Spark, begun at Berkeley in 2009 and described in papers in 2010 and 2012, kept MapReduce's recovery idea and removed the fixed shape. Its abstraction is the resilient distributed dataset, or RDD: a collection divided into partitions across the cluster, which can't be changed once made, and is produced from files or from other RDDs by operations such as map, filter, join and group. Two decisions make it work.

An RDD remembers how it was made. Each one carries its lineage: the operation that produced it and the RDDs that operation read. Nothing is computed when a transformation is declared. Spark only records the recipe, and does the work when a result is asked for. If a machine dies and takes some partitions with it, Spark looks at the lineage and computes those partitions again from their inputs, and theirs if need be, back to data that is still available. It is "run the task again", extended from one fixed stage to an arbitrary graph. Intermediate data therefore needn't be written three times to a file system, or at all.

An RDD can be kept in memory. A dataset that will be used again is marked to be cached, and later passes read it from RAM. That one feature gave the tenfold and hundredfold speed-ups on iterative work that made Spark's name.

JavaRDD<String> lines = sc.textFile("hdfs://nameservice1/logs/2026/10/*");    // nothing is read yet

JavaPairRDD<String, Integer> counts = lines
		.flatMap(line -> Arrays.asList(line.toLowerCase().split("\\W+")).iterator())   // narrow: partition by partition
		.filter(w -> !w.isEmpty())                                              // narrow
		.mapToPair(w -> new Tuple2<>(w, 1))                                      // narrow
		.reduceByKey(Integer::sum);                                             // wide: the one shuffle, with combining built in

counts.cache();                                                             // keep the result in memory for reuse
counts.saveAsTextFile("hdfs://nameservice1/out/wordcount");                    // an action: now the whole chain runs
System.out.println(counts.toDebugString());                                 // prints the lineage

The comments mark the distinction that organises a Spark job. In a narrow dependency each output partition is computed from one input partition, on one machine, and several such steps are run together in one pass. In a wide dependency an output partition needs data from many input partitions: that is a shuffle, exactly as in MapReduce and for the same reason. Spark cuts a job into stages at the wide dependencies. Everything in this chapter's earlier sections carries over to a stage: tasks placed near their data, tasks re-run on failure, backup copies for stragglers, and skew in the shuffle.

Lineage has a limit that shows up in long-running work. A dataset derived through thousands of steps would take thousands of steps to rebuild, so Spark lets a program checkpoint an RDD, writing it to reliable storage and cutting its lineage there. Recomputation is cheap insurance for short histories and replication for long ones.

From batch to streaming

A batch job reads a finished input and stops. Much of the data it was used on never finishes: clicks, payments and sensor readings keep arriving. The first answer was to run the batch job over and over on whatever had arrived since last time, and Spark made that systematic. Spark Streaming, in 2013, cut the input into micro-batches of a second or so, each one a small RDD processed by the ordinary engine, with the ordinary recovery by lineage. Its later form, Structured Streaming, presents a stream as a table that keeps growing and runs a query over it incrementally.

The micro-batch has a floor on latency, the batch interval, and treats time as the moment a batch was cut. The engines of Chapter 30, Flink among them, start from the other end: they process each event as it arrives, keep state in the operators, recover with the distributed snapshots of Chapter 27, and reason in event time with watermarks. From that side a batch is the special case, a stream that happens to end. The two families have since borrowed heavily from each other, and for most uses the choice is made on latency needs and existing skills.

What didn't change across twenty years of these systems is the idea from the 2004 paper. Describe the computation as deterministic functions over immutable data, and recovery from any failure is to do part of it again.

Use case: sorting a hundred terabytes, in 2013 and in 2014

There is a long-running public contest in sorting large datasets, with strict rules and independent verification, and for a decade its results were a fair scoreboard for these systems. Its headline category is to sort 100 terabytes, a trillion records of 100 bytes each. In 2013 the record was set by a team at Yahoo using Hadoop MapReduce: 72 minutes, on a cluster of 2,100 machines. In 2014 a team at Databricks, the company formed by Spark's authors, entered Spark. It sorted the same 100 terabytes in 23 minutes on 206 machines rented from a cloud provider: three times as fast, on a tenth of the hardware. The result was widely read as proof that memory beats disk, and that reading is wrong in an instructive way. A hundred terabytes doesn't fit in the memory of 206 machines. Spark's in-memory caching, the feature that had made its name, played no part. Sorting is one enormous shuffle and nothing else, and the entry was won in the shuffle: the team had replaced Spark's shuffle with a sort-based design that kept the number of open files manageable at that scale, moved the network layer to one that sent data from disk to socket without copying it through the Java heap, and managed sort memory outside the garbage collector's reach. They also reported that at no point in the run did a task fail and need re-running, which says something about how far a cluster of 206 good machines is from the 1,800 unreliable ones the original paper was written for. Two lessons carry over. For jobs dominated by a shuffle, the engineering of the shuffle is what matters, more than the model on top. And a benchmark tells you what a system did, on that hardware, for that workload. Why it did so takes the write-up.

⚠️
Common mistakes
  • Side effects inside a task. A task may run twice, from a retry or a backup copy. One that sends an email or calls an API does so twice.
  • Non-deterministic functions. A map that uses random numbers or the current time gives a different answer when re-run, and recovery then mixes the two.
  • Ignoring skew. One hot key puts most of the shuffle on one task. Adding machines doesn't help. Salt the key or handle it separately.
  • Grouping where reducing would do. Sending every value across the network to add them up at the far end. Combine before the shuffle.
  • Caching everything in Spark. Memory spent on datasets used once is taken from the shuffle and the next stage.
  • Collecting a large result to the driver. One process receives what a thousand produced, and runs out of memory.
  • Endless lineage in iterative or streaming jobs. Recovery replays the whole history. Checkpoint to cut it.

Interview drill

Explain it simply: How does MapReduce work, and how does it handle machine failures?

How a strong answer sounds
The programmer writes two functions. Map takes an input record and emits key–value pairs; reduce takes a key and all the values for that key and produces output. The framework does everything else. It splits the input into chunks and runs a map task for each on a worker, preferably one that already has that chunk on local disk. Each map task partitions its output by hashing the key into R buckets and writes them to local disk. In the shuffle, each of R reduce tasks fetches its bucket from every map task, merges and sorts by key, and then calls reduce once per key, writing its output to the distributed file system. A master tracks the state of every task and pings the workers. If a worker fails, its in-progress tasks are rescheduled on other workers, and so are its completed map tasks, because their output lived on its local disk; completed reduce tasks are safe because their output is in the distributed file system. This works because map and reduce are deterministic and side-effect free, so re-executing a task gives the same result, and reduce output is committed by an atomic rename so duplicates don't matter. Slow machines are handled the same way: near the end of a job the master launches backup copies of the remaining tasks and takes whichever finishes first.

Deeper: A Spark job spends 90% of its time in one stage where a handful of tasks run for an hour while the rest finish in a minute. What is happening and what do you do?

How a strong answer sounds
That pattern, most tasks fast and a few very slow in the same stage, is almost always data skew in a shuffle rather than slow machines. The stage follows a wide dependency such as a join or groupBy; records are assigned to partitions by hashing the key, so if a few keys account for a large share of the rows, a null or default value, a very large customer, the partitions holding them are far bigger than the rest, and the tasks processing them take proportionally longer and may spill to disk or run out of memory. I'd confirm in the Spark UI by comparing shuffle read size and record count per task in that stage, and by counting rows per key in the input. If instead task sizes are similar and a few are slow, it is stragglers, bad nodes or contention, and speculation would help; with skew, speculation doesn't, because the backup copy has the same amount of work. Fixes for skew, roughly in order. Filter out or separately handle junk keys such as nulls before the join. If one side of a join is small, broadcast it so there is no shuffle. Turn on adaptive query execution, which can split skewed partitions at runtime. Salt the hot keys: append a random suffix from 0 to N on the large side and replicate the matching rows N times on the other side, so one key spreads over N partitions, then aggregate again. For aggregations, do it in two steps, partial aggregation on the salted key and then a final one. Increasing the number of partitions helps general unevenness but not a single hot key, since all its rows still hash to one partition. And I'd check whether the computation needs all the values together at all, replacing groupByKey with reduceByKey or an aggregation that combines map-side.

🧠 Key takeaways

  • MapReduce: the programmer writes map and reduce, and the library splits, schedules, shuffles and recovers.
  • Tasks are deterministic and without side effects, so any of them can be run again. That one property handles failures and stragglers alike.
  • The shuffle brings every value for a key to one place. It is the costly step, and skewed keys break its balance.
  • A slow machine can dominate a job. Backup copies of the last running tasks cut the tail for a few per cent of extra work.
  • Spark's RDDs are immutable datasets with lineage. Lost partitions are recomputed, and reused data is cached in memory.
  • Narrow dependencies run together in one pass. Wide ones are shuffles, and divide a job into stages.
  • Streaming began as small repeated batches, and the modern engines treat a batch as a stream that ends.

Check your understanding

Why is it safe for MapReduce to run the same task twice?

A second run reads the same input and produces the same output, and only one output file is ever put in place.

A worker dies after completing three map tasks. Why are those map tasks run again?

Map output is stored locally for the shuffle. Reduce output is in the distributed file system and survives its worker.

One reduce task runs for an hour, long after the others have finished, and a backup copy is just as slow. What is the likely cause?

A backup copy cures a slow machine. It has the same data to process, so it can't cure skew.

A Spark executor crashes and some partitions of an uncached RDD are lost. How are they recovered?

An RDD records the transformations that made it. Only the lost partitions are rebuilt, back as far as data that still exists.

Which Spark operation is a wide dependency, and so needs a shuffle?

All values for a key must be brought together, from every input partition. The others work on one partition at a time.
