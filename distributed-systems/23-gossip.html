Gossip Protocols

A cluster of a thousand machines has facts that every machine should know: which nodes are members, which are down, who owns which slice of the data, what version of the schema is current. Sending each change from one place to all the others makes that place a bottleneck and a single point of failure. Running the facts through a consensus log makes them exact and limits the cluster to what a handful of voters can handle. A third way gives up exactness for scale. Once a second, each node picks another node at random and the two exchange what they know. Nothing more. The news spreads the way a rumour or an infection does, doubling at each step, and reaches a thousand nodes in about ten rounds and a million in about twenty. No node is special, a lost message costs one round, and the load on each node stays the same however large the cluster grows. This chapter covers how fast gossip spreads and why, how clusters use it to keep a membership list, and how one corrupted bit can travel just as well as the truth.

Push, pull and push–pull

Time is divided into rounds, typically one a second. In each round a node chooses one or a few peers uniformly at random from the members it knows of. The number chosen is the fan-out. What happens next comes in three styles.

PushPullPush–pull
Who actsA node that has news sends it to its chosen peerEvery node asks its chosen peer "anything new?"The two exchange in both directions
When few nodes knowFast: each one that knows tells a new one, and the number doublesUnreliable: if nobody happens to ask a node that knows, a round passes with no progressFast
When most nodes knowSlow: most messages go to nodes that already knowFast: almost any peer asked has the newsFast
Cost when there is no newsNoneOne request a round from every nodeOne exchange a round from every node

The two halves of the spread behave differently, and it is worth seeing why. Early on, with push, each node that knows tells one more per round and nearly every message lands on a node that doesn't know: the count doubles. Late on, when a fraction u of the nodes are still unaware, push needs someone to choose each of them by chance. A given unaware node is missed by all the pushes in a round with probability about 1/e, a little over a third, so the unaware fraction shrinks by only that factor each round. Pull is strong where push is weak. An unaware node that asks a random peer stays unaware only if that peer is unaware too, so the fraction goes from u to u², then u⁴: one in ten, one in a hundred, one in ten thousand. Pull's weak point is the very beginning. While a single node knows, there is about a one in three chance in each round that nobody happens to ask it, and the news stands still. Push–pull gets a dependable start and the squaring at the end.

Real systems exchange digests first, a short summary such as "node 7 at version 412", and send the full data only for entries where the other side is behind. So the per-round cost stays small even when the state is large.

Convergence in O(log n) rounds

Doubling from one node reaches n in log2 n rounds: ten for a thousand, twenty for a million. The slow tail of push adds about as much again, and push–pull trims it to a few rounds. In every case the time grows with the logarithm of the cluster's size, which is why gossip is used at sizes where anything linear has stopped working. Each node's own work is constant: a fixed number of messages a round, whatever n is.

Fan-out and loss change the constant and not the shape. A fan-out of three spreads faster than one, at three times the traffic. A network that drops a fifth of all messages behaves like one with a slightly lower fan-out. There is nothing to retransmit and no failure to detect, since next round's random choice is the retry.

What gossip gives is a probability and not a promise. After enough rounds every node has the news with overwhelming likelihood, and no node can ever be sure that all have. The classic paper on the subject, from Xerox PARC in 1987, named two modes with this in mind. In rumour mongering a node spreads a new item for a while and then stops, which is cheap and can leave a few nodes untold. In anti-entropy a node regularly compares its whole state with a random peer and repairs any difference, which is costly and misses nothing. Systems use the first for speed and the second as a safety net. Chapter 24 makes the comparison cheap.

Things to notice. Start with the defaults: push, among 1,024 nodes. The count doubles for five rounds, 2, 4, 8, 16, 32, and passes half the cluster in round 10, which is log2 n. Then it slows. The second half takes seven more rounds, and in the last of them 1,020 messages are sent to find the final four nodes. Seventeen rounds in all. Switch to pull and it takes 13, with a different ending: the nodes still waiting number 253, then 61, then 2, then none, each fraction about the square of the one before. Push–pull finishes in 10, roughly tripling at first: 3, 8, 20, 62, 169. "A different run" changes the random choices. Over nine runs push took between 17 and 21 rounds, pull 13 to 15, and push–pull 9 or 10.

Now the size. With push, 64 nodes take 11 rounds, 256 take 15 and 1,024 take 17: sixteen times the nodes for six more rounds. A fan-out of 3 brings 1,024 nodes down from 17 rounds to 8, and the cost rises only from 7.0 messages per node to 8.5, since nodes spend fewer rounds repeating old news. Losing a fifth of all messages stretches push to 21 rounds, and losing half of them, to 29. Nothing breaks and nothing is retried.

Last, let each node stop after two rounds. Push now costs 1.6 messages per node, and it dies out with 221 nodes never told, about a fifth of the cluster. With a fan-out of 3 it misses one. That is the trade in rumour mongering: cheap, quick and incomplete, which is why a slower anti-entropy pass runs behind it.

Membership lists

The commonest thing to gossip is the list of members itself. Each node keeps a table with a row for every node it has heard of. The row holds a heartbeat counter, which only the node it describes may increase, and the local time at which this node last saw that counter go up.

record Entry(long heartbeat, long seenAtNanos) {}

class Membership {
	private final Map<NodeId, Entry> table = new ConcurrentHashMap<>();

	void everySecond() {
		table.compute(self, (id, e) -> new Entry(e.heartbeat() + 1, System.nanoTime()));   // "I am still here"
		send(randomPeer(), heartbeats());                         // node → counter, for every row
	}

	void onGossip(Map<NodeId, Long> theirs) {
		long now = System.nanoTime();
		theirs.forEach((id, beat) -> table.merge(id, new Entry(beat, now),
				(mine, incoming) -> incoming.heartbeat() > mine.heartbeat() ? incoming : mine));   // keep the higher counter
	}

	Status status(NodeId id) {
		long quiet = System.nanoTime() - table.get(id).seenAtNanos();
		return quiet > REMOVE_AFTER ? Status.GONE : quiet > SUSPECT_AFTER ? Status.SUSPECT : Status.ALIVE;
	}
}

Four details carry the design.

  • Merging is "keep the larger counter". That rule gives the same result whatever order messages arrive in and however often they are repeated, so duplicates and reordering are harmless. Chapter 25 builds a whole family of data types on this property.
  • No timestamps cross the network. Each node measures "how long since this counter moved" on its own monotonic clock (P5), so clock skew between machines doesn't matter.
  • A dead node's row must be kept for a while. If it is deleted at once, a peer that hasn't yet noticed the death gossips the old row back, and the node reappears. So a row is marked gone, kept for a second and longer timeout, and only then dropped.
  • A restart must not look like the past. A restarted node's counter starts again from zero and would lose every comparison. So each row also carries a generation, usually the start time, which is compared first. Cassandra's gossip uses this pair, generation and version.

A new node needs someone to talk to first, so clusters configure a few seed addresses. Seeds have no other role: they are where a newcomer sends its first message, after which it learns the full list by gossip like everyone else.

SWIM: spreading the news on the probes

Chapter 5 described how a SWIM node detects failures: each period it pings one random member, asks a few others to ping on its behalf if there is no reply, and marks the target suspect if that fails too. What it does with the result is this chapter's subject. SWIM sends no separate gossip messages. Every ping and every ack already travels between two random members, which is exactly what gossip needs, so each one carries a few recent membership updates in its spare bytes. This is called piggybacking, and it means the spread of news costs no extra packets.

Two rules keep this bounded and consistent.

Each update is sent a limited number of times. A node keeps a small buffer of recent updates and attaches those it has sent least often. After an update has gone out a few multiples of log n times, it is dropped from the buffer. By the arithmetic above that is enough to reach everyone with high probability, and it stops old news travelling for ever.

Updates about a node are ordered by its incarnation number. Messages arrive in any order, so "C is alive" and "C is suspect" need a rule for which wins. Each node has an incarnation number that only it can increase, and it does so in exactly one situation: when it hears that it is suspected.

Update receivedReplaces what a node currently believes if
Alive, incarnation iThe current belief is alive or suspect with a lower incarnation
Suspect, incarnation iThe current belief is alive with the same or a lower incarnation, or suspect with a lower one
DeadAlways. A node declared dead must rejoin as a new member
 
boolean replaces(Update incoming, Update current) {
	if (current.state() == DEAD) return false;
	if (incoming.state() == DEAD) return true;
	if (incoming.incarnation() != current.incarnation()) return incoming.incarnation() > current.incarnation();
	return incoming.state() == SUSPECT && current.state() == ALIVE;     // same incarnation: suspicion wins
}

A suspected node therefore has a fixed time to refute the suspicion with a higher incarnation before it is declared dead. HashiCorp's memberlist library, which Consul, Nomad and Serf use, is the best-known implementation. Its 2017 extension, Lifeguard, deals with the commonest cause of false suspicion in practice: the accuser is the unhealthy one, too overloaded to process acks in time. A node that notices its own probes failing unusually often lengthens its own timeouts before accusing anyone.

Many systems use both: Consul gossips membership among every agent in a datacentre and keeps its key–value store in a Raft log among three or five servers.

Use case: one flipped bit and Amazon S3, July 2008

On Sunday 20 July 2008, at about 8:40 in the morning Pacific time, error rates in every Amazon S3 datacentre began to climb, and within fifteen minutes almost no requests were succeeding. S3's servers used a gossip protocol to share state about one another, as this chapter describes. Amazon's account of the day says engineers found a large number of servers spending nearly all their time gossiping, and many that had failed while doing so. The cause was traced to a handful of messages in which a single bit had been corrupted. The damage was small enough that the message could still be parsed, and so it was accepted as true, merged, and passed on. S3 used checksums throughout to protect customers' data. This internal state had none. Gossip then did what it is designed to do, spreading the bad state to every server as efficiently as it would have spread good state, and no node could correct it, since in gossip no node has authority over another. There was no way to remove it piecemeal while servers kept re-infecting each other. The team shut down all communication between S3's servers, cleared the gossiped state everywhere, and brought the system back up from nothing, which took most of the day: service returned to normal a little before five in the afternoon, more than eight hours after it began. The changes Amazon listed afterwards were checksums on the internal state messages, monitoring for corrupted state, and work to make a full restart faster. The general lesson is that gossip's strengths have a mirror image. It has no single point of failure and no single point of control, and it will propagate anything that passes validation, so everything gossiped needs a checksum, a version, and a merge rule that can't be driven by one bad input.

⚠️
Common mistakes
  • Gossiping something that needs agreement. Two nodes will act on different views for a while. Use consensus for leaders and locks.
  • No checksum or validation on gossiped state. Bad state spreads as fast as good.
  • Sending full state in every message. The message grows with the cluster. Exchange digests, then differences.
  • Deleting a dead node's entry immediately. A peer that is behind gossips it back to life.
  • Comparing wall-clock timestamps from different nodes. Use counters that the owner increments.
  • Treating seeds as leaders. They are only a first address. A cluster whose seeds are all down still works, and can't be joined.

Interview drill

Explain it simply: How does a gossip protocol work, and why does it scale?

How a strong answer sounds
Every node, on a timer, picks one or a few other nodes at random and exchanges state with them. A node that has new information passes it on, and the nodes it told pass it on in the next round, so the number that know roughly doubles each round, like an epidemic. That means it takes on the order of log n rounds to reach n nodes: around ten for a thousand, twenty for a million. It scales because each node does a constant amount of work per round regardless of cluster size, and there is no coordinator to overload. It is robust because there is no fixed path: if a message is lost or a node is down, the information arrives by another route a round later. The trade-off is that it is probabilistic and eventually consistent. Nodes temporarily disagree, and no node knows for certain that everyone has the update. So it is used for things like membership, failure detection and cluster metadata, and not for decisions that need agreement, which go through consensus.

Deeper: Design cluster membership and failure detection for 5,000 nodes.

How a strong answer sounds
All-to-all heartbeats are out: 25 million messages per period. A central registry with leases works but is a bottleneck and a single dependency. I would use a SWIM-style protocol. For failure detection, each node pings one random member per period; if there is no ack, it asks k others to ping it indirectly, which rules out a bad link between just those two; if that also fails it marks the member suspect and not dead. Load per node is constant, and expected detection time is a small number of periods regardless of size. For dissemination, membership updates, joins, suspicions, confirmations, ride piggybacked on the ping and ack messages, each retransmitted on the order of log n times, so news reaches everyone in O(log n) periods with no extra packets. To handle ordering and false positives, each node has an incarnation number only it can bump; a suspected node that is alive refutes by announcing a higher incarnation, and after a suspicion timeout without refutation it is declared dead. I'd add Lifeguard-style self-awareness so an overloaded node becomes slower to accuse others, a periodic full state sync over TCP with a random peer as anti-entropy to fix anything the rumours missed, and seeds only for bootstrap. Dead entries are kept as tombstones for a while so they are not resurrected. Messages carry checksums and a protocol version. I'd be explicit that this membership view is eventually consistent: anything that needs one agreed answer, like who the leader is or who owns a shard, is decided through a small Raft group, with gossip only spreading the result.

🧠 Key takeaways

  • Gossip: each round, each node exchanges state with a few random peers. No coordinator, constant load per node.
  • News reaches n nodes in about log n rounds. Push is fast at the start, pull at the end, and push–pull at both.
  • It is probabilistic. Rumour spreading is backed by periodic anti-entropy, which compares everything.
  • Membership lists gossip counters that only their owner increments, and merge by keeping the larger.
  • SWIM carries updates on its probe messages, and incarnation numbers let a live node refute a suspicion.
  • Gossip spreads whatever it is given. Checksum it, version it, and keep agreement for consensus.
