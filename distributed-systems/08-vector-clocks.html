Vector Clocks

A Lamport timestamp answers half a question. If one event happened before another, its number is smaller. Given two numbers, though, you can't tell whether the events were ordered or independent (Chapter 7). For a replicated store that missing half is the one that matters. When two replicas hold different values for a key, either one is a later edit of the other, and the older can be thrown away, or two people edited the same thing without seeing each other's change, and throwing either away loses somebody's work. A vector clock carries enough to tell those cases apart: one counter for each participant in place of a single counter. This chapter covers the rules, the comparison, the form databases use to version data, and the hybrid clock that many newer systems chose instead.

Vector clock rules

In a system of N processes, each process keeps a vector of N counters, one for each process including itself. Entry j of process i's vector means "the number of events at process j that I know about". The rules are Lamport's, applied entry by entry.

  • Local event or send: add one to your own entry. A message carries a copy of the whole vector.
  • Receive: for every entry, take the larger of your value and the message's. Then add one to your own entry.
public record VectorClock(Map<String, Long> counters) {

	/** A local event or a send at this node. */
	public VectorClock tick(String node) {
		var next = new HashMap<>(counters);
		next.merge(node, 1L, Long::sum);
		return new VectorClock(Map.copyOf(next));
	}

	/** Entry-wise maximum: everything either side knows about. */
	public VectorClock merge(VectorClock other) {
		var next = new HashMap<>(counters);
		other.counters.forEach((node, n) -> next.merge(node, n, Math::max));
		return new VectorClock(Map.copyOf(next));
	}

	/** A message arrived at this node carrying the sender's clock. */
	public VectorClock onReceive(VectorClock fromMessage, String node) {
		return merge(fromMessage).tick(node);
	}
}

Comparing vectors

Two vectors are compared entry by entry. V is before W when every entry of V is less than or equal to the matching entry of W, and at least one is strictly less. If some entry of V is larger and some other entry is smaller, neither is before the other, and the two are concurrent.

public enum Order { BEFORE, AFTER, EQUAL, CONCURRENT }

public Order compareTo(VectorClock other) {
	boolean someLess = false, someGreater = false;
	var nodes = new HashSet<>(counters.keySet());
	nodes.addAll(other.counters.keySet());
	for (String node : nodes) {
		long mine = counters.getOrDefault(node, 0L), theirs = other.counters.getOrDefault(node, 0L);   // a missing entry is zero
		if (mine < theirs) someLess = true;
		if (mine > theirs) someGreater = true;
	}
	if (someLess && someGreater) return Order.CONCURRENT;
	if (someLess) return Order.BEFORE;
	return someGreater ? Order.AFTER : Order.EQUAL;
}

The point of the extra counters is that the guarantee now runs in both directions:

a → b exactly when V(a) is before V(b)

A Lamport clock gave only the left-to-right half. With vectors, the comparison is the happens-before relation: ordered events have ordered vectors, and concurrent events have vectors that can't be ordered. Nothing is guessed and nothing is lost, which is also why a vector can't be smaller than one entry for each participant. It has been proved that no scheme with fewer than N numbers can capture the relation exactly.

Detecting concurrency

Back to the two replicas with different values. With a vector attached to each value, the replica can decide properly. If one vector is before the other, the later value was written by someone who had seen the earlier one, so the earlier is obsolete and can be dropped. If the vectors are concurrent, the two values were written independently and there is a conflict. The store must not pick a winner by itself. It keeps both, which are then called siblings, and hands both to whoever reads the key next, to be merged by the application or shown to the user.

Try it: one shopping list on three devices

A family's shopping list is kept on a phone, a laptop and a tablet. Each device can be edited offline, and any two can be synchronised. Each copy carries a vector with an entry for each device: [phone, laptop, tablet].

An edit adds one to the editing device's own entry. A sync compares the vectors: a copy that is before another is replaced by it, and concurrent copies are both kept on both devices as a conflict. Merging takes every item from both copies and the larger of each pair of entries, and counts as an edit. Editing a device that holds a conflict merges it first.

Things to notice. Add an item on the phone, sync it to the laptop, then add an item on the laptop and sync again: the laptop's vector is ahead in one entry and behind in none, so its copy simply replaces the phone's. Now reset, sync nothing, and add an item on the phone and another on the laptop. Their vectors are [1, 0, 0] and [0, 1, 0]: each is ahead in one entry. On sync both copies are kept, on both devices, and the panel reports a conflict. A store using last-write-wins would have kept one of them and dropped an item with no trace. Merge on one device and sync again: the merged copy's vector is ahead of both originals, so it replaces them everywhere. Notice too what a vector doesn't do. It detects the conflict and says nothing about how to resolve it. Taking every item from both lists is a choice this application made, and it has a consequence of its own: an item one person removed while another was editing comes back.

Version vectors

The panel used the vector in the form databases use, which goes by a slightly different name. A vector clock timestamps every event in a computation. A version vector versions one piece of data: it has an entry for each replica that can accept updates, counting the updates to that item made through that replica. The arithmetic is the same, and the difference is in what is counted and where the vector lives. It is stored beside the value and travels with it.

Amazon's Dynamo made the technique widely known (Chapter 26 and Chapter 42 cover it in full). A client that reads a key receives the value together with its vector, as an opaque context. When the client writes, it sends that context back, which tells the store what the client had seen. A write whose context covers the stored version replaces it. A write whose context is concurrent with the stored version becomes a sibling beside it. A read that finds siblings returns all of them, and the client's next write, carrying a context that covers them all, collapses them into one.

Hybrid logical clocks

Many systems don't need to detect conflicts, since they route every write to a key through one leader. They do want timestamps that respect causality, fit in a fixed number of bytes, and mean something to a person, so that "the database as of 14:05" is a query one can ask. Lamport clocks fail the last requirement, and physical clocks the first. A hybrid logical clock, published in 2014, combines them. Its timestamp is a pair: a physical part, which is the largest wall-clock reading the node has seen anywhere, and a small logical counter that breaks ties.

public final class HybridClock {
	private long wall;       // the largest physical time seen so far, in ms
	private long logical;    // orders events that share the same wall value

	/** A local event or a send. */
	public synchronized Hlc now(long physicalMs) {
		if (physicalMs > wall) { wall = physicalMs; logical = 0; }
		else logical++;                                   // our clock hasn't advanced past what we've seen: count instead
		return new Hlc(wall, logical);
	}

	/** A message arrived carrying the sender's timestamp. */
	public synchronized Hlc onReceive(Hlc msg, long physicalMs) {
		long newWall = Math.max(Math.max(wall, msg.wall()), physicalMs);
		if (newWall == wall && newWall == msg.wall()) logical = Math.max(logical, msg.logical()) + 1;
		else if (newWall == wall) logical++;
		else if (newWall == msg.wall()) logical = msg.logical() + 1;
		else logical = 0;                                 // our own clock is ahead of both
		wall = newWall;
		return new Hlc(wall, logical);
	}
}
record Hlc(long wall, long logical) {}                   // compared by wall, then by logical

It behaves as a Lamport clock whose values happen to stay close to real time: a cause always has a smaller timestamp than its effect, even when the receiver's physical clock is behind the sender's, and the timestamp never strays from true time by more than the clock skew. It is one number in effect, so, like a Lamport clock, it can't detect concurrency. CockroachDB, YugabyteDB and MongoDB use hybrid clocks, and Chapter 35 shows what they build on them.

Use case: Riak and the trouble with siblings

Riak was an open-source database built closely on the Dynamo design, and its history is a record of what version vectors are like to live with. Early versions gave each client an entry in the vector. That detects conflicts exactly, and with thousands of short-lived clients the vectors grew until they outweighed the values they described, so Riak pruned old entries, and pruning occasionally threw away the information needed to see that one version had replaced another. Later versions switched to an entry for each storage node, which kept vectors small and brought a different problem. When two clients wrote the same key through the same node without reading in between, the node's single counter couldn't represent "two independent writes that both passed through me", and under some workloads keys accumulated siblings by the hundred or the thousand, a failure users called sibling explosion. Objects grew to megabytes and reads slowed to a crawl. The fix, which shipped as the default in Riak 2.0 in 2014, was a refinement called dotted version vectors, from researchers in Portugal working with the Riak team: each version records, in addition to the vector of what its writer had seen, the one specific event that created it, and that pair is enough to compare versions exactly with a vector no larger than the number of replicas. In the same release Riak added built-in data types that merge themselves, counters, sets and maps, so that for common cases applications never see a sibling at all. Detecting concurrency turned out to be the easy half of the problem. Keeping the vectors small, and deciding what to do with a conflict once it is found, took most of the engineering.

⚠️
Common mistakes
  • Comparing vectors by their sum or their largest entry. The comparison is entry by entry, and "neither" is a valid answer.
  • Forgetting to add one to your own entry after merging on receipt, so that the receipt has the same vector as an earlier event.
  • Resolving concurrent versions inside the store by timestamp. That is last-write-wins again, with extra bookkeeping.
  • Writing without the context from a read. Every such write looks concurrent, and siblings multiply.
  • An entry for each client. The vector grows with the number of clients that ever wrote.
  • Expecting a hybrid logical clock to detect conflicts. It orders events and can't tell that two were independent.

Interview drill

Explain it simply: What does a vector clock give you that a Lamport clock doesn't?

How a strong answer sounds
The ability to tell whether two events were causally related or concurrent. A Lamport clock is a single counter: if a happened before b then a's timestamp is smaller, but a smaller timestamp doesn't tell you a happened before b, since the events might be unrelated. A vector clock keeps one counter for each node. A node increments its own entry on each event, sends the whole vector with each message, and on receipt takes the entry-wise maximum and increments its own entry. To compare two vectors you look at every entry: if one is less than or equal everywhere and smaller somewhere, it happened before; if each is ahead in some entry, the events are concurrent. So the comparison captures happens-before exactly, in both directions. In a database that is what lets you distinguish "this version replaces that one" from "these two were written independently and conflict". The price is size, one entry for each node, where a Lamport clock is one number.

Deeper: A leaderless key-value store uses version vectors. Walk through how a conflict arises and how it gets resolved.

How a strong answer sounds
Say a key has value v1 with vector [A:1]. Two clients both read it and receive v1 with that vector as context. Client 1 writes v2 through node A, sending the context back: A increments its entry and stores v2 with [A:2], and since the context covered [A:1], v1 is discarded. Meanwhile client 2, perhaps on the other side of a partition, writes v3 through node B with the same context: B stores v3 with [A:1, B:1]. When the replicas exchange data, they compare [A:2] with [A:1, B:1]: the first is ahead in A, the second ahead in B, so they are concurrent and neither may be dropped. Both are stored as siblings. The next client to read the key gets both values with a context that is the merge of the two vectors, [A:2, B:1]. That client, or application logic on its behalf, merges them, for a shopping cart perhaps by union, and writes the result back with the merged context; the coordinator increments its entry, giving say [A:3, B:1], which dominates both siblings, so they are removed and the conflict is resolved. Points worth adding: the store can only detect the conflict, and the merge policy is application-specific, and a union brings back deleted items unless deletions are tracked; clients that write without a context create siblings on every write; and vectors keyed by server can misjudge two writes through the same node, which dotted version vectors fix.

🧠 Key takeaways

  • A vector clock keeps one counter for each node: increment your own on every event, and take the entry-wise maximum on receipt.
  • Compare entry by entry. One vector is before another only if it is behind or equal everywhere. Otherwise they are concurrent.
  • The comparison matches happens-before exactly, which a single Lamport number can't do.
  • Version vectors apply this to data: a version that is before another is obsolete, and concurrent versions are a conflict to keep.
  • Vectors detect conflicts. Resolving them is the application's job, or a self-merging data type's.
  • A hybrid logical clock is a Lamport clock that stays near wall-clock time: compact and causal, with no conflict detection.

Check your understanding

How are the vectors [3, 1, 2] and [2, 4, 2] related?

The first is ahead in entry one and the second in entry two. Neither has seen everything the other has.

Process P2 has vector [1, 2, 0] and receives a message carrying [3, 0, 1]. What is its vector afterwards?

Entry-wise maximum gives [3, 2, 1], and then P2 adds one to its own entry.

A store finds two versions of a key whose version vectors are concurrent. What should it do?

Concurrent means neither writer saw the other's value. Choosing one in the store discards an update nobody chose to discard.

Why do Dynamo-style stores key their vectors by server and not by client?

Vector size grows with the number of updaters. A handful of replicas keeps it small.

What does a hybrid logical clock give up, compared with a vector clock?

It is a Lamport clock kept close to physical time: compact and causal, and unable to detect conflicts.
