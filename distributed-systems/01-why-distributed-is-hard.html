Why Distributed Is Hard: The Eight Fallacies

A distributed system is several computers, connected only by a network, working on one job. Every design in this course exists because of three facts that never apply inside a single program: parts fail independently, the only way to learn anything is a message that may be late or lost, and there is no shared clock. In the 1990s, engineers at Sun Microsystems wrote down the false assumptions that newcomers make about networks. Thirty years later the list still describes most production outages. This chapter walks through it with real failures, then lets you break a simple money-transfer client in each of those ways.

Three facts that change everything

Inside one process, a method call either returns or throws, all threads share memory, and every thread reads the same clock. Distribute the program over a network and all three disappear:

  • Partial failure. One machine can crash, freeze in a garbage-collection pause or lose its network while the others carry on. Worse, the others can't reliably tell which of those happened (Chapter 5).
  • Communication only by unreliable messages. No shared memory: a node learns what another node did only from a message, and the message can be lost, delayed, duplicated or reordered. Whatever it says may already be out of date when it arrives.
  • No global clock. Each machine has its own clock, and they disagree (Chapter 6). So "which of these two events happened first?" has no simple answer (Chapters 7–8).

Everything else in this course, from retries to Raft to CRDTs, is a technique for getting a correct answer despite those three facts.

The eight fallacies

Around 1994, L. Peter Deutsch and colleagues at Sun listed seven assumptions that programmers new to distributed applications invariably make, and that all turn out to be false; James Gosling later added the eighth. Each row below is a real class of incident.

The first two cause most of the trouble, and they combine: because the network is unreliable and slow by an unknown amount, a missing reply is ambiguous. That is the partial-failure problem in one sentence.

Partial failure in one transfer

Take the smallest interesting distributed operation: move £10 from account A, held by one service, to account B, held by another. Here is one way it goes wrong with no bug in either service:

In code, the difference between a client that assumes the fallacies and one that doesn't is small but decisive:

// Assumes a reliable, zero-latency network.
void transferNaive(Transfer t) {
	accountsA.debit(t.from(), t.amount());                 // no timeout: may block forever
	accountsB.credit(t.to(), t.amount());                    // a lost reply throws: debit is stranded
}

// Assumes neither. Each step has a deadline and is safe to repeat.
Outcome<Void> transfer(Transfer t, Deadline deadline) {
	var debit  = new Debit(t.id() + ":debit",  t.from(), t.amount());   // idempotency keys
	var credit = new Credit(t.id() + ":credit", t.to(),   t.amount());
	return retry.untilDeadline(deadline, () -> accountsA.debit(debit, deadline.remaining()))
		.then(() -> retry.untilDeadline(deadline, () -> accountsB.credit(credit, deadline.remaining())));
	// Still Unknown at the deadline? Record it and let a reconciler finish it (Ch 22).
}

The second version still can't make the transfer atomic; that needs a saga or a transaction protocol (Chapter 21, Chapter 22). But it never hangs, never double-credits, and never lies about what it knows. Break both kinds of client yourself:

What this means for the rest of the course

The panel shows the shape of every solution you'll meet. Timeouts turn "stuck forever" into "unknown". Retries turn many unknowns into successes but create duplicates. Idempotency makes duplicates harmless. Each fix exposes the next problem, and each problem in that chain has a chapter: retries and idempotency (Ch 4), deciding a node is dead (Ch 5), ordering events without a shared clock (Ch 7), keeping copies in agreement (Ch 9 onwards).

Use case: the JVM that never noticed the move

Fallacy 5 has a classic Java form. The JVM caches DNS lookups in InetAddress, controlled by the security property networkaddress.cache.ttl. With a security manager installed, the historical default was to cache successful lookups forever; without one, the default is about 30 seconds. Teams that ran older application servers with a security manager found that after a database failover changed the IP behind db.internal, their services kept connecting to the old address until someone restarted them. AWS's SDK documentation still tells Java users to set the TTL to 60 seconds or less for exactly this reason. The topology changed; the client had assumed it wouldn't.

What interviews ask

Distributed-systems interviews, whether a dedicated round or the deep-dive part of a system design round, come back to the same few question types. You'll be able to answer all of them by the end of the course; Chapter 40 rehearses them.

  • "What happens if this node dies here?" Walk through a failure at a specific point in a protocol.
  • "How do you make this safe to retry?" Idempotency, deduplication, exactly-once effects.
  • "What consistency does this give?" Name the model precisely and say what a client might observe.
  • "Explain Raft (or Paxos) and why it's safe." Terms, majorities, and the invariant.
  • "Design X so it survives a partition." Choose between consistency and availability, and justify it.
⚠️
Common mistakes
  • Testing only on a laptop or a single data centre, where loss is near zero and latency tiny, then shipping to a world where neither is true.
  • Treating a missing reply as a failure instead of an unknown outcome.
  • Adding retries without idempotency, converting lost replies into duplicate side effects.
  • Caching addresses, membership or leaders forever. Topology changes; caches need a TTL and a refresh on error.
  • Making calls sequentially that could be parallel, so latency adds up across dozens of hops.
  • Assuming another team's network, firewall or quota won't change under you.

Interview drill

Explain it simply: What makes distributed systems fundamentally harder than concurrent programs on one machine?

How a strong answer sounds
Three things. Partial failure: parts fail independently, and the rest can't reliably tell a dead node from a slow one or a broken network. Communication only by unreliable messages: there's no shared memory, so everything a node knows about another node arrived in a message that may have been lost, delayed or duplicated, and may be stale. And no global clock: machines' clocks disagree, so you can't order events across machines just by timestamps. On one machine, threads share memory, see one clock, and the whole process fails together.

Deeper: A service calls a payment provider and times out. The team adds three retries and the timeouts stop. What new problem have they probably created, and how do you fix it?

How a strong answer sounds
Duplicate charges. A timeout often means the request reached the provider and only the reply was lost or late, so a retry charges the customer again. The retries hide the symptom (errors) and create a worse one (double charges). The fix is an idempotency key: generate a unique key per logical payment before the first attempt, send the same key on every retry, and have the provider return the original result for a key it has already processed. I'd also add jittered backoff and a retry budget so retries don't amplify an outage, and an alert on the rate of unknown outcomes.

🧠 Key takeaways

  • Distributed systems differ from local programs in three ways: partial failure, unreliable messages, and no global clock.
  • The eight fallacies: reliable network, zero latency, infinite bandwidth, secure network, fixed topology, one administrator, free transport, homogeneous network.
  • A missing reply is ambiguous: the request may have been applied.
  • Timeouts turn hangs into unknowns; retries turn unknowns into duplicates; idempotency makes duplicates harmless.
  • Caches of addresses, membership or leaders need expiry, because topology changes.
  • Most of this course is a toolkit for getting correct results despite these facts.

Check your understanding

What does "partial failure" mean?

On one machine, a crash takes everything down together. In a distributed system, parts fail independently, and from outside a crashed node looks like a slow one.

A client adds retries to calls that sometimes time out, but no idempotency key. Under packet loss, what new outcome appears?

A timeout often means "applied, but reply lost". Retrying such a request applies it twice unless the server can recognise the retry.

After a database failover, some application servers keep connecting to the old database IP until they are restarted. Which fallacy is this?

The client assumed the address behind a name never changes, typically by caching DNS forever. Addresses and membership need expiry and refresh.

A client with no timeout sends a request, and the request packet is lost. What happens to the calling thread?

The server never saw the request, so nothing will ever reply. Without a timeout (and, with TCP, without keepalives), the caller can wait forever.

Why can't a distributed system order events from different machines just by their timestamps?

Clock skew between machines can exceed the time between events. Logical clocks (Chapters 7–8) order events without relying on physical time.
