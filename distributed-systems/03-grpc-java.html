RPC in Java with gRPC

gRPC is the RPC framework you'll meet inside most modern clusters: etcd's API, Kubernetes components, Envoy's control plane and countless internal services speak it. It combines Protobuf messages (P3) with HTTP/2 transport and generated Java stubs, and it builds in the things P2 said every call needs: deadlines, cancellation and precise status codes. This chapter writes a small inventory service and its client in Java, then follows a deadline through a chain of services to see what happens when the caller gives up.

  • Define a gRPC service with unary and streaming methods in a .proto file
  • Implement the server and call it from Java with blocking and async stubs
  • Set deadlines, propagate them across hops, and honour cancellation on the server
  • Choose the right status code, and know which codes are safe to retry
  • Avoid the classic gRPC pitfalls: per-call channels and HTTP/2 load imbalance

Define the service

A gRPC service is declared in the same .proto file as its messages. Each rpc names a request type and a response type; the word stream on either side makes that side a sequence of messages.

syntax = "proto3";
package shop.inventory.v1;
option java_package = "com.example.inventory.v1";
option java_multiple_files = true;

service Inventory {
  rpc Reserve(ReserveRequest) returns (ReserveReply);              // unary
  rpc WatchStock(WatchRequest) returns (stream StockLevel);     // server streaming
}

message ReserveRequest { string request_id = 1; string sku = 2; int32 qty = 3; }
message ReserveReply   { bool reserved = 1; int32 remaining = 2; }
message WatchRequest   { repeated string skus = 1; }
message StockLevel     { string sku = 1; int32 level = 2; }

The protoc compiler with the gRPC Java plugin (usually run by the Gradle or Maven protobuf plugin) generates the message classes and an InventoryGrpc class containing a base class to implement (InventoryImplBase) and three client stubs: blocking, async (callback) and future. Note the request_id: it's an idempotency key, so the reserve can be retried safely (Chapter 4).

The server

final class InventoryService extends InventoryGrpc.InventoryImplBase {
	private final StockStore store;
	InventoryService(StockStore store) { this.store = store; }

	@Override
	public void reserve(ReserveRequest req, StreamObserver<ReserveReply> out) {
		if (req.getQty() <= 0) {
			out.onError(Status.INVALID_ARGUMENT.withDescription("qty must be positive").asRuntimeException());
			return;                                                  // rejected before doing anything
		}
		if (Context.current().isCancelled()) {                        // caller already gave up
			out.onError(Status.CANCELLED.asRuntimeException());
			return;
		}
		Reservation r = store.reserveOnce(req.getRequestId(), req.getSku(), req.getQty());   // dedup by id
		out.onNext(ReserveReply.newBuilder().setReserved(r.ok()).setRemaining(r.remaining()).build());
		out.onCompleted();
	}
}

Server server = Grpc.newServerBuilderForPort(50051, InsecureServerCredentials.create())   // TLS in production
	.addService(new InventoryService(store))
	.executor(Executors.newVirtualThreadPerTaskExecutor())
	.build()
	.start();

Every handler ends in exactly one of two ways: onNext then onCompleted, or onError with a Status. The status is not decoration; it tells the client whether the request was rejected before any work, failed in a way worth retrying, or ended in an unknown state.

The client

// One channel per target, created once and shared: it holds HTTP/2 connections and does load balancing.
ManagedChannel channel = Grpc.newChannelBuilder("dns:///inventory.internal:50051", InsecureChannelCredentials.create())
	.defaultLoadBalancingPolicy("round_robin")                   // spread calls over every resolved address
	.build();
var inventory = InventoryGrpc.newBlockingStub(channel);

Outcome<ReserveReply> reserve(String requestId, String sku, int qty) {
	var req = ReserveRequest.newBuilder().setRequestId(requestId).setSku(sku).setQty(qty).build();
	try {
		return new Outcome.Ok<>(inventory.withDeadlineAfter(300, TimeUnit.MILLISECONDS).reserve(req));
	} catch (StatusRuntimeException e) {
		return switch (e.getStatus().getCode()) {
			case INVALID_ARGUMENT, FAILED_PRECONDITION, NOT_FOUND -> new Outcome.Rejected<>(e.getStatus().getDescription());
			default -> new Outcome.Unknown<>(e);                     // DEADLINE_EXCEEDED, UNAVAILABLE, …
		};
	}
}

withDeadlineAfter returns a new stub with a deadline attached; the deadline travels to the server in the grpc-timeout header as a remaining duration, exactly as P2 recommended. If it passes before the reply arrives, the client gets DEADLINE_EXCEEDED and the call is cancelled on both sides.

Deadlines across a chain of services

gRPC Java keeps the incoming call's deadline in the request's Context. When a handler makes an outgoing call from that context, the outgoing call automatically gets the remaining time (or the stub's own deadline, if that's shorter). When the original caller's deadline passes or it disconnects, the context is cancelled, and every downstream call made from it is cancelled too. That only works if you keep the context: work handed to your own thread pool must be wrapped, or it runs outside the request's context and outlives it.

// In the order service's handler: the inventory call inherits what's left of the caller's deadline.
ReserveReply r = inventory.reserve(req);                              // no new deadline needed

// Handing work to another executor: carry the gRPC Context, or it loses the deadline and cancellation.
Executor ctxAware = Context.currentContextExecutor(workerPool);
CompletableFuture.supplyAsync(() -> pricing.quote(q), ctxAware);

// Long-running server work: stop when the caller is gone.
for (Batch b : batches) {
	if (Context.current().isCancelled()) return;                       // nobody will read the result
	process(b);
}

Streaming

A streaming RPC sends many messages over one call. Server streaming suits subscriptions ("tell me whenever stock changes"), client streaming suits uploads, and bidirectional streaming suits long conversations like Raft's replication between a leader and a follower, or etcd's watch API. Streams need flow control: if the server writes faster than the client reads, messages queue in memory. gRPC exposes HTTP/2's flow control through ServerCallStreamObserver.isReady() and setOnReadyHandler, so a well-behaved server writes only while the stream is ready.

@Override
public void watchStock(WatchRequest req, StreamObserver<StockLevel> out) {
	var call = (ServerCallStreamObserver<StockLevel>) out;
	Subscription sub = store.subscribe(req.getSkusList());
	call.setOnCancelHandler(sub::close);                                // client went away: free resources
	call.setOnReadyHandler(() -> {
		while (call.isReady() && sub.hasNext()) call.onNext(sub.next());   // respect backpressure
	});
}

Status codes: what to retry

CodeMeaningWas it applied?Retry?
OKSuccessYesNo
INVALID_ARGUMENTBad request, regardless of stateNoNever: fix the request
FAILED_PRECONDITIONSystem not in the required state (e.g. not leader)NoNot until the state changes
ALREADY_EXISTSThe thing you tried to create existsEarlier, perhaps by your own retryNo; treat as success if it's yours
ABORTEDConcurrency conflict, e.g. a transaction abortedNoYes, the whole read-modify-write
RESOURCE_EXHAUSTEDQuota or rate limit hitUsually noLater, with backoff
UNAVAILABLETransient: server down, connection failedUsually not, but not guaranteedYes with backoff, if idempotent
DEADLINE_EXCEEDEDRan out of timeUnknownOnly if idempotent
CANCELLEDThe caller cancelledUnknownUp to the caller
INTERNAL / UNKNOWNBug or unexpected errorUnknownRarely; investigate
☸️
Use case: the new pods that got no traffic

A team moves a gRPC service onto Kubernetes behind an ordinary ClusterIP Service and scales it from 3 to 10 pods during a traffic spike. The 7 new pods sit idle while the original 3 run hot. The reason is HTTP/2: a gRPC client opens one long-lived connection and multiplexes every call over it. The ClusterIP Service balances connections at layer 4, and the connections were made before the new pods existed, so they never see a request. The standard fixes are client-side load balancing (a headless Service so DNS returns every pod IP, plus the round_robin policy shown above and periodic re-resolution) or a layer-7 proxy or service mesh such as Envoy or Linkerd that balances individual requests. The same issue shows up with any connection-pinned protocol; gRPC just makes it common.

⚠️
Common mistakes
  • No deadline on calls. gRPC's default is no deadline at all; a hung server holds the caller forever.
  • Creating a channel per call. Channels are expensive (connections, TLS, name resolution); create one per target and reuse it.
  • Losing the Context by handing work to a plain executor, so downstream calls ignore the deadline and cancellation.
  • Ignoring cancellation in long handlers and streams, so servers burn resources for callers that left.
  • Retrying every non-OK status, including INVALID_ARGUMENT, or retrying non-idempotent calls after DEADLINE_EXCEEDED.
  • Relying on a layer-4 load balancer for gRPC traffic and getting all calls pinned to a few backends.

Interview drill

Explain it simply: What does gRPC give you over hand-written JSON over HTTP?

How a strong answer sounds
A schema-first contract in Protobuf, with generated, typed client and server code in many languages, so the interface is checked at compile time and evolves by the Protobuf rules. Compact binary messages over HTTP/2, with many concurrent calls multiplexed on one connection and streaming in either direction with flow control. And distributed-systems plumbing built in: deadlines that travel with the request, cancellation that propagates down the call chain, a precise set of status codes, plus hooks for interceptors, retries and client-side load balancing. The costs are less human-readable traffic and some care with load balancing, because of long-lived connections.

Deeper: A user request fans out from an API gateway through three gRPC services. During an incident, the innermost service's CPU stays at 100% even though most user requests are timing out. What's likely happening?

How a strong answer sounds
The inner service is doing work nobody is waiting for. Most likely deadlines aren't propagated: a middle service sets its own fresh timeout, or hands work to an executor without the gRPC Context, so when the user's request times out at the edge, the downstream calls aren't cancelled. Or the deadlines are propagated but the inner handlers never check Context.isCancelled() during long work. Each timed-out request still consumes full CPU at the bottom, which slows everything further: a feedback loop. Fixes: propagate the edge deadline through every hop, wrap executors with the current Context, check cancellation in loops, fail fast when the remaining deadline is shorter than the work needs, and shed load when queues build up.

🧠 Key takeaways

  • gRPC = Protobuf contracts + HTTP/2 transport + generated stubs, with unary and streaming calls.
  • A handler ends with onNext + onCompleted, or onError with a meaningful Status.
  • Set a deadline on every call; gRPC sends the remaining time and propagates it through the request Context.
  • Cancellation travels downstream; keep the Context across executors and check isCancelled() in long work.
  • Status codes tell you whether to retry: DEADLINE_EXCEEDED and UNAVAILABLE mean unknown or transient; INVALID_ARGUMENT means fix the request.
  • Share one channel per target, and balance per request (client-side or a layer-7 proxy), not per connection.

Check your understanding

A gRPC call returns DEADLINE_EXCEEDED. What does the client know?

The deadline passed before a reply arrived. The server may have finished, partly finished, or never started.

An order service handler calls inventory through a blocking stub, without setting a deadline on it. The incoming call had 300 ms left. What deadline does the inventory call get in gRPC Java?

The incoming deadline lives in the Context, and outgoing calls made from that Context inherit what is left of it, unless the work escapes the Context, for example onto an unwrapped executor.

Why should a gRPC client create one channel per target and reuse it?

Channels are designed to be long-lived and shared; they multiplex many concurrent calls over HTTP/2.

A gRPC service is scaled from 3 to 10 pods behind a layer-4 load balancer, but the new pods receive almost no requests. Why?

All calls are multiplexed over connections opened before scaling. Balance per request: client-side round robin with a headless service, or a layer-7 proxy.

Which status code should a server return when a client sends a negative quantity?

INVALID_ARGUMENT means the request itself is wrong regardless of system state. Retrying it is pointless; the client must fix it.
