Containers, Kubernetes & Shipping Safely

A design on a whiteboard is worth nothing until it runs in production — on hundreds of machines, updated many times a day, without users noticing. This chapter covers how modern systems are packaged, scheduled, scaled and released, and why most outages are caused not by traffic but by changes.

  • Explain containers vs VMs and what's in an image
  • Understand Kubernetes' declarative control loop and core objects
  • Reason about resource requests, limits and scheduling
  • Autoscale pods and nodes — and know the lag it introduces
  • Design a CI/CD pipeline and compare rolling, blue-green and canary releases
  • Use health probes, graceful shutdown, IaC and serverless well

From servers to containers

“It works on my machine” happens because the app depends on an exact OS, runtime and library set. Virtual machines solved isolation by virtualizing hardware — each VM boots a whole OS. Containers virtualize the operating system instead: processes share the host kernel but get isolated views of files, network and processes (Linux namespaces) and capped resources (cgroups).

🧅
Images are layered and immutable

Each instruction creates a cached, content-addressed layer shared between images. Tag releases with the git SHA (or pin by digest), never deploy :latest, and build once — the exact same artifact goes to staging and production. Configuration comes from the environment, not the image (12-factor apps).

Kubernetes: a declarative control loop

Running thousands of containers by hand is impossible. Kubernetes lets you declare the desired state (“3 replicas of api:v42, each with 500m CPU”) and runs controllers that continuously compare desired with actual state and act to close the gap. You never say “start a container on node 7” — you say what should exist.

kubectl apply → running pods → self-healingStep-through
  1. kubectl apply -f deployment.yaml. The API server authenticates you, checks RBAC and admission policies (e.g. “images must come from our registry”).
  2. The object is stored in etcd, a Raft-replicated key-value store (Chapter 13). Every component communicates only through the API server — which is why they can crash and restart freely.
  3. The ReplicaSet controller watches the API: desired 3 pods, actual 0. It creates 3 Pod objects with no node assigned.
  4. The scheduler filters nodes that fit each pod's resource requests, affinity rules and taints, scores the rest (spread across zones, least allocated) and binds each pod to a node.
  5. Each node's kubelet sees pods assigned to it, pulls the image, starts containers, and reports status. Readiness probes pass → the pod is added to the Service's endpoints and receives traffic.
  6. Heartbeats from node-3 stop. After a grace period its pods are marked lost. The controller sees desired 3, actual 2…
  7. …and creates a replacement pod, which is scheduled onto a healthy node. Nobody was paged. The same loop handles scaling, rolling updates and crashes.

Scheduling, requests & limits

Every container declares requests (what the scheduler reserves — guaranteed) and limits (the hard ceiling). Exceed a CPU limit and you're throttled (slow); exceed a memory limit and you're OOMKilled (restarted). Requests that are too high waste money; too low and noisy neighbours starve you.

Autoscaling

↔️

Horizontal Pod Autoscaler

Adjusts replica count to hold a target metric (CPU 60%, requests/sec, queue depth via KEDA): desired = ceil(current × actual / target).

🖥️

Cluster Autoscaler / Karpenter

When pods are pending for lack of room, adds nodes (1–3 minutes); removes underused nodes by draining them.

↕️

Vertical Pod Autoscaler

Recommends or adjusts requests/limits per pod based on observed usage — right-sizing rather than scaling out.

🧪 A low target (e.g. 40%) keeps headroom to absorb spikes while new pods boot — at the cost of more idle pods. Slow startup (JVM warm-up, model loading) makes spikes far more painful. For predictable events, pre-scale; for unpredictable ones, keep headroom and shed load gracefully (Chapter 16).

Health probes & graceful shutdown

❤️

Liveness

“Is the process wedged?” Fail → container restarted. Keep it trivial; never check dependencies here, or a database blip restarts your whole fleet.

✅

Readiness

“Should I receive traffic now?” Fail → removed from load balancing, not restarted. Use during warm-up, overload or lost critical dependencies.

🐢

Startup

“Has the slow boot finished?” Suspends liveness checks until the app has started, so slow starters aren't killed in a loop.

Pod marked Terminating

During a deploy or scale-down, Kubernetes sends SIGTERM and simultaneously starts removing the pod from Service endpoints — propagation takes a few seconds.

Keep serving briefly

A preStop sleep of ~5s lets load balancers stop sending new requests before the app stops accepting them. Otherwise every deploy produces a burst of connection errors.

Drain

Stop accepting new work, finish in-flight requests, close WebSockets with a reconnect hint, commit Kafka offsets, release locks.

Exit before the deadline

After terminationGracePeriodSeconds (default 30s) the pod gets SIGKILL. Size the grace period to your longest request.

CI/CD: from commit to production

Commit & review minutes

Small pull requests, trunk-based development, required review, branch protection.

Continuous integration < 10 min

Build once; unit and integration tests; lint; dependency and container vulnerability scans; secret scanning; produce a signed, immutable image tagged with the commit SHA.

Deploy to staging

Apply migrations (backward-compatible!), run end-to-end and contract tests against production-like infrastructure.

Progressive production rollout

Canary → automated analysis of error rate and latency against SLOs → gradually 100%, region by region. Automatic rollback on regression.

GitOps

The desired state of every environment lives in git. An in-cluster agent (Argo CD, Flux) continuously reconciles the cluster to match. Rollback = git revert; the audit trail is the git log.

Database migrations: expand, migrate, contract

During any zero-downtime rollout, old and new code run at the same time against the same database. Never rename or drop a column in one step. Expand: add the new column (nullable), deploy code that writes both. Migrate: backfill in batches. Switch reads to the new column. Contract: once no old code remains, drop the old column in a later release.

Plan before apply

Every change is a diff in a pull request, reviewed and applied by CI — no console clicking in production.

🧊

Immutable infrastructure

Don't SSH in and patch servers; build a new image and replace instances. No snowflake servers, no config drift.

🌍

Environments from modules

Dev, staging and each production region instantiate the same modules with different variables — critical for multi-region (Chapter 22).

Serverless

Functions-as-a-Service (AWS Lambda, Cloud Run, Cloudflare Workers) take the platform idea to its limit: upload code, and the provider runs it per request, scales from zero to thousands of instances, and bills per millisecond.

Shines for
  • Spiky or low, unpredictable traffic (scale to zero)
  • Event glue: “on S3 upload → generate thumbnail”
  • Scheduled jobs, webhooks, lightweight APIs
  • Tiny teams with no ops capacity
Watch out for
  • Cold starts (100 ms – seconds) on the first request to a new instance
  • Max execution time and memory limits
  • Connection storms: 1,000 functions × DB connections → use a proxy/pooler
  • At steady high volume, often pricier than containers; vendor lock-in
⚠️
Common mistakes
  • Liveness probes that check dependencies. A database blip then restarts your entire fleet at once.
  • Deploying without a fast rollback. If rolling back takes 20 minutes, your incident takes 20 minutes.
  • Breaking schema compatibility in one step. During any rolling deploy, old and new code run simultaneously — expand, migrate, contract.
🎤
Interview drill

Design: Roll out a change that alters both the API response and the database schema, with zero downtime.

How a strong answer sounds
Expand first: add the new column and the new response field while keeping the old ones, deploy code that writes both and reads the old. Backfill in batches. Then flip reads to the new field behind a flag, canary it, and watch error rates. Only once no client and no code path uses the old shape — verified from access logs, not assumption — contract by removing it in a later release. Each step is independently reversible.

Operate: Traffic triples in 30 seconds. Autoscaling takes 3 minutes to add pods. What saves you?

How a strong answer sounds
Headroom (run at ~60% so you can absorb a burst), fast startup (small images, lazy warm-up, pre-pulled layers), and a queue or admission control so excess load waits rather than failing everything. Then graceful degradation: serve cached or simplified responses, shed low-priority traffic, and keep the critical path alive. Pre-scaling for predictable events is the cheapest fix of all.

🧠 Key takeaways

  • Containers package an app with its dependencies and share the host kernel; build small, immutable images tagged by commit.
  • Kubernetes reconciles declared desired state through controllers watching the API server, giving self-healing.
  • Requests drive scheduling; limits throttle CPU and OOMKill memory. Spread vs bin-pack trades resilience for cost.
  • Autoscaling lags behind spikes: keep headroom, speed up startup, and pre-scale for known events.
  • Liveness restarts, readiness gates traffic; graceful shutdown drains in-flight work before exit.
  • Most outages come from changes — use canaries with automated analysis, fast rollback and feature flags.
  • Keep database migrations backward-compatible with expand → migrate → contract.
  • Manage infrastructure as reviewed code; use serverless for spiky, event-driven workloads.

Check your understanding

Your liveness probe checks that the database is reachable. The database has a 30-second blip. What happens?

Dependency checks belong in readiness (if anywhere). Liveness should only detect a stuck process.

A container exceeds its memory limit. What happens?

Memory isn't compressible, so exceeding the limit kills the container. CPU over-limit is throttled instead.

You deploy a release whose bug only shows up as elevated 500s for real users. Which strategy limits impact best?

Health checks pass, so only real-traffic metrics reveal the bug. A canary limits exposure while analysis decides.

You need to rename column fullname to display_name with zero downtime. First step?

Expand first. Old and new code coexist during the rollout, so both columns must work until the contract step.

Traffic doubles in 10 seconds, but new pods need 90 seconds to load a model. What best protects users?

No autoscaler can beat a 90-second startup. Spare capacity and graceful degradation cover the gap.
