Containers, Kubernetes & Shipping Safely

A design on a whiteboard is worth nothing until it runs in production. That means hundreds of machines, updated many times a day, without users noticing. This chapter covers how modern systems are packaged, placed on machines, scaled and released. It also explains why most outages are caused not by traffic, but by changes.

From servers to containers

“It works on my machine” happens because an app depends on an exact OS, runtime and set of libraries. Move it to another machine and something is slightly different. For example, your laptop has Python 3.12 and OpenSSL 3, while the server has Python 3.9 and OpenSSL 1.1. A library call that exists on one simply isn't there on the other. There are two ways to give each app its own sealed-off environment:

  • Virtual machines (VMs) fake the hardware. Each VM boots a whole operating system of its own.
  • Containers fake the operating system instead. All containers share the host's kernel (the core of the OS). But each one gets its own private view of files, network and processes (via Linux namespaces), and a cap on how much CPU and memory it can use (via cgroups).

Each container takes MBs and starts in about a second, so you can fit many on one machine. Isolation is weaker, though. To run untrusted code from many customers, use sandboxes like gVisor or Firecracker microVMs.

When to pick which: containers are the default for your own services, because they are light, fast to start and pack densely. VMs are the right choice when you need a different operating system (for example Windows next to Linux), a custom kernel, or strong isolation between customers who don't trust each other. In the cloud you usually get both: containers running inside VMs that the provider rents to you.

The Dockerfile below builds an image in two stages. The first stage has the full Go compiler (hundreds of MB) and builds the program. The second stage copies only the finished program into a tiny base image. The compiler never ships, so the final image is small, quick to download, and has fewer programs an attacker could misuse.

# Multi-stage Dockerfile: small, reproducible, non-root
FROM golang:1.23 AS build             # heavy toolchain only in the build stage
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                   # cached layer: only re-runs when deps change
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/api

FROM gcr.io/distroless/static:nonroot  # ~2 MB base, no shell, fewer CVEs
COPY --from=build /app /app
USER nonroot
ENTRYPOINT ["/app"]
🧅
Images are layered and immutable

An image is the packaged app plus everything it needs. Each Dockerfile instruction adds a layer. Layers are cached, named by a hash of their content, and shared between images. Some rules:

  • Tag each release with its git SHA (the commit ID), or pin it by digest (the image's hash).
  • Never deploy :latest, because it can point to a different image tomorrow.
  • Build once. The exact same image goes to staging and then production.
  • Settings come from the environment, not baked into the image (the “12-factor app” rule).

Kubernetes: a declarative control loop

Running thousands of containers by hand is impossible. Kubernetes works like a thermostat. You set the desired state, such as “3 copies of api:v42, each with half a CPU (500m)”. Then controllers (background loops) keep comparing what you asked for with what is actually running, and fix any gap. You never say “start a container on node 7”. You only say what should exist.

Why is “declarative” better than a script of commands? A script like “start 3 containers” runs once. If one container crashes an hour later, nothing notices. A control loop runs forever: every few seconds it asks “do 3 exist?” and fixes the answer. The same loop covers crashes, dead machines and your own changes. Change replicas: 3 to replicas: 5, and the loop simply sees a gap of 2 and closes it.

kubectl apply → running pods → self-healingStep-through
  1. You run kubectl apply -f deployment.yaml. The API server checks who you are, checks your permissions (RBAC), and applies admission policies, such as “images must come from our registry”.
  2. The request is saved in etcd, a key-value store copied across machines using Raft (Chapter 13). Every component talks only through the API server. That's why any of them can crash and restart without harm.
  3. The ReplicaSet controller watches the API for changes. It sees: desired 3 pods, actual 0. So it creates 3 Pod objects, not yet assigned to any machine.
  4. The scheduler picks a machine (node) for each pod. First it filters out nodes that can't fit the pod's resource requests or break its placement rules (affinity and taints). Then it scores the rest, for example preferring different zones and emptier nodes, and assigns each pod.
  5. Each node runs an agent called the kubelet. It sees the pods assigned to it, downloads the image, starts the containers and reports back. Once a pod's readiness probe passes, the pod is added to the Service and starts receiving traffic.
  6. Heartbeats from node-3 stop. After a grace period, its pods are marked as lost. The controller sees desired 3, actual 2…
  7. …and creates a replacement pod, which gets placed on a healthy node. Nobody was woken up. The same loop handles scaling, rolling updates and crashes.

Scheduling, requests & limits

Every container states two numbers. Requests are what the scheduler reserves for it, guaranteed. Limits are the hard ceiling. What happens at the ceiling depends on the resource:

  • Go over the CPU limit and you're throttled: you keep running, just slower.
  • Go over the memory limit and you're OOMKilled (killed for being “out of memory”) and restarted.

Set requests too high and you pay for machines that sit idle. Set them too low and busy neighbours on the same node starve you.

CPU is often written in millicores: 500m means half of one CPU core, 2000m means two cores. A sized example: a node has 4 cores (4000m) and 8 GiB of memory. A pod requesting 500m and 1 GiB fits 8 times by CPU and 8 times by memory, so 8 pods fit. A pod requesting 500m and 3 GiB fits 8 times by CPU but only 2 times by memory, so only 2 fit, and 3 cores sit unused. The tightest resource decides. Matching pod shapes to node shapes is a real cost lever (Chapter 24).

A common starting point: set requests near the pod's normal usage (say the p90 of what it actually uses), set the memory limit a little above its peak, and be cautious with CPU limits, because throttling can add latency even when the machine has spare CPU.

Autoscaling

Traffic is rarely flat. A shopping site may see 5× more requests at 8 pm than at 4 am. Running enough machines for the peak all day wastes money; running enough for the average falls over at the peak. Autoscaling adds capacity as load rises and removes it as load falls. There are three kinds, working at different levels.

↔️

Horizontal Pod Autoscaler

Adds or removes pod copies to keep a metric near a target, such as CPU at 60%, requests per second, or queue length (via KEDA): desired = ceil(current × actual / target).

🖥️

Cluster Autoscaler / Karpenter

When pods are waiting because there's no room, it adds machines (takes 1–3 minutes). It removes underused machines by moving their pods elsewhere first.

↕️

Vertical Pod Autoscaler

Suggests or changes each pod's requests and limits based on what it actually uses. It makes pods the right size, instead of adding more of them.

Working the HPA formula with numbers: 4 pods are running at 90% CPU, and the target is 60%. desired = ceil(4 × 90 / 60) = ceil(6) = 6 pods. Once the 2 new pods are ready, the same load spreads over 6 pods, and each sits near 60%. The catch is time. The HPA checks metrics every 15 seconds or so, a new pod may need a new machine (1–3 minutes), and then the app must start and warm up. During that whole gap, the original 4 pods carry all the extra load.

Health probes & graceful shutdown

Kubernetes cannot see inside your app. It only knows the process is running. A running process can still be stuck in a deadlock, still loading a 2 GB model, or unable to reach its database. Probes are small checks (usually an HTTP request like GET /healthz) that let the app tell Kubernetes which of these it is in. Each probe type answers a different question and triggers a different action, so mixing them up causes outages.

❤️

Liveness

“Is the process stuck?” If it fails, the container is restarted. Keep this check trivial. Never check dependencies here, or one database hiccup restarts your whole fleet.

✅

Readiness

“Should I get traffic right now?” If it fails, the pod stops getting traffic but is not restarted. Use it during warm-up, overload, or when a critical dependency is down.

🐢

Startup

“Has the slow boot finished?” It pauses liveness checks until the app has started. Otherwise slow starters get killed over and over.

Shutdown matters just as much. Pods are stopped all the time: every deploy, every scale-down, every node upgrade. If a pod simply dies, the requests it was handling fail. With 20 pods each handling 50 requests at any moment, a careless deploy fails about 1,000 in-flight requests. A graceful shutdown follows these steps:

Pod marked Terminating

During a deploy or scale-down, Kubernetes sends SIGTERM (a polite “please stop” signal). At the same time, it starts removing the pod from the Service. That removal takes a few seconds to reach every load balancer.

Keep serving briefly

A preStop sleep of about 5s gives load balancers time to stop sending new requests before the app stops accepting them. Without it, every deploy causes a burst of connection errors.

Drain

Stop accepting new work and finish the requests already in progress. Close WebSockets with a hint to reconnect elsewhere, commit Kafka offsets, and release locks.

Exit before the deadline

After terminationGracePeriodSeconds (default 30s), the pod gets SIGKILL, which stops it instantly. Set the grace period longer than your slowest request.

CI/CD: from commit to production

CI (continuous integration) means every change is built and tested automatically as soon as it is pushed. CD (continuous delivery or deployment) means a change that passes is released through an automated pipeline, not by someone typing commands. The point is small, frequent, boring releases. A deploy with 3 small changes is easy to check and easy to undo. A deploy with 300 changes from the last month is hard to test, and when it breaks, nobody knows which change did it.

Commit & review minutes

Small pull requests, merged often into one main branch (trunk-based development). Reviews are required and the main branch is protected.

Continuous integration < 10 min

Build once. Run unit and integration tests and a linter. Scan dependencies and the container for known security holes, and scan for leaked passwords. The output is a signed image that never changes, tagged with the commit SHA.

Deploy to staging

Apply database migrations (they must work with the old code too!). Run end-to-end and contract tests on production-like infrastructure.

Progressive production rollout

Start with a canary. Automatically compare its error rate and latency against your SLOs (reliability targets). Then grow gradually to 100%, region by region. Roll back automatically if things get worse.

GitOps

The desired state of every environment lives in git. An agent inside the cluster (Argo CD, Flux) keeps making the cluster match it. Rollback is just a git revert, and the git log is your audit trail.

Deployment strategies

Google's SRE (site reliability engineering) data suggests about 70% of outages are caused by changes. Your deployment strategy decides two things: how many users a bad change can hurt, and how fast you can undo it.

  • Recreate: stop every old copy, then start the new ones. Simple, but there is downtime in between.
  • Rolling: replace copies a few at a time (say 2 of 10), waiting for each batch to pass health checks. No downtime, but old and new versions serve traffic side by side for a while.
  • Blue-green: start a full second fleet (green) with the new version next to the old one (blue), then switch all traffic at once. Switching back is instant, but you pay for two fleets during the deploy.
  • Canary: send a small share of traffic (say 5%) to the new version, compare its metrics with the old one, and widen only if it looks healthy.

A sized example: 1 million requests an hour, and a release that fails 30% of requests. Blue-green sends everyone to it, so in the 5 minutes before someone switches back, about 25,000 requests fail. A 5% canary with automated analysis sends 50,000 requests an hour to the new version. If it detects the problem in 5 minutes and rolls back, only about 1,250 requests fail, about 20× fewer.

Database migrations: expand, migrate, contract

During any zero-downtime rollout, old and new code run at the same time against the same database. So never rename or drop a column in one step. Do it in three:

  • Expand: add the new column (allowing empty values), and deploy code that writes to both columns.
  • Migrate: fill in the new column for old rows, in batches. Then switch reads to the new column.
  • Contract: once no old code is left running, drop the old column in a later release.

Why not just rename in one step? During a rolling deploy, some pods still run the old code. The moment the column is renamed, every old pod's query for fullname fails, and if the new code has a bug and you roll back, the old code can't find its column at all. With the three steps, every moment in between works for both versions, and each step can be undone on its own.

Infrastructure as code

Your app runs on more than containers: databases, storage buckets, networks, load balancers, DNS records and permissions. If these are created by clicking in a cloud console, nobody can say exactly how production was built, review a change before it happens, or rebuild it in a new region. Infrastructure as code (IaC) describes all of it in text files kept in git. A tool such as Terraform compares the files with what exists in the cloud and makes only the changes needed, the same desired-state idea as Kubernetes.

# Terraform: the environment is reviewed, versioned and reproducible like application code
resource "aws_s3_bucket" "uploads" {
  bucket = "acme-prod-uploads"
}
resource "aws_db_instance" "orders" {
  engine              = "postgres"
  instance_class      = "db.r6g.xlarge"
  multi_az            = true                       # synchronous standby in another AZ
  backup_retention_period = 14
  deletion_protection = true
}
# $ terraform plan   → shows exactly what will change before anything does
📋

Plan before apply

Every infrastructure change is a diff in a pull request. It gets reviewed, then CI applies it. Nobody clicks around in the production console.

🧊

Immutable infrastructure

Don't log in to servers and patch them by hand. Build a new image and replace the old machines. That avoids “snowflake” servers that are each slightly different, and settings that slowly drift apart.

🌍

Environments from modules

Dev, staging and every production region are built from the same reusable modules, with different settings. This is essential for running in many regions (Chapter 22).

Serverless

Functions-as-a-Service (AWS Lambda, Cloud Run, Cloudflare Workers) take this idea as far as it goes. You just upload code. The provider runs it for each request, scales from zero to thousands of copies, and bills you per millisecond of use.

A rough cost comparison shows when it pays off. A webhook handler that gets 50,000 requests a day, each running 100 ms, uses about 1.4 hours of compute a day. On serverless you pay for those 1.4 hours; a container kept running around the clock pays for 24. Now take an API serving 2,000 requests per second all day. Its functions are almost never idle, and the per-request price is usually higher than an always-on container doing the same work. Rule of thumb: serverless wins when traffic is low, spiky or idle for long stretches; containers win when load is steady and high.

Shines for
  • Spiky or low, unpredictable traffic (scale to zero)
  • Event glue: “on S3 upload → generate thumbnail”
  • Scheduled jobs, webhooks, lightweight APIs
  • Tiny teams with no ops capacity
Watch out for
  • Cold starts: the first request to a new copy waits while it boots (100 ms to seconds)
  • Limits on how long a function can run and how much memory it gets
  • Connection storms: 1,000 functions each opening database connections. Put a connection pooler or proxy in between
  • At steady high volume, often pricier than containers. And it ties you to one vendor
⚠️
Common mistakes
  • Liveness probes that check dependencies. One database hiccup then restarts your entire fleet at once.
  • Deploying without a fast rollback. If rolling back takes 20 minutes, your incident lasts at least 20 minutes.
  • Breaking the database schema in one step. During any rolling deploy, old and new code run at the same time. Use expand, migrate, contract.
  • No resource requests at all. The scheduler then assumes the pod needs nothing, packs too many onto one node, and they fight over CPU and memory under load.
  • Deploying :latest or rebuilding per environment. Staging tested one image and production runs another. Build once, tag with the commit SHA, and promote that exact image.
🎤
Interview drill

Design: Roll out a change that alters both the API response and the database schema, with zero downtime.

How a strong answer sounds
Expand first. Add the new column and the new response field, but keep the old ones. Deploy code that writes both and still reads the old. Backfill old rows in batches. Then switch reads to the new field behind a feature flag, canary it, and watch error rates. Only remove the old shape (contract) in a later release, once no client and no code uses it. Confirm that from access logs, don't assume it. Each step can be undone on its own.

Operate: Traffic triples in 30 seconds. Autoscaling takes 3 minutes to add pods. What saves you?

How a strong answer sounds
Headroom: run at about 60% so you can absorb a burst. Fast startup: small images, lazy warm-up, and image layers downloaded in advance. A queue or admission control, so extra load waits instead of breaking everything. Then degrade gracefully: serve cached or simpler responses, drop low-priority traffic, and keep the most important path working. For events you can predict, pre-scaling is the cheapest fix of all.

🧠 Key takeaways

  • Containers package an app with its dependencies and share the host's kernel. Build small images that never change, tagged by commit.
  • Kubernetes controllers keep making the real state match the state you declared. That gives you self-healing.
  • Requests decide where pods are placed. Going over a CPU limit slows you down; going over a memory limit gets you killed. Spreading pods is safer, bin-packing is cheaper.
  • Autoscaling always lags behind spikes. Keep headroom, speed up startup, and pre-scale for known events.
  • A failed liveness probe restarts the pod; a failed readiness probe only stops its traffic. Graceful shutdown finishes in-progress work before exiting.
  • Most outages come from changes. Use canaries with automated analysis, fast rollback and feature flags.
  • Keep database migrations compatible with old code using expand → migrate → contract.
  • Manage infrastructure as reviewed code. Use serverless for spiky, event-driven workloads.

Check your understanding

Your liveness probe checks that the database is reachable. The database has a 30-second blip. What happens?

Dependency checks belong in readiness, if anywhere. Liveness should only detect a stuck process.

A container exceeds its memory limit. What happens?

You can't just hand out memory more slowly, so going over the limit kills the container. Going over the CPU limit only slows it down (throttling).

You deploy a release whose bug only shows up as elevated 500s for real users. Which strategy limits impact best?

Health checks pass, so only metrics from real traffic show the bug. A canary limits how many users see it while the analysis decides.

You need to rename column fullname to display_name with zero downtime. First step?

Expand first. Old and new code run side by side during the rollout, so both columns must work until the contract step.

Traffic doubles in 10 seconds, but new pods need 90 seconds to load a model. What best protects users?

No autoscaler can beat a 90-second startup. Spare capacity and graceful degradation cover the gap until new pods are ready.
