Design Ticket Booking

Ticketmaster, airline seats, cinema bookings, restaurant tables, conference passes. This system is unusual in this course: it is tiny in data, enormous in contention. Fifty thousand seats, half a million people, and one instant when they all press “buy”. Sell a seat twice and you have an angry customer at a turnstile; sell it zero times and you lost money.

  • Model seats, holds and orders
  • Guarantee no double-booking under extreme concurrency
  • Expire holds correctly without a nightly cleanup job
  • Absorb flash-sale load with a virtual waiting room
  • Keep browsing available while booking is saturated
  • Handle payment failures, bots and fairness
STEP 1 / 6

Requirements

🛠️ Functional

✓Browse events and see a live seat map with availability
✓Select seats and hold them for ~10 minutes during checkout
✓Pay; on success the seats become an order with tickets
✓Support both reserved seating and general admission (a counter)
✓Waiting room for high-demand on-sales; presale codes

📏 Non-functional

✓Never double-sell a seat — correctness beats availability here
✓Flash sale: 500K users arriving within seconds for 50K seats
✓Browsing stays up even when booking is at capacity
✓Fair and bot-resistant access
✓Seat map freshness within a second or two is fine

The asymmetry is the whole design. Reads are massive but cacheable; writes are small but must be perfectly serialized per seat; and 90% of the arriving traffic is destined to fail because there simply aren't enough seats. A good design rejects that excess load early and politely, instead of letting it reach the database.

STEP 3 / 6

Data model

seats(event_id, seat_id PK,
      section, row, number, price_cents,
      status ENUM('free','held','sold'),
      hold_id, hold_expires_at, version)

holds(hold_id PK, user_id, event_id,
      seat_ids[], expires_at, state)

orders(order_id PK, user_id, event_id,
       seat_ids[], amount_cents, state,
       idempotency_key UNIQUE)

ga_inventory(event_id, tier PK,
       total, sold)      -- general admission: a counter

Everything for one event lives on one shard, keyed by event_id. Events are independent, so this partitions perfectly — and it means a booking transaction never spans shards (Chapter 8).

Seat status is derived from holds, so the only durable truth is: a seat is sold, or it has an unexpired hold, or it's free. Storing hold_expires_at on the seat row lets a single conditional UPDATE both take a hold and reclaim an expired one.

🎯

General admission is much easier: it's a counter, not a set of unique items. UPDATE ga SET sold = sold + 2 WHERE sold + 2 <= total — one row, one atomic check. Reserved seating is harder precisely because each seat is a distinct, non-substitutable item.

STEP 4 / 6

The core problem: two people, one seat

Ten thousand people click seat H-14 in the same second. Exactly one must win. The naive implementation — read the seat, see it's free, then write — is a textbook race condition, and at this concurrency it fires constantly.

Pick a strategy and open the sale.
🧪 Read-then-write double-sells immediately. The conditional UPDATE is correct and fast — the database's row lock does the work, and losers get zero rows updated and simply pick another seat. Explicit FOR UPDATE locks are also correct but hold locks longer, so latency climbs with concurrency. A per-event queue serializes everything: bulletproof, but throughput is capped by one writer.
-- The whole correctness story in one statement: take the seat only if it is still takeable
UPDATE seats
   SET status = 'held', hold_id = :hold, hold_expires_at = now() + interval '10 minutes',
       version = version + 1
 WHERE seat_id = :seat
   AND (status = 'free'                                   -- free…
        OR (status = 'held' AND hold_expires_at < now()));  -- …or an expired hold (lazy reclaim)
-- 1 row updated → you got it.  0 rows → someone else did; pick another seat.
⏳

Expiring holds lazily

Don't rely on a sweeper job to free seats — the condition above reclaims an expired hold at the moment someone needs it. Run a background sweeper too, but only so the seat map looks right; correctness never depends on it.

🧊

Hold, then charge

Never charge before the seat is secured, and never confirm the order before the charge settles. The hold gives you a bounded window in which to run the payment saga (Chapter 37) with compensations if it fails.

🔁

Idempotency everywhere

Users double-click and mobile networks retry. Hold requests carry a hold ID, orders carry an idempotency key, and re-submitting either returns the original result instead of taking a second seat.

Absorbing the rush: the virtual waiting room

500,000 people, 50,000 seats. Letting everyone into the booking flow guarantees a meltdown and a terrible experience. Instead, admit users at the rate the system can actually serve, and tell everyone else exactly where they stand.

STEP 5 / 6

End-to-end architecture

From “on sale” to a ticket in a walletStep-through
  1. The event page, images and seat-map skeleton are static files on a CDN. Half a million people can load them without touching your servers at all (Chapter 6).
  2. The queue itself lives at the edge: a signed token with a position and an admit time. The booking tier only accepts requests carrying a valid token, so it can never be flooded.
  3. The full map is cached; changes stream as small deltas over WebSocket (“H-14 now held”). Slight staleness is fine — the authoritative check happens on the hold attempt.
  4. One atomic UPDATE per seat takes the hold for 10 minutes. Losers get a friendly “those seats just went — here are the closest available” rather than an error.
  5. The payment runs with an idempotency key (Chapter 37). Succeed → seats become sold in the same transaction that records the order. Fail or time out → the hold expires and the seats return to the pool automatically.
  6. Ticket generation, wallet passes, confirmation email and analytics are driven from order events (Chapter 17's outbox), so a slow email provider can never block a sale.
  7. Under stress: widen the admission interval, serve the seat map from cache only, disable seat-by-seat selection in favour of “best available”, and keep browsing read-only but alive.
STEP 6 / 6

Deep dives

🤖

Bots

Scalpers automate everything. Defences: account age and verification, presale codes, device fingerprinting, per-account and per-payment-instrument limits, CAPTCHA/attestation at queue entry, and honeypot endpoints. Purely technical measures never fully win — pair them with policy (ticket transfer rules, identity at entry).

⚖️

Fairness

FIFO rewards fast networks and bots; a randomized draw among everyone who joined within a window is fairer and reduces the stampede. Publish the rules — perceived unfairness is a bigger reputational problem than latency.

💥

Payment succeeded, hold expired

The nightmare interleaving. Prevent it by validating the hold inside the same transaction that confirms the order, and by keeping the payment window shorter than the hold. If it still happens: refund automatically, or upgrade the customer to an equivalent seat — and alert.

🛫

Deliberate overselling

Airlines oversell because no-shows are predictable and empty seats are pure loss. That's a business decision layered on the same inventory system: sell up to capacity × (1 + expected_no_show), with a compensation budget. Never accidental overselling — this kind is modelled, monitored and priced.

🗺️

Rendering 50,000 seats

Don't send 50K DOM nodes. Pre-render the venue as vector tiles or a canvas, ship availability as a compact bitmap (one bit per seat ≈ 6 KB), and patch it with deltas. Zoom levels load section summaries first — the same tiling idea as maps.

🔍

Observability that matters

Track hold success rate, time-to-first-hold, queue wait vs actual, conversion from admitted to sold, double-book count (must be 0), and payment failure rate. A sudden drop in hold success usually means bots or a stuck sweeper, not load.

🎤
What this problem is really testing

Whether you reach for a distributed lock when a single conditional UPDATE would do. The database already serializes writes to a row; use that. Bring in queues or locks only where you need cross-row invariants (“these 4 seats together, or none”) — and even then, one transaction on one shard usually beats a distributed protocol.

⚠️
Common mistakes
  • Reaching for a distributed lock. A single conditional UPDATE is simpler, faster and safer than any lock service here.
  • Letting everyone into the booking flow at once. Without admission control, the people who would have bought tickets get errors too.
  • Charging before securing the seat. Take the hold first; the payment happens inside that window.
🎤
Interview drill

Design: Four friends want four seats together, or none at all. How?

How a strong answer sounds
One transaction on the event's shard updating all four seat rows conditionally; if fewer than four rows are updated, roll back and return the next-best contiguous block. Because everything for an event lives on one shard, this stays a single-shard transaction rather than a distributed one. For best-available requests, compute candidate blocks from a cached seat map first, then attempt them in order — read from cache, verify with the write.

Operate: The on-sale starts and your booking tier is at 100% CPU with a growing queue. What do you do, in order?

How a strong answer sounds
Widen the waiting-room admission interval first — that's the one lever that reduces load without harming anyone already inside. Then shed non-essential work: disable seat-by-seat selection in favour of best-available, serve the seat map from cache only, and defer analytics. Communicate the queue position honestly. Scaling out helps only if the database isn't the bottleneck; if it is, admission control is the fix, not more app servers.

🧠 Key takeaways

  • Ticketing is a contention problem, not a data-volume problem: tiny data, extreme write conflicts on individual rows.
  • A conditional UPDATE (compare-and-set) prevents double-booking simply and fast — no distributed locks needed.
  • Holds bound the checkout window; reclaim expired holds lazily in the same conditional write.
  • Shard by event so every booking transaction stays on one shard.
  • A virtual waiting room admits users at the rate the system can serve, protecting everyone's experience.
  • Serve seat maps from cache with delta updates; the authoritative check happens at hold time.
  • Do payment inside the hold window with idempotency keys, and drive tickets/emails asynchronously.
  • Fairness, bot mitigation and clear communication matter as much as the technical design.

Check your understanding

10,000 requests try to hold seat H-14 simultaneously. Which approach is both correct and fastest?

The database serializes writes to that row; exactly one UPDATE affects a row and the rest see 0 rows changed. No extra infrastructure, no lock to leak.

Why reclaim expired holds inside the hold query instead of relying on a cleanup job?

If a sweeper is delayed or dead, lazy reclamation still frees seats. The sweeper only keeps the displayed map tidy.

What does a virtual waiting room actually buy you?

It converts an overload (everyone fails) into a queue (most people wait, then succeed or learn it's sold out).

A payment succeeds but the seat hold expired 3 seconds earlier and someone else took the seat. How do you prevent this?

The seat must be re-checked atomically at confirmation. If it still slips through, auto-refund or reseat, and alert — never silently double-sell.

How should the seat map for a 50,000-seat stadium be delivered?

Geometry never changes and availability is one bit per seat; deltas keep it fresh for a few hundred bytes per update.
