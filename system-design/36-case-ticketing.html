Design Ticket Booking

Ticketmaster, airline seats, cinema bookings, restaurant tables, conference passes. This system is unusual in this course. It has very little data, but huge contention — many people fighting over the same few items. Picture fifty thousand seats, half a million people, and one moment when they all press “buy”. Sell a seat twice and you have an angry customer at the gate. Sell it zero times and you lost money.

  • Model seats, holds (temporary reservations) and orders
  • Guarantee no seat is booked twice, even with huge numbers of people clicking at once
  • Expire holds correctly without a nightly cleanup job
  • Handle flash-sale crowds with a virtual waiting room
  • Keep browsing working while booking is at full capacity
  • Handle payment failures, bots and fairness

How these numbers are reached:

  • Arrivals: 500K people in ~30 s is about 17K new visitors every second.
  • Seat-map reads: each person on the page refreshes availability several times a second while clicking around. 500K × ~4 reads/s ≈ 2M reads/s. That is only survivable because every one of them can get the same cached answer.
  • Hold attempts: if most of the 500K try to grab a seat in the first ~10 s, that is 500K ÷ 10 = 50K writes/s, all aimed at the same 50K rows, and mostly at the best few thousand of them.
  • Data size: 50K seats × ~200 bytes per row = 10 MB. The whole event fits in memory many times over. Size is not the problem; contention is.

The whole design comes from one imbalance:

  • Reads are huge but cacheable. Millions of people look at the seat map, and they can all be shown a cached copy.
  • Writes are small, but each seat must be handled strictly one request at a time. Only one person can win a given seat.
  • 90% of the arriving traffic is going to fail anyway, simply because there aren't enough seats.

A good design turns that extra load away early and politely, instead of letting it reach the database.

STEP 3 / 6

Data model

seats(event_id, seat_id PK,
      section, row, number, price_cents,
      status ENUM('free','held','sold'),
      hold_id, hold_expires_at, version)

holds(hold_id PK, user_id, event_id,
      seat_ids[], expires_at, state)

orders(order_id PK, user_id, event_id,
       seat_ids[], amount_cents, state,
       idempotency_key UNIQUE)

ga_inventory(event_id, tier PK,
       total, sold)      -- general admission: a counter

Everything for one event lives on one shard (one database partition), chosen by event_id. Events don't depend on each other, so they split cleanly. It also means a booking transaction never has to touch two shards (Chapter 8).

A seat's status comes from its hold. So the only real truth is one of three things: the seat is sold, it has a hold that hasn't expired, or it's free. Because hold_expires_at is stored on the seat row, one conditional UPDATE can both take a hold and take back an expired one.

🎯

General admission is much easier. It's a counter, not a set of unique items: UPDATE ga SET sold = sold + 2 WHERE sold + 2 <= total — one row, one atomic check. Reserved seating is harder because every seat is different: H-14 can't be swapped for H-15 without asking.

Edge case: the GA counter is a hot row. One row can take perhaps a few thousand updates a second, because each update must wait for the one before it to release the row lock. At 50K attempts/s on a single ga_inventory row, the queue for that lock becomes the bottleneck. A common fix is to split the counter: 10 rows of 5,000 tickets each. Each request picks a row at random and tries the next if that one is sold out. Ten rows means ten requests can proceed at once, and the total can still never go over.

STEP 4 / 6

The core problem: two people, one seat

Ten thousand people click seat H-14 in the same second. Exactly one must win. The obvious approach is: read the seat, see it's free, then write “held”. That's a textbook race condition (a bug where the result depends on who gets there first). Two requests can both read “free” before either one writes. With this many people clicking at once, it happens all the time.

Here is the exact interleaving that breaks it:

  1. Alice's request reads H-14: free.
  2. Bob's request reads H-14: free. Alice hasn't written yet.
  3. Alice's request writes held by Alice.
  4. Bob's request writes held by Bob, overwriting Alice.

Both apps show “Seat reserved!”. Only one of them is true, and neither knows which. The gap between reading and writing is only a millisecond, but with thousands of requests per second on the same seat, that gap is hit constantly. The fix is to make the check and the write one indivisible step, so no one can squeeze in between.

🧪 Read-then-write sells seats twice right away. The conditional UPDATE is correct and fast. The database's own row lock does the work: losers see zero rows updated and just pick another seat. Explicit FOR UPDATE locks are also correct, but they hold the lock longer, so waiting time grows as more people click. A per-event queue handles everything one at a time. It can't go wrong, but one writer limits how many bookings per second you can do.
-- The whole correctness story in one statement: take the seat only if it is still takeable
UPDATE seats
   SET status = 'held', hold_id = :hold, hold_expires_at = now() + interval '10 minutes',
       version = version + 1
 WHERE seat_id = :seat
   AND (status = 'free'                                   -- free…
        OR (status = 'held' AND hold_expires_at < now()));  -- …or an expired hold (lazy reclaim)
-- 1 row updated → you got it.  0 rows → someone else did; pick another seat.

Why this works: the database takes a lock on the row while it updates it. If Alice's and Bob's updates arrive together, one waits for the other. When the second one gets the row, databases like PostgreSQL and MySQL check its WHERE condition against the latest committed version, which now says held, so it matches nothing. The lock is held only for the microseconds the update takes, not while anyone waits on the network.

Holding several seats together. A family wants H-14 to H-17, all or nothing. Run the update for all four in one transaction and check that exactly 4 rows changed. If only 3 did, roll back so none are held. One more edge case: if two families grab overlapping seats in different orders (one locks H-14 then H-15, the other H-15 then H-14), each can end up waiting for the other forever, a deadlock. Always lock seats in sorted seat_id order and the circle can't form. Databases also detect deadlocks and abort one side, which your code should treat as “retry”.

⏳

Expiring holds lazily

Don't rely on a sweeper job (a background task that cleans up) to free seats. The condition above takes back an expired hold at the moment someone needs that seat. You can run a sweeper too, but only so the seat map looks right. Correctness never depends on it. Example: Alice's hold starts at 20:00:00 and expires at 20:10:00. At 20:10:05 Bob tries the seat; his update sees held with an expiry in the past and takes it. Use the database's now(), not each app server's clock, so everyone judges expiry by one clock.

🧊

Hold, then charge

Never charge before the seat is secured. Never confirm the order before the charge goes through. The hold gives you a fixed time window to run the payment saga (Chapter 37) — a series of steps with an “undo” step for each if something fails.

🔁

Idempotency everywhere

Users double-click and mobile networks retry. So hold requests carry a hold ID and orders carry an idempotency key (a unique ID per request). Sending either one again returns the first result instead of taking a second seat.

Absorbing the rush: the virtual waiting room

500,000 people, 50,000 seats. If you let everyone into the booking flow at once, the system melts down and everyone has a terrible time. Instead, let people in only as fast as the system can actually serve them, and tell everyone else exactly where they stand. It's like a popular restaurant with a host at the door: you wait in line, but the kitchen doesn't collapse.

🧪 Without a waiting room, the booking servers get overloaded and everyone gets errors — including the people who would have bought tickets. FIFO (first in, first out) is predictable, but it rewards whoever had the fastest connection at the start (and bots). A lottery among everyone who joined in the first N minutes is fairer. It also removes the reason to keep hammering the site.

Sizing the admission rate. Suppose the booking tier comfortably handles 500 new shoppers a second. Admitting all 500K would take 1,000 s, about 17 minutes. But if buyers take ~2.5 tickets each, 50K seats run out after about 20K buyers, which is only the first ~40 seconds of admissions. So a good waiting room does two things: it admits at the rate the booking tier can handle, and it tells people far back in line early and honestly that tickets are likely gone, instead of making them wait 15 minutes for nothing. Seats released by expired holds can then go to the next people in line.

Edge cases for the admission token. It must be signed so nobody can forge one, carry an expiry so an old token can't be reused tomorrow, and be bound to the user's session or account so one person's token can't be copied and shared with a hundred bots.

STEP 5 / 6

End-to-end architecture

From “on sale” to a ticket in a walletStep-through
  1. The event page, images and the empty seat-map layout are static files on a CDN (a network of servers close to users). Half a million people can load them without touching your own servers at all (Chapter 6).
  2. The queue itself runs at the edge (the CDN). Each person gets a signed token holding their place in line and the time they're allowed in. The booking servers only accept requests with a valid token, so they can never be flooded.
  3. The full map is cached. Changes arrive as small deltas (just what changed) over a WebSocket: “H-14 now held”. Being slightly out of date is fine, because the real check happens when you try to hold the seat.
  4. One atomic UPDATE per seat takes the hold for 10 minutes. People who lose get a friendly “those seats just went — here are the closest available”, not an error.
  5. The payment runs with an idempotency key (Chapter 37). If it succeeds, the seats become sold in the same transaction that records the order. If it fails or times out, the hold expires and the seats go back on sale automatically.
  6. Creating tickets, wallet passes, the confirmation email and analytics all happen later, triggered by order events (Chapter 17's outbox). So a slow email provider can never block a sale.
  7. When overloaded: let people in more slowly, serve the seat map only from cache, and replace pick-your-own-seat with “best available”. Browsing may become read-only, but it stays up.
STEP 6 / 6

Deep dives

🤖

Bots

Scalpers automate everything. Defences include account age and verification, presale codes, device fingerprinting (recognising the same device across accounts), limits per account and per card, CAPTCHA or device checks when joining the queue, and honeypot endpoints (fake URLs only bots would hit). Technical measures alone never fully win. Pair them with policy, like ticket transfer rules and ID checks at the door.

⚖️

Fairness

FIFO rewards fast networks and bots. A random draw among everyone who joined within a time window is fairer and calms the stampede. Publish the rules. If people feel it's unfair, that hurts your reputation more than slowness does.

💥

Payment succeeded, hold expired

The nightmare timing: the card is charged just after the hold ran out and someone else took the seat. Prevent it by checking the hold inside the same transaction that confirms the order. Also keep the payment time limit shorter than the hold: with a 10-minute hold, a buyer who reaches payment at minute 9 might get only 60 seconds, so stop starting new charges in the last minute or extend the hold once when payment begins. If it still happens, refund automatically or move the customer to an equal seat — and raise an alert.

🛫

Deliberate overselling

Airlines oversell on purpose, because no-shows are predictable and an empty seat is pure loss. That's a business decision built on top of the same inventory system: sell up to capacity × (1 + expected_no_show), with a budget to compensate bumped customers. For a 180-seat plane with 5% expected no-shows, that is 180 × 1.05 = 189 tickets. It is never accidental — it's planned, watched and priced.

🗺️

Rendering 50,000 seats

Don't send 50K separate page elements (DOM nodes). Draw the venue ahead of time as vector tiles or a canvas. Send availability as a compact bitmap — one bit per seat, 50,000 ÷ 8 ≈ 6 KB in total — and patch it with deltas. When zoomed out, load section summaries first. It's the same tiling idea online maps use.

🔍

Observability that matters

Track: how often holds succeed, time until a user's first hold, promised queue wait vs actual wait, how many admitted users end up buying, double-book count (must be 0), and payment failure rate. A sudden drop in hold success usually means bots or a stuck sweeper, not heavy load.

🎤
What this problem is really testing

Whether you reach for a distributed lock when a single conditional UPDATE would do. The database already handles writes to one row one at a time — use that. Bring in queues or locks only when a rule covers several rows at once (“these 4 seats together, or none”). Even then, one transaction on one shard usually beats a distributed protocol.

⚠️
Common mistakes
  • Reaching for a distributed lock. A single conditional UPDATE is simpler, faster and safer than any lock service here.
  • Letting everyone into the booking flow at once. Without controlling who gets in, the people who would have bought tickets get errors too.
  • Charging before securing the seat. Take the hold first. The payment happens inside that hold window.
🎤
Interview drill

Design: Four friends want four seats together, or none at all. How?

How a strong answer sounds
Use one transaction on the event's shard that conditionally updates all four seat rows. If fewer than four rows change, roll back and offer the next-best block of seats side by side. Since everything for an event lives on one shard, this is a single-shard transaction, not a distributed one. For “best available” requests, first work out candidate blocks from the cached seat map, then try them in order. Read from the cache; confirm with the write.

Operate: The on-sale starts and your booking tier is at 100% CPU with a growing queue. What do you do, in order?

How a strong answer sounds
First, let people out of the waiting room more slowly. That's the one lever that cuts load without hurting anyone already inside. Then drop non-essential work: switch from pick-your-seat to best-available, serve the seat map only from cache, and postpone analytics. Tell people their queue position honestly. Adding servers only helps if the database isn't the bottleneck. If it is, controlling admission is the fix, not more app servers.

🧠 Key takeaways

  • Ticketing is a contention problem, not a data-size problem: very little data, but huge numbers of people trying to write the same rows.
  • A conditional UPDATE (compare-and-set) prevents double-booking simply and quickly — no distributed locks needed.
  • Holds put a time limit on checkout. Take back expired holds in the same conditional write, at the moment they're needed.
  • Shard by event so every booking transaction stays on one shard.
  • A virtual waiting room lets users in only as fast as the system can serve them, which protects everyone's experience.
  • Serve seat maps from cache with small delta updates. The real check happens when a seat is held.
  • Take payment inside the hold window using idempotency keys. Send tickets and emails later, in the background.
  • Fairness, stopping bots and clear communication matter as much as the technical design.

Check your understanding

10,000 requests try to hold seat H-14 simultaneously. Which approach is both correct and fastest?

The database handles writes to that row one at a time. Exactly one UPDATE changes the row; the rest see 0 rows changed. No extra systems, and no lock that could be left stuck.

Why reclaim expired holds inside the hold query instead of relying on a cleanup job?

If the sweeper is late or has crashed, seats are still freed when someone tries to hold them. The sweeper only keeps the displayed map tidy.

What does a virtual waiting room actually buy you?

It turns an overload (everyone fails) into a queue (people wait, then either buy or find out it's sold out).

A payment succeeds but the seat hold expired 3 seconds earlier and someone else took the seat. How do you prevent this?

The seat must be checked again, atomically, when the order is confirmed. If a case still slips through, refund automatically or give another seat, and alert. Never quietly sell a seat twice.

How should the seat map for a 50,000-seat stadium be delivered?

The layout never changes, and availability is one bit per seat. Deltas keep it up to date for a few hundred bytes per update.
