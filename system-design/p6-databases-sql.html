Databases & SQL Basics

Nearly every system you'll design keeps its most important data in a database — users, orders, messages, payments. The database is usually the hardest part to scale and the part you can least afford to lose. This chapter teaches what a database does that plain files can't, how data is laid out in tables, how to ask questions in SQL, and the two ideas that come up in every design discussion: indexes and transactions.

Why databases exist

Your app could save its data in ordinary files — one file per user, say. It would work for a demo. Then real usage arrives, and four problems appear. A database is software that solves all four for you:

🔎

Finding data fast

“Which user has this email?” among 50 million users. Reading every file would take minutes. A database uses indexes to answer in milliseconds.

👥

Many users at once

Two people buy the last ticket at the same moment. With files, one silently overwrites the other. A database uses locks and transactions so the result is always correct.

🧩

Never half-saved

A crash in the middle of a save leaves a corrupted file. A database guarantees each change is either fully saved or not at all.

💬

Asking new questions

“Orders over $50 from last week, by country.” With files, you write new code for every question. With a database, you write one query.

Because a database is the source of truth, most big design questions are really database questions: how to make it faster (caching, indexes), how to keep it safe (copies on other machines), and how to grow it past one machine (splitting the data). This chapter gives you the vocabulary; Chapter 7 and Chapter 8 go deep.

Tables, rows and keys

The most common kind of database is relational — PostgreSQL, MySQL, SQL Server, SQLite. It stores data in tables. Each table is like a spreadsheet with strict rules: every row is one record (one user), every column is one field (their email), and each column has a fixed type (integer, text, timestamp…). The list of tables and their columns is called the schema.

  • 🔑 A primary key uniquely identifies each row. No two users share an id, and it never changes. Usually a number the database generates.
  • 🔗 A foreign key is a column that points at another table's primary key. orders.user_id = 1 means “this order belongs to user 1”. The database can enforce that it always points at a real user.

Notice what's not stored: the orders table doesn't repeat Ada's name and email in every row. Each fact lives in exactly one place, and tables are linked by keys. This is called normalisation. If Ada changes her email, you update one row, not hundreds. (Big systems sometimes deliberately repeat data for speed — denormalisation — accepting the extra work of keeping copies in sync. You'll see that trade-off in Chapter 7.)

SQL: asking the database questions

You talk to a relational database in SQL (Structured Query Language). SQL is declarative: you describe what you want, and the database works out how to find it. Here are the statements you'll meet most:

-- Create a table: its columns and their types
CREATE TABLE users (
  id    INTEGER PRIMARY KEY,
  name  TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE
);

-- Add rows
INSERT INTO users (id, name, email) VALUES (1, 'Ada', 'ada@example.com');

-- Read: pick columns, filter rows, sort, and take only the first few
SELECT id, total FROM orders
WHERE status = 'shipped' AND total > 20
ORDER BY total DESC
LIMIT 10;

-- Change existing rows (always with a WHERE, or you change every row!)
UPDATE orders SET status = 'shipped' WHERE id = 102;

-- Remove rows
DELETE FROM orders WHERE id = 103;

-- Summarise: one row per user, with their order count and total spend
SELECT user_id, COUNT(*) AS orders, SUM(total) AS spent
FROM orders
GROUP BY user_id;

Those four verbs — create, read, update, delete — are called CRUD, and they line up neatly with the HTTP methods from P5: POST → INSERT, GET → SELECT, PUT/PATCH → UPDATE, DELETE → DELETE.

Joins: combining tables

  
Data is split across tables, but questions often span them: “show each order with the customer's name”. A JOIN combines rows from two tables wherever a condition matches — usually a foreign key equalling a primary key:


SELECT users.name, orders.id, orders.total
FROM users
JOIN orders ON orders.user_id = users.id;

Joins are powerful but not free. Joining two huge tables can be slow, and once data is split across many machines (Chapter 8), a join may need data from several of them. That's one reason large systems sometimes store data pre-joined.


  
Indexes: the index at the back of a book

  
How does the database find Grace's row? Without help, it must check every row one by one — a full table scan. With a million users, that's a million checks for every login. An index fixes this. It's a separate, sorted structure of one column's values, each pointing to its row — exactly like the index at the back of a book, which lets you jump to “TCP, page 212” instead of reading every page.


-- Build a sorted index on email (UNIQUE also stops two users sharing an email)
CREATE UNIQUE INDEX users_email_idx ON users (email);

The index keeps emails sorted, so the database can halve the search at each step (binary search). Real databases use a B-tree, a wide sorted tree that finds any row among millions in about 3–4 disk reads (P7 explains why).

  

  
Indexes are not free. Each one takes extra disk space, and every insert, update or delete must also update every index on that table, so writes get slower. The rule of thumb: add indexes for the questions you actually ask often — the columns in your common WHERE, JOIN and ORDER BY clauses — and not on every column.


  
Transactions: all or nothing

  
Moving $100 from Alice to Bob takes two changes: subtract from Alice, add to Bob. What if the server crashes between them? $100 disappears. A transaction groups several changes so they either all happen or none do. If anything fails before the end, the database rolls back — undoing the partial work as if nothing happened.


BEGIN;                                                   -- start the transaction
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                                                  -- make both changes permanent together

ACID in one line each

  
Relational databases promise four properties for transactions, known together as ACID:

  

    
⚛️
Atomic
All of the transaction's changes happen, or none do. No half-transfers.

    
📐
Consistent
The data always obeys your rules — unique emails, valid foreign keys, balances never negative if you said so.

    
🚧
Isolated
Transactions running at the same time don't see each other's half-finished work. This prevents the lost-update race from P2.

    
💾
Durable
Once the database says “committed”, the change survives a crash — it has been flushed to disk.

  

  
How much isolation you actually get depends on a setting called the isolation level, and stronger isolation costs speed. Chapter 7 shows exactly which anomalies each level allows.

SQL and NoSQL

  
Relational databases are the safe default, but they aren't the only kind. NoSQL (“not only SQL”) is a loose name for databases that store data differently, usually trading some of SQL's features — joins, flexible queries, multi-row transactions — for simpler scaling across many machines or a better fit for one kind of data.

  

    

      
KindStores data asGreat forExamples

      
        
Relational (SQL)Tables with a fixed schema, linked by keysMost business data; anything needing transactions and flexible queriesPostgreSQL, MySQL

        
Key–valueA giant dictionary: key → valueCaches, sessions, lookups by ID at huge scaleRedis, DynamoDB

        
DocumentJSON-like documents, each with its own shapeData read and written as one whole object, e.g. a product with nested optionsMongoDB, Firestore

        
Wide-columnRows with many columns, split across machines by keyEnormous write volumes: messages, events, time seriesCassandra, Bigtable

        
GraphNodes and relationshipsMany-hop relationship questions: “friends of friends”Neo4j

      
    

  

  
A good first instinct in an interview: start with a relational database unless you have a specific reason not to — a data shape it handles badly, or a scale it can't reach. Then say what that reason is. Chapter 7 compares the options in depth, and Chapter 12 covers graphs.


  
⚠️
Common mistakes

    
    
      
  • UPDATE or DELETE without WHERE. It changes every row in the table. Always check the WHERE clause first.
    • 
      
  • No index on a column you search by. Works in development with 100 rows; takes seconds per query in production with 10 million.
    • 
      
  • Indexing everything. Every index slows every write and uses space. Index for your real queries.
    • 
      
  • Doing multi-step changes without a transaction. A crash or error between steps leaves data half-changed.
    • 
      
  • Storing large files in the database. Put the bytes in object storage and keep only a reference in the database.
    • 
      
  • Using an INNER JOIN when you need every row. Rows without a match silently disappear. Use a LEFT JOIN when they must stay.
    • 
    


  
🎤
Interview drill

    
Model it: Design tables for a simple library: books, members, and loans (who borrowed which book, when, and whether it's returned).

    
How a strong answer sounds
books(id PK, title, author, isbn UNIQUE), members(id PK, name, email UNIQUE), and loans(id PK, book_id FK → books, member_id FK → members, borrowed_at, due_at, returned_at NULL). A loan is its own table because one book is borrowed many times and a member borrows many books. Index loans(member_id) for “my loans” and loans(book_id, returned_at) to find whether a book is currently out. Creating a loan and marking the book unavailable happen in one transaction, so two members can't borrow the same copy.

    
Explain it simply: Queries by email got fast after adding an index, but sign-ups got slightly slower. Why?

    
How a strong answer sounds
The index is a separate sorted structure. Searching it is fast, like binary search, instead of scanning every row. But every new user must now be written twice — into the table and into the right place in the index — so inserts do a bit more work. It's usually a great trade for a column you search often.

  


  

    
🧠 Key takeaways

    
    
      
  • Databases give you fast lookups, safe concurrent updates, all-or-nothing changes and flexible queries — things plain files don't.
    • 
      
  • Relational databases store rows in typed tables; primary keys identify rows, and foreign keys link tables. Each fact lives in one place.
    • 
      
  • SQL is declarative: SELECT … WHERE … ORDER BY … LIMIT to read, INSERT/UPDATE/DELETE to change, GROUP BY to summarise.
    • 
      
  • JOIN combines tables on matching keys; INNER drops unmatched rows, LEFT keeps them with empty values.
    • 
      
  • An index is a sorted copy of a column that turns scans into quick lookups, at the cost of space and slower writes.
    • 
      
  • Transactions make several changes atomic; ACID = atomic, consistent, isolated, durable.
    • 
      
  • NoSQL families (key–value, document, wide-column, graph) trade features for scale or fit. Default to relational and justify leaving it.
    • 
    

  


  

    
Check your understanding

    


    

      
Adding an index on the email column makes lookups by email much faster. What's the cost?

      

        
        
        
        
      

      
An index is a second, sorted copy of that column with pointers to the rows. It uses space and has to be kept up to date on every write. So you add indexes for the questions you actually ask, not on every column.

    


    

      
In an orders table, what is user_id most likely to be?

      

        
        
        
        
      

      
It records which user each order belongs to by holding that user's primary key. The orders table has its own primary key (orders.id).

    


    

      
You run SELECT users.name, orders.id FROM users JOIN orders ON orders.user_id = users.id. A user with no orders…

      

        
        
        
        
      

      
A plain JOIN is an INNER JOIN: only rows with a match in both tables are kept. A LEFT JOIN would keep the user, with NULL in the order columns.

    


    

      
Which ACID property guarantees that a committed change survives a power failure a second later?

      

        
        
        
        
      

      
Durability means “committed” really means “on disk”: the database flushes the change (usually to a write-ahead log) before confirming, so a crash can't undo it.

    


    

      
You need to store 20 million user profile photos and show each user's photo on their profile. Where should the photos go?

      

        
        
        
        
      

      
Big binary files belong in object storage, which is cheap and built for large blobs; a CDN can serve them. The database keeps the small facts, like which photo belongs to which user and where it is.
