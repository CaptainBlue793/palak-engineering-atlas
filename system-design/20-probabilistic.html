Probabilistic Structures & Gossip

At huge scale, exact answers often cost too much memory. Think of storing every URL a crawler has seen, every unique visitor, or how often every item appeared. A family of clever structures gives answers that are almost right, using a tiny fraction of the memory. The error is small, and the maths tells you exactly how small. This chapter also covers the protocols large clusters use to stay in sync without a central coordinator.

  • Use Bloom filters to skip expensive lookups
  • Count frequencies with a count-min sketch and find heavy hitters
  • Count billions of unique items in kilobytes with HyperLogLog
  • Find differences between replicas with Merkle trees
  • Spread information through a cluster with gossip
  • Detect failures with heartbeats, phi accrual and SWIM

Why accept approximate answers?

Say you need to know how many unique users visited each of 10,000 pages today, across 3 billion events. An exact answer must store every user ID for every page: about 40 bytes × hundreds of millions of IDs × 10,000 pages. That is far too much. Probabilistic structures accept a small, known error in exchange for using thousands of times less memory. Most are also mergeable: you can combine the summaries from different machines into one.

Put numbers on it for a single page. If 50 million different users visited it, an exact set costs about 50M × 40 bytes = 2 GB. A HyperLogLog costs 12 KB and answers “about 50.3 million”, off by well under 1%. For a dashboard that says “50M visitors”, nobody can tell the difference, and the memory saving is over 100,000×. Approximate answers are the right choice when the result is read by people or used as a hint (“skip this disk read”), and the wrong choice when every single item matters, such as money, permissions or deduplicating payments.

Bloom filters

A Bloom filter answers “have I seen this before?” using very little memory. It is a row of m bits (all starting at 0) plus k hash functions. Each hash function turns an item into a position in the row.

  • To add an item, hash it k times and set those k bits to 1.
  • To check an item, look at its k bits. If any is 0, the item was definitely never added.
  • If all are 1, it was probably added. Or other items happened to set those same bits. That wrong “yes” is called a false positive.

A small trace with m = 10 bits and k = 2 hash functions:

  1. Add “cat”: its hashes are 1 and 6. Bits 1 and 6 become 1. The row is now 0100001000.
  2. Add “dog”: its hashes are 3 and 6. Bit 3 becomes 1 (bit 6 is already 1). Row: 0101001000.
  3. Check “cow”: its hashes are 3 and 8. Bit 8 is 0, so “cow” was definitely never added.
  4. Check “fox”: its hashes are 1 and 3. Both are 1, set by “cat” and “dog”. The filter says “probably yes”, but “fox” was never added. That is a false positive.

Notice why there are no false negatives: adding an item only ever turns bits on. Once “cat” has set bits 1 and 6, nothing turns them off, so checking “cat” always finds them set. In practice you use the filter as a cheap first check: “definitely not” lets you skip the expensive lookup, and “probably yes” means you do the real lookup to be sure.

m = −n·ln(p) / (ln 2)². Notice that bits per item doesn't depend on n. It depends only on the error rate you accept. Each 10× cut in false positives costs only about 4.8 more bits per item.

Worked example: 1 billion URLs at 1% false positives. ln(0.01) ≈ −4.6 and (ln 2)² ≈ 0.48, so m ≈ 10⁹ × 4.6 / 0.48 ≈ 9.6 billion bits, about 9.6 bits per item, which is 1.2 GB. The best k is 9.6 × 0.69 ≈ 7 hash functions. Storing the 40-byte URLs themselves would take at least 40 GB, so the filter is over 30× smaller.

🗄️

Skip disk reads

LSM-tree databases (Cassandra, RocksDB, HBase — Chapter 7) store data in many sorted files called SSTables, each with its own Bloom filter. A lookup skips every file whose filter says “definitely not here”.

🕷️

Seen-URL checks

A web crawler checks billions of URLs. A false positive just means it occasionally skips a page, which is acceptable (Chapter 30).

🛡️

Cache penetration

Put every valid key in a Bloom filter in front of the cache. Then requests for IDs that don't exist never reach the database (Chapter 6).

🧰
Variants

A standard Bloom filter can't delete, because clearing a bit might also “remove” other items that share it. Counting Bloom filters store small counters instead of single bits, so you can count down. Cuckoo filters also support deletion, and use less space at low error rates. Scalable Bloom filters add new filters as the item count grows past the planned size.

Count-min sketch & heavy hitters

A count-min sketch estimates “how many times did X happen?” in a fixed amount of memory. It is a small grid of counters with d rows and w columns, and each row has its own hash function. To add an item, you bump one counter in each row (the column its hash picks).

To estimate an item's count, look at its d counters and take the minimum. Why the minimum? Other items can share a counter (a collision), and that only ever adds to it. So the smallest counter has the least extra noise. This also means it never undercounts.

A small example with d = 2 rows and w = 4 columns. The stream is: #cats 5 times, #dogs 2 times, #owls once.

  • Row 1 hashes #cats → column 0, #dogs → column 2, #owls → column 0. Row 1 ends as [6, 0, 2, 0].
  • Row 2 hashes #cats → column 1, #dogs → column 3, #owls → column 3. Row 2 ends as [0, 5, 0, 3].
  • Estimate for #owls: min(row 1 col 0 = 6, row 2 col 3 = 3) = 3. The true count is 1, so the sketch overcounts by 2, because #owls collided with a busier tag in both rows.
  • Estimate for #cats: min(6, 5) = 5, which is exact. Its row-2 counter was not shared.

That is the pattern: popular items are barely affected by small extra counts from rare items, while rare items can be badly inflated. The overcount grows with the total number of events divided by the width w, so doubling w roughly halves it.

Heavy hitters means the most frequent items in a stream. To find the top K, keep a small min-heap of the K highest estimates seen so far. After each event, ask the sketch for that item's estimate. If it beats the smallest entry in the heap, swap it in. The sketch does the counting; the heap only remembers who is winning.

HyperLogLog: counting distinct items

Flip a coin until you get heads. If someone tells you their longest run of tails was 10, they probably flipped a lot of times (around 2¹⁰). HyperLogLog (HLL) uses the same idea on hashes. It hashes each item and remembers the longest run of leading zeros it has seen. A rare pattern, like many zeros in a row, suggests many distinct items. A duplicate item hashes to the same value, so it changes nothing.

A single measurement like this is noisy. So HLL uses the first few bits of each hash to pick one of m buckets (called registers), and tracks the maximum per bucket. It then combines all the buckets with a harmonic mean (a kind of average that isn't thrown off by a few large values). Standard error ≈ 1.04 / √m.

Why do leading zeros tell you anything? A good hash makes every bit a fair coin flip. So a hash starts with “1” half the time, with “01” a quarter of the time, and with “001” an eighth of the time. Seeing a hash that starts with at least 10 zeros is a 1-in-2¹⁰ event, so you would expect to need around 1,000 distinct items before one shows up. Repeating the same item never helps, because it always produces the same hash.

Plug in numbers for the error formula: with m = 16,384 registers, √m = 128, and 1.04 / 128 ≈ 0.8%. So a true count of 10 million usually comes back somewhere around 9.92 to 10.08 million. Each register only needs about 6 bits (enough to store a count of up to 63 zeros), so 16,384 registers × 6 bits ≈ 12 KB, whether you count a thousand items or a billion.

Merkle trees: finding differences fast

Two replicas (copies of the same data) each hold a billion keys. Which keys differ? Sending every key over the network to compare is hopeless. A Merkle tree solves this. It hashes the data in blocks. Then it hashes pairs of those hashes, and pairs of those, up to a single root hash at the top.

If the two roots match, the replicas are identical. If not, you only follow the branches whose hashes differ. That takes O(log n) comparisons per difference (roughly the height of the tree).

A small walk-through with 8 keys. Each replica hashes keys in pairs, then pairs of those, then the root: 8 leaves, 4 hashes above them, 2 above those, 1 root. Suppose only key 6 differs.

  1. Compare roots: different. Something is wrong somewhere.
  2. Compare the two children of the root. The left half (keys 1–4) matches, so skip it entirely. The right half (keys 5–8) differs.
  3. Inside the right half, keys 5–6 differ and keys 7–8 match.
  4. Compare keys 5 and 6 directly: key 6 differs. Send just that key.

That is 7 hash comparisons (1 root, then 2 at each of the three levels below it) instead of comparing all 8 keys. The saving grows fast: with a billion keys there are about 30 levels, so roughly 60 small hash comparisons replace a billion key comparisons. The trade-off is upkeep: every write must update the hashes on its path to the root, so many systems rebuild the tree in the background before a repair run instead of keeping it live.

Gossip protocols

How does a 5,000-node cluster learn that a node joined, a schema changed, or a node died? A central coordinator could tell everyone, but it could also fail. The alternative is gossip. Every second, each node picks a few random peers and swaps what it knows. Like a rumour in a school, the news reaches everyone in about O(log N) rounds. It keeps spreading even if many nodes or messages are lost.

Why log N? Roughly, the number of informed nodes multiplies each round. With a fanout of 2 and no losses, 1 node tells 2 others (3 know), those 3 each tell 2 (about 9 know), then about 27, 81, 243. So a 5,000-node cluster is mostly informed after about 8 rounds, not 5,000. Growth slows at the end, because informed nodes increasingly pick peers that already know, which is why a few extra rounds are needed to reach the last stragglers.

The cost is bandwidth and delay, not correctness. Each node sends a few small messages per second whatever the cluster size, so load per node stays flat as the cluster grows. But news takes several seconds to reach everyone, and different nodes briefly disagree about the state. Gossip suits membership lists and metadata that can be a little stale; it is not a replacement for consensus when everyone must agree on one value (Chapter 13).

Failure detection

Over a network with no timing guarantees, you can never be sure a node is dead rather than just slow (Chapter 13). Failure detectors make a practical guess. They trade how fast they notice against how often they raise false alarms.

Both kinds of mistake hurt. Too slow: for, say, 30 seconds, requests keep going to a dead node and time out. Too eager: a healthy node that paused for a 2-second garbage collection is declared dead, its data is copied elsewhere (moving gigabytes), and a minute later it comes back and everything moves again. That thrashing can be worse than the original problem. So a good detector adapts to how the network normally behaves, and double-checks before declaring death.

💓

Heartbeats + timeout

Each node sends a regular “I'm alive” message (a heartbeat). No heartbeat for T seconds means dead. It's simple, but one fixed T is too trigger-happy on a busy network and too slow on a quiet one.

📈

Phi accrual

Instead of a yes/no answer, it outputs a suspicion level φ (phi). φ is based on how heartbeat gaps have actually looked so far. If heartbeats normally arrive every 1s ± 50ms, a 3s gap is extreme, so φ is high. Each application picks its own φ threshold. Used by Cassandra and Akka.

🏊

SWIM

Each round, ping one random member. If it doesn't answer, ask k other members to ping it for you. That avoids false alarms caused by one bad network link. Suspicions and deaths spread by gossip, riding along on the ping messages. Used by Consul, Nomad and memberlist.

SWIM: is node B really dead?Step-through
  1. In this round, A picks B at random and sends a ping. It expects an ack (reply) within about 200ms.
  2. Nothing comes back. But maybe only the link between A and B is congested. Declaring B dead now could trigger a costly, unnecessary reshuffle of data.
  3. A asks k = 2 random members (C and D) to ping B for it, using a ping-req. If either gets an ack, they pass it back to A, and B is fine.
  4. No indirect acks either. B is marked suspect, which is not dead yet. The suspicion rides along on normal gossip messages.
  5. If B is alive and hears it's suspected, it gossips an alive message with a higher incarnation number (a counter only B can increase). That cancels the suspicion. If the timeout runs out with no such reply, B is declared dead, and everyone learns within a few gossip rounds.

Common mistakes
  • Using a Bloom filter where a false positive is unacceptable. It's a quick filter in front of the real answer, not the real answer.
  • Adding up distinct counts. Unique users per day is not the sum of unique users per hour, because the same user shows up in many hours. Use mergeable sketches.
  • Forgetting to size for growth. A Bloom filter built for 10M items gets much worse at 100M. Plan capacity, or use a scalable variant.
  • Trusting count-min estimates for rare items. A tag seen twice can show up as 40 if it collides with popular tags. Use the sketch to rank the top items, not to report exact small counts.
  • Merging sketches built differently. Two HyperLogLogs or count-min sketches merge only if they use the same size and the same hash functions. Fix those settings once for the whole system.

Interview drill

Choose: Which structure for: “has this URL been crawled?”, “top 10 hashtags”, “how many unique viewers?”

How a strong answer sounds
A Bloom filter for seen URLs. A false positive just skips a page, and 10 bits per URL beats storing the full strings. A count-min sketch plus a small heap for the top K. It never undercounts, so the most popular items stay accurate, while rare items are noisy. HyperLogLog for unique viewers. It uses about 12 KB per counter with ~1% error. It also merges across shards and time windows, which exact sets can't do cheaply.

Explain: Two replicas hold a billion keys. How do you find what differs without shipping everything?

How a strong answer sounds
Exchange Merkle trees. Hash the keys in ranges, then hash pairs of hashes up to a root. Matching roots mean identical data, after just one comparison. Otherwise, follow only the branches whose hashes differ, so a single differing key is found in about 30 comparisons. This is exactly what Cassandra-style anti-entropy repair (a background sync job) does. It complements read repair, which only fixes data that someone happens to read.

🧠 Key takeaways

  • Probabilistic structures accept a small, known error for huge memory savings. Most can be merged across machines.
  • Bloom filters answer “definitely not” or “probably yes” using about 10 bits per item. They can't delete.
  • Count-min sketches never undercount. Pair one with a heap to find heavy hitters and trending lists.
  • HyperLogLog estimates billions of distinct items in kilobytes, with about 1% error.
  • Merkle trees find differences between replicas in O(log n) hash comparisons.
  • Gossip spreads information through a cluster in O(log N) rounds, and copes with lost messages and failed nodes.
  • Failure detectors trade speed for accuracy. Phi accrual adapts to network conditions. SWIM uses indirect pings.

Check your understanding

A Bloom filter says an item is not present. How confident can you be?

If any of the item's bits is 0, it was never added. Only “probably present” answers can be wrong.

Why does a count-min sketch take the minimum across rows?

Every counter for an item is at least its true count. The minimum is the closest overestimate.

You need unique visitors per page per hour, rolled up into days and months, for 1M pages. Best tool?

HLLs are tiny, and they merge without double-counting visitors who appear in several hours.

Two replicas with 1 billion keys have a Merkle tree each. Roughly how many hash comparisons to locate a single differing key?

Start at the root and follow only the branch that doesn't match: log₂(10⁹) ≈ 30 levels.

In SWIM, why ask other nodes to probe a non-responding node indirectly?

One slow or broken link shouldn't get a healthy node kicked out. Indirect pings test other network paths.
