Probabilistic Structures & Gossip

At planet scale, exact answers are often too expensive: storing every URL a crawler has seen, every unique visitor, every item's frequency. A family of clever structures gives answers that are almost right using a tiny fraction of the memory — with mathematically bounded error. Alongside them sit the protocols large clusters use to stay in sync without a central coordinator.

  • Use Bloom filters to skip expensive lookups
  • Count frequencies with a count-min sketch and find heavy hitters
  • Count billions of unique items in kilobytes with HyperLogLog
  • Find differences between replicas with Merkle trees
  • Spread information through a cluster with gossip
  • Detect failures with heartbeats, phi accrual and SWIM

Why accept approximate answers?

Imagine you need to know how many unique users visited today, across 3 billion events, for 10,000 different pages. An exact answer stores every user ID per page: ~40 bytes × hundreds of millions of IDs × 10,000 pages. Probabilistic structures trade a small, known error for orders of magnitude less memory, and they're usually mergeable across machines.

Bloom filters

A Bloom filter is a bit array of m bits plus k hash functions. To add an item, hash it k times and set those k bits. To check an item, look at its k bits: if any is 0, it was definitely never added. If all are 1, it was probably added — or those bits were set by other items (a false positive).

🗄️

Skip disk reads

LSM-tree databases (Cassandra, RocksDB, HBase — Chapter 7) keep a Bloom filter per SSTable. A lookup skips every file whose filter says “definitely not here”.

🕷️

Seen-URL checks

A web crawler checks billions of URLs; a false positive means skipping a page occasionally — acceptable (Chapter 30).

🛡️

Cache penetration

Put all valid keys in a Bloom filter in front of the cache, and requests for non-existent IDs never reach the database (Chapter 6).

🧰
Variants

Standard Bloom filters can't delete (clearing a bit might remove other items). Counting Bloom filters store small counters instead of bits. Cuckoo filters support deletion with better space at low error rates. Scalable Bloom filters chain new filters as n grows beyond the planned size.

Count-min sketch & heavy hitters

A count-min sketch is a small grid of counters: d rows, each with its own hash function, and w columns. Adding an item increments one counter per row. Estimating its count takes the minimum of its d counters — collisions only ever add to a counter, so the minimum is the least-polluted estimate. It never undercounts.

HyperLogLog: counting distinct items

Flip coins until you get heads. If someone tells you their longest run of tails was 10, they probably flipped many times (~2¹⁰). HyperLogLog applies this to hashes: hash each item, and track the maximum number of leading zeros seen. Rare patterns imply many distinct items. Duplicates hash the same, so they don't change anything.

One observation is noisy, so HLL splits hashes into m buckets (registers) using the first bits, tracks the max per bucket, and combines them with a harmonic mean. Standard error ≈ 1.04 / √m.

Merkle trees: finding differences fast

Two replicas each hold a billion keys. Which keys differ? Comparing every key over the network is hopeless. A Merkle tree hashes data in blocks, then hashes pairs of hashes up to a single root. If roots match, the replicas are identical. If not, descend only into branches whose hashes differ — O(log n) comparisons to find each difference.

Gossip protocols

How does a 5,000-node cluster learn that a node joined, a schema changed, or a node died — without a central coordinator that could fail? Gossip: every second, each node picks a few random peers and exchanges what it knows. Like a rumour in a school, information reaches everyone in about O(log N) rounds, and it keeps spreading even if many nodes or messages are lost.

Failure detection

In an asynchronous network you can never be sure a node is dead rather than slow (Chapter 13). Failure detectors make a practical guess, trading detection speed against false alarms.

💓

Heartbeats + timeout

Each node pings periodically; missing heartbeats for T seconds = dead. Simple, but one fixed T is too aggressive on a congested network and too slow on a quiet one.

📈

Phi accrual

Instead of dead/alive, output a suspicion level φ based on the observed distribution of heartbeat intervals. If heartbeats normally arrive every 1s ± 50ms, a 3s gap is extreme. Applications pick a φ threshold. Used by Cassandra and Akka.

🏊

SWIM

Probe a random member each round; if it doesn't answer, ask k other members to probe it indirectly, avoiding false positives from one bad link. Suspicions and deaths spread by gossip piggybacked on probes. Used by Consul, Nomad, memberlist.

SWIM: is node B really dead?Step-through
  1. This protocol period, A randomly picks B and sends ping, expecting an ack within ~200ms.
  2. Nothing comes back. But maybe only the A↔B link is congested — declaring B dead now could trigger an unnecessary, expensive data rebalance.
  3. A asks k = 2 random members (C and D) to ping-req B on its behalf. If any of them gets an ack, it's relayed back to A and B is fine.
  4. No indirect acks either. B is marked suspect (not dead yet), and the suspicion is piggybacked on normal gossip messages.
  5. If B is alive and hears it's suspected, it gossips an alive message with a higher incarnation number, overriding the suspicion. If the suspicion timeout expires with no refutation, B is declared dead and everyone learns within a few gossip rounds.

⚠️
Common mistakes
  • Using a Bloom filter where a false positive is unacceptable. It's a filter in front of the truth, not the truth.
  • Summing distinct counts. Unique users per day is not the sum of unique users per hour — use mergeable sketches.
  • Forgetting to size for growth. A Bloom filter built for 10M items degrades badly at 100M; plan capacity or use a scalable variant.

Interview drill

Choose: Which structure for: “has this URL been crawled?”, “top 10 hashtags”, “how many unique viewers?”

How a strong answer sounds
Bloom filter for seen-URLs — false positives just skip a page, and 10 bits per URL beats storing the strings. Count-min sketch plus a small heap for top-K — it never undercounts, so heavy hitters stay accurate while rare items are noisy. HyperLogLog for unique viewers — ~12 KB per counter, 1% error, and it merges across shards and time windows, which exact sets cannot.

Explain: Two replicas hold a billion keys. How do you find what differs without shipping everything?

How a strong answer sounds
Exchange Merkle trees: hash keys in ranges, then hash pairs of hashes up to a root. Matching roots mean identical data — one comparison. Otherwise descend only into branches whose hashes differ, so a single differing key is found in about 30 comparisons. This is exactly what Cassandra-style anti-entropy repair does, complementing read repair (which only fixes data someone happens to read).

🧠 Key takeaways

  • Probabilistic structures trade small, bounded error for enormous memory savings — and most are mergeable.
  • Bloom filters answer “definitely not” or “probably yes” in ~10 bits per item; they can't delete.
  • Count-min sketches never undercount; combine with a heap for heavy hitters and trending lists.
  • HyperLogLog estimates distinct counts of billions in kilobytes with ~1% error.
  • Merkle trees locate differences between replicas in O(log n) hash comparisons.
  • Gossip spreads state through a cluster in O(log N) rounds and tolerates loss and failures.
  • Failure detectors trade speed for accuracy; phi accrual adapts to network conditions, SWIM uses indirect probes.

Check your understanding

A Bloom filter says an item is not present. How confident can you be?

If any of the item's bits is 0, it was never added. Only “probably present” answers can be wrong.

Why does a count-min sketch take the minimum across rows?

Every counter for an item is ≥ its true count; the minimum is the tightest overestimate.

You need unique visitors per page per hour, rolled up into days and months, for 1M pages. Best tool?

HLLs are tiny and mergeable without double-counting visitors who appear in multiple hours.

Two replicas with 1 billion keys have a Merkle tree each. Roughly how many hash comparisons to locate a single differing key?

Descend from the root through only the mismatching branch: log₂(10⁹) ≈ 30 levels.

In SWIM, why ask other nodes to probe a non-responding node indirectly?

A single slow or broken link shouldn't evict a healthy node; indirect probes test other paths.
