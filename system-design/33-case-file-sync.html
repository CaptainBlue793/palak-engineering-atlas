Design Cloud File Sync

Dropbox, Google Drive, OneDrive, iCloud: a folder on your laptop that magically appears on your phone, your colleague's machine and the web. Three problems make this interesting. Bandwidth: don't re-upload a 2 GB file because one paragraph changed. Keeping the file list correct when millions of devices keep asking “what changed?”. And conflicts, when two people edit the same file while offline.

  • Split the system into three services: file details, file content and change alerts
  • Cut files into chunks whose boundaries follow the content, and store each chunk once
  • Sync only what changed, in both directions
  • Detect and resolve conflicts
  • Handle sharing, version history, cleaning up unused data, and security

Two facts shape the whole design:

  • Checking for changes happens far more often than moving files. Most sync traffic is just “has anything changed?”, so that question must be almost free to answer.
  • Most changed files are small edits inside large files. So sending only the changed pieces saves a huge amount of bandwidth and storage.

Where the numbers come from:

  • Storage: 500M users × 10 GB = 5 billion GB = 5 EB. Many users hold the same files (the same installer, the same shared PDF, old versions that barely differ), so storing each identical chunk once saves ~40%, leaving ~3 EB.
  • Changes: 10B a day ÷ 86,400 s ≈ 116K commits a second on average, more at peak working hours. Every one is a small database transaction, which is why the metadata must be sharded.
  • Why not just poll? If 300M devices asked “anything new?” every 30 seconds, that is 300M ÷ 30 = 10M requests a second, and almost all of them answer “no”. Holding an open connection instead costs only memory. At ~100K idle connections per server, 300M connections need ~3,000 servers that do almost nothing until a change arrives.
  • Bandwidth saved: editing one slide in a 200 MB presentation with 4 MB chunks means sending 1–2 chunks, 4–8 MB, instead of 200 MB, a 25–50× saving.
STEP 3 / 6

Architecture: split metadata from content

Why split the system three ways instead of storing files in one database? Because the three kinds of data behave completely differently. Metadata is small (a few hundred bytes per file) but must be exact and changed in transactions. Content is enormous (exabytes) but never edited in place, which suits cheap object storage. Notifications are neither: they're short-lived messages to connected devices. Putting 3 EB of file bytes into a relational database would make backups, replication and scaling impossible, while putting the file tree into object storage would lose transactions.

🗂️

Metadata service

This is the official record of the file tree: paths, sizes, versions, which chunks make up each file, permissions, and a change journal (an ordered log of what changed) per user. It's a relational database, always exact, split into shards by user or shared folder.

🧱

Block service + object storage

Chunks never change once written, and each one is named by a hash of its own bytes. So two identical chunks get the same name and are stored only once. Clients upload and download blocks directly using temporary signed links (Chapter 9).

📡

Notification service

Connections that stay open (WebSocket or long polling) tell each device “something in your folder changed, come and fetch it”. The messages are deliberately tiny. The device then asks the metadata service for the real details.

🧠
Why content-addressed chunks change everything

When the name is the hash of the content, four things follow:

  • Uploading the same chunk twice does nothing extra, so retries are safe.
  • Identical data is stored once, across all versions and all users.
  • You can check nothing was corrupted: hash the bytes again and compare.
  • Blocks never change, so caches never need clearing.

A version is then just a list of chunk hashes. That makes keeping version history almost free.

STEP 4 / 6

Deep dive: chunking & delta sync

Say you edit one sentence in the middle of a document. With fixed-size chunks (cut every 4 MB, say), adding a few characters pushes every later byte along. Every chunk after the edit now holds different bytes, gets a new hash, and has to be uploaded again.

Content-defined chunking (CDC) fixes this. Instead of cutting at fixed positions, it cuts wherever a hash of the last few bytes matches a pattern. The boundaries move with the content, so only the edited chunk changes.

How it works in practice: slide a small window (say 48 bytes) across the file one byte at a time, and compute a rolling hash of the window, a hash that can be updated cheaply as one byte enters and one leaves. Cut a chunk whenever the lowest 22 bits of that hash are all zero. That happens by chance about once every 222 bytes, so chunks average ~4 MB. The key point: whether a position is a boundary depends only on the 48 bytes right before it. Insert a sentence, and once the window has moved past the new text it sees exactly the same bytes as before, so it finds exactly the same boundaries. Only the chunk containing the edit changes.

Two edge cases need limits. A file full of identical bytes (say, zeros) may never produce a boundary, so there's a maximum chunk size that forces a cut. And unlucky data could produce boundaries every few bytes, so there's a minimum size too, often a quarter of the average.

The sync protocol

Laptop edits a file → phone sees itStep-through
  1. The client watches the folder using the operating system's file-watching API (FSEvents, inotify, ReadDirectoryChangesW). It waits for a pause so a burst of saves counts once, then re-chunks the file and compares the new chunk hashes with the ones it last synced.
  2. POST /commit_batch {path, base_version: 6, chunks:[a1,b2,z9,c3]}. The server answers “I already have a1, b2, c3, just send z9.” Because chunks are shared across all users, a chunk someone else uploaded may already be there.
  3. The client sends only the changed chunks, straight to block storage using a temporary signed link. The server checks each one's hash. For a 2 GB file with a small edit, that's a few megabytes instead of 2 GB.
  4. The metadata service checks in one step that base_version == current. This is optimistic concurrency: assume no one else changed it, and fail if they did. Then it writes v7 with the chunk list, and adds an entry to the user's change journal with a new cursor (a position marker). This is the moment the change becomes official.
  5. The journal entry sends a tiny message to every other device in the folder: “changes available”. Offline devices simply find out when they reconnect. The journal is the official record, not the push message.
  6. GET /delta?cursor=8341 returns every change since that position, plus a new position marker. Because the device tracks its own position (Chapter 3), it can be offline for a month and still get each change exactly once.
  7. The phone downloads only the chunks it doesn't have, rebuilds the file, checks the hashes, and saves it safely: write a temporary file first, then rename it. The phone now matches v7.

Why upload blocks first and commit last? The commit is the moment other devices can see the new version. If the order were reversed, the phone could fetch v7 and find that chunk z9 doesn't exist yet. Uploading first guarantees every chunk a version points to is already safely stored. The same order explains the failure cases:

  • The laptop crashes after uploading blocks but before committing. The server holds a few chunks that no version uses. Nothing is broken; garbage collection (Step 6) removes them later. When the laptop restarts, it re-chunks the file and the blocks are already there.
  • The commit times out and the laptop retries. The first attempt may have succeeded, so the retry now fails the version check (the server is already on v7). The server should notice that v7's chunk list is identical to what is being committed and simply reply “done”, instead of reporting a false conflict.
  • The push message is lost. Nothing is lost for good. The phone also asks for the delta when it reconnects and every few minutes, so it catches up from its cursor anyway.
  • The cursor is too old. If the journal has been trimmed past a device's cursor (say, after a year offline), the server replies “reset”. The device then compares its whole file list with the server's, a slow full resync, but correct.
STEP 5 / 6

Deep dive: conflicts

Two devices edit the same file while offline. Both later commit with base_version = 6. The first one wins. The second one's check fails, because the server is now on v7.

Now what? You usually can't merge two versions of a file automatically, since a PDF or a spreadsheet isn't plain text. So most sync products never quietly overwrite one with the other. They keep both and let a person decide.

A short trace. The server is on v6. Offline, the laptop saves chunks [a1, x5, c3] and the phone saves [a1, y8, c3]. The laptop reconnects first: base_version 6 == current 6, so it becomes v7. The phone reconnects: base_version 6 ≠ current 7, rejected. Its client downloads v7 as report.pdf, renames its own edit to a conflicted copy, and uploads that as a new file. Both edits survive.

Which resolution to choose depends on the data. For binary files (PDFs, images, spreadsheets), keep both copies. For small settings files where only the newest matters, “last writer wins” is acceptable. For text documents edited live by several people, merge automatically with OT or CRDTs (Chapter 34).

🔢

Detecting conflicts

Every commit says which version it started from. If that doesn't match the server's current version, someone else changed the file in the meantime. Compare the content hashes first: if both sides made the same edit, there's no real conflict.

🌳

Directory-level conflicts

Moves and deletes can conflict too. Device A moves /work to /archive/work while device B adds a file inside it. Track changes against permanent file IDs rather than paths. Otherwise renaming a folder looks like deleting and recreating everything inside it.

STEP 6 / 6

Deep dives & extensions

🧮

Metadata sharding

Split the data by namespace: one user's root folder, or one shared folder. Then all of that namespace's files, journal and locks sit on one shard, and a commit is a transaction on a single shard. A shared folder is one namespace that appears inside several users' trees. Rough size: 500M users × ~2,000 files × ~300 bytes per row is ~300 TB of metadata, which needs thousands of shards.

🗑️

Garbage collection

Blocks are shared between versions and users, so you can't just delete one. Count how many files still use each block (reference counting), or periodically scan all chunk lists and remove blocks nobody references. Wait a while before deleting, so restores and version history keep working. The wait also closes a race: the server may tell a client “I already have block b2” just as b2's last user deletes it. Without a grace period, the client would commit a version pointing at a block that has just vanished.

🕰️

Version history

A version is only a list of chunk hashes, so it's cheap to keep. Keep 30 days on free plans and longer for business ones. For files saved over and over, keep only every Nth version in between.

🔒

Security & dedupe

Sharing chunks across all users leaks information. Upload a chunk and see if it finishes instantly: that tells you someone else already has that file. Fixes: only share chunks within one user or folder, or make the client prove it really has the data. End-to-end encryption stops cross-user sharing completely, which is a real product trade-off.

📶

Client efficiency

Compress chunks before uploading. Limit how much bandwidth the client takes. Send many small files in one request. Copy directly between devices on the same local network. And offer selective sync or on-demand files: the folder shows placeholders that download only when you open them.

🧊

Storage tiering

Keep frequently used blocks on fast SSD storage and rarely used ones in cheap archive storage (Chapter 9). Dropbox famously moved off S3 to its own “Magic Pocket” storage at exabyte scale, to cut costs.

⚠️
Common mistakes
  • Hashing whole files. Then a one-byte edit re-uploads gigabytes. Cut files into content-defined chunks and hash each chunk.
  • Relying on push notifications to be correct. They only make sync faster. What actually guarantees it is the saved change journal plus each device's cursor.
  • Quietly picking a winner in a conflict. Binary files can't be merged. Keep both copies and let a person decide.
🎤
Interview drill

Design: Two devices and the web client all edit the same folder. How do you keep them consistent?

How a strong answer sounds
Each namespace has one metadata service that is always exact. It holds the file tree, the versions, and a change journal whose numbers only go up. A client commits with the version it started from, and gets back a new cursor. Other clients ask for everything after their own cursor, nudged by a tiny push message. The content sits in blocks that never change and are named by their hash, so transfers are deduplicated and verifiable. A conflict creates a conflicted copy instead of quietly overwriting.

Scale: A user has 2 million small files. What breaks and how do you fix it?

How a strong answer sounds
The cost is dominated by per-file work and by watching the filesystem: the first scan is slow, and every small change triggers more work. Fixes: send metadata operations in batches, merge bursts of file events with debouncing, pack tiny files into fewer blocks, and use selective sync or on-demand placeholders so most files aren't stored locally at all. Return the delta list one page at a time. The metadata store should also keep each namespace on one shard, so listing and moving files stay single transactions.

🧠 Key takeaways

  • Keep the always-exact file details separate from the content blocks, which never change and are named by their hash.
  • Content-defined chunking keeps an edit inside one chunk, so only that chunk is sent and stored.
  • Clients ask which blocks the server is missing, upload only those, then commit a new version, which fails if someone else got there first.
  • A change journal per folder, plus each device's cursor, means every change arrives exactly once and sync can resume any time. Push messages are only a hint.
  • Spot conflicts by the version a commit started from, and keep both copies instead of losing data. For live documents, use CRDTs or OT.
  • Shard the metadata by namespace. Count how many files use each block, so you can delete unused ones safely.
  • Sharing chunks across all users leaks information, and it doesn't work with end-to-end encryption.

Check your understanding

A user inserts one paragraph at the top of a 500 MB file. Why does fixed-size chunking re-upload nearly the whole file?

Fixed chunking cuts at fixed positions. Content-defined chunking cuts based on the content itself, so shifting the bytes only affects the chunks near the edit.

Why are blocks keyed by the hash of their content?

Naming data by its hash gives you all of those for free. That's why git, Docker, backup tools and file sync all do it.

A device has been offline for three weeks. How does it catch up correctly?

With the change journal and a saved cursor, the device catches up step by step and sees each change exactly once. Push messages only make it faster.

Two users edit the same spreadsheet offline and both commit with base version 6. What should happen?

Binary files can't be merged safely. Keeping both copies guarantees nothing is lost.

Why shard metadata by namespace rather than by file ID?

Sync work always happens within one namespace. Keeping it on one shard avoids transactions that span machines on the busiest path.
