Design Cloud File Sync

Dropbox, Google Drive, OneDrive, iCloud: a folder on your laptop that magically appears on your phone, your colleague's machine and the web. The interesting problems are bandwidth (don't re-upload a 2 GB file because one paragraph changed), metadata consistency (millions of devices asking “what changed?”), and conflicts (two people editing offline).

  • Split the system into metadata, block storage and notification services
  • Chunk files with content-defined boundaries and deduplicate
  • Sync only deltas, in both directions, efficiently
  • Detect and resolve conflicts
  • Handle sharing, versioning, garbage collection and security

Two observations drive the architecture. Metadata operations vastly outnumber content transfers — most sync traffic is “has anything changed?”, which must be nearly free. And most “changed” files are small edits to large files, so chunk-level deltas save enormous bandwidth and storage.

STEP 3 / 6

Architecture: split metadata from content

🗂️

Metadata service

The source of truth for the file tree: paths, sizes, versions, chunk lists, permissions, a per-user change journal. Relational and strongly consistent, sharded by user/namespace.

🧱

Block service + object storage

Immutable, content-addressed chunks: the key is the hash of the bytes. Identical chunks are stored once. Clients upload/download blocks directly with presigned URLs (Chapter 9).

📡

Notification service

Long-lived connections (WebSocket / long polling) telling devices “your namespace changed — come fetch the delta”. Deliberately tiny messages; the client then pulls authoritative state.

🧠
Why content-addressed chunks change everything

If the key is the hash, uploads are idempotent (re-uploading the same chunk is a no-op), dedupe is automatic across versions and users, integrity is verifiable (rehash and compare), and blocks are immutable — so they cache perfectly and never need invalidation. Versions become lists of chunk hashes, which makes version history almost free.

STEP 4 / 6

Deep dive: chunking & delta sync

You edit one sentence in the middle of a document. With fixed-size chunks, inserting a few characters shifts every following byte, so every subsequent chunk gets a new hash and must be re-uploaded. Content-defined chunking (CDC) places boundaries where a rolling hash of the last few bytes hits a pattern — so boundaries move with the content and only the edited chunk changes.

The sync protocol

Laptop edits a file → phone sees itStep-through
  1. The client watches the filesystem (FSEvents / inotify / ReadDirectoryChangesW), debounces rapid saves, and re-chunks the file. It compares the new chunk hashes with the ones it last synced.
  2. POST /commit_batch {path, base_version: 6, chunks:[a1,b2,z9,c3]}. The server replies “I already have a1, b2, c3 — send z9.” Cross-user dedupe means a chunk someone else uploaded may already exist.
  3. The client uploads just the changed chunk(s) directly to block storage with a presigned URL, verified by hash. For a 2 GB file with a small edit, that's a few megabytes.
  4. The metadata service atomically checks base_version == current (optimistic concurrency), writes v7 with the chunk list, and appends an entry to the user's change journal with a new cursor. This is the moment the change becomes real.
  5. The journal entry triggers a tiny push to every other device in the namespace: “changes available”. Devices that are offline simply pick it up on reconnect — the journal is the source of truth, not the push.
  6. GET /delta?cursor=8341 returns the list of changes since that cursor plus a new cursor. Cursor-based pulling (Chapter 3) means a device can be offline for a month and still catch up exactly once.
  7. The phone fetches only the chunks it lacks, reassembles the file, verifies hashes, and writes it atomically (write temp file → rename). Local state now matches v7.
STEP 5 / 6

Deep dive: conflicts

Two devices edit the same file while offline. Both eventually commit with base_version = 6. The first wins; the second's optimistic check fails. Now what? A file's bytes can't be merged automatically in general (a PDF isn't text), so most sync products never silently overwrite: they keep both.

🔢

Detecting conflicts

Every commit carries the base version (or a per-namespace vector). If it doesn't match the server's current version, there was a concurrent change. Comparing content hashes first avoids false conflicts when both sides made the same edit.

🌳

Directory-level conflicts

Moves and deletes conflict too: device A moves /work to /archive/work while device B adds a file inside it. Model the tree as operations on stable file IDs (not paths) so renames don't look like delete + create of every descendant.

STEP 6 / 6

Deep dives & extensions

🧮

Metadata sharding

Shard by namespace (a user's root or a shared folder) so all of a namespace's files, journal and locks live on one shard — commits stay a single-shard transaction. Shared folders are namespaces mounted into several users' trees.

🗑️

Garbage collection

Blocks are shared across versions and users, so deletion means reference counting (or periodic mark-and-sweep over chunk lists), with a grace period so restores and version history keep working.

🕰️

Version history

Versions are just chunk lists — cheap. Retain 30 days for free tiers, longer for business; prune intermediate versions of frequently saved files with a keep-every-N policy.

🔒

Security & dedupe

Naive global dedupe leaks information: “upload a chunk, was it instant?” reveals someone else has that file. Mitigations: dedupe per user/namespace, or require proof of possession. End-to-end encryption breaks cross-user dedupe entirely — a real product trade-off.

📶

Client efficiency

Compress chunks before upload, throttle bandwidth, batch small files into one request, sync over LAN between devices on the same network, and support selective sync / on-demand files (placeholders that download on open).

🧊

Storage tiering

Hot blocks on SSD-backed storage, cold ones in archive tiers (Chapter 9). Dropbox famously moved off S3 to its own “Magic Pocket” storage at exabyte scale for cost.

⚠️
Common mistakes
  • Hashing whole files. A one-byte edit then re-uploads gigabytes; chunk content-defined and hash chunks.
  • Trusting push notifications for correctness. They're a latency optimization; the durable change journal plus a cursor is what guarantees sync.
  • Silently resolving conflicts. Binary files can't be merged — keep both copies and let a human decide.
🎤
Interview drill

Design: Two devices and the web client all edit the same folder. How do you keep them consistent?

How a strong answer sounds
One strongly consistent metadata service per namespace holds the file tree, versions and a monotonically increasing change journal. Clients commit with the base version (optimistic concurrency) and receive a new cursor; other clients pull deltas from their cursor, triggered by a lightweight push. Content lives in immutable, content-addressed blocks, so transfers are deduplicated and verifiable. Conflicts produce a conflicted copy rather than a silent overwrite.

Scale: A user has 2 million small files. What breaks and how do you fix it?

How a strong answer sounds
Per-file metadata operations and filesystem watching dominate: the initial index is slow, and every change triggers work. Fixes: batch metadata operations, coalesce filesystem events with debouncing, pack tiny files into fewer blocks, use selective sync/on-demand placeholders so most files aren't materialized locally, and paginate the delta API. The metadata store must also keep namespace operations single-shard so listing and moves stay transactional.

🧠 Key takeaways

  • Separate strongly consistent metadata from immutable, content-addressed block storage.
  • Content-defined chunking keeps edits local so only changed chunks are transferred and stored.
  • Clients ask which blocks are missing, upload only those, then commit a new version with optimistic concurrency.
  • A per-namespace change journal plus cursors gives exactly-once, resumable delta sync; push notifications are only a hint.
  • Detect conflicts by base version and preserve both copies rather than losing data; use CRDTs/OT for live documents.
  • Shard metadata by namespace; reference-count blocks for safe garbage collection.
  • Global dedupe has privacy implications and conflicts with end-to-end encryption.

Check your understanding

A user inserts one paragraph at the top of a 500 MB file. Why does fixed-size chunking re-upload nearly the whole file?

Boundaries are at fixed offsets. Content-defined chunking anchors boundaries to content, so a shift affects only nearby chunks.

Why are blocks keyed by the hash of their content?

Content addressing gives all of those properties for free, which is why it appears in git, Docker, backups and file sync.

A device has been offline for three weeks. How does it catch up correctly?

The change journal plus a cursor makes catch-up incremental and exactly-once. Push is only a latency optimization.

Two users edit the same spreadsheet offline and both commit with base version 6. What should happen?

Binary files can't be merged safely. Preserving both copies guarantees no data loss.

Why shard metadata by namespace rather than by file ID?

Sync operations are namespace-scoped; co-locating them avoids distributed transactions on the hot path.
