Design a Metrics & Monitoring Platform

Prometheus, Datadog, Grafana Cloud, CloudWatch — the system that watches all the other systems. It has one unusual demand: it must stay up exactly when everything else is falling over. And it has to do that while taking in tens of millions of measurements a second from the very machines that are on fire.

  • Model each metric as a time series with labels attached
  • Keep cardinality (the number of distinct series) under control — it's what kills these systems
  • Squeeze each measurement into ~1.5 bytes using delta and XOR encoding
  • Answer queries using an index from labels to series, plus compressed blocks of values
  • Check alert rules without paging people for brief blips
  • Keep the monitoring system separate from what it monitors
📚
What you need before this chapter
  • Use inverted indexes to find labelled series.
  • Understand service targets, metrics and alerts.

STEP 1 / 6

Requirements

Define the behaviour for missing data before drawing dashboards. No sample is different from a measured zero. If an ingester drops a shard's data, an error-rate chart must not quietly report that shard as healthy. Mark incomplete query results, track collection freshness and give alert rules an explicit no-data or evaluation-error state.

🛠️ Functional

✓Ingest metrics from millions of hosts, containers and services
✓Query by metric name and labels, combining values over time and across groups
✓Dashboards, plus free-form digging when something looks odd
✓Alert rules checked continuously, with routing, grouping and silences
✓Keep old data, stored more coarsely over time; keep each team's data separate

📏 Non-functional

✓Independent of the systems it watches — it fails separately and deploys separately
✓Alert within ~30 s of a problem starting
✓99% of dashboard queries under 1 s, even across weeks of data
✓Under extreme load it may drop some data; it must never show wrong numbers
✓Cheap to run: this is overhead, not the product you sell
STEP 2 / 6

Estimate the scale

One million instances × 500 series gives 500 million active series. At one sample every 15 seconds, that is about 33.3 million samples/second and 2.88 trillion samples/day. Multiplying by 16 bytes gives 46.08 TB/day; at 1.4 bytes it is about 4.03 TB/day. These decimal totals exclude indexes, write-ahead logs, replicas and storage overhead.

Memory is a separate budget. At the simulator's illustrative 3 KB per active series, 500 million series need about 1.5 TB across ingesters. Doubling scrape frequency doubles sample traffic but does not double the number of series. Adding an unbounded label can increase both, which is why ingest-rate limits alone cannot prevent a memory incident.

Two numbers define this system.

  • Active series — how many distinct label combinations are currently being written. This decides memory and index size. It is the real measure of capacity.
  • Samples per second — how many measurements arrive. This decides ingest speed and storage, and it lives or dies on compression. Getting 10× better encoding is the difference between a workable product and an impossible one.
STEP 3 / 6

The data model

A counter rising from 100 to 145 over 15 seconds represents 45 ÷ 15 = 3 events/second. A later value of 5 may mean the process restarted; subtracting 145 from it would produce a meaningless negative request rate. Compute reset-aware rates per series before aggregating. A gauge needs a different rule: summing memory bytes across machines can be useful for total capacity, while finding an overloaded host needs a maximum or per-host view.

🔢

Counter

A number that only goes up: requests, errors, bytes. You almost always query it as a rate (how fast it's rising). The query engine must also cope with it resetting to zero when a process restarts.

📏

Gauge

A number that goes up and down: queue length, memory used, temperature. Combine gauges with average, min or max. Adding them up across hosts usually means nothing — the total memory number would be meaningless for “is any host in trouble?”.

📊

Histogram

A spread of values, such as latency, stored as counters per bucket (“under 10 ms”, “under 50 ms”, …). Because they're counts, you can add them across hosts first and work out percentiles afterwards. But each bucket is its own series, so a 12-bucket histogram costs 12× the cardinality. Chapter 20's t-digest is a smaller, sketch-based alternative.

Cardinality: the thing that kills these systems

The product of label counts is an upper bound when every combination occurs. Real labels may be related: a pod belongs to one service, not every service. Count observed combinations and the rate of new series, including short-lived pods. Removing a label at ingest can also merge formerly distinct series; aggregate them deliberately or reject the metric rather than overwriting competing values at the same timestamp.

The number of series is every label's distinct values multiplied together. With 40 services × 5 methods × 8 statuses, you have 1,600 series. Add one label with a million values and you have 1.6 billion.

So one careless label turns a healthy metric into a platform-wide incident. It's almost always user_id, a request ID, an email address, or a raw URL path.

STEP 4 / 6

Ingestion and storage

Hash a canonical label order together with the tenant ID so equivalent series reach the same owner and tenants remain separate. Define when a write is acknowledged: a local WAL survives a process crash, but not loss of its disk. Replicate acknowledged data if that failure must be tolerated. On replay, deduplicate repeated samples by series and timestamp and define a policy for conflicting values.

Compression relies on regularity. Timestamps 0, 15, 30 and 45 seconds have gaps 15, 15 and 15; changes between gaps are zero. A delayed sample at 61 seconds produces a gap of 16 and a change of one. Record that actual time rather than pretending the interval stayed perfect. Late or out-of-order samples need a bounded acceptance window and a visible rejection count.

From a scrape to a queryable blockStep-through
  1. With pull (Prometheus fetching /metrics from each target), you learn whether each target is healthy for free: one you can't reach is visibly down. It's also easy to run a second scraper as a backup. With push (agents, OTLP), short-lived jobs, serverless functions and machines behind NAT work better, because they reach out to you. Large platforms support both.
  2. Each sample is sent to an ingester chosen by hash(series labels). So every sample of one series lands on the same machine, next to its neighbours, which compresses far better. Consistent hashing (Chapter 8) means adding or removing ingesters moves only a small share of series.
  3. Each sample is written to a WAL (a crash-recovery log) and added to the in-memory head block. The last few hours are served straight from memory — and that's exactly the range dashboards and alerts ask for most.
  4. Inside a chunk, timestamps are stored as delta-of-delta: not the time, but the change in the gap between samples. With a steady 15-second interval, that change is zero and costs a bit or two. Values are XOR-encoded against the previous value, so a number that barely changes stores almost nothing (Facebook's Gorilla design). Typical result: ~1.3–1.5 bytes per sample instead of 16.
  5. Every two hours the head block is written out as a block that never changes: compressed chunks plus an index from labels to series. Later, blocks are merged into bigger ones — exactly like an LSM tree (Chapter 7).
  6. Blocks go to S3-style object storage (Chapter 9), which is cheap enough to keep them for years. Coarser copies (5-minute and 1-hour summaries) are generated too, so a dashboard showing a whole year doesn't have to read every raw sample.
  7. The query frontend splits a long time range into per-day pieces, caches the results, applies per-team limits, and asks both ingesters (for recent data) and store gateways (for older data), then merges what comes back.

Steady values compress best — a flat gauge, or a counter rising by a similar amount each time. XOR-ing two nearly identical numbers gives mostly zeros, which store in very few bits. Noisy, high-precision values compress worst. That's one reason not to store raw latency measurements as gauges.

STEP 5 / 6

Alerting without waking people up for nothing

With 15-second scrapes and 15-second rule evaluation, a new failure can wait nearly 30 seconds just to be observed and evaluated. A two-minute persistence requirement then intentionally delays firing by about two more minutes, before notification delivery. The 30-second target therefore applies to critical rules with suitable settings, not every rule in the platform. Persist pending state or define restart behaviour so evaluator restarts do not repeatedly reset the timer.

An alerting engine re-checks every rule on a loop — say every 15 seconds — against recent data. The checking itself is easy. The hard parts are not paging someone for a 20-second blip, and not sending 400 pages when a single rack dies.

🧺

Grouping & inhibition

One failing rack sets off 400 identical alerts. Group them by cluster or service and send one notification with a count. And suppress the follow-on alerts while a bigger parent alert like “cluster down” is already firing.

🔕

Silences & maintenance

Planned work shouldn't page anyone. Allow silences that match certain labels, but always with a time limit and a named owner. A silence that never expires is how real incidents get missed.

🐶

Dead man's switch

A rule that always fires, sent to an outside service that pages you if it ever stops arriving. Without it, a dead monitoring system looks exactly like a perfectly healthy platform: silence.

STEP 6 / 6

Deep dives

Do not average averages when rolling data up. If one interval has one request at 100 ms and another has nine requests at 10 ms, their mean latencies are 100 and 10 ms. Averaging those gives 55 ms; the combined mean is (100 + 90) ÷ 10 = 19 ms. Sum and count preserve this calculation. Histograms or mergeable sketches are needed for percentiles.

Test independence by breaking shared dependencies: identity, DNS, deployment control, networking and notification delivery. A second cluster with the same unavailable login service may still lock responders out. Reserve resources for alert evaluation and use an outside heartbeat receiver, then rehearse an outage in which dashboards themselves are unavailable.

🏝️

Independent failure domain

The monitoring platform must not depend on the systems it watches. Use a separate cluster and a separate cloud account, and ideally a different region and provider for delivering alerts. If your alerting needs your service discovery, your database and your CDN to be working, you'll be blind exactly when it matters.

🧬

HA by duplication + dedupe

Run two identical collection paths writing the same series, and drop the duplicates at query time, preferring whichever copy is more complete. That's simpler and tougher than trying to make one path perfectly reliable.

🧯

Overload behaviour

During a big incident, the volume of metrics spikes — retries, errors, restarts — at exactly the moment you need the data most. Protect ingest with per-team rate limits and clear rules about what to drop first. Keep queries cheap too: reject a query with no time limit rather than letting one dashboard take down the cluster.

🧾

Logs and traces alongside

Metrics cheaply answer “is something wrong, and how bad?” for every request. Traces (recorded for a sample of requests) answer “where is the time going inside this request?”. Logs answer “what exactly happened?”. Link them with exemplars and trace IDs, so clicking a spike on a graph takes you straight to a trace (Chapter 16).

📉

Downsampling & retention

Keep raw 15-second data for 15 days, 5-minute summaries for 90 days, and 1-hour summaries for 2 years. Store min, max, sum and count for each bucket, so most calculations still work on the summarised data. Percentiles don't — keep histograms if you need those.

👥

Multi-tenancy

Set firm per-team limits on active series, ingest rate, how many queries can run at once, and how far back a query may reach. Without them, one team's cardinality bug degrades monitoring for the whole company — the noisy-neighbour problem, with unusually high stakes.

And the alerting path runs in its own failure domain, with a dead man's switch.”

⚠️
Common mistakes
  • Putting identifiers in labels. A single user_id label can multiply active series by millions and take the platform down.
  • Running monitoring inside the system it monitors. You'll go blind exactly when it matters.
  • Alerting with no “for” duration. Every blip pages a human, and people quickly learn to ignore pages.
🎤
Interview drill

Design: A team wants per-customer latency dashboards for 50,000 customers. How do you say yes safely?

How a strong answer sounds
Not with a customer_id metric label — that's 50,000 times every other label combination. Better options: a label covering only the top N customers plus an “other” bucket; exemplars that link a metric to traces when you need to dig into one customer; or per-customer totals computed in a stream job and stored in an analytics (OLAP) table, where lots of distinct values are normal. The rule: metrics are for dimensions with a limited set of values. Anything unlimited belongs in logs, traces or an analytics store.

Operate: During a major incident, metric volume doubles and queries start timing out. What protects you?

How a strong answer sounds
Per-team ingest limits and clear rules about dropping samples, so the platform stays up — losing some data is acceptable, showing wrong data is not. Query limits that reject queries with no time bound or huge cardinality, instead of letting one dashboard eat the cluster. Separate priorities, so checking alert rules is never starved by people poking at dashboards. And a dead man's switch delivered by an outside service, to confirm the alerting path itself is still alive.

🧠 Key takeaways

  • A series is a metric name plus labels. The number of active series — not samples — is what decides capacity.
  • Cardinality is the main way these systems die. Never put unlimited identifiers in labels, and enforce limits as data arrives.
  • Route samples by a hash of the series labels, so each series' samples sit together and compress well.
  • Write-ahead log, plus an in-memory head block, plus unchanging 2-hour blocks in object storage — the LSM pattern.
  • Delta-of-delta timestamps and XOR-encoded values cut ~16 bytes per sample down to ~1.4.
  • Alert rules need a “for” duration, grouping and suppression to stay quiet. Burn-rate alerts beat plain thresholds.
  • Store older data more coarsely. Percentiles need histograms — you can't average percentiles together.
  • Run monitoring in its own failure domain, duplicated, with a dead man's switch.

Check your understanding

A team adds user_id as a label to a request-count metric with 2M daily users. What happens?

The number of series is every label's value count multiplied together. Per-user detail belongs in logs or sampled traces, not in metric labels.

Why does delta-of-delta encoding work so well for metric timestamps?

Because the interval is steady, the change in the gap is almost always zero, which takes barely any space. Values get a similar win from XOR encoding.

Your alert has for: 0 and pages whenever the error rate exceeds 1% for a single evaluation. What's the problem?

People who get too many pages start ignoring them, which is itself a reliability risk. Require the problem to last a while, and pick the duration based on how urgent and how noisy the signal is.

Why run the monitoring platform in a separate cluster/account/region from what it monitors?

If it shares anything with the systems it watches, you go blind during exactly the incidents you built it for. Add a dead man's switch delivered by an outside service.

You keep 1-hour rollups (min/max/sum/count) for 2 years. A dashboard asks for p99 latency over last year. What's the catch?

Averaging percentiles together gives a meaningless number. Keep bucketed histograms (or t-digest sketches, Chapter 20) if you need percentiles over long ranges.
