Design a Metrics & Monitoring Platform

Prometheus, Datadog, Grafana Cloud, CloudWatch — the system that watches all the other systems. It has a unique constraint: it must stay up precisely when everything else is falling over, and it must do so while ingesting tens of millions of samples a second from the very infrastructure that's on fire.

  • Model metrics as labelled time series
  • Control cardinality — the thing that kills these systems
  • Store samples in ~1.5 bytes each with delta and XOR encoding
  • Query with an inverted index plus columnar chunks
  • Evaluate alert rules without flapping
  • Keep the monitoring system independent of what it monitors
STEP 1 / 6

Requirements

🛠️ Functional

✓Ingest metrics from millions of hosts, containers and services
✓Query by metric name and labels, with aggregation over time and dimensions
✓Dashboards and ad-hoc exploration
✓Alert rules evaluated continuously, with routing, grouping and silences
✓Retention with downsampling; multi-tenant isolation

📏 Non-functional

✓Independent of the monitored systems — separate failure domain, separate deploy
✓Alert within ~30 s of a condition becoming true
✓Dashboard queries p99 < 1 s over weeks of data
✓Lossy under extreme load is acceptable; lying is not
✓Cost-efficient: this is infrastructure overhead, not product

🔢

Counter

Monotonically increasing (requests, errors, bytes). Always queried as a rate, and the query engine must handle resets when a process restarts.

📏

Gauge

Goes up and down (queue depth, memory, temperature). Aggregate with avg/min/max — summing gauges across hosts is usually meaningless.

📊

Histogram

Latency distributions as bucket counters, so percentiles can be computed after aggregation. Each bucket is a separate series — a 12-bucket histogram is 12× the cardinality (Chapter 20's t-digest is the sketch-based alternative).

Cardinality: the thing that kills these systems

Series count is the product of every label's distinct values. One thoughtless label turns a healthy metric into a platform incident — and it's almost always user_id, a request ID, an email, or a raw URL path.

STEP 4 / 6

Ingestion and storage

From a scrape to a queryable blockStep-through
  1. Pull (Prometheus scraping /metrics) gives you target health for free — a target that can't be scraped is visibly down — and makes it easy to run a second scraper for redundancy. Push (agents, OTLP) handles short-lived jobs, serverless and NAT'd networks better. Large platforms support both.
  2. Samples are routed by hash(series labels) to an ingester, so all samples of a series land together and compress well. Consistent hashing (Chapter 8) keeps reshuffling small when ingesters scale.
  3. Each sample is appended to a WAL and added to the in-memory head block. Recent data (hours) is served from memory — which is exactly what dashboards and alerts query most.
  4. Within a chunk, timestamps are stored as delta-of-delta (a 15-second scrape interval costs a bit or two) and float values are XOR-encoded against the previous value (Facebook's Gorilla). Typical result: ~1.3–1.5 bytes per sample versus 16 raw.
  5. Every two hours the head is flushed to an immutable block: compressed chunks plus an inverted index of labels → series. Blocks are later compacted into bigger ones, exactly like an LSM tree (Chapter 7).
  6. Blocks go to S3-style storage (Chapter 9), where they're cheap and infinitely retained. Downsampled copies (5-minute and 1-hour aggregates) are generated so long-range dashboards don't read raw data.
  7. The query frontend splits a range query by day, caches results, enforces per-tenant limits, and fans out to ingesters (recent) and store gateways (historical), merging the results.

Steady values (a flat gauge, a counter incrementing regularly) compress best — the XOR of consecutive floats is mostly zeros. Noisy, high-precision values compress worst, which is one reason to avoid storing raw latencies as gauges.

STEP 5 / 6

Alerting without waking people up for nothing

An alerting engine re-evaluates every rule on a loop (say every 15 s) over recent data. The subtlety isn't evaluation — it's not paging for a 20-second blip, and not sending 400 pages when one rack dies.

Longer isn't always better: for a total outage you want to know in seconds, so critical rules use short durations and noisy ones use long durations — or better, alert on a burn rate against the error budget (Chapter 16).
🧺

Grouping & inhibition

One failing rack produces 400 identical alerts. Group by cluster/service and send one notification with a count; inhibit dependent alerts when a parent alert (“cluster down”) is already firing.

🔕

Silences & maintenance

Planned work shouldn't page. Time-bounded silences matched by labels, always with an owner and an expiry — an eternal silence is how incidents get missed.

🐶

Dead man's switch

A rule that always fires, routed to an external service that pages you if it stops arriving. Without it, a dead monitoring system looks exactly like a perfectly healthy platform.

STEP 6 / 6

Deep dives

🏝️

Independent failure domain

The monitoring platform must not depend on the systems it watches: separate cluster, separate cloud account, ideally separate region and provider for the alert-delivery path. If your alerting needs your service discovery, your database and your CDN to work, you'll be blind exactly when it matters.

🧬

HA by duplication + dedupe

Run two identical scrapers/ingest paths writing the same series, and deduplicate at query time (prefer the replica with more complete data). It's simpler and more robust than trying to make one path perfectly reliable.

🧯

Overload behaviour

During a big incident, metric volume spikes (retries, errors, restarts) exactly when you need the data. Protect ingest with per-tenant rate limits and sample-drop policies, and make queries cheap: reject unbounded queries rather than letting one dashboard take the cluster down.

🧾

Logs and traces alongside

Metrics answer “is something wrong and how bad?” cheaply for every request. Traces (sampled) answer “where is the time going in this request?” and logs answer “what exactly happened?”. Link them with exemplars and trace IDs so a spike in a graph jumps straight to a trace (Chapter 16).

📉

Downsampling & retention

Raw at 15 s for 15 days, 5-minute aggregates for 90 days, 1-hour for 2 years. Store min/max/sum/count per bucket so most aggregations stay correct on rolled-up data (percentiles do not — keep histograms for those).

👥

Multi-tenancy

Hard per-tenant limits on active series, ingest rate, query concurrency and query range. Without them, one team's cardinality bug degrades monitoring for the entire company — the noisy-neighbour problem with unusually high stakes.

🎤
The line that shows you've operated one of these

“Active series is the capacity unit, so I'd enforce per-tenant series limits and drop high-cardinality labels at ingest; store recent data in memory with a WAL, flush 2-hour blocks to object storage with delta-of-delta and XOR compression, and run the alerting path in a separate failure domain with a dead man's switch.”

⚠️
Common mistakes
  • Putting identifiers in labels. One user_id label can multiply active series by millions and take down the platform.
  • Running monitoring inside the system it monitors. You'll go blind exactly when it matters.
  • Alerting without a “for” duration. Every blip pages a human, and people quickly learn to ignore pages.
🎤
Interview drill

Design: A team wants per-customer latency dashboards for 50,000 customers. How do you say yes safely?

How a strong answer sounds
Not with a customer_id metric label — that's 50,000 × every other label combination. Options: a bounded label for the top N customers plus an “other” bucket; exemplars linking metrics to traces for individual investigation; or per-customer aggregates computed in a stream job and stored in an OLAP table where high cardinality is normal. The rule is that metrics are for bounded dimensions; anything unbounded belongs in logs, traces or an analytics store.

Operate: During a major incident, metric volume doubles and queries start timing out. What protects you?

How a strong answer sounds
Per-tenant ingest limits and sample dropping so the platform stays up (lossy is acceptable, lying is not), query limits that reject unbounded range/cardinality queries rather than letting one dashboard consume the cluster, and prioritized paths so alert-rule evaluation is never starved by ad-hoc dashboards. A dead man's switch delivered by an external service confirms the alerting path itself is alive.

🧠 Key takeaways

  • A series is metric name + labels; active series — not samples — is the capacity unit.
  • Cardinality is the dominant failure mode: never put unbounded identifiers in labels, and enforce limits at ingest.
  • Shard by series hash so each series' samples compress together.
  • WAL + in-memory head block + immutable 2-hour blocks in object storage, LSM-style.
  • Delta-of-delta timestamps and XOR-encoded values cut ~16 bytes per sample to ~1.4.
  • Alert rules need a “for” duration, grouping and inhibition to avoid noise — and burn-rate alerts beat raw thresholds.
  • Downsample for long retention; percentiles need histograms, not averages of averages.
  • Run monitoring in an independent failure domain, duplicated, with a dead man's switch.

Check your understanding

A team adds user_id as a label to a request-count metric with 2M daily users. What happens?

Series = product of label cardinalities. Per-user detail belongs in logs or sampled traces, not metric labels.

Why does delta-of-delta encoding work so well for metric timestamps?

Regular intervals make second-order differences almost always zero; values then use XOR encoding for a similar win.

Your alert has for: 0 and pages whenever the error rate exceeds 1% for a single evaluation. What's the problem?

Alert fatigue is a reliability risk. Require the condition to persist, and tune the duration by how urgent and how noisy the signal is.

Why run the monitoring platform in a separate cluster/account/region from what it monitors?

Shared dependencies mean blindness during exactly the incidents you built it for. Add a dead man's switch delivered by a third party.

You keep 1-hour rollups (min/max/sum/count) for 2 years. A dashboard asks for p99 latency over last year. What's the catch?

Averaging percentiles is meaningless. Keep bucketed histograms (or t-digest sketches, Chapter 20) if you need long-range percentiles.
