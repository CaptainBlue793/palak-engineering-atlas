Load Balancing

As soon as you have more than one server, something has to decide which server handles each request. That “something” is a load balancer. It quietly becomes one of the most important parts of your system.

Why load balancers exist

A load balancer (LB) sits in front of a group of servers and shares incoming requests out among them. Clients only talk to one address. The LB hides how many servers are behind it.

Why not just give clients a list of server addresses and let them pick? You could, using DNS with several IPs (Chapter 2). But DNS answers are cached for minutes, so when a server dies, clients keep trying it. Clients can't see how busy each server is. And every time you add a server, you wait for caches to expire before anyone uses it. A load balancer fixes all three because it decides per request, with up-to-date knowledge of which servers are healthy.

A sized example. Peak traffic is 6,000 requests per second, and one app server comfortably handles 1,500 (keeping it around 70% busy). So you need 6,000 ÷ 1,500 = 4 servers, plus one spare in case one dies: 5 in total. The LB spreads the traffic at about 1,200 per server. If one server fails, the other four take 1,500 each, which they can still handle. Without the LB, you would have to tell every client about all five servers and hope they spread themselves out evenly.

🛒
Analogy: the supermarket checkout manager

Customers line up at one entrance. A manager points each one to a free till. If a cashier goes on break, the manager stops sending people there. If lines get long, a new till opens. Customers never need to know how many tills there are.

A short trace: round robin vs least connections

Two servers, A and B. Four requests arrive close together: a 10-second report (heavy), a quick 10 ms page, another heavy report, another quick page.

  • Round robin just alternates: A, B, A, B. Both heavy reports land on A, so A is busy with two long jobs while B finishes its two quick pages and then sits idle.
  • Least connections sends each request to whichever server has fewer requests open right now. Report 1 goes to A (A has 1 open). The quick page goes to B and finishes almost at once (B back to 0). Report 2 goes to B, because A still has 1 open and B has 0. Now each server holds one report, and the work is even.

Round robin only counts requests. Least connections sees how many are still running, which is a rough measure of how much work each server has.

Why plain hashing breaks when servers change

IP hash turns the client's IP into a number (the hash) and picks hash % N, the remainder after dividing by the number of servers. With 4 servers, a client whose hash is 7 goes to server 7 % 4 = 3. Remove one server, and the same client now goes to 7 % 3 = 1. That happens to almost everyone: of 12 clients with hashes 0 to 11, only the ones with hashes 0, 1 and 2 keep their server. The other 9 (75%) move, and every warm cache that depended on “same user, same server” is lost at once. Consistent hashing (Chapter 8) arranges things so that only about 1 in N clients move.

Layer 4 vs Layer 7 load balancing

Remember the network layers from Chapter 2? Load balancers work at one of two levels. The difference is how much of the request they can see.

📦 Layer 4 (transport)

src 203.0.113.9:51544
dst 93.184.216.34:443
proto TCP
GET /api/orders HTTP/1.1
Cookie: session=abc

Sees only IP addresses and ports — like reading the outside of an envelope. It passes the raw TCP/UDP traffic along. Extremely fast, works with any protocol, but can't route by URL. e.g. AWS NLB, LVS

✉️ Layer 7 (application)

GET /api/orders HTTP/1.1
Host: shop.com
Cookie: session=abc
X-Beta-User: true

Opens the letter: sees the URL, headers and cookies. This allows smart routing (e.g. by URL), TLS termination, retries and compression. It uses more CPU per request. e.g. NGINX, Envoy, HAProxy, AWS ALB

Why can an L7 balancer see so much more? Because it ends the client's connection itself. There are really two connections: client to LB, and LB to server. The LB decrypts the TLS, reads the whole HTTP request, picks a server, and sends the request on in a fresh connection. That is what makes URL routing, retries and header rules possible. It is also why L7 costs more CPU and adds a little delay. An L4 balancer usually just forwards packets, so the TLS stays encrypted all the way to the server and the LB never sees inside.

When to pick which: pick L7 for normal web and API traffic, where you want routing by path, TLS in one place and good logs. Pick L4 for non-HTTP protocols (database connections, game servers, custom TCP), for extremely high packet rates, or when the server must receive the encrypted traffic untouched.

Health checks

A load balancer is only useful if it knows which servers are alive. You saw this in the simulator: without health checks, the LB keeps sending traffic into a black hole.

🩺 Active checks

The LB checks each server on a timer, e.g. GET /health every 5s. After N failures in a row (e.g. 3), the server is marked unhealthy. After M successes, it's added back. A good /health endpoint also checks the things the server can't work without. But don't check too deeply: one slow database shouldn't mark every server dead at once.

👀 Passive checks

The LB watches real traffic. If a server returns lots of 5xx errors or timeouts, it's removed for a while (Envoy calls this “outlier detection”). It reacts faster to real failures, but only notices when there is traffic.

Why use both? Do the maths on active checks alone. With a check every 5 seconds and 3 failures needed, a dead server can keep receiving traffic for up to about 15 seconds. If the site serves 4,000 requests per second across 4 servers, that server gets 1,000 per second, so roughly 15,000 requests fail before the LB notices. Passive checks catch the problem after a handful of real errors instead. Checking more often shortens the window, but too-sensitive checks cause flapping: a server that is slow for a moment gets removed and re-added over and over.

Many systems split the health check in two. A liveness check asks “is the program running at all?” (if not, restart it). A readiness check asks “should this server get traffic right now?” A server that is still starting up, or is shutting down for a deploy, is alive but not ready.

Sticky sessions

Session affinity (sticky sessions) makes the LB send a given user to the same server every time. It usually does this with a cookie that the LB sets.

When it helps
  • Older apps that keep sessions in server memory
  • Each server's cache already holds that user's data (a “warm” cache)
  • WebSockets and other connections that stay open a long time
Why to avoid it
  • Uneven load (a few heavy users pile onto one server)
  • If the server dies, its users lose their session anyway
  • Harder to remove servers or roll out new versions
✅

Better: keep app servers stateless (Chapter 4), and store sessions in Redis or in signed tokens. Then you don't need stickiness at all.

Who balances the load balancer?

If all traffic goes through one LB, the LB is now your single point of failure: if it dies, everything stops. The classic fix is a pair of LBs sharing one virtual IP (VIP) — an address that can move from one machine to another.

Active–passive failover with a floating IPStep-through
  1. Clients send traffic to the virtual IP 10.0.0.100. LB-1 currently holds that address and passes traffic on to the servers.
  2. LB-1 and LB-2 send each other a “heartbeat” (an “I'm alive” message) every second, e.g. using VRRP via keepalived. LB-2 stays ready with the exact same settings.
  3. LB-1's hardware fails. Its heartbeats stop arriving. LB-2 waits for a few missed beats first, so a single delayed message doesn't cause a false alarm.
  4. LB-2 claims 10.0.0.100 and tells the local network “this address is now mine” (a gratuitous ARP message). Clients don't change anything — the address is the same.
  5. Within a couple of seconds, traffic flows through LB-2. In the cloud, managed LBs (ALB, Cloud Load Balancing) do all this for you across several zones (separate data centers).

Edge case: split brain. What if LB-1 is fine, but the link carrying the heartbeats breaks? LB-2 hears nothing, assumes LB-1 is dead, and claims the VIP too. Now two machines both think they own the same address, and traffic goes to whichever one the network happens to pick. Real setups guard against this with more than one heartbeat path, and some add a tie-breaker, such as a third machine that must agree before a takeover, so only one side can hold the address. It is the same “who is in charge?” problem that databases face with leader election (Chapter 13).

🌍
Going global

With several regions, balancing starts at the DNS or network edge. GeoDNS returns the IP of the nearest region. Anycast announces the same IP from many locations, so the internet's routing sends each user to the closest one. Then L7 load balancers in each region take over.

⚠️
Common mistakes
  • Round robin when some requests are much heavier than others. Slow requests can pile up on a server that's already struggling. Least connections, or balancing by response time, handles this better.
  • Health checks that only test that the program is running. A server that has run out of database connections will happily return 200 on /health while failing every real request.
  • Using sticky sessions instead of shared state. It works until a server dies, a new version is deployed, or traffic is uneven. Then you lose sessions and can't balance the load.

Interview drill

Design: How do you take a server out of rotation for a deploy without dropping requests?

How a strong answer sounds
First make the server fail its readiness check, so the balancer stops sending it new requests. Keep serving the requests already in progress. Wait a few seconds for the balancer to notice. Then let open connections finish (“draining”), with a time limit, before shutting down. For long-lived connections, tell clients to reconnect — with backoff and a bit of random delay (jitter) so they don't all reconnect at once.

Trade-off: L4 or L7 load balancing for a new public API?

How a strong answer sounds
L7. You'll want routing by path, TLS termination, rate limits per route, retries, header-based canary routing (sending a few users to a new version) and request logging. All of these need the LB to see the request. L4 is the right answer when you need maximum raw speed, use non-HTTP protocols, or want encryption to stay unbroken all the way to the server. Many systems use both: L4 anycast in front of L7 proxies.

🧠 Key takeaways

  • Load balancers spread traffic, hide how many servers there are, and route around failures.
  • L4 is fast and sees only IP and port. L7 sees the HTTP request, so it can route by content (URL, headers).
  • Round robin is fine when all requests cost about the same. Least connections handles requests of different cost. Hashing keeps a user on the same server.
  • Without health checks, a dead server silently swallows requests.
  • Prefer stateless servers over sticky sessions.
  • Give the LB a backup too (an active–passive pair with a VIP, or a managed LB that spans several zones).

Check your understanding

Requests vary from 5ms to 30s (report generation). Which algorithm spreads load most fairly?

Round robin counts requests, not how much work they are. Least connections sends new requests to servers that aren't still busy with long ones.

You want /api/* to go to API servers and /images/* to a static file cluster. What do you need?

Routing by URL path means reading the HTTP request, and only L7 can see it.

A server crashes but the LB keeps sending it ~25% of requests, which all fail. What's missing?

Health checks detect the dead server and remove it from the pool.

With simple hash(ip) % N routing, what happens when one of 4 servers is removed?

Changing N changes the result of almost every “% N” (remainder) calculation. Consistent hashing (Chapter 8) means only about 1/N of the keys move.

How do you stop the load balancer being a single point of failure?

A spare LB plus automatic handover of the shared address means clients never need to know which LB is active.
