HTTP, REST & JSON

HTTP is the language that web browsers, mobile apps and backend services use to talk to each other. It's plain, structured text: a request says what you want, a response says what happened and carries the data. Once you can read one HTTP exchange, you can read them all. This chapter teaches you to read them fluently, to design clean REST-style URLs, and to read and write JSON, the data format almost every API uses.

  • Read an HTTP request and response and name every part
  • Choose the right method, and explain which methods are safe to retry
  • Interpret status codes by family: 2xx, 3xx, 4xx and 5xx
  • Recognise the most important headers, including cookies and caching headers
  • Design REST-style URLs for a small API
  • Read and write JSON, and know its six value types

What HTTP is

HTTP (HyperText Transfer Protocol) is a set of rules for request–response conversations over a network connection. It was invented for fetching web pages, but today it carries nearly everything: API calls between mobile apps and backends, traffic between services inside a company, file uploads, even video segments.

Its great strength is that it's simple and universal. Every programming language has an HTTP library, every firewall understands it, and every tool from browsers to curl can speak it. When two teams need their systems to talk, HTTP is usually the default choice.

VersionWhat changedWhy you care
HTTP/1.1 (1997)Plain text messages; one request at a time per connection; keep-alive reuses connections.The format you'll read in this chapter. Still everywhere.
HTTP/2 (2015)Binary framing; many requests share one connection at the same time (multiplexing); compressed headers.Faster pages with many small files. Used heavily between services (gRPC runs on it).
HTTP/3 (2022)Runs over QUIC, built on UDP, with TLS built in; a lost packet only delays its own stream.Faster setup and better behaviour on lossy mobile networks.

The good news: the meaning of a request — method, path, headers, body, status code — is identical in all three versions. Only the way bytes are packed on the wire changed. Learn the meaning once and it applies everywhere.

Anatomy of a request and a response

Here is a client asking an API for user 42, and the server's answer. Read it top to bottom — every part is explained below.

# ---- the request (client → server) ----
GET /api/users/42 HTTP/1.1          ← method, path, version
Host: api.shop.com                  ← which website
Accept: application/json            ← “please answer in JSON”
Authorization: Bearer eyJhbGciOi...  ← who I am (a login token)
                                     ← blank line: headers end here (GET has no body)
# ---- the response (server → client) ----
HTTP/1.1 200 OK                      ← status code: it worked
Content-Type: application/json      ← the body is JSON
Content-Length: 94                  ← the body is 94 bytes
Cache-Control: max-age=60           ← you may reuse this for 60 s

{"id":42,"name":"Ada Lovelace","email":"ada@example.com","plan":"pro","tags":["admin","beta"]}
🎯

Method

The verb: what you want to do. GET reads, POST creates, and so on.

🛣️

Path

Which thing (resource) you mean: /api/users/42. It can end with a query string of options: ?page=2&limit=20.

🏷️

Headers

Name: value lines carrying extra information: the content type, a login token, caching rules and more.

📦

Body

The actual data, after a blank line. A GET request has none; a response usually does. Most often it's JSON.

The response has the same shape with one difference: its first line is a status line — the version, a three-digit status code and a short reason phrase, like 200 OK or 404 Not Found.

A full URL packs several of these pieces together. Take https://api.shop.com:443/api/users?page=2&limit=20: https is the scheme (HTTP over TLS), api.shop.com the host (looked up with DNS), 443 the port (usually left out, since it's the default for HTTPS), /api/users the path, and page=2&limit=20 the query string.

Methods: what you want to do

MethodMeaningExampleHas a body?Safe?Idempotent?
GETReadGET /users/42NoYesYes
POSTCreate, or do an actionPOST /usersYesNoNo
PUTReplace all of itPUT /users/42YesNoYes
PATCHChange part of itPATCH /users/42YesNoDepends
DELETERemoveDELETE /users/42Usually noNoYes

The last two columns are the reason methods matter in system design:

  • Safe means the request doesn't change anything on the server. Safe requests can be cached, prefetched and repeated freely.
  • Idempotent means doing it twice has the same effect as doing it once. DELETE /users/42 twice still leaves user 42 deleted. PUT with the same body twice leaves the same final state. But POST /orders twice creates two orders.

Why care? Because networks fail in an awkward way: a client can send a request, the server can do the work, and the response can be lost. The client doesn't know whether it worked. For idempotent requests, the fix is easy — just retry. For POST, a blind retry might charge a customer twice. Systems handle this with idempotency keys: the client attaches a unique ID to the request, and the server remembers which IDs it has already processed. You'll see this in Chapter 3 and, with real money, in Chapter 37.

Status codes: what happened

The status code is a three-digit number whose first digit tells you the family. Learn the families first; the individual codes follow naturally.

FamilyMeansCodes you'll meet all the time
2xxSuccess200 OK · 201 Created (after a POST) · 204 No Content (success, empty body)
3xxLook elsewhere301 Moved Permanently · 302 Found (temporary redirect) · 304 Not Modified (your cached copy is still good)
4xxThe client's mistake400 Bad Request · 401 Unauthorized (not logged in) · 403 Forbidden (logged in, not allowed) · 404 Not Found · 409 Conflict · 429 Too Many Requests
5xxThe server's problem500 Internal Server Error (a bug) · 502 Bad Gateway · 503 Service Unavailable (overloaded or down) · 504 Gateway Timeout
🔁
The retry rule

4xx means “you, the client, must change something” — retrying the exact same request won't help (except 429, which says “slow down and try later”). 5xx means “we, the server, had a problem” — retrying later might work, ideally with growing waits between attempts. This one rule drives how well-behaved clients handle errors (Chapter 16).

The difference between 502 and 504 is worth knowing. Both come from a server that sits in front of another one, such as a load balancer or gateway. 502 means the server behind it sent back something broken or refused the connection; 504 means it didn't answer in time. Both point at the service behind the one that replied.

Headers you'll meet

Headers carry everything that isn't the data itself. There are dozens, but these few come up constantly in system design:

HeaderDirectionWhat it does
HostrequestWhich website you want. One server can host many sites on one IP address.
Content-TypebothThe format of the body, e.g. application/json, text/html, image/png.
AuthorizationrequestProof of who you are, usually a token: Bearer eyJ….
Cookie / Set-Cookierequest / responseThe server sets a cookie once; the browser sends it back on every later request to that site.
Cache-ControlresponseWho may cache this and for how long: max-age=3600, no-store, private.
ETag / If-None-Matchresponse / requestA version tag for the content. The client asks “changed since this version?” and gets a tiny 304 if not.
LocationresponseWhere to go next — the target of a redirect, or the URL of a newly created resource.
Retry-AfterresponseWith 429 or 503: how long to wait before trying again.

Cookies vs tokens

HTTP is stateless: every request must carry what the server needs to know who you are. There are two common ways:

🍪 Session cookie

The server stores a session record (“session 8f3a… = user 42”) in a shared store and gives the browser a cookie holding just the random ID. Easy to revoke: delete the record. Needs a lookup on every request. Common for websites.

🎫 Bearer token (often a JWT)

The server gives the client a signed token that itself says “user 42, expires at 10:30”. Any server can check the signature without a lookup. Harder to revoke before it expires. Common for mobile apps and APIs.

Both are covered properly, with their security trade-offs, in Chapter 11.

REST: a style for designing URLs

An API is a set of URLs a program can call. REST (Representational State Transfer) is the most popular way to lay one out. The core idea: URLs name things (nouns), and the HTTP method says what to do with them (the verb).

Instead of…REST styleWhy
GET /getUser?id=42GET /users/42The method already says “get”.
POST /deleteUser?id=42DELETE /users/42Clients, caches and proxies understand DELETE is idempotent.
GET /user/42/order-listGET /users/42/ordersCollections are plural; nesting shows ownership.
GET /orders?action=cancel&id=7POST /orders/7/cancelA GET must never change data; actions that don't fit CRUD become POST sub-resources.

A few more conventions you'll see everywhere:

  • Query strings for filtering, sorting and paging: GET /orders?status=shipped&sort=-created&limit=20. A list endpoint should never return “everything” — it returns a page plus a way to get the next one. Chapter 3 compares paging methods.
  • Versioning: /v1/users or a header, so you can change the API without breaking old apps still in people's pockets.
  • Status codes that tell the truth: 201 plus a Location header after creating, 404 for a missing item, 400 with a helpful error body for bad input.

REST isn't the only style. GraphQL lets the client ask for exactly the fields it wants in one request; gRPC uses compact binary messages and is popular between internal services. Chapter 3 weighs them up.

JSON: the data format

  
JSON (JavaScript Object Notation) is plain text that describes structured data. Despite the name, every language reads and writes it. It has only six kinds of value, which is exactly why it's so portable:

  

    

      
TypeLooks likeNotes

      
        
object{"name": "Ada", "age": 36}Key–value pairs. Keys are always strings in double quotes.

        
array["admin", "beta"]An ordered list, of any mix of values.

        
string"hello"Double quotes only — single quotes are not valid JSON.

        
number42, 3.14, -7e3No separate integer type. Very large integers may lose precision in some languages, so big IDs are often sent as strings.

        
booleantrue, falseLowercase.

        
nullnull“No value”.

      
    

  

  
Objects and arrays can be nested to any depth, which is how JSON describes real things. Here is one order:


{
  "id": "ord_7Hq2",
  "customer": { "id": 42, "name": "Ada" },
  "items": [
    { "sku": "MUG-01", "qty": 2, "price_cents": 1299 },
    { "sku": "TEE-M",  "qty": 1, "price_cents": 2500 }
  ],
  "paid": true,
  "coupon": null,
  "created_at": "2026-09-25T14:03:00Z"
}

  
Notice two habits of good API design in that example. Money is stored as whole cents (1299), not as 12.99, because decimal fractions can't be represented exactly in binary floating point. And dates are strings in the standard ISO 8601 format with a time zone (Z means UTC), because JSON has no date type.

  
📏
JSON's cost
JSON is readable but wordy: every object repeats its key names, and numbers are stored as text. That's fine for most APIs. For very high-volume internal traffic, teams switch to compact binary formats such as Protocol Buffers, which can be several times smaller and faster to parse. Compression (gzip, br) also shrinks JSON a lot in transit.

⚠️
Common mistakes

    
    
      
  • Changing data with GET. Caches, browsers and link previewers call GET URLs freely. A “delete” behind a GET will eventually fire by accident.
    • 
      
  • Blindly retrying POST. If the response was lost, the first attempt may have worked. Use idempotency keys.
    • 
      
  • Returning 200 with an error message in the body. Clients, monitoring and retries all rely on the status code telling the truth.
    • 
      
  • Confusing 401 and 403. 401: we don't know who you are. 403: we know, and you're not allowed.
    • 
      
  • Storing money as floating-point numbers. Use integer cents (or a decimal type) to avoid rounding errors.
    •

Interview drill

    
Design: Sketch REST endpoints for a simple blog with posts and comments.

    
How a strong answer sounds
GET /posts?limit=20&cursor=… to list posts a page at a time; POST /posts to create (returns 201 and a Location header); GET /posts/{id}, PATCH /posts/{id}, DELETE /posts/{id}; comments nested as GET /posts/{id}/comments and POST /posts/{id}/comments. Authentication through a token in the Authorization header, 403 when editing someone else's post, 404 for missing posts, and an idempotency key on POST so a retried create doesn't make duplicates.

    
Explain it simply: A mobile app's “place order” request times out. Should the app just send it again?

    
How a strong answer sounds
Not blindly. A timeout doesn't mean the order failed — the server may have created it and the response got lost. POST isn't idempotent, so a plain retry could create a second order. The app should send a unique idempotency key with the original request and reuse the same key on retry; the server then recognises the repeat and returns the first result instead of creating another order.

  


  

    
🧠 Key takeaways

    
    
      
  • An HTTP request has a method, a path (plus optional query string), headers and an optional body; a response has a status code, headers and usually a body.
    • 
      
  • GET is safe; GET, PUT and DELETE are idempotent; POST is neither — which decides what's safe to retry and cache.
    • 
      
  • Status families: 2xx success, 3xx look elsewhere, 4xx client's fault (don't just retry), 5xx server's fault (retry later).
    • 
      
  • Key headers: Content-Type, Authorization, Cookie/Set-Cookie, Cache-Control, ETag, Location, Retry-After.
    • 
      
  • REST: nouns in URLs, verbs in methods, plural collections, nesting for ownership, query strings for filters and pages.
    • 
      
  • JSON has six types: object, array, string, number, boolean, null. Use integer cents for money and ISO 8601 strings for dates.

PUT replaces the resource with the given body, so sending it twice leaves the same final state — it's idempotent. Each of the POSTs could create a second payment, order or email if repeated.

    


    

      
A logged-in user tries to view another customer's invoice. Which status code fits best?

      

        
        
        
        
      

      
The server knows who the user is (so not 401), but they aren't allowed to see this resource: 403. (Some APIs return 404 instead, to avoid revealing that the invoice exists.)

JSON requires double quotes around keys and strings, and lowercase true/false. Single quotes, bare keys and False (a Python spelling) are all invalid.

Cancelling changes data, so it must not be a GET. It isn't a plain create/replace/delete either, so REST APIs model it as a POST to an action under the resource. (Deleting the order would lose its history.)
