Caching & CDNs

Caching is the most effective speed tool you have. The idea is simple: remember answers that were expensive to get, so you don't have to work them out again. It's also a classic source of sneaky bugs. Let's learn both sides.

Why caching works

A cache is a small, fast store that holds a copy of data that's slow to fetch or work out. It works because real traffic is skewed (lopsided). A small part of the data — trending posts, popular products, the profiles of logged-in users — gets most of the requests. This is often the famous 80/20 rule: about 20% of the data gets about 80% of the traffic.

📚
Analogy: your desk vs the library

The library (the database) has every book, but walking there takes 10 minutes. Your desk (the cache) holds only 5 books, but they're within arm's reach. You keep the books you use most on the desk. When the desk is full, you return one to make space. The rule for choosing which one is your eviction policy.

Where does “~10× faster” come from? Say a cache hit costs 0.5 ms and a database query costs 10 ms. With a 95% hit ratio, the average read costs 0.95 × 0.5 + 0.05 × 10 = 0.475 + 0.5 ≈ 1 ms, compared with 10 ms with no cache. The bigger win is often the load on the database. At 20,000 reads per second, the database now sees only the 5% that miss: 1,000 queries per second instead of 20,000. And small changes in hit ratio matter a lot. Going from 90% to 99% sounds minor, but misses fall from 10% to 1%, so the database gets 10× fewer queries.

Where caches live

Caching isn't one single part. It happens at every layer between the user and the data. The closer a cache is to the user, the faster it is — but the less control you have over it. Click a layer:

Cache-aside: the pattern you'll use most

In cache-aside (also called lazy loading), the application looks after the cache itself:

Check the cache

cache.get("user:42")

Hit → return it

Done in ~1ms.

Miss → read the database, then populate the cache

cache.set("user:42", row, ttl=60s) so the next reader finds it in the cache (a “hit”).

🧪 Try this: read user:1 twice (a miss, then a hit). Now rename user:1 without invalidation (removing the cached copy) and read again. You get stale (out-of-date) data until the TTL runs out. Then turn on invalidation and repeat.

Why is this the default? It only caches data someone actually asked for, so memory isn't wasted on items nobody reads. And if the cache goes down, the app still works, just slower, because it can always fall back to the database. Two details trip people up:

  • The key must describe the exact data. user:42 is fine for a public profile. A search result needs every input in the key, such as search:shoes:page2:sort=price, or two different searches will share one answer.
  • The first reader always pays. Right after a deploy or a cache restart, every read is a miss. A cache that is empty like this is called “cold”, and a cold cache can send a burst of traffic to the database (see “When caches go wrong” below).

Other caching patterns

The app only talks to the cache. On a miss, the cache itself loads the data from the database (using a loader function you set up). The app code is cleaner, because the cache library handles the logic.

Pros
Simple app code, consistent loading logic.
Cons
Needs a cache that supports loaders; the first request is still slow.

Writes go to the cache, which writes to the database straight away and waits for it before replying. So the cache is always fresh for anything written.

Pros
Cache and database always agree; reads usually find the data already cached.
Cons
Every write is slower (it waits for two writes); it caches data that may never be read.

Writes go to the cache and return right away. The cache saves them to the database later, in the background, in batches. Used for counters, analytics and “likes”.

Pros
Extremely fast writes; batching reduces database load.
Cons
Data is lost if the cache dies before saving it. The database only catches up eventually (eventual consistency).

Popular entries are refreshed ahead of time, before they expire. So users never hit a slow miss on popular (“hot”) keys.

Pros
Low, predictable latency for hot data.
Cons
Wasted work if you guess wrong about what's popular; more complex.

How to choose:

  • Cache-aside is the safe default for read-heavy data, such as profiles, product pages and settings.
  • Read-through is the same idea with the loading logic moved into the cache library. Pick it when many parts of the code read the same data and you want one place to get the loading right.
  • Write-through fits data that is read soon after it is written, like a user's own cart or settings, where a stale read would confuse them.
  • Write-behind is only for data you can afford to lose a few seconds of, such as view counters and like counts. Never use it for orders or payments.
  • Refresh-ahead is for a small set of known-hot keys (the home page, trending lists) where even one slow miss is too many.

Eviction policies

Caches have limited memory. When one is full, something must be removed (“evicted”). The rule you choose decides your hit ratio — the share of reads found in the cache. Tap keys below (or run a workload) and watch three caches of the same size make different choices:

A dry run with room for 3 items. The reads come in this order: A, B, C, A, D.

  1. A, B, C fill the cache (3 misses). It now holds A, B, C.
  2. A is read again: a hit. A is now the most recently used.
  3. D arrives and the cache is full, so one item must go.
    • FIFO evicts A, because it was put in first, even though it was just used.
    • LRU evicts B, because B has gone unused the longest (A was just used, C came after B).
    • LFU sees counts A=2, B=1, C=1. It evicts B or C (a tie; real systems break ties by age).

If the next read is A again, FIFO misses and LRU and LFU hit. That is the whole argument for LRU in one example: the item you just used is the one you are most likely to use again.

Invalidation: the hard part

💬

“There are only two hard things in Computer Science: cache invalidation and naming things.” — Phil Karlton

As soon as you cache, you have two copies of the data, and they can disagree. Removing or updating the out-of-date copy is called invalidation. Here are the main strategies:

⏳

TTL expiry

Accept data that is up to N seconds out of date. Simple, and it fixes itself. Choose the TTL by how old the data is allowed to be: stock price 1s, profile 5min, country list 1 day.

🗑️

Delete on write

After updating the database, DEL (delete) the key. The next read fills it again with fresh data. Watch out for timing problems (races): a slow reader may put old data back into the cache. Add a short TTL as a safety net.

📣

Event-driven

Every database change is announced as an event (e.g. change data capture → Kafka). Listeners then clear the matching cache entries everywhere. This works well across many services.

Here is the race behind “a slow reader may put old data back”, step by step. The user's name is “Ana” in both the database and the cache, and then the cache entry expires.

  1. Reader misses the cache and reads “Ana” from the database. Then it pauses for a moment (a slow network, a busy thread).
  2. Writer updates the database to “Anna” and deletes the cache key.
  3. Reader wakes up and writes what it read, “Ana”, into the cache.

Now the cache holds the old name, and nothing will delete it until the TTL runs out. That is why you keep a TTL even when you delete on write: it limits how long a mistake like this can last. It is also why you usually delete the key on write rather than set it to the new value. If two writers each set the cache, the slower one can overwrite the newer value, while a delete simply makes the next reader fetch fresh data.

When caches go wrong

At large scale, caches create new ways to fail. The root cause is the same in each case: once the database has been sized for the traffic that misses the cache, anything that suddenly raises the miss rate can overload it. Here is a stampede in numbers. A viral post is read 10,000 times a second, and rebuilding its cache entry takes a 200 ms database query. When the key expires, every request in those 200 ms misses: 10,000 × 0.2 = 2,000 identical queries hit the database at once, where normally there would be none. Flip each card for the fix.

🐃

Cache stampede

A hot key expires and thousands of requests hit the DB at once.
Fixes: request coalescing — a lock so only one request rebuilds the key while the others wait; keep serving the old value while a fresh one is fetched; add a random extra amount (jitter) to TTLs; refresh hot keys ahead of time.
👻

Cache penetration

Requests for keys that don't exist always miss and hit the DB (often an attack).
Fixes: cache “not found” answers (“user:999 → null”) with a short TTL; use a Bloom filter (a tiny structure that can say “this key definitely doesn't exist”) to reject those keys; check inputs are valid.
🏔️

Cache avalanche

Many keys expire at the same moment, or the cache cluster restarts cold.
Fixes: randomise TTLs (e.g. 60s ± 10s); keep copies of the cache so it stays up (high availability); fill (“warm”) the cache before sending traffic; use circuit breakers — switches that stop calls when the database is struggling.
🔥

Hot key

One key (a celebrity's post) gets so much traffic it overloads a single cache node.
Fixes: a small cache inside each app server's own memory, in front of Redis; copy the key to several nodes (key#1..#N) and pick one at random; read from replicas.

CDNs: caching at the edge of the planet

A Content Delivery Network (CDN) is a cache spread across the world. Hundreds of edge servers sit in locations close to users (these locations are called PoPs, points of presence). Requests for images, video, JS and CSS — and more and more, API responses — are answered by the nearest edge. They don't have to cross oceans to reach your main server (the origin).

Light in fibre-optic cable travels about 200,000 km/s. Sydney → Virginia is about 15,700 km each way, so a round trip takes 160ms or more before any processing. A page with 40 files feels that badly. With a CDN, most bytes only travel to a nearby edge.

⬇️ Pull CDN

The edge fetches from the origin on the first request, then caches it as the Cache-Control headers say. No upfront work, but the first user at each edge waits longer. The most common kind (Cloudflare, CloudFront).

⬆️ Push CDN

You upload content to the CDN ahead of time. Great for large files you know people will want (video libraries, game patches). You handle uploads and expiry yourself.

# HTTP headers that control caching everywhere (browser, CDN, proxies)
Cache-Control: public, max-age=31536000, immutable   # app.3f9a2c.js — fingerprinted, cache forever
Cache-Control: private, no-cache                  # user dashboard — revalidate every time
ETag: "v42-a1b2"                                   # lets clients ask "changed?" → 304 Not Modified

What those words mean:

  • max-age=N — the copy may be reused for N seconds without asking the origin. 31,536,000 seconds is one year.
  • public / private — public lets shared caches such as a CDN keep a copy. private means only the user's own browser may keep it, which is what you want for anything personal.
  • no-cache — confusingly, this does not mean “don't store”. It means “store it, but check with the server before each reuse”. no-store is the one that means “never keep a copy”, used for things like banking pages.
  • immutable — this file will never change at this URL, so don't even check.
  • ETag — a version label for the content. The browser sends it back with its next request, and if nothing changed the server replies 304 Not Modified with no body, which saves re-sending the file.

The trick with app.3f9a2c.js is called fingerprinting. The part in the middle is a hash of the file's contents. Change one character of the file and the name changes, so the HTML now points at a brand-new URL. That lets you cache files “forever” and still ship updates instantly. It only works for files the HTML links to. The HTML page itself keeps the same URL, so it gets a short max-age or no-cache.

🎤
Interview tip

Whenever a system is read-heavy (10 or more reads per write), say: where you'd cache, what the key is, the TTL, how you invalidate, and what happens when the cache is down. That last point is what sets strong candidates apart.

⚠️
Common mistakes
  • Caching without a plan for invalidation. “We'll just set a TTL” is a decision about how out-of-date data may be. Make that decision on purpose, and know which data must never be out of date.
  • Giving every key the same TTL. Thousands of keys expiring in the same second cause a stampede all at once. Add jitter.
  • Caching a response that only some users may see. The cache key must include who is allowed to see it (e.g. the user ID), or you'll show one user's data to another.
🎤
Interview drill

Design: A product page is read 50,000 times a second and updated a few times a day. Design the caching.

How a strong answer sounds
Use cache-aside in Redis, keyed by product ID and version, with a long TTL plus jitter. Put a CDN in front for the HTML/JSON that logged-out visitors see. On update, write the database, then invalidate the key (or write a key for the new version), so readers move to the fresh data. Protect against stampedes with request coalescing (“single-flight”: one request fetches, the rest wait). Protect against penetration (requests for IDs that don't exist) by caching “not found” or using a Bloom filter.

Failure: Your Redis cluster fails entirely at peak. What happens and what did you build for it?

How a strong answer sounds
The database suddenly gets the full 50K/s and falls over — unless you planned for it. Useful defences: request coalescing so only one request per key reaches the database; a small cache inside each app server as a second line; turning away extra requests on purpose (load shedding) and rate limiting; and serving slightly old content where that's OK. A good answer first says how much breaks (the “blast radius”). Once you've sized the database assuming the cache exists, the cache is no longer optional.

🧠 Key takeaways

  • Caches work because a little data gets most of the traffic. Memory is many times faster than disk or network.
  • You can cache at many layers: browser, CDN, reverse proxy, application, shared cache, database.
  • Cache-aside is the default pattern. Write-behind gives faster writes but risks losing data.
  • LRU is a great default eviction policy. LFU suits data whose popularity stays steady.
  • Invalidation needs a plan: TTL + delete-on-write is a solid starting point.
  • Protect the database from stampedes, penetration, avalanches and hot keys.
  • CDNs move content physically closer to users. You can't out-code physics.
