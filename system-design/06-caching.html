Caching & CDNs

Caching is the single most effective performance tool you have: remember expensive answers so you don't compute them again. It's also a classic source of subtle bugs. Let's master both sides.

  • Know where caches live in a system
  • Implement cache-aside and friends
  • Compare LRU, LFU and FIFO eviction
  • Handle TTLs, invalidation & staleness
  • Prevent stampedes, penetration & avalanches
  • Explain how CDNs cut global latency

Why caching works

A cache is a small, fast storage layer holding a copy of data that's expensive to fetch or compute. It works because real traffic is skewed: a small fraction of data (trending posts, popular products, logged-in user profiles) receives most of the requests — often the famous 80/20 rule.

📚
Analogy: your desk vs the library

The library (database) has every book but walking there takes 10 minutes. Your desk (cache) holds only 5 books but they're within arm's reach. You keep the books you use most on the desk. When the desk is full, you return one to make space — which one you pick is your eviction policy.

Where caches live

Caching isn't one component — it happens at every layer between the user and the data. The closer to the user, the faster, but the less control you have. Click a layer:

Other caching patterns

The app only talks to the cache. On a miss, the cache itself loads from the DB (via a configured loader). Cleaner app code; the cache library owns the logic.

Pros
Simple app code, consistent loading logic.
Cons
Needs a cache that supports loaders; first request still slow.

Writes go to the cache, which synchronously writes to the DB before returning. Cache is always fresh for written keys.

Pros
Cache and DB stay consistent; reads are always warm.
Cons
Every write pays double latency; caches data that may never be read.

Writes go to the cache and return immediately; the cache flushes to the DB asynchronously in batches. Used for counters, analytics, “likes”.

Pros
Extremely fast writes; batching reduces DB load.
Cons
Data loss if the cache dies before flushing. Eventual consistency.

Popular entries are proactively refreshed before they expire, so users never hit a cold miss on hot keys.

Pros
Low, predictable latency for hot data.
Cons
Wasted work if predictions are wrong; more complex.

Invalidation: the hard part

💬

“There are only two hard things in Computer Science: cache invalidation and naming things.” — Phil Karlton

The moment you cache, you have two copies of the data, and they can disagree. Strategies:

⏳

TTL expiry

Accept staleness up to N seconds. Simple and self-healing. Choose TTL by how stale is tolerable: stock price 1s, profile 5min, country list 1 day.

🗑️

Delete on write

After updating the DB, DEL the key. Next read repopulates. Beware races: a slow reader may re-cache old data — add a short TTL as a safety net.

📣

Event-driven

DB changes are published (e.g. change data capture → Kafka) and consumers invalidate caches everywhere. Scales across many services.

When caches go wrong

At scale, caches create their own failure modes. Flip each card for the fix.

🐃

Cache stampede

A hot key expires and thousands of requests hit the DB at once.
Fixes: request coalescing / a lock so only one request rebuilds the key; serve stale while revalidating; add random jitter to TTLs; refresh-ahead for hot keys.
👻

Cache penetration

Requests for keys that don't exist always miss and hit the DB (often an attack).
Fixes: cache negative results (“user:999 → null”) with a short TTL; use a Bloom filter to reject keys that definitely don't exist; validate inputs.
🏔️

Cache avalanche

Many keys expire at the same moment, or the cache cluster restarts cold.
Fixes: randomise TTLs (e.g. 60s ± 10s); replicate the cache for HA; warm the cache before sending traffic; circuit breakers to protect the DB.
🔥

Hot key

One key (a celebrity's post) gets so much traffic it overloads a single cache node.
Fixes: local in-process cache in front of Redis; replicate the key to several nodes (key#1..#N) and pick randomly; read from replicas.

CDNs: caching at the edge of the planet

A Content Delivery Network is a globally distributed cache. Hundreds of edge servers (PoPs) sit close to users. Requests for images, video, JS and CSS — and increasingly API responses — are answered from the nearest edge instead of crossing oceans to your origin.

Light in fibre travels ~200,000 km/s. Sydney → Virginia is ~15,700 km each way, so ~160ms+ per round trip before any processing. A page with 40 assets feels it badly. With a CDN, most bytes travel only to a nearby edge.

⬇️ Pull CDN

Edge fetches from origin on the first request, then caches per Cache-Control headers. Zero upfront work; first user per edge is slow. Most common (Cloudflare, CloudFront).

⬆️ Push CDN

You upload content to the CDN ahead of time. Great for large, predictable files (video libraries, game patches). You manage uploads and expiry.

# HTTP headers that control caching everywhere (browser, CDN, proxies)
Cache-Control: public, max-age=31536000, immutable   # app.3f9a2c.js — fingerprinted, cache forever
Cache-Control: private, no-cache                  # user dashboard — revalidate every time
ETag: "v42-a1b2"                                   # lets clients ask "changed?" → 304 Not Modified
🎤
Interview tip

Whenever you see a read-heavy system (read:write ≥ 10:1), say where you'd cache, what the key is, the TTL, how you invalidate, and what happens when the cache is down. That last one separates strong candidates.

⚠️
Common mistakes
  • Caching without an invalidation story. “We'll just set a TTL” is a decision about staleness — make it explicitly, and know which data can never be stale.
  • Uniform TTLs. Thousands of keys expiring at the same second produce a synchronized stampede; add jitter.
  • Caching the result of a request the user isn't allowed to see. Cache keys must include the authorization dimension, or you'll serve one user's data to another.
🎤
Interview drill

Design: A product page is read 50,000 times a second and updated a few times a day. Design the caching.

How a strong answer sounds
Cache-aside in Redis keyed by product ID and version, with a long TTL plus jitter, fronted by a CDN for the anonymous HTML/JSON. On update, write the database then invalidate (or write the new version key), so readers move to the fresh key. Protect against stampedes with single-flight/request coalescing, and against penetration (requests for IDs that don't exist) with negative caching or a Bloom filter.

Failure: Your Redis cluster fails entirely at peak. What happens and what did you build for it?

How a strong answer sounds
The database sees the full 50K/s and falls over unless you planned: request coalescing so only one request per key reaches the database, a small in-process cache as a second line, aggressive load shedding and rate limiting, and serving stale content where acceptable. The honest answer names the blast radius first — a cache is not optional capacity once you've sized the database assuming it.

🧠 Key takeaways

  • Caches exploit skewed access patterns; memory is orders of magnitude faster than disk or network.
  • Cache at many layers: browser, CDN, reverse proxy, application, distributed cache, database.
  • Cache-aside is the default pattern; write-behind trades durability for write speed.
  • LRU is a great default eviction policy; LFU suits stable popularity.
  • Invalidation needs a strategy: TTL + delete-on-write is a solid baseline.
  • Protect the DB from stampedes, penetration, avalanches and hot keys.
  • CDNs move content physically closer to users — physics beats optimisation.
