Design a URL Shortener

Like bit.ly or TinyURL: turn https://example.com/some/very/long/path?with=params into sho.rt/aZ3kP9x. It looks trivial — and that's why it's a perfect first case study: the interesting parts are ID generation, read-heavy scaling and redirects.

STEP 4 / 6

Generating short codes

This is the heart of the problem. First: how long must a code be? Using base62 characters [0-9a-zA-Z]:

Compute MD5(longUrl) or SHA-256, base62-encode, take the first 7 characters. Same URL → same code (natural dedupe). But truncating a hash creates collisions: two different URLs with the same 7 chars. You must check the DB and retry with a salt — and collisions get likelier as the table fills (birthday paradox).

Expected colliding pairs
P(next insert collides)

Use a globally unique, increasing integer (DB sequence, or a Redis INCR) and encode it in base62. Zero collisions, shortest possible codes. Downsides: a central counter to scale (hand out ranges of 1,000 IDs to each app server), and codes are sequential and guessable — anyone can enumerate links. Fix by scrambling the integer with a reversible permutation before encoding.

ID
Result →

A separate Key Generation Service pre-generates millions of random unique 7-char keys offline and stores them in an “unused” table. App servers grab batches of keys into memory; each key is used once. Fast, random-looking, no runtime collision checks. The KGS must be replicated (it's critical), and keys held by a crashed server are simply wasted — acceptable given 3.5 trillion possibilities.

Twitter's Snowflake: a 64-bit ID = 41 bits timestamp | 10 bits machine ID | 12 bits sequence. Each machine generates up to 4,096 IDs/ms with no coordination, and IDs sort by time. Base62-encoded it's ~11 chars — longer than necessary for a shortener, but perfect for tweets, messages and orders.

🎤
A strong answer

“I'll use a counter-based ID, allocated in ranges per server so there's no hot central counter, run through a bijective scramble so codes aren't sequential, and base62-encode to 7 characters. Custom aliases go in the same table with a uniqueness check. This avoids collision retries entirely.”

STEP 5 / 6

High-level design

Architecture
  1. The client submits the long URL. The gateway authenticates and applies a per-user rate limit — shorteners are magnets for spammers.
  2. Writes are ~1% of traffic, so a small, separately scaled service handles them. It validates the URL and checks it against a malware/phishing blocklist.
  3. The server takes the next ID from its locally cached range (e.g. 5,000,001–5,001,000), refilling from the allocator only occasionally. Scramble + base62 → aZ3kP9x.
  4. Store aZ3kP9x → long URL, replicated ×3. For custom aliases use a conditional put (“insert if not exists”) to guarantee uniqueness.
  5. 201 Created with https://sho.rt/aZ3kP9x. We don't pre-warm the cache: most links are rarely clicked.
  1. Someone clicks the link. DNS resolves sho.rt to the nearest region (GeoDNS/anycast), and the LB routes it to the redirect service.
  2. Stateless and horizontally scaled — this is ~99% of traffic, so it gets the most instances.
  3. Cache-aside lookup in Redis. Popular links are hit constantly, so the hit ratio is very high (~90%+) and the response comes back in ~1ms.
  4. Single-key lookup on the shard owning aZ3kP9x, then populate the cache with a TTL. Unknown codes get a short negative-cache entry to stop enumeration attacks hammering the DB.
  5. Fire-and-forget: publish {code, ts, country, referrer, UA} to Kafka. Analytics never slows down the redirect. Consumers aggregate into an OLAP store.
  6. 302 Found + Location: https://…. The browser follows it. Total server time: a few milliseconds.

301 or 302?

Both redirect. The difference is caching — and that changes your analytics and your load.

Deep dives & bottlenecks

⚡

Caching strategy

LRU cache sized for the hot set (~20% of daily-read links). Cache-aside with TTL; also cache at the CDN edge for the most viral links using short Cache-Control on 302s.

🧩

Sharding

Hash-partition by short_code (consistent hashing) — lookups always hit exactly one shard. Range-sharding by code would create hot spots with sequential IDs.

🛡️

Abuse & security

Rate limit creation per user/IP, scan destinations against malware lists, scrambled non-sequential codes, negative caching for unknown codes, and a takedown flag checked on redirect.

🗑️

Expiration

Check expires_at lazily on read (return 410 Gone), plus a background job or DB TTL feature to purge expired rows. Don't recycle codes — old links may still be printed somewhere.

🌍

Multi-region

Redirects are read-only, so replicate the KV store to several regions and serve reads locally. Writes can go to one primary region; replication lag of a second is fine for new links.

📊

Analytics at scale

Click events → Kafka → stream processor (Flink) → pre-aggregated counts per link/hour/country in ClickHouse. Never count clicks with a synchronous DB update on the hot path.

⚠️
Common mistakes
  • Hashing the long URL and hoping. Collisions are real at scale; use a counter/Snowflake-derived ID or check-and-retry on a unique index.
  • Sequential, guessable codes. They let anyone enumerate every link — fine for public marketing links, terrible for anything private.
  • Forgetting the analytics write path. Every redirect is also a write; don't put it in the user's critical path.
🎤
Interview drill

Design: 10,000 redirects per second, 100:1 read/write. What does the read path look like?

How a strong answer sounds
Redirect is a single key lookup, so: CDN or edge cache for the hottest links with a short TTL, then a Redis cache keyed by short code, then the database. Return 302 (not 301) if you want analytics and the ability to change or disable a link — a permanent redirect gets cached by browsers forever. The click event goes to a queue, never a synchronous database write, and expired or deleted codes are negative-cached so they don't hit the database repeatedly.

Extend: Add per-link analytics: clicks by country and hour, for millions of links.

How a strong answer sounds
Emit a click event per redirect to Kafka, aggregate in a stream job into (link, hour, country) counters, and upsert into an OLAP store — the same shape as Chapter 40. Serve the dashboard from those rollups, never from raw events. Keep raw events in the lake for 30–90 days so you can backfill new dimensions, and use HLL sketches if you need unique visitors rather than raw clicks.

🧠 Key takeaways

  • The workload is ~100:1 read-heavy with a simple key-value access pattern — optimise the redirect path.
  • 7 base62 characters give 3.5 trillion codes — plenty for decades.
  • Counter/range-based IDs avoid collisions; scramble them so they aren't guessable. Hash truncation needs collision handling.
  • Separate read and write services so each scales independently.
  • Cache hot links, shard by code, and push analytics asynchronously through a log.
  • 302 keeps every click visible to you; 301 saves load but browsers cache it.

Check your understanding

Your marketing team needs an accurate click count for every visit. Which redirect status should you use?

301 responses are cached by browsers, so repeat clicks never reach you. 302 keeps every click visible.

What's the main drawback of using MD5(longUrl) truncated to 7 characters?

Truncation throws away most of the hash's uniqueness; by the birthday paradox collisions appear long before the space is full.

Why split the system into a write service and a redirect service?

The redirect path needs many lean, cache-heavy instances; the write path needs validation and ID allocation but little capacity.

How should the redirect service record click analytics?

Keeps the hot path fast and isolates it from analytics failures; aggregation happens in a separate pipeline.
