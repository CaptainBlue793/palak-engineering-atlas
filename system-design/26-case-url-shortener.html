Design a URL Shortener

Like bit.ly or TinyURL: turn https://example.com/some/very/long/path?with=params into sho.rt/aZ3kP9x. It sounds simple, which makes it a great first case study. The interesting parts are three: how you create the short codes, how you handle far more reads than writes, and how the redirect works.

  • Estimate traffic, storage and cache size
  • Choose a way to create the short codes
  • Design the read path (following a link) and the write path (creating one)
  • Decide between 301 and 302 redirects
  • Spot the bottlenecks and the topics worth a closer look

STEP 1 / 6

Clarify requirements

Before drawing anything, pin down what the system must do (functional requirements) and how well it must do it (non-functional requirements). Two answers here shape everything that follows. First, links are followed far more often than they are created, so the design is built around the read path. Second, a short link is often printed on a poster or sent in an email that can't be changed later — so a link that stops working, or points to the wrong page, is a serious bug, not a small one.

🛠️ Functional

✓Given a long URL, create a unique short URL
✓Visiting the short URL redirects to the long URL
✓Optional custom alias (sho.rt/my-launch)
✓Optional expiration date
✓Basic click analytics
–Out of scope: user accounts UI, editing links, QR codes

📏 Non-functional

✓Very fast redirects (p99 < 50ms on the server: 99 out of 100 redirects finish within 50ms)
✓Highly available (almost never down) — a broken link breaks someone's campaign
✓Read-heavy: people follow links far more often than they create them
✓Short codes must be unique, and you should not be able to guess the next one
✓Links keep working for years

Conclusions:

  • Reads outnumber writes by 100× or more.
  • The whole dataset is only a few terabytes. That fits easily in a sharded KV store (a key-value database split across several machines).
  • A fairly small cache can serve most traffic. That's because popularity is very uneven: a few links get most of the clicks.

What do these numbers decide? 40 writes/s is tiny — one database could take them — so writes are not the hard part. 12,000 redirects/s at peak is more than you want to send straight to a database, so a cache is worth it. And 35 GB is really an upper bound: many of those 350M daily reads hit the same popular links, so the set of distinct hot links is far smaller. 3 TB of data fits on a handful of machines, so sharding here is mostly for availability and headroom, not because one machine is full.

The only query that runs constantly is lookup by short_code. It's a pure key-value lookup: give a key, get one value, no joins. So a distributed key-value or wide-column store (DynamoDB, Cassandra) fits naturally. PostgreSQL split into shards also works fine at this size.

Why not a “normal” relational design with joins? Because nothing here needs them. There is one entity, one lookup key and no transactions across rows. A relational database gives you features you won't use, while a key-value store makes the one query you do run — “give me the row for this code” — fast and easy to spread across machines. The exception is custom aliases: two users asking for my-launch at the same moment must not both succeed. Both kinds of store handle that with a conditional insert (“only if this key doesn't exist yet”), so it doesn't force the choice either way.

A few edge cases the API must decide on up front:

  • The same long URL shortened twice. Either return the existing code (needs an extra index on long_url) or create a new one each time. Most shorteners create a new one, because each user wants their own link with its own click stats.
  • Bad input. Reject URLs that aren't http/https, that are very long (over ~2 KB), or that point back at sho.rt itself — otherwise someone can build a redirect loop.
  • Alias rules. Limit aliases to safe characters and block reserved words like api or login, which would clash with your own URLs.
STEP 4 / 6

Generating short codes

This is the heart of the problem. First question: how long must a code be? We use base62: each character is one of 62 options, the digits and lowercase and uppercase letters [0-9a-zA-Z].

The count grows fast because each extra character multiplies the options by 62. With 6 characters you get 62⁶ ≈ 57 billion codes; at 1.2 billion new links a year (100M a month) that lasts about 47 years. With 7 characters you get 62⁷ ≈ 3.5 trillion codes, which lasts thousands of years at the same rate. Seven is the usual choice: still short enough to type, with so much spare room that random-looking codes rarely collide.

Run the long URL through a hash function like MD5(longUrl) or SHA-256. Encode the result in base62 and keep the first 7 characters. A nice bonus: the same URL always gets the same code, so duplicates merge on their own.

The problem is collisions. Cutting the hash down to 7 characters means two different URLs can end up with the same code. You must check the database, and on a clash retry with a salt (extra text added to change the hash). Collisions also get more likely as the table fills up. This is the birthday paradox: in a room of just 23 people, two probably share a birthday.

Why so early? What matters is the number of pairs, not the number of items. With n links there are about n²/2 pairs, and each pair has a 1-in-62⁷ chance of matching. So the expected number of clashes is roughly n² ÷ (2 × 62⁷). Put in 1 billion links: 10¹⁸ ÷ (7 × 10¹²) ≈ 140,000 clashing pairs. Even at 10 million links you'd expect about 14. Every one must be caught, or two different long URLs would share one short code.

P(next insert collides)

Keep one counter that only goes up, like a database sequence or a Redis INCR. Each new link takes the next number, and you encode it in base62. You get zero collisions and the shortest possible codes.

Two downsides:

  • One central counter must keep up with every write. Fix: hand each app server a block of 1,000 IDs at a time, so it rarely asks.
  • Codes come out in order, so they're guessable. Anyone can walk through them one by one and find every link. Fix: scramble the number with a reversible shuffle before encoding it.

How does a block of IDs work? The allocator stores one number, “next free block”. A server asks for a block, and the allocator adds 1,000 to that number in a single atomic update and hands back the range. The server then counts through its 1,000 IDs in memory with no network calls. At 40 writes/s across the whole system, the allocator is asked roughly once every 25 seconds. If a server crashes with half a block unused, those IDs are simply skipped; gaps are harmless.

A separate Key Generation Service (KGS) creates millions of random, unique 7-character keys ahead of time. It stores them in an “unused” table. App servers grab a batch of keys into memory, and each key is used once. This is fast, the codes look random, and you never check for collisions while serving requests.

The catches: everything depends on the KGS, so it must be replicated (copied to several machines). And if a server crashes, the keys it was holding are simply lost. That's fine, because there are 3.5 trillion possible keys.

The one rule the KGS must never break is handing the same key to two servers. The usual way is to move a batch from the “unused” table to a “used” table in one transaction before returning it, so even if two servers ask at the same moment, each batch is claimed only once.

Twitter's Snowflake builds a 64-bit ID from three parts: 41 bits timestamp | 10 bits machine ID | 12 bits sequence. Each machine can make up to 4,096 IDs per millisecond without talking to any other machine, and the IDs sort by time. In base62 it's about 11 characters. That's longer than a shortener needs, but perfect for tweets, messages and orders.

🎤
A strong answer

“I'll use a counter-based ID. Each server gets its own range of IDs, so no single counter gets overloaded. I'll pass each ID through a bijective scramble (a one-to-one shuffle) so codes aren't in order, then base62-encode it to 7 characters. Custom aliases go in the same table with a uniqueness check. This way I never need collision retries.”

When would you pick something else? Hash + truncate is reasonable if you want the same URL to always get the same code and you're happy to check for clashes. A KGS fits if codes must look fully random (for private links) and you're willing to run one more service. Snowflake-style IDs make sense when you already run a Snowflake service for other data and don't mind 11-character codes.

STEP 5 / 6

High-level design

Architecture
  1. The client sends the long URL. The gateway checks who the user is and applies a per-user rate limit (a cap on requests). Spammers love shorteners, so this matters.
  2. Writes are only ~1% of traffic, so a small service of their own handles them. It checks the URL is valid and not on a malware or phishing blocklist.
  3. The server takes the next ID from the range it holds in memory (e.g. 5,000,001–5,001,000). It asks the allocator for a new range only once in a while. Scramble + base62 → aZ3kP9x.
  4. Save aZ3kP9x → long URL, with 3 copies for safety. For custom aliases, use a conditional write (“insert only if it doesn't exist yet”). That guarantees no two users get the same alias.
  5. 201 Created with https://sho.rt/aZ3kP9x. We don't put the new link in the cache yet, because most links are rarely clicked.
  1. Someone clicks the link. DNS points sho.rt to the nearest region (using GeoDNS or anycast). The load balancer then sends the request to the redirect service.
  2. It is stateless (it keeps no data of its own), so you can add copies freely. It handles ~99% of traffic, so it gets the most instances.
  3. Look in the Redis cache first (cache-aside: the app checks the cache, and fills it itself on a miss). Popular links are requested constantly, so 90%+ of lookups are found there. The answer comes back in ~1ms.
  4. Look up the one key on the shard that holds aZ3kP9x. Then put it in the cache with a TTL (an expiry time). Codes that don't exist get a short “not found” entry in the cache too (negative caching). That stops attackers who try random codes from hammering the database.
  5. Fire and forget: send {code, ts, country, referrer, UA} to Kafka and don't wait for a reply. So analytics never slows down the redirect. Other services read these events and total them up in an OLAP store (a database built for reports).
  6. 302 Found + Location: https://…. The browser follows it. Total time on the server: a few milliseconds.

301 or 302?

Both send the browser to the long URL. The difference is caching: whether the browser remembers the answer. That changes both your click counts and your server load.

With 301 Moved Permanently, the browser saves the answer and next time goes straight to the long URL without asking you. You save load, but you never see repeat clicks and can't change or disable the link for that browser. With 302 Found, the browser asks every time. Pick 302 when you need click analytics, expiring links or takedowns — which is almost always the case for a shortener. Pick 301 only for links that truly never change and where you don't need counts.

Deep dives & bottlenecks

The basic design works. Now ask what goes wrong at scale or when parts fail. Each card below is one of those questions, with the reasoning behind the answer.

⚡

Caching strategy

Use an LRU cache (it drops the least recently used entry when full). Size it for the popular links, about 20% of those read each day. Use cache-aside with a TTL. For the most viral links, also cache at the CDN edge by sending a short Cache-Control time with the 302.

🧩

Sharding

Split data across shards by a hash of short_code (using consistent hashing). Each lookup then goes to exactly one shard. Splitting by ranges of codes would be a mistake: with sequential IDs, all new links would land on the same shard and overload it.

🛡️

Abuse & security

Several layers work together:

  • Rate limit link creation per user or IP.
  • Check destinations against malware lists.
  • Scramble codes so they're not in order.
  • Cache “not found” for unknown codes.
  • Keep a takedown flag that the redirect checks.
🗑️

Expiration

Check expires_at only when a link is read, and return 410 Gone if it's past. Separately, a background job (or the database's own TTL feature) deletes expired rows. Don't reuse old codes: those links may still be printed on a poster somewhere.

🌍

Multi-region

Redirects only read data, so copy the KV store to several regions and serve reads from the nearest one. Writes can all go to one main region. The copies may lag about a second behind, and that's fine for new links.

📊

Analytics at scale

Click events → Kafka → a stream processor (Flink) → ready-made totals per link, hour and country in ClickHouse. Never count clicks by updating the database while the user waits for the redirect.

What happens when parts fail?

  • The Redis cache goes down. Every redirect now reads the KV store. With a 90% hit rate, the store goes from ~1,200 reads/s to ~12,000 reads/s at peak — ten times the load in an instant. Run the cache with replicas, size the store so it can survive the spike for a while, and keep a small in-process cache of the very hottest codes on each redirect server.
  • One KV shard goes down. Only the codes on that shard fail. With 3 copies per shard, a replica takes over within seconds, and links already in the cache keep working during the switch.
  • The ID allocator goes down. Servers keep using the block they already hold, so link creation continues for a while. Redirects are not affected at all — they never touch the allocator.
  • Kafka is slow or down. The redirect must still succeed. Buffer click events in memory for a short time and drop them if the buffer fills. Losing a few clicks is acceptable; failing redirects is not.
  • A link goes viral. One code gets tens of thousands of clicks per second, all on one cache key and one shard. The short CDN cache on the 302 and the in-process cache on each redirect server spread that load so no single machine takes it all.
⚠️
Common mistakes
  • Hashing the long URL and hoping. At scale, collisions really happen. Use an ID from a counter or Snowflake, or check for a clash and retry using a unique index.
  • Sequential, guessable codes. Anyone can step through them and find every link. That's fine for public marketing links, terrible for anything private.
  • Forgetting the analytics write path. Every redirect is also a write (a click to record). Don't make the user wait for it.
🎤
Interview drill

Design: 10,000 redirects per second, 100:1 read/write. What does the read path look like?

How a strong answer sounds
A redirect is a single key lookup, so check three layers in order. First a CDN or edge cache for the hottest links, with a short TTL. Then a Redis cache keyed by short code. Then the database. Return 302 (not 301) if you want analytics and the ability to change or disable a link. A permanent redirect gets cached by browsers forever. The click event goes to a queue, never to a database write the user waits on. Expired or deleted codes get a “not found” cache entry, so they don't hit the database again and again.

Extend: Add per-link analytics: clicks by country and hour, for millions of links.

How a strong answer sounds
Send one click event per redirect to Kafka. A stream job totals them into (link, hour, country) counters and upserts them (insert or update) into an OLAP store. It's the same shape as Chapter 40. Serve the dashboard from those totals, never from raw events. Keep the raw events in the data lake for 30–90 days, so you can recompute history if you add a new breakdown later. If you need unique visitors rather than raw clicks, use HLL sketches (HyperLogLog: a tiny structure that estimates distinct counts).

🧠 Key takeaways

  • There are ~100 reads for every write, and each read is a simple key lookup. So focus on making the redirect path fast.
  • 7 base62 characters give 3.5 trillion codes. That's plenty for decades.
  • IDs from a counter (handed out in ranges) never collide. Scramble them so they can't be guessed. Cutting a hash short needs collision handling.
  • Separate read and write services so each scales independently.
  • Cache popular links, shard by code, and send analytics through a log in the background.
  • 302 lets you see every click. 301 saves load, but browsers cache it, so you miss repeat clicks.

Check your understanding

Your marketing team needs an accurate click count for every visit. Which redirect status should you use?

Browsers cache 301 responses, so repeat clicks never reach your server. With 302 the browser asks every time, so you see every click.

What's the main drawback of using MD5(longUrl) truncated to 7 characters?

Cutting the hash short throws away most of its uniqueness. Because of the birthday paradox, collisions show up long before all the codes are used.

Why split the system into a write service and a redirect service?

The redirect path needs many small instances that lean on the cache. The write path needs validation and ID handling, but little capacity.

How should the redirect service record click analytics?

This keeps redirects fast, and an analytics failure can't break them. The counting happens in a separate pipeline.

Attackers request millions of random codes to scrape links, flooding your DB with misses. Best mitigation mix?

This combines two earlier ideas: protecting against cache penetration (requests for keys that don't exist, Chapter 6) and rate limiting (Chapter 15).
