Design Collaborative Editing

Google Docs, Notion, Figma, Linear: several people type into the same document at the same time. Every keystroke shows up instantly, nobody's work is lost, and everyone ends up seeing exactly the same thing. In this case study, the data structure is the architecture. It's also where “last write wins” (keep whichever save came last) goes badly wrong.

  • See why edits made at the same time can't be merged by position alone
  • Understand operational transformation (OT)
  • Understand sequence CRDTs, and compare them with OT
  • Design the live session, the saving layer and presence (who's here, where their cursor is)
  • Handle offline editing, history and undo
  • Scale to many documents, and cope with very popular ones

Two things matter here:

  • Operations (“ops”: each small edit, like “insert x here”) are tiny and never stop. So the challenge is holding connections and sending each op to everyone, not bandwidth. The chat lessons from Chapter 28 apply.
  • Editors per document are very uneven. Almost every document has one editor. A handful, like a school worksheet or a company all-hands doc, have hundreds.

The arithmetic behind the numbers:

  • Ops per second: of 3M open sessions, most people are reading or thinking. Say ~10% are typing at any moment: 300K typists × ~5 keystrokes a second = 1.5M ops/s.
  • Bandwidth in: 1.5M × 60 bytes = 90 MB/s. Small. But each op is also sent to every other editor of that document. With an average of ~3 editors per active doc, outgoing traffic is roughly 2–3× the incoming.
  • Connections: 3M WebSockets at ~50K per gateway server is ~60 gateways, before spare capacity.
  • Op log growth: if the daily average is about a third of peak, 500K ops/s × 86,400 s × 60 bytes ≈ 2.6 TB a day. That is why the log is compacted into snapshots (Step 5).
STEP 3 / 6

Why naive merging destroys documents

Two people edit the same sentence while briefly disconnected. Each one sends “insert X at index 6”. But by the time it arrives, the other person's insert has already pushed everything after index 4 along. Use the index as-is and the characters land in the wrong places. Worse, the two copies (replicas) can end up different, for good.

A four-character trace makes it concrete. Both start with cat. Ana adds “s” at the end: insert("s", 3), giving cats. At the same time Bo adds “the ” at the start: insert("the ", 0), giving the cat. Now each receives the other's op:

  • Ana applies Bo's insert at 0: cats → the cats. Correct.
  • Bo applies Ana's insert at 3: the cat → thes cat. Wrong. Index 3 meant “after cat” in Ana's copy, but in Bo's copy it now points inside “the”.

The two replicas now disagree, and neither knows it. OT would fix Ana's op before applying it: Bo inserted 4 characters before position 3, so it becomes insert("s", 7), giving the cats on both sides.

STEP 4 / 6

The two families

Each operation says which document version it was made on: insert("x", 6) @ v12. A central server puts all operations into one agreed order. If an operation was made on an older version, each replica first transforms it: it adjusts the operation for every operation it missed. For example, if someone inserted 3 characters earlier in the text, “insert at 6” becomes “insert at 9”.

// Transform op A (from a client) against op B (already applied). Insert vs insert:
function transform(a, b) {
  if (b.pos < a.pos || (b.pos === a.pos && b.site < a.site)) return { ...a, pos: a.pos + b.text.length };
  return a;                       // b landed after a → a's index is unaffected
}

Read the code with the trace above: b is Bo's insert at 0, a is Ana's insert at 3. Since 0 < 3, Ana's position moves right by 4. The site comparison handles the tie: if both insert at the same index, both replicas must agree whose text goes first, so they compare a fixed ID for each user. Without the tie-break, each side might put its own text first and the copies would differ. Deletes need their own rules: an insert after a deleted range shifts left by the number of deleted characters, and every pair of op types (insert/insert, insert/delete, delete/delete, plus formatting) needs its own case. That multiplication is why OT is hard.

Why does the central server help so much? With one server choosing the order, each client only has to transform its ops against the server's sequence. Without it, every pair of clients could see ops in different orders, and the transform functions must satisfy much stricter rules that many published algorithms were later shown to break.

Strengths
  • Documents stay small, with no extra data per character
  • Ops are tiny and easy for people to read
  • Proven in real products: Google Docs, Etherpad, Office
Weaknesses
  • Needs a central server to put operations in order
  • Transform functions are famously hard to get right (rich text × many kinds of operation)
  • Every client must keep its history until everyone has confirmed receiving it

A CRDT (conflict-free replicated data type) gives every inserted character an ID that is unique everywhere and never changes. The ID also says where the character belongs: for example a fraction plus the ID of the device that typed it, or a pointer to the character before it. Think of numbering seats 1, 2, 3: to squeeze a seat between 2 and 3, call it 2.5.

Merging then works in any order: combine both sets of characters and sort by ID. A deleted character isn't removed. It's marked as deleted (a tombstone), so an insert made next to it at the same time still knows where it goes.

// Each char: { id: [fractionalPosition, siteId], ch, deleted }
H → [0.10, s1]   e → [0.20, s1]   y → [0.25, s2]   // s2 inserted between 0.20 and 0.30
merge(a, b) = sortById(union(a, b))      // commutative, associative, idempotent

Those three words at the end are what make it safe. Commutative: merging A into B gives the same result as B into A, so arrival order doesn't matter. Associative: merging in any grouping gives the same result, so three devices can sync in any pattern. Idempotent: merging the same op twice changes nothing, so resending after a dropped connection is harmless.

Edge cases the ID scheme must handle. If Ana and Bo both insert between 0.20 and 0.30 at the same moment, both may pick 0.25; the site ID breaks the tie, so both replicas sort them the same way. And if people keep inserting in the same gap (0.25, 0.255, 0.2555…), IDs grow longer, which is one reason real libraries use smarter schemes. The size cost is real: 30,000 characters with ~16-byte IDs would be ~480 KB instead of 30 KB. Libraries like Yjs store a run of characters typed in a row by one user as a single entry, which brings the overhead down a lot.

Strengths
  • No central server needed, so devices can sync directly with each other and work offline naturally
  • Merging is simple, and proven to always end up identical
  • A great fit for apps that keep data on the device first, and for long offline periods
Weaknesses
  • The extra data per character makes documents bigger (compressing runs of characters helps)
  • Tombstones pile up and need cleaning up
  • A technically “correct” merge can still read oddly (two people's words mixed together)

Libraries: Yjs, Automerge, Diamond Types, Fugue/RGA variants. Figma, Linear and Notion-style apps use CRDT-like structures. Figma's multiplayer is its own CRDT that works on each property of each object.

Both guarantee strong eventual consistency: any two copies that have received the same operations show the same document, whatever order the operations arrived in. Neither can tell you whether the merged result is what a person actually wanted. That's why products still add comments, suggestions, and locks for big structural changes.

Rule of thumb for choosing. Pick OT when you already run servers, users are almost always online, and you want compact documents, the classic Google Docs setup. Pick a CRDT when the app must work offline for long stretches, sync between devices without a server, or encrypt end to end. In an interview, either is fine if you say why; many new products pick a CRDT library simply because it already exists and is well tested.

STEP 5 / 6

The system around the algorithm

One keystroke, end to endStep-through
  1. The character appears right away; the editor never waits for the server. The op goes into a pending queue, labelled with the last server revision (version number) this client has seen.
  2. WebSockets (Chapter 28) carry a steady stream of tiny messages. The gateway routes by document ID, so everyone editing a document reaches the same session process.
  3. The session is the single place that decides the order of edits. It adjusts the incoming op for anything it accepted since the client's revision, gives it revision 42, and applies it to the official copy of the document. Because only one process writes each document, machines never have to agree with each other on the busy path.
  4. The op is added to the end of a saved log (one per document, split across shards). Only then does the client get a confirmation. So a confirmed keystroke survives a crash.
  5. The other editors receive the adjusted op and apply it. The client that sent it gets a confirmation with its revision number, and removes it from its pending queue.
  6. Cursor positions, selections and “Ana is typing” change constantly and are useless a second later. Limit them to ~10 a second, send them out without saving them, and drop them when the system is busy. Never let cursor traffic compete with edits.
  7. Replaying 400,000 ops to open a document is too slow. So the session regularly saves a snapshot (the full document at that moment). Opening = latest snapshot + the ops after it. Named versions and “see edit history” come from the same log.

Why one writer per document, and not a database transaction per keystroke? Ordering is the whole problem. If any server could accept an op, two servers would have to agree on which op is revision 42, which means a round of coordination for every keystroke. A single session process decides the order with a simple counter in memory. The durability comes from the op log: saving an op there takes a few milliseconds, well within the 200 ms budget. Snapshots keep loading fast: with one every ~1,000 ops, opening a document means reading one snapshot and replaying at most 1,000 ops, instead of the 400,000 since it was created.

Edge case: cursors need transforming too. If Bo's cursor sits at position 10 and Ana inserts 3 characters at position 2, Bo's cursor must move to 13, or it will suddenly appear in the middle of the wrong word. Each client adjusts the remote cursors it displays by the same rules it uses for ops.

📴

Offline & reconnect

The client stores its ops locally (in IndexedDB), each with the revision it was based on. On reconnect it sends them all. The server adjusts each op for everything that happened in the meantime, much like a git rebase. CRDTs shine after long offline periods, because an op is never “too old to adjust”.

↩️

Undo is harder than it looks

Undo must be per user: Ctrl-Z should undo your last edit, not your colleague's. So you keep an undo list of each user's ops. To undo, you create the opposite op and adjust it for everything that happened since. Undoing only your own edits is one of the hardest parts of any real editor.

🎨

Rich text & structure

Formatting is usually stored either as labels on ranges of text (Quill's delta format) or as a tree (ProseMirror). A “bold this” and an “insert here” made at the same time must both survive. Trees add operations like move and wrap, which are really hard to adjust correctly. That's why many products limit structural edits.

🔐

Permissions & encryption

The session checks every op against the document's access list (Chapter 11). Ops from a viewer are rejected, not just hidden. End-to-end encryption is hard here, because the server can't adjust ops it can't read. Products that offer it use CRDTs and do all the merging on the clients.

STEP 6 / 6

Scaling and failure

🧩

Shard by document

Documents don't depend on each other, so they split cleanly: hash the doc ID to pick a session shard (Chapter 8). Sessions hold live state, so combine consistent hashing with a lease (a time-limited ownership claim). That way exactly one process owns a document at a time (see fencing tokens, Chapter 17). The danger case: the old owner freezes (a long pause), its lease runs out, a new owner takes over, and then the old one wakes and tries to append ops. The log must reject writes carrying an older lease number, or two processes would number revisions independently.

💥

Session failover

If a session process dies, clients reconnect. The new owner loads the snapshot plus ops from the log, and clients resend their pending ops. Each op has an ID, so resending is safe. Because the log, not memory, is the official record, no confirmed edit is lost.

🐘

The 500-editor document

Each op must go to every editor. So with N editors all typing, traffic grows with N × N. For example, 500 editors with 50 typing at 5 ops/s is 250 ops/s in, but each goes to 499 people: ~125K messages a second for one document. Sending one batch every 50 ms instead is 20 batches/s × 500 people = 10K messages a second. Fixes: bundle ops into ~50 ms batches, merge cursor updates, cap the number of editors and put the rest in read-only mode, and split huge documents into sections that sync separately.

🧹

Compaction

Op logs grow forever. Take snapshots regularly, then delete ops older than your keep period (keeping some checkpoints for history). For CRDTs, clean up tombstones once every copy has seen the delete.

🌍

Global users

With one shared session, someone is always far away from it. Put the session in the region where most of the document's users are. Let an edge server near each user accept the WebSocket connection, to shorten the secure setup. And show local edits right away to hide the network delay.

🧪

Testing convergence

Convergence is a rule that must always hold: whatever order the operations arrive in, all copies end up identical. That's exactly what property-based testing and deterministic simulation are for (Chapter 19). Most real CRDT/OT bugs are found by random testing, not by hand-written examples.

⚠️
Common mistakes
  • Merging by index. Edits made at the same time shift positions. You need transformation or permanent IDs.
  • Waiting for the server before showing a keystroke. Show it locally first. Typing must never wait on the network.
  • Saving presence and cursors. They're short-lived and very frequent. Send them out and forget them; never write them to storage.
🎤
Interview drill

Reason: Why can't you just use last-write-wins on the document text?

How a strong answer sounds
Because the document isn't one value. It's a sequence of positions, and both people's edits change it at once. Last-write-wins throws away one user's entire set of changes: they watch their paragraph vanish. Conflicts must be handled per operation (OT) or per character ID (CRDT), and the merge must keep what both users meant instead of picking a winner.

Operate: The document session process crashes with 40 people editing. What do the users see?

How a strong answer sounds
A brief disconnect. Each client keeps its unconfirmed operations locally, so nothing typed is lost. A new session process takes ownership through a lease. It loads the latest snapshot plus the later ops from the saved log. Clients reconnect with backoff and jitter (increasing, randomized waits), and resend pending ops labelled with the last revision they saw. The server adjusts them for anything saved since. The log, not the process memory, is the official record.

🧠 Key takeaways

  • Edits can't be merged by index alone. You need either transformation (OT) or permanent IDs (CRDT).
  • OT keeps documents small, but needs a central server to order edits and tricky transform functions.
  • CRDTs merge correctly in any order without a server. The cost is extra data per character, plus tombstones.
  • Show edits locally first. Typing must never wait on the network.
  • One session process owns each document. It puts ops in order, saves them to a log that is only ever added to, then sends them to everyone.
  • Snapshots make document loading fast; the op log powers history and recovery.
  • Presence and cursors are short-lived and rate-limited. Never save them, and drop them first when busy.
  • Shard by document, recover from crashes using the log, and treat very popular documents as a special case.

Check your understanding

Two users insert text at index 6 of the same sentence while briefly disconnected. Why can't the server just apply both inserts at index 6?

Each op was made on a version of the document that no longer exists. OT adjusts the index; CRDTs don't use indexes at all.

What's the main architectural difference between OT and CRDT?

Needing one agreed order is exactly why Google Docs runs a central session, and Figma/Yjs-style apps don't have to.

Why do CRDTs keep tombstones for deleted characters?

If you removed the ID completely, other copies' operations that point to it would lose their anchor, and the copies would stop matching.

Opening a heavily-edited document takes 12 seconds because the server replays 400,000 ops. Fix?

It's the same pattern as event sourcing (Chapter 17). Snapshots limit how much you replay, while the log stays the official record.

A document with 300 simultaneous editors starts lagging badly. What's the first thing to do?

Every op goes to every editor, and cursor updates are usually most of the traffic. Batching, and cutting presence traffic, gives the biggest win fastest.
