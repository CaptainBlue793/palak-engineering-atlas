Design Collaborative Editing

Google Docs, Notion, Figma, Linear: several people type into the same document at the same time, every keystroke appears instantly, nobody's work is lost, and everyone ends up seeing exactly the same thing. This is the one case study where the data structure is the architecture — and where “last write wins” is catastrophically wrong.

  • See why concurrent edits can't be merged by position alone
  • Understand operational transformation (OT)
  • Understand sequence CRDTs and compare the two
  • Design the session, persistence and presence layers
  • Handle offline editing, history and undo
  • Scale to many documents — and survive very popular ones

STEP 3 / 6

Why naive merging destroys documents

Two people edit the same sentence while briefly disconnected. Each sends “insert X at index 6”. But by the time that arrives, the other person's insert has already shifted everything after index 4. Apply the raw index and the characters land in the wrong places — or worse, the two replicas end up different, permanently.

🧪 With raw indexes the replicas diverge — and no amount of retrying fixes it, because the information needed to merge correctly was thrown away. OT rewrites each incoming operation against the operations it didn't see. CRDTs give every character a stable identifier, so merging is just a sorted union.
STEP 4 / 6

The two families

Operations are expressed against a document version: insert("x", 6) @ v12. A central server puts operations in a total order. Before applying an operation that was written against an older version, each replica transforms it against every operation it missed.

// Transform op A (from a client) against op B (already applied). Insert vs insert:
function transform(a, b) {
  if (b.pos < a.pos || (b.pos === a.pos && b.site < a.site)) return { ...a, pos: a.pos + b.text.length };
  return a;                       // b landed after a → a's index is unaffected
}
Strengths
  • Documents stay small — no per-character metadata
  • Ops are tiny and human-readable
  • Battle-tested: Google Docs, Etherpad, Office
Weaknesses
  • Needs a central server to order operations
  • Transform functions are notoriously hard to get right (rich text × many op types)
  • Every client must keep history until everyone has acknowledged

Every inserted character gets a globally unique, immutable identifier that also encodes its position in the sequence (a fractional index plus a site ID, or a reference to its predecessor). Merging is then order-independent: take the union, sort by identifier. Deletes become tombstones so a concurrent insert next to a deleted character still knows where it goes.

// Each char: { id: [fractionalPosition, siteId], ch, deleted }
H → [0.10, s1]   e → [0.20, s1]   y → [0.25, s2]   // s2 inserted between 0.20 and 0.30
merge(a, b) = sortById(union(a, b))      // commutative, associative, idempotent
Strengths
  • No central server required — peer-to-peer and offline-first work naturally
  • Merging is simple and provably convergent
  • Great fit for local-first apps and long offline periods
Weaknesses
  • Per-character metadata inflates documents (mitigated by run-length encoding)
  • Tombstones accumulate and need garbage collection
  • “Correct” merges can still be semantically odd (interleaved words)

Implementations: Yjs, Automerge, Diamond Types, Fugue/RGA variants. Figma, Linear and Notion-style apps use CRDT-like structures; Figma's multiplayer is a custom CRDT over per-property values.

Both guarantee strong eventual consistency: replicas that have seen the same set of operations show the same document, regardless of the order they arrived in. Neither can tell you whether the merged result is what a human would have wanted — that's why products still add comments, suggestions and locks for structural edits.

STEP 5 / 6

The system around the algorithm

One keystroke, end to endStep-through
  1. The character appears immediately — the editor never waits for a round trip. The op is added to a pending queue tagged with the last server revision this client has seen.
  2. WebSockets (Chapter 28) carry a continuous stream of tiny messages. The gateway routes by document ID, so all editors of a document land on the same session process.
  3. The session is the serialization point: it transforms the incoming op against anything it has accepted since the client's revision, assigns revision 42, and applies it to the authoritative document. Single-writer-per-doc removes every distributed-consensus problem from the hot path.
  4. The op is appended to a durable log (per document, sharded). Only then is the client acknowledged, so an accepted keystroke survives a crash.
  5. Other editors receive the transformed op and apply it; the originating client gets an ack with the assigned revision and drops it from its pending queue.
  6. Cursor positions, selections and “Ana is typing” are high-frequency and worthless a second later: throttle to ~10/s, broadcast without persisting, and drop them under load. Never let cursor traffic compete with edits.
  7. Replaying 400,000 ops to open a document is too slow, so the session periodically writes a snapshot. Loading = latest snapshot + ops after it. Named versions and “see edit history” are built from the same log.
📴

Offline & reconnect

The client queues ops locally (IndexedDB) with the revision it was based on. On reconnect it sends the queue; the server transforms each op against everything that happened meanwhile — effectively a rebase. Long offline periods are where CRDTs shine, because there's no “too old to transform” cliff.

↩️

Undo is harder than it looks

Undo must be per user: Ctrl-Z should revert your last edit, not your colleague's. That means keeping a per-user undo stack of ops and transforming the inverse op against everything since. Selective undo is one of the trickiest parts of any real editor.

🎨

Rich text & structure

Formatting is usually modelled as attributes over ranges (Quill's delta format) or as a tree (ProseMirror). Concurrent “bold this” and “insert here” must both survive, and tree structures add move/wrap operations whose transforms are genuinely hard — which is why many products restrict structural edits.

🔐

Permissions & encryption

Every op is checked against the document ACL at the session (Chapter 11); a viewer's ops are rejected, not just hidden. End-to-end encryption is hard here because the server can't transform ciphertext — products that offer it use CRDTs and move merging entirely to clients.

STEP 6 / 6

Scaling and failure

🧩

Shard by document

Documents are independent, so this partitions perfectly: hash the doc ID to a session shard (Chapter 8). Sessions are stateful, so use consistent hashing plus a lease so exactly one process owns a document at a time (Chapter 17's fencing tokens).

💥

Session failover

If a session process dies, clients reconnect, the new owner loads snapshot + ops from the log, and clients resend pending ops (idempotent by op ID). Because the log — not memory — is the source of truth, no acknowledged edit is lost.

🐘

The 500-editor document

Fan-out per op is O(editors), so a popular doc becomes quadratic in traffic. Mitigations: batch ops into ~50 ms frames, coalesce cursor updates, cap concurrent editors and put the rest in read-only mode, and split huge documents into independently synced sections.

🧹

Compaction

Op logs grow forever. Snapshot regularly, then trim ops older than the retention window (keeping periodic checkpoints for history). For CRDTs, garbage-collect tombstones once every replica has seen the delete.

🌍

Global users

A shared session means someone is always far away. Put the session in the region of the document's primary audience, use edge WebSocket termination to shorten the TLS path, and rely on optimistic local application to hide the round trip.

🧪

Testing convergence

Convergence is a property: for any random interleaving of operations, all replicas end identical. That's exactly what property-based testing and deterministic simulation are for (Chapter 19) — most real CRDT/OT bugs are found by randomized testing, not examples.

⚠️
Common mistakes
  • Merging by index. Concurrent edits shift positions; you need transformation or stable identifiers.
  • Waiting for the server before showing a keystroke. Apply locally first — the network round trip must never be in the typing path.
  • Persisting presence and cursors. They're ephemeral and high-volume; broadcast and drop them, never write them to durable storage.
🎤
Interview drill

Reason: Why can't you just use last-write-wins on the document text?

How a strong answer sounds
Because “the document” isn't a value, it's a sequence of positions that concurrent edits both modify. LWW throws away one user's entire set of changes — they watch their paragraph vanish. The unit of conflict has to be the individual operation (OT) or the individual character identifier (CRDT), and the merge must preserve both users' intentions rather than picking a winner.

Operate: The document session process crashes with 40 people editing. What do the users see?

How a strong answer sounds
A brief disconnect. Each client keeps its unacknowledged operations locally, so nothing typed is lost. A new session process takes ownership (via a lease), loads the latest snapshot plus subsequent ops from the durable log, and clients reconnect with backoff and jitter, resending pending ops tagged with the last revision they saw — the server transforms them against anything committed since. The log, not the process memory, is the source of truth.

🧠 Key takeaways

  • Positional edits can't be merged by index; you need either transformation or stable identifiers.
  • OT keeps documents small but needs a central ordering server and subtle transform functions.
  • CRDTs merge commutatively without a server, at the cost of per-character metadata and tombstones.
  • Apply edits locally first; the network round trip must never be in the typing path.
  • One session process owns a document: it serializes ops, persists to an append-only log, then broadcasts.
  • Snapshots make document loading fast; the op log powers history and recovery.
  • Presence and cursors are ephemeral and throttled — never persisted, first to be dropped under load.
  • Shard by document, fail over via the log, and treat very popular documents as a special case.

Check your understanding

Two users insert text at index 6 of the same sentence while briefly disconnected. Why can't the server just apply both inserts at index 6?

Each op was written against a document version that no longer exists. OT transforms the index; CRDTs avoid indexes entirely.

What's the main architectural difference between OT and CRDT?

That ordering requirement is exactly why Google Docs runs a central session and Figma/Yjs-style apps don't have to.

Why do CRDTs keep tombstones for deleted characters?

Removing the identifier outright would lose the anchor that other replicas' operations refer to, breaking convergence.

Opening a heavily-edited document takes 12 seconds because the server replays 400,000 ops. Fix?

Same pattern as event sourcing (Chapter 17): snapshots cap replay cost while the log stays the source of truth.

A document with 300 simultaneous editors starts lagging badly. What's the first thing to do?

Fan-out is O(editors) per op, and cursors usually dominate. Batching and shedding presence traffic buys the most, fastest.
