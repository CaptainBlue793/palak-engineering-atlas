IDs, Outbox, CDC & Distributed Locks

Sooner or later your data lives in more than one place: a database and a queue, a cache, a search index, another service. At that point, a few small-looking problems cause most of the bugs in production. How do you give things unique IDs when many machines create them at once? How do you update two systems without losing one of the writes? How do you make sure only one worker does a job? This chapter is the toolkit for all three.

  • Create unique IDs on many machines that also sort by creation time (Snowflake, UUIDv7)
  • Understand why writing to two systems separately ("dual writes") loses data — and fix it with the transactional outbox
  • Use change data capture (turning database changes into events) to keep caches, search and analytics up to date
  • Build idempotent consumers (safe to receive the same message twice) with an inbox/dedupe table
  • Store history as a list of events with event sourcing, and split reads from writes with CQRS
  • Use leases (locks that expire) and fencing tokens so distributed locks are actually safe

Generating unique IDs at scale

A single database hands out 1, 2, 3… with an auto-increment column. That breaks once you shard the database (split it across machines) or create records in 40 different services: two shards will both produce ID 1001. You need IDs that are unique without machines having to check with each other. Ideally they should also be roughly sorted by time. Then new rows always go at the end of the B-tree index (the sorted structure databases use to find rows), and “newest first” is a cheap sort.

How a Snowflake ID is built. It packs three facts into one 64-bit number: when (a timestamp in milliseconds), who (which datacenter and worker made it) and which one (a counter within that millisecond). The field sizes explain the limits you'll see below:

  • 41 bits of time can count 241 ≈ 2.2 trillion milliseconds, which is about 69 years from a chosen start date (the "epoch", often the year the system launched).
  • 5 + 5 bits of datacenter and worker give 32 × 32 = 1,024 machines that can each make IDs on their own. Two machines can never clash, because their "who" bits differ.
  • 12 bits of sequence count 0 to 4,095 within one millisecond on one worker. If a worker needs a 4,097th ID in the same millisecond, it waits for the next millisecond.

Because the timestamp sits in the highest bits, a bigger number always means "made later" (give or take small clock differences between machines). That's what makes these IDs sort by time.

Which approach to pick: a single database with modest volume can keep using auto-increment internally. If you're sharded or have many services creating records, and 128-bit keys are fine, UUIDv7 is the easiest choice because it needs no setup. Choose Snowflake when you want compact 64-bit IDs (smaller indexes, fits in a BIGINT) and can assign each worker a unique number. Avoid UUIDv4 as a primary key on large, write-heavy tables because of the random-insert problem in the table above.

The dual-write problem

Here is a very common piece of code. Save an order to the database, then publish an OrderPlaced message to Kafka (a message broker) so email, analytics and shipping can react. It looks harmless. It's broken.

def place_order(order):
    db.insert(order)                 # ✓ committed
    # 💥 process crashes / deploy kills pod / network blips here
    kafka.publish("OrderPlaced", order)  # never happens → no email, no shipping

Swap the order and it breaks the other way. The event is published, then the database insert fails — and shipping sends a package for an order that doesn't exist. You can't put a Postgres commit and a Kafka publish inside one all-or-nothing (ACID) transaction. Two-phase commit (2PC) across them is slow and poorly supported (Chapter 13). The fix is to write to only one place.

The transactional outbox

Write the business row and the event into the same database, in the same transaction. The event goes into an extra table called the outbox. Either both rows are saved or neither is. A separate relay process then reads the outbox and publishes each event to the broker, retrying until it succeeds. Think of it like a mail tray: you drop the letter in the tray as part of your work, and the mail carrier picks it up later.

BEGIN;
  INSERT INTO orders (id, user_id, total, status) VALUES (7321, 42, 89.00, 'PLACED');
  INSERT INTO outbox (event_id, aggregate_id, type, payload, created_at)
       VALUES ('evt_01J…', 7321, 'OrderPlaced', '{"total":89.00,…}', now());
COMMIT;   -- atomic: the order and its event exist together, or not at all

🔁 Relay option A: polling publisher

A worker keeps running SELECT … FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED. It publishes the rows it gets, marks them as sent, and deletes old rows. Simple — but checking on a timer adds delay and extra database load.

📜 Relay option B: log tailing (CDC)

Debezium reads new outbox rows straight from the database's write-ahead log (the internal record of every change, written before the change is applied) and publishes them. No polling, low delay, and events keep their commit order. Rows can even be deleted right after insert — the log has already captured them.

Why the relay can send duplicates. The relay publishes an event, then marks the row as sent. If it crashes between those two steps, it restarts, sees the row still unsent, and publishes it again. There's no way to make "publish to Kafka" and "update the outbox row" a single atomic step, which is the dual-write problem in miniature. The difference is that this failure gives a duplicate, never a loss, and duplicates are easy to handle with the idempotent consumers described below. That's why every outbox event carries a unique event_id.

Choosing a relay: start with polling if you have modest volume (hundreds of events a second) and want no extra infrastructure; a 100–500 ms polling interval is usually fine. Move to log tailing when you need low delay, high volume, or strict ordering, and you're ready to run Debezium and Kafka Connect.

Change data capture (CDC)

Every serious database already keeps an ordered log of every change, so it can copy data to replicas: Postgres's WAL, MySQL's binlog, MongoDB's oplog. CDC (change data capture) tools read that log just like a replica would. They turn each committed insert, update or delete into an event. Your application doesn't need to publish anything at all.

Why is this useful? Think of a product price that must show up correctly in the database, the cache, the search index and the analytics warehouse. Without CDC, every piece of code that changes a price must remember to update all four, and the one forgotten place (a nightly admin script, a manual SQL fix) leaves them out of step. With CDC, any change that commits to the database, from any source, flows out to all four automatically.

CDC or outbox? Use raw CDC when the consumers are your own copies of the same data (cache, search index, warehouse) and matching the table layout is fine. Use an outbox when other teams consume the events: you choose a clean, stable event like OrderPlaced instead of exposing your internal columns, so you can change your tables without breaking them. Many systems use both: CDC for internal copies, and CDC on the outbox table to publish business events.

One write, many derived systemsStep-through
  1. UPDATE products SET price = 79 WHERE id = 5. The request code has no Kafka client, no code to clear the cache, and no code to update search.
  2. On commit, Postgres adds the change to the end of its write-ahead log. Each entry gets an LSN (log sequence number) that only ever goes up. Committed changes appear in the order they were committed.
  3. Debezium holds a replication slot (a bookmark in the log that Postgres keeps for it). It turns the change into {op: "u", before: {price: 99}, after: {price: 79}, lsn: …}. It saves the last LSN it handled, so after a restart it picks up exactly where it left off.
  4. Events are keyed by the row's primary key. So all changes to product 5 land in the same partition, and changes to each row stay in order (Chapter 14).
  5. Consumers clear the cache entry, update the search index, add a row to the data warehouse, and update other services' local copies — each at its own pace. If you add a new consumer next year, it can replay events from the beginning to fill in the past.
⚠️
CDC gotchas

Schema changes flow downstream to every consumer. Use a schema registry and make only backward-compatible changes. CDC on raw tables also ties consumers to your internal table layout. Publishing hand-picked business events through an outbox table avoids that. And if a replication slot is abandoned, Postgres keeps its WAL forever, until the disk fills up — so monitor how far behind each slot is.

Idempotent consumers

Outbox relays, CDC connectors and Kafka consumers all deliver at least once. After a crash or a rebalance (consumers reshuffling their work), the same event will arrive again. You get "exactly once" effects by making the consumer idempotent: processing an event twice has the same result as processing it once (Chapter 3's idempotency, applied to events).

📥

Inbox / dedupe table

In the same transaction as the real work, run INSERT INTO processed_events(event_id). If the insert fails because the ID already exists, the event was “already handled — skip it”.

🧮

Naturally idempotent writes

Prefer SET status = 'SHIPPED' or upserts (insert-or-update) over balance = balance + 10. Setting a value twice is harmless; adding twice is not.

🔢

Version checks

Put a version number or LSN in each event, and ignore anything older than what you've already stored. This handles duplicates and events that arrive out of order.

A small trace shows why the version check matters. The search indexer keeps product 5 at version 7, price $99. Then:

  1. Event {id: 5, version: 9, price: 79} arrives. 9 > 7, so apply it. Stored: v9, $79.
  2. A delayed event {id: 5, version: 8, price: 85} arrives late. 8 < 9, so ignore it. Without the check, the price would wrongly go back to $85.
  3. The v9 event is redelivered after a rebalance. 9 is not greater than 9, so ignore it. The duplicate is harmless.

A dedupe table alone would catch step 3 but not step 2; a version check catches both. Use the dedupe table when events are actions ("send this email") and the version check when events carry the new state of something.

Event sourcing

Most systems store the current state and overwrite it: balance = 70. Event sourcing instead stores the list of things that happened — Opened, Deposited 100, Withdrew 30 — and treats that list as the source of truth. You get the current state by replaying the events in order. Think of a bank statement: the balance is just the sum of every line. It's how ledgers, version control and databases' own logs work.

Two words matter here. A command is a request that might be refused: "withdraw $30". An event is a fact that already happened: "$30 was withdrawn". The system checks each command against the current state (is there enough money?), and only if it passes does it append an event. Events are never edited or deleted; a mistake is fixed by appending a new event, like a correcting line on a bank statement.

Snapshots keep replays fast. An account with 50,000 events would need 50,000 steps to rebuild. If you save a snapshot every 1,000 events ("balance was $4,210 after event 49,000"), loading it takes one read plus at most 1,000 replayed events.

Why teams choose it
  • A full audit trail comes built in — required in finance and healthcare
  • Time travel: rebuild the state at any past moment to debug
  • Build brand-new views of the data later by replaying history
  • Events feed other services naturally
What it costs
  • Replays get slow → you need snapshots
  • Old events are kept forever → you must version event formats and convert old ones when reading ("upcasting")
  • Deleting personal data (GDPR) is hard in a log you never change → crypto-shredding (encrypt each person's data with their own key, then delete the key)
  • Querying current state needs projections (pre-built views) → CQRS, and views that lag slightly behind (eventual consistency)

CQRS: separate models for writes and reads

Command Query Responsibility Segregation (CQRS) uses separate models for writing and reading. One model handles commands: it checks the rules that must always hold (invariants) and writes. One or more other models are built just for queries. The write side is normalized (no duplicated data) and transactional. The read sides are denormalized views, built from change events and shaped for fast reads — a search index, a Redis leaderboard, a pre-joined “order summary” table.

CQRS with projectionsStep-through
  1. PlaceOrder goes to the write model. It checks stock, credit limits and other rules in one transaction.
  2. If that succeeds, it sends out an OrderPlaced event (either as an event-sourced fact, or through the outbox).
  3. Projectors read the events and update each read model, each shaped exactly for the screens that use it. Reads and writes can now scale separately.
  4. Queries never touch the write model. The trade-off: views lag behind by milliseconds to seconds. So a user might think “I just placed an order but don't see it”. Fix that with read-your-writes tricks: return the new state in the command's response, or have the UI wait until the view has caught up to that command's version.
🧯

Don't use event sourcing + CQRS by default. They shine when there are complex business rules, audit requirements and many different ways to read the data. For a simple settings page that just creates, reads, updates and deletes (CRUD), they add a lot of machinery for nothing. CQRS without event sourcing — a normal database plus read views fed by CDC — is a much lighter and very common middle ground.

Distributed locks, leases & fencing tokens

Sometimes exactly one worker must do something: run the nightly billing job, process a given file, or act as leader. A distributed lock is a lock shared across many machines. It is usually a lease: a lock with a timeout, like a hotel key card that stops working at checkout. That way a crashed holder doesn't block everyone forever. The classic Redis version:

SET lock:billing worker-7:uuid NX PX 30000   # acquire only if absent, auto-expire in 30s
# … do work …
# release only if we still own it (atomic check-and-delete via Lua)
if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) end

Each part of that has a reason. NX means "only set it if it doesn't already exist", so only one worker can win. PX 30000 makes the key vanish after 30 seconds, so a crashed worker's lock frees itself. The value worker-7:uuid is a random ID unique to this attempt, and the release script deletes the key only if it still holds that value. Why check? Suppose worker 7 runs for 35 seconds. Its lock expired at 30 s and worker 9 took it. If worker 7 then blindly ran DEL, it would delete worker 9's lock, and a third worker could jump in.

But timeouts create a nasty problem. A process can pause for longer than the lease — for example, during a garbage-collection pause that freezes the whole program, a VM being moved to another host, or waiting for memory that was swapped to disk. Then it wakes up still believing it holds the lock.

You might think "just check the lease before each write". It doesn't help: the pause can happen right after the check and right before the write. The worker checks ("I still have 5 seconds left"), freezes for 15 seconds, then writes. No amount of checking inside the worker closes that gap. The fix has to be on the other side, in the storage being written to, which is what fencing tokens do.

The zombie lock holder — and how fencing tokens stop itStep-through
  1. The lock service grants a 10-second lease and returns a fencing token: a number that goes up every time the lock is granted (etcd's revision, ZooKeeper's zxid).
  2. A long garbage-collection (GC) pause stops Worker A for 15 seconds. It can't renew the lease, and it has no idea time is passing.
  3. After 10 s the lease expires. Worker B gets the lock, fairly, with token 34.
  4. B writes to storage, passing its token. Storage records “highest token seen = 34”.
  5. A carries on mid-task, still thinking it holds the lock, and writes with token 33. Without fencing, this quietly overwrites B's work. Two “exclusive” holders means corrupted data.
  6. With fencing, storage sees 33 < 34 and rejects the write. Safety no longer depends on clocks or pauses. The protected resource itself must do this check — e.g. UPDATE … WHERE fencing_token < :token.

⚡ Locks for efficiency

If two workers sometimes doing the same job only wastes a little effort (say, a duplicate request to pre-fill a cache), a single Redis SET NX PX lock is fine.

🛡️ Locks for correctness

If running twice would corrupt data or charge someone twice, use a store built on consensus — where several machines must agree before anything changes (etcd, ZooKeeper, Consul) — plus fencing tokens. Better still, avoid the lock entirely: use database constraints, conditional writes (compare-and-set: "update only if the value is still X") or idempotency keys.

⚠️
Common mistakes
  • Dual writes. Writing to the database and then publishing to a broker will lose events sooner or later. Use the outbox.
  • Assuming a lock makes you safe. A process can pause past the end of its lease. Without a fencing token, the old “exclusive” holder can still write.
  • Event sourcing everything. It's powerful where audits matter, but far too much machinery for a settings page.
🎤
Interview drill

Design: Keep a search index in sync with Postgres, with no lost updates and no dual writes.

How a strong answer sounds
There are two good options. First, CDC: Debezium reads the WAL and publishes row changes to Kafka, and the indexer reads them and upserts into search. Second, the outbox: the application writes a hand-picked business event in the same transaction as the row change, and a relay publishes it. CDC means less code, but it ties consumers to your table layout. The outbox gives you a stable contract. Either way, the indexer must be idempotent and must handle out-of-order events with a version check. And you must always be able to rebuild the whole index from the database.

Reason: Two workers both think they hold the lock for a job. How does your storage layer protect itself?

How a strong answer sounds
The lock service hands out a fencing token with each grant, and the number only ever goes up. Every write to the protected resource includes the token. The resource rejects any write whose token is lower than the highest it has seen — UPDATE … WHERE fencing_token < :token. That makes safety independent of clocks, GC pauses and lease timeouts, none of which can ever be fully relied on by themselves.

🧠 Key takeaways

  • Snowflake IDs and UUIDv7 are unique without machines checking with each other, and they sort by time, which keeps indexes healthy.
  • Writing to a database and a broker separately (dual write) will sooner or later lose events, or send events for things that never happened.
  • The transactional outbox saves the event in the same transaction as the data; a relay then publishes it at least once.
  • CDC turns the database log into an event stream to feed caches, search, warehouses and other services.
  • At-least-once delivery needs idempotent consumers: dedupe tables, upserts or version checks.
  • Event sourcing stores facts and works out the state from them; CQRS separates the write side (which enforces the rules) from views built for fast reads.
  • Distributed locks are leases that can expire while the holder is paused — use fencing tokens when correctness matters.

Check your understanding

Why are random UUIDv4 primary keys often slower to insert than Snowflake or UUIDv7 IDs?

Time-ordered IDs are always added near the end of the index. That keeps the busy pages in memory and page splits rare.

A service commits an order to Postgres and then publishes to Kafka. Sometimes customers never get confirmation emails. Best fix?

The outbox saves the data change and the event together — both or neither. Retries can't help if the process crashes between the two writes.

An outbox relay publishes an event, then crashes before marking it sent. What happens, and what must consumers do?

Outbox relays deliver at least once. Skip repeats by event ID (an inbox table), or write handlers so running them twice is harmless.

In an event-sourced system, how do you get current state quickly once an account has 2 million events?

Snapshots limit how much you must replay, while still keeping the full history for audits and new views.

A worker holding a Redis lock pauses for 40 s (lease 30 s). Another worker takes the lock. What prevents the first worker's late write from corrupting data?

A pause can outlast any timeout (TTL). Fencing tokens let the resource reject writes from a holder whose lease has already passed to someone else.
