IDs, Outbox, CDC & Distributed Locks

Once data lives in more than one place — a database and a queue, a cache, a search index, another service — a handful of small-looking problems become the source of most production bugs. How do you name things uniquely without coordination? How do you update two systems without losing one of the writes? How do you make sure only one worker does a job? This chapter is the toolkit.

  • Generate unique, sortable IDs across many machines (Snowflake, UUIDv7)
  • Understand why dual writes lose data — and fix it with the transactional outbox
  • Use change data capture to feed caches, search and analytics
  • Build idempotent consumers with an inbox/dedupe table
  • Model state as events with event sourcing and CQRS
  • Use leases and fencing tokens so distributed locks are actually safe

Generating unique IDs at scale

A single database hands out 1, 2, 3… with an auto-increment column. Shard that database, or create records in 40 services, and auto-increment breaks: two shards both produce ID 1001. You need IDs that are unique without coordination, and ideally roughly time-sortable (so B-tree inserts stay appended at the end and “newest first” is a cheap sort).

The dual-write problem

A very common piece of code: save an order to the database, then publish OrderPlaced to Kafka so email, analytics and shipping can react. It looks innocent. It's broken.

def place_order(order):
    db.insert(order)                 # ✓ committed
    # 💥 process crashes / deploy kills pod / network blips here
    kafka.publish("OrderPlaced", order)  # never happens → no email, no shipping

Flip the order and it's broken the other way: the event is published, then the DB insert fails, and shipping sends a package for an order that doesn't exist. You can't wrap a Postgres commit and a Kafka publish in one ACID transaction, and 2PC across them is slow and poorly supported (Chapter 13). The fix is to write only once.

The transactional outbox

Write the business row and the event into the same database, in the same local transaction. Either both commit or neither does. A separate relay process then reads the outbox and publishes to the broker, retrying until it succeeds.

BEGIN;
  INSERT INTO orders (id, user_id, total, status) VALUES (7321, 42, 89.00, 'PLACED');
  INSERT INTO outbox (event_id, aggregate_id, type, payload, created_at)
       VALUES ('evt_01J…', 7321, 'OrderPlaced', '{"total":89.00,…}', now());
COMMIT;   -- atomic: the order and its event exist together, or not at all

🔁 Relay option A: polling publisher

A worker runs SELECT … FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED, publishes, marks rows sent, and deletes old rows. Simple; adds polling latency and DB load.

📜 Relay option B: log tailing (CDC)

Debezium reads new outbox rows straight from the database's write-ahead log and publishes them. No polling, low latency, preserves commit order. Rows can be deleted immediately after insert — the log already captured them.

Change data capture (CDC)

Every serious database already keeps an ordered log of every change for replication: Postgres's WAL, MySQL's binlog, MongoDB's oplog. CDC tools subscribe to that log like a replica would and turn each committed insert/update/delete into an event. Your application doesn't need to publish anything at all.

One write, many derived systemsStep-through
  1. UPDATE products SET price = 79 WHERE id = 5. No Kafka client, no cache-invalidation code, no search sync code in the request path.
  2. On commit, Postgres appends the change to its write-ahead log with a monotonically increasing LSN (log sequence number). Committed changes appear in commit order.
  3. Debezium holds a replication slot and decodes the change into {op: "u", before: {price: 99}, after: {price: 79}, lsn: …}. It checkpoints its LSN, so after a restart it resumes exactly where it left off.
  4. Events are keyed by primary key, so all changes to product 5 land in the same partition — per-row ordering is preserved (Chapter 14).
  5. Consumers invalidate the cache, re-index the product, append to the warehouse, and update other services' local copies — each at its own pace. Add a new consumer next year and replay from the beginning to backfill.
⚠️
CDC gotchas

Schema changes flow downstream — use a schema registry and compatible evolution. Raw table CDC couples consumers to your internal schema; publishing curated domain events through an outbox table avoids that. And an abandoned replication slot makes Postgres retain WAL forever until the disk fills — monitor slot lag.

Idempotent consumers

Outbox relays, CDC connectors and Kafka consumers all deliver at least once. After a crash or rebalance, the same event will arrive again. Exactly-once effects come from making the consumer idempotent (Chapter 3's idempotency, applied to events).

📥

Inbox / dedupe table

In the same transaction as the side effect: INSERT INTO processed_events(event_id). A unique-key violation means “already handled — skip”.

🧮

Naturally idempotent writes

Prefer SET status = 'SHIPPED' or upserts over balance = balance + 10. Applying “set” twice is harmless.

🔢

Version checks

Carry a version or LSN in each event and ignore anything older than what you've stored — handles duplicates and out-of-order delivery.

Event sourcing

Most systems store current state and overwrite it: balance = 70. Event sourcing stores the sequence of facts that happened — Opened, Deposited 100, Withdrew 30 — as the source of truth. Current state is derived by replaying events. It's how ledgers, version control and databases' own logs work.

Why teams choose it
  • Complete audit trail by construction — required in finance and healthcare
  • Time travel: reconstruct state at any moment to debug
  • Build brand-new read models later by replaying history
  • Events feed other services naturally
What it costs
  • Replays get slow → need snapshots
  • Event schemas are forever → versioning and upcasting
  • Deleting personal data (GDPR) is hard in an immutable log → crypto-shredding
  • Querying current state requires projections → CQRS, eventual consistency

CQRS: separate models for writes and reads

Command Query Responsibility Segregation splits the model that handles commands (validate, enforce invariants, write) from one or more models optimized for queries. The write side is normalized and transactional; read sides are denormalized views built from change events — a search index, a Redis leaderboard, a pre-joined “order summary” table.

CQRS with projectionsStep-through
  1. PlaceOrder goes to the write model, which checks stock, credit limits and other invariants in one transaction.
  2. On success it emits OrderPlaced (event-sourced, or via the outbox).
  3. Projectors consume events and update each read model, shaped exactly for its screens. Reads and writes scale independently.
  4. Queries never touch the write model. The trade-off: views lag by milliseconds to seconds. Handle “I just placed an order but don't see it” with read-your-writes tricks: return the new state in the command response, or have the UI wait for the projection to reach the command's version.
🧯

Don't reach for event sourcing + CQRS by default. They shine in domains with rich business rules, audit needs and many read shapes. For a CRUD settings page, they add a lot of machinery for nothing. CQRS without event sourcing (a DB plus CDC-fed read views) is a much lighter, very common middle ground.

Distributed locks, leases & fencing tokens

Sometimes exactly one worker must do something: run the nightly billing job, process a given file, act as leader. A distributed lock is usually a lease: a lock with a timeout, so a crashed holder doesn't block everyone forever. The classic Redis version:

SET lock:billing worker-7:uuid NX PX 30000   # acquire only if absent, auto-expire in 30s
# … do work …
# release only if we still own it (atomic check-and-delete via Lua)
if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) end

But timeouts create a nasty failure mode. A process can pause for longer than the lease — stop-the-world garbage collection, VM migration, a page fault on a swapped-out process — then wake up still believing it holds the lock.

The zombie lock holder — and how fencing tokens stop itStep-through
  1. The lock service grants a 10-second lease and returns a fencing token: a number that increases every time the lock is granted (etcd's revision, ZooKeeper's zxid).
  2. A long GC pause stops Worker A for 15 seconds. It can't renew the lease, and it has no idea time is passing.
  3. After 10 s the lease expires. Worker B acquires the lock legitimately with token 34.
  4. B writes to storage, passing its token. Storage records “highest token seen = 34”.
  5. A resumes mid-task, still thinking it holds the lock, and writes with token 33. Without fencing, this silently overwrites B's work — two “exclusive” holders, corrupted data.
  6. With fencing, storage checks 33 < 34 and rejects the write. Safety no longer depends on clocks or pauses. The protected resource itself must enforce this — e.g. UPDATE … WHERE fencing_token < :token.

⚡ Locks for efficiency

If two workers occasionally doing the same job is merely wasteful (sending a duplicate cache-warming request), a single Redis SET NX PX lock is fine.

🛡️ Locks for correctness

If double execution corrupts data or double-charges money, use a consensus-backed store (etcd, ZooKeeper, Consul) and fencing tokens. Better still, avoid the lock entirely with database constraints, conditional writes (compare-and-set) or idempotency keys.

⚠️
Common mistakes
  • Dual writes. Writing to the database and then publishing to a broker will eventually lose events. Use the outbox.
  • Assuming a lock makes you safe. A process can pause past its lease; without a fencing token the “exclusive” holder can still write.
  • Event sourcing everything. It's powerful for audit-heavy domains and heavy machinery for a settings page.

Interview drill

Design: Keep a search index in sync with Postgres, with no lost updates and no dual writes.

How a strong answer sounds
Two good options. CDC: Debezium reads the WAL and publishes row changes to Kafka; the indexer consumes and upserts. Or the outbox: the application writes a curated domain event in the same transaction as the row change, and a relay publishes it. CDC is less code but couples consumers to your table schema; the outbox gives you a stable contract. Either way the indexer must be idempotent and handle out-of-order events with a version check, and a full rebuild from the database must always be possible.

Reason: Two workers both think they hold the lock for a job. How does your storage layer protect itself?

How a strong answer sounds
The lock service hands out a monotonically increasing fencing token with each grant. Every write to the protected resource carries the token, and the resource rejects any write whose token is lower than the highest it has seen — UPDATE … WHERE fencing_token < :token. That makes safety independent of clocks, GC pauses and lease timeouts, which can never be made reliable on their own.

🧠 Key takeaways

  • Snowflake IDs and UUIDv7 are unique without coordination and time-sortable, which keeps indexes healthy.
  • Writing to a database and a broker separately (dual write) will eventually lose or invent events.
  • The transactional outbox writes the event in the same local transaction; a relay publishes it at least once.
  • CDC turns the database log into an event stream to feed caches, search, warehouses and other services.
  • At-least-once delivery requires idempotent consumers: dedupe tables, upserts or version checks.
  • Event sourcing stores facts and derives state; CQRS separates write invariants from read-optimized views.
  • Distributed locks are leases that can expire under a paused holder — use fencing tokens for correctness.

Check your understanding

Why are random UUIDv4 primary keys often slower to insert than Snowflake or UUIDv7 IDs?

Time-ordered IDs append near the right edge of the index, keeping hot pages in memory and splits rare.

A service commits an order to Postgres and then publishes to Kafka. Sometimes customers never get confirmation emails. Best fix?

The outbox makes the state change and the event atomic. Retries can't help if the process crashes between the two writes.

An outbox relay publishes an event, then crashes before marking it sent. What happens, and what must consumers do?

Outbox relays provide at-least-once delivery. Dedupe by event ID (inbox table) or make handlers naturally idempotent.

In an event-sourced system, how do you get current state quickly once an account has 2 million events?

Snapshots cap replay cost while keeping the full history for audits and new projections.

A worker holding a Redis lock pauses for 40 s (lease 30 s). Another worker takes the lock. What prevents the first worker's late write from corrupting data?

Any TTL can be exceeded by a pause. Fencing tokens let the resource reject writes from holders whose lease was superseded.
