Design an LLM Chat Platform

ChatGPT, Claude, Gemini and every “AI assistant” inside a product have the same basic shape. A chat API sits in front of a very expensive tier of GPU servers. Those servers are limited by memory, and they are stateful: each one holds data about the conversations it is running. Everything you've learned still applies — gateways, queues, caching, streaming, multi-region. There's one new constraint: a GPU can only hold so many conversations at once, and every token (a word or piece of a word) you generate costs real money.

  • Estimate how many GPUs you need from tokens per second
  • Understand the two phases — prefill and decode — and KV cache memory
  • Compare static and continuous batching
  • Stream tokens to users as they're generated, and handle users disconnecting
  • Base answers on real documents (RAG) and use tools safely
  • Control cost with caching, routing and quotas

STEP 1 / 7

Requirements

Separate three targets: waiting for the first token, time between later tokens, and time to finish the answer. A 400-token answer at 30 tokens/second takes about 13.3 seconds after generation starts. A fast first word does not guarantee smooth delivery. Give streams an overall deadline and a cancellation path, and limit how long a request can wait in the admission queue.

🛠️ Functional

✓Multi-turn chat with streamed responses; stop/regenerate; conversation history
✓Several models (fast/cheap and slow/smart), attachments and images
✓Answers based on the user's own documents (RAG — retrieval-augmented generation) and tool/function calls
✓Safety filtering, usage quotas, and an API for developers

📏 Non-functional

✓First token appears in < 1 s; then at least 30 tokens/s (faster than people read)
✓Cost-efficient: GPUs are most of the bill, so keeping them busy is what matters
✓Under heavy load, slow down gracefully (queue, smaller model) instead of showing errors
✓Privacy: conversations are sensitive; keep them only as long as allowed, and keep customers' data separate
STEP 2 / 7

Estimate the scale

300 million messages × 400 tokens = 120 billion output tokens/day. Divide by 86,400 to get about 1.39 million tokens/second. At 3,000 tokens/second per node, the average requires about 463 nodes, explaining the rounded 500 figure. A 2.5-times peak requires about 1,158 nodes at that same measured throughput, before spare capacity, prefill work and failover.

At 300 million ÷ 86,400 ≈ 3,472 messages/second and 13.3 seconds of generation per message, average active decoding is roughly 46,300 requests. Check that those requests' KV caches fit as well as checking tokens/second. Measure throughput at the real context lengths and output-speed target; maximum batch throughput may violate the experience each user needs.

STEP 3 / 7

How inference actually works

For an example with 32 layers, 8 key/value heads, 128 numbers per head and 2 bytes per number, each token needs 2 × 32 × 8 × 128 × 2 = 131,072 bytes of KV state. At 8,192 tokens that is 1 GiB per request, before allocator overhead. Grouped-query attention reduces the number of key/value heads; reducing weight precision does not automatically reduce KV precision.

The planner below uses illustrative cache sizes and assumes only part of the MoE expert set resides in the displayed GPU group. A complete deployment must still make every required expert available across its groups or pay to load it. Do not size a standalone MoE replica from active parameters alone. Add temporary buffers and check the busiest individual GPU, not just total memory.

📥

Prefill (prompt processing)

The model reads the whole prompt at once, in parallel, in one heavy burst of computation. This produces the KV cache — the model's working memory for that conversation. The longer the prompt, the longer this takes. It's most of your time to first token (TTFT).

🔁

Decode (token by token)

After that, the reply is generated one token at a time. Each token needs a full pass that reads all the model's weights from GPU memory. So the speed limit is how fast memory can be read (memory-bandwidth-bound), not how fast the GPU can calculate. That's why adding more users to the same pass is nearly free — and why a GPU serving one user alone is mostly wasted.

🧠
The KV cache is the real capacity limit

Every active conversation keeps a KV cache, and its size grows with the length of that conversation's context. The model weights take their share of GPU memory first. Long contexts and many simultaneous users then fight over what's left. Planning capacity for LLM serving is mostly doing KV-cache arithmetic.

STEP 4 / 7

Deep dive: batching is everything

Batching shares weight reads, but additional users still require computation and KV-cache reads. As batches or contexts grow, another bottleneck can take over and each token step can slow down. Choose the batch and prefill-chunk limits from both throughput and token-gap measurements. Use fair scheduling so a stream of short requests cannot starve a long request indefinitely.

Because decode is limited by memory reads, running 32 conversations in one pass costs barely more than running one. So how you group requests (batching) matters enormously.

  • Static batching collects a batch, runs it until every reply is finished, then starts the next. If one reply is long, most slots sit idle waiting for it.
  • Continuous batching (vLLM, TensorRT-LLM, TGI) lets a waiting request in the moment any slot frees up, and mixes prefill and decode work together.

Think of a bus that only leaves when everyone on the previous trip has got off, versus a taxi rank where each free car takes the next person in line.

📄

Prefix caching

The start of many prompts is identical: long system prompts, tool definitions, earlier turns of the same chat. Cache the KV blocks for that shared beginning (PagedAttention-style) and reuse them. This cuts prefill work and TTFT dramatically for long chats and RAG prompts.

🔮

Speculative decoding

A small, fast “draft” model guesses the next several tokens. The big model then checks all of them in a single pass. Every correct guess is almost free. The result is typically 1.5–3× faster decoding, with exactly the same output.

✂️

Quantization & parallelism

Quantization stores weights in 8 or 4 bits instead of 16. That uses less memory and runs faster, at a small cost in quality. Models too big for one GPU are split up: tensor parallelism splits each layer across the GPUs in a node, and pipeline parallelism puts different layers on different nodes.

STEP 5 / 7

End-to-end architecture

Store stream events with a request ID and sequence number if the product promises resumable delivery. Reconnecting can then replay already-produced events without launching another generation. If the model process died, replaying text does not restore its KV state; a new generation may produce a different continuation. Report that boundary clearly and deduplicate any completed tool actions separately.

One chat message, start to finishStep-through
  1. Check who the user is. Check their plan's quota in tokens, not just requests — a 100K-token prompt costs 100× a short one. Apply rate limits per user and per organization, and pick which model tier to use.
  2. Fetch recent turns from the conversation store. That's just a normal database — chat history is ordinary create/read/update/delete data. Long histories are cut down or summarized to fit the model's context window (the most text it can read at once). Attachments are fetched from object storage.
  3. For questions about the user's own data, run hybrid retrieval: search by meaning (vectors) and by keywords (BM25) together (Chapter 10). Re-rank the top results and add the best chunks to the prompt, with citations. Treat retrieved text as untrusted input — never let it quietly slip instructions to the model.
  4. Before any GPU time is spent, classifiers screen the request for policy violations and obvious prompt-injection tricks.
  5. The router picks a model replica and region based on queue length, whether the prefix is already cached there, and priority (live chats go before batch API jobs). When overloaded, it queues requests instead of failing them, and can switch to a smaller model.
  6. The GPU builds the KV cache (reusing any cached prefix), then produces tokens one by one as part of the continuous batch. Each token is sent back through the stack as a server-sent event (SSE — a one-way stream from server to browser) the moment it exists.
  7. Output moderation checks the reply while it streams, a small piece at a time, so a violation can stop generation mid-answer. The client shows text as it arrives. That's why the wait users feel is the time to first token, not the total time.
  8. Save the message. Count input and output tokens for billing. Log latency and errors. Record feedback (👍/👎, regenerations) for evaluating quality. Bill and cache using exact token counts — not characters.

STEP 6 / 7

Deep dive: cost control

Distinguish an answer-cache hit from a prefix-cache hit. A valid cached answer can avoid generation; a cached prefix only reduces prompt processing, while new output still needs decoding. The calculator treats its cache slider as avoided output work, so interpret it as reusable answers for that calculation. Apply tenant, permission, model and freshness checks before reusing an answer.

For unit cost, compare the same time period and count actual delivered output tokens. If a fleet costs $720,000/month and delivers 100 billion output tokens/day for 30 days, cost is $720,000 ÷ 3,000,000 million tokens = $0.24 per million. A model-size-weighted workload is useful for sizing but is not the billed token count. Keep input processing and other platform costs separate when explaining the result.

🪜

Model cascade

Answer easy questions with a small, fast model. Pass a question up to the big model only when a classifier (or the small model's own uncertainty) says it's hard. Most chat messages are easy.

📦

Batch tier

Offer a cheaper API for jobs where nobody is waiting live, like summarizing a pile of documents overnight. These requests fill empty GPU slots during quiet hours, and can be paused (preempted) when live traffic needs the room.

♻️

Semantic + exact caching

Use an exact-match cache for identical prompts. Use a similarity cache (based on embeddings) for near-duplicates — carefully, because “almost the same question” can need a different answer. Plus KV prefix caching inside the server.

STEP 7 / 7

Reliability, safety & evaluation

Failover is a capacity and state problem together. Moving a conversation to another region may lose the cached prefix and increase prefill demand during an incident. Keep compatible model and prompt versions available, respect data-location constraints, and test the cold-cache case. Limit retries with a request budget so a slow GPU pool does not receive several generations for the same message.

🧯

Degrade, don't fail

When overloaded: queue users and show their place in line, drop low-priority traffic, and fall back to a smaller model or another region. A retry is neither free nor safe to repeat — retrying a generation costs a whole second response. So limit retries, and prefer resuming a stream.

💉

Prompt injection

Any retrieved document, web page or tool output might contain “ignore previous instructions”. Treat it as data, not commands. Give tools as few permissions as possible, limited to the current user. Ask for confirmation before anything that can't be undone. And never put secrets in text the model could repeat back.

🧪

Evals as CI

Changing the model or a prompt is a deploy, but there's no compiler to catch mistakes. Run offline test suites (evals) first. Then canary the change to a small share of traffic and compare quality signals — thumbs up/down, regenerations, tasks completed — before rolling it out (Chapter 21).

🔐

Privacy & isolation

Conversations are some of the most sensitive data a product holds. Encrypt them, keep them for a short time by default, and keep each business customer's data (and their vector indexes) separate. Using conversations for training should be opt-in and auditable.

🌍

Capacity & regions

GPUs are scarce and expensive, and you can't add more in seconds the way you can with web servers (Chapter 21). Reserve capacity ahead of time and keep pools warm, because loading a model takes minutes. Route between regions by queue length, while respecting rules about which country data must stay in (Chapter 22).

🔭

What to monitor

Percentiles for time to first token and time between tokens, queue length and wait time, tokens/s per node, how full the KV cache is, cache hit rate, preemptions, how often safety filters trigger, and cost per conversation.

⚠️
Common mistakes
  • Planning capacity in requests per second. The right units are conversations running at once and tokens per second — one request holds GPU memory for many seconds.
  • Retrying failed generations blindly. Each retry is another full, expensive response. Limit retries and prefer resuming a stream.
  • Trusting retrieved documents or tool output. They're untrusted input. Prompt injection is really a permissions problem: limit what the model is allowed to do.

Interview drill

Design: Time to first token is 4 s for long conversations. What do you do?

How a strong answer sounds
Time to first token is mostly prefill — reading the prompt — so give prefill less to do. Reuse cached KV prefixes for the system prompt and earlier turns. Summarize or cut long histories. Re-rank RAG results down to a few really useful chunks instead of stuffing the prompt. Then check queueing: if requests are waiting for a GPU slot, the problem is capacity or scheduling, not prefill. Streaming the first token the moment it exists is what makes the rest of the wait bearable.

Trade-off: Your GPU bill is growing faster than usage. Where do you look first?

How a strong answer sounds
First, how busy the GPUs are: are you using continuous batching, and how big are batches on average? Idle GPUs are the biggest waste. Next: caching (exact and prefix), routing (send easy questions to a small model), prompt length (system prompts tend to grow endlessly), and limits on maximum output tokens. Finally, consider a batch tier for work nobody is waiting on, to fill quiet hours. Track cost per conversation, not total spend, so you can see the effect of each change.

🧠 Key takeaways

  • Measure capacity in conversations running at once and tokens per second, not requests per second.
  • Prefill is limited by computation and sets time to first token. Decode is limited by memory reads, so it benefits hugely from big batches.
  • The KV cache shares GPU memory with the model weights, so longer contexts mean fewer conversations at once.
  • Continuous batching is the biggest throughput win; prefix caching and speculative decoding come next.
  • Stream tokens over SSE, stop generating when the client disconnects, and check the reply for safety as it streams.
  • Base answers on hybrid retrieval, and treat retrieved content and tool output as untrusted input.
  • Control cost by caching, sending easy questions to small models, batching, and shortening prompts.
  • Degrade gracefully under load, test model changes with evals and canaries, and treat conversation data as highly sensitive.
