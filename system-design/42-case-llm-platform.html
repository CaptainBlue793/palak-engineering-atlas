Design an LLM Chat Platform

ChatGPT, Claude, Gemini and every “AI assistant” inside a product share the same shape: a conversational API in front of an extremely expensive, memory-bound, stateful compute tier. Everything you've learned applies — gateways, queues, caching, streaming, multi-region — plus one new constraint: a GPU can only hold so many conversations at once, and every token you generate costs real money.

  • Estimate GPU capacity from tokens per second
  • Understand prefill vs decode, and KV cache memory
  • Compare static and continuous batching
  • Stream tokens to users and handle disconnects
  • Ground answers with RAG and tools safely
  • Control cost with caching, routing and quotas

STEP 3 / 7

How inference actually works

📥

Prefill (prompt processing)

The whole prompt is processed in parallel in one compute-heavy pass, producing the KV cache — the model's internal memory of that conversation. Cost grows with prompt length; this is what your time to first token is mostly made of.

🔁

Decode (token by token)

Each new token requires a full forward pass that reads all model weights from GPU memory. It's memory-bandwidth-bound, not compute-bound — which is why batching many users into one pass is nearly free, and why one user alone wastes a GPU.

🧠
The KV cache is the real capacity limit

Every active conversation holds a KV cache proportional to its context length. Long contexts and many concurrent users compete for the same GPU memory left over after the model weights. Capacity planning for LLM serving is mostly KV-cache arithmetic.

STEP 4 / 7

Deep dive: batching is everything

Because decode is memory-bound, running 32 conversations in one pass costs barely more than running one. Static batching collects a batch, runs it to completion, then starts the next — so a batch with one long reply leaves most slots idle. Continuous batching (vLLM, TensorRT-LLM, TGI) admits a waiting request the instant any slot frees, and mixes prefill and decode work.

📄

Prefix caching

Long system prompts, tool definitions and earlier conversation turns are identical across requests. Cache their KV blocks (PagedAttention-style) and reuse them — cutting prefill cost and TTFT dramatically for long chats and RAG contexts.

🔮

Speculative decoding

A small draft model proposes several tokens; the big model verifies them in one pass. Accepted guesses come nearly free — typically 1.5–3× faster decoding with identical output.

✂️

Quantization & parallelism

8-bit or 4-bit weights shrink memory and raise throughput at a small quality cost. Models too big for one GPU are split with tensor parallelism inside a node and pipeline parallelism across nodes.

STEP 5 / 7

End-to-end architecture

One chat message, start to finishStep-through
  1. Authenticate, check the plan's quota in tokens (not just requests — a 100K-token prompt costs 100× a short one), apply rate limits per user and per organization, and pick the model tier.
  2. Fetch recent turns from the conversation store (a plain database — chat history is ordinary CRUD). Long histories are truncated or summarized to fit the context window; attachments are pulled from object storage.
  3. For questions over the user's data, run hybrid retrieval (vector + BM25, Chapter 10), rerank the top candidates, and insert the best chunks with citations. Retrieved text is untrusted input — never let it silently carry instructions.
  4. Classifiers screen for policy violations and obvious prompt-injection patterns before any GPU time is spent.
  5. The router picks a model replica and region by queue depth, warm prefix cache, and priority (interactive chats before batch API jobs). Under overload it queues rather than failing, and can downgrade to a smaller model.
  6. The GPU builds the KV cache (reusing cached prefixes), then emits tokens one by one into the continuous batch. Tokens flow back through the stack as server-sent events the moment they exist.
  7. Output moderation runs on the stream in small windows so a violation can halt generation mid-answer. The client renders text as it arrives — which is why perceived latency is TTFT, not total time.
  8. Store the message, meter input/output tokens for billing, log latency and errors, and record feedback (👍/👎, regenerations) for evaluation. Bill and cache on exact token counts — not characters.

🪜

Model cascade

Answer easy turns with a small fast model and escalate only when a classifier (or the small model's own uncertainty) says the question is hard. Most conversational turns are easy.

📦

Batch tier

Offer a cheaper asynchronous API for non-interactive jobs (summarizing a corpus overnight). Those requests fill GPU slots during off-peak hours and absorb preemption.

♻️

Semantic + exact caching

Exact-match cache for identical prompts; embedding-similarity cache for near-duplicates (with care — “almost the same question” can need a different answer). Plus KV prefix caching inside the server.

STEP 7 / 7

Reliability, safety & evaluation

🧯

Degrade, don't fail

Under overload: queue with a visible position, shed low-priority traffic, fall back to a smaller model or another region. A retry is not free or idempotent — a retried generation costs a second full response, so cap retries and prefer resuming a stream.

💉

Prompt injection

Any retrieved document, web page or tool output may contain “ignore previous instructions”. Treat it as data, keep tool permissions minimal and user-scoped, require confirmation for irreversible actions, and never put secrets in context the model can echo.

🧪

Evals as CI

Model or prompt changes are deploys with no compiler to catch regressions. Run offline eval suites, then canary to a small traffic share and compare quality signals (thumbs, regenerations, task completion) before rolling out (Chapter 21).

🔐

Privacy & isolation

Conversations are among the most sensitive data a product holds. Encrypt, set short retention defaults, keep enterprise tenants' data (and their vector indexes) isolated, and make training-use opt-in and auditable.

🌍

Capacity & regions

GPUs are scarce and expensive; you can't autoscale them in seconds like web servers (Chapter 21). Reserve capacity, keep pools warm (model loading takes minutes), and route across regions by queue depth — with data-residency constraints respected (Chapter 22).

🔭

What to monitor

TTFT and inter-token latency percentiles, queue depth and wait time, tokens/s per node, KV cache utilization, cache hit rate, preemptions, safety-filter rates, cost per conversation.

⚠️
Common mistakes
  • Sizing capacity in requests per second. The unit is concurrent conversations and tokens per second — a single request occupies GPU memory for many seconds.
  • Retrying failed generations blindly. Each retry is another full, expensive response; cap retries and prefer resuming a stream.
  • Trusting retrieved documents or tool output. They're untrusted input; prompt injection is an authorization problem.
🎤
Interview drill

Design: Time to first token is 4 s for long conversations. What do you do?

How a strong answer sounds
TTFT is dominated by prefill over the prompt, so reduce prompt work: reuse cached KV prefixes for the system prompt and prior turns, summarize or truncate long histories, and rerank RAG results down to a few high-value chunks instead of stuffing context. Then check queueing — if requests wait for a GPU slot, that's capacity or scheduling, not prefill. Streaming the first token as soon as it exists is what makes the rest of the wait tolerable.

Trade-off: Your GPU bill is growing faster than usage. Where do you look first?

How a strong answer sounds
Utilization: are you running continuous batching, and what's the average batch size? Idle GPUs are the biggest waste. Then caching (exact and prefix), model routing (send easy turns to a small model), prompt length (people pad system prompts endlessly), and max-token limits. Finally, consider a batch tier for non-interactive work to fill off-peak capacity. Measure cost per conversation, not total spend, so the effect of each change is visible.

🧠 Key takeaways

  • Capacity is measured in concurrent conversations and tokens per second, not requests per second.
  • Prefill is compute-bound and sets TTFT; decode is memory-bandwidth-bound and loves big batches.
  • The KV cache competes with model weights for GPU memory — context length directly limits concurrency.
  • Continuous batching is the biggest throughput win; prefix caching and speculative decoding follow.
  • Stream tokens over SSE, cancel generation when clients disconnect, and moderate the stream as it flows.
  • Ground answers with hybrid retrieval, and treat retrieved content and tool output as untrusted input.
  • Control cost by caching, routing easy turns to small models, batching, and shortening prompts.
  • Degrade under load, canary model changes with evals, and treat conversation data as highly sensitive.
