Replication & Sharding

Sooner or later, one database server isn't enough. It can die, it can't answer every read, and it can't hold every byte. There are two answers: replication (keeping copies of the same data) and sharding (splitting the data across machines). Most big systems use both.

🧬 Replication

Keep the same data on several machines. You get high availability (the system survives a machine dying), read scaling (reads spread over the copies) and lower latency (a copy can sit near users).

🧩 Sharding (partitioning)

Put different data on different machines. This lets you handle more writes and store more data than one machine could. Each shard (piece) usually has copies of its own too.

Leader–follower replication

This is the most common setup (PostgreSQL, MySQL, MongoDB, Redis). One machine is the leader (also called the primary), and every write goes to it. It sends a stream of its changes to the followers (replicas). Each follower applies those changes in the same order, and can answer reads.

Why only one writer? If every write goes through one machine, there is exactly one order of events, and followers just replay it. Two machines accepting writes to the same row could each apply them in a different order and end up disagreeing. A sized example: a site doing 2,000 writes/s and 40,000 reads/s. One leader handles the writes easily; four followers each take about 10,000 reads/s. Reads scale by adding followers — writes don't, because every follower must still apply every write.

Failover is what happens when the leader dies. Something (a monitoring process, or the replicas voting among themselves) notices the leader has stopped answering, usually after a timeout of a few seconds, promotes the most up-to-date follower to leader, and points clients at it. The tricky edge cases: a timeout too short causes needless failovers during a brief slowdown; and if the old leader was only paused and comes back still thinking it's the leader, you have two leaders ("split brain") — so the old one must be fenced off.

When to pick which. Async is the common default when losing the last second of writes in a rare crash is tolerable (likes, views, most social data). Semi-sync is the usual choice for data you really can't lose, such as orders or payments: each write costs one extra round trip to the nearest follower (often under a millisecond in the same data center), and you keep working as long as one follower is healthy. Fully synchronous replication to every follower is rarely used, because one slow or dead follower stalls every write.

Replication lag problems

With async replication, followers are eventually consistent: they catch up in the end, but not right away. Usually they're milliseconds behind. Under heavy load it can be seconds or minutes. That causes strange things users can see:

🪞

Read-your-writes

You post a comment, refresh, and it's gone. Your read went to a replica that hadn't caught up yet. Fix: read your own recent data from the leader (say, for 60s after you write), or remember how far through the change log you've already seen and wait for the replica to reach it.

⏪

Monotonic reads

You see a new comment, refresh, and it disappears. Your second read went to a replica that was further behind. Fix: always send the same user to the same replica (for example, choose it by a hash of the user ID).

🔀

Consistent prefix

You see a reply before the message it answers, because different parts of the data copy at different speeds. Fix: keep related events that depend on each other in the same partition.

Multi-leader & leaderless replication

Here, several machines accept writes — usually one leader per data center — and they copy changes to each other. Writes stay fast and local, even if the link between regions is slow or broken. This is also how offline-first apps and shared document editors work: each device acts as its own “leader”.

⚔️
The catch: write conflicts

Two regions change the same record at the same moment. Ways to settle it: last write wins, decided by timestamp (simple, but quietly throws away someone's change); merging the two values; using CRDTs (special data types built so that any two versions can always be merged safely); or asking the user to choose.

There's no leader at all. The client (or a coordinator) sends each write to all N replicas and waits for W of them to confirm. A read asks R replicas and keeps the newest version it gets back. Cassandra, DynamoDB-style systems and Riak work this way. If W + R > N, then the group of replicas you read from must share at least one member with the group that took the write — so a read always sees the latest value.

A worked example with N = 3, W = 2, R = 2. You write v2 and replicas A and B confirm; C missed it and still holds v1. Now you read from any 2 of the 3. The possible pairs are A+B, A+C and B+C — every pair contains A or B, so you always get at least one v2, and since versions carry a number you keep the newest. With W = 1, R = 1 (1 + 1 = 2, not more than 3), you could write only to A and then read only from C, and get v1. Choosing the numbers is a trade: W = 3 makes every write wait for the slowest replica and fail if any is down; R = 1 makes reads fast but needs W = N for freshness. W = R = majority is the balanced middle.

Sharding: splitting the data

When there are more writes, or more data, than one machine can take, you partition the rows: each row goes to one shard, chosen by its shard key. How you map key → shard decides how evenly the load spreads, and how painful growth will be later.

Why it matters: replication gave you more copies, but every copy still holds all the data and applies every write. Suppose you have 20 TB of data and 50,000 writes/s, but one machine comfortably holds 4 TB and takes 10,000 writes/s. No amount of replicas fixes that. Split into 8 shards and each holds 2.5 TB and takes about 6,250 writes/s — with room to grow. The three ways to map a key to a shard:

  • Range — each shard owns a slice of sorted keys (A–F, G–L, …). Neighbouring keys stay together.
  • Hash — compute a hash of the key (a function that turns it into a random-looking number) and pick the shard from that number. Neighbouring keys end up far apart, so load spreads evenly.
  • Directory — a lookup table records which shard holds each key or customer. Most flexible, but it's one more service that must always be up.

Consistent hashing

With shard = hash(key) % N, going from 4 servers to 5 changes the answer for about 80% of keys. That means moving nearly all your data at once, or wiping nearly your whole cache. Consistent hashing fixes this. Picture a circle. Both servers and keys get a position on it, based on their hash. Each key belongs to the first server clockwise from it. Adding a server only takes keys from its neighbour on the circle, so only about 1/N of the keys move.

Where does "about 80%" come from? A key stays put only if hash % 4 and hash % 5 give the same answer. Try hashes 0 to 19: the remainders match only for 0, 1, 2, 3 (both give the number itself) — 4 out of 20, or 20%. So about 80% of keys change servers. In general, going from N to N+1 servers keeps only about 1 in N+1 keys in place. On the ring, adding a fifth server only claims the arc between it and the server before it, which is about 1/5 of the circle, so only about 20% of keys move — and they all move to the new server, never between old ones.

Consistent hashing is everywhere: how DynamoDB and Cassandra split data, Memcached client libraries, routing requests inside a CDN, load balancers that keep a user on one server (Chapter 5), and Discord's message routing.

The hard parts of sharding

🔥

Hot partitions

A celebrity's user ID, or a hashtag that goes viral, can overload one shard even when hashing is perfect. The fix: split that one key into several by adding a suffix (post_9#0..#9), then read all the pieces and add them up.

For example, a like counter getting 50,000 increments/s on one shard: each write picks a random suffix 0–9, so each of 10 sub-keys gets about 5,000/s, likely on different shards. A read fetches all 10 and sums them — 10 small reads instead of one, which is fine for a hot key.

🔗

Cross-shard queries

Joins and transactions that span several shards are slow, or simply not supported. Choose a shard key so most queries only need one shard. For example, shard by tenant_id so all of one customer's data sits together.

🚚

Rebalancing

Moving data between shards while the system is live takes care: copy the data, catch up using the change log, switch the routing, then delete the old copy. It's much easier if you split the data into many logical partitions up front (say 1,024) and map groups of them onto fewer machines.

🆔

Global uniqueness

Counting IDs up by one stops working once there are several shards, because each would count separately. Use UUIDs (long random IDs), or Snowflake-style IDs made of timestamp + machine ID + a counter. See the URL shortener case study.

🎤
Choosing a shard key — say this in interviews

A good shard key has three things. It has many different values (high cardinality), so data can spread out. Its values are used about equally often, so no single value gets hammered. And it matches your most common query, so most requests reach just one shard. For a user-focused app, user_id is the classic choice. Using created_at on its own is the classic mistake: every new write goes to the newest shard.

Resharding without downtime

Sooner or later the number of shards is wrong: shards grow too big, one customer outgrows its shard, or you just need more machines. You can't freeze a live system while you fix it. So resharding is a step-by-step migration that runs for days while traffic keeps flowing. The same steps work for moving to a completely different database.

Why so many steps? Each one keeps two promises: no write is ever lost (the old shard keeps receiving everything until the very end), and every step can be undone (you only stop writing to the old shard after the new one has proven itself). A one-shot "copy everything, then switch" breaks both: writes made during a copy that takes days would be missed, and if the new shard misbehaves after the switch there is nothing up to date to go back to.

Live migration: split shard 3 into 3a and 3bStep-through
  1. If the app works out shard = hash(key) % N in its own code, you're stuck. Instead, look the shard up in a table or config service (Vitess, or a shard map stored in etcd). Then you can change which shard owns which key range while the system runs, with no new deploy.
  2. Writes for the moving key range now go to both the old and the new shards. (Or the new shard simply follows the old one by replication, or a stream of database changes — CDC, Chapter 17.) Reads still come from the old shard. At this point you can undo everything.
  3. A background job copies the existing rows in batches, deliberately slowly. It remembers where it got to, and pauses when the replicas fall behind or CPU use climbs. This is the slow part — days for terabytes — so it must be able to stop and continue.
  4. A checking job compares rows on both sides — first samples, then eventually all of them — using checksums (short fingerprints of the data). Any difference means a bug in the double-writing. Find it before you switch over, not after.
  5. Move 1%, then 10%, 50% and 100% of reads to the new shards, comparing the answers and the speed each time. If anything looks wrong, switch straight back — the old shard is still receiving every write.
  6. Switch writes to the new shards. Freezing each key for a moment (usually milliseconds) makes sure no write is applied out of order. Keep copying changes back to the old shard for a while, just in case you need to go back. Then stop, delete the old key range and reclaim the space.
🔥

The hot shard

One celebrity, one huge customer or one popular key can max out a shard while the others sit idle. Fixes: split that key into several using a suffix (post:42#0…#9) and combine the pieces when reading; put a cache in front of it; give that customer a shard of their own; or limit the request rate for that key.

🧮

Pre-split into many shards

Create, say, 1,024 logical shards on day one, and put many of them on each real machine. Growing then means moving whole logical shards to new machines — you never have to recompute where keys live. This is how Vitess, Citus and most large fleets avoid painful splits later.

🧭

Cross-shard queries

Anything that needs data from every shard (reports, site-wide search, joins) turns into “ask them all and combine” — slow and easily broken. Serve those from a separate copy of the data instead: a search index or a data warehouse kept up to date by a stream of database changes (Chapters 10, 17, 18).

🧊
Choose the shard key like it's permanent

Because it nearly is permanent. A good key spreads the load evenly, keeps data that's read together on one shard, and avoids values that only ever go up — timestamps or counting IDs send every new write to the last shard. Getting it wrong means the whole migration described above. Plan it carefully once, then live with it.

⚠️
Common mistakes
  • Sharding too early. It's very hard to undo, and it breaks joins, transactions and day-to-day operations. First use up bigger machines, read replicas and caching.
  • Picking a shard key whose values only go up. Timestamps or counting IDs send every new write to the last shard, creating an instant overloaded shard.
  • Ignoring replication lag in the product design. “I posted, refreshed, and it's gone” is a design bug, not just a database quirk. Send a user's reads of their own data to the leader, or track how far the replica has caught up.
🎤
Interview drill

Design: Pick a shard key for a multi-tenant SaaS where 1% of tenants hold 60% of the data.

How a strong answer sounds
tenant_id keeps each customer's data together, so queries and transactions stay on one shard. The problem is the giant customers, who unbalance everything. So: split into many logical shards up front and map them onto machines; give the largest customers their own shards; and for the very biggest, split them further by (tenant_id, bucket), where the bucket comes from a second key. Say out loud that you'd watch the traffic per shard, because which customers are biggest will change over time.

Operate: You must double the shard count with no downtime. Walk me through it.

How a strong answer sounds
First, look shards up in a shard map instead of computing hash % N in code. Then: create the new shards; write the affected key ranges to both old and new (or copy changes across with CDC); copy the old rows over in small, slow batches, remembering where you got to; keep comparing checksums on both sides; move reads over gradually (1% → 100%) while writes still go to both; and finally switch writes, freezing each key for a moment as you do. Keep the old data until the checks all pass, then delete it.

🧠 Key takeaways

  • Replication = copies of the same data, for staying up and for handling more reads. Sharding = splitting the data, for handling more writes and storing more.
  • Async replication is fast, but writes the client was told had succeeded can be lost when the leader fails. Sync replication loses nothing, but is slower and stops if a follower is down.
  • Lagging replicas break “see your own writes” and can even show data going backwards. Route reads with care.
  • Leaderless systems use quorums: if W + R is greater than N, reads and writes always share a replica.
  • Range sharding makes range scans easy but risks overloaded shards. Hash sharding spreads load evenly.
  • Consistent hashing moves only about 1/N of the keys when servers change, and virtual nodes even out the load.

Check your understanding

A user updates their profile, refreshes, and sees the old version. Reads go to async replicas. Best targeted fix?

Users only need to see their own writes straight away. So send just those reads to the leader, and leave everything else on the replicas. Making all replication synchronous would also work but slows every write for everyone; more replicas or a longer cache TTL make staleness no better, or worse.

N = 5 replicas. Which configuration guarantees reads see the latest write?

You need W + R > N: here 3 + 3 = 6, which is more than 5. The other options add up to 5 or less, so the replicas you read from might all have missed the write.

You shard an events table by created_at ranges. What happens?

Time only moves forward, so “now” always falls in the last range. Put a hashed value first (such as device_id) to spread the writes out.

Your cache cluster uses hash(key) % N. You add one server to 9. Roughly what fraction of cache lookups now miss?

Going from 9 servers to 10 changes the remainder for about 9 out of 10 keys, so they all land somewhere new. With consistent hashing, only about 1 in 10 would move.

What problem do virtual nodes solve in consistent hashing?

A few random points around the circle leave gaps of very different sizes. Hundreds of points per server average out, and you can give bigger servers more points so they take more keys.
