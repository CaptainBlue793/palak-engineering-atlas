Replication & Sharding

One database server eventually isn't enough — it can't survive failure, can't serve every read, can't hold every byte. The two answers are replication (copies of the same data) and sharding (splitting data across machines). Most big systems use both.

🧬 Replication

Keep the same data on multiple machines. Gives high availability (survive a node dying), read scaling (spread reads) and lower latency (a copy near users).

🧩 Sharding (partitioning)

Split different data across machines. Gives write scaling and storage scaling beyond one machine. Each shard is usually replicated too.

Leader–follower replication

The most common setup (PostgreSQL, MySQL, MongoDB, Redis). One node is the leader (primary): all writes go to it. It streams its change log to followers (replicas), which apply changes in the same order and can serve reads.

Replication lag problems

With async replication, followers are eventually consistent — usually milliseconds behind, but under load it can be seconds or minutes. That creates user-visible weirdness:

🪞

Read-your-writes

You post a comment, refresh, and it's gone — your read hit a lagging replica. Fix: read your own recent data from the leader (e.g. for 60s after a write), or track the log position you've seen.

⏪

Monotonic reads

You see a new comment, refresh, and it disappears — the second read hit a more lagged replica. Fix: pin each user to one replica (e.g. hash of user ID).

🔀

Consistent prefix

You see an answer before the question it replies to, because partitions replicate at different speeds. Fix: write causally related data to the same partition.

Multi-leader & leaderless replication

Several nodes accept writes — typically one leader per data center — and replicate to each other. Writes stay fast and local even if the inter-region link is slow or down. Also how offline-first apps and collaborative editors work (each device is a “leader”).

⚔️
The catch: write conflicts

Two regions edit the same record at the same time. Resolution options: last-write-wins by timestamp (simple, silently loses data), merging values, CRDTs (data types designed to merge automatically), or asking the user.

No leader at all. The client (or a coordinator) sends each write to all N replicas and waits for W to confirm; reads query R replicas and take the newest version. Used by Cassandra, DynamoDB-style systems and Riak. If W + R > N, every read set overlaps every write set, so reads see the latest write.

Sharding: splitting the data

When writes or data volume exceed one machine, you partition rows across shards using a shard key. The strategy for mapping key → shard decides how evenly load spreads and how painful growth will be.

Consistent hashing

With shard = hash(key) % N, going from 4 to 5 servers changes the result for ~80% of keys — a massive, simultaneous data migration (or cache wipe). Consistent hashing fixes this: servers and keys are placed on the same circular hash space, and each key belongs to the next server clockwise. Adding a server only steals keys from its neighbour — about 1/N of keys move.

The hard parts of sharding

🔥

Hot partitions

A celebrity's user ID or a viral hashtag overloads one shard even with perfect hashing. Mitigate by adding a random suffix to hot keys (post_9#0..#9) and scatter-gathering on read.

🔗

Cross-shard queries

Joins and transactions across shards are slow or unsupported. Choose a shard key so most queries touch one shard (e.g. shard by tenant_id so each customer's data is colocated).

🚚

Rebalancing

Moving data between shards while serving traffic is delicate: copy, catch up via change log, switch routing, delete. Pre-splitting into many logical partitions (e.g. 1,024) mapped onto fewer machines makes it easier.

🆔

Global uniqueness

Auto-increment IDs no longer work across shards. Use UUIDs, or Snowflake-style IDs (timestamp + machine ID + sequence) — see the URL shortener case study.

🎤
Choosing a shard key — say this in interviews

A good shard key has high cardinality (many distinct values), even access frequency (no hot values), and matches the dominant query so most requests hit a single shard. user_id for a user-centric app is the classic choice; created_at alone is a classic mistake (all writes hit the newest shard).

Resharding without downtime

Sooner or later the shard count is wrong: shards get too big, one tenant outgrows its shard, or you simply need more machines. You can't take a global lock on a live system, so resharding is a migration protocol that runs for days while traffic keeps flowing. The same playbook works for moving to a different database entirely.

Live migration: split shard 3 into 3a and 3bStep-through
  1. If the app computes shard = hash(key) % N in code, you're stuck. Route through a lookup table or config service (Vitess, a shard map in etcd) so ownership can change at runtime, per key range, without a deploy.
  2. Writes for the affected range go to both old and new (or the new shard follows the old one via replication/CDC — Chapter 17). Reads still come from the old shard. Everything is reversible at this point.
  3. A throttled background job copies existing rows in batches, tracking a cursor and pausing when replication lag or CPU rises. This is the slow part — days for terabytes — and it must be resumable.
  4. A comparison job samples (and eventually sweeps) rows on both sides, comparing checksums. Any mismatch is a bug in the dual-write path — find it before cutover, not after.
  5. Move 1% → 10% → 50% → 100% of reads to the new shards, comparing results and latency. Any problem: flip back instantly, because the old shard is still being written.
  6. Flip writes to the new shards (a brief per-key freeze — usually milliseconds — guarantees ordering), keep dual-writing in reverse for a safety window, then stop, drop the old range and reclaim the space.
🔥

The hot shard

One celebrity, one huge tenant or one popular key can saturate a shard while others idle. Fixes: split that key with a suffix (post:42#0…#9) and merge on read, cache it in front, give the tenant a dedicated shard, or rate-limit per key.

🧮

Pre-split into many shards

Create, say, 1,024 logical shards on day one and map many of them onto each physical machine. Growth then means moving logical shards, never rehashing keys. This is how Vitess, Citus and most large fleets avoid painful resplits.

🧭

Cross-shard queries

Anything that needs data from all shards (reports, global search, joins) becomes scatter-gather — slow and fragile. Serve those from a derived store instead: a search index or warehouse fed by CDC (Chapters 10, 16, 17).

🧊
Choose the shard key like it's permanent

Because it nearly is. A good key spreads load evenly, keeps data that's read together on one shard, and avoids monotonic values (timestamps or auto-increment IDs put every new write on the last shard). Getting it wrong means the migration above — plan for it once, then live with it.

⚠️
Common mistakes
  • Sharding too early. It's a one-way door that breaks joins, transactions and operations. Exhaust vertical scaling, read replicas and caching first.
  • Choosing a monotonic shard key. Timestamps or auto-increment IDs put every new write on the last shard — an instant hot spot.
  • Forgetting replication lag in the product. “Post then refresh shows nothing” is a design bug, not a database quirk; route read-your-writes to the primary or track the log position.
🎤
Interview drill

Design: Pick a shard key for a multi-tenant SaaS where 1% of tenants hold 60% of the data.

How a strong answer sounds
tenant_id keeps each tenant's data together so queries and transactions stay single-shard — but the giant tenants break balance. So: pre-split into many logical shards mapped onto physical nodes, give the largest tenants dedicated shards, and for the very biggest, sub-shard by (tenant_id, bucket) where bucket is derived from a secondary key. Say explicitly that you'd monitor per-shard traffic, because the imbalance will move over time.

Operate: You must double the shard count with no downtime. Walk me through it.

How a strong answer sounds
Route through a shard map rather than hash % N in code. Then: create the new shards, dual-write the affected key ranges (or replicate via CDC), backfill history in throttled batches with a resumable cursor, run a continuous checksum comparison, shift reads gradually (1% → 100%) while writes still go to both, and finally cut over writes with a brief per-key freeze. Keep the old data until verification passes, then drop it.

🧠 Key takeaways

  • Replication = copies for availability and read scaling; sharding = splits for write and storage scaling.
  • Async replication is fast but can lose acknowledged writes on failover; sync is safe but slow and fragile.
  • Replica lag breaks read-your-writes and monotonic reads — route reads carefully.
  • Leaderless systems use quorums; W + R > N guarantees overlap between reads and writes.
  • Range sharding enables range scans but risks hot spots; hash sharding spreads load evenly.
  • Consistent hashing moves only ~1/N of keys when servers change; virtual nodes even out load.

Check your understanding

A user updates their profile, refreshes, and sees the old version. Reads go to async replicas. Best targeted fix?

Read-your-writes consistency only needs to apply to the writer's own data, so route just those reads to the leader.

N = 5 replicas. Which configuration guarantees reads see the latest write?

Need W + R > N: 3 + 3 = 6 > 5. The others sum to 5 or less, so read and write sets can miss each other.

You shard an events table by created_at ranges. What happens?

Time is monotonic, so “now” always falls in the last range. Prefix with a hashed key (e.g. device_id) to spread writes.

Your cache cluster uses hash(key) % N. You add one server to 9. Roughly what fraction of cache lookups now miss?

Changing N from 9 to 10 changes the modulo result for about 9/10 of keys. With consistent hashing, only ~1/10 move.

What problem do virtual nodes solve in consistent hashing?

A few random points give lumpy arcs. Hundreds of points per server average out, and weights can give bigger servers more points.
