Batch & Stream Processing

Your main database answers “what is in this user's cart?” in about a millisecond. Other questions are different: “what was revenue by country last quarter?”, “which videos are trending right now?”, or “flag this card payment as fraud within 200 ms”. These need a different kind of system: data pipelines. Some crunch large amounts of past data in one go (batch). Others react to each event the moment it arrives (stream).

OLTP vs OLAP

Data gets used in two very different ways. OLTP (online transaction processing) is the app's day-to-day work: read or update one order, one user, one cart. OLAP (online analytical processing) is analysis: add up or compare huge numbers of rows. If one database tries to do both, analysts' giant queries slow down checkout. And the way a checkout database lays out its data makes analytics painfully slow.

Why does the layout matter so much? A row store keeps each row's values together on disk: order 1's id, date, country, amount, and so on, then order 2's. A column store keeps each column together: all the ids, then all the dates, then all the countries. Now size it. An orders table has 1 billion rows and 100 columns, about 8 bytes each, so roughly 800 GB. The query SUM(amount) WHERE country = 'DE' needs just 2 columns. A row store must read every row in full to reach those two values: ~800 GB. A column store reads only the country and amount columns: 2 × 8 GB = ~16 GB, 50 times less, before compression makes it smaller still. The reverse also holds: fetching all 100 fields of order 1005 is one quick read in a row store but 100 separate lookups in a column store. That's why the app keeps a row store and the analysts get a column store.

🗜️

Compression loves columns

A column holds similar values, like DE, DE, DE, FR…. Tricks such as dictionary encoding (store each value once, then use short codes) and run-length encoding (“DE ×3”) shrink it 5–20×. So more data fits in memory and less has to be read from disk.

🏎️

Vectorized execution

The engine works on a column in batches of thousands of values at once, in tight CPU loops. Modern CPUs can even apply one instruction to many values together (SIMD). That is much faster than handling one row at a time.

✂️

Skip whole files

Parquet (a popular columnar file format) stores the min and max value of each column chunk. For WHERE date = '2026-09-17', the engine skips every chunk whose range can't contain that date. Add date partitioning (one folder per day) and most of the data is never even opened.

Batch processing: MapReduce

When data is too big for one machine, it's spread across many. Copying it all to one place would be slow, so instead you send the code to where the data lives. Google's MapReduce (2004) made this simple. You write just two functions: map (turn each record into key–value pairs) and reduce (combine all values for one key). The framework handles the rest: splitting the input, spreading work across machines, moving data between them, and retrying when a machine fails.

Here's a word count traced by hand, with the two lines the cat sat and the dog on two machines:

  1. Map. Machine 1 reads its line and emits (the,1) (cat,1) (sat,1). Machine 2 emits (the,1) (dog,1). Each machine works on its own data only.
  2. Shuffle. Every pair is sent to a reducer chosen by its key, using a hash of the word. Both (the,1) pairs travel to the same reducer, wherever they started.
  3. Reduce. That reducer gets the → [1, 1] and adds them: (the, 2). Others produce (cat,1) (sat,1) (dog,1).

The shuffle's "same key to the same reducer" rule is what makes it correct: no word's count is ever split between two reducers. Swap in other map and reduce functions and the same shape computes revenue per country, clicks per page, or a join between two datasets.

🧠 The shuffle is the expensive step. Every value for a key has to travel over the network to the same reducer. Real jobs add a combiner (a mini-reduce that runs on each mapper first). So machine 1 sends the:3 once, instead of three separate the:1s.

🔥 Spark: MapReduce, but in memory

MapReduce wrote every in-between result to disk. That is safe but slow, especially for ML jobs that loop over the same data many times. Apache Spark plans the whole job as a DAG (a graph of steps with no loops) and keeps in-between data in memory. If a machine dies, Spark doesn't need backup copies. It recomputes the lost piece from its lineage (the recorded steps that produced it). It's often 10–100× faster, and adds SQL and DataFrame APIs on top.

🧊 Batch properties you get for free

Inputs are immutable (files in object storage that never change). So if a task fails, you simply run it again. Outputs go to a new location and are swapped in all at once (atomically). Found a bug in the job? Fix the code and rerun it over past data. This “recompute from input that never changes” mindset is the great strength of batch.

🐘
Data skew: the one reducer that never finishes

Skew means some keys have far more data than others. Say 40% of events have country = 'US'. The US reducer does 40% of the work while 199 others sit idle, and the whole job waits for it. Fixes:

  • Salt hot keys: split the key into US#0…US#9 so ten reducers share it, then merge the results.
  • Broadcast joins: copy a small table to every machine instead of shuffling the big one.
  • Adaptive query execution: the engine notices an oversized partition at runtime and splits it.

Pipelines, warehouses & orchestration

Ingest

Pull data in from many places: CDC (change data capture, a feed of every change in an app database — Chapter 17), app events via Kafka, exports from third-party SaaS tools, and files dropped in object storage.

ETL or ELT?

ETL (extract, transform, load) cleans and reshapes data before loading it. That was the classic approach when warehouse computing power was expensive. ELT loads the raw data first, then transforms it inside the warehouse with SQL (often using dbt). ELT is today's default: cloud warehouses can scale up computing power on demand, and keeping the raw data means you can reprocess it later.

Model

Organize the data into fact tables (things that happened: orders, clicks) and dimension tables (the things they refer to: users, products). This layout is called a star schema, and it is easy for analysts to join. Lakehouse table formats (Iceberg, Delta — Chapter 9) give you warehouse-style tables on top of cheap object storage.

Orchestrate

Tools like Airflow, Dagster or Prefect run jobs as a DAG (a graph of jobs and which ones must finish first). They handle schedules, retries, backfills (re-running past dates) and alerts. Example: “build daily_revenue only after orders and fx_rates for that date succeed.”

Guard quality

Use data contracts (agreed formats between teams), schema checks, row-count tests and freshness tests. Bad data flowing silently into dashboards and ML models is the pipeline version of an outage.

Stream processing

Batch works on bounded data: a fixed set, like yesterday's files. Its answers arrive hours later. Stream processing treats data as unbounded: it never ends, so you compute continuously as events arrive. Results come in seconds or even milliseconds. Uses include fraud detection, live dashboards, trending topics, alerting and real-time recommendations.

When is streaming worth it? Ask what happens if the answer is an hour late. A fraud check that runs an hour after the payment is useless: the money is gone. A "revenue last quarter" report that arrives an hour later than it could have is fine. Streaming systems are harder to build, test and run than batch jobs, because they never stop and must handle late and out-of-order data. So use streaming when freshness changes the outcome, and batch for everything else.

🚰
Analogy: counting cars on a highway

Batch is reviewing yesterday's traffic camera footage. Streaming is standing on the bridge with a clicker. But some cars' photos reach you late, because a camera's upload got stuck in a tunnel. If you want “cars per minute”, do you count by when the car passed (event time) or when its photo arrived (processing time)? And how long do you wait for late photos before announcing the 9:00–9:01 total?

🕐 Event time

When the event actually happened, stamped where it happened (the phone, the server). It gives correct results even when events arrive late or out of order, for example because a phone was offline, the network was slow, or the processor fell behind.

🕓 Processing time

When the processor happens to see the event. It is simple and fast, but results depend on how far behind the processor is. Replay yesterday's data, and all of it would be counted as “now”.

Windows and watermarks

A stream never ends, so you can't compute a “grand total”. Instead you group events into windows: slices of time, like “9:00 to 9:01”. But when is a window finished, if late events can still show up? A watermark answers that. It is the processor's best guess that “all events up to time W have probably arrived”. When the watermark passes the end of a window, the window fires: it outputs its final result. Events that show up after that are called late.

A worked example with a 1-minute tumbling window and a watermark 5 seconds behind the newest event time seen:

  1. Clicks stamped 9:00:10, 9:00:40 and 9:00:58 arrive. They go into the 9:00–9:01 window (count 3).
  2. A click stamped 9:01:03 arrives. It goes into the 9:01–9:02 window. The watermark is now 9:01:03 − 5 s = 9:00:58, still before 9:01, so the 9:00 window stays open.
  3. A phone that was briefly offline sends a click stamped 9:00:55. The window is still open, so it's counted (count 4), even though it arrived out of order.
  4. A click stamped 9:01:07 arrives. The watermark moves to 9:01:02, past the end of the 9:00 window. The window fires: 9:00–9:01 = 4 clicks.
  5. A click stamped 9:00:50 arrives now. Its window already fired, so it is late: dropped, or handled as described in the callout below.

A bigger delay (say 30 s) would have caught that last click, but every result would come out 30 seconds later. Pick the delay from how late your events really are: if 99.9% arrive within 10 seconds, a 10–15 second delay is a sensible start.

🧱

Tumbling

Fixed-size buckets that don't overlap, like clicks per minute or revenue per hour. Each event lands in exactly one window.

🪟

Sliding / hopping

Fixed-size windows that overlap. Example: “requests in the last 5 minutes, updated every 30 seconds”. This gives smoother numbers, which is good for alerts.

💬

Session

Windows with no fixed size. A window stays open while events keep coming, and closes after a quiet gap. Examples: one user's browsing session, or a burst of sensor activity.

The same click at 9:03:20 lands differently in each. In a tumbling 5-minute window it counts once, in 9:00–9:05. In a sliding 5-minute window that moves every minute, it counts in five windows: 8:59–9:04, 9:00–9:05, 9:01–9:06, 9:02–9:07 and 9:03–9:08. That overlap is what makes sliding windows smooth, and also why they cost more state. In a session window with a 30-minute gap, it joins that user's current session if their previous click was within 30 minutes; otherwise it starts a new one.

🩹
Handling late data without losing it

Dropping late events isn't the only option. An engine can send an updated result for a window that already fired (called “allowed lateness”, where the old result is retracted and replaced). Or it can send late events to a side output, a separate stream that a batch job uses to fix the numbers later. Beam, Flink and Dataflow control this with triggers: early best-guess results, the on-time result when the watermark passes, then late corrections.

State, checkpoints & exactly-once

Windows, joins and deduplication all need to remember things. That memory is called state: counts per key, recent events, IDs already seen. It can grow to terabytes. A stream processor has to keep this state fast to reach, usually in a local RocksDB database (an embedded key–value store) on each worker. It also has to survive crashes without counting anything twice.

Flink-style checkpointing: consistent snapshots of a running pipelineStep-through
  1. The coordinator slips a special marker, a barrier, for checkpoint #42 into the stream at source offset 1,000 (position 1,000 in the Kafka log). The barrier travels along with the data. It separates “before this checkpoint” from “after”.
  2. When the barrier reaches the aggregator, it saves a copy of its state (counts per window and key) to durable storage. It does this in the background, without pausing processing. This method is the Chandy–Lamport snapshot algorithm.
  3. The sink (the final output step) has been writing results inside an open transaction, such as a Kafka transaction. When the barrier arrives, it pre-commits: the results are saved safely, but readers can't see them yet.
  4. Once every operator confirms, checkpoint #42 is complete. Source offset 1,000, all the saved state and the pre-committed output now form one consistent snapshot. The sink commits (the second step of a two-phase commit), and the output becomes visible.
  5. A worker dies at offset 1,450. Flink loads the state from checkpoint #42, rewinds Kafka to offset 1,000, and cancels the uncommitted sink transaction. Events 1,000–1,450 get processed again. But their first-time results were never committed, so each event counts once: exactly-once results from end to end.
🎤
“Exactly-once” is about effects, not delivery

Inside the system, an event may be processed more than once. The promise is that the state and the output count each event exactly once. You need three things for that: a source you can replay (like Kafka), checkpointed state, and a sink that is either transactional (all-or-nothing writes) or idempotent (writing twice has the same effect as once, e.g. upserts keyed by window + key). If your sink is “send an email”, you're back to idempotency keys (Chapter 17).

How often to checkpoint? It's a trade-off. Checkpointing every 10 seconds means a crash replays at most about 10 seconds of events, but snapshotting often costs extra I/O. Checkpointing every 10 minutes is cheaper, but a crash means reprocessing up to 10 minutes of data before the job is current again. There's a second cost with transactional sinks: output only becomes visible when a checkpoint commits, so a 1-minute interval means downstream readers see results up to a minute late. Intervals from a few seconds to a minute are typical.

Lambda vs kappa architecture

λ Lambda

Run two pipelines side by side. A batch layer recomputes accurate results from all past data every night. A speed layer gives rough real-time results for today. A serving layer merges the two for readers.

+
  • Accurate batch as a safety net
−
  • Same logic written twice, in two frameworks, that drift apart

κ Kappa

Everything is a stream. Keep the event log for a long time (with Kafka tiered storage, or in a data lake). When the logic changes, start a new version of the streaming job from the start of the log. Let it catch up, then switch readers over to it.

+
  • One codebase, one semantics
−
  • Reprocessing years of data through a stream can be slow and costly

Modern engines blur the line between the two. Flink and Spark Structured Streaming can run the same code in batch or streaming mode. Apache Beam (Google Dataflow) was built around one model for both. Kafka Streams and ksqlDB fit lighter stream processing inside a single service. Streaming SQL databases (Materialize, RisingWave) show a stream as a table view that keeps updating itself.

Picking between them. Kappa is the simpler default when your streaming engine can reprocess history at a reasonable speed and you can keep the log long enough. For example, if a job normally handles 10,000 events/sec and can replay at 200,000 events/sec, a month of history (about 26 billion events) takes around 36 hours to rebuild, which is fine for most fixes. Lambda earns its extra cost when the numbers must be exactly right and checkable (billing, payouts, regulatory reports), or when the full history is too large to push through a stream job quickly.

⚠️
Common mistakes
  • Using processing time when event time matters. Events from phones that were offline all get counted as “now”. That breaks every per-minute or per-hour number.
  • Assuming exactly-once delivery exists. What you can get is exactly-once effects, using checkpointed state and idempotent or transactional sinks.
  • Ignoring skew. One very busy key means one reducer or partition does most of the work while the rest sit idle.
🎤
Interview drill

Design: Compute “active users in the last 5 minutes” for a live dashboard, correct within seconds.

How a strong answer sounds
Use a streaming job keyed by user, with a 5-minute sliding window over event time. Set a watermark that allows a little lateness. To count distinct users per window, use HyperLogLog sketches (a tiny, approximate counter from Chapter 20). That keeps state small and lets windows merge cleanly. Upsert results into a serving store keyed by (window, dimension), so reprocessing overwrites old values instead of counting twice. Send events that arrive after the watermark to a side output, and let a batch job correct the numbers later.

Trade-off: Lambda or kappa for a system whose numbers are used for billing?

How a strong answer sounds
Lambda, on purpose. Streaming gives product teams the fresh numbers they need. A nightly batch recompute over the raw, unchanging log gives finance the correct numbers it needs, including late events and updated fraud rules. The cost is writing the logic twice. So keep the streaming job simple, and treat the batch result as the source of truth for money. Compare the two every day and alert if they drift apart.

🧠 Key takeaways

  • Keep analytics off the app's OLTP database. Columnar OLAP stores read only the columns a query needs, and compress them heavily.
  • MapReduce splits work into map, shuffle and reduce. Spark keeps a DAG of steps in memory and rebuilds lost pieces from their lineage.
  • Batch jobs over input that never changes are easy to retry and rerun. Watch out for skewed keys.
  • Load data into a warehouse or lakehouse (ELT), model it as facts and dimensions, and run it as a DAG with data-quality checks.
  • Streams add things up over tumbling, sliding or session windows. Use event time to get correct results.
  • Watermarks decide when a window fires. Waiting longer gives more complete results, but they arrive later.
  • Checkpoint barriers, a replayable source, and a transactional or idempotent sink together give exactly-once results.
  • Lambda runs batch and stream side by side. Kappa uses one streaming path and replays the log when logic changes.

Check your understanding

Why is SELECT SUM(amount) FROM sales WHERE year = 2025 much faster in a column store?

A row store must read every column of every row. A column store reads just 2 of maybe 100 columns, and those are heavily compressed.

In MapReduce word count, which phase moves all “the” pairs from every mapper to a single reducer?

The shuffle hashes each key to pick its reducer, then sends the data there over the network. It is usually the most expensive phase.

A mobile game computes “score per player per minute”. Phones buffer events offline and upload later. Which time should windows use?

Processing time would put offline play in the minute it was uploaded. Event time puts each event in the minute it really happened. Watermarks set a limit on how long to wait.

You reduce the watermark delay from 30 s to 1 s. What's the likely effect?

Watermarks trade completeness for freshness. A short delay fires windows sooner, but treats more slow events as late.

What makes Flink's exactly-once guarantee hold across a crash?

After a failure, input is replayed from the saved offset, state is restored, and output that was never committed is thrown away. So each event's effect happens once.
