Batch & Stream Processing

Your production database answers “what is this user's cart?” in a millisecond. But “what was revenue by country last quarter?”, “which videos are trending right now?” or “flag this card transaction as fraud within 200 ms” need a different family of systems: data pipelines that crunch history in bulk, or react to events continuously as they flow.

🗜️

Compression loves columns

A column holds similar values: DE, DE, DE, FR…. Dictionary and run-length encoding shrink it 5–20×, so more data fits in memory and less hits the disk.

🏎️

Vectorized execution

Engines process columns in tight CPU loops over batches of thousands of values (SIMD), instead of row-by-row interpretation.

✂️

Skip whole files

Parquet files store min/max per column chunk. WHERE date = '2026-09-17' skips every chunk whose range can't match — combined with date partitioning, most data is never opened.

Batch processing: MapReduce

When data doesn't fit on one machine, move the computation to the data. Google's MapReduce (2004) made this simple: you write two functions, and the framework handles splitting, distribution, shuffling, retries and failed machines.

🧠 The shuffle is the expensive part: every value for a key must travel over the network to the same reducer. Real jobs add a combiner (a mini-reduce on each mapper) so machine 1 sends the:3 instead of three the:1s.

🔥 Spark: MapReduce, but in memory

MapReduce wrote every intermediate result to disk — robust but slow, especially for iterative ML. Apache Spark builds a DAG of transformations, keeps intermediate data in memory, and recovers lost partitions by recomputing their lineage instead of replicating everything. Often 10–100× faster, with SQL and DataFrame APIs on top.

🧊 Batch properties you get for free

Inputs are immutable (files in object storage), so a failed task simply reruns. Outputs are written to a new location and swapped in atomically. A buggy job? Fix the code and rerun over history. This “recompute from immutable input” mindset is the great strength of batch.

🐘
Data skew: the one reducer that never finishes

If 40% of events have country = 'US', the US reducer does 40% of the work while 199 others sit idle, and the job waits for it. Fixes: salt hot keys (US#0…US#9, then merge), broadcast joins for small tables, and adaptive query execution that splits skewed partitions.

Pipelines, warehouses & orchestration

Ingest

CDC from OLTP databases (Chapter 17), app events via Kafka, third-party SaaS exports, files dropped in object storage.

ETL or ELT?

ETL transforms before loading (classic, when warehouse compute was expensive). ELT loads raw data first and transforms inside the warehouse with SQL (dbt) — today's default because cloud warehouses scale compute elastically and raw data can be reprocessed.

Model

Organize into fact tables (events: orders, clicks) and dimension tables (users, products) — a star schema that analysts can join easily. Lakehouse table formats (Iceberg, Delta — Chapter 9) give warehouse semantics over object storage.

Orchestrate

Airflow, Dagster or Prefect run jobs as a DAG with dependencies, schedules, retries, backfills and alerts: “build daily_revenue only after orders and fx_rates for that date succeed.”

Guard quality

Data contracts, schema checks, row-count and freshness tests. Bad data flowing silently into dashboards and ML models is the pipeline equivalent of an outage.

Stream processing

Batch answers questions about bounded data (yesterday's files) with hours of delay. Stream processing treats data as unbounded and computes continuously, with results in seconds or milliseconds: fraud detection, live dashboards, trending topics, alerting, real-time recommendations.

🚰
Analogy: counting cars on a highway

Batch is reviewing yesterday's traffic camera footage. Streaming is standing on the bridge with a clicker. But some cars' photos reach you late — a camera's upload got stuck in a tunnel. If you want “cars per minute”, do you count by when the car passed (event time) or when its photo arrived (processing time)? And how long do you wait for stragglers before announcing the 9:00–9:01 total?

🕐 Event time

When the event actually happened, stamped at the source. Gives correct results even when events arrive late or out of order (phones offline, network delays, consumer lag).

🕓 Processing time

When the processor happens to see the event. Simple and low-latency, but results change depending on lag — replaying yesterday's data would put all of it in “now”.

Windows and watermarks

An infinite stream can't be summed “in total”, so aggregations run over windows. A watermark is the processor's estimate that “all events with event time ≤ W have probably arrived”. When the watermark passes a window's end, the window fires its final result. Events arriving after that are late.

🧱

Tumbling

Fixed, non-overlapping buckets: clicks per minute, revenue per hour. Each event belongs to exactly one window.

🪟

Sliding / hopping

Fixed size, overlapping: “requests in the last 5 minutes, updated every 30 seconds” — smoother metrics for alerting.

💬

Session

Dynamic windows that close after a gap of inactivity: one user's browsing session, a burst of sensor activity.

🩹
Handling late data without losing it

Instead of dropping, engines can emit an updated result for an already-fired window (“allowed lateness” with retractions), or route late events to a side output that a batch job reconciles later. Beam/Flink/Dataflow expose this as triggers: early speculative results, on-time result at the watermark, late refinements.

State, checkpoints & exactly-once

Windows, joins and deduplication all need state — counts per key, recent events, seen IDs — potentially terabytes of it. A stream processor must keep that state fast (local RocksDB on each worker) and survive crashes without double-counting.

Flink-style checkpointing: consistent snapshots of a running pipelineStep-through
  1. The coordinator injects a barrier for checkpoint #42 into the stream at source offset 1,000. Barriers flow with the data, dividing “before checkpoint” from “after”.
  2. When the barrier reaches the aggregator, it asynchronously uploads its state (counts per window/key) to durable storage — without stopping processing. This is the Chandy–Lamport snapshot algorithm.
  3. The sink has been writing results inside an open transaction (e.g. a Kafka transaction). On the barrier it pre-commits — durable but not yet visible to readers.
  4. Once every operator acknowledges, checkpoint #42 is complete: source offset 1,000 + all state + pre-committed output form one consistent cut. The sink commits (two-phase commit). Output becomes visible.
  5. A worker dies at offset 1,450. Flink restores state from checkpoint #42, rewinds Kafka to offset 1,000, and aborts the uncommitted sink transaction. Events 1,000–1,450 are reprocessed, but their earlier effects were never committed — exactly-once results end to end.
🎤
“Exactly-once” is about effects, not delivery

Events may be processed more than once internally; what's guaranteed is that state and output reflect each event exactly once. That requires replayable sources (Kafka), checkpointed state, and sinks that are either transactional or idempotent (upserts keyed by window + key). If your sink is “send an email”, you're back to idempotency keys (Chapter 17).

Lambda vs kappa architecture

λ Lambda

Run two pipelines: a batch layer recomputes accurate results from all history nightly; a speed layer gives approximate real-time results for today. A serving layer merges them.

+
  • Accurate batch as a safety net
−
  • Same logic written twice, in two frameworks, that drift apart

κ Kappa

Everything is a stream. Keep the event log long enough (Kafka tiered storage, or a lake) and when logic changes, start a new version of the streaming job from the beginning, let it catch up, then switch readers over.

+
  • One codebase, one semantics
−
  • Reprocessing years of data through a stream can be slow and costly

Modern engines blur the line: Flink and Spark Structured Streaming run the same code in batch or streaming mode, and Apache Beam (Google Dataflow) was designed around a unified model. Kafka Streams and ksqlDB suit lighter per-service stream processing; managed stream SQL (Materialize, RisingWave) exposes streams as continuously updated views.

NeedChoose

⚠️
Common mistakes
  • Using processing time when event time matters. Offline mobile events all land “now”, corrupting every time-based aggregate.
  • Assuming exactly-once delivery exists. It's exactly-once effects, via checkpointed state and idempotent or transactional sinks.
  • Ignoring skew. One hot key means one reducer or one partition does most of the work while the rest idle.
🎤
Interview drill

Design: Compute “active users in the last 5 minutes” for a live dashboard, correct within seconds.

How a strong answer sounds
A streaming job keyed by user, with a 5-minute sliding window over event time and a watermark allowing a small amount of lateness. Distinct counting per window uses HyperLogLog sketches so the state stays bounded and windows merge cleanly. Results are upserted into a serving store keyed by (window, dimension) so reprocessing overwrites rather than double-counts, and late events past the watermark go to a side output for a batch correction.

Trade-off: Lambda or kappa for a system whose numbers are used for billing?

How a strong answer sounds
Lambda, deliberately. Streaming gives the freshness product teams need; a nightly batch recompute over the immutable raw log gives the correctness finance needs, including late events and updated fraud rules. The cost is running the logic twice, so keep the streaming layer's job simple and treat the batch result as the source of truth for money, reconciling the two daily and alerting on drift.

🧠 Key takeaways

  • Keep analytics off the OLTP database; columnar OLAP stores read only needed columns and compress heavily.
  • MapReduce splits work into map, shuffle and reduce; Spark keeps a DAG in memory and recomputes lost partitions via lineage.
  • Batch jobs over immutable input are easy to retry and rerun; beware skewed keys.
  • ELT into a warehouse or lakehouse, modelled as facts and dimensions, orchestrated as a DAG with data-quality checks.
  • Streams aggregate over tumbling, sliding or session windows, using event time for correctness.
  • Watermarks decide when windows fire: longer delays are more complete but less fresh.
  • Checkpoint barriers plus replayable sources and transactional/idempotent sinks give exactly-once results.
  • Lambda runs batch and stream side by side; kappa uses one streaming path and replays the log.

Check your understanding

Why is SELECT SUM(amount) FROM sales WHERE year = 2025 much faster in a column store?

A row store must read every column of every row; a column store reads 2 of perhaps 100 columns, heavily compressed.

In MapReduce word count, which phase moves all “the” pairs from every mapper to a single reducer?

The shuffle hashes each key to a reducer and transfers the data over the network — usually the most expensive phase.

A mobile game computes “score per player per minute”. Phones buffer events offline and upload later. Which time should windows use?

Processing time would assign offline play to the upload minute. Event time places events correctly; watermarks bound how long to wait.

You reduce the watermark delay from 30 s to 1 s. What's the likely effect?

Watermarks trade completeness for freshness. Aggressive watermarks fire sooner and treat more stragglers as late.

What makes Flink's exactly-once guarantee hold across a crash?

After failure, input is replayed from the checkpointed offset, state is restored, and uncommitted output is discarded — effects happen once.
