Design Search Autocomplete

Type “sys” into a search box and “system design interview” appears before you finish the word. Typeahead (autocomplete) looks simple. In fact it's one of the busiest services in any search product. Every keystroke from every user is a request. And the answer must come back before the user types the next letter.

  • Estimate traffic when every keystroke is a request
  • Use a trie (prefix tree) that stores the top suggestions at each node
  • Build the trie in the background from sampled, totalled search logs
  • Shard and cache to answer in under 100ms worldwide
  • Cut requests with debouncing (waiting for a pause in typing) and caching in the browser
  • Keep suggestions fresh, add trending searches, and filter bad content

STEP 1 / 6

Requirements

🛠️ Functional

✓As the user types a prefix, return the top 5 completions
✓Ranked by popularity (how often people search it); only matches that start with the typed text
✓Filter offensive / unsafe suggestions
✓Out of scope for v1: spell correction, personal suggestions

📏 Non-functional

✓p99 < 100 ms end to end (99 of 100 requests) — faster than typing speed
✓Highly available; slightly out-of-date suggestions are fine
✓Freshness: popular new searches show up within hours (trending ones within minutes is a bonus)

Why 100 ms? A typical person types a key every 150–250 ms. If suggestions take longer than the gap between keys, they arrive for a prefix the user has already typed past, and the box feels laggy. Why is stale data fine? If “super bowl 2027” is ranked 3rd instead of 2nd for an hour, nobody is harmed. That one relaxed requirement is what lets us precompute everything and cache it everywhere.

5B searches × ~6 suggest calls = 30B requests a day. So answering must be a lookup in memory, not a database query. Counting billions of searches is a different story. It can run in the background and be approximate, because nobody notices if a suggestion's rank updates an hour late.

Here is the arithmetic behind each number, so you can redo it in an interview:

  • Search rate: a day has 86,400 seconds (round to ~100K). 5B ÷ 86,400 ≈ 58K searches/s, which is the “60K/s” you'll see in the pipeline below.
  • Suggest rate: without any tricks a 20-character query would send 20 requests. Debouncing (Step 5) merges fast bursts, leaving ~6. So 58K × 6 ≈ 350K requests/s on average. Traffic peaks at roughly 3× the average in busy hours, so plan for ~1M/s.
  • Trie size: 100M queries × ~20 characters is at most 2B trie nodes; shared prefixes (“how to …”) cut that to perhaps ~1B. If each node stores 5 suggestion IDs (5 × 8 bytes = 40 bytes) plus ~20–60 bytes for its children, that is ~60–100 bytes × 1B ≈ 60–100 GB.
  • Response bandwidth: 5 suggestions × ~25 bytes plus JSON and headers is about 500 bytes. 1M/s × 500 bytes = 500 MB/s (4 Gbit/s). That is a lot for one data center but easy for a CDN, which is why caching at the edge matters.

100 GB fits in a big server's memory, but not comfortably with room to load the next version beside it. Splitting it into ~10 shards of ~10 GB each makes a fresh copy quick to download and load, and spreads the 1M requests/s across many machines.

STEP 3 / 6

API

GET /v1/suggest?q=sys&locale=en-US&limit=5
→ 200 OK   Cache-Control: public, max-age=3600
{ "prefix": "sys", "suggestions": ["system design interview", "system of a down", "systemctl", …] }

It's a GET with no user data, and the same prefix always gives the same answer. So the browser, the CDN and every layer in between can cache it. That does a lot of the scaling work for us.

Two details make the caching actually work. First, normalize the prefix before using it as a cache key: lowercase it, trim spaces and collapse double spaces, so “Sys”, “sys ” and “sys” share one cache entry instead of three. Second, the max-age is a trade-off. One hour means an edge server may show last hour's ranking, which the requirements allow. A breaking-news phrase needs the separate trending path (Step 6) rather than a shorter cache time, because cutting max-age for everyone would multiply the load on the service.

STEP 4 / 6

The core data structure: a trie with cached top-K

A trie (prefix tree) stores strings one character at a time. Each node stands for a prefix, like “s”, “sy”, “sys”. Finding the “sys” node means walking just 3 steps.

The problem comes next. To find the most popular completions, we'd have to search every branch below “sys”. That could be millions of nodes. The fix: work out the top 5 completions ahead of time and store them in every node. A lookup then takes only as many steps as the prefix has letters, O(prefix length). It's like a dictionary with a “most looked-up words” list printed on each letter tab.

How do we fill in those lists without scanning everything? Work from the leaves up. A node's top 5 is the best 5 out of: its own query (if a search ends there) plus the top-5 lists of its children. Looking only at each child's top 5 is safe. If a query makes the parent's top 5, fewer than 5 queries in the parent's subtree beat it. The child's subtree is only part of the parent's, so even fewer beat it there, and it must be in the child's top 5 too. A tiny example with top-2 lists:

  • Queries: “sys design” (98K), “system of a down” (61K), “syd weather” (88K).
  • Both “sys…” queries sit below node “sys”, so its list is [sys design 98K, system of a down 61K].
  • Node “syd” has [syd weather 88K].
  • Node “sy” merges its children: from [98K, 61K] and [88K] it keeps [sys design 98K, syd weather 88K].

Each merge touches at most 5 items per child, so building all the lists is one pass over the trie. Ties (two queries with the same count) need a fixed tie-break, such as alphabetical order, or two servers could show them in different orders.

🧮 Memory trade-off

Storing 5 suggestions at every node uses a lot more memory. Ways to reduce it:

  • Store pointers/IDs to the end nodes instead of full strings.
  • Merge chains of nodes that have only one child (this is a radix tree).
  • Limit the depth: few people need suggestions after 30 characters.
  • Drop searches that are too rare.

🔀 Alternatives

A simpler v1: a key-value map from prefix → top-K list, worked out ahead of time for every prefix of every popular search. Keep it in Redis or a static file. Reads are just as fast, O(1), with no tree code. Elasticsearch's completion suggester uses an FST (finite state transducer), a compressed trie-like structure.

When to pick which. The prefix map stores every prefix as its own key: 100M queries × ~20 prefixes is up to 2B keys, each carrying a copy of its list. That is wasteful at web-search scale but perfectly fine for a few million product names or city names, where it's the fastest thing to build. Pick the trie (or an FST) when the query set is huge and memory is the limit. Pick a search engine's built-in suggester when you already run one and the traffic is moderate.

Building the trie: the data pipeline

Updating one shared trie on every search, 60K times a second, would mean locking millions of nodes. Instead, keep writing and reading apart. Total up the logs in the background, and every so often publish a brand-new, read-only (immutable) trie.

From search logs to served suggestionsStep-through
  1. When a user submits a search (not on every keystroke), an event goes to Kafka: the cleaned-up search text, language/region, and time. Fire and forget: it must never slow down the search itself.
  2. At 60K events a second, we don't need every event to know what's popular. Keeping 1 in 10 still gives the right ranking for anything that matters. A stream job counts searches per language/region in time windows. Older counts slowly fade (exponential decay), so last week matters more than last year. Count-min sketches (Chapter 20), a compact way to estimate counts, keep memory use limited.
  3. Every hour (or day), a batch job takes the top ~100M searches. It filters out offensive terms, personal data like phone numbers, and legal takedowns. Then it builds the trie and fills in the top list for every node, working up from the leaves.
  4. The trie is saved into files, one per shard, and uploaded with a version number. Because old versions never change, going back is easy if a bad build slips through.
  5. Suggest servers download the new version and load it into memory next to the old one. Then they switch over in one instant step (an atomic pointer swap). Reads need no locks, and always see one complete, consistent trie.
  6. Answers for popular prefixes (“a”, “we”, “how to”) are cached at the CDN edge for an hour, and in the browser. The many rare prefixes (the “long tail”) reach the service, which answers from memory in ~1 ms.
  7. A small real-time path watches for searches that suddenly spike in the last few minutes (breaking news). It uses sketches and “heavy-hitter” detection (finding the most frequent items). The service mixes these into the results, so users don't wait for the next hourly build.

Why sampling and decay give the right answer

Sampling. Keeping 1 event in 10 sounds risky, but popular queries have huge counts. A query searched 10,000 times an hour appears about 1,000 times in the sample. Random noise on a count of 1,000 is roughly ±√1,000 ≈ ±32, about 3%, so its rank barely moves. A query searched 5 times an hour might vanish from the sample, but it would never have made anyone's top 5 anyway. Multiply sampled counts by 10 if you need real-looking totals.

Decay. A score that just adds up all-time counts would keep last year's news on top forever. Instead, give each count a weight that halves every week (a half-life). Example: “world cup” had 4,000 searches four weeks ago and “new phone launch” had 1,000 last week. Weighted: 4,000 × ½⁴ = 250 versus 1,000 × ½¹ = 500. The recent query wins, even though its raw count is four times smaller. Tune the half-life to the product: days for news search, months for a product catalog.

What can go wrong in the pipeline

  • The builder crashes or runs late. Servers simply keep the last good version. Suggestions get a little older, which the requirements allow. Alert if the newest version is more than a few hours old.
  • A bad build. A bug could produce an empty or tiny trie. Before publishing, compare with the previous version: node count, and the top results for a fixed list of common prefixes. If they change too much (say the size drops by 20%), refuse to publish and page someone.
  • Memory during the swap. Old and new versions sit in memory side by side for a moment, so each server needs about twice the shard size free. That is another reason to keep shards small.
  • Kafka falls behind. Nothing breaks for users. Counts just arrive late, so freshness suffers. Logging must never block the search request, so if Kafka is down the client drops events rather than waiting.
STEP 5 / 6

Scaling the read path

✂️

Sharding the trie

The obvious idea is to split by first letter: a–m, n–z. But traffic is very uneven: far more searches start with “s” than “x”. Instead, build a shard map from past traffic so each shard gets a similar load (e.g. “s–sh”, “si–sz”). A small router, or the client library, finds the right shard from the prefix.

🧬

Replicas, not consistency

Each shard has many copies across regions, and any copy can answer. During a rollout, copies may briefly serve different versions. For suggestions, that's completely fine.

A sized example of a traffic-based split: say the service sees 400K requests/s after the CDN and you want 10 shards of ~40K each. From yesterday's logs you find prefixes starting with “s” carry 60K/s on their own, so “s” is cut into two ranges (“s–sh” and “si–sz”, ~30K each). Rare letters like “q”, “x”, “y” and “z” together carry under 40K, so they share one shard. The shard map is built along with each trie version, so routing and data always agree.

Two edge cases for the router. A one-letter prefix like “s” is so common that the CDN and browser answer nearly all of it, so it hardly reaches the shards. If a shard's replica fails, the router retries another replica of the same shard. If all copies of a shard are down, return an empty list: an autocomplete box with no suggestions is annoying, but the user can still search.

The cheapest request is the one you never send. The client (browser or app) can do a lot of the work:

🧪 Set debounce to 0 and auto-type: you get one request per character. At ~120 ms, bursts of fast typing shrink into a few requests. With the prefix cache on, backspacing reuses answers you already fetched. But set the debounce too high and suggestions feel slow.

How debounce works, step by step. Each keystroke starts (or restarts) a short timer, say 120 ms. A request is sent only when the timer runs out, meaning the user paused. Someone typing “system” at 80 ms per key never pauses for 120 ms, so the six keys become one request for “system”. The pause at the space before “design” fires another. That is how a 20-character query shrinks to ~6 requests.

One more client-side edge case: responses can arrive out of order. The request for “sy” might be slow and land after the answer for “sys”. If the client blindly shows whatever arrives last, the box shows suggestions for the wrong prefix. The fix is to tag each request with its prefix (or a sequence number) and ignore any response that doesn't match what is in the box now, or cancel older requests when a new one starts.

STEP 6 / 6

Deep dives & extensions

🧹

Filtering

Blocklists and ML classifiers remove hateful, sexual, violent or defamatory suggestions when the trie is built. An emergency blocklist is also checked when answering, for instant takedowns. Why both? Build-time filtering is thorough but only runs hourly; the serve-time list is small and fast, so a harmful suggestion can be removed in seconds.

🌐

Languages & locales

Build a separate trie per language/region. Normalize Unicode so the same text is always stored the same way. For Chinese, Japanese and Korean, also match on typed pinyin/romaji, not just the characters.

🙋

Personalization

Mix the global top list with the user's own recent searches (kept on the device or in a small per-user store) and their location. Keep the global part cacheable, and do the merging on the client.

🔤

Typo tolerance

Allow matches that are one typo away (edit distance 1: “sytem” → “system”) using automata over the trie. Only do this when there are few exact matches.

🧠

Beyond popularity

Rank with an ML model that uses how often and how recently something was searched, how often people click the suggestion, and context. Log which suggestions were shown and picked, to train it.

🛡️

Abuse

Bots can flood fake searches to push a phrase into suggestions. Count distinct users/IPs, not raw events, and rate-limit how many searches you log. For example, 50,000 searches from 20 accounts should count as 20 votes, not 50,000.

⚠️
Common mistakes
  • Querying the database on every keystroke. Suggestions must come from memory. A database can't survive that much traffic.
  • Updating the trie on every search. Rebuild it in the background and swap it in. Changing it live means locking something that's read millions of times a second.
  • Sharding by first letter. Traffic is very uneven across letters. Split into prefix ranges that carry equal traffic instead.
🎤
Interview drill

Design: Show personalized suggestions (your history first) while keeping results cacheable.

How a strong answer sounds
Keep the global suggestions fully cacheable (on the CDN, same for every user). Merge in personal history on the client, which already has it. If the server must personalize, fetch a small per-user list separately and combine the two. That's two cheap requests, and one of them is shared by everyone. It beats one per-user request on every keystroke that nothing can cache.

Extend: A breaking news phrase must appear in suggestions within two minutes.

How a strong answer sounds
The hourly trie build is too slow, so add a small real-time path. A streaming job spots searches spiking in short time windows, using heavy-hitter sketches. It publishes a small “trending” list, and the suggest service mixes it on top of the main trie when answering. Cap the list's size, run the same safety filters, and let entries expire on their own. That way yesterday's spike disappears without a rebuild.

🧠 Key takeaways

  • Autocomplete runs on every keystroke. Expect hundreds of thousands of requests per second, each answered in under 100ms.
  • A trie that stores the top suggestions at each node makes a lookup take one step per typed letter.
  • Keep writing and reading apart: sample and total the logs, build read-only tries in the background, and swap in new versions.
  • Shard by prefix ranges with equal traffic. Make many copies, since slightly old data is fine.
  • Cache heavily in the browser, at the CDN edge and in memory. Answers are public, and the same request always gets the same answer.
  • Debounce keystrokes and cache prefixes on the client to cut out most requests.
  • Add a real-time trending path, filtering, language support and optional personal suggestions.

Check your understanding

Why store the top-K completions at every trie node?

Working it out ahead of time moves the expensive part to build time. Every read becomes a short walk plus reading one list. It actually costs extra memory, and it makes updates more expensive (a count change must refresh every list above it), which is why the trie is rebuilt in batches.

Why not update the trie in place on every search?

Suggestions a few hours old are fine. So rebuild in batches and swap in one step, and reads never need locks.

Sharding the trie by first letter puts 15% of traffic on the “s” shard. Better approach?

Setting range boundaries by traffic balances the load, while similar prefixes still stay on the same shard.

What does client-side debouncing do?

Fast typists don't need suggestions for every half-typed prefix. Debouncing removes those requests.

A major news event happens; people start searching a brand-new phrase. How does it appear in suggestions within minutes?

A small streaming path keeps sudden spikes fresh. The big batch-built trie handles everything else.
