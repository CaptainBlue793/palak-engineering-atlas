Design Search Autocomplete

Type “sys” into a search box and “system design interview” appears before you finish the word. Typeahead looks trivial, but it's one of the highest-QPS services in any search product: every keystroke from every user is a request, and the answer must come back faster than the user can type the next letter.

  • Estimate keystroke-level traffic
  • Use a trie with cached top-K suggestions per node
  • Build the trie offline from sampled, aggregated query logs
  • Shard and cache for sub-100ms global latency
  • Cut requests with debouncing and client-side caching
  • Handle freshness, trending queries and content filtering
STEP 1 / 6

Requirements

🛠️ Functional

✓As the user types a prefix, return the top 5 completions
✓Ranked by popularity (query frequency), prefix match only
✓Filter offensive / unsafe suggestions
✓Out of scope for v1: spell correction, personalization

📏 Non-functional

✓p99 < 100 ms end to end — faster than typing speed
✓Highly available; stale suggestions are fine
✓Freshness: popular new queries appear within hours (trending within minutes is a bonus)

5B searches × ~6 suggest calls = 30B requests/day. The read path must be a memory lookup, not a query. Meanwhile the write path — counting billions of searches — can be asynchronous and approximate, because nobody notices if a suggestion's rank updates an hour late.

STEP 4 / 6

The core data structure: a trie with cached top-K

A trie (prefix tree) stores strings character by character; every node represents a prefix. Finding completions for “sys” means walking 3 nodes. But then we'd have to explore the entire subtree under “sys” to find the most popular completions — potentially millions of nodes. The fix: precompute and store the top 5 completions at every node. A lookup becomes O(prefix length).

🧮 Memory trade-off

Storing 5 suggestions at every node multiplies memory. Mitigations: store pointers/IDs to terminal nodes rather than strings, compress chains of single-child nodes (a radix tree), cap depth (few people need suggestions after 30 chars), and prune queries below a minimum frequency.

🔀 Alternatives

A simpler v1: a key-value map from prefix → top-K list (every prefix of every popular query, precomputed) in Redis or a static file — same O(1) read with no tree logic. Elasticsearch's completion suggester uses an FST (finite state transducer), a compressed trie-like structure.

Building the trie: the data pipeline

Updating a shared trie on every search at 60K searches/second would need locking across millions of nodes. Instead, separate the write path from the read path: aggregate logs asynchronously and publish a new immutable trie periodically.

From search logs to served suggestionsStep-through
  1. When a user submits a search (not every keystroke), a query event goes to Kafka: normalized query text, locale, timestamp. Fire-and-forget — it must never slow the search itself.
  2. At 60K events/sec we don't need every event to know what's popular — sampling 1 in 10 preserves rankings for anything meaningful. A stream job counts queries per locale in windows, with exponential decay so last week matters more than last year. Count-min sketches (Chapter 20) keep memory bounded.
  3. Hourly (or daily), a batch job takes the top ~100M queries, applies filters (offensive terms, PII like phone numbers, legal takedowns), builds the trie and computes top-K bottom-up for every node.
  4. The trie is serialized into shard files and uploaded with a version number. Immutable snapshots make rollback trivial if a bad build slips through.
  5. Suggest servers download the new version, load it into memory next to the old one, then atomically swap the pointer. No locks on the read path: reads always see one complete, consistent trie.
  6. Responses for popular prefixes (“a”, “we”, “how to”) are cached at the CDN edge for an hour and in the browser. The long tail hits the service, which answers from RAM in ~1 ms.
  7. A small real-time path tracks queries spiking in the last minutes (breaking news) using sketches and heavy-hitter detection, and the service blends them into results — so users don't wait for the next hourly build.
STEP 5 / 6

Scaling the read path

✂️

Sharding the trie

Naively shard by first letter: a–m, n–z. But traffic is wildly skewed — far more queries start with “s” than “x”. Build a shard map from historical traffic so each shard carries similar load (e.g. “s–sh”, “si–sz”). A lightweight router or the client library looks up the shard by prefix.

🧬

Replicas, not consistency

Each shard is replicated many times across regions; any replica can answer. Replicas can briefly serve different snapshot versions during rollout — completely fine for suggestions.

The cheapest request is the one never sent. Clients do a lot of the heavy lifting:

STEP 6 / 6

Deep dives & extensions

🧹

Filtering

Blocklists and ML classifiers remove hateful, sexual, violent or defamatory completions at build time, plus an emergency blocklist applied at serve time for instant takedowns.

🌐

Languages & locales

Separate tries per locale; Unicode normalization; for CJK languages, match on pinyin/romaji input as well as characters.

🙋

Personalization

Blend global top-K with the user's own recent searches (stored client-side or in a small per-user store) and location. Keep the global part cacheable; merge on the client.

🔤

Typo tolerance

Fuzzy prefix matching within edit distance 1 (“sytem” → “system”) using automata over the trie, applied only when exact matches are few.

🧠

Beyond popularity

Rank with an ML model: frequency, recency, click-through on suggestions, and context. Log impressions and selections to feed it.

🛡️

Abuse

Bots can pump fake searches to push a phrase into suggestions. Count distinct users/IPs, not raw events, and rate-limit query logging.

⚠️
Common mistakes
  • Querying the database per keystroke. Suggestions must come from memory; the database can't survive keystroke-rate traffic.
  • Updating the trie on every search. Rebuild offline and hot-swap; live mutation means locking a structure that's read millions of times a second.
  • Sharding by first letter. Traffic is wildly skewed by letter — split by traffic-balanced prefix ranges instead.
🎤
Interview drill

Design: Show personalized suggestions (your history first) while keeping results cacheable.

How a strong answer sounds
Keep the global suggestions fully cacheable (CDN, no user dimension) and merge personal history on the client, which already has it locally. If server-side personalization is required, fetch a small per-user list separately and combine — two cheap requests, one of which is shared by everyone, rather than one uncacheable per-user request at keystroke rate.

Extend: A breaking news phrase must appear in suggestions within two minutes.

How a strong answer sounds
The hourly trie build is too slow, so run a small real-time path: a streaming job detects queries spiking in short windows with heavy-hitter sketches, publishes a compact “trending” overlay, and the suggest service merges it over the static trie at query time. Cap the overlay's size, apply the same safety filters, and let it expire automatically so yesterday's spike disappears without a rebuild.

🧠 Key takeaways

  • Autocomplete is keystroke-driven: expect hundreds of thousands of QPS with a sub-100ms budget.
  • A trie with precomputed top-K at each node makes lookups O(prefix length).
  • Separate write and read paths: sample and aggregate logs, build immutable tries offline, hot-swap snapshots.
  • Shard by traffic-balanced prefix ranges; replicate freely since slight staleness is fine.
  • Cache heavily: browser, CDN edge and in-memory; responses are public and idempotent.
  • Debounce keystrokes and cache prefixes on the client to eliminate most requests.
  • Add a real-time trending path, filtering, locale support and optional personalization.

Check your understanding

Why store the top-K completions at every trie node?

Precomputation moves the expensive work to build time, making every read a short walk plus a list read.

Why not update the trie in place on every search?

Freshness of hours is acceptable, so batch rebuilds with atomic swaps keep reads lock-free.

Sharding the trie by first letter puts 15% of traffic on the “s” shard. Better approach?

Traffic-aware range boundaries balance load while preserving prefix locality.

What does client-side debouncing do?

Fast typists don't need suggestions for every intermediate prefix; debouncing removes those requests.

A major news event happens; people start searching a brand-new phrase. How does it appear in suggestions within minutes?

A small streaming path handles freshness for spikes while the heavy batch trie handles the long tail.
