Message Queues & Event-Driven Design

Not everything needs to happen right now. Queues let services hand off work, absorb traffic spikes, and stay decoupled — so one slow or broken component doesn't drag everything else down with it.

  • Know when to go async
  • See how queues absorb spikes & create backpressure

  • Understand Kafka partitions & consumer groups
  • Reason about at-most / at-least / exactly-once
  • Apply event-driven patterns (event sourcing, CQRS)

Synchronous vs asynchronous

In a synchronous call, the caller waits for the answer. In an asynchronous design, the caller drops a message somewhere durable and moves on; a worker picks it up later.

🧾
Analogy: the restaurant ticket rail

The waiter doesn't stand in the kitchen until your steak is cooked. They clip the order ticket on the rail and go serve other tables. Cooks take tickets at their own pace. If there's a rush, tickets pile up on the rail — but the waiters keep taking orders. The rail is a queue.

Queues absorb spikes

A queue is a buffer between how fast work arrives and how fast it can be done. Play with the rates. If arrivals exceed capacity for long, the queue grows without bound — that's your cue to add consumers (or apply backpressure).

Backpressure

A queue can't grow forever — memory and disk run out, and ancient messages may be useless. Backpressure pushes the problem upstream: bounded queues that reject or block producers, 429 Too Many Requests to clients, or shedding low-priority work. Better to fail fast than to fall over slowly.

Kafka: partitions & consumer groups

A Kafka topic is split into partitions — each an ordered, append-only log. Partitions are the unit of parallelism: within a consumer group, each partition is read by exactly one consumer. Messages with the same key always land in the same partition, so they stay in order.

Delivery guarantees

Networks and consumers fail. When a consumer crashes mid-message, did the work happen? The answer depends on when the consumer acknowledges the message.

Consumer crashes while sending a “receipt email”Simulator

At-most-once

Ack before processing. Crash → message lost, never retried. OK for metrics sampling, non-critical logs.

At-least-once

Ack after processing. Crash → redelivered → possibly processed twice. The default in most systems.

Exactly-once (effectively)

At-least-once delivery + idempotent processing (dedupe by message ID) or transactional writes. True exactly-once delivery over a network is impossible; exactly-once effect is achievable.

Operational must-haves

☠️

Dead-letter queue (DLQ)

What about “poison” messages?
A malformed message that always crashes the consumer would be retried forever, blocking the queue. After N failed attempts, move it to a dead-letter queue for humans to inspect. Alert on DLQ depth.
🔁

Retries with backoff

Downstream is temporarily broken…
Retry with exponential backoff + jitter (1s, 2s, 4s…) so a recovering service isn't hammered. Many queues support delayed redelivery / visibility timeouts. See Chapter 16.
🔢

Ordering

Do messages arrive in order?
Standard queues with many consumers don't guarantee order. If order matters for an entity (a user's account events), route by key to one partition (Kafka) or use FIFO queues with message group IDs (SQS FIFO).
📤

Transactional outbox

Save to DB and publish — atomically?
Writing to the DB and then publishing can fail in between. Instead, write the event into an outbox table in the same DB transaction; a relay process (or CDC like Debezium) publishes rows from the outbox. No lost or phantom events.

Event-driven architecture patterns

Services emit small events like OrderPlaced {orderId: 91}. Interested services react and, if needed, call back for details. Minimal coupling — but consumers may need follow-up requests.

Events contain the full data consumers need: OrderPlaced {orderId, items, address, total}. Consumers keep their own local copy and never call back. Great for autonomy and availability; bigger messages and data duplication.

Instead of storing current state, store the sequence of events that led to it. State is derived by replaying events. You get a perfect audit trail and can rebuild views or debug “how did we get here?”.

// Bank account 881 — the events ARE the source of truth
AccountOpened   { owner: "ada" }
MoneyDeposited  { amount: 100 }
MoneyWithdrawn  { amount: 30 }
MoneyDeposited  { amount: 5 }
// replay → balance = 75. Snapshots avoid replaying millions of events.

Costs: schema evolution of old events, eventual consistency of read models, and a steeper learning curve.

Command Query Responsibility Segregation: use separate models for writes and reads. Commands update a normalised write store; events update one or more denormalised read stores optimised for each query (a search index, a cache, a reporting DB).

Reach for a queue when you hear: “send notifications”, “process uploads/videos”, “handle spikes”, “update search index / analytics”, “fan out to followers”. Then immediately address: delivery guarantee, idempotency, ordering, and what happens when consumers fall behind.

Inside the log: replication, retention & compaction

Kafka-style logs are the backbone of most event-driven systems, so it's worth knowing what's happening under the API you call.

🧬

Partitions are replicated

Each partition has a leader and followers. Followers that have caught up form the in-sync replica (ISR) set. With acks=all and min.insync.replicas=2, a write is acknowledged only once it's on at least two replicas — so a single broker loss can't lose it. acks=1 is faster and can lose the tail on a leader crash; acks=0 is fire-and-forget.

📜

Retention: time or size

Unlike a queue, consuming does not delete. Messages live for retention.ms (7 days by default) or until a size cap, which is what makes replay possible. Tiered storage pushes older segments to object storage so you can keep months cheaply (Chapter 9).

🗜️

Log compaction

With cleanup.policy=compact, Kafka keeps only the latest value per key forever. The topic becomes a replayable snapshot of current state — perfect for CDC streams and config/state topics that new consumers bootstrap from (Chapter 17).

🔀

Consumer groups & rebalancing

Partitions are divided among the consumers in a group. When one joins, leaves or stalls, the group rebalances — briefly pausing consumption. Frequent rebalances (from slow processing exceeding max.poll.interval.ms) look like a mysterious throughput collapse; cooperative/static membership reduces the pain.

Partition count sets your maximum consumer parallelism — you can't have more active consumers in a group than partitions, and increasing partitions later breaks key→partition ordering for existing keys. Over-provision modestly (and remember that idle partitions still cost broker memory and file handles).

🎯
Exactly-once in Kafka, precisely

Kafka transactions let a consumer read, process and produce results atomically (“consume-transform-produce”), committing offsets and output together. That gives exactly-once within Kafka. The moment your side effect is an external API call or a database write, you're back to idempotency keys and the outbox pattern (Chapter 17).

⚠️
Common mistakes
  • Using a queue to hide a capacity problem. If consumers are permanently slower than producers, the queue only delays the failure and adds latency.
  • Assuming ordering across partitions. Ordering is per partition/key only; design keys so causally related events share one.
  • No dead-letter queue or poison-message handling. One bad message reprocessed forever blocks a partition and looks like an outage.
🎤
Interview drill

Design: Order events must be processed in order per customer, but you need 200 consumers. How?

How a strong answer sounds
Partition by customer_id so all of one customer's events land on one partition and are consumed in order by one consumer in the group; parallelism comes from having many partitions (≥ 200), not from consuming a partition concurrently. If one customer is enormous, sub-key by (customer_id, aggregate_id) where ordering is only needed within an aggregate. State the trade-off: you can't exceed partition count in parallelism, and repartitioning breaks existing key→partition ordering.

Failure: A consumer group has been down for 6 hours. What happens when it comes back?

How a strong answer sounds
Nothing was lost if retention exceeds the outage — the log keeps messages regardless of consumption — but there's now a 6-hour backlog. On restart the group replays from its committed offsets, so the immediate risks are (a) overwhelming downstream systems, so rate-limit or scale consumers, (b) acting on stale events — drop notifications past their useful age, and (c) duplicate side effects on the messages that were in flight, which is why handlers are idempotent.

🧠 Key takeaways

  • Go async for slow, failure-prone or fan-out work that the user doesn't need to wait for.
  • Queues decouple services and level load; sustained overload still needs more consumers or backpressure.
  • Queue = one consumer per message; pub/sub = all subscribers; log = retained, replayable, per-group offsets.
  • Kafka parallelism = number of partitions; same key → same partition → ordered.
  • At-least-once + idempotent consumers is the practical path to exactly-once effects.
  • Use DLQs, backoff, the outbox pattern, and monitor consumer lag.

Check your understanding

A Kafka topic has 4 partitions. You run 6 consumers in one group. What happens?

Each partition is consumed by exactly one consumer in a group. To scale beyond 4, add partitions.

A new “fraud check” service must react to every order, alongside existing email and analytics services. Which model fits?

In a shared work queue each message goes to only one consumer. Fan-out needs pub/sub or separate consumer groups on a log.

Your consumer uses at-least-once delivery to charge credit cards. What else is essential?

Redeliveries will happen. Idempotency ensures a duplicate delivery doesn't cause a duplicate charge.

All events for a given bank account must be processed in order. With Kafka, how?

Same key → same partition → strict order within that partition, while other accounts are processed in parallel.

One malformed message crashes your consumer every time, and the queue stops moving. Fix?

A DLQ isolates poison messages so the rest of the queue keeps flowing.
