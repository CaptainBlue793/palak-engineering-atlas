Message Queues & Event-Driven Design

Not everything has to happen right now. A queue is a waiting line for work. It lets one service hand a job to another, soak up traffic spikes, and keep the two services independent, so one slow or broken part doesn't drag everything else down with it.

Synchronous vs asynchronous

In a synchronous call, the caller waits for the answer before doing anything else. In an asynchronous design, the caller leaves a message somewhere safe and carries on. A worker picks the message up later and does the job.

Why does this matter? Take a checkout that, after saving the order, calls three services in a row: payment (200 ms), email (300 ms) and analytics (150 ms). Done synchronously, the customer waits 650 ms, and if the email service is down, the whole checkout fails even though the order is fine. Done asynchronously, checkout charges the card, drops an OrderPlaced message on a queue and replies in about 200 ms. Email and analytics read the message whenever they're ready. A broken email service now means "receipts are late", not "nobody can buy anything".

When to stay synchronous: when the user needs the answer to continue. Checking a password, showing a search result or confirming a card was charged must happen in the request. When to go async: when the work is slow, can fail and be retried, or is a side effect the user doesn't need to see right away, like sending emails, resizing images or updating analytics.

🧾
Analogy: the restaurant ticket rail

The waiter doesn't stand in the kitchen until your steak is cooked. They clip the order ticket on the rail and go serve other tables. Cooks take tickets at their own pace. If there's a rush, tickets pile up on the rail — but the waiters keep taking orders. The rail is a queue.

Queues absorb spikes

A queue sits between how fast work arrives and how fast it can be done. Play with the rates below. If work arrives faster than you can handle it for long, the queue just keeps growing. That's your signal to add consumers, or to push back on the senders (backpressure).

The maths is simple enough to do in your head. Each consumer handles one message at a time, so its rate is 1 ÷ time per message. With 3 consumers at 400 ms each, capacity is 3 × 2.5 = 7.5 messages/sec. If 8 messages/sec arrive, the queue grows by 0.5 per second: 30 per minute, 1,800 per hour. It never drains on its own. If instead a spike of 150 messages lands on a system with spare capacity of 2 messages/sec, the backlog clears in 150 ÷ 2 = 75 seconds. That's the whole job of a queue: a short burst becomes a short delay instead of an error.

Backpressure

A queue can't grow forever. Memory and disk run out, and very old messages are often useless anyway. Backpressure means passing the problem back to whoever is sending the work. You can cap the queue size and reject or pause producers, return 429 Too Many Requests to clients, or drop low-priority work. It's better to fail fast and clearly than to slowly fall over.

How to choose. Ask two questions. First: should each message be handled by one worker (resize this image once) or by every interested service (email, analytics and fraud all react to an order)? One worker means a queue; every service means pub/sub or a log. Second: will anyone ever need to read old messages again, for example to rebuild a search index or to let a brand-new service catch up on last week's orders? If yes, use a log, because queues and plain pub/sub forget a message once it's delivered. A log costs more to run, so for a simple background-job system a plain queue is usually the right call.

Kafka: partitions & consumer groups

A Kafka topic (a named stream of messages, like “orders”) is split into partitions. Each partition is an ordered list that you can only add to at the end.

Partitions are how Kafka runs work in parallel. Inside a consumer group (a team of consumers sharing the work), each partition is read by exactly one consumer. Messages with the same key (say, the same customer ID) always go to the same partition, so they stay in order.

How does a key pick a partition? The producer hashes the key and takes the remainder: partition = hash(key) % number_of_partitions. With 3 partitions, if hash("cust-42") is 1,000,001, then 1,000,001 % 3 = 2, so every event for cust-42 goes to partition 2, every time. Each message in a partition gets a position number called an offset (0, 1, 2, …). A consumer remembers "I've finished up to offset 57", so after a restart it carries on from 58. Note the formula: if you change the partition count from 3 to 4, the same key can land on a different partition, which is why adding partitions later breaks ordering.

Delivery guarantees

Networks and consumers fail. If a consumer crashes halfway through a message, did the work happen or not? The answer depends on when the consumer acknowledges (acks) the message: the moment it tells the broker “I've got this, you can delete it”.

Consumer crashes while sending a “receipt email”Simulator

At-most-once

Ack before doing the work. If it crashes, the message is gone and is never retried. Fine for sampled metrics and unimportant logs.

At-least-once

Ack after doing the work. If it crashes, the message comes back, so the work may happen twice. This is the default in most systems.

Exactly-once (effectively)

At-least-once delivery, plus idempotent handling: doing it twice has the same result as doing it once (skip message IDs you've already seen), or write everything in one transaction. Truly delivering a message exactly once over a network is impossible. Getting the exact effect once is achievable.

Why is true exactly-once delivery impossible? Because it runs into the partial-failure problem from Chapter 13. The consumer does the work, then sends "ack". If that ack is lost, the broker can't tell "the consumer never did it" from "it did it but the ack vanished". It has to pick: redeliver (maybe a duplicate) or don't (maybe lost). So you pick at-least-once and make duplicates harmless. Here is what that looks like for message #42, "send receipt for order 91":

  1. Consumer receives #42. It checks a processed_messages table: #42 isn't there.
  2. It sends the email and inserts #42 into the table.
  3. It crashes before sending the ack. The broker redelivers #42 a minute later.
  4. The consumer checks the table, finds #42 already there, skips the work and just acks.

The customer gets one email. One gap remains: a crash in step 2, after the email is sent but before the ID is saved, still gives a second email. For email that's usually acceptable. For money, you pass the message ID as an idempotency key to the payment provider, so the provider itself refuses the duplicate charge.

Operational must-haves

A queue that works in a demo can still fail badly in production. The four cards below cover the problems every real queue meets sooner or later. The number to watch on a dashboard is consumer lag: how many messages (or how many seconds of messages) are waiting that consumers haven't handled yet. Lag that keeps rising is the earliest sign that something below is going wrong.

☠️

Dead-letter queue (DLQ)

What about “poison” messages?
A broken message that crashes the consumer every time would be retried forever, blocking everything behind it. After a set number of failed attempts, move it to a dead-letter queue so people can look at it. Raise an alert when that queue fills up.
🔁

Retries with backoff

Downstream is temporarily broken…
Wait longer between each retry (exponential backoff: 1s, 2s, 4s…) and add a little randomness (jitter) so all clients don't retry at the same instant. That way a recovering service isn't flooded. Many queues can delay redelivery for you. See Chapter 16.
🔢

Ordering

Do messages arrive in order?
Ordinary queues read by several consumers make no promise about order. If order matters for one thing (all events for one bank account), send by key to a single partition (Kafka), or use FIFO queues with message group IDs (SQS FIFO).
📤

Transactional outbox

Save to DB and publish — atomically?
If you save to the database and then publish the event, a crash in between leaves the two out of step. Instead, write the event into an outbox table in the same database transaction as the data. A separate relay process (or a CDC tool like Debezium) then publishes those rows. No lost events, and no events for data that was never saved.

Event-driven architecture patterns

Once services talk through events, you still have to decide what goes in an event and where the truth lives. These four patterns are the common answers. They aren't competitors: many systems use event notification for most things and event sourcing only for one core area, like a ledger.

Services send small events like OrderPlaced {orderId: 91}: just “this happened”. Interested services react, and call back for the details if they need them. The services stay loosely connected, but consumers often need extra requests.

Each event carries all the data consumers need: OrderPlaced {orderId, items, address, total}. Consumers keep their own copy and never call back. That makes them independent and available even if the sender is down. The cost is bigger messages and the same data stored in several places.

Instead of storing the current state, store the list of events that produced it, like a bank statement rather than just a balance. You work out the state by replaying the events. You get a perfect history, and you can rebuild views or answer “how did we get here?”.

// Bank account 881 — the events ARE the source of truth
AccountOpened   { owner: "ada" }
MoneyDeposited  { amount: 100 }
MoneyWithdrawn  { amount: 30 }
MoneyDeposited  { amount: 5 }
// replay → balance = 75. Snapshots avoid replaying millions of events.

The costs: old events still have to be readable when their format changes, the views built from events lag slightly behind, and the whole idea takes a while to learn.

A snapshot is a saved copy of the state at some point, such as "balance = 75 after event 4". To rebuild, you load the latest snapshot and replay only the events after it. Event sourcing earns its keep where history is the product: bank ledgers, audit trails, order workflows. For a simple user-profile table it's usually overkill.

Command Query Responsibility Segregation means using different models for writing and for reading. Commands (writes) update one tidy, non-duplicated store. Events then update one or more read stores, each shaped for a specific query, with data pre-joined and duplicated: a search index, a cache, a reporting database.

Use CQRS when reads and writes look very different: for example, writes are simple order updates but reads need full-text search, dashboards and a per-customer summary. Skip it for plain CRUD screens, where one database serves both well. The cost to remember: a user may save a change and not see it in a read model for a moment, so the UI has to cope with that lag.

Inside the log: replication, retention & compaction

Kafka-style logs are the backbone of most event-driven systems. It's worth knowing what happens beneath the simple API you call.

🧬

Partitions are replicated

Each partition has one leader copy and several follower copies. Followers that are fully caught up are called the in-sync replicas (ISR). With acks=all and min.insync.replicas=2, a write is only confirmed once at least two replicas have it, so losing one broker can't lose the message. acks=1 is faster but can lose the most recent messages if the leader crashes. acks=0 means send and never check.

📜

Retention: time or size

Unlike a queue, reading a message does not delete it. Messages stay for retention.ms (7 days by default), or until the topic hits a size limit. That's what makes replay possible. Tiered storage moves older parts to cheap object storage, so you can keep months of history (Chapter 9).

🗜️

Log compaction

With cleanup.policy=compact, Kafka keeps only the newest value for each key, forever. The topic becomes a replayable snapshot of the current state. That's perfect for CDC streams, and for config or state topics that a new consumer reads from scratch to catch up (Chapter 17).

🔀

Consumer groups & rebalancing

The partitions are shared out among the consumers in a group. When a consumer joins, leaves or stalls, the group rebalances: it redistributes partitions, pausing reads for a moment. If processing is so slow that a consumer misses its max.poll.interval.ms deadline, rebalances happen again and again, and throughput mysteriously collapses. Cooperative rebalancing and static membership reduce the pain.

Here's a sizing example you can check by hand. An app produces 20,000 events/sec, each about 1 KB. That's 20 MB/sec. Over 7 days of retention: 20 MB × 86,400 s × 7 ≈ 12 TB, and with 3 copies for safety, about 36 TB of broker disk. If one consumer can handle 2,000 events/sec, you need at least 20,000 ÷ 2,000 = 10 partitions just to keep up. Round up to, say, 24 or 30 so you have room to catch up after an outage and to grow. The number of partitions sets the maximum number of consumers working at once. A group can't have more active consumers than partitions. Adding partitions later sends existing keys to different partitions, which breaks their ordering. So allow a little room to grow, but remember that unused partitions still cost broker memory and open files.

🎯
Exactly-once in Kafka, precisely

Kafka transactions let a consumer read a message, process it, and write the result as one all-or-nothing step (“consume-transform-produce”). The new position and the output are saved together. That gives exactly-once inside Kafka. As soon as the work involves an outside API call or another database, you're back to idempotency keys and the outbox pattern (Chapter 17).

⚠️
Common mistakes
  • Using a queue to hide a capacity problem. If consumers are permanently slower than producers, the queue only delays the failure and makes everything slower.
  • Expecting order across partitions. Order is only guaranteed within one partition (one key). Choose keys so that related events share a partition.
  • No dead-letter queue and no plan for bad messages. One bad message retried forever blocks a partition and looks just like an outage.
🎤
Interview drill

Design: Order events must be processed in order per customer, but you need 200 consumers. How?

How a strong answer sounds
Use customer_id as the key, so all of one customer's events land on one partition and one consumer reads them in order. You get parallelism from having many partitions (at least 200), not from several consumers sharing a partition. If one customer is enormous, use a finer key like (customer_id, aggregate_id) wherever order only matters within that smaller unit. Say the trade-off out loud: you can't run more consumers than partitions, and changing the partition count reshuffles existing keys and breaks their ordering.

Failure: A consumer group has been down for 6 hours. What happens when it comes back?

How a strong answer sounds
Nothing is lost as long as the retention period is longer than the outage, because the log keeps messages whether or not anyone reads them. But there's now a 6-hour backlog. On restart, the group carries on from its saved positions. Three risks follow. (a) It can overwhelm the systems it calls, so rate-limit or add consumers carefully. (b) It may act on events that are now too old, so drop notifications past their useful age. (c) Messages that were mid-flight may be processed twice, which is why handlers must be idempotent.

🧠 Key takeaways

  • Go asynchronous for work that is slow, likely to fail, or sent to many services, when the user doesn't need to wait for it.
  • Queues keep services independent and smooth out bursts. But if overload lasts, you still need more consumers or backpressure.
  • Queue: each message goes to one consumer. Pub/sub: to every subscriber. Log: kept and replayable, with each group tracking its own position.
  • In Kafka, the number of partitions caps how much runs in parallel. The same key always goes to the same partition, so those messages stay in order.
  • At-least-once delivery plus idempotent consumers is the practical way to get an exactly-once effect.
  • Use dead-letter queues, retry backoff and the outbox pattern, and watch how far behind your consumers are (consumer lag).

Check your understanding

A Kafka topic has 4 partitions. You run 6 consumers in one group. What happens?

Each partition is read by exactly one consumer in a group. To use more than 4 consumers, you need more partitions.

A new “fraud check” service must react to every order, alongside existing email and analytics services. Which model fits?

In a shared work queue, each message goes to only one consumer, so two services would miss it. Sending to everyone needs pub/sub, or a log with a separate consumer group per service.

Your consumer uses at-least-once delivery to charge credit cards. What else is essential?

Messages will sometimes be delivered again. Idempotency makes sure a repeat delivery doesn't charge the customer twice.

All events for a given bank account must be processed in order. With Kafka, how?

The same key always goes to the same partition, and one partition is read in strict order. Meanwhile, other accounts are processed at the same time on other partitions.

One malformed message crashes your consumer every time, and the queue stops moving. Fix?

A dead-letter queue puts the bad message to one side so the rest of the queue keeps moving.
