Graph & Social Data

Followers, friends, org charts, permissions, fraud rings, recommendations, dependency trees — a huge share of interesting data is relationships. Relational databases store relationships fine but traverse them badly, and “who are the friends of my friends?” turns into a query that melts a production database.

  • See why multi-hop queries explode in SQL
  • Model graphs as edge tables, adjacency lists or property graphs
  • Traverse efficiently — including bidirectional search
  • Build “people you may know” from mutual friends
  • Understand how Facebook-scale social graphs are actually served
  • Know when a graph database is (and isn't) the answer

The multi-hop problem

In SQL, each hop is another self-join on the friendship table. With an average of 200 friends each, one hop touches 200 rows, two hops 40,000, three hops 8 million — and the database does a lot of duplicate work because most of those paths lead to the same people.

-- "Friends of friends of friends" — three self-joins, exponential intermediate rows
SELECT DISTINCT f3.friend_id FROM friends f1
  JOIN friends f2 ON f2.user_id = f1.friend_id
  JOIN friends f3 ON f3.user_id = f2.friend_id
WHERE f1.user_id = 42;

Real social graphs are “small world”: with 200 friends each, almost everyone is within 4–5 hops. So unbounded traversals don't just get slow — they end up returning half the planet. Practical systems cap depth, cap fan-out per node, and rank aggressively.

Three ways to store a graph

A simple table of (from_id, to_id, type, created_at) with indexes both ways. Transactional, familiar and perfectly good for one or two hops.

CREATE TABLE edges (
  from_id  BIGINT, to_id BIGINT, type SMALLINT, created_at TIMESTAMPTZ,
  PRIMARY KEY (from_id, type, to_id)          -- "who do I follow?" is a range scan
);
CREATE INDEX ON edges (to_id, type, from_id);    -- "who follows me?" — the reverse index

Sharded by from_id, so one user's outgoing edges live together. The reverse index must be maintained separately — often as a second row written in the same transaction, or asynchronously via an outbox (Chapter 17).

Store each node's neighbours as a single value: a list, a wide-column row, or a Redis sorted set. One key lookup returns the whole neighbourhood, which is exactly what a traversal wants.

# Redis / wide-column shape
following:42        → [17, 88, 1201, …]        # sorted set scored by time
followers:42        → [3, 17, 954, …]
counts:42           → {following: 312, followers: 11840}   # denormalized counters
Strengths
  • One read per hop, no joins
  • Trivially cacheable and shardable by node
  • Fast “is A connected to B?” with a set membership check
Weaknesses
  • Huge lists for celebrities (millions of entries)
  • Two writes per edge (both directions) → consistency work
  • No ad-hoc query language

A dedicated graph database stores nodes and edges as first-class objects with properties, and uses index-free adjacency: each node holds direct pointers to its edges, so a hop is a pointer dereference rather than an index lookup.

// Cypher (Neo4j): people my friends know, that I don't, ranked by mutual friends
MATCH (me:Person {id: 42})-[:FRIEND]->(f)-[:FRIEND]->(fof)
WHERE fof <> me AND NOT (me)-[:FRIEND]->(fof)
RETURN fof.name, count(f) AS mutuals
ORDER BY mutuals DESC LIMIT 10;

Good when the shape of the traversal is the query: fraud rings, supply chains, permissions hierarchies, knowledge graphs. Less good as a primary store for high-volume transactional data, and horizontal scaling is genuinely hard (see below).

Shortest path: search from both ends

“How am I connected to this person?” is a shortest-path query. A one-directional BFS to depth 4 with 200 friends each visits ~1.6 billion nodes. Searching from both endpoints and meeting in the middle visits two searches of depth 2 instead — roughly the square root of the work.

How a social graph is really served

Facebook's TAO is the canonical design, and it's deliberately boring: the source of truth is sharded MySQL, and everything fast is caching.

A read-mostly graph serviceStep-through
  1. The API is deliberately tiny: obj_get(id), assoc_get(id, type, limit), assoc_count(id, type), assoc_range. No ad-hoc queries means every access pattern is bounded and cacheable.
  2. A follower cache near the application absorbs most reads. On a miss it asks the leader cache for that shard, which serializes writes and protects the database from stampedes (Chapter 6).
  3. Cache hit rates are in the high 90s, so MySQL sees a trickle. Edges are sharded by from_id, so a neighbourhood read is a single-shard range scan.
  4. A new friendship writes the edge, bumps the counter, and invalidates the affected cache entries in every region. Counts are denormalized because COUNT(*) on 10 million followers is not a thing you do per page view.
  5. “A follows B” also needs B's follower list. That second write is asynchronous and idempotent, so the two directions can be briefly inconsistent — an accepted trade-off at this scale (Chapter 17).
⭐

Celebrity nodes

A node with 100M edges breaks every assumption: you can't read the list, cache it, or fan out to it. Store counts separately, page the list, and treat celebrities as a special case (Chapter 27's hybrid fan-out).

✂️

Partitioning is genuinely hard

Splitting a graph means cutting edges, and every cut edge becomes a network call. Balanced graph partitioning is NP-hard, so systems shard by node ID and accept cross-shard edges — another reason to keep traversals shallow.

🔒

Privacy at read time

Visibility (blocked, private, friends-only) must be applied on every read of a relationship, which is a per-viewer authorization check on potentially thousands of edges (Chapter 11). Precomputed results still need filtering before display.

Online vs offline

Heavy algorithms (PageRank, communities, embeddings) run offline over a snapshot of the graph in a batch system (Spark GraphX, Pregel-style engines) and publish results to a fast store. Online serving only does 1–2 hop lookups plus a ranking model. Confusing the two is the classic design mistake here.

Do you actually need a graph database?

Reach for one when…
  • Variable-depth traversals are the core query (“how is X connected to Y?”)
  • The schema is genuinely heterogeneous: many node and edge types with properties
  • Analysts need to explore relationships ad hoc
  • The dataset fits comfortably on a few machines
Stick to SQL/KV when…
  • Queries are 1–2 hops (“my followers”, “my permissions”) — an indexed edge table is faster and simpler
  • You need extreme write throughput or petabyte scale
  • You'd be adding a second database (and a second consistency problem) for one feature

Examples: Neo4j and Memgraph (property graph, Cypher), Amazon Neptune and JanusGraph (Gremlin/SPARQL), TigerGraph and Nebula (analytics at scale), plus pgRouting/recursive CTEs when you just need a little traversal in Postgres.

⚠️
Common mistakes
  • Unbounded traversals. Three hops in a social graph reaches most of the network; always cap depth and fan-out per node.
  • Running PageRank or community detection online. Those are batch jobs whose results are served from a store, not per-request queries.
  • Forgetting the reverse edge. “Who follows me” needs its own index, written transactionally or asynchronously — and it will be briefly inconsistent if async.
🎤
Interview drill

Design: Design “mutual friends” shown on every profile view, for 500M users.

How a strong answer sounds
It's a 2-hop intersection, far too expensive to compute live at profile-view rates for large accounts. Keep each user's friend set in a cache (sorted set or bitmap); for two normal users, intersect the smaller set against the larger with a membership check — microseconds. For high-degree accounts, cap the work: sample, or show “50+ mutual friends” rather than an exact count. Precompute nothing per pair; there are too many pairs.

Scale: A celebrity with 100M followers posts. What breaks in a graph store, and what do you do?

How a strong answer sounds
Reading or fanning out to that edge list is impossible at request time, and the follower list can't be cached as one value. Treat high-degree nodes as a special case: store counts separately (denormalized counters), page the edge list, and switch from fan-out-on-write to fan-out-on-read for that account — consumers pull the celebrity's posts at read time and merge (Chapter 27).

🧠 Key takeaways

  • Each extra hop multiplies work in SQL; graphs are small worlds, so unbounded traversals reach everyone.
  • Store edges in an indexed edge table or adjacency lists, sharded by node, with a separately maintained reverse index.
  • Graph databases use index-free adjacency, which pays off when variable-depth traversal is the query.
  • Bidirectional search turns depth-4 problems into two depth-2 problems.
  • Serve social graphs from heavy caching over a boring sharded database, with denormalized counters.
  • Celebrity nodes, cross-shard edges and per-viewer privacy are the real scaling problems.
  • Run PageRank, communities and embeddings offline; keep online queries to 1–2 hops plus ranking.

Check your understanding

Why does a 3-hop friends-of-friends query bring down a relational database?

200 → 40,000 → 8,000,000 intermediate rows, most of them duplicate paths to the same people.

You need “who follows me?” as well as “who do I follow?”. What does that imply?

Edges are directional; the reverse view needs its own index or row, which is extra write work to keep correct.

Finding a connection path of length 4 between two users: what's the efficient approach?

Work drops from roughly d⁴ to 2·d², and all-pairs precomputation is impossible at social-network sizes.

How should “people you may know” be produced for 500M users?

Candidate generation is expensive and tolerant of staleness — exactly the profile for batch precomputation.

Why is sharding a social graph across machines fundamentally awkward?

This is why large systems shard by node, keep traversals shallow, and lean on caching rather than distributed traversal.
