Search & Specialized Indexes

A normal database index (a B-tree, a sorted tree that finds a value in a few steps) is great at “find the row where id = 42”. But some questions need a completely different kind of index: “find recipes about spicy noodles”, “find drivers within 2 km”, or “find documents that mean the same as this question”. This chapter tours those special indexes.

Why LIKE '%noodle%' doesn't scale

A normal index is sorted by the whole value, like names in a phone book. So it can find values that start with something (LIKE 'nood%'). It can't find a word in the middle of a text.

A wildcard at the start, as in the heading above, forces a full table scan: the database reads every row and checks every string. With 100 million product descriptions, that takes minutes per query. And even if it were fast, the results would be poor:

🔤

No normalization

“Noodles”, “noodle” and “NOODLES” count as different strings. Users expect all three to match.

🏆

No relevance

Every match counts the same. A document that mentions “noodle” once in a footnote ranks equal to one titled “The Noodle Bible”.

🧩

No typos, synonyms, facets

Handling typos (“nodle”), synonyms (“ramen” means “noodles”) and facets (“filter by price and brand, with counts”) all needs a real search engine.

The inverted index

The fix is to flip the relationship around. Instead of storing document → words, store word → list of documents that contain it. That list is called the postings list.

It works exactly like the index at the back of a textbook: look up “noodle”, get the page numbers. A query becomes a few quick lookups plus merging some sorted lists. No scanning needed.

A tiny worked example with four documents:

  • Doc 1: “Spicy noodle soup” · Doc 2: “Roast chicken” · Doc 3: “Chicken noodle stir fry” · Doc 4: “Cold noodles”
  • After cleaning (lowercase, “noodles” → “noodle”), the index holds noodle → [1, 3, 4], chicken → [2, 3], spicy → [1], and so on.
  • Query “chicken noodles” with AND: walk both sorted lists side by side and keep IDs found in both → [3]. With OR: keep IDs found in either → [1, 2, 3, 4], then rank them.

Because each list is sorted, merging two lists takes one pass over them, never a comparison of every pair. The cost depends on how long the lists for the query's words are, not on how many documents exist in total.

Character filters & tokenizer

Strip out HTML. Then split the text into tokens (single words) at spaces and punctuation. Language-aware tokenizers also handle languages without spaces, like Chinese and Japanese, and long compound words.

Token filters

Clean up each token: make it lowercase, drop stop words (common filler words like “the”, “with”), stem it (cut it to its root: “boiled” → “boil”), add synonyms (“ramen” → “noodle”), and remove accents (“café” → “cafe”).

Write postings

For each term, store which documents contain it, how often (term frequency), and where (positions). Positions make phrase queries like "soft boiled" possible. The lists are kept sorted and heavily compressed (delta + variable-byte encoding: store small gaps between IDs instead of the full IDs).

Query time

Run the query through the same analyzer and look up each term. For AND, keep documents in every list (intersect). For OR, keep documents in any list (union). Then score them and return the top K.

🔤
Fuzzy matching and autocomplete

Typos are handled with edit distance: the number of single-letter changes between two words (“nodle” is 1 edit from “noodle”). Search engines check this quickly with finite automata (small state machines) run over the list of known terms.

Autocomplete on a prefix uses edge n-grams (also index the word's beginnings: “noo”, “nood”, “noodl”…) or a special suggester structure. We build one in the Autocomplete case study (Chapter 31).

Ranking: TF-IDF and BM25

Finding matches is the easy part. Putting them in a good order is what makes search feel smart. Classic relevance scoring rests on three simple ideas:

🔁

Term frequency (TF)

A document that says “ramen” 3 times is probably more about ramen than one that says it once. But each extra mention counts for less (diminishing returns).

💎

Inverse document frequency (IDF)

Rare words tell you more. Matching “tikka” (in 1 document) matters more than matching “chicken” (in half of all documents).

📏

Length normalization

Shorter documents get a boost. One mention in a 6-word title beats one mention in a 5,000-word article.

// BM25 — the default scorer in Lucene, Elasticsearch, OpenSearch and Solr
score(doc, query) = Σ over terms t in query:
    IDF(t) × ( tf × (k1 + 1) ) / ( tf + k1 × (1 − b + b × docLen / avgDocLen) )

IDF(t) = ln( 1 + (N − nt + 0.5) / (nt + 0.5) )      // N docs total, n_t docs containing t
k1 ≈ 1.2   // how quickly repeated terms saturate
b  ≈ 0.75  // how strongly long documents are penalised

Plug in numbers to see what the formula does. Take N = 1,000 documents.

  • IDF: “chicken” appears in 500 documents, so IDF = ln(1 + 500.5 / 500.5) = ln 2 ≈ 0.69. “tikka” appears in 1, so IDF = ln(1 + 999.5 / 1.5) ≈ ln 667 ≈ 6.5. A “tikka” match is worth about 9× a “chicken” match.
  • TF saturation: for a document of average length, the second part becomes tf × 2.2 / (tf + 1.2). One mention gives 1.0, two give about 1.38, three about 1.57, ten about 1.96 — and it can never pass 2.2. So stuffing a word 50 times into a page barely helps it.
  • Length: if the document is twice the average length, the bottom grows (1 − 0.75 + 0.75 × 2 = 1.75 instead of 1), so the same one mention now scores 2.2 / (1 + 1.2 × 1.75) ≈ 0.71 instead of 1.0.
🎤
Real ranking is multi-stage

Real search systems (shops, feeds, web search) work in two stages:

  • Retrieval: a cheap scorer like BM25 or vector similarity quickly picks ~1,000 candidates.
  • Re-ranking: an expensive ML model re-orders the top candidates. It uses signals like click-through rate, freshness, personalization and business rules.

Mentioning this two-stage funnel is a strong interview signal.

Search engines at scale

Lucene is the library that builds and searches inverted indexes on one machine. Elasticsearch and OpenSearch spread Lucene across many machines.

An index (roughly, a searchable collection like “recipes”) is split into shards, and each shard is a complete Lucene index. Each shard also has replicas (copies) on other nodes. Replicas keep data safe if a node dies and let more machines serve reads.

Why split an index into shards at all? Because one machine can only hold and search so much. A sized example: 500 million product documents at about 2 KB each, plus index overhead, is roughly 1–1.5 TB. At the 10–50 GB per shard guideline, that's about 30–100 shards spread over, say, 10 data nodes, and each query is answered by all of them in parallel, each searching only its own slice. Documents are assigned to shards by a hash of their ID, much like the hash sharding in Chapter 8.

GET /recipes/_search?q=spicy ramen — scatter, gather, fetchStep-through
  1. The request lands on a coordinating node, which acts as the organizer for this query. It is often a dedicated node that holds no data. It knows the cluster state: which shards exist, and where each main (primary) copy and each replica lives.
  2. The query goes out to one copy of every shard. It can be the primary or a replica, whichever is less busy. Each shard runs the analyzer, reads its postings lists and computes BM25 scores on its own data.
  3. Each shard sends back only its top 10 document IDs + scores. These are tiny messages, not full documents. The coordinator merges the 30 candidates into one overall top 10, using a priority queue (a structure that keeps the best items on top).
  4. Only now does it fetch the full documents (_source) of the 10 winners, from the shards that hold them.
  5. Results come back with highlights and facet counts. Counts (aggregations) are merged the same scatter-gather way. The total wait is set by the slowest shard. That's tail latency again!
⏱️

Near-real-time, not real-time

New documents wait in a memory buffer first. They become searchable after a refresh (every 1s by default), which writes them into a new segment: a small index file that is never changed afterwards. Segments are merged into bigger ones from time to time, very much like an LSM tree (Chapter 7). In between, a translog (a write-ahead log) keeps new data safe from crashes.

🧮

Choosing shard count

You pick the shard count when you create the index. Changing it later means reindexing everything. Aim for shards of roughly 10–50 GB. Too many tiny shards waste memory and slow down scatter-gather. Too few huge shards can't spread the load. For logs, create one index per time period (logs-2026.09.17) and use aliases (nicknames that point to them).

🔄

Search is a secondary index

Keep your source of truth in a database. Stream changes into the search cluster using CDC (change data capture) or an outbox (Chapter 17). If the search index gets corrupted, you can always rebuild it from the database. The reverse is not possible.

⚠️

Deep pagination hurts

Asking for page 1,000 (10 per page, 3 shards) means every shard must find its top 10,010 results, and the coordinator must sort 30,030. Limit how deep users can go, or use search_after cursors (Chapter 3's cursor pagination, again).

Geospatial indexes

“Find restaurants within 2 km” is a range query in 2 dimensions (latitude and longitude). A B-tree on latitude alone doesn't help much. It finds a thin strip that wraps around the whole planet.

There are two tricks. One is to turn 2D positions into 1D keys, so a normal index can scan a range of them. The other is to use a tree that divides up the space itself.

Geohash cuts the world in half again and again. The first bit answers “east or west half?”, the next “north or south half?”, and so on, taking turns. The bits are then written as base-32 characters.

The key property: nearby points share a prefix. So WHERE geohash LIKE '9q8yy%' is an ordinary, fast index range scan. Each extra character makes the cell about 32× smaller.

Why does a shared prefix mean "nearby"? Each bit halves the area the point could be in, so two points that agree on the first 25 bits (5 characters) must sit in the same cell after 25 halvings — a cell about 4.9 km across. Six characters give a cell of roughly 1.2 km × 0.6 km. For "drivers within 2 km", you'd pick a precision whose cell is about the size of your radius, then search that cell and its 8 neighbours. The reverse is not true, though: two points can be 10 metres apart but sit on opposite sides of a cell border and share almost no prefix. That's the edge problem the simulator shows.

Time-series databases

Metrics, IoT sensors, stock prices and app telemetry all produce the same kind of data. Each record has a timestamp, new records are only ever added at the end (append-only), and they arrive very fast. You query them by time range and almost never update them.

A general database can store this. But a time-series database (TSDB) built for this pattern is 10–100× more efficient.

A sized example of why that matters: 10,000 servers each report 500 metrics every 10 seconds. That's 500,000 samples per second. Stored plainly as an 8-byte timestamp plus an 8-byte value, that's 8 MB/s, or about 690 GB per day — before any index, in a B-tree that must update on every insert. Compressed to about 1.4 bytes per sample, the same day fits in about 60 GB, written in large sequential blocks.

📦

Time-partitioned chunks

Data is split into blocks, one per hour or day. A query reads only the blocks in its time range. Deleting old data just means dropping whole old blocks.

🗜️

Extreme compression

Timestamps arrive at steady intervals, and values change little. So TSDBs store only the tiny changes (delta-of-delta timestamps, XOR-encoded numbers, from Facebook's Gorilla). That shrinks each sample to ~1.4 bytes.

📉

Downsampling

Keep full 10-second detail for a week, then only 5-minute summaries for a year. You rarely need fine detail from long ago.

🏷️

Cardinality is the enemy

Cardinality means how many unique values there are. Every unique combination of labels becomes its own series. Putting user_id in a metric label can create millions of series and overload the TSDB.

Examples: Prometheus, InfluxDB, TimescaleDB (Postgres extension), VictoriaMetrics, ClickHouse for analytics-heavy workloads.

Vector search: searching by meaning

An embedding model turns text, images or audio into a vector: a list of hundreds or thousands of numbers. Think of it as coordinates on a huge map of meaning. The model places things so that similar meanings end up close together. “How do I reset my password?” lands near “forgot login credentials”, even though they share no words.

Semantic search, recommendations and RAG for LLMs (Chapter 42) all come down to one query: find the K nearest vectors.

Exact nearest-neighbour search compares the query to every single vector. With 100M vectors of 1,536 numbers each, that is far too slow per query: about 150 billion multiply-and-add operations for a single search, over roughly 600 GB of numbers (4 bytes each). So vector databases use approximate nearest neighbour (ANN) indexes. They occasionally miss a true neighbour (slightly lower recall), but they are massively faster.

Recall is simply the share of the true nearest neighbours you actually found. If the real top 10 contains 10 documents and the index returned 9 of them, recall@10 is 90%. For search and RAG, 95% recall at 100× the speed is almost always the better deal: the tenth-best match was probably nearly as good as the eleventh anyway. Each ANN index has a knob that trades speed for recall — nprobe in the demo below.

🕸️

HNSW

A layered graph linking each vector to its neighbours. A search starts on the top layer's long jumps, like taking a highway, then moves down to short local links, like side streets. It always hops toward the query. Excellent recall and speed, but uses a lot of memory. The default in pgvector, Qdrant, Weaviate and OpenSearch.

🗂️

IVF + PQ

Group vectors into clusters (IVF, as in the demo). Then shrink each vector to a few bytes with product quantization, a lossy compression. Billions of vectors fit in RAM, at some cost in recall. Popular in FAISS and at massive scale.

🤝

Hybrid search

Vectors are bad at exact tokens like product codes (SKUs), error codes and names. So run BM25 and vector search together and combine the two rankings (for example with reciprocal rank fusion). Then re-rank. For most RAG systems this beats either one alone.

Start simple

Plain Postgres goes a long way. Its built-in full-text search (tsvector + GIN index), plus the PostGIS and pgvector extensions, handle surprisingly large workloads. You get it all in one system, with transactions keeping everything consistent.

Add a separate search or vector cluster only when you need it: for scale, for fine relevance tuning, or for heavy query load. It's one more system to run and keep in sync.

⚠️
Common mistakes
  • Making the search index the source of truth. It's derived data (built from other data). Keep the database as the official copy so you can always rebuild the index.
  • Ignoring the analyzer. If indexing and querying clean text differently, you get “why does nothing match?” bugs. No amount of tuning fixes those.
  • Deep pagination. Page 500 makes every shard sort 5,000+ results. Limit the depth or use search-after cursors.
🎤
Interview drill

Design: Add “search your documents” to a product with 200M documents and per-user permissions.

How a strong answer sounds
Copy documents into a search cluster using CDC from the source database. Store the permission fields (owner, shared-with, team) as terms you can filter on. At query time, filter by the viewer's identities before scoring. That way the engine enforces the access rules (ACLs) itself. Filtering results afterwards breaks pagination and counts. For complex sharing, store a flattened acl_ids array on each document, and re-index it when permissions change.

Choose: Keyword search, vector search, or both?

How a strong answer sounds
Both, combined. BM25 handles exact tokens (error codes, SKUs, names), which embeddings blur. Vectors handle rephrasing and intent. Run both searches, merge them with reciprocal rank fusion, then re-rank the top ~100 with a cross-encoder (a slower, more accurate ML scorer) or business rules. If you can only ship one first, ship BM25. It's cheaper, easy to explain, and users expect exact matches to work.

🧠 Key takeaways

  • An inverted index maps each word to a list of documents that contain it. Text search becomes fast lookups and list merges.
  • Documents and queries must go through the same analyzer: split into words, lowercase, drop stop words, stem, add synonyms.
  • BM25 ranks by how often a word appears (with diminishing returns), how rare it is (IDF) and how long the document is. Real systems add ML re-ranking on top.
  • Distributed search sends the query to every shard, collects each one's top-K IDs, then fetches the winning documents. The slowest shard sets the speed.
  • Search indexes are derived data. Keep the source of truth in a database and sync changes with CDC.
  • Geohashes turn 2D positions into keys you can search by prefix (always check the neighbouring cells). Quadtrees adapt to how crowded an area is.
  • Time-series databases take advantage of append-only, time-ordered data with chunking, compression and downsampling.
  • Vector search finds similar meanings with ANN indexes like HNSW and IVF. They give up a little recall for huge speedups.

Check your understanding

A user searches “Running Shoes” but the product says “runner shoe”. Where is this mismatch fixed?

The analyzer cleans both the documents and the query into the same terms, using lowercasing, stemming and synonyms (“Shoes” → “shoe”). So different forms of a word meet in the index.

Why does BM25 give a rare term like “tikka” more weight than a common term like “chicken”?

IDF rewards words that appear in only a few documents. Such a word does a better job of picking out the relevant documents from all the rest. In a 1,000-document collection, a word in 1 document gets an IDF of about 6.5, while a word in half of them gets about 0.7.

Your geohash-based “nearby drivers” query sometimes misses a driver 50 m away. What's the most likely cause?

Two points on either side of a cell edge can be very close but have completely different prefixes. Always search the 8 neighbouring cells as well.

In an Elasticsearch query across 20 shards, what do shards return in the query phase?

Sending back only IDs and scores keeps the scatter-gather step cheap. Full documents are fetched later, and only for the overall winners.

A RAG system's vector search fails to find documents mentioning error code E-4012. Best improvement?

Embeddings capture meaning but blur exact identifiers like error codes. Keyword search catches exact tokens. Combining both gives you the strengths of each.
