Search & Specialized Indexes

A B-tree index answers “find the row where id = 42” brilliantly. But “find recipes about spicy noodles”, “find drivers within 2 km”, or “find documents that mean the same as this question” need entirely different data structures. This chapter is your tour of them.

  • Build and query an inverted index by hand
  • Understand relevance ranking with TF-IDF and BM25
  • Explain how Elasticsearch shards and queries data
  • Index locations with geohashes and quadtrees
  • Know when to reach for a time-series database
  • Explain vector search and approximate nearest neighbours

Why LIKE '%noodle%' doesn't scale

A normal index is sorted by the whole value, so it can find prefixes (LIKE 'nood%') but not words in the middle of text. A leading wildcard forces a full table scan: read every row, check every string. At 100 million product descriptions that's minutes per query. And even if it were fast, it would be dumb:

🔤

No normalization

“Noodles”, “noodle” and “NOODLES” are different strings. Users expect them to match.

🏆

No relevance

Every match is equal. A doc that mentions “noodle” once in a footnote ranks the same as one titled “The Noodle Bible”.

🧩

No typos, synonyms, facets

“nodle”, “ramen ≈ noodles”, “filter by price and brand with counts” — all need a real search engine.

The inverted index

Flip the relationship around. Instead of document → words, store word → list of documents containing it (the postings list). It's exactly the index at the back of a textbook. A query becomes a few dictionary lookups plus a merge of sorted lists — no scanning.

Character filters & tokenizer

Strip HTML, then split text into tokens on whitespace and punctuation. Language-aware tokenizers handle Chinese/Japanese (no spaces) and compound words.

Token filters

Lowercase, remove stop words (“the”, “with”), stem or lemmatize (“boiled” → “boil”), expand synonyms (“ramen” → “noodle”), fold accents (“café” → “cafe”).

Write postings

For each term store doc IDs, term frequency and positions (positions enable phrase queries like "soft boiled"). Lists are sorted and heavily compressed (delta + variable-byte encoding).

Query time

Run the query through the same analyzer, look up each term, intersect (AND) or union (OR) the postings lists, then score and return the top K.

🔤
Fuzzy matching and autocomplete

Typos are handled with edit distance (“nodle” is 1 edit from “noodle”), searched efficiently using finite automata over the term dictionary. Prefix autocomplete uses edge n-grams (index “noo”, “nood”, “noodl”…) or a dedicated suggester structure — we build one in the Autocomplete case study (Chapter 31).

Ranking: TF-IDF and BM25

Finding matches is easy; ordering them is what makes search feel smart. Classic relevance rests on three intuitions:

🔁

Term frequency (TF)

A doc mentioning “ramen” 3 times is probably more about ramen than one mentioning it once — but with diminishing returns.

💎

Inverse document frequency (IDF)

Rare words are more informative. Matching “tikka” (1 doc) matters more than matching “chicken” (in half of all docs).

📏

Length normalization

One mention in a 6-word title beats one mention in a 5,000-word article.

// BM25 — the default scorer in Lucene, Elasticsearch, OpenSearch and Solr
score(doc, query) = Σ over terms t in query:
    IDF(t) × ( tf × (k1 + 1) ) / ( tf + k1 × (1 − b + b × docLen / avgDocLen) )

IDF(t) = ln( 1 + (N − nt + 0.5) / (nt + 0.5) )      // N docs total, n_t docs containing t
k1 ≈ 1.2   // how quickly repeated terms saturate
b  ≈ 0.75  // how strongly long documents are penalised
🎤
Real ranking is multi-stage

Production search (e-commerce, feeds, web search) does retrieval with a cheap scorer like BM25 or vector similarity to get ~1,000 candidates, then re-ranks the top candidates with an expensive ML model using signals like click-through rate, freshness, personalization and business rules. Mentioning this two-stage funnel is a strong interview signal.

Search engines at scale

Elasticsearch and OpenSearch wrap Lucene indexes in a distributed system. An index is split into shards (each a full Lucene index), and each shard has replicas on other nodes for fault tolerance and read throughput.

GET /recipes/_search?q=spicy ramen — scatter, gather, fetchStep-through
  1. The request lands on a coordinating node (often a dedicated, data-less node). It knows the cluster state: which shards exist and where each primary and replica copy lives.
  2. The query goes to one copy of every shard (primary or replica — chosen by load). Each shard runs the analyzer, walks its postings lists and computes BM25 locally.
  3. Each shard sends back its top 10 doc IDs + scores — tiny payloads, not full documents. The coordinator merges 30 candidates into a global top 10 with a priority queue.
  4. Only now does it fetch the full _source of the 10 winners from the shards that hold them.
  5. Results return with highlights and facet counts (aggregations are merged the same scatter-gather way). Latency is dominated by the slowest shard — tail latency again!
⏱️

Near-real-time, not real-time

New documents sit in an in-memory buffer and become searchable after a refresh (default 1s) writes a new immutable segment. Segments are periodically merged — very similar to an LSM tree (Chapter 7). A translog provides durability in between.

🧮

Choosing shard count

Shard count is fixed at index creation (changing it means reindexing). Aim for shards of roughly 10–50 GB. Too many tiny shards waste memory and slow scatter-gather; too few huge shards can't spread load. Use time-based indexes (logs-2026.09.17) plus aliases for logs.

🔄

Search is a secondary index

Keep your source of truth in a database. Stream changes into the search cluster via CDC or an outbox (Chapter 17). If the search index is corrupted you can always rebuild it — never the other way round.

⚠️

Deep pagination hurts

Page 1,000 of results means every shard must find its top 10,010 and the coordinator must sort 30,030. Cap result depth, or use search_after cursors (Chapter 3's cursor pagination, again).

Geospatial indexes

“Find restaurants within 2 km” is a 2-dimensional range query. A B-tree on latitude alone finds a thin horizontal band spanning the whole planet. The trick is to map 2D space onto 1D keys that a normal index can range-scan — or to use a tree that divides space itself.

Geohash repeatedly halves the world: one bit for “east or west half?”, the next for “north or south?”, alternating. Interleaved bits are encoded in base-32. Nearby points share a prefix, so WHERE geohash LIKE '9q8yy%' is an ordinary index range scan. Each extra character shrinks the cell ~32×.

A quadtree splits a region into 4 quadrants only when it holds too many points. Dense downtown areas get tiny cells; empty oceans stay as one big cell. Each leaf holds at most a few points, so searching is fast regardless of density.

Time-series databases

Metrics, IoT sensors, stock ticks and app telemetry produce append-only, timestamped data at huge write rates, queried by time range and almost never updated. General databases work, but time-series databases (TSDBs) are 10–100× more efficient.

📦

Time-partitioned chunks

Data is split into blocks per hour/day. Queries touch only relevant chunks; retention simply drops whole old chunks.

🗜️

Extreme compression

Delta-of-delta timestamps and XOR-encoded floats (Facebook's Gorilla) shrink a sample to ~1.4 bytes.

📉

Downsampling

Keep 10-second resolution for a week, 5-minute rollups for a year. Old detail is rarely needed.

🏷️

Cardinality is the enemy

Every unique label combination is a separate series. Putting user_id in a metric label can create millions of series and melt the TSDB.

Examples: Prometheus, InfluxDB, TimescaleDB (Postgres extension), VictoriaMetrics, ClickHouse for analytics-heavy workloads.

Vector search: searching by meaning

An embedding model turns text, images or audio into a vector of hundreds or thousands of numbers, placed so that similar meanings end up close together. “How do I reset my password?” lands near “forgot login credentials” even with zero words in common. Semantic search, recommendations and RAG for LLMs (Chapter 42) all boil down to one query: find the K nearest vectors.

Exact nearest-neighbour search compares the query to every vector — 100M vectors × 1,536 dimensions per query is far too slow. So vector databases use approximate nearest neighbour (ANN) indexes that trade a little recall for massive speedups.

🕸️

HNSW

A multi-layer “small world” graph: greedily hop toward the query through sparse long-range links, then dense local ones. Excellent recall and latency; memory hungry. Default in pgvector, Qdrant, Weaviate, OpenSearch.

🗂️

IVF + PQ

Cluster vectors (IVF, as in the demo) and compress each with product quantization to a few bytes. Fits billions of vectors in RAM at some recall cost. Popular in FAISS and at massive scale.

🤝

Hybrid search

Vectors are bad at exact tokens (SKUs, error codes, names). Run BM25 and vector search together and fuse the rankings (e.g. reciprocal rank fusion), then re-rank. This beats either alone for most RAG systems.

Start simple

Postgres with full-text search (tsvector + GIN index), PostGIS and pgvector handles surprisingly large workloads in one system with transactional consistency. Introduce a dedicated search or vector cluster when scale, relevance tuning or query load justifies another system to operate and keep in sync.

⚠️
Common mistakes
  • Making the search index the source of truth. It's derived data — keep the database authoritative so you can always rebuild.
  • Ignoring the analyzer. Mismatched analysis between indexing and querying produces “why does nothing match?” bugs that no amount of tuning fixes.
  • Deep pagination. Page 500 makes every shard sort 5,000+ results; cap depth or use search-after cursors.
🎤
Interview drill

Design: Add “search your documents” to a product with 200M documents and per-user permissions.

How a strong answer sounds
Index documents into a search cluster via CDC from the source database, with the permission fields (owner, shared-with, team) stored as filterable terms. At query time apply a filter for the viewer's identities before scoring, so ACLs are enforced in the engine rather than post-filtering (which breaks pagination and counts). For complex sharing, denormalize an acl_ids array per document and re-index on permission change.

Choose: Keyword search, vector search, or both?

How a strong answer sounds
Both, fused. BM25 handles exact tokens — error codes, SKUs, names — which embeddings blur. Vectors handle paraphrase and intent. Run both retrievals, fuse with reciprocal rank fusion, then re-rank the top ~100 with a cross-encoder or business rules. If you can only ship one first, ship BM25: it's cheaper, explainable, and users expect exact matches to work.

🧠 Key takeaways

  • An inverted index maps terms to postings lists, turning text search into fast lookups and list merges.
  • Documents and queries must pass through the same analyzer: tokenize, lowercase, remove stop words, stem, add synonyms.
  • BM25 ranks by saturating term frequency, rarity (IDF) and document length; production systems add ML re-ranking.
  • Distributed search scatters queries to every shard, gathers top-K IDs, then fetches documents — tail latency matters.
  • Search indexes are derived data: keep the source of truth in a database and sync via CDC.
  • Geohashes map 2D to prefix-searchable keys (always check neighbouring cells); quadtrees adapt to density.
  • Time-series databases exploit append-only, time-ordered data with chunking, compression and downsampling.
  • Vector search finds similar meanings with ANN indexes like HNSW and IVF, trading a little recall for huge speedups.

Check your understanding

A user searches “Running Shoes” but the product says “runner shoe”. Where is this mismatch fixed?

Text analysis normalizes both sides into the same terms, so different surface forms meet in the index.

Why does BM25 give a rare term like “tikka” more weight than a common term like “chicken”?

IDF rewards terms that separate a few relevant documents from the rest of the corpus.

Your geohash-based “nearby drivers” query sometimes misses a driver 50 m away. What's the most likely cause?

Close points can have completely different prefixes at cell edges. Query the 8 neighbouring cells as well.

In an Elasticsearch query across 20 shards, what do shards return in the query phase?

Returning just IDs and scores keeps the scatter-gather cheap; full documents are fetched only for the global winners.

A RAG system's vector search fails to find documents mentioning error code E-4012. Best improvement?

Embeddings capture meaning but blur exact identifiers. Keyword retrieval catches exact tokens; fusing both gives the best of each.
