How Computers Work

System design is about many computers working together. Before you can reason about a fleet, you need a clear picture of one machine: what its parts do, how fast each part is, what it forgets when the power goes, and how it eventually breaks. Every later decision — “cache it”, “write it to disk”, “keep a copy in another building” — comes straight from this chapter.

Why a system designer cares about hardware

You might expect system design to be all boxes and arrows: “load balancer here, database there”. It is. But every one of those boxes is a real computer with real limits, and the arrows are real cables with real delays. When a design is slow, expensive or loses data, the cause is almost always one of a few physical facts about hardware.

Here are three questions you will be asked again and again in this course. Each has an answer that comes straight from hardware:

⚡

“Why add a cache?”

Because reading from memory is roughly 1,000× faster than reading from an SSD, and a million times faster than crossing an ocean. A cache keeps a copy of hot data in the fast place.

💾

“Why is the database the hard part?”

Because anything that must survive a crash has to be written to disk, which is slow — and a single disk can die. So databases must write carefully and keep copies.

🌍

“Why run in several regions?”

Because light in fibre needs about 50 ms to cross the Atlantic and back, and whole buildings lose power. Distance and failure are physics, not bugs.

This chapter gives you the mental model behind all three. You won't need to memorise part numbers. You need ratios (“memory is about a thousand times faster than an SSD”) and behaviours (“RAM forgets on power loss”). Those stay true even as hardware gets faster every year.

The four parts of every computer

Your laptop, your phone and a server in a data center are built from the same four kinds of parts. They differ in size, not in kind.

🧠

CPU

The processor. It runs instructions: add these two numbers, compare those, jump to that line. It is where work actually happens.

⚡

RAM (memory)

Working space for running programs. Very fast, but volatile: when the power goes off, everything in RAM is gone.

💾

Disk (SSD / HDD)

Long-term storage. Data survives a power cut. Much bigger and cheaper than RAM, but much slower.

📡

Network card

The NIC (network interface card). It sends and receives data over a cable. Talking to another machine through it is usually the slowest thing a program does.

🧑‍🍳
Analogy: a chef in a kitchen

The CPU is the chef. RAM is the countertop: small, but everything on it is within arm's reach. The disk is the pantry down the hall: huge and permanent, but every trip costs time. The network is ordering an ingredient from another restaurant across town. A good chef keeps what they need on the counter. A good system keeps hot data in memory.

The CPU: cores and clock speed

A CPU does its work in tiny steps called cycles. The clock speed says how many cycles happen per second. A 3 GHz (gigahertz) CPU runs 3 billion cycles per second, and a modern core can finish several simple instructions per cycle. So one core can do billions of simple operations every second.

A core is one independent worker inside the CPU. Each core runs one stream of instructions at a time. A laptop might have 8 cores; a server might have 32 to 128. More cores means more things can happen at the same time — which is exactly what a server needs, because it answers many users at once. You'll see how programs use many cores in P2.

💡
Why CPUs rarely are the bottleneck

Billions of operations per second sounds like a lot, and it is. Most web requests need only a few million CPU instructions of real work. What usually makes a request slow is waiting: for the disk, for the database, for another server across the network. While a program waits, the CPU core sits idle or switches to other work. That's why so much of system design is about avoiding waits, not about faster CPUs.

RAM: fast, small, forgetful

RAM (random-access memory) holds the programs that are running right now and the data they are working on. “Random access” means any byte can be read equally fast, no matter where it is. Reading from RAM takes about 100 nanoseconds (a nanosecond, ns, is a billionth of a second). A server might have 64 to 512 GB of it.

RAM stores each bit as a tiny electrical charge that must be refreshed constantly. Cut the power and the charges drain away within moments. That is what volatile means, and it is the single most important fact about RAM for system design.

Disk: slow, big, permanent

A disk keeps data without power. There are two kinds you'll meet:

💿 HDD — hard disk drive

A spinning magnetic platter with a moving arm, like a tiny record player. To read a random spot, the arm must move and wait for the platter to spin round: about 10 ms per random read. Reading data that sits in one long stretch (sequential reading) is much faster, around 100–200 MB per second. Cheapest per gigabyte, so used for backups and archives.

🔲 SSD — solid-state drive

Flash memory chips with no moving parts. A random read takes around 100 µs (microseconds, millionths of a second) — about 100× faster than an HDD. Fast NVMe SSDs read several GB per second sequentially. This is where databases keep their files today.

Even an SSD is roughly a thousand times slower than RAM for a random read. Keep that ratio in your head. It's the reason caches exist.

The network card

The NIC connects the computer to a network cable. Server NICs typically move 10 to 100 gigabits per second. Sending bytes out is fast; the slow part is the distance — waiting for the other machine to receive the message and reply. Inside one data center a round trip takes about 0.5 ms. Across an ocean it takes 100–150 ms. You'll learn why in P4.

That is the single most important hardware fact for system design: anything that must survive a crash has to be written to disk — and, because a disk can die too, usually copied to other machines. Anything kept only in RAM is a fast, temporary copy.

This splits all data in a system into two kinds:

📌 Source of truth

The one place where the real, authoritative data lives — usually a database on disk, copied to several machines. If it's lost, it's gone for good. Orders, payments, user accounts.

♻️ Derived data

A copy you can rebuild from the source of truth — a cache in RAM, a search index, a pre-computed report. Losing it hurts speed for a while, but nothing is lost forever. Chapter 6 is built on this idea.

“Written to disk” is subtler than it sounds

When a program saves a file, the operating system often keeps the new bytes in RAM for a moment and writes them to the disk a little later, in bigger batches. That's much faster. But if the power fails in that moment, the “saved” data is lost. Programs that must never lose data — databases above all — ask the operating system to flush the data to the physical disk (a call named fsync on Linux) before they tell the user “saved”. A flush costs time, which is why durable writes are slower than you might expect. You'll see how databases handle this with a write-ahead log in Chapter 7.

Make the numbers human

Nanoseconds are too small to feel. So stretch time: pretend one nanosecond lasts one second. Then:

OperationReal timeIf 1 ns were 1 second
Read from the CPU's own cache~1 nsa heartbeat
Read from RAM~100 nsabout 2 minutes
Random read from an SSD~100 µsabout 1 day
Round trip to another machine in the same data center~0.5 msabout 6 days
Random read from an HDD~10 msabout 4 months
Round trip across an ocean~150 msabout 5 years

Seen that way, a program that reads from RAM is chatting across a desk, while a program that calls a server on another continent has posted a letter and is waiting years for the reply. You'll meet a fuller version of this table in P8 and Chapter 4.

Sequential beats random

There's a second lesson hiding in the ladder. Reading data that sits together, in order (sequential) is far faster than jumping around (random). On an HDD this is dramatic: one long read at ~150 MB/s versus ~100 random reads per second. Even on SSDs and in RAM, reading in order is faster, because hardware fetches data in chunks and guesses what you'll want next.

This is why many storage systems prefer to append to the end of a file rather than update data in place. Logs, message queues like Kafka, and many databases are designed around sequential writes. You'll meet this idea as the “log” in P7 and again in Chapter 14.

Everything is bits and bytes

Inside a computer, everything — numbers, text, photos, programs — is stored as bits. A bit is a single 0 or 1: a charge present or absent, a magnetic spot pointing one way or the other. Eight bits make a byte, the basic unit of storage.

Counting in binary

With one bit you can count two things (0, 1). With two bits, four (00, 01, 10, 11). Each extra bit doubles the count, so 8 bits give 2⁸ = 256 different values — which is why one byte holds a number from 0 to 255. Each position in a binary number is worth twice the one to its right: 1, 2, 4, 8, 16… Click the bits to build a number.

What a byte can mean

A byte is just a pattern. What it means depends on how a program reads it:

  • A number. One byte holds 0–255. Bigger numbers use more bytes: a 4-byte (32-bit) integer reaches about 4.3 billion, and an 8-byte (64-bit) integer reaches about 18 quintillion (1.8 × 10¹⁹). This is why database IDs are usually 64-bit: you'll never run out.
  • Text. Each character gets a number. In UTF-8, the encoding used almost everywhere on the web, English letters take 1 byte, most European and Asian characters take 2–3 bytes, and an emoji takes 4. So “hello” is 5 bytes, and a tweet of 280 characters is usually 280–1,100 bytes.
  • Images, audio, video. Long sequences of numbers describing pixels or sound samples, usually compressed. A phone photo is 2–5 MB; an hour of HD video is a few GB.
  • A program. Instructions for the CPU, themselves stored as bytes in a file.

A file is simply a named sequence of bytes on a disk. When two programs exchange data over a network, they turn their in-memory data into a sequence of bytes, send it, and the receiver turns the bytes back into data. That conversion is called serialization (and deserialization). JSON, which you'll meet in P5, is one popular way to do it.

The operating system: the manager

Programs don't talk to hardware directly. They ask the operating system (OS) — Linux on almost every server, or Windows, or macOS — to do it for them. The OS is the manager that shares one machine fairly and safely between many programs.

🧮

Shares the CPU

It decides which program runs on which core, and switches between them thousands of times per second so they all make progress. This is called scheduling.

🧱

Shares the memory

It gives each program its own private slice of RAM, so one buggy program can't overwrite another's data. If RAM runs out, it may move rarely used data to disk (called swap), which makes everything dramatically slower.

🗂️

Manages files

The file system organises the raw disk into folders and named files, and remembers where each file's bytes physically are.

🔌

Drives devices

It talks to disks, network cards and everything else through small programs called drivers. A program just says “send these bytes”; the OS handles the details.

When a program asks the OS for something — read a file, open a network connection — that request is called a system call. System calls are much slower than ordinary code, because the CPU has to switch into the OS and back. That's one reason efficient servers batch their work into fewer, bigger reads and writes. How the OS runs many programs at once — processes and threads — is the whole subject of P2.

Servers, racks and data centers

A server is just a computer whose job is to answer requests. Physically it's a flat metal box with no screen or keyboard, bolted into a rack — a tall shelf holding a few dozen servers plus a network switch that connects them. Racks stand in rows inside a data center: a building with serious power supplies, backup generators, cooling, and many network cables to the outside world.

It's the same parts as your laptop — CPU, RAM, SSD, network card — only bigger, more reliable, and switched on 24 hours a day. A typical cloud server might have 32 cores, 128 GB of RAM and a few terabytes of SSD.

The cloud, virtual machines and containers

Most companies don't buy servers any more. They rent them from a cloud provider (AWS, Google Cloud, Azure and others), paying by the hour. What you usually rent is a virtual machine (VM): a slice of a big physical server that behaves like a whole computer of its own, with its own OS. One physical machine might host a dozen VMs for different customers.

A container is lighter still: a packaged program with everything it needs, sharing the host's OS but isolated from other containers. Containers start in about a second, which makes it easy to add or remove copies of a service as traffic changes. You'll meet them properly in Chapter 21.

Regions and availability zones

Cloud providers group data centers geographically. A region is an area such as “US East” or “Frankfurt”. Inside each region are several availability zones (AZs): separate data centers a few kilometres apart, with their own power and cooling, but linked by fast private cables (round trips of about 1 ms or less). Putting copies of a service in two or three zones protects it from one building losing power. Putting copies in two regions protects it from a whole area going dark. That's the subject of Chapter 22.

💡
Two meanings of “server”

People say “server” for the machine (“we have 40 servers”) and for the program that answers requests (“the web server crashed”). One machine can run several server programs. Context tells you which is meant.

Hardware fails — constantly, at scale

A single laptop might run for years without a disk failure. But a large system has thousands of machines, and small probabilities add up. Disks wear out, power supplies burn out, memory chips flip bits, network switches die, and people unplug the wrong cable.

Hard drives in large fleets fail at roughly 1–2% per year. That sounds rare. Now use the calculator: with 10,000 drives at 1.5%, you expect about 150 failures a year — one every two or three days. At that scale, “a disk died” isn't an emergency. It's Tuesday.

This is why every serious system is designed around redundancy — keeping extra copies so that losing one doesn't lose anything:

  • Data is stored on at least two or three machines (replication, Chapter 8).
  • Services run as several identical copies behind a load balancer, so one crash just removes one copy (Chapter 5).
  • Buildings fail too, so important systems spread across availability zones or regions (Chapter 22).

The mindset shift is important: at scale you don't try to prevent all failures. You assume they happen all the time and make the system keep working anyway. That property is called fault tolerance, and Chapter 16 is devoted to it.

⚠️
Common mistakes
  • Treating RAM as storage. Anything only in memory — a session, a shopping cart, a counter — is gone after a crash or restart. If it matters, it goes to disk, and to more than one machine.
  • Believing “saved” means “on disk”. The OS may hold writes in RAM briefly. Systems that must not lose data force a flush before confirming.
  • Blaming the CPU for slowness. Most slow requests are waiting — on disk, database or network — not computing.
  • Forgetting that sequential beats random. The same amount of data can be read 10–1,000× faster if it's stored together and read in order.
  • Assuming hardware is reliable. One machine usually is. A thousand machines never are, all at once.
🎤
Interview drill

Explain it simply: Why do we put a cache in front of a database, and why is it OK for the cache to lose its data?

How a strong answer sounds
A cache keeps popular data in RAM, which is about a thousand times faster to read than an SSD and avoids a network trip to the database. The database stays the source of truth on disk, replicated to several machines. The cache only holds copies, so if it crashes we lose speed, not data: requests fall through to the database and the cache refills itself. The thing to watch is that the database can survive that burst of extra reads while the cache warms up.

Estimate: You run 2,000 servers, each with 4 SSDs that fail at 0.8% a year. How many SSD failures per week should the operations team expect?

How a strong answer sounds
2,000 × 4 = 8,000 SSDs. 8,000 × 0.008 = 64 failures a year, which is a bit more than one a week (64 ÷ 52 ≈ 1.2). So replacing drives is routine work, the data on each drive must also exist elsewhere, and the replacement process should be automated rather than treated as an incident.

🧠 Key takeaways

  • Every computer has a CPU (does the work), RAM (fast, temporary working space), a disk (slow, permanent storage) and a network card (talks to other machines).
  • RAM is volatile: it forgets everything when power is lost. Anything that must survive goes to disk — flushed, not just “written” — and to more than one machine.
  • Speeds differ by factors of thousands: RAM ~100 ns, SSD ~100 µs, same-building network ~0.5 ms, cross-ocean ~150 ms. Ratios matter more than exact values.
  • Reading data in order (sequential) is much faster than jumping around (random), which is why logs and append-only designs are everywhere.
  • Everything is bytes: 8 bits per byte, 64-bit IDs, UTF-8 text at 1–4 bytes per character. Serialization turns data into bytes to store or send.
  • The OS shares the CPU, memory, files and devices between programs; system calls into it are relatively expensive.
  • Servers live in racks, in data centers, grouped into availability zones and regions. Most are rented as VMs or run as containers.
  • At scale, hardware failure is routine. Systems stay up through redundancy, not through perfect hardware.

Check your understanding

A server loses power and restarts. Which data is gone?

RAM is volatile: it's wiped when power is lost. Anything on the SSD survives, including the program file, which the OS loads back into RAM on restart. That's why important data must be written to disk, and why a cache must always be something you can rebuild.

Roughly how much slower is a random read from an SSD than a read from RAM?

RAM takes about 100 ns; an SSD random read takes about 100 µs, which is 100,000 ns. 100,000 ÷ 100 = 1,000. That thousand-fold gap is the reason caches exist.

What is the largest number one byte can hold?

A byte is 8 bits, so it has 2⁸ = 256 different patterns. Counting starts at 0, so the values run from 0 to 255. (256 is the number of values, not the largest one.)

Why do many storage systems append new data to the end of a file instead of editing data in place?

Writing in one long run avoids jumping around the disk. On HDDs the difference is enormous; on SSDs and even RAM it still helps. Append-only logs are a core building block of databases and message queues for exactly this reason.

A fleet has 20,000 hard drives, each failing at about 1.8% per year. What should the design assume?

20,000 × 0.018 = 360 failures a year — about one per day. At that rate, failure is routine. Every piece of data needs copies on other machines, and replacing a failed drive should be an automated, boring process.
