Databases Deep Dive

The database is usually the heart — and the hardest-to-scale part — of any system. Understanding how databases store, find and protect data lets you make choices that hold up for years.

  • Model data relationally and understand joins

  • See why indexes make queries fast (and writes slower)
  • Reason about isolation levels & anomalies

The relational model

Relational databases (PostgreSQL, MySQL, SQL Server, Oracle) store data in tables of rows and columns with a fixed schema. Tables reference each other with foreign keys, and SQL lets you JOIN them at query time. Hover a row:

SELECT u.name, SUM(o.total) FROM users u
JOIN orders o ON o.user_id = u.id
GROUP BY u.name;   -- Ada $141, Grace $18, Linus $7

Normalisation stores each fact once (a user's city lives only in users), avoiding inconsistencies. At scale, systems sometimes denormalise — duplicating data to avoid expensive joins — trading storage and update complexity for read speed.

ACID transactions

A transaction groups several operations into one all-or-nothing unit. Relational databases guarantee four properties:

⚛️

Atomicity

All or nothing. If any step fails, every change in the transaction is rolled back.
📐

Consistency

click to flip
Rules hold. Constraints (foreign keys, CHECK balance ≥ 0, unique) are never violated by a committed transaction.
🚧

Isolation

No interference. Concurrent transactions behave (to a configurable degree) as if run one at a time.

Indexes: how databases find things fast

Without an index, finding WHERE email = 'ada@x.com' means reading every row — a full table scan. An index is a separate sorted data structure (usually a B-tree) that maps column values to row locations, like the index at the back of a book.

Real B-tree nodes hold hundreds of keys (fan-out ~100–500), so even a billion rows is only ~4–5 levels deep — and the top levels are cached in RAM.

Indexes give you
  • O(log n) lookups instead of O(n)
  • Fast range queries & ORDER BY (B-trees are sorted)
  • Enforced uniqueness
Indexes cost you
  • Every INSERT/UPDATE must update every index → slower writes
  • Extra storage (sometimes bigger than the table)
  • Unused indexes are pure overhead
💡

Composite index order matters. An index on (country, city) helps WHERE country='UK' and WHERE country='UK' AND city='London' — but not WHERE city='London' alone. Think of a phone book sorted by last name, then first name.

NoSQL: the four big families

“NoSQL” is an umbrella for databases that drop some relational features (fixed schemas, joins, sometimes transactions) to gain flexibility, horizontal scale or specialised performance.

A giant distributed hash map. Get/put by key, nothing else. Blazing fast and trivially shardable. Redis, DynamoDB, Memcached, etcd.

session:abc123→{"userId":42,"exp":1735689600}
cart:42→["sku_991","sku_12"]
rate:ip:203.0.113.9→17

Use for: sessions, caching, shopping carts, rate-limit counters, feature flags. Avoid when: you need to query by anything other than the key.

Self-contained JSON-like documents in collections. Flexible schema, nested data, queries and indexes on any field. MongoDB, Couchbase, Firestore.

  "_id": "prod_77", "name": "Trail Shoe", "price": 89,

Use for: catalogues, CMS content, user profiles — data read as a whole unit with varying shape. Avoid when: data is highly relational with many-to-many joins.

Rows keyed by a partition key, with sorted, sparse columns. Designed for massive write throughput across many machines. You model tables around your queries. Cassandra, HBase, ScyllaDB, Bigtable.

Nodes and edges as first-class citizens. Traversing relationships is cheap no matter how deep. Neo4j, Amazon Neptune, JanusGraph.

Use for: social graphs (“friends of friends who like X”), fraud rings, recommendations, knowledge graphs. Avoid when: data isn't about relationships.

🔎 Search engines

Elasticsearch, OpenSearch. Inverted indexes for full-text search, fuzzy matching, faceting.

📈 Time-series

InfluxDB, TimescaleDB, Prometheus. Optimised for append-only timestamped metrics and downsampling.

🧮 Columnar / OLAP

ClickHouse, BigQuery, Snowflake. Scan billions of rows for analytics by reading only needed columns.

🧭 Vector

pgvector, Pinecone, Milvus. Nearest-neighbour search over embeddings for AI/semantic search.

S3, GCS. Not a DB, but where images, videos and backups live — cheap and practically infinite.

Under the hood: B-trees vs LSM trees

Storage engines come in two main designs. B-trees (PostgreSQL, MySQL) update pages in place — great for reads. LSM trees (Cassandra, RocksDB, LevelDB) turn every write into a fast sequential append — great for writes. Here's the LSM write path:

LSM tree: how write-optimised databases workStep-through
  1. The write is first appended to a log file on disk — a fast sequential write. If the machine crashes, the log is replayed. This is the D in durability.
  2. The write also goes into an in-memory sorted structure. The client gets “OK” now — no random disk seeks needed. Writes are extremely fast.
  3. When the memtable fills (e.g. 64MB), it's written to disk as an immutable, sorted file — a Sorted String Table. The WAL segment can be deleted.
  4. In the background, overlapping SSTables are merge-sorted into bigger, non-overlapping files. Old versions and deleted keys (tombstones) are discarded.
  5. A read checks the memtable, then L0, then L1… Bloom filters per file skip files that definitely don't contain the key. Reads can touch several files — the price of fast writes.

Choosing a database

Start from your access patterns and consistency needs, not from what's fashionable. Answer three questions:

Database chooserWizard
1. What does your data mostly look like?
2. Do you need multi-record transactions with strong consistency? (money, inventory, bookings)
3. Expected write volume?
🎤
Interview tip

“I'll start with PostgreSQL” is a perfectly strong answer for most systems — if you justify it (relations, transactions, mature tooling) and explain what would make you switch (write volume beyond one primary, schema-less data, global distribution). Real systems often use several databases, each for what it's best at — that's called polyglot persistence.

Operating a database: pools, plans and locks

Most “the database is slow” incidents aren't about choosing the wrong database — they're about four things that every team rediscovers the hard way.

1. Connection pooling

Each Postgres connection is a process with its own memory; a few hundred is plenty, a few thousand is a meltdown. But 50 app servers × a 20-connection pool = 1,000 connections, and serverless functions can open one per invocation.

📐 Size the pool with Little's Law

Connections needed ≈ QPS × average query time. 500 queries/s × 4 ms ≈ 2 connections busy on average — so a pool of 10–20 per instance is generous. Bigger pools don't add throughput; they add queueing inside the database and make everything slower (Chapter 4).

🚪 Add a proxy pooler

PgBouncer, RDS Proxy or Vitess multiplex thousands of client connections onto a small number of real ones (transaction pooling). Essential for serverless and large fleets — just know that session-level features (some prepared statements, advisory locks, SET) behave differently in transaction mode.

2. Reading the query plan

EXPLAIN ANALYZE shows what the planner decided and what actually happened. The surprising part for newcomers: an index is not always faster. Index scans jump around the table for each match, so once a query touches a large fraction of rows, reading the whole table sequentially wins.

➕
The N+1 query problem
Fetch 50 posts, then loop and fetch each author: 51 round trips, each paying network latency. ORMs make this invisible. Fix with a join, an IN (…) batch, or a dataloader that coalesces the lookups. It's the single most common cause of “the page takes 3 seconds” — and the fix is usually two lines.


  
3. MVCC, long transactions and locks

  

    
🧬
MVCC
Postgres, MySQL/InnoDB and Oracle keep multiple versions of each row so readers never block writers and writers never block readers. Each transaction sees a consistent snapshot — the mechanism behind the isolation levels above.

    
🧹
Old versions must be cleaned
Dead row versions are removed by vacuum/purge. One forgotten transaction left open for hours pins every version created since, so tables bloat and queries slow down. Set idle_in_transaction_session_timeout and keep transactions short.

    
🔒
Deadlocks
Transaction A locks row 1 then row 2; B locks 2 then 1 — both wait forever, and the database kills one with a deadlock error. Prevention: always acquire locks in a consistent order, keep transactions short, and retry the victim (it's a normal, expected error).

  


-- Two patterns worth knowing by heart
SELECT * FROM jobs WHERE status = 'queued'
  ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;   -- competing workers never block each other

UPDATE accounts SET balance = balance - 10
  WHERE id = 42 AND balance >= 10;                 -- compare-and-set: no read-modify-write race


  
4. Shaping data for reads

  

    
📐
Normalize first
One fact in one place: no update anomalies, smaller writes, referential integrity. Start here — it's much easier to denormalize later than to un-tangle duplicated data.

    
📋
Denormalize deliberately
Copy the author's name onto each post to kill a join on the hottest query; accept that renames must fan out (asynchronously, Chapter 17). Denormalization is a cache with a consistency cost — treat it like one.

    
🧊
Materialized views
Precomputed query results stored as a table, refreshed periodically or incrementally. Great for dashboards and leaderboards; the trade-off is staleness and refresh cost.

  

  
📊
What to watch in production
Slow-query log and p99 per query shape · cache hit ratio · connection count vs pool size · replication lag (Chapter 8) · deadlocks and lock waits · table/index bloat and vacuum progress · disk and IOPS headroom. Most database incidents are visible in these numbers long before users notice.


  
⚠️
Common mistakes

    
    
      
  • Choosing NoSQL for “scale” without knowing the access patterns. The query shapes decide the store; a single well-indexed Postgres handles more than most people assume.
    • 
      
  • Adding indexes without measuring. Every index slows writes and takes space, and the planner may ignore the one you added.
    • 
      
  • Long transactions. They hold locks, bloat MVCC versions and turn a small hiccup into an outage. Keep them short and never wait on a network call inside one.

Interview drill

    
Choose: Pick a database for an order system: 5K writes/s, strict consistency, complex queries for support staff, and 5 years of history.

    
How a strong answer sounds
A sharded relational database (Postgres/MySQL with Vitess-style sharding) for the orders themselves — you need transactions, constraints and ad-hoc queries. Shard by customer or order ID so a single order's lifecycle stays on one shard. Push analytics and support search to derived stores fed by CDC: a warehouse for reporting and a search index for lookups, so the OLTP path stays predictable.

    
Debug: A query that used to take 5 ms now takes 4 seconds, with no code change. Where do you look?

    
How a strong answer sounds
EXPLAIN ANALYZE first: did the plan change from an index scan to a sequential scan? Common causes are stale statistics after a bulk load, data growth crossing a selectivity threshold, a parameter-sniffing/plan-cache issue, an index that's bloated or was dropped, or lock waits rather than execution time. Check pg_stat_activity/lock waits, then run ANALYZE and compare plans before touching the query.

Check your understanding

    

    

      
A query SELECT * FROM orders WHERE customer_id = 42 takes 8 seconds on 50M rows. Most likely fix?

      

      
Without an index the DB scans all 50M rows. A B-tree index finds matching rows in a handful of page reads.

    

    

      
Two users click “like” at the same moment; the count goes from 10 to 11 instead of 12. Which anomaly, and a simple fix?

      

      
Both read 10 and wrote 11. Atomic increments, row locks (FOR UPDATE) or optimistic version checks prevent it.

    

    

      
Which database family fits storing billions of IoT sensor readings written continuously and queried by device + time range?

      

      
Partition by device, cluster by timestamp: massive sequential writes and efficient range reads.

    

    

      
What guarantees a committed transaction survives a power cut?

      

      
The DB records changes in a durable log before acknowledging the commit, then replays it after a crash.

    

    

      
Why might adding 12 indexes to a write-heavy table hurt?

      

      
Indexes speed reads but each one adds write work and storage. Only index what your queries actually use.
