The relational model

Relational databases (PostgreSQL, MySQL, SQL Server, Oracle) store data in tables of rows and columns. Each table has a fixed schema: a list of its columns and their types. Tables point at each other using foreign keys (a column holding another table's ID), and SQL lets you JOIN them together when you query. Hover a row:

SELECT u.name, SUM(o.total) FROM users u

Here is what that query does, step by step. The JOIN pairs each order with the user whose id matches the order's user_id: order 101 and 103 pair with Ada, 102 with Grace, 104 with Linus. GROUP BY u.name then puts all of Ada's pairs in one pile, Grace's in another, and so on. Finally SUM(o.total) adds up each pile: Ada's is $42 + $99 = $141.

Normalisation means storing each fact in exactly one place. A user's city lives only in users, so it can't disagree with itself. If Ada moves to Paris, you change one row, and every order that points at her instantly "sees" the new city. If instead the city were copied onto every order, you'd have to find and change all of them — and if one update is missed, the data now says two different things. At large scale, systems sometimes denormalise: they copy data into several places to avoid slow joins. That buys read speed, and costs extra storage and more work on every update.

ACID transactions

Why care? Many real actions are more than one write. Moving money means taking it from one account and adding it to another. Placing an order means creating the order and lowering stock. If the server crashes, or two users act at the same moment, between those writes, you get money that vanished or stock sold twice. Transactions are how the database protects you from that.

A transaction groups several steps into one all-or-nothing unit. Either all of them happen, or none do. Relational databases promise four things about transactions, known as ACID:

How does the database undo a half-finished transaction after a crash? Before changing any data, it writes a note of the change to its write-ahead log (WAL), a file on disk that only ever grows at the end. A COMMIT is itself a line in that log. On restart, the database reads the log: changes whose transaction has a commit record are kept (re-applied if needed), and changes from transactions with no commit record are undone. That one log gives you both atomicity and durability.

Indexes: how databases find things fast

Without an index, finding WHERE email = 'ada@x.com' means reading every row in the table. That's called a full table scan. An index is a separate, sorted structure that maps column values to the rows that hold them, exactly like the index at the back of a book. Most indexes are B-trees: sorted trees that find any value in a few steps.

Why only a few steps? Each node of the tree holds a sorted list of keys that splits the values into ranges, and a pointer to a child node for each range. Suppose each node has 200 children. The root splits the table 200 ways; one level down, each child splits its share 200 ways again, so two levels cover 200 × 200 = 40,000 ranges, three levels cover 8 million, and four cover 1.6 billion. So finding one row in a billion-row table means reading about 4 small pages from disk, instead of a billion rows. Doubling the table adds almost nothing: that's what O(log n) means in practice.

A real B-tree node holds hundreds of keys (each node has 100–500 children). So even a billion rows is only about 4–5 levels deep, and the top levels are kept in RAM.

Indexes give you
  • Lookups take a few steps (O(log n)) instead of reading every row (O(n))
  • Fast range queries and sorting with ORDER BY, because B-trees are already sorted
  • The database can enforce that a value is unique
Indexes cost you
  • Every INSERT and UPDATE must also update every index, so writes get slower
  • Extra storage (sometimes more than the table itself)
  • An index nobody uses is pure cost
💡

In a multi-column index, the order matters. An index on (country, city) helps WHERE country='UK' and WHERE country='UK' AND city='London'. It does not help WHERE city='London' on its own. Think of a phone book sorted by last name, then first name: you can't look someone up by first name alone.

A handy rule: put the column you filter by equality first, and the column you filter by range or sort by last. An index on (user_id, created_at) answers "this user's orders from last week, newest first" by jumping to that user and reading a short, already-sorted slice.

Isolation levels & concurrency anomalies

Perfect isolation — behaving exactly as if transactions ran one at a time (“serializable”) — is slow. So databases offer weaker levels. Each weaker level allows certain odd results, called anomalies, in exchange for handling more work. Pick a scenario and a level, then play the timeline:

Why is serializable slow? To be sure two transactions could have run one after the other, the database must either make one wait (locking) or watch for conflicts and cancel one of them so the app retries. Under heavy load, both mean more waiting and wasted work. Weaker levels skip some of those checks. The four anomalies below are the specific things that can go wrong when they do:

  • Dirty read — you see another transaction's change before it commits, and it may later be undone.
  • Non-repeatable read — you read the same row twice in one transaction and get two different values.
  • Lost update — two transactions read, change and write back the same value; one change silently disappears.
  • Phantom — you run the same search twice and a new row that matches it has appeared (for example, a new booking in the same time slot).

* PostgreSQL's Repeatable Read (it gives each transaction a snapshot of the data) spots lost updates and cancels one transaction. MySQL's does not. Always check your own database's documentation. Common fixes for lost updates: lock the row with SELECT … FOR UPDATE; use a single update that does the maths in the database (SET likes = likes + 1); or use optimistic locking, where a version column lets the write fail if someone changed the row first.

Which fix when? Use the single atomic update when the change is simple maths on one row (counters, balances). Use SELECT … FOR UPDATE when you must read the row, run some logic, then write, and conflicts are common — the second transaction simply waits a few milliseconds. Use optimistic locking (UPDATE … SET version = 8 WHERE id = 1 AND version = 7; zero rows changed means someone beat you, so reload and retry) when conflicts are rare, or when the "read" and the "write" happen in different requests, such as a user editing a form for two minutes.

NoSQL: the four big families

“NoSQL” is a broad label for databases that give up some relational features — fixed schemas, joins, sometimes transactions — in exchange for flexibility, easy scaling across many machines, or speed at one specific job.

Why would anyone give those up? Joins and multi-row transactions are easy when all the data sits on one machine. Once data is split over 100 machines, a join may need to ask many of them and wait for the slowest, and a transaction touching rows on two machines needs extra coordination. Most NoSQL stores make the trade upfront: each request touches one key or one partition, so it can be answered by a single machine, and adding machines adds capacity almost in a straight line.

A giant lookup table spread over many machines. You can get or put a value by its key, and that's all. Very fast, and easy to split across machines. Redis, DynamoDB, Memcached, etcd.

session:abc123→{"userId":42,"exp":1735689600}
cart:42→["sku_991","sku_12"]
rate:ip:203.0.113.9→17

Use for: sessions, caching, shopping carts, rate-limit counters, feature flags. Avoid when: you need to search by anything other than the key.

Complete JSON-like documents, grouped into collections. Each document can have a different shape. Data can be nested inside it, and you can query or index any field. MongoDB, Couchbase, Firestore.

{
  "_id": "prod_77", "name": "Trail Shoe", "price": 89,
  "variants": [ { "size": 42, "stock": 3 }, { "size": 43, "stock": 0 } ],
  "specs": { "waterproof": true, "drop_mm": 6 }   // other products may have different specs
}

Use for: catalogues, website content, user profiles — things you read as one whole item, where the fields vary. Avoid when: your data is full of links between things that need many-to-many joins.

Rows are grouped by a partition key, and each row's columns are kept sorted. Rows don't all need the same columns. Built for huge numbers of writes across many machines. You design the tables around the queries you'll run. Cassandra, HBase, ScyllaDB, Bigtable.

Reading this table: all messages for chat_881 live together on one machine (the partition key picks the machine), already sorted newest first (the clustering key sets the order). So "the last 20 messages in chat 881" is one short read from one place. But "every message Ada ever sent" is not: her messages are scattered across millions of chat partitions. If you need that query, you add a second table partitioned by sender, and write each message to both.

Use for: chat history, sensor readings over time, activity logs — anything with heavy writes at huge scale. Avoid when: you need to ask new, unplanned questions of the data, or to join tables.

The data is stored as nodes (things) and edges (links between them). Following links stays cheap, however many hops you take. Neo4j, Amazon Neptune, JanusGraph.

Use for: social networks (“friends of friends who like X”), rings of fraudsters, recommendations, knowledge graphs. Avoid when: your data isn't mainly about connections.

🔎 Search engines

Elasticsearch, OpenSearch. They build an inverted index — a map from each word to the documents holding it — for text search, near-miss matching and filters by category.

📈 Time-series

InfluxDB, TimescaleDB, Prometheus. Built for measurements that are only ever added, each with a timestamp, and for shrinking old data to a coarser resolution.

🧮 Columnar / OLAP

ClickHouse, BigQuery, Snowflake. They store data column by column, so an analytics query over billions of rows only reads the few columns it needs.

🧭 Vector

pgvector, Pinecone, Milvus. They find the items most similar in meaning to a query, by comparing lists of numbers (embeddings) that AI models produce.

🌍 NewSQL

Spanner, CockroachDB, YugabyteDB. SQL and ACID transactions, but spread across many machines.

🪣 Object storage

S3, GCS. Not a database, but where images, videos and backups live. Cheap, and it never really runs out of room.

Under the hood: B-trees vs LSM trees

The part that actually stores data on disk (the storage engine) comes in two main designs. B-trees (PostgreSQL, MySQL) change data where it already sits on disk, which is great for reads. LSM trees (Cassandra, RocksDB, LevelDB) instead add every write to the end of a file, which is fast because the disk head never jumps around. That's great for writes. Here's how an LSM write works:

The trade-off in one sentence each. A B-tree update finds the right page and rewrites it in place, so a key lives in exactly one spot and a read is one tree walk; but each small write can cause a random page write somewhere on disk. An LSM tree never rewrites old data on the spot; it batches writes in memory and writes big sorted files in one go, so writes are cheap; but a key may exist in several files, so reads may check several places, and background merging (compaction) uses disk bandwidth later. Rule of thumb: mostly reads and range scans with moderate writes → B-tree; very high write rates (logs, metrics, chat) → LSM.

LSM tree: how write-optimised databases workStep-through
  1. The write is first added to the end of a log file on disk. Writing to the end is fast. If the machine crashes, the database replays that log to recover. This is the D in durability.
  2. The write also goes into a sorted structure in memory, called the memtable. The client gets “OK” right away, with no need to hunt around the disk. That makes writes extremely fast.
  3. When the memtable is full (say 64MB), it's written to disk as one sorted file that is never changed again — a Sorted String Table (SSTable). That part of the write-ahead log can then be deleted.
  4. In the background, SSTables covering the same keys are merged into bigger files that don't overlap. Old versions, and keys marked as deleted (“tombstones”), are thrown away.
  5. A read checks the memtable first, then level 0, then level 1, and so on. Each file has a Bloom filter: a tiny structure that can say “this key is definitely not in here”, so the file is skipped. Even so, one read may open several files. That's the price of fast writes.

Choosing a database

Start from how your data will be read and written (your access patterns) and how fresh and correct it must be (your consistency needs). Don't start from what's fashionable. Answer three questions:

Database chooserWizard
1. What does your data mostly look like?
2. Do you need multi-record transactions with strong consistency? (money, inventory, bookings)
3. Expected write volume?
🎤
Interview tip

“I'll start with PostgreSQL” is a strong answer for most systems — as long as you say why (relationships, transactions, well-proven tools) and what would make you switch (more writes than one main server can take, data with no fixed shape, users spread around the world). Real systems often use several databases, each for what it does best. That's called polyglot persistence.

Operating a database: pools, plans and locks

Most “the database is slow” incidents have nothing to do with picking the wrong database. They come down to four things that every team learns the hard way.

1. Connection pooling

Opening a database connection is expensive: a network handshake, often TLS, a login check, and on Postgres a new server process. That can take several milliseconds — longer than the query itself. A connection pool opens a handful of connections once and lends them out to requests, which hand them back when done. Each Postgres connection is a separate process with its own memory. A few hundred is plenty; a few thousand brings the server down. But 50 app servers each holding a pool of 20 connections is already 1,000 connections — and serverless functions can open one connection per call.

📐 Size the pool with Little's Law

Connections needed ≈ queries per second × average query time. 500 queries/s × 4 ms ≈ 2 connections busy at any moment, so a pool of 10–20 per instance is already generous. Bigger pools don't get more work done. They just move the queue inside the database and make everything slower (Chapter 4).

🚪 Add a proxy pooler

PgBouncer, RDS Proxy and Vitess sit in the middle and share a small number of real database connections between thousands of client ones, handing one out for each transaction. This is essential for serverless apps and big fleets. Just be aware that features which rely on one long-lived session (some prepared statements, advisory locks, SET) behave differently in this mode.

2. Reading the query plan

EXPLAIN ANALYZE shows the plan the database chose and what actually happened when it ran. The surprise for newcomers: an index is not always faster. Using an index means jumping to a different place in the table for every match. Once a query matches a large share of the rows, reading the whole table straight through wins.

A sized example: a 10-million-row table fills about 100,000 pages of 8 KB. A query matching 0.01% of rows (1,000 rows) via the index reads a few index pages plus up to 1,000 table pages — tiny. A query matching 30% (3 million rows) could need up to 3 million scattered page reads through the index, while a sequential scan reads all 100,000 pages once, in order. The full scan wins by a wide margin. The planner does this sum for you using statistics: stored estimates of how many rows each value matches.

The N+1 query problem
You fetch 50 posts, then loop through them and fetch each author separately: that's 51 round trips, each paying the network delay. ORMs (libraries that map objects to tables) hide this, so it's easy to miss. Fix it with a join, one IN (…) query for all the authors, or a “dataloader” that collects the lookups and sends them as one. It's the most common cause of “the page takes 3 seconds”, and the fix is usually two lines.


  
3. MVCC, long transactions and locks

  

    
🧬
MVCC
MVCC means multi-version concurrency control. Postgres, MySQL/InnoDB and Oracle keep several versions of each row, so readers never have to wait for writers and writers never wait for readers. Each transaction sees one steady snapshot of the data. This is how the isolation levels above are built.

    
🧹
Old versions must be cleaned
Old row versions that nobody needs are cleaned up by vacuum (or purge). But one forgotten transaction left open for hours keeps every version made since then, so tables swell up and queries slow down. Set idle_in_transaction_session_timeout and keep transactions short.

    
🔒
Deadlocks
Transaction A locks row 1, then wants row 2. Transaction B locks row 2, then wants row 1. Each waits for the other forever, so the database cancels one with a deadlock error. To prevent it: always take locks in the same order, keep transactions short, and simply retry the cancelled one — this error is normal and expected.

  

  
What the two patterns below do. The first is a job queue in plain SQL: each worker grabs up to 10 queued jobs and locks them; SKIP LOCKED means a second worker skips rows another worker already holds, instead of waiting, so ten workers each get different jobs. The second is a compare-and-set: the check (balance >= 10) and the change happen in one statement, so no other transaction can sneak in between them. If the database reports "0 rows updated", the balance was too low and you tell the user.


-- Two patterns worth knowing by heart
SELECT * FROM jobs WHERE status = 'queued'
  ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;   -- competing workers never block each other

UPDATE accounts SET balance = balance - 10
  WHERE id = 42 AND balance >= 10;                 -- compare-and-set: no read-modify-write race


  
4. Shaping data for reads

  

    
📐
Normalize first
Keep each fact in one place. Then an update can't leave two copies disagreeing, writes are smaller, and links between tables stay valid. Start here: it's much easier to copy data later than to untangle copies that have drifted apart.

    
📋
Denormalize deliberately
For example, copy the author's name onto each post so your busiest query needs no join. In return, accept that renaming an author means updating many posts, usually in the background (Chapter 17). Denormalization is really a cache that can go out of date — treat it like one.

    
🧊
Materialized views
The result of an expensive query, worked out ahead of time and stored as a table. It's refreshed on a schedule, or updated bit by bit. Great for dashboards and leaderboards. The trade-off: the numbers are slightly old, and refreshing costs work.

  

  
📊
What to watch in production
The slow-query log, and the p99 time for each kind of query · the cache hit ratio · how many connections are open versus your pool size · how far behind the copies are (replication lag, Chapter 8) · deadlocks and time spent waiting for locks · wasted space in tables and indexes, and how vacuum is keeping up · spare disk space and spare disk operations per second (IOPS). Most database incidents show up in these numbers long before users notice.

Common mistakes

    
    
      
  • Choosing NoSQL for “scale” before knowing how the data will be queried. The queries decide the store. One well-indexed Postgres handles far more than most people expect.

  • Adding indexes without measuring. Every index slows writes and takes space, and the planner may not even use the one you added.
    •

Run EXPLAIN ANALYZE first: did the plan switch from using the index to reading the whole table? Check your understanding

    

    

      
A query SELECT * FROM orders WHERE customer_id = 42 takes 8 seconds on 50M rows. Most likely fix?

      

      
Without an index the database reads all 50M rows. A B-tree index finds the matching rows in a handful of disk reads. Switching databases or adding app RAM doesn't change the fact that every row is being read, and isolation levels affect concurrency, not lookup speed.

    

    

      
Two users click “like” at the same moment; the count goes from 10 to 11 instead of 12. Which anomaly, and a simple fix?

      

      
Both transactions read 10 and wrote 11, so one update was lost. Letting the database do the “+1” itself, locking the row with FOR UPDATE, or checking a version column all prevent it.

    

    

      
Which database family fits storing billions of IoT sensor readings written continuously and queried by device + time range?

      

      
Group rows by device, and keep each device's rows sorted by timestamp. That gives fast writes at the end and efficient reads of a time range.

    

    

      
What guarantees a committed transaction survives a power cut?

      

      
The database writes the changes to a safe log on disk before it confirms the commit, then replays that log after a crash.

    

    

      
Why might adding 12 indexes to a write-heavy table hurt?

      

      
Indexes speed up reads, but each one adds work on every write and takes up space. Only index what your queries actually use.
