Scalability & Performance

Performance vs scalability

⚡ Performance problem

The system is slow even for a single user. A page takes 4 seconds at 3am with nobody else online. Fix: smarter code, database indexes, caching, less work per request.

📈 Scalability problem

The system is fast for one user but slow when busy. At peak times it slows down or crashes. Fix: add capacity in a way that really lets it handle more requests per second.

A system is scalable if adding resources adds capacity at about the same rate. Double the servers, and you handle nearly double the requests — without redesigning anything.

An example. One server handles 2,000 requests per second. You add three more. If the system is scalable, four servers handle close to 8,000 per second (maybe 7,500, since nothing is perfect). If instead all four servers wait on the same database lock, you might get only 3,000 per second. You paid 4× the money for 1.5× the capacity. That second system has a scalability problem, and the fix is removing the shared bottleneck, not buying more servers. Why you tell the two problems apart: they have opposite fixes. Adding servers does nothing for a performance problem, and tuning one request's code rarely fixes a scalability problem.

Vertical vs horizontal scaling

🏋️

Vertical scaling (scale up)

Buy a bigger machine: more CPU, more RAM, faster disks. No code changes needed. But there's a limit to how big a machine can get, the biggest ones are very expensive, and if it dies, everything dies.

🐜

Horizontal scaling (scale out)

Add more ordinary machines behind a load balancer. There's almost no limit, and losing one machine is fine. But your app must be built for it: servers must be stateless, and shared data must live in a shared store.

In practice: do both

Scale up first — it's simple, and modern machines are huge. Scale out the stateless parts (web and API servers) early, because it's cheap and gives you spares. Databases are usually scaled up for as long as possible before splitting them across machines (sharding, Chapter 8).

Stateless services: the key to scaling out

A server is stateless if it keeps no data about a particular user between requests. Then any server can handle any request, and the load balancer can send traffic anywhere. The most common hidden state? User sessions (who is logged in) kept in a server's memory.

Why did I just get logged out?Simulator

There are three common ways to fix the logged-out problem. Each has a cost:

  • Shared session store (like Redis, a fast in-memory database). Every server looks up the session there. Simple and flexible, and you can log a user out instantly by deleting their session. The cost: one extra network call per request (well under a millisecond inside a data center), and the store itself must be kept running.
  • Signed tokens (such as JWTs, covered in Chapter 11). The login details travel inside the cookie, with a signature the servers can check. No lookup needed. The cost: it is hard to cancel a token before it expires, so you keep their lifetime short.
  • Sticky sessions. The load balancer always sends Alice to Server A. Quick to set up, but it only hides the problem: if Server A restarts, Alice is still logged out, and load spreads unevenly. Chapter 5 covers this.

Sessions are not the only hidden state. Files uploaded to a server's local disk, in-memory caches that others rely on, and scheduled jobs that run on “the” server all break when there are several servers. Move each one to a shared place: object storage for files, a shared cache, a job queue.

Latency numbers every engineer should know

Good design instincts come from knowing roughly how long things take. Memory is fast, disks are slower, and networks across continents are very slow. The fastest and slowest differ by about a billion times (9 orders of magnitude). So the bars below use a log scale, where each step is 10× bigger. Switch to human scale to feel the difference.

How long does it take?
🧠

Memory ≫ disk

Reading from RAM is about 100× faster than a random read from an SSD. That's the whole reason caching works.

📡

Avoid round trips

One round trip across continents takes about 150ms. Group calls together, and put data near users (CDNs, regions).

🗜️

Compress before sending

CPU time is cheap compared to network time. Compressing data before sending usually wins.

Here is how these numbers change a design. A page needs 50 items from a database, and the code fetches them one at a time, in a loop.

  • Database in the same data center (about 0.5 ms per round trip): 50 × 0.5 ms = 25 ms. Wasteful, but nobody notices.
  • Database in another region (about 150 ms per round trip): 50 × 150 ms = 7.5 seconds. The page is unusable.
  • One query that fetches all 50 at once: a single round trip, so 150 ms even across regions.

The code is identical in all three cases. Only the distance changed. That is why engineers count round trips first and optimise code second.

Measuring latency: percentiles, not averages

Say 99 requests take 20ms and 1 takes 5 seconds. The average is about 70ms — which matches nobody's experience. So engineers use percentiles instead. p50 is the median: half of requests are faster. p95 means 95% are faster. p99 means only the slowest 1% are slower than this. The slow end (the “tail”) is often your most valuable users, because they have the most data.

How do you actually get a percentile? Collect the latency of every request in a time window, say 1,000 requests in the last minute. Sort them from fastest to slowest. The p50 is the 500th value, the p95 the 950th, and the p99 the 990th. So a p99 of 800 ms means 10 of those 1,000 requests took 800 ms or longer. (Monitoring tools estimate this with clever summaries instead of storing every value, but the meaning is the same.)

of page loads will hit at least one slow backend call. At 100 calls, that's 63%. The “rare” p99 becomes the normal experience. That's why big companies care so much about p99 and p999 (the slowest 1 in 1,000).

Where does 63% come from? Each call is fast 99% of the time, a probability of 0.99. For the page to be fast, every call must be fast. With independent calls you multiply: two calls are both fast 0.99 × 0.99 = 98% of the time. With 100 calls it is 0.99¹⁰⁰ ≈ 0.37, so 37% of pages are fully fast and 1 − 0.37 = 63% hit at least one slow call. With just 10 calls it is 1 − 0.99¹⁰ ≈ 10%. Common fixes: make fewer calls, run them in parallel rather than one after another, and send a second copy of a request if the first is taking unusually long (a “hedged request”), then use whichever answer comes back first.

Where the shortcuts come from. 1M requests a day ≈ 12 QPS because 1,000,000 ÷ 86,400 ≈ 11.6. A full storage estimate, step by step, for a service that saves 400 million posts a day at about 1 KB each:

  1. Per day: 400,000,000 × 1 KB = 400 GB.
  2. Per year: 400 GB × 365 ≈ 146 TB.
  3. Over 5 years: 146 TB × 5 ≈ 730 TB.
  4. With 3 copies for safety (replication): 730 TB × 3 ≈ 2.2 PB.

The conclusion matters more than the number: 2 PB will never fit on one database server, so the data must be spread across many machines. Photos or videos attached to posts would add far more, and they would go to object storage (Chapter 9).

Queueing: why latency explodes before capacity runs out

A server that can handle 100 requests per second doesn't slow down gently at 95 per second. It slows down badly. Requests arrive at random times, so they bunch up. When a bunch arrives while the server is busy, they wait in a queue. As the server gets close to 100% busy (its utilization), the queue — and so the delay — grows without limit. This is the most useful piece of math in capacity planning.

🛒
Analogy: the supermarket checkout

One cashier serves customers who arrive at random. At 50% busy, you walk straight up. At 90% busy, the queue is usually several people deep, because any small rush takes ages to clear. At 99% busy, the line goes out the door — with the same cashier working at the same speed.

📐

Little's Law

L = λ × W: items in the system = how fast they arrive × how long each one stays. 2,000 req/s × 50 ms = 100 requests in progress at once. So you need at least 100 workers or connections running at the same time. It's the quickest way to size thread pools, connection pools and queues.

⛓️

Amdahl's Law

If 5% of the work can only be done one step at a time (it's “serial”), then no amount of parallel machines gets you past a 20× speedup. Find that serial part — a global lock, a single writer, one shared counter — before buying machines.

📉

Universal Scalability Law

This adds a second cost: coherency, the cost of machines coordinating with each other (locks, clearing stale caches, agreeing on values). It grows with the square of the number of machines. So past some point, adding servers makes the system slower. Real clusters have a peak size.

Where Amdahl's 20× comes from. Say a job takes 100 seconds on one machine, and 5 of those seconds can't be split up. With N machines, the other 95 seconds shrink to 95 ÷ N, but the 5 seconds stay. With 10 machines: 5 + 9.5 = 14.5 seconds, a 6.9× speedup, not 10×. With 1,000 machines: 5 + 0.095 ≈ 5.1 seconds, about 19.6×. However many machines you add, the job never gets below 5 seconds, so the best possible speedup is 100 ÷ 5 = 20×.

🎯
Practical rules

Keep each server around 60–70% busy at peak. Size pools with Little's Law instead of guessing. Fix one-at-a-time sections and coordination costs before adding hardware. And remember that timeouts + retries on an overloaded system make it worse — a queue that's already too long doesn't need duplicate requests (Chapter 16).

⚠️
Common mistakes
  • Quoting averages. A 50 ms average with a 2 s p99 is a bad experience for a lot of people — and fan-out makes the slow tail matter even more.
  • Planning for 100% utilization. Queueing math says delay explodes as a server gets close to full. Aim for ~60–70% and keep spare room.
  • Assuming linear scaling. One-at-a-time sections and coordination costs mean the tenth machine adds much less than the second. Past some point, adding machines makes things slower.

Interview drill

Estimate: 200M daily users each make 2 writes and 40 reads. Size it out loud.

How a strong answer sounds
400M writes/day ÷ ~10⁵ s ≈ 4,600 writes/s on average. With a 3× peak factor that's ~14K/s — more than one main SQL database can take. So split the data (shard) or use a database built for heavy writes. 8B reads/day ≈ 92K/s on average, 280K/s at peak. Reads can be cached, so a cache that answers most reads, plus read replicas, can handle it. Then say what that means: the write side needs the data split up, the read side needs caching, and the two can grow separately.

Diagnose: Throughput is fine but p99 doubled after you added servers. What's your hypothesis?

How a strong answer sounds
More servers means more connections to shared things — database connection pools, a shared cache, a lock. So the waiting (contention, queueing) moved somewhere else rather than going away. Another possibility: more parallel fan-out means each request now waits on more responses, so the slowest of them decides the time. Before adding capacity, I'd check the latency of each dependency, whether pools are full, and whether the work has a one-at-a-time section (Amdahl).

🧠 Key takeaways

  • Performance = fast for one user. Scalability = stays fast as load grows.
  • Latency rises steeply, not steadily, as servers get busier — keep spare room (≈60–70% busy at peak).
  • Little's Law (L = λW) sizes pools and queues. Amdahl's Law and the USL set limits on what more servers can give you.
  • Scaling up is simple but has a ceiling and a single point of failure. Scaling out has almost no limit but needs stateless servers.
  • Move session and other state out of app servers into shared stores.
  • Memory is far faster than SSD, which is far faster than a network hop across regions. Design around those gaps.
  • Track p95/p99, not averages. Fan-out makes slow-tail latency worse.
  • Estimate QPS, storage and the read/write ratio before choosing an architecture.

Check your understanding

Users are randomly logged out after you add a second web server. Most likely cause?

Keeping sessions in memory makes servers stateful. Store sessions in a shared store (like Redis), or use signed tokens, so any server can handle any request.

Your dashboard shows average latency 80ms. Users still complain. What should you look at?

Averages hide the slow tail. A p99 of 3s means 1 in 100 requests is terrible — and heavy users hit it often.

A service handles 50M requests/day, evenly spread. Roughly what is the average QPS?

50,000,000 ÷ 86,400 ≈ 580. Shortcut: 1M/day ≈ 12 QPS, so 50M ≈ 600.

Which is roughly the slowest?

~150ms, vs ~0.25ms (RAM), ~0.5ms (round trip inside a data center), ~0.15ms (SSD). Physics — the speed of light in fibre-optic cable — sets the minimum.

What's the main drawback of relying only on vertical scaling?

Bigger machines need no code changes, which makes them a great first step. But they hit a limit, and there's no spare if the one machine fails.
