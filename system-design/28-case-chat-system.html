Design a Chat System

WhatsApp, Messenger, Slack, Discord. Real-time messaging combines nearly everything in this course: persistent connections, stateful servers, message queues, ordering, durable storage, delivery guarantees and presence. Let's build it.

  • Choose the right real-time protocol
  • Route messages between stateful gateway servers
  • Implement sent / delivered / read receipts
  • Handle offline users with push & sync
  • Guarantee per-conversation ordering
  • Design presence at scale

STEP 3 / 6

Connections: why WebSockets

Recall Chapter 3: the server must push messages the instant they arrive, and clients send frequently too. Polling wastes battery and adds latency; SSE is one-way. WebSockets give a persistent, full-duplex, low-overhead channel. (Mobile apps often use MQTT or a custom protocol over TCP for the same reasons.)

🔌

Chat gateways are stateful

Each gateway holds ~100K live sockets in memory. Alice's messages must reach the specific gateway holding Bob's socket.

📍

Session registry

On connect, record bob → gateway-17, device-2 in Redis (with TTL refreshed by heartbeats). Lookups route each message.

🧠

Keep gateways thin

Gateways only manage connections. Business logic lives in stateless chat services, so gateways can be drained and redeployed safely.

Client sends over WebSocket with a client message ID

The client-generated ID makes retries idempotent: if the connection drops before the ack, resending won't duplicate.

Chat service assigns a sequence number & persists

Per-conversation monotonically increasing seq. Write to the messages DB (replicated). Only then ack the sender → ✓. Durability before acknowledgement.

Route via the session registry

Look up all of the recipient's connected devices. For each, forward to the owning gateway (via internal pub/sub channel per gateway, or direct RPC).

Deliver or push

Online: push down the socket; the device acks → ✓✓. Offline: send a push notification; the message waits in the DB.

Sync on reconnect

Each device remembers the last seq it has per conversation, and asks “give me everything after seq 41”. Works identically for new devices and flaky networks.

Ordering messages correctly

Phone clocks are wrong all the time. If you sort by the client's timestamp, replies can appear before the questions they answer. Instead the server assigns an increasing sequence number per conversation (or a Snowflake ID from a single sequencer per conversation).

Presence: who's online?

Presence seems small but it's one of the highest-traffic parts of a chat system: every app open, close and network blip changes it, and each change could notify hundreds of friends.

⚙️ How it works

Clients heartbeat every ~5s over the socket; the presence service stores last_heartbeat in Redis with a TTL. No heartbeat for ~30s → offline, “last seen” = last heartbeat. A graceful close marks offline immediately. The timeout avoids flapping when a train goes through a tunnel.

📉 Keeping it cheap

Don't broadcast every change to every friend. Only publish presence to users currently viewing that contact (subscribe on screen open), batch updates, and for large groups show just a member count — or skip presence entirely, like Slack's big channels.

STEP 5 / 6

Group chats

👨‍👩‍👧 Small groups (≤ ~500)

Fan-out on write: store the message once in the group's conversation, then deliver to each member's connected devices (via the registry) and push to offline ones. Like the feed chapter's push model — member counts are bounded, so it's affordable.

📣 Huge channels (100K+)

Fan-out on read: don't push to everyone. Clients viewing the channel subscribe to it; others see an unread badge computed lazily from the latest seq vs their last-read seq. Exactly the celebrity trade-off from Chapter 27.

STEP 6 / 6

Deep dives & failure handling

🌊

Reconnect storms

A gateway dies → 100K clients reconnect at once. Use exponential backoff with jitter on the client (Chapter 16), and spread reconnections across gateways with the load balancer (least connections).

🚚

Deploying gateways

Stateful servers can't just be killed. Stop routing new connections, tell clients to reconnect elsewhere gradually, then drain — a rolling deploy can take hours.

🔐

End-to-end encryption

With the Signal protocol, only devices hold keys; servers store and route ciphertext. Multi-device means encrypting per device, and servers can't search or moderate content.

🖼️

Media

Upload images/video directly to object storage with a pre-signed URL; the message carries only a reference and thumbnail. Serve via CDN.

🛡️

Spam & abuse

Rate limit messages per user and per new conversation (Chapter 15), detect bulk senders asynchronously from the message stream, and allow reporting/blocking.

🗄️

Storage tiers

Recent messages in a fast wide-column store (Cassandra/ScyllaDB/HBase); older ones compacted to cheaper storage. WhatsApp historically deleted messages from servers after delivery.

⚠️
Common mistakes
  • Using timestamps for message order. Device clocks disagree; use a per-conversation sequence assigned by the server.
  • Treating presence like messages. Presence is high-volume, low-value and ephemeral — throttle it and drop it under load.
  • Ignoring the reconnect storm. When a gateway dies, 100K clients reconnect at once unless they back off with jitter.
🎤
Interview drill

Design: A user has three devices. How do they all stay in sync, including after being offline for a week?

How a strong answer sounds
Each conversation has a monotonically increasing sequence number assigned server-side. Every device stores the highest sequence it has applied per conversation, and on reconnect asks for everything after it — a cursor sync that's idempotent and works no matter how long it was away. Read state (“last read seq”) is per device-user and synced the same way, so unread badges converge. Push notifications are just a hint to come and sync.

Scale: How do you find which server holds a given user's WebSocket connection?

How a strong answer sounds
Keep a session registry: user → gateway instance, in Redis with a TTL refreshed by heartbeat. To deliver a message, look up the recipient's gateways and forward to them — or publish to a pub/sub channel per user and let gateways subscribe for their connected users, which avoids a lookup per message. Either way, handle the race where the user reconnects elsewhere mid-delivery by making delivery idempotent and letting the client re-sync by sequence.

🧠 Key takeaways

  • Use persistent full-duplex connections; keep gateways thin and track sessions in a registry.
  • Persist before acknowledging; client message IDs make resends idempotent.
  • Receipts are just acks flowing back: sent (server stored), delivered (device got it), read (user opened).
  • Offline users get push notifications and sync by last-seen sequence number on reconnect.
  • Order by server-assigned per-conversation sequence, never by device clocks.
  • Presence uses heartbeats + timeouts and should only be published to interested viewers.

Check your understanding

Alice is connected to gateway 3 and Bob to gateway 41. How does Alice's message reach Bob?

A registry (e.g. Redis) maps user/device → gateway, so messages are routed precisely instead of broadcast.

When should the server send the “sent ✓” acknowledgement to the sender?

Acking before persistence could lose a message the sender believes was sent — violating the “never lose” requirement.

Messages in a group appear out of order for some users. What's the most robust fix?

Device clocks can't be trusted (Chapter 13). A per-conversation sequencer gives everyone the same total order.

Bob's phone was offline for 3 hours. On reconnect, how does it get the messages it missed?

Cursor-style sync by sequence number is simple, idempotent and works across multiple devices.

A gateway holding 100K connections crashes. What prevents the reconnect wave from knocking over other gateways?

Jitter spreads 100K simultaneous reconnects over time — the thundering herd fix from Chapter 16.
