Design a Chat System

WhatsApp, Messenger, Slack, Discord. Real-time chat uses nearly everything in this course: connections that stay open, servers that remember who is connected, message queues, ordering, safe storage, delivery guarantees and presence (who's online). Let's build it.

  • Choose the right protocol for real-time messages
  • Route messages between gateway servers that each hold live connections
  • Implement sent / delivered / read receipts
  • Handle offline users with push notifications and sync
  • Keep messages in the right order within each conversation
  • Design presence (online / last seen) at scale

STEP 1 / 6

Requirements

Notice how different these are from the news feed. There, a few seconds of delay and the odd missing post were fine. Here, the user is watching the screen waiting for a reply, and a lost message is a real failure — someone missed “the meeting moved”. So chat trades some of the feed's freedom for stronger promises: low latency, no loss and a fixed order. Each of those promises will cost us something specific below.

Unlike the news feed, writes and reads are roughly balanced: each message is written once and delivered about once. The unusual cost is keeping 100 million connections open.

The working behind the tiles: 500M users × 40 messages = 20B messages/day. Divide by 86,400 s ≈ 230K messages/s, and a 3× evening peak gives ~700K/s. At ~100 bytes per message (text plus IDs and timestamps), 20B × 100 B = 2 TB/day, or about 730 TB a year before copies — so old messages will need cheaper storage. If about one user in five is connected at any moment, that's 100M open connections; at ~100K per gateway server you need ~1,000 gateways.

Why ~100K connections per server and not more? An idle open connection costs little CPU but some memory — tens of kilobytes for buffers and TLS state. 100K × ~20 KB ≈ 2 GB, which is comfortable. Well-tuned servers can hold millions, but keeping each one smaller limits the damage when one dies: 100K users reconnecting is a spike; 2M is a storm.

STEP 3 / 6

Connections: why WebSockets

Recall Chapter 3. The server must push each message the moment it arrives, and clients send often too. Let's check the options:

  • Polling (asking “anything new?” over and over) drains the battery and adds delay.
  • SSE (Server-Sent Events) only works one way, server to client.
  • WebSockets keep one connection open, let both sides talk at any time (full-duplex), and add little overhead per message.

Mobile apps often use MQTT or their own protocol over TCP, for the same reasons.

A quick comparison with numbers. Suppose 100M phones poll every 5 seconds: that's 20M requests per second, almost all answering “nothing new”, and each message waits up to 5 seconds. With WebSockets, the same phones send only a small heartbeat now and then, and a message arrives in the time it takes to cross the network — tens of milliseconds. The price is that each server now remembers its connections, which the next cards deal with.

🔌

Chat gateways are stateful

A gateway is a server that holds users' open connections. Each one keeps ~100K live sockets in memory. So Alice's message must reach the exact gateway holding Bob's socket.

📍

Session registry

When a user connects, save bob → gateway-17, device-2 in Redis. The entry has a TTL (expiry time) that each heartbeat renews. To route a message, look up the recipient here.

🧠

Keep gateways thin

Gateways only manage connections. The real app logic lives in separate chat services that keep no state. That way, gateways can be emptied and redeployed safely.

Why must the registry entry have a TTL? Phones vanish without saying goodbye — the battery dies or the train enters a tunnel. Without an expiry, the registry would keep saying “Bob is on gateway-17” long after that connection died, and messages would be sent into nothing. With a TTL of, say, 30 seconds that each heartbeat renews, a dead connection clears itself within half a minute, and the message falls back to “store and push”.

Client sends over WebSocket with a client message ID

The client creates the ID itself. That makes retries idempotent (safe to repeat): if the connection drops before the server confirms, resending won't create a duplicate.

Chat service assigns a sequence number & persists

Each conversation has its own seq counter that only goes up. Write the message to the messages DB (which keeps copies). Only then confirm to the sender → ✓. Save first, confirm second.

Route via the session registry

Look up all of the recipient's connected devices. Forward the message to the gateway holding each one. This can go through an internal pub/sub channel per gateway, or a direct call (RPC).

Deliver or push

Online: send it down the socket, and the device confirms → ✓✓. Offline: send a push notification, and the message waits in the DB.

Sync on reconnect

Each device remembers the last seq it has in each conversation. It asks: “give me everything after seq 41”. This works the same way for brand-new devices and for shaky networks.

Why this exact order? Each step closes a gap the previous one left open:

  • Save before ✓. If the server said ✓ and then crashed before saving, the sender would believe a message was sent that no longer exists. Saving first means ✓ is a real promise.
  • Client message ID. Suppose the message is saved but the ✓ is lost on a bad network. The phone resends. The server sees the same client ID already stored and just repeats the ✓ instead of saving a second copy.
  • Deliver after saving. Even if the recipient's gateway crashes mid-delivery, the message is safe in the database, and the sync step picks it up on reconnect. Live delivery is a speed-up; the database is the source of truth.

A tiny trace: Alice sends message with client ID a-77. The server stores it as seq 42 and replies ✓. Bob's phone is offline, so a push goes out. Two hours later Bob opens the app; his phone last saw seq 41, so it asks for “after 41”, gets seq 42, and confirms → Alice sees ✓✓.

Ordering messages correctly

Phone clocks are often wrong. If you sort by the client's timestamp, a reply can appear before the question it answers. Instead, the server gives each message the next sequence number for that conversation. (Another option: a Snowflake ID from one ID generator per conversation.) Think of the ticket machine at a deli counter: the order comes from the machine, not from anyone's watch.

How do you give out sequence numbers when many servers handle one conversation? The simplest way is to make one place own each conversation's counter — for example an atomic INCR on a Redis key seq:grp_lunch, or a conditional write in the database. Since a single chat rarely gets more than a few messages per second, one counter per conversation is never a bottleneck, and different conversations don't share counters at all. Notice what we are not promising: there's no global order across different chats, and nobody needs one.

One edge case: two people send at the same instant. Both messages get numbers, one is 7 and the other 8. Which is first is decided by who reached the counter first — a fair tie-break, and crucially the same order for every member.

Using conversation_id as the partition key keeps a whole chat on one partition. Sorting rows by seq on disk turns “latest 50” and “after seq N” into one range read each. Very large chats are also split into time buckets (Discord uses (channel_id, bucket)).

Presence: who's online?

Presence looks like a small feature. In fact it's one of the busiest parts of a chat system. Every app open, app close and network blip changes it, and each change could notify hundreds of friends.

Some rough numbers show why. Heartbeats alone: 100M connected devices, each sending one every 5 seconds, is 20M heartbeats per second — about 100 times the message rate. And if each status change were sent to all of a user's ~200 contacts, a few hundred million status changes a day would turn into tens of billions of updates. That's why presence is built to be cheap and to be the first thing dropped under load.

⚙️ How it works

Every ~5s, each client sends a heartbeat (a tiny “I'm still here” message) over the socket. The presence service stores last_heartbeat in Redis with a TTL. No heartbeat for ~30s → offline, and “last seen” = the last heartbeat. Closing the app normally marks you offline at once. The 30s wait stops your status from flapping (flipping on and off) while your train passes through a tunnel.

📉 Keeping it cheap

Don't send every change to every friend. Instead:

  • Only send presence to users looking at that contact right now (they subscribe when they open the screen).
  • Group updates into batches.
  • For large groups, show just a member count, or skip presence entirely, like Slack's big channels.
STEP 5 / 6

Group chats

👨‍👩‍👧 Small groups (≤ ~500)

Fan-out on write: store the message once in the group's conversation. Then deliver it to each member's connected devices (found through the registry), and send push notifications to offline ones. It's like the push model from the feed chapter. Groups have a size limit, so the cost stays affordable.

📣 Huge channels (100K+)

Fan-out on read: don't push to everyone. Clients looking at the channel subscribe to it. Everyone else sees an unread badge, worked out only when needed by comparing the latest seq with their last-read seq. It's exactly the celebrity trade-off from Chapter 27.

Worked example for a 500-member group. One message becomes up to 500 deliveries. If 5,000 such groups each send one message a second, that's 2.5M deliveries per second — heavy but fine, since each is a small socket write. A 200,000-member channel would turn one message into 200,000 deliveries, and a busy channel sends several a second. That is why the design switches to pull above a size limit: members who have the channel open get the message live, and everyone else just sees a number next to it.

STEP 6 / 6

Deep dives & failure handling

Chat's promises — no loss, fast, ordered — are easy when nothing breaks. These cards cover what happens when something does, and a few features that change the design.

🌊

Reconnect storms

When a gateway dies, its 100K clients all reconnect at once. On the client, wait longer after each failed try (exponential backoff) and add a random delay (jitter) so clients don't all retry together (Chapter 16). The load balancer spreads the reconnections across gateways, picking the one with the fewest connections.

🚚

Deploying gateways

You can't just kill a server that holds live connections. First stop sending it new connections. Then slowly ask its clients to reconnect elsewhere, until it's empty. A rolling deploy across all gateways can take hours.

🔐

End-to-end encryption

With the Signal protocol, only the devices hold the keys. Servers only store and pass along scrambled text (ciphertext). Multiple devices means encrypting once per device. And servers can't search or moderate the content.

🖼️

Media

Upload images and video straight to object storage with a pre-signed URL (a temporary upload link). The message carries only a reference and a thumbnail. Serve the files through a CDN.

🛡️

Spam & abuse

Rate limit messages per user and per new conversation (Chapter 15). Spot bulk senders in the background by watching the message stream. Let users report and block.

🗄️

Storage tiers

Keep recent messages in a fast wide-column store (Cassandra/ScyllaDB/HBase). Pack older ones into cheaper storage. WhatsApp used to delete messages from its servers once they were delivered.

More edge cases to mention

  • The session registry is wrong. Bob moved to another gateway a moment ago, but the registry still says the old one. The old gateway finds no socket and reports failure; the chat service treats Bob as offline for this message and sends a push. When Bob's phone syncs, it gets the message anyway. No loss, only a slightly slower delivery.
  • The message store is slow or a partition is down. The server can't save, so it must not send ✓. The client keeps the message in an outbox with a clock icon and retries with backoff. Because of the client message ID, a retry that succeeds twice still stores one copy.
  • A device is offline for months. Syncing “everything after seq N” could mean thousands of messages. Send them in pages, newest conversations first, so the app is usable quickly.
  • Group membership changes. Someone is removed at seq 120. They must not receive seq 121 onward. Check membership when the message is fanned out, not only when the group was created.

⚠️
Common mistakes
  • Using timestamps for message order. Device clocks disagree. Use a sequence number per conversation, assigned by the server.
  • Treating presence like messages. Presence changes are many, each one matters little, and they go stale fast. Limit them, and drop them when the system is busy.
  • Ignoring the reconnect storm. When a gateway dies, 100K clients reconnect at once unless they back off with jitter.

Interview drill

Design: A user has three devices. How do they all stay in sync, including after being offline for a week?

How a strong answer sounds
The server gives each conversation a sequence number that only goes up. Every device stores the highest number it has seen in each conversation. On reconnect, it asks for everything after that number. This “cursor sync” is safe to repeat, and works no matter how long the device was away. Read state (“last read seq”) is synced the same way, so unread badges end up matching on all devices. Push notifications are just a nudge to come and sync.

Scale: How do you find which server holds a given user's WebSocket connection?

How a strong answer sounds
Keep a session registry: user → gateway, stored in Redis with a TTL that each heartbeat renews. To deliver a message, look up the recipient's gateways and forward it to them. Another option: publish to a pub/sub channel per user, and let each gateway subscribe for the users connected to it. That avoids a lookup per message. Either way, the user might reconnect to a different gateway in the middle of a delivery. Handle that by making delivery safe to repeat, and letting the client re-sync by sequence number.

🧠 Key takeaways

  • Use connections that stay open and carry traffic both ways. Keep gateways simple and track who's connected where in a registry.
  • Save the message before confirming it. Client message IDs make resends safe.
  • Receipts are just confirmations flowing back: sent (server stored it), delivered (device got it), read (user opened it).
  • Offline users get push notifications. When they reconnect, they sync everything after the last sequence number they have.
  • Order messages by a per-conversation sequence number from the server, never by device clocks.
  • Presence uses heartbeats plus timeouts. Only send it to people who are looking.

Check your understanding

Alice is connected to gateway 3 and Bob to gateway 41. How does Alice's message reach Bob?

A registry (e.g. Redis) maps each user/device to its gateway. So messages go straight to the right place instead of being sent everywhere.

When should the server send the “sent ✓” acknowledgement to the sender?

If you confirm before saving, a crash could lose a message the sender thinks was sent. That breaks the “never lose a message” requirement.

Messages in a group appear out of order for some users. What's the most robust fix?

Device clocks can't be trusted (Chapter 13). One sequence counter per conversation gives everyone exactly the same order.

Bob's phone was offline for 3 hours. On reconnect, how does it get the messages it missed?

Syncing “everything after sequence N” is simple, safe to repeat, and works across multiple devices.

A gateway holding 100K connections crashes. What prevents the reconnect wave from knocking over other gateways?

Jitter spreads 100K reconnects out over time instead of all at once. It's the “thundering herd” fix from Chapter 16.
