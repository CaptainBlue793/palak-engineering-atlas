Object Storage, Files & Media at Scale

Databases are for structured records. But most of the bytes on the internet are photos, videos, backups, logs and ML datasets. Those live in object storage — the cheapest, most durable, most infinitely-scalable storage ever built. Knowing how to use it well is a core system design skill.

  • Understand how an object store is built internally
  • Upload huge files with presigned URLs and multipart uploads
  • Explain replication vs erasure coding and “11 nines” durability
  • Choose storage tiers and lifecycle policies to cut costs 10×

Three ways to store bytes

Every storage system answers the same question differently: what is the unit you read and write? A fixed-size block, a file in a folder tree, or an entire immutable object addressed by a key.

🏬
Analogy: a warehouse, an office cabinet and a coat check

Block storage is raw warehouse shelving — numbered slots, you decide what goes where. File storage is an office filing cabinet with nested folders that many people browse. Object storage is a coat check: hand over your coat, get a ticket (the key). You can't alter a sleeve in place — you swap the whole coat — but the coat check scales to billions of coats.

The disk is split into fixed-size blocks (e.g. 4 KB) addressed by number. There's no notion of files — a filesystem or database running on top decides what the blocks mean. Attached to one machine at a time (usually).

Great for
  • Databases (Postgres, MySQL data directories)
  • VM boot disks
  • Anything needing low-latency random reads/writes
Limits
  • Tied to one host / one AZ
  • You provision (and pay for) capacity up front
  • Sizes top out at terabytes

Examples: AWS EBS, GCP Persistent Disk, local NVMe SSDs, SAN volumes.

A hierarchy of directories and files with POSIX semantics: open, seek, write byte 1,000, lock, rename. Shared over the network by many machines via NFS or SMB.

Great for
  • Shared home directories, CMS uploads on legacy apps
  • ML training jobs reading a shared dataset
  • Lift-and-shift apps expecting a filesystem
Limits
  • Metadata operations (list, rename) get slow at billions of files
  • Locking & consistency across clients is hard
  • More expensive per GB than objects

Examples: AWS EFS, Azure Files, NetApp, HDFS (a distributed file system for big data), Lustre for HPC.

A flat namespace of buckets containing objects. Each object = key + bytes + metadata. Accessed over HTTP: PUT, GET, DELETE, LIST. Objects are immutable — to change one byte you upload a new version.

PUT https://media.s3.amazonaws.com/users/42/avatar.jpg
Content-Type: image/jpeg
x-amz-meta-uploaded-by: 42
<binary bytes>
→ 200 OK   ETag: "9b2cf535f27731c974343645a3985328"

The “folders” you see in a console are an illusion: users/42/avatar.jpg is just a key containing slashes. Listing by prefix makes it look like a tree.

Great for
  • Images, video, audio, documents
  • Backups, logs, archives
  • Data lakes and ML datasets
  • Static website assets behind a CDN
Limits
  • No in-place edits or appends
  • Higher per-request latency (tens of ms)
  • Not a database: no queries, no transactions across objects

Interview rule of thumb

Never store large binary blobs (images, PDFs, video) inside your database. Put the bytes in object storage and store only the key/URL and metadata in the database. Databases get bloated backups, slow replication and expensive storage when you stuff them with blobs.

Inside an object store

Systems like Amazon S3, Google Cloud Storage, Azure Blob and open-source MinIO or Ceph all share a similar shape: a stateless API tier, a strongly consistent metadata service that maps keys to physical locations, and a huge fleet of storage nodes holding the actual bytes spread across failure domains.

PUT /photos/cat.jpg — what really happensStep-through
  1. The client streams the bytes over HTTPS to any frontend server (behind DNS and load balancers). The frontend authenticates the signature (e.g. AWS SigV4) and checks the bucket policy allows PutObject.
  2. The metadata service chooses a placement: which storage nodes, in which availability zones, will hold this object's chunks. Big objects are split into chunks; each chunk is placed independently.
  3. Bytes are erasure-coded (or replicated) and written to nodes in three separate AZs, so losing an entire data centre loses no data. Each node verifies a checksum before acknowledging.
  4. Only after enough fragments are durably stored does the frontend commit cat.jpg → [chunk locations], size, ETag, version to the metadata store. This commit is the moment the object “exists” — which is how S3 provides strong read-after-write consistency.
  5. The client gets 200 OK plus an ETag (a hash of the content). A later GET reads metadata, fetches fragments in parallel, reassembles and streams the bytes back.
🗂️

Flat keys, smart prefixes

There are no real directories. LIST ?prefix=users/42/ scans a sorted key index. High-traffic buckets auto-partition by key prefix, so hot prefixes get split across more metadata shards.

🕰️

Versioning

Enable it and overwrites create new versions instead of destroying data; deletes just add a “delete marker”. Your defence against accidental deletion and ransomware — pair with Object Lock for write-once compliance.

🔔

Event notifications

Each PUT can emit an event to a queue or function: “new video uploaded → start transcoding”. This is the backbone of media pipelines (Chapter 32).

Uploading big files the right way

A naive design proxies uploads through your app servers: client → your API → S3. That means your servers hold gigabytes in memory or on disk, their bandwidth becomes the bottleneck, and a crash mid-transfer loses the whole upload. Two patterns fix this.

Pattern 1 — Presigned URLs: upload straight to storage

Direct-to-bucket upload with a presigned URLStep-through
  1. POST /uploads {filename, size, type}. Your API authenticates the user, validates size and type limits, and decides the object key (e.g. uploads/u42/7f3a…mp4 — never trust the client's filename as a key).
  2. The API records a PENDING upload row, then uses its secret key to sign a URL granting exactly one action — PUT this key, max 2 GB, content-type video/mp4 — valid for 15 minutes. No network call to storage is needed to sign.
  3. The bytes flow straight to object storage, which checks the signature and expiry. Your app servers see zero bandwidth and no memory pressure, and the upload uses storage's globally distributed edge (and optionally transfer acceleration).
  4. An ObjectCreated event (or a client callback) tells your API the upload finished. It verifies size/checksum, marks the row READY, and kicks off processing like virus scanning or thumbnailing.
🧹
Don't forget the abandoned uploads

Some clients will get a presigned URL and never upload, or upload and never confirm. Expire PENDING rows with a background job, and use a bucket lifecycle rule to delete objects under uploads/tmp/ older than a day. Presigned GET URLs work the same way for serving private files.

Pattern 2 — Multipart uploads: survive flaky networks

Split the file into parts (e.g. 8–100 MB each), upload parts in parallel, retry only the parts that fail, then send a CompleteMultipartUpload call listing the part ETags. Storage stitches them into one object. Required above 5 GB on S3; recommended above ~100 MB.

⏯️ Resumable uploads

Store the uploadId and completed part numbers on the client. After an app crash or a train tunnel, call ListParts and upload only what's missing. Google's resumable protocol and the open tus protocol offer the same idea for your own servers.

✅ Integrity end to end

Send a Content-MD5 or SHA-256 checksum per part; storage rejects corrupted parts. Keep a whole-file hash in your database so downloads can be verified — silent corruption across billions of files is real.

Durability: how you never lose a byte

S3 advertises 99.999999999% (11 nines) durability — lose one object out of 10 million roughly every 10,000 years. Disks fail constantly at this scale (a fleet of a million drives loses dozens per day), so durability comes from redundancy plus fast repair. There are two ways to add redundancy.

📑 Replication

Store N full copies (typically 3). Simple, fast reads from any copy, cheap repair (just copy). But storage overhead is 3× — you pay for 3 TB to store 1 TB.

🧮 Erasure coding (Reed–Solomon)

Split data into k data fragments, compute m parity fragments. Any k of the k+m fragments rebuild the original. RS(10,4) survives 4 failures at only 1.4× overhead. Costs CPU and makes repairs/reads slower.

What real systems do

Hot, small, frequently-read data is often replicated (fast reads, fast repair). Large and colder data is erasure-coded for cost. Many systems write 3 replicas first for speed and convert to erasure coding in the background once the object is a few hours old. The other half of durability is scrubbing: continuously re-reading data to detect bit rot and rebuilding fragments before a second failure hits.

Storage classes & lifecycle policies

Most data is hot for days and then almost never read again. Object stores offer tiers that trade cheaper storage for more expensive (and sometimes slower) retrieval. A lifecycle policy moves objects between tiers automatically.

💸
The hidden bill: egress and requests

Storing data is cheap; moving it out of the cloud is not (often ~$0.05–0.09/GB to the internet). A popular 1 GB video watched 100,000 times is 100 TB of egress. This is why media is always served through a CDN — which has cheaper bandwidth and caches near users — and why millions of tiny PUTs can cost more than the storage itself. Batch small objects together when you can.

Serving media fast and safely

🌍

Always put a CDN in front

Make the bucket the CDN's origin and block public access to the bucket itself (origin access control). The CDN caches objects at the edge, absorbs traffic spikes, supports HTTP range requests for video seeking, and cuts egress cost.

🏷️

Immutable, content-addressed keys

Name objects by content hash or version: img/9b2cf5…jpg. Content never changes under a key, so you can set Cache-Control: max-age=31536000, immutable. “Updating” an avatar means writing a new key and pointing the DB row at it — no CDN purge needed.

🖼️

Resize on the fly

Instead of pre-generating 12 thumbnail sizes, an image service at the edge transforms on request (/img/9b2c.jpg?w=320&fmt=webp) and the CDN caches each variant. Pre-generate only the hottest sizes.

🔏

Private content

For paid or personal files, hand out signed CDN URLs or signed cookies with short expiry, bound to a path. Authorization happens in your API; the CDN only verifies signatures, so it stays fast.

Object storage as a data lake

Object storage has quietly become the foundation of analytics too. Instead of loading everything into an expensive warehouse, companies drop raw and processed data into buckets as columnar files and query them in place.

Raw zone bronze

Events, logs and database exports land as-is (JSON, CSV, Avro), partitioned by date: s3://lake/events/dt=2026-09-17/hour=14/.

Cleaned zone silver

Batch or streaming jobs (Chapter 18) deduplicate, fix schemas and convert to Parquet — compressed, columnar files that let queries read only the columns they need.

Curated zone gold

Business-level aggregates ready for dashboards and ML features.

Table formats add database powers lakehouse

Apache Iceberg, Delta Lake and Hudi keep a transaction log of which files make up a table, giving ACID commits, schema evolution and time travel on top of plain objects. Engines like Spark, Trino, Snowflake and DuckDB query them directly.

⚠️
Common mistakes
  • Proxying uploads through your API. Your servers become the bandwidth bottleneck and hold gigabytes in memory; presign and let clients talk to storage directly.
  • Millions of tiny objects. Request costs and listing performance dominate; batch small items into larger objects or use a database.
  • Ignoring egress. Serving media straight from a bucket to users is the most expensive way to do it — put a CDN in front.
🎤
Interview drill

Design: Users upload 2 GB videos from phones on flaky networks. Design the upload path.

How a strong answer sounds
Client asks your API for an upload session; the API authorizes, records a PENDING row and returns presigned multipart URLs. The client uploads parts in parallel, retrying only failed parts, and resumes after a disconnect by listing completed parts. On completion the client (or an ObjectCreated event) tells the API, which verifies size and checksum, marks the record READY and triggers processing. Lifecycle rules clean up abandoned multipart uploads after a day.

Trade-off: Replication or erasure coding for a photo service?

How a strong answer sounds
Both, at different ages. Fresh uploads are replicated ×3 for fast writes, fast reads and cheap repair. Once objects cool (hours to days), a background job converts them to erasure coding — RS(10,4) gives the same tolerance at 1.4× instead of 3× storage, at the cost of more CPU and slower repair. Thumbnails stay replicated because they're small and hot.

🧠 Key takeaways

  • Block storage for databases and VMs, file storage for shared POSIX access, object storage for everything big, binary and write-once.
  • Store blobs in object storage and only their keys and metadata in your database.
  • Object stores separate a strongly consistent metadata layer from a massive fleet of storage nodes spread across availability zones.
  • Presigned URLs let clients upload and download directly, keeping bytes off your app servers.
  • Multipart uploads parallelize transfers and retry only failed parts; they're essential for large files on unreliable networks.
  • Replication is simple and fast; erasure coding gives the same fault tolerance for far less storage.
  • Lifecycle policies and storage tiers cut costs dramatically — but watch retrieval and egress fees.
  • Serve media through a CDN with immutable, content-addressed keys and signed URLs for private content.

Check your understanding

Your social app stores profile photos as BLOB columns in Postgres. Backups now take 9 hours. What's the best fix?

Binary media belongs in object storage. The database stays small, fast to back up and replicate, and photos can be served via a CDN.

Why do presigned URLs improve an upload flow?

Your API still authorizes the request and signs a narrow, short-lived permission — but the heavy data transfer bypasses your servers.

An RS(10,4) erasure-coded object has fragments on 14 nodes. How many node failures can it survive, and what's the storage overhead?

Any 10 of the 14 fragments rebuild the data, so up to 4 can be lost. Raw storage is 14/10 = 1.4× the data size.

Compliance requires keeping audit logs for 7 years; they are almost never read after the first month. Best approach?

Archive tiers cost a fraction of standard storage. Retrieval is slower and pricier, which is fine for rarely accessed compliance data.

Users update their avatar, but friends keep seeing the old one for hours. Avatars are served via a CDN from avatars/{userId}.jpg. Cleanest fix?

Immutable, versioned keys never need invalidation: the new URL is a cache miss by definition, and old URLs can be cached forever.
