Object Storage, Files & Media at Scale

Databases are for neat, structured records. But most of the bytes on the internet are photos, videos, backups, logs and machine-learning datasets. Those live in object storage: the cheapest, safest storage ever built, and it never runs out of room. Using it well is a core system design skill.

Three ways to store bytes

Every storage system answers one question differently: what is the smallest thing you read or write? A fixed-size block of bytes, a file in a folder tree, or one whole object that you look up by its key and never edit in place.

Why does that choice matter so much? The smaller and more editable the unit, the more work the system does to keep everything in step, and the harder it is to spread across many machines. Blocks let a database overwrite 8 KB in the middle of a file in under a millisecond, but only one machine can safely own them. Whole, never-edited objects are the opposite: because nothing changes after it's written, any server anywhere can hand out a copy without checking with anyone else — which is exactly what lets object storage grow without limit.

🏬
Analogy: a warehouse, an office cabinet and a coat check

Block storage is bare warehouse shelving: numbered slots, and you decide what goes where. File storage is an office filing cabinet, with folders inside folders that many people can browse. Object storage is a coat check: you hand over your coat and get a ticket (the key). You can't change one sleeve — you swap the whole coat — but a coat check can handle billions of coats.

The disk is cut into fixed-size blocks (say 4 KB), each with a number. There are no files at this level. Whatever runs on top — a filesystem or a database — decides what the blocks mean. A block volume is usually attached to one machine at a time.

Great for
  • Databases (Postgres, MySQL data directories)
  • VM boot disks
  • Anything that needs fast reads and writes at any position on the disk
Limits
  • Tied to one machine, in one availability zone (a separate data center)
  • You choose the size and pay for it up front, used or not
  • The biggest volumes are only a few terabytes

Examples: AWS EBS, GCP Persistent Disk, local NVMe SSDs, SAN volumes.

Folders inside folders, holding files, with all the usual operations: open a file, jump to a position, overwrite byte 1,000, lock it, rename it. (These standard rules are called POSIX.) It's shared over the network by many machines using NFS or SMB.

Great for
  • Shared home folders, and uploads for older apps that expect a disk
  • Machine-learning training jobs that all read one shared dataset
  • Apps moved to the cloud unchanged, which still expect a filesystem
Limits
  • Listing or renaming gets slow once there are billions of files
  • Locking, and keeping every client's view in step, is hard
  • Costs more per GB than object storage

Examples: AWS EFS, Azure Files, NetApp, HDFS (a file system spread over many machines, for big data), and Lustre for supercomputing.

You have buckets, and each bucket holds objects in one flat list — no real folders. Each object is a key (its name) plus its bytes plus some metadata (labels describing it). You use it over HTTP: PUT, GET, DELETE, LIST. Objects can't be edited: to change one byte, you upload the whole thing again.

The “folders” you see in the web console aren't real. users/42/avatar.jpg is simply a key that happens to contain slashes. Listing everything that starts with a given prefix makes it look like a folder tree.

Interview rule of thumb

Never put big binary files (images, PDFs, video) inside your database. Put the bytes in object storage, and keep only the key or URL, plus the metadata, in the database. Stuffing files into a database makes backups huge, replication slow, and storage expensive.

A sized example: 10 million users with a 200 KB avatar each is 2 TB of images. In a database on block storage (roughly $0.10/GB-month, times 3 for replicas) that's around $600 a month, and every replica must copy it. In object storage at about $0.023/GB-month it's about $46 a month, and the database keeps just a short key per user — around 10 million × 50 bytes = 500 MB.

Inside an object store

Amazon S3, Google Cloud Storage, Azure Blob and the open-source MinIO and Ceph are all built the same way. There's a stateless API tier that handles requests. There's a metadata service, always exactly up to date, that remembers where each key's bytes live. And there's a huge fleet of storage nodes holding the actual bytes, spread out so that no single failure can take them all.

Why split it this way? Each part has a different job and grows differently. The API tier holds no data, so you add or remove servers freely as traffic changes. The metadata service is small (a few hundred bytes per object) but must be exactly right — two readers must never disagree on what cat.jpg is — so it's built like a carefully replicated database. The storage nodes hold almost all the bytes and fail constantly, so they're treated as replaceable: when one dies, its data is rebuilt elsewhere from the other copies.

PUT /photos/cat.jpg — what really happensStep-through
  1. The client sends the bytes over HTTPS to any frontend server (reached through DNS and load balancers). The frontend checks the request's signature to confirm who sent it (e.g. AWS SigV4), and checks that the bucket's rules allow PutObject.
  2. The metadata service decides where the data goes: which storage nodes, in which availability zones (separate data centers), will hold the pieces of this object. Big objects are split into chunks, and each chunk is placed separately.
  3. The bytes are copied (or split into fragments with extra repair data — see erasure coding below) and written to nodes in three separate availability zones. So losing a whole data center loses no data. Each node checks a checksum before confirming.
  4. Only once enough fragments are safely on disk does the frontend save cat.jpg → [chunk locations], size, ETag, version in the metadata store. That save is the moment the object starts to “exist”. This is how S3 guarantees that a read right after a write always sees the new data.
  5. The client gets 200 OK plus an ETag: a short fingerprint (hash) of the content. A later GET looks up the metadata, fetches the fragments at the same time, puts them back together and streams the bytes back.
🗂️

Flat keys, smart prefixes

There are no real folders. LIST ?prefix=users/42/ just scans a sorted list of keys. Busy buckets are split up automatically by key prefix, so a popular prefix gets spread over more metadata machines.

🕰️

Versioning

Turn this on, and writing over an object creates a new version instead of destroying the old one. A delete just adds a “delete marker”. It's your protection against accidental deletion and ransomware. Add Object Lock when the rules say data must never be changed once written.

🔔

Event notifications

Each PUT can send an event to a queue or a function: “new video uploaded → start converting it”. This is the backbone of media processing pipelines (Chapter 32).

Uploading big files the right way

The obvious design sends uploads through your app servers: client → your API → S3. That means your servers hold gigabytes in memory or on disk, their bandwidth becomes the bottleneck, and a crash halfway through loses the whole upload. Two patterns fix this.

Put numbers on it: 1,000 users each uploading a 2 GB video in the same hour is 2 TB flowing in. Relayed through your API, every byte crosses your network twice (in from the phone, out to storage), and an app server with a 10 Gbit/s link (about 1.25 GB/s) could spend nearly an hour doing nothing but moving those bytes. Sent straight to storage, your API handles 1,000 tiny "may I upload?" requests, a few kilobytes each.

Pattern 1 — Presigned URLs: upload straight to storage

Direct-to-bucket upload with a presigned URLStep-through
  1. POST /uploads {filename, size, type}. Your API checks who the user is, checks the size and file type are allowed, and chooses the object key itself (e.g. uploads/u42/7f3a…mp4). Never use the client's own filename as the key — it can't be trusted.
  2. The API saves a PENDING row for this upload. Then it uses its secret key to sign a URL that allows exactly one action: PUT to this key, at most 2 GB, content type video/mp4, and only for the next 15 minutes. Signing is pure maths — it needs no call to the storage service.
  3. The bytes go straight to object storage, which checks the signature and the expiry time. Your app servers carry no traffic and use no extra memory. The upload also takes advantage of the storage provider's worldwide entry points.
  4. An ObjectCreated event from the storage service (or a call from the client) tells your API the upload finished. The API checks the size and checksum, marks the row READY, and starts follow-up work such as virus scanning or making thumbnails.
🧹
Don't forget the abandoned uploads

Some clients will ask for a presigned URL and never upload. Others will upload but never confirm. Use a background job to clear out old PENDING rows, and a bucket lifecycle rule to delete anything under uploads/tmp/ that's more than a day old. Presigned GET URLs work the same way when you need to hand out private files.

Pattern 2 — Multipart uploads: survive flaky networks

Split the file into parts (say 8–100 MB each). Upload the parts at the same time, and if one fails, retry just that part. When they're all up, send a CompleteMultipartUpload call listing each part's ETag, and the storage service joins them into one object. S3 requires this above 5 GB, and it's a good idea above about 100 MB.

Why it helps so much on a bad network: suppose a connection drops on average once every 500 MB. A single 1.2 GB upload almost never gets through in one go, and each failure throws away everything sent so far. Split into 12 parts of 100 MB, most parts succeed first time, and a failure costs at most 100 MB of re-sending. Sending 4 parts at once also fills the connection better than one stream. Edge cases to handle: S3 parts must be at least 5 MB (except the last one), there's a limit of 10,000 parts (so pick the part size from the file size), and an upload you start but never complete leaves hidden parts that you're billed for until you abort it.

⏯️ Resumable uploads

Keep the uploadId and the list of finished part numbers on the client. After the app crashes, or the phone goes through a tunnel, call ListParts and upload only the parts that are missing. Google's resumable upload protocol and the open tus protocol do the same thing for your own servers.

✅ Integrity end to end

Send a checksum (a Content-MD5 or SHA-256 fingerprint) with each part, so storage can reject any part that arrived damaged. Also keep a fingerprint of the whole file in your database, so downloads can be checked. Across billions of files, data really does get quietly corrupted.

Durability: how you never lose a byte

S3 advertises 99.999999999% durability — “11 nines”. That means if you store 10 million objects, you'd expect to lose one about every 10,000 years. At this scale disks fail all the time: a fleet of a million drives loses dozens every day. So durability comes from keeping spare copies and repairing fast. There are two ways to do that.

📑 Replication

Keep N complete copies, usually 3. It's simple, any copy can serve a read, and repairing just means copying again. But you store 3× the data — 3 TB of disk to hold 1 TB.

🧮 Erasure coding (Reed–Solomon)

Split the data into k fragments, then compute m extra “parity” fragments from them — a bit like a clever checksum you can rebuild from. Any k of the k+m fragments are enough to rebuild the original. RS(10,4) survives 4 lost fragments while storing only 1.4× the data. The cost is CPU work, and slower reads and repairs.

The simplest possible erasure code shows the idea. Split the data into two halves, A and B, and store a third fragment P = A XOR B (XOR compares bits: 1 if they differ, 0 if they're the same). Say A = 1010 and B = 0110; then P = 1100. Lose A, and you rebuild it as B XOR P = 0110 XOR 1100 = 1010. That's RS(2,1): any 2 of the 3 fragments give you everything back, for 1.5× storage. Reed–Solomon generalises this to survive several lost fragments at once. The trade-off shows up in repairs: to rebuild one lost fragment of RS(10,4), a node must read 10 other fragments over the network, while replication just copies one.

What real systems do

Small, popular data that's read constantly is usually copied (fast reads, fast repair). Large data that's rarely touched is erasure-coded to save money. Many systems write 3 copies first for speed, then convert to erasure coding in the background once the object is a few hours old. The other half of durability is scrubbing: constantly re-reading stored data to catch bits that have quietly decayed, and rebuilding those fragments before a second failure arrives.

Storage classes & lifecycle policies

Most data is popular for a few days, then almost never read again. Object stores offer tiers: cheaper storage in exchange for paying more (and sometimes waiting longer) when you read it back. A lifecycle policy moves objects between tiers for you, by age.

A sized example: a logging system keeps 100 TB, and anything older than 30 days is almost never read. At roughly $0.023/GB-month in the standard tier, 100 TB costs about $2,300 a month. If 90 TB of it is old and moved to a deep archive tier at about $0.001/GB-month, that 90 TB costs about $90 instead of $2,070 — the bill falls to around $320. The catch: reading from archive tiers can take hours and charges per GB retrieved, and most cold tiers bill a minimum storage time (often 30–180 days), so objects you delete or read often shouldn't go there.

The hidden bill: egress and requests

Storing data is cheap. Sending it out of the cloud is not — often about $0.05–0.09 per GB to the internet. This outbound traffic is called egress. One popular 1 GB video watched 100,000 times is 100 TB of egress. That's why media is always served through a CDN, which has cheaper bandwidth and caches copies near users. It's also why millions of tiny PUT requests can cost more than the storage itself, since you pay per request. Group small objects together where you can.

Serving media fast and safely

Storage is only half the job; the other half is getting bytes to viewers quickly without a huge bill or leaking private files. Each object store request takes tens of milliseconds and every GB sent out costs money, so the goal is to answer most requests from a CDN cache near the user, and let the bucket see only the first request for each file.

🌍

Always put a CDN in front

Make the bucket the CDN's origin (the source it fetches from), and block public access to the bucket itself, so everything must go through the CDN. The CDN keeps copies near users, soaks up traffic spikes, supports range requests so video players can jump to the middle of a file, and cuts your egress bill.

🏷️

Immutable, content-addressed keys

Name each object after a fingerprint of its content, or a version number: img/9b2cf5…jpg. Then the content at a key can never change, so you can safely say Cache-Control: max-age=31536000, immutable. “Updating” an avatar means writing a new key and pointing the database row at it. You never have to clear the CDN's cache.

🖼️

Resize on the fly

Instead of making 12 thumbnail sizes up front, an image service near the user resizes on request (/img/9b2c.jpg?w=320&fmt=webp), and the CDN caches each version. Only pre-make the few sizes you use most.

🔏

Private content

For paid or personal files, give out signed CDN URLs or signed cookies: links that expire soon and only work for one path. Your API decides who is allowed what. The CDN just checks the signature, so it stays fast.

Object storage as a data lake

Object storage has quietly become the base for analytics too. Instead of loading everything into an expensive data warehouse, companies drop raw and processed data into buckets as column-based files (files that store each column together), and run queries directly against them.

Why column-based files help: a table of 1 billion events with 50 columns might be 1 TB. A query like "count events per country yesterday" needs just 2 of those columns. Stored row by row, the engine reads the whole 1 TB. Stored column by column, it reads only those two columns — perhaps 20–40 GB before compression — and the date folders (dt=…) let it skip every other day's files entirely.

Raw zone bronze

Events, logs and database exports land exactly as they are (JSON, CSV, Avro), organised into folders by date: s3://lake/events/dt=2026-09-17/hour=14/.

Cleaned zone silver

Scheduled or continuous jobs (Chapter 18) remove duplicates, fix the field names and types, and convert everything to Parquet: compressed files that store data column by column, so a query only reads the columns it actually needs.

Curated zone gold

Summary tables in business terms, ready for dashboards and for feeding machine-learning models.

Table formats add database powers lakehouse

Apache Iceberg, Delta Lake and Hudi keep a log of exactly which files make up a table at any moment. That gives you all-or-nothing commits, the ability to change a table's columns safely, and “time travel” to query the table as it was last Tuesday — all on top of plain objects. Query engines like Spark, Trino, Snowflake and DuckDB read them directly.

⚠️
Common mistakes
  • Sending uploads through your API. Your servers become the bandwidth bottleneck and hold gigabytes in memory. Sign a URL and let clients talk to storage directly.
  • Millions of tiny objects. The per-request cost and slow listing start to dominate. Group small items into bigger objects, or use a database instead.
  • Forgetting about egress. Serving media straight from a bucket to users is the most expensive way to do it. Put a CDN in front.

Interview drill

Design: Users upload 2 GB videos from phones on flaky networks. Design the upload path.

How a strong answer sounds
The client asks your API to start an upload. The API checks the user is allowed, saves a PENDING row, and returns presigned URLs for each part. The client uploads the parts at the same time, retrying only the ones that fail, and after a dropped connection it asks which parts already arrived and continues from there. When it's done, the client — or an ObjectCreated event from storage — tells the API, which checks the size and checksum, marks the record READY, and starts processing. A lifecycle rule deletes abandoned part-uploads after a day.

Trade-off: Replication or erasure coding for a photo service?

How a strong answer sounds
Use both, depending on the age of the data. New uploads get 3 full copies, for fast writes, fast reads and easy repair. Once an object cools off (after hours or days), a background job converts it to erasure coding. RS(10,4) survives just as many failures while storing 1.4× instead of 3×, at the cost of more CPU and slower repairs. Thumbnails stay copied, because they're small and constantly read.

🧠 Key takeaways

  • Use block storage for databases and virtual machines, file storage when many machines need a shared filesystem, and object storage for everything big, binary and written once.
  • Keep the files themselves in object storage, and only their keys and metadata in your database.
  • An object store has two halves: a metadata layer that is always exactly up to date, and a huge fleet of storage nodes spread across availability zones.
  • Presigned URLs let clients upload and download straight from storage, so the bytes never pass through your app servers.
  • Multipart uploads send parts at the same time and retry only the failed ones. They're essential for large files on unreliable networks.
  • Replication is simple and fast. Erasure coding survives just as many failures using far less storage.
  • Lifecycle rules and storage tiers cut costs a lot — but watch the fees for reading data back and for sending it out.
  • Serve media through a CDN, using keys that never change their content, and signed URLs for private files.

Check your understanding

Your social app stores profile photos as BLOB columns in Postgres. Backups now take 9 hours. What's the best fix?

Images and other binary files belong in object storage. The database then stays small, quick to back up and copy, and the photos can be served through a CDN.

Why do presigned URLs improve an upload flow?

Your API still decides who is allowed to upload, and signs a narrow permission that expires quickly. But the heavy data transfer never touches your servers.

An RS(10,4) erasure-coded object has fragments on 14 nodes. How many node failures can it survive, and what's the storage overhead?

Any 10 of the 14 fragments can rebuild the data, so up to 4 may be lost. The disk space used is 14/10 = 1.4× the size of the data.

Compliance requires keeping audit logs for 7 years; they are almost never read after the first month. Best approach?

Archive tiers cost a small fraction of normal storage. Getting data back is slower and costs more, which is fine for records you almost never read.

Users update their avatar, but friends keep seeing the old one for hours. Avatars are served via a CDN from avatars/{userId}.jpg. Cleanest fix?

If each key's content never changes, you never have to clear the cache. A new avatar means a new URL, which no cache has yet, and the old URLs can be kept forever.
