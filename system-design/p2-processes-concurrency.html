Processes, Threads & Concurrency

A popular website answers thousands of requests every second, and a single server handles hundreds of them at the same moment. How can one machine do many things at once? This chapter explains the operating system's two basic units of work — processes and threads — and the tricks servers use to stay busy while they wait. You'll also meet the classic bug that appears when two workers touch the same data: the race condition.

Why one server must do many things at once

Picture a web server answering one request. It spends about 5 ms of CPU time figuring out what to do, then asks the database for data and waits 50 ms for the answer, then spends 5 ms building the response. Total: 60 ms, of which the CPU was busy for only 10 ms.

If the server handled requests strictly one after another, it could answer only about 16 requests per second (1,000 ms ÷ 60 ms), and its CPU would sit idle five-sixths of the time. Meanwhile a queue of users would pile up. That's absurdly wasteful for a machine that could do billions of operations per second.

The fix is to work on other requests while one is waiting. That is the core idea of this chapter, and it's how every real server works. The operating system gives you two building blocks for it — processes and threads — and there's a third, popular technique called the event loop.

🍳
Analogy: one cook, many dishes

A cook who puts pasta on to boil doesn't stand staring at the pot for ten minutes. They chop vegetables for the next dish, then stir a sauce, then come back when the timer rings. The cook is one person, but many dishes are in progress. A server does the same with requests: while one waits for the database, it works on another.

Programs, processes and threads

These three words get mixed up constantly. They mean different things:

📄

Program

A file on disk containing instructions, like shop-app or postgres. It does nothing by itself — it's a recipe, not a meal.

📦

Process

A running copy of a program. The OS loads the program into RAM, gives it its own private memory and an ID number (the PID), and starts it. You can run the same program as several processes.

🧵

Thread

A single line of execution inside a process. Every process starts with one thread and can create more. Threads in the same process share its memory.

Processes: isolated and sturdy

The OS keeps each process's memory separate. Process A cannot read or overwrite process B's memory, even by accident. This isolation is valuable: if one process crashes, the others carry on. Your browser uses it — each tab often runs in its own process, so one broken page doesn't take down the whole browser.

The price is cost and distance. Starting a process takes milliseconds and a fair amount of memory. And since processes don't share memory, they must talk through the OS: pipes, files, or network connections. That's slower and more work than simply reading a shared variable.

Threads: cheap and sharing

Threads inside one process all see the same memory. One thread can put a result into a variable, and another can read it immediately. Creating a thread is much cheaper than creating a process. Each thread only needs its own small stack — the memory that tracks which function it's in and its local variables — typically from a few hundred KB to a few MB.

Sharing is both the power and the danger of threads. If two threads change the same data at the same moment, they can corrupt it. And a crash in one thread usually kills the whole process, taking every other thread with it.

📦 Process

Own memory · strong isolation · a crash stays contained · slower to start (ms) · talks to others through the OS. Example: each worker of a Python web server, a database server, a browser tab.

🧵 Thread

Shared memory · cheap to start (µs) · easy to share data · must guard shared data with locks · one crash can kill all. Example: the request handlers inside a Java web server.

Concurrency vs parallelism

These two words sound the same but describe different things. Getting them straight makes the rest of the chapter easy.

🤹 Concurrency — juggling

Several tasks are in progress over the same period of time, but not necessarily running at the same instant. One core can be concurrent: it switches between tasks thousands of times per second, so each makes progress. Concurrency is about structure: dealing with many things at once.

🙌 Parallelism — many hands

Several tasks literally run at the same instant, on different cores. You need more than one core for this. Parallelism is about execution: doing many things at once to finish faster.

A server needs both. Concurrency lets it keep hundreds of requests in progress while most of them wait on I/O (input/output: disk reads, network calls). Parallelism lets it use all 32 of its cores for the parts that actually compute.

💡
How the OS fakes “at the same time” on one core

The OS scheduler gives each runnable thread a short time slice — a few milliseconds — then pauses it and runs another. Switching from one thread to another is called a context switch: the OS saves the first thread's position and registers, then loads the next one's. Each switch costs a few microseconds. That's cheap once, but with thousands of busy threads the switching itself can eat a noticeable share of the CPU.

Three lessons from the simulator:

  • Waiting dominates. With one worker, the CPU is idle most of the time, and the last request waits for all the others.
  • More threads help — up to a point. Each extra thread lets one more request wait in parallel. But threads cost memory and context switches, so pools are usually sized in the tens or hundreds, not tens of thousands.
  • An event loop gets the same effect with one thread. It never blocks: while request 1 waits, it starts request 2. The CPU parts still run one at a time, but the waits all overlap.

Three ways servers handle many requests

Real server software uses one of these designs, or a mix. You don't need to build any of them, but you should know what each means when you read about a system.

Modern languages blur the lines. Go runs thousands of cheap “goroutines” on a few OS threads. Java now has virtual threads. Both let you write simple top-to-bottom code while the runtime does event-loop-style juggling underneath.

Blocking vs non-blocking code

A blocking call stops the thread until the result arrives. A non-blocking (asynchronous) call starts the work and lets the thread do something else; the result arrives later. Most modern languages use the words async and await for this. await means “pause this task until the result is ready, and let the loop run other tasks meanwhile”.

// Each request handler is async: while it awaits the database,
// the single event-loop thread serves other requests.
async function getProfile(req, res) {
  const user   = await db.query("SELECT * FROM users WHERE id = $1", [req.params.id]);
  const orders = await db.query("SELECT * FROM orders WHERE user_id = $1", [req.params.id]);
  res.json({ user, orders });
}

// Two independent calls? Start both, then wait for both: the waits overlap.
const [user, orders] = await Promise.all([getUser(id), getOrders(id)]);
import asyncio

async def fetch(name, seconds):
    await asyncio.sleep(seconds)      # stands in for a network call
    return name

async def main():
    # Three 1-second waits run concurrently: this takes ~1 s, not 3 s.
    results = await asyncio.gather(fetch("a", 1), fetch("b", 1), fetch("c", 1))
    print(results)                      # ['a', 'b', 'c']

asyncio.run(main())
🧊
The event loop's one rule: never block it

An event loop runs everything on one thread. If one handler does heavy CPU work — resizing an image, parsing a 200 MB file — for two seconds, every other request freezes for two seconds. Heavy work belongs on separate worker threads or processes, or in a background job queue (Chapter 14).

Race conditions: when sharing goes wrong

Here is the most famous concurrency bug. Two threads share a counter, say “number of likes”, which is 5. Both want to add one. Adding one looks like a single step in code (likes = likes + 1), but the CPU really does it in three: read the value, add one, write it back. If the two threads interleave badly, one update is lost:

A lost update, step by stepStep-through
  1. The shared counter holds 5. Two users click “like” at the same moment, so two threads each want to add one. The correct final answer is 7.
  2. Thread A reads the counter into its own local copy: 5.
  3. Before A writes anything back, the OS switches to Thread B. B also reads the counter: still 5.
  4. A adds one to its copy and writes 6.
  5. B adds one to its stale copy (5) and also writes 6. A's update has been overwritten. Two likes, but the counter only went up by one.
  6. The bug depends on exact timing, so it appears rarely and randomly — often only under heavy load in production, and almost never on a developer's laptop. That's why it's called a race condition: the result depends on who wins a race.

The fix: a lock

A lock (also called a mutex, for “mutual exclusion”) is a rule that only one thread at a time may run a certain piece of code — the critical section. A thread must acquire the lock before reading the counter and release it after writing. If another thread holds the lock, the newcomer waits. Now the read-add-write happens as one indivisible (atomic) step, and no update is lost.

Locks have costs: waiting and deadlock

Locks fix races, but they bring two new problems:

  • Contention. While one thread holds a lock, others wait. If a lock protects something every request needs, it turns your parallel server back into a one-at-a-time server. Keep critical sections short.
  • Deadlock. Thread A holds lock 1 and waits for lock 2. Thread B holds lock 2 and waits for lock 1. Neither can ever continue — the program freezes. The standard defence is to always acquire locks in the same order everywhere.

Exactly the same problems appear at the scale of whole systems. Two web servers updating the same database row can lose an update just like two threads. Databases solve it with transactions and row locks (P6, Chapter 7). Machines that must coordinate across a network use distributed locks and leases (Chapter 17). The vocabulary you've just learned carries straight over.

How many requests are in flight? Little's law

One simple formula connects load, speed and concurrency. It's called Little's law, and it holds for any stable system — a server, a coffee shop, a motorway:

🧮
Little's law

in flight = arrival rate × time each one spends inside

Written as L = λ × W. If 1,000 requests arrive per second and each takes 0.2 seconds, then on average 1,000 × 0.2 = 200 requests are being handled at any moment.

This tells you how much concurrency you need. Worked example: your service receives 500 requests per second, and each spends 120 ms (0.12 s) waiting on a database. Then 500 × 0.12 = 60 requests are in progress at once. With a thread-per-request design you need at least 60 threads (more for bursts). With only 20 threads, requests would queue, and the queue would grow until users time out.

Little's law calculatorCalculator

Notice what happens when the database slows down: time per request doubles, so the number in flight doubles, and a pool that was big enough suddenly isn't. This is how one slow dependency can make a whole service fall over — a pattern Chapter 16 teaches you to defend against with timeouts and circuit breakers.

⚠️
Common mistakes
  • Mixing up concurrency and parallelism. One core can be highly concurrent. Parallelism needs several cores.
  • Assuming x = x + 1 is safe with threads. It's three steps. Without a lock or an atomic operation, updates get lost.
  • Doing heavy CPU work on an event loop. Everything else freezes until it finishes.
  • Making thread pools huge “to be safe”. Thousands of threads waste memory and time on context switches, and can overwhelm the database behind them.
  • Forgetting that a slow dependency multiplies concurrency. By Little's law, doubling latency doubles the requests in flight.
🎤
Interview drill

Explain it simply: Why can a single-threaded server like Node.js or Redis handle thousands of connections at once?

How a strong answer sounds
Because most of a connection's life is spent waiting — for the network, for disk, for another service. An event loop never blocks on those waits: it starts the I/O, moves on to other connections, and comes back when the OS says the data is ready. So thousands of connections can be in progress while the one thread only does the short bursts of real work. The catch is that any long CPU task blocks everyone, so that work must be kept small or moved elsewhere.

Estimate: A service gets 2,000 requests per second at peak. Each request takes 50 ms. How many requests are in flight, and is a pool of 64 threads enough?

How a strong answer sounds
By Little's law, 2,000 × 0.05 = 100 requests in flight on average. A pool of 64 is too small: requests would queue, and the queue grows until timeouts. I'd size it for the average plus headroom for bursts — say 150–200 — or spread the load across several instances, and check that the database can take that many concurrent queries.

🧠 Key takeaways

  • A program is a file; a process is a running copy with its own memory; threads run inside a process and share its memory.
  • Concurrency means many tasks in progress; parallelism means many tasks running at the same instant on different cores.
  • Servers spend most of each request waiting on I/O, so they must keep many requests in flight to use the CPU well.
  • Three designs: process per worker (isolated, heavy), thread pool (simple, needs locks), event loop (light, must never block).
  • Unprotected shared updates cause race conditions and lost updates. Locks fix them but add contention and the risk of deadlock.
  • Little's law: requests in flight = arrival rate × time per request. Slower dependencies mean more in flight.

Check your understanding

What is the key difference between two threads and two processes?

Threads live inside a process and share its memory, which makes sharing data easy but dangerous. Processes are isolated from each other, so they are safer but must communicate through the OS. Threads can run on many cores in parallel, and they are cheaper to start than processes.

A one-core machine runs a server that juggles 300 open requests, switching between them as each one waits. This is an example of…

Many requests are in progress at once, which is concurrency. But with one core, only one instruction stream runs at any instant, so there is no parallelism.

Two threads each run count = count + 1 once, starting from 10, with no lock. What final values are possible?

If the steps don't overlap, you get 12. If both read 10 before either writes, both write 11 and one update is lost. At least one write always happens, so 10 is impossible. That uncertainty is exactly what a lock removes.

A Node.js server suddenly stops responding to everyone for 3 seconds whenever one user uploads a large spreadsheet for parsing. What is the most likely cause?

An event loop handles many connections only because each piece of work is short. A long CPU task keeps the one thread busy, so nothing else runs. The fix is to move the parsing to a worker thread, another process, or a background job.

A service handles 400 requests per second, and each request takes 250 ms. By Little's law, about how many requests are in flight?

In flight = rate × time = 400 per second × 0.25 seconds = 100. Remember to convert milliseconds to seconds before multiplying.
