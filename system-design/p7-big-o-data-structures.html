Big-O & Everyday Data Structures

Every database, cache and message queue is built from a handful of classic data structures: arrays, hash tables, sorted trees, queues and logs. You don't need to implement them to design systems — but you do need to know what each one is fast and slow at, because that decides which component fits a job. This chapter teaches Big-O, the shorthand engineers use to describe how cost grows with size, and then tours the structures hiding inside every system you'll meet.

Why “how it grows” matters more than “how fast it is”

A piece of code that takes 1 ms on 1,000 items might take 1 second on a million items — or 17 minutes. Which one depends on how its work grows as the input grows. In system design the inputs grow enormously: from 100 test users to 100 million real ones. So the question is never just “is it fast?”, but “will it still be fast when the data is 1,000 times bigger?”

Engineers describe growth with Big-O notation. O(n), read “order n”, means “the work grows in proportion to the size of the input, n”. Big-O deliberately ignores constant factors and small details. It only captures the shape of the growth, because at large sizes the shape dominates everything else.

A 20-second logarithm refresher

log₂ n answers: “how many times can I halve n before I reach 1?” 8 → 4 → 2 → 1 is three halvings, so log₂ 8 = 3. Because 2¹⁰ = 1,024 ≈ a thousand, every factor of 1,000 adds about 10: log₂ 1,000 ≈ 10, log₂ 1,000,000 ≈ 20, log₂ 1,000,000,000 ≈ 30. That's why O(log n) feels almost free even for billions of items.

🧪 Try n = 1,000,000. O(log n) is ~20 steps; O(n) is a hundredth of a second; O(n²) would take almost three hours. That's why “compare everything with everything” doesn't survive real data.

Two practical translations for system design. First: anything O(n) over all your data is a batch job, not a request. Scanning a billion rows takes minutes, so it can't happen while a user waits. Requests must use O(1) or O(log n) lookups. Second: at scale, the constant factors come back. An O(1) lookup that crosses a network (~0.5 ms) is slower than an O(log n) search in local RAM (~microseconds). Big-O tells you the shape; the speed ladder from P1 tells you the size of each step.

Arrays: items side by side

An array (or list) stores items one after another in a single block of memory. Because every slot is the same size, the computer can jump straight to item #500 by arithmetic: start address + 500 × item size. That makes reading by position O(1).

The weakness is changing the middle. To insert an item at the front of a million-item array, every other item must shift one place: O(n). Searching an unsorted array for a value also means checking each item: O(n). Arrays shine when you append to the end and read by position — and, because the data sits together, when you read it in order, which hardware loves.

Hash tables: find any key in one step

A hash table (called a dictionary, map or object in most languages) stores key–value pairs and finds any key in about one step, however many keys it holds. It's the most important data structure in system design: caches, sessions, key–value databases and many indexes are hash tables at heart.

The trick is a hash function: a function that turns any key into a number, always the same number for the same key, and spread evenly across the range. Take that number modulo the number of buckets (slots), and you know exactly which bucket the key lives in. No searching needed — you compute where to look. Two keys can land in the same bucket (a collision); the bucket then holds a short list, which stays short as long as there are enough buckets.

A hash table with 8 bucketsInteractive
Look up any key: the hash tells you the bucket directly, so you only ever check that one short list. The catch: keys are scattered by design, so a hash table can't answer “all keys between A and M” or “the 10 smallest” without checking everything.

Hash tables return in system design at a larger scale. To split data across 10 database machines, you can hash each key and take the result modulo 10 — each machine becomes a “bucket”. That's hash partitioning, and its weakness (almost every key moves when you change from 10 to 11 machines) leads to consistent hashing in Chapter 8.

Sorted structures: ranges and order

Hash tables are great for “find exactly this key”. But many questions are about order and ranges: “orders from last week”, “the 10 highest scores”, “users whose name starts with Mc”. For those you need data kept sorted.

Binary search

In a sorted list, you can find any value by looking at the middle, deciding which half it must be in, and repeating. Each look halves what's left, so a million items take about 20 looks: O(log n). And once you've found where a range starts, the rest of the range is right next to it, in order.

Balanced trees and B-trees

A sorted array is slow to insert into (everything shifts). A balanced search tree keeps data sorted while allowing O(log n) inserts and deletes too. Each node holds keys and points to child nodes holding smaller and larger keys.

Databases use a special version called the B-tree, designed for disks. Instead of two children per node, each node has hundreds — enough keys to fill one disk page (often 8–16 KB). This huge fan-out makes the tree very shallow. Worked example: with 500 children per node, three levels reach 500³ = 125 million rows, and four levels reach 500⁴ ≈ 62 billion. So finding any row among billions takes about 4 page reads, and the top levels are usually cached in RAM, leaving just one or two real disk reads. That is why a database index lookup is fast even on enormous tables.

🌳
Where you'll meet sorted structures

Almost every relational database index is a B-tree (Chapter 7). Sorted sets in Redis power leaderboards. Many NoSQL stores keep data sorted on disk in LSM trees, which combine the append-only log below with periodic sorting. Autocomplete uses a trie, a tree keyed by letters (Chapter 31).

Queues and stacks: order of arrival

Some structures care only about the order items arrived in:

🚶 Queue — first in, first out (FIFO)

Like a line at a shop: new items join the back, work is taken from the front. Adding and removing are both O(1). Systems use queues everywhere work arrives faster than it can be done: incoming requests waiting for a thread, emails waiting to be sent, video waiting to be transcoded. A message queue (Chapter 14) is a queue shared between machines.

🥞 Stack — last in, first out (LIFO)

Like a pile of plates: you add and remove at the top. Also O(1). Programs use a stack to track function calls (the call stack from P2), and browsers use one for the back button.

The queue absorbs bursts: jobs wait instead of being rejected, and the worker drains them at its own pace. If jobs keep arriving faster than workers finish them, though, the queue grows without limit — the signal to add workers or slow the senders (called backpressure).

Logs: append-only and in order

A log in the data-structure sense is the simplest structure of all: a sequence of records that you only ever add to the end. You never change or delete old entries in place. Each record gets the next position number (its offset).

That sounds limiting, but it has remarkable properties:

  • Writes are fast. Appending is sequential disk access — the fastest kind (P1).
  • Crash-safe. A half-written record at the end is easy to detect and discard; nothing earlier was touched.
  • Replayable. Anyone can read from any offset and see events in the exact order they happened. A reader that falls behind simply remembers its offset and catches up.

Logs are everywhere once you look. Databases write every change to a write-ahead log before touching their tables, so they can recover after a crash (Chapter 7). Database replicas copy the leader by replaying its log (Chapter 8). And Kafka is, at heart, a distributed, replicated log that many services read at their own pace (Chapter 14).

⚠️
Common mistakes
  • Ignoring growth. “It's fast on my test data” says nothing about O(n²) code on real data.
  • Using a hash-based store for range queries. “All events between 2 pm and 3 pm” needs data sorted by time.
  • Putting O(n) work in a request path. Scanning everything belongs in a background job, not while a user waits.
  • Letting a queue grow without limit. A queue hides overload until memory runs out or delays reach hours. Watch its length.
  • Forgetting constant factors at scale. An O(1) network call can still be slower than an O(log n) lookup in local memory.

Interview drill

Choose: You need (a) a user's session by session ID, (b) a game's top 100 scores, updated constantly, (c) every order placed yesterday. Which structure fits each?

How a strong answer sounds
(a) A hash table / key–value store: exact-key lookup in O(1), no ordering needed — Redis or a similar cache. (b) A sorted structure that keeps scores in order as they change — a sorted set (skip list or balanced tree) with O(log n) updates, or a heap if we only ever need the top-K. (c) An index sorted by order date — a B-tree on created_at — so the database can jump to yesterday's start and read the range in order.

Explain it simply: Why can a database find one row among a billion in just a few disk reads?

How a strong answer sounds
Because the index is a B-tree with a huge fan-out — hundreds of children per node. Each level narrows the search by a factor of hundreds, so a billion rows need only about four levels. The top levels are small and stay cached in memory, so a lookup usually costs one or two actual disk reads.

🧠 Key takeaways

  • Big-O describes how work grows with input size. From best to worst: O(1), O(log n), O(n), O(n log n), O(n²).
  • log₂ of a million is about 20 and of a billion about 30, so O(log n) is nearly free; O(n²) is hopeless at scale.
  • Arrays: O(1) by position, slow inserts in the middle, great for in-order reading.
  • Hash tables: O(1) average lookup by exact key, but no order and no ranges. They power caches and key–value stores.
  • Sorted trees, especially wide B-trees, give O(log n) lookups plus range queries — the basis of database indexes.
  • Queues (FIFO) absorb bursts of work; stacks (LIFO) track nested calls.
  • Append-only logs give fast, crash-safe, replayable writes and underpin write-ahead logs, replication and Kafka.

Check your understanding

About how many steps does binary search need to find an item in a sorted list of 1,000,000 items?

Each step halves the list, so the count is log₂ 1,000,000 ≈ 20 (because 2²⁰ ≈ 1,048,576). A linear scan would need 500,000 checks on average.

Which question is a hash table bad at answering?

A hash function deliberately scatters keys, so neighbouring keys end up in unrelated buckets. Exact lookups, existence checks and deletes are O(1); range and ordered queries need a sorted structure.

A function compares every pair of items in a list. The list grows from 1,000 to 100,000 items. How much more work does it do?

Comparing every pair is O(n²). The input grew 100×, so the work grows 100² = 10,000×. Code that took 0.1 seconds now takes about 17 minutes.

Why do database indexes use B-trees with hundreds of children per node rather than simple two-child trees?

Each level of the tree typically costs one page read. With 500 children per node, four levels cover billions of rows; a two-child tree would need about 30 levels for a billion rows, meaning many more reads.

Which property makes an append-only log a good foundation for replication and crash recovery?

Because nothing is ever changed in place, the log is an exact, ordered history. A replica or a recovering database just replays from the last offset it processed. Appending is also sequential, so it's fast.
