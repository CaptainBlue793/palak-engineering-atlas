Design a Web Crawler

Search engines, SEO tools, price trackers, archives and LLM training pipelines all start the same way: download a huge fraction of the web and keep it fresh. The algorithm is a breadth-first search anyone can write in 20 lines. Doing it for billions of pages — without hammering small websites, drowning in duplicates, or falling into infinite link traps — is a real distributed system.

  • Scope and estimate a billion-page crawl
  • Design the URL frontier with priority and politeness
  • Deduplicate URLs with Bloom filters and content with SimHash
  • Distribute crawling across many machines by host
  • Handle robots.txt, DNS, spider traps and JavaScript pages
  • Schedule recrawls to keep content fresh

STEP 3 / 6

High-level design

The crawl loopStep-through
  1. The crawl starts from a list of high-quality seed URLs (popular domains, sitemaps). They go into the URL frontier — the data structure that decides what to crawl next.
  2. A fetcher takes a URL whose host is allowed to be hit now. It checks the host's cached robots.txt, resolves DNS through a local cache (DNS is a notorious bottleneck at crawl scale) and downloads with timeouts and a size cap.
  3. Responses are appended to large WARC archive files (many pages per object) in object storage — never millions of tiny objects (Chapter 9). Metadata goes to a table: URL, status, fetch time, content hash.
  4. The parser extracts text and links. A SimHash of the content detects near-duplicate pages (mirrors, tracking-parameter variants, boilerplate-heavy pages) so we don't store or process them repeatedly.
  5. Links are resolved to absolute URLs and normalized: lowercase host, remove fragments, sort query parameters, strip session IDs and utm_*. Filters drop blocked domains, unwanted file types and suspiciously deep paths.
  6. A Bloom filter (Chapter 20) answers “definitely new” for most URLs in microseconds using ~10 bits per URL — ~60 GB for 50B URLs instead of terabytes. “Maybe seen” results are rare false positives we can afford to skip.
  7. New URLs are scored and added to the frontier, closing the loop. Parsed documents are published to Kafka for indexers and ML pipelines.
STEP 4 / 6

Deep dive: the URL frontier

The frontier has two jobs that pull in opposite directions: crawl important pages first (priority) and never overload any single host (politeness). The classic Mercator design uses two layers of queues:

⬆️ Front queues: priority

A prioritizer scores each URL (PageRank-like authority, change frequency, freshness need) and routes it into one of F priority queues. A selector pulls from higher-priority queues more often.

🚦 Back queues: politeness

Each back queue holds URLs for exactly one host. A min-heap stores (next_allowed_time, host). A worker pops the host whose time has come, fetches one URL, and pushes the host back with now + crawl_delay — so each host sees at most one connection at a time, spaced out.

🌐
Distributing the crawl

Partition by host, not by URL: crawler_node = consistent_hash(host) (Chapter 8). All URLs of one host land on one node, so politeness state (heap entry, robots.txt, DNS, connection pool) stays local and no cross-node coordination is needed. Links to other hosts are forwarded to the owning node. Nodes can also be placed near the regions they crawl.

Deep dive: duplicates everywhere

Roughly 30% of the web is duplicate or near-duplicate content: mirrors, printer-friendly versions, URLs differing only in tracking parameters, pages with identical content but a changing timestamp or ad. Exact hashes (MD5 of the page) only catch byte-identical copies. SimHash produces fingerprints where similar documents differ in only a few bits.

STEP 5 / 6

Deep dive: the hostile, messy web

🕸️

Spider traps

Infinite calendars (/calendar?month=2026-10, then 11, 12…), session IDs in URLs, and generated link loops create endless unique URLs. Defences: max URL length and path depth, per-host page budgets, detecting repeating path segments, and prioritizing by link authority so trap pages sink.

🤖

robots.txt

Fetch per host, cache for ~24h, and honour Disallow and Crawl-delay. Identify your crawler with a clear User-Agent and contact URL, and respond quickly to site-owner complaints.

📖

DNS bottleneck

Hundreds of lookups per second overwhelm public resolvers and add latency. Run local caching resolvers, cache per host, and resolve asynchronously ahead of fetching.

⚛️

JavaScript-rendered pages

Many sites render content client-side. Rendering in a headless browser costs ~10–100× a plain fetch, so do it in a separate, smaller pool only for pages whose HTML looks empty or for high-value domains.

⏳

Slow and malicious servers

Strict connect/read timeouts, maximum body size, streaming parsers, and sandboxed parsing processes. A single tar-pit server holding connections open must not tie up the fleet.

💾

Crash recovery

The frontier can hold billions of URLs — keep most of it on disk (or in Kafka/RocksDB) with only the heads of queues in memory, and checkpoint so a node restart resumes rather than starting over.

Deep dive: freshness & recrawling

A crawl is never done. News homepages change every minute; a 2009 blog post never changes. Crawling everything at the same interval wastes most of the budget.

Estimate each page's change rate

Compare content hashes between visits. If a page changed on 4 of the last 5 visits, visit more often; if not in 10 visits, back off exponentially.

Weight by importance

A stale popular page hurts users more than a stale obscure one. Recrawl priority ≈ importance × probability it changed since last visit.

Use cheap signals

Conditional requests (If-Modified-Since, ETag → 304 Not Modified) save bandwidth; sitemaps with lastmod, RSS feeds and push protocols like IndexNow tell you what changed.

⚠️
Common mistakes
  • Ignoring politeness. Hammering one host gets your IPs blocked and hurts a real site — the frontier must rate-limit per host, not globally.
  • Storing millions of tiny files. Batch pages into WARC-style archives; object stores hate 200 KB objects at billions of scale.
  • Crawling without budgets. Traps generate infinite unique URLs; cap pages per host and path depth.
🎤
Interview drill

Design: How do you distribute crawling across 200 machines without coordination on every URL?

How a strong answer sounds
Partition by host with consistent hashing: node = hash(host). All URLs for a host land on the node that owns it, so its politeness state — next-allowed time, robots.txt, DNS, connection pool — is local and needs no locks. Discovered links to other hosts are forwarded to the owning node over a queue. Adding or removing nodes moves ~1/N of hosts, and the frontier is persisted so a node restart resumes rather than re-crawls.

Reason: Your crawler fetched 40% fewer pages today with no config change. What do you check?

How a strong answer sounds
In order: DNS resolution failures or latency (a classic silent bottleneck), robots.txt changes or blocks from big hosts, frontier starvation (politeness delays dominating because the queue is skewed toward a few hosts), a rise in slow/timeout hosts occupying workers, and dedupe false positives from a Bloom filter that's now over capacity. Per-host metrics and worker-idle time tell you which one it is quickly.

🧠 Key takeaways

  • Crawling is BFS over the web; the hard parts are politeness, prioritization, dedupe and robustness at scale.
  • The frontier combines priority queues with per-host queues and a heap of next-allowed fetch times.
  • Partition crawler nodes by host so politeness state is local and coordination-free.
  • Normalize URLs, then use a Bloom filter to check tens of billions of seen URLs in little memory.
  • SimHash detects near-duplicate content where exact hashes fail.
  • Defend against spider traps, slow servers and JS-heavy pages; cache robots.txt and DNS.
  • Recrawl adaptively by change rate and importance, using conditional requests to save bandwidth.

Check your understanding

Why are crawler nodes partitioned by host rather than by full URL hash?

If a host's URLs were spread across nodes, they'd all hit it concurrently and would need a global rate limiter.

A Bloom filter says a newly discovered URL was “probably seen” but it actually wasn't. Consequence?

Bloom filter false positives make us miss a small fraction of pages, a good trade for huge memory savings.

Two pages are identical except for a “last updated” timestamp. Which technique flags them as duplicates?

Exact hashes change with any byte; SimHash fingerprints of near-identical text differ in only a few bits.

Your crawler finds /events?date=2026-09-18, then date=2026-09-19, and so on forever. What is this and a good defence?

Traps generate infinite unique URLs. Budgets and pattern detection bound the damage.

How should recrawl frequency be chosen?

Adaptive scheduling spends the crawl budget where content actually changes and matters.
