Design a Web Crawler

Search engines, SEO tools, price trackers, archives and LLM training pipelines all start the same way. They download a huge part of the web and keep it up to date. The basic algorithm is a breadth-first search (visit a page, queue its links, repeat) that anyone can write in 20 lines. Doing it for billions of pages is a real distributed system. You must not overload small websites, drown in duplicates, or fall into endless link traps.

  • Decide what a billion-page crawl must do and estimate its size
  • Design the URL frontier (the to-do list of pages) with priority and politeness
  • Spot repeated URLs with Bloom filters and repeated content with SimHash
  • Split crawling across many machines by website (host)
  • Handle robots.txt, DNS, spider traps and JavaScript pages
  • Schedule recrawls to keep content fresh

STEP 1 / 6

Requirements

The unusual thing about a crawler is who it has to be careful with. Most systems protect themselves from their users. A crawler must also protect other people's websites from itself: a small blog on a cheap server can be knocked offline by a crawler that sends it 50 requests a second. That's why politeness is a requirement here, not a nice-to-have — break it and site owners block you, which also ruins your crawl.

🛠️ Functional

✓Start from seed URLs, follow links, download HTML pages
✓Store raw pages for later steps, like search indexing or ML training
✓Recrawl pages periodically to keep them fresh
✓Out of scope: ranking and serving search results

📏 Non-functional

✓Scale: 1 billion pages per month
✓Politeness: obey robots.txt (the site's rules for crawlers); never overload a site
✓Robust: survive broken HTML, slow servers, traps and crashes
✓Extensible: add new content types (PDF, images) later

400 fetches per second sounds small. But each fetch can take seconds (slow servers, big pages), so we need thousands of connections open at once. We must also remember tens of billions of URLs we've already seen. Stored as a normal hash set, that doesn't fit comfortably in memory.

The working: 1B pages ÷ (30 × 86,400 s ≈ 2.6M s) ≈ 385 pages/s, call it 400, and ~800/s at peak. Storage: 1B × 100 KB = 100 TB a month; HTML compresses well (often around 4×), so about 25 TB. Links: ~50 per page × 1B pages = 50B URLs found, though many point to the same pages.

Why thousands of open connections? Use the rule “items in flight = rate × time each one takes” (Little's law, Chapter 4). If fetches average 2 seconds, 400/s × 2 s = 800 downloads in progress at once; at peak with slow sites taking 5–10 seconds, several thousand. That's why fetchers use asynchronous I/O — one process juggling thousands of sockets — rather than one thread per download.

And the seen-URL set: 50B URLs at ~40 bytes each (after compression) is ~2 TB; a hash set adds pointers and spare room on top. A Bloom filter at ~10 bits per URL needs 50B × 10 bits = 500 billion bits ≈ 62 GB — small enough to split across the memory of a few machines.

STEP 3 / 6

High-level design

At heart, this is the 20-line breadth-first search: take a URL from a to-do list, download it, find its links, add the new ones to the list. Each box in the diagram is one line of that loop, made big enough and careful enough to run on billions of pages. Step through it and notice where each problem from the estimates — politeness, the seen-URL set, storage — gets its own component.

The crawl loopStep-through
  1. The crawl starts from a list of good starting URLs, called seeds (popular domains, sitemaps). They go into the URL frontier: the data structure that decides what to crawl next.
  2. A fetcher takes a URL whose site may be visited right now. It checks the site's robots.txt (kept in a cache). It looks up the IP address through a local DNS cache, because DNS is a well-known bottleneck at this scale. Then it downloads the page, with timeouts and a size limit.
  3. Pages are added to large WARC archive files in object storage, many pages per file. Never store millions of tiny objects (Chapter 9). Details about each page go in a table: URL, status, fetch time, content hash.
  4. The parser pulls out the text and links. A SimHash (a fingerprint where similar pages get similar values) spots near-copies. Examples: mirror sites, the same page with different tracking parameters, or pages that are mostly the same template. So we don't store or process them again and again.
  5. Links are turned into full URLs and normalized (rewritten into one standard form): lowercase the host, remove the “#…” fragment, sort query parameters, and strip session IDs and utm_* tracking tags. Filters drop blocked domains, unwanted file types and suspiciously deep paths.
  6. A Bloom filter (Chapter 20) is a compact structure that can say “definitely new” or “maybe seen”. It answers in microseconds and uses ~10 bits per URL: ~60 GB for 50B URLs instead of terabytes. Now and then it says “maybe seen” for a URL that is actually new (a false positive). That's rare, so we can afford to skip those.
  7. New URLs get a priority score and go into the frontier, closing the loop. Parsed pages are sent to Kafka for search indexers and ML pipelines.

Why normalize before the “seen?” check? Because the web writes the same page many ways. HTTP://Example.com/a?b=2&a=1#top and http://example.com/a?a=1&b=2 are the same page. Without normalization, each spelling would pass the seen-check as “new” and we'd download the page again. With it, both become one string and the second is caught.

Why is a Bloom filter false positive acceptable here, when it wouldn't be for, say, a bank? The cost is small and bounded: we skip a page we haven't seen. At 10 bits per URL the false-positive rate is about 1%, and most pages are linked from many places, so a page skipped via one link is usually found through another. Missing 1% of new pages is a fair price for using 62 GB instead of several TB.

STEP 4 / 6

Deep dive: the URL frontier

The frontier has two jobs that pull in opposite directions. It must crawl important pages first (priority). And it must never overload any single site (politeness). The classic Mercator design solves this with two layers of queues:

Why do they pull against each other? Important pages cluster on a few big sites. If you only followed priority, you'd send all your workers to wikipedia.org at once. If you only followed politeness, you'd crawl sites in a fair rotation and waste time on junk. Two layers let each rule do its job: the front layer decides which URLs are worth fetching soon, and the back layer decides when each site may be visited.

⬆️ Front queues: priority

A prioritizer scores each URL. It looks at how trusted the page is (like PageRank), how often it changes, and how fresh it needs to be. It puts the URL into one of F priority queues. A selector takes from higher-priority queues more often.

🚦 Back queues: politeness

Each back queue holds URLs for exactly one host. A min-heap (a structure that always gives you the smallest item first) stores (next_allowed_time, host). A worker takes the host whose turn has come and fetches one URL. Then it puts the host back with now + crawl_delay. So each site gets at most one connection at a time, spaced out. Like a doctor's waiting room where each patient has an appointment time.

A short trace with a 2-second crawl delay per host. The heap holds (0s, a.com), (0s, b.org), (1s, c.net). At t = 0, a worker pops a.com, fetches one URL and pushes back (2s, a.com). Another worker pops b.org and pushes (2s, b.org). At t = 1 the top is c.net, which is fetched and pushed back as (3s, c.net). At t = 2, a.com's turn comes round again. Each host sees one request every 2 seconds, while the workers stay busy across different hosts. The rule of thumb: keep many more hosts than workers in the heap — often around three times as many — so a worker almost always finds a host whose turn has come.

🌐
Distributing the crawl

Split the work by host, not by URL: crawler_node = consistent_hash(host) (Chapter 8). All URLs of one site land on one machine. So everything needed for politeness (heap entry, robots.txt, DNS, open connections) stays on that machine, and machines don't need to coordinate. Links to other sites are forwarded to the machine that owns them. Machines can also sit near the regions they crawl.

Deep dive: duplicates everywhere

Roughly 30% of the web is duplicate or near-duplicate content. Think mirror sites, printer-friendly versions, URLs that differ only in tracking parameters, and pages that are identical except for a timestamp or an ad.

An exact hash (like MD5 of the page) only catches copies that match byte for byte. Change one character and the hash is totally different. SimHash is different: similar documents get fingerprints that differ in only a few bits.

Why use both? The exact hash is cheap and certain: if two pages have the same MD5, they are byte-for-byte the same, so store one. SimHash catches the rest — the copies with a different date, ad or footer. Comparing a new SimHash against billions of stored ones would be slow if done one by one, so real systems split each 64-bit fingerprint into blocks and index them: if two fingerprints differ in at most 3 bits, then out of 4 blocks of 16 bits, at least one block must match exactly, so you only compare against pages that share a block.

How it works: split the text into overlapping three-word pieces (“shingles”) and hash each one to 32 bits. For every bit position, add +1 if the bit is 1 and −1 if it's 0. If a position's total is positive, that fingerprint bit is 1; otherwise 0. A small edit changes only a few shingles, so only a few totals flip. The Hamming distance is the number of bits that differ. Google used 64-bit SimHash and treated pages within 3 bits as duplicates.

STEP 5 / 6

Deep dive: the hostile, messy web

The design so far assumes websites behave. Many don't — some by accident (broken HTML, endless calendars), a few on purpose (servers built to trap crawlers). Each card is a failure mode that will happen within the first day of a large crawl, and the defence for it.

🕸️

Spider traps

Endless calendars (/calendar?month=2026-10, then 11, 12…), session IDs in URLs and auto-generated link loops create an unlimited supply of new URLs. Defences: a max URL length and path depth, a page budget per site, detecting path segments that repeat, and ranking by how trusted the linking pages are, so trap pages sink to the bottom.

🤖

robots.txt

Fetch it once per site, cache it for ~24h, and obey Disallow and Crawl-delay. Name your crawler clearly in the User-Agent, with a contact URL. Respond quickly when site owners complain.

📖

DNS bottleneck

Hundreds of lookups per second overwhelm public DNS servers and add delay. Run your own local DNS servers with a cache, cache per site, and look up addresses in the background before you need them.

⚛️

JavaScript-rendered pages

Many sites build their content in the browser with JavaScript. Running a headless browser (a real browser with no screen) costs ~10–100× a plain fetch. So do it in a separate, smaller pool, and only for pages whose HTML looks empty or for high-value sites.

⏳

Slow and malicious servers

Use strict timeouts, a max page size, parsers that read as data streams in, and parsing in isolated (sandboxed) processes. A “tar pit” server, one that deliberately holds connections open, must not tie up all your workers.

💾

Crash recovery

The frontier can hold billions of URLs. Keep most of it on disk (or in Kafka/RocksDB), with only the front of each queue in memory. Save checkpoints, so a restarted machine picks up where it left off instead of starting over.

Deep dive: freshness & recrawling

A crawl is never finished. News homepages change every minute, while a 2009 blog post never changes. Recrawling everything at the same pace wastes most of your budget.

Put a number on the budget. At 1B fetches a month, if you already know 5B pages, you can revisit each only once every five months on average. So every recrawl spent on a page that didn't change is a fetch taken away from one that did. Worked example of the doubling rule: a page is checked after 1 day and hasn't changed, so wait 2 days; still the same, wait 4, then 8, up to a cap such as 60 days. The moment it changes, shrink the wait again (for example halve it). Pages settle at a revisit rate close to how often they really change.

Estimate each page's change rate

Compare content hashes between visits. If a page changed on 4 of the last 5 visits, visit more often. If it hasn't changed in 10 visits, keep doubling the wait between visits.

Weight by importance

An out-of-date popular page hurts users more than an out-of-date obscure one. Recrawl priority ≈ importance × chance it changed since the last visit.

Use cheap signals

Conditional requests ask “only send it if it changed” (If-Modified-Since, ETag → 304 Not Modified). That saves bandwidth. Sitemaps with lastmod, RSS feeds and push protocols like IndexNow tell you what changed.

Before the wrap-up, a few edge cases each component should handle:

  • Fetcher: redirects (follow a few, then stop, to avoid loops), 429 or 503 responses (slow down for that host — they are telling you it's too much), and pages that never finish sending (hard timeout and a size cap).
  • robots.txt: if it can't be fetched because of a server error, the safe choice is to not crawl the site until it can; if it simply doesn't exist (404), the site has set no rules.
  • Frontier node crash: its sites move to other nodes by consistent hashing, and the frontier is reloaded from its last checkpoint. A few URLs get fetched twice, which is harmless.
  • Bloom filter filling up: the false-positive rate rises as more URLs go in. Size it for the expected count with room to spare, and start a new, larger filter when it gets close.
⚠️
Common mistakes
  • Ignoring politeness. Hammering one site gets your IPs blocked and hurts a real business. The frontier must limit the rate per site, not just overall.
  • Storing millions of tiny files. Bundle pages into WARC-style archives. Object stores handle billions of 200 KB objects badly.
  • Crawling without budgets. Traps create endless new URLs. Cap pages per site and path depth.

Interview drill

Design: How do you distribute crawling across 200 machines without coordination on every URL?

How a strong answer sounds
Split by host with consistent hashing: node = hash(host). All URLs for a site land on the machine that owns it. So its politeness state (next allowed time, robots.txt, DNS, open connections) is local and needs no locks. Links found to other sites are forwarded to their owning machine through a queue. Adding or removing a machine moves only ~1/N of the sites. The frontier is saved to disk, so a restarted machine carries on instead of crawling again.

Reason: Your crawler fetched 40% fewer pages today with no config change. What do you check?

How a strong answer sounds
Check these in order:
  • DNS lookups failing or slow (a classic hidden bottleneck).
  • robots.txt changes, or big sites blocking you.
  • A starved frontier: the queue is mostly a few sites, so workers sit waiting on politeness delays.
  • More slow or timing-out sites tying up workers.
  • False positives from a Bloom filter that is now too full, so new URLs look “seen”.
Per-site metrics and worker idle time quickly show which one it is.

🧠 Key takeaways

  • Crawling is a breadth-first search over the web. The hard parts are politeness, priority, duplicates and staying robust at scale.
  • The frontier combines priority queues with one queue per site, plus a heap of “next allowed fetch” times.
  • Split crawler machines by site, so politeness state stays on one machine and needs no coordination.
  • Normalize URLs, then use a Bloom filter to check tens of billions of seen URLs using little memory.
  • SimHash detects near-duplicate content where exact hashes fail.
  • Defend against spider traps, slow servers and JavaScript-heavy pages. Cache robots.txt and DNS.
  • Recrawl based on how often a page changes and how important it is. Use conditional requests to save bandwidth.

Check your understanding

Why are crawler nodes partitioned by host rather than by full URL hash?

If one site's URLs were spread across machines, they'd all hit it at the same time. You'd then need a shared rate limiter across all machines.

A Bloom filter says a newly discovered URL was “probably seen” but it actually wasn't. Consequence?

Bloom filter false positives make us miss a small fraction of pages. That's a good trade for the huge memory savings.

Two pages are identical except for a “last updated” timestamp. Which technique flags them as duplicates?

An exact hash changes completely if any byte changes. SimHash fingerprints of nearly identical text differ in only a few bits.

Your crawler finds /events?date=2026-09-18, then date=2026-09-19, and so on forever. What is this and a good defence?

Traps create endless new URLs. Page budgets and spotting repeated patterns limit the damage.

How should recrawl frequency be chosen?

Adjusting per page spends the crawl budget where content really changes and matters.
