What is system design?

System design means deciding three things about a piece of software: which parts (components) it needs, how those parts connect, and how data moves between them. The goal is a system that has the right features and is fast, reliable and affordable.

Writing code answers a small question: “how do I build this function?”. System design answers bigger ones: “What happens when 10 million people use this at once? What if a server dies at 3am? Where does the data live?”

Here is why it matters, with numbers. Say a photo app has 1,000 users who each open it 10 times a day. That is 10,000 requests a day, or about one every 9 seconds. A laptop could serve that. Now say it has 10 million users doing the same. That is 100 million requests a day, about 1,160 per second on average and several times more at the evening peak. The code for “show my photos” is identical in both cases. What changes is everything around it: how many machines you need, where the photos are stored, and what happens when one of those machines breaks. That surrounding plan is the system design.

🍳
Analogy: from home kitchen to restaurant chain

Cooking dinner for yourself needs one person and one stove. Serving 500 guests a night needs more: a head chef, line cooks, a pantry, a queue of orders, and a plan for when the fryer breaks. Serving 5 million meals a day across 1,000 locations needs central warehouses, standard recipes and delivery trucks. The food is the same — the system around it is completely different. That's system design.

The golden rule

Don't design for 100 million users on day one. Good system design means solving today's problems while leaving room for tomorrow's. Building too much (over-engineering) wastes money and time, just like building too little does.

The client–server model

Nearly every system you'll design follows one basic pattern. A client asks for something. A server does the work and sends back an answer. That's it. Everything else is detail added on top.

💻

Client

Starts the conversation by sending a request. Browsers, mobile apps, smart TVs — or even another server calling an API (a set of URLs a program can call).

🖥️

Server

Waits for requests, runs the app's rules (the “business logic”), reads or saves data, and sends back a response.

📨

Request / Response

The conversation itself. Usually it uses HTTP, the web's main language: “GET /profile/42” → “200 OK + JSON data”.

Here is one full exchange, written out. The client sends a short text message: GET /profile/42, which means “please give me the profile of user 42”. The server looks up user 42, then replies with a status code and the data: 200 OK followed by {"id": 42, "name": "Asha", "followers": 318}. The 200 means “it worked”. If user 42 did not exist, the server would reply 404 Not Found instead. That text format in curly braces is JSON, a simple way to write data as names and values that almost every language can read.

Why does this split matter for design? Because the two sides have very different jobs. There are millions of clients, and you do not control them: people use old phones, slow networks and modified apps. There are relatively few servers, and you control them fully. So the rule is: keep the data and the important decisions on the server, and let the client mostly ask and display.

🔁
Roles, not machines

“Client” and “server” are roles, not types of machine. Your web server is a server to the browser, but a client when it asks the database for data. In big systems, most machines play both roles at once.

What happens when you open a website?

Let's follow a single request from start to finish. This is one of the most famous interview questions, and it touches nearly every topic in this course. Step through it:

Life of a request: https://shop.com/productsStep-through
  1. The browser splits the URL into parts: protocol https, host shop.com, path /products. It first checks its own cache (its store of recent answers) — maybe it already knows what it needs.
  2. Computers find each other by IP address (a number like a phone number), not by name. So the browser asks DNS, the internet's phone book: “what's the IP for shop.com?” It gets back 93.184.216.34. (Chapter 2 zooms into this.)
  3. The browser opens a TCP connection to that IP. TCP is the rule set for reliable delivery, and it starts with a quick “handshake” to say hello. Then the two sides agree on TLS encryption so nobody can snoop — that's the S in HTTPS.
  4. Over that connection it sends GET /products HTTP/1.1. It also sends headers (extra labels) such as cookies and which languages you accept.
  5. The server runs the app's code. First it checks who you are (authentication). Then it asks the database for data: SELECT * FROM products LIMIT 20.
  6. The database finds the matching rows and sends them back to the server. It finds them quickly using an index, like the index at the back of a book (Chapter 7).
  7. The server builds a response — 200 OK with HTML or JSON — and sends it back over the same connection.
  8. The browser reads the HTML and fetches the CSS, JavaScript and images. These often come from a CDN, a network of servers placed close to users (Chapter 6). Then it draws the page. All of this usually takes under a second.

Why walk through all eight steps? Because every step costs time, and the costs add up. One round trip means a message going to the server and the reply coming back. Say you are in Mumbai and the server is in Virginia, so one round trip takes about 200 ms. Before the page can even start to arrive, you pay for:

  • The TCP handshake: 1 round trip, about 200 ms.
  • The TLS handshake: 1 more round trip with modern TLS 1.3, another 200 ms.
  • The request and the response: 1 more round trip, plus the time the server and database spend working.

That is roughly 600 ms before the first byte of HTML shows up, and the DNS lookup can add more if the answer is not cached. This is why so many later chapters are about removing steps (keeping connections open, caching) or moving servers closer to users (CDNs, more regions).

Requirements: what are we actually building?

Every design starts with requirements: a list of what the system must do. They come in two kinds. Mixing them up is the #1 beginner mistake.

🛠️ Functional requirements

What the system does. Features a user can see and use. Usually written as “users can…”.

“Users can upload a video.”
“Users can comment on a post.”

📏 Non-functional requirements

How well the system does it. Qualities like speed, uptime, scale, not losing data (durability) and security.

“Videos start playing within 2 seconds.”
“The service is available 99.99% of the time.”

A quick test to tell them apart: if you removed the requirement, would a feature disappear from the app? If yes, it is functional. If the app would still have the same buttons but be slower, flakier or smaller, it is non-functional.

Non-functional requirements only help if they are written as numbers. Compare these two versions of the same wish:

Vague wishMeasurable requirementWhat it changes in the design
“It should be fast”Feed loads in under 200 ms for 99% of requestsYou probably need a cache, since a database query plus ranking can take longer than that
“It should always be up”99.9% availability (about 43 minutes of downtime a month)You need at least two copies of every part, so one can fail without taking the site down
“It should scale”10 million daily users, 5,000 requests per second at peakOne server is not enough; you need a load balancer and several app servers
“Don't lose data”A saved photo survives the loss of any one data centerEvery photo must be copied to a second location before you say “saved”

Interview tip

Non-functional requirements decide the architecture (the overall shape of the system). “Users can send messages” could be built a hundred ways. “Deliver messages to 500M users in under 100ms” rules out most of them. Always ask about scale, latency (delay) and availability (uptime) before you draw anything.

The qualities every system is judged by

These are the qualities (people call them the “-ilities”) you'll hear about all the time. Click each card to flip it.

📈

Scalability

click to flip
Handles growth well. Can the system serve 10× more users just by adding more machines — without a rewrite?
🟢

Availability

click to flip
Is it up right now? Measured as % of time it's working. 99.9% = about 8.8 hours down per year. 99.999% = about 5 minutes.
🎯

Reliability

click to flip
Does it work correctly, even when parts break? A system can be “up” but return wrong data — that's unreliable.
⚡

Latency

click to flip
How long one request takes. Measured in milliseconds (ms). People often quote p99: 99% of requests are faster than this, so it shows the slowest 1%.
🚚

Throughput

click to flip
How much work it does per second. Counted in requests per second (RPS or QPS) or MB per second. Latency is speed; throughput is capacity.
🔒

Consistency

click to flip
Does everyone see the same data? After you update your profile, does every server show the new version immediately?
💾

Durability

click to flip
Once saved, never lost. Data survives crashes, power cuts and broken disks — usually by keeping copies on several machines (replication).
🔧

Maintainability

click to flip
Easy to change and operate. Can new engineers understand it? Can you deploy safely on a Friday?

Where the numbers come from

Availability. A year has 365 × 24 = 8,760 hours. At 99.9% availability, the system may be down 0.1% of that: 8,760 × 0.001 ≈ 8.8 hours a year. Each extra 9 cuts the allowed downtime by 10×: 99.99% allows about 53 minutes a year, and 99.999% about 5 minutes. Each extra 9 also costs a lot more, because you need more spare machines and faster, automatic recovery.

Latency vs throughput. These two are easy to mix up, so here is an example. One server takes 50 ms to answer each request (its latency) and can work on 20 requests at the same time. Each of those 20 slots finishes 1000 ÷ 50 = 20 requests per second, so the server handles 20 × 20 = 400 requests per second (its throughput). Add a second identical server and throughput doubles to 800 per second, but each request still takes 50 ms. More machines raise throughput. They do not make any single request faster.

Averages hide pain. That is why people quote p99 latency. If 98 out of 100 requests take 20 ms and the other 2 take 3 seconds, the average is about 80 ms and looks fine. The p99 is 3 seconds, which shows the slow requests that users actually complain about. Chapter 4 covers percentiles properly.

Everything is a trade-off

There is no perfect architecture. Every decision gives you something and costs you something else. So learning system design really means learning the trade-offs, and being able to explain why you picked one side.

You gain……but you pay withExample
⚡ Lower latencyStale data riskCaching a profile for 5 minutes
🟢 Higher availabilityWeaker consistencyLetting copies of the database (replicas) answer reads while the network is cut in two
📈 Horizontal scaleOperational complexitySplitting one big app (a monolith) into 40 small services (microservices)
💾 DurabilityWrite latency & costWaiting for 3 replicas to confirm every write
🧩 Flexibility (schemaless)Query power & integrityChoosing a document DB over SQL

Let's play out the first row to see how you pick a side. A profile page reads from the database in 40 ms. If you cache profiles for 5 minutes, most page loads take 2 ms instead. The cost: when someone changes their name, other people may see the old name for up to 5 minutes. For a profile name, that is fine, so you take the cache. For a bank balance, showing an old number could let someone spend money twice, so you would not cache it that way. Same technique, different answer, because the requirement is different. That is the habit to build: name what you gain, name what you pay, and tie the choice back to a requirement.

A framework for any design problem

Whether it's an interview or a real project, these steps keep you from getting lost. Every case study in this course follows them.

Clarify requirements ~5 min

Which features are included, what the quality goals are (scale, latency, availability), and what is clearly out of scope.

Estimate the scale ~5 min

Do rough “back-of-envelope” math: number of users, requests per second, storage per year, and how many reads there are per write. Chapter 4 teaches this math.

Define the API & data model ~5 min

Which URLs (endpoints) can clients call? What kinds of data (entities) exist, and how are they linked? This fixes the agreement between client and server before you build the plumbing.

High-level design ~10 min

Draw the boxes and arrows: clients, load balancers, services, databases, caches, queues. Then walk one request through it.

Deep dive ~15 min

Zoom into the hardest 1–2 parts. Examples: the busiest request path (the “hot path”), how the data is split across machines, or how you keep copies in agreement.

Bottlenecks & trade-offs ~5 min

What breaks first at 10× traffic? Which single parts would take everything down if they failed (single points of failure)? What did you give up, and why?

Here is how the first two steps look for a small example: “design a link-sharing board like a simple Reddit”.

  1. Clarify. In scope: post a link, upvote, view the front page. Out of scope: comments, private messages. Quality goals: the front page loads in under 300 ms; it is fine if a vote count is a few seconds out of date.
  2. Estimate. 1 million daily users, each viewing 20 pages a day, gives 20 million page views a day. A day has 86,400 seconds, so that is about 230 reads per second on average, and maybe 1,000 at peak. If 1 in 100 users posts a link each day, that is 10,000 new posts a day, well under 1 per second. So this system does far more reading than writing.

That one number, “many reads, very few writes”, already points the design toward caching the front page and toward read copies of the database. That is the point of the early steps: they tell you what the later boxes need to be.

⚠️
Common mistakes
  • Designing before scoping. You start drawing boxes in minute two. Then you find out the system only has 10,000 users and none of it was needed.
  • Treating non-functional requirements as an afterthought. “Fast” and “reliable” aren't requirements. “p99 < 200 ms” and “99.9% availability” are — and they change the architecture.
  • Confusing the client–server boundary. Putting trust, checks or secrets in the client because “it's our app”. But anyone can change what a client sends, so treat all of it as possibly coming from an attacker.

Interview drill

Warm-up: A colleague says “we need a scalable system”. What three questions do you ask before agreeing to anything?

How a strong answer sounds
Ask for three things. Scale in numbers: users, requests per second, and how much data, today and in a year. The qualities that matter: the latency target, the availability target, and how much out-of-date data is OK. What's out of scope. Without those, “scalable” is a wish, not a requirement. Building for traffic that never comes is as much a failure as building too little.

Explain it simply: Walk through what happens between pressing Enter on a URL and seeing the page.

How a strong answer sounds
DNS turns the name into an IP address (with caches at several levels). The browser opens a TCP connection and does the TLS handshake. It sends an HTTP request. A CDN may answer it directly. If not, the request reaches a load balancer, then an application server, which may check a cache and a database. The response flows back, and the browser reads and draws the page, fetching more files as it goes. The strength of this answer: every box you name is a place you can dig deeper.

🧠 Key takeaways

  • System design is choosing the parts, how they connect and how data flows, so the system meets its goals for features, speed, reliability and cost.
  • Systems grow step by step: add a part only when a real problem needs it.
  • Client and server are roles — most machines in a big system are both.
  • Functional requirements = what it does. Non-functional requirements (NFRs) = how well it does it. NFRs shape the architecture.
  • There are no right answers, only trade-offs you can justify.

Check your understanding

Which of these is a non-functional requirement?

It describes how well search performs (latency), not a new feature. The others describe what users can do.

Your single server runs the app and the database. It's running out of CPU and memory. What's the most sensible first step?

Moving the database to its own machine lets the web part and the data part grow separately. It's a small change that fixes the real problem. The other options add a lot of complexity before it's needed.

A web server queries a database. In that interaction, the web server is acting as a…

Whoever starts the request is the client. The web server is a server to browsers, but a client to the database.

A service is “up” 100% of the time, but 2% of responses contain another user's data. Which quality is it failing?

Available means it answers. Reliable means it answers correctly. Returning wrong data is a reliability (and security!) failure.

In a design interview, what should you do FIRST?

Every later decision depends on the requirements. Designing without them means solving a problem you don't understand yet.
