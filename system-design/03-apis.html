APIs & Communication

Parts only become a system when they can talk to each other. APIs are the agreements that make that conversation predictable. The style you choose affects speed, flexibility and how well you handle live updates.

What is an API?

An API (Application Programming Interface) is a contract, or agreement: “send me a request shaped like this, and I promise to answer with something shaped like that.” The caller doesn't need to know how the server works inside. It only needs to know the contract.

A tiny example. A weather service promises: “send GET /v1/weather?city=Pune and you'll get back {"city": "Pune", "tempC": 29, "updatedAt": "2026-09-23T10:00:00Z"}”. Today the numbers might come from one database. Next year the team might switch to a different data supplier and rewrite everything in another language. As long as the same request still gets the same shape of answer, every app built on it keeps working. That freedom is why APIs matter in system design: they are the lines along which you can split work between teams and services.

🍽️
Analogy: the restaurant menu

A menu lists what you can order and what you'll get. You don't walk into the kitchen, and you don't care whether the chef cooks on gas or electric. The kitchen can be completely rebuilt. As long as the menu (API) stays the same, customers notice nothing. That's why good APIs let teams change the inside freely.

REST: resources over HTTP

REST is the most common style for web APIs. Its main idea: everything is a resource — a thing, like a book or a user — with its own URL (a noun). You act on it using the standard HTTP methods (the verbs), like GET or DELETE.

Goal❌ RPC-ish / avoid✅ RESTful
List booksGET /getAllBooksGET /books
Fetch one bookPOST /fetchBook {id:7}GET /books/7
Create a bookGET /createBook?title=…POST /books
Delete a bookPOST /books/7/deleteDELETE /books/7
A user's reviewsGET /reviewsForUser?u=3GET /users/3/reviews

Why does it matter whether you write GET /books/7 or POST /fetchBook, if both return the same book? Because the rest of the internet reads the method and acts on it. Browsers, CDNs and proxies know a GET is safe, so they may cache the answer and serve it again without asking you. Retry libraries know a GET or PUT can be repeated safely, but a POST might not be. Web crawlers and link-preview bots follow GET links freely. So if GET /createBook?title=… creates a book, a bot scanning your pages could create hundreds of them. Using the methods as intended lets all this existing machinery work for you instead of against you.

✅
REST design checklist

Use plural nouns (/books) · nest URLs to show what belongs to what (/users/3/orders) · use the right status codes (201 on create, 404 when missing) · put a version in your API (/v1/) · filter and sort with query parameters · never put verbs in URLs.

REST vs GraphQL vs gRPC

REST isn't the only option. Each style is best at something different. Two terms first. Over-fetching means getting more data than you need: a phone screen that shows just a user's name still downloads their whole profile. Under-fetching means one call doesn't give you enough, so you make several in a row: first the user, then their posts, then each post's comments. On a phone with a 200 ms round trip, three calls in a row cost over half a second before the screen can draw.

Built around resources. It uses HTTP's own methods and status codes directly, and sends JSON that humans can read. It works with every browser, proxy and CDN — and GET responses are very easy to cache (save and reuse).

GET /users/42
→ 200 OK
{ "id": 42, "name": "Ada", "email": "ada@…", "bio": "…", "avatar": "…", … }

GET /users/42/posts   // second round-trip for related data
Strengths
  • Simple, universal, cache-friendly
  • Great for public APIs
Weaknesses
  • Over-fetching: you get fields you don't need
  • Under-fetching: you need many round trips to get related data

One single URL (endpoint), where the client describes exactly which data it wants. Facebook created it for mobile apps on slow networks.

POST /graphql
query {
  user(id: 42) {
    name
    posts(last: 3) { title }
  }
}
Strengths
  • No over- or under-fetching — one round trip
  • A strict schema (a typed description of all the data), with great tools
  • Front-end teams can change what they fetch without new endpoints
Weaknesses
  • HTTP caching is harder (everything is a POST)
  • It's easy to write very expensive queries — you need limits on how deep or complex they get
  • The N+1 query problem on the server: one query for a list, then one more query for each item

Google's high-speed RPC framework. RPC (remote procedure call) means calling a function on another machine as if it were local. You describe your services in Protocol Buffers (Protobuf), and the tool generates the client and server code for you. Data is sent in compact binary over HTTP/2.

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
  rpc StreamUpdates(Req) returns (stream Update);
}
message User { int64 id = 1; string name = 2; }
Strengths
  • Very fast, with compact binary messages (often 5–10× smaller than JSON)
  • Strict contracts, plus generated code in many languages
  • Built-in streaming: client to server, server to client, or both ways
Weaknesses
  • Not human-readable, so harder to debug with tools like curl
  • Browsers can't easily call it directly

(CRUD, in the table, stands for Create, Read, Update, Delete: the four basic things you do to stored data.) A simple way to choose:

  • Pick REST when outsiders will call your API, or when the data is mostly “get this thing, change that thing”. Everyone knows it, every tool supports it, and GET responses can be cached by CDNs for free.
  • Pick GraphQL when many different screens need different slices of the same connected data, and the extra round trips of REST are hurting (often on mobile). Be ready to add limits so one heavy query can't overload your servers.
  • Pick gRPC for calls between your own services, where you control both sides, want strict types, and send a lot of small messages. Its binary format saves CPU and bandwidth at high volume.

Many real systems use all three: REST for the public API, GraphQL or a BFF (a “backend for frontend”: a small server built just for one app) for their own apps, and gRPC inside the data center.

The cost of polling adds up quickly. Say 1 million users have your app open, and each one polls every 5 seconds. That is 1,000,000 ÷ 5 = 200,000 requests per second, and if a typical user gets a new message once a minute, about 11 out of every 12 of those requests come back empty. Each one still pays for a round trip, headers, an auth check and maybe a database lookup. Polling every 30 seconds cuts the load 6×, but now a message can take up to 30 seconds to show up. Long polling, SSE and WebSockets escape this trade-off: they send data only when there is data. What they cost instead is open connections. Each connection holds a bit of memory on the server and must be kept alive, so 1 million users means 1 million connections spread across many servers.


  

    
⚠️

    
Persistent connections change your architecture
With WebSockets, servers become stateful: each one holds thousands of open connections and has to remember them. Load balancers must support connections that stay open for a long time. You also need a way to find which server holds a given user's connection. We'll solve this in the Chat System case study (Chapter 28).

  


  
Pagination: offset vs cursor

  
You never return 10 million rows at once. You return them in pages. But how you split them into pages matters, especially for feeds where new items keep arriving.


  

    
Offset pagination
GET /posts?limit=5&offset=10
SELECT … ORDER BY id DESC LIMIT 5 OFFSET 10
Simple, and lets you jump straight to page 50. But the database still reads and throws away the first 10 rows, so deep pages get slow. And new items shift every position.

    
Cursor (keyset) pagination
GET /posts?limit=5&after=P16
SELECT … WHERE id < 16 ORDER BY id DESC LIMIT 5
The cursor is a bookmark: “give me items after P16”. The database jumps straight there using an index, so it's fast at any depth. It also stays correct when new items arrive. The downside: you can't jump to any page number you like.

  


  
Here is the bug traced step by step. A feed shows the newest posts first, 5 per page. The posts are P20 (newest) down to P1.

  
    
    
  1. Page 1 with offset=0 returns P20, P19, P18, P17, P16. The cursor version remembers “last seen: P16”.
    2. 
    
  2. While you read, 3 new posts (P21, P22, P23) are published at the top. Every older post moves down 3 places.
    3. 
    
  3. Offset page 2 asks for offset=5: “skip the first 5”. The first 5 are now P23–P19, so you get P18, P17, P16, P15, P14. Three of those you have already seen.
    4. 
    
  4. Cursor page 2 asks for “posts older than P16” and gets P15, P14, P13, P12, P11. No repeats, no gaps.
    5. 
  

  
If posts are deleted instead, offset pagination makes the opposite mistake: items slide up and get skipped. It is also slow deep down. OFFSET 1000000 makes the database walk past a million rows just to throw them away, while a cursor query jumps straight to the right place in the index.

  
Edge case for cursors: the sort key must be unique. If you sort by created_at and two posts share the same timestamp, “after this time” can skip one of them. The usual fix is to sort by (created_at, id) and put both values in the cursor. Most APIs also encode the cursor as an opaque string, so clients treat it as a bookmark and don't try to build one themselves.

Idempotency: making retries safe

  
Networks can fail in a nasty way. A request can succeed on the server, but the response gets lost on the way back. The client only sees a timeout, so it tries again. If the request was “charge $50”, a simple retry charges the customer twice.


  

    
The double-charge problemSimulator

    

      

      

      

    

  



// Server-side idempotency (simplified)
async function createCharge(req) {
  const key = req.headers['idempotency-key'];
  const saved = await store.get(key);
  if (saved) return saved;            // replay: return the original result
  const result = await bank.charge(req.body);
  await store.set(key, result, { ttl: '24h' });
  return result;
}

  
In real systems you also lock the key while the first request is still running. That way, two retries arriving at the same time can't both get through.


  
Walk through it once with the key. The checkout page creates a random key, say 8f14e45f, when you press Pay, and sends it with the request. The server has never seen that key, so it charges $50 and saves “8f14e45f → charge #c_901, $50, success”. The response is lost on the way back, so the client retries, with the same key. The server finds the key, skips the charge, and returns the saved answer. The customer paid once and the app still gets a normal success reply.

  
Some operations are safe to repeat by nature, and need no key. “Set the quantity to 3” gives the same result however many times you send it. “Add 1 to the quantity” does not: send it three times and you get 3 extra. When you design a write, ask first whether you can phrase it as a “set” instead of an “add”. If you can't (money transfers, sending a message, creating an order), use a key.

  
Edge cases a real implementation must handle:

  
    
    
  • The key is generated once per user action, not once per HTTP attempt. If the client makes a new key on each retry, the server can't tell they are the same request.
    • 
    
  • Same key, different body. If a client reuses a key for a different payment, return an error (often 422 or 409) instead of replaying the old answer.
    • 
    
  • How long keys are kept. Stored keys expire (24 hours in the example). That must be longer than any client will keep retrying.
    • 
    
  • Failures. If the first attempt failed because of bad input, replaying that same error is correct. If it failed because the server crashed half-way, the saved state must show that, so the retry can finish or safely start over.
    • 
  


  
Designing APIs that survive contact with users

  
Once someone builds on your API, you can't take things away. Mobile apps stay installed for years, and partners upgrade slowly. Every breaking change becomes a big job for other people. The habits below are what make an API age well instead of becoming a support headache.


  

    

    

      
Whenever you can, change things by adding: new optional fields and new endpoints don't break anyone. Clients must ignore fields they don't recognise (the “tolerant reader” rule). Save a new version number for changes that really break the contract.

      
What counts as breaking? Anything that makes an existing, correctly written client fail or misbehave: removing or renaming a field, changing its type (an id that was a number becomes a string), making an optional input required, or changing what a value means (a price in dollars becomes cents). Safe changes: adding a new optional field to a response, adding a new endpoint, or adding a new optional input with a sensible default.

      

        
StyleExampleTrade-off

        
          
URL path/v1/usersObvious, cacheable, easy to route — the usual default

          
HeaderAccept: application/vnd.api+json;version=2Keeps URLs stable; harder to test in a browser and to cache

          
Date-pinnedStripe-Version: 2026-03-14Each client locks in a date and upgrades when it chooses; the server keeps small adapters so old dates still work

          
No versionAdditive changes onlySimplest — until you truly must break something

        
      

      
Retiring old features politely (deprecation): announce it, send Deprecation and Sunset headers, measure who still calls the old path, contact them, and only then remove it. Never quietly change the meaning of an existing field.

    

    

      
Errors are part of your API too. Use the right status code. Return a body that code can read and act on (like an error code), not just a sentence for humans.


→ 422 Unprocessable Entity
{
  "type": "https://api.example.com/errors/validation",
  "title": "Invalid request",
  "code": "card_expiry_invalid",     // stable, documented, safe to switch on
  "detail": "Expiry must be in the future",
  "field": "card.exp_year",
  "request_id": "req_01J8…"          // lets support find the exact log line
}

      

        
Client's fault (4xx)
400 malformed · 401 not authenticated · 403 not allowed · 404 missing (or hidden) · 409 conflict · 422 well-formed but makes no sense (e.g. an expiry date in the past) · 429 rate limited (send Retry-After). Don't retry these without changing something.

        
Our fault (5xx)
500 bug · 502/504 upstream failed or timed out · 503 overloaded or in maintenance. Safe to retry, waiting longer each time (backoff) plus a little randomness (jitter) — which is exactly why writes need idempotency keys.

      

      
Never show internal details like stack traces or SQL. Always include a request ID, and log it on both sides so problems can be traced.

    

    

      
Asking over and over “did it finish yet?” wastes requests. A webhook flips this around: you call the client's URL when something happens. But now you are the client, so you get all of a client's problems.

      
    
        
  • Sign every delivery with an HMAC (a secret-key signature) of the body plus a timestamp. The receiver can then check it's really you, and reject old messages being replayed.
    • 
        
  • At-least-once: a message may arrive more than once. Include a fixed event_id so receivers can drop duplicates. Expect receivers to be slow, so send from a queue in the background (Chapter 14).
    • 
        
  • Retry with exponential backoff (waiting 1s, 2s, 4s, 8s...) for hours. Then switch the endpoint off and alert its owner. Give them a screen to inspect and resend events.
    • 
        
  • Order isn't guaranteed — send a sequence number or version so receivers can ignore out-of-date events.
    • 
        
  • Receivers should reply 2xx right away and do the work later. Otherwise, their slowness becomes your timeout.
    • 
      

    

    

      

        
📦 Batch endpoints
On slow mobile networks, “chatty” APIs (many small calls) hurt. Offer POST /v1/items/batch, or combine calls with GraphQL or a BFF (a backend built for one front-end). Return a status for each item. If 3 out of 100 fail, the other 97 should still succeed — unless you've promised all-or-nothing (transactional).

        
⏳ Long-running work
Don't hold an HTTP connection open for 5 minutes. Return 202 Accepted with a job ID and a status URL. The client checks that URL, or gets a webhook when the job is done. This is the background-job pattern from Chapter 14, offered through the API.

        
🔎 Filtering & sparse fields
?fields=id,name&include=author&sort=-created_at lets one endpoint serve many screens without over-fetching. It's GraphQL's big advantage, added to REST.

        
📣 Tell clients the rules
Publish your usage limits and return X-RateLimit-* headers (Chapter 15). Document how idempotency works. Publish an OpenAPI spec (a machine-readable description of your API), so client libraries (SDKs) and fake test servers can be generated from it.

⚠️
Common mistakes

    
    
      
  • Offset pagination on data that changes. As new items are added, users see duplicates and gaps. Cursors avoid this completely.
    • 
      
  • Writes that aren't safe to repeat, plus client retries. Every mobile client retries. Without an idempotency key, you get duplicate orders and double charges.
    • 
      
  • Chatty APIs for mobile. Ten round trips on a 200 ms connection is two seconds of waiting. Combine calls on the server (a BFF) or batch them.
    • 
    


  
🎤
Interview drill

    
Design: Design the API for a “save post” button that works offline and syncs later.

    
How a strong answer sounds
Use PUT /v1/posts/{client_generated_id} with an idempotency key. The client creates the ID itself while offline, so it can retry safely. The server “upserts” (creates the post, or updates it if it exists) and returns the official version. The client keeps a local queue of changes waiting to be sent. Each one remembers which version of the post it was based on. When the connection returns, the client sends them in order. If someone else changed the post in the meantime, the server reports a version mismatch instead of quietly overwriting their work.

    
Trade-off: REST, GraphQL or gRPC for a new mobile app backed by 12 internal services?

    
How a strong answer sounds
Use gRPC between the internal services: it's binary, typed, supports streaming and has low overhead. For the app, use either REST with a backend-for-frontend (one server that gathers data from the 12 services for the app), or GraphQL if different screens need very different shapes of the same data. The deciding factors: caching (REST gets HTTP caching for free), how many kinds of clients you have, and how much over-fetching hurts on mobile networks.

  


  

    
🧠 Key takeaways

    
    
      
  • An API is a contract that lets both sides change their insides without breaking each other.
    • 
      
  • REST = nouns in URLs + HTTP verbs + the right status codes. Simple and easy to cache.
    • 
      
  • GraphQL lets clients choose the shape of the response (no over- or under-fetching). gRPC is fast binary calls between internal services.
    • 
      
  • Polling wastes requests. Long polling and SSE let the server push events. WebSockets let both sides talk at once, but make servers stateful.
    • 
      
  • Prefer cursor pagination for big or fast-changing lists.
    • 
      
  • Any operation that isn't safe to repeat, and might be retried, needs an idempotency key.
    •

A live sports app pushes score updates to viewers; viewers never send data back. Simplest good fit?

      

      
One-way server → client streams are exactly what SSE is for. It's plain HTTP, reconnects on its own, and is simpler than WebSockets.

    

    

      
Why does offset pagination show duplicates in a live feed?

      

      
An offset is a position (“skip 10”), not a specific item. A cursor points at a specific item, so new items added elsewhere don't matter.

    

    

      
Your 20 internal microservices exchange millions of small messages per second. Which API style fits best?

      

      
gRPC's compact binary Protobuf format, HTTP/2's many-requests-per-connection, and its generated client code make it ideal for heavy internal traffic.

    

    

      
A client times out on POST /transfers and retries. How do you prevent a double transfer?

      

      
A longer timeout only makes a retry less likely. The key makes the operation safe to repeat — that's the real fix.
