APIs & Communication

Components only become a system when they can talk to each other. APIs are the contracts that make that conversation predictable — and the style you choose shapes performance, flexibility and real-time behaviour.

  • Design clean RESTful endpoints
  • Compare REST, GraphQL and gRPC
  • Pick between polling, long polling, SSE & WebSockets
  • Paginate correctly with cursors
  • Make retries safe with idempotency keys

What is an API?

An API (Application Programming Interface) is a contract: “send me a request shaped like this, and I promise to respond with something shaped like that.” The caller doesn't need to know how the server works inside — only the contract.

🍽️
Analogy: the restaurant menu

A menu lists what you can order and what you'll get. You don't walk into the kitchen or care whether the chef uses gas or induction. The kitchen can be completely renovated — as long as the menu (API) stays the same, customers are unaffected. That's why good APIs let teams change internals freely.

REST: resources over HTTP

REST is the most common style for web APIs. Its core idea: everything is a resource identified by a URL (a noun), and you act on it using standard HTTP methods (the verbs).

✅
REST design checklist

Plural nouns (/books) · nest for ownership (/users/3/orders) · use the right status codes (201 on create, 404 when missing) · version your API (/v1/) · filter/sort with query params · never put verbs in URLs.

REST vs GraphQL vs gRPC

REST isn't the only option. Each style optimises for something different.

Resource-oriented, uses HTTP semantics directly, human-readable JSON. Works with every browser, proxy and CDN — and GET responses are trivially cacheable.

GET /users/42
→ 200 OK
{ "id": 42, "name": "Ada", "email": "ada@…", "bio": "…", "avatar": "…", … }

GET /users/42/posts   // second round-trip for related data
Strengths
  • Simple, universal, cache-friendly
  • Great for public APIs
Weaknesses
  • Over-fetching: get fields you don't need
  • Under-fetching: many round-trips for related data

A single endpoint where the client describes exactly the shape of data it wants. Created by Facebook for mobile apps on slow networks.

POST /graphql
query {
  user(id: 42) {
    name
    posts(last: 3) { title }
  }
}
Strengths
  • No over/under-fetching — one round trip
  • Strongly typed schema, great tooling
  • Frontends evolve without new endpoints
Weaknesses
  • HTTP caching is harder (everything is POST)
  • Expensive queries are easy to write — need depth/complexity limits
  • N+1 query problems on the server

Google's high-performance RPC framework. You define services in Protocol Buffers; code is generated for client and server. Binary encoding over HTTP/2.

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
  rpc StreamUpdates(Req) returns (stream Update);
}
message User { int64 id = 1; string name = 2; }
Strengths
  • Very fast, compact binary payloads (often 5–10× smaller than JSON)
  • Strict contracts + codegen in many languages
  • Built-in streaming (client, server, bidirectional)
Weaknesses
  • Not human-readable; harder to debug with curl
  • Limited direct browser support

Persistent connections change your architecture
With WebSockets, servers become stateful — each holds thousands of open connections. Load balancers need to support long-lived connections, and you need a way to find which server holds a given user's socket. We'll solve this in the Chat System case study (Chapter 28).

  


  
Pagination: offset vs cursor

  
You never return 10 million rows at once. But how you page matters — especially for feeds where new items keep arriving.


  

    
Offset pagination
GET /posts?limit=5&offset=10
SELECT … ORDER BY id DESC LIMIT 5 OFFSET 10
Simple and lets you jump to page 50. But the DB still scans & discards 10 rows, getting slow for deep pages — and inserts shift everything.

    
Cursor (keyset) pagination
GET /posts?limit=5&after=P16
SELECT … WHERE id < 16 ORDER BY id DESC LIMIT 5
Uses an index seek — fast at any depth — and stable when new items arrive. Can't jump to an arbitrary page.

Idempotency: making retries safe

  
Networks fail in an evil way: a request can succeed on the server while the response gets lost. The client sees a timeout and retries. If the operation is “charge $50”, a naive retry charges twice.


  

    
The double-charge problemSimulator

    

      

      

      

    

  



// Server-side idempotency (simplified)
async function createCharge(req) {
  const key = req.headers['idempotency-key'];
  const saved = await store.get(key);
  if (saved) return saved;            // replay: return the original result
  const result = await bank.charge(req.body);
  await store.set(key, result, { ttl: '24h' });
  return result;
}

  
In production you also lock the key while the first request is in flight, so two concurrent retries can't both slip through.


  
Designing APIs that survive contact with users

  
Once someone integrates with your API, you can't take things away. Mobile apps stay installed for years, partners upgrade slowly, and every breaking change becomes a migration project for other people. These conventions are what separate an API that ages well from one that becomes a support burden.


  

    

    

      
Change additively whenever possible: new optional fields and new endpoints don't break anyone. Clients must ignore unknown fields (“tolerant reader”). Reserve a version bump for changes that genuinely break the contract.

      

        
StyleExampleTrade-off

        
          
URL path/v1/usersObvious, cacheable, easy to route — the common default

          
HeaderAccept: application/vnd.api+json;version=2Keeps URLs stable; harder to test in a browser and to cache

          
Date-pinnedStripe-Version: 2026-03-14Each integration pins a date and upgrades deliberately; the server keeps compatibility shims

          
No versionAdditive changes onlySimplest — until you truly must break something

        
      

      
Deprecation with grace: announce, send Deprecation and Sunset headers, measure who still calls the old path, contact them, and only then remove. Never silently change the meaning of an existing field.

    

    

      
Errors are part of your API. Use the right status code, and return a machine-readable body a client can branch on — not prose.


→ 422 Unprocessable Entity
{
  "type": "https://api.example.com/errors/validation",
  "title": "Invalid request",
  "code": "card_expiry_invalid",     // stable, documented, safe to switch on
  "detail": "Expiry must be in the future",
  "field": "card.exp_year",
  "request_id": "req_01J8…"          // lets support find the exact log line
}

      

        
Client's fault (4xx)
400 malformed · 401 not authenticated · 403 not allowed · 404 missing (or hidden) · 409 conflict · 422 semantically invalid · 429 rate limited (send Retry-After). Don't retry these unchanged.

        
Our fault (5xx)
500 bug · 502/504 upstream failed or timed out · 503 overloaded or in maintenance. Safe to retry with backoff + jitter — which is exactly why writes need idempotency keys.

      

      
Never leak stack traces or SQL. Always include a request ID and log it on both sides.

    

    

      
Polling for “did it finish yet?” wastes requests. A webhook inverts the flow: you call the client's URL when something happens. You then inherit all the problems of being a client yourself.

      
    
        
  • Sign every delivery (HMAC of the body + timestamp) so the receiver can verify it's really you and reject replays.
    • 
        
  • At-least-once: include a stable event_id; receivers dedupe. Expect them to be slow — deliver asynchronously from a queue (Chapter 14).
    • 
        
  • Retry with exponential backoff for hours, then disable the endpoint and alert the owner. Provide a replay/inspection UI.
    • 
        
  • Order isn't guaranteed — send a sequence number or version so receivers can ignore stale events.
    • 
        
  • Receivers should respond 2xx immediately and process asynchronously; anything else becomes your timeout.
    • 
      

    

    

      

        
📦 Batch endpoints
Mobile clients on high-latency networks suffer from chatty APIs. Offer POST /v1/items/batch (or GraphQL/BFF aggregation) and return per-item statuses — a batch of 100 where 3 fail should not be all-or-nothing, unless you say it's transactional.

        
⏳ Long-running work
Don't hold an HTTP connection open for 5 minutes. Return 202 Accepted with a job ID and a status URL; the client polls it or gets a webhook when done. This is the async pattern from Chapter 14 exposed through the API.

        
🔎 Filtering & sparse fields
?fields=id,name&include=author&sort=-created_at lets one endpoint serve many screens without over-fetching — GraphQL's advantage, retrofitted to REST.

        
📣 Tell clients the rules
Publish quotas and return X-RateLimit-* headers (Chapter 15), document idempotency behaviour, and ship an OpenAPI spec so SDKs and mocks can be generated.

⚠️
Common mistakes

    
    
      
  • Offset pagination on data that changes. Users see duplicates and gaps as items are inserted; cursors avoid it entirely.
    • 
      
  • Non-idempotent writes with client retries. Every mobile client retries. Without an idempotency key, that's duplicate orders and double charges.
    • 
      
  • Chatty APIs for mobile. Ten round trips on a 200 ms connection is two seconds of nothing. Aggregate server-side (BFF) or batch.
    • 
    


  
🎤
Interview drill

    
Design: Design the API for a “save post” button that works offline and syncs later.

    
How a strong answer sounds
PUT /v1/posts/{client_generated_id} with an idempotency key, so the client can generate the ID offline and retry safely; the server upserts and returns the canonical resource. The client keeps a local queue of pending operations with the base version they were written against, and on reconnect replays them; conflicts are surfaced with a version mismatch rather than silently overwritten.

    
Trade-off: REST, GraphQL or gRPC for a new mobile app backed by 12 internal services?

    
How a strong answer sounds
gRPC between the internal services (binary, typed, streaming, low overhead), and for the app either REST with a backend-for-frontend that aggregates, or GraphQL if screens need very different shapes of the same data. The deciding factors are caching (REST gets HTTP caching for free), client diversity, and how much over-fetching hurts on mobile networks.

  


  

    
🧠 Key takeaways

    
    
      
  • An API is a contract that lets both sides evolve independently.
    • 
      
  • REST = nouns in URLs + HTTP verbs + proper status codes. Simple and cacheable.
    • 
      
  • GraphQL lets clients shape responses (no over/under-fetching); gRPC is fast binary RPC for internal services.
    • 
      
  • Polling wastes requests; long polling & SSE push server events; WebSockets give full-duplex, but make servers stateful.
    • 
      
  • Prefer cursor pagination for large or fast-changing lists.
    • 
      
  • Any non-idempotent operation that may be retried needs an idempotency key.

Check your understanding

    

    

      
Which endpoint best follows REST conventions for cancelling order 91?

      

      
Use the resource URL and let the method express the action. GET must never change state.

    

    

      
A live sports app pushes score updates to viewers; viewers never send data back. Simplest good fit?

      

      
One-directional server → client streams are exactly what SSE is for. It's plain HTTP, reconnects automatically and is simpler than WebSockets.

    

    

      
Why does offset pagination show duplicates in a live feed?

      

      
Offsets are positions, not identities. Cursors anchor to a specific item, so inserts elsewhere don't matter.

    

    

      
Your 20 internal microservices exchange millions of small messages per second. Which API style fits best?

      

      
gRPC's binary Protobuf encoding, HTTP/2 multiplexing and generated clients make it ideal for high-volume internal traffic.

    

    

      
A client times out on POST /transfers and retries. How do you prevent a double transfer?

      

      
Longer timeouts only reduce the chance; the key makes the operation safe to repeat, which is the real fix.
