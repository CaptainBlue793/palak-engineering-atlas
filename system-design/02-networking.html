Networking Essentials

Every distributed system is just computers sending messages over a network. Let's understand how those messages are addressed, found, delivered and secured.

Layers: how networking is organised

Networking is split into layers. Each layer solves one problem and relies on the layer below. The theoretical OSI model has 7 layers; in practice engineers think in the simpler TCP/IP model with 4:

LayerJobExamplesUnit
4 · ApplicationWhat the message meansHTTP, DNS, SMTP, WebSocketMessage
3 · TransportDeliver between programs (ports), reliably or notTCP, UDP, QUICSegment
2 · NetworkRoute between machines across networksIP (v4, v6)Packet
1 · LinkMove bits across one physical hopEthernet, Wi-FiFrame
✉️
Analogy: sending a letter inside envelopes

You write a letter (application data). You put it in an envelope addressed to a person in an apartment (transport → port). That goes into a bigger envelope addressed to the building (network → IP). The postal truck carries it one road at a time (link). At the other end, each envelope is opened in reverse. This wrapping is called encapsulation.

  1. Your browser writes an HTTP request: GET /index.html. It has no idea how it'll be delivered — that's someone else's job.
  2. TCP wraps it with source & destination ports (e.g. 51034 → 443) and sequence numbers so pieces can be reordered and missing ones re-sent.
  3. IP wraps that with source & destination IP addresses. Routers only read this layer to decide where to forward the packet next.
  4. Wi-Fi/Ethernet adds a frame with the MAC address of the next hop (your router) plus an error-check trailer.
  5. Everything becomes electrical signals / radio waves, hopping router to router. Each router unwraps the frame, reads the IP header, and re-wraps it for the next hop.
  6. The server's network card checks the frame, removes it, and passes the IP packet up.
  7. IP confirms “this is addressed to me” and hands the segment up.
  8. TCP uses the port (443) to find which program should get this — the web server — and puts bytes back in order.
  9. The web server finally sees exactly what the browser wrote: GET /index.html. Each layer only ever talked to its peer layer.

IP addresses, ports & sockets

An IP address identifies a machine on a network. A port identifies a specific program on that machine. Together they form a socket address — the full delivery address for a conversation.

🏢

IP address = building

IPv4: 142.250.72.14 — 4.3 billion possible, basically exhausted.
IPv6: 2607:f8b0:4005::200e — 3.4×10³⁸ possible.

🚪

Port = apartment

0–65535. Well-known: 80 HTTP, 443 HTTPS, 22 SSH, 5432 Postgres, 6379 Redis.

🔗

Connection = 4-tuple

(src IP, src port, dst IP, dst port). That's how one server on :443 keeps millions of clients apart.

🏠
Public vs private IPs

Your laptop has a private IP like 192.168.1.23 that only means something inside your home network. Your router has one public IP and uses NAT (Network Address Translation) to share it. Inside data centers, servers talk over private IPs in a VPC; only load balancers face the public internet.

DNS: the internet's phone book

Humans remember netflix.com; routers need 54.155.178.5. The Domain Name System translates between them. It's a globally distributed, hierarchical, heavily cached database — and a beautiful example of system design in its own right.

Resolving www.shop.comStep-through
  1. Browser cache → OS cache → hosts file. If a recent answer exists (and its TTL hasn't expired), we're done instantly. Most lookups end here.
  2. Cache miss. The OS asks a recursive resolver (your ISP's, or a public one like 1.1.1.1). It will do the legwork and check its own big cache first.
  3. “Where's www.shop.com?” The root doesn't know, but it knows who handles .com: “ask the .com TLD servers at a.gtld-servers.net”.
  4. The TLD server doesn't know the IP either, but knows which name servers are authoritative for shop.com: “ask ns1.shop.com”.
  5. The authoritative name server owns the zone and returns the real record: A 93.184.216.34 with a TTL of 300 seconds.
  6. The resolver caches the answer for the TTL and returns it. The OS and browser cache it too. The whole walk typically takes 20–120ms — and next time, ~0ms.

🧰 DNS as a system design tool

  • DNS load balancing: return several IPs, rotate them.
  • GeoDNS: return the IP of the data center nearest the user.
  • Failover: health-checked records swap to a backup region.
  • TTL trade-off: long TTL = fewer lookups but slow failover; short TTL = fast changes, more DNS traffic.

TCP vs UDP

Both live at the transport layer and both use ports. The difference is what they promise.

📦 TCP — the registered courier

  • Connection-oriented: 3-way handshake first (SYN → SYN-ACK → ACK)
  • Reliable: every byte is acknowledged; lost data is re-sent
  • Ordered: bytes arrive in the order they were sent
  • Flow & congestion control: slows down when the network is busy
  • Used by: HTTP/1.1 & 2, databases, SSH, email

📣 UDP — shouting across the room

  • Connectionless: just send, no handshake
  • Unreliable: packets can be lost, duplicated, reordered
  • Tiny overhead: 8-byte header vs TCP's 20+
  • Low latency: no waiting for retransmits
  • Used by: video calls, gaming, DNS, live streaming, QUIC/HTTP3

Rule of thumb

If late data is useless (a video frame from 2 seconds ago, a player's old position), use UDP. If every byte matters (a bank transfer, a web page, a file), use TCP.

HTTP: the language of the web

HTTP is a simple text-based request/response protocol on top of TCP (or QUIC). It is stateless: each request carries everything the server needs — which is exactly why web servers are so easy to scale horizontally. Click any part of this request:

HTTPS & TLS

HTTPS is HTTP inside a TLS tunnel. TLS gives you three guarantees:

🙈

Confidentiality

Traffic is encrypted — Wi-Fi snoopers see gibberish.

🧾

Integrity

Any tampering in transit is detected and the connection dropped.

🪪

Authentication

A certificate signed by a trusted authority proves you're really talking to shop.com.

ClientHello

Browser: “Hi! I support TLS 1.3, these cipher suites, and here's my key-share.”

ServerHello + Certificate

Server picks a cipher, sends its key-share and its certificate (public key signed by a CA).

Verify & derive keys

Browser checks the certificate chain against trusted CAs. Both sides combine key-shares (Diffie-Hellman) to derive the same symmetric session key — without ever sending it.

Encrypted HTTP

All further traffic uses fast symmetric encryption. TLS 1.3 does all this in one round trip.

🎤
System design angle: TLS termination

Encryption costs CPU. Large systems usually terminate TLS at the load balancer or edge, then use plain HTTP (or internal mTLS) inside the private network. It also means certificates live in one place.

⚠️
Common mistakes
  • Ignoring round trips. A design with five sequential cross-region calls can't be fast, no matter how well each service is written — latency floors are physics, not engineering.
  • Assuming DNS changes take effect instantly. Resolvers and clients cache; a failover plan that relies on a TTL change needs the TTL lowered in advance.
  • Forgetting that TCP connections and TLS handshakes cost something. Connection reuse, keep-alive and pooling matter more than most micro-optimizations.
🎤
Interview drill

Trade-off: When would you choose UDP over TCP, and what do you have to build yourself?

How a strong answer sounds
Real-time media, gaming, DNS, QUIC-style protocols — anywhere a late packet is worthless and retransmission would make things worse. You give up ordering, reliability and congestion control, so you implement what you actually need: sequence numbers for ordering, selective retransmission or forward error correction for loss, and your own pacing so you don't melt the network.

Debug: A page is slow only for users in Australia. How do you find out why?

How a strong answer sounds
Separate the components of latency: DNS resolution, TCP+TLS handshake, time to first byte, and content transfer. High TTFB with a fast handshake points at the origin being far away or slow; slow handshake points at missing edge termination; slow transfer points at bandwidth or object size. Fixes differ completely — a CDN with edge TLS termination, HTTP/3, smaller payloads, or a regional replica.

🧠 Key takeaways

  • Networking is layered: application → transport → network → link. Each layer wraps the one above.
  • IP finds the machine, the port finds the program; a connection is a 4-tuple.
  • DNS is hierarchical and cached by TTL — and can be used for load balancing and geo-routing.
  • TCP = reliable & ordered but slower; UDP = fast & lossy. Pick based on whether late data is useful.
  • HTTP is stateless, which makes horizontal scaling easy. HTTP/2 multiplexes; HTTP/3 fixes TCP head-of-line blocking with QUIC.
  • TLS provides encryption, integrity and authentication; terminate it at the edge.

Check your understanding

A multiplayer game sends player positions 30 times per second. Which transport fits best?

Retransmitting an old position just delays newer ones. UDP lets the game drop stale updates and keep latency low.

You're migrating your site to a new data center and want DNS changes to take effect quickly. What should you do beforehand?

Resolvers cache records for the TTL. Lower it ahead of time so old cached answers expire quickly when you switch.

Which HTTP method is idempotent and replaces a resource entirely?

PUT sets the resource to exactly the given state — repeat it and the result is the same.

A client gets 503 Service Unavailable. What's the most likely meaning?

5xx means server-side problems. 503 specifically signals temporary unavailability, often with a Retry-After header.

What problem does HTTP/3 (QUIC) solve that HTTP/2 could not?

HTTP/2 multiplexes streams over one TCP connection, so one lost TCP packet blocks them all. QUIC runs over UDP with independent streams.
