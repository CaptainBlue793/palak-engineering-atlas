Layers: how networking is organised

Why do we need layers at all? Because sending a message across the world involves many separate problems: turning bits into radio waves, finding a path through thousands of routers, making sure nothing is lost, and agreeing what the message means. If one program had to solve all of them, every web browser would need to know about Wi-Fi chips. Layers let each problem be solved once. Your browser speaks HTTP and never cares whether you are on Wi-Fi, a phone network or a cable. Swap the bottom layer and the top ones keep working unchanged.

Networking is split into layers. Each layer solves one problem and relies on the layer below it. The textbook OSI model has 7 layers. In practice, engineers use the simpler TCP/IP model, which has 4:

LayerJobExamplesUnit
4 · ApplicationWhat the message meansHTTP, DNS, SMTP, WebSocketMessage
3 · TransportDeliver between programs (using ports), with or without a delivery guaranteeTCP, UDP, QUICSegment
2 · NetworkRoute between machines across networksIP (v4, v6)Packet
1 · LinkMove bits across one physical link (one “hop”), e.g. laptop to routerEthernet, Wi-FiFrame

You can see the layers directly in a packet capture. This is how a tool such as Wireshark or tcpdump shows one packet carrying the start of an HTTP request. Each indented line is one layer's header, wrapped around everything below it:

# one captured frame, 583 bytes on the wire
Ethernet II  src 3c:22:fb:1a:07:9e  dst 00:1b:21:3a:4f:10      ← link: next hop only
  IPv4       src 10.0.0.7  dst 93.184.216.34  TTL 64       ← network: which machine
    TCP      src port 51034  dst port 443  seq 1  ack 1   ← transport: which program, what order
      TLS    Application Data (encrypted, 517 bytes)       ← the HTTP request, sealed

This wrapping is called encapsulation. Notice what each device can read. Your Wi-Fi router reads only the Ethernet line. Internet routers read the IPv4 line. Only the server sees the TCP ports and, after decryption, the HTTP request. That is why a layer-4 load balancer can route on IPs and ports but cannot see URLs, while a layer-7 one must decrypt first (Chapter 5).

  1. Your browser writes an HTTP request: GET /index.html. It doesn't know or care how it will be delivered — that's another layer's job.
  2. TCP wraps it with a header holding the source & destination ports (e.g. 51034 → 443). It also adds sequence numbers — numbered labels on each piece — so the pieces can be put back in order and missing ones sent again.
  3. IP wraps that with the source & destination IP addresses. Routers (the machines that pass traffic along) only read this layer to decide where to send the packet next.
  4. Wi-Fi or Ethernet adds a frame around it. The frame holds the MAC address (the hardware ID of a network card) of the next stop, which is your router. It also adds an error check at the end.
  5. Everything becomes electrical signals or radio waves, hopping from router to router. Each router removes the frame, reads the IP header, and wraps it in a new frame for the next hop.
  6. The server's network card checks the frame, removes it, and passes the IP packet up a layer.
  7. IP confirms “this is addressed to me” and hands the segment up.
  8. TCP uses the port (443) to find which program should get this — the web server. It also puts the bytes back in the right order.
  9. The web server finally sees exactly what the browser wrote: GET /index.html. Notice that each layer only ever “talked” to the same layer on the other side.

Connections are the expensive part

From P4 you know a connection is named by four values: source IP, source port, destination IP, destination port. What matters for design is what a new connection costs before a single useful byte moves. Play the diagram: it shows a brand-new HTTPS request from a phone to a server 100 ms away (one round trip = 100 ms).

Now scale that up. An app server calls a database 2,000 times per second. If every call opened a new TCP connection with TLS, each would pay 2 extra round trips. Inside one data center a round trip is about 0.5 ms, so that is 1 ms of pure waiting per call, plus the CPU for 2,000 TLS handshakes a second on both sides. A connection pool keeps, say, 20 connections open and lends them out. Each call then pays only its own round trip. The pool also protects the database, which may only handle a few hundred open connections (Chapter 7).

When the four values run out

A connection needs a unique 4-tuple. When a proxy or NAT device opens many connections to one backend IP and port, three of the four values are fixed, so only the source port can vary. There are only about 28,000 ports in Linux's default ephemeral range (32768–60999). A closed connection also keeps its tuple reserved in the TIME_WAIT state for about 60 seconds, to catch late packets. So a proxy that opens and closes 1,000 short connections per second to one backend holds about 60,000 tuples in TIME_WAIT and runs out of ports. The symptom is confusing: random connection failures while CPU and memory look fine. The fix is the same as before: reuse connections instead of opening new ones.

🧱
Real-world use case: NAT gateway limits

Cloud NAT gateways let private servers reach the internet through a shared public address, so they hit exactly this limit. AWS documents that one NAT gateway supports up to 55,000 simultaneous connections to each unique destination. A fleet of workers calling one third-party API through one NAT gateway can hit that ceiling and see failed connections even though every server is healthy. Teams fix it with connection reuse, more NAT addresses, or by spreading calls over several gateways.

DNS as a traffic-routing tool

You know from P4 that DNS turns names into addresses. For a designer, the interesting part is that you control the answer. The authoritative server can return a different IP depending on who is asking, which region is healthy, or how you want to split traffic. That makes DNS the very first load balancer a request meets. Here is the full lookup once more, so you can see where the caches sit:

Resolving www.shop.comStep-through
  1. Browser cache → OS cache → hosts file. Each saved answer has a TTL (“time to live”: how long it may be reused). If a recent answer exists and its TTL hasn't run out, we're done instantly. Most lookups end here.
  2. No saved answer (a “cache miss”). The OS asks a recursive resolver: a server that does the lookup work for you. It might belong to your internet provider (ISP), or be a public one like 1.1.1.1. It checks its own big cache first.
  3. “Where's www.shop.com?” The root server doesn't know. But it knows who handles .com: “ask the .com TLD servers at a.gtld-servers.net”. (TLD = top-level domain, the last part of a name like .com or .org.)
  4. The TLD server doesn't know the IP either. But it knows which name servers are authoritative for shop.com — the ones that hold the official answer: “ask ns1.shop.com”.
  5. The authoritative name server is in charge of shop.com (its “zone”). It returns the real record: A 93.184.216.34, with a TTL of 300 seconds.
  6. The resolver saves the answer for the TTL and returns it. The OS and browser save it too. The whole walk usually takes 20–120ms. Next time, it takes about 0ms.

🧰 DNS as a system design tool

  • DNS load balancing: return several IPs and rotate their order, so traffic spreads out.
  • GeoDNS: return the IP of the data center nearest the user.
  • Failover: DNS checks that servers are healthy, and if one region fails it points users to a backup region.
  • TTL trade-off: a long TTL means fewer lookups but slow failover. A short TTL means changes spread fast, but more DNS traffic.

DNS is only one of several ways to send a user to the right place. They are often combined, so compare them:

A common production stack uses all of them: GeoDNS or anycast picks the region, and a load balancer in that region picks the server. For example, a user in Frankfurt resolves api.shop.com and gets the eu-central load balancer's IP; that load balancer spreads requests across 40 servers. If eu-central fails, health-checked DNS starts returning the eu-west address, and users move over as their cached answers expire.

Why is DNS built as a tree instead of one big server? Size and load. There are hundreds of millions of domain names and many billions of lookups a day. No single server could hold them all or answer them all. The tree splits the work: root servers only know who runs each ending (.com, .org), TLD servers only know who runs each domain, and each company runs (or rents) the servers for its own names. Caching at every level means the root servers see only a tiny share of all lookups.

The TTL trade-off, with numbers. Say shop.com has a TTL of 3,600 seconds (1 hour) and its server in one region dies. You update the record to point at a backup region. A resolver that cached the old answer one minute ago will keep handing out the dead IP for another 59 minutes. With a TTL of 60 seconds, the worst case drops to about a minute. The cost: resolvers now come back to your name servers up to 60 times more often. For most sites, 60–300 seconds is a sensible middle ground. (Some resolvers and apps keep answers longer than the TTL says, so DNS failover is never perfectly fast.)

📉
Real-world use case: when DNS itself disappears

On 4 October 2021, Facebook, Instagram and WhatsApp were unreachable for about six hours. A command run during routine maintenance accidentally disconnected Facebook's backbone network. Its DNS servers were built to withdraw their own network routes when they could not reach the data centers, so the rest of the internet could no longer reach Facebook's authoritative name servers at all. Every lookup for facebook.com failed, and resolvers worldwide saw a surge of retries. Engineers also lost the internal tools they would normally use to fix things remotely. The lessons: DNS is part of your critical path, and your recovery tools should not depend on the system that is down.

TCP vs UDP: what reliability costs

P4 covered the basic difference: TCP sets up a connection and guarantees every byte arrives, in order; UDP sends independent packets with no guarantees. For design, the question is what that guarantee costs when the network misbehaves.

What “reliable and ordered” costs you. Say the sender sends packets 1 to 5, and packet 3 is lost. The receiver gets 1, 2, 4 and 5. TCP hands 1 and 2 to the program, but it must hold 4 and 5 in a buffer, because it promised to deliver bytes in order. It waits until the sender notices the gap and re-sends 3, which takes at least one more round trip. Only then are 3, 4 and 5 handed over together. For a file download that pause is fine. For a video call, 4 and 5 were perfectly good and are now late. With UDP, the program gets 1, 2, 4 and 5 straight away and simply skips 3.

DNS is a good example of a UDP user. A lookup is one small question and one small answer, each usually fitting in a single packet. Setting up a TCP connection first would double the time. If the question gets lost, the client just asks again after a short timeout. (DNS does fall back to TCP when an answer is too big for one packet.)

Rule of thumb

If late data is useless (a video frame from 2 seconds ago, a player's old position), use UDP. If every byte matters (a bank transfer, a web page, a file), use TCP.

HTTP at scale: versions and status codes

HTTP's request format is covered in P5. Two of its properties shape every design in this course. First, HTTP is stateless: each request carries its own proof of identity (a cookie or token), so any server can answer any request, and you can add servers freely (Chapter 4). Second, status codes are machine-readable, so load balancers, retry libraries and CDNs act on them without understanding your app.

Status codes, read by machines

👆 Pick a status code.

You don't need to memorise every code. The first digit tells you who to blame and what to do next:

  • 2xx — success. The request worked. 200 OK for a normal answer, 201 Created when something new was made.
  • 3xx — go somewhere else. The thing you asked for is at another URL. The browser follows the Location header automatically.
  • 4xx — the client made a mistake. Bad input, not logged in, not allowed, not found. Sending the exact same request again will fail again, so don't retry it blindly. (429 Too Many Requests is the exception: wait, then retry.)
  • 5xx — the server failed. The request may have been fine. Retrying later, with a pause between tries, often works.

That split drives real design decisions. A load balancer counts 5xx responses to decide a server is sick. A retry library retries 503s but not 400s. Two codes deserve special attention because proxies create them, not your application:

HTTP/1.1 vs HTTP/2 vs HTTP/3

All three versions mean the same things (same methods, headers and codes). They differ in how they move the bytes. The big villain is head-of-line (HOL) blocking: one slow or lost item holds up everything queued behind it on the same connection. HTTP/1.1 suffers it per connection (one response at a time), HTTP/2 suffers it at the TCP level (one lost packet stalls every stream), and HTTP/3 avoids it by giving each stream its own ordering.

Which one should you use? In practice you rarely pick by hand: browsers and servers agree on the best version they both support. What matters for design is knowing where each one helps. HTTP/2 is a big win for pages that load many small files, because they all share one connection instead of queueing for about 6. HTTP/3 helps most on bad networks, such as phones on patchy mobile data, where packets get lost often. It also survives a network change (Wi-Fi to mobile) without reconnecting. Inside a data center, where packet loss is rare, HTTP/1.1 or HTTP/2 between services is usually fine.

HTTPS & TLS

HTTPS is HTTP sent through a TLS tunnel. TLS is the security layer. It gives you three guarantees:

🙈

Confidentiality

Traffic is encrypted, so anyone snooping on the Wi-Fi sees gibberish.

🧾

Integrity

If anyone changes the data on the way, it's detected and the connection is dropped.

🪪

Authentication

A certificate (a digital ID card) signed by a trusted authority proves you're really talking to shop.com.

HandshakeRound trips before the requestAt 150 ms awayNotes
TCP + TLS 1.23450 msOlder clients and servers

QUIC 0-RTT resume0 (data sent with the hello)~0 ms extraOnly safe for requests that can be replayed
Reused connection00 msKeep-alive or pooling; the cheapest option of all

Why two kinds of keys? Public-key maths (the certificate and the key-shares) lets two strangers agree on a secret over an open network, but it is slow. Symmetric encryption with one shared key is very fast, but both sides must already have the key. TLS uses each for what it is good at: the slow maths once, at the start, to agree on a key; then the fast symmetric encryption for every byte after that.

What it costs, in round trips. On a new connection you pay 1 round trip for the TCP handshake plus 1 for TLS 1.3, before the first HTTP request can be sent. The older TLS 1.2 needed 2 round trips, so 3 in total. For a user 150 ms away, moving from TLS 1.2 to 1.3 saves 150 ms on every new connection. Reusing an open connection (keep-alive) skips both handshakes completely, which is why it matters so much.

🎤
System design angle: TLS termination

Encryption costs CPU time. So large systems usually terminate TLS at the load balancer or at the edge: that's where the traffic gets decrypted. Inside the private network they use plain HTTP, or internal mTLS (TLS where both sides show certificates). A bonus: certificates only need to live in one place.

⚠️
Common mistakes
  • Ignoring round trips. A design that makes five calls in a row between far-apart regions can't be fast, however well each service is written. The minimum delay is set by physics (distance), not by your code.
  • Assuming DNS changes take effect instantly. Resolvers and clients keep cached answers. If your failover plan depends on a TTL change, you need to lower the TTL in advance.
  • Forgetting that TCP connections and TLS handshakes cost time. Reusing connections (keep-alive, connection pools) matters more than most tiny code tweaks.
🎤
Interview drill

Trade-off: When would you choose UDP over TCP, and what do you have to build yourself?

How a strong answer sounds
Choose UDP for live audio/video, gaming, DNS and QUIC-style protocols — anywhere a late packet is worthless and re-sending it would make things worse. You give up ordering, reliability and congestion control. So you build only the parts you need: sequence numbers for ordering; re-sending only important packets, or adding spare data so lost bits can be rebuilt (forward error correction); and your own speed control so you don't flood the network.

Debug: A page is slow only for users in Australia. How do you find out why?

How a strong answer sounds
Split the delay into its parts: DNS lookup, TCP+TLS handshake, time to first byte (TTFB — how long until the server starts answering), and download time. A high TTFB with a fast handshake means the main server (the origin) is far away or slow. A slow handshake means there's no nearby edge server doing TLS. A slow download points at bandwidth or big files. Each needs a different fix: a CDN with TLS at the edge, HTTP/3, smaller responses, or a copy of the data in a nearby region.

🧠 Key takeaways

  • Networking is layered: application → transport → network → link. Each layer wraps the data from the layer above.
  • A new HTTPS connection costs DNS + 2–3 round trips before the first request. Keep-alive, pooling and edge termination remove most of that; reusing connections also avoids port exhaustion.
  • DNS is a tree of servers, and answers are cached for their TTL. It can also spread load and send users to the nearest region.
  • TCP = reliable and in order, but slower. UDP = fast, but data can be lost. Pick based on whether late data is still useful.
  • HTTP is stateless, which makes it easy to add more servers. HTTP/2 sends many requests over one connection at once (multiplexing). HTTP/3 uses QUIC to fix TCP's head-of-line blocking.
  • TLS provides encryption, tamper detection and proof of identity. Terminate (decrypt) it at the edge.

Check your understanding

A multiplayer game sends player positions 30 times per second. Which transport fits best?

Re-sending an old position just delays the newer ones. UDP lets the game skip out-of-date updates and keep the delay low.

You're migrating your site to a new data center and want DNS changes to take effect quickly. What should you do beforehand?

Resolvers keep records for the length of the TTL. Lower it ahead of time, so old saved answers expire quickly when you switch.

Which HTTP method is idempotent and replaces a resource entirely?

PUT sets the resource to exactly the state you send. Repeat it and the result is the same.

A client gets 503 Service Unavailable. What's the most likely meaning?

5xx codes mean a problem on the server's side. 503 means the server is temporarily unavailable. It often comes with a Retry-After header saying when to try again.

What problem does HTTP/3 (QUIC) solve that HTTP/2 could not?

HTTP/2 sends many streams over one TCP connection, so one lost TCP packet blocks all of them. QUIC runs over UDP and keeps each stream independent.
