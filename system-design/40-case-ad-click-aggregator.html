Design an Ad Click Aggregator

Advertisers pay real money based on these numbers, so this system has an unusual mix of demands. It must take in a million events per second. It must show counts that are less than a minute old. And its billing numbers must be exactly right — even after machines crash, events arrive late, and bots try to inflate the totals. It's the practical showcase for everything in the streaming chapter.

  • Take in ad clicks at a million events per second
  • Add them up using time windows, watermarks and rules for late data
  • Avoid overloading one partition when an ad goes viral
  • Count each click exactly once, despite crashes and retries
  • Answer dashboard queries in milliseconds from pre-computed totals (rollups)
  • Check the live stream's numbers against a nightly recount, and bill from the recount

STEP 1 / 6

Requirements

🛠️ Functional

✓Record every ad impression and click with attributes (ad, campaign, country, device)
✓Advertiser dashboard: clicks over time, filtered and grouped, for any range up to a year
✓Totals per campaign per day that are accurate enough to bill from
✓Filter out fake and bot traffic; allow recounting old data after the rules change

📏 Non-functional

✓Scale: 10B events/day, peaking around 1M/s
✓Freshness: dashboards no more than ~1 minute behind
✓Billing counts each click exactly once; live dashboards can be approximate
✓99% of queries under 1 second, even across months of data
✓The click redirect itself must be instant — users must never wait for analytics

Why two accuracy levels? "Exactly right, within a minute, at a million events a second" is very hard to deliver in one path. So the requirements split the job: dashboards need to be fresh and can be off by a fraction of a percent for a few hours; invoices need to be exact and can wait until tomorrow. Spotting that split is the key move in this design — it lets the fast path be simple and the slow path be thorough.

The raw stream is huge, but the totals are small. That gap is the whole design. Keep raw events cheaply in object storage (like S3) so you can recount and audit them later. Answer every dashboard query from the small, pre-computed totals instead.

The arithmetic:

  • Average rate: 10B ÷ 86,400 s ≈ 115K events/s. Traffic follows daytime in big markets and spikes during major events, so peak is planned at ~1M/s — about 9× average.
  • Raw volume: 10B × 100 bytes = 1 TB/day. Stored as compressed columnar files (Parquet), repetitive fields like country and device shrink a lot, so ~4× compression gives ~250 GB/day, or ~90 TB/year.
  • Aggregated rows: a rollup row exists only for a (minute, ad, country, device) combination that actually had clicks. If ~140K such combinations are active in a typical minute, that is 140K × 1,440 minutes ≈ 200M rows/day. So 10B events become 200M minute rows (50× smaller), and hour rows are smaller again.
  • Kafka partitions: with 64 partitions, peak load per partition is 1M ÷ 64 ≈ 16K events/s, about 1.6 MB/s — easy for one consumer. Partition count sets the maximum number of consumers that can work in parallel, so you size it for peak with room to grow.
STEP 3 / 6

High-level design

Click → count → dashboard → invoiceStep-through
  1. The ad links to /click?ad=…&sig=…. The redirect service checks a signature so clicks can't be faked, gives the click a click_id, writes the event to a local buffer, and sends the user on to the advertiser's page with a 302 redirect — all within milliseconds. Nothing further down the pipeline makes the user wait.
  2. Events are sent to Kafka in batches, split across partitions to spread the load while keeping events with the same key in order. Kafka soaks up the 1M/s spikes, and several independent consumers can read the same stream (Chapter 14).
  3. Flink groups events by (ad_id, country, device), drops duplicates using click_id, filters out known bots, and counts them into 1-minute windows that don't overlap (tumbling windows). A watermark lets events arrive up to ~2 minutes late and still be counted in their own minute (Chapter 18).
  4. When a window closes, its total is upserted — inserted, or overwritten if it's already there — into an analytics (OLAP) store keyed by (minute, ad_id, dims). Upserting makes the write safe to repeat: recounting the same window overwrites the old total instead of adding to it.
  5. “Clicks per hour for campaign 42 in Germany, last 30 days” reads a few thousand pre-computed rows, instead of scanning billions of events.
  6. A second consumer saves the raw events to the data lake as Parquet files, grouped by hour (Chapter 9). This is the source of truth for audits, filling gaps, and any change to how you count.
  7. Overnight, a batch job recounts yesterday from the raw data, using the full fraud model, and compares the result with the streaming numbers. A small difference is expected and corrected. A large one pages someone. Advertisers are billed from the batch result.
λ
This is a lambda architecture — on purpose

A lambda architecture runs two paths over the same data. Streaming gives freshness: dashboards update within seconds. Batch gives correctness: it sees every event, including late ones, and can be re-run at any time. Running both costs more, but with money on the line it's worth it. If you only needed dashboards, one streaming path (the kappa architecture) would be simpler. If you only needed invoices, a nightly batch job alone would do.

Event time, watermarks and the one-minute promise

Each click carries the time it happened (event time). It reaches Flink a little later (processing time), and not always in order. The window for 12:00–12:01 must contain clicks that happened in that minute, whenever they arrive. A watermark is Flink's running estimate of "I have probably seen everything up to time T" — here, the latest event time seen minus 2 minutes.

A trace: a click at 12:00:59 arrives at 12:01:40. The 12:00 window is still open (the watermark is only around 11:59:40), so the click is counted in the right minute. How does that square with dashboards being only ~1 minute behind? The usual answer is to emit early and correct later: the window publishes a running total every few seconds while it is open, then a final total when the watermark passes. Because each publish is an upsert of the whole window total, the dashboard's number simply gets replaced with a slightly more accurate one — nothing is added twice.

STEP 4 / 6

Deep dive: hot partitions

Splitting the stream by ad_id puts all of one ad's events on one partition, in order. That works — until a Super Bowl ad becomes 40% of all traffic. The one consumer reading that partition can't keep up, it falls further and further behind, and dashboards for every ad on that partition go stale with it.

🧪 Go viral with key = ad_id: one partition falls far behind while seven consumers sit idle. Now switch to a salted key — the ad id plus a small random number, like “ad_99:3”. The viral ad now spreads across all partitions. Each one produces a partial count, and the aggregator adds those up by ad_id. The cost is that the ad's events are no longer in order. That's fine for counting, but not for events that must stay in sequence.

Merging the partial counts is a second, tiny step. Stage 1 counts per (ad_99:3, 12:00) on each partition. Stage 2 is keyed by the plain ad_99 and adds up at most 8 partial totals per minute — 8 small numbers, no matter how many millions of clicks the ad got. Most systems salt only keys detected as hot (the top few ads by rate), so the 99.9% of normal ads skip the extra step.

Why not simply add more partitions? Kafka sends every event with the same key to the same partition, whatever the partition count. With key = ad_99, going from 8 to 800 partitions still puts all of that ad's traffic on exactly one of them.

Deep dive: counting exactly once

Three separate things can push counts up or down: the client retrying, a consumer reprocessing events after a crash, and bots. Each needs its own defence.

🧪 Run everything with all three defences off, then turn them on one at a time. Deduplication fixes client retries. Idempotent upserts fix consumer replays: adding 1 each time would double-count, but writing the window's total again is harmless. And only filtering fixes bots — no amount of exactly-once machinery makes fake clicks disappear.

Why replays happen at all. Flink regularly takes a checkpoint: it saves its counting state together with the Kafka offsets (positions in each partition) it has read up to. After a crash it restores the last checkpoint and re-reads everything after those offsets. So every event since the last checkpoint — perhaps 30 seconds' worth — is processed a second time. Inside Flink that is fine, because the restored state is from before those events. The danger is outside Flink: anything already written to the database from those 30 seconds gets written again. An upsert of the window total makes that second write harmless; count = count + 1 does not.

Sizing the dedupe state. Remembering every click_id for 24 hours means holding up to 10B IDs. At ~16 bytes each that is ~160 GB — too big for memory on one machine, but fine when split across 64 Flink tasks (~2.5 GB each) in an on-disk state store such as RocksDB. You might ask: why not a Bloom filter, which is far smaller? Because a Bloom filter sometimes says "seen it" for an ID it has never seen. Here that would silently drop a real, billable click. For billing, a small exact store beats a tiny approximate one.

STEP 5 / 6

Deep dive: serving queries fast

Advertisers break the numbers down by campaign, country, device and time, over ranges from “last hour” to “this year”. Scanning raw events for each query is impossible. The answer is a ladder of rollups — totals per minute, per hour and per day — stored in a columnar database, which only reads the columns a query needs.

A sized example: "clicks per hour for campaign 42 over the last 30 days". From raw events, that means filtering through 30 × 10B = 300B events. From the hourly rollup, it is 30 × 24 = 720 rows per country/device combination — a few thousand rows in total, which a columnar store answers in milliseconds. The rule of thumb: pick the coarsest rollup that still gives the granularity asked for (per-hour charts read the hour table, even for a range of one day).

Why sums roll up but uniques don't. Clicks in an hour = the sum of clicks in its 60 minutes, exactly. But if user U clicks in minute 1 and again in minute 2, U is one of the uniques in both minutes; adding the minute counts counts U twice. The fix is to store something that can be merged rather than added — a HyperLogLog sketch per minute (a few KB), which estimates unique counts to within about 1–2%.

Rollups are built by chaining stream jobs (minute → hour → day), or by the analytics engine itself (Druid or ClickHouse materialized views). “Unique users” needs special handling: use HyperLogLog sketches (Chapter 20), small summaries that can be merged from minutes into hours. Plain counts of distinct users can't be added up that way, because the same user appears in several minutes.
STEP 6 / 6

Wrap-up

🤖

Invalid traffic

Use quick rules in real time: too many clicks per IP or device, timings no human could produce, networks known for bots. Then review more carefully offline with ML. Billing waits for a hold-back period, so credits for invalid clicks are worked out before the invoice goes out.

🔁

Reprocessing

Raw events live in the lake, and rollups are written with upserts that are safe to repeat. So you can replay a whole month through corrected logic and simply overwrite the affected windows. No hand-patching of counters.

⏱️

Late events

Phone apps upload clicks made offline hours later. Accept late events for a set period, send anything later than that to a side output, and let the nightly batch job fold them into the final numbers.

🌍

Multi-region

Count locally in each region, then add the partial counts together centrally. Addition doesn't care about grouping or order, so partial sums combine cleanly. HLL sketches merge the same way.

💾

Retention & cost

Keep raw events in fast storage for 30–90 days, then archive them. Keep minute rollups for 3 months, hour rollups for a year, and day rollups forever. Storage cost comes mostly from raw data; query cost comes from how fine-grained the rollup is.

🔭

Monitoring the pipeline

Watch how far behind each partition's consumer is, how delayed the watermark is, how many late events were dropped, how far streaming and batch numbers differ, and how fresh the rollups are. These are the signals that tell you the numbers can be trusted.

⚠️
Common mistakes
  • Doing analytics work inside the redirect. The user's click must be a fast 302. Everything else happens afterwards, in the background.
  • Adding to counters when reprocessing. Write the window's total instead, so replays don't double-count.
  • Deleting raw events. Without them you can't fill gaps, re-run corrected logic, or defend an invoice.

Interview drill

Design: Advertisers dispute a bill. What lets you answer them?

How a strong answer sounds
The raw events in the lake, grouped by hour, each with a click ID and the signature that proved the click was genuine. The nightly batch job recounts the invoice from that raw data using the current fraud model, and its output — not the streaming dashboard — is what the advertiser is billed for. You can show how far streaming and batch differed, how many events were filtered out as invalid, and replay any window to prove the number.

Scale: One advertiser's campaign is 60% of all traffic. What do you change?

How a strong answer sounds
Salt the partition key (ad_id:0–N) so that campaign's events spread across partitions, then add the partial counts back together by ad_id. Addition doesn't care about grouping, so partial totals merge cleanly. You lose ordering within that ad, which doesn't matter for counting. Also check the store the dashboards read: the same hot key can become one hot row there, so aggregate before writing, and consider giving the huge advertiser its own partition.

🧠 Key takeaways

  • Keep the user's click redirect instant. All the analytics happens later, behind Kafka.
  • Count events into windows based on when they happened, using watermarks. Expect late events and have a plan for them.
  • A very popular key overloads one partition. Salt the key and add the partial counts back together.
  • Counting exactly once needs two things: dropping duplicate event IDs, and writing window totals with upserts that are safe to repeat.
  • Filtering bots is a separate problem from exactly-once processing.
  • Serve dashboards from a ladder of rollups in a columnar analytics store. Use HLL sketches for unique-user counts.
  • Archive raw events so any change in logic can be replayed. Bill from a nightly recount that is checked against the streaming numbers.

Check your understanding

A single ad generates 60% of all clicks. Events are keyed by ad_id. What happens and what's the fix?

All events with the same key go to one partition. Salting spreads them out, and the partial counts can simply be added back together.

A consumer crashes and reprocesses the last minute of events. Why does writing the window total (upsert) beat incrementing a counter?

Writes that can be repeated safely make reprocessing safe. That's the foundation of getting exactly-once results.

Why keep raw events in a data lake when rollups answer every dashboard query?

Totals throw away detail. Raw data is the only way to answer a question you didn't plan for — or to prove an invoice is right.

A mobile SDK uploads clicks that happened 3 hours ago, past the 2-minute allowed lateness. What should happen?

Counting them in the current minute would put clicks in the wrong hour, and waiting 3 hours would make every dashboard 3 hours behind. The nightly batch job corrects the record instead.

Why can't you sum “unique users per hour” from 60 per-minute unique-user counts?

You can't add up counts of distinct things. Storing a HyperLogLog sketch per minute lets you merge them into any larger window.
