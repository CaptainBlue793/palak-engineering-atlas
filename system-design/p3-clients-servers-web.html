Clients, Servers & the Web

Almost every system in this course follows one pattern: something asks, something answers. This chapter makes that pattern precise — clients and servers, requests and responses, frontends and backends — and walks through what really happens when you open a web page. It ends with the idea that makes large websites possible at all: keeping servers stateless.

One pattern behind almost everything

A client sends a request: a message asking for something. A server does the work and sends back a response: a message with the answer. Your phone asking Instagram for your feed is a request. The feed coming back is the response. Almost every system design, from a URL shortener to a video platform, is a large arrangement of this one conversation.

One request, one responseDiagram

Three properties of this pattern shape everything that follows:

⏳

Every request takes time

The time from sending a request to receiving the full response is its latency. Much of system design is about keeping latency low while traffic grows.

🧾

Both sides follow a protocol

A protocol is an agreed set of rules for the conversation, so each side understands the other. On the web that's mostly HTTP (P5).

❓

Anything can fail

The request can be lost, the server can crash halfway, the response can arrive too late. A client must decide what to do when no answer comes — wait, retry, or give up.

Roles, not machines

“Client” means “the one who asks”. “Server” means “the one who answers”. These are roles in one conversation, not kinds of computer. The same program is often both at once.

A chain of requestsStep-through
  1. Your browser is the client. It sends a request to the shop's web app: “place this order”.
  2. The web app was a server a moment ago. Now it becomes a client, sending its own request to the payment service.
  3. The payment service is also both: a server to the web app, a client to its database.
  4. Each server answers the one that asked it, in reverse order. Your browser gets its response only after every step below it has finished.
  5. Your latency is the sum of every hop in the chain, and your request fails if any hop fails. That's why deep chains of services are slow and fragile, and why Chapter 15 spends time on where to draw service boundaries.

Frontend and backend

Web developers split an application into two halves, depending on where the code runs:

🎨 Frontend — runs on the user's device

Everything the user sees and touches. On the web, it's written in HTML (the structure of a page), CSS (how it looks) and JavaScript (how it behaves). A mobile app is also a frontend. The frontend can't be trusted: users can read and change any code that runs on their own device.

⚙️ Backend — runs on your servers

The code users never see: checking passwords, reading and writing the database, charging cards, sending emails. Written in any language (Java, Python, Go, JavaScript…). This is where rules are enforced and data is kept safe. System design is mostly about the backend.

The two halves talk through an API (application programming interface): a published list of requests the backend accepts and the responses it gives, such as “GET /api/orders returns your orders as JSON”. The same API often serves a website, an iPhone app and an Android app at once. You'll learn to design APIs in Chapter 3.

🛡️
Never trust the client

A frontend might hide the “delete” button from normal users, but anyone can send the delete request directly with a tool like curl. Every check that matters — is this user logged in, may they see this order, is this price correct — must happen again on the backend. Chapter 11 builds on this rule.

What happens when you open a web page

Typing an address and pressing Enter sets off a surprisingly long chain of events. Here is the whole journey at a high level. Each step is a topic of its own later on, so for now just get the order right.

From URL to pixelsStep-through
  1. The browser has a name, shop.com, but networks deliver to numeric addresses. It asks DNS, the internet's phone book, for the IP address (P4).
  2. It opens a connection to that address and sets up encryption (the S in HTTPS). This takes a couple of round trips before any real data moves.
  3. The browser sends an HTTP request: GET / — “give me the home page” (P5).
  4. The web server runs backend code. It might ask the database for today's featured products, then build an HTML page containing them.
  5. The HTML comes back. The browser starts reading it and discovers it also needs a stylesheet, some JavaScript files and a dozen images.
  6. Those files are the same for every visitor, so they usually come from a CDN — servers placed close to users around the world (Chapter 6). Many downloads run in parallel.
  7. The JavaScript runs in the browser and may call the backend's API for more data — your cart count, recommendations — and update the page.
  8. The browser combines HTML and CSS into a layout and paints it on screen. A “simple page load” involved dozens of requests to several kinds of server — and every one is a place where latency adds up or something fails.

Static vs dynamic content

Not all responses are created equal. Sorting them into two kinds tells you how to serve each cheaply.

Static contentDynamic content
What it isFiles that are the same for everyone: images, CSS, JavaScript, fonts, videos.Responses built fresh for each request: your feed, your cart, search results.
Who produces itMade once, stored as files.Backend code, usually reading a database.
How to serve it fastCache it everywhere — in the browser, on a CDN near the user.Make the code and database fast; cache the parts that repeat.
Typical share of bytesMost of the bytes on a typical page.Fewer bytes, but most of the backend's work.

A good design pushes as much as possible into the static column. Every image served by a CDN is a request your servers never see. That's why case studies such as video streaming (Chapter 32) move nearly all the bytes to CDNs and keep the backend for the small, personal parts.

State: why servers stay stateless

State is anything the system remembers between requests: who you are, what's in your cart, which page of results you're on. Where that state lives turns out to be one of the most important decisions in any design.

HTTP itself is stateless: each request is independent, and the server isn't required to remember anything from the previous one. So how does a website know you're logged in? The usual answer:

  1. When you log in, the server creates a session — a small record like “session 8f3a… belongs to user 42” — and stores it somewhere.
  2. It sends your browser a cookie containing the session ID. A cookie is a small piece of text the browser stores and automatically sends back with every request to that site.
  3. On each later request, the server reads the cookie, looks up the session, and knows who you are.

The crucial question is where the session record is stored. Big sites run many identical copies of the web server behind a load balancer, which spreads requests across them. Try both options below.

Where do sessions live?Simulator
🗄️ Shared session store (e.g. Redis or a database): empty
The load balancer sends each request to the next server in turn (round-robin). Log in, then send a few requests in each mode.

Keeping state out of the web servers is called making them stateless, and it's the foundation of scaling out: any server can handle any request, you can add or remove servers freely, and a crash loses nothing but the requests in progress. The state still exists — it has just moved into a dedicated store built to keep it safe. Chapter 4 and Chapter 5 build directly on this.

Other ways programs talk

Request–response, where the client asks and waits, is the default. But some problems need other patterns. You'll meet all of these properly later; here's the map.

PatternHow it worksGood forWhere it's taught
Request–responseClient asks, waits for the answer.Almost everything: loading pages, API calls.Ch 3
PollingClient asks again every few seconds: “anything new?”Simple status checks. Wasteful when nothing changes.Ch 3
Push (WebSockets, streaming)A connection stays open, so the server can send messages whenever something happens.Chat, live scores, collaborative editing, streaming AI answers.Ch 28
WebhooksYour server gives another company a URL; they call it when an event happens.“Payment succeeded” notifications from a payment provider.Ch 37
Message queueThe sender drops a message in a queue and moves on; a worker processes it later.Slow or bursty work: sending emails, resizing images, video transcoding.Ch 14

The key distinction is synchronous (the caller waits for the result) versus asynchronous (the caller hands the work off and continues). Asynchronous designs absorb bursts and survive slow workers, at the cost of results arriving later. Choosing between them is one of the most common trade-offs in this course.

How a system grows

Most systems start tiny and grow in predictable stages. Knowing the stages helps you read any architecture diagram: you'll recognise which stage it's at and which problem each new box solves.

One server does everything

Web app and database on one machine. Cheap and simple, and perfectly fine for many real products. But if that machine dies, everything is down.

Separate the database

The database moves to its own machine, so each can be sized for its job. The web app is now a client of the database over the network.

Several web servers + a load balancer

Stateless web servers, copied several times behind a load balancer. One crash no longer takes the site down, and you add servers as traffic grows.

Add caches and a CDN

A cache in memory absorbs repeated database reads; a CDN serves static files near users. Most requests now never reach the database.

Replicate and split the data, add queues

Database copies for reads and safety, data split across machines when it no longer fits, and queues for slow background work. This is where the rest of the course lives.

Chapter 1 walks through this growth story in detail, with the reasoning at each step.

⚠️
Common mistakes
  • Thinking “server” is a kind of machine. It's a role. Most backend services are servers to one side and clients to the other.
  • Trusting checks done in the frontend. Anything on the user's device can be bypassed. Enforce rules on the backend.
  • Keeping sessions in one web server's memory. Behind a load balancer, users get randomly logged out, and a restart logs everyone out.
  • Serving static files from your app servers. Put them on a CDN and let your servers focus on dynamic work.
  • Forgetting that latency adds up along a chain. Five services called one after another, at 40 ms each, is 200 ms before any other work.

Interview drill

Explain it simply: What does it mean for a web server to be stateless, and why do we want that?

How a strong answer sounds
A stateless server keeps nothing about a user between requests in its own memory — every request carries or points to what's needed, like a session ID in a cookie, and the session itself lives in a shared store or database. That means any copy of the server can handle any request. So a load balancer can spread traffic freely, we can add or remove servers as load changes, and if one crashes users don't lose their login or cart.

Walk through it: What happens, at a high level, when someone types a web address and presses Enter?

How a strong answer sounds
DNS turns the name into an IP address. The browser opens a connection to that address and sets up TLS encryption. It sends an HTTP GET for the page. The backend may query a database and returns HTML. The browser parses it and fetches CSS, JavaScript and images — usually from a CDN, in parallel. JavaScript may then call APIs for personal data. Finally the browser lays out and paints the page. Each step adds latency and is a place where caching or failure handling matters.

🧠 Key takeaways

  • Clients send requests; servers send responses. “Client” and “server” are roles, and most backend services play both.
  • Latency adds up along a chain of calls, and any failing link fails the whole request.
  • The frontend runs on the user's device and can't be trusted; the backend runs on your servers and enforces the rules. They talk through an API.
  • Loading a page means DNS, a secure connection, the HTML request, backend work, then many parallel fetches for static files and API data.
  • Static content is the same for everyone and belongs on a CDN; dynamic content is built per request by the backend.
  • Keep web servers stateless: sessions go in a shared store, identified by a cookie, so any server can handle any request.
  • Besides request–response there are polling, push connections, webhooks and message queues — synchronous vs asynchronous is a core trade-off.

Check your understanding

A web server receives a request from a browser and then queries a database. In the conversation with the database, the web server is…

“Client” means the side that asks. When the web server asks the database for data, it is the client in that conversation, even though it's a server to the browser.

Your site hides the “refund” button from customers in the frontend. Is that enough to stop customers issuing refunds?

Code on the user's device is under the user's control. They can send any request with a tool like curl. The backend must check, on every request, that the caller is allowed to do what they ask.

You run 5 web servers behind a round-robin load balancer, and each keeps login sessions in its own RAM. What will users experience?

Each server only knows the sessions it created. With round-robin, most requests go to other servers, which don't recognise the session. Moving sessions to a shared store (or signed tokens) makes the servers stateless and fixes it.

Which of these is best served from a CDN?

Static files are identical for every visitor, so copies can sit on servers near users worldwide. Carts, login results and balances are personal and change, so they come from the backend.

A photo app must create five resized versions of every upload. Resizing takes 3 seconds. What pattern keeps the upload fast for the user?

Slow work that the user doesn't need to wait for is a classic job for a message queue. The upload returns quickly, and background workers do the resizing at their own pace — absorbing bursts too.
