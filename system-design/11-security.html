Security, Authentication & Authorization

A system that is fast, scalable and available but leaks every user's data is a failure. Security isn't a feature you bolt on at the end — it's a set of design decisions about identity, trust boundaries, secrets and blast radius that shape the architecture from day one.

  • Think in threat models, trust boundaries and least privilege
  • Store passwords correctly with salted, slow hashes
  • Compare server sessions with JWTs — and break a JWT
  • Walk through OAuth 2.0 and OpenID Connect with PKCE
  • Design authorization with RBAC, ABAC and relationship-based models
  • Encrypt data in transit and at rest with envelope encryption
  • Defend against injection, XSS, CSRF, SSRF and DDoS

The security mindset

Security engineers ask one question relentlessly: “what could an attacker do here?” Start with what you're protecting — the CIA triad — then find where untrusted input crosses into trusted territory.

🤫

Confidentiality

Only authorized parties can read data. Broken by leaks, weak access control, unencrypted backups.

🧾

Integrity

Data can't be modified undetected. Broken by tampering, injection, forged tokens.

🟢

Availability

Legitimate users can still use the system. Broken by DDoS, resource exhaustion, ransomware.

🔑 Least privilege

Every user, service and API key gets the minimum permissions needed, for the shortest time. The image-resizing service should be able to read uploads/, not drop the users table.

🧅 Defense in depth

Assume each layer will eventually fail. WAF and input validation and parameterized queries and a DB user without DROP rights and encrypted backups.

🚧 Zero trust

Being “inside the network” grants nothing. Every request is authenticated and authorized — service to service included (mTLS + identity). The old castle-and-moat model collapses after one phished laptop.

💥 Minimize blast radius

Isolate tenants, segment networks, scope credentials per service, and shorten token lifetimes, so one compromise can't cascade into everything.

AuthN vs AuthZ: the hotel

Authentication is the front desk checking your passport: who are you? Authorization is your key card opening room 412 but not 413 or the staff room: what are you allowed to do? Confusing the two is behind many breaches — a perfectly authenticated user fetching another user's data is an authorization bug.

Storing passwords

Assume your database will leak one day. The question is whether attackers can recover passwords from it — and since people reuse passwords, that means access to their email and bank too.

Plaintext never

A leak is instantly game over for every user.

Encrypted no

Reversible by design. The key usually lives next to the data and leaks with it.

Fast hash (MD5, SHA-256) no

Identical passwords produce identical hashes, and GPUs compute billions of SHA-256 hashes per second. Precomputed rainbow tables reverse common passwords instantly.

Salted, slow, memory-hard hash yes

Argon2id (preferred), scrypt or bcrypt with a unique random salt per user. The salt kills rainbow tables; deliberate slowness (and memory cost) makes each guess expensive. Optionally add a pepper — a secret key held outside the database.

Beyond passwords

MFA (TOTP apps, push) blocks most credential-stuffing attacks. Passkeys (WebAuthn/FIDO2) go further: the device holds a private key per site and signs a challenge, so there's no shared secret to phish or leak from your database. Increasingly the best answer to “how do you store passwords?” is “we mostly don't”.

Sessions vs tokens

HTTP is stateless, so after login the client needs something to prove identity on every request. There are two families.

On login the server creates a random session ID, stores session_id → {user_id, expires} in Redis or a DB, and sends it as a cookie. Every request looks the session up.

Set-Cookie: sid=b1f9c2e0a7…; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
Strengths
  • Instant revocation: delete the row → logged out everywhere
  • Tiny cookie, no secrets in the client
  • Simple and battle-tested
Weaknesses
  • A lookup on every request (fast with Redis)
  • Session store must be shared by all servers (Chapter 4)
  • Awkward for third-party APIs and mobile clients

A JSON Web Token packs claims (user ID, roles, expiry) into a signed, base64url-encoded string. Any service with the verification key can validate it without a database call.

Strengths
  • Stateless verification — scales across many services
  • Carries identity between microservices
  • Asymmetric signing (RS256/ES256): only the auth server can issue, everyone can verify
Weaknesses
  • Can't be revoked before expiry without extra state
  • Payload is readable by anyone — it's signed, not encrypted
  • Easy to misuse: alg: none, weak secrets, stored in localStorage (XSS-stealable)

OAuth 2.0 & OpenID Connect

OAuth 2.0 lets a user grant an app limited access to their data on another service without sharing their password (“Allow PhotoPrinter to read your Google Photos”). OpenID Connect (OIDC) adds an identity layer on top — an id_token saying who logged in — which powers “Sign in with Google/Apple/Microsoft” and enterprise SSO.

Authorization Code flow with PKCEStep-through
  1. The app generates a random code_verifier and its hash, the code_challenge (PKCE), plus a random state value to prevent CSRF. It stores both privately.
  2. The browser is redirected to /authorize?response_type=code&client_id=…&scope=photos.read openid&redirect_uri=…&state=…&code_challenge=…. The app never sees the password.
  3. Google authenticates the user (password, passkey, MFA) and shows a consent screen: “PhotoPrinter wants to view your photos.” Scopes limit exactly what's granted.
  4. Google redirects to the registered redirect_uri with a short-lived authorization code and the same state. The app checks state matches. The code alone is useless to anyone who intercepts it…
  5. …because the app's server exchanges it directly with Google, sending the original code_verifier. Google hashes it and checks it matches the earlier challenge — proving the same client started the flow. It returns an access token, a refresh token and (with OIDC) an id_token.
  6. Authorization: Bearer eyJ…. The photos API validates the token's signature, expiry, audience and scope (photos.read — so deleting photos is refused). When it expires, the refresh token quietly gets a new one.

🧭 Which grant when?

Authorization Code + PKCE: web, mobile and single-page apps (the default for users). Client Credentials: service-to-service with no user. Device Code: TVs and CLIs. Implicit and password grants: deprecated — don't use.

🏢 SSO in the enterprise

Companies centralize identity in an IdP (Okta, Entra ID, Google Workspace). Apps trust it via OIDC or the older XML-based SAML, and user provisioning flows via SCIM. Offboarding an employee in one place revokes access everywhere.

Authorization models

Once you know who someone is, you decide what they can do. Authorization must be enforced on the server, on every request, for every object — the most common critical API vulnerability (OWASP API #1) is Broken Object Level Authorization: checking the user is logged in but not that invoice 1002 is theirs.

Centralize policy, enforce locally

At scale, teams extract authorization into a dedicated service or library (a policy decision point) so rules are consistent and auditable, while each service enforces the decision in its own request path. Zanzibar-style systems cache aggressively and use consistency tokens to avoid the “new enemy problem” — a user removed from a doc seeing edits made after removal.

In transit: TLS everywhere

TLS 1.3 on every external connection (Chapter 2), HSTS to prevent downgrade, and mTLS between internal services so both sides prove identity with certificates. Service meshes automate certificate issuance and rotation (e.g. SPIFFE identities).

💾

At rest: envelope encryption

Disks, databases, backups and object storage are encrypted. Keys never sit next to the data: a KMS/HSM holds master keys that never leave it, and only wraps smaller data keys.

Envelope encryption with a KMSStep-through
  1. The service calls GenerateDataKey. IAM policy checks this service is allowed to use this master key — every call is audit-logged.
  2. KMS returns the data key (DEK) in plaintext and encrypted under the master key.
  3. The service encrypts the record/file locally with AES-GCM using the plaintext DEK — no network round trip per byte — then wipes the plaintext key from memory.
  4. Storage holds the ciphertext next to the encrypted DEK. Stealing the whole disk gives an attacker nothing usable. To read, the service asks KMS to decrypt the DEK (authorized + logged), then decrypts locally.
  5. Rotating the master key only requires re-wrapping small data keys, not re-encrypting petabytes. Use one DEK per tenant and you can delete a tenant's key to make all their data unrecoverable — handy for GDPR erasure.
🗝️
Secrets management

Never hard-code credentials or commit .env files. Use a secrets manager (Vault, AWS Secrets Manager), inject at runtime, rotate automatically, prefer short-lived credentials via workload identity (no static keys at all), and run secret scanning in CI. Leaked keys on public repos are exploited within minutes.

Common attacks and defenses

📜

XSS

Cross-site scripting — tap to flip
Attacker content like <script> runs in other users' browsers and steals tokens. Defend: context-aware output encoding (frameworks do it by default), a strict Content-Security-Policy, HttpOnly cookies so scripts can't read sessions.
🎭

CSRF

Cross-site request forgery
A malicious site makes the victim's browser send an authenticated request (cookies attach automatically). Defend: SameSite=Lax/Strict cookies, anti-CSRF tokens, and never change state on GET.
🛰️

SSRF

Server-side request forgery
“Fetch this URL” features get pointed at internal addresses like the cloud metadata endpoint 169.254.169.254 to steal credentials. Defend: allowlists, block private IP ranges after DNS resolution, egress proxies, IMDSv2.
🔢

IDOR / BOLA

Insecure direct object references
Changing /orders/1001 to /orders/1002 shows someone else's order. Defend: check ownership on every object access; unguessable IDs help but are not authorization.
🧨

Credential stuffing

Reused leaked passwords
Bots try millions of leaked email/password pairs. Defend: MFA/passkeys, rate limits per account and IP, breached-password checks, bot detection, anomaly alerts on impossible travel.
📦

Supply chain

Compromised dependencies
A malicious package or build step ships backdoors to you. Defend: lockfiles and pinned versions, dependency scanning, signed artifacts and provenance (SLSA, Sigstore), minimal base images, SBOMs.

Surviving DDoS and abuse

A distributed denial-of-service attack floods you with traffic from thousands of compromised machines — modern attacks exceed millions of requests per second and hundreds of gigabits. You don't out-muscle that with your own servers; you absorb it at the edge in layers.

Anycast edge network L3/L4

A CDN/DDoS provider (Cloudflare, AWS Shield, Akamai) announces your IPs from hundreds of locations, spreading volumetric floods (UDP amplification, SYN floods) across massive capacity and scrubbing them before they reach you.

Web application firewall L7

Blocks known attack patterns (SQLi/XSS signatures), bad reputation IPs, and anomalous request shapes. Hide your origin IP so attackers can't bypass the edge.

Rate limiting & bot management

Per IP, per API key, per account (Chapter 15). Challenge suspicious clients (JS challenges, proof-of-work, CAPTCHA) instead of blocking outright.

Protect expensive endpoints

Login, search, and anything that hits the DB hard get stricter limits, caching, and queue-based load shedding (Chapter 16) so the core keeps working under attack.

Autoscaling — with a budget cap

Scale to absorb bursts, but cap it: an attack can also be a “denial of wallet” on pay-per-use infrastructure.

🏢 Multi-tenant isolation

SaaS platforms must guarantee tenant A never sees tenant B's data. Options from cheapest to strongest: a tenant_id column enforced by row-level security → schema per tenant → database per tenant → dedicated infrastructure (cells, Chapter 22) for the largest or most regulated customers.

📜 Audit logging & compliance

Record who did what, to which resource, when, from where — append-only, tamper-evident, stored separately from app data. Regulations (GDPR, HIPAA, PCI DSS, SOC 2) shape retention, data residency, encryption and access reviews.

⚠️
Common mistakes
  • Checking authentication but not authorization. The most common critical API bug: a logged-in user reading another user's object by changing an ID.
  • Rolling your own crypto or token format. Use vetted libraries and standard flows; the failure modes of homemade schemes are silent.
  • Treating internal networks as trusted. One compromised service or laptop turns a flat network into full access — authenticate service-to-service too.
🎤
Interview drill

Design: A user pastes a URL and your service fetches it to generate a preview. What could go wrong?

How a strong answer sounds
SSRF: the URL can point at internal addresses — 169.254.169.254 for cloud credentials, internal admin panels, or localhost. Defences: resolve DNS first and block private/link-local ranges (re-checking after redirects to defeat DNS rebinding), allowlist schemes and ports, fetch through an egress proxy in an isolated network with no credentials, cap size and time, and never reflect raw response bodies back to the user.

Explain: Where do you store the session token in a web app, and why?

How a strong answer sounds
An HttpOnly, Secure, SameSite=Lax cookie: JavaScript can't read it, so XSS can't exfiltrate it, and SameSite blocks most CSRF. localStorage is convenient for SPAs but any XSS becomes full account takeover. If you need cross-site API calls, use short-lived access tokens in memory plus a refresh token in an HttpOnly cookie, and add anti-CSRF tokens for state-changing requests.

🧠 Key takeaways

  • Threat-model trust boundaries; apply least privilege, defense in depth and zero trust.
  • Authentication proves identity; authorization decides access — check authorization on every object, server-side.
  • Hash passwords with Argon2id/bcrypt/scrypt and a unique salt; prefer MFA and passkeys.
  • Sessions revoke instantly; JWTs verify statelessly but can't be revoked — pair short-lived access tokens with rotating refresh tokens.
  • OAuth 2.0 delegates access with scoped tokens; OIDC adds identity. Use Authorization Code + PKCE.
  • RBAC for roles, ABAC for attribute rules, ReBAC for sharing and hierarchies.
  • TLS/mTLS in transit; envelope encryption with a KMS at rest; secrets in a manager, never in code.
  • Parameterize queries, encode output, use SameSite cookies, block SSRF, and absorb DDoS at the edge.

Check your understanding

Why add a unique random salt to each password before hashing?

Salts force attackers to crack each user separately. Slowness (Argon2id/bcrypt) then makes each guess expensive — you need both.

An employee is fired and their JWT access token is valid for 24 more hours. What's the best design fix?

JWTs can't be un-issued. Short lifetimes bound the exposure, and revoking the server-side refresh token stops renewal.

In the OAuth Authorization Code flow with PKCE, what stops an attacker who intercepts the authorization code?

The authorization server verifies that hash(code_verifier) equals the code_challenge sent at the start of the flow.

A logged-in user changes /api/invoices/1001 to /1002 and sees another company's invoice. What kind of bug is this?

The user is authenticated correctly; the server failed to check they're authorized for that specific object.

Why use envelope encryption instead of sending all data to the KMS to encrypt?

Envelope encryption avoids per-byte network calls and makes master-key rotation cheap, while every key unwrap stays authorized and audited.
