Security, Authentication & Authorization

A system can be fast, scalable and always up. If it leaks every user's data, it has still failed. Security isn't a feature you add at the end. It's a set of design choices that shape the architecture from day one: who users are (identity), where you stop trusting input (trust boundaries), how you guard keys and passwords (secrets), and how much damage one break-in can do (blast radius).

  • Think in threat models, trust boundaries and least privilege
  • Store passwords correctly with salted, slow hashes
  • Compare server sessions with JWTs — and break a JWT
  • Walk through OAuth 2.0 and OpenID Connect with PKCE
  • Design authorization with RBAC, ABAC and relationship-based models
  • Encrypt data in transit and at rest with envelope encryption
  • Defend against injection, XSS, CSRF, SSRF and DDoS

The security mindset

Security engineers ask one question over and over: “what could an attacker do here?” Start with what you're protecting. The classic checklist is the CIA triad below. Then find every place where untrusted input (from users, the internet, other companies) enters the trusted parts of your system.

🤫

Confidentiality

Only the right people can read the data. Broken by leaks, weak access control and unencrypted backups.

🧾

Integrity

Nobody can change data without it being noticed. Broken by tampering, injection and forged tokens.

🟢

Availability

Real users can still use the system. Broken by DDoS (flooding with traffic), running out of resources, and ransomware.

🔑 Least privilege

Every user, service and API key gets only the permissions it truly needs, for as short a time as possible. The image-resizing service should be able to read uploads/. It should not be able to delete the users table.

🧅 Defense in depth

Assume every layer will fail someday, so stack several. A firewall (WAF) and input checks and parameterized queries and a DB user that can't DROP tables and encrypted backups.

🚧 Zero trust

Being “inside the network” earns no trust. Every request must prove who it is and be checked for permission, including calls between your own services (mTLS + identity). The old castle-and-moat model (hard outside, soft inside) collapses after one phished laptop.

💥 Minimize blast radius

Limit the damage one break-in can do. Isolate customers (tenants), split networks into zones, give each service its own narrow credentials, and keep tokens short-lived.

Threat modeling means listing what could go wrong before an attacker finds it. Draw how data flows through your system. Mark every trust boundary, where data moves from one trust level to another (internet → gateway, service → database, your code → third-party API). Then check each boundary against STRIDE, a checklist of six threat types:

A tiny example: a "download invoice as PDF" feature. The boundary is internet → your API. Walking STRIDE: could someone spoof another user (stolen cookie)? Tamper with the invoice ID in the URL? Deny sending a refund (is it logged)? Disclose another customer's invoice? Take the service down by requesting 10,000 PDFs a second? Elevate to admin by adding ?role=admin? Each "yes, maybe" becomes a task: an ownership check, a rate limit, an audit log entry.

AuthN vs AuthZ: the hotel

Authentication (AuthN) is the front desk checking your passport: who are you? Authorization (AuthZ) is your key card opening room 412, but not 413 or the staff room: what are you allowed to do?

Mixing the two up is behind many breaches. If a properly logged-in user can fetch another user's data, that is an authorization bug.

Storing passwords

Assume your database will leak one day. The question is whether attackers can recover the passwords from it. People reuse passwords, so a recovered password often unlocks their email and bank too.

Plaintext never

One leak and every user's password is exposed at once.

Encrypted no

Encryption is reversible by design. The key usually lives next to the data and leaks along with it.

Fast hash (MD5, SHA-256) no

A hash is a one-way fingerprint of the data. But the same password always gives the same hash, and GPUs compute billions of SHA-256 hashes per second. Rainbow tables (huge precomputed lists of password → hash) reverse common passwords instantly.

Salted, slow, memory-hard hash yes

Use Argon2id (preferred), scrypt or bcrypt, with a unique random salt per user. A salt is random text mixed into the password before hashing. It makes rainbow tables useless. The hash is also deliberately slow and memory-hungry, so each guess costs the attacker a lot. Optionally add a pepper: a secret key kept outside the database.

How login works with a salted hash: at sign-up you generate a random salt (say 16 bytes), compute hash = Argon2id(password, salt), and store both the salt and the hash — the salt isn't secret. At login you fetch that user's salt, hash the typed password with it, and compare the result to the stored hash. You never need the original password back, which is why a one-way hash is enough.

Why "slow" is the whole point. Take an 8-character password drawn from letters and digits: 628 ≈ 218 trillion possibilities. At about 10 billion SHA-256 guesses per second, trying them all takes around 6 hours. At about 5,000 bcrypt (cost 12) guesses per second, it takes over 1,000 years. Your server only computes one hash per login, so a hash taking 100 ms costs you almost nothing — but it costs the attacker billions of times over.

🔐
Beyond passwords

MFA (multi-factor authentication, such as a code from an authenticator app or a push prompt) blocks most attacks that replay leaked passwords. Passkeys (WebAuthn/FIDO2) go further. Your device keeps a private key for each site and uses it to sign a challenge. There's no shared secret that can be phished or leaked from your database. More and more, the best answer to “how do you store passwords?” is “we mostly don't”.

Sessions vs tokens

HTTP is stateless: the server doesn't remember you between requests. So after you log in, your client must send some proof of identity with every request. There are two main ways to do that.

When you log in, the server creates a random session ID. It stores session_id → {user_id, expires} in Redis or a database, and sends the ID to your browser as a cookie. On every request, the server looks the session up. It's like a coat-check ticket: the ticket itself means nothing, the server holds the real record.

Set-Cookie: sid=b1f9c2e0a7…; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
Strengths
  • Instant revocation: delete the row and the user is logged out everywhere
  • Tiny cookie, no secrets stored on the client
  • Simple and proven over decades
Weaknesses
  • A lookup on every request (fast with Redis)
  • All servers must share the session store (Chapter 4)
  • Awkward for third-party APIs and mobile apps

A JSON Web Token (JWT) packs facts about the user, called claims (user ID, roles, expiry time), into a signed text string (base64url-encoded). Any service with the verification key can check it without calling a database. It's like a signed concert wristband: staff just check it's genuine, they don't phone the box office.

A JWT is three parts joined by dots: header.payload.signature. The header says which algorithm signed it (e.g. {"alg":"RS256"}), the payload holds the claims (e.g. {"sub":"42","role":"viewer","exp":1767225600}), and the signature is computed over the first two parts with the auth server's key. Change even one character of the payload — say viewer to admin — and the signature no longer matches, so the API rejects it. The exp claim is a Unix timestamp (seconds since 1970); the API refuses the token once that moment has passed.

Strengths
  • Checked without shared state, so it scales across many services
  • Carries the user's identity between microservices
  • With asymmetric signing (RS256/ES256), only the auth server can create tokens, but everyone can verify them
Weaknesses
  • Can't be cancelled before it expires, unless you add extra state
  • Anyone can read the contents. It's signed, not encrypted
  • Easy to misuse: accepting alg: none, weak secrets, or storing it in localStorage where XSS can steal it

OAuth 2.0 & OpenID Connect

OAuth 2.0 lets a user give an app limited access to their data on another service, without sharing their password. Think “Allow PhotoPrinter to read your Google Photos”. It's like a valet key: it starts the car but doesn't open the glovebox.

OpenID Connect (OIDC) adds identity on top. It returns an id_token that says who logged in. That powers “Sign in with Google/Apple/Microsoft” and company-wide single sign-on (SSO).

Why so many steps in the flow below? Each one closes a specific hole. The user types the password only at Google, so the app can't steal it. The browser only ever carries a short-lived code, not a token, because browser URLs end up in history, logs and referrer headers. The real tokens are handed over on a direct server-to-server call. PKCE proves the app redeeming the code is the one that started the flow, and state proves the redirect back belongs to a login this browser actually began.

Authorization Code flow with PKCEStep-through
  1. The app creates a random secret, the code_verifier, and its hash, the code_challenge. This pair is PKCE (Proof Key for Code Exchange). It also creates a random state value to block CSRF (forged requests from other sites). It keeps both private.
  2. The browser is redirected to /authorize?response_type=code&client_id=…&scope=photos.read openid&redirect_uri=…&state=…&code_challenge=…. The user types their password at Google, so the app never sees it.
  3. Google checks who the user is (password, passkey, MFA). Then it shows a consent screen: “PhotoPrinter wants to view your photos.” Scopes (named permissions, such as “read photos”) limit exactly what is granted.
  4. Google sends the browser back to the app's registered redirect_uri. It carries a short-lived authorization code and the same state. The app checks that state matches. The code alone is useless to anyone who intercepts it…
  5. …because the app's server trades it in directly with Google, and must also send the original code_verifier. Google hashes it and checks it matches the earlier challenge. That proves the same client started the flow. Google then returns an access token, a refresh token and (with OIDC) an id_token.
  6. The app sends Authorization: Bearer eyJ…. The photos API checks the token's signature, expiry, audience (who it's meant for) and scope. The scope is photos.read, so a delete request is refused. When the token expires, the refresh token quietly gets a new one.

🧭 Which grant when?

A “grant” is one of OAuth's login flows. Authorization Code + PKCE: web, mobile and single-page apps (the default when a user is involved). Client Credentials: one service calling another, with no user. Device Code: TVs and command-line tools. Implicit and password grants: outdated and unsafe, don't use them.

🏢 SSO in the enterprise

Companies keep all identities in one place, an identity provider or IdP (Okta, Entra ID, Google Workspace). Apps trust the IdP through OIDC or the older XML-based SAML. User accounts are created and removed automatically through SCIM. Remove an employee in one place and they lose access everywhere.

Authorization models

Once you know who someone is, you decide what they can do. Authorization must be checked on the server, on every request, for every object.

The most common serious API weakness (#1 on the OWASP API list) is Broken Object Level Authorization. The server checks that the user is logged in, but not that invoice 1002 actually belongs to them.

The fix is one extra condition on every lookup: instead of SELECT * FROM invoices WHERE id = 1002, run … WHERE id = 1002 AND company_id = :callers_company, and return "not found" when no row comes back (not "forbidden", which confirms the invoice exists). The three models below differ only in how the "is this allowed?" question gets answered:

  • RBAC (role-based) — users get roles, roles get permissions. "Editors can edit documents." Simple, but it can't express "only their own documents" on its own.
  • ABAC (attribute-based) — rules over attributes of the user, the object and the context. "Users may read documents whose region equals their region, during work hours."
  • ReBAC (relationship-based) — permission follows links in a graph. "You can view a file if you can view the folder it's in, and you can view the folder because it was shared with your team."

Centralize policy, enforce locally

At scale, teams move the permission rules into one dedicated service or library, called a policy decision point. That keeps the rules consistent and easy to audit. Each service still enforces the answer in its own request handling.

Zanzibar-style systems (Google's permission service) cache heavily. They use consistency tokens to avoid the “new enemy problem”: a user removed from a document still seeing edits made after they were removed.

Encryption in transit and at rest

Data is exposed in two places: while it travels over a network (anyone on the path — a café Wi-Fi, a compromised router — could read it) and while it sits on a disk or in a backup (a stolen drive, a leaked snapshot, a misconfigured bucket). "In transit" and "at rest" encryption cover those two cases. First, four words that are often mixed up:

In transit: TLS everywhere

Use TLS 1.3 on every external connection (Chapter 2). Add HSTS so browsers can't be tricked into plain HTTP. Use mTLS between internal services (mutual TLS), where both sides prove who they are with certificates. Service meshes issue and renew those certificates automatically (for example with SPIFFE identities).

💾

At rest: envelope encryption

Encrypt disks, databases, backups and object storage. Keys never sit next to the data. A KMS/HSM (a key management service backed by tamper-proof hardware) holds the master keys, which never leave it. It only uses them to encrypt (“wrap”) smaller data keys.

Envelope encryption with a KMSStep-through
  1. The service calls GenerateDataKey. The access policy (IAM) checks that this service may use this master key. Every call is written to an audit log.
  2. KMS returns the new data key (DEK) in two forms: in plaintext, and encrypted with the master key.
  3. The service encrypts the record or file itself with AES-GCM, using the plaintext DEK. No network trip is needed for the data. Then it wipes the plaintext key from memory.
  4. Storage keeps the encrypted data (ciphertext) next to the encrypted DEK. Stealing the whole disk gives an attacker nothing usable. To read the data, the service asks KMS to decrypt the DEK (checked and logged), then decrypts the data locally.
  5. Changing the master key only means re-wrapping the small data keys, not re-encrypting petabytes. Give each tenant (customer) its own DEK, and you can delete a tenant's key to make all their data unreadable forever. That's handy for GDPR “right to be forgotten” requests.
🗝️
Secrets management

Never write passwords or keys into code, and never commit .env files. Instead:

  • Keep them in a secrets manager (Vault, AWS Secrets Manager) and load them when the app starts.
  • Change (rotate) them automatically.
  • Prefer short-lived credentials tied to the workload's identity, so there are no permanent keys at all.
  • Scan for leaked secrets in CI.

Keys leaked on public repos get used by attackers within minutes.

Common attacks and defenses

SQL injection — log in as anyoneSimulator
alice' OR '1'='1' --admin' --x'; DROP TABLE users; --

Why the injection works: with string concatenation, the query is built as … WHERE username = ' + input + ' AND password = '…'. Type ' OR '1'='1' -- and the quote closes the string early, OR '1'='1' makes the condition true for every row, and -- turns the password check into a comment. The database can't tell your code from the user's text. A parameterized query sends the SQL and the values separately, so the input is only ever treated as data, whatever characters it contains.

📜

XSS

Cross-site scripting — tap to flip
An attacker's content, like a <script> tag, runs in other users' browsers and steals their tokens. Defend: escape output so it shows as text, not code (frameworks do it by default); set a strict Content-Security-Policy; use HttpOnly cookies so scripts can't read sessions.
🎭

CSRF

Cross-site request forgery
A malicious site makes the victim's browser send a request to your site. The browser attaches your cookies automatically, so it looks like the real user. Defend: SameSite=Lax/Strict cookies, anti-CSRF tokens, and never change state on GET.
🛰️

SSRF

Server-side request forgery
A “fetch this URL” feature gets pointed at internal addresses, like the cloud metadata endpoint 169.254.169.254, to steal credentials. Defend: allowlists; block private IP ranges after looking up the hostname; send outgoing requests through a proxy; use IMDSv2.
🔢

IDOR / BOLA

Insecure direct object references
Changing /orders/1001 to /orders/1002 shows someone else's order. Defend: check ownership on every object access. Hard-to-guess IDs help, but they are not a permission check.
🧨

Credential stuffing

Reused leaked passwords
Bots try millions of leaked email/password pairs. Defend: MFA or passkeys, rate limits per account and per IP, checks against breached passwords, bot detection, and alerts on “impossible travel” (logins from two far-apart places minutes apart).
📦

Supply chain

Compromised dependencies
A malicious package or build step sneaks a backdoor into your software. Defend: lockfiles and pinned versions, dependency scanning, signed builds with a record of where they came from (SLSA, Sigstore), minimal base images, and SBOMs (a list of every component you ship).

Surviving DDoS and abuse

A distributed denial-of-service (DDoS) attack floods you with traffic from thousands of hijacked machines. Modern attacks reach millions of requests per second and hundreds of gigabits. You can't out-muscle that with your own servers. Instead, you absorb it at the edge (the provider's network in front of you), in layers.

Put numbers on it: a botnet of 100,000 machines each sending just 10 requests a second is 1 million requests per second. If your servers each handle 2,000 requests a second, you'd need 500 of them just to stay up — and the attacker can grow the botnet faster than you can add servers. An edge network with hundreds of locations and many terabits of capacity can soak that up and drop the junk long before it reaches you.

Anycast edge network L3/L4

A CDN/DDoS provider (Cloudflare, AWS Shield, Akamai) advertises your IP addresses from hundreds of locations at once (anycast). Raw traffic floods (UDP amplification, SYN floods) get spread across huge capacity and filtered out before they reach you.

Web application firewall L7

A WAF blocks known attack patterns (SQL injection and XSS signatures), IPs with a bad reputation, and requests that look unusual. Keep your real server's IP hidden, so attackers can't go around the edge.

Rate limiting & bot management

Limit requests per IP, per API key and per account (Chapter 15). Give suspicious clients a challenge (a JS check, a small proof-of-work puzzle, a CAPTCHA) instead of blocking them outright.

Protect expensive endpoints

Login, search, and anything that works the database hard get stricter limits and caching. Add queue-based load shedding (dropping extra work on purpose, Chapter 16) so the core keeps working under attack.

Autoscaling — with a budget cap

Add servers automatically to absorb bursts, but set a limit. On pay-per-use cloud, an attack can also be a “denial of wallet” that runs up your bill.

🏢 Multi-tenant isolation

SaaS platforms serve many customers (tenants) and must guarantee tenant A never sees tenant B's data. Options, from cheapest to strongest: a tenant_id column enforced by row-level security → a schema per tenant → a database per tenant → dedicated infrastructure (cells, Chapter 22) for the largest or most regulated customers.

📜 Audit logging & compliance

Record who did what, to which resource, when and from where. Make the log append-only and tamper-evident, and store it apart from app data. Regulations (GDPR, HIPAA, PCI DSS, SOC 2) set rules on how long you keep data, where it lives, encryption and access reviews.

⚠️
Common mistakes
  • Checking authentication but not authorization. The most common serious API bug: a logged-in user reads someone else's object just by changing an ID.
  • Rolling your own crypto or token format. Use well-tested libraries and standard flows. Homemade schemes fail silently, so you don't find out until it's too late.
  • Treating internal networks as trusted. In a flat network, one hacked service or laptop gets access to everything. Make services prove their identity to each other too.
🎤
Interview drill

Design: A user pastes a URL and your service fetches it to generate a preview. What could go wrong?

How a strong answer sounds
SSRF. The URL can point at internal addresses: 169.254.169.254 for cloud credentials, internal admin panels, or localhost. Defences: look up the hostname first and block private and link-local IP ranges. Check again after every redirect, to defeat DNS rebinding (a hostname that switches to an internal IP). Allow only certain schemes and ports. Fetch through an outbound proxy in an isolated network with no credentials. Limit size and time. Never send the raw response body back to the user.

Explain: Where do you store the session token in a web app, and why?

How a strong answer sounds
In an HttpOnly, Secure, SameSite=Lax cookie. JavaScript can't read it, so an XSS attack can't steal it, and SameSite blocks most CSRF. localStorage is convenient for single-page apps, but then any XSS bug means full account takeover. If you need cross-site API calls, keep short-lived access tokens in memory plus a refresh token in an HttpOnly cookie. Add anti-CSRF tokens for requests that change data.

🧠 Key takeaways

  • Map your trust boundaries and threats. Apply least privilege, defense in depth and zero trust.
  • Authentication proves who you are. Authorization decides what you may do. Check authorization on the server, for every object.
  • Hash passwords with Argon2id, bcrypt or scrypt and a unique salt. Better still, add MFA and passkeys.
  • Sessions can be cancelled instantly. JWTs are checked without a lookup but can't be cancelled, so pair short-lived access tokens with rotating refresh tokens.
  • OAuth 2.0 grants limited access with scoped tokens; OIDC adds identity. Use Authorization Code + PKCE.
  • RBAC for roles, ABAC for rules based on attributes, ReBAC for sharing and folder-style hierarchies.
  • TLS/mTLS for data in transit; envelope encryption with a KMS for data at rest; secrets in a secrets manager, never in code.
  • Parameterize queries, escape output, use SameSite cookies, block SSRF, and absorb DDoS at the edge.

Check your understanding

Why add a unique random salt to each password before hashing?

Salts force attackers to crack each user one at a time. A slow hash (Argon2id/bcrypt) then makes each guess expensive. You need both.

An employee is fired and their JWT access token is valid for 24 more hours. What's the best design fix?

A JWT can't be taken back once issued. A short lifetime limits how long a stolen or leftover token works. Revoking the refresh token on the server stops it from being renewed.

In the OAuth Authorization Code flow with PKCE, what stops an attacker who intercepts the authorization code?

The authorization server checks that hash(code_verifier) equals the code_challenge sent at the start. An attacker with only the code doesn't have the verifier.

A logged-in user changes /api/invoices/1001 to /1002 and sees another company's invoice. What kind of bug is this?

The user is logged in correctly. The server just never checked whether they're allowed to see that specific invoice. The fix is to include the owner in every lookup (WHERE id = ? AND company_id = ?), not to hide or scramble the IDs.

Why use envelope encryption instead of sending all data to the KMS to encrypt?

Envelope encryption means the data never travels over the network to be encrypted, and changing the master key is cheap. Every time a key is unwrapped, it is still checked and logged.
