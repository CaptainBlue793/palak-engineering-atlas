Microservices, Gateways & Rate Limiting

As a system and its teams grow, one big codebase slows people down as much as machines. Microservices split the system into separate services, each owning one part of the business. That solves some problems and creates new ones, which is why you then need gateways, service discovery, sagas and rate limits.

Monolith vs microservices

Why would anyone split one working program into many? Usually not for speed of the code, but for speed of the people. With 10 engineers in one codebase, everyone can coordinate over lunch. With 300 engineers, a single codebase means every release waits on every team's tests, and one bad change blocks everyone's deploy. Splitting into services lets each team ship on its own schedule. The price is that calls which used to be free function calls now travel over a network, where they can be slow or lost.

🏛️ Monolith

One program with all the features in it, usually using one database. Parts talk to each other with ordinary function calls. Simple to build, test, deploy and debug. It's the right starting point for most products.

🧩 Microservices

Many small services. Each one owns a single job in the business and its own data, and they talk over the network. You can deploy and scale each one separately, but you take on all the difficulties of distributed systems.

The network cost adds up faster than people expect. Say loading a product page needs data from 6 services, called one after another, each taking 20 ms. That's 120 ms before you've done any real work, versus well under 1 ms for 6 function calls in a monolith. Reliability multiplies too: if each service is up 99.9% of the time, a request that needs all 6 succeeds only about 0.9996 ≈ 99.4% of the time. That's why good microservice designs call services in parallel where they can, and keep the chain of calls short.

A rough guide for choosing. Stay with a monolith (ideally a modular one, with clean internal boundaries) while you have one or a few teams and the product is still changing shape. Consider pulling out a service when one of these is true: a part needs to scale very differently (image processing vs the settings page), a part needs different reliability or security (payments), or teams are regularly blocked on each other's releases.

🍝
Beware the distributed monolith

Suppose every service shares one database, or changing one service means deploying five others at the same time. Then you pay all the costs of microservices and get none of the benefits.

Split by what each part does for the business (in design language, a bounded context), with a clear API and its own data. And remember Conway's Law: your architecture ends up looking like your team structure.

A bounded context is an area of the business where words have one clear meaning. In a shop, "product" in the catalogue means photos and descriptions, while "product" in the warehouse means shelf location and stock count. Those are good places to draw a line: the catalogue service and the inventory service each keep the fields they care about, linked by a shared product ID.

🌿
Migrating: the Strangler Fig pattern

Don't rewrite everything from scratch. Put a proxy in front of the monolith. Build one new service at a time, and send just that slice of traffic to it. The monolith shrinks bit by bit until you can delete it, like a strangler fig vine slowly replacing the tree it grew on.

The API gateway

With dozens of services, a phone app shouldn't have to know every address. An API gateway is the single front door for all clients. It handles the jobs every service would otherwise need to do itself: checking logins, limiting traffic, routing, logging.

Without a gateway, a home screen that needs user, feed and notification data means the phone makes 3 separate trips over a slow mobile network, and each of 40 services must check tokens and rate limits on its own, 40 slightly different ways. With a gateway, the phone makes 1 trip, and those shared rules live in one place. Two cautions: the gateway is now on the path of every request, so it must run as several copies behind a load balancer; and it should stay thin. Business logic belongs in the services, or the gateway turns into a new monolith that every team must change.

GET /api/home — through the gatewayStep-through
  1. The app calls one host: api.example.com. It knows nothing about the 40 services behind it. The encrypted TLS connection ends here.
  2. The gateway checks the token's signature and expiry once, then passes the user ID on to the services in a trusted header. Each service doesn't have to verify tokens itself.
  3. It checks this user's allowance (say, 100 requests a minute). Over the limit, it replies 429 Too Many Requests without bothering any service at all. More on this below.
  4. The path /api/home needs data from three services. The gateway looks up where they are (service discovery) and calls all three at the same time.
  5. The three replies are merged into exactly the shape the mobile screen needs. The client makes one trip instead of three. A gateway built for one type of client is called a Backend-for-Frontend.
  6. Each request gets a trace ID that is passed to every service, so you can follow it end to end. The gateway also records access logs and timings. Then the response goes back to the client.

Service discovery & service mesh

Copies of a service start and stop all the time: autoscaling, deploys, crashes. Their network addresses keep changing. Service discovery keeps an up-to-date directory of where each service is running right now.

📒

Registry

Each instance signs itself into the directory when it starts, then keeps sending “I'm alive” messages (Consul, etcd, Eureka). Kubernetes does this for you for pods behind a Service.

🧭

Client-side vs server-side

Client-side: the caller looks up the directory and picks an instance itself. Server-side: the caller uses one fixed name (like payments.svc.cluster.local) and a load balancer picks for it.

🕸️

Service mesh

A small helper proxy (a sidecar, usually Envoy) runs next to every service and handles discovery, retries, timeouts, mTLS and metrics. Your application code doesn't have to. Istio, Linkerd.

When is a mesh worth it? A mesh adds a proxy to every service and a control plane to run, which costs memory, a little latency on each hop (often around a millisecond) and a lot to learn. It pays off when you have many services written in several languages and want the same retries, encryption (mTLS: both sides prove who they are) and metrics everywhere without rewriting each one. With a handful of services in one language, a shared client library or plain Kubernetes Services is usually enough.

Rate limiting

A rate limiter caps how many requests one client may make in a period of time. It protects your services from abuse, from scripts stuck in a loop, and from one heavy customer slowing everyone else down. It also keeps your bill under control.

There are five classic algorithms, each behaving a little differently. In the lab below, the limit is 5 requests per 2 seconds.

Two of them, worked by hand

Token bucket. Picture a bucket that holds at most 5 tokens and gets 1 new token every 0.4 seconds (so 2.5 per second on average). Each request takes one token; no token means 429.

  1. At t = 0 s the bucket is full: 5 tokens. A burst of 7 requests arrives. The first 5 take a token each and pass. Requests 6 and 7 find it empty and are rejected.
  2. At t = 1.0 s, 1.0 ÷ 0.4 = 2.5 tokens have dripped back in, so 2 whole tokens are available. Two more requests pass.
  3. If the client goes quiet for 2 seconds, the bucket refills to 5 (never more), ready for the next burst.

You never need a timer to add tokens. You store just "tokens left" and "last updated time", and on each request you work out how many tokens should have dripped in since then. That's why it needs only two numbers.

Sliding window counter. Say the limit is 100 per minute. It's 12:01:15, so we're 25% of the way into the current minute. The previous minute (12:00) had 80 requests; the current one has 30 so far. The algorithm estimates the last 60 seconds as 30 + 80 × (1 − 0.25) = 30 + 60 = 90. It assumes the previous minute's requests were spread evenly, and counts the 75% of them that still fall inside the sliding window. 90 is under 100, so the request is allowed. It isn't exact, but it avoids the fixed window's double burst while storing only two counters.

Which one to pick: token bucket for public APIs where short bursts are normal (a page load fires 10 calls at once). Leaky bucket when the thing behind you needs a smooth, steady flow, like a third-party SMS provider with a strict per-second limit. Sliding counter for large-scale "N per minute" limits. Fixed window only for rough daily or monthly quotas, where a boundary burst doesn't matter.

🌐 Distributed rate limiting

With 50 gateway servers, counting inside each one doesn't work: each would let the full limit through, so the real limit is 50×. Keep the counters in one shared place, usually Redis, using operations that can't interleave wrongly (INCR + EXPIRE, or a small Lua script for token buckets). Either accept a little imprecision, or split counters by client key.

Sagas: transactions across services

Each service has its own database. So you can't wrap “create order + charge card + reserve stock + book courier” in a single all-or-nothing transaction. Two-phase commit could, but it gets stuck when the coordinator dies (Chapter 13).

A saga does it differently. It's a chain of small local transactions, one per service. If a step fails, the earlier steps are undone by compensating transactions: new actions that reverse the effect, such as a refund.

Order saga — inventory is out of stockStep-through
  1. Order service inserts the order with status PENDING in its own database, then announces OrderCreated.
  2. The payment service hears that, charges $89 in its own transaction, and announces PaymentCharged.
  3. The inventory service tries to reserve the shoe, but it's out of stock. It announces StockReservationFailed. The payment is already committed and can't be rolled back, so we have to undo it with a new action.
  4. The payment service runs its compensating action: refund $89. Note that a compensation is a new action going forwards, not a rollback. The customer may see both a charge and a refund on their statement.
  5. The order service marks the order CANCELLED and tells the customer. Everything agrees again, just not instantly: eventually.

💃 Choreography

Like dancers who each know their steps. Every service listens for events and decides what to do next. There's no central brain and the services stay independent. But the overall flow isn't written down anywhere, so it gets hard to follow as it grows.

🎼 Orchestration

Like an orchestra with a conductor. One coordinator tells each service what to do and decides what happens when a step fails. The whole flow lives in one place where you can read it. Tools: Temporal, AWS Step Functions, Camunda.

Choosing between them. Choreography suits short flows of two or three steps, where each service reacting to an event is easy to follow. Once a flow has five or more steps, branches ("if the item is oversized, book a freight courier") or deadlines ("cancel if payment hasn't arrived in 15 minutes"), orchestration is usually clearer, because you can open one file and see the whole process and where each order is stuck.

Edge cases a saga must handle.

  • Some steps can't be undone. You can refund a charge, but you can't un-send an email or un-ship a parcel. Put those steps last, after everything that might still fail.
  • Compensations can fail too. The refund call might time out. Compensations must be retried until they succeed, so they must be idempotent: refunding order 91 twice should still refund only once.
  • Other users see the in-between state. Between "charged" and "refunded", the order really is charged. That's why the order sits in a PENDING state, which tells the UI and other services "not final yet".
⚠️
Common mistakes
  • Splitting by technical layer instead of by business job. A “database service” and a “logic service” always have to be deployed together. That's a distributed monolith.
  • Sharing one database between services. It removes the only real benefit (each service changing on its own) and keeps every cost.
  • No timeouts or limits on retries between services. One slow dependency then ties up every thread in every service that calls it.

Interview drill

Decide: A 6-person team with one product asks whether to split into microservices. What do you say?

How a strong answer sounds
No. Start with a modular monolith: clear boundaries between modules, separate schemas inside one database, one thing to deploy. You get most of the design benefits without paying the distributed-systems tax. Split later, when a specific pain shows up: one component needs to scale very differently, one team is blocked waiting for another team's releases, or one capability needs much higher availability than the rest. Conway's law says the shape of your teams should drive the split, not the other way round.

Design: Place an order that must reserve stock, charge a card and book a courier, across three services.

How a strong answer sounds
Use a saga, not a distributed transaction. The orders service writes the order as PENDING and publishes OrderPlaced through its outbox table. Payment charges the card with an idempotency key (so a retry can't charge twice) and publishes PaymentCaptured. Inventory reserves stock and publishes its result. Shipping books the courier. Every step has an undo action (refund, release stock). The flow is either driven by events between services, or by an orchestrator if you want it visible in one place. Every handler must be idempotent, because every step will be retried sooner or later.

🧠 Key takeaways

  • Start with a well-organised monolith. Split it into services when team size or scaling actually hurts.
  • Microservices give you independent deploys, independent scaling and contained failures. You pay in network calls, data that takes time to agree, and much more operational work.
  • Each service owns its own data. Sharing one database creates a distributed monolith.
  • API gateways handle login checks, rate limiting, routing, combining responses and monitoring in one place.
  • Token bucket is the usual choice for rate limiting. Fixed windows let a double burst through at the edges. When you run many servers, keep the counters in one shared store.
  • Sagas replace distributed transactions with local transactions plus undo actions.

Check your understanding

A 4-person startup with an unproven product asks if they should start with microservices. Best advice?

Microservices solve team-size and scaling problems that this startup doesn't have yet, while adding a lot of operational work.

Your API allows 100 req/min using fixed windows. A client sends 100 at 12:00:59 and 100 at 12:01:00. What happens?

The two bursts land in different windows, and each window starts with a fresh counter. Sliding windows or token buckets prevent this.

Which algorithm allows short bursts but enforces an average rate, using just two numbers per client?

Token bucket stores just two things: how many tokens are left and when they were last topped up. The bucket size sets the biggest burst; the refill speed sets the average rate.

In a saga, shipping fails after payment succeeded. What happens to the payment?

Each saga step is already committed in its own database. Undoing it takes a new business action, like issuing a refund.

You run 20 gateway instances, each with an in-memory limit of 100 req/min per user. What's the effective limit?

Each instance keeps its own count, so 20 instances allow up to 20 × 100. Use a shared store like Redis to enforce one overall limit.
