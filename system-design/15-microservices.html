Microservices, Gateways & Rate Limiting

As systems and teams grow, a single codebase becomes a bottleneck for people as much as for machines. Microservices split the system along business boundaries — and bring a whole new set of problems that need gateways, discovery, sagas and rate limits.

Monolith vs microservices

🏛️ Monolith

One deployable unit containing all features, usually sharing one database. Function calls between modules. Simple to build, test, deploy and debug — the right starting point for most products.

🧩 Microservices

Many small services, each owning one business capability and its own data, communicating over the network. Independent deploys and scaling, at the cost of distributed-systems complexity.

Beware the distributed monolith

If every service shares one database, or a change to one service requires deploying five others together, you have all the costs of microservices and none of the benefits. Split along business capabilities (bounded contexts) with clear APIs and data ownership. And remember Conway's Law: your architecture will mirror your team structure.

🌿
Migrating: the Strangler Fig pattern

Don't rewrite from scratch. Put a proxy in front of the monolith, build one new service at a time, and route that slice of traffic to it. The monolith shrinks gradually until it can be removed — like a strangler fig vine replacing its host tree.

The API gateway

With dozens of services, clients shouldn't need to know every address. An API gateway is the single front door that handles cross-cutting concerns, so each service doesn't reimplement them.

GET /api/home — through the gatewayStep-through
  1. The app calls one host: api.example.com. It knows nothing about the 40 services behind it. TLS is terminated here.
  2. The gateway validates the JWT signature and expiry, and attaches the user ID as a trusted header. Services don't each re-verify tokens.
  3. Checks this user's quota (e.g. 100 requests/min). Over the limit → 429 Too Many Requests without touching any backend. More on this below.
  4. Based on path, /api/home needs data from three services. The gateway calls them in parallel via service discovery.
  5. Responses are merged and shaped into exactly what the mobile screen needs — one round trip for the client instead of three. (A dedicated gateway per client type is called a Backend-for-Frontend.)
  6. Every request gets a trace ID propagated to all services, plus access logs and latency metrics. Then the response goes back to the client.

Service discovery & service mesh

Service instances come and go constantly (autoscaling, deploys, crashes), so their IPs change. Service discovery keeps a live registry of where each service is running.

📒

Registry

Instances register on startup and send heartbeats (Consul, etcd, Eureka). Kubernetes does this automatically for pods behind a Service.

🧭

Client-side vs server-side

Client-side: caller queries the registry and load-balances itself. Server-side: caller hits a stable name/LB (e.g. payments.svc.cluster.local) that routes for it.

🕸️

Service mesh

A sidecar proxy (Envoy) next to every service handles discovery, retries, timeouts, mTLS and telemetry — so application code doesn't. Istio, Linkerd.

Rate limiting

A rate limiter caps how many requests a client can make in a time period. It protects services from abuse, runaway scripts and noisy neighbours, controls cost, and keeps one customer from degrading everyone else. There are five classic algorithms — each with a different personality. Limit here: 5 requests per 2 seconds.

🌐 Distributed rate limiting

With 50 gateway instances, local counters don't work — each would allow the full limit. Keep counters in Redis with atomic operations (INCR + EXPIRE, or a Lua script for token buckets). Accept slight inaccuracy, or shard counters by client key.

Sagas: transactions across services

With a database per service, you can't wrap “create order + charge card + reserve stock + book courier” in one ACID transaction (and 2PC blocks — Chapter 13). A saga is a sequence of local transactions. If a step fails, previously completed steps are undone by compensating transactions.

Order saga — inventory is out of stockStep-through
  1. Order service inserts the order with status PENDING in its own DB and publishes OrderCreated.
  2. Payment service reacts, charges $89 in its local transaction, publishes PaymentCharged.
  3. Inventory service tries to reserve the shoe… out of stock. It publishes StockReservationFailed. We can't roll back payment's committed transaction — so we compensate.
  4. Payment service runs the compensating action: refund $89. Note: compensation is a new forward action, not a rollback — the customer may see a charge and a refund.
  5. Order service marks the order CANCELLED and notifies the customer. The system is consistent again — eventually.

💃 Choreography

Each service listens for events and decides what to do next. No central brain, very decoupled — but the overall flow is implicit and hard to follow as it grows.

🎼 Orchestration

A saga orchestrator tells each service what to do and handles failures explicitly. Flow is visible in one place. Tools: Temporal, AWS Step Functions, Camunda.

⚠️
Common mistakes
  • Splitting by technical layer instead of business capability. A “database service” and a “logic service” must be deployed together — that's a distributed monolith.
  • Sharing one database between services. It removes the only real benefit (independent evolution) and keeps all the costs.
  • No timeouts or retry budgets between services. One slow dependency then consumes every thread in every caller.
🎤
Interview drill

Decide: A 6-person team with one product asks whether to split into microservices. What do you say?

How a strong answer sounds
No — start with a modular monolith: clear module boundaries, separate schemas inside one database, one deployable. You get most of the design benefits with none of the distributed-systems tax. Split later when a specific pain appears: a component with very different scaling needs, a team that is blocked by another team's release cadence, or a capability with genuinely different availability requirements. Conway's law means the org shape should lead the split, not the other way round.

Design: Place an order that must reserve stock, charge a card and book a courier — across three services.

How a strong answer sounds
A saga, not a distributed transaction. Orders service writes the order as PENDING and emits OrderPlaced via the outbox; payment charges with an idempotency key and emits PaymentCaptured; inventory reserves stock and emits its result; shipping books the courier. Each step has a compensation (refund, release stock) and the flow is either choreographed through events or run by an orchestrator for visibility. Every handler is idempotent because every step will be retried.

🧠 Key takeaways

  • Start with a well-structured monolith; split into services when team or scaling pain justifies it.
  • Microservices buy independent deploys, scaling and fault isolation at the price of network calls, eventual consistency and operational complexity.
  • Each service owns its data; sharing a database creates a distributed monolith.
  • API gateways centralise auth, rate limiting, routing, aggregation and observability.
  • Token bucket is the go-to rate limiter; fixed windows allow edge bursts; store counters centrally when distributed.
  • Sagas replace distributed transactions with local transactions plus compensations.

Check your understanding

A 4-person startup with an unproven product asks if they should start with microservices. Best advice?

Microservices solve organisational and scaling problems they don't have yet, while adding heavy operational cost.

Your API allows 100 req/min using fixed windows. A client sends 100 at 12:00:59 and 100 at 12:01:00. What happens?

They fall into two different windows, each with a fresh counter. Sliding windows or token buckets prevent this.

Which algorithm allows short bursts but enforces an average rate, using just two numbers per client?

Token bucket stores token count and last refill time. Capacity sets burst size; refill rate sets the average.

In a saga, shipping fails after payment succeeded. What happens to the payment?

Each saga step commits locally, so undoing requires an explicit business-level compensation.

You run 20 gateway instances, each with an in-memory limit of 100 req/min per user. What's the effective limit?

Each instance counts independently. Use a shared store like Redis for a global limit.
