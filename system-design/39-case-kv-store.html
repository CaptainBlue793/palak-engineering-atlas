Design a Distributed Key-Value Store

This chapter pulls together all the distributed-systems chapters. You'll build Amazon's Dynamo, the ancestor of DynamoDB, Cassandra, Riak and ScyllaDB. It has just two operations: get(key) and put(key, value). What makes it hard is one requirement: writes must always succeed. That includes during failures and network partitions (when parts of the cluster can't reach each other), on thousands of cheap machines where something is always broken.

  • Split data across machines with consistent hashing and virtual nodes
  • Copy each key to a “preference list” of machines in different racks and zones
  • Tune consistency with N, R and W quorums (how many copies must answer)
  • Keep accepting writes during failures with sloppy quorums and hinted handoff
  • Detect writes that happened at the same time with vector clocks, and resolve the resulting “siblings”
  • Fix copies that have drifted apart using read repair, Merkle trees and gossip

STEP 1 / 6

Requirements

🛠️ Functional

✓get(key) → value (or conflicting versions)
✓put(key, context, value) — values are opaque blobs (~1 KB): the store never looks inside them
✓No transactions across keys, no joins, no SQL
✓Add or remove nodes without downtime

📏 Non-functional

✓Always writeable (“add to cart” must never fail) → “AP” in CAP terms: stay Available during a Partition
✓p99 < 10 ms (99% of requests under 10 ms) as a promised target, not just the average
✓Grows in small steps — add one node at a time
✓No boss node: every node is equal, with no master
✓Tunable consistency per operation
🎤
The requirement that drives everything

“Always writeable” is the one decision that shapes the whole design. You can't block writes during a partition (CAP, Chapter 13). So two sides of the cluster may accept different writes to the same key, and you must live with conflicting versions. That is what forces vector clocks, siblings, read repair and anti-entropy.

If the requirement were “never return stale data” instead, you'd build a system with a leader that agrees on every write using consensus (Raft, Chapter 13), and accept that it sometimes can't take writes. Same problem, opposite architecture.

How the numbers fit together:

  • Data: 100B keys × ~1 KB = 100 TB of real data. Every key is stored N = 3 times, so the cluster holds 300 TB.
  • Nodes: 300 TB ÷ 2 TB usable per node = 150 nodes. You never fill disks to 100% — compaction needs spare room to write new files before deleting old ones, and a failed node's data must fit somewhere — so plan ~200 nodes.
  • Traffic per node: 1M ops/s = 800K reads + 200K writes. Each write goes to 3 replicas, so replicas handle 600K write operations/s. Each read at R = 2 touches 2 replicas: 1.6M read operations/s. Spread over 200 nodes that is roughly 3K writes and 8K reads per node per second — comfortable for one SSD-backed server.
  • Failures: if a server fails about once every 3 years on average, 200 servers see roughly 200 ÷ 156 weeks ≈ 1–2 failures a week from servers alone. Add disks, network cards and bad deploys, and "several a week" is normal.

With a few hundred machines, hardware failure is routine, not rare. The system must treat losing a node as a normal event and handle it automatically — no one gets paged, and no one has to switch things over by hand.

STEP 3 / 6

Partitioning: consistent hashing with virtual nodes

Picture a clock face. Each key is hashed to a position on this ring, and it belongs to the first node you meet going clockwise. That's consistent hashing: when a node joins or leaves, only the keys next to it move.

Virtual nodes go one step further: each physical machine owns many small slices of the ring instead of one big one. That evens out how much data each machine holds. It also means that when a machine fails, its work is spread across the whole cluster, instead of all landing on one neighbour.

Why not just hash(key) % number_of_nodes? It's the obvious approach, and it works until the cluster changes size. With 4 nodes, a key whose hash is 10 lives on node 10 % 4 = 2. Add a fifth node and it moves to 10 % 5 = 0. In fact about 4 out of every 5 keys change nodes — at 300 TB, that means copying ~240 TB across the network just to add one machine. On the ring, adding a fifth node only takes over the keys in the slices it lands on: about 1/5 of the data, and nothing else moves.

Why virtual nodes make the numbers even. With one random point per machine, the gaps between points are uneven by chance; one machine can easily own twice the share of another. With 8 (or, in real systems, 100–256) points per machine, each machine owns many small random slices, and the ups and downs average out. When a machine dies, each of its many slices falls to a different neighbour, so ~200 machines each take a small piece of the extra load and of the copying needed to rebuild it.

Replication & the preference list

Each key is stored on the next N different physical machines clockwise on the ring, skipping extra vnodes of a machine already chosen. That list is the key's preference list. It is chosen to spread across different racks and availability zones, so one rack losing power can't take out every copy of a key.

Any node can act as coordinator for a request — the node that talks to the replicas on the client's behalf. Clients (or a smart client library) learn the ring layout through gossip (nodes chatting to share cluster news), and usually go straight to a node in the preference list.

Example with N = 3: cart:u42 hashes to a point just before vnode A-3. Walking clockwise you meet A-3, then A-7 (another slice of machine A — skipped, A is already chosen), then C-1, then B-5. The preference list is A, C, B. If A and C happened to sit in the same rack, a rack-aware placement would skip C as well and pick the next machine in a different rack. The list usually also includes a few extra machines beyond N, which become the stand-ins when one of the first N is down (see sloppy quorum below).

STEP 4 / 6

Deep dive: quorums (N, R, W)

For each operation, you choose how many replicas must respond. There are N copies of each key. A write waits for W of them to confirm; a read waits for R of them to answer.

If R + W > N, the replicas you read from and the ones you wrote to must share at least one node. So a read always sees the latest confirmed write. For example, with N=3, W=2 and R=2, any two nodes you read include at least one of the two you wrote. If R + W is not greater than N, reads can be stale — which may be perfectly fine for some data.

Why the overlap is guaranteed: it's counting, not magic. Replicas are A, B, C. A write confirmed by W = 2 landed on at least two of them, say A and B. A read from R = 2 picks any two, say B and C. There are only 3 nodes, and 2 + 2 = 4 picks, so at least one node must be picked twice — here B. B has the new value, and version numbers (vector clocks) tell the coordinator which answer is newest. With W = 1 and R = 1, the write might land only on A and the read might ask only C: 1 + 1 = 2 picks out of 3 nodes can miss each other entirely.

The latency cost. A write waits for the W-th fastest replica, not the slowest. If replica round trips take 2 ms, 3 ms and 40 ms (one busy node), W = 2 answers in 3 ms, while W = 3 waits 40 ms. This is why W = N is rarely used for hot data: one slow node slows every write.

Deep dive: staying writeable

🧭

Sloppy quorum

If a node in the preference list can't be reached, the write goes to the next healthy node on the ring instead. So you can still collect W confirmations during failures. It's called “sloppy” because the write isn't in its permanent home yet.

📨

Hinted handoff

The stand-in node stores the data with a hint: “this belongs to node C”. When gossip reports C is healthy again, the stand-in delivers the data and deletes its own copy. Like a neighbour holding your parcel until you're home. Hints expire after a while; if a node is gone for hours, anti-entropy takes over.

🩹

Read repair

If a read finds replicas with different versions, the coordinator returns the newest one (or the siblings) to the client. It also writes the merged value back to the out-of-date replicas. So popular keys get fixed for free by normal read traffic.

🌳

Anti-entropy

Keys that are rarely read would never get read repair, so they could stay out of sync forever. So replicas regularly swap Merkle trees (Chapter 20) — trees of hashes that summarise their key ranges — and sync only the parts that differ.

Why three repair mechanisms and not one? Each covers a different gap. Hinted handoff is cheap and fast but only covers short outages (hints are dropped after a few hours, and are lost if the stand-in node itself dies). Read repair costs nothing extra but only fixes keys someone reads. Anti-entropy fixes everything but is expensive, so it runs in the background, perhaps once a day or week per range. The numbers show why Merkle trees matter: two replicas each holding 1 billion keys can't send each other a billion hashes to compare. Instead they compare the single root hash; if it matches, they're done. If not, they compare the children, and walk down only the branches that differ — for a handful of bad keys, that is a few dozen hash comparisons per level instead of a billion.

A sloppy-quorum edge case to know: during a failure, a write with W = 2 may land on B and a stand-in D, while a read with R = 2 asks A and C. The "R + W > N" overlap was among the home replicas, and D isn't one, so this read can be stale until the hint is delivered. Sloppy quorums trade the freshness guarantee for availability — exactly the "always writeable" choice.

STEP 5 / 6

Deep dive: conflicting writes & vector clocks

With no leader, two clients can update the same key at the same time — during a partition, or just by reaching different coordinators. Which one wins?

Using a clock timestamp (“last write wins”) is simple, but it quietly loses data when machines' clocks disagree. Dynamo instead attaches a vector clock to each version: a small map of counters, one per node, like “Sx:2, Sy:1”. Comparing two vector clocks tells you whether one version was built on top of the other (descends from it), or whether they were truly written at the same time without seeing each other (concurrent).

How to compare two vector clocks, step by step. Version X descends from version Y if every counter in X is at least as big as the same counter in Y (a missing counter counts as 0). Three examples:

  • [Sx:2] vs [Sx:1]: 2 ≥ 1, so the first descends from the second. Keep only [Sx:2]; the old one can be thrown away.
  • [Sx:2, Sy:1] vs [Sx:2]: Sx 2 ≥ 2 and Sy 1 ≥ 0, so again the first descends. Someone read [Sx:2], changed it and wrote via Sy.
  • [Sx:2] vs [Sx:1, Sy:1]: Sx says the first is ahead, Sy says the second is ahead. Neither descends — they are concurrent siblings, and both must be kept.

This is why put takes a context: it is the vector clock you got from your last get. It tells the store which version your new value was built on, so the store can tell "update" apart from "conflict". One practical edge case: with many coordinators, clocks keep growing, so real systems cap their size and drop the oldest entries, accepting a rare false conflict.

What the client sees

📖 Reading [Sx:1] and [Sy:1]: neither clock is ahead of the other on every counter, so they're concurrent siblings. The store can't merge blobs it doesn't understand, so it returns both and lets the application decide. For a cart, you take the union (all items from both). That causes the famous “resurrected item” quirk: a deleted item can come back. Amazon decided that was better than losing an item someone added.
⏱️
Why not last-write-wins?

Last-write-wins (LWW) throws away one of two concurrent writes based on timestamps. But those timestamps come from machines whose clocks can differ by milliseconds or even seconds (Chapter 13). Cassandra uses LWW per column by default. That's fine for “set status = X” but terrible for “add to a list”. When you expect concurrent updates, prefer CRDTs (Chapter 22 — data types that merge automatically) or merging in your application.

Inside a single node

📝

Commit log

Every write is added to a WAL (write-ahead log) on disk before it's confirmed, so it survives a crash.

🧠

Memtable

Writes also go into a sorted structure in memory. That's why writes are so fast — no jumping around the disk.

💾

SSTables + compaction

Full memtables are saved as sorted files that never change (SSTables). In the background, compaction merges them and drops old versions (Chapter 7's LSM tree).

🎯

Bloom filters

One per SSTable. It quickly says “definitely not here”, so a lookup can skip files that don't contain the key (Chapter 20).

🪦
Deletes need tombstones

You can't just remove a key. A replica that was offline still has it, and during the next repair it would copy the key back — “resurrecting” it. So a delete writes a tombstone: a marker meaning “deleted” that is copied like any other value. It is only purged after a grace period (gc_grace_seconds) that is longer than your repair interval. Too many tombstones make reads slow — a classic Cassandra trap when it's used like a queue.

Following one write and one read through a node. A put appends to the commit log (one sequential disk write), inserts into the memtable, and is acknowledged — no existing file is touched, which is why writes are fast. A get checks the memtable first, then the SSTables from newest to oldest. With, say, 10 SSTables, the Bloom filters rule out most of them in memory, so a typical read opens only one or two files. Compaction keeps that file count low; if it falls behind (heavy writes), reads get slower because there are more files to check. That is why compaction backlog is one of the first metrics operators watch.

STEP 6 / 6

Wrap-up: operations & gotchas

🌡️

Hot keys & partitions

One very popular “celebrity” key can overwhelm its N replicas. Fixes: add a suffix to split the key into several shards, put a cache in front of it, or rate-limit that key. Watch traffic per partition, not just the cluster average.

🌍

Multi-datacenter

Spread the preference list across data centers, and copy data between them in the background. Use LOCAL_QUORUM so a read or write only waits for replicas in its own data center, not a round trip across the ocean (Chapter 22).

➕

Bootstrapping a node

A new node takes over some ranges of the ring and copies their data from the current owners. The copying is slowed down on purpose so it doesn't starve live traffic. Gossip spreads the new ring layout, and clients update their routing.

🔎

Secondary indexes

A local index (one per partition) is cheap, but every query must ask all partitions and combine the answers (scatter-gather). A global index is a separate table that is updated in the background and can lag. That's why you must know how you'll query the data before you design it.

📊

Measure p99, not averages

Dynamo's performance promise was set at the 99.9th percentile — the slowest 1 in 1,000 requests. Coordinators can send an extra request when a replica is slow (hedging). These speculative retries add a little load but make the slowest requests much faster (Chapter 4).

🧯

Backpressure

When queues grow, reject or drop some load instead of accepting everything and timing out. An overloaded node that goes silent is worse than one that says “no” (Chapter 16).

⚠️
Common mistakes
  • Assuming R + W > N gives you linearizability (every operation appearing to happen in one single, agreed order). It only guarantees overlap. Concurrent writes still need to be reconciled.
  • Using last-write-wins on data where concurrent updates are normal. Machine clocks disagree, so you'll lose writes without noticing.
  • Deleting data without tombstones. A replica that was offline will bring it back during the next repair.
🎤
Interview drill

Reason: Your store has N=3, W=2, R=2. One node is down for an hour. What is the user experience?

How a strong answer sounds
Writes still succeed: the two healthy replicas are enough for W=2. With sloppy quorum, a stand-in node also holds hinted data for the missing one. Reads still succeed and stay fresh, because any two live replicas overlap with the ones that took the write. When the node comes back, hinted handoff delivers what it missed, and read repair or anti-entropy fixes the rest. The user notices nothing; the operator sees hint counts and repair activity.

Design: How would you add a secondary index (“find users by email”) to a Dynamo-style store?

How a strong answer sounds
Option one is a local index per partition. It's cheap to write, but every query has to ask all partitions and combine the results (scatter-gather). Option two is a global index: a separate table keyed by email, updated in the background. It's fast to read but can lag behind (eventually consistent). It also needs care on updates — delete the old entry, insert the new one — and when two writes hit the same email at once. That trade-off is exactly why these stores insist you know how you'll query the data up front.

🧠 Key takeaways

  • “Always writeable” forces an AP design: accept conflicts and sort them out later, instead of blocking writes.
  • Consistent hashing with virtual nodes spreads data evenly. When a node joins or leaves, only ~1/N of the keys move.
  • Each key lives on a preference list of N different machines across racks and zones. Any node can coordinate a request.
  • R + W > N means reads overlap writes, so reads are fresh. Smaller values give up some consistency for speed and availability.
  • Sloppy quorums plus hinted handoff keep writes succeeding during failures.
  • Vector clocks tell apart “this version built on that one” from “these were written at the same time” (siblings). Last-write-wins quietly loses data.
  • Read repair fixes often-read data; Merkle-tree anti-entropy fixes rarely-read data; gossip spreads who's in the cluster.
  • Each node stores data in an LSM tree. Deletes need tombstones that are kept for a grace period.

Check your understanding

With N=3, W=1, R=1, a client writes and immediately reads from another coordinator. What can happen?

Only one replica confirmed the write. A read that asks just one replica may hit a different one that hasn't received it yet.

A node in the preference list is down and W=3 with N=3. How does the write still succeed?

Hinted handoff keeps the store writeable, then gives the data back to its real owner when that node returns.

A get returns two versions with vector clocks [Sx:1] and [Sy:1]. What does that mean?

Neither clock is ahead of the other, so both are valid siblings. Carts merge by taking all items from both; other kinds of data need their own merge rule.

Why are virtual nodes used instead of one ring position per machine?

With only one ring position per machine, the ranges are uneven, and a failure dumps everything on the single next node.

Why must deletes create tombstones rather than removing the key?

You can't copy “nothing” to another replica. A tombstone is a value meaning “deleted”, kept until every replica has surely seen it.
