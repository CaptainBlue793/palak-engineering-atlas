Design a Distributed Key-Value Store

This is the capstone of the distributed-systems chapters: build Amazon's Dynamo (the ancestor of DynamoDB, Cassandra, Riak and ScyllaDB). Two operations — get(key) and put(key, value) — but the requirement that makes it hard: writes must always succeed, even during failures and network partitions, on a cluster of thousands of commodity machines where something is always broken.

  • Partition data with consistent hashing and virtual nodes
  • Replicate to a preference list across failure domains
  • Tune consistency with N, R and W quorums
  • Stay writeable during failures with sloppy quorums and hinted handoff
  • Detect concurrent writes with vector clocks and resolve siblings
  • Repair divergence with read repair, Merkle trees and gossip
STEP 1 / 6

Requirements

🛠️ Functional

✓get(key) → value (or conflicting versions)
✓put(key, context, value) — values are opaque blobs (~1 KB)
✓No cross-key transactions, joins or SQL
✓Add/remove nodes without downtime

📏 Non-functional

✓Always writeable (“add to cart” must never fail) → AP in CAP terms
✓p99 < 10 ms under an SLA, not just averages
✓Incrementally scalable — add one node at a time
✓Symmetric & decentralized: every node is equal, no master
✓Tunable consistency per operation
🎤
The requirement that drives everything

“Always writeable” is the decision that produces the whole design. Because you can't block writes during a partition (CAP, Chapter 13), you must accept conflicting versions — which forces vector clocks, siblings, read repair and anti-entropy. If instead the requirement were “never return stale data”, you'd build a leader-based, consensus-backed system (Raft, Chapter 13) and accept unavailability. Same problem, opposite architecture.

STEP 3 / 6

Partitioning: consistent hashing with virtual nodes

Keys are hashed onto a ring; each key belongs to the first node clockwise. Virtual nodes (each physical machine owns many small ranges) even out the distribution and spread the work of a failure across the whole cluster instead of dumping it on one neighbour.

🧪 Turn virtual nodes off and add/remove nodes: load imbalance jumps (some node owns twice its share) and one unlucky neighbour absorbs everything a failed node held. With vnodes on, both are smoothed — and the rebuild after a failure is parallelized across many nodes.

Replication & the preference list

Each key is stored on the next N distinct physical nodes clockwise (skipping vnodes of the same machine) — its preference list. The list is extended to prefer distinct racks and availability zones, so one rack losing power doesn't take all replicas of a key. Any node can act as coordinator for a request: clients (or a smart client library) know the ring from gossip and usually talk to a node in the preference list directly.

STEP 4 / 6

Deep dive: quorums (N, R, W)

Per operation you choose how many replicas must respond: W acknowledgements for a write, R responses for a read, out of N replicas. If R + W > N, the read set and write set must overlap in at least one replica, so a read sees the latest acknowledged write. If not, reads can be stale — which may be perfectly fine.

⚡

W=1, R=1

Lowest latency and highest availability; reads may be stale. Good for caches, counters, presence.

⚖️

W=2, R=2 (N=3)

The common default: R+W > N with only one extra replica to wait for. Tolerates one node down on either path.

🧱

W=N, R=1

Fast reads from any replica, expensive and fragile writes. Good for write-rarely, read-constantly config data.

Deep dive: staying writeable

🧭

Sloppy quorum

If a node in the preference list is unreachable, the write goes to the next healthy node on the ring instead — so W acks are still achievable during failures. It's “sloppy” because the write isn't on its permanent home yet.

📨

Hinted handoff

The substitute stores the data with a hint: “this belongs to node C”. When gossip reports C healthy again, the hint is delivered and the local copy deleted. Hints expire after a while — if a node is gone for hours, anti-entropy takes over.

🩹

Read repair

If a read sees replicas with different versions, the coordinator returns the newest (or siblings) to the client and writes the reconciled value back to the stale replicas — repair paid for by read traffic on hot keys.

🌳

Anti-entropy

Cold keys are never read, so they'd stay divergent forever. Replicas periodically exchange Merkle trees (Chapter 20) of their key ranges and sync only the differing parts.

STEP 5 / 6

Deep dive: conflicting writes & vector clocks

With no leader, two clients can update the same key concurrently — during a partition, or simply by reaching different coordinators. Which wins? A wall-clock timestamp (last-write-wins) is simple but silently loses data when clocks disagree. Dynamo instead attaches a vector clock: a per-node counter map that reveals whether one version descends from the other or whether they're truly concurrent.

What the client sees

📖 Reading [Sx:1] and [Sy:1]: neither clock dominates the other, so they're concurrent siblings. The store can't merge opaque blobs, so it returns both and lets the application decide — for a cart, union the items (the famous “resurrected item” quirk: a deleted item can come back, which Amazon considered better than losing an added one).
⏱️
Why not last-write-wins?

LWW discards one of two concurrent writes based on timestamps from machines whose clocks differ by milliseconds to seconds (Chapter 13). Cassandra defaults to LWW per column, which is fine for “set status = X” and terrible for “append to a list”. Prefer CRDTs (Chapter 22) or application-level merges when concurrent updates are expected.

Inside a single node

📝

Commit log

Every write is appended to a WAL on disk before acknowledgement, for crash durability.

🧠

Memtable

Writes also go into a sorted in-memory structure — which is why writes are so fast (no random disk I/O).

💾

SSTables + compaction

Memtables flush to immutable sorted files; background compaction merges them and drops obsolete versions (Chapter 7's LSM tree).

🎯

Bloom filters

Per SSTable, so a lookup skips files that definitely don't contain the key (Chapter 20).

🪦
Deletes need tombstones

You can't just remove a key: a replica that was offline would “resurrect” it during the next repair. Deletes write a tombstone marker that replicates like any value and is purged only after a grace period (gc_grace_seconds) longer than your repair interval. Too many tombstones make reads slow — a classic Cassandra operational trap with queue-like workloads.

STEP 6 / 6

Wrap-up: operations & gotchas

🌡️

Hot keys & partitions

One celebrity key can overwhelm its N replicas. Mitigate by adding a shard suffix to spread the key, caching it in front, or per-key rate limiting. Monitor per-partition traffic, not just cluster averages.

🌍

Multi-datacenter

Extend the preference list across DCs and replicate asynchronously between them; use LOCAL_QUORUM so a read or write doesn't wait for a cross-ocean round trip (Chapter 22).

➕

Bootstrapping a node

A new node claims ranges and streams data from current owners, throttled so it doesn't starve live traffic. Gossip spreads the new ring; clients update their routing tables.

🔎

Secondary indexes

Local indexes (per partition) are cheap but require scatter-gather reads; global indexes are another table that must be kept consistent asynchronously. This is why access patterns must be known up front.

📊

Measure p99, not averages

Dynamo's SLA was expressed at the 99.9th percentile. Coordinators can hedge slow replicas with extra requests, and speculative retries trade a little load for much better tails (Chapter 4).

🧯

Backpressure

Reject or shed load when queues grow rather than accepting everything and timing out — an overloaded node that stays silent is worse than one that says no (Chapter 16).

⚠️
Common mistakes
  • Assuming R + W > N gives you linearizability. It gives overlap, not a total order — concurrent writes still need reconciliation.
  • Using last-write-wins on data where concurrent updates are normal. Wall clocks disagree; you'll lose writes silently.
  • Deleting data without tombstones. An offline replica will resurrect it during the next repair.
🎤
Interview drill

Reason: Your store has N=3, W=2, R=2. One node is down for an hour. What is the user experience?

How a strong answer sounds
Writes still succeed — two healthy replicas satisfy W=2 — and with sloppy quorum a substitute node holds hinted data for the absent one. Reads still succeed and remain fresh, because any two live replicas overlap with the write set. When the node returns, hinted handoff delivers what it missed and read repair or anti-entropy fixes the rest. The user notices nothing; the operator sees hint counts and repair activity.

Design: How would you add a secondary index (“find users by email”) to a Dynamo-style store?

How a strong answer sounds
Either a local index per partition — cheap to write, but every query is a scatter-gather across all partitions — or a global index stored as a separate table keyed by email, maintained asynchronously. The global index is fast to read but eventually consistent and needs careful handling of updates (delete the old entry, insert the new) and of concurrent writes to the same email. That asymmetry is exactly why these stores insist you know your access patterns up front.

🧠 Key takeaways

  • “Always writeable” forces an AP design: accept conflicts and reconcile, rather than blocking writes.
  • Consistent hashing with virtual nodes spreads data and rebalances only ~1/N of keys when membership changes.
  • Each key lives on a preference list of N distinct nodes spanning racks and zones; any node can coordinate.
  • R + W > N gives overlap and fresh reads; smaller values trade consistency for latency and availability.
  • Sloppy quorums plus hinted handoff keep writes succeeding during failures.
  • Vector clocks distinguish causal updates from concurrent siblings; LWW silently loses data.
  • Read repair fixes hot data; Merkle-tree anti-entropy fixes cold data; gossip spreads membership.
  • Nodes are LSM-tree stores; deletes need tombstones with a grace period.

Check your understanding

With N=3, W=1, R=1, a client writes and immediately reads from another coordinator. What can happen?

Only one replica acknowledged the write; a read of one replica may hit a different one that hasn't received it yet.

A node in the preference list is down and W=3 with N=3. How does the write still succeed?

Hinted handoff preserves availability, then restores the data to its rightful owner when it returns.

A get returns two versions with vector clocks [Sx:1] and [Sy:1]. What does that mean?

Neither clock dominates, so both are valid siblings. Carts merge by union; other domains need their own merge rule.

Why are virtual nodes used instead of one ring position per machine?

With a single token per machine, ranges are uneven and a failure dumps everything on one successor.

Why must deletes create tombstones rather than removing the key?

Absence can't be replicated. A tombstone is a value meaning “deleted”, kept until every replica has surely seen it.
