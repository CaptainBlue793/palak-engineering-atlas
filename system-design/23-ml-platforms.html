ML Platforms & Feature Stores

Recommendations, fraud scoring, search ranking, ETA prediction, spam filtering: most large products are now partly machine-learned. The model itself is usually the smallest part. The system around it — pipelines that build features, guarantees that training and serving see the same numbers, evaluation that proves a change helped, and monitoring for a world that shifts underneath you — is the engineering.

  • Map the ML lifecycle onto systems you already know
  • Explain what a feature store is and why it exists
  • Avoid training/serving skew and label leakage
  • Choose between batch, real-time and streaming inference
  • Evaluate models offline and online without fooling yourself
  • Detect drift and retrain safely

Why ML systems are different

🧪

Behaviour comes from data

The same code produces a different system when the data changes. Your “deployable artifact” is code plus a dataset plus weights — all three need versions, lineage and rollback.

🔁

Feedback loops

The model influences what users do, which becomes tomorrow's training data. Recommend only popular items and you'll learn that only popular items get clicked — a loop that quietly narrows the product.

🤫

Failures are silent

A broken feature pipeline doesn't throw an exception; it returns zeros, and the model keeps confidently scoring. Most “model degradation” is really a data outage nobody alerted on.

The lifecycle

From raw events to a served prediction — and back againStep-through
  1. Pipelines turn raw events and tables into features: “purchases in the last 7 days”, “average session length”, “merchant risk score”. Batch jobs (Chapter 18) handle history; streaming jobs keep fast-moving features fresh.
  2. The same definition is materialized into an offline store (columnar, full history, for training) and an online store (key-value, latest value only, for millisecond lookups). One definition, two shapes — this is the core idea of a feature store.
  3. A point-in-time join attaches to each training row only the feature values that existed before its label. Getting this wrong is the most common and most damaging bug in applied ML — see below.
  4. Hold-out and time-based splits, per-segment metrics (does it get worse for new users?), fairness and guardrail checks, comparison against the current production model.
  5. Weights, the training data snapshot, the feature definitions, the code commit and the metrics are registered together. Without that bundle you cannot reproduce or roll back a model.
  6. The serving path fetches features by entity key from the online store and calls the model. Shadow first, then canary by traffic share, with automatic rollback (Chapter 21).
  7. Track feature distributions, missing-value rates, prediction distributions and latency. A feature that silently becomes null is far more common than a model that “gets worse”.
  8. Ground truth is delayed: a click within minutes, a chargeback in 90 days. Join labels back to the features that produced each prediction (log them!), measure real performance, and retrain on a schedule or on drift.

Training/serving skew & leakage

Two failure modes account for a huge share of models that look brilliant offline and disappoint online.

🪞 Training/serving skew

The feature is computed one way in the training pipeline (SQL over a warehouse) and another way in the serving path (application code). Slightly different windows, time zones, null handling or rounding, and the model sees inputs it was never trained on.

🔮 Label leakage

A feature accidentally includes information from after the moment of prediction — “number of chargebacks for this card” computed today, when scoring a transaction from last month. Offline accuracy soars; online it collapses, because at prediction time that information doesn't exist yet.

Ranking 200 candidates with 12 features each is 2,400 lookups. One multi-get plus a vectorized model call is the difference between 15 ms and a timeout — the same N+1 problem as Chapter 7, in ML clothing. Two-stage ranking (cheap retrieval → expensive re-ranking of the top 50) is the standard fix.

Evaluating honestly

📏

Offline ≠ online

Offline metrics (AUC, NDCG, RMSE) measure fit on logged data; they can't see the feedback loop, the UI, or how users react. A +2% AUC often produces no business change at all. Offline is a filter, not a decision.

🅰️

Online experiments decide

Randomize users, define one primary metric plus guardrails (latency, revenue, complaints), run long enough for novelty effects to fade, and pre-register the decision rule. For ranking, interleaving gives sensitive results with far less traffic.

👻

Shadow mode first

Send real traffic to the new model, log its predictions, serve the old one. You get real-world input distributions and latency numbers with zero user risk — the ML version of dark launching.

⏳

Delayed labels

If ground truth arrives in 90 days, you cannot wait 90 days to detect a broken model. Use proxy metrics (acceptance rate, prediction distribution, agreement with the old model) as early warnings, and backfill the real metric when labels land.

Drift & retraining

Models decay because the world moves: new products, new fraud patterns, a marketing campaign that changes who shows up. Watch the inputs as closely as the outputs.

🧪 “Retrain never” decays slowly then falls off a cliff when the sudden shift lands. Scheduled retraining catches gradual drift but reacts late to shocks. Drift-triggered retraining reacts fastest — but note the pipeline break: retraining on broken data makes things worse, which is why data-quality checks must gate training.
📊

Data drift

Inputs change distribution (PSI / KL divergence per feature). Often benign, often the first sign of a broken upstream pipeline.

🎯

Concept drift

The relationship between features and label changes — fraudsters adapt, tastes shift. Only visible once labels arrive.

🛑

Gate the pipeline

Great Expectations-style checks before training and before serving: row counts, null rates, ranges, schema, freshness. A failed check should block the model, not warn in a dashboard nobody reads.

🎤
Designing an “ML system” in an interview

Spend most of the time on the data path: where features come from, how they're kept consistent between training and serving, how labels are collected, how you evaluate and roll out, and what you monitor. Mention the model architecture briefly and move on. Interviewers for ML-systems roles are testing whether you'll build a maintainable pipeline — not whether you can name architectures.

⚠️
Common mistakes
  • Computing features twice. Two implementations of “average order value in 7 days” will diverge; one definition, materialized for both training and serving.
  • Shipping on offline metrics. A +3% AUC often produces zero business change — shadow, then A/B.
  • Monitoring only accuracy. The usual failure is a silent feature-pipeline break, visible in input distributions long before labels arrive.
🎤
Interview drill

Debug: A fraud model's precision dropped 20% overnight. How do you triage?

How a strong answer sounds
Check the data path before the model. Did a feature pipeline fail or start returning nulls/zeros? Did an upstream schema change? Compare serving-time input distributions with training distributions per feature, and check the model version actually deployed. Only after inputs are cleared do I look at concept drift — fraudsters adapting — which is a slower, gentler decline. Have a rollback to the previous model version ready while you investigate.

Design: Serve personalized ranking for 200 candidates per request under 150 ms.

How a strong answer sounds
Two-stage: cheap retrieval (ANN over embeddings or a simple scorer) to get candidates, then an expensive model on the top ~50. Fetch all features for all candidates in one batched multi-get from the online store, not per candidate. Score in a vectorized call. Cache user-level features per request, precompute item features offline, and set a hard deadline with a degraded fallback (popularity ranking) so a slow model can't break the page.

🧠 Key takeaways

  • An ML artifact is code + data + weights; version and roll back all three together.
  • A feature store gives one definition materialized twice: columnar history for training, key-value for serving.
  • Point-in-time joins prevent leakage; a shared definition prevents training/serving skew.
  • Choose batch, real-time or streaming inference by freshness and context needs; beware N+1 feature lookups.
  • Offline metrics filter candidates; shadow deployments and online experiments make the decision.
  • Monitor input distributions and data quality, not just accuracy — silent pipeline failures are the top cause of degradation.
  • Retrain on a schedule and on drift, with data-quality gates so you never retrain on broken data.

Check your understanding

A fraud model scores 0.95 AUC offline and 0.71 in production. The feature “chargebacks for this card” was computed from today's data over historical transactions. What happened?

At serving time that future information doesn't exist. A point-in-time join computes each feature as of the event's timestamp.

What problem does a feature store's dual online/offline storage solve?

Two hand-written implementations of the same feature inevitably diverge; the store makes one definition produce both shapes.

Your ranking service must score 300 candidates in under 150 ms. Feature lookups are 1 ms each. What's the fix?

Per-candidate round trips are the N+1 problem. Batch retrieval plus two-stage ranking is the standard architecture.

Ground-truth labels for loan defaults arrive 6 months later. How do you detect a broken model sooner?

Input monitoring catches pipeline breaks and population shifts immediately; delayed labels then confirm the real metric.

A new model improves offline AUC by 3%. What should happen before it serves all users?

Offline gains often don't transfer. Shadow mode validates inputs and latency; the experiment measures actual user impact.
