ML Platforms & Feature Stores

Recommendations, fraud scoring, search ranking, delivery-time estimates, spam filtering: most large products now use machine learning somewhere. The model itself is usually the smallest part. The real engineering is the system around it: pipelines that build the model's inputs, guarantees that training and live serving see the same numbers, tests that prove a change actually helped, and monitoring for a world that keeps changing underneath you.

Why ML systems are different

A few terms first. A model is a function learned from examples instead of written by hand: give it inputs, get back a prediction, such as “probability this payment is fraud: 0.93”. The inputs are called features (for example “amount”, “country”, “purchases in the last hour”). The correct answer for a past example is its label (“was it actually fraud?”). Training means fitting the model to many past examples with known labels. Inference or serving means using the trained model to predict on new, live requests. Everything in this chapter is about keeping those two sides honest with each other.

🧪

Behaviour comes from data

The same code behaves differently when the data changes. So what you ship is code plus a dataset plus the model's learned weights. All three need version numbers, a record of where they came from, and a way to roll back.

🔁

Feedback loops

The model changes what users do, and that becomes tomorrow's training data. Recommend only popular items, and the model learns that only popular items get clicked. The loop quietly narrows the product.

🤫

Failures are silent

A broken data pipeline doesn't crash. It just returns zeros, and the model keeps making confident predictions from them. Most “the model got worse” cases are really a data outage that nobody alerted on.

The lifecycle

From raw events to a served prediction — and back againStep-through
  1. Pipelines turn raw events and tables into features: the numbers a model learns from. Examples: “purchases in the last 7 days”, “average session length”, “merchant risk score”. Batch jobs (Chapter 18) crunch the history. Streaming jobs keep fast-changing features up to date.
  2. The same feature definition is written into two places. The offline store keeps the full history in columnar form, for training. The online store keeps only the latest value as key-value data, for millisecond lookups while serving. One definition, two shapes: that is the core idea of a feature store.
  3. A point-in-time join gives each training row only the feature values that existed before its outcome was known. Getting this wrong is the most common and most damaging bug in applied ML. More on it below.
  4. Test the model on data it has never seen, including data from later time periods. Break the results down by group: does it get worse for new users? Check fairness and safety limits, and compare it against the model currently in production.
  5. Record five things together: the weights, a snapshot of the training data, the feature definitions, the code commit and the metrics. Without that bundle, you can't reproduce or roll back a model.
  6. To serve a request, look up the features for that user or item in the online store, then call the model. Run the new model in shadow mode first, then as a canary on a small share of traffic, with automatic rollback (Chapter 21).
  7. Track the spread of each feature's values, how often values are missing, the spread of predictions, and latency. A feature that quietly turns into null is far more common than a model that genuinely “gets worse”.
  8. You learn the true answer (the label) later: a click within minutes, a chargeback in 90 days. Match those labels back to the exact features used for each prediction, which means logging them. Then measure real performance, and retrain on a schedule or when drift appears.

Training/serving skew & leakage

Two problems explain most models that look brilliant in testing and disappoint in production. Both have the same root: the model is trained on inputs that differ from what it will see when it runs for real. A model can only be as good as the match between those two.

🪞 Training/serving skew

The same feature is computed in two different places: SQL in the warehouse for training, and application code when serving. A slightly different time window, time zone, way of handling missing values, or rounding rule is enough. The model then sees inputs unlike anything it trained on.

🔮 Label leakage

A feature accidentally includes information from after the moment of the prediction. For example, “number of chargebacks for this card” computed today, while scoring a transaction from last month. Offline accuracy looks amazing. In production it collapses, because at prediction time that information doesn't exist yet.

A skew example with numbers: training computes “purchases in the last 7 days” in the warehouse, using UTC days. Serving computes it in app code, using the user's local day, and counts only completed orders. For a user in Tokyo with 6 purchases, one of them still pending, training saw 6 while serving sends 4. The model learned that 6 means a regular, trusted customer; it now sees a quieter user, and its scores shift for thousands of people at once. No error is thrown anywhere.

How a point-in-time join fixes leakage. Take one training row: a card payment on 1 March, later labelled fraud when a chargeback arrived on 20 March.

  • Naive join: attach the card's features as they are today (say 1 April): “chargebacks on this card: 1”. That chargeback happened because of this payment, so the model learns “a chargeback count of 1 means fraud”, which is useless on 1 March, when the count was still 0.
  • Point-in-time join: attach the latest feature values recorded before 1 March: “chargebacks: 0, purchases in last hour: 5, new device: yes”. Those are exactly the values a live model would have seen, so what it learns will still work in production.

To make this possible, the offline store keeps every feature value with the timestamp it became true, not just the latest value.

🧪 The first case is the dangerous one. A model that looks better offline is exactly the model that gets shipped. Three rules prevent it: compute every feature from a single definition in a feature store, always join features as of the event's own time, and log the features used at serving time so you can compare them with training later.

Serving patterns

Once a model is trained, you have to decide when it runs. The two questions that decide it: how fresh must the prediction be, and does it need information that only exists in the current request (the basket contents, the search text, the device)? If a prediction can be a day old and needs nothing from the request, compute it ahead of time. If it depends on what the user is doing right now, compute it per request.

Ranking 200 candidates with 12 features each means 2,400 lookups. Doing them in one batched request, then scoring all candidates in one call, is the difference between 15 ms and a timeout. It's the same N+1 problem as Chapter 7, wearing an ML costume. The standard fix is two-stage ranking: a cheap model picks candidates, then an expensive model re-ranks only the top 50.

The arithmetic: if each lookup is a separate 1 ms network round trip done one after another, 2,400 lookups take 2.4 seconds. Sent as a single multi-get, the store answers them together in a few milliseconds. The same work, over 100× faster, just by removing waiting.

Evaluating honestly

Some score names you will meet. AUC measures how well a model ranks positives above negatives: 0.5 is a coin flip, 1.0 is perfect. NDCG scores a ranked list, giving more weight to getting the top positions right. RMSE is the typical size of the error when predicting a number, such as delivery time in minutes. All three are computed on a held-out set of past examples the model did not train on. For anything that changes over time, hold out the most recent weeks rather than a random sample, because in production the model always predicts the future from the past.

📏

Offline ≠ online

Offline scores like AUC, NDCG and RMSE only measure how well the model fits recorded data. They can't see the feedback loop, the user interface, or how people actually react. A 2% better AUC often changes nothing for the business. Treat offline results as a filter for candidates, not as the decision.

🅰️

Online experiments decide

Split users at random. Pick one main metric, plus guardrails that must not get worse, such as latency, revenue and complaints. Run it long enough for the novelty of the change to wear off, and decide the pass/fail rule before you look at results. For ranking, interleaving (mixing both rankings for the same user) gives a clear answer with far less traffic.

Why it takes a while: if 5% of users click today, detecting a small relative lift, say to 5.1%, needs roughly 750,000 users in each group before the difference stands out from random noise. Small products often cannot measure small wins at all, and should test bigger changes.

👻

Shadow mode first

Send real traffic to the new model and log what it predicts, but keep serving the old model's answers to users. You get real input data and real latency numbers with zero risk. It's the ML version of a dark launch.

⏳

Delayed labels

If you only learn the truth after 90 days, you can't wait 90 days to spot a broken model. Use stand-in signals as early warnings: the acceptance rate, the spread of predictions, and how often the new model agrees with the old one. Fill in the real metric once the labels arrive.

Drift & retraining

Models get worse over time because the world keeps changing: new products, new fraud tricks, a marketing campaign that brings in a different kind of user. This is called drift. Watch the model's inputs just as closely as its outputs.

Why inputs? Labels are slow. A fraud label may take 90 days, so accuracy tells you about a problem three months late. Inputs are available instantly. If the share of payments from a new country jumps from 2% to 15% this week, you know today that the model is seeing something it was not trained on.

🧪 “Retrain never” declines slowly, then falls off a cliff when the sudden shift lands. Retraining on a fixed schedule handles slow drift, but reacts late to shocks. Retraining when drift is detected reacts fastest. But watch what happens when you break the pipeline: retraining on broken data makes things worse. That's why data-quality checks must block training when they fail.
📊

Data drift

The inputs themselves change shape. You measure it per feature with scores like PSI or KL divergence, which compare today's spread of values with the training one. It is often harmless, and often the first sign of a broken upstream pipeline.

A common rule of thumb for PSI: below 0.1 means little change, 0.1 to 0.25 is worth a look, and above 0.25 is a significant shift.

🎯

Concept drift

The relationship between the inputs and the answer changes. Fraudsters adapt, tastes shift. You can only see this once the true labels arrive.

🛑

Gate the pipeline

Run automatic data checks (with a tool like Great Expectations) before training and before serving: row counts, how many values are missing, value ranges, the schema, and how fresh the data is. A failed check should stop the model, not just add a warning to a dashboard nobody reads.

🎤
Designing an “ML system” in an interview

Spend most of your time on the data path: where features come from, how you keep them identical between training and serving, how labels are collected, how you evaluate and roll out a change, and what you monitor. Mention the model architecture briefly, then move on. Interviewers for ML-systems roles want to know whether you can build a pipeline that survives contact with reality, not whether you can name architectures.

⚠️
Common mistakes
  • Computing a feature twice. Two separate implementations of “average order value over 7 days” will drift apart. Write one definition and generate both the training and serving copies from it.
  • Shipping because the offline number went up. A 3% better AUC often changes nothing for the business. Shadow it first, then run an A/B test.
  • Monitoring accuracy only. The usual failure is a data pipeline breaking silently. You can see it in the input data long before the labels arrive.
  • Random train/test splits on time-ordered data. Mixing next month's examples into training lets the model peek at the future, so the test score is too good. Split by time: train on older data, test on newer.
  • No fallback when the model service is slow or down. Ranking, pricing and fraud checks sit on the request path. Set a timeout and a simple rule-based answer to use instead, so a model outage does not become a product outage.
🎤
Interview drill

Debug: A fraud model's precision dropped 20% overnight. How do you triage?

How a strong answer sounds
Check the data path before you blame the model. Did a feature pipeline fail, or start returning nulls and zeros? Did an upstream table change its schema? Compare each feature's values at serving time against the training data, and confirm which model version is actually deployed. Only once the inputs look clean would I consider concept drift, meaning fraudsters adapting. That causes a slow decline, not an overnight drop. Meanwhile, keep a rollback to the previous model version ready.

Design: Serve personalized ranking for 200 candidates per request under 150 ms.

How a strong answer sounds
Use two stages. First, cheap retrieval to pick candidates, using approximate nearest-neighbour search over embeddings or a simple scoring function. Then run the expensive model on only the top 50 or so. Fetch the features for all candidates in one batched request to the online store, not one request per candidate, and score them all in a single call. Cache the user's own features once per request, precompute item features offline, and set a hard deadline with a simple fallback, such as ranking by popularity, so a slow model can't break the page.

🧠 Key takeaways

  • What you ship is code + data + weights. Version all three, and roll them back together.
  • A feature store writes one definition into two stores: columnar history for training, key-value for serving.
  • Point-in-time joins prevent leakage. One shared definition prevents training/serving skew.
  • Pick batch, real-time or streaming inference based on how fresh the data must be and whether you need the current request's context. Watch out for N+1 feature lookups.
  • Offline metrics narrow the candidates. Shadow deployments and online experiments make the decision.
  • Monitor the input data and its quality, not just accuracy. Silent pipeline failures are the top cause of a model going bad.
  • Retrain on a schedule and when drift appears, with data-quality checks so you never retrain on broken data.

Check your understanding

A fraud model scores 0.95 AUC offline and 0.71 in production. The feature “chargebacks for this card” was computed from today's data over historical transactions. What happened?

When you actually score a live transaction, that future information doesn't exist yet. A point-in-time join computes each feature as of the event's own timestamp.

What problem does a feature store's dual online/offline storage solve?

Two hand-written versions of the same feature always drift apart eventually. The store makes one definition produce both copies.

Your ranking service must score 300 candidates in under 150 ms. Feature lookups are 1 ms each. What's the fix?

One round trip per candidate is the N+1 problem. Batched lookups plus two-stage ranking is the standard design.

Ground-truth labels for loan defaults arrive 6 months later. How do you detect a broken model sooner?

Watching the inputs catches broken pipelines and shifting user populations straight away. The delayed labels later confirm the real number.

A new model improves offline AUC by 3%. What should happen before it serves all users?

Offline gains often don't carry over. Shadow mode checks the inputs and latency; the experiment measures the real effect on users.
