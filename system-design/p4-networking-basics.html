Networking Basics

Every arrow on a system-design diagram is a network connection, and every connection costs time and can fail. A request can't just “go to Instagram”: it needs an address, a way to look that address up, rules for delivery, and protection from eavesdroppers. This chapter teaches the handful of networking ideas the whole course relies on — IP addresses, ports, DNS, TCP and UDP, TLS — and the two different meanings of “fast”.

How data travels: packets and routers

When your laptop sends a 2 MB photo, it doesn't send one giant blob. The data is chopped into packets: small chunks, usually around 1,500 bytes each. Each packet carries a label with where it's from and where it's going, like an envelope. A 2 MB photo becomes roughly 1,400 packets.

Packets travel through a series of routers — devices whose only job is to look at a packet's destination and forward it one step closer. Your home Wi-Fi box is a router. So are the big machines run by internet providers. A packet crossing the world typically passes through 10 to 20 routers, called hops. Different packets from the same photo can even take different routes and arrive out of order.

✉️
Analogy: posting a book one page at a time

Imagine mailing a book by tearing out each page, putting it in its own numbered envelope, and posting them all. Each sorting office forwards envelopes towards the destination. Some envelopes take different routes, a few arrive out of order, and occasionally one gets lost. Someone at the other end must put the pages back in order and ask for missing ones. That's the internet — and “someone” is TCP, which you'll meet below.

Why packets and not one long connection wire, like old telephone calls? Because sharing is efficient. Millions of conversations interleave their packets on the same cables, and if one router fails, packets simply route around it. The cost is that delivery is best effort: the network itself makes no promise that a packet arrives, arrives once, or arrives in order.

IP addresses: which machine

Every device on a network has an IP address (IP stands for Internet Protocol), which works like a street address for a building. Packets are delivered to IP addresses.

IPv4

Four numbers from 0 to 255, like 93.184.216.34. That's 32 bits, so there are about 4.3 billion possible addresses — fewer than the number of devices on Earth, which is why several workarounds exist.

IPv6

128-bit addresses written in hexadecimal, like 2606:2800:220:1::248. There are about 3.4 × 10³⁸ of them — effectively unlimited. Adoption is steadily growing; most systems support both.

Public vs private addresses, and NAT

Some address ranges are reserved as private: 10.x.x.x, 192.168.x.x and 172.16–31.x.x. They're used inside homes, offices and data centers and can't be reached directly from the internet. Your laptop probably has something like 192.168.1.23.

When your laptop talks to the internet, your router swaps the private address for its own single public address and remembers which conversation belongs to which device. This is NAT (network address translation). It lets a whole household share one public IPv4 address. In a data center, the same idea means your database servers can have only private addresses, reachable by your own services but invisible to the outside world — an important security layer.

Ports: which program

One machine runs many programs that use the network: a web server, a database, an SSH server for administrators. An IP address gets a packet to the right machine; a port — a number from 0 to 65,535 — gets it to the right program on that machine. If the IP address is the building, the port is the apartment number.

A program “listens” on a port, and the OS hands it every packet addressed to that port. Well-known services use standard ports, so clients know where to knock:

DNS: turning names into addresses

People remember shop.com; the network needs 93.184.216.34. The Domain Name System (DNS) is the internet's phone book. It is itself a huge distributed system, organised as a tree so that no single server has to know every name.

A full DNS lookup (when nothing is cached)Step-through
  1. Your browser and OS first check their own caches: have we looked up shop.com recently? Most lookups end right here, taking no time at all.
  2. Not cached, so the laptop asks a recursive resolver — usually run by your internet provider, or a public one like 1.1.1.1 or 8.8.8.8. The resolver does the legwork. It also has a big cache shared by all its users, so popular names are usually answered immediately.
  3. If the resolver doesn't know, it starts at the top: a root server. The root doesn't know shop.com, but it knows who is in charge of .com.
  4. The top-level domain (TLD) server for .com doesn't know the address either, but it knows which name servers the owner of shop.com has registered.
  5. shop.com's authoritative name server gives the real answer: 93.184.216.34, along with a TTL (time to live) of 300 seconds — “you may cache this for 5 minutes”.
  6. The resolver passes the answer back and caches it for the TTL. So does your laptop. For the next five minutes, nobody using this resolver needs to repeat steps 3–5.

DNS matters to system designers in two ways. First, it's the first step of nearly every request, so it must be fast — which is why caching is everywhere. Second, DNS is a traffic-steering tool: by changing what a name resolves to, you can send users to a different data center, or answer users in Europe with a European server's address. The TTL is the trade-off: long TTLs mean fewer lookups, short TTLs mean changes take effect quickly. You'll use this for failover in Chapter 22.

TCP and UDP: how data is delivered

IP gets packets to the right machine — on a best-effort basis. On top of IP sit two transport protocols that programs actually use. They make opposite choices.

📦 TCP — reliable and ordered

Transmission Control Protocol. Before sending data, the two sides set up a connection. Every packet is numbered. The receiver acknowledges what arrived; anything unacknowledged is re-sent; the receiver reassembles everything in order. TCP also slows down when the network is congested. The price: setup time, and delays whenever a packet is lost. Used for web pages, APIs, databases, payments, email.

🚀 UDP — fast and unguaranteed

User Datagram Protocol. No connection, no acknowledgements, no re-sending, no ordering. Each packet is sent and forgotten. Lost packets stay lost. The benefit: no setup and no waiting. Used where late data is useless — video calls, online games, live streams — and for tiny exchanges like DNS queries.

The TCP handshake

Before any data flows, TCP does a three-way handshake: the client sends SYN (“let's talk”), the server replies SYN-ACK (“sure, ready”), and the client sends ACK (“great”), usually together with its first data. That costs one full round trip before the request can even be sent. On a 100 ms link, that's 100 ms of pure waiting — which is why clients keep connections open and reuse them for many requests (called keep-alive or connection pooling).

For a video call, UDP's gaps are a tiny glitch — and waiting for a re-sent frame would be worse. For a bank transfer, a missing piece is unacceptable, so TCP's delay is the right price. (Newer protocols such as QUIC, used by HTTP/3, build reliability on top of UDP to avoid some of TCP's delays.)

TLS and HTTPS: keeping it private

Packets pass through many routers owned by other people. Without protection, anyone along the way could read them — passwords, messages, card numbers — or even change them. TLS (Transport Layer Security) wraps a TCP connection in encryption. HTTP over TLS is HTTPS, the padlock in your browser.

🔒

Confidentiality

The data is encrypted. Routers along the way see only scrambled bytes, plus the destination address.

🪪

Authenticity

The server proves who it is with a certificate, signed by an authority your device trusts. That stops an impostor from pretending to be your bank.

🧷

Integrity

Any tampering with the data in transit is detected, so nobody can quietly change “pay £10” into “pay £1,000”.

Setting up TLS takes a handshake of its own, in which the two sides agree on encryption keys: one extra round trip with modern TLS 1.3 (two with older versions). After that, encrypting and decrypting is cheap on modern CPUs. Today essentially all traffic on the public internet uses TLS, and many companies encrypt traffic inside their data centers too. Chapter 11 covers how it works.

Follow one request across the network

Now put it all together. Step through a first visit to shop.com and count the round trips.

From your laptop to a server and backStep-through
  1. Your browser has a name, shop.com, but needs an IP address to send anything. First it checks its DNS cache.
  2. Not cached, so it asks a DNS resolver over UDP, port 53: “What's the IP for shop.com?” Answer: 93.184.216.34. Round trip 1.
  3. The laptop opens a TCP connection to 93.184.216.34:443: SYN, SYN-ACK, ACK. Your router's NAT swaps your private address for its public one on the way out. Round trip 2.
  4. The two sides agree on encryption keys and the server shows its certificate. Round trip 3.
  5. Over the encrypted connection, the browser sends GET /products. The server's OS sees port 443 and hands the bytes to the web app listening there.
  6. A thread in the app sends a query to the database at its private address, port 5432 — a round trip inside the data center, well under a millisecond of network time.
  7. The app sends 200 OK plus the data back over the same connection. Round trip 4 completes.
  8. DNS + TCP + TLS + request ≈ 4 round trips before the first byte of the page arrives. If the server is 100 ms away, that's 400 ms of pure waiting. A second request on the same connection needs only 1 round trip — which is why connection reuse and CDNs near users matter so much.

Latency vs bandwidth: two kinds of “fast”

People say a connection is “fast”, but they could mean two very different things:

⏱️ Latency — how long one trip takes

The delay for a message to get there and back (the round-trip time, RTT), in milliseconds. Distance sets a hard floor: light in fibre covers about 200 km per millisecond, so New York to London (~5,600 km) can never be faster than about 56 ms round trip. Real routes are longer and add router delays.

🚚 Bandwidth — how much fits per second

How many bits the link carries each second, in Mbps or Gbps (mega/gigabits per second). A 100 Mbps link moves 12.5 megabytes per second, because 1 byte = 8 bits. Throughput is the rate you actually achieve, which is often lower.

🛣️
Analogy: a motorway

Latency is how long the drive takes. Bandwidth is how many lanes the motorway has. Adding lanes lets more cars through per hour, but doesn't make any single car's trip shorter.

A simple model covers most cases: time ≈ round trips × RTT + size ÷ bandwidth. Worked example: a 20 KB API response from a server 100 ms away, over 50 Mbps, needing 4 round trips on first contact. Waiting: 4 × 100 ms = 400 ms. Transfer: 20 KB = 160,000 bits ÷ 50,000,000 bits/s ≈ 3 ms. The response is 99% waiting. Doubling bandwidth would save about 1.5 ms; moving the server closer would save hundreds.

Simplified model: time ≈ round trips × RTT + size ÷ bandwidth, with RTT at the speed-of-light minimum. Real networks add routing and queueing delays on top.

🧪 Try it: a small API response (a few KB) is almost all waiting — a faster link barely helps, but a closer server does. A 1 GB download is the opposite. That's why CDNs (Chapter 6) move content closer, and why big files are split and sent in parallel.
⚠️
Common mistakes
  • Mixing up bits and bytes. A “100 Mbps” connection moves 12.5 MB per second, not 100. Network speeds are in bits; file sizes are in bytes.
  • Confusing latency with bandwidth. A bigger pipe doesn't shorten the trip. For small requests, distance and the number of round trips decide the speed.
  • Assuming the network is reliable. Packets get lost, connections drop, and a request can succeed on the server while its response is lost. Clients need timeouts and careful retries.
  • Opening a new connection per request. Each one costs TCP and TLS round trips. Reuse connections with keep-alive and pools.
  • Forgetting DNS caching. A DNS change takes up to the old TTL to reach everyone. Lower the TTL well before a planned migration.
🎤
Interview drill

Explain it simply: Why does a website load slowly for someone on the other side of the world, even with a very fast internet connection?

How a strong answer sounds
Loading a page needs several round trips before any content arrives: DNS, the TCP handshake, TLS, then the request. Each round trip across the world takes 150 ms or more, limited by the speed of light in fibre. A fast connection is more bandwidth, which helps big downloads, but it can't shorten those trips. The fixes are fewer round trips — reused connections, TLS 1.3 — and moving content closer with a CDN or a server in their region.

Choose and justify: TCP or UDP for (a) a payment API, (b) a multiplayer game's player positions, (c) a DNS lookup?

How a strong answer sounds
(a) TCP: every byte must arrive, in order, and a delay is acceptable. (b) UDP: positions are sent many times a second, so a lost update is replaced by the next one; waiting for a re-send would make the game feel laggy. (c) UDP by default: a DNS query and answer each fit in one small packet, so a connection setup would double the cost; if no answer comes, the client simply asks again. (Large DNS answers fall back to TCP.)

🧠 Key takeaways

  • Data travels as small packets, forwarded hop by hop by routers. The network itself is best effort: packets can be lost, duplicated or reordered.
  • An IP address finds the machine; a port finds the program. Private addresses plus NAT keep internal machines hidden from the internet.
  • DNS turns names into IP addresses through a tree of servers, with answers cached for their TTL. It also steers traffic.
  • TCP gives reliable, ordered delivery at the cost of a handshake and re-send delays; UDP is fast and unguaranteed.
  • TLS (the S in HTTPS) encrypts traffic, proves the server's identity, and detects tampering, for one extra round trip.
  • A first request often costs ~4 round trips. Latency (trip time) and bandwidth (bits per second) are different; small requests are ruled by latency.

Check your understanding

A packet reaches the right machine. What decides which program on that machine receives it?

The IP address identifies the machine (the building); the port identifies the program listening on it (the apartment). A web server listens on 443, PostgreSQL on 5432, and so on.

You change your domain's DNS record to point at a new server. The old record had a TTL of 1 hour. What happens?

Resolvers and devices cache the old answer for its TTL. Until each cache expires, it keeps returning the old address. That's why engineers lower the TTL before a planned move.

Which job is the best fit for UDP?

In a live call, a frame that arrives late is useless, so re-sending it would only add delay. UDP's “send and forget” fits. Downloads, payments and web pages need every byte in order, so they use TCP (or reliable protocols built on UDP, like QUIC).

You download a 1 GB file over a 100 Mbps connection. Ignoring latency, roughly how long does it take?

1 GB = 8,000 megabits (1 byte = 8 bits). 8,000 Mb ÷ 100 Mb per second = 80 seconds. Forgetting the ×8 is the classic mistake — it gives 10 seconds.

A tiny API call to a server 150 ms away takes about 600 ms the first time and about 150 ms on later calls. What best explains the difference?

First contact costs about four round trips: DNS, TCP, TLS and the request itself — 4 × 150 = 600 ms. With the name cached and the connection kept alive, each later call needs only one round trip.
