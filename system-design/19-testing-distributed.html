Testing Distributed Systems

Every earlier chapter designed systems that tolerate partial failure, reorder messages and replicate asynchronously. This chapter asks the uncomfortable follow-up: how do you know any of it actually works? Ordinary tests run one process, on one machine, with no clock skew and no packet loss — precisely the conditions under which distributed bugs never appear.

  • Understand why concurrency and partial failure defeat example-based tests
  • Place tests along a pipeline that catches bugs early and cheaply
  • Use contract tests instead of brittle end-to-end suites
  • Find edge cases with property-based testing and shrinking
  • Hunt consistency violations with fault injection and deterministic simulation
  • Load-test and verify safely in production

Why this is hard

🎲

Nondeterminism

Message order, thread scheduling, GC pauses and retries differ every run. A bug that appears in 1 of 10,000 interleavings passes your test suite 10,000 times — then happens hourly in production.

🔌

Partial failure

The interesting states are “the write succeeded but the ack was lost”, “the follower is 9 seconds behind”, “the lock expired mid-work”. None of these occur when everything runs happily on localhost.

🕰️

Time

Timeouts, TTLs, leases, watermarks and clock skew are logic. Tests that sleep(5) to wait for them are slow, flaky, and still don't test what happens at the boundary.

🧟
Flaky tests are a design smell

The usual fix — add a retry, add a sleep — hides a genuine race. The durable fixes are injectable clocks (never call the system clock directly), deterministic scheduling in tests, and waiting on conditions rather than durations. A suite people re-run until it's green provides no signal at all.

Where should a bug be caught?

Every stage that a bug survives multiplies the cost of fixing it. The goal isn't “100% coverage” — it's pushing each class of bug to the cheapest stage that can realistically catch it.

The layers, concretely

Pure logic, no I/O: ranking functions, rate-limiter maths, retry backoff, sharding functions, state machines. Milliseconds to run, so run thousands. Inject the clock and the random source so the tests are deterministic.

If a “unit” test needs five mocks, that's a sign the unit is really an orchestration — test it as integration instead, or move the logic somewhere pure.

Your service plus its real dependencies — a real database, a real broker — started in containers (Testcontainers, docker-compose). This catches the things mocks lie about: SQL that doesn't parse, missing indexes, transaction behaviour, serialization formats, migrations.

Never mock the database for queries you care about. An in-memory substitute has different isolation semantics, different type coercion and different failure modes.

The consumer writes down exactly what it needs from the provider; that expectation becomes a test the provider runs in its own CI. If the provider changes a field, its build fails — before deploying.

// consumer test (Pact-style): "when I ask for order 7321, I need these fields"
provider('orders-api')
  .given('order 7321 exists')
  .uponReceiving('a request for order 7321')
  .withRequest({ method: 'GET', path: '/v1/orders/7321' })
  .willRespondWith({ status: 200, body: { id: like(7321), total_cents: like(8900), status: like('PAID') } });

This replaces most of what teams try to get from end-to-end suites, at a fraction of the runtime and flakiness. Schema registries (Avro/Protobuf compatibility checks) do the same job for event streams (Chapter 17).

A handful of journeys through the real system: sign up, checkout, refund. Valuable as smoke tests, terrible as your main safety net — they're slow, flaky, and when they fail they rarely tell you which service broke.

Keep them few, make them deterministic (seeded data, no shared mutable fixtures), and run them against every environment as a health check rather than a change gate.

Some properties only exist in production: real traffic shapes, real data skew, real dependency behaviour. Verify there deliberately.

  • Synthetic monitoring: a robot performs the critical journey every minute from several regions.
  • Canary + automated analysis (Chapter 21): compare error rate and latency against the baseline before promoting.
  • Shadow / dark traffic: mirror real requests to the new version, discard the responses, compare them offline.
  • Feature flags and dark launches: ship code disabled, enable for 1% of users, watch.
  • Chaos experiments (Chapter 22) and game days for failover paths.

Property-based testing

Example-based tests check the cases you thought of. Property-based tests state an invariant — something that must hold for all inputs — then generate hundreds of random inputs to try to break it, and shrink any failure to a minimal counterexample.

A buggy “merge overlapping intervals” — find and shrink a counterexampleSimulator
// Implementation under test (has a real bug)
function merge(iv) {
  const out = [];
  for (const [s, e] of iv) {           // ⚠️ no sort!
    const last = out[out.length - 1];
    if (last && s <= last[1]) last[1] = Math.max(last[1], e);
    else out.push([s, e]);
  }
  return out;
}

// Property: outputs are disjoint, and every input point is still covered

Fault injection & deterministic simulation

The most valuable distributed-systems tests control the environment: they decide when packets drop, when nodes pause, and in which order messages arrive — all from a random seed, so any failure replays exactly.

🎰

Deterministic simulation

FoundationDB famously runs its whole database in a single-threaded simulator where time, disks and the network are fake and driven by a seed. A week of simulated chaos runs in hours, and every bug reproduces exactly. TigerBeetle, Antithesis and others use the same idea.

🧨

Fault injection in staging

Kill pods, add 300 ms of latency, drop 5% of packets, blackhole a dependency, fill a disk, pause a process (to simulate a GC pause and test your fencing tokens — Chapter 17). Tools: toxiproxy, Chaos Mesh, AWS FIS.

📐

Formal methods

For protocols where a subtle bug is catastrophic (consensus, membership, payment state machines), model the protocol in TLA+ or Alloy and let the checker explore every interleaving. AWS uses TLA+ on core services precisely because tests can't cover that space.

Load, soak and capacity testing

📈

Open vs closed models

A closed model (fixed number of virtual users waiting for responses) hides overload — as the system slows, load drops. An open model (fixed arrival rate, regardless of responses) is what real traffic does, and it's what reveals queue growth and collapse (Chapter 4). Most tools default to closed; choose deliberately.

⏳

Soak & spike

Run at 70% load for 12 hours to surface leaks, unbounded caches, disk fill, connection exhaustion and log growth. Then spike to 4× instantly to test autoscaling lag, backpressure and shedding.

🎯

Test to failure, on purpose

Don't just confirm “it handles 10K rps”. Push until something breaks so you know what breaks first, at what number, and whether it degrades or collapses. That number is your capacity plan (Chapter 24).

🧬

Realistic data & traffic

Uniform random keys hide hot partitions and cache behaviour. Replay anonymized production traffic shapes, with production-like data volumes and skew, or your results are fiction.

🎤
In an interview

When asked “how would you test this?”, avoid “unit and integration tests”. Say which risk each layer buys down: contract tests for the service boundary, property tests for the sharding/ranking logic, fault injection for the failover path, a shadow deployment for the new ranking model, and a canary with automated analysis for the rollout. That's a systems answer, not a QA answer.

⚠️
Common mistakes
  • Mocking the database. Mocks encode your assumptions, not the database's behaviour — SQL errors, isolation and index problems all slip through.
  • Relying on end-to-end tests as the safety net. Slow, flaky, and they tell you something broke without telling you what.
  • Retrying flaky tests. Intermittent failures are usually real races; hiding them moves the bug to production.
🎤
Interview drill

Plan: What tests would you write for the outbox relay from Chapter 17?

How a strong answer sounds
Unit tests for the batching and backoff logic with an injected clock. Integration tests against a real database and broker in containers, covering: relay crashes after publish but before marking sent (expect a duplicate, and assert the consumer dedupes), broker unavailable (rows accumulate, nothing lost), and ordering per aggregate. Property test: for any interleaving of writes and crashes, every committed row is published at least once. Then a fault-injection test in staging that kills the relay mid-batch under load.

Explain: Your service passes CI but fails in production once a week. How do you hunt it?

How a strong answer sounds
Assume nondeterminism: concurrency, time, or partial failure. Reproduce by controlling those — deterministic simulation with a seed, fault injection (latency, packet loss, pauses), and property tests over random interleavings rather than more examples. In parallel, improve observability so the next occurrence is diagnosable: structured logs with request IDs, traces on the suspicious path, and metrics on the invariant you believe is being violated.

🧠 Key takeaways

  • Distributed bugs come from nondeterminism, partial failure and time — conditions ordinary tests never create.
  • Push every class of bug to the cheapest stage that can catch it; cost multiplies at each stage it survives.
  • Integration tests against real dependencies beat mocks for anything involving a database or broker.
  • Contract tests catch incompatible changes at the boundary without slow end-to-end suites.
  • Property-based testing plus shrinking finds edge cases you'd never enumerate, and yields minimal repros.
  • Seeded fault injection and deterministic simulation make rare interleavings reproducible.
  • Load-test with an open model, soak for leaks, and test to failure to learn your real capacity.
  • Finish verification in production: synthetics, shadow traffic, canaries and flags.

Check your understanding

Service A breaks when Service B renames a JSON field. Which test type catches this most cheaply?

A mock encodes A's assumption but never checks it against B. The contract test fails B's build before it deploys.

What does “shrinking” mean in property-based testing?

A 40-element random failure is unreadable; shrinking turns it into a two-element case you can debug and keep as a regression test.

Why do FoundationDB-style simulators run the whole system single-threaded with fake time and network?

Reproducibility is the whole point: a one-in-a-billion interleaving becomes a test case you can rerun while you debug it.

Your load test with 500 virtual users shows stable 200 ms latency, but production melts at the same request rate. Likely cause?

Closed models feed back on themselves. Real users keep arriving regardless of how slow you are — test with a fixed arrival rate.

A test fails roughly once every 30 runs. The team adds a retry. What's the risk?

Intermittent failures usually indicate genuine nondeterminism. Fix it with injectable clocks, condition-based waits or deterministic scheduling.
