Testing Distributed Systems

Earlier chapters designed systems that keep working when some parts fail, when messages arrive out of order, and when copies of data lag behind. This chapter asks the awkward follow-up: how do you know any of it actually works? Ordinary tests run one process on one machine. Clocks agree and no network packets get lost. Those are exactly the conditions where distributed bugs never show up.

  • Understand why concurrency and partial failure defeat example-based tests
  • Place tests along a pipeline that catches bugs early and cheaply
  • Use contract tests instead of brittle end-to-end suites
  • Find edge cases with property-based testing and shrinking
  • Hunt consistency violations with fault injection and deterministic simulation
  • Load-test and verify safely in production

Why this is hard

A normal test works like this: set up some input, call the code, check the output. If the output is right today, it will be right tomorrow, because the code does the same thing every time. Distributed systems break that promise. The same code, with the same input, can give a different result depending on which message arrived first or whether a network call timed out. Three things cause this.

🎲

Nondeterminism

Things happen in a different order on every run: messages, thread scheduling, GC pauses (when the runtime freezes to clean up memory), retries. Say a bug appears in only 1 of 10,000 possible orderings (interleavings). It passes your test suite 10,000 times, then happens every hour in production.

🔌

Partial failure

The dangerous states look like “the write worked but the ack (reply) was lost”, “the follower is 9 seconds behind”, or “the lock expired halfway through the work”. None of these happen when everything runs happily on localhost.

🕰️

Time

Timeouts, TTLs (expiry times), leases, watermarks and clock skew (machines' clocks disagreeing) are all part of your logic. Tests that sleep(5) to wait for them are slow and flaky. And they still don't test what happens right at the edge.

A tiny example of how an ordering bug hides. Two workers both run “read the counter, add 1, write it back” on a counter that starts at 5. If worker A finishes before worker B starts, the counter ends at 7, which is correct. If both read 5 before either writes, both write 6, and one increment is lost. On your laptop, A almost always finishes first, because the work takes microseconds. So the test passes. In production, with hundreds of workers and slow network calls in between, the bad ordering happens many times a day.

🧟
Flaky tests are a design smell

A flaky test passes sometimes and fails sometimes. The usual fix, adding a retry or a sleep, hides a real race condition (a bug that depends on timing). Lasting fixes are:

  • Injectable clocks: code asks a clock object for the time, and tests pass in a fake one. Never call the system clock directly. A test of a 30-minute session expiry can then say “move the fake clock forward 30 minutes and 1 second” and finish instantly, and it can also check the exact edge at 29:59.
  • Deterministic scheduling in tests, so things run in a fixed order. The test (not the operating system) decides which task runs next, so it can force the bad ordering on purpose.
  • Waiting on conditions (“until the row exists”) instead of fixed durations. Poll every few milliseconds with an overall limit, for example 5 seconds. A fast machine finishes in 20 ms; a slow CI machine still passes instead of failing because 1 second wasn't enough.

If people re-run a suite until it's green, it tells you nothing at all.

Where should a bug be caught?

Each stage a bug slips past makes it more expensive to fix. A typo caught on your laptop costs seconds. The same bug found by customers costs hours of incident work. So the goal isn't “100% coverage”. It's catching each kind of bug at the cheapest stage that can realistically find it.

Why does the cost grow so fast? On your laptop, you still remember the code you just wrote, and only you are affected. In CI, someone has to read a failure log. In production, the bug has already hurt users. Now someone must notice it, find which of many services caused it, roll back or patch, maybe repair bad data, and explain what happened. The simulator's “relative cost” column (1× for a unit test, up to 300× in production) is a rough illustration of that growth, not a measured law.

This is often drawn as a test pyramid: many fast unit tests at the bottom, fewer integration and contract tests in the middle, and only a handful of slow end-to-end tests at the top. The shape follows from cost: cheap tests can be numerous; expensive ones must be few and chosen carefully.

The layers, concretely

Test pure logic with no I/O (no disk, network or database): ranking functions, rate-limiter maths, retry backoff, sharding functions, state machines. Each runs in milliseconds, so you can run thousands. Pass in the clock and the random-number source, so every run gives the same result.

Example: an exponential backoff function should wait 100 ms, then 200, 400, 800, and never more than a 5-second cap. A unit test calls it with attempt numbers 1 to 10 and checks each result, including the edges: attempt 0, and attempt 60, where 100 × 260 would overflow if the code doesn't cap before multiplying.

If a “unit” test needs five mocks, the “unit” is really code that coordinates other parts. Test it as an integration test instead, or move the logic into a pure function.

Test your service together with its real dependencies, such as a real database and a real message broker, started in containers (Testcontainers, docker-compose). This catches the things mocks get wrong: SQL that doesn't parse, missing indexes, how transactions behave, data formats, and migrations.

Never mock the database for queries you care about. An in-memory stand-in handles isolation differently, converts types differently, and fails in different ways.

The trade-off is speed: starting a Postgres container takes a few seconds, so start it once per test run and reset the data between tests (for example by wrapping each test in a transaction that is rolled back), rather than starting a fresh database for every test.

The consumer (the service making the call) writes down exactly what it needs from the provider (the service answering). That written expectation becomes a test the provider runs in its own CI. If the provider changes a field the consumer relies on, the provider's build fails before it deploys.

// consumer test (Pact-style): "when I ask for order 7321, I need these fields"
provider('orders-api')
  .given('order 7321 exists')
  .uponReceiving('a request for order 7321')
  .withRequest({ method: 'GET', path: '/v1/orders/7321' })
  .willRespondWith({ status: 200, body: { id: like(7321), total_cents: like(8900), status: like('PAID') } });

Here like(8900) means “any number, shaped like this one”. The consumer is not pinning exact values, only the fields and types it reads. So the provider is free to add new fields or change other fields nobody uses. It fails only if it removes or renames id, total_cents or status, or changes their type, which is exactly the change that would break this consumer.

This gives you most of what teams hope to get from end-to-end suites, but runs far faster and is far less flaky. For event streams, schema registries (which check that Avro/Protobuf message formats stay compatible) do the same job (Chapter 17).

Run a few real user journeys through the whole system: sign up, checkout, refund. They are useful as smoke tests (quick “is it basically working?” checks). They are a poor main safety net: slow, flaky, and when they fail they rarely tell you which service broke.

Keep them few. Make them repeatable, using fixed seeded test data and no shared data that tests change. Run them against every environment as a health check, not as a gate every change must pass.

Some things only exist in production: real traffic patterns, real data skew, real behaviour of the services you depend on. So check there, on purpose.

  • Synthetic monitoring: a robot walks through the most important journey every minute, from several regions.
  • Canary + automated analysis (Chapter 21): send a little traffic to the new version and compare its error rate and latency with the old one before rolling it out further.
  • Shadow / dark traffic: copy real requests to the new version, throw its responses away, and compare them offline. Only safe for reads, or when writes go to a separate copy: a shadowed “charge card” request must never really charge anyone.
  • Feature flags and dark launches: ship the code switched off, turn it on for 1% of users, and watch.
  • Chaos experiments (Chapter 22) and game days (planned practice drills) for failover paths.

Property-based testing

Normal example-based tests only check the cases you thought of. Property-based tests work differently. You state a rule (an invariant) that must be true for every input, such as “sorting never changes the number of items”. The tool then generates hundreds of random inputs to try to break it. When one fails, it shrinks it: it keeps simplifying the input until it finds the smallest one that still fails.

Good properties for backend code often look like these:

  • Round trip: decode(encode(x)) == x for any message x. Catches serialization bugs with odd characters, empty lists or huge numbers.
  • Invariant preserved: after any sequence of deposits and withdrawals, a balance is never negative and always equals the sum of the entries.
  • Same answer as a simple model: a clever sharded cache returns the same values as a plain dictionary, for any sequence of gets and puts.
  • Idempotent: applying the same event twice leaves the same state as applying it once.

Shrinking matters because random failures are messy. The first failing input might be 6 intervals with values up to 17. The tool then tries smaller versions: drop one interval, does it still fail? Lower a number by one, does it still fail? It keeps every change that still fails and undoes every change that makes the test pass. What is left is the core of the bug, often just two items.

A buggy “merge overlapping intervals” — find and shrink a counterexampleSimulator
// Implementation under test (has a real bug)
function merge(iv) {
  const out = [];
  for (const [s, e] of iv) {           // ⚠️ no sort!
    const last = out[out.length - 1];
    if (last && s <= last[1]) last[1] = Math.max(last[1], e);
    else out.push([s, e]);
  }
  return out;
}

Fault injection & deterministic simulation

The most valuable distributed-systems tests control the environment. The test decides when network packets drop, when machines pause, and what order messages arrive in. All those choices come from a random seed (a starting number for the random generator). Run the same seed again and you get exactly the same failure, so you can debug it.

Why a seed works: a computer's “random” numbers come from a formula. Start the formula at 1337 and it always produces the same sequence, say 0.42, 0.07, 0.91 and so on. If every decision in the test (“drop this packet?”, “which replica answers?”) reads the next number from that sequence, then seed 1337 always makes the same decisions in the same order. The simulator below uses exactly this trick.

It also checks a property of the whole history, not a single output. Here the property is read-your-writes: once a write of value 3 has been acknowledged, no later read may return less than 3. With N=3 and W=1, a write may land on only replica r0. If a later read (R=1) asks only r2, it sees the old value. That is the violation the checker flags.

🧪 Switch to W=2/R=2 and run again. Now every read overlaps with every write on at least one replica, so read-your-writes (you always see your own writes) holds even with network partitions. This is exactly what Jepsen does to real databases. It runs many operations at once while injecting faults, records the history, and then a checker tests that history against a consistency model (such as linearizability or snapshot isolation).
🎰

Deterministic simulation

FoundationDB famously runs its whole database inside a single-threaded simulator. Time, disks and the network are all fake, and a seed drives them. A week of simulated chaos runs in hours, and every bug can be replayed exactly. TigerBeetle, Antithesis and others use the same idea.

🧨

Fault injection in staging

Break things on purpose: kill pods, add 300 ms of delay, drop 5% of packets, make a dependency silently swallow requests, fill a disk. Or pause a process to mimic a GC pause and test your fencing tokens (Chapter 17). Tools: toxiproxy, Chaos Mesh, AWS FIS.

📐

Formal methods

Some protocols can't afford even a subtle bug: consensus, cluster membership, payment state machines. For these, describe the protocol in a modelling language such as TLA+ or Alloy. A checker then tries every possible ordering of events. AWS uses TLA+ on core services because tests can't cover that many cases.

Which one should you reach for? They cost very different amounts. Fault injection in staging is the cheapest start: it uses your real code and off-the-shelf tools, but a failure may be hard to reproduce. Deterministic simulation gives perfect replay, but your code must route all time, randomness and I/O through replaceable pieces, which is a big design commitment best made early. Formal methods check the design, not the code, so a correct TLA+ model can still be implemented wrongly. Most teams start with fault injection and property tests, and add simulation or TLA+ only for the core of a database, a consensus layer or money movement.

Load, soak and capacity testing

Functional tests ask “is the answer right?”. Load tests ask “is it still right, and fast enough, when a lot of people ask at once?”. Many real outages are not logic bugs at all. A connection pool of 50 runs out at 3,000 requests per second, or a queue grows faster than workers drain it. You only see these under realistic load.

📈

Open vs closed models

A closed model uses a fixed number of virtual users, each waiting for a reply before sending the next request. It hides overload: as the system slows down, the load drops too. An open model sends requests at a fixed rate, whatever the replies. That is how real traffic behaves, and it shows queues growing and the system collapsing (Chapter 4). Most tools default to closed, so choose on purpose.

Numbers: 500 users each waiting for a 200 ms reply send about 2,500 requests per second. If latency rises to 1 s, the same 500 users send only 500 per second, so the load drops fivefold just as the system struggles. Real users would keep arriving at 2,500 per second.

⏳

Soak & spike

A soak test runs at 70% load for 12 hours. It reveals slow problems: memory leaks, caches that grow forever, disks filling up, running out of connections, growing logs. A spike test jumps to 4× load instantly. It checks how slowly autoscaling reacts, and whether backpressure and load shedding work.

🎯

Test to failure, on purpose

Don't just confirm “it handles 10K requests per second”. Keep pushing until something breaks. Then you know what breaks first, at what number, and whether it slows down gracefully or falls over. That number is your capacity plan (Chapter 24).

🧬

Realistic data & traffic

Evenly spread random keys hide hot partitions and real cache behaviour. Replay the shape of real production traffic (anonymized), with production-sized data and the same skew. Otherwise your results are fiction.

🎤
In an interview

When asked “how would you test this?”, don't just say “unit and integration tests”. Say which risk each kind of test reduces. For example: contract tests for the boundary between services, property tests for the sharding or ranking logic, fault injection for the failover path, a shadow deployment for the new ranking model, and a canary with automated analysis for the rollout. That's a systems answer, not a QA answer.

⚠️
Common mistakes
  • Mocking the database. A mock only captures what you think the database does. SQL errors, isolation problems and index problems all slip through.
  • Relying on end-to-end tests as the safety net. They are slow and flaky, and they tell you something broke without telling you what.
  • Retrying flaky tests. Failures that come and go are usually real timing bugs. Hiding them just moves the bug to production.
  • Testing only the happy path of a remote call. Every network call has at least three outcomes: success, a clear error, and a timeout where you don't know whether it worked. Tests that never simulate the third one miss the most dangerous case.
  • Load-testing with tiny or uniform data. A table with 1,000 rows, or keys spread perfectly evenly, hides slow queries and hot partitions that production will hit on day one.

Interview drill

Plan: What tests would you write for the outbox relay from Chapter 17?

How a strong answer sounds
Unit tests for the batching and backoff logic, using an injected clock. Integration tests against a real database and broker in containers, covering three cases. First, the relay crashes after publishing but before marking the row as sent: expect a duplicate, and check that the consumer removes it. Second, the broker is down: rows pile up, but nothing is lost. Third, ordering is kept per aggregate (per entity). Add a property test: for any order of writes and crashes, every committed row is published at least once. Then a fault-injection test in staging that kills the relay halfway through a batch, under load.

Explain: Your service passes CI but fails in production once a week. How do you hunt it?

How a strong answer sounds
Assume the cause is nondeterminism: concurrency, timing, or partial failure. Reproduce it by taking control of those things. Use deterministic simulation with a seed, fault injection (delay, packet loss, pauses), and property tests over random orderings, rather than adding more examples. At the same time, improve observability so the next occurrence can be diagnosed: structured logs with request IDs, traces on the suspicious path, and metrics on the rule you think is being broken.

🧠 Key takeaways

  • Distributed bugs come from nondeterminism, partial failure and time. Ordinary tests never create those conditions.
  • Catch each kind of bug at the cheapest stage that can find it. The cost grows at every stage it slips past.
  • For anything involving a database or broker, integration tests against the real thing beat mocks.
  • Contract tests catch breaking changes between services, without slow end-to-end suites.
  • Property-based testing with shrinking finds edge cases you'd never think of, and gives you the smallest failing input.
  • Seeded fault injection and deterministic simulation make rare timing bugs repeatable.
  • Load-test with an open model, soak-test for leaks, and push to failure to learn your real capacity.
  • Finish checking in production: synthetic monitors, shadow traffic, canaries and feature flags.

Check your understanding

Service A breaks when Service B renames a JSON field. Which test type catches this most cheaply?

A mock records what A assumes, but never checks it against B. The contract test fails B's build before B deploys.

What does “shrinking” mean in property-based testing?

A random failing input with 40 elements is unreadable. Shrinking turns it into a two-element case you can debug and keep as a regression test.

Why do FoundationDB-style simulators run the whole system single-threaded with fake time and network?

Being able to repeat a failure is the whole point. A one-in-a-billion ordering of events becomes a test case you can rerun while you debug it.

Your load test with 500 virtual users shows stable 200 ms latency, but production melts at the same request rate. Likely cause?

In a closed model, a slower system means fewer requests, so the test eases off by itself. Real users keep arriving however slow you are. Test with a fixed arrival rate.

A test fails roughly once every 30 runs. The team adds a retry. What's the risk?

Failures that come and go usually point to a real timing problem. Fix it with injectable clocks, waiting on conditions, or deterministic scheduling.
