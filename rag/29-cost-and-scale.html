Cost & Scale

A prototype over a few thousand chunks costs nothing. The same design over a hundred million chunks, answering a million questions a day, has a bill. The bill has three main parts:

  • memory for the index;
  • compute for embedding the corpus and every query;
  • tokens for every answer.

Each part scales differently, and each has a lever: quantised vectors, a faster embedder, fewer and shorter chunks in the prompt.

This chapter measures the inputs on the lab's laptop: embedding throughput on GPU and CPU, recall and latency for a sharded index, and token counts per question from earlier chapters. It combines them in a calculator. Prices are inputs you set, because they change by provider and over time.

Index memory

Memory is vectors times bytes per vector, plus the index structure. bge-small's 384 float32 numbers take 1,536 bytes. An HNSW graph with M 16 added about 148 bytes per vector in Chapter 8, and the chunk text and metadata usually live in a separate store. At 100 million chunks that is about 170 GB of vectors and graph in memory: several large machines, or quantisation.

Embedding throughput

Embedding the corpus is a one-off cost that recurs whenever the model changes (Chapter 22). On the lab's laptop, bge-small embedded Atlas chunks of about 216 tokens at 398 chunks per second on the GPU in half precision, 130 in full precision, and 12 on eight CPU threads. At those rates a million chunks take 42 minutes on the GPU and about 23.7 hours on the CPU. Larger embedding models are slower roughly in proportion to their size, and hosted embedding APIs charge per token instead.

memory_gb   = n_vectors * (bytes_per_vector + graph_bytes) / 1e9
embed_hours = n_chunks / chunks_per_second / 3600
tokens_q    = system_prompt + question + k_chunks * tokens_per_chunk + answer_tokens
cost_q      = tokens_in * price_in / 1e6 + tokens_out * price_out / 1e6         # prices from your provider

int8 and binary vectors

Chapter 8 measured the trade on the Atlas's 83,118 sentence vectors:

  • 8-bit scalar quantisation cuts vectors to a quarter, with recall@10 of 0.992.
  • Binary vectors cut them to a thirty-second, but recall fell to 0.47, recovering to 0.80 when the top 100 were rescored with full vectors kept on disk.

Many embedding models are now trained to survive int8 or binary quantisation, and some vector databases quantise by default.

  • 100 million chunks, float32 → int8 → binary: memory falls from about 170 GB to about 53 GB with int8 and under 6 GB with binary codes, at the recall shown.

  • Price per million input tokens: the bill scales linearly. Tokens per question decide how hard a price change hurts.

Sharding an index

When an index outgrows one machine, split it into shards: query every shard, then merge the top results. Recall holds up, and was even slightly higher here, because each shard's graph is smaller. The cost is latency and coordination. In the lab's 83,118 vectors:

  • one shard answered in 0.45 ms;
  • eight shards searched one after another took 2.57 ms;
  • eight shards searched in parallel took 1.37 ms.

Shard when memory or write volume forces it, search shards in parallel, and keep shards balanced. Partitioning by tenant (Chapter 23) lets most queries touch one shard.

Cost per question

Per question, a hosted RAG system pays for one query embedding (negligible), one vector search (negligible per query, but the index must stay in memory) and the model's tokens (dominant). Tokens per question are mostly retrieved context: 1,805 input tokens with ten 120-word sources against about 60 output tokens. Cutting context with reranking and compression (Chapter 16) and caching frequent answers (Chapter 28) usually save more than switching vector database. Track cost per question as a production metric, next to quality and latency (Chapter 36).

💰
Use case: binary and int8 embeddings in production

In 2024 several embedding providers and libraries made quantised embeddings a first-class option. Cohere released embedding models that return int8 and binary vectors directly. Hugging Face and the sentence-transformers maintainers published measurements of binary quantisation with float rescoring: large reductions in memory and search cost, with most retrieval quality kept after rescoring. Vector databases added built-in binary and scalar quantisation with optional rescoring. The economics match this chapter. At hundreds of millions of vectors, memory dominates the infrastructure bill, and a 4× or 32× smaller index can decide whether the system fits on one machine or needs a cluster. The trade is the recall measured in Chapter 8, which rescoring recovers only when the full vectors are kept somewhere.

⚠️
Common mistakes
  • Sizing memory for vectors only.
  • Benchmarking throughput on one chunk at a time.
  • Quantising without measuring recall.
  • Sharding too early.
  • Ignoring context tokens.
  • Hard-coding prices.

Interview drill

Explain it simply: What drives the cost of a RAG system?

How a strong answer sounds
Three things. Index memory: vectors times bytes per vector plus the index graph, which at hundreds of millions of chunks dominates infrastructure cost; int8 or binary quantisation cuts it four to thirty-two times at some recall cost. Embedding compute: a one-off per corpus version, from measured throughput, recurring when the model changes. And tokens per question, mostly retrieved context, which usually dominates the per-question bill with hosted models; reranking to fewer chunks, compressing them, and caching frequent answers are the biggest levers.

Deeper: Estimate the infrastructure for 200 million chunks with a 384-dimension model, and how you would cut it.

How a strong answer sounds
Float32 vectors are 1,536 bytes each, about 310 GB, plus roughly 150 bytes per vector of HNSW graph at M 16, so around 340 GB of RAM before text and metadata: several machines, sharded and searched in parallel. With int8 that falls to about 110 GB; with binary codes plus rescoring from SSD, under 15 GB in RAM. I would measure recall@k against exact search on a sample of real queries for each option: in testing, int8 kept recall at 0.99, while binary needed rescoring to recover from 0.47 to 0.80. Then embedding: at a few hundred chunks per second per GPU, the corpus is days of GPU time, so plan batch jobs and a blue/green index for re-embedding.

🧠 Key takeaways

  • Memory = vectors × (bytes + graph); quantise when it stops fitting.
  • Embedding time comes from measured throughput; GPU half precision was 34× faster than CPU here.
  • int8 keeps recall; binary needs rescoring.
  • Shard for capacity, search shards in parallel, accept some latency.
  • Context tokens drive the per-question bill; cut them first.
