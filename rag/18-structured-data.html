Tables & Structured Data

A lot of what people ask is in tables: order histories, prices, inventory, metrics, spreadsheets. Retrieval built for prose handles tables badly. Turning rows into sentences and retrieving the closest twenty works for "what is the price of X?" and fails for "how many", "how much in total" and "which is largest". Those need every row, not the twenty most similar. The alternative is to let the model write a database query and run it, which brings its own failure modes and a security problem.

The lab builds a SQLite table with one row for each of the Atlas's 4,230 sections. It asks 54 questions whose exact answers are computed in SQL, in four ways: rows retrieved as text, and three versions of text-to-SQL. It also tries five hostile requests against the query path.

  • Explain when tables-as-text works and when it cannot
  • Build a text-to-SQL path and give the model a usable schema
  • Make generated queries safe: read-only, allow-listed, bounded
  • Handle questions that mix tables and text
  • Keep numbers and units correct in the answer

Tables as text

The simplest approach serialises each row as a sentence, such as "Course: DSA. Chapter 3: Arrays. Section: Two pointers. Words: 412.", then embeds and retrieves rows like any chunk. It suits lookups of one row, especially mixed into a prose index. It cannot answer aggregates: a count over 56 chapters, or a sum over 400 sections, needs every matching row, and retrieval returns the most similar twenty. In the lab it answered 35% of lookups and 0% of counts and sums. Small tables can instead go into the prompt whole, as Markdown or CSV, while they fit.

Text-to-SQL

For aggregates, give the model the schema and the question, let it write one query, run it, and have the model phrase the result. Three things decide whether this works:

  • how the schema is shown;
  • whether errors are fed back;
  • whether the model understood the question's logic.

Describing the table in a sentence, the 3B model invented tables called courses and table_name, and half its queries failed (28 errors in 54). Showing it a real CREATE TABLE statement with column comments and three example rows cut errors to 2 and doubled accuracy to 63%. One retry with the error message added a little (65%). What no fix changed were queries that ran and returned the wrong thing.

SYSTEM = """You write one SQLite SELECT query over this single table. Use only this table and these columns.
CREATE TABLE sections (course TEXT, course_name TEXT, chapter_file TEXT, chapter_no REAL, chapter_title TEXT, section TEXT, words INTEGER);
-- example rows: ('databases', 'Database Internals & SQL', '09-indexes-first-look.html', 9.0, 'Indexes: A First Look', 'Why a full scan hurts', 412)
Reply with the SQL only."""
sql = llm(SYSTEM, question)
if not ALLOWED.match(sql) or BANNED.search(sql): raise Refused(sql)              # SELECT only
rows = readonly_conn.execute(sql).fetchmany(20)                                     # read-only connection, bounded result

Safety for generated queries

A model that writes SQL is a SQL injection vector by design: anything in the question, or in a retrieved document, can steer it (Chapter 31). Defend in layers:

  • a database role with read-only access to exactly the views it needs;
  • a SELECT-only allow-list checked before running;
  • row limits and statement timeouts;
  • no access to system catalogues or other schemas;
  • a log of every query.

In the lab the model obligingly wrote DELETE, INSERT, UPDATE and DROP TABLE when asked. The allow-list refused all four, and the read-only connection would have refused them anyway. A fifth request, to list every table including system tables, passed both, because reading the catalogue is a SELECT. That is why the role should only see allow-listed views.

Mixed questions

Many questions need both: "Which of our enterprise customers mentioned outages in their last support ticket?" joins a table (customers, plans) with text (tickets). Route the parts (Chapter 15). The structured part goes to SQL, the text part to retrieval, and the model answers from both results with their sources marked. Alternatively, put the text into the database as a searchable column with full-text or vector search, so a single query can filter on both.

Numbers and units

Language models copy numbers well from short contexts and do arithmetic badly. Let the database compute: sums, averages, differences and percentages belong in SQL, not in the prompt. Pass results as exact values with units and column names, and ask the model to repeat them, not recompute them. Then check: in the lab, answers were graded by whether the exact number appeared. That simple check is worth running in production too, comparing numbers in the answer against numbers in the result set.

Use case: Spider and BIRD, the text-to-SQL benchmarks

In 2018 Tao Yu and colleagues at Yale released Spider. It has about 10,000 questions over 200 databases, with the test databases unseen in training, so models had to read schemas rather than memorise them. Spider showed the gap between writing valid SQL and writing correct SQL, and it judged queries by execution: the right result, not identical text. BIRD (2023) added large, messy, real-world databases with dirty values and questions needing outside knowledge, and models scored far below human experts. Both point to the same habits this chapter measured. Show the real schema with examples, check queries by running them, and remember that a query that runs is not a query that answers the question.

⚠️
Common mistakes
  • Answering aggregates from retrieved rows.
  • Describing the schema in prose.
  • Running generated SQL with a writable account.
  • Trusting a query because it ran.
  • Asking the model to do the arithmetic.
  • Unbounded results.

Interview drill

Explain it simply: How would you let users ask questions about data in a SQL database?

How a strong answer sounds
Text-to-SQL: give the model the real schema, as CREATE TABLE statements with column comments and a few example rows, plus the question, and have it write one SELECT. Run it on a read-only role that can only see allow-listed views, with an allow-list check, row limits and a timeout. Feed errors back once for a retry, then have the model phrase the result, quoting the numbers rather than recomputing them. Retrieving rows as text only works for single-row lookups; counts, sums and rankings need the database to see every row.

Deeper: Your text-to-SQL feature is 60% accurate. Where do you look first?

How a strong answer sounds
Split failures into queries that error and queries that run but return the wrong thing. Errors usually mean the model cannot see the schema well: show DDL with comments and sample rows instead of prose, add a retry with the error message, and narrow the schema to the relevant tables. Wrong-but-running queries need semantic fixes: few-shot examples of tricky patterns (aggregate then rank, joins), views that pre-join or pre-aggregate common needs, a stronger model, and an execution-based evaluation set by question type. In testing, the CREATE TABLE schema doubled accuracy, but "which chapter has the most words" stayed near 10% because the model ranked rows instead of summing groups.

🧠 Key takeaways

  • Rows as text answer lookups; aggregates need every row, so they need a query.
  • Show the schema as real DDL with examples; it doubled accuracy here.
  • Retries fix failing queries, not wrong-but-valid ones; evaluate by execution.
  • Read-only roles, SELECT allow-lists, limits and allow-listed views make generated SQL safe.
  • Let the database compute numbers; let the model quote them.
