Graph RAG & Knowledge Graphs

Vector search finds passages similar to a question. Some questions are not about similarity:

  • "Which documents discuss both X and Y?";
  • "How is A connected to B?";
  • "What are the main themes of this whole collection?".

Graph RAG extracts entities and relations from the text into a knowledge graph and retrieves through it: by following links, intersecting neighbourhoods, or summarising communities. The extraction is done by a model, chunk by chunk, so it is expensive and imperfect.

The lab builds a graph from 300 chunks of the Atlas's Databases course with a 3B model. It measures what extraction costs and how faithful it is. It then compares graph lookup with vector search on 150 "which passages discuss both X and Y?" questions and on one global question.

  • Build a graph from text with a model, and check its quality

Entities and relations

An entity is a thing the text talks about: a concept, a system, a person, a product. A relation links two entities with a type, such as "B-tree | used by | InnoDB". A knowledge graph stores these triples, with each entity and relation pointing back to the passages it came from. The graph makes explicit what embeddings only blur: that two passages mention the same thing, or that a chain of facts connects two topics.

Building a graph

Ask a model to list the entities and relations in each chunk, in a fixed format. Then normalise names, so that "WAL" and "write-ahead log" become one node, and link every node to its source chunks. Extraction quality varies: models miss entities, invent some, name the same thing several ways, and produce relations of uneven value. In the lab the 3B model extracted 6.7 entities per chunk at 5.7 s per chunk. 93% of them appear in their chunk's text, but many were generic ("query", "rows"). The words of the output template itself, "subject" and "object", became two of the most connected entities, and 25 replies did not follow the format at all.

SYS = ("Extract the key technical entities ... and the relations between them. Reply in exactly this format:\n"
       "ENTITIES: entity1; entity2; ...\nRELATIONS:\nsubject | relation | object")
for chunk in chunks:
    ents, rels = parse(llm(SYS, chunk.text))
    for e in ents: graph.add_node(normalise(e)).sources.add(chunk.id)       # every node remembers its passages
    for s, r, o in rels: graph.add_edge(normalise(s), normalise(o), type=r, source=chunk.id)

Graph traversal for retrieval

With a graph, some questions become lookups. "Which passages discuss both X and Y?" is the intersection of the passages linked to X and to Y. "How is A related to B?" is a path search. In principle co-occurrence is a perfect fit for a graph. In the lab it was not: graph intersection found a passage mentioning both entities only 9% of the time, while vector search found one in its top 3 34% and its top 10 50% of the time. The graph only knows that two entities share a passage if the extractor wrote both down for that passage. The small model listed an entity in one chunk and missed it in most of the others that mention it. A graph is only as complete as its extraction, and extraction recall is the first thing to measure. Graph and vector retrieval also combine well: find entities in the question, expand through the graph, and rank the linked passages by similarity, so extraction gaps are covered.

Global questions

"What are the main themes across all our incident reports?" has no single passage that answers it. Vector search returns a few passages similar to the word "themes". Graph-based approaches answer from structure: rank entities by how connected they are, cluster the graph into communities, and summarise each community with a model, ahead of time. Microsoft's GraphRAG (below) does exactly this. The summaries are what make global questions answerable, and they are also most of the cost.

Cost of extraction

Extraction is a model call per chunk, with long outputs, so it costs many times more than embedding the same chunk (Chapter 29). It has to be redone when chunks change or the extraction prompt improves, and its quality needs its own evaluation. Build a graph when questions are about relationships, co-occurrence or the whole collection, and when the corpus is stable enough to amortise the cost. Otherwise, metadata filters, hybrid search and hierarchical summaries often cover the need more cheaply.

Use case: Microsoft GraphRAG

In 2024 Darren Edge and colleagues at Microsoft Research published "From Local to Global: A Graph RAG Approach to Query-Focused Summarization" and released GraphRAG as open source. A language model extracts entities and relations from every chunk. The graph is partitioned into hierarchical communities with the Leiden algorithm, and each community gets a model-written summary. Global questions, such as the main themes in a dataset, are answered by combining community summaries rather than retrieving chunks. On such questions over podcast transcripts and news articles, judges preferred its answers to standard RAG for comprehensiveness and diversity. The authors were explicit about the cost: indexing makes many model calls, which motivated cheaper variants. The lab's small experiment shows both halves: questions a graph answers well, and an extraction step that is slow and imperfect.

⚠️
Common mistakes
  • Building a graph for similarity questions.
  • Trusting extraction unchecked.
  • No name normalisation.
  • Nodes without source links.
  • Underestimating indexing cost.
  • Graph only.

Interview drill

Explain it simply: What is Graph RAG and when is it worth it?

How a strong answer sounds
Graph RAG uses a model to extract entities and relations from every chunk into a knowledge graph, with each node linked back to its passages, and retrieves through the graph: following relations, intersecting entity neighbourhoods, and summarising communities for whole-collection questions. It is worth it when questions are about relationships ("how is A connected to B"), co-occurrence ("which documents mention both"), or the corpus as a whole ("main themes"), and when the corpus is stable enough to amortise the extraction cost. For ordinary similarity questions, vector and hybrid search are cheaper and as good.

Deeper: Your team wants to add a knowledge graph to the RAG system. What do you check before building it?

How a strong answer sounds
Which questions users actually ask that the current system fails, and whether they are relationship, co-occurrence or global questions a graph helps with; measure on a labelled sample. Estimate extraction cost: a model call per chunk with long outputs, redone when content or prompts change. In testing, a small model took seconds per chunk, missed most repeat mentions of an entity, and turned format words into entities, so graph lookup lost to plain vector search; plan extraction-recall checks, normalisation and source links. Consider cheaper alternatives first: metadata filters, hybrid search, hierarchical summaries. If it goes ahead, combine graph expansion with vector ranking rather than replacing retrieval.

🧠 Key takeaways

  • A knowledge graph stores entities and relations, each linked to its passages.
  • Graphs suit co-occurrence, path and global questions, if extraction is good enough; here it was not.
  • Model extraction is slow and incomplete; a graph knows only what was extracted, so measure extraction recall.
  • Community summaries make whole-collection questions answerable, at a high indexing cost.
  • Combine graph expansion with vector ranking; build a graph only for questions that need one.
