Tokens & Context Windows

Models do not read characters or words; they read tokens, pieces of text from a fixed vocabulary. Everything in a RAG system is counted in them: how much context fits in a prompt, what a request costs, how long it takes, and how much of a chunk an embedding model actually sees before it silently stops reading. Two pieces of text of the same length can differ several times over in tokens, depending on language, code and numbers.

This chapter explains tokenisers, counting, context windows, cost and latency per token, and truncation. The lab tokenises the same content seven ways with two real tokenisers, Qwen2.5's (the model this course runs locally) and bge-small's (its embedding model), and measures what fraction of the Atlas corpus would be cut off at the embedding model's limit.

Tokenisers

A tokeniser maps text to a sequence of integer IDs from a fixed vocabulary. Modern ones are subword tokenisers: common words are one token, rare words are split into pieces, so any text can be represented without an enormous vocabulary. Byte-level BPE (byte-pair encoding), used by GPT-style models including Qwen2.5 with its 151,665-token vocabulary, starts from raw bytes, so it never meets an unknown character; anything it has not seen often just becomes more tokens. WordPiece, used by BERT-family models including bge-small with 30,522 tokens, works on characters, lowercases English, and replaces characters outside its vocabulary with an [UNK] token, which carries no meaning at all.

from tokenizers import Tokenizer
tok = Tokenizer.from_file("qwen2.5/tokenizer.json")       # the model's own tokeniser, never a guess
ids = tok.encode(text, add_special_tokens=False).ids
print(len(ids), "tokens")

Counting tokens

Always count with the tokeniser of the model that will read the text. Rules of thumb ("a token is about four characters of English") are fine for back-of-envelope estimates and wrong for anything else: in the lab, the same sentence costs 35 Qwen tokens in English and 155 in Hindi, and a line of order IDs and timestamps costs a token for every 1.5 characters, because byte-level BPE splits digits individually. Across the Atlas corpus, Qwen averaged 1.34 tokens per word. Count prompts before sending them, and log the counts the API returns.

Context windows

The context window is the maximum number of tokens a model handles in one request, input and output together. It must hold the system prompt, any conversation history, the retrieved chunks, the question and room for the answer. A 4,096-token window holds about 7 median Atlas sections once you leave room for instructions and an answer, and a 32,768-token window about 81, at a cost: more context means slower, more expensive requests, and models use the middle of long contexts less reliably (Chapter 16). Budget explicitly: fix the answer allowance and the instructions, then fill the remainder with the best chunks, cutting at chunk boundaries.

Cost and latency per token

Hosted models charge per input token and per output token, output usually several times more; local models cost GPU time instead. Latency has two parts: processing the prompt (prefill), which handles all input tokens in parallel and is relatively fast, and generating the answer, one token at a time, which dominates for long answers. So retrieved context mostly costs money and some time to first token, while answer length mostly costs time. P2 measures both on the local model.

Truncation

Every model has a maximum input length, and many libraries silently cut longer input instead of raising an error. Embedding models are the dangerous case: bge-small reads at most 512 tokens (including two special tokens), and sentence-transformers truncates anything longer without a warning, so the end of a long chunk is never embedded and can never be found. Keep chunks below the embedding model's limit, measured in its own tokens, and check the distribution of chunk lengths before indexing.

Use case: the token tax on other languages

In 2023 researchers at the University of Oxford (Aleksandar Petrov and colleagues) published "Language Model Tokenizers Introduce Unfairness Between Languages", measuring how many tokens popular tokenisers need for the same text translated into many languages. They found that the same content could take several times, and for some languages more than ten times, as many tokens as English, which means higher prices for the same service, slower responses, and less room in the context window for users who write in those languages. Tokenisers trained mostly on English text learn long tokens for English words and short fragments for everything else, exactly the pattern this lab measured for Hindi. Newer multilingual tokenisers narrow the gap, so for a RAG system serving several languages it is worth measuring the token cost per language on your own content when choosing a model.

⚠️
Common mistakes
  • Estimating tokens from characters or words instead of counting.
  • Counting with a different model's tokeniser.
  • Chunks longer than the embedding model's limit, silently truncated.
  • English-only embedding models for multilingual content.
  • Filling the whole window with context and leaving no room for the answer.
  • Cutting context mid-chunk to hit a budget.

Interview drill

Explain it simply: What is a token, and why does it matter for a RAG system?

How a strong answer sounds
A token is a piece of text from the model's fixed vocabulary, often a whole common word or part of a rare one, produced by a subword tokeniser such as BPE. Models read and write tokens, so everything is counted in them: the context window limits how many retrieved chunks fit, prices are per token, latency grows with input and especially output tokens, and embedding models truncate input beyond their limit. Token counts vary a lot by language and content type, so I count with the model's own tokeniser rather than estimating from characters.

Deeper: Retrieval quality is poor for long documents, though short ones work well. What might be happening?

How a strong answer sounds
A likely cause is truncation in the embedding step: if chunks exceed the embedding model's maximum length, often 512 tokens, the library silently embeds only the beginning, so anything later in the chunk can never be retrieved. I would measure chunk lengths with the embedding model's tokeniser and check the share over the limit, then re-chunk below it with sensible overlap, or move to a model with a longer input limit if the content needs it. I would also check that a single long chunk is not diluting its embedding with several topics, and re-run retrieval evaluation on questions whose answers sit late in long documents.

🧠 Key takeaways

  • Models read tokens from a fixed vocabulary; subword tokenisers split rare words into pieces.
  • Count with the model's own tokeniser; language, code and numbers change the ratio a lot.
  • Budget the context window: instructions, chunks, question and answer.
  • Input tokens cost money and time to first token; output tokens cost generation time.
  • Embedding models truncate silently: keep chunks under their limit.
