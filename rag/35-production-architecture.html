Production RAG Architecture

The pipeline of Chapter 2 fits in one script. A RAG system that many teams depend on is a set of services:

  • ingestion jobs that keep indexes fresh;
  • a query service that retrieves, reranks and assembles context;
  • a model gateway;
  • stores for text, vectors, keywords, caches and logs;
  • guards around all of it.

Each part can be slow, wrong or down. The design question is not only how it works, but how it behaves when a part fails.

This chapter lays out the architecture and then prices its failure modes with numbers measured earlier in the course: recall from Chapter 13's 500-term sample, latency from Chapter 28, and citation behaviour from Chapter 10. Pick a failure and see what the fallback path costs.

  • Separate the offline indexing path from the online query path
  • Choose the stores a RAG system needs and what each holds
  • Place guardrails on input, retrieval and output
  • Version indexes so changes can be tested and rolled back
  • Design fallbacks and know what each costs

Online and offline paths

The offline path runs on a schedule or on change events. It lists sources, extracts text, finds personal data, chunks, embeds and writes to the stores (Chapter 22). It can be slow and retried, and it never touches a user request. The online path serves questions:

  • authenticate;
  • check the cache;
  • rewrite if needed;
  • retrieve with permission filters;
  • rerank;
  • assemble context;
  • call the model;
  • check the output;
  • log and return.

The online path must be fast and degrade gracefully. Keep the two paths separate: a re-index must never slow down queries, and a traffic spike must never block ingestion.

ask(question, user):
    ctx  = auth(user)                                      # tenant and groups from the session
    hit  = cache.get(key(question, ctx, INDEX_VERSION))   # Chapter 28
    if hit: return hit
    cand = retrieve(question, filter=ctx, timeout=150ms)   # hybrid; fall back to BM25 alone
    top  = rerank(cand, timeout=200ms) or cand[:5]         # skip reranking on timeout
    ans  = llm(prompt(top, question), timeout=8s)          # or return the passages themselves
    return guard(ans, top)                                 # citations, links, refusals checked

Stores and indexes

Typical stores, each with its own scaling and backup needs:

  • a document and chunk store (text, metadata, permissions, versions);
  • a vector index;
  • a keyword index;
  • optionally a graph or SQL store (Chapters 18 and 26);
  • caches;
  • a trace store for logs and feedback (Chapter 36).

Many teams start with one database that offers several of these, such as PostgreSQL with pgvector and full-text search, and split them out only when scale or isolation demands it.

Guardrails

Guards sit at three points:

  • Input: rate limits, size limits, and a check for abuse or prompt-injection patterns.
  • Retrieval: permission filters inside the search (Chapter 23), and untrusted-content handling (Chapter 31).
  • Output: are citations present and valid (Chapter 17), are links allow-listed, is the answer within policy, and should it abstain (Chapter 32)?

Guards are code and configuration outside the model. A prompt asking the model to behave is a hint, not a guard.

Versioning indexes

Every change to the chunker, embedding model, index parameters or prompt changes answers. Give each index a version that records all of these. Build new versions beside the old (Chapter 22), evaluate them on the golden set (Chapter 19), then shift a small share of traffic and compare online metrics before switching fully. Keep the previous version ready for rollback, and put the version in cache keys and logs so every answer can be traced to what produced it.

Things to try.

  • Embedding service down: fall back to keyword search alone. Retrieval quality drops only from 87.8% to 86.6% on these terms, a cheap fallback here.
  • Keyword index down: dense alone falls to 80.8%. For this corpus, losing keywords hurts more than losing embeddings.
  • Reranker timing out: skipping it cost nothing measurable on this data (Chapter 13).
  • Model overloaded: 3 sources instead of 10 shortens the prompt and, for this model, cited the right source no less often.
  • Model down: returning the passages keeps the service useful at a fraction of the latency.

Failure modes

Beyond outages, production RAG fails quietly, and each quiet failure needs its own monitor (Chapter 36):

  • stale indexes, when ingestion stopped;
  • drift, when users ask about something new;
  • permission sync lag;
  • cache poisoning, a bad answer cached for everyone;
  • runaway costs from long prompts or agent loops;
  • a model update that changes behaviour under an unchanged name.

Write the runbook before the incident: for each component, how it fails, how you detect it, the fallback and how to recover.

Use case: graceful degradation, from Netflix's Hystrix to model gateways

Netflix open-sourced Hystrix in 2012, a library that wrapped every call to another service with a timeout, a circuit breaker and a fallback: what to return when the dependency is slow or down. The idea was that a page with a missing personalised row is better than an error page. Hystrix was retired into maintenance in 2018, but the pattern became standard in service meshes and resilience libraries. RAG systems need it more than most, because they depend on several components that can each be slow: an embedding service, a vector store, a reranker, a model API with rate limits. Model gateways now apply the same pattern to language models, with timeouts, retries, fallbacks to another model and budget limits. The lab's table is the RAG version of a fallback plan, with each row priced.

⚠️
Common mistakes
  • One process for indexing and serving.
  • No timeouts on model calls.
  • No fallbacks.
  • Guardrails as prompt instructions.
  • Unversioned indexes.
  • Monitoring only uptime.

Interview drill

Explain it simply: Sketch the architecture of a production RAG system.

How a strong answer sounds
Two paths. Offline: connectors list and fetch sources, then extraction, personal-data handling, chunking, embedding, and writes to a chunk store, a vector index and a keyword index, all versioned and keyed by document id with permissions. Online: authenticate, check a permission-scoped cache, retrieve with filters inside the search (hybrid), rerank, assemble context within a token budget, call the model through a gateway with timeouts and fallbacks, check citations and links, log the trace with the index version, and return. Plus feedback collection, evaluation on a golden set before every change, and dashboards for freshness, quality, latency and cost.

Deeper: The model API you depend on has a 30-minute outage. What should your RAG product do?

How a strong answer sounds
Degrade, not fail. A circuit breaker on the model gateway trips after a few timeouts so requests stop waiting. Cached answers still serve frequent questions. Other questions fall back to a secondary model if one is configured and evaluated, or to returning the top retrieved passages with titles and links and a notice that summaries are unavailable, which keeps search useful. Retrieval itself is unaffected. Surface the incident on the status page, alert the on-call, and check afterwards that the breaker closed and quality metrics recovered. Each of these fallbacks should have been tested in advance, with known quality and latency.

🧠 Key takeaways

  • Separate the offline indexing path from the online query path.
  • Use as few stores as you can, keyed by document id and versioned.
  • Guardrails are code outside the model, on input, retrieval and output.
  • Version indexes, evaluate before switching, keep rollback ready.
  • Every component needs a timeout and a priced fallback.
