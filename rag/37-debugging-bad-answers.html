Debugging a Bad Answer

"The bot gave a wrong answer" is where most RAG debugging starts, and where most fixes go wrong. Teams change the prompt, swap the model or raise k, without knowing which stage failed. A bad answer has one of a few causes:

  • the evidence was never in the index;
  • it was indexed but not retrieved;
  • it was retrieved but ranked out of the prompt;
  • it was in the prompt but the model did not use it.

Each has different fixes, and finding out which takes minutes with the right trace.

The lab traces 200 answers from a small pipeline, dense retrieval into a 3B model, stage by stage, and sorts every failure by where it happened. It then applies the fix each stage calls for, only to the failures of that stage, and checks that the fix did not break answers that were already right.

  • Start from the bad answer and work backwards
  • Check whether the evidence was indexed, retrieved, ranked and used
  • Match each failure stage to the fixes that address it
  • Measure a fix on the failures it targets and on the cases it might break
  • Turn every debugged failure into a regression test

Start from the answer

Collect the failing case completely before changing anything:

  • the exact question;
  • the user and permissions;
  • the index version;
  • the retrieved chunks with their scores and ranks;
  • the prompt as sent;
  • the answer;
  • what the right answer is and where it lives.

A trace (Chapter 36) makes this one click. Without one, reproduce the request with logging on. Then ask the questions below in order, because each one rules out the stages after it.

def diagnose(case):
    if not any(case.answer_text in t for t in corpus_text(case.source_doc)):   return "not indexed"
    ranks = rank_of(case.source_doc, retrieve(case.question, k=50))
    if ranks is None:                                                          return "not retrieved"
    if ranks >= len(case.prompt_chunks):                                       return "ranked too low"
    if not cites(case.answer, case.source_doc):                                return "retrieved but not used"
    return "answered"

Was the evidence indexed?

Search the stores directly for the text that holds the answer, not through the RAG pipeline. Common reasons it is missing:

  • the document was never ingested;
  • extraction dropped it: a table, an image, a scanned page (Chapter 3);
  • chunking split it from its context (Chapter 4);
  • a permission filter hides it from this user (Chapter 23);
  • the index is stale (Chapter 22).

In the lab, 17 of 200 terms never appeared in their defining chapter's extracted text. Their glossary wording differed from the chapter's, which retrieval cannot fix.

Was it retrieved?

Retrieve the top 50 for the question and look for the evidence. If it is absent, the retriever does not see the match: vocabulary mismatch, short queries, exact identifiers. Fixes are hybrid search (Chapter 12), query rewriting (Chapter 14) or fine-tuning (Chapter 33). If it is present but below the cut-off, ranking is the problem: try a reranker (Chapter 13), a larger k, or better fusion. In the lab, dense retrieval missed the defining chapter entirely for 14 terms and ranked it 6th to 50th for 26.

Was it used?

If the evidence was in the prompt and the answer still ignored or contradicted it, the problem is context assembly or generation:

  • position (Chapter 16);
  • too many distracting chunks;
  • a prompt without a citation instruction or an "I don't know" path (Chapter 10);
  • a model too small for the task.

In the lab 39 answers had the right chunk in their top 5 and did not cite it, the largest single failure group.

Things to try.

  • Retrieved but not used: the biggest group. The fix is in the prompt, not the retriever.

Fix and add a test

Fix the stage that failed, then measure the fix twice:

  • on the failures it targets, to see how many it repairs;
  • on cases that already worked, to see whether it breaks anything.

The lab's prompt fix is the example: it repaired many unused-evidence failures, and the regression check showed what it cost on answers that were right before. Then add the failing question, with its right source, to the golden set (Chapter 21), so it is checked on every future change. Over time the golden set becomes a record of every failure the team has debugged.

Use case: "Seven Failure Points When Engineering a RAG System"

In 2024 Scott Barnett and colleagues at Deakin University published a study of three RAG systems they had built for research, education and biomedicine. It listed seven failure points:

  • missing content;
  • missed top-ranked documents;
  • not in context after consolidation;
  • not extracted from the context;
  • wrong format;
  • incorrect specificity;
  • incomplete answers.

Their conclusion was that RAG systems are validated by operating them, and that failures must be traced to a stage to be fixed. The lab's categories match the first four of their failure points, and its result, that "retrieved but not used" was the largest group for a small model, is the kind of finding that decides whether to spend effort on the retriever or the prompt.

⚠️
Common mistakes
  • Changing the prompt or model first.
  • Debugging from memory.
  • Raising k to fix everything.
  • Measuring a fix only on its target failures.
  • Not adding the case to the golden set.
  • Ignoring "not indexed".

Interview drill

Explain it simply: A user reports a wrong answer from your RAG assistant. How do you debug it?

How a strong answer sounds
Pull the full trace: question, user and permissions, index version, retrieved chunks with ranks, the prompt sent and the answer. Find where the right answer lives. Then go stage by stage: is that text in the index at all, extracted and visible to this user? Is it in the top 50 for this question? Did it make the cut into the prompt? Was it cited or ignored? The first "no" is the failing stage: ingestion or extraction, retrieval, ranking, or context and generation. Fix that stage, check the fix does not break cases that worked, and add the question to the golden set.

Deeper: Your team wants to switch to a larger model because answers are often wrong. How do you decide?

How a strong answer sounds
Classify a sample of wrong answers by stage first. If most fail before generation (evidence not indexed, not retrieved or ranked out), a larger model cannot help; it only sees what retrieval gives it. If most are "retrieved but not used", the model and prompt matter: try cheap prompt fixes such as citation instructions, fewer chunks and the question at both ends, measured on those failures and on cases that already work, and then a larger model if needed. In testing with a 3B model, the largest group was evidence retrieved but not used, and repeating the question before the sources repaired about two in five of those failures, while breaking a few answers that had been right.

🧠 Key takeaways

  • Capture the whole case before changing anything.
  • Ask in order: indexed, retrieved, ranked, used. The first "no" is the stage to fix.
  • Different stages need different fixes; a bigger model fixes only the last.
  • Measure a fix on its targets and on what already worked.
  • Every debugged failure becomes a regression test.
