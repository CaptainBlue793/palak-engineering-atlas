Permissions & Multi-Tenant Retrieval

A RAG system that can read every document in the company will happily quote any of them to anyone who asks. The language model has no idea who is asking. Permissions must be enforced before text reaches the prompt, at every place text can enter it: the search, the cache, the context expansion, the summaries. Each of those is a separate chance to leak.

This chapter treats permissions as something to test, not assume. The lab plants 40 canary notes ("the internal codename for topic is word") in the Atlas's twelve course tenants. Users who should not see them then ask for them, against seven retrieval set-ups. The leak rate of each is measured, along with whether the rightful owner still gets the answer.

  • Model document permissions as metadata the retriever can filter on
  • Filter by ACL inside the search, not after it
  • Separate tenants by filter, partition or index
  • Find leaks through caches, context expansion and summaries
  • Test access with canary documents

Document permissions

Copy each source document's access control into its chunks when indexing. That means the tenant, plus the users or groups allowed to read it, or a reference to them. Permissions change, so the indexing pipeline must update them as it updates content (Chapter 22), and deleted access must take effect quickly. When a document has parts with different permissions, such as a page with a restricted section, the chunks must carry the stricter permission of the text they hold. Anything derived from several chunks (summaries, parents, caches) carries the union of their restrictions.

user = auth.current_user()
allowed = {"tenant": user.tenant, "groups_any": user.groups}               # from the identity provider, never from the prompt
hits = index.search(embed(query), k=5, filter=allowed)                      # inside the search
context = [expand(h) for h in hits]
context = [c for c in context if acl.can_read(user, c)]                    # re-check after every expansion

Filtering by ACL

Chapter 9 compared ways to filter; here the filter is a security boundary. Filtering inside the search, with matching restricted to what the user may read, gave no leaks and full results in the lab. Post-filtering the top 5 also leaked nothing, but for 84% of questions from other tenants it left nothing at all to answer from. Their top results were the other tenant's documents. A forgotten filter, one code path that skips it, leaked every single canary to every other tenant. That is the realistic failure: not a wrong filter, but a path without one.

Tenants

A tenant (a customer company, a team) is the strongest boundary. There are three ways to isolate tenants:

  • A filter field in a shared index: cheapest, but a missed filter exposes everyone.
  • Partitions or namespaces: the store scopes every query to one, and you must pass it.
  • Separate indexes or collections per tenant: strongest isolation, most to operate.

Many systems combine them: separate collections for large tenants, partitions for small ones, and a tenant field checked again in the application. The tenant must come from the authenticated session, never from anything the user or a document can write.

Leaks through caches and expansion

The search can be perfect and the system can still leak. The lab measured two common examples.

  • Shared answer cache. One shared across tenants, keyed only by the question, served the owner's answer to other tenants. With an exact key that happened whenever the wording matched (50%). With a semantic key at a similarity threshold of 0.90 it happened every time (100%), and still 81% of the time at 0.95.
  • Context expansion. Small-to-big retrieval (Chapter 24) that returned whole sections without re-checking them handed the restricted paragraph to colleagues without the role 68% of the time.

Summaries, multi-document answers and conversation memory leak the same way: any artefact built from several documents is only as public as its most private input.

Simulator: forty canaries, seven set-ups

Each canary note was added to a random chunk's tenant. Its owner asked one phrasing first, and the caches stored that correct, filtered answer. Users from the eleven other tenants then asked two phrasings each: 880 questions per set-up. For the expansion test, a member of the owning tenant without the restricted role asked both phrasings, and a leak means the section returned for them contained the note.

Testing access

Access control in RAG needs tests that look for leaks, not just tests that look for answers. The lab's method works in production too:

  • Plant canary documents with unique strings in each permission scope.
  • Run questions designed to retrieve them, as users who must not see them, through every path: search, cache, expansion, summaries, follow-ups.
  • Fail the build if a canary string appears anywhere in the retrieved context or the answer.

Add the test whenever a new path or cache is added, and log, for audits, which documents went into every answer.

Use case: canary tokens

Canary values have long been used to detect leaks: a unique, meaningless string placed where only authorised readers should see it, so that its appearance anywhere else proves a leak. Thinkst's free Canarytokens service popularised the idea for documents, credentials and URLs that alert their owner when opened or used. Data-loss-prevention tools and security teams use the same technique, seeding fake records and watching for them. For a RAG system the canary is a sentence in a restricted document. The alarm is that sentence turning up in another user's retrieved context, in a cached answer, or in a summary. The lab shows why every path needs its own test: the search was safe while the cache and the expansion leaked.

⚠️
Common mistakes
  • Filtering after retrieval on a small k.
  • One path without the filter.
  • Caches keyed only by the question.
  • Expanding to parents or neighbours without a re-check.
  • Taking the tenant from the request body or the prompt.
  • Summaries across permission scopes.

Interview drill

Explain it simply: How do you stop a RAG system from showing users documents they are not allowed to see?

How a strong answer sounds
Store each chunk's permissions (tenant, allowed groups) as metadata at indexing time, kept in sync with the source system. At query time take the user's identity from authentication and pass it as a filter inside the vector search, so restricted chunks are never candidates; post-filtering a small top-k either leaks nothing but returns nothing, or, if forgotten, leaks everything. Then re-check permissions on anything added after the search (parent sections, neighbours, cached answers, summaries), key caches by tenant and permissions, and test every path with canary documents that must never appear for the wrong user.

Deeper: You add a semantic answer cache to cut latency in a multi-tenant RAG product. What can go wrong and how do you prevent it?

How a strong answer sounds
A cache keyed only by the question serves one tenant's answer, built from their private documents, to another tenant who asks something similar. In testing, an exact-key cache leaked whenever the wording matched, and a semantic cache at a 0.90 similarity threshold leaked on every paraphrase. Key the cache by tenant and by the permission set used for retrieval, or by a hash of the retrieved document ids together with the user's access. Invalidate entries when documents or permissions change. Keep a canary test that asks restricted questions from another tenant after the owner has populated the cache. Semantic caching also returns wrong answers for different questions that happen to be similar, so measure that rate too (Chapter 28).

🧠 Key takeaways

  • Permissions are chunk metadata, synced from the source and filtered inside the search.
  • A single path without the filter leaks everything; test every path.
  • Caches, expansions and summaries leak unless keyed and re-checked by permission.
  • Tenant identity comes from authentication, never from user or document text.
  • Canary documents turn "we think it is safe" into a test that fails.
