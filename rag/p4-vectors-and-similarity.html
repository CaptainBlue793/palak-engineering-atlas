Vectors & Similarity

Retrieval turns text into vectors and then asks which stored vectors are closest to the question's. "Closest" has several definitions, and they do not agree: the dot product, cosine similarity and Euclidean distance can rank the same documents in very different orders, and one of them, used carelessly, returns nonsense. This chapter covers vectors in NumPy, the three measures, and normalisation, the one-line step that makes them agree.

The lab measures all of it on a real corpus: 4,230 sections of the Engineering Atlas's own chapters, searched with 1,922 terms from the course glossaries, each labelled with the chapter that defines it.

Text as vectors

A vector is a list of numbers, and a set of vectors of the same length is a matrix. The simplest way to make text into a vector is to count words: give every word in the vocabulary a position, and store how often each appears. That is a bag-of-words vector: for this corpus, 24,703 positions, nearly all of them zero. Weighting the counts by how rare each word is across the corpus (TF-IDF, P7) makes distinctive words count for more. The embeddings in P5 are different, short and dense, but every measure in this chapter works the same way on them.

import numpy as np
a = np.array([3.0, 0.0, 1.0])     # "cache" ×3, "lock" ×0, "evict" ×1
b = np.array([1.0, 0.0, 1.0])

a @ b                              # dot product: 4.0
np.linalg.norm(a)                  # length: 3.16
(a @ b) / (np.linalg.norm(a) * np.linalg.norm(b))    # cosine: 0.894
np.linalg.norm(a - b)              # Euclidean distance: 2.0

Dot product and cosine

The dot product multiplies matching positions and adds them up. For word-count vectors it is large when two texts share many words, but also simply when either text is long: a long section mentions more words more often, so it scores higher against almost any query. Cosine similarity divides the dot product by both vectors' lengths, leaving only the angle between them: 1 when they point the same way, 0 when they share nothing. It asks "what proportion of this text is about the query", not "how much text is there".

Normalisation

Dividing a vector by its length, L2 normalisation, makes every vector length 1. After that the dot product equals the cosine, and Euclidean distance is a simple function of it (distance² = 2 − 2 × cosine), so all three rank documents in exactly the same order. That is why retrieval code normalises embeddings once, when they are stored, and then uses the fast dot product (an "inner product" index) to get cosine ranking. Many embedding models are trained for cosine similarity, so skipping normalisation quietly changes what the scores mean.

X = X / np.linalg.norm(X, axis=1, keepdims=True)   # every row now has length 1
q = q / np.linalg.norm(q)
scores = X @ q                                          # cosine similarity with every document at once
top5 = np.argsort(-scores)[:5]

Euclidean distance

Euclidean distance is the straight-line distance between two points. On unnormalised text vectors it is a poor choice: a short query is a short vector, close to the origin, and the documents closest to it are the shortest ones, whatever they say. On normalised vectors it gives the same ranking as cosine. Some vector databases default to it (often called L2); with normalised embeddings that is fine.

Things to try.

  • dot product versus cosine: the dot product's first result is a median of about 900 words long, more than three times the corpus median; cosine's is near the median, and it finds the right chapter more often.
  • Euclidean distance: every query returns the same three tiny sections, 17 to 32 words long. Recall falls to under 1%.
  • Euclidean, normalised: identical numbers to cosine, because on unit vectors the two give the same order.
  • word counts versus TF-IDF: weighting rare words more lifts recall@5 from about 0.69 to 0.78 with cosine. P7 explains why.

Scoring many vectors at once

Never loop over documents in Python to compute similarities. Stack the document vectors into a matrix and compute every score with one matrix-vector product, which NumPy hands to optimised linear-algebra code. Measured here on 4,230 dense 384-dimensional vectors, the size of a small embedding model's output: a Python loop took 96 ms per query and D @ q took 0.12 ms, about 790 times faster, with the same top result. For a batch of queries, one matrix-matrix product scores them all.

Use case: the vector space model and SMART

Representing documents and queries as vectors and ranking by the cosine of the angle between them is older than the web. Gerard Salton and his colleagues at Cornell built it into the SMART information retrieval system in the 1960s and 1970s, and described it in the 1975 paper "A Vector Space Model for Automatic Indexing". They found, as this lab does, that raw term counts reward long documents, and that weighting terms by how rare they are and normalising for length gives better rankings; the length-normalisation problem stayed an active research topic for decades and is part of why BM25 (Chapter 11) has its length parameter. Today's embedding search replaced counted words with learned dense vectors, but kept the rest of SMART's model intact: documents and queries are vectors, similarity is an angle, and the top-k nearest vectors are the answer.

⚠️
Common mistakes
  • Unnormalised vectors in an inner-product index, which turns "most similar" into "longest".
  • Euclidean distance on unnormalised vectors.
  • Normalising documents but not queries, or the other way round.
  • Python loops over documents instead of one matrix product.
  • Reading a cosine of 0.8 as "80% relevant": scores only rank; their scale depends on the model.

Interview drill

Explain it simply: What is the difference between dot product and cosine similarity?

How a strong answer sounds
The dot product multiplies matching coordinates and sums them, so it grows with both the angle between the vectors and their lengths. Cosine similarity divides by both lengths, so it depends only on the angle: how much the two point in the same direction. For text, length mostly reflects how long a document is, so the dot product favours long documents while cosine compares what they are about. If you normalise every vector to length one, the two are identical, which is why retrieval systems normalise embeddings once and then use a fast inner-product index.

Deeper: Your vector database search returns very short, unrelated chunks for most queries. What would you check?

How a strong answer sounds
That pattern points to Euclidean or L2 distance on unnormalised vectors: a short query vector sits near the origin, and the nearest stored vectors are the short ones. I would check which metric the index uses and whether embeddings were normalised at write time and at query time, consistently. I would also check that the embedding model's recommended similarity is cosine, that the right query prefix is applied, and that tiny chunks such as headings or boilerplate were not indexed on their own. Fix by normalising both sides or switching the index to cosine or inner product with normalised vectors, then re-measure recall on a labelled set.

🧠 Key takeaways

  • Text becomes a vector; similarity search compares a query vector with every stored vector.
  • Dot product grows with length; cosine depends only on direction.
  • Euclidean distance on raw vectors favours short texts; avoid it unless vectors are normalised.
  • Normalise once, then dot product, cosine and L2 all rank the same way.
  • Score with matrix products, never Python loops.
