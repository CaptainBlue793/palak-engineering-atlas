Query Routing & Decomposition

Real systems often have more than one index: product docs and support tickets, one index per team, a SQL database beside the text (Chapter 18). They also get questions that bundle two or three asks into one sentence. Routing sends each question to the right index. Decomposition splits a compound question into pieces that can each be retrieved well. Both sound like obvious wins, and both can quietly lose more than they gain.

The lab treats the Atlas as twelve course indexes. It routes 300 glossary terms by course centroids, by a 3B model and, as a ceiling, by the true course. It then builds 150 two-part questions from terms in different courses and retrieves each as one query, split by a simple rule, or split by the model.

  • Build rule, embedding and model routers, and measure their accuracy

Several indexes

Separate indexes make sense when the data differs in kind (code, tables, prose), in owner or permissions (Chapter 23), in update rate, or in the retrieval method that suits it. If the data is all prose of the same sort, one index with a metadata field is usually better. It can still search everything when the question's home is unclear, and it can still filter when it is clear (Chapter 9). Routing is the price of splitting: something must choose where each question goes.

Routing by rules or a model

A router can be any of three things:

  • Rules: keywords, the page the user is on, the product they selected. These are cheap and exact when they apply.
  • Embeddings: compare the query with each index's centroid or with example questions.
  • A model: ask it to choose from described options, as in the lab, or let it call one of several search tools (Chapter 34).

Whatever the router, its accuracy is the ceiling of everything after it. In the lab, routing each term to one course cut the right-chapter rate in the top 5 from 77% (searching every course) to 32% with centroids and 27% with qwen2.5:3b. Even perfect routing reached only 90%, a gain of 12 points that no real router came close to capturing.

ROUTES = {"dsa": "Data structures and algorithms", "databases": "Databases and SQL", ...}
choice = llm("Pick the one course most likely to explain the user's term. Courses:\n" + listing(ROUTES) +
             "\nReply with the course id only.", query).strip().lower()
targets = [choice] if choice in ROUTES else list(ROUTES)                  # unparseable → search everything
hits = merge(index[t].search(query, k=5) for t in targets)

Decomposing questions

A question like "What is a covering index, and how does Kosaraju's algorithm work?" asks about two unrelated things. One embedding of the whole question lands between them and finds neither well. Decomposition splits it into sub-queries, retrieves for each, and gives each a share of the context budget. In the lab, a single query found both relevant chapters in its top 6 only 21% of the time. Splitting on "and" raised that to 51%, and asking the model to split raised it to 37%. The model's splits failed in two ways. It returned the whole question unchanged, or it added extra sub-queries such as "When would I use…?" that took slots from the two that mattered.

Simulator: twelve indexes, three routers, three splitters

Routing used 300 random glossary terms. The right chapter counts if it appears in the top 5 chunks from the chosen course's index. Decomposition used 150 questions made from two terms of different courses, in three phrasings. Each method had six slots in total, split evenly between its sub-queries. Success means both terms' defining chapters were among the six.

Multi-hop questions

Some questions cannot be split up front, because the second step depends on the first answer. "Who maintains the library that our billing service uses for retries?" needs the library's name before you can search for its maintainer. These multi-hop questions need an iterative loop: retrieve, extract the intermediate answer, form the next query, retrieve again. That is the step from a fixed pipeline to agentic retrieval (Chapter 34). Benchmarks such as HotpotQA were built to test exactly this.

Combining answers

After decomposition you have either several result lists or several partial answers. Merge lists by giving each sub-query a fixed share of the context, or by rank fusion (Chapter 12), so one sub-query cannot crowd out the others. For answers, either generate one answer from all the merged context, or answer each sub-question and then compose. The second is clearer for comparisons ("how do X and Y differ"), but costs a call per part and risks inconsistency between the parts.

Use case: HotpotQA and multi-hop retrieval

In 2018 Zhilin Yang, Peng Qi, Saizheng Zhang and colleagues at Carnegie Mellon, Stanford and Université de Montréal released HotpotQA. It holds 113,000 Wikipedia questions that each need facts from two articles, such as "Which magazine was started first, Arthur's Magazine or First for Women?". It also labels the supporting sentences, so systems can be checked for using the right evidence. Single-step retrievers did poorly, because the second article often shares no words with the question. That pushed the field towards iterative retrieval: methods that retrieve, read, and query again. The same split runs through this chapter. Compound questions whose parts are known up front can be decomposed once. Questions whose next step depends on an answer need a loop.

⚠️
Common mistakes
  • Routing to one index on a weak signal.
  • Splitting indexes that should be one with a metadata field.
  • Not handling unparseable router output.
  • Letting one sub-query take all the context slots.
  • Decomposing every question.
  • Treating multi-hop questions as decomposable.

Interview drill

Explain it simply: What are query routing and query decomposition?

How a strong answer sounds
Routing chooses which index or data source a question should go to, for example product docs versus support tickets versus a SQL database, using rules, embeddings or a model. Decomposition splits a question that asks several things into separate sub-queries, retrieves for each, and combines the results, so one embedding does not have to represent two unrelated topics. Both add a decision that can be wrong: a misrouted question cannot find its answer, and a bad split wastes context. So measure the router's accuracy and the end-to-end recall against simply searching everything.

Deeper: Your company has 40 team knowledge bases and wants an LLM router in front of them. How do you design and validate it?

How a strong answer sounds
First ask whether one index with a team field and a global search would do: it avoids unrecoverable routing errors, and filtering can still narrow results when the team is known. If routing is needed (permissions, different systems), use reliable signals first: the user's team, the app they are in, explicit selections. Then build a model router with clear descriptions, route to the top two or three candidates rather than one, and fall back to all when its output is unparseable or uncertain. Validate with labelled questions: routing accuracy per team, end-to-end recall against global search, and a confusion matrix to find attractor categories. In testing, a 3B model router picked the right course 29% of the time and pulled many terms into one broad category.

🧠 Key takeaways

  • Split indexes only for real reasons; otherwise use one index with metadata.
  • A router's accuracy caps everything after it; route to several candidates and keep a fallback.
  • Decomposition helps compound questions; even a simple rule beat no split by a wide margin.
  • Multi-hop questions need an iterative loop, not a one-off split.
  • Give each sub-query a fair share of the context.
