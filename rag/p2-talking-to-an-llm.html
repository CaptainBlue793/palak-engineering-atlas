Talking to an LLM

The "G" in RAG is a language model that reads a prompt and writes an answer. Using one well needs only a few ideas: messages with roles, a system prompt that sets the rules, sampling settings that decide how predictable the output is, limits on length, and an awareness of what the model actually received. That last one catches people out more than any other, because servers can quietly cut a long prompt to fit.

This chapter runs a small open model locally, Qwen2.5 with 3 billion parameters served by Ollama, and measures four things: how temperature and seeds change answers, how reliably it returns JSON, where the time goes, and what happens when a prompt is longer than the server's context setting.

  • Structure a request as system, user and assistant messages
  • Use a system prompt to fix rules and output format
  • Choose temperature and seeds for evaluation and for production
  • Control length and detect when output was cut off
  • Run a local model and check how much of the prompt it received

Chat messages and roles

Chat models take a list of messages, each with a role. The system message sets standing instructions; user messages carry requests; assistant messages are the model's previous replies, included to continue a conversation. The server turns the list into one token sequence using the model's chat template, and the model writes the next assistant message. The model has no memory between requests: anything it should know, including earlier turns and retrieved documents, must be in the messages you send.

import httpx
ollama = httpx.Client(base_url="http://localhost:11434", timeout=120)
r = ollama.post("/api/chat", json={
    "model": "qwen2.5:3b", "stream": False,
    "messages": [
        {"role": "system", "content": "You extract structured data. Reply with one JSON object and nothing else."},
        {"role": "user", "content": 'Extract "entity", "id" and "event" from: Invoice 5521 for £240 is overdue.'}],
    "options": {"temperature": 0, "seed": 7, "num_ctx": 8192, "num_predict": 200}})
body = r.json()
answer, used = body["message"]["content"], body["prompt_eval_count"]      # check how much of the prompt was read

System prompts

The system prompt is where rules belong: the task, the output format, what to do when unsure, what never to do. Models follow it more consistently than instructions buried in a user message, and keeping it fixed makes behaviour testable. For RAG, it is where "answer only from the sources, cite them, and say when they do not contain the answer" lives (Chapter 10). For machine-readable output, ask for the exact format in the system prompt and, where the server supports it, also turn on structured output (Ollama's format: "json" or a JSON schema), then still parse defensively.

Temperature and sampling

At each step the model produces a probability for every token in its vocabulary. Temperature rescales those probabilities before one is drawn: at 0 the most likely token is always chosen, so output is effectively deterministic; higher values flatten the distribution and produce more varied text. top-p and top-k restrict the draw to the most likely tokens. A seed fixes the random draws, so the same request repeats exactly even at higher temperature. For RAG and for evaluation, use temperature 0 or a low value with a fixed seed; save higher temperatures for brainstorming.

Stopping and length

Generation stops when the model emits its end-of-turn token, when a stop sequence you set appears, or when it reaches the maximum number of new tokens (num_predict in Ollama, max_tokens elsewhere). The response says which: a done_reason (or finish_reason) of "stop" means it finished; "length" means it was cut off mid-thought. Asked to explain a vector index with a 25-token limit, the model here stopped at "…to efficiently store and query high-dimensional vectors", with done_reason "length". Always check it: a truncated answer can look complete.

Running a local model

A local model trades quality for control: no per-token cost, no data leaving the machine, predictable latency once loaded. Ollama serves quantised models over a small HTTP API; this one is 1.9 GB and runs entirely on a 4 GB laptop GPU. Two settings matter more than any other for RAG. The first request loads the model (here 34 s); keep it loaded. And the context size (num_ctx) is a server setting, not just a model limit: if the prompt is longer than the server allows, it is truncated before the model sees it.

Simulator: four experiments

Each experiment ran against qwen2.5:3b in Ollama 0.40.4 on an RTX 3050 Ti. Sampling: one creative prompt, ten runs per setting. JSON: 20 short sentences, each to be turned into a JSON object, three ways. Latency: summarising text of four lengths with a 100-token answer. Context: a fact at the start of a 6,000-token prompt, asked about at the end, with the server's default context and with num_ctx set to 8,192.

Use case: llama.cpp and running models locally

In March 2023, days after Meta's LLaMA weights became available to researchers, Georgi Gerganov released llama.cpp, a C and C++ implementation that ran the model on an ordinary laptop CPU by loading weights quantised to 4 bits. It showed that useful language models did not need a data-centre GPU, and it grew into one of the most widely used inference engines, with GPU back-ends and its own GGUF model file format. Ollama, released later in 2023, packages llama.cpp behind a simple command line and HTTP API with a model library, which is what this course uses. The same stack explains this chapter's context finding: llama.cpp allocates memory for a fixed context size when a model is loaded, so servers built on it choose a default and truncate prompts that do not fit, rather than reserve memory for the model's full theoretical window.

⚠️
Common mistakes
  • Not checking how many prompt tokens the server actually used.
  • Leaving the server's default context size for long RAG prompts.
  • Parsing model output with json.loads and no fallback.
  • Evaluating at high temperature without a seed.
  • Ignoring done_reason, so cut-off answers look complete.
  • Putting rules in the user message instead of the system prompt.

Interview drill

Explain it simply: What does temperature do, and what would you set it to for a RAG system?

How a strong answer sounds
At each step the model assigns probabilities to every possible next token, and temperature rescales them before one is sampled. At zero it always takes the most likely token, so output is effectively deterministic; higher values make less likely tokens more probable, giving more varied text. For RAG I want answers that stick to the retrieved sources and are reproducible for evaluation, so I would use zero or a low value with a fixed seed, and keep higher temperatures for creative tasks.

Deeper: Your RAG system answers well in testing but says "the information is not available" for some long documents in production. What do you check?

How a strong answer sounds
First whether the model received the whole prompt: compare the prompt token count the server reports with the count of what we sent, because a server context setting smaller than the prompt truncates it silently, often dropping the beginning where instructions or key chunks sit. I would set the context size explicitly above our largest prompt, enforce a token budget when assembling context, and alert when the reported prompt tokens fall short. Then I would check retrieval for those documents, chunk lengths against the embedding limit, and where in the prompt the relevant chunk landed, since models use the middle of long contexts less reliably.

🧠 Key takeaways

  • Requests are role-tagged messages; the model remembers nothing between them.
  • Put rules and formats in the system prompt; it took JSON from 0 to 20 of 20 parseable as-is.
  • Temperature 0 or a fixed seed for RAG and evaluation.
  • Reading the prompt is fast; generating the answer dominates latency.
  • Set the context size and check prompt tokens: servers truncate silently.
