Python for AI Engineering

Every chapter in this course is Python: loading documents, calling an embedding model, searching an index, asking a model to answer, and measuring how well it did. None of it needs advanced Python, but it needs Python written with a few habits that matter more here than in most code: environments that pin the exact library versions, small typed data structures for chunks and results, careful calls to model APIs over HTTP, JSON in and out, and scripts that give the same answer every time you run them.

The last habit is the one people learn the hard way. A RAG evaluation that changes when you rerun it cannot tell you whether a change helped. The lab runs one small retrieval script 20 times, as it is often first written and then fixed, and shows how many different answers it gives.

  • Create an environment per project and pin the versions that change results
  • Model chunks and search results with type hints and dataclasses
  • Call a model's HTTP API with timeouts and handle its JSON
  • Store corpora and evaluation sets as JSON Lines
  • Remove the hidden sources of randomness from a script

Environments and packages

Give every project its own environment, a conda environment or a venv, so its libraries do not collide with another project's. In AI work, pin the exact versions of anything that touches numbers: torch, transformers, sentence-transformers, faiss and the model itself. A new library version can change tokenisation or pooling, and therefore every embedding, so an index built last month may no longer match queries embedded today. Write the versions into a lock file, record them alongside every evaluation result, and name the model by its exact identifier and revision, not "the small one".

# once per project
conda create -n rag python=3.11 && conda activate rag
pip install "sentence-transformers==6.1.0" "faiss-cpu==1.15.1" "httpx==0.28.1"
pip freeze > requirements.lock                    # the exact versions this project was measured with

Type hints and dataclasses

A retrieval system passes the same few shapes around: a chunk of a document, a search hit, a question with its known answers. Declare them once as dataclasses with type hints, and every function says what it takes and returns. Frozen dataclasses cannot be changed after creation, which prevents one stage of a pipeline from quietly editing another's data, and they can be used as dictionary keys and in sets.

from dataclasses import dataclass, field

@dataclass(frozen=True)
class Chunk:
    id: str                      # "vpn-setup#2": document and position
    doc_id: str
    text: str
    meta: dict = field(default_factory=dict, compare=False, hash=False)   # source, page, permissions

@dataclass(frozen=True)
class Hit:
    chunk_id: str
    score: float

def search(query: str, k: int = 5) -> list[Hit]: ...

Calling HTTP APIs

Models are usually reached over HTTP, whether a hosted API or a local server such as Ollama on localhost:11434. Use a client with an explicit timeout, because generation can take seconds and a hung connection should fail rather than wait forever; reuse one client so connections are kept alive; and check the status code before reading the body. Hosted APIs add rate limits and transient errors, so retries with backoff belong there too (the Backend & API course covers them in Chapter 29).

import httpx

client = httpx.Client(base_url="http://localhost:11434", timeout=httpx.Timeout(60, connect=5))

def chat(prompt: str, model: str = "qwen2.5:3b") -> str:
    r = client.post("/api/chat", json={"model": model, "stream": False,
                                      "messages": [{"role": "user", "content": prompt}],
                                      "options": {"temperature": 0, "seed": 7}})
    r.raise_for_status()
    return r.json()["message"]["content"]

JSON in and out

Corpora, evaluation sets and results are best stored as JSON Lines: one JSON object per line, so files can be appended to, streamed and compared line by line. Write with ensure_ascii=False so accented and non-Latin text stays readable, and open files with encoding="utf-8", especially on Windows, where the default is still a legacy code page. When a model is asked for JSON, parse what comes back defensively: it may add prose or a code fence around the object, and P2 shows how often that happens.

import json
with open("eval.jsonl", "w", encoding="utf-8") as f:
    for q in questions:
        f.write(json.dumps({"q": q.text, "relevant": sorted(q.relevant)}, ensure_ascii=False) + "\n")

with open("eval.jsonl", encoding="utf-8") as f:
    rows = [json.loads(line) for line in f if line.strip()]

Reproducible scripts

A script is reproducible when running it twice on the same inputs gives the same output. Three sources of variation hide in ordinary Python. Set and hash order: the order you iterate a set of strings depends on a hash seed that Python randomises per process, so anything that turns a set into a list, then sorts with ties, can change between runs. Unseeded randomness: random.sample, shuffling and train/test splits without a seed. Hidden inputs: the time, the order files come back from the disk, a model or library that was silently upgraded. Fix them by sorting with an explicit, complete key, seeding every random generator you create, and recording versions. For models, temperature 0 and a fixed seed make generation far more repeatable, though GPU arithmetic can still differ slightly between runs and machines.

Use case: left-pad, 2016

In March 2016 a developer unpublished his packages from the npm registry after a dispute, among them left-pad, an eleven-line function that pads a string. Thousands of projects depended on it indirectly, including widely used build tools such as Babel, and builds across the JavaScript world began failing within hours because installing dependencies fetched whatever the registry had, and it no longer had left-pad. npm restored the package and later changed its policy so packages that others depend on cannot simply be unpublished. The episode made a habit mainstream that matters even more in AI code: know exactly which versions you depend on, lock them, and be able to rebuild the same environment tomorrow. In a RAG system an unnoticed upgrade does not even fail loudly; it changes the embeddings and quietly lowers retrieval quality.

⚠️
Common mistakes
  • One shared environment for every project, with whatever versions were installed last.
  • Turning a set into a list and assuming the order is stable.
  • Unseeded sampling in evaluation, then comparing numbers across runs.
  • No timeout on calls to a model server.
  • Opening files without encoding="utf-8" on Windows.
  • Not recording the model name, revision and library versions with each result.

Interview drill

Explain it simply: Why might the same Python script give different results on two runs?

How a strong answer sounds
Because something in it is not fixed. Common causes are randomness without a seed, such as sampling or shuffling; the iteration order of sets of strings, which depends on a per-process hash seed, so ties in a sort can come out in a different order; model sampling with a temperature above zero; and hidden inputs like the time, file listing order or a library or model that was upgraded. I fix it by seeding a dedicated random generator, sorting with a complete key that breaks ties, using temperature zero for tests and evaluation, pinning versions and recording them with the results.

Deeper: Your team's RAG evaluation score drops from 0.81 to 0.74 overnight with no code changes. How do you investigate?

How a strong answer sounds
First rerun it twice to see whether the score is even stable; if it moves between identical runs, the evaluation itself is nondeterministic and must be fixed first: seeds, tie-breaking, temperature, full question set. If it is stable, compare everything that could change without code: the lock file and installed versions, especially the embedding model, tokenizer and vector library; the model tag on the generation server; the corpus and index build date; and the evaluation set itself. Each result should record those, so the diff is quick. A new embedding model version with an old index is a classic cause; re-embedding or pinning the old version would confirm it.

🧠 Key takeaways

  • One environment per project; pin and record the versions that change numbers.
  • Dataclasses with type hints make chunks, hits and questions explicit.
  • Call model APIs with timeouts, and parse their JSON defensively.
  • Store corpora and evaluation sets as UTF-8 JSON Lines.
  • Sort with complete keys, seed randomness and use temperature 0 so runs repeat.

Check your understanding

Three documents tie on score and the top 3 came out in six different orders over 20 runs. Why?

Python's sort is stable; it preserved an input order that changed. Sorting by (-score, id) fixed it.

An evaluation on a random sample reports recall from 0.75 to 1.0 for the same code. What is the best fix?

A seed makes the number repeatable; the full set makes it representative (0.917 here).

Why pin sentence-transformers and the model revision for a RAG project?

Record versions with every result too.

What should every call to a model server have?

Reuse one client so connections stay open.

Why store an evaluation set as JSON Lines?

Write with ensure_ascii=False and read with encoding="utf-8".
