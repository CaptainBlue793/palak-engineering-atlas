Agentic RAG: Retrieval as a Tool

Every pipeline in this course so far decided in advance when to retrieve and what to search for. Agentic RAG hands that decision to the model. Retrieval becomes a tool it can call, as many times as it likes, with queries it writes itself, before it answers. That can handle multi-part and multi-hop questions a fixed pipeline cannot. It also adds model calls, latency and new ways to fail: not searching, searching badly, or never stopping.

The lab gives a 3B model a search tool through Ollama's tool calling, with up to four searches per question. It compares the result with a fixed one-search pipeline on 100 single-term questions and 100 two-part questions, measuring whether the right chapters were found, how many searches were made, and how long it took.

  • Expose retrieval as a tool a model can call
  • Design iterative search for multi-part and multi-hop questions
  • Add self-checks and stopping rules
  • Measure what agentic retrieval costs in calls and latency
  • Decide when a fixed pipeline is the better choice

Retrieval as a tool

Describe the search function to the model with a name, a description and a parameter schema. The model replies either with an answer or with a request to call the tool. The application runs the search, appends the results as a tool message, and asks again. The model now chooses the query wording, how many searches to make, and whether to search at all. Every other part of the system stays as before: filters, reranking and permissions apply inside the tool.

TOOLS = [{"type": "function", "function": {"name": "search",
          "description": "Search the course chapters. Returns the three most relevant passages.",
          "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}}}]
for step in range(MAX_STEPS):
    msg = chat(messages, tools=TOOLS)
    if not msg.tool_calls: break                         # the model chose to answer
    for call in msg.tool_calls:
        messages.append(tool_result(search(call.arguments["query"], user=user)))   # filters still apply

Iterative search

The promise is that the model searches for each part of a question, reads the results, and searches again if something is missing. On two-part questions the agent made 1.46 searches on average and found both relevant chapters 26% of the time, against 18% for one search of the whole question. But it stopped after a single search on 55 of 100 two-part questions, often with both terms in one query such as "Gini impurity Secret". A larger model plans better. A small one needs the plan written into the prompt or the code.

Simulator: fixed pipeline against an agent

Single questions ask what one Atlas glossary term means. Two-part questions ask about two terms from different courses. The fixed pipeline searches once with the whole question and takes the top 6 chunks. The agent's search tool returns the top 3 per call, for up to four calls. Things to try.

  • Two terms, fixed → agent: both chapters found 18% → 26%, for 1.8× the time.
  • One term, fixed → agent: 72% → 64%. The agent always searched once with the bare term and saw only 3 passages.
  • Searches per question: one term always 1; two terms 1 or 2, almost never more.
  • Failure modes: 1 repeated query and 0 runs hitting the step limit. The common failure was one combined search, not a runaway loop.

Self-checking

An agent can check its own work: ask itself whether the retrieved passages answer every part of the question, and search again if not. It can also verify claims against sources before answering (Chapter 20). Self-checks help larger models, and they add calls. Implement the important ones in code. For example, count the parts of the question, check that each has at least one retrieved passage, and if not prompt the model to search for the missing part.

Stopping

Agents need hard limits: a maximum number of steps, a token and time budget, and detection of repeated identical searches. When a limit is hit, answer from what was found, with a note, rather than failing. Log every step, the query, results and time, because agent traces are the only way to see why it searched what it did (Chapter 36).

Cost and latency

Each step is a model call plus a search, and calls are sequential, so latency adds up. Here the agent took 3.6 s per two-part question against 2.1 s for the fixed pipeline. Use an agent where questions genuinely need several searches, such as research, multi-hop questions or several tools. Keep fixed pipelines, perhaps with decomposition (Chapter 15), where the pattern is predictable. Route between them if both kinds of question arrive.

Use case: ReAct and Self-RAG

ReAct (Shunyu Yao and colleagues, Princeton and Google, ICLR 2023) prompted language models to interleave reasoning ("I need to find X") with actions such as Wikipedia searches and lookups, reading each observation before the next step. On multi-hop question answering and fact verification, interleaving beat both reasoning alone and acting alone. Self-RAG (Akari Asai and colleagues, 2023) trained a model to decide when to retrieve and to critique its own outputs with special tokens, retrieving only when needed and checking that its answers were supported. Both are ancestors of today's agentic RAG. They also show this chapter's caveat: the gains came from models able to plan, and smaller models need more structure around them.

⚠️
Common mistakes
  • An agent for every question.
  • No step or budget limits.
  • Trusting the model to decompose.
  • Filters outside the tool.
  • No traces.
  • Comparing systems with different retrieval depth.

Interview drill

Explain it simply: What is agentic RAG, and when would you use it?

How a strong answer sounds
Instead of a fixed pipeline that retrieves once, the model gets retrieval as a tool and decides whether, what and how many times to search before answering, in a loop of plan, call, read. It helps for questions that need several searches: multi-part, multi-hop, or several tools. It costs more model calls and latency and can fail by not searching, searching badly or looping, so it needs step and budget limits, coverage checks and traces. For predictable questions a fixed pipeline, possibly with decomposition, is cheaper and often as good.

Deeper: Your agentic RAG prototype is slower than the old pipeline and not clearly better. What do you look at?

How a strong answer sounds
Traces first: how many searches per question, what queries the model wrote, where it stopped. Small models often search once with a combined query or stop early. In testing, a 3B agent searched once on more than half of two-part questions, often with both topics in one query. Then compare like with like: the same retrieval depth and reranking inside the tool as in the pipeline. Fixes: write the decomposition into code or the prompt, add a coverage check that triggers another search, use a stronger planning model, and route only multi-part or multi-hop questions to the agent.

🧠 Key takeaways

  • Agentic RAG lets the model choose when and what to search, in a loop.
  • It helped two-part questions here and cost more time; it did not help single ones.
  • Small models under-decompose; put the plan or a coverage check in code.
  • Limits, traces and filters inside the tool are not optional.
  • Use agents where questions need several searches; route the rest to a fixed pipeline.
