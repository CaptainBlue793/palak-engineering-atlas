Multi-Vector & Late-Interaction Retrieval

An embedding squeezes a whole chunk into one point in space. For a chunk about one idea that works well. For a chunk that covers five ideas, the single vector is an average that may sit close to none of them. Multi-vector retrieval stores several vectors per document, and scores the document by how well its best parts match the query.

The extreme is ColBERT's late interaction, which keeps one vector per token. This chapter measures the practical middle ground: one vector per sentence, scored by the best-matching sentence (MaxSim). It runs on SciFact abstracts and on the Atlas's chunks, and records what each extra vector costs in storage.

One vector is a summary

A sentence-transformer pools its token outputs (bge takes the first token's output) into one vector per input. That vector is a summary of the whole input, and summaries lose detail. A query about one fact mentioned in passing competes with the chunk's main topic for the vector's attention. The longer and more varied the chunk, the more is lost. Chapter 4's smaller chunks fight this by making each vector cover less; multi-vector retrieval fights it without changing what is returned.

Multiple vectors per document

Store several vectors for each document: one per sentence, per passage window, or per generated question it can answer. Score the document by the best match among them, called MaxSim, or by a blend of that and the whole-document vector. In the lab, the best sentence lifted the Atlas's right-chapter rate from 72.2% to 80.6%, because a glossary term is usually defined in one sentence of a broader chunk. On SciFact, where claims are about a whole abstract's finding, the best sentence alone did slightly worse (0.690 against 0.707). The blend did best on both (0.723 and 80.8%). Averaging the sentence vectors was worst everywhere: it is just a blurrier single vector.

# sentence vectors S (n_sentences × 384), doc_of[i] = the document of sentence i
sims = S @ q                                                     # one score per sentence
best = np.full(n_docs, -1.0); np.maximum.at(best, doc_of, sims)        # MaxSim per document
score = 0.5 * (D @ q) + 0.5 * best                                  # blend with the whole-document vector
top = np.argsort(-score)[:10]

Late interaction

ColBERT takes the idea to tokens. It keeps the contextualised vector of every token in every document, and also embeds the query token by token. A document's score is the sum, over query tokens, of each query token's best match among the document's tokens. The query and the document interact only at this last, cheap step, hence "late interaction". It catches term-level matches that a pooled vector blurs, and it generalises well to new domains. It needs a model trained for it: plain bge token vectors are not trained to be compared one by one. This lab therefore stays at sentence level, and the page describes ColBERT rather than measuring it.

Storage cost

Multi-vector indexes multiply storage by the number of vectors per document. Sentence-level vectors here meant about 9 times as many for the Atlas and 10 times for SciFact. Token-level late interaction is far larger again, with one vector per token, often hundreds per passage. That is why ColBERTv2 compresses each token vector to a cluster centroid plus a small quantised residual, and why engines such as PLAID first prune candidates using the centroids alone. The quantisation from Chapter 8 applies here too, and the cheapest saving is a first-stage retriever that limits MaxSim to a shortlist.

When it pays

Multi-vector scoring pays when documents cover several distinct points and queries target one of them: glossaries, FAQs, manuals and long technical chunks. It pays less when queries are about a document's overall claim, as in SciFact. Before adopting it, consider the cheaper relatives:

  • smaller chunks (Chapter 4);
  • small-to-big retrieval (Chapter 24), which gets the same precision with the same sentence index;
  • a reranker over a single-vector shortlist (Chapter 13).

Use case: ColBERT, from a 2020 paper to production engines

Omar Khattab and Matei Zaharia introduced ColBERT at SIGIR 2020, in "ColBERT: Efficient and Effective Passage Search via Contextualized Late Interaction over BERT". Cross-encoders (Chapter 13) were accurate but needed a full model pass per query–document pair. ColBERT encoded documents offline, one vector per token, and matched them to query tokens with cheap MaxSim sums. That made accuracy close to a cross-encoder affordable at retrieval time. The cost was storage, which the follow-up ColBERTv2 (2022) cut sharply with residual compression, while the PLAID engine made search over compressed token vectors fast. Late-interaction models are now offered in several vector databases and search libraries. The lab's sentence-level version shows the same trade at a smaller scale: precision from matching parts, paid for in vectors.

⚠️
Common mistakes
  • Averaging part vectors and calling it multi-vector.
  • Using best-part scores alone for queries about whole documents.
  • Token-level MaxSim with a model not trained for it.
  • Forgetting the storage multiplier.
  • Scoring every part of every document.
  • Skipping the cheaper alternatives.

Interview drill

Explain it simply: What is late interaction, and why is it more accurate than a single embedding?

How a strong answer sounds
A single embedding pools a whole passage into one vector, so specific details get averaged away. Late interaction, as in ColBERT, keeps one vector per token for the document, computed offline, and one per token for the query. The score sums, over query tokens, each one's best-matching document token. Query and document only meet at this cheap final step, so documents can still be indexed in advance, yet individual terms are matched precisely, giving accuracy closer to a cross-encoder. The cost is storage, roughly one vector per token, which ColBERTv2 reduces with compression.

Deeper: Your FAQ pages each answer ten questions, and retrieval often misses specific ones. Would you move to multi-vector retrieval?

How a strong answer sounds
It is a good fit: each page covers many distinct points and queries target one, which is exactly where a single vector blurs. In testing, best-sentence scoring raised the right-chapter rate on glossary terms from about 72% to 81%. But first try the cheaper options: chunk per question-and-answer pair, or index small units and return the page (small-to-big). If multi-vector is still better, blend the best-part score with the whole-document score, limit MaxSim to a first-stage shortlist, quantise the part vectors, and budget for roughly as many vectors as parts. Measure on labelled queries against those alternatives.

🧠 Key takeaways

  • One vector summarises a document and blurs details a query may target.
  • MaxSim over part vectors matches the best part; blend it with the whole for safety.
  • It helped short, specific queries a lot and whole-claim queries little.
  • ColBERT applies the idea to tokens and needs a model trained for it.
  • Storage grows with vectors per document; compress, shortlist and compare with cheaper options.
