Text Processing Basics

Text extracted from PDFs, web pages and word processors looks fine on screen and is full of traps underneath: the "fi" in "configuration" stored as one ligature character, words broken across lines with a hyphen, invisible zero-width spaces, accents stored as two characters, curly apostrophes where users type straight ones. A keyword search for the word you can see fails, and an embedding model sees odd tokens. These steps are unglamorous, and they decide retrieval quality before any model is involved.

This chapter covers Unicode and normalisation, cleaning extracted text, splitting it into sentences and paragraphs, regular expressions and language detection. The lab injects eight common extraction artefacts into real Atlas text, 3,116 cases in all, and measures how often an exact lookup still finds the word after each cleaning step.

Unicode and normalisation

Python strings are sequences of Unicode code points; UTF-8 is the usual way to store them as bytes. The same visible text can be different code points: "é" can be one code point (U+00E9) or "e" followed by a combining accent (U+0301); "ﬁ" can be one ligature code point or two letters; a space can be ordinary or non-breaking. Unicode defines normalisation forms that make equivalent text identical. NFC composes characters ("e" + accent becomes "é"), and is what most text should be stored in. NFKC also folds "compatibility" variants into their plain forms: ligatures into letters, full-width letters into ordinary ones, non-breaking spaces into spaces, "²" into "2". NFKC is right for a search index and wrong for display, so keep both.

import unicodedata
s = "conﬁguration café menu"            # a ligature, a decomposed é, a non-breaking space
len(s), len(unicodedata.normalize("NFC", s))      # NFC composes é
unicodedata.normalize("NFKC", s)                    # 'configuration café menu'

Cleaning extracted text

Clean in a fixed order and measure each step. Normalise Unicode (NFKC for the index). Remove invisible characters NFKC keeps: zero-width spaces and joiners, soft hyphens and byte-order marks. Rejoin words hyphenated at line ends, carefully, since "well-known" at a line end should keep its hyphen. Collapse runs of whitespace, but keep paragraph breaks, which chunking will need. Map curly quotes and dashes to straight ones for matching. Remove repeated headers, footers and page numbers that a PDF extractor puts on every page. Lowercase only the copy used for keyword matching; embedding models were trained on cased text.

import re, unicodedata
INVISIBLE = re.compile(r"[​‌‍­﻿]")
QUOTES = str.maketrans({"’": "'", "‘": "'", "“": '"', "”": '"', "–": "-", "—": "-"})

def for_index(text: str) -> str:
    t = unicodedata.normalize("NFKC", text)
    t = INVISIBLE.sub("", t)
    t = re.sub(r"(\w)-\n(\w)", r"\1\2", t)          # line-end hyphenation
    t = re.sub(r"[ \t]+", " ", t.translate(QUOTES))
    return re.sub(r"\n{3,}", "\n\n", t).strip()          # keep paragraph breaks

Sentences and paragraphs

Chunking (Chapter 4) splits on paragraphs first and sentences second, so both must be found reliably. Paragraphs are usually blank lines, or block elements in HTML; keep them through cleaning. Sentences are harder than splitting on full stops: "e.g.", "U.S.", "3.5 GB", "app.py" and "Dr." all contain full stops that do not end a sentence. Use a tested splitter (a rule-based one such as pySBD or the one in spaCy or NLTK) rather than a regular expression, and check it on your own text, especially for code, lists and tables.

Regular expressions

Regular expressions are the right tool for small, well-defined cleaning rules: invisible characters, hyphenation, whitespace, page-number lines. Keep each rule separate and named, test it on real samples, and prefer raw strings (r"...") so backslashes mean what you wrote. Beware patterns that can backtrack catastrophically, such as nested quantifiers like (a+)+, on long untrusted text, and never use regular expressions to parse HTML: use an HTML parser and take the text from the elements you want.

Language detection

A corpus that mixes languages needs to know which is which: to choose a multilingual embedding model or route by language, to apply the right sentence splitter and stop words, and to answer in the user's language. Detection libraries (fastText's language identifier, lingua, CLD3) work well on paragraphs and poorly on very short strings; detect per document or per section, not per sentence, and store the result as metadata.

Use case: Spotify's Unicode usernames

In 2013 Spotify's engineering blog described a security bug that came from text normalisation. To stop people registering look-alike names, Spotify mapped usernames to a canonical form, so that, for example, "ᴮᴵᴳᴮᴵᴿᴰ" with small-capital letters would be treated like "bigbird". The function it used was not idempotent under the Unicode library version in use: applying it twice could change a name again. An attacker could register a name that canonicalised to an existing user's name during the password-reset flow and take over that account. Spotify fixed it by checking that canonicalisation is idempotent and rejecting names where it is not. The lesson carries straight into retrieval: normalisation decides which strings count as "the same", so choose the form deliberately, apply the same function on every path (indexing, querying, filtering), test it on hostile input, and pin the library version so that the definition of "the same" does not change underneath you.

⚠️
Common mistakes
  • Indexing raw extracted text without normalisation.
  • Normalising documents but not queries, or with a different function.
  • Collapsing all whitespace, including the paragraph breaks chunking needs.
  • Splitting sentences on every full stop.
  • Lowercasing or NFKC-normalising the text you display.
  • Parsing HTML with regular expressions.

Interview drill

Explain it simply: Why would a keyword search fail to find a word that is clearly visible in a PDF?

How a strong answer sounds
Because what you see is not what is stored. PDF extraction often produces ligature characters like "ﬁ", words hyphenated across lines, non-breaking or zero-width spaces, decomposed accents and curly apostrophes, all of which look normal on screen but are different code points. I would normalise the index text with Unicode NFKC, remove invisible characters such as soft hyphens and zero-width spaces, rejoin line-end hyphenation, map quotes and collapse whitespace, applying exactly the same function to queries, and keep the original text for display.

Deeper: You are ingesting 50,000 PDFs of mixed quality for a RAG system. How do you make the text reliable?

How a strong answer sounds
Sample first: extract a few hundred documents and look at the text, counting non-ASCII characters, ligatures, hyphenation, empty pages and repeated headers and footers, and checking scanned pages that need OCR. Then build a cleaning pipeline of small, tested steps in a fixed order: NFKC for the index copy, invisible-character removal, careful dehyphenation, header and footer removal by repetition across pages, whitespace normalisation that keeps paragraphs, and language detection per document. Measure each step on a labelled set, for example how many known phrases become findable, and keep the original text and page numbers for citations. Version the pipeline and record which version produced each chunk, so a fix can trigger reprocessing of exactly the affected documents.

🧠 Key takeaways

  • The same visible text can be different code points; normalise it.
  • NFC to store, NFKC to index; apply the same function to documents and queries.
  • NFKC does not remove soft hyphens or zero-width spaces: strip them separately.
  • Rejoin line-end hyphenation and keep paragraph breaks for chunking.
  • Keep the original text for display and citations.
