Indexing Pipelines & Updates

A demo indexes its documents once. A real system's documents change every day: pages edited, files deleted, new ones added, permissions revised. The indexing pipeline has to keep the index matching the source without re-embedding everything each time, leaving stale chunks behind, or serving a half-updated index. Most of that comes down to two questions. What actually changed? And how do you change the index to match?

This chapter answers both with real edits. It replays four commits from 13 October 2026, when this Atlas's own chapters were revised in bulk, through an extractor and two chunkers, and counts how many chunks each edit really changed. It then measures adding and deleting vectors in a live HNSW index against rebuilding it.

  • Design an ingestion job: fetch, extract, chunk, embed, write
  • Detect changes with content hashes at file and chunk level
  • Explain how the chunking strategy decides the cost of an edit
  • Handle deletes and in-place updates in a vector index
  • Plan a full re-embedding when the model changes

Ingestion jobs

An ingestion job runs the same stages for every source:

  • list what exists;
  • fetch what changed;
  • extract clean text;
  • chunk it;
  • embed the chunks;
  • write vectors and metadata, keyed by document and chunk id.

Make each stage idempotent, so a crashed run can simply be repeated. Record per document the source version, the content hash, the chunker and embedding-model versions, and the time indexed. Run it on a schedule or on change events (webhooks, a database's change stream), and alert when a source stops updating.

for doc in source.changed_since(last_run):
    text = extract(doc)
    if sha256(text) == state[doc.id].text_hash: continue      # edit outside the indexed text: nothing to do
    new = {sha256(c): c for c in chunk(text)}
    old = state[doc.id].chunk_hashes
    index.delete([chunk_id(doc, h) for h in old - new.keys()])
    index.upsert([(chunk_id(doc, h), embed(new[h]), meta(doc)) for h in new.keys() - old])

Change detection

Timestamps say a file was touched; hashes say whether its content changed. Hash at two levels. A file hash of the extracted text skips files whose edits fall outside the indexed text. The lab's first commit reworded quiz options in 50 chapters, and the extractor ignores quizzes, so not one chunk needed re-embedding. A chunk hash then re-embeds only the chunks whose text differs. How many differ depends on the chunker.

Simulator: four real edits, two chunkers

Each commit's changed chapters were extracted before and after with Chapter 4's extractor. Each version was chunked two ways: fixed 200-word windows, and recursive chunks that follow sections and paragraphs up to 200 words. A chunk needs embedding if its SHA-256 hash did not exist before the edit. The whole corpus at the time was 508 chapters: 6,368 fixed chunks or 8,164 recursive ones.

Things to try.

  • Paragraph breaks, fixed vs recursive: the reverse. Fixed windows barely changed (37 (1%)) because the words did not, while recursive chunks (468 (12%)) follow paragraphs, so new breaks moved their boundaries.
  • Removing repeated teaching: deletions shift fixed windows too (306 (31%) against 114 (9%)).

Deduplication

Documents arrive more than once: the same PDF in two folders, a page and its print view, a section quoted in another chapter. Hash extracted documents and chunks, and keep one copy, recording every place it appears so permissions and citations stay right (Chapter 23). Near-duplicates need a similarity check, such as MinHash on shingles at indexing time, or embedding similarity at query time (Chapter 16).

Deletes

A deleted source document must disappear from the index, or the system will cite pages that no longer exist, or worse, ones a user is no longer allowed to see (Chapter 39). Key chunks by document id so a delete can find them. Graph indexes usually mark deleted vectors and skip them at query time, then clean up by rebuilding or reusing the slots. The lab measured this on Chapter 7's 83,118 sentence vectors:

  • Adding 5,000 vectors to a live HNSW index took 1.7 s, against 23 s to rebuild with them.
  • Marking 8,312 (10%) deleted took 0.01 s.
  • Recall@10 against exact search on the remaining vectors was 0.991, the same as a freshly rebuilt index (0.990).

Marked vectors still use memory, so schedule rebuilds when deletes pile up.

Re-embedding a corpus

A new embedding model makes every stored vector incomparable with new queries, so the whole corpus must be re-embedded. Old and new vectors cannot be mixed. Build the new index alongside the old one and switch reads with an alias when it is complete and evaluated: a blue/green swap. Store the model name and version with every vector. Budget the job from the measured throughput: Chapter 5 embedded about 9,400 documents (SciFact plus the Atlas sections) in 29 seconds in half precision on a laptop GPU, so a corpus a thousand times larger needs most of a day on that hardware. Keep the chunk text so you never need to re-extract.

Use case: index aliases and zero-downtime reindexing

Search engines solved the "rebuild without downtime" problem long before RAG. Elasticsearch and OpenSearch let an application read and write through an alias, a name that points at one or more real indexes. To change mappings or re-process every document, operators build a new index in the background (the reindex API copies and transforms documents), check it, and then move the alias in one atomic step. The old index stays for rollback. Vector databases adopted the same pattern for changing the embedding model, where no in-place update is possible: Qdrant and Weaviate offer collection aliases for exactly this. The lab's numbers show why both paths exist. Small edits are cheap in place, while a new model means a rebuild that must not interrupt reads.

⚠️
Common mistakes
  • Re-embedding every file on every run.
  • Chunk ids that are just positions.
  • No delete path.
  • Mixing vectors from two embedding models.
  • Hashing raw files instead of extracted text.
  • Never rebuilding after many deletes.

Interview drill

Explain it simply: How do you keep a RAG index up to date as documents change?

How a strong answer sounds
Run an incremental ingestion job: find documents changed since the last run, extract their text and compare its hash with the stored one, skipping documents whose indexed text did not change. For changed ones, chunk and hash each chunk, embed only chunks whose hash is new, and delete chunks whose hash vanished. Key everything by document and chunk id so deletes and updates can find their vectors, and record the model and chunker versions. Graph indexes mark deletes and need periodic rebuilds; a new embedding model needs a full rebuild in a parallel index, swapped in with an alias.

Deeper: After a routine content edit, your nightly job re-embedded almost half the corpus. Why, and how would you fix it?

How a strong answer sounds
Probably fixed-size chunking: windows of N words or tokens mean any insertion or deletion shifts every later window in the document, so every chunk after the edit gets a new hash. In testing, splitting long sentences across 231 chapters changed 47% of fixed-window chunks but 10% of section-and-paragraph chunks. Switch to structure-aware chunking so edits stay local, add a document-level hash of the extracted text so edits outside it are skipped, and check the extractor is deterministic. Then confirm chunk ids are content-derived rather than positional, so unchanged chunks keep their vectors.

🧠 Key takeaways

  • Hash extracted text per document and per chunk; embed only new hashes.
  • The chunker decides how far an edit ripples: fixed windows shift, structure-aware chunks stay local.
  • Key chunks by document id so deletes and updates can find them.
  • HNSW handles adds and marked deletes in place cheaply; rebuild periodically.
  • A new embedding model means a full rebuild beside the old index, then an alias swap.
