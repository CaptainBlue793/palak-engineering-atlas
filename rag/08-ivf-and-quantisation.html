IVF, Product Quantisation & Memory

HNSW (Chapter 7) is fast but keeps every full-precision vector, plus a graph, in RAM. At a few hundred million vectors that is hundreds of gigabytes. This chapter covers the other family of vector indexes. These split the collection into clusters so a query scans only a few of them (IVF), and they compress each vector to a few dozen bytes (quantisation), trading recall for memory.

The lab runs eleven faiss indexes over the same 83,118 sentence embeddings and 1,000 queries as Chapter 7, from exact float search to 48-byte binary codes. It measures recall@10 against exact search, latency and memory for each, and shows why rescoring a compressed index's top 100 with the original vectors recovers most of what compression loses.

Inverted file indexes

An inverted file index (IVF) runs k-means over the vectors to find nlist centroids. It then files each vector in the list of its nearest centroid, the way a book index files each page under a few headings. A query is compared with the centroids first, and only the vectors in the closest lists are scanned. With 256 lists over 83,118 vectors, each list holds about 325 vectors, so scanning one list touches 0.4% of the collection. A common starting point is an nlist near the square root of the number of vectors. Training the centroids needs a representative sample of the data.

nprobe

nprobe is how many of the nearest lists a query scans. It is IVF's query-time dial, like HNSW's ef_search. A true neighbour that was filed in a list just outside the nprobe closest is simply never seen. So recall depends on how well the clusters separate the data, and on whether queries sit near the centroids the way documents do. The lab shows that the second condition matters a lot. Short queries and claims land between the clusters of full sentences far more often than sentences from the collection do.

import faiss
index = faiss.index_factory(384, "IVF256,PQ48x8", faiss.METRIC_INNER_PRODUCT)  # 256 lists, 48 one-byte codes per vector
index.train(sample)                                                             # k-means for the lists and the PQ codebooks
index.add(vectors)
index.nprobe = 32                                                                 # lists scanned per query
scores, ids = index.search(queries, 100)                                       # then rescore these 100 with full vectors

Product quantisation

Product quantisation (PQ) splits each 384-number vector into m sub-vectors, for example 48 pieces of 8 numbers each. It learns a codebook of 256 typical values for each piece, and stores, for every vector, the index of the closest codebook entry for each piece: 48 bytes instead of 1,536, a 32-fold saving. Distances to a query are estimated from small lookup tables, which is fast. But the estimate is coarse, so neighbours whose true scores differ by less than the quantisation error swap places. That is why PQ's recall plateaus: scanning more lists cannot fix errors that are in the codes themselves. Training the codebooks is also slow, from 50 to 183 seconds here against about a second for IVF-Flat.

Scalar and binary quantisation

Scalar quantisation rounds each number separately: to 16-bit floats (half the memory) or to 8-bit integers (a quarter, SQ8). Because each dimension keeps its own value, the ranking barely changes. Binary quantisation keeps one bit per dimension, its sign, and compares vectors by counting differing bits (Hamming distance). That is 48 bytes for 384 dimensions, and very fast on modern CPUs, but much cruder. Both binary and PQ codes work best as a first pass. Fetch the top 100 or so candidates from the compressed index, then rescore them with the full vectors, which can live on disk because only 100 are read per query.

Things to try.

  • IVF-Flat, nprobe 1 → 128: recall climbs from 0.23 to 0.96, but reaching 0.96 means scanning half the lists, at 3.2 ms. Chapter 7's HNSW reached 0.95 at 0.36 ms on the same queries.
  • The same IVF index with sentences from the collection as queries (held out, 1,000 of them): nprobe 16 gives 0.83 and nprobe 64 gives 0.97, against 0.65 and 0.88 for the real queries. IVF's lists are drawn around the documents, and short queries fall between them.
  • IVF-PQ 96 → 48 → 24 bytes at nprobe 128: recall stops at 0.77, 0.59 and 0.39. More lists cannot fix errors in the codes.
  • IVF-PQ 48 B + rescore: the same 5 MB of codes, but rescoring the top 100 with full vectors lifts recall at nprobe 128 from 0.59 to 0.92.
  • Binary vs Binary + rescore: 0.47 → 0.80 overall, but 0.93 on glossary queries against only 0.51 on SciFact claims. Compression hurts some query types far more than others.
  • SQ8: a quarter of the memory with recall 0.992, nearly free in accuracy.

Memory budgets

Estimate memory before choosing an index. Multiply the bytes per vector by the number of vectors, then add the structure: about 148 bytes per vector for an HNSW graph with M 16 (measured above), and 8 bytes per vector for the ids in an IVF list. The table uses 384 dimensions, as here. A 1,024-dimension model multiplies the float, fp16 and SQ8 rows by about 2.7, while PQ and binary sizes are whatever you choose them to be.

Use case: product quantisation and faiss

Hervé Jégou, Matthijs Douze and Cordelia Schmid introduced product quantisation for nearest neighbour search in a 2011 paper in IEEE Transactions on Pattern Analysis and Machine Intelligence. They combined it with an inverted file so that image descriptors numbering in the billions could be searched from memory on a single machine. The same group, later at Facebook AI Research, built faiss around these ideas and released it as open source in 2017, with a paper on billion-scale similarity search on GPUs by Jeff Johnson, Douze and Jégou. The index_factory strings used in this chapter, such as "IVF256,PQ48x8", come from faiss. Vector databases that offer IVF, PQ, scalar or binary quantisation, with or without a rescoring step, are applying the same trade-off measured in the lab: memory saved against neighbours lost.

⚠️
Common mistakes
  • Tuning nprobe on documents as queries rather than real queries.
  • Expecting more nprobe to fix PQ's recall plateau.
  • Compressing without rescoring when the full vectors could sit on disk.
  • Training the centroids and codebooks on a sample that is unlike the full data.
  • Forgetting graph and id overhead in a memory estimate.
  • Checking recall on one query type only.

Interview drill

Explain it simply: How do IVF and product quantisation make vector search cheaper?

How a strong answer sounds
IVF clusters the vectors with k-means and files each in the list of its nearest centroid. A query compares itself with the centroids and scans only the nprobe closest lists, so it touches a small fraction of the data; the cost is missing neighbours filed in other lists. Product quantisation compresses each vector by splitting it into sub-vectors and storing, for each, the id of the nearest entry in a learned 256-entry codebook. That turns 1,536 bytes into, say, 48, and distances are estimated from lookup tables. The estimate is coarse, so recall plateaus, and the usual fix is to fetch the top 100 or so from the compressed index and rescore them with the full vectors.

Deeper: You need to serve 500 million 768-dimension embeddings on machines with 256 GB of RAM. What do you do?

How a strong answer sounds
Do the arithmetic first: float32 is 3,072 bytes per vector, about 1.5 TB, so full vectors in RAM would need six or more machines before any graph overhead. Options: shard across machines; use SQ8 (768 bytes, about 384 GB) with HNSW and shard in two; or keep PQ or binary codes in RAM (64–96 bytes, roughly 32–48 GB) with the full vectors on SSD for rescoring the top 100–200. A disk-based graph index such as DiskANN is another route. Choose by measuring recall@k against exact search on a sample of real queries, at the k the pipeline uses, and by the latency budget, since SSD reads for rescoring add time.

🧠 Key takeaways

  • IVF scans only the nprobe nearest lists; recall depends on the queries sitting near the centroids.
  • PQ shrinks vectors by 16–64 times, but its recall plateaus because the codes are approximate.
  • Rescoring a compressed index's top 100 with full vectors recovers most of the loss.
  • SQ8 cuts memory to a quarter for almost no recall.
  • Estimate memory per vector, times vectors, plus structure, before choosing.
