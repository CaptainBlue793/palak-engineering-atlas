Your First RAG Pipeline

A working RAG system is six stages and not much code: load documents, split them into chunks, embed the chunks, store the vectors in an index, retrieve the nearest chunks for a question, and generate an answer from them. Every later chapter improves one of those stages, so it pays to build the whole thing once, end to end, and see where the time and the problems are.

This chapter builds that pipeline over the Atlas itself and times every stage at three sizes: one course, four courses and all eleven. Then it asks the finished system three questions and shows the sources it retrieved and the answers it wrote.

The six stages

Three stages run offline, whenever documents change: load (read and parse documents into text with structure, Chapter 3), chunk (split into retrievable pieces, Chapter 4) and embed and index (turn chunks into vectors and store them, Chapters 5 to 9). Three run online, for every question: retrieve (embed the question and find the nearest chunks), assemble (build a prompt from instructions, sources and the question, Chapter 10) and generate (call the model). Keeping the two paths separate matters: indexing can take minutes and run in a batch job; answering must take about a second.

A minimal index

For a few thousand chunks, an exact flat index is all you need: faiss's IndexFlatIP stores the normalised vectors and returns the top-k by inner product, which is cosine similarity (P4). Store the chunk text and metadata in the same order as the vectors, so a result's position leads back to its text and source.

import faiss, numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-small-en-v1.5", device="cuda")
chunks = [c for doc in load(paths) for c in recursive_chunks(doc)]           # load, chunk
vecs = model.encode([f"{c.title}\n{c.text}" for c in chunks], batch_size=32, normalize_embeddings=True)
index = faiss.IndexFlatIP(vecs.shape[1]); index.add(vecs.astype(np.float32))   # embed, index

def retrieve(question: str, k: int = 4):
    q = model.encode([QUERY_PREFIX + question], normalize_embeddings=True).astype(np.float32)
    scores, ids = index.search(q, k)
    return [(chunks[i], float(s)) for i, s in zip(ids[0], scores[0])]

Retrieving top-k

The number of chunks to retrieve, k, trades recall against prompt size. Too few and the answer may not be among them (Chapter 1's two misses); too many and the prompt grows, costs rise and the model has more irrelevant text to ignore. Start with 3 to 5 chunks of 200 to 300 tokens, measure recall@k on your questions (Chapter 19), and log the scores: a top score far below usual is a sign the corpus may not contain the answer.

The prompt

The first prompt should do three things: give the sources as numbered blocks with their titles, tell the model to answer only from them and cite the numbers, and tell it what to do when they do not contain the answer. The answers below show that even this small model follows the second and third rules most of the time, and they show the main failure of a first pipeline: when retrieval brings a weak passage, such as a table row out of context, the answer is weak too.

SYSTEM = ("Answer the question using only the numbered sources. Cite sources like [1]. "
          "If they do not contain the answer, say you do not know.")
sources = "\n\n".join(f"[{i}] {c.title} ({c.course})\n{c.text}" for i, (c, _) in enumerate(retrieve(q), 1))
answer = chat(SYSTEM, sources + "\n\nQuestion: " + q, num_ctx=8192)

Where the time goes

Measured here, the offline path scales with the corpus (about a minute for 600 chapters on a laptop GPU), and it runs only when documents change. The online path is dominated by generation, which scales with answer length (P2), not corpus size. Exact search over thousands of vectors is effectively free; approximate indexes (Chapter 7) start to matter around millions. So the first optimisations are usually a shorter answer, streaming tokens to the user, caching (Chapter 28) and a smaller prompt, not a faster index.

Use case: the first wave of RAG frameworks

When ChatGPT appeared at the end of 2022, building "chat with your documents" became the most common first project for developers using language models, and two open-source libraries grew up around exactly this chapter's pipeline. LlamaIndex (first released as GPT Index in November 2022 by Jerry Liu) focused on loading, indexing and querying documents; LangChain (October 2022, Harrison Chase) on chaining model calls, of which retrieval was one. Both offered document loaders, text splitters, embedding wrappers, vector store integrations and prompt templates, so a working pipeline took a dozen lines. Teams learned quickly that the dozen lines were the easy part: the defaults for splitting, retrieval and prompting rarely suited their documents, and quality came from measuring and changing each stage, which is why this course builds each stage by hand before reaching for a framework.

⚠️
Common mistakes
  • Optimising the index before measuring where the time goes.
  • Mixing indexing and answering in the request path.
  • Losing the link from vector position back to chunk text and source.
  • No instruction for "not in the sources" in the prompt.
  • Leaving the model server's default context size (P2).
  • Judging the system on a couple of questions instead of an evaluation set.

Interview drill

Explain it simply: Walk me through a basic RAG pipeline.

How a strong answer sounds
Offline, documents are loaded and parsed into text, split into chunks of a few hundred tokens along their structure, embedded with an embedding model, and stored in a vector index together with each chunk's text and metadata. Online, a question is embedded with the same model, the index returns the top few most similar chunks, and those are put into a prompt as numbered sources with instructions to answer only from them, cite them and say when they do not contain the answer. The model generates the answer. Most of the user's wait is generation; most of the quality depends on parsing, chunking and retrieval.

Deeper: Your prototype answers in 6 seconds and the product team wants under 2. Where do you look?

How a strong answer sounds
First measure each stage of the online path, because usually generation dominates and search is negligible. Then shorten the work the model does: a lower maximum answer length or a prompt asking for brevity, fewer or shorter retrieved chunks, and streaming so the first words appear quickly. Make sure the model stays loaded and the context size is not oversized. Consider a smaller or faster model if quality allows, and caching for repeated questions. Only if retrieval itself is slow, for example a reranker or a remote vector database, optimise there. Track time to first token and total time as separate metrics.

🧠 Key takeaways

  • Six stages: load, chunk, embed and index offline; retrieve, assemble and generate online.
  • A flat index is enough for thousands of chunks: searching took under a millisecond.
  • Embedding dominates indexing; generation dominates answering.
  • Number the sources, ask for citations and give the model a way to decline.
  • Weak answers usually trace back to retrieval and chunking, so measure those first.
