Retrieval over Code & Technical Docs

Code assistants are one of the biggest uses of RAG, and code breaks the assumptions prose retrieval relies on. Meaning sits in identifiers such as get_max_seq_length and HTTPStatusError that no tokenizer for English handles well. Structure matters: a function cut in half is two useless chunks. And users ask two very different kinds of question, "how do I do X?" and "where is Y defined?".

The lab indexes the Python source of six real libraries: 4,358 functions in 395 files. It asks 400 questions taken from docstrings and 200 identifier lookups. It compares chunking by syntax with fixed line windows, and plain keyword, identifier-aware keyword, embedding and hybrid retrieval.

  • Chunk code along its syntax tree, not by line counts
  • Tokenize identifiers so keyword search can match them
  • Pick the retriever for "how do I" and "where is" questions
  • Combine code, documentation and history
  • Keep a code index fresh as the repository changes

Chunking code

Parse the code and cut along its structure: one chunk per function or method, with the class and file it belongs to, and small classes or modules whole. Python's ast module does this; tree-sitter does it for most languages. Prefix each chunk with where it lives, such as # requests/models.py :: Response.raise_for_status. That way the path and qualified name are searchable, and the model knows what it is reading. In the lab, function chunks beat 40-line windows on every retriever. For docstring questions, dense retrieval found the function in the top 5 80.5% of the time against 67.2% with windows.

for node in ast.walk(ast.parse(src)):
    if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
        body = "\n".join(lines[node.lineno - 1:node.end_lineno])
        chunks.append(f"# {path} :: {qualname(node)}\n{body}")      # location is part of the text

Identifiers and exact matches

A plain tokenizer splits encode_multi_process on underscores but leaves SentenceTransformer as one unusual word, and never matches the user who types "sentence transformer". An identifier-aware analyser emits the whole identifier and its parts: sentencetransformer, sentence, transformer. For "where is X defined?" questions it raised BM25's top-1 hit from 58.0% to 81.5%. Exact identifiers are also where keyword search beats embeddings once the chunk text lacks the name. With line windows and no location header, identifier lookups found the definition in the top 5 71.5% of the time with dense retrieval and 88.5% with identifier-aware BM25.

Docs plus code

Questions about code are often answered best by documentation, examples, tests or past discussions, not the code alone. Index them all, with a source-type field, and retrieve across them. Tests show real usage, and docstrings and READMEs say what is intended. Issue and pull-request history explains why the code is as it is. Use a code-trained embedding model when you can. bge-small here is a general model, and code-specific embedders are trained on pairs of docstrings and functions exactly like this lab's queries.

Repository maps

For questions about how a codebase fits together, chunks are too local. A repository map is a compact outline of files, classes and function signatures, often ranked by how many references point at each. It gives the model the shape of the code in a few thousand tokens. Coding assistants combine a map with retrieved chunks and with tools that follow references: go to definition, find usages. That moves towards agentic retrieval (Chapter 34).

Freshness

Code changes constantly, and stale code is worse than none, because the model will confidently cite a function that no longer exists. Re-index on every commit, using file hashes and function-level chunk hashes (Chapter 22). Store the commit with each chunk, and prefer the developer's working copy over the main branch when answering about their checkout.

Use case: CodeSearchNet and code-aware retrieval

In 2019 GitHub and Microsoft Research released the CodeSearchNet corpus and challenge (Hamel Husain, Ho-Hsiang Wu, Tiferet Gazit, Miltiadis Allamanis and Marc Brockschmidt). It held about two million functions with their documentation, in six languages, plus a set of real natural-language queries with expert relevance judgements. Its key move was the one this lab copies: use each function's docstring as a stand-in query and the function as the answer, giving millions of free training pairs. Code-trained encoders and code search tools learned from that data and its successors. They also found what the lab shows in small: keyword search with good identifier handling remains a strong baseline for lookups, while learned models win for natural-language intent.

Common mistakes
  • Chunking code by lines or tokens.
  • No location in the chunk text.
  • An English analyser on identifiers.
  • Embeddings only.
  • Stale indexes.
  • Leaving tests and docs out.

Interview drill

Explain it simply: How is retrieval over code different from retrieval over documents?

How a strong answer sounds
Code has structure that chunks must respect, so you split by functions and classes from a parser rather than by length, and prefix each chunk with its file and qualified name. Meaning lives in identifiers, so keyword search needs an analyser that keeps whole identifiers and splits camelCase and snake_case. Questions come in two kinds: "where is X" lookups, where exact keyword matching shines, and "how do I" intent questions, where embeddings, ideally code-trained, do better. And code changes constantly, so the index must update per commit.

Deeper: Your code assistant often retrieves the wrong half of a function, and misses functions users name exactly. What do you change?

How a strong answer sounds
Both symptoms point at chunking and analysis. Half-functions mean fixed-size chunking: switch to syntax-aware chunks from a parser (ast or tree-sitter), one per function or method, splitting only very long ones at statement boundaries. Missed exact names mean the keyword side lacks an identifier-aware analyser, or there is no keyword side at all: add BM25 with identifier splitting, and put the path and qualified name in each chunk's text. Then fuse keyword and dense results, or route lookups to keywords. Measure with docstring-style queries for intent and with identifier queries for lookups, as separate sets.

🧠 Key takeaways

  • Chunk code by syntax and prefix each chunk with its path and name.
  • Identifier-aware analysers make keyword search work on code.
  • Embeddings win for "how do I"; keywords and hybrids for "where is".
  • Index tests, docs and history alongside code.
  • Re-index per commit; stale code misleads.
