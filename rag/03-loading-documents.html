Loading & Parsing Documents

Retrieval can only find what the loader extracted, and the generator can only answer from what retrieval returns. If the loader keeps navigation menus, cookie banners and scripts, they end up in chunks and prompts; if it loses headings, chunking has nothing to split on; if it scrambles a table, no model can recover which value belonged to which row. Parsing is the first quality decision in a RAG pipeline, and the least glamorous.

This chapter covers HTML and Markdown, PDFs and their traps, tables, structure and metadata. The lab takes 60 chapters of the Atlas, prints each to PDF with Chrome, and extracts text five ways, then measures how much of each result is not content, what structure survives, and how well keyword retrieval works on it.

  • Extract the main content of HTML and Markdown and drop page furniture
  • Recognise what PDF text extraction loses and adds
  • Keep tables as rows instead of streams of cells
  • Preserve headings and positions for chunking and citations
  • Attach the metadata retrieval and filtering will need

HTML and Markdown

A web page is mostly not its content: navigation, headers and footers, sidebars, scripts, styles, cookie notices and related links surround the article. Parse HTML with a real parser (BeautifulSoup with lxml, or a dedicated extractor such as trafilatura), select the main content element (main, article, or the element your site uses), remove scripts, styles and interactive widgets, and walk the remaining elements in order, keeping headings as headings, list items as lines and table rows as rows. Markdown is easier: it is already structured text, and a Markdown parser gives headings, lists, code blocks and tables directly. Never strip tags with a regular expression: it keeps script and style contents as if they were prose.

from bs4 import BeautifulSoup

def extract(html: str) -> str:
    soup = BeautifulSoup(html, "lxml")
    main = soup.select_one("main, article") or soup.body
    for el in main.select("script, style, nav, form, .quiz-wrap"):
        el.decompose()                                           # page furniture and widgets
    lines = []
    for el in main.find_all(["h1", "h2", "h3", "p", "li", "pre", "tr"]):
        if el.name == "tr":                                           # one table row per line
            lines.append(" | ".join(c.get_text(" ", strip=True) for c in el.find_all(["th", "td"])))
        elif el.name[0] == "h":
            lines.append("#" * int(el.name[1]) + " " + el.get_text(" ", strip=True))
        else:
            lines.append(el.get_text(" ", strip=True))
    return "\n".join(l for l in lines if l)

PDFs and their traps

A PDF is a set of instructions for placing glyphs on pages, not a document structure. Text extraction reconstructs words and lines from glyph positions, and gets several things wrong: headings become ordinary lines, page headers, footers and page numbers repeat on every page, words are hyphenated at line ends, icon fonts come through as private-use characters, multi-column layouts can be read across columns, and table cells are emitted in reading order rather than by row. Scanned PDFs have no text at all and need OCR. For important corpora, prefer the source format (HTML, DOCX, Markdown) when you have it; when you must use PDFs, try a layout-aware extractor and look at its output on your own documents.

Tables

Tables are where extraction most often destroys meaning. A row is a fact ("What can change | How data is stored | The logical schema"); emitted as a stream of cells, the row structure is gone, and in a two-column PDF table the cells of different columns can interleave line by line. Keep each row on one line with a separator, keep the header row and repeat it, or convert each row into a sentence ("For logical data independence, what can change is the logical schema"). Very large tables are better stored as structured data and queried (Chapter 18) than chunked as text.

Simulator: one corpus, five extractions

Sixty Atlas chapters (the first ten in each of six courses) were extracted five ways: stripping tags from the HTML with a regular expression; BeautifulSoup's get_text() on the whole page; structure-aware extraction of the main content as above; and Chrome's printed PDF of each page read with pypdf, raw and after cleaning (repeated header and footer lines, page numbers, line-end hyphenation and private-use glyphs removed). The PDFs came to 675 pages. Each result was split into 200-word chunks and searched with BM25 for the 247 glossary terms defined in those chapters.

Keeping structure

Keep the document's own structure through loading: headings with their levels, paragraphs, list items, code blocks and table rows. Chunking can then split on sections rather than arbitrary word counts, retrieval can return a section with its heading, and citations can point to "Section 3.2, page 14". Record the position of every piece (heading path, page number, character offsets) so that an answer can be traced back to exactly where it came from.

Metadata to keep

Attach metadata at load time, because it is hard to recover later: the source URL or path, title, author and owner, created and modified dates, document type, language, version, access permissions (Chapter 23), and the heading path and page of each piece. Metadata drives filters ("only the current policy", "only documents this user may read"), freshness checks and deletion, and makes citations useful. Also store a content hash, so unchanged documents are not reprocessed (Chapter 22).

Use case: Common Crawl and the cost of boilerplate

Common Crawl, a non-profit, has published regular crawls of billions of web pages since 2008, and its archives are the starting point for most large language model training sets. Its raw text extractions are notoriously noisy: navigation menus, cookie banners, "related articles" and footers make up a large share of the text. Projects that built training data from it, such as Google's C4 corpus (2019) and later RefinedWeb and FineWeb, spent most of their effort on extraction and filtering: using HTML-aware extractors such as trafilatura on the raw pages, dropping lines without terminal punctuation, removing pages with too little text or too much repetition, and deduplicating. The FineWeb team reported that re-extracting text from the raw HTML with trafilatura, rather than using the crawl's own text extraction, measurably improved the models trained on the result. A RAG system faces the same problem at smaller scale: whatever boilerplate the loader keeps is indexed, retrieved and pasted into prompts.

⚠️
Common mistakes
  • Stripping HTML tags with a regex, keeping scripts and styles.
  • Indexing the whole page instead of its main content.
  • Trusting PDF text extraction without reading its output.
  • Flattening tables into streams of cells.
  • Throwing away headings, pages and positions needed for chunking and citations.
  • No metadata, so nothing can be filtered, refreshed or deleted later.

Interview drill

Explain it simply: Why does document parsing matter for a RAG system?

How a strong answer sounds
Everything downstream works on what the loader extracted. If it keeps navigation, scripts or boilerplate, those end up in chunks and prompts; if it loses headings, chunking cannot follow the document's sections; if it scrambles tables, the facts in them are gone; and if it drops metadata, you cannot filter, cite or delete properly. I would extract main content with a real parser, keep headings, lists, code and table rows, clean the text, and record source, dates, permissions and positions for every piece.

Deeper: You must ingest 20,000 PDFs of financial reports with many tables. How do you approach it?

How a strong answer sounds
First look for better sources, such as the HTML or XBRL versions of the filings, which carry tables as structure. If PDFs are all there is, sample a hundred and compare extractors, including a layout-aware one, on how well they preserve table rows, headers and multi-column text, and identify scanned pages that need OCR. Keep tables separately: extract them as structured rows with their captions and units, store them in a table or database, and index a textual description of each table for retrieval, with questions over numbers answered by querying the structured data. For prose, keep headings and page numbers for chunking and citations, remove running headers and footers, and record company, period, document type and page as metadata. Then evaluate with real questions whose answers sit in tables.

🧠 Key takeaways

  • Retrieval can only find what the loader extracted; parse deliberately.
  • Extract HTML's main content with a parser; never regex away tags.
  • PDF text loses headings, repeats furniture and scrambles tables: read its output.
  • Keep tables as rows, and headings, pages and positions for chunking and citations.
  • Record metadata at load time: source, dates, version, permissions, position, hash.
