Citations & Grounded Answers

A citation is a promise: this sentence comes from that source. Kept, it lets readers check answers, lets you grade grounding automatically (Chapter 10), and turns the system from an oracle into a guide to its documents. Broken, it is worse than no citation, because it lends a guessed claim the authority of a real document. So a RAG system has to produce citations reliably and then verify that each cited source supports its claim.

The lab asks a 3B model to answer 150 questions in two citation styles, paraphrase with [n] and exact quotes with [n]. It checks every quote against its source, then tests three verifiers on pairs where support is known: embedding similarity, a cross-encoder and the model itself.

  • Choose a citation format the model and the reader can both use
  • Attribute claims to sources at sentence level
  • Verify citations automatically, and know each verifier's limits
  • Weigh quoting against paraphrasing
  • Show sources in the interface so they are actually checked

Citation formats

The usual format is a bracketed source number after each claim, [2], with a numbered source list rendered below the answer. It is short, the model handles it well, and code can parse it. Richer formats carry more:

  • source and passage ids, [doc-14 §3];
  • character spans;
  • structured output with a list of claims, each with its supporting source ids.

Structured output is easiest to verify and to render, and needs a model that follows a schema reliably. Whatever the format, keep a mapping from the numbers the model sees to stable document ids and URLs, because the model's [3] means nothing outside this one prompt.

QUOTE = ("Answer using only the numbered sources. Support each point with an exact quotation from a source, "

Sentence-level attribution

A single citation at the end of a paragraph says little about which claims it covers. Ask for a citation after every sentence or claim, so each statement can be traced and checked on its own. A sentence with no citation is then itself a signal: either it is connective text, or it came from the model's memory. Sentence-level citations also make partial failures visible. An answer can be half supported, and the interface can show which half.

Verifying citations

Verification asks, for each claim and the source it cites, whether the source supports the claim. On controlled pairs, each glossary definition against the section that defines it or the nearest section that does not, all three verifiers separated supported from unsupported well:

  • embedding similarity, AUC 0.86;
  • the cross-encoder, 0.90;
  • the 3B model asked "is the claim supported?", 0.91.

Set to keep 90% of correct citations, the model verifier flagged 75% of wrong ones and similarity only 56%. These pairs are the easy case: an off-topic source. Chapter 20 showed that a single changed fact defeats similarity and strains even the model. Use verification to catch citations to the wrong document, and quotes or an entailment check for the subtle cases.

Things to try.

  • Paraphrase vs quotes: right source cited in 48 against 71 of 150 answers. Asking for quotes made the model cite more, and more accurately.
  • Are the quotes real? 23 of 43 quotes were word for word in the cited source and 13 quoted its heading. Only 3 appeared in no source at all.

Quoting vs paraphrasing

Quotes are checkable without a model: a string match proves the words are in the source. That makes them the strongest defence against invented support. In the lab, asking for quotes also raised right citations from 48 to 71 of 150. Quotes read less naturally, and a quote can be real yet out of context. A practical blend is paraphrased answers with a short supporting quote per claim, shown on hover, and an automatic check that every quote exists in its source.

Showing sources in the UI

Citations only build trust if people use them:

  • render numbers as links to the exact passage, highlighted;
  • show source titles and dates beside the answer;
  • mark sentences without support;
  • let users flag a wrong citation, which is a valuable feedback signal (Chapter 36).

Never show a citation the system could not resolve to a document the user may read (Chapter 23).

Use case: "Evaluating Verifiability in Generative Search Engines"

In 2023 Nelson Liu, Tianyi Zhang and Percy Liang audited four popular generative search engines. Human annotators checked whether each generated sentence was supported by its citations, and whether each citation supported its sentence. The answers read fluently and looked helpful, but only about half of the generated sentences were fully supported by their citations, and about three quarters of citations supported their sentence. Their conclusion was that citations which look authoritative are not the same as citations that verify. This chapter's checks are the cheap first line against the same problem: exact quote matching, and an automatic verifier on every claim–source pair.

⚠️
Common mistakes
  • One citation per paragraph.
  • Prompt-local numbers in the UI.
  • Never verifying.
  • Trusting similarity for subtle errors.
  • Quotes without a check.
  • Citing sources the user cannot open.

Interview drill

Explain it simply: How do you make a RAG system's answers verifiable?

How a strong answer sounds
Number the sources in the prompt, map the numbers to stable document ids, and ask for a citation after every claim, or an exact supporting quote. Parse the citations, check quotes by string matching against the source, and run a verifier on each claim and cited source, such as a cross-encoder or an entailment model, flagging low scores. In the interface, link each citation to the highlighted passage, mark sentences without support, and let users report wrong citations. Measure citation accuracy on a labelled set.

Deeper: Users say citations "look right but don't say what the answer claims". How do you investigate and fix it?

How a strong answer sounds
Sample answers and label each claim–citation pair: supported, partly, not at all, wrong document. If citations point to the wrong document, a verifier can flag them, and in testing embedding similarity, a cross-encoder and a model judge all separated off-topic sources well. If the document is right but the detail is wrong (a changed number or negation), similarity verifiers fail, so require exact quotes checked by string match or use an entailment model. Then change the prompt to quote-plus-cite, add the checks to the pipeline, mark or drop unsupported sentences, and track citation precision over time.

🧠 Key takeaways

  • Cite per claim, with numbers mapped to stable document ids.
  • Asking for exact quotes raised right citations and made checking trivial.
  • Most quotes were real; check every one anyway.
  • Verifiers catch off-topic citations well; subtle errors need quotes or entailment.
  • Show sources so people check them, and collect their corrections.
