Latency & Caching

A RAG request runs several stages in a row:

  • embed the question;
  • search;
  • perhaps rerank;
  • build the prompt;
  • generate.

Users feel the total, and above all the wait before anything appears. Speeding it up means knowing where the time goes, then removing work with caches and hiding the rest with streaming. Caches bring their own risk: serving yesterday's answer, someone else's answer, or the answer to a different question.

This chapter measures every stage on the lab's laptop. It then replays 20,000 questions, skewed the way real traffic is, through exact, normalised and semantic caches. It counts how many answers each cache serves and how many of them are wrong.

  • Build a latency budget for a RAG request from measurements
  • Cache embeddings and retrieval results safely
  • Decide whether a semantic cache is worth its risks
  • Use streaming to cut the time to the first word
  • Know what to invalidate when documents change

A latency budget

Measure each stage separately, one request at a time, on the hardware you will use. On the lab's laptop:

  • embedding the question took 17 ms on the GPU;
  • HNSW search over 9,379 chunks took 0.2 ms;
  • reranking 20 candidates took 29 ms;
  • the 3B model took 694 ms to its first token and 1,566 ms for a full answer of about 58 tokens.

Generation is about 97% of the total. That is typical, and it decides where effort pays:

  • a faster or smaller model;
  • fewer prompt tokens (Chapter 16);
  • shorter answers;
  • skipping generation altogether with an answer cache.

Shaving the search from 0.2 ms to 0.1 ms changes nothing a user can feel.

Embedding and retrieval caches

Some caches are safe because they are deterministic:

  • a query-embedding cache keyed by the model version and the exact text;
  • a document-embedding cache keyed by the content hash, so an unchanged chunk is never re-embedded (Chapter 22);
  • a retrieval cache keyed by query, filters, permissions and index version.

Real traffic is skewed, with a few questions asked very often, so even small caches catch much of it. In the lab's stream, a 2,000-entry cache keyed by exact text served 82% of requests. Normalising the key raised that to 93%: lowercasing, trimming punctuation and stripping "what is" and "explain".

key = sha256(f"{EMBED_MODEL}|{INDEX_VERSION}|{tenant}|{acl_hash}|{normalise(question)}")   # everything that changes the answer
if (hit := cache.get(key)) is not None:
    return hit
answer = pipeline(question)
cache.set(key, answer, ttl=3600)                                           # and purge on index updates

Semantic caching and its risks

A semantic cache returns a stored answer when a new question's embedding is close enough to a cached one. It catches paraphrases that exact keys miss, and it can also hand out an answer to a different question that merely sounds similar. The threshold sets the trade-off. In the lab's stream:

  • at 0.90 it served 87% of requests, and 0.20% of all requests got another term's answer;
  • at 0.80 it served 88%, with 2.0% wrong.

The normalised exact key served about as many with no wrong answers. Embeddings of close-but-different questions are often very similar: 5% of glossary terms had a different term above 0.90. Semantic caches also leak across users unless keyed by permission (Chapter 23). Use them only where a wrong answer is cheap, and prefer key normalisation first.

Things to try.

  • No cache: the model is about 97% of every request.
  • Exact → normalised: 76% → 87% served from cache, still with no wrong answers, and level with the 0.90 semantic cache.
  • Semantic 0.95 → 0.80: more hits, more wrong answers. Each step down the threshold buys little over normalisation and adds risk.
  • Embedding on CPU, reranker off: under 30 ms of difference, invisible next to generation.

Streaming

Streaming sends tokens as the model writes them, so the user starts reading after the first token, here 694 ms, instead of after the whole answer at 1,566 ms. Time to the first token is mostly prompt processing, which grows with the number of prompt tokens. It is the number to optimise for perceived speed, and the reason long contexts feel slow. Use case: Zipf's law and why caches work

In the 1930s and 1940s the linguist George Kingsley Zipf observed that the frequency of words falls off as a power of their rank. The second most common word appears about half as often as the first, the third about a third as often, and so on. Web and search traffic follow the same shape. Lee Breslau and colleagues showed in 1999 that web requests follow a Zipf-like distribution, which explains why modest caches achieve high hit rates. The lab's stream uses that shape. The practical point for RAG is that a few hundred popular questions can make up a large share of traffic, so caching their answers, safely keyed, can remove the most expensive stage for a large fraction of users.

⚠️
Common mistakes
  • Optimising the vector search first.
  • Cache keys without the index version.
  • Cache keys without tenant and permissions.
  • Semantic caching with a loose threshold.
  • Not streaming.
  • Timing batches instead of one request at a time.

Interview drill

Explain it simply: Where does a RAG request spend its time, and how would you make it faster?

How a strong answer sounds
Measure each stage: in typical setups, embedding the query and searching take milliseconds, reranking tens of milliseconds, and generation most of the total, with time to first token driven by prompt length. So: stream the answer, cut prompt tokens with fewer, better chunks, use a faster model where quality allows, and cache. Cache deterministic work (query and document embeddings, retrieval results) with keys that include model and index versions and permissions; cache whole answers for frequent questions with normalised keys; consider a semantic cache only where a wrong answer is cheap, with a strict threshold.

Deeper: Your product manager wants a semantic cache to cut model costs by half. What do you say?

How a strong answer sounds
First measure the traffic: with skewed traffic, an exact cache with normalised keys may already serve a large share with zero wrong answers. In testing, normalisation took a 2,000-entry cache from 82% to 93% of requests. A semantic cache adds paraphrase hits but also serves answers to different questions that embed similarly; the wrong-answer rate depends on the threshold and must be measured on real traffic, with users' tolerance in mind. It must be keyed by tenant and permissions to avoid leaks, and invalidated when the index or documents change. If we proceed: strict threshold, scoped keys, per-entry TTL, logging of hits for review, and a metric for user corrections.

🧠 Key takeaways

  • Generation dominates RAG latency; optimise prompt length, model and answer length first.
  • Stream: time to first token is what users feel.
  • Skewed traffic makes small caches effective; normalise keys before going semantic.
  • Semantic caches trade hits for wrong answers and leak across users if keyed loosely.
  • Keys include model, index version, tenant and permissions; purge on updates.
