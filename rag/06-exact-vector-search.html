Exact Vector Search

The simplest way to find the nearest vectors is to compare the query with every stored vector and keep the best k. That is exact search: it always returns the true nearest neighbours, it needs no tuning and no build step, and it is the yardstick every approximate index is measured against. For a surprising number of RAG systems it is also all that is needed. The question is where it stops being enough.

This chapter covers brute-force top-k, why it is a matrix multiplication, flat indexes, and the scaling wall. The lab times six ways of doing exact search, on the CPU and the GPU, one query and batches of a hundred, from 10,000 to a million vectors.

  • Compute exact top-k with a matrix-vector product and partial selection
  • Use a flat index and know what it adds over raw NumPy
  • Batch queries and use a GPU to multiply throughput
  • Estimate latency and memory as the corpus grows
  • Decide when exact search is enough

Top-k by brute force

With normalised vectors stacked in a matrix X (one row per chunk), the similarity of a query q to every chunk is one matrix-vector product, X @ q. Then select the k largest. Sorting all N scores costs O(N log N); a partial selection such as NumPy's argpartition finds the top k in O(N) and sorts only those. Either way the cost is dominated by touching every number in X once: N × d multiply-adds, where d is the dimension.

scores = X @ q                                            # (N,) cosine similarities, one pass over X
top = np.argpartition(-scores, k)[:k]                     # the k best, in O(N)
top = top[np.argsort(-scores[top])]                       # sort just those k

Matrix multiplication

Brute-force search is a matrix multiplication, the operation CPUs and GPUs are most optimised for. One query uses a matrix-vector product, which is limited by how fast memory can be read; a batch of queries becomes a matrix-matrix product (Q @ XT), which reuses each row of X for many queries and runs much closer to the hardware's peak. That is why batching queries, when you can, makes exact search several times cheaper per query, and why a GPU, with far more memory bandwidth and arithmetic, is faster still.

Flat indexes

A flat index, such as faiss's IndexFlatIP or IndexFlatL2, is brute force packaged: it stores the vectors contiguously, computes scores with optimised kernels, selects top-k with a heap, handles batches, and offers the same interface as the approximate indexes in the next two chapters, so you can switch later without changing code. Vector databases use the same idea for small collections and as a fall-back when filters leave few candidates (Chapter 9).

index = faiss.IndexFlatIP(384)
index.add(X)                                   # no training, no parameters
scores, ids = index.search(Q, k)               # Q: (n_queries, 384); batch when you can

Things to try.

  • 10,000 vectors: every method answers in about a millisecond or less. For a typical company knowledge base, exact search is simply the right choice.
  • numpy full sort vs argpartition: partial selection saves a third of the time; the multiplication still dominates.
  • batch of 100: faiss's per-query cost drops about fivefold, because one pass over X now serves 100 queries.
  • 1,000,000 vectors: a single CPU query takes about 62 ms, too slow to share a request budget with a reranker and a model call. The GPU does it in 4.4 ms, or 0.15 ms per query in batches.

When exact is enough

Exact search time grows linearly with N and memory is N × d × 4 bytes. Measured here, a single CPU query costs roughly 0.06 ms per thousand vectors at 384 dimensions, so up to a few hundred thousand vectors it fits easily in a 50 ms retrieval budget, and that covers most internal RAG systems: a 5,000-page wiki is about 50,000 chunks. Above about a million vectors, or with many queries a second on CPU, the linear cost and the memory start to bite: that is the point to batch, move to a GPU, or switch to an approximate index (Chapters 7 and 8), and to measure their recall against exact results.

Use case: faiss on GPUs

Facebook AI Research released faiss in 2017, and its accompanying paper by Jeff Johnson, Matthijs Douze and Hervé Jégou, "Billion-scale similarity search with GPUs", made the case this chapter's numbers make on a small scale: brute-force and near-brute-force search is a dense linear-algebra problem, and GPUs are built for exactly that. They implemented k-selection on the GPU efficiently enough to run near the hardware's memory-bandwidth limit, and reported building a k-nearest-neighbour graph over a billion vectors in under half a day on four GPUs. faiss kept both exact (flat) and approximate indexes behind one interface, so systems could start exact and switch when they had to, and it remains the library under many vector databases today.

⚠️
Common mistakes
  • Reaching for an approximate index or a vector database for 20,000 chunks.
  • Looping over vectors in Python instead of one matrix product.
  • Sorting all N scores to take the top 10.
  • One query at a time in batch jobs such as evaluation.
  • Forgetting to normalise, so inner product is not cosine.
  • Not measuring recall after switching to an approximate index.

Interview drill

Explain it simply: When would you use exact vector search instead of an approximate index?

How a strong answer sounds
Whenever it is fast enough, which is more often than people expect. Exact search computes the similarity with every vector in one matrix product and takes the top k, so it always returns the true nearest neighbours, needs no tuning and no build time. Its cost grows linearly with the number of vectors: on a CPU, a few hundred thousand 384-dimension vectors still answer in tens of milliseconds, and a GPU or batching goes further. I would switch to an approximate index around millions of vectors or when latency or memory budgets are exceeded, and use exact search as the reference to measure the approximate index's recall.

Deeper: You need to evaluate retrieval for 50,000 questions against 2 million chunks every night. How do you make it fast?

How a strong answer sounds
Batch the queries: compute Q @ Xᵀ in blocks of a few thousand queries and a slice of X at a time, so each pass over the vectors serves many queries, and take top-k per row with a partial selection. On a GPU in fp16, 2 million 384-dimension vectors fit in about 1.5 GB, and batched search measured well under a millisecond per query at a million vectors, so 50,000 queries take seconds to minutes. Use exact search here precisely because evaluation needs the true neighbours. Store the results so later runs only recompute what changed.

🧠 Key takeaways

  • Exact search is one matrix product plus a top-k selection, and is always correct.
  • Cost and memory grow linearly with N: about 0.06 ms per thousand vectors per CPU query here.
  • Batching turns many matrix-vector products into one matrix-matrix product.
  • A GPU in fp16 searched a million vectors in a few milliseconds.
  • Use exact until it is measurably too slow, then measure ANN recall against it.
