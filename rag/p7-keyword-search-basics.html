Keyword Search Basics

Before embeddings, search engines found documents by the words in them, and the method still matters: it is fast, it needs no model, it explains itself, and it finds exact strings, error codes, product numbers and names, that embeddings often blur. Most production RAG systems use it alongside vector search (Chapter 12). This chapter builds it from the ground up: the inverted index, tokenising, term frequency and TF-IDF.

The lab builds a real inverted index over the 4,230 Atlas sections from P4 three ways and ranks results four ways, then measures each combination on the same 1,922 glossary queries: how often the right chapter is in the top five, how many queries find nothing, and how much work each query does.

Inverted indexes

Scanning every document for every query is linear in the size of the corpus. An inverted index turns it round: for every term, store the list of documents that contain it (a postings list), with how many times it appears. A query then reads only the postings of its own terms. Here, the term "hnsw" appears in 9 sections and "backpressure" in 19, so a query for them touches a few dozen entries instead of 4,230 documents; "the" appears in 4,226, which is why common words are expensive and nearly useless for ranking. Real engines (Lucene, which powers Elasticsearch and OpenSearch; PostgreSQL full-text search; Tantivy) compress postings, store positions for phrase queries, and update in segments, but the idea is this dictionary.

from collections import Counter, defaultdict
index: dict[str, dict[int, int]] = defaultdict(dict)     # term -> {doc id: term frequency}
for doc_id, text in enumerate(texts):
    for term, tf in Counter(tokenise(text)).items():
        index[term][doc_id] = tf

Tokenising for search

The tokeniser decides what a "word" is, and it must be the same for documents and queries. Splitting on whitespace keeps punctuation and case, so "Cache," and "cache" become different terms: this corpus had 97,012 distinct whitespace tokens against 22,433 lowercased words, and 72 queries found nothing at all. Lowercasing and splitting on non-alphanumeric characters fixes that, at the cost of exactness for things like "C++" or "Write-ahead" (split into "write" and "ahead"). Removing stop words ("the", "and", "of") shrinks the index; stemming ("caching" → "cach") and lemmatising merge word forms. Each choice trades exactness for recall, so measure it.

Term frequency and TF-IDF

Once candidate documents are found, they must be ranked. Term frequency scores a document by how often it contains the query terms, which lets a common word like "key" swamp a distinctive one like "idempotency". Inverse document frequency fixes that: a term's weight is the log of how rare it is across the corpus, so "idempotency" (in 118 sections) counts far more than "data" (in 1,610). TF-IDF multiplies the two, usually with a damped term frequency (1 + log tf) so that the tenth repetition adds less than the first. Chapter 11's BM25 refines it further.

import math
def tfidf(query: str, N: int) -> dict[int, float]:
    scores = defaultdict(float)
    for term in dict.fromkeys(tokenise(query)):
        postings = index.get(term, {})
        idf = math.log(N / (1 + len(postings))) + 1
        for doc_id, tf in postings.items():
            scores[doc_id] += (1 + math.log(tf)) * idf
    return scores

Exact matches embeddings miss

Keyword search shines where meaning is less important than the exact string: error codes ("error 809"), identifiers and part numbers, names, rare technical terms, and anything newer than the embedding model. An embedding model may place "error 809" close to other VPN errors; keyword search returns the one page that contains it. It fails on synonyms and paraphrase ("car" versus "automobile"), where embeddings help. That complementarity is why hybrid search (Chapter 12) usually beats either alone.

Use case: Lucene, under most search boxes

Doug Cutting started Lucene in 1999 as a Java library for full-text search, and it became an Apache project in 2001. Its core is the structure in this chapter, an inverted index of terms to postings, built in immutable segments that are periodically merged, with analysers that tokenise, lowercase, remove stop words and stem. Solr (2004) and Elasticsearch (2010) built servers around it, and OpenSearch forked from Elasticsearch in 2021, so Lucene sits underneath a large share of the world's site search, log search and e-commerce search. Lucene's default ranking moved from a TF-IDF formula to BM25 in version 6 (2016). Recent versions also store dense vectors with an HNSW index, which is how many teams run the hybrid keyword-plus-vector retrieval this course builds towards, in one engine.

⚠️
Common mistakes
  • Different tokenisers for indexing and querying.
  • Splitting on whitespace and keeping punctuation and case.
  • Ranking by raw term frequency, so common words dominate.
  • Using Boolean AND as a ranking.
  • Dropping keyword search entirely once embeddings arrive, losing exact matches.
  • Tokenising away identifiers such as "C++", "e5-small" or "ERR_809" without testing them.

Interview drill

Explain it simply: What is an inverted index and why is it fast?

How a strong answer sounds
It is a map from each term to the list of documents that contain it, often with counts and positions. Building it costs one pass over the corpus; afterwards a query reads only the postings lists of its own terms instead of scanning every document, so a query for rare terms touches a handful of entries even in a huge corpus. Ranking then scores just those candidate documents, typically with TF-IDF or BM25, which weight terms by how often they appear in the document and how rare they are in the corpus.

Deeper: Your RAG system uses only embeddings, and users complain that searching for an error code returns the wrong pages. What do you do?

How a strong answer sounds
Embeddings capture meaning, so an exact identifier like an error code is close to other errors rather than matched exactly. I would add keyword retrieval with a tokeniser that keeps codes intact, check it on a set of identifier queries, and combine it with vector results using rank fusion, so exact matches surface while paraphrased questions still work. I would also consider routing queries that look like identifiers to keyword search first, and measure recall on both kinds of query before and after.

🧠 Key takeaways

  • An inverted index maps terms to postings, so queries touch only their own terms.
  • Tokenise identically for documents and queries; lowercasing and word splitting matter most.
  • IDF weights rare terms up; TF-IDF beat raw term frequency by a wide margin.
  • Boolean AND filters; it does not rank.
  • Keyword search finds exact strings embeddings blur: keep it, and combine the two.
