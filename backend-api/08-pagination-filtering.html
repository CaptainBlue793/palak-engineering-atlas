Pagination, Filtering & Sorting

No list endpoint should return everything. A table that holds 200 rows at launch holds two million a few years later, and an endpoint that returned all of them goes from fast to slow to fatal without a line of code changing. So list endpoints return pages, let clients filter and sort, and the design of those three features decides whether deep pages stay fast and whether a client paging through live data sees every item exactly once.

This chapter compares the two ways to paginate, offset and cursor (also called keyset), on a table of 1,000,000 orders, and shows what happens to each when new orders arrive while a client is paging.

  • Implement offset pagination, and know where it breaks
  • Implement cursor (keyset) pagination with an opaque cursor
  • Make ordering stable with a unique tie-breaker
  • Accept filters and sort fields safely, with allowlists and limits
  • Decide whether a list needs a total count, and what it costs

Offset pagination

The familiar version: GET /orders?limit=50&offset=100, implemented as ORDER BY ... LIMIT 50 OFFSET 100. It is simple, lets a client jump to page 37, and works well for small tables and shallow pages. It has two problems. The database still has to walk past every skipped row, so page 10,000 costs 10,000 pages' worth of work. And the window is defined by position, so if rows are inserted or deleted ahead of it between requests, items shift: a client sees some twice and misses others.

Cursor (keyset) pagination

Instead of "skip N rows", the client says "give me the rows after this one". The server returns a cursor encoding the last row's sort key, and the next request continues from there: WHERE (created_at, id) < (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 50. With an index in that order, every page is a short index range scan, however deep. Encode the cursor as an opaque string, for example base64 of the key values, so clients do not build or depend on its contents and you can change it later:

import base64, json
from fastapi import Query

def encode(row) -> str:
    return base64.urlsafe_b64encode(json.dumps([row.created_at, row.id]).encode()).decode()

@app.get("/orders")
def list_orders(limit: int = Query(50, ge=1, le=200), cursor: str | None = None, db=Depends(get_db)):
    sql = "SELECT id, created_at, status, total_cents FROM orders"
    params = {"limit": limit + 1}                     # one extra row tells us if there is a next page
    if cursor:
        created_at, last_id = json.loads(base64.urlsafe_b64decode(cursor))
        sql += " WHERE (created_at, id) < (:c, :i)"
        params |= {"c": created_at, "i": last_id}
    rows = db.execute(text(sql + " ORDER BY created_at DESC, id DESC LIMIT :limit"), params).all()
    page, more = rows[:limit], len(rows) > limit
    return {"items": [dict(r._mapping) for r in page], "next_cursor": encode(page[-1]) if more else None}

The trade-offs: no jumping to page 37, only next (and, with a little more work, previous), and the sort must be on indexed columns. For feeds, timelines, exports and syncing, that is exactly right, which is why large public APIs such as Stripe's, GitHub's GraphQL API and Slack's use cursors.

Things to try.

  • Read the bars: page 1 costs the same either way. By page 19,001, offset takes about 310 times as long as cursor, which stays flat, because offset walks past 950,000 index entries first.
  • offset with 3 new orders: page 3 starts with three orders the client already saw on page 2. Every item shifts down three places; a client syncing records would process them twice.
  • cursor with 3 new orders: page 3 continues exactly after the last order seen. The new orders are newer than the cursor, so they appear at the top on the next fresh read, not in the middle of this one.

Stable ordering

Pagination is only correct if the order is total: no two rows may tie. Sorting by created_at alone looks fine until two orders share a timestamp, and in the lab's table several share every second. With ties, the database may return tied rows in a different order on each query, so one can straddle a page boundary and appear twice or never. Always add a unique column as the last sort key, usually the primary key: ORDER BY created_at DESC, id DESC, with an index in the same order. The same applies to any client-chosen sort field.

Filtering safely

Filters are query parameters with types and limits: ?status=paid&created_after=2026-01-01T00:00:00Z&customer_id=7. Validate them like any input (enums for status, real datetimes, bounded lists), and pass them as SQL parameters. Sort fields and directions cannot be parameters, so map them through an allowlist: SORTS = {"created_at": Order.created_at, "total": Order.total_cents}, with a 400 for anything else. Cap limit (the code above uses 200), and decide which filters need indexes: an unindexed filter on a big table is a full scan on every request, and an API that allows arbitrary combinations of filters and sorts is promising more indexes than any table can have.

Totals and their cost

Clients often ask for "total": 1832 to show "page 3 of 37". That is a COUNT(*) over the whole filtered set on every request, separate from fetching the page. Measured on the million-row table: 50 ms to count everything and 236 ms to count with an unindexed filter, against well under a millisecond for a cursor page. Options: drop the total and return has_more (as the code above does with its extra row); return an estimate (PostgreSQL's planner statistics, or "more than 1,000"); cache counts; or make the total optional, ?include_total=true, so only the screens that need it pay.

Use case: GitHub caps deep pages

GitHub's REST API long paginated with page numbers in Link headers, and over time it has put limits on how far they go. Its search API returns at most the first 1,000 results for any query, however many match, and several busy list endpoints, such as listing repository events and certain timelines, document their own caps or have moved to cursor-based parameters (before and after). Its GraphQL API, launched in 2016, used cursors from the start, with first, after and a pageInfo { hasNextPage endCursor } object, and a maximum of 100 items per page. The pattern is common across large APIs: deep offset pages are expensive to serve and rarely what a person wants, so services cap them, steer clients to filters and cursors, and offer exports or event streams for anyone who really needs every record.

⚠️
Common mistakes
  • No limit, or no maximum limit, on a list endpoint.
  • Sorting without a unique tie-breaker, so items repeat or vanish between pages.
  • Offset pagination for syncing or exporting live data.
  • Sort and filter fields passed into SQL without an allowlist.
  • A COUNT(*) on every request for a total nobody reads.
  • Transparent cursors that clients start constructing themselves.
  • Filters with no index behind them on large tables.

Interview drill

Explain it simply: What is the difference between offset and cursor pagination?

How a strong answer sounds
Offset pagination says "skip this many rows, then give me the next 50". It is simple and lets you jump to any page, but the database still walks past all the skipped rows, so deep pages get slow, and if rows are inserted or deleted between requests, items shift, so you see duplicates or miss some. Cursor pagination says "give me the 50 rows after this one", using the last row's sort key, such as its timestamp and ID, so the database jumps straight there with an index. Every page costs the same, and changes elsewhere in the list do not shift your position. The cost is that you can only go to the next page, and you can only sort by indexed keys with a unique tie-breaker.

Deeper: Design the list endpoint for a partner API that lets partners sync all their orders, which keep changing.

How a strong answer sounds
Partners need every change exactly once, including updates to old orders, so I would paginate by modification, not creation: sort by (updated_at, id) ascending, with an index in that order, and return an opaque cursor. A partner starts from the beginning or from a timestamp and follows next_cursor until has_more is false, then stores the last cursor and resumes from it next time. Updated rows move to the end, so they are picked up again on the next sync, which is what syncing wants; deletions need tombstones or a separate deletions feed, since a deleted row no longer appears. I would cap the page size, reject unknown filters, skip totals, and document that updates can arrive slightly out of order around the current moment, so partners should overlap their resume point by a few seconds or I should only return rows older than a small safety window. For partners who need changes promptly, webhooks complement the feed (Chapter 21).

🧠 Key takeaways

  • Every list endpoint is paginated, with a default and a maximum limit.
  • Offset is simple but slows with depth and shifts when data changes.
  • Cursor (keyset) pagination is constant-time with an index and sees each row once.
  • Order by a unique tie-breaker; allowlist sort fields; validate and index filters.
  • Totals cost a full count; prefer has_more, estimates or opt-in totals.
