Testing APIs

A service's tests exist to answer one question before every deploy: would this change break anything a client relies on? For an API, what clients rely on is the behaviour of HTTP requests against a real database: status codes, response shapes, which rows come back, what happens on the second page. Tests that check something else, such as whether one function called another with the right arguments, can all pass while every one of those behaviours is broken.

This chapter is about choosing what to test at which level, testing endpoints against a real database, contract and property tests, and keeping the suite trustworthy by removing flakiness. The lab plants three realistic bugs in a small service and runs three real pytest suites against each, then measures a flaky test.

  • Balance unit, endpoint, integration, contract and end-to-end tests
  • Test endpoints through HTTP with TestClient and dependency overrides
  • Use a real database in tests, isolated per test
  • Add contract and property-based tests where examples miss cases
  • Find and fix flaky tests

The test pyramid for services

The classic pyramid says: many fast unit tests, fewer integration tests, very few end-to-end tests. For an API service, the middle deserves more weight than the picture suggests, because most bugs live at the joins, in SQL, serialisation, validation, routing and configuration, which unit tests with mocks skip by design. A practical mix: unit tests for genuinely complex logic (pricing rules, state machines); endpoint tests through HTTP against a real database for every endpoint, as the bulk of the suite; contract tests that check the service against its OpenAPI document and its consumers' expectations; and a few end-to-end tests of critical journeys against a deployed environment.

Testing endpoints

FastAPI's TestClient sends real HTTP requests through the whole application, middleware, routing, validation, dependencies and response models, without a network. Assert on what a client sees: status, body, headers, and on what the database holds afterwards. Swap only the edges with app.dependency_overrides: the database session for a test one, external services for fakes (Prerequisite 7).

import sqlite3

import pytest
from fastapi.testclient import TestClient

from shop import app, get_db

SCHEMA = "CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INTEGER, status TEXT, total_cents INTEGER)"


@pytest.fixture
def db():
    con = sqlite3.connect(":memory:", check_same_thread=False)   # a real database, fresh for every test
    con.execute(SCHEMA)
    yield con
    con.close()


@pytest.fixture
def client(db):
    def override():
        yield db
    app.dependency_overrides[get_db] = override
    yield TestClient(app)
    app.dependency_overrides.clear()


def add_orders(db, customer_id, statuses):
    for s in statuses:
        db.execute("INSERT INTO orders (customer_id, status, total_cents) VALUES (?, ?, 1000)", (customer_id, s))
    db.commit()


# test_api_db.py
from conftest import add_orders


def test_lists_only_this_customers_orders(client, db):
    add_orders(db, 7, ["paid", "shipped"])
    add_orders(db, 8, ["paid"])
    body = client.get("/customers/7/orders").json()
    assert [o["status"] for o in body["items"]] == ["paid", "shipped"]
    assert body["next_offset"] is None


def test_status_filter(client, db):
    add_orders(db, 7, ["paid", "shipped", "paid"])
    body = client.get("/customers/7/orders?status=paid").json()
    assert [o["status"] for o in body["items"]] == ["paid", "paid"]

A real database in tests

Mocks of a repository return whatever the test author believed the SQL would return; they cannot catch a wrong WHERE, a missing index, a constraint or a migration that does not apply. Use a real database: give each test a fresh one, or wrap each test in a transaction rolled back at the end, and build data with small factory functions. Use the same engine as production where it matters: SQLite is fine for the lab, but PostgreSQL behaves differently in types, locking, JSON and error codes, so integration suites usually start a real PostgreSQL in a container (Testcontainers does this from pytest) and run the migrations first, which also tests the migrations.

  • field dropped from response: unit tests pass again; they never looked at the full response. Endpoint tests fail immediately.

Contract and property tests

Contract tests check that the running service matches its published contract. Schemathesis reads the OpenAPI document (Chapter 14) and generates requests for every operation, checking that responses match the declared schemas and status codes and that the server never returns 500. Consumer-driven contract tests, with tools such as Pact, record what each client actually uses and replay it against the provider, so a provider change that breaks a real consumer fails in the provider's CI. Property-based tests, with Hypothesis, state a rule that must hold for all inputs, "paging returns every order exactly once", and generate inputs to break it, shrinking any failure to a minimal example: measured here, with 2 orders and a page size of 1, paging returned only order 2. They are ideal for pagination, serialisation round trips, parsers and anything with edge cases you would not think to write down.

Flaky tests

A flaky test passes and fails without code changes. A few are enough to teach a team to ignore red builds, which defeats the suite. Common causes and fixes: fixed sleeps waiting for asynchronous work (wait for the condition, with a timeout); the real clock (inject time, or freeze it); shared state between tests, such as database rows or global overrides (a fresh database per test, clear overrides in fixtures); test order dependencies (run in random order to find them); real network calls (fakes); and unseeded randomness (seed it, and print the seed). Track flaky tests, quarantine them so they do not block others, and fix them quickly.

Use case: flaky tests at Google

In 2016 John Micco, who worked on Google's continuous integration systems, wrote on the Google Testing Blog about flaky tests at Google's scale. He reported that about 1.5% of all test runs produced a flaky result, a test that both passed and failed on the same code, and that almost 16% of their tests showed some level of flakiness. With millions of test runs a day, even that small rate produced a steady stream of false failures, and engineers responded by rerunning failed tests until they passed, which also hides real, intermittent bugs. Google built tooling around it: rerunning failures automatically to classify them as flaky, reporting flakiness per test, and quarantining the worst. The lab's sleep-based test shows the commonest root cause in miniature: a test that guesses how long asynchronous work will take. The cure is the same at every scale: make tests wait for conditions rather than time, isolate their state, and treat a flaky test as a bug to fix, not a nuisance to rerun.

⚠️
Common mistakes
  • Mocking the database layer in tests meant to check API behaviour.
  • Asserting that functions were called instead of what the client receives.
  • Tests sharing a database and depending on each other's rows or order.
  • A different database engine in tests than in production, for behaviour that differs.
  • Fixed sleeps waiting for background work.
  • Rerunning flaky tests until green instead of fixing them.
  • Only examples smaller than a page, or other boundaries never crossed.

Interview drill

Explain it simply: Should API tests mock the database?

How a strong answer sounds
Mostly not. A mock returns whatever the test author assumed the query would return, so it cannot catch a wrong filter, a type mismatch, a constraint violation or a broken migration, which is where many API bugs live. In a small experiment, an inverted SQL filter passed every mocked unit test and failed the first endpoint test against a real database. I would test endpoints through HTTP with FastAPI's TestClient against a real database, fresh or rolled back per test, ideally the same engine as production running in a container, and keep mocks for things outside the service: payment providers, email, other teams' APIs. Pure logic with many cases still gets fast unit tests.

Deeper: Your service's test suite takes 25 minutes and fails randomly about once a day. What do you do?

How a strong answer sounds
Treat both as bugs. For flakiness: rerun failures automatically in CI only to classify them, record which tests flake, quarantine those so they stop blocking merges, and fix them, starting with sleeps and timing, shared database state, test order (run with random ordering to expose dependencies), real network calls and unseeded randomness. For speed: profile the suite with pytest's durations report; run in parallel with pytest-xdist, which first requires isolated data per worker; replace per-test database creation with a transaction rolled back after each test on a database created once per worker; move slow end-to-end checks to a smaller suite that runs after merge; and delete tests that duplicate each other. Aim for a fast, trustworthy core suite on every change, with a broader one before release.

🧠 Key takeaways

  • For APIs, endpoint tests through HTTP against a real database carry most of the value.
  • Mocks of your own data layer hide SQL and serialisation bugs; mock only external edges.
  • Isolate each test's data; prefer the production database engine for integration tests.
  • Property-based and contract tests find the cases examples never cross.
  • Flaky tests are bugs: wait for conditions, isolate state, seed randomness.
