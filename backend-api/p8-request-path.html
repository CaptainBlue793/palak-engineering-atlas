How a Request Reaches Your Code

When someone calls GET https://api.example.com/items, your handler is the last stop of a long trip. The client looks up an address, opens a connection, negotiates encryption, and sends the request to a load balancer, which passes it to a reverse proxy, which passes it to the process running your Python. Inside that process, an ASGI server parses the bytes and hands them to FastAPI, which runs middleware, finds the route, resolves dependencies, validates the input, calls your function, and turns the result back into bytes.

Each layer adds time, and each is a place where things go wrong: a timeout set too low, a header the proxy dropped, a client address that is really the load balancer's. This page walks the path, and the lab times every stage on a real FastAPI service running behind a real (if small) proxy, with and without TLS.

DNS and TCP, briefly

DNS turns api.example.com into an IP address. Answers are cached, by the operating system and by resolvers along the way, for as long as the record's TTL allows, so most lookups cost nothing, but a cold lookup costs at least one round trip to a resolver. Then TCP opens a connection with a three-way handshake, which costs one round trip before any data flows. On a laptop that is a fraction of a millisecond; between continents it is 100 ms or more.

Names can surprise you even locally. Measured on Windows, a plain curl http://localhost:8041/ took 205 ms to connect, while 127.0.0.1 took under a millisecond: localhost resolved to the IPv6 address ::1 first, nothing was listening there because uvicorn binds to IPv4 by default, and curl waited before falling back. A slow first request with a fast second is often a resolution or connection problem, not your code.

TLS termination

HTTPS wraps HTTP in TLS, which needs a handshake on each new connection: the client and server agree on keys, and the server proves its identity with its certificate. TLS 1.3 needs one extra round trip; TLS 1.2 needed two. The handshake also costs CPU for the key exchange and signature: measured on this laptop, over loopback with no network delay at all, it added about 11 ms per new connection.

In most deployments, TLS is terminated at the edge: the load balancer or reverse proxy holds the certificate, decrypts the request and forwards plain HTTP, or a fresh internal TLS connection, to your service. Your code then sees http, not https, so the proxy reports the original scheme and client in headers (below). Terminating at the edge centralises certificates and renewal, and it means the proxy sees every request in plaintext, which is why it is one of the most sensitive components you run.

Load balancers and reverse proxies

A load balancer spreads requests across several copies of your service and stops sending to copies that fail health checks. A reverse proxy, such as nginx, Envoy, Caddy or Traefik, often in the same role, sits in front of a service and adds: TLS termination, routing by host and path, compression, request size and rate limits, buffering of slow clients so your workers are not tied up by them, and timeouts. Cloud load balancers, API gateways (Chapter 35) and Kubernetes ingress controllers are all variations on the same idea.

Because the proxy opens its own connection to your service, the TCP peer your service sees is the proxy, not the user. Proxies pass the original details in headers: X-Forwarded-For (the client's IP), X-Forwarded-Proto (http or https) and X-Forwarded-Host, or the standard Forwarded header. Only trust these from your own proxy, since any client can send them: uvicorn reads them only when started with --proxy-headers and only from the addresses in --forwarded-allow-ips. Get this wrong and rate limits, audit logs and IP allowlists all act on an address the attacker chose.

# the service behind a proxy at 10.0.0.5: trust its forwarded headers, nobody else's
uvicorn app:app --host 0.0.0.0 --port 8000 --proxy-headers --forwarded-allow-ips 10.0.0.5

ASGI servers and workers

FastAPI does not read sockets itself. An ASGI server, usually uvicorn (Hypercorn and Granian are alternatives), accepts connections, parses HTTP, and calls your application as an ASGI callable: await app(scope, receive, send), where scope describes the request (method, path, headers, client), receive yields the body and send writes the response. That interface is all the lab's timing wrapper needed: it is a few lines of ASGI that stamps the time on entry and adds a header when the response starts.

One uvicorn process runs one event loop on one CPU core. To use more cores, run several worker processes: uvicorn app:app --workers 4, or Gunicorn managing uvicorn workers, or, common in containers, one process per container and more containers. Workers share nothing in memory, so anything that must be shared, such as sessions, caches and rate-limit counters, belongs in a database or Redis (Chapter 18).

The framework stack

Inside the application, a request passes through middleware (outermost first: added last runs first), then routing, which matches the path and method, then dependency resolution and request validation, then your handler, then response-model validation and JSON serialisation, and back out through the middleware. The lab's service reports the first four stages to the client in a Server-Timing header, which browsers show in the network tab's timing view:

server-timing: routing;dur=0.378, deps;dur=0.392, handler;dur=0.003, serialise;dur=0.440

Things to try.

  • Start with the defaults, a new HTTPS connection: the TLS handshake is most of the time, and FastAPI's part is about a millisecond. Switch to a reused connection: the handshake disappears entirely.
  • Set the distance to another continent, new connection: three round trips before the first byte. Reuse the connection and it is one. This is why clients should keep connections open and why APIs put servers close to users.
  • Add the proxy. It adds a couple of milliseconds here, because it is written in Python; the larger point is the hop itself, with its own connection pool and timeouts.
  • Ask for 1,000 items: serialisation grows, and at a distance, the 70 KB download needs extra round trips while TCP's window grows. Pagination (Chapter 8) and compression both help.

Use case: Cloudbleed, 2017

In February 2017, Tavis Ormandy of Google's Project Zero noticed corrupted web pages coming through Cloudflare, which acts as a reverse proxy for millions of websites: they contained fragments of other people's requests, including cookies, authentication tokens and private messages. The cause was a bug in an HTML parser that Cloudflare's edge servers ran on some responses to rewrite them on the fly: in certain malformed pages, a pointer check ran past the end of a buffer, and the proxy copied whatever was next in its memory into the response. Because Cloudflare terminated TLS for all of those sites, that memory held other customers' traffic in plaintext. At its peak about 1 in every 3.3 million requests leaked, and some leaked pages had been cached by search engines, which Cloudflare then worked with to purge. The fix was quick; the lesson lasts. The proxy layer is shared infrastructure that sees everything, so its bugs are everyone's bugs, and every feature you turn on at that layer runs on every request.

⚠️
Common mistakes
  • Trusting X-Forwarded-For from anyone, so clients choose their own IP address.
  • Timeouts that do not line up: a proxy giving up at 30 seconds while the app keeps working for 60, or retrying a request the app already processed.
  • Opening a new connection per request to another service, paying DNS, TCP and TLS every time; reuse one client (httpx.AsyncClient) for the process.
  • Generating absolute URLs from the scheme the app sees, producing http:// links behind a TLS-terminating proxy.
  • Running one worker on a many-core machine, or keeping per-process state that other workers cannot see.
  • Health checks that only prove the process is alive, not that it can reach its database.

Interview drill

Explain it simply: What happens between a user's browser sending a request and your FastAPI handler running?

How a strong answer sounds
The browser resolves the domain name with DNS, opens a TCP connection and does a TLS handshake, unless it can reuse an existing connection. The request reaches a load balancer, which picks a healthy instance of the service, usually through a reverse proxy that terminates TLS, applies limits and routing, and adds forwarded headers with the client's real address and scheme. The proxy forwards the request to uvicorn, the ASGI server, which parses the HTTP and calls the FastAPI app. FastAPI runs the middleware, matches the route, resolves dependencies and validates the input against the models, and only then calls the handler. The return value is validated against the response model, serialised to JSON, and travels back the same way.

Deeper: Your service's p99 latency is 400 ms, but your traces show the handler takes 20 ms. Where would you look?

How a strong answer sounds
The other 380 ms is outside the handler, so I would measure each layer separately. First, compare the latency the load balancer or proxy records with what the app records: a big gap means queueing before the app, such as all workers busy, a blocked event loop, or the proxy's own connection limits. Within the app, middleware, dependency resolution, validation and serialisation of large responses all happen outside the handler; a Server-Timing header or tracing spans around those show it. On the client side, look at whether connections are reused: new TLS connections from distant clients cost several round trips each, and large responses need several more while TCP's window grows. Then fix the biggest piece: more workers or unblocking the loop for queueing, keep-alive and connection pooling for handshakes, pagination and compression for large bodies, and servers or a CDN closer to users for distance.

🧠 Key takeaways

  • A request passes DNS, TCP, TLS, a load balancer, a reverse proxy and an ASGI server before FastAPI sees it.
  • New connections cost round trips and CPU; reusing connections removes most of that.
  • TLS usually terminates at the edge; the proxy forwards the client's details in headers that you must only trust from it.
  • uvicorn calls your app through ASGI; scale across cores with worker processes that share nothing.
  • Inside FastAPI, middleware, routing, dependencies, validation and serialisation all run around your handler.

Your service runs behind a TLS-terminating proxy. What does request.url.scheme show without proxy-header handling?

The proxy reports the original scheme in X-Forwarded-Proto; uvicorn applies it with --proxy-headers from trusted addresses.

Why should a service only trust X-Forwarded-For from its own proxy?

Rate limits, logs and IP allowlists would otherwise use an address the attacker picked.

A client 90 ms away opens a new HTTPS connection (TLS 1.3) for each request. Roughly how many round trips before the first response byte?

About 270 ms of waiting before any server time. With a reused connection, only the request's round trip remains.

What does running uvicorn with --workers 4 do?

Processes share nothing in memory, so shared state goes in a database or Redis.

In the lab, which stage inside FastAPI grew most when the response went from 1 item to 1,000?

Each item is validated against the response model and turned into JSON; the handler only sliced a list.
