Structuring a Service

A new service fits in one file. A year later it has forty endpoints, three background jobs, an admin script and a second API, and the question is no longer whether the code works but whether anyone can change it safely. Structure is how a codebase answers "where does this rule live?" with one place, so that a business change is one edit, testable without starting a web server, and the same no matter which entry point, web request, job or script, triggers it.

This chapter covers the common layering of handlers, services and repositories, dependency injection, keeping domain logic in one place, a sensible project layout, and when, and when not, to split a service in two. The lab applies the same business change to the same feature built two ways, and measures the consequences.

  • Separate handlers, services, domain logic and repositories
  • Use dependency injection to wire and replace components
  • Keep business rules in one pure, testable place
  • Lay out a FastAPI project that grows well
  • Decide when splitting into separate services pays off

Handlers, services, repositories

A widely used split has three or four layers, each with one job:

  • Handlers (the API layer) speak HTTP: parse and validate input with Pydantic, call a service, turn the result or a domain error into a response. No SQL, no business rules.
  • Services (application layer) carry out one use case: "place an order" loads what it needs, applies domain rules, saves the result, and defines the transaction boundary (Chapter 17).
  • Domain code holds the business rules as plain Python: prices, discounts, state transitions, invariants. It imports neither FastAPI nor SQLAlchemy.
  • Repositories (data access) hide storage behind methods named for what the domain needs: customer_tier(id), save_order(...).

The direction of dependencies matters more than the names: outer layers depend on inner ones, never the reverse, so the domain can be tested and reused without the web framework or the database. This is the core of what are variously called layered, hexagonal ("ports and adapters") and clean architectures; for most services the plain version below is enough.

# ---------- domain.py: no FastAPI, no SQL ----------
from dataclasses import dataclass

VIP_DISCOUNT_PCT = 10


@dataclass(frozen=True)
class Line:
    sku: str
    quantity: int
    unit_cents: int


def price_order(lines: list[Line], tier: str, promo: str | None) -> int:
    subtotal = sum(l.quantity * l.unit_cents for l in lines)
    pct = VIP_DISCOUNT_PCT if tier == "vip" else 0
    if promo == "SPRING5":
        pct += 5
    discount = subtotal * pct // 100
    shipping = 0 if subtotal - discount >= 5000 else 399
    return subtotal - discount + shipping


# ---------- service.py: uses the domain, talks to storage through a repository ----------
class OrderService:
    def __init__(self, repo):
        self.repo = repo

    def place(self, customer_id: int, lines: list[Line], promo: str | None) -> int:
        tier = self.repo.customer_tier(customer_id)
        total = price_order(lines, tier, promo)
        self.repo.save_order(customer_id, total)
        return total

    def reprice_all(self, baskets):
        return [price_order(lines, self.repo.customer_tier(cid), promo) for cid, lines, promo in baskets]


# ---------- api.py: HTTP only ----------
from fastapi import Depends, FastAPI
from pydantic import BaseModel


class LineIn(BaseModel):
    sku: str
    quantity: int
    unit_cents: int


class OrderIn(BaseModel):
    customer_id: int
    lines: list[LineIn]
    promo: str | None = None

# ... a repository class implementing customer_tier() and save_order() ...
app = FastAPI()


def get_service():
    return OrderService(REPO)


@app.post("/orders")
def place_order(body: OrderIn, svc: OrderService = Depends(get_service)):
    total = svc.place(body.customer_id, [Line(**l.model_dump()) for l in body.lines], body.promo)
    return {"total_cents": total}

Dependency injection

Components should receive their collaborators rather than create them: OrderService(repo) rather than a service that opens its own database connection. FastAPI's Depends is a dependency-injection system for the request path: a handler declares it needs an OrderService, a provider function builds one with a session from another provider, and tests override any provider (app.dependency_overrides). For jobs and scripts, construct the same objects with the same functions, so every entry point wires the service identically. Keep construction in one module, the "composition root", rather than scattered through the code.

Domain logic in one place

The most expensive structural mistake is not a missing layer but a duplicated rule: the price calculated in the checkout handler, again in the nightly invoicing job, and again, slightly differently, in the admin tool. Each copy is correct the day it is written; the first business change makes them disagree. Put each rule in exactly one function that every entry point calls, and keep it pure, a function of its inputs, so it can be tested exhaustively in microseconds.

Simulator: one change, two structures

The same feature, pricing an order with a VIP discount, a promotion and a free-shipping threshold, was built two ways. In fat handlers, the rules live in the POST /orders handler, and the nightly repricing job has its own copy. In layered, both call one price_order function through a service. Then the business asks for one change, "VIP discount rises from 10% to 15%", made where a developer looking for pricing would find it. 200 real baskets were priced through the HTTP endpoint and by the nightly job, before and after.

Project layout

Organise by feature (a package per area of the business) rather than by technical type, once there is more than a handful of endpoints; it keeps everything about orders together, and makes boundaries visible:

shop/
  main.py              # create_app(): routers, middleware, exception handlers
  settings.py          # the validated settings object (Prerequisite 6)
  db.py                # engine, session provider
  orders/
    api.py             # FastAPI router: handlers only
    schemas.py         # Pydantic request and response models
    service.py         # use cases: place, cancel, reprice
    domain.py          # pure rules: price_order, can_cancel
    repository.py      # SQLAlchemy queries
    models.py          # ORM tables
  payments/ ...
  jobs/                # entry points that call the same services
tests/
  orders/test_domain.py  test_api.py

When to split a service

Splitting one service into several, microservices, buys independent deployment and scaling, separate ownership by different teams, and fault isolation. It costs network calls where there were function calls, so latency, partial failure and retries (Chapter 29); data that can no longer be joined or updated in one transaction (Chapter 30); more infrastructure, deployment and observability; and harder debugging. Split when there is a real reason: a part with very different scaling or reliability needs, a team boundary that the codebase keeps colliding on, or a component that must be deployed independently. Until then, a well-structured single service, a "modular monolith" with clear package boundaries and no reaching into another module's tables, gives most of the benefits and keeps the option to split later.

Use case: Prime Video moves back to a monolith, 2023

In March 2023 Amazon Prime Video's engineering team published a post about a tool that monitors the quality of thousands of live video streams, checking for frozen frames, audio problems and block corruption. It had originally been built as distributed components, using AWS Step Functions to orchestrate each step and passing video frames between services through Amazon S3. At scale, the orchestration transitions and the data passed between components became the dominant costs, and the system hit scaling limits. The team rebuilt it as a single process, with the same components as modules communicating in memory, still scaled out by running more copies, and reported cutting the infrastructure cost by more than 90%. The post was widely discussed as an argument against microservices; its real lesson is narrower and matches this chapter: the boundaries between components should follow how data and work actually flow, and network boundaries are worth their cost only where independence is worth more than that cost.

⚠️
Common mistakes
  • Business rules in handlers, then copied into jobs and scripts.
  • Domain code importing FastAPI or the ORM, so it cannot be tested or reused alone.
  • Services that create their own connections and clients instead of receiving them.
  • Layers that only forward calls, adding files without separating anything.
  • One module reaching into another's tables directly.
  • Splitting into microservices to fix a messy codebase, which distributes the mess.

Interview drill

Explain it simply: How would you structure a FastAPI service so it stays maintainable?

How a strong answer sounds
Thin handlers that only deal with HTTP: validate with Pydantic, call a service, map results and domain errors to responses. Services for each use case, which own the transaction and coordinate. Business rules in plain domain functions with no framework imports, each rule in exactly one place, so jobs, scripts and the API all call the same code. Repositories hiding the SQL. Wiring through dependency injection, FastAPI's Depends for requests and the same provider functions for jobs, so tests can swap the database or external clients. Code organised by feature package. The payoff is that a business change is one edit, testable in milliseconds; in an experiment, a duplicated pricing rule made the website and the nightly job disagree on 50 of 200 orders after one change.

Deeper: Your team wants to split a monolith into microservices. How do you decide, and how would you do it?

How a strong answer sounds
First ask what problem it solves: independent deploys for teams that block each other, very different scaling or reliability needs, or isolating a risky component. If the real problem is tangled code, fix the structure inside the monolith first: feature modules with clear interfaces, no shared tables, domain logic in one place. That is cheaper and makes any later split easy. If a split is justified, pick the boundary along a business capability with little data shared with the rest, and extract it gradually with the strangler pattern: route its traffic through an interface, build the new service behind it, move the data with a migration plan, replace synchronous joins with API calls or events from an outbox, and add timeouts, retries and tracing from the start. Measure latency and error rates before and after, and stop if the costs outweigh the gains.

🧠 Key takeaways

  • Handlers speak HTTP; services run use cases; domain code holds rules; repositories hide storage.
  • Every entry point calls the same service, so each rule lives in one place.
  • Pure domain functions are testable exhaustively in milliseconds.
  • Inject dependencies, wired in one place, so tests and jobs can reuse or replace them.
  • Prefer a modular monolith; split services only for a concrete reason, along business boundaries.
