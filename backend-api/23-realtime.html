Real-Time: WebSockets & Server-Sent Events

HTTP is a conversation the client starts: it asks, the server answers. But many features need the server to speak first: a delivery status that changes, a chat message, a price that moves, a long job that finishes. There are four ways to get server events to a client, from the simplest, asking repeatedly, to the most capable, a WebSocket held open both ways, and each trades latency against requests, connections and complexity.

This chapter covers polling, long polling, server-sent events and WebSockets, then the two problems that appear in production: getting an event to the right connection when there are many server processes, and the cost of holding many connections open. The lab delivers the same 20 events through each method from a real server and measures it.

Polling and long polling

Polling asks "anything new since event N?" every few seconds. It works with any client and any infrastructure, and it is the right first answer more often than people think. Its costs are that events wait, on average, half an interval, and most requests return nothing; shortening the interval cuts the wait and multiplies the requests. Long polling holds each request open on the server until something happens (or a timeout), then the client immediately asks again: near-instant delivery over plain HTTP, at the cost of one request per event and a held connection per client.

Server-sent events

Server-sent events (SSE) keep one HTTP response open and write events into it as they happen, in a simple text format, text/event-stream, with id:, event: and data: lines and a blank line between events. Browsers support it natively with EventSource, which also reconnects automatically after a drop and sends the last id it saw in a Last-Event-ID header, so the server can resume where it left off. SSE is one-way, server to client, which is all most features need, and it is ordinary HTTP, so it passes through proxies, works with HTTP/2 and uses existing authentication. Over HTTP/1.1 browsers allow only about six connections per site, so keep to one stream per page or serve over HTTP/2.

@app.get("/events/stream")
async def sse(after: int = 0):
    async def gen():
        last = after
        while True:
            for e in [e for e in EVENTS if e["seq"] > last]:
                last = e["seq"]
                yield "id: %d\nevent: shipment\ndata: %s\n\n" % (e["seq"], json.dumps(e))
            try:
                await asyncio.wait_for(NEW.wait(), timeout=15)
            except asyncio.TimeoutError:
                yield ": keep-alive\n\n"          # a comment line keeps proxies from closing an idle stream

WebSockets

A WebSocket starts as an HTTP request with Upgrade: websocket; after the server agrees (status 101), the connection becomes a two-way channel of messages, outside HTTP's request-response model. Use it when the client also sends a stream of messages: chat, collaborative editing, games, live trading interfaces. Because it leaves HTTP behind, you rebuild some things yourself: authenticate during the handshake (a cookie, or a short-lived ticket obtained from a normal API call; browsers cannot set custom headers on WebSockets), check the Origin header so other sites cannot open sockets with your users' cookies, define a message format and versioning, send heartbeats (ping/pong) so dead connections are noticed, and handle reconnection and missed messages in the client.

Fan-out with pub/sub

In production the service runs as many processes on many machines, and each holds its own connections. When an order ships, the event is created on whichever process handled that request, but the customer's WebSocket may be on another one. In-memory event lists, like the lab's, only work with one process (Chapter 1). Connect them with publish/subscribe: every process subscribes to a broker, such as Redis pub/sub or Redis Streams, NATS or Kafka, and forwards messages to its own connected clients; the code that creates an event publishes it once. Pub/sub in Redis is fire-and-forget, so pair it with a store that clients can read to catch up after a reconnect, which is what SSE's Last-Event-ID is for.

Connection limits

Long-lived connections are cheap per message and expensive per client. Measured on this service, 1,000 idle WebSocket connections added about 201 MB to the server process, about 206 KB each, and 1,000 idle SSE streams about 93 MB, about 95 KB each. A Python process can hold thousands, but not millions, and each connection also needs a file descriptor (raise the operating system's limit) and passes through load balancers with their own idle timeouts, so send a heartbeat every 15 to 30 seconds. Plan for reconnect storms: when a server restarts or a deploy rolls out, every client reconnects at once, so clients must back off with jitter, and deploys should drain connections gradually. Many teams terminate real-time connections in a dedicated gateway or a managed service, and keep the API itself request-response.

Use case: WhatsApp's two million connections per server, 2012

In January 2012 WhatsApp's engineers wrote a short blog post titled "1 million is so 2011", reporting that they had tuned a single server to hold more than two million concurrent TCP connections from phones. Their service was built in Erlang, whose lightweight processes cost a few hundred bytes to a few kilobytes each, on FreeBSD, with kernel and runtime settings adjusted for huge numbers of mostly idle connections. The figure is a useful yardstick for this chapter's measurement: at about 100 to 200 KB per connection in the lab's Python stack, the same server would hold a few tens of thousands. Neither number is wrong; they reflect different tools for different jobs. A product whose core is millions of persistent connections, chat, presence, live updates, often puts them in a component built for that, while ordinary API services keep request-response at their centre and delegate connections to something that holds them cheaply.

⚠️
Common mistakes
  • Reaching for WebSockets when SSE, or polling, would do.
  • In-memory event lists behind several processes.
  • WebSocket handshakes without authentication or Origin checks.
  • No heartbeats, so dead connections linger and proxies cut idle ones.
  • Clients that reconnect instantly, all together, after a restart.
  • No way to catch up on events missed during a disconnection.
  • Blocking calls in async connection handlers, freezing every connection on the worker (Prerequisite 2).

Interview drill

Explain it simply: When would you use server-sent events instead of WebSockets?

How a strong answer sounds
When only the server needs to push, which covers most features: notifications, order status, progress of a long job, live dashboards. SSE is plain HTTP, a response that stays open and carries events in a simple text format, so it works with existing authentication, proxies, HTTP/2 and load balancers, and the browser's EventSource reconnects automatically and tells the server the last event it received. WebSockets are for genuinely two-way, high-frequency traffic such as chat, collaborative editing or games; they need their own authentication at the handshake, origin checks, a message protocol and heartbeats. If the client only occasionally sends something, SSE for the push plus normal POST requests for the client's actions is usually simpler.

Deeper: Design live order-tracking updates for a delivery app with a million active users.

How a strong answer sounds
Updates are server-to-client and infrequent per user, so SSE (or a WebSocket only if the app already has one). Connections terminate on a dedicated, horizontally scaled real-time tier, designed for many cheap idle connections, rather than on the main API workers. The order service publishes each status change once, keyed by user, to a durable stream such as Redis Streams or Kafka; real-time nodes consume it and push to the users connected to them, or a routing layer maps users to nodes. Each event has an ID, and on reconnect the client sends its last ID and the node replays what was missed from the stream, so drops lose nothing; the app also fetches the order on open, so the stream is an optimisation, not the source of truth. Authentication uses a short-lived token at connect; heartbeats every 20 seconds; clients reconnect with exponential backoff and jitter; deploys drain nodes slowly to avoid reconnect storms. When a user is offline, a push notification goes through the platform's notification service instead.

🧠 Key takeaways

  • Polling is simple but trades latency against wasted requests; long polling costs a request per event.
  • SSE streams server events over plain HTTP with built-in reconnection and resume.
  • WebSockets are two-way; authenticate the handshake, check Origin, add heartbeats.
  • Fan out with pub/sub across processes, plus a store for catch-up.
  • Connections cost memory and descriptors; plan heartbeats, drain on deploy, back off on reconnect.
