The Backend & API Interview Playbook

Backend interviews test the same knowledge this course has built, in four formats: designing an API on a whiteboard, explaining concepts, talking through a production problem, and building a small service at home. Each rewards a structured answer that starts from requirements, names trade-offs and mentions failure, and each has a handful of mistakes that sink otherwise good candidates.

This chapter gives a framework for each format and points every topic back to the chapter that covers it. The answer builder at its centre lets you practise: choose the points you would make for eight common questions, then compare them with a rubric of essentials, strong extras and red flags.

  • Run an API design round with a repeatable structure
  • Answer concept questions with a definition, a trade-off and an example
  • Talk through a debugging scenario from symptom to fix
  • Scope and present a take-home service
  • Avoid the red flags interviewers listen for

API design rounds

"Design the API for a food-delivery app" is open on purpose: the interviewer is watching how you structure it. Start with requirements: who the clients are (mobile, partners), the main use cases, scale and latency expectations, and what must never go wrong (double charges, leaking another user's data). Then the resources and their relationships, and the endpoints: methods, URLs, status codes, request and response shapes (Chapter 4). Then the cross-cutting decisions that separate strong candidates: authentication and per-object authorisation (Chapter 10), idempotency for creates (Chapter 15), pagination and filtering (Chapter 8), errors (Chapter 5), rate limits (Chapter 19), versioning (Chapter 13), and anything asynchronous: webhooks, jobs or real-time updates (Chapters 20, 21 and 23). Finish with the data model and one or two deep dives the interviewer chooses.

Concept questions

Questions such as "What is idempotency?" or "PUT versus PATCH?" are short, but a strong answer has three parts: a precise definition, the trade-off or the mistake it prevents, and a concrete example, ideally one you have measured or seen fail. The most common topics, with their chapters: HTTP semantics and status codes (2), REST resource design (4), authentication, OAuth and JWT (9, 11, 12), authorisation and object ownership (10, 33), transactions and isolation (17), caching and invalidation (18), rate limiting (19), idempotency (15), optimistic concurrency and ETags (16), N+1 queries (7, 25), pagination (8), async Python and the event loop (28, P2), retries, timeouts and circuit breakers (29), the outbox pattern (30), and REST versus gRPC versus GraphQL (24, 25).

Debugging scenarios

"Latency doubled after the deploy" or "users see each other's data" test judgement under pressure. Follow Chapter 39 out loud: clarify the symptom and its scope, ask what changed, say how you would mitigate first (a rollback is often the right first move), then narrow with metrics, traces and logs (Chapter 31), name the likely causes in order of probability and how you would confirm each, and close with how you would prevent a recurrence: a test, an alert, a review. Interviewers listen for calm structure, not for guessing the answer immediately.

Take-home services

A take-home, "build a small URL shortener API" or "an inventory service", is judged as a sample of your everyday work. Scope it deliberately and say what you left out. Give it a clear structure (Chapter 27), validation and consistent errors, a real database with migrations (Chapter 7), configuration from the environment (P6) and tests of behaviour, including authorisation and failure cases (Chapter 26). A Dockerfile with a health check (Chapter 36) and a README with how to run it, the design decisions, the trade-offs and what you would do next are often what reviewers read first. Keep commits small and messages clear; reviewers read the history too.

A design framework

Whatever the format, the same skeleton keeps answers organised and makes your reasoning visible. Say it as you go, so the interviewer can steer: requirements and constraints; the contract (resources, endpoints, errors); the data model and consistency needs; failure modes (retries, timeouts, partial failure, abuse); and operations (observability, deploys, limits). Use numbers when you can: an estimate of requests per second, a latency budget, a pool size from Little's law (Chapter 32). And name trade-offs rather than presenting one option as obviously right; "offset pagination is simpler, cursor pagination stays correct as data changes, so for this feed I would choose cursors" is the kind of sentence interviewers remember.

Use case: Google's public API design guidance

A good way to practise API design is to compare your answers with guidance written by teams that review APIs for a living. In 2017 Google published its API Design Guide, the style guide it had used internally since 2014 for its Cloud APIs, and it has since grown into the API Improvement Proposals at aip.dev: short, numbered documents covering resource-oriented design, standard methods (get, list, create, update, delete), resource names, pagination with page tokens, filtering, long-running operations, errors and versioning. Each proposal states a rule and explains why, which is exactly what an interviewer wants to hear: not just "use page tokens" but why they behave better than offsets as data changes. Reading a few, then designing an API and checking it against them, turns this course's chapters into the habits that show up under interview pressure. Microsoft's REST API Guidelines and Zalando's RESTful API Guidelines are similar public documents worth comparing.

⚠️
Common mistakes
  • Jumping to endpoints before asking about clients, scale and what must not fail.
  • Forgetting authorisation, idempotency or pagination until prompted.
  • Definitions without trade-offs or examples.
  • Guessing a cause in a debugging round instead of narrowing it.
  • Take-homes with no tests or no README explaining decisions.
  • Absolute claims such as "always use microservices" or "JWTs are always better".
  • Not saying your reasoning out loud.

Interview drill

Explain it simply: How do you approach an API design question?

How a strong answer sounds
I start by asking who the clients are, the main use cases, the scale and what must never go wrong, such as double charges or one user seeing another's data. Then I sketch the resources and their relationships, and the endpoints with methods, status codes and shapes, using consistent conventions. Before going deeper I cover the cross-cutting parts: authentication and per-object authorisation, idempotency keys on creates, cursor pagination, a consistent error format, rate limits and how the API will evolve. Then the data model and transactions, the failure modes, and finally observability and deployment, going deep wherever the interviewer wants. I say trade-offs out loud as I choose.

Deeper: Tell me about a production incident you were involved in.

How a strong answer sounds
A strong answer is structured and specific, and blameless. The situation and its impact in numbers: which users, which endpoints, how long. How it was detected, and what that says about alerting. The investigation in order: symptom, what had changed, how the scope was narrowed, which evidence confirmed the cause, for example pool checked-out at its maximum with the database idle, pointing to a connection leaked on an error path. The mitigation and when it took effect, then the root-cause fix and the follow-ups: a test that reproduces it, a new alert on pool wait, a change to the code review checklist. Finish with what you personally learned and would do differently. If you have not had a real incident, describe one you reproduced while learning, and say so.

🧠 Key takeaways

  • Design rounds: requirements, contract, data, failure, operations, out loud.
  • Bring up authorisation, idempotency, pagination and errors before you are asked.
  • Concept answers: definition, trade-off, concrete example.
  • Debugging rounds: scope, what changed, mitigate, narrow, prevent.
  • Take-homes: small scope done well, tested, with a README that explains the decisions.

Check your understanding

What should come first in an API design round?

Everything else follows from them, and asking shows judgement.

Which makes a concept answer strong?

An example you have measured or seen fail is especially convincing.

In a debugging scenario, latency doubled right after a deploy. What is a good first action to propose?

Stop the impact first; most incidents follow a change.

What do take-home reviewers often read first?

And the tests, which show what you consider important to get right.

Which statement is a red flag in a payments API design?

Networks fail; retries will happen. Make them safe instead.
