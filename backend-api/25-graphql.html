GraphQL

GraphQL turns an API around: instead of the server offering fixed endpoints with fixed responses, it publishes a typed schema of everything that can be asked, and each client sends a query naming exactly the fields it wants, across related objects, in one request. A mobile screen that needed eight REST calls (Chapter 4) needs one query, and no field it did not ask for.

That flexibility moves work and risk to the server: a query can touch any combination of fields, and naive resolvers turn one query into hundreds of database calls, or a malicious one into millions. This chapter covers the schema, queries and mutations, resolvers and the DataLoader pattern, and the limits every public GraphQL server needs. The lab runs real queries through Strawberry, a Python GraphQL library, and counts every SQL statement.

Schema and types

A GraphQL API is defined by its schema: object types with typed fields, where a field can be a scalar (Int, String, Boolean, ID, custom scalars such as DateTime) or another type, and lists and non-null markers ([Item!]!). Special root types define the entry points: Query for reads, Mutation for writes and Subscription for streams. The schema is introspectable, so tools can generate typed clients and documentation from it, much like OpenAPI (Chapter 14). This is the schema the lab's Strawberry code produces:

type Customer {
  id: Int!
  name: String!
  orders: [Order!]!
}

type Item {
  quantity: Int!
  product: Product!
}

type Order {
  id: Int!
  totalCents: Int!
  customer: Customer!
  items: [Item!]!
}

type Product {
  id: Int!
  name: String!
  priceCents: Int!
}

type Query {
  orders(first: Int! = 50): [Order!]!
}

Queries and mutations

A query mirrors the shape of the answer: { orders(first: 50) { id customer { name } } } returns exactly that tree. Clients pass inputs as variables rather than pasting them into the query text, reuse field sets with fragments, and can fetch several roots in one request. A mutation is a named write operation, placeOrder(input: {...}), that returns the changed objects so the client can update its view without another request. Errors are returned in an errors array alongside whatever data could be resolved, usually with HTTP status 200, so clients must check both; many schemas also model expected business failures as typed results, such as an OutOfStock type in a union.

Resolvers and DataLoader

Each field has a resolver, a function that produces its value given its parent object. That makes GraphQL composable, and it makes the N+1 problem automatic: resolving customer on each of 50 orders calls the customer resolver 50 times, and a naive resolver runs 50 queries. The fix is the DataLoader pattern, invented at Facebook alongside GraphQL: within one request, resolvers ask a loader for a key and get back a promise; the loader collects all the keys requested in the same tick of the event loop and fetches them with one batched query, WHERE id IN (...), caching results for the rest of the request.

async def load_customers(ids):
    found = dict(rows("SELECT id, name FROM customers WHERE id IN (%s)" % marks(len(ids)), list(ids)))
    return [Customer(id=i, name=found[i]) for i in ids]

# in the Order type
@strawberry.field
async def customer(self, info: strawberry.Info) -> "Customer":
    if USE_LOADERS["on"]:
        return await info.context["customers"].load(self.customer_id)
    r = rows("SELECT id, name FROM customers WHERE id = ?", (self.customer_id,))[0]             # one query per order
    return Customer(id=r[0], name=r[1])

Query cost limits

In REST, the server decides how expensive each endpoint is. In GraphQL, the client does, so a public GraphQL server must limit what a query may ask for: a maximum depth (Strawberry's QueryDepthLimiter, as in the lab); a cost or complexity calculation before execution, where each field has a cost and list fields multiply by their page size; required and capped pagination arguments on every list (first: 100 at most); limits on aliases and query size; an execution timeout; and rate limits by computed cost rather than by request (Chapter 19). For first-party apps, persisted queries go further: the server only accepts queries registered at build time, identified by hash, which also allows GET requests that HTTP caches can store. Turn off introspection in production if the schema is private, and apply authorisation in resolvers, at the object level (Chapter 10), since any field can be reached from many paths.

Use case: where GraphQL came from

In 2012 Facebook was rebuilding its iOS app as a native app instead of a wrapper around web pages. The News Feed needed deeply nested, varied data, stories, their authors, comments, likes and attachments, and the existing REST-style endpoints either returned far more than the phone needed or required many round trips over slow mobile networks. Engineers including Lee Byron, Nick Schrock and Dan Schafer designed a query language in which the client described the shape of the data it wanted, backed by a typed schema, and built the DataLoader pattern alongside it to keep the many small resolver calls efficient. Facebook published the specification and a reference implementation in 2015, and in 2018 handed GraphQL to the GraphQL Foundation under the Linux Foundation. Its design reflects that origin: it shines where many clients, especially mobile ones, need different slices of a rich graph of data, and it asks the server team to take on batching, limits and caching that REST gets more or less for free.

⚠️
Common mistakes
  • Resolvers that query the database per object, without DataLoaders.
  • No depth, cost or pagination limits on a public endpoint.
  • DataLoaders shared across requests, leaking cached data between users.
  • Authorisation only on root fields, while the same objects are reachable through nested paths.
  • Treating HTTP 200 as success without checking the errors array.
  • Exposing the database schema directly as the GraphQL schema.
  • Expecting CDN caching without persisted queries.

Interview drill

Explain it simply: What is the N+1 problem in GraphQL and how does DataLoader solve it?

How a strong answer sounds
Each field is resolved independently, so for a query asking for 50 orders and each order's customer, the customer resolver runs 50 times; if it queries the database each time, that is one query for the orders plus 50 more. DataLoader batches and caches within a request: resolvers ask the loader for a key and get a promise back, the loader waits until the end of the current tick, collects every key requested, and runs one query with an IN clause, returning each resolver its result. In a measurement, a query for orders with customers, items and products went from 251 SQL statements to 4. The loader must be created per request, so its cache never mixes users.

Deeper: You are opening a GraphQL API to third-party developers. How do you keep it safe and affordable?

How a strong answer sounds
Assume queries are written by strangers. Before execution: parse and validate, reject queries deeper than a set limit, compute a cost from per-field weights multiplied by requested page sizes and reject or charge above a budget, require pagination arguments on every list with a maximum, and cap aliases and query length. During execution: DataLoaders everywhere, a timeout, and object-level authorisation in resolvers, since data is reachable through many paths. Around it: rate limits by computed cost per client, as GitHub does with points, results reporting the cost so clients can optimise, introspection allowed but sensitive fields excluded from the public schema, and monitoring of the most expensive queries. Evolve the schema additively with @deprecated, and offer persisted queries to first-party apps for caching.

🧠 Key takeaways

  • A typed schema publishes everything clients may ask; each query chooses its own shape.
  • Resolvers run per field, so naive ones cause N+1 queries; DataLoader batches per request.
  • Public GraphQL needs depth, cost, pagination and size limits, checked before execution.
  • Authorise at the object level in resolvers; check errors as well as data.
  • GraphQL suits varied clients and aggregation; REST suits caching and simple public resources.
