curl, HTTPie & the Browser Dev Tools

Every chapter in this course ends in an HTTP request, and the fastest way to understand what a service really does is to send one by hand and read exactly what comes back: the status line, every header and the raw body. Not what the client library decided to show you, not what the front end rendered, but the bytes on the wire.

This page covers the three tools you will use constantly: curl, which is installed almost everywhere, HTTPie, which is friendlier for JSON, and the browser's network tab, which shows what a real web page sends. All the curl output on this page is real, captured from a small FastAPI service.

  • Send GET and POST requests with curl, with headers and JSON bodies
  • Read -v output: what was sent, what came back
  • Handle redirects and make curl fail on HTTP errors in scripts
  • Use HTTPie for quick JSON requests
  • Inspect, copy and replay requests from the browser's network tab

curl: the flags that matter

curl ships with Windows 10 and later, macOS and almost every Linux distribution, so it is the tool you can count on inside a container or on a server. On Windows, PowerShell 5 aliased curl to its own Invoke-WebRequest; type curl.exe to be sure you get the real one. A handful of flags cover nearly everything:

# GET, body only
curl http://127.0.0.1:8000/items/1
# -i: include the status line and response headers
curl -i http://127.0.0.1:8000/items/1
# -v: verbose; shows the request too (written to stderr)
curl -v http://127.0.0.1:8000/items/1
# POST JSON: --json sets the body, Content-Type and Accept (curl 7.82 or later)
curl --json '{"name":"mug","price":8.5}' http://127.0.0.1:8000/items
# the long way, on older curl
curl -X POST -H "Content-Type: application/json" -d '{"name":"mug","price":8.5}' http://127.0.0.1:8000/items
# other methods and headers
curl -X DELETE -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/items/1
# -L follow redirects; -f exit with an error on 4xx/5xx; -s quiet; -S still show errors
curl -sSfL http://127.0.0.1:8000/old-items/1
# timing breakdown
curl -o /dev/null -s -w "dns %{time_namelookup}s connect %{time_connect}s first byte %{time_starttransfer}s total %{time_total}s\n" https://example.com

Reading verbose output

With -v, curl prints a trace with three kinds of line: * lines are curl's own notes (resolving, connecting, TLS), > lines are the request it sent, and < lines are the response headers it received. The trace goes to stderr and the body to stdout, so curl -v ... | python -m json.tool still pretty-prints the body while the trace stays on screen. When an API "ignores" your header or rejects your body, the > lines show exactly what was actually sent, which is usually not what you assumed.

Bodies, content types and the 422

  
A body is just bytes; the Content-Type header tells the server how to read them. -d defaults to application/x-www-form-urlencoded, the format HTML forms use, and switches the method to POST. FastAPI reads a Pydantic body parameter as JSON, so a JSON-looking string sent as form data fails validation with 422 Unprocessable Entity, as the simulator shows. Use --json, or add -H "Content-Type: application/json" yourself. On Windows cmd.exe, single quotes do not quote, so either escape the double quotes inside the JSON or put the body in a file and send it with -d @body.json.


  
Redirects

  
A 3xx response carries a Location header and usually no useful body; curl stops there unless you pass -L. Two details matter when following redirects. For 301 and 302, clients including curl change a POST into a GET on the next hop, for historical reasons; 307 and 308 keep the method and body. And a redirect can point at a different host, which is why curl, since 2018, does not forward an Authorization header you set yourself to another host (see the use case below).


  
HTTPie

  
HTTPie (pip install httpie) is designed for JSON APIs. It sends JSON by default, colours and formats the response, and shows headers. key=value sends a string field, key:=value a raw JSON value such as a number, and Header:value sets a header:


http :8000/items/1                                # GET http://localhost:8000/items/1
http :8000/items name=mug price:=8.5               # POST with {"name": "mug", "price": 8.5}
http DELETE :8000/items/1 "Authorization:Bearer $TOKEN"
http -v :8000/items/1                             # show the request too


  
The browser's network tab

  
Open the developer tools (F12) and the Network tab, and every request the page makes is listed with its method, status, size and timing. Click one to see its headers, payload, response and a timing breakdown of DNS, connection, TLS, waiting for the server (time to first byte) and download. Tick Preserve log to keep requests across a redirect or page load, and Disable cache to see what a first visit does. Right-click a request and choose Copy as cURL to get a command that reproduces it exactly, cookies and all, which is the fastest way to turn "the page is broken" into a request you can replay and change. Treat that copied command as a secret: it contains your session cookie or token.


  
Saving requests

  
Requests you send more than twice deserve to be saved. A shell script of curl commands works anywhere. .http files, supported by VS Code's REST Client extension and JetBrains IDEs, keep requests in plain text next to the code, so they live in version control. GUI clients such as Postman, Insomnia and Bruno add collections, environments and scripting. For anything that should keep working, write it as a test with httpx (Prerequisite 7), which turns a manual check into an automatic one.

Use case: a token that followed a redirect
In January 2018 the curl project published CVE-2018-1000007. If you passed your own Authorization header with -H and also asked curl to follow redirects with -L, curl sent that header to every host in the redirect chain. A server that answered with a redirect to another domain, whether by mistake or on purpose, would receive your credentials. curl 7.58.0 fixed it: custom Authorization headers now go only to the host you originally asked for, and you must opt in with --location-trusted to send them further. Similar leaks on redirect were fixed in later years for cookies and for redirects that change port or protocol. The lesson for backend engineers goes both ways. As a client, know what your tool and your HTTP library forward on a redirect. As a server, never redirect to a URL taken from user input without checking it, because an open redirect lets an attacker borrow your domain's reputation, and sometimes your users' credentials.

Common mistakes

    
    
      
  • Sending JSON with -d and no Content-Type, then debugging the server's 422.
    • 
      
  • Assuming curl failed when it printed nothing: a 301 or 204 has no body. Use -i.
    • 
      
  • Using curl in scripts without -f, so 404s and 500s count as success.
    • 
      
  • Pasting a "Copy as cURL" command into a ticket or chat, session cookie included.
    • 
      
  • Turning off certificate checks with -k to make an error go away, and leaving it in a script.
    • 
      
  • Getting PowerShell's curl alias instead of curl.exe on older Windows.

Interview drill

    
Explain it simply: A teammate's POST to your API keeps getting 422 errors, but their JSON looks fine. What do you check first?

    
How a strong answer sounds
I would ask for the exact request, ideally with curl -v, because the > lines show what was really sent. The most common cause is the content type: curl -d sends application/x-www-form-urlencoded, so the server tries to read form data, not JSON. Then I would read the 422 body itself: FastAPI lists every failing field with its location, so it says whether the body could not be parsed at all or a particular field had the wrong type, for example a price sent as a string. Fix with --json or an explicit Content-Type: application/json.

    
Deeper: Users report a page is slow. How would you use the tools on this page to find out where the time goes?

    
How a strong answer sounds
I would start in the browser's network tab with the cache disabled, sorted by time, to find which requests are slow and whether the time is in DNS, connecting, TLS, waiting for the first byte, or downloading. A long wait for the first byte points at the server; a long download points at a large response; many small requests one after another points at the front end's request pattern. Then I would copy the slow request as cURL and replay it with -w timing variables, from my machine and from inside the network where the service runs, to separate network distance from server time. If the server is slow, I would move to its logs and traces (Chapter 31) for that request.

  


  

    
🧠 Key takeaways

    
    
      
  • curl -i shows the status and headers; -v also shows the request, on stderr.
    • 
      
  • -d sends form data; use --json or set Content-Type for JSON.
    • 
      
  • curl does not follow redirects without -L, and exits 0 on HTTP errors without -f.
    • 
      
  • HTTPie is quicker for interactive JSON; := sends numbers and booleans.
    • 
      
  • The network tab shows what a page really sends; "Copy as cURL" makes it replayable, secrets included.
