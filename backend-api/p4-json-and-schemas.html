JSON, Schemas & Serialisation

Almost every API in this course speaks JSON. It looks simple, and the format itself is: six kinds of value, a page of grammar. The trouble is everything JSON does not have. There is no date type, no decimal type, no distinction between integers and floats, and no rule for what a missing field means. Every service fills those gaps with conventions, and bugs live where two services fill them differently.

This page covers JSON's types and their traps, how a schema pins down what a body must look like, how Pydantic and FastAPI validate and convert incoming JSON, and how Python objects become JSON again on the way out. The validation results in the lab below are real responses from a FastAPI 0.142.2 service using Pydantic 2.13.5.

JSON's six types

JSON (RFC 8259) has exactly six kinds of value: object ({"key": value}, keys always strings), array, string (double quotes only), number, true/false and null. There are no comments, no trailing commas, no single quotes and no special number values such as NaN. Everything else, including dates, money, binary data and identifiers, has to be encoded as one of those six, usually as a string with an agreed format.

Two details of Python's standard json module are worth knowing. json.dumps writes float("nan") as NaN and infinity as Infinity, which are not valid JSON: measured, json.dumps({"x": float("nan")}) returns {"x": NaN}, and a strict parser in another language will reject it; pass allow_nan=False to get an error instead. And JSON does not forbid duplicate keys, so parsers choose: json.loads('{"a": 1, "a": 2}') returns {'a': 2}, while another parser might keep the first. Two services reading the same document differently is the root of several security bugs.

Numbers: integers, floats and money

JSON numbers have no size or precision limit in the grammar, but the programs that read them do. JavaScript, and many JSON libraries in other languages, read every number as a 64-bit floating-point value, which represents integers exactly only up to 253 = 9,007,199,254,740,992. Beyond that, integers silently round: Pydantic, asked for a float, read 9007199254740993 as 9007199254740992.0. Large IDs should travel as strings.

Floating point also cannot represent most decimal fractions exactly: in Python, 0.1 + 0.2 is 0.30000000000000004. That is fine for a temperature and wrong for money. For amounts, use Python's Decimal and send it as a string ("19.99"), which is what Pydantic does when it serialises a Decimal, or send an integer number of the smallest unit, such as cents, which is what Stripe's API does ("amount": 1999 with "currency": "usd").

Dates, times and nulls

JSON has no date type, so the convention is an ISO 8601 string, specifically the RFC 3339 profile: "2026-10-14T09:30:00Z", where Z means UTC, or an explicit offset such as +05:30. Always include the offset. A naive timestamp with no offset means whatever local time the reader assumes, and two servers in different time zones will disagree about it by hours. Pydantic accepts a bare date such as "2026-10-14" for a datetime field in lax mode and turns it into a naive midnight, which is exactly this trap. Unix timestamps (seconds since 1970) are unambiguous but unreadable, and ambiguous in a different way: seconds or milliseconds?

null and missing are different. A field sent as null says "this has no value"; a field left out says nothing. The difference matters most for partial updates: in a PATCH, {"phone": null} means "remove my phone number", while leaving phone out means "do not touch it". In Pydantic, Optional[int] only allows None; the field is still required unless you give it a default. To tell "sent as null" from "not sent", use model.model_fields_set or model_dump(exclude_unset=True).

Schemas: writing the contract down

JSON Schema is a JSON document that describes what another JSON document must look like: its type, required properties, formats, ranges and patterns. Pydantic generates one from every model, and FastAPI collects them into the OpenAPI document behind /docs (Chapter 14), which is what client generators and API explorers read. This is the schema Pydantic produced for a model with a Decimal, a datetime and a UUID:

class Price(BaseModel):
    amount: Decimal
    at: datetime
    id: UUID

# Price.model_json_schema(), measured:
{
  "properties": {
    "amount": {
      "anyOf": [
        {
          "type": "number"
        },
        {
          "pattern": "^(?!^[-+.]*$)[+-]?0*\\d*\\.?\\d*$",
          "type": "string"
        }
      ],
      "title": "Amount"
    },
    "at": {
      "format": "date-time",
      "title": "At",
      "type": "string"
    },
    "id": {
      "format": "uuid",
      "title": "Id",
      "type": "string"
    }
  },
  "required": [
    "amount",
    "at",
    "id"
  ],
  "title": "Price",
  "type": "object"
}

Note what the schema says about amount: a number, or a string matching a decimal pattern. The schema is a promise to clients about what you accept, so a change to a model is a change to your API contract.

Serialising: objects to bytes

The standard library cannot serialise most of what a service holds: measured, json.dumps({"at": datetime(...)}) raises TypeError: Object of type datetime is not JSON serializable. Pydantic models know how. model_dump() gives a dict of Python objects (Decimal('19.99'), a datetime, a UUID); model_dump(mode="json") gives a dict of JSON-safe values; and model_dump_json() gives the bytes directly, which for the model above was:

{"amount":"19.99","at":"2026-10-14T09:30:00Z","id":"00000000-0000-0000-0000-000000000001"}

FastAPI does this for you: the value a handler returns is validated against its response_model, filtered to the declared fields, and serialised. Declaring a separate output model is also how you avoid leaking fields, such as a password hash, that exist on the internal object (Chapter 5).

By default Pydantic ignores unknown fields in input: {"name": "mug", "colour": "blue"} validated into a model with only name silently drops colour. That is forgiving for clients, and it also hides typos such as "colour" for "color". model_config = ConfigDict(extra="forbid") rejects them with the error extra_forbidden.

Unicode and encodings

JSON exchanged between systems must be encoded as UTF-8 (RFC 8259), so Content-Type: application/json needs no charset parameter. Inside strings, any character may also be written as an escape: Python's json.dumps escapes everything outside ASCII by default, so {"city": "Kraków"} comes out as {"city": "Kraków"}; ensure_ascii=False writes the character itself. Both mean the same thing. Characters outside the Basic Multilingual Plane, such as most emoji, are written as two escapes (a surrogate pair), and string lengths differ between languages: len("👍") is 1 in Python and "👍".length is 2 in JavaScript. When you set a maximum length on a field, be clear about what you are counting.

Use case: Twitter's IDs outgrow JavaScript

In 2010 Twitter replaced its sequential tweet IDs with IDs generated by Snowflake, a service that packs a timestamp, a machine number and a sequence number into a 64-bit integer. The new IDs were far larger than 253, so any JavaScript client that parsed the API's JSON in the usual way silently rounded them: an ID came back as a slightly different number, and requests for that tweet then fetched a different tweet or none at all. Twitter's fix was to send every ID twice, once as a number in id and once as a string in id_str, and its documentation told developers to use the string. The same pattern appears across large APIs. The general rule: a JSON number is only as precise as the least precise parser that reads it, so identifiers, large counters and money travel as strings, even when the server's language could handle the number.

⚠️
Common mistakes
  • Sending 64-bit IDs as JSON numbers, which JavaScript rounds above 253.
  • Using floats for money instead of Decimal strings or integer minor units.
  • Timestamps without an offset, read differently by every server.
  • Treating null and a missing field as the same in PATCH requests.
  • Returning the internal object instead of a response model, leaking fields.
  • Assuming lax validation is strict: true becomes 1 for an int field.
  • Emitting NaN from Python's json, which other parsers reject.

Interview drill

Explain it simply: How would you represent a price in a JSON API, and why not just use a number?

How a strong answer sounds
Most clients read JSON numbers as binary floating point, which cannot represent most decimal fractions exactly, so 0.1 plus 0.2 is not quite 0.3, and errors creep into totals and comparisons. I would either send an integer number of the smallest currency unit with the currency code, such as 1999 and "usd", the way Stripe does, or a decimal string such as "19.99" with the currency, parsed into a Decimal type on both sides. Integer minor units are simplest to compute with; I would just need to know each currency's number of decimal places, since some have none and some have three. And I would never store or add money as floats on the server, whatever the wire format.

Deeper: A mobile client sends {"quantity": "3"} and your FastAPI service accepts it. Another team wants strict validation everywhere. What are the trade-offs?

How a strong answer sounds
Pydantic's lax mode converted the string to 3 because the meaning was unambiguous. That is forgiving to clients and lets old clients keep working, but it hides client bugs and has surprises: true is accepted as 1 for an int, and a bare date becomes a naive midnight datetime. Strict mode makes the contract exactly what the schema says, which is better for public APIs and for fields where conversion is dangerous, such as money and dates. Switching an existing API to strict is a breaking change, though, since clients that relied on conversion will start getting 422s. I would enable strict on new models and sensitive fields (Pydantic allows strict per field, with Field(strict=True); under FastAPI, leave dates and decimals lax, since a strict datetime or Decimal field rejects every JSON input), measure how often old endpoints receive values that only pass because of conversion, and tighten them in a new API version (Chapter 13).

🧠 Key takeaways

  • JSON has six types; dates, decimals, bytes and large IDs travel as strings by convention.
  • Integers above 253 lose precision in JavaScript and in any float-based parser.
  • Money is a Decimal string or integer minor units, never a float.
  • Timestamps carry an offset; null and missing mean different things.
  • Pydantic's lax mode converts obvious values; strict mode requires exact types, and under FastAPI rejects every date and decimal.
  • Models generate JSON Schema, which becomes your API contract in OpenAPI.
