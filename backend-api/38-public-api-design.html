Designing Public APIs & SDKs

An internal API can be changed by walking over to the team that calls it. A public API cannot: its callers are strangers who wrote their code months ago, against your documentation, and will not change it because you would like them to. Every design decision is a long-term promise, and the quality of the API is judged by how easily a developer can get from reading the docs to code that works in production, including when things go wrong.

This chapter covers what makes a public API good to build on: consistency, errors developers can act on, SDKs, documentation and changelogs, and deprecation handled as a promise. The lab runs the same integration task, create 50 charges and total them, written three ways against an API that sometimes rate-limits, fails and loses responses.

  • Write and enforce consistency rules across every endpoint
  • Design error responses a developer and a program can act on
  • Decide what an official SDK must handle for its users
  • Keep documentation and changelogs trustworthy
  • Deprecate with notice, signals and a sunset date you keep

Consistency rules

Developers learn an API from its first few endpoints and guess the rest. Consistency makes those guesses right. Write the rules down in a short style guide and enforce them in CI with a linter over the OpenAPI document (Spectral, as in Chapter 14): one naming case for fields (snake_case or camelCase, never both); plural resource nouns; one pagination style (cursor with limit, starting_after and has_more, say) on every list; one timestamp format (RFC 3339 in UTC); money as integers in minor units with a currency code; prefixed opaque IDs (ch_, cus_) that tell a reader what an ID is; the same envelope for every list and every error; and the same idempotency, filtering and expansion mechanisms everywhere. Each rule removes a whole category of support questions.

Errors developers can act on

An error response has two readers: a program deciding what to do next, and a developer working out what went wrong. Give the program a correct HTTP status and a stable, documented machine-readable code, plus whether to retry and when (Retry-After). Give the developer a message that says what to change, the parameter at fault, a link to the documentation and a request ID they can quote to support. Never change codes once published: clients branch on them. The format can follow RFC 9457 problem details (Chapter 5) or a documented envelope like this one:

HTTP/1.1 400 Bad Request
{
  "error": {
    "type": "invalid_request_error",
    "code": "amount_too_small",                                       # stable; programs branch on it
    "param": "amount",
    "message": "Amount must be at least 30 pence (got 12).",          # says what to change
    "doc_url": "https://docs.example.com/errors#amount_too_small",
    "request_id": "req_8f2c1a9e04b7"                                  # quote this to support
  }
}

SDKs and client libraries

Most developers will meet your API through a client library, so the SDK is part of the API's design. A good official SDK does the things every careful integration must do and most hand-written ones forget: retries on 429, 5xx and timeouts with exponential backoff and jitter, honouring Retry-After; idempotency keys generated per logical operation, so a retried create cannot create twice; auto-pagination as an iterator; typed errors carrying the code and request ID; sensible timeouts; and warnings when the server signals deprecation. Generate the boring parts (models, method signatures) from the OpenAPI document so the SDKs cannot drift from the API, and write the behaviour by hand, idiomatically for each language. Version SDKs with semantic versioning and keep them backward compatible as carefully as the API itself.

Simulator: one task, three clients

The task: create 50 charges of £1.00 to £1.49, then list them all and add them up (correct total 6,225 pence). It ran against a FastAPI service with three fault modes: none; rate limiting, where 15% of calls get a 429 with Retry-After; and server errors, where 10% of calls fail with 503 and a further 8% of creates are processed but their response is lost, also as a 503. The naive client is what the quick-start page encourages: call, raise on error. The retrying client retries 429 and 5xx up to six times but sends no idempotency keys. The SDK is the vendor's library described above; only the user's code is counted in its line total.

Documentation and changelogs

Documentation is where a public API is actually used, and it has layers: a quick start that gets to a first successful call in minutes, guides for common tasks (including errors, retries, idempotency and webhooks, not only the happy path), a complete reference generated from the OpenAPI document so it cannot be wrong, and runnable examples in each SDK's language. Keep a public changelog with dates, one entry per change, marking anything that requires action; let developers subscribe to it. Test the docs: run the code samples in CI, and watch which pages precede support tickets.

Deprecation as a promise

Removing something from a public API breaks someone, so treat deprecation as a contract with a timeline. Announce it with the reason and the replacement, a migration guide and a sunset date far enough away for customers' release cycles (often six to twelve months or more). Signal it in the API itself, in responses: the Deprecation header (RFC 9745) says when it was deprecated, Sunset (RFC 8594) when it will stop working, and a Link with rel="deprecation" points to the guide. Track who still calls the deprecated endpoint, by API key, and contact them directly; consider brief scheduled "brownouts" near the end so remaining callers notice in testing rather than on sunset day. Then keep the date: an API whose deprecations slip forever, or arrive without notice, teaches developers not to trust it.

Use case: Stripe's API versioning and SDKs

Stripe's API is widely cited as a model public API, and much of this chapter describes practices it popularised. Its errors carry a type, a stable code, the parameter at fault, a human-readable message, a documentation link and a request ID. Its SDKs retry safely and attach idempotency keys to retried requests, the mechanism Chapter 15 measured. And it handles change without breaking integrations through date-based API versions: each account is pinned to the version current when it first made requests, a request can override it with a Stripe-Version header, and every breaking change is released as a new dated version listed in a public changelog with an upgrade guide. Stripe's engineers have described how this works inside: the latest code handles every request, and a chain of small "version change" modules transforms responses back into the shape each older version expects, so years-old integrations keep working while the API keeps improving. Developers upgrade when they choose, deliberately, after reading exactly what changed.

⚠️
Common mistakes
  • Inconsistent naming, pagination or dates across endpoints.
  • Error responses with only a message, or codes that change.
  • Quick starts that show only the happy path.
  • SDKs that retry creates without idempotency keys.
  • Hand-maintained reference docs that drift from the API.
  • Breaking changes without a version, notice or changelog entry.
  • Deprecations with no sunset date, or one that is not kept.

Interview drill

Explain it simply: What makes an API error response useful?

How a strong answer sounds
It serves both a program and a person. For the program: the right HTTP status, a stable machine-readable error code it can branch on, and a clear signal about retrying, such as a 429 with Retry-After. For the developer: a message that says what to change, the parameter at fault, a link to documentation for that code, and a request ID they can give to support so we can find the exact request in our logs. The format is the same for every error on every endpoint, and published codes never change meaning.

Deeper: You are launching a public payments API next quarter. What do you put in place before launch?

How a strong answer sounds
A written style guide enforced by a linter on the OpenAPI document: naming, prefixed IDs, integer money with currency, RFC 3339 times, one cursor pagination style, one error envelope with stable codes and request IDs. Idempotency keys on every create, rate limits with 429 and Retry-After, and webhooks signed and retried. A versioning policy, ideally dated versions pinned per account, so later breaking changes do not break anyone. Official SDKs for the main languages, models generated from the spec, behaviour written by hand: retries with backoff, idempotency keys, auto-pagination, typed errors, deprecation warnings. Documentation with a quick start, task guides that cover failures, a generated reference, runnable samples tested in CI, a sandbox with test cards and the ability to trigger errors, and a public changelog. Finally a deprecation policy with minimum notice periods, Deprecation and Sunset headers, and usage tracking by key so we can contact callers before anything is removed.

🧠 Key takeaways

  • Write consistency rules down and lint every endpoint against them.
  • Errors need a status, a stable code, an actionable message, a doc link and a request ID.
  • An official SDK should retry safely, send idempotency keys, paginate and surface deprecations.
  • Generate references and SDK models from the contract; keep a dated public changelog.
  • Deprecate with notice, in-band headers, outreach and a sunset date you keep.
