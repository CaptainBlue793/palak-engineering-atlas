Talking to a Database

Almost every request a backend handles reads or writes the database, so the way a service connects to it shapes how fast the service is and how it fails. Database connections are expensive to open and limited in number, so services keep a small pool of them and lend one to each request. Used well, a pool of five connections can serve hundreds of requests a second. Used badly, holding a connection while waiting for something else, or forgetting to give one back, a pool turns a slow dependency into an outage.

This chapter covers drivers, connections, pools and a clean session-per-request pattern in FastAPI with SQLAlchemy. The lab bursts 60 requests at a real service, with SQLAlchemy's real pool, in three styles of handler.

  • Keep connections out of slow work, and never leak one

Drivers and connections

A driver speaks a database's wire protocol: sqlite3 in the standard library, psycopg or asyncpg for PostgreSQL, and others for MySQL and SQL Server. Most follow Python's DB-API (PEP 249): connect, get a cursor, execute with parameters, fetch, commit. A connection to a server database is a real, stateful thing at the other end: PostgreSQL starts a separate server process for each one, with its own memory, and opening one costs a TCP handshake, usually TLS, and authentication, typically a few milliseconds and more across a network. Every connection also holds its own transaction state, so two requests must never share one at the same time.

Databases cap connections: PostgreSQL's max_connections defaults to 100. That number has to cover every process of every service, every migration, every analyst's tool, all at once.

Connection pools

A pool keeps a few connections open and lends them out: a request checks one out, uses it, and returns it, and the next request reuses it without paying to connect. SQLAlchemy's engine pools by default. Its main settings:

  • pool_size (default 5): connections kept open.
  • max_overflow (default 10): extra connections opened under load and closed when returned.
  • pool_timeout (default 30 s): how long a request waits for a free connection before failing.
  • pool_pre_ping=True: test a connection before lending it, so one the database or a firewall silently dropped is replaced instead of failing a request; pool_recycle closes connections older than a given age.

The total is per process: a service with 4 workers per container and 10 containers, each with 5 + 10, can open 600 connections. Size pools from the database's limit downwards, and when there are too many processes, put a pooler such as PgBouncer between the services and PostgreSQL.

A session per request

In SQLAlchemy, a Session is a unit of work: it checks a connection out of the pool when it first needs one, keeps it for the duration of the transaction, and returns it on commit(), rollback() or close(). In FastAPI, a dependency with yield gives every request its own session and guarantees it is closed, even if the handler raises. This is the pattern the lab's service uses, with the switch that makes it buggy:

import os
import time

from fastapi import Depends, FastAPI
from fastapi.responses import JSONResponse
from sqlalchemy import create_engine, text
from sqlalchemy.exc import TimeoutError as PoolTimeout
from sqlalchemy.orm import Session, sessionmaker

PATTERN = os.environ.get("PATTERN", "release")   # hold | release | leak
engine = create_engine("sqlite:///" + os.environ.get("DB", "pool.db"),
                       pool_size=int(os.environ.get("POOL", 5)), max_overflow=int(os.environ.get("OVERFLOW", 0)),
                       pool_timeout=2)          # wait at most 2 s for a free connection (default 30)
SessionLocal = sessionmaker(engine)
app = FastAPI()
LEAKED = []


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        if PATTERN != "leak":
            db.close()                           # returns the connection to the pool
        else:
            LEAKED.append(db)                    # the bug: a reference kept, so the connection never returns


def call_payment_provider():
    time.sleep(0.2)                              # a slow external HTTP call


@app.exception_handler(PoolTimeout)
async def pool_timeout(request, exc):
    return JSONResponse({"code": "db_pool_timeout", "detail": str(exc).split("(")[0].strip()}, status_code=503)


@app.post("/checkout")
def checkout(db: Session = Depends(get_db)):
    price = db.execute(text("SELECT 850")).scalar()  # first query: a connection is checked out here
    if PATTERN == "release":
        db.commit()                                   # the transaction ends, the connection goes back to the pool
        db.close()
    call_payment_provider()
    return {"ok": True, "price": price}


@app.get("/pool")
def pool_status():
    return {"status": engine.pool.status()}

Queries use text("... WHERE id = :id") with parameters, or the ORM (Chapter 7), never string formatting (Prerequisite 5).

Things to try.

  • commit, then call the provider: each request holds a connection for well under a millisecond, so five connections serve all 60 requests, and everything finishes in the time the provider calls take.
  • hold the connection during the call, pool of 5: only five checkouts can be in their 200 ms provider call at once, so the rest queue for a connection. Total time quadruples. Add overflow: better, at the price of 15 connections per process.
  • leak the session: the first five requests succeed and never give their connections back. Every later request waits 2 seconds and fails with SQLAlchemy's own error. Overflow only postpones it.

Pool exhaustion

When every connection is checked out, new requests wait, then fail. The usual causes: holding a session open across slow work, such as calls to other services, file uploads or sleeping retries; leaked sessions, from code paths that skip close() or objects that keep a session alive; long transactions, including one left open by an error; slow queries; and a sudden rise in traffic with the pool sized for an average day. The symptoms are distinctive: latency rises for every endpoint that touches the database, CPU stays low, and logs fill with "QueuePool limit ... reached" or connection timeouts. Monitor checked-out connections and pool wait time, set pool_timeout lower than your request timeout so requests fail fast rather than pile up, and keep transactions short: read, write, commit, then do the slow work.

Use case: Instagram and PgBouncer, 2011

When Instagram's engineers described their stack in late 2011, about a year after launch and with around 14 million users, it was a Django application running on many app servers, backed by PostgreSQL. Each application process needs database connections, and the number of processes grew with traffic, while PostgreSQL, with a process per connection, does not like thousands of them. Their answer, described in the post, was PgBouncer: a lightweight pooler between the application and the database, so many application connections share a small number of real PostgreSQL connections. The same arithmetic applies to any service today: connections per process times processes must fit the database, and when it no longer does, an external pooler, or a managed equivalent such as Amazon RDS Proxy, is the standard answer, with the pool in each process kept small.

⚠️
Common mistakes
  • Calling other services, uploading files or sleeping while a transaction is open.
  • Sessions that are not closed on every path, including errors.
  • A new engine, and so a new pool, per request, or a new connection per query.
  • Sharing one session between concurrent requests or threads.
  • Pool sizes chosen per process without multiplying by the number of processes.
  • A 30-second pool timeout behind a 10-second request timeout, so requests pile up long after clients gave up.

Interview drill

Explain it simply: What is a connection pool and why do services use one?

How a strong answer sounds
Opening a database connection is slow, a network handshake, often TLS, authentication and, in PostgreSQL, a new server process, and the database only allows a limited number at once. A pool keeps a few connections open and lends one to each request for as long as it needs it, then takes it back for the next request. That removes the connection cost from every request and caps how many connections the service can open. The settings that matter are the pool size, how many extra connections may be opened under load, and how long a request waits for one before failing.

Deeper: Latency for every endpoint jumps from 50 ms to 5 seconds, CPU is low, and the logs show "QueuePool limit of size 5 overflow 10 reached". What do you do?

How a strong answer sounds
That is pool exhaustion: requests are waiting for connections, not working. Short term, find what is holding them. In the database, list active sessions and their states (in PostgreSQL, pg_stat_activity): many "idle in transaction" sessions mean code is holding transactions open while doing something else, long-running queries mean a slow query, and connections that never go away suggest a leak. Correlate with recent deploys and with a slow downstream service, since a provider that went from 200 ms to 5 s will hold every connection if calls happen inside transactions. Mitigate by rolling back the change or failing the slow dependency fast. Raising the pool size buys time but can push the database over its limit. The lasting fixes: commit before calling other services, close sessions in a finally, a pool timeout shorter than the request timeout, statement timeouts in the database, and alerts on checked-out connections and pool wait time.

🧠 Key takeaways

  • Database connections are expensive and limited; services pool them.
  • Pool size times processes must fit the database's connection limit; PgBouncer helps when it does not.
  • One session per request, from a yield dependency that always closes it.
  • Hold a connection only between the first query and the commit, never across slow work.
  • Exhaustion shows as slow everything with low CPU; fail fast and monitor pool usage.
