What a Backend Does

Behind every app on your phone and most websites is a backend: programs running on servers that receive requests, apply the rules of the business, keep the data, and send answers back. The phone shows a basket; the backend knows what is in it, what each item costs today, whether there is stock, and whether this customer is allowed to use that discount code.

This chapter sets out the jobs a backend does and the qualities it is judged on, and it starts with the most important design rule in the course, shown with a real experiment: the code of a service should be disposable, and its state should not be.

Clients and servers

A client is anything that sends a request: a browser, a mobile app, a command-line tool, or very often another backend service. A server waits for requests and answers them. Over the web, the exchange is HTTP: the client sends a method and a path, such as POST /orders, with headers and perhaps a body; the server sends back a status code, headers and a body, usually JSON. Each request is complete in itself: the server does not remember the conversation unless something, a cookie, a token or an ID in the URL, tells it who is asking and what they mean.

A backend is rarely one program. A typical product has an API that its apps call, a database, a cache, some background workers sending emails and processing payments, and calls out to other companies' APIs for payments, maps or messages. The course builds all of these, in Python with FastAPI.

State lives in the backend

State is everything the system must remember between requests: accounts, orders, balances, who is logged in. The client cannot be trusted to keep it, since users can change anything on their own device, and the service's processes cannot keep it either. Production services run several copies of their code at once, as worker processes and on several machines, so that one crash or one busy machine does not take everything down; and they restart those copies all the time, on every deploy, every crash and every scale-up or scale-down. Any value stored in a Python variable lives in one copy, and dies with it.

So the rule is: keep processes stateless and put state in a shared store built for it, usually a database (Chapter 6), with caches and queues for special cases. Then any copy can answer any request, and copies can be added, removed and replaced freely.

  • Compare the time for 300 hits: the database version was slower, because each hit is a durable write. Correct and a little slower beats fast and wrong; later chapters show how to make it fast too.

APIs as contracts

An API (application programming interface) is the set of requests a service accepts and the responses it promises: the paths, methods, fields, types, status codes and error formats. Once another team, a mobile app already installed on a million phones, or a customer's integration depends on it, that API is a contract. You can change everything behind it, the database, the language, the whole architecture, but changing the contract breaks people who did nothing wrong.

The contract is larger than the documentation. Hyrum's law, named after a Google engineer, says that with enough users, every observable behaviour of your API will be depended on by somebody: the order of fields, the exact error message, how long a request takes. So the course treats API design as a first-class skill, with chapters on resource design (Chapter 4), written contracts with OpenAPI (Chapter 14), versioning (Chapter 13) and public APIs (Chapter 38).

Latency, correctness, availability

A service is judged on a handful of qualities, and most design decisions trade one against another:

  • Correctness: the right answer, every time, including when two requests race, a retry arrives twice, or a downstream service fails halfway. A wrong balance is worse than a slow one.
  • Latency: how long a request takes. Report it as percentiles, not averages: p50 is the typical request, p99 the slowest 1%, and a user loading a page that makes 20 calls will very likely meet your p99.
  • Availability: the share of time, or of requests, that succeed. It is usually written in "nines", and each extra nine is roughly ten times harder to reach.
  • Security, cost and operability: who can see and change what, what it costs to run, and whether the team can understand and fix it at 3 a.m.

Use case: GitLab's database, 31 January 2017

Late at night, a GitLab engineer fighting a replication problem ran a command to empty a database directory, in a terminal connected to the primary production server rather than the secondary. About 300 GB of live data was deleted in seconds. The application servers were fine: they could be restarted or replaced at will. The problem was entirely the state. Then the team found that the backups they relied on were not working: of five backup and replication methods, none gave a recent, usable copy, and GitLab restored from a snapshot about six hours old, taken by chance for a staging environment. Issues, comments, merge requests and user accounts created in those six hours were lost. GitLab live-streamed the recovery and published a frank account of it. The lessons are the ones this chapter starts with: state is the irreplaceable part of a backend, so it lives in a store that is backed up, replicated and, crucially, regularly restored as a test, while the code around it stays disposable.

⚠️
Common mistakes
  • Keeping state in process memory, such as counters, sessions or carts, then adding a second worker.
  • Trusting the client to hold prices, roles or balances.
  • Changing an API's behaviour without treating it as a change to a contract.
  • Reporting average latency, which hides the slow requests users actually notice.
  • Promising an availability figure the architecture cannot deliver.
  • Untested backups: a backup you have never restored is a hope, not a backup.

Interview drill

Explain it simply: What does "stateless service" mean, and why do we want services to be stateless?

How a strong answer sounds
A stateless service keeps nothing between requests in its own memory that it would need later; everything that must be remembered, such as users, orders and sessions, is in a shared store like a database or Redis. That means any copy of the service can handle any request, so we can run many copies for load and resilience, put a load balancer in front without sticky sessions, restart or replace copies during deploys, and scale up and down freely. If state lived in a process, two copies would disagree, and a restart would lose it. A tiny experiment shows it: a hit counter in a Python dictionary under three workers gave three different totals, and all three reset to zero on restart.

Deeper: A product manager asks for 99.99% availability for a new API. How do you respond?

How a strong answer sounds
I would first make the number concrete: 99.99% allows about 4 minutes of downtime a month, so one bad deploy or a short database failover could use the whole budget. Then I would ask what it is for: which operations need it, measured how, and over what period, and what the cost of downtime actually is. Reaching it means several copies across availability zones, a database with automatic failover, deploys that never take the service down, careful handling of every dependency, and on-call staff, and the API can be no more available than everything it depends on in series. Often the right answer is a tiered target: the read path or checkout at 99.95% or 99.99%, admin features lower, written down as service-level objectives with error budgets that tell the team when to slow down releases.

🧠 Key takeaways

  • A backend receives requests, applies the business rules, keeps the data and answers.
  • Processes are disposable and run as many copies; state belongs in a shared store.
  • An API is a contract, and with enough users every observable behaviour is part of it.
  • Services are judged on correctness, latency percentiles, availability, security, cost and operability.
  • Each extra nine of availability is roughly ten times harder to deliver.
