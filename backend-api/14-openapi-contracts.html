OpenAPI & Contract-First Design

An API's contract can live in people's heads, in a wiki page that drifts, or in a machine-readable document that tools can check. OpenAPI is that document for HTTP APIs: every path, parameter, body, response and error, described precisely enough to generate documentation, client libraries, mock servers and tests, and to compare two versions and say whether one breaks the other.

FastAPI writes the document for you. This chapter looks at what is in it, how to use it as the contract rather than an afterthought, and how to stop breaking changes reaching production. The lab generates the real document for a base API and for thirteen changed versions, and runs each through a breaking-change check.

  • Read an OpenAPI 3.1 document: paths, operations, schemas and responses
  • Choose between code-first and design-first, and make either reviewable
  • Generate clients from the spec, with good operation IDs
  • Lint the spec for consistency and completeness
  • Diff specs in CI to catch breaking changes before release

The OpenAPI document

An OpenAPI document, in JSON or YAML, has info (title, version), paths (each URL template with its operations: GET, POST and so on), and components (reusable schemas, parameters, responses and security schemes). Each operation lists its parameters, request body, possible responses with their schemas, and security requirements. Since version 3.1, schemas are full JSON Schema (2020-12). FastAPI 0.142.2 produced OpenAPI 3.1.0 for the lab's API; this is part of it, exactly as generated:

              "schema": {

              }
            }
          },
          "required": true
        },

            "content": {

                }
              }
            }
          },
          "422": {
            "description": "Validation Error",
            "content": {
              "application/json": {
                "schema": {

                }
              }
            }
          }
        }
      }
    }
  },
  "components": {
    "schemas": {
      "OrderIn": {
        "properties": {
          "sku": {
            "type": "string",
            "maxLength": 40,

Two things in it come from FastAPI rather than from anything you wrote. The integer field's limits appear as 100.0 and 1.0, floats. And every operation got a generated operationId:

OperationGenerated operationId
GET /orders/{order_id}get_order_orders__order_id__get
DELETE /orders/{order_id}cancel_order_orders__order_id__delete
POST /orderscreate_order_orders_post

Client generators turn operationId into method names, so a generated SDK would offer client.get_order_orders__order_id__get(...). Set clean IDs, for example by passing generate_unique_id_function=lambda route: route.name to FastAPI(), so the handler get_order becomes the method get_order.

Code-first versus design-first

Code-first, FastAPI's natural mode, generates the document from the code: it cannot drift from what the service does, and nobody maintains two things. Design-first writes the document before the code: frontend, mobile and partner teams can review it, build against a mock server generated from it, and agree the contract before anyone writes a handler; the server then implements the spec and tests check it conforms. Many teams combine them: design new endpoints as a spec change, reviewed like code, and implement them in FastAPI, with CI comparing the generated document with the agreed one. In both cases, the document belongs in the repository, exported on every build (json.dump(app.openapi(), ...)), so every pull request shows how it changes the contract.

Generated clients

Generators such as openapi-generator (many languages), openapi-typescript and oapi-codegen (Go) turn the document into typed client code, so callers get autocompletion and compile-time checks, and a renamed field becomes a build error rather than a production bug. Generated clients inherit the spec's quality: missing error responses mean untyped errors, vague schemas mean any, and ugly operation IDs mean ugly methods. Configure them to tolerate unknown fields and enum values (Chapter 13), or a harmless addition to your API will crash your users' apps.

Linting the spec

A linter such as Spectral or Redocly checks a document against style rules: every operation has a description, error responses are documented, paths are kebab-case, properties are snake_case, schemas have examples, every operation declares security. Running a few rules of that kind over the lab's generated document found 17 issues, all of them things FastAPI cannot know unless you tell it:

RuleFindingsFix in FastAPI

Simulator: catch it in CI

Each change below was made to the FastAPI code, the document regenerated, and the result compared with the base document by a small breaking-change checker written for this lab in the spirit of oasdiff: it compares operations, request bodies and success responses, and reports breaking changes, warnings and safe changes. A CI job running such a check fails the build on anything breaking.

openapi diff, base → changedMeasured
Change made in the code
Every document was produced by app.openapi() from a real FastAPI app; only the code change differs. The checker is about 60 lines of Python and covers fewer cases than a dedicated tool such as oasdiff, which also checks parameters, headers, security and much more. Findings appear once per affected operation.

Things to try.

  • rename field: the checker sees a removal and an addition, and fails the build. A rename is a breaking change however it is spelled in the code.
  • new status value and nullable field: warnings, not failures. Whether they break depends on clients; a team might fail the build on them for public APIs.
  • tighter limit: lowering the maximum quantity from 100 to 10 is breaking, because requests that used to succeed will now get 422s. Easy to miss in review.
  • 201 → 200: a one-word change to a decorator, and a client that checks for 201 now thinks every order failed.

Diffing for breaking changes

Put the check in CI: export the document from the main branch and from the pull request, diff them, and fail on breaking changes unless the pull request is explicitly marked as a new version. Tools such as oasdiff do this with hundreds of rules. Combine it with contract tests, which send real requests and validate responses against the document (Schemathesis generates them from the spec, Chapter 26), so the document is not only stable but true.

Use case: SDKs generated from the spec

Companies whose APIs are their product have moved their client libraries onto their OpenAPI documents. Twilio publishes OpenAPI descriptions of its APIs in a public repository, twilio-oai, and generates its helper libraries for several languages from them, so a new endpoint or field reaches every language at once instead of waiting for someone to hand-write it in each. Stripe likewise publishes its OpenAPI specification in a public repository and builds its SDKs from it. Both arrangements make the document the single source of truth, and they explain why such companies treat spec quality, from operation IDs to documented error responses and examples, as seriously as code: every gap in the document becomes a gap in every SDK, and every accidental breaking change in the document ships in every language at once.

⚠️
Common mistakes
  • Treating /docs as the contract without exporting, reviewing or versioning the document.
  • Leaving generated operation IDs, producing unreadable SDK methods.
  • Documenting only the success response, so clients cannot handle errors properly.
  • Tightening validation without treating it as a breaking change.
  • A spec that drifts from behaviour, because nothing tests the service against it.
  • Generated clients that reject unknown fields, turning additions into outages.

Interview drill

Explain it simply: What is an OpenAPI document and what is it used for?

How a strong answer sounds
It is a machine-readable description of an HTTP API: every path and method, parameters, request and response bodies as JSON Schema, status codes, errors and authentication. Because tools can read it, it drives interactive documentation, generated client libraries, mock servers for frontend teams, contract tests that check the real service matches it, linting for consistency, and diffs that detect breaking changes between versions. In FastAPI it is generated from the code, which keeps it accurate, as long as you also export it, review it and test against it.

Deeper: Three teams consume your API and a release broke one of them. How do you stop it happening again?

How a strong answer sounds
Make the contract explicit and checked. Export the OpenAPI document in every build and commit it, so pull requests show contract changes for review. Add a CI step that diffs the document against the main branch with a tool like oasdiff and fails on breaking changes, including subtle ones such as tighter validation, changed status codes or required request fields, unless the change is deliberately versioned. Add contract tests that validate real responses against the document, so it cannot lie. Lint it so errors and examples are documented. For the three consumers, add consumer-driven contract tests if their usage is specific, and publish a changelog and deprecation notices. Finally, review why the break was not caught: often it was a behavioural change, such as ordering or rounding, that no schema shows, which calls for tests of behaviour, not only shape.

🧠 Key takeaways

  • OpenAPI describes paths, operations, schemas, responses and security in a machine-readable way.
  • Code-first keeps it accurate; design-first makes it reviewable early; export and review it either way.
  • Generated clients are only as good as the spec: fix operation IDs, document errors, tolerate unknowns.
  • Lint for completeness; diff in CI to fail builds on breaking changes, including tighter validation.
  • Contract tests keep the document true to the running service.
