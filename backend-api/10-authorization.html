Authorization: Roles, Scopes & Ownership

Once a service knows who is asking, it must decide what they may do, request by request and object by object. This is authorisation, and it is where APIs most often fail: not because someone broke the login, but because a logged-in user changed an ID in a URL and got someone else's data. Broken object level authorisation has been number one in OWASP's API Security Top 10 in both its editions, 2019 and 2023.

This chapter covers roles, permissions and scopes, the object-level checks that roles alone cannot provide, and how to structure checks so none is forgotten. The lab runs the same six actions, as five different users, against two real implementations of one API.

  • Separate authentication from authorisation
  • Model roles as sets of permissions, and check permissions
  • Limit tokens with scopes
  • Check ownership of every object, and scope every list query
  • Centralise checks so they are consistent and testable

Authentication versus authorisation

Authentication establishes identity: this request comes from Alice. Authorisation decides whether Alice may perform this action on this object: read order 4, refund $900, change Bob's role. Failing the first is a 401 ("who are you?"); failing the second is a 403 ("you may not"), or a 404 when even admitting the object exists would leak information. A perfect login system protects nothing if every authenticated user can do everything.

Roles and permissions

Role-based access control (RBAC) groups permissions into roles: a customer may read their own orders, a support agent may read any order and refund up to a limit, an admin may do everything. Write the checks against permissions (orders:refund), not role names, so adding a role, such as a senior agent with a higher limit, does not mean finding every if role == "support". Give each role the least it needs. Some rules depend on attributes of the user, the object and the request, such as amounts, regions, tenants or time; that is attribute-based control, and in practice most systems mix both.

Scopes

A scope limits what a particular token may do, independently of who the user is: a reporting integration might get a token with only orders:read, even though its owner is an admin. The effective permission is the intersection: the user must be allowed, and the token must carry the scope. Scopes come from OAuth (Chapter 11), and the same idea applies to API keys: let customers create keys restricted to what each integration needs, so a leaked analytics key cannot issue refunds.

Object-level checks

Roles answer "may a customer read orders?". They cannot answer "may this customer read order 4?", which depends on the object. Every endpoint that takes an ID must check that the caller may access that specific object, and every list must be scoped to what the caller may see, ideally in the query itself (WHERE customer_id = :me), so a forgotten filter cannot return everyone's rows. For objects a caller may not see, answer 404, not 403, so IDs reveal nothing; and make IDs hard to guess (Chapter 4), as a second layer, never as the only one.

Where checks belong

Authorisation scattered through handlers is authorisation that will be forgotten in one of them. Put the rules in one policy function or module, can(user, action, object), deny by default, and call it from a small number of places: a dependency that loads an object and authorises it, so a handler cannot get the object without the check; scoped query helpers for lists; and the input models, which decide which fields a user may set at all (OWASP calls the failures "broken function level" and "broken object property level" authorisation). This is the second implementation's core, taken from the code the lab ran:

def can(user: User, action: str, order: dict | None = None, amount: int = 0) -> bool:
    if user.role is Role.admin:
        return True
    if action == "read_order":
        return user.role is Role.support or order["owner"] == user.name
    if action == "refund":
        return user.role is Role.support and amount <= SUPPORT_REFUND_LIMIT
    if action == "set_role":
        return False
    return False


def load_order(order_id: int, user: User = Depends(current_user)) -> dict:
    order = ORDERS.get(order_id)
    if order is None or not can(user, "read_order", order):
        raise HTTPException(404, "Order not found")          # 404, so other people's IDs reveal nothing
    return order

Then test it the way the lab does: a table of users, actions and objects, with the expected outcome of each, run on every change. Policy engines such as Open Policy Agent, Cedar and OpenFGA (based on Google's Zanzibar) take this further, for organisations with many services or complex sharing rules.

Use case: the US Postal Service API, 2018

In November 2018 the security journalist Brian Krebs reported that a USPS web API, part of its "Informed Visibility" programme for tracking mail, let anyone with a free usps.com account query the account details of other users: email addresses, user names, account numbers, street addresses and phone numbers, for around 60 million accounts. Users were authenticated; the API simply did not check that the records requested belonged to the person asking, and it even accepted wildcard searches, so a single query could return many accounts. A researcher had warned USPS about it more than a year earlier. After Krebs contacted the agency, it was fixed within days. It is the bob-reads-alice row of the lab at national scale, and the fix is the same: every object and every search filtered by what the caller is allowed to see.

⚠️
Common mistakes
  • Checking that a user is logged in, but not that the object is theirs.
  • List endpoints without a scope filter, returning everyone's records.
  • Input models that accept fields such as role, owner_id or is_verified.
  • 403 for objects the user may not know exist, confirming that the ID is valid.
  • Checks scattered across handlers, each slightly different, one missing.
  • Role checks without limits on amounts, regions or tenants.
  • Trusting the client to hide buttons for actions the server does not forbid.

Interview drill

Explain it simply: What is broken object level authorisation, and how do you prevent it?

How a strong answer sounds
It is when an API checks that a user is logged in, and maybe their role, but not that the specific object in the request belongs to them or is shared with them. A user changes /orders/123 to /orders/124 and gets someone else's order. It is the top item in OWASP's API Security Top 10. To prevent it: every endpoint that takes an object ID loads the object through a function that also checks the caller may access it, returning 404 if not; every list and search query is filtered by what the caller may see, in the query itself; IDs are unguessable as an extra layer; and there is an automated test matrix of users and objects, including "other user's object", for every endpoint.

Deeper: Design authorisation for a support tool where agents can view customers' orders and issue refunds.

How a strong answer sounds
Agents authenticate with single sign-on and a second factor. Permissions are explicit: orders:read_any, refunds:create with a limit, and a higher limit or an approval flow for seniors; roles are just bundles of those. Every refund passes a policy check that considers the amount, the order's total and what was already refunded, the agent's limit, and perhaps the region or tenant the agent serves. Access to customer data is logged with who, what and why, ideally with a ticket reference, and the audit log is reviewed; very sensitive fields are masked unless the agent asks for them with a reason. Large refunds need a second person. The policy lives in one module with a test matrix, the support tool's API tokens are scoped, and the tool never trusts its own front end to hide forbidden actions, since every rule is enforced on the server.

🧠 Key takeaways

  • Authentication says who; authorisation decides what, for every action and every object.
  • Roles bundle permissions; check permissions, plus limits that depend on attributes.
  • Scopes restrict what a token may do, on top of what its user may do.
  • Check ownership of every object, answer 404 for others', and scope every list in the query.
  • Centralise policy, forbid sensitive input fields, and test a user-by-object matrix.
