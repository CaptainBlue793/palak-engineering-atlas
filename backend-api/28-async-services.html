Concurrency Inside a Service

A busy service does many things at once: it serves many requests, and a single request may call several other services. Done well, concurrency turns five seconds of sequential waiting into half a second. Done carelessly, it sends fifty simultaneous calls to a service that can take ten, or accepts more work than it can finish and makes every caller wait twenty seconds for an answer.

This chapter builds on the event loop of Prerequisite 2: worker processes for CPU, keeping the loop unblocked, running calls concurrently with asyncio.gather, limiting them with semaphores, and back-pressure, the art of saying no early. The lab measures each with real services.

  • Scale CPU-bound work with worker processes
  • Keep the event loop free of blocking calls
  • Run independent calls concurrently with gather and TaskGroup
  • Bound concurrency with semaphores and connection pools
  • Apply back-pressure and shed load before queues explode

Worker processes

One Python process runs Python code on one core at a time. For I/O-bound services that is fine, since the event loop overlaps waiting; for CPU-bound work, hashing, image processing, large JSON, run several worker processes (uvicorn --workers N, or more containers). A common starting point is one worker per core, adjusted by measurement. Workers share no memory, so anything shared lives in a database or Redis, and each worker has its own connection pools, which multiply (Chapter 6). Heavy CPU work that does not belong in a request at all goes to background jobs (Chapter 20) or a process pool.

Blocking the event loop

The rule from Prerequisite 2 grows teeth inside a real service: one synchronous call in an async def handler, a requests.get, a sync database driver, a big json.loads, pauses every other request on that worker. Use async libraries throughout (httpx, asyncpg or psycopg's async mode, redis.asyncio), push unavoidable blocking calls to threads with await asyncio.to_thread(...), and detect mistakes in development with asyncio's debug mode, which logs any callback that holds the loop for more than 100 ms.

Concurrent calls with gather

When a request needs several independent things, prices, stock and reviews, or 50 items' availability, start them together and await them together. asyncio.gather(*calls) runs them concurrently and returns results in order; Python 3.11's asyncio.TaskGroup does the same with better error handling, cancelling the rest if one fails. Concurrency turns the total time from the sum of the calls into roughly the slowest one, which the lab measures. But it also turns one request into many simultaneous requests for the service you call.

Limits and semaphores

Every dependency has a capacity, and unbounded concurrency finds it. An asyncio.Semaphore(10) lets at most 10 coroutines into a block at once; the rest wait their turn. Put one around calls to each downstream service, sized from what that service can take, and remember that the HTTP client's connection pool (httpx.Limits) and the database pool are limits too. A limit per process multiplies by the number of processes, so for strict global limits the downstream must enforce them as well, with 429 or 503 (Chapter 19).

client = httpx.AsyncClient(base_url=os.environ.get("DOWN", "http://127.0.0.1:8101"), timeout=10)
limit = asyncio.Semaphore(10)


async def one(sku):
    r = await client.get("/stock/" + sku)
    return r.status_code


async def one_limited(sku):
    async with limit:                    # at most 10 calls in flight from this process
        return await one(sku)


@aggregator.get("/basket/{mode}")
async def basket(mode: str, n: int = 50):
    skus = ["SKU-%d" % i for i in range(n)]
    if mode == "sequential":
        codes = [await one(s) for s in skus]
    elif mode == "gather":
        codes = await asyncio.gather(*(one(s) for s in skus))
    else:
        codes = await asyncio.gather(*(one_limited(s) for s in skus))
    return {"ok": codes.count(200), "failed": len(codes) - codes.count(200)}

Things to try.

  • fan-out: one by one takes over 5 seconds. Unbounded gather takes a quarter of a second, and 30 of the 50 calls fail, because they all arrived at once at a service built for 10. With a semaphore, all 50 succeed in well under a second.
  • overload, accept everything: every request succeeds, eventually. The queue grows by about 100 requests every second, so by the end answers take 10 seconds or more, long after any user gave up. With load shedding, about half are refused at once with 503 and a Retry-After, and everyone who is served gets an answer in about 300 ms.
  • CPU and workers: four processes nearly double the throughput of one for CPU-bound work here; with the load generator on separate machines, the gain would be closer to the number of cores.

Back-pressure

When requests arrive faster than a service can finish them, the excess waits somewhere, in the server's queue, in the event loop, in the load balancer, and every wait adds to every later request's latency. An unbounded queue turns a short overload into a long outage: work keeps being accepted that will finish only after the caller has timed out, so it is wasted. Back-pressure means pushing the overload back to the source: bounded queues and concurrency limits, and when they are full, refusing new work fast with 503 or 429 and Retry-After (load shedding), so the requests that are accepted are answered in time. The measure that matters under overload is goodput, requests answered usefully within their deadline, not throughput. Shed the least important work first, health checks and payments last, and keep timeouts consistent end to end (Chapter 29).

Use case: load shedding at Amazon

In the Amazon Builders' Library article "Using load shedding to avoid overload", David Yanacek describes the behaviour the lab's overload experiment shows. Pushed past its capacity without protection, a service's throughput can stay high while its latency climbs until almost every response arrives after the client has given up: the server is busy, but it is doing useless work. Amazon's services therefore measure goodput rather than throughput, and when they approach overload they reject excess requests cheaply and early, so that the requests they accept still complete within their deadlines. The article also covers prioritising which requests to drop, checking whether a request's deadline has already passed before starting work on it, and bounding every queue. The lab's shedding service is the simplest version: a cap on waiting requests and an immediate 503 with Retry-After, which kept the median latency of accepted requests around 300 ms instead of 8 seconds.

⚠️
Common mistakes
  • Unbounded gather over large lists, overwhelming downstream services and pools.
  • Awaiting independent calls one after another.
  • Blocking calls inside async handlers.
  • Unbounded queues that turn overload into minutes of latency.
  • Per-process limits treated as global ones, forgetting how many processes run.
  • One worker on a many-core machine for CPU-heavy endpoints.
  • gather without error handling, leaving other tasks running after one fails; prefer TaskGroup.

Interview drill

Explain it simply: An endpoint makes 50 calls to another service. How do you make it fast without breaking that service?

How a strong answer sounds
Run the calls concurrently, with asyncio.gather or a TaskGroup, so the total time is close to one call rather than fifty, but limit how many are in flight at once with a semaphore sized to what the other service can handle, and share one HTTP client with a sensible connection pool. Unbounded concurrency would send all 50 at once: in a measurement against a service built for 10 concurrent calls, 30 of 50 failed, while a semaphore of 10 completed all 50 in about 0.7 seconds instead of 5.6 sequentially. Each call also needs a timeout, and if the other service supports it, a batch endpoint that takes all 50 IDs in one request is better still.

Deeper: During a traffic spike your service's latency goes from 100 ms to 20 seconds, but error rates stay low. What is happening and what do you change?

How a strong answer sounds
Requests are queuing: the service accepts work faster than it completes it, so every request waits behind a growing queue, and since clients probably time out long before 20 seconds, much of the work being done is wasted, even though the server reports success. I would add back-pressure: cap concurrency and the number of waiting requests per worker, and above that reject immediately with 503 and Retry-After; check at the start of a request whether its deadline has already passed and drop it if so; make timeouts consistent from the edge down, so downstream work stops when the caller gives up; shed low-priority traffic first. Then address capacity: more workers or instances with autoscaling on concurrency or latency, not CPU alone, and look for whatever made each request slower, such as a dependency or a lock.

🧠 Key takeaways

  • Workers scale CPU across cores; the event loop overlaps I/O within one.
  • Never block the loop; use async libraries or to_thread.
  • gather or TaskGroup makes independent calls take as long as the slowest.
  • Bound concurrency per dependency with semaphores and pools.
  • Under overload, refuse early: bounded queues and load shedding protect goodput.
