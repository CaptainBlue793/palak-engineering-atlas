Multi-Tenancy

A business-to-business service usually serves many customer organisations, called tenants, from one deployment. Sharing is what makes it affordable: one codebase, one fleet, one database to run. It also creates the two problems this chapter is about. Isolation: one tenant must never see another's data, even through a forgotten filter or a concurrency bug. Fairness: one tenant's traffic spike must not become every tenant's outage.

The lab measures both: five ordinary handlers checked for cross-tenant leaks with manual filters and with an automatic ORM filter, 400 concurrent requests with two ways of holding the current tenant, and a shared worker pool where one tenant sends 600 requests a second while another sends 20.

  • Choose a tenancy model: shared tables, schema per tenant or database per tenant
  • Enforce row-level isolation centrally, in the ORM and in the database
  • Carry tenant context safely through async code
  • Recognise noisy neighbours and choose a fairness policy
  • Apply per-tenant limits and quotas

Tenancy models

There are three common ways to store many tenants' data. Shared tables (pool model): every table has a tenant_id column and all tenants' rows sit side by side. It is the cheapest to run and to migrate (one schema), scales to many thousands of small tenants, and puts all the isolation burden on your code. Schema per tenant (PostgreSQL schemas, or one SQL Server schema each): the same tables repeated per tenant in one database; queries are naturally scoped by setting the search path, but migrations run once per tenant and thousands of schemas strain catalogue and tooling. Database per tenant (silo model): the strongest isolation, per-tenant backups, restores and encryption keys, and the easiest story for regulated customers, at the highest cost per tenant and with fleet-wide migrations to orchestrate. Many products mix them: shared tables for most tenants, dedicated databases for the largest or most regulated.

Row-level isolation

In the shared model, every query must include tenant_id = current tenant. Relying on each developer to remember is how leaks happen. Enforce it in layers. In the application, an ORM hook that adds the tenant filter to every query on a tenant-scoped model; SQLAlchemy's with_loader_criteria in a do_orm_execute event does this, and refuses to run if no tenant is set. In the database, PostgreSQL row-level security (RLS): a policy such as USING (tenant_id = current_setting('app.tenant_id')::int), with the application setting app.tenant_id at the start of each transaction (SET LOCAL) and connecting as a role that cannot bypass RLS. RLS applies to raw SQL, reporting queries and anything else that reaches the table, which an ORM hook cannot.

@event.listens_for(Session, "do_orm_execute")
def tenant_filter(state):
    if state.is_select and not state.is_column_load and not state.is_relationship_load:
        tid = current_tenant.get()
        if tid is None:
            raise RuntimeError("query without a tenant")                   # fail closed
        state.statement = state.statement.options(with_loader_criteria(
            TenantScoped, lambda cls: cls.tenant_id == tid, include_aliases=True))

Also add tenant_id to unique constraints and to the leading column of indexes ((tenant_id, created_at)), so uniqueness is per tenant and every tenant's queries stay fast; and include it in cache keys, object-storage paths, search indexes and queue messages, which no database feature protects.

Tenant context in requests

The current tenant should come from the verified credential, a claim in the token or the API key's owner, never from a header or path the client can change freely. Once known, it has to be available to code deep in the request: the ORM hook, the cache wrapper, the logger. In async Python that means a contextvars.ContextVar, set in middleware or a dependency and reset afterwards; each task gets its own copy. A module-level variable or a thread-local is shared by every request the event loop is interleaving, so the tenant one request set can be read by another request's code after any await. Background jobs must carry the tenant ID in the message and set the context before doing any work.

Simulator: leaks and neighbours

Two experiments. Isolation: two tenants share SQLite tables of projects and invoices. Five handlers were written as a team might: three remember the tenant filter, one forgets it, one uses raw SQL. They ran with manual filters only and again with the automatic ORM filter; then 400 concurrent requests from the two tenants ran through FastAPI with the tenant held in a module global and in a context variable. Neighbours: 8 worker threads, each request 20 ms of work, so capacity is 400 a second; for 3 seconds the "big" tenant sends 600 a second (a bulk import) and the "small" tenant 20 a second, under four scheduling policies.

Things to try.

  • manual filters: the forgotten filter made tenant 1's monthly total include tenant 2's invoices, three times the right figure, with nothing to show it was wrong. The raw SQL export returned both tenants' rows.
  • automatic ORM filter: the forgotten filter no longer matters, but the raw SQL still leaks, because ORM hooks only see ORM queries. That gap is what database row-level security closes.
  • tenant in a global: exactly half of 400 concurrent requests got the other tenant's projects. The code is correct in every single-request test.
  • noisy neighbour, shared queue: the small tenant waited as long as the big one, nearly 0.9 s at the median, for its own 20 ms requests.
  • per-tenant cap: the small tenant is perfect, but half the workers sat idle while the big tenant's backlog grew to over 6 seconds. Fair queueing protects the small tenant just as well and wastes nothing.

Noisy neighbours

In shared infrastructure, one tenant's load lands on resources every tenant needs: worker slots, database connections, CPU, cache memory, queue throughput. A single customer's bulk import, a runaway integration retrying in a loop, or a heavy report can make the service slow for everyone, even though each tenant's own traffic is modest. Defences, roughly in order of cost: per-tenant rate limits and quotas at the edge; fair scheduling of shared queues and worker pools, giving each tenant a turn rather than serving strictly in arrival order; separate lanes for heavy work (a bulk-import queue with its own workers, a reporting replica); per-tenant concurrency caps where some slots must stay free; and, for the largest tenants, dedicated capacity or their own database. Watch per-tenant metrics (requests, errors, latency, queue depth) so you can see who the noisy neighbour is; Chapter 31 warned against tenant IDs as metric labels in general, but a bounded "top tenants" breakdown or logs and traces carrying the tenant make this tractable.

Per-tenant limits

Limits are part of the product as well as protection. Express them per tenant and per plan: requests per second with a burst, concurrent requests, records stored, file storage, jobs in flight, seats. Return 429 with Retry-After for rate limits and a clear 4xx error that names the quota for hard limits, and expose current usage in an API and the dashboard so customers can see a limit coming. Keep the counters where every instance can see them (Redis, Chapter 19), and make limits configurable per tenant so sales can raise one without a deploy.

Use case: Salesforce's multitenant architecture

Salesforce built one of the earliest and largest multi-tenant platforms, and has described its design publicly in a widely read architecture white paper. All customer organisations share the same application servers and the same database tables; every row carries an organisation ID, and the platform's query layer adds it to every query, so customer code cannot leave it out. Customers can define their own objects and fields, but rather than altering the shared schema for each, Salesforce stores customisations as metadata and maps them onto generic shared data tables. To keep one organisation from harming the others, the platform enforces "governor limits": per-transaction caps on queries, records retrieved, CPU time and callouts, plus daily API request allowances per organisation, and code that exceeds them is stopped with an error. The two ideas in this chapter appear at platform scale: isolation enforced below the application code, and explicit per-tenant limits as part of the product contract.

⚠️
Common mistakes
  • Taking the tenant from a client-supplied header rather than the verified credential.
  • Relying on every query to remember tenant_id.
  • Holding the tenant in a global or thread-local in async code.
  • Forgetting the tenant in cache keys, file paths, search indexes and job payloads.
  • Unique constraints without tenant_id, so one tenant's value blocks another's.
  • One shared queue for all tenants, served strictly first in, first out.
  • Limits only for the whole service, none per tenant.

Interview drill

Explain it simply: How do you keep tenants' data apart in a shared database?

How a strong answer sounds
Every tenant-owned table has a tenant_id, and the current tenant comes from the verified token, held in a context variable for the request. I enforce the filter centrally rather than trusting each query: an ORM hook that adds tenant_id to every query on tenant-scoped models and fails if no tenant is set, and PostgreSQL row-level security as a second layer that also covers raw SQL, with the app setting the tenant per transaction and connecting as a role that cannot bypass RLS. I put tenant_id first in indexes and in unique constraints, scope caches, files and jobs by tenant too, and keep tests that try to read another tenant's data through every endpoint.

Deeper: Your largest customer's nightly import makes the API slow for everyone. What do you do?

How a strong answer sounds
First confirm it with per-tenant metrics: their request rate, the shared queue's depth and other tenants' latency during the import. Short term, apply a per-tenant rate limit or concurrency cap for that kind of traffic and switch shared queues to fair scheduling, so other tenants get a turn even while the import is queued. Then give bulk work its own lane: a bulk import API that accepts a file and processes it with separate workers and connection limits, ideally off-peak, with progress reporting. Make the limits part of the plan, visible in the dashboard and returned with 429 and Retry-After. If the customer is large enough, move them to dedicated capacity or their own database. Finally, alert on per-tenant saturation so the next noisy neighbour is caught before customers complain.

🧠 Key takeaways

  • Pick a tenancy model per tier; shared tables are cheapest and need the strongest enforcement.
  • Enforce tenant filters centrally in the ORM and again with database row-level security.
  • Take the tenant from the verified credential and hold it in a ContextVar, never a global.
  • Scope caches, files, search and jobs by tenant too.
  • Fair queueing and per-tenant limits stop one tenant's spike from becoming everyone's outage.
