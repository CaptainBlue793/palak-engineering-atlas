Transactions in Application Code

Moving money between two accounts is two writes: take it from one, add it to the other. If the service crashes between them, money vanishes. If two transfers from the same account run at once, each may check the balance, see enough, and together overdraw it. Databases have solved both problems for decades with transactions, but only for code that uses them properly: the right boundaries, the right statements inside them, nothing slow inside them, and a plan for when the database says "try again".

This chapter is about transactions from the application's side. The lab runs 400 real transfers between ten accounts on eight threads, crashes ten per cent of them half-way, and checks whether the bank still holds the £100,000 it started with.

  • Draw transaction boundaries around a whole unit of work
  • Know what isolation levels do and do not protect against
  • Fix read-modify-write races with atomic statements or locks
  • Keep external calls out of transactions
  • Retry serialisation failures and deadlocks correctly

Unit of work

A transaction makes a group of statements atomic: all of them take effect, or none do. Its boundaries should match one business operation, "transfer £50", "place an order", not one SQL statement and not one whole HTTP session. In SQLAlchemy, with session.begin(): commits at the end of the block and rolls back if anything inside raises; in a FastAPI service, a request usually performs one unit of work, opened and committed by the dependency or service function that owns it. Code that runs each statement in its own implicit transaction, called autocommit, gives up atomicity, and the lab shows what that costs.

def transfer(session, src: int, dst: int, amount: int) -> bool:
    with session.begin():                                     # one unit of work
        debited = session.execute(
            text("UPDATE accounts SET balance = balance - :a WHERE id = :s AND balance >= :a"),
            {"a": amount, "s": src}).rowcount
        if not debited:
            return False                                         # insufficient funds; nothing changed
        session.execute(text("UPDATE accounts SET balance = balance + :a WHERE id = :d"), {"a": amount, "d": dst})
        session.add(LedgerEntry(src=src, dst=dst, amount=amount))   # the record of it, in the same transaction
    return True                                              # committed; now notify, email, call others

Isolation from the application's side

Atomicity covers crashes; isolation covers concurrency: what one transaction can see of others running at the same time. SQL defines levels, and the defaults are weaker than many developers assume. PostgreSQL defaults to READ COMMITTED: each statement sees data committed before it began, so two transactions can both read a balance of £1,000 and both subtract £800 from their own copies, and neither gets an error. REPEATABLE READ gives each transaction a consistent snapshot and, in PostgreSQL, aborts a transaction that tries to update a row someone else changed. SERIALIZABLE guarantees the outcome of some serial order, aborting transactions that would break it. MySQL's InnoDB defaults to REPEATABLE READ with its own semantics. SQLite, used in the lab, allows one writer at a time and refuses to let a transaction write if another committed a write after it started reading. Whatever the database, know which level you run at, and know that stronger levels turn races into errors you must retry.

Simulator: a bank under load

Ten accounts start with £10,000 each. Eight threads perform 400 random transfers of £100 to £3,000, refusing any that would overdraw the source. One transfer in ten crashes between its debit and its credit, as a bug or a killed process would. Pick a design; every number is from a real run against SQLite.

Design
Python's sqlite3 with one connection per thread, WAL mode and a 10-second busy timeout. Things to try.

  • no transaction: the bank lost tens of thousands of pounds, one debit at a time, in the transfers that crashed after taking the money. And an account went negative: two transfers checked its balance at the same moment.
  • transaction, read then write: the money is all there, but most transfers failed. SQLite refused to let a transaction that had read a balance write after someone else changed the database. Add retries and they succeed, after hundreds of conflicts.
  • atomic update: balance = balance - :a WHERE balance >= :a checks and debits in one statement. No conflicts, no overdrafts, the highest throughput.
  • a 20 ms call inside the transaction: same correctness, a fraction of the throughput, because each transaction holds the write lock while it waits. Move the call after commit and the throughput comes back.

Read-modify-write races

"Read the balance, check it in Python, write the new value" is the same race as Chapter 16's lost update, inside a transaction. At READ COMMITTED it silently loses money or overdraws; at stronger levels, or in SQLite, it fails with conflicts that must be retried. Three fixes, in order of preference: express the change as an atomic conditional statement (UPDATE ... SET balance = balance - :a WHERE id = :s AND balance >= :a) and check the row count; lock the rows you are about to change with SELECT ... FOR UPDATE, in a consistent order such as ascending ID to avoid deadlocks; or run at SERIALIZABLE and retry. Let constraints help too: CHECK (balance >= 0) turns any bug that would overdraw into an error instead of bad data.

External calls inside transactions

Do not call other services, send email or upload files inside a transaction. While the transaction is open it holds locks, other writers wait, and the connection is out of the pool (Chapter 6); measured here, a 20 ms call inside each transfer cut throughput by a factor of seven. Worse, the outside world does not roll back: if the email is sent and then the commit fails, the customer is told about a transfer that never happened. Commit first, then do the external work, and if that work must be guaranteed, record the intent in the same transaction and deliver it afterwards with the outbox pattern (Chapter 30).

Retrying serialisation failures

Under stronger isolation, or with optimistic schemes, the database will sometimes abort a transaction: PostgreSQL reports serialisation failures as SQLSTATE 40001 and deadlocks as 40P01; SQLite reports "database is locked". These are not bugs to log and give up on; they are the database asking you to try again. Retry the whole transaction, from its first read, not just the failed statement; use a few attempts with jittered backoff; and make sure everything inside it is safe to repeat, which is one more reason to keep external calls out.

Use case: Flexcoin, 2014

Flexcoin was a small Bitcoin bank. On 2 March 2014 it announced that its hot wallet had been emptied of 896 bitcoins and that it was closing. The attacker had used Flexcoin's feature for transferring coins between its own users. By sending many transfer requests at the same moment, they had several transfers check the same balance before any of them updated it, so each saw enough funds, and together they moved far more than the account held, repeatedly, into accounts the attacker then withdrew from. Reports at the time described it as a race condition in the balance update, the read-modify-write race of this chapter, and a similar flaw was reported at the exchange Poloniex days later. A single conditional statement, debiting only where the balance was still sufficient, or a row lock around the check and the debit, would have made every concurrent transfer after the first fail cleanly.

⚠️
Common mistakes
  • Several related writes outside one transaction.
  • Checking a balance in Python and writing a computed value at READ COMMITTED.
  • HTTP calls, emails or uploads inside a transaction.
  • Retrying only the failed statement instead of the whole transaction.
  • Swallowing serialisation failures and deadlocks as generic 500s.
  • Locking rows in inconsistent orders, producing deadlocks under load.
  • Assuming the default isolation level without checking it.

Interview drill

Explain it simply: How would you implement a money transfer between two accounts safely?

How a strong answer sounds
In one database transaction: debit the source with a conditional statement, UPDATE accounts SET balance = balance - :amount WHERE id = :src AND balance >= :amount, and check that one row changed, so the balance check and the debit are a single atomic step that concurrent transfers cannot both pass; credit the destination; insert a ledger entry; commit. If anything fails, the whole thing rolls back. A CHECK (balance >= 0) constraint backs it up. The request carries an idempotency key so a retried transfer does not run twice. Notifications happen after the commit, ideally through an outbox. If the database aborts the transaction because of a conflict or deadlock, I retry the whole transaction a few times with backoff.

Deeper: Your service uses PostgreSQL at READ COMMITTED. An on-call rule says "at least one doctor must be on call". Two doctors go off call at the same time and both succeed, leaving nobody. Why, and how do you fix it?

How a strong answer sounds
It is write skew. Each transaction counts the doctors on call, sees two, and updates its own doctor's row to off call. They update different rows, so neither blocks the other and READ COMMITTED, or even REPEATABLE READ in PostgreSQL, allows both commits, breaking the rule that depended on rows neither of them wrote. Fixes: run this transaction at SERIALIZABLE and retry on serialisation failure, which PostgreSQL detects for exactly this pattern; or lock the rows the decision depends on with SELECT ... FROM shifts WHERE on_call FOR UPDATE before counting, so the second transaction waits and then sees one doctor; or materialise the constraint, for example a row per shift that both transactions must update, turning the conflict into a write-write conflict on one row. I would pick SERIALIZABLE with retries for clarity if the transaction is short.

🧠 Key takeaways

  • One business operation, one transaction: all its writes commit or none do.
  • Default isolation is usually READ COMMITTED, which allows read-modify-write races.
  • Prefer atomic conditional statements; otherwise lock rows or use SERIALIZABLE with retries.
  • Keep external calls out of transactions; commit first, or use an outbox.
  • Retry whole transactions on serialisation failures and deadlocks.
