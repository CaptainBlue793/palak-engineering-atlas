Your First Service with FastAPI

FastAPI turns ordinary Python functions into HTTP endpoints. You write a function with type hints; FastAPI reads those hints to decide where each argument comes from (the path, the query string, a header or the JSON body), converts and validates the incoming values, rejects bad requests with a detailed 422 before your code runs, filters and serialises what you return, and publishes the whole thing as an OpenAPI description with interactive documentation.

That is a lot of behaviour hidden in a signature, so this chapter makes it visible. The lab sends ten real requests, good and bad, to one endpoint and shows exactly what FastAPI passed to the function, or why it never called it.

  • Predict whether a parameter comes from the path, query, header or body
  • Validate request bodies with Pydantic models and field constraints
  • Use response models to control exactly what leaves the service
  • Read the generated OpenAPI document and interactive docs

Routes and handlers

A route pairs a method and a path template with a handler function. The decorator registers it; uvicorn serves it. This is the whole service the lab uses:

# shop.py: run with  uvicorn shop:app --reload
from fastapi import FastAPI, Header, Query
from pydantic import BaseModel, Field

app = FastAPI(title="Shop")


class ItemIn(BaseModel):
    name: str = Field(min_length=1, max_length=80)
    price_cents: int = Field(gt=0)


class ItemOut(BaseModel):
    id: int
    shop_id: int
    name: str
    price_cents: int
    tags: list[str]


@app.post("/shops/{shop_id}/items", status_code=201, response_model=ItemOut)
def create_item(
    shop_id: int,                                   # in the path template, so a path parameter
    item: ItemIn,                                   # a Pydantic model, so the JSON body
    dry_run: bool = False,                          # a simple type not in the path, so a query parameter
    tags: list[str] = Query(default=[]),            # lists must be marked Query explicitly
    x_request_id: str | None = Header(default=None),  # read from the X-Request-Id header
):
    saved = {"id": 101, "shop_id": shop_id, **item.model_dump(), "tags": tags,
             "cost_cents": 412, "dry_run": dry_run, "request_id": x_request_id}  # internal fields
    return saved                                    # response_model filters what goes out

--reload restarts the server when a file changes, for development only. Handlers may be def or async def; the rule from Prerequisite 2 applies: blocking code goes in plain def. Routes are matched in the order they were declared, so put /items/latest before /items/{item_id}, or "latest" will be parsed as an item ID and fail.

Path and query parameters

FastAPI decides each parameter's source from its declaration:

  • A name that appears in the path template, like {shop_id}, is a path parameter, always required.
  • Any other parameter of a simple type (int, str, bool, float, an enum) is a query parameter: required if it has no default, optional if it has one.
  • A parameter whose type is a Pydantic model is the JSON body.
  • Anything else needs saying: Query() for lists, which would otherwise be read as a body; Header() for headers, where underscores become hyphens, so x_request_id reads X-Request-Id; Cookie(), Form() and File() likewise.

Values arrive as text and are converted to the declared type. A query bool accepts true, 1, yes and on (and their opposites), and nothing else; a list[str] comes from repeating the parameter, ?tags=a&tags=b, not from a comma-separated value.

Request bodies with Pydantic

A body model describes the JSON a client must send. Field constraints, Field(gt=0), min_length, max_length, patterns, enums, put the rules where they are visible, in the schema, rather than in if statements inside the handler. When validation fails, FastAPI answers 422 with every error at once, each with a loc saying where it was (["body", "price_cents"], ["query", "dry_run"]) and the handler is never called. Unknown fields in the body are ignored by default (Prerequisite 4).

Response models

response_model=ItemOut, or a return type annotation of -> ItemOut, makes FastAPI validate whatever the handler returns against that model and send only its fields. In the lab, the handler returned a dictionary including a cost price and two internal values; the client saw five fields. This is the main defence against accidental data exposure: when someone later adds password_hash or internal_notes to the database row, it does not leak, because the output model never had it. Keep separate input and output models, such as ItemIn without an id and ItemOut with one, rather than one model for everything. Set the success status with status_code=201 on the decorator.

Interactive docs

FastAPI builds an OpenAPI document from your routes, parameters and models, served at /openapi.json, and two documentation pages from it: Swagger UI at /docs, where you can send requests from the browser, and ReDoc at /redoc. This is how the generated document describes the lab's endpoint's parameters, taken from the real /openapi.json:

Because the document comes from the code, it cannot drift from it; client libraries can be generated from it, and contract tests can check it (Chapter 14). Give routes a summary, models descriptions and fields examples, and the docs become good enough to hand to another team. In production, decide deliberately whether /docs is public.

Use case: Peloton's API, 2021

In January 2021, security researchers at Pen Test Partners reported that Peloton's API returned private account data to anyone who asked: user IDs, age, gender, city, weight, workout statistics and more, even for members who had set their profiles to private, and at first without any authentication. The data was available because the endpoints returned what the backend had rather than what the caller should see. Peloton's first fix required a logged-in user but still let any member read other members' private data; the full fix came only after TechCrunch asked about it in May 2021, months after the report. Two habits from this chapter would have narrowed the problem: an explicit output model per endpoint, so a field is only exposed when someone deliberately adds it, and treating "who is asking" as part of every handler's input (Chapter 10).

⚠️
Common mistakes
  • Returning database rows or internal dicts without a response model, leaking fields added later.
  • One model for input and output, letting clients set id, is_admin or created_at.
  • A list parameter without Query(), which FastAPI then expects in the body.
  • Expecting ?tags=a,b to give two tags.
  • A specific route declared after a parameterised one (/items/latest after /items/{id}).
  • Validating in the handler with if statements instead of field constraints the schema can show.
  • Running with --reload in production.

Interview drill

Explain it simply: How does FastAPI know whether a function parameter is a path parameter, a query parameter or the request body?

How a strong answer sounds
From the declaration. If the name appears in the path template, it is a path parameter. If it is a Pydantic model, it is the JSON body. Otherwise, a simple type such as int, str or bool is a query parameter, required unless it has a default. For anything else you say it explicitly: Query for lists, Header, Cookie, Form or File. FastAPI then converts the text it received to the declared types, validates everything, and if anything fails it returns a 422 listing each error with its location, without calling the function.

Deeper: Why use separate input and output models for the same resource?

How a strong answer sounds
Because they answer different questions. The input model is what a client may set: for an item, a name and a price, but not its ID, owner, creation time or any server-computed field; if the same model were used, a client could send "owner_id" or "is_admin" and, depending on how it is saved, change them, which is a mass-assignment bug. The output model is what a client may see: the ID and timestamps, but never internal fields such as cost prices or password hashes, even when they exist on the database row. With FastAPI's response models, the output is filtered automatically, so new internal fields stay private by default. Often there are more than two, such as a create model, a partial update model where every field is optional, and a public versus an admin view.

🧠 Key takeaways

  • Path template names are path parameters, Pydantic models are the body, simple types are query parameters.
  • Lists need Query(); headers need Header(), with underscores read as hyphens.
  • Invalid input gets a 422 listing every error with its location, and the handler never runs.
  • Response models filter what leaves the service; use separate input and output models.
  • The OpenAPI document and /docs are generated from the code, so they stay in sync.
