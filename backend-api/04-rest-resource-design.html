REST Resource Design

A well-designed API is one people can guess. If GET /orders/42 returns an order, a developer will try GET /orders for the list, GET /orders?status=paid to filter it, and DELETE /orders/42 to remove one, without reading the documentation. REST, the style most web APIs follow, gets there by modelling the domain as resources with URLs, and using HTTP's methods and status codes for what they already mean.

This chapter covers the conventions, the places where they get hard (actions that are not just "update", related data, long-running work), and one decision that matters more than it looks: how much a single response should contain. The lab measures three designs for loading the same screen.

  • Model a domain as resources and collections
  • Design URLs that are consistent and guessable
  • Map actions to methods, including ones that are not plain updates
  • Choose between links, embedding and expansion for related data
  • Recognise when REST does not fit, and what to do instead

Resources and collections

A resource is anything worth naming: an order, a customer, a product, a refund, even a search or a report. Each has a URL, and clients work with representations of it, usually JSON. Resources come in collections (/orders) and items in them (/orders/42). The URL names the thing; the method says what to do with it. That is why REST URLs are nouns: POST /orders, not POST /createOrder.

Identifiers deserve a thought. Sequential integers are simple, but they reveal how many orders you have and invite people to try /orders/43; random identifiers such as UUIDs or prefixed IDs (ord_8f3k2…, as Stripe uses) reveal nothing, and a prefix tells a human what kind of object an ID belongs to. Whatever you choose, treat IDs as opaque strings in the contract, so you can change how they are made later.

URL design

  • Plural nouns for collections, lower case, words separated by hyphens: /purchase-orders/42.
  • Hierarchy only for real ownership: /orders/42/items (items belong to one order), but /products/7, not /orders/42/items/3/products/7. Two levels is usually enough.
  • The query string for filtering, sorting, searching and paging: /orders?status=paid&sort=-created_at&limit=50 (Chapter 8).
  • No verbs, file extensions or implementation details: not /getOrders.php, not /api/v1/tbl_orders.
  • Consistency over cleverness: the same names, casing (pick snake_case or camelCase for fields and keep it), date formats and error shape everywhere.
  • URLs are forever: once clients depend on one, it is part of the contract (Chapter 13).

Mapping actions to methods

Most operations map directly to a method on a resource. Some are actions with side effects and rules of their own, such as cancelling an order (which may trigger a refund and a stock release), and forcing them into "PATCH the status field" hides the rules. Common, defensible patterns:

Turning an action into a noun, a refund, a cancellation, an export, is often the most RESTful move, because the new resource can then be listed, fetched and audited like any other.

Nested and related resources

An order has a customer, line items, and products on each line. A response can link to related resources ("customer_url": "/customers/7"), embed them, or let the client ask for embedding with an expand parameter (?expand=customer&expand=items.product, the pattern Stripe uses). Links keep responses small and cacheable but make clients chatty; embedding everything makes every response heavy. The cost of chattiness depends on the network, which is why the lab adds a modelled distance to measured requests.

Things to try.

  • Linked resources, 5 lines, mobile: 8 requests, one after another, about half a second before the screen can draw. Switch the client to parallel: the requests that only depend on the order, then the products, go together, and it is 3 round trips.
  • Raise the order to 20 lines: 23 requests. Then pick ?expand=: one request, whatever the size, at the cost of a bigger response with fields the screen does not use.
  • Compare ?expand= with the screen endpoint at 20 lines: the same single round trip, and less than half the bytes, because it only contains what the screen shows. The price is an endpoint tied to one client's layout.
  • Set the network to same machine: the differences shrink to milliseconds. Designs that seem fine in local testing behave very differently on a phone.

When REST does not fit

REST is a good default, not a law. Some needs fit badly. Screens that combine many resources push you towards expansion, screen-specific endpoints or a backend for frontend (Chapter 35), or GraphQL, which lets the client specify the shape (Chapter 25). Service-to-service calls with strict contracts and high volume often suit gRPC (Chapter 24). Live updates need WebSockets or server-sent events (Chapter 23). Long-running work becomes a job resource with 202 Accepted. And some operations are honestly remote procedure calls, such as "recalculate prices"; a clear POST /price-recalculations is better than pretending otherwise.

Use case: Netflix redesigns its API, 2012

Netflix's original public API, launched in 2008, was a conventional one-size-fits-all REST API: fine-grained resources that any device could combine. By 2012 it served hundreds of different devices, televisions, consoles, phones and set-top boxes, and the generic design had become a problem. Each device needed different data for its screens, so clients made many requests to assemble one page, over home and mobile networks where every round trip was expensive, and every change to a resource had to suit every device at once. Netflix's API team described the redesign in a series of posts: device teams wrote small adapter scripts that ran on the server, next to the API, and each script fetched what one screen needed in a single call, combining the fine-grained services inside the data centre where round trips are cheap. It is the screen-endpoint design from the lab, at scale, and an early form of the backend-for-frontend pattern. Netflix also shut its public API down in 2014 to focus on its own devices.

⚠️
Common mistakes
  • Verbs in URLs for plain CRUD: /getOrder, /updateCustomer.
  • Deep nesting that hard-codes every relationship into the path.
  • Business actions disguised as field updates, such as PATCH {"status": "cancelled"} silently triggering a refund.
  • Chatty designs tested only on localhost, then shipped to phones.
  • Embedding everything everywhere, making every response slow and uncacheable.
  • Inconsistent naming and casing between endpoints.
  • Sequential IDs in public URLs without authorisation checks on every one (Chapter 10).

Interview drill

Explain it simply: Design the endpoints for cancelling an order.

How a strong answer sounds
Cancelling is an action with rules, not a field edit: it may only be allowed before shipping, and it may trigger a refund and release stock. So I would make it explicit: POST /orders/42/cancel, or model the cancellation as a resource, POST /orders/42/cancellations with an optional reason, returning 201 with the cancellation, which can then be fetched and audited. If the order has already shipped, return 409 Conflict with an error explaining why. It should be safe to retry: cancelling an already cancelled order returns the existing cancellation rather than an error or a second refund. The order's representation then shows its status as cancelled, and GET /orders?status=cancelled lists them.

Deeper: A mobile team complains that the order screen is slow. Your API is clean REST with linked resources. What are your options?

How a strong answer sounds
First measure: count the requests the screen makes and how many must happen in sequence; on a 60 ms mobile network, eight sequential requests is half a second before any server time. Options, roughly from least to most change: let the client parallelise independent requests over HTTP/2; add an expand parameter so one call returns the order with its customer and products, which keeps the resource model and helps every client; add a screen-specific endpoint or a backend for frontend owned by the mobile team, which gives the smallest response but couples the API to a layout; or offer GraphQL, where the client asks for exactly the fields it needs, at the cost of new infrastructure and new ways to write expensive queries. I would usually start with expansion and parallel requests, and add a backend for frontend only if several screens need it.

🧠 Key takeaways

  • Model the domain as resources with noun URLs; methods carry the verbs.
  • Plural collections, shallow nesting, the query string for filtering, and consistency everywhere.
  • Actions with rules become explicit endpoints or new resources such as refunds and exports.
  • Related data can be linked, embedded or expanded; count round trips on a slow network to choose.
  • When REST fits badly, use expansion, a backend for frontend, GraphQL, gRPC or job resources.
