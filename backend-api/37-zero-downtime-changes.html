Zero-Downtime Changes

Chapter 36 made deploys of code safe. The harder part is changing what code and data agree on: renaming a column, changing a field's type, splitting a table, changing an API response. During a rolling deploy, old and new versions of your service run side by side against the same database, so a change that is correct for the new version alone can break the old one, or let the two quietly disagree about the data.

This chapter covers the technique that makes such changes safe, expand and contract, with backfills, a column rename done properly, feature flags and what to do when a data change goes wrong. The lab renames a column under live traffic three ways and backfills a million rows in one statement and in batches, while another writer keeps working.

  • Split a breaking change into expand, migrate and contract steps
  • Backfill data in batches without blocking live writes
  • Rename a column with old and new code running at once
  • Use feature flags to separate deploying code from releasing behaviour
  • Plan how to undo a data change before making it

Expand and contract

Any change that old code cannot tolerate is done in phases, each deployed and verified before the next, so that every adjacent pair of versions works together. Expand: add the new structure alongside the old (a new column, table or field), nullable and unused, so nothing breaks. Migrate: ship code that writes to both, backfill existing data into the new structure, then switch reads to the new one. Contract: once no running code reads or writes the old structure, remove it. The same pattern, also called parallel change, applies to API fields (add the new one, migrate clients, deprecate and remove the old, Chapter 13), message schemas and configuration. It costs several deploys instead of one; in exchange, every step can be rolled back on its own.

Backfills

A backfill fills the new structure for existing rows. Written as one UPDATE ... SET new = old, it is a single transaction over the whole table: on PostgreSQL it locks every row it touches until it commits, bloats the table and the write-ahead log, and can delay replicas; on SQLite it blocks every other writer. Run it instead as a separate job in batches keyed by primary key, a few thousand rows per transaction with a short pause between them, idempotent (WHERE new IS NULL) so it can be stopped and resumed, and with progress logged. Watch database load and replication lag while it runs, and throttle if they climb.

def backfill_display_name(engine, batch=5000, pause=0.05):
    last = 0
    while True:
        with engine.begin() as conn:                                   # one short transaction per batch
            ids = conn.scalars(text("SELECT id FROM customers WHERE id > :last ORDER BY id LIMIT :n"),
                                {"last": last, "n": batch}).all()
            if not ids:
                return
            conn.execute(text("UPDATE customers SET display_name = fullname "
                              "WHERE id BETWEEN :lo AND :hi AND display_name IS NULL"), {"lo": ids[0], "hi": ids[-1]})
        last = ids[-1]
        log.info("backfill progress", extra={"fields": {"last_id": last}})
        time.sleep(pause)                                                  # leave room for live traffic

Renaming a column safely

Renaming customers.fullname to display_name looks like one line of SQL. Under a rolling deploy it is five steps. (1) Add display_name, nullable. (2) Keep the two columns in sync for every write, from either version: a database trigger, or a release of the old code that writes both. (3) Backfill existing rows in batches. (4) Deploy code that reads and writes display_name, still writing fullname too. (5) Once no instance of the old code is left, stop writing fullname, then drop it in a later deploy. Step 2 is the one most often missed: without it, any write the old version makes after the backfill leaves display_name out of date, and the new version reads stale data with no error at all.

Simulator: a rename and a backfill under load

Rename: two app instances read and update 200 frequently used customers in a SQLite database, 30% writes. One second in, the migration runs; then instance a switches to v2, and a second later instance b does. Every read is compared with the most recent write, so stale reads are counted as well as errors. Three strategies: rename the column in one migration; expand and backfill without keeping the columns in sync; and expand with a sync trigger. Backfill: copying a column across a million rows while another connection inserts a row every 5 ms, in one statement and in batches of 50,000, 5,000 and 1,000.

Things to try.

  • rename in one migration: from the moment the migration ran until the last instance switched, every v1 read and write failed with "no such column: fullname". With a rollback, the old code would fail just the same against the renamed column.
  • expand, no sync: no errors at all, which is what makes it dangerous. Writes by v1 after the backfill updated only fullname, so v2 kept reading the old display_name.
  • expand + sync trigger: no errors and no stale reads, through the whole rollout and the final contract step.
  • backfill: one statement held the write lock for its whole duration, and the live writer's slowest insert waited that long. Batches capped the wait per batch, at the price of a longer total.

Feature flags

A feature flag is a runtime switch, read from a flag service or configuration, that decides whether new behaviour runs. It separates deploying code from releasing behaviour: code ships dark, then the flag is turned on for staff, then 1%, 10% and 100% of users or tenants, and off again in seconds if metrics worsen, without a deploy. Flags make expand and contract easier too ("read from the new column" can be a flag). Keep them disciplined: give each flag an owner and an expiry, evaluate it once per request so a user sees consistent behaviour, default to the safe value when the flag service is unreachable, and delete flags once fully released, because stale flags are exactly what woke the dead code in Knight Capital's deployment (Chapter 36).

if flags.enabled("pricing.new-tax-engine", tenant=tenant.id, default=False):
    total = new_tax_engine.quote(cart)
else:
    total = legacy_tax.quote(cart)

Rolling back data changes

Code can be rolled back; data usually cannot. Before a data change, decide how you would undo it. Keep the old structure until the new one is proven (the contract step waits for days, not minutes). Make transformations reversible, or record what you changed: a backfill that overwrites values should write the old value somewhere first. For destructive operations, take a backup or snapshot and test restoring it. Prefer roll forward for bugs that wrote bad data: fix the code, then run a corrective job, because restoring a backup also discards every good write since it was taken. And remember side effects outside your database, such as emails sent and events published, which no rollback reaches.

Use case: GitHub's gh-ost for online schema changes

GitHub runs very large MySQL tables, and in 2016 it open-sourced gh-ost, its tool for changing their schema without downtime. Altering a large table directly in MySQL could lock it or take hours, and earlier online-change tools copied rows into a new table while keeping it in sync with triggers, which added load to the busiest tables. gh-ost applies the ideas in this chapter at the level of a whole table. It creates a "ghost" copy with the new schema, copies existing rows in small batches that it throttles automatically when replication lag or load rises, and keeps the copy in sync by reading the database's binary log rather than with triggers. Only when the copy has caught up does it swap the tables, in a brief, controlled cut-over that operators can postpone, and the whole migration can be paused or abandoned at any time with nothing lost. Expand (a new table), backfill in throttled batches, keep in sync, then cut over and contract: the same sequence, built so engineers could change production tables during working hours.

⚠️
Common mistakes
  • Renaming or dropping a column in the same deploy as the code change.
  • Backfilling without syncing new writes, leaving silently stale data.
  • One giant UPDATE instead of throttled, resumable batches.
  • Contracting too early, before every instance, job and client has moved.
  • Feature flags that never get removed.
  • Overwriting data with no record of the old values.
  • Assuming a rollback undoes data changes and side effects.

Interview drill

Explain it simply: How do you rename a database column without downtime?

How a strong answer sounds
Not in one step, because during a rolling deploy the old code still uses the old name. I expand first: add the new column as nullable. Then I make every write keep the two in sync, with a trigger or by releasing a version of the old code that writes both, and backfill existing rows in small batches. Next I deploy code that reads the new column and still writes both. Once no old code is running, I stop writing the old column and, in a later deploy, drop it. Each step is deployed and verified separately and can be rolled back on its own; skipping the sync step is the classic mistake, because it causes stale data without any error.

Deeper: You must change orders.amount from a float in pounds to an integer in pence on a 400-million-row table, with no downtime. Plan it.

How a strong answer sounds
Expand: add amount_pence BIGINT NULL, which is a metadata-only change in PostgreSQL. Sync: deploy code that writes both columns on every insert and update, converting with explicit rounding, and add a trigger as a safety net for other writers. Backfill: a resumable job in batches of a few thousand by primary key, with a pause and throttling on replication lag and database CPU, recording rows whose float values do not convert cleanly for review. Verify: a reconciliation query comparing the two columns over all rows. Switch reads behind a feature flag, per endpoint, watching errors and totals. Then add the NOT NULL constraint as NOT VALID and validate it separately, stop writing the float column, wait through a release cycle, and drop it. API responses keep their old field until clients migrate. At every step the previous version still works, and the old column stays until I am sure.

🧠 Key takeaways

  • During a rollout, old and new code share the database: every step must work for both.
  • Expand, sync and backfill, switch reads, then contract, each as its own deploy.
  • Keep old and new structures in sync for every writer, or reads go silently stale.
  • Backfill in small, resumable, throttled batches.
  • Feature flags release behaviour without deploys; plan how to undo data changes before making them.
