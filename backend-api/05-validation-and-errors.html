Validation & Error Responses

Most of what an API sends back, in a busy system, is not success. Clients send bad data, ask for things that do not exist, break business rules and hit bugs. The error responses are therefore part of the product: a client developer reads them to fix their code, a mobile app reads them to show the user a sensible message, and a retry loop reads them to decide whether to try again. They are also a classic way to leak secrets.

This chapter covers validating input at the edge of the service, choosing the right status, a standard error format, and turning exceptions into responses safely. The lab sends six kinds of failure to the same endpoints under three configurations and shows exactly what a client receives.

  • Validate every input at the boundary, before business logic runs
  • Choose between 400, 404, 409, 422 and 500 consistently
  • Return RFC 9457 problem details with stable, machine-readable codes
  • Map exceptions to responses with FastAPI exception handlers
  • Keep internal details in the logs, not in responses

Validation at the boundary

Everything that arrives from outside, bodies, query strings, headers, uploaded files, IDs in the path, is untrusted until checked. Check it once, at the edge, and turn it into typed values your code can rely on: "parse, don't validate". Pydantic models do most of it: types, required fields, ranges (Field(gt=0, le=10)), lengths, patterns and enums. Add limits that protect the service itself: maximum body size, list lengths and string lengths, so nobody can post a 2 GB JSON array. Then the business logic deals only in valid values and can concentrate on business rules, such as stock levels, account status or permissions, which need the database and produce their own errors.

400 versus 422

400 Bad Request is for requests the server cannot even read: malformed JSON, the wrong content type, a broken header. 422 Unprocessable Content is for requests that parse fine but break the rules: a negative quantity, a missing field. FastAPI uses 422 for both by default, as the lab shows: broken JSON comes back as a 422 with error type json_invalid. Both are client errors and both mean "do not retry unchanged", so the distinction matters less than consistency; but it helps clients, and the problem-details configuration below separates them. Business-rule failures get their own codes: 404 for something that does not exist, 409 Conflict for a request that clashes with current state (out of stock, already cancelled), 403 for something not permitted.

Problem details

Every endpoint should fail in the same shape, so clients write one error handler. RFC 9457, "Problem Details for HTTP APIs" (2023, replacing RFC 7807), defines a standard one, sent as application/problem+json: type (a URI identifying the kind of problem, ideally a page documenting it), title (a short human summary), status, detail (this occurrence) and instance (where it happened). You may add members: a stable code, a list of field errors, and a request_id that support staff can find in the logs.

Exception handlers

FastAPI turns exceptions into responses through exception handlers, registered per exception class. Use them to keep handlers clean: business code raises meaningful exceptions (OutOfStock, OrderAlreadyShipped), and one place maps each to a status and code. Override the built-in handlers for RequestValidationError and HTTPException so they use your format too, and add a catch-all for Exception that logs everything and returns nothing internal. This is the configuration the lab calls "problem details":

PROBLEM = "application/problem+json"


def problem(status, code, title, detail, request, errors=None):
    body = {"type": "https://api.example.com/problems/" + code, "title": title, "status": status, "detail": detail,
            "instance": request.url.path, "code": code, "request_id": request.state.request_id}
    if errors:
        body["errors"] = errors
    return JSONResponse(body, status_code=status, media_type=PROBLEM)


def problem_app():
    app = FastAPI()

    @app.middleware("http")
    async def request_id(request: Request, call_next):
        request.state.request_id = "req_" + uuid.uuid4().hex[:12]
        return await call_next(request)

    @app.exception_handler(RequestValidationError)
    async def invalid(request, exc):
        bad_json = [e for e in exc.errors() if e["type"] == "json_invalid"]
        if bad_json:   # not JSON at all: the client sent something unreadable, which is a 400
            return problem(400, "malformed_json", "The request body is not valid JSON",
                           "%s at character %s" % (bad_json[0]["ctx"]["error"], bad_json[0]["loc"][-1]), request)
        errs = [{"field": ".".join(str(p) for p in e["loc"][1:]) or e["loc"][0], "code": e["type"], "message": e["msg"]} for e in exc.errors()]
        return problem(422, "validation_failed", "Your request has invalid fields", "%d field(s) failed validation" % len(errs), request, errs)

    @app.exception_handler(StarletteHTTPException)
    async def http_error(request, exc):
        codes = {404: "not_found", 405: "method_not_allowed"}
        return problem(exc.status_code, codes.get(exc.status_code, "http_%d" % exc.status_code), str(exc.detail), str(exc.detail), request)

    @app.exception_handler(OutOfStock)
    async def out_of_stock(request, exc):
        return problem(409, "out_of_stock", "Not enough stock", "Only %d of %s left" % (STOCK[exc.sku], exc.sku), request)

    @app.exception_handler(Exception)
    async def unexpected(request, exc):
        log.exception("unhandled error, request_id=%s", request.state.request_id)   # full detail goes to the logs only
        return problem(500, "internal_error", "Something went wrong", "Quote request_id %s if you contact support" % request.state.request_id, request)

Without a catch-all, an unhandled exception reaches Starlette's error middleware, which, as measured, sends a plain-text Internal Server Error, not JSON, so clients that always parse JSON fail a second time. With debug=True it sends the whole traceback instead.

Error codes clients can use

Clients branch on errors: show "sold out" for one, retry another, ask the user to log in again for a third. They need something stable to branch on. The status is too coarse (several different 409s), and the message is for humans and will be reworded or translated. A short, documented, machine-readable code such as out_of_stock or card_declined is the contract; Stripe's API is a well-known example, with a code on every error and a page documenting each. For validation errors, report every failing field at once with its path, its own code and a message.

Use case: debug mode as a way in, CVE-2021-3129

Laravel, a popular PHP framework, shows a detailed error page in debug mode, powered by a package called Ignition, with the stack trace, environment details and, in some versions, buttons that fix common problems for you. In January 2021 a researcher at Ambionics Security published CVE-2021-3129: one of those helper features could be abused, through a chain of PHP file-handling tricks, to run arbitrary code on the server, without logging in. Only sites running with debug mode enabled in production were exposed, and there were many, because enabling debug mode to diagnose a problem and forgetting to turn it off is easy. Attackers began scanning for them within days of the publication. Even without that bug, debug pages in production routinely leak source paths, configuration and secrets, as the lab's traceback shows. Debug output belongs in logs that only your team can read; the response should carry a request ID that leads there.

⚠️
Common mistakes
  • Debug mode or tracebacks in production responses.
  • Business rules surfacing as 500s because nobody mapped the exception.
  • A different error shape per endpoint, or plain text from the default handler.
  • Clients forced to parse messages because there is no stable code.
  • Reporting only the first validation error.
  • 200 with an error in the body.
  • Echoing user input into error messages unescaped, which a web client may render as HTML.

Interview drill

Explain it simply: What should an API return when something goes wrong on the server?

How a strong answer sounds
A 500, or a 503 if it is temporary, in the same JSON error format as every other error, with a generic message, a stable code such as internal_error, and a request ID. Nothing internal: no stack trace, no exception text, no SQL, no file paths, since those help attackers and can contain secrets. The full details go to the server's logs and error tracker, tagged with the same request ID, so when a customer quotes it, the team can find exactly what happened. In FastAPI that means a catch-all exception handler that logs with the request ID and returns the safe response, and never running with debug mode on in production.

Deeper: Design the error responses for a checkout API used by a web app, a mobile app and partners.

How a strong answer sounds
One format everywhere, RFC 9457 problem details as application/problem+json, with a stable code, a type URI pointing at documentation for that code, a human title and detail, a request_id, and for validation an errors array with each field's path, code and message, all reported at once. Status codes chosen by what the client should do: 400 unreadable, 422 invalid, 401 or 403 for authentication and permission, 404, 409 for conflicts such as out of stock or a price that changed, 429 with Retry-After, and 5xx only for real server failures, with 503 and Retry-After when retrying will help. Payment failures get specific codes like card_declined and insufficient_funds so apps can show the right message. Codes are documented and never renamed; messages may change and are not for parsing. Internals go only to logs, and error rates per code are monitored, since a spike in one code often reveals a broken client release.

🧠 Key takeaways

  • Validate all input at the edge into typed values; business rules come after, with their own errors.
  • 400 for unreadable requests, 422 for invalid ones, 404/409/403 for business rules, 5xx only for server failures.
  • Use one error format, RFC 9457 problem details, with a stable code and a request ID.
  • Map exceptions with handlers, including a catch-all that logs and reveals nothing.
  • Never run debug mode in production: it can leak secrets and worse.
