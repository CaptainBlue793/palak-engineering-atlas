Rate Limiting & Quotas

Every API eventually meets a client that sends too much: a script in a loop, a scraper, an attacker trying stolen passwords, a partner's batch job, a mobile app with a retry bug released to a million phones. A rate limit caps how many requests a client may make in a period, and a quota caps how much it may use over a longer one. Together they keep one client from degrading the service for everyone, make costs predictable, and slow down abuse.

The interesting part is the algorithm: "10 requests per second" can mean quite different things at the edges. The lab runs four real limiters, all set to 10 per second, against three traffic patterns.

Why limit

Limits protect four things: availability, so one heavy client cannot exhaust shared capacity; fairness between customers on the same plan; cost, for endpoints that call paid services or run expensive queries; and security, since credential stuffing, card testing and scraping all depend on volume. Choose the key to count by: an API key or user ID for authenticated traffic, an IP address only as a fallback (many users share one behind a NAT or mobile carrier), and sometimes a target, such as "login attempts for this email address". Different endpoints deserve different limits, generous for cheap reads and strict for logins, password resets and expensive exports, and some APIs limit by cost rather than count, so a heavy query uses more of the budget than a light one.

Fixed and sliding windows

  • Fixed window: count requests in each calendar second (or minute); reset at the boundary. One counter per key per window, the easiest to build, and the lab shows its flaw: a client can send a full allowance just before a boundary and another just after.
  • Sliding log: keep each request's timestamp and count those in the last second. Exact, but it stores one entry per request.
  • Sliding window counter: keep the counts of the current and previous fixed windows and weight the previous one by how much of it still overlaps the last second. Two counters per key, close to exact, and a common choice for Redis-based limiters.

Token bucket

A token bucket holds up to capacity tokens and is refilled at a steady rate; each request takes a token, and a request that finds the bucket empty is refused. It allows short bursts up to the capacity while holding the long-run average to the rate, which matches how real clients behave: a page load fires a dozen requests at once, then nothing for a while. The leaky bucket is its mirror image, smoothing output to a constant rate, and is used more for shaping traffic than for API limits.

class TokenBucket:
    """Capacity 10 tokens, refilled at 10 per second: bursts up to 10, sustained 10/s."""
    def __init__(self, capacity=LIMIT, rate=LIMIT / WINDOW):
        self.cap, self.rate, self.state = capacity, rate, {}

    def allow(self, key, now):
        tokens, last = self.state.get(key, (self.cap, now))
        tokens = min(self.cap, tokens + (now - last) * self.rate)
        if tokens >= 1:
            self.state[key] = (tokens - 1, now)
            return True, int(tokens - 1), 0.0
        self.state[key] = (tokens, now)
        return False, 0, (1 - tokens) / self.rate

Things to try.

  • fixed window, around a boundary: 20 requests allowed within a fifth of a second, twice the limit, because 10 landed in the first second's window and 10 in the second's. Switch to sliding log: never more than 10 in any second.
  • sliding window counter: close to the log with only two counters per client, a little generous at the boundary because the weighting assumes requests were spread evenly.
  • token bucket, burst then trickle: the first 10 pass at once, then roughly one in two as tokens refill, then everything once the client slows to 10 a second. Its "most in any 1 s" is above 10: by design, it allows a burst on top of the rate.
  • steady 15/s: the window limiters allow 30 of 45, the bucket 39, the extra being its initial burst capacity.

Distributed counters in Redis

A limiter that keeps counts in process memory limits each worker separately: with eight workers, a client gets eight times the limit (Chapter 1). Keep counters in a shared store, almost always Redis, and update them atomically. A fixed window is INCR on a key such as rl:{client}:{window} plus EXPIRE; a sliding log is a sorted set of timestamps, trimmed with ZREMRANGEBYSCORE and counted with ZCARD; a token bucket keeps tokens and a timestamp and must update them in one step, so it runs as a Lua script inside Redis. Decide what happens if Redis is down: usually fail open, allowing traffic, for ordinary limits, and fail closed for security limits such as login attempts. Many teams enforce coarse limits at the API gateway or CDN (Chapter 35) and fine-grained ones in the service.

429 and Retry-After

Refuse with 429 Too Many Requests, a Retry-After header in seconds, and a problem-details body with a code such as rate_limited (Chapter 5). Tell well-behaved clients where they stand on every response, so they can slow down before hitting the limit: many APIs use X-RateLimit-Limit, -Remaining and -Reset, and an IETF draft standardises RateLimit-Policy and RateLimit headers, which the lab's service sends. Clients should honour Retry-After and back off exponentially with random jitter, so a thousand clients refused at the same moment do not all retry at the same moment.

Use case: GitHub's API limits

GitHub's REST API shows the layers of a mature rate-limiting design. Unauthenticated requests are limited to 60 an hour per IP address, which is enough to try the API and far too little to scrape it; authenticated requests get 5,000 an hour per user or token, with higher limits for some GitHub Apps and enterprise accounts. Every response carries x-ratelimit-limit, x-ratelimit-remaining, x-ratelimit-used and x-ratelimit-reset, so clients can pace themselves, and a dedicated endpoint reports the current status without counting against it. On top of these primary limits, GitHub applies "secondary rate limits" to patterns that are expensive or abusive even within the hourly budget: too many concurrent requests, too many content-creating requests in a short time, or heavy CPU use, answered with 403 or 429 and a Retry-After header. The GraphQL API is limited by a points system that charges each query by how much work it asks for. Count-based limits, cost-based limits and behaviour-based limits, all communicated in headers: that is the shape most large APIs converge on.

⚠️
Common mistakes
  • Counters in process memory behind several workers or instances.
  • Limiting only by IP, punishing everyone behind one NAT and missing distributed attackers.
  • One limit for every endpoint, too loose for logins and too tight for cheap reads.
  • No Retry-After, so clients guess and hammer.
  • Non-atomic read-then-increment in Redis, letting concurrent requests slip through.
  • Clients retrying 429s immediately and in lockstep, without jitter.
  • Counting before authentication, so attackers can exhaust a victim's limit.

Interview drill

Explain it simply: How does a token bucket rate limiter work, and why use it?

How a strong answer sounds
Each client has a bucket that holds up to a fixed number of tokens and refills at a steady rate, say 10 tokens and 10 per second. Every request takes one token; if the bucket is empty, the request is refused with 429 until tokens refill. It lets a client burst, sending up to the bucket's capacity at once, which suits real clients that fire several requests together, while the refill rate caps the long-run average. It needs only two numbers per client, the tokens and the last update time, which can be updated atomically in Redis with a small Lua script so every instance of the service shares the same bucket.

Deeper: Design rate limiting for a public API with free and paid plans, plus a login endpoint under credential-stuffing attack.

How a strong answer sounds
For the API, identify clients by API key and apply per-plan token buckets in Redis, for example 10 per second with bursts of 20 for free and 100 per second for paid, plus monthly quotas tracked as fixed-window counters, with RateLimit headers and 429 with Retry-After; expensive endpoints cost more than one token. Enforce a coarse IP-based limit at the edge or CDN to absorb floods before they reach the service. For login, credential stuffing comes from many IPs trying many accounts, so limit along several keys: attempts per account (sliding log, strict, for example 5 in 15 minutes, then require a CAPTCHA or delay), attempts per IP and per IP range, and a global rate of failed logins that triggers stronger defences. Do these checks before the expensive password hash, return the same error whether or not the account exists, fail closed if Redis is unavailable, and alert on spikes. Encourage two-factor authentication and breached-password checks, since rate limits slow attacks rather than stop them.

🧠 Key takeaways

  • Limit by the right key, per endpoint, to protect availability, fairness, cost and security.
  • Fixed windows allow double bursts at boundaries; sliding windows fix it.
  • Token buckets allow bounded bursts with a steady average rate.
  • Shared, atomic counters in Redis, or the limit multiplies with every worker.
  • Answer 429 with Retry-After and rate-limit headers; clients back off with jitter.
