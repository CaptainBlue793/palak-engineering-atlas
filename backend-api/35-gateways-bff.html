API Gateways & Backends for Frontends

Once a product has several services and several kinds of client (a web app, iOS and Android apps, partners), something has to sit between them. An API gateway is the single front door: it routes requests to services and handles the concerns every request shares, such as TLS, authentication, rate limits and logging. A backend for frontend (BFF) goes further for one particular client, turning many service calls into one response shaped for exactly one screen.

This chapter explains both, and where each goes wrong. The lab loads a shopping app's home screen, profile, recent orders and recommendations, four ways over three networks, with the recommendations service healthy and slow, and measures time, round trips and bytes.

What gateways do

A gateway (Kong, Envoy-based gateways, AWS API Gateway, Azure API Management, Apigee, NGINX, Traefik) is a reverse proxy with API features. Its proper jobs are the cross-cutting ones: terminating TLS; routing by path, host or header (/orders/* to the orders service); authenticating callers and enforcing coarse authorisation such as scopes; rate limits and quotas per client; request size limits; CORS; request IDs and access logs; and canary or blue-green routing during deploys. Centralising these means each service does not reimplement them, and there is one place to see and control all traffic. What a gateway should not hold is business logic: once routing rules start transforming payloads and making decisions about orders, you have a hard-to-test service written in configuration.

Authentication at the edge

The gateway can validate the access token once, reject bad requests before they reach any service, and pass the caller's identity onward. How it passes it matters. Forwarding a plain header such as X-User-Id is only safe if services cannot be reached except through the gateway, enforced by network policy or mutual TLS, because anything that can reach a service directly could set that header itself. Stronger: forward the original token, or a short-lived internal token the gateway signs, and have services verify it. Either way, services keep their own object-level authorisation (Chapter 33); the gateway can check that a token has the orders:read scope, but only the orders service knows whether order 42 belongs to this user.

Backends for frontends

General-purpose service APIs are designed around data; screens need data from several of them, in a specific shape, at once. A mobile app calling four services directly pays four network round trips (or several waves when calls depend on each other), downloads full objects to show three fields, and must be released through app stores to change which calls it makes. A BFF, a small service owned by the client team, exposes endpoints such as GET /bff/home that call the services over the fast internal network, in parallel, and return only what the screen shows. Sam Newman popularised the pattern from its use at SoundCloud: one BFF per client experience (web, iOS, Android, or one shared mobile BFF), so each can evolve without negotiating with the others.

@app.get("/bff/home")
async def home(user: User = Depends(current_user)):
    profile, orders, recs = await asyncio.gather(
        users.get(user.id), orders_api.recent(user.id, limit=3),
        recommended_products(user.id, timeout=0.25),                    # optional: has its own deadline
        return_exceptions=True)
    degraded = []
    if isinstance(recs, Exception):
        recs, degraded = [], ["recommendations"]                   # the screen still renders
    return HomeScreen(user=profile.summary(), recent_orders=orders, recommended=recs, degraded=degraded)

Things to try.

  • 4G, healthy: four sequential calls take 609 ms, of which 320 ms is just four round trips. Calling in parallel helps, but recommendations and products must still be two waves.
  • Through the gateway: the pass-through gateway adds an extra hop costing about 1.7 ms per request here; it centralises authentication and limits but does nothing for round trips or bytes.
  • The BFF: one round trip and 0.9 KB instead of 11.1 KB, because it returns three orders' summaries rather than twenty full orders, and six product cards rather than full product records.
  • Slow recommendations: direct clients wait for the slowest service on every load. The BFF gives up on recommendations after 250 ms and returns the rest, marked as degraded, so the screen renders and fills the carousel later.

Aggregation

Aggregating in a BFF or gateway only helps if it is done carefully. Call independent services concurrently; total time is then the slowest dependency chain, not the sum. Give every call a deadline derived from the overall budget for the screen, and decide in advance which parts are essential (fail the request) and which are optional (omit them and say so in the response). Bound the fan-out with a semaphore and pool limits, so one popular screen cannot exhaust connections (Chapter 28). Cache stable parts, such as product cards, for seconds or minutes. And keep aggregation to orchestration and shaping: if the BFF starts calculating prices or deciding eligibility, that logic belongs in a service where other clients can use it too. GraphQL (Chapter 25) is an alternative that lets clients choose the shape themselves; a BFF is simpler when one team owns both the screen and its endpoint.

Gateway pitfalls

The gateway is on every request, so its mistakes are everyone's. It is a single point of failure: run several instances across zones, keep its configuration in version control with review and staged rollout, and test config changes like code. It adds latency, small per hop but multiplied when gateways are chained or plugins do heavy work. Timeouts must nest: the gateway's must be longer than the services' and shorter than the clients', or requests are abandoned while work continues. Retries at the gateway multiply with retries in services and clients (Chapter 29), and must never apply to non-idempotent requests without idempotency keys. A gateway that becomes the place for business rules turns into a bottleneck team. And services that trust identity headers without verifying where they came from are only as secure as the network around them.

Use case: SoundCloud and the backend-for-frontend pattern

SoundCloud is the company most associated with the BFF pattern. As it moved from a single Ruby on Rails application towards microservices, its web, iOS and Android clients were all calling one general-purpose public API, and every change to what a screen needed became a negotiation between client teams and that API's owners. Phil Calçado, then at SoundCloud, has written about how teams instead built a separate backend for each client experience, owned by the team that built the client, which called the internal services and returned data shaped for that app's screens. In 2015 Sam Newman wrote it up as the "Backends For Frontends" pattern, crediting Calçado and SoundCloud, and the name stuck. The benefits SoundCloud described match the lab: fewer round trips and smaller payloads for mobile clients, and client teams able to change their own endpoints without waiting for anyone else. The costs are the ones to watch: duplicated code across BFFs, and logic drifting into them that should live in services.

⚠️
Common mistakes
  • Business logic in gateway configuration or plugins.
  • Services trusting identity headers while reachable without the gateway.
  • A single gateway instance, or configuration changes without review and staged rollout.
  • Sequential calls in a BFF, or no deadline on optional parts.
  • Retries at every layer, including for non-idempotent requests.
  • One giant BFF for every client, which recreates the general-purpose API.
  • Returning whole objects to mobile clients that show three fields.

Interview drill

Explain it simply: What is the difference between an API gateway and a backend for frontend?

How a strong answer sounds
A gateway is the shared front door for all clients: it terminates TLS, routes requests to services, validates tokens, applies rate limits and records logs, the concerns every request has in common, and it should contain no business logic. A backend for frontend is a small service for one client experience, such as the mobile app, that calls several services in parallel and returns exactly the data one screen needs in one response. The gateway reduces duplication of cross-cutting concerns; the BFF reduces round trips and payload size for a specific client and lets that client's team change its API without negotiating with every other client. They usually work together: client, gateway, BFF, services.

Deeper: Design the API layer for a shopping app with web, iOS and Android clients and twelve backend services.

How a strong answer sounds
A managed or Envoy-based gateway in front, run in several zones, handling TLS, routing, token validation with scopes, per-client rate limits, request IDs and access logs, with its configuration in Git and rolled out in stages. Behind it, one BFF for web and one shared mobile BFF, owned by the client teams, exposing screen-level endpoints such as home, product page and checkout. Each BFF calls services concurrently with per-call deadlines from the screen's budget, marks optional parts as degraded instead of failing, caches stable data briefly and limits fan-out. Services sit on a private network, accept traffic only through mutual TLS, verify a signed identity or the original token, and enforce object-level authorisation and business rules themselves. Retries live in one layer only, with idempotency keys for writes. I would trace across all layers, watch each BFF endpoint's p99, and keep pricing or eligibility logic in services so all clients share it.

🧠 Key takeaways

  • A gateway centralises cross-cutting concerns; it should hold no business logic.
  • Authenticate at the edge, but services must still verify identity and own authorisation.
  • A BFF turns many client round trips into one screen-shaped response.
  • Aggregate in parallel, with deadlines and explicit partial responses.
  • Run gateways redundantly, nest timeouts, and retry in one layer only.
