File Uploads & Object Storage

Profile photos, invoices, spreadsheets, videos: sooner or later users send files. Files are unlike JSON bodies in two ways. They can be big, so code that casually holds a whole one in memory can exhaust a server with a few concurrent uploads. And they are opaque bytes chosen by whoever sends them, so a file called holiday.jpg may be a script, a program or a bomb designed to crash whatever opens it.

This chapter covers receiving uploads without loading them into memory, sending large files straight to object storage with presigned URLs, validating what a file really is, and serving downloads safely. The lab measures a real server's memory during uploads of up to 300 MB, and runs a real image and five disguised files through four validators.

  • Accept multipart uploads with FastAPI's UploadFile
  • Stream large files instead of reading them into memory
  • Use presigned URLs to upload directly to object storage
  • Validate files by their content, with size and pixel limits
  • Serve downloads without letting files attack your users

Multipart form data

Browsers and most clients upload files as multipart/form-data: the body is split into parts by a boundary string, each with its own headers (a field name, a filename, a content type) and bytes. FastAPI handles it with UploadFile (it needs the python-multipart package). Starlette parses the stream into a temporary file that stays in memory up to 1 MB and spills to disk beyond that, so receiving is already efficient; what matters is what your handler then does with it. Alternatively, a client can PUT the file as the raw request body with its own Content-Type, which is simpler for APIs and is what object stores expect.

@app.post("/upload/read-all")
async def read_all(file: UploadFile = File(...)):
    data = await file.read()                         # the whole file in memory
    with open(os.path.join(OUT, "u1.bin"), "wb") as f:
        f.write(data)
    return {"bytes": len(data)}


@app.post("/upload/chunked")
def chunked(file: UploadFile = File(...)):
    with open(os.path.join(OUT, "u2.bin"), "wb") as f:
        shutil.copyfileobj(file.file, f, length=1024 * 1024)   # 1 MiB at a time
    return {"bytes": os.path.getsize(os.path.join(OUT, "u2.bin"))}


@app.put("/upload/raw-body")
async def raw_body(request: Request):
    data = await request.body()                      # a raw upload, all in memory
    with open(os.path.join(OUT, "u3.bin"), "wb") as f:
        f.write(data)
    return {"bytes": len(data)}


@app.put("/upload/raw-stream")
async def raw_stream(request: Request):
    n = 0
    with open(os.path.join(OUT, "u4.bin"), "wb") as f:
        async for chunk in request.stream():         # chunks as they arrive
            f.write(chunk); n += len(chunk)
            if n > 500 * 1024 * 1024:
                raise HTTPException(413, "File too large")
    return {"bytes": n}

Streaming large files

await file.read() and await request.body() return the whole file as one bytes object, in memory. That is fine for an avatar and dangerous for anything big: ten people uploading 300 MB at once means gigabytes of memory, and the container is killed. Copy in chunks instead, from file.file to the destination, or iterate request.stream() for raw uploads, and count bytes as they arrive so you can stop at a limit with 413 Content Too Large rather than after the whole file has arrived. Set a body-size limit at the proxy too (Prerequisite 8).

  • decode with Pillow: only the real photo passes; the bomb is refused before its 2.5 billion pixels are allocated.

Presigned URLs

Large files should not pass through your API servers at all. Store them in object storage, such as Amazon S3, Google Cloud Storage, Azure Blob Storage or a compatible service, and let clients upload directly. The API checks the user may upload, chooses the object key (never the user's filename), and returns a presigned URL: a URL signed with the service's credentials that allows one operation, such as PUT to that key, with a given content type and size range, for a few minutes. The client uploads straight to storage; storage sends an event, or the client calls back, and a background job validates and processes the file. Downloads work the same way, with short-lived signed GET URLs, so private files never need public buckets.

import boto3, uuid
s3 = boto3.client("s3")

@app.post("/uploads", status_code=201)
def start_upload(body: UploadRequest, user: User = Depends(current_user)):
    key = f"incoming/{user.id}/{uuid.uuid4()}"               # our name, not the client's
    post = s3.generate_presigned_post("acme-uploads", key,
        Conditions=[["content-length-range", 1, 20 * 1024 * 1024], {"Content-Type": "image/jpeg"}],
        Fields={"Content-Type": "image/jpeg"}, ExpiresIn=300)    # 20 MB max, 5 minutes
    uploads.create(key=key, owner=user.id, status="pending")
    return {"key": key, "url": post["url"], "fields": post["fields"]}

Validating files

The filename and the Content-Type of an upload are claims made by the uploader; the lab shows they prove nothing. Validate by content: check the magic bytes as a first, cheap filter, then parse the file with a library that understands the format, under limits on size, pixel count, page count or archive expansion. For images, the strongest step is to re-encode them, decoding and writing a fresh JPEG or PNG, which strips anything hidden in the original along with metadata such as GPS coordinates. Run heavy processing in a background job, in a sandbox if the format is complex, and scan documents for malware where the risk warrants it. Allow-list formats; SVG, HTML and anything executable deserve special care, because browsers run scripts inside them.

Serving downloads

A file a user uploaded can attack other users when it is served. Serve user content from a separate domain (usercontent.example.com), so scripts in it cannot read your main site's cookies; set Content-Type from your validated format, not the original upload; send X-Content-Type-Options: nosniff so browsers do not guess; use Content-Disposition: attachment; filename="..." for anything that should download rather than display, with the filename sanitised; and check authorisation on every download, or use short-lived presigned URLs, never guessable public paths.

Use case: ImageTragick, 2016

In May 2016 researchers disclosed a set of vulnerabilities in ImageMagick, the image-processing library behind countless web services' thumbnail and resize features, nicknamed "ImageTragick" (the most serious was CVE-2016-3714). ImageMagick decides how to handle a file by looking at its content and supports many formats, including some, such as its MVG drawing format, that can make it run external commands. A file uploaded as avatar.jpg but containing crafted MVG or SVG content could therefore make the server execute commands of the attacker's choosing, simply by being resized. Exploits appeared in the wild within days. The published mitigations were the ones in this chapter: verify that the file's magic bytes match an allowed image format before handing it to ImageMagick, and use ImageMagick's policy.xml to disable the formats ("coders") a service does not need. The broader lesson is that file processing libraries parse hostile input, so restrict what reaches them, limit what they may do, and run them somewhere a compromise is contained.

⚠️
Common mistakes
  • await file.read() or request.body() on large uploads.
  • No size limit, or a limit checked only after the whole file has arrived.
  • Trusting the filename or Content-Type to decide what a file is.
  • Using the uploader's filename as a storage path, inviting path traversal and overwrites.
  • Serving uploads from the main domain without nosniff or Content-Disposition.
  • Public buckets for private files.
  • Processing images or documents in the request, with no pixel or page limits.

Interview drill

Explain it simply: How should a service accept a 2 GB video upload?

How a strong answer sounds
Not through the API servers. The client asks the API to start an upload; the API checks the user may upload, picks a storage key, records a pending upload, and returns a presigned URL for object storage, limited to that key, a size range and a few minutes, using multipart upload for a file that large so parts can be retried. The client uploads straight to storage. When storage reports the upload complete, a background job checks the file is really a video in an allowed format, within limits, and transcodes it, then marks it ready. Downloads use short-lived signed URLs. If files must pass through the service, it streams them in chunks to storage with a byte counter and a hard limit, never reading them whole into memory.

Deeper: Users can upload profile pictures that other users see. What can go wrong, and how do you defend against it?

How a strong answer sounds
An attacker can upload HTML or SVG with scripts disguised as an image, which runs in other users' browsers if served inline from our domain; a polyglot or malformed file that exploits the image library; a decompression bomb that exhausts memory when decoded; a huge file that fills storage; or an image whose metadata leaks the uploader's location. Defences: limit size at the edge and in the presigned policy; allow only JPEG, PNG and WebP; validate by decoding with a pixel limit in a background job, then re-encode to a fresh file at a fixed maximum size, which also strips metadata; store under our own keys; serve from a separate cookie-less domain or CDN with the correct Content-Type and nosniff; and keep the image library patched and its formats restricted. Moderation for abusive content is a separate pipeline.

🧠 Key takeaways

  • Never read large uploads into memory; stream in chunks with a running size limit.
  • For big files, presigned URLs send bytes straight to object storage.
  • Filenames and Content-Type prove nothing; validate by decoding with limits, and re-encode images.
  • Store under your own keys and process in background jobs.
  • Serve user files from a separate domain, with nosniff, Content-Disposition and signed URLs.
