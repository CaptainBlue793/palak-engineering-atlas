Webhooks

A webhook is an API call in reverse: instead of a client asking "has the payment succeeded yet?" every few seconds, the service that knows calls the client's URL the moment it happens. Payment providers, Git hosts, messaging platforms and shops all use them, and sooner or later your service will both send and receive them.

The mechanism is just an HTTP POST, and that is the problem. Anyone on the internet can POST to a URL, deliveries fail and get retried, events arrive twice or out of order, and a slow receiver makes the sender give up. This chapter covers delivery, signatures, replay protection and receiving safely. The lab sends real signed deliveries, genuine and malicious, to three receivers.

  • Choose between webhooks and polling
  • Deliver webhooks reliably with retries and backoff
  • Sign payloads with HMAC and verify the raw body
  • Reject replays with timestamps and deduplicate by event ID
  • Receive webhooks quickly and process them asynchronously

Push versus poll

Polling, a client asking repeatedly, is simple and needs nothing from the client but outgoing requests; but most polls return nothing new, and changes are seen only at the next poll. Webhooks deliver changes immediately and only when they happen, but the client must run a public HTTPS endpoint, handle retries and duplicates, and cope with missed deliveries. The robust design offers both: webhooks for speed, and a list endpoint, ideally a cursor-paginated feed of events (Chapter 8), so clients can catch up after downtime and reconcile. Many providers send "thin" webhooks containing just the event type and an ID, and let the receiver fetch the current state through the API, which also sidesteps out-of-order delivery.

Delivery and retries

On the sending side, a webhook is a background job (Chapter 20): record the event in the same transaction as the change, then deliver it from a worker. Treat any 2xx response as success and anything else, including timeouts, as failure; retry with exponential backoff and jitter over hours or days (Stripe, for example, retries for up to three days in live mode); give each event a stable ID that stays the same across retries; disable endpoints that fail for too long and tell their owners; and let customers see delivery attempts and replay events from a dashboard. Delivery is at least once, so every receiver must expect duplicates.

Signing payloads

A receiver needs to know a request really came from the sender and was not altered. The standard answer is an HMAC signature: the sender and receiver share a secret per endpoint; the sender computes HMAC-SHA256 of a timestamp and the exact body bytes, and sends it in a header; the receiver recomputes it over the bytes it received and compares in constant time. The lab's sender uses a t=<timestamp>,v1=<hex> header in the style of Stripe's:

def sign(raw: bytes, ts: int, secret: bytes = SECRET) -> str:
    mac = hmac.new(secret, b"%d." % ts + raw, hashlib.sha256).hexdigest()
    return "t=%d,v1=%s" % (ts, mac)

Verify the raw body, not a parsed and re-encoded copy: JSON libraries change whitespace, key order and number formats, so re-serialising produces different bytes and a different signature. The lab's second receiver makes exactly this mistake.

Simulator: six deliveries, three receivers

A payment.succeeded event for order ord_8812 is delivered in six ways: genuine; with the amount edited to 1 pence but the original signature; signed with a guessed secret; a genuine delivery captured ten minutes ago and replayed; the same event delivered twice by a retrying sender; and with no signature. The trusting receiver just parses the JSON; the re-serialising receiver verifies a signature over json.dumps of the parsed body; the proper receiver verifies the raw bytes, checks the timestamp against a 5-minute tolerance and deduplicates by event ID.

Things to try.

  • trusting receiver: every delivery is processed, including the one claiming a £0.01 payment and the unsigned one. Anyone who learns the URL can mark orders as paid.
  • verifies re-serialised JSON: everything is rejected, including the genuine delivery. The sender wrote compact JSON; json.dumps adds spaces after commas and colons, so the bytes, and the HMAC, differ. Secure by accident, broken in practice.
  • proper: the genuine delivery is processed; edits and forgeries fail the signature; the ten-minute-old replay passes the signature but fails the timestamp check; the duplicate is acknowledged with 200, so the sender stops retrying, but processed only once.

Replay protection

A valid signed request can be captured, from a log, a proxy or a compromised network, and sent again. Two defences work together. The timestamp is inside the signed material, so it cannot be changed; reject deliveries whose timestamp is more than a few minutes from now. Within that window, deduplicate by event ID: record processed IDs with a unique constraint, and answer duplicates with 200 without acting. Deduplication also handles the sender's own legitimate retries.

Receiving webhooks

Senders wait only a few seconds for a response. A receiver that does its work inline, generating an invoice or calling other services, will time out, the sender will retry, and the work will run again. Measured with a real sender that waits 1 second and retries up to four times, against a receiver whose work takes 1.5 seconds:

ReceiverEventsDeliveries the sender madeTimes the work ranWhat the sender saw
Work done inline52020Timeouts on every attempt
Acknowledge, then work in the background (deduplicated)555200 in about 30 ms

So: verify the signature, record the event (deduplicated) or enqueue a job, return 2xx at once, and process asynchronously. Handle events in any order, for example by ignoring an older state change that arrives after a newer one, or by fetching the current state from the API. Keep each endpoint's secret in a secret store and support two secrets at once so it can be rotated, and never log full payloads or signatures.

Use case: the Standard Webhooks specification

For years every provider signed webhooks its own way: different header names, different signed material, hex in one place and base64 in another, with or without a timestamp. Receivers wrote and maintained a verifier per provider, and many got at least one of them wrong, typically by verifying a re-serialised body or skipping the timestamp. In late 2023 a group of companies that send webhooks at scale, led by the webhook-delivery company Svix and joined by contributors from firms such as Zapier, Twilio, ngrok, Supabase and Kong, published Standard Webhooks, an open specification with reference libraries in many languages. It fixes the choices this chapter describes: a webhook-id header for deduplication, a webhook-timestamp for replay protection, and a webhook-signature carrying an HMAC-SHA256 over the ID, the timestamp and the raw body, with support for several signatures at once so secrets can be rotated. If you are designing webhooks today, following it means your customers can verify your deliveries with an existing library instead of writing their own.

⚠️
Common mistakes
  • Unverified webhook endpoints that act on anything posted to them.
  • Verifying a re-serialised body instead of the raw bytes.
  • Comparing signatures with == instead of a constant-time comparison.
  • No timestamp check or deduplication, so replays and retries are processed again.
  • Doing slow work before responding, causing timeouts and retries.
  • Assuming events arrive in order.
  • Sending webhooks from the request path instead of a queue with retries.

Interview drill

Explain it simply: How do you know a webhook really came from the provider?

How a strong answer sounds
The provider and I share a secret for my endpoint. When it sends a webhook, it computes an HMAC-SHA256 of the timestamp and the exact body bytes with that secret and puts it in a header. My endpoint reads the raw body before parsing it, recomputes the HMAC with the same secret, and compares the two in constant time; if they differ, the request was not from the provider or was altered, and I reject it. Because the timestamp is part of the signed data, I also reject deliveries older than a few minutes, and I deduplicate by event ID so a captured or retried delivery is not processed twice.

Deeper: Design the webhook system for your platform's customers.

How a strong answer sounds
When something happens, the change and an event row are written in one transaction (an outbox, Chapter 30), each event with a stable ID. A dispatcher creates one delivery per subscribed endpoint and workers send them as background jobs, signed following Standard Webhooks: ID, timestamp and HMAC-SHA256 of the raw body, with per-endpoint secrets that can be rotated with an overlap. Short timeouts, any 2xx is success, retries with exponential backoff and jitter for up to a few days, per-endpoint concurrency limits so one slow customer cannot block others, and automatic disabling with an email after prolonged failure. Customers get a dashboard of attempts with responses, manual replay, a test-event button, and an events list endpoint with cursors to reconcile. Payloads are thin or versioned so evolving them does not break receivers, and the sender only connects to public addresses, to avoid being used to probe internal networks.

🧠 Key takeaways

  • Webhooks push changes immediately; pair them with a list or events endpoint for catch-up.
  • Send from a queue with stable event IDs and backoff retries; delivery is at least once.
  • Sign with HMAC over the timestamp and raw body; verify raw bytes in constant time.
  • Reject stale timestamps and deduplicate by event ID.
  • Acknowledge quickly and process asynchronously, tolerating any order.
