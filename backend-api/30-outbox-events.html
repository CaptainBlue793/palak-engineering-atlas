The Outbox Pattern & Reliable Events

When an order is placed, other parts of the system need to know: the warehouse must ship it, the email service must confirm it, analytics must count it. The natural design is to save the order and then publish an "order placed" event to a message broker. That is two writes to two systems, and no transaction spans both. A crash between them, or a rollback after the publish, and the database and the events disagree for good: an order that never ships, or a shipment for an order that does not exist.

This chapter explains the dual-write problem and its standard solution, the transactional outbox, together with relaying, idempotent consumers and change data capture. The lab runs 500 orders through four designs with crashes injected at the dangerous moments, and counts what went wrong.

The dual-write problem

A database transaction makes its own writes atomic; it cannot include a write to Kafka, RabbitMQ, SQS, another service or an email provider. So any code that writes to the database and to a broker has a gap, and each order of operations fails in its own way. Commit, then publish: if the process dies, is redeployed, or the broker is down after the commit, the event is lost and nothing downstream ever hears about the order. Publish, then commit: if anything later in the transaction fails, the event describes something that never happened. Distributed transactions (two-phase commit) exist, but most brokers and cloud services do not support them, and they couple every system's availability together. The lab shows both failure modes.

Transactional outbox

The fix is to stop writing to two systems in the request. Write the event as a row in an outbox table, in the same database transaction as the business change. Either both commit or neither does: no lost events, no phantom events. A separate process, the relay, then reads the outbox and publishes to the broker.

def place_order(session, order_in) -> Order:
    with session.begin():                                    # one transaction
        order = Order(id=new_id("ord"), total_cents=order_in.total_cents, ...)
        session.add(order)
        session.add(OutboxEvent(id=uuid4(), topic="orders", type="order.placed",
                                aggregate_id=order.id, payload=OrderPlaced.from_order(order).model_dump_json()))
    return order                                                   # no broker call here at all

Relaying the outbox

The relay polls for unsent rows in order, publishes each, then marks it sent (or deletes it). It can crash between publishing and marking, so after a restart it publishes that row again: the outbox gives at-least-once delivery, never at-most-once. Details that matter: publish rows for the same aggregate (the same order) in commit order, so consumers do not see "shipped" before "placed"; in PostgreSQL, claim batches with SELECT ... FOR UPDATE SKIP LOCKED so several relay instances do not send the same rows; keep each event's ID stable so duplicates can be recognised; delete or archive sent rows so the table stays small; and alert when the oldest unsent row is too old, which means the relay or the broker is stuck.

Simulator: 500 orders, four designs

Orders are written to one SQLite database; events go to a second database standing in for the broker, so, as with a real broker, no transaction can span both. Across 500 orders, the process crashes right after committing 5% of the time, and 5% of orders fail late in their transaction (a stock check, say) and roll back. In the outbox designs, the relay also dies between publishing and marking a row 3% of the time. A consumer then ships an order for every event it receives.

Things to try.

  • commit, then publish: every crash after a commit left an order in the database that the warehouse never heard about. No error was logged anywhere it would be noticed.
  • publish, then commit: no events lost, but every late failure had already published its event, so the warehouse shipped orders that were rolled back.
  • transactional outbox: nothing lost and nothing invented, but a few orders were shipped twice: the relay published them, died before marking them sent, and published them again after restarting.
  • + idempotent consumer: the consumer records each event ID it has handled and skips repeats. Every committed order shipped exactly once.

Idempotent consumers

Because the relay, the broker and the consumer's own retries all deliver at least once, every consumer must cope with duplicates. Record each handled event ID in a table with a unique constraint, in the same transaction as the consumer's own changes (an "inbox"), and skip IDs already present; or make the operation naturally idempotent, such as "set order status to shipped" rather than "increment shipments". Together, an outbox on the producer and an inbox on the consumer give effectively-once processing over at-least-once delivery, the same combination as Chapter 20's jobs.

Change data capture

Instead of polling, a relay can read the database's own change log, PostgreSQL's write-ahead log or MySQL's binlog, and turn committed changes into events. This is change data capture (CDC), and Debezium is the best-known open-source implementation. Pointed at the outbox table, CDC gives low latency and no polling load while keeping the explicit, versioned event design of the outbox. Pointed at ordinary business tables, it streams every change without application code, but couples consumers to your internal schema, so most teams prefer CDC on an outbox.

Use case: Debezium's outbox event router

The outbox pattern became mainstream partly through tooling. In 2019 Gunnar Morling of Red Hat, then lead of the Debezium project, published "Reliable Microservices Data Exchange With the Outbox Pattern" on the Debezium blog. It laid out the problem this chapter measures, services that update their database and send messages to Kafka and end up inconsistent when one of the two fails, and showed the outbox as the answer: write events to an outbox table in the same transaction, and let Debezium read the committed inserts from the database's transaction log and route them to Kafka topics, with the outbox row's ID as the event ID and its aggregate ID as the message key, so all events for one order stay in order on one partition. Debezium shipped an "outbox event router" to do exactly that. The approach is now common across languages and stacks, and the pieces are the ones in this chapter: one local transaction, a relay reading only committed data, stable IDs, per-aggregate ordering, and consumers that tolerate repeats.

⚠️
Common mistakes
  • Publishing to a broker inside a request, before or after the commit.
  • An outbox row written in a different transaction from the change it describes.
  • Consumers that assume exactly-once delivery.
  • Relays that publish out of order for the same aggregate.
  • Several relay instances claiming the same rows without locking.
  • An outbox that is never cleaned up, or a stuck relay that nobody alerts on.
  • Events that expose internal table structure instead of a designed, versioned schema.

Interview drill

Explain it simply: What is the transactional outbox pattern and what problem does it solve?

How a strong answer sounds
When a service changes its database and also needs to publish an event, those are two writes to two systems with no shared transaction, so one can succeed while the other fails: commit then crash, and the event is lost; publish then roll back, and the event describes something that never happened. The outbox pattern writes the event as a row in an outbox table inside the same database transaction as the change, so they commit or fail together. A separate relay reads committed outbox rows and publishes them to the broker, marking them sent. The relay can crash between publishing and marking, so delivery is at least once, and consumers must be idempotent, typically by recording processed event IDs.

Deeper: Orders, payments and shipping are separate services. Design how "order placed" leads to payment and shipping reliably.

How a strong answer sounds
The orders service writes the order and an order.placed outbox row in one transaction, and a relay, polling with SKIP LOCKED or Debezium CDC, publishes to a topic keyed by order ID so events for one order stay ordered. The payments service consumes it, records the event ID in an inbox table in the same transaction as creating the payment attempt, calls the provider with an idempotency key derived from the order, and writes payment.succeeded or payment.failed to its own outbox. Orders consumes those to update status, shipping consumes payment.succeeded the same way. Each step is local, idempotent and retried; failures become compensating events such as refunds or cancellations rather than distributed rollbacks (a saga). I would monitor outbox age and consumer lag per topic, dead-letter poison messages with alerts, and run a daily reconciliation that compares orders, payments and shipments.

🧠 Key takeaways

  • Writing to a database and a broker is two writes; no ordering of them is safe on its own.
  • Write events to an outbox table in the same transaction as the change.
  • A relay publishes committed rows, in order per aggregate, at least once.
  • Consumers deduplicate by event ID in the same transaction as their own changes.
  • CDC on the outbox table gives low-latency relaying without polling.
