Deploying a Service

A deploy replaces running instances of your service with new ones while customers are using it. Done carelessly, every deploy is a small outage: requests cut off mid-flight, requests sent to instances that are not ready, and a schema change that the old code cannot handle. Done well, deploys are boring enough to run many times a day. The difference is a few specific behaviours in the service itself and in how the platform replaces it.

This chapter covers a production container image, liveness and readiness checks, graceful shutdown, migrations at deploy time and rollbacks. The lab runs a rolling deploy of two instances under steady load three ways and counts every failed request.

  • Build a small, safe production container for a Python service
  • Separate liveness from readiness and implement both
  • Shut down gracefully: stop taking work, finish in-flight requests, then exit
  • Run database migrations so old and new code both work
  • Roll back quickly, and know what a rollback cannot undo

A production container

A good image is small, reproducible and runs as an unprivileged user. Use a slim official base pinned to a version, install dependencies from a lock file in their own layer so code changes do not reinstall them, copy only what the app needs, and run the server directly (not through a shell) so it receives signals. Configuration comes from the environment, secrets from the platform's secret store, and logs go to standard output as JSON (Chapter 31). Scan the image in CI and rebuild it regularly for base-image security fixes.

FROM python:3.12-slim AS base
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app
COPY requirements.lock .
RUN pip install --no-cache-dir -r requirements.lock         # cached until the lock file changes
COPY app/ app/
RUN useradd --uid 10001 --no-create-home appuser
USER 10001                                                  # never run as root
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--timeout-graceful-shutdown", "20"]

Health and readiness

Platforms ask two different questions, and mixing them up causes outages. Liveness: is this process healthy, or should it be restarted? Answer it cheaply and locally, from the process itself; if a liveness check calls the database, a database blip restarts every instance at once. Readiness: should this instance receive traffic right now? It is false while the instance warms up (loading configuration, filling caches, opening pools), true when it can serve, and false again as soon as it starts shutting down. Kubernetes has a third, the startup probe, for slow-starting apps. Load balancers route only to ready instances; the deploy moves on only when new instances are ready.

@app.get("/live")
def live():
    return {"ok": True}                                              # the process answers: that is all

@app.get("/ready")
def ready(response: Response):
    if not state.warm or state.draining:
        response.status_code = 503
    return {"warm": state.warm, "draining": state.draining}

Graceful shutdown

When the platform stops an instance it sends SIGTERM, waits a grace period, then kills it. A graceful shutdown uses that window: fail readiness so the load balancer stops sending new requests, keep serving for a moment while that change propagates (in Kubernetes, a short preStop sleep), then stop accepting connections, let in-flight requests finish, close pools and flush telemetry, and exit. Uvicorn does the middle part on SIGTERM, bounded by --timeout-graceful-shutdown; the readiness flip and the delay before it are yours to add. Long-running work does not belong in requests at all: background jobs (Chapter 20) must be resumable, because some shutdown will always interrupt one.

Simulator: a rolling deploy under load

Two instances of a FastAPI service each take 1.5 seconds to warm up after starting, during which they answer 503. Eight client threads send a steady stream of 50 ms requests, spread over the instances by a load balancer. The deploy replaces version 1 with version 2 one instance at a time, three ways. Hard kill: kill the process, start the new one, move on when its port is open. Graceful: trigger uvicorn's graceful shutdown, start the new one, move on when its port is open; the load balancer has no health checks. Graceful + readiness: fail readiness first, let the balancer (checking /ready every 100 ms) remove the instance, then shut down gracefully, and move on only when the new instance is ready.

Things to try.

  • hard kill: requests in progress at the moment of the kill were cut off, and then the new instance, reachable but still warming up, answered 503 to everything sent to it.
  • graceful shutdown: no request was cut off, but there were even more 503s. Moving on as soon as a port opens meant the second instance was taken down while the first was still warming, so for a while neither could serve.
  • graceful + readiness: zero failures. Traffic shifted from v1 to v2 one instance at a time. The deploy took longer, because it waited for each new instance to be ready: that wait is the point.

Migrations at deploy time

During a rolling deploy, old and new versions of the code run at the same time against the same database, so every schema change must work with both. That rules out renaming or dropping a column that the old code still reads, in one step; Chapter 37 covers the expand-and-contract sequence that makes such changes safe. Run migrations as their own step before the new code rolls out (a CI job or a one-off Kubernetes Job), not on application start-up, where several instances race to migrate at once. Keep each migration small and fast: on large PostgreSQL tables add columns as nullable or with constant defaults, create indexes CONCURRENTLY, set a lock_timeout so a migration that cannot get its lock fails instead of queueing every query behind it, and backfill data in batches outside the migration.

Rollbacks

A rollback redeploys the previous version, and should be one command or button, rehearsed. Make it cheap by keeping images immutable and tagged by commit, deploying gradually (a canary instance or a small percentage of traffic first, watching error rate and latency, Chapter 31), and stopping automatically when they get worse. Know what a rollback cannot undo: data the new version wrote in a new format, messages it published, emails it sent and migrations that dropped something. That is why schema changes are additive and separately deployed, and why risky behaviour goes behind a feature flag that can be turned off without a deploy.

Use case: Knight Capital's deployment, 2012

On 1 August 2012 Knight Capital, then one of the largest traders in US equities, lost more than $460 million in roughly 45 minutes, according to the US Securities and Exchange Commission's later order, which describes the cause. New code for a retail trading programme was deployed to eight servers by hand, and one server was missed. The new release reused a configuration flag that had once activated an old, long-unused function called Power Peg; on the server still running old code, the flag woke that function up, and it sent millions of orders into the market. There was no automated, verified deployment, no check that all servers ran the same version, and no quick, rehearsed way to stop or roll back; early responses even made it worse by removing the new code from the correct servers. The lessons are this chapter's: deploy the same immutable artefact everywhere by automation, verify what is running, remove dead code instead of leaving it behind flags, and be able to stop a bad release in minutes.

⚠️
Common mistakes
  • Liveness checks that call the database, so a blip restarts every instance.
  • No readiness check, or treating "port open" as ready.
  • Ignoring SIGTERM, or starting the server through a shell that does not pass it on.
  • Running migrations on application start-up from every instance.
  • Destructive schema changes in the same deploy as the code that stops using them.
  • Mutable image tags such as latest in production.
  • A rollback procedure nobody has ever run.

Interview drill

Explain it simply: What is the difference between a liveness check and a readiness check?

How a strong answer sounds
Liveness asks whether the process should be restarted: it should be a cheap check that the process itself is responsive, with no calls to dependencies, otherwise a database problem restarts every instance at once. Readiness asks whether the instance should receive traffic now: it is false while the instance warms up, true when it can serve, and false again when it starts shutting down, so the load balancer stops sending it requests. During a deploy, the platform only moves on when new instances are ready, and drains old ones by failing their readiness before stopping them.

Deeper: Every deploy of your service causes a burst of 502 and 503 errors. How do you get to zero?

How a strong answer sounds
First find which phase the errors come from with logs and load-balancer metrics: requests cut off on old instances, or requests sent to new instances before they are ready. For the old instances: handle SIGTERM by failing readiness immediately, wait a few seconds for the balancer to notice (a preStop sleep in Kubernetes), then stop accepting connections, finish in-flight requests within a grace period longer than the slowest normal request, and exit; make sure the server process actually receives the signal. For the new ones: a readiness endpoint that is false until caches and pools are warm, and a rollout that waits for it, with maxUnavailable at zero and enough surge capacity. Check keep-alive timeouts too, so the balancer does not reuse connections the app is closing. Then canary each deploy and alert if error rate rises, and keep migrations backward compatible so old and new versions can share the database.

🧠 Key takeaways

  • Ship a small, pinned, non-root image that receives signals directly.
  • Liveness is local and cheap; readiness says whether to send traffic now.
  • On SIGTERM, fail readiness, finish in-flight work, then exit.
  • Migrate as a separate, backward-compatible step before rolling out code.
  • Deploy gradually and keep a rehearsed one-step rollback; know what it cannot undo.
