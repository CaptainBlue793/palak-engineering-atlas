Debugging a Service in Production

Production problems rarely announce their cause. You get a symptom: p99 latency doubled, a wave of 500s, memory climbing until the container restarts, an outage that does not end when its trigger does. Debugging in production means going from symptom to cause with the evidence the system already produces, quickly and without making things worse, and fixing the immediate harm before the root cause.

This chapter gives a method and four of the most common culprits: slow endpoints, connection pool exhaustion, memory growth and retry storms. Each was reproduced for the lab and measured before and after its fix, together with the evidence that pointed to it.

  • Start from user-visible symptoms and narrow down methodically
  • Find a slow endpoint's cause with traces and query plans
  • Recognise connection pool exhaustion and the leak behind it
  • Find the line that allocates growing memory
  • Stop a retry storm and prevent the next one

Start from symptoms

Begin with what users experience, from the RED metrics: which routes, how much error rate or latency, since when. Then narrow the scope with three questions. What changed? A deploy, a config change, a feature flag, a traffic shift, a dependency's incident: check the change log first, because most incidents follow a change. Where? All instances or one, one region, one tenant, one endpoint, one kind of request. Which resource? Use the USE checklist (Chapter 32): CPU, memory, connection pools, threads, queues, database, downstream APIs. Mitigate as soon as you have a plausible cause, by rolling back, turning off a flag, shedding load or scaling out, and keep investigating afterwards. Write a timeline as you go; it becomes the post-incident review.

Slow endpoints

If one route's latency rose, open slow traces for it (Chapter 31) and compare them with normal ones: a single span that grew points to a dependency or a query; many more spans points to an N+1 loop; a long gap with no child spans points to CPU work or waiting for a pool. For a slow query, look at the plan (EXPLAIN ANALYZE in PostgreSQL, EXPLAIN QUERY PLAN in SQLite) and at the database's own statistics (pg_stat_statements). The classic causes are a missing index, a query that stopped using one after data grew or statistics went stale, and a lock held by something else.

Pool exhaustion

When every request needs a database connection and none are free, requests wait in the pool queue and then fail with a pool timeout, including requests that have nothing wrong with them. The signature is distinctive: many timeouts at once across all routes, the pool's checked-out count stuck at its maximum, and the database itself quiet. Causes: a connection leaked on an error path, a slow query or long transaction holding connections, a downstream HTTP call made while holding a connection (Chapter 17), or more concurrency than the pool size allows. Always acquire connections in a context manager, set pool and statement timeouts, and alert on pool wait time, not only on errors.

Memory growth

Memory that rises steadily with traffic and never falls, ending in an out-of-memory kill and restart, is usually an unbounded structure: a cache without a size limit, a list of "recent" items that is never trimmed, objects kept alive by a global registry, or a per-request object attached to something long-lived. Compare memory snapshots taken some time apart: Python's tracemalloc shows which lines allocated what grew, and tools such as memray and objgraph go further. Container restarts hide the problem until they become frequent, so alert on memory trend, not just on restarts.

import tracemalloc
tracemalloc.start()
before = tracemalloc.take_snapshot()
# ... serve traffic for a while ...
after = tracemalloc.take_snapshot()
for stat in after.compare_to(before, "lineno")[:5]:
    print(stat)                     # file:line, size_diff, count_diff: the lines whose allocations grew

Retry storms

A brief slowdown makes some requests time out; clients retry; the retries add load, so more requests time out and are retried, and the system stays overloaded long after the original cause has gone. Worse, servers keep doing work for requests whose callers have already given up. This self-sustaining state is a metastable failure: the trigger is over, but the system cannot recover on its own. The signature is offered load several times higher than normal traffic with near-zero successes. To stop one, cut the amplified load: shed load at the edge, open circuit breakers, or disable retries with a flag. To prevent one: exponential backoff with jitter, a retry budget (retries limited to a fraction of normal requests), deadlines propagated so servers drop work nobody is waiting for, and bounded queues.

Simulator: four incidents

Each incident was reproduced and measured with the bug, then with the fix. Slow endpoint: a customer summary query against 400,000 orders. Pool exhaustion: four threads calling a handler 50 times a second through a pool of 5 connections (0.5 s pool timeout), where 3% of requests have invalid input and the handler leaks its connection on that error path. Memory growth: 60,000 report requests through a cache keyed by user and query string, where the query string includes a timestamp. Retry storm: 400 requests a second to 8 workers (capacity 800 a second) with a 100 ms client timeout, and the database slowing from 10 ms to 60 ms per request between 2 and 3 seconds.

Use case: AWS us-east-1, December 2021

On 7 December 2021 an outage in Amazon Web Services' us-east-1 region affected many AWS services and the companies built on them for several hours. In its public summary, AWS explained that an automated activity to scale capacity of a service in its main network triggered unexpected behaviour from a large number of clients inside the internal network. The result was a large surge of connection activity that overwhelmed the networking devices between the internal network and the main AWS network, and the congestion caused more delays and errors, which caused clients to retry and so kept the congestion going. The retries also hurt the recovery: the same congestion made AWS's own monitoring data unavailable to the operators trying to find the problem. AWS said it was disabling the scaling activity that triggered the event until fixes were deployed, and changing clients so that their retries and back-off would not overwhelm the network again. It is the retry storm in this chapter at the scale of a cloud region: a short trigger, a feedback loop of retries, and a recovery that required removing load rather than waiting.

⚠️
Common mistakes
  • Investigating for hours before trying the obvious mitigation, a rollback.
  • Changing several things at once, so nobody knows which helped.
  • Raising pool sizes or timeouts to hide a leak.
  • Treating restarts as a fix for memory growth.
  • Immediate retries without budgets, in clients you control.
  • Dashboards that share the failing dependency, so they go dark during the incident.
  • No post-incident review, or one that blames a person.

Interview drill

Explain it simply: All endpoints suddenly time out, but the database's CPU is low. What do you suspect?

How a strong answer sounds
Connection pool exhaustion. If every request needs a pooled connection and none are free, requests queue in the application and time out, while the database is idle because nothing reaches it. I would check the pool's checked-out count and wait time, look for what is holding connections, such as a leak on an error path, a long transaction, or a slow external call made while a connection is held, and see what changed recently. To mitigate I would roll back or restart instances; the fix is acquiring connections with context managers, keeping transactions short, and alerting on pool wait.

Deeper: A dependency was slow for a minute an hour ago. It is healthy now, but your service is still failing. Walk through it.

How a strong answer sounds
That is the shape of a metastable failure, usually a retry storm or a backlog that cannot drain. I would look at request rate compared with normal: if it is several times higher with few successes, retries are sustaining the overload, and queues are full of work for callers who have already given up. Mitigation is to remove load: shed at the edge, open circuit breakers, disable or cap retries with a flag, and drop queued work past its deadline; scaling up may help but often cannot outrun the amplification. Once it is stable, I would make sure retries use exponential backoff with jitter and a retry budget, deadlines are propagated so servers skip abandoned requests, queues are bounded, and there is an alert on the ratio of retries to first attempts.

🧠 Key takeaways

  • Start from symptoms; ask what changed, where, and which resource is saturated.
  • Mitigate first, rolling back if in doubt, then find the root cause.
  • Slow routes: traces and query plans; pool exhaustion: checked-out at maximum, database quiet.
  • Memory growth: compare snapshots; bound every cache.
  • Retry storms outlast their trigger; backoff, jitter, budgets and deadlines prevent them.
