API Versioning & Evolution

An API is never finished: products add features, models change, mistakes need fixing. But clients you do not control, apps on millions of phones, partners' integrations, other teams' services, keep running code written against the API as it was. The skill is changing the API without breaking them, and, for the rare change that must break, giving them a new version, time and a clear warning.

Whether a change is "breaking" depends on the client as much as the server. The lab applies eight common changes, one at a time, to a real FastAPI service and runs three clients written against the original: a strict one, a tolerant one, and one that only places orders.

Breaking versus non-breaking changes

A change is non-breaking if every correctly written existing client keeps working. Broadly, you may add: new endpoints, new optional request fields, new response fields, new optional query parameters. You must not remove, rename or tighten: removing or renaming fields, changing a field's type or format, making an optional request field required, adding validation that rejects what used to pass, changing defaults or error codes, or changing behaviour clients rely on. Two changes sit in between: new enum values and fields that can now be null are additions on paper, and break any client that assumed the old, closed set. The lab shows each case with real code.

Things to try.

  • add a response field: the strict client fails with extra_forbidden. Adding fields is the textbook safe change, and it broke a client anyway, because that client was written to reject surprises.
  • new status value: the strict client rejects partially_refunded; the tolerant client shows "Partially refunded" with a generic label. Clients must expect enums to grow.
  • rename a field: both readers break. No client can tolerate the data it needs disappearing; this one needs a new version or a period of sending both names.
  • new required request field: every reader is fine, and every old sender gets a 422. Make new request fields optional with a sensible default.

Tolerant readers

Martin Fowler's tolerant reader pattern is the client's half of evolution: read only the fields you need, ignore everything else, treat IDs as opaque strings, handle unknown enum values with a default, cope with missing optional data, and never depend on field order or exact error text. In Python that means models with extra="ignore" (Pydantic's default) and a fallback for open enums. Servers help by documenting which enums can grow, never reusing a field name for a different meaning, and testing changes against real client code, as the lab does. Strict generated clients are valuable, catching mistakes early, but generate them so that unknown fields and enum values do not crash the app.

URL, header and media-type versions

SchemeExampleForAgainst
URL path/v1/orders, /v2/ordersObvious, easy to route, cache and test in a browserWhole-API versions; resources' URLs change
HeaderApi-Version: 2Stable URLs; can version per requestInvisible in logs and links unless recorded; caches need Vary
Media typeAccept: application/vnd.shop.v2+jsonVersions the representation, as HTTP intendsAwkward for clients and tools
Date, pinned per accountStripe-Version: 2024-06-20Small breaking changes ship often; each client upgrades when readyNeeds a translation layer and discipline to maintain

Most APIs do well with a major version in the URL that changes very rarely, plus additive evolution inside it. Whatever you choose, record each request's version in logs and metrics, so you know who still uses what.

Deprecation and Sunset headers

Retiring anything, an endpoint, a field or a whole version, starts with telling clients, in the place they will notice: the responses themselves. The Deprecation header (RFC 9745) says a resource is deprecated, and since when; the Sunset header (RFC 8594) says when it will stop working; a Link header points to the migration guide. Then use your metrics: find the clients still calling, contact them, and consider brief, scheduled "brownouts" before the date, so forgotten integrations fail during working hours rather than for good.

from fastapi import APIRouter, Response

v1 = APIRouter(prefix="/v1")
v2 = APIRouter(prefix="/v2")

@v1.get("/orders/{order_id}", response_model=OrderV1)
def get_order_v1(order_id: str, response: Response):
    response.headers["Deprecation"] = "@1767225600"            # deprecated since 1 Jan 2026 (Unix time)
    response.headers["Sunset"] = "Wed, 30 Sep 2026 23:59:59 GMT"
    response.headers["Link"] = '<https://docs.example.com/migrate-v2>; rel="deprecation"'
    return to_v1(orders.get(order_id))                         # one core, translated at the edge

@v2.get("/orders/{order_id}", response_model=OrderV2)
def get_order_v2(order_id: str):
    return orders.get(order_id)

app.include_router(v1)
app.include_router(v2)

Running two versions

Never fork the codebase per version. Keep one core, the domain logic and database, at the newest model, and translate at the edge: each old version is a thin layer that converts requests up to the current shape and responses back down, as to_v1 does above. Stripe works this way at scale, as the use case below describes. Test every supported version on every change, and keep the number of live versions small: each one is code to maintain and behaviour to remember.

💳
Use case: Stripe's date-based versions

Stripe's API has been changed in breaking ways hundreds of times, yet integrations written years ago still work. Each breaking change ships as a new version named by date, such as 2024-06-20. An account is pinned to the version current when it made its first request, and a request can override it with the Stripe-Version header, so every client upgrades when it chooses, one step at a time, with a changelog per version. Internally, as Stripe engineer Brandur Leach described in a 2017 post, "APIs as infrastructure: future-proofing Stripe with versioning", the core code speaks only the newest version, and each breaking change is written as a small, self-contained "version change" module that knows how to transform a response back to the previous shape. A request on an old version passes through the chain of modules, newest to oldest. It is the "translate at the edge" idea from this chapter, applied to every change, and it lets Stripe improve the API continuously without forcing customers through large migrations.

⚠️
Common mistakes
  • Renaming a field "to tidy up" in a live version.
  • Adding a required request field instead of an optional one with a default.
  • Clients that reject unknown fields or enum values by default.
  • A new major version for every change, or a copy of the codebase per version.
  • Retiring a version without usage metrics, warnings or a date.
  • Changing behaviour silently (defaults, ordering, rounding) because "the schema did not change".

Interview drill

Explain it simply: Is adding a field to an API response a breaking change?

How a strong answer sounds
By convention, no: additive changes are how APIs evolve, and well-written clients ignore fields they do not know. But it depends on the clients. A client generated with strict models that reject unknown fields will break, as a small experiment shows: a strict Pydantic model with extra="forbid" failed as soon as a currency field appeared. So I would document that clients must ignore unknown fields, generate SDKs that do, and, for a big integration, test new fields against the real client before release. New enum values are the same in a stronger form: they are additive on paper but break clients with closed enums, so APIs should say which enums may grow.

Deeper: You need to change how prices are represented, from a float to integer minor units with a currency. Plan the change.

How a strong answer sounds
It is a type change, so it breaks existing readers. First, the additive step: add new fields, amount_cents and currency, alongside the old price, in the current version, filled from one source of truth, and document the old field as deprecated with Deprecation and Sunset headers on responses that include it. Publish a migration guide, update the official SDKs to use the new fields, and measure which clients still read the old field if possible, or at least which still call the endpoints. If request bodies also carry prices, accept both forms for a while and reject requests that send conflicting values. After the sunset date, after contacting remaining users and a brownout or two, remove the old field in the next major or dated version, translated at the edge for anyone pinned to the old one.

🧠 Key takeaways

  • Add, don't change: new optional fields and endpoints are safe; removals, renames and type changes are not.
  • New enum values and nullable fields break clients that assumed closed sets.
  • Clients should be tolerant readers: ignore unknown fields, handle unknown values.
  • Keep versions few; translate old versions at the edge of one codebase.
  • Retire with Deprecation, Sunset and Link headers, usage metrics and time.
