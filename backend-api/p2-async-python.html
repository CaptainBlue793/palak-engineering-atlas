Async Python & the Event Loop

A web service spends most of its time waiting: for the database, for Redis, for another service, for the client to send the rest of the body. While one request waits, the server could be working on another. Async Python is a way of writing code that hands control back during those waits, so a single thread can juggle hundreds of requests that are mostly idle.

It comes with one rule that is easy to break and expensive when broken: inside async def, never block. One call to a synchronous library, one time.sleep, one long computation, and every other request on that server stops until it finishes. This page explains how the event loop works, why that happens, and how FastAPI gives you an escape hatch with plain def handlers.

Coroutines and the event loop

A function defined with async def is a coroutine function. Calling it does not run it; it returns a coroutine object, which runs when it is awaited or scheduled. Inside, await marks a point where the coroutine may pause, typically while waiting for I/O, and let something else run. The event loop is the scheduler: it runs one coroutine until that coroutine reaches an await on something not yet ready, then switches to another coroutine that is ready, and resumes the first when its data arrives, using the operating system's notifications (epoll, kqueue or IOCP) to know when that is.

All of this happens on one thread. The loop never interrupts a running coroutine; switching only happens at await. That makes async code free of most thread-safety bugs, and it is also why blocking is so damaging: a coroutine that never awaits never gives the loop a chance to run anything else.

import asyncio, time

async def fetch(name: str, delay: float) -> str:
    await asyncio.sleep(delay)          # stands in for a database or HTTP call
    return name

async def main():
    t = time.perf_counter()
    a = await fetch("user", 0.1)
    b = await fetch("orders", 0.1)       # one after the other: about 0.2 s
    c, d = await asyncio.gather(fetch("user", 0.1), fetch("orders", 0.1))   # together: about 0.1 s
    print(f"{time.perf_counter() - t:.2f} s")

asyncio.run(main())

Blocking calls

A blocking call holds the thread until it finishes: time.sleep, the requests library, a synchronous database driver such as psycopg2, reading a large file, or a tight loop of CPU work. Inside async def, nothing else can run on that loop until it returns, so every concurrent request on the server waits too. Measured on a laptop with FastAPI and uvicorn, ten simultaneous requests to a handler that does await asyncio.sleep(0.1) all finished in 0.12 seconds; with time.sleep(0.1) inside the same async def handler, they took 1.03 seconds, because they ran one at a time; fifty took 5.1 seconds.

The fix is to use async libraries for I/O (httpx's AsyncClient, asyncpg or psycopg 3's async mode, redis.asyncio), or to move unavoidable blocking work off the loop with await asyncio.to_thread(func, ...).

FastAPI's escape hatch: plain def

FastAPI accepts both kinds of handler. An async def handler runs on the event loop and must not block. A plain def handler is run in a thread pool (Starlette's run_in_threadpool, backed by AnyIO), so blocking inside it only ties up one thread. The pool has 40 threads by default, so the 41st simultaneous blocking request waits for a free one. In the same measurement, ten simultaneous requests to a def handler with time.sleep(0.1) took 0.25 seconds, not 1.03. Use def when you must call blocking libraries; use async def with async libraries when you can, because coroutines are far cheaper than threads.

  • Go back to async def + await and set the CPU work to 50 ms. The I/O still overlaps, but the computing queues up: async does not help computation.

CPU-bound work

Async helps with waiting, not with computing. A coroutine that resizes an image or hashes a password for 50 ms holds the loop for those 50 ms, and threads do not help much in CPython either: the global interpreter lock (GIL) lets only one thread run Python bytecode at a time, though C extensions that release it, such as many hashing and compression libraries, can overlap. Heavy computation belongs in a separate process: a process pool, more uvicorn worker processes, or a background job queue. Python 3.13 added an experimental build without the GIL, but the libraries a service depends on are only gradually supporting it.

🌩️
Use case: one regular expression, every CPU

On 2 July 2019, Cloudflare deployed a new rule to its web application firewall, which inspects every HTTP request passing through its network. The rule contained a regular expression that, on certain inputs, backtracked catastrophically: the time to evaluate it grew explosively with the length of the input. The rule went out to every machine at once, the regular expression consumed the CPU on every core that handled HTTP traffic, and for 27 minutes requests across Cloudflare's network failed with 502 errors. Nothing had crashed and no network was down; the servers were simply too busy computing to serve anyone. It is the same failure this page warns about inside one process: work that holds the processor without ever yielding starves every other request queued behind it. Cloudflare's fixes included limits on how long a rule may run and a regular-expression engine that cannot backtrack. In a service, the equivalents are timeouts on work, keeping heavy computation off the request path, and testing code paths with large inputs.

⚠️
Common mistakes
  • Calling requests, time.sleep or a synchronous database driver inside async def.
  • Forgetting await, so a coroutine object is created and never runs (Python warns "coroutine was never awaited").
  • Awaiting independent calls one after another when asyncio.gather could run them together.
  • Making every handler async def by habit, then calling blocking code from it; plain def would have been safe.
  • Doing CPU-heavy work on the request path, async or not.
  • Unbounded gather over thousands of items, overwhelming the database; limit concurrency with a semaphore (Chapter 28).

Interview drill

Explain it simply: Why does async make a web server handle more requests, if it all runs on one thread?

How a strong answer sounds
Most of the time a request spends on the server is waiting, for the database, another service or the network, not computing. With async, a request that is waiting hands control back to the event loop, which immediately works on another request that is ready. So one thread can keep hundreds of requests in flight, each mostly idle, instead of needing one thread per request sitting blocked. It only works if the code actually hands control back, by awaiting async I/O; a blocking call stops the whole loop. And it does not make computation faster: CPU-heavy work still runs one piece at a time.

Deeper: Your FastAPI service's latency jumps for every endpoint whenever one particular endpoint is called. What do you suspect and how do you confirm it?

How a strong answer sounds
I would suspect that endpoint blocks the event loop: an async def handler calling a synchronous library, a time.sleep, a large synchronous file read, or CPU-heavy work such as parsing a big document or hashing passwords. While it runs, every other request on that worker waits, so latency rises everywhere. To confirm, I would look at the code for blocking calls, enable asyncio's debug mode, which logs callbacks that take longer than 100 ms, or measure event-loop lag directly, and reproduce it by calling a cheap endpoint while the suspect one runs. The fix depends on the cause: switch to an async library, make the handler plain def so it runs in the thread pool, wrap the blocking call in asyncio.to_thread, or move heavy computation to a process pool or a background job.

🧠 Key takeaways

  • The event loop runs coroutines on one thread, switching only at await.
  • Async lets one thread overlap many I/O waits; it does not speed up computation.
  • A blocking call inside async def stalls every request on that worker.
  • FastAPI runs plain def handlers in a 40-thread pool, so blocking there is contained.
  • Use asyncio.gather for independent waits and asyncio.to_thread for unavoidable blocking calls.
  • CPU-heavy work belongs in another process or a background job.

What does calling an async def function, without awaiting it, do?

Forgetting await is a classic bug: Python warns that the coroutine was never awaited, and the work never happens.

An async def handler calls time.sleep(0.1). Ten requests arrive at once. Roughly how long until the last one finishes?

time.sleep blocks the event loop, so the requests run one after another: 10 × 0.1 s. Measured: 1.03 s.

How does FastAPI run a handler declared with plain def?

The pool has 40 threads by default, so more than 40 simultaneous blocking requests start to queue.

Which change speeds up a handler that awaits two independent database queries one after the other?

gather starts both and waits for both, so the total is about the slower of the two rather than their sum.

A handler spends 50 ms hashing a password in pure Python. What helps most under load?

CPU-bound Python is serialised by the event loop or the GIL. Separate processes can use separate cores. (Real password hashing libraries are C code that may release the GIL.)
