Performance: Profiling & Load Testing

Performance work goes wrong in two predictable ways: optimising code that was never the slow part, and believing a service can handle a load that nobody has actually sent it. The cure for both is measurement. A profiler tells you where one request spends its time. A load test tells you how the whole service behaves as traffic rises: how much it can serve, how latency grows, and which resource runs out first.

This chapter profiles a slow report endpoint and makes it 23 times faster in two steps, then load-tests a FastAPI service from 1 to 128 concurrent users in three configurations, and follows the bottleneck as it moves from the database connection pool to the CPU.

  • Profile a request and fix the top item first
  • Choose and configure a load-testing tool, closed or open model
  • Read latency as percentiles and explain why tails matter
  • Use Little's law to relate concurrency, throughput and latency
  • Find the saturated resource, fix it, and find the next one

Profiling a request

A profiler records where a program spends its time, function by function. Python ships one, cProfile; it is deterministic, hooking every call, which makes it precise about call counts but adds overhead to code with many small calls. Sampling profilers such as py-spy, pyinstrument and Scalene instead look at the stack many times a second; they are cheap enough to attach to a live production process (py-spy can, by process ID, without restarting it). Read a profile in two columns: tottime, time inside the function itself, finds hot code; cumtime, including everything it calls, finds the expensive path. Then fix the top item and profile again, because the second item is now the first.

The handler below builds a report of 5,000 orders: it loads them, fetches each order's customer, works out VAT with Decimal, reformats the date with a regular expression and returns JSON. It took 407 ms. Its profile, sorted by tottime:

  ncalls  tottime  function                                  (cProfile, 452 ms profiled)
    5001  328.7 ms  sqlite3.Connection.execute               # 73% of the time: one query per order
       1   56.6 ms  report_v1
    5000   26.2 ms  sqlite3.Cursor.fetchone
    5000    7.2 ms  re.Pattern.match
       1    6.0 ms  json encoder iterencode
    5000    5.4 ms  re._compile                              # the regex is looked up on every row

The answer was not "Python is slow" or "JSON is slow": 5,001 calls to execute, the N+1 query pattern from Chapter 7, took almost three quarters of the time. Replacing it with one JOIN brought the handler to 27.5 ms, 15 times faster. Profiled again, the top items were now the loop itself, JSON encoding (6.8 ms) and fetching rows (5.8 ms), with Decimal and the per-row regex below them. Doing VAT in integer pence and slicing the date string brought it to 17.7 ms; all three versions were checked to produce byte-identical output. Note too that cProfile reported 40.8 ms for the 27.5 ms version: tracing every call inflated it by half, so compare profiles with profiles and wall-clock times with wall-clock times.

Load-testing tools

A load generator sends many requests and records how the service copes. Common choices are k6 (JavaScript scripts, good reports), Locust (Python users), Gatling, wrk and wrk2, vegeta and oha (fast command-line tools). Two things matter more than the brand. First, the generator must not be the bottleneck: the Python client first written for this lab managed only about 220 requests per second, so it was replaced by a small Node.js generator that reached 3,705 a second against a trivial endpoint. Second, choose the workload model. In a closed model a fixed number of virtual users each send a request, wait for the reply and send the next, so the service can never receive more than that many requests at once. In an open model requests arrive on a schedule, say 100 a second, whether or not earlier ones have finished, which is how independent users on the internet behave. Test against something production-like (same instance size, realistic data volume, warm caches), ramp up gradually, and run long enough to see steady state.

Simulator: following the bottleneck

The service under test handles GET /quote: it takes a connection from a pool, runs a 40 ms query, then does 4 ms of CPU work (pricing rules, serialisation) on the event loop. The Node.js generator ran a closed workload of 1 to 128 users for 4 seconds after a 2-second warm-up, against three configurations. Inside the service, every request recorded how long it waited for a connection, how long the query took and how long the CPU work took; the generator measured CPU use of each worker process.

Things to try.

  • Pool of 4, rising users: throughput stops at 89 requests a second from 8 users on, while CPU sits at about 42%. Every extra user only adds time waiting for a connection: latency doubles each time users double.
  • Pool of 16: the ceiling rises to 221 a second and the CPU hits 100%. Now the query itself appears to take 58 ms instead of 41: the event loop is so busy that finished queries wait to be resumed.
  • Two workers: two processes, two CPUs, 448 a second. At 8 users, two separate runs had connections stall until the client's 20-second timeout; uvicorn's multi-worker mode on Windows did not spread a few long-lived connections evenly. At 128 users, p50 (173 ms) and mean (287 ms) diverge for the same reason: one worker held more of the connections.
  • On every row, compare λ × W with the number of users: that is Little's law, and it holds to within 2% everywhere except the stalled run.

Percentiles and tails

Report latency as percentiles from a histogram: p50 for the typical request, p95 and p99 for the slow ones that users remember, and the maximum to spot outliers. Averages hide structure, as Chapter 31 showed. Tails matter more than they look. A page that makes 20 backend calls sees the p99 of at least one of them on about 18% of loads (1 − 0.9920), and a heavy user making hundreds of requests a day meets the tail daily. Measure latency from when the request should have been sent, not from when the generator got round to sending it. A closed-loop generator stops sending while the service stalls, so it never records the requests that would have queued behind the stall; Gil Tene called this coordinated omission and wrote wrk2 to measure with an open model and fix it.

The open model also shows what overload really looks like. Against the pool-of-4 configuration (capacity about 89 a second), open arrivals measured:

arrivals/s   p50      p99      median latency in each second of the test
    50       52 ms    60 ms    52  52  52  52  52
    80       51 ms    66 ms    51  51  53  50  52
   100      392 ms   715 ms   116 238 392 521 655    # 12% over capacity: the queue grows every second

At 80 arrivals a second, 90% of capacity, the service was fine. At 100, only 12% over, latency climbed by about 130 ms every second and up to 64 requests were in flight at once; it would keep climbing until clients time out. A closed test cannot show this, because its users politely wait. Production traffic does not.

Little's law

For any stable system, the average number of requests inside it equals the arrival rate times the average time each spends there: L = λ × W. It needs no assumptions about distributions, and it turns capacity planning into arithmetic. A pool of 4 connections each held for about 45 ms can complete at most 4 / 0.045 ≈ 89 requests a second, which is exactly the measured ceiling. To serve 1,000 requests a second with 45 ms queries you need at least 1,000 × 0.045 = 45 connections busy at once, plus headroom, and the database must be able to run 45 queries concurrently. In a closed test, L is the number of users, so once throughput is fixed by the bottleneck, W must grow in proportion to the users: the doubling latency in the lab is Little's law, not bad luck.

Finding the bottleneck

Throughput is set by the scarcest resource, so the job is to find which one is saturated. Brendan Gregg's USE method gives a checklist: for each resource (CPU, memory, connection pool, worker threads, disk, network, the database itself, a downstream API) look at Utilisation, Saturation (work queued waiting for it) and Errors. In the lab, the pool of 4 was 100% utilised with requests queueing for it, while CPU was at 42%: adding CPU would have done nothing. Enlarging the pool moved the bottleneck to the event loop's single core; adding a worker process moved it again. Each fix raises throughput only until the next resource saturates, and the database behind a bigger pool is often that next resource, so check it before and after. Use case: "The Tail at Scale" at Google

In 2013 Jeffrey Dean and Luiz André Barroso published "The Tail at Scale" in Communications of the ACM, explaining why Google's large services cared so much about rare slow responses. Their example: if a single server answers in 10 ms but takes a second 1% of the time, a user request that waits on 100 such servers in parallel is slower than a second 63% of the time. Fan-out turns one server's p99 into the whole service's typical case. Slowness came from mundane sources: shared machines, background jobs such as compaction and garbage collection, queueing and power management. Rather than trying to remove every source, they described techniques that tolerate it, such as hedged requests: send a request to one replica and, if it has not answered within the 95th-percentile expected latency, send it to another and use whichever replies first. In one Bigtable benchmark, hedging after 10 ms cut the 99.9th-percentile latency from 1,800 ms to 74 ms while sending only 2% more requests. The lesson for any backend is the one in this chapter: measure percentiles, not means, and remember that every extra call in a request path multiplies the tail.

⚠️
Common mistakes
  • Optimising without a profile, or optimising the second item before the first.
  • Reporting average latency instead of percentiles.
  • A load generator that is itself the bottleneck, or that runs on the same busy machine.
  • Only closed-model tests, which hide overload and coordinated omission.
  • Testing against an empty database or cold caches unlike production.
  • Raising one limit, such as pool size, without checking the resource behind it.
  • Short runs that never reach steady state.

Interview drill

Explain it simply: What is Little's law and how would you use it?

How a strong answer sounds
Little's law says that in a stable system the average number of items inside equals the arrival rate times the average time each spends inside: L equals lambda times W. For a backend, it links concurrency, throughput and latency. If each request holds a database connection for 45 ms and I need 1,000 requests a second, I need about 45 connections in use at once, plus headroom, and the database must handle that concurrency. Turned round, a pool of 4 connections at 45 ms each can never exceed about 89 requests a second, however many users arrive; extra users just wait, and their latency grows in proportion.

Deeper: A service handles 200 requests a second today and must handle 1,000 for a launch. How do you get there?

How a strong answer sounds
Start with a target: 1,000 requests a second at, say, p99 under 300 ms and under 0.1% errors, on a realistic mix of endpoints. Build a load test with production-like data and a production-sized environment, using an open arrival model so overload shows up. Ramp until the target or failure, and at each step check every resource for utilisation, queueing and errors: CPU per worker, connection pool wait, database CPU and locks, downstream calls and their limits. Fix the saturated one: profile hot endpoints and remove N+1 queries or heavy serialisation, add caching, size pools by Little's law, add worker processes or instances, and offload slow work to queues. Re-run after every change, because the bottleneck moves, and usually ends at the database or a third-party limit. Finally keep headroom, add load shedding and rate limits for traffic beyond the plan, and set alerts on the same percentiles.

🧠 Key takeaways

  • Profile first; fix the top item, then profile again.
  • Make sure the load generator is not the bottleneck, and use an open model to see overload.
  • Report p50, p95 and p99; tails multiply across calls.
  • Little's law, L = λW, sizes pools and predicts ceilings.
  • Throughput is set by the saturated resource; fixing it moves the bottleneck.
