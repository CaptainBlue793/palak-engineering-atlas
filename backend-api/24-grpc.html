gRPC & Protocol Buffers

Inside a company, services call each other millions of times a minute, written by different teams in different languages. For that traffic, many organisations use gRPC: you describe a service and its messages once in a .proto file, generate typed client and server code for every language, and the calls travel as compact binary Protocol Buffers over HTTP/2, with streaming, deadlines and standard status codes built in.

This chapter explains Protocol Buffers and their rules for evolving safely, services and stubs, the four kinds of call, deadlines and status codes, and when gRPC beats REST. The lab measures the same order as JSON and as protobuf, a real gRPC server against a FastAPI endpoint, streaming against repeated calls, and a deadline running out.

  • Explain services, stubs and code generation
  • Use server, client and bidirectional streaming
  • Set deadlines and map gRPC status codes
  • Choose between gRPC and REST for a given API

Protocol Buffers

Protocol Buffers (protobuf) is a schema language and a binary encoding. Each field has a name, a type and a field number; on the wire, a field is written as its number and type tag followed by the value, compactly (small integers take one byte), and the names never appear. That is why protobuf messages are small and fast to parse, and why the rules for changing a schema are about numbers:

  • You may add fields with new numbers; old readers skip numbers they do not know, and new readers see missing fields as defaults.
  • You may rename a field: names are not on the wire (but they are in the JSON form, so renames still break JSON clients).
  • Never change a field's type or number, and never reuse the number of a deleted field: mark it reserved, or old data will be read as the new field.
  • In proto3, fields have defaults (0, "", false) and you cannot tell "unset" from "zero" unless you declare the field optional.

The lab's schema, and a two-item order encoded both ways, exactly as produced:

syntax = "proto3";
package shop.v1;
message LineItem { string sku = 1; int32 quantity = 2; int64 unit_price_cents = 3; }
message Order    { string id = 1; string customer_id = 2; repeated LineItem items = 3; int64 total_cents = 4;
                   string currency = 5; int64 created_at_unix = 6; string status = 7; }
message GetOrderRequest { string id = 1; }
message WatchRequest    { string customer_id = 1; int32 count = 2; }
service Orders {
  rpc GetOrder(GetOrderRequest) returns (Order);
  rpc WatchOrders(WatchRequest) returns (stream Order);
}

Services and stubs

A service block declares RPC methods with their request and response types. The protoc compiler, with a gRPC plugin per language (for Python, the grpcio-tools package), generates a stub for clients, an object whose methods make the calls, and a base class for servers to implement. Calls run over HTTP/2: each call is a stream on a long-lived connection, so many calls share one connection without head-of-line blocking at the HTTP level, and metadata, such as authentication tokens, travels as headers. (The lab built the same message classes at runtime from a descriptor, because the code generator was not installed, and registered the methods with gRPC's generic handlers; the bytes and behaviour are identical.)

Streaming RPCs

gRPC has four kinds of method: unary (one request, one response, like a REST call), server streaming (one request, a stream of responses, such as a feed of order updates or a large result set sent in pieces), client streaming (a stream of requests, one response, such as uploading telemetry), and bidirectional streaming (both, independently, such as chat or a long-lived sync). Streaming avoids a round trip and a set of headers per item, which the lab measures, but a long-lived stream also pins a connection and complicates load balancing, retries and resumption, like the WebSockets of Chapter 23.

Things to try.

  • message size: protobuf is about a third of the JSON at every size, mostly because field names are not repeated for every line item.
  • encode / decode at 1,000 items: protobuf is many times faster in Python, because its encoder runs in C.
  • calls: a unary gRPC call took about half the time of the REST call here, and streaming 1,000 orders was several times faster than 1,000 separate calls, each with its own headers and round trip.
  • deadlines: the slow call failed with DEADLINE_EXCEEDED at about 100 ms, and the server saw the cancellation and stopped its work.

Deadlines and status codes

Every gRPC call should carry a deadline: the client says how long it will wait, the deadline travels to the server in the request, and when it passes, the client gets DEADLINE_EXCEEDED and the server's context is cancelled, so it can stop working on an answer nobody will read. Servers should pass the remaining deadline on to the calls they make, so a whole chain of services gives up together (Chapter 29). Errors use a small set of status codes instead of HTTP's:

gRPC versus REST

gRPC suits internal service-to-service traffic: strict, generated contracts across languages, compact and fast messages, streaming, deadlines and cancellation, and one schema file as the source of truth. REST and JSON suit public and browser-facing APIs: anyone can call them with curl, browsers speak them natively (gRPC needs gRPC-Web or a protocol such as Connect through a proxy), responses are readable and cacheable with ordinary HTTP caches, and tooling is everywhere. Many organisations use both: gRPC inside, REST or GraphQL at the edge, often with a gateway translating between them (Chapter 35). The lab's speed differences are real but small per call; at the edge, network latency dominates, and the choice is mostly about contracts, tooling and clients.

Use case: from Stubby to gRPC

For more than a decade before 2015, Google connected its services with an internal RPC system called Stubby, built on Protocol Buffers, which Google described as handling tens of billions of calls per second across its data centres. In February 2015 Google announced gRPC, an open-source successor designed for the world outside Google: Stubby's ideas, protobuf contracts, generated stubs, deadlines, cancellation and flow control, rebuilt on public standards, chiefly HTTP/2, so that any company could run it. gRPC joined the Cloud Native Computing Foundation in 2017 and is now used for internal traffic at many large companies, and as the API protocol of infrastructure such as Kubernetes' container runtime interface and etcd. The lessons it carried over are the ones in this chapter: one schema as the contract, field numbers that never change, and a deadline on every call.

⚠️
Common mistakes
  • Reusing or renumbering fields, or changing their types.
  • Calls without deadlines, which wait for ever when something hangs.
  • Not propagating deadlines to downstream calls.
  • Mapping every error to UNKNOWN or INTERNAL, so clients cannot decide whether to retry.
  • gRPC for a public browser API without gRPC-Web or Connect planned in.
  • Load balancing long-lived HTTP/2 connections at layer 4, so all calls stick to one backend; balance per call instead.
  • Relying on proto3 defaults when "unset" and "zero" mean different things.

Interview drill

Explain it simply: Why are Protocol Buffers smaller than JSON, and how do you change a message safely?

How a strong answer sounds
JSON repeats every field name as text in every object and writes numbers as decimal text. Protobuf writes each field as a small numeric tag plus a compact binary value, so names never travel and small integers take a byte or two; in a measurement, an order with line items was about a third of the size of its JSON. Because fields are identified by number, changes are safe as long as numbers keep their meaning: you can add new fields with new numbers, since old readers skip unknown fields and new readers use defaults; you can rename fields; but you must never change a field's type or number, and never reuse a deleted field's number, which you mark as reserved.

Deeper: A chain of four gRPC services sometimes hangs for 30 seconds under load. What would you check and change?

How a strong answer sounds
First, deadlines: every call should have one, and each service should pass the remaining deadline downstream rather than starting a fresh timer, so when the edge gives up after, say, 2 seconds, every service in the chain stops. Hangs of 30 seconds suggest some call has no deadline or a default timeout. Second, cancellation: servers should check the context and stop expensive work when the call is cancelled. Third, retries: only retry UNAVAILABLE and idempotent calls, with backoff and a budget, since retries at four layers multiply. Fourth, load balancing: long-lived HTTP/2 connections can pin traffic to one overloaded backend, so use client-side or proxy load balancing per call. And add per-hop latency metrics and tracing (Chapter 31) to find which hop is slow.

🧠 Key takeaways

  • Protobuf encodes fields by number: small, fast, and safe to evolve if numbers never change meaning.
  • One .proto file generates typed stubs and servers for every language.
  • gRPC runs over HTTP/2 with unary and three kinds of streaming call.
  • Set a deadline on every call, propagate it, and use status codes that tell clients whether to retry.
  • gRPC for internal services; REST or GraphQL for public and browser clients.
