SQL for Application Developers

Most backend services are a thin layer of HTTP over a relational database, and most of their performance problems and many of their security problems are in the SQL. You do not need to be a database administrator to write a good service, but you do need a working set: the four statements every endpoint uses, joins, enough about indexes to know when one is missing, parameters to keep attackers out, and how to ask the database what it is actually doing.

Every timing and query plan on this page was measured with SQLite 3.53.4 on a table of 500,000 orders. PostgreSQL and MySQL print plans differently, but the shapes are the same.

  • Write the CRUD statements a service uses, safely
  • Use joins instead of one query per row (the N+1 problem)
  • Choose an index for a query, including column order
  • Pass values as parameters, never by string formatting
  • Read a query plan and spot a full table scan

CRUD: the four statements

Almost every endpoint maps to one of four statements: INSERT to create, SELECT to read, UPDATE to change and DELETE to remove. Three habits keep them safe. Name your columns, so adding a column later does not break anything. Always give UPDATE and DELETE a WHERE clause, and check how many rows were affected, so "update order 42" that matched nothing becomes a 404 rather than a silent success. And use RETURNING (PostgreSQL, and SQLite since 3.35) to get generated values back without a second query.

import sqlite3
con = sqlite3.connect("shop.db")

# create: the database assigns the id
row = con.execute(
    "INSERT INTO orders (customer_id, status, created_at, total_cents) VALUES (?, ?, ?, ?) RETURNING id",
    (4242, "pending", "2026-10-14T09:30:00Z", 1999),
).fetchone()

# read one
order = con.execute("SELECT id, status, total_cents FROM orders WHERE id = ?", (row[0],)).fetchone()

# update: check that something matched
cur = con.execute("UPDATE orders SET status = ? WHERE id = ? AND status = ?", ("paid", row[0], "pending"))
if cur.rowcount == 0:
    ...  # not found, or no longer pending: 404 or 409, not 200

# delete
con.execute("DELETE FROM orders WHERE id = ?", (row[0],))
con.commit()

The AND status = ? in the update is a small but important pattern: the change only happens if the row is still in the state you expect, which protects against two requests racing (Chapter 16).

Joins and the N+1 problem

A join combines rows from two tables in one query: JOIN (an inner join) keeps only rows with a match on both sides, and LEFT JOIN keeps every row from the left table, with NULLs where the right side has no match, for example customers with no orders yet.

The classic mistake is the N+1 query: fetch a list of N orders, then loop and run one more query per order to fetch its customer. It is easy to write by accident, especially through an ORM's lazy loading (Chapter 7). Measured on this table, fetching 100 orders with their customers' emails took 5.6 ms as 101 queries and 0.14 ms as one join, and that is with SQLite running inside the same process. Against a database server, every query also pays a network round trip, often 0.5 to 1 ms inside a data centre, so the 101-query version gets slower by roughly 50 to 100 ms while the join barely changes.

# N+1: one query for the list, one per row
orders = con.execute("SELECT id, customer_id FROM orders ORDER BY id DESC LIMIT 100").fetchall()
emails = [con.execute("SELECT email FROM customers WHERE id = ?", (cid,)).fetchone() for _, cid in orders]

# one query
rows = con.execute("""
    SELECT o.id, c.email
    FROM orders o JOIN customers c ON c.id = o.customer_id
    ORDER BY o.id DESC LIMIT 100""").fetchall()

Indexes, briefly

Without an index, finding rows that match a WHERE clause means reading every row in the table: a full scan. An index is a separate sorted structure, usually a B-tree, that maps column values to rows, so the database can jump straight to the matches. The primary key is indexed automatically; most other columns are not.

Indexes are not free: each one takes space and must be updated on every insert and update, so you add them for the queries you actually run. For a composite index on (customer_id, created_at), column order matters. It is sorted by customer first, then by date within each customer, so it serves WHERE customer_id = ?, and WHERE customer_id = ? ORDER BY created_at with no sorting at all, but it is a poor fit for WHERE created_at >= ? on its own. Put equality columns first and range or sort columns after.

Things to try.

  • Start with a customer's orders and no index: a full scan of every row to find a couple of dozen. Add (customer_id) and the time falls by a factor of several hundred.
  • Pick their latest 20. With (customer_id) the plan still needs a temporary B-tree to sort; with (customer_id, created_at) the sort disappears, because the index is already in that order.
  • Now try their latest 20 with (created_at). SQLite chose to walk the whole date index backwards looking for this customer's orders, and it was slower than having no index at all. An index on the wrong column can make a query worse.
  • Pick pending orders with (status). It helps, but less than you might hope: 10,000 matching rows each need a jump from the index back to the table.
  • Pick the last day's orders with (customer_id, created_at): SQLite uses a skip-scan, jumping through every customer's slice of the index. Better than a scan, far worse than (created_at).

Parameterised queries

Never build SQL by pasting values into the string. If a value comes from a request, an attacker chooses it, and a quote character ends your string and starts their SQL. Measured on the customers table, looking up an email with string formatting and the "email" x' OR '1'='1 returned 20,000 rows, every customer; the same lookup with a parameter returned 0. A parameterised query sends the SQL and the values separately, so the database never parses the values as SQL.

email = request_value                          # x' OR '1'='1

# vulnerable: the value becomes part of the SQL
con.execute(f"SELECT id FROM customers WHERE email = '{email}'")     # 20,000 rows

# safe: the value is sent as data
con.execute("SELECT id FROM customers WHERE email = ?", (email,))   # 0 rows

Placeholder syntax varies by driver: ? in sqlite3, %s in psycopg (which is not Python string formatting, despite looking like it), $1 in asyncpg, and :name in SQLAlchemy's text(). Parameters can only stand for values, not table or column names, so a user-chosen sort column must be checked against an allowlist of known names before it goes into the SQL.

Reading a slow query

When a query is slow, ask the database for its plan: EXPLAIN QUERY PLAN in SQLite, EXPLAIN ANALYZE in PostgreSQL (which also runs the query and reports actual rows and times), EXPLAIN in MySQL. You are looking for a few things: a scan of a large table where you expected an index lookup, a sort that an index could have avoided, and a big difference between the rows the planner expected and the rows it actually found, which suggests stale statistics. To find which queries are slow in the first place, use the database's own statistics, such as PostgreSQL's pg_stat_statements, or a slow-query log.

Use case: TalkTalk, 2015

In October 2015 attackers used SQL injection against web pages of TalkTalk, a British telecoms company, and extracted personal data on 156,959 customers, including bank account numbers and sort codes for more than 15,000 of them. The vulnerable pages had come with TalkTalk's acquisition of another provider's business years earlier and ran on outdated database software; the technique was well known and simple enough that teenagers carried it out. The Information Commissioner's Office fined TalkTalk £400,000, then a record, and said the attack could have been prevented by basic measures. TalkTalk reported the incident cost it about £42 million and over 100,000 customers. Every one of those pages would have been safe if user input had been passed as a query parameter rather than pasted into the SQL.

⚠️
Common mistakes
  • Building SQL with f-strings, % or + from request values.
  • N+1 queries in a loop or through lazy loading.
  • UPDATE or DELETE without checking the affected row count.
  • No index for the query an endpoint runs on every request, found only when the table grows.
  • Indexing every column "just in case", slowing every write.
  • Composite index columns in the wrong order for the query.
  • SELECT * in application code, which breaks when columns change and fetches data you do not need.

Interview drill

Explain it simply: What is SQL injection and how do you prevent it?

How a strong answer sounds
SQL injection happens when a program builds a query by pasting user input into the SQL text. If the input contains a quote, it can close the string and add SQL of the attacker's own, such as OR '1'='1', which makes a lookup return every row, or worse. The fix is parameterised queries: the SQL is sent with placeholders and the values separately, so the database treats the values only as data. ORMs and query builders do this for you, as long as you do not drop down to raw strings. For parts of the query that cannot be parameters, such as a column to sort by, I would check the input against an allowlist. And the database account the service uses should only have the permissions it needs, to limit the damage of any mistake.

Deeper: An endpoint listing a customer's recent orders got slow as the table grew. Walk through how you would fix it.

How a strong answer sounds
First, confirm which query is slow, from the database's statistics or the service's traces, and get the exact SQL with real parameter values. Then run EXPLAIN (in PostgreSQL, EXPLAIN ANALYZE). For "WHERE customer_id = ? ORDER BY created_at DESC LIMIT 20", I would expect to see a full scan, or an index on customer_id followed by a sort. The right index is composite, on (customer_id, created_at): equality column first, then the sort column, so the database can jump to the customer and read the newest 20 entries in order without sorting. I would create it without locking the table (in PostgreSQL, CREATE INDEX CONCURRENTLY), confirm the plan changed and the latency dropped, and check whether any existing index, such as one on customer_id alone, is now redundant, since every index costs write time. I would also check the endpoint does not fetch the customer per order in a loop.

🧠 Key takeaways

  • Check the affected row count on every UPDATE and DELETE; use RETURNING for generated values.
  • Replace N+1 loops with a join: one round trip instead of N+1.
  • An index turns a full scan into a lookup; composite indexes go equality columns first, then sort or range.
  • The wrong index can make a query slower, and every index slows writes.
  • Values go in parameters, never in the SQL string; identifiers go through an allowlist.
  • EXPLAIN shows what the database actually does: look for scans and sorts.

Which query can an index on (customer_id, created_at) serve without any sort?

Within one customer the index is already in date order, so the database reads the newest 20 entries directly.

A handler fetches 50 posts, then runs one query per post to fetch its author. What is this called and what is the fix?

51 round trips instead of one or two. Measured here: 101 queries took about 40 times as long as one join, before any network latency.

Why can't you pass the column in ORDER BY as a query parameter?

A parameter for ORDER BY would sort by a constant string, not by the column.

In a SQLite plan, what does SCAN orders tell you?

PostgreSQL calls it a Seq Scan. Fine for a small table, a warning sign for a large one on a hot path.

Measured here: about 3 times slower than no index. The right index is (customer_id, created_at).
