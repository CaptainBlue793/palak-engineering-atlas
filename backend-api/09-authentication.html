Authentication: Passwords, Sessions & Tokens

Authentication answers "who is making this request?". A person proves it once, usually with a password and ideally a second factor, and the service then recognises their later requests by something they carry: a session cookie in a browser, a bearer token in an app, an API key in a script. Each step has a well-known way to get it wrong, and the consequences arrive all at once, in a breach.

This chapter covers storing passwords so a stolen database does not reveal them, and the session, token and key mechanisms that carry identity afterwards, with the cookie flags and revocation rules that keep them safe. The lab measures, on this laptop, how much each password-hashing scheme slows an attacker down.

  • Store passwords with a slow, salted, memory-hard hash such as Argon2id
  • Implement server-side sessions with secure cookies
  • Use bearer tokens and API keys for apps and scripts
  • Set HttpOnly, Secure and SameSite correctly, and defend against CSRF
  • Log people out and revoke credentials when it matters

Password hashing

Never store passwords, and never store them encrypted, since whoever steals the database may steal the key too. Store a hash: a one-way function of the password, so that logging in means hashing what was typed and comparing. Three properties matter. The hash must be salted: a random value per user, stored alongside, so identical passwords produce different hashes and precomputed tables are useless. It must be slow, so each guess costs an attacker real time. And it should be memory-hard, needing lots of memory per guess, which blunts the advantage of GPUs and custom hardware. General-purpose hashes such as MD5 and SHA-256 fail the second and third tests: they are designed to be fast.

Use Argon2id, the winner of the 2015 Password Hashing Competition and OWASP's first recommendation, through a maintained library such as argon2-cffi; scrypt and bcrypt are acceptable, and PBKDF2-SHA256 with at least 600,000 iterations where a FIPS-validated algorithm is required. The library produces a self-describing string holding the algorithm, parameters, salt and hash, so later you can raise the cost and rehash each user at their next login:

from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher()                     # Argon2id, t=3, m=64 MiB, p=4 by default

stored = ph.hash("correct horse battery staple")
# $argon2id$v=19$m=65536,t=3,p=4$npg8PNF4nhMgC1ai6MNKFw$Gtf1dGHvSkpNeZBY2XDl+d+PBd7c+7aV2Bwbd3wsiJY

def check_password(user, password: str) -> bool:
    try:
        ph.verify(user.password_hash, password)    # constant-time comparison inside
    except VerifyMismatchError:
        return False
    if ph.check_needs_rehash(user.password_hash):  # parameters were raised since this was stored
        user.password_hash = ph.hash(password)
    return True

Measured: hashing the same password twice gave two different strings, because each has its own salt, and after raising time_cost to 4, check_needs_rehash returned True for the old hash. A slow hash also costs you CPU on every login, roughly 70 ms per attempt here, which is one more reason login endpoints need rate limits (Chapter 19).

Time per hash, one at a time, measured in Python on this laptop: MD5 and SHA-256 with hashlib (dominated by Python's call overhead, so real cracking tools are far faster), PBKDF2 and scrypt with hashlib, Argon2id with argon2-cffi 25.1.0 at its default parameters (parallelism 4, which may use several threads). GPUs compute MD5 and SHA-256 at billions of guesses per second, many thousands of times this model's figure, while memory-hard schemes gain far less from them.

Things to try.

  • salted SHA-256, 8 lower-case letters, 1,000 machines: under an hour, and on GPUs, seconds. Salt stops precomputed tables; it does not slow guessing.
  • Same password, Argon2id: about 85 days for the same attacker. Every guess costs 70 ms and 64 MiB of memory.
  • Choose in a breach list: even Argon2id falls quickly, because the attacker tries the most common passwords first. Hashing cannot rescue a known password; check new passwords against breach lists, as NIST's guidance recommends, and offer a second factor.
  • Choose 4 random words or 12 random characters: out of reach with any decent scheme. Long, random passwords from a password manager are the user's half of the deal.

Session cookies

After a successful login in a browser, the classic approach is a server-side session: generate a long random ID (secrets.token_urlsafe(32), 256 bits), store {user_id, created, expires} under it in a shared store such as the database or Redis, and send the ID in a cookie. Every request carries the cookie automatically; a dependency looks the ID up and returns the user. Because the session lives on the server, it can be ended at any moment by deleting it.

import secrets
from fastapi import Cookie, Depends, HTTPException, Response

@app.post("/login")
def login(body: LoginIn, response: Response, db=Depends(get_db)):
    user = users.by_email(db, body.email)
    if user is None or not check_password(user, body.password):
        raise HTTPException(401, "Wrong email or password")   # same message either way
    sid = secrets.token_urlsafe(32)                           # a new ID at every login
    sessions.create(db, sid, user.id, ttl_hours=12)
    response.set_cookie("__Host-session", sid, max_age=12 * 3600,
                        httponly=True, secure=True, samesite="lax", path="/")
    return {"ok": True}

def current_user(session: str | None = Cookie(default=None, alias="__Host-session"), db=Depends(get_db)):
    user = sessions.user_for(db, session) if session else None    # None if missing or expired
    if user is None:
        raise HTTPException(401, headers={"WWW-Authenticate": "Cookie"})
    return user

Cookie security flags

  • HttpOnly: JavaScript cannot read the cookie, so a cross-site scripting bug cannot steal it.
  • Secure: sent only over HTTPS.
  • SameSite=Lax (or Strict): not sent on cross-site POSTs, iframes or background requests, the main defence against cross-site request forgery (CSRF), where another site makes the victim's browser submit a request with their cookie. SameSite=None (which requires Secure) turns that off, for cookies that genuinely must work across sites.
  • The __Host- prefix: browsers only accept the cookie if it is Secure, has Path=/ and no Domain, so a sibling subdomain cannot set or overwrite it.
  • An expiry, idle and absolute, and a new session ID at every login, which prevents session fixation.

For state-changing requests from browsers, add a CSRF token or check the Origin header as well, especially if any cookie must be SameSite=None.

Bearer tokens and API keys

Mobile apps, single-page apps calling another domain, and other services usually send credentials in a header instead: Authorization: Bearer <token>. "Bearer" means whoever holds it is trusted, so tokens must be long, random, sent only over HTTPS and never logged. An opaque token is a random string the server looks up, like a session ID; a self-contained token such as a JWT carries signed claims that can be checked without a lookup (Chapter 12), which makes revocation harder. API keys identify a program rather than a person: generate them with a recognisable prefix (sk_live_..., which also lets secret scanners spot leaks), show the full key once, store only its hash, and let customers create several, name them and revoke them individually.

Logout and revocation

Logging out must end the session on the server, not just delete the cookie in one browser, since a stolen copy would still work. Revoke all of a user's sessions and tokens when they change their password, enable a second factor, or report a lost device, and give users a list of active sessions. For short-lived signed tokens, revocation is handled with short expiry plus refresh tokens that live on the server and can be revoked (Chapter 11).

Use case: LinkedIn's unsalted hashes, 2012

In June 2012 a file of about 6.5 million password hashes from LinkedIn appeared on a Russian password-cracking forum. They were SHA-1 hashes with no salt, so identical passwords had identical hashes, and SHA-1 is fast enough that a large share were cracked within days, by people working together in public. LinkedIn confirmed the breach and moved to salted hashes. The story had a second act: in May 2016 the full set from the 2012 breach, about 117 million email addresses and hashes, was offered for sale, and because so many people reuse passwords, accounts on other services were broken into with them for years afterwards. Both lessons are in this chapter: store passwords with a slow, salted, memory-hard function so a stolen table is close to useless, and assume every user reuses passwords, so offer and encourage a second factor and check new passwords against known breaches.

⚠️
Common mistakes
  • Fast hashes (MD5, SHA-1, SHA-256) or encryption for stored passwords.
  • Session cookies without HttpOnly, Secure or SameSite.
  • Different errors for "no such user" and "wrong password", which reveal who has an account.
  • No rate limit on login, inviting credential stuffing and burning CPU on slow hashes.
  • Logout that only deletes the cookie, leaving the session valid on the server.
  • Tokens or API keys in URLs or logs, or stored in plain text.
  • Session IDs kept after login, allowing session fixation.

Interview drill

Explain it simply: How should a service store users' passwords?

How a strong answer sounds
As a hash from a function designed for passwords: Argon2id, or scrypt or bcrypt, never MD5 or SHA-256 and never encryption. The function must be salted, so every user's hash is different even for the same password and precomputed tables are useless; slow, so each guess costs an attacker real time; and ideally memory-hard, so GPUs gain little. A library produces a string containing the algorithm, parameters, salt and hash, verifies in constant time, and tells you when stored hashes use old parameters so you can rehash at the next login. Around it: rate-limit logins, check new passwords against breach lists, and support a second factor, because no hash protects "123456".

Deeper: Your web app uses session cookies. A security review asks how you prevent session theft and CSRF. What do you say?

How a strong answer sounds
Session IDs are 256 random bits from a cryptographic generator, stored server-side with idle and absolute expiry, and replaced at every login to prevent fixation. The cookie is HttpOnly, so scripts cannot read it, Secure, so it never crosses plain HTTP, and uses the __Host- prefix, so subdomains cannot set it. For CSRF, SameSite=Lax stops browsers sending it on cross-site POSTs and background requests; on top of that, state-changing endpoints check the Origin header or require a CSRF token, and no state changes happen on GET. A strict Content Security Policy reduces the cross-site scripting risk that HttpOnly does not cover. Logout and password changes delete sessions server-side, users can see and end their active sessions, and anomalies, such as a session suddenly used from another country, can trigger re-authentication.

🧠 Key takeaways

  • Hash passwords with Argon2id (or scrypt, bcrypt): salted, slow and memory-hard; rehash when parameters rise.
  • No hash saves a password from a breach list: rate-limit logins, check breaches, offer a second factor.
  • Browser sessions: a random server-side ID in an HttpOnly, Secure, SameSite cookie, renewed at login.
  • Apps and scripts use bearer tokens or API keys; store only hashes of keys and never log them.
  • Logout and password changes revoke credentials on the server.
