Concurrency Control: ETags & Optimistic Locking

Two people open the same shared shopping list, each adds an item, each saves. Both saves succeed, and one item is gone: the second save wrote back the list as its author had read it, without the first person's change. This is the lost update, and it happens whenever a client reads a resource, changes its copy and writes the whole thing back, which is exactly what a REST client doing GET then PUT does.

This chapter covers the standard defences: version numbers, HTTP's ETag and If-Match, 412 Precondition Failed, locks, and avoiding the read-modify-write altogether. In the lab, twenty real clients add an item each to the same list at the same moment, against four server designs.

  • Recognise the lost update in read-modify-write code
  • Add a version column and use conditional updates
  • Expose versions as ETags and require If-Match on writes
  • Answer conflicts with 412, and know how clients should react
  • Choose between optimistic, pessimistic and atomic approaches

The lost update

The pattern is: read the current state, compute a new state in the application, write it back. Between the read and the write, someone else may have written, and the write overwrites their change with a stale copy. It does not matter whether the gap is a person editing a form for five minutes or a handler that takes fifty milliseconds; under concurrency, some writes are lost, silently, with every request returning success. The lab's first design shows how bad it gets when many writers collide.

Version columns

Give each row a version integer, incremented on every update. A writer remembers the version it read and makes the update conditional on it still being current:

cur = con.execute(
    "UPDATE lists SET items = ?, version = version + 1 WHERE id = 1 AND version = ?",
    (json.dumps(new_items), version_i_read))
if cur.rowcount == 0:
    ...   # someone else updated it first: do not overwrite

The condition and the write are one atomic statement, so the database guarantees only one writer per version succeeds. This is optimistic concurrency control: no locks are held while the client works, and conflicts are detected at write time. SQLAlchemy can do it for you with a version_id_col on the mapper, raising StaleDataError when the conditional update matches no row.

ETag and If-Match

HTTP carries the same idea. The server sends the version as an ETag on GET (ETag: "v7"); the client sends it back on the write as If-Match: "v7"; the server applies the write only if the resource still has that ETag, and otherwise answers 412 Precondition Failed. A server can insist on it, answering 428 Precondition Required to writes without If-Match, so no client can blindly overwrite. On a 412, the client fetches the resource again and either reapplies its change automatically, if it is a simple addition like the lab's, or shows the user both versions and lets them decide.

@app.put("/lists/1")
def put_list(body: ListIn, if_match: str | None = Header(default=None)):
    con = db()
    try:
        if if_match is None:                       # blind write: last writer wins
            con.execute("UPDATE lists SET items = ?, version = version + 1 WHERE id = 1", (json.dumps(body.items),))
            return {"ok": True}
        expected = int(if_match.strip('"').lstrip("v"))
        cur = con.execute("UPDATE lists SET items = ?, version = version + 1 WHERE id = 1 AND version = ?", (json.dumps(body.items), expected))
        if cur.rowcount == 0:                      # someone else changed it since this client read it
            return JSONResponse({"code": "precondition_failed", "detail": "The list changed; fetch it again"}, status_code=412)
        return {"ok": True}
    finally:
        con.close()

Simulator: twenty writers, one list

Twenty clients start at the same moment. Each reads the list, spends 50 ms on it, and adds its own item: item-01 to item-20. In the first two designs that is a GET then a PUT of the whole list; with ETags, a client that gets 412 starts again. The third design locks before reading; the fourth asks the server to append, so nothing is read in the client at all. Each design ran three times.

Things to try.

  • blind PUT: every request returned 200, and one item survived. Nineteen users were told their change was saved.
  • ETag + If-Match: all twenty survive, but look at the 412 count. With twenty writers fighting over one resource, most attempts lose and retry; the unluckiest client needed close to twenty tries. Optimistic concurrency is excellent when conflicts are rare and expensive when they are constant.
  • pessimistic lock: all twenty, no retries, but the writers queue: twenty times the 50 ms of work, one after another.
  • atomic append: all twenty in a fraction of the time. When the change can be expressed as an operation ("add this item"), let the database apply it, and there is nothing to race.

412 Precondition Failed, and what clients do

A 412 is not an error in the usual sense; it is the system working. Clients should treat it as "your copy is stale": fetch again, then reapply or merge. Automatic reapplying is fine for commutative changes, such as adding an item; for edits where both sides changed the same field, show the conflict to a person. Keep the retry loop bounded and add a small random delay, or, as the lab shows, heavy contention turns into many wasted round trips. Return the current ETag with the 412, or include the current resource, to save the client a request.

Pessimistic locks, briefly

A pessimistic lock blocks other writers while you work: SELECT ... FOR UPDATE in PostgreSQL and MySQL locks the selected rows until the transaction ends. It avoids retries and suits short, high-contention critical sections inside one request, such as allocating the last seat. It is a poor fit across HTTP requests: a lock held while a user edits a form ties up a connection (Chapter 6) and blocks everyone else until a timeout. Keep locks short, lock rows in a consistent order to avoid deadlocks, and set lock timeouts.

Use case: Wikipedia's edit conflicts

Wikipedia has always faced the shopping-list problem at enormous scale: thousands of people editing the same pages, each spending minutes in an edit box. Locking a page while someone edits would let one idle editor block everyone, so MediaWiki, the software behind it, uses optimistic concurrency. When you open the editor, the form records which revision of the page you started from. When you save, MediaWiki checks whether anyone else has saved a newer revision in the meantime. If not, your edit is saved. If they have, it tries to merge the two changes automatically, which works when you edited different parts of the page; if the edits overlap, it shows an "edit conflict" screen with the current text, your version and the differences, and asks you to combine them. It is the ETag pattern with a human merge on 412, and it is why concurrent editing on Wikipedia loses almost nothing despite its scale.

⚠️
Common mistakes
  • GET then PUT of whole resources with no version check.
  • Checking the version in Python and then writing instead of one conditional UPDATE.
  • Unbounded retry loops on 412 under heavy contention.
  • Pessimistic locks held across HTTP requests or user think time.
  • Read-modify-write for counters and lists that one atomic statement could change.
  • Weak ETags (W/"...") used for If-Match, which requires strong comparison.

Interview drill

Explain it simply: What is a lost update and how do ETags prevent it?

How a strong answer sounds
A lost update happens when two clients read the same resource, each changes its copy, and each writes it back: the second write overwrites the first, so one change disappears even though both requests succeeded. With ETags, the server sends a version identifier when the client reads, and the client sends it back in an If-Match header when it writes. The server only applies the write if the resource still has that version, using a conditional update in the database; otherwise it returns 412 Precondition Failed, and the client re-reads and reapplies or merges. Conflicts are detected instead of silently lost.

Deeper: A ticketing system sells the last seats to a popular concert and sees many 412s and slow checkouts. What do you change?

How a strong answer sounds
Optimistic concurrency is the wrong tool for a hot spot: when everyone is writing the same row, most attempts conflict and retry, wasting round trips, as an experiment with twenty writers on one list shows. I would avoid read-modify-write on the shared counter entirely: reserve a seat with a single atomic statement, such as UPDATE seats SET held_by = :me, held_until = now() + interval '10 minutes' WHERE id = (SELECT id FROM seats WHERE event = :e AND held_by IS NULL LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING id in PostgreSQL, so each buyer grabs a different free seat without waiting on others, or decrement an inventory count with WHERE remaining > 0. Holds expire if payment does not complete. For extreme demand, put a queue in front so requests are admitted at a rate the system can serve. Optimistic locking stays for things like editing an order's address, where conflicts are rare.

🧠 Key takeaways

  • Read-modify-write without a check loses updates silently.
  • A version column plus a conditional UPDATE detects conflicts atomically.
  • Over HTTP: ETag on read, If-Match on write, 412 on conflict, optionally 428 without If-Match.
  • Optimistic suits rare conflicts; pessimistic locks suit short, hot sections inside one request.
  • Best of all, express changes as atomic operations so there is nothing to race.
