Caching: HTTP Caches & Redis

The fastest request is the one your service never computes. A cache keeps the result of expensive work and hands it out again: in the client, in a CDN, in a shared store such as Redis in front of your database. Done well, it turns a 150 ms aggregation into a 15 ms lookup and lets a small database serve a large audience. Done carelessly, it serves yesterday's prices, or, at the worst moment, sends every request to the database at once.

This chapter covers HTTP caching, which the rest of the internet does for you when you set the right headers, and application caching with Redis: the cache-aside pattern, expiry and invalidation, and the stampede. The lab puts four strategies in front of a deliberately expensive query and measures how often the database is hit.

  • Set Cache-Control so browsers and CDNs cache correctly
  • Use ETags and conditional requests to revalidate cheaply
  • Implement cache-aside with Redis
  • Choose TTLs and invalidate on writes
  • Prevent stampedes with single-flight and stale-while-revalidate

Cache-Control and max-age

HTTP caches, in browsers, in CDNs and in reverse proxies, follow the Cache-Control response header (RFC 9111). The directives that matter for APIs:

  • max-age=60: the response may be reused for 60 seconds without asking. s-maxage sets a different lifetime for shared caches such as CDNs.
  • public / private: whether shared caches may store it. Anything that depends on who is asking, a user's orders, a personalised price, is private.
  • no-cache: store it, but revalidate before every reuse. no-store: never store it, for sensitive data.
  • stale-while-revalidate=30: after expiry, serve the stale copy for up to 30 seconds while fetching a fresh one in the background (RFC 5861).
  • Vary: the request headers the response depends on, so caches keep separate copies (Vary: Accept-Encoding).

A public product catalogue might send Cache-Control: public, max-age=60, stale-while-revalidate=300 and let a CDN absorb most of its traffic. A user's account page sends private, no-cache. Responses with an Authorization header are not stored by shared caches unless you explicitly allow it.

Conditional requests

When a cached copy expires, the cache does not have to download it again: it sends If-None-Match with the ETag it holds, and the server answers 304 Not Modified with no body if nothing changed (Chapter 2). That saves bandwidth and serialisation, though the server still has to work out whether the resource changed, which is cheap if the ETag comes from a version column or an updated_at, and expensive if it is a hash of a response you must first build.

Cache-aside with Redis

Inside the service, the common pattern is cache-aside: on a read, look in the cache; on a miss, compute from the database, store the result with a time-to-live, and return it. Redis is the usual store because it is shared by every worker and every instance, which an in-process dictionary is not (Chapter 1), and it expires keys itself:

import json, redis

r = redis.Redis(host="cache", port=6379, decode_responses=True)

def product_summary(pid: int) -> dict:
    key = f"summary:v3:{pid}"                       # a version in the key lets you change the format safely
    if (hit := r.get(key)) is not None:
        return json.loads(hit)
    if r.set(f"lock:{key}", "1", nx=True, ex=5):       # single-flight: only one request recomputes
        try:
            value = compute_summary(pid)              # the expensive query
            r.set(key, json.dumps(value), ex=60 + random.randint(0, 10))   # TTL with jitter
            return value
        finally:
            r.delete(f"lock:{key}")
    return wait_for(key) or compute_summary(pid)    # others poll briefly for the result

No Redis server ran for this page, so the lab uses an in-process cache with the same three operations, GET, SET ... EX and SET ... NX EX, in a single uvicorn worker, where it behaves like a Redis that every request shares.

TTLs and invalidation

A TTL is a promise about staleness: "readers may see data up to 60 seconds old". Choose it per kind of data, from what users and the business can accept: product descriptions for hours, stock levels for seconds, balances not at all. To be fresher than the TTL, invalidate on write: after committing a change, delete the affected keys, and the next read recomputes. Delete rather than overwrite, and do it after the commit, or a concurrent reader may cache the old value again; for extra safety, keep the TTL anyway, so any missed invalidation heals itself. Changing a value's format? Put a version in the key (summary:v3:42) so old entries are simply never read. And remember the hardest part is knowing which keys a write affects: keep cached items close to single resources, and be wary of caching aggregates that many writes touch.

Stampedes

A cache stampede, or thundering herd, happens when a popular entry expires and every request that misses recomputes it at once: the database gets N copies of its most expensive query exactly when traffic is highest. The defences, all visible in the lab: single-flight (one request takes a short lock with SET key NX EX and recomputes; the others wait or get stale data); stale-while-revalidate (keep serving the old value while one background refresh runs); jittered TTLs (random extra seconds so many keys do not expire together); and early refresh (recompute hot keys shortly before they expire). Also plan for the cache itself failing: if Redis restarts empty, every key misses at once, so ramp traffic back, or protect the database with limits (Chapter 29).

Use case: Facebook's outage of 23 September 2010

For about two and a half hours, Facebook was down or unusable for many users. In the post-mortem, engineering director Robert Johnson explained that a system meant to protect the site made it worse. Facebook ran an automated check that looked for invalid configuration values in its caches; when it found one, it deleted the cached value and fetched a fresh one from the database. That day, someone changed a configuration value in the database itself, to a value the check considered invalid. Every client saw the invalid value, deleted the cache entry and queried the database, which was immediately flooded with hundreds of thousands of queries a second; when queries failed, clients treated that as another invalid value, deleted the key again and queried again, a feedback loop. The only way out was to stop all traffic to the database cluster, which meant taking the site down, and let it recover. It is a stampede with no single-flight, no backoff and no fallback to stale data, and each of this chapter's defences would have damped it.

⚠️
Common mistakes
  • Personalised responses marked public, so a CDN serves one user's data to another.
  • In-process caches in multi-worker services, each with different contents.
  • No single-flight on hot, expensive keys, inviting stampedes.
  • Updating the cache before the database commit, or overwriting instead of deleting.
  • Caching without TTLs, so a missed invalidation lasts forever.
  • All keys sharing one TTL, expiring together.
  • Treating the cache as the source of truth for data that must not be lost.

Interview drill

Explain it simply: How does cache-aside work, and what can go wrong?

How a strong answer sounds
On a read, the service checks the cache; on a hit it returns the cached value, and on a miss it reads from the database, stores the result in the cache with an expiry time, and returns it. Writes go to the database and then delete the cached entry so the next read is fresh. Things that go wrong: stale data, bounded by the TTL unless you invalidate on write; invalidation races, if you write the cache before the database commit; stampedes, when a hot key expires and many requests recompute it at once, which needs a single-flight lock or stale-while-revalidate; and the cache going down, when every request falls through to the database, so the database needs protection too.

Deeper: A product page API is slow under a flash sale. Walk through how you would use caching to fix it safely.

How a strong answer sounds
Split the page into what is the same for everyone and what is personal. The shared part, description, images, price, is served with Cache-Control: public, s-maxage=30, stale-while-revalidate=120 so a CDN absorbs most requests, with a purge when the product is edited. Behind it, the service caches the expensive product summary in Redis with cache-aside, a short TTL with jitter, single-flight on misses and stale-while-revalidate for the hottest keys, and deletes the key when the product changes. Stock is the exception: it changes every second, so I would not cache it beyond a second or two, and the actual purchase always checks stock in the database atomically (Chapter 17). Per-user data, basket and recommendations, is fetched separately and marked private. Finally, I would warm the cache before the sale starts, monitor hit rates and database load, and have a fallback if Redis fails, such as serving stale data or shedding load, rather than letting every miss hit the database.

🧠 Key takeaways

  • Cache-Control tells browsers and CDNs what to keep: max-age, public or private, no-store, stale-while-revalidate.
  • ETags and 304s make revalidation cheap.
  • Cache-aside in a shared store like Redis: read through on miss, TTL on every key.
  • Invalidate by deleting after the commit; version keys when formats change.
  • Stop stampedes with single-flight locks, stale-while-revalidate and jittered TTLs.
