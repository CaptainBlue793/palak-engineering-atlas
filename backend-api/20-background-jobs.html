Background Jobs & Task Queues

Some work does not belong in the request. Sending a welcome email, resizing a photo, generating an invoice PDF, syncing with a CRM: the user does not need to wait for any of it, and much of it depends on other services that are slow or occasionally down. Put such work in a queue, answer the request immediately, and let workers process jobs in the background, retrying when something fails.

Queues bring their own failure modes: jobs that fail for ever, retries that hammer a struggling provider, and jobs that run twice when a worker dies. The lab builds a small queue on SQLite, with leases, retries and a dead-letter state, and runs four experiments on it.

What to move out of the request

Move work to a background job when the client does not need its result to continue, when it is slow (more than a few hundred milliseconds), when it calls a service that may be down, or when it is heavy and would tie up web workers (Prerequisite 2). Typical candidates: emails and notifications, image and video processing, exports and reports, webhooks to customers (Chapter 21), search indexing, and anything batch-shaped. Keep in the request what the client must know now: whether the order was accepted, whether the card was charged. For long work the client does want, return 202 Accepted with a job resource to poll (Chapter 4).

Queues and workers

A queue stores jobs durably; workers, separate processes that can be scaled independently of the web tier, take jobs and run them. In Python, common choices are Celery, RQ, Dramatiq and arq with Redis or RabbitMQ as the broker; managed queues such as Amazon SQS or Google Cloud Tasks; or, for modest volumes, a table in the database you already have, which is what the lab uses. Whatever the technology, the core mechanism is the same: a worker claims a job with a lease (visibility timeout) so no other worker takes it; if the worker finishes, it marks the job done; if it dies, the lease expires and another worker takes the job. That makes delivery at least once: a job can run twice, so every job must be idempotent.

def claim(con, lease):
    """Atomically take the oldest runnable job: queued and due, or running with an expired lease (its worker died)."""
    now = time.time()
    return con.execute("""UPDATE jobs SET status = 'running', attempts = attempts + 1, locked_until = ?
                          WHERE id = (SELECT id FROM jobs
                                      WHERE (status = 'queued' AND run_at <= ?) OR (status = 'running' AND locked_until < ?)
                                      ORDER BY run_at, id LIMIT 1)
                          RETURNING id, kind, payload, attempts""", (now + lease, now, now)).fetchone()

Things to try.

  • the request path: inline, every signup waits for the email provider; queued, the response returns as soon as the job is written, and the emails follow a few seconds later.
  • a flaky provider with 3 immediate retries: three times the calls and almost no extra deliveries, because the retries arrive during the outage. Backoff with jitter spreads them out and outlasts it.
  • a poison message: retried for ever, one broken file eats most of a worker for the whole run. With a limit, it moves to the dead-letter state after 5 attempts, with its error, for a person to look at.
  • a worker dies: the job's lease expires and another worker runs it again, so receipt 1006 is sent twice. The idempotent handler records a key before sending, and the second run finds it and does nothing.

Retries and backoff

Most job failures are transient: a timeout, a 503, a rate limit. Retry them, but not immediately: a provider that is struggling or down for two minutes will not recover in the next 50 milliseconds, and immediate retries from every worker multiply the load on it. Use exponential backoff (wait roughly 1, 2, 4, 8 seconds…, capped) with jitter (randomise each wait, so failures that happened together do not retry together), honour Retry-After when the provider sends one, and limit the total attempts or time. Distinguish permanent failures, such as a 400 for an invalid address, and do not retry those at all.

def fail(con, jid, attempts, error, max_attempts, backoff):
    if max_attempts is not None and attempts >= max_attempts:
        con.execute("UPDATE jobs SET status = 'dead', last_error = ? WHERE id = ?", (error, jid))   # dead-letter: kept for a human
        return "dead"
    delay = backoff(attempts)
    con.execute("UPDATE jobs SET status = 'queued', run_at = ?, last_error = ? WHERE id = ?", (time.time() + delay, error, jid))
    return "retry in %.2fs" % delay


def exp_backoff(base=0.1, cap=2.0):
    # "full jitter": a random delay between 0 and base * 2^attempt, capped
    return lambda attempts: random.uniform(0, min(cap, base * 2 ** attempts))

Poison messages

A poison message is a job that can never succeed: a corrupt file, a payload from an old code version, a bug triggered by one customer's data. Without a limit it is retried for ever, wasting workers and, in queues that preserve order, blocking everything behind it. Give every job a maximum number of attempts; after the last, move it to a dead-letter queue (or state) with its last error, alert on the dead-letter count, and give operators a way to inspect, fix and requeue or discard.

Scheduling and cron

Recurring work, nightly reports, hourly syncs, expiring old sessions, is scheduled by a single scheduler (Celery beat, a Kubernetes CronJob, the cloud provider's scheduler) that enqueues jobs, so the work runs on ordinary workers with ordinary retries. Make sure only one scheduler runs, or that duplicate schedules are harmless; write scheduled jobs to process "everything due since the last successful run", not "everything from the last hour", so a missed run catches up; and set alerts on jobs that have not succeeded for longer than expected.

Use case: retry storms and the AWS guidance on jitter

In 2015 Marc Brooker of AWS published "Exponential Backoff And Jitter" on the AWS Architecture Blog, with simulations of many clients competing for one contended resource. Plain exponential backoff spread the retries out in time but kept them clustered: clients that failed together retried together, at 1, 2, 4 seconds, colliding again each time. Adding randomness, in particular "full jitter", picking each wait uniformly between zero and the exponential cap, cut both the total work done and the time to complete dramatically. The same reasoning appears in AWS's later Builders' Library article "Timeouts, retries, and backoff with jitter", which also warns that retries at several layers of a system multiply each other; with three layers each making three attempts, for example, one failing call becomes 27. The lab's flaky-provider experiment is a small version: immediate retries tripled the calls during an outage and delivered almost nothing more, while jittered backoff outlasted the outage. The queue in this chapter uses full jitter for exactly this reason.

⚠️
Common mistakes
  • Slow or unreliable calls in the request path that could be jobs.
  • Non-idempotent jobs on an at-least-once queue.
  • Immediate retries, or no jitter, against a struggling dependency.
  • No attempt limit and no dead-letter queue.
  • Leases shorter than the job's run time, so healthy jobs are taken by a second worker.
  • Enqueuing before the database commit, so workers look for data that does not exist yet, or that is rolled back (Chapter 30).
  • Treating FastAPI's BackgroundTasks as a durable queue.

Interview drill

Explain it simply: Why would you send a welcome email from a background job instead of inside the signup request?

How a strong answer sounds
The user does not need to wait for the email to be sent before they can continue, and sending it means calling an external provider, which can be slow or temporarily down. Inside the request, that adds hundreds of milliseconds to every signup and, if the provider fails, either fails the signup or loses the email. As a background job, the request only records the job and returns quickly; a worker sends the email, and if the provider is down, the job is retried later with backoff. The job must be idempotent, for example keyed by user ID and email type, because a worker crash can cause it to run twice.

Deeper: A nightly job generates invoices and emails them. Last night it sent some customers two invoices and others none. How do you investigate and redesign it?

How a strong answer sounds
Duplicates suggest at-least-once redelivery without idempotency, for example a lease or visibility timeout shorter than the job took, so a second worker picked it up, or the scheduler running twice. Missing invoices suggest jobs that failed without retry, died without a lease expiring, or a run that selected "the last 24 hours" and missed a window. I would check the job records and logs for those customers. The redesign: the scheduler enqueues one job per customer per billing period, with an idempotency key such as invoice:{customer}:{period} enforced by a unique constraint on the invoices table, so generating and recording an invoice happens once whatever the delivery count; emailing is a separate job keyed the same way, with its own retries and backoff. Select work by "billing periods not yet invoiced" rather than by time window, so missed runs catch up. Leases longer than the worst-case job time, a dead-letter queue with alerts, and a daily reconciliation that counts customers versus invoices sent.

🧠 Key takeaways

  • Move slow, unreliable or non-essential work out of the request into durable jobs.
  • Workers claim jobs with leases; delivery is at least once, so jobs must be idempotent.
  • Retry transient failures with exponential backoff and full jitter; never retry permanent ones.
  • Cap attempts and dead-letter poison messages, with alerts.
  • Schedulers enqueue jobs; select work by what is due, so missed runs catch up.
