API Security: the OWASP API Top 10

Most API breaches do not involve clever cryptography. They happen because an endpoint returned a record without checking who owned it, accepted a field the client should never set, returned a field the client should never see, or trusted a URL or an origin it should not have. The OWASP API Security Top 10 (2023 edition) lists these failures, and nearly all of them are prevented by a handful of habits applied to every endpoint.

This chapter covers those habits and verifies each one the way you should in your own service: with a security regression suite. The lab runs the same ordinary and boundary requests against an invoicing API with each control present and with it missing, so you can see exactly what each control is responsible for.

  • Check object ownership on every request that names an object
  • Use separate input and output schemas so clients cannot set or see internal fields
  • Keep user input out of query text with parameters
  • Allow-list the URLs your server fetches on a user's behalf
  • Configure CORS and security headers deliberately, and test them

The OWASP API Security Top 10

The 2023 list is: API1 broken object-level authorisation, API2 broken authentication, API3 broken object property-level authorisation (which covers both mass assignment and excessive data exposure), API4 unrestricted resource consumption, API5 broken function-level authorisation, API6 unrestricted access to sensitive business flows, API7 server-side request forgery, API8 security misconfiguration, API9 improper inventory management and API10 unsafe consumption of third-party APIs. Authentication is Chapter 9, rate limits Chapter 19 and versioned inventories Chapter 13; this chapter takes the items that live in every handler you write.

Broken object-level authorisation

An endpoint such as GET /invoices/{id} receives an ID from the client. Authentication tells you who is asking; it says nothing about whether this invoice is theirs. If the handler loads the invoice by ID alone, any logged-in user can read any invoice by changing the number. This is the most common serious API flaw because the code looks correct and works in every demo. The fix is to scope every lookup to the caller, in the query itself, and to return 404 rather than 403 so the API does not confirm which IDs exist:

@app.get("/invoices/{invoice_id}")
def get_invoice(invoice_id: int, user: User = Depends(current_user)):
    invoice = session.scalar(select(Invoice).where(Invoice.id == invoice_id, Invoice.tenant_id == user.tenant_id,
                                                  Invoice.owner_id == user.id))      # ownership is part of the query
    if invoice is None:
        raise HTTPException(404, "invoice not found")                    # same answer for "missing" and "not yours"
    return invoice

Random, non-sequential IDs (UUIDs) make guessing harder but are not a fix; IDs leak through URLs, logs and shared links. The fix is the check, applied centrally (a repository method that always takes the user, or row-level security in the database, Chapter 34) and covered by a test that asks for someone else's object.

Mass assignment and excessive data exposure

Two mirror-image mistakes come from using one model, or the raw database row, for everything. Mass assignment: the handler copies every field in the request body onto the record, so a client that adds "role": "admin" or "balance": 1000000 to an ordinary profile update gets it. Excessive data exposure: the handler returns the whole row, password hash, internal flags and all, trusting the front end to show only some of it. Both are fixed by explicit schemas at the boundary: an input model that lists the fields a client may set and rejects anything else (extra="forbid"), and an output model that lists the fields a client may see (response_model).

class ProfileUpdate(BaseModel):
    model_config = ConfigDict(extra="forbid")                     # unknown fields are a 422, not ignored
    name: str = Field(min_length=1, max_length=80)

class UserOut(BaseModel):                                            # no role, no password_hash
    id: int; email: str; name: str

@app.patch("/me", response_model=UserOut)
def update_me(body: ProfileUpdate, user: User = Depends(current_user)): ...

Injection

Injection happens whenever user input is pasted into text that another system interprets as instructions: SQL, shell commands, LDAP filters, HTML, log formats. The fix for SQL is never to build query text from input. Pass values as parameters (? or :name), which the driver sends separately from the query, so input is always treated as data. ORMs do this for you as long as you use their expressions rather than formatting strings into text(). Identifiers such as column names for sorting cannot be parameters; map them through an allow-list ({"date": Invoice.created_at}). The same principle applies elsewhere: pass argument lists to subprocess rather than a shell string, and let templates escape HTML.

Server-side request forgery

Features such as "import an avatar from a URL" or "send a webhook to this address" make your server fetch a URL the user chose. Your server sits inside your network, so without limits it can be pointed at internal services that are not exposed to the internet, including cloud metadata endpoints that hand out credentials. Defences, in order of strength: avoid fetching user-supplied URLs at all (accept an upload instead); otherwise allow-list the hosts you will fetch from and require HTTPS; reject IP literals and non-standard ports; resolve the hostname and refuse private, loopback and link-local addresses, checking again after any redirect (or disable redirects); and run the fetcher with network egress rules so that even a mistake cannot reach internal ranges. On AWS, require IMDSv2 so the metadata service needs a session token.

Security headers and CORS

Browsers enforce the same-origin policy: a page from one site cannot read responses from another unless the API says so with CORS headers. CORS loosens protection, it never adds any, so configure it narrowly: list the exact origins of your own front ends, allow credentials only if you use cookies, and never combine "any origin" with credentials. Add security headers to every response: Strict-Transport-Security so browsers only use HTTPS, X-Content-Type-Options: nosniff, Cache-Control: no-store for personal data, and a restrictive Content-Security-Policy. For JSON APIs that browsers should never frame or render, default-src 'none'; frame-ancestors 'none' is a good default.

Things to try.

  • object ownership, missing: Alice reads Bob's invoice with a 200. Nothing in the response looks wrong, which is why this flaw survives code review and needs a test.
  • input schema, missing: adding "role": "admin" to a name change made Alice an admin, and an empty name was stored too. With the schema, both are 422 with a precise error.
  • query parameters, missing: an ordinary customer name containing an apostrophe, O'Brien Builders, broke the query and returned the database's error message. The apostrophe ended the SQL string literal, so the input had become part of the query: the same mechanism injection relies on.
  • CORS, missing: with allow_origins=["*"] and credentials allowed, Starlette 1.7 answered a cookie-bearing request from an unknown site by echoing that site back in Access-Control-Allow-Origin, so that site's scripts could read Alice's profile.

Testing security like any other behaviour

Every control in this chapter can be checked by an ordinary automated test, and should be, because each one is a single line that a refactor can delete. For every endpoint that takes an ID, test another user's ID. For every write, test an unexpected field. For every read, assert the exact set of response fields. Test the CORS response for an unlisted origin and the presence of headers. Add dependency scanning (pip-audit), a static analyser (Bandit, Semgrep) and secret scanning in CI, and commission a penetration test before big launches; none of them replaces tests written by people who know which objects belong to whom.

Use case: Capital One and the cloud metadata service

In 2019 Capital One disclosed that personal data of about 100 million people in the United States and 6 million in Canada had been taken from its cloud storage. The route in was server-side request forgery: a misconfigured web application firewall running on AWS could be made to send requests on an outsider's behalf, including to the EC2 instance metadata service, which handed back temporary credentials for the server's role. That role could read far more storage than the firewall needed. Three lessons from this chapter and Chapter 9 combine here: a server that fetches attacker-chosen addresses is reaching into your private network; the credentials a server holds should allow only what it needs; and defence in depth matters. In late 2019 AWS introduced IMDSv2, which requires a session token obtained with a PUT request, making the metadata service much harder to reach through simple request forgery, and in 2020 Capital One agreed an $80 million civil penalty with the US Office of the Comptroller of the Currency.

⚠️
Common mistakes
  • Loading objects by ID without the caller in the query.
  • Copying the request body onto the record, or returning the database row directly.
  • Formatting input into SQL or shell strings.
  • Fetching user-supplied URLs with no allow-list or egress limits.
  • allow_origins=["*"] with credentials, or origin patterns that match look-alike domains.
  • Database errors and stack traces in responses.
  • No tests for any of the above.

Interview drill

Explain it simply: What is broken object-level authorisation and how do you prevent it?

How a strong answer sounds
It is when an API checks that the caller is logged in but not that the specific object they asked for belongs to them, so changing an ID in the URL returns someone else's data. It is the top item on the OWASP API list because handlers that look up by ID alone look correct and pass ordinary tests. I prevent it by making ownership part of every query, for example filtering by tenant and user as well as ID, ideally through a repository layer or database row-level security so it cannot be forgotten, returning 404 for objects the caller cannot see, and writing a test for each endpoint that requests another user's object.

Deeper: You inherit an API with 80 endpoints and no security tests. Where do you start?

How a strong answer sounds
First an inventory: list every route from the OpenAPI document and the router, which ones take object IDs, which write data, which fetch URLs or call other systems, and which are unauthenticated. Then the highest-risk checks across all of them, automated so they stay: an authorisation test per ID-taking endpoint using a second user, an extra-field test per write, an exact-fields assertion per read, CORS and header checks, and searches for string-built SQL, shell calls and outbound fetches. Fix by centralising: a dependency that loads objects scoped to the caller, separate input and output schemas, a single outbound HTTP client with an allow-list. Add pip-audit, Bandit or Semgrep and secret scanning to CI, review logging so tokens and personal data are not written, and plan an external penetration test once the basics are in.

🧠 Key takeaways

  • Authentication says who; every object lookup must also check ownership.
  • Separate input and output schemas stop mass assignment and data exposure.
  • Parameters keep input as data; allow-list anything that cannot be a parameter.
  • Allow-list outbound URLs and limit egress; your server is inside your network.
  • CORS only loosens protection: list exact origins, and test security like any other behaviour.
