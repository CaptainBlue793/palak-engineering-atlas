Configuration, Secrets & Environments

The same service runs on your laptop, in a test environment and in production. Its code should be identical in all three; what changes is configuration: which database to connect to, how much to log, which keys to use for the payment provider. Getting configuration right means one build that behaves correctly everywhere, and a service that refuses to start rather than running with a wrong or missing setting.

Some of that configuration is secret: database passwords, API keys, signing keys. Secrets need extra care, because the usual ways they leak are boring: a file committed to Git, a settings object printed in a log line, a crash report. This page builds a small settings loader and runs it, for real, in 48 combinations of environment and configuration sources.

  • Keep configuration out of code, in the environment
  • Load settings into a validated object that fails fast at startup
  • Know which source wins when a setting is defined twice
  • Keep secrets out of Git, logs and error reports
  • Run local, staging and production from one build, with local services in Docker Compose

Environment variables

The Twelve-Factor App, a set of practices published by Heroku engineers in 2011, puts it simply: store configuration in the environment. Anything that varies between deployments, such as URLs, credentials and feature switches, is read from environment variables rather than written in the code, so the same build runs everywhere and no secret lives in the repository. Every platform, from Docker and Kubernetes to Heroku and Cloud Run, knows how to set environment variables.

Environment variables are always strings, which causes a classic bug: bool(os.environ["DEBUG"]) is True for "false", because any non-empty string is truthy. Parse them properly, ideally with a library that knows "false", "0" and "off" mean false, which is what Pydantic does.

Settings with validation

Read configuration once, at startup, into a typed and validated settings object, and pass that object around instead of calling os.environ all over the code. If a value is missing or malformed, the service should fail to start with a clear message, not fail at 3 a.m. when the code path that reads it finally runs. Rules about combinations belong here too: debug mode must be off in production, and production must have a real API key.

This is the loader the simulator below runs. It is about 40 lines, built on Pydantic and python-dotenv, so you can see every step. In a real service use pydantic-settings, whose BaseSettings does the same job, with the same order of sources by default.

class Settings(BaseModel):
    model_config = ConfigDict(frozen=True)

    app_env: Literal["local", "staging", "production"] = "local"
    database_url: str = "sqlite:///./dev.db"
    debug: bool = False
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "INFO"
    api_key: Optional[SecretStr] = None

    @model_validator(mode="after")
    def safe_for_production(self):
        if self.app_env == "production":
            if self.debug:
                raise ValueError("DEBUG must be off in production")
            if self.api_key is None:
                raise ValueError("API_KEY is required in production")
            if self.database_url.startswith("sqlite"):
                raise ValueError("production needs a real database, not SQLite")
        return self


def load_settings(environ=os.environ, env_file=".env", secrets_dir="/run/secrets"):
    """Lowest to highest priority: defaults, secret files, .env, environment variables."""
    values, sources = {}, {}
    names = list(Settings.model_fields)
    for name in names:                                   # one file per secret
        f = Path(secrets_dir) / name
        if f.is_file():
            values[name], sources[name] = f.read_text().strip(), "secret file"
    if env_file and Path(env_file).is_file():                # a local .env file
        for key, value in dotenv_values(env_file).items():
            if key.lower() in names:
                values[key.lower()], sources[key.lower()] = value, ".env"
    for name in names:                                   # real environment variables win
        if name.upper() in environ:
            values[name], sources[name] = environ[name.upper()], "environment"
    return Settings(**values), sources

settings, _ = load_settings()        # at import time: a bad config stops the process here

Things to try.

  • Start with local and the .env file: everything comes from .env, which is exactly what it is for. Look at the log line: the API key is masked, but the database password dev is printed, because database_url is a plain str.
  • Switch to production with the .env file still there. The service refuses to start: DEBUG=true came from a file that should never have been deployed.
  • Production, no .env, then add the platform DATABASE_URL and the secret file, one at a time, and watch each startup error disappear.
  • Now staging with the secret file and a .env file. It starts, but the API key is the development key from .env, not the mounted secret, because .env outranks secret files. A stray .env in an image silently overrides real configuration.
  • Add the LOG_LEVEL typo in any environment: the service stops at startup with a message naming the field and the allowed values.

Secrets

Secrets never go in code, and never in Git: once committed, a secret stays in the repository's history even after you delete the file, and automated scanners search public repositories for keys within minutes of a push. Put .env in .gitignore on day one, commit a .env.example with placeholder values instead, and turn on secret scanning in your Git host. If a secret is ever committed, rotate it: assume it has been copied.

In production, secrets come from a secret manager (AWS Secrets Manager, Google Secret Manager, Azure Key Vault, HashiCorp Vault) or your platform's secrets feature, delivered as environment variables or, better, as files: Docker mounts secrets under /run/secrets, and Kubernetes can mount them as files too. Files are a little safer than environment variables, which are inherited by every child process and often appear in crash reports and debugging endpoints.

Inside the service, wrap secrets in Pydantic's SecretStr. Measured: repr(), str(), f-strings, logging and model_dump_json() all print **********; only an explicit .get_secret_value() returns the real value. Do the same for anything that contains a secret, such as a database URL with a password in it, or keep the password in its own field.

Environments

Most teams run at least three: local on a developer's machine, staging, which mirrors production as closely as possible and is where changes are tested before release, and production. The goal is that they differ only in configuration. Every code path that checks if settings.app_env == "production" is a path you cannot test before it reaches production, so keep such checks to safety rules like the ones in the validator, and use explicit settings (send_real_emails: bool) rather than inferring behaviour from the environment's name. Each environment gets its own credentials, so a leaked staging key cannot touch production data.

Local services with Docker Compose

A service usually needs a database, a cache and sometimes a queue. Docker Compose starts them locally from one file, at the same versions as production, so "it works on my machine" means something:

# compose.yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: dev           # fine for a local-only database
      POSTGRES_DB: shop
    ports: ["5432:5432"]
    volumes: ["pgdata:/var/lib/postgresql/data"]
  redis:
    image: redis:7
    ports: ["6379:6379"]
volumes:
  pgdata: {}

docker compose up -d starts both, and a .env with DATABASE_URL=postgresql://dev:dev@localhost:5432/shop points the service at them. In CI, the same file can start the same services for integration tests (Chapter 26).

Use case: Uber, 2016

In late 2016 attackers got into a private GitHub repository used by Uber engineers, using login details exposed in an earlier, unrelated breach. In the code they found AWS access credentials, and with those they downloaded data from Uber's cloud storage: names, email addresses and phone numbers of 57 million riders and drivers, and the driving licence numbers of about 600,000 drivers in the United States. Uber paid the attackers $100,000 through its bug bounty programme to delete the data and keep quiet, and did not disclose the breach until November 2017. It later paid $148 million to settle with US states, and its former chief security officer was convicted in 2022 of obstructing an investigation. The technical root of it is the subject of this page: a long-lived cloud credential sat in source code, where anyone who could read the repository could use it. Credentials belong in a secret manager, scoped to what the service needs and rotated, so that reading the code is not the same as owning the infrastructure.

⚠️
Common mistakes
  • Committing .env, keys or passwords to Git, even in a private repository.
  • Copying .env into the container image, where it overrides real configuration.
  • bool(os.environ["DEBUG"]), which is True for "false".
  • Reading os.environ all over the code instead of one validated settings object.
  • Logging the settings object with secrets, or URLs containing passwords, as plain strings.
  • Sharing credentials between staging and production.
  • Behaviour hidden behind if env == "production", which no test environment exercises.

Interview drill

Explain it simply: How should a service get its database password?

How a strong answer sounds
Not from the code or the repository. The password lives in a secret manager or the platform's secrets store, and the platform gives it to the service at start-up, as an environment variable or, better, a mounted file. The service reads it once into a validated settings object, keeps it in a type such as SecretStr so it is masked if anything prints it, and refuses to start if it is missing. Each environment has its own password, the database account has only the permissions the service needs, and the password can be rotated without a code change.

Deeper: A developer accidentally pushed an AWS access key to a public GitHub repository ten minutes ago, then deleted the commit. What do you do?

How a strong answer sounds
Assume it has been copied: automated scanners watch public pushes and find keys in minutes, and deleting the commit does not remove it from forks, caches or anyone who already fetched it. First, deactivate the key in AWS immediately and issue a new one to whatever legitimately used it. Then look at what the key could do and what it did: CloudTrail logs for that key since the push, especially new users, new keys, unusual regions and compute launched for cryptocurrency mining, and access to data stores. Clean up anything unexpected and, if data was accessed, follow the incident and disclosure process. Afterwards, remove the secret from the history properly, and fix the cause: secret scanning with push protection on the repository, a pre-commit hook, and short-lived credentials, such as role-based access or OIDC from CI, so there is no long-lived key to leak.

🧠 Key takeaways

  • One build, many environments: everything that varies is configuration, read from the environment.
  • Load configuration once into a validated settings object, and fail fast at startup.
  • Know your sources' order: environment variables beat .env, which beats secret files and defaults.
  • Secrets live in a secret manager, never in Git, and are wrapped in SecretStr inside the service.
  • Environments differ only in configuration, each with its own credentials.
  • Docker Compose runs the same backing services locally and in CI.
