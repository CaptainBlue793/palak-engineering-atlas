Testing Basics with pytest

A test is a small program that calls your code and checks the answer. A good suite of them lets you change a service on a Friday afternoon and know, within a minute, whether you broke something. pytest is the standard tool for this in Python: tests are plain functions, checks are plain assert statements, and a small set of features, fixtures, parametrisation and monkeypatching, covers almost everything a backend needs.

This page teaches those features on a tiny pricing service, then plants five realistic bugs in it and runs three test suites against each one. All the output in the lab is from real pytest 9.1.1 runs, and it makes one point very clearly: a suite can run every line of your code and still miss the bug.

  • Write tests with plain assert and read pytest's failure output
  • Share setup with fixtures, including a FastAPI test client
  • Test many cases at once with parametrize
  • Replace slow or external pieces with fakes, mocks and dependency overrides
  • Know what line coverage measures, and what it does not

The code under test

A discount function and an endpoint that uses it. Codes are case-insensitive, unknown codes are an error, and a percentage discount is rounded down to whole cents.

# pricing.py
CODES = {"SAVE10": 10, "HALF": 50}


def apply_discount(subtotal_cents: int, code: str | None) -> int:
    """Return the total after a percentage discount, rounding the discount down to whole cents."""
    if code is None:
        return subtotal_cents
    pct = CODES.get(code.upper())
    if pct is None:
        raise ValueError(f"unknown discount code {code!r}")
    discount = subtotal_cents * pct // 100
    return subtotal_cents - discount

# app.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

from pricing import apply_discount

app = FastAPI()


class QuoteIn(BaseModel):
    subtotal_cents: int
    code: str | None = None


@app.post("/quote")
def quote(body: QuoteIn):
    try:
        total = apply_discount(body.subtotal_cents, body.code)
    except ValueError as e:
        raise HTTPException(status_code=400, detail=str(e))
    return {"total_cents": total}

Assertions

A pytest test is any function whose name starts with test_, in a file whose name starts with test_. Inside, use a plain assert. pytest rewrites assert statements so that when one fails, it shows the values involved, not just "AssertionError". Measured, from one of the planted bugs below:

test_values.py:15: in test_discounts
    assert apply_discount(subtotal, code) == expected
E   AssertionError: assert 499 == 500
E    +  where 499 = apply_discount(999, 'HALF')

To check that code raises, use with pytest.raises(ValueError, match="unknown discount code"):. To compare floats, use pytest.approx, since 0.1 + 0.2 == 0.3 is false. Run the suite with pytest, a single file with pytest test_values.py, one test with pytest -k save10, and stop at the first failure with -x.

# test_happy.py
import pytest
from fastapi.testclient import TestClient

from app import app
from pricing import apply_discount


@pytest.fixture
def client():
    return TestClient(app)


def test_no_code_charges_full_price():
    assert apply_discount(10_000, None) == 10_000


def test_save10_takes_ten_percent_off():
    assert apply_discount(10_000, "SAVE10") == 9_000


def test_quote_endpoint(client):
    r = client.post("/quote", json={"subtotal_cents": 10_000, "code": "SAVE10"})
    assert r.status_code == 200
    assert r.json() == {"total_cents": 9_000}

Fixtures

A fixture is a function that provides something a test needs; a test asks for it by naming it as a parameter, as test_quote_endpoint(client) does above. Fixtures keep setup in one place, and with yield they also clean up afterwards:

# conftest.py: fixtures here are available to every test file in the folder
import pytest
from fastapi.testclient import TestClient
from app import app

@pytest.fixture
def client():
    with TestClient(app) as c:       # runs the app's startup and shutdown events
        yield c

@pytest.fixture
def db(tmp_path):                  # tmp_path: a fresh temporary folder, built in
    con = sqlite3.connect(tmp_path / "test.db")
    con.executescript(SCHEMA)
    yield con                         # the test runs here
    con.close()                       # teardown, even if the test failed

By default a fixture runs once per test, so every test starts clean. @pytest.fixture(scope="session") runs it once for the whole run, which suits something expensive, such as starting a database container, as long as tests do not leave data behind for each other. Useful built-in fixtures include tmp_path, monkeypatch and caplog (captured log records).

Parametrize

When the same check applies to many inputs, write the test once and list the cases. Each case runs, and is reported, as a separate test, so one failing case does not hide the others:

# test_values.py
import pytest

from pricing import apply_discount


@pytest.mark.parametrize(
    "subtotal, code, expected",
    [
        (10_000, "save10", 9_000),  # codes are case-insensitive
        (999, "HALF", 500),         # the discount rounds down
        (0, "HALF", 0),
    ],
)
def test_discounts(subtotal, code, expected):
    assert apply_discount(subtotal, code) == expected

Things to try.

  • Start with rounding and + error paths: 5 tests pass with 100% line coverage, and the bug ships. Every line ran; no test checked an odd amount. Switch to + edge values to catch it.
  • Try case-sensitive codes with the same suites. Same story: a customer typing "save10" gets an error, and nothing checked lower case.
  • Pick unknown code ignored with happy path: all green. Now the error-path tests fail, and coverage drops to 87%, because the bug made the error branch unreachable.
  • Pick discount always zero: even the happy path catches it. Bugs on the main path are the easy ones.

Mocks and fakes

Services call things you do not want in a unit test: a payment provider, an email service, the clock. Replace them with a test double. A fake is a simple working implementation, such as an in-memory repository or an email sender that appends to a list. A mock records how it was called so the test can check, for example, that exactly one email was sent to the right address. pytest's monkeypatch fixture swaps an attribute for the duration of one test, and FastAPI's app.dependency_overrides swaps a dependency for the whole app:

class FakeMailer:
    def __init__(self): self.sent = []
    def send(self, to, subject): self.sent.append((to, subject))

def test_order_sends_receipt(client):
    mailer = FakeMailer()
    app.dependency_overrides[get_mailer] = lambda: mailer   # the endpoint gets the fake
    client.post("/orders", json={"sku": "MUG", "email": "a@example.com"})
    assert mailer.sent == [("a@example.com", "Your receipt")]
    app.dependency_overrides.clear()

def test_quote_uses_new_codes(monkeypatch):
    monkeypatch.setitem(pricing.CODES, "VIP", 20)            # undone after the test
    assert pricing.apply_discount(1000, "vip") == 800

Prefer fakes at the edges of your system, and do not mock your own code's internals: a test that asserts "function A called function B with these arguments" breaks on every refactor and proves little. For outgoing HTTP calls made with httpx, the respx library intercepts requests by URL.

Coverage, briefly

Line coverage (pytest --cov=yourpackage, with pytest-cov) reports which lines ran during the tests. It is very good at one thing: showing code that no test touches, such as the error branches the happy-path suite above missed (87%). It cannot tell you whether the tests checked the right things: in the lab, the error-path suite reached 100% and still missed two of the five bugs. Branch coverage (--cov-branch) is stricter, since it also requires each if to go both ways, but has the same blind spot. Treat a coverage number as a floor, not a goal. The question to ask is the one the lab asks: if I broke this line, would a test fail? Mutation-testing tools, such as mutmut, automate exactly that by planting small bugs and checking that your suite catches them.

Use case: Ariane 5 Flight 501, 1996

On 4 June 1996 the first Ariane 5 rocket veered off course and was destroyed about 37 seconds after lift-off. The inquiry traced it to software reused from Ariane 4 in the inertial reference system: a conversion of a 64-bit floating-point value, related to horizontal velocity, into a 16-bit signed integer overflowed, because Ariane 5 flew a faster trajectory than Ariane 4 ever had. The exception shut down both the main and backup units, which ran identical code, and the flight computer steered on diagnostic data as if it were real. The code had worked for years and had been tested; it had never been tested with values from the new flight profile, and the inquiry board noted that tests with realistic Ariane 5 trajectory data would have exposed the fault. It is the lab's lesson at a larger scale: tests that run every line on familiar inputs prove little about the inputs you have not tried. Choose test values at the edges: odd amounts, empty strings, the largest value, the new customer's data.

⚠️
Common mistakes
  • Testing only the happy path, then reading 100% coverage as "done".
  • Tests that depend on each other's leftovers or on the order they run in.
  • Asserting on internal calls instead of results, so every refactor breaks the tests.
  • Calling real external services from unit tests, making them slow and flaky.
  • Forgetting to clear dependency_overrides, leaking a fake into later tests (a fixture with yield fixes it).
  • Comparing floats with == instead of pytest.approx.

Interview drill

Explain it simply: Your service has 100% test coverage. Is it well tested?

How a strong answer sounds
Not necessarily. Coverage only says every line ran during the tests; it says nothing about whether the tests checked the right results. A test can call a function and never assert on its output, or use only easy inputs. In a small experiment, a suite with 100% line coverage missed a rounding bug and a case-sensitivity bug, because no test used an odd amount or a lower-case code. Coverage is useful for finding code that no test touches at all. To judge quality, I would look at whether tests cover edge values and error cases, and whether breaking a line makes a test fail, which is what mutation testing checks automatically.

Deeper: How would you test a FastAPI endpoint that charges a card through a payment provider and then writes an order to the database?

How a strong answer sounds
I would make the payment client a dependency, so tests can override it with a fake that records charges and can be told to succeed, decline or time out. Endpoint tests then use TestClient with that fake and a real but disposable database, a temporary SQLite file or, better, the same database engine as production in a container, created by a fixture and cleaned up after each test. I would cover the success path, a declined card returning the right error without writing an order, a provider timeout, and validation errors, and check both the response and the database state. Retries and duplicate requests deserve a test with an idempotency key (Chapter 15). Separately, a small number of tests against the provider's test environment would check that the real client and the fake agree, run less often than the main suite.

🧠 Key takeaways

  • Tests are functions named test_* with plain asserts; pytest shows the values when one fails.
  • Fixtures provide setup and teardown; conftest.py shares them.
  • Parametrize runs one test over many cases, each reported separately.
  • Fakes and dependency overrides replace external services; avoid asserting on internals.
  • Coverage finds untested code; it does not prove tested code is checked. Test edge values.
