Idempotency & Safe Retries

Networks fail in an awkward way: when a request times out, the client cannot know whether the server never got it, got it and failed, or got it, did the work, and the answer was lost on the way back. The only sensible client behaviour is to retry, and the only safe server behaviour is to make sure a retry cannot do the work twice. For reading data that is free. For "charge this card £49.99" it is the difference between a reliable payment system and one that charges customers twice.

This chapter explains why retries duplicate work and how idempotency keys prevent it, including the subtle case of two identical requests arriving at once. The lab charges real (fake) cards through a FastAPI service in three implementations and counts the charges.

Why retries duplicate work

A client sends POST /payments. The server charges the card, which takes a moment, and replies. If the reply is slower than the client's timeout, or the connection drops, or a load balancer gives up, the client sees a failure for a payment that actually happened. It retries, and the card is charged again. Retries come from everywhere: users pressing the button twice, apps retrying on timeouts, HTTP libraries retrying on connection errors, proxies and queues redelivering. You cannot stop them, and you should not want to, since without them every network blip would lose an order. You make them harmless instead.

Idempotent methods

HTTP already defines GET, HEAD, PUT and DELETE as idempotent (Chapter 2), and a server must honour that: PUT /orders/42/address sent twice leaves one address, and DELETE /orders/42 sent twice leaves one deleted order. Sometimes you can design an operation to be naturally idempotent, for example by letting the client choose the ID, PUT /payments/{client_generated_id}, so a repeat finds the existing payment. POST, the method for "create something new" and "do this action", is not idempotent, and needs an idempotency key.

Idempotency keys

The client generates a unique key, usually a UUID, for each logical operation, sends it in a header (Idempotency-Key, as Stripe popularised and an IETF draft standardises), and reuses the same key for every retry of that operation. The server records the key with the outcome. A new key means new work; a known key means "you asked this already", and the server returns the original result instead of doing it again. Three details make it correct:

  • Reserve before working. Insert the key as "in progress" with a unique constraint before charging. Checking first and inserting afterwards leaves a window where two concurrent requests both see "new".
  • Fingerprint the request. Store a hash of the body with the key; if the same key arrives with a different body, it is a client bug, answer 422, never replay a different payment's result.
  • Answer the in-progress case. A duplicate that arrives while the first is still running gets 409 Conflict with Retry-After; once the first finishes, duplicates get the stored response, marked as a replay.
@app.post("/payments", status_code=201)
def create_payment(body: PaymentIn, idempotency_key: str | None = Header(default=None)):
    con = db()
    try:
        if MODE == "none" or idempotency_key is None:
            return charge_card(con, body)

        fingerprint = hashlib.sha256(body.model_dump_json().encode()).hexdigest()
        if MODE == "naive":
            # check, then act: two requests can both pass the check
            row = con.execute("SELECT response FROM idem WHERE key = ?", (idempotency_key,)).fetchone()
            if row:
                return JSONResponse(json.loads(row[0]), status_code=201, headers={"Idempotent-Replayed": "true"})
            result = charge_card(con, body)
            con.execute("INSERT OR REPLACE INTO idem (key, fingerprint, status, response) VALUES (?, ?, 'done', ?)", (idempotency_key, fingerprint, json.dumps(result)))
            return result

        # proper: reserve the key atomically first, then do the work, then store the response
        try:
            con.execute("INSERT INTO idem (key, fingerprint, status) VALUES (?, ?, 'in_progress')", (idempotency_key, fingerprint))
        except sqlite3.IntegrityError:
            fp, status, response = con.execute("SELECT fingerprint, status, response FROM idem WHERE key = ?", (idempotency_key,)).fetchone()
            if fp != fingerprint:
                return JSONResponse({"code": "idempotency_key_reused", "detail": "This key was used with a different request body"}, status_code=422)
            if status == "in_progress":
                return JSONResponse({"code": "request_in_progress", "detail": "A request with this key is still being processed"}, status_code=409, headers={"Retry-After": "1"})
            return JSONResponse(json.loads(response), status_code=201, headers={"Idempotent-Replayed": "true"})
        result = charge_card(con, body)
        con.execute("UPDATE idem SET status = 'done', response = ? WHERE key = ?", (json.dumps(result), idempotency_key))
        return result
    finally:
        con.close()

Things to try.

  • no idempotency, timeouts and retries: every payment charged four times, and the client still saw only timeouts, so it reported every payment as failed. The worst of both worlds.
  • key, check then act: retries are mostly fixed, because by the time the client retries, the first request has stored its result and the retry gets a replay. Now switch to double clicks: both requests check at the same moment, both see nothing, and both charge.
  • key, reserved atomically: one charge per payment in both scenarios. The second of a concurrent pair gets 409 "in progress"; a retry after the first finished gets the stored response.

Storing and replaying responses

Store the status code and body of the completed operation and return exactly that for duplicates, with a header such as Idempotent-Replayed: true so clients and logs can tell. Decide what to store: final outcomes, successes and business failures such as "card declined", are replayed; failures that happened before any work, such as validation errors, need not be stored, so the client can fix the request and retry with the same key; and if the server crashes mid-operation, an "in progress" row older than a timeout should be resolved by checking with the provider, not by blindly retrying. Scope keys to the client or account, so two customers cannot collide, and expire them after a period long enough to cover retries; Stripe, for example, keeps them for at least 24 hours. When this service calls another service, pass a key on too: idempotency must hold end to end.

Measured on the lab service: the first request with key k-reuse got 201 {"id":"ch_7a8969f7c7","amount_cents":4999,"status":"succeeded"}; the same key with a different amount got 422 {"code":"idempotency_key_reused","detail":"This key was used with a different request body"}; and the original body again got the stored response, with Idempotent-Replayed: true.

Concurrent duplicates

The lab's double-click results are the general lesson: any "check, then act" sequence is a race unless the check and the claim are a single atomic step. The database's unique constraint is the simplest atomic step available, which is why the correct version inserts the key first and lets the database decide who wins. The same pattern appears in Chapters 16 and 17: correctness under concurrency comes from constraints, conditional updates and transactions, not from reading and then deciding in application code.

Use case: client tokens in the Amazon EC2 API

Launching virtual machines has the same problem as charging cards: if a RunInstances call times out and the caller retries, it may launch two fleets and pay for both. The EC2 API therefore accepts a ClientToken, a unique string chosen by the caller for each launch request, and AWS's SDKs and tools use it so that retries return the original result instead of starting more instances. AWS's Builders' Library article "Making retries safe with idempotent APIs" describes the reasoning behind the design, and it maps directly onto this chapter: the caller supplies the unique token; the service records it atomically with the request; a repeat with the same token and the same parameters returns the response to the original request; and a repeat with the same token but different parameters is rejected as an error, rather than silently treated as the same request. Idempotency is not a payments-only concern. Any API whose operations cost money or cannot be undone needs it.

⚠️
Common mistakes
  • Generating a new key on every retry, which makes each retry look new.
  • Check-then-insert instead of an atomic reservation.
  • Replaying the stored response for a different request body.
  • Keys shared across customers, so one customer can receive another's replay.
  • Doing the work before storing the key, leaving a window for duplicates.
  • Not passing idempotency downstream to the payment provider or other services.
  • Client timeouts shorter than normal server latency, turning every request into several.

Interview drill

Explain it simply: What is an idempotency key and why do payment APIs need them?

How a strong answer sounds
When a payment request times out, the client cannot tell whether the charge happened, so it has to retry, and without protection a retry charges again. An idempotency key is a unique value the client creates for one logical payment and sends with every attempt. The server records the key with the outcome the first time; later requests with the same key get the original response instead of a new charge. To be correct, the server must claim the key atomically before doing the work, using a unique constraint, so two simultaneous duplicates cannot both proceed; it should reject the same key with a different body; and while the first request is still running, duplicates get a 409 and retry later.

Deeper: Your service receives a payment request with an idempotency key, charges the card through a provider, and crashes before storing the result. What happens on retry, and how do you make it safe?

How a strong answer sounds
The key is stuck "in progress", and the service does not know whether the charge succeeded. Blindly retrying could charge twice; refusing forever loses the payment. First, pass an idempotency key to the provider too, derived from ours, so if we call the provider again with the same key, the provider returns the original charge instead of creating a new one: the end-to-end chain is idempotent. Then, when a retry finds an "in progress" record older than a reasonable timeout, a recovery step either re-issues the provider call with the same downstream key or queries the provider for the charge, records the real outcome, and replays it. A background job can sweep stale in-progress records too. Using the outbox pattern (Chapter 30), recording the intent in our database before calling out, makes the recovery systematic.

🧠 Key takeaways

  • Timeouts make retries unavoidable; idempotency makes them harmless.
  • GET, PUT and DELETE must be idempotent; POST needs an idempotency key.
  • Reserve the key atomically before working; check-then-act fails under concurrent duplicates.
  • Fingerprint requests, replay stored responses, answer 409 while in progress.
  • Scope and expire keys, and pass idempotency downstream.
