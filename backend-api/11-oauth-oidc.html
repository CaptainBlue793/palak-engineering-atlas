OAuth 2.0 & OpenID Connect

A photo-printing app wants your photos from another service. The bad old way was to give the app your password for that service. OAuth 2.0 replaces that with delegation: you sign in at the photo service itself, approve a limited request ("read your photos"), and the app receives a token that allows only that, for a limited time, revocable at any moment, without ever seeing your password. OpenID Connect builds "Sign in with ..." on top of the same flow.

OAuth is mostly a set of rules for exchanging redirects and tokens safely, and each rule closes a specific attack. So the lab runs a small but real authorization server, and you can watch the normal flow and five attacks against it, request by request.

The roles in OAuth

  • Resource owner: the user, Alice, who owns the photos.
  • Client: the app that wants access. Confidential clients run on servers and can keep a secret; public clients, mobile apps and single-page apps, cannot, since anything in them can be extracted.
  • Authorization server: signs Alice in, shows the consent screen, and issues tokens. Often a product: Auth0, Okta, Keycloak, Microsoft Entra ID, Google.
  • Resource server: your API. It accepts access tokens and checks their scope; it never sees Alice's password.

Authorization code with PKCE

The flow every kind of client should use, as the OAuth 2.0 Security Best Current Practice (RFC 9700, 2025) and the OAuth 2.1 draft recommend:

  1. The app creates a random code_verifier and keeps it. It sends Alice's browser to the authorization server's /authorize with its client_id, a registered redirect_uri, the scope, a random state, and code_challenge = base64url(SHA-256(verifier)).
  2. Alice signs in and consents. The server redirects her browser back to the redirect_uri with a one-time authorization code and the same state; the app checks state matches, which stops an attacker injecting their own code (login CSRF).
  3. The app posts the code and the verifier to /token. The server checks the code is unused, fresh and for this client and redirect URI, and that SHA-256 of the verifier equals the challenge it saw in step 1. Then it issues tokens.

PKCE (Proof Key for Code Exchange, RFC 7636) matters because step 2 travels through the browser and the operating system, where codes can leak: to a malicious app that registered the same custom URL scheme, to logs, to browser history. A stolen code is useless without the verifier, which never left the app. The older implicit flow, which put tokens straight into the redirect, and the password grant, where the app collected the password, are deprecated.

Things to try.

  • stolen code, no PKCE: the malicious app redeems the intercepted code itself and reads Alice's photos. Then with PKCE: the same theft gets invalid_grant, and the real app still completes.
  • code replayed: a second use of a code fails, and the server also revokes the tokens the first use produced, since a replay means the code leaked. The real app's next call is a 401.
  • stolen refresh token: the attacker refreshes first and gets in. When the real app later uses the same, already used, refresh token, the server treats it as theft and revokes the whole session, cutting the attacker off too.
  • client credentials: a back-end job gets a token for orders:read, is refused photos with insufficient_scope, and cannot ask for scopes it was not granted.

Access and refresh tokens

The access token goes to the resource server with every request, so it is short-lived, typically 5 to 60 minutes; it may be opaque, checked with the authorization server, or a signed JWT checked locally (Chapter 12). The refresh token goes only to the authorization server, to get new access tokens without bothering the user. For public clients, refresh tokens should be rotated: each use returns a new one and invalidates the old, and a second use of an old one is treated as theft and revokes the whole family, which is what the lab shows. Your API should answer a missing or invalid token with 401 and WWW-Authenticate: Bearer error="invalid_token", and a token without the needed scope with 403 and error="insufficient_scope".

Client credentials

When there is no user, a nightly report job calling the orders API for example, the client authenticates as itself with the client credentials grant: its ID and secret (or, better, a private-key JWT or mutual TLS) go straight to /token, and it receives an access token limited to the scopes registered for it. This replaces long-lived shared API keys between services with short-lived, scoped, centrally revocable tokens.

OpenID Connect

OAuth is about access: the app gets a token for an API, and the token says nothing to the app about who the user is. OpenID Connect (OIDC) adds authentication: request the openid scope, and the token response also contains an ID token, a signed JWT for the client saying who signed in (sub, the user's stable ID at that provider), when, for which client (aud), with a nonce that ties it to this login. The client must verify its signature, issuer, audience, expiry and nonce. Providers publish their endpoints and keys at /.well-known/openid-configuration. Keep the two tokens in their lanes: the ID token is for the client to log the user in; the access token is for APIs.

🍎
Use case: Sign in with Apple, 2020

In April 2020 the security researcher Bhavuk Jain reported a flaw in Sign in with Apple, which follows the OpenID Connect pattern: after authenticating, Apple issues a signed ID token (a JWT) containing the user's email address, and third-party apps trust that token to log the user in. Before issuing it, Apple's server let the client ask for a token for a chosen email address, and did not properly check that the address belonged to the signed-in user. An attacker could obtain a validly signed token for any email address and take over that person's account in any app using Sign in with Apple that had not added its own checks. Apple found no evidence of abuse, fixed it, and paid Jain $100,000 under its bug bounty programme. Every signature check in the apps passed, because the token really was from Apple; the flaw was in what the provider was willing to assert. Relying parties should verify everything they can, issuer, audience, expiry and nonce, and treat the provider's stable subject identifier, not the email address, as the account key.

⚠️
Common mistakes
  • No PKCE for public clients, or a client secret embedded in a mobile app.
  • Not checking state on the redirect, allowing login CSRF.
  • Loose redirect URI matching, such as prefixes or wildcards, letting codes go to attacker URLs.
  • Long-lived access tokens and refresh tokens that never rotate.
  • Using the access token as proof of identity in the client, or sending ID tokens to APIs.
  • Linking accounts by email address from an unverified claim instead of the provider's subject ID.
  • Writing your own authorization server for production instead of using a maintained one.

Interview drill

Explain it simply: What problem does OAuth solve, and what is PKCE for?

How a strong answer sounds
OAuth lets a user give an app limited access to their data on another service without giving the app their password. The user signs in at the service, approves specific scopes, and the app gets a short-lived access token limited to those scopes, which can be revoked. In the authorization code flow, the service sends a one-time code back to the app through a browser redirect, and the app swaps it for tokens. That redirect is the weak point: on a phone, another app can register the same URL scheme and grab the code. PKCE fixes it: the app makes a random secret, sends only its hash at the start, and must present the secret itself when redeeming the code, so a stolen code is worthless to anyone else.

Deeper: Your company's mobile app and single-page web app call your own API. How would you set up authentication?

How a strong answer sounds
Use a proper authorization server, managed or self-hosted like Keycloak, rather than building one. Both apps are public clients using the authorization code flow with PKCE and exact redirect URIs, with the system browser on mobile rather than an embedded web view. They request the scopes they need, get short-lived access tokens, and on mobile keep a rotating refresh token in the platform's secure storage. For the single-page app I would prefer a backend-for-frontend: a small server-side component does the OAuth flow, keeps tokens on the server and gives the browser an HttpOnly, SameSite session cookie, so tokens are never exposed to JavaScript. The API validates access tokens, either signed JWTs checked against the server's published keys with issuer, audience and expiry, or opaque tokens via introspection, and enforces scopes and object-level checks. OpenID Connect gives the apps the user's identity, with accounts keyed by the subject identifier.

🧠 Key takeaways

  • OAuth delegates limited access without sharing passwords: owner, client, authorization server, resource server.
  • Use the authorization code flow with PKCE and state for every client; implicit and password grants are deprecated.
  • Access tokens are short; refresh tokens rotate, and reuse revokes the session.
  • Services authenticate as themselves with client credentials and limited scopes.
  • OpenID Connect adds a signed ID token for the client; access tokens are for APIs.

Check your understanding

A malicious app intercepts an authorization code issued with PKCE. What happens when it tries to redeem it?

Measured: "PKCE verification failed". The verifier never left the real app.

What is the state parameter for?

Without it, an attacker can log the victim into the attacker's account (login CSRF).

With refresh-token rotation, what should the server do when an already-used refresh token is presented?

Either the attacker or the real app is replaying it; revoking cuts off both, and the user signs in again.

Which grant should a nightly back-end job use to call an API, with no user involved?

The job authenticates as itself and receives only its registered scopes.

What does OpenID Connect add to OAuth?

OAuth on its own is about access to APIs; OIDC is about authentication for the client.
