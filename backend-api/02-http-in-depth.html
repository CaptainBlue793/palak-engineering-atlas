HTTP for API Builders

HTTP is the language your API speaks, and it is richer than "GET to read, POST to write". Each method carries promises that browsers, proxies, caches and retry logic rely on. Each status code tells a client what to do next. Headers carry caching rules, content types, locations and limits. When a service uses these as intended, the rest of the internet cooperates with it for free; when it does not, clients guess, and some of their guesses cause damage.

This chapter looks at HTTP from the server's side, and checks what FastAPI actually does: the lab is 96 real requests, every combination of six methods, four paths and four request headers, sent to a small FastAPI service, with the raw responses.

  • Know which methods are safe and which are idempotent, and why it matters
  • Choose status codes that tell clients what to do
  • Use the headers that matter: Location, ETag, Cache-Control, Vary, Allow, Retry-After
  • Handle content negotiation and compression
  • Explain keep-alive, and what HTTP/2 and HTTP/3 change

Safe and idempotent methods

HTTP (RFC 9110) defines two properties that the rest of the web relies on. A safe method is read-only from the client's point of view: GET, HEAD and OPTIONS. Crawlers, link previews, browser prefetching and caches will happily send safe requests on their own, so a GET must never change anything that matters. An idempotent method has the same effect whether it is sent once or ten times: every safe method, plus PUT and DELETE. Proxies and client libraries retry idempotent requests after a network failure, because a retry cannot do harm. POST is neither, which is why a retried payment needs extra machinery (Chapter 15). PATCH is not idempotent in general: "add 1 to quantity" applied twice is not "add 1" once.

Status codes that mean something

The first digit tells a client how to react: 2xx succeeded, 3xx look elsewhere, 4xx the client must change the request, 5xx the server failed and a retry might work. Within each class, a few codes carry most of the meaning in an API:

  • 200 OK with a body; 201 Created with a Location header naming the new resource; 202 Accepted for work that will finish later; 204 No Content for success with nothing to say.
  • 304 Not Modified for a conditional GET whose resource has not changed; 307 and 308 for redirects that keep the method and body (301 and 302 let clients turn a POST into a GET).
  • 400 malformed request; 401 not authenticated (who are you?) versus 403 authenticated but not allowed; 404 no such resource; 405 method not supported here, with an Allow header; 409 Conflict with the current state; 412 Precondition Failed for a failed If-Match; 415 unsupported body type; 422 well-formed but invalid; 429 Too Many Requests with Retry-After.
  • 500 an unexpected server error; 502 and 504 a proxy could not get a good or timely answer from upstream; 503 temporarily unavailable, ideally with Retry-After.

Never return 200 with {"error": ...} in the body: monitoring, caches, retries and client libraries all read the status code, and they will treat that failure as a success.

Things to try.

  • HEAD /items/1: 405 Method Not Allowed. HTTP requires general-purpose servers to support HEAD wherever they support GET, but FastAPI only answers the methods you declare. Declare @app.api_route("/items/{item_id}", methods=["GET", "HEAD"]) if clients, monitors or link checkers send HEAD.
  • POST /items/1: 405, with allow: GET, even though PUT and DELETE exist on that path too. FastAPI registers each method as a separate route, and the header lists only the first match's methods. Try OPTIONS: same story.
  • Any method on /items/1/: a 307 redirect to the path without the slash, and the Location is an absolute http:// URL. Behind a TLS-terminating proxy, that is a redirect from HTTPS to HTTP unless proxy headers are configured (Prerequisite 8).
  • GET /items/1 with If-None-Match: 304 with an empty body. The client already has this version.
  • GET /items with Accept-Encoding: gzip: the same JSON in far fewer bytes, plus vary: Accept-Encoding. Then Accept: application/xml: FastAPI ignores it and sends JSON with a 200.
  • PUT /items/99: 201 Created, because PUT to a URL that does not exist creates it here. DELETE /items/99: 404.

Headers

Headers carry everything about a message other than its content. The ones an API builder uses most: Content-Type and Content-Length describe the body; Location points at a created resource or a redirect target; ETag is a version identifier for a representation, which clients send back in If-None-Match (to skip downloading an unchanged resource) or If-Match (to update only if nobody else has, Chapter 16); Cache-Control says who may cache a response and for how long (Chapter 18); Vary tells caches which request headers changed the response; Allow lists permitted methods; Retry-After tells a client when to try again. For your own headers, pick plain descriptive names: the X- prefix was deprecated by RFC 6648 in 2012.

from fastapi import FastAPI, Request, Response
from fastapi.responses import JSONResponse

@app.api_route("/items/{item_id}", methods=["GET", "HEAD"])
def get_item(item_id: int, request: Request):
    item = ITEMS.get(item_id)
    if item is None:
        return JSONResponse({"detail": "Item not found"}, status_code=404)
    tag = etag_of(item)                                  # a hash of the representation
    if request.headers.get("if-none-match") == tag:
        return Response(status_code=304, headers={"ETag": tag})
    return JSONResponse(item, headers={"ETag": tag, "Cache-Control": "private, max-age=0, must-revalidate"})

Content negotiation

A client says what it can handle: Accept for media types, Accept-Encoding for compression, Accept-Language for languages. The server picks, and says what it picked in Content-Type, Content-Encoding and Content-Language, plus Vary so caches keep the versions apart. Most JSON APIs support one media type and, like FastAPI, simply ignore Accept, as the lab shows; if you do support several, answer an unsupported one with 406 Not Acceptable. Compression is the negotiation that pays: measured, the 40-item list went from 1,814 bytes to 331 bytes with gzip, about 5.5× smaller. Compress text responses above a few hundred bytes; smaller ones gain little and cost CPU.

Keep-alive and connections

HTTP/1.1 keeps connections open by default, so a client can send request after request without a new TCP and TLS handshake each time. Measured on loopback, with no network latency at all, 200 GET requests took 0.15 s on one kept-alive connection and 1.96 s with a new connection for each, about 13× slower; across a real network, each new connection also costs one or more round trips. Use one long-lived client per process (httpx.Client or AsyncClient, or a requests.Session) rather than a new one per call. HTTP/1.1 still handles one request at a time per connection, so browsers open several. HTTP/2 multiplexes many requests over one connection and compresses headers; HTTP/3 runs over QUIC on UDP, which avoids head-of-line blocking when packets are lost and makes connection setup faster. For an API, these are mostly configured at the proxy or load balancer, while your service keeps speaking HTTP/1.1 behind it.

🗑️
Use case: Google Web Accelerator, 2005

In May 2005 Google released Web Accelerator, a browser add-on that sped up browsing by prefetching: while you read a page, it followed the links on it in the background, so the next page was already loaded. Following links is a GET, and GET is supposed to be safe. But several web applications, including some from 37signals, had "delete" and "cancel" links that were plain GET requests, protected only by a JavaScript confirmation dialog. The accelerator did not run the dialogs; it simply requested the URLs, and users found records in their own applications deleted by their own browsers. The developers blamed Google; the HTTP specification sided with Google. The pattern still recurs with search crawlers, link previews in chat apps and security scanners, which all follow GET links freely. Anything that changes state must use POST, PUT, PATCH or DELETE, and never a GET, however convenient a link would be.

⚠️
Common mistakes
  • State-changing GET requests, such as GET /orders/42/cancel.
  • 200 with an error in the body, invisible to monitoring and retries.
  • 401 and 403 swapped, or 500 for invalid input that deserves a 4xx.
  • 201 without a Location header, leaving clients to guess where the new resource is.
  • Forgetting HEAD, which FastAPI does not add for you.
  • A new HTTP client per call to another service, paying a handshake every time.
  • Compression without Vary: Accept-Encoding when you build it yourself, so caches serve gzip to clients that cannot read it.

Interview drill

Explain it simply: What is the difference between PUT and POST?

How a strong answer sounds
PUT puts a complete representation at a URL the client names, such as PUT /items/42: it replaces that resource, or creates it if it does not exist, and doing it twice leaves the same result, so it is idempotent and safe to retry. POST asks the server to process the body, typically to create a new item in a collection, POST /items, where the server chooses the ID and returns 201 with a Location header. Sending the same POST twice usually creates two items, so it is not idempotent, which matters when a client retries after a timeout. PATCH is for changing part of a resource.

Deeper: A mobile app shows a product list that rarely changes but is fetched on every screen. How can HTTP itself make this cheaper?

How a strong answer sounds
Several layers. Give the response an ETag, a hash or version of the representation, and support conditional requests: the app sends If-None-Match and gets a 304 with no body when nothing changed, which saves bandwidth and serialisation. Add Cache-Control: if the list can be a minute stale, max-age=60 lets the app's HTTP cache, and a CDN if the data is public, answer without asking the server at all; private keeps per-user responses out of shared caches. Compress with gzip or Brotli and set Vary: Accept-Encoding. Keep connections alive, ideally over HTTP/2, so repeated calls skip handshakes. And paginate, so each call is small. Each of these is a standard behaviour that clients and caches already implement.

🧠 Key takeaways

  • GET, HEAD and OPTIONS are safe; PUT and DELETE are idempotent; POST is neither.
  • Status codes drive client behaviour: 201 with Location, 204, 304, 409, 412, 422, 429 with Retry-After.
  • FastAPI does not add HEAD, lists only one route's methods in Allow, and redirects trailing slashes with an absolute URL.
  • ETags make conditional requests and safe concurrent updates possible.
  • Compress text responses, set Vary, and reuse connections.

Which methods are idempotent?

Sending them several times has the same effect as once, so retries are safe. OPTIONS is idempotent too.

412 is for If-Match failing on an update; 304 is for an unchanged GET.
