ORMs, Migrations & N+1 Queries

An ORM (object-relational mapper) lets you work with database rows as Python objects: order.customer.name instead of a join you wrote yourself. It saves a great deal of code, and it hides a great deal too, above all when SQL runs. A loop that touches order.customer looks free and may send a query per iteration. Migrations are the other half: the schema changes over time, and every database, on every laptop and in every environment, has to change with it, in the same order.

This chapter uses SQLAlchemy 2.x, Python's most widely used ORM, and Alembic, its migration tool. Every SQL statement in the lab was captured from real runs against a database of 5,000 orders.

  • Map tables to classes with SQLAlchemy's typed declarative models
  • Create, review and apply migrations with Alembic
  • Choose lazy, joined, select-in or raise loading for each relationship
  • Spot and fix N+1 queries, and stop them coming back
  • Know when to drop down to SQL

Mapping tables to classes

In SQLAlchemy 2.x, each table is a class with typed Mapped[...] attributes, and relationships are attributes too. These are the models the lab uses:

from datetime import datetime

from sqlalchemy import ForeignKey, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship


class Base(DeclarativeBase):
    pass


class Customer(Base):
    __tablename__ = "customers"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(80))
    orders: Mapped[list["Order"]] = relationship(back_populates="customer")


class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    customer_id: Mapped[int] = mapped_column(ForeignKey("customers.id"))
    status: Mapped[str] = mapped_column(String(20))
    created_at: Mapped[datetime]
    customer: Mapped[Customer] = relationship(back_populates="orders")
    lines: Mapped[list["OrderLine"]] = relationship(back_populates="order")


class OrderLine(Base):
    __tablename__ = "order_lines"
    id: Mapped[int] = mapped_column(primary_key=True)
    order_id: Mapped[int] = mapped_column(ForeignKey("orders.id"))
    sku: Mapped[str] = mapped_column(String(40))
    quantity: Mapped[int]
    order: Mapped[Order] = relationship(back_populates="lines")

Two ideas sit underneath. The session keeps an identity map: within one session, each row is one Python object, so loading customer 7 twice returns the same object without a second query. And it is a unit of work: you change objects, and on commit() the session works out the INSERTs, UPDATEs and DELETEs, in the right order.

Migrations with Alembic

A migration is a versioned script that moves the schema from one revision to the next (upgrade) and back (downgrade). Alembic keeps them in a folder, in a chain, and records the current revision in an alembic_version table in each database. alembic revision --autogenerate compares your models with the database and drafts the script. In the lab project, adding index=True to OrderLine.order_id and a new gift_note column produced, for real:

# alembic revision --autogenerate -m "gift note"
Detected added index 'ix_order_lines_order_id' on '('order_id',)'
Detected added column 'orders.gift_note'

# the generated script
def upgrade() -> None:
    """Upgrade schema."""
    # ### commands auto generated by Alembic - please adjust! ###
    op.create_index(op.f('ix_order_lines_order_id'), 'order_lines', ['order_id'], unique=False)
    op.add_column('orders', sa.Column('gift_note', sa.String(length=200), nullable=True))
    # ### end Alembic commands ###


def downgrade() -> None:
    """Downgrade schema."""
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_column('orders', 'gift_note')
    op.drop_index(op.f('ix_order_lines_order_id'), table_name='order_lines')
    # ### end Alembic commands ###

# alembic upgrade <previous>:head --sql  (the SQL it would run, on SQLite)
CREATE INDEX ix_order_lines_order_id ON order_lines (order_id);
ALTER TABLE orders ADD COLUMN gift_note VARCHAR(200);

Always read the draft. Autogenerate cannot tell a rename from a drop and an add, so renaming a column produces a script that deletes the column and its data and creates an empty one. It also misses some changes, such as certain constraint and type changes, depending on the database. Commit migrations with the code that needs them, run them as a separate deploy step rather than from every worker at startup, and on large production tables, make each change safe to run while the old code is still serving (Chapter 37).

Lazy and eager loading

When you touch a relationship, SQLAlchemy must load it. The loading strategy decides when and how:

  • Lazy (the default, lazy="select"): one query the first time each object's relationship is touched. Fine for one object; an N+1 in a loop.
  • joinedload: add a JOIN to the original query, so everything comes back in one statement. Best for many-to-one relations such as an order's customer; for collections it repeats each parent row once per child, so call .unique(), and watch the row count grow.
  • selectinload: after the main query, one more query per relationship, WHERE id IN (...). Usually the best choice for collections.
  • raiseload: touching an unloaded relationship raises an error. A guard that turns a hidden N+1 into a failing test.

Things to try.

  • lazy, 50 orders: 100 statements, one for the orders, then a customer and a lines query per order, minus customers already in the identity map. At 200 orders it is 359.
  • selectinload: 3 statements whatever the size, with IN (...) lists. joinedload: one statement, built around a subquery so the LIMIT applies to orders, not rows.
  • Switch the index on: every strategy speeds up, lazy loading most, because each of its many lines queries no longer scans the whole table. That is the migration above.
  • raiseload: the first touch of order.customer raises. In a test suite, this is how you stop an N+1 from creeping back in.

The N+1 problem

N+1 queries are the most common ORM performance bug because they are invisible in the code and harmless in development, where lists are short and the database is on the same machine. They show up in production as endpoints that slow down as data grows and as databases with high query rates but low work per query. Find them by counting: log SQL in development (create_engine(..., echo=True)), count statements per request in tests or in tracing (Chapter 31), and fail a test when a list endpoint's query count depends on the list's length. Fix them with eager loading chosen per query, and consider lazy="raise" on relationships, so every load is a deliberate decision. Async SQLAlchemy already behaves like this: implicit lazy loading would need hidden I/O, so it raises instead.

When to write raw SQL

An ORM is best at loading and saving objects. For other work, SQL is clearer and faster: reports with grouping and window functions, bulk updates (UPDATE orders SET status = 'expired' WHERE ... as one statement, not 10,000 objects loaded and saved), upserts, recursive queries and anything where you are fighting the ORM to produce a specific query. SQLAlchemy makes this easy without leaving it: select() and update() in Core build SQL from Python, and text("... :param") runs SQL you wrote, with parameters, in the same session and transaction.

Use case: Braintree's safe operations for PostgreSQL, 2014

Braintree, the payments company, ran large PostgreSQL databases behind a Rails application, where migrations are as routine as they are with Alembic. Some of those routine migrations caused trouble on large, busy tables, and in 2014 the team published "Safe Operations For High Volume PostgreSQL", a list of which schema changes lock tables and how to avoid it. Adding a column with a default value, in the PostgreSQL versions of the time, rewrote the whole table while holding a lock, so writes queued behind it; add the column without a default, backfill in batches, then set the default. Adding an index normally blocks writes; use CREATE INDEX CONCURRENTLY. Changing a column's type rewrites the table; add a new column instead. PostgreSQL 11 (2018) later made adding a column with a constant default instant, but the rule stands: a one-line migration that is instant on a laptop can be a long lock in production, so migrations deserve the same review as code, against production-sized data.

⚠️
Common mistakes
  • Relationships touched in loops without eager loading.
  • joinedload on large collections, multiplying rows and memory.
  • Committing an autogenerated migration unread, including a rename turned into drop and add.
  • Running migrations from every worker at startup, racing each other.
  • Foreign keys without indexes, which many databases, including PostgreSQL and SQLite, do not add for you.
  • Loading thousands of objects to update a field that one UPDATE statement could change.
  • Editing a migration that has already run somewhere, instead of adding a new one.

Interview drill

Explain it simply: What is the N+1 query problem and how do you fix it with an ORM?

How a strong answer sounds
It happens when code loads a list of N objects with one query, then touches a relationship on each one, and the ORM lazily runs one more query per object: N+1 queries where one or two would do. It is invisible in the code, since order.customer.name looks like an attribute, and invisible in development with short lists, but in production it multiplies round trips and database load as data grows. The fix is to load relationships eagerly for that query: in SQLAlchemy, joinedload for many-to-one, selectinload for collections, which brings it to a fixed small number of queries. To keep it fixed, I would count queries per request in tests and use raiseload so unplanned lazy loads fail loudly.

Deeper: You need to rename a column in a busy production table used by a running service. How do you do it with Alembic?

How a strong answer sounds
Not as one migration: autogenerate would draft a drop and an add, losing the data, and even a real ALTER TABLE ... RENAME breaks the old code that is still running during a rolling deploy. I would use expand and contract. First migration: add the new column. Deploy code that writes to both columns and reads the old one. Backfill the new column in batches, outside a long transaction. Deploy code that reads the new column, still writing both. Then deploy code that only uses the new column, and finally a migration that drops the old one. Each step is backwards compatible with the code running alongside it, each migration is small and quick to apply, and any step can be rolled back. On PostgreSQL, I would also check each statement's locks and set a lock timeout, so a migration waiting for a lock cannot block all writes behind it.

🧠 Key takeaways

  • SQLAlchemy maps tables to typed classes; the session's identity map and unit of work manage objects.
  • Alembic autogenerates migration drafts; read every one, especially for renames.
  • Lazy loading in a loop is N+1: 359 statements for 200 orders in the lab.
  • Use joinedload for many-to-one, selectinload for collections, and raiseload as a guard.
  • Index foreign keys, and use SQL directly for reports and bulk changes.
