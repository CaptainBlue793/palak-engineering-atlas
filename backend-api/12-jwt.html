JWTs Done Right

A JSON Web Token is a set of claims, such as "this is user 42, allowed to read orders, until 10:40", signed by an issuer so that any service holding the issuer's public key can check it without calling anyone. That makes JWTs popular as access tokens: an API can verify one in a fraction of a millisecond, with no database lookup. It also makes them dangerous, because everything rests on the verifier checking the right things, and the token itself tells the verifier how to check it.

This chapter takes a JWT apart, then runs eight tokens, one valid and seven forged or misused, through three verifiers written with PyJWT, from careless to strict.

  • Read a JWT's header, payload and signature, and know none of it is secret
  • Verify with a fixed algorithm list, the right key, issuer and audience
  • Handle expiry and clock skew with exp, nbf, iat and a small leeway
  • Plan for revocation: short lifetimes, refresh tokens, denylists and key rotation
  • Choose between JWTs and opaque tokens

Header, payload, signature

A JWT is three base64url-encoded parts joined by dots. The header names the signing algorithm (alg) and usually the key ID (kid). The payload holds the claims: registered ones such as iss (issuer), sub (subject), aud (audience), exp (expiry), nbf (not before), iat (issued at) and jti (token ID), plus your own, such as scope. The signature covers the first two parts. Base64url is an encoding, not encryption: anyone holding a JWT can read its payload, so never put secrets or personal data in one you would not show the bearer. (Encrypted JWTs, JWE, exist but are rarely what an API needs.)

# the lab's valid token, decoded (signed RS256 with a 2048-bit key)
header:  {"alg": "RS256", "kid": "k1", "typ": "JWT"}
payload: {"iss": "https://auth.example.com", "aud": "orders-api", "sub": "user_42", "scope": "orders:read", "iat": 1792032326, "exp": 1792032926}

Verifying signatures

Verification is where JWT bugs live. The rules, all visible in the lab:

  • Never trust a token you have not verified. Decoding without verification is fine for debugging and nothing else.
  • Fix the algorithms yourself. Pass an allowlist, such as algorithms=["RS256"]; never take alg from the token. Two classic attacks abuse it: "alg": "none", an unsigned token, and algorithm confusion, where an attacker signs with HMAC using your public key as the secret and sets "alg": "HS256", hoping the verifier feeds the same key to HMAC.
  • Get keys from the issuer you trust, usually its JWKS document (from /.well-known/openid-configuration), selected by kid and cached. Never fetch keys from a URL inside the token.
  • Check iss and aud. A genuine token issued for another API must not work on yours.
  • Require the claims you rely on, such as exp and sub, so a token without them is rejected rather than treated as everlasting.
import jwt
from jwt import PyJWKClient

jwks = PyJWKClient("https://auth.example.com/.well-known/jwks.json")   # caches keys, picks by kid

def verify(token: str) -> dict:
    key = jwks.get_signing_key_from_jwt(token).key
    return jwt.decode(token, key,
        algorithms=["RS256"],                     # never from the token
        audience="orders-api", issuer="https://auth.example.com",
        leeway=30,                                # seconds of clock skew
        options={"require": ["exp", "iat", "sub", "aud", "iss"]})

Things to try.

  • no verification: every forged token is accepted, including alg: none and an edited payload. The attacker is now admin_1 with refund rights.
  • algorithm from the header with alg none and the confusion token: PyJWT refuses both on its own, because it will not use a key with "none" and will not use an RSA public key as an HMAC secret. Older libraries in several languages did, which is how the attacks became famous. But other audience and no exp still get in.
  • strict with expired 20 s ago: accepted, because of the 30-second leeway for clock differences between servers. With leeway=0, PyJWT answered: ExpiredSignatureError: Signature has expired.

Expiry and clock skew

A JWT is valid until exp, whatever happens in the meantime, so access tokens should live minutes, not days: 5 to 15 minutes is common. Servers' clocks differ slightly, so allow a small leeway, around 30 to 60 seconds, when checking exp, nbf and iat; more than that quietly extends every token's life. Keep clocks synchronised with NTP, and reject tokens whose iat is in the future beyond the leeway.

Revocation

The price of not looking anything up is that you cannot simply delete a JWT. The tools, roughly in order of use: short lifetimes, so a stolen token expires soon, with refresh tokens, which live on the server and can be revoked, to get new ones (Chapter 11); a denylist of revoked jti values or of users whose tokens before a certain time are invalid, checked on each request in a fast store, which reintroduces a lookup but a cheap one; and key rotation, publishing a new key with a new kid and, in an emergency, withdrawing the old one, which invalidates every token it signed.

JWT versus opaque tokens

An opaque token is a random string the API checks by asking the authorization server (token introspection, RFC 7662) or a shared store; it reveals nothing and can be revoked instantly, at the cost of a lookup per request, usually cached for a short time. HS256 needs the same secret to sign and verify, so every verifying service could also mint tokens; use it only inside one trust boundary. RS256 and ES256 let any number of services verify with a public key while only the issuer signs, which is why authorization servers use them. Either way, verification is far cheaper than a network round trip, which is the whole appeal.

Use case: the JWT library vulnerabilities of 2015

In March 2015 the security researcher Tim McLean published "Critical vulnerabilities in JSON Web Token libraries". He had found that many popular libraries, in JavaScript, Python, PHP and other languages, trusted the token's alg header. Some accepted "alg": "none" tokens, with no signature at all, as valid, if the application called the verify function without restricting algorithms. Others, given an RSA public key and a token claiming HS256, used the public key as an HMAC secret, so anyone who knew the public key, which is public by design, could forge tokens. The libraries were fixed, which is why PyJWT refused both attacks in the lab, and the JWT best current practices document (RFC 8725, 2020) now tells verifiers to allow only specific algorithms and to bind each key to one. The general lesson is about where trust comes from: input that arrives inside the token can never decide how the token is checked.

⚠️
Common mistakes
  • Decoding without verifying and then trusting the claims.
  • Taking the algorithm from the token, or allowing "none".
  • Not checking aud and iss, so tokens for other services work on yours.
  • Long-lived access JWTs with no revocation plan.
  • Secrets or personal data in the payload, which anyone holding the token can read.
  • Weak HS256 secrets, which can be brute-forced offline from any token.
  • Storing JWTs in localStorage in browsers, where any cross-site scripting bug can read them.

Interview drill

Explain it simply: How does an API verify a JWT access token?

How a strong answer sounds
It reads the key ID from the header and fetches the matching public key from the issuer it trusts, from the issuer's published JWKS, cached. It verifies the signature using an algorithm it has fixed in its own configuration, such as RS256, never the algorithm the token names. Then it checks the claims: the issuer is the expected one, the audience is this API, the token has not expired and is not used before its not-before time, allowing a small clock skew. Only then does it use the subject and scopes, and it still does its own authorisation, such as object-level checks. If any step fails, the answer is 401 with a WWW-Authenticate header.

Deeper: Your API uses 24-hour JWT access tokens. A user's laptop is stolen. What can you do now, and what would you change?

How a strong answer sounds
Right now the stolen token stays valid for up to 24 hours on its own, so I need state: add the user, or that token's jti, to a denylist checked on every request, in Redis or a cached table, with entries expiring when the tokens would. Revoke the user's refresh tokens and sessions at the authorization server so no new access tokens are issued, and force re-authentication. If the signing key itself might be compromised, rotate it. Going forward, I would cut access-token lifetime to minutes, rely on rotating refresh tokens kept on the server, use a "tokens issued before this time are invalid" timestamp per user for cheap mass revocation, and consider sender-constrained tokens, such as DPoP or mutual TLS, so a copied token is useless on another device.

🧠 Key takeaways

  • A JWT is signed, not encrypted: anyone can read the payload.
  • Verify with a fixed algorithm list and keys from a trusted issuer; check iss, aud and exp.
  • Allow a small leeway for clock skew, not a large one.
  • JWTs cannot be deleted: keep them short-lived, revoke refresh tokens, and keep a denylist for emergencies.
  • RS256 and ES256 let many services verify while only the issuer signs; opaque tokens trade a lookup for instant revocation.
