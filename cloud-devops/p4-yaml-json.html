YAML & JSON

Kubernetes manifests, GitHub Actions workflows, Docker Compose files, Helm values and Ansible playbooks are all YAML. Cloud APIs answer in JSON. YAML looks friendly, but it guesses the type of every unquoted value, and some of its guesses are famous for breaking deployments: a country code becomes false, a file mode becomes a different number, a version number loses a digit. This chapter covers the structure you need and the traps to quote your way around, then shows how to slice JSON with jq.

  • Reuse configuration with anchors, aliases and merge keys
  • Predict how YAML 1.1 and 1.2 parsers type unquoted values, and when to quote
  • Query and reshape JSON from cloud CLIs with jq

YAML structure in five rules

YAML describes the same data JSON does (maps, lists, strings, numbers, booleans and null) using indentation instead of brackets. Five rules cover nearly everything you will write:

  • Maps are key: value pairs; the space after the colon is required.
  • Lists are lines starting with - ; a list item can itself be a map.
  • Nesting is indentation, with spaces only. Tabs are not allowed. The number of spaces does not matter as long as siblings line up; two is the convention.
  • Comments start with #. JSON has no comments, which is one reason people prefer YAML for configuration.
  • Multi-line strings: | keeps line breaks (use it for scripts and certificates); > folds lines into one long line (use it for prose).
# A Kubernetes container spec: a map containing lists of maps.
containers:
  - name: web
    image: ghcr.io/shop/web@sha256:4c1e…
    ports:
      - containerPort: 8080
    env:
      - name: LOG_LEVEL
        value: "info"
    command: ["/bin/sh", "-c"]        # flow style: JSON-like brackets also work
    args:
      - |                                  # literal block: newlines kept
        echo "starting"
        exec /app/server --port 8080

One file can hold several documents separated by ---. Kubernetes uses this constantly: a Deployment, its Service and its ConfigMap in one app.yaml, applied together with kubectl apply -f app.yaml.

Anchors, aliases and merge keys

Configuration repeats itself: three services with the same logging and restart settings. YAML lets you name a node with an anchor (&name), reuse it with an alias (*name), and merge a map into another with <<:, overriding individual keys:

# docker-compose.yaml
x-defaults: &defaults                 # x- keys are ignored by Compose: a place to keep anchors
  restart: unless-stopped
  logging:
    driver: json-file
    options: { max-size: "10m", max-file: "3" }

services:
  api:
    <<: *defaults                         # copy every key from defaults…
    image: shop/api:4.18.2
  worker:
    <<: *defaults
    image: shop/worker:4.18.2
    restart: always                       # …and override one

Anchors are resolved by the parser, so the program reading the file never sees them. Not every tool supports the merge key: it was part of YAML 1.1 and is not in the 1.2 core schema, though most libraries still accept it. Check before relying on them in a given tool; Helm and Kustomize (Chapter 16) are the usual way to remove repetition from Kubernetes manifests.

The traps: YAML guesses types

In JSON, "NO" is a string and false is a boolean, and you can always tell which. In YAML, an unquoted value's type is inferred from how it looks, by rules that changed between YAML 1.1 (2005) and YAML 1.2 (2009). Many widely used parsers still follow 1.1 for some values, including PyYAML (Python) and the YAML library Kubernetes uses, which treats yes, no, on and off as booleans. The rule that avoids all of them: quote every string that could look like something else: country and language codes, versions, file modes, times, phone numbers, IDs with leading zeros, and environment variable values. In Kubernetes, env values must be strings, so value: yes or value: 8080 is rejected by the API server; value: "8080" is correct.

JSON and jq

JSON is stricter and simpler: double-quoted strings, no comments, no trailing commas, and the type is always explicit. YAML 1.2 is designed as a superset of JSON, so a JSON file is also valid YAML. You will read JSON far more than you write it: every cloud CLI can print it (aws … --output json, kubectl get … -o json, gcloud … --format=json). jq is the tool for slicing it:

# Names of pods that are not Running
$ kubectl get pods -o json | jq -r '.items[] | select(.status.phase != "Running") | .metadata.name'
checkout-7d9f6b-x2kq9

# Instance ID and state as tab-separated columns
$ aws ec2 describe-instances | jq -r '.Reservations[].Instances[] | [.InstanceId, .State.Name] | @tsv'
i-0a12b3c4d5e6f7081    running
i-0b98c7d6e5f4a3210    stopped

# Build JSON safely in a script (no hand-escaped quotes)
$ jq -n --arg v "$VERSION" '{version: $v, deployed_by: "ci"}'
{ "version": "4.18.2", "deployed_by": "ci" }

.items[] iterates an array, | feeds each element on, select(…) filters, and -r prints raw strings without quotes, ready for the next shell command. yq does the same for YAML files, which is handy in CI for reading a value out of a Helm chart.

Use case: the Norway problem

A service keeps its supported markets in YAML: countries: [GB, IE, FR, DE, NO]. Loaded with a YAML 1.1 parser, the list becomes ["GB", "IE", "FR", "DE", false]. Nothing crashes; Norwegian customers simply stop seeing the shop, and the bug appears only when someone asks why sales from one country went to zero. The fix is one pair of quotes, "NO", and the lasting fix is a linter in CI: yamllint has a "truthy" rule that flags unquoted yes, no, on and off.

⚠️
Common mistakes
  • Unquoted look-alikes: NO, yes, 0755, 1.10, 22:22. Quote them.
  • Tabs for indentation. YAML forbids them; editors that insert tabs produce parse errors.
  • Wrong indentation level. env: indented under ports: becomes part of the port, and Kubernetes may silently drop an unknown field. Validate with kubectl apply --dry-run=server.
  • Numbers in env values. Environment variables are strings; write "8080".
  • Building JSON with string concatenation in Bash. One quote in a value breaks it. Use jq -n --arg.

Interview drill

Explain it simply: Why does country: NO sometimes become false in YAML?

How a strong answer sounds
YAML infers the type of unquoted values. Under the YAML 1.1 rules, the words yes, no, on and off in any common capitalisation are booleans, so NO is false. YAML 1.2 narrowed booleans to true and false, but many parsers in use, such as PyYAML and the library Kubernetes uses, still apply the 1.1 rules to these words. The fix is to quote string values that could be read as something else, and to run a linter in CI.

Deeper: A teammate's manifest applies without error but the container never gets its LOG_LEVEL variable. What would you check?

How a strong answer sounds
Indentation first: if env: is nested at the wrong level, for example under ports or at the pod level instead of the container, it is either a different field or an unknown one. Older clients and some fields drop unknown keys silently. I would run kubectl apply --dry-run=server -f (the server warns about unknown fields), compare with kubectl get pod -o yaml to see what was actually stored, and check kubectl exec … -- env. To prevent it, validate manifests in CI with a schema validator such as kubeconform.

🧠 Key takeaways

  • YAML is maps, lists and scalars nested by space indentation; | keeps newlines, > folds them, --- separates documents.
  • Anchors (&), aliases (*) and merge keys (<<:) remove repetition, if your tool supports them.
  • Unquoted values are typed by guessing; YAML 1.1 rules turn NO into false, 0755 into 493 and 22:22 into 1342.
  • Quote anything that is meant to be a string; Kubernetes env values must be strings.
  • JSON is explicit and strict; slice it with jq and build it with jq -n --arg.

Check your understanding

A YAML 1.1 parser reads countries: [GB, NO, SE]. What does the program receive?

In YAML 1.1, unquoted yes/no/on/off (and their capitalisations) are booleans, so NO is false. Quote country codes.

What is the value of version: 1.10 after parsing?

An unquoted 1.10 matches the float pattern in every version, and the float 1.10 equals 1.1. Write "1.10" when it is a version.

Which YAML string keeps its line breaks, as needed for an embedded shell script?

| is a literal block scalar and keeps newlines; > folds them into spaces. & defines an anchor, not a string style.

Why does Kubernetes reject env: [{name: PORT, value: 8080}]?

EnvVar.value is typed as a string in the API. The YAML is converted to JSON with 8080 as a number, so decoding fails. Write "8080".

Which jq program prints the names of pods that are not Running, one per line, without quotes?

.items[] iterates, select filters, .metadata.name extracts, and -r prints raw strings.
