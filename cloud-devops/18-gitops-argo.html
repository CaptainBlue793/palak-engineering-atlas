GitOps with Argo CD

Ask of any cluster "what is supposed to be running here?" and the honest answer is often: whatever the last few pipelines and people applied. GitOps replaces that with a rule. A Git repository holds the complete desired state, and a controller inside the cluster keeps making the cluster match it. A deployment becomes a merged pull request, a rollback is a revert, and a change made by hand is something the system notices and can undo. This chapter covers the two models of deployment, Argo CD's Application object, what "synced", "drifted" and "healthy" mean, and how a version is promoted from one environment to the next.

Push and pull

In the pipeline from Chapter 10, the last job ran a deploy script against the cluster. That is push-based deployment: something outside the cluster connects to it and applies changes. It is simple, and it has three weaknesses that grow with scale. The CI system must hold credentials powerful enough to change production, which makes it the best target in the company. The cluster's state is only correct at the moment of the push: whatever happens afterwards, a manual kubectl edit or a half-failed deploy, goes unnoticed. And to answer "what is running?" you must reconstruct it from pipeline logs.

In pull-based deployment, an agent runs inside the cluster. It watches a Git repository, compares what the repository says with what the cluster has, and applies the difference. Nothing outside needs cluster credentials: the pipeline's last step is a commit.

The idea is usually summarised as four principles. The desired state is declarative. It is versioned and immutable, which Git provides. It is pulled automatically by agents. And it is continuously reconciled: the agents keep comparing and correcting, not only when something is deployed. Argo CD and Flux are the two widely used implementations; this chapter uses Argo CD, and the ideas transfer.

Argo CD applications

Argo CD runs in the cluster as a few Deployments, with a web interface and a CLI. Its unit of work is the Application: an object that says "render what is at this path of this repository at this revision, and make that namespace of that cluster match it".

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: web-prod, namespace: argocd }
spec:
  project: shop                               # limits which repositories and namespaces this app may use
  source:
    repoURL: https://github.com/acme/deploy-config
    path: apps/web/overlays/prod               # a Kustomize overlay, a Helm chart or plain manifests
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc     # the cluster Argo CD itself runs in
    namespace: shop
  syncPolicy:
    automated:
      prune: true                              # delete what was removed from Git
      selfHeal: true                           # undo changes made directly in the cluster
    syncOptions: [CreateNamespace=true]
$ argocd app get web-prod
Name:               argocd/web-prod
Repo:               https://github.com/acme/deploy-config
Path:               apps/web/overlays/prod
Sync Policy:        Automated (Prune)
Sync Status:        Synced to main (41d07e3)
Health Status:      Healthy

$ argocd app diff web-prod        # what differs between Git and the cluster, field by field
$ argocd app history web-prod     # every revision that was synced, and when

Argo CD does the rendering itself, so the repository holds Helm values or Kustomize overlays, exactly as in Chapter 16. With dozens of services and clusters, Applications are themselves generated: an ApplicationSet stamps one out for each directory or each cluster, and the Application objects live in Git like everything else.

Sync and drift

Argo CD reports two separate things about every application, and confusing them is the most common mistake.

  • Sync status compares Git with the cluster. Synced means the live objects match what the repository renders to. OutOfSync means they differ: Git moved ahead and nothing has applied it yet, or someone changed the cluster.
  • Health asks whether the objects are working: a Deployment's pods are ready, a Service has endpoints. An application can be perfectly Synced to a commit that names an image which does not exist, and be Degraded. Synced means "the cluster is what Git says", not "what Git says is good".

What Argo CD does about a difference is set by three switches.

SettingOffOn
Automated syncDifferences are shown. A person presses SyncA new commit is applied without anyone pressing anything
Self-healA change made in the cluster stays, shown as OutOfSync, until the next commit is syncedA change made in the cluster is reverted within seconds
PruneAn object deleted from Git stays in the cluster, marked as needing pruningAn object deleted from Git is deleted from the cluster

Notice what automated sync alone does not do: it reacts to changes in Git, not to changes in the cluster. Without self-heal, a manual edit survives until some later commit happens to overwrite it. Argo CD looks for new commits every three minutes by default, or at once if the Git host sends it a webhook; it watches the cluster continuously.

One conflict deserves a warning. If Git says replicas: 3 and an autoscaler (Chapter 25) sets 7, self-heal and the autoscaler will fight for ever. A field that another controller owns must not be in Git: leave replicas out of the manifest, or tell Argo CD to ignore differences in that field.

Argo CD notices a new commit when three minutes pass or when Sync is pressed, and notices a change in the cluster at once. Automated sync applies each new commit once. Self-heal needs automated sync to be on, as in Argo CD itself. A manual Sync applies the newest commit, and deletes removed objects only if prune is on. An image tag that does not exist leaves the old pods serving and the application Degraded, as a stalled rollout does in Chapter 12.

Things to try. Press Reset between experiments; it also switches the three settings off.

  • With everything off, merge a new image tag. Nothing happens. Argo CD has not looked yet, as the grey badge says. Wait three minutes: the application is OutOfSync, the difference is listed, and the cluster is untouched. Press "Sync now" and the tag is applied. This is Argo CD as a reporting tool with a button.
  • Switch on automated sync and merge again. After the wait, the commit is applied with nobody involved.
  • Automated sync without self-heal: scale to 1 by hand and wait. The cluster stays at one replica, OutOfSync, for as long as you like. Merge a new tag and wait: the sync of that commit puts replicas back to 3. The manual change was not being protected; it was merely not being looked at.
  • Add self-heal and scale by hand, or set an image by hand. Each change is undone at once. Read the explanation for the hotfix: in a real incident this is the moment someone discovers how GitOps works.
  • Remove debug-tools from Git, first without prune and then with it. Without: the Deployment keeps running and the application stays OutOfSync. With: it is deleted. Prune is the difference between a repository that describes the cluster and one that describes part of it.
  • Merge the tag that does not exist, with all three settings on. After the wait the badges read Synced and Degraded, and the old pods are still serving. Press "git revert" and wait: Healthy. The rollback was a commit.
  • Tested at random: 4,772 random actions and policy changes were run against rules stated separately from the panel's code. A merge alone never changed the cluster, nothing was ever deleted while prune was off, and with all three settings on no manual change survived.

Promotion between environments

With GitOps the layout of the repository is the layout of your environments, so it is worth getting right.

  • Keep configuration apart from application code. A separate repository (or at least a separate directory with its own owners) holds the manifests. Otherwise every code commit looks like a deployment change, and a pipeline that writes a new image tag triggers itself.
  • One directory per environment, not one branch. Each environment is an overlay over a shared base. Differences between environments are then visible side by side in one commit. With a branch per environment, "promote" means a merge, the branches drift, and nobody can easily say how staging differs from production.
  • Promotion is a change to one line. The image tag, or better the digest (Chapter 9), is copied from the staging overlay to the production overlay in a pull request. The image is never rebuilt.
deploy-config/
└── apps/web/
    ├── base/                         # shared by every environment
    └── overlays/
        ├── dev/kustomization.yaml       # newTag: 4.20.0-rc2   ← written by CI on every merge
        ├── staging/kustomization.yaml   # newTag: 4.19.0       ← promoted automatically after tests
        └── prod/kustomization.yaml      # newTag: 4.18.2       ← promoted by a reviewed pull request

Two things do not go in the repository. Secrets: commit references to a secret store, or ciphertext, as in Chapter 13. And decisions that need metrics: Git can say "run 4.19.0", but whether to continue a canary is a judgement about live traffic, which is why Argo Rollouts (Chapter 17) works alongside Argo CD and not inside it.

Use case: Weaveworks and the forty-five minutes

The word "GitOps" comes from Weaveworks, a company that ran a hosted service on Kubernetes and described its way of working in a 2017 article titled "Operations by Pull Request". The article opens with the incident that convinced them. Some time earlier, an engineer had pushed a change that accidentally destroyed the company's production environment, the cluster and the cloud resources around it. Because every part of the system, from the infrastructure definitions to each service's manifests, was described in Git and applied by automation, the team rebuilt the whole environment from the repository and was serving again in about forty-five minutes. Without that, recovery would have meant remembering what had been installed, by whom and with which settings. Weaveworks drew the general conclusion: if Git holds everything needed to recreate the system, then Git should also be the only way to change it, with an agent in the cluster doing the applying. The tool they built for that, Flux, is now a project of the Cloud Native Computing Foundation and outlived the company, which closed in 2024. Whichever tool you use, the test of a GitOps setup is still the one from that story: could you lose the cluster today and have it back from the repository?

⚠️
Common mistakes
  • Reading "Synced" as "working". Synced means the cluster matches Git. Health is a separate answer.
  • Automated sync without self-heal, and assuming manual changes are being reverted. They are not.
  • No prune. Objects removed from Git live on in the cluster for years.
  • A branch per environment. Environments drift, and promotion becomes merge conflict resolution.
  • Application code and deployment config in one repository with a pipeline that commits to it: build loops and noisy history.
  • Fields owned by another controller in Git, such as replicas under an autoscaler: the two fight.
  • kubectl hotfixes during an incident that self-heal silently undoes, or that nobody writes back to Git, so the next sync removes the fix.
  • Secrets committed "temporarily". Git history is permanent.
  • Giving the GitOps controller cluster-admin everywhere, and letting any repository deploy anywhere. Use projects to limit sources and destinations.

Interview drill

Explain it simply: What is GitOps, and how does it differ from deploying with a CI pipeline?

How a strong answer sounds
GitOps means a Git repository holds the full desired state of the system, declaratively, and an agent running in the cluster continuously pulls that state and makes the cluster match it. To deploy, I merge a pull request; to roll back, I revert it. A traditional pipeline pushes: a CI job connects to the cluster and applies changes once. The differences are where the credentials live, since with GitOps nothing outside the cluster needs access to it; that reconciliation is continuous, so drift from manual changes is detected and can be corrected; and that Git history is a complete, reviewable audit trail of what ran when. The cost is a controller to operate and the discipline that every change, including urgent ones, goes through Git.

Deeper: During an incident an engineer scales a Deployment up by hand, and a few seconds later it is back at the old replica count. What is happening, and how should this work?

How a strong answer sounds
The application is managed by a GitOps controller with self-heal on. It saw the live replica count differ from Git and reverted it, which is the system working as designed and exactly wrong for this moment. There are a few correct ways out. The fastest that keeps the model intact is to make the change in Git: a one-line pull request with an expedited review, which the controller applies within seconds if a webhook is configured. If that is too slow for the emergency, pause reconciliation for that one application, by disabling its automated sync, make the manual change, and then write the same change to Git before re-enabling it, because otherwise the next sync removes the fix. I would record who paused it and why, and alert on applications that stay paused. Then the design question: replica count under load should not be a hand-edited number in Git at all. If an autoscaler owns it, the manifest should omit replicas or the controller should be told to ignore that field, so that capacity can change without fighting the desired state. More generally the team needs a written break-glass procedure, so that nobody learns how self-heal behaves in the middle of an outage.

🧠 Key takeaways

  • Push: a pipeline applies changes from outside. Pull: a controller in the cluster applies what Git says, continuously.
  • GitOps: declarative, versioned, pulled automatically, continuously reconciled.
  • An Argo CD Application ties a path in a repository to a namespace in a cluster, with a sync policy.
  • Sync status is "does the cluster match Git?" Health is "is it working?" They are independent.
  • Automated sync follows Git; self-heal undoes changes in the cluster; prune deletes what Git no longer has.
  • Use a directory per environment and promote by changing one tag in a pull request.
  • Every change goes through Git, including urgent ones. Keep secrets and controller-owned fields out.

Check your understanding

In a pull-based GitOps setup, what credential does the CI pipeline need in order to deploy to production?

The pipeline's last step is a commit. The controller inside the cluster does the applying, so no cluster credential leaves the cluster.

An application shows Synced and Degraded. What does that mean?

Sync status compares Git with the cluster. Health looks at whether the objects work. A commit naming a missing image syncs perfectly and never becomes healthy.

Automated sync is on and self-heal is off. An engineer edits a Deployment's image directly in the cluster. What happens?

Automated sync reacts to new commits. Reverting changes made in the cluster is what self-heal adds.

A Deployment's manifest is deleted from the repository. Prune is off. What happens to the Deployment in the cluster?

Without prune, Argo CD never deletes. The leftover object makes the application OutOfSync until someone prunes it or turns the setting on.

Why is "one directory per environment" preferred to "one branch per environment"?

Long-lived environment branches diverge. With overlays in one branch, what differs between staging and production is exactly what the overlays say.
