Helm & Kustomize

A real service is a Deployment, a Service, a ConfigMap, an Ingress and a few more objects, and it runs in at least three environments that differ in a handful of values: the image tag, the number of replicas, a memory limit, a hostname. Copying the YAML per environment works for a week. Then someone fixes a probe in production and forgets staging, and the copies drift apart. The two standard tools for keeping one source of truth take opposite approaches. Helm turns manifests into templates with parameters. Kustomize keeps manifests as plain YAML and applies patches on top. This chapter shows both doing the same job, with a simulator that renders one service for three environments each way.

Why templating

Three things push teams beyond a folder of plain manifests.

  • Environments. Development, staging and production should be the same definition with a short, visible list of differences. If they are three copies, the differences are whatever accumulated.
  • Repetition. Thirty services each need a Deployment with the same probes, labels and security settings. A fix to the pattern should be made once.
  • Distribution. The authors of an ingress controller or a database operator need to ship hundreds of lines of manifests that every user can adapt without editing them.

Whatever tool you use, keep one property: the rendered output can be looked at before it is applied. Both tools here can print the final manifests without touching a cluster, and a pipeline should show that output, or its difference from what is running, in every pull request.

Helm: charts and values

Helm calls itself a package manager for Kubernetes. A package is a chart: a directory of manifest templates and a file of default values. Installing a chart into a cluster creates a release, which Helm tracks by name and revision.

web/
├── Chart.yaml             # name, chart version, app version, dependencies
├── values.yaml            # the defaults, and the chart's documentation
├── values.schema.json     # optional: types and required keys for values
└── templates/
    ├── deployment.yaml    # manifests with {{ placeholders }}
    ├── service.yaml
    └── _helpers.tpl       # shared snippets, such as the standard labels
# templates/deployment.yaml (part)
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ required "image.tag is required" .Values.image.tag }}"
          {{- if .Values.resources }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
          {{- end }}

The placeholders are Go template expressions. .Values is the merged set of values, .Release describes this installation, and pipes apply functions: quote, default, toYaml, nindent. The checksum/config line is the trick from Chapter 13: it puts a hash of the ConfigMap into the pod template, so that a configuration change rolls the pods.

Values come from several places, and later ones override earlier ones:

  values.yaml in the chart        the defaults
        ▼ overridden by
  -f values-prod.yaml             one file per environment (several -f allowed, in order)
        ▼ overridden by
  --set image.tag=4.19.0          single values on the command line: what a pipeline sets
$ helm template prod ./web -f values-prod.yaml             # render to stdout: nothing is applied
$ helm upgrade --install prod ./web -n shop -f values-prod.yaml --set image.tag=4.19.0 --atomic --wait
Release "prod" has been upgraded. Happy Helming!
$ helm history prod -n shop
REVISION  UPDATED                   STATUS      CHART      APP VERSION  DESCRIPTION
6         Tue Oct  6 14:02:11 2026  superseded  web-1.4.0  4.18.2       Upgrade complete
7         Wed Oct  7 10:42:07 2026  deployed    web-1.4.0  4.19.0       Upgrade complete
$ helm rollback prod 6 -n shop                              # re-apply everything revision 6 rendered

--atomic --wait makes the upgrade wait for the rollout and roll back by itself if the new pods never become ready. Third-party software is installed the same way from a chart repository or an OCI registry, with your settings in a values file that you keep in Git.

Kustomize: bases and overlays

Kustomize has no templates. You write complete, valid manifests once, as a base, and for each environment an overlay that says how it differs. It is built into kubectl.

web/
├── base/
│   ├── deployment.yaml          # ordinary manifests: you could apply them as they are
│   ├── service.yaml
│   └── kustomization.yaml       # resources: [deployment.yaml, service.yaml]
└── overlays/
    ├── staging/kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── patch.yaml
# overlays/prod/kustomization.yaml
resources: [../../base]
namespace: shop
namePrefix: prod-
labels:
  - pairs: { env: prod }
    includeTemplates: true
images:
  - { name: ghcr.io/acme/web, newTag: 4.19.0 }       # what a pipeline rewrites
configMapGenerator:
  - name: web-config                                # generated with a content hash in its name (Chapter 13)
    literals: [LOG_LEVEL=warn]
patches:
  - path: patch.yaml

# overlays/prod/patch.yaml: only the fields that differ
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 6
$ kubectl kustomize overlays/prod          # render to stdout
$ kubectl diff -k overlays/prod            # what would change in the cluster
$ kubectl apply -k overlays/prod

A patch is merged into the object it names: fields in the patch replace fields in the base, and everything else is left alone. The transformers (namePrefix, labels, images, namespace) make the common changes without a patch, and they understand Kubernetes: rename a ConfigMap and every reference to it is renamed too. What Kustomize deliberately lacks is logic. There are no loops, no conditions and no variables, and there is no release history: rollback is "apply the previous commit".

Both renderers are real in miniature. The Helm side merges values.yaml, the environment's file and --set, then substitutes them into the template text. The Kustomize side starts from the base object and applies the overlay's name prefix, label, image tag and patch. With no typo, the two outputs are compared character by character. The apply step uses the API server's strict field validation, the default in current Kubernetes.

Things to try.

  • Production, each tool. With Helm you maintain 5 lines for production and 35 shared lines (the template and the defaults). With Kustomize it is 22 lines for production and 26 shared. Six of the 27 rendered lines differ from development, and the two outputs are identical, character for character. Helm's file is shorter because the chart's author already decided what may vary. Kustomize's overlay is longer because it shows where in the object each change lands.
  • Development and staging. Helm's development file is empty: defaults are the development settings. Staging changes two values. Seen side by side, an environment is its list of differences, which is the property the copied-manifest approach loses.
  • Let the pipeline set the image tag. One --set flag for Helm, two lines under images for Kustomize. Either way the tag changes in exactly one place, and exactly one rendered line changes.
  • Misspell the replica count, with Helm. The upgrade succeeds, and production runs 2 replicas instead of 6. Look at the right-hand pane: nothing in it is wrong as YAML, and nothing is marked. The only way to see the problem is to compare with what you expected.
  • The same typo with Kustomize. The misspelt field appears in the output, in red, and the API server rejects the whole object. Production is unchanged. The mistake was the same; plain manifests failed loudly where a template failed silently.
  • Agreement, checked: across the twelve combinations of environment and image tag, the two renderers were compared and produced the same manifest every time.

Choosing

HelmKustomize
ModelTemplates with parametersPlain manifests with patches
What the source looks likeYAML mixed with template syntax; not valid YAML until renderedValid YAML everywhere; editors and linters work on it directly
LogicConditions, loops, functionsNone, on purpose
Differences between environmentsOnly what the chart's author made a parameterAnything can be patched, whether or not the base's author expected it
Packaging and versionsYes: versioned charts in repositories and OCI registries, with dependenciesNo: a directory in Git
Release trackingHistory and rollback per release; removes objects that left the chartNone; pruning removed objects is the applying tool's job
A misspelt valueSilently ignored unless the chart has a schema or uses requiredPassed through, and rejected by the API server
Typical troubleIndentation and whitespace in templates; charts with hundreds of parametersLong chains of patches that are hard to follow; repetition where a loop would help
Best atSoftware you install from others, or publish to othersYour own services across your own environments

Many teams use both, and that is reasonable: third-party components come as Helm charts with a values file per cluster, and in-house services are plain manifests with overlays. The two also combine, since Kustomize can take a chart's rendered output as its base and patch what the chart forgot to make configurable. What matters more than the choice is the discipline around it: render in CI, review the output, and let one automated path apply it.

Use case: Tiller, and why Helm 3 removed it

Helm 2, the version most of the industry adopted, had a second half that ran inside the cluster: a server called Tiller. The helm command on your machine sent it charts, and Tiller rendered them and created the objects. To be able to install anything, Tiller was normally given full administrative rights over the cluster, and in its default set-up it accepted requests from any pod that could reach its port, without authentication. The consequence was spelled out in security write-ups from 2018 onwards: a single compromised container anywhere in the cluster could ask Tiller, politely, to install whatever it liked with cluster-admin rights. Kubernetes' own access control, which decides who may do what, was bypassed, because every user's actions were carried out under Tiller's identity. Securing it was possible and fiddly, and most installations did not. Helm 3, released in November 2019, removed Tiller altogether. The client now renders the chart and talks to the API server directly, with the credentials and permissions of whoever runs it, and release history is stored as ordinary Secrets in the release's namespace. The lesson reaches beyond Helm. A deployment tool holds the power to change everything, so how it authenticates, whose identity it acts with and what it is allowed to touch are part of your security design. Common mistakes
  • One copy of the manifests per environment. The copies drift, and nobody can say what the intended differences were.
  • Applying without rendering. If the pull request shows only a changed value, nobody has seen what it does to the output.
  • No schema on a chart's values. A misspelt key is ignored, and the default quietly ships.
  • Indentation bugs in templates. A template works on text, so toYaml without the right nindent produces YAML that parses into something else.
  • A parameter for everything. A chart with three hundred values is harder to understand than the manifests it replaced.
  • helm upgrade from a laptop, with local values nobody else has. Releases belong to the pipeline.
  • Secrets in values files committed to Git. Use references to a secret store (Chapter 13).
  • kubectl edit on an object a tool owns. The next upgrade overwrites it, or merges it in a way you did not expect.
  • Unpinned chart versions. "Latest" of someone else's chart is an unreviewed change to your cluster.

Interview drill

Explain it simply: What is the difference between Helm and Kustomize?

How a strong answer sounds
Both produce Kubernetes manifests for several environments from one source. Helm does it with templates: a chart contains manifests with placeholders and a values file of defaults, and you override values per environment. It is also a package manager, with versioned charts, dependencies, and releases that it tracks and can roll back. Kustomize has no templates: you keep a base of plain, valid manifests and overlays that patch them, with built-in transformers for names, labels and image tags, and it is part of kubectl. Helm is strongest for distributing software with many options; Kustomize for your own services, where the YAML stays readable and anything can be patched. In both cases what reaches the cluster is plain manifests, so I render and review that output in CI.

Deeper: After a routine helm upgrade, production is running one replica of a service that should have six. Nobody changed the replica count. How could that happen, and how do you prevent it?

How a strong answer sounds
I would start with facts: helm get values and helm get manifest for the current and previous revisions, and a diff of the two renders. The usual causes are these. A key was misspelt or moved: the values file says replicaCout, or the chart was restructured so that the value now lives under another path, and Helm ignores keys the template does not use, so the chart's default applied. Or the template rendered nothing for replicas, because the value was missing altogether, and an absent field means the API's default of one. Or the upgrade was run without the production values file, or with --reuse-values and --reset-values confused, so earlier overrides were dropped. Or the value is right and something else owns the field: an autoscaler is managing replicas and the chart keeps resetting it, in which case the chart should not set replicas at all when autoscaling is on. To prevent it: add a values.schema.json that rejects unknown keys and wrong types, and required for values with no sensible default; render in CI and post the diff against the live release on every pull request, so that "replicas: 6 → 1" is seen by a reviewer; run upgrades only from the pipeline with the values files in Git; and add a policy check on the output, such as a minimum replica count for production workloads.

🧠 Key takeaways

  • Environments should be one definition plus a short, visible list of differences, not copies.
  • Helm: templates and values. Defaults, then -f files in order, then --set. Releases have history and rollback.
  • Kustomize: a base of plain manifests and overlays of patches and transformers, built into kubectl.
  • Helm ignores a misspelt value silently unless a schema forbids it; Kustomize passes it through to an API server that rejects it.
  • Both render to plain manifests: review that output, or its diff, before anything is applied.
  • Helm suits packaged software; Kustomize suits your own services. Using both is normal.
  • A deployment tool's identity and permissions are part of your security design.

Check your understanding

A chart's values.yaml sets replicaCount: 2. The release is upgraded with -f values-prod.yaml, which sets replicaCount: 6, and --set replicaCount=4. How many replicas are rendered?

Later sources override earlier ones: chart defaults, then files given with -f, then --set on the command line.

A production values file contains replicaCout: 6 (misspelt). The chart has no values schema. What does helm upgrade do?

Values are just data handed to the templates. A key no template reads has no effect and raises no error, unless a schema says otherwise.

Which statement about a Kustomize base is true?

Kustomize never puts placeholders in manifests. Overlays change a complete, valid base by patching it.

What does helm rollback prod 6 do?

Helm stores each revision's rendered output in the cluster. A rollback applies an earlier one again and records that as the newest revision.

A team must install a third-party monitoring stack with dozens of settings, and also deploy its own small service to three environments. Which combination is the most natural?

Packaged software arrives as a chart whose options the vendor maintains. A service you own is easiest to read and review as plain YAML with small overlays.
