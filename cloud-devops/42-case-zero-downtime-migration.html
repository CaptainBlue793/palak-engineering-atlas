Case Study: A Zero-Downtime Database Migration

Replacing a stateless service is easy: start the new one, move the traffic, stop the old one. Replacing the database underneath a live service is the hardest routine job in operations, because the data cannot be in two places by magic and the service cannot stop while it is moved. This case study follows an online shop that moves its orders, 400 gigabytes of them, from an old self-managed MySQL server to a new managed PostgreSQL cluster while customers keep ordering. The method is slow, methodical and built from steps that can each be undone: write to both, copy the history, prove they match, move the reads, move the writes, and only then let go of the old system. The simulator lets you perform the migration yourself, in any order, and shows what each wrong order costs.

  • Compare three ways to move a database, and say when each fits
  • Break a migration into phases that can each be reversed
  • Implement dual writes that tolerate failure and concurrent updates
  • Backfill history without overwriting newer data
  • Verify with counts, checksums and shadow reads before trusting the new system
  • Plan the cutover, the rollback at each phase, and the point of no return

The plan

The shop's orders data lives on a MySQL server that the company runs itself, on hardware that is out of support. It holds 400 GB, takes about 2,000 writes a second at peak, and is read by the checkout, the warehouse system and customer support. The goal is a managed PostgreSQL cluster in the cloud, with a tidied schema. The constraint is that the shop takes orders around the clock, and an hour of downtime costs more than the migration project.

There are three ways to move a database.

The shop is changing engine and schema together, so it chooses dual writes. That is the most work and gives the most control. The plan is a sequence of phases, each one a small change behind a flag, and each with a way back.

Two decisions shape everything else. One source of truth at a time. At every moment exactly one database is authoritative, and the other is a follower being brought into line. And rehearse. The whole sequence is run first against a copy of production in a staging environment, with timings recorded, because the first attempt at any phase always finds something.

Dual writes

In the dual-write phase the application writes each change to the old database, and if that succeeds, to the new one. The old database remains the truth, and reads still come from it. Three problems have to be designed for.

The second write can fail. The two databases cannot share a transaction, so sometimes the old one will accept a write and the new one will not: a timeout, a restart, a constraint the new schema enforces. The customer's order succeeded, so the request must not fail. The failure is recorded and repaired later, and counted on a dashboard, because a rate that is not zero is a bug to find.

Writes can arrive out of order. Two updates to the same order, a few milliseconds apart, can reach the two databases in opposite orders, leaving each with a different final value. The defence is to make every write to the new database conditional on a version: apply it only if it is newer than what is there. Then order does not matter, and a write that is repeated does no harm.

-- The write to the new database: an upsert that never goes backwards
INSERT INTO orders (id, customer_id, status, total_pence, version, updated_at)
VALUES ($1, $2, $3, $4, $5, $6)
ON CONFLICT (id) DO UPDATE
   SET customer_id = EXCLUDED.customer_id, status = EXCLUDED.status, total_pence = EXCLUDED.total_pence,
       version = EXCLUDED.version, updated_at = EXCLUDED.updated_at
 WHERE orders.version < EXCLUDED.version;        -- an older or repeated write changes nothing

Some writes do not go through the application. A nightly job, an administrator's script and a second service may all write to the old database directly. Each must be found, by searching the code and by watching the database's own log of connections, and either changed to dual write or covered by the repair job.

Backfill and verification

Dual writes handle every row that changes from now on. The backfill copies the rest: the years of orders nobody is touching. It must start after dual writes are on, or rows changed in between are missed, and it must use the same version-guarded upsert, or it will overwrite a fresh dual-written row with the stale copy it read an hour earlier.

# backfill.sh: resumable, throttled, reading from a replica so that production is not slowed
last=$(cat checkpoint 2>/dev/null || echo 0)
while true; do
  next=$(copy_batch --from mysql-replica --to postgres --after-id "$last" --limit 5000 --guarded)   # the upsert above
  [ -z "$next" ] && break
  echo "$next" > checkpoint; last=$next
  sleep 0.2                                   # and slow down further if replication lag or database load rises
done

At 5,000 rows per batch, the shop's 1.5 billion rows take about four days. That is fine. A backfill should be boring: restartable from its checkpoint, gentle on both databases, and watched.

Then comes the phase that is most often cut short, verification. The team does not believe the two databases match until three different checks say so.

  • Counts and checksums by range of keys: cheap, and they point at where a difference is.
  • Row-by-row comparison of a continuous random sample, and of every row the repair queue has touched.
  • Shadow reads. In production, each real read is still answered from the old database, and the same read is also sent to the new one in the background. The two answers are compared and any difference is logged. This tests the new schema and queries with real traffic, with no user depending on the result.
-- A checksum for one range of keys. Run the equivalent on both sides and compare the two lines.
SELECT count(*), sum(version), md5(string_agg(id || ':' || status || ':' || total_pence, ',' ORDER BY id))
  FROM orders WHERE id > 41000000 AND id <= 42000000;

A difference is never just patched. Each one is traced to its cause: a writer that was missed, a time zone conversion, a column that rounds differently, text that is truncated. Fixing the cause and re-running the comparison is the work of this phase, and the exit condition is strict: zero differences from shadow reads for a week.

Cutover and rollback plan

With the databases proven equal, the move itself is two flag changes made days apart.

Reads first. A flag sends 1% of reads to the new database, then 10%, then all, with latency and error rates watched at each step as in any canary. The old database is still the truth and still receives every write, so going back is a flag flip with nothing lost.

Then writes. The order of the two writes is reversed: the new database is written first and is now the truth; the old one is written second and kept in step. This is the moment of real commitment, and the reason the old database keeps being written is that the migration may yet have to be undone. A problem that only shows under the full write load, or at month-end, can still be answered by switching back to a database that is current.

If something goes wrong duringRoll back byData at risk
Dual writes or backfillTurning the dual-write flag offNone. The new database is simply discarded or refilled
Reads moving to newSending reads back to oldNone. Old was the truth throughout
Writes on new, old kept in stepReversing the write order and the readsOnly writes that failed to reach old, which the repair queue holds

The shop keeps the old database in step for two weeks, through a month-end close, before the last phase. Then it stops the writes, takes a final backup of the old server and keeps it for a year, removes the dual-write code and the flags, and switches the server off. The cutovers are done mid-week, mid-morning, with the team present and other changes frozen. From first dual write to switch-off the project takes about seven weeks, and no customer notices any of it.

Things to try. Press Reset between attempts; the traffic is the same each time, so the numbers below are what you will see.

  • The correct order: dual writes on, traffic, backfill, traffic, verify, move reads, traffic, cut writes over, traffic, verify, switch off old. Both verifications report 12 of 12 matching, all 24 reads are correct, and the panel says nobody noticed.
  • Backfill first: backfill, traffic, dual writes on, traffic, verify. 3 of 12 rows differ. They changed after the backfill and before dual writes began, and nothing ever copied them.
  • An unguarded backfill: untick the first option, then dual writes on, traffic, backfill, verify. 5 rows differ. The backfill replaced fresh dual-written rows with the older copies in its snapshot.
  • Reads too early: dual writes on, move reads, traffic. Two of the six reads return missing data. The new database only has the rows that happened to be written since.
  • No way back: untick "keep writing to old", then dual writes on, traffic, backfill, move reads, cut over, traffic, roll back, traffic. The roll back succeeds mechanically and serves two wrong reads, because old missed everything written while it was not being kept in step.
  • Failing dual writes: tick the third option, then dual writes on, traffic, backfill, traffic, traffic, verify. Two rows differ. Run the repair job and verify again: none. Failures are normal; unrecorded failures are the problem.
  • Switching off early: dual writes on, cut over, move reads, switch off old. All 12 orders are lost.
  • In a test of 3,954 random button presses the migration reached "switched off" 46 times, and in all 46 users had been served wrong data on the way; 25 lost rows outright. In a second test that pressed buttons at random but obeyed three rules (never turn dual writes off, move reads only after a clean verify, cut over only after reads), it finished 38 times with no wrong read and no lost row.

Use case: Stripe's four steps for migrating subscriptions

In 2017 Stripe published an account of moving its subscriptions data to a new model, and it has become the standard description of this pattern. Subscriptions had originally been stored inside each customer's record, which had become limiting as the product grew. Stripe wanted them in their own table. There were hundreds of millions of them, the service takes payments continuously, and there could be no maintenance window. The engineers described the work as four steps. First, dual writing: every change was written to both the old place and the new table, and the existing data was copied across. Second, all read paths were changed to use the new table. Third, the write paths were changed to write to the new table as the primary store. Fourth, the old data was removed. Two details of how they did it are worth as much as the outline. To verify, they used a technique of running the old and new read paths side by side in production and comparing the results on real requests, with the old result still the one returned to the user, so that every difference surfaced before anything depended on the new code. And for the copy of existing data they did not run queries against the production database at all. They used an offline snapshot of the data in their batch-processing system to work out what needed copying, which kept the load of a very large scan away from the systems taking payments. The whole migration was, by design, a long series of small, boring, reversible deployments, with no cutover night.

⚠️
Common mistakes
  • Backfilling before dual writes are on. Rows that change in between are silently missed.
  • A backfill that overwrites. It replaces fresh rows with the stale copies it read earlier.
  • Failing the user's request when the second write fails. The new database is not yet allowed to cause outages.
  • Ignoring dual-write failures instead of recording, repairing and counting them.
  • Writers that bypass the application: batch jobs, admin scripts, another service.
  • Verifying once with a row count. Counts can match while contents differ.
  • Moving reads before verification is clean, so users become the test.
  • Moving reads and writes in the same step. Two changes, one of which cannot be told from the other when something breaks.
  • Stopping writes to the old database on cutover day. The way back is gone before the new system has seen a full business cycle.
  • Never rehearsing on production-sized data, so the timings are guesses.
  • Leaving the dual-write code and flags in place afterwards. The migration is finished when they are deleted.

Interview drill

Explain it simply: How do you migrate a live database to a new one without downtime?

How a strong answer sounds
In reversible phases, with one source of truth at a time. First I make the application write every change to both databases, with the old one still authoritative and the write to the new one made idempotent and conditional on a version, so that failures and reordering cannot corrupt it. Then I backfill the existing rows in throttled batches using the same guarded upsert, so the backfill never overwrites newer data. Then I verify: checksums by key range, sampled row comparisons, and shadow reads in production that compare the two databases on real queries. Only when that is clean for a sustained period do I move reads to the new database, gradually, behind a flag. Then I move writes, making the new database the truth while still writing to the old one, so I can go back. After a full business cycle with no problems I stop writing to the old database, take a final backup and remove the migration code. If the schema is not changing, I would consider replication with change data capture instead, which gives the same result with less application work.

Deeper: During the dual-write phase, verification keeps finding a small number of rows that differ. What could cause that, and how do you find out?

How a strong answer sounds
A small persistent difference is the most informative thing that happens in a migration, so I would study the rows before repairing them. I would collect the differing rows and look for what they share: the column that differs, when they were last written, which code path or client wrote them. The usual causes fall into a few groups. A writer that bypasses the dual-write path: a batch job, a script, another service, or a database trigger. The old database's connection logs, or a column recording the writer, will show it. A race: two concurrent updates applied in different orders on the two sides, which shows up as rows written twice within milliseconds and means the write to the new database is not properly guarded by a version. Failed second writes that were swallowed and never queued for repair: I would check that the failure count matches the repair queue's intake. Transformation differences between the schemas: time zones, numeric precision and rounding, text encoding or truncation, nulls against empty strings, default values. Those show as the same column differing in the same way on every affected row. And the backfill itself: if it is not guarded, it rewrites recent rows with stale data, which shows as differences clustered just behind the backfill's position. For each hypothesis there is a cheap test, and I would fix the cause, repair the affected rows from the source of truth, and reset the clock on the verification period. I would not move reads while the number is above zero, even if it is small, because a rate of one in a million on a billion rows is a thousand customers with wrong orders.

🧠 Key takeaways

  • Migrate in reversible phases: dual write, backfill, verify, move reads, move writes, let go.
  • Exactly one database is the truth at any moment. The other is being brought into line.
  • Writes to the follower are idempotent and conditional on a version, so failure and reordering are harmless.
  • Backfill after dual writes begin, in guarded, throttled, resumable batches.
  • Verify with checksums, samples and shadow reads, and trace every difference to its cause.
  • Keep writing to the old database after cutover. Stopping is the point of no return.
  • The migration ends when the old system is off and the migration code is deleted.

Check your understanding

Why must the backfill start after dual writes are switched on, and not before?

Dual writes cover every change from the moment they start. A backfill that ran earlier has no way to learn about changes made in the gap.

During dual writes, the write to the old database succeeds and the write to the new one times out. What should the application do?

The old database is still the truth, so the user's operation succeeded. The gap is recorded, repaired from the truth and counted.

What does a shadow read do?

It tests the new database with real queries while no user depends on its answer. Differences are logged and investigated.

After writes have been cut over to the new database, why keep writing to the old one for a while?

While the old database is kept current, switching back is a flag change. Once it stops being written, going back means losing or hand-replaying everything since.

Why is every write to the new database made conditional on a version number?

Dual writes, the backfill and the repair job can all deliver the same row at different times. A version guard means the newest always wins.
