Disaster Recovery: RPO & RTO

High availability handles the failures you expect: a server dies, a zone goes dark, and the system carries on without anyone being woken. Disaster recovery is for the failures that take everything in one place: a whole region, the data itself, or the account it all lives in. For those you need a second place to run, a copy of the data that the disaster could not reach, and a plan somebody has actually practised. This chapter covers the two numbers that define a recovery target, the four standard strategies and what each costs, what a managed database's features do and do not protect against, and how to run a drill. The simulator pits each strategy against three different disasters.

RPO and RTO

Two numbers turn "we need disaster recovery" into something you can design and price.

  • The recovery time objective (RTO) is how long the service may be down. It is measured from the moment of the disaster to the moment users are served again.
  • The recovery point objective (RPO) is how much recent data may be lost. It is measured backwards from the disaster to the last moment whose data you can get back.

Neither is a technical choice. Both follow from what an hour of downtime, or an hour of lost orders, costs the business, set against what the protection costs. A payments ledger and an internal wiki in the same company deserve very different answers, so set objectives per system, in tiers, and spend accordingly.

The plan also depends on which disaster. There are three kinds, and a design that handles one can be useless against another.

DisasterExampleWhat is goneWhat saves you
Loss of a placeA region-wide outage, a data-centre fire (Chapter 2)The running system in one regionA second region to run in, with the data already there
Loss of the dataA migration drops a table; a bug overwrites rows; someone runs a script against productionCorrect data, everywhere it was replicated toA backup you can restore to a moment before the mistake
Loss of the accountStolen administrator credentials; ransomware; the provider deletes the account by mistakeEverything in the account, in every region, backups includedA copy outside the account, which the account's administrators cannot delete

Backup and restore

Backups are the foundation under every other strategy, because they are the only defence against the second and third kinds of disaster. A managed database gives you several protective features, and it is worth knowing precisely what each one covers.

FeatureServer or zone failsRegion lostTable droppedAccount deleted
Standby in another zone (multi-AZ)Yes: automatic failover in a minute or twoNoNo: the drop is copied at onceNo
Read replica, another regionYes, by promoting itYesNo: copied within secondsNo
Automated backups with point-in-time recoveryYes, slowlyOnly if copied to another regionYes: restore to the second beforeNo: deleted with the account
Backups copied to another account, lockedYes, slowlyYesYesYes

The third column carries the lesson people learn the hard way: replication is not a backup. A replica's job is to copy every change as fast as it can, and it copies mistakes with the same diligence.

# Point-in-time restore always creates a NEW instance. The damaged one is left alone.
$ aws rds restore-db-instance-to-point-in-time \
    --source-db-instance-identifier shop-prod \
    --target-db-instance-identifier shop-prod-restore-1432 \
    --restore-time 2026-10-07T14:32:00Z

# Promote a cross-region replica to a standalone primary. One-way: the old primary is no longer its source.
$ aws rds promote-read-replica --db-instance-identifier shop-prod-replica --region eu-west-1
# Backups copied to a vault in another account, where nobody can delete them early
resource "aws_backup_plan" "database" {
  name = "database-daily"
  rule {
    rule_name                = "daily"
    target_vault_name        = aws_backup_vault.local.name
    schedule                 = "cron(0 2 * * ? *)"
    enable_continuous_backup = true                      # point-in-time recovery
    lifecycle { delete_after = 35 }
    copy_action {
      destination_vault_arn = "arn:aws:backup:eu-west-1:999988887777:backup-vault:org-backups"   # the backup account, another region
    }
  }
}

resource "aws_backup_vault_lock_configuration" "org" {   # applied in the backup account
  backup_vault_name  = "org-backups"
  min_retention_days = 35                                # not even that account's administrator can delete sooner
}

Back up everything needed to rebuild, not just the database: object storage (with versioning switched on), secrets, and the cluster's own objects if they are not all in Git. Infrastructure and application configuration should already be code (Chapters 19 and 18), which is what makes "create the infrastructure in another region" a pipeline run and not a month's work. Two operational settings are worth a line each: turn on deletion protection for production databases, and require a final snapshot on deletion.

Pilot light and warm standby

For the loss of a region, the strategies differ in one thing: how much is already running in the second region when the first one fails. More running means faster recovery and a larger bill.

StrategyIn the second region before the disasterRecovery timeData lostExtra cost
Backup and restoreBackups onlyHours: build everything, then restoreBack to the last backupLowest: storage
Pilot lightA live database replica. Application servers defined and switched offTens of minutes: promote, start servers, redirectSeconds of replication lagLow: one database, no compute
Warm standbyA complete copy of the system running at small scaleMinutes: promote, scale up, redirectSecondsMedium
Active–activeA full-size copy serving live trafficAbout a minute, automaticSeconds, or noneHighest: roughly double

The name pilot light comes from a gas boiler: a small flame kept burning so that the main burner can be lit at once. The data is the part you cannot recreate quickly, so it is kept live; the servers are the part you can, so they are kept off. Warm standby goes one step further and keeps everything running at a fraction of the size, which means the standby is a working system that can be tested with real requests at any time.

Replication between regions is asynchronous, because waiting for another continent on every write would be too slow. So the replica is always a little behind, and a failover loses whatever had not yet arrived. That is why the recovery point of these strategies is "seconds" and not "zero".

Active–active

In an active–active design every region serves users all the time. When one fails, health checks stop sending it traffic and the rest carry on; there is nothing to start and nobody to wake. It is the fastest recovery and has one further advantage that is easy to overlook: the failover path is exercised by real traffic every day, so it is known to work.

It is also the most expensive and the hardest to build. Each region must have room for the others' traffic, so two regions each run at half capacity or less. And the data has to be writable in more than one place, which raises every hard question about conflicts and consistency. Chapter 33 is about that. For this chapter, the important point is what active–active does not do. A dropped table is dropped in every region. A stolen administrator credential works in every region. A bad deployment that goes everywhere breaks everywhere. Active–active is a defence against losing a place and against nothing else, so it needs the same backups as the cheapest strategy.

DR drills

A recovery plan that has never been run is a guess about how long recovery takes. Two kinds of practice turn it into a measurement.

  • Restore tests, automated. Every week a job restores the latest backup into a scratch database, runs checks (row counts, the newest record's timestamp, a few queries) and records how long it took. This catches the backup that has been silently empty for three months, and the recorded time is your restore time.
  • Failover drills, scheduled. Once or twice a year, in a planned window, actually run production from the second region. Use the runbook as written and note every place where it was wrong.
# restore-test.sh, run weekly by the scheduler
start=$(date +%s)
aws rds restore-db-instance-to-point-in-time --source-db-instance-identifier shop-prod \
    --target-db-instance-identifier restore-test --use-latest-restorable-time
aws rds wait db-instance-available --db-instance-identifier restore-test
psql "$RESTORE_TEST_URL" -Atc "select now() - max(created_at) from orders"     # how stale is the newest row? that is the measured RPO
echo "restore_seconds $(( $(date +%s) - start ))" | curl --data-binary @- "$PUSHGATEWAY/metrics/job/restore_test"
aws rds delete-db-instance --db-instance-identifier restore-test --skip-final-snapshot

Publishing the result as a metric means you can alert when a restore fails or slows down, like any other signal (Chapter 24). A drill should end with three numbers, the recovery time achieved, the data lost and the list of things that went wrong, and a comparison with the objectives. If the drill took four hours and the objective says one, either the design or the objective has to change. Chapter 34 takes the same idea further, into deliberate failure as a routine.

    Things to try.

    • The starting design is a warm standby that has never been rehearsed, and the region is lost. Recovery takes 30 minutes and the outage costs $10,000. Switch to "rehearsed": 10 minutes and $3,333. Practice is the cheapest improvement on the panel.
    • Backup and restore, never rehearsed, region lost: 24 hours down and up to 24 hours of data gone, a $480,000 outage against a standby that costs $30,000 a year. Rehearsed, it is 8 hours. Whether that is acceptable depends entirely on the system.
    • Active–active, and a migration drops a table. Recovery takes 12.5 hours with nightly snapshots and no practice, and a day of that table's data is lost. Now change the strategy: every one of the four gives the same answer, because all of them recover this from a backup.
    • Turn on continuous backups and rehearsal for that same disaster: 4.5 hours and about 5 minutes of data. The two cheap switches did what $600,000 a year of second region could not.
    • Active–active, continuous backups, rehearsed, and an attacker deletes the account's contents. Time to recover: never. Move the backups to another account, for about $6,000 a year, and it becomes 8 hours.
    • The cheapest design that survives all three disasters is backup and restore with continuous backups in a locked vault in another account, rehearsed: $48,000 a year, 8 hours for a lost region, 4.5 hours for a dropped table, 8 hours for an emptied account. Everything above that is paying for a faster answer to the first disaster only.

    Use case: UniSuper, and the backup that was somewhere else

    UniSuper is an Australian pension fund with more than 600,000 members and around A$125 billion under management. It ran its systems in a private cloud environment on Google Cloud, and it had done the textbook thing: the environment was duplicated across two regions, so the loss of one would not matter. In early May 2024 members found they could not log in to their accounts, and the outage went on for about two weeks. The cause, described in a joint statement by the heads of both companies and later in Google's own review, was not a failure of either region. When the environment had been set up a year before, one field in an internal provisioning tool had been left empty, and it defaulted to a fixed one-year term. At the end of that term the system did what it was built to do and deleted the whole subscription. Because the deletion was at the level of the account, it removed both regions at once. Replication between them was no protection: there was nothing left to replicate from or to. What saved the fund's data was a third copy. UniSuper also kept backups with a different provider, and its engineers and Google's rebuilt the environment and restored from those. Google called it a one-of-a-kind event and changed the tooling. The lesson for everybody else is the row at the bottom of this chapter's table: two regions protect you from losing a place. Only a copy outside the account protects you from losing the account, whoever's mistake it is.

    ⚠️
    Common mistakes
    • Treating a replica as a backup. It copies deletions and corruption within seconds.
    • Backups in the same account and region as the data. One credential, or one fire, removes both.
    • Never restoring. A backup is unproven until it has been restored and checked.
    • Objectives nobody measured. "RTO: one hour" in a document, against a restore that takes six.
    • A second region that was never given quota, secrets, DNS records or container images.
    • Waiting to declare. An hour of hoping the region returns is an hour added to the outage.
    • Assuming active–active covers everything. It covers the loss of a place, and still needs backups.
    • Two primaries after a failover, because the old one came back and nobody had fenced it off.
    • Forgetting everything that is not the database: object storage, secrets, queues, search indexes, the CI system you need to deploy.
    • The runbook kept only in the system that is down.
    • The same protection for every system. Tier them, and spend where downtime costs most.

    Interview drill

    Explain it simply: What are RPO and RTO, and how do the four DR strategies differ?

    How a strong answer sounds
    RTO is how long you can be down; RPO is how much recent data you can lose. Both come from what downtime and data loss cost the business. The four strategies trade money for those numbers. Backup and restore keeps only backups elsewhere: cheapest, hours to recover, and you lose everything since the last backup. Pilot light keeps a live database replica in the second region with the servers switched off: tens of minutes, seconds of data. Warm standby runs a small complete copy: minutes. Active–active runs full size in both and serves from both: about a minute, at roughly double the cost. All four still need backups, kept out of reach of the production account, because none of the replicated designs protects against deleted or corrupted data.

    Deeper: Your company has a multi-AZ database with a cross-region read replica and believes it is covered for disasters. What would you check?

    How a strong answer sounds
    That setup covers one of the three kinds of disaster, and only on paper so far. I would go through them. For losing the region: has anyone ever promoted that replica and run the application against it? I would check what else exists in the second region, because a database with no application servers, secrets, images, DNS plan or instance quota is not a recovery. I would ask how replication lag is monitored, since that lag is the data we lose, and who is authorised to declare a failover at three in the morning. For losing the data: multi-AZ and the replica both copy a dropped table within a second, so the question is about backups. Is point-in-time recovery enabled, what is the retention, and when was the last restore actually performed and timed? For losing the account: where do the backups live? If they are in the production account, an attacker with admin rights, or an administrative mistake, removes the database, the replica and the backups together, so I would want copies in a separate account under a lock that prevents early deletion. Then I would ask for the objectives. If nobody can state the RTO and RPO for this system, the design was not chosen, it accumulated. Finally I would propose two things with dates: an automated weekly restore test that publishes its duration, and a scheduled failover drill, because until those have run, the honest answer to "are we covered?" is that we do not know.

    🧠 Key takeaways

    • RTO is the time to recover; RPO is the data you may lose. Set them per system from the cost of downtime.
    • There are three disasters: a lost place, lost data and a lost account. Each needs a different defence.
    • Backup and restore, pilot light, warm standby, active–active: more running in the second region buys a shorter recovery.
    • Replication is not a backup. Mistakes replicate in seconds; point-in-time recovery goes back before them.
    • Keep backups in another account under a lock. It is the only cover against losing the account.
    • Active–active protects against losing a region and nothing else.
    • Test restores automatically and drill failovers on a schedule. The measured time is the real RTO.

    Check your understanding

    A database has a synchronous standby in another zone and an asynchronous replica in another region. A script deletes a million rows by mistake. Which copy still has them?

    Replicas copy every change, including wrong ones. Recovery needs a backup that can be restored to a point before the mistake.

    Which strategy keeps a live database replica in the second region but leaves the application servers switched off?

    Pilot light keeps the part that cannot be recreated quickly, the data, running. Warm standby also runs the application at small scale.

    A system takes one backup at 02:00 each night and has no other protection. What is its worst-case RPO?

    A failure just before the next backup loses nearly a full day of changes. Restore time is the RTO, a different number.

    Why should backups be copied to a separate account under a retention lock?

    An account boundary plus a lock puts the backups beyond the reach of whatever destroyed production.

    A team's documented RTO is one hour. Their first failover drill takes four. What does this tell them?

    A drill measures the truth. The gap is closed by fixing what was slow, rehearsing, changing the design, or agreeing a different objective with the business.
