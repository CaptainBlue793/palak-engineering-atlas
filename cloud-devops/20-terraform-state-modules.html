Terraform State, Modules & Teams

Chapter 19 worked with one person, one directory and one environment. Real Terraform is used by a team, across several environments, from a pipeline, and nearly every hard problem at that scale is about one file: the state. Who holds it, who may write it, what happens when two people write it at once, and how much of your infrastructure a single mistake in it can reach. This chapter covers what the state is for, remote backends and locking, modules for reuse, how to separate environments, and what a safe Terraform pipeline looks like. The simulator runs two engineers against one state under each kind of backend and counts the resources nobody is managing afterwards.

State and why it matters

Your configuration says aws_instance.web. The cloud knows only i-0a1b2c3d4e5f67890. The state is the file that connects the two: for every resource Terraform manages, it records the resource's address in the code, its real ID, the attributes it had at the last apply, and what it depends on.

$ terraform state list
aws_instance.web
aws_security_group.web
aws_subnet.app
aws_vpc.main
$ terraform state show aws_instance.web | head -4
# aws_instance.web:
resource "aws_instance" "web" {
    id            = "i-0a1b2c3d4e5f67890"
    instance_type = "t3.small"

Without the state, Terraform could not tell "this instance is mine and needs changing" from "an instance should be created". That makes the state the single point of truth about ownership, and it has four properties you must respect.

  • It is required. Lose it and Terraform believes nothing exists. The next plan proposes to create everything again, and the real resources become orphans: running, billed and managed by nobody.
  • It must be the only copy. Two diverging copies of the state mean two different opinions about what exists.
  • It contains secrets. Every attribute is stored, in plain text, including generated database passwords and private keys. Anyone who can read the state can read those.
  • It is not yours to edit. Change it only through Terraform's own commands and blocks.
# Renaming a resource in code without destroying it: tell Terraform it is the same object
moved {
  from = aws_instance.web
  to   = aws_instance.frontend
}

# Adopting something that was created by hand: bring it under management
import {
  to = aws_s3_bucket.uploads
  id = "acme-shop-uploads"
}

# Letting go of a resource without deleting it
removed {
  from = aws_instance.legacy
  lifecycle { destroy = false }
}

These blocks are reviewed in a pull request and planned like any other change, which is why they are preferable to the older terraform state mv and terraform state rm commands that edit the state directly.

Remote backends and locking

By default the state is a file called terraform.tfstate in the working directory. That is fine for an experiment and wrong for a team: it lives on one laptop, it tempts people to commit it to Git with its secrets, and nothing stops two people from applying at once. A backend moves the state to shared storage.

terraform {
  backend "s3" {
    bucket       = "acme-terraform-state"           # versioned, encrypted, not public, access tightly limited
    key          = "prod/network/terraform.tfstate"  # one key per configuration
    region       = "eu-west-2"
    encrypt      = true
    use_lockfile = true                             # take a lock in the bucket before reading or writing
  }
}

A good backend gives you four things. One shared copy that everyone and the pipeline read. Locking: before a plan or an apply, Terraform takes a lock on the state, and a second run fails at once instead of working from a copy that is about to be out of date. Versioning: every write keeps the previous version, so a corrupted or deleted state can be rolled back. And access control and encryption, because of the secrets inside. Object storage with a lock is the common choice on every cloud (S3, Azure Blob Storage, Google Cloud Storage), and hosted services such as HCP Terraform provide the same and run the applies for you.

    The model runs real steps in an order set by the scenario. An apply reads the state, creates its resource in the cloud, and writes back the state it read plus its own addition, with the serial number raised by one. With a file per laptop, each person reads and writes their own copy. With a shared bucket and no lock, the last write wins. With a lock, a second run is refused until the first has finished, and then starts from the new state. A versioned bucket keeps every earlier version of the state.

    Things to try. There are nine combinations, and each one is a situation teams get into.

    • A file on each laptop, both apply. Both applies succeed. The cloud has six resources and each state file knows five of them, a different five. The table marks two resources as disputed. Choose "one after the other": the result is the same, because taking turns does not help when each person has a private copy.
    • Shared bucket, no lock, at the same time. Read the timeline's last line. Both read serial 5; Alice writes serial 6; Bob writes his own serial 6 over it. One orphan: Alice's subnet exists, is billed, and is in no state. Both commands printed "Apply complete".
    • The same backend, one after the other. No problem at all, which is the dangerous part: an unlocked shared state works every day until two runs overlap.
    • Locked, at the same time. Bob gets "Error acquiring the state lock", waits, and runs again against serial 6. The final state is serial 7 with all six resources. The cost of correctness was one refused command.
    • The state file is deleted. On a laptop: the plan says "4 to add", and applying it builds a second VPC and a second instance next to the first. In an unversioned bucket: four orphans, each to be imported by hand. In a versioned bucket: the previous version is restored and the plan shows no changes.

    Modules

    A module is a directory of Terraform files used as a unit, with input variables as its parameters and outputs as its results. The directory you run Terraform in is the root module; anything it calls is a child module. Modules are how a team writes "a service with a load balancer, an autoscaling group and alarms" once and uses it twenty times.

    # modules/service/variables.tf
variable "name"          { type = string }
variable "subnet_ids"    { type = list(string) }
variable "instance_type" {
  type    = string
  default = "t3.small"
}

# modules/service/outputs.tf
output "load_balancer_dns" { value = aws_lb.this.dns_name }

# envs/prod/main.tf: the root module calls it
module "checkout" {
  source        = "git::https://github.com/acme/terraform-modules.git//service?ref=v2.4.0"   # pinned
  name          = "checkout"
  subnet_ids    = module.network.private_subnet_ids      # another module's output
  instance_type = "t3.medium"
}

module "network" {
  source  = "terraform-aws-modules/vpc/aws"               # from the public registry
  version = "~> 5.13"
  cidr    = "10.0.0.0/16"
}

    Three habits keep modules useful. Pin the version of every module you do not keep in the same repository, exactly as you pin images and actions: an unpinned source is someone else's change arriving in your plan. Keep the interface small: a module with sixty variables has reproduced the provider and hidden nothing. And do not wrap a single resource. A module earns its place when it encodes a decision your organisation made, such as "every bucket is encrypted, versioned and private".

    Environments

    Development, staging and production should be the same code with different inputs and, above all, separate states, so that a mistake in one cannot reach another. There are two ways to get that.

    WorkspacesA directory per environment
    HowOne configuration; terraform workspace select prod switches which state it usesenvs/dev, envs/staging, envs/prod: each a small root module that calls the shared modules, with its own backend key
    Which environment am I about to change?Whatever was selected last, which is invisible in the codeThe directory you are standing in

    Separate credentials and accountsHard: one backend and provider configurationEasy: each directory has its own

    The same reasoning applies inside one environment. Everything in a state can be destroyed by one bad apply to that state, so the size of a state is your blast radius. Split by how often things change and how much it would hurt to lose them: the network and DNS in one state, databases in another, each service in its own. A service's configuration then reads the network's IDs through that state's outputs or through data sources, and cannot touch the network itself. Plans also get faster, since each one refreshes tens of resources and not thousands.

    infrastructure/
├── modules/                 # shared, versioned building blocks
│   ├── network/
│   └── service/
└── envs/
    ├── staging/
    │   ├── network/         # its own state: staging/network/terraform.tfstate
    │   └── checkout/        # its own state: staging/checkout/terraform.tfstate
    └── prod/
        ├── network/
        ├── data/            # databases: changed rarely, guarded most
        └── checkout/

    Terraform in CI

    Once state is shared and locked, the last step is to stop running applies from laptops at all. The pipeline becomes the only thing with permission to change infrastructure, and a pull request becomes the only way to ask.

    The details that matter: the pipeline gets its cloud access by assuming a role with its identity token, with no stored keys (Chapter 6); the planning role can only read, and only the apply job on the main branch can assume the role that writes; runs for one state never overlap, which the state lock guarantees and a concurrency group makes orderly; and the plan output is treated as sensitive, because it can contain secrets.

    ⌨️
    Use case: Amazon S3, 28 February 2017, and a tool that did what it was told

    For about four hours on 28 February 2017, Amazon S3 in Northern Virginia was largely unavailable, and a good part of the internet that depends on it went with it. Amazon's summary of the event is short and candid. An engineer on the S3 team was debugging a slow billing system and ran an established command, from a runbook, to take a small number of servers out of service. One of the inputs was entered incorrectly, and the command removed a much larger set than intended. Those servers supported two of S3's core subsystems, the one that tracks where every object is and the one that allocates new storage, and both had to be restarted in full, which at S3's size took hours because they had not been completely restarted in years. Amazon did not blame the typing. It changed the tool: capacity is now removed more slowly, and the tool refuses any request that would take a subsystem below its minimum required capacity. Hold that against this chapter. The command was authorised, the person was qualified and the procedure was followed. What was missing was a limit on how much one command could reach. In Terraform that limit is the boundary of a state, the roles a pipeline may assume, and protections such as prevent_destroy. Design them on the assumption that one day someone will type the wrong value, because someone will.

    ⚠️
    Common mistakes
    • State on a laptop, or committed to Git. It is lost, or duplicated, or leaks every secret in it.
    • A shared backend without locking. Two applies overlap and one quietly erases the other's record.
    • A state bucket without versioning, or one that half the company can read.
    • Editing the state by hand, or reaching for force-unlock while a run is still going.
    • One state for everything. Every plan is slow, and every mistake can reach production's database.
    • Workspaces for production and development, and an apply to whichever one happened to be selected.
    • Unpinned module sources. A change upstream shows up in your next plan.
    • Modules as thin wrappers with a variable for every argument: more code, no decisions.
    • Applying from laptops "just this once". The pipeline's record is no longer complete, and the local credentials needed for it are a risk in themselves.
    • Renaming a resource without a moved block. Terraform sees one resource deleted and another created.

    Interview drill

    Explain it simply: What is the Terraform state, and why keep it in a remote backend with locking?

    How a strong answer sounds
    The state is Terraform's record of what it manages: it maps each resource in the code to the real object's ID and stores its last known attributes and dependencies. Terraform needs it to know whether to create, update or delete, so losing it or having two copies means resources that nobody manages or that get created twice. A remote backend keeps one shared copy in storage the whole team and the pipeline use. Locking makes sure only one plan or apply works on that copy at a time, so two runs cannot overwrite each other's results. Versioning on the bucket lets me recover an earlier state, and because the state contains secrets in plain text it is encrypted and access to it is restricted. It never goes into Git.

    Deeper: A company has three environments and about twenty services, all in one Terraform configuration with one state. Plans take fifteen minutes and people are afraid to apply. How would you restructure it?

    How a strong answer sounds
    The fear is rational: one state means any apply can reach everything, and every plan refreshes every resource. I would split along two lines. First by environment, with a directory per environment, each its own root module, backend key and, ideally, cloud account, so production's credentials and state are separate from development's. Second, inside each environment, by lifecycle and blast radius: a foundation layer for the network and DNS that changes rarely, a data layer for databases with the strictest protection, and one state per service. The shared parts become versioned modules, so the twenty services call the same "service" module pinned to a release, and a change to the pattern is rolled through environments by bumping the version in development first. Layers read each other's outputs through remote state or data sources and cannot modify each other. For the migration itself I would not destroy and recreate anything: I would move resources between states with moved and import or removed blocks, one slice at a time, checking that each new configuration plans to "No changes" before the next. Then the workflow: plan on every pull request with the output posted for review, apply only from the pipeline on merge, with approval for production, short-lived credentials, a nightly drift check, and prevent_destroy plus cloud-level deletion protection on the stateful resources. Plans drop to seconds for a service, and the worst a mistake in one service can do is break that service.

    🧠 Key takeaways

    • The state maps code to real IDs. It is required, must be unique, contains secrets and is not edited by hand.
    • A remote backend gives one shared copy, locking, versioning, encryption and access control.
    • Without a lock, overlapping applies leave orphans: real resources missing from the state.
    • Refactor with moved, import and removed blocks, which are planned and reviewed like any change.
    • Modules package decisions for reuse. Pin their versions and keep their interfaces small.
    • Separate environments by directory and state; split state further to limit the blast radius of one apply.
    • Plan on the pull request, review the plan, apply the saved plan from the pipeline with short-lived credentials.

    Check your understanding

    A team's state file is accidentally deleted, and there is no earlier version. The infrastructure is untouched. What does terraform plan show?

    The state is the only record of what Terraform owns. Without it the existing resources are orphans, and recovering means importing each one.

    Two engineers run terraform apply at the same moment against a shared state in a bucket with no locking. Each adds a different resource. What is the likely result?

    Each run read the same old state and wrote back that state plus its own resource. The last write replaces the first.

    You rename aws_instance.web to aws_instance.frontend in the code. Without anything else, what does the plan show, and what prevents it?

    The address is how the state identifies a resource. A new address looks like a new resource unless a moved block connects the two.

    Why split infrastructure into several states (network, data, each service) instead of one?

    The boundary of a state is the boundary of what one run can change or destroy. Smaller states mean a smaller blast radius and quicker plans.

    In a "plan on pull request, apply on merge" pipeline, what should the apply job run?

    Applying a saved plan guarantees that the reviewed effect is the effect that happens, even if the cloud changed in between: a stale plan is refused.
