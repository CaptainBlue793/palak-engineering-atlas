Bash Scripting

Deploy scripts, CI steps, container entrypoints, cron jobs and backup jobs are nearly all Bash. Bash is forgiving in the worst way: by default a script carries on after a command fails, treats a misspelt variable as an empty string, and reports success for a pipeline whose first half crashed. This chapter teaches the parts of Bash that operations work uses, and the three settings that turn those silent failures into loud ones.

  • Write loops over files and lines, and a retry loop with backoff

  • Structure a script with functions, local, trap and logging to stderr

A script is a file of commands

A Bash script is the commands you would type, saved in a file. The first line, the shebang, tells the kernel which interpreter runs it. #!/usr/bin/env bash finds bash on the PATH, which works on Linux, macOS and in containers where Bash is not at /bin/bash. Make the file executable with chmod +x and run it by path:

#!/usr/bin/env bash
set -euo pipefail                         # explained below; every script in this course starts with it

# deploy.sh: build the app and restart the service
APP_DIR="/srv/app"
cd "$APP_DIR"
git pull --ff-only
make build
sudo systemctl restart app
echo "deployed $(git rev-parse --short HEAD)"
$ chmod +x deploy.sh
$ ./deploy.sh
deployed 4f2a9c1

Variables and quoting

A variable is assigned with name=value, with no spaces around = (name = value runs a command called name). You read it with $name. The rule that prevents most Bash bugs is: put double quotes around every expansion, "$name". Without quotes, Bash splits the value on spaces and expands * and ? as file patterns, so a file called my report.txt becomes two arguments and a value of * becomes every file in the directory.

Environment variables are ordinary variables that have been exported, so child processes see them. That is how configuration reaches programs in every later chapter, from systemd units to Kubernetes pods: export DATABASE_URL=… in the shell, env: in YAML. By convention, environment and constant names are UPPER_CASE and a script's own working variables are lower_case.

Exit codes, && and ||

Every command finishes with an exit code between 0 and 255. Zero means success; anything else is a failure, and the number often says which kind (grep returns 1 for "no match" and 2 for an error; curl returns 7 for "could not connect"). The special variable $? holds the last command's code. Bash's control flow is built on it:

make test && make deploy                 # deploy only if the tests passed
grep -q "ERROR" app.log || echo "clean"  # the right side runs only if the left failed

if curl -fsS --max-time 5 http://localhost:8080/health >/dev/null; then
  echo "healthy"
else
  echo "health check failed with code $?" >&2     # >&2: errors go to stderr
  exit 1
fi

if runs a command and branches on its exit code; it does not need brackets. The brackets [[ … ]] are themselves a command that tests things: [[ -f "$path" ]] (file exists), [[ -z "$x" ]] (empty string), [[ "$env" == "prod" ]], [[ "$n" -gt 3 ]] (numbers use -eq, -lt, -gt). In curl, -f makes HTTP errors such as 500 return a non-zero exit code; without it, curl "succeeds" whenever it gets any response at all.

Loops

Two loop shapes cover most operations scripts: looping over files or arguments, and reading a file line by line.

# Compress yesterday's logs. The glob is expanded by Bash, so names with spaces are safe.
for f in /var/log/app/*.log.1; do
  [[ -e "$f" ]] || continue                 # no matches: the pattern stays literal
  gzip -9 "$f"
done

# Run a command on every host in a list.
while IFS= read -r host; do
  ssh -n "$host" uptime                   # -n: stop ssh reading the loop's stdin
done < hosts.txt

Both loops carry a detail you only learn from a bug. IFS= read -r reads a line exactly as written, without trimming spaces or treating backslashes as escapes. And ssh reads standard input by default, so without -n the first ssh swallows the rest of hosts.txt and the loop runs exactly once.

The third pattern is the retry loop. Networks fail briefly all the time, so scripts that call APIs or wait for a service retry with a growing delay (exponential backoff) rather than failing on the first error or hammering the server:

# retry ATTEMPTS COMMAND...: run COMMAND until it succeeds, doubling the wait each time.
retry() {
  local attempts="$1"; shift
  local delay=1
  for ((i = 1; i <= attempts; i++)); do
    if "$@"; then return 0; fi             # "$@" = all remaining arguments, each quoted
    echo "attempt $i/$attempts failed: $*" >&2
    sleep "$delay"; delay=$((delay * 2))
  done
  return 1
}

retry 5 curl -fsS http://localhost:8080/health   # waits 1, 2, 4, 8, 16 seconds at most

set -euo pipefail

These three options change Bash's defaults from "carry on" to "stop". Each one catches a different class of bug:

  • -e (errexit): exit as soon as a command fails. Without it, a failed make build is followed by the restart, as if nothing happened.
  • -u (nounset): treat an unset variable as an error. Without it, a misspelt $BUILD_DRI is silently empty, and rm -rf "$BUILD_DRI/"* becomes rm -rf /*.
  • -o pipefail: a pipeline fails if any command in it fails. Without it, a pipeline's exit code is only the last command's, so pg_dump shop | gzip > backup.gz succeeds even when pg_dump crashed, because gzip happily compressed nothing.

The rules have exceptions you must know, because they hide failures even with -e on. A command's failure does not stop the script when it is the condition of an if or while, or on the left of && or || (Bash assumes you are handling it). local out=$(cmd) hides cmd's failure, because the exit code checked is the one from local, which always succeeds; declare first, then assign: local out; out=$(cmd). And -e is not a substitute for checking: if a failure is expected, handle it explicitly with || true or an if, so the next reader knows it was deliberate.

Functions, trap and logging

Once a script passes about 30 lines, give it structure: small functions, a main, logs on stderr (so stdout stays clean for data that other tools may read), and a trap that cleans up however the script ends.

#!/usr/bin/env bash
set -euo pipefail

log() { printf '%s %s\n' "$(date -u +%FT%TZ)" "$*" >&2; }

main() {
  local env="${1:?usage: release.sh ENV}"
  local tmp; tmp="$(mktemp -d)"
  trap 'rm -rf "$tmp"' EXIT               # runs on success, failure or Ctrl+C

  log "building for $env in $tmp"
  tar -czf "$tmp/app.tgz" -C build .
  retry 3 scp "$tmp/app.tgz" "deploy@${env}-web-1:/srv/releases/"
  log "done"
}

main "$@"

trap … EXIT registers a command to run when the script exits for any reason, so temporary directories, lock files and half-uploaded artefacts are always removed. Finally, run ShellCheck (shellcheck release.sh) on every script: it is a linter that knows all of the quoting and exit-code traps in this chapter, and most teams run it in CI (Chapter 10).

Use case: the Steam script that deleted home directories

In January 2015 users of Valve's Steam client for Linux reported that it had deleted every file they owned. The launcher script contained rm -rf "$STEAMROOT/"*. If Steam's folder had been moved, the line that computed STEAMROOT produced an empty string, the command became rm -rf "/"*, and it removed everything the user had permission to delete, including mounted backup drives. The script even carried the comment # Scary! on that line. set -u would not have helped there, because the variable was set (to an empty value); "${STEAMROOT:?}" would have stopped it, and so would a check that the directory existed before deleting anything under it.

⚠️
Common mistakes
  • Unquoted variables. $f splits on spaces and expands globs. Write "$f", always.
  • Spaces around =. PORT = 80 runs a command named PORT.
  • rm -rf "$DIR/"* with no guard. Use "${DIR:?}" and check the directory exists first.
  • curl without -f. A 500 response is still exit code 0.
  • Thinking pipefail stops the script. It changes the pipeline's exit code; -e stops the script.
  • local x=$(cmd) hides cmd's failure. Declare and assign separately.
  • Logging to stdout in a script whose output is piped into another tool. Logs go to stderr (>&2).

Interview drill

Explain it simply: What does set -euo pipefail do, and why do people put it at the top of scripts?

How a strong answer sounds
It makes the script fail loudly instead of carrying on after errors. -e exits when a command fails, -u treats unset variables as errors instead of empty strings, and pipefail makes a pipeline fail if any stage fails rather than only the last. Together they stop a deploy script from restarting a service after a failed build, an rm from running on a misspelt path, and a backup from reporting success when the dump failed. I would add that -e has exceptions, such as commands inside if conditions or before ||, and local x=$(cmd), so it is a safety net, not error handling.

Deeper: A nightly backup job ran pg_dump db | gzip > /backups/db.gz && aws s3 cp … for months. When you needed a restore, every file was 20 bytes. What happened, and how do you prevent it?

How a strong answer sounds
Without pipefail, the pipeline's exit code was gzip's, which succeeded compressing empty input, so the upload ran and the job reported success, even though pg_dump had been failing (a changed password or an unreachable host). The fixes: set -euo pipefail so the job fails; alert on the job's exit code and on its absence; check the artefact (size above a threshold, gzip -t); and, most important, restore a backup regularly into a scratch database and run a query against it. A backup that has never been restored is a hope, not a backup (Chapter 32).

🧠 Key takeaways

  • Start every script with #!/usr/bin/env bash and set -euo pipefail.
  • Quote every expansion: "$var", "$@", "$(cmd)"; use ${VAR:?} for required values and ${VAR:-default} for optional ones.
  • Exit code 0 is success; &&, || and if branch on it, and CI reads only that number.
  • -e stops on failures, -u on unset variables, pipefail makes any failing stage fail the pipeline.
  • -e is skipped in conditions, before ||/&& and with local x=$(…): handle expected failures explicitly.
  • Use functions, local, trap … EXIT, logs on stderr, retries with backoff, and ShellCheck.

Check your understanding

A script has set -e but not pipefail. What happens on pg_dump shop | gzip > backup.gz when pg_dump fails?

Without pipefail, a pipeline returns the exit code of its last command. gzip compresses empty input successfully, so the line "succeeds" and set -e never fires.

Which line deletes the right thing when f="old logs.txt"?

Double quotes keep the value as one argument. Unquoted (with or without braces) it splits into "old" and "logs.txt"; single quotes pass the literal text $f.

With set -e on, which failing command does not stop the script?

A command on the left of || (or &&, or in an if/while condition) is being tested, so Bash assumes you handle its failure and carries on.

What does "${DB_URL:?DB_URL must be set}" do when DB_URL is empty?

:? is the "required" expansion: unset or empty makes a non-interactive shell print the message and exit. :- would supply a default instead.

A while read -r host loop over 40 hosts runs ssh "$host" uptime but only the first host is contacted. Why?

Inside the loop, stdin is hosts.txt. ssh consumes it, so the next read finds end of file. ssh -n (or </dev/null) stops that.
