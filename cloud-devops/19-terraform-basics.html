Infrastructure as Code: Terraform Basics

Everything from Chapters 2 to 6, the networks, the instances, the buckets and the roles, can be created by clicking through a console. It works once. It cannot be reviewed, repeated for a second environment or rebuilt after a mistake, and nobody remembers which box was ticked. Infrastructure as code means describing those resources in text files, keeping the files in Git and letting a tool make the cloud match them. Terraform is the most widely used such tool. This chapter covers how it thinks: providers and resources, the plan it shows you before it changes anything, variables and outputs, and the dependency graph that decides the order. The simulator is a small plan engine: edit a configuration and read exactly what would be created, changed, replaced or destroyed.

Declarative infrastructure

There are three ways to create a cloud resource, and they differ in what you keep afterwards.

ConsoleScript of commandsDeclarative code
You writeNothing: you clickThe steps: "create a VPC, then a subnet…"The result: "a VPC and a subnet exist"
Run it twiceYou get two of everything, or an errorThe same, unless you wrote checks for every stepThe second run changes nothing
Change one settingFind it and clickWrite a new script for the changeEdit the value; the tool works out the steps
See the effect firstNoNoYes: a plan
Review and historyAn audit log, at bestThe script, not what it didA pull request and a Git history
A second environmentDo it all again by handCopy the script and edit itThe same code with different variables

Terraform reads files written in HCL, compares what they describe with what exists, and calls the provider's API to close the gap. It is the same idea as Kubernetes' reconciliation with two differences: it runs when you run it, not all the time, and it shows you a plan and waits for a yes. OpenTofu is an open-source fork that reads the same language and works the same way, and everything in this chapter applies to both. The cloud providers have their own equivalents (CloudFormation, Bicep), and tools such as Pulumi do the same job from a general-purpose programming language.

Providers and resources

Terraform itself knows nothing about any cloud. A provider is a plugin that teaches it one API: there are providers for AWS, Azure and Google Cloud, and also for Kubernetes, GitHub, Cloudflare, Datadog and hundreds of other things with an API. A resource block declares one object that should exist.

terraform {
  required_version = "~> 1.9"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.70" }    # pin it: providers change behaviour between versions
  }
}

provider "aws" {
  region = "eu-west-2"                 # credentials come from the environment or a role, never from this file
}

resource "aws_vpc" "main" {            # type "aws_vpc", local name "main": its address is aws_vpc.main
  cidr_block = "10.0.0.0/16"
  tags       = { Name = "shop" }
}

resource "aws_subnet" "app" {
  vpc_id     = aws_vpc.main.id          # a reference: use the id the VPC gets when it is created
  cidr_block = "10.0.1.0/24"
}

data "aws_ami" "base" {               # a data source reads something that already exists; it creates nothing
  most_recent = true
  owners      = ["self"]
  filter {
    name   = "name"
    values = ["web-base-*"]
  }
}

A resource's arguments are what you set (cidr_block). Its attributes are what the cloud reports back after creating it (id, arn). References such as aws_vpc.main.id are how one resource uses another's attributes, and they are also how Terraform learns the order in which to work.

plan and apply

$ terraform init                    # once per directory: download the providers, set up the state
$ terraform fmt && terraform validate
$ terraform plan -out=tfplan        # compare configuration, state and reality; write the plan to a file
$ terraform apply tfplan            # carry out exactly that plan, and nothing that changed since

Between the configuration and the cloud sits the state: Terraform's record of what it has created and the ID of each object. A plan is a three-way comparison. Terraform reads the state, asks the provider for the current settings of every object in it (the refresh), and compares those with your files. The state file, where it should live and how it is locked, is the subject of Chapter 20.

The plan uses a small set of symbols, and one of them deserves your full attention.

SymbolMeaningWhat happens to the real object
+createA new object
~update in placeThe same object, modified. Usually harmless; some updates restart things
-/+replace: destroy, then createThe old object is deleted and a new one made, with a new ID and nothing that was on the old one. A database replaced is a database emptied
+/-replace: create, then destroyAs above, with the new object made first (create_before_destroy)
-destroyDeleted
<=readA data source will be read during the apply

Whether a change is an update or a replacement is decided by the cloud's API, not by Terraform. An instance's type can be changed on the existing instance. The subnet it lives in cannot: the only way to "change" it is a new instance. The provider knows which arguments are which, and the plan marks the second kind with # forces replacement. Values that will only exist after creation, such as a new ID, appear as (known after apply).

Dependencies

You never tell Terraform the order of operations. It builds a dependency graph from the references: the subnet refers to the VPC's ID, so the VPC is created first; the instance refers to the subnet and to the security group, so it comes after both. Things with no path between them are done in parallel. Destruction runs the graph backwards.

When a dependency exists that no reference expresses (a role that must be attached before a service starts, say), declare it with depends_on. A resource's lifecycle block adjusts how it is handled: create_before_destroy reverses the order of a replacement, prevent_destroy makes any plan that would delete the resource fail, and ignore_changes tells Terraform to leave an argument alone when something else manages it.

The engine compares each resource's arguments with the state, after refreshing the state from the "real" objects. A changed argument marked as forcing replacement replaces the resource; any other change updates it in place. A replaced resource gets a new ID, so every argument that refers to it becomes "known after apply" and counts as changed. The forcing arguments are the ones the AWS provider treats that way: a VPC's or subnet's CIDR block, a subnet's or security group's VPC, and an instance's subnet.

Things to try. Reset between experiments, so that each starts from the applied baseline.

  • Change the instance type. "0 to add, 1 to change, 0 to destroy": an update in place, with the same instance ID. The tile still says the instance restarts, because the cloud has to stop a machine to resize it. In place does not always mean uninterrupted.
  • Change the security group's port. Also one change, and this time nothing restarts.
  • Change the subnet's CIDR. One line, and the plan reads "2 to add, 2 to destroy". The subnet must be replaced, its ID becomes "known after apply", and the instance's subnet_id, which forces replacement, takes the instance with it. The steps under the plan show the order: destroy the instance, destroy the subnet, create the subnet, create the instance. The service is down in between.
  • Add create_before_destroy to the same change. The counts are identical and the symbol becomes +/-: the new instance is created before the old one is destroyed.
  • Change the VPC's CIDR. "4 to add, 4 to destroy". Every resource in the configuration hangs off the VPC's ID, so all of them are rebuilt. This is the plan that must never be applied by someone who only read the first screen.
  • Delete the instance block from the file: "1 to destroy". Removing code removes infrastructure.
  • Press the console button, with the configuration unchanged. The plan opens with "Objects have changed outside of Terraform" and proposes setting the type back. Terraform does not know the change was deliberate; the file is its only source of intent.
  • Apply anything, then look at the plan: "No changes". That was checked for all 64 switch settings and for 579 applies in a random sequence of edits and console changes: after every apply the next plan was empty, and no resource was left referring to an ID that no longer existed.

Variables and outputs

A configuration with every value written in place describes exactly one environment. Input variables are its parameters, locals are named expressions inside it, and outputs are the values it hands back.

variable "environment" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be dev, staging or prod."
  }
}

variable "instance_type" {
  type    = string
  default = "t3.small"
}

locals {
  name = "shop-${var.environment}"                 # computed once, used everywhere
  tags = { Environment = var.environment, ManagedBy = "terraform" }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.base.id
  instance_type = var.instance_type
  subnet_id     = aws_subnet.app.id
  tags          = merge(local.tags, { Name = "${local.name}-web" })
}

output "web_private_ip" {
  value = aws_instance.web.private_ip           # printed after apply; readable by other configurations and scripts
}
# prod.tfvars
environment   = "prod"
instance_type = "t3.medium"

$ terraform plan -var-file=prod.tfvars
$ terraform output web_private_ip
"10.0.1.37"

Values are taken, in rising order of priority, from the variable's default, a terraform.tfvars file, files named with -var-file, and -var on the command line; environment variables named TF_VAR_name sit just above the defaults. Mark a variable or output sensitive = true to keep it out of the plan's printed text. That hides it from the screen only: it is still stored in the state, which is one reason the state needs protecting.

🧹
Use case: Atlassian, April 2022, and a deletion nobody previewed

On 5 April 2022 Atlassian set out to remove an old, retired add-on from its customers' cloud sites, using an internal deletion script. According to the company's own post-incident review, two things went wrong together. The team that asked for the deletion supplied the identifiers of the sites on which the add-on was installed, where the script expected the identifiers of the add-on itself, and the script was run in a mode that deleted permanently instead of marking for deletion. In about twenty minutes it removed 883 sites belonging to roughly 775 customers: Jira, Confluence and everything else on them. Atlassian had backups, and what it lacked was a rehearsed way to restore hundreds of individual customers into a shared platform at once. Some of them waited two weeks. The review's remedies are this chapter in other words: deletions should be soft by default, changes should be staged, and destructive operations need a check of what they are about to do. That check is what a plan is. A line reading "883 to destroy", where the author expected a single add-on, is the kind of thing a reviewer notices. An imperative script has no such line, because it does not know what it is going to do until it has done it.

⚠️
Common mistakes
  • Applying without reading the plan. Especially the last line, and every -/+.
  • Missing "forces replacement" on something that holds data: a database, a volume, a bucket.
  • Changing things in the console that Terraform manages. The next apply reverts the change, or builds on a state that is wrong.
  • terraform apply without a saved plan in automation. What is applied may not be what was reviewed.
  • Unpinned provider versions. The same code plans differently next month.
  • Credentials or secrets in .tf or .tfvars files committed to Git.
  • No prevent_destroy or deletion protection on the resources you could not afford to lose.
  • depends_on everywhere. It hides the real relationships and slows every plan. Use references; add it only where no reference exists.
  • One enormous configuration for everything. Every plan is slow and every mistake can reach everything. Chapter 20 covers splitting it.

Interview drill

Explain it simply: What does terraform plan do?

How a strong answer sounds
It works out what an apply would change, without changing anything. Terraform reads its state, which records the resources it manages and their IDs, refreshes it by asking the provider for each resource's current settings, and compares that with the configuration files. From the differences and the dependency graph it produces a list of actions: create, update in place, replace, or destroy, with the arguments that differ and a summary such as "2 to add, 1 to change, 0 to destroy". I read it for anything destroyed or replaced that I did not intend, save it to a file, and apply that exact file, so that what runs is what was reviewed.

Deeper: You change one argument on a production database resource, and the plan says -/+ must be replaced. What do you do?

How a strong answer sounds
I stop, because replace means the database is deleted and an empty one is created. First I find out which argument forces the replacement; the plan marks it. Then I ask whether the change is needed in that form. Often there is an argument that achieves the same thing in place, or the provider can do it with a different procedure: a storage or instance class change is usually an in-place modification, whereas changing an identifier, an encryption setting or an availability zone is not. If the replacement is truly unavoidable, I plan it as a migration, not as an apply: create the new database as a separate resource, copy or replicate the data, switch the application over, verify, and remove the old one afterwards, each step its own reviewed change. In no case do I let the default order run, which destroys first. For protection in general I would have deletion protection on at the cloud level and prevent_destroy in the lifecycle block, so that a plan like this fails loudly instead of waiting for someone to read it, and I would make the pipeline flag any plan that destroys a stateful resource for explicit approval. And if the difference comes from drift, someone having changed the database outside Terraform, I would bring the configuration in line with reality instead of forcing reality back.

🧠 Key takeaways

  • Declarative code says what should exist; the tool computes the steps, and running it twice changes nothing.
  • A provider teaches Terraform one API. A resource block declares one object; a data source reads one.
  • The workflow is init, plan, apply. The plan compares configuration, state and reality, and touches nothing.
  • + create, ~ update, -/+ replace, - destroy. A replacement is a new object with none of the old one's contents.
  • References between resources form the dependency graph, which sets the order and carries replacements downstream.
  • Variables, locals and outputs turn one configuration into something reusable across environments.
  • Read the plan, save it, apply that file, and protect what must not be destroyed.

Check your understanding

A plan shows -/+ resource "aws_db_instance" "main" with one argument marked # forces replacement. What will an apply do?

-/+ is destroy, then create. The new object has a new ID and none of the old data.

How does Terraform know that a subnet must be created after its VPC?

References define dependencies. File order means nothing, and unrelated resources are created in parallel.

You run terraform apply twice in a row with no change to the files or the cloud. What does the second run do?

Declarative tools act on differences. With none, there is nothing to do, which is what makes them safe to run repeatedly.

An engineer resizes an instance in the cloud console. The Terraform configuration still names the old size. What does the next terraform plan show?

The refresh reads the real object, finds the new size, and compares it with the configuration. The configuration wins unless you change it.

Why save a plan with -out=tfplan and then run terraform apply tfplan?

A bare apply makes a fresh plan at that moment. In a pipeline, the saved file guarantees that what was approved is what runs.
