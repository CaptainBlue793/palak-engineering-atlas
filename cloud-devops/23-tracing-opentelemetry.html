Tracing with OpenTelemetry

Metrics say the checkout is slow. Logs say what each service did. Neither tells you where the 2.3 seconds went when one request crossed six services. A trace does: it is the record of one request's whole journey, with the time spent in every hop. This chapter is about running tracing in production, which is mostly three decisions. How do services get instrumented without rewriting them? What sits between the services and the tracing backend? And, since keeping every trace of a busy system costs more than the system itself, which traces do you keep? OpenTelemetry is the standard that answers the first two, and the simulator explores the third.

Traces and spans

A span is one timed operation: "handle POST /api/pay", "SELECT from orders", "call the acquirer". It has a name, a start time, a duration, a status, and attributes (key-value details such as the route, the status code or the database name). A trace is the set of spans that belong to one request, linked into a tree by parent IDs. Every span carries the same trace ID.

For the tree to form across services, each outgoing call has to carry the IDs along. The standard way is one HTTP header:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └── flags: 01 = this trace is sampled
             │  │                                └── the caller's span ID: the new span's parent
             │  └── the trace ID, the same in every service
             └── version

The receiving service reads the header, starts its own span as a child, and passes a new header on with its own span ID. That is context propagation. The last field matters later in this chapter: the caller can tell everyone downstream whether this trace is being kept.

The three signals answer different questions, and good tooling lets you move between them. A metric shows that p99 latency rose. An exemplar on that metric links to one trace that was slow. The trace shows which service's span took the time. That span's trace ID finds the log lines written while it ran.

OpenTelemetry

For years every tracing vendor had its own client library, and choosing a backend meant choosing how your code was instrumented. OpenTelemetry (OTel) is the open standard that ended that. It is not a backend and stores nothing. It defines how telemetry is produced and transported, for traces, metrics and logs alike.

Instrumentation

There are two kinds, and you want both. Automatic instrumentation gives you a span for every incoming request, outgoing call and database query, which is enough to see where time goes between services. Manual instrumentation adds the spans and attributes only your code knows about: "price the basket", the tenant, the number of items. Start with automatic everywhere, then add manual spans where a trace shows a long, unexplained gap.

On Kubernetes, the OpenTelemetry Operator can inject the automatic agent into pods, so a team opts in with one annotation. The SDK is configured through standard environment variables, which keeps it out of the image.

apiVersion: opentelemetry.io/v1alpha1
kind: Instrumentation
metadata: { name: default, namespace: shop }
spec:
  exporter: { endpoint: http://otel-agent.observability:4318 }
  propagators: [tracecontext, baggage]
  sampler: { type: parentbased_traceidratio, argument: "0.1" }
---
# in the Deployment's pod template: ask the operator to inject the Java agent
  template:
    metadata:
      annotations:
        instrumentation.opentelemetry.io/inject-java: "true"
---
# or set the SDK's standard variables yourself
          env:
            - { name: OTEL_SERVICE_NAME,            value: checkout }
            - { name: OTEL_EXPORTER_OTLP_ENDPOINT, value: "http://otel-agent.observability:4318" }
            - { name: OTEL_TRACES_SAMPLER,          value: parentbased_traceidratio }
            - { name: OTEL_TRACES_SAMPLER_ARG,      value: "0.1" }
            - { name: OTEL_RESOURCE_ATTRIBUTES,     value: "deployment.environment=prod,service.version=4.18.2" }

Span attributes can hold high-cardinality values that would be ruinous as metric labels (Chapter 21): an order ID or a tenant is exactly what makes a trace findable. The rule about secrets and personal data from Chapter 22 applies unchanged.

The collector

Applications could export straight to the tracing backend. In practice they send to a Collector, for the same reasons logs go through an agent: the application hands its spans off quickly and forgets them, and everything else (retries, batching, adding Kubernetes metadata, removing sensitive attributes, sampling, sending to two backends during a migration) is configuration in one place. A collector is a pipeline of receivers, processors and exporters, and the usual layout has two tiers.

# Gateway collector: decide which traces to keep, after they have finished
receivers:
  otlp: { protocols: { grpc: {}, http: {} } }
processors:
  memory_limiter: { check_interval: 1s, limit_percentage: 80 }
  tail_sampling:
    decision_wait: 10s                         # hold every trace this long, so that late spans arrive
    policies:
      - { name: errors, type: status_code, status_code: { status_codes: [ERROR] } }
      - { name: slow,   type: latency,     latency: { threshold_ms: 1000 } }
      - { name: rest,   type: probabilistic, probabilistic: { sampling_percentage: 1 } }
  batch: {}
connectors:
  spanmetrics: {}                              # request rate, errors and duration, computed from every span
exporters:
  otlp/tempo: { endpoint: tempo.observability:4317, tls: { insecure: true } }
  prometheusremotewrite: { endpoint: http://prometheus.monitoring:9090/api/v1/write }
service:
  pipelines:
    traces/metrics: { receivers: [otlp], processors: [memory_limiter], exporters: [spanmetrics] }   # before sampling
    traces:         { receivers: [otlp], processors: [memory_limiter, tail_sampling, batch], exporters: [otlp/tempo] }
    metrics:        { receivers: [spanmetrics], exporters: [prometheusremotewrite] }

Note the order in the last block. Metrics are derived from all spans in one pipeline, and only then is the trace stream sampled in another. The simulator shows why that order is not optional.

Sampling strategies

A service handling a thousand requests a second, with eight spans per request, produces hundreds of gigabytes of trace data a day. Nearly all of it describes requests that were fast and correct and that nobody will ever look at. Sampling is choosing which traces to keep, and there are two places to choose.

Head-based samplingTail-based sampling
DecidedWhen the trace starts, in the first serviceAfter the trace has finished, in a collector
KnowsNothing yet: not whether it will fail or be slowEverything: status, duration, every attribute
Rule"Keep 10% of traces", chosen by trace ID"Keep every error, everything over a second, and 1% of the rest"
Interesting traces keptThe same share as boring ones: 10% of errorsAll of them
Cost in the servicesUnsampled requests create almost no workEvery request is fully traced and exported
Cost in the pipelineNoneCollectors must buffer every span until the decision, and route by trace ID
FitsGetting started; very high volume; a predictable budgetWhen you need the failed request, not a similar one

Two details make head sampling work. The decision must be made once and followed by every service, which is what the parentbased sampler and the flag in traceparent are for: if each service rolled its own dice, most traces would be missing spans. And the choice should be a function of the trace ID, so that it is consistent and repeatable. The two approaches also combine well: head-sample at, say, 50% to halve the load on the services, then tail-sample what remains.

Things to try.

  • Keep everything. 346 GB a day and $3,110 a month at a thousand requests a second. Switch the traffic to 20,000 a second: 6,912 GB a day and $62,208 a month. Nobody keeps everything for long.
  • Head sampling at 10%, each service deciding for itself. 17,278 traces reach the backend, and 7 of them are complete. The rest are fragments: each service kept a different random tenth. The customer's request survives as a single span from one of its four services. You pay for a tenth of the data and get almost no usable traces.
  • Let the first service decide. 5,068 traces, every one complete, for the same money. 51 of the 473 errors were kept, which is the 10% you asked for and no more. The customer's request is there, by luck.
  • Head sampling at 1%. $32 a month. Three error traces out of 473, and the customer's request is not one of them. The p99 computed from the stored traces reads 1.50 seconds where the truth is 2.51: with so few slow traces in the sample, the tail of the distribution is simply missing.
  • Tail sampling. All 473 errors and all 1,010 slow traces, in 3.9% of the volume, for $123. Then read the two red tiles. The stored traces show an error rate of 24% and a p99 of 3.94 seconds, for a service whose real figures are 0.9% and 2.51. The sample is perfect for debugging and useless for statistics.
  • Tail sampling at 20,000 requests a second. The collectors hold 800 MB of spans in memory at every moment, and each service is tracing every request in full. Tail sampling moves cost from storage to the services and the pipeline. It does not remove it.

Use case: Uber, Jaeger and sampling by endpoint

Uber began building its tracing system, Jaeger, in 2015, when its architecture was growing from hundreds of services towards thousands and a single ride request could touch dozens of them. It released Jaeger as open source in 2017, and the project later graduated from the Cloud Native Computing Foundation. In talks and articles about running it, Uber's engineers kept returning to sampling as the central operational problem. A single fixed rate does not work for a system like that. An endpoint called a hundred thousand times a second produces far more traces than anyone can use at 1%, while an endpoint called once a minute would, at the same 1%, produce a trace every couple of hours and be invisible. Their answer was to let the tracing backend compute a sampling rate per service and per endpoint from the traffic it observed, aiming at a target number of traces per second for each, and to push those rates back out to the client libraries, so that nobody had to maintain sampling configuration by hand. The busy endpoints were sampled hard and the quiet ones generously. The idea carries over directly to today's tools: decide what you want to be able to see for each kind of request, then set rates to get that, instead of choosing one percentage and hoping the interesting traces are in it.

⚠️
Common mistakes
  • Every service sampling for itself. Traces arrive with holes in them. Use a parent-based sampler so one decision is followed everywhere.
  • Losing context at a boundary: a queue, a thread pool, a proxy that strips headers. The trace splits in two.
  • Computing error rates or percentiles from sampled traces. After tail sampling, the stored traces are mostly the bad ones. Derive metrics before sampling.
  • Tail sampling without routing by trace ID. Each collector sees part of a trace and decides on part of the evidence.
  • No memory limit on collectors. A traffic spike fills the tail-sampling buffer and the collector is killed, taking all telemetry with it.
  • Only automatic instrumentation. You see that a service took 800 ms and not which step inside it.
  • Secrets and personal data in span attributes, copied from request headers or bodies.
  • One sampling rate for every endpoint. The busy ones drown the backend and the rare ones never appear.
  • Traces that nobody can reach from a metric or a log line. Without exemplars and trace IDs in logs, tracing is a separate tool people forget to open.

Interview drill

Explain it simply: What is the difference between head-based and tail-based sampling?

How a strong answer sounds
Head-based sampling decides when a trace begins, in the first service, usually by keeping a fixed share of trace IDs, and passes the decision downstream so every service agrees. It is cheap, because unsampled requests are barely traced, but it is blind: it keeps the same share of errors and slow requests as of ordinary ones. Tail-based sampling decides after the trace has completed, in a collector that has all its spans, so it can keep every error and every slow trace and a small share of the rest. The cost is that every request is fully traced, collectors must buffer spans for the waiting period, and all spans of a trace must be routed to the same collector. Many setups use a moderate head rate to cap volume and tail sampling on what is left.

Deeper: Your team introduces tail sampling, and a week later the tracing backend's dashboards show a 40% error rate while users report nothing unusual. What happened?

How a strong answer sounds
Nothing happened to the service. The dashboards are computing statistics from the stored traces, and the stored traces are no longer a fair sample. Tail sampling keeps every error and only about 1% of the successes, so if the true error rate is 1%, the kept set is roughly one error for every successful trace, and a ratio taken over it reads near 50%. The same bias inflates latency percentiles, because every slow trace is kept. The fix is to stop deriving rates and percentiles from sampled data. Either compute request rate, error ratio and duration from all spans before the sampling step, with a span-metrics connector in the collector feeding Prometheus, or use the services' own metrics, and use traces only as examples to inspect. I would also make sure the dashboards say which they show. As a sanity check for the future, the kept traces can carry their sampling probability as an attribute so that tools which understand it can re-weight counts, but an SLO should never depend on that.

🧠 Key takeaways

  • A trace is one request's journey; spans are its timed steps; the traceparent header carries the IDs and the sampling flag between services.
  • OpenTelemetry standardises instrumentation and transport (OTLP) and stores nothing. The backend is replaceable.
  • Automatic instrumentation gets you every hop without code changes; add manual spans where it matters.
  • Collectors run as node agents and a gateway: enrich, limit memory, sample, redact, route.
  • Head sampling is cheap and blind. Tail sampling keeps the errors and the slow traces, and needs buffering and routing by trace ID.
  • One sampling decision per trace, followed by every service, or the traces have holes.
  • Never compute rates or percentiles from sampled traces: derive metrics before sampling.

Check your understanding

What is OpenTelemetry?

OpenTelemetry defines the APIs, SDKs, conventions, the OTLP protocol and the Collector. It stores nothing: a backend of your choice does that.

Four services each sample 10% of requests independently. Roughly what share of traces arrive complete, with spans from all four?

All four must independently say yes: 0.1 × 0.1 × 0.1 × 0.1 = 0.0001. A parent-based sampler makes one decision that all four follow, and every kept trace is complete.

A rare request fails, once. Which strategy is certain to have kept its trace?

A head sampler decides before the request has run and cannot know it will fail. Only a decision made after the trace completes can keep it for that reason.

Why must all spans of a trace reach the same collector instance when tail sampling is used?

The error span and the root span may arrive from different services. A load-balancing step keyed on trace ID puts them in front of one decision-maker.

Where should a service's request rate, error ratio and latency percentiles come from when traces are tail-sampled?

The stored traces deliberately over-represent errors and slow requests. Metrics from every span, or from the services themselves, are unaffected by what sampling keeps.
