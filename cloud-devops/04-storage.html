Storage: Block, Object & File

Clouds sell three kinds of storage, and they are not interchangeable. A block volume is a disk for one machine. Object storage is a key-value store for files of any size, reached over HTTP and replicated across a region for you. File storage is a network share that many machines mount at once. This chapter explains what each one is, what "eleven nines of durability" does and does not promise, and how lifecycle policies keep the bill from growing for ever. The simulator applies lifecycle rules to three years of uploads so that you can see which rules save money and which ones cost more than they save.

The short rule: a database gets a block volume, files that an application reads and writes whole go in object storage, and file storage is for the cases where several machines truly need the same directory. Object storage is the default for anything that is not a live database, because it is the cheapest, it has no size to manage and it survives the loss of a zone without any work from you.

Block volumes

A block volume behaves like a disk plugged into the instance, although it is really a service reached over the provider's network. It has four properties worth remembering.

  • It lives in one zone and can only attach to an instance in that zone. It is replicated inside the zone, which protects against a failed disk, not against the loss of the zone.
  • It outlives the instance if you ask for that. A root volume is deleted with its instance by default; a data volume is kept. Check the "delete on termination" flag before trusting either.
  • You pay for the size you provisioned, full or empty, and on current volume types you choose performance (operations per second and megabytes per second) separately from size.
  • A snapshot is a point-in-time copy stored in object storage, so it is regional and survives the zone. Snapshots are incremental: each stores only the blocks that changed since the last. A new volume can be made from a snapshot in any zone, which is how you move one.

Many instance types also have an instance store: a fast disk physically inside the host. It costs nothing extra and it is erased when the instance stops or the host fails. It is for caches and scratch space, never for the only copy of anything.

Volumes can grow and cannot shrink, so grow in steps. A managed database (a PaaS, such as RDS or Cloud SQL) sits on the same kind of volume and does these steps for you, along with scheduled snapshots and a transaction log that lets you restore to any second within a retention period you choose. Two settings there deserve a look on day one: how many days of backups are kept, and what happens to them when the database is deleted.

Object storage

Object storage has almost no structure. A bucket is a named container in a region. An object is a blob of bytes, from zero up to terabytes, stored under a key, which is just a string. logs/2026/10/07/web-3.gz is one key; the slashes mean nothing to the service, though tools show them as folders. You write and read whole objects over HTTPS.

$ aws s3 cp backup.tar.zst s3://acme-backups/db/2026-10-07.tar.zst      # upload (in parallel parts if large)
$ aws s3 ls s3://acme-backups/db/ --human-readable
2026-10-06 02:14:09   41.2 GiB 2026-10-06.tar.zst
2026-10-07 02:13:55   41.3 GiB 2026-10-07.tar.zst

# A link that lets its holder download one object for an hour, with no credentials of their own
$ aws s3 presign s3://acme-backups/db/2026-10-07.tar.zst --expires-in 3600
https://acme-backups.s3.eu-west-2.amazonaws.com/db/2026-10-07.tar.zst?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Expires=3600&...

# Keep every version of every object, so an overwrite or a delete can be undone
$ aws s3api put-bucket-versioning --bucket acme-backups --versioning-configuration Status=Enabled

What you get in exchange for the simple model:

  • It is regional. Each object is stored on several devices in at least three zones before the PUT returns, unless you choose a one-zone class.
  • It does not fill up. There is no capacity to provision. That is also the danger: nothing stops a forgotten job from writing to it for years.
  • It is consistent. On the major providers a read after a successful write returns the new object.
  • Versioning keeps old copies when an object is overwritten or deleted. A delete only adds a marker, and removing the marker brings the object back.
  • Storage classes trade a lower price per gigabyte for a retrieval fee, a minimum storage time or a wait. The table further down has the numbers.
  • Access is private by default, governed by policies (Chapter 6). A presigned URL grants one operation on one object for a limited time.

File storage

Managed file storage is a file system that many instances mount at the same time, usually over NFS: Linux sees an ordinary directory, with locks, permissions and partial writes. It grows and shrinks with its contents and you pay for what is stored. It is the right answer when software expects a shared directory, for example a content-management system that writes uploads to local disk on several web servers, or a Kubernetes volume that many pods must write to (Chapter 15).

It is also the most expensive of the three per gigabyte, by more than ten times over object storage, and every operation is a network round trip, so builds and workloads with many small files are slow on it. When you control the code, writing to object storage is nearly always the better design.

Durability, availability and backups

Storage services publish two numbers that are easy to mix up.

  • Durability is the chance that stored data is not lost. S3's standard class is designed for 99.999999999% (eleven nines) per object per year. AWS's own illustration: store ten million objects and you can expect to lose one every ten thousand years. It gets there by storing redundant pieces across zones and constantly checking and repairing them.
  • Availability is the chance that a request succeeds right now. The same class is designed for 99.99%. An outage of the storage service makes your data unreachable for a while; it does not lose it.

Neither number covers the ways data is lost in practice: someone deletes it, a script overwrites it, a lifecycle rule expires it, ransomware encrypts it, or an account is closed. Durable storage carries out all of those instructions faithfully. The defences are your configuration, as shared responsibility says: versioning so that overwrites and deletes can be undone, an object lock for data that must not change for a set time, replication to a bucket in another region or account, and tested backups of anything on a block volume. The old "3-2-1" rule still holds: three copies, on two kinds of storage, one of them somewhere else. Chapter 32 takes this further.

These are US list prices at the time of writing; Azure (hot, cool, cold, archive) and Google Cloud (standard, nearline, coldline, archive) have the same ladder under other names. A lifecycle policy is a set of rules on a bucket that moves objects down the ladder by age and finally deletes them.

# lifecycle.json
{
  "Rules": [{
    "ID": "application-logs",
    "Status": "Enabled",
    "Filter": { "Prefix": "logs/" },
    "Transitions": [
      { "Days": 30, "StorageClass": "STANDARD_IA" },
      { "Days": 90, "StorageClass": "DEEP_ARCHIVE" }
    ],
    "Expiration": { "Days": 1095 },
    "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
    "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
  }]
}

$ aws s3api put-bucket-lifecycle-configuration --bucket acme-logs --lifecycle-configuration file://lifecycle.json

The last two lines of the rule clean up what nobody sees. With versioning on, every overwrite leaves an old version that is billed at full price until a rule removes it. And a large upload that fails half way leaves its parts in the bucket, invisible in a listing and billed, until they are aborted.

Things to try.

  • No rules. The bill rises by $23 every month, reaches $828 a month after three years and totals $15,318. Nothing is wrong on any single day, which is why nobody notices.
  • Infrequent access after 30 days. The total falls to $8,707, a saving of 43%, and the data is still readable at once.
  • Add deep archive after 90 days. $2,267 over three years, 85% less, and month 36 costs $81.34 for the same 36 TB. The transition requests come to $20 in all. What you gave up is in the last tile: the oldest data now takes about 12 hours to read.
  • Add deletion after a year. The total only moves from $2,267 to $1,969, because archived data was already nearly free. Deleting on its own (with the other two rules off) saves 45%. Delete because a retention policy says so, not for the last few dollars.
  • Now make the objects 50 KB, with both transition rules on. The same 36 TB costs $46,011: three times the bill with no rules. Each month's upload is 20 million objects, moving them costs $1,200 in requests, and $40,000 of the total is transition fees. Infrequent access alone is also a loss, because each 50 KB object is billed as 128 KB: $32 per 1,000 GB against $23 in Standard. With small objects only the delete rule still saves money. The fix is upstream: write fewer, larger objects.
  • Read 10% of the older data every month (100 MB objects, archive after 90 days). The retrieval fees are $1,122 over three years and the rules still save 73%. The money is not the problem here: every one of those reads waits half a day. Data that is still being read belongs in a class with immediate access.

Use case: Dropbox and the price of a gigabyte at scale

Dropbox stored its users' file contents in Amazon S3 for its first eight years while keeping the metadata in its own data centres. By the mid-2010s it held hundreds of petabytes, and a storage price that is trivial per gigabyte had become one of the company's largest costs. Dropbox built its own object store, Magic Pocket, and over 2015 and 2016 moved roughly 90% of its users' data into it; its filing to go public in 2018 put the reduction in operating costs at about $75 million over the two years that followed. The engineering write-ups show the same ideas as this chapter at a larger size: data is split into pieces with redundancy across zones and regions, every piece is continually verified and repaired, the stated durability target is beyond twelve nines, and colder data is stored in a denser, cheaper layout. Two lessons carry down to ordinary bills. Storage is the one cost that only grows unless something deletes or demotes data. And Dropbox kept using the public cloud where the scale did not justify building its own, which for almost every company is everywhere.

⚠️
Common mistakes
  • Treating durability as backup. Eleven nines protects against failed hardware, not against a delete, an overwrite or a bad rule. Turn on versioning and keep a copy elsewhere.
  • The only copy on an instance store or a root volume. Both disappear with the instance.
  • A database on shared file storage, or object storage mounted as if it were a disk. Databases need block volumes.
  • Archiving millions of tiny objects. Transition requests and per-object overhead can exceed the saving. Bundle small objects into larger ones first.
  • Archiving data that is read. Retrieval fees and a twelve-hour wait turn a saving into an incident.
  • Versioning without a rule for old versions, and no rule for abandoned multipart uploads: storage you cannot see and still pay for.
  • An expiry rule on the wrong prefix. Lifecycle deletions are silent and permanent. Test on a copy.
  • Unattached volumes and old snapshots left behind by deleted instances, billed every month.

Interview drill

Explain it simply: When would you use block, object and file storage?

How a strong answer sounds
Block storage is a virtual disk attached to one instance in one zone. It is fast and supports changing any part of a file, so it is what a database or a boot disk needs. Object storage keeps whole objects under keys in a bucket and is reached over HTTP. It is regional, has no capacity to manage and is the cheapest, so it is the default for backups, logs, media, static sites and data lakes; the limits are that you replace whole objects and each request takes tens of milliseconds. File storage is a network file system that many instances mount at once. I use it when software needs a shared POSIX directory, and I avoid it otherwise because it costs more than ten times as much per gigabyte and is slow with many small files.

Deeper: A bucket of application logs grows by 40 TB a month and the storage bill keeps rising. How do you bring it down safely?

How a strong answer sounds
First I find out what is in the bucket and how it is used, with the provider's storage inventory and access logs: object sizes, the age of what is actually read, old versions and incomplete uploads. Then I ask what retention the business and any regulation require, because deleting is the largest saving and the only irreversible one. With that, a lifecycle policy: Standard while the logs are being searched, infrequent access after 30 days, an archive class after 90, expiry at the retention limit, plus rules to expire old versions and abort incomplete multipart uploads. Before applying it I check the traps. If the logs are millions of small files, transition requests and the 128 KB minimum can cost more than they save, so I would have the shipper write larger compressed batches. Archive classes have minimum storage periods and retrieval takes hours, so anything an incident investigation needs quickly stays in a class with immediate access. If access is unpredictable, Intelligent-Tiering avoids guessing. I would apply the rule to one prefix first, compare the next bill with the estimate, and only then to the rest.

🧠 Key takeaways

  • Block is a disk for one instance in one zone; object is whole files over HTTP across a region; file is a shared network directory.
  • Snapshots are incremental, regional copies of a volume. An instance store is erased when the instance stops.
  • Durability is not availability, and neither is a backup: deletes and overwrites are stored durably too.
  • Versioning, object lock, replication and tested backups are your side of shared responsibility.
  • Colder classes cost less per gigabyte and add retrieval fees, minimum durations and per-object charges.
  • A lifecycle policy moves data down by age and deletes it; deletion saves the most and cannot be undone.
  • Small objects and data that is still read are where archiving loses money.

Check your understanding

A PostgreSQL database on a virtual machine needs its data directory on cloud storage. Which kind fits?

A database rewrites small parts of large files and needs low latency: that is block storage. An instance store is fast but erased when the instance stops.

An engineer runs a clean-up script with the wrong prefix and deletes a year of objects from a bucket with eleven nines of durability and no versioning. What does the durability figure do for them?

Durability is about not losing data to failures. A delete is an instruction, and it is replicated to every copy. Versioning or a separate backup is what would have saved the data.

A volume in eu-west-2a must be attached to an instance in eu-west-2b. How?

A block volume belongs to one zone. A snapshot is stored regionally, so a volume can be created from it in any zone of the region.

A bucket holds 500 million objects of about 20 KB each. A rule moves them to infrequent access after 30 days. What is the likely effect on the bill?

Infrequent access bills a minimum of 128 KB per object, so a 20 KB object is charged for more than six times its size at about half the price, on top of a request charge per object moved.

Versioning is switched on for a bucket whose objects are overwritten every night. A year later the bill has grown far more than the visible data. Why?

With versioning, an overwrite adds a new version and keeps the old one, billed as normal storage. A lifecycle rule that expires noncurrent versions after a set number of days fixes it.
