Container Registries & Tags

An image built on a pipeline's machine is useless until the servers that will run it can fetch it. A registry is where images are stored and served, and the name you use to fetch one matters more than it looks. A tag such as web:latest is a label that can be moved to a different image at any time. A digest is a fingerprint of one exact image and can never mean anything else. Whether "what we tested" and "what is running" are the same thing comes down to which of the two your deployment uses. This chapter covers registries, tags against digests, why :latest causes trouble, and scanning images for known vulnerabilities.

  • Explain why a tag is mutable and a digest is not
  • Describe three ways :latest breaks a deployment
  • Choose a tagging scheme and promote one image through environments
  • Say what an image scanner finds, when to run it and what it misses

Registries

A registry is a server that stores images and hands them out over HTTPS. Docker Hub is the public one that Docker uses by default. Every cloud has its own (ECR on AWS, Artifact Registry on Google Cloud, ACR on Azure), GitHub and GitLab include one, and Harbor is a common choice to run yourself. They all speak the same protocol, so the same commands work everywhere. A full image name tells you where to go and what to ask for:

  ghcr.io / acme / web : 4.18.2 @ sha256:9f2c1ab4…
  │         │      │     │        └── digest: the fingerprint of one exact image (optional)
  │         │      │     └─────────── tag: a movable label (default: latest)
  │         │      └───────────────── repository: all the versions of one image
  │         └──────────────────────── namespace: a user, organisation or project
  └────────────────────────────────── registry host (default: docker.io)

  nginx   is short for   docker.io/library/nginx:latest

An image in a registry is two kinds of object. Blobs are the compressed layers and the configuration, each stored under the SHA-256 hash of its content. A manifest is a small JSON document that lists the blobs of one image. Pushing and pulling transfer only the blobs the other side lacks, which is why a small code change on a large base uploads in seconds.

Three operational facts about registries. Access is a permission like any other: pipelines get push rights to their own repository, clusters get pull rights, and nobody uses a personal password (Chapter 6). A registry is a dependency of every deployment and every scale-up: if a node cannot pull, it cannot start your container, so production should pull from a registry you control or mirror, close to the cluster. And registries fill up: every commit pushes an image, so set a retention rule that deletes untagged and old images, as you would for any storage (Chapter 4).

Why not :latest

latest is not special and does not mean "newest". It is only the tag that is used when you give none, and it points wherever the last untagged push left it. Deploying it causes three separate problems.

  • You cannot say what is running. "latest" at the time each machine pulled it. Two machines that pulled an hour apart can be running different code under the same name.
  • Deployments happen by accident, or not at all. If machines pull on every start, a restart quietly picks up whatever was pushed last, tested or not. If they reuse a cached copy, a new push changes nothing on the machines that have one, and "I pushed and it is still the old version" follows.
  • There is nothing to roll back to. The previous image still exists in the registry, but no name points at it any more.

The same applies, more quietly, to any tag that gets reused: stable, prod, 4.18, and a version tag that someone pushes a second time "to fix one thing". A scheme that works:

  • Tag every build with something unique and meaningful: the release version, the Git commit, or both (4.18.2, 4.18.2-9f2c1ab).
  • Make tags immutable in the registry. Most registries have a setting that rejects a push to a tag that already exists.
  • Deploy by digest where you can. Tools that render Kubernetes manifests can resolve the tag to a digest when the release is cut.
  • Build once and promote. The image tested in staging is the same digest that goes to production. Rebuilding "the same commit" for production gives a different image, because base images and dependencies have moved on.

Every push creates a new image with a new digest, moves latest to it and adds a new version tag. "Deploy the newest build" is a deliberate rollout that restarts the container on every node: with a version tag or a digest it first changes the reference to the newest build, and with :latest there is nothing to change. The two start-up behaviours are Kubernetes' IfNotPresent and Always pull policies. A digest reference always resolves to itself, so neither setting affects it. The immutability setting protects version tags; latest stays movable, as it does in registries that apply the rule by pattern.

Things to try.

  • :latest, nodes using cached copies. Push a build, then scale out. The new node runs build 813 while the two old nodes still run 812: two versions behind one name. Reset, push a build and press "Deploy the newest build": nothing changes. Every node already has an image called latest and starts that one again. This is the "I pushed and it is still the old code" problem.
  • :latest, nodes always asking the registry. Push a build, then restart the container on node-1. It comes back as build 813. A restart, which can happen at any time for any reason, has performed a deployment that nobody reviewed.
  • A version tag. Push a build and scale out: all three nodes run 812, because 4.18.2 still means what it meant. "Deploy the newest build" changes the reference to 4.18.3, every node pulls, and the old value is your rollback. Then try the weakness: reset, re-push the deployed tag and scale out. Skew again. Switch the registry to immutable tags and the re-push is refused.
  • A digest. Press everything. Pushes, re-pushes, restarts and new nodes change nothing, until you deploy on purpose and the reference itself changes.
  • Left to chance: a random sequence of about 1,440 of these actions was run under each setting. With :latest and cached copies, the nodes disagreed after 54% of the steps. With :latest and "always ask", after 24%, and 93 restarts changed the running code. With a version tag that can be overwritten, 18% with cached copies and 27% with "always ask". With immutable version tags, and with digests, the nodes never disagreed once.

Image scanning

An image carries an operating system's packages and your application's dependencies, and new vulnerabilities are published for those every day. An image scanner lists every package and library in an image, with versions, and looks each one up in databases of known vulnerabilities (CVEs).

$ trivy image --severity HIGH,CRITICAL --ignore-unfixed ghcr.io/acme/web:4.18.2

# In a pipeline: exit non-zero, so the build fails, when something critical has a fix available
$ trivy image --exit-code 1 --severity CRITICAL --ignore-unfixed ghcr.io/acme/web:4.18.2

Scan in two places, because they answer different questions. In the pipeline: "should this new image ship?" In the registry, continuously: "which images that are already running have become vulnerable?" Then keep the limits in mind. A scanner only knows published vulnerabilities in packages it can identify: it says nothing about bugs in your own code or a misconfiguration. It reports what is present, not what is reachable, so long lists need triage: fix what has a fix, start with what is exposed, and record a reasoned exception for the rest. The best way to shorten the list is the one from Chapter 8: a smaller base image has fewer packages to be vulnerable. Knowing exactly what is inside an image, and proving who built it, is taken further in Chapter 29.

Use case: the day Docker Hub started counting pulls

For years most pipelines and clusters pulled base images from Docker Hub without logging in, and it simply worked. In November 2020 Docker began enforcing limits on image pulls: anonymous users were limited to a fixed number of pulls every six hours, counted per IP address, with a higher limit for free accounts that logged in. Anonymous pulls are counted against the address the request comes from, and a company's whole build fleet, or a whole Kubernetes cluster in private subnets, usually leaves through one or two NAT addresses (Chapter 5). Teams found their builds failing with toomanyrequests: You have reached your pull rate limit, and, worse, found nodes unable to start containers during a scale-up because the image could not be pulled. Nothing in their own systems had changed. The repairs are this chapter's advice: authenticate pulls, keep copies of the base images you depend on in your own registry or a pull-through cache next to the cluster, and reference images by an immutable tag or a digest so that a node which already has the image does not need to ask at all.

⚠️
Common mistakes
  • Deploying :latest, or any tag that is moved, such as prod or stable.
  • Re-pushing a version tag. Machines that cached the old image keep it; new ones get the new one. Turn on tag immutability.
  • Rebuilding for each environment. Production then runs an image nobody tested. Build once, promote the digest.
  • Depending on a public registry at start-up time, without credentials or a mirror: rate limits and outages become your outages.
  • Never cleaning the registry. Thousands of untagged images, billed every month.
  • Scanning only at build time. Vulnerabilities are found after the image ships; scan what is deployed too.
  • Treating a clean scan as "secure". It means no known vulnerabilities in recognised packages, and nothing more.
  • Images pulled from unknown publishers because the name looked right. Use official or verified sources and pin by digest.

Interview drill

Explain it simply: What is the difference between a tag and a digest?

How a strong answer sounds
A tag is a human-readable name in a registry that points to an image, like a branch in Git. It can be moved: pushing a different image under the same tag makes the tag point to the new one. A digest is the SHA-256 hash of the image's manifest, like a commit hash. It identifies one exact image and cannot refer to anything else, and the client verifies the content against it on pull. So tags are for people and digests are for anything that must be reproducible: I tag builds with a version and commit, make tags immutable in the registry, and have deployments reference the digest.

Deeper: After a deployment, some pods of a service behave like the old version and some like the new one, although every pod spec names the same image tag. What happened, and how do you prevent it?

How a strong answer sounds
The tag was moved. Somebody pushed a new image under a tag that was already in use, either latest or a re-pushed version tag. Nodes that had the old image cached kept using it, because the default pull policy for a normal tag is to pull only if the image is not present, while nodes that had never pulled it, or new nodes from a scale-up, fetched the new one. To confirm, I would compare the image digest each pod is actually running, which the pod status reports, and I would expect two different digests behind one tag. To fix the incident I would roll out a reference that cannot be ambiguous: a new unique tag or, better, the digest. To prevent it: make tags immutable in the registry so that a re-push is rejected, have the pipeline tag every build uniquely with the version and commit, deploy by digest, and never use latest outside a laptop. Setting the pull policy to always is not the fix: it makes all pods agree only after each one restarts, and it turns every restart into an unreviewed deployment.

🧠 Key takeaways

  • A registry stores layers by content hash plus small manifests; only missing layers are transferred.
  • A tag is a movable name, like a branch. A digest is the hash of one exact image, like a commit.
  • latest is just the default tag. It hides what is running, makes deployments accidental and leaves nothing to roll back to.
  • Tag every build uniquely, make tags immutable, deploy by digest, and promote one image through every environment.
  • Every start of a container may need the registry: authenticate, mirror what you depend on, and clean up old images.
  • Scan in the pipeline and continuously in the registry. Most fixes are a rebuild on a newer, smaller base.

Check your understanding

What does docker pull nginx fetch?

With no registry the default is Docker Hub, and with no tag the default is "latest", which is an ordinary tag that the publisher moves.

A team pushes a fix under the existing tag web:4.18.2. Nodes that already ran 4.18.2 keep the old image; a new node gets the fix. Which registry setting would have prevented this?

With immutability on, a tag can be created once. The fix would have had to be pushed as a new version, which every node would then pull.

Why can two pulls of web@sha256:9f2c…, a year apart, never return different images?

A digest is a content address. It does not point to an image; it is computed from it.

An image passed its vulnerability scan when it was built three months ago and has not changed. Today the registry reports a critical finding in it. How?

Scanners match packages against a database that grows daily. The image is the same; what is known about it has changed. The fix is a rebuild on an updated base.

Why should the image deployed to production be the same digest that was tested in staging, and not a fresh build of the same commit?

The same source does not guarantee the same image. Promoting one digest through the environments is the only way to deploy exactly what was tested.
