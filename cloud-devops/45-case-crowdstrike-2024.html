Case Study: CrowdStrike 2024 & Staged Rollouts

Early on Friday 19 July 2024 a security company sent a small data file to its customers' Windows computers, as it did several times every day. Within seventy-eight minutes about eight and a half million machines had crashed and could not start again. Airlines stopped flying, hospitals cancelled operations, television channels went off air and emergency call centres fell back to paper. It was the largest IT outage on record, and it contained no attack, no hardware fault and no exotic bug: one file with a mistake in it, delivered to everyone at the same moment, to software that ran in the one place where a mistake stops the whole machine. This case study follows CrowdStrike's own reviews of the incident. It is about a single principle that this course has returned to again and again, and what it costs to make an exception to it.

The update

CrowdStrike sells Falcon, a security product installed on the computers of a large share of the world's big organisations. On each machine a small program called the sensor watches what the system does and blocks behaviour that looks like an attack. To see everything, part of the sensor runs inside the operating system's kernel, and it is loaded early in the boot sequence so that nothing can start before it.

The sensor receives two quite different kinds of update, and the difference is the heart of the story.

The reason for the right-hand column was a good one. New attacks appear within hours, and customers pay for protection that keeps up. Speed was the feature. At 04:09 UTC on 19 July, CrowdStrike published a rapid response content update, a file in a series numbered 291. Every Windows machine running a recent sensor that was switched on and connected began to download it.

Why every machine crashed

A data file cannot crash a computer by itself. The program that reads it can, and what that program did with this file is worth following, because the same pattern exists in any system that interprets configuration.

Earlier in 2024 a sensor release had added a new kind of detection, and with it a new template for content files. The template defined 21 input fields. The sensor's code that supplied values to it provided 20. For months this mismatch did nothing, because every content file published for that template put a wildcard, "match anything", in the 21st position, and a wildcard does not need to look at the value. The file published on 19 July was the first to put a real condition there. To evaluate it, the sensor read the 21st value from a list that held 20. In a kernel, reading past the end of a list is a read of memory that does not belong to you, and the processor stopped the machine.

Three properties of the design then turned a bug into a catastrophe.

  • It ran in the kernel. A faulty program in user space is ended by the operating system and everything else carries on. A fault in kernel code has nothing above it to catch it. The whole machine halts.
  • It loaded at boot, and kept the file. On restart the sensor loaded early, read the same file and crashed again, before the network was up and before any update could arrive. The machine could not rescue itself.
  • The check that should have caught it had the same blind spot. The automated validator approved the file, because of a fault in its own logic, and the file was never loaded on a real machine before release. The sensor itself did not check that the field it was asked for existed.

The wider lesson is in the phrase "only configuration". The content file was not code in the usual sense, but it was instructions to code, executed in the most privileged place on the machine. Anything that changes what production software does is a change, whatever its file extension, and deserves the caution given to a release. Cloudflare's outage in Chapter 17 was a rule; Reddit's in Chapter 43 was a label. This one was a threat pattern.

Recovery at scale

CrowdStrike identified the problem and withdrew the file in 78 minutes. For the machines that had already crashed, that made no difference, and the repair shows what "at scale" means when automation is unavailable.

# The fix, for one machine, with a person in front of it
1. Start Windows in Safe Mode or the Recovery Environment
2. If the disk is encrypted: find and type this machine's 48-digit BitLocker recovery key
3. Open a command prompt and delete the faulty file:
     del C:\Windows\System32\drivers\CrowdStrike\C-00000291*.sys
4. Restart normally

# For a virtual machine in a cloud: no keyboard to sit at
1. Stop the machine and detach its disk
2. Attach the disk to a healthy machine, delete the same file, detach
3. Reattach to the original machine and start it

Each step is simple. The difficulty was multiplication, and a set of dependencies that nobody had thought about until that morning.

  • Hands. Fifteen minutes per machine, times tens of thousands of machines in a large company, with a fixed number of technicians. Many machines were check-in kiosks, shop tills and screens in places with no IT staff at all.
  • Keys. Disk encryption, a good practice, meant each machine needed its own recovery key. In many organisations the keys were stored on servers that were themselves in the boot loop.
  • Tools. The remote management systems normally used to repair machines ran on Windows servers with the same sensor.
  • Order. Directory servers and the key stores had to be brought back first, by hand, before anything else could be.

Some machines recovered by being restarted again and again until, by luck, the network came up and fetched the corrected file before the crash. Microsoft and CrowdStrike published bootable tools within days. Most organisations were largely restored within a few days, and some took weeks. One airline cancelled around seven thousand flights. An insurer's estimate put direct losses to the largest American companies alone at over five billion dollars.

The lesson for anyone designing recovery is the one from Chapter 32 and Chapter 44: the way back must not run through the thing that is broken. Keys, management tools and instructions need a home that does not share the failure.

Staged rollout principles

The fix CrowdStrike announced was, in essence, to treat content the way it already treated code. The principles are the ones from Chapter 17, and the incident shows what each is for.

The objection to all this is speed. Protection against a new attack should not wait a day. But the steps need not take a day. A ring that holds for ten minutes while an automatic check confirms that the machines are still alive adds half an hour to a rollout and would have confined this incident to a few thousand machines. The trade was never between fast and safe. It was between staged and all at once.

There are two lessons for the software on the device as well. First, validate input where it is used, even when it comes from your own company: a bounds check on that one read would have turned a global outage into a detection that silently did not fire. Second, keep out of the kernel what does not need to be there, because the price of a mistake depends on where it runs.

And there is a lesson for customers, who cannot fix a supplier's process. Know which of your suppliers can push changes to your machines without asking. Where the product lets you, put your own machines in rings: a few first, the critical ones last. Do not let the systems you would use for recovery receive updates at the same instant as the systems they recover. And keep the keys somewhere that survives.

    Things to try.

    • The starting settings are the real incident: a validator only, everyone at once, stopped by people after 78 minutes, kernel code, encrypted disks. 8,478,261 machines cannot start, and repairing them takes about 3.5 million hours of hands-on work.
    • Change only the rollout to rings. 260,870 machines: about a thirtieth. Look at the timeline, though. People still took 78 minutes, and at minute 60 the clock opened the second ring to another 900,000 machines. Rings without a health gate only slow a failure down.
    • Add the automatic health check. 10,870 machines, a 780th of the real figure, and the rollout stopped before the first ring had finished downloading.
    • Go back to everyone at once, with the automatic check: 1,086,957. Fast detection alone still loses a ninth of the fleet, because in ten minutes the file has gone a long way. You need the small ring and the gate.
    • Move the component to user space, with the original rollout. The same 8.5 million machines load the file and none goes down: the component restarts and fetches the correction. Hours of repair: zero.
    • Switch off disk encryption in the real-incident settings: 2.1 million hours where there were 3.5 million. Encryption was the right choice. Keeping the keys only on machines that shared the failure was the mistake.
    • Load the file on a real machine before release: nothing is published at all, whatever the other four settings.

    Use case: McAfee, April 2010, and the update that ate Windows

    The 2024 outage had a close precedent fourteen years earlier, which makes it harder to call unforeseeable. On 21 April 2010 the antivirus company McAfee released one of its routine daily virus-definition files, numbered 5958. The file contained a faulty signature that matched a legitimate, essential component of Windows XP, a file called svchost.exe, as if it were a piece of malware. On machines running the affected version of Windows, the antivirus program did exactly what it was built to do with malware: it quarantined the file. Without it, Windows lost networking and fell into a cycle of restarts. Hospitals, universities, police forces and a large number of companies found their PCs unusable within hours. As in 2024, the vendor withdrew the file quickly, and as in 2024 that did not help the machines already affected, because they could no longer reach the network to receive anything. Technicians went from desk to desk restoring the missing file by hand. McAfee apologised and described the cause: the definition had not been tested against that configuration of Windows, and a recent change to its quality process had let it through. It promised more thorough testing and safeguards for critical system files. The parallels are close. A security product with deep privileges. A data update, shipped many times a day and thought of as routine. Delivery to everyone at once. And a failure that removed the very channel by which a fix could be sent. The principle that prevents both incidents, stage every change and watch what happens to the first few, was already well known in 2010.

    ⚠️
    Common mistakes
    • "It is only configuration." Rules, flags, content files, models and policy all change behaviour, and need a staged rollout.
    • Two release processes, a careful one and a fast one, with the fast one used most often.
    • Trusting a validator in place of loading the real artefact on a real system.
    • Releasing to everyone at once because the change is small. Size of change and size of consequence are unrelated.
    • A rollout that only people can stop. By the time people agree there is a problem, it is everywhere.
    • No health signal from the updated machines, or one that cannot tell "quiet" from "dead".
    • Code that trusts its own vendor's input and skips the bounds check.
    • A component that crashes the host when it fails, where it could disable itself and report.
    • No last-known-good fallback. The device loads the bad configuration at every start.
    • Recovery tools, keys and instructions that depend on the affected systems.
    • As a customer: every machine, including the recovery infrastructure, taking a supplier's updates at the same instant.

    Interview drill

    Explain it simply: What happened in the CrowdStrike outage, and what is the main lesson?

    How a strong answer sounds
    CrowdStrike's security sensor runs partly in the Windows kernel and loads at boot. In July 2024 the company pushed a routine content update, a data file describing threats, to all customers at once. The file exercised a mismatch in the sensor: it referred to a 21st input where the code supplied 20, so the sensor read memory out of bounds and, being kernel code, crashed the whole machine. Because it loaded at boot and re-read the file, machines went into a crash loop and could not download the fix that was published 78 minutes later. About 8.5 million machines needed manual repair. The main lesson is that anything that changes the behaviour of production systems is a change and must be rolled out in stages, with a small first ring, a health signal and an automatic stop, however small or routine it looks. The secondary lessons are to test the real artefact on a real system, to validate input where it is used, to fail safe with a last-known-good fallback, and to keep the recovery path independent of what can break.

    Deeper: You run a service that pushes configuration to an agent on 200,000 customer servers, and customers expect new rules within minutes. Design the rollout.

    How a strong answer sounds
    I would start by refusing the framing that fast means all at once, and design for both. Before release, every configuration is loaded by the real agent, on the real operating systems and versions we support, in an automated test that takes a minute or two. A schema validator is useful as a first filter and is not a substitute. Then rings. Ring zero is our own fleet. Ring one is a fraction of a per cent of customer servers, deliberately varied across operating systems and regions, including volunteers who have opted in to early updates. Then 5%, 25% and everyone. Between rings there is a gate, and the gate is automatic: every agent sends a heartbeat that includes the configuration version it is running, so within a few minutes I can compare the share of updated agents still reporting healthy with the baseline. If it drops, the rollout halts and reverts with nobody deciding, and pages a person afterwards. With gates of five minutes the whole rollout takes about twenty, which meets "minutes" for almost everything. For a real emergency there is a faster path, but it skips waiting time, not the first ring or the check. On the agent side I would build defences that do not depend on our getting the rollout right. The agent validates every configuration when it loads it and refuses what it does not understand, keeping the previous version. It keeps the last known good configuration on disk, and if it crashes shortly after applying a new one, it starts with the old one and reports the failure. The parser runs with as little privilege as possible, never in the kernel if it can be avoided, so the worst case is the agent restarting and not the server. For customers, I would expose control: which of their servers are in early rings, a delay they can set for critical systems, and a way to pin a version. And I would practise a bad push on purpose in a test environment, to confirm that the halt, the revert and the fallback all work, because those are the paths that otherwise run for the first time on the worst day.

    🧠 Key takeaways

    • One faulty content file, sent to all customers at once, crashed about 8.5 million Windows machines in 78 minutes.
    • It crashed the machine because the code that read it ran in the kernel, and looped because it loaded at boot.
    • The fix was quick and could not be delivered: crashed machines were beyond the reach of the network.
    • Configuration, content, rules and flags are changes. Stage them like code.
    • A staged rollout needs a real test, small rings, a health signal and an automatic stop.
    • On the device: validate input, fail safe, fall back to the last known good state.
    • Keep recovery tools and keys independent of the systems they recover.

    Check your understanding

    Why did withdrawing the faulty file after 78 minutes not repair the affected machines?

    The sensor loaded early in boot and re-read the stored file each time, so the machine never stayed up long enough to receive the correction.

    Why did a fault in reading a data file bring down the whole operating system?

    A user-space program that faults is ended and the system continues. Kernel code has nothing above it to contain the fault.

    The vendor rolled out sensor code in stages but sent content updates to everyone at once. What reasoning does this incident show to be wrong?

    Content interpreted by privileged code has the power of code. Anything that changes production behaviour needs a staged rollout.

    Which addition would have reduced the number of affected machines the most?

    A small ring limits who can be hit, and an automatic health gate stops the rollout in minutes without waiting for people to notice.

    Many organisations could not read their disk recovery keys during the outage. Why?

    The recovery path depended on systems that shared the failure. Keys and tools for recovery need a home that does not.
