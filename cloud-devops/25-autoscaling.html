Autoscaling: HPA, VPA & Cluster Autoscaler

Kubernetes can change three things about a workload without being asked: how many pods it has, how large each pod is, and how many nodes there are to put them on. Three different controllers do that, they watch different signals, and they act in sequence, so a burst of traffic sets off a chain: a metric rises, a controller notices, pods are created, they find no room, a node is ordered, the node boots, an image is pulled, the application starts. Each link takes time, and for that time the service is short of capacity. Autoscaling well is mostly the craft of shortening that chain. This chapter covers each autoscaler and then the lag, with a simulator that triples the traffic and counts the requests lost while the cluster catches up.

Everything rests on resource requests. The HPA expresses CPU utilisation as a percentage of the request. The scheduler places pods by their requests. The node autoscaler adds nodes when requests do not fit. A workload with no requests, or with requests that are fiction, cannot be autoscaled sensibly by any of the three.

HPA on CPU and custom metrics

The Horizontal Pod Autoscaler runs one calculation, every 15 seconds:

                                   current metric value
  desired replicas = ceil( current replicas × ────────────────────── )
                                    target metric value

  10 pods at 91% CPU, target 70%:   ceil(10 × 91 ÷ 70) = 13
  13 pods at 70%:                   ceil(13 × 70 ÷ 70) = 13     no change
  13 pods at 40%, later:            ceil(13 × 40 ÷ 70) = 8      scale in, after the stabilisation window
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: checkout, namespace: shop }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: checkout }
  minReplicas: 10
  maxReplicas: 60
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
    - type: Pods                                 # a custom metric, served by a metrics adapter
      pods:
        metric: { name: http_requests_per_second }
        target: { type: AverageValue, averageValue: "70" }
  behavior:
    scaleUp:   { stabilizationWindowSeconds: 0 }       # add pods at once
    scaleDown:
      stabilizationWindowSeconds: 300                # remove them only after five calm minutes
      policies: [{ type: Percent, value: 25, periodSeconds: 60 }]

With several metrics the HPA computes a replica count for each and takes the largest. A few details shape its behaviour. Changes within 10% of the target are ignored, so it does not flap. Scale-down waits for a stabilisation window, five minutes by default, and uses the highest recommendation seen in it. And it is bounded by minReplicas and maxReplicas, which you set from what the service needs to survive and what its dependencies can stand.

The choice of metric matters more than any tuning. CPU is free and it is the default, and it has the flaw Chapter 3 demonstrated: a saturated pod reports 100% whether it is slightly or hugely overloaded, so with a 70% target the HPA can ask for at most 100 ÷ 70, about 1.4 times, the current pods per round. Requests per second per pod has no ceiling: if each pod should take 70 requests a second and 2,100 are arriving, the answer is 30 pods, in one step. For workers, the right metric is the length of the queue. Use the signal that measures demand, not the one that measures how hard the existing pods are struggling.

VPA

The Vertical Pod Autoscaler watches what each container really uses and recommends requests to match, and it can apply them. Its first use is simply to tell you the truth: most requests are guesses made once, and the VPA's recommendation in Off mode is the cheapest right-sizing tool there is (Chapter 31). In its automatic modes it changes requests by replacing pods, although recent Kubernetes versions can resize a running pod in place. It suits things you cannot simply run more copies of: a database, a single-instance controller, a batch job.

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata: { name: checkout, namespace: shop }
spec:
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: checkout }
  updatePolicy: { updateMode: "Off" }          # recommend only; read it with kubectl describe vpa

One rule: do not let the HPA and the VPA act on the same metric for the same workload. If the HPA scales on CPU utilisation and the VPA raises the CPU request, utilisation falls, the HPA removes pods, utilisation rises, and the two chase each other. Scale horizontally on a traffic metric and let the VPA manage memory, or use the VPA for recommendations only.

Cluster Autoscaler and Karpenter

When the HPA asks for pods that fit on no node, they sit in Pending. A node autoscaler turns that into machines.

Cluster AutoscalerKarpenter
Works throughNode groups you define in advance, each one instance type or a few similar onesThe cloud's instance API directly
DecidesWhich existing group to grow by one or more nodesWhich instance types and sizes fit the pending pods best, then launches them
From Pending pod to ready nodeTypically two minutes or moreTypically about a minute
Removing nodesA node underused for ten minutes is drained and removedContinuous consolidation: repacks pods onto fewer or cheaper nodes
Spot and mixed capacityOne group per kindChosen per launch, with fallback
Runs onEvery major cloudAWS first, others following

Both obey the same inputs: pod requests, node selectors, topology constraints, and PodDisruptionBudgets, which say how many pods of a workload may be evicted at once when nodes are drained. And both are limited by things outside the cluster: instance quotas, the availability of the type you want in that zone, and IP addresses in the subnets (Chapter 5).

Scaling lag

Put the pieces in order and you have the path from "traffic rose" to "new capacity is serving".

Each link has its own remedy:

  • Metric and HPA: scale on a demand signal, with a short scrape interval. For traffic that rises at known times, raise minReplicas on a schedule beforehand.
  • Room: keep headroom. The standard trick is placeholder pods: a Deployment of do-nothing pods with a very low priority that reserve a node's worth of space. A real pod evicts them instantly and starts, and the evicted placeholders become the Pending pods that order the next node.
  • Node: a faster provisioner, and instance types that are actually available.
  • Image: small images (Chapter 8), and pre-pulled or baked onto the node image for the largest.
  • Start: fast application start-up, and a readiness probe that passes as soon as it truthfully can.
  • And for what remains: a lower utilisation target, so that existing pods can absorb more while help arrives.

Simulator: traffic triples

A service runs 10 pods on 2 nodes, five pods to a node. Each pod can serve 100 requests a second and the HPA aims for 70. At time zero, traffic jumps from 700 to 2,100 requests a second and stays there: the service now needs 30 pods and has capacity for 1,000 requests. Choose the set-up and see how long the gap lasts.

The model runs second by second. The HPA syncs every 15 seconds and sees metrics 30 seconds old. With CPU it computes from utilisation capped at 100%; with requests per pod it computes from the real request rate. A new pod on an existing node starts from a cached image; on a new node the image is pulled first. A pod is ready 5 seconds after its application has started, when the readiness probe next passes. Nodes hold five pods, are ordered as soon as pods are Pending, and arrive in parallel. Requests above the capacity of ready pods are counted as lost.

Things to try. Change one setting at a time and read the log each time.

  • The starting point: CPU metric, no spare room, a slow node provisioner, a large image and a slow start. The service is short of capacity for 7 minutes 55 seconds and loses 402,500 requests. The log shows three HPA rounds, at 0:30, 4:30 and 8:30, and the first new pod does not serve until 3:55.
  • Switch the metric to requests per pod. One decision, for all 30 replicas, at 0:30. Recovery falls to 3:55 and losses to 258,500, with the same nodes, image and application. The metric alone was worth half the outage.
  • Go back to CPU and add the placeholder room. The first five pods serve at 1:05 instead of 3:55, because they did not wait for a node. Recovery is 5:10: better, and still three rounds.
  • Use both. Recovery is 3:55 again, since the last pods still wait for nodes, but losses fall to 173,500: the headroom carried part of the load while the nodes were on their way.
  • Then shorten the node path one link at a time: the faster provisioner brings recovery to 2:45, the small image to 2:10, the fast start to 1:43, with 80,800 requests lost. That is a fifth of where you began.
  • What is left. In the best case the first new pod serves at 0:38, and thirty of those seconds passed before the HPA knew anything. No autoscaler removes that. The first half-minute of a spike is carried by the capacity already running, which is the argument for a utilisation target with real headroom in it.

KEDA

The HPA is built around metrics of the pods themselves. Many workloads should scale on something outside: messages waiting in a queue, lag on a Kafka topic, rows in a table, the time of day. KEDA (Kubernetes Event-Driven Autoscaling) is the standard add-on for that. You declare a ScaledObject with one or more scalers, and KEDA creates and feeds an ordinary HPA for you. It adds one thing the HPA cannot do alone: scaling to zero when there is nothing to do, and back to one when the first event arrives.

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: invoice-worker, namespace: shop }
spec:
  scaleTargetRef: { name: invoice-worker }
  minReplicaCount: 0                      # no messages, no pods
  maxReplicaCount: 40
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.eu-west-2.amazonaws.com/111122223333/invoices
        queueLength: "20"                 # aim for 20 waiting messages per pod
        awsRegion: eu-west-2
    - type: cron                          # and never fewer than 5 during the month-end run
      metadata: { timezone: Europe/London, start: "0 6 28 * *", end: "0 20 28 * *", desiredReplicas: "5" }

Use case: Pokémon GO and fifty times the forecast

When Niantic launched Pokémon GO in July 2016, its backend ran on Kubernetes on Google Cloud, with player data in Google's managed NoSQL database. Google's engineers later described the launch from their side. Niantic had planned capacity around a target level of traffic and had agreed a worst case of five times that target. Within fifteen minutes of the game going live in Australia and New Zealand, traffic had passed the target. It kept going, and eventually reached about fifty times the target: ten times the worst case anyone had planned for. The system had autoscaling, and autoscaling was not what saved it. Google's reliability engineers joined Niantic's, and together they provisioned capacity ahead of each country's launch instead of waiting for load to trigger it, added tens of thousands of cores to what became the largest Kubernetes cluster Google's cloud had run for a customer, and even upgraded the cluster to a newer version while it was serving millions of players, in order to raise its node limit. The launch in Japan two weeks later was planned with that experience and went smoothly. Everything in this chapter has a boundary, and this story is at it. Autoscaling reacts within limits set in advance: a maximum replica count, a quota, a database's throughput, the minutes a node takes to boot. For a predictable event, capacity is put in place beforehand, and Chapter 39 is about how to work out how much.

⚠️
Common mistakes
  • No resource requests, or invented ones. Utilisation is a percentage of the request, and scheduling and node scaling work from requests.
  • Scaling on CPU for a workload that waits on I/O. CPU stays low while the service drowns. Scale on requests or queue length.
  • A utilisation target of 90%. No room to absorb anything while new pods start.
  • HPA and VPA on the same metric. They fight.
  • replicas set in the manifest of an autoscaled Deployment: every deployment resets the count (Chapter 18).
  • maxReplicas as an afterthought. Too low and it caps you during the incident; too high and a runaway scale-up exhausts the database's connections.
  • Forgetting the layers below: quota, subnet addresses, instance availability. The HPA asks; the cloud may say no.
  • No PodDisruptionBudget. Node consolidation evicts every replica of a small service at once.
  • Scale-down as fast as scale-up. The pod count oscillates with every wave in the traffic.
  • Never testing it. The first real spike is the load test, in production.

Interview drill

Explain it simply: How does the Horizontal Pod Autoscaler decide how many pods to run?

How a strong answer sounds
Every 15 seconds it reads a metric for the pods of a workload and computes desired replicas as the current count times the current value over the target, rounded up. With 10 pods at 91% CPU and a 70% target that is 13. CPU utilisation is measured against each pod's request, so requests have to be set. It ignores differences within 10% of the target, scales up quickly, and waits through a stabilisation window, five minutes by default, before scaling down, taking the highest recent recommendation. It stays between the configured minimum and maximum. It can also use custom metrics such as requests per second per pod, or external ones such as queue length, and with several metrics it takes the largest answer. If the new pods do not fit on the existing nodes, they are Pending until a node autoscaler adds a node.

Deeper: A service has an HPA on CPU, and every traffic spike still causes several minutes of errors before it recovers. Where does the time go, and what would you change?

How a strong answer sounds
I would lay out the chain and measure each link for a real spike. First detection: the metrics pipeline averages over a window and the HPA syncs every 15 seconds, so half a minute passes before anything is decided. Then the decision itself: saturated pods report 100% CPU, so with a 70% target the HPA can only ask for about 1.4 times the current pods, and a tripling of traffic takes three rounds, each waiting for the previous pods to become ready. Then placement: if the nodes are full the new pods are Pending, and a node takes one to several minutes to be ordered, boot and join. Then the image has to be pulled on the empty node, and the application has to start and pass readiness. Events and timestamps on the HPA, the pods and the nodes show which of these dominates. The changes follow the chain. Scale on requests per second per pod so the right count is computed in one step. Keep headroom with low-priority placeholder pods so the first new pods start on existing nodes in seconds. Use a faster node provisioner and instance types that are available. Shrink the image and the start-up time. Lower the utilisation target and raise the minimum replicas, on a schedule if the spikes are predictable. And make the service shed excess load cleanly, so that the requests it does accept stay fast while capacity arrives. Then I would run a load test that reproduces the spike and confirm the gap is gone.

🧠 Key takeaways

  • HPA changes pod count, VPA changes pod size, the node autoscaler changes node count. All three work from resource requests.
  • HPA: desired = ceil(current × metric ÷ target), every 15 seconds, with a 10% tolerance and a slow scale-down.
  • Scale on a measure of demand. Saturated CPU caps each round at about 1.4 times.
  • Do not point the HPA and the VPA at the same metric.
  • The Cluster Autoscaler grows predefined node groups; Karpenter launches whatever fits the pending pods, faster.
  • Scaling lag is a chain: metric, decision, room, node, image, start. Headroom removes the slowest links for the first pods.
  • KEDA scales on external events and to zero. Autoscaling works inside limits; known events need capacity in advance.

Check your understanding

An HPA targets 60% CPU. The Deployment has 8 pods averaging 90%. How many replicas does it ask for?

ceil(8 × 90 ÷ 60) = 12. The same load spread over 12 pods gives 60% each.

Traffic to a service triples in a second. Its HPA scales on CPU with a 70% target. Why does it take several rounds to reach the right size?

Utilisation cannot exceed 100%, so the formula gives at most 100 ÷ 70 of the current count. A metric of demand, such as requests per pod, has no such ceiling.

The HPA has raised a Deployment from 10 to 20 replicas, and the 10 new pods stay Pending. What is the most likely reason, and what resolves it?

Pending means unscheduled. Pulling and probing happen only after a pod has been placed on a node.

What are low-priority "placeholder" pods for?

They turn a multi-minute wait for a node into a few seconds for the first new pods, at the cost of paying for a little idle capacity.

A worker Deployment processes messages from a queue, and on most nights the queue is empty. Which approach fits best?

Queue length is the demand. KEDA feeds it to an HPA and can scale the workers to zero when the queue is empty.
