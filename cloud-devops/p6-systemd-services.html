Processes & systemd

Running ./server & in an SSH session is not running a service. When you log out it may die; when it crashes nobody restarts it; when the machine reboots it does not come back; and its output goes nowhere. On almost every Linux server, systemd is the process that fixes all of that: it starts services in the right order at boot, restarts them by a policy you choose, captures their logs, and stops them gracefully. Kubernetes later does the same job for containers across many machines, and most of its ideas are here first.

  • Explain the start limit, and why a fast crash loop ends in start-limit-hit
  • Read logs with journalctl, filtered by unit, time and priority
  • Stop services gracefully and pass configuration and secrets safely

What a service manager does

systemd runs as process 1, the first process the kernel starts and the ancestor of every other. For each service it manages, it is responsible for five things: ordering (start the app after the network is up), supervision (notice when the process exits and decide whether to restart it), identity (run it as an unprivileged user), logging (collect stdout and stderr into the journal) and shutdown (stop it cleanly, then forcefully). You describe all of that declaratively in a unit file.

A unit file for a web app

# /etc/systemd/system/app.service
[Unit]
Description=Shop web app
After=network-online.target              # start after the network is configured…
Wants=network-online.target               # …and pull that target in

[Service]
Type=exec                                 # "started" once the binary has been exec'd
User=app                                  # never root
WorkingDirectory=/opt/app
EnvironmentFile=/etc/app/app.env          # KEY=value lines, file mode 0600
ExecStart=/opt/app/bin/server --port 8080
Restart=on-failure
RestartSec=2
TimeoutStopSec=30                          # SIGTERM, then SIGKILL after 30 s
LimitNOFILE=65536                         # open files: sockets count too
NoNewPrivileges=yes
ProtectSystem=strict                      # the OS is read-only to this service…
ReadWritePaths=/var/lib/app               # …except where it keeps state

[Install]
WantedBy=multi-user.target                # start at boot in normal multi-user mode
$ sudo systemctl daemon-reload            # re-read unit files after any edit
$ sudo systemctl enable --now app         # start now AND at every boot
$ systemctl status app
● app.service - Shop web app
     Loaded: loaded (/etc/systemd/system/app.service; enabled)
     Active: active (running) since Thu 2026-10-01 09:12:44 UTC; 3s ago
   Main PID: 4410 (server)
     Memory: 41.2M
$ sudo systemctl restart app             # stop + start (the deploy step from Prerequisite 1)

Three details catch people. enable and start are different: start runs it now, enable makes it start at boot; --now does both. After editing a unit, run daemon-reload, or systemd keeps using the old version and warns you in status. And the lines in [Service] are not a shell: ExecStart does not expand ~ or pipes or &&; if you need those, call a script.

Restart policies and the start limit

When the main process exits, systemd looks at how it exited and at Restart= to decide what to do. A clean exit is code 0, or one of the "polite" signals SIGHUP, SIGINT, SIGTERM or SIGPIPE; anything else (a non-zero code, a crash signal such as SIGSEGV, being killed by the out-of-memory killer, a timeout) is unclean:

The process…Restart=noon-abnormalon-failurealways
exits with code 0 (or SIGTERM)stays stoppedstays stoppedstays stoppedrestarts
exits with code 1, 2, …stays stoppedstays stoppedrestartsrestarts
is killed by a signal (SEGV, OOM SIGKILL)stays stoppedrestartsrestartsrestarts
times out starting or stoppingstays stoppedrestartsrestartsrestarts

on-failure is the usual choice for long-running services; always suits a process that should never exit, even cleanly; batch jobs that are meant to finish use no. Restarting has a limit, though: by default, if a unit is started more than 5 times within 10 seconds (StartLimitBurst and StartLimitIntervalSec, which live in [Unit]), systemd gives up and marks it failed with start-limit-hit. With the default RestartSec of 100 ms, a service that crashes at startup hits that limit in about half a second. Try it:

Green bars are time the process was running, grey is waiting to restart, red ticks are unclean exits, blue ticks clean exits. The journal shows the exact lines journalctl -u app would print (only the first and last few events when there are many).

Two lessons come out of the simulator. A crash at startup with no delay burns through the start limit almost instantly and leaves the unit failed, which is actually helpful: it stops a broken service from spinning, and status tells you to look. A longer RestartSec keeps it below the limit, so it crash-loops forever, quietly, unless something alerts on the restart count. Either way, the restart policy is a seat belt, not a fix. Recent systemd versions (254 and later) can also back off: RestartSteps= and RestartMaxDelaySec= grow the delay after each failure, which is what Kubernetes does by default with CrashLoopBackOff (Chapter 12).

Logs with journalctl

Everything a service writes to stdout and stderr goes to the journal, with the unit name, PID and priority attached, so services do not need their own log files. journalctl filters it:

$ journalctl -u app -f                     # follow, like tail -f
$ journalctl -u app --since "10 min ago"    # or --since "2026-10-01 02:00"
$ journalctl -u app -p err -b               # errors and worse, since this boot
$ journalctl -u app -o json-pretty -n 1     # one entry with every field
$ journalctl --disk-usage                    # the journal is capped; check its size

On some distributions the journal is kept only in memory by default and lost on reboot; creating /var/log/journal (or setting Storage=persistent in journald.conf) keeps it. On a real fleet, a log shipper also forwards it off the machine (Chapter 22), because the moment you most need a server's logs is often when the server is gone.

Stopping gracefully, and configuration

systemctl stop sends SIGTERM to the service's processes, waits up to TimeoutStopSec (90 s by default), and then sends SIGKILL to whatever is left. A well-behaved server catches SIGTERM, stops accepting new connections, finishes in-flight requests and exits. Deploys that restart services depend on that: if the app ignores SIGTERM, every restart waits the full timeout and then kills requests mid-flight.

Configuration reaches the service as environment variables, through Environment=KEY=value lines or an EnvironmentFile=. Keep secrets out of the unit file itself: unit files are world-readable and systemctl show app prints the environment to any user. Put them in an EnvironmentFile readable only by root (systemd reads it before dropping privileges), or better, use LoadCredential=, which hands the service a file in a private directory. Chapter 28 replaces both with a secrets manager.

🐝
Use case: 2,000 workers and one Redis

Consider a fleet of 2,000 queue workers, each a systemd service with Restart=always and the default 100 ms delay, all depending on one Redis cluster. Redis has a 40-second failover. Every worker crashes on its first failed connection and restarts ten times a second; most hit the start limit and stay down, and the ones that do not hammer Redis with thousands of connection attempts the moment it comes back, slowing its recovery. A better setup: workers retry the connection inside the process with backoff and jitter instead of exiting, the unit uses RestartSec=5 with RestartSteps backoff as a last resort, and an alert fires on the restart counter (systemctl show -p NRestarts app) rather than only on "unit failed".

⚠️
Common mistakes
  • Running services with nohup … & or in screen: no restart, no boot start, no log management.
  • Forgetting daemon-reload after editing a unit, then wondering why the change did nothing.
  • start without enable: the service is gone after the next reboot.
  • Shell syntax in ExecStart (pipes, &&, ~). Use a script, or /bin/sh -c '…' knowingly.
  • Secrets in Environment=: visible to every user via systemctl show.
  • Apps that ignore SIGTERM: every restart takes 90 s and ends with SIGKILL.
  • Running as root because it was easier; add User= and the hardening options.

Interview drill

Explain it simply: A service keeps showing failed (Result: start-limit-hit). What does that mean and what do you do?

How a strong answer sounds
systemd restarted it too many times too quickly, more than StartLimitBurst starts within StartLimitIntervalSec (5 in 10 seconds by default), so it stopped trying. The restarts are a symptom; the cause is whatever makes it exit, which I find with journalctl -u app -n 50: usually bad configuration, a missing file or permission, a port already in use, or a dependency that is down. After fixing it, systemctl reset-failed app clears the counter and systemctl start app starts it. If it is a dependency that is down, I would make the app retry internally instead of exiting.

Deeper: Every deploy of a service causes a burst of 502 errors, though the new version starts fine. What would you look at?

How a strong answer sounds
The stop and start around the restart. Does the app handle SIGTERM by draining in-flight requests, or does it die immediately (or ignore SIGTERM and get SIGKILLed after the timeout)? Is there a gap between the old process exiting and the new one listening, during which the proxy gets connection refused? Fixes: handle SIGTERM gracefully; take the instance out of the load balancer before stopping it and add it back after its health check passes; or run two instances and restart them one at a time. That is a rolling deploy, which Kubernetes automates with readiness probes (Chapter 12).

🧠 Key takeaways

  • systemd orders, supervises, logs and stops services, configured by declarative unit files.
  • After editing a unit: daemon-reload; to run now and at boot: enable --now.
  • Restart=on-failure restarts on non-zero exits and crash signals; always also on clean exits.
  • More than 5 starts in 10 s ends in start-limit-hit; slow restarts can crash-loop forever, so alert on restart counts.
  • journalctl -u app with -f, --since and -p err is the first place to look.
  • Stop is SIGTERM then SIGKILL after a timeout; keep secrets out of unit files and run as an unprivileged user.

Check your understanding

A batch job's unit has Restart=on-failure. The job finishes its work and exits with code 0. What does systemd do?

on-failure restarts only on unclean exits: non-zero codes, crash signals, timeouts. Exit 0 is clean; only Restart=always would restart it.

You edited /etc/systemd/system/app.service and ran systemctl restart app, but the change had no effect. What was missing?

systemd caches unit definitions. daemon-reload makes it re-read them; status shows a warning when a unit file changed on disk.

With systemd's defaults, a service crashes 50 ms after every start. Roughly what happens?

With Restart= set to restart on failure and the default RestartSec of 100 ms, the sixth start within 10 seconds is refused and the unit enters failed (start-limit-hit).

What does systemctl stop app do by default?

Stop is graceful first: SIGTERM lets the app drain. Only after the timeout does systemd escalate to SIGKILL. Disabling is a separate command.

Which command shows the last hour of error-level log lines for app.service?

journalctl filters by unit (-u), time (--since) and priority (-p err includes err, crit, alert and emerg).
