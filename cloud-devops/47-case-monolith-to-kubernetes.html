Case Study: Moving a Monolith to Kubernetes

Most software that earns money is not a set of tidy services built last year. It is one large application, ten or fifteen years old, running on servers that someone configured by hand, deployed by a script that only two people fully trust. This case study follows a travel-booking company moving such an application onto Kubernetes. The interesting parts are not the Kubernetes parts. They are the assumptions the old application made about the machine it lived on, files on a disk, sessions in memory, a scheduled job on "the first server", and what happened as each assumption met a platform where machines are temporary. The move was made without a rewrite and without a cutover night, one route at a time. The simulator gives you the routes and the assumptions, and lets you move them in any order.

  • Separate "run it on Kubernetes" from "split it into services", and do the first without the second
  • List what a long-lived application assumes about its server, and how each assumption is removed
  • Use the strangler fig pattern to move traffic route by route, with a canary each time
  • Choose what to move first and what to leave until last
  • Describe how daily operations change for the team
  • Recognise the failures that are typical of this migration, and prevent them

The starting point

The company sells holiday bookings. Its website and its back office are one application of about 900,000 lines, started twelve years ago. It runs on eight virtual machines behind a load balancer, with one large PostgreSQL database.

ConcernHow it workedThe assumption inside it
DeploymentA script copies the code to each server over SSH on Thursday evening and restarts itServers have names, and are there next week
ConfigurationA file on each server, edited by hand, slightly different on eachSomebody remembers what is in it
SessionsKept in each server's memory; the load balancer sends a user back to the same serverA user's server does not go away
Uploaded filesBooking documents and photos written to a local directory, copied between servers every few minutesThe disk outlives the process
Scheduled workCron on "web-01": nightly reports, reminder emails, clean-upThere is exactly one first server
LogsFiles under /var/log, read by logging inYou can log in, and the machine is the one that had the problem
ScalingA ticket to add a server, two weeks before the summer peakPeaks are predictable a fortnight ahead

It worked, and had made the company's money for a decade. The reasons to change were practical. Deployments were weekly, slow and frightening. Two engineers understood the servers. Adding capacity took weeks. New features had to be built inside the one application or not at all.

The team set two goals and one explicit non-goal. The goals: every server replaceable at any moment, and deployment on any working day in minutes. The non-goal: splitting the application into microservices. Running on Kubernetes and breaking a monolith apart are separate decisions, and the first delivers most of the operational benefit. A monolith in a container is a perfectly good workload. Services would be extracted later, only where there was a reason.

Containerising

Step one was to put the application in a container without changing what it does. The Dockerfile was the easy afternoon (Chapter 8). The months went on the right-hand column of the table above, because a container on Kubernetes can be stopped and replaced at any time, on any node, and every assumption that a server is permanent becomes a bug.

  • Configuration moved from files on servers to environment variables, supplied by ConfigMaps and by a secret store (Chapters 13, 28). Finding out what the eight slightly different files had in common took longer than the code change.
  • Sessions moved from memory to a shared Redis, so any copy can serve any user.
  • Files moved from local disk to object storage. Every place that opened a path had to be found.
  • Logs went to standard output as structured lines (Chapter 22).
  • Health endpoints were added, with a handler for SIGTERM that finishes requests in flight, so that a rolling update drops nothing.
  • Scheduled work was taken out of the web process and its server, to become Kubernetes CronJobs.
# The monolith as one Deployment. Nothing about the application's design has changed.
apiVersion: apps/v1
kind: Deployment
metadata: { name: booking-web }
spec:
  replicas: 8
  template:
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: web
          image: registry.example.com/booking/web@sha256:5e1d…a4c7
          envFrom: [{ configMapRef: { name: booking-config } }, { secretRef: { name: booking-secrets } }]
          resources: { requests: { cpu: "2", memory: 3Gi }, limits: { memory: 3Gi } }
          startupProbe:   { httpGet: { path: /healthz, port: 8000 }, periodSeconds: 5, failureThreshold: 36 }   # it takes 2 minutes to boot
          readinessProbe: { httpGet: { path: /ready,   port: 8000 } }
          livenessProbe:  { httpGet: { path: /healthz, port: 8000 }, timeoutSeconds: 5 }

Each of those changes was made and released while the application was still on its virtual machines. Moving sessions to Redis is safe on VMs. So is reading configuration from the environment. By the time a container existed, the code had already stopped caring where it ran, and the first container was dull, which was the aim. The database did not move at all: it stayed where it was, reachable from both worlds. Stateful things go last.

Strangler fig routing

With a working container, the team did not switch over. They used the strangler fig pattern, named after a tree that grows around its host until it stands alone. A router is placed in front of both systems. At first it sends everything to the old one. Then routes are moved across, one at a time, each as a small experiment, until nothing is left on the old side.

# The canary for /login: the same host and path as the main Ingress, with a weight (ingress-nginx)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: login-on-kubernetes
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"       # raise in steps; set to 0 to go back
spec:
  ingressClassName: nginx
  rules:
    - host: www.example.com
      http:
        paths:
          - { path: /login, pathType: Prefix, backend: { service: { name: booking-web, port: { number: 80 } } } }

The order of routes was chosen by risk and by what each depended on.

The same router later served the other purpose of the pattern. When the team did want a separate service, for search, the new service simply took over /search from the monolith's container, by the same weighted route. A service that writes data is harder: it needs to own its tables, or go through an interface, or two code bases will change the same rows by different rules.

Operational changes

The technology was perhaps a third of the work. The rest was that people's daily habits no longer applied.

  • Nobody logs in to a server. Debugging goes through logs, metrics, traces and kubectl. Engineers who had always fixed things with SSH needed the observability stack to be good before they would trust it (Chapters 21 to 24).
  • Deployment became a pull request through a pipeline and GitOps (Chapter 41), several times a day. Thursday evenings were given back.
  • Capacity became a number in a file. The summer peak was handled by an autoscaler and a scheduled minimum (Chapter 39).
  • Costs moved. The first month on Kubernetes cost more than the VMs, because requests had been set generously. Rightsizing from measured usage brought it under (Chapter 31).
  • On-call changed. There were new alerts and new runbooks, and for a while two platforms to know. The two engineers who understood the servers became the people who taught everyone else the new system, deliberately.

The team ran the two platforms side by side for five months. That felt slow, and it is what made every step reversible.

What went wrong

Plenty, in small ways, which is the argument for doing it in small steps. These are the incidents from the team's own log. Almost every team that makes this move meets most of them.

None of these was a Kubernetes fault. Each was an old assumption about servers, found late. The cheapest defence was the canary: every one of these that met real users met a tenth of them, for a few minutes, with the old system one setting away.

    Things to try.

    • With nothing ticked, move /search straight to Kubernetes. The container cannot start, and 40% of the site's requests fail. Set it to a 10% canary instead: 4%. The mistake is the same and the price is a tenth.
    • Tick the configuration work and try the canary again. Failures fall to 0.08%: requests dropped while pods are replaced. It is small enough to miss on a dashboard. Tick health and shutdown as well, and /search can go to 100% with nothing failing.
    • Put /login on a canary without shared sessions. One per cent of all requests fail: every login that lands on the new side.
    • Move /images to 100% without object storage: 15% of the site's requests fail, since half of all image requests reach a pod that does not have the file.
    • Tick everything except "one owner", and put /checkout on a canary. No request fails, and data consistency is "at risk". This is the only problem on the panel that no error rate shows.
    • Move the nightly report without object storage. Every web route is green and the report is lost each night.
    • With nothing ticked, move everything at once: the cutover night. All requests fail.
    • Of the 5,184 combinations of preparation and routing, exactly 2 have everything on Kubernetes with no failing request, and only 1 of those is also sound: all five pieces of preparation done. The order you move the routes in does not change that total. It changes how much each discovery costs.

    Use case: GitHub puts its Rails monolith on Kubernetes

    For most of its first decade, the web application behind github.com, a very large Ruby on Rails monolith, ran as a set of processes on physical servers that the company managed with configuration tooling. It worked at enormous scale. Its weakness, as GitHub's engineers described in 2017, was that capacity was slow to change: adding room for a new service or a traffic peak meant the infrastructure team provisioning and configuring machines, and that team's time had become the limit on everyone else. They decided to move the application to Kubernetes, and how they did it is a model of this chapter's method. They did not break the monolith up. The same application was packaged in containers. They began with something that carried no customer risk: a "review lab" in which any engineer could deploy a branch to a temporary environment on Kubernetes. That gave the organisation months of practice with the platform and found problems in the tooling while the stakes were low. Then came production, in stages. A small slice of real traffic was routed to the containers, first requests from GitHub's own staff, then a growing share of the public's, alongside the existing servers behind the same load balancers. The team watched for differences and met real surprises along the way, including failures of the cluster's own nodes that had to be understood and fixed before the next step. Roughly a year after starting, all web and API requests were served from Kubernetes. Afterwards deploying a new service took engineers an afternoon where it had taken the infrastructure team weeks. The application's architecture had not changed. The way it was run had.

    ⚠️
    Common mistakes
    • Combining the move to Kubernetes with a rewrite into microservices. Two large risks, impossible to tell apart when something breaks.
    • A cutover night. Everything changes at once and the way back is a second cutover.
    • Containerising before removing server assumptions. Fix sessions, files, config and cron while still on the old servers.
    • Cron inside the web container. It runs once per replica.
    • Writing to the container's disk. It is deleted with the pod and not shared with the others.
    • Probes copied from an example, with no allowance for a slow start.
    • Memory limits from averages.
    • Forgetting the database's connection limit when replicas multiply.
    • Moving the database first. Stateless parts first; state last, and separately.
    • Starting with the most valuable route. Learn on search, not on checkout.
    • Switching the old system off as soon as traffic reaches zero. Wait for a month-end, a peak and the quarterly job nobody remembers.
    • Treating it as an infrastructure project. Most of the work is in the application's code and the team's habits.

    Interview drill

    Explain it simply: What is the strangler fig pattern?

    How a strong answer sounds
    It is a way to replace a system gradually, without a big-bang cutover. You put a router in front of the old system, so that all traffic already flows through something you control. At first every route goes to the old system. Then you build or move one piece on the new side and switch just that route across, usually as a canary with a small percentage first. If it works you raise the percentage; if not, you set it back, and the old system is still there. You repeat this route by route until the old system receives nothing and can be switched off. It is named after a fig that grows around a host tree and eventually replaces it. Its strengths are that every step is small, measurable and reversible, and that the business keeps running throughout. Its requirement is that shared state such as sessions and data is reachable from both sides during the transition.

    Deeper: You are asked to move a ten-year-old monolith from virtual machines to Kubernetes. What is your plan?

    How a strong answer sounds
    I would first agree what we are doing and what we are not. The goal is replaceable servers and fast, safe deployment. Splitting the monolith into services is a separate decision that I would postpone, because doing both at once doubles the risk and makes every failure ambiguous. Then I would audit the application for assumptions about its server: configuration in files, sessions in memory with sticky load balancing, files on local disk, cron on one host, logs in files, no health endpoint, no handling of SIGTERM. Each of those I would fix while the application is still on its VMs, as ordinary releases, since each is safe there and each makes the eventual container uneventful. In parallel I would build the platform side: cluster, pipeline, GitOps, observability and alerts, and get the team using it for something low-risk such as preview environments. For the move itself I would use a strangler fig. The existing load balancer or an ingress sends everything to the VMs, and I shift routes one at a time with a weighted canary: read-only pages first, then media, then routes that need a session, with checkout last, and background jobs as CronJobs with care that each runs exactly once. The database stays where it is throughout, reachable from both sides, with a connection pooler because the number of clients is about to become elastic. I would size probes and limits from measurement, including the real start-up time and peak memory. I would keep the VMs through at least one month-end and one peak before switching them off. Along the way I expect a list of small surprises, duplicate cron runs, a forgotten file path, probes that are too strict, and the canary is what keeps each of them small. And I would plan for the people: training, runbooks, and the engineers who know the old system leading the teaching of the new one.

    🧠 Key takeaways

    • Running a monolith on Kubernetes and splitting it into services are separate decisions. Do the first; postpone the second.
    • The work is removing the application's assumptions about a permanent server: config, sessions, files, cron, logs, shutdown.
    • Make those changes on the old platform first, so the first container is dull.
    • Move traffic with a strangler fig: one route at a time, each as a weighted canary.
    • Order by risk: read-only first, sessions next, money-making writes last, state last of all.
    • Expect duplicate cron runs, lost files, strict probes, tight memory limits and connection storms.
    • Two-thirds of the migration is how the team works. Keep the old system until a full business cycle has passed.

    Check your understanding

    After the move, a nightly email job that used to run once now sends every email eight times. What is the most likely cause?

    Cron on "the first server" becomes cron in every pod. Scheduled work belongs in a CronJob, outside the web process.

    Why were sessions moved to a shared store before any route was moved to Kubernetes?

    During the migration one user's requests go to both systems, and pods are replaced at any time. State kept in one process's memory would be lost.

    Which route is the best candidate to move first?

    A read-only, stateless route cannot corrupt anything and is easy to compare between old and new, so it is the cheapest place to learn.

    An application takes two minutes to start. Its pods are killed and restarted endlessly. What is the right fix?

    A startup probe holds off the liveness probe until the application has booted, without weakening liveness checking afterwards.

    The team decides to move to Kubernetes and split the monolith into twelve services in the same project. What is the main objection?

    Running the monolith in containers delivers most of the operational benefit. Extraction can follow later, where there is a reason for it.
