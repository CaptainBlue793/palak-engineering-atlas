Compute: VMs & Autoscaling Groups

The virtual machine is the oldest thing a cloud sells and it is still underneath most of the others: your Kubernetes nodes, your CI runners and your managed database all run on one. This chapter covers the four decisions you make about a fleet of them. Which machine to rent (instance families), what it starts from (machine images), how many are running at each moment (autoscaling groups, configured by a launch template), and what you pay for them (on-demand or spot). The simulator runs one day of traffic through a group so that you can see what each choice costs and how many requests it loses.

Instance families: which machine to rent

A cloud virtual machine is called an instance. Providers sell hundreds of shapes, grouped into families by the ratio of CPU to memory and by any special hardware. On AWS the name itself tells you what you are getting:

  m   7   g   .   2xlarge
  │   │   │       └── size: doubles each step (large = 2 vCPU, xlarge = 4, 2xlarge = 8, ...)
  │   │   └────────── extras: g = ARM (Graviton) CPU, a = AMD, i = Intel, d = local NVMe disk, n = faster network
  │   └────────────── generation: higher is newer, and usually cheaper for the same work
  └────────────────── family: what the machine is shaped for
FamilyShapeMemory per vCPUTypical use
T (burstable)A share of a CPU, with credits to burst2 to 4 GBSmall or spiky services, development machines, bastions

Azure and Google Cloud use other letters for the same idea (Azure's D, F and E series, Google's general-purpose, compute-optimised and memory-optimised machine types). Three details are worth knowing on any provider.

  • A vCPU is not always a core. On most x86 instances one vCPU is one hyperthread, so two vCPUs share one physical core. On ARM instances such as AWS's Graviton a vCPU is a whole core, which is one reason they often do more work per dollar.
  • Burstable instances run on credits. A t3.medium may use 20% of each of its two vCPUs all the time. While it uses less it saves CPU credits, and it spends them to run at full speed for a while. When the credits are gone it is either throttled down to the 20% or billed extra, depending on its mode. A service that sits at 60% CPU all day should not be on a T instance.
  • Size for the resource that runs out first. Look at a week of CPU and memory use and pick the family whose ratio matches. A Java service using 30 GB of memory and one core does not belong on a compute-optimised machine.

Machine images: what the instance starts from

An instance boots from a machine image (an AMI on AWS): a snapshot of a root disk plus some metadata, stored per region. The provider publishes plain operating system images, and you can make your own. The question is how your application gets onto the machine, and there are two answers.

Install at bootBaked image
HowStart from a plain OS image; a startup script (user data, run by cloud-init) installs packages and fetches the applicationA pipeline starts a temporary instance, installs everything, snapshots it as a new image; instances boot from that

Baking wins for anything that scales automatically, because the time between "we need more machines" and "the machines are serving" is time during which requests fail. The simulator below puts a number on that. Baking also gives you immutable infrastructure: nobody logs in to change a running server; to change anything you build a new image and replace the instances. In practice most teams bake the slow parts (the OS updates, the runtime, the agents) and leave a few lines of user data for what differs per environment.

#!/usr/bin/env bash
# boot.sh: user data for a baked image. Nothing is downloaded here.
set -euo pipefail
echo "ENVIRONMENT=production" > /etc/checkout/env      # the only thing that differs per environment
systemctl enable --now checkout.service                # installed and tested when the image was built

Autoscaling groups and launch templates

You rarely create instances one at a time. You describe one in a launch template and hand it to an autoscaling group (ASG on AWS; a virtual machine scale set on Azure; a managed instance group on Google Cloud), which keeps the right number of copies running.

A launch template is the full recipe for an instance: the image, the instance type, the security groups, the role the instance runs as, the user data, the disk and the tags. Templates are versioned, so "roll out the new image" means "publish template version 8 and replace the instances made from version 7".

The group has three numbers, minimum, maximum and desired capacity, and it does three jobs:

  • It keeps the count. If desired is 6 and one instance dies, it launches a replacement. This self-healing is useful even for a fleet that never changes size.
  • It spreads them. Given subnets in three zones, it balances instances across them and rebalances after a zone recovers.
  • It changes the count. A scaling policy moves desired capacity between the minimum and the maximum. The usual policy is target tracking: "keep average CPU at 50%". There are also scheduled policies (more capacity at 08:00 on weekdays) and predictive ones that learn the daily pattern.
resource "aws_launch_template" "web" {
  name_prefix   = "web-"
  image_id      = var.ami_id                    # the baked image
  instance_type = "m7g.large"
  user_data     = filebase64("boot.sh")

  vpc_security_group_ids = [aws_security_group.web.id]
  iam_instance_profile { name = aws_iam_instance_profile.web.name }
  metadata_options     { http_tokens = "required" }   # see Chapter 6
}

resource "aws_autoscaling_group" "web" {
  min_size            = 2
  max_size            = 30
  vpc_zone_identifier = var.private_subnet_ids      # one subnet in each of three zones
  target_group_arns   = [aws_lb_target_group.web.arn]

  health_check_type         = "ELB"               # replace instances the load balancer calls unhealthy
  health_check_grace_period = 120                 # seconds to boot before health checks count
  capacity_rebalance        = true                # start a replacement when a spot instance is at risk

  mixed_instances_policy {
    instances_distribution {
      on_demand_base_capacity                  = 2     # the first two are always on demand
      on_demand_percentage_above_base_capacity = 0     # everything above that is spot
      spot_allocation_strategy                 = "price-capacity-optimized"
    }
    launch_template {
      launch_template_specification {
        launch_template_id = aws_launch_template.web.id
        version            = "$Latest"
      }
      override { instance_type = "m7g.large" }       # several interchangeable types:
      override { instance_type = "m6g.large" }       # more spot pools to draw from
      override { instance_type = "m7gd.large" }
    }
  }
}

resource "aws_autoscaling_policy" "cpu" {
  name                   = "cpu-50"
  autoscaling_group_name = aws_autoscaling_group.web.name
  policy_type            = "TargetTrackingScaling"
  target_tracking_configuration {
    predefined_metric_specification { predefined_metric_type = "ASGAverageCPUUtilization" }
    target_value = 50
  }
}

How does "keep CPU at 50%" become a number of instances? The group measures the average over its in-service instances and scales in proportion: with 6 instances at 75% it wants 6 × 75 ÷ 50 = 9. Two things follow from that arithmetic. A lower target keeps more spare capacity running, which costs money and buys time. And when the instances are saturated the measurement stops at 100%, so the group cannot see how far over it is: at a 70% target it can grow by at most 100 ÷ 70, about 1.4 times, in one step.

Spot and preemptible capacity

Providers have spare hardware at most hours, and they sell it at a large discount on one condition: they can take it back. AWS calls this Spot, Azure calls it Spot Virtual Machines, and Google Cloud calls it Spot VMs (formerly preemptible). The discount is often 60 to 90% and varies by instance type, zone and hour.

On demandSpot
PriceList priceOften 60 to 90% lower, and it moves
Can the provider take it back?NoYes: two minutes' warning on AWS, about 30 seconds on Azure and Google Cloud
Can you always get one?Nearly alwaysNo: a type may be unavailable in a zone for hours
Good forThe base of a fleet; anything with state on the machineStateless servers behind a load balancer, batch jobs, CI runners, Kubernetes worker nodes
Bad forA single database primary; a job that cannot be restarted

Three rules make spot safe. Keep a base of on-demand instances that can carry a reduced service alone. Diversify: allow several instance types in several zones, because spare capacity is reclaimed pool by pool and not all pools are reclaimed together. And handle the warning: stop taking new work and finish what is open. The warning arrives through the instance metadata service.

#!/usr/bin/env bash
# spot-watch.sh: runs as a systemd service on every spot instance
set -euo pipefail
IMDS="http://169.254.169.254/latest"

while sleep 5; do
  token="$(curl -fsS -X PUT "$IMDS/api/token" -H 'X-aws-ec2-metadata-token-ttl-seconds: 60')"
  # 404 (curl exits non-zero) while nothing is planned; a JSON body once the two-minute warning is given
  if curl -fsS -H "X-aws-ec2-metadata-token: $token" "$IMDS/meta-data/spot/instance-action"; then
    systemctl stop checkout.service      # its ExecStop fails the health check, waits for open requests, then exits
    break
  fi
done

The model works in one-minute steps. The tracking policy wants instances × average CPU ÷ target, with CPU read as 100% at most. It adds instances after the reading has been too high for 3 minutes in a row and removes them after it has been too low for 15, which is how AWS target tracking behaves by default. The group stays between 2 and 30 instances. On demand costs $0.0416 an hour; spot is priced 70% lower here. With spot, 40% of the spot instances are reclaimed at 13:30 and again at 20:15, with two minutes' warning, and the group starts replacements at once. Requests above capacity are counted as refused.

Things to try. Switch the view to "19:45 to 21:15" to see the spike closely.

  • The starting point: tracking 70% CPU, five minutes to boot, all on demand. The day costs $5.70 against $10.98 for a fixed fleet, because the group runs 3 instances at night and 14 at the worst. The price is 13 minutes short of capacity, from 20:02 to 20:14, and 206,301 refused requests. Look at the green line in the close view: capacity rises in two steps. The first batch of instances was too small, because saturated instances report 100% CPU however overloaded they are, so the group had to wait for the batch to arrive, measure again and order a second one.
  • Bake the image (one minute to serve). The shortage falls from 13 minutes to 5 and the refused requests to 44,265, and the day costs the same, $5.73. Nothing else in this panel improves the result for free.
  • Or keep the slow boot and track 50%. Also 5 minutes short (63,095 refused), but the day now costs $7.77, about a third more, because the extra headroom runs all day to be useful for half an hour.
  • Do both. One minute short and 1,007 requests refused, for $7.78: 71% of the fixed fleet's cost, with nearly its result.
  • Buy spot. With a baked image and the 50% target, the day costs $3.74, a third of the fixed fleet. The provider takes 4 instances at 13:30 and 8 at 20:15, in the middle of the spike, and no extra request is lost: the replacements serve after one minute and the warning is two.
  • Spot with a slow boot. Set the boot time back to five minutes and the policy to 70%: the reclaim at 20:15 adds three more short minutes. Even "Fixed, for the peak" loses 50,122 requests on spot with a slow boot, because 4 of its 11 instances vanish at the peak and their replacements need five minutes. Spot is safe in proportion to how quickly you can replace it.

Use case: Netflix bakes the image and predicts the load

Netflix runs on AWS and has written publicly about two choices that match this chapter. First, every deployment is a baked image. Their open-source tool Aminator, released in 2013, takes a base image and an application package and produces an AMI, and a release means new autoscaling groups of instances booted from it. They explained the reasoning in terms of launch time and reliability: an instance that has to download and install its software at boot is slow to help and can fail to start when a dependency is unavailable, which tends to be when you most need new instances. Second, they found that reacting to load was sometimes too slow even so, because their traffic rises steeply at predictable hours and a new instance still needed minutes before it could serve. In 2013 they described Scryer, a system that forecasts demand from past patterns and sets the group sizes ahead of time, with the ordinary reactive policy kept underneath as a safety net. The cloud providers now offer the same idea as predictive scaling.

⚠️
Common mistakes
  • A target that leaves no room. Tracking 80 or 90% CPU looks efficient and means every spike arrives before the capacity does.
  • Ignoring boot time. A scaling policy cannot react faster than an instance can start. Measure the time from launch to first request and shorten it.
  • Health checks that only test the process. If the group checks that the machine is on, but the application is hung, the broken instance stays in service. Use the load balancer's health check.
  • Too short a grace period. If health checks count before the service is up, the group kills every new instance and launches another, for ever.
  • State on the instance. Sessions, uploads or the only copy of the logs on a disk that is deleted with the instance.
  • All spot, one type, one zone. One reclaim takes the whole fleet. Keep an on-demand base and allow several types.
  • A burstable instance for steady load. It runs out of credits and is throttled or surcharged.
  • Changing servers by hand. The next instance the group launches will not have your change.

Interview drill

Explain it simply: What does an autoscaling group do?

How a strong answer sounds
It keeps a set number of identical instances running from a launch template. It has a minimum, a maximum and a desired capacity. It replaces any instance that fails a health check, so the fleet heals itself; it spreads the instances over the zones I give it; and a scaling policy moves the desired number up and down between the limits, most often by tracking a target such as 50% average CPU. It also registers the instances with a load balancer and drains them before terminating. The consequence for design is that instances are disposable: they can be replaced at any moment, so nothing important may live only on one of them.

Deeper: A service scales on 70% CPU. A new instance takes six minutes before it serves. Every sudden rise in traffic produces several minutes of errors. What do you change?

How a strong answer sounds
The errors last for the detection delay plus the six minutes, and possibly for two rounds of that, because saturated instances read 100% CPU and a 70% target can then only ask for about 1.4 times the current fleet at a time. I would work on three things. Make the instance faster to start: bake the image so that boot installs nothing, check what the six minutes are actually spent on, and consider a warm pool of stopped, already-initialised instances. Keep more headroom: lower the target to 50% or so, and raise the minimum, accepting the cost. And react earlier: scale on requests per instance, which keeps rising past the point where CPU has hit its ceiling, use one-minute metrics, and add scheduled or predictive scaling for the rises that happen at known times. For the cases that still get through, the service should shed load cleanly, rejecting the excess quickly, so that the requests it does accept stay fast. I would then verify with a load test that reproduces the rise.

🧠 Key takeaways

  • An instance type name gives family, generation, extras and size; pick the family whose CPU-to-memory ratio matches the workload.
  • Burstable instances are for low average CPU; they are throttled or surcharged when the credits run out.
  • A baked image boots in about a minute and depends on nothing; installing at boot is slower and can fail when you need it.
  • An autoscaling group keeps the count, heals, spreads across zones and scales; a launch template is the versioned recipe.
  • Spare capacity and boot time decide whether a spike is survived: a lower target buys time, a faster boot needs less of it.
  • Spot is cheap capacity that can be taken back: keep an on-demand base, diversify, and act on the warning.

Check your understanding

An autoscaling group tracks 50% average CPU. It has 8 instances in service and their average CPU is 75%. How many instances does the policy want?

Target tracking scales in proportion: 8 × 75 ÷ 50 = 12. The same load spread over 12 instances gives 50% each.

Why does a baked image make autoscaling work better than installing the application at boot?

The time from launch to serving is time during which the fleet is short. A baked image only has to boot and start the service, and nothing external can make that fail.

A service holds steady at about 60% CPU all day on t3 burstable instances. What should you expect?

Burstable instances have a baseline (20% per vCPU on a t3.medium). Steady use above it drains the credits. A general-purpose M instance fits this workload.

Which workload is the worst fit for spot instances?

Spot capacity can be withdrawn at short notice. The other three can lose a machine and carry on or retry; a single database primary cannot.

A new instance needs 3 minutes before its service answers. The group's health-check grace period is 30 seconds. What happens?

After the grace period a failed health check counts. An instance that is still booting fails it, is terminated and replaced, and the replacement meets the same fate.
