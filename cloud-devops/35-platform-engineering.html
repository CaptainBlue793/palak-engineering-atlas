Platform Engineering & Developer Platforms

This course has now asked one imaginary engineer to learn containers, Kubernetes, Terraform, CI pipelines, GitOps, metrics, tracing, alerting, secrets, supply-chain security and cost. No product engineer can hold all of that and also build a product. Platform engineering is the industry's answer: a small team turns that knowledge into a product, an internal platform, that other engineers use through self-service. The good version makes the right way the easy way. The bad version is the old operations team with a new name and a portal in front of the ticket queue. This chapter covers why platform teams exist, what a golden path contains, how Backstage and templates deliver one, and how to tell whether a platform is working. Why platform teams

"You build it, you run it" was a good correction to the old wall between developers and operations (Chapter 1). Taken literally at scale, it produces a different problem. Every product team has to choose and maintain its own pipeline, deployment method, dashboards and security controls. The cognitive load, the amount a person must keep in their head to do the job, grows until infrastructure crowds out the product. Fifty teams solve the same problems fifty slightly different ways, and nobody can move between teams, or fix a company-wide flaw, without learning each one.

The older alternative, a central team that does infrastructure work on request, fails in the other direction. Every new database or environment is a ticket, tickets wait in a queue, and the queue grows with the number of teams while the operations team does not.

Tickets to a central teamEvery team for itselfSelf-service platform
A new service takesDays to weeks of waitingDays to weeks of buildingMinutes

A platform team builds the third column. The book Team Topologies gave the idea its usual wording: a platform is a product whose customers are the company's own engineers, and its purpose is to reduce their cognitive load. Two consequences follow from the word "product". The platform team has to find out what its users actually struggle with, as any product team would. And the users must be free to say no. An internal developer platform is the result: the set of self-service tools, templates and automation that takes a team from an idea to a running, observable, secure service.

Golden paths

A golden path (Spotify's term; Netflix says "paved road") is the supported, opinionated way to do one common thing, such as creating a backend service, adding a database or shipping a scheduled job. It has four properties.

  • Opinionated. It makes the decisions: this language runtime, this pipeline, this deployment method. Fewer choices is the feature.
  • Complete. It ends at a service running in production with dashboards and alerts, not at a repository with a README.
  • Self-service. No ticket, no meeting, no waiting for another team.
  • Optional. A team may leave the path. They then own what the path would have given them. The platform wins by being better than the alternative, not by being compulsory.

The last property is what keeps a platform honest. If teams choose the path freely, adoption tells you whether it is good. If they are forced onto it, you learn nothing, and they route around it anyway.

Safety on the path comes from guardrails, not gates. A gate is a person who must approve: a security review before each release. A guardrail is a property built into the path that makes the unsafe thing hard to do by accident: the template's container already runs as a non-root user, its pipeline already signs the image, its database module already has backups switched on. Guardrails scale and gates do not. What cannot be built into a template is enforced automatically as policy, which is the subject of Chapter 36.

Backstage and templates

A platform needs a front door. The best known is Backstage, built at Spotify, made open source in 2020 and now a Cloud Native Computing Foundation project. It is a developer portal with three core parts.

  • The software catalog: one list of every service, library, data store and API in the company, each with an owner. It is fed by a small file that lives in each repository.
  • Software templates (the scaffolder): forms that create a new, complete project from a golden path.
  • TechDocs: documentation written as Markdown beside the code and published in the portal.
# catalog-info.yaml, in the root of the service's repository
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: orders-api
  description: Accepts and tracks customer orders
  annotations:
    github.com/project-slug: example/orders-api
    pagerduty.com/service-id: P4X2ZQ1                 # who is on call for it, shown on the page
spec:
  type: service
  lifecycle: production
  owner: team-orders                                # every component has exactly one owning team
  system: checkout
  dependsOn: [resource:orders-db, component:payments-api]
  providesApis: [orders-api]

That file answers the questions that waste hours in a large company: who owns this, what does it depend on, where is its dashboard, who is on call. A template is defined in the same declarative style: a form, then a list of steps.

apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata: { name: backend-service, title: New backend service }
spec:
  owner: team-platform
  type: service
  parameters:
    - title: About the service
      required: [name, owner, language]
      properties:
        name:     { type: string, pattern: '^[a-z][a-z0-9-]{2,30}$' }
        owner:    { type: string, 'ui:field': OwnerPicker }
        language: { type: string, enum: [go, python, node] }
        database: { type: string, enum: [none, postgres], default: none }
        public:   { type: boolean, default: false }
  steps:
    - id: fetch                                       # copy the skeleton, filling in the answers
      action: fetch:template
      input: { url: './skeleton/${{ parameters.language }}', values: { name: '${{ parameters.name }}', owner: '${{ parameters.owner }}' } }
    - id: publish                                     # create the repository, with branch protection
      action: publish:github
      input: { repoUrl: 'github.com?owner=example&repo=${{ parameters.name }}', protectDefaultBranch: true }
    - id: register                                    # add it to the catalog
      action: catalog:register
      input: { repoContentsUrl: '${{ steps.publish.output.repoContentsUrl }}', catalogInfoPath: /catalog-info.yaml }

That caption is the main caution about portals. The portal is not the platform. A catalogue and a set of forms are only as good as the automation behind them, and the commonest failed platform project is a carefully installed portal with nothing useful to click. Many good platforms start with no portal at all: a repository template, a command-line tool and well-kept shared modules. Commercial portals such as Port and Cortex, and infrastructure APIs such as Crossplane, fill the same roles as Backstage in other shapes.

Measuring the platform

Because a platform is a product, it is judged the way products are: by whether its users choose it and whether it makes them faster.

MeasureWhat it tells youWatch out for
Voluntary adoption: share of services on the golden pathWhether the path is better than the alternativesMeaningless if the path is mandatory
Time to first deploy for a new service, and time for a new engineer's first changes to reach productionHow much the platform removes from getting startedMeasure it by watching a real newcomer, not by estimate
Delivery metrics (the DORA four from Chapter 1) for teams on the path against teams off itWhether users of the platform actually ship faster and more safelyStronger teams may adopt first; compare the same team before and after
Developer satisfaction: a short regular survey and interviewsFriction that numbers missLow response rates; ask about specific tasks
Tickets and questions to the platform teamWhere self-service is missing or the documentation failsA falling count can also mean people gave up asking
The platform's own SLOs: pipeline success and duration, deploy availabilityWhether the platform is reliable enough to depend onA platform outage stops every team at once

The measures to avoid are the ones that count the platform team's output and not its users' outcomes: features shipped, templates published, portal page views. A platform with forty templates and 10% adoption is failing, however busy the team was.

      🎧
      
    
      Use case: Spotify and rumour-driven development
      By the late 2010s Spotify had hundreds of small autonomous teams and well over a thousand services. Autonomy had been the company's deliberate choice, and it had a cost that grew with size. There were many ways to build a service and several tools for every job, and the practical way to find out how anything was done was to ask around. Engineers inside the company called this "rumour-driven development". New joiners took a long time to become productive, and experienced engineers spent their days answering the same questions. Spotify responded with two things that it later described publicly. The first was the golden path: for each common kind of work, backend service, data pipeline, web feature, one supported and documented way of doing it, with a tutorial that took an engineer from nothing to production. The second was Backstage, a single portal holding the catalogue of every component and its owner, the templates for the golden paths, and the documentation. Spotify reported that the time for a new engineer to merge their tenth pull request, its measure of onboarding, fell by more than half. It released Backstage as open source in 2020, and it has since been adopted by thousands of companies. The detail worth keeping is that the paths were not enforced. Spotify kept its teams' freedom to choose and competed for their choice by making the supported way the least effort. Adoption was the evidence that it had worked.
      
  
      

  
      ⚠️
      Common mistakes
      
    
        
      
      • Renaming the operations team "platform" and keeping the ticket queue.
        • 
      
      • Installing a portal first. A catalogue and forms with no automation behind them change nothing.
        • 
      
      • Building for a year before the first user. Start with one path and one customer team.
        • 
      
      • Making the path compulsory to hit an adoption target. You lose the signal that tells you whether it is good.
        • 
      
      • Hiding everything. An abstraction that nobody can see through fails the first time something breaks underneath it. Leave the generated files readable and the escape hatches open.
        • 
      
      • Templates that only create. Ask how the three hundred services already generated will receive next year's pipeline fix.
        • 
      
      • No owner for the path's upkeep. A stale golden path is worse than none, because people trust it.
        • 
      
      • Gates where guardrails would do. A manual security approval on every release, where a signed image and a policy check would give the same assurance.
        • 
      
      • Measuring the platform team's output and not its users' results.
        • 
      
      • Forgetting that the platform is production. If the pipeline is down, nobody can ship a fix for anything.
        • 
    
      

  
      🎤
      Interview drill
      
    
      Explain it simply: What is a golden path?
      
    
      How a strong answer sounds
      A golden path is the supported, opinionated, self-service way to do a common piece of engineering work, such as creating a new backend service. It makes the decisions for you: the pipeline, the deployment method, the dashboards, the security settings. It takes you all the way to a service running in production. It is optional: a team can do something different, and then they own everything the path would have provided. The point is to cut the amount each product engineer has to know and decide, and to make the secure, observable, cost-tagged way also the easiest way. Safety comes from guardrails built into the path, not from approvals. And because nobody is forced to use it, how many teams choose it tells you whether it is good.
      
    
      Deeper: You are asked to start a platform team in a company of 150 engineers. What do you do in the first six months?
      
    
      How a strong answer sounds
      I would start by finding the problem, because the usual failure is to build what the platform team finds interesting. In the first few weeks I would interview a dozen teams, look at what is asked of the existing infrastructure people, and watch a new service being created and a new engineer being onboarded, timing each step. That normally shows one or two tasks that everyone does, slowly and differently, typically creating a service and getting a database. Then I would pick one of those and one team that wants help, and pave that path end to end with them: repository, pipeline, deployment through GitOps, dashboards, alerts and documentation, built from shared modules so it can be changed centrally later. No portal yet; a template repository and a small CLI are enough to prove it. The measure is the time from request to a service in production, before and after. In months three and four I would take it to a second and third team, fix what they trip over, and write the documentation for someone who has never met us. I would publish the adoption numbers and the time saved, and keep the path optional so that the numbers mean something. In months five and six, with real users, I would choose the next path by the same method, set SLOs for the platform's own pipeline, and work out how existing services are upgraded when the template changes, since that determines whether the platform stays one platform. Only then would I consider a portal, when there is enough behind it to be worth a front door. Throughout I would run it as a product: a roadmap users can see, a support channel, and regular conversations with the teams who chose not to adopt it, because their reasons are the most useful input I will get.
      
  
      

  
      
    
      🧠 Key takeaways
      
    
        
      
      • Platform engineering reduces the cognitive load on product teams by turning infrastructure knowledge into a self-service product.
        • 
      
      • Ticket queues do not scale with teams, and every-team-for-itself does not scale with complexity.
        • 
      
      • A golden path is opinionated, complete, self-service and optional.
        • 
      
      • Guardrails built into the path replace manual gates.
        • 
      
      • Backstage offers a catalogue with owners, templates and documentation. The portal is the front door; the automation behind it is the platform.
        • 
      
      • Leaving the path is allowed, and means owning what it provided.
        • 
      
      • Measure voluntary adoption, time to first deploy, delivery metrics and satisfaction, never the platform team's output.
