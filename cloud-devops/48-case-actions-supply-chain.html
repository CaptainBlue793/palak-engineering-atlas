Case Study: The 2025 GitHub Actions Supply-Chain Attack

A CI pipeline is the most trusted program a company runs. It holds the keys to the registry, the cloud and the package index, and it executes, with those keys in memory, whatever code its workflow file names. In March 2025 an attacker changed what one of those names meant. A widely used GitHub Action called tj-actions/changed-files, referenced by some 23,000 repositories, had its version tags quietly moved to a malicious commit. For about a day, every pipeline that asked for "version 45" of the action ran the attacker's code, which read the pipeline's secrets out of memory and printed them into the build log. This last case study follows the public analyses of that attack. It is a fitting place to end the course, because the defences are things you have already met: content-addressed references, short-lived credentials and least privilege. The simulator shows what one workflow file would have given away.

  • Describe how moving a Git tag compromised thousands of pipelines without changing their code
  • Explain how the payload extracted secrets, and why log masking did not stop it
  • Work out the blast radius of a compromised job from what it held and who could read its log
  • Pin actions to a full commit hash, and keep the pins current safely
  • Reduce what a pipeline can lose: token permissions, short-lived identity, separated jobs
  • Respond correctly when a dependency of your pipeline is found to be compromised

The compromise

A GitHub Action is a reusable step that a workflow runs by name. tj-actions/changed-files does a modest job: it reports which files a pull request has changed, so that later steps can, for example, lint only those. Thousands of projects used it, and nearly all referred to it the way its documentation showed, by a version tag.

- uses: tj-actions/changed-files@v45          # "whatever the tag v45 points to when this job starts"

A tag in Git is a label on a commit, and whoever can write to the repository can move it. On 14 March 2025 an attacker who had obtained a credential for the project's automation account did so. They added a commit containing malicious code and then pointed the project's existing version tags at it, old versions included. No workflow file in any consuming repository changed. No pull request appeared anywhere. The next time each pipeline ran, it fetched "v45" as always and received different code.

It was noticed within a day, and by observation, not by review. A security company's monitoring agent on a build runner flagged an action making a network request it had never made before, to fetch a script from an unfamiliar address. GitHub took the action down, the maintainers regained control and restored the tags, and the incident was catalogued as CVE-2025-30066. By then the malicious version had been available for roughly a day, across every repository whose pipeline ran in that time.

How secrets leaked

The payload was short and its method is instructive. A workflow's secrets are sent to the runner, the machine executing the job, and are held in the memory of the runner's own process so that steps can use them. The malicious step ran a script that scanned that process's memory, picked out everything that looked like a secret, and wrote the result to standard output. Whatever a step writes there becomes part of the job's log.

# What an affected job's log contained, in the middle of an ordinary-looking step
Run tj-actions/changed-files@v45
  ...
SW1WaFRYQkpSV3hHVkd0U1ZGWkdUa1ZTVmtaR1ZWWlZPVkJT ... (several hundred characters)
  ...

# Decoding it twice gives the job's secrets back
$ echo "SW1WaFRYQkpSV3hHVkd0U1Z..." | base64 -d | base64 -d
"AWS_ACCESS_KEY_ID":{"value":"AKIA...","isSecret":true}
"NPM_TOKEN":{"value":"npm_...","isSecret":true}
"GITHUB_TOKEN":{"value":"ghs_...","isSecret":true}

Two details explain why this worked. GitHub masks secrets in logs: it knows each secret's value and replaces it with asterisks if it appears. Masking is a string match, so encoding the output, here in base64 twice, walks straight past it. And the payload did not need to send anything anywhere. On a public repository, build logs are public. Anyone who knew what to look for could read the secrets of thousands of projects with a web browser.

The general point is uncomfortable. A step in a job can read everything that job can: its secrets, its token, its source code, its network. An action is not a sandboxed plugin. It is someone else's program, running inside your pipeline with your pipeline's privileges.

Blast radius

About 23,000 repositories referenced the action. The number actually harmed was far smaller, and the reasons for the difference are the lesson. For any one repository the damage depended on four questions.

QuestionBetter answerWorse answer
How was the action referenced?By full commit hash: the malicious code was never fetchedBy tag: it ran on the next job
Did a job run during the window?No: nothing happened, by luckYes: active projects with frequent builds were hit most
What did the job hold?Only the built-in token, which expires when the job endsLong-lived keys for a cloud account, a package index or a registry
Who could read the log?Members of a private repositoryThe whole internet
What could the job's token do?Read the repositoryPush commits, alter releases, change workflows

Researchers who examined public logs afterwards found that the repositories which had printed real, lasting secrets numbered in the low hundreds. Most affected jobs had exposed only the short-lived built-in token. That is what good defaults buy. It was still a serious incident for those hundreds, among them widely used open-source projects whose publishing credentials could be used to poison their own next release, which is precisely how the attack had travelled to this action in the first place.

If your pipeline ran the compromised version, the response follows Chapter 28: assume every secret available to that job is known, revoke and replace each one, then read the audit logs of the systems those secrets opened for the period of exposure. Deleting the log is housekeeping. It does not un-leak anything.

Pinning by SHA

The fix for the central weakness is one line per action. Refer to the action by the full commit hash, which names exact content and cannot be moved, with the version in a comment for the reader.

# Before: a label that the action's owner, or a thief, can move
- uses: tj-actions/changed-files@v45

# After: exact content. The comment is for people and for the update robot
- uses: tj-actions/changed-files@<the full 40-character commit hash>   # v45.0.7

# Finding the hash a tag points to today
$ gh api repos/actions/checkout/git/ref/tags/v4.2.2 --jq .object.sha
11bd71901bbe5b1630ceea73d27597364c9af683

Workflows pinned this way were untouched in March 2025, whatever else was true of them. Pinning needs three companions to be workable.

  • An update robot. Dependabot or Renovate opens a pull request when a new version is released, changing the hash and the comment together. The update becomes a reviewable change that waits for you, and a waiting period of a few days means a poisoned release is usually reported before you take it.
  • Enforcement. An organisation setting can require every action to be pinned to a full hash, so the rule does not depend on memory (Chapter 36).
  • Fewer actions. Each third-party action is a dependency with access to your secrets. Listing changed files is one git diff command. Prefer a few lines of script, or actions published by the platform itself, to a convenience from a stranger.

Pinning has limits worth knowing. It fixes the action's own code, and not what that action downloads when it runs, or other actions it calls by tag internally. And a hash is only as trustworthy as the moment you chose it: pin a version you have reason to believe is good, and read the diff when the robot proposes the next.

Least-privilege tokens

Pinning lowers the chance that hostile code runs in your pipeline. Least privilege lowers what it finds when it does, which matters because pinning will not stop every route in.

permissions: {}                                  # the built-in token starts with nothing

jobs:
  test:                                          # runs third-party actions and untrusted code: holds no secrets
    runs-on: ubuntu-24.04
    permissions: { contents: read }
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683   # v4.2.2
      - run: git diff --name-only origin/main...HEAD > changed.txt       # no action needed for this
      - run: make test

  publish:                                       # holds the power to release: runs almost nothing
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    environment: production                      # secrets scoped to this environment; can require approval
    permissions: { contents: read, id-token: write }
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
      - uses: aws-actions/configure-aws-credentials@<full commit hash>
        with: { role-to-assume: arn:aws:iam::111122223333:role/release, aws-region: eu-west-2 }   # one hour, this repo and branch only
      - run: ./scripts/release.sh

The fifth step refers to a class of weakness that fed this incident's earlier stages: workflows triggered by a pull request from a stranger's fork, but run with the privileges of the main repository. Such workflows must not check out or execute the stranger's code.

      •

    🎯
    
    
    Use case: Ultralytics, December 2024, and a pipeline that published the attacker's build
    Three months before the tj-actions incident, a different weakness in GitHub Actions was used against Ultralytics, the maintainers of a very widely installed computer-vision library. In early December 2024, two new versions of the library appeared on the Python package index, published through the project's own release process, and they contained a cryptocurrency miner. Nothing had been stolen in the usual sense at that point. The attacker had opened pull requests from a fork with a carefully chosen branch name. One of the project's workflows ran automatically for pull requests with the privileges of the main repository, and it inserted the branch name into a shell command without quoting. The branch name contained shell code, so the workflow executed it. From there the attacker tampered with the build environment so that the next legitimate release build would include their payload, and the project's own trusted pipeline packaged, signed off and published it. Users who installed the new version got the miner. After the first malicious versions were removed, two more appeared, this time uploaded with a publishing token that had evidently been taken along the way. The parallels with this chapter are close, and the differences are useful. In both cases the pipeline was the target and its privileges were the prize. Here the way in was not a moved tag but untrusted input, a branch name, reaching a privileged workflow. Pinning actions would not have helped. The defences were the other half of this chapter: workflows triggered by forks get no secrets and no write access, untrusted text is never pasted into a command, and the job that publishes is isolated from anything an outsider can influence.
    
  
    

  
    ⚠️
    Common mistakes
    
    
      
      
    • Referencing actions by tag or branch, because the README does.
      • 
      
    • Pinning to a short hash, or pinning once and never reviewing updates.
      • 
      
    • Leaving the built-in token at its broadest setting. Declare permissions in every workflow.
      • 
      
    • Long-lived cloud keys and publishing tokens stored as repository secrets, where identity tokens would do.
      • 
      
    • One job that tests, builds and publishes, so every third-party step runs beside the release credentials.
      • 
      
    • Trusting log masking. Any encoding defeats it.
      • 
      
    • Forgetting that public repositories have public logs.
      • 
      
    • Privileged workflows triggered by pull requests from forks that check out or run the fork's code.
      • 
      
    • Pasting untrusted text (branch names, titles, comments) into a shell command.
      • 
      
    • An action for everything. Each one is a stranger's program with your secrets.
      • 
      
    • After exposure, deleting the logs and moving on. Rotate every secret the job could see, then read the audit trails.
      • 
      
    • No inventory of which workflows use which actions, so the first hour of a response is spent searching.

    🎤
    Interview drill
    
    
    Explain it simply: Why should GitHub Actions be pinned to a commit hash and not a tag?
    
    
    How a strong answer sounds
    A tag is a movable label. Whoever controls the action's repository, including someone who has stolen a maintainer's credential, can point an existing tag at different code, and every workflow that references the tag will run that code on its next job with no change on the consumer's side. That is what happened to tj-actions/changed-files in March 2025: the tags were moved to a commit that dumped pipeline secrets into the logs. A full commit hash names exact content and cannot be moved, so a pinned workflow keeps running the code that was reviewed. The cost is that you stop receiving updates automatically, so pinning goes together with Dependabot or Renovate proposing each new hash as a pull request. Pinning is not the whole answer, because code inside your pipeline can still turn hostile by other routes, so it sits alongside minimal token permissions and short-lived credentials.
    
    
    Deeper: On Monday you learn that an action used in forty of your repositories was compromised over the weekend. What do you do?
    
    
    How a strong answer sounds
    I treat it as a security incident with a clear order: stop, scope, revoke, investigate, harden. First, stop further exposure. I disable or remove the action across the organisation, with an allow-list policy or a quick search-and-patch, so that no new job runs it. Second, scope. I need to know which workflows reference it and by tag or hash, and which of those actually ran during the window. Workflow run history answers the second part, and the logs of those runs show whether the payload's output is present. Repositories pinned to a hash that predates the compromise are out of scope. Third, for every job that ran the bad version, I list everything it could see: repository and organisation secrets it referenced, the built-in token's permissions, and any cloud role it could assume. All long-lived secrets on that list are revoked and replaced now, without waiting to prove they were read, starting with those from public repositories, since their logs were public. The built-in token has expired, and short-lived cloud credentials have too, but I still review what was done with them while they lived. Fourth, investigate: the audit logs of the cloud accounts, the package index and the Git host for the exposure period, looking for use of those credentials from unfamiliar addresses, new access keys or users, unexpected package versions, commits, releases or workflow changes. Anything published in that window by an affected pipeline is treated as suspect and rebuilt. If customer data or published artefacts were affected, that goes to the disclosure process. Fifth, harden, so this is not repeated: all actions pinned to full hashes with an update robot, enforced by organisation policy; default token permissions set to read-only; stored keys replaced with short-lived identity tokens; publishing separated into jobs that run no third-party code; and monitoring of runners' outbound connections. Finally I would write it up, including how long scoping took, because the lack of an inventory of actions is usually the slowest part and the easiest to fix.
    
  
    

  
    
    
    🧠 Key takeaways
    
    
      
      
    • An action is someone else's program running with your pipeline's privileges.
      • 
      
    • In March 2025 the tags of a popular action were moved to malicious code, which printed pipeline secrets into build logs.
      • 
      
    • Log masking is defeated by encoding, and public repositories have public logs.
      • 
      
    • Damage depended on the reference, whether a job ran, what the job held, and who could read the log.
      • 
      
    • Pin actions to full commit hashes, let a robot propose updates, enforce the rule, and use fewer actions.
      • 
      
    • Give the token nothing by default, replace stored keys with short-lived identity, and keep secrets away from jobs that run others' code.
      • 
      
    • After exposure: stop, scope, revoke everything the job could see, investigate, then harden.

    GitHub masks secrets in logs. Why did the secrets still appear?
    
      
    
        
        
        
        
      
    
      
    Masking is a string match. Base64-encoding the output, twice, means the known values never appear literally.
    
    
    

    
    
      
    Two workflows ran the compromised action. One held a stored cloud access key; the other obtained cloud access through a short-lived identity token. How do their exposures differ?
    
      
    
        
        
        
        
      
    
      
    Both can be read from the job. What differs is how long the stolen value is useful, which is the argument for short-lived credentials.
    
    
    

    
    
      
    A team pins every action to a full commit hash. What must they add for this to stay healthy?
    
      
    
        
        
        
        
      
    
      
    Pins stop surprise changes, including fixes. A robot turns each update into a visible, reviewable change, ideally after a short waiting period.
    
    
    

    
    
      
    Why split a pipeline into a test job with no secrets and a publish job that holds them?
    
      
    
        
        
        
        
      
    
      
    A compromised step can read everything in its own job. Separation limits what shares a job with the release credentials.
