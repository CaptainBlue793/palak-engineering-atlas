Serverless & Cold Starts

Everything so far has involved something that stays running: an instance, a pod, a node. Serverless turns that round. You hand the platform a piece of code and a description of what should trigger it, and the platform starts a copy when an event arrives, bills you for the milliseconds it ran, and keeps nothing running in between. There are still servers, and they are someone else's problem. What becomes your problem is a different set of things: the delay when a copy has to be started from nothing, the limit on how many copies may run at once, a bill that follows traffic in a straight line, and events that can arrive twice. This chapter covers each, and the simulator finds the point at which a function becomes dearer than a container.

The execution model

A function is a handler: code that receives one event and returns. You upload it with a few settings (memory, a timeout, a role), and attach event sources: an HTTP endpoint, a queue, a bucket, a schedule. From then on the platform does the following for every event.

  • If an idle instance of the function exists, the event is given to it.
  • If none is idle, a new instance is created: a small, isolated sandbox with your code loaded. This is a cold start.
  • On AWS Lambda one instance handles one event at a time. A hundred simultaneous requests need a hundred instances.
  • An instance that has been idle for some minutes is destroyed. With no events there are no instances and no charge.

You are billed for the number of invocations and for the time each ran, multiplied by the memory you configured. The limits are part of the model: an invocation may run for 15 minutes at most on Lambda, the local disk is temporary, and nothing in memory is guaranteed to survive to the next invocation, so all state lives in a database, a queue or object storage.

Cold starts

When no idle instance exists, the platform has to make one before your handler can run, and the request waits. That is a cold start.

How long it takes depends on the runtime and on you. A small Node.js or Python function starts in a few hundred milliseconds. A large one that imports heavy libraries can take a second or two. A Java or .NET function that boots a framework can take several seconds. Cold starts happen when traffic rises (each extra concurrent request needs a new instance), after quiet periods, and after every deployment, when all instances are new. What you can do:

  • Ship less. Fewer dependencies and a smaller package mean less to fetch and less to load.
  • Initialise once, outside the handler. Clients and connections created at start-up are reused by every warm invocation.
  • Pay to keep instances warm. Provisioned concurrency keeps a set number initialised and ready. It works, and it brings back the idle cost that serverless removed.
  • Use a snapshot. Lambda's SnapStart saves an image of an initialised function and restores it, which removes most of a JVM's start-up.
  • Do not put a slow-starting runtime on an interactive path if occasional seconds of delay are unacceptable.

Concurrency limits

Because one instance serves one request, the number of instances in use is simple arithmetic:

  concurrency  =  requests per second  ×  average duration in seconds

     50 requests a second × 0.2 s   =    10 instances
    500 requests a second × 0.2 s   =   100 instances
    500 requests a second × 2 s     = 1,000 instances      # the default regional limit on AWS

An account has a limit on total concurrency in a region, 1,000 by default on AWS, shared by all its functions. When it is reached, further invocations are throttled: synchronous callers receive a 429, and asynchronous events are retried later. Two settings let you manage this per function. Reserved concurrency sets aside part of the limit for one function and also caps it there, which protects the others from it and protects whatever it calls. Provisioned concurrency is the pre-warmed pool from the last section.

The cap matters more than it seems. A function that scales to 1,000 instances opens 1,000 database connections, and a relational database sized for 200 falls over. Serverless scales the stateless part of your system instantly, and the stateful part behind it is exactly as scalable as it was before. Limit the function's concurrency to what its dependencies can take, or put a connection pooler in between.

resource "aws_lambda_function" "invoice" {
  function_name = "invoice-worker"
  role          = aws_iam_role.invoice.arn
  package_type  = "Image"
  image_uri     = "${aws_ecr_repository.invoice.repository_url}@${var.image_digest}"   # by digest: Chapter 9
  memory_size   = 1024
  timeout       = 30

  reserved_concurrent_executions = 50          # never more than 50 at once: the database allows 60 connections
}

resource "aws_lambda_event_source_mapping" "invoice_queue" {
  event_source_arn        = aws_sqs_queue.invoices.arn
  function_name           = aws_lambda_function.invoice.arn
  batch_size              = 10
  function_response_types = ["ReportBatchItemFailures"]   # retry only the messages that failed, not the whole batch
}

Cost crossover

A function's bill is a straight line through zero: no traffic, no cost; double the traffic, double the cost. An always-on service is a step: it costs the same whether its two instances are idle or busy, and more only when another instance is needed. Lines like that always cross.

Lambda, per month       =  requests × $0.20 per million
                         +  requests × duration (s) × memory (GB) × $0.0000166667

  1 request a second, 200 ms, 1 GB:      2.59 M requests   →  $0.52 + $8.64    =  $9.16
  200 requests a second, same function:   518 M requests   →  $104 + $1,728    =  $1,832

Two small always-on containers (0.5 vCPU, 1 GB each)     →  $35.55 a month, idle or busy

At one request a second the function costs a quarter of the containers. At two hundred it costs many times what the containers needed for that load would. Two things move the crossing point. One is the work in each request: a function that runs for a second costs twenty times as much per request as one that runs for 50 ms, while a container task simply serves fewer of them. The other is how well the always-on service follows its load. One that shrinks to its two-task floor between peaks stays cheap; one that has to be sized for its busiest hour around the clock pays for every idle hour, and against that a function wins up to far higher traffic.

Things to try.

  • One request a second (200 ms, 1 GB, steady). The function costs $9.16 a month and the containers $36, nearly all of it for two tasks that are mostly idle. The curves cross at about 3.9 requests a second.
  • 200 requests a second. $1,832 against $107: the containers are 17 times cheaper. Six busy tasks at a flat price do what 518 million individually billed invocations do.
  • A few requests an hour. One cent a month. And about 60% of requests start cold, because the instance has usually been reclaimed by the time the next request arrives. Cheap and slow is the right trade for a webhook.
  • Change the request itself. At 50 ms and 256 MB the break-even moves up to 33.6 requests a second; at one second and 1 GB it falls to 0.8. The amount of compute in a request shifts the crossover forty-fold, which is why "is serverless cheaper?" has no answer without it.
  • All the traffic in one hour a day, averaging 20 a second. The function needs 96 instances at once, and all of them are created in the first moments of that hour. Cold starts are a tiny share of the month and a visible stall at the start of every busy period.
  • 2,000 requests a second at one second each. Concurrency is 2,000, twice the default limit, so the function is throttled until the limit is raised. The bill would be $87,437 against $5,083.
  • What the panel flatters. The container service here follows its load hour by hour and never needs more than its floor when idle. A real one sized for its peak all day costs more, and a front door, whether an API gateway billed per request or a load balancer billed per hour, adds to both sides.

Event sources

How a function is invoked decides what happens when it fails, and that is where most serverless bugs live. There are three models.

SynchronousAsynchronousPolled (queues and streams)
SourcesAn HTTP gateway, a load balancer, a direct callObject storage events, notifications, schedules, an event busA queue (SQS), a stream (Kinesis, Kafka, a database's change stream)
The callerWaits for the answerHands the event over and leavesThe platform reads batches and invokes the function with them
On failureThe caller gets the error and decidesThe platform retries, twice by default, then sends the event to a dead-letter destination if you set oneThe batch returns to the queue or blocks the stream, and is retried until it succeeds or expires
On throttling429 to the callerKept and retried for hoursThe platform slows its reading
Watch forCold starts in the user's pathEvents silently dropped with no dead-letter destinationOne bad message retried for ever, blocking everything behind it

Hence the one rule that applies to every event-driven function: delivery is at least once, so the handler must be idempotent. Processing the same event twice has to leave the same result as processing it once: record the event's ID and skip repeats, or make the write itself safe to repeat. And every asynchronous or polled source gets a dead-letter queue with an alarm on it, because the alternative to a visible pile of failed events is an invisible one.

Use case: Prime Video and the 90% saving

In 2023 a team at Amazon Prime Video published an account of rebuilding one of its own services, and it was widely read because of where it came from. The service monitors the quality of video streams: it takes frames and audio from a stream, runs detectors on them for defects such as frozen pictures or lost sound, and raises alerts. The first version was assembled from serverless parts. A workflow service orchestrated each step, functions did the work, and intermediate frames were written to object storage so that the next function could read them. It worked, and it could not scale to the number of streams the team needed to watch. The orchestration made several state transitions for every second of every stream, each billed, and hit account limits; and fetching every frame from storage for every step was the largest cost of all. The team moved the whole pipeline into a single long-running process on containers, passing frames in memory. They reported an infrastructure cost reduction of more than 90% and a higher ceiling on scale. It is not a story against serverless: the same team kept it elsewhere. It is the cost model of this chapter in a real system. A workload that runs continuously at high volume is on the wrong side of the crossover, and a design that hands large data between many small functions pays for every hand-over.

⚠️
Common mistakes
  • Handlers that are not idempotent. A retry charges the customer twice or sends the email twice.
  • No dead-letter queue on asynchronous and polled sources, or one that nobody watches.
  • No concurrency cap on a function that talks to a database. A traffic spike becomes a connection storm.
  • Creating clients and connections inside the handler, on every invocation, instead of once at start-up.
  • Steady, high-volume work on functions. Past the crossover you pay several times the price of containers.
  • A slow-starting runtime on an interactive endpoint with no provisioned concurrency.
  • A function that triggers itself: it writes to the bucket or queue that invokes it. The loop runs until the bill is noticed.
  • One role for every function. Each should have only the permissions its own job needs.
  • Long workflows inside one invocation. It times out at 15 minutes and starts again from the beginning.
  • Thinking "no servers" means "no operations". Limits, retries, cold starts, costs and observability are all still yours.

Interview drill

Explain it simply: What is a cold start, and how do you reduce it?

How a strong answer sounds
A function runs in instances that the platform creates on demand. When a request arrives and no idle instance exists, the platform has to create a sandbox, load the code, start the runtime and run the function's initialisation before the handler can run, and the request waits for all of it. That delay is the cold start: a few hundred milliseconds for a small Node.js or Python function, seconds for a large package or a JVM framework. It happens when concurrency rises, after idle periods and after deployments. To reduce it I keep the package and its dependencies small, do initialisation once outside the handler so warm invocations reuse it, choose a fast-starting runtime for interactive paths, and where the delay is unacceptable pay for provisioned concurrency or use a snapshot feature such as SnapStart. I would also measure it first: for many asynchronous workloads nobody is waiting, and it does not matter.

Deeper: A team wants to move its main API, 300 requests a second around the clock, from Kubernetes to functions "to save money and stop managing servers". What do you advise?

How a strong answer sounds
I would run the numbers before discussing anything else. Three hundred requests a second is about 780 million a month. At, say, 150 ms and 1 GB, that is roughly $156 for requests and close to $2,000 for compute, plus an HTTP gateway in front at around a dollar a million, another $780, against a container service that needs perhaps a dozen small tasks for the same load at a few hundred dollars. Steady, high-volume traffic is the case where functions are the expensive option, because you pay for every millisecond at a premium and there is no idle time to save on. Then the operational points. Concurrency would be around 45 on average, which is fine, but a spike can exceed the account limit and throttle unrelated functions, and every instance holds its own database connection, so the database needs a pooler or a cap. Cold starts will appear in tail latency after every deployment and on every rise in traffic. And the work they want to stop doing does not all disappear: retries, limits, observability and per-function permissions replace nodes and upgrades. So my advice would be to keep the steady API on containers, perhaps on a serverless container platform if the goal is to stop managing nodes, and to move the things serverless is good at: the spiky and occasional parts, such as webhooks, scheduled jobs, file processing and queue consumers. Those are cheaper there and are less work to run.

🧠 Key takeaways

  • A function is a handler run on demand: one event per instance, no instances when idle, billed per invocation and per millisecond.
  • A cold start is the time to create and initialise an instance. Keep packages small, initialise outside the handler, and pay for warmth only where it matters.
  • Concurrency is requests per second × duration. At the limit, calls are throttled. Cap each function at what its dependencies can take.
  • Function cost is a line through zero; always-on cost is a step. Low or spiky traffic favours functions, steady high traffic favours containers.
  • Synchronous callers handle their own errors; asynchronous and polled sources retry for you and need a dead-letter queue.
  • Delivery is at least once: every handler must be idempotent.

Check your understanding

A function receives 400 requests a second and each takes 500 ms. How many instances run at once on a platform that gives each instance one request at a time?

Concurrency is rate × duration: 400 × 0.5 = 200. Halving the duration halves the instances needed.

Which change does not reduce cold-start time?

The timeout only limits how long an invocation may run. The others shrink what must be loaded, keep instances warm, or avoid repeating initialisation.

A function consumes orders from a queue and charges a card. It times out after charging but before finishing, and the message is delivered again. What prevents a double charge?

Queues and event sources deliver at least once. The handler has to make a repeated event harmless.

Which workload is the best fit for functions on cost?

Low, bursty traffic is where paying only for use wins. Steady high volume is past the crossover, a two-hour job exceeds the time limit, and a database is stateful.

Why set reserved concurrency of 50 on a function that writes to a relational database?

The function scales instantly and the database does not. A cap keeps the number of connections within what the database can serve; excess events wait or are throttled.
