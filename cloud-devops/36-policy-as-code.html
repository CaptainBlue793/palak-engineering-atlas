Policy as Code: OPA & Admission Control

Every organisation has rules for its infrastructure: containers must not run as root, images must come from our registry, every resource needs an owner tag. Written in a wiki, such rules are followed by the careful and missed by everyone in a hurry. Policy as code turns each rule into a program that checks every change automatically, in the pull request and again at the door of the cluster, and refuses the ones that break it. This chapter covers the two layers of control in Kubernetes, who may ask (RBAC) and what may be asked for (admission), then the built-in pod security levels, the two main policy engines, OPA and Kyverno, and how to introduce a policy without stopping every deployment. The simulator sends a pod through the whole chain.

  • Explain why rules should be code: reviewed, tested, versioned and enforced by machine
  • Write and check RBAC roles and bindings, and spot dangerous permissions
  • Trace a request through authentication, authorisation, mutating and validating admission
  • Apply the three Pod Security Standards to a namespace
  • Read a Rego rule and a Kyverno policy, and say when to choose each engine
  • Run the same policies in CI, and roll a new one out from audit to enforce

Why policy as code

A rule in a document depends on every engineer knowing it, remembering it and having time for it. A rule in a review checklist depends on the reviewer. Both fail quietly, and you learn that they failed from an incident. Policy as code means writing the rule in a form a machine evaluates against every change, with no exceptions for seniority or urgency.

Treating policy as code gives it everything code has. It is reviewed, so a new rule is a pull request that affected teams can see and discuss. It is tested, with examples of what must pass and what must fail. It is versioned, so you can say which rules were in force on a given day. And it is consistent: the same policy file can run on a developer's laptop, in CI and in the cluster, so nobody is surprised at the last step.

In Kubernetes there are two separate questions, answered by two separate mechanisms. People who confuse them leave gaps.

RBAC (authorisation)Admission control (policy)

RBAC: who may ask

Role-based access control has four kinds of object. A Role lists permissions, as verbs on resources, inside one namespace; a ClusterRole does the same for the whole cluster. A RoleBinding or ClusterRoleBinding gives a role to subjects: users, groups, or the service accounts that pods run as.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: deployer, namespace: shop }
rules:
  - apiGroups: ["apps"]
    resources: [deployments]
    verbs: [get, list, watch, create, update, patch]
  - apiGroups: [""]
    resources: [pods, pods/log]
    verbs: [get, list, watch]                    # may read pods and their logs; may not exec into them
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: team-shop-deployer, namespace: shop }
subjects:
  - { kind: Group, name: team-shop, apiGroup: rbac.authorization.k8s.io }
roleRef: { kind: Role, name: deployer, apiGroup: rbac.authorization.k8s.io }
$ kubectl auth can-i create deployments -n shop --as alice --as-group team-shop
yes
$ kubectl auth can-i create deployments -n payments --as alice --as-group team-shop
no
$ kubectl auth can-i --list -n shop --as system:serviceaccount:shop:checkout     # everything a workload's identity can do

RBAC is additive only. There is no deny rule: a subject can do the union of everything its bindings grant, and nothing else. So the work is in granting little. A few permissions are far more powerful than they look and deserve suspicion wherever they appear:

  • Reading Secrets in a namespace is reading every credential in it (Chapter 13).
  • Creating pods is close to the same thing, because a pod can mount any Secret in its namespace and run as any service account there.
  • pods/exec is a shell inside running workloads.
  • Wildcards (verbs: ["*"], resources: ["*"]) grant things that do not exist yet.
  • bind, escalate and impersonate let a subject give itself more.
  • The cluster-admin ClusterRole bound to anything other than a small break-glass group.

Give each workload its own service account with only the API permissions it needs. Most need none at all, and those should set automountServiceAccountToken: false so there is no token in the pod to steal.

Admission controllers

After RBAC says the caller may create a pod, the API server asks a second question: is this pod acceptable? That is admission control, and it runs in two phases.

Kubernetes ships with one important validating policy built in. The Pod Security Standards define three levels, and Pod Security Admission applies a level to a namespace through labels.

LevelWhat it forbidsUse it for
PrivilegedNothingSystem components that genuinely need the host: network plugins, storage drivers
BaselineThe known ways out of a container: privileged mode, host network and process namespaces, mounting host paths, dangerous capabilitiesThe minimum for any ordinary workload
RestrictedAll of baseline, and also running as root, privilege escalation, and any capability not explicitly allowed. Requires a seccomp profileThe target for application workloads
 
apiVersion: v1
kind: Namespace
metadata:
  name: shop
  labels:
    pod-security.kubernetes.io/enforce: baseline      # reject what breaks baseline
    pod-security.kubernetes.io/warn: restricted       # and tell the user what would break restricted
    pod-security.kubernetes.io/audit: restricted

These levels matter because a container is only a restricted process on a shared kernel. A privileged container has those restrictions removed and is root on the node in all but name. From the node it can read every other pod's secrets.

Rules beyond pod security need a policy engine. Engines usually plug in as admission webhooks: the API server sends each object to the engine over HTTPS and waits for a verdict. That makes the engine part of the path of every deployment, with one setting to decide deliberately. With failurePolicy: Fail, an unreachable webhook blocks all changes, which is safe and can lock you out of your own cluster. With Ignore, changes go through unchecked while it is down. Run the engine with several replicas, and exempt the system namespaces so the cluster can always repair itself. Newer clusters also offer ValidatingAdmissionPolicy, which evaluates simple rules written in an expression language called CEL inside the API server, with no webhook to fail.

OPA and Rego

Open Policy Agent (OPA) is a general-purpose policy engine. You give it a JSON document and a policy, and it returns a decision. Nothing about it is specific to Kubernetes: the same engine checks Terraform plans, API requests and CI configurations. Policies are written in Rego, a declarative language in which you describe what a violation looks like, and the engine finds every match. Gatekeeper is the project that runs OPA as a Kubernetes admission controller.

# Rego: every container image must come from the company registry
package k8sallowedrepos

violation[{"msg": msg}] {
  container := input.review.object.spec.containers[_]            # for each container in the pod
  not startswith(container.image, "registry.example.com/")
  msg := sprintf("container %v uses image %v, which is not from the approved registry", [container.name, container.image])
}

The line with [_] is the part that takes getting used to. It does not loop. It says "there exists a container such that the following lines hold", and Rego reports a violation for each one it finds. With Gatekeeper, that Rego goes inside a ConstraintTemplate, and a second small object, a constraint, says which namespaces it applies to and with which parameters.

Kyverno

Kyverno was built only for Kubernetes, and its policies are ordinary Kubernetes YAML with no new language. A policy holds rules of four kinds: validate (accept or reject), mutate (change the object), generate (create other objects, such as a default network policy in each new namespace) and verifyImages (check signatures).

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: disallow-latest-tag }
spec:
  validationFailureAction: Audit                 # record violations; change to Enforce to reject
  rules:
    - name: require-pinned-image
      match: { any: [{ resources: { kinds: [Pod] } }] }
      validate:
        message: "Images must be pinned to a version or digest, not :latest."
        pattern:
          spec:
            containers:
              - image: "!*:latest"
---
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-image-signature }      # the admission check promised in Chapter 29
spec:
  validationFailureAction: Enforce
  rules:
    - name: signed-by-release-workflow
      match: { any: [{ resources: { kinds: [Pod] } }] }
      verifyImages:
        - imageReferences: ["registry.example.com/*"]
          attestors:
            - entries:
                - keyless:
                    issuer: "https://token.actions.githubusercontent.com"
                    subject: "https://github.com/example/*/.github/workflows/release.yml@refs/heads/main"

Policies in CI

A policy that first speaks at the cluster door speaks too late. The developer finds out at deploy time, after review, with the least context. So the same policies run earlier, in the pull request, against the rendered manifests and the Terraform plan.

# In the pull request: the same Kyverno policies the cluster enforces, applied to the rendered manifests
$ kustomize build deploy/overlays/prod | kyverno apply policies/ --resource -
policy disallow-latest-tag -> resource shop/Deployment/web failed:
  require-pinned-image: Images must be pinned to a version or digest, not :latest.
pass: 14, fail: 1, warn: 0, error: 0, skip: 0

# Rego against a Terraform plan: no public buckets, every resource tagged with an owner
$ terraform show -json plan.out | conftest test --policy policy/terraform -
FAIL - aws_s3_bucket.exports - bucket must not allow public access
FAIL - aws_instance.worker - missing required tag "team"

$ kyverno test policies/           # unit tests for the policies themselves: these manifests pass, those fail

Introducing a new policy to a cluster that already runs hundreds of workloads needs care, because switching it straight to "enforce" will block the next deployment of every service that happens to violate it, including an urgent fix.

    ⛏️
    
    
    Use case: "RBAC Buster", a cluster taken over with its own access rules
    In 2023 researchers at Aqua Security described an attack campaign they had caught in their honeypots and then found running in dozens of real clusters. The way in was a misconfiguration, not a vulnerability: Kubernetes API servers reachable from the internet that accepted anonymous requests and, through a careless binding, gave the anonymous user real privileges. The interesting part is what the attackers did next. They did not simply start a pod. They used RBAC itself to make their access permanent: they created a ClusterRole with close to administrator rights, a service account in the system namespace, and a ClusterRoleBinding joining the two, all with names chosen to look like built-in components. Even if the anonymous access was later closed, their service account would still work. Then they deployed a DaemonSet, one pod on every node, running a cryptocurrency miner from an image on Docker Hub whose name was one letter away from the official Kubernetes one; the image had been pulled many thousands of times. Each control in this chapter cuts that chain at a different link. Anonymous access with privileges is an RBAC error that a routine kubectl auth can-i --list --as system:anonymous would show. A policy restricting images to the company registry would have rejected the look-alike image whoever asked for it, administrator or not. And a policy or alert on new ClusterRoleBindings would have flagged the persistence step, because in a healthy cluster those are rare and deliberate.
    
  
    

  
    ⚠️
    Common mistakes
    
    
      
      
    • Thinking RBAC is enough. RBAC decides who may create a pod. It has no opinion about what is in the pod.
      • 
      
    • cluster-admin for CI, for developers, or for a workload's service account.
      • 
      
    • Treating "create pods" as a harmless permission. It reaches every Secret and service account in the namespace.
      • 
      
    • Namespaces left at the privileged level because one old workload needed it. Move that workload, not the standard.
      • 
      
    • Switching a new policy straight to enforce. The first thing it blocks will be an urgent fix.
      • 
      
    • Policies only at admission. Run them in the pull request too, so the feedback arrives early.
      • 
      
    • Unhelpful rejection messages. Say what is wrong and how to fix it.
      • 
      
    • A webhook with failurePolicy: Fail, one replica, and no exemption for system namespaces. When it goes down, so does every deployment, including its own.
      • 
      
    • Permanent exceptions. Give each one an owner and an expiry date.
      • 
      
    • Untested policies. A rule with a typo either blocks everything or, worse, nothing.
      • 
      
    • Mutating so much that the running object no longer resembles the manifest in Git, which confuses people and GitOps tools alike.
      • 
    
    

  
    🎤
    Interview drill
    
    
    Explain it simply: What is the difference between RBAC and admission control in Kubernetes?
    
    
    How a strong answer sounds
    They answer different questions at different points in a request. RBAC is authorisation: may this user or service account perform this verb on this type of resource in this namespace? It looks at who is asking and what kind of action it is, never at the content of the object, and it only grants; there is no deny. Admission control runs after RBAC has said yes and looks at the object itself. Mutating admission can change it, for example to add default resource limits, and validating admission can reject it, for example because the container is privileged or the image comes from an unapproved registry. Admission policies apply to everyone, cluster administrators included. You need both: RBAC to limit who can do things, and admission to limit what can be done by anyone.
    
    
    Deeper: You want to require that every image in production is signed by your release pipeline. Two hundred services run in the cluster today. How do you roll that out?
    
    
    How a strong answer sounds
    I would not start with the policy, I would start with the pipeline, because a rule nobody can satisfy only produces exceptions. First the standard build pipeline signs every image by default, so that any service that rebuilds becomes compliant without doing anything. Then I add the verification policy in audit mode, scoped to production namespaces, and read the policy report. That shows who is not compliant and why, and the reasons fall into groups: services not rebuilt recently, teams with their own pipelines, and third-party images we do not build at all. Each group needs a different answer. The stale ones need a rebuild. The custom pipelines need the signing step, which I would offer as a reusable workflow. For third-party images I would either verify the vendor's own signature or mirror them into our registry through a pipeline that scans and signs them, and write the policy to match. Meanwhile the same check runs in pull requests as a warning, with a message that links to the fix. I would publish the list and a date, and watch the violation count fall. Before enforcing I would check the operational side: the policy engine has several replicas, system namespaces are exempt, and there is a documented break-glass procedure for an emergency deployment, which is audited. Then I enforce one namespace or one tier at a time, lowest risk first. The few remaining exceptions are explicit policy exceptions with an owner and an expiry, not a quiet carve-out. After that, the report becomes a dashboard and an alert, since any violation that appears from then on is news.
    
  
    

  
    
    
    🧠 Key takeaways
    
    
      
      
    • Policy as code makes rules reviewed, tested, versioned and enforced on every change.
      • 
      
    • RBAC decides who may act on which resources. It is additive, and several ordinary-looking permissions are powerful.
      • 
      
    • Admission control judges the object itself: mutate first, then validate. It binds administrators too.
      • 
      
    • Pod Security Standards: privileged, baseline, restricted. Aim application namespaces at restricted.
      • 
      
    • OPA with Rego is one engine for everything. Kyverno is Kubernetes-native YAML that validates, mutates, generates and verifies signatures.
      • 
      
    • Run the same policies in pull requests and at the cluster door.
      • 
      
    • Roll out by audit, warn, then enforce, with helpful messages and expiring exceptions.
      •

    A user with the cluster-admin role applies a privileged pod to a namespace whose pod security level is baseline. What happens?
    
      
    
        
        
        
        
      
    
      
    RBAC allowed the request. Admission then judged the pod itself, and that judgement does not depend on who sent it.
    
    
    

    
    
      
    Why does mutating admission run before validating admission?
    
      
    
        
        
        
        
      
    
      
    A pod with no limits may be given defaults by a mutating policy, and then pass a validator that requires limits.
    
    
    

    
    
      
    A service account can create pods in a namespace but has no permission to read Secrets. Why is that still a risk to the namespace's Secrets?
    
      
    
        
        
        
        
      
    
      
    "Create pods" is an indirect path to every Secret and service account in the namespace, which is why it is treated as a powerful permission.
    
    
    

    
    
      
    A new policy is deployed in audit mode. What does that do?
    
      
    
        
        
        
        
      
    
      
    Audit mode shows the size of the problem and who needs to change, before enforcement can break a deployment.
    
    
    

    
    
      
    What is the main reason to run admission policies in the pull-request pipeline as well as in the cluster?
    
      
    
        
        
        
        
      
    
      
    Early feedback is cheaper to act on. The cluster check remains, as the one that cannot be skipped.
