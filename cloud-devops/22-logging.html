Logging at Scale

A metric tells you that 5% of payments are failing. A log line tells you that this payment, for this request, failed because the upstream rejected an expired token. Logs are the detailed record, and they are also the most expensive kind of telemetry: one busy service writes more bytes of log than it serves of real data, and at scale the logging bill rivals the compute bill. Operating logs is therefore a set of trade-offs between what you can afford to keep and what you will wish you had kept. This chapter covers structured logging, the pipeline that carries logs off the nodes, the two ways of storing them for search, and how retention and filtering control the cost. The simulator runs an hour of logs through a pipeline you configure and checks which questions you can still answer.

Structured logging

A traditional log line is a sentence written for a person. That works while one person reads one file. It fails when a machine has to answer "show me every failed payment over 100 euros in the last hour" across four hundred pods, because the machine would first have to parse the sentence, and every service phrases its sentences differently.

# Unstructured: three services, three formats
203.0.113.7 - - [07/Oct/2026:10:42:07 +0000] "POST /api/pay HTTP/1.1" 502 153
ts=10:42:07 level=info service=checkout msg="request completed" status=200 duration_ms=41
[ERROR] 10:42:07 payments: upstream returned 502 for order 812 (trace a3f91c)

# Structured: one JSON object per line, the same field names everywhere
{"ts":"2026-10-07T10:42:07.318Z","level":"error","service":"payments","version":"4.18.2",
 "trace_id":"a3f91c","route":"/api/pay","status":502,"duration_ms":1840,
 "msg":"upstream returned 502","upstream":"acquirer","order_id":812}

A structured log is an event with named fields. The practices that make it useful:

  • One event per line, as JSON, written to stdout. The application does not open files, rotate them or ship them. The platform collects stdout.
  • The same core fields in every service: timestamp in UTC, level, service, version, and a message that is a constant string. Put the variable parts in fields, not in the message: "msg":"upstream returned 502" with "order_id":812, not "order 812 failed".
  • A correlation ID on every line. The first service to see a request creates a trace_id and every service downstream logs the same one. Searching for that ID then returns the whole story of one request, in order, across services (and Chapter 23 uses the same ID for traces).
  • Levels that mean something: ERROR for a failed operation someone may need to act on, WARN for something odd that was handled, INFO for normal business events, DEBUG for the detail a developer needs.
  • Never log secrets or personal data: passwords, tokens, card numbers, full request bodies. Logs are copied to more systems, and read by more people, than any database.
$ kubectl logs deploy/payments -n shop --since=1h | jq -c 'select(.status >= 500) | {ts, trace_id, msg, upstream}'
{"ts":"2026-10-07T10:42:07.318Z","trace_id":"a3f91c","msg":"upstream returned 502","upstream":"acquirer"}

$ kubectl logs deploy/payments -n shop --since=1h | jq -r 'select(.level == "error") | .msg' | sort | uniq -c | sort -rn
     38 upstream returned 502
      3 card declined by issuer

The second command works only because the message is a constant. With the order number in the message there would be 41 different lines, each seen once.

Collectors and pipelines

kubectl logs reads a file on one node, for one pod, and that file is deleted when the pod is. To search across everything and keep history, logs have to leave the node. The path has four stages.

The collector usually runs as a DaemonSet, one pod per node: Fluent Bit, Vector, Grafana Alloy and the OpenTelemetry Collector are the common ones. It must not lose logs when the backend is slow, so it buffers to disk and retries, which also means the backend can receive the same line twice. A collector's configuration is a small pipeline of its own.

# OpenTelemetry Collector, running on every node
receivers:
  filelog:
    include: [/var/log/pods/*/*/*.log]
    operators:
      - { type: container }                      # unwrap the container runtime's line format
      - { type: json_parser, if: 'body matches "^{"' }   # structured lines become fields
processors:
  k8sattributes: {}                              # add namespace, pod, deployment, node
  filter/drop-debug:
    logs:
      log_record: ['severity_number < SEVERITY_NUMBER_INFO']    # drop DEBUG before it costs anything
  transform/redact:
    log_statements:
      - context: log
        statements:
          - replace_pattern(body, "[0-9]{4} ?[0-9]{4} ?[0-9]{4} ?[0-9]{4}", "[REDACTED-CARD]")
  batch: {}
exporters:
  otlphttp: { endpoint: http://logs-gateway.observability:4318 }
service:
  pipelines:
    logs:
      receivers: [filelog]
      processors: [k8sattributes, filter/drop-debug, transform/redact, batch]
      exporters: [otlphttp]

Indexing and search

Where the logs land decides what searches are fast and what the storage costs. There are two main designs.

Full-text indexLabel index over object storage
ExamplesElasticsearch, OpenSearch, SplunkGrafana Loki and similar
What is indexedEvery word of every lineOnly a few labels per stream (service, namespace, level). The lines themselves are compressed chunks in object storage
"Find this request ID anywhere in the last week"Fast: look it up in the indexSlow: every chunk in the time range has to be read and scanned
"Errors from payments in the last hour"FastFast: the labels select a small set of chunks
Storage usedMore than the raw logs: data plus index, on fast disksA fraction of the raw logs: compressed, on object storage
Cost per gigabyte ingestedHighLow
Operating itA cluster to size, shard and upgradeMostly stateless services in front of a bucket
FitsSecurity investigations, unpredictable searchesApplication debugging, where you usually know the service and the time
 
# Full-text store (Lucene-style query): any field, any word
service:payments AND status:[500 TO 599] AND upstream:acquirer

# Label store (LogQL): choose streams by label, then filter and parse the lines
{namespace="shop", service="payments"} | json | status >= 500 | upstream = "acquirer"

# Counting lines over time turns logs into a metric, in either system
sum by (service) (count_over_time({namespace="shop"} | json | level = "error" [5m]))

The last query is legitimate for rare events, and a poor way to measure anything frequent. If you need "requests per second" or "error ratio", emit a metric: it costs a few bytes every fifteen seconds instead of a line per request, and it does not change when you start sampling the logs.

Retention and cost

Log volume is close to linear in traffic, and the bill has three parts: getting the bytes in (network, parsing, indexing), keeping them (storage × days), and querying them. The levers, from most effective to least:

  • Do not emit it. DEBUG off in production by default, with a way to turn it on for one service or one request when you need it.
  • Drop or sample in the collector. Health-check requests, successful requests on very busy endpoints. Keep every error and warning.
  • Keep less for less time. Thirty days searchable is plenty for debugging; a year belongs in archive storage. Use different retention for different streams: audit logs long and immutable, DEBUG a few days.
  • Tier the storage. Recent logs on fast storage, older ones moved to cheaper classes by lifecycle rules (Chapter 4).
  • Give each team a budget and show them their volume. The noisiest service is usually unaware that it is.

    Things to try.

    • The starting point keeps everything, as each service's own text, in a full-text store for 30 days: $9,450 a month. Two of the four questions fail. Fourteen lines an hour hold a card number, and the search for 5xx responses finds 8 of 22, because only one of the three formats writes status=.
    • Switch to structured JSON. The bill does not move, and the 5xx question now returns all 22 from one condition on one field. Structure costs nothing to store and decides what you can ask.
    • Drop DEBUG. Volume falls to 31% and the bill to $2,971: DEBUG was 60% of the lines and most of the bytes. Now read the first answer. The error is still there and its explanation is gone. That is the real price of the cheapest saving, and the reason to be able to switch DEBUG back on for one service when you need it.
    • Keep 1 in 10 INFO lines as well. 10% of the volume, $947. The count of checkout requests now says 17 where the truth is 126. Anything you were measuring by counting log lines has just become wrong.
    • Redact. The lines with personal data go to zero, and the sample line at the bottom of the box shows what was stored instead. The saving here is not money.
    • Change the store to labels over object storage. The same trimmed pipeline costs $80 a month instead of $947. Then put everything back, DEBUG and all INFO, on that store for 90 days: $905, with all four questions answered. That is a tenth of the starting bill for three times the retention. What you gave up is in the comparison table above: a search for one ID across everything is slow.
    🔐
    Use case: Twitter, May 2018, and passwords in a log

    On 3 May 2018 Twitter asked all of its users, about 330 million accounts, to consider changing their passwords. Nothing had been breached. The company stored passwords correctly, as hashes that cannot be reversed. But a bug had been writing passwords to an internal log before the hashing step, so that the plain text sat in a log file. Twitter found it during an internal review, removed the data, fixed the bug, and said it had no sign that anyone had misused the log, and then told everyone anyway, because it could not prove that nobody had read it. GitHub disclosed a very similar bug the same week, and Facebook reported one the following year that had left hundreds of millions of passwords readable in internal logs. The pattern is the same each time: a developer logs a request or an object "for debugging", and one of its fields is a secret. Logs are less protected than the database, copied to more systems, kept by retention rules written for convenience, and readable by many more people. That is why the defences in this chapter come in layers: log named fields instead of whole objects, keep secrets out of loggable types in code, redact known patterns in the collector, and restrict who can search production logs. Any one of them fails sometimes.

    ⚠️
    Common mistakes
    • Free-text messages with the data inside them. Unsearchable, uncountable and different in every service.
    • No correlation ID. Finding one request's lines across five services becomes guesswork by timestamp.
    • Logging whole requests, responses or objects. That is how passwords, tokens and card numbers reach the logs.
    • DEBUG on in production, for ever. Most of the bill, read by nobody.
    • Using logs to count things. A metric is cheaper, faster and survives sampling.
    • One retention period for everything. Audit logs need years; debug output needs days.
    • Sampling errors. Sample the boring majority and keep every error and warning.
    • Applications that write log files inside the container, or ship logs themselves. The disk fills, or the logs are lost with the pod.
    • A collector with no buffer and no limits. When the backend slows down, either logs are lost or the agent takes the node's memory.

    Interview drill

    Explain it simply: What is structured logging, and why does it matter?

    How a strong answer sounds
    Structured logging means each log entry is an event with named fields, usually one JSON object per line, instead of a free-text sentence. Every service uses the same core fields: timestamp, level, service, a constant message and a correlation ID, with the variable data in separate fields. It matters because at scale logs are read by machines first. With fields I can filter by status or service, group by message to see which errors are most frequent, and pull every line for one request across services by its trace ID, without writing a parser for each service's wording. It also makes processing in the pipeline reliable: dropping a level, redacting a field or sampling a route are simple rules on fields.

    Deeper: The logging bill has doubled in six months and finance wants it halved. What do you do?

    How a strong answer sounds
    I would start by measuring where the volume comes from: bytes per service, per level and per message pattern. It is nearly always concentrated, with a few services and a few repeated lines producing most of it, typically DEBUG output left on, health checks and per-request INFO lines on busy endpoints. Then I work down the levers in order of effect. Stop emitting what nobody reads: DEBUG off by default with a way to enable it per service or per request. Drop or sample in the collector: health checks dropped, successful requests on the hottest routes sampled, every warning and error kept. Replace counting-by-logs with metrics, so that sampling does not break dashboards. Shorten and tier retention: perhaps two weeks searchable for application logs, a short period for anything verbose, and audit and security logs archived to cheap object storage for as long as compliance requires. If the store is a full-text index and most searches are "this service, this time range", move application logs to a label-indexed store on object storage and keep the full-text system for security data. Throughout I would keep correlation IDs intact so that what remains is still usable, show each team its own volume and give it a budget, and agree with the teams what questions the logs must still answer, because every one of these cuts removes some ability to investigate and that should be a decision, not a surprise during an incident.

    🧠 Key takeaways

    • Log events, not sentences: JSON to stdout, the same fields in every service, a constant message, a correlation ID.
    • An agent on each node collects, enriches, filters, samples, redacts and ships. That stage decides the cost.
    • Full-text indexes make any search fast and cost the most. Label indexes over object storage are cheap and need you to narrow by service and time.
    • Cost is ingest plus storage × retention. Drop DEBUG, sample the routine, keep every error.
    • Each saving removes an answer: without DEBUG you may see that something failed and not why.
    • Count with metrics, explain with logs.
    • Secrets and personal data must never be logged; redact in the pipeline as a second line of defence.

    Check your understanding

    Which log line is easiest to work with at scale?

    Named fields, a constant message and a correlation ID, with no personal data. The first option hides its data inside a sentence and logs an email address.

    A request passes through five services and fails. What lets you collect all its log lines in one search?

    Timestamps overlap between thousands of requests. A shared ID on every line identifies one request exactly.

    A team drops all DEBUG lines in the collector to cut costs. What is the main thing they give up?

    Errors are kept. What is lost is the surrounding detail, so the usual compromise is DEBUG off by default with a way to enable it selectively.

    Engineers nearly always search "errors from service X in the last hour". Which store is the economical fit?

    When queries are narrowed by service and time, a label index finds the right chunks quickly at a fraction of the storage cost. Full-text indexing earns its price on needle-in-a-haystack searches.

    A dashboard shows "requests per minute" by counting INFO log lines. The team then starts sampling INFO lines at 10%. What happens?

    Anything computed by counting log lines changes when the pipeline changes. A counter metric is unaffected and far cheaper.
