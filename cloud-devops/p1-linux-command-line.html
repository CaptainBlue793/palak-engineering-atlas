The Linux Command Line

Almost every server you will run in this course is a Linux machine with no screen and no mouse. When something breaks at two in the morning, you connect over SSH and all you have is a shell prompt. This chapter covers the commands you will use in that moment: finding your way around the file system, reading logs, finding which process is doing what, fixing permissions, and installing software. At the end you will use them on a broken server in the simulator.

  • Know where Linux keeps configuration, logs, state and live process information
  • Read and search logs with less, tail -f, grep and short pipelines
  • Inspect processes and listening ports with ps, top, ss and kill
  • Read and set permissions (rwx, 640, chown) and use sudo deliberately
  • Install packages with apt, dnf or apk and know why scripts pin versions

Where things live on a server

Linux has one tree of directories starting at /. Disks, USB sticks and network shares are all mounted somewhere inside that tree rather than getting their own drive letter. You do not need to know every directory, but an operator goes to the same six or seven all the time:

PathWhat is thereYou go there when…
/etcSystem and service configuration: /etc/nginx/nginx.conf, /etc/ssh/sshd_configa service behaves differently from what you expected
/var/logLog files: /var/log/nginx/error.log, /var/log/syslogsomething failed and you want to know why
/var/libProgram state: databases, Docker images (/var/lib/docker)the disk is filling up and logs are not the culprit
/procNot real files: a live view of the kernel and every process (/proc/meminfo, /proc/1234/)you want facts about a running process
/home, /rootUsers' home directories (~); root's is separateyou look for your own files or SSH keys
/tmpScratch space, often cleared on rebootyou need somewhere to put a download
/opt, /usr/localSoftware installed by hand rather than by the package manageryou look for an app that was not installed with apt

Six commands get you around. pwd prints where you are, cd moves, ls -lah lists everything (including hidden dot-files) with sizes humans can read, find searches by name, size or age, du says how much space a directory uses, and df says how full each file system is:

# Which file system is full, and what is filling it?
$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p1   20G   19G  1.0G  95% /
$ sudo du -sh /var/* 2>/dev/null | sort -h | tail -n 3
1.2G    /var/cache
3.9G    /var/lib
11G     /var/log                         # logs: look here first
$ find /var/log -type f -size +1G     # files over 1 GB
/var/log/app/debug.log

Two details in that listing come up constantly. 2>/dev/null throws away error messages (here, "permission denied" for directories you cannot read), and sort -h sorts human-readable sizes so that 11G comes after 3.9G.

Reading and searching logs

Most debugging is reading. cat prints a whole file, which is fine for a ten-line config and useless for a two-gigabyte log. For big files you use tools that read only part of it:

  • less file pages through a file of any size. Inside it, G jumps to the end, / searches, n finds the next match and q quits.
  • tail -n 50 file shows the last 50 lines; tail -f keeps printing new lines as they are written, which is how you watch a log during a deploy. tail -F also survives log rotation, when the file is renamed and a new one created.
  • grep pattern file prints matching lines. The flags you will use most: -i ignore case, -v invert (lines that do not match), -n line numbers, -c count, -r search a directory, -E extended regular expressions.

The real power comes from the pipe, |, which feeds one command's output into the next. Each tool does one small job, and you chain them. This pipeline answers "which five clients sent the most requests?" from an nginx access log, where the client IP is the first field on each line:

$ awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -n 5
  48211 203.0.113.42                    # one client sent 48k requests: a scraper or a retry loop
   1893 198.51.100.7
   1544 192.0.2.19
    977 198.51.100.23
    840 192.0.2.88

# Same idea for status codes (field 9 in the default log format): how many 5xx?
$ awk '{print $9}' /var/log/nginx/access.log | grep -c '^5'
3120

Read it left to right. awk '{print $1}' keeps only the first field. sort puts identical IPs next to each other, which matters because uniq -c only counts adjacent duplicates. sort -rn sorts by that count, biggest first, and head keeps the top five. You will write pipelines like this during almost every incident.

Processes and ports

A process is a running program with a numeric ID (the PID), an owner, and some memory and CPU time. A service such as nginx is usually several processes: a master that runs as root and opens port 80, and workers that run as an unprivileged user and handle requests.

  • ps aux lists every process with its owner, CPU and memory share, and full command line. Pipe it to grep to find one: ps aux | grep nginx. pgrep -a nginx does the same more neatly.
  • top (or the friendlier htop) refreshes the list every few seconds, sorted by CPU. The first line shows the load average: the average number of tasks running or waiting over the last 1, 5 and 15 minutes. Compare it with the number of cores (nproc): a load of 8 on a 4-core machine means work is queuing.
  • ss -ltnp lists listening TCP sockets: listening, tcp, numeric ports, and the process that owns each one. It answers "is anything actually listening on 8080?", the first question when a proxy cannot reach an app. Without sudo, the process column is blank for sockets owned by other users.
  • kill PID sends a signal. With no option it sends SIGTERM (15), a polite request to shut down that the program can catch to finish requests and close files. kill -9 sends SIGKILL, which the kernel enforces immediately and the program never sees: no cleanup, possibly half-written files. Use it only when SIGTERM has failed.

Permissions and sudo

Every file has an owner, a group, and three sets of permissions: for the owner, for members of the group, and for everyone else. Each set is read (r), write (w) and execute (x; for a directory, "may enter"). ls -l shows them as a ten-character string, and chmod sets them, usually as three octal digits where r = 4, w = 2 and x = 1:

$ ls -l /etc/app/config.yaml
-rw-r----- 1 root app 812 Oct  1 02:01 /etc/app/config.yaml   # owner root, group app
$ sudo chown root:app /etc/app/config.yaml   # set owner and group
$ sudo chmod 640 /etc/app/config.yaml         # root writes, the app group reads, nobody else
$ chmod 600 ~/.ssh/id_ed25519               # ssh refuses a private key others can read

root is the user with ID 0, which bypasses permission checks. You normally log in as an ordinary user and put sudo in front of the one command that needs root, so that each privileged action is deliberate and logged (in /var/log/auth.log on Debian and Ubuntu). Two things catch people out: sudo applies to the command, not to the redirect after it, so sudo echo x > /etc/file fails because your own shell opens the file (use echo x | sudo tee /etc/file); and services should run as their own unprivileged user, so that a bug in the app cannot rewrite the whole server.

Installing software

Linux distributions install software from signed package repositories using a package manager, which also installs dependencies and handles upgrades. Which one you use depends on the distribution, and in this course you will meet all three, because container base images differ:

ManagerDistributionsInstallPackage formatWhere you meet it
apt / apt-getDebian, Ubuntuapt-get update && apt-get install -y nginx.debmost VMs, debian and ubuntu images
dnf (was yum)RHEL, Fedora, Rocky, Amazon Linux 2023dnf install -y nginx.rpmenterprise servers, AWS's default image
apkAlpineapk add --no-cache nginx.apksmall container images (Chapter 8)

In scripts, use apt-get rather than apt: apt is meant for people and warns that its output format may change. Run update first, because the list of available versions is cached locally and goes stale. And for anything that must be reproducible, pin the version (apt-get install -y nginx=1.24.0-2ubuntu7) so that a server built next month gets the same software as one built today. That idea, "pin everything", comes back in every later chapter.

Simulator: the 02:00 page

You are paged: checkout on shop.example.com returns 502. You have SSH'd into the web server as user ops. Type real commands (try help for the list); the checklist ticks itself as you find each clue. The chips under the checklist suggest a next command if you get stuck.

Terminal: ops@web-1, checkout is returning 502Interactive
ops@web-1:~$
    Root disk
    A small simulated server: the file system, processes, disk and the app's service state are modelled, and permissions are enforced, so some fixes need sudo. Try deleting the big file with rm before you look at what has it open.

    If you deleted debug.log and the disk stayed full, you met one of the most common surprises in operations. Deleting a file removes its name; the space is freed only when the last process holding it open closes it. lsof +L1 lists files that are open but no longer have a name. Either stop that process, or empty the file in place with truncate -s 0 instead of deleting it, which frees the space at once even while the writer keeps it open.

    🔎
    Use case: one client, half the traffic

    An API's error rate doubles on a Saturday with no deploy. The on-call engineer runs the pipeline from earlier on the access log and finds one IP address responsible for 48,000 of the last 90,000 requests, nearly all POST /login returning 401. It is a credential-stuffing bot. A one-line grep -c confirmed the pattern, the IP was blocked at the load balancer within ten minutes, and the team later added rate limiting per client. No dashboard existed for "requests per client IP"; three Unix tools built one on the spot.

    ⚠️
    Common mistakes
    • Deleting a log that a process still has open. The space is not freed. Use truncate -s 0, or restart the writer.
    • cat on a huge file floods your terminal and can hang a slow SSH session. Use less, tail or grep.
    • chmod 777 to "fix" a permission error. It lets every user and every compromised process write the file. Find out which user needs access and grant exactly that.
    • Reaching for kill -9 first. SIGKILL skips cleanup, so open transactions and half-written files are left behind. Send SIGTERM and wait a few seconds.
    • uniq without sort. uniq only merges adjacent duplicate lines, so unsorted input gives wrong counts.
    • Working as root all the time. One mistyped rm -rf with a stray space then has no safety net.
    🎤
    Interview drill

    Explain it simply: You SSH into a server that users say is slow. What do you run in the first minute?

    How a strong answer sounds
    Broad and cheap first. uptime for the load average, compared with nproc, to see whether work is queuing. top to see which process is using CPU or memory and whether there is I/O wait. df -h because a full disk breaks things in strange ways, and free -h for memory and swap. Then the service itself: is it running and listening (ps, ss -ltnp), and what do its newest log lines say (tail, grep -i error). Only after that do I go deep on one hypothesis. I would also ask what changed recently, because most incidents follow a change.

    Deeper: df says the disk is 100% full, but du on every directory adds up to much less. What is going on?

    How a strong answer sounds
    Space is being held by files that have been deleted but are still open. du walks the directory tree, so it cannot see a file with no name; df asks the file system how many blocks are allocated, which includes them. lsof +L1 (or ls -l /proc/*/fd | grep deleted) shows which process holds them. The fix is to restart that process, or truncate the file through /proc/PID/fd/N. To prevent it, rotate logs with a tool that signals the writer to reopen its file, such as logrotate with a postrotate reload, or with copytruncate.

    🧠 Key takeaways

    • Configuration lives in /etc, logs in /var/log, state in /var/lib, live process facts in /proc.
    • df -h shows which file system is full; du -sh … | sort -h shows what is filling it.
    • Read big files with less, tail -f and grep; combine tools with pipes: sort | uniq -c | sort -rn.
    • ps and top show processes, ss -ltnp shows who is listening; kill sends SIGTERM, kill -9 is the last resort.
    • Permissions are owner/group/other × read/write/execute; grant exactly what is needed and use sudo per command.
    • Deleting an open file does not free its space; package installs in scripts use apt-get and pinned versions.

    Check your understanding

    You run sudo rm /var/log/app/debug.log (13 GB), but df -h still shows the disk 100% full. Why?

    rm removes the directory entry. The data stays allocated while any process holds an open descriptor. lsof +L1 finds it; restart the process or truncate the file instead.

    nginx logs "connect() failed (111: Connection refused) while connecting to upstream 127.0.0.1:8080". Which command checks the most likely cause?

    "Connection refused" means no process is listening on that address and port. ss shows listening sockets and, with sudo, which process owns each.

    What does chmod 640 config.yaml allow?

    Each digit is a sum of r = 4, w = 2, x = 1, for owner, group and others in that order: 6 = rw-, 4 = r--, 0 = ---.

    What is the difference between kill 4242 and kill -9 4242?

    SIGTERM (15) is a request; well-behaved services finish in-flight work and exit. SIGKILL (9) cannot be caught or ignored, so nothing gets cleaned up.

    Which pipeline correctly lists the five IPs (first field) with the most requests in access.log?

    uniq -c only counts adjacent identical lines, so the input must be sorted first. Without the first sort, one IP appears many times with small counts.
