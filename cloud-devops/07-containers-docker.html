Containers & Docker

A container packages a program with everything it needs to run, so that the thing tested on a laptop is byte for byte the thing running in production. It is the unit that every later chapter deploys: pipelines build container images, registries store them, Kubernetes schedules them. This chapter is the operator's view. What an image is and what a container is, the docker run flags that decide how a container behaves, where its data lives and when that data disappears, how it is reached over the network, and how it differs from a virtual machine. The simulator runs one container through crashes, reboots and redeployments so that you can see what each flag is for.

Images and containers

Two words are used loosely and mean different things.

  • An image is a file system and some settings, frozen. It holds the program, its libraries, a minimal set of operating system files, and metadata: which command to start, which port it listens on, which environment variables it expects. An image is read-only and is identified by a name and a tag, such as postgres:17, or exactly by a content hash. Chapter 8 builds them and Chapter 9 stores them.
  • A container is a running instance of an image: one ordinary Linux process (sometimes a few) that the kernel has given its own view of the file system, the network and the process list, and a limit on the memory and CPU it may use. On top of the image's read-only files it gets a thin writable layer of its own.

The relationship is the one between a program on disk and a running process, or a class and an object. One image can be running as a hundred containers. Stopping a container does not change its image, and nothing a container writes ever goes back into the image.

Docker is the tool most people meet first, and it is not the only one. The image format and the way a container is started are open standards (the Open Container Initiative), so an image built with Docker runs under containerd, which is what Kubernetes uses, or Podman, without change.

The docker run flags that matter

Everything about how a container behaves is fixed when it is created. To change a published port or a volume you remove the container and run a new one, which is why real deployments keep the command in a file (a Compose file, a Kubernetes manifest) and not in someone's shell history.

Volumes: where the data lives

A container's writable layer is scratch space. It survives a stop and a start, and it is deleted with the container. Since every deployment of a new version removes the old container and runs a new one, anything that must outlive a deployment has to be stored outside it.

A volume still lives on one machine. Across a fleet, state belongs in a managed database or object storage (Chapter 4), and the containers themselves should be stateless.

Container networking

Each container gets its own network interface and a private IP address on a virtual network inside the host. Three consequences decide most container networking questions.

  • localhost inside a container is the container. An application that connects to localhost:5432 is looking for a database inside its own container, not on the host and not in the neighbouring container.
  • Containers on the same user-defined network find each other by name. Docker runs a small DNS server for each network you create, so db resolves to the database container's address. The default network does not do this, which is the reason to always create one.
  • Publishing a port is how the outside gets in. -p 8080:80 tells the host to forward its port 8080 to the container's port 80. By default it listens on every interface of the host and is inserted ahead of the host's usual firewall rules. For something that only a local reverse proxy should reach, publish on loopback: -p 127.0.0.1:8080:80.
$ docker network create shop
$ docker run -d --name db  --network shop --env-file db.env -v pgdata:/var/lib/postgresql/data postgres:17
$ docker run -d --name web --network shop -p 127.0.0.1:8080:80 -e DATABASE_HOST=db ghcr.io/acme/web:4.18.2

$ docker exec web getent hosts db              # name resolution between containers
172.18.0.2      db
$ curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/healthz
200

The database has no -p at all. Only web needs to reach it, and web does so over the shop network; nothing outside the host can connect to it.

Simulator: one container, many bad days

A small service runs in a container. It keeps records under /var/lib/app, listens on port 80 and uses about 80 MB of memory. Choose its flags, write a few records, then make things go wrong. Changing a flag removes the container and runs a new one, exactly as it would on a real host.

The behaviour follows Docker's documented rules. A manual docker stop is respected by every restart policy. After the Docker daemon restarts (a reboot), unless-stopped starts containers that were not stopped by hand and on-failure starts nothing. A container that exceeds its memory limit is killed with exit code 137. The writable layer survives stop, start and reboot, and is deleted by docker rm. "Deploy again" keeps the same flags, as a new version of the image would.

Things to try.

  • With no flags at all, write three records, then docker stop and docker start: the three records are still there. Reboot the host: the container is not started (it shows as exited), and after docker start it still has three. Now press "Deploy again": zero. The writable layer survives everything except removal, and removal is what every deployment does.
  • Choose the named volume and repeat. Three records before the deployment, three after. The data never was in the container.
  • Crash the app under each restart policy. With no it stays at "exited 1" until a person starts it. With on-failure it is back at once, but reboot the host and it stays down, because that policy does not act when the daemon starts. With unless-stopped it comes back after the crash and after the reboot. Then stop it by hand and reboot: it stays stopped, which is the point of the name.
  • The memory leak shows why the two flags belong together. No limit: the container grows to 400 MB and nothing stops it. A limit and no policy: the kernel kills it (exit 137) and the service is down. A limit and unless-stopped: it is killed and restarted every time, the host is protected and the service keeps answering. The restart counter climbing is then the thing to alert on.
  • "curl it" under each port setting. No published port: refused from the host and from outside. -p 8080:80: reachable from both. -p 127.0.0.1:8080:80: reachable from the host only, which is what you want behind a reverse proxy.

Containers and virtual machines

Both give a program an isolated place to run, and they do it at different levels. A virtual machine imitates hardware: it boots its own kernel and a full operating system. A container is a process on the host's kernel, isolated by features of that kernel. The OS course covers virtual machines and the kernel features behind containers; what matters for operating them is the trade.

Virtual machineContainer
Isolated byA hypervisor; each has its own kernelThe host's kernel, shared by all containers
ContainsA whole operating systemThe application and its libraries
SizeGigabytesMegabytes to a few hundred
Starts inTens of seconds to minutesAbout as long as the process takes to start
How many per hostTensHundreds
Strength of the boundaryStrong: an escape needs a hypervisor bugWeaker: a kernel bug or a careless flag such as --privileged can cross it
Can run another OSYes: Windows on a Linux hostNo: Linux containers need a Linux kernel
Patched byUpdating inside the machine, or replacing its imageBuilding a new image and replacing the container

They are layers, not rivals. In a cloud your containers run on virtual machines: the provider uses the hypervisor boundary between customers, and you use containers to pack and ship your own software inside it. Where strangers' code must be isolated in containers, platforms add a small virtual machine around each one.

It also helps to say what a container is not. It is not a small server: you do not log in to patch it, you replace it. It is not a place to keep data. And "it runs in a container" is not a security statement by itself, least of all when the process inside is root.

🚢
Use case: Google and two billion containers a week

Containers looked new when Docker appeared in 2013, but the kernel features underneath came largely from Google's own needs. Google engineers contributed control groups, the mechanism that limits a group of processes' CPU and memory, to the Linux kernel in 2007, because the company wanted to pack many jobs onto each machine without one starving another. By 2014 Google said publicly that everything it ran, from search to Gmail, ran in containers, and that it was starting about two billion of them a week under its cluster manager, Borg. The reasons it gave are the reasons in this chapter. An image that carries its own dependencies runs the same on any machine in the fleet. Limits make it safe to put a batch job next to a latency-sensitive service. And containers that hold no state can be killed and started elsewhere at will, which is what lets a scheduler repair and rebalance a cluster without asking anyone. What Docker added in 2013 was not the isolation but the packaging: a simple image format, a registry to share images, and one command to run them. Kubernetes, which Google released in 2014, is the descendant of Borg and the subject of Chapter 11.

⚠️
Common mistakes
  • Data in the writable layer. It works until the first redeployment removes the container.
  • No restart policy on a service, or no memory limit, so one leak takes the host down with it.
  • Connecting to localhost to reach another container or the host. Use the container's name on a shared network.
  • Publishing a database port to the world with -p 5432:5432. A published port listens on every interface and is not stopped by the host's usual firewall rules.
  • Treating a container like a server: logging in with docker exec to install a fix. The fix is gone at the next deployment. Change the image.
  • Ignoring SIGTERM. If the application does not shut down on the signal, every stop takes ten seconds and ends in a kill, dropping open requests.
  • Running as root with --privileged or with the Docker socket mounted. Either one gives the container control of the host.
  • Assuming a container is a virtual machine when judging isolation between tenants.

Interview drill

Explain it simply: What is the difference between an image and a container, and between a container and a virtual machine?

How a strong answer sounds
An image is a read-only package: the application, its libraries and a minimal file system, plus settings such as the start command. A container is a running instance of an image, an ordinary Linux process that the kernel isolates with namespaces and limits with cgroups, with a thin writable layer on top. One image can run as many containers. A virtual machine virtualises hardware and boots its own kernel and operating system, so it is larger, slower to start and more strongly isolated. A container shares the host's kernel, so it starts as fast as the process does and many more fit on a host, at the price of a weaker boundary. In practice containers run inside virtual machines and the two solve different problems.

Deeper: A container keeps restarting. docker ps shows "Restarting (137)". How do you investigate?

How a strong answer sounds
137 is 128 plus 9, so the process was killed with SIGKILL, and the usual cause is the memory limit. I would confirm with docker inspect, which has an OOMKilled field, and with the kernel log on the host, which records the kill. I would also read docker logs for the last lines before each death and check docker stats or the monitoring history for memory climbing to the limit. If it is out of memory, there are two possibilities. The limit may simply be too low for the workload, for example a JVM whose heap setting is larger than the container's limit, in which case I fix the application's memory settings or raise the limit. Or the application leaks, in which case the limit is doing its job by protecting the host, and the fix is in the code; the restart policy is keeping the service partly available in the meantime. If OOMKilled is false, something else sent the kill: a health check, an orchestrator, or a stop that timed out because the application ignores SIGTERM. I would also check that the restart loop is not hiding a start-up failure, such as a missing environment variable, by running the image once in the foreground.

🧠 Key takeaways

  • An image is a read-only package; a container is a running process started from it, with a writable layer of its own.
  • A container lives as long as its main process. Exit code 137 means killed, most often for exceeding a memory limit.
  • Flags are fixed at creation: changing one means removing the container and running a new one.
  • The writable layer survives stop and reboot and is deleted on removal. Put state in a volume, or better, outside the host.
  • Containers reach each other by name on a user-defined network; the outside gets in only through a published port.
  • A service needs a restart policy and a memory limit.
  • A container shares the host's kernel: lighter and faster than a virtual machine, and a weaker boundary.

Check your understanding

A container running a database has no volume. An engineer deploys a new image version with docker rm -f db followed by docker run. What happens to the data?

A container's writable layer belongs to that container and is removed with it. Only volumes and bind mounts outlive the container.

Two containers, web and db, are on the same user-defined network. Which address should web use for the database?

Docker's DNS resolves container names on a user-defined network. Inside a container, localhost is the container itself.

A container exits with code 137 and OOMKilled is true. What happened?

137 is 128 + 9, a SIGKILL. With OOMKilled set, the kernel's memory controller did it because the container went over its limit.

A service's container was started with --restart unless-stopped. An operator runs docker stop on it, and later the host reboots. Is the container running after the reboot?

That is the difference from always. Without the manual stop, the same policy would have started it after the reboot.

Which statement about containers and virtual machines is correct?

Sharing the kernel is what makes containers small and fast to start, and it is also why the boundary between them is weaker than a hypervisor's.
