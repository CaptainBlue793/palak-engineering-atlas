VPCs, Subnets & Security Groups

Every instance, database and Kubernetes node you create lives in a virtual network that you design. That network decides what can be reached from the internet, what can reach the internet, and which of your own machines may talk to each other. Most "it deployed but I can't connect" problems are one of six things in it: an address, a route, a gateway, a security group, a network ACL or an endpoint. This chapter builds the standard layout piece by piece, and the simulator traces a packet through it hop by hop so that you can see exactly where it is dropped.

The VPC and its address range

A virtual private cloud (VPC; a virtual network on Azure) is a private network inside one region that belongs to your account. Nothing gets in or out of it unless you add a way. You give it a block of private addresses in CIDR notation, for example 10.0.0.0/16, which is the 65,536 addresses from 10.0.0.0 to 10.0.255.255. Every resource you launch gets an address from that block.

You then cut the block into subnets. On AWS a subnet sits in exactly one availability zone, so a layout that survives a zone needs each kind of subnet once per zone. A common plan:

VPC  10.0.0.0/16                         65,536 addresses

  zone a     public   10.0.0.0/24           251 usable    load balancers, NAT gateway
             private  10.0.16.0/20        4,091 usable    application servers, Kubernetes nodes
             data     10.0.64.0/24          251 usable    databases
  zone b     public   10.0.1.0/24     private  10.0.32.0/20     data  10.0.65.0/24
  zone c     public   10.0.2.0/24     private  10.0.48.0/20     data  10.0.66.0/24

  unused     10.0.80.0 and upwards: room to add subnets later

Three rules save pain later. The provider keeps a few addresses in every subnet (five on AWS and Azure, four on Google Cloud), which is why a /24 has 251 usable addresses and not 256. Make the private subnets big: load balancers, functions and above all Kubernetes pods take addresses from them, and a subnet cannot be resized once it has things in it. And never reuse a range: two networks with overlapping addresses cannot be connected to each other, so give every VPC and every office network its own block from the start, even if joining them seems unlikely today.

Public and private subnets

"Public" and "private" are not settings on a subnet. They describe its route table:

  • A public subnet is one whose route table sends 0.0.0.0/0 (everything not in the VPC) to an internet gateway.
  • A private subnet is one whose route table has no such route. It may send 0.0.0.0/0 to a NAT gateway, so that its instances can start connections outwards, or have no route out at all.

To be reachable from the internet an instance needs two things: it must be in a public subnet, and it must have a public IP address. Being in a public subnet without a public address makes it unreachable from outside; having neither is how most things should be. The usual layout puts only the things that must face the internet (load balancers, NAT gateways) in public subnets and everything else in private ones. Your application servers are then reached through the load balancer and administered through a session manager or a bastion (Prerequisite 7), never directly.

Route tables, the internet gateway and NAT

Every subnet is associated with one route table, a list of "destination range → target" lines. For each packet leaving an instance, the VPC picks the most specific matching line (the longest prefix).

$ aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=subnet-0priv2a \
    --query 'RouteTables[].Routes[].[DestinationCidrBlock||DestinationPrefixListId,GatewayId||NatGatewayId,State]' --output text
10.0.0.0/16     local                    active     # inside the VPC: always present, cannot be removed
0.0.0.0/0       nat-0b2c4d6e8f0a1b2c3    active     # everything else: out through the NAT gateway
pl-7ca54015     vpce-0c3d5e7f9a1b2c3d4   active     # S3's address ranges: through a gateway endpoint

Two gateways do the work at the edge.

  • An internet gateway connects the VPC to the internet in both directions. It also translates one to one between an instance's private address and its public address: the instance itself only ever sees its private address. It has no capacity to manage and costs nothing.
  • A NAT gateway lets instances in private subnets start connections to the internet (to fetch packages, call an external API) without being reachable from it. It sits in a public subnet, has a public address of its own, and rewrites each outgoing connection to come from that address. Replies come back to it and are forwarded; unsolicited connections from outside match nothing and are dropped. It is zonal, so a resilient layout has one in each zone, and it is charged per hour and per gigabyte.

Security groups and network ACLs

Routes decide where a packet can go. Two kinds of firewall decide whether it is allowed to.

Security groupNetwork ACL
Attached toAn instance's network interfaceA subnet: every packet crossing its edge
StateStateful: replies to an allowed connection are allowed automaticallyStateless: each direction is checked separately, so replies need their own rule
RulesAllow only; anything not allowed is droppedAllow and deny, numbered, first match wins
Sources you can nameAddress ranges, or another security groupAddress ranges only
DefaultNo inbound, all outboundThe default one allows everything
Traffic inside one subnetCheckedNot checked
Use it forNearly everythingA coarse block at the subnet edge: denying an address range, or a compliance rule

The most useful feature in the table is naming a security group as a source. The database's group does not say "allow 10.0.16.0/20 on 5432"; it says "allow members of the application's group on 5432". The rule then follows the instances wherever autoscaling puts them, and a machine that merely lands in the same subnet gets nothing.

resource "aws_vpc_security_group_ingress_rule" "db_from_app" {
  security_group_id            = aws_security_group.db.id       # on the database's group...
  referenced_security_group_id = aws_security_group.app.id      # ...admit members of the application's group
  ip_protocol                  = "tcp"
  from_port                    = 5432
  to_port                      = 5432
}

Statelessness is what catches people with network ACLs. A client connects from a random high port (an ephemeral port, somewhere in 1024 to 65535) to port 443. The reply therefore travels from port 443 to that high port. A network ACL that allows "443 in and 443 out" lets the request in and drops every reply. The simulator has a switch for exactly this.

    The model follows AWS's rules: security groups are stateful and allow all outbound traffic by default, network ACLs are stateless and are checked at the edge of a subnet, the most specific route wins, and the route inside the VPC is always there. A NAT gateway's traffic passes the network ACL of the subnet it sits in. The private subnet keeps the default network ACL throughout.

    Things to try.

    • Switch on the custom network ACL and visit each connection. One rule set that looks reasonable ("443 in, 443 out") breaks three of the four, each at a different hop. Internet → web: the request gets in and the reply to port 51844 is dropped on the way out. Worker → internet: the request leaves and the reply to the NAT gateway's port 1027 is dropped on the way in. Web → database: the request to port 5432 never leaves the subnet. In two of the three the first packet got through, which is what makes stateless rules hard to debug.
    • Remove the internet gateway route (ACL back to default). Internet → web fails at step 7, not step 1: the request reaches the server, and it is the reply that has no route. A flow log on the server would show the connection accepted. Now look at Worker → internet: it fails too, although the private route table is untouched, because the NAT gateway can only get out if its own subnet is public.
    • Remove the NAT route. The worker's packet is dropped at the second step, inside its own subnet. Nothing else in the VPC is involved.
    • Worker → S3, with and without the endpoint. Through the NAT gateway the trace has 11 steps and passes the public subnet twice. With the gateway endpoint it has 5. Then break everything else: remove both default routes and switch on the custom ACL. S3 still works, because the endpoint's route is more specific than anything it replaced and the path never enters the public subnet.
    • Count what has to be right. Of the 128 possible switch settings, Internet → web works in 8. It needs a public address, a security group rule, a route and a permissive ACL all at once, and every one of the failures looks the same to the client: a timeout.

    Peering and endpoints

    A VPC is isolated from every other network until you connect it. These are the ways, from simplest to largest.

    ConnectionJoinsHow it worksKnow this
    VPC peeringTwo VPCs, in any region or accountA private link; each side adds routes for the other's rangeRanges must not overlap. Not transitive: if A peers with B and B with C, A cannot reach C
    Transit gatewayMany VPCs and on-premises networksA regional router that every network attaches to onceReplaces a mesh of peerings; billed per attachment and per gigabyte, and it is one shared component
    Gateway endpointA VPC and S3 or DynamoDBA route-table entry that sends the service's address ranges over the provider's networkNo charge. Removes that traffic from the NAT gateway's bill
    Interface endpoint (PrivateLink)A VPC and one service: the provider's APIs, or another company'sA network interface with a private address in your subnet; DNS for the service resolves to itBilled per hour and per gigabyte. Lets a subnet with no internet route call APIs
    VPN or dedicated lineA VPC and an office or data centreAn encrypted tunnel over the internet, or a private circuitAgain, the address ranges must not overlap

    Endpoints matter for two reasons. Security: a database subnet with no route to the internet can still write backups to object storage. Cost: an instance in a private subnet that moves a terabyte to S3 through a NAT gateway pays the NAT gateway's per-gigabyte charge on all of it, and through a gateway endpoint pays nothing for the path.

    🔀
    Use case: Slack, 4 January 2021, and a shared network hub

    On the first working day of 2021 Slack was degraded or down for several hours. Slack's own account of it starts in the network. The company had moved to many VPCs joined through AWS transit gateways, so traffic between its services, and to its monitoring systems, crossed that shared hub. As customers returned from the holiday, traffic rose sharply; the transit gateways did not scale up quickly enough and began to drop packets between VPCs. The loss made backend calls slow, which made the web servers' request queues grow, and the fleet began scaling in the wrong direction on misleading signals and then trying to add many instances at once, which overloaded the provisioning system. Because the dashboards and alerting were reached across the same gateways, the engineers were working partly blind. AWS engineers increased the gateways' capacity by hand, and Slack wrote that the gateways would in future be scaled up before that week. The lessons are about this chapter's last table: a hub that every network attaches to is convenient and is also one component whose trouble is felt everywhere at once, and the tools you need during an incident should not depend on the thing most likely to be broken.

    ⚠️
    Common mistakes
    • Overlapping address ranges. Every VPC created as 10.0.0.0/16, and then two of them need to be connected.
    • Subnets too small. A /24 for Kubernetes nodes runs out of addresses long before it runs out of anything else.
    • Everything in public subnets with public IPs, because it "just worked". Databases and application servers belong in private subnets.
    • 0.0.0.0/0 on port 22 or on a database port. Bots find an open port within minutes.
    • Forgetting that network ACLs are stateless. Allowing a port in and not the ephemeral ports out drops every reply.
    • One NAT gateway for three zones. When its zone fails, the private subnets in the other two lose their way out.
    • Sending S3 traffic through NAT. A gateway endpoint is free and removes the per-gigabyte charge.
    • Security group rules by address range where a group reference would do: the rule goes stale when instances move.
    • Expecting peering to be transitive. A peered with B and B with C does not connect A to C.

    Interview drill

    Explain it simply: What is the difference between a public and a private subnet?

    How a strong answer sounds
    The route table. A public subnet's route table sends 0.0.0.0/0 to an internet gateway, so an instance there that also has a public IP address can be reached from the internet and can reach it. A private subnet has no route to the internet gateway. Its instances cannot be reached from outside at all; if they need to start connections outwards, the route table sends 0.0.0.0/0 to a NAT gateway that sits in a public subnet. I put load balancers and NAT gateways in public subnets and everything else, application servers and databases, in private ones.

    Deeper: An instance in a private subnet cannot reach an external API: the request times out. Walk me through finding the cause.

    How a strong answer sounds
    A timeout means packets are being dropped, not refused, so I follow the path out and back. First DNS: does the name resolve from the instance? Then the instance's security group: outbound is open by default, but someone may have restricted it. Then the private subnet's route table: there must be a 0.0.0.0/0 route to a NAT gateway, and the NAT gateway must be in the available state. Then the NAT gateway's own subnet: it has to be a public subnet, meaning its route table has 0.0.0.0/0 to an internet gateway; a NAT gateway placed in a private subnet is a common cause. Then the network ACLs on both subnets, in both directions, remembering they are stateless: the reply from the API comes back to an ephemeral port on the NAT gateway, so the public subnet's ACL must allow inbound 1024 to 65535. If all of that is right, I check whether the far end allow-lists source addresses, since it sees the NAT gateway's public address. To confirm rather than guess I would read the VPC flow logs for the instance's and the NAT gateway's interfaces, or run the provider's reachability analysis on the path.

    🧠 Key takeaways

    • A VPC is a private address block in one region, cut into subnets that each sit in one zone. Plan ranges so that they never overlap.
    • A subnet is public only because its route table points 0.0.0.0/0 at an internet gateway.
    • The internet gateway gives two-way access to instances with public addresses; a NAT gateway gives private instances outbound-only access.
    • Security groups are stateful, allow-only and can name other groups. Network ACLs are stateless, numbered and sit at the subnet edge.
    • A dropped packet shows as a timeout. Check address, route out, security groups, network ACLs both ways, route back, then the host.
    • Peering joins two VPCs and is not transitive; endpoints reach provider services without the internet or NAT.

    Check your understanding

    What makes a subnet "public"?

    Public and private describe the route table. A subnet whose default route points at an internet gateway is public; its instances still need public IP addresses to be reachable.

    A network ACL on a web server's subnet has two rules: allow inbound TCP 443, allow outbound TCP 443. Clients on the internet time out. Why?

    The reply leaves from port 443 towards a high port such as 51844. A network ACL does not remember the connection, so outbound 1024 to 65535 must be allowed explicitly.

    An instance in a private subnet needs to download operating system updates from the internet and must not be reachable from it. What does it need?

    A NAT gateway allows connections that start inside and their replies, and nothing that starts outside. A route straight to the internet gateway does nothing for an instance without a public address.

    Why is "allow 5432 from the application's security group" better than "allow 5432 from 10.0.16.0/20"?

    A group reference follows membership. Autoscaled instances are covered automatically, and another machine placed in the same subnet is not.

    VPC A is peered with VPC B, and B is peered with C. Can an instance in A reach an instance in C through B?

    A peering connection carries traffic only between its two VPCs. That limit is the reason transit gateways exist.
