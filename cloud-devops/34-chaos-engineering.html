Chaos Engineering

Every system has weaknesses its builders do not know about: a missing timeout, a fallback that was never exercised, a runbook that points at a dashboard which no longer exists. They will be found. The only choice is whether they are found at three in the morning during an outage, or on a Tuesday afternoon by an engineer who caused the failure deliberately, was watching for the result and could stop it in seconds. Chaos engineering is the second option done with discipline. This chapter covers the experimental method, how to keep an experiment from becoming an incident, the tools that inject faults, and game days, which test the people as well as the machines. The simulator lets you design an experiment and see what it finds, and what it costs.

  • State a chaos experiment as a hypothesis about a measurable steady state
  • Limit blast radius with scope, duration and automatic abort conditions
  • Explain why some weaknesses only appear in production, under real load
  • Choose a fault type that matches a real failure, and know that slow is different from down
  • Inject faults with Kubernetes-native tools and a service mesh
  • Plan and run a game day, and turn its findings into fixes

The method

Chaos engineering is the practice of running controlled experiments on a system to find out how it behaves when something fails. The word "chaos" is misleading. Nothing about it is random or reckless. It is the scientific method applied to operations, and each experiment has the same five parts.

A test checks something you already know should be true: this function returns that value. An experiment asks a question you cannot answer by reading the code: what really happens to checkout when a dependency three calls away slows down? In a system of any size nobody holds the whole thing in their head, so those questions have to be asked of the running system.

Two conditions come first. You need observability good enough to see the steady state and to tell the experiment group from the control. And you should fix what you already know is broken. Injecting a fault you know the system cannot survive teaches nothing and causes an outage with a purpose statement attached.

# experiment: recommendations-slow.yaml  (the write-up comes before the fault)
hypothesis:    Checkout success stays at or above 99.5% when recommendations responds in 2 s.
steady_state:  checkout success rate and p99 latency, experiment pods against control pods
fault:         2 s of added latency on calls from checkout to recommendations
scope:         1 checkout pod in 10; production; Tuesday 14:00, team present
duration:      10 minutes
abort_if:      checkout success below 98% for 30 s on the experiment pods   # automatic
rollback:      delete the fault object; effect ends within seconds
owner:         team-checkout; announced in #incidents beforehand

Blast radius

The blast radius of an experiment is the most harm it can do if the hypothesis turns out to be false. Controlling it is what separates an experiment from an outage, and there are three controls.

  • Scope. Affect the smallest slice that can show the effect: one pod, one host, one per cent of requests, one cell. Widen it only after the hypothesis has held at the smaller size.
  • Duration. Every fault has an end time written into it. A fault that needs a person to remember to remove it will one day be left in place.
  • Abort conditions. A rule, checked by a machine, that ends the experiment the moment the steady state is breached. A human watching a dashboard reacts in minutes; an alarm wired to the fault reacts in seconds.

The middle rows explain why practitioners insist on production. Staging has a trickle of synthetic traffic, smaller machines, different timeouts and none of production's history. A whole class of failures, queues filling, thread pools running out, caches going cold, needs load to appear at all. An experiment that passes in staging has shown the code path works. It has not shown the system survives.

Ordinary good manners apply as well. Run experiments in working hours with the owning team present. Announce them. Do not run them during an incident, a release freeze or the busiest hour of the year. And never run one on a team that has not agreed to it.

Tools

The first widely known tool was Netflix's Chaos Monkey (2011), which terminated random production instances during office hours so that every service had to tolerate losing one. Today's tools inject many more kinds of fault, and on Kubernetes the fault is an object like any other: declared in YAML, limited by selectors, removed when its duration ends.

# Chaos Mesh: 2 s of latency from one checkout pod in ten to recommendations, for ten minutes
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata: { name: recommendations-slow, namespace: shop }
spec:
  action: delay
  mode: fixed-percent
  value: "10"                                  # the scope: 10% of the pods the selector matches
  selector: { namespaces: [shop], labelSelectors: { app: checkout } }
  direction: to
  target:
    mode: all
    selector: { namespaces: [shop], labelSelectors: { app: recommendations } }
  delay: { latency: "2s", jitter: "200ms" }
  duration: "10m"                              # the fault removes itself
# A service mesh can inject the same fault per request, with no extra tool (Chapter 27)
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: recommendations, namespace: shop }
spec:
  hosts: [recommendations]
  http:
    - fault:
        delay: { fixedDelay: 2s, percentage: { value: 10 } }      # or: abort: { httpStatus: 503, ... }
      route: [{ destination: { host: recommendations } }]

Other common choices: LitmusChaos (also Kubernetes-native), Gremlin (a commercial service with a safety-focused interface), and the cloud providers' own AWS Fault Injection Service and Azure Chaos Studio, which can fail managed resources such as a database instance or a zone's network, and which stop automatically when a chosen alarm fires. The tool matters less than the experiment design. A kubectl delete pod with a hypothesis and a dashboard is chaos engineering. An expensive platform firing faults nobody watches is not.

Game days

Automated experiments test the software. A game day tests the whole response: the alerts, the dashboards, the runbooks and the people. A team sets aside a few hours, one person plays the part of the failure, and everyone else responds as they would to the real thing.

The cheapest version needs no fault at all. In a tabletop exercise someone describes an outage aloud and the on-call engineer talks through what they would do, opening the real dashboards and runbooks as they go. It takes an hour, risks nothing and reliably finds gaps. It is also the best way to train new people for on-call (Chapter 38) and to rehearse the roles of incident response (Chapter 37).

A sensible path for a team starting out: tabletop exercises first; then one small experiment in staging to learn the tooling; then the same experiment in production at the smallest scope with an automatic abort; then widen, and schedule the ones that held to run continuously so that a later change cannot quietly break them.

Production serves 1,000 checkouts a second; staging has a trickle of synthetic traffic and no customers. The hypothesis is "checkout success stays at or above 99.5%". Without a timeout, a slow dependency holds each request's thread for two seconds: under production load the pod runs out of threads and every request on it fails, while under staging's trickle the requests are merely slow. For comparison, the same weakness met in a real outage is taken as every pod affected for 45 minutes.

Things to try.

  • The starting experiment makes recommendations return errors, in staging. The hypothesis holds, and the team goes home reassured. The system has a fallback and no timeout, so the fault that would hurt it was never tried.
  • Change the fault to "responds in 2 seconds", still in staging. The hypothesis holds again, wrongly: success stays at 100% because nothing is under load. The only clue is the latency, 2,250 ms.
  • Move it to production, one pod in ten, automatic abort. Refuted in 30 seconds, at a cost of 3,000 failed checkouts. The same weakness met in a real outage costs 2,700,000, nine hundred times as many.
  • Now run it on every pod with no abort. The finding is identical and the cost is 600,000. Scope and abort conditions change the price of the knowledge, not the knowledge.
  • Set the truth to "timeout, no fallback". Either fault finds it, and staging is enough, at no cost. Functional gaps do not need load. Do the cheap experiments first.
  • Set the truth to "timeout and fallback" and run the slow fault in production. It holds, with p99 at 550 ms: the 300 ms timeout plus normal work. That number is evidence you did not have before.
  • Of the 72 experiments, 36 hold, 30 find a weakness and 6 pass wrongly. All six are the slow fault against the missing timeout, run in staging. The production findings cost between 3,000 and 600,000 failed checkouts, for the same two lessons.

Use case: Google's DiRT, and the failures that were not technical

Since 2006 Google has run an annual company-wide exercise called DiRT, for Disaster Recovery Testing. For several days, teams across the company respond to large simulated disasters. An early scenario was an earthquake that cut the headquarters in California off from the rest of the world: the offices, the people in them and the systems hosted nearby were all declared unavailable, and everyone else had to keep the company running. Faults are injected for real where that is safe, and the exercise is planned by a central team that keeps an "abort" authority throughout. The published accounts of those early years, by the engineers who ran them, are instructive because of what failed. The software failovers largely worked, since they were tested often. The surprises were around them. Teams discovered that an emergency communication plan depended on a system in the affected location. A conference bridge set up for the response could not hold everyone who needed to join. Approval for an unusual emergency purchase had to come from someone who, in the scenario, was unreachable. People who had never been told they were the backup for a critical role found out during the test. None of this would appear in a load test or a code review. It is why game days exist. The technical system is one part of what keeps a service running; the rest is people, authority and communication, and those can only be tested by acting the disaster out.

⚠️
Common mistakes
  • No hypothesis. "Let's break something and see" produces an outage and a shrug.
  • No automatic abort. The experiment is then as long as someone's attention.
  • Starting with a large scope, or in production before the tooling has been learnt somewhere safe.
  • Testing only "down" and never "slow". Fast errors exercise fallbacks. Slowness exercises timeouts, and missing timeouts cause the worst outages.
  • Trusting a pass in staging for a weakness that needs load to show.
  • Measuring the wrong steady state: CPU and memory looked fine while checkouts failed.
  • Injecting a fault you already know will break things. Fix it first.
  • Running experiments on other teams' services without their agreement.
  • Finding weaknesses and not fixing them. The value is in the repair and the re-run.
  • One-off experiments. A property that held in March can be broken by a change in May. Automate the ones that matter.
  • Game days that test only the system, with the on-call engineer told in advance what will fail and where to look.

Interview drill

Explain it simply: What is chaos engineering, and how is it different from testing?

How a strong answer sounds
Chaos engineering is running controlled experiments on a system, ideally in production, to learn how it behaves when something fails. You define a steady state from a user-facing metric, form a hypothesis that it will hold under a specific fault, inject that fault into a small part of the system with an automatic abort, and compare against a control group. A test verifies something already known: given this input, expect that output. An experiment explores something not known, typically how many components interact under failure, load and real configuration, which nobody can work out from the code. If the hypothesis holds you have evidence in place of an assumption. If it does not, you have found a weakness cheaply and on your own schedule. The important disciplines are a small blast radius, a defined end and stop condition, and actually fixing what is found.

Deeper: How would you introduce chaos engineering in a company that has never done it and is nervous about it?

How a strong answer sounds
I would treat the nervousness as correct and design around it. First, the prerequisites: there has to be a user-facing metric we trust and dashboards that can separate an experiment group from the rest. If we cannot see the steady state, the first project is observability. Then I would start with something that injects no fault at all: a tabletop exercise with one willing team, talking through a realistic outage against their real runbooks. That usually finds several gaps in an hour and costs nothing, which builds appetite. Next, one small experiment chosen with that team, on a failure they believe they handle, such as killing a single pod or adding latency to an optional dependency. We write the hypothesis, scope, duration and abort condition down first, run it in staging to learn the tool, then in production on one pod with an automatic stop, in office hours, announced. Whatever the result, we publish it: either "we now have evidence" or "we found this and fixed it before customers did". Stories like that do more than any policy. From there I would widen gradually, more fault types, more teams, larger scopes, and put the experiments that matter on a schedule so regressions are caught. Throughout I would keep some rules fixed: nothing without the owning team's consent, nothing during incidents or peak periods, an abort on every experiment, and every finding ends as a ticket with an owner. And I would be clear with leadership about the trade: we are choosing to meet these failures at a time and size of our choosing, since the alternative is meeting them anyway.

🧠 Key takeaways

  • An experiment is a steady state, a hypothesis, one injected fault, a comparison and a fix.
  • Both results are useful: evidence that it holds, or a weakness found on your own schedule.
  • Blast radius is controlled by scope, duration and an automatic abort condition.
  • Some weaknesses need production load to appear. A pass in staging proves the code path, not the system.
  • Slow is different from down. Test latency as well as errors.
  • On Kubernetes, faults are declared objects with selectors and durations; a mesh can inject them per request.
  • Game days and tabletop exercises test alerts, runbooks, access and people, which is where much of the surprise is.

Check your understanding

What should be written down before any fault is injected?

Without a hypothesis and a defined steady state the result cannot be interpreted, and without scope and abort rules the experiment can become an outage.

Checkout has a fallback for when recommendations fails, but no timeout on the call. Which fault reveals the weakness?

A fast error triggers the fallback. A slow response holds the request open, and with no timeout the fallback never runs.

An experiment passes in staging. Why might the same weakness still exist in production?

Queues, pools and caches behave differently under real load and real configuration. Staging shows that a path works, not that the system survives.

Which control limits an experiment's harm fastest when the hypothesis turns out to be wrong?

A machine-checked stop condition ends the fault in seconds. People take minutes, and reviews happen afterwards.

What does a game day test that an automated fault injection does not?

A game day exercises the human response end to end, which is where many of the surprises turn out to be.
