Ingress & Load Balancing

A Service gives pods a stable address, but only inside the cluster. Users are outside. Getting their requests in takes a chain of pieces: a DNS name, a cloud load balancer, a reverse proxy running in the cluster that understands hostnames and paths, a certificate, and finally the Service and its pods. Each piece fails with its own symptom, so someone who knows the chain can usually name the broken link from the status code alone. This chapter walks the chain: the Service types that open a door, Ingress and the controllers that implement it, certificates that renew themselves, and the Gateway API that is replacing Ingress.

NodePort and LoadBalancer

A Service's type decides how far its address reaches. Each type builds on the one before.

TypeReachable fromHowUse it for
ClusterIP (default)Inside the cluster onlyA virtual IP that each node forwards to the ready podsEverything that only other services call
NodePortAnything that can reach a node's IPThe same port (from 30000 to 32767) is opened on every node and forwarded to the ServiceRarely on its own: it is the building block for the next type
LoadBalancerThe internet, or a private networkThe cloud controller creates a cloud load balancer that forwards to the nodes or straight to the podsExposing one service, especially non-HTTP ones: a database proxy, MQTT, the ingress controller itself
 
apiVersion: v1
kind: Service
metadata: { name: edge, namespace: ingress }
spec:
  type: LoadBalancer
  selector: { app: edge-proxy }
  ports:
    - { name: https, port: 443, targetPort: 8443 }

$ kubectl get svc edge -n ingress
NAME   TYPE           CLUSTER-IP     EXTERNAL-IP     PORT(S)         AGE
edge   LoadBalancer   10.96.118.20   203.0.113.80    443:31724/TCP   12d

A LoadBalancer Service works at layer 4: it forwards connections and knows nothing about hostnames, paths or cookies. Giving every HTTP service its own would mean a cloud load balancer, a public address, a certificate and a monthly charge per service. The usual design therefore has one LoadBalancer Service, in front of a reverse proxy that runs in the cluster and does the layer-7 routing for everything else. That proxy is the ingress controller.

Ingress and ingress controllers

An Ingress is an object that holds routing rules: for this hostname and this path, send the request to that Service. It is only data. An ingress controller is the program that makes the data true: a reverse proxy (Traefik, HAProxy, an Envoy-based proxy, NGINX) with a small controller that watches Ingress objects and rewrites the proxy's configuration. Cloud providers also offer controllers that configure their own layer-7 load balancer instead of a proxy in the cluster. A cluster has no ingress controller until you install one, and an Ingress that no controller claims is silently ignored.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt        # see the next section
spec:
  ingressClassName: traefik                             # which controller should act on this
  tls:
    - hosts: [shop.example.com, "*.shop.example.com"]
      secretName: shop-tls                              # a Secret of type kubernetes.io/tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - { path: /,      pathType: Prefix, backend: { service: { name: web,  port: { number: 80 } } } }
          - { path: /api,   pathType: Prefix, backend: { service: { name: api,  port: { number: 8080 } } } }
          - { path: /login, pathType: Exact,  backend: { service: { name: auth, port: { number: 80 } } } }
    - host: "*.shop.example.com"
      http:
        paths:
          - { path: /, pathType: Prefix, backend: { service: { name: tenant-router, port: { number: 80 } } } }

The matching rules are short and worth knowing exactly, because "why did my request go there?" is a daily question.

  • Host first. An exact host wins over a wildcard. A wildcard such as *.shop.example.com matches exactly one extra label: admin.shop.example.com, but neither shop.example.com nor a.b.shop.example.com.
  • Prefix paths match whole path segments. /api matches /api, /api/ and /api/orders. It does not match /apiary.
  • Exact paths match one string. /login does not match /login/.
  • The longest matching path wins, and at equal length Exact beats Prefix. The order in the file does not matter.
  • No match means the controller's default backend answers, normally with a 404.

Anything beyond host and path (rewrites, timeouts, rate limits, authentication) is not in the Ingress API. Each controller added its own annotations for those, so an Ingress written for one controller often does not behave the same on another. That gap is the main reason the Gateway API exists. A note on history, because older material assumes it: the community ingress-nginx controller was for years the default choice, and the Kubernetes project retired it in 2026. The Ingress API itself remains supported and receives no new features.

    Matching follows the Kubernetes Ingress specification: an exact host before a wildcard, a wildcard for one label only, Prefix by whole path segments, Exact by the whole string, the longest match first and Exact before Prefix at equal length. Every hostname is assumed to resolve to the cluster's load balancer. A request whose host matches no rule is answered by the controller's default backend.

    Things to try.

    • Step through the listed requests with everything switched on. /api/orders/812 goes to api; /apiary goes to web, because a prefix matches whole segments. /login goes to auth, and /login/ goes to web, because Exact means exact. admin.shop.example.com matches the wildcard; a.b.shop.example.com does not, and fails earlier than you might expect: at the certificate.
    • Remove the ingressClassName. Over HTTP every request returns 404; over HTTPS every request gets a certificate error. The Ingress object is still there and looks correct. Nothing is reading it.
    • Remove the Secret. Every HTTPS request stops at the handshake with the controller's self-signed certificate. No rule is consulted, which is why a certificate problem never shows up as a status code.
    • Take the api Service's endpoints away. /api/orders/812 returns 503 and the home page still returns 200. One Service without ready pods breaks its own paths and nothing else.
    • Switch the redirect off and request http://shop.example.com/cart. It works, in plain text. With the redirect on, the answer is a 308 before any path is looked at.
    • Type your own URLs. The matcher was checked against a separately written statement of the rules on 4,000 random requests, across every combination of the four switches, and agreed on all of them.

    TLS with cert-manager

    The ingress controller normally terminates TLS: it holds the certificate, decrypts the request, and speaks plain HTTP (or a second, internal TLS connection) to the pods. The certificate and its private key live in a Secret of type kubernetes.io/tls, named by the Ingress. The operational problem is that certificates expire, and a renewal that depends on someone remembering will be forgotten. cert-manager is the controller that removes the person. You tell it once how to obtain certificates, and it creates, stores and renews them.

    apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: { name: letsencrypt }
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: platform@example.com
    privateKeySecretRef: { name: letsencrypt-account }
    solvers:
      - http01: { ingress: { ingressClassName: traefik } }

$ kubectl get certificate -n shop
NAME       READY   SECRET     AGE
shop-tls   True    shop-tls   41d
$ kubectl describe certificate shop-tls -n shop | grep -E 'Not After|Renewal Time'
  Not After:     2026-11-25T09:14:02Z
  Renewal Time:  2026-10-26T09:14:02Z

    Two things still need a human eye. Alert on certificates that are close to expiry anyway, because automation fails quietly: a changed DNS record, a firewall rule or a rate limit at the authority, and the renewal stops working weeks before anyone notices. And remember what the challenge needs: with HTTP-01, the name must already point at the cluster and port 80 must be reachable.

    The Gateway API

    The Gateway API is the successor to Ingress, stable since 2023 and implemented by most current controllers. It fixes the two weaknesses of Ingress. Features that needed annotations (header matching, redirects, rewrites, traffic splitting by weight, timeouts) are part of the API, so a route means the same thing on any implementation. And one object is split into several, matched to who should own each.

    IngressGateway API
    ObjectsOne: Ingress (plus an IngressClass)GatewayClass: which implementation. Gateway: the listeners, ports and certificates. HTTPRoute: hosts, matches and backends
    Who writes themThe application team writes all of it, certificates includedThe platform team owns the Gateway; each application team owns its own routes, in its own namespace
    Routing featuresHost and path. Everything else through controller-specific annotationsHeaders, methods, query parameters, redirects, rewrites, weights and mirroring, in the standard
    ProtocolsHTTP and HTTPSAlso gRPC, TLS passthrough, TCP and UDP routes
    Across namespacesNot addressedA Gateway states which namespaces may attach routes to it
    StatusSupported, with no new featuresWhere new work happens
     
    apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: api, namespace: shop }
spec:
  parentRefs: [{ name: public, namespace: ingress }]     # attach to the platform team's Gateway
  hostnames: [shop.example.com]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api } }]
      backendRefs:
        - { name: api,        port: 8080, weight: 90 }
        - { name: api-canary, port: 8080, weight: 10 }   # 10% of requests to the new version

    The weights in the last two lines are a canary release written as plain configuration, which Chapter 17 builds on. For a new cluster, start with the Gateway API. You will still meet Ingress in most existing ones.

    🚪
    Use case: "IngressNightmare", 2025

    In March 2025 researchers at the security firm Wiz published a set of vulnerabilities in ingress-nginx, then the most widely deployed ingress controller, and named them IngressNightmare. The most serious, CVE-2025-1974, was rated 9.8 out of 10. The controller includes a component that checks new Ingress objects before they are accepted, by building a test configuration from them. An attacker able to send a crafted object to that component could inject configuration and get code running inside the controller's pod, without any credentials. That pod is an unusually good place to land: to serve TLS for any application, the controller is normally allowed to read Secrets in every namespace, so taking it over could mean taking the cluster's secrets with it. Wiz estimated that over 40% of cloud environments ran a vulnerable version, and found thousands of clusters where the checking component was reachable from the internet. Patches were released the same day. The lesson for this chapter is about what an ingress controller is: the one component that is exposed to the internet by design and also holds broad permissions inside. It deserves the fastest patching in the cluster, the narrowest permissions it can work with, and internal endpoints that only the API server can reach. When the project was retired the following year, its maintainers gave the difficulty of keeping such a flexible design safe as one of their reasons.

    ⚠️
    Common mistakes
    • A LoadBalancer Service for every application. One cloud load balancer and certificate each, where one ingress would do.
    • No ingressClassName, or the wrong one: the Ingress exists and no controller acts on it.
    • Assuming /api matches /apiary, or that /login matches /login/. Prefix works on segments; Exact on the whole string.
    • Reading a 503 as "the ingress is broken". It means the route matched and no pod is ready. Look at the Service's endpoints.
    • Certificates renewed by hand, or renewed automatically with no alert on expiry.
    • Controller-specific annotations copied between clusters that run different controllers.
    • An unpatched, over-privileged ingress controller. It is the most exposed component you run.
    • Losing the client's address. Behind a proxy the application sees the proxy's IP; use the forwarded headers, and only trust them from your own proxy.
    • Ignoring shutdown. A pod that exits before the proxy stops sending to it produces 502s on every rollout.

    Interview drill

    Explain it simply: What is the difference between a Service of type LoadBalancer and an Ingress?

    How a strong answer sounds
    A LoadBalancer Service asks the cloud provider for a load balancer that forwards connections to one Service. It works at layer 4, so it suits any protocol, and it costs one cloud load balancer per Service. An Ingress is a set of layer-7 rules, hostnames and paths mapped to Services, implemented by an ingress controller, which is a reverse proxy running in the cluster. Many applications share that one proxy, one external load balancer and one place where TLS is terminated. The two work together: the ingress controller itself is exposed through a single LoadBalancer Service. For new designs the Gateway API replaces Ingress, with the same idea split into Gateway and route objects.

    Deeper: Users report that https://shop.example.com/api/orders returns 503, while the home page works. How do you find the cause?

    How a strong answer sounds
    The home page working tells me DNS, the load balancer, TLS and the controller are fine, and that the problem is specific to the /api route. A 503 from the proxy, as opposed to a 404, means a rule matched and the proxy found no backend to send to. So I go to the Service behind that path. First kubectl get endpointslices for it: if the list is empty, either no pod matches the Service's selector or none is ready. Then the pods: are they running, are they failing their readiness probe, did a rollout just replace them with a version that never becomes ready, or were they scaled to zero? kubectl describe and the events answer that. If the endpoints list is not empty, I check that the Ingress names the right Service and port and that the Service's targetPort matches what the container listens on, though a wrong port more often shows as a 502. I would also look at the controller's own logs for that request, which usually say "no endpoints available" in so many words, and check whether a 503 with a body from the application, not the proxy, means the application itself is shedding load. The fix depends on which it is, and in the common case it is a readiness problem in the API pods, not anything in the ingress.

    🧠 Key takeaways

    • ClusterIP is internal; NodePort opens a port on every node; LoadBalancer adds a cloud load balancer in front, at layer 4.
    • An Ingress is routing data; an ingress controller is the proxy that obeys it. One external load balancer serves many applications.
    • Host, then path: exact host before wildcard, longest path first, Prefix by segments, Exact by the whole string.
    • 404 means no rule matched, 503 no ready endpoints, 502 the pod connection failed, 504 the pod was too slow.
    • cert-manager obtains and renews certificates by proving control of the name. Alert on expiry all the same.
    • The Gateway API standardises what Ingress left to annotations and splits ownership between platform and application teams.
    • The ingress controller is internet-facing and privileged: patch it first.

    Check your understanding

    An Ingress has two paths for one host: / (Prefix) to web and /api (Prefix) to api. Which Service receives a request for /apiary/list?

    Prefix matching is by segment. /api matches /api and /api/… only, so the request falls to the / rule.

    An Ingress was applied successfully, DNS is correct, and every request returns 404 from the proxy. The Ingress has no ingressClassName and the cluster has no default class. What is happening?

    An Ingress is only data. Without a class that a controller watches, it is ignored, and the proxy answers from its default backend.

    Requests to one path return 503 from the ingress while other paths work. What does that point to?

    No rule would be a 404, and DNS or certificate problems would affect every path. A 503 is "I know where this should go and nobody is there".

    How does a certificate authority using the HTTP-01 challenge verify that you control shop.example.com?

    Serving the token proves that whoever asked can answer for that name. cert-manager adds a temporary route for it through the ingress controller.

    Which statement describes the Gateway API correctly?

    Platform teams own Gateways (listeners and certificates); application teams attach routes with matching, redirects and traffic weights defined in the standard.
