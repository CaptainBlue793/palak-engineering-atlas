Writing Good Dockerfiles

A Dockerfile is the recipe for an image, and the difference between a careless one and a careful one is large: a build that takes ten seconds or two minutes on every commit, an image of 250 MB or 1.9 GB, a process that runs as root or as nobody, a secret that stays on the build machine or ships to everyone who pulls. None of it needs cleverness. It needs an understanding of layers and the build cache, and five habits: order instructions by how often they change, build in one stage and ship from another, choose a small base, drop root, and keep the build context clean. The simulator builds one application under each choice and shows the time, the size and what leaked.

  • Explain how instructions become layers and when the build cache is reused
  • Order a Dockerfile so that a code change does not reinstall dependencies
  • Write a multi-stage build that leaves the toolchain out of the final image
  • Choose between full, slim, Alpine, distroless and scratch base images
  • Run the container as a non-root user
  • Use .dockerignore and build secrets so that nothing private ends up in a layer

A Dockerfile, instruction by instruction

A Dockerfile is a list of instructions that docker build carries out from top to bottom, starting from a base image. Here is a first attempt for a Node.js service. It works, and nearly every line of it can be improved.

FROM node:22                    # the base image: Debian with Node.js 22
WORKDIR /app                    # create the directory and make it the working directory
COPY . .                        # copy the build context (this directory) into the image
RUN npm ci                      # run a command inside the image and save the result
RUN npm run build
EXPOSE 8080                     # documentation: the port the service listens on
CMD ["node", "dist/server.js"]   # the process a container starts
$ docker build -t ghcr.io/acme/web:4.18.2 .        # the dot is the build context: the files COPY can see
$ docker history ghcr.io/acme/web:4.18.2           # one line per layer, newest first
IMAGE          CREATED BY                              SIZE
5d0c1e9f7a22   CMD ["node" "dist/server.js"]           0B
<missing>      EXPOSE map[8080/tcp:{}]                 0B
<missing>      RUN /bin/sh -c npm run build            2.1MB
<missing>      RUN /bin/sh -c npm ci                   348MB
<missing>      COPY . .                                481MB
<missing>      WORKDIR /app                            0B
<missing>      /bin/sh -c #(nop)  CMD ["node"]         0B      # ...and the base image's own layers below

The CMD is written as a JSON list on purpose. In that form the program is started directly and is process 1 in the container, so it receives the SIGTERM that docker stop sends. Written as a plain string, CMD node dist/server.js, it is started through a shell, the shell is process 1, and the application never hears the signal.

Layers and the build cache

Every instruction that changes the file system (FROM, COPY, ADD, RUN) produces a layer: an archive of the files that instruction added, changed or deleted. An image is a stack of layers, and a container sees them merged into one file system. Two consequences follow at once.

  • Layers only add. Deleting a file in a later instruction hides it and does not shrink the image; the bytes are still in the earlier layer, and anyone with the image can extract them. That is true of a 500 MB download you removed, and of a secret you removed.
  • Layers are shared. Ten images built on the same base store and download that base once.

The builder also keeps every layer it has made, and reuses one when it can prove the result would be the same. That is the build cache, and its rule is short:

So the order of instructions decides how much work a small change causes. In the first attempt, COPY . . comes before npm ci. Editing any source file changes the checksum of that copy, the cache misses there, and all the dependencies are downloaded and installed again, although none of them changed. The fix is to copy first only what the expensive step needs:

FROM node:22
WORKDIR /app
COPY package.json package-lock.json ./     # changes rarely
RUN npm ci                                 # cached until a dependency changes
COPY . .                                   # changes on every commit
RUN npm run build
CMD ["node", "dist/server.js"]

The general rule: order instructions from what changes least to what changes most. The same pattern exists for every language: copy go.mod and go.sum before the Go source, requirements.txt before the Python source, pom.xml before the Java source.

Multi-stage builds

Building software needs compilers, package managers and development dependencies. Running it does not. A multi-stage build uses several FROM lines in one Dockerfile: early stages do the building, and the last stage starts from a clean base and copies in only the finished result. Everything else is thrown away.

# ---- stage 1: build ----
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/checkout ./cmd/checkout

# ---- stage 2: what actually ships ----
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/checkout /checkout
USER nonroot
ENTRYPOINT ["/checkout"]

The build stage is several hundred megabytes of Go toolchain. The image that ships is the base plus one binary, around 15 to 20 MB, with no shell, no package manager and no compiler in it.

Base images

The FROM line decides most of the image's size and most of what a vulnerability scanner will find in it, because every package in the base is a package you now ship and must keep patched.

Sizes are approximate and change with every release. Three habits apply to any base. Pin the version: node:22.11-slim and not node:latest, so that a build next month uses what was tested (Chapter 9 goes further and pins by digest). Use official or verified images, not something an unknown account uploaded. And rebuild regularly: an image built once and left for a year carries a year of unpatched vulnerabilities in its base, whatever your own code does.

Running as non-root

Unless told otherwise, the process in a container runs as root. It is root restricted by the container's isolation, but it shares a kernel with the host, and every known container escape is far more damaging when the process inside was root. Root can also write anywhere in the container's file system, which is what an attacker who gets in wants. Dropping it takes two lines:

FROM node:22-slim
WORKDIR /app
COPY --chown=node:node package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --chown=node:node dist ./dist
USER node                                  # everything from here on, and the running process, is not root
CMD ["node", "dist/server.js"]

Many official images already contain an unprivileged user (node, nginx, nonroot in distroless). Where there is none, create one with RUN useradd --system --uid 10001 app and use the number: USER 10001. Kubernetes can then verify that the image does not run as root (Chapter 36). Depending on the runtime, a non-root process may not be allowed to listen on ports below 1024. That does not matter: listen on 8080 and let the published port or the load balancer present it as 80.

.dockerignore and build secrets

The build context is the directory you pass to docker build. All of it is sent to the builder, and COPY . . copies all of it into a layer. In a typical repository that includes .git, a local node_modules, test output and a .env file with real credentials. A .dockerignore file, with the same syntax as .gitignore, leaves them out:

# .dockerignore
.git
node_modules
dist
.env*
*.md
Dockerfile
.dockerignore

That makes builds faster, keeps secrets out of the image, and improves caching, since a change to the README or a new commit in .git no longer invalidates the COPY.

Sometimes a build really does need a secret, such as a token for a private package registry. Do not pass it with ARG or ENV, and do not COPY it in and delete it afterwards: all three leave it readable in the image's layers or history. Mount it for the one instruction that needs it:

# in the Dockerfile: the file exists only while this RUN executes and is never written to a layer
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci

# on the command line
$ docker build --secret id=npmrc,src=$HOME/.npmrc -t ghcr.io/acme/web:4.18.2 .

Things to try. The panel opens on the first attempt from the top of the chapter, after one source file has changed.

  • The starting point: 73 seconds, 4 of 6 instructions run again, a 1,932 MB image, and .env and .git inside it. One changed line of code reinstalled every dependency.
  • Reorder the instructions. The same change now builds in 28 seconds: npm ci stays cached and only the copy and the compile run.
  • Change "only the README". Still 28 seconds, and 73 with the first ordering, because the README is part of what COPY . . copies. Switch on the .dockerignore: 0.2 seconds and nothing runs. The same switch shrinks the image from 1,932 to 1,462 MB and the context from 482 MB to 2.
  • Go multi-stage and step through the bases. With node:22 as the final base the image is 1,192 MB; with the slim base 322 MB; with distroless 252 MB. Most of an image is its base. The build for a source change is 21 seconds.
  • Multi-stage without the .dockerignore. The credentials no longer reach the image that ships, because only two directories are copied across. They were still sent to the builder and sit in the build stage's cache. Treat the two measures as two layers of defence and keep both.
  • The changes you cannot avoid. A new dependency costs 68 seconds whatever you do, and an updated base image about 100, because everything is built on it. Good ordering does not make those cheaper. It makes them rare.
  • End to end: from 73 seconds, 1,932 MB, root and a leaked .env, to 21 seconds, 252 MB, an unprivileged user and nothing private inside, without changing a line of the application.

Use case: Codecov, 2021, and a credential in an image

Codecov makes a coverage tool that thousands of companies ran inside their CI pipelines by downloading a shell script, the "Bash Uploader". In April 2021 Codecov disclosed that the script had been altered by an attacker since the end of January. According to the company's account, the way in was its own Docker image: an error in how the image was built allowed the attacker to extract a credential from it, and that credential gave write access to the storage bucket the script was served from. The modified script added one line that sent the environment variables of every CI job running it to a server the attacker controlled. CI environments are full of secrets, such as cloud keys, repository tokens and signing keys, so for about two months each of those pipelines was handing its credentials over. A customer noticed only because the checksum of the downloaded script did not match the one published. The start of the chain is this chapter: something secret was reachable in an image's layers, and an image should be treated as public from the moment it is built. The rest of the chain, downloading and running unpinned code in a pipeline, is the subject of Chapter 29.

⚠️
Common mistakes
  • COPY . . before installing dependencies. Every code change reinstalls everything.
  • Deleting in a later layer. RUN rm secret.key or RUN rm -rf /var/cache hides the files; they are still in the layer that added them. Clean up in the same RUN, or use a separate stage.
  • Secrets through ARG, ENV or COPY. All are readable from the image. Use a secret mount.
  • No .dockerignore. .git, .env and a local node_modules go into the context and often into the image.
  • Shipping the build stage. Compilers and development dependencies in production: larger, slower to pull and more to patch.
  • Running as root because nothing said otherwise.
  • FROM something:latest. The build is no longer repeatable, and a base update arrives unannounced.
  • Shell-form CMD. The application is not process 1 and never receives SIGTERM.
  • apt-get update in its own RUN. That layer is cached for months, and the later apt-get install uses a stale package list. Put both in one instruction.

Interview drill

Explain it simply: Why does the order of instructions in a Dockerfile matter?

How a strong answer sounds
Each instruction produces a layer, and the builder caches layers. It reuses a cached layer only if the instruction is unchanged, the files a COPY brings in are unchanged, and every layer above it was also reused. So the first instruction that differs, and everything after it, runs again. If I copy the whole source tree before installing dependencies, any code change invalidates the copy and the install runs again from scratch. If I copy only the dependency manifests first, install, and copy the source afterwards, a code change reuses the installed dependencies and only the last steps run. The rule is to order from least frequently changed to most frequently changed.

Deeper: A service's image is 1.4 GB and each build takes ten minutes. What do you change?

How a strong answer sounds
I would look before changing anything: docker history shows which layers are large, and the build log shows which steps run instead of coming from the cache. For size, the usual causes are a full distribution as the base, build tools and development dependencies in the final image, and an unfiltered build context. So: a multi-stage build that compiles in one stage and copies only the output and production dependencies into a slim or distroless final stage, a .dockerignore that removes .git and local dependency directories, and clean-up in the same instruction that created the mess. That commonly takes an image from over a gigabyte to a couple of hundred megabytes, which also shortens every pull during deployment and scaling. For time, I reorder so that dependency manifests are copied and installed before the source, so that a normal commit reuses that layer. In CI the runner usually starts with an empty cache, so I would also export and import the build cache through the registry or the CI system's cache, and use cache mounts for the package manager's download directory. While I am there I would pin the base image, add a non-root user and check that no secret is passed as a build argument. Then measure again: build time on a one-line change, and image size.

🧠 Key takeaways

  • Each file-changing instruction makes a layer. Layers only add: deleting later does not remove bytes or secrets.
  • The cache is reused until the first instruction or copied file that differs; everything after that runs again.
  • Copy dependency manifests and install before copying the source. Order from least to most frequently changed.
  • Multi-stage builds keep compilers and development dependencies out of the image that ships.
  • A smaller, pinned base means less to download and less to patch. Rebuild regularly to pick up fixes.
  • Add a USER. Root in a container is still root on a shared kernel.
  • .dockerignore and secret mounts keep private files out of the context and out of the layers.

Check your understanding

A Dockerfile has COPY . . followed by RUN npm ci. A developer changes one line in one source file and rebuilds. What happens to the npm ci layer?

The builder cannot know that npm ci would produce the same result. It only knows that the layer above changed, so it runs every later instruction again.

A Dockerfile copies a private key in one instruction and removes it with RUN rm key.pem two instructions later. Is the key in the image?

Layers only add. A later deletion records "this file is hidden" in a new layer; the earlier layer still contains the bytes.

What is the main benefit of a multi-stage build?

Only the last stage becomes the image. Earlier stages can be as large and messy as the build needs, because nothing from them ships unless you copy it across.

Why add USER 10001 near the end of a Dockerfile?

Containers share the host's kernel. An unprivileged user inside the container is the cheapest reduction of that risk, and platforms can enforce it.

A repository has no .dockerignore and its Dockerfile uses COPY . .. Which problem does this not cause?

Signal handling depends on the form of CMD or ENTRYPOINT, not on the build context. The other three are direct results of an unfiltered context.
