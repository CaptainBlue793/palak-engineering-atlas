Multi-Region Deployments

Running in more than one region is the most expensive reliability decision a team makes, and the one most often made for the wrong reason. It protects against exactly one thing, the loss of a region, and it brings new ways to fail: traffic that goes to the wrong place, data that disagrees with itself, and surviving regions that fall over under the load they inherit. This chapter is about operating such a system: how users are steered between regions, what the managed global databases actually promise, what has to be true for a failover to work on the day, and how cells limit the damage of every other kind of failure. The simulator takes a region away and shows what happens to the others.

Why multi-region

There are three honest reasons to run in several regions.

  • Surviving the loss of a region. Rare, but it happens to every provider, and for some businesses hours of downtime are not acceptable.
  • Latency. A user in Sydney talking to a server in Virginia waits about a quarter of a second per round trip, before any work is done. The only fix is a server nearer the user.
  • Law. Some data must stay inside a country or a region.

And there is a set of costs that should be stated just as plainly. The compute bill rises by half or doubles. Data transfer between regions is charged (Chapter 31). Every data store needs a replication story. Every deployment, secret, alert and runbook now exists several times. Most important of all: the commonest cause of outages is a team's own change, and a change deployed to every region at once breaks every region at once. Multiple regions do nothing for that unless the rollout is staged.

Global load balancing

Something has to send each user to a region, and take a region out when it is unhealthy. There are two mechanisms.

DNS-based steering answers the name lookup differently for different users. The provider's DNS service offers routing policies: latency (the region with the fastest path from the user's resolver), geolocation (by the user's country, for data-residency rules), weighted (a percentage split, for gradual migrations) and failover (a primary and a backup). Each record can be tied to a health check, and an unhealthy region simply stops being given out.

resource "aws_route53_health_check" "london" {
  fqdn              = "london.api.example.com"
  type              = "HTTPS"
  resource_path     = "/healthz"
  request_interval  = 30
  failure_threshold = 3                               # 3 failures 30 s apart: about 90 s to notice
}

resource "aws_route53_record" "api_london" {
  zone_id         = aws_route53_zone.main.zone_id
  name            = "api.example.com"
  type            = "A"
  set_identifier  = "london"
  health_check_id = aws_route53_health_check.london.id
  latency_routing_policy { region = "eu-west-2" }
  alias {
    name                   = aws_lb.london.dns_name
    zone_id                = aws_lb.london.zone_id
    evaluate_target_health = true
  }
}   # and one more record per region, with the same name

DNS steering is simple and works with anything. Its weakness is the cache. Every answer carries a lifetime (the TTL), and until it expires, resolvers and clients keep using the old address. A 60-second TTL means a failover takes effect for most users within a couple of minutes. Some clients, and some long-lived connection pools, hold addresses far longer than the TTL says.

Anycast steering avoids the cache. The service has one IP address, announced from many locations, and the network delivers each packet to the nearest healthy one (AWS Global Accelerator, and the global load balancers of Google Cloud and Cloudflare, work this way). Taking a region out changes routing inside the provider's network within seconds, and no client has to look anything up again.

One caution about health checks. If the check in every region depends on the same thing, say a shared login service, then one failure marks every region unhealthy and the steering layer has nowhere to send anyone. Keep regional health checks about the region, and configure the steering to fail open: when everything looks unhealthy, send traffic anyway.

Data replication

Stateless services are easy to run in many regions. The data is where the decisions are, and the managed global databases have each made a different one.

Whichever you choose, three things become operational duties. Replication lag is a signal to graph and alert on, because it is the data you would lose right now (Chapter 24). Users notice inconsistency at the edges: someone who writes in one region and is then routed to another may not see their own change, so keep a user on one region for the length of a session where you can. And requests will be repeated across a failover, so writes need the idempotency keys covered in the Distributed Systems course's chapter on retries.

Regional failover

A failover plan has one property that matters more than its speed: it must still work while the provider is having a bad day. That leads to the idea of static stability: when a region fails, the others carry on without anything having to change.

Cloud services have two parts. The data plane does the work: running instances serve requests, load balancers forward them, DNS answers queries. The control plane makes changes: launching instances, editing records, creating load balancers. Data planes are built to be far more robust, and during large incidents the control plane is the part that struggles, because every customer is trying to launch capacity somewhere else at once. A plan that says "when the region fails, we scale up the other one" depends on the control plane at its worst moment. A statically stable plan has the capacity already running.

The capacity sum is simple and frequently got wrong. With N regions sharing traffic equally, losing one multiplies the load on each survivor by N / (N − 1). For the survivors to cope, each region must normally run below (N − 1) / N of its capacity: under 50% with two regions, under 67% with three. Three regions at 60% cost less than two at 45% and are just as safe, which is one reason large systems use three. Run hotter than the limit and the failover does not save you: the surviving regions are pushed past their capacity, and an overloaded service does less useful work than a busy one, because it spends its effort on requests that time out before they finish.

Regions are also the last and largest stage of a rollout. A change goes to one region, is watched for long enough to see problems, and only then goes to the next (Chapter 17). This is the only way multiple regions protect you from your own changes. Chapter 44 studies an incident in which control planes and global dependencies decided who stayed up.

Cell-based architecture

Regions limit the damage of a place failing. Cells limit the damage of everything else. A cell is a complete, independent copy of the service: its own servers, queues and databases, serving a fixed subset of customers. In front of the cells sits a thin router that knows which customer lives in which cell and does nothing else.

  • Blast radius. A bad deployment, a poisoned request, a full disk or a runaway customer takes out one cell. With twenty cells, that is 5% of customers and not all of them.
  • Deployment. Changes roll out one cell at a time, so the first cell is a canary with real traffic and a hard wall around it.
  • Scale. A cell has a maximum size, and you test at that size. Growth means adding cells, not making an untested giant.

The costs are real. Anything that spans cells (a search across all customers, moving a customer from one cell to another) needs special machinery. The router is shared by everyone, so it has to be simple enough to be near-perfect. And cells cost a little more than one pooled fleet. AWS builds its own services this way and describes the pattern publicly. Slack moved to a cellular design by availability zone after incidents in which one zone's trouble spread to the whole service, and Salesforce has long placed each customer on a named instance, which is why its outages are reported per instance.

Health checks take 90 seconds to declare the region dead. With DNS, the failed region's users move over evenly as their cached answers expire; with anycast they move at once. A region loaded beyond its capacity loses useful output in proportion: at 120% load it completes 80% of its capacity, at 150% half, at 200% nothing. Extra capacity, when it can be added, is requested at detection and arrives 10 minutes later.

Things to try.

  • The starting design is two regions at 60%, which sounds comfortable. When one fails the other is asked for 120% of its capacity. With extra capacity arriving after ten minutes, 13.5% of all requests in the half-hour fail and normal service returns after 11.5 minutes.
  • Now impair the control plane, as happens in large incidents. No capacity arrives, 34.1% of requests fail and the service does not recover within the half-hour. The surviving region completes only 67% of what it receives.
  • Lower the regions to 45%. Only 3.5% of requests fail and service is normal after 2.5 minutes, with or without the control plane. This is static stability, and it costs capacity equal to 222% of the traffic.
  • Three regions at 60% give 2.3% and 2.5 minutes, for capacity equal to 167% of the traffic. Safer and cheaper than two regions at 45%, because each survivor takes only half of the lost region's load.
  • Switch to anycast: 1.7% and 90 seconds, which is the detection time and nothing else. A five-minute TTL gives 4.5%.
  • Two regions at 80%, control plane impaired: 73% of requests fail. The survivor is asked for 160% and completes a quarter of what it receives. One region's outage has become everyone's.
  • Set a one-hour TTL on any stable design: 25.8% of requests fail with three regions and 38.7% with two, because more than half of the failed region's users are still being sent there when the half-hour ends.

Use case: Netflix and the seven-minute evacuation

On Christmas Eve 2012 a fault in a load-balancing service in one AWS region stopped Netflix streaming for many customers on one of the busiest viewing nights of the year. Netflix ran in that one region. Over the following year it rebuilt the service to run actively in several regions at once, with customer data replicated between them, so that any region could serve any customer. The company then did the part most organisations skip: it practised. It regularly moved all traffic out of a healthy region on purpose, in production, to prove that the others could carry it. Those exercises exposed the real bottleneck, which was the one this chapter's simulator shows. Steering users away was quick. Making the remaining regions big enough to receive them was slow, because scaling up hundreds of services took most of an hour, and the old process started that scaling only after the decision to evacuate. In 2018 Netflix described a project that cut the evacuation from about 45 minutes to under ten. The main change was to stop depending on scaling in the moment: capacity for the failover was kept in a state that could take traffic almost immediately, and the long chain of steps was reduced to a few. The lesson is the order of operations. A failover is as fast as its slowest dependency, that dependency is usually capacity, and the only way to find out is to evacuate a region on a day when nothing is wrong.

⚠️
Common mistakes
  • Going multi-region before being good at one region. It multiplies whatever operational weakness you already have.
  • Running each of two regions at 70%. The survivor would need 140% of its capacity.
  • A failover plan that begins with "scale up". It depends on the control plane during the incident.
  • Deploying to all regions at the same time. Your own change is then a global outage.
  • A hidden single-region dependency: the identity provider, the CI system, the image registry, a feature-flag service, a control-plane API that lives in one region.
  • Long DNS TTLs on names you intend to fail over, and clients that never look the name up again.
  • Health checks that share a dependency, so every region turns unhealthy together. Fail open.
  • Not watching replication lag. You find out how much data you lost afterwards.
  • Last-writer-wins with data that cannot afford to lose a write, such as balances or stock counts.
  • Never evacuating a region on purpose. The first test is then the real event.
  • A cell router that does real work. It is the one thing every cell shares; keep it trivial.

Interview drill

Explain it simply: What is static stability?

How a strong answer sounds
A system is statically stable if it keeps working through a failure without needing to change anything. For regions, that means when one fails, the others already have the capacity running to take its traffic, and the traffic moves by health checks alone. Nothing has to be launched, reconfigured or approved. It matters because the parts of a cloud that make changes, the control planes, are the least reliable parts during a big incident: everyone is trying to launch capacity at once. The practical consequence is pre-provisioned headroom. With N regions, each must run below (N − 1)/N of capacity, so under half with two and under two-thirds with three. It costs money all year, and it is the difference between a failover that works and one that overloads the survivors.

Deeper: Your service runs active–active in two regions. During a real regional outage, the surviving region also went down. What do you investigate?

How a strong answer sounds
I would start from the timeline and look for which of four usual causes it was. First, capacity. What was each region's utilisation before the event? If they were above 50%, the survivor was asked for more than it had. I would check whether autoscaling tried to add capacity and how long that took, or whether it failed because the provider's control plane was also degraded, or because we hit a quota in that region. Second, the shape of the load. Failed requests are retried, so the survivor may have received more than double: I would look at retry rates, connection storms as clients reconnected, and cold caches, since the survivor had to serve keys it had never loaded. Third, shared dependencies. Was there something both regions used that lived only in the failed one, such as the primary database, an auth service or a configuration store? Did the database failover complete, and did the application in the surviving region find the new writer? Fourth, the steering. Did health checks mark the survivor unhealthy once it slowed down, leaving nowhere to send users? From that I would expect action items of a familiar kind: a utilisation ceiling that is enforced and alerted on, load shedding so that an overloaded region serves what it can and does not collapse, retry budgets and backoff in clients, removal or replication of the single-region dependency, fail-open steering, and then a scheduled evacuation exercise to prove it, because this outage was the first time the plan had been run.

🧠 Key takeaways

  • Multi-region protects against losing a region, helps latency and satisfies residency rules. It does not protect against your own changes unless rollouts are staged by region.
  • Steer with DNS policies and health checks, or with anycast to avoid cached answers. Fail open.
  • Managed global databases choose between one writer, last-writer-wins and synchronous agreement. Know which you bought.
  • Static stability: the capacity is already running and failover needs no control-plane call.
  • With N regions, run each below (N − 1)/N of capacity: 50% for two, 67% for three.
  • An overloaded survivor does less work, not more. Shed load before it collapses.
  • Cells give every failure a wall: one cell's customers, not everyone.
  • Evacuate a region on purpose, regularly. That is the only real test.

Check your understanding

A service runs in three regions with equal traffic. What is the highest utilisation each region can normally run at and still absorb the loss of one region?

Losing one of three multiplies each survivor's load by 3/2. To stay at or below 100%, each must normally be at or below 2/3.

Why is "scale up the other region when one fails" a weak failover plan?

Statically stable designs have the capacity running already, so the failover needs only the data plane.

What is the main advantage of anycast steering over DNS steering during a failover?

With anycast the routing changes inside the provider's network. With DNS, users keep the old address until their cached answer expires, and some clients keep it longer.

Two regions both accept writes to a table that resolves conflicts by "last writer wins". Two users change the same record in different regions within the same second. What happens?

Last-writer-wins keeps the write with the later timestamp. Neither user sees an error. It is fine for some data and dangerous for counters and balances.

A service is split into twenty cells. A deployment with a serious bug goes to the first cell. Roughly what share of customers is affected?

Each cell serves a fixed subset of customers and shares nothing with the others, so the damage stops at the cell's wall: one twentieth.
