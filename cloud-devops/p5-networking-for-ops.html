Networking for Operations

"The site is down" almost always turns into one of five questions: does the name resolve to the right address, can a connection reach the port, is anything listening there, does the TLS certificate check out, and what did the application answer? This chapter is the operator's toolkit for those questions: ports and bind addresses, the DNS records you will edit, TLS certificates and their expiry dates, and curl and dig as debugging instruments. How the protocols work inside is the Networks course's job; here we use them.

  • Explain ports, listening sockets, and why binding to 127.0.0.1 hides a service
  • Read and change A, AAAA, CNAME and TXT records, and plan around TTLs
  • Check a TLS certificate's names, chain and expiry from the command line
  • Tell "connection refused", "timed out", a TLS error and a 5xx apart, and what each points to
  • Use curl -v, --resolve and -w timings to find where a request fails or slows

Ports and bind addresses

An IP address gets a packet to a machine; a port (0 to 65535) gets it to one program on that machine. A server program asks the kernel to listen on an address and port; clients connect to it. Ports below 1024 traditionally need root, which is why web servers start as root to open port 443 and then drop privileges, and why containers usually listen on 8080 instead.

The bind address matters as much as the port, and it is behind a whole class of "works on my machine" bugs:

  • 127.0.0.1:8080 (localhost) accepts connections only from the same machine. Right for a database admin port or an app that sits behind a local proxy.
  • 0.0.0.0:8080 accepts connections on every network interface. Needed when anything outside the machine, including another container or a load balancer, must reach it.
$ sudo ss -ltnp
State  Local Address:Port   Process
LISTEN 0.0.0.0:443          users:(("nginx",pid=812,fd=6))     # reachable from outside
LISTEN 127.0.0.1:5432       users:(("postgres",pid=990,fd=5))  # local only, on purpose
LISTEN 127.0.0.1:8080       users:(("app",pid=4410,fd=7))      # local only: the load balancer can't reach it

Many frameworks default to 127.0.0.1 in development (Flask, Rails, Vite). Put that app in a container or behind a load balancer and every health check fails with "connection refused", although the app is running and curl localhost:8080 on the box works perfectly. The fix is a setting such as --host 0.0.0.0.

DNS records you will edit

DNS turns names into addresses. As an operator you rarely think about the resolution chain; you edit records in a hosted zone (Route 53, Cloud DNS, Cloudflare) and wait for caches. Five record types cover almost everything:

  • A maps a name to an IPv4 address; AAAA to an IPv6 address.
  • CNAME makes a name an alias of another name (www.shop.example.com → shop-lb-1234.eu-west-1.elb.amazonaws.com). A CNAME cannot sit at the zone apex (shop.example.com itself) next to other records, which is why DNS providers offer ALIAS or ANAME records for pointing an apex at a load balancer.
  • TXT holds text, used to prove domain ownership to certificate authorities and SaaS tools, and for email security (SPF, DMARC).
  • MX says where email for the domain goes; NS says which servers are authoritative for the zone.

Every record has a TTL (time to live, in seconds): how long resolvers may cache the answer. That number decides how fast a change takes effect. If the record had a TTL of 86,400, some clients will keep using the old address for up to a day after you change it. So for a planned migration you lower the TTL a day ahead (to 60 or 300), make the change, confirm, and raise it again.

$ dig +short shop.example.com                # what my resolver says now
203.0.113.10
$ dig +noall +answer shop.example.com @1.1.1.1   # ask a specific resolver; shows remaining TTL
shop.example.com.   3412   IN   A   203.0.113.10
$ dig +short shop.example.com @ns-1203.awsdns-22.org   # ask the authoritative server: the truth
198.51.100.20

When the authoritative answer and your resolver disagree, you are looking at a cache that has not expired. The second column of the full answer is the seconds left before it will.

TLS certificates

HTTPS servers present a certificate that says "this public key belongs to these names", signed by a certificate authority (CA) the client already trusts, usually through one or more intermediate certificates. A client accepts it only if three things hold: the chain leads to a trusted root, one of the certificate's Subject Alternative Names (SANs) matches the host name it connected to, and the current time is inside the validity period. Each of those fails in production regularly:

$ openssl s_client -connect shop.example.com:443 -servername shop.example.com </dev/null 2>/dev/null \
    | openssl x509 -noout -subject -ext subjectAltName -enddate
subject=CN = shop.example.com
X509v3 Subject Alternative Name:
    DNS:shop.example.com, DNS:www.shop.example.com
notAfter=Dec 30 23:59:59 2026 GMT                  # alert well before this date

-servername sends the host name in the handshake (SNI), which servers hosting several sites need in order to pick the right certificate; leave it out and you may be shown a different certificate and chase the wrong problem. Certificates from Let's Encrypt last 90 days, which forces automation: a tool such as certbot or cert-manager (Chapter 14) renews them, and monitoring alerts if any certificate is within 14 days of expiry, because automation fails too.

Debugging with curl

curl is the operator's universal client. Four flags do most of the work:

# -v: show DNS, connect, TLS and headers, i.e. where it fails
$ curl -v https://shop.example.com/health
*   Trying 198.51.100.20:443...
* Connected to shop.example.com (198.51.100.20) port 443
* SSL connection using TLSv1.3 / TLS_AES_128_GCM_SHA256
> GET /health HTTP/2
< HTTP/2 200

# --resolve: test the new server under the real name BEFORE changing DNS
$ curl -sS --resolve shop.example.com:443:198.51.100.20 https://shop.example.com/health

# -w: where does the time go?
$ curl -o /dev/null -sS -w 'dns %{time_namelookup}  connect %{time_connect}  tls %{time_appconnect}  first-byte %{time_starttransfer}  total %{time_total}\n' https://shop.example.com/
dns 0.004  connect 0.021  tls 0.048  first-byte 0.912  total 0.915

The timings are cumulative from the start. In that example DNS, TCP and TLS together took 48 ms and the server then thought for 864 ms before sending the first byte, so the slowness is in the application, not the network. --resolve is the safe way to verify a migration: it connects to the new IP while sending the real host name for SNI and the Host header, exactly as browsers will after the DNS change.

Use case: the certificate nobody owned

On 3 February 2020, Microsoft Teams was unavailable for several hours because an authentication certificate had expired, and Microsoft said so publicly. Expiry outages like this hit large companies every year because the certificate was issued by hand, the person who set the reminder left, and nothing alerted. The operational fix is boring and effective: issue certificates automatically (ACME with Let's Encrypt or a cloud certificate manager), monitor the expiry date of every certificate an external probe can see, and page when one is under 14 days.

⚠️
Common mistakes
  • Binding to 127.0.0.1 in a container, then debugging the load balancer for an hour.
  • Changing a DNS record with a one-day TTL and expecting it to take effect now. Lower the TTL a day before.
  • Testing a new server by IP (curl https://198.51.100.20): wrong SNI and Host header, so you see a certificate error that users will never see. Use --resolve.
  • Reading "refused" and "timed out" as the same thing. Refused means a host answered; timed out means something dropped the packets.
  • curl -k in scripts to "fix" certificate errors: it turns off verification permanently and hides the real problem.
  • No expiry monitoring for certificates, including internal ones and the ones on load balancers.

Interview drill

Explain it simply: What is the difference between "connection refused" and "connection timed out"?

How a strong answer sounds
Refused means the packet reached the host and its kernel replied with a TCP reset because nothing is listening on that port, so I look at the server: is the process running, on which port and address (ss -ltnp)? Timed out means no reply came back at all, which usually means a firewall or security group silently dropped the packet, a routing problem, or a wrong IP. So refused sends me to the service, timeout sends me to the network path.

Deeper: You are moving shop.example.com to a new load balancer tomorrow. How do you do it with no downtime?

How a strong answer sounds
Today: check the current TTL and lower it to 60–300 seconds so caches turn over quickly; make sure the new load balancer has a valid certificate covering every name, including www; and test the new path end to end with curl --resolve shop.example.com:443:<new-ip>, which uses the real name for SNI and Host. Tomorrow: change the record, keep the old load balancer serving until its traffic drains (watch its request count fall to near zero, allowing for clients that ignore TTLs), then decommission it and raise the TTL again. Rollback is just changing the record back, which is fast because the TTL is short.

🧠 Key takeaways

  • A service must listen on the right port and address: 0.0.0.0 to be reachable, 127.0.0.1 for local only.
  • A, AAAA, CNAME, TXT and MX cover most DNS work; TTL decides how long old answers live, so lower it before a change.
  • A certificate must chain to a trusted root, list the host name in its SANs, and be in date; automate renewal and monitor expiry.
  • Refused points at the server; timeout points at the network path; TLS errors at the certificate; 5xx at what sits behind the proxy.
  • curl -v, --resolve and -w timings, plus dig and openssl s_client, answer most "it is down" questions.

Check your understanding

An app works with curl localhost:8080 on its server, but the load balancer's health check gets "connection refused". What is the most likely cause?

Refused means the host answered with a reset: nothing listens on that address for outside connections. A security group would cause a timeout, not a refusal.

You changed an A record an hour ago, but some users still reach the old server. The record's TTL was 86,400. What is happening?

Caches keep an answer until its TTL runs out. Lower the TTL at least one old-TTL period before a planned change.

Which command tests a new server under the real host name before the DNS change?

--resolve pins the name to that IP for this request, so SNI and the Host header are correct. Connecting by IP gives the wrong certificate, and -k hides errors.

curl -w reports: connect 0.020, tls 0.045, first-byte 1.310, total 1.320. Where is the time going?

Timings are cumulative. Connection and TLS were done by 45 ms; the wait until the first byte is server processing time.

Browsers show "certificate is not valid for www.shop.example.com" while shop.example.com works. What should you check?

A certificate is valid only for the names in its SAN list. Reissue it with both names (or a wildcard).
