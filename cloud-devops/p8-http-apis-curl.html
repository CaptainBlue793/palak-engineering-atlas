HTTP APIs & curl

Everything in the cloud is an API call. The console's buttons, aws and kubectl commands, Terraform providers and CI pipelines all send HTTP requests to an API and read the answer. When one of them fails, you get a status code and a JSON error, and the fastest way to understand it is to make the same call yourself. This chapter covers methods and status codes from an operator's angle, tokens and headers, the curl flags you will use, and the two habits that make automation safe: retrying the right errors and making writes idempotent.

  • Pick the right HTTP method, and know which ones are safe to retry
  • Read status codes: 401 vs 403, 404, 409, 422, 429 and the 5xx family
  • Send authenticated JSON requests with curl, and fail on HTTP errors
  • Handle rate limits with Retry-After and backoff
  • Make a POST safe to retry with an idempotency key

Methods and what they promise

Most cloud APIs are REST-style: URLs name resources (/v1/deployments/dep_812) and the HTTP method says what to do with them. What matters to an operator is not the theory but two promises each method makes, because they decide whether automation may retry it blindly:

  • Safe: does not change anything. GET and HEAD are safe, so you can call them as often as you like.
  • Idempotent: doing it twice has the same effect as doing it once. PUT (replace this resource with this body) and DELETE are idempotent: a retried PUT writes the same thing again; a retried DELETE finds it already gone.
  • POST (create something new, or trigger an action) is neither. If a POST /deployments times out and you send it again, you may get two deployments, and you cannot tell from the timeout whether the first one happened. PATCH (change some fields) is not guaranteed to be idempotent either.

The single most useful distinction is 4xx versus 5xx: 4xx means "you asked wrong, asking again will not help", 5xx means "we failed, it may work later". Retrying a 400 a hundred times is how a broken script becomes a self-inflicted rate limit.

curl for APIs

TOKEN="$(cat ~/.config/deployctl/token)"            # never paste tokens into commands that land in history

# GET with a bearer token; -f fails on HTTP errors, -sS is quiet but still shows errors
$ curl -fsS -H "Authorization: Bearer $TOKEN" https://api.example.com/v1/deployments?service=checkout | jq '.items[0]'

# POST JSON (--json sets the body and both Content-Type and Accept headers; curl 7.82+)
$ curl -sS --fail-with-body -X POST https://api.example.com/v1/deployments \
    -H "Authorization: Bearer $TOKEN" \
    -H "Idempotency-Key: $(uuidgen)" \
    --json '{"service":"checkout","version":"4.18.2"}'

# Just the status code, for scripts
$ curl -s -o /dev/null -w '%{http_code}\n' https://api.example.com/healthz
200

# Let curl retry transient failures (timeouts, 408, 429, 500, 502, 503, 504) with backoff
$ curl -fsS --retry 5 --retry-max-time 60 https://api.example.com/v1/deployments/dep_812

Four habits. Use -f or --fail-with-body in scripts: without it, curl exits 0 on a 500 and your set -e never fires (Prerequisite 2). Read the token from a file or environment variable, not the command line, where it ends up in shell history and in ps output. Keep the request ID: most APIs return one in a header (x-request-id, x-amzn-requestid), and it is the first thing a provider's support team asks for. And let the official CLI or SDK do request signing when the API needs it (AWS's SigV4 signs every request with your secret key); curl is for understanding and quick checks.

Use case: why payment APIs made idempotency keys famous

When a payment request times out, the client cannot know whether the customer was charged. Stripe's API solves this with an Idempotency-Key header on POST requests: the first request's result is saved under that key, and a retry with the same key returns the saved result instead of charging again. Stripe documents that keys can be removed after they are at least 24 hours old, so retries must happen within that window. The same pattern now appears in many cloud and internal APIs, and it is the right default for any automation that creates things: deployments, tickets, DNS records, invoices.

⚠️
Common mistakes
  • curl without -f in scripts: a 500 is exit code 0.
  • Retrying 4xx errors. A 400 or 403 will fail the same way every time, and the retries burn your rate limit.
  • Retrying POST blindly after a timeout: duplicate deployments, charges or records. Use an idempotency key.
  • Ignoring Retry-After and retrying immediately on 429, which keeps you rate-limited.
  • Tokens on the command line or in logs. Read them from a file or environment variable and mask them in CI.
  • Confusing 401 and 403: 401 means "who are you?" (fix the token), 403 means "not allowed" (fix the permission).

Interview drill

Explain it simply: What is the difference between a 401 and a 403?

How a strong answer sounds
401 Unauthorized really means unauthenticated: the server does not know who you are, because the token is missing, expired or invalid, so getting a fresh token can fix it. 403 Forbidden means the server knows who you are and you are not allowed to do this; a new token with the same permissions will fail the same way, so the fix is the role or policy. Some APIs return 404 instead of 403 so as not to reveal that a resource exists.

Deeper: Your pipeline's "create DNS record" step sometimes times out, and the retry then fails with 409 Conflict. How do you make the step reliable?

How a strong answer sounds
The first call succeeded but the response was lost, so the retry tries to create something that now exists. Options, best first: use an idempotency key if the API supports one, so the retry returns the original result; or use an idempotent operation such as PUT/"upsert" that sets the record to the desired value whether or not it exists; or treat 409 as "check the current state": GET the record and succeed if it already matches. More generally, steps should converge on a desired state rather than issue one-shot commands, which is exactly what Terraform and Kubernetes do (Chapters 11 and 19).

🧠 Key takeaways

  • GET is safe; PUT and DELETE are idempotent; POST is neither, so retrying it can duplicate work.
  • 4xx means fix the request (401: identity, 403: permission, 422: body); 5xx means the server failed.
  • Retry only 429, 503, other 5xx and timeouts, with backoff and jitter, honouring Retry-After.
  • In scripts use curl -fsS (or --fail-with-body), read tokens from files, and keep request IDs.
  • Idempotency keys make creates safe to retry; desired-state APIs make them unnecessary.

Check your understanding

A script's POST /v1/deployments times out. What is the risk of simply sending it again?

A timeout does not tell you whether the server did the work. POST is not idempotent, so use an idempotency key (or an idempotent operation) before retrying.

A token with only deploy:read sends POST /v1/deployments. Which status code fits?

The caller is authenticated (the token is valid) but lacks the permission. 401 would mean the token itself is missing or invalid.

Which error should a script NOT retry automatically?

422 is a client error: the same body will fail the same way. 429 and 503 ask you to come back later; a GET is safe to repeat.

Why add -f (or --fail-with-body) to curl calls in a CI script?

By default curl only fails on transport errors. -f turns HTTP error statuses into a non-zero exit code (22); --fail-with-body also prints the error body.

An API answers 429 with Retry-After: 30. What should the client do?

Retry-After is the server telling you when to come back. Retrying sooner just extends the throttling.
