ConfigMaps & Secrets

The same image has to run in development, staging and production, so everything that differs between them (addresses, feature flags, log levels, passwords) has to come from outside the image. Kubernetes has two objects for that: ConfigMaps for ordinary settings and Secrets for sensitive ones. Both are simple key-value stores, and both hide details that cause real incidents. A Secret is encoded, not encrypted. A changed ConfigMap may never reach a running pod, or may reach three pods at three different times. This chapter covers the two objects, the two ways of handing their values to a container, how changes propagate, and where real secrets should live.

  • Predict when a change to a ConfigMap reaches a running pod, and when it never does

Configuration belongs outside the image

If the database address is compiled into the image, you need one image per environment, and what you tested is no longer what you ship. So the image holds the code and its defaults, and the environment supplies the rest when the container starts. A useful test: could you publish the image to the world without leaking anything and without it being tied to one environment? If not, something in it is configuration.

ConfigMaps

A ConfigMap is a named set of keys and string values in a namespace. A value can be a short setting or the whole content of a configuration file.

apiVersion: v1
kind: ConfigMap
metadata: { name: web-config, namespace: shop }
data:
  LOG_LEVEL: info
  PAYMENTS_URL: http://payments.shop.svc.cluster.local
  nginx.conf: |                 # a whole file as one value
    server {
      listen 8080;
      location / { proxy_pass http://127.0.0.1:3000; }
    }

A pod can receive those values in two ways, and the difference matters more than it looks.

    spec:
      containers:
        - name: web
          image: ghcr.io/acme/web:4.18.2
          envFrom:                                   # 1. every key becomes an environment variable
            - configMapRef: { name: web-config }
          env:
            - name: DATABASE_PASSWORD                 #    or one variable from one key
              valueFrom: { secretKeyRef: { name: web-db, key: password } }
          volumeMounts:                              # 2. every key becomes a file in a directory
            - { name: config, mountPath: /etc/web, readOnly: true }
      volumes:
        - name: config
          configMap: { name: web-config }           #    /etc/web/LOG_LEVEL, /etc/web/nginx.conf, ...

Secrets and base64

A Secret has the same shape as a ConfigMap and is consumed in the same two ways. Its values are stored base64-encoded, and that is the single most misunderstood fact about it. Base64 is a way of writing arbitrary bytes as text. It is not encryption, it has no key, and anyone can reverse it.

$ kubectl create secret generic web-db -n shop --from-literal=password='s3cr3t-pa55'
$ kubectl get secret web-db -n shop -o yaml
apiVersion: v1
kind: Secret
type: Opaque
data:
  password: czNjcjN0LXBhNTU=                    # looks scrambled...

$ echo 'czNjcjN0LXBhNTU=' | base64 -d
s3cr3t-pa55                                     # ...and is not

So a Secret manifest committed to Git is a password committed to Git. What protects a Secret is not its encoding but everything around it:

  • Permissions. Reading Secrets is a separate permission in Kubernetes' access control, and should be granted to very few identities. Note the indirect route: anyone who may create pods in a namespace can mount any Secret in that namespace and read it from inside.
  • Encryption at rest. By default the API server writes Secrets to etcd as they are. Managed clusters encrypt the underlying disk, and both managed and self-run clusters can be set to encrypt Secret values with a key from a key management service before they are stored (Chapter 28). Without that, a backup of etcd contains every secret in the cluster.
  • Handling on the node. A Secret is sent only to nodes that run a pod using it, and mounted Secrets are kept in memory, not written to the node's disk.

Secrets also have types that tools rely on: kubernetes.io/tls for a certificate and its key, kubernetes.io/dockerconfigjson for registry credentials, and Opaque for everything else.

Two details about mounted files. The kubelet updates all the files of a volume together by switching a symbolic link, so an application never sees half an update. And a file mounted with subPath, which places a single file into an existing directory, is not updated at all after the container starts.

How you make the change
The kubelets on the three pods' nodes pick up a changed ConfigMap 20, 45 and 70 seconds after the change, as their periodic syncs come round. An environment variable and a subPath file are fixed for the life of the container. Changing the ConfigMap's name in the Deployment changes the pod template, which starts an ordinary rolling update: one pod is replaced every 10 seconds. kubectl rollout restart replaces all pods in the same way.

Things to try. Changing a setting at the top resets the panel.

  • Environment variable, edited in place. Change the value and wait 90 seconds: 0 of 3 pods use it, and no amount of waiting helps. Press kubectl rollout restart, wait 30 seconds, and all three do.
  • Mounted file, application reads once. After 90 seconds the file in every pod says debug and every application still logs at info. The change has arrived and nobody read it. This is the case that confuses people most, because kubectl exec … cat shows the new value.
  • Mounted file, application re-reads. Wait 30 seconds after the change: one pod of three has switched and the panel reports that the pods disagree. After 90 seconds all three have. It works, with a minute in which identical pods behaved differently and nothing would have stopped a bad value from reaching all of them.
  • subPath. Never updates, whatever the application does.
  • The second way of changing it, a new ConfigMap name. Under every one of the six combinations the result is the same: a rolling update starts at once, and 30 seconds later all three pods run with the new value. How the pod consumes configuration stops mattering, because every pod that has the new configuration is a new pod.

The second way of making the change is what tools do for you. Kustomize's configMapGenerator and Helm's checksum annotation (Chapter 16) both derive something in the pod template from the configuration's content, so that a configuration change is a rollout: gradual, gated by readiness probes, visible in the rollout history and undone by a rollback. Marking a ConfigMap immutable: true enforces the habit and spares the kubelets from watching it.

External secret stores

A Kubernetes Secret is a delivery mechanism, and a poor system of record. It has no versions, no rotation, little audit trail, and its definition cannot safely live in Git. Organisations therefore keep the real secret in a dedicated store (AWS Secrets Manager, Google Secret Manager, Azure Key Vault, HashiCorp Vault) and let the cluster fetch it. There are three common patterns.

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: web-db, namespace: shop }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aws-secrets-manager, kind: ClusterSecretStore }
  target: { name: web-db }                       # the Kubernetes Secret to create and keep in sync
  data:
    - secretKey: password
      remoteRef: { key: prod/shop/web-db, property: password }

This file is safe to commit: it says where the secret is and contains none of it. The controller reads the store with a cloud role given to it through workload identity, so no credential is stored anywhere to bootstrap the process. How stores issue short-lived secrets and rotate them is the subject of Chapter 28.

⛏️
Use case: Tesla's open dashboard, 2018

In February 2018 the security firm RedLock reported that it had found a Kubernetes administration console belonging to Tesla reachable from the internet with no password. Whoever got there first had used it to run cryptocurrency-mining software in Tesla's cluster, taking care to keep CPU use low and to hide the traffic so that it would not be noticed. The more serious finding was what else the console exposed: one of the pods held credentials for Tesla's AWS account, and with them the intruders could reach a storage bucket containing vehicle telemetry. Tesla fixed the exposure within hours of being told and said it found no sign that customer data had been compromised. Everything in the chain is this chapter read backwards. A secret readable inside the cluster is readable by anyone who gains access to the cluster's API, so access to that API and to Secrets has to be tightly held. And the credential that did the damage was a long-lived cloud key stored where a pod could use it: with an identity assigned to the pod, as in Chapter 6, there would have been nothing durable to steal.

⚠️
Common mistakes
  • Treating base64 as protection, and committing Secret manifests to Git.
  • Configuration baked into the image, so that each environment needs its own build.
  • Editing a ConfigMap and expecting pods to change. Environment variables never update, and subPath mounts never update.
  • Editing in place in production. Pods pick the change up at different times, nothing gates it and nothing records it. Make configuration changes a rollout.
  • Secrets in environment variables that end up in crash dumps, debug endpoints and logs.
  • Wide permission to read Secrets, or to create pods in a namespace that holds them.
  • No encryption at rest for etcd, and etcd backups stored without care.
  • Long-lived cloud keys in Secrets where a workload identity would do.
  • One giant ConfigMap for every service. Any change restarts everything, and everyone can read everyone's settings.

Interview drill

Explain it simply: What is the difference between a ConfigMap and a Secret? Is a Secret encrypted?

How a strong answer sounds
Both are key-value objects that inject configuration into pods as environment variables or files. A ConfigMap is for non-sensitive settings; a Secret is for sensitive ones, and Kubernetes treats it more carefully: a separate permission to read it, delivery only to nodes that need it, and mounted copies kept in memory. A Secret's values are base64-encoded, which is an encoding and not encryption, so anyone who can read the object can read the value, and by default it is stored in etcd unencrypted. Real protection comes from restricting who can read Secrets and create pods in the namespace, enabling encryption at rest with a KMS key, and keeping the source of truth in an external secret store. I would never commit a Secret manifest to Git.

Deeper: You changed a value in a ConfigMap and the application still behaves as before. Why, and how should configuration changes be rolled out?

How a strong answer sounds
It depends on how the pod consumes the value. If it is an environment variable, it was copied into the container's environment at start and will not change until the pod is replaced. If it is a mounted volume, the kubelet updates the file after its next sync, which can take a minute or two, but the application has to re-read the file, and many read configuration only at start. If the file is mounted with subPath it is never updated. So the quick fix is kubectl rollout restart. The better answer is that editing a ConfigMap in place is the wrong way to change configuration in production: pods get the change at different times, a bad value reaches all of them with nothing to stop it, and there is no record or rollback. I would make the configuration versioned and immutable: generate the ConfigMap with a hash of its content in the name, or put a checksum of it in the pod template's annotations, so that changing configuration changes the pod template and triggers a normal rolling update. Then the change is gradual, gated by readiness probes, and rollout undo brings back the old configuration together with the old pods.

🧠 Key takeaways

  • One image, many environments: what differs comes from ConfigMaps and Secrets at start-up.
  • Both are key-value objects, consumed as environment variables or as files.
  • A Secret is base64-encoded, not encrypted. Permissions, encryption at rest and an external store are what protect it.
  • Environment variables and subPath files never change in a running container; mounted volumes update after a delay, pod by pod.
  • Treat a configuration change as a rollout: a new, immutable ConfigMap and a changed pod template.
  • Keep the source of truth for secrets in a secret store; commit pointers or ciphertext, never the value.
  • Prefer an identity for the workload over a stored credential.

Check your understanding

A Secret's manifest shows password: aHVudGVyMg==. A colleague says it is safe to commit because the value is encrypted. Are they right?

Base64 is an encoding with no key. base64 -d turns it back into the password, and Git history keeps it for ever.

A pod gets LOG_LEVEL from a ConfigMap through envFrom. The ConfigMap is edited. When does the running container see the new value?

A process's environment is set when it starts. Only a new pod reads the ConfigMap again.

A ConfigMap is mounted as a volume in ten pods on several nodes and then edited in place. What is true shortly afterwards?

Each kubelet updates mounted volumes on its own sync schedule, so the change arrives pod by pod, with no gate and no restart.

Why do tools put a hash of the configuration into the ConfigMap's name or into the pod template's annotations?

A Deployment only rolls when its pod template changes. Tying the template to the configuration's content turns a config change into a normal release.

With the External Secrets Operator, what is committed to Git?

The ExternalSecret object is a pointer. The value stays in the store, and the controller fetches it using its own identity.
