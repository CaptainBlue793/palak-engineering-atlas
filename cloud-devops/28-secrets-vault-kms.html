Secrets Management: Vault & KMS

A secret is anything that grants access by being known: a database password, an API token, a signing key. The uncomfortable fact about secrets is that they leak, steadily, through ordinary work: a commit, a log line, a screenshot, a laptop. A mature approach therefore stops trying to guarantee that no secret ever escapes and asks a better question: when one does, how long is it useful, and for what? This chapter covers the places secrets leak from, secret stores and short-lived dynamic credentials, how a key management service encrypts data without ever handing out its keys, rotation, and scanning. The simulator leaks a credential and measures how long an attacker can use it.

Where secrets leak

Secrets rarely escape through clever attacks. They escape through the places people put them for convenience.

WhereHow it gets thereDefence
GitA config file, a test, a notebook, a .env committed "for now". Deleting it later leaves it in history, in forks and in clonesPush protection and scanning; a store, so that there is nothing to commit
CI logs and variablesA script echoes its environment; a debug flag prints requestsShort-lived identity tokens instead of stored secrets (Chapter 10)

The pattern across the table: a long-lived secret that many things share will, given enough time, turn up in one of these places. So the two properties to attack are "long-lived" and "shared".

Vault and dynamic secrets

A secret store (HashiCorp Vault, AWS Secrets Manager, Google Secret Manager, Azure Key Vault) is a service whose only job is to hold secrets and release them to the right callers. Compared with a file or an environment variable it adds four things.

  • Access by identity. A workload proves who it is, with its Kubernetes service account token or its cloud role, and a policy says which secrets that identity may read. There is no "master password" to distribute first.
  • An audit log. Every read is recorded: who, which secret, when. After an incident you can say what was accessed.
  • Versions. A new value does not destroy the old one, which is what makes rotation and rollback possible.
  • Leases. A secret can be handed out with an expiry, and revoked early.

The last point leads to the idea that changes the risk the most. With dynamic secrets, the store does not hold a database password at all. It holds the right to create database users. When a service asks, Vault creates a brand-new user with a random password, valid for an hour, and deletes it when the lease ends.

$ vault read database/creds/checkout-readonly
Key                Value
---                -----
lease_id           database/creds/checkout-readonly/2f6a1c9e
lease_duration     1h
lease_renewable    true
password           A1a-8kQz4mVx2Tn7pLw3                 # exists only for this lease
username           v-k8s-checkout-readonly-x7Hq2m       # a unique database user: the audit trail names it

$ vault lease revoke database/creds/checkout-readonly/2f6a1c9e   # the user is dropped at once

# The policy that lets the checkout service ask, and nothing else
path "database/creds/checkout-readonly" {
  capabilities = ["read"]
}

A leaked dynamic credential is worth at most an hour, belongs to exactly one workload, and can be revoked without touching anything else. The same idea appears elsewhere under other names: the temporary credentials of a cloud role (Chapter 6) are dynamic secrets, and so are the short-lived certificates of a service mesh (Chapter 27). Where a platform offers identity-based access to a resource, such as a database that accepts the cloud's own tokens, prefer that to any stored password.

KMS and envelope encryption

A key management service (KMS) holds encryption keys inside hardware that will not export them. You cannot download a KMS key. You can only ask the service to use it: "encrypt this", "decrypt this". Every such request is checked against a policy and written to an audit log. That solves the oldest problem in encryption, where to keep the key, by making the key a thing nobody has.

It creates a practical one. Sending a 50 GB database backup to an API to be encrypted is not workable, and KMS calls accept only a few kilobytes. The answer is envelope encryption, which uses two layers of key.

  • The data key (DEK) encrypts the data. It is used locally, so it is fast, and there can be one per object, per volume or per row.
  • The key-encryption key (KEK) is the KMS key. It encrypts only data keys.

The design pays off in several ways. Access control collapses to one place: whoever may not call Decrypt on the KMS key cannot read the data, however they obtained the ciphertext. Rotation is cheap: a new KMS key version re-wraps small data keys and not terabytes of data. Deletion can be absolute: destroy the KMS key and everything encrypted under it is unreadable for ever, which is how data is provably erased, and also why key deletion has a mandatory waiting period. This is what "encrypted with KMS" means for object storage, block volumes, managed databases, Kubernetes Secrets and Terraform state.

$ aws kms generate-data-key --key-id alias/prod-backups --key-spec AES_256 \
    --query '{plain:Plaintext,wrapped:CiphertextBlob}'
{ "plain": "3q2+7w…(32 bytes, base64)…", "wrapped": "AQIDAHh…(the same key, encrypted under alias/prod-backups)…" }

# SOPS uses the same pattern to keep encrypted secrets in Git: values are encrypted with a data key,
# and the data key is wrapped by a KMS key that only the cluster's role may use
$ sops --encrypt --kms arn:aws:kms:eu-west-2:111122223333:alias/gitops secrets.yaml > secrets.enc.yaml

Rotation

Rotation is replacing a secret with a new one on a schedule. It does not prevent leaks. It limits how long a leaked secret works, and it guarantees that you can change the secret, which is the capability you need on the day of an incident. A secret that has not been rotated in three years is one that nobody knows how to change. Rotation without downtime needs a short period in which both old and new are valid.

Three things make rotation automatic. The secret lives in one place, the store, and nowhere else. Each consumer has its own credential, so that changing one does not require coordinating twelve teams. And applications reload: they fetch the secret at connection time or watch the file, and do not cache it for the life of the process. Dynamic secrets are this taken to its conclusion: rotation every hour, with no schedule to maintain.

Secret scanning

Because leaks happen anyway, you look for them, at three points.

  • Before the commit: a pre-commit hook (gitleaks, detect-secrets) checks the change on the developer's machine.
  • At the push: push protection on the Git host rejects a push that contains a recognised credential. This is the most valuable of the three, because the secret never reaches the server.
  • After the fact: continuous scanning of repositories, images and logs. Git hosts also report credentials found in public repositories to the provider that issued them; AWS, for instance, responds by restricting the exposed key.
$ git push origin feature/billing
remote: error: GH013: Repository rule violations found for refs/heads/feature/billing.
remote: - GITHUB PUSH PROTECTION
remote:   —— Amazon AWS Access Key ID ————————————————————————
remote:     locations:
remote:       - commit: 9f2c1ab   path: scripts/backfill.py:14
remote:   Push cannot contain secrets
 ! [remote rejected] feature/billing -> feature/billing (push declined due to repository rule violations)

$ gitleaks git --redact .          # scan the whole history of a repository you have inherited

When a scan finds a real secret, the order of the response matters. Revoke it first. Assume it has been copied: automated scrapers pick up credentials from public pushes within minutes. Then find out what it was used for, from the audit logs, during the time it was exposed. Only then tidy up the repository. Rewriting Git history to remove the secret is housekeeping. It does not make the secret secret again.

    The attacker has the credential 4 minutes after the push. A scanner raises an alert 5 minutes after the push, and someone starts acting on it 15 minutes later. Changing a password by hand takes 20 minutes per service that uses it; with automated rotation in place it takes 5 minutes in total; revoking a dynamic lease takes 2. Scheduled rotation is taken at its worst case, with the full interval still to run. Push protection rejects the push, so the credential never becomes public. The bar's scale is logarithmic.

    Things to try.

    • The starting position is the common one: a password that is never rotated, shared by twelve services, with no scanning. The attacker's access lasts indefinitely, and nothing on the timeline after minute 4 belongs to the defenders.
    • Turn on repository scanning. The exposure falls to 4.3 hours, and the breakdown is the lesson: 16 minutes to notice and react, then 4 hours changing one password in twelve places. Switch to one service and the same response takes 36 minutes.
    • Rotate every 90 days by hand, with no detection: the credential works for 90 days. Slow rotation meets a compliance rule and does almost nothing for a live leak.
    • Rotate every 24 hours, automated: 23.9 hours with no detection at all, and 21 minutes with scanning, because revoking is now a five-minute job that touches no service.
    • Dynamic, one-hour lease: 56 minutes with nobody watching, 18 minutes with scanning. The worst case is bounded by design, whichever of the other switches you set.
    • Push protection gives no exposure in every one of its 24 settings. It is the only control here that acts before the leak.
    • Switch between administrator and read one schema. The time never changes; what the attacker can do in that time does. Least privilege and short lifetime are separate defences, and you want both.
    • Across all 72 settings: 24 have no exposure, 32 are under an hour, 8 are under a day, 4 last 90 days and 4 never end. All four that never end are the static, never-rotated, unscanned password.

    Use case: Uber, 2016, and the keys in a repository

    In late 2016 two attackers got into a private GitHub repository used by Uber's engineers, apparently with passwords that had been exposed in earlier breaches of other sites. A private repository is not a secret store, and in it they found what they were looking for: access keys for Uber's Amazon Web Services account, sitting in code. With those keys they read a storage bucket containing the names, email addresses and phone numbers of about 57 million riders and drivers, including some 600,000 driving licence numbers. Uber paid the attackers $100,000, routed through its bug bounty programme, and did not tell regulators or the people affected for a year. When it came out in 2017, the company's security chief was dismissed and later convicted for concealing the breach, and Uber paid $148 million to settle with US states. Take the legal story away and the technical chain is short. A long-lived cloud key was in a repository. The repository's protection was a reusable password. The key could read a great deal. Every control in this chapter cuts that chain somewhere: scanning would have flagged the key, a role with temporary credentials would have left no key to find, and a narrowly scoped identity would have had no access to that bucket.

    ⚠️
    Common mistakes
    • One shared credential for many services. It leaks through the weakest of them and cannot be changed without all of them.
    • Secrets that are never rotated, which really means secrets that nobody knows how to rotate.
    • Treating a private repository as safe storage. Everyone with read access, every clone and every CI job has the secret.
    • Deleting a leaked secret from Git and moving on. It is in history and already copied. Revoke it.
    • Encrypting data and storing the key beside it, or in the same repository.
    • A KMS key policy that lets everyone decrypt. The encryption is then decoration.
    • Applications that read a secret once at start and hold it for weeks. Rotation then means a restart, and people avoid it.
    • No audit trail. After a leak you cannot say whether the secret was used.
    • Scanning with nobody assigned to the alerts. A finding that sits in a dashboard is a leak with a timestamp.
    • The secret store's own bootstrap secret in a config file. Authenticate workloads by platform identity.

    Interview drill

    Explain it simply: What is envelope encryption, and why is it used?

    How a strong answer sounds
    Envelope encryption uses two keys. The data is encrypted locally with a data key, and the data key is itself encrypted with a master key held in a key management service; the encrypted data key is stored next to the data. To read the data, you ask the KMS to decrypt the data key, then decrypt locally. It is used because the master key never has to leave the KMS, large data never has to be sent to it, and access comes down to one question: is this identity allowed to call Decrypt on that key? Every use is logged. Rotation becomes re-encrypting small data keys instead of all the data, and destroying the master key makes everything under it unreadable. Cloud storage, disk and database encryption with KMS all work this way.

    Deeper: A developer tells you they pushed an AWS access key to a public repository twenty minutes ago and have just deleted the commit. What do you do?

    How a strong answer sounds
    I treat the key as compromised, because scrapers pick up keys from public pushes within minutes, and deleting the commit removes nothing from anyone who already has it. So the first action is to deactivate the key and issue a replacement, accepting that something may break: an outage from a revoked key is recoverable and an attacker in the account may not be. Next I find out what the key could do and what it did. Its permissions tell me the possible blast radius. The API audit trail for the period from the push until deactivation tells me the actual one: calls from unfamiliar addresses, new users, roles or access keys, new instances, usually for mining, in regions we do not use, reads from storage. Anything the attacker created is removed, and any credential the key could have read or created is rotated too, since a common move is to mint a second key for persistence. If data was read, that goes to the security and legal process for disclosure. Then the repair: restore service with the new credential delivered through the secret store, not a file. After that, the causes: why was a long-lived key in use at all where a role would do, why did it have more permission than the job needed, and why did nothing stop the push? I would turn on push protection and scanning for the organisation, and thank the developer for reporting it quickly, because the next person needs to know that telling us at once is the right thing to do.

    🧠 Key takeaways

    • Secrets leak through Git, CI, images, logs, state files and people. Design for the leak, not against the idea of one.
    • A secret store gives access by identity, an audit log, versions and leases.
    • Dynamic secrets are created per workload and expire in an hour. Identity-based access removes the secret altogether.
    • Envelope encryption: a data key encrypts the data, a KMS key encrypts the data key, and the KMS key never leaves.
    • Rotation limits a leak's lifetime and proves you can change the secret. It needs an overlap, one credential per consumer, and applications that reload.
    • Scan before the commit, at the push and afterwards. Found a secret? Revoke first, investigate, then clean up.
    • Shared and long-lived are the two properties that make a leak expensive.

    Check your understanding

    A database password is found in a commit from eight months ago. The file was deleted in a later commit. What is the correct first action?

    History, clones and forks still contain it. Revoking the credential is the only step that ends the exposure; cleaning history comes afterwards.

    What makes a dynamic database credential from a secret store safer than a static password?

    Dynamic secrets can leak like any other. What changes is how long the leak matters, who it implicates, and how easily it is revoked.

    In envelope encryption, what does the KMS key encrypt?

    The data is encrypted locally with a data key. Only that small key goes to the KMS to be wrapped, and the wrapped copy is stored with the data.

    A password is rotated by changing it in the database and then updating the twelve services that use it. Several services fail for some minutes. What was missing?

    Zero-downtime rotation creates the new credential first, lets every consumer move to it, confirms the old one is unused, and only then revokes it.

    Which control stops a secret before it has leaked at all?

    A rejected push never reaches the server. The other three limit or reveal the damage after the secret is out.
