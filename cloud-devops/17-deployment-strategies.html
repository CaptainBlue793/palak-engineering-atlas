Deployment Strategies: Rolling, Blue-Green & Canary

Every release carries some chance of being broken in a way that tests did not catch. You cannot remove that chance, so the engineering question is a different one: when a bad version ships, how many users meet it, for how long, and how quickly can you take it back? A deployment strategy is your answer. This chapter compares the four standard ones (recreate, rolling, blue-green and canary), adds feature flags, which separate shipping code from switching it on, and finishes with automated rollback. The simulator releases a good or a faulty version under each strategy and counts the requests that fail.

  • Describe automated canary analysis: what is measured, against what, and for how long
  • Use feature flags as a release tool and as a kill switch, and know their cost
  • Design a rollback that is automatic, fast and has been tested

Deploying is not releasing

Two words are worth keeping apart. To deploy a version is to get it running in production. To release it is to send users' requests to it. The simplest strategies do both in one step, and that is exactly their weakness: the first real test of the new version is all of your traffic. Every better strategy opens a gap between the two, so that the new version can be observed on a little traffic, or none, before it carries everything.

The damage a bad release does is roughly the share of users exposed × the time until it is withdrawn. Strategies differ in how they limit the first factor and in how fast they make the second.

Recreate and rolling

Recreate stops every old pod and then starts the new ones. There is downtime in between, and it is the only strategy in which two versions never run together. That makes it the right choice in a few real cases: a schema change the old code cannot survive, a volume that only one pod can mount (Chapter 15), or an internal batch system that nobody uses at night.

Rolling is the Kubernetes default: replace pods a few at a time, each new one gated by its readiness probe. There is no downtime and no extra environment. It has two limits. Readiness is the only judgement made: a version that starts cleanly and then returns wrong answers will roll out to 100% without anything objecting. And exposure grows quickly: by the time a dashboard shows a problem, half the fleet may be new.

Rolling, blue-green and canary all have a period in which old and new versions serve at the same time, and a rollback returns to the old one. That puts a requirement on everything the two share:

  • APIs and messages: the new version must accept what the old one sends, and the other way round.
  • The database: a schema change must work with both versions. The standard pattern is expand, then contract: first add the new column or table (both versions work), then ship code that uses it, and only in a later release remove what is no longer needed. Renaming a column in one step breaks whichever version is not expecting it. Chapter 42 works through a full migration.

Blue-green

In a blue-green deployment you run two complete copies of the service. Blue is live. You deploy the new version as green, next to it, receiving no user traffic. You test green in place, on production infrastructure. Then you switch the router, the Service selector or the DNS weight, and all traffic moves to green at once. Blue stays running for a while, so that going back is the same switch in the other direction.

What you buy is a rehearsal on the real infrastructure and the fastest possible rollback. What you pay is double the capacity during the release, and the awkward fact that both colours share one database. And the switch still exposes every user at the same moment, so a fault that the smoke tests miss is met by everyone.

Canary

A canary release sends a small share of real traffic, often 1%, to the new version while the rest stays on the old one. You compare the two, and only if the new one is at least as healthy do you raise its share, in steps, to 100%. The name comes from the birds miners carried to detect gas: the canary meets the danger first.

A canary needs three things that the simpler strategies do not.

  • Traffic splitting. By weight at the gateway or the mesh (Chapter 14, Chapter 27), or crudely by running one new pod among ninety-nine old ones.
  • Metrics per version. Error rate, latency and saturation, labelled by version, so that the canary can be compared with the baseline running beside it at the same moment under the same load (Chapter 21).
  • Enough traffic and enough time. One percent of ten requests a second is too little to tell a 0.5% error rate from bad luck. And some faults take time to appear: a memory leak, a cache that expires, a job that runs on the hour. The time spent at each step is the bake time, and it is a trade between speed and what you can catch.

In Kubernetes this is usually run by a controller such as Argo Rollouts or Flagger, which replaces the Deployment's built-in strategy with the steps you describe.

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: web, namespace: shop }
spec:
  replicas: 12
  strategy:
    canary:
      trafficRouting: { plugins: { argoproj-labs/gatewayAPI: { httpRoute: web, namespace: shop } } }
      analysis:                                  # runs in the background for the whole rollout
        templates: [{ templateName: error-rate }]
        startingStep: 1
      steps:
        - setWeight: 1
        - pause: { duration: 5m }                # bake
        - setWeight: 10
        - pause: { duration: 5m }
        - setWeight: 50
        - pause: { duration: 5m }
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: error-rate, namespace: shop }
spec:
  metrics:
    - name: canary-error-rate
      interval: 30s
      failureLimit: 1                          # one failed measurement aborts and shifts traffic back
      successCondition: result[0] < 0.011       # under 1.1% of the canary's requests fail
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{app="web",version="canary",code=~"5.."}[1m]))
              / sum(rate(http_requests_total{app="web",version="canary"}[1m]))

Rolling replaces a quarter of the pods every 30 seconds. Recreate has 30 seconds of downtime. Blue-green runs smoke tests for a minute, which catch only a version that fails every request, and then switches all traffic. Canary steps through 1%, 10% and 50% to 100%. Automated analysis checks the new version's own error rate over the last minute, needs 30 seconds and 300 requests to judge, and fails above 1.1%. The alert fires when the overall error rate has been above 1% across five minutes, and the person takes five more minutes to act. Going back takes 5 seconds for blue-green and for a canary that is not yet fully promoted, about two minutes of reverse rollout otherwise, and another 30 seconds of downtime for recreate. Blue-green keeps the old environment for the whole hour shown.

Things to try.

  • The starting point is a rolling update of a version that fails 5% of its requests, watched by a person. The alert fires after 4 minutes 55 seconds, with all traffic already on the new version, and the old version is back at 11 minutes 55 seconds. 30,625 requests fail.
  • Change only who is watching. With automated analysis the same rolling update is stopped after 25 seconds and reversed by 1 minute 30 seconds: 1,470 failed requests, a twentieth of the damage, with no change of strategy.
  • Canary, watched by a person. 15,582 failed requests. At 1% and at 10% of traffic the fault is too diluted to move the overall error rate past the alert's threshold, so the canary is promoted on schedule, twice. The alert fires at 11 minutes, at 50%, and by the time the person acts the release is at 100%. A canary that nobody analyses is a slow rolling update.
  • Canary with automated analysis. 17 failed requests. One percent of traffic met the bad version for 35 seconds.
  • A version where every request fails. Blue-green never releases it: the smoke tests on green stop it, and no user is affected. A rolling update watched by a person gives ten minutes of total outage, 624,375 failed requests. The automated canary loses 350.
  • The fault that appears after eight minutes, with the automated canary. With a 1-minute bake the canary is fully promoted long before the fault shows, and 23,920 requests fail. With a 5-minute bake it is caught at 10% of traffic: 299. With 15 minutes, at 1%: 30. Then select the healthy version and look at what the bake costs on a good day: 3, 15 or 45 minutes to finish a release.
  • Blue-green with that late fault and automation: every user is exposed, for ten seconds, and 2,990 requests fail. Blue-green does not limit how many users see a bad version. It limits how long.
  • Recreate with a healthy version: 29,970 failed requests, on every release, by design.

Feature flags

A feature flag moves the release decision out of the deployment and into the code: the new behaviour ships switched off, behind a condition that is read at run time from a flag service or a configuration store.

if flags.enabled("new-checkout", user):      # evaluated per request; changed without a deployment
    return new_checkout(cart)
return old_checkout(cart)

That gives you finer control than any routing rule. A flag can be on for employees only, then for 1% of users, then for one country. Turning it off takes effect in seconds and touches nothing else that shipped in the same deployment, which makes a flag the best kill switch there is. Deployments become dull, frequent and separate from the moment the business chooses to launch.

Flags have a price, and it is paid later. Every flag doubles the number of code paths that can run in production. An old flag that nobody remembers is a loaded configuration change waiting for someone to flip or reuse it: the Knight Capital loss in Chapter 1 began with a reused flag that woke up dead code. So give every flag an owner and an expiry date, remove it once the feature is fully on, and treat flag changes like deployments: recorded, reviewable and rolled out gradually.

Automated rollback

The simulator shows that who is watching matters as much as the strategy. A person needs an alert to fire, then to wake up, find a laptop, understand the situation and act. A rule reacts in a minute, at three in the morning, for every release.

  • What triggers it. The new version's own error rate or latency against the baseline, a failed rollout (kubectl rollout status timing out, helm upgrade --atomic), or the service's error budget burning too fast (Chapter 24).
  • Roll back first, understand later. This is "mitigate, then diagnose" from Chapter 1. The exception is a change that cannot be undone, such as a destructive migration, and the lesson there is to stop making such changes in one step.
  • The rollback must itself be safe. It has to work when the new version is broken, it must not depend on the system that is failing, and the old version must still be able to read the data the new one wrote.
  • Practise it. A rollback that has never been run is a hope. Run one on purpose, regularly.

Use case: Cloudflare, 2 July 2019

Cloudflare's network sits in front of millions of websites, and on 2 July 2019 it returned errors for most of them for 27 minutes. The company's post-mortem is unusually detailed. An engineer had added a new rule to the web application firewall, and one regular expression in it could, on certain inputs, make the matching engine backtrack almost endlessly. Every CPU core handling HTTP traffic, in every data centre in the world, went to 100% within seconds. The interesting part is why it was every data centre at once. Cloudflare's software releases already went out progressively: first to a small group of locations, then more, with checks between stages. Firewall rules did not. They were pushed through a separate system built to update the whole network in seconds, because rules are often a response to an attack in progress, and that path skipped the staged rollout. The rule had been deployed in a mode meant only to log matches, and that made no difference, since the cost was in evaluating it. Traffic through the network fell by about 80% until the team used a global kill switch for the firewall. Among the changes Cloudflare made afterwards, the first was to put rule changes through the same progressive rollout as code. The lesson is the widest one in this chapter: a canary protects you only for the kinds of change that go through it. Configuration, rules, flags and data are changes too, and they break production just as well as code does.

⚠️
Common mistakes
  • Treating "the rollout succeeded" as "the release is good". Readiness probes say the process started, not that its answers are right.
  • A canary nobody analyses. Sending 1% of traffic to a new version and then promoting it on a timer is a slow rolling update.
  • Too little traffic or too little bake time for the analysis to mean anything, or comparing the canary with yesterday instead of with a baseline running now.
  • Schema changes that only the new version understands. The old version breaks during the rollout, and the rollback breaks afterwards.
  • Scaling blue down straight after the switch. The instant rollback you paid for is gone.
  • Config and flag changes that bypass the rollout process and reach everything at once.
  • Flags that live for ever. Each one is an untested combination and a trap for the next person.
  • A rollback procedure that has never been run, or that needs the broken system to work.
  • Rolling out everywhere at once. Regions and clusters should also be stepped: one first, then the rest.

Interview drill

Explain it simply: What is the difference between a blue-green deployment and a canary release?

How a strong answer sounds
Both run the new version beside the old one, and they differ in how traffic moves. In blue-green there are two full environments: the new one is deployed and tested while it receives no user traffic, and then all traffic is switched to it at once. Rollback is switching back, which takes seconds, and the cost is double capacity and an all-or-nothing release. In a canary, a small share of real traffic, say 1%, goes to the new version first; its error rate and latency are compared with the old version's, and the share is raised in steps only if it looks healthy. A bad version therefore reaches few users, and the cost is the machinery: weighted routing, per-version metrics and enough traffic for the comparison to mean something. Blue-green limits how long a bad release lasts; canary also limits how many users see it.

Deeper: Design the release process for a payments API that handles a few thousand requests a second and must not lose or double-charge payments.

How a strong answer sounds
I would start from the fact that old and new versions will run together and that I must be able to go back, so every change has to be backward compatible: API changes are additive, and database changes follow expand and contract over several releases, never a rename or a drop in the same release as the code that needs it. Writes are idempotent, with idempotency keys, so that a request retried across a version switch cannot charge twice. The rollout is a canary with automated analysis: 1% of traffic first, compared with a baseline on the old version at the same time, on error rate, latency percentiles and a business signal such as the payment success rate, since a 200 response with a wrong result is the failure I fear most. Bake times long enough to gather thousands of requests per step and to cover slow faults, then 10%, 50% and 100%, with the analysis able to abort and shift traffic back in seconds without a person. I would step across regions as well, one region completely before the next. Risky new behaviour ships behind a feature flag, off, and is turned on separately for internal accounts and then a small percentage, so that the deployment and the launch are different events and the flag is the kill switch. Before any of it, the pipeline runs contract and integration tests, and the rollback path is exercised regularly. Finally the release is tied to the error budget: if the service has already spent its budget, releases other than fixes wait.

🧠 Key takeaways

  • Deploying puts a version in production; releasing sends it traffic. Good strategies separate the two.
  • Damage is exposure × time. Canary limits exposure; blue-green and automation limit time.
  • Recreate has downtime; rolling is the default and judges only readiness; blue-green rehearses and switches all at once; canary tests on a small share of real traffic.
  • Whenever two versions overlap, APIs and schemas must work with both: expand, then contract.
  • A canary needs traffic splitting, per-version metrics, enough requests and enough bake time.
  • Feature flags release by configuration and act as kill switches; remove them when they are done.
  • Automate the rollback, make it independent of what is failing, and practise it. Config changes need the same care as code.

Check your understanding

A new version starts correctly, passes its readiness probe, and returns HTTP 500 for one request in twenty. What does a plain rolling update do?

A rolling update is gated by readiness, which says the process can accept requests, not that it answers them correctly. Catching this needs analysis of real traffic.

What is the main advantage of blue-green over a rolling update?

Blue-green costs double capacity and still releases to everyone at once. What it buys is a rehearsal and the fastest way back.

A canary receives 1% of a service's 20 requests a second and is promoted after one minute with "no errors observed". Why is that weak evidence?

0.2 requests a second for 60 seconds is twelve requests. A version failing 5% of the time would show no error at all in more than half of such samples.

A release renames a database column, and the new code uses the new name. It is rolled out as a canary. What goes wrong?

Both versions share the database. A change that only one version understands breaks the other; add the new column first and remove the old one in a later release.

What can a feature flag do that a canary release cannot?

A flag controls one behaviour at run time, per user if you like. A canary moves whole versions and all the changes inside them together.
