Case Study: From Laptop to Production

Forty chapters have each taken one piece of the path to production and examined it alone. This case study puts the pieces back together. We follow one small service, a notes API with a PostgreSQL database, from a developer's laptop to real users: packaged as an image, built and checked by a pipeline, given infrastructure by Terraform, deployed through GitOps, released with a canary and watched by alerts tied to an SLO. Nothing here is new. The point is the join between the parts, and one question asked at each stage: what kind of mistake does this step exist to catch? The simulator sends eight different defects down the pipeline and shows where each one stops.

The service

The service is notes-api: an HTTP API that stores and returns short notes, with a PostgreSQL database. On a laptop it runs with one command, and that is where many projects stop thinking.

$ docker compose up          # the API on :8080 and a throwaway PostgreSQL beside it (Chapter 7)
$ curl -s localhost:8080/notes -d '{"text":"ship it"}'
{"id":1,"text":"ship it"}

"Works on my laptop" and "can be operated in production" are different properties. Before any pipeline exists, the code has to gain six habits, and each one is something a later stage relies on.

ConcernOn the laptopWhat production needsWho relies on it
ConfigurationValues in the code or a local fileEverything from environment variables; fail fast with a clear message if one is missingConfigMaps and Secrets (Chapter 13)
StateFiles on disk, sessions in memoryNothing kept in the process: any copy can serve any requestRolling updates, autoscaling
Health"It printed a log line"/healthz (am I stuck?) and /ready (can I serve now?), kept separateProbes, Services, rollouts (Chapter 12)
ShutdownCtrl-COn SIGTERM: stop accepting, finish requests in flight, close connections, exitZero-downtime deploys
LogsFree text to a fileStructured JSON to standard output, with a request IDThe log pipeline (Chapter 22)
SignalsNoneA /metrics endpoint with request rate, errors and duration; trace context passed onAlerts, canary analysis (Chapters 21, 23)

The last column is the theme of the whole case study. A canary cannot judge a release that exports no metrics. A rolling update cannot be safe for a service that drops its connections on SIGTERM. The pipeline is only as good as what the service tells it.

Build and CI

The first automated step turns a commit into an image: one immutable artefact, identified by a digest, that will be the thing running in every environment.

# Dockerfile (Chapter 8): build with the toolchain, ship without it
FROM golang:1.23@sha256:4c1e…a09f AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                              # cached until the dependencies change
COPY . .
RUN CGO_ENABLED=0 go build -o /out/notes-api ./cmd/notes-api

FROM gcr.io/distroless/static@sha256:9d2b…77c1
COPY --from=build /out/notes-api /notes-api
USER 65532                                       # not root
ENTRYPOINT ["/notes-api"]
# .github/workflows/ci.yaml (Chapters 10 and 29), condensed
on: { push: { branches: [main] }, pull_request: {} }
permissions: { contents: read, packages: write, id-token: write }
jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@<commit hash>
      - run: go vet ./... && go test -race ./...              # 1. is the code right?
      - run: docker build -t "$IMAGE:$GITHUB_SHA" .           # 2. one artefact
      - run: trivy image --exit-code 1 --severity CRITICAL,HIGH "$IMAGE:$GITHUB_SHA"   # 3. known flaws? secrets?
      - if: github.ref == 'refs/heads/main'
        run: |
          docker push "$IMAGE:$GITHUB_SHA"
          DIGEST=$(crane digest "$IMAGE:$GITHUB_SHA")
          cosign sign "$IMAGE@$DIGEST"                         # 4. who built it? keyless
          ./scripts/open-deploy-pr.sh dev "$IMAGE@$DIGEST"     # 5. hand over to GitOps, by digest

Five steps, five different jobs. The tests ask whether the code is right. The build produces the one artefact everything else will use. The scan asks whether it contains known vulnerabilities or a credential. The signature records which pipeline built it, and the cluster will check that later. The last step does not deploy anything. It proposes a change to another repository, which is where the pipeline's authority ends: CI builds, and something else deploys. The CI system never holds credentials for the cluster.

Infrastructure

The service needs things that are not containers: a network, a cluster, a database, an image registry, DNS. These are declared in Terraform, built from shared modules, with state kept remotely and locked (Chapters 19 and 20).

module "database" {
  source  = "git::https://github.com/example/tf-modules.git//postgres?ref=v4.2.0"
  name    = "notes"
  size    = "small"
  multi_az                = true
  backup_retention_days   = 14                    # point-in-time recovery (Chapter 32)
  deletion_protection     = true
  tags = { team = "notes", service = "notes-api", environment = "prod" }   # cost allocation (Chapter 31)
}

resource "aws_secretsmanager_secret_version" "db_url" {      # the connection string goes to the secret store,
  secret_id     = aws_secretsmanager_secret.db_url.id           # never to Git or to a person (Chapter 28)
  secret_string = module.database.connection_url
}

An infrastructure change travels a different road from a code change, with its own checks. A pull request runs terraform plan and posts the result. A policy check reads the plan as data (Chapter 36): no public buckets, required tags present, and above all nothing that would replace a stateful resource without an explicit override. A person reviews the plan, not just the code, because the plan says what will actually happen. Only after merge does a pipeline with its own narrow role apply it.

$ terraform plan -out plan.out
  # module.database.aws_db_instance.this must be replaced
-/+ resource "aws_db_instance" "this" {
      ~ engine_version = "15.4" -> "16.1"   # forces replacement
    }
Plan: 1 to add, 0 to change, 1 to destroy.

$ terraform show -json plan.out | conftest test --policy policy/ -
FAIL - module.database.aws_db_instance.this would be destroyed. Stateful resources need the label "allow-replace" and a second approver.

That failed check is the most valuable line in the chapter. One innocent-looking edit would have deleted the production database, and no test of the application could have known.

Deploy and canary

What should run is written in a Git repository as Kubernetes manifests: a base, plus a small overlay per environment (Chapter 16). Argo CD watches that repository and makes the cluster match it (Chapter 18). Deploying is therefore merging a pull request that changes one line, the image digest.

# deploy/base/rollout.yaml: a Deployment's pod template, released as a canary (Chapter 17)
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: notes-api }
spec:
  replicas: 6
  strategy:
    canary:
      steps:
        - setWeight: 10                     # one user in ten gets the new version
        - pause: { duration: 5m }
        - analysis: { templates: [{ templateName: error-rate-and-latency }] }   # compare with the old version
        - setWeight: 50
        - pause: { duration: 5m }
  template:
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: notes-api
          image: registry.example.com/notes/api@sha256:7f3a…c21d      # the line the pipeline changes
          envFrom: [{ secretRef: { name: notes-db } }]               # synced from the secret store
          resources: { requests: { cpu: 250m, memory: 256Mi }, limits: { memory: 256Mi } }
          readinessProbe: { httpGet: { path: /ready, port: 8080 } }
          livenessProbe:  { httpGet: { path: /healthz, port: 8080 } }
          lifecycle: { preStop: { exec: { command: ["sleep", "10"] } } }

The development environment exists to catch what unit tests cannot see: the service running with real manifests, real configuration and a real database. The canary exists to catch what dev cannot see: real traffic, real data sizes and real load, on a tenth of the users, judged automatically against the version beside it.

Monitoring and alerts

The service is live when someone would be told if it stopped working. That needs a statement of what "working" means, an SLO, and an alert that fires when it is at risk (Chapter 24).

# SLO: 99.9% of requests succeed, measured over 30 days. The alert: budget burning 14 times too fast.
- alert: NotesApiErrorBudgetBurn
  expr: |
    sum(rate(http_requests_total{app="notes-api",code=~"5.."}[5m])) / sum(rate(http_requests_total{app="notes-api"}[5m])) > 14.4 * 0.001
    and
    sum(rate(http_requests_total{app="notes-api",code=~"5.."}[1h])) / sum(rate(http_requests_total{app="notes-api"}[1h])) > 14.4 * 0.001
  labels: { severity: page, team: notes }
  annotations:
    summary: "notes-api is failing {{ $value | humanizePercentage }} of requests"
    runbook_url: "https://runbooks.example.com/notes/error-budget-burn"     # Chapter 38

Around that one alert sit the things a person needs once it has fired: a dashboard of rate, errors, latency and saturation; structured logs searchable by request ID; traces that show which hop was slow; and a runbook whose first line is "was there a deploy in the last hour? Roll it back". The same error-rate query is what the canary analysis uses, so a release is judged by the measure that defines the service's health.

A short list finishes the job, and it is the part most often left for later. The team is on a rotation for this service (Chapter 38). The database backup has been restored once, on purpose (Chapter 32). Resources carry cost tags (Chapter 31). And the service appears in the catalogue with an owner (Chapter 35).

Stages in place
    Times are minutes after the merge: tests finish at 3, the scan at 5, policy checks at 8, the dev deployment at 12, the canary's analysis at 25 (after 5 minutes at 10% of traffic) and the full rollout at 30. The SLO alert fires 2 minutes after a faulty full rollout and the rollback takes 5. With no alert, customers report the problem after 15 minutes. The service handles 50 requests a second.

    Things to try.

    • The starting pipeline has tests and a scan, which is where many teams stop. The missing index passes both, reaches every customer, and is found by complaints 45 minutes after the merge, with 36,000 requests failed.
    • Tick all six stages. The same defect is caught by the canary at minute 25 with 900 failed requests and nobody paged. Untick the canary and the alert catches it instead, after everyone has had it: 12,600.
    • Go through the eight defects with only "tests" ticked. One is caught. Add the scan and it is three. Tests are necessary and cover an eighth of this list.
    • Try each stage alone. Tests catch 1 of the 8, the scan 2, policy 2, dev 1, the canary 3 and the alert 3. No single stage catches more than three, and no two catch the same set: that is why there are six.
    • Choose the Terraform edit, with every stage on except policy. Tests, scan, dev, canary and alert all pass, and the database is destroyed. It was never in the application.
    • Choose the wrong result, with every stage on except tests. It goes to production and nobody knows, because a wrong answer is not an error. Later stages measure whether the service responds, not whether it is right.
    • With all six in place, six of the eight defects never reach a user, and the other two are confined to a tenth of users for five minutes: 900 and 30 failed requests.
    🛍️
    Use case: Etsy, where new engineers deployed on their first day

    Around 2009 Etsy, the marketplace for handmade goods, deployed its website roughly twice a week. Each deployment was a large batch of changes, took hours, needed a dedicated release engineer and regularly broke the site. Over the next few years the company rebuilt how it shipped, and wrote and spoke about it in enough detail that it became a reference point for the industry. The centre of it was a tool called Deployinator: a web page with a button, which any engineer could press to send the current main branch to production, and which showed everyone what was going out and who was doing it. Around that button the company built the things this chapter has assembled. A test suite ran on every change. Changes were small, so each deployment carried little risk and was easy to undo. New code could be merged switched off behind a configuration flag and turned on for a small share of users first. And the company measured almost everything, with graphs of business and system metrics on screens around the office and a vertical line drawn on each graph at every deployment, so that cause and effect were visible within minutes. By the early 2010s Etsy was deploying more than fifty times a day. The detail people remember is the onboarding ritual: a new engineer, on their first day, made a small change, adding their photo to the staff page, and deployed it to production themselves. That was only possible because the path from laptop to production was so well paved, and so well watched, that a newcomer could walk it safely on day one. A safe path to production is the thing this course has been building towards, more than any single tool on it.

    ⚠️
    Common mistakes
    • Building a pipeline for a service that cannot be operated: no health endpoints, no metrics, no graceful shutdown.
    • Rebuilding the image for each environment. What reaches production is then not what was tested. Build once, promote the digest.
    • CI with credentials to deploy to production. Let CI propose and GitOps apply.
    • Treating tests as the only safety net. Tests cannot see configuration, scale, infrastructure or security posture.
    • Reviewing Terraform code and not the plan. The plan is what will happen.
    • A dev environment that nobody looks at. Without a smoke test, a crash there is found in production.
    • A canary judged by eye, or with no metrics to judge it by.
    • Alerts added after the first outage. The SLO alert is part of going live.
    • Skipping the pipeline "just this once" for an urgent fix. The urgent fix is the change most likely to be wrong.
    • No rollback that has ever been used. Practise it on an ordinary day.

    Interview drill

    Explain it simply: Walk me through what happens between a developer merging a change and users seeing it.

    How a strong answer sounds
    The merge triggers CI. It runs the tests, builds one container image, scans it for known vulnerabilities and secrets, pushes it to the registry and signs its digest. CI then opens a change in the GitOps repository setting the development environment to that digest. Argo CD, which watches that repository, applies it to the cluster; admission control checks the image signature and the policies; the pods start and a smoke test runs. Promotion to production is another change to the same repository, with the same digest and usually an approval. In production the release is a canary: a small share of traffic goes to the new version, its error rate and latency are compared automatically with the old version, and it either proceeds in steps to 100% or is rolled back without anyone intervening. After that the SLO alerts are the safety net. The properties I would point out are that the image is built once and promoted, CI never has cluster credentials, every change is a reviewed commit, and each stage catches a class of problem the previous ones cannot.

    Deeper: A team has unit tests and a pipeline that deploys straight to production on merge. They have had three outages in two months. What would you add, and in what order?

    How a strong answer sounds
    I would start by reading the three postmortems, because the order depends on what the outages were. But the usual pattern has a usual answer, and I would work backwards from the customer. First, detection and undo, since they limit the damage of every kind of failure: an alert on the service's error rate and latency tied to an SLO, and a rollback that is one action and has been practised. That alone turns a forty-minute outage into a ten-minute one. Second, a canary with automated analysis, so that a bad release reaches a tenth of users for a few minutes instead of everyone until a human notices. It needs the same metrics as the alert, so step one pays for part of it. Third, a development or staging environment that every change passes through with a smoke test, which catches the release that cannot start at all: missing configuration, bad manifests, a failed migration. Fourth, checks on the things tests do not look at: scanning the image, and a policy check on infrastructure plans, especially anything that would replace a database. I would also change how deployment is wired: build the image once and promote it by digest, and move the deploy step out of CI into GitOps so that production changes are reviewed commits. I would not try to do all of this in one quarter or stop feature work for it. Each step is small, and each one removes a class of outage, so I would deliver them in that order and show the team where their past incidents would have been stopped.

    🧠 Key takeaways

    • A service must be operable before it is deployable: configuration from the environment, health endpoints, graceful shutdown, metrics.
    • CI turns a commit into one signed image and proposes a deployment. It does not deploy.
    • Infrastructure changes are judged by their plan, checked by policy and applied by a separate pipeline.
    • GitOps makes production a reviewed commit. The same digest is promoted from dev to production.
    • A canary judges a release on real traffic with the metrics that define the SLO.
    • Each stage catches a class of defect the others cannot see. Tests are one of six.
    • The path is finished when someone would be paged, and would know what to do.

    Check your understanding

    Why is the same image digest promoted from dev to production, and not rebuilt for each environment?

    A rebuild can pick up a different base image or dependency. Promoting one digest removes that difference.

    A query works instantly against the test database and is very slow against production's 200 million rows. Which stage is the first that can catch it?

    Tests and dev use small data. Only production traffic against production data shows the latency, and a canary exposes a tenth of users to it for a few minutes.

    In this design, why does the CI pipeline open a pull request to a GitOps repository instead of running kubectl apply?

    Separating build from deploy shrinks what a compromised pipeline can do and gives production a complete history in Git.

    A Terraform change edits one line and the plan says a database "must be replaced". What does that mean?

    Replacement is destroy then create. For a stateful resource that is data loss, which is why plans are reviewed and policy blocks it without an explicit override.

    A service has no /metrics endpoint. Which part of this pipeline cannot do its job?

    Both judge the service by its request rate, errors and latency. Without those signals a canary is only a slow rollout.
