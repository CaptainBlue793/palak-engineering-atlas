Metrics with Prometheus

You cannot run what you cannot see. The earlier chapters kept saying "watch the error rate", "compare the canary with the baseline", "alert on expiry": all of that needs numbers, collected continuously and kept over time. A metric is such a number, and Prometheus is the system most of the industry uses to gather, store and query them. This chapter covers the four types of metric, how Prometheus collects them by scraping, enough of its query language to answer real questions, the two checklists that tell you what to measure (RED and USE), and cardinality, the one way a metrics system reliably falls over. The simulator is a small query engine over thirty minutes of data that include a restart and an incident.

Metric types

A metric is a named measurement with a set of labels, sampled over time. http_requests_total{service="checkout", code="500"} is one time series: a list of (timestamp, value) pairs. Change any label value and you have a different series. Metrics are cheap to store, because each sample is one number, and they aggregate well. They tell you that something is wrong and roughly where. For why, you move to logs (Chapter 22) and traces (Chapter 23).

CounterOnly goes up, and resets to zero when the process restartsRequests served, errors, bytes sentNever directly. Take its rate(): the increase per second
GaugeGoes up and down: a current valueMemory in use, queue length, temperature, replicas readyDirectly, or with avg_over_time, max_over_time
HistogramCounts observations into buckets by size; each bucket is a counterRequest duration, response sizehistogram_quantile() over the rate of the buckets: percentiles, across any number of pods
SummaryPercentiles calculated inside the applicationOlder libraries' latency metricsDirectly, per instance only: percentiles from different pods cannot be combined

An application exposes its metrics as plain text on an HTTP endpoint, by convention /metrics. A client library keeps the numbers in memory and renders this page on request:

Scraping and exporters

Prometheus pulls. On a fixed interval, commonly 15 or 30 seconds, it sends an HTTP GET to each target's /metrics and stores every value it finds with the current timestamp. It learns what to scrape from service discovery: in Kubernetes it asks the API for pods and Services matching a selector, so new pods are picked up without any change to configuration, and it attaches labels such as namespace and pod to everything it scrapes.

Software that cannot expose metrics itself is covered by an exporter: a small process that reads the thing's own statistics and translates them. node_exporter does it for a Linux machine (CPU, memory, disks, network), kube-state-metrics for the state of Kubernetes objects, and there are exporters for PostgreSQL, Redis, NGINX and most other things. A blackbox_exporter probes endpoints from outside, which is how you measure what a user would see. Short batch jobs that are gone before the next scrape are the one case for pushing: they hand their final numbers to a Pushgateway, which Prometheus then scrapes.

# With the Prometheus Operator, scrape configuration is a Kubernetes object
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata: { name: checkout, namespace: shop }
spec:
  selector: { matchLabels: { app: checkout } }     # scrape the pods behind Services with this label
  endpoints:
    - { port: metrics, interval: 15s }

PromQL basics

PromQL is the query language. A few patterns cover most of what you will write.

# Select series by name and labels: an "instant vector", one current value per series
http_requests_total{service="checkout", code=~"5.."}        # =~ is a regular-expression match

# A counter's value is meaningless; its rate of increase per second, over a window, is what you want
rate(http_requests_total{service="checkout"}[5m])

# Aggregate across pods, keeping the labels you care about
sum by (code) (rate(http_requests_total{service="checkout"}[5m]))

# A ratio: the share of requests that fail
  sum(rate(http_requests_total{service="checkout", code=~"5.."}[5m]))
/ sum(rate(http_requests_total{service="checkout"}[5m]))

# The 99th percentile of latency, across all pods
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{service="checkout"}[5m])))

# A gauge is used as it is
max by (pod) (container_memory_working_set_bytes{namespace="shop"})

Three rules prevent most mistakes. Rate first, then sum. rate has to see each counter separately to handle its resets; summing first destroys that. Never take the rate of a gauge, and never graph a raw counter. And choose the window deliberately: it must cover at least a few scrapes, a short window reacts quickly and is noisy, and a long window is smooth and slow to show a change.

What rate does at a restart is worth understanding once. A counter that was at 36,000 comes back at 0. rate knows counters only go up, so a lower value can only mean a reset, and it counts from zero again instead of reporting a huge negative jump. That is why counters are safe across deployments, and why the "only goes up" property matters.

Simulator: thirty minutes of one service

One pod of checkout, scraped every 15 seconds for half an hour. It normally serves 50 successful requests a second and half an error. From minute 18 to minute 22 there is an incident: traffic rises, errors rise and responses slow down. Optionally the pod restarts at minute 12. Run each query against this data.

Query
The pod restarts at minute 12
The engine stores real samples and evaluates each expression at every scrape time. rate uses the samples inside its window, adds up the increases, treats any decrease as a counter reset, and divides by the time between the first and last sample (real Prometheus also extrapolates to the edges of the window). histogram_quantile interpolates linearly inside the bucket that contains the requested rank. At the restart the pod is down for a few seconds, so nine seconds of requests are never counted.

Things to try, with the restart switched on.

  • The raw counter. 30,000 at minute 10 and 3,300 at minute 13. Neither number means anything about traffic: the second is lower only because the process had just restarted. The incident, the one thing you would want to see, is a slight change of slope.
  • Rate over one minute. A flat 50 requests a second, a clear step to 120 during the incident, and errors rising from 0.5 to 6. At the restart the rate reads 40 for one sample and never goes negative. Those missing 10 are the nine seconds in which the pod was down and served nothing.
  • Rate over five minutes. At minute 21, three minutes into the incident, it reads 94 where the truth is 120, and it stays high for five minutes after the incident ends. The window is a trade between calm and speed.
  • The error ratio. 0.99% on a normal minute, 4.76% in the incident. Traffic more than doubled and errors rose twelve-fold; the ratio is the one number that says what happened to users.
  • The 99th percentile. 0.45 seconds normally and 2.33 seconds in the incident, recovered from seven bucket counters.
  • The rate computed by hand. Identical to rate all the way, except at the restart, where it reports minus 545 requests a second. Switch the restart off and the two agree everywhere. Counter resets are the whole reason the function exists.
  • Memory. 240 MB at minute 10 and 186 MB at minute 13: a saw-tooth. With the restart off it climbs to 360 MB without pause. Only a gauge, read directly, shows this.

RED and USE

A service can expose thousands of metrics. Two short checklists tell you which ones to put on the first dashboard and alert on.

RED: for every serviceUSE: for every resource
Stands forRate, Errors, DurationUtilisation, Saturation, Errors
AsksWhat are the users of this service getting?Is this CPU, disk, pool or queue the bottleneck?
First signalRequests per second: sum(rate(http_requests_total[5m]))How busy it is: CPU in use ÷ CPU available; connections in use ÷ pool size
SecondThe share that fail: the error ratio aboveHow much work is waiting: run-queue length, requests queued, throttled periods
ThirdHow long they take: p50 and p99 from the histogramError counts: disk errors, dropped packets, failed allocations
Alert on it?Yes: these are symptoms users feelRarely page on it. Use it to diagnose, and to plan capacity

Google's SRE book lists four "golden signals": latency, traffic, errors and saturation. That is RED plus the S of USE. Whichever names you use, the working rule is the same: alert on what users experience and investigate with what machines report. High CPU is not a problem if every request is fast and correct. Slow requests are a problem whatever the CPU says.

Cardinality

Every distinct combination of label values is its own time series, held in memory and written to disk. The number of series a metric produces is the product of the number of values of each label, and it is called the metric's cardinality.

http_request_duration_seconds_bucket

   services   pods each   routes   status codes   histogram buckets
      10    ×    20     ×   50   ×      5       ×        12          =        600,000 series

add one label, customer_id, with 20,000 customers:
                                                   600,000 × 20,000  = 12,000,000,000 series

The first number is a healthy Prometheus. The second is a server that runs out of memory within minutes, and it takes only one line of code that looked helpful. The rule: a label's values must come from a small, bounded set. Status code, HTTP method, route template (/orders/:id, never /orders/812), region and version are fine. User IDs, email addresses, request IDs, session tokens, full URLs and error messages are not: they belong in logs and traces, which are built for one-of-a-kind values. To find what is costing you, ask Prometheus itself:

# The ten metric names with the most series
topk(10, count by (__name__) ({__name__=~".+"}))

# How many values does one label have on one metric?
count(count by (path) (http_requests_total))

Use case: SoundCloud and why Prometheus pulls

Prometheus was started at SoundCloud in 2012 by engineers who had come from Google and missed its internal monitoring system, Borgmon. SoundCloud was moving from one large application to hundreds of small services on a cluster scheduler of its own, with instances appearing and disappearing constantly, and the monitoring tools of the time assumed a list of named hosts that someone maintained by hand. The team wanted three things those tools did not offer together: a data model in which every series carries labels, so that one question can be asked across all instances of a service or cut by version or zone; a query language that works on those labels; and a server simple enough to keep running when everything else is broken, with no dependency on a distributed database. They chose to pull metrics, discovering targets from the scheduler, so that a new instance is monitored as soon as it exists and a missing one is noticed. Prometheus was developed in the open, announced publicly in 2015, and became the second project, after Kubernetes, to join the Cloud Native Computing Foundation. Its exposition format has since become a standard that nearly every piece of infrastructure software speaks, which is the real reason to learn it: whatever you operate, there are Prometheus metrics for it.

⚠️
Common mistakes
  • Graphing or alerting on a raw counter. Its value depends on when the process started. Use rate.
  • rate(sum(...)) instead of sum(rate(...)). Resets in individual pods turn into false spikes.
  • Averaging percentiles, or using a summary and trying to combine pods. Use histograms and histogram_quantile over the summed buckets.
  • Histogram buckets that do not bracket your target. If the objective is 300 ms and the buckets jump from 100 ms to 1 s, the percentile is a guess.
  • Unbounded labels: user IDs, raw paths, request IDs. One of them can take the whole monitoring system down.
  • A rate window shorter than a few scrape intervals. With two samples or fewer there is nothing to compute.
  • Dashboards of averages. A mean of 80 ms hides the 1% of users waiting three seconds.
  • Monitoring only causes (CPU, memory) and never symptoms (errors, latency).
  • No alert on the monitoring itself. If Prometheus is down, silence looks like health.

Interview drill

Explain it simply: What is the difference between a counter, a gauge and a histogram?

How a strong answer sounds
A counter only increases, and restarts from zero when the process restarts: requests served, errors. Its absolute value is meaningless, so I always query its rate. A gauge is a current value that goes up and down, such as memory in use or queue length, and I read it directly. A histogram records observations, typically request durations, into buckets by size; each bucket is itself a counter. From the rate of the buckets I can compute percentiles with histogram_quantile, and because buckets are plain counters they can be summed across pods first, which gives a correct percentile for the whole service. A summary computes percentiles inside each process and cannot be aggregated that way.

Deeper: Prometheus' memory use has tripled in a week and it keeps being killed. How do you find and fix the cause?

How a strong answer sounds
Memory in Prometheus follows the number of active time series, so I would look for a jump in cardinality. Prometheus reports it about itself: prometheus_tsdb_head_series over time shows when the growth began, and the TSDB status page or a query such as topk(10, count by (__name__)({__name__=~".+"})) shows which metric names hold the most series. For the worst metric I count the values of each label, and there is usually one label with tens of thousands of values: a user or tenant ID, a full URL path with IDs in it, a pod name multiplied by constant redeployments, or an error message. I would match the start of the growth against deployments to find the change that introduced it. The immediate fix is in the scrape configuration: a metric relabelling rule that drops the label or the whole metric, which stops the bleeding without a code change. The proper fix is in the instrumentation: replace the raw value with a bounded one, such as the route template, and move the detail to logs or traces. To stop it happening again I would set a per-target sample limit so that one misbehaving service fails its own scrape instead of taking the server down, alert on series growth, and review new metrics' labels the way we review schema changes.

🧠 Key takeaways

  • A time series is a metric name plus a set of label values. Counters only rise, gauges move both ways, histograms count observations into buckets.
  • Prometheus pulls: it discovers targets, scrapes /metrics on an interval, and records up for each.
  • Query counters with rate, which handles restarts. Rate first, then sum.
  • Percentiles for a whole service come from histogram_quantile over summed bucket rates, never from averaged percentiles.
  • RED for services (rate, errors, duration); USE for resources (utilisation, saturation, errors). Alert on symptoms.
  • Series count is the product of label values. Labels must be bounded: no IDs, raw paths or messages.

Check your understanding

A dashboard plots http_requests_total directly. After a deployment the line drops to zero and starts climbing again. What is wrong?

A counter's absolute value only reflects how long the process has been running. Its rate of increase is the meaningful quantity, and rate handles the reset.

A service runs on 20 pods. Which expression gives its 99th-percentile latency correctly?

Bucket counters can be summed across pods, and the percentile is then computed from the combined distribution. Percentiles themselves cannot be averaged.

A developer adds a user_id label to a request counter, on a service with two million users. What happens?

Each label value multiplies the number of series. Unbounded identifiers belong in logs and traces, not in metric labels.

Why does Prometheus' pull model make a dead target easy to detect?

With push, a silent service is indistinguishable from one with nothing to report. With pull, the scraper notices that it could not get an answer.

Which signal is the best thing to page someone for?

Errors and latency are symptoms that users feel. Utilisation and restarts are causes worth graphing and investigating, but each can be high while users are perfectly well served.
