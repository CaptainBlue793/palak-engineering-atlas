Git Workflows

Every pipeline in this course starts with a Git event: a push, a pull request, a merge to main, a tag. Infrastructure is reviewed as a diff, deployed by a commit, and rolled back by reverting one. This chapter is not a Git tutorial for beginners; it is the part of Git that operations depends on: what commits and branches really are, merge versus rebase, how a pull request gates a change, which branching model a team picks, and why release tags must never move.

Commits are snapshots; branches are pointers

A commit records the full state of the project's files at one moment, plus metadata: author, time, message, and the ID of its parent commit (two parents for a merge). Its ID, the SHA, is a hash of all of that. Change anything, even the parent, and you get a different SHA. That is why a commit ID identifies exactly one version of the code forever, and why CI systems, container image tags and deploy records all use it.

A branch is just a name that points at one commit. Committing on a branch creates a new commit whose parent is the old tip, then moves the name forward. HEAD is the name of the branch you have checked out. Creating a branch is therefore free: it is a 41-byte file.

$ git log --oneline --graph -5
* 4f2a9c1 (HEAD -> main, origin/main) Retry payment calls with backoff
* 9b1e2d0 Add /health endpoint
* 31c07aa Pin base image by digest
$ git rev-parse main                # a branch resolves to one commit
4f2a9c1e7d3b0a65c2f9e4d81b7a3c6e5f0d2b19
$ cat .git/refs/heads/main            # …and is literally stored as that SHA
4f2a9c1e7d3b0a65c2f9e4d81b7a3c6e5f0d2b19

Merge, fast-forward, rebase and squash

When work on a feature branch is finished, it has to be combined with main. There are four ways, and they produce different histories:

  • Fast-forward: if main has not moved since the branch was created, Git just moves the main pointer to the branch's tip. No new commit.
  • Merge commit: if both have moved, Git creates a commit with two parents that joins them. History shows exactly what happened, including the branch.
  • Rebase: replays the branch's commits on top of the current main, creating new commits with new SHAs, so the result is a straight line. The old commits are abandoned.
  • Squash merge: combines all of the branch's changes into one new commit on main. Common for pull requests: one PR becomes one commit, which is easy to read and to revert.

Slate-blue circles are commits on main, orange ones on feature; a hollow circle is a merge commit with two parents. Faded commits were replaced by a rebase: they still exist in your local reflog, and in the clone of anyone who already pulled them.

The rebase is the one to watch. The rebased commits have the same changes but new SHAs, because their parent changed. If nobody else has the old commits, that is harmless and gives a tidy line. If a colleague already pulled the branch, their copy now disagrees with yours, and pushing requires --force, which overwrites theirs. Hence the rule: rebase your own unpublished work freely; never rebase a branch others are using, and if you must force-push your own branch, use git push --force-with-lease, which refuses if someone else pushed in the meantime.

Pull requests: the gate before main

A pull request (GitHub, Bitbucket) or merge request (GitLab) is a proposal to merge a branch, with a diff, a discussion and automated checks. In an operations team it is the control point for everything: application code, Dockerfiles, Kubernetes manifests and Terraform all change through PRs, so every production change has an author, a reviewer, a test run and a record. Branch protection rules on main enforce it: no direct pushes, required status checks, at least one approval, and often "branch must be up to date".

Branching models: trunk-based vs GitFlow

A branching model is a team's agreement on which branches exist and how long they live. Two dominate:

AspectTrunk-based developmentGitFlow
Long-lived branchesOnly mainmain, develop, plus release/* and hotfix/*
Feature branch lifeHours to a day or twoDays to weeks
Unfinished featuresMerged but hidden behind feature flags (Chapter 17)Kept on their branch until done
Merge conflictsSmall and frequentLarge and painful at integration time
ReleaseAny commit on main that passes CI can deployCut a release branch, stabilise, merge to main and tag
FitsWeb services deployed many times a dayVersioned products shipped on a schedule (mobile apps, installed software)

The DORA research (Chapter 1) found trunk-based development, with three or fewer active branches and merges at least daily, to be one of the practices that predicts high delivery performance. Most teams running services in the cloud use it, and the rest of this course assumes it.

Tags, releases and undoing changes

A tag is a name for one commit, like a branch that never moves. Releases are tagged with a version, usually semantic versioning: v2.4.1 means major 2 (breaking changes bump it), minor 4 (new features), patch 1 (fixes). Use annotated tags, which record who tagged and when, and push them explicitly:

$ git tag -a v2.4.1 -m "Fix checkout timeout"   # annotated tag on the current commit
$ git push origin v2.4.1                       # tags are not pushed by default

# Undo a bad change that is already on main: add a new commit that reverses it.
$ git revert 7c1d0e2                            # history stays intact; everyone just pulls
# Never on a shared branch: git reset --hard + push --force rewrites what others have.

Git lets you delete and re-create a tag on a different commit and force-push it. Never do that to a published release tag. Anyone who refers to v2.4.1 expects the same code every time, and tooling relies on it: Go modules, Helm charts and, notably, GitHub Actions, where uses: some/action@v4 fetches whatever commit the tag points to today. In March 2025 attackers who had obtained a token for the popular tj-actions/changed-files action moved its version tags to a malicious commit, and thousands of workflows ran it on their next build (Chapter 48). That is why later chapters pin actions by full commit SHA rather than by tag.

🏢
Use case: trunk-based development at very large scale

Google keeps most of its code in a single repository and develops on one trunk. A 2016 paper described about 25,000 engineers making some 16,000 human commits a day to it, with no long-lived development branches; releases are cut from a known-good trunk commit, and unfinished work ships behind flags. It works because every change is small, reviewed, and tested automatically before it lands. The same discipline at a ten-person team gives the same benefit: nobody spends a week merging a month-old branch.

⚠️
Common mistakes
  • Rebasing or force-pushing a shared branch. Teammates' clones diverge. Rebase only your own unpublished work; use --force-with-lease.
  • git reset --hard on main to undo a deploy. Use git revert: a new commit, safe for everyone.
  • Moving a published tag. Releases must be immutable; cut v2.4.2 instead.
  • Long-lived feature branches. The merge at the end becomes a project of its own. Merge small changes daily behind flags.
  • Committing secrets. Deleting the file in a later commit does not remove it from history. Rotate the secret immediately (Chapter 28).
  • No branch protection on main. One direct push skips tests and review and deploys straight to production.

Interview drill

Explain it simply: What is the difference between merge and rebase, and when would you use each?

How a strong answer sounds
Both combine work from two branches. Merge creates a merge commit with two parents and keeps history exactly as it happened. Rebase replays my commits on top of the other branch as new commits with new SHAs, giving a straight line. I rebase my own local branch onto main before opening a PR to keep it current and readable, and I never rebase a branch someone else has pulled, because it rewrites commits they already have. For landing PRs, many teams use squash merge so each PR becomes one revertible commit on main.

Deeper: A bad commit was merged to main an hour ago and deployed; three other PRs have merged since. How do you roll back?

How a strong answer sounds
First, mitigate: if the deploy system can redeploy the previous good image or the change is behind a flag, do that immediately, because it is faster than any Git operation. Then fix history with git revert <sha>, which adds a new commit undoing only that change and leaves the three later PRs in place; it goes through a PR and CI like any change, and the pipeline deploys it. I would not reset and force-push main: it would drop the later work, break everyone's clones and remove the audit trail. Afterwards, the postmortem asks why CI and review did not catch it.

🧠 Key takeaways

  • A commit is a snapshot identified by a hash of its content and parents; a branch is a pointer to one commit.
  • Fast-forward moves a pointer; merge adds a two-parent commit; rebase rewrites commits with new SHAs; squash makes one new commit.
  • Rebase only unpublished work; force-push only your own branch, with --force-with-lease.
  • Pull requests plus branch protection make every change reviewed, tested and recorded before it reaches main.
  • Trunk-based development (short branches, daily merges, feature flags) suits continuously deployed services.
  • Release tags are immutable; undo shared history with git revert, not reset.

Check your understanding

You rebase your feature branch onto the latest main. What happens to your branch's commit SHAs?

A commit's ID covers its content and its parent. Rebase creates new commits with new parents, so every replayed commit gets a new SHA.

When does git merge feature on main produce a fast-forward rather than a merge commit?

If main has not moved since the branch was created, Git can just move the main pointer forward. If both moved, a merge commit is needed (no conflicts required either way).

A bad commit reached main and later commits followed it. What is the safe way to undo it in Git?

Revert adds history instead of rewriting it, so later commits stay and nobody's clone breaks. Reset and rebase rewrite shared history.

Which situation fits trunk-based development best?

Trunk-based relies on small, frequent merges, automated tests and feature flags, which is what continuously deployed services have. Scheduled versioned releases suit GitFlow better.

Why should a published release tag such as v2.4.1 never be moved to another commit?

Git allows it with force, which is the danger: tools that fetch by tag (actions, modules, charts) get different code without anyone noticing. That is how the 2025 tj-actions compromise spread.
