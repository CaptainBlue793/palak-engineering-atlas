Kubernetes Architecture

One container on one host is easy. A few hundred containers across fifty machines raise questions that docker run cannot answer: which machine has room, what restarts a container when its machine dies, how a new version replaces the old without dropping requests. Kubernetes answers them with one idea. You store a description of what you want in a database, and a set of independent programs each keep comparing what exists with what is wanted and close the gap. This chapter is about those programs: what each one does, what happens between kubectl apply and a running container, and what keeps working when a part of the system is down. The last question is the one interviewers ask, and the simulator lets you answer it by breaking things.

The shape of a cluster

A Kubernetes cluster is a set of machines, called nodes, in two roles. The control plane holds the cluster's state and makes decisions. The worker nodes run your containers. Your workloads are the data plane: the part that serves users. Keep that split in mind, because the most useful fact in this chapter follows from it: the data plane does not need the control plane in order to keep running.

The smallest thing Kubernetes runs is a pod: one or more containers that share a network address and are always placed on the same node. For now, read "pod" as "a running copy of your container". Chapter 12 covers pods and the objects that manage them.

The scheduler and the controllers hold no state of their own. Each one watches the API server, and everything it does is a write back to the API server. That is why the design is easy to extend: a new feature is one more controller watching one more kind of object. On a managed service (EKS, GKE, AKS) the provider runs all of this for you, across zones, and you only ever see the API endpoint.

Nodes and the kubelet

Every node, including the control plane's own, runs three things.

  • The kubelet is the node's agent. It watches the API server for pods assigned to its node, tells the container runtime to start and stop containers so that reality matches, runs the health checks you define, and reports the status of the node and its pods back. It also sends a heartbeat every few seconds; when the heartbeats stop for about 40 seconds (the long-standing default), the control plane marks the node NotReady.
  • The container runtime, usually containerd, pulls images and runs containers. It is the same technology as in Chapter 7, driven by the kubelet instead of by you.
  • The network components: a plugin that gives each pod an IP address reachable from every other pod, and kube-proxy (or an equivalent), which programs the node so that traffic to a Service's address is spread over the pods behind it.

The kubelet is the only component that touches containers. The scheduler never starts anything: it writes a node's name into a pod object, and that node's kubelet notices.

Desired state and reconciliation

You do not tell Kubernetes to do things. You tell it what should be true, and it works out what to do. A request like "run three copies of this image" is stored as an object whose spec says replicas: 3. A controller then runs the same loop for ever:

This is called level-triggered behaviour: the controller reacts to the current state, not to a stream of events it must not miss. If a controller is down for an hour, nothing is lost. When it returns it sees three wanted and one existing, and creates two. The same property makes the system self-healing without special cases: a pod that crashed, a pod that someone deleted and a pod lost with its node are all just "fewer than wanted".

Larger behaviours come from chaining small loops. Here is everything that happens between a command and a running container.

The API and kubectl

Everything in a cluster is an object in the API, and every object has the same five parts.

apiVersion: apps/v1              # which API group and version defines this kind
kind: Deployment                 # what sort of object
metadata:
  name: web
  namespace: shop                # a folder for names and permissions
  labels: { app: web }           # free-form tags: how objects find each other
spec:                            # what you want. You write this
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: web
          image: ghcr.io/acme/web:4.18.2
status:                          # what is true. Controllers write this; you only read it
  replicas: 3
  readyReplicas: 3

kubectl is an HTTP client for that API and nothing more. It reads the server's address and your credentials from a kubeconfig file and turns each command into a request, which you can see by adding -v=6.

$ kubectl config current-context                 # which cluster am I about to change? Check before every apply
prod-eu-west-2
$ kubectl get pods -n shop -v=6 2>&1 | grep GET
GET https://10.0.0.10:6443/api/v1/namespaces/shop/pods?limit=500 200 OK in 18 milliseconds

$ kubectl apply -f deployment.yaml               # make the cluster match this file (create or update)
$ kubectl diff -f deployment.yaml                # what would apply change?
$ kubectl get deploy,rs,pods -n shop -o wide     # list; -o yaml prints the whole object, status included
$ kubectl describe pod web-7c9d8-x2kfp -n shop   # one object in detail, with its recent events at the end
$ kubectl logs web-7c9d8-x2kfp -n shop --previous # output of the container, or of its previous crashed run
$ kubectl exec -it web-7c9d8-x2kfp -n shop -- sh # a shell in a running container
$ kubectl get events -n shop --sort-by=.lastTimestamp
$ kubectl explain deployment.spec.strategy       # built-in documentation for any field

When something is wrong, the order is nearly always get (what state is it in?), describe (what do the events say?), logs (what did the application say?). The events at the bottom of describe are the controllers and the kubelet telling you what they tried: "0/3 nodes are available: insufficient memory", "Back-off pulling image".

The model follows Kubernetes' defaults. A kubelet restarts its own containers and needs nothing else to do so. The control plane marks a node NotReady after 40 seconds without a heartbeat and removes its pods from the Service; after 5 more minutes it deletes them, and the ReplicaSet controller creates replacements. (A real cluster shows such pods as Terminating until the node returns.) The scheduler only places pods on nodes it believes are ready. Every control loop needs both the API server and etcd. "Requests succeeding" is the share of the Service's current targets that can actually answer.

Things to try. Press Reset between experiments.

  • With everything up, delete a pod. The explanation lists five separate actions inside one second: the Service drops the pod, the ReplicaSet controller creates a new pod object, the scheduler assigns it, a kubelet starts it, and the Service adds it. That is the chain from the sequence diagram, run by loops that never call each other.
  • Switch off the API server. Crash a container on node-1: the kubelet restarts it and requests stay at 100%. Now try kubectl get pods (connection refused) and kubectl scale (nothing recorded). The workload is fine and you are blind and unable to change anything. etcd off behaves the same way with a different error.
  • Switch off only the scheduler and scale to 5. Five pod objects exist, two are Pending with no node, and three keep serving.
  • Switch off only the controller manager and delete a pod. Two of three remain and nothing replaces the third. Requests drop to 67%, because the Service's target list is also maintained by a controller and still contains the deleted pod. Wait six minutes: nothing changes. A cluster without its controllers does not heal.
  • Power off node-2. At once, 67% of requests succeed, and the API says the node is Ready and all three pods are Running. Wait a minute: the node is NotReady, the Service has dropped its pod, and requests are back to 100% on two pods. Wait six minutes: the lost pod has been replaced on node-1. Recovery from a dead node takes seconds for traffic and minutes for capacity, which is one reason to run more than the bare minimum of replicas.
  • Stop only the kubelet on node-2 and wait six minutes. The control plane cannot tell this from a dead node, so it replaces the pod on node-1. The original container is still running on node-2, shown with a dashed outline, known to nobody until its kubelet returns and removes it.
  • Power off node-2 with the controller manager off as well, and wait. Requests stay at 67% for good: the component that would have noticed is the one that is down.
  • Reconciliation, tested: the model was driven through 4,000 random actions and component failures. On 778 occasions everything was switched back on and six minutes allowed to pass, and every time the cluster returned to exactly the desired number of running, reachable pods, whatever had been done to it before.

Use case: Spotify deletes its clusters, twice

In 2018, while Spotify was moving its services onto Kubernetes, an engineer deleted a production cluster by mistake, believing a browser tab showed a test cluster. Rebuilding it took a little over three hours, because the scripts that were supposed to recreate a cluster had gaps nobody had hit before. A month later, while the team was moving cluster creation into Terraform to prevent exactly that, a mistake in handling its state led to two production clusters being deleted. Spotify's engineers told the story in a conference talk the following year, under a title that gives away the ending: there was no impact on users. Two things from this chapter explain why. The clusters held no unique state: everything that ran in them was described in files in Git, so a new cluster could be brought to the same condition by applying the same descriptions, which is what desired state buys you. And the services were built to find each other through service discovery and to fail over, so traffic simply went to the copies that still existed. The lessons the team drew were to back up the cluster's state, to practise restoring it, to codify how clusters are created, and to treat a cluster as something replaceable. Chapter 18 and Chapter 20 return to both halves of that.

Common mistakes
  • Thinking in commands. "Kubernetes restarted my pod" hides which loop acted and why. Ask what the desired state is and which controller owns it.
  • Assuming kubectl apply returning means the application is running. It means the object was stored. Check the rollout.
  • Editing live objects by hand and not the files. The next apply from Git overwrites the edit, or worse, does not.
  • No backup of etcd on a self-managed cluster. Everything else can be rebuilt from Git; etcd is the one place with unique state.
  • One control plane node. etcd needs a majority: one member tolerates no failures, three tolerate one.
  • Believing the API during a node failure. For the first 40 seconds the API still says the node is fine and its pods are running.
  • Running kubectl against the wrong cluster. Check the context; make production's prompt look different.
  • Treating a control plane outage as a total outage. Running pods keep serving. What you have lost is the ability to change or repair anything, which is urgent but different.

Interview drill

Explain it simply: What happens when you run kubectl apply -f deployment.yaml?

How a strong answer sounds
kubectl reads the file and sends it to the API server over HTTPS. The API server authenticates me, checks that I am allowed to create Deployments in that namespace, runs admission checks, validates the object and writes it to etcd, then replies. At that point nothing is running. The Deployment controller, which watches the API, sees the new Deployment and creates a ReplicaSet for it; the ReplicaSet controller sees that three pods are wanted and none exist, and creates three Pod objects with no node assigned. The scheduler watches for pods without a node, picks a suitable node for each and writes the binding. The kubelet on each chosen node sees a pod assigned to it, has the container runtime pull the image and start the containers, runs the probes and reports the status back. If the pods are behind a Service, the endpoints controller adds them once they are ready and kube-proxy on each node starts routing to them. Every step is a separate loop reacting to state in the API, not one component calling the next.

Deeper: The API server of a cluster is unreachable. What still works and what does not?

How a strong answer sounds
The workloads keep running. Containers that are up stay up, and traffic keeps flowing, because the kubelets, the container runtime and the networking rules on each node work from what they already know. A kubelet will even restart a container that crashes, since that needs only the pod definition it already has. What stops is everything that passes through the API, which is everything else. I cannot deploy, scale or inspect with kubectl. The controllers and the scheduler cannot observe or act, so a deleted or evicted pod is not replaced, a failed node is not detected and its pods are not moved, autoscaling stops, and Services are not updated when pods change. So the cluster is frozen in its last state: fine while nothing changes and steadily worse as things fail without being repaired. That makes it urgent but not a user-facing outage in itself. I would check whether it is the API server or etcd underneath it, since an API server that cannot reach an etcd quorum fails in the same way, and in a managed cluster I would look at the provider's status and at whether something is overloading the API, such as a controller in a tight loop.

🧠 Key takeaways

  • The control plane is the API server, etcd, the scheduler and the controller manager. Nodes run a kubelet, a container runtime and network components.
  • Only the API server talks to etcd, and every other component talks only to the API server.
  • You declare desired state; controllers loop: observe, compare, act. They react to the present difference, so nothing is lost when one restarts.
  • The scheduler only assigns pods to nodes. The kubelet is the only thing that starts containers.
  • Every object has apiVersion, kind, metadata, spec and status. kubectl is an HTTP client for the API.
  • If the control plane is down, running pods keep serving and nothing can be changed or repaired.
  • The API's view lags behind reality: a dead node looks healthy for about 40 seconds, and its pods are replaced only after minutes.

Check your understanding

The scheduler of a cluster has crashed. An engineer scales a Deployment from 3 to 5 replicas. What happens?

The API server accepts the change and the ReplicaSet controller creates the pod objects. Choosing a node is the scheduler's job alone, so the new pods wait.

Which component actually starts a container on a node?

The scheduler writes a node name into the pod object. The kubelet on that node sees the assignment and tells the runtime to start the containers.

The whole control plane is unreachable for ten minutes. During that time a container in a running pod crashes. What happens to it?

Restarting a container on the same node is a local decision by the kubelet. Moving a pod to another node would need the control plane.

What does "level-triggered" mean for a Kubernetes controller?

A controller that was down while pods were deleted needs no record of the deletions. On return it counts, compares with the spec and creates what is missing.

A node loses power. For the first half-minute, kubectl get pods still shows its pods as Running. Why?

The API holds the last status the kubelet reported. Until the node controller declares the node NotReady, nothing in the cluster knows anything is wrong, and the Service still sends traffic there.
