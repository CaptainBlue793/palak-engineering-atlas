IAM & Least Privilege

Every request to a cloud API is checked twice: who is asking, and are they allowed to do this to that? Identity and access management (IAM) is the system that answers, and it is the real security boundary of a cloud account. A network rule protects a port; an IAM policy protects everything. This chapter covers the vocabulary (principals, roles, policies), the exact order in which a request is evaluated, how to write permissions that grant only what is needed, and how machines get credentials without anyone storing a key. The simulator is a small policy engine: change the policies and watch the decision and the error message change.

  • Write a least-privilege policy and spot a dangerous wildcard
  • Explain how an instance, a pod and a CI job get temporary credentials
  • Turn an "access denied" message into the policy that needs changing

Principals, roles and policies

IAM has two halves. Authentication establishes who is making a request; authorisation decides whether that identity may perform it. Whatever makes requests is a principal, and there are only a few kinds.

PrincipalWhat it isCredentialsUse it for
Root userThe identity that created the account. Its own account's policies cannot restrict itPassword and a second factorAlmost nothing: lock it away and use it only for the few tasks that require it
UserA named identity inside one accountA password, and optionally long-lived access keysLegacy. People should sign in through the company's identity provider instead
GroupA set of users that share policiesnone of its ownGranting the same permissions to many users. A group is not a principal and cannot make requests
RoleAn identity with permissions and no password or keys. Something assumes it and receives temporary credentialsTemporary: issued for minutes or hoursEverything: people (through single sign-on), instances, pods, functions, CI jobs, other accounts
ServiceThe provider's own services acting for youmanaged by the providerLetting, say, the autoscaling service launch instances in your account

Azure and Google Cloud use different words for the same parts: Azure has users, service principals and managed identities, with role assignments at a scope; Google Cloud has users and service accounts, with role bindings on a resource. The ideas in this chapter carry over unchanged.

Permissions are written in policies. A policy is a JSON document with a list of statements, and every statement answers the same five questions.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ReadWriteBuildArtifacts",
    "Effect": "Allow",                                   // Allow or Deny
    "Action": ["s3:GetObject", "s3:PutObject"],              // which API calls
    "Resource": "arn:aws:s3:::acme-artifacts/*",           // on which resources
    "Condition": {                                        // only when...
      "Bool": { "aws:SecureTransport": "true" }
    }
  }]
}

(The // notes in these listings are annotations; real JSON has no comments.) The fifth question, who, is answered by where the policy is attached. An identity-based policy is attached to a user, group or role, and the "who" is that identity. A resource-based policy is attached to a resource, such as a bucket or a queue, and names the "who" in a Principal element. Resources are named by ARN (Amazon Resource Name), and both actions and ARNs accept * as a wildcard.

A role has two policies of its own. Its trust policy says who may assume it, and its permissions policies say what it can do once assumed. Assuming a role is an API call to the security token service, which returns an access key, a secret and a session token that all expire together.

$ aws sts get-caller-identity             # the first command when anything is denied: who am I?
{
    "UserId": "AROAEXAMPLEID:ci-run-8841",
    "Account": "111122223333",
    "Arn": "arn:aws:sts::111122223333:assumed-role/deploy/ci-run-8841"
}

$ aws sts assume-role --role-arn arn:aws:iam::111122223333:role/deploy --role-session-name debug \
    --query 'Credentials.[AccessKeyId,Expiration]' --output text
ASIAEXAMPLEKEY000001    2026-10-07T15:42:10+00:00

How a request is evaluated

Several policies can apply to one request, and they combine by fixed rules. Three sentences cover nearly every case.

  • Everything is denied by default. With no policy that allows a request, it is refused. This is an implicit deny.
  • An explicit deny always wins. If any applicable policy has a matching Deny statement, the request is refused, whatever else allows it.
  • Otherwise an allow is needed from the right place. Inside one account, an allow in either the identity's policy or the resource's policy is enough. Across accounts, both sides must allow: the caller's account must let the caller ask, and the resource's owner must let that caller in.

Two more kinds of policy only ever take away. A permissions boundary on a role and an organisation's service control policy on an account (Chapter 30) set a ceiling: a request must be inside the ceiling and be allowed by an ordinary policy. Neither one grants anything.

    Things to try. Read the last line of each denial: it is the wording AWS uses, and its ending names the kind of policy that refused.
    
  
      
    
    • The starting point is the pipeline reading an artefact with a policy that names two actions on one bucket. One statement matches and the request is allowed.
      • 
    
    • Ask for the payroll bucket. Denied, "because no identity-based policy allows" it: nothing was forbidden, it was simply never granted. Now change the role's policy to s3:* on *. The pipeline can read payroll. Nobody decided that; the wildcard did.
      • 
    
    • Keep the wide policy and delete an artefact. Allowed. Add the bucket policy that denies deletes to everyone: denied "with an explicit deny in a resource-based policy", although the role has s3:*. This is how you protect something from every role at once, including ones that do not exist yet.
      • 
    
    • Add the read-only boundary and try to write. Denied, "because no permissions boundary allows" it, whichever identity policy is selected. Then read payroll again with the wide policy: still allowed. A boundary limits the kind of action; it is not a substitute for naming the resources.
      • 
    
    • Switch to the partner's role and read an artefact. Its own policy allows reading any bucket, and it is denied "because no resource-based policy allows" it. Select the bucket policy that names the partner: allowed. Now ask for payroll as the partner: denied again, because that bucket's owner never let them in. A broad policy in someone else's account cannot reach into yours. A broad policy in your own can.

    Least privilege
    
  
    Least privilege means each identity can do what its job needs and nothing more. The reason is not distrust of colleagues. Credentials leak, code has bugs, and a request can be forged through a vulnerable application. When that happens, the permissions of the identity involved are the size of the incident.
    
  
    
    
    
      
    Too broadWhat goes wrongNarrower
    
      
        
    "Action": "*", "Resource": "*"The identity is an administrator. A leaked key is a lost accountList the actions the workload calls, on the resources it uses
    
        
    "Action": "s3:*" on *Reads every bucket in the account, including ones created later, and can delete thems3:GetObject and s3:PutObject on one bucket's ARN

    Nobody writes a perfect policy first time, so treat it as a loop. Start from nothing, or from a policy generated out of what the workload actually called during a test run. Add what a denial shows to be missing, one statement at a time. Then, every few months, remove what the provider's access reports show has not been used. Conditions tighten a statement further without listing more resources: require encryption in transit, restrict to a network or an organisation, or allow an action only on resources that carry a given tag.
    

  
    Instance and workload identity
    
  
    A program running in the cloud needs credentials to call the cloud's APIs. The wrong answer is an access key in a configuration file: it never expires, it is copied into images and backups, and sooner or later into a repository. The right answer is that the platform gives the workload a role, and the workload fetches short-lived credentials when it needs them.
    
  
    
    
    
      
    Where the code runsHow it gets a roleWhere the credentials come from
    
      
        
    A virtual machineAn instance profile in the launch template (Chapter 3)The instance metadata service, at 169.254.169.254
    
        
    A container or function on a managed platformA task or execution role in its definitionInjected by the platform
    
        
    A Kubernetes podIts service account is mapped to a cloud roleA signed token mounted in the pod, exchanged for credentials
    
        
    A CI job outside the cloudThe role's trust policy accepts the CI system's identity tokensA token signed by the CI provider, exchanged for credentials
    
        
    A personSingle sign-on maps their group to a roleThe sign-in portal or the CLI's login command
    
          
    
    
  
    
  
    The SDKs find these credentials by themselves and refresh them before they expire, so application code contains no secrets at all. On an instance you can see the mechanism with curl:
    

    # Version 2 of the metadata service: first obtain a session token with a PUT...
$ TOKEN="$(curl -sS -X PUT http://169.254.169.254/latest/api/token -H 'X-aws-ec2-metadata-token-ttl-seconds: 300')"
# ...then present it. The answer is the role's temporary credentials.
$ curl -sS -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/web-role
{ "AccessKeyId": "ASIAEXAMPLEKEY000002", "SecretAccessKey": "...", "Token": "...", "Expiration": "2026-10-07T18:21:07Z" }
    
  
    The first version of this service answered any plain GET. That turned every bug that lets an attacker make a server fetch a URL (server-side request forgery) into a way to read the server's credentials. Version 2 requires the PUT step and a header, which such bugs can rarely produce, and keeps the token from travelling beyond the instance. Requiring version 2 is the http_tokens = "required" line in Chapter 3's launch template.
    
  
    For a CI system the same idea removes stored keys from the pipeline. The CI provider signs a token describing the job; the role trusts tokens with the right claims.
    

    // Trust policy of role/deploy: who may assume it
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:acme/checkout:ref:refs/heads/main"
      }
    }
  }]
}

    Use case: Capital One, 2019
    In March 2019 an attacker took data on about 100 million people in the United States and 6 million in Canada from Capital One's storage buckets; the bank learned of it that July. Court documents and the bank's statements describe the path. A web application firewall running on a cloud instance was misconfigured in a way that let the attacker make it send requests of the attacker's choosing, a server-side request forgery. The attacker pointed it at the instance metadata service, which in its first version answered any GET, and received the temporary credentials of the firewall's role. That role had permission to list the account's buckets and read their contents, which a firewall has no need to do, and the attacker used the credentials to copy the data out. The cloud provider's infrastructure did what it was configured to do. The US banking regulator fined Capital One $80 million in 2020, and AWS introduced version 2 of the metadata service a few months after the breach became public. Two controls from this chapter would each have broken the chain: a metadata service that demands a session token, and a role that could only do what a firewall needs.
    
  
    

  
    ⚠️
    Common mistakes
    
    
      
      
    • Using the root user, or leaving it without a second factor.
      • 
      
    • Long-lived access keys in code, images, CI variables or laptops. Use roles and temporary credentials.
      • 
      
    • Wildcards to make an error go away. "Action": "*" fixes the denial and creates the incident.
      • 
      
    • Fixing a denial by reading only the identity policy. The error says which kind of policy refused; an explicit deny or a boundary cannot be fixed by adding an allow.
      • 
      
    • Trust policies that trust too much: a whole account, or every repository of a CI provider, with no condition.
      • 
      
    • One role for everything. Each workload should have its own.
      • 
      
    • Forgetting cross-account needs both sides. A bucket policy alone, or an identity policy alone, is not enough.
      • 
      
    • Never removing permissions. Roles collect them. Review unused access on a schedule.
      • 
      
    • Leaving the old metadata service enabled. Require version 2 everywhere.
      • 
    
    

  
    🎤
    Interview drill
    
    
    Explain it simply: What is the difference between an IAM user and an IAM role?
    
    
    How a strong answer sounds
    A user is a permanent identity with long-lived credentials: a password and possibly access keys that work until someone rotates them. A role is an identity with permissions and no credentials of its own. Something trusted assumes it, whether a person through single sign-on, an instance, a pod, a CI job or another account, and receives temporary credentials that expire in minutes or hours. A role has a trust policy that says who may assume it and permission policies that say what it can do. I use roles for everything, because nothing long-lived exists to leak, and keep users, if any, for break-glass access.
    
    
    Deeper: A service's role has s3:GetObject on a bucket, and the call still fails with AccessDenied. What could be denying it?
    
    
    How a strong answer sounds
    First I confirm who the caller really is with sts get-caller-identity, because the code may be using different credentials from the ones I think. Then I read the error, which now usually names the kind of policy involved. The candidates, in evaluation order: an explicit deny somewhere, such as a bucket policy that denies requests not using TLS or not coming from a given network, or an organisation's service control policy; a permissions boundary on the role that does not include the action; a session policy if the role was assumed with one. Then the allow itself: the resource in my statement may be wrong, for example the bucket's ARN without /* for objects, or the object may be under a prefix the statement does not cover. If the bucket is in another account, the bucket policy must also allow my role. And there are causes outside IAM policies proper: the object is encrypted with a key my role may not use, so the denial is really from the key service, or the object does not exist and I lack s3:ListBucket, in which case the service answers 403 instead of 404. To confirm I would use the policy simulator and the API audit log entry for the failed call.
    
  
    

  
    
    
    🧠 Key takeaways
    
    
      
      
    • A principal makes requests; a policy says which actions on which resources are allowed or denied.
      • 
      
    • Roles have no credentials of their own: they are assumed, and the credentials expire. Prefer them for people and machines alike.
      • 
      
    • Default deny; an explicit deny always wins; otherwise an allow is needed, from either side in one account and from both sides across accounts.
      • 
      
    • Boundaries and organisation policies only limit. They never grant.
      • 
      
    • Least privilege limits what a leaked credential or a forged request can do. Name actions and resources; review what is unused.
      • 
      
    • Workloads get identity from the platform: instance profiles, pod identities and CI tokens, not stored keys.
      • 
      
    • Read the denial message: it says which kind of policy stopped the request.
      • 
    
    
  
    

  
    
    
    Check your understanding
    
    
    

    
    
      
    A role's identity policy allows s3:* on every resource. A bucket's policy contains a statement that denies s3:DeleteObject to everyone. The role tries to delete an object in that bucket. What happens?
    
      
    
        
        
        
        
      
    
      
    Explicit deny always wins. It is the tool for guard rails that no later, broader allow can undo.
    
    
    

    
    
      
    A role in account A has a policy allowing s3:GetObject on a bucket owned by account B. The bucket has no bucket policy. Can the role read the objects?
    
      
    
        
        
        
        
      
    
      
    Cross-account access needs an allow on both sides. Otherwise any account could grant itself access to anyone else's resources.
    
    
    

    
    
      
    What does a permissions boundary do?
    
      
    
        
        
        
        
      
    
      
    A boundary is a ceiling. The effective permissions are what is both inside the boundary and allowed by an ordinary policy. Who may assume a role is the trust policy's job.
    
    
    

    
    
      
    Why are temporary role credentials safer than an access key stored in a pipeline's settings?
    
      
    
        
        
        
        
      
    
      
    A stored key works for whoever holds it until someone rotates it. Temporary credentials limit the damage in time, and the trust policy limits who can obtain them.
    
    
    

    
    
      
    A call fails with: "…is not authorized to perform: s3:PutObject … because no permissions boundary allows the s3:PutObject action". What fixes it?
    
      
    
        
        
        
        
      
    
      
    The message names the policy type that refused. A boundary is a ceiling, so no allow elsewhere can lift the request past it.
