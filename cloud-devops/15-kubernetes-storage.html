Storage in Kubernetes

Pods are disposable, and data is not. Kubernetes reconciles the two by keeping storage in objects that live apart from pods: a pod claims a piece of storage, and when the pod is replaced, the new one makes the same claim and gets the same disk back. That sentence hides the questions that cause incidents. What is lost when a pod is deleted? Why is a pod stuck "Pending" after a node failure although other nodes are free? What happens to the disk when the claim is deleted? Why does scaling a database with a Deployment corrupt it? This chapter covers volumes, claims, storage classes and StatefulSets, and the simulator answers those questions by letting you break things and count the records that survive.

Volumes

A container's own file system is thrown away whenever the container restarts. A volume is a directory that a pod declares and its containers mount, and what a volume survives depends entirely on its type.

PersistentVolumes and PersistentVolumeClaims

Persistent storage is described by two objects, so that the people who need storage do not have to know how it is provided.

  • A PersistentVolumeClaim (PVC) is a request, written by the application's owner: "20 GiB, mountable read-write by one node, of the class fast". It lives in the application's namespace.
  • A PersistentVolume (PV) is the storage that satisfies it: a record in the cluster that stands for one real cloud disk or network share. It belongs to no namespace.

A claim binds to exactly one volume, and the pair stays together until the claim is deleted. Pods refer only to the claim. That indirection is the whole trick: a replacement pod names the same claim and therefore gets the same disk.

apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: uploads, namespace: shop }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: fast
  resources: { requests: { storage: 20Gi } }
---
# in the pod template
      containers:
        - name: web
          volumeMounts: [{ name: uploads, mountPath: /var/lib/web/uploads }]
      volumes:
        - name: uploads
          persistentVolumeClaim: { claimName: uploads }
$ kubectl get pvc,pv -n shop
NAME                            STATUS   VOLUME        CAPACITY   ACCESS MODES   STORAGECLASS
persistentvolumeclaim/uploads   Bound    pvc-3f9c1a…   20Gi       RWO            fast

NAME                           CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM
persistentvolume/pvc-3f9c1a…   20Gi       RWO            Delete           Bound    shop/uploads

The access mode says how many nodes may mount the volume at once, and it is set by what the storage can physically do:

Access modeMeaningTypical backing
ReadWriteOnce (RWO)Mounted read-write by one node. Several pods on that same node can share itCloud block volumes (Chapter 4): the usual case
ReadWriteOncePodMounted by exactly one podBlock volumes, when even same-node sharing must be prevented
ReadOnlyMany (ROX)Mounted read-only by many nodesShared reference data
ReadWriteMany (RWX)Mounted read-write by many nodesNetwork file systems (NFS, EFS, Filestore): slower and dearer

Two properties of block volumes shape everything else in this chapter. A block volume attaches to one node at a time, so two pods on different nodes cannot share it. And it lives in one zone, so a pod that uses it can only ever run on nodes in that zone. A pod with a claim is not as free to move as a pod without one.

Storage classes

Nobody creates PersistentVolumes by hand any more. A StorageClass describes a kind of storage and names the driver that can create it, and when a claim asks for that class, the driver creates a matching disk and its PV on the spot. This is dynamic provisioning.

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: fast }
provisioner: ebs.csi.aws.com            # the CSI driver that talks to the cloud's storage API
parameters: { type: gp3, iops: "6000" }
reclaimPolicy: Delete                    # what happens to the disk when its claim is deleted
volumeBindingMode: WaitForFirstConsumer  # create the disk only once a pod has been scheduled
allowVolumeExpansion: true               # claims may be made larger later

Three of those lines decide outcomes you will care about.

  • reclaimPolicy. With Delete, the default for dynamic provisioning, deleting the claim deletes the cloud disk and everything on it. With Retain, the disk is kept and the PV becomes Released: the data is safe, and an administrator has to clean up or reconnect it by hand. For data that matters, use Retain or make sure snapshots exist, because kubectl delete namespace deletes claims too.
  • volumeBindingMode. With Immediate, the disk is created as soon as the claim exists, in some zone, before anyone knows where the pod will run; the pod may then be unschedulable because that zone has no room. WaitForFirstConsumer lets the scheduler choose a node first and creates the disk in that node's zone.
  • allowVolumeExpansion. Growing a volume is then an edit of the claim's size. Volumes cannot shrink.

StatefulSets

A Deployment treats its pods as interchangeable: random names, any order, and if the pod template has a claim, every replica uses the same one. That is fine for one pod with a disk and wrong for a replicated database, where each member must have its own data and a name the others can find it by. A StatefulSet is the controller for that case.

DeploymentStatefulSet
Pod namesRandom: web-7c9d8-x2kfpStable and numbered: db-0, db-1, db-2
StorageAll replicas share whatever claim the template namesA claim per replica, made from a template: data-db-0, data-db-1…
A replaced podNew name, and the shared claimSame name, and its own claim again
Network identityOnly the Service's addressA DNS name per pod through a headless Service: db-0.db.shop.svc.cluster.local
Start, stop and update orderAny order, several at onceOne at a time, in order: 0, 1, 2 up; 2, 1, 0 down
Scale down, or delete the setNothing stored per podThe claims and their disks are kept (and billed) until you delete them
ForStateless servicesDatabases, message brokers, anything with per-member state
 
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: db, namespace: shop }
spec:
  serviceName: db                    # a headless Service (clusterIP: None) that gives each pod a DNS name
  replicas: 3
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      containers:
        - name: postgres
          image: postgres:17
          volumeMounts: [{ name: data, mountPath: /var/lib/postgresql/data }]
  volumeClaimTemplates:               # one claim per pod: data-db-0, data-db-1, data-db-2
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: fast
        resources: { requests: { storage: 100Gi } }

A StatefulSet gives a database stable names and disks. It does not make three PostgreSQL pods into a cluster: replication, failover and backups are the database's business, and are usually handled by an operator, a controller written for that database. That is real operational work, and it is why a managed database service (Chapter 4) is the right default for most teams. Run state in Kubernetes when you have a reason and the people to operate it.

Claims are ReadWriteOnce on zonal block volumes, created with WaitForFirstConsumer in the zone of the node the pod is first scheduled to. A pod with a bound claim can only be scheduled in its disk's zone. A volume attaches to one node at a time; pods on that node may share it. A failed node's pods are replaced immediately here (a real cluster waits several minutes first). Deleting a workload does not delete its claims. A claim in use cannot be deleted. Each disk is billed at $1.60 a month while it exists.

Things to try. In each case write three records first.

  • emptyDir, one replica. Crash the container: the three records are still there. Delete the pod: zero readable, three destroyed. The crash test is why emptyDir fools people. With three replicas, fail node-a1: six of nine records remain. The pod moved to another node and its data did not.
  • Deployment with one claim, one replica. Delete the pod, then fail node-a1: all three records are readable each time, because the replacement mounts the same disk from the other node in zone a. Now fail zone a. The pod is Pending with a volume node affinity conflict, although node-b1 is idle. Bring the nodes back and the records are there again. Nothing was lost; for a while nothing was available.
  • The same with three replicas. Two pods run and one is stuck with a Multi-Attach error, and the two that run are writing to one disk.
  • StatefulSet, three replicas. Three disks, one per pod. Delete a pod: it returns as db-0 with its data. Fail zone a: one of three pods keeps running, the one whose disk is in zone b. A replicated database spread like this survives a zone; a single pod on a zonal disk does not.
  • Scale the StatefulSet to 1, write one more record, and scale back to 3. Three disks were billed the whole time, and db-1 and db-2 come back with what they had before, now one record behind db-0. Old data returning unannounced is something a database's replication has to be ready for.
  • Delete the workload, then apply it again. All nine records are back: the claims never went away.
  • Delete the claims. While pods use them, the request is refused. After deleting the workload it goes through, and the reclaim policy decides everything. With Delete: nine records destroyed and no disks left. With Retain: nothing destroyed, three Released disks kept, and after applying again there are six disks on the bill and nine records that the new, empty pods cannot see until someone reconnects the volumes by hand.
🗄️
Use case: GitLab, 2017, and the copies that were not there

On 31 January 2017 an engineer at GitLab, working late on a replication problem, ran a command to wipe a database directory on what he believed was the broken secondary. It was the primary. He stopped it within seconds, and about 300 GB of production data was already gone. What turned a mistake into an eighteen-hour outage was the storage and backup layer underneath, which GitLab described in a frank public post-mortem. The regular logical backups had been failing silently for some time, because of a version mismatch in the tool, and the failure notices were being rejected as email. Disk snapshots in the cloud were not enabled for the database servers. The replica could not help, since replication was the thing being repaired. What saved most of the data was a snapshot that an engineer had happened to take by hand six hours earlier for an unrelated test. GitLab restored from it, slowly, and lost about six hours of issues, comments and merge requests. Nothing in that story is specific to Kubernetes, and all of it applies to a PersistentVolume. A replicated, durable disk carries out a delete as faithfully as it does a write. The reclaim policy, the snapshot schedule and above all a restore that has actually been tried are what stand between one command and the loss. Chapter 32 returns to backups that work.

⚠️
Common mistakes
  • Data in emptyDir or in no volume at all. It survives a crash, which makes it look safe, and disappears at the next rollout.
  • A database in a Deployment with replicas above one. Every replica gets the same claim: either they cannot all attach it, or they all write to one data directory.
  • A rolling update with a ReadWriteOnce claim. The new pod waits for a volume the old pod still holds. Use the Recreate strategy, or a StatefulSet.
  • Forgetting that the disk is zonal. A pod stays Pending with "volume node affinity conflict" when no node is available in its disk's zone. Keep capacity in every zone that holds volumes.
  • Reclaim policy Delete on data you cannot lose, and then deleting a namespace or a Helm release.
  • Assuming a StatefulSet cleans up. Scaling down or deleting it leaves claims and disks behind, still billed.
  • Thinking a StatefulSet makes a database highly available. It provides names and disks. Replication and failover are separate work.
  • hostPath for application data. The data stays on one node, and the pod may not.
  • No snapshots and no tested restore. A persistent volume is not a backup.

Interview drill

Explain it simply: What are a PV, a PVC and a StorageClass?

How a strong answer sounds
A PersistentVolumeClaim is a request for storage made by an application: a size, an access mode and a class. A PersistentVolume is the piece of real storage, such as a cloud disk, that satisfies it; the two bind one to one, and pods mount the claim, so a replacement pod gets the same disk. A StorageClass describes a kind of storage and names the CSI driver that creates it, so that volumes are provisioned on demand when a claim appears. The class also sets the reclaim policy, which decides whether the disk is deleted or kept when the claim is deleted, and the binding mode, which decides whether the disk is created immediately or only after the pod has been scheduled, so that it lands in the right zone.

Deeper: After a node failure, a pod with a PersistentVolumeClaim has been Pending for ten minutes, although the cluster has free nodes. What is going on?

How a strong answer sounds
I would run kubectl describe pod and read the scheduler's events, and I would expect one of two messages. The first is a volume node affinity conflict: the claim is bound to a block volume, a block volume lives in one zone, and the free nodes are in other zones. The scheduler will not place the pod where its disk cannot follow. The fix is capacity in the right zone: a node group that spans zones evenly, or an autoscaler that can add a node in that specific zone, and I would check why the zone has no schedulable node. The second possibility is that the pod was scheduled and is stuck in ContainerCreating with a Multi-Attach error: the volume is still attached to the failed node, which never confirmed the detach, and the control plane waits several minutes before forcing it. That resolves by itself, or can be hurried by deleting the dead node object once I am sure the machine is really gone, since forcing a detach from a node that is still writing would corrupt the data. If neither message appears, I would look at ordinary causes: resource requests that fit nowhere, taints, or a claim that is itself Pending because provisioning failed. For the longer term, a single pod on a zonal disk has availability no better than its zone, so anything that must survive a zone failure needs replicas with their own volumes in several zones, which is what a StatefulSet with a replicated database gives.

🧠 Key takeaways

  • emptyDir survives a container restart and dies with the pod. Only a claim outlives the pod.
  • A PVC is a request; a PV is the storage that satisfies it; a pod mounts the claim.
  • A StorageClass provisions volumes on demand and sets the reclaim policy and the binding mode.
  • Block volumes attach to one node and live in one zone, so a pod with a claim can only run in that zone.
  • Reclaim policy Delete destroys the disk with the claim. Use Retain or snapshots for data that matters.
  • A StatefulSet gives each replica a stable name and its own claim, and keeps the claims when it is scaled down or deleted.
  • Persistent is not backed up: take snapshots and practise restoring.

Check your understanding

A pod writes files into an emptyDir volume. Its container crashes and is restarted by the kubelet. Later the Deployment is rolled out to a new version. What happens to the files in each case?

An emptyDir lives as long as its pod. A container restart keeps the pod; a rollout creates new pods with new, empty directories.

A claim with reclaim policy Delete is bound to a cloud disk holding a database. Someone runs kubectl delete pvc after removing the pod. What happens to the data?

Delete means the storage follows the claim. With Retain the disk would have been kept and the PV marked Released.

A pod's ReadWriteOnce volume was provisioned in zone a. Zone a's only node fails; zone b has two idle nodes. Where does the replacement pod run?

A block volume is zonal. The scheduler only considers nodes in the volume's zone, and if none is available the pod waits.

A team scales a single-replica PostgreSQL Deployment, whose pod template names one ReadWriteOnce claim, to three replicas. What is the result?

A Deployment's replicas share the template's claim. Per-replica storage needs a StatefulSet with volumeClaimTemplates.

A StatefulSet with three replicas is scaled down to one and, a week later, back up to three. What do db-1 and db-2 find in their volumes?

By default a StatefulSet never deletes claims. That protects data, and it means stale data and unused disks stay around until someone removes them.
