SSH & Keys

SSH is how you get a shell on a server, how Git talks to GitHub, how Ansible configures a fleet and how many deploy pipelines copy files. Every server with port 22 open to the internet receives automated login attempts within minutes of booting. This chapter covers key-based authentication, host keys, the client configuration that makes jump hosts painless, and the handful of sshd settings that turn a server from a target into a dead end, without locking yourself out while you change them.

Key pairs

A key pair is two linked keys. The private key stays on your machine and never leaves it; the public key can be copied anywhere. The server stores your public key in ~/.ssh/authorized_keys. When you connect, the client proves it holds the matching private key by signing data unique to this session, and the server checks the signature with the public key. No secret crosses the network, so a server that is compromised or an attacker listening in learns nothing they can reuse, which is the core advantage over passwords.

$ ssh-keygen -t ed25519 -C "palak@laptop-2026"    # Ed25519: small, fast, the modern default
Enter passphrase (empty for no passphrase):                # use one: it encrypts the key on disk
Your identification has been saved in /home/palak/.ssh/id_ed25519
Your public key has been saved in /home/palak/.ssh/id_ed25519.pub
$ ssh-copy-id ops@203.0.113.10                         # appends the .pub to the server's authorized_keys
$ ls -l ~/.ssh
-rw------- 1 palak palak  411 id_ed25519                    # 600: ssh refuses a private key others can read
-rw-r--r-- 1 palak palak   99 id_ed25519.pub

Use Ed25519 unless an old system forces RSA (then 3072 bits or more). Protect the private key with a passphrase and let ssh-agent hold the unlocked key in memory, so you type the passphrase once per session rather than once per connection (ssh-add ~/.ssh/id_ed25519; macOS and most desktops start an agent for you).

Host keys: is this really my server?

Authentication goes both ways. The server also has a key pair, its host key, and proves its identity first. The first time you connect, your client shows the host key's fingerprint and asks whether to trust it; the answer is saved in ~/.ssh/known_hosts. On every later connection the client checks the server presents the same key.

If the host key changes, you get a loud warning: WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED! Sometimes that is legitimate: the server was rebuilt, or the IP now belongs to a new instance, which happens constantly in the cloud. Sometimes it is someone intercepting the connection. Do not delete the line from known_hosts by reflex: check that the server really was replaced (the console shows the new host key fingerprints in its boot log), then remove the old entry with ssh-keygen -R host.

Client config and jump hosts

Private servers are not reachable from the internet; you reach them through a bastion (or jump host), a small, hardened server that is the only machine accepting SSH from outside. ~/.ssh/config turns a long command into a short name, and ProxyJump makes the hop transparent:

# ~/.ssh/config
Host bastion
    HostName bastion.prod.example.com
    User palak
    IdentityFile ~/.ssh/id_ed25519

Host 10.20.*                       # every host in the private subnets
    User ops
    ProxyJump bastion                # tunnel through the bastion; keys never leave the laptop

$ ssh 10.20.1.17                    # laptop → bastion → 10.20.1.17, one command
$ scp app.tgz 10.20.1.17:/tmp/      # scp and rsync use the same config

The tempting alternative is agent forwarding (ssh -A, ForwardAgent yes): log in to the bastion, then SSH onward from there using your laptop's agent. It works, but while you are connected, anyone with root on the bastion can use your forwarded agent to log in anywhere your key is accepted. ProxyJump avoids that: the bastion only relays an encrypted stream it cannot read.

Hardening sshd

Four settings in /etc/ssh/sshd_config remove most of the risk, and a firewall rule removes most of the noise:

# /etc/ssh/sshd_config (or a file in /etc/ssh/sshd_config.d/)
PasswordAuthentication no          # keys only: brute-forcing passwords becomes pointless
KbdInteractiveAuthentication no    # closes the other password-style path
PermitRootLogin no                 # log in as yourself, then sudo: actions are attributable
AllowGroups ops                    # only members of this group may log in at all

$ sudo sshd -t                       # test the config: a typo here can lock everyone out
$ sudo systemctl reload ssh           # reload keeps existing sessions open (the unit is sshd on RHEL)

The safe procedure matters as much as the settings: keep your current session open, check the config with sshd -t, reload, then open a second terminal and log in again. Only when that works do you close the first one. The simulator below lets you skip a step and see what happens.

Use case: agent forwarding in a real breach

In April 2019 an attacker got into Matrix.org's production infrastructure through an unpatched Jenkins server. Matrix's public postmortem listed SSH agent forwarding among the things that let the attacker move from machine to machine, and its first recommendations were to stop using it, to restrict which hosts accept which keys, and to put SSH behind a VPN. The general lesson: access paths are part of the attack surface. A bastion is only as safe as what an attacker can do from it, which is why ProxyJump, short-lived certificates and session managers exist.

⚠️
Common mistakes
  • Disabling passwords before your key works, then closing the only session. Test in a second session first.
  • Reloading without sshd -t: a typo can stop sshd accepting anyone.
  • Private keys without a passphrase on laptops, or copied to servers and CI runners "temporarily".
  • Agent forwarding to shared hosts. Use ProxyJump.
  • Deleting a known_hosts entry by reflex when the host key changes. Verify first.
  • Never removing keys of people who left. Centralise access (certificates, IAM) so leaving revokes it.
  • Port 22 open to 0.0.0.0/0 when only the bastion or a VPN needs it.

Interview drill

Explain it simply: Why is key-based SSH safer than passwords?

How a strong answer sounds
With a password, the secret itself is sent to the server, so it can be guessed by bots, reused from another breach, or captured by a compromised server. With keys, the private key never leaves my machine; I prove I hold it by signing data unique to this session, and the server checks it against my public key. Nothing reusable crosses the network, and a 256-bit key cannot be brute-forced. Once every user has a key, turning off PasswordAuthentication makes the constant brute-force traffic harmless.

Deeper: How would you give 40 engineers SSH access to 300 private servers, and remove it the day someone leaves?

How a strong answer sounds
Not with individual public keys copied to 300 authorized_keys files, because removal is the part that fails. I would use short-lived SSH certificates: engineers log in through SSO, a CA (Vault, Teleport, or step-ca) signs their key for eight hours with their username as the principal, and servers trust the CA instead of individual keys. Leaving the company disables SSO, so no new certificates are issued and existing ones expire the same day. Alternatively, on AWS or GCP, a session manager removes inbound SSH entirely and ties access to IAM. In both cases servers stay in private subnets, root login is off, and sessions are logged centrally.

🧠 Key takeaways

  • Private keys stay on your machine (mode 600, with a passphrase and ssh-agent); public keys go in authorized_keys.
  • Host keys prove the server's identity; a changed host key needs checking, not deleting.
  • Reach private servers via a bastion with ProxyJump; avoid agent forwarding.
  • Harden with PasswordAuthentication no, PermitRootLogin no, AllowGroups, and a firewall that limits port 22.
  • Change SSH safely: sshd -t, reload, test a second session, then close the first.
  • At scale, prefer short-lived certificates or a cloud session manager over hand-managed keys.

Check your understanding

During key-based SSH login, what does the client send to prove who it is?

The private key never leaves the client. The server verifies the signature with the public key from authorized_keys; the signature is useless for any other session.

Why is ProxyJump safer than agent forwarding for reaching servers behind a bastion?

ProxyJump opens the inner SSH connection end to end from your laptop. A forwarded agent is a socket on the bastion that anyone with enough privilege there can use while you are connected.

You set PasswordAuthentication no on a server. What is the safe next sequence?

Testing the config and proving a fresh login works, while the old session is still open, is what prevents a lockout.

ssh warns REMOTE HOST IDENTIFICATION HAS CHANGED for a server. What should you do first?

A changed host key is either a replaced server or an interception. Verify out of band before trusting the new key.

Which setting means bots guessing passwords for root can never succeed, even if a root password is weak?

With password authentication off, there is nothing to guess. Moving the port only reduces log noise; MaxAuthTries slows but does not stop guessing.
