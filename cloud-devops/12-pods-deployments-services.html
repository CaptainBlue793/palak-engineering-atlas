Pods, Deployments & Services

Three kinds of object carry almost every stateless application on Kubernetes. A Pod runs the containers. A Deployment keeps the right number of pods running and replaces them, a few at a time, when you release a new version. A Service gives that changing set of pods one stable address. What ties the three together, and decides whether a release is invisible to users or an outage, is a fourth thing that is easy to skip: probes, the checks that tell Kubernetes whether a pod is really able to serve. This chapter covers all four, and the simulator rolls out a new version under different settings so that you can see exactly when requests fail.

Pods

A pod is the smallest thing Kubernetes schedules: one or more containers that are always placed together on one node. The containers in a pod share a network address, so they reach each other on localhost, and they can share volumes. Most pods hold one application container. A second container is justified when it is a helper that must live and die with the first, such as a proxy or a log shipper; such helpers are called sidecars.

The fact to hold on to is that pods are disposable. A pod is never repaired or moved. When its node dies, or it is evicted, or you roll out a new version, it is deleted and a new one is created, with a new name and a new IP address. Two things follow, and they are the next two sections. You do not create pods yourself: you create a controller that keeps creating them. And nothing should ever connect to a pod's address directly.

ReplicaSets and Deployments

A ReplicaSet has one job: keep exactly n pods alive that match a label selector, creating them from a template when there are too few. A Deployment sits one level above and manages ReplicaSets, and it is the object you write. The reason for two levels is releases. When you change anything in the Deployment's pod template, most often the image, the Deployment creates a new ReplicaSet for the new template and shifts pods from the old one to the new one step by step. The old ReplicaSet is kept at zero pods, which is what makes a rollback instant: scaling it back up needs no rebuild and no pull.

apiVersion: apps/v1
kind: Deployment
metadata: { name: web, namespace: shop }
spec:
  replicas: 4
  selector: { matchLabels: { app: web } }      # which pods belong to this Deployment
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  template:                                    # the pod to stamp out
    metadata: { labels: { app: web } }           # must match the selector
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: web
          image: ghcr.io/acme/web:4.18.2
          ports: [{ containerPort: 8080 }]
          resources:
            requests: { cpu: 250m, memory: 256Mi }   # what the scheduler reserves on a node
            limits:   { memory: 512Mi }              # above this the container is killed
          readinessProbe:
            httpGet: { path: /readyz, port: 8080 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /livez, port: 8080 }
            periodSeconds: 10
            failureThreshold: 3

Rolling updates and rollbacks

A rolling update replaces pods a few at a time, and two numbers set the pace. Both can be absolute or a percentage of replicas.

  • maxSurge: how many pods above the desired count may exist during the rollout. More surge is faster and needs spare room in the cluster.
  • maxUnavailable: how many pods below the desired count may be unavailable. Zero means capacity never drops; a higher number means the rollout can start by removing old pods.

The Deployment controller follows two rules at every step: never more than replicas + maxSurge pods in total, and never fewer than replicas − maxUnavailable pods available. "Available" means ready, and ready is decided by the readiness probe. That one dependency is why probes decide whether a rollout is safe.

$ kubectl set image deployment/web web=ghcr.io/acme/web:4.19.0 -n shop      # or, better, change the file and apply it
$ kubectl rollout status deployment/web -n shop
Waiting for deployment "web" rollout to finish: 2 out of 4 new replicas have been updated...
Waiting for deployment "web" rollout to finish: 1 old replicas are pending termination...
deployment "web" successfully rolled out

$ kubectl get rs -n shop                       # one ReplicaSet per version; the old one is kept, empty
NAME             DESIRED   CURRENT   READY   AGE
web-7c9d8b6f4    0         0         0       3d
web-5f6b9c8d7    4         4         4       2m

$ kubectl rollout history deployment/web -n shop
$ kubectl rollout undo deployment/web -n shop  # scale the previous ReplicaSet back up, with the same rules

If the new pods never become ready, the rollout does not fail loudly. It stops and waits, with the old pods still serving, and after progressDeadlineSeconds (ten minutes by default) the Deployment is marked as not progressing. A pipeline should run kubectl rollout status, which exits non-zero in that case, and roll back when it does.

Services and endpoints

Pods come and go and change address each time. A Service is the stable name in front of them. It has a label selector, a virtual IP address that never changes while the Service exists, and a DNS name: web from the same namespace, web.shop.svc.cluster.local from anywhere in the cluster.

apiVersion: v1
kind: Service
metadata: { name: web, namespace: shop }
spec:
  selector: { app: web }          # send traffic to ready pods carrying this label
  ports:
    - port: 80                     # the port clients use on the Service
      targetPort: 8080           # the port the container listens on

Behind every Service the control plane maintains a list of endpoints: the IP addresses of the pods that match the selector and are ready. Every node is programmed with that list, and a connection to the Service's address is forwarded to one of them. The list is the live routing table of your application:

$ kubectl get endpointslices -n shop -l kubernetes.io/service-name=web
NAME        ADDRESSTYPE   PORTS   ENDPOINTS                             AGE
web-k7x2p   IPv4          8080    10.244.1.14,10.244.2.9,10.244.2.31    3d

$ kubectl get pods -n shop -l app=web -o wide      # four pods, three endpoints: one pod is not ready

When a Service "does not work", look here first. An empty list means the selector matches no pod (a typo in a label is the usual cause) or no matching pod is ready. This kind of Service, a ClusterIP, is reachable only inside the cluster; Chapter 14 covers the ways in from outside.

Probes

A running process is not the same as a working service. A probe is a check that the kubelet runs against a container, again and again: an HTTP request, a TCP connection or a command. There are three kinds, and they differ only in what happens when they fail.

Typical mistakeLeaving it outChecking a database or another service: when that is slow, every pod is restarted at onceUsing a long liveness delay in its place

The liveness mistake deserves a second sentence, because it turns small problems into outages. If the liveness endpoint queries the database, a slow database makes every pod fail its probe together, the kubelet restarts all of them, and they come back to a database that is still slow and now receives a burst of new connections. A restart fixes a stuck process. It does not fix a dependency. Keep liveness trivial, and let readiness carry the richer check.

The end of a pod's life needs the same care as the beginning. When a pod is deleted, two things start at once: it is removed from the endpoints, and its containers receive SIGTERM. Removing it from every node's routing takes a moment, so for a second or two requests can still arrive at a process that has been told to stop. A well-behaved service keeps answering for a few seconds after SIGTERM, finishes its open requests and then exits, all inside terminationGracePeriodSeconds. A short preStop sleep is the common way to give the routing time to catch up.

One step is one second. A new pod's container is running 2 seconds after the pod is created; the application then needs the time you chose before it can answer. With a readiness probe, a pod counts as ready, and joins the Service, only when it can answer. Without one, it counts as ready as soon as its container is running. The controller keeps at most 4 + maxSurge pods and at least 4 − maxUnavailable ready pods, and removes an old pod whenever those rules allow. Requests are spread evenly over the pods in the Service. A rollout with no progress for 45 seconds is shown as stalled.

Things to try.

  • The starting point is a cautious-looking strategy (one extra pod, none unavailable) with no readiness probe, and a version that needs 30 seconds to warm up. Kubernetes reports the rollout done after 8 seconds. Requests fail for 36 seconds, and for most of that time every request fails, because all four working pods were replaced by pods that were still starting.
  • Add the readiness probe. The rollout takes 128 seconds, never has fewer than four pods able to serve, and loses no request. It is sixteen times slower because it now waits for each pod to be able to answer. That wait was the missing safety.
  • Make it faster without losing that. With maxSurge at 100% it finishes in 32 seconds, still with no errors, and needs room for eight pods at once. With maxSurge 0 and maxUnavailable 2 it takes 64 seconds on only four pods, and capacity drops to two of four on the way. Speed is paid for in spare room or in capacity.
  • Release a version that never serves, with no probe. "Successfully rolled out" after 8 seconds, and the service is down for good. Kubernetes did exactly what it was told.
  • The same broken version with a probe. The rollout stalls. With one surge pod and none unavailable, all four old pods keep serving and one new pod sits unready. With maxSurge 0 and maxUnavailable 1, the stall leaves three old pods serving: a rollout that may remove before it adds gives up capacity for as long as it is stuck.
  • Set both numbers to 0. The API refuses the object: there is no first step that satisfies both rules.
  • Across all 48 valid settings, every one with a readiness probe lost no request, and every one without it lost some.

Use case: Monzo, October 2017, and a service with no endpoints

The British bank Monzo runs on Kubernetes, and in October 2017 its payments were failing for well over an hour. The bank published a detailed post-mortem. Its services found each other through a proxy layer that learned each service's endpoints from the Kubernetes API, the list described in this chapter. A change had left one service, for a short time, with no healthy endpoints at all. That is a legal state, and a brief one during a careless rollout. But the combination of versions Monzo was running had a bug in how the empty list was reported and handled, and the proxies stopped receiving updates for that service: when its pods came back, callers still believed there was nowhere to send requests. The failure spread to the services that depended on it, and recovery meant restarting the proxy layer across the platform. Two lessons belong to this chapter. The endpoints list is not bookkeeping: it is the routing table that every request depends on, and "zero endpoints" is a state that every consumer of it must be able to survive. And a rollout should be configured so that the state does not occur in the first place: keep maxUnavailable low, and make readiness mean what it says.

⚠️
Common mistakes
  • No readiness probe. New pods get traffic before they can answer, and a broken release replaces every working pod.
  • A liveness probe that checks dependencies. A slow database becomes a restart storm.
  • The same endpoint for liveness and readiness. They ask different questions and should fail in different situations.
  • Creating bare pods. Nothing recreates a pod that has no controller.
  • Labels that do not match. A Service whose selector matches nothing has no endpoints and gives no error.
  • Connecting to pod IP addresses, or caching them. They change on every restart. Use the Service name.
  • No resource requests. The scheduler packs nodes blindly, and pods are evicted under memory pressure.
  • Ignoring SIGTERM. Each pod removed during a rollout drops its open requests.
  • Not waiting for the rollout in the pipeline. kubectl apply succeeds the moment the object is stored; use kubectl rollout status.

Interview drill

Explain it simply: What are a Pod, a Deployment and a Service, and how do they relate?

How a strong answer sounds
A pod is one or more containers scheduled together on a node, sharing a network address. It is disposable: when it dies it is replaced by a new pod with a new address. A Deployment declares how many copies of a pod template should run. It manages ReplicaSets, one per version of the template, and when the template changes it moves pods from the old ReplicaSet to a new one gradually, which gives rolling updates and quick rollbacks. A Service is a stable virtual IP and DNS name that selects pods by label and forwards traffic to the ones that are ready. Labels are the glue: the Deployment's selector says which pods it owns, and the Service's selector says which pods it sends traffic to. They are usually the same label and are still two independent selections.

Deeper: Every deployment of a service causes about thirty seconds of 502 errors, although the new version is healthy. Where do you look?

How a strong answer sounds
Errors during an otherwise healthy rollout come from traffic reaching pods at the wrong moment, either too early at the start of a pod's life or too late at the end, so I check both ends. Start: is there a readiness probe, and does it only pass when the application can really serve? Without one, a pod is added to the Service as soon as its container starts, and requests hit it during warm-up; the errors would last about as long as the application takes to start. I would add a readiness probe on an endpoint that reflects real readiness, and a startup probe if the start is slow. End: when an old pod is terminated, it is removed from the endpoints and sent SIGTERM at the same time, and nodes and any external load balancer take a moment to stop sending to it. If the process exits immediately, in-flight and late-arriving requests fail. The fix is graceful shutdown: handle SIGTERM, keep serving for a few seconds, finish open requests, and add a short preStop sleep so that routing catches up; with a cloud load balancer in front, align its deregistration delay as well. Then the rollout settings: with maxUnavailable above zero, capacity drops during the rollout, and the remaining pods may be overloaded, so I would use maxUnavailable 0 with a surge. I would confirm which case it is by lining up the error timestamps with pod start and termination events.

🧠 Key takeaways

  • A pod is disposable: replaced, never repaired, with a new address each time.
  • A Deployment manages one ReplicaSet per version and keeps the old ones for rollback.
  • A rollout never exceeds replicas + maxSurge pods and never drops below replicas − maxUnavailable ready pods.
  • A Service is a stable name and address in front of the pods that match its selector and are ready: the endpoints.
  • Readiness controls traffic, liveness restarts, startup protects slow starters. Keep liveness trivial.
  • With a readiness probe a bad release stalls safely. Without one it replaces every working pod.
  • Shut down gracefully on SIGTERM, and have the pipeline wait for rollout status.

Check your understanding

A Deployment has replicas: 10, maxSurge: 2 and maxUnavailable: 1. During a rollout, what are the most pods that can exist and the fewest that must be ready?

The total may reach replicas + maxSurge = 12, and the number of ready pods may not fall below replicas − maxUnavailable = 9.

A pod's readiness probe starts failing. What does Kubernetes do?

Readiness only controls traffic. Restarting is what a failing liveness probe causes.

A Service has been created, and requests to it fail with "connection refused". kubectl get endpointslices shows no addresses for it, although the pods are Running and READY 1/1. What is the most likely cause?

Endpoints are the ready pods that match the selector. Ready pods and an empty list point at the selector: a label typo is the usual culprit.

A liveness probe calls an endpoint that runs a query against the database. The database becomes slow for two minutes. What is the likely result?

Restarting the callers cannot fix the dependency, and the restarts add a reconnection burst. Liveness should test only the process itself.

A new image that crashes on start is rolled out to a Deployment whose pods have a correct readiness probe, with maxSurge: 1 and maxUnavailable: 0. What happens to the service?

An old pod may only be removed while the ready count stays at the full number. The new pod never becomes ready, so no old pod is ever removed. Nothing rolls back by itself: the pipeline has to notice the stall.
