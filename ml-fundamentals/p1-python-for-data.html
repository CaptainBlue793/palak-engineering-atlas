Python for Data Work

Every listing in this course is Python, and nearly all of it runs either in a notebook or in a small script. This page sets up the working environment and covers the handful of language features the rest of the course leans on: comprehensions, small pure functions, reading CSV and JSON, and random seeds.

It also covers the most common way a data project goes wrong before any model is involved. A notebook remembers everything you ran, in the order you ran it, and that order is invisible on the page. The simulator lets you run four cells in any order and watch the answer drift away from what a fresh run would give.

  • Explain how a notebook kernel keeps state, and why "Restart & Run All" matters
  • Write list and dict comprehensions and small functions that return new data
  • Read CSV and JSON files with the standard library, and know what type each value arrives as
  • Seed Python's, NumPy's and scikit-learn's randomness so that a result can be reproduced

One environment per project

Python packages are installed into an environment, and by default that is the single system-wide Python. Two projects that need different versions of pandas cannot both be satisfied there, and an upgrade for one silently changes the other. The fix is a virtual environment: a folder holding its own copy of the interpreter's package directory, created per project and thrown away when the project is.

# Create and activate an environment inside the project folder
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate

# Install what this course uses, then record the exact versions
pip install numpy pandas scikit-learn matplotlib jupyter
pip freeze > requirements.txt        # exact versions, e.g. scikit-learn==1.5.2

# Anyone (including you, next year) rebuilds the same environment with
pip install -r requirements.txt

The requirements.txt file is the important artefact. Model results depend on library versions more than people expect: default hyperparameters change between releases, and so do the random number streams behind some algorithms. A result you cannot rebuild the environment for is a result you cannot check.

Notebooks and the kernel

A Jupyter notebook is a list of cells, but the cells are not what runs. Behind the page sits a kernel: one long-running Python process. Each time you run a cell, its code executes in that process, and every variable it creates stays there until the kernel restarts. The number beside a cell, such as [7], is the order in which it last ran.

This is what makes notebooks good for exploration: load a large file once, then poke at it in twenty small cells without reloading. It is also what makes them dangerous. The state of the kernel depends on the order you ran things in, including cells you have since edited or deleted, and the page shows only the final text of each cell. Two people can open the same notebook and get different answers.

The rule that prevents this is simple. Before you trust or share a result, use Kernel → Restart & Run All. If the notebook still produces the same numbers from a clean start, top to bottom, the page tells the truth.

Kernel state

The cells are evaluated exactly as Python would evaluate them, including the NameError for a variable that does not exist yet and float division for the mean. A variable is marked stale (amber) when a value it was computed from has changed since.

Things to try.

  • Run 1, 2, 3, 4. The mean is 7.75, and the check agrees with a fresh run.
  • Now run cell 2 again, then cell 4. The printout still says 7.75, and the check says no. The list in memory has been doubled twice, but total was summed before the second doubling, so the stale total happens to give the old answer. Run cell 3 and then 4, and the mean jumps to 15.5.
  • Restart the kernel and run cell 4 first. NameError: nothing exists yet. In a real notebook you would see this only on a clean run, which is exactly why you do one.
  • Run 1, 3, 2, 4. Every cell has run exactly once and every counter looks innocent, yet the mean is 3.875, half the right answer: total was summed before the list was doubled.

The Python you will see in every chapter

Data code is mostly transformations: take a collection, keep some items, compute something from each, summarise. Python's comprehensions say that in one line, and they are the idiom the course uses whenever NumPy or pandas is not the better tool.

prices = [310_000, 245_000, 512_000, 189_000]
cities = ["Leeds", "York", "Leeds", "Hull"]

# list comprehension: keep some items, transform each
leeds = [p for p, c in zip(prices, cities) if c == "Leeds"]      # [310000, 512000]

# dict comprehension: build a lookup
index = {c: i for i, c in enumerate(sorted(set(cities)))}     # {'Hull': 0, 'Leeds': 1, 'York': 2}

# generator expression inside a function call: no list is built
n_expensive = sum(1 for p in prices if p > 300_000)          # 2

The second idiom is the small pure function: it takes data, returns new data, and changes nothing else. Pure functions are easy to test, easy to reuse between a notebook and a script, and immune to the hidden-state problem above, because nothing they do depends on what ran before.

def price_per_m2(rows: list[dict]) -> list[float]:
    """Price per square metre for each sale; rows without an area are skipped."""
    return [r["price"] / r["area_m2"] for r in rows if r.get("area_m2")]

# Avoid: a function that edits its argument in place. The caller's list
# changes too, and running the notebook cell twice changes it twice.
def add_ratio_in_place(rows):
    for r in rows:
        r["ppm2"] = r["price"] / r["area_m2"]

As a notebook grows, move anything you call twice into a function, and anything you use in two notebooks into a .py file next to them that both import. Notebooks are for looking; modules are for code you depend on.

Reading CSV and JSON

Datasets arrive as files, and the two formats you will meet most are CSV (rows of comma-separated values, one record per line) and JSON (nested objects, as returned by most web APIs). The standard library reads both, and it is worth doing once by hand to see what you get.

import csv, json
from pathlib import Path

data_dir = Path("data")

with open(data_dir / "sales.csv", newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))        # one dict per row, keyed by the header line

rows[0]            # {'date': '2024-03-01', 'city': 'Leeds', 'price': '310000'}
rows[0]["price"] * 2   # '310000310000'  -- every CSV value is a string

with open(data_dir / "listing.json", encoding="utf-8") as f:
    listing = json.load(f)                # dicts, lists, str, int, float, bool, None

Two details matter. CSV has no types: every value comes back as text, and a missing value is an empty string, so "310000" * 2 repeats the text instead of doubling the number. And JSON keeps numbers as numbers but has no date type, so dates arrive as strings too. Converting types by hand row by row is exactly the work pandas does for you, which is why Prerequisite 3 reads the same file with one call. Knowing what the raw file contains is what lets you notice when pandas guessed wrong.

Random seeds

Much of machine learning is deliberately random: shuffling rows, splitting into training and test sets, initialising weights, sampling features in a random forest. Computers produce this randomness with a pseudo-random number generator, a deterministic sequence that looks random and starts from a number called the seed. Same seed, same sequence, same result.

import random
import numpy as np
from sklearn.model_selection import train_test_split

random.seed(42)                                # Python's own random module
rng = np.random.default_rng(42)                  # NumPy: a Generator object you pass around
noise = rng.normal(0, 1, size=5)                 # identical on every run

X_train, X_test = train_test_split(X, test_size=0.2, random_state=42)   # scikit-learn

Prefer a Generator from default_rng over the older global np.random.seed: a generator is an object you pass to the code that needs it, so two parts of a program cannot disturb each other's sequence. In scikit-learn, every estimator and splitter with randomness takes a random_state argument. The course always sets it.

Seeding is not the same as choosing a lucky seed. If a result holds for seed 42 and collapses for seed 7, the result is noise. Chapter 13 and Chapter 36 turn that into a method: run several seeds or folds and report the spread.

Use case: how many published notebooks still run?

In 2019 a team of researchers from Brazil and the United States (Pimentel, Murta, Braganholo and Freire, at the Mining Software Repositories conference) collected about 1.4 million Jupyter notebooks from public GitHub repositories and tried to re-execute them. Roughly one in four of the notebooks they attempted ran from top to bottom without an error, and only about one in twenty-five reproduced the outputs saved in the file. The causes were the ones on this page: packages that were never recorded, files that existed only on the author's machine, and cells that had been run out of order, so that the saved outputs came from a kernel state the page no longer described. None of this needs exotic tooling to avoid. An environment file, relative paths, and a clean "Restart & Run All" before committing would have rescued most of them.

⚠️
Common mistakes
  • Installing packages into the system Python, then wondering why another project broke.
  • No requirements.txt, or one written by hand without versions.
  • Trusting a notebook you have not restarted. The numbers on screen may come from cells that no longer exist.
  • Cells that are not safe to run twice, such as data = [x * 2 for x in data] or a function that edits a list in place.
  • Arithmetic on CSV values without converting them. "5" + "5" is "55".
  • Absolute paths like C:\Users\me\Desktop\data.csv, which exist on exactly one machine.
  • Forgetting a seed somewhere, so the split is reproducible but the model is not, or the other way round.

Interview drill

Explain it simply: Why can the same notebook give a colleague a different answer from the one you got?

How a strong answer sounds
A notebook's cells all run in one long-lived Python process, the kernel, and every variable a cell creates stays in that process. So the result depends on which cells ran and in what order, including cells I have since edited or deleted, but the page only shows the final text of each cell. If I ran a cell twice, or ran them out of order, my numbers came from a state my colleague cannot recreate by running the page top to bottom. Add to that a different package version or a missing seed, and the answers diverge. The fix is to restart the kernel and run everything from the top before sharing, pin the environment, and seed every random step.

Deeper: How would you make a modelling experiment reproducible for someone else on your team?

How a strong answer sounds
I would cover four things: code, environment, data and randomness. Code: the logic lives in functions and modules under version control, and the notebook only calls them, and it passes a clean "Restart & Run All". Environment: a pinned requirements or lock file, plus the Python version, so the same library versions produce the same defaults. Data: a fixed snapshot with a version or checksum, read through relative paths, never "whatever is in the database today". Randomness: one seed set at the top and passed explicitly to every splitter and model as random_state, with NumPy's default_rng rather than global state. I would also record the outputs that matter, the metrics with their cross-validation spread, so that a rerun can be compared with them. And I would be honest about the limits: some operations are not bit-for-bit deterministic across hardware or thread counts, so I would aim for results that agree within their noise, and check that by rerunning with a few different seeds.

🧠 Key takeaways

  • One virtual environment per project, and pip freeze > requirements.txt so that it can be rebuilt.
  • A notebook's kernel keeps every variable you created, in the order you ran things; the page does not show that order.
  • "Restart & Run All" before trusting or sharing a result.
  • Comprehensions and small pure functions keep data code short, testable and safe to rerun.
  • CSV values arrive as strings and JSON has no dates: know your types before you compute.
  • Seed every source of randomness, and treat a result that depends on the seed as noise.

Check your understanding

After running all four cells once, you accidentally run data = [x * 2 for x in data] a second time. What does data now hold?

The cell reads the current data from the kernel and doubles it again. Cells are not idempotent unless you write them that way.

What is the main reason to create a separate virtual environment for each project?

Isolation is the point: upgrading pandas for one project cannot change another, and pip freeze records exactly what this project used.

A CSV file has a price column of whole numbers. What type is row["price"] after reading it with csv.DictReader?

The csv module does no type conversion: every value is text, and an empty field is an empty string. Converting is your job, or pandas'.

Two separate scripts each run rng = np.random.default_rng(42) and then rng.random(5). What do they print?

A seeded generator is a deterministic sequence: the same seed and the same calls give the same numbers, on any machine running the same NumPy version.

You are about to send a notebook to a colleague. Which single step best checks that its numbers are real?

Only a clean top-to-bottom run proves the results do not depend on hidden state from cells run out of order, edited or deleted.
