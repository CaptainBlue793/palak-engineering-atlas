pandas DataFrames

Real datasets arrive as tables: sales with a date, a customer and an amount; customers with a city and a sign-up date. pandas is the library that loads those tables, cleans them, combines them and summarises them, and almost every feature in this course is computed with it before the numbers are handed to scikit-learn as an array.

Most pandas mistakes do not raise errors. A join that matches more rows than you expected, a group-by that drops the rows with a missing key, an integer column that quietly becomes a float: each one produces a table that looks fine and is wrong. The simulator joins two small tables and shows exactly how a duplicated key multiplies rows and inflates a total.

  • Load a CSV with the right types and read what .dtypes tells you
  • Select rows and columns with loc and iloc, and assign safely
  • Summarise with groupby and named aggregations, including missing keys
  • Join tables with merge, choose the join type, and guard it with validate
  • Handle dates and categorical columns

Series, DataFrames and dtypes

A DataFrame is a table: named columns, each with its own dtype, sharing one row index. A single column is a Series. The index labels the rows; for a freshly loaded file it is simply 0, 1, 2…

import pandas as pd

sales = pd.read_csv("data/sales.csv", parse_dates=["date"])
sales.head()          # first five rows
sales.shape           # (rows, columns)
sales.dtypes
# date     datetime64[us]   -- parsed because we asked
# city                str   -- pandas 3 has a real string dtype (older versions: object)
# price           float64   -- whole numbers, but one price is missing
sales.info()          # dtypes plus non-null counts per column
sales.describe()      # count, mean, std, min, quartiles, max of numeric columns

Read that last dtype carefully. The prices are whole numbers, yet the column is float64, because one is missing and pandas represents a missing number as NaN, which is a float. An integer column turning into floats is often the first visible sign of missing data. Always look at dtypes and info() before doing anything else with a new file.

Selecting rows and columns

sales["price"]                        # one column, a Series
sales[["city", "price"]]                # several columns, a DataFrame

sales.loc[sales["price"] > 300_000, ["date", "price"]]   # loc: rows by label or mask, columns by name
sales.loc[0:2]                           # labels 0, 1 AND 2: loc slices include the end
sales.iloc[0:2]                          # positions 0 and 1: iloc slices exclude it, like Python

# Assigning: one loc call with the row mask and the column together
sales.loc[sales["city"] == "Leeds", "region"] = "Yorkshire"
sales = sales.assign(price_k=sales["price"] / 1000)   # or build a new frame

One rule saves a lot of confusion: loc uses labels, iloc uses positions, and they slice differently at the end. And when you assign, do it in one loc call. Writing sales[sales.city == "Leeds"]["region"] = … selects a filtered copy first and assigns into that; since pandas 3.0, where copy-on-write is the default, it never changes sales, and pandas warns about it.

Group, aggregate, combine

Most summaries have the same shape: split the rows into groups by a key, compute something per group, and combine the answers into a new table. That is groupby.

# orders, with each customer's city joined on (joins are the next section)
orders.groupby("city").agg(
    orders=("order_id", "count"),
    revenue=("amount", "sum"),
    avg=("amount", "mean"),
)
#        orders  revenue   avg
# city
# Hull        1       30  30.0
# Leeds       2      100  50.0
# York        1       25  25.0      <- where did the order with no city go?

orders.groupby("city", dropna=False)["amount"].sum()   # now a NaN group holds the missing 15

# transform: a per-group value broadcast back to every row (a feature, not a summary)
orders["city_avg"] = orders.groupby("city")["amount"].transform("mean")

Two details are worth remembering. By default, groupby drops rows whose key is missing, so totals can shrink without a word; pass dropna=False when you need every row counted. And transform returns one value per original row rather than per group, which is how "this customer's average spend" becomes a column you can feed to a model.

Joining tables

Features usually live in several tables. Orders know the customer ID; customers know the city. merge lines the rows up on a key column, and the how argument decides what happens to rows without a partner.

how=KeepsRows without a matchTypical use
innerKeys present in both tablesDropped from both sidesOnly rows you can fully describe
leftEvery row of the left tableLeft rows kept, right columns NaNAdding features to a training table: never lose an example
rightEvery row of the right tableRight rows kept, left columns NaNRarely; swap the tables and use left
outerKeys from either tableKept from both sides, NaN where missingReconciling two sources, finding what is missing where

The join type controls rows without a match. The more dangerous question is rows with more than one match. If a customer ID appears twice in the customers table, every one of that customer's orders comes out twice. Nothing fails; the table is just longer, and every sum over it is too big. The defence is to say what you expect: validate="many_to_one" makes pandas raise an error if the right-hand keys are not unique.

train = orders.merge(customers, on="customer_id", how="left",
                     validate="many_to_one",      # each order has at most one customer
                     indicator=True)               # adds _merge: both / left_only / right_only
assert len(train) == len(orders)                 # a left join must not add rows

Things to try.

  • left, each ID once. Five rows, total 170. Order 104's customer C4 is not in the customers table, so its city is NaN. Nothing was lost.
  • inner. Four rows, total 155. Order 104 has vanished, and with it 15 of revenue. An inner join is a filter as well as a join.
  • left, with C1 entered twice. Seven rows, total 270. Orders 101 and 103 now appear twice, once as Leeds and once as Bradford. Every per-city count, every average, every model trained on this table is wrong.
  • Now set validate. pandas refuses: the duplicate is caught at the join instead of in next month's revenue report.
  • right and outer. Customer C5 has no orders, so a row with NaN order ID and amount appears, and both integer columns become floats.

Dates and categories

sales["date"].dt.dayofweek                      # 0 = Monday
sales["month"] = sales["date"].dt.to_period("M")
sales.set_index("date").resample("W")["price"].mean()   # weekly averages

sales["city"] = sales["city"].astype("category")   # integer codes plus a lookup table
sales["city"].cat.categories
sales["city"].value_counts()                    # how often each city appears

Dates parsed with parse_dates (or pd.to_datetime) gain the .dt accessor, which turns one timestamp into the features models can use: day of week, month, hour, days since an event. A category dtype stores a column with few distinct values as small integer codes, which saves memory on large tables and makes the set of allowed values explicit. Both come back in Chapter 15 and Chapter 30.

Use case: the revenue that grew overnight

A familiar story in analytics teams goes like this. A dashboard's monthly revenue jumps 12% from one day to the next, with no change in sales. The pipeline behind it joins the orders table to a customers table to attach a region, then sums by region. Overnight, a sync from the CRM wrote a second row for a few hundred customers whose account had been merged, so those customers' orders started appearing twice in the join, exactly like C1 in the simulator. Every downstream number moved, and the same join fed the training table for a churn model, which now saw duplicated customers in both its training and test sets. The fix takes one line, validate="many_to_one", plus an assert that a left join leaves the row count unchanged. Both turn a silent data change into a loud failure at the moment it happens.

⚠️
Common mistakes
  • Joining on a key that is not unique on one side, and multiplying rows without noticing.
  • Using an inner join to add features, and quietly dropping every example without a match.
  • Summing after groupby and losing the rows with a missing key.
  • Chained assignment such as df[df.x > 0]["y"] = 1, which never updates df.
  • Confusing loc and iloc, especially after filtering, when labels no longer match positions.
  • Not checking dtypes after loading: dates as text, numbers as text, integers as floats.
  • Looping over rows with iterrows to compute a column that one vectorised expression would give.

Interview drill

Explain it simply: What is the difference between a left join and an inner join, and which would you use to add features to a training table?

How a strong answer sounds
Both match rows on a key. An inner join keeps only the keys found in both tables, so a row on either side without a partner disappears. A left join keeps every row of the left table and fills the right table's columns with missing values where there is no match. To add features to a training table I use a left join with the training table on the left, because I must not lose examples just because one feature source has no record for them; the missing values become something to handle, often a feature in themselves. I also check that the row count did not change, because if the right table's key is not unique, a left join adds rows too.

Deeper: After a join, your training set has 1.2 million rows instead of 1 million. What happened, and how would you prevent it?

How a strong answer sounds
The join matched some rows more than once, which means the key was not unique in the table I joined in: duplicate customer records, a history table with several rows per customer, or a key that is only unique together with another column, like customer and date. I would find it with customers["customer_id"].duplicated().sum() and look at the duplicated keys to understand why they exist, because the right fix depends on the cause: deduplicate if they are errors, choose the right row if it is a history table, such as the latest record before each order's date, or aggregate the right table to one row per key before joining. Then I would make it impossible to happen silently again: validate="many_to_one" on the merge, an assertion that the row count is unchanged after a left join, and ideally a uniqueness check on the source table in the pipeline. I would also check whether duplicates leaked across my train and test split, because the same order appearing in both makes the test score optimistic.

🧠 Key takeaways

  • Check dtypes and info() first: missing numbers turn integer columns into floats.
  • loc is by label and includes the end of a slice; iloc is by position and excludes it.
  • Assign with one loc call; chained assignment does not change the original.
  • groupby drops missing keys unless dropna=False; transform gives a per-row feature.
  • Use a left join to add features, and assert the row count did not change.
  • validate="many_to_one" turns a duplicated key into an error instead of inflated numbers.

Check your understanding

A freshly loaded DataFrame has the default index 0, 1, 2, … How many rows does df.loc[0:2] return?

loc slices by label and includes the end label, so it returns rows 0, 1 and 2. iloc[0:2] would return two.

You left-join 5 orders to a customers table in which one customer ID appears twice, and that customer has 2 orders. How many rows come out?

Each of that customer's 2 orders matches 2 customer rows, so 2 extra rows appear: 5 + 2 = 7, with no error.

Some rows have a missing city. What happens to them in df.groupby("city")["amount"].sum()?

By default groupby drops rows whose key is missing, so the totals shrink. dropna=False keeps them as a NaN group.

A CSV column holds whole-number prices, but one price is blank. What dtype does pandas give the column?

pandas marks a missing number as NaN, which is a float, so the whole column becomes float64. It is often the first sign of missing data.

What does validate="many_to_one" do in orders.merge(customers, on="customer_id", validate="many_to_one")?

It is an assertion, not a fix: if the right-hand keys are not unique, pandas raises MergeError instead of multiplying rows.
