From Notebook to Production

A model in a notebook has answered a question once, on data someone already had. A model in production answers it thousands of times a day, on data that arrives one request at a time, through code written by different people, months after training. Most of what goes wrong lives in that gap: the model cannot be rebuilt, the saved file will not load, the service computes a feature slightly differently from training, or the world changes and nobody notices.

This chapter covers the minimum craft for crossing the gap with a scikit-learn model: training that can be reproduced, saving and versioning the whole pipeline safely, a small prediction API, catching training/serving skew, and a first look at monitoring for drift. MLOps is a field of its own; these are the habits every model needs before it is trusted with real decisions.

  • Make training reproducible: pinned data, code, seeds and versions
  • Save and load a whole pipeline, and know the security risks of pickle
  • Serve predictions behind an API with validated inputs
  • Detect training/serving skew by comparing logged features
  • Monitor input and score drift with the population stability index

Reproducible training

Anyone, including you in six months, should be able to rebuild the model exactly. That needs four things pinned: the data, a snapshot or a query with a fixed cut-off date and a hash of the result; the code, a training script in version control rather than notebook cells run in some order; the environment, exact library versions in a lock file or container image; and the randomness, seeds for every split and estimator. Record all of it next to the model, together with the validation metrics, so every model file can answer "what is this, and how good was it?"

# train.py: run from version control, not from a notebook
import json, hashlib, joblib, sklearn, pandas as pd
from datetime import date

df = pd.read_parquet("data/churn_2026-09-30.parquet")             # fixed snapshot
data_hash = hashlib.sha256(pd.util.hash_pandas_object(df).values).hexdigest()

Saving models safely

Save the whole fitted pipeline, preprocessing included, never the model alone (Chapter 24). joblib and pickle are the usual formats, with two cautions. Loading a pickle can execute arbitrary code, so only load files from sources you trust; the skops library offers a format that lists the types a file contains and refuses unknown ones. And pickles are tied to library versions: load them with the same scikit-learn version that saved them, which is why the version goes in the metadata. Check size and speed too: on California housing, a 300-tree random forest saved to a 543 MB file and took 59 ms to score one row, while a histogram gradient-boosted model was 0.4 MB and took 1.3 ms, with better accuracy.

A prediction API

The simplest serving pattern loads the pipeline once at start-up and exposes a prediction endpoint. Validate every request against a schema, so a missing field or a string where a number belongs is rejected with a clear error rather than silently becoming a wrong prediction. Log each request's features, the prediction and the model version: those logs are what skew checks, monitoring and the next training set are built from. For high volumes, batch scoring on a schedule is often simpler and cheaper than a live API.

from fastapi import FastAPI
from pydantic import BaseModel, Field
import joblib, pandas as pd

app = FastAPI()
model = joblib.load("models/churn-v7.joblib")              # once, at start-up

class Customer(BaseModel):
    tenure_days: int = Field(ge=0)
    monthly_spend: float | None = None                  # missing allowed: the pipeline imputes it
    plan: str

@app.post("/predict")
def predict(c: Customer):
    p = float(model.predict_proba(pd.DataFrame([c.model_dump()]))[0, 1])
    log_prediction(c, p, model_version="churn-v7")        # features, score, version
    return {"churn_probability": p, "model_version": "churn-v7"}

Training/serving skew

Skew is any difference between the features the model was trained on and the features it receives in production. It arises when the serving path re-implements feature logic: tenure computed in hours instead of days, missing values filled with 0 instead of the training median, a new category mapped to the wrong column, a timezone, a rounding rule. Nothing crashes; predictions are just quietly wrong. The defences are to share one implementation of feature logic between training and serving (the pipeline itself, or a feature store), and to log the features as served, then recompute them offline for a sample of requests and compare.

Simulator: skew and drift

Skew: a churn model trained with a correct pipeline; the serving code has up to three bugs. Compare its predictions with what the training pipeline would have produced for the same 1,000 requests. Drift: 30 weeks of production data in which a pricing change from week 13 raises customers' spending and makes long-standing customers as likely to leave as new ones; watch the population stability index of an input and of the model's score, and the model's AUC as labels arrive four weeks late.

Things to try.

  • Skew: set tenure to hours. 995 of 1,000 predictions move by more than 0.05 and the average predicted churn falls from 35.3% to 0.5%, because every customer now looks 24 times as loyal. AUC drops from 0.720 to 0.659. No error is raised; the skew check flags all 1,000 logged tenure values.
  • Reset tenure; fill missing spend with zero. 145 predictions shift, exactly the requests with a missing value, and AUC falls to 0.669: a zero spend looks like a customer who barely uses the service.
  • Map the new family plan to premium. 100 predictions shift, the family-plan customers, and AUC falls to 0.708. Treating an unknown category as "none of the known ones" is the safer default.
  • Drift, alert at 0.2. The price change starts in week 13. Spend's PSI fires in week 14 and the model score's in week 16. Average AUC falls from 0.735 to 0.602 over the last ten weeks; the first clear drop is in week 13, but with labels four weeks late nobody can see it until week 17. Lower the threshold to 0.1 and the spend alert comes in week 13.
  • Read the churn rates. Over the last ten weeks the model predicts 52% churn and 56% actually churn: drift breaks calibration as well as ranking.

Drift, a first look

Data drift is a change in the inputs' distribution; concept drift is a change in how inputs relate to the outcome. Both erode a model, and labels usually arrive too late to see it in accuracy until weeks have passed. So monitor what you can see immediately: input distributions and the model's score distribution, with a statistic such as the population stability index (PSI) or a two-sample test, alongside the share of missing values and unseen categories. When labels arrive, track performance by week and by segment. Alerts should lead to investigation, not automatic retraining: drift can be a pipeline bug, a seasonal pattern the model already handles, or a genuine change that needs new data.

Use case: the hidden technical debt of machine learning

In 2015 D. Sculley and colleagues at Google published "Hidden Technical Debt in Machine Learning Systems", drawn from years of running production models. Its best-known figure shows a real ML system as a large diagram of boxes, configuration, data collection, data verification, feature extraction, resource management, serving infrastructure, monitoring, in which the machine learning code itself is a small black square in the middle. The paper catalogued the ways such systems decay: models that silently depend on undeclared data sources, glue code and pipeline jungles that re-implement features in several places, feedback loops in which a model's outputs shape its future training data, and configuration nobody fully understands. Many of its remedies are this chapter's habits: one shared implementation of features, logged inputs, monitoring of predictions and data, and treating training as reproducible software rather than an experiment. The companion "Rules of Machine Learning" by Martin Zinkevich put one of them bluntly: the best way to make sure you train like you serve is to save the features used at serving time and use those logs for training.

⚠️
Common mistakes
  • Training in a notebook with cells run out of order, so nobody can reproduce the model.
  • Saving the model without its preprocessing, and rewriting the preprocessing in the service.
  • Loading pickles from untrusted sources or with different library versions.
  • No input validation, so bad requests become confident wrong predictions.
  • Not logging served features, leaving skew invisible.
  • Monitoring only accuracy, which arrives weeks after the problem began.

Interview drill

Explain it simply: What is training/serving skew?

How a strong answer sounds
It is when the data a model sees in production is computed differently from the data it was trained on, even though it is supposed to be the same. For example, training code might fill missing incomes with the median, while the service that makes live predictions fills them with zero, or one computes an age in years and the other in months. Nothing crashes, but the model's predictions are quietly wrong. The best prevention is to use exactly the same code for features in training and serving, for example by saving the whole pipeline, and the best check is to log the features the service actually used and compare them with what the training code would compute for the same inputs.

Deeper: You are deploying a churn model as an API. What do you put in place before and after launch?

How a strong answer sounds
Before launch: a training script in version control with pinned data snapshot, library versions and seeds; the whole pipeline saved with metadata, metrics and the scikit-learn version; a deploy test that loads the file and scores a fixed set of requests against expected outputs; an API with schema validation, sensible handling of missing values and unseen categories, and logging of raw inputs, computed features, scores and model version. I would run it in shadow mode first, scoring live traffic without acting on it, and compare served features and scores with an offline recomputation to catch skew. After launch: dashboards for request volume, latency, errors, invalid inputs, missing and unseen values, PSI on key features and on the score distribution, and, as labels arrive, AUC and calibration by week and segment, with alerts that page a person to investigate. Plus a rollback path to the previous model version and a schedule for retraining on recent data.

🧠 Key takeaways

  • Reproducibility needs pinned data, code, environment and seeds, recorded with the model.
  • Save the whole pipeline; load pickles only from trusted sources with the same versions.
  • Validate inputs at the API and log features, scores and model version.
  • Skew is silent; share feature code and compare served features with offline recomputation.
  • Monitor input and score drift immediately, performance when labels arrive.
