scikit-learn Pipelines

A real model is never just a model. Before the classifier sees anything, missing values are imputed, numbers scaled, categories encoded, and perhaps features selected. Each of those steps learns something from data: a median, a mean and standard deviation, a list of categories, a ranking of features. If it learns from the rows you later evaluate on, your scores are inflated, sometimes slightly and sometimes catastrophically.

A Pipeline bundles the preprocessing and the model into one object that is fitted, cross-validated, tuned and saved as a unit, so every learned step only ever sees training data. ColumnTransformer applies different steps to different columns. Together they are the most effective tool scikit-learn has against leakage, and the simulator shows how much a single misplaced step can fake.

  • Use ColumnTransformer for mixed numeric and categorical data
  • Explain why preprocessing must be fitted inside each cross-validation fold
  • Tune preprocessing and model hyperparameters together

Pipeline

Every scikit-learn transformer has fit, which learns from data, and transform, which applies what it learned. A Pipeline chains transformers and ends with an estimator. Calling pipe.fit(X, y) fits the first step on X, transforms X, passes the result to the next step, and so on until the model is fitted on fully processed data. Calling pipe.predict(X_new) runs only transform through the preprocessing steps, using what they learned during fit, and then predicts. The pipeline behaves like a single estimator, so anything that accepts a model, such as cross_val_score or GridSearchCV, accepts the pipeline.

ColumnTransformer

Tables mix types. ColumnTransformer sends each group of columns through its own steps and concatenates the results: median imputation and scaling for the numbers, most-frequent imputation and one-hot encoding for the categories. Columns you do not list are dropped unless you set remainder="passthrough".

from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline, make_pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.linear_model import LogisticRegression

prep = ColumnTransformer([
    ("num", make_pipeline(SimpleImputer(strategy="median"), StandardScaler()), ["age", "income"]),
    ("cat", make_pipeline(SimpleImputer(strategy="most_frequent"), OneHotEncoder(handle_unknown="ignore")), ["plan"]),
])
pipe = Pipeline([("prep", prep), ("model", LogisticRegression())]).fit(X_train, y_train)
pipe[:-1].get_feature_names_out()
# ['num__age', 'num__income', 'cat__plan_basic', 'cat__plan_pro', 'cat__plan_team']
pipe.predict(new_rows)      # a missing income and an unseen plan "enterprise" are handled, not errors

Leakage-free cross-validation

When you cross-validate a pipeline, each fold refits every step on that fold's training rows. The validation rows never influence an imputer's median, a scaler's mean, an encoder's categories or a selector's choice of features. Doing those steps on the full dataset first, and then cross-validating only the model, lets information from the validation rows leak into training. How much that matters depends on the step: on the breast cancer data, scaling before or inside cross-validation gave the same accuracy to four decimal places, 0.9789. Supervised steps that look at the target, such as feature selection or target encoding, are a different matter entirely. On 20 random datasets of 100 rows and 5,000 pure-noise features, SelectKBest(k=20) fitted before cross_val_score reported 88.6% accuracy on average, and never less than 82%; the same steps inside a pipeline reported 53.5%.

Things to try.

  • Start with 1,000 noise features, 100 rows, 20 kept. Selecting on all rows reports 85.6% on average, between 79% and 90% across the 30 datasets. The pipeline reports 47.8%, as it should for labels that are coin flips.
  • Toggle the left plot. With features chosen on all rows, the two class means sit well apart; with features chosen without each row, they sit much closer together. The leaky procedure picked features for separating the very rows it then scored.
  • Add features. With 3,000 noise features the leaky score rises to 88.5%; with 100 it is 70.7%. More features means more that line up with the labels by chance.
  • Shrink the data to 40 rows. With 1,000 features and 20 kept, the leaky score is 95.3%, and some datasets reach 100%. This is the shape of early microarray studies: few samples, thousands of features.
  • Keep more features. 50 kept gives 91.6%, 5 kept 73.6%. Across all 27 settings, the pipeline stays between 46% and 51%.

Tuning the whole pipeline

Grid search over a pipeline can tune preprocessing choices along with the model, using step__parameter names that follow the nesting. Whether to impute with the mean or the median, how many features to keep, and the regularisation strength are then all chosen by the same honest cross-validation.

from sklearn.model_selection import GridSearchCV

grid = {
    "prep__num__simpleimputer__strategy": ["mean", "median"],
    "model__C": [0.01, 0.1, 1, 10],
}
search = GridSearchCV(pipe, grid, cv=5, scoring="roc_auc").fit(X_train, y_train)
search.best_estimator_        # the whole fitted pipeline, refitted on all training data

Custom transformers and saving

For a stateless function, such as a log transform or a ratio of two columns, wrap it in FunctionTransformer. For a step that learns something, write a class with fit and transform, inheriting from BaseEstimator and TransformerMixin so it works with cloning, grid search and fit_transform. Learn state in fit only, store it in attributes ending in an underscore, and never look at y in transform.

from sklearn.base import BaseEstimator, TransformerMixin
import numpy as np, joblib

class Clipper(BaseEstimator, TransformerMixin):
    """Clip each column to quantiles learned on the training data."""
    def __init__(self, q=0.01):
        self.q = q
    def fit(self, X, y=None):
        self.lo_, self.hi_ = np.quantile(X, [self.q, 1 - self.q], axis=0)
        return self
    def transform(self, X):
        return np.clip(X, self.lo_, self.hi_)

joblib.dump(search.best_estimator_, "churn_model.joblib")   # preprocessing and model together
model = joblib.load("churn_model.joblib")                     # same scikit-learn version, trusted file only

Saving the whole pipeline means the service that loads it applies exactly the preprocessing the model was trained with, with no second implementation to drift out of step. Load pickled models only from sources you trust, since unpickling can run arbitrary code, and with the same library versions; record those versions next to the file (Chapter 39).

Use case: gene signatures that were too good to be true

Around 2000, microarrays let researchers measure the activity of thousands of genes in a few dozen tumour samples, and a stream of papers reported classifiers that predicted cancer type or outcome with near-perfect cross-validated accuracy. Many used the same procedure: rank the genes by how well they separated the classes across all the samples, keep the best few dozen, then cross-validate a classifier on those genes. In 2002 Christophe Ambroise and Geoffrey McLachlan showed in the Proceedings of the National Academy of Sciences that this procedure was badly biased. Re-analysing published datasets, including a colon cancer study with 62 samples and 2,000 genes, they found that cross-validation with the gene selection done outside the folds gave error rates close to zero, while repeating the selection inside each fold, on the training samples only, gave considerably higher and honest ones. With thousands of genes and dozens of samples, some genes will separate the classes by chance, and choosing them with the validation samples in view guarantees they look good on those samples. The fix they recommended is exactly what a pipeline does automatically.

⚠️
Common mistakes
  • Fitting a scaler, imputer, encoder or selector on all the data before splitting or cross-validating.
  • Calling fit_transform on the test set instead of transform with the training-fitted steps.
  • Preprocessing in pandas by hand for training and again, slightly differently, in the serving code.
  • Forgetting handle_unknown="ignore" so a new category in production raises an error.
  • Saving only the model, not the preprocessing it depends on.
  • Unpickling models from untrusted sources, or loading them with a different library version.

Interview drill

Explain it simply: Why use a scikit-learn Pipeline rather than preprocessing the data first?

How a strong answer sounds
A pipeline bundles the preprocessing steps and the model into one object. When I fit it, each step learns only from the training data; when I predict, it applies exactly the same learned transformations. That has three benefits. It prevents leakage, because during cross-validation every step is refitted inside each fold, so the validation rows never influence things like the scaler's mean or which features are selected. It lets me tune preprocessing choices together with the model in one grid search. And it lets me save and deploy one object, so production applies the same preprocessing as training without a second implementation.

Deeper: A colleague selected the 50 best features out of 10,000 using all the data, then reported 95% cross-validated accuracy on 120 samples. What do you say?

How a strong answer sounds
That estimate is biased, possibly enormously. With 10,000 features and 120 samples, many features will correlate with the label by chance, and selecting them using every sample means the validation folds helped choose the features they are then scored on. On pure noise this procedure regularly reports well above 80% accuracy. I would put the selection inside a pipeline so it is refitted on each fold's training rows, ideally with nested cross-validation if k is also being tuned, and compare against a permutation test: rerun the whole procedure with shuffled labels to see what accuracy it gets on no signal. If the honest estimate is far lower, the reported 95% should not be used, and if the result goes into a paper or a decision, a truly held-out test set or an external dataset is the real check.

🧠 Key takeaways

  • A Pipeline chains transformers and a model into one estimator; fit learns, transform and predict apply.
  • ColumnTransformer gives each column group its own preprocessing.
  • Cross-validating a pipeline refits every step inside each fold, which prevents leakage.
  • Unsupervised steps like scaling leak little; supervised steps like feature selection can fake strong results on noise.
  • Tune preprocessing and model together with step__parameter names.
  • Save the whole fitted pipeline, record library versions, and load only trusted files.

Check your understanding

What happens to a StandardScaler inside a pipeline when you call cross_val_score on the pipeline?

Every step of the pipeline is cloned and refitted for each fold, using only that fold's training rows.

Which preprocessing step done before cross-validation is most likely to inflate scores dramatically?

Supervised steps use the labels of the validation rows to shape the features. Scaling uses no labels and usually leaks very little; case folding and dropping IDs learn nothing at all.

In GridSearchCV over Pipeline([("prep", ...), ("model", LogisticRegression())]), how do you refer to the model's C?

Parameter names join step names and parameter names with double underscores, nesting as deep as needed.

Why set handle_unknown="ignore" on a OneHotEncoder in a deployed pipeline?

New categories appear in production. Ignoring them encodes the row as "none of the known categories" rather than crashing the request.

In a custom transformer, where should learned values such as quantiles be computed?

fit learns from training data; transform only applies. __init__ should just store the hyperparameters so cloning and grid search work.
