What Machine Learning Is

Ordinary software is a rule someone wrote down: if the basket total is over £50, delivery is free. Machine learning is for the cases where nobody can write the rule down, but plenty of examples exist. Instead of coding "this is what a bot looks like", you collect requests already labelled bot or human and let an algorithm find a rule that separates them.

That trade, examples in place of rules, has consequences that run through this whole course. The rule you get is only as good as the examples. You must check it on examples it has not seen. And when the world changes, the examples go stale and so does the rule. The simulator puts a hand-written rule and a learned one side by side on the same bot-detection problem, and then lets the bots change their behaviour.

Rules you write, rules you learn

A website wants to block scraping bots without blocking people. An engineer looks at the logs and writes a rule: block any client making more than 15 requests a minute. It works, mostly. Then some legitimate power users get blocked, some bots slow down to 14 requests a minute, and the rule grows: unless logged in, or the user agent is a known browser, or… Each exception is reasonable and the whole becomes unmaintainable.

The machine-learning version starts somewhere else. Collect thousands of past sessions where you know the answer, because the bot was later confirmed or the human completed a purchase. Describe each session with measurable features: requests per minute, pages per session, the share of requests for images. Then let an algorithm search a family of possible rules for the one that best separates bots from humans on those examples. The output is still a rule, a function from features to "bot" or "human", but nobody typed it.

The kinds of learning

In supervised learning, every training example comes with the answer, the label, and the model learns to predict it from the features. If the label is a number, such as a price or a delivery time, it is regression. If it is a category, such as bot or human, or which of ten products a customer will buy, it is classification. Most of this course, and most ML in industry, is supervised.

In unsupervised learning there are no labels. The goal is to find structure: groups of similar customers (clustering, Chapter 25), a few directions that summarise many features (dimensionality reduction, Chapter 27), or the rare examples unlike the rest (anomaly detection, Chapter 29). A third family, reinforcement learning, learns by trial and reward and is outside this course.

The four ingredients, and the one test that matters

Every supervised learning algorithm in this course, from linear regression to gradient boosting, is the same four pieces put together differently.

  • Data: examples described by features, with labels.
  • A model family: the set of rules the algorithm may choose from, such as "every straight-line boundary" or "every decision tree of depth 6". Each member is picked out by its parameters.
  • A loss: a number measuring how wrong a given set of parameters is on the training data (Chapter 6).
  • An optimiser: a procedure that adjusts the parameters to make the loss small, such as gradient descent (Chapter 5).

And then the test. A model that scores well on its training data has only shown that it can remember those examples. What you want is generalisation: good performance on new examples from the same source. So you always hold some labelled data back, never let the model see it during training, and judge the model on it. Chapter 3 is about doing that properly, and the chapters after it keep returning to the same question in new forms.

Things to try.

  • Last month, the rule at 15 requests a minute. 97% accurate: 92 of 100 bots caught and one human blocked. Slide it to 10 and you catch 99 bots but block 7 people; slide it to 25 and nobody is blocked, but only 60 bots are caught. You are choosing a trade-off by hand.
  • Switch to this month. The same rule catches 2 bots out of 100. The bots slowed down to a human pace while still crawling dozens of pages.
  • Rewrite the rule for this month. No limit on request rate, more than 20 pages: 78 bots caught, 4 people blocked. It works, after someone noticed the problem and experimented.
  • Learned model, trained on last month, shown last month. 99% accurate, 97 bots caught, nobody blocked: better than any pair of thresholds, because its boundary is slanted and uses both features at once.
  • Show it this month's traffic. It catches 26 of 100 bots. Its examples are out of date, just like the rule.
  • Train it on this month. 87 bots caught, 13 people blocked. This month is genuinely harder, because slow bots overlap with busy humans and nothing separates them perfectly. But the fix was one retraining run, not a rewrite.

When not to use machine learning

Machine learning is a heavy tool. It needs labelled data, a way to evaluate, monitoring once deployed, and retraining as the world drifts. Plenty of problems do not justify it.

📘
Use case: Google's first rule of machine learning

Google publishes a guide for engineers called Rules of Machine Learning: Best Practices for ML Engineering, written by Martin Zinkevich and distilled from many production systems. Its first rule is "Don't be afraid to launch a product without machine learning". The argument is practical: a heuristic gets the product in front of users sooner, and those users generate the labelled data a model will later need. Its third rule completes the thought, "Choose machine learning over a complex heuristic". A simple rule is a fine start, but once the rule has sprouted dozens of special cases, like the bot rule at the top of this page, it has become a hand-built model that nobody can maintain or evaluate, and a learned model with proper evaluation is the more honest replacement.

⚠️
Common mistakes
  • Reaching for ML when a clear, stable rule exists, such as a tax calculation or a validation check.
  • Judging a model on its training data, which measures memory, not generalisation.
  • Training on data that does not look like the data the model will face, such as last year's bots.
  • Treating a model as finished. When behaviour changes, the examples go stale and the model with them.
  • Skipping the baseline and celebrating a model that a one-line rule would have matched.
  • Calling clustering results "classes". Unsupervised groups have no labels; someone still has to decide what they mean.

Interview drill

Explain it simply: What is machine learning, and how is it different from regular programming?

How a strong answer sounds
In regular programming a person writes the rule and the computer applies it to data. In machine learning you give the computer examples where you already know the answer, and an algorithm searches a family of possible rules for the one that fits those examples best; the result is a function you can apply to new data. It is the right tool when the rule is too complicated to write down but examples are plentiful, like recognising spam or predicting prices. The catch is that the rule is only as good as the examples, so you have to test it on data it did not learn from and keep it up to date when the world changes.

Deeper: A team asks you to "add ML" to decide which support tickets are urgent. How do you decide whether ML is the right approach?

How a strong answer sounds
I would start with how the decision is made today and what it costs to get it wrong. If urgency is defined by clear criteria, such as payment failures or a customer on a top-tier plan, a rule implements that exactly and is easy to audit, so I would ship rules first. ML becomes worth it if the signal is in messy text and context that rules cannot capture, and if we have, or can collect, labels: past tickets marked urgent by agents, or proxies like time to escalation. I would check the labels are consistent between agents, because a model cannot be more consistent than its training data. I would define the metric with the team, probably recall on truly urgent tickets at a manageable volume of flags, and compare any model against the rule-based baseline on held-out recent tickets. If the model clearly beats the rules, we deploy it alongside them, keep the hard rules for the cases that must never be missed, and plan monitoring and retraining, because ticket topics change with every product release.

🧠 Key takeaways

  • Machine learning finds a rule from labelled examples instead of a person writing it.
  • Supervised learning predicts a label: a number (regression) or a category (classification). Unsupervised learning finds structure without labels.
  • Every algorithm combines data, a model family, a loss and an optimiser.
  • Generalisation, performance on unseen data, is the only score that counts; always evaluate on held-out data.
  • When behaviour changes, a model trained on old examples degrades; retraining on recent data is the fix.
  • If a clear, stable rule exists, write the rule. Start with a heuristic baseline and make any model beat it.

Check your understanding

Predicting how many days a parcel will take to arrive is which kind of task?

The label is a number, so it is supervised regression. Predicting "late or on time" instead would make it classification.

A shop wants to group customers by purchase behaviour, with no predefined groups. What kind of learning is that?

There are no labels to learn from, only features. Finding groups of similar examples is clustering.

Which problem is least suited to machine learning?

Tax bands are an exact, published rule. Writing the rule is cheaper, exact and auditable; learning it from examples could only add errors.

What does it mean for a model to generalise well?

Training performance can come from memorising. Generalisation is measured on held-out examples from the same source.

A bot detector trained on last month's traffic misses many bots this month, after bots changed behaviour. What is the most direct fix?

The model learned last month's patterns. More old data teaches the same lesson; recent labelled examples teach the new one.
