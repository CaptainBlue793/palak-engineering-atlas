JSON & JSON Schema

Every tool call travels as JSON: the model writes an object of arguments, your code parses it, checks it and runs the tool. JSON Schema is the language you describe that object in. The model reads the schema to decide what to write, and your code uses the same schema to check what came back. It is the contract between the two, and the model only keeps the parts of it that you actually write down.

This chapter covers the JSON types and their traps, how to write a schema for a real tool, and how to validate against it with jsonschema and Pydantic. Then it measures qwen3:14b turning 30 plain-English alert requests into calls to one tool, given a schema with only types and given the full schema.

  • Use JSON's six types and know where Python and JavaScript disagree about them
  • Write a tool schema with enums, patterns, ranges and required fields
  • Decide which fields are required and whether extra fields are allowed
  • Validate arguments and turn the errors into messages a model can act on
  • Define the same contract once as a Pydantic model

JSON types

JSON has six types: object (keys are always strings), array, string, number, boolean and null. That is all. There is no integer type separate from number, no date, no bytes, no set, and officially no NaN or infinity. Everything else is a convention on top of these: a date is a string in a format both sides agree on, an enum is a string from a list.

Parsers disagree at the edges, and agent code sits between Python tools and JavaScript front ends, so it meets both. Measured with Python 3.12's json and Node's JSON.parse:

  • {"a": NaN}: Python parses it, and json.dumps writes it; JavaScript rejects it as a syntax error. Pass allow_nan=False when you write JSON other programs will read.
  • {"a": 1, "a": 2}: both silently keep the last value, 2.
  • {"id": 9007199254740993}: Python keeps the exact integer; JavaScript turns it into 9007199254740992, because its numbers are 64-bit floats. Send large IDs as strings.
  • Trailing commas and single quotes are errors in both. Models write them now and then; a parse failure must become a message back to the model, not a crash.

Writing a schema

A schema describes an object: its properties, each with a type and whatever rules narrow it down. The rules are what turn "a string" into "a string the tool can use": enum lists the allowed values, pattern is a regular expression the string must match, minimum and maximum bound numbers, minItems, maxItems and uniqueItems constrain arrays. And a description on every property says, in words, what goes there and in which unit. The model reads all of it.

CREATE_ALERT = {
    "type": "object",
    "additionalProperties": False,
    "required": ["name", "metric", "threshold", "window", "severity", "notify"],
    "properties": {
        "name":      {"type": "string", "pattern": "^[a-z0-9-]{3,40}$", "description": "Lower-case id with hyphens, e.g. checkout-errors-high"},
        "metric":    {"type": "string", "enum": ["cpu_pct", "disk_used_pct", "p99_latency_ms", "error_rate_pct"]},
        "threshold": {"type": "number", "minimum": 0, "description": "Fire above this value, in the metric's own unit"},
        "window":    {"type": "string", "pattern": "^[0-9]+(s|m|h)$", "description": "How long the condition must hold, e.g. 5m"},
        "severity":  {"type": "string", "enum": ["page", "ticket", "info"], "description": "page wakes someone; ticket is next working day"},
        "notify":    {"type": "array", "minItems": 1, "maxItems": 3, "uniqueItems": True,
                      "items": {"type": "string", "pattern": "^(#[a-z0-9-]+|[^@ ]+@[^@ ]+)$"},
                      "description": "Slack channels like #ops or email addresses"},
    },
}

Measured, the rules decided almost everything. Given the same six properties with types only, qwen3:14b produced a valid call for 0 of 30 requests: it invented metric names (checkout_error_rate, disk_usage, CPU), severities (high), names with spaces and capitals, and windows such as "30 minutes". Given the full schema, 27 of 30 were valid, and the model converted units on its own: "half a second" became 500 for p99_latency_ms, "1.2 seconds" became 1200.

Required and optional fields

required lists the properties that must be present; everything else is optional. Two decisions matter for tools. First, make a field optional only if the tool has a sensible default, and say what the default is in the description: a model cannot guess that a missing region means eu-west-1. Second, set additionalProperties: false. Without it, a misspelt or invented field passes validation and is silently ignored, which is how a model's "dry_run": true ends up as a real deletion when the field is actually called dryRun.

Validating

Validate every argument object before the tool runs, whatever the model was shown. The jsonschema library reports every error with the path to the bad value, which is exactly what a model needs to fix its call. Return the errors as the tool's result instead of running the tool.

from jsonschema import Draft202012Validator

validator = Draft202012Validator(CREATE_ALERT)

def create_alert_tool(args: dict) -> str:
    errors = sorted(validator.iter_errors(args), key=lambda e: list(e.path))
    if errors:
        return "error: invalid arguments\n" + "\n".join(f"- {'/'.join(map(str, e.path)) or '(root)'}: {e.message}" for e in errors)
    return save_alert(args)
# error: invalid arguments
# - window: '1d' does not match '^[0-9]+(s|m|h)$'

Validation checks shape, not meaning. Of the 27 valid calls, 26 did what was asked. The odd one out asked for "high memory over 90%": there is no memory metric, so the model picked disk_used_pct, a perfectly valid value that watches the wrong thing. The three invalid calls were more honest failures: a window of "1d" (a day is not in the pattern), four Slack channels where the schema allows three, and "ops at example dot com" turned into example.com. Each of those error messages tells the model exactly what to change, or tells you to ask the user.

Pydantic models

Pydantic lets you write the contract once as a class and get both the validator and the schema from it. The class is easier to read and refactor than a dictionary, model_json_schema() produces the JSON Schema to send to the model, and model_validate checks what comes back. On the same 30 calls it agreed with jsonschema exactly: the same 27 valid in each condition.

from typing import Annotated, Literal
from pydantic import BaseModel, ConfigDict, Field

class Alert(BaseModel):
    model_config = ConfigDict(extra="forbid")                 # additionalProperties: false
    name: Annotated[str, Field(pattern="^[a-z0-9-]{3,40}$")]
    metric: Literal["cpu_pct", "disk_used_pct", "p99_latency_ms", "error_rate_pct"]
    threshold: Annotated[float, Field(ge=0)]
    window: Annotated[str, Field(pattern="^[0-9]+(s|m|h)$")]
    severity: Literal["page", "ticket", "info"]
    notify: Annotated[list[str], Field(min_length=1, max_length=3)]

schema = Alert.model_json_schema()        # send this to the model
alert = Alert.model_validate(arguments)   # raises ValidationError listing every problem

One difference to know: by default Pydantic is lax, so it converts "90" to 90.0 for a float field and accepts it, while JSON Schema says a string is not a number. Use strict=True on fields where a wrong type means a wrong call. RAG P1 measures what lax mode accepts.

Use case: JSON Schema as the shared language of tool calling

JSON Schema began in 2009 as an internet draft for describing JSON documents and spent years in API tooling: OpenAPI, which describes most HTTP APIs, uses it for request and response bodies. When OpenAI added function calling to its chat API in June 2023, it chose JSON Schema to describe function parameters, and the other model providers followed, as did Ollama, the Model Context Protocol and every major agent framework. One consequence is that the agent ecosystem inherited JSON Schema's toolchain for free, from validators in every language to generators like Pydantic. Another is that providers support different subsets of it: strict structured-output modes accept only some keywords and require others, so a schema that validates fine in your code may need adjusting before an API will accept it.

⚠️
Common mistakes
  • Schemas with types only, so the model fills enums and formats with plausible English.
  • Trusting the model to follow the schema and running the tool without validating.
  • Leaving out additionalProperties: false, so invented fields are ignored silently.
  • Optional fields with unstated defaults the model cannot know.
  • Raising an exception on bad arguments instead of returning the errors for the model to fix.
  • Treating a valid call as a correct one; validation checks shape, not meaning.

Interview drill

Explain it simply: Why give a model a detailed JSON Schema for a tool, and why validate its output against the same schema afterwards?

How a strong answer sounds
The schema is what the model reads to decide what to write, so every rule in it narrows its choices: enums give it the exact values, patterns the format, descriptions the units. With only types, a model fills fields with sensible English the tool does not accept; measured, that was 0 valid calls in 30 against 27 with the full schema. But the model is still guessing, so the code validates the same schema before running anything and returns precise errors when it fails, which gives the model a chance to fix the call. The schema guides; validation enforces.

Deeper: Every call your agent makes passes schema validation, but users report alerts that watch the wrong thing. What is going on?

How a strong answer sounds
Validation only checks that values are allowed, not that they match the request. When a user asks for something the tool cannot express, for example a memory alert when the enum only has CPU, disk, latency and errors, the model maps it to the nearest valid value instead of saying it cannot. I would look at those cases in the logs, make the tool's description say what it does not support and that the model should tell the user, consider an explicit "other" value that returns a clear refusal, and add evaluation cases with unsupported requests that check for a refusal rather than a valid call.

🧠 Key takeaways

  • JSON has six types; dates, enums and IDs are conventions you have to state, and parsers disagree on NaN and large numbers.
  • Enums, patterns, ranges and descriptions are what make a schema useful: valid calls went from 0 to 27 of 30.
  • Require what has no default, say the default when there is one, and forbid extra fields.
  • Validate every call and return the errors to the model instead of running the tool.
  • A valid call can still be wrong: one in 27 watched the disk when memory was asked for.
