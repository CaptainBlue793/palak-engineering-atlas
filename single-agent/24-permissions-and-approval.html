Permissions, Approval & Human in the Loop

An agent that can only read can be wrong; an agent that can write can be wrong and do something about it. Approval is the oldest safeguard: before an action that matters, a person says yes. It works when the agent asks about the right things, shows what the approver needs to decide, and does not ask so often that "yes" becomes automatic.

This chapter gives the incident agent from earlier chapters three write tools (roll back a deploy, restart a service, scale a service) and the task "Checkout is failing. Find the cause and fix it." qwen3:14b ran twelve incidents with no approval, with an approver who says only "denied", and with one who says why. The approver is simulated: it approves only the rollback that fixes the incident.

  • Rank actions by risk, and decide which need approval
  • Put the approval gate in the tool, not in the prompt
  • Give the agent only the permissions the task needs
  • Keep approval requests few and meaningful
  • Record who approved what, and why

Risk of an action

Rank actions by what happens if they are wrong. Reading errors is harmless. Scaling up costs money and is easy to undo. Restarting drops in-flight requests. Rolling back the wrong deploy can remove a fix someone else shipped. Deleting data or sending messages to customers cannot be undone at all. Two questions place an action: can it be undone, and who notices if it is wrong? Reads need no approval. Cheap, reversible writes may be allowed with logging. Anything costly, visible or irreversible needs a person.

Without approval, the agent fixed 11 of 12 incidents, and on the way it ran 11 changes that were not needed. In one incident it rolled back the wrong deploy of the cache, restarted checkout and scaled it before finding the real cause. In another it rolled back, restarted and scaled payments, then did the same to orders, six changes, and hit the 20-step limit without fixing anything or answering. When the agent is unsure, it tries things, and with write tools, trying things changes production.

Approval gates

The gate belongs in the tool, where it cannot be skipped. The model sees a normal tool whose description says it needs approval. When the model calls it, the host stops, shows the request to a person, and returns either the result or the denial as the tool result:

def gated(fn, risk: str):
    def call(**args):
        if risk == "read":
            return fn(**args)
        decision = ask_approver(action=fn.__name__, args=args, evidence=recent_tool_results())   # blocks; a person decides
        audit_log(fn.__name__, args, decision)
        if not decision.approved:
            return f"denied by {decision.who}: {decision.reason}"          # the reason is what the agent learns from
        return fn(**args)
    return call

With the gate, the agent fixed the same 11 of 12 incidents and no unnecessary change ran. Every one was stopped at the gate. Approval did not make the agent smarter; it made its mistakes cost nothing. In a real system the approver would also see the evidence (the error counts and deploy times the agent read), because "approve rollback of payments v4.18.1?" is not something a person can judge without it.

One incident changed for the worse under approval, and it shows how sensitive agents are to small changes. With "Needs approval from the on-call engineer" in the tool descriptions, the agent ended incident 7 with "I will now check the deploys of the checkout service…" and no tool call. The loop takes a reply without a tool call as the final answer, so the run ended there. Without that phrase, the same incident was fixed.

Least privilege

Approval limits what the agent does with the permissions it has; least privilege limits the permissions. Give an incident agent rollback rights for the services it is responsible for, not the deploy pipeline's admin token. Use credentials that only allow what the tools expose, so a tool that takes a free-text command (Chapter 19) cannot be used to do more. Grant writes for a session or a task, not permanently. The approval gate and the credential are separate layers. If the gate has a bug, the credential still bounds the damage.

Approval fatigue

Every request costs a person attention, and people who approve dozens of requests start approving without reading. Two things kept requests down here. First, gate only writes: reads never asked. Second, explain denials. With a bare "denied by the on-call engineer.", the agent treated a refusal as a reason to try something else on the same service: denied a rollback of payments, it asked to restart payments, then to scale it. That made 17 requests and 6 denials. With a reason ("that deploy is not the cause; check which service's own errors start the chain"), it went back to investigating and asked once more, correctly. That made 13 requests and 2 denials. A denial is feedback, and a bare "no" teaches the agent nothing.

Beyond that, batch: let the agent propose a plan of actions and approve the plan, or let a person approve a class of action ("restarts of checkout for the next hour") rather than each instance. Measure the approval rate. If people approve nearly everything, either the gate is on the wrong actions or nobody is reading.

Audit trails

Record every write the agent requests: the action and arguments, what the agent had read before asking (the evidence), who approved or denied it and why, when, and the result. When something goes wrong later, "the agent did it" is not an answer; the trail shows what it saw, what it proposed, and who agreed. It is also the data for improving the agent: denials with reasons are a list of its mistakes, labelled by an expert.

Use case: approval modes in coding agents

Coding agents made approval settings a visible part of the product. Claude Code asks before editing files or running commands unless the user has allowed them. It keeps allow and deny lists of specific commands and tools, and offers modes from "ask every time" to accepting edits automatically, with plan mode for proposing a plan before any change. OpenAI's Codex CLI launched with three approval modes, from suggesting changes for the user to apply, to editing files automatically, to a full-auto mode that runs commands only inside a sandbox with network access off. Both designs reflect this chapter. Reads are free, writes are gated by risk, people can approve whole classes of action to avoid fatigue, and the most autonomous mode is paired with the strongest sandbox (Chapter 23).

⚠️
Common mistakes
  • Approval by prompt ("ask before acting") instead of a gate in the tool.
  • Asking about everything, reads included, until approvals are automatic.
  • Bare denials, so the agent tries the next write tool instead of rethinking.
  • Approval requests without the evidence the person needs to judge them.
  • Broad credentials behind a narrow tool.
  • No audit trail of requests, decisions and reasons.

Interview drill

Explain it simply: Your agent can now restart services and roll back deploys. How do you keep it safe?

How a strong answer sounds
Rank actions by reversibility and blast radius, and gate the risky ones in the tool itself, so a person approves each request with the evidence in front of them. Reads stay ungated. Give the agent credentials that only allow what its tools expose, and log every request and decision. In a measured test without approval the agent fixed 11 of 12 incidents but ran 11 unnecessary restarts, scalings and wrong rollbacks on the way. With a gate it fixed the same 11 and none of those ran.

Deeper: Your on-call engineers complain about too many approval requests. What do you change?

How a strong answer sounds
First, check what is gated: reads and cheap, reversible actions should not ask. Then improve denials. In a measured test, bare denials led the agent to request the next write on the same service, 17 requests, while denials with a reason sent it back to investigating, 13 requests. Then batch: approve plans or classes of action for a time window. Finally, track the approval rate and the time to decide; near-100% approval means either the gate is misplaced or people are not reading.

🧠 Key takeaways

  • Without approval the agent fixed 11 of 12 but ran 11 unnecessary changes on the way.
  • A gate in the tool kept the same fixes and stopped every unnecessary change.
  • Denials with a reason cut requests from 17 to 13 and denials from 6 to 2.
  • Least privilege bounds the damage if the gate fails.
  • Log every request, the evidence, the decision and the reason.
