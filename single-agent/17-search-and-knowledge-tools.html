Search & Knowledge Tools

Retrieval-augmented generation (the RAG course) runs one search before the model answers. A search tool hands that decision to the agent: it writes the query, decides whether to read further, and can search again. That helps with questions one search cannot answer. It also lets the agent write a poor query, answer from a snippet, or not search at all.

This chapter measures both. A library of 88 runbooks: 12 topics with an outdated and a current version that disagree, 12 facts in a single document, 6 questions that need two documents ("who manages the team that owns search?"), and 40 documents of filler. qwen3:14b answered the same 30 questions with ten versions of the search setup. The worst got 0, the best 29.

  • Wrap search as a tool, with results the agent can actually use
  • See how the agent writes queries, and where they go wrong
  • Know why agents answer from snippets, and what to return instead
  • Handle outdated and conflicting sources with dates and a rule
  • Get questions that need two lookups answered

Search as a tool

Without search the model scored 0 of 30. It answered every question anyway, with plausible defaults: "the gateway admin interface typically uses port 8080", "100 requests per second", "wait at least 30 minutes". One fixed search (the question itself as the query, top three documents pasted in) scored 19 of 30. It got all twelve single-document facts, 7 of 12 conflicting topics (it took one of the two versions, with no way to tell which was current), and none of the two-document questions. The agent with a search tool and a read tool did no better at first: 16 of 30. To see why, look at what it did with the tools.

def search(query: str) -> str:
    """Search the runbook library. Returns up to 5 documents with a snippet."""
    return "\n".join(f"{d.id} | {d.title} | updated {d.updated} | {d.body[:90]}..."
                     for d in bm25(query, k=5))

def read(doc_id: str) -> str:
    """Read one runbook in full by its id, e.g. RB-104."""
    d = DOCS[doc_id]
    return f"{d.id}: {d.title} (updated {d.updated}, owner {d.owner})\n{d.body}"

Query writing by the agent

The agent searched once per question and wrote reasonable keyword queries: gateway health checks failover timeout, maximum number of replicas for checkout. The exceptions are instructive. For the two-document questions it often passed the question through unchanged (Who manages the team that owns orders?). For one certificate question it wrote TLS certificate rotation before expiry and dropped the service name, so the search returned other services' certificate runbooks plus the old orders runbook, and the agent answered 45 days instead of 7. Every setup in which the agent wrote the query got that question wrong, including the one told to "search with short keyword queries that keep the service name". The fixed search, which used the question itself as the query, got it right. If an entity matters, make it a parameter (search(query, service=...)) rather than hoping it ends up in the query.

The agent also sometimes did not search at all: 2 to 4 runs out of 30 in the first setups, 10 of 30 in one variant. Every one of those answers was wrong. Most stated an invented value as fact ("managed by the Order Management Team", "typically 15 minutes"), one adding "as outlined in the most recent runbook" without having searched. A few said the model had no access to the information, without trying the tool it had. A one-line rule in the loop fixed it: if the first reply has no tool call, reply "Search the runbook library before answering" and continue. With the rule, every run searched.

Reading results

The agent almost never called read. In 120 runs with snippets it opened a full document once, in the setup told that "search results show only a snippet: read a runbook in full before answering from it". That cost all three escalation questions in the conflict set, whose snippet ended exactly here:

RB-103 | db-main escalation contacts | updated 2026-07-05 | For db-main incidents, page the primary on-call first. The second-level escalation contact...

The agent's answer was "the contact is listed in RB-103", true and useless. The fix was in the tool, not the prompt: these runbooks are short, so return them whole. With whole documents in the results, conflicts went from 8 to 11 of 12. If documents are long, return the passage that matched instead of the first 90 characters. A snippet that stops before the answer just tells the agent where the answer is.

Fetching pages

A read or fetch tool still matters for long documents and for the web, where a search result is only a title and a snippet. The same caution applies: the agent prefers to answer from what it has. Make the tool cheap to use, return the relevant part rather than the whole page, and check in your evaluation whether answers cite text the agent actually read. Web content is also untrusted input. A fetched page can contain instructions (Chapter 25).

Sources and trust

Twelve topics had two runbooks that disagreed, one from 2023 and one from 2026. Without dates, the agent hedged ("some procedures recommend 5 minutes, while others suggest up to 14") or picked one, and got 4 of 12. With the update date in each result, 6 of 12. With dates plus one sentence in the system prompt ("Runbooks may be outdated. When sources disagree, prefer the most recently updated one, and say that an older runbook disagrees"), 8 of 12, every one naming the older runbook as outdated. The remaining misses were the snippet problem above and the query that dropped the service name; with whole documents the score reached 11 of 12. Ranking by relevance does not rank by truth. Give the agent the metadata that decides between sources (dates, owners, status) and a rule for using it.

Two lookups

"Who manages the team that owns search?" needs the ownership runbook ("search is owned by the Delta team") and then the Delta team's charter ("managed by Tomasz Nowak"). The agent did the first search and stopped: "the team that owns orders is managed by the Atlas team". It treated the owner as the answer. In runs where it did not search, it invented a manager: "the Engineering Leadership group". That was 0 of 6 in the first five setups. Instructions helped little. "If the answer needs a second fact, search again" got 2 of 6 in one setup and 1 in another, and in that second setup it made the agent skip searching for 10 of 30 questions. What worked was putting the second hop in the data: ownership runbooks link to the team's charter, and search returns linked documents with the result. 6 of 6, and 29 of 30 overall.

Use case: WebGPT

WebGPT (Nakano and colleagues, OpenAI, 2021) fine-tuned GPT-3 to answer questions by operating a text-based web browser through commands: search, click a link, scroll, find in page, and quote a passage. Answers had to be built from the quoted passages, which were shown as references, and human raters compared answers partly on how well the references supported them. The design anticipated the problems measured here: the model had to open pages rather than trust result snippets, collect evidence before answering, and expose its sources so a reader could judge them. Later search products that cite their sources follow the same pattern.

⚠️
Common mistakes
  • Snippets cut at a fixed length, ending before the answer; return the matching passage.
  • Expecting the agent to open documents because the prompt says so; it read 1 in 120 times.
  • No dates or owners in results, so outdated and current sources look equally good.
  • Letting the agent answer without searching; enforce one search in the loop.
  • Leaving key entities to the query text instead of a parameter.
  • Expecting multi-hop questions to work without links between documents or a planning step.

Interview drill

Explain it simply: What is the difference between RAG and giving an agent a search tool?

How a strong answer sounds
RAG runs a fixed search before the model answers; the agent version lets the model decide what to search for, whether to read more and whether to search again. That can answer questions a single search cannot, such as ones needing two documents. It also adds failure modes: poor queries, answering from snippets, or not searching at all. In a measured runbook library, one fixed search scored 19 of 30 and a basic search agent 16. The agent only pulled ahead (29 of 30) once the tool returned whole documents with dates and linked documents, and the loop required a search before answering.

Deeper: Your agent cites the right runbook but gives an outdated value, or says "the answer is in RB-103". What would you change?

How a strong answer sounds
For the outdated value: put update dates (and owners or status) in the results, and add a rule to prefer the newest source and mention the disagreement. That took conflicts from 4 to 8 of 12. Archiving or labelling old documents at the source is better still. For "it's in RB-103": the snippet ended before the answer and the agent did not open the document. In 120 runs it opened one, even when told to. Return the matching passage or the whole short document instead of the first 90 characters; that took conflicts to 11 of 12.

🧠 Key takeaways

  • Without search the model answered every question, wrongly: 0 of 30.
  • The agent almost never opened documents, so snippets must contain the answer.
  • Dates plus a "prefer newest" rule took conflicting sources from 4 to 8 of 12; whole documents to 11.
  • Two-hop questions failed (0 of 6) until search returned linked documents (6 of 6).
  • A loop rule requiring one search stopped answers made from nothing.
