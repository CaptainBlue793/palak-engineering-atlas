Designing Tools a Model Can Use

A tool is an interface, and its user is a model that reads the definition every time and nothing else. It cannot open the source, ask a colleague or learn from last week's mistakes. Whatever it needs to choose the tool, fill its arguments and act on its result has to be in the name, the description, the schema and the text that comes back.

This chapter takes each of those parts in turn and measures what changing it does, with qwen3:14b. The 40 requests from Chapter 3 ran three times each with tool descriptions removed, terse, rich, and with meaningless names; then with 8, 20 and 50 tools on offer. The 12 investigations from Chapter 1 ran with three shapes of return value. Some results were what tool-design advice predicts. The most useful one was not.

  • Write names and descriptions that say what a tool does, when to use it and which values are valid
  • Keep arguments few and unambiguous
  • Return what the model needs for its next decision, not everything you have
  • Write error messages a model can act on
  • Decide how many tools to offer, and spot tools that overlap

Names and descriptions

A description should answer three questions: what the tool does, when to use it, and which values it accepts. The terse descriptions from Chapter 3 ("Current error rate and p99 latency of a service") answer the first. The rich versions added the other two: "Use it for questions about health, speed or latency. Services: checkout, payments, inventory…". Measured over 120 calls each:

  • No descriptions at all: 113 correct. The names alone carried most of it.
  • Terse: 114. "Is inventory healthy?" and "What does cache depend on?" failed every time: the model did not know those words were service names.
  • Rich: 117. Listing the services fixed both, every time. But "Use it for questions about health" pulled one general question ("Is 0.2% an acceptable error rate for checkout?") into a live lookup, three times in three. Descriptions steer; they steer everything that resembles them.
  • Opaque names (tool_1 to tool_8, terse descriptions): 114, the same as with real names. With descriptions present, the names mattered little here. Meaningful names still matter to the people reading traces.

The differences are small because this toolbox is easy: eight distinct tools and short requests. The failures were not random, though. Each one was a specific request failing every time, and each was fixed or caused by a specific sentence. That is the pattern to expect: description changes move particular requests, so evaluate them request by request (P8).

{"name": "get_metrics",
 "description": "Current error rate and p99 latency of one production service. "          # what
                "Use it for questions about health, speed or latency of a named service. "   # when
                "Services: checkout, payments, inventory, auth, search, orders, db-main, cache, email, gateway.",  # valid values
 "parameters": {"type": "object", "required": ["service"],
                "properties": {"service": {"type": "string", "enum": SERVICES}}}}

The service list belongs in the schema as an enum as well as in prose: the enum lets your code reject an invented name, the prose helps the model recognise "inventory" in a question.

Few, clear arguments

Every argument is a decision the model can get wrong. Prefer one obvious argument over several optional ones, enums over free strings, and units in the name (timeout_seconds, p99_latency_ms). When a tool needs many settings, ask whether it is really several tools, or whether your code can supply the values the model does not need to choose. A useful test is to read a definition as if you were new to the system: if you would need to ask a question before filling an argument, so will the model, and it will not ask. With the clear arguments here, the model got the arguments right almost whenever it chose the right tool, including "double the replicas of payments from 4" as 8. The one exception is a warning: with 20 tools on offer, "Reduce search to 3 replicas, traffic is low" was sent as scale_service(service="your-service-name", replicas=3) in two of three runs, a placeholder copied from nowhere in particular. A free-string argument accepts it; an enum of service names would have rejected it before anything was scaled.

Useful return values

The common advice is to return small, aggregated results instead of raw data, to save tokens. Measured on the investigations, that advice was half right. The get_errors tool returned errors in three shapes:

  • Aggregated counts ("714 × 503 from payments: upstream request failed"): 7 of 12, 3,463 tokens per investigation.
  • Raw log lines (60 timestamped lines): 10 of 12, at 13,326 tokens, almost four times as many.
  • Counts plus when they started ("714 × 503 from payments… (first seen 13:53)"): 10 of 12, at 3,667 tokens.

The raw lines won not because raw is better but because they contained timestamps. The bad deploy went out at 13:52; errors starting at 13:53 point straight at it, and without times the model picked deploys by keyword. Adding one field to the aggregate recovered all of the gain at a quarter of the tokens. Design a return value backwards from the next decision: what will the model have to decide after reading this, and what does it need to decide it?

Errors the model can act on

A tool's error is an observation the model reads like any other result, so write it for that reader. "Error 500" gives it nothing to do. "No service named 'inventry'. Services: checkout, payments, inventory, …" tells it how to fix the call. Say what was wrong, which input caused it, and what would work; say whether retrying could help. Chapter 8 measures how the wording of errors changes what the model does next.

def get_metrics(service: str) -> str:
    if service not in SERVICES:
        close = difflib.get_close_matches(service, SERVICES, n=1)
        hint = f" Did you mean '{close[0]}'?" if close else ""
        return f"error: no service named '{service}'.{hint} Services: {', '.join(SERVICES)}"
    m = metrics.current(service)
    return f"{service}: error rate {m.error_rate:.1f}% (normal under 0.5%), p99 {m.p99_ms} ms"   # say what is normal too

How many tools

Every tool is offered on every request, so more tools means more tokens and more chances to choose wrong. Adding plausible operations tools (alerts, pods, logs, SLOs, configuration, traces and so on) to the eight: with 20 tools, 115 of 120 correct, the same as with 8, at twice the prompt tokens (1,100 against 554). With 50 tools, 108 of 120, at 2,444 tokens per request. The new failures at 50 are instructive. "Anything weird in db-main's logs?" now went to get_logs instead of get_errors, three times in three: arguably a fair choice, because the two tools overlap. And "What changed in payments this morning?" got no call at all, three times in three, where with 8 tools it went to get_deploys. Overlapping tools make the model's choice depend on wording, and a long list makes the right tool easier to miss.

Keep a toolbox small and non-overlapping, and when the job needs many tools, offer only the ones relevant to the current state or task (the graph of P7, or the tool search of Chapter 20) rather than all of them every time.

Use case: the agent-computer interface of SWE-agent

SWE-agent, from Princeton researchers in May 2024, set out to get language models to fix real GitHub issues and found that the design of the tools mattered as much as the model. Instead of giving the model a plain shell, they built an "agent-computer interface": a file viewer that shows 100 lines at a time with line numbers, a search command that returns a compact list of matching files instead of every hit, and an edit command that runs a linter and refuses edits that introduce syntax errors, telling the model why. Each choice is a return-value or error-message decision of the kind measured in this chapter: show what the next decision needs, keep it small, and make failures informative. With the same model, their interface solved substantially more issues on the SWE-bench benchmark than a plain shell did. Case study 44 looks at it in detail.

⚠️
Common mistakes
  • Descriptions that say what a tool does but not when to use it or which values it accepts.
  • "Use it for anything about X" phrasing that pulls in requests that need no tool.
  • Returning aggregates that drop the one field the next step needs, such as when errors began.
  • Returning raw dumps "to be safe" and paying four times the tokens.
  • Overlapping tools (get_logs and get_errors) that make the choice depend on wording.
  • Offering every tool on every step as the toolbox grows.

Interview drill

Explain it simply: What makes a good tool description for an LLM?

How a strong answer sounds
It answers three questions: what the tool does, when to use it, and which values its arguments accept, ideally with the valid values also enforced as an enum in the schema. The model reads nothing else, so anything a new colleague would have to ask about belongs there. I would keep it specific, because broad phrases like "use it for anything about health" also attract questions that need no tool. And I would test changes on a labelled set request by request: in a measured case, adding the service list fixed two requests that failed every time and broke one that had worked.

Deeper: To save tokens, a teammate changed a tool to return aggregated counts instead of log lines, and the agent got worse. Why might that be, and what would you do?

How a strong answer sounds
The aggregation probably removed something the model used for its next decision. In a measured version, raw logs solved 10 of 12 investigations against 7 for counts, because the raw lines carried timestamps that matched errors to the deploy that caused them. Adding a "first seen" time to the counts brought success back to 10 of 12 at a quarter of the raw version's tokens. So I would compare traces of the cases that regressed, find what the model was using, and add that field to the compact format rather than reverting to raw dumps.

🧠 Key takeaways

  • Descriptions should say what, when and which values; listing services fixed two requests that always failed.
  • Description changes move specific requests both ways; evaluate them request by request.
  • Design return values from the next decision: one "first seen" field matched raw logs at a quarter of the tokens.
  • Write errors that say what was wrong and what would work.
  • From 8 to 50 tools, accuracy fell from 115 to 108 of 120 and tokens rose 4.4 times; keep toolboxes small and distinct.
