Building an Agent Benchmark

Every chapter in this course has measured agents on the same simulated estate: ten services, a failing checkout, a chain of errors leading to one bad deploy. It is a benchmark, built for the course, and this chapter audits it the way you should audit yours. The audit found a flaw that had been there since Chapter 1. A rule that never calls a tool, "name the most recent deploy anywhere", solves every task.

The chapter covers what makes a benchmark trustworthy: checkable tasks, resettable environments, difficulty and coverage, leakage and shortcuts, and running it often. It then measures qwen3:14b on 24 tasks of the original benchmark and on a hardened version, against two shortcut baselines that do no investigation at all.

  • Write tasks whose success a program can check
  • Build environments that reset exactly
  • Measure difficulty instead of assuming it
  • Hunt for shortcuts with dumb baselines
  • Keep a benchmark cheap enough to run on every change

Checkable tasks

A benchmark task is a starting state, an instruction, and a check that a program can run. Here the check was whether the answer names the version of the deploy that caused the incident. That is checkable because the simulator knows the cause. Write the check before the task's wording, and prefer checks on state (Chapter 27). Every task must have exactly one right answer, or the check must accept every right one. An ambiguous task measures luck.

Resettable environments

Each incident is generated from a seed: services, deploys, errors and the cause are a deterministic function of it. World(seed) rebuilt the same task in every chapter, so runs on different days and with different agents saw identical tasks. Write tools that change state (rollbacks, refunds, file edits) against a copy that is rebuilt per run, never against shared state. A benchmark you cannot reset is one you cannot repeat.

class World:
    def __init__(self, seed, root, change):
        self.r = random.Random(seed)                         # everything below derives from the seed
        self.version = f"v{self.r.randint(2, 9)}.{self.r.randint(0, 30)}.{self.r.randint(0, 9)}"
        for s in SERVICES:                                    # harmless deploys: 06:00 to 12:59
            self.deploys[s] = [(f"{self.r.randint(6, 12):02d}:...", ...)]
        self.deploys[root].append(("13:52", self.version, change))   # the cause: always 13:52

The two comments in that code are the flaw.

Leakage and shortcuts

Every harmless deploy was generated between 06:00 and 12:59, and the cause was always at 13:52. So the cause was always the most recent deploy in the whole estate. Two baselines that never investigate show what that means. "Name the latest deploy anywhere" solved 24 of 24 tasks. "Follow the error chain, then name that service's latest deploy", which ignores timing and the error text, also solved 24 of 24. The agent, which actually investigated, solved 19 of 24, fewer than a rule that reads nothing.

Shortcuts like this are common, and they are found the same way: by running baselines that should fail. Some baselines do nothing, some guess the most frequent answer, some apply one obvious heuristic. If a baseline scores well, the benchmark is measuring the shortcut. It also changes how to read earlier chapters. The agent did not exploit the shortcut (if it had, it would have scored 24), and the comparisons between designs still hold, but "11 of 12" never meant the agent could reason about timing. The tasks never required it.

The hardened version keeps the estate and changes three things. The cause happens at a random time between 08:00 and 15:59. Harmless deploys are spread over the whole day, including one on the guilty service after the cause. And the error logs say when errors were first seen, so the right answer is "the deploy just before the errors began", which is what the system prompt had always said. Both baselines fell to 0 of 24. The agent scored 21 of 24, higher than on the original, because the logs now gave it the timing evidence the method asked for.

Difficulty and coverage

The tasks were built in three levels by how far the cause was from checkout: zero, one or two hops. The assumption was that longer chains are harder. The measurement disagreed. On the hardened benchmark the agent solved 6 of 8 tasks where checkout itself was the cause, 7 of 8 at one hop, and 8 of 8 at two hops. On the original, 5, 7 and 7. At zero hops the agent found the right service and then picked the wrong one of its deploys: an earlier one whose change sounded related to the error, or the harmless one after the errors began. Label difficulty by measured success rate, not by a property you assumed matters, and make sure every kind of task your agent will meet in production appears in the benchmark.

Running it often

A benchmark that takes a day to run gets run before releases. One that takes ten minutes gets run on every change, and catches regressions when they are cheap to fix. These tasks take about 3 seconds each with thinking off when the model has the GPU to itself (Chapter 22), a little over a minute for all 24. Keep a fast suite for every change, a larger one nightly, and the same seeds in both, so a change in score means a change in the agent. Score changes of one or two tasks need repeated runs before they mean anything (Chapter 29).

Use case: shortcuts in public benchmarks

Shortcut learning has a long history in machine-learning benchmarks. In 2018 several groups showed that models could classify many natural-language inference examples from the hypothesis sentence alone, without reading the premise: the dataset's wording leaked the label. Agent benchmarks have had their own versions. Audits of SWE-bench found tasks whose tests rejected valid fixes or whose issue text contained the solution, which led to the curated SWE-bench Verified subset. The authors of τ-bench and later agent benchmarks report pass^k over repeated runs partly because single-run scores hid how often agents succeeded by chance. Each case was found the way this chapter's was: someone tried a method that should not have worked, and it did.

⚠️
Common mistakes
  • No baselines, so nobody notices that reading nothing scores 100%.
  • Generated tasks with a fixed pattern, such as the answer always being the latest or the first.
  • Difficulty labels from intuition instead of measured success.
  • Environments that are not reset, so earlier runs change later ones.
  • A benchmark too slow to run on every change.
  • Reading a one-task change in score as a real change.

Interview drill

Explain it simply: How would you build a benchmark for your company's agent?

How a strong answer sounds
Collect real tasks from the agent's job and turn each into a starting state that resets exactly, an instruction, and a check a program can run, ideally on final state. Measure difficulty by success rate and make sure every task type appears. Before trusting it, run dumb baselines. In one case a rule that never called a tool, "name the latest deploy", solved 24 of 24 because the generator always put the cause last. Keep a fast suite to run on every change.

Deeper: Your agent scores 95% on your benchmark but fails in production. What would you check?

How a strong answer sounds
Whether the benchmark can be solved without the skill production needs. Run baselines that should fail: no tools, most-frequent answer, one obvious heuristic. If they score well, the tasks leak the answer. In a measured case, the "latest deploy" shortcut scored 24 of 24 on the original tasks and 0 of 24 on a hardened version with random timings and a later harmless deploy. Then I would compare task types in the benchmark with production failures, and add the missing types as new tasks.

🧠 Key takeaways

  • A rule that never investigated solved all 24 original tasks; the agent solved 19.
  • The generator always put the cause last: a shortcut present since Chapter 1.
  • The hardened version scored both shortcuts at 0 and the agent at 21 of 24.
  • Measured difficulty contradicted the assumed difficulty levels.
  • Run baselines that should fail, reset environments exactly, and run the suite often.
