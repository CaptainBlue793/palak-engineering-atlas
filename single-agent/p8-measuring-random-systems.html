Measuring Systems That Vary

Change a prompt, run the agent, see it succeed, ship it. That is how most agent changes are judged, and it is how most bad agent changes get shipped. An agent's output varies from run to run, and its success varies far more from task to task, so one run of one task says almost nothing about whether a change helped. Every claim in the rest of this course is checked the way this chapter describes: many tasks, repeated runs, a success rate with an interval around it, and a comparison made task by task.

The measurement here is a real prompt change. Two system prompts for the alert-creating tool from P3, a minimal one and one with three rules of guidance added, were run ten times each on 30 hand-labelled requests at temperature 0.7: 600 runs.

  • Compute a success rate with a 95% confidence interval
  • Compare two versions task by task, and see what averages hide

One run proves nothing

Two things vary. The same task, run again, can give a different result because the model samples its tokens. And different tasks have very different difficulty: here, 27 of the 30 requests got the same result in every run under both prompts, and the remaining three decided everything. A demo that tries one task with each version is a coin with both faces chosen by which task you happened to pick. Measured: drawing 10 random tasks with one run per prompt, 10,000 times, the guided prompt looked better 26% of the time, worse 18% and equal 56%. Each of those draws would have produced a confident conclusion.

Success rate

The basic measure of an agent is its success rate: the fraction of runs that finish the task correctly, judged against a label you wrote before looking at the outputs. That needs three things: a set of tasks that represents the real work, a checkable definition of success for each one (here: a valid call with the right metric, threshold, window and severity, or no alert when the metric is not supported), and enough runs. Labels are part of the experiment. One request here, "alert when the disk on db-03 is more than ninety percent full", says nothing about urgency; labelled "page", the guided prompt's sensible "ticket" counted as a failure. Labelled "page or ticket", the difference disappeared. Look at failures before trusting a score.

def success_rate(agent, tasks, runs: int = 10) -> list[list[bool]]:
    """ok[task][run]: keep the whole matrix, not just the average."""
    return [[task.check(agent.run(task.prompt, seed=1000 + r)) for r in range(runs)] for task in tasks]

Confidence intervals

A rate measured on a sample is an estimate. A 95% confidence interval is a range built so that, over many repeated experiments, 95% of such ranges would contain the true rate. For a success rate, the Wilson interval behaves well even near 0% or 100%. With 300 runs per prompt, the minimal prompt scored 86.3% (82.0% to 89.8%) and the guided prompt 87.0% (82.7% to 90.3%). The intervals overlap almost entirely. With 30 runs the same rate would carry an interval about three times as wide.

import math

def wilson(k: int, n: int, z: float = 1.96) -> tuple[float, float]:
    p = k / n
    centre = (p + z * z / (2 * n)) / (1 + z * z / n)
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / (1 + z * z / n)
    return centre - half, centre + half

wilson(259, 300)   # (0.820, 0.898)

Runs of the same task are not independent: a task that fails once tends to fail every time. The Wilson interval over all runs treats them as independent, so it is narrower than it should be when tasks differ a lot. The honest unit of evidence is the task, which is what a paired comparison uses.

Paired comparisons

When comparing two versions, run both on the same tasks and compare task by task. Each task's difference cancels out how hard that task is, leaving only the effect of the change. Then estimate the average difference and its interval by bootstrapping: resample the 30 tasks with replacement thousands of times and see how the average moves. Here the paired difference was +0.7 points, with a 95% interval from −7.0 to +9.7. No evidence either way.

The per-task view also shows something no average can. The guided prompt was not neutral: it changed three tasks. It fixed the memory request completely (0 of 10 to 10 of 10), because it now said to refuse unsupported metrics. It broke the "API errors!!" request (8 of 10 to 1 of 10), because the model now kept the punctuation in the alert's name, and it lost the one lucky success on a garbled email address. A prompt change is rarely an improvement or a regression; it is usually a trade, and only a task-by-task comparison shows what was traded.

import random

def paired_bootstrap(a: list[list[bool]], b: list[list[bool]], n: int = 10_000):
    diffs = [sum(rb) / len(rb) - sum(ra) / len(ra) for ra, rb in zip(a, b)]   # one number per task
    means = sorted(sum(random.choices(diffs, k=len(diffs))) / len(diffs) for _ in range(n))
    return sum(diffs) / len(diffs), (means[int(.025 * n)], means[int(.975 * n)])

Seeds and temperature

A seed fixes the model's random draws, so the same request repeats exactly. That is useful for debugging and dangerous for measuring. Run three times with seed 42 at temperature 0.7, the minimal prompt gave the same result on 29 of 30 tasks and the guided prompt on 30 of 30: a fixed seed makes a sampled system look perfectly consistent, because you are measuring one sample three times. To measure variation, vary the seed (here 1000 + a different number per run and task). At temperature 0 both prompts scored 26 of 30, about the same as the average at 0.7, because on this task the variation lay almost entirely between tasks, not between runs. Measure at the temperature you will run in production, with different seeds, and report the temperature with the result.

Use case: τ-bench and pass^k

τ-bench (tau-bench), published by Sierra in June 2024, tests agents on customer-service tasks in simulated airline and retail domains, with tools, policies and a simulated user. Its authors noticed that a single success rate hid how unreliable agents were, so they ran each task several times and reported pass^k: the probability that an agent succeeds on a task in all of k independent attempts. In their results, models whose single-run success looked respectable fell sharply as k grew: an agent that a customer meets k times must get it right every time, and the leading model at the time succeeded on all eight attempts for only about a quarter of retail tasks. The idea follows directly from this chapter: keep the full matrix of tasks by runs, because the average throws away exactly the information about consistency that users experience. Chapter 29 measures pass^k for the agents in this course.

⚠️
Common mistakes
  • Judging a change on one or a few runs, often of the task that prompted the change.
  • Comparing versions on different tasks, so task difficulty swamps the effect.
  • Reporting a rate without an interval or without the number of tasks and runs.
  • Repeating runs with the same seed and calling the agreement "consistency".
  • Writing labels after seeing the outputs, or never re-reading labels that the failures question.
  • Looking only at the average, so a fix on one task and a regression on another cancel unseen.

Interview drill

Explain it simply: A colleague changed the agent's system prompt, tried five examples and says it is better. What would you want to see before shipping it?

How a strong answer sounds
A comparison on a fixed set of labelled tasks that represents real traffic, with both the old and new prompt run on the same tasks, several times each with different seeds at the production temperature. I would want the success rate of each with a confidence interval, the paired difference per task with its own interval, and a list of the tasks that changed in each direction, because a prompt change often fixes some tasks and breaks others. In a measured case, five examples would have shown whatever we happened to pick; on 30 tasks with ten runs each, the new prompt fixed one task, broke another, and the net difference was zero within plus or minus about eight points.

Deeper: Your evaluation runs every task once at temperature 0 and the score is stable from day to day. Is that enough?

How a strong answer sounds
It is a useful regression test, but it is not a measure of how the agent behaves for users if production samples at a higher temperature, or if the provider's outputs are not deterministic. At temperature 0 you see one path per task, so you learn nothing about the spread: a task that succeeds half the time can look like a solid pass or a solid fail depending on which path greedy decoding takes. I would add runs at the production temperature with different seeds, report pass rates and something like pass^k for consistency, and make sure the comparison between versions is paired by task. Stability from day to day only shows the evaluation is deterministic, not that the agent is reliable.

🧠 Key takeaways

  • Most variation is between tasks, so evidence comes from many tasks; repeated runs add the spread within each.
  • Report rates with intervals: 86.3% (82.0–89.8) and 87.0% (82.7–90.3) are not different.
  • Compare versions on the same tasks, task by task, and bootstrap the paired difference.
  • Read the tasks that changed: the "neutral" prompt fixed one task and broke another.
  • A fixed seed shows reproducibility, not consistency; vary seeds and measure at production temperature.
