Structured Output & Validation

Agents end their work by handing something to code: a ticket to file, a record to store, a decision another system acts on. That hand-off needs structured output, an object with the right fields and types, every time. There are four common ways to get it: ask for JSON in the prompt, switch on the server's JSON mode, constrain decoding to a schema, or validate the output and send the errors back for another try.

This chapter measures all four, plus one variation, with qwen3:14b. The task: turn 30 short incident reports, written with varied phrasing and time formats ("1:14pm", "47 minutes past 11 in the morning", "version 8.30.6"), into a seven-field record with types, formats and an enum, and a severity worked out by a rule. Each report was extracted twice at temperature 0.7: 60 records per method.

  • Know what each method guarantees: parsing, types, or neither
  • Use JSON mode and constrained decoding for what they are good at
  • Validate every structured output and retry with the errors
  • Separate what a schema can check from what it cannot
  • Move derived fields out of the model and into code

Free text vs JSON

The target was this schema: service (an enum of the ten services), version (pattern v1.2.3), started_at (24-hour HH:MM), customer_impact (boolean), error_rate_pct (number), severity (sev1, sev2 or sev3, by a rule given in the prompt) and actions (up to three short strings). Asked in the system prompt for "one JSON object with these fields: service, version, started_at, …", the model produced JSON that parsed 60 times in 60, and was valid 0 times. Every record had customer_impact as a sentence ("Shoppers reported failed payments") instead of true or false. The prompt named the fields; it never said their types. Everything else was mostly right: times converted from "1:14pm" to "13:14" every time, versions normalised to "v1.13.1" in 55 of 60.

JSON mode

JSON mode (Ollama's format="json") constrains the reply to be valid JSON. It was: 60 of 60 parsed, and also 0 of 60 valid, for the same reason. JSON mode guarantees syntax, not shape. Adding the full JSON Schema to the system prompt fixed the types (60 of 60 valid) but made something else worse: the severity rule. "sev1 if customers are affected and the error rate is above 10%" was misapplied in 16 of 60 records (eight at 12%, the rest at rates far above the threshold, 18.5% to 47%), against 4 without the long schema in the prompt, all at 12%. More text in the prompt is more for the model to weigh, and it weighed the rule less.

Constrained decoding

With schema-constrained decoding (Ollama's format=<schema>), the server only lets the model produce tokens that keep the output valid against the schema: customer_impact can only be true or false, service only one of the ten names, started_at only digits in the HH:MM shape. Every record was valid, and every field of every record was correct: 60 of 60, at 1.2 s per record, the fastest of all methods. The schema is passed as data, not as prose the model has to read.

from pydantic import BaseModel
class Incident(BaseModel):
    service: Literal["checkout", "payments", ...]
    version: Annotated[str, Field(pattern=r"^v\d+\.\d+\.\d+$")]
    started_at: Annotated[str, Field(pattern=r"^([01]\d|2[0-3]):[0-5]\d$")]
    customer_impact: bool
    error_rate_pct: Annotated[float, Field(ge=0, le=100)]
    actions: Annotated[list[str], Field(max_length=3)]

r = ollama.chat(model="qwen3:14b", messages=messages, format=Incident.model_json_schema(), options=OPTIONS)
incident = Incident.model_validate_json(r.message.content)      # still validate: the guarantee is the server's, the check is yours

Constrained decoding has limits. Not every server or provider supports every keyword (patterns and some formats are often unsupported), it guarantees shape not truth, and forcing a field the text does not support makes the model fill it with something. Use it where the schema is known in advance and every field should always be present.

Validate and retry

Where constrained decoding is unavailable, validate the output and, if it fails, send the validation errors back and ask again. Here every first attempt failed (the boolean problem), and every second attempt passed: 60 of 60 valid after 120 model calls, 2.4 s per record, twice the time of constrained decoding. The retry fixed what the validator could see, the types, and nothing else: severity was still wrong in 4 records.

for attempt in range(3):
    reply = ollama.chat(model="qwen3:14b", messages=messages, format="json", options=OPTIONS).message.content
    try:
        return Incident.model_validate_json(reply)
    except ValidationError as e:
        messages += [{"role": "assistant", "content": reply},
                     {"role": "user", "content": f"That output is invalid:\n{e}\nReply with the corrected JSON object only."}]
raise ExtractionFailed(messages)

Choosing a method

One field was never a schema problem: severity. It follows mechanically from two other fields (customer impact and error rate), and every method that asked the model to apply the rule got it wrong on some records with a 12% error rate. The schema can check that severity is one of three values; it cannot check that it is the right one. The robust fix is to stop asking: extract the facts (impact, rate) and compute derived fields in code, where a rule is applied the same way every time. Then choose by what you need: constrained decoding when it is available, validate-and-retry when it is not, and never free-text JSON for anything another program reads.

def severity(i: Incident) -> str:
    if not i.customer_impact:      return "sev3"
    return "sev1" if i.error_rate_pct > 10 else "sev2"    # the rule, applied by code, the same way every time

Use case: strict structured outputs

In August 2024 OpenAI added Structured Outputs to its API: with strict: true, responses and function arguments are generated under constraints derived from a supplied JSON Schema, and the company reported that its models matched complex schemas every time in its tests, against well under half for earlier models that were only instructed to. Open-source libraries such as Outlines and llama.cpp's grammar support had offered the same idea, compiling a schema or grammar into rules about which tokens may come next, and Ollama added schema-constrained output in December 2024. Every implementation documents a supported subset of JSON Schema and the same caveat this chapter measured: the guarantee covers the shape of the output, and the values inside it are still the model's judgement.

⚠️
Common mistakes
  • Naming fields in the prompt without their types; 60 of 60 records parsed and none was valid.
  • Treating JSON mode as schema validation.
  • Pasting a long schema into the prompt and losing accuracy on the rules around it.
  • Skipping validation because decoding was constrained.
  • Asking the model to apply a mechanical rule instead of computing it in code.
  • Retrying forever instead of failing explicitly after two or three attempts.

Interview drill

Explain it simply: What is the difference between JSON mode and schema-constrained output?

How a strong answer sounds
JSON mode only guarantees that the reply is valid JSON: any keys, any types. Schema-constrained output restricts generation, token by token, so the reply must match a given schema: the right keys, types, enums and patterns. In a measured extraction task JSON mode parsed every time and was valid none of the time, because a boolean field came back as a sentence; schema-constrained output was valid and fully correct every time. Even so I validate the result, because the guarantee covers shape, not whether the values are right.

Deeper: Your extraction pipeline always passes schema validation, but downstream teams say severity is sometimes wrong. What do you do?

How a strong answer sounds
Validation can only check that severity is one of the allowed values, not that it follows the rule. If severity is derived from other fields, such as customer impact and error rate, I would stop asking the model for it: extract the underlying facts, which the model gets right reliably, and compute severity in code. In a measured case the model misapplied "above 10% is sev1" to 12% in 4 to 16 of 60 records depending on the prompt, while it extracted impact and rate correctly in all of them. Then I would add records at the rule's boundaries to the evaluation set.

🧠 Key takeaways

  • Asking for JSON gave 60 parsed records and 0 valid ones: field names are not a schema.
  • JSON mode guarantees syntax only; a schema in the prompt fixed types but hurt a rule.
  • Schema-constrained decoding: 60 of 60 valid and correct, fastest of all.
  • Validate and retry reached 60 of 60 valid at twice the calls; it fixes what the validator sees.
  • Compute derived fields like severity in code; the model misapplied the rule in every unconstrained method.
