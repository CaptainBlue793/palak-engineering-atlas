Reflection & Self-Correction

An agent that has finished can be asked to look again: review its answer, check it against the evidence, and correct it if needed. This "reflection" is cheap to add and intuitively appealing, since people catch their own mistakes this way. Whether a model does depends on one thing above all: whether the second look brings new information, or only the same model reading the same transcript again.

This chapter measures three kinds of second look with qwen3:14b on 24 incident investigations, using the counts-only error tool that made choosing the right deploy hard in Chapter 4. The single attempt was wrong 5 times. Self-critique asked the model to review its own answer. An external check, in code, tested the answer against the tools and said what was wrong. Reflexion turned a failed check into a written lesson and started a fresh attempt with it.

  • Add a self-critique step and know what to expect from it
  • Build external checks that use tools or tests, not the model's opinion
  • Use Reflexion-style lessons across attempts, and see where they fall short
  • Spot reflection that changes right answers to wrong ones
  • Measure fixes and breaks, not just the final score

Self-critique

After its first answer the model was asked: "Review your answer against the tool results above. Is the root cause right, and is the deploy right? If anything is wrong or unchecked, investigate further and give a corrected final answer; otherwise repeat it." It reviewed 24 answers and changed none. The 19 right answers stayed right, which is good, and the 5 wrong ones stayed wrong. The mistake in each case was a deploy chosen from a list the model had already read, and reading the same list with the same reasoning led to the same choice. Self-critique costs a model call per task (7.7 steps against 6.7) and here bought nothing.

External checks

An external check tests the answer against something other than the model's judgement. Here it was a few lines of code using the same tools: does the named service's own error log point elsewhere ("503 from X")? Is the named version really one of that service's deploys? Is it the most recent deploy before the incident? When a check failed, its message went back to the model: "2.25.5 is not the most recent deploy of email before the incident; the most recent is v2.2.1 at 13:52." All 5 wrong answers were fixed, in one round each, and none of the 19 right ones was touched, since the check passed them: 24 of 24, at 7.5 steps.

def check(answer: str) -> str | None:
    svc, ver = parse_root(answer)                                       # "ROOT: email, v2.25.5"
    errs = get_errors(svc)
    if "503 from" in errs:
        return f"{svc}'s errors come from another service; continue from {upstream(errs)}"
    deploys = deploys_of(svc)
    if ver not in [d.version for d in deploys]:
        return f"{svc} has no deploy {ver} today"
    latest = max(deploys, key=lambda d: d.time)
    if latest.version != ver:
        return f"{ver} is not the most recent deploy of {svc} before the incident; the most recent is {latest.version} at {latest.time}"
    return None                                                          # passes: accept the answer

Be honest about what made the check so effective. In this simulated estate the bad deploy is always the most recent one, so "pick the most recent deploy" is always right. Real checks are rarely that sharp. A test suite, a schema, a query that confirms a record exists, a second data source: each catches some errors and misses others, and a wrong check can push a right answer to a wrong one. The principle holds though: the second look helps when it brings evidence the first look did not use.

Reflexion

Reflexion (Shinn and colleagues, 2023) keeps the external signal but changes what happens after a failure: the model writes a short lesson about what went wrong, and a fresh attempt starts with that lesson in its prompt. Here the lessons were good. After choosing v2.25.5 for email, the model wrote: "I should always check deploys in chronological order and ensure I select the most recent one before the incident occurred." The fresh attempt, reading the same deploy list, chose v2.25.5 again. Reflexion fixed 1 of the 5 errors in 9 retry rounds, at 10.4 steps per task. The lesson was general; the external check's message was specific (the version and the time). A model that misread a list once, perhaps taking the larger-looking version number (2.25.5) for the later one (2.2.1 at 13:52), was helped by being shown the answer to its specific mistake, not by being reminded to be careful.

When reflection hurts

A second look can also change a right answer to a wrong one, especially when the review is phrased so that changing something looks like the expected outcome, or when a check is wrong. None of the 72 reviewed answers here was broken, but count both directions whenever you add reflection: answers fixed, answers broken, and the cost in steps. The self-critique prompt above deliberately allowed "otherwise repeat it"; prompts like "find the mistake in your answer" invite the model to invent one.

Measuring the lift

A reflection step should be judged by its lift over the single attempt on the same tasks (P8), split into fixes and breaks, against its cost. Here that gives a clear ranking: an external check, +5 fixes, 0 breaks, +0.8 steps; Reflexion, +1, 0, +3.7 steps; self-critique, 0, 0, +1 step.

Use case: when self-correction works

Research on self-correction has converged on the pattern measured here. Reflexion (2023) reported large gains on coding tasks, where its feedback came from running unit tests, an external signal. "Large Language Models Cannot Self-Correct Reasoning Yet" (Huang and colleagues, 2023) found that without external feedback, asking models to review and correct their own reasoning did not improve accuracy and sometimes lowered it, because models changed correct answers. Coding agents built on this: they run the tests, the linter or the type checker after an edit and feed the failures back, which is self-correction with a check that brings new information.

⚠️
Common mistakes
  • Adding "review your answer" and expecting it to catch errors the same model just made.
  • Feedback that is general ("be careful with dates") when a specific one is available.
  • Prompts that imply something must be wrong, inviting the model to change right answers.
  • Trusting a check without measuring its errors; a wrong check breaks right answers.
  • Reporting only the final score, not fixes, breaks and extra cost.
  • Unlimited retry rounds after a failed check.

Interview drill

Explain it simply: Does asking an agent to check its own work make it more accurate?

How a strong answer sounds
Only if the check brings new information. Asking the same model to review the same transcript tends to repeat the same reasoning: measured on 24 investigations, self-critique fixed none of five wrong answers. A check that tests the answer against something external, such as tools, tests or data, and says specifically what is wrong, fixed all five with no right answer broken. So I build checks in code where I can, feed back specific failures, cap the rounds, and measure fixes and breaks separately.

Deeper: You add Reflexion-style lessons between attempts and the agent writes sensible lessons but repeats its mistakes. Why?

How a strong answer sounds
A lesson is a general rule, and the mistake was a specific misreading. In a measured case the model wrote "select the most recent deploy before the incident" and then, reading the same list, chose the same wrong version again, probably taking the larger-looking version number for the later one. Feeding back the specific failure ("the most recent is v2.2.1 at 13:52") fixed it in one round. I would keep lessons for patterns that recur across tasks, use specific feedback within a task, and change the input the model reads, for example by sorting deploys by time in the tool, so the mistake is harder to make.

🧠 Key takeaways

  • A second look helps only if it brings new information.
  • Self-critique reviewed 24 answers and changed none: 5 wrong stayed wrong.
  • A check in code with a specific message fixed all 5, broke none, for under one extra step.
  • Reflexion's general lessons fixed 1 in 9 rounds; specific feedback beats general advice.
  • Measure fixes, breaks and cost, and know your check's own error rate.
