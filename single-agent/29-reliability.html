Reliability: pass@k, pass^k & Variance

Throughout this course, results have been reported as "11 of 12" from a single run, with warnings that a one-task difference might be noise. This chapter measures the noise. The twelve incidents ran ten times each in three settings, 360 runs, with the same model, prompt, tools and tasks every time. It also introduces the two numbers that describe reliability. pass@k is the chance of at least one success in k tries. pass^k is the chance of succeeding every time in k tries.

The headline: at temperature 0 with a fixed seed, which most people assume is deterministic, the same twelve tasks scored anywhere from 9 to 11 across ten repeats, and some incidents took up to four different paths. For an agent that has to work every time, that difference is the whole story.

  • Measure run-to-run variance before comparing designs
  • Compute and interpret pass@k
  • Compute and interpret pass^k, the number that matters for production
  • Know where variance comes from, even at temperature 0
  • Make runs as repeatable as they can be

Run-to-run variance

Three settings, ten runs of all twelve incidents in each. At temperature 0, seed 1, the settings used throughout this course, the totals of the ten runs were 10, 11, 10, 10, 10, 10, 10, 9, 11, 11. At temperature 0 with a different seed per run: 11, 10, 10, 10, 10, 10, 10, 10, 8, 10. At temperature 0.7: 8, 10, 11, 10, 11, 11, 10, 8, 7, 8. So a single run of this suite can score anywhere in a range of two or three tasks even when nothing changed. Several chapters reported differences of one task between designs. Those were within this range, and the chapters said so. Differences of three or more, such as 4 of 12 against 11, are not.

The variance was not spread evenly. At temperature 0, seed 1, nine incidents passed all ten times, two failed nearly every time (2 and 1 of 10), and one passed 9 of 10. Most of the uncertainty about this agent lives in three incidents. That is typical: per-task results are usually stable-pass, stable-fail, or flaky, and the flaky ones are where the work is.

pass@k

pass@k is the probability that at least one of k attempts succeeds. It comes from code generation, where you can run k candidate programs and keep one that passes the tests. With n runs per task of which c succeeded, the unbiased estimate is 1 − C(n−c, k)/C(n, k), averaged over tasks. At temperature 0, seed 1: pass@1 = 0.85, pass@5 = 0.94. pass@k is the right number when you can check results and retry: a coding agent with tests, a search with a verifier (Chapter 22's routing), anything where a failed attempt is cheap and visible.

from math import comb

def pass_at_k(n: int, c: int, k: int) -> float:      # chance at least one of k tries succeeds
    return 1 - comb(n - c, k) / comb(n, k)

def pass_hat_k(n: int, c: int, k: int) -> float:     # chance all k tries succeed
    return comb(c, k) / comb(n, k)

# average each over tasks; n runs per task, c of them successful

pass^k

pass^k ("pass hat k") is the probability that all k attempts succeed: C(c, k)/C(n, k), averaged over tasks. It is the number for agents that act on their first answer, where a failure is not seen and retried but shipped. At temperature 0, seed 1: pass^1 = 0.85, pass^5 = 0.79, pass^10 = 0.75. At temperature 0.7: pass^5 = 0.53 and pass^10 = 0.42. The 0.7 agent looks only a little worse on pass@1 (0.78 against 0.85), but by pass^10 more than half its tasks have failed at least once. If your users run the same kind of task every day, pass^k is the experience they have.

Sources of variance

At temperature 0.7 the source is obvious: sampling picks different tokens. At temperature 0 it is less obvious. Greedy decoding should be deterministic, but in practice it was not. One documented cause is that GPU arithmetic is not bit-identical across different execution paths, and a tiny difference in one number can flip which token is most likely. After that the transcripts diverge, and a different tool call means a different trajectory. These runs shared the server with other experiments, so whether a prompt prefix was already cached depended on what had run just before, a likely source of such path differences. Changing the seed at temperature 0 made results vary more here (pass^10 fell from 0.75 to 0.58), which suggests that this server's decoding was not purely greedy at temperature 0. The environment adds its own variance in real systems too: data changes, services time out, results arrive in a different order.

Making runs repeatable

Fix what you can: temperature 0, a fixed seed, pinned model and server versions, a fixed context size and options sent explicitly (Chapter 21), and seeded, resettable environments (Chapter 28). Then measure what remains. Run each task several times, report pass^k next to pass@1, and compare designs on the same tasks with repeats, using a paired comparison (Primer 8). Record every run's trace, so that a flaky task's good and bad runs can be compared side by side. That comparison usually points straight at the step where they diverge. For production, make the agent robust rather than repeatable: checks that catch a bad run (Chapter 14) turn pass@k into reliability you can ship.

Use case: HumanEval's pass@k and τ-bench's pass^k

pass@k was popularised by OpenAI's Codex paper (Chen and colleagues, 2021), which introduced the HumanEval benchmark and the unbiased estimator used above. Generating many programs and keeping one that passes the tests made pass@100 far higher than pass@1, which suited code, where tests can pick the winner. τ-bench (Yao and colleagues, Sierra, 2024) argued that customer-facing agents need the opposite measure. A support agent gets one try per customer, so it introduced pass^k and showed that agents' scores fell sharply as k grew, even for the strongest models of the time. The two measures answer different questions: can it ever do this, and will it do it every time.

⚠️
Common mistakes
  • Reporting one run as the agent's score.
  • Assuming temperature 0 is deterministic: run totals still ranged from 9 to 11.
  • Comparing designs on one run each and trusting a one-task difference.
  • Quoting pass@k for an agent that cannot retry; its users experience pass^k.
  • Averaging away flaky tasks instead of investigating them.
  • Not pinning model, server and option versions between comparisons.

Interview drill

Explain it simply: What is the difference between pass@k and pass^k?

How a strong answer sounds
pass@k is the chance that at least one of k tries succeeds; it fits settings where you can check results and keep a good one, like code with tests. pass^k is the chance that all k tries succeed; it fits agents that act on their first answer, because users see every failure. On a measured suite, temperature 0 gave pass@5 of 0.94 but pass^5 of 0.79, and temperature 0.7 dropped pass^10 to 0.42 while pass@1 only moved from 0.85 to 0.78.

Deeper: Your agent scored 11 of 12 yesterday and 9 of 12 today with no changes. What is happening?

How a strong answer sounds
Probably nothing changed. That range is normal run-to-run variance. Measured with temperature 0 and a fixed seed, ten repeats of the same twelve tasks ranged from 9 to 11, because tiny numerical differences on the GPU can flip a token and send the run down a different path. I would run each task several times, report the mean and pass^k, compare changes with paired repeats, and look at the few flaky tasks where most of the variance lives, by diffing their passing and failing traces.

🧠 Key takeaways

  • At temperature 0 with a fixed seed, ten repeats of twelve tasks scored from 9 to 11.
  • Variance concentrated in a few flaky tasks; most passed or failed every time.
  • pass@5 was 0.94 while pass^5 was 0.79; temperature 0.7 took pass^10 to 0.42.
  • Use pass@k where results can be checked and retried, pass^k where they cannot.
  • Fix what you can, repeat runs, compare paired, and diff traces of flaky tasks.
