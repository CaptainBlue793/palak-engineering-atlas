Cost Control & Budgets

An agent's cost is not the price of one model call. It is that price times the number of steps, with each step re-sending a transcript that grows, plus every output token, plus the runs that go wrong. Agents are cheap per run and expensive in aggregate, and a few runs that do not stop can cost more than thousands that do.

This chapter measures where the tokens go in the incident agent, and what three kinds of limit do: a step limit only, a hard budget of 6,000 prompt tokens per run, and the same budget shown to the agent at every step. They ran on the twelve normal incidents and on twelve "broken" ones, where the deploy history always answers "temporarily unavailable. Try again." That task can be diagnosed but not finished, the classic source of runaway runs.

  • Compute cost per task, not per call
  • Know where an agent's tokens go
  • Set budgets from measured distributions
  • Use caching where it actually saves
  • Route easy work to cheaper options

Cost per task

A normal incident took 8 model steps on average and consumed about 5,240 prompt tokens and 244 output tokens. Prompt tokens dominate because every step re-sends the system prompt, the tools and the whole transcript so far. At an illustrative price of $3 per million input tokens and $15 per million output tokens (round numbers, not a quote), that is about 1.6 cents of input and 0.4 cents of output, 2 cents per incident. Small, until it is multiplied. A thousand incidents a day is $20. The changes measured elsewhere in this course move that number more than any price difference does. Thinking added about 1,900 output tokens per incident (Chapter 22). Sixty unused MCP tools raised prompt tokens per run from about 5,300 to 32,000 (Chapter 20). Raw HTML pages cost three times an outline (Chapter 34).

Runaway runs

The broken incidents could not be finished: the deploy history never answered. A runaway agent would retry forever. This one did not. With only the 30-step limit, every broken run ended by itself in about 10 steps, retrying the deploy history about three times and then answering with what it had: the root service named in 8 of 12, the version "unknown". Broken runs cost about 6,960 prompt tokens, a third more than normal ones, and the largest single run used 10,532. This matches Chapter 7, where no run came near the step limit. qwen3:14b with these tools gives up rather than loops. Other models, tasks or tool errors behave differently, and one runaway at hundreds of steps would cost as much as a hundred normal runs, so limits are insurance even when you have not yet seen the failure.

Budgets

A hard token budget of 6,000 prompt tokens per run (checked before each step, then one final call asking for a report) stopped 7 of 12 broken runs. Each stopped run still ended with a useful report of what was found and what remained unknown, and 10 of 12 named the root service. But it also stopped 3 of 12 normal runs, and one of them would have succeeded: 11 of 12 instead of 12. Total tokens on the broken set fell by about 5%. The budget was set below the normal runs' largest (8,743 tokens), so it cut good runs as well as bad ones, and saved little because nothing was running away.

Showing the budget to the agent at every step ("Budget: 3,412 prompt tokens left of 6,000. If you cannot finish within it, stop and report what you found so far") changed its behaviour. It economised, checking deploys 16 times across the normal set instead of 28, and used the fewest tokens. It also solved only 8 of 12 normal incidents, stopping early with plausible but unchecked answers. On the broken set it named the root service in all 12. A visible budget makes the model trade accuracy for thrift, and you do not get to choose the rate.

def over_budget(used: int, limits: dict) -> bool:
    """Insurance against runaways, set above the measured tail of normal runs."""
    return used > limits["p99_normal_tokens"] * 1.5       # here: about 13,000, not 6,000

# on stop: one final call without tools - "Report what you found and what is still unknown." - then escalate

Set budgets from data: record tokens per run for normal tasks, set the hard limit well above their tail, and keep it hidden from the model. When it trips, ask for a final report and alert a person, because a run that hits the budget is a run that needs looking at.

Caching

Three caches save real money in agents. Prompt caching reuses the processed prefix of a prompt that has not changed. In Primer 4 a 4,829-token prompt took 1,579 ms to process the first time and 14 ms when repeated, but 1,383 ms after a one-word change near the start. Put stable content (system prompt, tool schemas) first and changing content last. Hosted APIs bill cached input tokens at a discount. Tool-result caching answers repeated identical calls without running them again: the agents in Chapter 27 repeated calls 1 to 5 times per twelve runs, and after a crash a result store saved 90 of 90 repeated calls (Chapter 32). Answer caching returns a stored answer for a repeated question. It is safe only for questions whose answer cannot change, which for agents that look at live systems is rare.

Cheaper models for easy steps

Not every step needs the strongest option. In Chapter 22 routing every incident through the fast mode first, and escalating only the answers an evidence check rejected, solved 11 of 12 at 7.6 seconds per incident against 26.7 for the slow mode everywhere. The same idea saves money across models: a small model for routine steps (formatting, extraction, classification of tool output), the large one for decisions, and escalation on a failed check. Measure cost per successful task: an option that is half the price and fails twice as often costs the same.

Use case: prompt caching and spend limits in hosted APIs

Hosted model providers built cost controls around the patterns in this chapter. Anthropic introduced prompt caching for the Claude API in 2024: developers mark a stable prefix (system prompt, tool definitions, long documents), and later requests that reuse it are billed at a fraction of the normal input price and processed faster. OpenAI applies a similar discount automatically to repeated prompt prefixes. Both encourage the ordering recommended above, stable content first. Providers also offer organisation-level spend limits and usage alerts. Agent products add their own per-task limits: coding agents expose maximum turns or budget settings for unattended runs, so a run that does not converge stops instead of spending without bound.

⚠️
Common mistakes
  • Pricing per call instead of per completed task.
  • Budgets below the normal tail, which stop good runs.
  • Showing the budget to the model, trading accuracy for thrift: 8 of 12 here.
  • Changing text at the start of the prompt every step, defeating prompt caching.
  • Connecting every tool to every request.
  • A budget that just stops, without a final report or an alert.

Interview drill

Explain it simply: How would you control the cost of an agent in production?

How a strong answer sounds
Measure cost per completed task first: prompt tokens dominate because every step re-sends the transcript. Then shrink what each step sends: fewer tools, condensed tool results, stable prefixes for prompt caching. Route routine work to cheaper options with escalation on a failed check. Finally set a hard, hidden budget above the measured tail of normal runs as insurance, with a final report and an alert when it trips. In a measurement, a budget set too tight stopped 3 of 12 normal runs and cost one success.

Deeper: Should the agent know its budget?

How a strong answer sounds
Usually not. Measured, showing a 6,000-token budget at every step made the agent cut corners: fewer deploy checks (16 against 28) and 8 of 12 normal incidents solved instead of 12, while saving about 15% of tokens. A hidden limit plus a final "report what you found" call gets the protection without changing behaviour on normal runs. The exception is tasks where partial results are acceptable and the user wants speed over completeness. Then I would say so explicitly and measure the trade.

🧠 Key takeaways

  • A normal incident cost about 5,240 prompt and 244 output tokens: roughly 2 cents at illustrative prices.
  • Runs that could not finish ended by themselves in about 10 steps; budgets are insurance, not savings.
  • A budget below the normal tail stopped 3 good runs and cost one success.
  • A budget shown to the agent cut normal successes from 12 to 8.
  • Most savings come from what each step sends: tools, results, stable prefixes and routing.
