Debugging a Failing Agent

One task has followed this course from the start. In the twelve-incident suite, incident 5 failed in almost every chapter, under every prompt, tool design and framework, while its neighbours passed. This chapter debugs it the way any agent failure should be debugged: start from the trace, sort out what kind of failure it is, form a hypothesis, test the cheapest fixes against the failing case and a regression suite, and turn the case into a test.

Two candidate fixes were tested with qwen3:14b on five seeds of the failing incident and once on all twelve incidents. One changed the environment; one changed the prompt. The results were 5 of 5 and 0 of 5.

  • Read a trace to find where a run went wrong
  • Tell wrong-tool, wrong-argument, lost-context and environment failures apart
  • Test a fix on several seeds, not one run
  • Check every fix against a regression suite
  • Keep the failure as a permanent test

Start from the trace

Not from the prompt, and not from a theory about the model. The trace of a failing run shows every call, every result and the answer. Here it showed a clean investigation. The agent read checkout's errors ("243 × 503 from inventory"), moved to inventory, read its errors ("384 × protocol error: unexpected message type") and its deploys, and chose between the two deploys it found:

inventory deploys today:
  07:19 v5.20.5: new retry policy
  13:52 v5.9.1: upgraded driver

It chose v5.20.5: "This change might have caused a protocol mismatch with upstream services." The culprit was v5.9.1. The right service, the right tools, the right order; the wrong choice at the last step.

Wrong tool or wrong arguments

Sort the failure before fixing it. Wrong tool or wrong arguments: the trace shows a call that could not have worked, such as a misspelt service or a missing parameter (Chapter 4). Lost context: something the agent knew earlier is gone or overridden (Chapter 10). Environment problems: a tool returned an error, an empty result or misleading data. Reasoning with missing evidence: the calls were right, but the results did not contain what was needed to decide. This was the last kind. The method in the system prompt said to pick "the deploy whose time is just before the errors began", but no tool ever said when the errors began. The model had two deploys and no timing evidence, so it matched on meaning, and "retry policy" sounded more like a protocol problem than "upgraded driver".

Lost context

It is worth ruling out the other kinds explicitly. The prompt was about 1,000 tokens at its largest, far below the context window, so nothing was truncated. The method was present on every step. The agent did not loop; at worst it read inventory's errors a second time before deciding. Ruling out causes is part of the method. Each one you exclude narrows what the fix needs to do.

Environment problems

The hypothesis, "the agent lacks the evidence its method requires", suggests two fixes. Fix A changes the environment: error logs say when errors were first seen (inventory errors, last hour (first seen 13:54)), as a real log system would. Fix B changes the prompt: "If several deploys could explain the error, prefer the most recent deploy before the errors began." Each was tested on the failing incident with five seeds, because one passing run proves little (Chapter 29), and once on the full suite of twelve, to catch regressions.

The baseline passed incident 5 in 1 of 5 seeds and the suite 10 of 12. Fix A passed incident 5 in 5 of 5 and the suite 12 of 12; it also fixed incident 9, which had failed for the same reason. Fix B passed incident 5 in 0 of 5 and the suite 10 of 12. Worse, it changed how the agent explained its wrong choice. With the prompt rule in place, the agent described the 07:19 deploy as "the most recent one before the errors began", a timing claim it had no way to know. A prompt that demands evidence the tools do not provide produces confident justifications instead of better decisions.

Fix and add a test

The fix belongs where the cause was: in the tool output. Then the failure becomes a permanent test, the incident's seed, the check, and the expected answer, in the regression suite that runs on every change (Chapter 28). If a later change to tools, prompts or models brings the failure back, the suite says so the same day.

def test_incident_5_picks_the_deploy_before_errors():
    """Regression: v5.20.5 (retry policy) sounds related; v5.9.1 at 13:52 is the cause. Needs first-seen times."""
    w = incidents(12)[4]
    passes = sum(grade_root(w, run_agent(TASK, tools_with_first_seen(w), SYSTEM, options={"seed": s}).answer)
                 for s in range(1, 6))
    assert passes >= 4, f"incident 5 passed {passes} of 5 seeds"

Use case: error analysis in practice

Teams that run agents in production describe the same loop under different names. Practitioners' guides to evaluating LLM applications recommend reading many traces by hand, labelling each failure with a short description, grouping the labels into categories, and fixing the largest category first, before writing any automated metric. Anthropic's engineering write-up on building its multi-agent research system (2025) describes debugging agents by tracing their decisions and watching them work step by step in simulations, where they found failures such as agents continuing after they already had enough results, or choosing poor search queries, which the team then fixed in prompts and tools. The common thread is the one this chapter measured: look at what the agent saw before deciding what to change.

⚠️
Common mistakes
  • Editing the prompt before reading a trace.
  • Testing a fix on one run; the baseline passed this incident once in five seeds.
  • No regression suite, so a fix that breaks other tasks goes unnoticed.
  • Prompt rules that demand evidence the tools do not provide.
  • Trusting the agent's explanation: fix B made it invent timing it never saw.
  • Fixing the failure and not keeping it as a test.

Interview drill

Explain it simply: How do you debug an agent that fails on some tasks?

How a strong answer sounds
Start from the traces of failing runs and classify each failure: wrong tool, wrong arguments, lost context, environment problem, or missing evidence. Form a hypothesis for the biggest group and test the cheapest fixes on several seeds of the failing task plus a regression suite, then keep the task as a test. In a measured case, the agent chose between two deploys with no timing information. Adding when errors began to the logs took it from 1 of 5 seeds to 5 of 5 and the suite to 12 of 12; a prompt rule scored 0 of 5.

Deeper: Why did the prompt fix fail, and what does it teach?

How a strong answer sounds
The prompt told the agent to prefer the deploy just before the errors began, but no tool said when errors began. The model could not follow the rule, so it rationalised its existing choice, claiming the 07:19 deploy was the most recent before the errors began. The lesson is to fix failures where the cause is. When the cause is missing evidence, change the tools or the environment, and treat the agent's explanations as claims to verify, not as diagnoses.

🧠 Key takeaways

  • The trace showed the right investigation and a wrong final choice made without timing evidence.
  • Classify failures before fixing: tool, arguments, context, environment, or missing evidence.
  • Logs with first-seen times: 5 of 5 seeds and 12 of 12 in the suite.
  • A prompt rule demanding that evidence: 0 of 5, plus confident invented justifications.
  • Test fixes on several seeds and a regression suite, then keep the failure as a test.
