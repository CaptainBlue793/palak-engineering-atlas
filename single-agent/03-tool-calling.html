Tool Calling

A tool call is the model's way of saying "run this function with these arguments". The model only writes the request; your code decides whether to run it. How that request travels has changed. Early agents asked the model to write it as text in an agreed format and parsed it with regular expressions. Model servers now offer native tool calling, where you pass tool definitions with the request and get the calls back as structured data. A third option sits between them: ask for one JSON object and let the server's JSON mode guarantee it parses.

This chapter explains each, then measures all three with qwen3:14b on 40 labelled requests over an eight-tool operations toolbox: 32 requests that need a specific tool with specific arguments, and 8 that need no tool at all. Each ran once at temperature 0 and five more times at 0.7.

  • Write a tool definition and say what the model actually receives
  • Compare native, text-protocol and JSON-mode tool calls
  • Check arguments, not just which tool was chosen
  • Handle replies that cannot be parsed and calls that should not have been made
  • Measure call accuracy on a labelled set and read the failures

Tool definitions

A tool definition has three parts: a name, a description of what it does and when to use it, and a JSON Schema for its arguments. Passed in the tools parameter, the definitions are rendered into the system turn by the chat template (P2), so the model reads them as text on every request. The eight definitions here cost 547 prompt tokens per request in native mode, against about 290 when the same tools were described in a compact line each in the system prompt. Native mode sends the full schemas, word for word.

scale_service = {
    "type": "function",
    "function": {
        "name": "scale_service",
        "description": "Set the number of replicas of a service.",
        "parameters": {"type": "object", "required": ["service", "replicas"], "properties": {
            "service":  {"type": "string", "description": "Service name"},
            "replicas": {"type": "integer", "description": "Replica count, 1-50"}}},
    },
}
r = ollama.chat(model="qwen3:14b", messages=messages, tools=TOOLS, think=False, options=OPTIONS)
for call in r.message.tool_calls or []:
    print(call.function.name, call.function.arguments)    # scale_service {'service': 'inventory', 'replicas': 12}

Native vs text-based calls

With native calls the model writes its request in the format it was trained on (for qwen3, a JSON object inside <tool_call> tags), the server parses it, and you receive tool_calls as data. With a text protocol you describe the tools and a format in the system prompt, for example two lines, Action: scale_service and Action Input: {...}, and parse the reply yourself. With JSON mode you ask for one JSON object with fields for the tool, the arguments and an answer, and the server constrains generation so the reply always parses.

# text protocol: you own the format, so you own the parser
m = re.search(r"Action:\s*([\w_]+)\s*\n\s*Action Input:\s*(\{.*\})", reply, re.S)
if m:     name, args = m.group(1), json.loads(m.group(2))
elif re.search(r"^\s*Answer:", reply, re.M):     name = None
else:     raise ParseError("no Action or Answer line")

# JSON mode: the server guarantees valid JSON, not valid content
r = ollama.chat(model="qwen3:14b", messages=messages, format="json", think=False, options=OPTIONS)
d = json.loads(r.message.content)    # {"tool": "scale_service", "arguments": {...}, "answer": null}

Measured over 200 runs each at temperature 0.7: native calls were correct 190 times, the text protocol 174 and JSON mode 195. The text protocol's 16 parse failures were all conversational requests ("Thanks, that's all for now") where the model simply replied without the Answer: prefix: a format the model was not trained on drifts on exactly the requests that are furthest from tools. JSON mode never failed to parse. Native mode's only failures were two requests it answered without a tool, which every mode found hard.

Arguments and types

Choosing the right tool is half a call. The arguments must be right too: the service name spelt as the system knows it, "twenty replicas" as the integer 20, "low-priority" as the enum value p3, "double the replicas of payments from 4" as 8. In this set the model got every argument right whenever it chose the right tool, in all three modes, including the arithmetic. That reflects simple, well-described arguments; P3 showed what happens without enums, and Chapter 4 measures descriptions that are less clear. Grade arguments explicitly anyway: a call to the right tool for the wrong service is worse than no call, because it does something.

Malformed calls

Three kinds of bad call reach your code, and each needs its own handling. A reply that does not parse (text protocol only, here): send the parse error back and ask for the format again, or treat it as an answer if it is plainly conversational. A call that should not have been made: JSON mode, asked whether 0.2% is an acceptable error rate for checkout, fetched checkout's live metrics instead of answering the general question, five times out of five. And the most dangerous, a call that should have been made but was described instead: asked to open a low-priority ticket, the text protocol replied "Answer: A low-priority ticket has been opened", five times out of five, without calling create_ticket. Nothing was opened. In native mode the same request produced the call every time. A claimed action with no matching tool call is a check worth automating: if the reply says "opened", "restarted" or "scaled" and no such call happened, do not pass it to the user as fact.

Measuring call accuracy

Call accuracy is measured like any agent behaviour (P8): a labelled set of requests, each with the expected tool (or none) and the arguments that must match, run several times. The labels here are deliberately coarse: an exact match on the service, replica count or priority, and no constraint on free-text titles and search queries. Keep the full table of request × run, because the totals hide the pattern: almost every failure was the same request failing five times out of five. "Is inventory healthy?" failed in native and text modes every time, because nothing told the model that inventory is a service: it asked what "inventory" meant. That is a fix in the tool descriptions, not in the model.

Use case: function calling arrives in the APIs

OpenAI added function calling to its Chat Completions API in June 2023: developers passed function definitions as JSON Schema, and models fine-tuned for the purpose returned a structured function_call instead of text. Later that year it became tool_calls, which allowed several calls in one reply. Anthropic's tool use for Claude became generally available in May 2024 with tool_use and tool_result content blocks, and open models followed with tool-calling formats in their chat templates (Llama 3.1, Qwen 2.5 and later), which servers such as Ollama parse into the same structured form. The shift moved the fragile part, parsing free text, out of every application and into the model and server, where training could make it reliable. The text-protocol results here show what that saved: format drift on conversational turns and an action claimed in prose.

⚠️
Common mistakes
  • Writing your own text protocol when native tool calling is available.
  • Grading only the tool name and not the arguments.
  • Trusting a reply that says an action was done when no tool call was made.
  • Tool descriptions that never say which values are valid ("inventory" is a service).
  • Treating JSON mode as correctness: it guarantees parsing, not the right decision.
  • Reading only the total instead of which requests fail, and how consistently.

Interview drill

Explain it simply: What happens, end to end, when a model "calls a function"?

How a strong answer sounds
The application sends the conversation along with tool definitions: names, descriptions and JSON Schemas for the arguments. The server renders those into the prompt, and the model, trained for it, writes a call in a structured format instead of a normal reply. The server parses that into a list of tool calls with names and argument objects. The model has not run anything: the application validates the arguments, decides whether to run the function, runs it, and sends the result back as a tool message so the model can continue. Every effect on the world goes through the application's code, which is where the safety checks belong.

Deeper: Users report that your agent told them it had opened a ticket, but no ticket exists. How could that happen and what would you change?

How a strong answer sounds
The model wrote that it had done the action instead of calling the tool. In a measured comparison, a text-based tool protocol did exactly that five times out of five on a ticket request, while native tool calling made the real call every time. I would move to native tool calling if we are not on it, check the tool description makes clear the tool is how tickets get opened, and add a guard that compares claims in the final answer with the tool calls actually made in the run: an answer saying "opened", "restarted" or "deleted" without a matching successful call is rewritten or flagged. Then I would add this request to the evaluation set so it cannot come back unnoticed.

🧠 Key takeaways

  • The model writes the call; your code parses, validates and runs it.
  • Native calls: 190 of 200 correct, no parsing to maintain; the text protocol 174, with 16 parse failures.
  • JSON mode guarantees a parse (195 of 200) but not the right decision.
  • Check claimed actions against real calls: the text protocol "opened" a ticket it never created, five times in five.
  • Failures were per request, not random: fix descriptions and grade arguments, request by request.
