Chat Messages, Roles & Turns

A model remembers nothing between requests. Everything an agent knows about its task, the tools it called and what they returned lives in one list of messages that your code sends again on every step. That list, the transcript, is the agent's whole state. Getting its shape right is most of what "talking to a model" means in agent code.

This chapter looks at the four roles, how a transcript grows, how tool calls and results are recorded, and what the server's chat template turns it all into. With qwen3:14b it measures three things: what tool definitions cost on every request, which badly shaped transcripts the model survives, and the one mistake it cannot survive: two tool results that come back in a different order.

  • Use system, user, assistant and tool messages for what each is for
  • Grow a transcript correctly across turns and tool calls
  • Read a chat template and see what the model really receives
  • Estimate the token cost of the tools you send on every step
  • Return tool results the model cannot misattribute

Roles

Every message has a role. The system message holds standing instructions: who the agent is, the rules it follows, how to use its tools. User messages carry the task and any follow-ups. Assistant messages are the model's own replies, either text or requests to call tools. Tool messages carry a tool's result back. The model sees all of them, every time, as one long sequence of tokens; nothing persists on the server between calls.

That statelessness is easy to forget in a chat UI. Measured below: asked "And what was the value?" with no earlier messages, qwen3:14b replied 20 times out of 20 that it needed to know which metric and host were meant. The model was not confused. It had simply never seen the earlier turns, because they were not sent.

Multi-turn transcripts

An agent loop appends to the transcript as it goes: the task, the model's reply, the tool results, the next reply. The rule is to append the assistant's reply exactly as it came back, tool calls included, and to append one tool message per call. The next request is the whole list.

messages = [
    {"role": "system", "content": "You are an on-call assistant. Check metrics with the tools before answering."},
    {"role": "user", "content": "How full is the disk on db-03?"},
]
reply = ollama.chat(model="qwen3:14b", messages=messages, tools=[get_metric], think=False, options=OPTIONS).message
messages.append(reply)                                    # content "" and one tool call
for call in reply.tool_calls:
    result = TOOLS[call.function.name](**call.function.arguments)
    messages.append({"role": "tool", "tool_name": call.function.name, "content": result})
reply = ollama.chat(model="qwen3:14b", messages=messages, tools=[get_metric], think=False, options=OPTIONS).message
# "The disk on db-03 is 61% full."

Tool messages

A tool call is a pair: the assistant message that asks for it, and a tool message with the result. The model was forgiving about how that pair was recorded when there was one call. With the result sent as ordinary user text, with the assistant's call missing, or with the call hidden behind text, it still answered all 20 questions with the right value. Two shapes did break it. With the call recorded and no result, the reply was empty in 20 of 20 cases: the transcript ended on the assistant's own turn, so the server treated the request as a continuation of that turn, and the model added nothing. A loop that treats "no tool calls" as "finished" would return an empty answer.

The serious failure was with two calls at once. The agent asked for the disk usage of two hosts; the tools ran concurrently and, as concurrent work does, finished in the other order. Returned as bare values ("88%", "35%") in completion order, every one of 20 answers attributed each value to the wrong host and named the wrong host as fuller. The reason is in the template: Ollama's template for qwen3 does not include tool_name at all, so results are matched to calls only by position. Returned with the host in the text ("disk_used_pct on web-11: 35%"), in the same swapped order, all 20 were right. Make every tool result say what it is a result of.

Chat templates

The model never sees your list of dictionaries. The server renders it into one string with the model's chat template and tokenises that. For qwen3 the template puts the tool definitions into the system turn inside <tools> tags, writes the model's calls inside <tool_call> tags, and sends each tool result back as a user turn wrapped in <tool_response>. Turning thinking off appends /no_think to the last real user message and pre-fills an empty <think> block. This is the transcript above, as the model received it:

<|im_start|>system
# Tools
You may call one or more functions to assist with the user query.
You are provided with function signatures within <tools></tools> XML tags:
<tools>
{"type": "function", "function": {"name": "get_metric", "description": "Current value of a metric on a host.", "parameters": {...}}}
</tools>
For each function call, return a json object with function name and arguments within <tool_call></tool_call> XML tags: ...
<|im_end|>
<|im_start|>user
How full is the disk on db-03? /no_think<|im_end|>
<|im_start|>assistant
<tool_call>
{"name": "get_metric", "arguments": {"host": "db-03", "metric": "disk_used_pct"}}
</tool_call><|im_end|>
<|im_start|>user
<tool_response>
disk_used_pct on db-03: 61%
</tool_response><|im_end|>
<|im_start|>assistant
<think>

</think>

Three things follow from reading it. Tool definitions are ordinary prompt text, so they are paid for in tokens on every request. A tool result is just text in a user turn, which is why text inside it can try to give the model instructions (Chapter 25). And an assistant message with both text and tool calls renders only the text in this template: the calls vanish from the history the model sees on later steps. Run ollama show <model> --template once for any model you use.

Running a local model

Ollama serves the model behind /api/chat, applies the template and returns the reply with timing and token counts. Two numbers in that response are worth logging on every agent step: prompt_eval_count (tokens the model read) and eval_count (tokens it wrote). The first one grows in two ways. The transcript gets longer every step (Chapter 10), and the tool definitions are sent every step. Measured with one short question: 22 prompt tokens with no tools, 222 with one tool, 1,268 with ten and 5,954 with fifty, about 118 tokens per tool of this size. Fifty tools added a second of prompt reading to every call, before the model wrote a word.

r = ollama.chat(model="qwen3:14b", messages=messages, tools=tools, think=False, options=OPTIONS)
print(r.prompt_eval_count, r.eval_count, r.prompt_eval_duration / 1e6)   # 5954 1 1084.0 with 50 tools

Use case: tool-call IDs in the OpenAI and Anthropic APIs

Hosted APIs solve the pairing problem with IDs rather than order. In OpenAI's Chat Completions API every tool call the model makes carries an id, and each tool message you send back must name it in tool_call_id; a request whose assistant message has a tool call without a matching tool message is rejected with an error rather than sent to the model. Anthropic's Messages API does the same with tool_use blocks that have an id and tool_result blocks that cite it as tool_use_id, all returned together in the next user message. Both designs make the mistake measured here, a result attached to the wrong call, impossible to make silently. With a local model and a template that drops the name, the label inside the result text is the only safeguard you have.

⚠️
Common mistakes
  • Returning bare values from tools ("35%") so results can be attributed to the wrong call.
  • Dropping the assistant's tool-call message or rewriting it before appending it.
  • Forgetting to append a result for every call, so the next reply is empty or confused.
  • Sending every available tool on every step without counting what they cost in tokens and latency.
  • Never reading the chat template, so surprises such as dropped names or hidden calls go unnoticed.
  • Assuming the server remembers the conversation; it remembers nothing you do not send.

Interview drill

Explain it simply: What is in the messages list on the fifth step of an agent run, and why does it all have to be sent again?

How a strong answer sounds
The system prompt with the agent's rules, the user's task, then every step so far: each assistant reply exactly as the model produced it, including its tool calls, and one tool message with the result for each call. The model is stateless: the server keeps nothing between requests, so the transcript is the agent's entire memory of what it has done and seen. That is also why each step costs more than the last: the tool definitions and the whole history are read again every time, which is what context management later in the course is about.

Deeper: An agent compares metrics from several hosts using parallel tool calls and sometimes reports the right numbers against the wrong hosts. What is going on and how do you fix it?

How a strong answer sounds
The results are probably being matched to calls by position. Parallel calls finish in any order, and if the code appends results as they complete, the order no longer matches the calls. If the chat template also ignores the tool name or call ID, as Ollama's template for qwen3 does, the model has only the order to go on. Measured, unlabelled results in completion order were misattributed in 20 of 20 comparisons. I would append results in the order of the calls, use call IDs where the API supports them, and above all make each result self-describing, naming the host and metric, which fixed all 20 even with the order swapped. Then I would add a regression test with deliberately reordered results.

🧠 Key takeaways

  • The transcript is the agent's whole state; the model remembers nothing you do not send.
  • Append the assistant's reply as it came back, then one tool message per call.
  • The chat template decides what the model sees: tool results become user text, and qwen3's drops the tool name.
  • Tool definitions are prompt text: about 118 tokens each here, on every step.
  • Make every tool result name what it is a result of; unlabelled parallel results went 0 of 20.
