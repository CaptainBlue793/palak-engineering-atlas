Latency & Parallel Tool Calls

An agent's response time is the sum of its steps, and each step has three parts. The model processes the prompt, the model generates its reply, and the tools run. Which part dominates decides what to optimise. Guess wrong and you speed up the part that did not matter.

This chapter measures the three parts with qwen3:14b on three fan-out tasks: the metrics of all ten services, the errors of every service checkout calls, and the deploys of four named services. Every tool took half a second, like a slow internal API. Each task ran with tool calls executed one after another and concurrently, with and without a hint asking for parallel calls, and once more with the prompt cache deliberately defeated.

  • Break an agent run into a latency budget
  • Use parallel tool calls and execute them concurrently
  • Know when streaming helps and when it does not
  • Keep the prompt cache working
  • Prefer fewer, bigger steps

A latency budget

On the all-services task with concurrent tools, the run took 6.7 seconds in three model steps. Processing prompts took 0.17 s in total, because the server reused the cached prefix of each prompt. Generating replies took 5.5 s. Tools took 1.0 s. Generation was over 80% of the run, at about 12 ms per output token on this GPU. The model wrote 201 tokens in the step that requested ten tool calls and 227 in the final answer. So the first thing to cut is output tokens: compact tool arguments, a final answer of the length the user needs, and no thinking unless it pays (Chapter 22). With long prompts and a cold cache the balance shifts. In Primer 4 a 4,829-token prompt took 1.6 seconds to process the first time.

Parallel tool calls

qwen3:14b put independent calls in one reply without being asked. All ten get_metrics calls came in a single step, the three dependency checks in one, the four deploy lists in one. The hint "request them all at once" changed nothing, because there was nothing left to change. What mattered was what the loop did with them. Executed one after another, ten half-second calls took 5.5 s and the run 11.6 s. Executed concurrently they took 1.0 s, and the run 6.7 s, a 42% cut from one change in the harness. The four-deploys task went from 4.9 to 3.3 s, and the dependencies task from 3.7 to 2.7 s.

from concurrent.futures import ThreadPoolExecutor

def run_calls(calls, tools):
    """Independent calls from one model reply run at the same time; results keep the reply's order."""
    with ThreadPoolExecutor(max_workers=16) as pool:
        return list(pool.map(lambda c: tools[c.name](**c.arguments), calls))

Run calls concurrently only when they are independent and safe to overlap: reads, generally yes; writes to the same resource, no. Keep the results in the order the model asked for them, and cap concurrency so a reply asking for fifty calls does not overload the service behind the tools (Primer 5).

Streaming

Streaming sends the reply token by token as it is generated. It does not make the run finish sooner, but it changes what the user waits for. The final answer here took 2.9 s to generate; streamed, its first words would appear after about a tenth of a second. For agents, stream the final answer and show progress during tool steps ("checking 10 services…"). Streaming the tool-call steps themselves helps nobody, since a half-written tool call cannot be run.

Prompt caching

Each step re-sends the whole conversation, and a server that caches the processed prefix only has to process what is new. One version of the all-services run put the current time on the first line of the system prompt, a common pattern, so the prefix changed at every step. Prompt processing went from 22, 27 and 120 ms per step to 101, 118 and 234 ms, from 0.17 s to 0.45 s in total, with the same prompts otherwise. On prompts of a few hundred tokens that is a small cost. On long prompts with many tools or documents it is the difference between milliseconds and seconds per step, and on hosted APIs it also changes the bill (Chapter 31). Put stable content first (system prompt, tool schemas) and anything that changes, such as the time, the user or the retrieved documents, at the end.

Fewer, bigger steps

Every model step pays for prompt processing and generation, so the number of steps is a direct latency multiplier. The all-services task took 3 model steps because the calls were batched. Called one at a time it would have needed 11, with eleven rounds of generation. Encourage batching with tools that accept several items (get_metrics(services=[...])), make tools return everything the next decision needs so the model does not have to come back, and merge small steps into one where the order does not matter. The opposite move, splitting work into more agents or more rounds, multiplies latency and is worth it only when it buys accuracy (Chapter 13).

Use case: parallel function calling in model APIs

Model APIs added parallel tool calls in 2023 and 2024: a single reply can request several functions at once, each with its own call id. OpenAI introduced parallel function calling in late 2023, and Anthropic's and Google's APIs support several tool calls in one reply. The API only returns the requests. Running them concurrently is the application's job, and many early agent loops executed them one by one and lost the benefit, as the sequential runs here did. Agent frameworks now run independent tool calls concurrently by default. Providers also document latency guidance that matches this chapter: reduce output tokens, stream, cache stable prefixes, and use fewer round trips.

⚠️
Common mistakes
  • Executing a batch of independent calls one by one: 11.6 s instead of 6.7 s here.
  • Optimising tools or prompts when generation is 80% of the time.
  • A timestamp or user name at the top of the prompt, defeating the cache.
  • Overlapping writes to the same resource because "they were in one reply".
  • Not streaming the final answer.
  • Many small steps where one batched step would do.

Interview drill

Explain it simply: Your agent is slow. Where do you start?

How a strong answer sounds
Measure each step's prompt processing, generation and tool time before changing anything. In a measured run of 6.7 seconds, generation was 5.5, tools 1.0 and prompt processing 0.17 thanks to caching, so the first cuts are output tokens and thinking. Then make sure independent tool calls in one reply run concurrently: that alone took a run from 11.6 to 6.7 seconds. Keep stable content at the start of the prompt for caching, stream the final answer, and reduce the number of steps with tools that take several items.

Deeper: The model already requests parallel calls. Why might the agent still be slow?

How a strong answer sounds
Because the loop may execute them one by one. The API returns several call requests; running them concurrently is the application's job. Measured, the model batched ten calls in one reply whether or not it was asked to, and the sequential loop still spent 5.5 seconds on them against 1.0 concurrently. I would run independent reads in a bounded thread pool, keep result order, never overlap writes to the same resource, and check that the prompt prefix is stable so each step does not reprocess it.

🧠 Key takeaways

  • Generation was over 80% of run time; prompt processing was 0.17 s thanks to caching.
  • The model batched independent calls unprompted; the loop decided whether they ran concurrently.
  • Concurrent execution cut the ten-service task from 11.6 to 6.7 seconds.
  • A changing first line made prompt processing 2.6 times slower.
  • Stream the final answer and prefer fewer, bigger steps.
