Production Agent Architecture

Everything so far has been one agent run in one Python process. In production there are many users, many runs at once, runs that take minutes, tools that need sandboxes, state that must survive restarts, and a model server with finite capacity. The architecture around the loop decides how the system behaves under load and when parts of it fail.

This chapter walks through the parts: synchronous and background runs, queues and workers, sandboxes as a service, state stores, and failure modes. It measures the constraint that shapes all of them, the capacity of the model server. The incident agent ran with 1, 2, 4 and 8 runs at once against one GPU serving qwen3:14b, one request at a time.

  • Choose between synchronous and background runs
  • Size queues and workers from measured capacity
  • Run tools in sandboxes as a separate service
  • Keep run state outside the worker process
  • Design for the ways each part fails

Synchronous vs background runs

A synchronous run keeps the user's request open until the agent answers. That suits runs of a few seconds with someone waiting, like a chat reply. A background run accepts the request, returns a job id at once, and lets the client follow progress by polling, a stream of events, or a notification when it is done. That suits anything that can take more than a few seconds, anything that must survive a closed browser or a restarted server, and anything that waits for approval (Chapter 24). The measurement below shows how quickly "a few seconds" stops being true under load. With eight runs at once, the median run took 20 seconds and the slowest 35, longer than many HTTP clients and proxies will hold a request open.

Queues and workers

One GPU running the model one request at a time completed about 19 runs a minute, whether it was given 1, 2, 4 or 8 runs at once (19.1, 19.6, 19.3 and 18.9). Concurrency did not add capacity; it added waiting. The median run took 3.1 s alone, 6.0 s with two at once, 10.0 s with four and 19.7 s with eight. The slowest run (the 95th percentile) took 4.6, 8.8, 17.7 and 34.5 s. Each run's own model time also grew (3.1, 5.8, 10.4, 21.5 s), because that time includes waiting in the model server's queue. Accuracy did not change.

So put the queue where you can see and control it. Accept requests into a job queue, run a fixed number of workers sized to what the model server can actually serve, and report queue length and waiting time as first-class metrics. Then latency under load is a number you choose (reject, defer, or tell the user their place in line), not one that grows silently inside the model server. Servers that batch many requests together, such as vLLM, or Ollama with OLLAMA_NUM_PARALLEL above 1, can raise throughput at some cost per request. That was not measured here; measure it on your hardware before sizing workers.

# API: accept and return immediately
def submit(task: str, user: str) -> str:
    job_id = store.create_job(task=task, user=user, status="queued")
    queue.put(job_id)
    return job_id                                         # client polls or subscribes to events

# Worker: N of these, N sized to the model server's measured capacity
def worker():
    while job_id := queue.get():
        job = store.load(job_id)                          # messages + result cache, if resuming
        for step in agent_steps(job):
            store.checkpoint(job_id, step)                   # Chapter 32
            events.publish(job_id, step.summary())          # progress for the user
        store.finish(job_id, check(job))                    # final-state check, Chapter 27

Sandboxes as a service

Tools that run code, browse or touch files need isolation (Chapter 23). In production that becomes a service: the worker asks for a sandbox, sends commands, reads results, and releases it. Sandboxes can be pooled and pre-warmed so starting one costs milliseconds, not seconds. Each run or user gets its own, with the run's files, no shared credentials and a network policy. The sandbox service is also where resource limits, timeouts and audit logs for code execution live, separate from the model and from the workers that hold API keys.

State stores

Nothing about a run should live only in a worker's memory. The job record (status, user, task, result) goes in a database. Message checkpoints and the tool-result store go in a store that survives worker restarts (Chapter 32). Long-term memory has its own store with sources and dates (Chapter 16). Traces go to the observability system (Chapter 36). Then a worker is replaceable. Kill it mid-run and another picks up the job from its last checkpoint, without repeating calls that completed.

Failure modes

Each part fails in its own way, and the design should say what happens then. When the model server is slow or down, queue length grows: alert on waiting time, shed or defer new work, and fall back to a smaller model only where an evidence check guards the answer (Chapter 22). When a tool's backend fails, the agent gets errors it can act on (Chapter 8) and retries happen inside the tool with idempotency keys (Chapter 19). When a worker dies, the job resumes from its checkpoint. When a run never converges, a hidden budget stops it and a person is told (Chapter 31). When the sandbox pool is exhausted, jobs wait in the queue rather than run without isolation. Write these down as runbooks before launch, and test them by causing each failure on purpose.

Use case: background agents in products

Agent products moved long tasks to background runs as tasks grew. OpenAI's Codex (2025) runs each coding task in its own cloud sandbox in the background, possibly several in parallel, and reports back when done with logs and a proposed change. Anthropic's Claude Code can run in the cloud and as background tasks with checkpoints. Research agents from several providers accept a question, work for many minutes, and notify the user when the report is ready. Under the products sit the parts described in this chapter: a job queue, workers, a sandbox per task, state that survives restarts, and progress streamed to the user. The model server's capacity decides how many tasks run at once, and queueing absorbs the rest.

⚠️
Common mistakes
  • Synchronous requests for runs that can take tens of seconds under load.
  • More concurrent runs than the model server can serve: the queue hides inside it.
  • Run state in worker memory, lost with the worker.
  • Sandboxes in the same process or account as the workers' credentials.
  • No metrics for queue length and waiting time.
  • Failure modes left unwritten and untested until they happen.

Interview drill

Explain it simply: How would you deploy an agent for many users?

How a strong answer sounds
Requests go to an API that creates a job and returns at once. A queue feeds a fixed pool of workers sized to the model server's measured capacity. Workers run the loop, checkpoint after every step, store tool results, and stream progress events. Tools that run code use a sandbox service, and state lives in stores that outlive any worker. Concurrency beyond capacity only adds waiting: measured on one GPU, throughput stayed at about 19 runs a minute from 1 to 8 runs at once while the median run went from 3 to 20 seconds.

Deeper: Users say the agent got much slower after launch, but each run's model time looks normal in tests. What is happening?

How a strong answer sounds
Probably queueing at the model server. In a measurement the work per run did not change, but measured model time per run rose from 3.1 to 21.5 seconds at eight concurrent runs, because that time includes waiting for the server, and throughput stayed fixed at about 19 runs a minute. I would move the queue in front of the workers, size workers to capacity, expose queue length and waiting time as metrics, add capacity or batching where the hardware allows, and switch long runs to background jobs with progress updates.

🧠 Key takeaways

  • One GPU served about 19 runs a minute at every concurrency level from 1 to 8.
  • Extra concurrency only added waiting: median 3.1 s alone, 19.7 s with eight at once.
  • Use background runs with progress events for anything that can take more than a few seconds.
  • Queue in front of workers sized to capacity, and measure queue length and waiting time.
  • Keep state outside workers and sandboxes outside the workers' trust boundary.
