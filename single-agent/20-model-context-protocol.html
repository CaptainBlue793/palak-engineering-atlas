The Model Context Protocol (MCP)

Every tool so far was a Python function in the same program as the agent. That works until you want the same tools in a second agent, a code editor and a chat app, or want to use tools someone else wrote. The Model Context Protocol is a standard way to package tools (and documents and prompt templates) as a server that any MCP-aware application can connect to. Write a GitHub server once and every MCP client can use it.

This chapter builds an MCP server for the simulated production estate from earlier chapters with the official Python SDK (version 2.3), writes a small host that connects to it, and measures three things with qwen3:14b on the same twelve incidents. Does an agent do as well through MCP as with direct tools? What happens when it is connected to many servers at once? What does the protocol cost in time?

Why a protocol

Without a standard, every pairing of application and tool needs its own glue: ten applications and twenty tool providers make two hundred integrations. MCP turns that into thirty. Each application implements the client side once, each provider writes one server, and any client can talk to any server. Anthropic published the protocol in November 2024 as an open specification. OpenAI, Google and Microsoft added support to their agent tools during 2025, and Anthropic later donated it to an open foundation under the Linux Foundation.

MCP standardises how tools are described and called: messages in JSON-RPC 2.0, a list call that returns each tool's name, description and JSON Schema, a call that runs one. It does not make tools better. A badly described tool is just as bad over MCP (Chapter 4), and the agent loop, the prompt and the decisions all stay in your application.

Servers, clients and hosts

Three roles. The host is the application the user runs (a chat app, an editor, your agent). It holds the conversation and calls the model. Inside it, one client per connection speaks the protocol to one server, a separate program that exposes capabilities. The model never talks to a server. The host lists the server's tools, includes them in the model's request as ordinary tool schemas, and when the model asks for one, routes the call through the right client and passes the result back.

Tools, resources, prompts

A server can offer three kinds of thing. Tools are functions the model may call. Resources are documents identified by a URI that the host may read and show or include: here, the team's investigation method. Prompts are templates the user picks, often from a menu ("investigate a failing service"). The distinction is about who decides: the model chooses tools, the application chooses resources, the user chooses prompts. Clients can offer capabilities to servers too, for example sampling (a server asks the host's model for a completion) and elicitation (a server asks the user a question).

from mcp.server.mcpserver import MCPServer          # called FastMCP before version 2 of the SDK

server = MCPServer("ops", instructions="Read-only access to the production estate.")

@server.tool()
def get_errors(service: str) -> str:
    """Top error messages for a service in the last hour, with counts."""
    return estate.get_errors(service)

@server.resource("runbook://incident-method")
def method() -> str:
    """How we investigate a failing service."""
    return "Start at the failing service and read its errors. ..."

@server.prompt()
def investigate(service: str) -> str:
    """Start an investigation of a failing service."""
    return f"{service} is failing. Find the service where the problem starts and the deploy that caused it."

if __name__ == "__main__":
    server.run("stdio")                               # or "streamable-http"

The SDK builds each tool's schema from the type hints and the description from the docstring. For get_errors it produced {"type": "object", "properties": {"service": {"title": "Service", "type": "string"}}, "required": ["service"]}, plus an output schema, because the function is annotated to return str. The docstring is now the tool description every model will read, so it deserves the care described in Chapter 4.

A minimal host

The host side is the agent loop from Chapter 2 with a routing table. It connects to each server, turns the listed tools into the model's tool format, prefixes each name with its server so two servers cannot collide, and sends each call back to the server it came from:

from mcp import Client, StdioServerParameters

async def connect(servers: dict, stack) -> tuple[list, dict]:
    tools, route = [], {}
    for name, params in servers.items():                 # e.g. {"ops": StdioServerParameters(command="python", args=["ops_server.py"])}
        client = await stack.enter_async_context(Client(params))
        for t in (await client.list_tools()).tools:
            exposed = f"{name}__{t.name}"                    # ops__get_errors: no collisions between servers
            route[exposed] = (client, t.name)
            tools.append({"type": "function", "function": {"name": exposed, "description": t.description,
                                                         "parameters": t.input_schema}})
    return tools, route

async def call(route: dict, name: str, args: dict) -> str:
    client, real_name = route[name]
    result = await client.call_tool(real_name, args)
    return "\n".join(block.text for block in result.content if block.type == "text")

Over MCP the agent solved 10 of 12 incidents (11 of 12 with server-prefixed names), against 11 of 12 with the same functions called directly. The one incident every version missed is the hard one from earlier chapters; the other difference is the variation you expect from slightly different schemas. The prompts were even a little smaller (about 430 tokens on the first step instead of 444), because the hand-written schemas had a description for the service parameter that the SDK's did not. Moving tools behind MCP changed neither what the model saw in any important way nor how well it did.

Transports

A stdio server is a local program the host starts, talking JSON-RPC over its standard input and output. It suits local tools such as files, Git or a database on your machine, and runs with your user's permissions. A Streamable HTTP server is a web service at a URL, possibly remote and shared, with authorisation by OAuth. It replaced the earlier HTTP-plus-Server-Sent-Events transport in 2025. With the SDK used here, the client negotiated protocol version 2026-07-28 and first tried a server/discover request, falling back to the older initialize handshake for servers that do not support it.

Measured on this machine, one get_errors call took about 0.6 ms over stdio, 1.3 ms over HTTP to a local server, and 0.2 ms in-process, against well under a microsecond for the direct function call. Connecting cost 0.6 seconds for stdio, which starts a Python process, and 39 ms for HTTP to a running server. A model step takes seconds, so the transport is irrelevant to an agent's speed. Starting servers is not: start them once per session, not once per call.

Many servers at once

The ease of adding servers is also MCP's main cost. Every connected server's tools go into every request. Connecting ten more ordinary servers (GitHub, calendar, tickets, chat, wiki, CRM, billing, cloud, HR, analytics; 60 tools, none of them relevant to the incident) grew the first prompt from 434 to 2,832 tokens, about 40 tokens per tool. A whole investigation averaged about 32,000 prompt tokens instead of 5,300, and took 11.5 seconds instead of 3.8. The model never called an irrelevant tool, but it solved 9 of 12 instead of 11, and it took more steps. On twelve incidents that difference is small evidence, but the direction matches the token count. The remedies are to connect only the servers a task needs, let users switch servers off, and, with hundreds of tools, offer a search over tools rather than every schema in every request.

Trusting a server

A server is code you run, or a service you send data to, and its tool descriptions and results go straight into the model's context. Treat it like any dependency. Install servers from sources you trust, pin versions, and read what they do. A stdio server runs with your user's rights: it can read whatever you can. A remote server sees every argument the model sends it. Its descriptions are text the model will follow, and they can change after you approved them, so a careful host shows which server each tool comes from, notices when a server's tool list changes, and asks before tools that write or send anything. Prefixing names by server, as the host above does, also stops one server's tool silently replacing another's. Tool results and descriptions are untrusted input; Chapter 25 measures what happens when that input contains instructions.

Use case: MCP in editors and chat apps

The first MCP hosts were Anthropic's Claude Desktop app and coding tools, with reference servers for the file system, Git, GitHub, Postgres and Slack published alongside the specification in November 2024. Within a year, code editors and IDEs such as Cursor, VS Code and JetBrains, OpenAI's Agents SDK and ChatGPT, and Google's and Microsoft's agent platforms could all connect to MCP servers, and companies published official servers for their own products. The pattern measured here showed up in practice too. Users connecting many servers found requests bloated by tool definitions, and hosts responded by letting users turn servers and individual tools on and off, and by searching tool definitions on demand instead of sending them all.

⚠️
Common mistakes
  • Connecting every server you have to every agent; each tool costs about 40 tokens in every request.
  • Unprefixed tool names across servers, so one silently replaces another.
  • Starting a stdio server per call instead of once per session.
  • Treating server descriptions and results as trusted; they are input, like a web page.
  • Installing servers like scripts from a forum post, without pinning or reading them.
  • Expecting MCP to fix a badly designed tool; it only standardises how it is delivered.

Interview drill

Explain it simply: What is MCP, and why would you use it instead of defining tools in your agent's code?

How a strong answer sounds
MCP is a standard protocol for exposing tools, resources and prompts as servers that any compatible application can connect to. A host lists a server's tools, gives them to the model as normal tool schemas and routes calls back over JSON-RPC, locally over stdio or remotely over HTTP. It is worth it when tools should be shared across applications or come from other people; for a few tools used by one agent, plain functions are simpler. It does not change agent quality: measured on twelve incidents, the same tools solved 11 directly and 10 to 11 over MCP.

Deeper: Your agent is connected to fifteen MCP servers and has become slower and less accurate. What is going on and what would you do?

How a strong answer sounds
Every connected tool's schema is sent with every request. In a measurement, adding ten servers (60 tools) grew the first prompt from about 430 to 2,800 tokens, a run from about 5,300 to 32,000 tokens and from 3.8 to 11.5 seconds, and success fell from 11 to 9 of 12 even though the irrelevant tools were never called. I would connect servers per task, let users disable servers and tools, prefix names by server, and with very many tools search tool definitions on demand. I would also review which servers are connected at all, since each one is code or a service the agent trusts.

🧠 Key takeaways

  • MCP standardises how tools, resources and prompts are listed and called; it does not make them better.
  • The same tools did as well over MCP as directly: 10 to 11 of 12 against 11.
  • Transport costs under 2 ms per call; starting a stdio server costs about 0.6 s, so start it once.
  • Sixty extra tools made each request six times bigger and three times slower, and solved two fewer incidents.
  • Servers are dependencies: pin, prefix, show their origin and ask before writes.
