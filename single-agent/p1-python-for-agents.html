Python for Agent Code

An agent is ordinary Python around a model call: functions the model may ask to run, a loop that waits on the model and on those functions, and processes it starts and must be able to stop. Four parts of the language do most of that work. Type hints become the schema the model sees. Dataclasses hold the steps of a run. async lets the program wait on many slow things at once. subprocess runs commands with a time limit.

Each of those has a trap that only shows up when you measure, so this chapter measures them with qwen3:14b served by Ollama: what schema a library builds from your type hints and how the model's arguments change with it, what concurrency really buys against a local model server, and what happens to a command that will not stop.

  • Pin an agent's Python packages, model and server so a run can be repeated
  • Write type hints and docstrings that turn into a correct tool schema, and check the schema
  • Use asyncio for slow tools, and know when concurrency does not help
  • Run a command with a timeout that really stops it, and keep its output to a safe size
  • Record what a run needs to be reproduced

Environments and pinned versions

An agent's behaviour depends on more than your code. The model file, the server that runs it, the client library that builds requests and the settings you pass all change what the model sees. A bug report that says "it called the wrong tool" is useless unless you can rerun the same request against the same versions. So every project gets its own virtual environment, its packages pinned to exact versions, and the model and server versions written down beside them.

# once per project
python -m venv .venv
.venv\Scripts\activate              # source .venv/bin/activate on Linux and macOS
pip install ollama pydantic httpx
pip freeze > requirements.txt      # ollama==0.6.3, pydantic==2.14.1, httpx==0.28.1 ...

# and outside Python: the server and the exact model build
ollama --version                    # ollama version is 0.40.6
ollama list                         # qwen3:14b  bdbd181c33f2  9.3 GB

The model's ID (bdbd181c33f2) is a digest of its files, so it changes when the model behind a tag changes. A tag such as qwen3:14b can be updated in the library; the digest cannot. Record both.

Type hints and dataclasses

A type hint such as name: str does nothing when Python runs, but tools read it. Agent libraries turn a function's hints and docstring into the JSON Schema the model is given, so the hints you write are the interface the model reads. Ollama's Python library does this when you pass a function in tools=[...]. It is convenient, and it is lossy. Measured below on four functions, it kept names, basic types and the Google-style Args: descriptions, but:

  • a Literal["INFO", "WARN", "ERROR"] became a plain "string": the three allowed values disappeared;
  • parameters with defaults (level="ERROR", limit=20) were marked required;
  • list[str] became "array" with no item type, and dict[str, str] a bare "object";
  • a function with no docstring got empty descriptions everywhere.

Pydantic builds a schema from the same signature that keeps all of it: the enum, the defaults (so only service is required), the item types. Whichever you use, print the schema once and read it, because that JSON, not your Python, is what the model is shown.

import inspect
from typing import Literal
from pydantic import create_model

def search_logs(service: str, level: Literal["INFO", "WARN", "ERROR"] = "ERROR", limit: int = 20) -> list[str]:
    """Search a service's logs."""

def tool_schema(fn, descriptions: dict[str, str]) -> dict:
    fields = {n: (p.annotation, ... if p.default is p.empty else p.default)
              for n, p in inspect.signature(fn).parameters.items()}
    params = create_model(fn.__name__, **fields).model_json_schema()
    for name, prop in params["properties"].items():
        prop.pop("title", None); prop["description"] = descriptions[name]
    return {"type": "function", "function": {"name": fn.__name__, "description": inspect.getdoc(fn), "parameters": params}}

Dataclasses are the other half: a typed record with no boilerplate. An agent run is a list of steps, and each step is worth keeping as a record you can log, replay and compare, rather than as loose dictionaries.

from dataclasses import dataclass, field

@dataclass(frozen=True)
class ToolCall:
    name: str
    arguments: dict
    result: str
    ok: bool
    seconds: float

@dataclass
class Run:
    task: str
    model: str
    steps: list[ToolCall] = field(default_factory=list)   # never a bare [] default

async and await

An agent spends almost all of its time waiting: for the model to generate, for an HTTP API to answer, for a command to finish. A function declared with async def is a coroutine: at each await it hands control back to the event loop, which runs another coroutine until the first one's result arrives. asyncio.gather starts several at once; a Semaphore caps how many run together, which is how you stay under an API's rate limit.

import asyncio, httpx

async def fetch_status(client: httpx.AsyncClient, url: str, limit: asyncio.Semaphore) -> int:
    async with limit:                      # at most N requests in flight
        r = await client.get(url, timeout=10)
        return r.status_code

async def check_all(urls: list[str]) -> list[int]:
    limit = asyncio.Semaphore(4)
    async with httpx.AsyncClient() as client:
        return await asyncio.gather(*(fetch_status(client, u, limit) for u in urls))

Concurrency only helps if the thing you are waiting on can serve several requests at once. Eight calls to a slow HTTP endpoint (half a second each) took 4.05 s one at a time and 0.51 s all together: the server had threads to spare. Eight calls to qwen3:14b took 2.94 s one at a time and 2.91 s all together, because Ollama's default is one request at a time per model (OLLAMA_NUM_PARALLEL=1); the rest wait in its queue. Letting the server run four at once has a price, because each slot gets its own context memory: with four 16k-token slots the model no longer fitted on the 16 GB GPU, 28% of it ran on the CPU and the eight calls took 4.78 s at best. With four 4k-token slots it stayed on the GPU and finished in 1.21 s, 2.4 times faster, not eight. The GPU is shared, so slots split its speed between them.

Running subprocesses

Agents run commands: tests, linters, scripts the model wrote. subprocess.run with a list of arguments (no shell), capture_output=True and a timeout covers most cases. Read the exit code, keep stderr, and cut the output before it goes back to the model: one command here printed 50 million characters in a quarter of a second, millions of tokens if you passed it on.

import subprocess

def run_command(args: list[str], timeout: float = 30, max_chars: int = 4000) -> str:
    try:
        r = subprocess.run(args, capture_output=True, text=True, timeout=timeout)
    except subprocess.TimeoutExpired:
        return f"error: timed out after {timeout} s"
    out = r.stdout + r.stderr
    if len(out) > max_chars:
        out = out[-max_chars:] + f"\n[first {len(out) - max_chars} characters cut]"
    return f"exit code {r.returncode}\n{out}"

The timeout has one trap. When it expires, subprocess.run kills the process it started. If that process is a shell (shell=True) or any launcher, the program the shell started keeps running, still holding the output pipe open, so Python waits for the pipe to close and the call does not return. Measured below: a direct timeout returned in 2.01 s with nothing left running; the same loop started through a shell was still running and still blocking the caller 10 seconds after its 2-second timeout. Killing the whole process tree (taskkill /T on Windows, a process group and os.killpg on Linux) ended it in 2.62 s. Chapter 23 turns this into a sandbox with CPU, memory and network limits.

Reproducible runs

A model call has more settings than it looks. For anything you will compare later (a bug, a prompt change, an evaluation) send them explicitly and record them with the run: model and digest, temperature and seed, context size, the tool schemas, the library versions. Two of these were decisive in this chapter. With the server's default context, qwen3:14b was given a 40,960-token context, ran 10% on the CPU and took 5.5 s for the eight calls; with num_ctx set to 16,384 it ran fully on the GPU in 2.9 s. And temperature 0 with a fixed seed made each tool-argument test repeatable. Writing each run as one JSON line per step gives you a log you can search, diff and replay.

import json, ollama

OPTIONS = {"temperature": 0, "seed": 1, "num_ctx": 16384}   # the course default for qwen3:14b
reply = ollama.chat(model="qwen3:14b", messages=messages, tools=[schema], think=False, options=OPTIONS)
with open("runs.jsonl", "a", encoding="utf-8") as log:
    log.write(json.dumps({"model": "qwen3:14b@bdbd181c33f2", "options": OPTIONS,
                          "tools": [schema], "reply": reply.message.model_dump()}) + "\n")

Use case: the OpenAI Agents SDK and Pydantic function schemas

Agent frameworks all solve the problem this chapter measured: turning a Python function into a schema a model will use correctly. The OpenAI Agents SDK, released in March 2025, does it with its @function_tool decorator, which reads the function's signature and type hints, builds a Pydantic model from them, takes descriptions from the docstring and produces the JSON Schema sent to the model. By default it generates a strict schema, which lists every property as required and forbids extra ones, so that the API's structured-output mode can guarantee the model's arguments match it. The design choice is the point: the framework treats the schema as a contract checked before your code runs, rather than a hint the model may or may not follow, which is exactly the gap the enum experiment here exposed.

⚠️
Common mistakes
  • Never reading the generated tool schema, so lost enums and wrongly required fields go unnoticed.
  • Using shell=True with a timeout and assuming the command stops when it expires.
  • Returning a command's whole output to the model instead of the tail and a note of what was cut.
  • Expecting asyncio.gather to speed up model calls to a server that runs one request at a time.
  • Leaving the server's default context size and not checking whether the model still fits on the GPU.
  • Logging only the final answer, without the options, versions and tool schemas needed to rerun it.

Interview drill

Explain it simply: Your agent calls three slow HTTP tools that do not depend on each other. How would you make it faster, and what would you watch out for?

How a strong answer sounds
Run them concurrently with asyncio: write the calls as coroutines on one async HTTP client and start them with gather, so the total time is close to the slowest call instead of the sum. I would cap concurrency with a semaphore so we stay under each API's rate limit, give every call its own timeout so one slow service cannot hold up the step, and use return_exceptions so one failure becomes an error result for the model rather than cancelling the others. I would not expect the same gain from running several model calls at once against one local server unless it is configured for parallel requests, and even then each slot costs context memory.

Deeper: An agent's "run tests" tool sometimes hangs the whole agent even though it has a 60-second timeout. What is happening and how do you fix it?

How a strong answer sounds
Most likely the command is started through a shell or a launcher, so when the timeout fires only that parent is killed. The real test process keeps running and keeps the stdout pipe open, and reading the output waits for the pipe to close, so the call never returns. I would start the command without a shell from an argument list, put it in its own process group (or a job object on Windows), and on timeout kill the whole group, then read what output there is with a bounded wait. Beyond that I would run it in a sandbox with CPU and memory limits, cap the output returned to the model, and record the timeout as an error result so the agent can decide what to do next.

🧠 Key takeaways

  • Pin packages and record the server version, model digest and options with every run.
  • The schema built from your type hints is what the model sees; ollama-python's dropped an enum, and valid levels fell from 19 of 19 to 1 of 18.
  • Keep runs and steps in dataclasses, and log them one JSON line per step.
  • asyncio made eight slow HTTP calls 8× faster but did nothing against a one-slot model server.
  • A timeout must kill the whole process tree, and command output must be cut before it reaches the model.
