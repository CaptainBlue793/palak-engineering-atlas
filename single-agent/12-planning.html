Planning: Plan-then-Execute vs Step by Step

A step-by-step agent decides each action after seeing the last result. A planning agent writes down the steps first and then works through them. Planning promises order on long tasks: no forgotten parts, no wandering. It also adds a new way to fail, because a plan can be wrong before anything has been looked at, and an agent may follow a wrong plan faithfully.

This chapter measures five designs with qwen3:14b on a three-part incident brief: find the root cause and its deploy, give the error rate of every service between checkout and the root cause, and list every service that would be affected if the root cause went down. The designs: no plan; a plan the model writes first; a plan the model keeps up to date with a to-do tool; a correct plan written by a person; and that plan with a tool that does its one loop-shaped step.

  • Compare step-by-step agents with plan-then-execute
  • Keep a plan as state the agent updates, and replan when a result contradicts it
  • Check a plan before trusting it
  • Recognise steps a model will not carry out reliably, and move them into tools
  • Measure each part of a multi-part task separately

Step-by-step agents

With no plan, the agent did what earlier chapters showed: followed the errors, read deploys, fetched metrics. It got the error rates right in all 12 briefs and the root cause in 8, but the impact list right in only 2, and the whole brief in none, averaging 11.7 steps. The impact part needs a walk up the dependency graph, and a step-by-step agent without a reason to keep walking stopped after the first level or listed downstream services instead.

Plan then execute

Asked to write a numbered plan before using any tool, the model produced a tidy five-step list, and its third step read: "Use the dependency mapping tool to trace all services affected by the root-cause service." The dependency tool returns what a service calls, the wrong direction for "affected if it goes down", and the agent followed the plan: impact right in 1 of 12, the whole brief in 1. Planning made the run shorter (9.5 steps) without making it more correct. A plan written before looking at anything encodes the model's first guess about the tools, and execution then carries the guess out.

plan = ask(messages + [{"role": "user", "content": "Before using any tool, write a short numbered plan: the tool calls you will make, in order."}])
problems = check_plan(plan, tools)        # every step names a real tool; the tool does what the step needs
if problems:
    plan = ask(..., f"Your plan has problems: {problems}. Revise it.")
system += "\n\nYour plan (follow it, and revise it if a result shows it is wrong):\n" + plan

Replanning and plans as state

The third design gave the agent an update_plan tool: write the plan as a to-do list, then mark items done or change them as results arrive. It used the tool in 7 of 12 runs, took 14.9 steps, and scored the same: impact 2 of 12, whole brief 1. A plan kept as state is valuable for long runs: it survives compaction (Chapter 15), lets a person see progress, and lets a crashed run resume (Chapter 32). It does not by itself make the plan right or make the agent finish it.

When plans help

To separate "the plan was wrong" from "the plan was not carried out", the fourth design gave the agent a correct plan written by a person, step 4 of which said: "get_dependents on the root cause, then get_dependents on each service returned, until no new services appear." Impact rose only to 3 of 12. Most runs called get_dependents once and stopped, so a root cause in payments came back as "checkout" without gateway. The plan was right; the loop inside one of its steps was not carried out.

The fifth design kept the person's plan and replaced that step with a tool, get_impact, that walks the graph in code and returns the whole set. Impact rose to 9 of 12 and the whole brief to 7 of 12, in 8.4 steps, the fewest of any design. Of the three remaining impact failures, two were not planning failures at all: the "cache stampede" error in checkout's logs sent the agent to the wrong root cause, and the deploy and the impact list followed from that mistake. In the third, the agent found the right root and still listed the services it calls instead of those that call it. Plans help when every step is something the agent can do in a call or two. A step shaped like a loop ("until no new services appear") belongs in a tool or in code.

Use case: plan-and-solve and to-do lists in coding agents

"Plan-and-Solve Prompting" (Wang and colleagues, 2023) found that asking a model to first devise a plan and then carry it out improved accuracy on multi-step reasoning problems over plain step-by-step prompting, and planner-executor agent designs such as LangChain's plan-and-execute followed. In practice, today's coding agents keep the plan as state rather than as a preamble: Claude Code and similar tools maintain a visible to-do list that the agent writes, ticks off and revises as it works, mainly so that long tasks are not forgotten halfway and so the user can see progress. Both lines of work agree with the measurement here on one point: a plan helps most when its steps are concrete actions the agent can complete, and least when a step hides open-ended work.

⚠️
Common mistakes
  • Trusting a plan written before any data was seen; one wrong tool in step 3 decided the result.
  • Grading only the final answer of a multi-part task, so the failing part is invisible.
  • Plans with loops in them ("until no new services appear") that the agent stops after one round.
  • Adding a to-do tool and expecting better reasoning; it adds visibility, not correctness.
  • Never telling the agent to revise the plan when a result contradicts it.
  • Blaming the plan for a wrong turn that came from a misleading tool result.
🎤
Interview drill

Explain it simply: When would you have an agent write a plan before acting?

How a strong answer sounds
When the task has several parts that are easy to forget, when people need to see or approve the steps, or when a long run needs a record of progress to survive compaction and restarts. I would keep the plan as state the agent updates, check that each step uses a real tool in the right way before execution, and tell it to replan when results contradict the plan. In a measured comparison, a plan the model wrote up front sent it to the wrong tool and did not improve accuracy at all; what helped was turning the plan's one loop-shaped step into a tool.

Deeper: You gave an agent a correct, detailed plan and it still gets one part of the task wrong. What do you look at?

How a strong answer sounds
Whether that part of the plan is something the agent can actually carry out in a few calls. In a measured case the step was "call get_dependents on each service returned, until no new services appear", a loop, and the agent did one round and stopped, so the impact list was right in 3 of 12 briefs. Replacing the step with a tool that walks the graph in code raised it to 9 of 12. So I would read traces of the failing part, find steps that hide iteration, counting or bookkeeping, move those into tools or code, and grade each part of the task separately so the next weak part shows up.

🧠 Key takeaways

  • No design improved the error-rate part (12 of 12 in every one); planning changed only how the other parts failed.
  • The model's own plan picked the wrong dependency tool, and the agent followed it: impact 1 of 12.
  • A to-do tool added visibility and steps, not correctness.
  • Even a correct plan failed on its loop-shaped step (3 of 12); a tool for that step made it 9 of 12.
  • Check plans, keep them as state, and move iteration into tools.
