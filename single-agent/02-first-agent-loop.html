Your First Agent Loop

An agent fits in about sixty lines of Python: send the transcript and the tools to the model, run whatever tools it asks for, append the results, and go round again until it answers. The pieces are small, but each one has a way to go wrong that does not raise an error, only a worse agent. This chapter writes the loop in full and then breaks it on purpose.

Four versions of the loop ran the 24 tasks from Chapter 1 (12 lookups and 12 incident investigations) against qwen3:14b, with every tool slowed to a realistic 0.2 to 0.6 seconds: one call with no loop, a loop that forgets to record the model's own tool calls, a correct loop, and a correct loop that runs parallel calls concurrently. The time of every run is split into prompt reading, generation, tools and everything else.

  • Write a complete agent loop with tools, a transcript and a step limit
  • Dispatch tool calls safely, including unknown tools and failing ones
  • Feed results back so the model knows what it has already done
  • Stop on an answer, a limit or an error, and recognise a "stop" that is not an answer
  • Measure where an agent's time goes

The loop

Here is the whole agent. Everything later in the course adds to one of its parts: better tools (Chapters 3 to 4), better instructions (5), better stopping (7), better error handling (8), better use of the context (10 and 11).

import json, time
from dataclasses import dataclass, field
import ollama

MODEL = "qwen3:14b"
OPTIONS = {"temperature": 0, "num_ctx": 16384}

@dataclass
class Result:
    status: str                       # "answer", "step limit" or "error"
    text: str
    steps: list = field(default_factory=list)

def dispatch(tools: dict, name: str, args: dict) -> str:
    if name not in tools:
        return f"error: no tool named {name}; available: {', '.join(tools)}"
    try:
        return str(tools[name]["fn"](**args))
    except Exception as e:                           # a failing tool is an observation, not a crash
        return f"error: {type(e).__name__}: {e}"

def run_agent(task: str, tools: dict, system: str, max_steps: int = 15) -> Result:
    schemas = [t["schema"] for t in tools.values()]
    messages = [{"role": "system", "content": system}, {"role": "user", "content": task}]
    log = []
    for step in range(max_steps):
        t0 = time.perf_counter()
        reply = ollama.chat(model=MODEL, messages=messages, tools=schemas, think=False, options=OPTIONS).message
        if not reply.tool_calls:                                        # 1. the model answered
            return Result("answer", reply.content or "", log)
        messages.append({"role": "assistant", "content": reply.content or "",          # 2. record what it asked for
                         "tool_calls": [{"function": {"name": c.function.name, "arguments": dict(c.function.arguments)}}
                                        for c in reply.tool_calls]})
        for c in reply.tool_calls:                                     # 3. run every call, in order
            result = dispatch(tools, c.function.name, dict(c.function.arguments))
            messages.append({"role": "tool", "tool_name": c.function.name, "content": result})
            log.append({"step": step, "tool": c.function.name, "args": dict(c.function.arguments),
                        "result": result[:200], "seconds": round(time.perf_counter() - t0, 2)})
    return Result("step limit", f"stopped after {max_steps} steps", log)           # 4. the limit

Dispatching tool calls

The model does not run anything. It returns the name of a tool and a dictionary of arguments, and dispatch decides what happens. Three cases need code: the tool exists and works, the tool exists and raises, and the model asks for a tool that does not exist. In all three the loop carries on, and the model is told what happened in words it can act on. A loop that lets an exception escape turns one bad argument into a crashed run; a loop that silently skips an unknown tool leaves the model waiting for a result that never comes. Chapter 8 is about what those error messages should say.

Feeding results back

After the tools run, two things go into the transcript: the assistant message with the calls the model made, then one tool message per call. The first is easy to forget, because the loop already has what it needs to run the tools. Measured, forgetting it cost three of seven investigations. Without its own calls in the history, the transcript shows tool results arriving that nobody asked for, and the model lost track of where it was. Twice it wrote, as its reply, "To identify the specific deploy, we need to check the deployment history of the checkout service. I will now retrieve the deployment history", and then did not call the tool. Once it returned nothing at all. Lookups, which need only one call, were unaffected: the damage grows with the length of the run.

Stopping

The loop above stops in three ways, and the status says which. The subtle case is the first one: "no tool calls" means the model has stopped asking for tools, not that it has answered. The forgetting loop above shows the difference. "I will now retrieve the deployment history" has no tool call in it, so the loop returned it as the final answer. A production loop checks the final text before accepting it: is it empty, does it announce an action instead of reporting a result, does it contain what the task asked for? Chapter 7 measures those checks.

Where the time goes

A correct investigation took about 3.8 seconds on average: 6 model calls and 5 tool calls. The split:

  • Generation, 1.75 s. Each step writes a short tool call (about 20 tokens) or the answer, at about 80 tokens a second, plus a fixed cost per call.
  • Tools, 1.9 s. Five calls at 0.2 to 0.6 s each. With real APIs, tools are often half of an agent's time.
  • Prompt reading, 0.17 s. Small, because the server's cache reuses the unchanged start of the transcript (P4).
  • Everything else, 0.04 s. Python, HTTP and JSON are not where the time goes.

The fourth version ran tool calls in parallel when the model asked for more than one in a step. It made no difference, because in 24 tasks qwen3:14b never asked for more than one: every step was one call. Parallel execution only helps a model that issues parallel calls, and only for calls that do not depend on each other. Chapter 30 measures when it does.

Use case: ReAct and the loop everyone copied

The loop in this chapter is essentially the one described in "ReAct: Synergizing Reasoning and Acting in Language Models" by Yao and colleagues, published in October 2022, before any model API had native tool calling. The model wrote "Thought:", "Action:" and "Action Input:" lines as plain text, the program parsed the action, ran it against tools such as a Wikipedia search API, and appended an "Observation:" line before asking the model to continue. Early agent libraries such as LangChain's agents and AutoGPT were built on that text protocol, and its fragility (a model that writes "Action:" slightly wrong breaks the parser) is one reason model providers added structured tool calls in 2023. The structure survived unchanged: today's tool-calling loops are ReAct with the parsing moved into the model server. Chapter 6 measures what the "Thought" part still adds.

⚠️
Common mistakes
  • Not appending the assistant's tool-call message, so the model cannot see what it has already done.
  • Letting a tool exception escape the loop instead of returning it as a result.
  • Running only the first tool call when the model asked for several.
  • Treating "no tool calls" as "answered" without checking the text.
  • No step limit, or a limit that returns nothing to say it was hit.
  • Optimising Python overhead when the time is in generation and tools.

Interview drill

Explain it simply: Walk me through what happens in one iteration of an agent loop.

How a strong answer sounds
The loop sends the whole transcript, system prompt, task and every earlier step, together with the tool definitions, to the model. The model replies with either text or one or more tool calls. If it is text, the loop checks it and returns it as the answer. If it is tool calls, the loop appends the model's message with those calls to the transcript, runs each call through a dispatcher that handles unknown tools and exceptions, appends each result as a tool message, and goes round again. A step limit guarantees it ends. Every iteration rereads everything, so the transcript is both the agent's memory and its main cost.

Deeper: Your agent sometimes ends with a message like "I will now check the deployment history" and never does it. What is wrong?

How a strong answer sounds
The loop treats any reply without tool calls as the final answer, and the model has written its intention as text instead of making the call. I would look first at the transcript the loop builds: in a measured case, the loop was not appending the assistant's own tool-call messages, so the model saw results with no record of asking for them and lost track; fixing that took investigations from 4 to 7 correct out of 12. Then I would add a check on final answers: if the text is empty or announces an action, send it back with a reminder to call the tool or give the answer, with a limit on how often. Native tool calling and a clear system prompt reduce it further.

🧠 Key takeaways

  • An agent is a loop: model, tool calls, results, model again, with three ways to stop.
  • Dispatch every call through code that turns unknown tools and exceptions into results.
  • Append the model's own tool-call message; forgetting it took investigations from 7 to 4 of 12.
  • "No tool calls" is not the same as an answer; check the final text.
  • Time went to generation (1.75 s) and tools (1.9 s), not prompt reading (0.17 s) or Python (0.04 s).
