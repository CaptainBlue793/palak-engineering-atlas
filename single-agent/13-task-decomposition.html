Task Decomposition & Subgoals

A large task can be split into smaller ones, each done by its own short agent run with its own small context, and the results combined. Decomposition is how agents handle work that would not fit in one context window, and how independent parts run in parallel. It is also a new place for errors: each piece loses sight of the whole, the pieces can disagree, and someone has to check and join them.

This chapter measures decomposition with qwen3:14b on a health report: for each of ten services, its error rate, p99 latency, most frequent error and latest deploy, 40 fields checked against the simulated estate. It ran four ways on six estates: one agent run for the whole report; split by code into ten per-service runs; the same with a check on each piece; and split by the model, which wrote its own list of subtasks.

  • Decide when a task should be split and when one run is better
  • Split by code or let the model split, and know the costs of each
  • Give each subtask the context it needs to be unambiguous
  • Check each piece before combining, and retry so the retry can differ
  • Recognise tasks too big for one run

Subgoals

The report has an obvious split: ten services, four fields each, no dependency between services. That makes it a good test, because decomposition should be at its easiest here. It turned out not to be needed at all. With compact tool results, one agent run fetched everything (mostly in parallel calls), never needed more than 2,300 prompt tokens, and got 236 of 240 fields right in 12 steps. Splitting is a response to a problem, usually a context that will not fit or work that must run in parallel. Without that problem it is cost and new risk.

To-do lists

Asked to break the report into independent subtasks before doing any work, the model wrote 40 of them, one per field ("Fetch error rate for checkout service", "Fetch p99 latency for checkout service", …). Run one by one, they got 233 of 240 right, but took 89 steps and about 40,000 prompt tokens, 2.6 times the single run, because every subtask paid for its own system prompt, tools and lookups. A model's own decomposition tends to be fine-grained and literal: correct, and expensive. When you let the model split, ask for subtasks of a size you want ("one per service"), or split in code where the structure is known.

Checking each piece

Split by code into ten per-service runs ("Report on the service inventory. Reply with one line…"), the report got only 210 of 240, worse than one run, and the failures were instructive. In every estate the inventory subtask came back with a report on all ten services: read on its own, "report on the service inventory" can mean "report the inventory of services", and the model did exactly that, calling 30 tools. The join step, which took each subtask's last line, then recorded gateway's line in inventory's place. In the single run, the ten names side by side had made the meaning obvious. A piece of a task loses the context of the whole, and every ambiguity that context used to resolve comes back.

A check that each line was about the service it was asked for caught the problem twice per estate, and the retry fixed nothing: 211 of 240. At temperature 0 the same request produced the same answer. A retry must change something the model sees: the specific failure ("you reported on gateway; report on the service named 'inventory' in this estate"), a disambiguated subtask ("the service called inventory, one of: checkout, payments, …"), or a different method. The best fix is earlier still, when the subtask is written: give each piece the context it needs to mean only one thing.

SUBTASK = ("Report on one production service, named '{s}' (one of: {all}). "
           "Reply with one line exactly: {fmt}")

for s in SERVICES:
    line = run_agent(SUBTASK.format(s=s, all=", ".join(SERVICES), fmt=FMT), tools, SYSTEM).answer
    if not about(line, s):                                        # check the piece before using it
        line = run_agent(SUBTASK.format(...) + f"\nYour last answer was about '{first_cell(line)}', not '{s}'.", ...).answer
    lines.append(line)

Dependencies

Ten service reports are independent, so their order does not matter and they could run at the same time. Most real decompositions are not like that: an investigation must find the root cause before reading its deploys, and an impact list needs the root cause first (Chapter 12). Write the dependencies down as a graph, run what is ready, and pass each finished piece's result to the pieces that need it, explicitly, rather than hoping a later subtask rediscovers it. Splitting dependent work into context-free pieces is how the inventory mistake happens at a larger scale.

Too big for one run

Decomposition earns its cost when one run cannot hold the work. The sweep in Chapter 10 was that case: ten raw logs overflowed the window, and per-service runs of about 2,000 tokens each would have fitted easily where one run of 22,000 failed. The trade-off is the one measured here. Each piece is small and focused but blind to the whole, so the pieces need the shared context written into them, a check on the way back, and a final step that combines and cross-checks. Multi-Agent Systems turns that last step into a design of its own.

Use case: least-to-most and map-reduce over long inputs

"Least-to-Most Prompting" (Zhou and colleagues, 2022) showed that breaking a hard problem into a sequence of easier subproblems, each solved with the answers to the earlier ones in view, let models solve problems harder than any in their examples. The same idea, applied to inputs instead of problems, is map-reduce summarisation: split a document too long for the window into chunks, summarise each, then combine the summaries, a pattern built into libraries such as LangChain from its early versions. Both carry the costs measured here. Least-to-most passes earlier answers forward because a subproblem alone lacks context, and map-reduce summaries are known to lose details that only matter in combination. Decomposition works when each piece is given what it needs, and the join step is designed, not assumed.

⚠️
Common mistakes
  • Splitting a task that fits in one run; here it lost 26 fields.
  • Subtasks stripped of the context that made them unambiguous.
  • Retrying a failed piece with the identical request at temperature 0.
  • Letting the model split freely and paying for 40 subtasks where 10 would do.
  • Hiding dependencies between pieces instead of passing results forward.
  • Combining pieces without a check that each answered its own question.

Interview drill

Explain it simply: When should an agent break a task into subtasks?

How a strong answer sounds
When one run cannot do it well: the context would overflow, the parts are independent and worth running in parallel, or different parts need different tools or instructions. Splitting has costs: each piece pays its own overhead, loses the context of the whole, and needs checking and combining. In a measured health report that fitted comfortably in one run, the single run scored 236 of 240 fields, a code split 210, and the model's own split 233 at 2.6 times the tokens. So I split for a reason, give each piece the context it needs, check each result, and design the join.

Deeper: One subtask in your decomposed pipeline keeps returning results about the wrong thing, and retrying does not help. What is going on?

How a strong answer sounds
Probably the subtask is ambiguous once separated from the whole, and the retry is the same request, so a deterministic model repeats the same answer. In a measured case "report on the service inventory" was read as "report the inventory of services" in every estate; the full task listed ten service names, which made the meaning obvious. I would rewrite the subtask brief to carry the context ("the service named inventory, one of ..."), make the retry include the specific failure, and keep the check on each piece. I would also ask whether the split is needed at all.

🧠 Key takeaways

  • Split for a reason: when the task fitted, one run scored 236 of 240 fields and every split did worse or cost more.
  • A piece loses the context of the whole: "report on the service inventory" failed in every estate.
  • Check each piece, and make the retry different from the attempt; an identical retry repeated the mistake.
  • The model's own split was correct (233) but fine-grained: 40 subtasks, 2.6 times the tokens.
  • Decompose when one run cannot hold the work, and pass results between dependent pieces explicitly.
