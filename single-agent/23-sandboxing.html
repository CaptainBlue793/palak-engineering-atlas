Sandboxing & Isolation

An agent that runs code runs code nobody reviewed. Usually the code is fine. Sometimes it is wrong in ways that matter: it loops forever, fills the disk, deletes the wrong folder. And if the agent reads untrusted text (Chapter 25), what it writes may not be what you asked for. A sandbox decides what that code can do, whatever it tries.

This chapter tests sandboxes the way you should test yours: with a suite of small, harmless probe scripts that each try one thing a sandbox should stop. That means reading a decoy file outside the work folder, reading a decoy secret from the environment, opening network connections, using too much memory, and so on. Twelve probes ran under five set-ups of increasing strictness on Linux (Ubuntu 24.04 under WSL 2). Then the data-analysis agent from Chapter 18 ran its twenty questions inside the strictest one.

  • Apply process limits: time, CPU, memory, processes, file size
  • Isolate files, network and processes with namespaces and bubblewrap
  • Test a sandbox with probes instead of trusting its configuration
  • Know what stronger isolation (containers, microVMs) adds

What can go wrong

The Python tool from Chapter 18 ran each script as a normal subprocess with a timeout and a clean environment. Under that set-up the probes could read a file in the user's home folder, list the Windows drive mounted at /mnt/c, write and delete files outside the work folder, connect to a service on the host and to the internet, allocate 2 GB of memory, start 300 processes, write a 500 MB file and see every process on the machine. Only two probes were stopped. The clean environment hid the decoy secret, and the timeout killed the endless loop. A plain subprocess runs as you, so it can do anything you can.

Process limits

The kernel enforces per-process limits (rlimits), set here with prlimit: 1 GB of address space, 64 processes, 100 MB per file, 10 seconds of CPU time. They stopped the 2 GB allocation (MemoryError), the 300 processes (refused after 21), the 500 MB file (File too large), and the endless loop at exactly 10 seconds of CPU, before the 15-second wall-clock timeout. Limits protect the machine from runaway code but not your data. Every file and network probe still succeeded.

prlimit --as=1073741824 --nproc=64 --fsize=104857600 --cpu=10 -- python script.py

Note what the process limit counts: --nproc counts all processes of the user, so the same limit allowed 21 new processes in one run and 63 in another, depending on what else was running. Give sandboxed code its own user, or a fresh user namespace, so the count starts from zero.

Containers

Containers are built from Linux namespaces: a process gets its own view of the file system, the network, the process list and the user ids. Adding unshare -rn (a new user namespace and an empty network namespace) stopped both network probes ("Network is unreachable", name resolution failed). Files were still exposed, because the file system was shared.

bubblewrap (bwrap) builds a whole sandbox from namespaces without root and without a daemon. Here it mounted /usr read-only, mounted only the work folder writable, gave the process fresh /tmp, /proc and /dev, unshared every namespace, cleared the environment, and killed the sandbox if the parent died. Combined with the same limits, it stopped all twelve probes. Files outside the work folder simply did not exist ("No such file or directory"); the home folder, the Windows drive and the host's processes were invisible (two processes visible: the sandbox's own first process and the probe).

bwrap --ro-bind /usr /usr --symlink usr/bin /bin --symlink usr/lib /lib --symlink usr/lib64 /lib64 \
      --ro-bind ~/sbx/venv ~/sbx/venv \                # the Python environment, read-only
      --bind ~/sbx/work /work --chdir /work \          # the only writable folder
      --proc /proc --dev /dev --tmpfs /tmp \
      --unshare-all --die-with-parent --new-session \  # own network, processes, users; no terminal
      --clearenv --setenv PATH /usr/bin --setenv HOME /work -- \
      prlimit --as=1073741824 --nproc=64 --fsize=104857600 --cpu=10 -- python -

Note the opposite approach that fails: mounting the whole root read-only (--ro-bind / /) and then hiding parts of it. On this machine that would still have exposed /mnt/c, the Windows drive, because WSL mounts it under the root. Start from nothing and add what the code needs.

Network and file rules

Decide both from the task. A data-analysis tool needs its input files and a folder to write to, and no network at all. A tool that installs packages needs the package index and nothing else, which means an egress proxy with an allow-list rather than "network on". Read-only mounts for code and libraries, one writable folder per session, no access to the home folder, the SSH keys or the cloud credentials, and no environment variables you did not set on purpose. When the agent needs to send data somewhere, give it a tool that does that one thing, rather than network access from its code.

Testing the sandbox

A sandbox configuration is a claim; the probes are the test. Each probe here is one harmless line or two that attempts something and prints ALLOWED or the error it got. Run the suite whenever the sandbox, the base image or the host changes, and treat an ALLOWED as a failing test. The suite caught two things a configuration review might have missed: the Windows drive under /mnt, and the shared process count.

Isolation did not cost the agent anything. The Chapter 18 agent, with its best tool (last value shown, sample rows in the description), answered 19 of 20 questions inside the bubblewrap sandbox, the same as outside it, with 22 scripts and no errors caused by the sandbox. Starting the sandbox added about 4 ms per run (11 ms against 7 to 9 ms for the lighter set-ups). A complete sandboxed pandas run took a median of 245 ms, against 443 ms for a plain subprocess on the Windows side, so the isolation was not the slow part.

Use case: how coding agents sandbox commands

Coding agents run shell commands all day, so their makers built sandboxes from the same parts. Anthropic's sandboxing for Claude Code, released in 2025, restricts commands to the project's folder and to approved network hosts. It uses bubblewrap on Linux and macOS's built-in Seatbelt sandbox on the Mac, with network access going through a proxy that enforces the allow-list. OpenAI's Codex CLI similarly uses Seatbelt on macOS and the Linux kernel's Landlock and seccomp features on Linux, with network access off by default. Hosted code sandboxes for agents, such as E2B, go a level stronger and start each session in its own Firecracker microVM, a lightweight virtual machine with its own kernel, which also protects against kernel bugs that namespaces share with the host. The pattern matches the measurement here: deny by default, allow a work folder and specific hosts, and enforce it below the code rather than in a prompt.

⚠️
Common mistakes
  • A timeout as the whole sandbox: it stopped 1 of 12 probes.
  • Mounting everything read-only and hiding parts, instead of starting empty and adding what is needed.
  • Network on "because pip needs it", instead of a proxy with an allow-list.
  • Credentials in the environment or home folder the sandbox can see.
  • Process limits counted against your own user, so they vary with what else is running.
  • Never testing the sandbox after the image or host changes.

Interview drill

Explain it simply: How would you let an agent run code safely?

How a strong answer sounds
Treat the code as untrusted and enforce limits below it. Resource limits for time, CPU, memory, processes and file size protect the machine. Namespaces give the code its own empty file system with one writable folder, no network unless needed, its own process list and no inherited environment. Tools like bubblewrap do that without root; containers or microVMs are stronger. In a measured test, a plain subprocess with a timeout stopped 1 of 12 harmless probe scripts, limits 5, limits plus no network 7, and bubblewrap with limits all 12, adding about 4 ms per run. The agent's accuracy was unchanged, 19 of 20.

Deeper: How do you know your sandbox works?

How a strong answer sounds
Test it like code. Keep a suite of small probes that each try one thing the sandbox should stop: read a decoy file outside the work folder, read a decoy secret from the environment, reach a local service and the internet, allocate too much memory, start many processes, write a huge file, loop forever, list other processes. Run it in CI whenever the image or host changes and fail on any success. Such a suite found two things I would have missed by reading the configuration: a host drive mounted under the root on WSL, and a process limit counted against the whole user.

🧠 Key takeaways

  • A plain subprocess runs as you: it stopped 1 of 12 probes.
  • Resource limits protect the machine (memory, processes, file size, CPU) but not your files or network.
  • Namespaces close the network; bubblewrap with limits stopped all 12 probes.
  • Start from an empty file system and add what the code needs.
  • The sandbox cost about 4 ms per run and no accuracy: 19 of 20 inside and out.
