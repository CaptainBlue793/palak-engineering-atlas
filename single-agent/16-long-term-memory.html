Long-Term Memory Across Sessions

Short-term memory (Chapter 15) keeps one session within the context window. Long-term memory carries facts from one session to the next: who is on call, which channel to use, what the user prefers. It means writing facts to a store, finding the right ones later and, hardest of all, changing them when the world changes. Facts that are never corrected make an agent confidently out of date.

This chapter measures four designs with qwen3:14b. Eight short sessions state facts and then change them: the on-call moves from Priya to Omar, a deploy freeze is lifted, the update channel moves, the cache cluster grows. Ten questions afterwards ask for the current facts. Then the same sessions are repeated with 296 unrelated facts mixed in, to see what changes at scale.

  • Decide what an agent should remember, and in what form
  • Write memories from a conversation with an extraction step
  • Recall them in full or by retrieval, and know the cost of each
  • Update and forget safely, and recognise destructive memory operations
  • Treat memories as data that can be wrong or planted

What to remember

Durable facts about the user, the team and their systems: names, rules, preferences, decisions. Not the conversation itself, not tool output, not things that are only true for today. Here is the whole input, eight sessions of one to three messages:

1  The on-call for db-main this week is Priya. · Our status page lives at status.shopco.example. · Payments is in a deploy freeze until Friday.
2  Rollbacks need approval from Tomasz in release engineering. · Checkout's error budget is 0.5 percent per month.
3  Please always post incident updates in #inc-checkout. · The cache cluster has 8 nodes.
4  Correction: the db-main on-call changed, it's Omar now, Priya is on leave. · The search team owns the gateway service now, not us.
5  We resized the cache cluster to 12 nodes. · Our weekly incident review is on Thursdays at 10:00.
6  The payments deploy freeze is lifted, they can ship again. · Tomasz is still the rollback approver.
7  Incident updates should now go to #inc-updates; #inc-checkout was archived. · The ticket prefix for incidents is INC.
8  Forget what I said about the status page address; it moved to status.shopco.example/live.

Five of the ten answers changed after they were first stated. With no memory the model answered 0 of 10. Seven times it said it did not know, which is the right behaviour. Twice it gave generic advice ("it depends on the organization's policies"). Once it guessed: "incident tickets typically use the prefix INC-" happens to match, but it was a convention, not a memory.

Writing memories

A memory write is a small model call after each message: extract the durable facts, one short sentence each. The 16 messages became 23 memories, because the model split compound messages: "Correction: the db-main on-call changed, it's Omar now, Priya is on leave" became three, "The db-main on-call has changed", "Omar is now the db-main on-call" and "Priya is on leave". Splitting is good for retrieval and, as the managed designs below show, risky for corrections.

def extract(message: str) -> list[str]:
    out = ask("Extract each durable fact in the message as a short standalone sentence, one per line. "
              "If none, reply NONE.", message)
    return [l.strip("-• ") for l in out.splitlines() if l.strip() and not l.startswith("NONE")]

memories.extend(extract(message))      # append-only: never edit, never delete

Recalling them

Append-only, all memories in the prompt, oldest first: 10 of 10. Both versions of every changed fact were there ("The cache cluster has 8 nodes", later "We resized the cache cluster to 12 nodes"), and the model took the later one every time. With 296 unrelated facts mixed in (dashboards, runbook pages, stand-up times), the store grew to 319 memories and about 4,200 prompt tokens, and the score was still 10 of 10. Order is doing real work here: the list is chronological, and the prompt says so.

Append-only, top 3 by word overlap with the question: about 80 prompt tokens instead of 4,200, and 8 of 10 at both sizes. Retrieval separates a fact from its correction. At scale, "Who is on call for db-main?" retrieved "The on-call for db-main this week is Priya" and two unrelated db-main facts ("db-main logs are kept for 30 days"), but not "Omar is now the db-main on-call". The model answered Priya. In the small run, the prefix question retrieved nothing about tickets and the model guessed. Retrieval needs to fetch every version of a fact together, by subject, with dates, or the newest one may not be among the results.

Updating and forgetting

The usual answer to a growing store is to let the model manage it: given the current memories and a new message, return operations (add, update a memory by id, delete one, or none) as structured output. That keeps the store small (9 memories in the small run, 79 at scale) and avoids old facts competing with new ones. It scored 9 of 10, then 8 of 10 at scale, and the misses all came from the same kind of message: one that retracts an old fact and states a new one.

message:  Incident updates should now go to #inc-updates; #inc-checkout was archived.
ops:      delete #5   (was: Incident updates for Checkout should be posted in the #inc-checkout channel.)
          # no add: the new channel is never stored

The model read "archived" and deleted, and the new channel was lost. Asked later where updates go, it answered "on the status page at status.shopco.example/live", built from a memory that was there. At scale the same message did the same thing. "The search team owns the gateway service now, not us" became a delete of an unrelated memory, "The gateway service account is svc-gateway-82", with no add. Asked who owns the gateway, it answered "the team whose service account is svc-gateway-305". A filler message, "db-main logs are kept for 30 days", deleted "The on-call for db-main this week is Priya". That was harmless here only because Omar had been added separately.

A two-step version, which extracts facts first and then decides operations one fact at a time (a simplified form of the design Mem0 uses), did worse: 8 of 10, then 7 of 10. Splitting a correction into separate facts made the retraction its own fact, and that fact then removed the new one. "The search team owns the gateway service" was added, then "We no longer own the gateway service" deleted it. At scale, "Incident updates should now go to #inc-updates" correctly updated the channel, and then "#inc-checkout was archived" deleted that updated memory. "The weekly incident review is at 10:00" replaced "Our weekly incident review is on Thursdays", losing the day.

def apply(memory: dict, ops: list[dict], message: str) -> None:
    for o in ops:
        if o["op"] == "add":
            memory[new_id()] = {"text": o["text"], "since": now()}
        elif o["op"] in ("update", "delete"):                  # supersede, never destroy
            old = memory[o["id"]]
            old["superseded_at"], old["because"] = now(), message
            if o["op"] == "update":
                memory[new_id()] = {"text": o["text"], "since": now(), "replaces": o["id"]}

Every lost fact here was lost by a destructive operation that nobody checked. The listing above is the design this suggests, not one measured in this chapter. Keep history and mark old memories superseded rather than deleting them, so a bad delete can be undone and audited. Show current memories by default. Flag a delete that comes with no add when the message states a new value.

Wrong memories

Memories outlive the conversation that wrote them, which makes mistakes durable. Every failure in this chapter was silent. The model answered from its memory store with the same confidence whether the store was right or not. Three habits help. Store where each memory came from (session, message, date) so it can be checked and explained. Let users see and correct what is remembered. Treat memory as untrusted input. A memory extracted from a web page or a document can carry an attacker's instruction into every later session (Chapter 25). Only write memories from the user's own messages, or review the others.

Use case: ChatGPT memory and Mem0

OpenAI began testing memory in ChatGPT in February 2024: the model saves short facts about the user ("prefers concise answers", "has a daughter") that carry into later chats, and users can view, delete or turn them off in settings. In April 2025 it was extended to draw on past conversations as well. The open-source Mem0 project (Chhikara and colleagues, 2025) describes the managed design measured here: an extraction step, then an update step in which a model compares each new fact with similar stored memories and chooses ADD, UPDATE, DELETE or NOOP. Both show the same concerns as this chapter: memories need to be visible and correctable, because the model's decisions about what to change are not always right. In 2024 the security researcher Johann Rehberger showed that a prompt injection in content ChatGPT read could plant false memories that persisted into later conversations.

⚠️
Common mistakes
  • Hard deletes chosen by the model with no check, history or undo.
  • Retrieval that returns a fact without its later correction.
  • No order or dates on memories, so old and new versions look equally current.
  • Splitting corrections into fragments that are then applied one by one.
  • Writing memories from tool output or web pages, which lets anyone write to the agent's memory.
  • Memories users cannot see or correct.
🎤
Interview drill

Explain it simply: How would you give an assistant memory that lasts between conversations?

How a strong answer sounds
After each user message, extract durable facts as short sentences with their source and date, and store them. At answer time, give the model the relevant ones, ordered by date so it can tell a correction from the original. In a measured test with eight sessions of changing facts, keeping every memory in order scored 10 of 10, even with 319 memories, at about 4,200 tokens. Retrieving only the top 3 by word overlap scored 8, because a fact could be retrieved without its correction. As the store grows I would retrieve by subject and fetch all versions together, and let users see and edit what is stored.

Deeper: You let the model manage its memory with add, update and delete. What goes wrong, and how do you make it safe?

How a strong answer sounds
The model's operations are decisions and can be wrong. Measured on messages that retract one fact and state another, like "updates should now go to #inc-updates; #inc-checkout was archived", it often deleted the old memory and never added the new one, and later answered with an invented channel. Splitting messages into facts first made it worse, because the retraction half deleted the new fact. I would make deletes soft (mark superseded, keep history), log every operation with the message that caused it, flag a delete with no add when a message states a new value, and test memory on corrections specifically, not only on new facts.

🧠 Key takeaways

  • Append-only memory, shown in order, answered 10 of 10, even at 319 memories (about 4,200 tokens).
  • Top-3 retrieval scored 8: a fact can be retrieved without its correction.
  • Model-managed memory lost facts by deleting without adding: 9, then 8 of 10.
  • Extracting facts first and managing them one by one did worse, 8 then 7, as halves of a correction cancelled out.
  • Supersede instead of delete, keep sources and dates, and only write memories from the user.
