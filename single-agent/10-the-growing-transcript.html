The Growing Transcript

Everything an agent does stays in its transcript: the task, every call, every result. That is how it remembers what it has learned, and it is also how it runs out of room. P4 measured the cost of that growth, step by step. This chapter measures the failure at the end of it: what happens when the transcript no longer fits the context window.

The task was a sweep: check the error logs of all ten services and report the most frequent error of each. qwen3:14b ran it on six incidents with the log tool returning four shapes of output: 60 raw log lines per service at the course's usual 16k-token context, the same at 32k, only the first 15 lines, and aggregated counts. The model fetched all ten logs in one step, in parallel, so the whole problem arrived at once: one prompt of about 22,000 tokens, or 600.

  • Shape large tool outputs so they fit and still carry the answer
  • Truncate results safely when you must

What accumulates

Four things: the system prompt and tool definitions (fixed, re-sent every step), the task, the model's own messages (small: a tool call is about 20 tokens), and tool results. The last dominate. In this sweep each raw log of 60 lines was about 2,200 tokens; ten of them made 22,000. The same information as aggregated counts ("714 x 503 from payments: upstream request failed") was about 40 tokens per service. What you choose to return from a tool decides almost everything about a transcript's size.

Tokens per step

A step adds its tool results to every later request. In P4's eight-step run each log added about 1,600 tokens and the requests together read 35,818 tokens. Here the model asked for all ten logs in its first step, the parallel calls Chapter 2 never saw, so the second request carried everything: 22,000 tokens of raw logs, 6,000 of first-15-lines, 600 of counts. Fewer steps, same transcript.

Latency per step

Prefill time grows with the prompt. Reading the 22,000-token prompt took 8.8 s at the 32k setting; the 6,000-token one 1.7 s; the 600-token one 0.1 s. Those seconds are paid on every step that carries the transcript, and with the prompt cache only the new part is reread (P4), so in a longer run the cost of a large result is paid in full once and then in cache memory and window space for the rest of the run.

Big tool outputs and the context window

At the course's usual num_ctx of 16,384, the 22,000-token prompt did not fit. Ollama did not raise an error. It dropped the start of the prompt to make it fit, and reported 15,662 prompt tokens. The start was the system prompt, the task and the first services' logs. The model answered as if asked to summarise some logs: a list of "client closed request" counts for auth, search and orders, in its own format, with checkout's real failure (the one the task was about) never mentioned. 0 of 60 service lines were right, across six incidents. Raising num_ctx to 32,768 made everything fit and gave 54 of 60, at 8.8 s of prefill and a larger memory reservation for the context (P1). The only trace of the failure in the 16k run was the prompt token count, a few hundred tokens below the context limit when the transcript should have been much larger.

r = ollama.chat(model="qwen3:14b", messages=messages, tools=tools, options={"num_ctx": 16384})
if r.prompt_eval_count >= OPTIONS["num_ctx"] - 1024:                    # the server is at its limit: assume it dropped something
    raise ContextOverflow(f"prompt reached {r.prompt_eval_count} tokens; compact the transcript before continuing")
# better: count before sending, and compact or refuse then (Chapter 11)

Truncating results

Cutting each tool result is the obvious fix and the risky one. Keeping only the first 15 of 60 lines fitted easily (6,000 tokens) and scored 35 of 60: when a service's errors were not among its first 15 lines, the model reported "no errors" for it, reasonably, from what it had been shown. Aggregated counts, computed by code from all 60 lines, fitted in 600 tokens and scored 60 of 60. If you must cut, cut in a way that keeps the answer: summarise in code (counts, top-N, first-seen times, as in Chapter 4), say what was cut ("45 more lines not shown, 12 of them errors"), and offer a way to get more (a tool argument for a page or a filter).

def get_errors(service: str) -> str:
    lines = logs.last_hour(service)
    counts = collections.Counter(message(l) for l in lines if " ERROR " in l)
    if not counts:
        return f"{service}: no errors in {len(lines)} lines"
    return f"{service} errors, last hour ({len(lines)} lines read):\n" + "\n".join(
        f"  {n} x {msg} (first seen {first_seen(lines, msg)})" for msg, n in counts.most_common(5))

Use case: context windows and "context rot"

Context windows have grown fast: from 4,096 tokens for GPT-3.5 in 2022 to hundreds of thousands and then a million or more in some 2024 and 2025 models. Larger windows move the cliff measured here but do not remove the slope before it. Research such as "Lost in the Middle" (Liu and colleagues, 2023) showed models using information at the start and end of long contexts better than the middle, and later benchmarks of long-context models found accuracy falling as inputs grew, well before the advertised limit, a decline practitioners came to call context rot. Hosted APIs usually reject a request that exceeds the window with an error instead of truncating, which is safer; local servers often truncate, as here. Either way, an agent that keeps every raw tool result is spending its window on the wrong things, which is the subject of the next chapter.

⚠️
Common mistakes
  • Returning raw logs and pages because the model "can read them": 22,000 tokens for an answer that needed 600.
  • Not checking prompt tokens against the window, so truncation goes unnoticed.
  • Assuming the server will error on overflow; this one silently dropped the task.
  • Truncating results blindly (first N lines) and losing the lines that mattered.
  • Raising the window as the only fix, paying memory and seconds for tokens the task did not need.
  • Testing with small inputs only, then meeting the cliff in production.

Interview drill

Explain it simply: What happens when an agent's transcript gets longer than the model's context window?

How a strong answer sounds
It depends on the server. Hosted APIs usually reject the request with an error. Many local servers truncate, often by dropping the oldest tokens, which are the system prompt and the task. Then the model answers a question it can no longer see, fluently and wrongly, and nothing raises an error. In a measured sweep, a 22,000-token transcript sent to a 16k window produced zero correct lines out of sixty. So I count tokens before sending, check the reported prompt tokens after, and keep transcripts small in the first place by shaping tool output.

Deeper: An agent's tool returns large log dumps and the transcript keeps overflowing. Raise the context window, truncate the output, or something else?

How a strong answer sounds
Change what the tool returns. A larger window worked in a measured case (54 of 60 lines right at 32k against 0 at 16k) but cost 8.8 seconds of prefill per request and more memory. Truncating to the first lines fitted but lost answers that were further down, 35 of 60. Aggregating in code, counts per message with when each started, fitted in 600 tokens and got 60 of 60. I would return a compact summary by default, say what was omitted, and give the tool a parameter to fetch a page or filter when the agent needs the raw lines.

🧠 Key takeaways

  • Tool results dominate a transcript: ten raw logs were 22,000 tokens, ten summaries 600.
  • Over the window, this server silently dropped the start, including the task: 0 of 60 lines right.
  • Check prompt tokens against the limit; count before sending.
  • A bigger window fixed it (54 of 60) at 8.8 s of prefill per request.
  • Summarise in code instead of truncating: first-15-lines got 35 of 60, aggregated counts 60 of 60.
