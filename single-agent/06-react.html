Reasoning and Acting: ReAct

ReAct, the pattern under almost every agent, interleaves thinking with acting: the model writes a thought about what it knows and what to do next, takes an action, reads the observation, and thinks again. Two things have changed since it was introduced. Tool calling became native, so many models now act without writing any thought at all. And reasoning models arrived, trained to think at length before every reply. Both raise the same question: what does the thinking actually buy?

This chapter measures it with qwen3:14b, which can run with its thinking on or off. Four ways of running the same agent (act only, ReAct-style written thoughts with two ways of keeping them, and native thinking) faced three kinds of task: 12 incident investigations, 12 comparisons that need a little arithmetic, and 8 questions about which services an outage would affect. The answer turned out to depend less on the thinking than on what it had to think about.

  • Explain what a reasoning model does differently, and how to switch it on and off
  • Tell tasks where thinking helps from tasks where it only costs

Act-only agents

An act-only agent replies with tool calls and nothing else until it answers. With native tool calling this is the default: asked to investigate, qwen3:14b emitted a bare call at almost every step. Any reasoning happens inside the model, invisibly, for the length of one short reply. For many tasks that is enough. On the 12 investigations an act-only agent with a clear method solved 10; on the 12 comparisons (which of checkout's dependencies is slowest, and by how many milliseconds) it solved all 12, subtracting four-digit latencies correctly.

Thought, action, observation

ReAct asks the model to write its reasoning as text before each action. In the original text-protocol agents (Chapter 3) the thought was part of the format. With native tool calling you have to ask for it, and the model may not oblige. The system prompt here added: "Before every tool call, write one or two sentences: what you learned from the last result and what you will check next and why." Across 140 steps that called a tool, in the investigations and comparisons, qwen3:14b wrote such a sentence once: no more often than the act-only agent did unprompted (twice in 119). It went straight to the call. The instruction still changed behaviour, for the worse: investigations fell from 10 to 8 of 12, and one comparison misread a latency.

Keeping or stripping the thoughts from the history made no difference here, because there were almost no thoughts to keep. It matters with other models and templates: in qwen3's Ollama template an assistant message with text renders the text and drops the tool calls (P2), so a loop that keeps ReAct thoughts can erase its own record of what it called.

Reasoning models

A reasoning model is trained to produce a long chain of thought before its reply, in a separate channel that most APIs return apart from the answer. qwen3 does this when thinking is on; Ollama exposes it as think=True and returns the reasoning in message.thinking. Thinking is not free text the agent loop has to manage: it is generated, returned and normally not sent back in later requests.

r = ollama.chat(model="qwen3:14b", messages=messages, tools=schemas, think=True, options=OPTIONS)
print(len(r.message.thinking))      # thousands of characters of reasoning
print(r.message.tool_calls)         # then the same kind of call an act-only model would make
print(r.eval_count)                 # output tokens include the thinking: this is what you pay for

When thinking helps

On the investigations and comparisons, thinking changed nothing that mattered: 10 of 12 investigations (a different pair failed: it fixed the "cache stampede" red herring of Chapter 1 and missed another) and 12 of 12 comparisons, the same as act only. The third task was harder: "If db-main went down completely, which other services would be affected, directly or through other services?" The tools only report what a service calls, downstream; the question asks who calls it, upstream, through several levels. Answering it means calling get_dependencies on many services and inverting the graph.

  • Act only: 0 of 8 exactly right. It mostly listed services in the wrong direction (what db-main's callers call, or everything it had seen). Recall 35%, precision 28%.
  • Thinking on: 0 of 8. Better (recall 48%, precision 55%), at 75 s and 6,000 output tokens per question, but it reasoned about a graph it had only partly fetched.
  • Act only, plus a get_dependents tool that returns a service's callers: 0 of 8. It found more of the right services (recall 65%) and added many wrong ones.
  • Thinking on, plus get_dependents: 6 of 8 exactly right, with no wrong services named in any answer (precision 100%, recall 91%), in 34 s, less than half the time thinking took without the tool.

Neither the better tool nor the thinking was enough alone. The tool turned an impossible inversion into a walk up the graph; the thinking kept track of the walk and stopped listing services that were not on it. Thinking helps where there is real reasoning to do over the right information. It does not substitute for the information.

Cost of reasoning

Thinking is paid for in output tokens, the slow and expensive kind (P4). Averaged over the investigations, thinking multiplied output tokens by about ten (2,353 against 228) and time by about nine (29 s against 3 s). On the impact questions without the dependents tool it averaged 75 s, and one question took 143 s. On a hosted reasoning model the same ratio applies to the bill. Use it where measurement shows it pays: hard multi-step reasoning over data the agent can actually get. Elsewhere, leave it off or route only the hard steps to it (Chapter 22).

Use case: ReAct, then reasoning models

The ReAct paper (Yao and colleagues, 2022) showed that interleaving written reasoning with actions beat both reasoning alone and acting alone on question answering over Wikipedia and on text-game tasks: thoughts let the model plan, track progress and recover from failed searches. Two years later, OpenAI's o1 (September 2024) and then open models such as DeepSeek-R1 (January 2025) and Qwen3 (April 2025) moved that reasoning inside the model, trained with reinforcement learning to think at length before replying; Qwen3 made it switchable per request. Both generations found the same limit this chapter measured: reasoning improves how a model uses information, and is most valuable on problems that need many dependent steps, but it cannot recover information the agent never fetched, and it costs output tokens on every step where it is on.

⚠️
Common mistakes
  • Turning thinking on everywhere because it sounds smarter: ten times the tokens for the same accuracy here.
  • Asking for ReAct-style thoughts with native tool calling without checking the model writes them, or what the request does to accuracy.
  • Keeping thoughts in history on a template that then drops the tool calls.
  • Expecting reasoning to stand in for a missing tool, like a way to look up callers.
  • Comparing thinking on and off on easy tasks only, where both succeed.
  • Ignoring the latency: one impact question with thinking took 143 seconds.

Interview drill

Explain it simply: What is ReAct, and how does it relate to today's reasoning models?

How a strong answer sounds
ReAct is the pattern of interleaving reasoning and actions: the model writes a thought, takes an action such as a tool call, reads the observation and thinks again, which helps it plan and recover from mistakes. Early agents did this through a text format the program parsed. Today tool calls are native, and reasoning models do the thinking internally before each reply, often switchable per request. In practice many tool-calling models act without written thoughts, so the question becomes when to turn internal reasoning on; I measure it per task type because it costs roughly ten times the output tokens.

Deeper: Your agent gives wrong answers on a class of multi-step questions. Someone proposes switching to a reasoning model. What would you check first?

How a strong answer sounds
Whether the agent can get the information the question needs. In a measured case, questions about which services an outage affects needed the callers of a service, but the tools only listed what each service calls. Reasoning alone got none of eight exactly right; adding a tool that returns callers, with reasoning on, got six of eight with no wrong services named, in half the time reasoning took without the tool. So I would read failing traces, check whether the missing step is reasoning or data, add or reshape tools first, and then compare reasoning on and off on that task set, routing only the hard questions to the expensive mode.

🧠 Key takeaways

  • With native tool calls the model acted without written thoughts: asked for them, it wrote one in 140 steps, and still lost two investigations.
  • Thinking matched act-only accuracy on investigations and comparisons at about ten times the tokens and time.
  • On impact questions, thinking alone and a better tool alone both scored 0 of 8; together, 6 of 8 with no wrong services.
  • Reasoning improves the use of information; it does not replace fetching it.
  • Turn thinking on per task type, where measurement shows it pays.
