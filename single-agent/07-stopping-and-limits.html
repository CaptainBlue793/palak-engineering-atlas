Stopping, Step Limits & Loops

Every agent loop needs to end, and the textbook danger is a loop that does not: an agent that calls the same failing tool forever, or wanders until the step limit and the bill both run out. That danger is real and the defences are cheap. But measuring an agent on tasks it cannot finish showed a different, quieter failure much more often: an agent that stops promptly, confidently, with an answer it made up.

This chapter gives qwen3:14b three kinds of impossible task: every log lookup fails because the log backend is down; the guilty service has no deploy history; the user asks about a "billing" service that does not exist. Each ran under a plain loop, with an honesty instruction and a visible step budget, and with a check that rejects non-answers. The ordinary investigations ran alongside, to see what the changes cost.

  • Recognise a final answer, and a reply that only looks like one
  • Detect repeated actions and runaway loops
  • Set step, time and token limits, and report when one is hit
  • Ask an agent to give up well: say what it checked and what is missing
  • Know which stopping problems prompts can fix and which need code

A final answer

The loop ends when the model replies without a tool call. That reply can be an answer, an honest "I could not find out", an empty string, or an announcement of something it meant to do next. Chapter 2 showed the announcement case ("I will now retrieve the deployment history") when the loop was broken. Here, with a correct loop, a check that sent such replies back to the model never fired in 108 runs. The replies that mattered were all real answers; the question was whether they were true.

Repeated actions

A doom loop is an agent repeating the same call, usually a failing one, hoping for a different result. It is easy to detect: keep a count of each tool name with its exact arguments, and after the second or third repeat, append a note to the result telling the model it has already tried this. In these runs it barely happened. With every log lookup failing, the agent tried the logs once or twice per service, then moved on or stopped. Across 108 runs no single call was repeated more than three times, and no run came near the 30-step limit: the longest took 18 steps. Keep the detector and the limit anyway. They cost nothing on a good day, and a different model, tool or error message can turn a polite agent into an expensive one.

seen = collections.Counter()
for call in reply.tool_calls:
    key = call.function.name + json.dumps(call.function.arguments, sort_keys=True)
    seen[key] += 1
    result = dispatch(tools, call)
    if seen[key] >= 3:
        result += ("\n[loop guard] You have made this exact call " + str(seen[key]) + " times with the same result. "
                   "Try something different, or stop and report what you know and what is missing.")

Step and time limits

A step limit caps the number of model calls; a time limit caps wall-clock time, which also covers slow tools; a token budget caps cost directly. Set each from what a normal run needs (here, 6 to 12 steps) with room to spare, and make hitting one a visible outcome: the loop should return "stopped at the step limit after checking X and Y", never an empty string the caller mistakes for an answer. Telling the model its budget ("You have at most 30 tool steps") is also worth doing. Combined with the honesty instruction below, it shortened the failing-logs runs from 10 steps to 6.

Token budgets

Steps are a rough proxy for cost, because a step late in a run reads the whole transcript (P4). For long runs, budget prompt and output tokens directly from the counts the server returns, and stop, or summarise and continue (Chapter 15), before the budget runs out. A budget that is only checked after the call that exceeded it is still a budget, as long as it is checked every step.

Giving up well

Here is what the agent did when it could not succeed:

  • Log backend down. A plain loop said it could not determine the cause 4 times in 6; the other two answers rambled without a conclusion. With the instruction "If you cannot find the answer, stop and say so: list what you checked and what is missing. Never guess a cause or a version you did not see in a tool result", all 6 gave a clear report of what had failed, in 6 steps instead of 10.
  • No deploy history for the guilty service. The plain loop named a version anyway 3 times in 6; with the instruction, 2 times in 6. In one of those the agent had been led to the wrong service by a misleading error, then blamed a real deploy there: a wrong answer for a reason the instruction could not reach.
  • "Billing is failing", where no billing service exists. In all 18 runs across the three designs, the agent never said billing did not exist. It investigated the services that do exist and, in 15 of the 18, blamed a deploy on one of them: an unrelated, harmless deploy, stated as the cause. Adding the list of services and "If the user names a service that is not in this list, say so and stop before investigating" changed nothing: 6 of 6 still investigated something else.

Instructions help an agent give up well when it notices it is stuck. They do little when it does not notice, as when it quietly substitutes a question it can answer for the one it was asked. That case needs a check in code before the loop starts: resolve every service the task names against the real list, and stop with a clear message if one is unknown. A ten-line check catches all six billing requests by construction; the model, given the same list, caught none.

def preflight(task: str) -> str | None:
    named = set(re.findall(r"\b([a-z][a-z-]+)\b(?= (?:is|service|has|was)\b)", task.lower()))
    unknown = named - set(SERVICES) - COMMON_WORDS
    if unknown:
        return f"There is no service called {', '.join(sorted(unknown))}. Services: {', '.join(SERVICES)}."
    return None                       # fine: run the agent

Use case: Auto-GPT's endless loops

Auto-GPT, an open-source project that became the most-starred new repository on GitHub in spring 2023, let GPT-4 pursue a goal by planning, calling tools and critiquing itself in an unbounded loop. Its users quickly discovered the failure this chapter's limits are for: agents repeating the same search, rewriting the same file, or re-planning in circles, sometimes until their API budget ran out. The project added a "continuous mode" warning, step limits and ways to cap spending, and the episode shaped how later agents were built, with explicit limits, budgets and clear terminal states. Today's models loop far less, as the runs here show; what Auto-GPT's users also saw, and this chapter measured more often, is an agent declaring success on a task it had not done.

⚠️
Common mistakes
  • No step, time or token limit, or a limit that returns an empty answer when hit.
  • Only guarding against loops and not checking whether the confident answer is grounded.
  • Expecting the prompt to catch unknown entities; 6 of 6 runs ignored a service list and a stop rule.
  • No instruction on how to give up, so failure looks like a vague essay.
  • Hiding the budget from the model, which then cannot plan within it.
  • Measuring agents only on tasks they can complete.

Interview drill

Explain it simply: How do you make sure an agent loop always ends, and ends usefully?

How a strong answer sounds
Three hard limits in code: steps, wall-clock time and tokens, each returning an explicit "stopped at the limit" result that says what was done. A repeat detector that notices identical calls and tells the model to change approach. An instruction in the prompt for how to give up: say what was checked and what is missing, never guess. And checks on the final reply: it should be a real answer or a real failure report, not an empty string or an announced next step. Then I would test it on tasks the agent cannot finish, because that is where both loops and invented answers show up.

Deeper: Users report your incident agent confidently blames a deploy for a service that does not exist. What happened and how do you fix it?

How a strong answer sounds
The agent substituted a question it could answer for the one it was asked: it investigated the services that do exist and reported a cause there. In a measured version, it did so in 15 of 18 runs, never once saying the named service did not exist, and giving it the service list with an explicit stop rule did not change that. The fix is in code: before the loop starts, resolve every entity the request names against the system of record and stop with a clear message if one is unknown; inside tools, return explicit "no such service" errors; and add these requests to the evaluation set, scored on refusing rather than answering.

🧠 Key takeaways

  • No run came near its 30-step limit; the common failure was a confident made-up answer, not a loop.
  • Keep step, time and token limits and a repeat guard anyway, with explicit results when they trigger.
  • An honesty instruction plus a visible budget gave clean "could not determine" reports when tools failed, in fewer steps.
  • When the agent did not notice it was stuck, as with a non-existent service, prompts failed 18 times in 18.
  • Validate the task's entities in code before the loop starts.
