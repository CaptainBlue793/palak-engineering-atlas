Evaluating Agents: Outcomes & Trajectories

Every chapter so far has graded the agent with a check written for it: the right root deploy named, the right rollback made, one refund issued. That is evaluation, and choosing the check is most of the work. Grade the wrong thing and an agent that refunds customers twice scores perfectly. This chapter compares the ways of grading agent runs on runs whose true outcome is known.

The material is 48 recorded runs from earlier chapters. There are 36 incident runs with write tools (Chapter 24), where the simulator knows whether the incident was fixed. There are also 12 refund conversations (Chapter 19), where the payment ledger knows how many refunds were issued. Each run was graded by its final state, by a string check on the answer, and by qwen3:14b as a judge given the answer only, the whole trajectory, or the trajectory plus a reference solution.

  • Define task success as a check on the world, not on the words
  • Grade by final state wherever you can
  • Use trajectory metrics to tell apart runs with the same outcome
  • Know when a model judge works, and when it cannot
  • Read agent benchmarks for what they actually measure

Task success

Success is a property of the world after the run: the incident is fixed, the order is refunded once, the tests pass, the file contains the right numbers. The agent's last message is a claim about the world. Some checks read the claim: "does the answer name the version?", or a model asked "was the task done?". Others read the world: the simulator's state, the ledger, the database. The two can disagree in either direction, and on these 48 runs they did both.

The string check from earlier chapters (the root version must appear in the answer) agreed with the true outcome on 27 of 36 incident runs. All nine disagreements were runs that fixed the incident but did not repeat the exact version in the final message. It never passed a failed run, but it failed nine good ones. String checks on answers measure how the agent reports, which is worth knowing, but it is not the outcome.

Checking final state

The strongest check reads the system the agent changed. For the incidents: was the culprit deploy rolled back? For the refunds: how many refunds does the ledger hold for this order? The refund runs show why this matters. In six of them the first refund call succeeded but its reply timed out, the agent retried, and the customer was refunded twice. In every one the agent's final message said the refund "has been successfully issued". Only the ledger showed two.

def grade_refund(order_id: int, ledger) -> bool:
    """Success is a fact about the payment system, not about the conversation."""
    return len(ledger.refunds(order_id=order_id)) == 1

def grade_incident(world) -> bool:
    return world.rolled_back(world.root, world.culprit_version) and world.error_rate("checkout") < 1.0

Final-state checks need an environment you control and can inspect: a simulator, a test database, a sandbox with a ledger. That is why agent benchmarks are built around such environments (Chapter 28).

Trajectory metrics

Two runs with the same outcome can differ in everything else. All three approval policies fixed 11 of 12 incidents, but without approval the agent made 11 unnecessary changes to production on the way, and with approval none. A success rate cannot see that; trajectory metrics can. Count steps and tool calls, the cost of a run (Chapter 31). Count repeated identical calls, a sign of looping, which ranged from 1 to 5 per policy. Count writes that were not needed, the risk of a run, and calls to tools outside the task's scope. Report them next to the success rate, and set limits on the ones that matter: "solves 11 of 12" and "solves 11 of 12 while restarting three services it did not need to" are different agents.

Model as judge

On the 36 incident runs all three judges agreed with the final state, 36 of 36: given the answer only, given every tool call, and given a reference ("the cause was v4.18.1 of payments; the fix is to roll back exactly that deploy"). The three failures were visible in the transcript. One run ended with no answer at the step limit; two ended with "I will now check the deploys…" and nothing more.

On the 12 refund runs the judges failed. Given only the agent's last message, the judge passed all six double refunds and also failed five of the six correct runs. In those runs the last message was a pleasantry ("You're welcome! If you need any further assistance…") sent after the refund had been confirmed earlier. Given the whole conversation, the judge passed all six double refunds. Given the conversation and the rule "correct means refunded exactly once", it still passed all six, and explained: "The refund was successfully issued after the initial timeout. The order was refunded exactly once." The transcript showed a timeout and then a success. Nothing in it said the timed-out call had also gone through, so no reader of the transcript, model or person, could have known. Final state: 12 of 12. Every judge: 6 of 12 or worse.

A judge can only grade what is in front of it. It is useful for qualities that live in the text (was the answer clear, did it cite evidence, was it polite) and for outcomes the transcript fully shows. It cannot see side effects the transcript does not record. Grade by state when you can, by a judge when you must, and check the judge against state on a sample.

What benchmarks measure

Read a benchmark as a definition of success. SWE-bench counts a task solved when the repository's hidden tests pass after the agent's patch: a final-state check, with the tests as the state. τ-bench checks the database at the end of a customer-service conversation against the expected state, and reports pass^k, success on every one of k attempts (Chapter 29). WebArena checks the web application's state or the answer string, depending on the task. Each measures one thing well and misses others: a patch that passes the tests but is unreadable, a conversation that reached the right state rudely. Before trusting a score, read what counts as success, what the agent was allowed to see, and whether the check could be passed without doing the task.

Use case: SWE-bench Verified

SWE-bench (Jimenez and colleagues, 2023) gave agents real GitHub issues from popular Python repositories and counted an issue resolved if the project's own tests, including tests added with the real fix, passed after the agent's patch. This is a final-state check, which made it convincing. In 2024 OpenAI worked with professional developers to review 1,699 of the tasks and found that many were underspecified, or that their tests rejected valid solutions. The result was SWE-bench Verified, 500 tasks that reviewers judged fair and solvable. The lesson matches this chapter: a state-based check is only as good as the state it checks. Here the ledger was perfect and the judges were blind; in SWE-bench, flawed tests made some correct patches look like failures until people audited them.

⚠️
Common mistakes
  • Grading the agent's claim instead of the system it changed.
  • Using a judge for side effects the transcript does not record.
  • Grading "the final message" without checking which message that is.
  • Reporting success rate alone, hiding unnecessary or risky actions.
  • Never auditing the judge against ground truth.
  • Quoting a benchmark score without reading its definition of success.

Interview drill

Explain it simply: How would you evaluate an agent that takes actions?

How a strong answer sounds
Run it on tasks in an environment I control and can reset, and grade the final state of that environment, not the agent's description of it. Next to the success rate, report trajectory metrics: steps, repeated calls and unnecessary writes. Two policies in a measurement both fixed 11 of 12 incidents, but one made 11 unneeded changes on the way. Use a model judge only for qualities in the text, and check it against state on a sample.

Deeper: Your model judge says the support agent succeeds 100% of the time, but customers complain. What might be wrong?

How a strong answer sounds
The judge may be grading claims the transcript cannot verify. In a measured case, six conversations refunded customers twice: the first call succeeded but timed out, and the agent retried. Every judge passed them, including one given the full transcript and the rule "refunded exactly once", because nothing in the transcript showed the first call had worked. Only the payment ledger did. I would add state checks against the systems of record, grade the right message rather than the last one, and audit the judge against those checks.

🧠 Key takeaways

  • Success is a fact about the world; grade final state wherever you can.
  • A string check on answers failed 9 good runs that worded the result differently.
  • Judges matched the truth on all 36 incident runs, where failures were visible in the text.
  • On refunds every judge passed all six double refunds; only the ledger saw them.
  • Report trajectory metrics too: same outcome, 11 unneeded changes versus none.
