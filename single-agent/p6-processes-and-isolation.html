Processes, Files & Isolation Basics

When an agent reads a file or runs a command, it does so as your program, with your program's rights. It can open any file your user can open, read every environment variable you have set, use as much memory and CPU as the machine will give, and connect anywhere on the network. The model does not know any of that, and it does not need to be malicious to hurt you. A wrong path or a loop with no end is enough.

This chapter is about the operating-system controls that narrow what a process can do: keeping file access inside a folder, choosing what a child process inherits, and putting limits on memory, CPU, disk and network. Each is measured: path checks against ten escape attempts on Windows, and limits on Linux (Ubuntu under WSL) with prlimit and unshare.

  • Explain what an agent's process can reach by default
  • Keep a file tool inside its workspace, including against links
  • Start child processes with an explicit environment, without your secrets
  • Cap memory, CPU time and file size, and cut off the network
  • Say what a container adds to these controls

Processes and permissions

A process is a running program with its own memory, a user it runs as, a current directory, a set of environment variables and open files. The operating system checks every file open, network connection and process start against that user's rights. An agent therefore has exactly the rights of whoever started it. On a developer's laptop that usually means the home folder with its SSH keys and cloud credentials, the source code of every project, and the whole network. Measured: a plain Python process on Linux read /etc/passwd and listed the home folder without any error, and on Windows it read C:\Windows\win.ini. Nothing was wrong; that is simply the default.

Working directories

Giving a file tool a workspace folder is the first narrowing, and it is easy to get wrong. A path from the model is joined to the workspace, and the result must be checked to still be inside it. Three versions of that check, against ten paths:

  • os.path.join only (no check): read the secrets file through .., through sub/../.., through a backslash, through an absolute path, and the Windows system file. Seven of eight escape attempts succeeded.
  • abspath then startswith(root): stopped the obvious ones, but let through two. A neighbouring folder whose name starts with the same letters (ws2 next to ws) passes a string-prefix check. And a directory junction inside the workspace that points outside (a Windows link any user can create, like a symbolic link on Linux) leads straight to the secrets.
  • resolve() then is_relative_to(root): blocked all eight. resolve follows links and collapses .. before the comparison, and is_relative_to compares whole path components, not characters.
from pathlib import Path

ROOT = Path("workspace").resolve()

def safe_path(name: str) -> Path:
    path = (ROOT / name).resolve()                  # follows links, removes ".."
    if not path.is_relative_to(ROOT):             # whole components, so "ws2" is not inside "ws"
        raise PermissionError(f"{name}: outside the workspace")
    return path

A check in your tool only covers your tool. Any command the agent runs in a shell can still cd ... That is why code execution needs the operating-system limits below, and a sandbox (Chapter 23), rather than path checks.

Environment and secrets

Environment variables are where API keys usually live, and a child process inherits all of them by default. Measured: with PAYMENTS_API_KEY set in the agent's process, a child Python process started normally saw all 82 of its variables, the key included. Started with an explicit env= of only PATH and SYSTEMROOT, it saw 2 and no key. An agent that runs code the model wrote should never hand that code its own credentials; a model asked to "debug the connection" may well print the environment.

SAFE_ENV = {"PATH": os.environ["PATH"], "SYSTEMROOT": os.environ.get("SYSTEMROOT", ""), "HOME": str(ROOT)}
subprocess.run(args, cwd=ROOT, env=SAFE_ENV, capture_output=True, text=True, timeout=30)

Resource limits

The kernel can cap what one process may use. On Linux, prlimit (or resource.setrlimit from Python) sets per-process limits. Each one turned a runaway into a clean, readable failure:

  • Memory (--as, address space): uncapped, the script took 800 MB without complaint. Capped at 512 MB, Python raised MemoryError when it tried to reach 500 MB, and stopped at 400 MB.
  • CPU time (--cpu): an endless loop was still running after 10 seconds. Capped at 2 seconds of CPU, the kernel killed it at 2.0 s.
  • File size (--fsize): a 50 MB write succeeded; capped at 10 MB it failed with OSError: [Errno 27] File too large.
prlimit --as=536870912 --cpu=2 --fsize=10485760 -- python3 agent_script.py
# or inside Python, in the child before exec:
# resource.setrlimit(resource.RLIMIT_AS, (512 * 2**20, 512 * 2**20))

Windows has no setrlimit; the equivalent is a job object, which caps memory and CPU for a group of processes, and it is what containers use on Windows. Limits cover one process; a program that starts many processes needs a limit on the group, which is what cgroups provide on Linux.

Containers in one page

A container is an ordinary process that the kernel shows a restricted view of the system. Namespaces give it its own view of files, processes, network and users; cgroups cap the memory, CPU and process count of the whole group. You can feel one of those pieces directly: unshare --user --map-root-user --net starts a program in a new, empty network namespace. The same connection that succeeded from a plain process in 20 ms failed at once with Network is unreachable. Container runtimes such as Docker and Podman combine all of this with an image of the files the program may see. OS Chapter 34 explains how each part works; Chapter 23 builds a sandbox for agent code from them.

Use case: OpenAI Codex CLI's sandbox

OpenAI's Codex CLI, an open-source coding agent released in April 2025 that runs on the developer's own machine, executes the commands its model proposes inside an operating-system sandbox. On macOS it uses Apple's Seatbelt sandbox profiles; on Linux it uses Landlock, a kernel feature that lets an unprivileged process restrict which files it and its children can access, together with seccomp filters, and its default modes allow writes only inside the working folder and block network access unless the user allows it. The design matches this chapter's layering: rather than trusting a check in each tool, the agent runs its commands as a process the kernel itself will not let out of the workspace or onto the network, whatever the command tries.

⚠️
Common mistakes
  • Checking paths with startswith, which lets ws2 pass as ws and ignores links.
  • Relying on a file tool's check while the agent can also run shell commands.
  • Letting child processes inherit the agent's environment, API keys included.
  • No memory or CPU limit on code the model wrote, so one bad loop takes the machine down.
  • Leaving network access on for code that only needs to compute.
  • Running the agent as an administrator or with your personal credentials.

Interview drill

Explain it simply: Your agent has a read_file(name) tool limited to a workspace folder. How do you make sure it cannot read anything outside it?

How a strong answer sounds
Join the name to the workspace, resolve the result to a real absolute path, which collapses ".." and follows symbolic links or junctions, and then check that the resolved path is inside the resolved workspace by comparing path components, for example with is_relative_to. A string startswith check is not enough: a neighbouring folder whose name begins the same way passes it, and a link inside the workspace leads out of it. I would test it with parent-directory paths, absolute paths, both separators and a link pointing outside. And I would remember it only protects that one tool; if the agent can run commands, the process itself needs to be confined.

Deeper: The agent runs Python scripts the model writes. What operating-system controls would you put around them, and why each?

How a strong answer sounds
Start it with the workspace as its working directory and an explicit, minimal environment, so it inherits no credentials. Put limits on memory, CPU time and file size so a bad loop or allocation fails fast with a readable error, and keep the wall-clock timeout that kills the whole process tree. Cut off the network unless the task needs it, with a network namespace or a container with no network. Run it as an unprivileged user, and ideally in a container or a kernel sandbox such as Landlock or Seatbelt so the file restrictions apply to everything it starts, not just to my tools. Each control covers a different failure: secrets, runaway resources, data leaving, and access outside the folder.

🧠 Key takeaways

  • An agent's process has all of its user's rights: every readable file, every variable, the whole network.
  • Keep file tools in the workspace with resolve and is_relative_to; startswith let a look-alike folder and a junction through.
  • Start children with an explicit environment: 82 inherited variables, key included, became 2.
  • Kernel limits turn runaways into clean errors: MemoryError at 400 MB, a kill at 2 s of CPU, Errno 27 at 10 MB.
  • Namespaces and cgroups, the parts of a container, confine everything a command starts, not just your tools.
