Browser & Computer-Use Agents

Many systems have no API, only a user interface built for people: admin panels, internal tools, websites. Browser and computer-use agents operate those interfaces directly, reading pages and clicking, typing and submitting as a person would. Everything that made tools easy for agents in earlier chapters, short exact outputs and clear inputs, is missing. A page is noisy, long and built for eyes.

This chapter measures the first decision in building one: what the model sees. A local shop-admin website, with realistic markup (styles, scripts, menus, hidden form fields), served the same pages to qwen3:14b in three forms: raw HTML, readable text with link addresses, and a compact outline of headings, links, table rows and form fields. Eight tasks: lookups, a count, a search, and two status updates checked on the server. qwen3:14b reads text only, so screenshots are discussed but not measured.

  • Choose how pages are presented to the model
  • Understand screenshot-and-coordinate agents and their trade-offs
  • Design browser actions the model can use reliably
  • Know why user interfaces are harder than APIs
  • Keep a browsing agent safe on pages others wrote

Pages as text

The same order page was 1,476 characters as raw HTML, 249 as readable text and 377 as an outline. Most of the raw page was a style block, an analytics script and attributes. The orders list was 4,565, 1,323 and 1,303. Across all eight tasks, raw HTML used about 70,000 prompt tokens, readable text 38,000 and the outline 25,000. The outline was the cheapest and, with raw HTML, the most successful: 6 of 8 each, against 3 of 8 for readable text.

Readable text lost what the model needed in order to act. Stripping tags threw away each form's action address and its hidden fields, including the anti-forgery token the site requires. On both update tasks the agent found the right order, then posted the new status to the page's own address without the token, was refused three times, and gave up ("Please check the form submission process or contact support"). The outline kept forms as structure:

[form POST /order/status]
  field id = 1043 (hidden)
  field csrf = tok1043 (hidden)
  field status (choose one):
    - pending
    - paid
    - shipped
    - refunded
[end form]

Raw HTML kept the forms too, at three times the tokens. The prompt reached 5,652 tokens on one step, so a few more pages would have pressed against the context window (Chapter 10). Accessibility trees, the structure browsers expose for screen readers, are the production version of the outline: roles, names, values and states, without the presentation.

Screenshots and coordinates

The other approach gives a vision model a screenshot and lets it act by coordinates: click at (412, 230), type, scroll. It works on anything a person can see, including canvas apps, remote desktops and pages whose structure is useless, and it is how general computer-use agents operate. It costs more per step (an image instead of short text), depends on the model locating small targets precisely, and breaks when layouts shift. Many systems combine the two: structure when the page exposes it, pixels when it does not. qwen3:14b reads text only, so this chapter's measurements cover the text side.

Actions

The agent had two actions: open_page(url) and submit_form(action, fields). Small action sets with exact inputs work best, the lesson of Chapter 4. Two failures here came from actions, not pages. In the first run, every task that started from an order number opened /orders/1043, a guess at a common URL pattern; the site uses /order?id=1043. The agent got a 404, said "Let me check the orders list…", and the loop ended, because a reply without a tool call counts as the answer. Adding one loop rule, "Go ahead." when the agent announces a step without taking it (at most twice), lifted raw HTML from 4 to 6 and the outline from 5 to 6. A harness bug of mine also counted. The search form uses GET, but submit_form always posted, and every search failed until the site accepted both. Check the harness before blaming the model.

The remaining misses were the same two tasks in every format: looking up orders 1043 and 1058, on the third page of the list. The agent paged through pages 1 and 2, announced page 3 and ran out of nudges. A link to each order's page, or a search by order number, would have made both trivial. Where you control the site, the best browser agent is often an API.

Why GUIs are hard

Interfaces are written for people who can see layout, remember what they clicked and know conventions. Agents get none of that for free. Pages are long, so tokens and context fill quickly. State is hidden in forms, cookies and scripts. Actions have side effects and no undo. Pages change between visits. And the same task takes many more steps than through an API: here 13 to 22 page loads for 8 tasks, where an API would have needed 8 calls. Expect lower success and higher cost than tool-based agents, and prefer an API wherever one exists.

Safety on the open web

A browsing agent reads pages written by anyone, which makes every page a possible source of instructions (Chapter 25). It also acts with the user's logged-in sessions, so a hijacked agent can buy, post or send as the user. Limit it to the sites the task needs, keep it out of sensitive accounts unless the task requires them, require confirmation before purchases, submissions and messages, and run the browser in an isolated profile or sandbox (Chapter 23). In this test no task changed an order it was not asked to change, but the agent was never shown a page designed to make it try.

Use case: WebArena, computer use and Operator

WebArena (Zhou and colleagues, 2023) built realistic, self-hosted websites, including a shop, a forum, a code host and a content-management system, and checked tasks by the sites' final state, as this chapter did. Its agents read pages as accessibility trees, and even strong models of the time succeeded on a small fraction of tasks that people completed easily. In October 2024 Anthropic released "computer use" for Claude, an API in which the model sees screenshots and acts by moving the mouse and typing at coordinates. In January 2025 OpenAI launched Operator, a browsing agent that works in its own browser and hands control back to the user for logins, payments and confirmations. Both pair the pixels approach with the safety measures above: isolated browsers, confirmation before consequential actions, and caution about instructions found on pages.

⚠️
Common mistakes
  • Raw HTML into the context: three times the tokens of an outline.
  • Stripping pages to plain text, losing form addresses and hidden fields.
  • Letting the model guess URLs instead of following links.
  • A loop that ends on "Let me check…" without acting.
  • Using a browser agent where an API exists.
  • Logged-in sessions, no confirmation step and untrusted pages in the same agent.

Interview drill

Explain it simply: How would you let an agent operate a web app that has no API?

How a strong answer sounds
Give it a small set of actions (open a page, follow a link, submit a form) and present each page as a compact outline of headings, links, table rows and form fields, like an accessibility tree, rather than raw HTML or plain text. In a measurement the outline completed 6 of 8 tasks at about a third of raw HTML's tokens, while plain text completed 3 because it lost form addresses and hidden fields. I would check results in the system rather than in the page and confirm before changes. Where possible I would ask for an API.

Deeper: Screenshots or page structure?

How a strong answer sounds
Structure where the page exposes it: it is cheaper, exact, and gives the model names and values rather than pixels. Screenshots where it does not, such as canvas apps, remote desktops or broken markup, at the cost of more tokens per step, precise clicking, and sensitivity to layout changes. Production agents often combine them. Either way the risks are the same: untrusted page content, actions with the user's sessions, and no undo. So the agent runs in an isolated browser with an allow-list of sites and confirmation before consequential actions.

🧠 Key takeaways

  • An outline of the page completed 6 of 8 tasks at about a third of raw HTML's tokens.
  • Plain readable text completed 3: it lost form addresses and hidden fields, so updates failed.
  • Guessed URLs and announced-but-untaken steps caused more failures than page format.
  • Check the harness: a GET form posted as POST failed every search until fixed.
  • Isolate the browser, limit sites and confirm before actions with side effects.
