The Agent Interview Playbook

Interviews for roles that build agents use four formats. A design round ("build an agent that handles refunds"), concept questions ("what is the difference between a workflow and an agent?"), debugging scenarios ("your agent works in testing and fails in production"), and take-home projects. All four reward the same thing: decisions backed by evidence, and knowing where agents fail.

This chapter is a playbook for each format, built from the measurements in this course. Its centre is a design framework of eight decisions. For each, the panel below shows what a strong candidate would decide for four common agents, and the measured result that justifies the decision. Bring numbers like these to an interview, and say how you would get them for the system in front of you.

  • Run a design round with a clear structure
  • Answer concept questions with a mechanism and a number
  • Debug from the trace, not from guesses
  • Scope a take-home so it shows evaluation, not only features
  • Use one framework for any agent design

Agent design rounds

A design round gives you a vague goal and 45 minutes. Interviewers look for structure: you clarify before building, you choose the simplest thing that works, you know where it breaks, and you say how you would measure it. Spend the first five minutes on the job and the success check. "What counts as done, and how would a program check it?" is the single most useful question, because every later decision follows from it. Then work through the eight decisions in the panel. Close with what you would measure first and what you expect to go wrong.

Three habits separate strong answers. Prefer structure over autonomy where the path is known: a fixed workflow is cheaper and easier to test, and an agent earns its place only where the next step depends on what the last tool returned (Chapter 1). Put rules in the tools, not the prompt: approval gates, idempotency, read-only connections and automatic test runs held in every chapter where they were measured, while instructions often did not. Name the failure modes: guessed arguments, false success claims, injection through tool results, runaway loops.

Concept questions

Concept questions test whether you can explain a mechanism simply and know its limits. A good pattern is the definition, the mechanism, a measured consequence and the remedy. "Why is prompt injection worse for agents?" → instructions in tool results can't be reliably separated from the real ones → one planted log line steered an agent in 12 of 12 runs, and a system-prompt warning stopped none of 36 attacks (Chapter 25) → so limit what untrusted text can reach and what the agent can do. Questions that come up often, with the chapter that answers each:

  • Workflow or agent, and when? (1) · How does tool calling work under the hood? (3) · How do you design a good tool? (4)
  • What happens when the transcript outgrows the context? (10, 11) · Short- vs long-term memory? (15, 16)
  • What is MCP? (20) · Framework or plain code? (21) · How do you choose a model? (22)
  • How do you make an agent safe to run code and take actions? (23, 24) · How do you evaluate an agent? (27, 28)

Debugging scenarios

"Our agent is wrong 20% of the time. What do you do?" Answer with a method, not a guess. Start from the traces of failing runs (Chapter 36). Sort the failures into kinds: wrong tool, wrong arguments, missing evidence, a context that lost something, an environment that misbehaved. Form a hypothesis for the largest group and test the cheapest fix against the failing cases and a regression suite. Then add the failing case as a test (Chapter 37). The course's own example: one incident failed in nearly every chapter. The trace showed the model choosing between two plausible deploys on the right service, with no timing evidence to choose by. The fix was in the tool output, not the prompt.

Typical scenarios and the first thing to check:

  • Slow and slightly more accurate after a framework migration: the options the framework sends; defaults turned on thinking and ran 18 times slower (21).
  • Invented numbers in a data agent: scripts that printed nothing (18).
  • Customers refunded twice: a retry after a timeout without an idempotency key (19).
  • Judge says 100%, customers complain: the judge grades a transcript that cannot show the side effect (27).
  • Great benchmark score, poor production: a shortcut in the benchmark; run baselines that should fail (28).

Take-home projects

A take-home is judged less on features than on judgement. Scope it small. Build one agent with a few well-described tools, an environment that resets, and a check a program can run. Then spend at least a third of the time on evaluation: twenty to fifty tasks, baselines (no tools, a fixed workflow, one heuristic), success measured from final state, and repeated runs. The README should report what works, what fails and why, with numbers and two or three traces. "It solves 19 of 24, the failures are all one kind, and here is the trace" is a stronger submission than a long feature list with no measurements.

Use case: what the labs tell builders

The design guides published by model developers read like answers to a design round. Anthropic's "Building effective agents" (December 2024) separates workflows from agents, recommends the simplest pattern that works, and stresses tool design ("agent-computer interfaces") and testing in sandboxed environments. OpenAI's "A practical guide to building agents" (2025) covers when an agent is worth it, choosing models by evaluating the task with the most capable model first, designing tools, layered guardrails, and planning for human intervention on high-risk actions and repeated failures. Interviewers read the same guides. A candidate who can add measured evidence and say where the advice breaks stands out.

⚠️
Common mistakes
  • Designing before asking how success is checked.
  • Reaching for multi-agent or a framework before one agent works.
  • Safety as a system-prompt sentence rather than gates, sandboxes and least privilege.
  • Evaluation as "we'll use a judge" without saying what the judge cannot see.
  • Debugging by rewriting the prompt without reading a trace.
  • Take-homes with no baselines and no reported failures.

Interview drill

Explain it simply: Walk me through how you would design an agent for a new task.

How a strong answer sounds
First the job and how a program checks success, preferably on final state. Then whether it needs to be an agent at all: if the path is fixed, a workflow. Then tools with clear descriptions, putting rules inside them (approval, idempotency, read-only access, automatic tests). Then the loop: limits and what to do when it stops. Then context and memory, then safety, meaning a sandbox, least privilege and treating tool results as untrusted. Then evaluation with baselines and repeated runs, and finally operating it with traces and budgets. At each step I would cite what I would measure.

Deeper: What is the most common way agents fail in production, and how do you design against it?

How a strong answer sounds
Agents claim success they did not achieve, and evaluation that reads their claims cannot see it. Measured examples: a support agent refunded customers twice after a timeout while saying the refund succeeded; a coding agent said a bug was fixed while the last test run failed; a model judge passed all six double refunds. I design against it with checks on the systems of record, loops that cannot finish while a check is failing, idempotent writes, and evaluation that grades state, not text.

🧠 Key takeaways

  • Start every design from the success check a program can run.
  • Use the simplest structure that can follow the path; agents only where the next step depends on results.
  • Put rules in tools and loops, not prompts: they held where instructions did not.
  • Debug from traces, test fixes against a regression suite, add the failure as a test.
  • In take-homes, evaluation with baselines and honest failures beats features.
