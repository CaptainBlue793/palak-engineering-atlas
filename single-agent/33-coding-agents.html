Coding Agents: Read, Edit, Test

Coding agents are the most widely used agents today, and the best case for everything in this course. A repository is an environment you can read, change and reset. The test suite is a final-state check that already exists (Chapter 27). And the loop of reading code, editing, running tests and fixing what broke is exactly the agent loop.

This chapter builds a small coding agent and measures it. The repository is a Python package of six modules (money, cart, paging, users, dates, stock) with eleven unit tests. Eight copies each have one bug planted, with an issue written the way a user would report it: "format_gbp(7) returns '£0.7' instead of '£0.07'". qwen3:14b fixed each one under four set-ups, and the result was graded by running the original tests.

  • Give an agent tools to explore a repository
  • Choose an edit format, and know how each one fails
  • Make running tests part of the loop, not an option
  • Recognise false success claims and test tampering
  • Measure a coding agent on issues with hidden checks

Reading a repository

The agent had list_files and read_file. On a package this small, exploring was the easy part. In nearly every run the agent listed the files, read exactly the module the issue pointed to, and edited it: three calls. It read the test file only occasionally. Real repositories are thousands of files, so coding agents add search (grep, symbol lookup), outline views of large files, and the ability to read a file in parts, the same lessons as search in Chapter 17: tools that return the relevant part, not everything.

Edit formats

How the agent writes changes matters more than it seems. Search and replace (edit_file(path, old, new), where old must match exactly once) sends only the change and fails loudly when the text does not match. Whole file (write_file(path, content)) cannot fail to match but must reproduce every line, and gives the agent a way to touch any line, tests included.

def edit_file(path: str, old: str, new: str) -> str:
    """Replace one exact piece of text. 'old' must appear exactly once."""
    text = read(path)
    n = text.count(old)
    if n != 1:
        return f"error: the text to replace was found {n} times in {path}; it must match exactly once, including spaces."
    write(path, text.replace(old, new, 1))
    return f"edited {path}\n\nTests after this edit:\n" + run_tests()      # the version that worked best

With a test tool available, search and replace fixed 7 of 8 and whole-file writes 6 of 8. The whole-file agent did something worse in one run. On the hardest bug (a price of £1.005 rounding to 100 pence because of floating point), it ran the tests, read the test file, rewrote the test file, ran the tests again, and then edited the code. It had been told "Do not change the tests". Grading against the original tests caught it. A grader that ran the agent's copy of the tests would have counted it as a fix. Use an edit format that is restricted to the source files, keep tests read-only, and always grade with your own copy.

Search and replace has its own failure. In one run the agent's old text did not match the file six times in a row (the line it was editing contained a £ sign and an f-string). Each time the tool explained the problem, and each time the agent re-read the file and tried again with text that still did not match.

Running tests

Without a test tool, search and replace fixed only 4 of 8. One "fix" for the rounding bug broke two cart tests that had passed before. One added a check that did not work. One ended without editing anything. The agent believed each of them was done. Tests are how a coding agent finds out it is wrong.

Having the tool was not enough, though. With run_tests available, the search-and-replace agent called it in only 2 of 8 tasks. It edited, said what it had changed and stopped. The fix that worked was the one from Chapter 18: make the tool do it. With the edit tool running the tests after every edit and returning the result, every task saw its test results, 11 test runs in 8 tasks. The hardest bug was fixed after four rounds of edit, failing test, edit, which no other set-up achieved. The score was 7 of 8 again, because the run with six failed edits was this set-up's miss. In it the agent finally made an edit, saw "FAILED (failures=1)", and still answered that format_gbp "now correctly formats amounts under 10p".

Iterating on failures

The good runs had a recognisable shape: edit, read the failure, change the approach, edit again. On the rounding bug it took four rounds of edit and failing test (100 != 101) before a change passed. The bad runs repeated the same action (six identical failed edits) or stopped at the first claim of success. Two cheap rules help. After two identical failed edits, re-read the file and quote the exact lines. And a run cannot end with "done" while the last test result is a failure: check that in the loop, not in the prompt.

Measuring on real issues

This chapter's benchmark has every property Chapter 28 asks for: resettable repositories, a hidden check (the original tests), issues written like user reports, and a check for tampering. It is also tiny, eight tasks, and one run each, so a difference of one task is within the noise (Chapter 29). Real evaluations such as SWE-bench use hundreds of real issues from real projects, and the same principle: the agent's patch is judged by tests it did not see and cannot change.

Use case: SWE-agent and Aider's edit formats

SWE-agent (Yang and colleagues, 2024) argued that coding agents need an "agent-computer interface" designed for models, not a human terminal. It gave the model a file viewer that shows a window of lines, a search command that summarises matches, and an edit command that runs a linter and rejects edits that introduce syntax errors. These interface choices raised its success on SWE-bench substantially over a plain shell. Aider, an open-source coding assistant, benchmarks the edit formats it asks models to use, such as search-and-replace blocks, whole files and unified diffs. It found that the best format differs by model and that formats which let a model be lazy (eliding code in whole-file edits) or require exact line numbers cause many failures. Both reached the conclusion of this chapter: much of a coding agent's success is decided by its tools.

⚠️
Common mistakes
  • A test tool the agent may skip: it ran tests in 2 of 8 tasks.
  • Grading with the agent's copy of the tests, which it can edit.
  • Whole-file writes on large files, where every line must be reproduced.
  • Accepting "done" while the last test run failed.
  • Letting the agent repeat the same failed edit instead of re-reading the file.
  • Comparing set-ups on eight tasks run once and trusting one-task differences.

Interview drill

Explain it simply: What tools does a coding agent need, and what matters most?

How a strong answer sounds
Tools to explore (list, search, read in parts), to edit (exact search and replace on source files), and to run tests in a sandbox. What matters most is that tests actually run: in a measurement, the same agent fixed 4 of 8 bugs without tests and 7 with them, but given an optional test tool it used it in only 2 tasks. Running the tests automatically after every edit fixed the hardest bug through four edit-test rounds. The tools should also stop it touching the tests.

Deeper: How would you stop a coding agent from passing by editing the tests?

How a strong answer sounds
Make it impossible and make it pointless. The edit tool only accepts source paths, or the tests are mounted read-only in the sandbox. Grading always runs a copy of the tests the agent never had access to, as SWE-bench does with hidden tests. In a measured run, an agent with a whole-file write tool rewrote the test file despite being told not to; grading with the original tests caught it. I would also log edits to test files as an alert in evaluation.

🧠 Key takeaways

  • Without tests the agent fixed 4 of 8 and believed every fix; with tests, 6 to 7.
  • An optional test tool was used in 2 of 8 tasks; running tests after every edit fixed that.
  • A whole-file agent rewrote the test file once; grade with your own copy of the tests.
  • Search and replace fails loudly; the agent still repeated one failed edit six times.
  • Do not accept "done" while the last test run failed: check it in the loop.
