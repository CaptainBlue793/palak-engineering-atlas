Observability & Tracing Agent Runs

When an agent gets something wrong in production, the final answer says almost nothing about why. Every chapter of this course found its explanations in the record of what the agent did: the call it made, the result it read, the choice it made next. Observability means keeping that record for every run, in a form you can search, count and compare.

This chapter builds the record. A small tracer, with no dependencies, records each run as a tree of spans: one for the run, one per model call with its tokens and timings, one per tool call with its arguments and result. It traced the twelve incidents with qwen3:14b. Then it uses recorded traces for the other half of observability: the 360 runs from Chapter 29 sorted into failure categories automatically, and the categories turned into tests.

  • Record agent runs as traces and spans
  • Decide what to log, and what not to
  • Build dashboards that show agent health
  • Collect and use user feedback
  • Turn failure categories into regression tests

Traces and spans

A trace is one run. A span is one timed operation inside it, with a name, a start and end time, a parent, and attributes. For an agent the natural tree is the run at the root, a span per model call, and under each model call a span per tool call it requested. This is the same model OpenTelemetry uses for distributed services, so agent traces can sit beside the traces of the services the tools call.

def traced_run(task, tools):
    run = tracer.start("agent.run", task=task, model=MODEL)
    for step in range(1, MAX_STEPS + 1):
        llm = tracer.start("llm.chat", parent=run, step=step, messages=len(msgs))
        r = chat(msgs, tools)
        tracer.end(llm, prompt_tokens=r.prompt_eval_count, output_tokens=r.eval_count, tool_calls=len(r.message.tool_calls or []))
        if not r.message.tool_calls:
            break
        for call in r.message.tool_calls:
            span = tracer.start("tool." + call.function.name, parent=llm, args=call.function.arguments)
            result = run_tool(call)
            tracer.end(span, result=result[:300], error=result.startswith("error"))
    tracer.end(run, answer=r.message.content, ok=check(r.message.content))   # the outcome, from a state check

The twelve traced runs had 10 to 24 spans each and took 2 to 4.5 seconds. They solved 11 of 12, failing on incident 5 as in nearly every chapter. In every trace the model spans held all the time; the simulated tools returned instantly. That reading takes seconds with a trace and is impossible from logs of final answers. The tracer itself was not timed separately; it adds a few dictionary writes per step, negligible next to model calls of hundreds of milliseconds.

What to log

For each model call: the step, the prompt and output token counts, the timings, the number of tool calls, and the text it produced or a hash of the full prompt. For each tool call: the name, the arguments, a truncated result, whether it was an error, and its duration. For the run: the task, the model and options actually sent (Chapter 21), the outcome from a state check rather than the agent's claim (Chapter 27), and the stop reason. What not to log in plain text: secrets, credentials and personal data from tool results or prompts. Redact them at the tracer, before anything is stored, and set a retention period. Traces of agents that read email or customer records are as sensitive as the records.

Dashboards

A dashboard for an agent shows, over time: success rate from state checks, with pass^k where tasks repeat (Chapter 29); steps, tokens and cost per run with their tails (Chapter 31); latency split into model, tools and queueing (Chapter 35); tool error rates per tool; how often runs hit step or token limits; and the share of runs in each failure category. Alert on changes, not only on thresholds. A failure category that doubles overnight usually means a tool or a data source changed.

User feedback

Users notice failures no check catches. A thumbs-down, an edited answer or a retried request attaches to the trace it came from, and gives a labelled example of failure. Feedback is sparse and biased toward strong reactions, so treat it as a source of cases, not as a success rate. The useful habit is a weekly review: read a sample of traces with negative feedback, label what went wrong, and add the new kinds to the failure categories below.

From failures to tests

Traces make failures countable. The 360 runs from Chapter 29 were sorted by rules that read only the trace: did the run stop at a limit, did it announce a step and end without taking it, did it ever read the guilty service's deploy history, and did it then name the right version. Of the 65 failures, 57 read the guilty service's deploys and named another version, and 50 of those came from just two incidents, 5 and 9. Another 5 announced a step and stopped, the loop-ending pattern seen in Chapters 17, 24 and 34. And 3 never reached the guilty service. One category is 88% of the failures, and it is the one Chapter 37 traced to missing timing evidence and fixed in the tool output, taking incident 5 from 1 of 5 seeds to 5 of 5. Each category becomes a test in the regression suite, with the incidents that showed it, so that the fix stays fixed.

Use case: OpenTelemetry for generative AI

OpenTelemetry, the open standard for traces, metrics and logs, added semantic conventions for generative AI in 2024. These are standard attribute names for model calls, such as the system and model, the token counts for input and output, and the request's parameters, plus spans for tool execution and agent operations. Tracing tools for agent applications, including LangSmith, Langfuse and Arize Phoenix, record runs as trees of spans like the ones above. They add views for comparing runs, attaching user feedback and building evaluation datasets from traces. The common shape lets an agent's model and tool spans appear in the same trace as the database queries and HTTP calls its tools make, so a slow or failing run can be followed from the user's request to the service that caused it.

⚠️
Common mistakes
  • Logging only final answers, which explain nothing about failures.
  • Recording the agent's claim as the outcome instead of a state check.
  • Storing secrets and personal data in traces without redaction or retention.
  • Dashboards of averages that hide tails and category shifts.
  • Reading failures one by one without categorising and counting them.
  • Fixing a category without adding it to the regression suite.

Interview drill

Explain it simply: What would you log for an agent in production?

How a strong answer sounds
A trace per run: a root span with the task, model, options, stop reason and an outcome from a state check; a span per model call with tokens, timings and number of tool calls; a span per tool call with arguments, a truncated result, errors and duration. I would redact secrets and personal data before storage and keep it for a set period. From those traces come dashboards of success, cost, latency and failure categories, and the examples for debugging and evaluation.

Deeper: You have thousands of traces and a 15% failure rate. Where do you start?

How a strong answer sounds
Categorise failures with rules over the traces, then fix the biggest category. Did it stop at a limit, end on an announced step, never reach the right data, or reach it and decide wrongly? On 360 recorded runs that sorted 65 failures into three categories, with 57 in one, mostly from two tasks. That category had one cause, missing timing evidence in a tool's output, and fixing the tool took the worst task from 1 of 5 to 5 of 5. Each category then becomes a regression test.

🧠 Key takeaways

  • Trace every run as spans: run, model calls with tokens and timings, tool calls with arguments and results.
  • Record the outcome from a state check, and redact secrets and personal data before storage.
  • Rules over 360 traces sorted 65 failures into three categories; one held 88% of them.
  • The largest category had one cause, fixed in a tool, and became a regression test.
  • Dashboards should show tails and failure categories over time, not just averages.
