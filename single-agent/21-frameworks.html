Agent Frameworks vs Plain Code

Every agent in this course so far has been a loop of about thirty lines. Agent frameworks package that loop with state management, checkpoints, streaming, tracing and integrations, at the price of code you did not write running between you and the model. This chapter builds the same incident agent three ways and measures what changes and what is hidden.

The builds are the plain loop from Chapter 2; a graph assembled by hand in LangGraph 1.2; and LangChain 1.4's prebuilt create_agent, once with the model configured explicitly and once with its defaults. qwen3:14b ran the same twelve incidents with the same prompt and tools in every build.

  • Recognise the agent loop inside any framework
  • Build the same agent as a state graph and as a prebuilt agent
  • Use checkpoints to pause, inspect and resume a run
  • Find the defaults a framework chose for you
  • Decide when a framework is worth it

The plain loop

Call the model with the messages and tools. If it asks for tools, run them, append the results and go round again. If it answers, stop. Here it is with the parts this course has added: options set explicitly, thinking off, a step limit.

def run_agent(task, tools, system, max_steps=15):
    messages = [{"role": "system", "content": system}, {"role": "user", "content": task}]
    for _ in range(max_steps):
        msg = ollama.chat(model="qwen3:14b", messages=messages, tools=[t["schema"] for t in tools.values()],
                          think=False, options={"temperature": 0, "seed": 1, "num_ctx": 16384}).message
        messages.append(msg)
        if not msg.tool_calls:
            return msg.content
        for call in msg.tool_calls:
            result = tools[call.function.name]["fn"](**call.function.arguments)
            messages.append({"role": "tool", "tool_name": call.function.name, "content": str(result)})
    return None                                                   # step limit reached

It solved 11 of 12 incidents in 3.2 seconds per run on average. Everything it does is on screen. What it lacks is everything around the loop: saving progress, pausing for approval, streaming tokens to a user, tracing, retries.

Graph frameworks

LangGraph describes an agent as a graph. Nodes are functions that read and update a shared state, here the message list; edges say which node runs next, and conditional edges decide at run time. The agent loop becomes two nodes and a conditional edge:

from langgraph.graph import StateGraph, MessagesState, START
from langgraph.prebuilt import ToolNode, tools_condition

model = ChatOllama(model="qwen3:14b", temperature=0, seed=1, num_ctx=16384, reasoning=False).bind_tools(tools)

def call_model(state: MessagesState):
    return {"messages": [model.invoke([SystemMessage(SYSTEM)] + state["messages"])]}

g = StateGraph(MessagesState)
g.add_node("model", call_model)
g.add_node("tools", ToolNode(tools))
g.add_edge(START, "model")
g.add_conditional_edges("model", tools_condition)            # tool calls -> "tools", otherwise finish
g.add_edge("tools", "model")
app = g.compile()
app.invoke({"messages": [HumanMessage(TASK)]}, config={"recursion_limit": 40})

The prebuilt version is one call: create_agent(model, tools, system_prompt=SYSTEM) from langchain.agents (it replaced LangGraph's create_react_agent, which version 1 marks as deprecated). With the model configured the same way, the graph and the prebuilt agent sent identical requests and both solved 10 of 12, in 3.2 seconds per run. About 0.3 seconds of that, roughly 35 ms per step, was spent in framework code rather than the model. Their one extra miss against the plain loop is within the run-to-run variation seen elsewhere in this course; the one visible difference in what they sent was the tool schema (below).

State and checkpoints

What a graph framework does well is keeping the state outside the loop. Compile with a checkpointer and every step is saved under a thread id. The run can then stop and continue: after a crash, after a deploy, or while a person approves something. Here the agent was compiled to pause before every tool call and was resumed each time with invoke(None, config), as an approval flow would (Chapter 24):

app = create_agent(model, tools, system_prompt=SYSTEM, checkpointer=InMemorySaver(), interrupt_before=["tools"])
config = {"configurable": {"thread_id": "incident-3"}}
app.invoke({"messages": [HumanMessage(TASK)]}, config=config)   # runs until the first tool call, then pauses
while app.get_state(config).next:                               # a person could inspect or edit the state here
    app.invoke(None, config=config)                              # continue from the saved state

The run paused 12 times, saved 25 checkpoints, made exactly 12 model requests (none repeated on resume) and reached the right answer. Doing this with the plain loop means saving the message list yourself after every step and reloading it. That is not hard (Chapter 32), but it is work the framework has already done and tested. A production checkpointer would use Postgres or SQLite rather than memory.

What gets hidden

Model defaults. The fourth build used ChatOllama(model="qwen3:14b") with nothing else set. The first request it sent carried "options": {} and no think setting, so every choice fell to the model and the server. qwen3 thinks by default, so every step began with hidden reasoning. With no context size requested, this Ollama version loaded the model with its full 40,960-token context, and sampling used the model's defaults rather than temperature 0. That run solved 12 of 12 but took 58.6 seconds per run instead of 3.2, eighteen times longer, and was no longer reproducible. Whether the trade is worth it is a real choice (Chapter 22); the problem is making it without knowing. Log the first request your framework actually sends and read it.

Tool schemas. The framework builds each schema from the function's signature and docstring. The hand-written schema described the parameter ("service: Service name"); the generated one had only {"service": {"type": "string"}}, because the docstring had no Args: section. The descriptions you used to write by hand now live in docstrings, and they matter just as much (Chapter 4).

Limits. In LangGraph 1.2.16, a graph run without a recursion_limit stops only after 10,007 steps; a test graph that looped forever ran its node 10,007 times before raising GraphRecursionError. For an agent that is about 5,000 model calls. Set the limit on every call, as you would max_steps (Chapter 7). Older guides quote 25; check the version you have.

Choosing

A framework earns its place when you need what it has already built and tested: durable checkpoints, pausing for people, streaming, multi-step workflows with branches, tracing, many integrations. Plain code earns its place when the loop is simple, when you need to see and control every request, or when you are learning. Many teams start plain and adopt a framework at the point where they would otherwise write a checkpointer. Either way, the agent's quality came from the same places in all four builds: the model's configuration, the tools and their descriptions, the prompt and the limits.

Use case: Anthropic's "Building effective agents"

In December 2024 Anthropic published guidance drawn from its work with customers building agents. It recommended starting with the simplest solution, often a single model call or a fixed workflow, and adding agentic loops only when needed. It also noted that frameworks make it easy to start but "often create extra layers of abstraction that can obscure the underlying prompts and responses", and suggested developers begin by calling model APIs directly and make sure they understand the underlying code if they adopt a framework. The framework developers' own documentation moved the same way: LangGraph presents itself as low-level orchestration with durable execution and human-in-the-loop support, and LangChain 1.0 rebuilt its agent on top of it with explicit middleware for the steps around the model call. The measurement here shows why the advice holds. The framework added little time and no intelligence, and its defaults changed the agent's behaviour more than anything else.

⚠️
Common mistakes
  • Leaving model options to defaults: thinking, context size and sampling change speed and results.
  • No recursion limit: LangGraph 1.2's default is 10,007 steps.
  • Docstrings without parameter descriptions, now that they are the tool schema.
  • Never reading the request the framework actually sends.
  • Adopting a framework before understanding the loop, then debugging its abstractions.
  • Writing your own checkpointing badly when a tested one exists.

Interview drill

Explain it simply: Would you use an agent framework or write the loop yourself?

How a strong answer sounds
It depends on what I need around the loop. The loop itself is about twenty lines, and when I built the same agent plainly and with LangGraph, configured the same way, they solved the same incidents in the same time. The framework added about 35 ms per step. A framework is worth it for durable checkpoints, pausing for human approval, streaming, branching workflows and tracing, which I would otherwise build and test myself. Either way I would set model options and limits explicitly and log the first request it sends.

Deeper: After moving your agent into a framework it became far slower but slightly more accurate. What would you check?

How a strong answer sounds
What the framework sends to the model. In a measured case, a prebuilt agent with a default model object sent no options and no thinking setting. The model thought at every step, the server loaded its full 40k context, and sampling was no longer deterministic. Runs went from 3.2 to 58.6 seconds and from 10 to 12 of 12 solved. I would capture the raw request, set thinking, context size, temperature and seed explicitly, decide deliberately whether thinking is worth it, and also check the recursion limit and the generated tool schemas.

🧠 Key takeaways

  • Configured the same way, a plain loop, a LangGraph graph and create_agent behaved the same: 10 to 11 of 12, 3.2 s per run.
  • The framework cost about 0.3 s per run, roughly 35 ms per step.
  • Defaults sent no options: thinking on, full context, default sampling, 18 times slower.
  • Checkpoints let a run pause and resume without repeating model calls.
  • Set limits yourself: LangGraph 1.2's default recursion limit is 10,007 steps.
