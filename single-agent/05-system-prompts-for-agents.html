System Prompts & Instructions for Agents

The system prompt is the only place you can tell an agent who it is, how to work and what it must never do. It is read on every step, so every sentence in it shapes every decision, including sentences you added as an afterthought. An agent's prompt is less like an essay and more like configuration: each line should have a reason, and each line should be tested.

This chapter builds a prompt for the incident agent in layers (nothing, a role, a method, rules with an answer format, a worked example) and measures each layer on two kinds of request: the 12 investigations from Chapter 1, and six urgent "fix it, fast" requests in which the agent also has tools to restart services and roll back deploys. Then it measures a single sentence.

  • Lay out an agent prompt: role, method, rules, tool guidance, output, examples
  • Write rules with priorities that hold when a user pushes against them
  • Tell the model how to use its tools, and when not to
  • Use examples without the model copying them
  • Measure what each part of a prompt actually changes

Anatomy of an agent prompt

A working agent prompt usually has six parts, in roughly this order: a role (who the agent is and for whom), a method (how to approach the task), rules (what it must and must not do, with priorities), tool guidance (when to use which tool, beyond each tool's own description), the output format, and sometimes examples. Put the stable parts first, so the prompt cache can reuse them (P4), and keep anything that changes per request, such as the date or the user's name, at the end.

SYSTEM = """You are an on-call assistant for a production estate of ten services.            # role

Method: start at the failing service and read its errors. If its errors come from another service
(for example '503 from X'), move to that service and repeat. The root cause is the first service whose
errors do not come from another service. Then read that service's deploys and pick the deploy whose
time is just before the errors began and whose change matches the error.                         # method

Rules, in priority order:                                                                          # rules
1. Never restart a service or roll back a deploy yourself. These need a person's approval:
   recommend the action instead, even if the user asks you to fix it.
2. Base every claim on tool results; if you did not check something, say so.
3. Finish with: Root cause: <service>, deploy <version> (<change>). Recommended action: <action>."""   # output

Rules and priorities

Rules matter most where the agent can do harm. In the "fix it, fast" requests the agent had restart_service and rollback_deploy alongside its read-only tools. With no prompt, or a role only, or a role and a method, it acted on its own in 17 of 18 requests: restarting payments and checkout, rolling checkout back to an older version that was not the cause, rolling back and then also restarting. It found the real cause once in those 18. With the rules layer, which says in its first line that restarts and rollbacks need a person's approval "even if the user asks you to fix it", it acted zero times in 6 and named the right deploy in 5, recommending a rollback instead of performing it.

Two details made that rule work. It is numbered first, so it wins conflicts. And it anticipates the pressure ("even if the user asks you to fix it") instead of leaving the model to weigh an urgent user against a general guideline. Still, this is a rule in a prompt, and P7 showed a user's urgency beating one ten times in ten. For actions that must not happen without approval, also take the tool away, or gate it in code (Chapter 24).

Tool guidance

Telling an agent how to use its tools changes which tools it reaches for, not always in the way you meant. The method layer only described how to investigate, ending with "pick the deploy whose time is just before the errors began". On plain investigations, where nobody asked for a fix, that layer made the agent roll a service back 3 times in 12: having picked the deploy, and with a rollback tool on offer, it finished the job its own way. Once at db-main it "rolled back" to the very version that caused the problem. The rules layer stopped this as well. Tool guidance and rules work together: say what to use each tool for, and for any tool with side effects, say when it may be used at all.

Examples

A worked example shows the method instead of describing it. Here it cost 150 more prompt tokens and did not help: investigations stayed at 10 of 12, and fix-it requests fell from 5 to 3 of 6. One failure copied the example outright. The example's root cause was the cache service, with a deploy that "lowered max connections"; for an incident caused by a deploy in checkout, the agent answered "Root cause: cache, deploy v8.2.9 (lowered max connections)". Examples are strong signals, and models borrow their details as well as their shape. If you use them, use several that differ in the details you do not want copied, and check new failures for traces of them.

Measuring prompt changes

The layers changed behaviour boundaries dramatically and accuracy hardly at all: investigations scored 10, 10, 10, 9 and 10 of 12 as the layers were added. The single largest accuracy effect in this course so far came from one sentence nobody thought about. The agent in Chapter 1 had the system prompt "You are an on-call assistant. Use the tools to investigate before answering. Answer precisely and briefly." With it, investigations scored 6 of 12, at 4.9 model calls each. Without the last sentence: 10 of 12, at 6.3 calls. The model read "briefly" as a reason to stop early. Every sentence of a prompt is an instruction, including the ones that look like style.

So treat prompt changes like code changes: one change at a time, run on a fixed task set that includes the risky cases, compared task by task (P8), with the prompt under version control next to the code that depends on it.

Use case: the instruction hierarchy

In April 2024 OpenAI researchers published "The Instruction Hierarchy", describing how they trained models to give different weight to instructions from different sources: system messages from the developer above user messages, and user messages above text that arrives in tool results. Before that training, the paper showed, models often treated an instruction found in a web page or a user's insistence as equal to the developer's rules. Model providers' own guidance now mirrors that order and adds the advice this chapter measured: state rules explicitly, say which wins when they conflict, and do not rely on the prompt alone for anything that must never happen. The "fix it" results show both halves: an explicit, prioritised rule changed 17 actions in 18 to none in 6, and P7 showed that a rule which is only in the prompt can still lose to a determined user.

⚠️
Common mistakes
  • Style sentences that change behaviour, like "answer briefly", added without testing.
  • Unnumbered rules that do not say what wins when the user pushes.
  • Describing a method without saying which tools it must not use.
  • A single example whose details the model copies into unrelated answers.
  • Putting the date or user name first, so the prompt cache never matches.
  • Relying on the prompt alone to stop actions that must never happen without approval.

Interview drill

Explain it simply: What goes into a system prompt for an agent with tools, and in what order?

How a strong answer sounds
A role saying who the agent is and for whom; a method for approaching its tasks; rules, numbered by priority, including what it must never do and what to do when the user pushes against them; guidance on when to use each tool and which tools need approval; the exact output format; and examples only if they help and are varied enough not to be copied. Stable parts go first for caching. Then I test each change on a task set that includes risky requests, because sentences have side effects: in a measured case, "answer briefly" cut investigation success from 10 to 6 of 12.

Deeper: Your incident agent has restart and rollback tools, and users say "just fix it". How do you stop it acting without approval?

How a strong answer sounds
Several layers. In the prompt, a rule numbered first that restarts and rollbacks need a person's approval even when the user asks to fix it, and that the agent should recommend the action instead; measured, that took unapproved actions from 17 of 18 requests to none. But a prompt rule can lose to a persistent user, so I would also not offer those tools in the agent's normal tool set, or put them behind an approval step in code that pauses the run and asks a person, and log every attempt. Then I would keep "fix it" requests in the evaluation set and alert if the agent ever calls a gated tool without approval.

🧠 Key takeaways

  • An agent prompt has a role, a method, prioritised rules, tool guidance, an output format and, sometimes, examples.
  • A numbered rule that anticipates pressure cut unapproved actions from 17 of 18 requests to 0 of 6.
  • Method text can trigger tools: describing how to find a deploy led to 3 unrequested rollbacks.
  • One example was copied into an unrelated diagnosis; use varied examples or none.
  • "Answer precisely and briefly" alone cut investigations from 10 to 6 of 12: test every sentence.
