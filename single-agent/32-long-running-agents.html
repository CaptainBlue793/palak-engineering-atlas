Long-Running Agents: Checkpoints & Resumption

A run that takes seconds can simply be repeated if it fails. A run that takes an hour, makes hundreds of calls and changes things along the way cannot: something will interrupt it, such as a deploy, a crash, a timeout or a laptop lid, and starting again repeats every call, including the ones with side effects. Long-running agents need what long-running programs have always needed: saved state, and a way to resume from it without doing work twice.

This chapter measures resumption on a long task: audit all ten services (metrics and errors for each), then write a table with a verdict per service. Each run was interrupted twice, right after the 8th and 16th tool calls and before the step was saved, as a real crash would. It was resumed four ways: from scratch, from a checkpoint saved after each step, from that checkpoint plus a cache of every tool result, and from a progress file the agent wrote for itself. qwen3:14b, six incidents per strategy.

Why runs die

Processes are restarted by deploys and autoscalers. Connections to model servers time out. Machines run out of memory. Users close tabs. Rate limits and provider outages stop calls for minutes. A step limit or budget ends a run that was nearly done. The longer a run, the more likely one of these happens, and the more an unplanned restart costs. In this test, restarting from scratch after two interruptions took 42 model calls instead of 18 and re-ran 96 tool calls that had already been made. For read-only tools that costs time and tokens. For tools that refund, deploy or send messages it is the double refund of Chapter 19.

Checkpointing state

An agent's state is its message list plus any external state it changed. Save the messages after every step and a resumed run can continue where it was. The first version of this experiment found a subtlety. The agent batched its calls, asking for all ten services' metrics and errors in one or two replies, so a whole audit took about three model steps. Interruptions placed between steps never happened mid-batch and the checkpoint was never tested. Placed by tool call, as real crashes happen, they landed inside a batch. The checkpoint, saved after the previous step, then lost the whole batch, and resuming re-ran 90 of the 96 repeated calls. It cut model calls from 42 to 30 and tokens from about 23,000 to 18,000, but barely reduced repeated work.

The fix was a second, finer layer: a cache of every tool result, written as each call completes, keyed by the tool name and arguments. On resume the model re-issued the same batch, 90 calls, and every one was answered from the cache. Nothing was executed twice. For tools with side effects, this cache is the idempotency key of Chapter 19 applied to the whole run.

def call_tool(name: str, args: dict, store) -> str:
    key = json.dumps([name, args], sort_keys=True)
    if (done := store.get(key)) is not None:          # finished before the crash: do not repeat it
        return done
    result = TOOLS[name](**args)
    store.put(key, result)                                # durable before the agent sees it
    return result

# after every model step: store.put("messages", messages); on start: messages = store.get("messages") or fresh()

Resuming

Resuming is loading the messages and continuing the loop, with three cautions. A call that was in flight when the process died may or may not have happened. The cache cannot know, so writes still need idempotency keys or a status check. The world may have changed while the run was stopped, so long-paused runs should re-read anything they act on. And a resumed run should be visibly the same run in traces and logs (Chapter 36), so a person can see that it was interrupted. Accuracy did not depend on the strategy here: every strategy got 56 of 60 table rows right, the same as uninterrupted runs.

Progress files

A progress file is the agent's own notes on what is done and what remains, kept outside the conversation. Coding agents use files like this on tasks that span sessions. Here the agent was given a save_progress tool and asked to save notes after each service. That changed how it worked. Instead of batching, it went service by service, writing notes between them, and with two interruptions it used 254 model calls and about 234,000 prompt tokens, thirteen times the checkpoint's, and re-ran as many calls as starting from scratch. A resumed run read the notes, but notes say what is finished, not which calls were made, so resumed runs repeated calls. Progress files are good for what they are: a summary a person or a fresh session can read, which survives model changes and context limits. They are an expensive and lossy way to avoid repeated work.

Durable execution

Durable execution systems make the pattern above general. Every step's inputs and outputs are recorded in a log, and after a crash the program is replayed from the log, with completed steps returning their recorded results instead of running again. Temporal is the best-known example. Agent frameworks offer simpler versions: LangGraph's checkpointers save state after each node (Chapter 21). Use them when runs are long, expensive or have side effects. A run of a few seconds with read-only tools does not need any of this; just run it again.

Use case: Temporal and agent harnesses

Temporal, which grew out of Uber's Cadence project, runs "workflows" whose every step is recorded in an event history. When a worker crashes, another replays the workflow from that history, and completed activities return their recorded results rather than running again. Several teams building long-running agents have adopted it or similar systems so that hours-long runs survive restarts. For coding agents that work across many sessions, Anthropic's engineering guidance (2025) describes the lighter pattern. A first session sets up the environment and a progress file listing features and their status. Each later session reads the progress file and the git history, works on one item, commits, and updates the file. That is the progress-file approach measured here, used for what it does well: handing work between sessions, not avoiding repeated calls within one.

⚠️
Common mistakes
  • Testing resumption only between steps, when real crashes land inside batches of calls.
  • Checkpointing messages but not tool results, so resumed batches re-run.
  • Assuming an in-flight write did not happen; use idempotency keys or check status.
  • Progress notes instead of a result store, at many times the tokens.
  • Resuming a long-paused run without re-reading the state it acts on.
  • Durable machinery for short, read-only runs that could simply be repeated.

Interview drill

Explain it simply: How do you make a long-running agent survive a crash?

How a strong answer sounds
Save the conversation after every step and store every tool result as it completes, keyed by tool and arguments. On restart, load the messages and continue; when the model re-issues calls that already completed, answer them from the store. In a measurement with two crashes per run, restarting re-ran 96 calls, a step checkpoint alone still re-ran 90 because the crashes fell inside batched calls, and the checkpoint plus result store re-ran none. For writes I would still use idempotency keys, because a call in flight at the crash may or may not have happened.

Deeper: Your team wants the agent to keep a progress file instead. What would you say?

How a strong answer sounds
A progress file is useful for handing work between sessions or to a person, but it is a poor way to avoid repeated work. Measured, asking the agent to save notes after each service changed it from batching to one-at-a-time: 254 model calls and about 234,000 prompt tokens against 30 calls and 18,000 for a checkpoint. It still repeated as many calls as a restart, because notes record what is finished, not which calls were made. I would use a checkpoint and result store for correctness, and a progress file only if people or later sessions need a summary.
