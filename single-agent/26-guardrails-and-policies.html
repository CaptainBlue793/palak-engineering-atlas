Guardrails & Policy Checks

A guardrail is a check outside the model: on what comes in, on each tool call the agent proposes, and on what goes out. Each one is a classifier, and like any classifier it has two error rates. It misses things it should stop, and it stops things it should allow. The second rate is the one teams forget, until users complain that the assistant refuses ordinary requests.

This chapter measures three guardrails for the incident agent as classifiers on labelled sets: 40 proposed tool calls checked against a written operations policy, 30 user requests checked for scope, and 30 answers checked for secrets and customer contact details. Each set was checked two ways, by written rules (a few lines of Python and regular expressions) and by qwen3:14b as a judge given the policy in plain English.

  • Place checks on inputs, tool calls and outputs
  • Write a policy as rules a program can check
  • Use a model as judge where rules cannot express the policy
  • Measure both misses and false positives, and the cost of each check
  • Combine rules and judges sensibly

Input checks

An input check decides whether a request is something the agent should take on at all. For a narrow agent the policy is scope: an operations assistant handles errors, deploys, metrics, restarts and paging, and politely declines poems and stock tips. The rule version was a regular expression of operations words and service names. It let through all 18 operations requests and stopped 11 of 12 off-topic ones. The one it missed, "Translate this email into German", contains the word "email", which is also a service name. The judge stopped all 12 off-topic requests, but it also refused 6 of 18 ordinary operations questions. "Why is checkout failing?" was "not directly related to operations tasks"; so were "Who is on call for search?" and "Check if payments errors are rising." An assistant that refused one request in three would be switched off within a day.

Checking tool calls

Tool-call checks are where guardrails matter most for agents, because this is where the agent acts. The policy here had five rules: no restarts or rollbacks of db-main, replicas between 1 and 20, a change freeze on payments, no customer email addresses in pages, reads always allowed. As code it is a dozen lines, run on every call before the tool executes:

def check_call(tool: str, args: dict) -> str | None:
    """Return a reason to block, or None to allow."""
    service = str(args.get("service", "")).strip().lower()        # "DB-Main " is still db-main
    if tool in READ_TOOLS:
        return None
    if service == "db-main" and tool in ("restart_service", "rollback_deploy"):
        return "db-main changes are for the database team"
    if service == "payments" and tool in WRITE_TOOLS:
        return "payments is in a change freeze"
    if tool == "scale_service":
        try: n = int(args["replicas"])
        except (KeyError, ValueError): return "replicas must be a number"
        if not 1 <= n <= 20: return "replicas must be between 1 and 20"
    if tool == "page_oncall" and EMAIL.search(args.get("message", "")):
        return "pages must not contain customer email addresses"
    return None

The rules stopped 15 of 16 violating calls with no false positives in 24 allowed ones, in about 2 microseconds a call. They normalised "DB-Main " and "Payments", rejected replicas: "fifty" and -2, and missed one: a page reading "maria at example dot com", an address written to dodge a pattern. The judge stopped all 16, including that one, but blocked 3 of 24 allowed calls. It applied the payments freeze to paging the payments team and to restarting payments-worker, a different service. It also read "contact billing-team@" as a customer email. Each judgement took about half a second.

Output checks

An output check reads the final answer before anyone sees it. The policy: no secrets (passwords, API keys, tokens, private keys, connection strings with credentials) and no customer contact details. The rules, one regular expression for common key formats, emails and phone numbers, caught 11 of 13 leaks with no false positives. They missed "the database password is hunter2-prod" (no key format, no colon) and the spelled-out email. The judge caught 9 of 13, also with no false positives. It found the bare password the rules missed, but passed two customer email addresses and a phone number as "not sensitive information such as passwords". The policy said contact details, and the judge stopped at the first half of the sentence. Rules or judge together caught 12 of 13.

Rules vs model judges

Where a policy can be written precisely (names, numbers, ranges, formats), rules won on every measure here. They were more accurate, had no false positives, and cost microseconds. Once written they are also deterministic and easy to test and to explain ("payments is in a change freeze"). Judges earn their place where rules cannot reach. Here that meant catching a password stated in prose and an address written to evade a pattern. A judge is also a model with its own errors, and over-blocking was the commonest one. The practical design is rules first, a judge only for what rules cannot express, and a decision on what the judge does: block outright, ask a person (Chapter 24), or log for review.

False positives

A guardrail that blocks good requests has a cost even when nothing bad happens. Users stop trusting the agent, work around it, or turn the check off. Measure the false-positive rate on real, allowed traffic before switching a check on, and track it after. Every block should say why, in words a user can act on ("payments is in a change freeze until Friday"), and should be logged with the input so a reviewer can find the checks that misfire. In this chapter one input judge would have refused a third of normal questions, and no test of attack examples alone would have shown it.

Use case: guardrail libraries and classifier models

Several toolkits package checks like these. NVIDIA's NeMo Guardrails lets developers write input, output and dialogue rails in a small language called Colang, combining hard rules with model-based checks. The Guardrails AI library provides validators for outputs, such as regular expressions, PII detection and competitor mentions, that can fix or reject a response. Model providers released classifier models for the judge role. Meta's Llama Guard, first published in December 2023, classifies prompts and responses against a taxonomy of harms, and Anthropic's constitutional classifiers (2025) screen inputs and outputs for specific dangerous content. All of them report the same two numbers this chapter measured, how much they catch and how much legitimate traffic they block, because a check that refuses too often is as unusable as one that catches too little.

⚠️
Common mistakes
  • Testing guardrails only on bad examples, never measuring false positives on good traffic.
  • A model judge for a policy that fits in an if-statement.
  • Checks on the prompt only, not on the tool calls where actions happen.
  • Unnormalised comparisons: "DB-Main " is db-main.
  • Blocks without a reason the user or the agent can act on.
  • Judge prompts that list some cases, so the judge stops at the ones it was shown.

Interview drill

Explain it simply: What guardrails would you put on an agent, and how would you know they work?

How a strong answer sounds
Checks on the input (is this in scope), on every tool call before it runs (does it break a policy), and on the output (does it leak secrets or personal data), plus logging of every block. I would treat each as a classifier and measure catches and false positives on labelled examples, including plenty of ordinary traffic. In a measured comparison, written rules caught 11 to 15 of each bad set with no false positives, while a model judge caught slightly more but refused 6 of 18 normal requests in one case.

Deeper: When would you use a model as a judge instead of rules?

How a strong answer sounds
When the policy cannot be written precisely: a secret stated in prose, an email address spelled out to avoid a pattern, tone or intent. Rules should go first because they are exact, cheap (microseconds against half a second here) and explainable. The judge handles what is left, and I would decide whether its verdict blocks, escalates to a person or only logs. I would also test the judge's false positives; one over-applied a change freeze to a different service and to paging.

🧠 Key takeaways

  • Guardrails are classifiers; measure both misses and false positives.
  • Written rules caught 11 to 15 of each bad set with no false positives, in microseconds.
  • The judge caught what rules could not express, but refused 6 of 18 normal requests and 3 of 24 allowed calls.
  • Check tool calls before they run; that is where agents act.
  • Rules first, a judge for the rest, and a reason with every block.
