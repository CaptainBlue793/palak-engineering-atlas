What an Agent Is (and When Not to Build One)

An agent is a program in which a language model decides its own next step: which tool to call, with which arguments, whether to look further or to stop. Everything else in this course follows from that one freedom. It is what lets an agent handle a problem nobody planned for, and it is what makes an agent slower, costlier and harder to test than code that follows a fixed path.

This chapter separates three designs, a single prompt, a fixed workflow and an agent, and then measures them against each other with qwen3:14b on a small simulated production estate: twelve incidents, each with a simple lookup and a real investigation. The result is the rule of thumb for the whole course: build the simplest design that can do the task, and use an agent only where the path cannot be written down in advance.

  • Tell a prompt, a workflow and an agent apart by who decides the next step
  • Describe the think, act, observe loop
  • Treat autonomy as a dial, not a yes-or-no choice
  • Recognise tasks where a fixed workflow is as good and far cheaper
  • Know what an agent does not fix: missing data, a weak method, misleading evidence

Prompt, workflow, agent

The useful distinction is who decides the next step.

  • A prompt: one model call. The model sees only what you put in the prompt and decides nothing beyond its reply.
  • A workflow: your code decides the steps. It fetches the data, calls the model one or more times in a fixed order, and may branch on the results, but every possible path is written in the code.
  • An agent: the model decides the steps. It is given tools and a goal, and in a loop it chooses what to call, reads the result and chooses again, until it decides it is done.

A workflow can use a model at every step and still not be an agent. An agent can be one line of loop around a model call. The question is only where the path comes from.

# a fixed workflow: the code knows the steps
def top_error(service: str) -> str:
    data = get_errors(service)                           # step 1, always
    return ask(f"What is the most frequent error and how many times did it occur?\n\n{data}")   # step 2, always

# an agent: the model chooses the steps
def investigate(question: str) -> str:
    return run_agent(question, tools=[list_services, get_errors, get_metrics, get_deploys, get_dependencies], max_steps=15)

The think, act, observe loop

Inside every agent is the same loop. The model thinks: it reads the transcript and decides what to do. It acts: it asks for a tool call, which your code runs. It observes: the result is appended to the transcript. Then it thinks again, now knowing more. The loop ends when the model writes an answer instead of a tool call, or when your code stops it. Chapter 2 builds this loop in full; everything after that is about doing each part of it well.

Autonomy as a dial

Between a single prompt and an agent that acts on its own there are several positions, and most good systems sit somewhere in the middle. Each step to the right lets the model decide more, handles more surprises, and costs more to run, test and trust.

One callSummarise this text. Nothing to decide.
Fixed chainFetch, then summarise, then format. The code decides.
RouterThe model picks one of several fixed paths.
Agent with toolsThe model chooses tools in a loop; a person sees the result.
Acting agentThe model changes real systems without a person in between.

Moving right is a decision to make deliberately, for a reason the task supplies: the steps depend on what the earlier steps find. The release agent in P7 shows that you can also move left inside one system, letting the model choose freely where it is safe and fixing the order where it is not.

When a workflow is better

The measurement: a simulated estate of ten services with error logs, metrics, deploy histories and dependencies, and twelve incidents in which checkout fails because of a bad deploy somewhere: in checkout itself, or one or two services further down the chain of calls. Each incident got two tasks. The first was a lookup with a known path: "what is the most frequent error on inventory, and how many times did it occur?"

Without tools, the model answered all 12 lookups with a specific, invented error and count ("Incorrect item count, occurring 12 times"), never once saying it could not know. With a fixed workflow (code fetches the errors, one model call reads them) it answered 12 of 12 correctly, using 74 input tokens and 0.3 s per task. With an agent it also answered 12 of 12, but it first had to decide to call the tool: 2 model calls, 774 input tokens and 0.76 s per task. Same accuracy, ten times the tokens. When you know the steps, write them down.

What agents cannot fix

The second task was an investigation: "Checkout is failing. Find the service where the problem starts and the deploy that caused it." Here the path depends on the evidence: checkout's errors say "503 from payments", so the next step is payments, and so on. A fixed workflow that reads checkout's errors, metrics and deploys can only solve the incidents caused inside checkout: 4 of 12. The agent could follow the chain. It mostly did not: it read checkout's errors and deploys, then blamed the most recent harmless deploy on checkout. It solved 5 of 12, only one of them below checkout.

Given the method in its system prompt, four sentences saying to follow "503 from X" to X until reaching a service whose errors are its own, the same agent solved 7 of 12, including 5 of the 8 deeper incidents, at 6 model calls and 3,463 tokens per task. Its remaining failures are the instructive ones. Three times it reached the right service and picked the wrong deploy, matching on a keyword in the change description. Twice a checkout error that mentioned "cache stampede" sent it to the cache service, though the bad deploy was in checkout. An agent does not supply missing data (the prompt-only answers were invented), a method nobody gave it, or the judgement to doubt misleading evidence. Those come from tools, prompts and checks, which is what the rest of this course builds.

Use case: "Building effective agents"

In December 2024 Anthropic published "Building effective agents", drawn from its work with teams building agents on Claude. It draws the same line as this chapter: workflows, where models and tools are orchestrated through predefined code paths, and agents, where the model dynamically directs its own process and tool use. It catalogues common workflow patterns (prompt chaining, routing, parallelisation, orchestrator and workers, evaluator and optimiser) and advises finding the simplest solution possible and adding complexity only when it demonstrably improves results, noting that agents trade latency and cost for better task performance and that many applications need no more than a single well-prepared model call with retrieval and examples. It observed that the most successful implementations used simple, composable patterns rather than complex frameworks. The lookup results here are that advice measured: the agent was as accurate as the workflow and ten times as expensive.

⚠️
Common mistakes
  • Building an agent for a task whose steps you could write down, and paying ten times the tokens for it.
  • Asking a model about live data without giving it tools; it invented an answer 12 times in 12.
  • Assuming tools make the agent use them well; without a method it stopped after the first service.
  • Judging an agent on the incidents it got right instead of the share it gets right.
  • Treating autonomy as all or nothing instead of choosing where on the dial each part of the task belongs.
  • Expecting the agent to doubt misleading evidence that nothing in its tools or prompt helps it check.

Interview drill

Explain it simply: What is the difference between an LLM workflow and an agent, and how do you choose?

How a strong answer sounds
In a workflow, my code decides the sequence of steps, calling the model at fixed points; in an agent, the model decides the next step itself, choosing tools in a loop until it judges the task done. I start from the simplest design that can work: a single call if the information is already in the prompt, a workflow if I can write the steps down, and an agent only when the steps depend on what earlier steps find, like following an error from service to service. I would measure it: on simple lookups an agent matched a fixed workflow's accuracy at ten times the tokens, while on open-ended investigations the workflow could not go beyond the first service.

Deeper: Your team's incident agent finds the root cause less than half the time. What would you look at before changing models?

How a strong answer sounds
I would read traces of the failures and classify them. In a measured version of this, most failures were the agent stopping too early: it read the symptom service and blamed its latest deploy without following "503 from payments" downstream. Giving it an explicit method in the system prompt raised success from 5 to 7 of 12. The remaining failures were different: picking the wrong deploy by keyword, and being misled by an error message that mentioned another component. Those call for better tools, such as one that returns errors with their source service, or a check that the chosen deploy's time matches when errors began, and for an evaluation set that covers these cases. Only after that would I compare models on the same set.

🧠 Key takeaways

  • A workflow's code decides the steps; an agent's model decides them.
  • Autonomy is a dial: give the model only as much choice as the task needs.
  • On lookups with a known path, the agent matched the workflow (12 of 12) at ten times the tokens.
  • Without tools the model invented live data 12 times in 12.
  • On open-ended investigations the agent could go where the workflow could not, but only with a method: 5 of 12 without, 7 of 12 with.
