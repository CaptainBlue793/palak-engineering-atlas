Choosing a Model for an Agent

An agent asks more of a model than a chatbot does. It must pick the right tool, fill in exact arguments, notice when it should not call a tool at all, read the results, and keep going for many steps. And every step costs time and money, so a model that is slightly better but five times slower can make an agent worse to use. Choosing a model means measuring those things on your tasks, not reading a leaderboard.

Every measurement in this course uses one model, qwen3:14b, so this chapter measures the choices you have within a model and the method for comparing models: thinking on or off, context size, and routing between a fast mode and a slow one. It uses two tool-calling tests of 30 single requests each, an easy one and a hard one, and the twelve incidents. The same harness, pointed at other models, is how you would choose between them.

  • List what an agent needs from a model
  • Build a small tool-call test with requests that should not call tools
  • Measure what thinking buys and what it costs
  • Estimate latency and cost per task, not per token
  • Route between a fast and a slow mode with an evidence check

What an agent needs from a model

Five abilities, in roughly the order they fail. Calling tools correctly: the right name, arguments of the right type, exact values. Not calling tools when a request is underspecified or out of reach, and asking instead. Reading results and acting on what they say rather than what was expected (Chapter 18). Staying on task for many steps without looping or stopping early. And speed: an agent makes many calls per task, so a model's per-step latency is multiplied. A good test covers all five with your tools and your kind of requests.

Tool-call accuracy

The first test was easy: 20 clear requests with obvious tools ("Restart the cache", "Roll back auth v3.12.4", "Open a SEV2 ticket titled …") and 10 that need no tool ("What does p99 latency mean?"). With thinking off, qwen3:14b got 30 of 30 in 0.43 seconds per request. A test the model passes perfectly tells you nothing about the differences between options, so the second test was harder. It used informal names ("the database", "the edge proxy"), arithmetic ("double checkout's replicas; it runs 6"), two requests in one message, requests no tool can do ("increase the database's disk to 2 TB"), and underspecified requests that should be questions, not calls ("Restart it.").

With thinking off: 25 of 30. Three of the five misses were underspecified requests acted on with guesses. "Restart it." restarted checkout. "Get the metrics." fetched checkout's. "Roll back the bad deploy." rolled back checkout v1.2.3, a version that appeared nowhere. The other two passed made-up service names through: "storefront" and "edge-proxy" instead of checkout and gateway. A model that guesses arguments is the most dangerous failure for an agent with write tools. Test for it explicitly, and gate writes (Chapter 24).

Reasoning models

qwen3 can think before answering, producing hidden reasoning tokens first. On the hard test, thinking on scored 26 of 30. It asked instead of guessing on all three underspecified requests, but it introduced two new misses: it rewrote a ticket title the user had dictated, and it read "the version before 3.4.0" as "roll back to 3.3.0" (an ambiguous request in fairness). It still invented "storefront" and "edge-proxy". Each request took 2.75 seconds instead of 0.37, with about 220 output tokens instead of 28.

On the incidents the trade was worse. Thinking on solved 10 of 12 against 11 with thinking off, and took 26.7 seconds per run instead of 3.1, writing about 9,000 characters of reasoning per incident. For a well-specified, tool-driven investigation, the tools supply the information and the method is in the prompt, so extra reasoning mostly adds time. Thinking helped where the model had to decide whether to act on an ambiguous request. Measure it per task type; do not switch it on everywhere.

Context size

Running the incidents with a 4,096-token context instead of 16,384 changed nothing: 11 of 12 both times. The largest single prompt in any step was about 1,040 tokens. Context size matters when the transcript grows (Chapter 10), where an Ollama context that is too small silently drops the start, so set it from the largest prompt your agent actually produces, with a margin. A larger context reserves more memory on the GPU and can slow every request, even when the prompt is short.

Latency and cost

Compare models by cost per task, not per token. An incident took 8 to 9 model calls. With thinking off that came to 3.1 seconds and about 240 output tokens. With thinking on it was 26.7 seconds and about 2,100 output tokens, nine times the output a hosted API would bill. A model with half the price per token and twice the steps costs the same, and a slower model with fewer steps can be faster overall. The only reliable comparison is to run your task suite on each candidate and record success rate, seconds and tokens per task. That is what the routing below does within one model.

Routing between models

Routing sends easy work to a fast, cheap option and hard work to a slow, strong one. The difficulty is knowing which is which, and here the external check from Chapter 14 did the job. Each incident ran first with thinking off. A check that does not know the answer then asked whether the version named was the latest deploy of a service whose own errors did not come from elsewhere. If not, the incident ran again with thinking on.

def solve(incident):
    fast = run_agent(TASK, incident.tools(), SYSTEM, think=False)
    if evidence_supports(fast):                   # named version = latest deploy of a service with its own errors
        return fast.answer
    return run_agent(TASK, incident.tools(), SYSTEM, think=True).answer

The check agreed with the true result on all 12 incidents. It passed the 10 correct fast answers and flagged the 2 wrong ones. Re-running those two with thinking fixed one. Routed, the agent solved 11 of 12 in an average of 7.6 seconds, against 10 of 12 for the fast pass alone in the same session (about 3 seconds) and 10 of 12 in 26.7 seconds for thinking on. The same pattern works across models: a small model first, a large one when a check fails. It only works if the check is good. The first version of this check, which only asked that the version appear in some deploy list, passed every answer, wrong ones included, and so never escalated anything.

One more number to keep in mind: the thinking-off runs scored 11 of 12 in one session and 10 of 12 in another, with the same settings and temperature 0. Differences of one incident in twelve are within run-to-run variation (Chapter 29), so compare options over repeated runs before deciding.

Use case: leaderboards and model cascades

Public benchmarks track exactly the abilities listed above. The Berkeley Function-Calling Leaderboard (BFCL) scores models on single, parallel and multi-turn tool calls, including cases where no function should be called. Agent benchmarks such as τ-bench (Sierra, 2024) run multi-turn customer-service tasks against tools and policies, and report pass^k, the chance of succeeding on every one of k tries. Leaderboards are a shortlist, not an answer: they use other tools and tasks, and differences of a few points often vanish on yours. On the cost side, FrugalGPT (Chen, Zaharia and Zou, 2023) showed that a cascade, which tries cheaper models first and escalates only when a scorer is unsure, could match the best single model's accuracy at a fraction of the cost. Model providers now build the same idea into products, with routers that choose between fast and reasoning modes per request.

⚠️
Common mistakes
  • Choosing from a leaderboard without running your own tasks.
  • Tool tests with no "do not call" cases, so guessing is never caught.
  • Thinking on everywhere: 8 times slower on incidents for no gain here.
  • Comparing price per token instead of cost per completed task.
  • Routing on a weak check that passes wrong answers.
  • Deciding on a one-in-twelve difference from a single run.

Interview drill

Explain it simply: How would you choose a model for an agent?

How a strong answer sounds
Build a small test suite from my own tasks: single tool calls including ones that should not call a tool, and complete multi-step tasks with a checkable outcome. Run each candidate, and each setting such as thinking on or off, several times, recording success rate, seconds and tokens per task. Choose on cost per successful task, not price per token or a leaderboard. In one measurement, thinking made a model ask instead of guess on vague requests, but made full investigations eight times slower with no gain.

Deeper: Your strong model is too slow and your fast model makes mistakes. What can you do?

How a strong answer sounds
Route between them with a check. Run the fast option first, verify its result against evidence it gathered (without knowing the answer), and escalate only when the check fails. Measured on twelve incidents, a fast mode plus an evidence check plus a slow mode on failure solved 11, against 10 for either alone, at 7.6 seconds per incident instead of 26.7. The check has to be strict: a weaker version passed every answer, including the wrong ones, and so never escalated.

🧠 Key takeaways

  • Test with your tools, and include requests that should not call a tool.
  • Without thinking, the model guessed arguments for vague requests, including a version that did not exist.
  • Thinking fixed the guessing but made investigations 8 times slower with no gain.
  • Compare cost and time per completed task, over repeated runs.
  • Fast first, slow when an evidence check fails: 11 of 12 at 7.6 s per incident.
