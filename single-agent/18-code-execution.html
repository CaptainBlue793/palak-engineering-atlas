Code Execution as a Tool

A model cannot count 5,000 rows in its head, but it can write three lines of pandas that do. A code-execution tool turns arithmetic, filtering and statistics from things the model guesses at into things a computer does. It also adds new ways to fail: code that crashes, code that runs and prints nothing, and code that runs, prints a number, and answers a slightly different question.

This chapter measures them. qwen3:14b answered 20 questions about a 5,000-row request log (counts, percentiles, top clients, error rates in an hour) with six versions of the tool. The model was the same throughout; only the tool changed. Correct answers went from 2 of 20 to 19 of 20.

  • Explain when running code beats reading data
  • Write a Python tool with a timeout, a clean environment and capped output
  • Recognise the empty-output failure and fix it in the tool
  • Give the model the file's shape so it stops guessing column names
  • Know which wrong answers still get through, and why

Why run code

The baseline tool returned 100 lines of the file at a time, as a person might scroll through it. The model read the first 100 lines, once, and answered from them: "the file contains 5,001 rows" (it counted the header line), "payments received 15 requests in the first 100 lines", a p95 latency of 286 ms where the true value was 1,598. 2 of 20 were right, and both were lucky: "payments" had the most 503 responses and the highest average latency in the first 100 rows as well as in all 5,000. Reading 5,000 rows 100 at a time would have taken 50 calls and far more than the 16k context window. Questions about a whole dataset need a tool that computes over the whole dataset.

A Python tool

The tool runs a script in a separate process, in the folder with the data, and returns what it printed. Three details matter even before proper sandboxing (Chapter 23): a timeout, so a loop that never ends costs 30 seconds and not the session; a clean environment, so the script does not inherit API keys from the agent's process; and capped output, keeping the start and the end, because a script that prints a whole DataFrame would otherwise flood the context (Chapter 10).

def run_python(code: str) -> str:
    path = os.path.join(WORK, "snippet.py")
    open(path, "w").write(code)
    try:
        r = subprocess.run([sys.executable, path], capture_output=True, text=True, timeout=30, cwd=WORK,
                           env={"PATH": os.environ["PATH"]})          # no secrets passed through
    except subprocess.TimeoutExpired:
        return "error: timed out after 30 s"
    out = (r.stdout + r.stderr).strip()
    if len(out) > 3000:                                          # keep the start and the end
        out = out[:1000] + f"\n[... {len(out) - 2000} characters cut ...]\n" + out[-1000:]
    return f"exit code {r.returncode}\n{out}"

With only "pandas is installed" in the description, the model guessed the column names. It wrote df['timestamp'] and df['duration'], and 27 of its 45 scripts failed, mostly with KeyError. It recovered twice. Five answers ended on the column problem instead ("please check the column names and provide the correct one"), one of them listing columns the file does not have. It never printed df.columns to find out. 4 of 20. Listing the six columns in the tool description cut failures to 4 of 24 scripts and doubled the score to 9 of 20.

Reading errors

Nine of 20 with the right column names was still poor, and the cause was not an error at all. In 12 of the 20 first scripts, the model ended with a bare expression, notebook style:

num_404 = data[data['status'] == 404].shape[0]

num_404

In a notebook that shows the value. In a script it does nothing. The tool returned exit code 0 and nothing else, and the model answered anyway: "There were 1234 404 responses" (the true count was 153), "the maximum latency recorded was 1234 milliseconds", "the service with the highest average latency is service_B", "the client that sent the most requests is client_123". Eleven of those twelve runs were wrong. An empty result is easy to miss, and the model filled the gap with placeholder values that look like answers.

The first fix was in the tool's reply: when nothing is printed, say so. "(no output: the script printed nothing. Use print() to see a value.)" The invented numbers stopped, but the score stayed at 9 of 20. Of the 11 runs that got the message, the model ran another script in 3. In the rest it passed the problem to the user ("please try running it again with a script that includes a print statement"). That answer is honest, but it is still not an answer.

Iterating to a result

The second fix made the tool behave the way the model expected: if the script ends with a bare expression, print its value, as a notebook cell does. It is a few lines with Python's ast module, and it took the score to 16 of 20, with one empty output left. That came from a final expression inside an if, which notebooks would not show either.

def show_last_value(code: str) -> str:
    tree = ast.parse(code)
    if tree.body and isinstance(tree.body[-1], ast.Expr):      # ends with a bare expression
        last = tree.body[-1].value
        tree.body[-1] = ast.Expr(ast.Call(ast.Name("print", ast.Load()),
                                           [ast.Call(ast.Name("repr", ast.Load()), [last], [])], []))
    return ast.unparse(ast.fix_missing_locations(tree))

The third fix added the first three rows of the file to the tool description, so the model could see that status is a number, not text, and that timestamps look like 2026-10-20T13:07:51Z. Without the rows, the model filtered on status == '503' (a string, which matches nothing) and on timestamps starting 2023-04-05T13:, a date it made up. Both scripts ran without error and returned an empty result or zero. With the rows: 19 of 20.

What still gets through

The last miss is the kind no tool change catches. Asked what fraction of payments requests failed between 13:00 and 14:00, the model filtered with dt.hour.between(13, 14), which includes the 14:00 hour, and answered 13.3%. The true figure was 25.8%. In the run before, it dropped the payments filter and divided by all 5,000 requests: 1.9%. Both scripts ran cleanly and printed one plausible number. Code that runs is not code that answers the question. For anything that matters, make the script print what it filtered on (the row count, the time range it actually covered) so a person or a check (Chapter 14) can see the question it answered.

Limits and timeouts

The limits in this tool are for keeping the agent's own context and loop healthy, not for security. A 30-second timeout stops one bad loop from stalling the session. A 3,000-character cap, keeping the start and the end, stops one print(df) from filling the context while still showing a traceback's last line. A working folder keeps files the script writes in one place. None of this stops a script from deleting files it can reach, opening network connections or using all the memory. Code the model writes is untrusted code. Run it in a container or a locked-down process (Chapter 23), and never in the process that holds your credentials.

Use case: Code Interpreter and CodeAct

OpenAI's Code Interpreter (later Advanced Data Analysis) gave ChatGPT a sandboxed, stateful Jupyter environment in 2023: users uploaded a spreadsheet and the model wrote and ran Python against it, keeping variables between calls, and seeing a cell's last value just as in a notebook, the fix that mattered most here. The CodeAct paper (Wang and colleagues, 2024) went further and made Python the agent's action format for every action, not only for data, reporting higher success than JSON tool calls on its benchmarks because code can loop, branch and combine tools in one step. Both designs rely on the lessons measured in this chapter: the model writes code the way it has seen code written, in notebooks, so the tool should behave like one, and the environment has to be isolated because the code is written by a model.

⚠️
Common mistakes
  • Returning nothing when nothing was printed, so the model invents a value.
  • Not describing the data: column names, types and a few sample rows belong in the tool description.
  • Trusting a clean run: exit code 0 says the code ran, not that it answered the question.
  • Unbounded output that floods the context when the model prints a whole table.
  • No timeout, so one endless loop stalls the agent.
  • Running model-written code in the agent's own process, with its credentials and files.

Interview drill

Explain it simply: Why give an agent a code-execution tool, and what does the tool need to do well?

How a strong answer sounds
Because models are bad at counting and arithmetic over a lot of data, and code is exact. Asked 20 questions about a 5,000-row log with only a file reader, a model got 2 right. With Python it can compute over all the rows. The tool should run code in a separate, isolated process with a timeout and capped output, describe the data (columns, types, a few rows), and return something useful every time: the output, the last expression's value as a notebook would, or an explicit "nothing was printed". Those tool changes alone took the same model from 4 to 19 of 20.

Deeper: Your data-analysis agent sometimes reports numbers like 1234 that appear nowhere in the data. What is happening, and how would you fix it?

How a strong answer sounds
Likely its script ran and printed nothing, usually because it ended with a bare expression as in a notebook, and the model filled the gap with a placeholder value. In a measured case 12 of 20 first scripts did this and 11 of those answers were wrong, with values like 1234 and "service_B". I would make the tool print the value of a final expression, return an explicit message when there is no output, and check in an evaluation that every number in an answer appears in some tool output. A message alone was not enough: the model then often gave up instead of rerunning.

🧠 Key takeaways

  • Reading the file in pages answered 2 of 20 questions; questions about a whole dataset need code.
  • Without column names the model guessed them and 27 of 45 scripts failed.
  • Scripts that printed nothing led to invented answers such as 1234 and "service_B".
  • Showing the last expression's value, as a notebook does, and three sample rows took the score to 19 of 20.
  • A clean run can still answer the wrong question; make scripts print what they filtered on.
