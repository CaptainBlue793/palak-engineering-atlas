Tokens, Context & Cost

A chatbot sends one prompt and gets one answer. An agent sends a prompt, reads the reply, runs a tool, appends the result and sends the whole thing again, step after step. Every step reads everything before it. That one fact decides an agent's latency, what it costs on a hosted model and when it runs out of room. It is also the fact most often missing from a first estimate.

This chapter measures a real eight-step agent run with qwen3:14b, step by step: tokens in, tokens out, time spent reading and time spent writing. Then it changes two things and measures again: turning the model's thinking on, and putting the current time at the top of the system prompt.

Tokens

Models read and write tokens: pieces of words, numbers and symbols from a fixed vocabulary. English prose runs at roughly three-quarters of a word per token, but agent traffic is not prose. Log lines, JSON, IDs and timestamps split into many short tokens. One line of the logs used below (14:07:31 checkout ERROR 503 upstream payments timeout req=48213977) is about 26 tokens; a tool result of 60 such lines added about 1,600 tokens to the transcript. Count tokens from the server's response, not by estimating from characters.

Context windows

The context window is the most tokens a model can take in one request, prompt and output together. qwen3:14b was trained for 40,960; this course runs it with num_ctx 16,384 so it fits on a 16 GB GPU (P1). In the run below, the transcript reached 9,818 tokens after six tool results, 60% of the window, for a question about six services. Six more services and it would not have fitted. Agents hit the window not because one message is large but because every message stays.

Prefill and generation

Each request has two phases. Prefill reads the prompt; it processes all the tokens in parallel, so it is fast per token. Generation writes the reply one token at a time, at about 80 tokens a second here. Servers also keep a prompt cache: if a request starts with exactly the same tokens as the last one, the work for that prefix is reused and only the new tokens are read. Measured on a 4,829-token prompt: 1,579 ms the first time, 14 ms the second, 27 ms with one short turn appended, and 1,383 ms again after changing a single word in the system prompt, because everything after the change had to be reread. Ollama's prompt_eval_count reported 4,829 tokens all four times; only the time shows the cache.

r = ollama.chat(model="qwen3:14b", messages=messages, tools=tools, think=False, options=OPTIONS)
step = {
    "prompt_tokens": r.prompt_eval_count,                # the whole prompt, cached or not
    "output_tokens": r.eval_count,
    "prefill_ms": r.prompt_eval_duration / 1e6,         # small when the prefix was cached
    "generate_ms": r.eval_duration / 1e6,
}

Cost per call

On a hosted model you pay per token, with output tokens usually priced several times higher than input. Most providers now discount input tokens that hit their prompt cache, often heavily. A local model has no bill, but the same quantities show up as time: input tokens as prefill, output tokens as generation, which is almost always the larger share. Either way, the numbers to log per step are the same four: prompt tokens, how many of them were cached, output tokens, and time.

Why loops multiply cost

Step n of an agent reads the system prompt, the tool definitions and everything from steps 1 to n − 1. If each step adds roughly the same amount, the total input over a run grows with the square of the number of steps. Measured: the final transcript was 9,818 tokens, but the eight requests together read 35,818, 3.6 times as much. Output was 184 tokens in total. On a hosted model, that run's bill is almost entirely input; on a local one, the cache is what keeps prefill from growing with it.

Two changes showed how easily the picture shifts. Thinking on: the model wrote 3,816 tokens of reasoning and answer in four steps instead of 184 in eight, spent 49 s generating instead of 2.4 s, and stopped after checking two of the six services. A timestamp at the top of the system prompt: the same 8 steps and almost the same tokens, but every request now differed from the last in its first line, so the cache never matched. Prefill rose from 3.2 s to 10.9 s, and the last step took 3.1 s to read its prompt instead of 0.6 s. Put anything that changes per request at the end, never the start.

Use case: prompt caching at the model providers

Anthropic introduced prompt caching for Claude in August 2024. You mark where a reusable prefix ends, and later requests that start with the same tokens read it from the cache at a fraction of the normal input price, while writing it to the cache costs a little more than normal. OpenAI added automatic caching for prompts over 1,024 tokens in October 2024, with cached input tokens billed at a discount. Google offers context caching for Gemini. All of them match on an exact prefix, which is why provider guidance says to put stable content first: tools, system prompt, then the conversation, with anything that varies at the end. The timestamp run in this chapter is the failure every one of those guides warns about, measured on a local server that caches in the same way.

⚠️
Common mistakes
  • Estimating cost from the final transcript instead of summing every step's prompt.
  • Putting a timestamp, request ID or user name first in the system prompt, so the cache never matches.
  • Turning on thinking for every step without measuring what it adds in tokens, time and behaviour.
  • Returning whole log files to the model when a count or the top lines would do.
  • Logging only total tokens, not per step and not cached versus uncached.
  • Forgetting the window: six tool results used 60% of a 16k context here.

Interview drill

Explain it simply: Why can an agent that takes 20 steps cost far more than 20 times a single chat request?

How a strong answer sounds
Because each step sends the whole transcript again: the system prompt, the tool definitions and every earlier reply and tool result. If each step adds about the same amount, step 20 reads twenty steps' worth, step 19 reads nineteen, and the total input grows with the square of the number of steps. In a measured eight-step run the final transcript was about 9,800 tokens but the requests read about 35,800 in total. Prompt caching softens it, because a stable prefix is cheap to reread, and so does keeping tool results small.

Deeper: After a small prompt change, your agent's latency per step doubled and its hosted bill went up, though token counts barely moved. What would you suspect?

How a strong answer sounds
That the prompt cache stopped matching. Caches reuse an exact prefix, so anything that varies per request near the start of the prompt (a timestamp, a request ID, a user's name, tools sent in a different order) makes every request a cache miss. Token counts stay the same, but every token is read and billed at the full rate. Measured locally, a timestamp on the first line took prefill for an eight-step run from 3.2 to 10.9 seconds. I would compare cached-token counts or prefill time per step before and after the change, move the varying part to the end of the prompt, and add a test that checks consecutive requests share their prefix.

🧠 Key takeaways

  • Every step reads the whole transcript: 8 steps read 35,818 tokens to answer from 9,818.
  • Input cost grows with the square of the number of steps; output was under 1% of tokens here.
  • Prompt caches reuse an exact prefix: keep what is stable first, put what varies last.
  • Thinking multiplied output tokens by 20 and generation time by 20, and did not make the run more thorough.
  • Log prompt, cached and output tokens per step; the totals alone hide where the cost is.
