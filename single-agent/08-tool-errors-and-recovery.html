Tool Errors & Recovery

Tools fail: a service times out, a backend is briefly down, the model passes an identifier the system does not recognise. In ordinary code an exception stops the program. In an agent, the error becomes an observation: text the model reads before choosing its next step. Whatever that text says is, in effect, the instruction for what happens next.

This chapter measures that directly with qwen3:14b on the 12 incident investigations. In the first experiment, the first call to fetch each service's errors fails with a transient outage, shown to the model as a raw Python traceback, as a plain message, or retried in the tool so the model never sees it. In the second, the deploy system names services differently from every other tool (payments-svc rather than payments), and the error says KeyError, "unknown service", or "unknown service, did you mean payments-svc?".

  • Sort tool failures into transient, caller-fixable and permanent
  • Write error results as observations the model can act on
  • Retry transient failures in code, out of the model's sight
  • Give the model what it needs to fix its own arguments
  • Fail safely when nothing can be fixed

Kinds of tool failure

Three kinds, each with its own handler. Transient failures (timeouts, 503s, rate limits) succeed if you try again soon; the request was fine. Caller-fixable failures (bad argument, unknown identifier, missing field) succeed if the request changes; the model is the one who can change it, if it is told how. Permanent failures (no permission, the data does not exist, the system is down for the day) will not succeed this run; the right move is to stop that line of work and say so (Chapter 7).

Errors as observations

Whatever a tool returns, the model reads. A raw traceback is the worst kind of observation: long, full of irrelevant detail (file paths, object addresses, "Max retries exceeded"), and with no hint of what to do. Measured: when the first fetch of each service's errors came back as a 300-character requests.exceptions.ConnectionError traceback, the agent almost never retried the call (twice after 55 failures). It moved on to metrics, deploys and dependencies for service after service, averaging 15.7 steps (3 runs hit the 20-step limit), and solved 4 investigations of 12 against 9 with no errors. The same outage described in one plain sentence ("the log service is temporarily unavailable (503). This is usually brief: calling get_errors again should work") made the agent retry immediately: 6 of 12, in 10.2 steps.

Retrying in code

Better still is for the model never to see the transient failure. Retried inside the tool (P5), the same outages cost 0.3 s each and were invisible: 10 of 12 investigations, in 8.6 steps, at least as good as no errors at all (9 of 12; the one-incident difference is within run-to-run noise). The model has nothing useful to add to a transient failure. Every error it sees costs a step, tokens, and a chance to wander off.

def get_errors(service: str) -> str:
    for attempt in range(3):
        try:
            return format_errors(logs.top_errors(service, timeout=5))
        except (TimeoutError, ServiceUnavailable):
            time.sleep(random.uniform(0, 0.5 * 2 ** attempt))       # backoff with jitter, out of the model's sight
    return ("error: the log service is unavailable after 3 attempts. This is not caused by your request. "
            "Continue with other tools or report that logs could not be read.")

Letting the model fix arguments

When the request itself is wrong, only the model can change it, and only if the error tells it how. In the identifier experiment, every other tool and every error message said "payments", but the deploy system wanted "payments-svc". With KeyError: 'payments' as the error, the agent solved 0 of 12: it retried the same name, then tried every service in turn (90 failed calls across the twelve runs), then concluded "none of the services have deploys available" and blamed the deploy system. "error: unknown service 'payments'" did no better: 0 of 12, 95 failed calls. Neither message said what a valid identifier looks like. Adding one sentence, "The deploy system uses ids ending in -svc; did you mean 'payments-svc'?", fixed it at the next call: 11 of 12, in 8.7 steps, with 16 failed calls in total.

def get_deploys(service: str) -> str:
    if service not in DEPLOY_IDS:
        hint = difflib.get_close_matches(service + "-svc", DEPLOY_IDS, n=1)
        return (f"error: unknown service id '{service}'. The deploy system uses ids ending in -svc"
                + (f"; did you mean '{hint[0]}'?" if hint else ".") + " Ids: " + ", ".join(DEPLOY_IDS))
    ...

Better still, again, is not to need the fix: let the tool accept either form and translate it, so the identifier mismatch between two systems never reaches the model. Error messages are for the problems you could not design away.

Failing safely

Some errors cannot be fixed this run. The tool's job then is to say clearly that the failure is permanent and not the model's fault, and what the model should do instead ("continue with other tools or report that logs could not be read"), so that it stops spending steps and gives up well. Two more rules. Never let a failing write look like a success: an error result must start with something unmistakable ("error:"), and the loop should not let a final answer claim an action whose tool call failed. And log every error with its tool, arguments and run, because a rising error rate on one tool is often the first sign that something upstream has changed.

Use case: compiler errors that suggest the fix

The Rust and Elm compilers became known for error messages that explain the problem in plain words, point at the exact place, and suggest the likely fix ("did you mean user_name?"), and their maintainers treat unclear messages as bugs. The same idea runs through Python's own recent releases, which added "Did you mean ...?" suggestions for misspelt names and attributes. Agents are the reader those designers had in mind, taken to the extreme: a reader that will do exactly what the message suggests and nothing it does not. The identifier experiment here is the measurement: the same failure, the same model, and 0 of 12 against 11 of 12 depending on whether the message said what would work.

⚠️
Common mistakes
  • Passing raw tracebacks to the model; it retried after 2 of 55.
  • Letting the model handle transient failures the tool could retry in a fraction of a second.
  • Error messages that say what is wrong but not what is right: 0 of 12 either way.
  • Making the model translate between two systems' identifiers instead of doing it in the tool.
  • Not saying whether a failure is permanent, so the agent keeps retrying or keeps wandering.
  • Not logging tool errors, and missing the upstream change they signal.

Interview drill

Explain it simply: A tool your agent uses sometimes times out. Should the model see that error?

How a strong answer sounds
Usually not. A timeout is transient and says nothing about the request, so the tool should retry it with backoff and only report to the model if it keeps failing, in a plain sentence that says the failure is not the model's fault and what to do instead. Errors the model sees cost steps and invite it to change course: in a measured case, showing a transient failure as a raw traceback cut successful investigations from 9 to 4 of 12, a plain message got 6, and retrying inside the tool got 10.

Deeper: Your agent keeps failing on a tool whose error says "unknown service". How do you approach it?

How a strong answer sounds
Read the traces: is the model passing a name the tool does not accept, and does the error tell it what would be accepted? In a measured case the deploy system used ids like payments-svc while every other tool said payments; with "unknown service" the agent tried every service and blamed the system, 0 of 12, and adding "ids end in -svc; did you mean payments-svc?" made it 11 of 12. I would first make the tool accept both forms, because a mismatch between two systems is the tool's job to translate, then keep the improved error for whatever cannot be translated, and add the case to the evaluation set.

🧠 Key takeaways

  • A tool error is an observation; its wording decides the next step.
  • Retry transient failures in the tool: 10 of 12 investigations, against 4 when the model saw raw tracebacks.
  • Write errors in plain words that say what to do: a plain message alone lifted 4 to 6.
  • For caller-fixable errors, say what would work: 0 of 12 became 11 of 12 with "did you mean payments-svc?".
  • Say when a failure is permanent and not the model's fault, so it stops cleanly.
