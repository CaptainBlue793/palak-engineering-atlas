Context Engineering

An agent's transcript is a record of everything that happened. Its context, what the model reads on a given step, does not have to be the same thing. Context engineering is the job of deciding, step by step, what goes into that limited window: which instructions, which history, which tool results in full and which condensed, in what order. It is the step from "send the transcript" to "build the prompt".

This chapter takes the sweep from Chapter 10, ten raw service logs that together overflow the 16k window, and builds each step's context four ways: keep everything; replace older tool results with a placeholder; replace older tool results with a short digest computed by code; keep everything and restate the task at the end. Same model, same tools, same data; only the context changes.

  • Treat the context window as a budget with a plan
  • Decide what to keep in full, what to condense and what to drop
  • Use ordering to keep the task and rules where they survive
  • Condense tool results without losing the answer
  • Build context so the prompt cache still works

The context budget

A window of 16,384 tokens has to hold the system prompt and tool definitions (here about 300 tokens), the task, the history of calls and results, and room for the reply. Plan it like any budget: a fixed allowance for instructions, a ceiling for history, and a rule for what happens when history would exceed it. Without a plan the server applies its own rule. For Ollama that rule was to drop the oldest tokens first, which removed the task, and keeping everything scored 0 of 60 service lines here, exactly as in Chapter 10.

def build_context(transcript: list[dict], budget: int = 12_000) -> list[dict]:
    system, task, history = transcript[0], transcript[1], transcript[2:]
    tool_idx = [i for i, m in enumerate(history) if m["role"] == "tool"]
    keep_full = set(tool_idx[-2:])                                   # the two newest results, verbatim
    out = [system, task]
    for i, m in enumerate(history):
        if m["role"] == "tool" and i not in keep_full:
            m = {**m, "content": digest(m["tool_name"], m["content"])}       # older ones, condensed by code
        out.append(m)
    assert count_tokens(out) <= budget, "still too big: compact further (Chapter 15)"
    return out

What to keep

Keep in full what the next decision needs; condense what only matters as a conclusion; drop what is finished. The two condensing strategies tested here differ only in what replaced the older results. A placeholder ("output of get_errors(checkout) removed to save space") kept the context at 5,000 tokens and scored 17 of 60: the model answered for the two services whose results it could still see and had nothing for the other eight. A digest computed by code from the raw log ("checkout: 40 x certificate verify failed, 9 x client closed request"), the same size, scored 60 of 60. Dropping information is free only if nothing later needs it; condensing keeps the conclusion and drops the bulk.

Who writes the digest matters. Here code computed it, because counting error lines is mechanical and code does it exactly. Where a result needs judgement to condense (a long document, a page of search results), a model can summarise it, at the cost of a call and the risk of dropping the one detail that mattered later (Chapter 15 measures that).

Ordering

Where something sits in the context changes whether it survives and whether it is used. Instructions belong at the start, in the system prompt, where they are stable and cacheable; but the start is also what a truncating server drops first. Restating the task at the end of the context ("Reminder of the task: …") kept it in the part that survived: with everything else unchanged, the score rose from 0 to 41 of 60. The model now produced the right format and the right answer for every service whose log was still in the window, and nothing for the first few, whose logs had been cut. Ordering rescued the instruction; it could not rescue the data.

Trimming tool output

The cheapest context engineering happens before a result ever enters the transcript: return compact results in the first place (Chapter 4, Chapter 10). Condensing in the loop is the second line, for results that must be large at first (a file the agent is editing, a page it is reading) and only need to be large while they are being used. A good rule is "full while it is the newest, condensed once the agent has moved on", which is exactly the digest strategy above.

Prompt caching

Rewriting old messages changes the prompt's prefix, and a changed prefix breaks the cache (P4). Two habits keep both. Condense a result once, at a fixed point (when it stops being one of the newest two), and leave it condensed, so the prefix changes once per result rather than every step. And keep everything stable (system prompt, tools, task) at the start, untouched by compaction. A reminder appended at the end, as in the restating strategy, costs a few tokens and no cache. In this sweep the digest strategy read 5,210 prompt tokens per run in total, against 23,710 for keeping everything, which never gave a right answer.

Use case: clearing old tool results

Coding agents hit this problem first, because file contents and test output are large and arrive at almost every step. SWE-agent's configurable history processors, for example, can collapse older observations to a short note while keeping the latest few in full. Model providers have since built the same idea into their platforms: Anthropic, for instance, introduced context editing for Claude in 2025, which clears stale tool results from the context as a conversation approaches its limit while keeping the record of the calls, and recommends pairing it with a memory store for anything the agent needs to keep. In September 2025 the company described this kind of work under the name "context engineering", alongside compaction and structured note-taking. All of these are versions of the digest strategy measured here: keep the newest results whole, keep a trace of the older ones, and never let the window silently decide what to drop.

⚠️
Common mistakes
  • Sending the whole transcript and letting the server decide what to drop.
  • Dropping old results without a trace, so the model forgets what it found: 17 of 60.
  • Using a model to condense what code can compute exactly, such as counts.
  • Instructions only at the start of a context that may be truncated from the start.
  • Rewriting history every step, so the prompt cache never matches.
  • No token budget and no check before sending.

Interview drill

Explain it simply: What is context engineering for an agent?

How a strong answer sounds
Deciding what the model reads at each step, as opposed to sending the full transcript. The transcript keeps everything; the context is built from it within a token budget: stable instructions and the task first, recent tool results in full, older results condensed, finished work dropped, and sometimes a reminder of the task at the end. In a measured sweep where ten raw logs overflowed the window, sending everything scored zero; replacing older results with code-computed digests, at the same size as simply deleting them, scored 60 of 60 against 17.

Deeper: Your agent forgets findings from early in long runs. You consider dropping old tool results to save space. What would you watch for?

How a strong answer sounds
Dropping is only safe for what no later step needs. Measured, replacing old results with placeholders cut the context to a third and lost most answers, because the model could no longer see what it had found. I would replace each old result with a digest of what it established, computed in code where possible and by a model where judgement is needed; condense each result once when it stops being recent, so the prompt cache survives; keep the task and rules in the stable prefix and restate them at the end of long contexts; and add a token budget check before every call. Then I would test on long runs specifically, comparing answers that depend on early findings.

🧠 Key takeaways

  • The transcript keeps everything; the context is built each step within a budget.
  • Letting the server truncate scored 0 of 60; a plan scored 60 of 60 in a third of the window.
  • Condense old results instead of dropping them: digests 60 of 60, placeholders 17 of 60, same size.
  • Restating the task at the end kept it alive through truncation (0 to 41), but could not restore lost data.
  • Condense each result once and keep the prefix stable, so the cache still works.
