Fine-Tuning a Model for Tool Use

When prompts and tool descriptions are not enough, the next lever is the model's weights. Fine-tuning on examples of your tools being used well can teach exact argument formats, your names for things, and when to ask instead of act. It also costs data collection, training runs, a model to host and version, and re-training whenever the tools change. Most problems that look like they need fine-tuning can be fixed more cheaply first.

This chapter explains when fine-tuning is worth it, how to build the training data from traces, and how LoRA works. It measures the cheaper alternative that every fine-tune should be compared with: putting worked examples in the prompt, either a fixed set or examples retrieved for each request. The test is Chapter 22's hard tool-call test with qwen3:14b. No model was trained for this chapter: the course measures one model, qwen3:14b, and fine-tuning it was out of scope for this machine. The training recipe below is explained, not run.

When to fine-tune

Fine-tune when four things are true. The failure is consistent, the same kind of mistake on the same kind of request. It is not fixed by better tool descriptions, schemas or loop rules (most failures in this course were). You have hundreds to thousands of good examples, or can make them. And the gain is worth hosting and maintaining your own model. Typical good cases are a large fixed set of internal tools with conventions the base model cannot guess, a small model that must match a large one's tool-calling accuracy to save cost or latency, and a strict output format that prompting cannot hold. Typical bad cases are facts that change (put them in retrieval or memory instead) and failures that come from the environment, like the incident every chapter missed until its tools said when errors began (Chapter 37).

Collecting traces

Training data for tool use is conversations: the system prompt with the tool schemas, the user's request, the assistant's tool calls, the tool results, and the final answer. They come from three places. Successful production traces, filtered by a final-state check (Chapter 27) so that only runs that really worked are kept. Corrected failures, where a person or a stronger model fixes the wrong step. And written examples for cases that rarely occur but matter, like asking instead of guessing. Include the cases where the right action is not to call a tool; a dataset of only calls teaches the model to always call. Hold out a test set the model never trains on, and keep it the same across experiments.

LoRA in one page

Full fine-tuning updates every weight of the model, which for a 14-billion-parameter model means storing gradients and optimiser state for all of them. LoRA (low-rank adaptation; Hu and colleagues, 2021) freezes the original weights and learns a small correction for selected weight matrices. A matrix W of size d × d becomes W + B·A, where A is r × d, B is d × r, and the rank r is small, typically 8 to 64. For qwen3:14b, whose hidden size is 5,120, one 5,120 × 5,120 matrix has 26.2 million weights. Its LoRA correction at rank 16 has 2 × 5,120 × 16 = 163,840, about 0.6%. QLoRA goes further and keeps the frozen base in 4-bit precision during training, which is what makes a 14B model trainable on a single consumer GPU at all. The result is a small adapter file applied on top of the unchanged base model; you can keep several for different tasks.

Training

A training run formats each conversation with the model's own chat template, computes the loss only on the assistant's turns (the tool calls and answers), and trains for a small number of passes over the data. More passes overfit: the model memorises the training requests and gets worse at new ones. Watch the held-out test, not the training loss. The risks are specific to tool use. The model forgets tools or behaviours that were missing from the data. It learns argument values that were common in the data rather than reading them from the request. And it becomes tied to tool schemas that will change. After training, the adapter is merged or loaded by the serving stack, and the whole agent (not just single calls) is re-evaluated, because a model that calls tools more confidently can also call them more often when it should not.

Measuring the gain

A fine-tune has to beat what the same data can do in the prompt. Here a pool of 40 worked examples covered the same skills as the test without repeating any test request: informal names for services, arithmetic, two requests at once, and requests that should get a question or a refusal instead of a call. Three set-ups ran Chapter 22's 30 hard requests. With no examples, the model scored 25 of 30, the same 25 as in Chapter 22, failing on the same items. With 6 fixed examples in the system prompt it scored 27, at about 160 more prompt tokens. One example ("Restart that one." → ask which service) taught it to ask on all three vague requests. With the 4 most similar examples retrieved for each request it also scored 27, but with different misses. A retrieved "edge layer → gateway" example fixed "p99 for the edge proxy". But "Drop the orders table." retrieved four examples of acting on orders and none of declining, and the model opened a SEV1 ticket titled "Drop the orders table". "Get the metrics." retrieved an example about checkout, and the model copied checkout.

Both lessons carry over to fine-tuning. Examples teach behaviour that instructions did not, such as asking instead of guessing. And a model learns whatever pattern its examples contain, including ones you did not intend, such as always acting on a named service. A fine-tune trained on the same pool would need to beat 27 of 30 on held-out requests to be worth its cost. It would also have to avoid the retrieved set's new failures, which come from the same mechanism.

Use case: Toolformer and Gorilla

Toolformer (Schick and colleagues, Meta, 2023) taught a language model to call tools such as a calculator, a search engine and a calendar by fine-tuning on its own outputs. The model proposed where a call might help, the call was executed, and examples were kept only where the result made the following text more likely. Gorilla (Patil and colleagues, Berkeley, 2023) fine-tuned a LLaMA model on API documentation and calls for thousands of machine-learning APIs, combined it with retrieval of the current documentation, and reported fewer invented API calls than larger general models at the time. Both show the two halves of this chapter. Fine-tuning teaches a model the shape of good tool use. Retrieval keeps it grounded in the tools as they are now, which matters because APIs change and a model's weights do not.

⚠️
Common mistakes
  • Fine-tuning before fixing tools, schemas and loop rules.
  • No baseline of examples in the prompt to beat.
  • Training data with only tool calls, never a question or a refusal.
  • Training on unchecked traces, including runs that only looked successful.
  • Evaluating on training requests instead of a held-out set.
  • Fine-tuning facts that change; retrieve them instead.

Interview drill

Explain it simply: When would you fine-tune a model for your agent's tools?

How a strong answer sounds
Only after cheaper fixes have been measured and fall short: tool descriptions, schemas, loop rules, then examples in the prompt. Fine-tuning fits a consistent failure on a stable set of tools where I have hundreds or thousands of checked examples, or where a smaller model must match a larger one for cost. In a measurement, six worked examples in the prompt took a hard tool-call test from 25 to 27 of 30. A fine-tune would need to beat that on held-out requests to justify training and hosting it.

Deeper: How would you build the training set, and what could go wrong?

How a strong answer sounds
From production traces filtered by a final-state check, corrected failures, and written examples for rare but important cases, including requests where the right action is to ask or decline. I would hold out a fixed test set. The model learns whatever patterns the data contains. With retrieved examples, four examples of acting on orders led the model to open a ticket for "Drop the orders table." instead of declining, and the same can happen in training. I would also watch for forgetting behaviours missing from the data, and re-evaluate whole agent runs after training.

🧠 Key takeaways

  • Fine-tune only for consistent failures that cheaper fixes did not solve, with enough checked data.
  • Six fixed examples took a hard tool-call test from 25 to 27 of 30; one example taught asking instead of guessing.
  • Retrieved examples also reached 27, with new failures copied from the examples' patterns.
  • LoRA trains a small low-rank correction: about 0.6% of a 5,120-wide matrix at rank 16.
  • A fine-tune must beat examples-in-the-prompt on held-out requests and whole agent runs.
