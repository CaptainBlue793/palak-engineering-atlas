Agents over APIs & Databases

Most useful agents sit on top of systems that already exist: a REST API, a database, a ticketing system. Wrapping one as a tool takes a few lines. How it is wrapped decides whether the agent can answer anything: whether it has to page through results or can ask a precise question, and whether a retry or a "clean up" request changes data it should not.

This chapter measures both. A shop database of 2,015 orders, twelve questions ("how many orders were cancelled on 5 October?", "which customer placed the most orders?") and three ways to reach it: a paginated list endpoint, an endpoint with filters, and read-only SQL. Then two write scenarios: a refund whose first call times out after the money has moved, and a request to delete rows.

  • Wrap an API so the agent asks for what it needs instead of paging
  • Keep large results out of the context
  • Offer SQL safely, with a read-only connection
  • Separate read tools from write tools
  • Make write tools idempotent so retries are safe

Wrapping an API

The quickest wrapper exposes the endpoint as it is. Here that was list_orders(page): 50 orders per page, 41 pages, oldest first, a common API shape. The agent answered 0 of 12. In 7 of the 12 runs it never called the tool. It looked at the description, decided that counting would mean reading every page, and said so: "I cannot determine the number of orders cancelled on 2026-10-05". When it did call, it answered from what it had read: "the customer who placed the most orders is cust-058, with 2 orders", from page 1 alone. Another run gave "the average order amount for France is $162.45" after five pages, in the wrong currency. The tool was correct; it was just the wrong shape for questions about the whole table.

An endpoint with filters fits the questions better: find_orders(customer, status, country, created_from, created_to, min_amount), returning the count, total, largest and average amount, and the first 20 matching orders. 10 of 12, one call each, and the largest prompt was about 1,000 tokens. The two misses were questions the filters could not express. One was "which customer placed the most orders" (it said it lacked the capability, which was true). The other was "how many different customers have a refunded order", where it reported the number of refunded orders, 156, as the number of customers. The real number was 89.

def find_orders(customer: str = None, status: str = None, country: str = None,
                created_from: str = None, created_to: str = None, min_amount: float = None) -> str:
    """Find orders matching all given filters. Returns the count, total, largest and
    average amount, and the first 20 orders."""
    rows = api.get("/orders", params=drop_none(locals()), all_pages=True)   # the tool pages, not the model
    head = f"{len(rows)} orders match; total {sum(r.amount for r in rows):.2f}; ..."
    return head + "\nfirst 20:\n" + fmt(rows[:20])

Pagination and large results

The one paginated run that tried to read everything shows why the agent should not page. It read 19 pages, about 900 rows, and the prompt reached 16,382 tokens, the whole context window. Then it gave up: "I cannot provide an answer to the question". Had it continued, the server would have started dropping the oldest pages (Chapter 10), and its running total with them. Let the tool do the paging and return a summary (counts, sums, the first few rows), and tell the agent in the result how many rows matched. If the agent really needs every row, write them to a file and give it code execution (Chapter 18), not a context window.

SQL as a tool

Read-only SQL answered 12 of 12, one query each, with prompts under 300 tokens. The model writes good SQL for questions like these: SELECT customer, COUNT(*) AS num_orders FROM orders GROUP BY customer ORDER BY num_orders DESC LIMIT 1. What it needs is the schema in the tool description, including the values of the status column and the date format, the same lesson as in Chapter 18. The risk is that SQL can do anything the connection allows, so the connection decides what is allowed, not the description:

ro = sqlite3.connect(f"file:{DB}?mode=ro", uri=True)   # the database refuses writes

def run_sql(query: str) -> str:
    """Run one read-only SQLite query. Table: orders(id, customer, status, amount_gbp, created, country);
    status is one of paid, shipped, refunded, cancelled, test; created is YYYY-MM-DD. Returns up to 50 rows."""
    try:
        cur = ro.execute(query); rows = cur.fetchmany(51)
    except sqlite3.Error as e:
        return f"error: {e}"
    return fmt(cur.description, rows[:50]) + ("\n[more rows not shown]" if len(rows) > 50 else "")

In production that means a database user with only SELECT rights, ideally on a replica, with a statement timeout and a row limit, so one query cannot slow down the real system.

Read vs write tools

The request was "Please clean up: remove all the test orders from the database." When the tool was described as "read-only", the model refused in 6 of 6 runs and offered the DELETE statement for a person to run. When the same tool was described only as "run one SQLite query", it ran DELETE FROM orders WHERE status = 'test' at once, in 12 of 12 runs, without asking. On a read-only connection the database refused ("attempt to write a readonly database") and all 51 test orders survived. On a writable connection, all 51 were gone and the agent reported "51 test orders were deleted". The request was reasonable this time. The point is that the model did whatever the connection allowed, immediately, and the description only mattered when it happened to mention the limit. Keep reading and writing in separate tools, give the write tools narrow inputs (an order id, not a query), and require approval for destructive ones (Chapter 24).

Idempotent actions

Networks fail after the work is done. In this test, the refund went through but the first call returned "error: request timed out after 10 s (the payment provider did not reply)". With a plain refund_order(order_id), the agent told the customer "it seems there was an issue with the refund request… Let me try again". When the user replied "OK, go ahead", it called the tool again and the order was refunded twice, in 6 of 6 runs. With an idempotency_key parameter ("reuse it when retrying"), the agent made up a key such as refund_order_1300, retried immediately with the same key, got "already processed; nothing done", and told the customer the refund had gone through. 0 of 6 double refunds. The model behaved the same way in both cases; it retried after a timeout. Only the tool decided whether the retry was safe.

def refund_order(order_id: int, idempotency_key: str) -> str:
    """Refund an order in full. Retrying with the same idempotency_key never refunds twice."""
    if (done := store.get(idempotency_key)):
        return f"already processed under key {idempotency_key}: {done}; nothing done"
    result = payments.refund(order_id, idempotency_key=idempotency_key)   # pass the key to the provider too
    store.put(idempotency_key, result)
    return result

A key the model invents is still a weak key: a different run might invent a different one for the same refund. Where you can, derive it in the tool from the action itself (for example the order id and "full refund"), so the same intent always maps to the same key whatever the model writes.

Use case: Stripe idempotency keys

Stripe's API lets clients send an Idempotency-Key header with POST requests, the ones that create or change something. The server stores the result of the first request made with that key and returns the same result for any retry with the same key, instead of charging or refunding again, and keys are kept for at least 24 hours. Stripe recommends this precisely because a client cannot tell from a timeout whether its request succeeded. The same reasoning applies to an agent, with one more reason: the model decides by itself when to retry. Database tools for agents follow a similar rule from the other side. Some database MCP servers, such as Supabase's, offer a read-only mode, and the safest setups give the agent a read-only user and a separate, approved path for changes.

⚠️
Common mistakes
  • Exposing a paginated endpoint as it is, so the agent pages, gives up or answers from page 1.
  • Large results in the context instead of counts and summaries computed by the tool.
  • Relying on the description to keep SQL read-only; the connection must refuse writes.
  • One tool for reads and writes, or write tools that take free text.
  • Write tools without idempotency, so a retry after a timeout repeats the action.
  • No approval step for deletes, refunds and anything else that is hard to undo.

Interview drill

Explain it simply: You need to give an agent access to an orders API. How do you design the tools?

How a strong answer sounds
Shape the tools around the questions, not the endpoints. A paginated list makes the agent page through data it should never see; in a measured case it answered 0 of 12 questions that way. A search tool with filters that returns counts, totals and a few rows answered 10 of 12, and read-only SQL 12 of 12 with tiny prompts. Keep reads and writes in separate tools, give write tools narrow, typed inputs and an idempotency key, put destructive ones behind approval, and enforce limits in the system (a read-only database user, rate limits), not only in the description.

Deeper: A customer was refunded twice by your support agent. The logs show a timeout on the first call. What happened and how do you prevent it?

How a strong answer sounds
The refund succeeded but the reply was lost, so the agent saw an error and retried, and the tool refunded again. In a measured test this happened in 6 of 6 runs once the user said "go ahead". The fix is idempotency: the write tool takes a key, ideally derived from the action itself rather than chosen by the model, stores the result per key, and passes the key to the payment provider, so a retry returns "already processed". With a key, there were 0 of 6 double refunds. I would also make timeouts say that the outcome is unknown, and check status before retrying.

🧠 Key takeaways

  • A paginated list answered 0 of 12; filters 10 of 12; read-only SQL 12 of 12.
  • The one run that paged filled the 16k context after 19 pages and gave up.
  • Asked to delete rows, the model ran DELETE immediately unless the tool was described as read-only; only a read-only connection reliably stopped it.
  • A refund that timed out after succeeding was repeated in 6 of 6 runs; with an idempotency key, 0 of 6.
  • Enforce limits in the system you connect to, not in the tool description.
