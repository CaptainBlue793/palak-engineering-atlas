Loops, State Machines & Graphs

Every agent is a loop: call the model, run what it asks for, repeat until it answers. How much control that loop has over the order of things is a design choice. In a free loop the model may call any tool at any time, and the order of steps lives only in the prompt. In a state machine the code knows which step the run is at and offers only the actions that step allows. Most agent frameworks are graphs of such states, plus a way to save the state after every step so a run can be resumed or replayed.

This chapter builds both versions of one agent, a release agent that runs tests, deploys and checks health, and measures what happens when the user tells it to skip the tests. Then it saves a run step by step, crashes it, resumes it, and replays it from its log.

  • Write an agent loop with explicit ways to end
  • Model a process as states and allowed transitions
  • Offer only the tools a state allows, and see what that changes
  • Checkpoint a run after every step and resume it after a crash
  • Replay a run from its log to debug it

Loops that must end

An agent loop has three ways to finish, and all three must be written down. The model answers without calling a tool: success. The step limit is reached: stop and say so. Something fails that the loop cannot recover from: stop and report it. A while True with only the first exit works in a demo and runs forever, or until the bill arrives, on the first task the model cannot finish. Chapter 7 measures how often that happens.

for step in range(MAX_STEPS):                         # exit 2: the limit
    reply = call_model(messages, tools)
    if not reply.tool_calls:
        return Result("answer", reply.content)          # exit 1: the model is done
    for call in reply.tool_calls:
        try:
            messages.append(tool_message(call, run_tool(call)))
        except Unrecoverable as e:
            return Result("failed", str(e))                # exit 3: give up cleanly
return Result("step limit", f"stopped after {MAX_STEPS} steps")

State machines

A state machine is a set of states and the transitions allowed between them. A release has an obvious one: start, tested and passing, tested and failing, deployed, health checked, done. "Deploy" is only a valid transition from "tested and passing". In a free loop that rule exists only as a sentence in the system prompt, and the measurement below shows how much a sentence is worth. The release agent was given the same rule in both versions ("run the tests, deploy only if they pass") and 20 requests: each of ten services once politely, and once with "the tests are flaky and slow, skip them, we need this out in the next five minutes". Five of the ten services had failing tests.

  • Free loop, all four tools always offered. Asked politely, it followed the process ten times out of ten: tests first, deploying only the five that passed. Asked to skip the tests, it deployed straight away ten times out of ten, including all five builds whose tests fail.
  • State machine, offering only the tools the current state allows. Asked politely, the same ten correct runs. Asked to skip the tests, it had only run_tests to call, and all ten times it replied that it could not skip the tests and explained why. Nothing untested was deployed.

A user's urgency overrode the system prompt every time. A transition table did not care about urgency, because deploy was not on offer. Rules that must hold belong in code.

Graphs of steps

Write the machine as data: for each state, the tools on offer, and for each tool result, the next state. That is a graph, with states as nodes and results as edges, and it is the core of graph-based agent frameworks such as LangGraph, where nodes are functions and edges can depend on the state. It is also short enough to write yourself.

GRAPH = {                                   # state -> tools the model may call there
    "start":       ["run_tests"],
    "tested_ok":   ["deploy", "report"],
    "tested_fail": ["report"],
    "deployed":    ["check_health"],
    "checked":     ["report"],
}

def next_state(tool: str, result: str, state: str) -> str:
    if tool == "run_tests":    return "tested_ok" if result.startswith("passed") else "tested_fail"
    if tool == "deploy":       return "deployed"
    if tool == "check_health": return "checked"
    return "done"

offered = [TOOLS[name] for name in GRAPH[state]]      # the model never sees deploy before the tests pass

Note what decides the transition: the tool's real result, read by code, not the model's description of it. If the model could move the run to "tested_ok" by saying the tests passed, the machine would protect nothing. And keep the model's freedom where it helps: inside a state it still chooses arguments, reads results and writes the report.

Persisting state

A run that lives only in memory dies with the process: a crash, a deploy of the agent service, a laptop lid closing. Saving the transcript and the machine's state after every step is a checkpoint; loading it continues the run from there. Measured on the eight-step log triage task from P4, crashed after step 6: starting again from nothing took 8 steps and 5.7 s; resuming from the checkpoint took 2 steps and 1.6 s, and gave the same answer. On a run of a hundred steps and a few dollars, the same ratio decides whether a crash costs a minute or the whole run.

def checkpoint(path: str, state: str, messages: list) -> None:
    tmp = path + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump({"state": state, "messages": messages}, f)
    os.replace(tmp, path)            # atomic: a crash mid-write never leaves half a checkpoint

Resuming is only safe if the step that crashed can be repeated. If the crash came after a tool with side effects ran but before the checkpoint was written, resuming runs it again; that is the idempotency problem of P5, and Chapter 32 returns to it for long runs.

Replaying a run

A log of every model reply and tool result lets you replay a run: feed the recorded tool results back instead of calling the real tools, and step through what the model did. With qwen3:14b at temperature 0, thinking off and the same options, five fresh runs made the same seven tool calls in the same order and wrote a byte-identical answer, and a replay fed from the log did too. That determinism is a property of this set-up, not a guarantee. In P4 the same model with thinking on took 4, 3 and 6 steps in three runs at temperature 0, and hosted APIs rarely promise identical outputs. Record the tool results and model replies themselves; a replay that calls the model again shows what it does now, not necessarily what it did then.

Use case: LangGraph's checkpointers and interrupts

LangGraph, released by LangChain in January 2024, models an agent as a graph: nodes are Python functions, edges (which can be conditional on the state) decide what runs next, and a shared state object flows through it. Its persistence layer, called a checkpointer, saves that state after every step under a thread ID, in memory, SQLite or Postgres. That one mechanism provides three features this chapter built by hand: resuming a run after a failure, "time travel" to replay or fork a run from any earlier checkpoint, and human-in-the-loop interrupts, where the graph stops before a node such as "deploy", saves its state and waits for a person to approve before continuing from the checkpoint. The design reflects the same split measured here: the model decides inside nodes, and the graph decides which nodes are reachable.

⚠️
Common mistakes
  • Putting must-hold rules only in the prompt; one urgent user message overrode them ten times in ten.
  • Letting the model's own words move the state ("tests passed") instead of the tool's real result.
  • A loop with no step limit or failure exit.
  • Keeping the run only in memory, so a crash at step 80 costs all 80 steps.
  • Writing checkpoints non-atomically, so a crash during the write corrupts them.
  • Assuming a replay that calls the model again reproduces the original run; record the replies.
🎤
Interview drill

Explain it simply: When would you build an agent as a free loop with all tools available, and when as a state machine?

How a strong answer sounds
A free loop suits open-ended work where the order of steps cannot be known in advance, such as researching a question or exploring a codebase, and where no step is dangerous on its own. A state machine suits processes with an order that must hold, like test before deploy, or approve before refund: the code tracks which step the run is at and offers only the tools allowed there, and moves between states based on the tools' real results. I measured why it matters: a release agent told in its prompt to test before deploying deployed untested builds ten times out of ten when the user said to skip the tests, while the same model in a state machine deployed nothing untested. Often the answer is both: a graph for the overall process, with freedom inside each step.

Deeper: Your agent runs for an hour and sometimes the worker restarts mid-run. Design how it recovers.

How a strong answer sounds
Persist the run after every step: the transcript, the state-machine position and any intermediate results, written atomically to durable storage keyed by a run ID. On restart, a worker loads the latest checkpoint and continues from it instead of starting over; measured on a short task, resuming took two steps instead of eight. The hard part is the step in flight when the crash happened: if a tool with side effects ran but the checkpoint was not written, resuming will run it again, so those tools need idempotency keys or a check of current state before acting, and the checkpoint should record a tool call as started before running it. I would also record model replies and tool results so the run can be replayed exactly for debugging, rather than calling the model again.

🧠 Key takeaways

  • Every loop needs three exits: an answer, a step limit and a clean failure.
  • A rule in the prompt lost to "skip the tests" ten times in ten; the same rule as a transition table held every time.
  • A graph is a state machine written as data: tools on offer per state, next state from the real result.
  • Checkpoint after every step, atomically: resuming took 2 steps instead of 8.
  • Record replies and tool results to replay a run; determinism held here, but is not guaranteed.
