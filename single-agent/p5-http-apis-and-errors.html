Calling APIs: Timeouts, Retries & Rate Limits

Most agent tools are thin wrappers around someone else's API: a ticketing system, a payments provider, a search service, a cloud console. Those APIs are slow sometimes, fail sometimes and refuse to serve you when you call too often. An agent loop calls them more often and more erratically than any person would, so the plumbing around each call (timeouts, retries, rate limits and idempotency) decides whether a run finishes, how long it takes and whether it does something twice.

This chapter builds that plumbing in Python and measures it against a local API written to misbehave in the ways real ones do: one request in five fails, a few take seconds, a rate limit allows five calls a second, and a refund endpoint sometimes commits the refund and then answers too late.

  • Read status codes as "retry", "fix the request" or "stop"
  • Set timeouts that bound the slowest calls
  • Retry with exponential backoff and jitter, a limited number of times
  • Stay under a rate limit instead of fighting it
  • Make retried writes safe with idempotency keys

Requests and status codes

A status code tells the tool what to do next, and it is worth deciding once, in code, rather than leaving it to the model each time. Codes in the 2xx range mean success. 4xx means the request itself was wrong: retrying the same request will fail the same way, so the error goes back to the model to fix the arguments (400, 404, 422), or to a person (401, 403). Two 4xx codes are exceptions: 408 (request timeout) and 429 (too many requests) are worth retrying later. 5xx means the server failed; 502, 503 and 504 are usually temporary, while a 500 may not be.

RETRY = {408, 429, 500, 502, 503, 504}

def classify(status: int) -> str:
    if status < 300:     return "ok"
    if status in RETRY: return "retry"          # the tool retries, the model never sees it
    if status in (401, 403): return "stop"    # credentials: a person must act
    return "fix"                                # 400, 404, 409, 422: tell the model what was wrong

Timeouts

Without a timeout, one stuck call holds up the whole agent. With one, you choose how long the slowest call may take. Latency in real services has a long tail: in the test API, the median call took 76 ms, but one in a hundred took over 1.7 s and the slowest 4.3 s. A 1-second timeout followed by a retry cut the 99th percentile of the whole operation from 3.4 s to 1.3 s, because a fresh attempt is usually fast. httpx's default timeout is 5 seconds; set one per tool that matches what the tool should take, and remember the whole agent step waits for the slowest tool.

Retries and backoff

Retrying a temporary failure turns most of them into successes. Against an API that failed 20% of calls at random, one attempt succeeded 235 times in 300; up to four attempts succeeded 299 and 300 times. Two rules keep retries from making things worse. Cap them: three retries, then report the failure. And wait between them, longer each time, with randomness: exponential backoff with full jitter waits a random time between zero and a limit that doubles with each attempt. Against random failures, waiting made little difference. Against a server that is overloaded or rate-limiting you, it is the difference between recovering and keeping it overloaded, as the next section measures.

import random, time, httpx

def get_with_retries(client: httpx.Client, url: str, tries: int = 4, timeout: float = 1.0) -> httpx.Response:
    for attempt in range(tries):
        try:
            r = client.get(url, timeout=timeout)
            if classify(r.status_code) != "retry":
                return r
            wait = float(r.headers.get("Retry-After", 0))
        except httpx.TimeoutException:
            wait = 0
        if attempt < tries - 1:
            time.sleep(max(wait, random.uniform(0, 0.1 * 2 ** attempt)))   # full jitter: 0-0.1, 0-0.2, 0-0.4 s
    raise RuntimeError(f"{url}: still failing after {tries} attempts")

Rate limits

APIs limit how often you may call them and answer 429 Too Many Requests when you go over, often with a Retry-After header saying how many seconds to wait. An agent that fans out tool calls hits these limits easily. Measured with 40 concurrent calls against a limit of 5 a second: retrying a 429 straight away produced a storm of 860 requests, 842 of them refused, and only 18 calls finished within 30 attempts each. Honouring Retry-After finished 38 calls but still sent 587 requests, because 40 clients that all wait the advised time come back together. A client-side token bucket that releases 4.5 requests a second, just under the limit, finished all 40 with exactly 40 requests and no 429s, in 8.7 s. If you know the limit, keep under it; treat 429s as the exception.

class Bucket:
    """Release at most `rate` requests per second across all callers."""
    def __init__(self, rate: float):
        self.rate, self.next = rate, time.monotonic()
    async def take(self):
        now = time.monotonic()
        wait = max(0.0, self.next - now)
        self.next = max(now, self.next) + 1 / self.rate
        if wait: await asyncio.sleep(wait)

Idempotency

A timeout does not mean the request failed. It means you stopped waiting. If the server had already done the work, a retry does it again. Measured with a refund endpoint that saved the refund and then, three times in ten, answered after the client's one-second timeout: 200 refunds retried without protection produced 268 refunds; 55 orders were refunded two or three times. Sending an Idempotency-Key header, the same key on every attempt for the same refund, let the server recognise the repeats and return the first result: exactly 200 refunds. Reads (GET) are safe to retry; writes are safe to retry only with a key or an operation that is naturally idempotent, such as "set status to closed".

def refund(client: httpx.Client, order_id: str, amount: int) -> dict:
    key = f"refund-{order_id}-{amount}"               # same key on every attempt for this refund
    for attempt in range(3):
        try:
            r = client.post("/refunds", json={"order": order_id, "amount": amount},
                            headers={"Idempotency-Key": key}, timeout=1.0)
            return r.json()
        except httpx.TimeoutException:
            continue                                     # safe: the server returns the first result
    return {"error": "refund status unknown after 3 attempts; check before retrying"}

In an agent there is a second source of repeats: the model itself. A model that sees an error or a timeout often calls the same tool again, a step later, with the same arguments. Key the operation on what it does (this refund for this order), not on the attempt, and the server catches both kinds of repeat.

Use case: Stripe's idempotency keys

Stripe's API lets a client send an Idempotency-Key header with any POST request. The first request with a given key is processed and its result, whether success or error, is stored; repeats with the same key within 24 hours get that stored result back instead of creating a second charge or refund, and a repeat with the same key but different parameters is rejected. Stripe's own client libraries generate a key automatically and reuse it when they retry a request after a network failure. The design exists for the case measured in this chapter, a timeout that hides a successful write, and an agent with a refund tool is a client that will hit it: from the network, and from a model that decides to try again. ⚠️
Common mistakes
  • No timeout, so one stuck API call hangs the agent.
  • Retrying 4xx errors that will fail the same way every time.
  • Retrying forever, or immediately, so an overloaded service stays overloaded.
  • Answering 429s with more requests instead of slowing down before the limit.
  • Retrying writes without an idempotency key, so a timeout turns into a duplicate refund.
  • Letting the model handle transient errors that the tool could have retried in a few milliseconds.

Interview drill

Explain it simply: Your agent's tool calls a ticketing API that sometimes returns 503. Should the tool retry, or should it return the error to the model?

How a strong answer sounds
The tool should retry. A 503 is temporary and says nothing about the request, so the model cannot do anything useful with it except try again, and each round trip through the model costs a full step of tokens and seconds. In the tool I would retry up to three times with exponential backoff and jitter, honour Retry-After if the API sends one, and use a timeout per attempt. Only if it still fails would I return a clear error to the model, saying the service is unavailable, so it can tell the user or move on. Errors that mean the request was wrong, like 400 or 422, go straight back to the model with the details, because retrying them is pointless.

Deeper: Finance reports that a few customers got two refunds after your agent processed refund requests. How could that happen, and how do you prevent it?

How a strong answer sounds
Most likely a refund request timed out after the payments API had already processed it, and something retried: the tool's retry logic, or the model calling the refund tool again after seeing an error. Without an idempotency key the API treated each attempt as a new refund; measured, retried refunds with a 30% slow-reply rate created 268 refunds for 200 orders. The fix is an idempotency key derived from the operation, such as the order and amount, sent on every attempt, so repeats return the original result; plus a check in the tool for an existing refund before creating one, a reconciliation report, and treating "status unknown" as its own result the model must not retry blindly.

🧠 Key takeaways

  • Decide per status code: retry (408, 429, 5xx), fix the request (other 4xx) or stop (401, 403).
  • Every call gets a timeout; a 1 s timeout plus retry cut p99 from 3.4 s to 1.3 s.
  • Retry a few times with exponential backoff and jitter, inside the tool, not through the model.
  • Stay under rate limits with a client-side limiter: 40 calls in 40 requests instead of 860.
  • A timeout can hide a success; retried writes need idempotency keys (268 refunds became 200).
