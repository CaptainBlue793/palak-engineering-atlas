Case Study: Vending Machine & ATM

Two machines that take money and give things back, and two classic interview questions with the same hidden trap. The vending machine is the textbook State pattern: what a button does depends on whether you've paid. The ATM's cash dispenser is the textbook Chain of Responsibility: each denomination handles what it can and passes the rest on. Both need to return an exact amount from a limited supply of coins or notes, and the obvious greedy answer fails in cases the interviewer will ask about. The fix is the same design rule for both: plan the whole payout before moving anything.

  • Model a vending machine's lifecycle with the State pattern
  • Make change from a limited coin supply, and know when greedy fails
  • Build an ATM dispenser as a chain of cassette handlers that follows a plan
  • Order steps so money and goods are never lost on failure
  • Handle jams, partial dispenses, power loss and bank timeouts

Requirements and API

Vending machine: accepts coins; shows credit; the user selects a slot; if credit covers the price and the product is in stock, it dispenses and returns change; cancel returns the inserted coins; an operator restocks products and coins and collects cash. ATM: card and PIN (three tries), balance and withdrawal; notes come from cassettes of fixed denominations with limited counts; the bank authorises the debit; cash and card must never be lost. Out of scope: deposits, card readers and PIN encryption, which are hardware and security topics.

public interface VendingMachine {
	void insert(Coin coin);
	void select(SlotCode slot);
	void cancel();
	Display display();                      // credit, message, state: observed by the screen
}

public interface CashDispenser {
	Optional<NotePlan> plan(Money amount);         // can we pay this exactly, from what's loaded?
	DispenseResult dispense(NotePlan plan);   // moves notes; reports what was actually presented
}

Vending machine as a State machine

The same button means different things at different times: “A1” with no money shows the price; with enough credit it vends; while vending it's ignored. A pile of if (hasMoney && !dispensing && …) checks is the “flag soup” of Chapter 18. Instead each state is an object that implements the events legal in it and returns the next state; the machine just forwards events and keeps whatever comes back.

interface VendingState {
	default VendingState insert(Machine m, Coin c)     { m.returnCoin(c); return this; }   // safe default: give it back
	default VendingState select(Machine m, SlotCode s) { return this; }
	default VendingState cancel(Machine m)             { return this; }
}

final class HasCredit implements VendingState {
	public VendingState insert(Machine m, Coin c) { m.escrow(c); return this; }

	public VendingState select(Machine m, SlotCode code) {
		Slot slot = m.slot(code);
		if (slot.isEmpty()) { m.show("SOLD OUT"); return this; }
		int changeDue = m.credit() - slot.price();
		if (changeDue < 0) { m.show("INSERT " + Money.cents(-changeDue)); return this; }
		Optional<CoinPlan> change = m.planChange(changeDue);         // escrowed coins count as available
		if (change.isEmpty()) { m.show("EXACT CHANGE ONLY"); return this; }   // before anything moves
		m.commit(slot, change.get());                                   // escrow → cash box, change reserved
		return new Dispensing(slot, change.get());
	}

	public VendingState cancel(Machine m) { m.refundEscrow(); return new Idle(); }
}

public final class Machine implements VendingMachine {
	private VendingState state = new Idle();
	public synchronized void insert(Coin c)      { state = state.insert(this, c); }
	public synchronized void select(SlotCode s) { state = state.select(this, s); }
	public synchronized void cancel()            { state = state.cancel(this); }
}

Inserted coins sit in escrow until a purchase commits, which makes cancel trivial and honest: the customer gets back the exact coins they put in. And the escrowed coins count toward making change, so a customer paying $1.25 for a $0.95 item can receive a coin they just inserted.

Inventory and change-making

Returning 30¢ sounds easy: take the biggest coin that fits, repeat. That greedy rule is optimal for a canonical coin system like US coins, but only with an unlimited supply. A real machine has limited coins. With one quarter, three dimes and no nickels, greedy takes the quarter and is stuck needing 5¢, while three dimes would have worked. Greedy with limited stock can fail even when an answer exists, and with non-canonical denominations it can fail even with unlimited stock (for 6 from {1, 3, 4}, greedy gives 4 + 1 + 1 where 3 + 3 is better). So the machine plans: a small search that tries the most large coins first and backs off when the remainder can't be made.

// Denominations high → low; stock = how many of each are available. Few denominations, so the search is tiny.
static Optional<Map<Integer, Integer>> plan(int amount, List<Integer> denoms, Map<Integer, Integer> stock, int i) {
	if (amount == 0) return Optional.of(new HashMap<>());
	if (i == denoms.size()) return Optional.empty();
	int d = denoms.get(i);
	for (int k = Math.min(amount / d, stock.getOrDefault(d, 0)); k >= 0; k--) {   // as many as possible, then fewer
		Optional<Map<Integer, Integer>> rest = plan(amount - k * d, denoms, stock, i + 1);
		if (rest.isPresent()) { if (k > 0) rest.get().put(d, k); return rest; }
	}
	return Optional.empty();                                               // no combination works: "exact change only"
}

It finds a combination whenever one exists, preferring big coins so the machine keeps small change in stock. With a handful of denominations and limited counts the search space is tiny; for many denominations a bounded-knapsack dynamic program does the same in O(amount × denominations). The design point matters more than the algorithm: planning is a pure function of the amount and the stock, separate from the hardware, so it's trivially unit-tested with every awkward combination.

ATM cash dispenser as a Chain of Responsibility

An ATM has several cassettes, each holding one denomination. The textbook design makes each cassette a handler in a chain (Chapter 19): the $100 handler dispenses as many hundreds as it can and passes the remainder to the $50 handler, and so on. The chain is a good fit for the hardware: each cassette module owns its motor, its count and its faults, and cassettes can be added or reordered. But a chain where each link greedily takes what it can is exactly the greedy algorithm, and it fails the same way: $60 with one $50 and plenty of $20s dispenses the $50, then can't make $10, after a note has already come out.

// The naive chain: each link decides greedily. Fails on $60 = 50 + (10?) even though 20 + 20 + 20 works.
abstract class NaiveHandler {
	NaiveHandler next;
	void dispense(int amount) {
		int n = Math.min(amount / denomination, cassette.count());
		cassette.eject(n);                                         // notes are already moving…
		int rest = amount - n * denomination;
		if (rest > 0) { if (next == null) throw new CannotDispenseException(rest); next.dispense(rest); }   // …when we discover it can't work
	}
}

// The fix: plan first (pure, with the same search as the vending machine), then let the chain execute the plan.
final class CassetteHandler {
	private final int denomination; private final Cassette cassette; private final CassetteHandler next;

	DispenseResult dispense(NotePlan plan, DispenseResult soFar) {
		int wanted = plan.count(denomination);
		int presented = wanted == 0 ? 0 : cassette.eject(wanted);           // the hardware reports what it actually counted out
		DispenseResult r = soFar.with(denomination, presented);
		return next == null ? r : next.dispense(plan, r);
	}
}

Now each link has one job, moving its notes and reporting what it moved, and the decision about which notes is made once, up front, where it can be tested. The plan also lets the ATM refuse before involving the bank: “this ATM can dispense amounts in multiples of $20 up to $400” is a question for the planner, not something discovered halfway through a withdrawal.

Failure handling

Machines that handle money fail in physical ways, and the design has to decide, in advance, what happens to the money in each case. The ATM withdrawal shows the ordering that makes failures recoverable: plan the notes before asking the bank; place a hold (authorise) before dispensing; return the card before the cash (many ATMs do this so the card isn't left behind once the customer has what they came for); and only confirm the debit after the dispenser reports what it actually presented.

“Exact change only” and canonical coins

The “EXACT CHANGE ONLY” light on real vending machines is this chapter's planner saying no: the coin tubes are low enough that some payouts can't be made, so the machine asks for exact payment rather than risk keeping a customer's money. The underlying maths is well studied: a coin system is called canonical when the greedy algorithm always gives the fewest coins, and the US system of 1, 5, 10 and 25 cents is canonical. But canonical-ness assumes unlimited coins; with a finite stock, even a canonical system needs a real search, which is why well-designed machines plan the whole payout before moving a single coin.

⚠️
Common mistakes
  • Boolean flags (hasMoney, isDispensing) instead of explicit states.
  • Dispensing the product, then discovering change can't be made. Plan first.
  • Greedy change or greedy note chains with a limited stock.
  • A chain that ejects notes while still deciding whether the amount is possible.
  • Debiting the account before dispensing without a hold-and-confirm, or retrying bank calls without a key.
  • Trusting that the motor turned instead of checking drop sensors and note counters.
  • No journal, so a power cut loses track of the customer's money.

Interview drill

Explain it simply: Why is the vending machine a good fit for the State pattern?

How a strong answer sounds
Because the same inputs mean different things depending on where the machine is in its lifecycle: selecting a product with no credit shows the price, with credit it vends, and while dispensing it's ignored. With flags, every method grows conditions for every combination. With states, each state class implements only the events that make sense in it and returns the next state, defaults safely reject the rest (a coin inserted while dispensing is returned), and adding a state like OutOfService doesn't touch the others.

Deeper: Your ATM's dispenser is a Chain of Responsibility. The interviewer asks for $60 when the cassettes hold one $50 and many $20s. Walk through it.

How a strong answer sounds
A naive greedy chain dispenses the $50, passes $10 on, and finds no $10s, after a note has already been ejected, so it would have to retract or leave the customer short. I'd separate deciding from doing: a pure planner searches for a combination with the loaded counts (trying most of the big notes first and backing off, or a bounded-knapsack DP), finds 3 × $20, and only then does the chain execute the plan, each cassette ejecting its planned count and reporting what it actually presented. The planner runs before the bank is even called, so an impossible amount is rejected up front. The chain still earns its place: each cassette handler owns its hardware and faults, and cassettes can be added without changing the others.

🧠 Key takeaways

  • Vending machine: explicit states (Idle, HasCredit, Dispensing, OutOfService) that return the next state; safe defaults reject illegal events.
  • Escrow inserted coins so cancel returns exactly what was inserted.
  • Greedy payout fails with limited stock (and with non-canonical denominations); plan the whole payout with a search or DP first.
  • ATM: cassettes as a chain of handlers that execute a plan, not decide it.
  • Order the steps: plan, authorise with a key, return the card, dispense, confirm what was actually presented.
  • Verify physical outcomes with sensors and journal state so every failure has a defined money outcome.

The coin box has one 25¢, three 10¢ and no 5¢ coins. Change due is 30¢. What does greedy do?

Greedy commits to the biggest coin without checking the remainder is makeable. A planner backs off and finds 10 + 10 + 10.

When should the machine check that it can make change?

Planning first means an impossible payout is rejected while nothing has moved yet.

In the fixed ATM design, what does each cassette handler in the chain do?

Deciding happens once in the planner; the chain executes and reports, keeping each hardware module's concerns local.

Why are inserted coins held in escrow instead of dropped straight into the cash box?

Escrow separates “offered” from “paid”, which makes cancellation and failure refunds exact.

The dispenser presents only $40 of a planned $60 due to a jam. What should the ATM do with the bank?

The note counter's report is the truth. Confirm what was presented, release the rest, and alert for service.
