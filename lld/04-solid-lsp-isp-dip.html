SOLID II: Liskov, Interface Segregation & Dependency Inversion

The first two SOLID principles were about individual classes. The last three are about the boundaries between them: whether an implementation can really stand in for its interface, whether an interface asks too much of the classes that use it, and which way dependencies should point. Get these right and swapping a storage engine, a payment provider or a test fake becomes routine.

  • State Liskov substitution as a set of contract rules, and spot subtypes that break them
  • Explain why UnsupportedOperationException in an implementation is a design smell
  • Check substitutability with contract tests run against every implementation
  • Split a fat interface into role interfaces that match what each client needs
  • Apply dependency inversion: business rules own the interfaces, infrastructure implements them

Liskov substitution: honour the contract

Barbara Liskov's principle, in practical terms: code written against a type must keep working when given any of its subtypes. Compiling isn't enough; the compiler only checks method signatures. What matters is behaviour: what a method accepts, what it promises afterwards, and what it may throw. A subtype, whether a subclass or an interface implementation, must follow four rules:

RuleMeaningViolation example
Don't strengthen preconditionsAccept at least everything the type acceptsThe interface allows blobs up to 5 GB; one store rejects anything over 1 MB
Don't weaken postconditionsPromise at least what the type promisesAfter put, get should return the data; one store may silently evict it at once
Keep the invariantsWhat's always true of the type stays trueA “sorted” collection subtype that allows unsorted insertion
No new kinds of failureDon't throw exceptions callers were never told to expectA read-only store whose put throws UnsupportedOperationException

Here's an interface for object storage, the kind every service has for uploads, reports or backups, with its contract written where callers will see it:

/**
 * Stores byte blobs by key.
 * put: accepts any key and any blob up to 5 GB; afterwards get(key) returns exactly those bytes. Overwrites.
 * get: returns Optional.empty() for a missing key; never throws for "not found".
 */
public interface BlobStore {
	void put(String key, byte[] blob);
	Optional<byte[]> get(String key);
}

Five teams wrote implementations. Each compiles. Only some are substitutable. The standard way to find out is a contract test: one abstract test class that states the interface's promises as tests, and a small subclass per implementation that just says how to create it. Every implementation runs the same tests. Run them below.

In JUnit this is an abstract class BlobStoreContractTest with an abstract newStore() method, and one tiny subclass per implementation. A new implementation gets every test for free, and can't claim to be a BlobStore until they pass.

The UnsupportedOperationException smell

The read-only archive store failed because it implements an interface it can't fully honour, and fills the gap with throw new UnsupportedOperationException(). The JDK does this too: List.of(...) returns a list whose add throws. Java gets away with it because the Collection documentation labels mutation methods as “optional operations”, so strictly the contract permits it. It's still a known weak spot: code that takes a List can't know whether add will work without knowing where the list came from.

In your own designs, an implementation that needs to throw “unsupported” is telling you the interface is too big for it. It's the doorway to the next principle: split the interface so the archive can implement just the part it supports.

public interface BlobReader { Optional<byte[]> get(String key); }
public interface BlobStore extends BlobReader { void put(String key, byte[] blob); }

public final class ArchiveStore implements BlobReader { … }   // honest: it can only read
public final class ReportDownloader { private final BlobReader reports; … } // takes only what it needs

Interface segregation: role interfaces

The principle: no client should be forced to depend on methods it doesn't use. Fat interfaces grow naturally, because it's easiest to add one more method to the interface that already exists. A typical one:

public interface UserRepository {
	Optional<User> findById(UserId id);          Optional<User> findByEmail(EmailAddress e);
	void save(User u);                           void delete(UserId id);
	Page<User> search(String text, int page);    List<User> inactiveSince(Instant t);
	void ban(UserId id, String reason);         void exportCsv(OutputStream out);
	UserStats stats();                           // … and five more
}

The login service needs exactly one of those methods, findByEmail. Yet it depends on all thirteen. Three things go wrong. Its test fake must implement thirteen methods, most throwing “not needed”. A change to exportCsv's signature forces the login code to recompile and redeploy. And reading the login service's constructor tells you nothing about what it actually does with users.

The fix is role interfaces: small interfaces shaped by what each client needs, all implemented by the same class.

public interface UserLookup    { Optional<User> findById(UserId id); Optional<User> findByEmail(EmailAddress e); }
public interface UserWriter    { void save(User u); void delete(UserId id); }
public interface UserSearch    { Page<User> search(String text, int page); }
public interface UserAdmin     { void ban(UserId id, String reason); UserStats stats(); void exportCsv(OutputStream out); }

public final class JdbcUserRepository implements UserLookup, UserWriter, UserSearch, UserAdmin { … }

public final class LoginService {
	public LoginService(UserLookup users, PasswordHasher hasher) { … }    // says exactly what it uses
}

Nothing changed in the database code; there's still one repository class. What changed is what each client can see. The login test fake is now a two-method lambda-sized class, and the constructor documents that login only ever reads users.

Dependency inversion: who owns the interface

The last principle has two parts. High-level modules (business rules like billing) should not depend on low-level modules (details like the Stripe SDK); both should depend on an abstraction. And the part people miss: the abstraction belongs to the high-level side. The billing package defines PaymentGateway in its own terms, and the Stripe adapter, in an infrastructure package, implements it. The source-code dependency now points from the detail to the policy: it's been inverted.

Before: business rules import the SDK, so changing provider, or testing without the network, means editing billing. After: billing owns PaymentGateway, and the dashed arrow from StripeGateway into billing is the inversion: infrastructure depends on business rules.

// package com.shop.billing: the interface speaks billing's language, not Stripe's
public interface PaymentGateway {
	ChargeResult charge(Money amount, PaymentToken token, IdempotencyKey key);
}

// package com.shop.infra.stripe: depends on billing, translates to and from the SDK
public final class StripeGateway implements PaymentGateway { … }

Notice the method signature: Money, PaymentToken, ChargeResult, all billing types. If the interface had been charge(StripeChargeRequest req), billing would still depend on Stripe, just with an interface in between. An abstraction shaped by the detail is not an inversion. This is also how you choose which way dependencies should point in general: towards the code that changes least often and matters most. Tax rules and booking rules outlive any payment provider or database driver.

🧠
Switching payment providers in a week, not a quarter

A company processing card payments through one provider wants a second one for cheaper fees in Europe. If BillingService calls the first provider's SDK directly, its request and response types are threaded through refunds, receipts, retries and tests, and the switch is a multi-month rewrite. If billing owns PaymentGateway in its own terms, the work is one new adapter class, its contract tests, and a routing rule choosing a gateway by region (Strategy). This is the most common real-world payoff of dependency inversion, and it comes up in interviews as “how would you add a second payment provider?” (Chapter 12).

⚠️
Common mistakes
  • Checking substitutability by compiling. Signatures match; behaviour may not. Run the same contract tests against every implementation.
  • Implementing an interface with throw new UnsupportedOperationException(). Split the interface instead.
  • Subtypes that quietly reject valid input, or weaken what the type promises (“it's a cache, so saves may be lost”).
  • One repository interface for every client. Give each client a role interface; one class can implement them all.
  • Interfaces shaped like the vendor SDK, placed in the vendor adapter's package. The abstraction must belong to, and speak the language of, the business code.
  • Interfaces for classes with one implementation and no test need, “because DIP”. Invert where a detail sits behind the boundary, like I/O, vendors or time.

Interview drill

Explain it simply: What does Liskov substitution mean beyond “subclasses must compile”?

How a strong answer sounds
Code written against a type must keep working with any subtype, so a subtype must keep the type's behavioural contract. It can't accept less input than the type (no stronger preconditions), can't promise less afterwards (no weaker postconditions), must keep the invariants, and can't throw new kinds of exceptions. A read-only store whose put throws, or a store that silently drops what you just saved, compiles but breaks callers. I check it with contract tests that run against every implementation.

Deeper: Your checkout service calls the Stripe SDK directly. How would you restructure it so adding Adyen is easy and checkout is unit-testable?

How a strong answer sounds
Apply dependency inversion. The billing package defines a PaymentGateway interface in billing's own types, like charge(Money, PaymentToken, IdempotencyKey) returning a ChargeResult. Checkout depends only on that. A StripeGateway in an infrastructure package implements it and translates to and from the SDK, including error mapping. Adyen is then a second adapter plus a routing rule, both run against the same contract tests, and checkout's unit tests use a fake gateway with no network.

🧠 Key takeaways

  • Liskov: a subtype must keep its type's behavioural contract: no stronger preconditions, no weaker postconditions, same invariants, no new failures.
  • Compiling proves nothing about substitutability; contract tests run against every implementation do.
  • An implementation that throws “unsupported” means the interface is too big for it: split it.
  • Interface segregation: give each client a role interface with only what it uses; one class can implement several.
  • Dependency inversion: business rules own the interfaces, in their own terms; infrastructure implements them.
  • Point dependencies towards what changes least and matters most.

Check your understanding

BlobStore.put is documented to accept blobs up to 5 GB. One implementation throws for anything over 1 MB. Which Liskov rule does it break?

A caller that correctly relies on the 5 GB contract fails with this implementation. Accepting less than the type accepts is a stronger precondition, which subtypes may not have.

An ArchiveStore can only read, so it implements BlobStore.put by throwing UnsupportedOperationException. What's the better design?

Doing nothing silently breaks the postcondition, and checks in every caller spread the problem. The honest fix is an interface the archive can fully honour, which is interface segregation serving Liskov.

LoginService takes a 13-method UserRepository but only calls findByEmail. What does interface segregation suggest?

Other clients still need the other methods, so they stay, grouped into role interfaces. LoginService depends only on what it uses, and its test fake shrinks to a couple of methods.

Under dependency inversion, where should the PaymentGateway interface live?

The high-level module owns the abstraction, so the source dependency points from infrastructure to billing. An interface in the adapter's package, or shaped like the SDK, leaves billing depending on the detail.

What is a contract test?

An abstract test class with a factory method per implementation. Each implementation must pass the same behavioural tests, which is a practical check that it can be substituted for the interface.
