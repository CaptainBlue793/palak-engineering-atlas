Case Study: Connection Pool

Opening a database connection means a TCP handshake, often TLS, authentication and session setup: milliseconds each time, far longer than many queries. A connection pool keeps a few open and lends them out. It's a small class with a lot of concurrency in it: callers block for a connection with a timeout, connections go stale and must be validated, callers forget to give them back, and the “obvious” fix of a bigger pool usually makes things slower. This case study builds one, then lets you size it under load.

  • Define a pool API where returning a connection can't be forgotten
  • Bound concurrency with a semaphore and hand out idle connections safely
  • Fail fast with acquire timeouts instead of hanging threads
  • Validate, reset and retire connections at the right moments
  • Detect leaks and size the pool from throughput and hold time

Requirements and API

Clarify: a maximum number of connections (the database's limit is shared by every instance of the service); a minimum kept warm; acquire blocks when all are in use, but only up to a timeout; broken or stale connections are never handed out; connections are reset between borrowers; idle ones are closed after a while, and every connection is retired after a maximum lifetime; leaks are detected and reported; many threads at once. The caller-facing API is the standard JDBC one, which gives a strong design constraint: the caller returns a connection by calling close().

public interface ConnectionPool extends AutoCloseable {
	Connection acquire() throws PoolTimeoutException;          // waits up to config.acquireTimeout
	PoolStats stats();                                           // active, idle, waiting, created, timeouts
}

public record PoolConfig(int maxSize, int minIdle, Duration acquireTimeout, Duration idleTimeout,
                         Duration maxLifetime, Duration leakThreshold) {}

// Callers: the connection goes back to the pool when the try block ends, even on an exception.
try (Connection c = pool.acquire()) {
	return orders.findById(c, id);
}

acquire returns a proxy (Chapter 13) wrapping the real connection. Its close() doesn't close the socket; it returns the connection to the pool. That's what makes try-with-resources work, and the proxy also guards against misuse: after close(), any call on it throws, so a caller that kept a reference can't use a connection that now belongs to someone else.

final class PooledConnection implements Connection {
	private final Connection real;
	private final DefaultPool pool;
	private final AtomicBoolean returned = new AtomicBoolean();
	final Instant createdAt; Instant lastUsed; Throwable borrowSite;   // borrowSite: stack captured when leak detection is on

	public void close() { if (returned.compareAndSet(false, true)) pool.release(this); }   // double close is harmless

	public PreparedStatement prepareStatement(String sql) throws SQLException {
		ensureOpen();                                              // use after close → SQLException
		return real.prepareStatement(sql);
	}
	// … every other Connection method: ensureOpen(), then delegate
}

Object pool with a semaphore

Two things need guarding: how many connections exist (never more than maxSize), and which idle connection a borrower gets. A Semaphore with maxSize permits answers the first: a borrower takes a permit before touching anything, and it's released when the connection comes back or is destroyed. A concurrent deque of idle connections answers the second, used as a stack, last in first out, so the most recently used connections stay warm and the rarely used ones age out naturally. Creating a connection is slow network I/O, so it happens while holding a permit but no lock: a creation in progress already counts toward the maximum, and nobody else is blocked by it.

public final class DefaultPool implements ConnectionPool {
	private final Semaphore permits;                                   // = maxSize, fair
	private final Deque<PooledConnection> idle = new ConcurrentLinkedDeque<>();
	private final ConnectionFactory factory;                            // opens real connections; a fake in tests
	private final PoolConfig config;
	private final Clock clock;

	public Connection acquire() throws PoolTimeoutException {
		Instant deadline = clock.instant().plus(config.acquireTimeout());
		if (!tryAcquirePermit(config.acquireTimeout())) throw new PoolTimeoutException(stats());
		try {
			while (true) {
				PooledConnection c = idle.pollFirst();                   // LIFO: warmest first
				if (c == null) return lend(create(deadline));                // under the permit, outside any lock
				if (usable(c)) return lend(c);
				destroy(c);                                            // stale or broken: try the next one
			}
		} catch (RuntimeException | Error e) {
			permits.release();                                       // never leak a permit on failure
			throw e;
		}
	}

	void release(PooledConnection c) {
		try {
			if (expired(c) || !reset(c)) destroy(c);                 // reset: rollback, autocommit on, clear warnings
			else { c.lastUsed = clock.instant(); idle.offerFirst(c.fresh()); }   // a new proxy for the next borrower
		} finally { permits.release(); }
	}
}

Note c.fresh(): the pool stores the real connection wrapped in a new proxy for each loan, so the previous borrower's proxy stays closed forever. Reusing the same proxy object would let a stale reference work again as soon as someone else borrowed it.

Acquire timeouts

When every connection is busy, a borrower waits. It must not wait forever: a slow database would otherwise pile up every request thread behind the pool, and the service would stop responding to anything, including health checks. tryAcquire(timeout) bounds the wait, and on timeout the caller gets a PoolTimeoutException carrying the pool's statistics (“10 active, 0 idle, 37 waiting”), which is exactly the context needed when it shows up in a log. This is the bulkhead of Chapter 25: the pool caps how much of the service one dependency can tie up. Use a fair semaphore, so waiters are served in order and no request starves.

Validation and eviction

A connection that sat idle can be dead without the pool knowing: the database restarted, a firewall silently dropped an idle TCP session, a failover moved the primary. Handing one out means the caller's first query fails. So the pool validates before lending, with JDBC's isValid(timeout) (or a trivial query on old drivers), but only if the connection has been idle for more than a short window, since validating on every borrow adds a round trip to every request. It also resets state on return, so one borrower's open transaction or changed session setting never leaks into the next borrower's work.

A background housekeeper (a scheduled task, Chapter 35) handles the rest every few seconds: close connections idle longer than idleTimeout while keeping minIdle; retire any connection older than maxLifetime, set a little shorter than any timeout the database or network imposes, so the pool closes connections on its own terms instead of discovering them dead; and top up to minIdle. Retiring a borrowed connection waits until it's returned: release checks expired(c) and destroys it instead of pooling it.

Leak detection

The most common pool failure isn't the database; it's a code path that borrows a connection and never returns it: a close() missing on an early return, or a connection held while waiting on a slow HTTP call. Each leak permanently removes one connection, and the pool degrades quietly until it's exhausted, as the leak option in the simulation shows. Detection is cheap: when leak detection is on, record the borrower's stack trace at acquire (new Throwable()), and let the housekeeper report any connection borrowed for longer than the threshold, with that stack trace, which points straight at the line that forgot to close. Reclaiming a leaked connection automatically is risky (the borrower may still be using it), so report and fix the code instead.

Sizing the pool

Intuition says more connections means more throughput. The database disagrees: it has a fixed number of CPU cores and disks, so beyond a point more concurrent queries just take turns, each one slower, while adding context switches and lock contention. Little's law gives the starting estimate: connections needed ≈ throughput × time each connection is held. At 150 queries per second holding each connection for 20 ms, that's 3 connections busy on average; add headroom for bursts and you're near 8, not 50. The simulation shows the other side: under overload, a big pool doesn't raise throughput, it spreads the database across more queries at once and lowers it.

🧠
HikariCP's advice: smaller than you think

HikariCP, the default connection pool in Spring Boot, is built on the ideas in this chapter: a bounded pool, connection timeouts, validation, idle and maximum lifetimes, and an optional leakDetectionThreshold that logs the stack trace of a connection held too long. Its documentation page “About Pool Sizing” argues that most pools are far too large, and quotes a starting formula from the PostgreSQL project, connections = (core count × 2) + effective spindle count, for a database server; for a 4-core database with one disk that suggests around 9 or 10. Remember too that the database's limit is shared: 20 service instances with a pool of 50 each ask for 1,000 connections, more than many databases allow.

⚠️
Common mistakes
  • No acquire timeout: a slow database hangs every request thread behind the pool.
  • close() that really closes the socket, or a reused proxy that lets a stale reference work again.
  • Creating connections while holding a lock, blocking every borrower behind one slow handshake.
  • Losing a permit on an exception during creation or validation, shrinking the pool one failure at a time.
  • No reset on return, leaking an open transaction or session setting to the next borrower.
  • Validating on every borrow, or never: pay the round trip only after idle time.
  • Sizing by guesswork (“set it to 100”) instead of throughput × hold time and the database's limits.

Interview drill

Explain it simply: How does a caller return a connection, and how do you stop them using it afterwards?

How a strong answer sounds
The pool hands out a proxy that implements Connection. Its close() returns the underlying connection to the pool instead of closing it, so the standard try-with-resources pattern returns connections automatically. The proxy has an atomic “returned” flag: a second close does nothing, and any other call after close throws. Each loan gets a new proxy, so an old reference can never reach a connection that's now lent to someone else.

Deeper: Production alerts show pool timeouts, but the database's CPU is at 30%. What could be happening, and how would you investigate?

How a strong answer sounds
If the database isn't busy, connections are being held without doing database work. Likely causes: a leak (a code path that never closes), or code holding a connection across slow non-database work, like an HTTP call inside a transaction (Chapter 26). I'd turn on leak detection with a threshold well above normal query time and read the borrow-site stack traces; look at the pool stats over time (active stuck at max while query rate is flat points to leaks); and check hold-time metrics per call site. It could also be lock waits in the database: queries blocked on row locks hold connections without using CPU, which the database's lock views would show. The fix is in the code, not a bigger pool; a bigger pool would just delay the same failure.

🧠 Key takeaways

  • Callers return connections by calling close() on a per-loan proxy; closed proxies reject further use.
  • A fair semaphore bounds the number of connections; an idle deque used LIFO supplies them; creation happens under a permit, outside locks.
  • Always bound the wait with an acquire timeout, and release permits on every failure path.
  • Validate after idle time, reset on return, and retire by idle timeout and max lifetime in a housekeeper.
  • Detect leaks by recording the borrow-site stack and reporting long loans.
  • Size with Little's law and the database's cores; past saturation, bigger pools are slower.

Check your understanding

Why does the pool return a proxy rather than the real connection?

The proxy intercepts close() and every other call, turning the standard JDBC lifecycle into borrow and return.

Why is a slow new connection created while holding a permit but not a lock?

Counting the creation against the limit is essential; blocking everyone else during network I/O is not.

A service handles 400 queries per second, each holding a connection for 10 ms. Roughly how many connections are busy on average?

Little's law: 400/s × 0.01 s = 4. Add headroom for bursts, and the pool is still far smaller than intuition suggests.

What should happen to a connection when it's returned to the pool?

Resetting protects the next borrower; retiring expired or broken connections keeps the pool healthy without a round trip on every return.

What is the most useful information in a leak-detection warning?

A leak is a code bug. The borrow-site stack trace identifies the exact call path to fix.
