Testing a Design

A design is only as good as your ability to show it works, and to keep showing it after every change. Good designs are easy to test almost by accident: dependencies come in through constructors, time and randomness are injected, rules live in small objects. This chapter covers what to test in a low-level design, which test double to use where, how to make time-dependent code deterministic, and how to read a painful test as a message about the design.

  • Decide what each kind of class needs tested, through its public behaviour
  • Choose between dummies, stubs, spies, mocks and fakes
  • Make time- and randomness-dependent code deterministic with an injected Clock and generator
  • Test concurrent code for its invariants
  • Treat hard-to-write tests as design feedback

What to test in LLD

Test behaviour through the public API: what a caller can observe. For a design that means the rules (invariants), the transitions of any state machine, the edge cases the requirements named, and the events or outgoing calls the design promises. Don't test getters, private methods, or which internal helper got called: those tests fail when you refactor and pass when behaviour is wrong. Different kinds of class need different tests:

Kind of classWhat to testDoubles needed
Value objectValidation rejects bad input; equality by value; operations (Money.plus)None
Aggregate / entityInvariants hold after every method; legal and illegal transitions; events recordedNone; pass time in as a value
Domain service / strategyThe rule's outputs for representative and boundary inputsNone, or a stub for its data
Application serviceThe use case end to end: state saved, events emitted, errors mappedFake repositories, a fixed or mutable clock, a fake gateway
Adapter (JDBC, HTTP client)It really talks to the real thing correctlyNone: an integration test against a real database or a recorded server

Name tests as sentences about behaviour, so the test list reads like a specification of the design:

class SessionTest {
	private static final Instant T0 = Instant.parse("2026-10-01T09:00:00Z");

	@Test void rejectsABookingWhenEverySeatIsTaken() {
		Session s = Session.open(new SessionId(1), 2);
		s.book(new AttendeeId(1), T0);
		s.book(new AttendeeId(2), T0);
		assertThrows(SessionFull.class, () -> s.book(new AttendeeId(3), T0));
	}

	@Test void fillingTheLastSeatRecordsSessionFilled() {
		Session s = Session.open(new SessionId(1), 1);
		s.book(new AttendeeId(1), T0);
		assertThat(s.pullEvents()).hasAtLeastOneElementOfType(SessionFilled.class);   // AssertJ
	}

	@Test void theSameAttendeeCannotBookTwice() { /* … */ }
}

Notice that the aggregate takes the time as a parameter (Instant now) rather than reading a clock. Pure domain objects that receive time as a value need no clock at all in their tests; the clock lives one layer up, in the application service.

Test doubles

A test double is anything standing in for a real dependency in a test. The names come from Gerard Meszaros's xUnit Test Patterns, and they're worth using precisely, because each suits a different job:

DoubleWhat it doesUse it for
DummyFills a parameter; never actually usedA required argument irrelevant to this test
StubReturns canned answers to queriesFeeding inputs: “the exchange-rate service returns 1.08”
SpyA stub that also records how it was calledChecking an outgoing call afterwards, by hand
MockPre-programmed with expected calls; the test verifies themOutgoing commands at a boundary you don't own: “charge exactly once”
FakeA real, simplified working implementationYour own interfaces with state: repositories, queues, gateways, clocks

The practical default: fakes for your own stateful interfaces, stubs for queries, mocks sparingly for outgoing commands. The difference shows when you refactor. A mock-based test asserts how the code talked to its collaborator; a fake-based test asserts what ended up true:

// Mock (Mockito): verifies the interaction. Breaks if checkout batches, reorders or changes the request shape.
PaymentGateway gateway = mock(PaymentGateway.class);
when(gateway.charge(any())).thenReturn(ChargeResult.ok("ch_1"));
new Checkout(orders, gateway, clock).pay(orderId);
verify(gateway).charge(new ChargeRequest(orderId, Money.eur(1999), new IdempotencyKey("order-8412")));

// Fake: verifies the outcome. Survives any refactor that keeps the behaviour.
FakePaymentGateway gateway = new FakePaymentGateway();
new Checkout(orders, gateway, clock).pay(orderId);
assertEquals(List.of(Money.eur(1999)), gateway.chargesFor(orderId));
assertEquals(OrderStatus.PAID, orders.findById(orderId).orElseThrow().status());

Mocks earn their place when the interaction is the behaviour: that a charge carries an idempotency key, that no email is sent when payment fails. A related rule: don't mock what you don't own. Mocking a vendor SDK's classes encodes your guess about how it behaves; wrap it in an adapter you own (Chapter 12), fake the adapter in unit tests, and cover the adapter itself with a few integration tests against the real sandbox.

Injecting Clock and Random

Code that reads the system clock or calls Math.random() can't be tested deterministically: expiry, rate-limit windows, retry backoff and token generation all behave differently on every run. java.time.Clock exists for exactly this. Production passes Clock.systemUTC(); tests pass Clock.fixed(...), or a small mutable clock they can move forward:

public final class MutableClock extends Clock {          // test helper
	private Instant now;
	private final ZoneId zone;

	public MutableClock(Instant start) { this(start, ZoneOffset.UTC); }
	private MutableClock(Instant start, ZoneId zone) { this.now = start; this.zone = zone; }

	public void advance(Duration d) { now = now.plus(d); }
	@Override public Instant instant() { return now; }
	@Override public ZoneId getZone() { return zone; }
	@Override public Clock withZone(ZoneId z) { return new MutableClock(now, z); }
}

Randomness works the same way: inject a RandomGenerator (or a Supplier of ids), and tests pass a seeded one or a fixed sequence. Testing concurrent code

No test can prove a class is thread-safe, but a stress test can catch the common bugs, if it maximises overlap and checks an invariant rather than an exact interleaving. Start all threads at once with a latch, hammer the shared object, then assert what must be true regardless of order:

@Test void neverOversellsUnderContention() throws Exception {
	SeatInventory inv = new SeatInventory(100);
	CountDownLatch start = new CountDownLatch(1);
	AtomicInteger sold = new AtomicInteger();
	try (ExecutorService pool = Executors.newFixedThreadPool(16)) {
		for (int i = 0; i < 1_000; i++) pool.submit(() -> { start.await(); if (inv.tryReserve()) sold.incrementAndGet(); return null; });
		start.countDown();                                   // release every thread at once
	}                                                          // close() waits for all tasks (Java 19+)
	assertEquals(100, sold.get());                          // the invariant, whatever the interleaving
	assertEquals(0, inv.remaining());
}

Run such tests many times (JUnit's @RepeatedTest) and keep them out of the fast suite if they're slow. For lock-free code where memory-model subtleties matter, the OpenJDK project's jcstress harness explores interleavings far more thoroughly than a hand-written stress test.

Tests as a design check

Writing the test first, or at least early, is the cheapest design review there is: a design that's hard to test is hard to use, and the kind of pain points at the fix.

🧠
Flaky tests at scale

In a 2016 post on the Google Testing Blog, “Flaky Tests at Google and How We Mitigate Them”, Google reported a continual rate of about 1.5% of all test runs reporting a flaky result, and that almost 16% of its tests had some level of flakiness. At that scale a flaky test is not a nuisance but a tax: engineers rerun builds, learn to ignore red, and real failures hide among the noise. Timing assumptions, like the sleeping test above, are a classic source; injected clocks, fakes and deterministic seeds remove whole categories of them before they start.

⚠️
Common mistakes
  • Testing implementation details: private methods, call order of internal helpers, every getter. Refactors break them; bugs slip past.
  • Mocking everything, including value objects and your own repositories, so tests restate the code line by line.
  • Mocking types you don't own. Wrap them in an adapter and fake that.
  • Thread.sleep in tests, for timing or for “waiting for async work”. Inject a clock; wait on a latch or a condition with a timeout.
  • Unseeded randomness in code under test, so failures can't be reproduced.
  • Fakes that drift from the real implementation. Share a contract test (Chapter 26).
🎤
Interview drill

Explain it simply: What's the difference between a mock and a fake, and when would you use each?

How a strong answer sounds
A fake is a working simplified implementation, like an in-memory repository; tests use it and then check the resulting state. A mock is programmed with expected calls and the test verifies those calls happened. I default to fakes for my own interfaces because the tests check outcomes and survive refactoring. I use a mock when the interaction itself is the requirement, like “the payment gateway is charged exactly once with this idempotency key”, and I avoid mocking third-party types directly by putting an adapter in front of them.

Deeper: How would you test the rate limiter you just designed?

How a strong answer sounds
Inject a Clock. Unit tests with a mutable clock: N requests inside the window are allowed and the N+1th rejected; advancing to exactly the window boundary allows again; different keys have independent budgets; a burst at the edge of two windows behaves as the chosen algorithm says. If the algorithm uses randomness, inject a seeded generator. Then one concurrency test: many threads released by a latch against one key, asserting the number allowed never exceeds the limit. Each strategy (fixed window, sliding log, token bucket) runs the same shared test suite as a contract, plus its own boundary tests.

🧠 Key takeaways

  • Test observable behaviour: invariants, transitions, edge cases and promised events, not private methods.
  • Value objects and aggregates need no doubles; application services use fakes; adapters get integration tests.
  • Fakes for your own stateful interfaces, stubs for queries, mocks only when the interaction is the requirement.
  • Don't mock what you don't own: wrap it in an adapter and fake the adapter.
  • Inject Clock and randomness; a mutable clock tests exact boundaries instantly and deterministically.
  • Concurrency tests release threads together and assert invariants, run many times.
  • Test pain is design feedback: too many mocks, sleeps and reflection each point to a specific fix.

Check your understanding

Which test double is a simplified but working implementation, such as an in-memory repository?

A fake really works, just more simply. Stubs return canned answers, mocks verify expected calls, and dummies are never used.

A test for a 1-second hold sleeps 900 ms and asserts the hold is still active. Why does it fail occasionally in CI?

Scheduling delays and GC pauses make real elapsed time unpredictable. Injecting a clock the test advances removes the dependency on real time.

When is a mock the right choice?

Mocks verify interactions, which is right when the interaction is the behaviour. Elsewhere they pin implementation details and make refactoring painful.

A service's test needs six mocks just to construct it. What does that most likely say about the design?

Many dependencies usually mean many reasons to change. Splitting the class shortens both its tests and its callers' code.

What should a concurrency stress test for a seat inventory assert?

Interleavings are nondeterministic, so assert what must be true in every one of them.
