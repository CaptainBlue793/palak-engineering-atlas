Interfaces, Abstract Classes & Generics

Nearly every class diagram you draw in this course starts with an interface: Cache, EvictionPolicy, RateLimitPolicy, PaymentGateway. Interfaces are how you say “any object that can do this” without choosing which one. Generics are how you say it once for every type. This chapter covers both, plus abstract classes, the in-between option, and the wildcard rules that confuse almost everyone the first time.

  • Program to an interface, and explain what that buys you in a design
  • Choose between an interface and an abstract class for a given job
  • Use default methods, and resolve a clash between two of them
  • Write generic classes and methods, with bounds, and know what type erasure prevents
  • Apply PECS (“producer extends, consumer super”) to wildcard parameters
  • Use functional interfaces and lambdas as small, swappable behaviours

Programming to an interface

An interface is a type that lists operations without saying how they're done. A class implements it by providing every operation. Code that only uses the interface works with any implementation, including ones written years later. That is the single most important move in low-level design, and you already use it: List<String> names = new ArrayList<>(); declares the interface and chooses the implementation in one place.

Here is the cache every later chapter builds on. The service that uses it doesn't know, or need to know, how entries are stored or evicted:

Cache.java: a role, not an implementation
public interface Cache<K, V> {
	Optional<V> get(K key);
	void put(K key, V value);
	int size();

	/** Returns the cached value, or loads, stores and returns it. Every implementation gets this for free. */
	default V getOrLoad(K key, Function<? super K, ? extends V> loader) {
		return get(key).orElseGet(() -> {
			V v = loader.apply(key);
			put(key, v);
			return v;
		});
	}
}

public final class UserService {
	private final Cache<String, User> users;             // the interface, not a class
	private final UserRepository repo;

	public UserService(Cache<String, User> users, UserRepository repo) {
		this.users = users;
		this.repo = repo;
	}
	public User find(String id) { return users.getOrLoad(id, repo::load); }
}
What this buys: start with a simple HashMap-backed cache, switch to an LRU cache (Case Study 31) when memory matters, and give tests a fake that counts hits. UserService never changes. Each Cache implementation is a separate class that says implements Cache<K, V>.

Interfaces vs abstract classes

An abstract class is a class marked abstract: it can't be instantiated, and it can declare abstract methods (no body) that subclasses must implement. Unlike an interface it can hold fields and have constructors, so it's the tool for sharing state and code among closely related classes. The cost is the one you saw in P3: a class can extend only one class, and subclasses are coupled to the parent's internals.

A typical good use is a skeleton that does the repetitive work and leaves one step open. Every JSON endpoint in a small web framework decodes errors and encodes responses the same way:

public interface RequestHandler { Response handle(Request req); }

public abstract class JsonHandler implements RequestHandler {
	private final JsonCodec codec;                          // shared state: needs a class

	protected JsonHandler(JsonCodec codec) { this.codec = Objects.requireNonNull(codec); }

	@Override public final Response handle(Request req) {    // final: the skeleton can't be broken
		try {
			return Response.ok(codec.encode(process(req)));
		} catch (BadRequestException e) {
			return Response.status(400, codec.encode(Map.of("error", e.getMessage())));
		}
	}
	protected abstract Object process(Request req);           // the one step each endpoint writes
}

Notice that the abstract class still implements an interface. Callers depend on RequestHandler; JsonHandler is just one convenient way to implement it. The JDK does the same: List is the interface, AbstractList the optional skeleton. This “interface plus skeletal abstract class” pairing gives you the flexibility of the first and the code reuse of the second.

Default methods and the diamond

A default method is an interface method with a body. It exists so an interface can grow without breaking every class that already implements it. When Java 8 added forEach to Iterable and removeIf and stream to Collection, thousands of collection classes in other libraries kept compiling, because they inherited the default bodies.

Since a class can implement several interfaces, two of them might supply a default method with the same signature. Java resolves it with three rules, applied in order:

  1. Classes win. A method declared in the class or any superclass beats any interface default.
  2. The more specific interface wins. If JsonSink extends Sink and both define describe(), JsonSink's version is used.
  3. Otherwise you must choose. If two unrelated interfaces both provide describe(), the class doesn't compile until it overrides it. It can delegate to one explicitly with Sink.super.describe().
public final class AuditedFileSink implements Sink, Audited {
	@Override public String describe() {                    // required: both interfaces have a default describe()
		return Sink.super.describe() + " (audited)";
	}
	// ...
}

Default methods are for evolving an interface and for small conveniences built from its abstract methods, like getOrLoad. They can't touch fields, because interfaces have none. If you find yourself wanting state in a default method, you wanted an abstract class or a separate helper object.

Generics: one class, every type

Before generics (Java 5), a cache stored Object, and every read needed a cast: User u = (User) cache.get("u42");. Put a String in by mistake and the program compiled fine, then crashed with ClassCastException at the read, far from the bug. A type parameter like the K and V in Cache<K, V> lets the compiler check every put and get, and removes the casts.

Cache<String, User> users = new MapCache<>();   // <> lets the compiler infer the types
users.put("u42", alice);                                 // checked: must be a User
users.put("u43", "bob");                                 // compile error, not a crash later

// A generic method: the type parameter goes before the return type.
static <T> T firstOr(List<T> xs, T fallback) { return xs.isEmpty() ? fallback : xs.get(0); }

// A bounded type parameter: T must be comparable to itself (or to a supertype).
static <T extends Comparable<? super T>> T latest(Collection<? extends T> xs) { return Collections.max(xs); }

Type erasure is the one thing to know about how generics work. The type arguments exist only at compile time. At run time a List<String> and a List<Integer> are both just List. So a few things are impossible: new T() and new T[10] (the JVM doesn't know what T is), x instanceof List<String> (only List<?> is allowed), and two overloads that differ only in type arguments, like f(List<String>) and f(List<Integer>). When a class really needs the type at run time, pass it in explicitly, as Class<T> or a factory function.

Wildcards and PECS

Here is the rule that surprises everyone: a List<Integer> is not a List<Number>, even though an Integer is a Number. If it were, this would compile and corrupt the list:

List<Integer> ids = new ArrayList<>();
List<Number> nums = ids;      // suppose this were allowed...
nums.add(3.14);                // ...a Double goes into a list of Integers
Integer first = ids.get(0);    // ClassCastException

Generic types are invariant, so that assignment is a compile error. But then how do you write a method that sums any list of numbers, or one that adds events to any collection that can hold them? With wildcards:

  • List<? extends Number> means “a list of some subtype of Number”. You can read Numbers out of it, but you can't add anything (except null), because you don't know whether it's really a list of Integers or of Doubles. It's a producer.
  • List<? super Integer> means “a list of Integer or some supertype of it”. You can add Integers to it, but reading only gives you Object. It's a consumer.

The mnemonic is PECS: Producer Extends, Consumer Super. A method that copies from a source to a sink takes Collection<? extends T> src and Collection<? super T> dst. The JDK's own Collections.copy is declared exactly that way, and so is the loader parameter of getOrLoad above. Try the combinations:

Functional interfaces and lambdas

  
An interface with exactly one abstract method is a functional interface, and any lambda or method reference with a matching shape can implement it. That makes small behaviours as easy to pass around as values. The standard library has the common shapes: Function<T, R> (T in, R out), Predicate<T> (T in, boolean out), Supplier<T> (nothing in, T out), Consumer<T> (T in, nothing out) and Comparator<T>.


@FunctionalInterface
public interface RetryPolicy {
	boolean shouldRetry(int attempt, Throwable error);
}

RetryPolicy never = (attempt, e) -> false;
RetryPolicy ioThrice = (attempt, e) -> attempt < 3 && e instanceof IOException;

Comparator<Session> soonestExpiry = Comparator.comparingInt(Session::ttlMinutes);

  
@FunctionalInterface is optional, but it makes the compiler reject a second abstract method, so the interface can't stop working with lambdas by accident. A named interface like RetryPolicy is usually better than a raw BiPredicate<Integer, Throwable> in a design: the name says what the behaviour means, and it can grow a default method later. This is the Strategy pattern in miniature, and Chapter 15 builds on it.

JDBC: one interface, every database
java.sql.Connection, Statement and ResultSet are interfaces. Your code calls connection.prepareStatement(sql) and never names a database. PostgreSQL, MySQL and Oracle each ship a driver JAR with classes that implement those interfaces. Switching databases means changing a connection URL and a dependency, not your data-access code. The same design shows up whenever a system must support vendors it doesn't control: payment gateways, cloud storage SDKs, message brokers. Chapter 12 shows how to wrap vendors that don't share an interface.

Common mistakes

    
    
      
  • Declaring fields and parameters with concrete types. HashMap<…> and ArrayList<…> in a signature lock every caller to one implementation. Use Map and List.
    • 
      
  • Reaching for an abstract class first. It uses up the one superclass slot and couples implementers to its internals. Start with an interface.
    • 
      
  • Using raw types (List with no type argument). You lose all checking and get warnings; write List<?> if you truly don't care about the type.
    • 
      
  • Expecting List<Integer> to be a List<Number>. It isn't. Use List<? extends Number> for a parameter you only read from.
    • 
      
  • Putting state-like logic in default methods. Interfaces have no fields; if a default needs state, the design wants a class.
    • 
      
  • Returning wildcard types. Wildcards belong in parameters. A return type of List<? extends T> forces every caller to deal with it.

Interview drill

    
Explain it simply: When would you use an abstract class instead of an interface?

    
How a strong answer sounds
I default to an interface, because a class can implement many of them and callers aren't tied to any implementation. I add an abstract class when several implementations genuinely share state or a fixed algorithm, like a JSON handler skeleton that does decoding and error mapping and leaves one process step abstract. Even then, the abstract class implements an interface, and callers depend on the interface, the way AbstractList sits behind List.

    
Deeper: Write the signature of a method that moves every event from a source queue into a destination collection, working for a queue of ClickEvent into a List<Event> or a List<Object>.

    
How a strong answer sounds
static <T> int drainTo(Queue<? extends T> src, Collection<? super T> dst). The source only produces values I read, so it's ? extends T. The destination only consumes values I add, so it's ? super T. With T inferred as ClickEvent, a Queue<ClickEvent> can drain into a List<Event> or a List<Object>. That's PECS, and it's how BlockingQueue.drainTo is declared too.

  


  

    
🧠 Key takeaways

    
    
      
  • Program to interfaces: callers depend on a role like Cache<K, V>, so implementations can change freely.
    • 
      
  • Abstract classes share state and a fixed skeleton among related classes; pair them with an interface and keep callers on the interface.
    • 
      
  • Default methods let interfaces evolve. Clashes resolve as: class wins, then the more specific interface, else you must override.
    • 
      
  • Generics move type errors from run time to compile time. Erasure means no new T() and no instanceof List<String>.
    • 
      
  • Generic types are invariant. PECS: read from ? extends T, write to ? super T.
    • 
      
  • Functional interfaces turn small behaviours into values; name them after what they mean.

Several request handlers share a JSON codec field and the same error-mapping code, and differ in one step. What's the best structure?

      

        
        
        
        
      

      
Shared state needs a class, because interfaces have no fields. Keeping the interface means callers aren't tied to the skeleton, and handlers that don't fit it can implement the interface directly.

    


    

      
A method is declared double total(List<Number> xs). What happens when you call it with a List<Integer>?

      

        
        
        
        
      

      
List<Integer> is not a subtype of List<Number>. Since total only reads, the list is a producer: ? extends Number accepts lists of any Number subtype.

    


    

      
You want a parameter you can add(Integer) to, which accepts a List<Integer>, a List<Number> or a List<Object>. Which type?

      

        
        
        
        
      

      
The list consumes Integers, so it's ? super Integer: any list whose element type is Integer or a supertype. Any such list can safely hold an Integer.

    


    

      
A class implements interfaces Sink and Audited, unrelated to each other, and both have a default describe(). The class doesn't declare describe(). What happens?

      

        
        
        
        
      

      
With no class method and no more-specific interface, Java refuses to guess. The class must override the method, and can delegate to either default explicitly with Interface.super.method().

    


    

      
Why doesn't if (payload instanceof List<String>) compile?

      

        
        
        
        
      

      
Erasure removes type arguments after compilation. At run time there is only List, so Java only allows instanceof List<?> (or plain List) and makes you check elements yourself.
