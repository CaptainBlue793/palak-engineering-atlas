SOLID I: Single Responsibility & Open/Closed

SOLID is five principles that describe classes which are cheap to change. They get recited far more often than they get understood, usually as slogans like “a class should do one thing”. This chapter covers the first two with a precise definition for each, a real class that breaks it, the refactoring that fixes it, and when applying it would be over-engineering.

  • Define single responsibility as “one reason to change”, meaning one group of people asking for changes
  • Spot a god class from its fields, methods, dependencies and change history
  • Split a class along its reasons to change, and coordinate the pieces
  • Apply open/closed: add behaviour with a new class instead of editing tested code
  • Recognise when a plain switch is the better design

Single responsibility: one reason to change

“A class should do one thing” is too vague to use: everything does one thing at some level of zoom. The precise version is: a class should have one reason to change, and a reason to change is a group of people who ask for changes. If finance, the data team and operations can each send you a ticket that edits the same class, that class has three responsibilities, and their changes will collide.

Here's a class almost every company has somewhere. It produces the nightly sales report:

ReportService.java: four teams' code in one class
public class ReportService {
	private final DataSource db;
	private final SmtpClient smtp;

	public void sendDailyReport(LocalDate day, String format, List<String> recipients) {
		// 1. Data team: which rows count as a sale (joins, filters, the schema)
		List<Order> orders = query("SELECT … FROM orders o JOIN refunds r … WHERE o.day = ?", day);
		// 2. Finance: totals, tax rules, currency conversion
		Money gross = sum(orders), tax = gross.times(taxRate(day)), net = gross.minus(tax);
		// 3. Operations: what the file looks like
		String body = switch (format) {
			case "csv"  -> toCsv(orders, gross, tax, net);
			case "json" -> toJson(orders, gross, tax, net);
			default     -> throw new IllegalArgumentException(format);
		};
		// 4. Platform team: how it's delivered
		smtp.send(recipients, "Sales " + day, body);
	}
	// … query, sum, taxRate, toCsv, toJson, retry logic for SMTP: 600 lines in total …
}
Four reasons to change: the order schema, the tax rules, the output format and the delivery channel, each owned by a different team. A tax change and a new CSV column land in the same file in the same week, and each must be tested against the other three.

The fix is to split along those reasons, so each class answers to one group, and have one small class coordinate them:

public interface SalesQuery { List<Order> completedOrders(LocalDate day); }       // data team
public final class SalesCalculator { SalesSummary summarise(List<Order> orders, LocalDate day) { … } }  // finance
public interface ReportFormatter { String format(SalesSummary s); }           // operations
public interface ReportDelivery { void deliver(String title, String body); }  // platform

public final class DailySalesReportJob {                                       // coordinates; owns no rules
	private final SalesQuery query;
	private final SalesCalculator calculator;
	private final ReportFormatter formatter;
	private final ReportDelivery delivery;
	// constructor assigns all four

	public void run(LocalDate day) {
		SalesSummary summary = calculator.summarise(query.completedOrders(day), day);
		delivery.deliver("Sales " + day, formatter.format(summary));
	}
}

Each piece can now change, and be tested, on its own. SalesCalculator in particular has no database or network, so finance's tax rules get fast unit tests with plain lists of orders. That's a good sign you've split in the right place: the part with the most important rules ended up with the fewest dependencies.

Spotting a god class

A god class knows too much and does too much. You rarely need to read all 600 lines to find one; the signs are visible from outside:

  • Its name is a vague noun: Manager, Service, Helper, Utils, Processor. Names that can't describe the job usually mean there's more than one job.
  • Its fields split into groups that are used by different, non-overlapping groups of methods. That is low cohesion, and each group is a class waiting to get out.
  • Its imports span layers: JDBC, an HTTP client, a PDF library and a tax table in one file.
  • Its tests need five mocks to test one rule.
  • Its git history shows commits from several teams, and merge conflicts between unrelated features.

Open/closed: extend without editing

The second principle says a module should be open for extension but closed for modification. In plain terms: adding a new variant of something should mean adding new code, not editing code that already works and is already tested. In Java that means the variation sits behind an interface, and the code that uses it never names the concrete classes.

The god class's switch (format) is the classic violation. Adding XLSX output means editing that method, and the same switch has usually been copied into the file-naming code and the content-type code too. After the split, formats are a ReportFormatter interface, and choosing one is a lookup:

public final class XlsxFormatter implements ReportFormatter { … }         // the new code: one new class

Map<String, ReportFormatter> formatters = Map.of(
	"csv",  new CsvFormatter(),
	"json", new JsonFormatter(),
	"xlsx", new XlsxFormatter());                                   // plus one line where things are wired

No existing formatter, no calculator and no job changed. The wiring line is the one place that does change, and that's by design: a system is never closed to every change. The skill is choosing which changes it's closed against. Here it's new formats, because the requirement was “operations keeps asking for new formats”. When OCP is over-engineering

Every interface is a cost: another file, another indirection, another thing to name. Open/closed pays off where variants really are added over time by people who shouldn't have to understand the rest. It doesn't pay off where the set of cases is fixed and yours:

  • A closed set. HTTP methods, days of the week, the four states of a job. A switch over an enum or sealed interface is clearer than four classes, and the compiler checks that a switch expression covers every case (for enums since Java 14, for sealed types since Java 21).
  • Only one variant, with no second one in sight. Don't add ReportFormatter for a report that has only ever been CSV. When the second format arrives, extracting the interface takes minutes. A common rule of thumb is to abstract on the second or third variant, not the first.
  • Throwaway code: a one-off migration script needs no extension points.

In an interview this judgment is itself a signal. Saying “I'll put pricing behind an interface because the prompt says rates change; vehicle sizes are a fixed enum, so a switch is fine there” shows you know both the principle and its price.

🧠
Logging frameworks are open/closed in practice

SLF4J and Logback ship with appenders for the console, files and rolling files. When a company needs logs shipped to its own collector, nobody edits Logback. They write a class that implements Logback's Appender interface, and add a few lines to logback.xml naming it. The logging core, used by millions of applications, is closed to that change and open to the extension. The same shape shows up in JDBC drivers, servlet filters, and Case Study 33, where you build a logging framework yourself.

⚠️
Common mistakes
  • Reading SRP as “one method per class”. A class can have many methods that all answer to one group of people.
  • Splitting by technical layer only (a Controller, a Service, a DAO) while one Service still mixes four teams' rules.
  • Duplicated switches. The same switch (format) in three places means every new format needs three edits, and one gets missed.
  • An interface for everything, on day one. Abstract where variation is expected or has appeared, not everywhere.
  • A coordinator that grows rules. The job class should call the pieces, not compute tax “just this once”.
  • Thinking OCP means never editing anything. Wiring changes; the goal is that tested behaviour doesn't.

Interview drill

Explain it simply: What does the single responsibility principle actually mean?

How a strong answer sounds
A class should have one reason to change, and a reason to change is a group of people who request changes. If finance's tax rules, the data team's queries and operations' file formats all live in one class, three groups edit the same file and their changes collide and need retesting together. So I split along those lines: one class per group of rules, plus a small coordinator that calls them. It's not “one method per class”.

Deeper: Your exporter has a switch over formats, and product says new formats arrive every quarter. What do you change, and where would you still keep a switch?

How a strong answer sounds
I'd put formats behind a ReportFormatter interface, one class per format, and choose one by looking it up in a map built where the application is wired. A new format is then a new class plus one registration line, and no tested formatter changes. That's open/closed, aimed at the change we were told to expect. I'd still use a switch for closed sets I own, like a job-state enum, where an exhaustive switch expression is clearer and the compiler checks every case is handled.

🧠 Key takeaways

  • Single responsibility: one reason to change, meaning one group of people requesting changes.
  • God classes show themselves: vague names, field groups used by separate method groups, imports from every layer, many mocks per test.
  • Split by reason to change, and keep a thin coordinator that calls the pieces and owns no rules.
  • Open/closed: a new variant is a new class behind an interface, not an edit to tested code.
  • Choose which changes to be closed against, based on what the requirements say will vary.
  • Closed sets you own are fine as enum or sealed switches; abstract on the second or third variant, not the first.

Check your understanding

In “a class should have one reason to change”, what is a “reason to change”?

SRP is about who drives change. If requests from different groups land in the same class, their changes collide. One method per class is not the goal.

Which sign most strongly suggests a class has several responsibilities?

Separate field-and-method groups mean low cohesion: the class is really several classes sharing a name. Size alone isn't the test.

The exporter chooses output with switch (format), copied in three methods. What does adding XLSX require?

A switch spread over several places means each new variant modifies existing code in each of them. That's exactly what open/closed is designed to avoid.

With formats behind ReportFormatter and chosen from a map, what does adding XLSX involve?

The extension is a new class; the only edit is at the wiring point, which is designed to change. Tested formatters and the calculator are untouched.

When is a plain switch the better design?

A closed set gains nothing from extension points, and an exhaustive switch over an enum or sealed type is short, clear and compiler-checked. Plugins from other teams are the opposite case, where OCP pays off.
