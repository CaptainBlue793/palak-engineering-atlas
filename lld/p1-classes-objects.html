Classes, Objects & References

Every low-level design question ends in the same place: a handful of classes, the objects made from them, and the references that connect those objects. Before you can argue about patterns you need an exact picture of what new does, where an object lives, and what a variable of a class type really holds. This chapter builds that picture, one line of Java at a time.

  • Write a Java class with fields, a constructor and methods, and create objects from it
  • Explain what lives on the stack (frames, primitives, references) and what lives on the heap (objects)
  • Predict what happens when two variables refer to the same object
  • Explain why Java is always pass-by-value, and why a swap method can't swap its callers' variables
  • Decide when a member should be static, and why static state is global state
  • Describe when an object becomes garbage, and how a Java program can still leak memory

Why an LLD course starts with objects

In a low-level design round you are asked to design something like a rate limiter or a parking lot, and then write the core of it. What the interviewer is really checking is whether your objects are right: what each one knows, what each one does, and which ones point at which others. A wrong picture of objects shows up fast. Two parts of the code change "different" sessions that turn out to be the same object. A method is expected to replace a caller's object and silently doesn't. A cache holds on to memory forever.

All three bugs come from the same few rules, and all of them are in this chapter:

  • A class is a type; an object is one value of that type, created at run time with new.
  • Objects live on the heap. Variables of a class type hold a reference to an object, never the object itself.
  • Assignment and method calls copy the reference, so two variables can share one object.
  • An object lives as long as something can still reach it. The garbage collector frees the rest.

A class is a blueprint, an object is an instance

A class describes a kind of thing: the data each one holds (its fields) and the operations it supports (its methods). An object is one concrete instance of that class, with its own copy of every field. The class is written once; a running program may create millions of objects from it.

Take a web server. Every logged-in user has a session: which user it belongs to, and how many minutes it has left before it expires. That's a natural class:

Session.java
public final class Session {
	private final String userId;       // field: set once, never changes
	private int ttlMinutes;            // field: changes as the session is extended

	public Session(String userId) {     // constructor: runs once, inside new
		this.userId = Objects.requireNonNull(userId);
		this.ttlMinutes = 30;
	}

	public void extend(int minutes) {   // method: operates on this object's fields
		if (minutes <= 0) throw new IllegalArgumentException("minutes must be positive");
		ttlMinutes += minutes;
	}

	public String userId() { return userId; }
	public int ttlMinutes() { return ttlMinutes; }
}
Reading it: two fields, one constructor, three methods. Inside the class, this means “the object this method was called on”. private and final are covered properly in P2 and P6; for now read them as “only this class can touch it” and “assigned once”.

Creating and using objects looks like this:

Session alice = new Session("u1");   // allocate an object, run the constructor, return a reference
Session bob   = new Session("u2");   // a second, independent object
alice.extend(15);                      // changes alice's ttlMinutes only
System.out.println(alice.ttlMinutes()); // 45
System.out.println(bob.ttlMinutes());   // 30

new Session("u1") does three things in order. It asks the JVM for enough memory for one Session and sets every field to its default (null, 0, false). It runs the constructor, which sets the real values. Then it returns a reference to the new object, which is what gets stored in alice. Each object has its own ttlMinutes, so extending Alice's session leaves Bob's at 30.

Where things live: the stack and the heap

A running Java program keeps data in two very different places, and the difference explains almost every surprise in this chapter.

  • The stack holds one frame per method call that hasn't returned yet. A frame holds that call's parameters and local variables. Each thread has its own stack, and it is small: 1 MB by default on 64-bit Linux. When a method returns, its frame is thrown away instantly.
  • The heap holds every object ever created with new. It is large (usually hundreds of megabytes to many gigabytes, set with -Xmx) and shared by all threads. Objects stay there until the garbage collector finds that nothing can reach them.

A local variable of a primitive type (int, long, double, boolean, char and the rest) holds its value directly in the frame. A local variable of a class type holds only a reference: a small value, 4 or 8 bytes, that tells the JVM where the object is on the heap. You never see the address itself, and you can't do arithmetic on it. You can only copy it, compare it, set it to null, or follow it with a dot.

How big is the object itself? On a typical 64-bit JVM every object starts with a 12-byte header (used for locking, hashing and garbage collection), then its fields, rounded up to a multiple of 8. A Session is 12 + 4 (the userId reference) + 4 (the int) = 20, rounded to 24 bytes. The string "u1" is a separate object that the session points at. A million sessions is therefore at least 24 MB of heap before you count the strings, a quick estimate worth having when a design keeps objects in memory.

Two variables, one object

Because assignment copies the reference and not the object, two variables can end up pointing at the same object. This is called aliasing. Change the object through one variable and the other variable “sees” the change, because there was only ever one object. That is usually exactly what you want: a session store and a request handler should share the one live session, not two copies drifting apart. It becomes a bug when you thought you had made a copy.

Java is pass-by-value, even for objects

  
When you call a method, Java copies each argument into a new variable in the new frame. That rule has no exceptions. For a primitive argument the copy is the number. For an object argument the copy is the reference, so the method gets its own variable pointing at the caller's object.

  
Two things follow, and the second program in the explorer shows both:

  
    
    
  • The method can change the caller's object. s.extend(30) follows the copied reference to the same object, so the caller sees the new TTL. That's how a method like SessionStore.touch(session) can work.
    • 
    
  • The method can't change the caller's variable. s = new Session("x") only re-points the method's own copy. The caller's variable still refers to the original object, and the new one becomes garbage when the method returns.
    • 
  

  
That is why the third program's swap(a, b) changes nothing for its caller: it swaps its own two copies of the references, then its frame is thrown away. People sometimes describe this as “objects are passed by reference”. They aren't. The reference is passed by value, and the difference is exactly the swap. If a method needs to hand back a different object, it returns it: session = sessionStore.renew(session);.


  

  
static: members of the class itself

  
Most fields belong to an object: each Session has its own ttlMinutes. A field marked static belongs to the class instead. There is exactly one copy, shared by every object and by code that has no object at all. A static method likewise runs without any object, so it has no this and can't read instance fields.


public final class Session {
	public static final int DEFAULT_TTL_MINUTES = 30; // a constant: static + final, fine
	private static int created = 0;                    // one counter for the whole program

	public Session(String userId) {
		// ... as before ...
		created++;                                          // every constructor call bumps the one shared counter
	}

	public static int createdSoFar() { return created; } // called as Session.createdSoFar()
}

  
Good uses of static are narrow. Constants (static final values that never change) are always fine. Pure helper methods that only use their arguments, like Math.max, are fine. Factory methods such as List.of(...) are fine, and Chapter 10 covers them.

  
Mutable static fields are global state, and they cause trouble in exactly the places LLD interviews probe. Every test in a test run shares the same counter, so tests start depending on each other. Two threads incrementing created at once can lose updates (Chapter 22). And any class can reach the value without it ever appearing in a constructor, which hides a dependency. Chapter 8 shows the alternative: create one object and pass it to whoever needs it.


  
Object lifetime and garbage collection

  
Java has no delete. You create objects; the garbage collector (GC) frees them. It decides what to free by reachability. It starts from a set of GC roots: the local variables in every live stack frame, every static field, and a few JVM internals. It follows references from those roots, and then from those objects' fields, and so on. Anything it can reach is alive. Anything it can't reach is garbage, and its memory will be reused.

  
  
Two consequences matter for design. First, memory is not the only resource. A socket, a file handle or a database connection must be closed explicitly, because the GC might not run for minutes, and you never want correctness to depend on it. That's what try-with-resources is for (P7). Second, a garbage-collected program can still leak memory, whenever something reachable keeps holding references it no longer needs.


  

    
🧠

    
A real leak: the session map that only grows
A common first version of a session store is private static final Map<String, Session> SESSIONS = new HashMap<>();. Login does SESSIONS.put(token, session). Nothing ever removes entries, because users rarely click “log out”. The static field is a GC root, the map is reachable from it, and every session is reachable from the map. So not one session is ever collected. At 24 bytes per session plus its strings and the map's entries, a busy service fills its heap in days and dies with OutOfMemoryError. The fix is design, not GC tuning: sessions need an owner that expires them. That means a TTL sweep, or a bounded cache that evicts old entries, which is exactly what Case Study 31 builds.

Common mistakes

    
    
      
  • Thinking b = a copies the object. It copies the reference. To get an independent object you must construct one (Chapter 11 covers copying properly).
    • 
      
  • Reassigning a parameter and expecting the caller to see it. Return the new object instead.
    • 
      
  • Comparing objects with ==. It asks “same object?”, not “equal contents?”. Two separate Session("u1") objects are !=. Use equals (P6).
    • 
      
  • Calling a method through a null reference. A field of class type starts as null; validate in the constructor so it never stays that way.
    • 
      
  • Mutable static fields for convenience. They are global variables with a class name in front: shared by every test and every thread.
    • 
      
  • Assuming the GC prevents leaks. It frees what is unreachable. A static collection that never shrinks keeps everything reachable forever.
    •

Interview drill

    
Explain it simply: Is Java pass-by-value or pass-by-reference?

    
How a strong answer sounds
Always pass-by-value. For objects, the value that gets copied is the reference. So a method can change the object the caller passed, because both copies point at it, but it can't make the caller's variable point at a different object. The swap test proves it: a method that swaps two parameters leaves the caller's variables unchanged. If a method needs to replace an object, it returns the new one.

    
Deeper: A Java service's heap grows steadily and it dies with OutOfMemoryError after about a day. Java has a garbage collector, so how is that possible, and how would you find and fix it?

    
How a strong answer sounds
The GC only frees unreachable objects, so the service must be keeping references it no longer needs. Typical culprits: a static map or cache with no eviction, listeners registered and never removed, or objects parked in a long-lived queue. I'd take a heap dump (for example with jcmd <pid> GC.heap_dump) and look at what retains the most memory and the reference path from a GC root to it. The fix is ownership in the design: a bounded cache with a size limit or TTL, removing listeners when their owner closes, and not using mutable static collections for per-request data.

  


  

    
🧠 Key takeaways

    
    
      
  • A class declares fields and methods; new allocates an object, zeroes its fields, runs the constructor and returns a reference.
    • 
      
  • Frames with their primitives and references live on the small per-thread stack; every object lives on the shared heap.
    • 
      
  • Assigning or passing an object copies the reference, so several variables can share one object (aliasing).
    • 
      
  • Java is always pass-by-value: a method can change the caller's object but never re-point the caller's variable.
    • 
      
  • static members belong to the class. Constants and pure helpers are fine; mutable static fields are global state.
    • 
      
  • An object lives while a chain of references from a GC root reaches it. Collections that never shrink leak memory even with a GC.
    • 
    

  


  

    
Check your understanding

    


    

      
After Session a = new Session("u1"); Session b = a; b.extend(30); what does a.ttlMinutes() return? (A new session starts at 30.)

      

        
        
        
        
      

      
b = a copies the reference, so a and b point at the same object. Extending it through b changes the one object both variables see, so it is now 60.

    


    

      
static void swap(Session x, Session y) { Session t = x; x = y; y = t; } is called as swap(a, b), where a is user u1's session and b is u2's. What does a.userId() print afterwards?

      

        
        
        
        
      

      
Java copies each reference into x and y. The method swaps those two local copies, then its frame is discarded. The caller's a and b never changed. No object was copied either: only references are passed.

    


    

      
Inside a method, Session s = new Session("u1"); runs. Where do the variable s and the Session object live?

      

        
        
        
        
      

      
Local variables, including references, live in the frame of the call that declares them. Every object created with new lives on the heap. That is why the object can outlive the method, for example if it is returned or stored in a field.

    


    

      
When does a Session object become eligible for garbage collection?

      

        
        
        
        
      

      
Java's collectors use reachability from GC roots. An object returned or stored in a field survives its creating method. Cycles are collected once nothing outside reaches them. System.gc() is only a hint and never frees a reachable object.

    


    

      
Why is private static int activeSessions, incremented and decremented from constructors and a close() method, a risky design?

      

        
        
        
        
      

      
A static field has exactly one copy for the whole program. That makes it global mutable state: hidden from constructors, shared across tests, and racy under concurrency unless guarded. A counter object passed to whoever needs it avoids all three problems.
