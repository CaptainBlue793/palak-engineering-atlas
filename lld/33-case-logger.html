Case Study: Logging Framework

Every service logs, and most engineers have used SLF4J with Logback or Log4j without looking inside. Designing one is a favourite LLD question because it's a tour of patterns that genuinely belong: a facade for callers, a hierarchy of named loggers, filters as a chain, layouts as strategies, appenders as pluggable outputs, and an asynchronous appender that must never lose the error you'll need at 3 a.m. It also has a hard constraint most designs ignore: logging must be nearly free when it's turned off, and must never take the application down when it's turned on.

  • Design the caller-facing API so disabled log calls cost almost nothing
  • Resolve effective levels through a hierarchy of logger names
  • Separate appenders, layouts and filters, each behind its own interface
  • Build an async appender with a bounded queue and an explicit overflow policy
  • Make configuration swappable at runtime without locks on the hot path

Requirements and API

Clarify: levels TRACE, DEBUG, INFO, WARN, ERROR; per-package levels (DEBUG for payments only); several outputs at once (console, file, JSON for the log pipeline), each with its own format and filters; asynchronous writing so a slow disk doesn't slow requests; levels changeable at runtime without a restart; thread-safe. Out of scope: shipping logs to a remote store (that's another appender), rotation details.

The API callers see should be tiny and cheap. The key constraint is that a disabled call must do almost no work: no string building, no timestamp, no allocation beyond the argument array. That's why log calls take a template with {} placeholders instead of a concatenated string: "Order " + id + " paid" builds the string even when INFO is off; log.info("Order {} paid", id) doesn't.

public enum Level {
	TRACE, DEBUG, INFO, WARN, ERROR;
	public boolean isAtLeast(Level other) { return compareTo(other) >= 0; }
}

public record LogEvent(Instant time, Level level, String logger, String thread,
                       String message, Throwable error, Map<String, String> context) {}   // immutable: safe to hand to another thread

public final class Logger {
	private final String name;
	private final LoggerContext ctx;

	public void info(String template, Object... args) { log(Level.INFO, template, args, null); }
	public void error(String message, Throwable t)      { log(Level.ERROR, message, NO_ARGS, t); }
	// trace, debug, warn: same shape

	private void log(Level level, String template, Object[] args, Throwable t) {
		if (!ctx.isEnabled(name, level)) return;                           // the hot path for disabled calls
		LogEvent e = new LogEvent(ctx.clock().instant(), level, name, Thread.currentThread().getName(),
			MessageFormatter.format(template, args), t, Mdc.snapshot());      // captured on the caller's thread
		ctx.dispatch(e);
	}
}

// Callers never construct loggers: a static facade hands out one per name.
private static final Logger log = LoggerFactory.getLogger(OrderService.class);

LoggerFactory is one of the few places a static access point is justified (Chapter 9): logging is used from every class, including ones created long before any dependency injection runs. The facade stays thin; everything behind it is ordinary injected objects, which is also how SLF4J separates the API that application code compiles against from the backend (Logback, Log4j) chosen at deploy time.

Levels and filtering

Loggers are named after classes, and the dots form a hierarchy: com.shop.payments.StripeClient is a child of com.shop.payments, which is a child of com.shop, and so on up to the root. Configuration sets levels on a few names; every other logger inherits the level of its nearest configured ancestor. That's how one line (“payments at DEBUG”) turns on detail for a whole package.

Level effectiveLevel(String name) {
	return cache.computeIfAbsent(name, n -> {
		for (String cur = n; !cur.isEmpty(); cur = parent(cur)) {        // "a.b.C" → "a.b" → "a" → ""
			Level l = config.levels().get(cur);
			if (l != null) return l;
		}
		return config.rootLevel();
	});                                                                  // cache cleared when config changes
}

The level check is the coarse, fast filter. Finer decisions (“drop health-check noise”, “only ERRORs to the pager appender”, “sample 1% of DEBUG”) belong to filters, run as a chain (Chapter 19). Each filter answers ACCEPT, DENY or NEUTRAL; the first non-neutral answer wins, and if every filter is neutral the event passes. This is the model Logback and Log4j 2 both use.

public interface Filter {
	enum Verdict { ACCEPT, DENY, NEUTRAL }
	Verdict decide(LogEvent e);
}

static boolean passes(List<Filter> chain, LogEvent e) {
	for (Filter f : chain) {
		switch (f.decide(e)) { case ACCEPT: return true; case DENY: return false; default: continue; }
	}
	return true;
}

Appenders and formatters

Three concerns that are easy to tangle: where an event goes (appender), what it looks like (layout), and whether this output wants it (filters). Keep them separate and every combination is configuration: a console appender with a coloured pattern layout and a WARN threshold, a file appender with a JSON layout and no filters. Adding a Kafka appender or a logfmt layout never touches the others.

public interface Appender { void append(LogEvent e); default void close() {} }
public interface Layout   { String format(LogEvent e); }       // Strategy: pattern, JSON, logfmt

public final class FileAppender implements Appender {
	private final Layout layout;
	private final List<Filter> filters;
	private final Writer out;

	public synchronized void append(LogEvent e) {                     // one writer: lines never interleave
		if (!passes(filters, e)) return;
		try { out.write(layout.format(e)); out.write('\n'); }
		catch (IOException ex) { ErrorReporter.once("file appender failed", ex); }   // never throw into the app
	}
}

Async logging with a queue

Writing to disk takes microseconds when things are fine and much longer when the disk is busy or a network log agent is backed up. With synchronous appenders, that latency lands on every request thread that logs. An async appender is a decorator (Chapter 13) around any appender: append puts the event on a bounded queue and returns; one worker thread takes events off and calls the real appender. That's producer-consumer (Chapter 23), and the design question is the same one: what happens when the queue is full?

A simplified model: 2,000 events arrive from request threads within one second, half of them in the first 250 ms; the disk writes at a fixed rate. “Caller time spent waiting” adds up how long request threads were stuck in a log call instead of serving requests.
public final class AsyncAppender implements Appender {
	private final Appender delegate;
	private final BlockingQueue<LogEvent> queue;             // bounded, e.g. ArrayBlockingQueue(256)
	private final int discardBelow;                           // remaining capacity that triggers shedding
	private final LongAdder dropped = new LongAdder();
	private final Thread worker = Thread.ofPlatform().daemon().name("log-writer").unstarted(this::drain);   // started by the constructor

	public void append(LogEvent e) {
		if (queue.remainingCapacity() < discardBelow && !e.level().isAtLeast(Level.WARN)) {
			dropped.increment(); return;                              // shed the least important events first
		}
		try { queue.put(e); }                                       // WARN/ERROR wait rather than vanish
		catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
	}

	private void drain() {
		try {
			while (true) {
				LogEvent e = queue.take();
				if (e == POISON) break;
				delegate.append(e);
			}
		} catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
	}

	public void close() {                                           // from a shutdown hook
		try { queue.put(POISON); worker.join(5_000); }            // flush what's queued, but don't hang shutdown
		catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
		delegate.close();
	}
}

This overflow policy is not invented for the example: Logback's AsyncAppender behaves this way by default, with a queue of 256 events, and once less than a fifth of the queue remains it discards TRACE, DEBUG and INFO events while keeping WARN and ERROR. Three details decide whether async logging helps or hurts. Capture caller data on the caller's thread: the thread name, the timestamp and the MDC context (request id, user id) must go into the event before it's queued; a worker that reads them later records its own thread and an empty context. Make the event immutable: if the message is formatted later from a mutable argument, the log may show the object's state from after the call. And flush on shutdown, with a time limit, or the last seconds before a crash, the ones you need, never reach the file.

Configuration

Configuration is an immutable object: levels per logger name, appenders with their layouts and filters, the root level. Build it with a builder (Chapter 11) in code, or parse it from a file into the same object. To change levels at runtime (“turn on DEBUG for payments for ten minutes”) build a new configuration and swap it in one atomic step; loggers read the current configuration through a volatile field, so the hot path never takes a lock, and no thread ever sees half a configuration.

LoggingConfig cfg = LoggingConfig.builder()
	.root(Level.INFO)
	.level("com.shop.payments", Level.DEBUG)
	.appender(new AsyncAppender(new FileAppender(path, new JsonLayout(), List.of()), 256))
	.appender(new ConsoleAppender(new PatternLayout("%time %level %logger - %msg"), List.of(new ThresholdFilter(Level.WARN))))
	.build();

context.reconfigure(cfg);      // volatile write of the new config + clear the effective-level cache

Log4Shell: when a layout interprets data

In December 2021, CVE-2021-44228, “Log4Shell”, was disclosed in Log4j 2. Its message formatting supported lookups: a ${…} expression in a message could be evaluated, including JNDI lookups that fetched and loaded remote code. Since applications routinely log attacker-controlled strings (a user agent, a username), an attacker only had to get the string ${jndi:ldap://…} logged to run code on the server. Patches first disabled message lookups by default and then removed them. The design lesson is general: a logging framework must treat the content of messages as inert data. Formatting substitutes arguments into placeholders; it must never interpret what those arguments contain.

⚠️
Common mistakes
  • String concatenation in log calls, paying for formatting even when the level is off. Use placeholders.
  • An unbounded async queue: during an incident it grows until the JVM runs out of memory.
  • Dropping everything when full, including the ERROR that explains the incident. Shed low levels first.
  • Reading thread name or MDC on the worker thread. Capture them at the call site.
  • Appenders that throw into application code. A full disk must not fail a checkout.
  • No flush on shutdown, losing the final events before a crash.
  • Interpreting message content (lookups, expressions) in formatting.

Interview drill

Explain it simply: What are the main classes in a logging framework, and what does each do?

How a strong answer sounds
A Logger per name, which callers get from a LoggerFactory; it checks the level first and, if enabled, builds an immutable LogEvent. Levels come from a hierarchy of dotted names, inherited from the nearest configured ancestor. The event goes to Appenders, which decide where it's written; each has a Layout strategy for the format and a chain of Filters that can accept or deny it. An AsyncAppender decorator moves writing to a background thread through a bounded queue. All of it is described by an immutable configuration object that can be swapped at runtime.

Deeper: During an outage, the log volume spikes tenfold and the disk slows down. What does your design do, and what would you tune?

How a strong answer sounds
With a synchronous appender, request threads would stall on writes and the outage would spread. With the async appender, the bounded queue absorbs the first part of the spike. When remaining capacity drops below the threshold, DEBUG and INFO events are shed and counted, while WARN and ERROR still go into the queue, blocking briefly if it's completely full; that's a deliberate choice that the errors matter more than a few milliseconds. I'd expose the dropped count as a metric and log a summary of it, so the drop is visible. Tuning: a larger queue, a faster layout, batching writes in the worker, and a rate-limiting filter on the noisiest logger. If blocking on ERROR is unacceptable for a latency-critical service, the alternative is never-block mode, which drops even errors, and I'd make that choice explicitly per service.

🧠 Key takeaways

  • Disabled log calls must be nearly free: check the level first, and use placeholders instead of concatenation.
  • Dotted logger names form a hierarchy; effective levels are inherited and cached.
  • Appenders (where), layouts (format) and filters (whether) are separate interfaces.
  • An async appender is a decorator over a bounded queue; choose the overflow policy explicitly and shed low levels first.
  • Capture time, thread and context on the caller's thread, and make events immutable.
  • Configuration is an immutable snapshot swapped atomically; message content is never interpreted.

Check your understanding

Why is log.debug("Cart {} has {} items", id, n) preferred to log.debug("Cart " + id + " has " + n + " items")?

Arguments to a method are evaluated before the call. Placeholders defer formatting until after the level check.

Only com.shop is configured, at WARN. What's the effective level of com.shop.payments.StripeClient?

The lookup walks up the dotted name: com.shop.payments.StripeClient → com.shop.payments → com.shop, which is configured.

An async appender's worker thread reads the MDC request id when it writes each event. What goes wrong?

Thread-scoped data must be captured into the event on the calling thread, before it's queued.

What should an async appender do when its bounded queue is nearly full during an incident?

Unbounded growth risks running out of memory; throwing breaks the application; shedding by importance keeps the events that explain the incident.

Which pattern best describes filters that each return ACCEPT, DENY or NEUTRAL, evaluated in order until one decides?

Each handler either decides or passes the event to the next, and new rules are added without changing the others.
