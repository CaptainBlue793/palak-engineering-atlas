Iterator & Visitor

Two patterns about walking over structures. Iterator lets you go through a collection one element at a time without knowing how it's stored, whether that's an array, a tree, or a paged REST API fetched lazily. Visitor lets you add new operations over a fixed set of node types, like evaluating, printing or type-checking an expression tree, without editing the node classes. Java has built the first into the language, and has recently made the second much simpler with sealed types and pattern matching.

Iterator: one element at a time

An Iterator hides how a collection is stored behind two questions: “is there another element?” and “give me the next one”. Anything that implements Iterable<T> works in a for-each loop, so callers write the same loop over a list, a set, a tree or something that doesn't exist in memory at all.

That last case is where writing your own pays off. A REST API returns orders 100 at a time, with a cursor pointing to the next page. Callers shouldn't have to know about pages or cursors; they want to loop over orders:

PagedOrders.java: an Iterable over a paged API, fetched lazily
public final class PagedOrders implements Iterable<Order> {
	private final OrdersApi api;
	public PagedOrders(OrdersApi api) { this.api = api; }

	@Override public Iterator<Order> iterator() {                           // a fresh cursor per loop
		return new Iterator<>() {
			private Iterator<Order> page = Collections.emptyIterator();
			private String cursor = "";                                   // "" = first page, null = no more

			@Override public boolean hasNext() {
				while (!page.hasNext() && cursor != null) {             // fetch only when the current page runs out
					Page<Order> p = api.list(cursor, 100);
					page = p.items().iterator();
					cursor = p.nextCursor();                                  // null on the last page
				}
				return page.hasNext();
			}
			@Override public Order next() {
				if (!hasNext()) throw new NoSuchElementException();
				return page.next();
			}
		};
	}
}

for (Order o : new PagedOrders(api)) {                                   // the caller never sees a page
	if (o.total().isGreaterThan(threshold)) flag(o);
}
Details that matter: iterator() returns a new iterator each time, so two loops don't share a position; pages are fetched only when needed, so a loop that stops early never fetches the rest; hasNext() loops, so an empty page in the middle doesn't end iteration; and next() throws NoSuchElementException at the end, as the contract requires.

Fail-fast iterators

Removing from an ArrayList while looping over it with for-each throws ConcurrentModificationException, even in a single-threaded program. The collection keeps a modification counter; the iterator records it when created and checks it on each step. If they differ, the list changed underneath the loop, and rather than skip or repeat elements silently, the iterator fails fast.

for (Session s : sessions) if (s.isExpired(now)) sessions.remove(s);    // ConcurrentModificationException

sessions.removeIf(s -> s.isExpired(now));                             // correct, and clearer

for (Iterator<Session> it = sessions.iterator(); it.hasNext(); )
	if (it.next().isExpired(now)) it.remove();                      // also correct: remove through the iterator

Fail-fast is a best-effort bug detector, not a concurrency tool: it isn't guaranteed to trigger, and it doesn't make sharing a list between threads safe. The concurrent collections behave differently on purpose. CopyOnWriteArrayList iterates over a snapshot and never throws (Chapter 16 used it for listeners), and ConcurrentHashMap's iterators are “weakly consistent”: they never throw, and may or may not see changes made during the loop.

Visitor: new operations over a fixed set of types

A pricing engine stores discount rules as expression trees: total > 100 && (status == "open" || vip). The node types are few and stable: And, Or, comparisons, variables, constants. The operations keep coming: evaluate a rule for an order, print it for the admin screen, list the variables it reads, check its types, compile it to SQL. Adding a method to every node class for each new operation scatters each operation across many files, and every node class grows every time.

Visitor puts each operation in its own class, with one method per node type. Each node has a single accept method that calls the right one:

The classic Visitor: double dispatch
public interface Expr { <R> R accept(ExprVisitor<R> v); }

public interface ExprVisitor<R> {
	R visitAnd(And e);  R visitOr(Or e);  R visitCompare(Compare e);  R visitVar(Var e);  R visitConst(Const e);
}

public record And(Expr left, Expr right) implements Expr {
	public <R> R accept(ExprVisitor<R> v) { return v.visitAnd(this); }     // "I am an And": the second dispatch
}
// Or, Compare, Var and Const are the same one-liner

public final class Evaluate implements ExprVisitor<Object> {             // one operation = one class
	private final Map<String, Object> vars;
	public Evaluate(Map<String, Object> vars) { this.vars = vars; }
	public Object visitAnd(And e) { return (Boolean) e.left().accept(this) && (Boolean) e.right().accept(this); }
	public Object visitVar(Var e) { return vars.get(e.name()); }
	// … visitOr, visitCompare, visitConst
}

Object matches = rule.accept(new Evaluate(Map.of("total", 140, "status", "open", "vip", false)));
String text = rule.accept(new Print());                                // a new operation: a new class, no node edits
Why “double dispatch”: Java picks a method by the runtime type of one object, the receiver (P3), and picks overloads by declared argument types at compile time. Visitor needs the choice to depend on two runtime types, the node and the visitor. rule.accept(v) dispatches on the node's type; inside it, v.visitAnd(this) dispatches on the visitor's type. The trade-off, and the modern alternative

Visitor makes one kind of change easy and the other hard. Adding an operation is one new visitor class. Adding a node type, say Not, means a new method in ExprVisitor and an edit to every visitor. That's the opposite of ordinary methods on the nodes, where new node types are easy and new operations touch every class. It's a known tension called the expression problem, and the right choice depends on which will change more: for rule engines, compilers and document formats, the node set is usually the stable part.

Since Java 21, sealed interfaces and pattern matching give you Visitor's benefits with much less ceremony. There's no accept method and no visitor interface; an operation is just a function with a switch, and the compiler checks that it handles every node type:

public sealed interface Expr permits And, Or, Compare, Var, Const {}

static boolean eval(Expr e, Map<String, Object> vars) {
	return switch (e) {
		case And(Expr l, Expr r)       -> eval(l, vars) && eval(r, vars);          // record patterns deconstruct
		case Or(Expr l, Expr r)        -> eval(l, vars) || eval(r, vars);
		case Compare c                  -> c.test(vars);
		case Var(String name)            -> (Boolean) vars.get(name);
		case Const(Object v)             -> (Boolean) v;
	};                                                                      // add Not to "permits" and this stops compiling
}

Compilers are built on visitors

A compiler parses source code into a syntax tree whose node types (class declaration, method, loop, call, literal) almost never change, then runs dozens of passes over it: name resolution, type checking, constant folding, code generation. That's the situation Visitor was designed for. The javac compiler walks its trees with visitor-style scanners, the Java Compiler Tree API exposes a TreeVisitor interface, and java.nio.file.Files.walkFileTree takes a FileVisitor with a method for each event (preVisitDirectory, visitFile, postVisitDirectory) so you can write a new file-tree operation without touching the traversal.

⚠️
Common mistakes
  • Removing elements inside a for-each loop. Use removeIf or Iterator.remove().
  • An Iterable that returns the same iterator every time. The second loop sees nothing. Return a fresh one.
  • Loading everything up front in a paged iterator. Fetch the next page only when the current one runs out.
  • Using Visitor for a hierarchy that keeps growing. Every new node type breaks every visitor.
  • Visitors that switch on instanceof inside one method. That's neither pattern; use real visit methods or a sealed switch.
  • A default branch in a sealed switch. It silences the compiler's exhaustiveness check, so new node types slip through.

Interview drill

Explain it simply: Why does removing from an ArrayList inside a for-each loop throw, and how do you fix it?

How a strong answer sounds
For-each uses the list's iterator, which remembers the list's modification count when it's created and checks it on every step. Removing through the list, not the iterator, changes the count, so the next step throws ConcurrentModificationException instead of silently skipping an element. The fixes are list.removeIf(predicate), or an explicit iterator and it.remove(). It's a bug detector, not thread safety; for concurrent access I'd use a concurrent collection.

Deeper: Discount rules are expression trees. Product wants to evaluate them, show them in the admin UI, and export them to SQL. How do you structure the operations?

How a strong answer sounds
The node types are few and stable, while operations keep arriving, so I'd separate operations from nodes. In modern Java: a sealed Expr interface with records for And, Or, Compare, Var and Const, and each operation as a function with an exhaustive pattern-matching switch: eval, print, toSql. Adding an operation is a new function; adding a node type makes the compiler list every switch to update. On older Java I'd use a classic Visitor with double dispatch for the same effect.

🧠 Key takeaways

  • Iterator traverses a collection without exposing its storage; implement Iterable to get for-each.
  • Return a fresh iterator per loop, fetch lazily, and throw NoSuchElementException past the end.
  • Fail-fast iterators throw on modification during a loop; use removeIf or Iterator.remove().
  • Visitor puts each operation in its own class; accept plus visitX is double dispatch on node and visitor type.
  • Visitor makes new operations easy and new node types hard: choose it when the node set is stable.
  • In modern Java, a sealed interface with an exhaustive switch gives the same benefits with less code; avoid default branches.

Check your understanding

What does the Iterator pattern provide?

Iterator hides the storage behind hasNext/next, so one loop works over arrays, trees or paged remote data. It doesn't add operations (Visitor) or thread safety.

for (Session s : sessions) if (s.isExpired(now)) sessions.remove(s); throws. Which fix is correct?

removeIf removes safely in one pass. Ignoring the exception leaves elements unprocessed, synchronization doesn't change the single-threaded modification, and for-each has no backwards form.

With a classic Visitor, which change is expensive?

Visitor trades cheap new operations for expensive new node types. That's why it suits stable hierarchies such as syntax trees.

What is “double dispatch” in Visitor?

Java dispatches on one receiver at a time, and overloads are chosen at compile time. Two virtual calls, one on each object, give a choice that depends on both runtime types.

Why avoid a default branch in a switch over a sealed interface?

Without default, the compiler knows every permitted subtype and errors when one is missing. A default quietly catches the new type instead.
