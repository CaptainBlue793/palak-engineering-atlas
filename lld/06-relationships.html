Modeling Relationships

A class diagram's lines are decisions. Who creates this object? Who is allowed to keep a reference to it? When it's deleted, what goes with it? Can you get from A to B, and also from B to A? This chapter turns the UML relationships from P8 into concrete Java: the field types, the constructors, and the methods that keep both ends of a relationship consistent.

  • Implement composition in Java: the whole creates, owns and hides its parts
  • Choose the Java type for each multiplicity: a field, Optional, List, Set or Map
  • Model many-to-many relationships, and promote them to a class when they carry data
  • Decide whether a link should be navigable one way or both, and keep both ends in sync when it is
  • State who owns each object's lifecycle

Composition in Java

Composition means the whole owns the lifecycle of its parts. In Java, three habits make that true rather than just drawn:

  1. The whole creates the parts. Callers ask the channel to post a message; they don't construct a Message and push it in. That way the channel can enforce its rules (not archived, author is a member) on every message.
  2. The whole never hands out the mutable parts collection. Return an unmodifiable view or a copy (P2).
  3. Deleting the whole deletes the parts. In memory, dropping the channel makes its messages unreachable. In a database, that's a cascade delete, or the messages live inside the channel's record.
Channel.java: composition, done properly
public final class Channel {
	private final ChannelId id;
	private final String name;
	private final List<Message> messages = new ArrayList<>();       // ◆ 0..*: ordered, owned
	private boolean archived;

	/** The only way a message comes into existence: the channel checks its rules first. */
	public Message post(UserId author, String text, Instant at, Predicate<UserId> isMember) {
		if (archived) throw new IllegalStateException("channel is archived");
		if (!isMember.test(author)) throw new IllegalArgumentException("not a member: " + author);
		Message m = new Message(MessageId.random(), author, text, at);    // immutable record
		messages.add(m);
		return m;
	}

	public List<Message> recent(int n) {                           // a copy, never the list itself
		return List.copyOf(messages.subList(Math.max(0, messages.size() - n), messages.size()));
	}
	public void archive() { archived = true; }
}

public record Message(MessageId id, UserId author, String text, Instant sentAt) {}
//                                   ↑ association by id: the message refers to its author, doesn't own them
Two details worth copying: the message refers to its author by UserId, not by holding a User object, so a message never keeps a whole user graph alive and never goes stale when the user renames themselves. And membership arrives as a predicate, because who belongs to a channel is a separate relationship, next section.

Many-to-many, and when a link becomes a class

A user belongs to many channels; a channel has many users. There are three ways to store that, and the choice matters more than it looks:

  • A set on each side: Channel.members and User.channels. Navigation is easy both ways, but there are now two copies of one fact, and every change must update both.
  • A set on one side only: Channel.members. One copy, one place to change. Finding a user's channels means searching, or asking an index.
  • A separate association object: a Membership(userId, channelId, role, joinedAt) record held in one registry, like a join table in a database. The relationship itself is the thing stored.

The third option becomes the only good one as soon as the relationship has its own data. “Alice is an admin of #incidents since March” is a fact about the pair, not about Alice or about the channel. UML calls this an association class:

public record Membership(UserId user, ChannelId channel, Role role, Instant joinedAt) {}

public final class Memberships {                                        // the single source of truth
	private final Map<ChannelId, Map<UserId, Membership>> byChannel = new HashMap<>();
	private final Map<UserId, Set<ChannelId>> byUser = new HashMap<>();         // an index, kept in step privately

	public void join(UserId u, ChannelId c, Role role, Instant at) {
		byChannel.computeIfAbsent(c, k -> new HashMap<>()).put(u, new Membership(u, c, role, at));
		byUser.computeIfAbsent(u, k -> new HashSet<>()).add(c);
	}
	public void leave(UserId u, ChannelId c) { /* remove from both maps */ }
	public boolean isMember(UserId u, ChannelId c) { … }
	public Set<ChannelId> channelsOf(UserId u) { return Set.copyOf(byUser.getOrDefault(u, Set.of())); }
}

There are still two maps, but they're private to one class and changed only by join and leave, so they can't drift apart. That's the general rule for bidirectional links: two copies are fine as long as one method changes both and nobody else can touch either. Try all three designs:

The invariant: Alice is in #general.members exactly when #general is in alice.channels. Two public sets break it in two ways: an update that changes only one side, and a caller editing a side directly.

  


  
Navigate one way unless you need both

  
A link you can follow in both directions costs more than keeping two sets in step. Objects that point at each other make equals, hashCode and toString easy to get wrong: a generated toString on Channel prints its members, each member prints its channels, and the program dies with StackOverflowError. Serializing to JSON loops the same way. And it's harder to see who owns what.

  
So default to one direction, the one the use cases navigate most, and answer the reverse question with a query or an index held by one class, as Memberships.channelsOf does. Referring to other entities by id rather than by object reference, like Message.author, is a good default at entity boundaries: it breaks cycles, keeps object graphs small, and matches how the data is stored anyway. Chapter 27 turns this into the rule that aggregates reference each other by id.

The join table is the association class
In a relational database, a many-to-many relationship is always a third table: channel_members(user_id, channel_id, role, joined_at), with a primary key on the two ids. Nobody stores a list of channel ids inside the user row. The in-memory design above mirrors that on purpose. When a repository later loads memberships from the database (Chapter 26), one table maps to one record type, and the question “are both sides in sync?” can't come up, because there is only one side.

  


  
⚠️
Common mistakes

    
    
      
  • Letting callers construct parts and add them. channel.getMessages().add(new Message(...)) skips every rule. The whole creates its parts.
    • 
      
  • Two public sets for one relationship. They will drift apart. One method updates both, or keep one source of truth.
    • 
      
  • Putting relationship data on either end. A role is about the user-in-a-channel pair: make a Membership class.
    • 
      
  • Bidirectional object references everywhere. Generated toString and JSON serialization recurse forever. Navigate one way; use ids across entities.
    • 
      
  • A List where the rule is “no duplicates”, or a Set where order matters. The collection type is part of the model.
    • 
      
  • Deleting a whole without its parts. Orphaned messages with no channel are a data bug. Composition means cascade.
    •

Interview drill

    
Explain it simply: How do you implement composition in Java, beyond drawing a filled diamond?

    
How a strong answer sounds
The whole creates the parts through its own methods, so it can enforce its rules; for example channel.post(author, text) creates the message rather than letting callers construct one and add it. It keeps the collection private and returns copies or unmodifiable views. And the parts go when the whole goes: in memory they become unreachable, in a database it's a cascade delete. Parts usually refer to other entities by id, so they don't keep unrelated objects alive.

    
Deeper: Users join channels, and each membership has a role and a join date. How do you model it?

    
How a strong answer sounds
The role and join date belong to the pair, not to either side, so the relationship becomes a class: a Membership(userId, channelId, role, joinedAt) record. I'd keep memberships in one registry class that is the single source of truth, with a private index by user for “which channels is Alice in?”, both updated only by join and leave. I wouldn't give User and Channel public sets of each other, because they'd drift apart and create cycles in toString and serialization. It's the in-memory version of a join table.

  


  

    
🧠 Key takeaways

    
    
      
  • Every relationship answers: who creates it, can it be shared, is it deleted with the whole.
    • 
      
  • Composition in Java: the whole creates its parts, hides the collection, and takes the parts with it when it goes.
    • 
      
  • Multiplicity is a type: final field, Optional, List (ordered), Set (unique), Map (by key), non-empty check for 1..*.
    • 
      
  • Many-to-many with data of its own is an association class, like Membership: the in-memory join table.
    • 
      
  • Two copies of one link are safe only if one method changes both and nothing else can touch them.
    • 
      
  • Default to one-way navigation, and refer to other entities by id to avoid cycles and stale graphs.
