From Requirements to Classes

Every LLD round opens with something vague: “design a URL shortener.” The first ten minutes decide the next thirty-five. This chapter is the method for those ten minutes: ask the questions that change the design, write down use cases and actors, pull candidate classes and methods out of the words, throw most of them away, and end with a short, defensible class list.

  • Ask clarifying questions that change the design, and know what each answer changes
  • Write use cases and actors, and cut scope out loud
  • Turn nouns into candidate classes and verbs into methods, then filter them
  • Decide whether a concept is an entity, a value object, a field, an interface or out of scope
  • Produce a first class list and skeleton for a URL shortener

Questions that change the design

A clarifying question is only worth asking if the answer changes what you'll build. “What colour is the button?” doesn't. “Can two users pick the same custom alias at the same moment?” does: it decides whether the repository needs an atomic insert. Before designing, run through the handful of questions below, which fit almost any LLD prompt. For a URL shortener, here is what each answer changes:

QuestionIf yes, the design gains…If no
Can users pick a custom alias?An Alias value object with validation, and a uniqueness check that can failOnly generated codes
Do links expire?An expiresAt field, and an injected Clock so expiry is testableLinks live forever
Do we count clicks?A counter on the link, updated on every redirect, which must be thread-safeRedirect is read-only
Many threads at once?Atomic “insert if absent”, a concurrent map or locks (Chapter 22)A plain HashMap is fine
Can owners delete or edit links?An owner id on the link, and a permission checkAnonymous, immutable links
Must links survive a restart?A LinkRepository interface with a database implementationAn in-memory store behind the same interface

Ask these in a batch, not one at a time over ten minutes. A good pattern is to propose defaults and let the interviewer correct them: “I'll assume custom aliases are allowed, links can expire, we count clicks, and the store is shared by many request threads. Anything you'd change?” That takes thirty seconds and gets the same information.

Use cases, actors and scope

A use case is one thing an actor wants to achieve, stated as a verb phrase. An actor is whoever, or whatever, starts it: a person, another service, a scheduled job. Writing use cases down, even as five short lines, gives you a checklist for the design and a clear way to say what you won't do.

In scope

  • Creator shortens a URL, with an optional custom alias and expiry
  • Visitor opens a short link and is redirected, and the click is counted
  • Owner deletes one of their links
  • Owner sees a link's click count

Out of scope (said out loud)

  • Sign-up and login: assume we're given an authenticated owner id
  • Analytics dashboards, per-country stats
  • Abuse detection and malicious-URL scanning
  • Distribution across servers: that's the system design version

Notice the actors aren't classes. A visitor is someone making an HTTP request; nothing in the design needs a Visitor object. The owner shows up only as an ownerId on a link. Actors tell you who calls the design, not what's inside it.

Nouns become candidates, verbs become methods

The oldest trick in object-oriented design still works as a starting point: read the requirements, underline the nouns (candidate classes or fields) and the verbs (candidate methods). Then filter hard, because most nouns are not classes. Try it on the shortener's spec. Click a word to cycle through the categories, then check your answers.

    Filtering: which candidates earn a class?

    A candidate becomes a class only if it earns its place. Four tests cover almost every case:

    1. It has rules or behaviour. A ShortLink knows when it has expired and counts its clicks: a class. A link's creation time just sits there: a field.
    2. Several values always travel together, or one value needs validation. An alias must be 4–32 characters from a fixed set; making it an Alias value object means it's checked once, in the constructor, and every method that takes an Alias can trust it.
    3. It varies. Codes might be random, or a counter in base 62, or come from a pre-generated pool. That variation point becomes an interface, CodeGenerator.
    4. It hides a detail the rest shouldn't know. Where links are stored is LinkRepository's business, not the service's.

    Everything else is a field, a parameter, or nothing at all. Being strict here is what keeps the diagram at six boxes instead of fifteen.

    A first class list

    Here is where the ten minutes should land: six types, each with a one-line job. In an interview you'd draw these as a class diagram (P8) and then write the two that carry the design, ShortLink and LinkService.

    The URL shortener's core, first cut
    /** A validated short code. Value object: equal aliases are interchangeable. */
public record Alias(String value) {
	private static final Pattern VALID = Pattern.compile("[A-Za-z0-9_-]{4,32}");
	public Alias {
		if (!VALID.matcher(value).matches()) throw new IllegalArgumentException("invalid alias: " + value);
	}
}

/** Entity: identified by its alias, with state that changes (clicks). */
public final class ShortLink {
	private final Alias alias;
	private final URI target;
	private final String ownerId;
	private final Instant expiresAt;
	private final AtomicLong clicks = new AtomicLong();          // many redirect threads increment it

	public ShortLink(Alias alias, URI target, String ownerId, Instant expiresAt) { /* requireNonNull each */ }

	public boolean isExpired(Instant now) { return !now.isBefore(expiresAt); }
	public URI visit() { clicks.incrementAndGet(); return target; }     // tell, don't ask
	public boolean isOwnedBy(String userId) { return ownerId.equals(userId); }
	public Alias alias() { return alias; }
	public long clicks() { return clicks.get(); }
}

public interface CodeGenerator { Alias next(); }           // random, base-62 counter, pre-generated pool…

public interface LinkRepository {
	Optional<ShortLink> find(Alias alias);
	boolean insertIfAbsent(ShortLink link);                   // atomic: false if the alias is taken
	void delete(Alias alias);
}

/** The use cases. Holds no data of its own; coordinates the others. */
public final class LinkService {
	private final LinkRepository links;
	private final CodeGenerator codes;
	private final Clock clock;                                    // injected, so expiry is testable

	public LinkService(LinkRepository links, CodeGenerator codes, Clock clock) { /* assign, requireNonNull */ }

	public ShortLink shorten(URI target, String ownerId, Duration ttl) {
		for (int attempt = 0; attempt < 3; attempt++) {                // generated codes can collide, rarely
			ShortLink link = new ShortLink(codes.next(), target, ownerId, clock.instant().plus(ttl));
			if (links.insertIfAbsent(link)) return link;
		}
		throw new IllegalStateException("could not allocate a unique code");
	}

	public ShortLink shortenAs(Alias custom, URI target, String ownerId, Duration ttl) {
		ShortLink link = new ShortLink(custom, target, ownerId, clock.instant().plus(ttl));
		if (!links.insertIfAbsent(link)) throw new AliasTakenException(custom);
		return link;
	}

	public Optional<URI> resolve(Alias alias) {
		return links.find(alias)
			.filter(link -> !link.isExpired(clock.instant()))
			.map(ShortLink::visit);
	}
}
    Decisions to say out loud: Alias validates once; ShortLink owns its expiry and click rules; generation and storage are interfaces because they vary; uniqueness is an atomic insertIfAbsent, never “check, then save”, which two threads could both pass; and the clock is injected so a test can move time forward. AliasTakenException is an unchecked exception the web layer maps to 409 Conflict.
    🧠
    Why “check, then save” fails for custom aliases

    The obvious code is if (links.find(alias).isEmpty()) links.save(link);. With two request threads choosing the alias launch at the same moment, both run find, both see nothing, and both save. One user's link silently overwrites the other's, and both got a success response. Real stores solve this with one atomic operation: ConcurrentHashMap.putIfAbsent in memory, or a unique index with INSERT in a database, which rejects the second insert. Designing the repository method as insertIfAbsent from the start puts the atomicity in the contract, where every implementation has to honour it.

    ⚠️
    Common mistakes
    • A class per noun. User, Visitor, Visit, Dashboard, Url… Most are actors, fields or out of scope.
    • Asking questions that don't change anything, or asking them one at a time for ten minutes. Propose defaults in one batch.
    • Raw strings for validated concepts. Every method taking String alias must re-validate or trust blindly. Make it a value object.
    • “Check, then save” for uniqueness. Put an atomic insert in the repository contract.
    • Calling Instant.now() inside domain classes. Inject a Clock, or tests can't check expiry.
    • A LinkManager that does everything. Logic about one link belongs on ShortLink; the service only coordinates.
    🎤
    Interview drill

    Explain it simply: How do you decide whether a noun from the requirements becomes a class?

    How a strong answer sounds
    It becomes a class if it has rules or behaviour of its own, if it's a group of values that belong together or need validation, if it's a point where behaviour varies (then it's an interface), or if it hides a detail like storage. Otherwise it's a field or a parameter. Actors like “visitor” are who calls the system, so usually they aren't classes at all, and features we've agreed to skip don't get classes either.

    Deeper: Walk me through your first ten minutes on “design a URL shortener”.

    How a strong answer sounds
    I'd propose defaults in one go: custom aliases allowed, optional expiry, click counts, many request threads, in-memory storage behind an interface. Then I'd list four use cases (shorten, redirect, delete, see clicks) and cut login, dashboards and abuse detection. From the nouns I'd keep ShortLink as the entity, Alias as a validated value object, CodeGenerator and LinkRepository as interfaces, and a LinkService for the use cases, with a Clock injected. Then I'd walk the redirect flow through them to check nothing's missing, before writing code.

    🧠 Key takeaways

    • Ask only questions whose answers change the design, and ask them as a batch of proposed defaults.
    • Write use cases as actor + verb phrase; state what's out of scope out loud.
    • Nouns are candidate classes, verbs candidate methods, and most candidates don't survive filtering.
    • A class earns its place with rules or behaviour, validation, variation (interface) or hiding a detail.
    • Actors call the system; they are rarely classes inside it.
    • Walk one use case through the class list before coding; it exposes missing methods and misplaced logic.

    Check your understanding

    The interviewer confirms that short links can expire. What should that add to the design?

    Expiry is a rule about one link, so it lives on the link, checked when the link is resolved. Injecting a Clock makes “one second after expiry” testable. Cleanup of old links can come later, as a separate concern.

    In “each car in the parking lot has a colour”, what should colour become?

    A candidate that just holds a value, with no rules, behaviour or variation, is a field. An enum type is reasonable if the set of colours is fixed and matters to the design.

    Why make Alias a value object instead of passing String alias around?

    A value object turns a rule (“4–32 characters from this set”) into a type. Invalid aliases can't exist, and a method signature like resolve(Alias) can't be called with a target URL by mistake.

    Two users request the custom alias launch at the same moment. Which repository design prevents both from succeeding?

    Check-then-save has a gap between the check and the save where both threads can pass. The check and the insert must be one atomic operation: putIfAbsent in memory, or a unique index in a database.

    Which requirement is the most reasonable to cut out loud in a 45-minute shortener round?

    The dashboard is a separate feature built on top of the core. The other three are the core: the main use case, a data rule, and the concurrency problem the interviewer is most likely to probe.
