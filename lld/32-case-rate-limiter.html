Case Study: Rate Limiter

A rate limiter decides, for each incoming request, whether this client has used up its allowance. As an LLD problem it's compact and rich: four well-known algorithms that make different trade-offs, per-client state that has to be created safely and cleaned up, time that must be injectable to test anything, and a hot path hit by every request on every thread. This case study builds a library you could put in front of an API.

  • Turn “limit clients to N requests per window” into an API with a useful answer
  • Implement fixed window, sliding log, sliding counter and token bucket behind one interface
  • Create per-client state safely and keep memory bounded
  • Test time-based behaviour exactly with an injected ticker
  • Keep the hot path correct and fast under concurrency

Requirements and API

Clarify first. Is this a library inside one service, or a shared service for a fleet? (Library, in-process; distributed limits are the follow-up.) What's the client key? (An API key; could be user id or IP.) Do all clients get the same limit? (No: free and paid tiers.) Are bursts acceptable? (Yes, briefly.) What does a rejected caller need? (Enough to send HTTP 429 with a Retry-After header.) So the answer to “may I?” is more than a boolean:

public interface RateLimiter {
	Decision tryAcquire(ClientKey client);            // never blocks
}

public record Decision(boolean allowed, long remaining, Duration retryAfter) {
	static Decision allow(long remaining) { return new Decision(true, remaining, Duration.ZERO); }
	static Decision deny(Duration retryAfter)  { return new Decision(false, 0, retryAfter); }
}

public record RateLimitPolicy(int permits, Duration window, int burst) {     // “100 per minute, bursts of 20”
	public RateLimitPolicy { if (permits <= 0 || burst <= 0 || window.isNegative() || window.isZero()) throw new IllegalArgumentException(); }
}

The design splits into three roles. A Limiter holds one client's state for one algorithm. A KeyedRateLimiter maps client keys to limiters and implements RateLimiter. A LimiterFactory decides which algorithm and which policy each new client gets (by tier), so neither of the others knows about tiers or algorithm choice.

Algorithms as strategies

Each algorithm is a small class implementing one method, taking the current time as a parameter so it never reads a clock itself:

Token bucket is the usual default, because its two parameters map directly onto what product people ask for: a sustained rate and a tolerated burst. It also needs no timer thread: tokens are refilled lazily, computed from the elapsed time whenever a request arrives.

final class TokenBucket implements Limiter {
	private final double capacity;
	private final long permits, windowNanos;              // refill rate = permits / window
	private double tokens;
	private long last;

	TokenBucket(RateLimitPolicy p, long now) {
		capacity = p.burst(); permits = p.permits(); windowNanos = p.window().toNanos();
		tokens = capacity; last = now;                       // a new client starts with a full bucket
	}

	public synchronized Decision tryAcquire(long now) {
		long elapsed = Math.max(0, now - last);
		tokens = Math.min(capacity, tokens + (double) elapsed * permits / windowNanos);
		last = now;
		if (tokens >= 1) { tokens -= 1; return Decision.allow((long) tokens); }
		long wait = (long) Math.ceil((1 - tokens) * windowNanos / permits);
		return Decision.deny(Duration.ofNanos(wait));
	}
}

final class FixedWindow implements Limiter {
	private final int limit; private final long windowNanos;
	private long windowStart; private int count;

	public synchronized Decision tryAcquire(long now) {
		if (now - windowStart >= windowNanos) { windowStart = now - (now - windowStart) % windowNanos; count = 0; }
		if (count < limit) { count++; return Decision.allow(limit - count); }
		return Decision.deny(Duration.ofNanos(windowStart + windowNanos - now));
	}
}
// SlidingWindowLog: an ArrayDeque<Long> of accepted times, trimmed from the front.
// SlidingWindowCounter: two counts and the current window's start.
Four algorithms, same traffic: “10 requests per 10 s”Interactive
Green dots were allowed, red were rejected. Dashed lines are the fixed window's boundaries. The token bucket here has capacity 10 and refills 1 token per second, which is a different contract (“bursts of 10, 1 per second sustained”) from “never more than 10 in any 10 s”.

The boundary pattern is the classic interview point: a fixed window lets a client send its full allowance at the end of one window and again at the start of the next, 20 requests in about two seconds. The sliding log enforces the limit exactly, over any window, at the cost of storing a timestamp per request. The sliding counter gets close with two numbers, but it assumes the previous window's traffic was spread evenly, so traffic bunched at a window's end fools it. Pick by what the requirement actually says.

Per-client limiters

The keyed limiter creates a client's limiter on first use. The creation must be atomic: a get, then a put if absent, is a check-then-act race (Chapter 22) where two threads can each create a fresh bucket for the same client and one of them hands out a second full allowance. computeIfAbsent on a ConcurrentHashMap does the check and the insert as one step.

public final class KeyedRateLimiter implements RateLimiter {
	private final ConcurrentHashMap<ClientKey, Limiter> limiters = new ConcurrentHashMap<>();
	private final LimiterFactory factory;                   // algorithm + policy for a client's tier
	private final Ticker ticker;                             // monotonic time source, injected

	public Decision tryAcquire(ClientKey client) {
		long now = ticker.nanos();
		return limiters.computeIfAbsent(client, k -> factory.create(k, now)).tryAcquire(now);
	}
}

LimiterFactory tiers = (client, now) -> new TokenBucket(policies.forTier(accounts.tierOf(client)), now);

Memory has to be bounded. A limiter per API key is fine; a limiter per IP address, under a scan from millions of addresses, is a memory leak. Idle limiters must go. A token bucket that has refilled to full is indistinguishable from a brand-new one, so it's safe to drop; a periodic sweep can remove buckets idle for longer than the time to refill completely. The simpler route is to hold limiters in a cache with expire-after-access (Chapter 31) and a maximum size.

Clock injection for tests

Rate limiting is all about time, so untestable time means an untestable limiter. Two decisions make it testable. First, limiters take now as a parameter, so unit tests of an algorithm pass numbers. Second, the keyed limiter reads time from an injected Ticker, a one-method interface returning nanoseconds. Production uses System::nanoTime, which is monotonic: unlike the wall clock (Clock, currentTimeMillis), it never jumps backwards when the system clock is adjusted, which would otherwise hand out tokens or lock clients out. Tests use a fake they advance by hand:

@Test void burstThenOnePerSecond() {
	FakeTicker time = new FakeTicker();
	RateLimiter limiter = new KeyedRateLimiter((k, now) -> new TokenBucket(new RateLimitPolicy(10, Duration.ofSeconds(10), 10), now), time);

	for (int i = 0; i < 10; i++) assertTrue(limiter.tryAcquire(ALICE).allowed());
	Decision d = limiter.tryAcquire(ALICE);
	assertFalse(d.allowed());
	assertEquals(Duration.ofSeconds(1), d.retryAfter());

	time.advance(Duration.ofSeconds(1));
	assertTrue(limiter.tryAcquire(ALICE).allowed());         // exactly one token after 1 s
	assertFalse(limiter.tryAcquire(ALICE).allowed());        // and only one
	assertTrue(limiter.tryAcquire(BOB).allowed());           // clients are independent
}

This is also why the refill is computed as elapsed × permits / window rather than multiplying by a precomputed rate: 10 tokens per 10 s as a rate is 10−9 per nanosecond, which isn't exact in binary floating point, and a test that expects exactly one token after exactly one second could fail by a rounding error. Multiplying first keeps whole-second cases exact. Fractions still accumulate across many small refills, so a test that probes 999 ms and then 1 ms more may land a hair either side of one token. If exact boundaries matter, store time instead of tokens: the GCRA variant of the token bucket keeps a single integer, the “theoretical arrival time” of the next allowed request, and compares nanoseconds with no floating point at all.

Concurrency

Every request on every thread passes through here, so the design keeps contention narrow. The map is a ConcurrentHashMap, so lookups for different clients don't block each other. Each limiter synchronizes on itself, so threads only wait for other requests from the same client, and the critical section is a few arithmetic operations with no I/O. That's enough for most services. If one very hot key (a big customer's integration) makes its lock a bottleneck, a token bucket can be made lock-free by packing its state into one AtomicLong and updating it with a compare-and-set loop, at the cost of harder code. Measure before going there.

Rate limiting a payments API

Stripe's 2017 engineering post “Scaling your API with rate limiters” describes running several limiters in production: a request-rate limiter per user, implemented as a token bucket stored in Redis; a limit on concurrent in-flight requests per user; and load shedders that reserve capacity for the most critical traffic when the whole fleet is under pressure. The post's advice matches this chapter's design: return 429 with clear information so well-behaved clients can back off (Chapter 25), start new limiters in a dark mode that only logs what they would reject, and make it easy to adjust limits per user without a deploy.

⚠️
Common mistakes
  • get then put to create a client's limiter: concurrent first requests get separate buckets.
  • One global lock around all clients, so every request in the service waits for every other.
  • A timer thread per bucket to add tokens. Refill lazily from elapsed time.
  • Wall-clock time (currentTimeMillis) that can jump backwards; use a monotonic ticker, and inject it.
  • Unbounded per-client state keyed by IP address. Expire idle limiters.
  • Returning only a boolean, so the API can't tell clients when to retry.
  • Promising “never more than N per window” with a fixed window, which allows 2N around boundaries.

Interview drill

Explain it simply: How does a token bucket work, and why is it a popular choice?

How a strong answer sounds
Each client has a bucket with a capacity and a refill rate. Tokens are added continuously at the rate, up to the capacity; each request takes one token, and a request with no token available is rejected with the time until the next token. It's popular because the two numbers map straight onto the requirement, a sustained rate plus an allowed burst, the state is just two numbers per client, and refilling can be computed lazily from the elapsed time, so there's no background thread.

Deeper: The service now runs on 20 instances behind a load balancer, and a client's limit must hold across all of them. What changes in your design?

How a strong answer sounds
The RateLimiter interface doesn't change; the Limiter implementation does. Option one: keep the state in a shared store and make each check atomic there, for example a Redis script that refills and spends a token in one step, keyed by client. It's exact, but adds a network round trip to every request and makes the store a dependency, so it needs a timeout and a fail-open or fail-closed decision (Chapter 25). Option two: give each instance a local bucket with 1/20th of the rate; there's no network call, but it's only approximate, since a client whose traffic lands unevenly gets limited early. A hybrid syncs local counts to the store in the background. I'd pick based on how strict the limit is: billing-grade quotas go to the shared store, abuse protection can be local.

🧠 Key takeaways

  • Return a Decision (allowed, remaining, retry-after), not a boolean, so the API can send a useful 429.
  • Algorithms are strategies behind Limiter; a factory picks algorithm and policy per client tier.
  • Fixed window is simple but allows 2× at boundaries; sliding log is exact but stores timestamps; token bucket gives burst plus rate with two numbers.
  • Create per-client limiters atomically with computeIfAbsent, and expire idle ones.
  • Refill lazily; take time as a parameter; inject a monotonic ticker so tests are exact.
  • Lock per client, not globally; distributed limits swap the Limiter implementation, not the API.

Check your understanding

With a fixed window of “10 per 10 s”, what's the most a client can get through in about two seconds?

The counter resets at the boundary, so two full allowances can land back to back. A sliding log prevents this.

Why use computeIfAbsent to create a client's limiter?

Get-then-put is check-then-act: two threads can both see “absent” and both create limiters, doubling the client's allowance.

How does a token bucket add tokens without a background thread?

Lazy refill: tokens = min(capacity, tokens + elapsed × rate). Nothing happens between requests.

Why should the rate limiter read time from an injected monotonic ticker rather than System.currentTimeMillis()?

Backwards jumps corrupt elapsed-time calculations; injection makes refill and retry-after behaviour testable to the millisecond.

The limiter keys by IP address and memory grows steadily during a scan from millions of addresses. What's the fix?

A full, idle token bucket is equivalent to a new one, so dropping it is safe. Bounding the map keeps memory under control.
