Case Study: Movie Ticket Booking

Two people click the same seats a second apart. Exactly one of them must get them, neither may end up with half the seats they asked for, and seats held by someone who wanders off must come back. That's the whole problem, and it touches most of the Advanced level: a contract for holds (Chapter 7), an aggregate that guards an invariant (Chapter 27), expiry driven by a clock, a booking state machine, and a payment that can arrive after the hold it was paying for has already expired.

  • Model movies, screens, shows, seats and bookings with the show as the consistency boundary
  • Hold several seats all-or-nothing, with an expiry
  • Prevent double booking in memory and in the database
  • Drive bookings through explicit states, including late and failed payments
  • Keep payment and confirmation retry-safe

Requirements and API

Clarify: customers browse shows of a movie, see the seat map, pick several seats, and have a few minutes to pay while those seats are held for them; seats can't be booked twice or held by two people; a partial hold is never acceptable (a family of four doesn't want two seats); abandoned holds are released; payment happens through an external gateway; confirmed bookings get tickets. Out of scope: recommendations, dynamic pricing, and the waiting room that protects the system during huge on-sales.

public interface BookingService {
	SeatMap seatMap(ShowId show);                                           // free, held and booked seats, with prices
	Hold hold(ShowId show, Set<SeatId> seats, CustomerId who);          // all or nothing; throws SeatUnavailableException
	PaymentSession checkout(HoldId hold);                                    // starts payment, keyed by the hold
	Booking onPaymentSucceeded(HoldId hold, PaymentRef payment);            // the gateway's callback; idempotent
	void release(HoldId hold);                                                // customer backs out
}

Entities: movie, show, screen, seat, booking

Separate what's shared from what's per screening. A Movie and a Screen (with its fixed seat layout and seat categories) exist independently. A Show is one screening: a movie on a screen at a time, with its own prices and, crucially, its own seat states. The invariant, “no seat of this show is held or booked by two customers”, only ever involves the seats of one show, so the Show is the aggregate that guards it: one object, one lock, one version to check. Different shows never contend with each other.

Seat holds with expiry

A hold is a promise with a deadline: these seats are yours for five minutes. Implement it inside the Show, under the show's lock, as check-all-then-change-all: first verify every requested seat is free, and only if all are, mark them held. Nothing changes on failure, so there's never a half hold to clean up. Expiry is lazy: each operation first releases holds whose time has passed, measured by an injected clock, so an abandoned hold can't block anyone even if no background job has run yet. A scheduled sweep (Chapter 35) still releases idle ones, so seat maps don't show stale holds.

sealed interface SeatState permits Free, Held, Booked {}
record Free() implements SeatState {}
record Held(HoldId hold) implements SeatState {}
record Booked(BookingId booking) implements SeatState {}

public final class Show {                                                  // aggregate root
	private final Map<SeatId, SeatState> seats;
	private final Map<HoldId, Hold> holds = new HashMap<>();
	private final Clock clock;

	public synchronized Hold hold(Set<SeatId> wanted, CustomerId who, Duration ttl) {
		Instant now = clock.instant();
		expireHolds(now);                                                  // lazy expiry first
		List<SeatId> taken = wanted.stream().filter(s -> !(seats.get(s) instanceof Free)).toList();
		if (!taken.isEmpty()) throw new SeatUnavailableException(taken);   // check all: nothing has changed yet
		Hold h = new Hold(HoldId.random(), who, Set.copyOf(wanted), now.plus(ttl));
		wanted.forEach(s -> seats.put(s, new Held(h.id())));               // then change all
		holds.put(h.id(), h);
		return h;
	}

	public synchronized Booking confirm(HoldId id, PaymentRef payment) {
		expireHolds(clock.instant());
		Hold h = holds.remove(id);
		if (h == null) throw new HoldExpiredException(id);                  // the caller must refund
		Booking b = Booking.confirmed(h, payment);
		h.seats().forEach(s -> seats.put(s, new Booked(b.id())));
		return b;
	}

	private void expireHolds(Instant now) {
		holds.values().removeIf(h -> {
			if (now.isBefore(h.expiresAt())) return false;
			h.seats().forEach(s -> seats.put(s, new Free()));
			return true;
		});
	}
}

Preventing double booking

In memory, the synchronized Show makes each hold one atomic step: two requests for overlapping seats run one after the other, and the second sees the first one's holds. The race in the simulator shows what happens without that: if each seat is checked and set independently, two overlapping requests interleave, both see free seats, and the result is some seats claimed twice and customers holding partial sets.

With a database, the same all-or-nothing step becomes one transaction of conditional updates, and the updated-row count is the check:

UPDATE show_seats
   SET status = 'HELD', hold_id = :hold, expires_at = :expiry
 WHERE show_id = :show AND seat_id IN (:seats)
   AND (status = 'FREE' OR (status = 'HELD' AND expires_at < :now));   -- expired holds count as free
-- rows updated == number of seats requested → COMMIT; otherwise ROLLBACK and report unavailable

Then add a safety net that holds even if application code has a bug: a unique constraint on (show_id, seat_id) in the booked-seats table, so the database itself refuses a second booking of the same seat. Belt and braces is right here: a double-booked seat is the one failure every customer notices.

Payment and booking states

Payment is the slow, unreliable step, and it's where the edge cases live. The hold's id is the payment's idempotency key (Chapter 25), so a retried checkout can't charge twice. Starting checkout extends the hold once, up to a cap, so a customer typing a card number doesn't lose seats to the timer. And the gateway's success callback can arrive after the hold expired and the seats went to someone else, so confirm must be ready to fail, and the service must refund.

public Booking onPaymentSucceeded(HoldId hold, PaymentRef payment) {
	Optional<Booking> done = bookings.findByHold(hold);
	if (done.isPresent()) return done.get();                             // the gateway retried its callback
	try {
		Booking b = shows.get(showOf(hold)).confirm(hold, payment);
		bookings.save(b);
		events.publish(new BookingConfirmed(b.id()));                       // tickets, email: after commit
		return b;
	} catch (HoldExpiredException e) {
		payments.refund(payment, new IdempotencyKey("refund-" + hold));     // never keep money for seats we can't give
		throw new BookingFailedException("seats were released before payment completed");
	}
}

When the whole city clicks at once

In November 2022, the Ticketmaster presale for Taylor Swift's Eras Tour was overwhelmed by demand; fans faced long queues, errors and lost carts, the general sale was cancelled, and the episode led to a US Senate hearing in January 2023. The lesson for this chapter is about layers. Everything above, holds that are all-or-nothing, expire on time and never double-book, is necessary, and it's also not enough: at that scale the seat logic has to be protected by admission control (a virtual waiting room that lets buyers in at a rate the inventory service can handle), bot detection and sharded inventory, which is the System Design chapter's territory. Correct classes are the foundation that makes those layers safe to add.

⚠️
Common mistakes
  • Checking and setting seats one at a time without one atomic step: partial holds and double booking.
  • Seat state on the Screen instead of the Show: every screening shares one seat map.
  • Holds that only expire when a background job runs; check expiry lazily on every operation too.
  • No refund path for a payment that succeeds after the hold expired.
  • Non-idempotent payment and callbacks: retries charge twice or book twice.
  • Relying only on application logic; add a unique constraint on (show, seat) bookings.
  • A global lock across all shows, when the invariant only spans one show.

Interview drill

Explain it simply: Two users try to book overlapping seats at the same moment. What happens in your design?

How a strong answer sounds
Both requests go to the same Show, which is the aggregate that owns its seats' states. hold is synchronized on the show: it first expires stale holds, then checks every requested seat is free, and only then marks them all held. Whichever request runs first gets all its seats; the second sees some of them held and fails with SeatUnavailableException without changing anything, so nobody ends up with a partial set. In the database the same step is a conditional update of all the seats in one transaction, checking the row count, plus a unique constraint on booked (show, seat) as a final guard.

Deeper: A blockbuster premiere sells out in minutes and the show's lock becomes a hotspot. How would you change the design?

How a strong answer sounds
First, keep the critical section tiny: no I/O under the lock, just seat-state changes, which is microseconds, so a single show can handle a lot. If that's still the bottleneck, I'd narrow the boundary: split a large venue into sections, each its own aggregate with its own lock, since most holds fall within one section; a multi-section hold locks sections in a fixed order to avoid deadlock. In the database, row-level conditional updates already give per-seat concurrency. And the bigger lever is upstream: a waiting room that admits buyers at a controlled rate, and moving seat selection to “best available” in a section, which reduces conflicts on the exact same seats. I'd measure lock wait time before choosing.

🧠 Key takeaways

  • Seat state belongs to the Show, the aggregate whose invariant is “no seat claimed twice”.
  • Hold all-or-nothing: check every seat, then change every seat, in one atomic step.
  • Expire holds lazily on each operation and sweep in the background; use an injected clock.
  • In the database: one transaction of conditional updates with a row-count check, plus a unique constraint.
  • Bookings follow explicit states; key payments and refunds by the hold id so retries are safe.
  • Handle the late payment: if the hold expired, refund automatically.

Check your understanding

Where should the state of each seat (free, held, booked) live?

The layout belongs to the screen, but availability belongs to one screening. The Show is the aggregate that guards it.

A customer asks to hold C3, C4 and C5, but C5 is already held. What should happen?

All or nothing: check every seat first, and change nothing if any is taken, so there's no partial hold to clean up.

Why check hold expiry lazily inside hold and confirm, rather than only with a background job?

Correctness can't depend on job timing. The job keeps seat maps tidy; the lazy check makes expiry exact.

The payment gateway reports success for a hold that expired a minute ago, and the seats are now Bob's. What should the system do?

Bob's hold is legitimate. The late payment becomes an explicit REFUND transition, idempotent so a retried callback can't refund twice.

What is the database-level safety net against double booking?

Even if application code has a bug, the database refuses a second booking of the same seat for the same show.
