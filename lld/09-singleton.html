Singleton (and Why It’s Usually Wrong)

Singleton is the pattern everyone learns first and the one interviewers most like to poke at. It guarantees a class has exactly one instance, reachable from anywhere. The “exactly one” part is sometimes useful. The “reachable from anywhere” part is global state, with all the problems that brings. This chapter shows how to write a singleton correctly under concurrency, which is harder than it looks, and why most designs are better off without one.

  • Explain why the holder idiom and enums are thread-safe without explicit locks
  • Name the design costs of a singleton: hidden dependencies, shared test state, fixed lifecycle
  • Replace a singleton with one instance created in the composition root and injected

The pattern, and where it's tempting

A Singleton has a private constructor, so nobody else can create one, and a static method or field that hands out the single instance. It's tempting whenever something “should only exist once” in a process: a configuration registry, a metrics registry, a connection pool, a cache. The JDK has a few, like Runtime.getRuntime(), and many immutable “singletons” like Collections.emptyList() and Comparator.naturalOrder().

The simplest correct version is eager: create it when the class is initialised.

public final class ConfigRegistry {
	private static final ConfigRegistry INSTANCE = new ConfigRegistry();   // created once, at class init
	private final Map<String, String> values;

	private ConfigRegistry() { values = loadFromFileAndEnvironment(); }          // private: no one else can new it
	public static ConfigRegistry get() { return INSTANCE; }
	public Optional<String> value(String key) { return Optional.ofNullable(values.get(key)); }
}

This is thread-safe with no locks at all. The JVM initialises a class exactly once, under an internal lock, the first time it is actually used (not simply when the program starts), and guarantees every thread sees the fully initialised static fields afterwards. For most singletons, “eager” is already lazy enough.

Lazy initialisation, and its race

When construction is expensive and might never be needed, people write it lazily. The obvious version is broken:

public static ConfigRegistry get() {
	if (instance == null) {                  // check…
		instance = new ConfigRegistry();       // …then act: two threads can both get here
	}
	return instance;
}

It's the check-then-act race again. Two request threads arrive at startup, both see null, both construct, and the process briefly has two registries, possibly with different contents if the loaded files changed in between. Making the whole method synchronized fixes it, at the cost of taking a lock on every call forever, even though it's needed only once. Double-checked locking tries to take the lock only on the first call, and it has a famous trap: without volatile, another thread can see the reference before the constructor has finished, because the JIT compiler and CPU may reorder “publish the reference” ahead of “initialise the fields”. Step through all five versions below; you control which thread moves.

The “DCL, no volatile” mode shows the reordering the Java memory model allows: allocate, publish the reference, then run the constructor. Real hardware and JITs do this; the bug is rare, timing-dependent, and nearly impossible to reproduce on demand, which is exactly why it's dangerous.

// Holder idiom: the nested class isn't initialised until get() touches it
public final class ConfigRegistry {
	private ConfigRegistry() { … }
	private static final class Holder { static final ConfigRegistry INSTANCE = new ConfigRegistry(); }
	public static ConfigRegistry get() { return Holder.INSTANCE; }
}

// Enum singleton (Effective Java's recommendation)
public enum MetricsRegistry {
	INSTANCE;
	private final ConcurrentHashMap<String, LongAdder> counters = new ConcurrentHashMap<>();
	public void increment(String name) { counters.computeIfAbsent(name, k -> new LongAdder()).increment(); }
}

  
Both rely on the same JVM guarantee as the eager version: class initialisation happens once, under a lock, and its results are visible to every thread. The holder just delays it until get() is first called.


  
Why it's usually wrong

  
Getting one instance safely is solved. The trouble is what the pattern does to the rest of the design:

  
    
    
  • It's a hidden dependency. Any method can call ConfigRegistry.get(), so a class's constructor no longer tells you what it depends on (Chapter 8).
    • 
    
  • It can't be substituted. Code that calls MetricsRegistry.INSTANCE can't be given a fake, so tests either touch the real thing or can't run.
    • 
    
  • State leaks between tests. One test increments a counter; the next test sees it. Test order starts to matter, and a suite that passes alone fails in CI.
    • 
    
  • It fixes lifecycle and count forever. “Exactly one per JVM” was true until the day you need one registry per tenant, or two connection pools for two databases.
    • 
    
  • It's often mutable global state, so it needs thread safety everywhere it's used.
    • 
  

  
The fix keeps the useful half. “Only one instance” is a wiring decision, not a property the class must enforce: create one instance in the composition root and pass it to everyone who needs it.


// Composition root: one instance by construction, not by a private constructor
Metrics metrics = new InMemoryMetrics();
OrderService orders = new OrderService(payments, mailer, clock, ids, metrics);
SearchService search = new SearchService(index, metrics);      // same object, visibly shared

// In a test: a fresh, isolated instance per test
RecordingMetrics metrics = new RecordingMetrics();

  
DI frameworks call this “singleton scope”, and it's what they mean by a singleton: one instance per container, created and injected by the wiring. The Gang of Four pattern, with its private constructor and static accessor, is a different and much more rigid thing.

  

  

    
🧠

    
The tests that only fail together
A payments team keeps a FeatureFlags.getInstance() singleton. One test turns on new_checkout to test the new flow, and forgets to turn it off. Every test that runs after it in the same JVM now takes the new path. Locally, running one test at a time, everything passes. In CI, where the test runner happens to order that test first, eleven unrelated tests fail, and nobody can reproduce it. The fix that sticks isn't adding a reset method; it's passing a FeatureFlags object into the classes that read flags, so each test builds its own.

  


  
⚠️
Common mistakes

    
    
      
  • Unsynchronised lazy init. Two threads can both create an instance.
    • 
      
  • Double-checked locking without volatile. Another thread can see a half-constructed object.
    • 
      
  • Hand-rolling laziness nobody needs. Eager static final is already initialised on first use of the class.
    • 
      
  • Mutable singletons with plain fields. Every thread shares them: use concurrent types or locks.
    • 
      
  • Calling X.getInstance() deep inside business code. Take it as a constructor parameter instead.
    • 
      
  • Adding reset() for tests. A sign the object should be created per test, not global.
    •

Interview drill

    
Explain it simply: Write a thread-safe lazy singleton in Java and say why it's safe.

    
How a strong answer sounds
I'd use the holder idiom: a private constructor, a private static nested Holder class with a static final INSTANCE, and get() returning Holder.INSTANCE. It's lazy because the nested class isn't initialised until get() first touches it, and thread-safe because the JVM runs class initialisation exactly once under a lock and publishes the result to all threads. An enum with one constant is equally safe and also resists reflection and serialization. Double-checked locking works too, but only with a volatile field.

    
Deeper: Your design has a RateLimiterRegistry.getInstance() used in twenty places. What problems do you expect, and how would you refactor?

    
How a strong answer sounds
Hidden dependencies, tests sharing limiter state and depending on execution order, no way to use a fake or a fixed clock, and trouble the day we need per-tenant registries. I'd create one registry in the composition root and pass it through the constructors of the twenty classes, starting with the ones we test most. During the migration the static accessor can delegate to the injected instance so nothing breaks, and I'd delete it once the last caller is converted. “Only one” becomes a wiring decision the tests can override.

  


  

    
🧠 Key takeaways

    
    
      
  • Singleton: private constructor plus a static accessor to the one instance.
    • 
      
  • Eager static final is thread-safe and already lazy to first class use; it's the default.
    • 
      
  • Naive lazy init races; double-checked locking needs volatile to stop half-built objects being seen.
    • 
      
  • Holder-class and enum singletons are lazy (or near enough) and thread-safe through the JVM's class-initialisation lock.
    • 
      
  • The design cost is global state: hidden dependencies, no substitution, state leaking between tests, a fixed count.
    • 
      
  • Prefer one instance created in the composition root and injected: “singleton scope” without the pattern.

Check your understanding

    


    

      
Two threads call an unsynchronised lazy get() (if (instance == null) instance = new X();) at the same moment. What can happen?

      

        
        
        
        
      

      
The check and the assignment are separate steps, so both threads can pass the check. Each atomic step is safe on its own; the sequence isn't.

    


    

      
Why does double-checked locking need the instance field to be volatile?

      

        
        
        
        
      

      
The unsynchronised first check can see a non-null reference that was written before the object's fields. A volatile write can't be reordered before the constructor's writes, and a volatile read sees everything written before it.

    


    

      
Why is the holder-class idiom thread-safe without any synchronized keyword?

      

        
        
        
        
      

      
Class initialisation is specified to happen exactly once with proper visibility. The holder idiom borrows that guarantee and delays it until first use.

    


    

      
What is the main testing problem with calling FeatureFlags.getInstance() inside business classes?

      

        
        
        
        
      

      
A global instance is shared by every test in the JVM and hidden from constructors. Passing a FeatureFlags object in lets each test build its own.

    


    

      
What's the usual better alternative to a Singleton for a metrics registry?

      

        
        
        
        
      

      
One shared instance, created once and passed explicitly, gives the “only one” you wanted, with visible dependencies and a fresh instance per test.
