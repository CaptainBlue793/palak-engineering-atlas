What an LLD Interview Tests

“Design a parking lot” sounds like a question about parking lots. It isn't. A low-level design round measures how you turn a vague request into a small set of well-shaped classes, and then how well that design survives a change nobody mentioned at the start. This chapter sets out what the round is, how the 45 minutes should go, what gets scored, and the Java house style every listing in this course follows.

  • Tell an LLD round apart from a DSA round and a system design (HLD) round
  • Plan the 45 minutes: requirements, entities, class design, APIs, code, extension
  • Know the eight things interviewers score, and what a strong signal looks like for each
  • Handle the “now add X” follow-up that decides most rounds

Three rounds, three different questions

Most software engineering loops include up to three technical round types, and they test different skills. Mixing them up is a common way to fail an LLD round: candidates either start optimising an algorithm (the DSA reflex) or start drawing load balancers and databases (the HLD reflex).

The same problem can appear in both design rounds at different zoom levels. This course's case studies link to their System Design course counterparts wherever that happens: the LLD version designs the classes inside one of the services the HLD version draws.

The 45-minute timeline

Rounds run 35 to 60 minutes, and 45 is the most common. Strong candidates follow roughly the same shape every time. The shape matters because each phase feeds the next: code written before the entities are settled gets rewritten, and a design with no time left for the follow-up never shows that it is extensible.

    What gets scored

    Companies word their rubrics differently, but they measure the same eight things. The mock-interview room in this course scores you on exactly these, from 0 to 3 each:

    DimensionWeak signalStrong signal
    Requirements & scopeStarts designing immediately; discovers requirements mid-codeLists use cases and actors, asks the two questions that change the design, states what's out of scope
    Entities & relationshipsA class per noun, including ones that are just fieldsRight-sized classes; clear ownership; values vs entities
    AbstractionsNo interfaces, or an interface for everythingInterfaces exactly where things vary: pricing, allocation, notification
    PrinciplesGod class; logic in callers; getters and setters everywhereSmall cohesive classes; behaviour next to data; SOLID applied where it pays
    PatternsPattern names recited, then forced inA pattern used because it solves a stated problem, and named in one sentence
    Code qualityPseudo-code, or code that wouldn't compileCompiling-quality Java: names, validation, immutability, clear signatures
    Extensibility & concurrencyFollow-up needs a rewrite; shared state unguardedFollow-up is one new class or one changed method; knows what is shared and how it's protected
    CommunicationLong silences; defends every choice; ignores hintsThinks aloud, states trade-offs, takes a hint and adapts

    Notice what isn't on the list: remembering the “correct” parking-lot design. There isn't one. Two very different designs can both score well if their decisions are stated, justified and consistent.

    The follow-up is the real question

    Around minute 35 the interviewer adds something: “Now add a monthly pass.” “Two gates can issue tickets at the same time.” “How would you test the fee calculation?” This is where the round is usually decided, because it tests the one thing the first 35 minutes can only claim: that the design is easy to change.

    🧠
    Cutting scope out loud

    A candidate asked to design a movie-booking system has 45 minutes and could spend all of them on payments, seat maps, loyalty points and refunds. The strong move in minute 3 is a sentence like: “I'll cover browsing shows, holding seats and confirming a booking. Payment I'll treat as an interface we call, and I'll leave refunds and loyalty out unless you want them.” The interviewer either agrees, or tells you what they actually wanted to see. Either way you've shown judgment, and you've protected the time you need for the seat-hold logic, the part that is actually hard (Case Study 42).

    The house style

    Every Java listing in this course follows the same rules, so the shape of the code becomes a memory aid instead of noise. They're also a good default for an interview, because each rule prevents a specific bug or a specific follow-up you can't answer.

    The rules, in one listing
    // 1. Interface first: name the role before any class plays it. No "I" prefix, no "Impl" suffix.
public interface SpotAllocator {
	Optional<Spot> allocate(Vehicle vehicle);           // 4. Optional for "might not exist"
}

// 2. Final by default; composition over inheritance.
public final class NearestSpotAllocator implements SpotAllocator {
	private final List<Level> levels;                       // 3. Collaborators injected, fields final

	public NearestSpotAllocator(List<Level> levels) {
		if (levels.isEmpty()) throw new IllegalArgumentException("at least one level");   // 5. Fail fast
		this.levels = List.copyOf(levels);                  //    and copy what you store
	}

	@Override public Optional<Spot> allocate(Vehicle vehicle) {
		for (Level level : levels) {
			Optional<Spot> spot = level.claimFreeSpot(vehicle.size());   // tell, don't ask
			if (spot.isPresent()) return spot;
		}
		return Optional.empty();
	}
}

public record Vehicle(String plate, VehicleSize size) {}     // 6. Records for values; enums for fixed sets
    Also: modern Java (records, sealed interfaces, switch expressions, pattern-matching instanceof); unchecked exceptions grouped by what the caller does (P7); no framework annotations or Lombok, so the design is visible in the code; tabs, braces on the same line. And every design names its pattern and the change it survives.

    In an interview you won't write every class this carefully, and you shouldn't try. Write the two or three classes that carry the design properly, and stub the rest with one-line comments like // Level: holds spots per size; claimFreeSpot is synchronized. Saying what you are skipping is part of the signal.

    ⚠️
    Common mistakes
    • Coding in minute two. The requirements you skipped arrive later as rewrites.
    • Drawing an architecture. Load balancers and databases are the HLD round. Here, the database is an interface (BookingRepository).
    • A class for every noun. “Colour” and “Name” are fields, not classes. Classes earn their place with behaviour or rules.
    • Pattern bingo. Naming six patterns without a problem for each reads as memorisation. One well-justified Strategy beats that.
    • Pseudo-code. Most rubrics ask for code that would compile. Keep it real Java, even if some methods are stubbed.
    • Arguing the follow-up. “That wasn't in the requirements” loses the round. Show where the change goes.
    🎤
    Interview drill

    Explain it simply: What do you do in the first five minutes of an LLD round?

    How a strong answer sounds
    I restate the problem, then ask the questions that change the design: who the actors are, what the core use cases are, whether it's single-threaded or shared by many threads, and whether it needs to persist. I write the use cases down as a short list and say out loud what I'm leaving out of scope. Then I check with the interviewer before moving on to entities, so we agree on what I'm designing.

    Deeper: At minute 38 the interviewer says, “Now make it thread-safe.” You have seven minutes. What do you do?

    How a strong answer sounds
    I don't add synchronized everywhere. First I name the shared mutable state, which is usually one or two objects, like the spot inventory or the booking store. Everything immutable or confined to one request is already safe, and I say so. Then I guard the shared state at the smallest scope that keeps the invariant: one synchronized method, or a concurrent map with an atomic compute, making sure check-then-act happens inside one operation. Then I point out what I'd test, such as two threads booking the last seat.

    🧠 Key takeaways

    • LLD designs classes inside one program; DSA optimises a function; HLD arranges services across machines.
    • The round's shape: requirements, entities, class design, APIs and flows, code, extension. The order matters more than the minutes.
    • Eight scored dimensions: scope, entities, abstractions, principles, patterns, code quality, extensibility and concurrency, communication.
    • The follow-up decides most rounds: answer by pointing at where the change goes and what stays the same.
    • Cut scope out loud early; it shows judgment and protects time for the hard part.
    • House style: interface first, final classes, injected final fields, fail fast, records and enums for values, Optional for absence.

    Check your understanding

    “Design a rate limiter” comes up in an LLD round. Which answer fits the round?

    LLD is about classes and code inside one program: interfaces at the variation points and correct, extensible Java. The first answer is the HLD version of the question, and the second the DSA version.

    Why spend the first few minutes on requirements instead of starting on classes?

    Questions like “concurrent or not?” and “which features are in scope?” change the design. Settling them first, and writing them down, is cheaper than discovering them at minute 30.

    The interviewer asks for weekend pricing at minute 35. Which answer shows the strongest design?

    A good follow-up answer names the variation point from the diagram, adds one class, and says what stays untouched. That's the evidence of extensibility the round is looking for.

    Which of these is not something an LLD rubric typically scores?

    There is no single correct design. Rubrics score the quality and justification of your decisions: scope, abstractions, principles, code, extensibility, concurrency and communication.

    You have 14 minutes to code a parking-lot design with eight classes. What's the best plan?

    Depth on the interesting parts, such as allocation and fee calculation, shows more than breadth on trivial classes. Saying what you're skipping keeps the design complete without spending the minutes.
