Case Study: Task Scheduler

Send the digest email at 08:00, retry the webhook in 30 seconds, clean expired sessions every five minutes. A task scheduler runs work at a time rather than on a request, and designing one touches almost everything in the Advanced level: jobs as commands, triggers as strategies, a priority queue ordered by run time, a dispatcher thread that sleeps exactly as long as it should, a worker pool, retries with backoff, and cancellation that works whether a job is waiting, retrying or running.

  • Model jobs as commands and schedules as trigger strategies
  • Order pending runs in a priority queue and wake the dispatcher correctly
  • Separate dispatching from execution with a worker pool
  • Get fixed-rate vs fixed-delay semantics, and overlap, right
  • Add retries, dead-lettering and cancellation with a small state machine

Requirements and API

Clarify: jobs can run once at a time, after a delay, or repeatedly (every N seconds, or on a calendar expression like “08:00 on weekdays”); several jobs run in parallel on a bounded pool; one slow job mustn't delay the others; a recurring job never overlaps with itself; failures retry with backoff, then go to a dead-letter list; jobs can be cancelled; time is injectable; shutdown lets running jobs finish. Out of scope: durability across restarts and running on many machines, which is the System Design problem.

public interface Scheduler {
	JobHandle schedule(Job job, Trigger trigger, RetryPolicy retries);
	void shutdown(Duration grace);
}

public interface Job { void run(JobContext ctx) throws Exception; }        // Command

public interface Trigger {                                                  // Strategy: when's the next run?
	Optional<Instant> nextRun(Instant now, Optional<Instant> lastScheduled);   // empty = no more runs
}

public interface JobHandle { boolean cancel(); JobStatus status(); }

public record JobContext(int attempt, BooleanSupplier cancelled) {}       // long jobs check cancelled() between steps

A Job is a command (Chapter 17): a request packaged as an object that can be queued, run later, retried and cancelled. A Trigger is a strategy that answers one question, when's the next run, so “once”, “every 5 minutes” and a cron expression are three small classes, and the scheduler never switches on a schedule type.

record Once(Instant at) implements Trigger {
	public Optional<Instant> nextRun(Instant now, Optional<Instant> last) { return last.isEmpty() ? Optional.of(at) : Optional.empty(); }
}
record FixedRate(Instant first, Duration period) implements Trigger {         // anchored to the schedule
	public Optional<Instant> nextRun(Instant now, Optional<Instant> last) { return Optional.of(last.map(l -> l.plus(period)).orElse(first)); }
}
record FixedDelay(Duration initial, Duration delay) implements Trigger {     // anchored to the previous finish
	public Optional<Instant> nextRun(Instant now, Optional<Instant> last) { return Optional.of(now.plus(last.isEmpty() ? initial : delay)); }
}
// CronTrigger: parses "0 8 * * MON-FRI" and computes the next matching minute after 'now' in a given ZoneId.

A priority queue ordered by run time

Pending runs live in a priority queue (a min-heap) ordered by due time, with a sequence number to keep ties in submission order. One dispatcher thread looks at the head: if it's due, remove it and hand it to the pool; if not, sleep until it is. The subtle part is the sleep. If the dispatcher sleeps until 08:00 and someone schedules a job for 07:59, the sleep must end early, so the wait is on a Condition that schedule signals, and after every wake-up the loop re-checks the head instead of assuming.

public final class DefaultScheduler implements Scheduler {
	private final PriorityQueue<ScheduledRun> queue =
		new PriorityQueue<>(Comparator.comparing(ScheduledRun::due).thenComparingLong(ScheduledRun::seq));
	private final ReentrantLock lock = new ReentrantLock();
	private final Condition changed = lock.newCondition();
	private final ExecutorService workers;                 // bounded pool: jobs run here, never on the dispatcher
	private final Clock clock;
	private final AtomicLong seq = new AtomicLong();

	public JobHandle schedule(Job job, Trigger trigger, RetryPolicy retries) {
		JobRecord rec = new JobRecord(job, trigger, retries);
		Instant first = trigger.nextRun(clock.instant(), Optional.empty()).orElseThrow();
		enqueue(new ScheduledRun(rec, first, first, 1, seq.incrementAndGet()));
		return rec;
	}

	private void enqueue(ScheduledRun run) {
		lock.lock();
		try { queue.add(run); changed.signal(); }       // the new run may be earlier than the one being waited for
		finally { lock.unlock(); }
	}

	private void dispatchLoop() {                             // runs on the single dispatcher thread
		lock.lock();
		try {
			while (running) {
				ScheduledRun head = queue.peek();
				if (head == null) { changed.await(); continue; }
				long wait = Duration.between(clock.instant(), head.due()).toNanos();
				if (wait > 0) { changed.awaitNanos(wait); continue; }   // woken early? loop and re-check the head
				queue.poll();
				if (!head.record().isCancelled()) workers.execute(() -> runAttempt(head));
			}
		} catch (InterruptedException e) { Thread.currentThread().interrupt(); }
		finally { lock.unlock(); }
	}
}

Two design notes to say out loud. Cancelled runs are skipped lazily when they reach the head, rather than searched for and removed (O(n) in a heap). And the dispatcher only dispatches: running a job on the dispatcher thread would let one slow job delay every other job's start, which is exactly what the simulation below shows with one worker. Java's DelayQueue packages the same wait-for-the-head logic; writing it with an injected Clock keeps it testable, and tests can skip the thread entirely by calling a runDue(now) step directly with a fake clock and a same-thread executor.

Jobs as commands on a worker pool

When a run reaches a worker, runAttempt executes it and then decides what happens next: schedule the next occurrence, schedule a retry, or give up. Queuing the next occurrence after the current run finishes is what prevents a recurring job overlapping with itself; with fixed rate, a late next run simply starts immediately.

private void runAttempt(ScheduledRun run) {
	JobRecord rec = run.record();
	if (!rec.transition(JobStatus.SCHEDULED, JobStatus.RUNNING)) return;   // cancelled in the meantime
	try {
		rec.job().run(new JobContext(run.attempt(), rec::cancelRequested));
		scheduleNext(rec, run.occurrence());
	} catch (Exception e) {
		Optional<Duration> backoff = rec.retries().delayFor(run.attempt(), e);   // Chapter 25's policy
		if (backoff.isPresent() && rec.transition(JobStatus.RUNNING, JobStatus.SCHEDULED)) {
			enqueue(run.retryAt(clock.instant().plus(backoff.get()), seq.incrementAndGet()));
		} else {
			deadLetters.record(run, e);                                          // visible, not swallowed
			scheduleNext(rec, run.occurrence());                               // a failed occurrence doesn't kill a recurring job
		}
	}
}

private void scheduleNext(JobRecord rec, Instant occurrence) {
	Optional<Instant> next = rec.trigger().nextRun(clock.instant(), Optional.of(occurrence));
	if (next.isEmpty()) { rec.transition(JobStatus.RUNNING, JobStatus.DONE); return; }
	if (rec.transition(JobStatus.RUNNING, JobStatus.SCHEDULED))                 // fails if cancel() won the race
		enqueue(new ScheduledRun(rec, next.get(), next.get(), 1, seq.incrementAndGet()));
}

Retries and cancellation

Each job has a small state machine (Chapter 18), held in an AtomicReference<JobStatus> so that the worker and a cancelling thread can race safely: every change is a compare-and-set from an expected state, and exactly one side wins.

Cancellation of a running job is cooperative: Java can't safely stop a thread, so the scheduler sets a flag the job polls between steps (and may interrupt the worker, which unblocks sleeps and interruptible I/O). A job that never checks can't be stopped early, which is worth stating in the interview. Shutdown is the same idea at scale: stop the dispatcher, stop accepting new runs, let running jobs finish within a grace period, then interrupt what's left and report which scheduled runs never ran.

🧠
The recurring job that silently stopped

Java's own ScheduledThreadPoolExecutor is built from the same parts: a delay queue ordered by run time (a heap), and a worker pool. Its scheduleAtFixedRate documentation contains a line many teams discover in production: if any execution of the task throws an exception, subsequent executions are suppressed. An unhandled exception in a nightly cleanup job doesn't crash anything or log anything by itself; the job just never runs again, and the Future nobody checks holds the exception. The usual fix is to catch and log everything inside the task. This chapter's design makes that the scheduler's job instead: failures go to retries and a dead-letter list, and a failed occurrence never cancels the next one.

⚠️
Common mistakes
  • Running jobs on the dispatcher thread: one slow job delays every start.
  • Sleeping until the head's time without waking on new, earlier jobs. Wait on a condition that schedule signals, and re-check after waking.
  • A timer thread per job instead of one queue and one dispatcher.
  • Scheduling the next occurrence when a run starts, so slow runs overlap with themselves.
  • Letting an exception end a recurring job silently.
  • Cancelling with a plain boolean that races with the worker; use compare-and-set transitions.
  • Reading the system clock directly, making timing untestable.

Interview drill

Explain it simply: How does a scheduler know when to run the next job without checking every job constantly?

How a strong answer sounds
Pending runs are kept in a priority queue ordered by due time, so the earliest is always at the head in O(1) and insertion is O(log n). One dispatcher thread sleeps until the head is due, on a condition variable. Scheduling a new job signals the condition, so if the new job is earlier the dispatcher wakes and re-checks. Due runs are handed to a worker pool, so the dispatcher never runs job code itself.

Deeper: A job scheduled every minute sometimes takes three minutes. What happens with fixed rate, with fixed delay, and what would you want?

How a strong answer sounds
In both, the next occurrence is only queued when the current one finishes, so it never overlaps with itself. With fixed rate the next run is anchored to the schedule: the 12:01 and 12:02 occurrences are already overdue, so they run back to back immediately, catching up. With fixed delay the next run is one minute after the finish, so it runs at 12:04 and the schedule drifts. Which is right depends on the job: for “aggregate the last minute's metrics” you want every occurrence; for “poll for new files” catching up is wasted work, so I'd use fixed delay, or fixed rate with a misfire policy that skips missed occurrences and runs once. I'd also alert when a run takes longer than its period, since that's usually the real problem.

🧠 Key takeaways

  • Jobs are commands; triggers are strategies that compute the next run (once, fixed rate, fixed delay, cron).
  • Pending runs sit in a min-heap by due time; one dispatcher waits on a condition that new schedules signal.
  • The dispatcher only dispatches; a bounded worker pool runs jobs.
  • Queue the next occurrence after a run finishes to prevent overlap; fixed rate catches up, fixed delay drifts.
  • Failures retry through a backoff policy, then dead-letter; a failed occurrence never kills a recurring job.
  • A compare-and-set state machine makes cancellation safe; cancelling a running job is cooperative.

Check your understanding

The dispatcher is sleeping until a job due at 08:00. A new job is scheduled for 07:59. What must happen?

Waking on every insert and re-checking the head is what keeps an earlier job from being delayed by a sleep that started before it existed.

Why does the dispatcher hand jobs to a worker pool instead of running them itself?

With one thread doing both, an 8-second export makes everything behind it 8 seconds late, as the simulation shows with one worker.

A job runs every 60 s at a fixed delay and takes 20 s. Roughly how far apart are the starts of consecutive runs?

Fixed delay = finish + delay, so start-to-start is duration + delay. Fixed rate would keep starts 60 s apart.

How does the scheduler prevent a recurring job from overlapping with itself?

Only one run of a job is ever in the queue or running at a time. A late next run starts right after, never alongside.

Why are job status changes done with compare-and-set?

With a plain field, cancel could be overwritten by a worker rescheduling the job. Each transition succeeding only from its expected state removes the race.
