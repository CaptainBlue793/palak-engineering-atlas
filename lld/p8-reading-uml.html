Reading UML: Class & Sequence Diagrams

In an LLD round you have a whiteboard and two minutes to show your design before anyone reads code. UML is the shared shorthand for that: boxes for classes, a handful of arrow styles for how they relate, and lifelines for how a request moves through them. You need a small, precise subset of it, and this chapter teaches exactly that subset, in both directions: diagram to Java, and Java to diagram.

  • Read and draw a class box: name, fields, methods, visibility, static and abstract
  • Recognise the six relationships (dependency, association, aggregation, composition, inheritance, realization) and write the Java for each
  • Read multiplicities like 1, 0..1 and *
  • Read a sequence diagram: lifelines, calls, returns, self-calls and fragments
  • Keep an interview diagram small enough to be useful

Why a diagram, and how much of UML you need

UML (the Unified Modeling Language) is huge: fourteen diagram types and a specification hundreds of pages long. An LLD interview uses two of them. A class diagram shows structure: which classes and interfaces exist and how they relate. A sequence diagram shows behaviour: which objects call which, in what order, for one use case. Drawn well, the first answers “what did you build?” and the second answers “does it actually work?”, before either of you reads a line of code.

Precision matters more than completeness. A diagram with six boxes and correct arrows beats one with twenty boxes and every getter listed. The interviewer is reading it for your decisions: what's an interface, who owns whom, where the variation points are.

Class boxes

A class is a box with up to three compartments: the name, the fields (UML calls them attributes) and the methods (operations). Each member starts with a visibility symbol, and types come after a colon, the opposite of Java:

You can leave out anything that isn't relevant to the point you're making: a compartment, types, even all the fields. In an interview, list the fields that carry the design (the capacity and tokens that the invariant is about) and the public methods. Skip getters, setters, equals and toString.

The six relationships

Almost everything interesting in a class diagram is in the lines between boxes. There are six line styles to learn, and each one has a direct Java meaning. Two things are drawn at the target end of the line (arrowheads and triangles), and one at the source end (diamonds, which sit on the whole, not the part):

RelationshipMeansIn JavaLifetime of the other object
Dependency“uses, briefly”A parameter, local variable or return typeUnrelated
Association“knows about, keeps a reference to”A fieldIndependent
Aggregation“has, as a loose part”A field (often a collection) of objects that can exist without the whole, or belong to several wholesIndependent
Composition“owns, as a part”A field of objects the whole creates, manages and doesn't shareDies with the whole
Inheritance“is a kind of”extendsSame object
Realization“implements the role”implementsSame object

Aggregation vs association is the one fuzzy line. In Java both are just a field, and many teams never draw aggregation at all, using a plain association plus a multiplicity instead. Composition is worth drawing, because it answers a real design question: who creates this object, and who is allowed to hold on to it? A ConnectionPool creates, hands out and closes its connections: composition. An OnCallRotation lists engineers who exist anyway and may be in several rotations: aggregation at most.

Multiplicity

A multiplicity written near the end of a line says how many objects can be at that end. The common ones are 1 (exactly one), 0..1 (optional), * (any number, including zero) and 1..* (at least one). Read it from the far box: in Router ◆— * Route, the * sits next to Route and means “one router has any number of routes”. It maps straight to the Java type: 1 is a plain field validated non-null, 0..1 an Optional or nullable field, * a List, Set or Map.

A whole design on one page: a small HTTP serverDiagram
  • HttpServer ◆— 1 Router and Router ◆— * Route: the server creates its router and the router its routes; none of them is shared.
  • HttpServer ◇— * Middleware: middleware objects are passed in and may be shared between servers.
  • Route → 1 RequestHandler: each route keeps a reference to one handler, which it doesn't own.
  • StaticFileHandler and ApiHandler ⇢▷ RequestHandler: two implementations of one interface, the variation point of the design.
  • Router ⇢ Request: the router only receives requests as a parameter to dispatch.
Read it the way an interviewer will: interfaces first (they're the extension points), then diamonds (who owns what), then everything else. Adding a new kind of endpoint means one new class under RequestHandler, and nothing else changes.

Sequence diagrams

  
A sequence diagram shows one scenario over time. Each participant is a lifeline: a box at the top with a vertical dashed line under it. Time runs downwards. Arrows between lifelines are messages, usually method calls, numbered or simply read top to bottom.

  

    

      
NotationMeans

      
        
Solid line, filled arrowheadA synchronous call: the caller waits for it to return

        
Dashed line, open arrowheadA return value (often left out when it's obvious)

        
Solid line, open arrowheadAn asynchronous message: the sender doesn't wait (a queue publish, an event)

        
An arrow from a lifeline back to itselfA self-call: an object calling its own method

        
A thin rectangle on a lifelineAn activation: the object is busy running a method

        
A labelled frame: alt [cond], opt, loopIf/else branches, an optional part, a repeated part

How the diagram is used in a real LLD round
A typical 45-minute round spends minutes 5 to 15 on the class diagram, and the interviewer's follow-ups are almost always about it: “where would you add a new payment method?” (point at the interface), “who deletes a booking's seat holds?” (point at the composition diamond), “what happens when two requests hit this at once?” (walk a sequence diagram). A small, correct diagram turns each follow-up into pointing and a sentence. Common mistakes

    
    
      
  • Diamond on the wrong end. It goes on the whole (Order), not the part (LineItem).
    • 
      
  • Triangle pointing the wrong way. The hollow triangle points at the parent or interface: “this is a kind of that”.
    • 
      
  • Solid line with a triangle for an interface. Implementing an interface is a dashed line with a hollow triangle.
    • 
      
  • Drawing a field as a dependency. A field is association or stronger; dependency is for parameters and locals.
    • 
      
  • Listing every getter and setter. They hide the methods that matter. Show the operations that carry the design.
    • 
      
  • Twenty boxes. Draw the core six to eight, and add detail only where the interviewer asks.

Interview drill

    
Explain it simply: What's the difference between aggregation and composition, and how would each look in Java?

    
How a strong answer sounds
Both are whole-part relationships held in a field. With composition the whole owns the parts' lifecycle: it creates them, doesn't share them, and they go away with it, like a connection pool and its pooled connections, or an order and its line items. With aggregation the parts exist independently and can belong to several wholes, like engineers in an on-call rotation. In Java the difference shows up in who calls new and whether references to the parts ever leave the class. Composition is a filled diamond on the whole; aggregation a hollow one.

    
Deeper: You've drawn PaymentService → PaymentGateway with StripeGateway and AdyenGateway under it. The interviewer asks how you'd add PayPal. Answer by pointing at the diagram.

    
How a strong answer sounds
PaymentGateway is an interface, drawn with «interface», and the two gateways realize it with dashed lines and hollow triangles. Adding PayPal is one new box, PayPalGateway, with the same dashed arrow to the interface. PaymentService has an association to the interface only, so it doesn't change. The only other edit is wherever gateways are created and chosen, ideally one factory, which I'd point to as well.

  


  

    
🧠 Key takeaways

    
    
      
  • Class boxes: name, fields, methods; + − # ~ for visibility; types after a colon; underline for static, italic for abstract, «interface» for interfaces.
    • 
      
  • Dependency (dashed, open arrow) is a parameter or local; association (solid) is a field.
    • 
      
  • Aggregation (hollow diamond) and composition (filled diamond) sit on the whole; composition means the whole owns the parts' lifecycle.
    • 
      
  • Inheritance is a solid line, realization a dashed line, both with a hollow triangle pointing at the parent or interface.
    • 
      
  • Multiplicities (1, 0..1, *, 1..*) sit at the far end and map to a field, an Optional or a collection.
    • 
      
  • Sequence diagrams: lifelines, solid calls, dashed returns, self-calls and alt/opt/loop frames. Keep both diagrams small and precise.

The filled diamond on Order means composition: Order is the whole and owns the parts' lifecycle. 1..* at the LineItem end means each order has one or more of them.

    


    

      
In a class box, what does - tokens: int mean?

      

        
        
        
        
      

      
The minus sign is private visibility, and UML writes the type after a colon: private int tokens;.

Using a type only as a parameter, local variable or return type is a dependency. Association needs a field that keeps a reference to it.
