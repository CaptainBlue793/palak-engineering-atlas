Composition over Inheritance

“Favour composition over inheritance” is the most repeated line in object-oriented design, and one of the least explained. This chapter shows what goes wrong when inheritance is used to combine features, what composition looks like in real Java, and the specific cases where inheritance is still the right tool.

  • Recognise a subclass explosion, and count what it will cost
  • Build behaviour by wrapping and delegating to objects behind an interface
  • Fix a fragile subclass with a forwarding class
  • Apply the “is-a” substitution test, and spot the two famous JDK mistakes that fail it
  • Say when inheritance is still the right choice

The subclass explosion

A notification service sends messages over email and SMS. Then product asks for retries on flaky gateways, then rate limiting so a bug can't text a user 500 times, then an audit log for compliance. Each feature is optional per channel. If each variation is a subclass, you need a class for every combination: RetryingSmsNotifier, RateLimitedRetryingSmsNotifier, AuditedRateLimitedRetryingEmailNotifier…

The count is channels × 2features, because each feature is independently on or off. Two channels and three features is 2 × 8 = 16 classes. Add a Slack channel and a metrics feature and it's 3 × 16 = 48. Each new feature doubles the total. The classes also repeat the same retry loop and the same audit call in dozens of places, and Java allows only one superclass, so you can't mix “retrying” and “audited” in from two parents anyway.

Composition builds the same behaviour from objects instead of classes. Each feature is one class that wraps another Notifier and adds one thing. You combine them when the program starts, in any order and any combination:

One interface, one class per channel, one class per feature
public interface Notifier { void send(Message m); }

public final class SmsNotifier implements Notifier { /* calls the SMS gateway's HTTP API */ }

public final class RetryingNotifier implements Notifier {
	private final Notifier inner;                 // has-a Notifier
	private final RetryPolicy policy;

	public RetryingNotifier(Notifier inner, RetryPolicy policy) {
		this.inner = Objects.requireNonNull(inner);
		this.policy = Objects.requireNonNull(policy);
	}

	@Override public void send(Message m) {
		for (int attempt = 1; ; attempt++) {
			try { inner.send(m); return; }         // delegate the real work
			catch (RuntimeException e) {
				if (!policy.shouldRetry(attempt, e)) throw e;
			}
		}
	}
}

// Wiring, once, at startup: audited → retrying → SMS
Notifier sms = new AuditedNotifier(new RetryingNotifier(new SmsNotifier(gateway), ioThrice), auditLog);
Reading it: RetryingNotifier doesn't know or care what it wraps: an SMS sender, an email sender, or another wrapper. Retries are written once, for every channel. The count is now channels + features: 2 + 3 = 5 classes instead of 16. (A real retry loop also waits between attempts; Chapter 25 adds backoff.)

Delegation by hand: fixing the fragile subclass

  
The InstrumentedHashSet from P3 counted every element twice, because HashSet.addAll calls the overridden add. The composition fix is to stop being a HashSet and hold one instead. Effective Java splits it into two classes, and the first one is reusable for any wrapper you'll ever need around a Set:


// 1. Implements Set by passing every call to a Set it holds. Written once.
public class ForwardingSet<E> implements Set<E> {
	private final Set<E> s;
	public ForwardingSet(Set<E> s) { this.s = Objects.requireNonNull(s); }
	public boolean add(E e) { return s.add(e); }
	public boolean addAll(Collection<? extends E> c) { return s.addAll(c); }
	public boolean contains(Object o) { return s.contains(o); }
	public int size() { return s.size(); }
	// ... the other Set methods, each one line ...
}

// 2. The actual feature: small, and independent of how the inner set works.
public final class CountingSet<E> extends ForwardingSet<E> {
	private int addCount = 0;
	public CountingSet(Set<E> s) { super(s); }
	@Override public boolean add(E e) { addCount++; return super.add(e); }
	@Override public boolean addAll(Collection<? extends E> c) { addCount += c.size(); return super.addAll(c); }
	public int addCount() { return addCount; }
}

Set<String> tags = new CountingSet<>(new HashSet<>());   // or a TreeSet, or a concurrent set

  
  
Yes, CountingSet still uses extends, but on a class built for it: ForwardingSet has no hidden self-use, since every method is a plain one-line forward. The wrapper also works with any Set implementation, which the subclass of HashSet never could.

That last row is composition's one real catch, sometimes called the self problem. If the inner object calls one of its own methods, or registers this as a callback somewhere, the call goes to the inner object directly and skips every wrapper. It's usually harmless, but it's why a wrapper can't reliably intercept everything.


  
Is-a vs has-a: the substitution test

  
Before writing class B extends A, ask one question: can a B be used everywhere an A is expected, with every A operation still making sense? If yes, B really is an A. If some inherited operations would be wrong for a B, B only has or uses an A, and should hold one. Chapter 4 turns this into the Liskov substitution principle; for now, two famous classes in the JDK itself show what failing it looks like.

  
    
    
  • java.util.Stack extends Vector. A stack should allow push, pop and peek. Because it inherits from Vector, every Stack also has add(index, e), remove(index) and get(index), so any caller can insert into the middle and break last-in-first-out. The JDK's own documentation now recommends Deque<E> stack = new ArrayDeque<>() instead.
    • 
    
  • java.util.Properties extends Hashtable<Object, Object>. Properties are supposed to be string keys and string values. But the inherited put accepts any object, so props.put("timeout", 30) compiles, and then getProperty("timeout") returns null, because getProperty only returns values that are strings.
    • 
  

  
Both classes date from Java 1.0, and both can't be fixed now without breaking existing code, which is the other lesson: a public inheritance relationship is permanent.


  

    
🧠

    
java.io: a whole library built by composition
Reading a gzipped UTF-8 log file line by line is new BufferedReader(new InputStreamReader(new GZIPInputStream(new FileInputStream(path)), UTF_8)). Four small classes, each adding one thing: bytes from a file, decompression, bytes to characters, buffering and readLine. The library has no BufferedGzipUtf8FileReader class, and doesn't need one. Swap FileInputStream for a socket's input stream and the same three wrappers read a compressed network stream. Chapter 13 names this the Decorator pattern.

  


  
When inheritance is still right

  
“Favour” composition doesn't mean “never inherit”. Inheritance is the right tool in a few specific cases:

  
    
    
  • A genuine subtype that passes the substitution test, where the parent was designed and documented for extension. Framework base classes like HttpServlet or JUnit's extension points are built this way on purpose.
    • 
    
  • A fixed algorithm with a few open steps, the skeleton from P4's JsonHandler, with the skeleton method made final. Chapter 19 calls this Template Method.
    • 
    
  • A closed set of variants you own. A sealed interface lists exactly which classes may implement it, so the hierarchy can't grow behind your back: sealed interface Command permits Get, Set, Delete {} for a key-value store's protocol. The compiler can then check that a switch handles every case.
    • 
    
  • Inside one package or module you control, where parent and subclasses change together and nobody outside can subclass.
    • 
  

  

  
⚠️
Common mistakes

    
    
      
  • Extending a class just to reuse a few of its methods. You inherit all of them, including ones that break your class's rules. Hold an instance and call what you need.
    • 
      
  • Modelling optional features as subclasses. Features that combine turn into 2n classes. Make each feature a wrapper.
    • 
      
  • Extending JDK collections (HashMap, ArrayList) to add behaviour. Their internal self-calls aren't part of their contract. Wrap them.
    • 
      
  • Wrappers that don't implement the interface. If RetryingNotifier isn't a Notifier, you can't stack it or pass it where a notifier is expected.
    • 
      
  • Forgetting to forward a method in a hand-written wrapper, so it silently does nothing. Write the forwarding class once and extend that.
    • 
      
  • Treating “composition” as a ban on extends. Sealed hierarchies and designed-for-extension skeletons are good inheritance.
    • 
    


  
🎤
Interview drill

    
Explain it simply: Why do people say to favour composition over inheritance?

    
How a strong answer sounds
Inheritance couples a subclass to its parent's internals, including which methods call which, so the subclass can break when the parent changes. It's also fixed at compile time and you get one parent, so optional features that combine turn into a class per combination. Composition holds an object behind an interface and delegates to it: each feature is one small wrapper, you combine them at run time, and you only depend on the public interface. I still use inheritance for true subtypes, sealed hierarchies and deliberate template skeletons.

    
Deeper: Notifications have 3 channels and 4 optional features that can combine freely. How many classes would each approach need, and what does the composed version look like?

    
How a strong answer sounds
Subclassing every combination needs 3 × 2⁴ = 48 classes, and each new feature doubles that. Composition needs 3 + 4 = 7: a Notifier interface, one class per channel, and one wrapper per feature that implements Notifier and holds the Notifier it wraps. At startup I'd wire each channel with the features it needs, like new Audited(new RateLimited(new Retrying(new Sms(gateway), policy), limiter), log), ideally in one factory, so the order of wrappers is decided in one place.

  


  

    
🧠 Key takeaways

    
    
      
  • Features as subclasses cost channels × 2features classes; features as wrappers cost channels + features.
    • 
      
  • Composition: implement the interface, hold the thing you wrap, add one behaviour, delegate the rest.
    • 
      
  • A forwarding class fixes the fragile subclass: the inner object's self-calls never reach your overrides.
    • 
      
  • The substitution test: B extends A only if every A operation is right for a B. Stack and Properties fail it.
    • 
      
  • Composition's catch: calls the inner object makes to itself bypass the wrappers.
    • 
      
  • Inheritance is right for true subtypes, sealed closed hierarchies and deliberate template skeletons.
    • 
    

  


  

    
Check your understanding

    


    

      
A payment client supports 4 gateways and 3 optional features (retries, circuit breaker, metrics) that can be combined freely. How many classes does one-subclass-per-combination need, compared with composition?

      

        
        
        
        
      

      
Each feature is on or off independently: 2³ = 8 combinations per gateway, times 4 gateways = 32 subclasses. Composition needs one class per gateway and one wrapper per feature: 4 + 3 = 7.

    


    

      
CountingSet extends ForwardingSet and wraps a HashSet. Why does addAll of 3 elements now count 3 instead of 6?

      

        
        
        
        
      

      
The inner set is a separate object that doesn't know it's wrapped, so its self-calls go to its own methods. CountingSet counts only in its own add and addAll, which callers invoke directly.

    


    

      
What is wrong with java.util.Stack extends Vector?

      

        
        
        
        
      

      
It fails the substitution test in reverse: Vector's operations don't all make sense for a stack, but Stack exposes them anyway. Holding a list internally, as ArrayDeque does for the Deque interface, would have kept the operations to push, pop and peek.

    


    

      
Which is a good use of inheritance?

      

        
        
        
        
      

      
A sealed hierarchy is closed, owned by you, and each variant truly is a Command. The others extend a class not designed for it, encode feature combinations as classes, or inherit a whole API to reuse one method.

    


    

      
What is a genuine downside of composition?

      

        
        
        
        
      

      
Forwarding every method takes code (write a forwarding class once to contain it), and the inner object's calls to this bypass any wrapper. The other options describe inheritance's problems, or aren't true.
