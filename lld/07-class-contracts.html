Class APIs & Contracts

A class's public methods are a promise to every caller, now and in the future. Good ones say exactly what they need, what they guarantee and how they fail, and they make wrong calls fail to compile. Bad ones accept anything and leave callers to guess: whether 30 means seconds or milliseconds, which string is the currency, what true, false switches on. This chapter is about writing the first kind.

  • State a method's contract: preconditions, postconditions and failure modes
  • Validate at public boundaries, then trust the data inside
  • Design signatures that are hard to misuse, using types instead of raw strings, ints and booleans
  • Apply command-query separation, and know when an atomic “command that answers” is the right call
  • Choose parameter and return types: accept general, return specific, never return null collections

A method is a contract

Bertrand Meyer's design by contract describes every method with three parts. Preconditions are what the caller must guarantee before calling. Postconditions are what the method guarantees afterwards, if the preconditions held. Invariants are what's true of the object before and after every call (P2). Add the ways it can fail, and you have the whole contract. Write it where callers read it, in the Javadoc:

/**
 * Holds seats for a customer while they pay.
 *
 * Pre:  seats is non-empty and every seat belongs to this show; ttl is between 1 and 15 minutes.
 * Post: on success, every seat is held by holder until now + ttl, and no one else can hold or book them.
 *       On failure, no seat has changed state (all or nothing).
 * @return the hold, whose id is needed to confirm or release it
 * @throws SeatUnavailableException if any seat is already held or booked (nothing is held)
 * @throws IllegalArgumentException if a precondition is broken
 */
public SeatHold hold(Set<SeatId> seats, CustomerId holder, Duration ttl)

Look at what that contract lets a caller rely on. It says “all or nothing”, so the caller never has to clean up half a hold. It says which failure is expected (SeatUnavailableException, show the user other seats) and which is a bug (IllegalArgumentException, fix the caller). And the signature itself already encodes most of the preconditions: a Set can't contain a seat twice, and SeatId, CustomerId and Duration can't be confused with one another.

Validate at the boundary, trust inside

Where should arguments be checked? At the boundary: every public constructor and public method, where data enters from code you don't control. Check once there, fail fast with a message naming the bad value, and then trust it everywhere inside. Private helpers don't re-check what their public caller already verified; re-validating everywhere clutters the code and makes it unclear which check is the real one.

public SeatHold hold(Set<SeatId> seats, CustomerId holder, Duration ttl) {
	Objects.requireNonNull(holder, "holder");
	if (seats.isEmpty()) throw new IllegalArgumentException("no seats");
	if (ttl.compareTo(MIN_HOLD) < 0 || ttl.compareTo(MAX_HOLD) > 0) throw new IllegalArgumentException("ttl out of range: " + ttl);
	if (!layout.containsAll(seats)) throw new IllegalArgumentException("unknown seats: " + unknown(seats));
	return holdValidated(Set.copyOf(seats), holder, ttl);          // private: no re-checks inside
}

Value objects move validation even earlier. If EmailAddress's constructor rejects malformed addresses, then every method that takes an EmailAddress has that precondition for free. That's why the course keeps turning validated strings into small types: the check happens once, at construction, instead of in every method that might receive one.

Signatures that are hard to misuse

The best check is one that happens at compile time. A signature built from raw ints, Strings and booleans lets callers swap, mis-scale and mistype arguments, and the compiler can't help. Command-query separation

  
Bertrand Meyer's other rule: a method should either be a command, which changes state and returns nothing, or a query, which returns something and changes nothing. Never both. The payoff is that queries are safe to call anywhere: in a log line, in a debugger, in an assertion, twice in a row. A query that secretly changes state turns every one of those into a bug.


// A query with a side effect: every call to "look" at the balance charges a fee
public Money getBalance() { balance = balance.minus(INQUIRY_FEE); return balance; }

// Separated: reading is free and repeatable; charging is an explicit command
public Money balance() { return balance; }
public void chargeInquiryFee() { balance = balance.minus(INQUIRY_FEE); }

  
There's one important exception, and it shows up constantly in LLD. When several threads share an object, splitting “check” from “act” creates a race: two threads both see the last seat as free, then both hold it. Operations that must be atomic therefore combine the command with its answer: tryAcquire() returns whether it got a token, Map.putIfAbsent returns what was there, Queue.poll removes and returns. That breaks the letter of CQS on purpose. The rule of thumb: separate commands and queries by default; merge them when the check and the change must happen as one step.

  

  
Parameter and return types

  
A few more rules keep APIs easy to call and hard to break:

  
    
    
  • Accept the most general type you need; return the most specific useful one. Take Collection<SeatId> or Set<SeatId>, not HashSet<SeatId>; return List<Booking>, not Collection, if order matters to callers.
    • 
    
  • Never return null for a collection. Return an empty one, so callers can always loop.
    • 
    
  • Return Optional for “may not exist”, and throw for “couldn't do its job” (P7).
    • 
    
  • Keep parameter lists short. Past three or four parameters, especially of the same type, group them into a record (a “parameter object”) or use a builder (Chapter 11).
    • 
    
  • Don't return mutable internals. Copies or unmodifiable views only (P2).
    •

The date API everyone got wrong
The old java.util.Date(int year, int month, int day) constructor counts years from 1900 and months from zero. So new Date(2026, 9, 30) is 30 October in the year 3926. It compiled, it ran, and it produced wrong dates in real systems for years, because three ints in a row carry no meaning of their own. Its replacement, java.time, fixed it with types: LocalDate.of(2026, Month.OCTOBER, 30). Month is an enum, so a zero-based slip can't compile. When your own API takes several plain numbers in a row, you're building the same trap.

  


  
⚠️
Common mistakes

    
    
      
  • Units in the caller's head: int timeout, long amount. Use Duration and Money.
    • 
      
  • Several String or long parameters in a row. Callers will swap them. Use id types or a parameter object.
    • 
      
  • Boolean flags. true, false means nothing at the call site. Use enums or separate methods.
    • 
      
  • Validating deep inside instead of at the boundary, so the error surfaces far from the bad call.
    • 
      
  • Queries with side effects. A getter that increments, charges or caches wrongly breaks every log line that calls it.
    • 
      
  • Separate check and act on shared state. Offer one atomic method that returns whether it worked.
    •

Interview drill

    
Explain it simply: What makes a method signature “hard to misuse”?

    
How a strong answer sounds
The types carry the meaning, so a wrong call doesn't compile. Durations are Duration, amounts are Money, ids have their own types so they can't be swapped, options are enums instead of booleans, and long parameter lists become a record or a builder with named steps. Then I validate at the boundary, fail fast with a clear message, and document the contract: what the method needs, what it guarantees, and which exceptions mean an expected failure versus a caller bug.

    
Deeper: Command-query separation says don't return values from commands. Why do tryAcquire and putIfAbsent break that rule, and is that OK?

    
How a strong answer sounds
They exist for shared, concurrent state. If a caller first asks “is it free?” and then says “take it”, another thread can act in between, so both callers succeed. Combining the check and the change into one atomic operation that reports whether it worked closes that gap. So I separate commands and queries by default, because it makes queries safe to call anywhere, and deliberately merge them where the check and the action must happen as one step.

  


  

    
🧠 Key takeaways

    
    
      
  • A method's contract: preconditions, postconditions, invariants and failure modes. Write it in the Javadoc.
    • 
      
  • Validate at public boundaries once, fail fast with a clear message, and trust the data inside.
    • 
      
  • Hard-to-misuse signatures use types for meaning: Duration, Money, id types, enums, parameter objects and builders.
    • 
      
  • Command-query separation: commands change state, queries return data; neither does both.
    • 
      
  • Exception: atomic check-and-act on shared state returns whether it worked (tryAcquire, putIfAbsent).
    • 
      
  • Accept general types, return specific ones; empty collections, never null; Optional for absence.
    • 
    

  


  

    
Check your understanding

    


    

      
Where should a class validate its arguments?

      

        
        
        
        
      

      
The boundary is where untrusted data arrives. Checking there once, and failing fast, gives clear errors near the bad call without cluttering every internal method.

    


    

      
What's the best replacement for void setTimeout(int timeout)?

      

        
        
        
        
      

      
Duration carries its unit, so Duration.ofSeconds(30) and Duration.ofMillis(30) can't be confused. The other options keep the unit in the caller's head or add a flag.

    


    

      
Which method breaks command-query separation in a harmful way?

      

        
        
        
        
      

      
A query that changes state makes innocent reads, like a log line or a debugger, charge the customer. tryAcquire merges check and act on purpose, for atomicity on shared state.

    


    

      
charge(long amount, String currency, String customerId) is called as charge(1999, "cus_42", "USD"). What's the best fix?

      

        
        
        
        
      

      
With distinct types the swapped call doesn't compile. Validation would catch this one swap at run time, but not a swap between two valid-looking strings. Comments and names don't reach the call site.

    


    

      
hold(seats, holder, ttl) documents “all or nothing”. What may a caller assume if it throws SeatUnavailableException?

      

        
        
        
        
      

      
The postcondition on failure is part of the contract. “All or nothing” means a failed call left everything as it was, so the caller can simply offer other seats.
