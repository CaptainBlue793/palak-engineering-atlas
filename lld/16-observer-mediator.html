Observer & Mediator

When an order is placed, five things should happen: reserve stock, send a confirmation, record analytics, run a fraud check, award loyalty points. If the order service calls all five, it depends on all five, and every new reaction means editing it. Observer flips that around: the order service announces what happened, and whoever cares subscribes. Mediator handles the related problem of many objects that all need to talk to each other. Both reduce coupling, and both come with sharp edges this chapter covers: failures, slowness, ordering and memory leaks.

  • Implement a subject with subscribe, unsubscribe and notify, or a small event bus
  • Choose between pushing event data and letting listeners pull state
  • Isolate listener failures, and decide between synchronous and asynchronous delivery
  • Prevent the lapsed-listener memory leak
  • Use a Mediator to replace many-to-many references with one coordinator

Observer: announce, don't call

Here's the coupled version. The order service knows every downstream reaction, and its fan-out grows with each feature:

public Order place(Cart cart, Customer c) {
	Order order = createAndCharge(cart, c);
	inventory.reserve(order);        mailer.sendConfirmation(order);
	analytics.trackPurchase(order);  fraud.review(order);   loyalty.award(order);   // and next month, one more…
	return order;
}

In the Observer pattern, a subject keeps a list of observers (listeners) and notifies them when something happens. It knows only that they implement a listener interface. In modern Java, the usual form is a small event bus: events are immutable records, and listeners subscribe by event type.

A minimal, safe in-process event bus
public record OrderPlaced(OrderId id, CustomerId customer, Money total, Instant at) {}   // the event: immutable

public final class EventBus {
	private final Map<Class<?>, List<Consumer<Object>>> listeners = new ConcurrentHashMap<>();
	private final ErrorLog errors;

	public <E> Subscription subscribe(Class<E> type, Consumer<? super E> listener) {
		Consumer<Object> wrapped = e -> listener.accept(type.cast(e));
		listeners.computeIfAbsent(type, k -> new CopyOnWriteArrayList<>()).add(wrapped);   // safe to iterate while others subscribe
		return () -> listeners.get(type).remove(wrapped);                            // Subscription extends AutoCloseable
	}

	public void publish(Object event) {
		for (Consumer<Object> l : listeners.getOrDefault(event.getClass(), List.of())) {
			try { l.accept(event); }
			catch (RuntimeException e) { errors.record(event, e); }                           // one bad listener can't stop the rest
		}
	}
}

// The order service now depends on the bus, not on five services
Order order = createAndCharge(cart, c);
bus.publish(new OrderPlaced(order.id(), c.id(), order.total(), clock.instant()));

// Each reaction subscribes itself at startup
bus.subscribe(OrderPlaced.class, inventory::reserveFor);
bus.subscribe(OrderPlaced.class, mailer::sendConfirmation);
Three safety details: CopyOnWriteArrayList, so a listener subscribing or unsubscribing during a publish can't cause a ConcurrentModificationException; a try/catch per listener, so one failure doesn't skip the others or fail the order; and a Subscription handle, so unsubscribing is easy (see the leak section). Adding loyalty points is now a subscription, not an edit to the order service.

Push or pull

A notification can carry the data (push: OrderPlaced(id, customer, total, at)) or just say “something changed” and let listeners ask the subject for what they need (pull: onChanged(order), then order.total()). Push is the modern default for events. The event is an immutable snapshot of what happened, so it can be queued, logged, sent to another process or replayed, and every listener sees the same facts. Pull fits UI-style observers of a live model, like a chart redrawing from a data model, where listeners only care about the current state, not each change.

Sync or async, and when a listener fails

The simple bus above is synchronous: publish runs every listener on the caller's thread before returning. That's easy to reason about, but a slow listener makes checkout slow, and a listener that throws, if not caught, fails the order. An asynchronous bus hands each event to a thread pool and returns immediately. Checkout is fast, but listener failures no longer reach the publisher, and events in memory are lost if the process dies before they're handled. Compare them:

Two more rules for synchronous listeners. Don't rely on ordering: if fraud review must run before the confirmation email, that's a workflow step, not two independent listeners. And be careful with re-entrancy: a listener that publishes another event runs that event's listeners in the middle of the first publish, which is fine when it's intended and confusing when it's not. For events that must not be lost, the usual production answer is to write the event to the database in the same transaction as the order (an “outbox” table) and have a separate process deliver it (Chapter 26).

The lapsed-listener leak

A subject holds a reference to every listener. From P1: an object stays alive while something reachable points at it. So a listener that subscribes and never unsubscribes lives as long as the subject does, and so does everything the listener references. A long-lived event bus plus short-lived subscribers, like a dashboard widget that subscribes each time it opens, is a slow leak. It's common enough to have a name: the lapsed listener problem.

Lapsed listeners: open and close a widgetInteractive
Each widget holds a 2 MB chart buffer. A closed widget that is still subscribed can never be collected, and it keeps receiving, and processing, every event.

The fix is ownership: whoever subscribes is responsible for unsubscribing, and the API should make that easy. Returning a Subscription that is AutoCloseable lets the owner close it in its own close() method, or use try-with-resources for a scoped subscription. Weak references can hide the problem, but they make listeners disappear at unpredictable moments, so explicit unsubscription is the better default.

Mediator: one coordinator instead of a mesh

Observer is one-to-many: one subject, many independent listeners. Some problems are many-to-many. In a checkout form, choosing “ship to a different address” enables the address fields; choosing a country changes the postcode format and the available shipping methods; choosing express shipping disables cash on delivery. If each widget holds references to the others, ten widgets can mean up to ninety one-way links, and nobody can see the rules in one place. A Mediator is the single object every participant talks to. It knows the rules and tells the others what to do:

public final class CheckoutFormMediator {
	private final Toggle separateShipping; private final AddressFields shippingAddress;
	private final CountryPicker country; private final ShippingMethods methods; private final PaymentMethods payments;

	public void changed(Widget source) {                                  // every widget reports here, and only here
		if (source == separateShipping) shippingAddress.setEnabled(separateShipping.isOn());
		if (source == country) { shippingAddress.usePostcodeFormat(country.selected()); methods.show(methodsFor(country.selected())); }
		if (source == methods) payments.setCashOnDeliveryAllowed(!methods.selected().isExpress());
	}
}

Widgets now know only the mediator, and the form's rules are readable in one method. A chat room is the other classic example: users send messages to the room, and the room decides who receives them, so users never hold references to each other. The risk is the obvious one: a mediator that absorbs every rule in the system becomes a god class (Chapter 3). Keep one mediator per coherent group of collaborators: one form, one room.

Observer across processes

The in-process bus in this chapter is the small version of an architecture you'll meet in the System Design course: services publishing events like OrderPlaced to a message broker such as Kafka, with other services consuming them (SD Chapter 14). The same trade-offs reappear at scale: publishers don't know their consumers, consumers must tolerate failures and duplicates, and ordering is only guaranteed where you ask for it. ⚠️
Common mistakes
  • Not isolating listener failures. One throwing listener skips the rest, or fails the publisher's operation.
  • Slow work in synchronous listeners on a request path. Move it to an async bus or a queue.
  • Forgetting to unsubscribe. The subject keeps listeners, and everything they reference, alive forever.
  • Mutable events. One listener changing the event changes what the others see. Use records.
  • Relying on listener order for correctness. If B must happen after A, make it an explicit step.
  • A mediator for the whole application. One per coherent group, or it becomes the god class it replaced.

Interview drill

Explain it simply: What does the Observer pattern buy you, and what can go wrong with it?

How a strong answer sounds
It decouples the thing that changes from the things that react: the order service publishes OrderPlaced and doesn't know who listens, so new reactions are new subscribers, not edits. What can go wrong: a listener that throws can break the publisher unless each call is isolated; a slow synchronous listener slows everyone; order between listeners isn't guaranteed; async delivery loses events on a crash unless they're persisted; and listeners that never unsubscribe leak memory, because the subject holds references to them.

Deeper: The confirmation email is sent by a synchronous listener, and the email provider is sometimes down for minutes. Orders are failing. What do you change?

How a strong answer sounds
First, isolate listener failures in the bus so an email outage never fails an order; record the failure. Second, make email asynchronous: the listener enqueues a send-confirmation job, and a worker sends it with retries and backoff, so checkout latency no longer depends on the provider. If confirmations must never be lost, write the event or job in the same database transaction as the order and deliver it from there, the outbox pattern. Emails can then arrive late, so they should be idempotent per order id in case of retries.

🧠 Key takeaways

  • Observer: a subject notifies subscribed listeners of changes without knowing who they are; an event bus is the common modern form.
  • Push immutable event records by default; pull suits observers of a live model.
  • Isolate each listener's failures; keep slow work out of synchronous listeners.
  • Async delivery trades feedback and durability for speed; persist events that must not be lost.
  • Subscribers must unsubscribe: return an AutoCloseable subscription to prevent lapsed-listener leaks.
  • Mediator replaces a many-to-many mesh with one coordinator per group, so the rules live in one place.

Check your understanding

What is the main benefit of publishing OrderPlaced instead of calling inventory, mailer and analytics directly?

Observer removes the publisher's knowledge of its dependents. It adds no speed on its own, doesn't guarantee order, and failures still need handling.

In a synchronous bus with no per-listener try/catch, the email listener throws. What happens?

A plain loop stops at the first exception, which travels back to the caller of publish. Catching per listener keeps one failure from affecting the others and the publisher.

What do you give up by switching to an asynchronous in-memory event bus?

Async delivery makes publishing fast, but failures happen later on other threads, and events held only in memory don't survive a crash. Persisting events (an outbox) fixes the second.

Why does a widget that subscribes to a long-lived event bus and never unsubscribes leak memory?

Reachability from a long-lived object keeps the whole chain alive. Unsubscribing removes the reference, making the widget collectable.

How does a Mediator differ from an Observer?

Mediator centralises the logic of how participants affect each other. Observer decouples a subject from independent listeners.
