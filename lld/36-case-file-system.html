Case Study: In-Memory File System

“Design an in-memory file system” sounds like a Composite exercise, and it starts as one: Chapter 14 built the tree. The interview's real content is everything around the tree: turning a string like ../bob/./logs//today into a node, mkdir -p, moving a directory without creating a cycle, per-user permissions checked on every step of a path, and a current directory that belongs to a session rather than to the file system. You can try all of it in a working shell below.

  • Split the design into a shared file system and per-user sessions
  • Model files and directories so rename and move are cheap
  • Parse and resolve paths, including . and .., relative to a working directory
  • Implement mkdir -p, ls, cat, write, rm -r and mv with the right errors
  • Check Unix-style permissions at each step, and know which bit each operation needs

Requirements and API

Clarify: absolute and relative paths; directories and files with byte contents; create, list, read, write and append, delete (recursively on request), move and rename; users with owner-and-others permissions; several users working at once, each with their own current directory. Out of scope: persistence, symbolic links and quotas, which make good follow-ups.

The first design decision is that the current directory isn't part of the file system. Two users can be in different directories at the same time, so the working directory and the acting user live in a Session, like a shell process, and every operation takes one. The file system itself is shared and knows nothing about who is “in” which directory.

public interface FileSystem {
	Session login(User user);                                    // cwd starts at the user's home
	void mkdir(Session s, String path, boolean parents);         // parents = mkdir -p
	List<String> list(Session s, String path);
	byte[] read(Session s, String path);
	void write(Session s, String path, byte[] data, boolean append);
	void remove(Session s, String path, boolean recursive);
	void move(Session s, String from, String to);
	void chmod(Session s, String path, Mode mode);
}
// Errors are specific exceptions: NoSuchFileException, NotADirectoryException, FileExistsException,
// DirectoryNotEmptyException, AccessDeniedException — the messages a shell prints come straight from them.

Composite: files and directories

The tree is the Composite from Chapter 14, with two refinements. First, a node's name lives in its parent's map, not in the node. That makes rename a matter of moving one map entry, and it's how Unix works too: a directory is a table from names to inodes, which is what makes hard links possible. Second, each directory keeps a parent pointer, which gives .. and the cycle check for mv in O(depth). Directory entries sit in a TreeMap, so ls is sorted for free.

abstract sealed class Node permits FileNode, DirNode {
	UserId owner;
	Mode mode;                                              // value object: owner rwx + others rwx
	Instant modified;
}

final class DirNode extends Node {
	final NavigableMap<String, Node> children = new TreeMap<>();   // the names live here
	DirNode parent;                                           // root's parent is itself
}

final class FileNode extends Node {
	private byte[] data = new byte[0];
	byte[] read() { return data.clone(); }                  // never hand out the internal array
	void write(byte[] d, boolean append) { data = append ? concat(data, d) : d.clone(); }
}

record Mode(int bits) {                                    // e.g. 0755
	boolean allows(boolean isOwner, Access a) { int set = isOwner ? (bits >> 6) & 7 : bits & 7; return (set & a.bit) != 0; }
}

Path resolution

Every operation starts by turning a string into a node, so this is the heart of the design. Parse the string once into a Path value object (P6): split on /, drop empty components (so a//b is a/b) and ., and remember whether it was absolute. Then walk it from the root or from the session's working directory, one component at a time, checking the execute (search) permission on every directory you pass through, following .. through the parent pointer, and failing with the precise error.

private Node walk(Session s, Path path) {
	Node cur = path.absolute() ? root : s.cwd();
	for (String part : path.parts()) {
		if (!(cur instanceof DirNode dir)) throw new NotADirectoryException(path);
		check(s, dir, Access.EXECUTE);                        // search permission on every directory passed
		cur = part.equals("..") ? dir.parent : dir.children.get(part);
		if (cur == null) throw new NoSuchFileException(path);
	}
	return cur;
}

record Target(DirNode parent, String name) {}                     // for mkdir, write, rm, mv
private Target target(Session s, Path path) {
	if (path.parts().isEmpty()) throw new IllegalArgumentException("operation needs a name");
	if (!(walk(s, path.parent()) instanceof DirNode dir)) throw new NotADirectoryException(path.parent());
	return new Target(dir, path.last());
}

This resolves .. physically, through the tree. Some shells also normalise it lexically (a/b/.. becomes a as text); the two differ once symbolic links exist, a good point to raise if the interviewer adds links as a follow-up.

Operations: mkdir, ls, cat, rm, mv

With walk and target in place, each operation is a few lines, and most of the work is choosing the right error. mkdir -p walks and creates missing directories, but must fail if a component exists as a file. rm refuses a directory unless recursive, and rm -r has to empty every directory inside it first, so it needs r, w and x on each of them, not just w on the top one's parent. And mv has the one genuinely tricky rule: you can't move a directory into its own subtree, or the subtree detaches into a cycle.

public void mkdir(Session s, String raw, boolean parents) {
	lock.writeLock().lock();
	try {
		Path p = Path.parse(raw);
		if (!parents) { create(s, target(s, p), new DirNode(s.user(), Mode.DIR_DEFAULT)); return; }
		Node cur = p.absolute() ? root : s.cwd();
		for (String part : p.parts()) {
			if (!(cur instanceof DirNode dir)) throw new NotADirectoryException(p);   // "a" exists as a file
			check(s, dir, Access.EXECUTE);
			Node next = part.equals("..") ? dir.parent : dir.children.get(part);
			if (next == null) next = create(s, new Target(dir, part), new DirNode(s.user(), Mode.DIR_DEFAULT));
			cur = next;
		}
	} finally { lock.writeLock().unlock(); }
}

private Node create(Session s, Target t, Node node) {
	check(s, t.parent(), Access.WRITE);                         // creating = changing the parent's table
	if (t.parent().children.putIfAbsent(t.name(), node) != null) throw new FileExistsException(t.name());
	if (node instanceof DirNode d) d.parent = t.parent();
	return node;
}

public void move(Session s, String from, String to) {
	lock.writeLock().lock();
	try {
		Target src = target(s, Path.parse(from));
		Node node = Optional.ofNullable(src.parent().children.get(src.name())).orElseThrow(() -> new NoSuchFileException(from));
		Target dst = destination(s, Path.parse(to), src.name());       // "into dir" or "as new name"
		for (DirNode d = dst.parent(); ; d = d.parent) {               // walk up from the destination
			if (d == node) throw new IllegalArgumentException("cannot move a directory into itself");
			if (d == root) break;
		}
		check(s, src.parent(), Access.WRITE); check(s, dst.parent(), Access.WRITE);
		if (dst.parent().children.containsKey(dst.name())) throw new FileExistsException(to);
		src.parent().children.remove(src.name());
		dst.parent().children.put(dst.name(), node);
		if (node instanceof DirNode d) d.parent = dst.parent();           // O(1): no copying, whatever the subtree size
	} finally { lock.writeLock().unlock(); }
}

Permissions

Unix permission bits mean different things on files and directories, and getting that right is what the interviewer is listening for. On a directory, r lets you list its names, w lets you create, delete and rename entries in it, and x lets you pass through it to reach what's inside. So deleting a file is an operation on its directory: you need w and x on the parent, and nothing at all on the file.

OperationOn every directory in the pathOn the parent directoryOn the node itself
cd dirx–x on dir
ls dirx–r on dir (names); x too to see details
cat filex–r on file
echo > file (exists)x–w on file
touch / mkdir new namexw–
rm file, mvxw (on both parents for mv)nothing
chmodx–be the owner (or root)

Keep the check in one method, check(session, node, access), so root's bypass, owner-vs-others and any later addition (groups, ACLs) change in one place. For concurrency, the simplest correct choice is one ReentrantReadWriteLock for the whole tree: reads (ls, cat, resolution) share it, mutations take it exclusively. Operations like mv touch two directories anywhere in the tree, and a single lock rules out the deadlocks that per-directory locking would have to prevent with a lock order.

🧠
Why anyone can't delete your files in /tmp

Because deletion needs only write permission on the directory, a world-writable directory like /tmp would let any user delete or rename any other user's files there. Unix solves this with one more bit, the sticky bit (shown as t, as in drwxrwxrwt): in a sticky directory, an entry can be deleted or renamed only by its owner, the directory's owner, or root. It's a neat example of a design that put a permission on the wrong object for one use case and fixed it with a targeted extension, and a good follow-up to offer when the interviewer asks about shared directories.

⚠️
Common mistakes
  • Storing the current directory in the file system, so two users share one cwd. It belongs in a session.
  • Storing the name inside the node, making rename and hard links awkward.
  • Splitting paths naively: not handling //, ., .. at the root, or a trailing slash.
  • Checking permissions only on the final node, skipping x on the directories along the way.
  • Requiring write permission on a file to delete it; deletion needs w on the parent.
  • mv without a cycle check, letting a directory move into its own subtree.
  • Returning the internal byte array, letting callers change file contents without a write.

Interview drill

Explain it simply: Walk me through how your file system resolves ../bob/logs.

How a strong answer sounds
First I parse it into a path value: components .., bob, logs, relative. Relative means I start from the session's working directory. For each component the current node must be a directory and the user needs execute permission on it; .. follows the parent pointer, anything else is a lookup in the directory's sorted map of children. Missing names throw no-such-file, a file in the middle throws not-a-directory, a missing x throws access-denied. Every operation uses this same walk.

Deeper: Add symbolic links. What changes?

How a strong answer sounds
A third node type, SymlinkNode, holding a target path string; the sealed hierarchy makes every switch over node types show where it must be handled. During the walk, when a component is a symlink, I resolve its target (relative to the link's directory) and continue from there, except for the final component of operations that act on the link itself, like rm or lstat. Links can form cycles, so I cap the number of links followed per resolution, which is what Unix does with its ELOOP error. And .. semantics now matter: physical resolution follows the real parent of where the link led, lexical normalisation doesn't, so I'd pick physical for the file system API and say so. Permission checks on the target path still apply, since a link grants nothing by itself.

🧠 Key takeaways

  • The file system is shared; the working directory and user live in a per-user session.
  • Names live in the parent's sorted map, and directories keep a parent pointer: rename is O(1), ls is sorted, .. is easy.
  • Parse paths once into a value object, then walk component by component with precise errors.
  • Every directory passed needs x; creating and deleting need w on the parent, not on the file.
  • mkdir -p fails on a file in the way; rm needs -r for directories; mv must reject moving a directory into itself.
  • One read-write lock over the tree is simple and deadlock-free; refine only when it's a measured bottleneck.

Check your understanding

Where should the current working directory be stored?

Different users (and different shells of one user) can be in different directories simultaneously. The file system tree is shared; the cwd is per session.

Bob wants to delete /shared/report.txt. The file is mode 444 (read-only) and owned by alice; /shared is mode 777. Can bob delete it?

Deletion removes an entry from the parent's table, so it needs w (and x) on the parent. The file's own bits don't matter, unless the directory has the sticky bit.

Why store names in the parent's map rather than in each node?

A name is a property of a directory entry, not of the file. That's the Unix directory model: names map to inodes.

What must mv /a /a/b/c do?

Walking up from the destination's parent reaches /a itself, so the move would detach the subtree into a cycle. The check costs O(depth).

What does execute (x) permission mean on a directory?

x is “search” permission. r lists names, w changes entries, x traverses. Path resolution checks x on every directory it passes.
