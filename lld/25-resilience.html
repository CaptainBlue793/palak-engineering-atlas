Resilience at the Class Level

Every remote call eventually fails: a timeout, a 503, a dropped connection, a partner deploying at the worst moment. Resilience is making sure one failing dependency degrades one feature instead of taking the whole service down with it. Four small objects do most of the work: a timeout on every call, a retry policy that doesn't make things worse, a circuit breaker that stops calling something that's down, and idempotency so that retries are safe at all.

  • Put a timeout on every remote call, and size it from a latency budget
  • Retry only safe failures, with exponential backoff and jitter, within a budget
  • Implement a circuit breaker as a closed/open/half-open state machine
  • Isolate dependencies with bulkheads
  • Make retried operations idempotent with idempotency keys

Timeouts: the first line of defence

A call without a timeout can wait forever, and while it waits it holds a thread, a connection, and the user's request. When a dependency hangs rather than fails, every request that touches it piles up until the service runs out of threads, and a problem in one partner becomes an outage of yours. So every remote call gets a timeout, and the value comes from a budget, not a guess: if the page must respond in 800 ms and makes two sequential calls plus 100 ms of its own work, each call gets well under 350 ms. Set both a connect timeout (how long to establish the connection) and a request timeout (how long to wait for the answer).

Retries that don't make things worse

A retry turns a brief glitch into a success. It can also turn a struggling dependency into a dead one: if 1,000 clients each retry three times immediately, the failing service now receives 4,000 requests. Good retry policies follow four rules:

  • Retry only what's safe and might succeed. Timeouts, connection resets, 503 and 429 can be retried; a 400 or a declined card won't change. And only retry operations that are idempotent, or made so with a key (below).
  • Back off exponentially: wait base × 2attempt, so each retry gives the dependency more time to recover.
  • Add jitter. If every client computes the same delay, they all retry at the same moment, and the retries arrive as a synchronised wave. Randomising the delay spreads them out. “Full jitter”, a random delay between 0 and the exponential value, is a widely used choice.
  • Cap it: a maximum number of attempts, a maximum delay, and an overall deadline, so a request never retries past the point where its caller has given up.
RetryPolicy.java: exponential backoff with full jitter
public final class RetryPolicy {
	private final int maxAttempts;                 // e.g. 3
	private final Duration base, cap;              // e.g. 100 ms, 2 s
	private final Predicate<Throwable> retryable;
	private final RandomGenerator random;           // injected: tests use a fixed seed
	private final Sleeper sleeper;                 // injected: tests don't really sleep

	public <T> T call(Callable<T> op) throws Exception {
		for (int attempt = 1; ; attempt++) {
			try { return op.call(); }
			catch (Exception e) {
				if (attempt >= maxAttempts || !retryable.test(e)) throw e;
				long exp = Math.min(cap.toMillis(), base.toMillis() * (1L << (attempt - 1)));
				sleeper.sleep(Duration.ofMillis(random.nextLong(exp + 1)));   // full jitter: 0..exp
			}
		}
	}
}
Design notes: the retryable predicate keeps the “what's safe to retry” decision in one place; random and sleep are injected (Chapter 8) so tests are fast and deterministic; and the delay doubles per attempt up to the cap. With a 100 ms base, attempt 1 waits 0–100 ms, attempt 2 waits 0–200 ms, attempt 3 waits 0–400 ms.

Circuit breakers: stop calling what's down

Retries help with short blips. When a dependency is properly down, even well-behaved retries just spend threads and time waiting for errors, and add load to a service trying to recover. A circuit breaker watches recent failures and, past a threshold, stops calling the dependency for a while, failing immediately instead. It's a state machine (Chapter 18) with three states:

  • Closed: calls go through normally, and failures are counted. Too many failures in a row (or in a window) opens the breaker.
  • Open: calls fail immediately with a “circuit open” error, without touching the network. After a cooldown, the breaker moves to half-open.
  • Half-open: one trial call (a probe) is allowed through. If it succeeds, the breaker closes; if it fails, it opens again for another cooldown.

Thresholds: open after 5 consecutive failures; cooldown of 5 requests' worth of time; one probe in half-open. “Thread time spent waiting” counts the 1-second timeouts that real failing calls cost; fast failures cost almost nothing.
public final class CircuitBreaker {
	private enum State { CLOSED, OPEN, HALF_OPEN }
	private State state = State.CLOSED;
	private int failures;
	private Instant openedAt;
	private final int threshold; private final Duration cooldown; private final Clock clock;

	public synchronized <T> T call(Supplier<T> op) {         // simplified: one lock around the whole call
		if (state == State.OPEN) {
			if (clock.instant().isBefore(openedAt.plus(cooldown))) throw new CircuitOpenException();
			state = State.HALF_OPEN;                                    // cooldown over: allow a probe
		}
		try {
			T result = op.get();
			state = State.CLOSED; failures = 0;                          // success closes it
			return result;
		} catch (RuntimeException e) {
			if (state == State.HALF_OPEN || ++failures >= threshold) { state = State.OPEN; openedAt = clock.instant(); }
			throw e;
		}
	}
}

This teaching version holds its lock for the whole call, which serialises every request through the breaker; a production breaker (like Resilience4j's) only locks the state transitions, counts failures in a sliding window rather than a streak, and lets a limited number of probes through concurrently. The shape is the same, and it slots in as one more decorator around a client (Chapter 13), usually outside the retry layer so an open circuit doesn't retry at all.

Bulkheads: one failure, one compartment

A ship's hull is divided into watertight compartments so one breach doesn't sink it. A bulkhead in software limits how much of your capacity any one dependency can consume. If recommendations and payments share one 200-thread pool and the recommendation service hangs, 200 threads end up waiting on recommendations and payments can't get a thread. Give each dependency its own bounded pool, or a Semaphore with a fixed number of permits, and the hung dependency can only exhaust its own compartment:

private final Semaphore recommendationsBulkhead = new Semaphore(20);

List<Product> recommendations(UserId u) {
	if (!recommendationsBulkhead.tryAcquire()) return List.of();          // compartment full: degrade, don't wait
	try { return client.recommend(u); }
	finally { recommendationsBulkhead.release(); }
}

Idempotency: making retries safe

Retrying a read is harmless. Retrying “charge this card 1,999 cents” is not: if the first attempt actually succeeded and only the response was lost, a retry charges the customer twice. An operation is idempotent if doing it twice has the same effect as doing it once. Reads, puts of absolute values and deletes usually are; “add”, “charge” and “send” are not. The standard fix is an idempotency key: the client generates a unique key per logical operation and sends it with every attempt; the server records the key with the result, and a repeat of the same key returns the stored result instead of doing the work again.

The key must identify the operation, not the attempt: the order id is a good key for “charge this order”, a fresh UUID per retry is useless. The store needs an atomic insert-if-absent on the key (check-then-act from Chapter 22), and entries can expire after a day or two, once no client will retry.

🧠
Payment APIs build this in

Stripe's API accepts an Idempotency-Key header on requests that create or change things: a retried request with the same key returns the original result rather than performing the operation twice, and keys are pruned after about 24 hours. Its official client libraries can retry network failures automatically with backoff, and they attach an idempotency key so those retries are safe. It's this chapter's toolkit shipped as a product feature, because for a payments company a double charge caused by a retry is the worst kind of bug.

⚠️
Common mistakes
  • No timeout, or the library's default of “forever”. Every remote call needs one, from a budget.
  • Retrying everything: 400s, declined cards, validation errors. Retry only transient, safe failures.
  • Immediate or fixed-delay retries. Back off exponentially, with jitter, capped.
  • Retries at every layer. Three layers retrying three times each is 27 calls per request. Retry in one place.
  • Retrying non-idempotent operations without a key. Charges and emails happen twice.
  • One shared pool for every dependency. A single hung partner takes every feature down. Use bulkheads.

Interview drill

Explain it simply: What does a circuit breaker do, and why is it better than just retrying?

How a strong answer sounds
It tracks failures to a dependency. While things are fine it's closed and calls go through. After enough failures it opens and fails calls immediately without touching the network, which saves threads, gives the caller a fast answer to degrade with, and takes load off a service that's trying to recover. After a cooldown it goes half-open and lets a probe through; success closes it, failure reopens it. Retries handle brief blips; a breaker handles sustained outages, and it sits outside the retry layer so an open circuit doesn't retry at all.

Deeper: Your service calls a payment API that sometimes times out. Design the client-side resilience.

How a strong answer sounds
A request timeout from the page's latency budget, plus a connect timeout. A retry policy for timeouts, connection errors, 429 and 503 only: three attempts, exponential backoff with full jitter, capped, within the caller's deadline. Every charge carries an idempotency key derived from the order, so a retry after a lost response returns the original charge instead of charging twice. A circuit breaker outside the retries, so a sustained outage fails fast and checkout can show “try again shortly”. And a bulkhead, a dedicated bounded pool or semaphore for payment calls, so a hung provider can't starve the rest of the service.

🧠 Key takeaways

  • Every remote call needs a connect and a request timeout, derived from a latency budget.
  • Retry only transient, safe failures; back off exponentially with jitter, cap attempts and time, and retry in one layer.
  • A circuit breaker is a state machine: closed counts failures, open fails fast, half-open probes.
  • Bulkheads give each dependency its own bounded pool or semaphore, so one hang can't take everything down.
  • Idempotency keys identify an operation, so a retried charge returns the original result instead of charging twice.
  • These features compose as decorators around a client: breaker outside retry, retry outside the adapter.

Check your understanding

Why add random jitter to retry delays?

Deterministic delays synchronise clients into waves. Randomising spreads retries out over time, giving the dependency a steadier load while it recovers.

A circuit breaker is open. What happens to a new call before the cooldown ends?

Open means fail fast. Only after the cooldown does the breaker move to half-open and let a probe through.

Which error should a retry policy retry?

503 signals a transient problem, and retrying an idempotent request can't cause duplicate effects. The others will fail the same way every time.

What does a bulkhead protect against?

By bounding each dependency's share of capacity (its own pool or semaphore), a failure is contained to the features that use that dependency.

Which idempotency key design is correct for “charge the customer for order 8412”?

The key must be the same for every attempt of one logical operation, so the server can recognise a retry. A fresh UUID per attempt makes every retry look new.
