Composite & Flyweight

Two patterns about structure at scale. Composite is for trees: file systems, UI components, org charts, expression trees. It lets code treat one item and a whole group of items the same way, so “how big is this?” works on a file or a folder of ten thousand files. Flyweight is for huge numbers of small objects that mostly repeat the same data: text styles, map tiles, cached numbers. It shares the repeated part so memory scales with the number of distinct values, not the number of uses.

  • Model a tree with a common interface for leaves and containers
  • Implement recursive operations like size and search, and know their cost
  • Decide where child-management methods belong, and use sealed types for closed trees
  • Split an object's state into shared (intrinsic) and per-use (extrinsic) parts
  • Explain the Integer cache, and why == on boxed numbers fails at 128

Composite: one interface for leaves and groups

A file system has files and directories. Directories contain files and other directories, to any depth. Many operations don't care which is which: “how many bytes?”, “find every .log file”, “delete this”. Composite gives both a common interface; a directory implements each operation by asking its children, which may themselves be directories:

A file-system tree with a sealed interface
public sealed interface Node permits File, Directory {     // the component
	String name();
	long size();
	void collect(Predicate<File> test, List<File> out);
}

public record File(String name, long size) implements Node {  // the leaf
	public void collect(Predicate<File> test, List<File> out) { if (test.test(this)) out.add(this); }
}

public final class Directory implements Node {             // the composite
	private final String name;
	private final Map<String, Node> children = new TreeMap<>();   // by name, sorted, unique

	public Directory(String name) { this.name = name; }
	public String name() { return name; }
	public void add(Node child) {                               // only directories manage children
		if (children.putIfAbsent(child.name(), child) != null) throw new IllegalArgumentException("exists: " + child.name());
	}
	public long size() {                                        // same question, answered by asking the children
		long total = 0;
		for (Node child : children.values()) total += child.size();
		return total;
	}
	public void collect(Predicate<File> test, List<File> out) { children.values().forEach(c -> c.collect(test, out)); }
}

List<File> logs = new ArrayList<>();
root.collect(f -> f.name().endsWith(".log"), logs);                // works on a file or a whole tree
Reading it: callers hold a Node and never check whether it's a file or a directory. The recursion lives in Directory: its size() is the sum of its children's size(), however deep the tree goes. The sealed interface says these are the only two kinds of node, which the compiler can check (more below).

Click any file or folder to select it. size() visits every node under the selection exactly once, so it costs O(n) in the number of nodes below it. Real file managers cache directory sizes and update them on change for exactly that reason.

Where do child-management methods go?

The Gang of Four describes two variants. In the transparent one, add and remove are on the common interface, so callers can treat everything uniformly, but calling add on a file compiles and then fails at run time. In the safe one, only the composite has them, so misuse can't compile, but callers must know they're holding a directory before adding. Modern Java favours the safe variant, and sealed interfaces make it pleasant: the compiler knows every kind of node, so a switch over a Node can be checked for completeness:

static String describe(Node n) {
	return switch (n) {                                          // exhaustive: no default needed (Java 21)
		case File f      -> f.name() + " (" + f.size() + " B)";
		case Directory d -> d.name() + "/ (" + d.size() + " B total)";
	};
}

That gives you two ways to add an operation to a tree: a method on the interface, implemented in each node class (classic Composite), or a function that switches over the sealed types. The first suits operations that belong to the nodes, like size; the second suits operations that live elsewhere, like rendering or exporting. Chapter 20 compares this with the Visitor pattern.

Composite is everywhere once you look: the DOM (every element is a node with child nodes), Swing and JavaFX containers, JSON values (an object contains values that may be objects), abstract syntax trees in a compiler, and permission groups that contain users and other groups. Flyweight: share what repeats

A code editor's syntax highlighter turns a 50,000-line file into roughly two million tokens, and each token has a style: font, size, colour, bold, italic. If every token held its own style object, that's two million style objects, but a typical theme has about a dozen distinct styles. Flyweight splits an object's state in two:

  • Intrinsic state is the part that repeats and doesn't depend on context: the style itself. It's immutable, and one instance per distinct value is shared by everyone.
  • Extrinsic state is the part that differs per use: the token's position and length. It stays with the user, or is passed in when needed.
public record TokenStyle(String font, int size, int rgb, boolean bold, boolean italic) {}   // intrinsic, immutable

public final class StyleCache {                                      // the flyweight factory
	private final Map<TokenStyle, TokenStyle> pool = new ConcurrentHashMap<>();
	public TokenStyle of(String font, int size, int rgb, boolean bold, boolean italic) {
		TokenStyle s = new TokenStyle(font, size, rgb, bold, italic);
		return pool.computeIfAbsent(s, k -> k);                     // equal styles → one shared instance
	}
}

public record Token(int offset, int length, TokenStyle style) {}     // extrinsic data + a shared reference

The shared part must be immutable. If one token could change its style's colour, every token sharing that object would change too, which is the aliasing bug from P1, now across two million objects. Records and a pool keyed on equals make that easy. The saving is the size of a style object times the number of tokens, minus a small table of distinct styles. Try your own numbers:

32 bytes is what TokenStyle takes on a 64-bit JVM: a 12-byte header, a 4-byte reference, two ints and two booleans, rounded up to a multiple of 8 (P1). References are 4 bytes with compressed pointers. The String for the font name is already shared, since string literals are interned.

Flyweights in the JDK, and the == trap

You use flyweights without noticing. Integer.valueOf(n) returns a cached, shared Integer for values from −128 to 127, and autoboxing calls valueOf. String literals are interned: every "GET" in your program is one object. Boolean.TRUE, enum constants and BigDecimal.ZERO are all shared instances. The catch is the one comparison that notices:

Integer a = 127, b = 127;
a == b;        // true: both are the cached instance
Integer c = 128, d = 128;
c == d;        // false (by default): two separate objects
c.equals(d);   // true: always compare boxed values with equals
🧠
The order-status bug that only appeared in production

A service compared two Integer status codes with ==. Every test used small codes like 1, 2 and 3, all inside the cache, so the comparison always worked. In production a new code, 200, was introduced, and the check started failing for no visible reason: 200 == 200 was false, because each boxed 200 was a separate object. Nothing about the design was wrong except relying on a flyweight's identity. Compare boxed numbers with equals, use primitives where you can, and make status codes an enum (P6) so == is correct by construction.

⚠️
Common mistakes
  • Checking the node type in callers: if (n instanceof Directory) scattered everywhere. Put the operation on the interface, or switch over a sealed type in one place.
  • add() on the leaf interface that throws at run time. Keep child management on the composite.
  • Cycles in a tree (a directory containing its own ancestor), which make recursive operations loop forever. Validate on add.
  • Recomputing expensive aggregates on every call for huge trees. Cache and invalidate on change when it matters.
  • Mutable flyweights. Shared state must be immutable, or one user's change leaks to every other.
  • Comparing boxed numbers or strings with ==. It works only while you happen to hit a shared instance.

Interview drill

Explain it simply: What problem does Composite solve, and what does the code look like?

How a strong answer sounds
It lets code treat a single item and a group of items the same way, for tree structures like file systems or UI components. There's a common interface, say Node with size(); a leaf, File, answers directly; a composite, Directory, holds children and answers by asking each child and combining the results. I'd keep add and remove on the composite only, and in modern Java make the interface sealed so a switch over nodes is checked for completeness.

Deeper: A map service renders tiles, each with a terrain type that has a texture, colour palette and elevation shading rules. There are 50 million tiles and 20 terrain types. How do you keep memory down?

How a strong answer sounds
Flyweight. The terrain type's texture, palette and shading rules are intrinsic: immutable and identical for every tile of that type, so I'd create one TerrainType object per type from a factory that returns shared instances. Each tile keeps only its extrinsic state, its coordinates and a reference to its terrain type, or even just a one-byte type index into an array. That's 20 heavy objects instead of 50 million, plus a small per-tile record. The shared objects must be immutable so tiles can't affect each other.

🧠 Key takeaways

  • Composite: a common interface for leaves and containers; containers implement operations by delegating to their children.
  • Recursive operations visit each node once: O(n) in the subtree. Cache aggregates for large trees if needed.
  • Keep child management on the composite, and use a sealed interface for a closed set of node types.
  • Flyweight: share immutable intrinsic state from a factory; keep extrinsic state per use.
  • Memory then scales with the number of distinct values, not the number of objects.
  • The JDK caches Integers from −128 to 127 and interns string literals: compare boxed values with equals.

Check your understanding

What is the core idea of Composite?

Composite is about uniform treatment of trees. Sharing state is Flyweight, families are Abstract Factory, and wrapping to add behaviour is Decorator.

How does Directory.size() compute its answer?

The composite answers by delegating the same question to its children and combining the answers. That recursion reaches every file in the subtree, however deep.

Why keep add(Node) on Directory rather than on the Node interface?

The “safe” composite trades a little uniformity for compile-time correctness: only containers can have children, so only containers offer add.

In the syntax-highlighter flyweight, which state is intrinsic?

Intrinsic state is shared and context-free, so one instance serves every token with that style. Offset and length differ per token: extrinsic.

With default JVM settings, what do Integer a = 200, b = 200; a == b and a.equals(b) return?

Autoboxing uses Integer.valueOf, which shares instances only within the cache range. == compares references, equals compares values.
