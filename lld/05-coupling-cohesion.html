Coupling, Cohesion & the Law of Demeter

Every design review eventually asks two questions. If I change this class, how many others break? And does everything inside this class belong together? The first is coupling, the second is cohesion, and nearly every principle in this course is a way to lower the first and raise the second. This chapter makes both measurable, and covers the slogans that come with them, DRY, KISS and YAGNI, including when to ignore them.

  • Name the kinds of coupling, from harmless to dangerous, and spot each in code
  • Judge a class's cohesion from how its methods use its fields
  • Apply the Law of Demeter to replace train-wreck call chains
  • Use fan-in and fan-out to see which classes are expensive to change
  • Tell real duplication of knowledge from code that only looks the same

Coupling: how much a class must know

Coupling is how much one class depends on the details of another. Some coupling is unavoidable; a checkout that knows nothing about carts can't check anything out. What matters is how much it knows and what kind of thing it knows. Each dependency is a path along which a change can travel. The kinds below run from loosest to tightest:

KindWhat it looks likeWhy it hurts
Datafee(Duration parked): passes just the values neededIt barely does. This is the goal.
Stampfee(Ticket ticket), then reads only ticket.entryTime()Depends on a whole type to use one field; harder to test and reuse
Controlexport(report, true, false): flags choose the behaviourThe caller must know the callee's internal branches; unreadable at call sites
Temporal“Call init() before query(), and close() after”Correctness depends on call order that the types don't enforce
GlobalClasses communicating through a mutable static fieldHidden, shared by every caller and every test (P1)
ContentReaching through other objects' internals: a.getB().getC().setD(x)Any internal change in B or C breaks A

Each has a standard fix. Stamp coupling: pass the value, not the object. Control coupling: split the method in two (exportCsv, exportPdf) or pass a strategy. Temporal coupling: do the setup in the constructor or a factory, so an object can't exist half-initialised. Global coupling: pass the shared object in. Content coupling: the Law of Demeter, below.

Cohesion: what belongs together

Cohesion is how closely the parts of one class belong together. A quick test: look at which fields each method uses. In a highly cohesive class, most methods use most fields; they're all working on the same thing. When the methods split into groups that use separate groups of fields, you have two or three classes sharing a name.

Low cohesion

class UserManager {
	PasswordHasher hasher;  SessionStore sessions;   // used by login()
	SmtpClient smtp;        TemplateEngine templates;// used by sendWelcome()
	ImageResizer resizer;   BlobStore avatars;      // used by uploadAvatar()
}

Three pairs of fields, three unrelated jobs: login, email, avatars.

High cohesion

final class TokenBucket {
	int capacity; int refillPerSecond;
	int tokens;   long lastRefillMillis;
	// tryAcquire() and refill() use all four
}

Every method works with every field, towards one invariant.

High cohesion and low coupling go together. When everything about one concern lives in one class, the other classes only need that class's small public surface, so they're coupled to less.

The Law of Demeter: don't talk to strangers

The Law of Demeter, from a 1987 research project of that name, says a method should only call methods on: itself, its parameters, objects it creates, and its own fields. Not on objects returned by those. Break it and you get a train wreck, a line that navigates the whole object graph:

// CheckoutService, computing tax: knows the shape of four other classes
BigDecimal rate = order.getCustomer().getAddress().getCountry().getTaxRate();

// After: ask the object you have for what you actually need
BigDecimal rate = order.taxRate();
//   Order.taxRate()      → customer.taxRate()
//   Customer.taxRate()   → billingAddress.taxRate()
//   Address.taxRate()    → country.taxRate()

Before, CheckoutService depended on Customer, Address and Country, and would break if a customer gained several addresses. After, each class talks only to its neighbour, and the knowledge that “tax depends on the billing country” lives along the path where it belongs. The fix is tell-don't-ask again, applied across several objects.

Two things are not violations, even though they have dots in a row. Fluent builders and streams (list.stream().filter(…).map(…).toList()) keep calling methods on objects designed to be chained, not reaching into someone's internals. And value objects and data records are meant to be read: request.headers().get("Host") is fine. The law is about not navigating the internals of objects that have behaviour.

Seeing coupling: fan-in and fan-out

Two numbers per class make coupling visible. Fan-out (efferent coupling) counts the classes it depends on: high fan-out means it breaks when many things change. Fan-in (afferent coupling) counts the classes that depend on it directly: high fan-in means changing its API breaks many callers, so it should be stable, ideally an interface. DRY, and the wrong abstraction

DRY (“don't repeat yourself”) is usually quoted as “don't duplicate code”. Its authors, in The Pragmatic Programmer, meant something narrower: every piece of knowledge should have one authoritative representation. The tax rule should exist once. That's different from “no two blocks of code may look alike”.

static final Pattern USERNAME    = Pattern.compile("[a-z0-9_]{3,20}");
static final Pattern COUPON_CODE = Pattern.compile("[a-z0-9_]{3,20}");   // identical today…

Merging those two into one SHORT_ID pattern looks like good hygiene. But they encode two different pieces of knowledge, owned by two different teams. When marketing wants 24-character coupons, the merged pattern either changes usernames too, or sprouts a flag, which is control coupling. Sandi Metz's summary is the rule to remember: duplication is far cheaper than the wrong abstraction. Merge code when it represents the same knowledge and changes for the same reason, not because it happens to look the same today.

KISS and YAGNI in an interview

KISS (keep it simple) and YAGNI (“you aren't gonna need it”) push the other way from open/closed: don't build extension points, configuration or generality nobody has asked for. In an LLD round the balance is explicit. Build extension points where the prompt or the interviewer says things will vary (“pricing changes by season”), keep everything else concrete, and say so: “Vehicle sizes are a fixed enum; I won't add an interface there unless you expect new sizes.” That one sentence shows you know the principle, its cost, and how to choose.

🧠
Temporal coupling in the JDK: SSLContext

To set up TLS by hand in Java you call SSLContext.getInstance("TLS"), and then you must call init(keyManagers, trustManagers, random) before using it. Forget the second call and you get an IllegalStateException saying the context isn't initialised, at run time, possibly far from the setup code. The type system can't help, because the object exists in a half-ready state. Designs you control can avoid this: do all setup in a constructor or a static factory that returns a ready-to-use object (Chapter 11's Builder does this for objects with many options).

⚠️
Common mistakes
  • Boolean flag parameters. send(msg, true, false) is unreadable and couples callers to internal branches. Split the method or pass a small strategy.
  • Train wrecks through behavioural objects. Ask the first object for what you need; let it delegate.
  • Fixing Demeter with getter forwarding. order.getCustomerAddressCountryTaxRate() keeps the same coupling with a longer name. Move the decision, not just the dots.
  • Objects that need an init() call. Finish setup in the constructor or a factory.
  • DRY-ing look-alike code with different owners. Merge only the same knowledge.
  • Unstable classes with high fan-in. If many classes call it, make its API an interface and keep it stable.

Interview drill

Explain it simply: What are coupling and cohesion, and which way do you want each?

How a strong answer sounds
Coupling is how much one class depends on another's details; I want it low, so a change in one class doesn't ripple into others. Cohesion is how closely the parts inside a class belong together; I want it high, so each class has one job and its methods all work on the same fields. They go together: when each concern lives in one cohesive class, other classes only need its small public API.

Deeper: In review you see order.getCustomer().getAddress().getCountry().getTaxRate() inside CheckoutService. What's wrong, and how do you fix it?

How a strong answer sounds
It breaks the Law of Demeter. CheckoutService now depends on the structure of four classes, so if a customer gets separate billing and shipping addresses, checkout breaks even though it has nothing to do with addresses. I'd add order.taxRate() and let each object delegate to its neighbour: order to customer, customer to its billing address, address to country. That puts the rule “tax comes from the billing country” in one place, and checkout depends only on Order. I wouldn't just add a long forwarding getter; the point is moving the decision.

🧠 Key takeaways

  • Coupling is how much one class knows about another; aim for data coupling, and avoid control, temporal, global and content coupling.
  • Cohesion is how well a class's parts belong together: methods that use separate field groups mean separate classes.
  • Law of Demeter: call methods on yourself, your parameters, your fields and what you create; fix train wrecks by moving the decision.
  • Fan-out: how much a class depends on. Fan-in: how many depend on it. High fan-in classes need stable, interface-shaped APIs.
  • DRY is about one home for each piece of knowledge, not about merging code that merely looks alike.
  • KISS and YAGNI: extension points only where variation is stated or expected, and say so out loud.

Check your understanding

What kind of coupling is exporter.export(report, true, false)?

Boolean flags that select behaviour make the caller know about the callee's internal branches. Split the method (exportCsv, exportPdf) or pass a strategy.

Which line breaks the Law of Demeter?

The train wreck navigates the internals of three behavioural objects the service doesn't own. Streams are designed to chain, a field call is allowed, and reading a data record is fine.

A class's methods split into three groups, and each group uses its own two fields and none of the others. What does that say?

Cohesion is about methods and fields working together. Disjoint groups are separate responsibilities, and each group is a candidate class.

Username and coupon-code validation use identical regexes today, owned by different teams. Should you merge them into one shared pattern?

DRY is about one representation per piece of knowledge. These look alike by coincidence; merging them couples two teams' rules, and a flag would add control coupling.

Eleven classes call PaymentGateway directly. What does that high fan-in suggest?

Fan-in counts who depends on you. The more callers, the more a change costs, so high fan-in classes should have narrow, stable, interface-shaped APIs.
