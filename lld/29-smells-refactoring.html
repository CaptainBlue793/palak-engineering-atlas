Code Smells & Refactoring

Most design work isn't greenfield. It's code that grew one reasonable change at a time into a 200-line method with a switch in the middle. A code smell is a surface symptom that usually signals a design problem; refactoring is changing the structure of code without changing its behaviour, in small steps, with tests proving nothing broke. This chapter gives you a catalogue of smells, each paired with the refactoring (and often the pattern) that fixes it, and walks one method from smelly to clean in six safe steps.

  • Recognise the common smells and name the refactoring each one calls for
  • Pin existing behaviour with characterization tests before changing anything
  • Refactor in small steps that each keep the tests green
  • Replace a type-code conditional with polymorphism, and know when not to
  • Introduce parameter objects and value types to cure primitive obsession

A catalogue of smells

The names come mostly from Martin Fowler and Kent Beck's list in Refactoring. A smell isn't a bug and isn't always wrong; it's a prompt to look closer. What makes the catalogue useful is that each smell points at a specific fix:

Two of these deserve a closer look, because they sit behind most of the others. Feature envy is the lack of “tell, don't ask”: code that pulls data out of an object to make a decision the object should make itself.

// Before: the service envies Order's data
if (order.getStatus() == Status.OPEN && order.getLines().size() < 50 && !order.getCustomer().isBlocked()) { … }

// After: move the decision to where the data lives
if (order.canAddLine()) { … }                // Order owns its rule; the service just asks

And primitive obsession is the lack of value objects: when money is a double and a carrier is a String, every method that touches them re-validates, re-rounds and re-compares them, and each copy is a chance to get it slightly different.

Refactoring in small, safe steps

Refactoring only works if behaviour really stays the same, and you can only know that with tests. For code that has none, start with characterization tests (Michael Feathers's term, from Working Effectively with Legacy Code): tests that record what the code does today, right or wrong, so any change in behaviour shows up as a failure. Then change the structure in steps small enough that when a test goes red, the cause is the last thing you did.

Replace conditional with polymorphism

  
A switch on a type code is fine once. It becomes a smell when the same switch appears in several places, quote, estimateDays, labelFormat, because adding a carrier means finding and editing all of them (shotgun surgery), and missing one is a silent bug. The fix moves each branch into a class that implements one interface, so each carrier's behaviour lives in one place and a new carrier is a new class (Strategy). If the branches depend on an object's current state rather than its kind, the destination is the State pattern instead.

  
It isn't always the right move. When the set of kinds is closed and the operations keep growing, Java's sealed interfaces with exhaustive switch expressions are often better: the compiler rejects a switch that misses a case, which removes the “forgot one” risk without scattering each operation across classes (the expression problem from Chapter 20). And a single switch that picks which implementation to create, inside a factory (Chapter 10), is not a smell at all: it's the one place that decision should live.


  
Introduce parameter object

  
When the same group of parameters travels together (weightKg, fromCountry, toCountry), they're a concept that hasn't been named. Bundling them into a record shortens every signature, and more importantly gives behaviour a home: international() used to be recomputed as !from.equals(to) in every branch, and now it's one method.


public record Shipment(Weight weight, CountryCode from, CountryCode to) {
	public Shipment {
		Objects.requireNonNull(weight); Objects.requireNonNull(from); Objects.requireNonNull(to);
	}
	public boolean international() { return !from.equals(to); }
}

  
Once the object exists, follow-up refactorings come naturally: replace double weightKg with a Weight value that rejects negatives, replace country strings with a validated CountryCode. Each one moves validation to a single constructor and deletes checks from everywhere else.

The book's own opening example
The second edition of Martin Fowler's Refactoring (2018, examples in JavaScript) opens with a small program that prints a bill for a theatre company: one long statement function that switches on each play's type, tragedy or comedy, to compute the amount and the loyalty credits. Over the first chapter it's refactored in dozens of tiny steps, each followed by running the tests: extracting functions, splitting the calculation from the formatting so an HTML version becomes easy, and finally replacing the type switch with a calculator class per play type. The lesson Fowler draws is the rhythm, not the end state: small changes, test after each, and the code is never broken for long.

  


  
⚠️
Common mistakes

    
    
      
  • Refactoring without tests, so “no behaviour change” is a hope. Write characterization tests first.
    • 
      
  • Big-bang rewrites mixing many changes: when something breaks, nobody knows which change did it.
    • 
      
  • Mixing refactoring and features in one commit, so reviewers can't tell structure changes from behaviour changes.
    • 
      
  • “Fixing” odd behaviour mid-refactor. Pin it, finish the refactor, then change behaviour deliberately in its own commit.
    • 
      
  • Pattern-itis: replacing a single, stable switch with an interface and five classes. Refactor toward patterns when the smell is real.
    • 
      
  • Chasing every smell. Refactor the code you're about to change; leave stable, rarely-touched code alone.
    •

Interview drill

    
Explain it simply: What is refactoring, and how do you do it safely?

    
How a strong answer sounds
Refactoring is improving the structure of code without changing what it does. Safely means tests first: if there are none, characterization tests that pin current behaviour. Then small steps, like extracting a method, introducing a parameter object or moving a function, running the tests after each and committing when they're green. If a test goes red I revert the step and take a smaller one. Behaviour changes go in separate commits.

    
Deeper: The interviewer shows a 150-line processPayment(String type, …) with a switch over card, wallet and bank transfer, and asks how you'd improve it.

    
How a strong answer sounds
First I'd pin behaviour with tests per payment type, including failure paths. Then name the smells: a long method, a string type code, likely a long parameter list, and probably the same switch elsewhere (refunds, fees). Steps: introduce a parameter object for the payment details; replace the string with an enum parsed at the boundary; extract a method per branch; then introduce a PaymentMethod interface with one implementation per type, selected once by a factory or an EnumMap. Shared steps like validation, fraud check and ledger entry, if they're the same skeleton for every type, could become a template method. Each step is its own green commit, and adding a new method like buy-now-pay-later becomes one new class.

  


  

    
🧠 Key takeaways

    
    
      
  • A smell is a symptom that points to a specific refactoring; it isn't always wrong, but it's worth a look.
    • 
      
  • Refactoring changes structure, never behaviour; tests are what let you know the difference.
    • 
      
  • Pin untested code with characterization tests before changing it.
    • 
      
  • Take small steps, run tests after each, commit on green, revert on red.
    • 
      
  • Replace repeated type switches with polymorphism; for closed sets, sealed types with exhaustive switches also work.
    • 
      
  • Parameter objects and value types cure data clumps and primitive obsession, and give behaviour a home.
    • 
      
  • Keep refactoring commits separate from behaviour changes.

A method in InvoiceService calls six getters on Order to decide whether the order can be discounted. Which smell is this?

      

        
        
        
        
      

      
The method is more interested in Order's data than its own. Moving it to Order puts the rule next to the data it reads.

    


    

      
What is a characterization test?

      

        
        
        
        
      

      
It pins today's behaviour, correct or not, which is exactly what “no behaviour change” needs to be checked against.

    


    

      
During a refactoring step, one characterization test goes red. What should you do?

      

        
        
        
        
      

      
Red means the step changed behaviour. Since the step was small, the cause is obvious. Keep refactoring and behaviour changes apart.

    


    

      
When is a switch on a type NOT a smell?

      

        
        
        
        
      

      
Choosing an implementation has to happen somewhere; one switch in a factory is that place. The smell is the same switch repeated across behaviour.

    


    

      
Three methods all take (double weightKg, String from, String to). What's the refactoring?

      

        
        
        
        
      

      
A data clump is an unnamed concept. Naming it shortens signatures and gives shared logic, like international(), a single home.
