Encapsulation & Invariants

A rate limiter that lets a client set its token count to −3, or an API key whose permissions any caller can quietly add to: both are one missing keyword away. Encapsulation is how a class keeps promises about its own state. That means a promise that holds no matter what the rest of the codebase does. This chapter is about those promises, called invariants, and the few habits that make them impossible to break from outside.

  • Choose the right access level (private, package-private, protected, public) for each member
  • State a class's invariants and enforce them in the constructor and every method
  • Explain why public setters for every field are not encapsulation
  • Use defensive copies so callers can't change your state through a shared collection
  • Replace “ask for the data, decide, then set it” with a single method that does the work

Why encapsulation exists

A class is useful when other code can rely on it without reading its source. A rate limiter is useful because every caller can trust that it never hands out more requests than its limit. A connection pool is useful because nobody can end up holding a connection twice. Those guarantees only hold if the class is the only code that can change its own state. If any caller in a 200,000-line codebase can write to the fields, the guarantee depends on every one of those callers getting it right forever.

Encapsulation means bundling data with the methods that change it, and hiding the data so those methods are the only way in. It buys three concrete things:

  • Guaranteed rules. If only the class's own methods touch its fields, you only have to check those methods to know the rules always hold.
  • One place to change. When the rule changes (say, the limiter must now be thread-safe), you edit one class instead of hunting through every caller.
  • Freedom to change the inside. Callers depend only on the methods, so you can swap an int counter for a timestamp queue without breaking anyone.

Access modifiers: who can see what

Java gives you four access levels. They are the tool; encapsulation is using them deliberately. The default in this course is simple: fields are private, always, and methods get the smallest access that works.

(none) package-private✓✓✗✗Classes and methods shared by one package, but not part of its public API

Two details trip people up. protected is wider than package-private, not narrower: it adds subclasses to everything in the package. And leaving out a modifier is not “private by default”; it means package-private, which is visible to every class in the same package.

Invariants: what must always be true

An invariant is a condition about an object's fields that must hold whenever no method of that object is running. That means just after the constructor finishes, and just after every public method returns. Inside a method the object may pass through a broken state briefly, as long as it is repaired before the method returns.

Here is a token bucket, the core of most rate limiters, which Case Study 32 builds in full. It holds up to capacity tokens. Each request spends one. Tokens drip back in at a fixed rate. Its invariants are easy to say in one line each:

  • 0 ≤ tokens ≤ capacity: never negative, never over the limit.
  • capacity > 0 and refillPerSecond > 0: a bucket that can't hold or earn tokens is meaningless.
  • lastRefillMillis never moves backwards.
TokenBucket.java: every field private, every rule enforced inside
public final class TokenBucket {
	private final int capacity;
	private final int refillPerSecond;
	private int tokens;              // invariant: 0 <= tokens <= capacity
	private long lastRefillMillis;

	public TokenBucket(int capacity, int refillPerSecond, long nowMillis) {
		if (capacity <= 0) throw new IllegalArgumentException("capacity must be positive");
		if (refillPerSecond <= 0) throw new IllegalArgumentException("refill rate must be positive");
		this.capacity = capacity;
		this.refillPerSecond = refillPerSecond;
		this.tokens = capacity;                     // start full: invariant holds
		this.lastRefillMillis = nowMillis;
	}

	/** Spends one token if there is one. The check and the change happen together, in here. */
	public boolean tryAcquire(long nowMillis) {
		refill(nowMillis);
		if (tokens == 0) return false;
		tokens--;
		return true;
	}

	public int available() { return tokens; }     // a read-only view of one number

	private void refill(long nowMillis) {
		long elapsed = nowMillis - lastRefillMillis;
		long earned = elapsed * refillPerSecond / 1000;
		if (earned <= 0) return;
		tokens = (int) Math.min(capacity, tokens + earned);   // clamp: invariant holds
		lastRefillMillis += earned * 1000 / refillPerSecond;     // keep the unused fraction of a token
	}
}
How the invariant is kept: the constructor rejects bad arguments before the object exists, tryAcquire never decrements below zero, and refill clamps at capacity. earned is a long so a bucket idle for weeks can't overflow an int. There is no setter, so no other code can undo any of it. (It is not thread-safe yet; Chapter 22 fixes that in this one class.)

A quick check that the refill arithmetic is right: with a rate of 2 tokens per second and 1,700 ms elapsed, earned = 1,700 × 2 ÷ 1,000 = 3 (integer division drops the .4). The bucket gains 3 tokens, clamped to capacity. lastRefillMillis moves forward by 3 × 1,000 ÷ 2 = 1,500 ms, not 1,700, so the leftover 200 ms still counts toward the next token.

Public fields vs a guarded class

Now compare a version that “just exposes the data”: public fields, or private fields with a getter and a setter for each. Callers then write the rate-limiting logic themselves, as if (b.getTokens() > 0) b.setTokens(b.getTokens() - 1);. Every caller becomes responsible for the invariant. Try to break each version.

The encapsulated version doesn't need its callers to be careful. The two writes a buggy caller tries don't even compile, and the one place where check-then-act happens is inside the class, so it's the one place to add a lock.

  


  
Notice what “private fields with a getter and setter for every one” gives you: nothing. setTokens(-3) breaks the invariant exactly as tokens = -3 does. You could put validation in the setter, but then you're protecting a single field while the real rule (spend one token only if one exists) still lives in every caller. The fix is not better setters. It's to stop asking callers to manage the state at all, and give them the operation they actually want.


  

  
Defensive copies

  
Private fields are not enough when a field holds a mutable object, such as a List, a Set, a Map or a java.util.Date. From P1 you know that passing or returning an object passes a reference. So if your class stores a caller's list, or returns its own list, some other code now shares your internal state, and private protects the reference, not the object it points to.

  
An API key with a set of permission scopes shows the danger. This version looks encapsulated. It isn't:

  

    


// Broken: shares its set both ways
public final class ApiKey {
	private final Set<String> scopes;

	public ApiKey(Set<String> scopes) {
		this.scopes = scopes;       // shared!
	}
	public Set<String> getScopes() {
		return scopes;              // shared!
	}
}

// Somewhere in an admin screen:
key.getScopes().add("admin:write");  // escalated

    

    


// Fixed: copy in, expose a question
public final class ApiKey {
	private final Set<String> scopes;

	public ApiKey(Set<String> scopes) {
		this.scopes = Set.copyOf(scopes);
	}
	public boolean allows(String scope) {
		return scopes.contains(scope);
	}
	public Set<String> scopes() {
		return scopes;             // unmodifiable
	}
}

    

  

  
The broken version leaks in two directions. Copy-in: the caller that built the set still holds a reference to it, so a later set.add(...) in that code changes the key's permissions. Copy-out: getScopes() hands every caller the live internal set. The fix handles both. Set.copyOf makes a new set that nobody else has a reference to, and that set is unmodifiable, so returning it can't leak either. Most callers don't even need the set: allows(scope) answers the question they actually have.

One trap in that table: Collections.unmodifiableSet wraps; it doesn't copy. If you wrap the caller's own set in the constructor, the caller can still change it underneath you. For input, copy. Set.copyOf, List.copyOf and Map.copyOf also reject null elements with a NullPointerException, which is usually what you want at a boundary.

Why java.time replaced java.util.Date
java.util.Date is mutable: setTime() changes it in place. So every class that stored a start date, an expiry or a certificate's “not after” time had to copy the Date on the way in and again on the way out. Forgetting either copy let callers move a deadline from outside, and Effective Java uses exactly this Period class as its defensive-copy example. The java.time types added in Java 8 (Instant, LocalDate, Duration) are immutable, so they can be stored and returned freely with no copies. When you design your own classes, prefer immutable field types for the same reason (P6).

  


  
Tell, don't ask

  
The token-bucket and API-key fixes follow one rule of thumb, usually called tell, don't ask. Don't ask an object for its data so you can make a decision and write the result back. Tell the object what you want, and let it decide using its own data.

  

    
Asking (logic outside)


if (bucket.getTokens() > 0) {
	bucket.setTokens(bucket.getTokens() - 1);
	handle(request);
}
if (key.getScopes().contains("read")) { ... }

      
The rule is copied into every caller. Changing it, or making it thread-safe, means finding all of them.

    
Telling (logic inside)


if (bucket.tryAcquire(now)) {
	handle(request);
}

if (key.allows("read")) { ... }

      
The rule lives in one method, next to the data it needs. Callers can't get it wrong.

  

  
This isn't a ban on getters. available() for a dashboard, or userId() for a log line, are fine: reading a value to display or pass along is harmless. The smell is reading a value in order to make a decision about the object and then change it. That decision belongs inside the object. You'll see this again as “feature envy” in Chapter 29, and as the reason anemic data-only classes are an anti-pattern in Chapter 21.


  
⚠️
Common mistakes

    
    
      
  • Generating a getter and setter for every field. That is a struct with extra typing. Add operations callers need, and add getters only for values they need to read.
    • 
      
  • Leaving out the modifier and thinking it's private. No modifier means package-private: every class in the package can reach it.
    • 
      
  • Storing a caller's collection directly. Copy it in the constructor, or the caller can change your state later.
    • 
      
  • Returning an internal mutable collection or Date. Return an unmodifiable view, a copy, or better, a method that answers the caller's real question.
    • 
      
  • Validating in a setter but not the constructor. Objects built with bad arguments start life broken. Validate at every entry point.
    • 
      
  • Checking the invariant only in tests. Tests find some violations; making the fields private and the operations complete prevents all of them from outside.
    •

Interview drill

    
Explain it simply: Isn't encapsulation just making fields private and adding getters and setters?

    
How a strong answer sounds
No. Private fields are the mechanism; the goal is that the class alone keeps its invariants. A public setter for every field lets any caller put the object into any state, so it protects nothing. Encapsulation means exposing operations that each leave the object valid, like tryAcquire() instead of setTokens(), validating in the constructor, and not leaking mutable internals through getters.

    
Deeper: An Account class must never have more than 100 open orders. In review you see public List<Order> getOrders() { return orders; }. What can go wrong, and how would you fix it?

    
How a strong answer sounds
Any caller can do account.getOrders().add(order) and bypass the limit, or remove orders without the account knowing, because the getter returns the live internal list. I'd add an operation that enforces the rule, placeOrder(Order), which throws or returns false at 100. Then I'd change the getter to return Collections.unmodifiableList(orders) if callers need a live read-only view, or List.copyOf(orders) for a snapshot. If callers only ever count or search, I'd offer openOrderCount() or findOrder(id) and drop the list getter entirely.

  


  

    
🧠 Key takeaways

    
    
      
  • Encapsulation means a class alone controls its state, so the rules it promises can't be broken from outside.
    • 
      
  • Fields are private, always. No modifier means package-private, and protected is wider than package-private.
    • 
      
  • An invariant must hold after the constructor and after every public method; validate arguments before the object exists.
    • 
      
  • Getters and setters for every field protect nothing. Expose operations like tryAcquire() that keep the invariants true.
    • 
      
  • Copy mutable inputs in (List.copyOf) and never return mutable internals. An unmodifiable wrapper is a view, not a copy.
    • 
      
  • Tell, don't ask: put the decision inside the object that owns the data.

A field is declared as int tokens; with no modifier. Which code can read and write it?

      

        
        
        
        
      

      
Leaving out the modifier gives package-private access: the declaring class plus every class in the same package. To restrict it to the class, you must write private.

    


    

      
A TokenBucket has private fields but a public setTokens(int) with no validation, and callers write if (b.getTokens() > 0) b.setTokens(b.getTokens() - 1). What is the core design problem?

      

        
        
        
        
      

      
Private fields with an unchecked setter give callers full control of the state, so the class can promise nothing. The fix is an operation like tryAcquire() that does the check and the change inside the class.

    


    

      
An ApiKey constructor does this.scopes = scopes;. The code that created the key later runs scopes.add("admin:write") on its own variable. What happens, and what is the fix?

      

        
        
        
        
      

      
The key stored a reference to the caller's set, so both share one object. final only stops the field being re-pointed; the set itself can still change. Copying in the constructor gives the key its own set that no one else can reach.

    


    

      
A class returns Collections.unmodifiableList(orders) from a getter, and later adds a new order to orders internally. What does a caller holding the returned list see?

      

        
        
        
        
      

      
unmodifiableList wraps the original list without copying. Reads go through to the live list, and writes throw UnsupportedOperationException. Use List.copyOf when you want a snapshot.

    


    

      
Why is if (bucket.tryAcquire(now)) handle(req); a better design than if (bucket.available() > 0) { bucket.take(); handle(req); }?

      

        
        
        
        
      

      
“Tell, don't ask.” Splitting the check (available) from the action (take) puts the rule in every caller and leaves a gap between check and act where another thread can take the last token. One method closes both problems.
