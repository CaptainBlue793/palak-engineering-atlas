Case Study: Elevator System

An elevator bank looks like a scheduling puzzle, and it is one, but the LLD interview is really checking two design skills. First, can you model each car as a small state machine with clear transitions, so doors never open while moving and a car in maintenance never gets calls? Second, can you separate the two decisions, which car answers a hall call and in what order a car visits its stops, into strategies you can compare? The simulator below runs a 10-floor, 2-car building with three algorithms on the same passengers.

  • Separate hall calls, car calls, cars, and the controller that assigns work
  • Model a car as a state machine driven by a tick
  • Order a car's stops with LOOK using two sorted sets
  • Make dispatch a strategy, from nearest car to an ETA cost function
  • Drive the whole system from a simulation loop with an injectable clock

Requirements and API

Clarify: F floors and N cars; a hall call is a button pressed on a floor, with a direction (“I'm on 3 and want to go up”); a car call is a floor button pressed inside a car; each car has doors that stay open for a few seconds per stop; a car can be taken out of service; the goal is short waits without starving anyone. Out of scope for the base design: weight limits, fire mode and VIP priority, which make good follow-ups because the state machine absorbs them.

public enum Direction { UP, DOWN, IDLE }
public record HallCall(int floor, Direction direction) {}      // pressed on a landing

public interface ElevatorSystem {
	void requestPickup(HallCall call);                          // the controller chooses a car
	void requestFloor(CarId car, int floor);                   // pressed inside a car
	void tick();                                                // advance the simulation one step
	List<CarStatus> status();                                 // floor, direction, state, stops: for displays
}

Two decisions, two owners. The controller decides which car takes a hall call (dispatch). Each car decides the order it visits its own stops (scheduling). Mixing them into one big loop is the usual way this design becomes unreadable; keeping them apart makes each a strategy you can swap and test on its own.

Elevator car as a State machine

A car is always in exactly one state, and each state allows only some actions: doors only open when stopped at a floor, a moving car can't take on a fresh direction mid-floor, an out-of-service car ignores dispatch. Model the states explicitly (Chapter 18) and advance them on a tick, so time is a parameter rather than a sleeping thread, and the whole system can be tested and simulated deterministically.

public final class ElevatorCar {
	enum State { IDLE, MOVING, DOORS_OPEN, OUT_OF_SERVICE }

	private int floor;
	private Direction dir = Direction.IDLE;
	private State state = State.IDLE;
	private int dwell;
	private final NavigableSet<Integer> up = new TreeSet<>(), down = new TreeSet<>();

	void tick() {
		switch (state) {
			case OUT_OF_SERVICE -> { }
			case DOORS_OPEN -> { if (--dwell == 0) state = nextStop() == null ? State.IDLE : State.MOVING; }
			case IDLE, MOVING -> {
				Integer target = nextStop();
				if (target == null) { state = State.IDLE; return; }
				if (target == floor) { arrive(); return; }
				floor += target > floor ? 1 : -1;
				state = State.MOVING;
				if (floor == target) arrive();
			}
		}
	}

	private void arrive() {
		if (!(dir == Direction.DOWN ? down : up).remove(floor))   // serve the call for our direction…
			(dir == Direction.DOWN ? up : down).remove(floor);    // …or the turnaround call at the end of a sweep
		state = State.DOORS_OPEN; dwell = DOOR_TICKS;
		listeners.forEach(l -> l.onArrived(id, floor, dir));   // hall lanterns, displays, passengers
	}
}

Request queues: LOOK with two sorted sets

A car's stops aren't a FIFO queue. Visiting them in arrival order sends a car from 2 to 9 to 3 to 8, crossing the building repeatedly. Elevators use the same idea as disk-arm scheduling: SCAN sweeps to the end of the building and back, serving stops on the way; LOOK is the practical variant that turns around at the last stop instead of the top floor. Two sorted sets make LOOK simple: up holds stops to serve while travelling up, down while travelling down. The next stop is a ceiling or floor query, O(log n). Car calls go into the set for their side of the car; a hall call goes into the set for its direction, so a car going up doesn't stop for someone who wants to go down.

void addHallCall(int f, Direction d) { (d == Direction.UP ? up : down).add(f); }
void addCarCall(int f)              { if (f > floor) up.add(f); else if (f < floor) down.add(f); }

Integer nextStop() {
	if (dir == Direction.IDLE) dir = directionToNearest();         // IDLE again if both sets are empty
	for (int turns = 0; turns < 2 && dir != Direction.IDLE; turns++) {
		Integer f = dir == Direction.UP
			? first(up.ceiling(floor), down.isEmpty() || down.last() <= floor ? null : down.last())    // up-stops ahead, else the highest down-call above us
			: first(down.floor(floor), up.isEmpty() || up.first() >= floor ? null : up.first());       // down-stops ahead, else the lowest up-call below us
		if (f != null) return f;
		dir = dir == Direction.UP ? Direction.DOWN : Direction.UP;         // nothing ahead: turn around (LOOK)
	}
	dir = Direction.IDLE;
	return null;
}

The two-turn limit is what stops LOOK from looping when the only remaining stops are behind the car in both sets. And because the car keeps its direction while there's work ahead, a passenger can wait at most one sweep up and one down: LOOK can't starve anyone, which a “nearest stop next” rule can (a busy middle of the building would keep pulling the car back and away from the top floor).

Dispatch strategies: nearest car, SCAN, LOOK

The controller answers “which car?” through a strategy. Nearest car by distance is the obvious first answer and is decent, but it ignores direction: the nearest car might be moving away, or be full of stops. An ETA cost estimates when each car could actually arrive: straight there if it's idle or approaching in the right direction; otherwise to the end of its current sweep and back; plus a few seconds for each stop it has already promised.

public interface Dispatcher { ElevatorCar choose(HallCall call, List<ElevatorCar> available); }

final class EtaDispatcher implements Dispatcher {
	public ElevatorCar choose(HallCall call, List<ElevatorCar> cars) {
		return cars.stream().min(Comparator.comparingInt(c -> eta(c, call))).orElseThrow();
	}

	static int eta(ElevatorCar c, HallCall call) {
		int d = Math.abs(c.floor() - call.floor());
		boolean onTheWay = c.direction() == call.direction()
			&& (c.direction() == Direction.UP ? call.floor() >= c.floor() : call.floor() <= c.floor());
		int travel = c.direction() == Direction.IDLE || onTheWay ? d
			: Math.abs(c.sweepEnd() - c.floor()) + Math.abs(c.sweepEnd() - call.floor());
		return travel * FLOOR_TICKS + c.stopCount() * DOOR_TICKS;        // promised stops cost time too
	}
}

Simulation loop

The system has no threads inside it. A driver calls tick() at a fixed rate in production (from a scheduler, Chapter 35) or as fast as possible in a simulation or a test. Each tick, pending hall calls are dispatched, then every car advances one step. Button presses arrive between ticks and are queued. That single-threaded core means cars and the controller need no locks; only the inbound request queue is shared with the threads that handle button presses, and a ConcurrentLinkedQueue covers it.

🧠
Destination dispatch

In many modern office towers you don't press ▲ at all: you enter your floor on a keypad in the lobby and the screen tells you which car to take. The major elevator manufacturers all sell these destination dispatch systems. The change is exactly the kind of extension this design should absorb: the hall call gains a destination (HallCall(floor, destination) instead of a direction), and the dispatcher can now group people going to nearby floors into the same car, so each car makes fewer stops. The car state machine and its LOOK ordering don't change at all; only the dispatch strategy and the call type do.

⚠️
Common mistakes
  • One god class that dispatches, moves cars and opens doors in one loop.
  • Serving stops in arrival order (FCFS): the car crosses the building again and again.
  • “Nearest stop next” scheduling, which can starve the ends of the building.
  • No explicit states, so doors can open while moving or a broken car keeps receiving calls.
  • Ignoring direction on hall calls: stopping for someone going the other way.
  • A thread per car with sleeps, making the system nondeterministic and untestable. Tick it.
  • Forgetting to reassign calls when a car goes out of service.
🎤
Interview drill

Explain it simply: How does a car decide which floor to go to next?

How a strong answer sounds
It uses LOOK. The car keeps two sorted sets: stops to serve going up and stops to serve going down. While it's moving up, the next stop is the smallest up-stop at or above its floor (a ceiling query), or failing that the highest down-call above it; when nothing is left ahead, it turns around and does the mirror image going down. When both sets are empty it goes idle. That serves everything on the way, never starves the top or bottom floors, and each lookup is O(log n).

Deeper: Add fire service mode: on an alarm, every car must go to the lobby, open its doors and stop taking calls. Where does it go?

How a strong answer sounds
It's a new state and a controller command, not a scattering of if (fire) checks. The controller, on an alarm, stops dispatching new hall calls and tells each car to recall. Each car moves to a RECALL state: it clears its up and down sets, and heads to the lobby, and a moving car finishes to the nearest floor in its current direction without opening its doors first if that's the rule. On arrival it enters FIRE_SERVICE: doors open, and it ignores hall and car calls except from a firefighter key, which is its own small set of transitions. Because states are explicit, I can list exactly which events each state accepts, and tests can drive the alarm with the tick loop and assert every car ends at the lobby with doors open.

🧠 Key takeaways

  • Separate dispatch (which car) from scheduling (the order a car visits stops); each is a strategy.
  • Model each car as an explicit state machine advanced by a tick: IDLE, MOVING, DOORS_OPEN, OUT_OF_SERVICE.
  • LOOK with two sorted sets serves stops in sweeps, respects hall-call direction and can't starve anyone.
  • Dispatch by estimated arrival time, not just distance: direction and promised stops matter.
  • A single-threaded tick loop with a concurrent inbound queue makes the system deterministic and testable.
  • New modes (fire service, destination dispatch) land as new states or strategies, not scattered conditionals.

Check your understanding

What's the difference between SCAN and LOOK?

LOOK “looks” ahead and skips the empty travel to the top or bottom floor, which is why real elevators behave like LOOK.

A car on floor 5 is moving up with an up-stop at 8. Someone on floor 6 presses ▼. Should the car stop at 6 on the way up?

Stopping would pick up someone who wants to go down while the car is going up. Hall calls go into the set for their direction.

Why can a nearest-car dispatcher make poor choices?

An ETA estimate accounts for direction and promised stops; distance alone doesn't.

Why drive the system with tick() instead of one thread per car?

Time becomes an input. Only the inbound request queue is shared with I/O threads.

A car goes out of service with three hall calls assigned. What should happen?

Hall calls belong to passengers, not to a car. Reassigning them is part of the OUT_OF_SERVICE transition.
