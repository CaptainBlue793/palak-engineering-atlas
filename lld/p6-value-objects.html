Value Objects, Enums & Immutability

Some objects matter because of who they are: a user, an order, a session. Others matter only because of what they hold: an email address, an amount of money, a host and port. The second kind are value objects. Getting them right means getting equals, hashCode and immutability right, and those three decide whether your caches, sets and maps actually work.

  • Tell an entity (identity) from a value object (contents)
  • Write equals and hashCode that honour their contract, and explain the HashMap bugs when they don't
  • Use records for value objects, and know where they are only shallowly immutable
  • Make a class immutable, and say what that buys for sharing, hashing and threads
  • Put fields and behaviour on enums, and avoid persisting ordinal()
  • Represent money without floating-point errors

Entities and value objects

An entity has an identity that stays the same while its data changes. User u42 who changes their email is still user u42. Two users who happen to share a name are still two users. A value object has no identity beyond its contents. The address db1.internal:5432 is equal to any other db1.internal:5432; there's no sense in which one of them is “the real one”.

Designs get much simpler when more of the model is values. Money with a currency catches “added euros to dollars” in one place. An EmailAddress type validates once, in its constructor, instead of every method re-checking a raw String. Chapter 27 builds on this split.

equals and hashCode: the contract

Object.equals compares identity, the same as ==. For a value object you override it to compare contents. The moment you do, you must also override hashCode, because hash-based collections rely on one rule: equal objects must have equal hash codes. (Unequal objects may share a hash code; that's just a collision.) equals must also be reflexive, symmetric, transitive, consistent over time, and return false for null.

HostAndPort.java: a value object written by hand
public final class HostAndPort {
	private final String host;
	private final int port;

	public HostAndPort(String host, int port) {
		if (port < 1 || port > 65_535) throw new IllegalArgumentException("bad port: " + port);
		this.host = host.toLowerCase(Locale.ROOT);        // normalise once: DB1 and db1 are the same host
		this.port = port;
	}

	@Override public boolean equals(Object o) {           // Object, not HostAndPort: an override
		if (this == o) return true;
		if (!(o instanceof HostAndPort other)) return false;   // also handles null
		return port == other.port && host.equals(other.host);
	}
	@Override public int hashCode() { return Objects.hash(host, port); }  // same fields as equals
	@Override public String toString() { return host + ":" + port; }
}
The rule of thumb: hashCode uses exactly the fields equals compares. Because the class is final and immutable, the hash never changes after construction, so the object is safe as a map key forever.

Why does the rule matter? A HashMap is an array of buckets. To store a key it computes key.hashCode(), uses it to pick one bucket, and puts the entry there. To look a key up it computes the hash again, goes straight to that one bucket, and only then calls equals on the few entries inside. If two equal keys have different hash codes, the lookup goes to the wrong bucket and never even calls equals. Break the rule, or change a key's fields after inserting it, and the map loses entries. A real HashMap starts with 16 buckets and spreads the hash bits first; eight buckets and a simple hash keep the picture readable without changing the idea. In “equals without hashCode” mode, every new key gets a different identity hash, as Object.hashCode() does.

Records: value objects in one line

Writing equals, hashCode, toString and accessors by hand is error-prone. Since Java 16, a record generates all of them from a list of components, and makes the fields private final. A compact constructor is where you validate and normalise:

public record HostAndPort(String host, int port) {
	public HostAndPort {                                        // compact constructor: no parameter list
		if (port < 1 || port > 65_535) throw new IllegalArgumentException("bad port: " + port);
		host = host.toLowerCase(Locale.ROOT);                  // reassign the parameter, then fields are set
	}
}

public record Route(String path, List<HostAndPort> backends) {
	public Route {
		backends = List.copyOf(backends);                     // a record is only shallowly immutable
	}
}

var a = new HostAndPort("DB1", 5432);
a.host();                                                   // "db1": accessors are named after the components
a.equals(new HostAndPort("db1", 5432));                   // true

“Shallowly immutable” is the catch. A record's fields can't be reassigned, but if a component is a mutable object, like an ArrayList, the list itself can still change, and with it the record's equals and hashCode. Copy mutable components in the compact constructor, exactly as P2 copied the API key's scopes. Records can't extend other classes (they already extend Record), but they can implement interfaces.

Making a class immutable

An immutable object's state can't change after its constructor finishes. The recipe is short:

  1. Make the class final (or use a record), so no subclass can add mutable state.
  2. Make every field private final.
  3. Provide no setters. Operations that “change” the value return a new object instead: money.plus(tax), instant.plusSeconds(30).
  4. Copy mutable inputs in, and never hand mutable internals out.

What you get in return is a lot. An immutable object is thread-safe with no locks, because there is nothing to race on. It is safe as a map key, because its hash can't change. It can be shared and cached freely: one HostAndPort can sit in a thousand routes. And it's easy to reason about, because it is always exactly what its constructor made. The cost is a new object for every change, which the JVM's allocator and garbage collector handle cheaply for small objects.

🧠
Why String is immutable

Java's String is final and immutable, and the platform depends on it. The JVM can keep one copy of each string literal and share it everywhere (the string pool). String caches its own hash code, which is safe only because the contents can't change, and that makes strings fast map keys. And it closes a security hole: code that checks a file path or class name and then uses it can't have the string changed between the check and the use. If String were mutable, every one of those would need a defensive copy.

Enums with fields and behaviour

A Java enum is a class with a fixed set of instances, created once when the class loads. Because there's exactly one instance of each constant, comparing with == is correct. Enums can have fields, constructors and methods, so the data and rules about each constant live with the constant instead of in switch statements scattered around the codebase:

public enum JobState {
	QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELLED;

	public boolean isTerminal() { return this == SUCCEEDED || this == FAILED || this == CANCELLED; }

	public boolean canMoveTo(JobState next) {
		return switch (this) {                           // the compiler checks every constant is handled
			case QUEUED  -> next == RUNNING || next == CANCELLED;
			case RUNNING -> next == SUCCEEDED || next == FAILED || next == CANCELLED;
			case SUCCEEDED, FAILED, CANCELLED -> false;
		};
	}
}

public enum HttpStatus {
	OK(200), CREATED(201), NOT_FOUND(404), TOO_MANY_REQUESTS(429), SERVICE_UNAVAILABLE(503);

	private final int code;
	HttpStatus(int code) { this.code = code; }
	public int code() { return code; }
	public boolean isRetryable() { return code == 429 || code == 503; }
}

Two tools pair with enums: EnumSet and EnumMap, a set and a map specialised for enum keys that are backed by a bit vector or an array, so they're faster and smaller than the hash versions. And one rule: never persist ordinal(), the constant's position in the declaration. Insert a new constant in the middle, like PAUSED after RUNNING, and every stored number after it now means a different state. Store name(), or an explicit code field like HttpStatus.code(). Money is a value object, never a double

double is binary floating point. It can't represent 0.1 exactly, so 0.1 + 0.2 is 0.30000000000000004, and summing a million cents drifts. For money, use one of two representations, wrapped in a value object that also carries the currency:

  • A long of minor units (cents, paise): exact, fast, and what most payment APIs use. $19.99 is 1999.
  • BigDecimal, when you need arbitrary precision or rates with many decimal places. Beware one trap: new BigDecimal("1.0").equals(new BigDecimal("1.00")) is false, because equals also compares scale. Compare amounts with compareTo(...) == 0, or normalise the scale in your value object's constructor.
public record Money(long minorUnits, Currency currency) {
	public Money { Objects.requireNonNull(currency); }

	public Money plus(Money other) {
		if (!currency.equals(other.currency)) throw new IllegalArgumentException(currency + " + " + other.currency);
		return new Money(Math.addExact(minorUnits, other.minorUnits), currency);   // throws on overflow
	}
}
⚠️
Common mistakes
  • Overriding equals but not hashCode. Equal keys land in different buckets; sets hold duplicates and maps miss lookups.
  • Writing equals(HostAndPort o) instead of equals(Object o). That's an overload that collections never call. @Override catches it.
  • Using a mutable object as a map key and changing it afterwards. Its entry is stranded in the old bucket.
  • Assuming records are deeply immutable. Copy list, set and map components in the compact constructor.
  • Persisting ordinal() of an enum. Reordering or inserting constants silently changes stored data.
  • Money as double, or comparing BigDecimal amounts with equals.

Interview drill

Explain it simply: Why must you override hashCode whenever you override equals?

How a strong answer sounds
Hash-based collections use hashCode to pick a bucket and only call equals on entries in that bucket. The contract says equal objects must have equal hash codes. If I override equals but keep the identity hashCode, two equal keys usually land in different buckets, so get misses and a HashSet holds duplicates. I compute hashCode from exactly the fields equals compares, or I use a record, which generates both consistently.

How a strong answer sounds
An immutable value object: a record with a long of minor units and a Currency, validated in the compact constructor. No double, because binary floating point can't represent most decimal amounts exactly. Arithmetic returns new instances, checks that currencies match, and uses Math.addExact so overflow throws instead of wrapping. Being immutable, it's safe to share across threads and use as a map key. For conversion or tax rates I'd use BigDecimal with an explicit rounding mode, and compare with compareTo, not equals, because equals also compares scale.

🧠 Key takeaways

  • Entities are defined by identity; value objects only by their contents, and should be immutable.
  • Equal objects must have equal hash codes: override equals(Object) and hashCode together, over the same fields.
  • A HashMap looks in one bucket chosen by the hash. A broken hash, or a key mutated after insertion, loses entries.
  • Records generate equals, hashCode, toString and accessors, but are only shallowly immutable: copy mutable components.
  • Immutable objects are thread-safe, safe as keys and freely shareable. Recipe: final class, private final fields, no setters, copies in and out.
  • Enums hold data and rules per constant; compare with ==, never persist ordinal(). Money is minor units or BigDecimal, never double.

Check your understanding

A class overrides equals to compare host and port but doesn't override hashCode. You add two equal instances to a HashSet. What is the set's size, most likely?

The set picks a bucket from hashCode. The default identity hash differs between the two objects, so the second one goes to a different bucket where there's nothing to compare with. The contract was broken, so the set can't do its job.

A mutable key is put in a HashMap, then one of its fields used in hashCode is changed. What does map.get(sameKeyObject) return?

HashMap computes the hash once at insertion and never looks again. After the change, lookups go to the bucket for the new hash, while the entry sits in the old one. Keys should be immutable.

record Route(String path, List<HostAndPort> backends) {} is created with an ArrayList the caller keeps. Is the record immutable?

Final fields stop reassignment, not changes to the object a field points at. Records generate no setters, but they don't copy components either. A compact constructor with backends = List.copyOf(backends); makes it truly immutable.

Why store an amount like $19.99 as long 1999 (cents) rather than double 19.99?

0.1 has no exact binary representation, so 0.1 + 0.2 != 0.3 in a double, and errors accumulate over many operations. Integer minor units (or BigDecimal) are exact. Both a long and a double are 8 bytes.

Jobs are stored with state.ordinal(). Someone adds PAUSED between RUNNING and SUCCEEDED. What happens to existing rows?

The ordinal is just the declaration position. Inserting a constant shifts every later one, and old rows are silently misread. Persist name() or an explicit code.
