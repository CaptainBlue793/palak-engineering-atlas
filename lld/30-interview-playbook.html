The LLD Interview Playbook

Chapter 1 described what an LLD round is. Twenty-nine chapters later you have the toolkit; this chapter is about running it under a clock, with someone watching. It covers how the scoring actually works, a minute-by-minute plan for the 45 minutes, the questions worth asking in the first five, a worked example, a playbook for “now add X”, and the failure modes that turn a good design into a no-hire.

  • Know what evidence each rubric dimension needs, and make it visible
  • Time-box the round so that code and the follow-up both happen
  • Ask the few clarifying questions that actually change the design
  • Absorb an extension follow-up by naming where it lands in the design
  • Recognise and recover from the common failure modes

The scoring rubric, from the interviewer's side

Chapter 1 listed the eight dimensions interviewers score. What matters in the room is how the scoring happens: the interviewer writes down evidence as you go, then rates each dimension against it afterwards. Anything you decided silently doesn't exist on their notes. So the practical rule is: make every decision audible, in one sentence, with its reason. “Booking is its own class rather than a field on Room, because it has a lifecycle: confirmed, cancelled.” That sentence is evidence for three dimensions at once.

DimensionEvidence the interviewer writes downWhat the bar usually rises to for senior candidates
Requirements & scopeUse cases listed; questions asked; scope cut statedSpots the requirement that drives the design (concurrency, a variation axis) unprompted
Entities & relationshipsClass list with ownership; entity vs value choicesAggregate boundaries around invariants (Ch 27)
Abstractions & patternsInterfaces where things vary; pattern named with its reasonAlso says where they chose not to abstract, and why
Code qualityCompiling-quality core methods; validation; clear namesInvariants enforced in one place; errors modelled deliberately
Extensibility & concurrencyFollow-up absorbed with small changes; shared state named and guardedRaises concurrency and testability before being asked
CommunicationThinks aloud; takes hints; states trade-offsDrives the session: proposes the plan, checks in at each phase

Hiring decisions are usually made on the overall picture, but a single dimension with no evidence at all is the most common reason a promising round becomes a no-hire. That's why time-boxing matters: the phases you never reach score zero.

Time-boxing the 45 minutes

Plan for about 42 working minutes; introductions and your questions at the end take the rest. The budget below is a default, not a law. The point is to have one, say it out loud at the start (“I'll spend about five minutes on requirements, then sketch the classes, then code the core flow”), and notice when you drift.

The first five minutes: questions that change the design

Clarifying isn't a ritual; every question should be able to change what you build. If the answer wouldn't change your classes, don't ask it, propose a default instead (“I'll assume a single building; tell me if that's wrong”). These are the questions that usually matter:

Ask aboutExample questionDesign decision it changes
Core use cases“Book, cancel and search for a free room: anything else in scope?”Which methods the service exposes; what you cut
Variation axes“Will room-selection rules differ per office?”Where interfaces go (a Strategy here, Ch 15)
Concurrency“Can two people book the same room at the same moment?”Aggregate boundary, locking or version checks (Ch 22)
Lifecycle“Can a booking be tentative, then confirmed? Does it expire?”A state machine, and an injected clock (Ch 18)
Persistence“In memory is fine for this, behind a repository interface?”Repository interfaces with in-memory implementations (Ch 26)
Notifications / side effects“Should anyone be told when a booking changes?”Domain events and listeners (Ch 16)

A worked example: meeting-room booking

Here is how the phases sound for “design a meeting-room booking system”, compressed. Clarify: book a room for a time slot, cancel, find free rooms by size and equipment; many users concurrently; single office; in-memory behind interfaces; payments and calendar sync out of scope. Model: Room (entity: id, capacity, equipment), TimeSlot (value: start and end, validates start < end, knows overlaps), Booking (entity: id, organiser, slot, status). The invariant, “no two confirmed bookings for one room overlap”, needs every booking of a room at once, so a RoomSchedule per room is the aggregate that guards it. Interfaces: BookingService for the use cases, RoomScheduleRepository, and a RoomSelectionPolicy strategy (smallest room that fits, by default). Then code the part that carries the invariant:

public record TimeSlot(Instant start, Instant end) {
	public TimeSlot { if (!start.isBefore(end)) throw new IllegalArgumentException("start must be before end"); }
	public boolean overlaps(TimeSlot o) { return start.isBefore(o.end) && o.start.isBefore(end); }   // half-open: back-to-back is fine
}

public final class RoomSchedule {                                        // aggregate: one per room
	private final RoomId room;
	private final Map<BookingId, Booking> bookings = new HashMap<>();

	public synchronized Booking book(UserId organiser, TimeSlot slot, BookingId id) {
		boolean clash = bookings.values().stream().anyMatch(b -> b.isActive() && b.slot().overlaps(slot));
		if (clash) throw new SlotUnavailable(room, slot);
		Booking b = new Booking(id, room, organiser, slot);
		bookings.put(id, b);
		return b;
	}
	public synchronized void cancel(BookingId id, UserId by) { /* only the organiser; idempotent */ }
}

While writing it, say the decisions: “Half-open intervals, so a meeting ending at 10:00 doesn't clash with one starting at 10:00. Synchronized per schedule, so bookings for different rooms don't contend; with a database this becomes a version check on the schedule. Handling “now add X”

The follow-up is where the design is actually tested (Chapter 1). Don't start editing. Use four moves: restate the requirement in one sentence; locate the axis of change and say where it lands; show the diff, meaning what's new, what changes, and what stays untouched; and name the trade-off. Most follow-ups fall into a few families:

Follow-up familyExampleWhere it usually lands
A new variant“Add hot desks as well as rooms”A new implementation behind an existing interface; maybe a factory entry
A new rule or policy“VPs can bump other bookings”A new strategy, or a link in a chain of rules (Ch 19)
A new lifecycle stage“Bookings expire if nobody checks in within 10 minutes”A state and transition, plus the injected clock and a scheduled check
A cross-cutting concern“Log every change for audit”A decorator (Ch 13) or a domain-event listener
A composite request“Recurring weekly meetings”A value that expands to many slots, booked all-or-nothing inside one aggregate
Concurrency or scale“Thousands of bookings per second”Name the shared state, the lock or version check guarding it, and what partitions it

If a follow-up genuinely needs a change to your core model, say so plainly: “my model assumed one organiser per booking; co-organisers means Booking holds a set, and cancel checks membership.” A small, honest change you can explain beats a contortion that avoids admitting it. What reads badly is either a rewrite or a new if in the middle of an existing method with no acknowledgement.

Common failure modes

Most no-hire rounds fail in one of a handful of recognisable ways, and each has a recovery line you can use mid-interview:

  • Coding before modelling. By minute 25 the code has three responsibilities per class. Recovery: “Let me step back and list the classes before I write more.”
  • Never reaching code. Twenty-five minutes of boxes and arrows. Recovery: pick the one method that carries the invariant and write it now.
  • Pattern stuffing. Factory, builder, singleton and observer in the first ten minutes, none tied to a requirement. Name a pattern only when a requirement asks for it.
  • Silent thinking. Two minutes without a word gives the interviewer nothing to write down. Think out loud, even when unsure: “I'm weighing a map per room against one global list.”
  • Defending instead of adapting. A hint (“what if two people book at once?”) is a gift, not an attack. Say “good point” and change the design.
  • Ignoring the clock. Ask for time checks; cut depth, not phases.

Why interviews use rubrics at all

Frank Schmidt and John Hunter's widely cited 1998 meta-analysis of hiring methods found that structured interviews, with the same questions and defined scoring for every candidate, predicted job performance better than unstructured ones (validity coefficients of about 0.51 versus 0.38). That research is a large part of why tech companies train interviewers to ask a fixed problem, take notes on evidence, and score against a rubric rather than a gut feeling. For you, it means the round rewards visible, specific evidence in each dimension, which is exactly what announcing your plan, stating decisions and reaching every phase provide.

⚠️
Common mistakes
  • Asking questions whose answers don't change the design, while missing the one about concurrency.
  • Making decisions silently. If you didn't say it, it isn't on the interviewer's notes.
  • Spending the code phase on getters, constructors and CRUD instead of the method that enforces the rule.
  • Treating the follow-up as a new problem and redesigning, instead of locating where it lands.
  • Memorising a “correct” design for common problems and reciting it regardless of the stated requirements.
  • No summary. The last minute is a chance to restate the design and its trade-offs in thirty seconds.

Interview drill

Explain it simply: You have 45 minutes for an LLD problem. How do you spend them?

How a strong answer sounds
I say my plan up front: about five minutes clarifying use cases, the questions that change the design and the scope cut; about eight modelling entities, values and which class guards each invariant; about seven on the service API and the interfaces at the variation points; around seventeen coding the methods that carry the rules; and the last five on the follow-up. I check in at the boundaries, think out loud, and if I'm running late I cut depth, not whole phases, so every part of the rubric gets some evidence.

Deeper: In the meeting-room design, the interviewer asks: “Support recurring weekly meetings for the next three months, and it must be all-or-nothing.” Walk through your answer.

How a strong answer sounds
Restate: one request books thirteen weekly slots in one room, or none. Locate: this is a composite request. A Recurrence value object (start slot, weekly, until date) expands into a list of TimeSlots. Because all the slots are in the same room, they're all in one RoomSchedule aggregate, so a new method bookAll(organiser, slots) checks every slot for clashes first and only then adds them, inside the same lock or version check; that's what makes it atomic. What stays untouched: TimeSlot, the selection policy, cancel. Trade-offs: the policy must now find a room free for all thirteen slots, and I'd store a series id on each booking so “cancel this and all future occurrences” is easy to add later. If recurrences could span rooms, it would cross aggregates and I'd need a saga or a relaxed rule, which I'd raise rather than hide.

🧠 Key takeaways

  • Interviewers score written evidence: state each decision and its reason aloud.
  • Announce a time plan, check in at phase boundaries, and cut depth rather than whole phases.
  • Ask only questions whose answers change the design; propose defaults for the rest.
  • Code the methods that carry the invariants, not the boilerplate.
  • For follow-ups: restate, locate the axis of change, show the small diff, name the trade-off.
  • Hints are help. Adapt quickly and say what changed.

Check your understanding

Why should you say each design decision and its reason out loud?

Rubric scoring is evidence-based. One sentence per decision, with its reason, turns good thinking into scoreable notes.

You're at minute 32 and haven't written any code. What's the best move?

A phase with no evidence scores zero. Cut depth elsewhere and put real code behind the most important rule.

Which clarifying question is most worth asking for a booking system?

The concurrency answer changes the aggregate boundary and how the invariant is guarded. The others don't change the classes.

Follow-up: “Log every booking change for audit.” Where does it usually land?

Auditing is cross-cutting. A decorator or an event listener adds it without touching the classes that enforce the rules.

The interviewer asks, “What happens if two people book at once?” and your design ignores it. What's the strongest response?

Hints are an invitation to adapt. A quick, specific change that's clearly explained is strong evidence for both extensibility and communication.
