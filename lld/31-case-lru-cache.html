Case Study: LRU & LFU Cache

“Design an LRU cache” is the most common LLD warm-up, and it's a good one: it has a hard complexity requirement (O(1) get and put), a data-structure trick that satisfies it, a natural extension point (the eviction policy), and a concurrency twist that catches people out, because in an LRU cache even a read is a write. This case study goes through it the way the interview does: requirements, model, core code, the follow-up to LFU, and thread safety.

  • Pin down the cache's requirements and a small generic API
  • Build O(1) LRU from a hash map and a doubly linked list
  • Pull eviction out into a Strategy so LRU, LFU and FIFO are interchangeable
  • Implement O(1) LFU with frequency buckets, and know when it loses to LRU
  • Make the cache thread-safe, knowing why a read-write lock doesn't help

Requirements and API

Clarify the few things that change the design, and propose defaults for the rest: capacity is a number of entries (not bytes); get and put must be O(1); when full, put evicts the least recently used entry; the eviction policy should be swappable (LFU is the likely follow-up); many threads will use it; null keys and values are rejected. Out of scope for now: expiry (TTL), loading on a miss, and statistics, which make good follow-ups.

RequirementDesign consequence
O(1) lookup by keyA HashMap from key to entry
O(1) “which entry is least recently used?”Entries kept in recency order, with O(1) move-to-front: a doubly linked list
Swappable eviction policyAn EvictionPolicy interface; the cache asks it for a victim (Strategy)
Many threadsA lock around every operation, including get, or a design that buffers access records
No nullsget returns Optional; put fails fast on null
 
public interface Cache<K, V> {
	Optional<V> get(K key);          // a hit also counts as a use
	void put(K key, V value);        // may evict one entry
	boolean remove(K key);
	int size();
}

HashMap + doubly linked list

A hash map alone finds entries in O(1) but has no order. A list alone keeps order but finds entries in O(n). Together they cover each other: the map goes from key to list node, and the list keeps nodes from most to least recently used. On a hit, the map gives you the node, and you unlink it and relink it at the front, both O(1) because the node knows its neighbours. The list has to be doubly linked: unlinking a node from a singly linked list needs its predecessor, which you'd have to search for. Two sentinel nodes at the head and tail mean there's always a neighbour, so no null checks for the first or last entry.

public final class LruCache<K, V> implements Cache<K, V> {
	private static final class Node<K, V> {
		final K key; V value; Node<K, V> prev, next;
		Node(K key, V value) { this.key = key; this.value = value; }
	}
	private final int capacity;
	private final Map<K, Node<K, V>> index = new HashMap<>();
	private final Node<K, V> head = new Node<>(null, null), tail = new Node<>(null, null);   // sentinels

	public LruCache(int capacity) {
		if (capacity <= 0) throw new IllegalArgumentException("capacity must be positive");
		this.capacity = capacity;
		head.next = tail; tail.prev = head;
	}

	public Optional<V> get(K key) {
		Node<K, V> n = index.get(key);
		if (n == null) return Optional.empty();
		moveToFront(n);
		return Optional.of(n.value);
	}

	public void put(K key, V value) {
		Objects.requireNonNull(key); Objects.requireNonNull(value);
		Node<K, V> n = index.get(key);
		if (n != null) { n.value = value; moveToFront(n); return; }
		if (index.size() == capacity) {
			Node<K, V> lru = tail.prev;
			unlink(lru);
			index.remove(lru.key);                  // why the node stores its key
		}
		n = new Node<>(key, value);
		index.put(key, n);
		linkFront(n);
	}

	private void moveToFront(Node<K, V> n) { unlink(n); linkFront(n); }
	private void unlink(Node<K, V> n) { n.prev.next = n.next; n.next.prev = n.prev; }
	private void linkFront(Node<K, V> n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
	// remove(k): unlink + index.remove; size(): index.size()
}

Worth saying in the interview: Java already ships this. new LinkedHashMap<>(16, 0.75f, true) keeps entries in access order, and overriding removeEldestEntry to return size() > capacity turns it into an LRU cache in a few lines. Mention it, then build the explicit version, because the interviewer wants to see that you understand the structure, and because the next requirement needs it opened up.

Eviction policy as Strategy

The follow-up is almost always “now support LFU” (or FIFO, or “let callers choose”). If recency order is welded into the cache, that's a rewrite. Split the two jobs instead: the cache owns storage and capacity; an eviction policy watches accesses and names the victim when space is needed (Strategy). The cache never knows which policy it has.

public interface EvictionPolicy<K> {
	void recordInsert(K key);
	void recordAccess(K key);      // a hit, or an update of an existing key
	void recordRemove(K key);
	K victim();                     // the key to evict; only called when the cache is non-empty
}

public final class BoundedCache<K, V> implements Cache<K, V> {
	private final int capacity;
	private final Map<K, V> values = new HashMap<>();
	private final EvictionPolicy<K> policy;               // injected

	public Optional<V> get(K key) {
		V v = values.get(key);
		if (v != null) policy.recordAccess(key);
		return Optional.ofNullable(v);
	}

	public void put(K key, V value) {
		if (values.containsKey(key)) { values.put(key, value); policy.recordAccess(key); return; }
		if (values.size() == capacity) {
			K out = policy.victim();
			values.remove(out);
			policy.recordRemove(out);
		}
		values.put(key, value);
		policy.recordInsert(key);
	}
}

public final class LruPolicy<K> implements EvictionPolicy<K> {
	private final LinkedHashSet<K> order = new LinkedHashSet<>();     // oldest use first
	public void recordInsert(K k) { order.add(k); }
	public void recordAccess(K k) { order.remove(k); order.add(k); }   // both O(1): re-append at the end
	public void recordRemove(K k) { order.remove(k); }
	public K victim() { return order.iterator().next(); }
}
// FifoPolicy: identical, except recordAccess does nothing.

LinkedHashSet is a hash table threaded with a doubly linked list, the same structure as before, so removing a key and re-adding it at the end are both O(1). The policy stores only keys; the cache stores values. That costs a second hash lookup per operation compared with the fused LruCache, which is the price of pluggability, and a fair trade-off to state out loud.

LFU with frequency buckets

LFU evicts the key used least often, breaking ties by recency. A heap ordered by count would make every access O(log n). The O(1) version, described by Shah, Mitra and Matani in 2010, groups keys into buckets by frequency and remembers the smallest non-empty frequency. An access moves a key from bucket f to bucket f + 1; the victim is the oldest key in the minimum bucket; a new key always starts at frequency 1, which resets the minimum.

public final class LfuPolicy<K> implements EvictionPolicy<K> {
	private final Map<K, Integer> freq = new HashMap<>();
	private final Map<Integer, LinkedHashSet<K>> buckets = new HashMap<>();   // each bucket in recency order
	private int minFreq;

	public void recordInsert(K k) { freq.put(k, 1); bucket(1).add(k); minFreq = 1; }

	public void recordAccess(K k) {
		int f = freq.get(k);
		leave(k, f);
		if (!buckets.containsKey(f) && minFreq == f) minFreq = f + 1;   // emptied the minimum bucket
		freq.put(k, f + 1);
		bucket(f + 1).add(k);
	}

	public void recordRemove(K k) {
		int f = freq.remove(k);
		leave(k, f);
		if (f == minFreq && !buckets.containsKey(f) && !buckets.isEmpty())
			minFreq = Collections.min(buckets.keySet());   // only on explicit remove(); an eviction is always followed by an insert
	}

	public K victim() { return buckets.get(minFreq).iterator().next(); }   // least frequent, oldest among ties

	private void leave(K k, int f) { LinkedHashSet<K> b = buckets.get(f); b.remove(k); if (b.isEmpty()) buckets.remove(f); }
	private LinkedHashSet<K> bucket(int f) { return buckets.computeIfAbsent(f, x -> new LinkedHashSet<>()); }
}

Which is better depends on the traffic, and the lab above shows both sides. LFU protects genuinely popular keys from a one-off scan (a report reading every row once flushes an LRU cache). But LFU has long memory: keys that were popular yesterday keep high counts and squat in the cache while today's hot keys evict each other. Real LFU implementations therefore age counts, halving them periodically or decaying them over time, and modern caches combine both ideas.

Making it thread-safe

The trap: get looks like a read, so a ReadWriteLock seems natural. But every hit changes the recency list (or the frequency buckets), so two concurrent “reads” race on the same pointers and can corrupt the list. Every operation needs exclusive access. The simplest correct answer is a lock around the whole cache, most cleanly as a decorator (Chapter 13) so the single-threaded class stays simple and testable:

public final class SynchronizedCache<K, V> implements Cache<K, V> {
	private final Cache<K, V> inner;
	private final ReentrantLock lock = new ReentrantLock();

	public Optional<V> get(K key) { lock.lock(); try { return inner.get(key); } finally { lock.unlock(); } }   // yes, get too
	public void put(K key, V value) { lock.lock(); try { inner.put(key, value); } finally { lock.unlock(); } }
	// remove, size: same pattern
}

One lock is correct and fast enough for many services, since each operation is a few pointer updates. When it becomes a bottleneck, there are two classic next steps. Lock striping: split the cache into N segments by key hash, each an independent LRU with its own lock; contention drops by roughly N, at the cost of eviction being LRU per segment rather than globally. Buffered access records: serve reads from a concurrent hash map without locking, append “key was read” to a buffer, and replay the buffer into the policy in batches under a lock; recency becomes slightly delayed, which barely matters for hit rate.

🧠
How production caches bend the textbook

Caffeine, the widely used Java caching library, uses the buffered approach: reads hit a concurrent hash map, and access events go into striped ring buffers that are drained into the eviction policy under a lock, so reads rarely contend. Its policy, W-TinyLFU, pairs a small LRU window with a frequency-based main area and admits a new key only if an approximate frequency sketch says it's more popular than the would-be victim, combining LRU's responsiveness with LFU's scan resistance. Redis, with maxmemory set, offers LRU and LFU eviction policies (allkeys-lru, allkeys-lfu and others), but approximates both by sampling a handful of keys and evicting the best candidate among them, rather than maintaining an exact list; its LFU uses a small probabilistic counter per key that decays over time. Exact O(1) structures are the right interview answer; approximations are what scale buys you.

⚠️
Common mistakes
  • A singly linked list, or an ArrayList for order: removal becomes O(n).
  • Forgetting to store the key in the node, so eviction can't remove the map entry and the map leaks.
  • Updating an existing key without moving it, or treating an update as an insert and evicting unnecessarily.
  • A read-write lock with get under the read lock: concurrent hits corrupt the list.
  • Welding recency into the cache so LFU needs a rewrite. Keep eviction behind an interface.
  • LFU without tie-breaking or aging, so eviction order is arbitrary and old favourites never leave.

Interview drill

Explain it simply: How do you get O(1) get and put in an LRU cache?

How a strong answer sounds
A hash map from key to a node in a doubly linked list ordered by recency. get finds the node through the map and moves it to the front, which is O(1) because the node has prev and next pointers. put either updates and moves an existing node, or, if full, removes the node before the tail sentinel, deletes its key from the map (the node stores the key for this), and inserts the new node at the front. Sentinels remove edge cases. In Java, LinkedHashMap in access order with removeEldestEntry gives the same thing.

Deeper: Now add a loader: get(key, loader) computes missing values, and 200 threads miss the same key at once. What happens, and how do you fix it?

How a strong answer sounds
Naively all 200 threads miss, all call the loader, and the database gets 200 identical queries: a cache stampede. Fix it by caching the in-flight computation, not just the result: keep a ConcurrentHashMap<K, CompletableFuture<V>> of pending loads, and use computeIfAbsent so exactly one thread creates the future and runs the loader while the others wait on the same future. When it completes, store the value in the cache and remove the pending entry; if it fails, remove the pending entry so a later call retries, rather than caching the failure forever. The loader runs outside the cache's lock, so a slow database doesn't block hits on other keys. This is what Caffeine's LoadingCache does.

🧠 Key takeaways

  • O(1) LRU = hash map to nodes + doubly linked list in recency order, with sentinels, and keys stored in nodes.
  • LinkedHashMap in access order is the built-in version; build the explicit one in the interview.
  • Split storage from eviction: BoundedCache plus an EvictionPolicy strategy makes LRU, LFU and FIFO interchangeable.
  • O(1) LFU uses frequency buckets and a minimum-frequency pointer; it resists scans but needs aging.
  • In LRU even get mutates state, so every operation needs the lock; a read-write lock doesn't help.
  • Beyond one lock: striping by key, or buffering access records as production caches do.

Check your understanding

Why must the LRU list be doubly linked?

Unlinking needs the previous node. With a prev pointer that's O(1); in a singly linked list it's a search.

Why does each list node store its key as well as its value?

Eviction starts from the list, not the map. Without the key, the map entry for the evicted node would leak.

Why doesn't a ReadWriteLock, with get under the read lock, make an LRU cache thread-safe?

In LRU, get is a write to the ordering. Every operation needs exclusive access, or reads must be recorded and applied later under a lock.

A nightly report reads every product once. Which policy best protects the cache's usual hot keys?

A scan makes every scanned key “most recently used”, flushing LRU. LFU sees each scanned key used once and keeps the frequently used ones.

In the Strategy-based design, what does BoundedCache decide, and what does the EvictionPolicy decide?

Storage and capacity belong to the cache; ordering and victim choice belong to the policy. Swapping policies never touches the cache.
