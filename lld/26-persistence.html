Persistence: Repository, DAO & Unit of Work

Your domain classes enforce the rules: an order's total matches its lines, a paid order can't be edited. The database has to store those objects without breaking the rules on the way in or out. This chapter is about the seam between the two: repositories that let the domain pretend it lives in a collection, mappers that turn aggregates into rows, and transactions that make a whole change land or none of it.

  • Explain what a Unit of Work tracks and why it writes in one transaction
  • Place the transaction boundary on the use case, and prevent lost updates with a version column
  • Write an in-memory repository that tests can trust

DAO vs Repository

Both hide SQL behind an interface, but they face different ways. A DAO (Data Access Object) is shaped like the database: one per table, with methods that insert, update and delete rows. A repository is shaped like the domain: one per aggregate (a cluster of objects that change together, like an order and its lines), with methods that read like a collection: find this order, save this order. The domain and the application services talk to repositories; DAOs, if you have them at all, sit underneath a repository's implementation.

// Domain-facing: no SQL types, no table names, one per aggregate.
public interface OrderRepository {
	Optional<Order> findById(OrderId id);
	List<Order> findOpenFor(CustomerId customer);   // named queries, not a generic filter language
	void save(Order order);                          // insert or update the whole aggregate
}

Notice what's missing: no updateTotal, no deleteLine. Those would let a caller change part of an order behind the domain's back and store a total that doesn't match the lines. The only way to change an order is through Order's own methods, and the only way to persist it is to save all of it.

Mapping objects to tables

An aggregate rarely fits one table. An Order with a list of OrderLines becomes an orders row plus order_lines rows keyed by order_id. Value objects usually become columns: Money becomes total_cents and currency, an enum becomes a string (not its ordinal, which breaks when someone reorders the constants). Put this translation in a mapper next to the repository implementation, so the domain classes carry no annotations and no knowledge of column names:

record OrderRow(long id, String status, long totalCents, String currency, long version) {}
record LineRow(long orderId, String sku, int qty, long unitCents) {}

final class OrderMapper {
	OrderRow toRow(Order o) {
		return new OrderRow(o.id().value(), o.status().name(), o.total().cents(), o.total().currency().getCurrencyCode(), o.version());
	}
	Order toDomain(OrderRow r, List<LineRow> lines) {
		return Order.rehydrate(new OrderId(r.id()), OrderStatus.valueOf(r.status()),
			lines.stream().map(this::toLine).toList(), r.version());   // rehydrate re-checks invariants
	}
}

Order.rehydrate is a factory (Chapter 10) for rebuilding an existing order from storage: unlike the “place a new order” constructor it takes an id and a version, and it still validates, so corrupt rows fail loudly on load rather than spreading. The cost of this separation is some boilerplate; the benefit is that you can change a column, or the whole database, without touching the domain.

Unit of Work and transactions

A use case often changes several rows: edit one line, remove another, add a third, update the total. If each change is written the moment it's made, a failure halfway leaves the database holding a mix of old and new: lines that no longer add up to the stored total. A Unit of Work keeps a list of what the use case created, changed and removed, and at the end writes it all inside one database transaction, so either every change lands or none does.

You rarely write a Unit of Work by hand in Java. JPA's persistence context is one: every entity loaded through an EntityManager is tracked, changes are detected at flush time, and the SQL runs inside the surrounding transaction. What you do decide is where the transaction starts and ends. The right place is the application service method that runs one use case, not each repository call:

public final class EditOrderService {
	private final OrderRepository orders;
	private final Transactions tx;                 // or @Transactional on the method in Spring

	public void edit(OrderId id, OrderEdit edit) {
		tx.run(() -> {                                 // one use case = one transaction
			Order order = orders.findById(id).orElseThrow(() -> new OrderNotFound(id));
			order.apply(edit);                           // domain rules: status, quantities, total
			orders.save(order);                         // version-checked update
		});
		// Emails, payment calls and other remote work go after the commit, never inside it.
	}
}

Two rules follow. Keep remote calls out of the transaction: holding row locks and a pooled connection while waiting for a payment provider (Chapter 25) turns a slow partner into a stalled database. And prefer one aggregate per transaction; if a use case must change two aggregates, that's a signal to reconsider the boundaries, which is where Chapter 27 picks up.

Optimistic locking: lost updates between requests

A transaction protects one use case from its own partial failure. It doesn't stop two users from each loading version 3 of an order, editing it in their browsers for a minute, and saving in turn, with the second save quietly overwriting the first. Holding a database lock for that minute isn't an option. Instead, add a version column and make every update conditional on it:

UPDATE orders SET total_cents = ?, status = ?, version = version + 1
WHERE id = ? AND version = ?      -- the version this request loaded
-- 0 rows updated → someone saved in between: roll back, throw ConcurrentUpdateException

JPA does this for you when an entity has a field annotated @Version: the update includes the version in its WHERE clause and a mismatch throws OptimisticLockException. It's the right default whenever conflicts are rare; pessimistic locking (SELECT … FOR UPDATE) is for short, hot, high-conflict rows, and even then only inside a short transaction.

In-memory repositories for tests

Because the domain only knows the OrderRepository interface, tests of services can use an in-memory implementation and run in milliseconds. The trap is aliasing (P1): if the fake stores the very object you passed in, a test that forgets to call save still passes, because the “stored” order is the one you mutated. Copy on the way in and on the way out, as a database effectively does:

public final class InMemoryOrderRepository implements OrderRepository {
	private final Map<OrderId, Order> store = new ConcurrentHashMap<>();

	public Optional<Order> findById(OrderId id) { return Optional.ofNullable(store.get(id)).map(Order::copy); }

	public void save(Order o) {
		store.compute(o.id(), (id, cur) -> {                                  // same version rule as the database
			if (cur != null && cur.version() != o.version()) throw new ConcurrentUpdateException(id);
			return o.copyWithVersion(o.version() + 1);
		});
	}
	// findOpenFor: filter store.values(), copying each result
}

To keep the fake honest, write the repository's tests once as an abstract contract test and run it against both implementations: the in-memory one, and the JDBC one against a real database in a container. If the fake passes the same tests as the real thing, service tests that use it are trustworthy. Chapter 28 covers fakes in more depth.

🧠
JPA is these patterns, packaged

In a typical Spring Boot service, interface OrderRepository extends JpaRepository<OrderEntity, Long> gets its implementation generated at startup; the EntityManager's persistence context is the Unit of Work, comparing loaded entities against a snapshot to find dirty ones; @Transactional on a service method draws the transaction boundary; and @Version adds optimistic locking. Knowing the patterns underneath explains its classic surprises: a change to a loaded entity is saved even though nobody called save (dirty checking), and looping over orders to read each one's lazy lines issues one query per order (the “N+1 queries” problem), which a fetch join or a dedicated query fixes.

⚠️
Common mistakes
  • A repository per table. OrderLineRepository lets callers edit lines without the order checking its total. One repository per aggregate.
  • Persistence leaking into the domain: ResultSet, table names or SQL exceptions in service or domain code. Translate at the repository.
  • Transactions per repository call instead of per use case, so a multi-step change can half-succeed.
  • Remote calls inside a transaction, holding locks and a connection while a partner is slow.
  • No version column, so concurrent edits silently overwrite each other.
  • A generic Repository<T> with findAll(Predicate) that loads the table into memory, or a query-builder that exposes SQL shape to callers. Add named query methods instead.
  • An in-memory fake that stores references, so tests pass without ever saving.

Interview drill

Explain it simply: What's the difference between a DAO and a repository?

How a strong answer sounds
A DAO mirrors the database: one per table, with row-level insert, update and delete. A repository mirrors the domain: one per aggregate, with collection-like methods such as findById and save that take and return whole domain objects. The domain talks to repositories, so it can only persist a complete, valid aggregate; DAOs, if used, are an implementation detail underneath.

Deeper: In your parking-lot design, two requests try to take the last spot at the same time. How does the persistence layer stop both succeeding?

How a strong answer sounds
Each request runs as one transaction in the application service: load the lot or spot, call the domain method that assigns it, save. The save is a conditional update: either a version column (WHERE id = ? AND version = ?) or a state check (WHERE id = ? AND status = 'FREE'). The first commit updates one row; the second updates zero, so its repository throws a conflict, the transaction rolls back, and the service reports “lot full” or retries on fresh data. A unique constraint on active assignments per spot is a good safety net. And the in-memory repository used in tests enforces the same version rule, so the race is testable without a database.

🧠 Key takeaways

  • DAOs are shaped like tables; repositories are shaped like aggregates. The domain sees only repositories.
  • A repository saves and loads whole aggregates, so invariants can't be bypassed through storage.
  • Mappers translate aggregates to rows and back; domain classes stay free of SQL and annotations, and rehydration still validates.
  • A Unit of Work collects changes and writes them in one transaction: all or nothing.
  • Draw the transaction around the use case in the application service, with no remote calls inside it.
  • A version column turns silent lost updates between requests into detectable conflicts.
  • In-memory repositories must copy objects and share a contract test with the real implementation.

Check your understanding

An order has lines stored in a separate table. How many repositories should the domain see?

Repositories are per aggregate. A separate line repository would let callers change lines without the order recomputing and checking its total.

A use case runs four UPDATE/INSERT/DELETE statements, each auto-committed. The connection drops after the second. What's in the database?

Auto-commit makes each statement its own transaction. Only wrapping all four in one transaction, as a Unit of Work does, gives all-or-nothing.

Where should the transaction boundary usually be?

The use case is the unit that must succeed or fail as a whole. Per-repository transactions let a multi-step use case half-succeed.

What does UPDATE … WHERE id = ? AND version = ? updating 0 rows tell you?

That's optimistic locking: the version moved on since you read it. Roll back and report a conflict, or reload and reapply the change.

Why should an in-memory repository copy objects in save and findById?

Storing references lets later mutations appear “saved” without a save call, hiding bugs the real database would expose.
