Strategy

If you remember one pattern from this course, make it this one. Strategy puts a family of interchangeable algorithms behind one interface, so the code that uses an algorithm doesn't know or care which one it has. It's how load balancers pick a server, how rate limiters count, how prices are calculated, and how List.sort knows what order you want. It is also the shape of almost every “now support X too” follow-up in an LLD interview.

  • Replace a growing if/switch over algorithms with a Strategy interface
  • Write strategies as classes or as lambdas, and know when each fits
  • Choose a strategy at run time from configuration or per request
  • Keep stateful strategies thread-safe
  • Tell Strategy apart from State and Template Method

From an if-chain to a strategy

A load balancer receives requests and forwards each to one of several backend servers. How it chooses is a policy: round robin, random, least busy, weighted by capacity, or by a hash of the client so the same client always lands on the same server. The first version usually looks like this:

Backend pick(List<Backend> backends, Request req) {
	if (policy.equals("round_robin")) { return backends.get(next++ % backends.size()); }
	else if (policy.equals("random")) { return backends.get(random.nextInt(backends.size())); }
	else if (policy.equals("least_conn")) { /* 12 lines */ }
	else if (policy.equals("ip_hash")) { /* 8 lines */ }
	throw new IllegalArgumentException(policy);
}

Every new policy edits this method (breaking open/closed), the fields each policy needs pile up in one class (next for one, random for another), and no policy can be tested on its own. Strategy pulls each branch out into its own class behind an interface:

The strategy interface, three strategies, and the context that uses one
public interface LoadBalancingStrategy {                          // the strategy
	Backend pick(List<Backend> healthy, Request req);
}

public final class RoundRobin implements LoadBalancingStrategy {
	private final AtomicInteger next = new AtomicInteger();          // its own state, thread-safe
	public Backend pick(List<Backend> healthy, Request req) {
		return healthy.get(Math.floorMod(next.getAndIncrement(), healthy.size()));
	}
}

public final class LeastConnections implements LoadBalancingStrategy {
	public Backend pick(List<Backend> healthy, Request req) {
		return Collections.min(healthy, Comparator.comparingInt(Backend::activeConnections));
	}
}

public final class ClientHash implements LoadBalancingStrategy {         // same client, same server
	public Backend pick(List<Backend> healthy, Request req) {
		return healthy.get(Math.floorMod(req.clientIp().hashCode(), healthy.size()));
	}
}

public final class LoadBalancer {                                   // the context
	private final BackendPool pool;
	private final LoadBalancingStrategy strategy;
	public LoadBalancer(BackendPool pool, LoadBalancingStrategy strategy) { … }

	public Response forward(Request req) {
		List<Backend> healthy = pool.healthy();                     // the context owns everything else:
		if (healthy.isEmpty()) return Response.status(503);          // health checks, errors, forwarding…
		return strategy.pick(healthy, req).send(req);            // …and delegates only the choice
	}
}
The division of labour: the context handles the common work and the edge cases (an empty pool returns 503 before any strategy runs, so strategies can assume a non-empty list). Each strategy handles one policy and owns its own state. Adding weighted round robin is one new class; nothing above changes.

Strategies as lambdas, and choosing at run time

When a strategy is a single method with no state of its own, a lambda is a complete implementation. This is why Java's functional interfaces are, in effect, ready-made strategy interfaces:

LoadBalancingStrategy first = (healthy, req) -> healthy.get(0);                       // for a primary/standby pair
LoadBalancingStrategy random = (healthy, req) -> healthy.get(ThreadLocalRandom.current().nextInt(healthy.size()));

// Chosen from configuration at startup: a registry of strategy factories (Chapter 10)
Map<String, Supplier<LoadBalancingStrategy>> strategies = Map.of(
	"round_robin", RoundRobin::new,
	"least_conn",  LeastConnections::new,
	"ip_hash",     ClientHash::new);
LoadBalancer lb = new LoadBalancer(pool, strategies.get(config.policy()).get());

Prefer a named class when the strategy has state (RoundRobin's counter), needs its own tests, or would be a long lambda. Prefer a lambda when it's a one-liner. Strategies can also be chosen per call rather than at startup: a pricing service might pick WeekendPricing or SurgePricing for each ride, based on the time and demand. The shape is the same; only who makes the choice, and when, differs.

One detail that's easy to miss: a strategy object is usually shared by every request thread. A stateless strategy is automatically thread-safe. A stateful one, like round robin, must protect its state; a plain int next with next++ would lose increments under load and skew the distribution. AtomicInteger fixes it, and Math.floorMod keeps the index valid even after the counter overflows past Integer.MAX_VALUE and turns negative.

The strategy you use every day: Comparator

List.sort(Comparator) is Strategy in its purest form. The sorting algorithm is fixed, written once in the JDK; the ordering is a strategy you pass in. The Comparator combinators build strategies out of smaller ones:

orders.sort(Comparator.comparing(Order::priority)            // most urgent first…
	.thenComparing(Order::placedAt)                           // …then oldest first…
	.thenComparing(Order::id));                               // …then a stable tie-break

PriorityQueue<Job> queue = new PriorityQueue<>(Comparator.comparing(Job::runAt));   // same strategy, a different context

nginx's load-balancing methods

nginx, one of the most widely used web servers and reverse proxies, distributes requests across an upstream group with round robin by default. One directive switches the policy: least_conn for least connections, ip_hash to keep each client on the same server, or hash $request_uri consistent for consistent hashing on any key. Server weights adjust round robin for machines of different sizes. The proxying, health checks and retries around the choice stay exactly the same. That's the Strategy pattern expressed as configuration, and it's a good example to mention when an interviewer asks for real-world usage.

⚠️
Common mistakes
  • Keeping the switch and calling it Strategy. If the context still branches on the policy name, nothing was gained.
  • Strategies that reach back into the context's internals. Pass them what they need as parameters.
  • Unsafe shared state in a strategy. One instance serves every thread: use atomics, or keep strategies stateless.
  • Letting every strategy handle edge cases. An empty backend list is the context's job, handled once before delegating.
  • Strategy for a choice that never varies. One algorithm with no second in sight doesn't need an interface (YAGNI).
  • Hard-coding the choice deep inside the context. Choose in the composition root or a selector, so tests can pass any strategy.

Interview drill

Explain it simply: What is the Strategy pattern, and why use it instead of a switch?

How a strong answer sounds
Strategy puts each interchangeable algorithm in its own class behind one interface, and the context that needs the algorithm holds a reference to that interface. Compared with a switch, adding an algorithm is a new class rather than an edit to tested code, each algorithm keeps its own state and gets its own tests, and the choice can be made at startup or per request. Comparator passed to List.sort is the everyday example.

Deeper: Design the server-selection part of a load balancer that must support round robin, least connections and client affinity, and switch between them by config.

How a strong answer sounds
A LoadBalancingStrategy interface with pick(List<Backend> healthy, Request req), and one class per policy. The LoadBalancer context gets healthy backends from the pool, returns 503 itself if there are none, and delegates only the choice. Round robin keeps an AtomicInteger and uses floorMod so overflow can't produce a negative index; least connections picks the minimum active count; affinity hashes the client key. A registry maps config names to strategy factories at startup. I'd note that simple modulo hashing reshuffles most clients when a backend leaves, so for real affinity I'd use consistent hashing.

🧠 Key takeaways

  • Strategy: one interface for a family of interchangeable algorithms; the context holds one and delegates the decision.
  • It replaces a growing if/switch: new algorithm, new class; the context is closed to that change.
  • The context owns common work and edge cases; strategies own one policy and their own state.
  • Lambdas are strategies when they're short and stateless; named classes when they have state or need tests.
  • Shared strategies must be thread-safe: atomics for counters, floorMod for wraparound.
  • Strategy is chosen by the client; State changes itself; Template Method varies steps by inheritance.

Check your understanding

What does the Strategy pattern encapsulate?

Strategy makes the algorithm a swappable part. The other options describe Abstract Factory, State and Proxy.

With Strategy in place, what does adding weighted round robin require?

The context and existing strategies are closed to this change; the new policy is an addition, plus one line in the selection wiring.

A shared RoundRobin strategy uses private int next; and next++. What goes wrong under heavy concurrent load?

next++ is a read, an add and a write; two threads can read the same value. An AtomicInteger.getAndIncrement() does it as one step. floorMod then handles the overflow to negative numbers.

One backend becomes three times slower than the others. Which strategy adapts on its own?

Round robin, random and hashing ignore load, so the slow server keeps getting its full share and its queue grows. Least connections reacts to the queue.

How does Strategy differ from State?

Both hold an interface and delegate. The difference is who changes it: with Strategy, the outside chooses; with State, the object moves itself from state to state as events happen.
