Case Study: Ride-Hailing (LLD)

The last case study pulls the course together. A ride-hailing core has a trip that moves through a strict lifecycle (State), drivers who must never be offered two trips at once (atomic claims), a matching policy and a pricing policy that the business will keep changing (Strategy), and a stream of events that riders, drivers, payments and analytics all react to (Observer). Chapter 27 sketched its aggregate boundaries; this chapter designs the classes, and the simulator shows why “nearest available driver” is not the best matching rule.

  • Scope the core use cases and the API between apps and the dispatch service
  • Model riders, drivers and trips, with the trip as an explicit state machine
  • Offer trips to drivers safely, with timeouts and fallbacks, and compare matching strategies
  • Quote and compute fares with a pricing policy and surge multiplier
  • Publish trip events to observers without coupling the core to every consumer

Requirements and API

Clarify: a rider requests a ride from a pickup to a drop-off and sees an upfront price; the system offers the trip to a suitable nearby driver, who accepts or declines within a few seconds; the rider sees the driver approach; the trip starts on pickup and ends at drop-off; the fare is charged; either side can cancel, with rules and fees; drivers go online and offline and stream their location. Out of scope: the routing engine and maps (an ETA service interface), payments internals (a gateway), shared rides and scheduled rides (follow-ups).

public interface RideService {

}

public interface DriverService {
	void goOnline(DriverId d); void goOffline(DriverId d);

}

Entities and trip lifecycle

Three aggregates, each guarding its own invariant, referring to one another by id (Chapter 27). The Trip owns the lifecycle: which transitions are legal, who may cancel when, and what the fare is. The Driver owns availability: a driver is in at most one offer or trip at a time. The Rider owns profile and payment method, and has at most one active trip. Locations, quotes and fare breakdowns are value objects.

public final class Trip {                                              // aggregate root
	private final TripId id; private final RiderId rider; private final FareQuote quote;
	private TripState state = TripState.MATCHING;
	private DriverId driver;
	private final List<TripEvent> events = new ArrayList<>();
	private long version;

	public void assign(DriverId d, Instant now) {
		require(TripState.MATCHING);
		driver = d; state = TripState.DRIVER_ASSIGNED;
		events.add(new DriverAssigned(id, d, now));
	}

	public CancellationFee cancelByRider(Instant now, CancellationPolicy policy) {
		require(TripState.MATCHING, TripState.DRIVER_ASSIGNED, TripState.DRIVER_ARRIVED);
		CancellationFee fee = policy.feeFor(this, now);                     // Strategy: grace periods, no-show rules
		state = TripState.CANCELLED;
		events.add(new TripCancelled(id, Party.RIDER, fee, now));
		return fee;
	}

	private void require(TripState... allowed) {
		if (!List.of(allowed).contains(state)) throw new IllegalTripTransition(id, state);
	}
	// arrived(), start(), complete(distance, duration, fare): same pattern — check state, change it, record an event.
}

Driver matching strategy

Matching has three separable steps. Find candidates: available drivers near the pickup, from a spatial index (a grid of cells, geohash prefixes, or hexagons) that answers “drivers in these cells” without scanning every driver. Rank them: a MatchingStrategy, from straight-line distance up to real road ETAs from a routing service. Offer: claim the top driver atomically and send the offer with a timeout; on decline or timeout, release the driver and try the next.

public interface MatchingStrategy {
	List<DriverId> rank(Trip trip, List<DriverSnapshot> nearby);             // best first
}

final class Dispatcher {
	void offerNext(Trip trip, Iterator<DriverId> ranked) {
		while (ranked.hasNext()) {
			Driver d = drivers.get(ranked.next());
			if (!d.tryReserve(trip.id())) continue;                          // CAS AVAILABLE → OFFERED; lost the race: next
			Offer o = offers.create(trip.id(), d.id(), clock.instant().plus(OFFER_TTL));
			push.send(d.id(), o);
			scheduler.schedule(() -> onTimeout(o, ranked), OFFER_TTL);          // Chapter 35
			return;
		}
		trips.update(trip.id(), t -> t.noDrivers(clock.instant()));         // widen the radius first, in practice
	}

	void onResponse(Offer o, boolean accept) {
		if (!offers.close(o.id())) return;                                // already timed out: ignore the late answer
		if (accept) trips.update(o.trip(), t -> t.assign(o.driver(), clock.instant()));
		else { drivers.get(o.driver()).release(o.trip()); offerNext(trips.get(o.trip()), o.remaining()); }
	}
}

Two races are handled by design. A driver can't receive two offers, because tryReserve is a compare-and-set from AVAILABLE (the same idea as a parking spot in Chapter 40). And an accept that arrives after the timeout can't assign a trip that has moved on, because closing the offer is itself atomic and only the first of “accepted” or “timed out” wins.

The ranking policy matters more than it looks. Matching each request to its nearest free driver as it arrives is greedy: an early request can take the only driver who was close to a later one, leaving that rider a long wait. Batching collects the requests from a short window (a second or two) and assigns them together, minimising the total pickup time across the batch, which is an assignment problem with a well-known optimal solution (the Hungarian algorithm; for a handful of requests, trying the permutations is fine).

Pricing and surge

Pricing changes more often than any other part of the system, by city, by product and by promotion, so it's a pipeline of small strategies: a FarePolicy computes the base price from estimated distance and time; a SurgePolicy computes a multiplier from demand and supply in the pickup zone; promotions adjust the result. The rider accepts a quote (a value object with its own id and an expiry) before requesting, and the trip stores it, so the price the rider agreed to is the price charged under upfront pricing, even if surge changes a second later. The final fare is computed at completion from the quote or from actual distance and time, depending on the product.

public record FareQuote(QuoteId id, Money base, BigDecimal surge, Money total, Instant expiresAt) {}

final class StandardFare implements FarePolicy {
	public Money base(RouteEstimate r, CityRates c) {
		Money m = c.flagFall().plus(c.perKm().times(r.km())).plus(c.perMinute().times(r.minutes()));
		return Money.max(m, c.minimumFare());
	}
}

final class SupplyDemandSurge implements SurgePolicy {
	public BigDecimal multiplier(ZoneStats z) {
		double ratio = z.openRequests() / (double) Math.max(1, z.availableDrivers());
		double m = Math.min(CAP, Math.max(1.0, ratio));
		return BigDecimal.valueOf(m).setScale(1, RoundingMode.HALF_UP);    // shown to the rider as e.g. 1.5×
	}
}

Observers for trip updates

Many parts of the system care about a trip: the rider's app (driver on the way, arrived), the driver's app, the ETA display, payments (charge on completion), receipts, ratings prompts, fraud checks and analytics. If the trip or the dispatcher called each of them, every new consumer would mean editing the core. Instead the Trip aggregate records domain events, they're published after the state change commits (through an outbox, Chapter 27), and each consumer subscribes to the ones it needs (Observer). Location updates are the exception worth calling out: they arrive every few seconds per driver, so they go to a separate, lossy, latest-value-wins stream rather than the durable event log.

🧠
Hexagons and batches in production

Two ideas in this chapter come straight from how ride-hailing companies describe their systems. For the spatial index, Uber open-sourced H3 in 2018, a hierarchical grid of hexagonal cells covering the globe; hexagons are used because every neighbour is the same distance from the centre, which makes “nearby drivers” and zone-level surge calculations cleaner than with square cells. For matching, ride-hailing companies including Uber and Lyft have written publicly about moving beyond “nearest available driver” toward matching requests in batches to improve pickup times across the whole marketplace, the same effect you can see in the simulator's total and worst pickup distances.

⚠️
Common mistakes
  • Trip status as a free-form string any service can set, instead of transitions the Trip enforces.
  • Offering one driver two trips because availability is checked, then set, non-atomically.
  • No offer timeout, or honouring an accept that arrives after the offer moved on.
  • Scanning every driver to find nearby ones instead of a spatial index.
  • Recomputing the price at completion when the rider agreed to an upfront quote.
  • The trip calling payments, notifications and analytics directly; publish events instead.
  • Putting location pings in the durable event log, flooding it with data only the latest value of which matters.

Interview drill

Explain it simply: How do you make sure a driver isn't assigned two trips at once?

How a strong answer sounds
Driver availability is the Driver aggregate's invariant. Offering a trip first calls tryReserve, a compare-and-set from AVAILABLE to OFFERED for that trip; if two dispatchers race for the same driver, only one CAS succeeds and the other moves to its next candidate. Accepting moves the driver to EN_ROUTE, and declining or timing out releases them back to AVAILABLE. With a database it's a conditional update on the driver row, WHERE status = 'AVAILABLE', checking one row was updated.

Deeper: Add shared rides (pooling): two riders going the same way share a car. What changes in your design?

How a strong answer sounds
The unit a driver serves stops being a single trip. I'd introduce a Route (or ride) aggregate on the driver side: an ordered list of stops (pickups and drop-offs) for one or more trips, with capacity and detour limits as its invariants. Each rider still has their own Trip with its own lifecycle and fare, now referencing a route id. Matching becomes “which existing route can absorb this request within the detour limit, or which free driver starts a new one”, a new MatchingStrategy that scores insertion positions. Pricing gets a pooled FarePolicy with a discount. Events stay per trip, so the rider apps and payments don't change. The biggest new rule is ordering: a stop can't be dropped off before it's picked up, which the Route enforces when inserting stops.

🧠 Key takeaways

  • Trip, Driver and Rider are separate aggregates referenced by id; the Trip owns an explicit lifecycle.
  • Reserve drivers with a compare-and-set, offer with a timeout, and let only the first of accept or timeout win.
  • Find candidates with a spatial index; rank with a matching strategy; batching beats first-come nearest-driver.
  • Price with fare and surge strategies; the rider agrees to a quote with an expiry, which the trip keeps.
  • Publish trip events to subscribers through an outbox; keep high-frequency locations on a separate, lossy stream.
  • Every piece is a pattern from earlier in the course, combined deliberately.

Check your understanding

Why can “assign each request to its nearest free driver, in order” produce worse pickups than batching?

Greedy decisions are locally best but globally poor. Batching over a short window minimises total pickup time across requests.

A driver accepts an offer 2 seconds after it timed out and was sent to someone else. What should happen?

Closing an offer is atomic, and only the first of “accepted” or “timed out” wins.

Why does the trip store the fare quote the rider accepted?

A quote is a value object with an id and an expiry: the contract between rider and service for this trip.

How should the payments service learn that a trip has completed?

Events decouple the core from consumers; the key makes redelivered events harmless.

Why keep driver location updates out of the durable trip event log?

Business events (assigned, started, completed) must be durable; high-frequency telemetry needs freshness, not every value.
