Thread-Safe Class Design

Almost every LLD question ends with the same follow-up: “now two requests arrive at once.” A web server runs each request on its own thread, so any object shared between requests, like a rate limiter, a seat map or a cache, is being used by many threads at the same moment. A class is thread-safe when its invariants hold no matter how those threads interleave, without callers having to coordinate. This chapter is the toolkit for that, from the cheapest option (don't share) to the most expensive (a lock), and the two classic bugs you'll be asked to spot: lost updates and deadlock.

  • Explain the three root problems: atomicity, visibility and ordering
  • Choose the cheapest safe strategy: confinement, immutability, concurrent building blocks, then locks
  • Use synchronized, ReentrantLock, atomics and volatile for what each is for
  • Make compound actions atomic, including on concurrent collections
  • Prevent deadlock with a global lock order and timeouts

Three ways shared state goes wrong

Every concurrency bug in ordinary application code comes from one of three problems:

ProblemWhat happensExampleFixed by
AtomicityA multi-step operation is interrupted halfway by another threadbalance += amount is read, add, write: two threads can both read 100 and both write their own resultLocks, atomics, single atomic operations
VisibilityA write by one thread is never seen, or seen late, by anotherA running = false flag that a worker thread keeps reading as true from a cached valuevolatile, locks, atomics, immutable publication
OrderingThe compiler or CPU reorders writes, and another thread sees them in the wrong orderA reference published before the object's fields are set (Chapter 9)The same tools: they all create “happens-before” edges

The Java Memory Model defines the rules with one idea, happens-before: if action A happens-before action B, B sees A's effects. Releasing a lock happens-before the next acquisition of the same lock; a write to a volatile field happens-before every later read of it; Thread.start() happens-before everything in the started thread. Without such an edge, the JVM is free to let threads disagree about what memory contains.

The cheapest safe strategy first

Locks are the most expensive and the most error-prone tool, so reach for them last. Work down this ladder and stop at the first rung that fits:

Confinement is underrated. In a web service, the request object, the parsed body, the list you build while handling the request and the response all belong to one request thread. None of them needs any synchronisation. The shared parts are usually few: caches, rate limiters, connection pools, in-memory stores. Those are the classes to design carefully.

The tools, and what each one is for

A per-client rate limiter: building blocks plus one small lock
public final class RateLimiter {
	private final ConcurrentHashMap<ClientId, TokenBucket> buckets = new ConcurrentHashMap<>();
	private final LongAdder rejected = new LongAdder();              // a hot counter many threads bump
	private final Clock clock;
	private final int capacity, refillPerSecond;

	public boolean tryAcquire(ClientId client) {
		TokenBucket b = buckets.computeIfAbsent(client,                  // atomic: exactly one bucket per client
			c -> new TokenBucket(capacity, refillPerSecond, clock.millis()));
		boolean ok = b.tryAcquire(clock.millis());
		if (!ok) rejected.increment();
		return ok;
	}
	public long rejectedCount() { return rejected.sum(); }
}

final class TokenBucket {                                                  // from P2, now thread-safe
	private final Object lock = new Object();                              // private lock: no outsider can hold it
	private int tokens;              // guarded by lock
	private long lastRefillMillis;    // guarded by lock: one invariant, two fields, one lock

	boolean tryAcquire(long now) {
		synchronized (lock) {                                               // refill + check + decrement as one step
			refill(now);
			if (tokens == 0) return false;
			tokens--;
			return true;
		}
	}
}
Each tool doing its job: ConcurrentHashMap.computeIfAbsent creates each client's bucket exactly once; each bucket's two fields form one invariant, so one small lock guards both; the lock is per bucket, so different clients never wait for each other; and the rejection counter, bumped by every thread, uses LongAdder, which spreads contention across cells.

Compound actions are the trap

Using thread-safe parts doesn't make their combination thread-safe. Each call to a ConcurrentHashMap is atomic; two calls in a row are not:

// Racy even on a ConcurrentHashMap: two threads can both see "absent" and both put
if (!sessions.containsKey(token)) sessions.put(token, new Session(user));

// Atomic: the map runs the check and the insert as one operation per key
sessions.computeIfAbsent(token, t -> new Session(user));
viewCounts.merge(pageId, 1L, Long::sum);                             // atomic increment per key

The same rule applies to your own classes: every operation that reads state and then acts on it (check-then-act) or reads, computes and writes (read-modify-write) must happen inside one lock or one atomic call. That's why Chapter 7 preferred tryHold(seat) over isFree(seat) followed by hold(seat). And keep locked sections short. Never do network or disk I/O while holding a lock: every other thread that needs it waits for the slowest call in the system.

Deadlock, and how lock ordering prevents it

  
A deadlock is two or more threads each holding a lock the other needs, waiting forever. The classic case is a bank transfer that locks the source account and then the destination: one thread transfers A→B while another transfers B→A. Deadlock needs four conditions at once (named by Coffman in 1971): mutual exclusion, holding one lock while waiting for another, no forced release, and a circular wait. Break any one and deadlock is impossible. The practical ones to break:

  
    
    
  • Circular wait, with a global lock order. Always acquire locks in the same order, for example by account id. Then two transfers between the same accounts lock in the same order, and a cycle can't form.
    • 
    
  • No forced release, with timeouts. ReentrantLock.tryLock(50, MILLISECONDS) gives up and releases what it holds, so the transfer can retry or fail cleanly.
    • 
    
  • Hold-and-wait, with one lock. If the invariant allows it, guard both accounts with a single coarser lock. Simpler, less concurrent.
    • 
  


public void transfer(Account from, Account to, Money amount) {
	Account first = from.id().compareTo(to.id()) < 0 ? from : to;       // global order: lower id first
	Account second = first == from ? to : from;
	synchronized (first.lock()) {
		synchronized (second.lock()) {
			from.withdraw(amount);                                              // the invariant (total money) holds under both locks
			to.deposit(amount);
		}
	}
}

Finding a deadlock in production
When a Java service stops responding but its CPU is idle, take a thread dump: jstack <pid> or jcmd <pid> Thread.print. The JVM detects deadlocks among intrinsic and java.util.concurrent locks and prints a section headed “Found one Java-level deadlock”, listing each thread, the lock it holds and the lock it's waiting for. It's the fastest way to turn “the site is hung” into two stack traces pointing at the code that locks in inconsistent order. Thread dumps also show the more common production problem: hundreds of threads all BLOCKED on one lock that someone holds while making a slow network call.

  


  
⚠️
Common mistakes

    
    
      
  • count++ on a shared field, even a volatile one. It's three steps. Use an atomic or a lock.
    • 
      
  • Check-then-act across two thread-safe calls (containsKey then put). Use computeIfAbsent, putIfAbsent, merge.
    • 
      
  • Separate locks for fields in one invariant. Tokens and last-refill time must change together, under one lock.
    • 
      
  • I/O while holding a lock. Every waiting thread inherits the slowest call.
    • 
      
  • Locking on this or a public object. Outside code can take the same lock. Use a private final lock object.
    • 
      
  • Nested locks in inconsistent order. Pick a global order, or use tryLock with a timeout.

Interview drill

    
Explain it simply: What does it take to make a class thread-safe?

    
How a strong answer sounds
First I find which state is actually shared and mutable; everything confined to a request or immutable is already safe. For the rest, every invariant must hold under any interleaving, which means each check-then-act or read-modify-write happens atomically, and writes are visible to other threads. I use thread-safe building blocks where one variable or one map key is involved, like ConcurrentHashMap.computeIfAbsent, AtomicLong or LongAdder, and a small private lock where an invariant spans several fields, held briefly with no I/O inside.

    
Deeper: Your transfer method locks the source account then the destination, and the service occasionally hangs. What's happening and how do you fix it?

    
How a strong answer sounds
Two concurrent transfers in opposite directions each hold one account's lock and wait for the other's: a circular wait, so a deadlock. A thread dump would show it. The fix is a global lock order: always lock the account with the lower id first, regardless of direction, so both transfers try the same lock first and one simply waits. Alternatively, ReentrantLock.tryLock with a timeout lets a transfer back off and retry. I'd also keep the critical section to the two balance updates, with no I/O inside.

  


  

    
🧠 Key takeaways

    
    
      
  • Thread-safe means invariants hold under any interleaving without callers coordinating.
    • 
      
  • Three root problems: atomicity, visibility and ordering; the tools work by creating happens-before edges.
    • 
      
  • Climb the ladder: confine, then share immutable, then concurrent building blocks, then locks around multi-field invariants.
    • 
      
  • volatile is visibility only; atomics are single-variable; locks cover invariants across fields.
    • 
      
  • Compound actions must be one atomic step: computeIfAbsent, merge, tryAcquire; no I/O inside locks.
    • 
      
  • Prevent deadlock with a global lock order or tryLock timeouts; diagnose it with a thread dump.

Check your understanding

    


    

      
Two threads run balance += 50 on a shared long balance that starts at 100. What can the final balance be?

      

        
        
        
        
      

      
+= is read, add, write. An interleaving where both threads read 100 makes both write 150. A lock or AtomicLong.addAndGet makes it one step.

    


    

      
What does declaring a field volatile guarantee?

      

        
        
        
        
      

      
volatile fixes visibility and ordering for one field. It doesn't make read-modify-write sequences atomic; that needs an atomic class or a lock.

    


    

      
Why is if (!map.containsKey(k)) map.put(k, v); unsafe even with a ConcurrentHashMap?

      

        
        
        
        
      

      
Thread-safe parts don't make a thread-safe sequence. putIfAbsent or computeIfAbsent do the check and the insert as one atomic operation.

    


    

      
A token bucket has tokens and lastRefillMillis, which must change together. What's the right protection?

      

        
        
        
        
      

      
Atomics and volatile protect single variables. An invariant spanning two fields needs both updated inside one critical section.

    


    

      
Transfers lock the source account, then the destination. Two opposite transfers sometimes hang forever. Which fix removes the deadlock?

      

        
        
        
        
      

      
Deadlock needs a circular wait. A consistent lock order makes every transfer between two accounts try the same lock first, so a cycle can't form.
