Factory Method & Abstract Factory

Every new ConcreteClass() is a decision about which class to use, made at that exact spot in the code. Factories move that decision somewhere better: to a named method that can validate and cache, to a subclass, to a family of related objects that must match, or to a registry looked up at run time. This chapter covers all four, using code you already call every day: List.of, Duration.ofSeconds and JDBC's DriverManager.

  • Use static factory methods, and say what they can do that constructors can't
  • Recognise the GoF Factory Method, and its modern replacement: an injected factory
  • Design an Abstract Factory that keeps a family of objects consistent
  • Replace a switch over types with a registry of factories
  • Explain how JDBC picks a driver from a connection URL

Static factory methods

The smallest factory is a static method that returns an instance. You use dozens: List.of(…), Optional.empty(), Duration.ofSeconds(30), Instant.parse(…), Integer.valueOf(42). Effective Java's very first item recommends considering them instead of constructors, for four reasons a constructor can't match:

A static factory can…Example
Have a name that says what it buildsDuration.ofSeconds(30) vs Duration.ofMillis(30): two constructors with one long each couldn't coexist
Return an existing instance instead of a new oneInteger.valueOf(42) returns a cached object for values −128 to 127; Collections.emptyList() always returns the same list
Return any subtype, hiding the real classList.of(…) returns internal immutable list classes you never name
Parse and validate before an object existsHostAndPort.parse("db1:5432") can throw a clear error or return a normalised value
 
public record HostAndPort(String host, int port) {
	public static HostAndPort parse(String text) {                    // named, validating
		int colon = text.lastIndexOf(':');
		if (colon < 1) throw new IllegalArgumentException("expected host:port, got " + text);
		return new HostAndPort(text.substring(0, colon), Integer.parseInt(text.substring(colon + 1)));
	}
	public static HostAndPort localhost(int port) { return new HostAndPort("localhost", port); }
}

The naming conventions are worth following, because readers recognise them: of and valueOf (convert the arguments), from (convert another type), parse (from text), create or newX (always a new instance), getX or instance (may return a shared one).

Factory Method: let a subclass choose

The Gang of Four Factory Method is narrower: a class runs an algorithm that needs an object, but leaves which object to a method that subclasses override. The classic shape:

public abstract class ExportJob {
	public final void run(Report report) {                       // the fixed algorithm
		ReportFormatter f = createFormatter();                   // the factory method
		upload(report.name() + f.extension(), f.format(report));
	}
	protected abstract ReportFormatter createFormatter();
}
public final class CsvExportJob extends ExportJob {
	@Override protected ReportFormatter createFormatter() { return new CsvFormatter(); }
}

It works, and you'll see it in frameworks and older codebases. But it uses inheritance to make a choice that composition makes more flexibly (P5): one subclass per formatter, fixed at compile time. The modern version passes the choice in, either the formatter itself or a factory for it:

public final class ExportJob {
	private final Supplier<ReportFormatter> formatters;              // "a factory", as a functional interface
	public ExportJob(Supplier<ReportFormatter> formatters) { this.formatters = formatters; }
	public void run(Report report) { ReportFormatter f = formatters.get(); /* … */ }
}
new ExportJob(CsvFormatter::new);                                // chosen at wiring time

Pass a Supplier (a factory) rather than an instance when the job needs a fresh object each time: a formatter with per-run state, a parser that isn't thread-safe, one connection per task.

Abstract Factory: families that must match

Sometimes objects come in families that only work together. A service that runs on AWS uses S3 for blobs, SQS for queues and Secrets Manager for credentials. On Google Cloud, it's Cloud Storage, Pub/Sub and Secret Manager. Locally, in tests, it's the filesystem, an in-memory queue and environment variables. Mixing them, say S3 with Pub/Sub, is at best a configuration bug and at worst a data leak across clouds. An Abstract Factory is an interface with one creation method per product, and one implementation per family:

One factory per platform, one method per product
public interface Platform {                                    // the abstract factory
	BlobStore blobStore(String bucket);
	MessageQueue queue(String name);
	SecretStore secrets();
}

public final class AwsPlatform implements Platform {
	private final Region region;
	public AwsPlatform(Region region) { this.region = region; }
	@Override public BlobStore blobStore(String b) { return new S3BlobStore(region, b); }
	@Override public MessageQueue queue(String n) { return new SqsQueue(region, n); }
	@Override public SecretStore secrets() { return new AwsSecretsManager(region); }
}
public final class LocalPlatform implements Platform { /* LocalDiskStore, InMemoryQueue, EnvSecrets */ }

// Composition root: one decision picks the whole family
Platform platform = switch (config.cloud()) {
	case AWS   -> new AwsPlatform(config.region());
	case GCP   -> new GcpPlatform(config.project());
	case LOCAL -> new LocalPlatform(Path.of("/tmp/app"));
};
UploadService uploads = new UploadService(platform.blobStore("uploads"), platform.queue("thumbnails"));
What it guarantees: products always come from one family, because there's no way to get an S3 store and a Pub/Sub queue from the same Platform. Adding a cloud is one new class implementing every method. The switch over a closed enum in the composition root is fine (Chapter 3): it's the one place that knows the concrete families.

The trade-off: adding a new product (say, a Cache) means adding a method to Platform and to every implementation. Abstract Factory makes new families cheap and new products expensive. Use it when the family set grows more often than the product set.

Registries instead of switches

When implementations are chosen by a key at run time (a payment method, a file format, a notification channel) and new ones keep arriving, a registry of factories keeps the choosing code closed to change. Each implementation is registered once, usually in the composition root, and lookups fail fast with a useful message:

public final class GatewayRegistry {
	private final Map<String, Supplier<PaymentGateway>> factories = new HashMap<>();

	public void register(String method, Supplier<PaymentGateway> factory) {
		if (factories.putIfAbsent(method, factory) != null) throw new IllegalStateException("duplicate: " + method);
	}
	public PaymentGateway create(String method) {
		Supplier<PaymentGateway> f = factories.get(method);
		if (f == null) throw new IllegalArgumentException("unknown payment method '" + method + "'; known: " + new TreeSet<>(factories.keySet()));
		return f.get();
	}
}

JDBC takes the same idea one step further: drivers register themselves. Each driver JAR lists its driver class in a META-INF/services/java.sql.Driver file, and java.util.ServiceLoader finds and registers every one on the classpath. DriverManager.getConnection(url) then asks each registered driver whether it accepts the URL, and the first that does becomes the factory for your Connection. The Connection is itself a factory too: prepareStatement returns that driver's own PreparedStatement implementation, so the whole family always matches.

Test doubles for free with an Abstract Factory

A team building a video pipeline on AWS wanted integration tests that didn't touch AWS. Because every S3, SQS and Secrets Manager client was created through one Platform interface, the whole test setup was new LocalPlatform(tempDir): files instead of S3, an in-memory queue instead of SQS, a map instead of Secrets Manager. The same test suite also ran nightly against new AwsPlatform(testRegion) to catch real integration issues. Without the factory, each client would have been constructed wherever it was used, and swapping them for tests would have meant editing dozens of classes.

⚠️
Common mistakes
  • A switch over types copied to every place that creates things. Centralise creation in one factory or registry.
  • Subclassing just to choose a collaborator (Factory Method), when a Supplier or instance could be passed in.
  • Letting callers assemble families by hand, so an S3 store can end up next to a Pub/Sub queue. One factory per family.
  • Factories that return null for unknown keys. Throw, and list the known keys.
  • Factories that also configure, cache, retry and log. A factory creates; other concerns belong elsewhere.
  • Abstract Factory when products change often. Every new product touches every family; it suits a stable product set.

Interview drill

Explain it simply: What's the difference between a static factory method, Factory Method and Abstract Factory?

How a strong answer sounds
A static factory method is just a named static method that returns an instance, like Duration.ofSeconds; it can validate, cache, or return a hidden subtype. Factory Method is the GoF pattern where a base class's algorithm calls an overridable create method, so subclasses choose the object; today I'd usually pass a Supplier in instead. Abstract Factory is an interface with one creation method per product, implemented once per family, so related objects like an AWS blob store, queue and secret store are always created together and never mixed with GCP ones.

Deeper: Your checkout supports cards and UPI, and product says wallets, bank transfers and BNPL are coming. How do you create the right gateway for a payment?

How a strong answer sounds
Each method gets a PaymentGateway implementation, and a GatewayRegistry maps a payment-method key to a factory. Implementations register in the composition root, so checkout calls registry.create(order.paymentMethod()) and never changes when a method is added. Unknown keys fail fast with the list of known ones, and duplicate registration throws at startup. If gateways carry per-payment state I'd register Suppliers; if they're stateless and thread-safe, instances.

🧠 Key takeaways

  • Static factory methods can be named, return cached instances or hidden subtypes, and validate before creating.
  • Factory Method lets a subclass choose the object an algorithm uses; passing a Supplier is the composition-based alternative.
  • Abstract Factory creates a whole family through one interface, so products are never mixed across families.
  • Abstract Factory makes new families cheap and new products expensive.
  • A registry of factories replaces a growing switch; fail fast on unknown keys and duplicates.
  • JDBC is all three: drivers self-register via ServiceLoader, DriverManager picks one by URL, and a Connection creates matching Statements.

Check your understanding

Which of these can a static factory method do that a constructor can't?

A constructor always creates a new object. A static factory like Integer.valueOf or Collections.emptyList() can return a cached one. Both can take parameters and throw.

What problem does Abstract Factory solve?

One factory per family (AWS, GCP, local) creates every product in that family, so an S3 store never ends up paired with a Pub/Sub queue. The other options are Singleton, Builder and Strategy.

With a Platform abstract factory, what does adding Azure support involve?

New families are the cheap direction: one new implementation, selected in the composition root. Adding a new product would be the expensive direction.

A registry is asked to create a gateway for an unknown key. What should it do?

Failing fast with context turns a typo or missing registration into an obvious error. Null or a silent default pushes the failure somewhere harder to debug, or charges the wrong way.

DriverManager.getConnection("jdbc:mysql://…") throws “No suitable driver found”. What's the most likely cause?

DriverManager asks every registered driver whether it accepts the URL before any network connection. If none does, it fails immediately. A down server or bad password would fail later, inside the chosen driver's connect.
