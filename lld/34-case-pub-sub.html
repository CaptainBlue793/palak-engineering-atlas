Case Study: In-Memory Pub-Sub Broker

Chapter 16's event bus called listeners directly: fast, simple, and gone the moment a listener is slow or the process restarts. A broker puts a buffer between publishers and subscribers, and the most useful buffer is the one Kafka popularised: an append-only log per partition, which consumers read at their own pace by remembering an offset. This case study builds that design inside one JVM: topics and partitions, consumer groups that share work, offsets that make replay trivial, and the thread model that holds it together.

  • Specify a broker API with publish, subscribe-as-a-group, poll and commit
  • Partition topics by key so per-key order is preserved while work spreads out
  • Track consumer offsets to get at-least-once delivery and replay
  • Handle slow consumers with retention and lag, instead of blocking publishers
  • Choose locks and long-polling for a correct, simple thread model

Requirements and API

Clarify: many publishers and many subscribers on named topics; each subscriber group receives every message (billing and analytics both see every OrderPlaced), while consumers within a group share the work; messages with the same key (an order id) must be processed in order; a slow subscriber must not slow publishers; subscribers can replay from an earlier point; delivery is at least once. Out of scope: persistence to disk and replication, which is where a single process stops and the System Design course starts.

The biggest decision is push or pull. Push, as in the event bus, hands each message to subscriber callbacks or per-subscriber queues; the broker must then decide what to do when a subscriber falls behind. Pull stores messages in a log and lets each group read from its own position; the broker keeps one copy, and a slow group just has a larger lag. Pull is the design Kafka uses, and it makes replay and multiple groups nearly free.

	RecordMetadata publish(String topic, String key, byte[] value);   // → (partition, offset)
	Consumer subscribe(String topic, String group);                  // joins the group; triggers a rebalance
}

public interface Consumer extends AutoCloseable {
	List<Record> poll(Duration maxWait, int maxRecords);   // from this consumer's partitions
	void commit();                                          // “processed up to here”
	void seek(int partition, long offset);                  // replay
}

public record Record(long offset, String key, byte[] value, Instant time) {}

Topics and partitions

A topic with a single log would be one ordered sequence consumed by one reader per group, so a group couldn't scale past one thread. A topic therefore has several partitions, each its own log. The publisher's key picks the partition, hash(key) mod partitions, so every message about order 8412 lands in the same partition in the order it was published. That's the whole ordering guarantee: per key, not per topic. Messages with different keys in different partitions can be processed in any relative order, which is exactly what lets the work spread out.

final class Topic {
	private final String name;
	private final List<Partition> partitions;
	private final Clock clock;

	RecordMetadata publish(String key, byte[] value) {
		int p = Math.floorMod(key.hashCode(), partitions.size());    // same key → same partition → ordered
		long offset = partitions.get(p).append(key, value, clock.instant());
		return new RecordMetadata(name, p, offset);
	}
}

final class Partition {
	private final ArrayList<Record> log = new ArrayList<>();       // a ring buffer or segments in practice
	private long startOffset;                                     // offset of log.get(0); rises as retention trims
	private final int retention;
	private final ReentrantLock lock = new ReentrantLock();
	private final Condition appended = lock.newCondition();

	long append(String key, byte[] value, Instant now) {
		lock.lock();
		try {
			long offset = startOffset + log.size();
			log.add(new Record(offset, key, value.clone(), now));    // defensive copy: callers can't mutate history
			if (log.size() > retention) { log.remove(0); startOffset++; }
			appended.signalAll();                                    // wake long-polling consumers
			return offset;
		} finally { lock.unlock(); }
	}

	List<Record> read(long from, int max, Duration maxWait) throws InterruptedException {
		lock.lock();
		try {
			if (from < startOffset) throw new OffsetOutOfRangeException(from, startOffset);   // fell off the log
			long nanos = maxWait.toNanos();
			while (from >= startOffset + log.size() && nanos > 0) nanos = appended.awaitNanos(nanos);   // long poll
			int i = (int) (from - startOffset);
			return List.copyOf(log.subList(Math.min(i, log.size()), Math.min(log.size(), i + max)));
		} finally { lock.unlock(); }
	}
}

A Record is immutable and the log is append-only, so a record, once written, never changes: many consumers can read the same record with no coordination beyond the partition lock. Offsets are just positions in the log, stable forever, even after retention removes older entries. The while loop around awaitNanos handles spurious wake-ups and wakes for other offsets, the standard condition-variable idiom from Chapter 22.

Consumer offsets and replay

A consumer group has two pieces of state: which consumer owns which partition (the assignment), and for each partition the committed offset, the next offset the group has yet to process. Within a group each partition has exactly one owner, which keeps per-key order; a consumer can own several partitions; and a group with more consumers than partitions leaves some consumers idle. When members join or leave, the group rebalances: it recomputes the assignment with a pluggable strategy, and new owners resume from the committed offsets.

final class ConsumerGroup {
	private final Map<Integer, Long> committed = new ConcurrentHashMap<>();   // partition → next offset
	private final List<String> members = new ArrayList<>();
	private final PartitionAssignor assignor;                                   // Strategy: range, round-robin, sticky
	private volatile Map<String, List<Integer>> assignment = Map.of();
	private volatile int generation;

	synchronized void join(String member)  { members.add(member);    rebalance(); }
	synchronized void leave(String member) { members.remove(member); rebalance(); }

	private void rebalance() {
		assignment = assignor.assign(List.copyOf(members), partitionCount);      // immutable map, swapped in one write
		generation++;
	}

	long committed(int p) { return committed.getOrDefault(p, 0L); }
	void commit(int p, long next, int gen) {
		if (gen != generation) throw new RebalanceInProgressException();              // a stale owner can't overwrite the new one
		committed.merge(p, next, Math::max);                                      // offsets only move forward (seek is separate)
	}
}

When the consumer commits decides the delivery guarantee. Process, then commit: a crash between the two means the next owner re-reads those records, so each record is processed at least once, and handlers must be idempotent (Chapter 25). Commit, then process: a crash loses the records, so at most once. Exactly-once processing needs the side effect and the offset to be stored atomically together, for example in the same database transaction, which is the outbox idea (Chapter 27) in reverse. Replay is seek: set the position back and reprocess, useful after fixing a bug in a consumer.

Bounded queues and backpressure

In the pull design, publishers never wait for consumers: the log absorbs the difference, and each group's lag (end offset minus committed offset) measures how far behind it is. Lag is the broker's key health metric. But memory is finite, so the log is bounded by retention (a count, a byte size or an age). If a group lags past retention, the records it hadn't read are gone: its next read throws OffsetOutOfRangeException, and the group needs a policy: reset to the earliest retained record (accept the loss, keep going) or to the latest (skip ahead), and alert either way.

Where you do need backpressure is inside a consumer that hands records to a worker pool: a consumer that polls faster than its workers finish must stop polling, or its in-memory queue grows without bound. The rule from Chapter 23 applies: a bounded queue between the poller and the workers, and a poller that blocks (or pauses its partitions) when it's full. And an in-process broker that must never lose messages would add the opposite policy on publish: a maximum lag after which publish blocks or fails, making the slowest group slow down the producers. Both are legitimate; the design should make the choice explicit.

Thread model

Keep it as simple as the guarantees allow. Each partition has one lock: appends are serialised (they have to be, to assign offsets), and reads hold it briefly to copy a slice. Long polling uses the partition's Condition, so idle consumers sleep instead of spinning and wake as soon as a record arrives. Each consumer is used by one thread, like a Kafka consumer, so its positions need no locking. The group synchronizes membership changes and publishes each new assignment as an immutable map through a volatile field, with a generation number that stops a consumer that lost a partition in a rebalance from committing over the new owner.

🧠
Kafka's model, in one JVM

Apache Kafka is built around exactly these ideas. A topic is split into partitions, each an ordered, append-only log; producers choose partitions by key hash by default, so ordering is guaranteed only within a partition. Consumers form consumer groups, each partition is consumed by at most one member of a group, and groups rebalance as members come and go. Committed offsets are themselves stored in an internal Kafka topic, __consumer_offsets, and retention is configured per topic by time or size. What Kafka adds on top of this chapter is what one JVM can't give you: partitions stored on disk in segment files, replicated across brokers, with leaders and followers.

⚠️
Common mistakes
  • Promising topic-wide ordering while spreading work across partitions. Order is per key.
  • Committing before processing without meaning to: silent message loss on a crash.
  • Non-idempotent handlers under at-least-once delivery: duplicates after every rebalance.
  • More consumers than partitions, expecting more throughput; the extras sit idle.
  • A per-subscriber unbounded queue in a push design; one slow subscriber exhausts memory.
  • Mutable records or shared byte arrays, so one consumer's changes appear in another's view.
  • Busy-polling an empty partition in a loop instead of waiting on a condition.

Interview drill

Explain it simply: How can two services both receive every message, while three instances of one service share the work?

How a strong answer sounds
Consumer groups. Each service is a group, and every group reads the whole topic independently from its own committed offsets, so both get every message. Within a group, the topic's partitions are divided among the instances, one owner per partition, so the three instances each process a share. Since the key decides the partition, all messages for one key go to the same instance, in order.

Deeper: A consumer processes a batch, then its process is killed before it commits. Walk through what happens, and what the handler must guarantee.

How a strong answer sounds
The group notices the member is gone (a heartbeat timeout, or in-process a closed session) and rebalances, incrementing the generation. The partitions it owned are assigned to other members, which start from the last committed offsets, before the lost batch, so they process those records again. That's at-least-once delivery. If the dead consumer somehow comes back and tries to commit, its old generation is rejected. So the handler must be idempotent: for example, record processed message ids or use the business key (the order id) with an upsert or a unique constraint, so a second application is a no-op. If duplicates are unacceptable, store the effect and the offset in the same transaction.

🧠 Key takeaways

  • A pull-based broker stores one append-only log per partition; each group tracks its own offsets.
  • Keys choose partitions, so ordering is per key; partitions are the unit of parallelism.
  • Within a group each partition has one owner; rebalances move ownership, and a generation check blocks stale commits.
  • Process then commit gives at-least-once delivery; handlers must be idempotent. Replay is a seek.
  • Slow groups show up as lag; retention bounds memory and defines when unread records are lost.
  • One lock and condition per partition, one thread per consumer, immutable assignments swapped atomically.

Check your understanding

A topic has 4 partitions. What ordering does key-based partitioning guarantee?

Same key → same partition → one ordered log with one owner per group. Across partitions there's no ordering.

A group has 5 consumers reading a topic with 3 partitions. What happens?

A partition has at most one owner per group, so parallelism within a group is capped by the partition count.

Which commit order gives at-least-once delivery?

If the consumer dies after processing but before committing, the records are processed again by the next owner: duplicates, but no loss.

Group B's committed offset on a partition is 40, but retention has trimmed the log so it now starts at 52. What happens on B's next read?

Offsets are permanent positions. Once retention passes a lagging group, those records are gone for that group; lag monitoring exists to prevent this.

Why does commit check the group's generation number?

After a rebalance a slow, stale consumer might still try to commit. Rejecting commits from an old generation keeps ownership unambiguous.
