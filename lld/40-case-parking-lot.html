Case Study: Parking Lot

The parking lot is the classic object-oriented design question, and the version most people remember (a Vehicle superclass with Car, Truck and Motorcycle subclasses) misses what the interviewer is actually scoring. The interesting decisions are elsewhere: which spot a vehicle gets, as a swappable strategy; how two entry gates avoid giving out the same spot; how a fee is computed from a ticket and an injected clock; and how the display boards stay current. This case study makes those decisions, and the simulator shows why the allocation strategy matters.

  • Scope the problem and choose data over subclasses where behaviour doesn't differ
  • Model levels, spots, vehicles, tickets and gates with clear ownership
  • Make spot allocation a strategy, and see how best-fit beats nearest-first
  • Compute fees with tiered hourly rates and a daily cap
  • Keep concurrent gates from double-assigning a spot

Requirements and API

Clarify: several levels; spot types for motorcycles, compact cars, large vehicles, and EVs with chargers; each vehicle type fits some spot types; entry gates issue a ticket and assign a spot, or refuse when nothing fits; exit gates compute the fee and take payment; display boards show free spots per level and type; several gates operate at once; pricing may change. Out of scope: reservations, licence-plate recognition, and payment-provider details (an interface).

public interface ParkingLot {
	Ticket enter(Vehicle vehicle, GateId gate);                 // throws LotFullException for this vehicle type
	Receipt exit(TicketId ticket, PaymentMethod payment);
	Map<SpotType, Integer> freeSpots(int level);
}

Entities and relationships

The tempting first move is a class hierarchy of vehicles. But ask what a Truck does differently from a Car: nothing. They differ only in which spots they fit, which is data. So vehicle type is an enum that carries a table of fitting spot types, in order of preference. Adding a vehicle type is one line, and the fitting rules sit in one place instead of being spread across overridden methods (Chapter 6: prefer a field when only data varies).

public enum SpotType { MOTORCYCLE, COMPACT, LARGE, EV }

public enum VehicleType {                                     // fits = best fit first
	MOTORCYCLE(SpotType.MOTORCYCLE, SpotType.COMPACT, SpotType.LARGE),
	CAR(SpotType.COMPACT, SpotType.LARGE),
	EV_CAR(SpotType.EV, SpotType.COMPACT, SpotType.LARGE),
	TRUCK(SpotType.LARGE);

	private final List<SpotType> fits;
	VehicleType(SpotType... fits) { this.fits = List.of(fits); }
	public boolean fits(SpotType s) { return fits.contains(s); }
	public int preference(SpotType s) { return fits.indexOf(s); }   // 0 = ideal
}

public record Vehicle(LicensePlate plate, VehicleType type) {}
public record Ticket(TicketId id, Vehicle vehicle, SpotId spot, Instant entry) {}

public final class ParkingSpot {
	final SpotId id; final SpotType type; final int level, distance;   // distance from the entrance
	private final AtomicReference<Vehicle> occupant = new AtomicReference<>();

	boolean tryPark(Vehicle v) { return occupant.compareAndSet(null, v); }   // the only way in
	void vacate(Vehicle v) { if (!occupant.compareAndSet(v, null)) throw new IllegalStateException("not parked here: " + v); }
	boolean isFree() { return occupant.get() == null; }
}

The lot owns levels, levels own spots, and a spot holds a reference to its current vehicle; tickets refer to the spot by id. Gates don't own anything: they're thin callers of ParkingLot, and display boards are observers of availability changes.

Spot allocation strategy

Which spot should a car get? “The nearest free one” sounds right, and it's a mistake: a car parked in the nearest large spot takes the place of a truck that can't park anywhere else. Best fit fixes it: prefer the vehicle's ideal spot type, and only among equals pick the nearest. Other lots want other rules (fill upper levels first to keep the ground floor free for short stays, spread load across levels), so allocation is a strategy that returns candidates in order, and the lot tries them in turn.

public interface AllocationStrategy {
	Stream<ParkingSpot> candidates(VehicleType v, Collection<ParkingSpot> spots);
}

final class NearestFirst implements AllocationStrategy {
	public Stream<ParkingSpot> candidates(VehicleType v, Collection<ParkingSpot> spots) {
		return spots.stream().filter(s -> v.fits(s.type)).sorted(Comparator.comparingInt((ParkingSpot s) -> s.level).thenComparingInt(s -> s.distance));
	}
}

final class BestFit implements AllocationStrategy {
	public Stream<ParkingSpot> candidates(VehicleType v, Collection<ParkingSpot> spots) {
		return spots.stream().filter(s -> v.fits(s.type))
			.sorted(Comparator.comparingInt((ParkingSpot s) -> v.preference(s.type))    // ideal type first
				.thenComparingInt(s -> s.level).thenComparingInt(s -> s.distance));
	}
}

Spots are ordered by distance from the entrance, level 1 first, and the large spots are the nearest ones. Rush hour sends the same 20 vehicles every time, in pairs that reach the two gates at the same moment. Fees: see the pricing section below.

Tickets and pricing

Entry stamps the ticket with the time from an injected Clock; exit computes the fee from the ticket, the spot type and the clock again, through a PricingPolicy strategy so rate changes, weekend pricing or an event-day flat rate are new classes rather than edits. A typical policy charges each started hour, with a higher first hour and a daily cap. Money is a value type in cents, never a double (P6).

public record Rates(Money firstHour, Money perHour, Money dailyCap) {}

final class HourlyWithDailyCap implements PricingPolicy {
	private final Map<SpotType, Rates> rates;

	public Money fee(Ticket t, SpotType type, Instant exit) {
		Rates r = rates.get(type);
		long minutes = Duration.between(t.entry(), exit).toMinutes();
		long hours = Math.max(1, (minutes + 59) / 60);                    // every started hour counts
		long days = hours / 24, rest = hours % 24;
		return r.dailyCap().times(days).plus(Money.min(r.dailyCap(), cost(r, rest)));
	}

	private static Money cost(Rates r, long hours) {
		return hours == 0 ? Money.ZERO : r.firstHour().plus(r.perHour().times(hours - 1));
	}
}

Exit is where ordering matters. Remove the ticket atomically first (so the same ticket can't exit twice through two gates), charge, and only then free the spot and notify the boards. If the charge fails, put the ticket back and keep the barrier down. Charges carry the ticket id as an idempotency key (Chapter 25), so a retried payment can't bill twice.

Concurrent gates

With two entry gates, two threads can pick the same “best” free spot at the same instant. If each checks isFree() and then sets the occupant, both succeed and two cars get tickets for one spot, the check-then-act race from Chapter 22. The fix is to make claiming atomic and to treat losing the race as normal: tryPark is a compare-and-set, and the entry loop simply moves on to the next candidate.

public Ticket enter(Vehicle v, GateId gate) {
	Iterator<ParkingSpot> it = strategy.candidates(v.type(), spots).iterator();
	while (it.hasNext()) {
		ParkingSpot s = it.next();
		if (s.isFree() && s.tryPark(v)) {                           // lost the race? try the next one
			Ticket t = new Ticket(ids.next(), v, s.id, clock.instant());
			tickets.put(t.id(), t);
			events.publish(new SpotTaken(s.level, s.type));            // display boards observe these
			return t;
		}
	}
	throw new LotFullException(v.type());
}

Scanning every spot per entry is O(n), fine for a few hundred spots. For a large lot, keep per-level, per-type queues of free spot ids (ConcurrentLinkedDeque): allocation polls the preferred queue, which is both O(1) and atomic, and exit pushes the id back.

The textbook answer, and where to improve it

The parking lot appears in the object-oriented design chapter of Cracking the Coding Interview, and countless blog posts copy one shape of answer: an abstract Vehicle with subclasses, a ParkingSpot with a size, and a lot that finds the first spot that fits. It's a fine starting point, and it's the answer interviewers have heard hundreds of times. What distinguishes a strong round is going past it: noticing the subclasses carry no behaviour, making allocation and pricing strategies with a reason for each, handling two gates at once with an atomic claim, and making the exit use case safe to retry. That's the difference between reciting a design and making one.

⚠️
Common mistakes
  • A subclass per vehicle that differs only in size. Use an enum with a fitting table.
  • Nearest-first allocation that parks cars in large spots and turns trucks away.
  • Check-then-park across gates: two tickets for one spot.
  • Fees in double, partial hours rounded inconsistently, or Instant.now() called directly.
  • Freeing the spot before payment succeeds, or letting one ticket exit twice.
  • Display boards that recount every spot on each change instead of observing events.
  • A god class ParkingLotManager that allocates, prices, charges and displays.

Interview drill

Explain it simply: Why is vehicle type an enum here rather than a class hierarchy?

How a strong answer sounds
Because vehicles don't behave differently in this system; they only differ in which spot types they fit. That's data, so an enum that carries its list of fitting spot types, in order of preference, keeps the rule in one table. Adding a type is one line, and allocation code reads the table instead of calling overridden methods. If a vehicle type later needed real behaviour, like EVs starting a charging session, I'd add that behaviour where it belongs, for example a charging service keyed by spot type, rather than subclassing vehicles.

Deeper: Add reservations: a customer books a spot for 2 pm to 5 pm tomorrow. What changes?

How a strong answer sounds
Occupancy stops being “who's in the spot now” and becomes a schedule. I'd add a Reservation (vehicle type, time slot, status) and, rather than pinning a specific spot days ahead, keep a per-type capacity calendar: for each hour, how many spots of each type are promised. A booking succeeds only if every hour in its slot has capacity, checked and incremented atomically. At arrival, the gate looks up the reservation and allocates a concrete spot with the same strategy, but only from capacity held back for reservations, so walk-ins can't take it. No-shows release their hold after a grace period, via the scheduler from Chapter 35. Pricing gets a reservation-rate policy, and cancellations follow a rule stated up front. The existing enter, tryPark and exit flows barely change.

🧠 Key takeaways

  • Model what varies: vehicle types differ only in data, so an enum with a fitting table beats a hierarchy.
  • Allocation is a strategy; best fit (ideal spot type first, then nearest) keeps large spots for large vehicles.
  • Claim spots with a compare-and-set and move on when a race is lost; never check-then-park.
  • Pricing is a strategy over ticket, spot type and an injected clock; count started hours, cap per day, use Money.
  • Exit removes the ticket atomically, charges idempotently, then frees the spot and notifies observers.
  • Display boards observe events; large lots keep per-type free queues for O(1) allocation.
