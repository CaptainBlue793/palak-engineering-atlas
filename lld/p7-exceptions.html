Exceptions & Error Contracts

Every method has two contracts: what it returns when things go right, and what happens when they don't. The second one decides whether a gateway timeout gets retried, a declined card gets a friendly message, and a database connection gets returned to the pool. This chapter is about designing that second contract on purpose.

  • Explain the exception hierarchy, and choose between checked and unchecked exceptions
  • Design a small exception hierarchy that callers can act on, and wrap low-level errors with their cause
  • Use try-with-resources, and predict the close order and suppressed exceptions
  • Choose between returning Optional, throwing, and returning a result object
  • Fail fast at boundaries, and avoid swallowing or double-logging exceptions

The hierarchy, and checked vs unchecked

Everything you can throw extends Throwable, which splits into two branches. Error means the JVM itself is in trouble, like OutOfMemoryError or StackOverflowError. You almost never catch these. Exception is for problems a program can reasonably deal with, and it splits again:

  • Checked exceptions extend Exception but not RuntimeException, like IOException and SQLException. The compiler forces every caller to either catch them or declare them with throws.
  • Unchecked exceptions extend RuntimeException, like IllegalArgumentException, IllegalStateException and NullPointerException. The compiler doesn't make anyone handle them.

Compiler enforces handling?Yes: catch or declare throwsNo

A practical rule used in most modern Java codebases: throw unchecked exceptions for invalid arguments, broken invariants and domain failures, and reserve checked exceptions for the rare case where every direct caller truly must decide what to do. When a checked exception from a library crosses into your design, translate it at that boundary instead of letting throws SQLException spread through every layer above.

Designing exceptions callers can act on

An exception type is an API. The question to design it around is: what will the caller do differently? A payment client has three kinds of failure, and each needs a different reaction:

Payment failures, grouped by what the caller should do
public abstract class PaymentException extends RuntimeException {
	protected PaymentException(String message, Throwable cause) { super(message, cause); }
	public abstract boolean isRetryable();
}

/** The bank said no. Show the customer; retrying won't help. */
public final class CardDeclinedException extends PaymentException {
	private final String declineCode;
	public CardDeclinedException(String declineCode) { super("card declined: " + declineCode, null); this.declineCode = declineCode; }
	public String declineCode() { return declineCode; }
	@Override public boolean isRetryable() { return false; }
}

/** We never got an answer. Safe to retry with the same idempotency key. */
public final class GatewayUnavailableException extends PaymentException {
	public GatewayUnavailableException(String message, Throwable cause) { super(message, cause); }
	@Override public boolean isRetryable() { return true; }
}

// Inside the Stripe adapter: translate low-level errors at the boundary, keeping the cause.
try {
	return http.send(request, BodyHandlers.ofString());
} catch (HttpTimeoutException e) {
	throw new GatewayUnavailableException("stripe: no response in 5 s", e);   // e becomes getCause()
} catch (IOException e) {
	throw new GatewayUnavailableException("stripe: connection failed", e);
} catch (InterruptedException e) {
	Thread.currentThread().interrupt();                                         // restore the flag
	throw new GatewayUnavailableException("stripe: interrupted", e);
}
Three habits in one listing: exception types grouped by the caller's reaction (show, retry), carrying the data the caller needs (declineCode, isRetryable); low-level exceptions translated where they enter your design, so HttpTimeoutException never leaks into the order service; and the original exception passed as the cause, so the stack trace still shows the socket timeout. (A real HttpClient call also needs its request and body handler set up; they're left out here.)

try-with-resources

Some objects hold something the garbage collector doesn't manage: a database connection borrowed from a pool, a file handle, a socket. They must be closed on every path, including when an exception is thrown halfway through. Any class that implements AutoCloseable can be declared in a try (...) header, and Java guarantees its close() runs when the block exits, however it exits:

try (Connection conn = dataSource.getConnection();                 // opened first
     PreparedStatement ps = conn.prepareStatement(UPDATE_BALANCE)) {  // opened second
	ps.setLong(1, amount);
	ps.setString(2, accountId);
	ps.executeUpdate();
}                                                                       // ps.close(), then conn.close(): reverse order

Resources are closed in reverse order, because later ones usually depend on earlier ones: the statement belongs to the connection. If the body throws, and then a close() throws too, Java doesn't let the second exception hide the first. The body's exception propagates, and the close exception is attached to it as a suppressed exception, visible in the stack trace and through getSuppressed(). Old-style finally { conn.close(); } code got this wrong: an exception from close() in finally replaced the original one, and the real cause of the failure vanished from the logs.

    🧠
    The outage that one missing close() causes

    A service has a pool of 10 database connections. One code path borrows a connection and closes it at the end of the method, but not when a query throws. Every failing request now leaks one connection. After ten failures the pool is empty, and every request, including the healthy ones, waits for a connection until it times out. The site is down, and the database is idle. The logs show pool timeouts, not the query error that started it. try-with-resources makes this bug impossible to write, which is why every resource in this course is acquired in a try (...) header. Case Study 39 builds the pool, including leak detection.

    Optional, null, exception or result?

    Not every “no” is an error. The contract should say which outcomes are normal and which are failures:

    SituationReturnExample
    The thing might legitimately not existOptional<T>Optional<User> findByEmail(EmailAddress e)
    No results for a queryAn empty collection, never nullList<Order> openOrders(UserId id) returns List.of()
    An expected outcome the caller always branches onboolean, or a small result typeboolean tryAcquire(now); sealed interface ChargeResult permits Approved, Declined
    The operation couldn't do its jobThrowDatabase unreachable; gateway timed out
    The caller broke the contractThrow, immediatelyIllegalArgumentException("port must be 1–65535")

    Optional is for return values. Don't use it for fields or parameters: an optional parameter is better as an overload, and an optional field is just a nullable field with extra allocation. And never return null from a method declared to return Optional, which defeats the whole point.

    Fail fast, and never swallow

    Fail fast means detecting a problem as close to its cause as possible and stopping there. A null accepted by a constructor might not blow up until an hour later, in a different thread, with a stack trace that says nothing about where it came from. Checking arguments at the boundary with Objects.requireNonNull and explicit range checks turns a mystery into a one-line error message that names the bad value.

    ⚠️
    Common mistakes
    • Swallowing: catch (Exception e) {}. The failure happened; now nobody will ever know why the data is wrong.
    • Log and rethrow at every layer. One failure produces five copies of the same stack trace. Log once, at the top.
    • Dropping the cause: throw new PaymentException("failed") inside a catch, without passing e. The root cause disappears.
    • Catching InterruptedException and carrying on. Restore the flag with Thread.currentThread().interrupt() so the thread can still be stopped.
    • Using exceptions for normal control flow, like “user not found” in a lookup. Return Optional.
    • Closing resources by hand in finally. It's easy to miss a path, and a close exception can hide the real one. Use try-with-resources.
    🎤
    Interview drill

    Explain it simply: Checked or unchecked: how do you decide?

    How a strong answer sounds
    I ask whether every direct caller can and must do something specific about the failure. If so, a checked exception makes the compiler enforce it, but that's rare. Programming errors and broken preconditions are unchecked: IllegalArgumentException, IllegalStateException. Most domain and infrastructure failures are unchecked too, organised by what the caller does about them, such as a retryable gateway error versus a declined card. Checked exceptions from libraries I translate at the boundary into my own types, keeping the original as the cause.

    Deeper: In a try-with-resources with a connection and a statement, the query throws, and then closing the statement throws too. What does the caller see?

    How a strong answer sounds
    Resources close in reverse order, statement first, then connection, and both closes run even though the body failed. The query's exception is the one that propagates. The statement's close exception is attached to it as a suppressed exception, visible in the stack trace and through getSuppressed(). That's the improvement over a manual finally, where the close exception would replace the query error and hide the real cause.

    🧠 Key takeaways

    • Throwable splits into Error (don't catch) and Exception; checked exceptions must be caught or declared, RuntimeExceptions needn't be.
    • Default to unchecked exceptions; group them by what the caller will do, and give them the data the caller needs.
    • Translate low-level exceptions at your design's boundary, always passing the original as the cause.
    • try-with-resources closes every opened resource in reverse order; later failures are suppressed, not lost.
    • Return Optional for “might not exist”, empty collections for “none”, and throw when the operation couldn't do its job.
    • Fail fast at boundaries. Handle, translate or propagate; never swallow, and log once at the top.

    Check your understanding

    Which exception is unchecked, so the compiler doesn't force callers to handle it?

    IllegalArgumentException extends RuntimeException, so it's unchecked. The other three extend Exception but not RuntimeException, so they're checked.

    In a try-with-resources, the body throws SQLException A, then a resource's close() throws SQLException B. What propagates?

    The body's exception is the primary one. Exceptions thrown while closing are added to it with addSuppressed, so the original cause is never masked.

    try (Connection c = ...; PreparedStatement ps = c.prepareStatement(sql); ResultSet rs = ps.executeQuery()) { ... }. In what order are they closed?

    Resources close in the reverse of the order they were opened. Each one depends on the one before it, so the most dependent is closed first.

    A user lookup can fail in two ways: no user has that email, or the database is unreachable. How should findByEmail express them?

    A missing user is a normal outcome, and Optional puts it in the return type. An unreachable database means the method couldn't do its job, so it throws. Returning empty for that would make an outage look like “no such user”.

    Why write throw new GatewayUnavailableException("stripe timed out", e) instead of leaving out e?

    Passing e sets getCause(). Logs print the whole chain (“Caused by: HttpTimeoutException…”), so translating the exception hides the low-level type from callers without hiding it from whoever debugs the failure.
