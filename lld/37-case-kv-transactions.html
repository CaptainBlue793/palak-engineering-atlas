Case Study: Key-Value Store with Transactions

A key-value store with SET, GET and DELETE is a HashMap. Add BEGIN, ROLLBACK and COMMIT, allow them to nest, add keys that expire, and require that committed writes survive a crash, and it becomes one of the richest LLD problems there is. It's also a small model of how real databases work: an undo log for rollback, a write-ahead log for durability, and lazy plus active expiry. There's a working console to try it in below.

  • Specify commands and their exact semantics, including nested transactions
  • Implement rollback with an undo log of mementos, and compare it with layered write sets
  • Merge a committed inner transaction into its parent correctly
  • Expire keys lazily and actively, storing absolute expiry times
  • Make commits durable with a write-ahead log and an explicit fsync policy

Requirements and API

This problem lives or dies on precise semantics, so pin them down first. SET k v [EX seconds] sets a value, optionally with a time-to-live. GET k returns the value or nothing. DELETE k removes it. COUNT v returns how many keys currently hold value v (this forces an index). BEGIN opens a transaction, and transactions nest. ROLLBACK undoes everything in the innermost open transaction. COMMIT ends the innermost one, making its changes part of its parent; committing the outermost one makes them durable. Reads inside a transaction see its own writes. For this design, one client drives the store; concurrent sessions with isolation are the follow-up.

public interface KvStore {
	Optional<String> get(String key);
	void set(String key, String value, Optional<Duration> ttl);
	boolean delete(String key);
	long count(String value);
	void begin();
	void commit();      // throws NoTransactionException if none is open
	void rollback();
}

record Entry(String value, Instant expiresAt) {                     // expiresAt null = never
	boolean expired(Instant now) { return expiresAt != null && !now.isBefore(expiresAt); }
}

Some well-known variants of this exercise define COMMIT as closing all open transactions at once. Either is fine; the point is to choose one and say it. Nested commit-into-parent is the same behaviour as savepoints in SQL databases, and it's the more general of the two.

Nested transactions as a stack of change sets

Open transactions form a stack: BEGIN pushes, COMMIT and ROLLBACK pop. The question is what each level stores. There are two classic answers:

Undo log (write in place)Write-set layers (write aside)
On SET inside a transactionSave the key's old value in the level's undo map (first time only), then change the dataPut the new value in the level's own map; data untouched
GETO(1): read the dataO(depth): check each level from the top, then the data
COUNT vO(1) from an index kept on the dataHard: counts differ per level
ROLLBACKRestore the saved old valuesDiscard the top level: O(1)
COMMIT to parentMerge undo maps (parent's older values win)Merge the level's writes into the parent's
Concurrent readersSee uncommitted data unless isolatedNaturally isolated: others read only the data

For one client with COUNT, the undo log wins: reads and counts are O(1), and each level stores only the keys it touched. Each saved old value is a memento (Chapter 17): enough state to put that key back exactly as it was, including “it didn't exist”. Write-set layers are the better starting point once several sessions need isolation, because uncommitted writes never touch shared data, and that's where the follow-up goes.

final class Transaction {
	final Map<String, Entry> undo = new HashMap<>();     // key → entry before this level first touched it; null = absent
	final List<Op> redo = new ArrayList<>();               // the operations, for the WAL if this reaches the top
}

public final class InMemoryKvStore implements KvStore {
	private final Map<String, Entry> data = new HashMap<>();
	private final Map<String, Long> valueCounts = new HashMap<>();   // index for COUNT
	private final Deque<Transaction> tx = new ArrayDeque<>();
	private final WriteAheadLog wal;
	private final Clock clock;

	public synchronized void set(String key, String value, Optional<Duration> ttl) {
		Instant exp = ttl.map(d -> clock.instant().plus(d)).orElse(null);   // absolute time, not “seconds left”
		apply(key, new Entry(value, exp), new Op.Set(key, value, exp));
	}

	public synchronized boolean delete(String key) {
		if (live(key) == null) return false;
		apply(key, null, new Op.Delete(key));
		return true;
	}

	private void apply(String key, Entry next, Op op) {
		Transaction t = tx.peek();
		if (t == null) wal.append(List.of(op));                       // autocommit: log first, then apply
		else {
			if (!t.undo.containsKey(key)) t.undo.put(key, data.get(key));   // memento, once per level (null = absent)
			t.redo.add(op);
		}
		write(key, next);
	}

	private void write(String key, Entry next) {                  // the only place data and the index change
		Entry prev = next == null ? data.remove(key) : data.put(key, next);
		if (prev != null) valueCounts.merge(prev.value(), -1L, Long::sum);
		if (next != null) valueCounts.merge(next.value(), 1L, Long::sum);
	}
}

Note containsKey rather than putIfAbsent: the saved value is often null (“the key didn't exist”), and putIfAbsent treats a null mapping as absent, so a second write in the same level would overwrite the memento with the first write's value, and rollback would restore the wrong thing. It's exactly the kind of bug an interviewer probes with “what if I set the same key twice in one transaction?”

Rollback via Memento

Rollback pops the innermost level and restores each saved memento through the same write method, which keeps the COUNT index correct for free. Commit is the subtle one: an inner level's changes become part of its parent, so if the parent later rolls back, the inner changes must be undone too. Merge the undo maps, and where both levels saved a value for the same key, the parent's (older) memento wins, because it's the state from before either level began.

public synchronized void rollback() {
	Transaction t = pop();
	t.undo.forEach(this::write);                            // restore every key this level touched
}

public synchronized void commit() {
	Transaction t = pop();
	Transaction parent = tx.peek();
	if (parent == null) { wal.append(t.redo); return; }         // outermost: one durable batch
	t.undo.forEach((k, old) -> { if (!parent.undo.containsKey(k)) parent.undo.put(k, old); });
	parent.redo.addAll(t.redo);
}

private Transaction pop() {
	Transaction t = tx.poll();
	if (t == null) throw new NoTransactionException();
	return t;
}

Expired keys stay in memory (struck through) until something reads them or a sweep runs. With “every second”, WAL records written since the last fsync (amber) are lost if you CRASH before an ADVANCE.

TTL expiry

Store the absolute expiry instant, never the seconds remaining: an absolute time doesn't need updating as time passes, survives being written to the log and replayed, and compares with one call against an injected clock. Then expire in two ways, because neither is enough alone. Lazily: every read checks the entry and treats an expired one as absent (deleting it on the spot), so a client can never see a stale value. Actively: a periodic sweep removes expired keys nobody reads, which would otherwise hold memory forever.

private Entry live(String key) {
	Entry e = data.get(key);
	if (e != null && e.expired(clock.instant())) { write(key, null); return null; }   // lazy expiry
	return e;
}

public synchronized Optional<String> get(String key) { return Optional.ofNullable(live(key)).map(Entry::value); }

synchronized int sweep(int sample) {                        // scheduled (Chapter 35); samples keys that have a TTL
	int removed = 0;
	for (String k : randomKeysWithTtl(sample)) if (live(k) == null) removed++;
	return removed;                                             // caller repeats if many were expired
}

Sampling instead of scanning every key keeps each sweep's cost bounded. A sweep that finds a high share of expired keys in its sample runs again straight away, so the amount of expired-but-present memory stays proportional to how fast keys expire. Redis documents the same approach for its active expiry.

Write-ahead log

Durability means a COMMIT that returned OK survives a crash. The rule is in the name: write the log before you acknowledge. Every committed batch is appended to a file as one record, and on startup the store replays the file to rebuild memory. Two decisions make or break it. When to fsync: writing to a file only reaches the operating system's cache; force (fsync) waits for the disk, which is the durable point and is slow. Syncing on every commit is safest; syncing once a second is much faster and can lose about a second of acknowledged writes. Torn records: a crash mid-append leaves a partial record at the tail, so each record carries its length and a checksum, and replay stops at the first bad one.

final class WriteAheadLog {
	private final FileChannel channel;
	private final FsyncPolicy policy;                        // ALWAYS, or EVERY_SECOND via a scheduled force()

	synchronized void append(List<Op> batch) {
		ByteBuffer record = Codec.encode(batch);                 // [length][crc32][ops…]: a batch is all-or-nothing on replay
		while (record.hasRemaining()) channel.write(record);
		if (policy == FsyncPolicy.ALWAYS) channel.force(false); // durable before COMMIT returns
	}

	static void replay(Path file, Instant now, BiConsumer<String, Entry> apply) {
		// read records until EOF or a bad length/checksum (a torn tail); apply each op in order;
		// SETs whose expiresAt is already past are skipped — absolute times make that possible.
	}
}

What Redis does, and doesn't

Redis offers the same durability trade-off as a setting. With its append-only file (AOF) enabled, appendfsync always fsyncs every write, everysec (the default) fsyncs once per second and can lose about a second of writes in a crash, and no leaves flushing to the operating system; the file is compacted by periodically rewriting it. Its transactions, however, are different from this chapter's: MULTI … EXEC queues commands and runs them together without interleaving other clients, but there is no rollback. If one queued command fails at runtime, the others still take effect, and DISCARD only drops the queue before EXEC. It's a useful contrast in the interview: “atomic execution” and “all-or-nothing with rollback” are different promises.

⚠️
Common mistakes
  • Saving the old value on every write instead of the first per level, or with putIfAbsent, which overwrites a saved “absent”.
  • Letting the child's memento win when merging on commit; the parent's older value must.
  • Storing “seconds left” for TTLs, which goes stale and replays wrongly.
  • Only lazy expiry: expired keys nobody reads leak memory. Only active expiry: reads can see stale values.
  • Acknowledging before logging, or logging each operation of a transaction separately so a crash replays half of it.
  • No checksum, so a torn final record is replayed as garbage.
  • Forgetting the COUNT index on rollback paths; route every change through one write method.

Interview drill

Explain it simply: How do you implement ROLLBACK for nested transactions?

How a strong answer sounds
Keep a stack of open transactions. Each level has an undo map: the first time a key changes in that level, I save its previous value, including “didn't exist”. Changes go straight into the data, so reads are O(1). ROLLBACK pops the top level and writes each saved value back. COMMIT pops it and merges its undo map into the parent's, keeping the parent's value where both have one, so that a later rollback of the parent undoes the child's changes too. Only the outermost commit writes to the log.

Deeper: Now two clients use the store concurrently, each with its own transactions. What breaks, and how would you redesign?

How a strong answer sounds
With write-in-place undo logs, client B would read client A's uncommitted changes, and A's rollback could erase B's work on the same key. I'd move transactions into per-session objects and switch to write-set layers: a session's uncommitted writes live in its own maps, reads check its layers and then the committed data, so nobody sees uncommitted state. At the outermost commit, I apply the write set to the shared data atomically under a lock and log it. For conflicts, optimistic checking: record the version of each key the transaction read, and at commit reject it if any changed since (snapshot isolation with first-committer-wins); the client retries. COUNT then needs to combine the committed index with the session's own pending changes. That's the step from this chapter's design toward MVCC in real databases.

🧠 Key takeaways

  • Pin down semantics first: what nested COMMIT and ROLLBACK mean, and what reads inside a transaction see.
  • An undo log of mementos (first change per key per level) gives O(1) reads and an easy COUNT index.
  • On nested commit, merge undo maps with the parent's older memento winning; only the outermost commit is logged.
  • Store absolute expiry times; expire lazily on read and actively by sampling.
  • Log before acknowledging, one checksummed record per committed batch; fsync policy is an explicit durability trade-off.
  • For concurrent sessions, switch to per-session write sets and validate at commit.

Check your understanding

SET a 1; BEGIN; SET a 2; BEGIN; SET a 3; ROLLBACK; GET a — what's returned?

ROLLBACK undoes only the innermost transaction, restoring a to its value before that level: 2.

When an inner transaction commits into its parent, both have saved an old value for key k. Which one is kept?

If the parent later rolls back, k must return to its state before the parent began, which is exactly the parent's memento.

Why store a key's expiry as an absolute instant rather than “seconds remaining”?

A countdown would need constant updating and would restart from its logged value on replay, extending the key's life.

Why do stores use both lazy and active expiry?

Each covers the other's gap: correctness on read, and bounded memory for keys that are never read again.

With “fsync every second”, what can a crash lose?

Appended bytes sit in the OS cache until fsync. Syncing per second trades up to a second of acknowledged writes for much higher throughput. (Open transactions are lost in every mode.)
