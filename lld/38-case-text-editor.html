Case Study: Text Editor with Undo/Redo

Chapter 17 used a text editor to introduce Command: insert and delete as objects on an undo stack. A real editor has three more problems that make this a full case study. Storing the text so that typing in the middle of a large file is fast. Grouping keystrokes so that one undo removes a word, not one letter. And keeping the cursor, the selection and every other position in the document correct as edits shift text around them. You can type into a working gap-buffer editor below.

  • Specify an editor API around a buffer, a selection and an undo manager
  • Choose between a gap buffer, a rope and a piece table
  • Represent every edit as one invertible replace command that restores the selection
  • Coalesce keystrokes into undo groups with explicit, testable rules
  • Adjust cursors, selections and marks when text before them changes

Requirements and API

Clarify: insert text at the cursor, delete backwards and forwards, move the cursor, select a range and type over it; undo and redo, where undo removes a sensible chunk (a word you typed, a paste, a whole find-and-replace) and puts the cursor back where it was; files of several megabytes; every keystroke handled in well under a frame (16 ms). Out of scope: rendering, syntax highlighting, and multiple users, which is the collaborative-editing problem.

Three objects, each with one job: a TextBuffer stores characters and knows nothing about cursors or undo; a Selection value says where the user is; an UndoManager records edits and groups them. The Editor coordinates them for each user action.

public interface TextBuffer {
	int length();
	String substring(int from, int to);
	void replace(int from, int to, CharSequence text);         // insert and delete are special cases
}

public record Selection(int anchor, int caret) {              // anchor = where the drag started
	public int start()      { return Math.min(anchor, caret); }
	public int end()        { return Math.max(anchor, caret); }
	public boolean isEmpty() { return anchor == caret; }
	public static Selection at(int pos) { return new Selection(pos, pos); }
}

public final class Editor {
	private final TextBuffer buffer;
	private final UndoManager history;
	private Selection sel = Selection.at(0);

	public void type(String text)  { apply(Edit.replacing(buffer, sel, text)); }       // types over a selection
	public void backspace()        { if (sel.isEmpty() && sel.caret() == 0) return; apply(Edit.deleting(buffer, sel.isEmpty() ? new Selection(sel.caret() - 1, sel.caret()) : sel)); }
	public void moveTo(int pos, boolean extend) { sel = extend ? new Selection(sel.anchor(), pos) : Selection.at(pos); history.breakGroup(); }
	public void undo() { history.undo(buffer).ifPresent(s -> sel = s); }       // undo returns the selection to restore
	public void redo() { history.redo(buffer).ifPresent(s -> sel = s); }
}

Gap buffer vs rope

A String or a plain char array makes every insertion in the middle O(n): all the text after the cursor shifts by one, on every keystroke, in a 5 MB file. But edits have locality: people type many characters in one place, then move. A gap buffer exploits that. It's one array with an empty gap sitting at the cursor; typing fills the gap from the left in O(1), backspace widens it in O(1), and moving the cursor moves the gap, copying only the characters between the old and new position. When the gap runs out, the array grows (doubling, so appends are amortised O(1)).

public final class GapBuffer implements TextBuffer {
	private char[] buf = new char[64];
	private int gapStart = 0, gapEnd = 64;                    // the gap is buf[gapStart, gapEnd)

	public int length() { return buf.length - (gapEnd - gapStart); }

	public void replace(int from, int to, CharSequence text) {
		Objects.checkFromToIndex(from, to, length());
		moveGapTo(to);
		gapStart = from;                                           // deleting [from, to) = widening the gap leftwards
		ensureGap(text.length());
		for (int i = 0; i < text.length(); i++) buf[gapStart++] = text.charAt(i);
	}

	private void moveGapTo(int pos) {                            // cost: |pos - gapStart| characters
		if (pos < gapStart) {
			int n = gapStart - pos;
			System.arraycopy(buf, pos, buf, gapEnd - n, n);
			gapStart -= n; gapEnd -= n;
		} else if (pos > gapStart) {
			int n = pos - gapStart;
			System.arraycopy(buf, gapEnd, buf, gapStart, n);
			gapStart += n; gapEnd += n;
		}
	}

	private void ensureGap(int needed) {
		if (gapEnd - gapStart >= needed) return;
		int tail = buf.length - gapEnd;
		char[] bigger = new char[Math.max(buf.length * 2, length() + needed + 64)];
		System.arraycopy(buf, 0, bigger, 0, gapStart);
		System.arraycopy(buf, gapEnd, bigger, bigger.length - tail, tail);
		gapEnd = bigger.length - tail; buf = bigger;
	}
}

Because the Editor depends only on the TextBuffer interface, the choice is swappable: start with a gap buffer, which is the easiest to code correctly in an interview, and name the rope or piece table as the answer to “what about a 200 MB log file?” or “what if users jump around constantly?”.

Edits as Commands

Chapter 17 had separate Insert and Delete commands. An editor needs one more (typing over a selection replaces it), and three classes with three inverses is three chances for a bug. Notice that all three are the same operation: replace the text in [at, at + removed.length) with inserted. Insert has nothing removed; delete has nothing inserted. So one immutable record covers every edit, and its inverse is the same record with removed and inserted swapped. It also carries the selection before and after, so undo can put the cursor back exactly where the user was.

public record Edit(int at, String removed, String inserted, Selection before, Selection after) {
	static Edit replacing(TextBuffer b, Selection s, String text) {
		return new Edit(s.start(), b.substring(s.start(), s.end()), text, s, Selection.at(s.start() + text.length()));
	}
	static Edit deleting(TextBuffer b, Selection range) { return replacing(b, range, ""); }

	void applyTo(TextBuffer b) { b.replace(at, at + removed.length(), inserted); }
	Edit inverse() { return new Edit(at, inserted, removed, after, before); }       // the whole undo logic
	int delta() { return inserted.length() - removed.length(); }
}

Capturing removed when the edit is created, from the buffer, is what makes it reversible: a delete that doesn't remember what it deleted can't be undone (Chapter 17's lesson, now built into the only constructor). Because the record is immutable, the same object can sit on the undo stack, move to the redo stack and back, with no risk of it changing in between.

Undo/redo and coalescing

If every keystroke were its own undo step, undoing a sentence would take forty presses. Editors coalesce consecutive edits into one undo group, and the rules are a design decision worth stating precisely, because users feel them. A common set: keep extending the open group while the user keeps typing contiguously, or keeps deleting contiguously; close it when the cursor moves, when typing switches to deleting, when a new word starts after whitespace, or after a pause (about a second). Compound operations (paste, find-and-replace-all, auto-indent) open an explicit group so they undo in one step.

public final class UndoManager {
	private final Deque<Group> undo = new ArrayDeque<>(), redo = new ArrayDeque<>();
	private final Clock clock;
	private final int maxGroups;                                   // bound memory: drop the oldest
	private boolean open;

	public void record(Edit e) {
		Instant now = clock.instant();
		if (open && !undo.isEmpty() && undo.peek().canAbsorb(e, now)) undo.peek().add(e, now);
		else { undo.push(new Group(e, now)); if (undo.size() > maxGroups) undo.removeLast(); }
		open = true;
		redo.clear();
	}

	public void breakGroup() { open = false; }

	public Optional<Selection> undo(TextBuffer b) {
		open = false;
		if (undo.isEmpty()) return Optional.empty();
		Group g = undo.pop();
		g.edits().reversed().forEach(e -> e.inverse().applyTo(b));      // last edit first
		redo.push(g);
		return Optional.of(g.selectionBefore());
	}
	// redo: pop from redo, apply edits in order, push to undo, return selectionAfter
}

boolean canAbsorb(Edit e, Instant now) {                                // in Group
	Edit last = edits.getLast();
	if (Duration.between(lastAt, now).compareTo(PAUSE) > 0) return false;
	boolean typing = last.removed().isEmpty() && e.removed().isEmpty() && e.at() == last.at() + last.inserted().length();
	boolean deleting = last.inserted().isEmpty() && e.inserted().isEmpty() && e.at() + e.removed().length() == last.at();
	boolean newWord = typing && endsWithSpace(last.inserted()) && !startsWithSpace(e.inserted());
	return (typing || deleting) && !newWord;
}

Cursor and selection

The editor's own selection is set by each edit, but other positions in the document are not: a second cursor, a bookmark, a search highlight, a collaborator's caret, the scroll anchor. When an edit changes text before a position, that position must shift by the edit's delta; when it deletes text around a position, the position collapses to the edit point. Put that rule in one function and run every stored position through it after each edit, or positions drift and point at the wrong characters.

static int adjust(int pos, Edit e) {
	int removedEnd = e.at() + e.removed().length();
	if (pos <= e.at()) return pos;                         // before the edit: unaffected
	if (pos >= removedEnd) return pos + e.delta();        // after it: shift by the size change
	return e.at() + e.inserted().length();              // inside deleted text: move to the end of the insert
}

Selection adjust(Selection s, Edit e) { return new Selection(adjust(s.anchor(), e), adjust(s.caret(), e)); }

Whether a position exactly at the edit point stays before or moves after inserted text is a choice (“sticky left” or “sticky right”): a bookmark should usually stay put, another user's caret usually should too, while an end-of-selection marker often moves right. This same transform, applied to edits instead of positions, is the core of operational transformation in collaborative editors, which is where the System Design chapter picks up.

🧠
Emacs and VS Code chose differently

GNU Emacs stores each buffer's text in a gap buffer, the structure in this chapter, and it has served well for decades because editing is local. VS Code went the other way: in 2018 its team described reimplementing the text buffer as a piece tree, a piece table held in a balanced tree, replacing an array of line strings. Their motivation was very large files: the old model's memory use was many times the file size and loading was slow, while the piece table keeps the original file contents untouched in one buffer and represents edits as pieces pointing into it or into an append-only buffer of added text. Both are right for what they optimise; the design lesson is to hide the choice behind a TextBuffer interface so it can change.

⚠️
Common mistakes
  • Storing the document in a String and rebuilding it on every keystroke: O(n) per character.
  • Delete commands that don't capture the deleted text, so they can't be undone.
  • One undo step per keystroke, or grouping rules nobody wrote down or tested.
  • Forgetting to clear redo after a new edit, letting redo reapply edits to text that has changed.
  • Undo that doesn't restore the selection, leaving the cursor somewhere unrelated to the change.
  • Positions (bookmarks, other cursors) not adjusted after edits before them.
  • Unbounded history in a long session; cap the number of groups or their total size.

Interview drill

Explain it simply: How does a gap buffer make typing fast?

How a strong answer sounds
The text is one array with an unused gap at the cursor. Typing writes into the start of the gap and shrinks it, O(1); backspace just widens the gap, O(1). Moving the cursor moves the gap by copying only the characters between the old and new position. Since people type many characters in one place before moving, most keystrokes cost O(1), and when the gap fills up the array doubles, so growth is amortised O(1) too. The weak spot is jumping far away and editing repeatedly, where a rope or piece table does better.

Deeper: Add “Replace All” for a search term across the document, as one undo step. Walk through the design.

How a strong answer sounds
Find all match ranges first, against the unchanged text. Then open an explicit undo group, and apply one replace Edit per match from the last match to the first, so earlier offsets stay valid without adjusting them; alternatively apply them forwards and run each later range through adjust. Close the group, so undo applies all the inverses in reverse order and restores the selection from before. Redo is cleared once. For thousands of matches in a big file I'd consider building the new text in one pass and recording a single edit covering the changed span, trading undo granularity for speed; the group interface hides that choice from callers.

🧠 Key takeaways

  • Split the editor into a TextBuffer (storage), a Selection (value) and an UndoManager (history).
  • A gap buffer gives O(1) typing at the cursor by exploiting locality; ropes and piece tables handle huge files and far jumps.
  • One immutable replace Edit covers insert, delete and replace-selection; its inverse swaps removed and inserted.
  • Coalesce edits into undo groups with explicit rules: contiguity, same kind, word boundaries, pauses, explicit compound groups.
  • Undo restores the selection from before the group; any new edit clears redo.
  • Adjust every stored position through one function after each edit.

Check your understanding

In a gap buffer, what does it cost to move the cursor from position 100 to position 40 and type a character?

Moving the gap copies exactly the characters it passes over. After that, typing into the gap is O(1).

What is the inverse of Edit(at=5, removed="cat", inserted="dog")?

Swap removed and inserted at the same position: remove "dog", put "cat" back. The selections swap too.

The user types “hello”, clicks elsewhere, and types “world”. How many undo groups should there be?

Edits in different places are separate steps. A cursor move always breaks the group.

A bookmark is at position 50. The user deletes positions 10–19 (10 characters). Where should the bookmark be?

The bookmark is after the deleted range, so it shifts by the delta, −10. A bookmark inside the range would collapse to position 10.

Why must a new edit clear the redo stack?

Redo edits carry positions and removed text from the old future. After a new edit, those no longer match the buffer.
