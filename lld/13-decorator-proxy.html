Decorator & Proxy

Both patterns put an object in front of another object with the same interface, so callers can't tell the difference. A Decorator does it to add behaviour: retries, logging, caching, metrics. A Proxy does it to control access: load lazily, check permissions, call across the network. The mechanics are nearly identical. What differs is intent, and in practice the one thing that matters most with either is the order in which the layers are stacked.

  • Write a decorator that implements an interface, wraps an instance of it and adds one behaviour
  • Predict how the order of stacked decorators changes behaviour
  • Recognise decorators in the JDK: I/O streams and collection wrappers
  • Use virtual, protection and remote proxies, and JDK dynamic proxies
  • Explain why calls an object makes to itself bypass its proxy

Decorator: same interface, one more behaviour

A service calls other services over HTTP through one small interface. Different call sites need different extras: retries for flaky dependencies, a cache for expensive lookups, a client-side rate limit to protect a partner's API, logging for debugging. Subclassing each combination is the explosion from P5. A Decorator implements the same interface, holds an instance of it, and adds one behaviour around the delegated call:

One interface, one base implementation, one decorator per concern
public interface Fetcher { Response fetch(String path); }

public final class HttpFetcher implements Fetcher { /* the real network call */ }

public final class CachingFetcher implements Fetcher {
	private final Fetcher inner;
	private final Map<String, Response> cache = new ConcurrentHashMap<>();
	public CachingFetcher(Fetcher inner) { this.inner = inner; }

	@Override public Response fetch(String path) {
		Response hit = cache.get(path);
		if (hit != null) return hit;                    // behaviour added before…
		Response r = inner.fetch(path);                 // …delegation…
		if (r.status() == 200) cache.put(path, r);     // …and after
		return r;
	}
}
// RetryingFetcher, LoggingFetcher, RateLimitedFetcher: the same shape, one concern each

Fetcher users = new LoggingFetcher(new CachingFetcher(new RetryingFetcher(new HttpFetcher(client), 3)), log);
Why it works: every layer is a Fetcher, so layers stack in any order and the caller only ever sees Fetcher. Each concern is written once and tested alone. (This minimal cache has no expiry or size limit; Case Study 31 builds a real one.)

Now the interesting part. The order of the layers isn't cosmetic: logging outside retry logs once per request, inside it logs every attempt. A cache outside the rate limiter lets cache hits skip the limiter; inside it, every request spends a token even when it's served from memory. Decorators you already use

  
Java's I/O library is decorators all the way down (P5): BufferedInputStream, GZIPInputStream and DataInputStream each extend FilterInputStream, hold another InputStream, and add one capability. The collections framework has decorators too: Collections.unmodifiableList(list) returns a List that forwards reads and rejects writes, and Collections.synchronizedMap(map) returns a Map whose every method takes a lock before delegating. Neither copies the data; both wrap it.

  

  
Proxy: controlling access

  
A Proxy has the same structure as a decorator: it implements the subject's interface and holds (or will create) the real object. The intent is different. It doesn't add a feature; it decides whether, when and how the real object is reached. The common kinds:

  

    

      
KindWhat it controlsExample

      
        
Virtual (lazy)When an expensive object is created or loadedAn ORM loads an order's line items only when first accessed

        
ProtectionWhether the caller may use itAuthorizingDocumentStore checks the user's permission before each call

        
RemoteWhere it runs: the real object is in another processA gRPC or RMI stub that serialises the call and sends it over the network

        
Caching / smart referenceHow often the real object is reached, or counting referencesA cached view of a slow configuration service

      
    

  


// A virtual proxy: looks like a Report, loads the real one on first use
public final class LazyReport implements Report {
	private final ReportId id;
	private final ReportStore store;
	private Report real;                                   // null until needed

	@Override public String title() { return real().title(); }
	@Override public List<Row> rows() { return real().rows(); }
	private synchronized Report real() {                   // thread-safe lazy load
		if (real == null) real = store.load(id);           // the expensive part, at most once
		return real;
	}
}

  
Where decorator and proxy blur, don't worry about the name. A caching layer can be called either. The distinction worth making is whether the wrapper changes what the object does (decorator) or whether and when it's reached (proxy), because that tells a reader what to expect from it.


  
Dynamic proxies, and the self-invocation trap

  
Writing a timing decorator for one interface is easy. Writing one for fifty interfaces is tedious. The JDK can generate proxies at run time: java.lang.reflect.Proxy.newProxyInstance creates an object implementing any interfaces you name, and sends every method call to one InvocationHandler:


static <T> T timed(Class<T> type, T target, Metrics metrics) {
	InvocationHandler handler = (proxy, method, args) -> {
		long start = System.nanoTime();
		try { return method.invoke(target, args); }
		catch (InvocationTargetException e) { throw e.getCause(); }                 // rethrow the real exception
		finally { metrics.record(type.getSimpleName() + "." + method.getName(), System.nanoTime() - start); }
	};
	return type.cast(Proxy.newProxyInstance(type.getClassLoader(), new Class<?>[]{ type }, handler));
}

OrderRepository repo = timed(OrderRepository.class, new JdbcOrderRepository(ds), metrics);

  
JDK dynamic proxies only work for interfaces, which is one more reason to program to them. Frameworks use the same technique. Spring wraps beans in proxies to add transactions, security and caching, using JDK proxies for interfaces and generated subclasses (CGLIB) otherwise. Mockito generates classes at run time to create mocks.

  
They all share one limitation, the “self problem” from P5: a call that an object makes to its own method goes straight to this, not through the proxy wrapped around it. That's the best-known Spring surprise:

Why @Transactional sometimes does nothing
A Spring service has placeOrder(), which calls this.reserveStock(), and reserveStock is annotated @Transactional. Controllers call placeOrder through the Spring proxy, but placeOrder's call to reserveStock is an ordinary call on this, the real object. The proxy never sees it, so no transaction starts, and a failure halfway leaves half-reserved stock. The code looks right and the annotation is right there. The fixes all come back to routing the call through the proxy: put the annotation on the method callers invoke, move reserveStock to another bean, or restructure so the transactional boundary is the entry point.

  


  
⚠️
Common mistakes

    
    
      
  • A decorator that doesn't implement the interface. Then it can't be stacked or passed where the original was expected.
    • 
      
  • Stacking without thinking about order. Retry inside a rate limiter spends one token per request; outside, one per attempt. Choose deliberately, and wire the stack in one place.
    • 
      
  • Decorators that do several things. Retry-and-log-and-cache in one wrapper can't be reordered or reused. One concern per layer.
    • 
      
  • Forgetting to forward a method, so it silently skips the real object. Write a forwarding base class for large interfaces.
    • 
      
  • Lazy proxies without thread safety. Two threads can both load; guard the first load.
    • 
      
  • Expecting self-calls to go through the proxy. Calls on this never do.
    •

Interview drill

    
Explain it simply: What's the difference between a Decorator and a Proxy?

    
How a strong answer sounds
Structurally they're the same: a class that implements the same interface as the object it wraps and delegates to it. The intent differs. A decorator adds behaviour, like retries, logging or caching, and several decorators are often stacked. A proxy controls access to the real object: loading it lazily, checking permissions, or forwarding the call to another process. Both keep the interface, which is what separates them from an adapter.

    
Deeper: You have Logging, Retry, Cache and RateLimit decorators for an HTTP client. In what order would you stack them, and why?

    
How a strong answer sounds
Outermost to innermost: Logging, Cache, RateLimit, Retry, then the real client. Logging outermost records one line per logical request, with its final outcome. Cache next, so hits skip the rate limit and the network entirely. The rate limiter outside retry counts one token per request rather than per attempt. If the partner's limit counts every attempt, I'd move it inside retry instead, which is the kind of decision to state out loud. I'd build the stack in one factory so the order is decided in exactly one place.

  


  

    
🧠 Key takeaways

    
    
      
  • A decorator implements the same interface as what it wraps, holds it, and adds one behaviour around the delegated call.
    • 
      
  • Decorators stack in any order, and the order changes behaviour: decide it deliberately, in one place.
    • 
      
  • The JDK is full of decorators: I/O filter streams, unmodifiable and synchronized collection wrappers.
    • 
      
  • A proxy has the same shape but controls access: lazy loading, permission checks, remote calls, caching.
    • 
      
  • JDK dynamic proxies generate a proxy for any interface at run time; frameworks use them for transactions and security.
    • 
      
  • Calls an object makes on this bypass any proxy around it.

Check your understanding

    


    

      
What makes RetryingFetcher a decorator?

      

        
        
        
        
      

      
Same interface plus a wrapped instance of it plus one added behaviour. That's what lets it stack with other decorators and stand in for the original.

    


    

      
With the origin failing the first attempt, how many log lines does one request produce if Logging sits inside Retry (closer to the network)?

      

        
        
        
        
      

      
Retry calls whatever is inside it once per attempt. With logging inside, each attempt passes through the logger. Outside retry, the logger sees only the one logical request.

    


    

      
A Cache decorator is placed outside a RateLimited decorator. What happens on a cache hit?

      

        
        
        
        
      

      
Outer layers run first. A hit returns before delegating, so nothing inside the cache runs. Put the cache inside the limiter and every request would spend a token.

    


    

      
Which wrapper is best described as a Proxy rather than a Decorator?

      

        
        
        
        
      

      
Lazy loading controls when the real object is reached: a virtual proxy. Retries and metrics add behaviour (decorators); renaming to fit another interface is an adapter.

    


    

      
placeOrder() calls this.reserveStock(), and only reserveStock is @Transactional. Why does no transaction start?

      

        
        
        
        
      

      
Framework features live in the proxy around the object. Self-invocation skips the proxy, so its interceptors, including the transaction, never run.
