Producer-Consumer, Thread Pools & Futures

Most systems have some work that shouldn't happen on the request thread: sending email, resizing images, writing audit logs, calling slow partners. The standard shape is producer-consumer: something puts work on a queue, a pool of worker threads takes it off. It's simple until the producers are faster than the consumers, at which point the one design decision that matters is what the queue does when it fills. This chapter covers that decision, how many threads to run, how to compose asynchronous results with futures, and how to shut it all down without losing work.

  • Size a thread pool for CPU-bound and I/O-bound work
  • Configure a ThreadPoolExecutor with a bounded queue and a rejection policy
  • Compose parallel calls with CompletableFuture, with timeouts, and shut executors down gracefully

Producer-consumer with a BlockingQueue

A BlockingQueue is a thread-safe queue with two extra behaviours: take() waits when the queue is empty, and put() waits when a bounded queue is full. That's all you need to connect producers and consumers running at different speeds without busy-waiting or extra locks:

public final class ThumbnailWorker implements Runnable {
	private final BlockingQueue<ImageJob> jobs;
	private final Thumbnailer thumbnailer;

	@Override public void run() {
		try {
			while (!Thread.currentThread().isInterrupted()) {
				ImageJob job = jobs.take();                       // waits while there's nothing to do
				try { thumbnailer.create(job); }
				catch (RuntimeException e) { recordFailure(job, e); }   // one bad job can't kill the worker
			}
		} catch (InterruptedException e) {
			Thread.currentThread().interrupt();                   // shutdown asked us to stop
		}
	}
}

BlockingQueue<ImageJob> jobs = new ArrayBlockingQueue<>(1_000);   // bounded: the key decision
// producer, in the upload handler:
if (!jobs.offer(job, 100, TimeUnit.MILLISECONDS)) return Response.status(503);

The producer's choice of method is the backpressure policy. put() blocks until there's room, slowing the producer to the consumers' pace. offer(job, timeout) waits briefly, then gives up, so the caller can reject. add() throws immediately when full. An unbounded queue never pushes back at all, which sounds friendly and is usually a bug.

What happens under overload

If producers are faster than consumers for long enough, something has to give. The only question is what: memory, the producers, or some of the work. Set the rates and try each policy:

Capacity is workers ÷ time per job: 4 workers at 80 ms each finish 50 jobs a second. The bounded queue holds 200 jobs. The chart shows queue depth over the 60 seconds; latency includes time waiting in the queue.

Read the results as three different failure modes. Unbounded: nothing is rejected, and queue depth and latency grow without limit. Users wait minutes for work that no longer matters, and eventually the heap fills and the process dies with every queued job lost. Bounded + block: memory stays bounded, and the overload moves to the producers, which wait; end-to-end latency still grows, it's just spent waiting to get into the queue. That's right for a batch pipeline, and dangerous on a request thread, where blocking ties up the web server. Bounded + reject: some requests fail fast with a clear error, the rest are served within a bounded time (queue size ÷ throughput), and clients can retry later. For online services this is usually the right answer: shed load explicitly rather than accepting work you can't do.

Thread pools: how many threads?

An ExecutorService is a queue plus a set of reusable worker threads: you submit tasks, it runs them. The number of threads is a real design decision, and the answer depends on what the tasks spend their time doing:

  • CPU-bound work (image resizing, compression, parsing): about one thread per core. More threads just take turns on the same cores and add switching overhead.
  • I/O-bound work (HTTP calls, database queries): threads spend most of their time waiting, so you need more of them. Brian Goetz's rule of thumb: threads ≈ cores × (1 + wait time ÷ compute time). With 8 cores and calls that wait 90 ms for every 10 ms of work, that's 8 × (1 + 9) = 80 threads.
  • Little's law checks the result: work in flight = arrival rate × time per item. 400 requests a second at 200 ms each means 80 requests in progress at once, so you need about 80 threads (or connections) to keep up.

Then there's the trap. The convenient Executors.newFixedThreadPool(n) uses an unbounded LinkedBlockingQueue internally: exactly the policy that failed in the simulator. For anything that can be overloaded, build the executor explicitly:

ThreadPoolExecutor pool = new ThreadPoolExecutor(
	16, 16,                                               // core and max threads
	0, TimeUnit.MILLISECONDS,
	new ArrayBlockingQueue<>(500),                          // bounded queue
	new NamedThreadFactory("thumbnail-"),                     // names make thread dumps readable
	new ThreadPoolExecutor.AbortPolicy());                    // full? throw RejectedExecutionException

The last argument is the rejection policy: AbortPolicy throws, so the caller can return 503; CallerRunsPolicy runs the task on the submitting thread, which slows the producer down (backpressure without a separate mechanism); DiscardPolicy and DiscardOldestPolicy silently drop work, which is only acceptable for work that truly doesn't matter, like best-effort metrics.

Futures: waiting for results without blocking everything

Submitting a task returns a Future, a handle to a result that isn't ready yet. CompletableFuture adds composition: run several calls in parallel, combine their results, add timeouts and fallbacks, all without a thread sitting in a blocking get() for each step. A product page that needs three independent backend calls is the classic case:

CompletableFuture<Product> product = CompletableFuture.supplyAsync(() -> catalog.get(id), io);
CompletableFuture<Price> price = CompletableFuture.supplyAsync(() -> pricing.quote(id, user), io)
	.orTimeout(300, TimeUnit.MILLISECONDS);                     // required: fail after 300 ms
CompletableFuture<List<Review>> reviews = CompletableFuture.supplyAsync(() -> reviewsApi.top(id), io)
	.completeOnTimeout(List.of(), 200, TimeUnit.MILLISECONDS);   // optional: empty after 200 ms

ProductPage page = product
	.thenCombine(price, ProductPage::new)
	.thenCombine(reviews, ProductPage::withReviews)
	.join();                                                   // ~max of the three, not their sum

Three details make this production-grade. Pass your own executor (io): the default common pool is sized for CPU work and shared by the whole JVM, so blocking I/O in it starves everyone else. Give every remote call a timeout, and decide per call whether a timeout fails the page (price) or degrades it (reviews). And remember that join() rethrows failures wrapped in CompletionException, so the caller still needs a plan for errors.

Shutting down without losing work

Executors don't stop on their own; their threads keep the JVM alive. A graceful shutdown stops accepting work, lets queued and running tasks finish for a bounded time, and only then interrupts what's left:

pool.shutdown();                                              // no new tasks; queued ones still run
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
	List<Runnable> dropped = pool.shutdownNow();                  // interrupt workers, return unstarted tasks
	log.warn("{} tasks not run at shutdown", dropped.size());     // or persist them for the next start
}

That's why workers must respond to interruption (the InterruptedException handling in the first listing), and why work that must not be lost belongs in a durable queue, not only in memory (Chapter 17).

🧠
Virtual threads change the sizing, not the need for limits

Java 21's virtual threads are cheap: a server can run hundreds of thousands of them, one per request, and blocking I/O no longer ties up an OS thread. That removes most of the reason for hand-sized I/O thread pools. It doesn't remove the need for limits. Every virtual thread still calls the same database with its 20 connections and the same partner API with its rate limit. Without a bound, like a Semaphore around the partner call or a bounded connection pool (Case Study 39), a traffic spike becomes 50,000 simultaneous calls to a downstream that can handle 200. Backpressure moves from the thread pool to the resource itself.

⚠️
Common mistakes
  • Unbounded queues, including the one hidden in Executors.newFixedThreadPool. Bound them and pick a rejection policy.
  • Blocking I/O on the common ForkJoinPool via supplyAsync without an executor. Pass a dedicated I/O executor.
  • Remote calls without timeouts. One slow dependency then holds threads, and eventually the whole pool, forever.
  • Swallowing InterruptedException. Restore the flag and stop, or shutdown can't stop your workers.
  • Letting one failing task kill a worker thread. Catch per task inside the loop.
  • Never shutting executors down, or shutting down without waiting, silently dropping queued work.

Interview drill

Explain it simply: What is backpressure, and why does an unbounded queue break it?

How a strong answer sounds
Backpressure is how a slow consumer tells a fast producer to slow down or stop. A bounded queue provides it: when it's full, the producer blocks, waits briefly, or is rejected, so overload shows up at the edge where it can be handled. An unbounded queue never says no, so under sustained overload it grows until latency is useless and the heap runs out, losing everything queued. For online requests I'd use a bounded queue and reject with 503 when full; for batch pipelines, blocking the producer is fine.

Deeper: A page calls three backends sequentially and takes 900 ms. How would you get it under 400 ms, and what can go wrong?

How a strong answer sounds
If the calls are independent, fan them out in parallel with CompletableFuture.supplyAsync on a dedicated, bounded I/O executor and combine them with thenCombine, so the page takes roughly the slowest call rather than the sum. Every call gets a timeout: orTimeout for required parts, completeOnTimeout with a fallback for optional ones like reviews. What can go wrong: running blocking calls on the common pool, missing timeouts so one slow backend pins every thread, an unbounded executor queue under load, and forgetting that join() rethrows failures as CompletionException.

🧠 Key takeaways

  • Producer-consumer: a BlockingQueue between producers and a pool of worker threads.
  • The queue's full-queue behaviour is your backpressure policy: block, reject, or (unbounded) run out of memory.
  • Online services should usually bound queues and shed load fast; batch pipelines can block producers.
  • Size pools by workload: about one thread per core for CPU work; cores × (1 + wait/compute) for I/O, checked with Little's law.
  • Build ThreadPoolExecutor explicitly with a bounded queue, named threads and a rejection policy.
  • CompletableFuture fans out calls on your own executor, with a timeout on every call; shut executors down with shutdown, awaitTermination, then shutdownNow.

Check your understanding

Jobs arrive at 60 per second and workers can finish 50 per second. With an unbounded queue, what happens over the next hour?

An unbounded queue never pushes back. A sustained 10 jobs/s surplus is 36,000 queued jobs after an hour, each waiting longer than the last, until the heap is exhausted.

What's the hidden risk in Executors.newFixedThreadPool(16) for a request-handling path?

The fixed pool is backed by an unbounded LinkedBlockingQueue. Building a ThreadPoolExecutor with an ArrayBlockingQueue and a rejection policy gives you a bound.

An 8-core service makes HTTP calls that wait about 90 ms for every 10 ms of CPU work. Roughly how many threads should the I/O pool have?

I/O-bound threads spend most of their time waiting, so more threads are needed to keep the cores busy. The rule of thumb gives 80; measure and adjust from there.

What does ThreadPoolExecutor.CallerRunsPolicy do when the pool and its queue are full?

Running the task on the caller's thread means the producer can't submit more until it finishes: a simple form of backpressure. AbortPolicy throws; the discard policies drop.

Why pass a dedicated executor to CompletableFuture.supplyAsync for blocking HTTP calls?

Without an executor argument, tasks run on ForkJoinPool.commonPool(), typically cores − 1 threads shared by parallel streams and other async code. Blocking I/O belongs on its own bounded pool.
