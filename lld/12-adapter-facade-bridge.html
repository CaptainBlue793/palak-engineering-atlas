Adapter, Facade & Bridge

Real systems are stitched together from code you didn't write: payment SDKs, cloud clients, a twenty-year-old bank API. Their interfaces never match yours. Three structural patterns deal with that, each for a different mismatch. Adapter makes one interface look like another. Facade puts a simple front on a complicated subsystem. Bridge keeps two independent dimensions of variation from multiplying into a class per combination.

  • Write an object adapter that wraps a vendor API behind your own interface
  • Translate units, identifiers and error codes inside the adapter, never outside it
  • Use a Facade to simplify a subsystem without hiding it or turning it into a god class
  • Recognise two independent dimensions and split them with Bridge
  • Explain an anti-corruption layer, and tell these patterns apart from Decorator and Proxy

Adapter: make it fit

Billing depends on its own interface (Chapter 4): ChargeResult charge(Money, PaymentToken, IdempotencyKey). Two providers must implement it. One is a modern JSON API that takes integer amounts in minor units, lowercase currency codes and an Idempotency-Key header, and reports declines as structured errors. The other is a bank's legacy gateway that takes a decimal string like "19.99" and answers with two-digit ISO 8583 response codes, the codes card networks use: 00 approved, 05 do not honour, 51 insufficient funds, 91 issuer unavailable.

An Adapter implements your interface by translating to and from the other one. The standard Java form is an object adapter: it holds the vendor client and delegates to it.

LegacyBankGateway.java: an object adapter
public final class LegacyBankGateway implements PaymentGateway {   // the target: billing's interface
	private final BankSoapClient bank;                                // the adaptee: the vendor's client

	public LegacyBankGateway(BankSoapClient bank) { this.bank = Objects.requireNonNull(bank); }

	@Override public ChargeResult charge(Money amount, PaymentToken token, IdempotencyKey key) {
		AuthRequest req = new AuthRequest();                          // translate in: units, names, formats
		req.setAmount(amount.toDecimal().toPlainString());           // "19.99", not 1999
		req.setCurrency(amount.currency().getNumericCode());       // 840, not "USD"
		req.setCardToken(token.value());
		req.setMerchantReference(key.value());                    // the bank's version of idempotency
		try {
			AuthResponse res = bank.authorize(req);
			return switch (res.getResponseCode()) {                  // translate out: codes to meaning
				case "00"             -> new ChargeResult.Approved(new ChargeId(res.getAuthCode()));
				case "05", "51", "54" -> new ChargeResult.Declined(reasonFor(res.getResponseCode()));
				case "91", "96"       -> throw new GatewayUnavailableException("bank code " + res.getResponseCode(), null);
				default                 -> new ChargeResult.Declined(DeclineReason.OTHER);
			};
		} catch (SOAPFaultException | WebServiceException e) {        // vendor exceptions never leave this class
			throw new GatewayUnavailableException("bank unreachable", e);
		}
	}
}
Everything vendor-specific stays inside: decimal strings, numeric currency codes, response codes and SOAP exceptions. Billing sees Money in, and Approved, Declined or a retryable GatewayUnavailableException out, whichever provider answered. (AuthRequest, BankSoapClient and friends stand in for a vendor's generated client classes.)

A class adapter would instead extend the vendor class and implement the interface. Java allows only one superclass, it exposes every vendor method on your adapter, and it can only adapt that exact class, so the object adapter is almost always the right choice. You use adapters from the JDK every day: InputStreamReader adapts a byte InputStream to a character Reader, and Arrays.asList adapts an array to the List interface.

Facade: a simple front for a messy subsystem

  
Publishing an uploaded video touches five subsystems: a transcoder that produces several resolutions, a thumbnail extractor, blob storage, a metadata database and a CDN cache that must be purged. Every caller that publishes a video would otherwise need to know all five and the order to call them in. A Facade is one class with one simple method that does the choreography:


public final class VideoPublisher {                                          // the facade
	private final Transcoder transcoder; private final ThumbnailExtractor thumbnails;
	private final BlobStore storage; private final VideoCatalog catalog; private final CdnClient cdn;
	// constructor injects all five

	public VideoId publish(Upload upload, ChannelId channel) {
		List<Rendition> renditions = transcoder.transcode(upload, Resolution.STANDARD_LADDER);
		renditions.forEach(r -> storage.put(r.key(), r.bytes()));
		Thumbnail thumb = thumbnails.extract(renditions.get(0), Duration.ofSeconds(3));
		VideoId id = catalog.add(channel, renditions, thumb);
		cdn.purge("/channels/" + channel.value() + "/latest");
		return id;
	}
}

  
Three rules keep a facade healthy. It adds no business rules of its own, only orchestration; if it starts deciding things, it's becoming a god class (Chapter 3). It doesn't lock the subsystem away: an admin tool that only needs to purge the CDN can still use CdnClient directly. And it covers the common path, not every option; one method per use case, not one per subsystem method. DailySalesReportJob in Chapter 3 was a small facade.


  
Bridge: two dimensions, kept apart

  
Notifications vary in two independent ways. The kind: an urgent alert (sent immediately, bypasses quiet hours), a daily digest (batched), a marketing message (needs an unsubscribe link and consent). And the channel: email, SMS, push. Subclassing each combination gives the explosion from P5: AlertEmail, AlertSms, DigestPush… 3 × 3 = 9 classes, and a fourth channel means three more. Bridge gives each dimension its own hierarchy, and connects them with a reference: the kind has a channel.


public interface Channel { void deliver(Recipient to, RenderedMessage m); }   // implementor: Email, Sms, Push

public abstract class Notification {                                           // abstraction
	protected final Channel channel;                                            // the bridge
	protected Notification(Channel channel) { this.channel = channel; }
	public abstract void send(Recipient to, Event e);
}
public final class Alert extends Notification {                           // kinds: Alert, Digest, Marketing
	public Alert(Channel c) { super(c); }
	@Override public void send(Recipient to, Event e) { channel.deliver(to, RenderedMessage.urgent(e)); }   // ignores quiet hours
}

new Alert(new SmsChannel(twilio));  new Digest(new EmailChannel(ses));   // 3 kinds + 3 channels = 6 classes

  
Bridge is composition applied to two hierarchies. It's also the shape of JDBC: the java.sql API is the abstraction your code uses, and each driver is an implementor behind it, so the two evolve independently. The name comes from the reference that “bridges” the two hierarchies.

Anti-corruption layers

  
When the thing you're integrating with has a different model of the world, not just different method names, a single adapter class grows into a layer. A legacy order system might represent a customer as a flat row with 140 columns and status codes like "P2"; your domain has a Customer entity and an OrderStatus enum. Domain-driven design calls the translating layer an anti-corruption layer: adapters, translators and value mappings whose whole job is to stop the other system's concepts leaking into yours. The rule is the same as for one adapter, at a bigger scale: vendor types, codes and exceptions stop at the boundary. Chapter 27 returns to it.


  

    
🧠

    
Adding a second payment provider in two weeks
A typical case: an e-commerce company uses one card processor and wants UPI payments through a second provider for lower fees. Because checkout only knows PaymentGateway and ChargeResult, the work is one new adapter: translating to the second provider's order-then-capture flow, its amount format and its webhook-based confirmations, plus mapping its error codes into Declined reasons and retryable failures. The same contract tests from Chapter 4 run against both adapters, and a routing rule chooses a gateway by payment method (Strategy). Checkout, refunds and receipts don't change.

  


  
⚠️
Common mistakes

    
    
      
  • Adapters that leak: returning the vendor's response object, or letting its exceptions escape. Translate everything, both ways.
    • 
      
  • An interface shaped like the first vendor. charge(StripeChargeParams) can't be adapted for anyone else. Design it in your domain's terms.
    • 
      
  • Translating error codes in the callers. if (code.equals("51")) in checkout couples it to one bank. Codes stop at the adapter.
    • 
      
  • Facades that make decisions. Orchestration only; business rules belong in the domain classes.
    • 
      
  • Facades as the only door. Keep the subsystem usable directly for uncommon needs.
    • 
      
  • Subclassing combinations of two dimensions. Split them into two hierarchies joined by a reference.
    •

Interview drill

    
Explain it simply: What's the difference between an Adapter and a Facade?

    
How a strong answer sounds
An Adapter makes one existing interface fit another interface that clients already expect, usually one class for one vendor client, translating calls, units and errors, like a bank gateway implementing our PaymentGateway. A Facade defines a new, simpler interface over several classes in a subsystem, for common use cases, like one publish method that runs the transcoder, storage, catalog and CDN in order. Adapter converts; Facade simplifies.

    
Deeper: Design how checkout supports two payment providers with different APIs, amount formats and error codes.

    
How a strong answer sounds
Billing owns a PaymentGateway interface in its own types: charge(Money, PaymentToken, IdempotencyKey) returning a sealed ChargeResult of Approved or Declined, plus a retryable exception for outages. Each provider gets an object adapter that holds the vendor client and translates amounts, currency formats, idempotency and every error code into those types; vendor exceptions never leave the adapter. The same contract tests run against both adapters, a router picks one per payment, and checkout doesn't know which provider answered.

  


  

    
🧠 Key takeaways

    
    
      
  • Adapter implements the interface clients expect by translating to and from an existing one; prefer the object adapter (composition).
    • 
      
  • All vendor-specific units, codes and exceptions are translated inside the adapter, both ways.
    • 
      
  • Facade gives a subsystem a small interface for common use cases; it orchestrates, adds no rules, and doesn't lock the subsystem away.
    • 
      
  • Bridge splits two independent dimensions into two hierarchies joined by a reference: m + n classes instead of m × n.
    • 
      
  • An anti-corruption layer is the same translation idea at the scale of a whole foreign model.
    • 
      
  • Adapter changes the interface; Decorator and Proxy keep it.
    •

What is an Adapter's job?

      

        
        
        
        
      

      
Adapter converts one interface into another. Adding behaviour with the same interface is Decorator; one simple entry to a subsystem is Facade.

    


    

      
A legacy bank answers with response code "51". Where should that become DeclineReason.INSUFFICIENT_FUNDS?

      

        
        
        
        
      

      
Translating at the boundary keeps the rest of the system independent of one vendor's vocabulary. Another provider's adapter maps its own codes to the same reasons.

    


    

      
Why is an object adapter usually preferred over a class adapter in Java?

      

        
        
        
        
      

      
A class adapter extends the adaptee, so it inherits its whole public API and works only for that exact class. Holding the adaptee keeps the adapter's surface to the target interface.

    


    

      
Notifications come in 4 kinds and go over 3 channels. How many classes does Bridge need, compared with one class per combination?

      

        
        
        
        
      

      
One class per kind plus one per channel is 4 + 3 = 7, joined at run time. Subclassing every combination is 4 × 3 = 12, and grows by a whole row or column with each addition.

    


    

      
Which is a sign that a Facade is going wrong?

      

        
        
        
        
      

      
A facade orchestrates. Once it owns rules, it's on its way to being a god class. Direct access to the subsystem for uncommon needs is fine.
