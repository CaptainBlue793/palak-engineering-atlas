State

An order is created, paid, shipped, delivered, and sometimes cancelled or refunded. What you're allowed to do with it depends entirely on which of those it is: you can't ship an unpaid order or refund one that was never charged. Code that tracks this with a pile of booleans eventually reaches a combination that should be impossible. The State pattern, and its lighter cousin the state machine enum, make the legal lifecycle explicit and the illegal moves unrepresentable.

  • Recognise “flag soup” and count the impossible states it allows
  • Model a lifecycle as states and transitions, and draw it
  • Implement it with state objects that decide the next state
  • Use an enum transition table when states carry little behaviour
  • Use sealed records so each state carries exactly its own data

Flag soup

The first version of an order often grows booleans as features arrive: paid, shipped, delivered, cancelled, refunded. Every method then checks combinations of them:

public void ship(TrackingNumber tn) {
	if (!paid) throw new IllegalStateException("not paid");
	if (cancelled) throw new IllegalStateException("cancelled");
	// did anyone remember "refunded"? "already shipped"?
	shipped = true; tracking = tn;
}

Five booleans allow 25 = 32 combinations. Only seven are real states. The other 25, like “cancelled and delivered” or “refunded but never paid”, are bugs waiting for one forgotten check. Every new method has to re-check the right subset of flags, and every new flag doubles the combinations. The fix is to replace the flags with a single notion of which state the order is in, and to write down, once, which transitions between states are legal.

States and transitions

A state machine has a finite set of states, a set of events, and a transition rule: in state S, event E moves to state T, or is rejected. Drawing it is the best design step you can take, in an interview or at work, because gaps and contradictions jump out of a diagram. The State pattern: states as objects

In the State pattern, the order holds a reference to a state object and delegates each event to it. Each state class implements only the events that are legal from that state, and returns the next state. The order's own methods shrink to one line each:

State objects that carry their own data
public sealed interface OrderState permits Created, Paid, Shipped, Delivered, Cancelled, Refunded {
	default OrderState pay(PaymentId p)        { throw illegal("pay"); }
	default OrderState ship(TrackingNumber t)  { throw illegal("ship"); }
	default OrderState deliver(Instant at)      { throw illegal("deliver"); }
	default OrderState cancel()                { throw illegal("cancel"); }
	default OrderState refund()                { throw illegal("refund"); }
	private IllegalStateException illegal(String e) {
		return new IllegalStateException("cannot " + e + " an order that is " + getClass().getSimpleName());
	}
}

record Created() implements OrderState {
	public OrderState pay(PaymentId p) { return new Paid(p); }
	public OrderState cancel()           { return new Cancelled(List.of()); }
}
record Paid(PaymentId payment) implements OrderState {             // only a paid order has a payment id
	public OrderState ship(TrackingNumber t) { return new Shipped(payment, t); }
	public OrderState cancel()                { return new Cancelled(List.of(payment)); }   // charges to refund
}
record Shipped(PaymentId payment, TrackingNumber tracking) implements OrderState {
	public OrderState deliver(Instant at) { return new Delivered(payment, tracking, at); }
}
record Delivered(PaymentId payment, TrackingNumber tracking, Instant at) implements OrderState {
	public OrderState refund() { return new Refunded(payment); }
}
// Cancelled and Refunded override nothing: they are terminal.

public final class Order {
	private OrderState state = new Created();
	public void pay(PaymentId p)       { state = state.pay(p); }         // the state decides; the order just records
	public void ship(TrackingNumber t) { state = state.ship(t); }
	public void cancel()               { state = state.cancel(); }
	public OrderState state()          { return state; }
}
What changed: no flags and no scattered checks. An illegal event throws from the one default method, with a message naming the event and the state. And because each state is a record carrying its own data, impossible combinations can't even be constructed: a tracking number exists only inside Shipped and Delivered, and a Cancelled order knows whether it owes a refund.

Enum state machines

When states differ only in which transitions they allow, and carry no data of their own, classes are more than you need. An enum with a transition table is shorter and just as safe:

public enum JobState {
	QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELLED;

	private static final Map<JobState, Set<JobState>> NEXT = new EnumMap<>(Map.of(
		QUEUED,    EnumSet.of(RUNNING, CANCELLED),
		RUNNING,   EnumSet.of(SUCCEEDED, FAILED, CANCELLED),
		FAILED,    EnumSet.of(QUEUED),                 // retry
		SUCCEEDED, EnumSet.noneOf(JobState.class),
		CANCELLED, EnumSet.noneOf(JobState.class)));

	public JobState moveTo(JobState next) {
		if (!NEXT.get(this).contains(next)) throw new IllegalStateException(this + " → " + next);
		return next;
	}
}

Note the first column's last row: booleans are fine for properties that really are independent, like giftWrapped and expressShipping. Flag soup is the specific mistake of using booleans for one lifecycle.

State vs Strategy. Both hold an interface and delegate to it (Chapter 15). The difference is who changes it. A strategy is chosen from outside and stays until someone swaps it; a state replaces itself as events arrive, following the transition rules. If the object you're delegating to returns “the next one”, it's State.

🧠
TCP is a state machine

Every TCP connection your code opens is driven by a state machine defined in the original TCP specification, RFC 793: LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT and CLOSED. Each segment that arrives is an event, and the current state decides what it means. A FIN in ESTABLISHED starts a close; the same FIN in LISTEN is meaningless. When you run netstat or ss and see thousands of sockets in TIME_WAIT, you're looking at that state machine's current states. It's the canonical example of behaviour that depends entirely on state.

⚠️
Common mistakes
  • Several booleans for one lifecycle. Replace them with one state.
  • A public setState(). Then anything can jump anywhere. Expose events (pay, ship), not the state setter.
  • Silently ignoring illegal events. Throw, or return a result the caller must handle; a lost “ship” is worse than an error.
  • Transition rules scattered in callers: if (order.state() == PAID) order.ship(). The state machine enforces its own rules.
  • Nullable fields that belong to one state (trackingNumber on every order). Put them in that state's record.
  • Not drawing the diagram. Missing transitions (“can a failed payment be retried?”) are obvious on paper and invisible in code.

Interview drill

Explain it simply: When would you use the State pattern, and how does it differ from Strategy?

How a strong answer sounds
When an object's behaviour depends on a lifecycle stage and some operations are only legal in some stages, like an order, a payment, a TCP connection or a vending machine. Each state is an object implementing the events legal in it and returning the next state; the context forwards events and stores whatever comes back. Strategy has the same structure, but the strategy is chosen from outside and doesn't change itself, while states replace themselves as events arrive.

Deeper: Model a payment that can be authorized, captured, voided before capture, refunded after capture, and failed. How do you stop a refund of an uncaptured payment?

How a strong answer sounds
I'd draw the machine first: Created → Authorized or Failed; Authorized → Captured or Voided; Captured → Refunded, possibly partially. Then a sealed PaymentState with a record per state: Authorized(authId, amount), Captured(captureId, amount), Refunded(captureId, refunded) and so on. refund is only implemented on Captured; everywhere else the default throws, so refunding an uncaptured payment can't happen, and there's no way to hold a capture id without being captured. The payment exposes events, never a state setter.

🧠 Key takeaways

  • Booleans for one lifecycle create 2n combinations, most of them impossible states.
  • Draw the state machine: states, events, legal transitions, terminal states.
  • State pattern: the context forwards events to a state object, which returns the next state or refuses.
  • Sealed records per state carry exactly their own data, making illegal combinations unrepresentable.
  • An enum with a transition table is enough when states carry no data or behaviour.
  • Expose events, never a state setter; reject illegal events loudly.

Check your understanding

An order uses five booleans for its lifecycle. How many combinations can the fields hold, and why is that a problem?

Each flag doubles the combinations: 2⁵ = 32. The lifecycle has around seven legal states, so most combinations should be impossible, but nothing in the type stops them.

In the State pattern, who decides the next state after ship()?

State objects own the transition rules. The context just forwards events and stores the returned state, so illegal moves can't be made from outside.

What should happen when refund() is called on an order in Created?

An illegal event is a caller bug or a race; it must be visible. Ignoring it hides lost operations, and allowing it corrupts the lifecycle.

When is an enum with a transition table a better fit than state classes?

An enum plus a table of allowed transitions is compact and safe for rule-only lifecycles. Once states need their own data or behaviour, records or classes per state pay off.

What's the advantage of record Shipped(PaymentId payment, TrackingNumber tracking) over a nullable trackingNumber field on Order?

Putting per-state data inside the state makes illegal combinations impossible to construct, not just checked against. Code that has a Shipped knows the tracking number is there.
