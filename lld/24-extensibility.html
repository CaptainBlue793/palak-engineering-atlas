Designing for Extensibility

Extensibility means the next feature is an addition rather than a surgery. Patterns like Strategy give you the shape; this chapter is about the machinery around them. Where do extension points go, how do implementations get discovered and registered, when should behaviour live in configuration instead of code, and how do feature flags let you ship code before you turn it on? Each tool has a cost, and the last one has caused one of the most expensive software incidents on record.

  • Place extension points where change is expected, and design them as stable contracts (SPIs)
  • Register implementations with a registry or Java's ServiceLoader
  • Move the right things into typed, validated configuration, and keep logic in code
  • Implement feature flags with deterministic percentage rollout, and retire them
  • Evolve an extension interface without breaking existing implementations

Extension points are contracts

An extension point is a place in your design where new behaviour plugs in without editing existing code: a PaymentGateway, an Exporter, a Middleware, an event listener. The code that plugs in is written against an interface you publish, often called a Service Provider Interface (SPI): the API that providers implement, as opposed to the API that callers call. An SPI is a promise, and it needs four things spelled out:

Part of the contractQuestion it answersFor an Exporter SPI
InterfaceWhat must a provider implement?String format(), void export(Report r, OutputStream out)
RegistrationHow does the system find it?A registry at startup, or ServiceLoader
Lifecycle and threadingWhen is it created? Is it shared across threads?One instance per application; must be thread-safe and stateless
CompatibilityHow will the contract change without breaking providers?New methods only as default methods; never change an existing signature

Extension points aren't free: each is an interface to maintain forever, a registration mechanism, and a place where unknown code runs inside your process. So place them where the requirements say variation lives (Chapter 21), and keep everything else concrete.

Discovering implementations: registries and ServiceLoader

Inside one codebase, a registry filled in the composition root (Chapter 10) is the simplest and most explicit way to connect implementations to an extension point. When providers ship as separate JARs, like a PDF exporter from another team or a database driver from a vendor, Java has a built-in mechanism: java.util.ServiceLoader. Each provider JAR declares its implementation, and your code discovers every one on the classpath without naming them:

// In your code: the SPI and the lookup
public interface Exporter { String format(); void export(Report r, OutputStream out) throws IOException; }

Map<String, Exporter> exporters = ServiceLoader.load(Exporter.class).stream()
	.map(ServiceLoader.Provider::get)
	.collect(Collectors.toMap(Exporter::format, e -> e));      // duplicate formats fail fast here

// In the provider's JAR, a text file named after the interface:
//   META-INF/services/com.acme.reports.Exporter
//     com.partner.pdf.PdfExporter
// or, with Java modules, in module-info.java:
//   provides com.acme.reports.Exporter with com.partner.pdf.PdfExporter;

That's the mechanism JDBC drivers use (Chapter 10). It's powerful and a little magical: what runs depends on which JARs are present. Prefer an explicit registry unless providers genuinely come from outside your build, and either way, log the list of registered implementations at startup so “which exporters are active?” is answerable from the logs.

Configuration: data, not logic

Some things should change without a code release: a timeout, a rate limit, which region a feature is enabled in, the URL of a partner API. Those belong in configuration. The rules for doing it safely:

  • Parse config into typed records at startup, not strings read throughout the code. record RateLimits(int perMinute, Duration window) instead of config.get("rl.pm") in twelve places.
  • Validate everything at startup and fail fast. A negative timeout or a missing URL should stop the process from starting, not fail the first request at 3 a.m.
  • Keep logic in code. Numbers, names, lists and switches are data. Conditions, loops and branching rules are code; once YAML grows ifs, it's a programming language without a compiler, types or tests.
public record CheckoutConfig(URI paymentsUrl, Duration paymentTimeout, int maxItems) {
	public CheckoutConfig {                                                // validated once, at startup
		Objects.requireNonNull(paymentsUrl, "payments.url is required");
		if (paymentTimeout.isNegative() || paymentTimeout.isZero()) throw new IllegalArgumentException("payments.timeout must be positive");
		if (maxItems < 1) throw new IllegalArgumentException("checkout.maxItems must be ≥ 1");
	}
}

Feature flags

A feature flag decides at run time whether a code path is active. It separates deploying code from releasing it: the new checkout can ship dark, be turned on for employees, then 5% of users, then everyone, and be turned off in seconds if error rates rise. Flags come in a few kinds with very different lifetimes:

KindPurposeLifetime
Release toggleShip unfinished or risky code dark, roll out graduallyDays to weeks; delete after full rollout
ExperimentA/B test two variants against a metricUntil the experiment concludes
Ops / kill switchTurn off an expensive or failing feature under loadLong-lived, owned by operations
PermissionEnable a feature per plan, tenant or rolePermanent: really product configuration

Percentage rollouts must be deterministic: the same user must get the same answer on every request, or they'll see the new checkout, then the old one, then the new one. The standard technique hashes the flag name and the user id into a bucket from 0 to 99 and compares it with the rollout percentage. Including the flag name means different flags pick different 5% slices of users, so the same unlucky users aren't the guinea pigs for everything:

public final class FlagEvaluator {
	private final FlagStore store;                                          // flag rules, refreshed from config

	public boolean isEnabled(String flag, UserId user) {
		FlagRule rule = store.rule(flag).orElse(FlagRule.OFF);              // unknown flag: off, never on
		if (rule.killed()) return false;                                     // kill switch wins
		if (rule.allowlist().contains(user)) return true;                   // employees, testers
		return bucket(flag, user) < rule.percent();                        // stable 0–99 bucket
	}
	static int bucket(String flag, UserId user) {
		byte[] h = sha256(flag + ":" + user.value());                       // stable across restarts and machines
		return Math.floorMod(ByteBuffer.wrap(h).getInt(), 100);
	}
}

Note what isn't used: String.hashCode is stable in practice but not a well-mixed hash, and Math.random() would change every request. Business code asks flags.isEnabled("new-checkout", user) through an injected interface (Chapter 8), so tests can pass a fixed answer.

Evolving an extension point

Once other teams implement your SPI, changing it is changing their code. The safe moves are additive: add a method as a default with sensible behaviour (P4), add optional fields to parameter records, and add new, separately named interfaces for new capabilities. The breaking moves are the obvious ones: changing a signature, removing a method, or changing what a method is allowed to throw. When a break is unavoidable, add the new interface alongside the old, adapt old providers to it (Chapter 12), and remove the old one only after every provider has moved.

public interface Exporter {
	String format();
	void export(Report r, OutputStream out) throws IOException;
	default boolean supportsStreaming() { return false; }      // added in v2: old providers still compile and behave
}
🧠
Knight Capital, 2012: the flag that woke up dead code

On 1 August 2012, Knight Capital deployed new trading software to its order-routing servers. The deployment missed one of eight servers, which still contained old, unused code called “Power Peg”. The new release repurposed an existing flag that the old code also read. When the flag was switched on, the eighth server began executing the dormant logic, sending millions of unintended orders. In about 45 minutes the firm lost roughly 440 million US dollars, and it was acquired months later. The lessons are all about flag hygiene: delete dead code and retired flags, never reuse a flag name for a new meaning, and make deployments verify that every server runs the same version.

⚠️
Common mistakes
  • Extension points everywhere, “just in case”. Each is an interface to support forever.
  • Changing an SPI's method signatures. Add default methods or new interfaces instead.
  • Unvalidated config read as strings all over the code. Parse into typed records and fail fast at startup.
  • Logic in configuration files. Rules with conditions belong in tested code.
  • Random or non-deterministic rollout buckets. Users flip between versions on every request.
  • Flags that never die, or get reused. Remove release toggles after full rollout, together with the dead branch.

Interview drill

Explain it simply: How would you let other teams add new export formats without changing your code?

How a strong answer sounds
I'd publish an Exporter interface as the extension point, with a clear contract: one instance per application, thread-safe, identified by a format name, new methods only added as defaults. Providers register at startup, either in our composition root's registry or, if they ship as separate JARs, through ServiceLoader with a META-INF/services entry. Duplicate format names fail at startup, and we log the registered exporters. The export service looks up an exporter by format and never names implementations.

Deeper: Design a feature-flag check that rolls a new checkout out to 5%, then 25%, then 100% of users, and can be turned off instantly.

How a strong answer sounds
An injected FeatureFlags interface with isEnabled(flag, userId). Rules come from a store that can be updated without a deploy. Evaluation order: kill switch first, then an allowlist for employees, then a deterministic bucket, a stable hash of flag name plus user id mod 100, compared with the rollout percentage. Deterministic means each user always sees the same version, and raising the percentage only adds users. An unknown flag defaults to off. After 100% for a while, we delete the flag and the old code path, because flags left in place become risk, as Knight Capital showed.

🧠 Key takeaways

  • An extension point is a contract (SPI): interface, registration, lifecycle and threading, and compatibility rules.
  • Register implementations explicitly in a registry; use ServiceLoader when providers ship as separate JARs.
  • Configuration is typed data validated at startup; logic stays in code.
  • Feature flags separate deploy from release; kinds differ in purpose and lifetime.
  • Percentage rollouts use a stable hash of flag and user, so each user always gets the same answer.
  • Evolve SPIs additively with default methods; delete retired flags and their dead code, and never reuse a flag.

Check your understanding

How does ServiceLoader find implementations of an interface?

Providers opt in with a declaration file or module directive naming their implementation class; ServiceLoader instantiates what's declared. It doesn't scan classes.

What belongs in configuration rather than code?

Configuration is data. Once it contains conditions and branching, it's code without a compiler, types or tests.

Why must a percentage rollout use a stable hash of flag and user instead of Math.random() < 0.1?

Random evaluation hits about 10% of requests, not 10% of users, so everyone sees both versions. A stable bucket per user makes the experience consistent and the rollout measurable.

You need to add a capability to an SPI that other teams already implement. What's the safe change?

A default method keeps every existing provider compiling and behaving as before; new providers can override it. Anything else breaks code you don't own.

What is the main lesson of the Knight Capital incident for flag design?

A repurposed flag activated old code left on one un-updated server. Flag hygiene and deployment verification would have prevented it; flags themselves weren't the problem.
