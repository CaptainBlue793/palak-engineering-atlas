Case Study: Chess

Chess is the case study where polymorphism earns its keep. In the parking lot, vehicle types differed only in data, so an enum won. Here each piece genuinely moves differently, the rules have famous special cases (castling, en passant, promotion), and one rule cuts across all of them: you may never leave your own king in check. This case study designs the board, pieces, move generation, check and checkmate, and history, and the board below runs exactly that design, verified against the standard move-count tests.

  • Scope a two-player chess game with explicit rules and statuses
  • Model pieces polymorphically, sharing the sliding-piece logic as data
  • Separate pseudo-legal move generation from the king-safety filter
  • Detect check, checkmate and stalemate
  • Record history for undo, and test a move generator with perft

Requirements and API

Clarify: two players, human or computer; standard rules including castling, en passant and promotion; the game rejects illegal moves and reports check, checkmate and stalemate; moves can be undone (for analysis, not in rated play); the design should allow a clock and a computer player later. Out of scope for the core: the fifty-move rule and threefold repetition (history makes them easy to add), and draw offers.

public interface Game {
	List<Move> legalMoves();                             // for the side to move
	MoveResult play(Move move);                           // rejects anything not in legalMoves()
	GameStatus status();                                   // ACTIVE, CHECK, CHECKMATE, STALEMATE, RESIGNED
	void undo();
	Board board();                                         // read-only view for rendering
}

public record Square(int file, int rank) {                  // 0..7 each; validated
	public Optional<Square> plus(int df, int dr) { int f = file + df, r = rank + dr; return f < 0 || f > 7 || r < 0 || r > 7 ? Optional.empty() : Optional.of(new Square(f, r)); }
}

public record Move(Square from, Square to, Piece piece, Piece captured, Special special) {}   // special: NONE, CASTLE_K, CASTLE_Q, EN_PASSANT, PROMOTION(type), DOUBLE_PUSH

Notice play takes a Move and checks it against legalMoves(): the game never trusts the caller, whether that's a UI, a network message from the other player, or a buggy engine. Validation lives in one place, and every client gets it.

Board, pieces and players

The Board maps squares to pieces and knows the position-level facts: whose turn, castling rights, the en passant target. Make it immutable: apply(move) returns a new board. A board is 64 references, so copying is cheap, and immutability pays for itself three times: legal-move checking can try a move without undoing it, undo is popping the previous board, and a computer player can explore positions on other threads without locks.

Pieces are where behaviour really differs, so here a sealed hierarchy is right. But not every piece needs its own algorithm: rook, bishop and queen all “slide” until blocked, differing only in directions, and knight and king both “jump” to fixed offsets. So the hierarchy is thin, and the shared movement is expressed as data plus two helpers.

public sealed interface Piece permits King, Queen, Rook, Bishop, Knight, Pawn {
	Color color();
	Stream<Move> candidateMoves(Board b, Square from);      // pseudo-legal: ignores own-king safety
}

record Rook(Color color) implements Piece {
	public Stream<Move> candidateMoves(Board b, Square from) { return Moves.slide(b, from, this, Dir.ORTHOGONAL); }
}
record Queen(Color color) implements Piece {
	public Stream<Move> candidateMoves(Board b, Square from) { return Moves.slide(b, from, this, Dir.ALL); }
}
record Knight(Color color) implements Piece {
	public Stream<Move> candidateMoves(Board b, Square from) { return Moves.jump(b, from, this, Dir.KNIGHT_JUMPS); }
}
// Bishop: slide DIAGONAL. King: jump ADJACENT + castling. Pawn: its own rules (push, double push, captures, en passant, promotion).

final class Moves {
	static Stream<Move> slide(Board b, Square from, Piece p, List<Dir> dirs) {
		Stream.Builder<Move> out = Stream.builder();
		for (Dir d : dirs) {
			Optional<Square> s = from.plus(d.df(), d.dr());
			while (s.isPresent()) {
				Optional<Piece> there = b.at(s.get());
				if (there.isEmpty()) { out.add(Move.quiet(from, s.get(), p)); s = s.get().plus(d.df(), d.dr()); continue; }
				if (there.get().color() != p.color()) out.add(Move.capture(from, s.get(), p, there.get()));
				break;                                                     // blocked, by either colour
			}
		}
		return out.build();
	}
}

Players are a strategy: interface Player { Move choose(Game game); }, with a human implementation fed by the UI and a computer implementation that searches. The Game doesn't know which it has, so “human vs computer” and “computer vs computer” need no changes to the rules code.

Move generation per piece

Generating legal moves is a two-stage pipeline, and keeping the stages separate is the key design decision. Stage one, pseudo-legal generation, asks each piece where it could go by its own movement rules, ignoring checks. Stage two, the king-safety filter, applies each candidate to a copy of the board and discards any move after which the mover's king is attacked. That single filter handles pins, moving into check, and failing to escape check, without a special case for any of them.

Check and checkmate

“Is my king attacked?” runs for every candidate move, so it must be cheap. Rather than generating all the opponent's moves, look outward from the king's square: is there an enemy knight a knight's jump away, an enemy pawn on the right diagonal, the enemy king adjacent, or, along each ray, an enemy rook or queen (straight) or bishop or queen (diagonal) as the first piece hit? That's a few dozen square lookups instead of generating a whole move list.

boolean isAttacked(Square sq, Color by) {
	if (any(sq, Dir.KNIGHT_JUMPS, by, Knight.class)) return true;
	if (any(sq, Dir.ADJACENT, by, King.class)) return true;
	if (pawnAttacks(sq, by)) return true;                                      // the two diagonals behind sq, from by's side
	return firstOnRay(sq, Dir.ORTHOGONAL, by, Rook.class, Queen.class)
	    || firstOnRay(sq, Dir.DIAGONAL, by, Bishop.class, Queen.class);
}

GameStatus status() {
	boolean check = board.isAttacked(board.kingOf(turn), turn.opponent());
	if (!legalMoves().isEmpty()) return check ? GameStatus.CHECK : GameStatus.ACTIVE;
	return check ? GameStatus.CHECKMATE : GameStatus.STALEMATE;               // no legal moves: the only difference is check
}

Move history and undo

History is a list of Moves (for notation, the fifty-move rule and replays) plus, with an immutable board, a stack of positions: undo pops the last board, which is Memento (Chapter 17) for free. The alternative is Command with reversible moves on a mutable board, where each move stores what it captured, the castling rights and the en passant square it replaced; that's what engines searching millions of positions do, because allocating a board per position is too slow for them. For a game server, the immutable board is simpler and safer. Repetition detection follows directly: count identical positions in the history, which is why a position needs a proper equals (or a Zobrist hash, the standard 64-bit position fingerprint).

🧠
How engines test move generators: perft

Move generation is famously easy to get almost right: a missed en passant corner case or a castling rule off by one square only shows up in rare positions. Chess programmers test it with perft (performance test): count every position reachable in exactly n moves and compare with published values. From the starting position the counts are 20, 400, 8,902, 197,281 and 4,865,609 for depths 1 to 5; specially constructed positions like “Kiwipete” pack castling, en passant, promotions and pins together to catch subtler bugs. Strong engines such as Stockfish represent the board as bitboards (64-bit integers, one bit per square) with make/unmake moves for speed, but they're validated with the same perft counts, which is exactly the test the button above runs on this chapter's much simpler design. It's also a model for testing any rules engine: a known-answer test that exercises every rule in combination.

⚠️
Common mistakes
  • Putting the king-safety rule inside each piece, duplicating it six times and missing pins.
  • A separate class for rook, bishop and queen logic when they differ only in directions.
  • Trusting the UI's move; validate every move against the legal list.
  • Forgetting position state: castling rights and the en passant square aren't visible from piece placement alone.
  • Castling through or out of check, or after the rook has moved or been captured.
  • Checking “is the king attacked?” by generating every enemy move; scan outward from the king.
  • No automated perft test, so rare-rule bugs surface only in real games.

Interview drill

Explain it simply: How do you prevent a player from making a move that leaves their king in check?

How a strong answer sounds
I split move generation in two. Each piece generates its pseudo-legal moves from its own movement rules. Then the game filters them: apply each move to a copy of the board (easy, since my board is immutable) and reject it if the mover's king is attacked in the result. The attack check scans outward from the king square for knights, pawns, the king, and the first piece on each ray. That one filter handles pins, moving the king into check, and having to respond to check, with no special cases.

Deeper: Add a chess clock and a computer opponent. What changes, and what doesn't?

How a strong answer sounds
Neither touches the rules. The clock is an observer of the game (Chapter 16): on each MoveMade event it stops the mover's time and starts the opponent's, using an injected clock, with increments as a policy; when a flag falls it tells the game, which adds a LOST_ON_TIME status. The computer opponent is another Player implementation: it calls legalMoves(), searches with minimax and alpha-beta over board.apply results, which is safe to parallelise because boards are immutable, and returns a move through the same play call a human uses, so it's validated identically. If search speed became the bottleneck, I'd switch the engine's internal board to a mutable make/unmake representation, while the game keeps its immutable one.

🧠 Key takeaways

  • Use polymorphism where behaviour differs (pieces) and data where it doesn't (sliding directions, jump offsets).
  • Generate pseudo-legal moves per piece, then filter all of them by one king-safety check.
  • Detect attacks by scanning outward from the king, not by generating enemy moves.
  • Checkmate and stalemate both mean “no legal moves”; check decides which.
  • An immutable board makes legality checks, undo (Memento) and parallel search simple; engines trade it for make/unmake speed.
  • Test move generation with perft counts against known values.

Check your understanding

Why is a class hierarchy right for chess pieces but an enum was right for parking-lot vehicles?

Polymorphism pays when behaviour varies. Even here, sliding pieces share one algorithm parameterised by directions.

A knight is pinned to its king by an enemy bishop. Where is that handled in this design?

The knight generates its moves normally; applying any of them exposes the king, so the one filter rejects them.

It's black's turn, black is not in check, and black has no legal moves. What's the result?

No legal moves plus in check is checkmate; no legal moves without check is stalemate.

Which information is NOT visible from the piece placement alone, and must be stored in the position?

Whether a king or rook has ever moved, and whether the last move was a double pawn push, depend on history, so the position records them.

What does a perft test compare?

Any bug in move generation (a missing castle, a wrong en passant) changes the counts, so perft catches rule bugs across all combinations.
