Domain Modeling (DDD Lite)

Domain-Driven Design is a large body of ideas, much of it about organising teams and systems. A handful of its building blocks pay off in every design, and in every LLD interview: entities and value objects, aggregates that guard invariants, domain events that announce what happened, and a clear split between services that hold business rules and services that just run a use case. This chapter takes just those.

  • Decide whether a concept is an entity or a value object
  • Draw aggregate boundaries around real invariants, and keep them small
  • Reference other aggregates by id and change one aggregate per transaction
  • Record domain events in the aggregate and publish them after commit
  • Tell a domain service from an application service

Entities vs value objects

An entity has an identity that stays the same while its attributes change: order 8412 is still order 8412 after you add a line and after it ships. Two entities with identical attributes are still two different things. A value object is defined entirely by its values and has no identity: two Money(1999, EUR) are interchangeable, and “changing” one means replacing it with another. Value objects are immutable, compare by value, and validate themselves on construction (P6).

EntityValue object
IdentityHas an id; equality by idNone; equality by all fields
MutabilityChanges state over its lifecycle, through methods that keep it validImmutable; replace, don't modify

ExamplesOrder, Account, Session, DriverMoney, EmailAddress, DateRange, SeatNumber, OrderId

The same concept can be either, depending on the domain. An Address on an order is a value: if the customer moves, the order's shipping address shouldn't change. In a postal service's system, an address is an entity with a history of residents. Ask: does anything need to track this particular one over time? If not, make it a value object; most concepts should be. A design with many small value objects and a few entities is usually easier to get right than one where everything has an id and setters.

Aggregates and invariants

An aggregate is a cluster of entities and value objects that must stay consistent together, with one entity as its root. The boundary is drawn around an invariant: a rule that must hold after every change, like “a session never has more confirmed bookings than seats”. Everything that rule reads must be inside the boundary, so that one object can check it, and one transaction can save it, atomically. Four rules follow:

  • Only the root is referenced from outside. Callers ask the Session to book; they never add a Booking to its list directly.
  • Reference other aggregates by id, not by object: a booking holds an AttendeeId, not an Attendee. That stops one save from dragging in half the object graph.
  • Change one aggregate per transaction. The aggregate is the unit of consistency, and its version column (Chapter 26) is the unit of locking.
  • Keep aggregates small. Only as big as the true invariants force; everything else is kept in step by events, a little later (“eventually consistent”).
public final class Session {                                   // aggregate root
	private final SessionId id;
	private final int capacity;
	private final Map<AttendeeId, Booking> bookings = new LinkedHashMap<>();   // other aggregates by id
	private final List<DomainEvent> events = new ArrayList<>();
	private long version;

	public BookingId book(AttendeeId who, Instant now) {
		if (bookings.containsKey(who)) throw new AlreadyBooked(id, who);
		if (bookings.size() >= capacity) throw new SessionFull(id);          // the invariant, checked in one place
		Booking b = Booking.confirm(who, now);
		bookings.put(who, b);
		events.add(new BookingConfirmed(id, who, b.id(), now));
		if (bookings.size() == capacity) events.add(new SessionFilled(id, now));
		return b.id();
	}

	public List<DomainEvent> pullEvents() { List<DomainEvent> out = List.copyOf(events); events.clear(); return out; }
}

Where to draw the boundary is the real design decision, and it's a trade-off between consistency and concurrency. Too large, and unrelated requests fight over one version number; too small, and the invariant can't be checked atomically. Try the three boundaries below on a conference with 20 sessions of 10 seats each, where one keynote session is far more popular than the rest.

A version conflict isn't an error the user sees: the request reloads and retries after a short random backoff. But every retry is wasted work and extra latency, and under load a hot aggregate can retry many times over.

The Conference aggregate is correct but serialises every booking in the conference through one version, and loads every booking to add one. The Booking-alone design scales perfectly and oversells the keynote, because no single object sees the count it's checking. The Session boundary is the smallest one that still contains the rule. That's the general answer: as small as possible, and no smaller than the invariant.

Domain events

Many rules span aggregates without needing to be instantly consistent: when a session fills, open a waitlist; when a booking is confirmed, send a ticket and update the attendee's schedule. Putting those in the book transaction would widen it across several aggregates and a mail server. Instead the aggregate records a domain event, an immutable fact named in the past tense (BookingConfirmed, SessionFilled), and other parts of the system react after the booking commits.

The outbox is what makes events reliable. Publishing straight to a message broker from the service risks two failure modes: the commit succeeds and the publish fails (a lost event), or the publish succeeds and the commit fails (an event for something that never happened). Writing events to an outbox table inside the same transaction, and having a relay publish them afterwards, removes both. Since the relay may publish an event more than once, handlers use the event id to ignore repeats (Chapter 25's idempotency, again).

Services: domain vs application

Not every piece of logic belongs on an entity. When a rule involves several aggregates or an outside policy and no single object owns it, it goes in a domain service: a stateless class, named in the domain's language, holding business logic. Examples: a PricingPolicy that combines a fare, a surge multiplier and a promo; a SeatAllocator that picks adjacent seats. An application service is different: it runs one use case, and contains no business rules at all. It loads aggregates, calls domain methods, saves, and controls the transaction.

Domain serviceApplication service
ContainsBusiness rules that no single aggregate ownsUse-case orchestration: load, call, save, commit
Depends onDomain types only (maybe an interface for a policy's data)Repositories, transactions, clocks, authorization

Tested withPlain unit tests, no fakesIn-memory repositories and a fixed clock

A last idea from DDD worth keeping: use the domain's own words in the code, the ubiquitous language. If the business says a session “fills” and an attendee is “waitlisted”, the code says SessionFilled and waitlist(attendee), not updateStatus(3). And accept that the same word can mean different things in different parts of a business: a “product” in the catalogue has descriptions and photos, a “product” in shipping has a weight and dimensions. Those are separate models (DDD calls each area a bounded context), not one giant class.

The oversized aggregate

Vaughn Vernon's essay “Effective Aggregate Design” walks through a project-management tool whose first model made Product one large aggregate containing its backlog items, releases and sprints. It was consistent, but when several team members worked on the same product at once, their unrelated edits collided on the aggregate's version and failed with concurrency errors, and loading a product meant loading everything in it. The redesign split backlog items, releases and sprints into their own aggregates that refer to the product by id. That experience is where the widely quoted rules come from: model true invariants in consistency boundaries, design small aggregates, reference other aggregates by identity, and use eventual consistency outside the boundary.

⚠️
Common mistakes
  • Anemic domain model: entities with only getters and setters, with every rule in services. The invariants end up checked in some places and not others.
  • Giant aggregates built from “these things are related”, rather than “this rule reads them together”.
  • Object references between aggregates, so saving one cascades into others and transaction boundaries blur.
  • Changing two aggregates in one transaction as a habit. Use an event and a second transaction unless a real invariant spans both.
  • Publishing events before commit, or outside the transaction without an outbox: lost or phantom events.
  • Everything as an entity with an id, where immutable value objects would be simpler and safer.

Interview drill

Explain it simply: What is an aggregate, and how do you decide how big it is?

How a strong answer sounds
It's a group of objects that must stay consistent together, accessed through one root and saved in one transaction. I size it by the invariants: everything a rule has to read at once goes inside, so the root can check the rule and one version-checked save protects it. Anything else stays out and is referenced by id, because a bigger aggregate means more contention and bigger loads. Rules between aggregates are kept by domain events, eventually.

Deeper: In a ride-hailing design, where do the boundaries go for Rider, Driver, Trip and Payment?

How a strong answer sounds
Each is its own aggregate, referencing the others by id. Trip owns the trip's state machine (requested, accepted, in progress, completed) and its fare breakdown as value objects. Driver owns availability: the invariant “a driver is on at most one active trip” lives there, so accepting a trip changes the driver (mark busy, version-checked, so two trips can't claim one driver) and the trip records the acceptance; if both must change atomically I'd accept that one small cross-aggregate transaction or use the driver change first and a DriverAssigned event to update the trip. Payment reacts to TripCompleted via the outbox, charging idempotently by trip id. Fare calculation is a domain service, FarePolicy, because it combines distance, time, surge and promotions that no single aggregate owns.

🧠 Key takeaways

  • Entities have identity and a lifecycle; value objects are immutable and compare by value. Prefer value objects.
  • An aggregate is a consistency boundary drawn around invariants, with one root as the only entry point.
  • Reference other aggregates by id and change one aggregate per transaction.
  • Make aggregates as small as possible and no smaller than the invariant: too big serialises, too small can't enforce the rule.
  • Aggregates record past-tense domain events; an outbox publishes them reliably after commit, to idempotent handlers.
  • Domain services hold rules no single aggregate owns; application services orchestrate use cases and hold no rules.

Check your understanding

In an online shop, which should be a value object?

Nothing needs to track that particular address over time; it's defined by its values and should never change if the customer later moves. Accounts, orders and warehouses have identities and lifecycles.

What should decide an aggregate's boundary?

The boundary exists so the root can check a rule and one transaction can save it. Anything the rule doesn't need stays outside, to keep contention and load size down.

Bookings are modelled as independent aggregates, each checking countBookings(session) < capacity before inserting itself. What goes wrong under load?

No single object owns the count, so no version check protects it. The invariant belongs to the session, so the session must be the aggregate.

Why write domain events to an outbox table in the same transaction as the aggregate?

Publishing separately from the commit can lose events or publish phantom ones. The outbox ties them together; delivery is at least once, so handlers must be idempotent.

A BookSeatService loads a session, calls session.book(attendee), saves it and commits. What kind of service is it?

It handles loading, saving and the transaction, with no business rules of its own. A domain service would contain rules, such as a pricing or seat-allocation policy.
