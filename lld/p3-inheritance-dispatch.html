Inheritance & Dynamic Dispatch

A logging framework calls appender.append(event) without knowing whether the appender writes to the console, a file or a JSON stream. The right code still runs every time. That is dynamic dispatch, and it is what makes most design patterns work. Inheritance is one way to get it, and also one of the easiest ways in Java to build something fragile. This chapter covers both sides.

  • Write a subclass with extends, call the parent constructor with super(...), and reuse parent code with super.method()
  • Tell overriding (chosen at run time) from overloading (chosen at compile time)
  • Predict which method runs for any declared type and runtime class, using the method table
  • Use @Override and final to make intent explicit
  • Explain the fragile base class problem, and why calling overridable methods from a constructor is a bug

extends, super and what a subclass inherits

A class can extend one other class. The subclass inherits every non-private method and field of its parent (the superclass), can add its own, and can override inherited methods by redefining them with the same signature. Every Java class extends exactly one class; if you don't say which, it extends Object, which is why every object has toString(), equals() and hashCode().

A small logging framework shows all of it. An appender takes a message and writes it somewhere:

Appender.java, FileAppender.java, JsonFileAppender.java
public class Appender {
	public void append(String msg) { System.out.println(format(msg)); }
	protected String format(String msg) { return "[" + Instant.now() + "] " + msg; }
	public void flush() { System.out.flush(); }
}

public class FileAppender extends Appender {
	private final BufferedWriter out;

	public FileAppender(BufferedWriter out) {
		super();                                   // run Appender's constructor first
		this.out = Objects.requireNonNull(out);
	}
	@Override public void append(String msg) { writeLine(format(msg)); }  // replaces the parent's
	@Override public void flush() { /* out.flush(), wrapped for IOException */ }
	public void rotate() { /* start a new file: only FileAppender has this */ }
	private void writeLine(String line) { /* out.write(line); out.newLine(); */ }
}

public class JsonFileAppender extends FileAppender {
	public JsonFileAppender(BufferedWriter out) { super(out); }
	@Override protected String format(String msg) {          // only formatting changes
		return "{\"ts\":\"" + Instant.now() + "\",\"msg\":\"" + msg + "\"}";
	}
}
Reading it: FileAppender replaces append and flush and adds rotate. JsonFileAppender replaces only format, and inherits everything else from FileAppender. (Escaping quotes inside msg is left out to keep the listing short; a real JSON appender must do it.)

Three details in that listing matter:

  • super(...) runs the parent's constructor first. Before a subclass constructor can use this, the parent part of the object is built. If you don't write super(...), Java inserts super() for you, which fails to compile if the parent has no no-argument constructor.
  • super.method() calls the parent's version of an overridden method, so an override can extend behaviour instead of replacing it: super.append(msg); metrics.increment();.
  • @Override asks the compiler to check that you really are overriding something. Misspell the name, or get a parameter type wrong, and you get a compile error instead of a silent new method.

Dynamic dispatch: the object decides

A variable has a declared type (also called the static type), fixed when you write the code. The object it refers to has a runtime class, fixed when the object is created. They can differ, because a variable of type Appender may hold a reference to any subclass object:

Appender a = new JsonFileAppender(writer);   // declared type Appender, runtime class JsonFileAppender
a.append("server started");               // which append runs? which format?

Java answers in two stages, and the two stages use different types:

  1. Compile time, using the declared type. The compiler checks that Appender has an append(String) method. If it didn't, the code wouldn't compile, whatever the object really is. That's why a.rotate() is an error here: Appender has no rotate.
  2. Run time, using the object's class. The JVM looks up append in the method table (often called a vtable) of the object's actual class. JsonFileAppender didn't override append, so its table entry points at FileAppender.append. That method calls format(msg), which is dispatched again through the same table, and the entry for format points at JsonFileAppender.format.

So the line writes a JSON line to the file. The calling code never mentioned files or JSON. This is what every later pattern leans on: Strategy, Decorator, State and Observer all mean “call a method through a general type and let the object decide”.

Each class's method table lists every method it can respond to and whose code runs. Purple entries are written in that class; grey ones are inherited. The compiler only checks the declared type; the JVM only looks at the created object's table. (format is protected, so the call is shown as it would be written from inside the same package.)

Is all this lookup slow? No. The table lookup is one or two memory reads, and the JIT compiler removes it entirely when it sees that a call site only ever meets one class, which is the common case. Don't avoid polymorphism for speed.

Overriding vs overloading

The two words sound alike and behave completely differently. Overriding means a subclass redefines a method with the same signature, and the JVM picks the version at run time from the object's class. Overloading means one class has several methods with the same name but different parameter types, and the compiler picks one at compile time from the declared types of the arguments.

public class AuditLog {
	public void record(Object o) { write("object: " + o); }
	public void record(String s) { write("text: " + s); }
}

Object payload = "login ok";   // declared Object, actually a String
audit.record(payload);           // "object: login ok": chosen by the declared type, at compile time
audit.record("login ok");        // "text: login ok"

The accidental kind is the classic bug. public boolean equals(Session other) looks like it overrides Object.equals, but Object.equals takes an Object, so this is an overload. A HashSet calls equals(Object), never sees your method, and treats equal sessions as different. Put @Override on it and the compiler rejects it immediately (P6 writes equals properly).

final, and the fragile base class problem

Overriding lets a subclass change behaviour the parent's own code depends on. That is the source of a whole category of bugs, and the reason Java has final. A final method can't be overridden. A final class can't be extended at all: String and Integer are final, which is why nobody can make a String subclass that mutates.

Here is the best-known example, from Effective Java. You want a HashSet that counts how many elements were ever added, so you extend it and override both ways of adding:

public class InstrumentedHashSet<E> extends HashSet<E> {
	private int addCount = 0;

	@Override public boolean add(E e) { addCount++; return super.add(e); }
	@Override public boolean addAll(Collection<? extends E> c) { addCount += c.size(); return super.addAll(c); }
	public int addCount() { return addCount; }
}

s.addAll(List.of("a", "b", "c"));
s.addCount();   // 6, not 3

The subclass is correct only if it knows exactly which of the parent's methods call which others, an implementation detail the parent never documented and could change in the next JDK release. That is the fragile base class problem: changes inside a superclass can break subclasses that never changed. The rule that follows, from the same book, is design for inheritance or prohibit it. Either document which methods call which (and keep that stable forever), or make the class final. Every class in this course is final unless it is deliberately built to be extended. The fix for this particular class is composition, the subject of P5.

🧠
The constructor trap: a base class calling an overridable method

Suppose Appender's constructor logs a startup line with append(format("appender started")), and a subclass overrides format to prepend a private final String prefix set in its own constructor. new PrefixAppender("app: ") prints nullappender started. The subclass constructor calls super() first, the parent constructor calls format, dispatch sends it to the subclass's override, and prefix hasn't been assigned yet, so it is still null. Even a final field can be seen before it is set this way. The rule: constructors must not call methods that subclasses can override. Make such methods private or final, or the class final.

⚠️
Common mistakes
  • Leaving out @Override. A typo or a wrong parameter type silently creates an overload that never gets called.
  • Expecting overloads to be picked by the runtime type. They are picked from the declared types of the arguments, at compile time.
  • Calling a method that isn't on the declared type. Appender a = ...; a.rotate() doesn't compile, even if a really holds a FileAppender.
  • Extending a class you don't control (a JDK collection, a library class) to change its behaviour. Its internal self-calls can double or skip your logic, and can change between versions.
  • Calling overridable methods from a constructor. The override runs before the subclass's fields are set.
  • Using inheritance only to reuse code. If the subclass isn't truly a kind of the parent, use composition (P5).

Interview drill

Explain it simply: What's the difference between overriding and overloading, and when is each one decided?

How a strong answer sounds
Overriding is a subclass redefining an inherited method with the same signature. The JVM picks which version runs at run time, from the actual class of the object. Overloading is several methods with the same name and different parameter types. The compiler picks one at compile time, from the declared types of the arguments. So Object o = "x"; log(o) calls log(Object) even though there's a log(String). I always use @Override so an intended override can't silently become an overload.

Deeper: Someone extends HashSet to count additions by overriding add and addAll, and the count comes out doubled for addAll. Explain why, and how you'd design it instead.

How a strong answer sounds
The inherited addAll is implemented by calling add for each element, and that call is dynamically dispatched to the overridden add, so each element is counted once in addAll and again in add. The subclass depends on an undocumented implementation detail of its parent, which is the fragile base class problem. I'd use composition instead: a class that implements Set and holds a private Set, forwarding every call and counting in its own methods. Then its behaviour depends only on the public Set contract, not on how HashSet is written.

🧠 Key takeaways

  • A subclass inherits non-private members, can add its own, and overrides by redefining a method with the same signature. super(...) builds the parent part first.
  • The compiler checks calls against the declared type; the JVM runs the version in the object's own method table.
  • Calls from inside inherited code to overridable methods (this.format()) are dispatched too.
  • Overriding is chosen at run time by the receiver; overloading at compile time by the arguments' declared types. Always write @Override.
  • Subclasses depend on their parent's internal self-calls: the fragile base class problem. Design for inheritance or make the class final.
  • Constructors must not call methods a subclass can override.

Check your understanding

With the chapter's classes, Appender a = new JsonFileAppender(w); a.flush(); runs which method?

The object is a JsonFileAppender, which doesn't override flush, so its method-table entry points at the nearest override up the chain: FileAppender.flush. The declared type only matters for the compile-time check that flush exists.

Appender a = new FileAppender(w); a.rotate(); What happens?

The compiler checks the call against the declared type, Appender, which has no rotate. The runtime class is never consulted for this check. You'd need a variable of type FileAppender (or a cast) to call it.

A class has record(Object o) and record(String s). Which runs for Object p = "ok"; audit.record(p);?

Overload resolution uses the declared type of the argument expression, Object. Dynamic dispatch applies only to the object the method is called on, not to argument types.

InstrumentedHashSet overrides add (count++) and addAll (count += size) and calls super in both. After addAll of three new elements, what is the count?

addAll adds 3, then the inherited implementation calls add once per element, each dispatched to the override, adding 3 more. The subclass silently depends on how its parent is implemented: the fragile base class problem.

A base-class constructor calls format("started"). A subclass overrides format to use its private final String prefix, assigned in its own constructor after super(). What does the override see?

Dispatch works inside constructors, so the override runs, but the subclass's constructor body hasn't run yet, and prefix still holds its default, null. Constructors should only call private or final methods.
