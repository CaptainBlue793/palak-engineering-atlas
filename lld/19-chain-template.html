Chain of Responsibility & Template Method

Every web request you've ever sent passed through a chain: log it, identify the caller, check their limit, validate the input, then finally do the work, and any step can stop the request early. That's Chain of Responsibility. Its neighbour, Template Method, fixes the order of steps in an algorithm and lets subclasses fill in some of them. Both are about structuring a sequence of steps; one uses composition, the other inheritance.

  • Build a handler chain where each handler either handles, passes on, or stops the request
  • Write servlet-filter-style middleware that calls the next handler explicitly
  • Decide handler order, and see what a bad order costs
  • Write a Template Method with a final skeleton, abstract steps and optional hooks
  • Choose between Template Method and Strategy

Chain of Responsibility: pass it along, or stop it

A request should be rejected at the first check it fails: no token means 401 before anyone parses the body; over quota means 429 before the database is touched. Chain of Responsibility arranges handlers in a sequence. Each one looks at the request and does one of three things: handles it completely and stops (like returning 401), does some work and passes it to the next handler (like adding a request id), or passes it on untouched. The sender doesn't know which handler will end up responding.

The modern form, used by servlet filters and most web frameworks, gives each handler an explicit next to call:

Middleware: each handler decides whether to call next
public interface Middleware {
	Response handle(Request req, Chain next);
}
public interface Chain { Response proceed(Request req); }

public final class Authenticate implements Middleware {
	private final TokenVerifier tokens;
	public Response handle(Request req, Chain next) {
		Optional<UserId> user = tokens.verify(req.header("Authorization"));
		if (user.isEmpty()) return Response.status(401);                  // handled: stop here
		return next.proceed(req.withAttribute("user", user.get()));        // enrich and pass on
	}
}

public final class Pipeline {
	private final List<Middleware> middleware;
	private final Handler endpoint;                                        // the real work, at the end
	public Response handle(Request req) { return at(0).proceed(req); }
	private Chain at(int i) {
		return i == middleware.size()
			? endpoint::handle
			: r -> middleware.get(i).handle(r, at(i + 1));
	}
}

new Pipeline(List.of(new RequestLogging(log), new Authenticate(tokens), new RateLimit(limiter), new ValidateBody(schema)), ordersEndpoint);
How it differs from Decorator: the structure is almost the same, but a decorator always delegates and adds behaviour around it, while a chain handler is expected to decide whether the request continues. Short-circuiting is the point. Each handler is one concern, testable alone with a fake next.

Order is policy

The list of handlers is short, but its order encodes real decisions. Authentication must come before a per-user rate limit, or there's no user to count against. Cheap checks should come before expensive ones, so junk traffic is rejected cheaply. Logging usually goes first, so even rejected requests are recorded. Try it with four kinds of request:

The classic Gang of Four version has each handler hold a reference to its successor instead of receiving next as a parameter. It works the same way, but wiring and reordering are harder, and a handler can't be reused in two chains. The explicit-next style above is what servlet Filters (chain.doFilter(request, response)), OkHttp interceptors and most middleware frameworks use.

Template Method: a fixed skeleton with open steps

Now a different kind of sequence. Every data-import job does the same things in the same order: open the source, read rows, parse each one, validate it, save the valid ones, record the failures, and produce a report. Only parsing and saving differ between a customers CSV and a products spreadsheet. Template Method writes the skeleton once, in a final method of an abstract class, and leaves the varying steps to subclasses:

ImportJob.java: the algorithm is fixed; two steps are open, one is optional
public abstract class ImportJob<T> {
	public final ImportReport run(Path file) throws IOException {     // the template method: final
		ImportReport report = new ImportReport(file);
		try (BufferedReader in = Files.newBufferedReader(file)) {
			String line; int n = 0;
			while ((line = in.readLine()) != null) {
				n++;
				try {
					T item = parse(line);                                // step: subclass must provide
					Optional<String> problem = validate(item);            // hook: optional
					if (problem.isPresent()) report.rejected(n, problem.get());
					else { save(item); report.imported(); }              // step: subclass must provide
				} catch (RuntimeException e) { report.rejected(n, e.getMessage()); }
			}
		}
		afterImport(report);                                            // hook: optional
		return report;
	}
	protected abstract T parse(String line);
	protected abstract void save(T item);
	protected Optional<String> validate(T item) { return Optional.empty(); }   // default: everything valid
	protected void afterImport(ImportReport r) { }                          // default: nothing
}

public final class CustomerImport extends ImportJob<Customer> {
	@Override protected Customer parse(String line) { String[] f = line.split(","); return new Customer(f[0], new EmailAddress(f[1])); }
	@Override protected void save(Customer c) { customers.upsert(c); }
	@Override protected Optional<String> validate(Customer c) { return blocked.contains(c.email()) ? Optional.of("blocked") : Optional.empty(); }
}
The vocabulary: the template method (run) is final, so subclasses can't reorder or skip steps. Abstract steps (parse, save) must be provided. Hooks (validate, afterImport) have default bodies that subclasses may override. Row-level errors are caught inside the loop, so one bad row can't stop an import of a million.

The JDK uses this all over. AbstractList implements dozens of List methods on top of two you provide, get(int) and size(). InputStream.read(byte[], int, int) is written in terms of the abstract single-byte read(). And the JsonHandler from P4 was a template method with one open step.

Template Method or Strategy?

Both let part of an algorithm vary. Template Method does it with inheritance: the variation is a subclass, chosen at compile time, and it can see protected internals of the base class, which brings the fragile base class risks from P3. Strategy does it with composition: the variation is an object passed in, chosen at run time. You can often turn a template method into a strategy by passing the steps in as functions:

new Importer<Customer>(CustomerCsv::parse, customers::upsert, Validators.notBlocked(blocked)).run(file);

Spring Security is a filter chain

A Spring Security application puts every HTTP request through a chain of servlet filters, each responsible for one thing: reading a session, parsing a bearer token, handling a login form, translating security exceptions into 401 or 403 responses, and finally checking whether the authenticated user may access the URL. Applications add their own filters by position (“before the username-password filter”), and one misplaced filter is a classic source of security bugs, such as an authorization check that runs before the user has been authenticated. It's Chain of Responsibility at the centre of millions of applications, and a good illustration that handler order is policy.

⚠️
Common mistakes
  • A handler that forgets to call next on its success path: every request stops there with an empty response.
  • Handlers that depend on each other implicitly, like rate limiting that needs the user but runs before authentication. Order the chain deliberately and in one place.
  • Expensive checks first. Put cheap rejections (auth, limits) before expensive ones (body parsing, database lookups).
  • A non-final template method. Subclasses can override the skeleton and skip steps. Make it final.
  • Too many hooks. A template with ten overridable methods is hard to understand and fragile. Fewer, documented hooks, or switch to strategies.
  • Deep template hierarchies (BaseImport → CsvImport → CustomerCsvImport → …). Prefer one level, or composition.

Interview drill

Explain it simply: What is Chain of Responsibility, and where have you seen it?

How a strong answer sounds
A request passes along a sequence of handlers; each handles it and stops, does something and passes it on, or just passes it on. The sender doesn't know which handler will respond. HTTP middleware and servlet filters are the everyday example: logging, authentication, rate limiting and validation, each able to short-circuit with a 401, 429 or 400 before the endpoint runs. The order of handlers is part of the design: authenticate before a per-user limit, cheap checks before expensive ones.

Deeper: You have three import jobs sharing the same read-validate-save loop. Template Method or Strategy?

How a strong answer sounds
Both work. Template Method: an abstract ImportJob with a final run that loops, catches per-row errors and builds a report, with abstract parse and save and an optional validate hook. That's natural if the steps are closely related and each job is one fixed combination. If I want to mix parsers, validators and savers independently, or swap them in tests, I'd make one concrete Importer that takes those steps as interfaces or lambdas: Strategy, composition over inheritance. For three jobs I'd start with the template and switch if combinations appear.

🧠 Key takeaways

  • Chain of Responsibility: handlers in sequence; each handles and stops, or passes the request on.
  • The modern form passes an explicit next: servlet filters, interceptors, middleware.
  • Handler order is policy: authenticate before per-user limits, cheap checks before expensive ones, logging first.
  • Template Method: a final skeleton method with abstract steps and optional hooks overridden by subclasses.
  • Catch per-item failures inside a template's loop so one bad record doesn't abort the job.
  • Template Method varies steps by inheritance at compile time; Strategy varies them by composition at run time.

Check your understanding

What is the defining ability of a handler in a Chain of Responsibility?

Deciding whether the request continues, and being able to short-circuit it, is what distinguishes a chain handler from a decorator, which always delegates.

A per-user rate limiter is placed before the authentication handler. What's the problem?

Handlers can depend on work done by earlier ones. A per-user limit needs the user that authentication attaches, so authentication must come first.

Why is the template method (run) declared final?

The skeleton is the thing the base class guarantees. Making it final keeps that guarantee while subclasses fill in the open steps.

What's the difference between an abstract step and a hook in a template method?

Abstract steps are mandatory variation points; hooks are optional extension points with sensible defaults, like “validate: accept everything”.

You want to combine any of three parsers with any of two savers, and swap them in tests. Which approach fits better?

Template Method would need six subclasses and fixes each combination at compile time. Passing the steps in lets any combination be assembled at run time.
