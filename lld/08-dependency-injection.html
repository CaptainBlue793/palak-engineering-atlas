Dependency Injection & Testability

An order service that creates its own Stripe client, its own mailer and reads the system clock works fine in production and is almost impossible to test: every test charges a card, sends an email, and waits in real time. Dependency injection is the simple fix: a class receives the objects it needs instead of creating them. This chapter shows how to do it with plain constructors, where the wiring goes, and how it turns a two-minute flaky test suite into a two-second reliable one.

  • Spot hidden dependencies: new on collaborators, static calls, the clock and randomness
  • Refactor to constructor injection with final fields
  • Wire the application in one composition root
  • Replace real collaborators with fakes in tests, including a fixed clock
  • Recognise the service locator and setter injection as weaker alternatives

new is glue

Writing new StripeClient(apiKey) inside a class glues that class to Stripe forever. Nobody can hand it a different gateway, a test fake, or a client configured differently. The same is true of other ways to reach out and grab something: a static call like Config.get("stripe.key"), a singleton like Metrics.getInstance(), and two that are easy to miss, the clock (Instant.now()) and randomness (UUID.randomUUID()). Each is a hidden dependency: it isn't in the constructor, so reading the class's signature tells you nothing about it.

OrderService.java, hard-wired
public final class OrderService {
	private final StripeClient stripe = new StripeClient(System.getenv("STRIPE_KEY"));   // glue
	private final SmtpMailer mailer = new SmtpMailer("smtp.internal:25");             // glue

	public Order place(Cart cart, Customer c) {
		Order order = new Order(UUID.randomUUID(), cart, Instant.now());               // hidden: randomness, clock
		stripe.charge(cart.total(), c.paymentToken());
		mailer.send(c.email(), "Order confirmed", order.summary());
		return order;
	}
	public boolean isPaymentWindowOpen(Order o) {
		return Duration.between(o.placedAt(), Instant.now()).toMinutes() < 30;     // testable only by waiting
	}
}

Constructor injection

The fix is to ask for dependencies instead of creating them. Every collaborator becomes a constructor parameter, typed as an interface the business code owns, stored in a final field:

OrderService.java, injected
public final class OrderService {
	private final PaymentGateway payments;
	private final Mailer mailer;
	private final Clock clock;                                  // java.time.Clock
	private final Supplier<OrderId> ids;

	public OrderService(PaymentGateway payments, Mailer mailer, Clock clock, Supplier<OrderId> ids) {
		this.payments = Objects.requireNonNull(payments);
		this.mailer = Objects.requireNonNull(mailer);
		this.clock = Objects.requireNonNull(clock);
		this.ids = Objects.requireNonNull(ids);
	}

	public Order place(Cart cart, Customer c) {
		Order order = new Order(ids.get(), cart, clock.instant());
		payments.charge(cart.total(), c.paymentToken(), order.idempotencyKey());
		mailer.send(c.email(), "Order confirmed", order.summary());
		return order;
	}
	public boolean isPaymentWindowOpen(Order o) {
		return Duration.between(o.placedAt(), clock.instant()).toMinutes() < 30;
	}
}
Same behaviour, different shape: the constructor is now an honest list of everything the class touches. Notice that new Order(...) stayed. Creating value objects and entities the class owns is fine; injection is for collaborators: things with behaviour you might want to swap, and things that reach the outside world.

Why the constructor, rather than setters? A constructor produces a complete object: it can't exist with its mailer missing, the fields can be final, and the compiler lists every dependency at every construction site. Setter injection allows half-built objects and needs a “call all setters first” rule, which is the temporal coupling from Chapter 5. Keep setters for genuinely optional settings, if at all.

The composition root

If nobody creates their own collaborators, somebody has to. That's the composition root: one place, as close to main as possible, that builds the whole object graph and starts the application. It's the only code that knows which concrete classes are used, and the natural place to read configuration.

public static void main(String[] args) {
	Config config = Config.fromEnvironment();
	Clock clock = Clock.systemUTC();
	PaymentGateway payments = new StripeGateway(new StripeClient(config.stripeKey()));
	Mailer mailer = new SmtpMailer(config.smtpHost());
	OrderService orders = new OrderService(payments, mailer, clock, OrderId::random);
	new HttpServer(config.port(), new OrderController(orders)).start();
}

Frameworks like Spring, Guice and Dagger automate this wiring, and in a large application they save a lot of typing. They don't change the design: classes still declare dependencies in their constructors, and the framework is just a generated composition root. In an interview, write the constructors and one short wiring snippet; don't reach for annotations.

Fakes: what injection buys in tests

Once dependencies come in through the constructor, a test can pass in replacements. The most useful kind is a fake: a small, working implementation that keeps everything in memory. A fake payment gateway records charges in a list; a fake mailer records sent emails; Clock.fixed(...) freezes time at a moment the test chooses, and Clock.offset(...) moves it forward.

@Test void payment_window_closes_after_30_minutes() {
	MutableClock clock = new MutableClock(Instant.parse("2026-09-30T10:00:00Z"));   // a tiny Clock subclass for tests
	RecordingGateway payments = new RecordingGateway();
	OrderService service = new OrderService(payments, new RecordingMailer(), clock, () -> new OrderId("o-1"));

	Order order = service.place(cartWorth("19.99"), alice);
	assertEquals(List.of(Money.of("19.99", USD)), payments.charged());

	clock.advance(Duration.ofMinutes(29));
	assertTrue(service.isPaymentWindowOpen(order));
	clock.advance(Duration.ofMinutes(1));
	assertFalse(service.isPaymentWindowOpen(order));                     // 30 minutes, tested in microseconds
}

Chapter 28 covers when to prefer each. The design point here is simpler: none of them is possible unless the class accepts its dependencies from outside.

Two weaker alternatives

Service locator. Instead of receiving dependencies, the class asks a global registry: ServiceLocator.get(PaymentGateway.class). It's swappable, in theory, but the dependencies are hidden again. You can't tell from the constructor what the class needs, a missing registration fails at run time instead of compile time, and every test must configure the global registry and remember to reset it. Prefer parameters.

Too many constructor parameters. When injection makes a constructor take eight collaborators, the constructor is doing you a favour: it's showing you a class with too many responsibilities (Chapter 3). Split the class; don't switch to a locator or setters to hide the count.

The bug that only happens at midnight

A service enforces “at most 5 password resets per user per day”, counting from midnight UTC. With Instant.now() inside the class, the only test anyone writes runs at whatever time CI happens to run, and the day-boundary logic is never exercised. It ships with an off-by-one that resets the counter at 23:00, and it's found in production. With an injected clock, a test sets the time to 23:59:59, makes five requests, advances one second, and checks the sixth is allowed. Time is the dependency people most often forget to inject, and the one that most often hides bugs. Case Study 32 injects a clock for exactly this reason.

⚠️
Common mistakes
  • new on collaborators inside business classes. Create values and owned parts; receive collaborators.
  • Forgetting the clock and randomness. Instant.now() and UUID.randomUUID() in domain code make tests slow or nondeterministic.
  • Setter or field injection for required dependencies. Objects can exist half-built, and fields can't be final.
  • Wiring scattered through the codebase. One composition root; everything else just receives.
  • A service locator to “simplify” constructors. It hides dependencies and moves errors to run time.
  • Mocking everything. Tests that assert every internal call break on every refactor. Prefer fakes and check outcomes.

Interview drill

Explain it simply: What is dependency injection, and why do you use it?

How a strong answer sounds
A class receives the collaborators it needs, usually through its constructor, instead of creating or looking them up itself. Then the constructor honestly lists what the class depends on, the fields can be final, and the application wires real implementations in one composition root at startup. The main payoff is substitution: tests pass in fakes, like an in-memory gateway and a fixed clock, so they're fast and deterministic, and production can swap providers by changing the wiring.

Deeper: How would you unit-test “an unpaid order is cancelled after 30 minutes” without waiting 30 minutes?

How a strong answer sounds
Inject a java.time.Clock into the service instead of calling Instant.now(). In the test I'd use a clock I can move, either Clock.fixed recreated at a new instant or a small settable test clock. Place the order at 10:00, advance to 10:29 and assert it's still open, advance to 10:30 and assert it's cancelled. The payment gateway and mailer would be fakes, so the test runs in milliseconds and tests the exact boundary, which a real-time test never would.

🧠 Key takeaways

  • new on a collaborator, static lookups, Instant.now() and UUID.randomUUID() are hidden dependencies.
  • Constructor injection: collaborators as interface-typed constructor parameters in final fields, validated non-null.
  • Keep creating values and owned parts with new; inject collaborators and anything that reaches the outside world.
  • One composition root near main builds the object graph; frameworks only automate it.
  • Injection enables fakes and controllable clocks, which make tests fast, deterministic and able to hit exact boundaries.
  • Service locators and setter injection hide dependencies; a long constructor is an SRP warning, not a reason to hide it.

Check your understanding

What's the main problem with private final StripeClient stripe = new StripeClient(key); inside OrderService?

Creating a collaborator inside the class fixes the choice forever. Receiving a PaymentGateway through the constructor lets production pass Stripe and tests pass a fake.

Why prefer constructor injection over setter injection for required dependencies?

Setters allow half-built objects and require callers to remember to call them, which is temporal coupling. A constructor makes completeness a compile-time fact.

Where should concrete classes like StripeGateway and SmtpMailer be instantiated?

Keeping all wiring in one place means only one piece of code knows the concrete choices, and swapping an implementation is a one-line change.

What's wrong with ServiceLocator.get(PaymentGateway.class) inside a service?

A locator is swappable, but the class's needs are invisible from outside, and the registry is shared global state that every test must set up and reset.

After refactoring to constructor injection, a class needs nine collaborators. What does that suggest?

Injection made the dependencies visible; the count is a single-responsibility smell. Hiding it with fields or a locator keeps the problem and loses the warning.
