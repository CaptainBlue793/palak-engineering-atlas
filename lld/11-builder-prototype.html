Builder & Prototype

Some objects need a dozen settings, most of them optional: an HTTP request, a database connection pool, a retry policy, a search query. Constructors handle that badly. Builder assembles such an object step by step, with named methods, and checks the whole thing once before it exists. Prototype answers the neighbouring question: once you have a well-configured object, how do you get a slightly different copy without repeating all twelve settings?

  • Recognise the telescoping-constructor problem and why setters don't fix it
  • Write a Builder that produces an immutable object and validates in build()
  • Design a fluent API that reads like the thing it configures
  • Copy configured objects with copy constructors, with… methods or toBuilder()
  • Explain why clone() and Cloneable are best avoided

Too many constructor parameters

A connection-pool configuration has a required JDBC URL and several optional settings: maximum size, minimum idle connections, connection timeout, idle timeout, maximum lifetime, a validation query. The first attempt is usually telescoping constructors, each one adding a parameter and passing defaults to the next:

public PoolConfig(String url) { this(url, 10); }
public PoolConfig(String url, int maxSize) { this(url, maxSize, 2); }
public PoolConfig(String url, int maxSize, int minIdle) { this(url, maxSize, minIdle, 30_000, 600_000, 1_800_000); }
public PoolConfig(String url, int maxSize, int minIdle, long connTimeout, long idleTimeout, long maxLifetime) { … }

new PoolConfig(url, 20, 5, 600_000, 30_000, 1_800_000);   // which long is which? (two are swapped)

Three long values in a row is exactly the same-type-parameter trap from Chapter 7: the call above swaps the connection and idle timeouts, and it compiles. Wanting just one optional setting means passing every setting before it. The other common attempt, a no-argument constructor followed by setters, reads better but gives up two things you care about: the object can't be immutable, and it exists in an unfinished, possibly invalid state between the constructor and the last setter call.

The Builder

A Builder is a separate, mutable helper that collects settings through named methods and then creates the real object in one step, build(), where all the rules are checked together:

PoolConfig.java: an immutable product and its builder
public final class PoolConfig {
	private final String jdbcUrl;
	private final int maxSize, minIdle;
	private final Duration connectionTimeout, idleTimeout, maxLifetime;

	private PoolConfig(Builder b) {                           // only the builder can call this
		this.jdbcUrl = b.jdbcUrl; this.maxSize = b.maxSize; this.minIdle = b.minIdle;
		this.connectionTimeout = b.connectionTimeout; this.idleTimeout = b.idleTimeout; this.maxLifetime = b.maxLifetime;
	}
	public static Builder forUrl(String jdbcUrl) { return new Builder(jdbcUrl); }   // required value up front

	public static final class Builder {
		private final String jdbcUrl;
		private int maxSize = 10, minIdle = 2;                  // defaults in one place
		private Duration connectionTimeout = Duration.ofSeconds(30), idleTimeout = Duration.ofMinutes(10), maxLifetime = Duration.ofMinutes(30);

		private Builder(String jdbcUrl) { this.jdbcUrl = Objects.requireNonNull(jdbcUrl); }
		public Builder maxSize(int n) { this.maxSize = n; return this; }     // return this: chainable
		public Builder minIdle(int n) { this.minIdle = n; return this; }
		public Builder connectionTimeout(Duration d) { this.connectionTimeout = d; return this; }
		public Builder idleTimeout(Duration d) { this.idleTimeout = d; return this; }
		public Builder maxLifetime(Duration d) { this.maxLifetime = d; return this; }

		public PoolConfig build() {                                 // every cross-field rule, checked once
			if (maxSize < 1) throw new IllegalStateException("maxSize must be ≥ 1");
			if (minIdle < 0 || minIdle > maxSize) throw new IllegalStateException("minIdle must be 0.." + maxSize);
			if (idleTimeout.compareTo(maxLifetime) >= 0) throw new IllegalStateException("idleTimeout must be shorter than maxLifetime");
			return new PoolConfig(this);
		}
	}
}

PoolConfig config = PoolConfig.forUrl(url)
	.maxSize(20)
	.minIdle(5)
	.connectionTimeout(Duration.ofSeconds(30))
	.build();                                                    // every value is labelled
What each part buys: named methods make every value self-describing and let callers set only what they need; the private constructor means a PoolConfig can only come from build(), so it is always valid; build() checks rules that involve several fields at once (min idle ≤ max size, idle timeout < max lifetime), which no single setter could; and the product is immutable, so it can be shared across threads.

Validation in build() matters most for the cross-field rules. A setter can check that minIdle isn't negative, but it can't know whether maxSize will be set smaller later. Only the final step sees everything. The builder itself is mutable and meant to be used by one thread and thrown away; the object it builds is what gets shared.

Fluent APIs, and the JDK's own builder

A builder whose methods return this gives you a fluent API: calls chain into something that reads like a description of the object. Java 11's HTTP client is a good model. HttpRequest.newBuilder() returns a builder, build() returns an immutable HttpRequest, and build() refuses to produce a request without a URI. It also rejects a handful of “restricted” headers like Host and Content-Length, which the client must control itself. Try it:

A few guidelines for builders you write yourself:

  
    
    
  • Take required values up front (PoolConfig.forUrl(url)), so a builder can't exist without them.
    • 
    
  • Keep defaults in the builder's field initialisers, visible in one place.
    • 
    
  • Validate single values early in each method when it helps (a negative size can fail at once), and cross-field rules in build().
    • 
    
  • Don't add a builder to a record with three fields. A constructor or static factory is clearer. Builders pay off around four or more parameters, several of them optional.

Prototype: copying a configured object

  
Once a service has a carefully configured RetryPolicy or HttpRequest, it often needs a variant: the same policy with more attempts, the same request with one extra header. The Prototype pattern means creating new objects by copying an existing one rather than configuring from scratch. In Java there are three good ways to do it, and one to avoid.


// 1. "with" methods on an immutable object (the java.time style)
public record RetryPolicy(int maxAttempts, Duration baseDelay, double multiplier) {
	public RetryPolicy withMaxAttempts(int n) { return new RetryPolicy(n, baseDelay, multiplier); }
}
RetryPolicy payments = STANDARD.withMaxAttempts(5);

// 2. toBuilder(): copy every setting into a new builder, change a few, build
PoolConfig reporting = config.toBuilder().maxSize(4).build();

// 3. The JDK's own: copy a request, keeping only the headers the filter allows (Java 16+)
HttpRequest retry = HttpRequest.newBuilder(original, (name, value) -> !name.equalsIgnoreCase("Authorization"))
	.header("Authorization", "Bearer " + freshToken)
	.build();

  
With immutable objects, “copy” is cheap and safe: the new object can share every unchanged field with the original, because none of them can change. That's why Instant.plusSeconds, LocalDate.withDayOfMonth and String.replace all return new objects instead of modifying. For a mutable class, a copy constructor (new Cart(existingCart)) or a static copyOf is the explicit way to make an independent copy, deep where it needs to be.

  
The one to avoid is Object.clone() with Cloneable. Cloneable has no methods, yet changes how Object.clone() behaves; the copy is created without running any constructor, so invariants and final fields aren't handled normally; the default copy is shallow, so a cloned object shares its lists with the original (the aliasing bug from P1); and clone() declares a checked exception most callers can't do anything about. Effective Java advises copy constructors or copy factories instead, and so does this course.

Why connection-pool libraries use builders or config objects
Production connection pools such as HikariCP expose a dozen or more settings: pool size, minimum idle, connection, idle and validation timeouts, maximum lifetime, leak detection threshold, and more. Most applications change two or three. A constructor with a dozen positional parameters would be unusable, and would guarantee swapped timeouts somewhere. So these libraries use a configuration object with named properties that is checked when the pool starts, and reject invalid combinations with a clear message instead of misbehaving under load at 3 a.m. It's the builder idea: collect named settings, validate the whole configuration once, then create the thing. ⚠️
Common mistakes

    
    
      
  • A public constructor next to the builder. Callers can bypass build()'s validation. Make the constructor private.
    • 
      
  • Validating cross-field rules in setters. They can't see the final values. Check them in build().
    • 
      
  • Sharing a builder between threads, or reusing it after build(). Builders are throwaway, single-thread helpers.
    • 
      
  • A builder for three fields. A record or static factory is clearer.
    • 
      
  • Setters on the product “for convenience”. The whole point is an immutable, always-valid product.
    • 
      
  • Implementing Cloneable. Use copy constructors, with methods or toBuilder().
    •

Interview drill

    
Explain it simply: When would you use a Builder, and what makes a good one?

    
How a strong answer sounds
When an object has several parameters, especially optional ones or several of the same type, where a constructor would be unreadable and easy to call with swapped arguments. A good builder takes required values up front, holds defaults in one place, has named chainable methods, validates cross-field rules in build(), and produces an immutable object through a private constructor, so every instance is valid. The builder is mutable and throwaway; the product is what gets shared.

    
Deeper: You need an HTTP request identical to a previous one except for a refreshed auth token. How would you create it, and why not clone()?

    
How a strong answer sounds
Copy it through a builder: in the JDK, HttpRequest.newBuilder(original, filter) copies the request, dropping the old Authorization header via the filter, then I add the new header and call build(). Since HttpRequest is immutable, the copy safely shares everything else with the original. I'd avoid clone() because it bypasses constructors, makes shallow copies that share mutable state, and has an awkward checked-exception API; copy constructors, with methods and toBuilder() are explicit and go through the normal validation.

  


  

    
🧠 Key takeaways

    
    
      
  • Telescoping constructors are unreadable and invite swapped arguments; setters give up immutability and allow half-built objects.
    • 
      
  • A Builder collects named settings, holds defaults, and creates the object once in build() through a private constructor.
    • 
      
  • Check single values early if useful, and cross-field rules in build().
    • 
      
  • The builder is mutable and single-use; the product is immutable and shareable.
    • 
      
  • Prototype in Java: with methods, toBuilder(), copy constructors and copy factories.
    • 
      
  • Avoid clone()/Cloneable: no constructor, shallow by default, awkward API.

Check your understanding

    


    

      
What's the main problem with new PoolConfig(url, 20, 5, 600_000, 30_000, 1_800_000)?

      

        
        
        
        
      

      
Positional long timeouts carry no names at the call site, so a swap is invisible. A builder labels every value and lets callers set only what they need.

    


    

      
Where should a builder check “minIdle must not exceed maxSize”?

      

        
        
        
        
      

      
A rule spanning two fields can only be checked once both are set, and callers may set them in either order. build() sees the final configuration.

    


    

      
Why does PoolConfig have a private constructor that takes the builder?

      

        
        
        
        
      

      
If the constructor were public, callers could bypass build() and create invalid objects. With it private, a PoolConfig is valid by construction.

    


    

      
What does HttpRequest.newBuilder().GET().build() do, with no URI set?

      

        
        
        
        
      

      
The JDK builder validates in build() and refuses to produce a request without a URI, so a HttpRequest object is always complete.

    


    

      
Why prefer a copy constructor or with method over implementing Cloneable?

      

        
        
        
        
      

      
A shallow clone shares lists and other mutable objects with the original, which is aliasing by accident. Explicit copies run normal construction and validation, and make deep copies where needed.
