Patterns Together & Anti-Patterns

Real designs don't use one pattern. A payment flow is a factory choosing a strategy, wrapped in decorators, talking to an adapter, driving a state machine and publishing events. Knowing how patterns fit together is what turns a list of names into a design. Knowing when not to use one matters just as much: most over-engineered code is made of correctly implemented patterns applied to problems that didn't need them.

  • Trace one feature through several cooperating patterns, and name each one's job
  • Recognise the patterns that usually appear together
  • Spot over-engineering: speculative generality, needless layers, pattern names without a problem
  • Explain the anemic domain model and move behaviour back next to its data
  • Decide between a pattern, a plain function, and nothing yet

One feature, six patterns

Here's a single use case, “charge a customer for an order”, from a checkout service that supports cards and UPI through two providers. Every pattern in it is there because a requirement put it there:

Notice that checkout never mentions a pattern. It calls registry.create, gateway.charge, payment.capture and bus.publish. Good pattern use is invisible at the call site: the complexity is organised, not exposed.

Over-engineering: patterns without problems

Every pattern adds indirection: another interface, another class, another hop to follow when debugging. That cost is worth paying when it buys a change you expect. When it doesn't, you get code like the famous satire FizzBuzz Enterprise Edition, a real public repository that implements the three-line FizzBuzz exercise with dozens of factories, strategies and visitors. It's funny because everyone has worked on a milder version. The warning signs:

  • Speculative generality. An interface with one implementation and no test that needs a second; a plugin system with one plugin; generics nobody instantiates twice. Built for a future that hasn't asked. Remove it; extracting an interface later takes minutes.
  • Layers that only forward. OrderController → OrderFacade → OrderService → OrderManager → OrderRepository, where three of them just pass the call along. Each layer should own a decision.
  • Pattern names instead of domain names. UserServiceStrategyFactoryImpl tells you how it's built, not what it does. Name classes after their job: PasswordPolicy, RefundJob.
  • Configuration for everything. Behaviour moved into YAML “in case it changes” is code without a compiler, types or tests.
  • The golden hammer. The team just learned Strategy, and now every if is a strategy. A two-branch if that never grows is clearer as an if.

The anemic domain model

A quieter anti-pattern, named by Martin Fowler: entities that are only data, getters and setters, while all the rules live in “service” classes. It looks organised, and it quietly undoes encapsulation (P2): every service can put an object in any state, and each rule is enforced only in the service that remembered to.

Anemic

class Account {                      // just data
	Money getBalance(); void setBalance(Money m);
	Status getStatus(); void setStatus(Status s);
}
class TransferService {              // all the rules
	void withdraw(Account a, Money m) {
		if (a.getStatus() == FROZEN) throw …;
		if (a.getBalance().lessThan(m)) throw …;
		a.setBalance(a.getBalance().minus(m));
	}
}
// RefundService, FeeService… each re-checks, or forgets

Rich

final class Account {                // data + its rules
	private Money balance;
	private Status status;

	void withdraw(Money m) {
		if (status == FROZEN) throw …;
		if (balance.lessThan(m)) throw …;
		balance = balance.minus(m);
	}
	void freeze() { status = FROZEN; }
}
// services coordinate; they never set balances

In a rich model, services still exist, but they coordinate: load the accounts, call from.withdraw(m) and to.deposit(m), save both in one transaction. The rules live in the entity, once. Anemic classes are fine in one place: at the edges, as request and response DTOs, database rows and JSON messages, where they really are just data being carried across a boundary. Chapter 27 develops the rich side properly.

How strong candidates talk about patterns

Two candidates design the same pricing feature. The first opens with “I'll use the Strategy pattern with an Abstract Factory and a Singleton registry”, and the interviewer's next question is “why?”. The second says: “Prices differ by day of week and by demand, and the prompt says more rules are coming, so pricing goes behind an interface with one class per rule, and a small factory picks rules for each ride. That's Strategy.” Same design, but the second answer shows the reasoning the rubric scores (Chapter 1). Chapter 30 collects more phrasing like this.

⚠️
Common mistakes
  • Leading with pattern names instead of the problem they solve.
  • Interfaces with one implementation and no test or requirement that needs a second.
  • Class names made of pattern words: …StrategyFactoryImpl. Name the job.
  • Layers that only forward calls. Each layer should own a decision, or go.
  • Entities with public setters for every field and rules in services: the anemic model.
  • Refusing all patterns after reading this chapter. When variation is real and growing, the pattern is the simple solution.
🎤
Interview drill

Explain it simply: How do you avoid over-engineering in a design interview?

How a strong answer sounds
I add structure only where the requirements say something varies or will change, and I say so: pricing gets an interface because the prompt says rules change; vehicle sizes stay an enum because they're fixed. I avoid interfaces with one implementation unless tests need a seam, layers that only forward, and naming classes after patterns. I keep behaviour on the entities that own the data, and I name a pattern after I've described the problem it solves.

Deeper: Walk me through the patterns in a payment flow, and which one you'd drop first if the scope shrank.

How a strong answer sounds
A registry picks a PaymentGateway strategy by payment method; the factory wraps it in retry and metrics decorators; each provider is an adapter over its SDK; the Payment entity moves through a sealed state machine; success publishes an event for receipts and loyalty; refunds run as queued commands. If there were only one provider and no plans for more, I'd drop the registry and strategy first, and keep the adapter, since it still isolates the vendor's API and errors. The state machine and events stay, because the lifecycle and reactions exist regardless of the number of providers.

🧠 Key takeaways

  • Real features combine patterns, each doing one job: factory, strategy, decorator, adapter, state, observer, command.
  • Good pattern use is invisible at the call site; callers see a few intention-revealing calls.
  • Some patterns travel in pairs: factory with strategy or decorator, composite with visitor, command with memento, state with observer.
  • Over-engineering shows as speculative generality, forwarding layers, pattern-word class names and config for everything.
  • The anemic domain model puts rules in services and leaves entities as bags of setters; move behaviour to the data.
  • Start from what varies; use a pattern when variation is real and growing, a function when it's small, and nothing when there's none yet.

Check your understanding

Why are a registry of factories and Strategy so often used together?

Strategy defines the interchangeable algorithms; something still has to pick one. A registry centralises that choice, so adding a strategy is a class plus a registration.

A codebase has ReportExporter with exactly one implementation, CsvReportExporter, no test double, and no plans for other formats. What's the smell?

An interface earns its place with a second implementation, a test seam or a stated requirement. Without any, it's indirection to maintain; extract it when the second case arrives.

Which is the clearest sign of an anemic domain model?

When rules sit outside the data, every service can bypass them. DTOs at boundaries are fine; the problem is domain entities with no behaviour.

A sort order is needed in one report, and there's no sign of other orders. What's the right tool?

A Comparator already is a strategy, and a lambda is a complete implementation. Anything more is structure without a problem to solve.

In an interview, what's the best way to bring up a pattern?

The rubric scores reasoning. Problem first, then structure, then the name, shows you chose the pattern for a reason rather than reciting it.
