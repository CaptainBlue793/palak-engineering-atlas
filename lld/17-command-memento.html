Command & Memento

Undo is the feature that makes these two patterns click. To undo something, you have to remember what was done, which means turning an action into an object you can store: that's Command. Or you remember what things looked like before, without exposing an object's private insides to do it: that's Memento. The same two ideas power job queues, retries, audit logs, macros and database recovery.

  • Turn a request into a Command object with execute and undo
  • Implement undo and redo with two stacks, and know when redo is cleared
  • Use commands for job queues, retries and macros, and store them durably
  • Snapshot state with a Memento that keeps encapsulation
  • Choose between undo by inverse command and undo by snapshot

Command: a request as an object

Normally a request is a method call: it happens and it's gone. A Command packages the request, with everything needed to perform it, into an object. The code that triggers commands (the invoker: a button, a menu, a job runner) doesn't know what they do; it just calls execute(). Because the command is an object, you can also store it, queue it, log it, send it elsewhere, retry it, and, if it knows how to reverse itself, undo it.

Edits as commands in a text editor
public interface EditCommand {
	void execute(Document doc);
	void undo(Document doc);
}

public final class Insert implements EditCommand {
	private final int at; private final String text;
	public Insert(int at, String text) { this.at = at; this.text = text; }
	public void execute(Document doc) { doc.insert(at, text); }
	public void undo(Document doc) { doc.delete(at, text.length()); }       // the exact inverse
}

public final class Delete implements EditCommand {
	private final int at, length;
	private String removed;                                                  // captured when executed
	public Delete(int at, int length) { this.at = at; this.length = length; }
	public void execute(Document doc) { removed = doc.text(at, length); doc.delete(at, length); }
	public void undo(Document doc) { doc.insert(at, removed); }            // can't undo without what was removed
}

public final class History {                                             // the invoker
	private final Deque<EditCommand> undo = new ArrayDeque<>(), redo = new ArrayDeque<>();
	public void run(EditCommand c, Document d) { c.execute(d); undo.push(c); redo.clear(); }   // a new edit ends the redo branch
	public void undo(Document d) { if (!undo.isEmpty()) { EditCommand c = undo.pop(); c.undo(d); redo.push(c); } }
	public void redo(Document d) { if (!redo.isEmpty()) { EditCommand c = redo.pop(); c.execute(d); undo.push(c); } }
}
The rules of undo: every command must be able to reverse exactly what it did, so a delete must remember the text it removed. Undo moves a command to the redo stack; redo moves it back. Any new command clears redo, because the history has branched and the old “future” no longer applies to this document.

Insert and delete store a small delta. “UPPERCASE all” has no cheap inverse (which letters were already capitals?), so it stores a memento of the whole document instead, marked in amber, and its size grows with the document.

Commands beyond undo: queues, retries and macros

Undo is only one use. Because a command is an object, the invoker can do other things with it:

  • Queue it. Runnable and Callable are commands, and ExecutorService.submit(task) is an invoker that runs them later on another thread. A job scheduler is a queue of commands ordered by run time (Case Study 35).
  • Retry it. A failed command can be re-executed as-is, if it's idempotent.
  • Log it. An audit trail of commands records who asked for what, with their arguments.
  • Combine them. A macro is a command holding a list of commands; execute runs them in order, undo undoes them in reverse.

For queues that must survive a restart, store commands as data: a type name and its arguments, such as {"type": "SendInvoice", "orderId": "8412"}, not a serialized lambda or object graph. Data survives deployments and can be read by humans and other services; a lambda from last week's build can't be deserialized by this week's.

Memento: snapshots without breaking encapsulation

Some operations have no simple inverse: an auto-format, a sort, a find-and-replace across a whole file, a rules engine rewriting a configuration. The alternative is to save the state before the operation and restore it to undo. The naïve way breaks encapsulation: the caller reads every private field out through getters and writes them back through setters. Memento keeps the state private. The object (the originator) creates an opaque snapshot of itself; the caller (the caretaker) stores it without being able to look inside; only the originator can restore from it.

public final class Document {
	private StringBuilder text = new StringBuilder();
	private int cursor;
	private Selection selection;

	/** An opaque snapshot: callers can hold it, but not read or change it. */
	public static final class Snapshot {
		private final String text; private final int cursor; private final Selection selection;
		private Snapshot(String t, int c, Selection s) { text = t; cursor = c; selection = s; }   // no public accessors
	}
	public Snapshot save() { return new Snapshot(text.toString(), cursor, selection); }  // immutable copy
	public void restore(Snapshot s) { text = new StringBuilder(s.text); cursor = s.cursor; selection = s.selection; }
}

// A command that undoes by snapshot
public final class Reformat implements EditCommand {
	private Document.Snapshot before;
	public void execute(Document d) { before = d.save(); d.applyFormatting(); }
	public void undo(Document d) { d.restore(before); }
}

Because Snapshot is nested inside Document, only Document can read its private fields. The snapshot copies the text into an immutable String, so later edits can't change a saved state (the aliasing bug again, P1).

Undo by inverse commandUndo by memento (snapshot)
StoresOnly the change (a delta)The whole relevant state
Memory per stepSmall, independent of document sizeGrows with the state; 1,000 steps of a 1 MB file is 1 GB
Correctness riskEvery command needs an exact inverseTrivially correct: restore what was there
Best forSmall, frequent, reversible edits: typing, moving, deletingComplex operations with no simple inverse, or rarely taken checkpoints

Real editors combine them: deltas for ordinary typing, snapshots for big operations, and a limit on how much history is kept. They also group many keystrokes into one undo step, so undo removes a word or a sentence rather than one character; Case Study 38 builds that.

Databases run on a command log

A database doesn't change data files first and hope for the best. It first appends a record of each change to a write-ahead log, then applies the change. After a crash, recovery reads the log: it redoes changes from committed transactions that hadn't reached the data files yet, and undoes changes from transactions that never committed. That's a durable history of commands, with enough information in each record to redo or undo it, the same two operations as this chapter's editor, at the heart of every serious database. Case Study 37 builds nested transactions with rollback on the same idea.

⚠️
Common mistakes
  • Commands that can't undo themselves because they didn't capture what they changed, like a delete that forgets the removed text.
  • Keeping redo after a new command. The old future doesn't apply to the new present; clear it.
  • Unbounded history. Cap the number of steps, or the memory, especially with snapshots.
  • Mementos that share mutable state with the original, so later edits change the snapshot. Copy into immutable form.
  • Mementos with getters. Callers start reading and depending on another object's internals.
  • Persisting commands as serialized lambdas or object graphs. Store a type and data.

Interview drill

Explain it simply: How would you implement undo and redo?

How a strong answer sounds
Each edit is a Command with execute and undo, capturing whatever it needs to reverse itself, like the text a delete removed. A history object keeps two stacks. Running a command executes it, pushes it on undo and clears redo. Undo pops from undo, calls undo, pushes onto redo; redo does the reverse. For operations without a clean inverse, the command saves a Memento, an opaque snapshot from the document, and restores it on undo. I'd cap history size and group rapid keystrokes into one step.

Deeper: Your job queue stores tasks as serialized Java objects, and after a deployment old jobs fail to deserialize. How would you redesign it?

How a strong answer sounds
Treat jobs as commands described by data: a job type name, a schema version and a small JSON payload of arguments, stored in the queue. Workers look up a handler for the type in a registry and pass it the payload, so code can change freely as long as it can still read old payload versions. Handlers should be idempotent, keyed by a job id, because queues redeliver after failures. That keeps queued work readable, debuggable and compatible across deployments.

🧠 Key takeaways

  • Command: a request packaged as an object with execute (and undo), so an invoker can run it without knowing what it does.
  • Undo/redo: two stacks; undo moves a command to redo, redo moves it back, and a new command clears redo.
  • A command must capture what it needs to reverse itself, like the text a delete removed.
  • Commands enable queues, retries, audit logs and macros; persist them as type plus data, not serialized objects.
  • Memento: an opaque, immutable snapshot only the originator can read, for undoing operations without a simple inverse.
  • Deltas are small but need exact inverses; snapshots are simple but grow with state. Real systems mix both and cap history.

Check your understanding

What is the essence of the Command pattern?

Turning an action into an object is what makes storing, queuing, logging and undoing possible. Choosing algorithms is Strategy, notifying is Observer, restricting access is Proxy.

You undo twice, then type a new word. What happens to the two commands on the redo stack?

Redo only makes sense for the exact state the commands were undone from. A new edit creates a different present, so the old future is cleared.

Why does a Delete command store the removed text when it executes?

A command must capture whatever its inverse needs. After the delete, the text is gone from the document, so the command is the only place it survives.

What makes a Memento different from simply reading all of an object's fields through getters?

Memento saves and restores state without exposing the object's internals, so encapsulation survives. Getters and setters for everything would break it.

An editor keeps a full snapshot of a 2 MB document for each of the last 500 edits. What's the problem, and a better design?

Snapshots cost memory proportional to the state for every step. Deltas cost memory proportional to the change. Mixing them and bounding history keeps undo cheap.
