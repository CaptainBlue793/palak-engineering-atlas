Case Study: Expense Sharing (Splitwise)

Four friends share a trip: one pays for dinner, another for the taxi, a third for the hotel, each split differently. At the end, who owes whom, and how few payments settle it? The domain is small, but it's full of the details that separate careful designs from sloppy ones: money that must add up to the cent after splitting $100 three ways, split rules that vary (a Strategy), balances derived from an append-only ledger, and a debt-simplification step that turns a tangle of IOUs into a handful of transfers.

  • Specify expenses, splits, balances and settlements precisely
  • Implement equal, exact, percentage and share splits as strategies that always sum to the total
  • Keep an append-only ledger and derive net balances from it
  • Simplify debts to at most n − 1 transfers, and know why the true minimum is hard
  • Handle groups, edits and history without losing auditability

Requirements and API

Clarify: users belong to groups; an expense has a payer, an amount, a set of participants and a split rule (equal, exact amounts, percentages or shares); the app shows each user's net balance and who should pay whom; users record settlements (“Ben paid Asha $30”); expenses can be edited or deleted, and the history stays auditable. One currency per group for now; multi-currency is the follow-up.

public interface ExpenseService {
	ExpenseId addExpense(GroupId g, UserId paidBy, Money total, Split split, String description);
	void recordSettlement(GroupId g, UserId from, UserId to, Money amount);
	Map<UserId, Money> balances(GroupId g);                       // + is owed money, − owes money
	List<Transfer> suggestedSettlements(GroupId g);                  // simplified debts
	void deleteExpense(ExpenseId id);                                    // appends a reversal, keeps history
}

Split types as strategies

Each split rule answers one question: given the total, how much does each participant owe? That's a Strategy (Chapter 15) with one hard invariant, checked in one place: the shares must add up to the total, exactly, in cents. $100.00 split three ways can't be 33.33 × 3 = 99.99; one person pays 33.34. Use the largest remainder rule: give everyone the rounded-down amount, then hand the leftover cents one each to the participants with the largest fractional parts (ties broken by a stable order, so the result is deterministic).

public sealed interface Split permits Equal, Exact, Percent, Shares {
	Map<UserId, Money> allocate(Money total);                        // must sum to total, exactly
}

record Equal(List<UserId> who) implements Split {
	public Map<UserId, Money> allocate(Money total) { return Apportion.byWeights(total, weights(who, 1)); }
}
record Shares(Map<UserId, Integer> shares) implements Split {        // e.g. couples count as 2
	public Map<UserId, Money> allocate(Money total) { return Apportion.byWeights(total, shares); }
}
record Percent(Map<UserId, Integer> basisPoints) implements Split {   // 2500 = 25.00%
	public Percent { if (sum(basisPoints) != 10_000) throw new IllegalArgumentException("percentages must total 100%"); }
	public Map<UserId, Money> allocate(Money total) { return Apportion.byWeights(total, basisPoints); }
}
record Exact(Map<UserId, Money> amounts) implements Split {
	public Map<UserId, Money> allocate(Money total) {
		if (!Money.sum(amounts.values()).equals(total)) throw new IllegalArgumentException("exact amounts must add up to " + total);
		return Map.copyOf(amounts);
	}
}

final class Apportion {                                                  // largest remainder, in cents
	static Map<UserId, Money> byWeights(Money total, Map<UserId, Integer> w) {
		long cents = total.cents(), sumW = w.values().stream().mapToLong(Integer::longValue).sum();
		Map<UserId, Long> base = new LinkedHashMap<>();
		w.forEach((u, k) -> base.put(u, cents * k / sumW));                   // rounded down
		long left = cents - base.values().stream().mapToLong(Long::longValue).sum();
		w.keySet().stream()
			.sorted(Comparator.comparingLong((UserId u) -> cents * w.get(u) % sumW).reversed().thenComparing(UserId::value))
			.limit(left).forEach(u -> base.merge(u, 1L, Long::sum));              // one leftover cent each
		return Money.ofCents(base);
	}
}

Three of the four strategies reduce to “weights”, so they share one apportioning function and can't disagree about rounding. The sealed interface lists every split type, and each validates its own inputs in its constructor, so an invalid split can't even be created.

Balance sheet

Store what happened, not the running totals: every expense and settlement is an immutable entry in an append-only ledger. Balances are derived: for each entry, the payer is credited the total and each participant is debited their share. The group's net balances always sum to zero, an invariant worth asserting in tests. Deleting or editing an expense appends a reversing entry (and, for an edit, a new one), so the history explains every number, exactly like an accounting ledger.

public record Expense(ExpenseId id, UserId paidBy, Money total, Map<UserId, Money> owed,
                      String description, Instant at) implements LedgerEntry {}
public record Settlement(UserId from, UserId to, Money amount, Instant at) implements LedgerEntry {}

final class Group {
	private final List<LedgerEntry> ledger = new ArrayList<>();
	private final Map<UserId, Long> net = new HashMap<>();              // cache: cents, + = owed to them

	synchronized void add(Expense e) {
		if (!members.containsAll(e.owed().keySet())) throw new IllegalArgumentException("participant not in group");
		ledger.add(e);
		net.merge(e.paidBy(), e.total().cents(), Long::sum);
		e.owed().forEach((u, m) -> net.merge(u, -m.cents(), Long::sum));
		assert net.values().stream().mapToLong(Long::longValue).sum() == 0;   // money is conserved
	}

	synchronized void settle(Settlement s) {
		ledger.add(s);
		net.merge(s.from(), s.amount().cents(), Long::sum);                  // paying reduces what you owe
		net.merge(s.to(), -s.amount().cents(), Long::sum);
	}
}

Why net balances rather than a matrix of who owes whom? Pairwise debts are an artifact of who happened to pay; what matters for settling up is each person's net position. The matrix grows as n², and after a trip it's a tangle: Ben owes Asha for dinner while Asha owes Ben for the taxi. The next step turns net balances into the fewest sensible payments.

Debt simplification

Given net balances (Asha +$120, Ben −$30, Chen +$60, Dev −$150), find payments that bring everyone to zero. A greedy algorithm does it cleanly: repeatedly take the person who owes the most and the person owed the most, transfer the smaller of the two amounts, and repeat. Each transfer zeroes at least one person, so there are at most n − 1 transfers, and each one moves money in the “right” direction.

static List<Transfer> simplify(Map<UserId, Long> net) {
	PriorityQueue<Balance> creditors = new PriorityQueue<>(Comparator.comparingLong(Balance::cents).reversed());
	PriorityQueue<Balance> debtors   = new PriorityQueue<>(Comparator.comparingLong(Balance::cents).reversed());
	net.forEach((u, c) -> { if (c > 0) creditors.add(new Balance(u, c)); else if (c < 0) debtors.add(new Balance(u, -c)); });
	List<Transfer> out = new ArrayList<>();
	while (!creditors.isEmpty() && !debtors.isEmpty()) {
		Balance c = creditors.poll(), d = debtors.poll();
		long x = Math.min(c.cents(), d.cents());
		out.add(new Transfer(d.user(), c.user(), Money.ofCents(x)));
		if (c.cents() > x) creditors.add(new Balance(c.user(), c.cents() - x));
		if (d.cents() > x) debtors.add(new Balance(d.user(), d.cents() - x));
	}
	return out;                                                          // ≤ n − 1 transfers, O(n log n)
}

Greedy isn't always the absolute minimum. If the group splits into independent subgroups whose balances each sum to zero (say A +10, B −10, C +5, D −5), each subgroup settles separately and needs fewer payments; finding the true minimum means finding the most such zero-sum subsets, which is NP-hard in general. For real groups of a handful of people, greedy is the standard, explainable answer, and saying “n − 1 at most; the exact minimum is NP-hard” is what the interviewer wants to hear.

Groups and history

A group is the natural aggregate (Chapter 27): its members, its ledger and its balance cache change together, and balances never cross groups. Expenses between two people outside any group live in an implicit two-person group, so there's one code path. Because the ledger is append-only, “show me why I owe $42” is a filter over entries, and recomputing balances from the ledger is a cheap consistency check to run in tests or on a schedule. Multi-currency, the classic follow-up, keeps each entry in its original currency and converts only when simplifying, at a rate recorded with the settlement, so history never changes when exchange rates do.

🧠
“Simplify debts” in the real app

Splitwise offers a group setting called “simplify debts”, which restructures who pays whom so the group needs fewer payments, without changing anyone's total balance. Its effect is exactly this chapter's algorithm: people may end up paying someone they never shared an expense with, because only net positions matter. That's also why the feature is a setting rather than always on: some groups prefer that each person repays the specific friend who covered them, which is the pairwise view. Two views of the same ledger, chosen by the user, is a design that's easy only because balances are derived rather than stored.

⚠️
Common mistakes
  • double for money, or shares that don't sum to the total after rounding.
  • Rounding each share independently so a cent vanishes or appears; distribute the remainder deterministically.
  • A separate rounding rule per split type instead of one apportioning function.
  • Storing only balances and mutating them on edit: no history, no way to explain or recompute.
  • An n × n debt matrix as the source of truth when net balances are what settle the group.
  • Claiming greedy gives the optimal number of payments; it gives at most n − 1.
  • No validation that participants belong to the group or that percentages total 100.

Interview drill

Explain it simply: How do you split $100 equally among three people?

How a strong answer sounds
In integer cents: 10,000 cents divided by 3 is 3,333 each with 1 cent left over. The leftover cent goes to one participant chosen deterministically, by the largest remainder and then a stable order like user id, so the shares are 33.34, 33.33, 33.33 and always sum to exactly $100.00. The same apportioning function handles shares and percentages, so every split type rounds the same way, and the invariant “shares sum to the total” is checked in one place.

Deeper: A user edits a three-week-old expense from $90 to $120 after others have already settled up. What happens?

How a strong answer sounds
The ledger is append-only, so the edit appends a reversal of the original expense and a new expense for $120, both linked to the original id with who changed it and when. Net balances update from those two entries; previous settlements stay as recorded, so people who already paid now have small new balances, $10 each for an equal three-way split, which is correct and visible. The activity feed shows the change and notifies the participants, and the history can explain every number. If the product wanted to lock expenses after settlement, that's a rule on the edit command, not a change to the ledger.

🧠 Key takeaways

  • Money in integer cents; every split's shares sum exactly to the total.
  • Split rules are strategies behind a sealed interface; equal, share and percentage splits share one largest-remainder apportioner.
  • An append-only ledger is the source of truth; net balances are a derived cache that sums to zero.
  • Greedy largest-debtor-to-largest-creditor settles a group in at most n − 1 transfers; the true minimum is NP-hard.
  • Edits and deletions append reversals, keeping history auditable.
  • A group is the aggregate; multi-currency keeps original amounts and converts only at settlement.

Check your understanding

Split $10.00 equally among three people. Which result is correct?

1,000 cents ÷ 3 = 333 remainder 1. One participant gets the extra cent, so the shares sum to exactly $10.00.

Why store an append-only ledger instead of just updating balances?

Derived balances are a cache. The ledger answers “why do I owe this?” and allows consistency checks.

What must the net balances of a group always sum to?

Each expense credits the payer the total and debits participants the same total. Settlements move money between two people.

How many transfers does the greedy simplification need, at most, for n people?

Each transfer brings at least one person to zero, and the last person is zeroed automatically.

Which design makes split rules easiest to extend?

New rules (by income, by nights stayed) are new strategies; the ledger and balances don't change.
