Convolutions in Depth

A convolutional layer is P5’s sliding kernel with three changes: it learns its weights, it reads every input channel at once, and it has many kernels, one per output channel. Four numbers then decide its geometry, kernel size, stride, padding and dilation, and two formulas decide nearly everything else: the size of its output and the region of the input each output can see.

This chapter writes the layer from scratch two ways, checks both against F.conv2d to 10⁻¹⁴, verifies the output-size formula on 2,000 random configurations, measures what cuDNN does that the textbook versions do not, and measures ResNet-50’s receptive field by backpropagating from a single output unit: the theoretical 427 pixels, and the much smaller region that actually matters.

Many channels in, many channels out

An input with Cin channels (3 for RGB, 64 after the first layer) is convolved with a kernel that has the same depth: a 3 × 3 kernel on 64 channels is 3 × 3 × 64 = 576 weights, and its output at each position is one number, the sum over all 576 products plus a bias. One such kernel gives one output channel. A layer with Cout output channels has Cout of them, so its weight tensor is (C_out, C_in, K, K).

conv = nn.Conv2d(64, 128, kernel_size=3, padding=1)      # weight (128, 64, 3, 3), bias (128,)
sum(p.numel() for p in conv.parameters())           # 73,856 = 128 x 64 x 9 + 128
nn.Linear(3 * 224 * 224, 128)                         # 19,267,712 parameters: a dense layer on a whole image

Those 73,856 weights are used at every position of the image. A fully connected layer from a 224 × 224 RGB image to just 128 outputs would need 19.3 million, one for every pixel-to-output pair, and would have to learn a separate edge detector for every location. Weight sharing (the same kernel everywhere) and locality (each output looks only at a small neighbourhood) are the two assumptions that make convolutions work on images; Chapter 3 measures what they buy.

Stride, padding, dilation and the output size

Stride is how far the kernel moves between outputs; stride 2 halves the height and width. Padding adds a border of zeros so the kernel can be centred on edge pixels; with K = 3 and padding 1 the output keeps the input size. Dilation spaces the kernel’s taps apart, so a 3 × 3 kernel with dilation 2 covers a 5 × 5 area with nine weights. Together:

H_out = (H_in + 2·padding − dilation·(K − 1) − 1) // stride + 1

Tested against F.conv2d on 2,000 random combinations of size (5–80), kernel (1, 3, 5, 7), stride (1–4), padding (0–3) and dilation (1–3): 0 mismatches. Two consequences to remember: with stride greater than 1 the division rounds down, so some rows at the bottom and columns at the right are never visited (a 224 input with a 3 × 3 stride-2 kernel and padding 0 gives 111, not 112); and ResNet’s stem, a 7 × 7 stride-2 convolution with padding 3, maps 224 to exactly 112.

Writing it from scratch, twice

def conv_loops(x, w, b, stride=1, pad=0, dil=1):                # x (N, C, H, W), w (O, C, K, K)
    N, C, H, W = x.shape; O, _, K, _ = w.shape
    x = F.pad(x, (pad, pad, pad, pad))
    Ho = (H + 2*pad - dil*(K - 1) - 1) // stride + 1; Wo = (W + 2*pad - dil*(K - 1) - 1) // stride + 1
    out = torch.zeros(N, O, Ho, Wo)
    for i in range(K):                                            # loop over the K*K taps, as in P5
        for j in range(K):
            patch = x[:, :, i*dil : i*dil + stride*(Ho - 1) + 1 : stride,
                            j*dil : j*dil + stride*(Wo - 1) + 1 : stride]  # (N, C, Ho, Wo): the input under this tap
            out += torch.einsum("nchw,oc->nohw", patch, w[:, :, i, j])   # mix channels with this tap's weights
    return out + b.view(1, -1, 1, 1)

def conv_im2col(x, w, b, stride=1, pad=0, dil=1):
    N, C, H, W = x.shape; O, _, K, _ = w.shape
    cols = F.unfold(x, K, dilation=dil, padding=pad, stride=stride)  # (N, C*K*K, L): every patch as a column
    out = w.view(O, -1) @ cols + b.view(1, -1, 1)                 # (N, O, L): one matrix multiply
    return out.view(N, O, Ho, Wo)

In float64, both matched F.conv2d to 1.1 × 10⁻¹⁴ or better for stride 1, stride 2, dilation 2 and stride 3. The second version is the important idea. im2col (“image to columns”) copies every K × K × C patch into one column of a matrix, after which the whole layer is a single matrix multiply between the (O, C·K²) weights and the (C·K², positions) patches. Matrix multiplies are what GPUs are fastest at, which is why convolution libraries are built on this idea, or on cleverer variants of it. The cost is memory: for a batch of 64 feature maps of 64 × 56 × 56, the input is 49 MB and its columns are 441 MB, nine times larger, one copy per kernel tap.

FLOPs, and what cuDNN does better

Each output value takes Cin · K² multiply-adds, and there are Cout · Hout · Wout outputs per image, so a layer costs 2 · K² · Cin · Cout · Hout · Wout FLOPs per image (counting a multiply-add as two). Three real layer shapes at batch 32 on the RTX 5070 Ti, median of 30 runs:

Layer (3 × 3, batch 32)GFLOPim2col (fp32)cuDNN fp32cuDNN bf16, channels-lastAchieved
64 → 64 at 56 × 56 (ResNet stage 1)7.41.048 ms0.296 ms0.105 ms70.3 TFLOPS
256 → 256 at 14 × 14 (stage 3)7.40.827 ms0.192 ms0.097 ms76.2 TFLOPS
3 → 64 at 224 × 224 (a first layer)5.52.409 ms2.102 ms0.816 ms6.8 TFLOPS

The first two layers have the same FLOPs and run near the GPU’s matrix-multiply speed in bf16. The third has almost as many FLOPs and runs ten times slower per FLOP: with only 3 input channels each output needs just 27 multiply-adds, so the layer moves a lot of memory (a 224 × 224 × 64 output per image) for little arithmetic. Early high-resolution layers are often memory-bound, which is one reason networks downsample quickly. On the CPU, both from-scratch versions took about 2.8 ms for a small layer against 0.69 ms for F.conv2d: correct, and four times slower.

Receptive fields

The receptive field of a unit is the region of the input image that can affect it. One 3 × 3 layer sees 3 × 3 pixels; two stacked see 5 × 5; and every stride multiplies the growth of all later layers. With r the receptive field and j the “jump” (the distance in input pixels between neighbouring units), each layer updates them as r ← r + (K − 1) · d · j and j ← j · stride. For torchvision’s ResNet-50 this gives 11 pixels after the stem convolution and max pool, then 35 after layer1, 91 after layer2, 267 after layer3 and 427 after layer4, with a jump of 32 (each final unit is 32 pixels from its neighbour).

Measured by backpropagating from the centre unit, the region with any gradient at all matched: 35, 91, 265 and 426 pixels (the outermost rows of layer3 had gradients below the measurement threshold). But the gradient is far from uniform. It peaks in the middle and fades towards the edges, so most of the influence comes from a much smaller area, the effective receptive field. The square holding 90% of the gradient was 19, 45, 149 and 285 pixels wide for the trained network: about two thirds of the theoretical size by layer4, and half or less earlier on. For the random network it was 27, 55, 133 and 203: training widened the effective field at the deep layers, where context matters, and narrowed it early.

🧾
Use case: dilated convolutions in segmentation

Segmentation networks need large receptive fields (to know that a grey region is road, not wall) and high-resolution outputs (to draw its edges). Striding gives the first and destroys the second. DeepLab, the segmenter run in Chapter 1, replaces the strides of ResNet’s last stages with dilated 3 × 3 convolutions, so the feature map stays at 1/8 of the input size instead of 1/32 while the receptive field still grows, and then runs several dilation rates in parallel (atrous spatial pyramid pooling) to see context at several scales. The cost is compute: a layer at 1/8 resolution has 16 times the positions of the same layer at 1/32, which is why DeepLabV3 took 3–4 times as long as the classifier in Chapter 1.

⚠️
Common mistakes
  • Forgetting that the output size rounds down with stride, so feature maps are off by one where you expected a clean half.
  • Counting a convolution’s parameters as K² · C_out, forgetting the C_in depth of each kernel.
  • Assuming equal FLOPs means equal time. A 3-channel first layer ran ten times slower per FLOP than a 64-channel one.
  • Treating the theoretical receptive field as what the model uses. The effective field was a half to two thirds as wide.
  • Dilating without care: stacking the same dilation rate leaves a grid of input pixels that are never read (“gridding”).
  • Using im2col naively on large layers, and running out of memory on a nine-times-larger column matrix.

Interview drill

Explain it simply: A 224 × 224 × 3 image goes through a 7 × 7 convolution with stride 2, padding 3 and 64 filters. Give the output shape, the parameter count and the FLOPs.

How a strong answer sounds
Output size: (224 + 6 − 7) // 2 + 1 = 112, so the output is 64 × 112 × 112. Parameters: each filter is 7 × 7 × 3 = 147 weights, times 64 filters is 9,408, plus 64 biases if there are any (ResNet’s stem has none because batch norm follows, so 9,408 exactly). FLOPs: each output value is 147 multiply-adds, there are 64 × 112 × 112 = 802,816 outputs, so about 118 million multiply-adds or 236 MFLOPs per image. Then the caveat: with only 3 input channels this layer does little arithmetic per byte of output, so on a GPU it tends to be memory-bound and slower than its FLOPs suggest.

Deeper: What is the receptive field of ResNet-50’s last stage, and why does the effective receptive field matter for design?

How a strong answer sounds
Computing it layer by layer with r ← r + (K − 1)·j and j ← j·stride gives 427 pixels for torchvision’s ResNet-50, with a jump of 32. Backpropagating from one output unit confirms that 427-pixel extent, but the gradient falls off from the centre, roughly like a Gaussian, so the square containing 90% of the influence was about 285 pixels for the trained network, and much narrower at earlier stages. That matters because a unit cannot use context it barely sees: a detector that must classify a large object from one unit, or a segmenter that must tell road from wall, needs an effective field comparable to the object, not just a theoretical one. Ways to widen it include more depth or stride, dilated convolutions, large kernels (ConvNeXt uses 7 × 7 depthwise), pooling global context, or attention, which gives every unit the whole image (Chapter 19).

🧠 Key takeaways

  • A conv layer’s weights are (C_out, C_in, K, K): Conv2d(64, 128, 3) has 73,856 parameters, used at every position.
  • Output size = (H + 2p − d(K − 1) − 1) // s + 1; it matched PyTorch on 2,000 random configurations.
  • im2col turns convolution into one matrix multiply, at the cost of a K²-times-larger copy of the input (49 MB → 441 MB).
  • FLOPs = 2 K² C_in C_out H_out W_out per image; deep 3 × 3 layers reached 70–76 TFLOPS in bf16, a 3-channel first layer only 6.8.
  • ResNet-50’s receptive field grows 35, 91, 267, 427 pixels by stage; the effective field holding 90% of the gradient was 19, 45, 149, 285.

What is the output width for input 224, kernel 3, stride 2, padding 0, dilation 1?

(224 + 0 − 2 − 1) // 2 + 1 = 110 + 1 = 111. The division rounds down.

What does im2col trade for speed?

It is exact (matched F.conv2d to 10⁻¹⁴) and turns the layer into one matrix multiply, but the columns were 441 MB for a 49 MB input.

Two conv layers had the same FLOPs. Why was the 3 → 64 layer at 224 × 224 ten times slower per FLOP than the 64 → 64 layer at 56 × 56?

27 multiply-adds per output and a huge 224 × 224 × 64 output per image: arithmetic per byte is low, so memory bandwidth sets the speed (6.8 vs 70 TFLOPS).
