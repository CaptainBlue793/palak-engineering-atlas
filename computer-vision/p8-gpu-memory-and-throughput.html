GPU Memory & Throughput for Images

ResNet-50’s weights take 101 MB. Training it on a batch of 256 images took 11.2 GB. Almost all GPU memory in vision training goes to activations, the intermediate feature maps saved during the forward pass so the backward pass can use them, and they grow with every image in the batch and every pixel in each image.

This chapter measures that on an RTX 5070 Ti capped at 15 GB: peak memory for ResNet-50 at seven batch sizes and six resolutions (it follows a straight line to within a few MB), what bf16 and channels-last buy, why the fastest inference batch is not the lowest-latency one, and what an out-of-memory error looks like and how to plan around it.

  • Split training memory into weights, gradients, optimiser state and activations
  • Predict peak memory from batch size and resolution, before running out of it
  • Use bf16 autocast and channels-last, and know when each helps
  • Choose an inference batch size from latency and throughput
  • Fix an out-of-memory error with the right lever

Where the memory goes

Training memory has four parts. Weights: ResNet-50 has 25,557,032 parameters, 4 bytes each in float32, 101 MB. Gradients: one per weight, another 101 MB. Optimiser state: SGD with momentum keeps one more copy (101 MB); Adam keeps two. Together they are a fixed ~400 MB, whatever the batch. The fourth part, activations, is different: every layer’s output is saved for the backward pass, so it scales with the batch and with the image area.

m = resnet50().cuda().to(memory_format=torch.channels_last)    # 101 MiB of weights
x = torch.randn(32, 3, 224, 224, device="cuda")               # (32, 3, 224, 224): 18 MiB
with torch.autocast("cuda", torch.bfloat16):
    out = m(x)                                                  # saved for backward: +1,410 MiB
with torch.no_grad(), torch.autocast("cuda", torch.bfloat16):
    m(x)                                                        # inference: peak only +163 MiB

One forward pass of 32 images kept 1,410 MB alive for the backward pass, 14 times the weights. Without gradients (torch.no_grad(), inference) nothing is kept, and the same forward pass needed only 163 MB at its peak, because each layer’s output can be freed as soon as the next layer has used it. That asymmetry is why a GPU that can train at batch 64 can usually serve at batch 1,000.

Memory follows a straight line

Activations are proportional to batch × height × width, so peak training memory should be a fixed part plus a constant times the number of pixels in the batch. Measured with torch.cuda.max_memory_allocated() for ResNet-50 (bf16 autocast, channels-last, SGD with momentum):

bf16 and channels-last

Two settings change the picture. bf16 autocast runs convolutions and matrix multiplies in 16-bit bfloat16 while keeping weights and sensitive operations in float32 (LLMs P1 covers the format). The saved activations are 16-bit, so memory nearly halves, and the GPU’s tensor cores run at full rate. Channels-last stores a batch as N, H, W, C in memory (the tensor still reports its shape as N, C, H, W), which is the layout tensor-core convolution kernels want; without it, each convolution may transpose its input and output.

The second row is the warning: channels-last is a layout for tensor cores, and with plain fp32 convolutions on this setup it made training almost five times slower, presumably because the fastest fp32 kernels expect the default layout. Together with bf16 it was the fastest configuration by a wide margin. So: use both together, or neither, and measure on your own GPU and library versions, because which kernel wins changes with both.

Inference: latency vs throughput

Serving trades two numbers. Latency is how long one request waits; throughput is how many images per second the GPU handles. Batching raises throughput, because one large kernel uses the GPU better than many tiny ones, at the cost of each request waiting for its batch:

A single image took longer than a batch of four. At batch 1 the GPU is mostly idle between tiny kernel launches, and the convolution kernels chosen for such small shapes are not the efficient ones, so the time is set by overheads, not arithmetic. Throughput peaked at batch 64 (3,900 images a second, 14.6 times batch 1) and fell slightly at 256. A service that must answer within 10 ms per request can still batch up to about 16; Chapter 38 builds that kind of dynamic batching.

Out of memory

Batch 384 at 224 px and batch 32 at 800 px both failed with torch.OutOfMemoryError: CUDA out of memory, as the line predicted (16.7 GB and 17.7 GB against a 15 GB cap). On Windows, without a cap, the driver may instead quietly move GPU memory into system RAM and keep going many times slower, so a run that “fits” can still be badly wrong; capping the process with torch.cuda.set_per_process_memory_fraction turns that into an honest error. Use case: high-resolution segmentation on a single GPU

Medical and satellite images are often thousands of pixels on a side, and a U-Net (Chapter 17) at 2,048 × 2,048 needs roughly 84 times the activation memory of the same network at 224 × 224. Teams that train such models on one or two GPUs do not run whole images: they train on random tiles of 256 to 512 pixels, use batch sizes of 2 to 8 with gradient accumulation and GroupNorm rather than BatchNorm (Chapter 6), and at inference slide a window over the full image, overlapping tiles to avoid seams. The memory line in this chapter is what tells you the tile size before the first crash.

⚠️
Common mistakes
  • Sizing memory from the weights. ResNet-50 is 101 MB of weights and 11 GB of training at batch 256.
  • Raising the resolution “a little”: 224 to 320 doubles memory and halves throughput.
  • Running inference without torch.no_grad() (or inference_mode), so activations are kept for a backward that never happens.
  • Using channels-last with fp32 and assuming it is faster: here it was 4.7× slower.
  • Benchmarking batch 1 latency on a cold model, or reporting throughput at a batch the service will never use.
  • Letting the Windows driver spill into system RAM instead of failing, and reading the slowdown as a model problem.

Interview drill

Explain it simply: Why does training a 25-million-parameter CNN need 11 GB when its weights are only 100 MB?

How a strong answer sounds
Because the backward pass needs every layer’s output from the forward pass, so those activations are stored, and they scale with batch size times image area while the weights do not. For ResNet-50 the fixed part (weights, gradients, momentum and workspace) is a few hundred megabytes; activations add about 42 MB per 224 × 224 image in bf16. At batch 256 that is about 11 GB, which matched the 11.2 GB measured. Inference keeps none of it: the same forward pass at batch 32 peaked at 163 MB above the weights, against 1.4 GB kept when gradients were needed. So training memory is planned from batch × resolution, and the fixes for running out are the ones that shrink activations: bf16, smaller batches with accumulation, lower resolution, or checkpointing.

Deeper: You need to serve ResNet-50 with p99 latency under 10 ms at 2,000 images per second. Is one GPU like this enough?

How a strong answer sounds
Probably, with batching. At batch 1 it handles about 270 images a second, far short. At batch 16 a forward pass took 4.5 ms and the GPU handled about 3,500 images a second; at batch 64 about 3,900 but each batch took 16 ms, which breaks the latency budget on its own. So I would use dynamic batching with a maximum batch of around 16 and a short wait window (a millisecond or two) to fill it: worst-case latency is roughly the wait plus one batch time plus preprocessing and transfer, under 10 ms if decode and resize are not on the critical path. At 2,000 images a second against a capacity of about 3,500 the GPU would run near 57% utilisation, leaving headroom for bursts; I would load-test the p99, because queueing makes tail latency grow sharply as utilisation approaches 100%, and keep a second GPU for failover.

🧠 Key takeaways

  • Training memory = fixed (weights, gradients, optimiser state) + activations; for vision, activations dominate.
  • ResNet-50 peak memory was 372 MB + 42.4 MB per 224 × 224 image, a straight line that also predicted every resolution.
  • Memory scales with batch × side²: 640 px at batch 32 needed as much as 224 px at batch 256.
  • bf16 + channels-last trained 2.1× faster than fp32 at 55% of the memory; channels-last alone in fp32 was 4.7× slower.
  • Inference keeps no activations (163 MB vs 1,410 MB at batch 32); throughput peaked at batch 64, and batch 1 was slower than batch 4.
  • Cap GPU memory on Windows so an overflow is an error, not a silent slowdown; then fix it with bf16, smaller batches, lower resolution or checkpointing.

Check your understanding

What took most of the memory when training ResNet-50 at batch 256?

Weights, gradients and momentum are about 100 MB each; activations were about 42 MB per image, roughly 10.9 GB of the 11.2 GB peak.

Going from 224 × 224 to 448 × 448 at the same batch size multiplies activation memory by about…

Activations scale with height × width: (448/224)² = 4. Measured at batch 32: 1,737 MB to 5,812 MB.

Which configuration trained ResNet-50 fastest here?

1,200 images/s against 928 for bf16 alone, 576 for fp32 and 122 for fp32 with channels-last.

Why did inference at batch 64 give 14.6× the throughput of batch 1?

Per-batch overheads are paid once per batch. At batch 1 they dominate: 3.74 ms for one image, 16.4 ms for 64.

A run hits CUDA out of memory. Which fix keeps the same effective batch size?

Two half-batches with one optimiser step give the same update (for models without batch-statistics layers) at about half the activation memory.
