Geometry: Coordinates & Transforms

Resizing, cropping, rotating, flipping, warping a document flat, moving a bounding box along with its image: all of these are geometry, and all of them come down to two questions. Where does each output pixel come from in the input, and how do you compute a value there when it falls between pixels?

This chapter answers both with a 3 × 3 matrix and an interpolation rule. It builds an affine transform and a homography by hand and checks them against OpenCV to 10⁻¹¹, compares the same resize in six libraries, and measures how much rotation, scale and resolution a trained ResNet-50 can take before it stops recognising things.

  • Use pixel coordinates correctly, and know what align_corners changes
  • Write rotation, scaling, shear and translation as one 3 × 3 matrix in homogeneous coordinates
  • Compute a homography from four point pairs, and use it to flatten a photographed page
  • Choose an interpolation and antialiasing setting for resizing
  • Transform boxes along with their images, and predict how geometric changes affect a classifier

Pixel coordinates

In image coordinates the origin is the top-left corner, x runs right along a row and y runs down. Arrays are indexed img[y, x]; most geometry functions take points as (x, y) and sizes as (width, height). Because y points down, a rotation that is anticlockwise on the screen has the opposite sign from the one in a maths textbook, and every library documents which it means.

Next question: where is pixel (0, 0)? If pixels are little squares, pixel 0 covers 0 to 1 and its centre is at 0.5. If pixels are sample points, it sits at 0. Resizing depends on the answer. PyTorch exposes it as align_corners. Upsampling the row [0, 1, 2, 3] to eight values:

x = torch.tensor([[[[0., 1., 2., 3.]]]])                       # (1, 1, 1, 4)
F.interpolate(x, size=(1, 8), mode="bilinear", align_corners=False)
# [0.00, 0.25, 0.75, 1.25, 1.75, 2.25, 2.75, 3.00]   pixels are squares; edges repeat
F.interpolate(x, size=(1, 8), mode="bilinear", align_corners=True)
# [0.00, 0.43, 0.86, 1.29, 1.71, 2.14, 2.57, 3.00]   corner pixels pinned; evenly spaced

Neither is wrong, but they are different, and mixing them shifts features by up to half a pixel per resize. For a segmentation mask upsampled from 1/8 resolution that is 4 pixels of misalignment at the border. The convention (PyTorch and OpenCV both default to “pixels are squares”, align_corners=False) must match between training and use, and between an image and its labels.

Homogeneous coordinates

Rotation and scaling are linear maps, a 2 × 2 matrix times a point. Translation is not: it adds a constant. The trick that makes every transform a single matrix is to write a point (x, y) as (x, y, 1). Then translation by (tx, ty) is a 3 × 3 matrix too, and a sequence of transforms is one matrix product:

T = lambda tx, ty: np.array([[1, 0, tx], [0, 1, ty], [0, 0, 1.]])
R = np.array([[ c, s, 0],                                  # c, s = cos 30°, sin 30°; this sign makes the turn
              [-s, c, 0],                                  # anticlockwise on screen (y points down)
              [ 0, 0, 1]])
S = np.diag([0.8, 0.8, 1.])
M = T(cx, cy) @ R @ S @ T(-cx, -cy)                          # read right to left: centre at origin, scale, rotate, move back
cv2.getRotationMatrix2D((cx, cy), 30, 0.8)                # OpenCV's own: the same top two rows, max difference 7.1e-15

Both gave [[0.6928, 0.4, 9.269], [−0.4, 0.6928, 136.277]] for the 451 × 300 cat photo, and warping with either produced identical pixels. Read a composition right to left: the rightmost matrix acts first. Rotating about the image centre is “move the centre to the origin, rotate, move it back”, which is why rotating about the wrong point is a classic bug: the image swings out of the frame.

An affine transform is any matrix whose bottom row is (0, 0, 1): rotation, scale, shear, translation and flips, in any combination. It keeps straight lines straight and parallel lines parallel. That is the family used by geometric augmentation (Chapter 5).

Homographies: flattening a page

A photo of a flat page taken at an angle is not an affine change: the far edge of the page looks shorter than the near edge, so parallel lines meet. The map between two views of a plane is a homography, a general 3 × 3 matrix whose bottom row is not (0, 0, 1). It maps (x, y, 1) to (u′, v′, w), and the pixel is (u′/w, v′/w). That division is what makes the far edge shrink.

H has 8 unknowns (it is defined up to scale, so set H[2, 2] = 1), and each point pair gives two equations, so four corners determine it. Writing the equations out and solving them with an SVD (the direct linear transform):

src = [(40, 30), (420, 60), (400, 280), (60, 250)]     # page corners found in the photo
dst = [(0, 0), (399, 0), (399, 299), (0, 299)]          # where they should go: a 400 x 300 rectangle
A = []
for (x, y), (u, v) in zip(src, dst):                      # u = (h0 x + h1 y + h2) / (h6 x + h7 y + h8), same for v
    A += [[x, y, 1, 0, 0, 0, -u*x, -u*y, -u], [0, 0, 0, x, y, 1, -v*x, -v*y, -v]]
H = np.linalg.svd(np.array(A))[2][-1].reshape(3, 3)        # (3, 3): the null vector of the 8 x 9 system
H /= H[2, 2]                                              # bottom row (8e-05, -0.00048, 1): not affine
# cv2.getPerspectiveTransform(src, dst) gives the same H, max difference 7.0e-11

The point (230, 160) in the photo maps to (201.0, 148.0) on the flat page, with w = 0.942: that point was a little closer to the camera than the corners’ average, so it is shrunk by dividing by w < 1. This is the last step of every document scanner (P5’s use case) and the core of panorama stitching and of the camera geometry in Chapter 33.

Resampling: which pixel, and what value

To warp or resize, loop over the output pixels, map each one back into the input with the inverse transform, and read a value there. The point almost never lands on a pixel centre, so you interpolate. Nearest takes the closest pixel (blocky, but it never invents new values, which is what you want for label masks). Bilinear blends the four nearest, bicubic sixteen. When shrinking, one more thing matters: antialiasing. Shrinking by 4× with plain bilinear samples only a few input pixels per output pixel and ignores the rest, so fine patterns alias into false ones. Antialiased resizes average over the whole footprint first.

The libraries split into two camps: antialiased (PIL, torchvision with antialias=True, now its default) and not (OpenCV’s INTER_LINEAR, F.interpolate). They differ by almost 4 grey levels per pixel on average. A model trained on PIL-resized images and served with OpenCV-resized ones sees a small but systematic shift. For a mild downscale it barely matters: on Imagenette (320 → 232 px, 1.4×) bilinear without antialiasing scored 88.28% against 87.32% with it, the opposite of what you might expect, and within noise of bicubic (88.28%). For large downscales and for small, fine detail, it matters more. Either way, pick one and use it in both places.

Boxes move with their images

When an augmentation flips or rotates an image, every label tied to positions must get the same transform: bounding boxes, keypoints, masks. A horizontal flip of an image W pixels wide maps x to W − x, so a box (x1, y1, x2, y2) becomes (W − x2, y1, W − x1, y2): the corners swap roles. On the 451-pixel-wide cat photo, (100, 50, 220, 180) becomes (231, 50, 351, 180). A rotation is worse: the four corners of a box move to a tilted quadrilateral, and the new axis-aligned box around them is larger than the object, so detection training uses small rotations or none. torchvision’s v2 transforms apply the same transform to images, boxes and masks together when you pass them as tv_tensors, which avoids writing these by hand.

Use case: the half-pixel shift in segmentation masks

Upsampling layers in segmentation networks resize features and masks many times. Early versions of several frameworks disagreed about pixel centres, which is why PyTorch added the align_corners flag and changed its default for bilinear upsampling to False in version 0.4.0, with a warning for anyone relying on the old behaviour. Models exported from one framework to another (for example through ONNX to a mobile runtime) have shipped with masks shifted by half a pixel per upsampling stage, invisible on large objects and costly on thin ones such as lane markings, wires and text strokes. The fix is a conformance test: run the same input through both runtimes and compare outputs pixel by pixel before shipping.

⚠️
Common mistakes
  • Swapping (x, y) with (row, col), or (width, height) with (height, width).
  • Composing matrices in the wrong order: rotation about the origin instead of the image centre swings the image out of frame.
  • Using bilinear interpolation on label masks, inventing class 1.5 between classes 1 and 2. Use nearest for labels.
  • Mixing antialiased and non-antialiased resizes between training and serving.
  • Mixing align_corners settings between an image and its mask, or between frameworks.
  • Flipping or rotating an image and forgetting its boxes or keypoints. A flipped image with unflipped keypoints also needs left and right labels swapped.

Interview drill

Explain it simply: Why do vision libraries use 3 × 3 matrices for 2-D transforms?

How a strong answer sounds
Because translation is not linear in ordinary coordinates: it adds a constant, so it cannot be a 2 × 2 matrix. Writing a point as (x, y, 1), homogeneous coordinates, turns translation into a matrix product, so rotation, scale, shear, flips and translation all become 3 × 3 matrices, and any sequence of them is one matrix: multiply them together, rightmost first, and apply once. Rotating about the image centre is T(centre) · R · T(−centre). The same representation extends to perspective: a homography is a general 3 × 3 matrix whose output is divided by its third coordinate, which is what makes distant parts of a plane look smaller. One matrix per transform means you can also invert it to map output pixels back to input positions, which is how warping is actually implemented.

Deeper: A pretrained classifier is fine on your test set but poor on images from a new camera that are mostly rotated and taken from further away. What do the measurements here suggest?

How a strong answer sounds
That both are plausible causes and can be quantified. ResNet-50 on Imagenette lost under 1 point up to 20° of rotation, 4 points at 45°, and 11 points at 90°; the training data never had large rotations, so robustness falls off with angle. For scale, shrinking objects so the shorter side was 0.5 × the usual size cost 4 points, while 0.7 actually helped slightly here because less of the object was cropped away; enlarging them 2× (so the crop showed only part of the object) cost 13.5 points. Resolution matters more: images that had been downscaled to 64 px and upscaled back scored 63.8%, and 32 px 27.3%. So I would measure the new camera’s distribution of angles and object sizes, test the model on images transformed to match, and then either fix the input (rotate using EXIF or a gravity sensor, crop around the object) or fine-tune with rotation and scale augmentation matching the new range.

🧠 Key takeaways

  • Image y points down; arrays are [y, x]; sizes are often (W, H). Know which convention each call uses.
  • align_corners changes where pixel centres sit; it must match between images, masks and frameworks.
  • Homogeneous coordinates make every transform a 3 × 3 matrix; compose right to left. The hand-built matrix matched OpenCV to 7 × 10⁻¹⁵.
  • A homography from four point pairs flattens a photographed plane; divide by w to get the pixel.
  • Antialiased and plain bilinear resizes differ by about 4 grey levels per pixel; pick one for training and serving.
  • ResNet-50 lost under 1 point to 20° rotations, 11 points at 90°, and 60 points when the input had only 32 px of real resolution.

Check your understanding

Why is a point written as (x, y, 1) for geometric transforms?

With homogeneous coordinates every affine transform, translation included, is a 3 × 3 matrix, so sequences of transforms compose into one matrix.

You want to rotate an image about its centre (cx, cy). Which matrix, applied to (x, y, 1), does it?

Read right to left: move the centre to the origin, rotate, move back. It matched cv2.getRotationMatrix2D to 7 × 10⁻¹⁵.

Which interpolation should you use to resize a segmentation label mask?

Labels are categories. Blending class 1 and class 3 gives class 2, which is wrong. Nearest only ever copies existing labels.

How many point correspondences determine a homography?

H has 9 entries but is defined up to scale, so 8 unknowns; each point pair gives two equations. Four pairs (no three on a line) fix it. An affine transform needs only three.

An image 451 pixels wide is flipped left to right. What does the box (100, 50, 220, 180) become?

x maps to W − x, and the corners swap roles so that x1 < x2: (451 − 220, 50, 451 − 100, 180).
