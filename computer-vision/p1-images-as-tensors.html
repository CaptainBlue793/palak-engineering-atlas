Images as Tensors

A photo on disk is a compressed file. A network wants a block of floating-point numbers in a particular order, scaled a particular way. Everything between the two is preprocessing, and it is where most vision bugs live, because a wrongly prepared image still has the right shape, still runs, and still produces a confident answer.

This chapter follows one photo from file to tensor, then measures what eight common preprocessing mistakes do to a pretrained ResNet-50 on 3,925 real validation images. Some cost a few points. Two of them, both one-line slips, take accuracy from 87% to exactly zero.

  • Read an image’s shape, dtype and channel order, and know which library gives you which
  • Convert between HWC and CHW with permute, and know why reshape is not the same thing
  • Avoid uint8 arithmetic traps: wrap-around, failed means and averages that overflow
  • Scale and normalise pixels exactly as a model was trained, and batch them as (N, C, H, W)
  • Predict how badly each preprocessing mistake hurts, from a few points to total failure

Pixels and channels

A colour image is a grid of pixels, and each pixel is three numbers: how much red, green and blue light to show. In almost every file format each number is an unsigned 8-bit integer, uint8, from 0 (none) to 255 (full). The test photo in this chapter is scikit-image’s picture of Chelsea the cat: 300 rows, 451 columns and 3 channels, so 300 × 451 × 3 = 405,900 bytes once decoded. The same pixels as 32-bit floats take 1,623,600 bytes, four times as much, which is why images stay uint8 for as long as possible and become floats only on the GPU.

from skimage import data
img = data.chelsea()                      # numpy array (300, 451, 3) uint8: (H, W, C), RGB
print(img.shape, img.dtype, img.nbytes)    # (300, 451, 3) uint8 405900
print(img[150, 225])                       # [190 150 124]: row 150, column 225, as R, G, B

Note the indexing order: img[row, column], which is img[y, x]. Image libraries that take a size usually want (width, height), the other way round. That swap is the first of many places where an image can be silently transposed.

Three libraries, three answers

The same PNG file, read by the four loaders you will meet most often, comes back in three different arrangements. All of them are “correct”; they just disagree about channel order and layout.

PyTorch convolutions expect CHW (channels, height, width) for one image and NCHW for a batch. Files, NumPy, PIL and OpenCV all give you HWC. So every pipeline that does not use torchvision’s own decoder contains a conversion, and it is easy to get wrong.

HWC to CHW: permute, not reshape

The right conversion is permute(2, 0, 1): it moves the channel axis to the front. Like a transpose, it moves no data. It returns a view of the same memory with new strides (how many elements to step over to move one place along each axis).

t = torch.from_numpy(img)             # (300, 451, 3) uint8, shares memory with the numpy array
t.stride()                              # (1353, 3, 1): next row is 451×3 values on, next pixel 3 on
chw = t.permute(2, 0, 1)               # (3, 300, 451): a view, strides (1, 1353, 3)
chw.is_contiguous()                     # False: the values are still stored R,G,B,R,G,B,...
bad = t.reshape(3, 300, 451)          # (3, 300, 451) too, and completely wrong

reshape keeps the values in memory order and just cuts the sequence into new rows. Memory holds R, G, B, R, G, B… so the first “channel” of bad is the first third of the whole image with its three colours interleaved along each row. The shape is exactly what the model wants, nothing raises, and each channel the model sees holds a different third of the photo, squeezed three times narrower, with the colours mixed together: noise, as far as the weights can tell. On the Imagenette validation set below, that single word took ResNet-50 from 87.2% to 0.0%. The panel shows what the model received.

uint8 arithmetic bites

uint8 only holds 0 to 255, and arithmetic on it wraps around rather than saturating. Each of these ran without an error on PyTorch 2.11:

a = torch.tensor([200, 250], dtype=torch.uint8)
a + 100                                 # tensor([44, 94]): 300 and 350, minus 256
torch.tensor([10], dtype=torch.uint8) - 20   # tensor([246]): -10 wrapped
(a[:1] + torch.tensor([100], dtype=torch.uint8)) // 2   # tensor([22]), not 150: 300 wrapped to 44 before the divide
t.mean()                                # RuntimeError: mean(): could not infer output dtype.
                                        #   Input dtype must be either a floating point or complex dtype. Got: Byte
t.float().mean()                        # 115.31

The averaging bug is the dangerous one: blending two images, or brightening one, in uint8 produces bright patches turned dark (and the reverse) wherever the sum passed 255. Convert to float before doing arithmetic on pixels, and convert back with clamp(0, 255).round().to(torch.uint8) only at the end.

Scaling and normalising

A network trained on ImageNet did not see 0–255 integers. It saw each value divided by 255 and then normalised per channel: the training set’s mean subtracted and the result divided by its standard deviation, so each channel has roughly zero mean and unit spread. The torchvision ResNet-50 weights used here (IMAGENET1K_V2) state their exact recipe, and you must repeat it:

After the last step a typical image has values from −2.118 (a black pixel in the red channel: (0 − 0.485) / 0.229) to 2.64 (a white pixel in the blue channel). If those numbers are not roughly what you see when you print x.min(), x.max() just before the model, something upstream is wrong. That one print catches most of the mistakes measured below.

from torchvision.models import ResNet50_Weights
pre = ResNet50_Weights.IMAGENET1K_V2.transforms()  # the weights' own recipe, as one callable
x = pre(chw)                                      # (3, 224, 224) float32, min -2.118, max 2.64
batch = torch.stack([x, x2, x3])                 # (N, 3, 224, 224): N images in one tensor

Batches, and where to convert

Models process many images at once. A batch is a 4-D tensor (N, C, H, W), and every image in it must have the same size, which is one reason for the resize and crop. A batch of 256 images at 224 × 224 is 38.5 MB as uint8 and 154 MB as float32. Copying uint8 to the GPU and converting there moves a quarter of the bytes; data-loading chapters (P6) measure what that buys.

Three things stand out. Mistakes that keep the picture recognisable cost a few points: BGR lost 4.9, swapping height and width 10.3, skipping normalisation only 1.0 (ResNet’s first batch-norm layer absorbs much of the shift). Mistakes that change the scale of the numbers, or scramble their order, are total: 0–255 inputs and the reshape both scored 0.0%, and normalising twice 0.13%, each with the model answering one confident wrong class for nearly every image. And squashing the whole image to 224 × 224 instead of cropping did slightly better here (87.7%), because no part of the object was cut off. Preprocessing is a measured choice, not a ritual; it just has to match between training and use.

Use case: one architecture, two preprocessing contracts

Keras ships ResNet-50 weights whose preprocess_input uses the original “caffe” convention: convert RGB to BGR and subtract per-channel means on the 0–255 scale, with no division by a standard deviation. torchvision’s ResNet-50 expects RGB scaled to 0–1 and normalised by mean and std. Both are called ResNet-50, both take 224 × 224 colour inputs, and code ported from one framework to the other runs without complaint. The lesson every team learns once: the preprocessing function belongs to the weights, not to the architecture, so ship it with them and test it with a known image whose expected output you have written down.

⚠️
Common mistakes
  • Using reshape or view to go from HWC to CHW. Use permute(2, 0, 1); the shape is the same, the content is not.
  • Feeding OpenCV’s BGR arrays to a model trained on RGB. Convert once, at load time.
  • Calling .float() and forgetting to divide by 255, or dividing twice. Print min and max before the model.
  • Doing arithmetic on uint8 pixels, so sums wrap around 256.
  • Normalising in the dataset and again in a model wrapper. Exactly one place should own normalisation.
  • Mixing up (width, height) and (height, width) between PIL, OpenCV and PyTorch size arguments.
  • Converting to float32 on the CPU, then copying four times as many bytes to the GPU.

Interview drill

Explain it simply: A teammate loads images with OpenCV, converts them with torch.from_numpy(img).float().reshape(3, 224, 224), and the pretrained classifier is wrong on everything. Find every bug.

How a strong answer sounds
There are three, and the last two are each enough to break the model on their own. First, OpenCV returns BGR, so the channels need converting to RGB (alone that cost about 5 points of accuracy on ResNet-50). Second, .float() keeps the 0–255 range, but the weights expect values divided by 255 and then normalised with the ImageNet mean and std; feeding 0–255 values gave 0% because every activation is hundreds of times too large. Third, reshape does not move the channel axis: it cuts the interleaved R, G, B memory into three strips, so each channel holds a scrambled third of the image. The fix is cv2.cvtColor(img, cv2.COLOR_BGR2RGB), then torch.from_numpy(img).permute(2, 0, 1), then the weights’ own transforms. Then check it: print the tensor’s min and max (about −2.1 and 2.6) and run one known image whose top class you have written down.

Deeper: Why does forgetting to normalise cost ResNet-50 only about one point here, while forgetting to divide by 255 costs everything?

How a strong answer sounds
Skipping normalisation leaves values between 0 and 1 instead of about −2 to 2.6: a shift and a rescale by a factor of about four per channel. The first convolution is linear, so its outputs shift and scale too, but the relative pattern of edges and colours is intact, the batch-norm layer after it re-centres part of the shift, and later layers tolerate a moderate change in scale. Without the division by 255 the inputs are about 250 times too large, up to 1,136 after normalising. Every activation in the first layers is far outside anything seen in training, ReLUs that should be off are on, and the network collapses to one class: here it answered “bolo tie” with 100% for the cat. The general rule is that networks tolerate small, smooth shifts in their inputs and fail completely when inputs leave the range they were trained on by orders of magnitude, which is why a one-line range check is worth having in every pipeline.

🧠 Key takeaways

  • Decoded images are uint8 HWC; PyTorch wants float NCHW. Every pipeline converts, and every conversion is a place to go wrong silently.
  • PIL and scikit-image give RGB, OpenCV gives BGR, torchvision gives CHW. Know which one you used.
  • permute(2, 0, 1) moves the channel axis; reshape scrambles the image and took accuracy from 87.2% to 0%.
  • uint8 arithmetic wraps around: 200 + 100 is 44. Convert to float before computing with pixels.
  • Preprocessing belongs to the weights: resize, crop, ÷ 255 and the exact mean and std. Skipping ÷ 255 or normalising twice scored 0% and 0.13%.
  • Print the tensor’s min and max just before the model, and keep one known image with a known answer as a test.

Check your understanding

An image array has shape (300, 451, 3). Which call turns it into the layout a PyTorch convolution expects?

permute moves the channel axis to the front. reshape and view keep memory order and scramble the channels; permute(2, 1, 0) also swaps height and width.

What is torch.tensor([200], dtype=torch.uint8) + 100?

uint8 arithmetic wraps modulo 256: 300 − 256 = 44. It does not saturate at 255 and it does not raise.

Which library returns pixels in BGR order by default?

cv2.imread gives BGR. The pixel (150, 225) of the cat came back as [124, 150, 190] from OpenCV and [190, 150, 124] from the others.

On the Imagenette validation set, which mistake left ResNet-50’s accuracy almost unchanged?

Skipping normalisation cost about one point (87.18% to 86.22%). The other three scored 0.00%, 0.00% and 0.13%.

After the standard ImageNet preprocessing, what range of values should a batch roughly have?

Black in the red channel is (0 − 0.485) / 0.229 = −2.118 and white in the blue channel is (1 − 0.406) / 0.225 = 2.64.
