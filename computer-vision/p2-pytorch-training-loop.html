PyTorch & the Training Loop

Every model in this course, from a 30,000-parameter linear classifier to a diffusion model, is trained by the same five lines repeated thousands of times: run the model, compute a loss, clear the old gradients, compute new ones, take a step. PyTorch does the calculus; you are responsible for the order, the learning rate, and the data you feed in.

This chapter checks PyTorch’s gradients against a formula worked out by hand, builds the loop on CIFAR-10’s raw pixels, and then breaks it on purpose. Five real bugs, each one line, each run for ten epochs on this GPU: three end at exactly 10% accuracy, which on ten classes is guessing.

Autograd: gradients you don’t derive

Training needs the gradient of the loss with respect to every weight: how much the loss would change if that weight moved a little. PyTorch’s autograd records every operation applied to tensors that have requires_grad=True, building a graph from the weights to the loss. Calling loss.backward() walks that graph backwards with the chain rule and leaves each weight’s gradient in its .grad.

It is worth checking once that this is not magic. Take the simplest image classifier there is, softmax regression: flatten each 32 × 32 × 3 CIFAR-10 image to 3,072 numbers, multiply by a 3,072 × 10 weight matrix, add a bias, and apply cross-entropy. Its gradient has a known closed form: Xᵀ(p − y) / N, where p are the predicted probabilities and y the one-hot labels.

import torch, torch.nn.functional as F
torch.manual_seed(0)
x, y = prep(X_train[:256]), Y_train[:256]               # (256, 3072) normalised pixels, (256,) labels
W = (torch.randn(3072, 10, device="cuda") * 0.01).requires_grad_()
b = torch.zeros(10, device="cuda", requires_grad=True)
loss = F.cross_entropy(x @ W + b, y)                     # 2.4136; ln(10) = 2.3026 is "uniform guess"
loss.backward()                                          # fills W.grad (3072, 10) and b.grad (10,)

p = (x @ W + b).softmax(-1).detach()
by_hand = x.T @ (p - F.one_hot(y, 10).float()) / 256       # the closed form
(by_hand - W.grad).abs().max()                            # 1.49e-08: equal to float32 rounding

The two agreed to 1.5 × 10⁻⁸, which is float32 rounding. A finite difference (nudge one weight by ±0.001 and divide the change in loss by 0.002) gave −0.0577 where autograd said −0.05767. Note the first loss, 2.4136: with tiny random weights the model predicts nearly uniform probabilities, and cross-entropy of a uniform guess over 10 classes is ln 10 = 2.3026. A first loss far from ln(classes) is an early sign that something (the labels, the scale of the inputs, the initialisation) is off.

Modules, parameters and optimisers

You rarely write W and b by hand. An nn.Module owns its parameters, registers them so model.parameters() can find them, and moves them with model.to("cuda"). An optimiser holds a reference to those parameters and knows how to update them from their .grad.

import torch.nn as nn
linear = nn.Linear(3072, 10)                              # 30,730 parameters
mlp = nn.Sequential(nn.Linear(3072, 512), nn.ReLU(), nn.Linear(512, 10))   # 1,578,506
model = mlp.to("cuda")
opt = torch.optim.SGD(model.parameters(), lr=0.01, momentum=0.9)
# or: torch.optim.AdamW(model.parameters(), lr=1e-3)

SGD with momentum keeps a running average of recent gradients and steps along it, which smooths out noisy batches. AdamW also scales each parameter’s step by a running estimate of its gradient’s size, so it is much less sensitive to the learning rate; it is the usual default for transformers. Both have a learning rate, the step size, and it is the setting that matters most.

The loop

Here is the loop every chapter uses. CIFAR-10’s 50,000 training images fit on the GPU as uint8 (150 MB), so this version indexes them there directly; P6 covers the DataLoader for datasets that do not fit.

for epoch in range(10):
    perm = torch.randperm(50_000, device="cuda")          # a new shuffled order every epoch
    for k in range(0, 50_000, 128):
        idx = perm[k:k + 128]
        logits = model(prep(X[idx]))                       # 1. forward: (128, 10) raw scores
        loss = F.cross_entropy(logits, Y[idx])           # 2. loss: a scalar
        opt.zero_grad(set_to_none=True)                   # 3. clear last step's gradients
        loss.backward()                                  # 4. backward: fill every .grad
        opt.step()                                       # 5. update the weights

zero_grad is needed because backward() adds into .grad rather than overwriting it. That is deliberate (it lets you accumulate gradients over several small batches, Chapter 4), but it means forgetting to clear them makes every step use the sum of all gradients so far.

Too small a rate wastes time; too large makes each step overshoot the minimum by more than the last, so the loss grows exponentially until it overflows to infinity and then NaN, and the model predicts one class: exactly 10%. The usable range for SGD with momentum here was narrow, roughly 0.001 to 0.01. The gap between the best MLP’s training loss (0.94) and its test accuracy (53%) is overfitting: 1.6 million parameters memorising pixels. Chapter 3 shows how a convolutional network gets far more from the same images.

The double-softmax bug deserves a note because it does not look broken. F.cross_entropy already applies log-softmax to its input. Giving it probabilities means it computes the softmax of values between 0 and 1, which can never be very confident, so the loss cannot fall far and the gradients are small. It still reached 49.7%, three points short, and a run like that can survive for months in a codebase.

Overfit one batch first

Before any long run, take one small batch and train on it alone. A working model and loop must drive the loss to nearly zero on 64 images it sees over and over. Here the MLP with AdamW reached 100% training accuracy on its 64 images by step 10 and a loss of 0.00002 by step 300. If it cannot do that, nothing about the full run will work, and you find out in seconds instead of hours. On this GPU one full epoch of the MLP took 0.28 s; on the CPU (8 threads), 0.82 s. Small models gain little from a GPU; the convolutional networks of later chapters gain far more.

🧾
Use case: PyTorch 2.0 changed what zero_grad() does

Until PyTorch 2.0, optimizer.zero_grad() filled every .grad with zeros. In 2.0 the default became set_to_none=True: the gradients are deleted instead. That saves a write over every parameter on every step and the memory of the gradients between steps, so training got slightly faster for free. It also broke code that read p.grad after zero_grad() and expected a tensor of zeros, such as hand-written gradient-norm logging, which now hit None. The behaviour of the five-line loop did not change, but anything that inspected its internals had to.

⚠️
Common mistakes
  • Forgetting zero_grad(), so gradients pile up and the run explodes.
  • Applying softmax and then cross_entropy, which expects raw logits.
  • Not shuffling, or shuffling once instead of every epoch, so batches are correlated.
  • Choosing a learning rate without trying a few, or not noticing a loss that went to NaN.
  • Reading accuracy from loss.item() calls every step, which forces a GPU sync each time; log every N steps.
  • Starting a long run without overfitting one batch and checking the first loss is near ln(number of classes).

Interview drill

Explain it simply: Your loss goes to NaN within the first hundred steps. List what you would check, in order.

How a strong answer sounds
First, the learning rate: on CIFAR-10 an MLP with SGD and momentum diverged at 0.2 within 50 steps while 0.01 trained well, so I would drop it by 10 and see. Second, the loop itself: a missing zero_grad() makes the gradients accumulate and produced the same explosion at a sensible rate. Third, the inputs and labels: print the batch’s min, max and mean (unnormalised 0–255 pixels make huge activations), check the first loss is near ln(classes), about 2.3 for ten, and check labels are in range. Fourth, the data order: batches sorted by class drove the loss to 0.01 and then to NaN. Then the numerics: a log or a division by something that can be zero, fp16 overflow. To localise it, run with torch.autograd.set_detect_anomaly(True) for a few steps, or log the gradient norm each step and stop at the first inf.

Deeper: Why does PyTorch accumulate gradients instead of overwriting them, and how would you use that deliberately?

How a strong answer sounds
Because summing is what the chain rule needs when a tensor is used in more than one place in the graph: its gradient is the sum of the contributions from each use, so autograd adds into .grad. Extending that across calls gives gradient accumulation: if a batch of 512 does not fit in memory, run four batches of 128, call backward() on each loss divided by 4, and call step() and zero_grad() only after the fourth. The update is the same as one batch of 512 (exactly, for models without batch-dependent layers such as BatchNorm), at a quarter of the activation memory. The cost of this design is the bug: forget zero_grad() and every step uses the sum of all previous gradients, which here sent the loss to 120,000 by step 50.

🧠 Key takeaways

  • loss.backward() fills each parameter’s .grad with the chain rule; it matched the hand-derived gradient to 1.5 × 10⁻⁸.
  • The loop is forward, loss, zero_grad, backward, step, every batch, with a fresh shuffle every epoch.
  • The learning rate matters most: 0.01 gave 52.6%, 0.2 and 1.0 diverged to NaN and 10%. AdamW at 1e-3 matched the best SGD.
  • Missing zero_grad, a missing step and class-sorted batches each gave 10%; double softmax quietly cost 3 points.
  • The first loss should be near ln(classes); a model must overfit one small batch before any long run (here 100% by step 10).

What should the very first training loss of a fresh 10-class classifier be, roughly?

Near-uniform predictions give cross-entropy ln 10 = 2.303. The measured first loss was 2.41.

Why does forgetting opt.zero_grad() make training blow up?

Accumulation is by design. Without clearing, steps keep growing: the loss hit 120,332 by step 50 and then NaN.

What does F.cross_entropy expect as its first argument?

It applies log-softmax itself. Passing probabilities softmaxes twice; that run reached 49.7% instead of 52.6%.

An MLP trained with SGD at lr 0.2 ends with NaN loss. What will its test accuracy on balanced 10-class data be?

NaN weights give the same prediction for every image, so it is right for exactly one class in ten: 10.00%.

Why overfit one small batch before a long run?

The MLP reached 100% on 64 images by step 10. A model that cannot memorise 64 images has a bug in the model, the loss or the loop.
