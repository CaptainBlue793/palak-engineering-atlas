The CV Interview Playbook

Computer-vision interviews mix four kinds of question: explain a concept, do some arithmetic on a network, debug a failing model, and design a system. Each has a recognisable shape, and each rewards the same habits this course has drilled: write the shapes, count before guessing, and know what was actually measured.

This chapter collects the formulas you should be able to produce on a whiteboard, gives you calculators to check yourself, and lists the debugging and design prompts that come up most, with answers built from the numbers measured in the earlier chapters. Use it with the timed mock interview room.

  • Answer concept questions with a mechanism and a number, not a slogan
  • Compute output sizes, receptive fields, parameters, FLOPs and memory quickly
  • Compute IoU and average precision by hand
  • Work through a debugging scenario in a disciplined order
  • Structure a design round from requirements to evaluation and serving

Debugging scenarios

The interviewer wants an order of operations, not a guess. A reliable order: reproduce (same images, same code path), inspect the inputs (shape, dtype, channel order, value range, orientation, the exact bytes the model receives), check the mode and the numerics (eval mode, precision, NaNs), check the data (labels, leakage, duplicates, class balance, shift), and only then the model. Each step has a cheap test.

Design rounds

Most design prompts (visual search, defect inspection, document reading, people counting, content moderation) fit one structure. Spend the first minutes on requirements, because they decide everything else: what is the output, what error matters more, what latency and hardware, how many labels exist.

🧾
Use case: a worked design answer in outline

“Count people entering a shop from a ceiling camera, on a small edge device.” Requirements: count accuracy per hour within a few percent; 10–15 fps; an edge GPU or NPU; few labels. Data: a few thousand frames from the target cameras, boxes for people, split by day and by shop so the test set is new places and lighting. Model: a small one-stage detector pretrained on COCO’s person class, fine-tuned at the camera’s resolution (Chapters 8, 15); a tracker that links boxes across frames and counts line crossings (Chapter 32). Evaluation: count error per hour on held-out shops, ID switches near the door, AP for person as a component metric. Serving: int8 quantisation checked for accuracy loss, preprocessing implemented once and shared, per-camera monitoring of detection confidence to catch lens dirt or a moved camera (Chapters 38, 39). Every choice comes with a number to check.

⚠️
Common mistakes
  • Answering with a slogan, such as “ResNets fix vanishing gradients”, without the mechanism or a number.
  • Forgetting C_in when counting a convolution’s parameters, or the rounding in the output size.
  • Choosing an architecture before stating the metric and the latency budget.
  • Proposing “more data” first in a debugging question, before checking the pipeline.
  • Quoting mAP or accuracy without the operating threshold or the base rate.
  • Ignoring preprocessing, batching and monitoring in a serving design.

Interview drill

Explain it simply: Give the output shape, parameters and FLOPs of a 3 × 3 convolution, stride 2, padding 1, from 64 to 128 channels on a 56 × 56 input.

How a strong answer sounds
Output size (56 + 2 − 2 − 1) // 2 + 1 = 28, so (128, 28, 28). Parameters 128 × 64 × 9 = 73,728, plus 128 biases if present (usually none before BatchNorm). Multiply-adds: 73,728 per output position × 784 positions ≈ 57.8 million, so about 116 MFLOPs per image. Then a sanity line: that is about 1.4% of ResNet-50’s roughly 4.1 billion multiply-adds, which sounds right for one downsampling convolution in an early stage.

Deeper: Your team’s detector has 45 mAP on the validation set but the product team says it misses too many objects. How do you reconcile those?

How a strong answer sounds
mAP averages precision over all recall levels, all classes and IoU thresholds from 0.5 to 0.95; the product sees one threshold, a few classes that matter, and probably a looser localisation requirement. So I would compute precision and recall at the deployed score threshold for the classes the product cares about, at IoU 0.5, and break errors down by object size and by scene type, since small objects usually dominate misses. Then the fixes follow from where the misses are: a lower threshold if precision has room, higher input resolution or a different feature-pyramid level for small objects, NMS settings for crowds, or more labelled data for the failing slice. And I would agree a metric with the product team that matches their need, such as recall at a fixed precision, so the two numbers stop disagreeing.

🧠 Key takeaways

  • Four question types: concept, arithmetic, debugging, design. Each has a known shape.
  • Concept answers: mechanism, a measured number, a limit.
  • Know output size, parameters, FLOPs, receptive field, ViT tokens, memory, IoU and AP by heart, and sanity-check magnitudes.
  • Debug in order: reproduce, inputs, mode and numerics, data, then the model.
  • Design from requirements and metric first, and put numbers on every step through to serving.

Check your understanding

What is the output size of a 3 × 3 convolution with stride 2 and padding 1 on a 56 × 56 input?

(56 + 2 − 2 − 1) // 2 + 1 = 27 + 1 = 28.

How many parameters does a 3 × 3 convolution from 64 to 128 channels have, without bias?

128 × 64 × 3 × 3. Forgetting the 64 input channels gives 1,152.

How many tokens does ViT-B/16 process for a 384 × 384 image?

(384/16)² = 576 patches plus the class token = 577; at 224 it is 197.

In a debugging round, what should usually come before retraining?

Pipeline bugs (channel order, normalisation, eval mode, orientation) are common, cheap to test and invisible to retraining.

What should the first minutes of a design round be spent on?

Requirements decide the model, the data and the evaluation. A design without a metric cannot be judged.
