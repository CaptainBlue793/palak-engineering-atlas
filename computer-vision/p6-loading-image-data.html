Loading Image Data Fast

A GPU that trains on 2,800 images a second needs 2,800 JPEGs a second read from disk, decoded, cropped, flipped and normalised on the CPU, and copied across. If the CPU side falls behind, the GPU sits idle and the expensive part of the machine does nothing. Image training is often limited by the input pipeline rather than by the model.

This chapter measures that pipeline on Imagenette’s 9,469 training photos: what one decode costs in four libraries and at four sizes, how throughput scales with DataLoader worker processes, and how many workers ResNet-18 and ResNet-50 need before the GPU stops waiting.

  • Write a Dataset and a DataLoader and know what each worker does
  • Estimate decode and augmentation cost per image, and how it grows with image size
  • Choose a number of workers from measurements, not folklore
  • Use pinned memory, uint8 transfers and GPU decoding where they help
  • Tell whether a training run is data-bound or compute-bound

Dataset and DataLoader

A PyTorch Dataset answers two questions: how many items there are (__len__) and what item i is (__getitem__): here, read a JPEG, decode it and apply the training transforms. A DataLoader wraps it: it shuffles indices, calls __getitem__ for a batch of them, and stacks the results into one tensor. With num_workers > 0 it starts that many separate processes, each building whole batches in parallel while the main process trains on the previous one.

from torch.utils.data import Dataset, DataLoader
import torchvision.transforms.v2 as T

TRAIN_TF = T.Compose([T.RandomResizedCrop(224, antialias=True), T.RandomHorizontalFlip(),
                      T.ToDtype(torch.float32, scale=True), T.Normalize(MEAN, STD)])

class Imagenette(Dataset):
    def __init__(self, files, tf): self.files, self.tf = files, tf     # list of (path, label)
    def __len__(self): return len(self.files)
    def __getitem__(self, i):
        path, y = self.files[i]
        img = T.functional.pil_to_tensor(Image.open(path).convert("RGB"))  # (3, H, W) uint8
        return self.tf(img), y                                    # (3, 224, 224) float32, int

if __name__ == "__main__":                                         # required on Windows and macOS: workers re-import this file
    dl = DataLoader(Imagenette(files, TRAIN_TF), batch_size=128, shuffle=True,
                    num_workers=8, pin_memory=True, persistent_workers=True, drop_last=True)
    for x, y in dl:                                                  # x: (128, 3, 224, 224) float32 in pinned memory
        x, y = x.to("cuda", non_blocking=True), y.to("cuda", non_blocking=True)

The if __name__ == "__main__" guard is not optional on Windows and macOS. Workers there start by spawning a fresh Python process that imports your script; without the guard, each worker would start its own DataLoader, and so on. persistent_workers=True keeps the workers alive between epochs instead of paying their start-up every epoch.

What one image costs

Imagenette’s training photos average 416 × 356 pixels and 27.3 KB. Timed on 400 of them, one at a time on one CPU core:

Decoding is only half the cost; the random resized crop, flip, float conversion and normalisation doubled it. And decode cost grows with the number of pixels. The same photos re-encoded at different sizes (quality 90):

A model that trains at 224 × 224 gains nothing from 1280-pixel originals except a 15× slower decode. Storing a training copy of the dataset pre-resized (a shorter side of around 256 to 320 is common for 224 training) is the single cheapest speed-up there is. PIL’s draft mode does something similar on the fly: JPEG can decode at ½, ¼ or ⅛ scale by skipping high frequencies, which is why it beat the full decode.

How many workers?

With num_workers=0 everything happens in the training process: 260 images a second, well below the 950 the per-image timing predicts, because Python overhead, collation and the training step all share one core. Each extra worker adds a core’s worth of decoding: 435 with one, 1,074 with two, 2,387 with four, 3,939 with eight and 5,077 with twelve on this 16-thread CPU. The question is not “how many is best” but “how many does this model need”. ResNet-50 consumes 969 images a second, so two workers nearly suffice; ResNet-18 consumes 2,857, so it needs eight. Beyond the GPU’s rate, more workers only use more memory and CPU.

Pinned memory made little difference in this measurement because the loader, not the copy, was the bottleneck: a 128 × 3 × 224 × 224 float batch is 77 MB, which takes a few milliseconds at PCIe speeds against 30 ms to build it. Returning uint8 is the bigger win on both ends: workers skip the float conversion and normalisation, and the batch shrinks to 19 MB.

Is my run data-bound?

A quick test: time the training step on a batch that is already on the GPU (synthetic data, or one real batch reused), then time the real loop. If the real loop is much slower, the loader is the bottleneck. Here, at 8 workers, ResNet-18 ran at 2,813 images a second against 2,857 synthetic, and spent 3.9% of its time waiting in next(it): compute-bound, as it should be. Watching nvidia-smi is a rougher version of the same test: GPU utilisation that drops in a sawtooth between steps means the GPU is starving. Fixing it is the planner’s list: more workers, cheaper transforms, uint8 batches, smaller stored images, or moving the augmentation onto the GPU (the CIFAR chapters of this course keep the whole dataset on the GPU, which removes the loader entirely).

🧾
Use case: fast ImageNet training was a data-loading problem

Public speed records for training ResNet-50 on ImageNet, from hours down to minutes on large clusters, spent much of their engineering on input, not on the model: storing the dataset pre-resized to small sizes, decoding at reduced resolution, moving decode and augmentation onto the GPU with libraries such as NVIDIA DALI, and using progressive resizing, training first on small images (cheap to decode and to compute) and only at full size at the end. At 1.28 million images per epoch, the difference between 1,000 and 5,000 images a second is the difference between 21 minutes and 4 minutes per epoch on one machine.

⚠️
Common mistakes
  • Leaving num_workers=0, so decoding and training share one core (260 images/s here).
  • Forgetting the if __name__ == "__main__" guard on Windows or macOS.
  • Training at 224 px from 1,280 px originals, paying 15× the decode cost for pixels the model never sees.
  • Normalising to float32 in the workers, then copying four times the bytes.
  • Using the same random seed in every worker for custom NumPy augmentations, so workers produce identical crops (set seeds per worker with worker_init_fn).
  • Tuning the model while the GPU is idle half the time because the loader is the bottleneck.

Interview drill

Explain it simply: Your GPU shows 40% utilisation while training an image classifier. How do you find and fix the cause?

How a strong answer sounds
First prove where the time goes: time the training step on data already on the GPU, and time how long the loop waits in next() on the loader. If synthetic steps are fast and the loop waits, it is the input pipeline. Then fix the most expensive stage: add workers (here throughput scaled from 260 images/s with none to over 5,000 with twelve); store the dataset pre-resized close to the training resolution, because decode cost grows with pixels (a 1,280 px JPEG took 15 times longer than a 320 px one); return uint8 from the workers and normalise on the GPU (3,939 to 6,357 images/s); decode with a faster library or on the GPU; and pin memory with non-blocking copies. Stop when the loader is faster than the GPU’s measured step rate. If the loader is not the problem, look at small batches, synchronisation in the loop such as loss.item() every step, or CPU-side work between steps.

Deeper: Why does the same data pipeline starve ResNet-18 but not ResNet-50?

How a strong answer sounds
Because the loader’s rate depends on the data and the CPU, while the GPU’s rate depends on the model. ResNet-18 needs about 1.8 billion multiply-adds per 224 × 224 image and ResNet-50 about 4.1 billion, plus more memory traffic, so on this GPU ResNet-18 trained at 2,857 images a second and ResNet-50 at 969. Two workers produced about 1,074 images a second: enough for ResNet-50, about 38% of what ResNet-18 can use. Smaller and faster models, lower resolutions and faster GPUs all move the bottleneck onto the input pipeline, which is why efficient architectures (Chapter 12) are often benchmarked with data already in memory, and why their real-world training speed depends on the loader.

🧠 Key takeaways

  • A Dataset returns one item; a DataLoader batches, shuffles and runs worker processes that prefetch.
  • Decode plus augmentation cost about 1 ms per Imagenette photo on one core; decode alone grows with pixel count (6.3 ms at 1,280 px).
  • Workers scale throughput almost linearly: 260 images/s with none, 3,939 with eight, 5,077 with twelve.
  • Return uint8 and normalise on the GPU: 3,939 → 6,357 images/s, and 4× smaller batches to copy.
  • Stop adding workers once the loader beats the GPU: ResNet-50 needs about 970 images/s here, ResNet-18 about 2,860.
  • Check for starvation by comparing the real loop with synthetic data on the GPU, and by timing waits on the loader.

Check your understanding

Why must DataLoader code with workers sit under if __name__ == "__main__": on Windows?

On Windows and macOS workers start by spawning, which re-imports the main module. The guard stops that import from re-running the training code.

Decoding the same photo at 1,280 px instead of 320 px took how much longer?

6.257 ms against 0.423 ms: decode cost grows roughly with the number of pixels (16 times as many here).

A loader produces 1,074 images/s and the GPU can train ResNet-18 on 2,857 images/s. Roughly how busy is the GPU?

The pipeline runs at the slower stage: 1,074 / 2,857 ≈ 0.38. The GPU waits the rest of the time.

Which change raised 8-worker throughput from 3,939 to 6,357 images/s?

The workers skip the float conversion and normalisation, and each batch is a quarter of the bytes. Pinning made little difference here.

How do you test whether training is limited by data loading?

ResNet-18 ran 2,857 images/s on synthetic data and 2,813 with the real loader, waiting 3.9% of the time: compute-bound.
