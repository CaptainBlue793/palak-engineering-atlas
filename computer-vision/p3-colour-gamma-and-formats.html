Colour Spaces, Gamma & Image Formats

“The pixel value” is less simple than it looks. The same colour can be stored as RGB, BGR, YCbCr or HSV; the stored number is not proportional to the light it represents; and the file it came from may have thrown information away, or carry an instruction to rotate it that some libraries obey and others ignore.

This chapter takes each of those in turn and measures what it does: why the average of black and white is not 128, what JPEG quality costs a ResNet-50 in accuracy on 1,963 real photos, and which of five common image loaders turn a phone photo the right way up.

  • Convert between RGB, BGR, YCbCr, HSV and greyscale, and know where each is used
  • Explain sRGB gamma, and when to do arithmetic in linear light
  • Predict what JPEG quality does to file size, PSNR and a model’s accuracy
  • Choose between JPEG and PNG for a dataset
  • Handle EXIF orientation so images arrive the right way up

One colour, five encodings

Take an orange pixel, RGB (200, 120, 40). Each colour space below describes the same colour with different axes, chosen for a different job:

SpaceThis orangeAxesUsed for
RGB(200, 120, 40)red, green, blue lightdisplays, PIL, PyTorch models
BGR(40, 120, 200)the same, reversedOpenCV’s default
YCbCr (OpenCV order Y, Cr, Cb)(135, 174, 74)brightness (luma) plus two colour differencesJPEG and video compression
HSV (OpenCV, hue 0–179)(15, 204, 200)hue angle, saturation, valuecolour thresholds, hue jitter in augmentation
Greyscale134.780.299 R + 0.587 G + 0.114 Bedge detection, document images

Two details trip people up. Greyscale is a weighted sum, not the mean: the eye is most sensitive to green, so the orange is 134.78 in torchvision’s rgb_to_grayscale but 120 as a plain average. And OpenCV stores hue as 0–179 (degrees halved, to fit in a uint8), while most other tools use 0–360 or 0–1, so a hue threshold copied between libraries silently selects the wrong colours.

import cv2, numpy as np
px = np.array([[[200, 120, 40]]], np.uint8)          # (1, 1, 3) one RGB pixel
cv2.cvtColor(px, cv2.COLOR_RGB2YCrCb)                # [[[135 174  74]]]: Y, Cr, Cb
cv2.cvtColor(px, cv2.COLOR_RGB2HSV)                  # [[[ 15 204 200]]]: hue 15 = 30 degrees

Gamma: the stored number is not the light

Image files store values in the sRGB encoding, which is deliberately non-linear: a stored 128 does not mean half the light of 255. The curve (roughly value2.2) spends more of the 256 levels on dark tones, where eyes notice steps, and fewer on bright ones. Converting 128 to linear light gives 0.2159, about a fifth of full brightness. Half the light is stored as 187.5.

def to_linear(v):                                        # sRGB 0..255 -> linear light 0..1
    c = v / 255
    return np.where(c <= 0.04045, c / 12.92, ((c + 0.055) / 1.055) ** 2.4)
to_linear(128)                                         # 0.2159
to_srgb((to_linear(0) + to_linear(255)) / 2)              # 187.5: the physically correct average of black and white

So averaging stored values is physically wrong. A one-pixel black-and-white checkerboard, shrunk to half size, should become the grey that emits half the light, 187.5. PIL’s bilinear resize and OpenCV’s area resize both gave 128.0, visibly too dark; averaging in linear light gave 187.5. Every common resize, blur and augmentation works on stored values.

Does that matter for models? Mostly not, because networks are trained and used on the same gamma-encoded values, so the convention is consistent. It matters when you do physics on pixels: compositing, exposure changes, rendering (NeRF, Chapter 34, works in linear light), and colour-accurate downscaling. The rule is: do arithmetic that models light in linear space, and leave everything else alone so it matches how the model was trained.

JPEG: what quality costs

JPEG converts RGB to YCbCr, usually halves the resolution of the two colour channels (eyes see brightness detail far better than colour detail), cuts each channel into 8 × 8 blocks, transforms each block into frequencies with a discrete cosine transform, and divides the frequencies by a quality-dependent table before rounding. The rounding is where information is lost, and it hits fine detail and colour first. Re-encoding 1,963 Imagenette validation photos (about 426 × 320) at each quality, and running the same ResNet-50 as P1 on the result:

Two surprises. First, q75 scored a higher PSNR than q95. The originals are themselves JPEGs saved at quality 75 (they average 25.4 KB, exactly the q75 size), and re-encoding with the same table re-quantises to almost the same values; 0.4% of images came back bit-identical. q95 uses a different, finer table, so it moves every coefficient a little. Second, accuracy is remarkably flat: q30, at half the size, cost 3.3 points, and only below about q15 does the model start to fail. Photos stored for training are commonly JPEG at 85–95; going lower to save disk is a measurable trade, not a free one, and training on one quality and serving another is a distribution shift (Chapter 9).

EXIF orientation: the sideways photo

A phone camera’s sensor has one fixed orientation. When you hold the phone upright, the camera usually does not rotate the pixels; it writes them as captured and adds an EXIF metadata tag, Orientation, telling viewers how to rotate them for display (6 means “rotate 90° clockwise”). Photo viewers obey it. Whether your data pipeline does depends on the function. A 426 × 320 image saved with Orientation = 6 should load as 320 wide by 426 tall:

LoaderSize loaded (W × H)Applies EXIF?

cv2.imread(p, IMREAD_COLOR | IMREAD_IGNORE_ORIENTATION)426 × 320no
torchvision.io.decode_jpeg(data)426 × 320no
decode_jpeg(data, apply_exif_orientation=True)320 × 426yes
torchvision.io.decode_image(p)426 × 320no (by default)

So a training set built with OpenCV and a service that decodes with PIL see the same phone photos at different angles, and nothing reports it. Pick one behaviour, apply it at the point of decoding, and test it with a file that has the tag. (By contrast, the three decoders agreed exactly on the pixels themselves: on 200 Imagenette JPEGs PIL, OpenCV and torchvision differed by 0.0 on average, because the versions installed here all use the same libjpeg-turbo settings. Older or differently built libraries have been known to differ by a level or two.)

Use case: the image CDN that resizes for you

Image delivery services such as an image CDN typically resize, re-encode at a chosen quality, strip EXIF and convert formats (JPEG to WebP or AVIF) on the fly, depending on the requesting device. That is excellent for page speed and a hazard for a model that scores those images: the service can change what it sends without any change to your code. A team that trains on original uploads and serves on CDN-resized q60 thumbnails has built in a shift of several points. Check what the model actually receives in production by logging a sample of the exact bytes, and evaluate on those.

⚠️
Common mistakes
  • Treating greyscale as the mean of R, G and B, or copying a hue threshold between OpenCV (0–179) and other tools (0–360).
  • Blending, exposure or physically based maths on gamma-encoded values instead of linear light.
  • Saving training data as low-quality JPEG to save space, then serving high-quality images (or the reverse).
  • Repeatedly re-encoding JPEGs through a pipeline, losing a little at every step.
  • Ignoring EXIF orientation, or applying it in training and not in serving.
  • Using PNG for photos “to be safe”: here it was 8.7 times the size of q75 JPEG for no accuracy gain.

Interview drill

Explain it simply: Users say the app’s classifier works on photos taken in landscape and fails on portrait photos. What is the likely cause?

How a strong answer sounds
EXIF orientation. Phones usually store portrait photos as landscape pixels plus an Orientation tag saying “rotate 90° to display”. If the serving code decodes with something that ignores the tag (plain PIL.Image.open, or torchvision’s decode_jpeg without apply_exif_orientation=True), the model sees the photo sideways. A sideways image cost ResNet-50 about 11 points on Imagenette (87.3% to 76.3%), and more on classes where orientation matters. I would confirm by checking the Orientation tag on failing uploads, fix it by applying the tag at decode time (ImageOps.exif_transpose), make the training pipeline do exactly the same, and add a test image with the tag set.

Deeper: Why does JPEG convert to YCbCr before compressing, and what does that imply for colour-sensitive tasks?

How a strong answer sounds
Human vision resolves fine detail in brightness much better than in colour, so JPEG separates brightness (Y) from two colour-difference channels (Cb, Cr) and usually stores the colour channels at half resolution in each direction (4:2:0 subsampling), a quarter of the samples, before the lossy DCT quantisation. Most of the saving comes almost for free to a human viewer. For a model, it means fine colour detail, such as thin coloured lines, small coloured text, or the exact colour boundary of a small object, is blurred before the model ever sees it, and colour is quantised harder than brightness at low quality. Tasks that depend on small colour features (traffic-light state at a distance, medical stain colour, product colour) should store data with less compression or no chroma subsampling, and evaluate at the compression level used in production.

🧠 Key takeaways

  • The same colour is RGB, BGR, YCbCr or HSV depending on the job; greyscale weights green most (0.587).
  • sRGB values are gamma-encoded: half the light is 187.5, not 128, and normal resizes average stored values (128 for a black-white checkerboard).
  • JPEG q75 was 25 KB per image against 220 KB for PNG at the same accuracy; quality below about 15 cost a model real accuracy (q8 75.4%, q3 42.0%).
  • Re-saving a JPEG at its original quality is almost lossless; at a different quality it loses a little more each time.
  • EXIF orientation is applied by cv2.imread and exif_transpose, ignored by Image.open and torchvision by default. A sideways photo cost 11 points.

Check your understanding

In sRGB, which stored value emits half the light of 255?

sRGB is gamma-encoded. Linear 0.5 converts to 187.5; a stored 128 is only about 0.216 of full light.

Which loader applies a JPEG’s EXIF orientation tag by default?

OpenCV rotated the 426 × 320 test file to 320 × 426. PIL needs ImageOps.exif_transpose, and torchvision needs apply_exif_orientation=True.

Re-encoding Imagenette’s own JPEGs at quality 75 gave a higher PSNR than at quality 95. Why?

The originals averaged 25.4 KB, exactly the q75 size. Re-quantising with the same table changes almost nothing; q95’s different table moves every coefficient a little.

What is the greyscale value of RGB (200, 120, 40) with the standard luma weights?

0.299 × 200 + 0.587 × 120 + 0.114 × 40 = 134.78. The plain mean is 120.

Which change cost ResNet-50 the least accuracy on Imagenette?

Mirroring cost nothing (87.32% both ways): the model was trained with horizontal flips. Rotating cost 11 points, q8 12 points, BGR 4.9.
